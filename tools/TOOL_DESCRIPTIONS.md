# tools/ Directory Overview

`tools/` holds scripts that run documentation-consistency CI checks and bulk documentation/source edits. Most were created under the `AGENTS.md` rule: "if the same operation is performed three or more times, extract it into a script and place it under `tools/`".

Naming convention: `<verb>_<target>.py`.

- `check_*`: pass/fail judgment or detection.
- `fix_*`: applies a correction.
- `generate_*`: generates output.
- `manage_*`: several subcommands for managing one kind of object.
- `rename_*`: a single specific operation.

Drift in this file itself is detected by `check_tool_descriptions_sync.py`, which cross-checks `tools/*.py` against the backticked `*.py` names mentioned here.

## CLI and Exit-Code Convention

Exit codes: `0` pass, `1` findings, `2` usage or environment error. An entry point is `main(argv: list[str] | None = None) -> int`, and the `__main__` block calls `sys.exit(main(...))`. `main(None)` must not depend on the caller's `sys.argv` unless the tool documents it. Option names that already exist and are kept: `--check`, `--json`, `--format`, `--dry-run`; unifying them is out of scope here. Explicit `return 2` exists today in `check_ci_results.py` (`gh` read failures), `manage_workitem_stage.py`, `mark_procedure_new_symbols.py`, and `classify_changes.py`; argparse-based tools already exit `2` on a usage error.

Callers do not distinguish `1` from `2`: `run_validation_gates.py` maps exit `0` to `Pass` and any other code to `Fail`, and every pre-commit hook and CI step treats any non-zero code as failure. A deviation below is recorded, not changed; changing an exit code needs a review of every caller first.

| Tool | Observed behavior | Reason | Callers reviewed |
|---|---|---|---|
| `check_docs_japanese.py` | Exits `1` when `docs/` is missing | Missing input reported as a finding; convention says `2` | `docs-japanese` pre-commit hook, `check_docs_japanese` gate: any non-zero is failure |
| `check_dependency_graph_cycles.py` | Exits `1` when the graph document or section is missing | Same | `governance-docs-consistency.yml` step: any non-zero is failure |
| `check_tool_descriptions_sync.py` | Exits `1` when `TOOL_DESCRIPTIONS.md` is missing | Same | pre-commit hook, console script `check-tool-descriptions`: any non-zero is failure |
| `check_needs_confirmation_inventory.py` | Exits `1` when the inventory document is missing; warnings never produce a non-zero exit, only ERROR findings do | Same; the warning rule is a deliberate detection mode | `governance-docs-consistency.yml` step, console script `check-needs-confirmation`: any non-zero is failure |

## Output Format Audit

Readers of the output formats of `check_adr_authority.py`, `check_adr_reference.py`, `check_adr_invariant_matrix.py`, and `check_workitem_traceability.py`, recorded before the shared reporting module is introduced:

- Callers: pre-commit runs `check_adr_invariant_matrix.py`, `check_adr_reference.py`, and `check_workitem_traceability.py --active-only` in text mode through the module form; `.github/workflows/ci.yml` runs `check_adr_authority.py` by path in text mode. No pre-commit hook, CI workflow, `run_validation_gates.py`, skill, rule, prompt, `routing.md`, or document requests `--format json` or `--format csv` from these tools.
- Importers: tests, and for `check_adr_invariant_matrix.py` a lazy import in `generate_reference_table.py` of `ADR_INDEX`, `_matrix_rows`, `_read_lines`, and `_split_row`.
- Readers outside the repository cannot be searched from here; none is known.

| Tool | JSON keys | JSON order | Other formats |
|---|---|---|---|
| `check_adr_authority.py` | `code`, `location`, `message` | sorted by code, location, message | text only otherwise |
| `check_adr_reference.py`, `check_adr_invariant_matrix.py` | `file`, `line_no`, `severity`, `message` | sorted by file, line | text only otherwise |
| `check_workitem_traceability.py` | `category`, `file`, `detail` (keys sorted alphabetically) | finding order | CSV with header `category,file,detail` |
## --format Convention and JSON Schema

A tool offers only the formats it already supports through `add_format_argument` in `_report.py`, and its default stays human-readable text; JSON and CSV are on request with `--format`. Rendering is deterministic: the same findings give the same bytes. The JSON output is a list of objects; the keys are per tool and are a contract, so a change to them is listed here first.

| Tool | Formats | JSON keys (in order) | Ordering |
|---|---|---|---|
| `check_adr_authority.py` | text, `json` | `code`, `location`, `message` | code, location, message |
| `check_adr_reference.py`, `check_adr_invariant_matrix.py` | text, `json` | `file`, `line_no`, `severity`, `message` | file, line |
| `check_workitem_traceability.py` | text, `json`, `csv` | `category`, `detail`, `file` (sorted); CSV header `category,file,detail` | finding order |

The other tools that define their own `render_json`, `render_text`, or `render_csv` are not migrated yet; each follow-up batch is a separate change.


## --dry-run Convention

`--dry-run` prints the intended change as a unified diff, writes no file, and returns the exit code the real run would return. Writers that gained it: `module_nodes.py` (`extract`), `set_execution_status.py`, `fix_procedure_new_markers.py`, `migrate_runtime_tool_calls.py`, and `generate_workitem.py` (a dry run also leaves the Plan's pass-timestamp marker unwritten); `fix_docs_section_marks.py` previews by default and accepts `--dry-run` as the explicit form, which also prints the diff (it is mutually exclusive with `--apply`).

Every tool that rewrites a repository file writes through `_atomic_write.py`: `manage_workitem_stage.py`, `manage_frontmatter.py`, `rename_doc.py`, `close_procedures_batch.py`, `fix_docstring_paths.py`, `fix_docstring_blank_line.py`, `mark_procedure_new_symbols.py`, and the six above. `git mv` moves are unchanged. `module_nodes.py extract` stages both new contents first, replaces the destination, then the source; if the source replace fails it restores the destination (or removes one it created) and exits `1`, and if the restore also fails it reports both paths because the moved code is then in both files.

## Invocation forms

Supported today, and all three must keep working for every tool:

- Module form `uv run python -m tools.<name>`: used by `.pre-commit-config.yaml`.
- Path form `uv run python tools/<name>.py`: used by CI workflows, skills, and docs; `python3 "${REPO_ROOT}/tools/manage_binaries.py"` is the path form that `deploy/deploy.sh`, `deploy/build_binaries.sh`, and `deploy/start_agent.sh` use.
- Test import `tools.<name>`.

`_tool_common.py` is used by `check_adr_preservation.py`, `check_workitem_traceability.py`, `classify_changes.py`, `manage_binaries.py`, `module_nodes.py`, `rename_doc.py`, `run_validation_gates.py`, and `scan_change_consumers.py`. A tool that lacked the guarded bootstrap (`if __package__ in (None, ""): sys.path.insert(...)`) gained it so the path form can import `tools._tool_common`; the bootstrap and the remaining local repository-root definitions of other tools are removed by follow-up work after the standard invocation form is decided by the owner (not decided yet).

### manage_workitem_stage.py subcommands

Archive moves:

- `close-issue`, `close-plan`, `close-implementation` run the archive move through `git mv` (via GitPython): `issues/` to `issues/done/`, `plans/` to `plans/done/`, `implementations/` to `implementations/done/`.
- Common preconditions (`move_to_done()`): the source file exists; the destination does not exist; the `done/` directory exists (an explicit error message is returned otherwise).
- Uncommitted changes: if `git status --porcelain` shows uncommitted changes on the source file alone (untracked, staged, or post-commit modifications all count), the tool does not refuse. It auto-commits with `git add` + `git commit` (through the real command, so pre-commit hooks apply) and then moves. Commit message: `chore: auto-commit {kind} before archival move ({filename})`. Uncommitted changes in other files are ignored and not included. There is no bypass flag (the former `--allow-uncommitted` was removed and replaced by the auto-commit).
- `--stage-only` (on every `close-*` subcommand): instead of auto-committing, only runs `git add` (no commit is created). The move is included in the subsequent commit, and pre-commit hooks run at that commit.
- Remote check: if an `origin` remote is configured, the tool fetches. If the destination path already exists on the remote-tracking branch (another session may have already archived it), the move is refused. If the fetch fails, the check is skipped and the tool continues (non-blocking).
- Lock conflicts: if `.git/index.lock` contention is detected during `git status` / `git mv`, retries up to 3 times.
- `close-issue` guard: if a Plan under `plans/` (not `plans/done/`) points to the issue with a `- **Source issue**:` line and that Plan's `Freeze status` is not `Frozen` (it is `Draft`, or the line is missing), the move is blocked. It is forced only when both `--force` and `--reason <reason>` are given. An issue with no such Plan moves as usual.
- `close-implementation` guard: if the `### Execution Status` table of the target file still has a `Pending` row, the move is blocked. It is forced only when both `--force` and `--reason <reason>` are given. If the `Status` column itself cannot be found (for example, the column was renamed), the guard would be disabled, so the tool stops with an error instead.
- The single-file `close-*` subcommands (`close-issue`, `close-plan`, `close-implementation`) only move files; they never edit file content (such as Execution Status rows). `close-batch` is the exception — it marks rows `Completed` in addition to archiving (see below).
- `close-batch`: archives every procedure of a batch identified by a plan path or a shared `YYYYMMDD-HHMMSS` timestamp prefix, marking each procedure's `### Execution Status` rows `Completed` and the owning plan's rows `Completed` (reusing `move_to_done()` for the archive move). Its `Pending` pre-check is atomic across the whole batch: if any procedure still has a `Pending` row the move is refused with nothing moved, and this runs even under `--dry-run`. It carries `--dry-run` (prints the planned moves and edits without touching files) and always stages its moves via `--stage-only` so a batch's renames land in one real commit. A second run on an already-closed batch is a no-op (exit 0); an unknown batch exits 1.

Status updates and queries:

- `set-status`: updates the Status column of every step in the `### Execution Status` table to the same value.
- `set-step-status`: updates only a specific step, selected by `--step N` or `--description "text"`.
- `--notes` (both `set-status` and `set-step-status`): appends to the Notes column (sets it directly if empty; otherwise appends separated by a space).
- `detect-stale`: detects stale In Progress/Pending work items (`--days 7` sets the threshold).
- `list`: lists work items by kind and status. `list --plan <plan path> --order` instead lists that Plan's procedures (`implementations/*.md` whose `Source plan` is the Plan, `plans/` and `plans/done/` paths match alike) grouped by Plan phase order: the first `Implementation steps` item citing the procedure's target file, then `seq`; a procedure no step cites is listed last under `Phase (unmatched)` with a stderr warning, a `Gated:` Notes prefix adds ` [gated]`, and a Plan without procedures prints `No procedures found for plan {path}`. `--order` and `--plan` must be given together (exit 2 otherwise); a missing Plan exits 1.
- `show`: displays the Execution Status table of a work item.

## Stale Detector Rules

`stale_detector.py` verifies the references in an implementation procedure against the current source.

- What it checks: line numbers, symbol names, imports, and `# Before:` blocks cited by the procedure. A single mismatch marks the procedure stale and blocks execution. The CLI returns exit code 1 if stale.
- Import references: only import statements that start at the beginning of a line are checked. Mentions inside prose are out of scope.
- `(new)` marker on symbols and imports: a backticked name or import statement followed by `(new)` is treated as something the procedure will newly create and is excluded from the existence check. A missing name without the marker is stale as before.
- `(new)` marker on the target file: a backticked path in the Target file section followed by `(new)` declares the file as newly created.
  - The existence check on the file is skipped; the parent directory must exist (if absent, `new_target_dir_missing`).
  - If the file already exists, it is reported as `new_target_exists`.
  - symbol / import / `# Before:` checks run against an empty file.
  - Line-number citations that resolve to the target file are not checked.
  - A nonexistent target without `(new)` is `source_missing` as before.
- Sibling resolution: for a `symbol_missing` or `import_missing` mismatch, the tool looks for a declaration among the other procedures of the same Plan, that is, documents in `implementations/` and `implementations/done/` (under `--source-dir`, default the current directory) whose Traceability `Source plan` has the same file name (`plans/` and `plans/done/` paths match alike).
  - Order rule: only a sibling whose `seq` (the number in `{timestamp}_{seq}_{slug}.md`) is smaller than the document's counts; the output starts with `Sibling resolution: order rule = earlier`. `--sibling-order any` makes every sibling count (`order rule = any`); `--no-siblings` skips the pass and prints no sibling lines.
  - A resolved name is removed from the mismatches and printed as `resolved from sibling: {name} declared (new) in {document}`; it does not make the procedure stale.
  - A name declared only by a later sibling stays a mismatch: its detail keeps the `Symbol '{name}' not found in source` prefix and appends the sibling and the order rule.
  - A sibling that cannot be read is skipped with a `warning:` line and never turns a clean result stale.
  - A document without a `Source plan` (or with `N/A`) prints and behaves exactly as without the pass.
- Names never reported as `symbol_missing` (when the symbol is absent from every `.py` file):
  - builtin names and dunder names;
  - lint rule codes (1-4 uppercase letters followed by 2-4 digits);
  - sibling procedure numbers (`_` followed by digits only);
  - chapter ids that match a filename prefix under `docs/`;
  - names appearing in a key position of config-type files (`config/`, `conf.d/`, `schemas/`, `deploy/`, `init.d/`, `pyproject.toml`, `tox.ini`). A mention inside a comment is not treated as a key.

## Module Docstring Checker

| File | Description |

| `check_docstrings.py` | Validates the docstring format of Python files under `scripts/`. Checks that an em-dash (U+2014) is present and that the form `scripts/<path> — description` is valid. ### Limitations of docstring-editing scripts

A script that adds or fixes docstrings by transforming source with regular expressions has these problems:

- **Line-number shift**: inserting a docstring shifts line numbers and breaks existing code.
- **UTF-8 corruption**: the byte sequence of the em-dash (U+2014) can be corrupted.
- **Mixed quoting**: `"""` and `""""""` end up mixed together.

Editing docstrings safely requires an approach based on the syntax tree from the `ast` module. The current implementation never **adds** docstrings; only **format validation** of existing docstrings is recommended.
