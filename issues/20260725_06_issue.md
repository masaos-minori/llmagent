## [cmd_workflow] Approval task ID persists across turns without validation

### Summary

`/approve` コマンド実行後、`ctx.turn.pending_approval_task_id` に承認されたタスクIDが設定される。この値は次のターンまで保持され、別の approval を承認した際に上書きされるが、その検証が行われない。

### Problem

`cmd_workflow.py:124-129` で approval 承認後に以下の処理が行われる：

```python
self._ctx.turn.pending_approval_id = None
self._ctx.workflow.approval_pending = False
self._ctx.turn.pending_approval_task_id = task_id
```

`pending_approval_task_id` は次のターンで `_init_workflow_task()` で使用される：

```python
(workflow_id, task,) = self._init_workflow_task(
    ctx, session_id, ctx.turn.pending_approval_task_id, store
)
```

しかし、この値が設定された後、ユーザーが別の approval を承認した場合、`task_id` は上書きされる。元の approval に関連するタスクが正しく復元されない可能性がある。

また、`_init_workflow_task()` で `existing_task_id` が指定された場合、`get_task_by_id()` でタスクを取得するが、取得したタスクの status が "halted" である場合でも処理が続行される。

### Affected Files

- `scripts/agent/commands/cmd_workflow.py:124-129` — `_cmd_approve()`
- `scripts/agent/commands/cmd_workflow.py:175-177` — `_cmd_reject()`
- `scripts/agent/orchestrator.py:193-197` — `_init_workflow_task()`

### Attack Scenario

1. エージェントREPLが `/approve <uuid1>` を実行し、`pending_approval_task_id` に `task_id1` が設定される
2. 次に `/approve <uuid2>` が実行され、`pending_approval_task_id` が `task_id2` に上書きされる
3. 次のターンで `task_id2` のタスクが復元されるが、`task_id1` のタスクの状態は不明

### Severity

Medium — 複数の approval が存在する場合、承認されたタスクIDが意図せずに上書きされる可能性がある。

### Mitigation

- `pending_approval_task_id` の上書き前に既存の値を確認し、警告を表示する
- approval 解決後に `pending_approval_task_id` を即時クリアする
- タスクの status チェックを追加し、halted ステータスのタスクが復元された場合はエラーを返す
