# [High] Enforce Fail-Closed Tool Preparation and Remove Runtime tool_definitions Fallbacks

## Consolidated Tasks

- H-02: Remove fail-open argument validation for unregistered tools.
- M-06: Remove runtime fallback semantics from `tool_definitions`.

## Priority

High

## Summary

Introduce a fail-closed call-preparation phase before approval and scheduling. Require every executable call to resolve through `RuntimeToolRegistry`, validate against the discovered live schema, and produce a call-level `ToolSpec`.

Remove all runtime fallback from `RuntimeToolRegistry` to `ToolConfig.tool_definitions`. Retain `tool_definitions` only for startup drift validation and test fixtures.

## Reason for Change

The current `_validate_tool_args()` behavior is fail open:

1. It attempts to find the tool in `RuntimeToolRegistry`.
2. It catches `KeyError` and continues.
3. It searches `ctx.cfg.tool.tool_definitions`.
4. It returns success-equivalent `None` when neither source contains the tool.
5. The call may continue to `RepositoryGateway` or `ToolExecutor`.

This violates the architecture in which live `/v1/tools` discovery and `RuntimeToolRegistry` are the sole runtime authority.

The static fallback is also structurally inconsistent. One code path expects OpenAI-style definitions under `function`, while the argument-validation fallback expects top-level `name` and `inputSchema` fields. A stale or differently shaped static definition can therefore be ignored, misread, or used to bypass missing live metadata.

Argument parsing and validation currently happen after approval and during execution. This permits unknown tools, malformed JSON, non-object arguments, and invalid schemas to reach approval before the system knows whether they can be executed.

Keeping `tool_definitions` as a runtime fallback also recreates multiple sources of truth. It can repair or override missing live schemas, write classifications, serialization flags, resource scopes, and enabled status. This would undermine H-01 even after `RuntimeToolRegistry` becomes the scheduling authority.

## Intent of the Change

The intent is to establish one strict execution boundary:

```text
No registered RuntimeTool
  -> no validation
  -> no approval
  -> no scheduling
  -> no backend execution
```

Every runtime decision must use the exact tool definition discovered from the live MCP server and stored in `RuntimeToolRegistry`.

`tool_definitions` remains useful as an expected startup contract and test fixture, but it must never make an unavailable or incomplete live tool executable.

Invalid calls should fail independently where practical, allowing other valid calls in the same LLM batch to continue. Errors, denials, and successful results must still be restored to the original call order.

## Required Changes

### 1. Add a preparation phase before approval

Required order:

1. Validate the outer tool-call object.
2. Read and validate the call ID.
3. Read and validate the function name.
4. Parse the `arguments` JSON exactly once.
5. Require parsed arguments to be a JSON object.
6. Require an initialized `RuntimeToolRegistry`.
7. Resolve the tool from the registry.
8. Validate arguments against `RuntimeTool.input_schema`.
9. Resolve resource scopes from the `RuntimeTool` and parsed arguments.
10. Build the call-level `ToolSpec`.
11. Send only prepared calls to approval.
12. Send only approved calls to DAG planning and execution.

### 2. Define a prepared-call representation

Use an explicit representation or an equivalent structure that avoids reparsing arguments:

```python
@dataclass(frozen=True)
class PreparedToolCall:
    call_id: str
    name: str
    args: dict[str, Any]
    spec: ToolSpec
    original_call: dict[str, Any]
```

A separate dataclass is optional if `ToolSpec` and the original call can carry the same information without duplication.

### 3. Remove the fail-open branches

Delete:

```python
except KeyError:
    pass
```

Delete the fallback loop over:

```python
ctx.cfg.tool.tool_definitions
```

Delete any final return path that treats an unknown or unvalidated tool as valid.

### 4. Use explicit preparation errors

Use distinct error types or machine-readable codes:

```text
configuration
unknown_tool
validation
schema
metadata
```

Recommended mapping:

- Registry unavailable: `configuration`
- Tool not registered: `unknown_tool`
- Invalid JSON or non-object arguments: `validation`
- Invalid or unavailable live input schema: `schema`
- Incomplete live execution metadata or failed scope resolution: `metadata`

Preparation failures occur before transport and must not affect MCP server health.

### 5. Reject incomplete live tools

A tool must not become executable when the live registry entry lacks required schema 2.0 metadata.

Do not use `tool_constants.py` or `tool_definitions` to supply:

- `inputSchema`
- `is_write`
- `requires_serial`
- resource-scope rules
- server ownership
- enabled state

A known state-changing tool with valid classification but no scope rule may use the explicitly defined conservative `global:write` behavior. Unknown write classification must not be inferred.

### 6. Handle invalid calls independently

Prefer converting each invalid call into a synthetic tool error result while allowing other prepared calls to continue.

An invalid call must not enter:

- Approval
- DAG planning
- RepositoryGateway
- ToolExecutor

Merge preparation errors, approval denials, and execution results back into original tool-call order before updating conversation history.

### 7. Reuse parsed arguments

Remove JSON parsing from the final execution function when the call has already been prepared.

Execution must use the same parsed arguments that were validated and used for scope resolution and approval.

### 8. Remove runtime DAG fallback

Delete `_build_tool_meta(tool_definitions)` and all DAG reads of `ctx.cfg.tool.tool_definitions`.

This requirement is completed by H-01 implementation but must be verified in this issue's repository-wide fallback audit.

### 9. Update ToolConfig documentation

Replace the current fallback comment with:

```python
# Compatibility-only expected tool definition list.
# Used for startup drift validation and test fixtures.
# It is not a runtime source or fallback for routing, argument validation,
# scheduling, approval, or execution.
tool_definitions: list[dict] = field(default_factory=list)
```

### 10. Keep only approved static uses

Allowed uses:

- Startup comparison against live `/v1/tools`.
- Strict startup drift validation.
- Test fixture construction.

Startup findings must not populate, repair, or extend `RuntimeToolRegistry`.

### 11. Audit all call sites

Search for:

```text
cfg.tool.tool_definitions
ToolConfig.tool_definitions
tool_definitions
```

Classify every remaining use as:

- Startup drift validation
- Test fixture
- Dead code to remove
- Prohibited runtime dependency

Document the classification in the pull request or implementation notes.

### 12. Add a regression guard

Add a test proving that a tool cannot execute when it is missing from `RuntimeToolRegistry`, even if a matching static entry exists in `tool_definitions`.

## Acceptance Criteria

- `RuntimeToolRegistry` is mandatory for runtime tool preparation.
- Unknown tools fail before approval.
- Malformed argument JSON fails before approval.
- Non-object argument JSON fails before approval.
- Runtime validation uses only `RuntimeTool.input_schema`.
- No invalid call reaches DAG planning, RepositoryGateway, or ToolExecutor.
- Parsed arguments are reused without reparsing.
- Valid calls may continue when another call in the batch is invalid.
- Errors, denials, and execution results are restored to original call order.
- Preparation errors do not update MCP server health.
- `tool_definitions` is not used for runtime validation.
- `tool_definitions` is not used for runtime DAG metadata.
- `tool_definitions` is not used to repair incomplete live metadata.
- An unregistered tool fails even when a matching static definition exists.
- Startup drift validation continues to function.
- ToolConfig no longer documents runtime fallback behavior.

## Required Tests

- Registry is unavailable.
- Tool is not registered.
- Tool exists only in `tool_definitions`.
- Arguments contain malformed JSON.
- Arguments decode to a list, string, number, boolean, or null.
- Arguments violate the live schema.
- Live input schema is invalid.
- Live execution metadata is incomplete.
- Scope resolution fails for required input.
- One invalid and one valid call appear in the same batch.
- Gateway is not called for a rejected call.
- ToolExecutor is not called for a rejected call.
- DAG construction does not read `tool_definitions`.
- Startup drift validation still reads the expected definition list.
- Test fixtures may use static definitions without affecting production execution.
