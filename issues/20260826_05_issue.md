# Integrate Deletion First, ADR, Reporting, and Completion Gates

## Objective

Complete the enhanced workflow with a deletion-first transformation rule, ADR support, consolidated reporting, and Path C completion gates.

## Reason

The workflow does not explicitly prefer removal and simplification over new abstractions. It also lacks persistent architectural decision records and final completion checks for the new analysis and Path C requirements.

## Intent

Reduce unnecessary abstraction, preserve architectural rationale, and prevent incomplete Path C work from being reported as complete.

## Tasks

### Deletion First

Extend Step 6 with this evaluation order:

1. Can the responsibility be removed?
2. Can the state or side effect be removed?
3. Can duplicate paths be consolidated?
4. Can the code be simplified?
5. Can responsibility move to an existing boundary?
6. Can logic be extracted?
7. Is a new abstraction required?

Require justification for every new class, protocol, adapter, facade, manager, service, or registry.

The justification must describe:

- the problem being solved
- why removal or simplification is insufficient
- ownership
- lifecycle
- dependency direction
- callers
- test boundary

### ADR Support

Extend Step 10 with an ADR template containing:

- Status
- Context
- Problem
- Constraints
- Options Considered
- Decision
- Consequences
- Risks
- Compatibility Impact
- Migration Strategy
- Rollback Strategy
- Validation Strategy
- Documentation Impact
- Follow-up Work

Require an ADR for Path C.

Allow an ADR for Path B when it records an important trade-off.

Use the repository ADR convention when available. Otherwise, report an ADR draft in Step 10 without inventing a new storage convention.

### Reporting

Add these Step 10 sections:

- Technical Debt Findings
- Responsibility Analysis
- Documentation Drift
- Architecture Baseline
- Architecture Before and After
- Migration and Rollback Evidence
- ADR Status

Use `None found`, `Not applicable`, `Not run`, or `Blocked` when appropriate.

### Completion Gate

For Path C, require:

- Behavior Lock completed
- Architecture Baseline completed
- approved scope unchanged
- dependency direction verified
- no new circular dependency
- ownership changes verified
- migration completed
- rollback strategy recorded or validated
- removed references absent
- documentation impact classified
- required ADR completed
- Path C validation passed
- findings separated from implemented changes

## Out of Scope

- Weakening existing behavior-preservation requirements
- Automatic architectural changes
- Automatic staging or committing
- Architecture Smell detection
- Deprecated analysis

## Acceptance Criteria

- Deletion and simplification are evaluated before abstraction.
- New abstractions require explicit justification.
- ADR rules and template are defined.
- Step 10 reports all added capabilities.
- Path C cannot be completed without its required evidence.
- Existing completion requirements remain mandatory.
