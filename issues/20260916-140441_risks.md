# Risk follow-up: Wire the new Tool Call idempotency-key header into each MCP server's own route handler

## Priority
Medium

## Context
`plans/20260916-135754_plan.md` (REQ-003/REQ-004) adds an opt-in duplicate-check
capability to `scripts/mcp_servers/dispatch.py`'s `dispatch_tool()` and extends
`scripts/mcp_servers/server.py`'s `extract_request_context()` to extract a new
idempotency-key header, but deliberately leaves wiring that header into each of
the ten MCP server route-handler files that call `dispatch_tool()` directly out
of scope. Those ten files (confirmed via `grep -rl "dispatch_tool(" scripts/mcp_servers/`)
have an inconsistent request-context pattern: six
(`scripts/mcp_servers/cicd/cicd_server.py`, `git/git_server.py`,
`shell/shell_server.py`, `github/github_server.py`,
`web_search/web_search_server.py`, `mdq/mdq_server.py`) call the shared
`extract_request_context()` helper, while at least one confirmed exception
(`scripts/mcp_servers/file/write_server.py`) defines standalone FastAPI routes
with no `request_id`/`extract_request_context` reference at all. The remaining
three (`scripts/mcp_servers/file/read_server.py`,
`scripts/mcp_servers/file/delete_server.py`,
`scripts/mcp_servers/rag_pipeline/rag_pipeline_server.py`) were not confirmed
either way during that Plan's Path B analysis. Until this follow-up lands, no
MCP server actually exercises the new duplicate-check protection end-to-end,
so the source Issue's Acceptance Criterion ("a retried side-effecting Tool
Call... does not execute the underlying operation twice") remains only
partially satisfied by the core-mechanism Plan alone.

## Risk
Without this follow-up, the idempotency-key mechanism ships but is inert: every
one of the ten MCP server route handlers keeps calling `dispatch_tool()` with
no `idempotency_key`, so the duplicate-check added by REQ-003 never actually
fires for any live server, and a retried side-effecting Tool Call (file write,
git operation, external API call) can still execute twice in production.

## Suggested resolution
Investigate each of the ten route-handler files' own request-context
extraction pattern first (confirm which follow `extract_request_context()`,
and confirm the exact current mechanism — or absence of one — in
`file/read_server.py`, `file/delete_server.py`, `file/write_server.py`, and
`rag_pipeline_server.py`), then run this repository's `issue-to-plan` skill
again on the resulting findings to produce a dedicated Plan that: (a) extracts
the new idempotency-key header consistently across all ten handlers (adding
the shared extraction call where missing), and (b) passes the extracted key
into each handler's existing `dispatch_tool(...)` call site.
