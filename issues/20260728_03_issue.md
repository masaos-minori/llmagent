# Connect MCP `/health` schema, probe model, and status interpretation

## Priority

High

## Summary

Connect the common MCP `/health` response schema with Agent-side health probing and status interpretation.

## Background

MCP servers share a common `/health` response shape produced by `make_health_response()`.

The common response includes:

- `status`
- `ready`
- `liveness`
- `restart_recommended`
- `operator_action_required`
- `dependencies`
- `details`

Agent-side health probing returns `McpHealthProbeResult`, which stores:

- reachability
- HTTP status code
- restart recommendation
- operator action requirement
- parsed body
- parse failure information

## Problem

The Agent can preserve the `/health` body, but it does not consistently interpret the common fields.

In particular:

- `dependencies` are not consistently summarized.
- `details` are not consistently summarized.
- `restart_recommended` and `operator_action_required` need clearer operator-facing meaning.
- Some status logic looks for top-level `reason` or `message`, but the common health schema does not require these fields.
- Server self-reported health and Agent-observed health can be confused.

## Implementation Intent

Treat `/health` as a structured operational interface, not just a liveness probe.

The Agent should be able to interpret and display dependency failures, readiness state, restart recommendations, and operator-action requirements in a consistent way.

## Required Changes

### 1. Add health body interpretation helpers

Add helper logic to interpret `McpHealthProbeResult.body`.

The helper should extract:

- self-reported status
- ready flag
- dependency summary
- details summary
- restart recommendation
- operator action requirement
- parse failure reason

### 2. Define health reason extraction

Use this priority order:

1. `body.reason`
2. `body.message`
3. summary of `body.dependencies`
4. summary of `body.details`
5. `operator_action_required`
6. `restart_recommended`

This keeps backward compatibility with servers that return top-level reason or message while supporting the common schema.

### 3. Support structured dependencies

Extend dependency handling to support both legacy string values and structured dependency entries.

Legacy form:

- dependency name -> reason string

Preferred structured form:

- dependency name -> object with fields such as:
  - `status`
  - `reason`
  - `required`
  - `operator_action_required`
  - `restart_recommended`
  - `remediation`
  - `last_checked_at`

### 4. Distinguish health perspectives

Document and represent the difference between:

- server self-reported health from `/health`
- Agent observed health from `McpServerHealthRegistry`

These are related but not identical.

### 5. Surface useful status information

Make the interpreted health fields available to:

- `/mcp status`
- startup summary
- operational logs
- runbooks

## Acceptance Criteria

- `McpHealthProbeResult.body` is interpreted through a common helper.
- Health reason extraction works with the common `make_health_response()` schema.
- `dependencies` can be summarized.
- `details` can be summarized without dumping excessive JSON.
- String dependencies remain supported.
- Structured dependencies are supported.
- `restart_recommended` and `operator_action_required` produce clear status guidance.
- Server self-reported health is distinguished from Agent observed health.
- Health parse failures remain non-crashing and visible.
