Title: [BUG] EventBus consumer offset can move backwards (EVENTBUS-001)
Labels: priority/high, type/bug, area/eventbus

## Summary
`offsets.write_offset()` overwrites the on-disk offset unconditionally. A late or out-of-order ack carrying a smaller sequence rewinds the committed offset, causing a wide re-delivery (duplicate consumption) after reconnect.

## Rationale
- `write_offset()` writes the passed `seq` with no comparison against the stored value; `read_offset()` only reads it back. There is no monotonicity guard.
- Delivery is at-least-once, so occasional duplicates are acceptable by design. A backward jump is different in kind: it re-sends an already-processed range, multiplying redundant work and increasing pressure on every consumer's idempotency handling.
- Code and design docs currently disagree in spirit: the code silently allows rewind, while operators reading the docs may assume offsets only advance.

## Intent
Guarantee that a consumer's committed offset is non-decreasing, or make the "consumer must ack in ascending order" contract explicit so the behavior is a documented, intentional decision rather than a silent hazard.

## Tasks (choose one, owner decision)
- [ ] Option A (fix): in `write_offset()`, read the current offset and ignore any `seq <= current`.
- [ ] Option B (accept): keep current behavior and record it as a Known Issue, stating the consumer-side ascending-ack contract as the rationale.

## Acceptance criteria
- Option A: `write_offset()` never lowers a consumer's stored offset; a unit test drives out-of-order acks and asserts the offset does not regress.
- Option B: the behavior is documented as intentional; no silent contradiction remains between code and docs.
