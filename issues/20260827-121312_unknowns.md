# UNK-01: Confirm whether `_execute_with_stampede_protection()` should be kept or removed alongside the ToolExecutor cache

## Priority
High

## Summary
`plans/20260827-121312_plan.md` (REQ-002) proposes keeping
`ToolExecutor._execute_with_stampede_protection()` as an independent concurrency guard
after the tool-result cache is removed, based on the code evidence that it never reads
or writes the cache itself. However, `issues/done/20260825_docs_tool_cache_removal_stale_docs_issue.md`
was filed with the explicit assumption that stampede protection is removed together
with the cache ("identical concurrent calls now each hit the MCP server (stampede
protection removed)"). This contradiction must be resolved by a maintainer before
implementation of `plans/20260827-121312_plan.md` proceeds past its Phase 1.

## Background
`scripts/shared/tool_executor.py`'s `_execute_with_cache()` calls
`_execute_with_stampede_protection()` on every cache miss. The stampede-protection
method shares an inflight `asyncio.Future` per `cache_key` across concurrent callers
via a separate `self._inflight` dict — it does not read or write `self._cache` at any
point, and is invoked with a `cache_key` string that is otherwise only used for cache
lookup, not for anything stampede-protection-specific about its own logic.

This means the mechanism is structurally separable from the cache being removed by
`plans/20260827-121312_plan.md`. But `issues/done/20260825_docs_tool_cache_removal_stale_docs_issue.md`
(filed 2026-08-25, before `plans/20260827-121312_plan.md` was generated) explicitly
scoped its documentation-correction work around the assumption that stampede
protection is removed in the same change as the cache. No investigation found evidence
of *why* that assumption was made — whether it was an intentional maintainer decision
recorded elsewhere and not linked from that issue, or an unexamined carry-over from
whatever raw issue text `issues/done/20260825_docs_tool_cache_removal_stale_docs_issue.md`
was itself derived from.

## Problem
Two mutually exclusive implementation paths exist for `ToolExecutor.execute()` once
the cache is removed, and `plans/20260827-121312_plan.md` cannot proceed to its Phase
2 (Core Logic Implementation) without knowing which one is correct:

1. **Keep stampede protection** (this Plan's current default): `execute()` calls
   `_execute_with_stampede_protection()` directly for non-side-effecting tools.
   Concurrent identical calls still share one execution. This contradicts
   `issues/done/20260825_docs_tool_cache_removal_stale_docs_issue.md`'s stated
   assumption, which would then need a one-line wording correction.
2. **Remove stampede protection too** (matches the docs issue's assumption):
   `execute()` calls `_raw_execute()` directly for non-side-effecting tools, same as
   it already does for side-effecting tools. Concurrent identical calls each
   independently hit the MCP server. This removes a currently-tested
   concurrency-safety property with no cache-specific technical justification found
   during investigation — but may be the actually-intended design outcome if the
   original decision-maker considered per-call independence acceptable now that
   results are never cached anyway.

## Reason for Change
Implementing either path without confirmation risks either (a) leaving a stale
"stampede protection removed" claim in an already-approved follow-up issue's
documentation-correction plan, or (b) silently dropping a tested concurrency-safety
guarantee that a maintainer may have wanted kept. Both outcomes are avoidable with a
single explicit decision made before code changes begin.
