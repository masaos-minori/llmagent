## D-1 — ADR-008 approval scope for a state-dependent retention rule

**Summary:** `U-3` / REQ-006 remains unresolved. A state-dependent retention rule changes what
ADR-008 Decision Detail #23 defines (terminal rows past the retention). The pending entry that covers
Decision Detail #23 and the INV-09 accepted-risk wording is `AAL-026`, and its recorded scope names only
the `eventbus.sqlite` tables, so it does not cover `mcp_dedup.sqlite`.

**Evidence Missing:** `docs/00_governance/governance_03_issue-and-uncertainty-management.md` Part 5 and
`docs/10_adr/adr_02_05_008_db-six-sqlite-store-separation.md` line 392 confirm AAL-026 exists with Approver and
Date `Not recorded`, and that ADR-008 has no `## Needs Confirmation` section and only a task-level approval
with no named reviewers. What is not confirmed is whether the maintainer treats this change as inside
AAL-026's scope or as a new entry. `docs/00_governance/governance_01_documentation-policy.md` requires a
named approval record, and Part 5 states an implementer must not write approval text.

**Resolution Path:** the repository owner decides: (a) approve AAL-026 as-is and scope the plan to
terminal rows only, (b) widen AAL-026 to the dedup store and record the approval, or (c) open a new AAL
entry for the state-dependent rule. Option (b) or (c) needs an approval record with approver, date, and
scope; this phase cannot write it.

**Blocking Impact:**
- Blocking for: REQ-006, the plan's Phase 5, the ADR reference row, and the issue's move to `issues/done/`.
- Not blocking for: REQ-001 to REQ-004 (the state vocabulary mapping, the matrix tests, the metrics read,
  the health wiring), which can be specified under either outcome.

## D-2 — What counts as safety evidence: `call_attempt_history` rows

**Summary:** the issue's acceptance criterion "unresolved safety evidence is never purged by age alone"
does not say whether it covers history rows. `call_attempt_history` has no state column; the current sweep
deletes it by `recorded_epoch < cutoff` regardless of the state of the row it belongs to, and
`docs/41_db/db_03_07_mcp-dedup-and-execution-snapshot.md` documents history entries as deleted together
with the terminal row. `U-5` recorded only that history cannot be decided by the matrix; what the history
rule is remains undecided.

**Evidence Missing:** no document or test states whether history rows attached to an unresolvable row are
retained past the retention window. The nearest documented precedent is the same section's statement that
history outlives the terminal row "only within the same retention window", which is the opposite reading.

**Resolution Path:** decide one of: (a) AC applies only to state rows, and the matrix's history row states
the current state-independent rule as intentional; or (b) history rows whose parent row is unresolvable are
excluded from the sweep, which requires editing the documented rule and a test that asserts it.

**Blocking Impact:**
- Blocking for: the retention matrix definition of evidence and the matrix test written from it (Phase 1 and
  Phase 2), and for the matrix's history row.
- Not blocking for: the metrics read, the legal-hold configuration entry, and the health wiring.

## D-3 — Whether the matrix expresses reconciliation eligibility

**Summary:** the plan's Problem states that a row left `pending` is retained forever. That is not what the
code does: `scripts/shared/mcp_dedup_ledger.py::reconcile_execution` moves a stale `pending` row to
`interrupted` and appends a `reconciled` history entry, after which the sweep can purge it. Rows retained
indefinitely are only those that cannot be reconciled — attempts exhausted (`outcome_unknown`) or a row with
no external fact to reconcile against. The matrix therefore needs two branches, not one: reconcile-eligible
and not reconcile-eligible.

**Evidence Missing:** nothing states whether this plan's matrix expresses that branch or leaves it to
`issues/20261120-115845_mcpdl006_two-layer-failure-verification.md`, which this issue blocks.

**Resolution Path:** decide whether the matrix states "reconcile first, then the resulting terminal state is
purgeable" as its own row, or states only retention per state and defers the transition to mcpdl006. Then
correct the plan's Problem wording and the matrix test's expected rows.

**Blocking Impact:**
- Blocking for: the matrix rows for `pending` and the three classifications, and for the test written from
  the matrix.
- Not blocking for: the metrics module and the threshold mechanism, which report counts whatever the answer
  is.

## D-4 — Scope gap between the issue's Required Changes and the plan's In-Scope

**Summary:** the issue requires items the plan does not carry: free disk space, acquisition latency, purge
lag, busy-error counts, WAL checkpoint verification under multi-process use, store identity and fingerprint
status, operator runbooks for loss, replacement, contention, migration, capacity exhaustion and backlog,
referentially safe deletion across calls/attempts/results, requiring reconciliation completion for
side-effecting terminal calls, and redaction of status and diagnostics. The plan lists per-status counts,
growth, WAL size, lock wait, lease health, and threshold status, and puts alert delivery and automatic
action out of scope.

**Evidence Missing:** no document assigns the dropped items to another issue; `docs/23_agent/agent_10_04_operations-and-observability-validation-and-troubleshooting.md`
is the existing runbook the criteria table refers to, so runbook content is not created here. No redaction
rule for a status read exists: `scripts/shared/logger.py` redacts only registered secrets and Bearer headers
in log records, not a metrics payload.

**Resolution Path:** for each dropped item, the owner either puts it back in scope or records the issue that
carries it. Redaction is not a judgment call here: the issue's constraint already forbids raw arguments,
results, paths, and credentials in status output, so the metrics read must be counts and codes only — that
constraint is missing from the plan's Requirements and should be added as a row.

**Blocking Impact:**
- Blocking for: requirement traceability and the plan's Phase 4 rows, because the plan as written cannot
  satisfy the issue's Required Changes.
- Not blocking for: the items already in scope.

## D-5 — Threshold keys and the store-identity contract

**Summary:** the plan defines threshold keys in the `[dedup]` table with the same range contract as
`scripts/shared/mcp_dedup_config.py::_RANGES`. Whether they enter `_config_fingerprint()` is undecided. The
current contract lists exactly five keys, and `config/cicd_mcp_server.toml` states the values must stay
identical across all ten config files because the identity fingerprint gate refuses a reopen with drift.
Adding keys changes the fingerprint for existing stores, so it changes an already-confirmed behaviour.

**Evidence Missing:** no document says whether operational thresholds are part of the store identity. Store
identity is owned by `issues/20261120-115841_mcpdl002_store-identity-continuity.md`, which this issue lists
as out of scope, so the plan cannot settle it.

**Resolution Path:** decide whether threshold keys are (a) part of the fingerprint and therefore require
identical values across the ten files, or (b) excluded from the fingerprint as operator-only settings. If
(b), per-server values are impossible anyway under the existing "identical values" statement, so the
decision is also whether that statement changes.

**Blocking Impact:**
- Blocking for: REQ-007 and the `scripts/shared/mcp_dedup_config.py` row, and for the config-file inventory
  row.
- Not blocking for: the retention matrix and the metrics read itself.

## D-6 — Who evaluates the numeric thresholds

**Summary:** `docs/23_agent/agent_10_05_operations-and-observability-monitoring.md` has a `Dedup Protection
Degraded` row, but it is a list of log conditions, not numeric criteria, so the plan's claim that the table
has no criteria rows for this store is inaccurate. A numeric threshold needs something to evaluate it, and
the repository has no metric emitter, scheduler, or alert-delivery source. The plan reports threshold status
as a per-metric status field, which implies evaluation happens in the health read.

**Evidence Missing:** no component owns threshold evaluation, and no delivery channel exists for a warning
(`U-7`). Whether "fail-closed" means the health endpoint returns degraded, or the store refuses calls, is
not stated anywhere.

**Resolution Path:** decide whether the plan reports status only (no evaluation authority) or rewrites the
criteria row as a numeric evaluation performed by the health read. If evaluation authority is granted, name
the owner of the evaluation and what "fail-closed" changes.

**Blocking Impact:**
- Blocking for: REQ-005 and the criteria-table row.
- Not blocking for: the metrics module, which computes counts regardless.

## D-7 — Health wiring scope and the server count

**Summary:** the plan says "the 10 servers that have a `[dedup]` table". There are ten config files with a
`[dedup]` section and eight server modules; `file` has three config files (read, write, delete) sharing one
server module. `scripts/mcp_servers/dispatch.py` is the only module that opens the dedup store (`scripts/mcp_servers/server.py`
only loads the `[dedup]` section through `load_dedup_section`), so a server can have a `[dedup]` config
without opening the store in that process. Which servers publish the metrics read, and whether the three
`file` config files are three scopes or one, is not decided.

**Evidence Missing:** no document assigns the metrics read per server process or per config file. Three tests
assert whole-`details` equality and break when new keys appear
(`tests/mcp_servers/cicd/test_cicd_server_endpoints.py`, `tests/mcp_servers/github/test_github_server_endpoints.py`,
`tests/mcp_servers/file/test_file_health_posture.py`); the other per-server health tests assert key
membership only.

**Resolution Path:** decide the wiring scope: all eight server modules, or only the processes that open the
store through dispatch, and whether a `[dedup]` config without an open store reports an absent status or
nothing. Then correct the plan's count and the three equality tests.

**Blocking Impact:**
- Blocking for: REQ-004 and its thirteen traceability rows.
- Not blocking for: the metrics module's read logic.
