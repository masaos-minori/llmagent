# [HIGH] Establish the system security architecture and high-risk tool control model

## Priority

High

## Background

Security controls are distributed across Agent, MCP, RAG, deployment, and operations documents.

Individual controls exist, including:

- MCP allowlists
- Tool approval gates
- Production fail-closed behavior
- File-path restrictions
- Shell command restrictions
- RAG content sanitization
- Audit logging

However, there is no single system-wide security architecture.

The security boundaries for write-capable and destructive MCP tools are not consolidated into one policy.

## Reason for Change

The system can perform high-impact actions, including:

- File modification
- File deletion
- Shell execution
- Git operations
- GitHub operations
- CI/CD execution
- Database maintenance
- Workflow approval and execution

Without one trust and authorization model, an implementation AI may change one component without recognizing its impact on system-wide security.

Inconsistent tool-level controls can permit path traversal, symlink traversal, command bypass, unauthorized repository access, or execution without required approval.

## Intent

Create one security architecture that defines:

- Trust boundaries
- Protected assets
- Authentication
- Authorization
- Approval
- Audit
- Secret management
- Network exposure
- Prompt-injection boundaries
- Local and production differences
- Fail-open and fail-closed behavior

Create one common security policy for all high-risk tools, with tool-specific exceptions documented separately.

## Tasks

### System Security Architecture

1. Create a trust-boundary diagram.
2. Identify protected assets.
3. Define the threat model.
4. Identify every externally reachable API.
5. Assign authentication and authorization requirements.
6. Define:

   - Secret provisioning
   - Secret storage
   - Secret rotation
   - Secret revocation
   - Sensitive data prohibited from logs
   - Audit retention
   - Local and production behavior
   - Fail-open and fail-closed behavior
   - Prompt-injection responsibility boundaries

### High-Risk MCP Tools

7. Define a common policy for:

   - file-write
   - file-delete
   - shell
   - git
   - github
   - cicd
   - database maintenance tools

8. Define:

   - Allowed paths
   - Allowed repositories
   - Command allowlists
   - Argument validation
   - Path traversal prevention
   - Symlink traversal prevention
   - Approval requirements
   - Risk tiers
   - Audit fields
   - Production restrictions
   - Failure behavior

9. Document tool-specific exceptions.
10. Map human approval requirements to risk tiers.
11. Ensure tool documentation references the common policy.

## Acceptance Criteria

- [ ] All major processes appear in the trust-boundary diagram.
- [ ] Protected assets and threats are documented.
- [ ] Every externally reachable API has authentication and authorization requirements.
- [ ] Secret provisioning, storage, rotation, and revocation are documented.
- [ ] Sensitive fields prohibited from logs are documented.
- [ ] Audit requirements are documented.
- [ ] Prompt-injection responsibility boundaries are documented.
- [ ] Local and production behavior is clearly separated.
- [ ] Fail-open and fail-closed behavior is explicit.
- [ ] One common policy covers all high-risk MCP tools.
- [ ] Path and repository boundaries are explicit.
- [ ] Path traversal and symlink traversal are addressed.
- [ ] Command and argument restrictions are explicit.
- [ ] Approval requirements map to risk tiers.
- [ ] Tool-specific exceptions are documented.
- [ ] Audit fields are testable.
- [ ] All relevant area documents reference the security architecture.

## Validation

1. Trace an untrusted request through Agent, LLM, MCP, and the target resource.
2. Verify each trust-boundary transition has a documented control.
3. Test path traversal and symlink traversal.
4. Test command-allowlist bypass attempts.
5. Attempt an unapproved high-risk action.
6. Verify production fail-closed behavior.
7. Verify local-development behavior separately.
8. Verify secrets are not present in logs.

## Out of Scope

- Replacing the MCP protocol
- Redesigning the entire deployment network
- Implementing unrelated business-level permissions
