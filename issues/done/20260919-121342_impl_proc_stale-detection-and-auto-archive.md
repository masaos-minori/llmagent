# Implement stale detection and auto-archive for implementation procedures

## Priority
Medium

## Summary
Add stale detection to the `code-implementation` skill and automatic archiving of execution-complete procedures to prevent stale procedure accumulation and unbounded growth of `implementations/done/`.

## Background
The `implementations/*.md` directory contains file-level implementation procedures generated by `plan-to-implementation-procedure`. After execution, procedures should move to `implementations/done/`. However, two problems were identified:

1. Stale procedures persist in `implementations/` because `code-implementation` does not verify whether the referenced code changes already exist before attempting execution. Example: `implementations/20260916-232443_01_scripts_agent_orchestrator.py.md` references line numbers and symbols that were removed in commit `09091e4e` ("fix: remove dead _llm_runner/_guard code from Orchestrator").

2. Execution-complete procedures remain in `implementations/` indefinitely. Currently, archival to `implementations/done/` relies on either manual action or implicit git commit history tracking. No automated mechanism moves completed procedures.

As of 2026-09-19, `implementations/done/` has accumulated 4444 files, indicating long-term drift between execution state and archive location.

## Problem
- `code-implementation` can attempt to execute a procedure whose target code has already been modified by another process or prior execution, wasting effort and potentially causing confusion.
- Procedures that have been executed remain in `implementations/`, making it unclear which procedures are pending vs. completed without cross-referencing git history.
- `implementations/done/` grows unboundedly with no cleanup policy.

## Reason for Change
Maintainability risk: stale procedures mislead implementers into thinking work remains when it is already done. Archive drift makes auditing and cleanup difficult. Both issues compound over time as more procedures are generated and executed.

## Implementation Intent
Two independent but complementary improvements:

1. **Stale detection**: Before executing a procedure, verify that the code constructs it references (line numbers, symbol names, import paths) still exist in the current source. If they do not, mark the procedure as stale and skip execution. This prevents wasted effort and alerts operators to potential drift.

2. **Auto-archive**: After a procedure executes successfully, automatically move its source file from `implementations/` to `implementations/done/`. This ensures the archive reflects execution state rather than requiring manual intervention or git history inspection.

Both changes operate within the existing `code-implementation` skill's scope — no new infrastructure is required.

## Target Files or Areas
- `.opencode/skills/code-implementation/SKILL.md`
- `scripts/` (for stale detection logic)
- `tools/` (optional: utility for batch stale detection)
- `implementations/` and `implementations/done/` directories

## Required Changes
- Add a pre-execution stale check step to the `code-implementation` workflow:
  - For each target file row in the procedure, verify the cited line number exists and the cited symbol/content pattern matches the current source.
  - If any row fails validation, record the procedure as stale and abort execution.
  - Report which rows failed and why (missing line, mismatched content, etc.).
- Add an auto-archive post-execution step:
  - On successful execution, move the procedure file from `implementations/{timestamp}_{id}_{slug}.md` to `implementations/done/{timestamp}_{id}_{slug}.md`.
  - Preserve the same filename convention used for `issues/done/` archival.
- Document both behaviors in the `code-implementation` skill description.

## Constraints
- Stale detection must be lightweight — avoid full AST parsing; use simple regex/string matching against the cited line ranges.
- Auto-archive must not delete the procedure file until execution has fully succeeded (all steps verified).
- Neither change may alter the public contract of `code-implementation` — it must still accept the same inputs and produce the same outputs.
- Auto-archive must handle the case where the destination file already exists (collision avoidance per `rules/filename-collision.md`).

## Unresolved Questions
- Should stale detection report all failed rows at once, or stop at the first failure? (Performance vs. completeness trade-off)
- What threshold defines "stale" — any single mismatch, or a majority of mismatches?
- Should auto-archive include a rollback capability if post-archive verification fails?

## AI Implementation Instruction
Keep changes minimal: add a pre-execution validation step and a post-execution move step. Do not rewrite the existing `code-implementation` workflow. Use simple string/regex matching for stale detection — do not introduce AST parsing unless necessary. For auto-archive, reuse the same filename convention as `issues/done/` archival. Verify the destination path exists before moving. If the destination already exists, apply collision avoidance per `rules/filename-collision.md`.
