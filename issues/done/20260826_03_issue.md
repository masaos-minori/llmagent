# Add Architecture Baseline and Path C Validation

## Objective

Add the baseline and validation evidence required for Path C changes.

## Reason

Tests, linting, and type checking protect behavior but do not fully verify module ownership, dependency direction, lifecycle ownership, or structural migration.

## Intent

Make architectural changes verifiable before and after transformation without weakening the existing Behavior Lock.

## Tasks

- Extend Step 4 with an Architecture Baseline for Path C.
- Record:
  - module ownership
  - dependency direction
  - entry points
  - lifecycle ownership
  - state ownership
  - configuration dependencies
  - routing or registration
  - deployment references
- Do not start a Path C transformation if required baseline information is missing.
- Extend Step 7 with:
  - before-and-after dependency comparison
  - architecture-boundary comparison
  - ownership validation
  - migration validation
  - rollback validation
  - route, tool, or plugin registration comparison
  - configuration and deployment comparison
  - removed-symbol reference check
- Keep all existing validation requirements mandatory.
- Report unavailable validation as `Not run` or `Blocked`, not as passed.

## Out of Scope

- Replacing Behavior Lock
- Relaxing public API checks
- Relaxing exception or side-effect checks
- Changing Path A or Path B validation depth

## Acceptance Criteria

- Path C requires an Architecture Baseline.
- Baseline fields are clearly defined.
- Path C validation compares the structure before and after modification.
- Existing behavior, API, exception, and side-effect checks remain mandatory.
- Missing evidence prevents completion when required for safety.
