# `resolve_approval` does not reject approvals for halted tasks — test-fix will remove the only guard for this

## Priority

Medium

## Context

While planning the fix for `tests/agent/test_approval_task_persistence.py`
(`plans/20260804-104315_plan.md`, source requirement
`requires/done/20260804-094909_require.md`), reading `resolve_approval()`'s full body
(`scripts/agent/workflow/approval_ops.py` lines 45-67) confirmed it only checks the
*approval* row's own status (`not found` / `already resolved`) — it never queries or
checks the associated task's status. So resolving an approval for a task that has
already been marked `"halted"` (via `update_task_status(db, task_id, "halted")`)
succeeds today exactly as if the task were still `"running"`.

`tests/agent/test_approval_task_persistence.py::TestHaltedTaskStatusRejection::test_halted_task_prevents_resume`
currently asserts the opposite (`pytest.raises(RuntimeError)`) — an invented contract
that does not match `resolve_approval`'s real behavior, and therefore fails as written.
The source requirement's own instructions (and the plan built from it) direct fixing
this test by asserting the *true* outcome (no exception, approval resolves normally)
rather than adding a task-status check to `resolve_approval` itself, since production
code changes are explicitly out of scope for that document-only test-fix.

## Description

Once the test is corrected to assert the true (no-check) behavior, the codebase will
have **zero automated coverage** flagging the fact that a halted task's pending
approval can still be resolved. This may be an intentional current limitation, or it
may be a genuine product gap — the answer is not decidable from source code alone.

## Evidence

- `scripts/agent/workflow/approval_ops.py:45-67` — `resolve_approval()` body: two
  `SELECT`/`UPDATE` statements against the `approvals` table only; no reference to the
  `tasks` table or `task_id`'s current status anywhere in the function.
- `tests/agent/test_approval_task_persistence.py:154-164` —
  `test_running_task_allows_resume` already establishes, for a `"running"` task, that
  `resolve_approval` succeeds without any status check — confirming the halted-task
  case is symmetric (no differentiation by task status at all).
- `scripts/agent/commands/cmd_workflow.py` (`_cmd_approve`/`_cmd_reject`) also performs
  no halted-task check before calling `resolve_approval` — the gap is not compensated
  for at the command-handler layer either.

## Resolution Path

A maintainer needs to decide:
1. **Is halted-task rejection actually desired behavior?** If yes: file (or approve) a
   follow-up requirement to add a task-status check inside `resolve_approval` (or in the
   `_cmd_approve`/`_cmd_reject` command handlers before calling it), with its own test
   coverage restoring the guard this issue describes losing.
2. **If the current behavior is acceptable** (e.g., halting a task is meant to be an
   independent, orthogonal state that doesn't need to block approval resolution): no
   code change is needed, but the corrected test's docstring (per the plan) should stay
   as the documented characterization of this known gap, and this issue can be closed
   as "working as intended."

Either way, this decision is out of scope for the current document-only test-fix cycle
and must not be resolved by silently adding the check back into `resolve_approval`
without an explicit requirement authorizing that production-code change.

## Blocking

False — does not block the test-fix plan (`plans/20260804-104315_plan.md`), which
proceeds under option 2 above (accurate characterization) until a maintainer decides
otherwise. Flagged here so the decision isn't lost once the test stops signaling it.
