# Posture gate is bypassed by binary launchers, mcp_launcher and mdq __main__

## Priority
Medium

## Summary
Every MCP server refuses to bind when its security posture is not validated, but only inside the `if __name__ == "__main__":` block of its own module. The production entry paths do not run that block: the Nuitka launchers generated by `deploy/build_binaries.sh`, `scripts/mcp_launcher.py`, and `scripts/mcp_servers/mdq/__main__.py` all call `run_http()` directly. A server with a FAILED posture therefore starts and serves tool calls. Review severity: Medium after verification (the documented fail-closed control is not delivered by the production start path, but the Agent independently refuses to use or start with a server whose posture failed).

## Background
Each server module defines `_enforce_posture_gate()` (for example in `shell_server.py`, `git_server.py`, `mdq_server.py`) that exits with status 1 when `_security_posture.validated` is false, and calls it only from its `__main__` block before `server.run_http()`. `config/agent.toml` starts every server through `/opt/llm/bin/mcp_*` binaries. `gen_launcher()` in `deploy/build_binaries.sh` writes a launcher that does `from <module> import <Class>` and `<Class>().run_http()`, with a comment claiming it reproduces the entry's `__main__` behavior. `MCPServer.run_http()` in `scripts/mcp_servers/server.py` does not consult the posture. The request handlers (for example `/shell_run` and `/v1/call_tool` in `shell_server.py`) do not check the posture either; only `/health` reports it.

## Problem
Confirmed by code reading and by a probe (evidence label: Confirmed by repository evidence, confidence High). The gate exists in 10 server modules, is exercised by tests that call `_enforce_posture_gate()` directly (for example `tests/mcp_servers/shell/test_shell_health_posture.py`), and is skipped by the three launch paths above. Concretely, for shell-mcp with `shell_sandbox_backend = "none"`, `validate_shell_security()` returns `server.sandbox_backend: FAILED`, while `SubprocessRunner.build_argv()` returns the argv unwrapped for any backend other than `firejail`. Started through the production binary, the server would execute allowlisted commands without a sandbox instead of refusing to bind. The same bypass applies to every other FAILED posture check (for example file-write or git policy failures). `mdq/__main__.py` also documents a non-existent entry point (`python -m mcp_servers.mdq.server`).

Verification (issue-to-plan Step 2, 2026-10-23, adversarial): the bypass is confirmed, but the original High rating overstated the impact. Corrections: (1) The Agent compensates for Agent-managed servers: `collect_server_postures()` in `scripts/agent/services/mcp_health.py` reads the posture from `/health`, `allowed_server_keys()` excludes any server that is not fully green, and `_is_fatal_gate()` makes a Safety or Integrity posture failure block Agent startup regardless of `required`. A shell-mcp started by the Agent with an unsupported sandbox backend is therefore never used through the Agent. (2) What remains: the unsafe server is already bound and serving, so any holder of its Bearer token can call it directly (every subprocess server holds every token today, see the shell environment issue), and servers started outside the Agent (`mcp_launcher.py`, running a binary by hand) have no check at all. (3) The documentation states the opposite of the behavior: `docs/22_mcp/mcp_04_02_file-write-file-delete-shell.md` says a shell-mcp started independently of the Agent still refuses to bind when its posture fails; that holds only for `python -m <server module>`. (4) Tool-call handlers do not check the posture. (5) Only `server.py::MCPServer.run_http` is shared by all launch paths, and it is 12937 bytes, so a gate added there stays under the module size limit.

## Reason for Change
The posture gate is the documented fail-closed control for server startup. If it only runs for a launch mode that production does not use, a misconfiguration silently turns into a running, unsafe server, and the passing posture tests give false assurance.

## Implementation Intent
Make the gate part of the single start path that every launcher uses, so no entry point can reach `run_http()` without it. The gate belongs with the server definition, not with each launcher. Keep the test-friendly property that importing a server module never exits the process.

## Target Files or Areas
- `scripts/mcp_servers/server.py` (`MCPServer.run_http`)
- Each `*_server.py` defining `_enforce_posture_gate` (shell, git, github, cicd, web_search, rag_pipeline, mdq, file read/write/delete)
- `scripts/mcp_servers/mdq/__main__.py`
- `scripts/mcp_launcher.py`
- `deploy/build_binaries.sh` (`gen_launcher`)
- `tests/mcp_servers/`

## Required Changes
- Run the posture check from the common start path (or give each server class a hook the base `run_http()` calls) so the binary launchers, `mcp_launcher.py`, and `python -m` all enforce it.
- Fix or remove `mdq/__main__.py` so it cannot start the server without the gate, and correct its docstring.
- Remove the per-module duplication of the gate where the common path makes it redundant.
- Correct the `gen_launcher` comment so it no longer claims to reproduce `__main__` behavior it does not reproduce.

## Constraints
- Importing a server module in tests must not exit or bind a port.
- The gate must log only check ids and reason codes, never tokens or allow-list entries (existing behavior).
- Exit status for a failed posture stays 1.

## Acceptance Criteria
- Starting each server through a launcher equivalent to the generated binary launcher (`Class().run_http()`) with a FAILED posture exits with status 1 and does not bind the port.
- `mcp_launcher.py <key>` and `python -m mcp_servers.mdq` behave the same way.
- A validated posture still starts normally.
- No server module needs its own copy of the gate logic, or every copy is covered by a test that goes through `run_http()`.

## Testing Expectations
- Unit tests per server (or a parametrized test over `discover_servers()`): with a stubbed FAILED posture, `run_http()` raises `SystemExit(1)` before uvicorn is started.
- Regression test that the generated launcher text for each entry in `build_binaries.sh` reaches the gated start path (a static check of `gen_launcher` output is acceptable).
- Run `ruff`, `mypy`, `bandit`, and `pytest tests/mcp_servers tests/tools`.

## Documentation Impact
Update the MCP startup documentation to state where the posture gate is enforced and that every launch path goes through it (boundaries, failure behavior). Run the documentation checkers named in `routing.md` for any edited `docs/` file.

## Out of Scope
- Changing which checks are FAILED versus WARNING (see the empty-token issue).
- Adding posture checks to individual request handlers.
- Changing the deployment layout of `/opt/llm/bin`.

## Dependencies
- Related: the issue on empty `auth_token` fail-open servers (`mcpstart003`); fixing this gate does not by itself make that case FAILED.
- Related: the issue on import-time config loading (`mcpstart004`) touches the same server modules; apply in either order.
- No open issue under `issues/` covers these files.

## Unresolved Questions

## AI Implementation Instruction
