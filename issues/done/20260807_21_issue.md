# [High] Make RuntimeToolRegistry the Scheduling Authority and Resolve Call-Level Resource Scopes

## Consolidated Tasks

- H-01: Use `RuntimeToolRegistry` as the sole source of DAG scheduling metadata.
- H-04: Replace tool-name resource scopes with call-level resource scope resolution.

## Priority

High

## Summary

Establish one authoritative metadata path from each MCP server's `TOOL_LIST` through `/v1/tools`, `McpToolDiscoveryService`, `RuntimeTool`, `RuntimeToolRegistry`, and call-level `ToolSpec` objects.

Replace the current tool-name-based, static DAG metadata with per-call metadata keyed by tool call ID. Resolve normalized resource scopes from the actual call arguments instead of using the tool name as the default scope.

## Reason for Change

The current implementation has multiple sources of truth for the same execution properties:

- Runtime routing uses `RuntimeToolRegistry`.
- DAG scheduling rebuilds metadata from `ToolConfig.tool_definitions`.
- Write detection in the DAG path uses static tool-name sets.
- Shell serialization is handled through a separate hard-coded tool-name check.
- `RuntimeTool` already includes scheduling fields, but the scheduler does not consume them.

This split allows routing, argument validation, approval, and scheduling to disagree about whether a tool is state-changing or requires serialization.

The current metadata is also keyed by tool name. Two calls to the same tool therefore share one `ToolSpec`, even when their arguments identify different resources. For example, two `write_file` calls targeting different files cannot carry different scheduling scopes.

The current fallback scope uses the tool name for state-changing tools. This is not a resource identifier:

- `write_file(path="/data/a.txt")` and `edit_file(path="/data/a.txt")` receive different scopes even though they modify the same file.
- Two `write_file` calls for different files receive the same scope and are unnecessarily serialized.
- `move_file` cannot represent both source and destination with one scope string.
- A directory read and a write to a descendant path cannot be recognized as a conflict.

The MCP tool definitions currently provide incomplete execution metadata. Most tools do not explicitly declare `is_write`, `requires_serial`, or resource-scope rules. Missing `is_write` values are currently normalized to read-only behavior, which is unsafe for file writes, deletes, Git mutations, GitHub mutations, workflow dispatch, RAG deletion, and shell execution.

## Intent of the Change

The intent is to create a single, inspectable, fail-closed metadata flow for runtime scheduling.

After this change:

1. The MCP server owning a tool explicitly declares its execution characteristics.
2. The common `/v1/tools` endpoint publishes those characteristics without inference.
3. Discovery validates and preserves the metadata.
4. `RuntimeToolRegistry` becomes the only runtime authority for scheduling metadata.
5. Each actual tool call receives its own `ToolSpec` based on its parsed arguments.
6. Resource conflicts are calculated from real resources, not tool names.
7. Static tool-name sets and `tool_definitions` no longer influence DAG scheduling.

The first implementation should favor conservative correctness over maximum concurrency. Fine-grained locking can be introduced later after backend concurrency guarantees are verified.

## Required Changes

### 1. Define MCP Tool Schema 2.0

Update:

```python
MCP_TOOL_SCHEMA_VERSION = "2.0"
```

Every exported MCP tool must explicitly provide:

```python
{
    "is_write": False,
    "requires_serial": False,
    "resource_scope_kind": "",
    "resource_scope_keys": [],
}
```

Contract rules:

- `is_write` is required and must be a boolean.
- `requires_serial` is required and must be a boolean.
- `resource_scope_kind` is required and must be a string, including an empty string for an unscoped read-only tool.
- `resource_scope_keys` is required and must be a list of non-empty strings.
- Simple keys must exist in `inputSchema.properties`.
- Missing values must not be inferred from `tool_constants.py` or `tool_definitions`.

For this issue, `is_write=True` means the tool may modify local or external state. It includes write, delete, execute, workflow-trigger, and API-mutation operations.

### 2. Add explicit metadata to every TOOL_LIST

Use conservative initial classifications.

#### File operations

```text
read_text_file: filesystem + path, read-only
read_media_file: filesystem + path, read-only
get_file_info: filesystem + path, read-only
write_file: filesystem + path, state-changing
edit_file: filesystem + path, state-changing
create_directory: filesystem + path, state-changing
move_file: filesystem + source,destination, state-changing
delete_file: filesystem + path, state-changing
delete_directory: filesystem + path, state-changing
```

Directory listing, tree, search, and grep tools must use the confirmed root-path field from their request models.

#### Local Git

Use repository-level scope for every local Git operation:

```text
git_repo + repo_path
```

Git reads are read-only. `git_add`, `git_commit`, `git_checkout`, `git_pull`, and `git_push` are state-changing.

#### GitHub

Use repository-level scope for the initial implementation:

```text
github_repo + owner,repo
```

Do not introduce branch-, issue-, PR-, or file-level scopes until the repository-level model is tested.

#### CI/CD

Use:

```text
cicd_workflow + repo,workflow,ref
```

`trigger_workflow` is state-changing. Workflow status, run, and log retrieval are read-only.

#### RAG

Treat pipeline execution and document listing as read-only. Treat document deletion as state-changing. Use a store-level scope for deletion until storage-layer read/write concurrency is verified.

#### MDQ

Keep `index_paths` and `refresh_index` state-changing and `requires_serial=True`. Use a fixed MDQ store scope. Mark all remaining MDQ tools explicitly as read-only and non-serial.

#### Shell

Use:

```python
"is_write": True,
"requires_serial": True,
"resource_scope_kind": "process",
"resource_scope_keys": [],
```

Resolve it to a global process scope. Do not infer command effects from `cwd`, `command`, or `argv`.

#### Web search

Mark `search_web` and `browser_fetch` explicitly as read-only and non-serial with no resource scope.

### 3. Validate tool metadata before publication or during tests

Add a common tool-definition contract validator. It may execute during server startup or in mandatory tests.

The validator must reject:

- Missing or empty names.
- Invalid `inputSchema` values.
- Missing or non-boolean `is_write`.
- Missing or non-boolean `requires_serial`.
- Invalid scope kinds.
- Invalid scope-key lists.
- Scope keys that cannot be supported by the declared input schema.

The validator must not infer missing behavior.

### 4. Preserve metadata during discovery

Update `McpToolDiscoveryService` to validate and transfer:

```python
is_write
requires_serial
resource_scope_kind
resource_scope_keys
```

Do not silently normalize absent `is_write` to `False`.

Do not register incomplete schema 2.0 tools in `RuntimeToolRegistry`.

### 5. Update RuntimeTool

Replace the current static resolved-scope field:

```python
resource_scope: str
```

with scope-resolution metadata:

```python
resource_scope_kind: str
resource_scope_keys: tuple[str, ...]
```

Update documentation to state that this metadata describes how a later call resolves scheduling resources. It is not an already resolved path, repository, branch, or URL.

### 6. Update ToolSpec

Represent one actual tool call:

```python
@dataclass(frozen=True)
class ToolSpec:
    call_id: str
    name: str
    args: dict[str, Any]
    resource_scopes: tuple[str, ...] = ()
    requires_serial: bool = False
    is_write: bool = False
```

### 7. Add a shared resource-scope resolver

Add a pure shared-layer resolver, for example:

```text
shared/resource_scope.py
```

Suggested interface:

```python
def resolve_resource_scopes(
    tool: RuntimeTool,
    args: Mapping[str, Any],
) -> tuple[str, ...]:
    ...
```

The resolver must not perform authorization or import Agent configuration.

### 8. Resolve scopes conservatively

Initial scope strategy:

- Filesystem: normalized paths.
- Local Git: normalized repository path.
- GitHub: normalized `owner/repo`.
- CI/CD: normalized repository and workflow, with ref when supplied.
- RAG mutation: fixed store scope.
- MDQ mutation: fixed store scope.
- Shell: fixed global process scope.
- Unscoped read-only operation: no scope.

For a known state-changing tool with no resolved scope:

```python
resource_scopes = ("global:write",)
```

Do not use the tool name as the fallback scope.

### 9. Support multiple and hierarchical resources

`move_file` must contain both source and destination scopes.

Filesystem overlap must include ancestor and descendant relationships. For example, a directory read on `/data` conflicts with a write to `/data/a.txt`.

Read/read overlap may run concurrently. Read/write, write/read, and write/write overlap must conflict.

### 10. Generate ToolSpec per call ID

Build one `ToolSpec` for each actual call:

```python
call_specs: dict[str, ToolSpec]
```

Do not key scheduling metadata by tool name.

### 11. Remove the legacy DAG metadata path

Delete `tool_runner._build_tool_meta()` and the DAG path's dependencies on:

- `ctx.cfg.tool.tool_definitions`
- static `is_side_effect()`
- `SHELL_TOOLS`

The scheduler must fail if a call ID has no `ToolSpec`. Missing metadata must never become read-only behavior.

## Acceptance Criteria

- MCP tool schema version is `2.0`.
- Every exported tool explicitly declares `is_write` and `requires_serial`.
- Every exported tool explicitly declares scope kind and scope keys, including empty values for unscoped reads.
- Discovery rejects incomplete schema 2.0 entries.
- Metadata survives `TOOL_LIST` to `/v1/tools` to `RuntimeTool` to `ToolSpec` without loss.
- DAG scheduling metadata comes only from `RuntimeToolRegistry` derived data.
- Every scheduled call has a `ToolSpec` keyed by call ID.
- Two calls to the same tool may resolve different scopes.
- No state-changing tool uses the tool name as a scope.
- Scope-less state-changing calls resolve to `global:write`.
- `move_file` resolves both source and destination.
- Filesystem ancestor and descendant conflicts are detected.
- `_build_tool_meta()` is removed.
- DAG code no longer uses static tool-name classifications.

## Required Tests

- Contract validation for every exported tool.
- Missing `is_write` is rejected.
- Missing `requires_serial` is rejected.
- Invalid scope metadata is rejected.
- Metadata round-trip through `/v1/tools` and discovery.
- Same tool with different arguments yields different `ToolSpec` scopes.
- Different tool names targeting the same file conflict.
- Same tool name targeting different files may run concurrently.
- `move_file` source and destination conflicts.
- Directory read and descendant write conflict.
- Same and different local Git repositories.
- Same and different GitHub repositories.
- Shell resolves to a global serial process scope.
- Known state-changing tool without a scope resolves to `global:write`.
- `dry_run=true` remains conservatively state-changing for scheduling.

## Dependencies

None. This issue establishes the metadata contract required by the later fail-closed execution and DAG execution issues.

## Out of Scope

- Fine-grained GitHub branch, issue, PR, or file locking.
- Backend transaction changes.
- Authorization and allowlist enforcement.
- Symlink-security enforcement.
- HealthRegistry and circuit-breaker behavior.
- Renaming `is_write` to `has_side_effect`.
