## Orchestratorのfinallyブロックが承認待ち/停止タスクのステータスをcompletedに上書きする

### Summary

`Orchestrator._handle_workflow_engine()` の `finally` ブロックが、`WorkflowEngine` が既に正しく設定した `pending_approval` / `halted` ステータスを、単純な `error_kind is None` 判定だけで無条件に `completed` へ上書きしてしまう。承認待ち・停止タスクのDB状態が破損し、承認復元や監査ログの正確性が損なわれる。

### Problem

- `scripts/agent/workflow/workflow_engine.py:126-154` (`WorkflowEngine.run()`) は例外の種類ごとに正しくタスクステータスを管理している:
  - `WorkflowPendingApprovalError` 発生時: `_gate_approval()`(156-187行目)が事前に `update_task_status(task_id, "pending_approval")` を呼んでから例外を送出。`run()` 側は `except WorkflowPendingApprovalError: raise` のみでステータスを変更しない。
  - `(WorkflowHaltError, WorkflowTimeoutError)` 発生時: `update_task_status(task_id, "halted")` を呼んでから再送出。
  - 正常終了時: `update_task_status(task_id, "completed")`。
- しかし呼び出し元 `scripts/agent/orchestrator.py:291-307` (`Orchestrator._handle_workflow_engine()`) の `finally` ブロックは次の通り:
  ```python
  finally:
      try:
          _task = task
          if _task is not None and _task.task_id:
              if error_kind is not None:
                  store.update_task_status(_task.task_id, "failed")
              else:
                  store.update_task_status(_task.task_id, "completed")
      except Exception as e:
          logger.warning(...)
      self._deactivate_workflow(ctx)
      store.close()
  ```
  `error_kind` は `_process_turn()`(execute_fn内)でのみ設定されるローカル変数で、`WorkflowPendingApprovalError`/`WorkflowHaltError` が発生しても更新されない。両例外とも `except` 節(291-294行目)でDB更新を行わずに捕捉され、そのまま `finally` に流れ込む。
- 結果として、LLM応答が正常に返った通常のターンで承認ゲートに入った場合(`error_kind` はNoneのまま)、`finally` は無条件で `completed` を書き込み、直前に設定された `pending_approval` を上書きする。`WorkflowHaltError` 発生時も同様に `halted` が `completed` に上書きされる。

### Affected Files

- `scripts/agent/orchestrator.py` — `_handle_workflow_engine()` の `finally` ブロック(291-307行目付近)
- `scripts/agent/workflow/workflow_engine.py` — `WorkflowEngine.run()`(参照元としてステータス遷移を確認、126-154行目)
- `scripts/agent/workflow/approval_ops.py` — `find_all_pending_approvals()`(191-204行目、`WHERE t.status = 'pending_approval'` の影響範囲)

### Classification

**Critical** — DBの状態が黙って破損する(silent corruption)。承認待ちタスクが `find_all_pending_approvals()` の検索条件からヒットしなくなり、プロセス再起動時の承認復元(`StartupOrchestrator._recover_pending_approvals()`)が機能しなくなる。停止タスクも「正常完了」として記録され、監査ログが虚偽になる。[ADR-Workflow-Mandatory](../docs/05_agent_03_03_turn-processing-flow-workflow-engine-part1.md#ワークフロー実行必須化-adr-workflow-mandatory) が要求する監査可能性・回復可能性の前提を損なう。

### Evidence

- Explicit in code (High confidence) — コードの制御フローを静的にトレースして確認済み。
- テストギャップ: `tests/test_orchestrator.py` にはこの上書きを検証するテストが見当たらない。

### Recommended next action

- `finally` 内のステータス更新を、`WorkflowPendingApprovalError`/`WorkflowHaltError` を捕捉した分岐では実行しないよう条件を分ける(例: どの例外で終了したかを保持するフラグを追加し、`pending_approval`/`halted` で終了した場合は上書きしない)。
- 承認待ち・停止で終了した場合にDBステータスが維持されることを検証するテストを追加する。
