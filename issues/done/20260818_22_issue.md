### ISSUE-C1: 承認復元処理 (find_all_pending_approvals) の AttributeError による起動失敗 `[確認済]

優先度: Critical
対象ファイル: `scripts/agent/workflow/approval_ops.py`, `scripts/agent/startup.py`, `tests/agent/workflow/test_approval_ops.py`, `tests/agent/test_startup.py`

#### 修正理由
`StartupOrchestrator._recover_pending_approvals()` (`scripts/agent/startup.py`) は起動時に `find_all_pending_approvals()` を呼び出し、前回セッションで未解決の承認ゲートを復元する。しかし `find_all_pending_approvals()` (`scripts/agent/workflow/approval_ops.py:201`) は次のように、`sqlite3.Row` オブジェクトに対して直接 `.get()` を呼び出している。

```python
_approval_from_row(r, status="pending", expires_at=r.get("expires_at")),
```

`sqlite3.Row` は `.get()` メソッドを持たない。実際に Python で再現すると、`.get()` 呼び出しは常に `AttributeError: 'sqlite3.Row' object has no attribute 'get'` を送出する。

```
$ python3 -c "
import sqlite3
con = sqlite3.connect(':memory:'); con.row_factory = sqlite3.Row
cur = con.cursor()
cur.execute('CREATE TABLE t (a INTEGER)')
cur.execute('INSERT INTO t VALUES (1)')
row = cur.execute('SELECT * FROM t').fetchone()
row.get('a')
"
AttributeError: 'sqlite3.Row' object has no attribute 'get'
```

`StateStore.__init__()` は常に `row_factory=True` で DB を開いており (`scripts/agent/workflow/state_store.py:31`)、`find_all_pending_approvals(db)` に渡される行は必ず `sqlite3.Row` である。実際に `approvals`/`tasks` テーブルへ pending 行を1件投入し、`find_all_pending_approvals()` をモックなしで直接呼び出すと同じ `AttributeError` が再現することを確認済み。

同じファイル内の `_approval_from_row()` (17行目) は `workflow_id` を `r["workflow_id"] if "workflow_id" in r.keys() else ""` という、`sqlite3.Row` に `.get()` が無いことを踏まえた正しいパターンで参照している。また `scripts/agent/workflow/state_store.py:104` と `scripts/agent/workflow/task_ops.py:71` はいずれも `row = dict(r)` で辞書化してから `.get()` を呼んでおり、201行目だけがこの慣行から外れている。

`_recover_pending_approvals()` は `try/finally` で `store.close()` を呼ぶのみで例外を捕捉しないため、この `AttributeError` は `StartupOrchestrator.run()` の外側 `except Exception as setup_err:` まで伝播する。ここで `lifecycle.shutdown_all()` によるロールバックが発火し、起動済みサブプロセスを全て停止した上で元の例外が再送出される。結果として、**前回セッションに未解決の承認ゲートが1件でも残っていると、エージェントは起動できない**。

`tests/agent/test_startup.py` の `_recover_pending_approvals` 関連テストは全て `agent.startup.find_all_pending_approvals` をモックしており、`approval_ops.py` の実装本体を経由しない。`tests/agent/workflow/test_approval_ops.py` にも `find_all_pending_approvals()` を直接検証するテストが存在しない。このためこのバグはテストで一切検出されない。

#### 修正意図
`sqlite3.Row` に安全にアクセスする既存の慣行 (`"key" in r.keys()` チェック、または `dict(r)` 化してからの `.get()`) に合わせて修正し、承認復元処理が pending approval の存在時にクラッシュしないようにする。あわせて、モックに依存しない実DB経由のテストを追加し、同種の回帰が再発してもテストで検出できるようにする。

#### 作業内容
1. `scripts/agent/workflow/approval_ops.py:201` の `r.get("expires_at")` を、同ファイル17行目と同様の `r["expires_at"] if "expires_at" in r.keys() else None` 形式、または `dict(r).get("expires_at")` に修正する。
2. `tests/agent/workflow/test_approval_ops.py` に `find_all_pending_approvals()` を実DB (実際の `tasks`/`approvals` テーブル) 経由で直接呼び出すテストを追加する。pending approval が1件以上存在するケースを含める。
3. `tests/agent/test_startup.py` に、`find_all_pending_approvals` をモックせず実装本体を経由する `_recover_pending_approvals()` の統合テストを最低1本追加する。

#### 受け入れ条件
- pending approval が1件以上存在する状態で `find_all_pending_approvals()` を呼び出しても `AttributeError` が発生しない。
- `_recover_pending_approvals()` が正常に完了し、エージェント起動が失敗しない。
- 追加したテストが修正前のコードでは失敗し、修正後は成功することを確認する。
- 既存テストが通る。
