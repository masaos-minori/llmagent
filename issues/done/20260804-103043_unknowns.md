# Unresolved blocking unknown: `chunks_vec` runtime distance metric not empirically confirmed

## Summary

While planning the `memories_vec` NC-004 distance-metric clarification (see `plans/20260727-145945_plan.md`, UNK-02), the `memories_vec` table's runtime distance metric was empirically confirmed to be L2 (Euclidean) against the production `/opt/llm/sqlite-vec/vec0.so` build (VERSION `0.1.10-alpha.4`). However, the sibling `chunks_vec` table (RAG pipeline, `scripts/db/schema_sql.py:47-50`) shares the exact same ambiguity — no `distance_metric=` clause on its `CREATE VIRTUAL TABLE` statement — and was **not** separately empirically tested in this cycle.

This matters because `scripts/db/store_impl.py:39` carries a docstring claiming the `chunks_vec` search path uses "cosine distance", which — if the actual runtime default is L2, as it is for `memories_vec` (same `vec0` module, same missing clause, same binary) — would mean that docstring is factually wrong and potentially misleading to RAG pipeline maintainers.

## Evidence Missing

- No empirical test (analogous to `scratchpad/test_vec0_distance.py`, which was run against `memories_vec`) has been run against a `chunks_vec`-shaped table to confirm whether it returns L2-distance or cosine-distance values at runtime.
- Source-level reasoning (symmetry with `memories_vec`, since both use `CREATE VIRTUAL TABLE ... USING vec0(...)` with no `distance_metric=` clause, and `sqlite-vec.c:2984` initializes `VEC0_DISTANCE_METRIC_L2` as the default) strongly suggests `chunks_vec` also defaults to L2, but this has not been empirically verified.

## Resolution Path

1. Adapt the test methodology in `scratchpad/test_vec0_distance.py` (produced during this planning cycle) to a `chunks_vec`-shaped schema (matching whatever columns/dims `chunks_vec` actually declares in `scripts/db/schema_sql.py:47-50`).
2. Insert known vectors (near-identical, orthogonal, opposite, and a same-direction-different-magnitude pair — the magnitude pair is what distinguished L2 from cosine in the `memories_vec` test) and compare the `distance` column against both L2 and cosine formulas computed independently.
3. If confirmed L2: correct the "cosine distance" docstring in `scripts/db/store_impl.py:39` to state the actual metric, and consider adding an explicit `distance_metric=L2` clause to `chunks_vec`'s `CREATE VIRTUAL TABLE` statement in a follow-up requirement (kept out of the current plan's committed scope, see "Out-of-Scope" in `plans/20260727-145945_plan.md`).
4. If confirmed cosine (e.g., because some upstream normalization or a different code path applies before `chunks_vec` queries — not currently found in `scripts/db/store_impl.py` but worth double-checking): leave the docstring as-is and instead add `distance_metric=cosine` explicitly to the schema.

## Blocking Impact

- **Blocking for:** the optional/conditional `chunks_vec` clarification sub-task referenced in the source requirement's Implementation Instructions #4 and #6 ("Apply the same clarification to `chunks_vec` ... if it shares the same ambiguity").
- **Not blocking for:** the primary `memories_vec` schema/comment update, which this plan (`plans/20260727-145945_plan.md`) already scopes and can proceed independently, since `memories_vec`'s metric was fully confirmed.
