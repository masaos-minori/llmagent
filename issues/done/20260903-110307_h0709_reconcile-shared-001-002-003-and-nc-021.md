# Reconcile SHARED-001, SHARED-002, SHARED-003, and NC-021

## Priority
Medium

## Summary
Reconcile the active recovery documentation and issue inventories so that SHARED-001, SHARED-002, SHARED-003, and NC-021 each have one evidence-based current status.

## Background
`docs/90_shared_90_inconsistencies_and_known_issues.md` currently marks SHARED-001 "resolved" (`_classify_error()` classifies `sqlite3.DatabaseError` as `DbCondition.CORRUPTION`, verified by test) and SHARED-002 "resolved" (backup validation, atomic staging, and post-restore re-verification all implemented, verified by test) — both confirmed accurate by direct read of `scripts/db/recovery.py`. SHARED-003 is marked "partially resolved": target validation (`unsupported_target`) is implemented and verified, but the entry states "Still open: a documented step-by-step operator recovery runbook for these two domains does not yet exist." `docs/00_governance_03_issue-and-uncertainty-management.md`'s NC-021 remains `Status: open`, asking whether structured integrity-result classification is the intended model, even though ADR-008 already mandates it and `DbCondition`/`_classify_error()` already implement it.

## Problem
SHARED-003's "runbook does not yet exist" claim is itself stale: a "Manual Recovery: workflow.sqlite / eventbus.sqlite" section already exists at `docs/05_agent_10_01_operations-and-observability-startup-and-health.md` (confirmed by direct read, lines 87-107), produced by `plans/done/20260901-070239_plan.md`. The actual remaining gap is narrower and different from what SHARED-003 states: the existing runbook does not use the backups `rotate_all_dbs()` already takes for these domains (tracked separately by `H-07-08`, filed alongside this issue) — the gap is "runbook is incorrect," not "runbook is absent." Separately, NC-021's question ("is structured classification the intended model?") is already answered by ADR-008's existing decision and the existing `DbCondition` implementation, but NC-021 has not been updated to reflect this, leaving an open uncertainty item that duplicates already-settled information.

## Reason for Change
Contradictions between active issue inventories and actual implementation state prevent operators and implementation agents from determining current behavior, and risk the same discrepancy being independently rediscovered and re-filed (as happened with SHARED-003's stale claim during this issue's own investigation).

## Implementation Intent
Verify implementation and tests, transfer active requirements into canonical documents, and leave only genuinely unresolved issues in active inventories.
