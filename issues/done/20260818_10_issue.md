# [MEDIUM] Define EventBus operational lifecycle and establish canonical API schemas

## Priority

Medium

## Background

EventBus operational policies and API documentation are incomplete or manually duplicated.

Missing areas include:

- Event retention
- Replay availability
- Database capacity
- Purging
- WAL maintenance
- DLQ retention and requeue behavior
- Consumer-ID lifecycle
- Slow-consumer recovery
- Canonical endpoint and response schemas

## Reason for Change

An EventBus can pass functional tests while failing in long-running operation due to unbounded growth, stale consumers, replay ambiguity, or repeated DLQ cycling.

Manually maintained API documentation can also drift from FastAPI and Pydantic definitions.

## Intent

Define the full operational lifecycle and make executable schemas authoritative for EventBus APIs.

## Tasks

### Retention and Capacity

1. Define event retention and replay availability.
2. Define purge rules and consumer-offset protection.
3. Define database-size guidance, WAL checkpoints, VACUUM, low-disk behavior, metrics, and alerts.

### DLQ and Consumers

4. Define DLQ retention, deletion, requeue eligibility, and failure-count behavior.
5. Define consumer-ID creation, ownership, expiration, reuse, and offset cleanup.
6. Define slow-consumer detection and recovery.
7. Create a recovery sequence diagram.

### API Schema

8. Make FastAPI OpenAPI canonical for all EventBus endpoints.
9. Define all request, success, and error models.
10. Generate or validate Markdown documentation against OpenAPI.
11. Add schema and drift validation to CI.

## Acceptance Criteria

- [ ] Retention and replay periods are aligned.
- [ ] Purge behavior is deterministic.
- [ ] Database capacity and maintenance policies are documented.
- [ ] DLQ lifecycle and requeue behavior are defined.
- [ ] Consumer-ID lifecycle is defined.
- [ ] Slow-consumer recovery is documented.
- [ ] OpenAPI contains all supported endpoints.
- [ ] Request, response, and error models are complete.
- [ ] Markdown API documentation is generated or validated.
- [ ] CI detects API drift.
- [ ] Required health metrics and alerts are documented.

## Validation

1. Test purge and replay boundaries.
2. Test DLQ requeue behavior.
3. Expire a consumer and verify cleanup.
4. Complete the slow-consumer recovery sequence.
5. Compare OpenAPI with documented endpoints.
6. Validate sample payloads against schemas.

## Out of Scope

- Delivery semantics
- ACK/NACK semantics
- Authentication policy
