Title: [BUG] DiagnosticStore: make sensitive_fields configurable, handle encrypted read-back, fix docstring
Labels: priority/medium, type/bug, area/diagnostics, area/config

## Summary
Three related defects live in the diagnostics store and its config wiring:
1. `sensitive_fields` cannot actually be configured from agent.toml.
2. Encrypted rows cannot be read back (no decryption on `fetch()`).
3. The redaction docstring describes behavior the code does not implement.

## Rationale
- `config_builders._build_diagnostics_config()` reads only `encryption_key` and `retention_days` from the `[diagnostics]` table and constructs `DiagnosticsConfig` with those two arguments. `DiagnosticStore._load_diagnostics_config()` does the same. As a result `DiagnosticsConfig.sensitive_fields` is always the dataclass default, and a `sensitive_fields` entry in agent.toml is silently ignored. Operators who add a field to be redacted get no redaction and no warning — a data-hygiene risk.
- `DiagnosticStore.save(encrypt=True)` Fernet-encrypts content, but `DiagnosticStore.fetch()` returns rows verbatim with no decrypt step. Any encrypted row is unreadable (returned as ciphertext). The gap is latent today because every current caller uses `encrypt=False`, but it becomes a real defect the moment any `encrypt=True` path is added.
- `_filter_sensitive_fields()` docstring states the sensitive-field set is "loaded from DiagnosticsConfig", which is misleading given the config value never reaches it.

## Intent
Make diagnostics redaction and encryption behave the way the code and docstrings claim: configured `sensitive_fields` take effect, encrypted rows are readable (or explicitly marked unreadable), and the docstring matches reality.

## Tasks
- [ ] In `_build_diagnostics_config()` and `DiagnosticStore._load_diagnostics_config()`, read `sensitive_fields` from the `[diagnostics]` table and pass it to `DiagnosticsConfig`; keep union-with-defaults semantics.
- [ ] In `DiagnosticStore.fetch()`, decrypt rows with the configured Fernet key when encrypted (Option A), or add an explicit marker so encrypted rows are never treated as plaintext (Option B).
- [ ] Update the `_filter_sensitive_fields()` docstring to match the fixed behavior.
- [ ] Add `DiagnosticsConfig.sensitive_fields` to the diagnostics config design doc (describe purpose only; no concrete values).

## Acceptance criteria
- A `sensitive_fields` entry in agent.toml is honored by `_filter_sensitive_fields()`; unit test: an added field name causes its list value to be redacted.
- A row saved with `encrypt=True` is returned as plaintext by `fetch()` (Option A) or clearly flagged as encrypted-and-not-decodable (Option B); unit test covers the encrypted round-trip.
- Docstring and behavior agree; the design doc lists `sensitive_fields` without embedding its default value.
