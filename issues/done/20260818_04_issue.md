# [HIGH] Define the complete EventBus functional, persistence, and security contract

## Priority

High

## Background

The EventBus documentation does not currently provide one complete and internally consistent contract for:

- Delivery semantics
- Ordering
- Duplicate delivery
- Message loss
- Consumer offsets
- ACK and NACK
- Replay
- DB and JSONL persistence
- Partial persistence failures
- Production authentication and authorization

The current implementation may allow consumer offsets to move backward. Duplicate and conflicting ACK/NACK behavior is not fully defined.

The relationship between successful database persistence and secondary JSONL output is also unclear.

## Reason for Change

EventBus behavior affects workflow execution, event-driven Agent integration, auditability, and recovery.

Without an explicit contract, clients cannot determine:

- Whether duplicate delivery is expected
- Whether client-side deduplication is mandatory
- Whether ordering is guaranteed
- Whether a successful response guarantees DB persistence, JSONL persistence, or both
- Whether an older offset can overwrite a newer offset
- What happens when ACK and NACK requests race
- How a stored consumer offset interacts with `since_seq`
- How replay interacts with normal subscription
- Whether a production EventBus endpoint can be safely exposed

These ambiguities can lead to duplicate workflow execution, missed events, invalid recovery, or unauthorized access.

## Intent

Define one testable contract for the complete EventBus lifecycle, from authenticated publish through delivery, acknowledgement, offset persistence, replay, and recovery.

The contract must distinguish intended guarantees from known implementation limitations.

## Tasks

### Delivery and Ordering

1. Select and document the supported delivery guarantee.
2. Document:

   - Duplicate-delivery conditions
   - Message-loss conditions
   - Ordering scope
   - Retry behavior
   - Reconnection behavior
   - Replay behavior
   - Client deduplication responsibilities
   - Failure-recovery expectations

### Offset Behavior

3. Define whether offsets must be monotonic.
4. Define the behavior of older, equal, newer, and concurrent offset updates.
5. Define transaction boundaries.
6. Define the relationship between sequence numbers and offsets.
7. Define precedence between `since_seq` and a stored consumer offset.
8. Define behavior for unknown or mismatched consumers.

### ACK and NACK

9. Define:

   - First ACK
   - Duplicate ACK
   - First NACK
   - Duplicate NACK
   - ACK after NACK
   - NACK after ACK
   - Unknown event ID
   - Concurrent ACK and NACK
   - Consumer mismatch

10. Define HTTP status codes and response bodies.
11. Define persistence side effects.
12. Define idempotency guarantees.

### Persistence and Durability

13. Identify the authoritative event store.
14. Classify JSONL as authoritative, secondary, audit, or diagnostic output.
15. Define the exact conditions for returning success.
16. Define partial-failure behavior for:

    - DB success and JSONL failure
    - DB failure
    - JSONL success and DB failure
    - Response failure after persistence

17. Define reconciliation procedures.
18. Define required logs, metrics, and alerts.

### Authentication and Authorization

19. Select the supported production security model.
20. Evaluate and document:

    - Loopback-only binding
    - Static bearer token
    - Rotatable service token
    - Mutual TLS
    - Reverse-proxy authentication
    - Per-consumer authorization

21. Define local-development exceptions.
22. Define unauthorized and forbidden responses.
23. Define secret provisioning and rotation.
24. Add production validation for insecure configuration.
25. Reflect the security model in OpenAPI.

## Acceptance Criteria

- [ ] One delivery semantic is explicitly selected.
- [ ] Duplicate and loss scenarios are documented.
- [ ] Ordering guarantees are explicit and testable.
- [ ] Client deduplication responsibilities are explicit.
- [ ] Replay and normal subscription semantics are consistent.
- [ ] Offset monotonicity requirements are documented.
- [ ] Older, equal, newer, and concurrent offset updates have defined behavior.
- [ ] Sequence-number and offset relationships are documented.
- [ ] `since_seq` precedence is documented.
- [ ] Every ACK/NACK scenario has a defined status code and response.
- [ ] ACK/NACK side effects and idempotency are documented.
- [ ] The authoritative persistence layer is identified.
- [ ] JSONL responsibility is clearly classified.
- [ ] HTTP success guarantees are explicit.
- [ ] Partial persistence failures have defined behavior.
- [ ] Reconciliation and monitoring requirements are documented.
- [ ] A production authentication model is selected.
- [ ] Unauthorized and forbidden responses are defined.
- [ ] Secret provisioning and rotation are documented.
- [ ] Insecure production configuration is rejected.
- [ ] OpenAPI reflects the final security and API contract.
- [ ] Known implementation limitations are registered as Known Issues.
- [ ] Automated tests cover the defined contract.

## Validation

1. Test duplicate-delivery conditions.
2. Test out-of-order and concurrent offset updates.
3. Test all ACK/NACK transitions.
4. Simulate DB success with JSONL failure.
5. Simulate persistence success followed by response failure.
6. Verify replay after reconnection.
7. Attempt unauthorized access in production mode.
8. Verify local-development exceptions separately.
9. Verify that client deduplication satisfies the documented delivery model.

## Out of Scope

- Event retention duration
- DLQ retention duration
- Consumer-ID expiration
- General MCP security controls
