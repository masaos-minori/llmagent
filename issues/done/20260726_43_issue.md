# Implement meaningful Plan and Verify workflow stages

## Priority

High

## Summary

The workflow has `plan`, `execute`, and `verify` stages, but the current orchestration does not give `plan` and `verify` meaningful responsibilities. This task implements Plan JSON generation and Verify Report generation as first-class workflow artifacts.

## Background

The workflow definition includes:

- `plan`
- `execute`
- `verify`

However:

- `plan_fn` is currently a placeholder.
- `verify_fn` currently performs turn-end processing.
- `WorkflowEngine` already supports recording stage artifacts when a stage callback returns an artifact URI.

This means the system has the infrastructure to store Plan and Verify artifacts, but it does not yet use it.

## Problem

The workflow currently behaves more like a wrapper around the LLM turn than a true plan-execute-verify control plane.

Problems include:

- No explicit task plan is generated.
- Execute does not have a structured plan to reference.
- Verify does not inspect structured success criteria.
- Turn finalization is mixed into the Verify stage.
- Empty or low-quality answers may be treated as successful.

## Implementation Intent

Make the workflow stages meaningful:

- `plan`: define intent, constraints, expected tools, and success criteria.
- `execute`: perform the LLM/tool turn using the plan as context.
- `verify`: evaluate the result against the plan.
- `finalize`: handle audit, metrics, and cleanup outside Verify.

## Required Changes

### 1. Generate Plan JSON in plan stage

Create a lightweight Plan JSON artifact.

Suggested fields:

    {
      "task_id": "...",
      "user_goal": "...",
      "intent": "chat | retrieval | tool_task | write_task | destructive_task",
      "execution_mode": "direct_answer | tool_assisted | approval_required",
      "expected_tools": [],
      "success_criteria": [
        "answer is not empty",
        "tool errors are disclosed when relevant",
        "requested artifact is produced when required"
      ],
      "limits": {
        "max_tool_turns": 5,
        "max_repeated_tool_calls": 1
      }
    }

Plan generation can initially be rule-based. LLM-based planning can be introduced later.

### 2. Store Plan JSON as workflow artifact

The `plan_fn` should return the artifact URI so `WorkflowEngine` records it as a `plan` artifact.

### 3. Make execute stage aware of the plan

The execute stage should be able to read or reference the generated plan.

Short-term acceptable implementation:

- Store the plan URI in local orchestration state.
- Pass plan information to execute/verify through closure variables.

Long-term improvement:

- Add structured artifact lookup helpers.

### 4. Generate Verify Report

The verify stage should evaluate:

- `TurnResult.action`
- `TurnResult.answer`
- `TurnResult.reason`
- `TurnResult.error_kind`
- Plan success criteria
- Tool loop guard finalization status
- Empty answer cases
- Max tool turn cases
- Tool error disclosure when applicable

Suggested Verify Report:

    {
      "task_id": "...",
      "status": "passed | warning | failed",
      "reason": "tool_loop_guard_finalized",
      "checks": [
        {
          "name": "non_empty_answer",
          "result": "passed"
        },
        {
          "name": "tool_loop_guard",
          "result": "warning"
        }
      ]
    }

### 5. Separate finalize from verify

Turn-end audit and cleanup should not be the primary responsibility of `verify_fn`.

Move finalization to a distinct orchestrator-level step after `WorkflowEngine.run()`.

## Acceptance Criteria

- `plan_fn` generates a Plan JSON object.
- Plan JSON is stored as a `stage_id="plan"` artifact.
- Execute and Verify can access the Plan JSON or its URI.
- `verify_fn` evaluates `TurnResult` and Plan success criteria.
- Verify result is stored as a `stage_id="verify"` artifact or diagnostic record.
- Empty answers do not pass verification silently.
- `_handle_turn_end()` is no longer the only behavior of `verify_fn`.
- Turn finalization is clearly separated from verification.
- `plan.timeout_sec` and `verify.timeout_sec` remain appropriate or are adjusted.

## Test Cases

- Plan artifact is created for each turn.
- Verify report is created for each turn.
- Empty answer fails or warns in verification.
- Final answer after ToolLoopGuard is verified as warning or passed, not raw failure.
- Turn-end audit still occurs after workflow completion.
- Verify does not perform unrelated cleanup as its main responsibility.
