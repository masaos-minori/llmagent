# [High] Replace Dual Tool Execution Paths with One Correct DAG Execution Plan

## Consolidated Tasks

- H-05: Unify DAG and standard-path side-effect serialization semantics.

## Priority

High

## Summary

Remove the separate standard execution path and use one DAG execution-plan path for every prepared and approved tool-call batch.

Treat `serial_tool_calls` as a force-serial policy applied to the DAG planner. Correct the current scheduler defects involving scope-less writes, misplaced serial barriers, missing read/write conflict detection, and disconnected group execution flags.

## Reason for Change

The current implementation has two execution engines with different safety rules:

```text
serial_tool_calls = false
  -> DAG path

serial_tool_calls = true
  -> standard path
```

The DAG path uses `ToolSpec.requires_serial`, `is_write`, and resource metadata. The standard path uses static `is_side_effect()` and serializes the entire batch whenever one side-effect tool is detected.

This means changing a configuration flag changes not only concurrency but also the source of truth and the meaning of serialization.

The current scheduler also has concrete correctness defects:

1. Scope-less writes are collected into `write_first`, but the corresponding `serialize_flags` entry is `False`. The runner therefore executes those writes concurrently with `asyncio.gather()`.
2. `requires_serial` calls are removed from their original positions and placed before all other calls. They do not act as barriers between earlier and later calls.
3. Only writes are placed into resource groups. Reads are placed into the final parallel group, so a read and write against the same resource may execute concurrently.
4. Metadata is keyed by tool name instead of call ID.
5. `groups` and `serialize_flags` are separate parallel arrays, allowing invalid combinations.
6. The scheduler returns both a group list and metadata containing another execution-group representation, while the runner ignores the first result.
7. Serialization events can be emitted for one-call groups where no concurrency was prevented.
8. `requires_serial` events hard-code `is_write=True`, even for a read-only serial tool.

## Intent of the Change

The intent is to have one deterministic execution planner with one set of safety rules.

After this change:

- All calls use the same DAG plan and audit path.
- `serial_tool_calls=True` means only that the planner emits a fully sequential plan.
- `requires_serial` means a true barrier at the call's original position.
- Resolved call-level resource scopes determine conflicts.
- Reads participate in conflict detection.
- Scope-less state-changing calls use `global:write` and cannot run concurrently.
- The plan model binds each call group to its execution mode, preventing flag misalignment.
- Results are restored to original call order despite concurrent execution.

A deterministic greedy planner is sufficient. The goal is correctness and predictability, not maximum graph optimization.

## Required Changes

### 1. Make DAG the only execution path

Remove `_execute_standard()`.

Always execute through the DAG plan.

Pass:

```python
force_serial = ctx.cfg.tool.serial_tool_calls
```

into the planner.

### 2. Update ToolConfig documentation

Replace the current serial execution comment with:

```python
# When True, the DAG scheduler executes all prepared and approved tool calls
# sequentially in original call order. The DAG remains the sole execution path.
serial_tool_calls: bool = False
```

### 3. Define force-serial planning

When `force_serial=True`:

- Emit one sequential call at a time.
- Preserve original call order.
- Use the same execution-plan and audit path as normal DAG execution.
- Record the reason as `forced_serial`.

### 4. Implement true serial barriers

A call with `requires_serial=True` must remain at its original position.

Example:

```text
A
B
SERIAL C
D
E
```

Required phases:

```text
Phase 1: plan A and B under normal conflict rules
Phase 2: execute C alone
Phase 3: plan D and E under normal conflict rules
```

Do not collect serial calls into a leading bucket.

### 5. Build phases in input order

Suggested algorithm:

1. Iterate over prepared calls in original order.
2. Close the current normal phase when a serial barrier is encountered.
3. Add the serial call as its own phase.
4. Start a new normal phase after the barrier.
5. Within each normal phase, compare call-level `ToolSpec` conflicts.
6. Place only mutually non-conflicting calls into the same concurrent batch.
7. Preserve input order for conflicting calls.
8. Execute phases sequentially.

### 6. Use call ID metadata

Planner input:

```python
call_specs: dict[str, ToolSpec]
```

The planner must fail when a prepared call ID has no `ToolSpec`.

Never default missing metadata to read-only behavior.

### 7. Include reads in conflict detection

Required behavior for overlapping scopes:

- Read/read: may run concurrently.
- Read/write: serialize.
- Write/read: serialize.
- Write/write: serialize.

Filesystem scope overlap includes equal paths and ancestor/descendant relationships.

### 8. Remove write_first

Delete the current `write_first` bucket.

A state-changing call with no resolved scope must already carry:

```python
resource_scopes = ("global:write",)
```

`global:write` must conflict with every other call in the same normal phase.

Before the full planner is merged, an emergency patch may set the current `write_first` group to sequential execution. That patch is not sufficient to close this issue.

### 9. Replace parallel arrays with explicit plan objects

Recommended structure:

```python
@dataclass(frozen=True)
class ScheduledGroup:
    calls: tuple[PreparedToolCall, ...]
    sequential: bool
    reason: str = ""
```

```python
@dataclass(frozen=True)
class ScheduledBatch:
    groups: tuple[ScheduledGroup, ...]
```

```python
@dataclass(frozen=True)
class ExecutionPlan:
    batches: tuple[ScheduledBatch, ...]
    serialization_events: tuple[SerializationEvent, ...]
```

Equivalent names are acceptable if execution mode cannot become detached from its group.

### 10. Return one execution-plan object

Replace the current return value containing both `groups` and metadata with one `ExecutionPlan`.

The planner's return value must be the same structure the runner executes and audits.

### 11. Correct serialization events

Emit events only when concurrency was actually prevented.

Use explicit reasons:

```text
forced_serial
requires_serial
resource_read_write_conflict
resource_write_write_conflict
global_write_scope
```

Record:

- Triggering call ID
- Tool name
- Actual `is_write`
- Relevant resource scopes
- Number of affected calls
- Scheduling decision

Do not:

- Emit a conflict event for a one-call group with no competitor.
- Hard-code `is_write=True` for read-only serial calls.
- Report `parallel` mode when the plan executed sequentially.

### 12. Preserve final result order

Calls may execute concurrently, but collected results must be sorted by original call position before:

- Conversation history updates
- Session persistence
- User-visible output
- Failure-key accounting

## Acceptance Criteria

- `_execute_standard()` is removed.
- Every batch uses the DAG execution-plan path.
- `serial_tool_calls=True` executes all calls sequentially in original order.
- `requires_serial` remains at its original position and divides earlier and later phases.
- Scope-less state-changing calls never execute concurrently.
- Same-scope read/write calls serialize.
- Same-scope write/write calls serialize.
- Same-scope read/read calls may run concurrently.
- Different-scope state-changing calls may run concurrently when no other constraint applies.
- Planner metadata is keyed by call ID.
- Missing `ToolSpec` fails closed.
- The scheduler returns one coherent plan object.
- Group execution mode cannot become detached from its calls.
- Serialization events describe actual scheduling decisions.
- Final outputs remain in original call order.

## Required Tests

- Force-serial mode preserves order.
- One serial barrier between two normal phases.
- Multiple serial barriers.
- A read-only serial call records `is_write=False`.
- A `global:write` call runs alone in its phase.
- Same-scope read and write serialize.
- Same-scope writes serialize.
- Same-scope reads execute concurrently.
- Different-scope writes may execute concurrently.
- Parent directory read and descendant write serialize.
- A one-call scope does not emit a conflict event.
- Missing call ID metadata raises a planning error.
- Results from concurrent calls are restored to original order.
- Audit mode and scheduling mode match actual execution.
