## 起動時の承認復元ロジックが最新ではなく最古のpending approvalを復元する

### Summary

`StartupOrchestrator._recover_pending_approvals()` はコメント上「最新のpending approvalを復元する」設計だが、実装は`ORDER BY ... DESC`で取得したリストの末尾(`results[-1]`)を選んでおり、実際には**最も古い**pending approvalが復元される。

### Problem

- `scripts/agent/workflow/approval_ops.py:191-204` の `find_all_pending_approvals()` は `ORDER BY a.created_at DESC, a.rowid DESC` でpending approvalを取得する。先頭(`results[0]`)が最新、末尾(`results[-1]`)が最古。
- `scripts/agent/startup.py:518-519` は次の通り実装されている:
  ```python
  # Recover the most recent pending approval first
  task_id, approval = results[-1]
  ```
  コメントの意図(最新を復元)と実装(`[-1]` = 最古を選択)が矛盾している。
- 複数タスクが `pending_approval` 状態のまま再起動した場合、REPLが `ctx.turn.pending_approval_id` に設定し、ユーザーに提示するのは作成日時が最も古い承認レコードになる。

### Affected Files

- `scripts/agent/startup.py` — `_recover_pending_approvals()` (517-540行目付近)
- `scripts/agent/workflow/approval_ops.py` — `find_all_pending_approvals()` (191-204行目付近、参照元としてソート順を確認)

### Classification

**High** — ワークフロー承認ゲートは [ADR-Workflow-Mandatory](../docs/05_agent_03_03_turn-processing-flow-workflow-engine-part1.md) により必須の実行経路であり、承認対象の取り違えは誤ったタスクへの `/approve`/`/reject` 実行につながりうる。

### Evidence

- Explicit in code (High confidence) — `results[-1]` とコメントの矛盾は静的に確認可能。

### Recommended next action

- `results[0]` に修正するか、クエリ側を `ORDER BY ... ASC` に変更して `results[-1]` の意味を一致させる。
- 「複数pending approvalがある場合に最新のものが選ばれること」を固定するテストを追加する(既存テストにこの並び順を検証するものがないため回帰しない状態だった)。
