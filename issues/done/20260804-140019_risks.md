# `test_parent_dict_merge_one_level_deep` duplicates `load_all()`'s merge algorithm instead of exercising it

## Priority
Low

## Target files
- `tests/shared/test_shared_boundary_conditions.py` (`TestDictMergeConflictResolution::test_parent_dict_merge_one_level_deep`, lines 91-116)
- `scripts/shared/config_loader.py` (`ConfigLoader.load_all()`, lines 68-94 — reference only, not expected to change)

## Background
While executing the plan at `plans/20260804-135935_plan.md` (rewriting
`test_different_subsections_in_load_all_merged` to call the real `ConfigLoader.load_all()`
instead of hand-copying its merge algorithm), a sibling test in the *same* test class was found
to have the identical anti-pattern:

```python
def test_parent_dict_merge_one_level_deep(self, tmp_path: Path) -> None:
    """Parent dicts are merged one level deep in load_all."""
    ...
    loader = ConfigLoader(config_dir=tmp_path)
    # Manually merge like load_all does
    result_a = loader.load("extra_mcp.toml")
    result_b = loader.load("extra_mcp2.toml")
    merged: dict[str, Any] = {}
    for key, val in result_a.items():
        if isinstance(val, dict) and isinstance(merged.get(key), dict):
            merged[key] = {**merged[key], **val}
        else:
            merged[key] = val
    for key, val in result_b.items():
        ...
    assert "github" in merged.get("mcp_servers", {})
```

Its docstring — "Parent dicts are merged one level deep in load_all" — and its own comment
("Manually merge like load_all does") both make the same claim as the now-fixed
`test_different_subsections_in_load_all_merged` used to: that it verifies `load_all()`'s
behavior. In fact it asserts against a hand-rolled copy of the merge algorithm, not against
`load_all()`'s real return value, so it would not catch a regression in
`ConfigLoader.load_all()`'s one-level-deep dict merge (`config_loader.py` lines 82-93).

## Problem
This is the same coverage-duplication risk described in the requirement that produced
`requires/done/20260804-131256_require.md` and the sibling fix in
`requires/done/20260804-100530_require.md` — but it was not listed as a target file in either
requirement, so it was left unfixed by both cycles. It is not currently in scope for
`plans/20260804-135935_plan.md`, whose requirement document explicitly scoped only
`test_different_subsections_in_load_all_merged` and explicitly listed the other tests in the
class as "unaffected" without mentioning this one.

## Reason for change
If `ConfigLoader.load_all()`'s real merge logic ever regresses, this test would not catch it,
for the same reason the now-fixed test wouldn't have. The established fix pattern
(`monkeypatch.setattr("shared.config_loader._BASE_CONFIG_FILES", (...))` +
`loader.load_all()`, already used in `tests/shared/test_config_loader.py::TestMergeOrder::
test_nested_dict_merge` and in the just-rewritten `test_different_subsections_in_load_all_merged`)
applies directly here with no new technique needed.

## Suggested implementation intent
Rewrite `test_parent_dict_merge_one_level_deep` to use the same
`monkeypatch.setattr("shared.config_loader._BASE_CONFIG_FILES", (...))` pattern, replacing the
manual `loader.load(...)` + merge-loop calls with a single `loader.load_all()` call, and updating
assertions to read from its real return value. Do not modify `scripts/shared/config_loader.py`.

## Acceptance criteria
- `test_parent_dict_merge_one_level_deep` calls `ConfigLoader.load_all()` directly (via a
  monkeypatched `_BASE_CONFIG_FILES`) rather than hand-copying its merge algorithm.
- The test's assertions read from `load_all()`'s real return value.
- No production code (`scripts/shared/config_loader.py`) is modified.
- Other tests in `TestDictMergeConflictResolution` remain unmodified and continue to pass.
