## REPL起動成功時にもfinallyでプロセスterminateループが実行され、正常起動プロセスを即killしかねない設計矛盾

### Summary

`AgentREPL.run()` の `finally` ブロックは「部分起動失敗時にspawn済みサブプロセスをterminateする」意図のコメントが付いているが、実際には起動成功時にも必ず実行される。現状は既知バグ(`issues/20260727_02_issue.md` で報告済みの `_spawned_subprocesses` 追跡漏れ)により実害が隠れているだけであり、そのバグ単体を修正すると、正常に起動したMCPサブプロセスを起動直後に即terminateしてしまう新たな回帰を生む。

### Problem

- `scripts/agent/repl.py:736-752`:
  ```python
  startup = StartupOrchestrator(self._ctx, self._view)
  _spawned_subprocesses: list[subprocess.Popen] = []
  try:
      self._cmds, self._orchestrator, _spawned_subprocesses = await startup.run()
  except Exception as e:
      self._view.write_fatal(f"Startup failed: {e}")
      raise
  finally:
      # Terminate any subprocesses started during partial startup
      all_procs = _spawned_subprocesses
      if hasattr(startup, "_spawned_subprocesses"):
          all_procs = list(all_procs) + list(startup._spawned_subprocesses)
      for proc in all_procs:
          if proc.poll() is None:
              proc.terminate()
      await self._close_resources()
  ```
- コメント「Terminate any subprocesses started during partial startup」は「起動が部分的に失敗した場合のみ」terminateする意図を示しているが、`finally` は `try` ブロックが例外なく正常終了した場合(=起動成功時)にも必ず実行される。
- 現状は `issues/20260727_02_issue.md` で報告した別バグ(`_spawned_subprocesses` が常に空リストのまま追跡されない)のおかげで、`all_procs` が常に空になり実害が隠れている。
- しかし、そのバグを「戻り値・インスタンス属性に実際のプロセスを正しく格納する」形で単独修正すると、この `finally` ブロックが起動成功時にも実行される以上、**正常に起動したMCPサブプロセスを起動直後に即 `terminate()` してしまう**回帰が発生する。

### Affected Files

- `scripts/agent/repl.py` — `AgentREPL.run()` の `finally` ブロック(743-752行目)
- `scripts/agent/startup.py` — `StartupOrchestrator.run()` / `_start_servers()`(関連する既知バグの発生源、`issues/20260727_02_issue.md` 参照)

### Classification

**High** — 現状は別バグとの組み合わせで実害が隠れているが、`issues/20260727_02_issue.md` の修正だけを単独で行うと重大な回帰(正常起動プロセスの即時終了)を招く「隠れた地雷」。

### Evidence

- Explicit in code (High confidence) — `finally` の実行条件はPythonの言語仕様として例外の有無を問わないため、静的に確認可能。

### Recommended next action

- `finally` の terminate ループを、起動が例外で終了した場合(`except` 節に入った場合)のみ実行するよう分岐する。
- `issues/20260727_02_issue.md` の修正作業と同時に対応すること(片方だけの修正は新たな回帰を生むため、2つのissueは同一の修正PRで扱うことを推奨)。
