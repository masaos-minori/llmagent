# [HIGH] Canonicalize MCP runtime lifecycle and generate the active service inventory

## Priority

High

## Background

The documentation contains inconsistent descriptions of MCP server lifecycle behavior.

Some documents describe current MCP servers as Agent-managed subprocesses, while others describe them as persistent externally managed services.

The meanings of the following startup modes are not consistently documented:

- none
- persistent
- subprocess

Current server URLs, ports, startup modes, health-check modes, and enabled states are also repeated manually in multiple documents.

## Reason for Change

MCP startup mode determines:

- Process ownership
- Service startup order
- Health-check behavior
- Live tool discovery
- Routing availability
- Agent startup success or failure
- Local and production failure behavior

Incorrect documentation can lead to:

- Starting one server twice
- Failing to start a required server
- Treating an unavailable server as routable
- Assuming that health checks occurred when they did not
- Applying local fail-open behavior in production
- Applying production fail-closed behavior during local development

Manual service inventories also become stale when configuration changes.

## Intent

Create one canonical lifecycle specification and generate current operational values directly from active configuration.

Stable behavior and current configured values must be documented separately.

## Tasks

### Startup-Mode Specification

1. Define `none`, `persistent`, and `subprocess`.
2. For each mode, document:

   - Whether the Agent starts the process
   - Whether the process is externally managed
   - Whether health checks are performed
   - Whether live tool discovery is performed
   - Whether the server becomes routable
   - Expected process ownership
   - Local-profile failure behavior
   - Production-profile failure behavior

3. Document unsupported or invalid combinations.
4. Reconcile conflicting descriptions across:

   - Overview
   - Deployment
   - MCP documentation
   - Agent startup documentation
   - Operations documentation
   - Troubleshooting documentation

### Generated Service Inventory

5. Generate the active MCP inventory from current configuration.
6. Include:

   - Server key
   - Service name
   - URL
   - Port
   - Startup mode
   - Health-check mode
   - Enabled state
   - Security tier, if available

7. Replace manually maintained current-value tables with generated output.
8. Mark non-canonical examples explicitly.
9. Add generated-section guards.
10. Add CI stale-output detection.

## Acceptance Criteria

- [ ] One canonical document defines every startup mode.
- [ ] Agent, MCP, Overview, and Deployment documents use the same definitions.
- [ ] Process ownership is explicit for every mode.
- [ ] Health-check behavior is explicit for every mode.
- [ ] Tool-discovery behavior is explicit for every mode.
- [ ] Routing availability is explicit for every mode.
- [ ] Local and production failure behavior is documented separately.
- [ ] Unsupported combinations are documented.
- [ ] The service inventory is generated from active configuration.
- [ ] Every configured MCP server appears exactly once.
- [ ] Manual current-value tables are removed or marked as examples.
- [ ] Generated output is deterministic.
- [ ] Generated sections contain matching guard comments.
- [ ] CI detects stale generated output.
- [ ] Relevant implementation symbols and tests are referenced as evidence.

## Validation

1. Compare the generated inventory with active configuration.
2. Verify each configured server appears exactly once.
3. Verify every startup-mode enum value is documented.
4. Compare local and production failure descriptions with implementation and tests.
5. Change one temporary configuration value and verify that CI detects stale documentation.

## Out of Scope

- Changing startup-mode runtime behavior
- Changing configured startup modes
- Refactoring MCP process management
