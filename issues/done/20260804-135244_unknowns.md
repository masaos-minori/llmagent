# Decide: should `resolve_approval` reject approvals for halted tasks?

## Priority
Medium

## Context
Filed while converting `requires/done/20260804-131007_require.md` into
`plans/20260804-135114_plan.md`. `resolve_approval()`
(`scripts/agent/workflow/approval_ops.py`, lines 45-67) currently checks only the approval row's
own status (`not found` / `already resolved`); it never queries or checks the associated task's
status. Resolving an approval for a task already marked `"halted"` (via
`update_task_status(db, task_id, "halted")`) therefore succeeds today exactly as if the task were
still `"running"`.

`tests/agent/test_approval_task_persistence.py::TestHaltedTaskStatusRejection::test_halted_task_prevents_resume`
currently asserts the opposite (`pytest.raises(RuntimeError)`), which does not match current
behavior. The separate, already-approved `plans/done/20260804-104315_plan.md` directs correcting
that test to assert the true (no-exception) outcome, as a document-only test-fix — that fix has
not yet been applied to the test file as of this writing (the file still has unrelated pre-existing
collection errors: an import of `TurnContext` from `agent.context`, which does not exist there, and
`update_task_status` imported from `agent.workflow.approval_ops`, where it is not defined). Once
that fix lands, the codebase will have **zero automated coverage** of the halted-task-approval gap.

## Unknown
Is the current no-check behavior intentional and acceptable, or is it a product gap that should be
closed with an explicit guard?

This is a maintainer/product decision, not something derivable from source code, and no live
maintainer is available in the document-only planning cycle that produced this issue.

## Options

**Option 1 — Add a guard.** Halted-task rejection is desired behavior. A future, separate
requirement document should authorize adding a task-status check inside `resolve_approval` (or in
the `_cmd_approve`/`_cmd_reject` handlers in `scripts/agent/commands/cmd_workflow.py`, before
calling `resolve_approval`) that rejects resolution when the associated task's status is
`"halted"`, together with restoring a test equivalent to `test_halted_task_prevents_resume` that
asserts `pytest.raises(RuntimeError)` against the new, intentional guard.

Blast radius if authorized (see `plans/20260804-135114_plan.md` Affected Areas for full detail):
`scripts/agent/workflow/approval_ops.py`, `scripts/agent/commands/cmd_workflow.py`, and ~15+
existing `resolve_approval(...)` call sites across `tests/agent/test_approval_task_persistence.py`,
`tests/agent/workflow/test_approval_ops.py`, `tests/agent/workflow/test_workflow_state_store.py`,
`tests/agent/workflow/test_workflow_engine.py`, and `tests/agent/workflow/test_approval_race_condition.py`
would need their fixtures re-verified against the new guard.

**Option 2 — No change.** The current behavior is acceptable (e.g., a halted task is an
independent, orthogonal state that should not block approval resolution). No production code
changes needed. The corrected test's docstring (per `plans/done/20260804-104315_plan.md`) remains
the documented characterization of this known gap. This requirement/issue can then be closed as
"working as intended."

## Resolution path
A maintainer reviews this issue plus `plans/20260804-135114_plan.md` and
