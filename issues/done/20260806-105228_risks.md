# RISK-01: `# noqa: BLE001` / `# noqa: PLC0415` may be inert suppressions under the current ruff config

## Title
Adding justification text to `startup.py`'s noqa comments does not address whether those
suppressions are functionally meaningful under the project's active ruff `select` list

## Description
`plans/20260806-105228_plan.md` (implementing `requires/20260806-103649_require.md`, now at
`requires/done/`) adds inline em-dash justifications to five previously-unjustified `# noqa`
comments in `scripts/agent/startup.py`. This satisfies the letter of `rules/coding.md`
§Suppression governance ("Every `# noqa`... requires an inline justification"), but does not
resolve a deeper, related question: `pyproject.toml`'s `[tool.ruff.lint] select = ["E", "W", "F",
"I", "UP"]` does not include the `BLE` or `PLC` rule families that `BLE001`/`PLC0415` belong to,
so it is unclear whether ruff (the only lint tool configured in `tox.ini`) ever actually flags
these lines. If it does not, the suppressions — now justified in prose — are still suppressing
nothing.

## Context
- Same investigation as `issues/20260806-105228_unknowns.md` (UNK-01); filed separately here
  because it is a risk on the *implementation plan* (justifying text that may be moot) rather
  than a pure knowledge gap.
- Affects: `scripts/agent/startup.py` and, more broadly, every other file using `# noqa: BLE001`
  or `# noqa: PLC0415` (e.g. `tests/mcp_servers/mdq/test_mdq_service.py`,
  `tests/mcp_servers/cicd/test_mcp_server_health_status.py`).
- Not blocking for the current comment-only task: its acceptance criteria (per
  `requires/done/20260806-103649_require.md`) only requires every noqa line to carry an em-dash
  justification, verified via `rg` — it does not require verifying the underlying rule is
  actually active.

## Suggested resolution
- Track under the same follow-up as `issues/20260806-105228_unknowns.md` UNK-01: audit whether
  `BLE`/`PLC0415` should be added to `pyproject.toml`'s ruff `select` list, or whether the noqa
  codes across the codebase should be corrected to match rules that are actually enforced.
- No action needed within the scope of `plans/20260806-105228_plan.md` — mitigation there is
  "defer to a separate, dedicated requirement" since fixing the `select` list could surface new
  findings across many files, which is a materially larger change than a comment-only edit.

# RISK-02: No automated check enforces the "every noqa needs an em-dash justification" convention

## Title
The em-dash-justification convention in `rules/coding.md` is manually verified (via `rg`), not
enforced by CI, so it can regress silently

## Description
The requirement's own acceptance criterion —
`rg '# noqa' scripts/agent/startup.py | grep -v '# noqa:.*—'` returning no lines — is a manual
command a developer must remember to run. Searching `tests/` for existing enforcement (`rg -n
"noqa" tests/` and a check of `tests/agent/test_startup_consistency.py` specifically) found no
test or pre-commit hook that asserts every `# noqa` in `scripts/` carries an em-dash justification.
A future edit to `scripts/agent/startup.py` (or any other file) could add a bare `# noqa: CODE`
without justification, and nothing in the current toolchain (`rules/toolchain.md`'s standard
sequence: ruff, mypy, lint-imports, ast-grep constraint checks, bandit, pytest, diff-cover,
pre-commit) would catch it.

## Context
- Discovered while verifying, for `plans/20260806-105228_plan.md`, that no test parses the
  literal noqa comment text in `scripts/agent/startup.py` (confirmed safe to edit comment wording
  without breaking a test) — the flip side of that finding is that nothing would catch a
  regression either.
- Relevant: `rules/coding.md` §Suppression governance already documents three `rg`-based
  detection commands (for bare `# noqa`, bare `# type: ignore`, bare `# nosec`) but these are
  presented as commands to run manually ("run before every commit"), not wired into
  `ast-grep`/pre-commit/CI.

## Suggested resolution
- Consider adding the three `rg` commands already documented in `rules/coding.md`
  §Suppression governance as a pre-commit hook step or a dedicated lightweight CI check (e.g. a
  `tox` env or a `check-mcp-docs`-style entry point), so an unjustified suppression fails fast
  instead of relying on a human running `rg` before every commit.
- Out of scope for the current comment-only requirement; suggest scoping as its own
  small requirement (likely Path A: adds a check script/hook, no runtime interface change).
