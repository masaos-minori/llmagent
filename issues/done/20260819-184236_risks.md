# Risk follow-up: Option B decision for `tool_definitions` severity was inferred, not stakeholder-confirmed

## Priority
Low (non-blocking; recorded for traceability per `plans/20260819-184236_plan.md`)

## Context
`requires/done/20260818-224947_require.md` framed the `tool_definitions` FATAL/WARNING
contradiction between `docs/05_agent_10_01_operations-and-observability-startup-and-health.md`
and `scripts/agent/services/mcp_tool_discovery.py` as an explicit decision point: either the
doc is correct (Option A — `tool_definitions` should never be FATAL) or the implementation is
correct (Option B — `tool_definitions` follows the same unified `is_fatal = strict or
security_profile == PRODUCTION` scheme as drift and malformed-capabilities findings).

`plans/20260819-184236_plan.md` (Design section) selected **Option B** based on in-repo
evidence: the module docstring in `scripts/agent/services/mcp_tool_discovery.py` (lines 33-35
and 389-395) explicitly and deliberately groups `tool_definitions` into the unified severity
scheme and frames the current behavior as a fix for a prior bug ("this resolves the old quirk
where strict-mode drift detection was silently downgraded to 'skipped'"). No stakeholder or
product-owner sign-off was sought or obtained in this workflow cycle — the requirement
explicitly permits inferring intent from design history when a stakeholder decision is not
obtainable.

## Risk
If the actual intended operational policy is Option A (tool_definitions should never block
startup) rather than what the docstring implies, implementing Option B's doc change would
formally codify a production behavior (FATAL startup abort on tool_definitions mismatch under
`strict=True` or `security_profile=PRODUCTION`) that could surprise operators relying on the
old "never FATAL" documentation, without ever having received explicit confirmation that this
is desired.

## Suggested resolution
Before or during the implementation phase that consumes this plan:
- Optionally confirm with the operations/product owner that FATAL-on-production for
  `tool_definitions` mismatches is intended, especially given this changes a previously
  documented "always continue" guarantee into a "may abort startup" behavior.
- If confirmed, proceed with Option B exactly as specified in
  `plans/20260819-184236_plan.md` (doc-only edit + new tests).
- If contradicted, fall back to Option A as specified in the source requirement's
  "Implementation intent" section (`requires/done/20260818-224947_require.md`), which is fully
  specified there and does not require re-planning.
