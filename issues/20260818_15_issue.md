### ISSUE-H2: 副作用判定 (is_side_effect) の重複統合 `[確認済 / caller grep 要]

優先度: High
対象ファイル: `scripts/shared/runtime_tool_registry.py`, `scripts/shared/tool_executor_helpers.py

#### 修正理由
副作用判定 `is_side_effect()` が shared 層に二つ存在する。これは意図的な暫定重複であり、`runtime_tool_registry.py` の docstring に「intentionally duplicates ... this is temporary, parallel duplication pending a future unification decision」と明記されている。

- helpers 版 (`tool_executor_helpers.is_side_effect()`) は `_SIDE_EFFECT_TOOLS` frozenset を参照し、`ToolExecutor.execute()` の TTL キャッシュバイパス判定として現役稼働している。
- registry 版 (`RuntimeToolRegistry.is_side_effect()`) は `self.get(tool_name).is_write` から判定する別実装である。
- さらに registry には `classify_operation_type()` があり、これも同じ `is_write` から read/write を導出する派生である。docstring に「DELETE/EXECUTE/API_WRITE の粒度は導出できない (documented gap)」とある。

#### 修正意図
「同じ問いに二つの答えの出所がある」状態を解消し、副作用判定の出所を一つに定める。判定基準がドリフトして、キャッシュ挙動と別経路の挙動が食い違う将来事故を防ぐことが狙いである。

#### 混同防止 (設計上の明確化)
- バッチの直列 / 並列判定は既に `ToolSpec.requires_serial` / `is_write` (`tool_spec_for_call()` 経由) へ移行済みであり、registry 版 `is_side_effect()` とは無関係である。両ファイルの docstring がこの混同を明示的に警告している。統合作業でスケジューラの直列化ロジックに手を入れてはならない。

#### 作業内容
1. registry 版 `is_side_effect()` / `classify_operation_type()` の呼び出し側を repo 全体で grep する。
   - 例: `grep -rn "\.is_side_effect(\|classify_operation_type(" scripts/`
2. 呼び出し側が無ければ両メソッドを dead code として削除する。
3. 呼び出し側があれば helpers 版へ寄せる方針で統合し、registry 版を撤去する。

#### 受け入れ条件
- 副作用判定の出所が helpers 版に一本化されている。
- registry 版 `is_side_effect()` / `classify_operation_type()` が削除、または利用箇所ごと helpers 版へ移行済みである。
- スケジューラの `requires_serial` / `is_write` 経路は無変更である。
- 既存テストが通る。

#### 残作業 (この issue のブロッカー)
- registry 版 2 メソッドの caller grep 結果。dead か現役かでこの issue の作業量が変わる。
