# [Risk] `session.sqlite` has no incremental migration path despite holding non-reindexable data

## Context

`plans/20260819-183436_plan.md` (Design §5, Risks) documents the current
migration-policy asymmetry across the four project databases:

- `workflow.sqlite` — incremental migrations via `apply_workflow_migrations`
  and `_WORKFLOW_MIGRATIONS` (`scripts/db/schema_sql.py:252-294`).
- `rag.sqlite` — recreate-only (`CREATE TABLE IF NOT EXISTS`), acceptable
  because its contents are derived and reindexable from source documents.
- `eventbus.sqlite` — recreate-only (out of scope to change; eventbus
  implementation changes are prohibited by AGENTS.md Global Rule 8).
- `session.sqlite` — recreate-only (`_SESSION_SCHEMA_TEMPLATE`,
  `scripts/db/schema_sql.py:85-144`), but its tables (`sessions`, `messages`,
  `memories`, `memory_links`, `session_diagnostics`) hold conversation history
  and semantic/episodic memory — data that is **not** trivially re-derivable
  the way a RAG index is by re-crawling source documents.

## Risk

If a future change needs to add/alter a column on `sessions`, `messages`,
`memories`, or the other session-schema tables, there is currently no
`apply_*_migrations`-style incremental path (unlike `workflow.sqlite`). The
only mechanism available today is `CREATE TABLE IF NOT EXISTS`, which does
not alter existing tables at all — a genuine schema change would require
either a manual one-off migration script written at that time, or accepting
data loss on recreate, neither of which is documented as the intended
procedure.

## Why this is not resolved in the current plan

`plans/20260819-183436_plan.md` Design §5 explicitly excludes adding a
migration mechanism to RAG/session schemas now, because doing so with no
schema change currently pending would be speculative work
(`skills/require-to-plan/workflow.md` Step 9: "do not include speculative
steps — only steps required by the stated goal"). This issue exists so the
gap is tracked rather than silently dropped.

## Suggested resolution path (for a maintainer to decide, not prescribed here)

One of:
1. Extend the `workflow.sqlite`-style incremental migration mechanism
   (`_WORKFLOW_MIGRATIONS` + `apply_workflow_migrations` pattern) to
   `session.sqlite` proactively, before any concrete schema change is needed.
2. Explicitly accept and document (in `scripts/db/schema_sql.py`'s
   `_SESSION_SCHEMA_TEMPLATE` docstring) that any future `session.sqlite`
   schema change will require a hand-written, one-off migration script at
   that time, with conversation/memory data exported and reimported rather
   than dropped.
3. Defer the decision until the first concrete `session.sqlite` schema change
   is actually proposed, and make the migration-mechanism-vs-recreate
   decision as part of that future requirement/plan cycle.
