# No defined sign-off mechanism for the "higher risk" retry-classification consolidation (sub-task 2)

## Summary
`requires/done/20260813-172533_require.md` splits the `resolve_retryable` cleanup into two
independently schedulable sub-tasks and explicitly gates sub-task 2 (extracting one shared
three-branch classification helper used by both `LlmTransportErrorHandler` and
`LlmReconnectHandler`, in `scripts/shared/llm_transport_errors.py` and
`scripts/shared/llm_reconnect.py`) behind "explicit sign-off before implementation." The
requirement does not say who grants that sign-off, through what channel (a PR review approval, a
comment on the requirement/plan, a separate maintainer message), or what form of record should be
left so a future implementer can point to it when starting sub-task 2.

## Evidence Missing
- No repo convention was found (checked `rules/coding.md`, `rules/toolchain.md`,
  `skills/require-to-plan/SKILL.md`, `skills/python-refactoring/SKILL.md`) for how a
  "requires explicit sign-off before implementation" gate is normally satisfied or recorded in
  this project — e.g., whether a maintainer comment in the issue/plan file counts, or whether it
  must be a separate approval step in a PR.
- This plan (`plans/20260813-190710_plan.md`) therefore scopes sub-task 2 as documented design
  intent only and does not attempt to obtain or simulate sign-off itself, since doing so would
  exceed the document-only, no-source-changes scope of the requirement-to-plan phase.

## Resolution Path
- Before starting sub-task 2's implementation, a maintainer should state explicit approval in one
  of: a comment on this issue, a comment on `plans/20260813-190710_plan.md`, or a new short-lived
  approval note in `issues/` referencing both this issue and the plan. Record whichever channel is
  used here or in the follow-up plan so the precedent is reusable for future two-sub-task
  requirements with a risk-gated second half.
- Once sign-off is recorded, sub-task 2 can be scoped as its own plan (via `require-to-plan` or a
  direct `python-refactoring`/`python-design` pass) using the extraction design already described
  in the requirement's "Implementation intent" §2: a shared three-branch helper with the
  counter-threading signature, called from `LlmReconnectHandler._evaluate_stream_error` in place of
  today's `LlmReconnectHandler.resolve_retryable`.

## Blocking Impact
- Blocks: starting sub-task 2 (the cross-file consolidation) at all — per the requirement's own
  text, this is a hard gate, not a suggestion.
- Does not block: sub-task 1 (deprecation warning on the dead
  `LlmTransportErrorHandler.resolve_retryable`), which this plan schedules independently and which
  has no dependency on sub-task 2 landing first or ever.
