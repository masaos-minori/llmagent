**Title:** [Medium][mcp][agent] Unify tool availability metadata: web-search enabled/disabled_reason, registry rebuild, and include_disabled/disabled_code

**Labels:** enhancement, medium-priority, mcp, agent, consistency
**Covers:** M-1, M-4, L-9
**Area / Component:** `scripts/mcp_servers/web_search/`, `scripts/agent/services/mcp_tool_discovery.py`,
`scripts/shared/runtime_tool_registry.py`, `scripts/mcp_servers/*/server.py` (`/v1/tools`)

## Summary
Three related gaps in the `/v1/tools` availability metadata and its runtime lifecycle are addressed
together: missing `enabled`/`disabled_reason` for web-search, no registry rebuild on `/reload`, and
the unimplemented `include_disabled`/`disabled_code` fields.

## Rationale (Why this matters — detailed)
- **Inconsistent metadata (M-1):** `browser_fetch` declares `config_dependent: true` but does not
  return `enabled`/`disabled_reason` in `/v1/tools`, unlike git/file-read/file-write/file-delete
  which implement them. So the tool appears usable to the LLM even when it will fail (e.g., empty
  domain allowlist), enforcement happens only at call time via `BrowserAuthorizationError`, and
  operators cannot tell from `/v1/tools` alone whether it will work — wasting LLM turns and reducing
  diagnosability. Closing this also closes MCP-002.
- **Stale registry (M-4):** `RuntimeToolRegistry` is built once at startup via
  `McpToolDiscoveryService.discover_all()`. `/reload` calls only `apply_policy()` (policy-derived
  fields) and does not refresh discovery-derived state (`disabled_reason`, `status`). Consequently
  tool availability changes require a full restart, and the `/mcp status` DISABLED_REASON column can
  be stale and misleading.
- **Deferred fields (L-9):** `/v1/tools` accepts no query parameters and always returns all tools;
  the `include_disabled` filter and structured `disabled_code` (MCP-001) are evaluated but
  unimplemented. This is a discoverability gap and an open decision.
- All three concern the **same data path** — how tool availability is exposed via `/v1/tools` and how
  it is loaded into the registry — so a single developer can address them coherently and test them
  together.

## Fix Intent (How — detailed)
- **M-1:** Compute `enabled`/`disabled_reason` per request from the owning server's config state and
  include them in the web-search `/v1/tools` response, matching the other servers. Consider promoting
  `disabled_reason` to a first-class `RuntimeTool` field (currently deferred).
- **M-4:** Add a path to re-fetch `/v1/tools` and rebuild the registry on `/reload` (or a dedicated
  command). If a hot rebuild is out of scope, explicitly document that availability changes require a
  restart and surface staleness in `/mcp status`.
- **L-9:** Implement `include_disabled` (and optionally `disabled_code`) per the deferred plan, or
  record a permanent non-goal decision to remove the ambiguity.

## Sub-tasks
- [ ] (M-1) web-search `enabled`/`disabled_reason` in `/v1/tools`.
- [ ] (M-4) registry rebuild on `/reload` (or documented restart-required + staleness note).
- [ ] (L-9) implement `include_disabled`/`disabled_code`, or document as permanent non-goal.

## Acceptance Criteria
- [ ] web-search `/v1/tools` returns `enabled`/`disabled_reason` consistent with config; MCP-002 can
      be closed.
- [ ] Either `/reload` rebuilds discovery-derived registry state, or docs clearly state
      restart-required and `/mcp status` notes staleness.
- [ ] `include_disabled` implemented with tests, or documented as permanently deferred.
- [ ] Tests cover enabled and disabled (empty allowlist) states.
