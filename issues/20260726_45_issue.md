# Define workflow idempotency and attempt recovery semantics

## Priority

Medium

## Summary

Clarify the meaning of `processed_events` and define recovery behavior for workflow attempts left in `running` state after a crash or process termination.

## Background

`begin_stage_if_new()` inserts a row into `processed_events` and starts an attempt in the `attempts` table.

The workflow engine creates event IDs using a format similar to:

    task_id:stage_id:attempt

This means each retry attempt is treated as a distinct event.

## Problem

`processed_events` is inserted at stage start, not stage completion.

If the process crashes after `processed_events` is inserted but before the attempt is completed, the database can be left with:

- `processed_events` row present
- `attempts.status = running`

This creates ambiguity:

- Does `processed_events` mean "started"?
- Does `processed_events` mean "completed"?
- Should the same attempt be skipped on restart?
- Should a new attempt be started?
- Should the old running attempt be marked failed or halted?

## Implementation Intent

Make workflow idempotency and recovery behavior explicit and testable.

## Required Decisions

### 1. Define the meaning of processed_events

Recommended definition:

`processed_events` means the stage attempt has been started, not necessarily completed.

This matches the current implementation because the row is inserted before stage callback execution finishes.

### 2. Define recovery behavior for running attempts

Recommended startup recovery policy:

1. Find attempts with `status = running`.
2. Determine whether they are stale.
3. Mark stale running attempts as `failed` or `halted`.
4. Record a diagnostic or operational warning.
5. Allow a new attempt if retry policy permits.

### 3. Define task-level recovery behavior

For tasks left in transitional states:

- `pending`
- `running`
- `pending_approval`

Define restart behavior for each state.

Suggested behavior:

- `pending`: safe to fail or restart.
- `running`: inspect attempts and mark stale attempts failed.
- `pending_approval`: preserve and restore approval wait state.

### 4. Document retry/idempotency semantics

Document that retry attempts use distinct event IDs and are therefore distinct idempotency records.

## Acceptance Criteria

- `processed_events` semantics are documented.
- Running attempt recovery behavior is documented.
- Startup recovery behavior is defined for stale running attempts.
- Pending approval tasks are not incorrectly failed during recovery.
- Retry attempt event IDs are documented.
- Tests cover stale running attempt recovery.
- Tests cover retry after failed attempt.
- Tests cover process restart with pending approval.

## Test Cases

- Crash after `processed_events` insert leaves running attempt.
- Startup detects stale running attempt.
- Stale running attempt is marked failed or halted according to chosen policy.
- Retry can create a new event ID with incremented attempt number.
- Pending approval survives restart.
- Completed attempts are not modified by recovery.
