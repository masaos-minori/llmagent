# [HIGH] Establish a unified documentation governance, canonical-source, and review model

## Priority

High

## Background

The documentation set currently contains multiple and partially conflicting rules for determining which source is authoritative.

Depending on the document, authority may be assigned to:

- Runtime source code
- Automated tests
- An approved design document
- The most recently reviewed document
- An area document guide
- A specific specification document
- A source-code directory
- An active configuration file

The governance rules also refer to an area dependency graph that is not currently defined. Review-trigger conditions exist, but their responsible reviewers, approvers, and ownership roles are not sufficiently specified.

## Reason for Change

The current governance model does not always produce a deterministic answer when two sources conflict.

For example:

- Runtime behavior may differ from an approved design decision.
- A recently reviewed document may conflict with a canonical area specification.
- A configuration example may differ from the active configuration.
- A cross-area change may affect documents that are not identified by the current review process.

This ambiguity creates the following risks:

- An implementation AI may update the wrong document.
- Non-canonical documents may continue to contradict the corrected specification.
- Current implementation details may incorrectly overwrite approved design intent.
- Configuration examples may be treated as active values.
- Required reviews may be skipped.
- Cross-area impacts may remain undocumented.

## Intent

Create one project-wide governance model that allows a human reviewer or implementation AI to determine:

- Which source is authoritative
- Which documents must be updated
- Which areas are affected
- Which reviewers and approvers are required
- Whether an unresolved issue blocks a merge
- How observable behavior differs from approved design intent

The governance model must not depend on document recency alone.

## Tasks

### Canonical-Source Precedence

1. Define the following project-wide precedence:

   1. Runtime code and automated tests for observable behavior
   2. Approved ADRs for design intent
   3. Canonical area specifications designated by area document guides
   4. Active configuration files or generated configuration references
   5. Operations and runbook documents
   6. Notes and supporting information
   7. Known Issues and Needs Confirmation records

2. Remove "the most recently reviewed document" as a rule for selecting the canonical source.
3. Explicitly distinguish observable behavior from approved design intent.
4. Define how conflicts between code, ADRs, specifications, and configuration are resolved.

### Area-Specific Canonical Map

5. Create a canonical-source map for:

   - Overview
   - Deployment
   - RAG
   - MCP
   - Agent
   - EventBus
   - Shared/DB
   - Governance

6. For each area, identify:

   - Canonical document guide
   - Canonical specification
   - Implementation entry point
   - Configuration source
   - Operations document
   - Known Issues document

### Dependency and Change Impact

7. Create the missing area dependency graph.
8. Document dependency direction and permitted cycles.
9. Create a change-impact matrix for:

   - Architecture changes
   - Configuration changes
   - Command changes
   - Behavioral changes
   - Schema changes
   - Security changes
   - Documentation-only changes

10. Define which document classes must be updated for each change type.

### Review and Approval Model

11. Define a documentation RACI model.
12. Define required reviewers and approvers for:

   - Governance changes
   - Security changes
   - Database schema changes
   - Public API changes
   - Cross-area changes
   - Deprecations

13. Define conditions for merging changes that contain:

   - Open Known Issues
   - Open Needs Confirmation items
   - Deferred design decisions
   - Temporary implementation deviations

14. Align the governance model with CODEOWNERS or an equivalent ownership mechanism where available.

## Acceptance Criteria

- [ ] One governance document defines the project-wide canonical-source precedence.
- [ ] Document recency is not used as a canonical-source rule.
- [ ] Observable behavior and approved design intent are distinguished.
- [ ] Conflict-resolution rules are deterministic.
- [ ] Every area has exactly one canonical document guide.
- [ ] Every area identifies its implementation entry point.
- [ ] Every area identifies its configuration source.
- [ ] Every area identifies its operations and Known Issues documents.
- [ ] The area dependency graph covers all documentation areas.
- [ ] Dependency direction is explicitly documented.
- [ ] Permitted dependency cycles are documented.
- [ ] The change-impact matrix covers all supported change types.
- [ ] A documentation RACI model is documented.
- [ ] Required reviewers and approvers are defined.
- [ ] Merge conditions for unresolved issues are defined.
- [ ] All area guides link to the unified governance model.
- [ ] Conflicting governance statements are removed.
- [ ] All referenced files and directories exist.
- [ ] Documentation consistency checks pass.

## Validation

1. Select one code-versus-document conflict and verify that the model identifies the authoritative behavioral source.
2. Select one code-versus-ADR conflict and verify that behavioral fact and design intent are handled separately.
3. Select one configuration conflict and verify that active configuration is authoritative.
4. Select one cross-area change and verify that all affected areas are identified.
5. Verify that required reviewers and approvers can be determined without relying on undocumented conventions.

## Out of Scope

- Resolving individual implementation defects
- Changing runtime behavior
- Reorganizing source-code directories
- Migrating individual Known Issues
