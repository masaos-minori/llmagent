# No guard prevents a future GitPython call site from reintroducing the `git.exc.*` pyright false positive

## Priority
Low

## Target files
- `scripts/shared/git_helper.py` and `scripts/mcp_servers/git/git_service.py` (the 2 call
  sites being fixed by `plans/20260813-185356_plan.md`)
- Any future file that adds `import git` and then references `git.exc.<Name>` without also
  adding `import git.exc`

## Background
Discovered while running the requirement-to-plan workflow for
`requires/20260813-141541_require.md` (plan: `plans/20260813-185356_plan.md`), which fixes
the 2 currently-known call sites (3 error lines) of the `git.exc.*` pyright
`reportAttributeAccessIssue` false positive by adding an explicit `import git.exc` alongside
the existing `import git` at each site. The requirement's own Background section already
flags this as "a repeated pattern (same root cause at 2+ call sites), not an isolated typo."

## Problem
The fix is purely import-shape, applied by hand at each of the 2 known call sites. There is
no lint rule, `ast-grep` pattern, or pre-commit hook that would catch a future call site added
via `import git` followed by `git.exc.<Name>` without the accompanying `import git.exc`. A
contributor who copy-pastes the *old* (pre-fix) pattern from git history, another project, or
an LLM-generated snippet would silently reintroduce the same pyright false positive, and it
would only surface the next time someone runs `pyright` broadly and has to re-diagnose a
root cause that is already fully understood today.

## Reason for change
This is a structurally cheap gap to close (a single `ast-grep`/`rg` pattern could flag
`import git` co-occurring with `git.exc.` but not `import git.exc` in the same file), but
doing so is out of scope for `plans/20260813-185356_plan.md`, whose acceptance criteria are
scoped to the 2 currently-known call sites and explicitly exclude adding new tooling/stub
dependencies. Leaving it unfiled would mean the recurrence risk is undocumented once the
current fix lands.

## Suggested resolution
- Add a repo-local constraint check (e.g. alongside the existing `ast-grep` one-liners in
  `rules/coding.md` §Constraint checks) that flags any file matching `import git` where
  `git\.exc\.` appears in the body but `import git.exc` does not — something like:
  `rg -l "git\.exc\." scripts/ | xargs -I{} sh -c 'grep -q "^import git.exc" {} || echo {}'`
  (verify/refine the exact command before wiring it in).
- Optionally wire it into `.pre-commit-config.yaml` as a low-cost hook, mirroring how
  `check-suppression-justification` is wired in per `rules/coding.md`.
- Scope this as its own small requirement/plan since it adds a new constraint-check pattern
  rather than touching `git_helper.py`/`git_service.py` again.
