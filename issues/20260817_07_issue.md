Title: [REFACTOR] Config dataclass cleanup: dead fields, duplicate definitions, validation, defaults
Labels: priority/low, type/refactor, area/config, area/memory

## Summary
Clean up several config inconsistencies concentrated in `config_dataclasses`, `config_builders`, `config_validators`, and `factory`. They share the same files and are best done in one pass.

## Rationale
- Dead field: `AgentConfig.agent_memory_max_startup_snippets` has no build wiring and no reader. Startup injection is bounded by `InjectionPolicy.max_semantic`, which `factory._build_injection_service()` populates from `MemoryConfig.memory_max_inject_semantic`. The field misleads readers into thinking it controls injection.
- Duplicate definition: `security_lockdown_enabled` exists on both `MCPConfig` and `AgentConfig`, but the build path passes the toml value only to `MCPConfig`; the top-level field stays at its default, so which one is authoritative depends on the reader.
- Missing validation: `ToolConfig.progress_stagnation_window` is not validated in `ToolConfig.__post_init__`, unlike the other window fields (e.g. `tool_cycle_detect_window` is checked `>= 0`); a negative value slips through.
- Split validation: some MemoryConfig fields are validated only in the build path (`memory_max_inject_semantic`, `memory_max_inject_episodic`, `memory_embed_timeout_sec`, `memory_retention_days`) and others only in the dataclass (`memory_fts_limit`, `memory_rrf_k`, `memory_recency_days`), so a direct `MemoryConfig(...)` construction skips half the checks.
- Default mismatch: `InjectionPolicy.min_importance` default differs from `MemoryConfig.memory_min_importance`. In production the factory passes the MemoryConfig value, so the mismatch only bites direct `InjectionPolicy()` construction (e.g. tests), but it is a latent surprise.
- Hardcoded asymmetry: `factory._COMPRESS_TEMPERATURE` / `factory._COMPRESS_MAX_TOKENS` are fixed for the `HistoryManager` compression call, while other LLM parameters are configurable via `LLMConfig`.

## Intent
Make the config surface honest and uniform: no dead fields, one authoritative definition per setting, validation independent of construction path, and consistent defaults — so behavior is predictable regardless of how config objects are built.

## Tasks
- [ ] Remove `AgentConfig.agent_memory_max_startup_snippets` and any doc mention of it.
- [ ] Collapse `security_lockdown_enabled` to a single authoritative field (wire the top-level field in the build path, or remove it and update readers to use `MCPConfig`).
- [ ] Add a `>= 0` validator for `progress_stagnation_window` in `config_validators` and wire it into `ToolConfig.__post_init__`, or remove the field if unused.
- [ ] Move the build-path MemoryConfig checks into `MemoryConfig.__post_init__` (or document the two-layer split as intentional).
- [ ] Align `InjectionPolicy.min_importance` default with `MemoryConfig.memory_min_importance`.
- [ ] Decide whether the compression LLM params belong in `LLMConfig`; promote them or document that they are intentionally fixed.
- [ ] Doc updates (coupled to the code above): document `ToolConfig.progress_stagnation_window` (name/purpose only, no default value) and state that `memory_max_inject_semantic` / `memory_max_inject_episodic` / `memory_min_importance` are the effective memory-injection limits.

## Acceptance criteria
- The dead field is gone; build/tests pass; no doc references it.
- Only one `security_lockdown_enabled` is authoritative and all readers use it.
- A negative `progress_stagnation_window` is rejected, or the field is removed.
- Direct `MemoryConfig(...)` construction enforces the same invariants as the build path, or the split is documented as intentional.
- `InjectionPolicy` and `MemoryConfig` start from the same `min_importance`.
- Compression LLM params are either configurable or explicitly documented as fixed.
