# Implementation-order dependency: startup-interruption rollback requires the sibling orphan-subprocess fix to land first

## Priority
Medium

## Target files
- `scripts/agent/startup.py` (`StartupOrchestrator.run()`, lines 67-94 — rollback gating; `_start_servers()`, lines 133-204)
- `plans/20260804-142044_plan.md` (this plan — Risk 1)
- `plans/20260804-140300_plan.md` (sibling plan — Design §2, Implementation step 3)

## Background
`plans/20260804-142044_plan.md` (threading `shutdown_event` through `StartupOrchestrator` so a
`SIGINT`/`SIGTERM` can interrupt the startup sequence) introduces a new exception,
`StartupInterrupted`, raised whenever a shutdown request is observed inside `_start_servers()` or
`_verify_mcp_health()`. By design, this exception is a plain `RuntimeError` subclass with no
special handling: it is meant to flow through `StartupOrchestrator.run()`'s existing
`except Exception as setup_err:` block (`scripts/agent/startup.py:79-89`) so that the *same*
rollback call (`self._ctx.services_required.lifecycle.shutdown_all()`) that handles any other
setup failure also cleans up subprocesses on shutdown-interruption — deliberately avoiding a
second, divergent rollback path, per the requirement's explicit instruction.

However, in the *current* source (verified in Step 3 of the plan-creation cycle), that rollback
call is still gated by a local flag:

```python
_servers_started = False
...
try:
    self._spawned_subprocesses = await self._start_servers()
    _servers_started = True
    ...
except Exception as setup_err:
    if _servers_started:
        try:
            await self._ctx.services_required.lifecycle.shutdown_all()
        ...
```

`_servers_started` is only set `True` *after* `_start_servers()` returns normally. This is exactly
the bug `plans/20260804-140300_plan.md` (the sibling plan, produced from
`requires/done/20260804-131707_require.md`) fixes, by removing the flag and calling
`shutdown_all()` unconditionally inside the `except` block.

## Problem
If `plans/20260804-142044_plan.md`'s changes are implemented and merged *before*
`plans/20260804-140300_plan.md`'s fix, a shutdown request that fires while `_start_servers()` is
still inside its per-server loop (i.e. before it returns and before `_servers_started` would be
set `True`) will raise `StartupInterrupted`, but `run()`'s `except` block will see
`_servers_started == False` and skip `lifecycle.shutdown_all()` entirely — leaving any
already-started subprocess (from an earlier iteration of the same loop) orphaned. This reproduces
the sibling plan's own orphan-subprocess bug, specifically via the new shutdown-interruption code
path this plan adds, in a case the sibling plan's requirement did not anticipate (it was written
against ordinary setup failures, not signal-driven interruption).

This is a genuine implementation-sequencing risk, not something resolvable by source analysis
alone within the `require-to-plan` phase: it depends on a decision made at
`prompts/02_plan-to-implementation-procedure.md` / `prompts/03_implementation.md` time about which
plan's code lands first (or whether both are merged in the same change set).

## Reason for change
Without an explicit note tying these two plans together, a future implementer could reasonably
pick up `plans/20260804-142044_plan.md` in isolation (it is a separate, independently-approved
plan file) and ship it without realizing its correctness silently depends on
`plans/20260804-140300_plan.md` already being merged. The resulting regression (an orphaned
subprocess specifically on the SIGINT/SIGTERM interruption path) would be easy to miss in testing,
since it only manifests when: (a) 2+ MCP servers are configured, (b) a shutdown signal fires while
mid-loop, after at least one server already started successfully.

## Suggested implementation intent
When executing `prompts/02_plan-to-implementation-procedure.md` and
`prompts/03_implementation.md` for either plan, sequence `plans/20260804-140300_plan.md`'s
rollback-gating fix first (or combine both plans' changes into a single implementation procedure /
commit), so that by the time `StartupInterrupted` can be raised, `run()`'s `except` block already
calls `lifecycle.shutdown_all()` unconditionally. If the two plans are processed by independent
implementation cycles, the second one to land must re-verify — via a test exactly like this plan's
"pre-loop-interruption after a first successful server start" scenario — that no orphaned
subprocess results, regardless of merge order.

## Acceptance criteria
- Before `plans/20260804-142044_plan.md`'s `StartupInterrupted`-raising code is merged to a branch
  that will ship, `StartupOrchestrator.run()`'s rollback call is unconditional (i.e.
  `plans/20260804-140300_plan.md`'s fix is already present), OR both changes are landed together.
- A test exists (added under either plan's implementation) covering: 2+ configured servers, the
  1st starts successfully, shutdown fires before the 2nd server's start attempt begins, and
  `lifecycle.shutdown_all()` is asserted to be awaited (i.e. the 1st server's subprocess is not
  orphaned).

## Tests
- `uv run pytest tests/agent/test_startup.py -k TestStartupRollback -v` (or the equivalent renamed
  test class from the sibling plan) must include a case combining shutdown-interruption with a
  partially-completed server loop, and must pass.
