## Residual risk: abandoned `run_in_executor` worker thread on WAL-checkpoint timeout could delay interpreter shutdown

**Priority:** Low

**Source plan:** `plans/20260726-095135_plan.md`
**Source requirement:** `requires/done/20260726-090905_require.md`
**Related target files:** `scripts/agent/repl.py` (`AgentREPL._close_resources()`,
`_wal_checkpoint_sync()`, `_wal_backup_sync()`), `scripts/agent/http_lifecycle.py`
(precedent/comment referenced below)

### Description

The plan wraps `AgentREPL._close_resources()`'s blocking WAL-checkpoint sequence in
`loop.run_in_executor(None, self._wal_checkpoint_sync)` bounded by
`asyncio.wait_for(..., timeout=self._WAL_CHECKPOINT_TIMEOUT_S)` (default `30.0`s), per
the requirement doc's explicit instruction (`requires/done/20260726-090905_require.md`,
Implementation intent / Implementation instructions #1-2).

If the underlying blocking SQLite/OS call inside the worker thread does not return
before the `wait_for` timeout, the coroutine gives up waiting and proceeds — but the
worker thread itself is not cancelled (Python cannot forcibly interrupt a blocking
C-level call from another thread). That thread keeps running in the background as a
live, non-daemon `ThreadPoolExecutor` worker.

This codebase already has a documented precedent for exactly this failure mode:
`scripts/agent/http_lifecycle.py:95-103` (`_wait_exited`) deliberately avoids
`asyncio.to_thread`/executor-wrapping a blocking `proc.wait()` call, with the comment:

> "wrapping a blocking proc.wait() in a thread cannot be cancelled once
> asyncio.wait_for's timeout fires, so a process stuck in an uninterruptible (D) state
> leaves a live, non-daemon ThreadPoolExecutor worker that CPython's
> interpreter-shutdown atexit hook (concurrent.futures.thread._python_exit) then blocks
> on indefinitely."

### Why this plan proceeds anyway

The WAL-checkpoint scenario differs from `proc.wait()` in one material way: every
SQLite call in this path is already bounded to roughly 30 seconds by
`busy_timeout=30000` (`scripts/db/helper.py`'s `apply_connection_pragmas()`) and
`sqlite3.connect(..., timeout=30)` (`SQLiteHelper._connect()`), whereas `proc.wait()`
has no such bound and can hang forever on a zombied/D-state process. So the common-case
risk here is materially lower. However, `busy_timeout` only governs SQLite-level lock
contention (`SQLITE_BUSY`) — it does **not** bound genuine OS/filesystem-level I/O
stalls (e.g. a hung disk, a stalled network filesystem under the DB path, or similar
environmental failures). In that narrower but real class of failure, a
`_wal_checkpoint_sync()` or `_wal_backup_sync()` worker thread could still be abandoned
indefinitely, reproducing the same class of risk `http_lifecycle.py` was written to
avoid.

The plan proceeds with the `run_in_executor` + `wait_for` mechanism anyway because the
requirement doc explicitly and repeatedly directs this exact approach, and because the
risk window is narrower than the `proc.wait()` case it fixes. This issue exists to
track the residual risk explicitly rather than let it go unrecorded.

### Suggested mitigation / follow-up

- Keep `_WAL_CHECKPOINT_TIMEOUT_S` / `_WAL_BACKUP_TIMEOUT_S` comfortably below any
  process supervisor's SIGTERM->SIGKILL grace period, so that even if a worker thread
  is abandoned, the OS-level supervisor still bounds total process shutdown time
  (SIGKILL does not wait for Python's own atexit/thread-join machinery).
- If this is later observed in practice to delay process exit (e.g. via production
  shutdown-latency logs or supervisor SIGKILL events correlating with WAL checkpoint
  timeouts), consider a poll-based alternative similar to `http_lifecycle.py`'s
  `_wait_exited()` (non-blocking status polling with `await asyncio.sleep(...)`
  between checks) instead of `run_in_executor`, if a non-blocking way to probe SQLite
  checkpoint progress can be found — note this is nontrivial since `sqlite3`'s
  synchronous API offers no natural non-blocking polling primitive for an in-progress
  checkpoint, unlike `subprocess.Popen.poll()`.
- No immediate action required before implementing the plan; this is accepted as a
  documented, bounded residual risk, not a blocker.
