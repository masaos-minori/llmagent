# Add Path C for Architectural Refactoring

## Objective

Add a dedicated workflow path for architectural and structural refactoring.

## Reason

Path A and Path B do not adequately cover module movement, responsibility transfer, dependency-direction changes, or module restructuring.

## Intent

Allow architectural refactoring only when its scope, migration, and rollback controls are explicitly defined and approved.

## Tasks

- Add Path C to the path classification.
- Clarify the boundaries between Path A, Path B, and Path C.
- Classify a change as Path C when it includes:
  - module relocation
  - module merge or split
  - responsibility or ownership transfer
  - dependency-direction change
  - architectural boundary change
- Require before implementation:
  - explicit approval
  - affected-file scope
  - current and proposed boundaries
  - migration strategy
  - rollback strategy
  - documentation impact
  - ADR requirement
- Treat an unapproved Path C idea as a proposal only.
- Define an atomic migration group for Path C changes that cannot remain valid when processed one file at a time.
- Prohibit silent expansion of an atomic migration group.

## Out of Scope

- Executing an architectural migration
- Architecture Smell detection
- Deprecated analysis
- Changes to existing validation commands

## Acceptance Criteria

- Path C is clearly distinguished from Path B.
- Path C requires explicit approval.
- Migration and rollback requirements are defined.
- The atomic migration group resolves conflicts with the one-file-at-a-time rule.
- Existing behavior-preservation rules remain mandatory.
