# Risk follow-up: `docs/04_mcp_05_02_auth-profiles-and-sandboxing.md` will describe stale shell-sandbox enforcement once `adr004_07`'s fix lands

## Priority
Low (non-blocking; recorded for traceability per `plans/20260901-104253_plan.md`)

## Context
`plans/20260901-104253_plan.md` (source: `issues/20260831-192510_adr004_07_shell_mcp_sandbox_production_only_enforcement.md`) confirms that `scripts/agent/repl_health.py`'s `audit_security_defaults()` currently conditions its `RuntimeError` for `shell_sandbox_backend == "none"` on `production_mode`, and plans to make it unconditional (REQ-001), rewording only `docs/04_mcp_04_02_file-write-file-delete-shell.md` (the passage the source Issue named) to match (REQ-003).

`docs/04_mcp_05_02_auth-profiles-and-sandboxing.md` also documents the current, pre-fix conditional behavior in at least two places:
- "**Enforcement Point:** `agent/repl_health.py::audit_security_defaults()` raises an exception at startup if `security_profile == "production"` and an HTTP server has an empty `auth_token`. It also warns about `shell_sandbox_backend == "none"` and empty `tool.allowed_tools`."
- A "Sandbox Backend (shell-mcp)" example block: `shell_sandbox_backend = "none"    # WARNING at startup; no isolation` under a `# Development:` comment.

Both passages describe the current warning-only behavior for non-production environments, which will become inaccurate once `plans/20260901-104253_plan.md`'s REQ-001 lands (the check will raise `RuntimeError` unconditionally, not just warn).

## Risk
If `docs/04_mcp_05_02_auth-profiles-and-sandboxing.md` is not updated in the same rollout as `plans/20260901-104253_plan.md`'s code change, it will describe behavior that no longer matches the implementation — a reader following its "Development: ... WARNING at startup; no isolation" example would be misled into believing local/non-production deployments can safely run with `shell_sandbox_backend = "none"` and only get a warning, when startup will actually abort.

## Suggested resolution
Before or shortly after `plans/20260901-104253_plan.md`'s implementation lands:
- Update the "**Enforcement Point:**" sentence in `docs/04_mcp_05_02_auth-profiles-and-sandboxing.md` so it no longer states the shell-sandbox check is warning-only — split it from the `auth_token` sentence if needed, since `auth_token`'s production-conditional enforcement is unaffected by this change and remains accurately described as-is.
- Update the "Sandbox Backend (shell-mcp)" example block so the `# Development:` comment no longer shows `shell_sandbox_backend = "none"` as a warning-only, startable configuration.
- Confirm via `uv run python tools/check_docs_consistency.py --domain mcp` after the edit.
- This is a documentation-only follow-up; it does not require re-opening `plans/20260901-104253_plan.md`'s Implementation Target Files (which are already `Frozen`).
