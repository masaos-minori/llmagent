# Publish ChunkSplitter output atomically with a completion manifest

## Priority
High

## Suggested Labels
priority-high, rag, chunking, manifest, data-integrity

## Reason for Change
The splitter currently treats `{stem}-0000.json` as proof of completion, writes files directly to their final location, continues after individual write failures, and leaves obsolete higher-numbered files when regeneration produces fewer chunks. A partial or stale set can therefore be skipped as complete and later mixed into ingestion.

## Implementation Intent
Make one source document produce one verifiably complete, replaceable artifact set. A failed generation must never replace or masquerade as the previous complete set.

## Affected Files
- `rag/ingestion/chunk_splitter.py`
- `rag/ingestion/pipeline_utils.py`
- manifest model or helper
- splitter integration tests

## Implementation Scope
- [ ] Replace the `0000.json` completion sentinel with a dedicated manifest.
- [ ] Write the complete chunk set into a temporary location on the same filesystem.
- [ ] Validate every generated JSON artifact before publication.
- [ ] Create the manifest only after all chunks have been written and validated.
- [ ] Store at least `schema_version`, `artifact_type`, `source_file`, `source_hash`, `chunk_count`, `chunking_config_hash`, and completion status.
- [ ] Atomically replace the previous published set after validation succeeds.
- [ ] Remove obsolete higher-numbered chunk files as part of replacement.
- [ ] Skip processing only when the manifest exists and its source and configuration hashes match.
- [ ] Treat one write failure as a document-level failure.
- [ ] Leave the prior complete output set intact when regeneration fails.

## Non-Goals
- Do not move database ingestion into ChunkSplitter.
- Do not add legacy artifact migration.
- Do not use the first chunk file as a fallback completion marker.

## Acceptance Criteria
- [ ] A crash after writing one chunk cannot mark the source complete.
- [ ] Regeneration from ten chunks to six publishes exactly six current chunks.
- [ ] A source-content or chunking-configuration change triggers regeneration.
- [ ] A failed regeneration preserves the previous complete set.
- [ ] The manifest count and published contiguous indices agree.

## Required Tests
- [ ] partial write failure
- [ ] process termination simulation
- [ ] ten-to-six regeneration
- [ ] unchanged source/config skip
- [ ] changed source regeneration
- [ ] changed config regeneration
- [ ] manifest corruption

## Common Constraints
- Preserve support for Japanese and English only.
- Embedding dimensions remain fixed in code at 1024 and are not configurable.
- Do not add runtime validation for exactly 1024 embedding elements or a 4096-byte BLOB.
- Do not add migration logic for legacy vector dimensions; recreate databases after canonical schema changes.
- Keep unrelated refactoring out of this issue.
- Update design documentation only when this issue changes the documented contract.
