**Title:** [High][security][mcp][git] Add git-mcp branch/force-push protection, fix risk classification, and correct false security docs

**Labels:** security, high-priority, mcp, git, docs
**Covers:** H-4
**Area / Component:** `scripts/mcp_servers/git/git_service.py`, `git_security.py`, `git_models.py`,
`scripts/agent/tool_policy.py`, `config/agent.toml`, `docs/00_security_02_*`,
`docs/00_governance_07_*`

## Summary
git-mcp write tools (`git_checkout`/`git_pull`/`git_push`) have no branch-level or force-push
protection at the server layer, the agent approval layer enforces only a single-character y/N for
them, and the security policy document falsely claims protections that do not exist.

## Rationale (Why this matters — detailed, all confirmed in source)
- **Server layer has no branch/force guard:** `GitSecurityGuards` (in `git_security.py`) exposes only
  `_check_repo_path` (allowlist prefix) and `_check_write` (a **binary** `read_only` flag).
  `_check_write` returns "allow all writes" whenever `read_only=false`. `git_service.py::_WRITE_TOOLS`
  treats all five write tools uniformly — there is no per-tool branch or force-push branch.
- **Agent approval is weaker than the naming implies:** `tool_safety_tiers` marks
  `git_checkout/pull/push` as `WRITE_DANGEROUS`, but `tool_policy.py::_TIER_TO_RISK` maps
  `WRITE_DANGEROUS → RiskLevel.MEDIUM`, i.e. a single-character y/N prompt — **not** the full-word
  `yes` required by HIGH.
- **Escalation list omits git (confirmed in agent.toml):** `[approval_risk_rules]` explicitly
  escalates the truly dangerous tools to `high` (`delete_file`, `delete_directory`,
  `github_push_files`, `github_delete_file`, `github_merge_pull_request`, `shell_run`) but has **no
  entry for any git_* tool**. So delete_file requires `yes` while git_push requires only `y` — an
  inconsistency baked into the config.
- **Branch protection intent is silently ignored for git:** `approval_high_risk_branches =
  ["main","master","release"]` expresses a clear operator intent, but
  `tool_policy.py::_escalate_for_github_branch` only fires for `github_`-prefixed tools, so
  `git_push`/`git_checkout` targeting `main` are never escalated. `git_push` has no `force` argument
  in its tool definition, so the generic force/overwrite escalation does not apply either.
- **The security document is false:** `00_security_02_high-risk-tool-common-policy.md` states "Git
  MCP: protected_branches and force_push_blocked are additional restrictions (documented in
  04_mcp_04_05_git.md)". No such mechanism exists in code. Worse, the Needs-Confirmation pointer for
  this topic references NC-018, but NC-018 is actually a resolved workflow-approval item, so the
  concern is untracked. The net effect: operators are told main/master/release are protected while in
  practice `git_push branch=main` is approved with a single `y` — a dangerous false sense of safety.

## Fix Intent (How — detailed, staged)
1. **Doc correction (do first, independent of the design decision):** Remove or replace the false
   `protected_branches`/`force_push_blocked` claim for Git MCP in `00_security_02`. Repair the broken
   NC pointer and re-register this concern under a fresh NC id in
   `00_governance_07_needs-confirmation-inventory.md`. Align the ownership-matrix risk tier for git
   write tools with `tool_safety_tiers`.
2. **Immediate mitigation (config-only, low risk):** Add `[approval_risk_rules]` entries
   `git_checkout = "high"`, `git_pull = "high"`, `git_push = "high"` so these operations at least
   require full-word `yes`, matching the treatment of other dangerous writes.
3. **Design decision (owner):** Choose between "local git is user responsibility (no server guard)"
   and "add GitHub-parity protection". If protection is chosen:
   - **Server:** add `protected_branches` (fnmatch) and `force_push_blocked` to `GitConfig`; consume
     them in `_check_write`/handlers for `git_checkout`/`git_push` (which currently receive no
     branch-aware guard).
   - **Agent:** extend `_escalate_for_github_branch` (or add a git-specific escalation) so
     `approval_high_risk_branches` also escalates `git_push`/`git_checkout` targeting protected
     branches.
