## verify_running()がOSプロセスの生存のみ確認し、アプリケーションレベルの健全性を再チェックしない

### Summary

`HttpServerLifecycleManager.verify_running()` は `proc.poll()` によるOSプロセスの生存確認のみを行い、`ensure_ready()` はこの結果だけで「起動が必要か」を判断する。起動直後にはHTTPヘルスチェック(`/health`ポーリング)があるが、実行時の再利用判定にはこのチェックが含まれないため、後になってアプリケーションレベルでハングしたMCPサーバーが「起動済み」として扱われ続ける可能性がある。

### Problem

- `scripts/agent/http_lifecycle.py:148-157` (`verify_running()`):
  ```python
  def verify_running(self, server_key: str) -> bool:
      proc = self._http_procs.get(server_key)
      if proc is None or proc.poll() is not None:
          ...
          return False
      return True
  ```
  `proc.poll()` はOSプロセスが終了しているかどうかのみを確認し、アプリケーション層(HTTPサーバーが応答するかどうか)は一切確認しない。
- `scripts/agent/factory.py:114-136` (`_ServerLifecycleRouter.ensure_ready()`) は `verify_running()` の結果のみで再起動要否を判断し、`True` が返れば以降の処理を行わない。
- 起動直後の `start()`(`scripts/agent/http_lifecycle.py:258-295`)には `/health` へのHTTPポーリングがあるが、これは初回起動時のみに実行され、`ensure_ready()` 経由の再利用判定では再実行されない。

### Affected Files

- `scripts/agent/http_lifecycle.py` — `verify_running()`(148-157行目)、`start()`(258-295行目、比較対象)
- `scripts/agent/factory.py` — `_ServerLifecycleRouter.ensure_ready()`(114-136行目)

### Classification

**Medium** — OSプロセスが生存しているがアプリケーションレベルでハングした場合、プロセス管理層はこれを検知できず、自動復旧の対象にもならない。実際にツール呼び出し側のタイムアウトが発火するまで問題が表面化しない。

### Evidence

- Strongly implied by code (Medium confidence) — ロジック自体は静的に確認済みだが、実際のハングシナリオでの動作確認は未実施。

### Recommended next action

- `Needs confirmation` — 実行時ヘルスチェックの省略が意図的な設計判断(パフォーマンス上の理由等)か確認する。
- 意図的でない場合、`ensure_ready()` 経由の再利用判定に軽量なliveness確認(例: 一定間隔での`/health`再チェック)を追加する設計を検討する。
