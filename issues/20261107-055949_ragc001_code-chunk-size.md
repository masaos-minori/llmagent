# Code chunks are not bounded by max_chunk while text chunks are

## Priority
Medium

## Summary
The English and Japanese text chunkers bound every chunk to `min_chunk <= len <= max_chunk`, but the code chunker lets a single blank-line-separated code block pass through unbounded. A code-heavy corpus can therefore produce one oversized chunk that exceeds the embedding input limit and is silently dropped. Cap code chunks to the same `max_chunk` bound (or formally document the exemption) and pin it with a test.

## Background
`ChunkSplitter` composes `ChunkEnglishMixin` and `ChunkJapaneseMixin` via multiple inheritance. Both text paths route through buffer accumulators that enforce `max_chunk`; the code path routes through `merge_text_items` in `scripts/rag/ingestion/chunk_utils.py`, whose `else: buf = item` branch accepts a single item larger than `max_chunk` without splitting. The canonical chunksplitter doc lists code only under "empty line splitting" and never mentions `max_chunk` for code, so the asymmetry is undocumented as a choice. `config/chunk_splitter.toml` already marks the whole sizing area an "unvalidated heuristic, pending performance tuning" (see archived `issues/done/20260927-211412_nc034_confirm-rationale-for-chunk-size-bounds.md`), so this sits inside an area the owner has accepted as unvalidated.

## Problem
- `merge_text_items` (`scripts/rag/ingestion/chunk_utils.py`) enforces `min_chunk` at the tail but has no upper guard: a single `item` longer than `max_chunk` falls into the `else: buf = item` branch and is emitted as-is.
- `_chunk_code` (`scripts/rag/ingestion/chunk_splitter.py`) calls `merge_text_items` with the real `min_chunk`/`max_chunk`, so a `.py`-style source with few blank lines and long lines yields one code chunk larger than `max_chunk`.
- `EmbeddingService.get_embedding` returns `None` on network failure or empty input; `embed_and_store` maps that to `EMBEDDING_FAILED` and the chunk is dropped. An oversized code chunk that exceeds the embedding model's input length fails the same way, so a real ingestion run can report success while dropping the largest code chunks.

## Reason for Change
Text and code are treated inconsistently under the same sizing policy: text is always capped, code is not. For a repository whose corpus is largely source code, this produces the largest chunks precisely for the content type most likely to contain long single-line blocks. The fix is small and reversible, and it removes an untested assumption about code-chunk size.

## Implementation Intent
Extend the `max_chunk` upper guard in `merge_text_items` so a single item longer than `max_chunk` is split (for code, at whitespace or a fixed character boundary rather than sentence morphology) rather than passed through whole, OR keep the current empty-line-only behavior but document it as an intentional, tested exemption with a comment at the `else` branch. Prefer capping code to match text unless the owner prefers the documented-exemption path. Preserve `min_chunk` semantics, the `\n\n` separator, and overlap behavior. Do not change the text chunkers' algorithm.

## Required Changes
- Ensure a single code item longer than `max_chunk` never produces a chunk longer than `max_chunk`, or add an explicit, commented intentional-exemption decision.
- Add a unit test asserting `merge_text_items` caps a single oversized item to `max_chunk` (or asserts the documented exemption).
- Add a chunk_splitter-level test that a long single-line code block yields chunks within `max_chunk`.
- If the exemption path is chosen, add a one-line note in the chunksplitter doc's strategy table that code is intentionally exempt from `max_chunk`.

## Constraints
- Do not change the English/Japanese text chunking algorithm or its `max_chunk` behavior.
- Preserve `merge_text_items`'s existing `min_chunk` tail-merge and `chunk_overlap` behavior for normal-sized items.
- Any code split MUST NOT apply stopword removal or Sudachi morphological analysis (code stays language-independent).
- Do not alter the crawl/chunk artifact contract or `read_chunk_json`.
