# ROLE_KEY_WHITELIST does not cover all LLMMessage TypedDict fields

## Priority

Low

## Summary

While planning the `validate_message()` wiring work
(`plans/20260726-093008_plan.md`, source requirement
`requires/done/20260726-085634_require.md`), a schema/type mismatch was found between
`scripts/agent/message_schema.py`'s `ROLE_KEY_WHITELIST` and the `LLMMessage` TypedDict
in `scripts/shared/types.py` (L17-29).

`LLMMessage` declares `name`, `importance`, and `pinned` as valid optional fields (the
latter two are read by `scripts/agent/history_selection_policy.py`'s
`classify_importance()` — `msg.get("pinned", False)` / `msg.get("importance")` — to
prioritize which messages survive history compression). None of these three fields
appear in any `ROLE_KEY_WHITELIST` entry (`system`, `user`, `assistant`, `tool`) in
`scripts/agent/message_schema.py` (L26-31).

## Current impact

None today: a repo-wide check during planning confirmed no current call site that
constructs a `ctx.conv.history` message sets `pinned`, `importance`, or `name` on it
(those fields are only ever set on unrelated `agent/memory/*.py` record dataclasses,
not on conversation-history message dicts). So wiring `validate_message()` into the
append path, as planned, will not break any existing behavior.

## Future risk

If a future change starts setting `pinned` or `importance` directly on a
`ctx.conv.history` message (e.g. to protect a message from compression), the
newly-wired validation would treat those as "Unexpected keys" and either reject the
message or strip the field — silently degrading `history_selection_policy`'s
compression-priority behavior, since `classify_importance()` would then always see
`msg.get("pinned")` / `msg.get("importance")` as absent.

## Recommendation

Decide, in a follow-up (not in the `validate_message()`-wiring pass — that work is
explicitly scoped to leave `ROLE_KEY_WHITELIST`/`TRUSTED_SOURCES` unchanged unless a
genuine need is found), whether to:

- extend `ROLE_KEY_WHITELIST` to include `name`/`importance`/`pinned` where
  appropriate per role, or
- reconcile `LLMMessage`'s TypedDict fields down to what the schema actually
  supports, removing the unused optional fields.

In the interim, the append-path implementation should log a `warning` (not fail
silently) whenever `validate_message()` causes a key to be stripped, so any future
regression from this mismatch is visible in logs immediately rather than causing a
silent behavior change.
