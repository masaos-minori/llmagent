# `llm_turn_runner.py::_filter_disabled_tool_definitions()` still sources the LLM-facing tool list from `ctx.cfg.tool.tool_definitions`, not `RuntimeToolRegistry`

## Priority
Medium

## Summary
`scripts/agent/llm_turn_runner.py:207-223,282` builds the tool-definitions payload sent to the LLM
by starting from `ctx.cfg.tool.tool_definitions` (the static, config-driven list) and filtering out
names the `RuntimeToolRegistry` marks as not visible for LLM use. This is a genuine runtime
dependency on the static list — not a display/count-only read — even though the *execution* path
(argument validation, scheduling, approval) is being migrated to treat `RuntimeToolRegistry` as the
sole runtime authority by the sibling requirements `requires/done/20260813-140532_require.md` and
`requires/20260813-140801_require.md`.

## Target files
- `scripts/agent/llm_turn_runner.py` — `_filter_disabled_tool_definitions()` (lines 207-223) and its
  call site in `_stream_llm()` (line 282)
- `scripts/shared/runtime_tool_registry.py` — `RuntimeToolRegistry.llm_tool_definitions()`
  (lines 112-126), which already returns the LLM-facing shape (`name`, `description`,
  `parameters`) keyed off `enabled_for_llm`, and could serve as the base list directly instead of
  being used only as a name-visibility filter over the static list.

## Background
Discovered while running the requirement-to-plan workflow for
`requires/20260813-140801_require.md` (plan: `plans/20260813-184037_plan.md`), during the mandated
audit of every remaining `ctx.cfg.tool.tool_definitions` reference under `scripts/agent/`. That
requirement's acceptance criteria and its 9 numbered implementation instructions are scoped to the
call-execution path (`_validate_tool_args()`, `_build_tool_meta()`, approval ordering) and do not
mention `llm_turn_runner.py`'s tool-list construction, so fixing it there was explicitly out of
scope for that plan (see its Unknowns UNK-03 and Risks section).

## Problem
- `_filter_disabled_tool_definitions()` takes `tool_definitions: list[dict[str, Any]]` — sourced
  from `ctx.cfg.tool.tool_definitions` — and only *removes* entries whose name is known to the
  registry but not currently `enabled_for_llm`. It does not add or correct anything from the
  registry; the base content (schema, description) for every tool still comes from the static
  config list.
- If a tool is registered live (via `/v1/tools` discovery) but was never added to
  `ctx.cfg.tool.tool_definitions` (or the static entry has a stale/incorrect schema), the LLM either
  never sees that tool as callable, or sees a schema that has drifted from what
  `RuntimeToolRegistry`/`RuntimeTool.input_schema` actually validates against at call time — a
  second source of truth for tool *shape*, parallel to the one the sibling requirements are removing
  for tool *execution*.
- `RuntimeToolRegistry.llm_tool_definitions()` already exists and returns the correct LLM-facing
  shape derived from live discovery, but is currently used only as a name-visibility filter, not as
  the source of tool content.

## Reason for change
Once the execution path (this requirement and its sibling) treats `RuntimeToolRegistry` as the sole
runtime authority for tool metadata, leaving the LLM-payload construction on a separate static
source undermines that guarantee in a way that's easy to miss: a reader auditing
`ctx.cfg.tool.tool_definitions` usages after those requirements ship could reasonably (and
incorrectly) conclude the field is fully inert at runtime, when it is still load-bearing for what
tools the LLM is told it can call.

## Suggested resolution
- Change `_filter_disabled_tool_definitions()` (or its call site) to build the LLM payload directly
  from `registry.llm_tool_definitions()` when the registry is available, keeping
  `ctx.cfg.tool.tool_definitions` only as the fallback for the case the registry is `None`/empty
  (mirroring the existing early-return in `_filter_disabled_tool_definitions()` when
  `registry is None`).
- Add a regression test asserting that a tool present in `RuntimeToolRegistry` but absent from
  `ctx.cfg.tool.tool_definitions` is still offered to the LLM once this is fixed (currently it would
  not be, since the static list is the starting point).
- Scope this as its own requirement/plan — it changes what tools the LLM is offered mid-session,
  which is a user-visible behavior change distinct from the fail-closed execution-path work, and
  should get its own acceptance criteria and test plan rather than being folded into an unrelated
  change.
