# No defined grace-period duration for `LlmTransportErrorHandler.resolve_retryable`'s deprecation before removal

## Summary
`requires/done/20260813-172533_require.md` (implementation intent, sub-task 1) directs adding a
`DeprecationWarning` to `LlmTransportErrorHandler.resolve_retryable` in
`scripts/shared/llm_transport_errors.py` "for a grace period" before outright removal "in a later
change." The requirement does not state how long that grace period is, nor what event (elapsed
time, a release tag, a second explicit sign-off) triggers the follow-up removal change. Without a
defined trigger, the deprecated method plus its dedicated `TestResolveRetryable` test class in
`tests/shared/test_llm_transport_errors.py` could be left in the "warns but still present" state
indefinitely, which is exactly the kind of stale-dead-code state this requirement was raised to
eliminate.

## Evidence Missing
- `rg -n "grace period|deprecat" requires/done/20260813-172533_require.md rules/*.md
  skills/python-refactoring/SKILL.md` was checked; `skills/python-refactoring/SKILL.md` documents
  the "retain deprecated aliases" convention referenced by the requirement but (per the
  requirement's own citation) does not itself specify a standard duration — the requirement points
  to it only for the pattern (emit `DeprecationWarning`, keep old symbol working), not a timebox.
- No repository-wide policy document (checked `rules/coding.md`, `rules/toolchain.md`) defines a
  standard deprecation-to-removal interval (e.g., "one release", "30 days", "next major version").

## Resolution Path
- When implementing sub-task 1 (see `plans/20260813-190710_plan.md`, Implementation Steps, Phase
  2), ask a maintainer to confirm a concrete removal trigger — e.g., "remove once this warning has
  shipped in one deploy cycle with zero new callers appearing in `rg` checks" — and record that
  decision either as a code comment near the `warnings.warn` call or as a follow-up issue with a
  target date/condition.
- Alternatively, adopt a repo-wide default (e.g., "deprecated symbols are removed the next time
  `plans/` touches the same file for an unrelated reason, provided a zero-caller `rg` re-check
  still holds") and document it in `rules/coding.md` so future deprecations don't hit the same gap.

## Blocking Impact
- Not blocking: sub-task 1 (adding the `DeprecationWarning` itself) can proceed without this being
  resolved — the warning is added, the tests are adjusted, and the method remains callable exactly
  as today.
- Blocks only the *follow-up* removal change (deleting
  `LlmTransportErrorHandler.resolve_retryable` and `TestResolveRetryable` outright) from being
  scheduled with a concrete trigger condition; until resolved, that follow-up has no clear "now is
  the time" signal.
