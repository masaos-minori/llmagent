# Correct ToolRegistry/tool_constants docstrings to reflect verified production usage beyond drift validation

## Priority
Medium

## Target files
- `scripts/shared/tool_registry.py` (module docstring, `ToolRegistry` class docstring)
- `scripts/shared/tool_constants.py` (module docstring)
- `docs/04_mcp_03_02_tool-registry.md` (out of scope for this documentation-only requirement-drafting

## Background
`RuntimeToolRegistry` (populated from live `/v1/tools` discovery) is the sole runtime *routing*
authority. Given that migration, `scripts/shared/tool_registry.py`'s module docstring narrows
`ToolRegistry`'s remaining production role to a single sentence: "ToolRegistry now serves only as:
(a) drift-detection input for McpToolDiscoveryService." Similarly, `scripts/shared/tool_constants.py`'s
module docstring states that once `RuntimeToolRegistry` supplies live tool schemas, its frozensets
"become fallback/compatibility data for registry seed, side-effect detection, and risk
classification — never the first-checked source."

This requirement was scoped out of the two prior, related requirements already on file:
- `requires/20260818-223204_require.md` (removes `ToolRouteResolver`'s dead `server_configs`/
  `discovery_map`/`known_tools` constructor arguments and `_log_routing_coverage()`).
- `requires/20260818-223342_require.md` (removes `RuntimeToolRegistry.is_side_effect()`/
  `classify_operation_type()` as dead duplicate methods, concluding that
  `shared.tool_executor_helpers.is_side_effect()` — the frozenset-based classifier — remains the
  sole, surviving side-effect classifier used by `ToolExecutor.execute()`).

Neither of those two requirements touches `tool_registry.py`'s or `tool_constants.py`'s module
docstrings, or the `agent/tool_policy.py` risk-classification call path. This requirement is scoped
specifically to that gap.

## Problem
Verified directly against current source:

1. **`ToolRegistry` is not "drift-detection input" only.** `scripts/agent/tool_policy.py:54-71`
   defines the production `classify_operation_type()` free function (imported and called by
   `scripts/agent/repository_gateway.py:84` and `scripts/agent/tool_audit.py:52,183`, and covered by
   `tests/agent/test_tool_policy*.py`/`test_tool_approval_risk.py` — this is the *different*,
   unrelated symbol from the now-deleted `RuntimeToolRegistry.classify_operation_type()` method
   addressed by `requires/20260818-223342_require.md`; it must not be confused with it). At line 69,
   this function calls `get_registry().get_all_tool_names()` as a fail-safe membership check: a tool
   name not found in `ToolRegistry` is classified `OperationType.UNKNOWN` rather than `READ`. This
   runs on the live per-call risk-classification path that feeds real approval-gating decisions —
   it is not a startup drift/validation check. The module docstring's claim that `ToolRegistry`
   "serves only as... drift-detection input" is therefore factually incomplete: it omits this second,
   functionally load-bearing production consumer.
   - By contrast, the other two production callers of `get_registry().get_all_tool_names()` —
     `scripts/shared/production_config_validator.py:31-44` (`_resolve_known_tools()`, feeding
     `_check_missing_tool_safety_tiers()`/`_check_unknown_tool_safety_tiers()`) and
     `scripts/agent/repl_health.py:561-568` (feeding `ProductionConfigValidator().validate()`) — are
     genuinely drift/config-validation checks (tool_safety_tiers coverage vs. the registry), and are
     accurately described by the current docstring framing. Only the `tool_policy.py:69` use is
     misclassified.

2. **`tool_constants.py` frozensets are not accurately described as "fallback... never the
   first-checked source" for two of the three stated use cases.** Verified usages:
   - Side-effect detection: `scripts/shared/tool_executor_helpers.py`'s `_SIDE_EFFECT_TOOLS`
     (built from `WRITE_TOOLS | DELETE_TOOLS | {"shell_run"} | GIT_WRITE_TOOLS | GITHUB_WRITE_TOOLS
     | GITHUB_DANGEROUS_TOOLS | CICD_WRITE_TOOLS | RAG_WRITE_TOOLS | MDQ_WRITE_TOOLS`) drives
     `is_side_effect()`, the sole TTL-cache-bypass classifier consulted by
     `ToolExecutor.execute()` (`scripts/shared/tool_executor.py:234`). Per
     `requires/20260818-223342_require.md`'s conclusion, the only other candidate classifier
     (`RuntimeToolRegistry.is_side_effect()`) had zero production callers and is being deleted as
     dead code — meaning the frozenset-based classifier was never actually a fallback for
     anything in production; it has always been the only classifier consulted.
   - Risk classification: `scripts/agent/tool_policy.py:41-71`'s `classify_operation_type()` uses
     `_ALL_WRITE_TOOLS` (built from `WRITE_TOOLS | MDQ_WRITE_TOOLS | RAG_WRITE_TOOLS |
     CICD_WRITE_TOOLS | GIT_WRITE_TOOLS`), `DELETE_TOOLS`, `_EXEC_TOOLS`, and
     `_GITHUB_MUTATION_TOOLS` (`GITHUB_WRITE_TOOLS | GITHUB_DANGEROUS_TOOLS`) as the direct,
     first-checked classification tiers — there is no other, richer live source these fall back
     from; they are the primary and only mechanism for the WRITE/DELETE/EXECUTE/API_WRITE
     distinction.
   - The "fallback/compatibility... never first-checked" framing is accurate only for the third
     stated use case, registry seed data (`tool_registry.py`'s `_populate_default_registry()`,
     which imports these frozensets once at import time to populate `ToolRegistry`).

3. **The issue's open decision — whether to maintain or abolish drift validation
   (`validate_routing_against_config`/`validate_routing_against_live`/`validate_all_routing`/
   `check_tool_safety_tiers`/`check_unknown_tool_safety_tiers`) — is already resolvable from current
   evidence and does not require further design work.** Grep confirms these are live, wired-in
   production checks, not dead code:
   - `validate_routing_against_config()` — called from `scripts/agent/repl_health.py:405`.
   - `validate_routing_against_live()` — called from
     `scripts/agent/services/mcp_tool_discovery.py:371`.
   - `check_tool_safety_tiers()` — called from `scripts/agent/repl_health.py:430`.
   - `check_unknown_tool_safety_tiers()` — mirrored by
     `production_config_validator.py:_check_unknown_tool_safety_tiers()`, called from
     `repl_health.py:117` (via `ProductionConfigValidator().validate()`).
   - Each function is also covered by dedicated tests (`tests/shared/test_tool_registry.py`,
     `tests/shared/test_tool_safety_tiers.py`, `tests/agent/test_startup_routing_drift.py`,
     `tests/mcp_servers/cicd/test_tool_server_layer_consistency.py`).
   - `docs/04_mcp_03_02_tool-registry.md` and `docs/04_mcp_03_05_lifecycle-and-new-server.md`
     already document these as intentional, wired-in startup validation. Only `validate_all_routing()`
     (the combined convenience wrapper) is noted there as "not yet wired in" — the two functions it
     wraps are independently wired in already.
   - Given active, tested, production wiring with no dead-code signal, and given that `ToolRegistry`
     also has the load-bearing `tool_policy.py:69` dependency described in Problem #1, abolishing
     `ToolRegistry`/config `tool_names`/`tool_routing_validation.py` is not warranted. The correct
     resolution of the issue's "maintain vs. abolish" question is: **maintain**.

Because the "maintain" decision is answered by direct evidence and item 2 of the issue's own work
plan ("if maintaining, only tighten wording to 'validation-only'") is not fully correct — `ToolRegistry`
is not validation-only, per Problem #1 — the next-phase change should not merely restate
"validation-only" more firmly. It should correct the docstrings to name both real production roles
accurately.

## Reason for change
A shared, security-relevant module's docstring that under-describes its own blast radius is a latent
risk: a future maintainer reading "ToolRegistry serves only as drift-detection input" could
reasonably conclude it is safe to gate `ToolRegistry` behind a feature flag, make its population
best-effort/lazy, or remove it once live discovery is fully trusted — any of which would silently
break `tool_policy.classify_operation_type()`'s READ-vs-UNKNOWN fail-safe and could downgrade a
should-be-UNKNOWN tool call to READ risk. Likewise, `tool_constants.py`'s "fallback... never
first-checked" framing invites a future maintainer to treat the frozensets as low-priority,
removable-if-inconvenient data, when in fact they are the sole, first-checked mechanism for both
side-effect detection and write/delete/execute risk classification today. Fixing the docstrings to
match verified reality removes this drift risk without changing any runtime behavior.

## Implementation intent
Update the two module/class docstrings so they enumerate `ToolRegistry`'s and the frozensets'
actual, verified production consumers, rather than a single narrowed characterization. Do not change
any runtime logic, function signatures, or test behavior — this is a documentation-accuracy fix
confined to docstrings (and, if still inconsistent afterward, the corresponding reference doc). Do
not re-litigate or restate the "maintain vs. abolish" question as still open; state plainly that
drift validation and `ToolRegistry` are being kept because they are actively used in production,
citing the call sites.
