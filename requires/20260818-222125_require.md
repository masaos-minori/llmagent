## Background

The system already has two independent, canonical approval layers (ADR-001, documented in `docs/05_agent_06_04_tool-execution-and-approval-canonical.md`):

- Tool-level approval (`agent/tool_approval.py`): always active, per-tool-call, gated by risk tier (`READ_ONLY` / `WRITE_SAFE` / `WRITE_DANGEROUS` / `ADMIN`), documented with a full risk-tier table in `docs/04_mcp_05_03_fail-open-fail-closed-and-risk-tiers.md`.
- Workflow-level approval (`agent/workflow/workflow_engine.py`): a task-level human gate between the `execute` and `verify` stages, controlled by `WorkflowDef.require_approval` (default `false` in `config/workflows/default.json`).

Verification against current docs and code confirms:

- The claim that current wording conflates "workflow execution is mandatory" with "approval is mandatory" does **not** hold today: `docs/01_overview-arch-02-pipelines.md` (lines ~63-69) and `docs/02_deployment.md` (lines ~158-183) already state clearly that workflow execution/deployment is mandatory while `require_approval` is a separate, optional, default-`false` config field. This part of the original issue is stale and is excluded from this requirement.
- What remains genuinely undefined:
  - The workflow-level approval gate's own doc (`docs/05_agent_03_03_...`) explicitly marks its `require_approval` default behavior as "Needs Confirmation / 未決事項" — an open, unresolved question about whether disabling approval by default in production is intentional.
  - There is no documented mapping from operation category (file writes, file deletion, shell execution, git commits/pushes, GitHub changes, CI/CD execution, database maintenance) to a *workflow-level* approval requirement. The existing risk-tier table in `docs/04_mcp_05_03_...` covers only the tool-level y/N-vs-`yes` prompt, not the task-level human approval gate.
  - `approval_ops.py` implements an approval expiration TTL (`_APPROVAL_TTL_HOURS`, `expires_at`) that is not documented anywhere in `docs/`.
  - No `/cancel` command exists for `cmd_workflow.py`; only `/approve` and `/reject`. Cancellation behavior is neither implemented nor documented as intentionally unsupported.
  - No local-development exception is documented specifically for the workflow-level approval gate (as distinct from the unrelated tier-validation severity rules already documented in `docs/04_mcp_05_03_...`, which only cover missing `tool_safety_tiers` entries, not approval policy itself).
  - No automated tests exercise approval expiration or a cancellation path.

Note: a separate, already-drafted requirement (`requires/20260818-221156_require.md`, sourced from `issues/20260818_06_issue.md`) targets consolidating the *tool-level* MCP risk-tier/approval documentation into a single cross-cutting policy document. This requirement is scoped to the distinct, currently-undocumented *workflow-level* (task/execute-stage) approval gate and its production policy — implementers should cross-reference rather than duplicate that other requirement's content.

## Problem

The workflow-level human approval gate (`require_approval`) has no defined production policy: which operation categories should require it, how it maps to risk tiers, what applies differently in local development, and what its full lifecycle (approve / reject / expire / missing / cancel / resume) is. The one existing self-flagged ambiguity (default `false` in production) has stood undecided across multiple prior doc passes.

## Reason for change

The system already performs high-impact operations (file writes/deletion, shell execution, git/GitHub changes, CI/CD triggers, and — per the current gap — undocumented database maintenance actions) through this same execution path. Leaving the workflow-level approval policy undefined means: (a) the standing "Needs Confirmation" item can never be closed, (b) an operator cannot verify whether a given operation category is required to pause for human approval in production, and (c) the expiration and (absent) cancellation behavior are unverifiable and untested. Resolving this now prevents the ambiguity from being copy-pasted into future workflow definitions.

## Implementation intent

Produce a single authoritative policy — expressed in `docs/05_agent_03_03_turn-processing-flow-workflow-engine.md` (with cross-references from `docs/02_deployment.md` and `docs/01_overview-arch-02-pipelines.md`) — that:

1. Resolves the existing "Needs Confirmation" item: state explicitly whether `require_approval=true` is required for production deployments, and for which operation categories, rather than leaving the current default silently in place.
2. Maps each of the seven listed operation categories (file writes, file deletion, shell execution, git commits/pushes, GitHub changes, CI/CD execution, database maintenance) to a required workflow-level approval tier, referencing the existing tool-level risk tiers in `docs/04_mcp_05_03_...` rather than re-deriving them.
3. Defines local-development exceptions explicitly (e.g., which categories may skip the workflow-level gate outside production, consistent with the existing `security_profile` local/production distinction used elsewhere in the docs).
4. Documents the full approval lifecycle: approve, reject, expire (using the existing `expires_at`/TTL mechanism in `approval_ops.py`), missing-approval (new record created, workflow pauses), cancellation (decide and document whether a `/cancel` command should be added, or explicitly document that cancellation is unsupported and rejection is the only termination path), and resume (existing-task re-evaluation on next turn).
5. Ensures `config/workflows/default.json` (or documented per-environment overrides) actually enforces whatever policy is decided, rather than leaving `require_approval` implicitly `false` with no environment-specific override path.

This is a documentation-and-policy-decision task; it may also require a small config/schema change (e.g., adding cancellation support or a production override for `require_approval`) if the decided policy cannot be expressed through existing configuration alone — that decision belongs to the next phase (`require-to-plan`).

## Implementation instructions

1. Read `docs/05_agent_03_03_turn-processing-flow-workflow-engine.md` in full and replace the "Needs Confirmation / 未決事項" note with a decided, stated policy (do not leave it open without escalating the decision explicitly if it truly cannot be resolved from existing evidence).
2. Add a table mapping the seven operation categories to: required workflow-level approval (yes/no/conditional), the referenced tool-level risk tier (cross-link to `docs/04_mcp_05_03_...`), and any category-specific notes (e.g., database maintenance currently has no MCP tool or risk-tier entry at all — flag this gap explicitly if no such tool exists yet, rather than inventing one).

5. Document local-development exceptions for the workflow-level gate distinctly from the tool-level tier-validation severity rules already documented in `docs/04_mcp_05_03_...`.
6. Cross-link `docs/02_deployment.md` and `docs/01_overview-arch-02-pipelines.md` to the updated section rather than duplicating the policy text.
