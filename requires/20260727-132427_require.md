# Clarify or fix the unconditional firejail-binary-missing fatal check in audit_security_defaults()

## Priority

Low

## Target Files

- `scripts/agent/repl_health.py:516-521` — firejail binary presence check inside `audit_security_defaults()`

## Background

`audit_security_defaults()` in `scripts/agent/repl_health.py` implements a consistent security-audit pattern: most violations (missing `auth_token` on HTTP MCP servers, `sandbox_backend == "none"`, empty `command_allowlist`, etc.) are only fatal (`raise RuntimeError`) when `production_mode` is true; in local/dev mode they are downgraded to a logged warning appended to the returned `warnings` list.

The check for a missing `firejail` binary when `shell_cfg.sandbox_backend == "firejail"` does not follow this pattern:

```python
if shell_cfg.sandbox_backend == "firejail" and not _shutil.which("firejail"):
    msg = (
        "shell_sandbox_backend=firejail but firejail binary not found in PATH. "
        "Install firejail or change shell_sandbox_backend in shell_mcp_server.toml."
    )
    raise RuntimeError(msg)
```

This unconditionally raises regardless of `production_mode`, so a local developer who has `sandbox_backend = "firejail"` configured in `shell_mcp_server.toml` but does not have `firejail` installed cannot start the agent at all — unlike every other security check in the same function, which would only warn in this situation.

## Problem

The asymmetry is undocumented: there is no comment in the code explaining why this specific check is exempt from the `production_mode`-gated fatal/warning pattern used everywhere else in `audit_security_defaults()`. This makes it ambiguous whether the unconditional raise is an intentional security decision (a configured-but-non-functional sandbox backend is inherently unsafe to run with, even locally) or an oversight where the `production_mode` branch was simply forgotten.

## Reason for Change

Undocumented inconsistencies in security-critical code are a maintenance and audit risk: future readers/maintainers cannot tell whether behavior is deliberate or a bug, and local developers are blocked from starting the agent with no way to downgrade the failure to a warning, unlike for other similarly-severe misconfigurations.

## Implementation Intent

Resolve the ambiguity explicitly, choosing one of two consistent outcomes:

- Option A (keep behavior, document intent): If the unconditional fatal check is intentional — because a `sandbox_backend` configured as `firejail` but non-functional (binary missing) means shell commands would silently run unsandboxed, which is unacceptable in any environment — add a code comment directly above the check explaining this reasoning, so the asymmetry is self-evident and not mistaken for a bug in future reviews.
- Option B (align with existing pattern): If the asymmetry is unintentional, make this check follow the same `production_mode`-gated pattern as the other checks in the function: raise `RuntimeError` when `production_mode` is true, and log a warning (appended to `warnings`) when it is false, allowing local development to proceed with a visible warning.

The concrete choice between Option A and Option B should be made by whoever owns this security module's design intent (not inferable from source alone); this requirement documents both acceptable resolutions so the implementer can pick the one consistent with the module's actual security posture.
