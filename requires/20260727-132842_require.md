# Graceful shutdown timeout is not applied to a turn already in flight when the signal arrives

## Priority

High

## Target Files

- `scripts/agent/repl.py:462-502` (`_repl_loop`) — the `asyncio.wait_for` timeout is fixed at the moment it is scheduled and never re-evaluated
- `scripts/agent/repl.py:665-690` (`_sigterm_handler`) — comment incorrectly assumes the graceful timeout applies to the currently active turn

## Background

- `_repl_loop()` reads one line per iteration, then dispatches it via
  `asyncio.wait_for(self._dispatch_line(line, ctx), timeout=_GRACEFUL_TIMEOUT if ctx.conv.shutdown_requested else None)`.
- The intent (per `_sigterm_handler`'s comment) is: on SIGTERM/SIGINT, the current
  turn should be allowed at most `_GRACEFUL_TIMEOUT` (10.0s) to finish before the
  process forces an exit, so the REPL shuts down within a bounded grace period.

## Problem

- The `timeout=` argument to `asyncio.wait_for` is evaluated once, at the instant
  the call is made, using whatever `ctx.conv.shutdown_requested` is at that time.
  It is not re-checked afterward — `asyncio.wait_for` has no mechanism to change
  a running wait's timeout.
- If SIGTERM/SIGINT arrives after a turn has already started dispatching (i.e.
  after line 488's `asyncio.wait_for` call has been made with `shutdown_requested`
  still `False` at that instant, so `timeout=None`), then `_sigterm_handler` sets
  `shutdown_requested = True`, but the in-flight `wait_for(..., timeout=None)` is
  unaffected and continues to wait indefinitely.
- `_sigterm_handler`'s comment (lines 676-680) states that `_repl_loop()` "already
  checks shutdown_requested after each turn and applies the `_GRACEFUL_TIMEOUT`
  wait to end the turn" — this is only true for turns that start **after** the
  signal was received, not the turn that was already running when the signal
  arrived.
- Net effect: a turn whose LLM call or tool execution hangs, and which happened
  to be in flight at the moment of the shutdown signal, is never bounded by
  `_GRACEFUL_TIMEOUT`. The process can stay alive indefinitely past the intended
  10-second grace window, risking a hard SIGKILL from the container/orchestration
  layer instead of the intended graceful exit.

## Reason for Change

Graceful shutdown is a documented guarantee (10-second bound) used to keep the
process's exit within the shutdown grace period expected by process supervisors
/ container orchestrators. A guarantee that only holds depending on precise
signal-arrival timing relative to turn dispatch is not a guarantee at all, and
silently fails in the exact scenario (an in-progress turn hanging) it exists to
protect against.

## Implementation Intent

Make the `_GRACEFUL_TIMEOUT` bound apply based on when the shutdown signal is
actually received, not based on the state of `shutdown_requested` at the moment
`wait_for` was called. Concretely: run the turn dispatch as its own task, and
race it against the shutdown event; once the shutdown event fires while a turn
is active, start (or reduce to) a `_GRACEFUL_TIMEOUT`-bounded wait from that
point forward, regardless of when the turn itself started.

## Implementation Instructions

1. In `scripts/agent/repl.py`, change `_repl_loop()` so that `self._dispatch_line(line, ctx)`
   is wrapped in a task created up front (e.g. `dispatch_task = asyncio.ensure_future(self._dispatch_line(line, ctx))`)
   rather than being awaited directly inside a single `asyncio.wait_for(...)` call
   whose timeout is fixed at call time.
2. Concurrently wait on `dispatch_task` and `self._shutdown_event` (already available
   as `self._shutdown_event`, an `asyncio.Event()`), using `asyncio.wait(..., return_when=asyncio.FIRST_COMPLETED)`
   or an equivalent pattern.
3. If `dispatch_task` finishes first, proceed as today (no timeout needed).
4. If the shutdown event fires first (i.e. it fires while `dispatch_task` is still
   pending — this covers both the case where the signal arrived before dispatch
   started and the case where it arrives mid-dispatch), start counting
   `_GRACEFUL_TIMEOUT` **from that point** using `asyncio.wait_for(dispatch_task, timeout=_GRACEFUL_TIMEOUT)`
   (or `asyncio.wait({dispatch_task}, timeout=_GRACEFUL_TIMEOUT)`), so the bound is
   anchored to signal-arrival time rather than turn-start time.
5. On timeout expiry, preserve existing behavior: log the same warning message
   ("Graceful shutdown: turn did not complete within %.1fs; forcing exit") and
   break out of the loop.
6. Update the `_sigterm_handler` comment (around lines 676-680) to accurately
   describe the new behavior instead of the current inaccurate claim that
   `_repl_loop()` "already checks shutdown_requested after each turn" — clarify
   that the grace-period timer is anchored to signal-arrival time and applies
   even to a turn that was already in flight when the signal arrived.
7. Ensure cancellation/cleanup of `dispatch_task` on timeout is consistent with
   existing behavior elsewhere in the file (e.g. whether the task is cancelled
   explicitly or left to be garbage-collected) — check how similar patterns are
   handled in `_read_input()`'s `input_coro`/`shutdown_coro` race (lines 504-553)
   for the established convention in this file (cancel pending tasks in a `finally`
   or `for t in pending: t.cancel()` block).

## Acceptance Criteria

- [ ] A turn that is already dispatching when SIGTERM/SIGINT arrives is force-cut
      off no later than `_GRACEFUL_TIMEOUT` seconds after the signal was received,
      not left to run indefinitely.
- [ ] A turn that starts before any shutdown signal and completes normally is
      unaffected (no artificial timeout applied when no shutdown is in progress).
- [ ] The `_sigterm_handler` comment no longer makes the incorrect claim that the
      timeout is applied to turns based on a check "after each turn" that cannot
      reach an in-flight turn.
- [ ] Existing graceful-shutdown behavior for turns that start after the signal
      (i.e. `shutdown_requested` already `True` at dispatch time) continues to work.

## Tests

  `_dispatch_line` (or the orchestrator call within it) hangs (e.g. via an
  `asyncio.Event` that is never set, or a long `asyncio.sleep`), sets
  `shutdown_requested = True` and fires `self._shutdown_event` partway through
  that turn's execution (simulating a signal arriving mid-turn), and asserts that
  `_repl_loop()` exits within approximately `_GRACEFUL_TIMEOUT` seconds (using a
  short overridden timeout value in the test to keep it fast) rather than hanging
  indefinitely.
- Add/keep a test confirming the pre-existing behavior: signal arrives before a
  turn starts, turn hangs, and the loop still exits within the timeout (regression
  guard for the previously-working path).
- Add a test confirming turns that complete normally without any shutdown signal
  are not truncated or delayed.
