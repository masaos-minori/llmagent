## Background

`docs/05_agent_09_01_data-layer-session-db.md` documents two components involved in session/message persistence:

- `SessionMessageRepository` — business-logic layer (role validation, strict_mode, skip counters, content normalization, tool_calls JSON encode/decode).
- `SQLiteSessionStore` (`scripts/db/store_impl.py:167`) — thin DB adapter implementing the `SessionStore` protocol (`scripts/db/store_protocols.py`), intended for simple INSERT/LIST operations only.

The document states, as an explicit "Needs confirmation" item, that the current REPL/agent execution path (`AgentSession` in `scripts/agent/session.py`) does not go through `SQLiteSessionStore` at all — it calls `SQLiteHelper` directly (confirmed at `scripts/agent/session.py:103,145,158,182,211,247`). The actual production caller of `SQLiteSessionStore`, if any, was not identified during the original documentation survey.

## Problem

A repository-wide search (`grep -rn "SQLiteSessionStore" --include="*.py" .`) confirms:

- `SQLiteSessionStore` is defined in `scripts/db/store_impl.py:167`.
- It is exported through `scripts/db/store.py` and `scripts/db/__init__.py`.
- It is referenced only in docstrings/type comments in `scripts/db/store_protocols.py`.
- The only place that actually instantiates and calls it is `tests/test_db_store_impl.py` (unit tests for the store implementation itself, not a production caller).

No production code path (REPL, agent runtime, CLI, background tasks, etc.) was found calling `SQLiteSessionStore`. This confirms the doc's "Needs confirmation" claim is still accurate as of the current source tree — the open question in NC-017 remains unresolved: it is unclear whether `SQLiteSessionStore` is (a) genuinely dead/unused production code kept only for protocol-conformance testing, or (b) intended to be wired in as the actual persistence layer for `AgentSession` at some point, with that migration not yet done.

## Reason for Change

Leaving this ambiguity undocumented risks two failure modes: engineers spending time maintaining `SQLiteSessionStore` in lockstep with `SQLiteHelper`-based logic in `AgentSession` for a class that has no real caller (wasted effort / drift risk), or engineers deleting `SQLiteSessionStore` under the assumption it is dead code when it is actually meant to be adopted later (losing a protocol implementation prematurely). Resolving the "Needs confirmation" item removes this ambiguity and lets the documentation state a definitive, actionable fact instead of an open question.

## Implementation Intent

This is a documentation/investigation task, not a code change. The intent is to:

1. Conclusively determine whether `SQLiteSessionStore` has any production caller anywhere in the codebase (including CLI entry points, background/maintenance jobs, plugins, or any code outside `tests/`).
2. Based on that finding, decide the appropriate disposition: (a) mark it as intentionally-unused/test-only scaffolding for the `SessionStore` protocol, (b) identify it as a migration target still pending for `AgentSession`, or (c) flag it as a dead-code removal candidate for a separate follow-up issue.
3. Update `docs/05_agent_09_01_data-layer-session-db.md` (§SQLiteSessionStore callers, around line 115-121) to replace the "Needs confirmation" language with the confirmed answer, and update the NC-017 entry in `docs/00_governance_07_needs-confirmation-inventory.md` accordingly.

Documentation edits themselves are out of scope for this requirement's implementation phase gate (per workflow rules for this document-only cycle) but should be the deliverable of the downstream plan/implementation cycle that consumes this requirement.
