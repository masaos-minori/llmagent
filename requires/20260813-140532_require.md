# Make RuntimeToolRegistry the Sole Scheduling Authority and Resolve Call-Level Resource Scopes

High

## Background
The current implementation has multiple, disagreeing sources of truth for the same
execution properties (write/serial/scope classification of a tool call):

- Runtime routing uses `RuntimeToolRegistry`.
- DAG scheduling in `scripts/agent/tool_runner.py::_build_tool_meta()` (lines 60-70)
  rebuilds a tool-name-keyed metadata map from `ctx.cfg.tool.tool_definitions`
  (also referenced at lines 138, 157-158, 325-326), using the static
  `is_side_effect()` helper (`scripts/shared/tool_executor_helpers.py`, imported at
  `tool_runner.py:26` and also called directly at line 434) and the static
  `SHELL_TOOLS` name set (`scripts/shared/tool_constants.py`, imported at
  `tool_runner.py:25`).
- `scripts/agent/tool_scheduler.py::build_execution_groups()` (lines 71-91) consumes
  that name-keyed `tool_meta: dict[str, ToolSpec]` map and, when a call's tool name is
  missing from it, silently falls back to a synthetic `ToolSpec` with
  `is_write=False`/`requires_serial=False` (lines ~91-96) instead of failing.
- `scripts/shared/runtime_tool.py::RuntimeTool` (line 62) still has a single
  `resource_scope: str` field, and `build_runtime_tool()`'s `_or_default` helper
  (line 103) silently turns a missing/`None` `is_write` into `False`.
- `scripts/shared/tool_spec.py::ToolSpec` (lines 26-31) is already a frozen dataclass
  with `call_id`, `name`, `args`, `requires_serial`, `is_write`, but scope is still the
  singular `resource_scope: str = ""` (line 29), not a scope tuple.
- `scripts/shared/runtime_tool_registry.py::tool_spec_for_call()` (lines 156-164)
  already builds a correctly-shaped per-call `ToolSpec`, but it has no caller anywhere
  in `scripts/agent/` — the DAG path never uses it.
- No MCP server `TOOL_LIST` entry declares `is_write`, `requires_serial`,
  `resource_scope_kind`, or `resource_scope_keys` (spot-checked
  `scripts/mcp_servers/file/write_tools.py` and `scripts/mcp_servers/shell/shell_tools.py`
  — both carry only `name`, `description`, `inputSchema`).
- `scripts/mcp_servers/server.py:35` defines `MCP_TOOL_SCHEMA_VERSION = "1.0"`, but this
  is only a `/v1/tools` response-envelope field (used at line 201), unrelated to
  per-tool metadata completeness — there is no per-tool schema-2.0 contract today.
- `scripts/agent/services/mcp_tool_discovery.py::_validate_and_normalize_entry()`
  (lines 204-259) type-checks `is_write`/`requires_serial` only when present; it does
  not reject missing values, has no notion of `resource_scope_kind`/
  `resource_scope_keys` at all, and `_dedupe_and_build()` (line 300) passes
  `entry.get("is_write")` straight through to `build_runtime_tool()`, which silently
  normalizes an absent value to `False` — unsafe for tools whose write status was
  simply never declared.

This split allows routing, argument validation, approval, and scheduling to disagree
about whether a tool is state-changing or requires serialization, and prevents two
calls to the same tool (e.g. two `write_file` calls on different paths) from ever
carrying different scheduling scopes, since metadata is keyed by tool name rather than
by call.

Investigation confirms this issue is not resolved by any prior commit. `git log`
shows only precursor scaffolding (`dcb76d1f8` DAG scheduling scaffolding,
`e854ceddc` `ScheduledBatch`, and related design docs) — no commit introduces a
per-tool schema-2.0 contract, `resource_scope_kind`/`resource_scope_keys`, or a
`resolve_resource_scopes()` resolver.

## Problem
1. No MCP tool declares explicit `is_write` / `requires_serial` / resource-scope
   metadata; nothing validates that such metadata is present before a tool is
   published or registered.
2. `RuntimeTool` and `ToolSpec` still represent resource scope as a single
   `resource_scope: str`, which cannot express multiple or hierarchical resources
   (e.g. `move_file`'s source and destination, or a directory read conflicting with a
   descendant-path write).
3. The legacy DAG metadata path (`_build_tool_meta()`, `ctx.cfg.tool.tool_definitions`,
   `is_side_effect()`, `SHELL_TOOLS`) is still the only path actually wired into
   `scripts/agent/tool_scheduler.py::build_execution_groups()`. The already-built
   `RuntimeToolRegistry.tool_spec_for_call()` (correctly per-call, correctly shaped) is
   unused dead code.
4. Missing metadata is currently normalized to safe-looking defaults
   (`is_write=False` in `build_runtime_tool()`'s `_or_default`, and a synthetic
   all-`False` `ToolSpec` in the scheduler's `tool_meta.get(name)` miss path) instead of
   causing a fail-closed rejection/error. This is unsafe for file writes, deletes, Git
   mutations, GitHub mutations, workflow dispatch, RAG deletion, and shell execution.
5. Metadata is keyed by tool name throughout the active DAG path, so two calls to the
   same tool with different arguments (e.g. two `write_file` calls on different files)
   cannot be scheduled with different scopes, and `move_file` cannot represent both its
   source and destination as separate scopes.

## Reason for change
Scheduling correctness for concurrent tool execution depends on knowing, per call,
whether it writes, whether it must run alone, and which concrete resource it touches.
Today that knowledge is either absent (undeclared per-tool metadata), computed from
static heuristics that don't see call arguments (`is_side_effect()`, `SHELL_TOOLS`), or
silently defaulted to the unsafe value when missing. This risks unsafe concurrent
execution of conflicting writes and unnecessary serialization of independent writes,
and leaves four different code paths (routing, argument validation, approval,
scheduling) free to disagree about the same tool call's execution characteristics.

## Implementation intent
Establish one authoritative, fail-closed metadata flow: each MCP server's `TOOL_LIST`
explicitly declares `is_write`, `requires_serial`, `resource_scope_kind`, and
`resource_scope_keys` for every tool (schema 2.0); a contract validator rejects
incomplete or invalid declarations before publication/registration;
`McpToolDiscoveryService` validates and transfers the fields without inferring or
defaulting; `RuntimeToolRegistry` becomes the sole scheduling-metadata authority; a new
pure shared resolver turns a tool's declared scope kind/keys plus the actual call
arguments into one or more concrete resource-scope strings; a per-call `ToolSpec`
(keyed by `call_id`, not tool name) is produced for every scheduled call via
`RuntimeToolRegistry.tool_spec_for_call()`; and the legacy DAG metadata path
(`_build_tool_meta()`, `tool_definitions`, `is_side_effect()`, `SHELL_TOOLS`) is
deleted, with the scheduler failing (not silently defaulting) when a call has no
`ToolSpec`. Favor conservative correctness (e.g. an unresolved state-changing tool
falls back to a `global:write` scope, never to the tool name) over maximum concurrency
in this first pass; fine-grained locking can follow once backend concurrency
guarantees are verified.

## Implementation instructions

1. **Schema 2.0 contract.** In `scripts/mcp_servers/server.py`, define (or repurpose,
   with a version bump and clarified meaning) a per-tool schema-2.0 contract distinct
   from the existing envelope-level `MCP_TOOL_SCHEMA_VERSION` at line 35. Every
   exported tool must carry:
   ```python
   {
       "is_write": bool,          # required
       "requires_serial": bool,   # required
       "resource_scope_kind": str,   # required; "" allowed for unscoped reads
       "resource_scope_keys": list[str],  # required; keys must exist in inputSchema.properties
   }
   ```
   Do not infer missing values from `scripts/shared/tool_constants.py` or
   `tool_definitions`.

2. **Populate every `TOOL_LIST`** across all MCP servers with the conservative
   classifications specified in the source issue (`issues/done/20260807_21_issue.md`
   after this requirement is filed), including:
   - Filesystem: `read_text_file`/`read_media_file`/`get_file_info` read-only with
     `filesystem`+`path`; `write_file`/`edit_file`/`create_directory`/`delete_file`/
     `delete_directory` state-changing with `filesystem`+`path`; `move_file`
     state-changing with `filesystem`+`source,destination`.
   - Local Git: reads read-only, `git_add`/`git_commit`/`git_checkout`/`git_pull`/
     `git_push` state-changing, all scoped `git_repo`+`repo_path`.
   - GitHub: repository-level scope `github_repo`+`owner,repo` for all mutating calls;
     no branch/issue/PR/file-level scope yet.
   - CI/CD: `cicd_workflow`+`repo,workflow,ref`; `trigger_workflow` state-changing;
     status/run/log retrieval read-only.
   - RAG: pipeline execution and document listing read-only; document deletion
     state-changing with a fixed store-level scope.
   - MDQ: `index_paths`/`refresh_index` state-changing and `requires_serial=True` with a
     fixed MDQ store scope; all other MDQ tools read-only, non-serial.
   - Shell: `is_write=True`, `requires_serial=True`, `resource_scope_kind="process"`,
     `resource_scope_keys=[]`, resolved to a fixed global process scope — do not infer
     from `cwd`/`command`/`argv`.
   - Web search/browser: `search_web`/`browser_fetch` read-only, non-serial, unscoped.

3. **Contract validator.** Add a shared validator (server-startup or mandatory-test
   invocation) that rejects: missing/empty tool names; invalid `inputSchema`;
   missing/non-boolean `is_write` or `requires_serial`; invalid scope kinds; invalid
   `resource_scope_keys` lists; or scope keys absent from the tool's own
   `inputSchema.properties`. The validator must not infer missing behavior.

4. **`McpToolDiscoveryService`** (`scripts/agent/services/mcp_tool_discovery.py`):
   update `_validate_and_normalize_entry()` (currently lines 204-259) to require and
   validate all four schema-2.0 fields rather than checking type only when present;
   update `_dedupe_and_build()` (currently line ~300) to stop passing
   `entry.get("is_write")` through to a code path that silently defaults it — reject or
   exclude any tool whose schema-2.0 declaration is incomplete instead of registering it
   in `RuntimeToolRegistry`.

5. **`RuntimeTool`** (`scripts/shared/runtime_tool.py`): replace the `resource_scope:
   str` field (currently line 62) with `resource_scope_kind: str` and
   `resource_scope_keys: tuple[str, ...]`. Update `build_runtime_tool()` (and its
   `_or_default` safe-default logic, currently around line 103) accordingly, and update
   the class docstring to state that this metadata describes how a later call resolves
   scheduling resources — it is not itself an already-resolved path, repository,
   branch, or URL.

6. **`ToolSpec`** (`scripts/shared/tool_spec.py`): replace the singular
   `resource_scope: str = ""` field (currently line 29) with `resource_scopes:
   tuple[str, ...] = ()`, matching the shape already implied by the source issue:
   ```python
   @dataclass(frozen=True)
   class ToolSpec:
       call_id: str
       name: str
       args: dict[str, Any] = field(default_factory=dict)
       resource_scopes: tuple[str, ...] = ()
       requires_serial: bool = False
       is_write: bool = False
   ```

7. **New shared resource-scope resolver**, e.g. `scripts/shared/resource_scope.py`,
   pure function:
   ```python
   def resolve_resource_scopes(
       tool: RuntimeTool,
       args: Mapping[str, Any],
   ) -> tuple[str, ...]:
       ...
   ```
   Must not perform authorization or import Agent-layer configuration (respect the
   `shared`-is-leaf import-layer contract noted in `scripts/shared/runtime_tool.py`'s
   module docstring). Resolve: filesystem → normalized path(s); local Git → normalized
   repo path; GitHub → normalized `owner/repo`; CI/CD → normalized repo+workflow(+ref);
   RAG/MDQ mutation → fixed store scope; shell → fixed global process scope; unscoped
   read-only → no scope. For a known state-changing tool with no resolvable scope,
   return `("global:write",)` — never the tool name.

8. **Multi-resource and hierarchical scopes.** `move_file` must resolve both source and
   destination scopes. Filesystem scope comparison used later by the scheduler/registry
   must treat ancestor/descendant paths as overlapping (e.g. a directory read on
   `/data` conflicts with a write to `/data/a.txt`); read/read may run concurrently;
   read/write, write/read, write/write must conflict.

9. **Per-call `ToolSpec` generation.** Wire
   `RuntimeToolRegistry.tool_spec_for_call(call_id, name, args)` (already implemented at
   `scripts/shared/runtime_tool_registry.py:156-164`) into the actual DAG execution
   path so every scheduled call gets its own `ToolSpec` keyed by `call_id` in a
   `dict[str, ToolSpec]` — not by tool name.

10. **Remove the legacy DAG metadata path.** Delete
    `scripts/agent/tool_runner.py::_build_tool_meta()` (currently lines 60-70) and its
    call site (currently line 325-326), and remove the `ctx.cfg.tool.tool_definitions`
    dependency used for metadata (lines 138, 157-158, 325), the `is_side_effect()`
    import/calls (lines 26, 69, 434), and the `SHELL_TOOLS` import/use (lines 25, 70).
    Update `scripts/agent/tool_scheduler.py::build_execution_groups()` (currently lines
    71-91) to accept a call-id-keyed `dict[str, ToolSpec]` sourced from
    `RuntimeToolRegistry`, and to raise (not silently default to an all-`False`
    synthetic `ToolSpec`, as it currently does around lines 91-96) when a call ID has no
    matching `ToolSpec`. Also remove any remaining live uses of `SHELL_TOOLS` /
    `is_side_effect()` for scheduling purposes in `scripts/shared/tool_registry.py`,
    `scripts/agent/tool_policy.py`, `scripts/shared/tool_executor.py`, and
    `scripts/shared/tool_executor_helpers.py:48` — keep `is_side_effect()` /
    `SHELL_TOOLS` only where they still serve a purpose unrelated to DAG scheduling
    (e.g. approval-tier classification), or remove them entirely if scheduling was
    their only consumer; verify with grep before deleting.

## Acceptance criteria
- Every exported MCP tool explicitly declares `is_write`, `requires_serial`,
  `resource_scope_kind`, and `resource_scope_keys` in its `TOOL_LIST` entry.
- A contract validator rejects any tool missing or misdeclaring these fields, and
  rejects scope keys not present in the tool's `inputSchema.properties`.
- `McpToolDiscoveryService` no longer silently normalizes an absent `is_write` to
  `False`, and does not register schema-2.0-incomplete tools into
  `RuntimeToolRegistry`.
- `RuntimeTool` carries `resource_scope_kind`/`resource_scope_keys` instead of a single
  `resource_scope: str`.
- `ToolSpec` carries `resource_scopes: tuple[str, ...]` instead of a single
  `resource_scope: str`.
- `resolve_resource_scopes()` exists in a new shared module, is pure, and does not
  import Agent-layer configuration.
- Every scheduled tool call has its own `ToolSpec` produced via
  `RuntimeToolRegistry.tool_spec_for_call()`, keyed by `call_id`.
- Two calls to the same tool with different arguments can resolve to different scopes;
  `move_file` resolves both source and destination scopes; a directory read and a
  descendant-path write are detected as conflicting.
- A state-changing tool with no resolvable scope resolves to `global:write`, never to
  the tool name.
- `scripts/agent/tool_runner.py::_build_tool_meta()` is deleted, along with its
  `ctx.cfg.tool.tool_definitions`, `is_side_effect()`, and `SHELL_TOOLS` dependencies
  for scheduling purposes.
- `scripts/agent/tool_scheduler.py::build_execution_groups()` raises when a call ID has
  no `ToolSpec`, rather than defaulting to an all-`False` synthetic spec.
- DAG scheduling metadata comes only from `RuntimeToolRegistry`-derived data; no static
  tool-name classification remains in the active scheduling path.

## Tests
- Contract-validator unit tests: acceptance of a fully-declared tool; rejection of a
  tool missing `is_write`, missing `requires_serial`, an invalid scope kind, or scope
  keys absent from `inputSchema.properties`.
- `McpToolDiscoveryService` tests: metadata round-trip through `/v1/tools` and
  discovery preserves all four fields unchanged; a schema-2.0-incomplete tool is
  rejected/excluded rather than registered with defaulted values.
- `RuntimeToolRegistry`/`resolve_resource_scopes()` unit tests: same tool with
  different arguments yields different scopes; different tool names targeting the same
  file conflict; same tool name targeting different files may run concurrently;
  `move_file` produces separate source/destination scopes that each conflict correctly;
  a directory read and a descendant-path write conflict; same/different local Git
  repositories; same/different GitHub repositories; shell resolves to a global serial
  process scope; a known state-changing tool with no resolvable scope resolves to
  `global:write`; `dry_run=true` remains conservatively state-changing for scheduling
  purposes.
- `scripts/agent/tool_scheduler.py` tests: scheduling raises (does not silently
  proceed) when a call ID has no `ToolSpec`; per-call scopes (not per-tool-name) drive
  grouping/serialization decisions.
- Regression tests confirming `_build_tool_meta()`, the `tool_definitions`-based
  metadata path, and the `SHELL_TOOLS`/`is_side_effect()` scheduling dependencies are
  gone from `scripts/agent/tool_runner.py` (e.g. `grep -n "_build_tool_meta" scripts/agent/tool_runner.py` returns nothing).
