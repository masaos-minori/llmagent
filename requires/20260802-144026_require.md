# Document the impact scope of an MCP server startup RuntimeError in docs/04_mcp_06_05

## Priority
High

## Target files
- `docs/04_mcp_06_05_long-running-http-operation-startup_modesubprocess.md`

## Background
`docs/04_mcp_06_05_long-running-http-operation-startup_modesubprocess.md` currently states only:

> Agentは起動時にuvicornを起動し、`startup_timeout_sec` まで0.5秒ごとに `/health` をポーリングする。
> ヘルスチェックが一度も成功しない場合は `RuntimeError` となる。

It stops at "a `RuntimeError` occurs" without saying what happens next: does that exception crash the
entire Agent process, or is it isolated so only the failing server is disabled while the rest of the
Agent (and other MCP servers) continue running? This is a production-reliability-relevant gap because
operators need to know the actual blast radius of a single misconfigured MCP server before they can set
incident-response expectations.

## Problem
The document under-specifies the exception-propagation path for an MCP server startup failure, leaving
readers unable to determine whether a single server's `RuntimeError` at startup:
- terminates the whole Agent process, or
- is caught and isolated to that server, leaving the rest of the Agent process (and other MCP servers)
  running normally.

## Reason for change
This is a documentation gap with direct operational-risk implications: the actual behavior differs
depending on `security_profile` (see Investigation below), and the current doc text does not mention
this distinction at all. Without it, an operator reading only this doc could misjudge the severity of an
MCP server misconfiguration in production versus local/development environments.

## Investigation (confirmed, not inconclusive)

Traced the exception-propagation path in the startup/orchestration code (read-only; no code changes made
as part of this requirement):

1. **Per-server subprocess startup** — `scripts/agent/startup.py::StartupOrchestrator._start_servers()`
   (lines ~163-203) calls `ctx.services_required.lifecycle.start_http_subprocess(key, cfg)` for each
   `startup_mode=subprocess` + `transport=http` MCP server. This delegates to
   `HttpServerLifecycleManager.start()` in `scripts/agent/http_lifecycle.py` (lines 286-464), which polls
   `/health` every 0.5s until `cfg.startup_timeout_sec` elapses, then raises `HttpStartupError` (a
   `RuntimeError` subclass, defined at `http_lifecycle.py:44`) if the process exited early or never
   became healthy.
2. **Retry and severity branch** — `_start_servers()` catches `(OSError, RuntimeError)` from the first
   attempt (logged at INFO), retries once after `HEALTH_CHECK_RETRY_DELAY_SEC` (1.0s), and if the retry
   also fails:
   - **`security_profile == PRODUCTION`**: re-raises a new `RuntimeError` (`startup.py:195`) — this
     propagates out of `_start_servers()`, aborting the entire `StartupOrchestrator.run()` sequence.
   - **`security_profile == LOCAL`** (the only other value; see `shared/mcp_config.py:41-45`
     `SecurityProfile(StrEnum)`): the retry failure is only logged as a WARNING and shown to the user via
     `self._view.write_warning(...)` with a `NON_FATAL` tag (`startup.py:196-203`) — no exception is
     raised, and startup continues. That server is simply left out of `spawned` (not started); other
     servers and the rest of Agent startup are unaffected.
   - The same PRODUCTION-vs-LOCAL branch is repeated for the post-startup health re-check in
     `_verify_mcp_health()` (`startup.py:206-252`).
3. **Process-level outcome in PRODUCTION** — when `_start_servers()` raises, `StartupOrchestrator.run()`
   (`startup.py:67-94`) catches it only to attempt a best-effort `shutdown_all()` rollback (note: this
   rollback is actually skipped here — `_servers_started` is never set to `True` because the exception
   is raised *from inside* the awaited `_start_servers()` call, before line 74 executes; see "Related
   finding" below) and then **re-raises**. The caller, `AgentREPL.run()`
   (`scripts/agent/repl.py:833-846`), catches the exception only to write a fatal message to the view,
   terminate any spawned subprocesses, and **re-raise** again. This exception is never caught above that
   point: `main()` (`repl.py:863-865`) calls `asyncio.run(AgentREPL().run())` with no surrounding
   try/except, so the exception is unhandled and **the entire Agent process terminates** (Python prints
   the traceback and exits non-zero).

**Confirmed answer to the issue's question**: the blast radius depends on `security_profile`
(`config` — `LOCAL` or `PRODUCTION`, `shared/mcp_config.py:41-45`):
- In **PRODUCTION**, an MCP HTTP-subprocess server's startup `RuntimeError` (after one retry) crashes the
  **entire Agent process** — it is not isolated.
- In **LOCAL** (non-production), the same failure is caught, logged, and shown as a non-fatal warning;
  **only that specific server is disabled** (excluded from the spawned/available server set), and the
  rest of the Agent process — including other MCP servers — continues running normally.

This asymmetric fail-closed-in-production / fail-open-in-local pattern matches the existing documented
design intent elsewhere in the MCP docs (e.g. `docs/04_mcp_05_03_fail-open-fail-closed-and-risk-tiers.md`
§ tool_safety_tiers: "本番環境ではエラー（致命的な RuntimeError）、local/development では warning となる"),
so it is consistent with, not a deviation from, the project's established security-profile-driven
fail-safe design.

**Related finding (out of scope for this doc fix, do not act on it here per the issue's "Out of Scope"
instruction)**: in `StartupOrchestrator.run()`, when `_start_servers()` itself raises (the PRODUCTION
path), `_servers_started` remains `False` because the flag-set line never executes, so the
`shutdown_all()` rollback for already-started sibling subprocesses is skipped. `AgentREPL.run()` does
still terminate subprocesses tracked in `_spawned_subprocesses`/`startup._spawned_subprocesses`, but this
rollback gap in `StartupOrchestrator.run()` may be worth a separate issue if it results in orphaned
processes in practice — not addressed by this requirement.
