## [cmd_workflow] Race condition in approval resolution

### Summary

`/approve` コマンド実行時に、pending approval のチェックと解決の間に競合条件が存在する。複数の同時リクエストが同じ approval を同時に解決できる可能性がある。

### Problem

`cmd_workflow.py:103-116` で以下の順序で処理が行われる：

1. `count_pending_approvals(store._db)` — pending approval の数をチェック
2. `find_approval_by_id(store._db, explicit_id)` — 特定の approval を取得
3. `resolve_approval(store._db, approval.approval_id, "approved", reason)` — approval を解決

ステップ1とステップ2の間に別のプロセスが同じ approval を解決する場合、ステップ3はすでに解決済みの approval を再度解決しようとする。SQLite の WAL モードでは、異なる接続間で同一トランザクションの整合性が保証されない。

また、`find_approval_by_id()` が None または status != "pending" を返す場合、エラーメッセージが表示されるが、approval が既に解決されたのか、存在しないのかの区別がつかない。

### Affected Files

- `scripts/agent/commands/cmd_workflow.py:93-129` — `_cmd_approve()`
- `scripts/agent/commands/cmd_workflow.py:131-177` — `_cmd_reject()`
- `scripts/agent/workflow/approval_ops.py` — `resolve_approval()`, `find_approval_by_id()`

### Attack Scenario

1. エージェントREPLが `/approve <uuid>` を実行
2. 同時に別のプロセス（例: API経由）が同じ approval を解決
3. ステップ1と2の間で approval が解決される
4. ステップ3で既存の approval が再度解決され、二重承認が発生

### Severity

Medium — 同時実行環境での approval の二重解決が可能。単一のREPLセッション内では稀だが、API経由の並行アクセスがある場合に発生する。

### Mitigation

- `resolve_approval()` で optimistic locking または UPDATE ... WHERE status='pending' を使用
- 更新行数をチェックし、0件の場合は「すでに解決済み」のエラーを返す
- approval チェックから解決までを1つのトランザクション内に閉じる
