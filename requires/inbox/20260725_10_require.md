# Diagnostic store persists sensitive data without encryption

## Priority

Medium

## Target Files

- `scripts/agent/repl.py` — `_persist_session_diagnostics()`
- `scripts/agent/diagnostic_store.py` — `DiagnosticStore.save()`

## Background

When a session ends, diagnostic information including session statistics, workflow metrics, and query results is persisted to the DiagnosticStore for later analysis.

## Problem

In `repl.py:148-244`:

```python
summary = {
    ...
    "artifacts": artifacts,
    "rag_query_count": rag_query_count,
    "rag_stage_outcomes": rag_stage_outcomes,
}
```

The `artifacts` field contains a list of URIs obtained from `store.get_artifact_uris(sid)`, which may include file paths and URLs containing sensitive information. The `rag_stage_outcomes` field contains RAG query results, which may include portions of retrieved content. Additionally, `latency_summary` contains per-step latency statistics that can reveal internal system behavior. All this data is stored in plaintext on the filesystem.

## Reason for Change

Without filtering or encryption, sensitive data such as artifact URIs (which may point to confidential files), RAG query results (which may contain proprietary content), and latency patterns (which reveal system internals) are exposed in plaintext storage. This violates data minimization principles and creates unnecessary risk if the storage location is compromised.

## Implementation Intent

Add data filtering to remove sensitive fields before persistence. Implement optional encryption for diagnostic data. Add retention policies to automatically delete old diagnostic records.

## Implementation Instructions

1. Define a filter that removes or redacts sensitive fields from the diagnostic summary before saving (e.g., artifact URIs, RAG outcomes).
2. Add an optional encryption layer using a configurable key for diagnostic data storage.
3. Implement a retention policy that automatically deletes diagnostic records older than a configurable period (default: 30 days).
4. Log warnings when sensitive data would be persisted but is filtered out.

## Acceptance Criteria

- [ ] Sensitive fields (artifact URIs, RAG outcomes) are filtered or redacted before persistence
- [ ] Optional encryption is available for diagnostic data
- [ ] Retention policy automatically purges old records
- [ ] Warnings logged when sensitive data is filtered

## Tests

- Unit test: mock diagnostic summary with sensitive fields; verify they are filtered before save
- Integration test: verify encrypted diagnostic data can only be read with correct key
- Stress test: simulate large number of old diagnostic records; verify automatic cleanup works
