# Document the RAG/Agent responsibility boundary (RagPipeline core logic vs. rag-pipeline-mcp production boundary)

## Priority
High

## Target files
- `docs/04_mcp_05_04_mdq-rag-boundary.md` (preferred: extend the existing "Agent access patterns" section, since that section already covers MDQ+RAG access routing and is the closest canonical home for this content)
- Alternatively, a new dedicated file if the next phase (require-to-plan / documentation authors) decides the topic warrants separation from the MDQ-vs-RAG comparison doc

## Background
`docs/04_mcp_05_04_mdq-rag-boundary.md` documents the MDQ-vs-RAG *selection* boundary (when to use which system) and, in its "Agent access patterns" subsection, states three access paths: (1) MCP routing via `ToolRouteResolver` (primary/recommended), (2) an admin-only `/db` REPL bypass for `rag.sqlite` maintenance, and (3) a prohibition on raw `sqlite3` access to `mdq.sqlite`/`rag.sqlite` from application code. What this doc does not state anywhere is a class-level responsibility boundary between `RagPipeline` (the core query/ingestion logic implemented in `scripts/rag/pipeline.py`) and `rag-pipeline-mcp` (the production HTTP/MCP boundary that wraps it via `RagPipelineMCPService` / `RagPipelineMCPServer` in `scripts/mcp_servers/rag_pipeline/`). This gap was identified as the single most important undocumented viewpoint in the MCP domain review (`docs_review_mcp.md` §1 item 12, §4 "RAGとAgentの責務境界").

## Problem
There is no explicit, canonical statement that:
- `RagPipeline` (`scripts/rag/pipeline.py`) implements RAG's core logic (retrieval, chunking, hybrid search, augmentation).
- In production, Agent-layer code must reach this logic only through `rag-pipeline-mcp` (the MCP/HTTP boundary), not by importing `RagPipeline` directly.
- Any direct import of `RagPipeline` outside that boundary is test/dev-only.

Without this stated explicitly, a future implementer could add a production Agent code path that imports `RagPipeline` directly, bypassing the MCP boundary's access control, audit logging, and health-gating — silently reintroducing a responsibility-boundary violation the architecture is designed to prevent. The existing "direct DB access (discouraged)" note in the doc covers raw `sqlite3` access to the database files, which is a related but distinct concern from importing the `RagPipeline` Python class itself.

## Reason for change
This is flagged as the highest-value documentation gap in the entire MCP domain review. The architecture already relies on this boundary being respected (confirmed in verification below), but nothing states it as an explicit rule, so the guarantee currently rests entirely on unwritten convention.

## Verification performed (findings to carry into the documentation)

**1. Does any doc already state this boundary?**
No. `docs/04_mcp_05_04_mdq-rag-boundary.md` documents MDQ-vs-RAG system selection and covers DB-level access patterns (MCP routing / admin `/db` bypass / sqlite3-import prohibition), but has no statement distinguishing `RagPipeline` (core logic) from `rag-pipeline-mcp` (production boundary) at the class/module level, nor a statement that direct `RagPipeline` import is test/dev-only. This is a genuine, currently unfilled gap — not a stale or already-fixed issue.

**2. Does production Agent code import `RagPipeline` directly?**
No. `grep -rn "RagPipeline" scripts/agent/` returns zero matches. Broader checks confirm:
- `class RagPipeline` is defined only in `scripts/rag/pipeline.py`.
- All other `RagPipeline`-related symbols (`RagPipelineMCPServer`, `RagPipelineMCPService`, `RagPipelineConfig`, `RagPipelineServiceError`, `RagPipelineLike`) live under `scripts/mcp_servers/rag_pipeline/`, i.e. the MCP boundary layer, not the agent layer.
- No `from rag...` / `import rag...` statement inside `scripts/agent/` references the `rag.pipeline` module. The one agent file that touches `rag.sqlite` directly (`scripts/agent/services/rag_maintenance_service.py`, `RagMaintenanceService`) does so via `db.helper.SQLiteHelper` raw DB access for maintenance/consistency-check purposes — this is the already-documented admin `/db`-bypass path, not a `RagPipeline` class import, and is out of scope for this gap.
- `RagPipeline` is imported directly only from test files (`tests/test_rag_pipeline.py`, `tests/test_agent_rag.py`, `tests/test_rag_pipeline_stage.py`, `tests/test_rag_refiner.py`, `tests/test_rag_quality_regression.py`, `tests/test_pipeline_http_result_kind.py`, `tests/test_stage_observability.py`, `tests/test_rag_get_cfg.py`, `tests/test_rag_http_mode.py`, `tests/integration/test_rag_turn_integration.py`, and MCP-layer test/service files), confirming the issue's premise: direct import is currently confined to tests/dev tooling and is not reachable from any current production Agent code path.

**3. Is the boundary enforced by `lint-imports` / import-linter, or is it purely convention?**
It is **purely convention — not enforced**. `.importlinter` (repo root) defines the layering contract with root packages `agent, db, mcp_servers, rag, shared, eventbus`. Its own documented dependency hierarchy explicitly states: `agent → rag, db, shared, mcp_servers (installer only)` — i.e., import-linter's contracts (`rag-no-agent-or-mcp_servers`, `mcp_servers-no-agent`, `db-only-uses-shared`, `shared-is-leaf`, `eventbus-is-isolated`) only forbid the *reverse* direction (rag/db/shared/mcp_servers importing agent, or shared/db importing rag/mcp_servers). No contract forbids `agent` from importing `rag` (and therefore `RagPipeline`) directly — that direction is architecturally permitted by the layering rules as they stand today. This must be stated as **Needs Confirmation / tracked as a known enforcement gap** in the new documentation, per the issue's own instruction, rather than asserted as an absolute, enforced prohibition. Per the issue's explicit "Out of Scope," this requirement does not add a new import-linter contract to close that gap — it only documents that the gap exists.
