# Clarify Whether UTF8_PARTIAL_DECODE_ERROR and PREMATURE_EOF Are Distinct, Implemented LLMErrorKind Values

## Priority

Medium

## Target Files

## Background

`docs/05_agent_05_llm-and-streaming-part1.md` §Error Classification documents the `LLMErrorKind` values used by the LLM streaming transport layer. Two of the nine literal values defined in `scripts/shared/llm_exceptions.py` — `UTF8_PARTIAL_DECODE_ERROR` and `PREMATURE_EOF` — are flagged in the doc as `Needs confirmation`, questioning whether they are clearly distinguished error kinds, since no raise site was found within the three files the doc's own investigation scope covered (`llm_sse_stream.py`, `llm_transport_errors.py`, `sse_parser.py`).

## Problem

A read-only investigation (scoped to the full `scripts/` tree, not just the three files the doc mentions) found:

- `UTF8_PARTIAL_DECODE_ERROR` has zero raise/instantiation sites anywhere in production code or tests — it exists only as a Literal member in `llm_exceptions.py`.
- `PREMATURE_EOF` has zero raise sites in production code. It appears only in test files (`tests/test_llm_client.py:53`, `tests/test_orchestrator.py`, `tests/test_llm_partial_completion.py:12`) where tests manually construct `LLMTransportError(kind="PREMATURE_EOF", ...)` as a mock value — there is no implementation that actually detects a premature EOF condition and raises this kind automatically.
- The only `kind=` values actually raised in `scripts/` are: `HTTP_STATUS_RETRYABLE`, `HTTP_STATUS_FATAL`, `CONNECT_ERROR`, `READ_TIMEOUT`, `UNKNOWN_STREAM_ERROR`, `HEARTBEAT_TIMEOUT`, `MALFORMED_SSE_FRAME`.
- `docs/05_agent_05_llm-and-streaming-part2.md:62` describes a cause for `PREMATURE_EOF` ("stream ended unexpectedly") without the code-backed citation convention used elsewhere in that table, suggesting it may be a description inferred from the literal's name rather than from actual behavior.

This means the original question ("are these two error kinds clearly distinguishable?") cannot be answered as posed, because neither kind is currently implemented/raised at all — they are reserved/unused Literal values, not implemented-but-ambiguous ones. This is a stronger finding than the doc's original framing and the `Needs confirmation` item remains genuinely open (NC-001 status is still `open` as of last review 2026-07-22).

## Reason for Change

Unused reserved error-kind values sitting alongside actively-used ones in a Literal type create risk: callers/handlers may assume these kinds are reachable and write dead branches for them, or conversely miss that certain real failure modes (e.g. actual UTF-8 decode partial-byte errors, actual premature stream termination) are silently folded into `UNKNOWN_STREAM_ERROR` or another generic kind instead of being surfaced distinctly. Leaving the `Needs confirmation` marker unresolved means documentation and governance tracking (NC-001) stay stale and the ambiguity persists for future readers/implementers.

## Implementation Intent

Resolve the open question by determining, with the original author/maintainer or via deeper code-path analysis, whether `UTF8_PARTIAL_DECODE_ERROR` and `PREMATURE_EOF` are:
(a) intentionally reserved for future use and should stay as documented placeholders, or
(b) meant to be actively raised and are missing their implementation (a latent gap), or
(c) obsolete and should be removed from the Literal and any dependent handling code.

Based on the outcome, update the documentation (`docs/05_agent_05_llm-and-streaming-part1.md`, `docs/05_agent_05_llm-and-streaming-part2.md`, and NC-001 in `docs/00_governance_07_needs-confirmation-inventory.md`) to remove the `Needs confirmation` label and record the resolution. This requirement covers only the investigation and requirement framing; actual doc edits and any code changes happen in later workflow phases (plan / implementation).
