# Fix `TestMergeOrder` to match `ConfigLoader.load()`'s documented flat-merge behavior

## Priority
Medium

## Target files
- `tests/shared/test_config_loader.py` (`TestMergeOrder` class — to be modified)
- `scripts/shared/config_loader.py` (`load()` ~line 58-66, `load_all()` ~line 68-94 — reference only, not expected to change based on current audit)

## Background
`scripts/shared/config_loader.py` has two merge code paths with different semantics:
- `load(*names)` (lines 58-66): builds `merged: dict[str, Any] = {}` and for each name does
  `merged.update(filtered)` — a flat, top-level overwrite only. No merge-depth note exists in its
  docstring.
- `load_all()` (lines 68-94): explicitly merges dict-valued keys one level deep —
  `if isinstance(val, dict) and isinstance(merged.get(key), dict): merged[key] = {**merged[key], **val}`
  — and its docstring states this explicitly: "Dict-valued keys are merged one level deep so that
  multiple MCP server config files can each contribute a `[mcp_servers.<key>]` section without
  overwriting entries from previously loaded files."

`tests/shared/test_config_loader.py::TestMergeOrder` contains four tests, all of which call
`loader.load("a.toml", "b.toml")` (not `load_all()`):
`test_later_file_overrides_earlier`, `test_first_file_values_preserved_when_no_overlap`,
`test_nested_dict_merge`, `test_meta_keys_filtered_from_both_files`. Three of the four assert
nested-dict values survive the merge (e.g. `result["section"]["bar"]`,
`result["mcp_servers"]["server_a"]["url"]`) — i.e. they assert `load_all()`-style one-level-deep
merge semantics against a method (`load()`) that only does a flat `dict.update()`.

## Problem
Running `PYTHONPATH=scripts pytest tests/shared/test_config_loader.py::TestMergeOrder -v` currently
produces 1 passed, 3 failed:
- `test_later_file_overrides_earlier`: `KeyError: 'bar'`
- `test_nested_dict_merge`: `KeyError: 'server_a'`
- `test_meta_keys_filtered_from_both_files`: `KeyError: 'foo'`

All three failures occur because `load()`'s flat `merged.update(filtered)` replaces the entire
top-level `[section]`/`[mcp_servers]` table from the first file with the second file's version of
that table, discarding sibling keys the first file defined, instead of merging the two tables one
level deep.

## Reason for change
A call-site audit was performed as required by the issue before deciding whether this is a
production bug or a test-authoring error:
- `grep -rn "\.load(" scripts --include=*.py` (excluding `load_all`) shows every production call
  to `ConfigLoader().load(...)` (and thin wrappers like `WebSearchConfig.load()`,
  `ShellConfig.load()`) passes exactly **one filename** — e.g.
  `scripts/mcp_servers/web_search/web_search_models.py:126: ConfigLoader().load("web_search_mcp_server.toml")`,
  `scripts/db/rotation.py:21: ConfigLoader().load("agent.toml")`,
  `scripts/rag/ingestion/ingester.py:63: ConfigLoader().load("ingester.toml")`.
  No production call site passes multiple filenames to `load()`, so no production code path
  currently depends on `load()` merging overlapping nested tables across files.
- `grep -rn "\.load_all(" scripts --include=*.py` shows 5 call sites (`rag/pipeline.py:74`,
  `rag/llm_client.py:68,81`, `agent/config_builders.py:60`, `agent/commands/cmd_config.py:53`),
  all no-arg/`strict=` only — these are the call sites that would actually benefit from the
  one-level-deep merge (e.g. multiple MCP server config files each contributing a
  `[mcp_servers.<key>]` section), and they already use `load_all()`, which already implements that
  merge correctly.

Because no caller relies on `load()` merging nested tables across multiple files, this is
conclusively case (a) from the issue: `TestMergeOrder` was written against the wrong method's
semantics, not a production bug. Changing `load()`'s merge depth to match `load_all()` would be an
unrequested behavior change to a documented, working, flat-merge API with no driving use case, and
is explicitly discouraged by the issue's own framing ("if in doubt about whether the shallow-merge
behavior is load-bearing, stop and report the call sites found rather than guessing" — the call
sites are not load-bearing here, so no doubt remains).

## Implementation intent
Fix `TestMergeOrder` to exercise the behavior it is actually meant to verify:
- The tests that only need flat top-level overwrite semantics (`test_later_file_overrides_earlier`,
  `test_first_file_values_preserved_when_no_overlap`, `test_meta_keys_filtered_from_both_files`)
  should keep calling `load()` but have their fixtures/assertions adjusted to match `load()`'s
  actual flat-overwrite behavior (i.e. stop asserting that sibling keys inside a
  later-overwritten top-level table survive).
- `test_nested_dict_merge` is specifically about the one-level-deep dict-merge behavior; it should
  be rewritten to call `load_all()` instead of `load()` (adjusting its fixture files to match
  `_BASE_CONFIG_FILES` naming/setup conventions used elsewhere in the test file, e.g. how other
  `load_all()` tests such as `TestLoadAllStrictMode` set up their fixtures), since that is the
  method that actually implements and documents this behavior.
- Do not change `load()` or `load_all()` production logic — the call-site audit shows no caller
  needs it, and the issue explicitly says not to change `load_all()`'s behavior and to only change
  `load()`'s behavior if a real caller depends on it (none do).
