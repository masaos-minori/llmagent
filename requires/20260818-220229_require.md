## Priority

High

## Background

The design documentation set already has a governance layer (`docs/00_governance_01` through `00_governance_08`) covering document classes, update rules, review triggers, evidence labels, Known Issues, and AI-reading metadata. However, verification against the current repository shows several concrete gaps that match the issue's claims:

- `docs/00_governance_02_canonical-source-rule.md` §General Rule still states, verbatim: "2. The most recently reviewed document is authoritative among conflicting documents." This is the exact rule the issue asks to remove.
- The same document's General Rule has only 3 precedence levels (code, most-recently-reviewed document, area document-guide), not the 7-level hierarchy needed to deterministically rank runtime code, ADRs, area specs, configuration, operations docs, notes, and Known Issues/Needs Confirmation against each other.
- No `adr/` directory exists anywhere in the repository (confirmed via `find`), and no document defines what an "approved ADR" is or where it lives, even though the canonical-source area table in `00_governance_02` already lists an `ADR` row pointing to `adr/`.
- `docs/00_governance_01_documentation-governance.md` §Change Impact Rule references "the area dependency graph" as something to consult, but no such graph exists in any file (confirmed via repo-wide grep for "dependency graph" — the only hit is the sentence describing the need for it).
- No RACI model, no change-impact matrix, and no CODEOWNERS (or equivalent) file exist anywhere in the repository (confirmed via grep and `find`).
- Each area's document guide (RAG, MCP, Agent, EventBus, Shared) defines its own "canonical source" section independently and inconsistently — some point to a source directory, some to superseded legacy files, some to "source code in general" — with no shared schema (canonical document guide / canonical specification / implementation entry point / configuration source / operations document / Known Issues document) across areas.
- The Overview and Deployment areas, both explicitly in scope per `00_governance_01`, have no `_00_document-guide.md` equivalent and no dedicated Known Issues document, unlike the other five areas.

## Problem

There is no single, deterministic, project-wide rule for resolving conflicts between runtime code, ADRs, area specifications, configuration, operations docs, and Known Issues/Needs Confirmation records. The existing rule set relies partly on document recency (explicitly disallowed by the issue) and partly on per-area conventions that are not uniform across areas. There is also no dependency graph between the eight governance areas, no change-impact matrix tying change types to required document updates, and no RACI/approval model defining who must review or approve governance, security, schema, API, cross-area, or deprecation changes. As a result, two AI agents (or a human and an AI agent) working from the same conflicting inputs can reach different, non-reproducible conclusions about which document to trust or update.

## Reason for change

Because the canonical-source rule currently permits "most recent review" to override area specifications or design intent, an implementation AI can legitimately update the wrong document, or leave a stale document unchanged because it happens to have a more recent review date. Because no area dependency graph or change-impact matrix exists, cross-area impacts of a change can go undocumented, and no reviewer/approver is guaranteed to be identified for governance, security, schema, or cross-area changes. These are exactly the risks the issue enumerates, and verification against the current repository confirms none of them has been closed by existing governance documents.

## Implementation intent

Revise the governance document set so that:

- `docs/00_governance_02_canonical-source-rule.md` states one deterministic, project-wide precedence order (runtime code/tests for behavior → approved ADRs for design intent → canonical area specifications → active configuration/generated config reference → operations/runbook docs → notes → Known Issues/Needs Confirmation), and no longer references document recency as a tie-breaker.
- Observable behavior (what code/tests currently do) and approved design intent (what an ADR says should happen) are treated as two distinct questions with two distinct authoritative sources, so a mismatch between them is classified as a "design deviation" or "outdated code" case rather than an unresolvable conflict.
- Each of the eight governance areas (Overview, Deployment, RAG, MCP, Agent, EventBus, Shared/DB, Governance) has exactly one canonical document guide, and that guide (or a shared governance document referencing all areas) records, per area: canonical specification, implementation entry point, configuration source, operations document, and Known Issues document — filling the gap for Overview and Deployment, which currently lack this structure.
- A new area dependency graph document defines the eight areas as nodes, documents dependency direction, and states which cycles (if any) are permitted, closing the gap referenced but never defined in `00_governance_01`.
- A new change-impact matrix maps each supported change type (architecture, configuration, command, behavioral, schema, security, documentation-only) to the document classes that must be updated, extending the existing but coarser Update Rule in `00_governance_01`.
- A documentation RACI model defines required reviewers/approvers for governance, security, DB schema, public API, cross-area, and deprecation changes, and defines merge conditions when Known Issues, Needs Confirmation items, deferred design decisions, or temporary implementation deviations are still open — and states how this model would map onto CODEOWNERS or an equivalent mechanism if one is introduced later (no such file exists today; this phase documents the mapping, it does not create the file).
- All area document guides are updated to link to the unified governance model and to stop stating area-specific canonical-source rules that conflict with the project-wide precedence order.

## Implementation instructions

1. In `docs/00_governance_02_canonical-source-rule.md`, replace the `## General Rule` section's 3-item list with the 7-level precedence order from the issue's "Canonical-Source Precedence" task list (runtime code/tests → approved ADRs → canonical area specs → active config/generated config reference → ops/runbook docs → notes → Known Issues/Needs Confirmation). Delete the sentence "The most recently reviewed document is authoritative among conflicting documents" and do not replace it with any other recency-based rule.
2. Add a subsection distinguishing "observable behavior" (governed by code/tests) from "approved design intent" (governed by ADRs), and update the existing `## Code vs Document Conflict Rule` classification (Outdated code / Design deviation / Provisional implementation / Bug / Missing documentation) to reference this distinction explicitly.
3. Replace or extend the existing "領域別の正典入口" table in `00_governance_02` (or move it into a new dedicated document, e.g. `docs/00_governance_09_area-canonical-map.md`) so each of the eight areas lists: canonical document guide, canonical specification, implementation entry point, configuration source, operations document, and Known Issues document. For Overview and Deployment, either identify an existing equivalent or explicitly record the gap (no document-guide/Known Issues doc exists today) so the acceptance criterion "every area has exactly one canonical document guide" can be met or explicitly tracked as unmet.
4. Create a new governance document for the area dependency graph (e.g. `docs/00_governance_10_area-dependency-graph.md`) defining the eight areas as nodes, edges with direction, and any permitted cycles. Update `00_governance_01`'s Change Impact Rule to reference this new document instead of the currently undefined "area dependency graph."
5. Create a new governance document for the change-impact matrix (e.g. `docs/00_governance_11_change-impact-matrix.md`) covering architecture, configuration, command, behavioral, schema, security, and documentation-only change types, each mapped to required document-class updates. This supersedes/extends the current per-type bullets in `00_governance_01`'s Update Rule.
6. Create a new governance document for the documentation RACI model (e.g. `docs/00_governance_12_raci-and-approval.md`) defining required reviewers/approvers for governance, security, DB schema, public API, cross-area, and deprecation changes; define merge conditions for open Known Issues, Needs Confirmation items, deferred design decisions, and temporary implementation deviations; and describe how this would align with CODEOWNERS or an equivalent mechanism (documenting the intended mapping only — do not create a CODEOWNERS file in this phase).
7. Update each area document guide (`docs/03_rag_00_document-guide.md`, `docs/04_mcp_00_document-guide.md`, `docs/05_agent_00_document-guide.md`, `docs/06_eventbus_00_document-guide.md`, `docs/90_shared_00_document-guide.md`) to remove area-local statements that conflict with the new project-wide precedence order, and to add a link to the new area-canonical-map, dependency-graph, change-impact-matrix, and RACI documents.
8. Update the "Related Governance Documents" cross-reference lists in every existing `00_governance_*` file to include the new documents created in steps 3-6.
9. This is a documentation-only phase: do not modify source code, do not create ADRs, do not create a CODEOWNERS file — only produce/update governance documentation and its cross-references.
