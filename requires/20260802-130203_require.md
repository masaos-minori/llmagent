# Confirm and document the actual GITHUB_TOKEN loading mechanism referenced by docs/02_deployment-part1.md §2.3

## Priority
Medium

## Target files
- `docs/02_deployment-part1.md` (§2.3 "実装上の補足(起動方法)", the line: `GitHub 操作: GITHUB_TOKEN を conf.d/github-mcp に設定`)
- `conf.d/github-mcp` (stale reload instruction)
- `conf.d/cicd-mcp` (same stale reload instruction, for consistency)
- `conf.d/web-search-mcp` (same stale reload instruction, for consistency)
- Reference only, no change expected: `scripts/mcp_servers/github/service_init.py`, `scripts/mcp_servers/cicd/service_init.py`, `scripts/agent/http_lifecycle.py`, `deploy/setup_services.sh`, `deploy/start_agent.sh`

## Background
The source issue claimed that `docs/02_deployment-part1.md` §2.3 references a `conf.d/github-mcp` setup mechanism that does not exist anywhere in the repository, and that the GitHub-related service_init modules only read `GITHUB_TOKEN` via `os.environ.get(...)`.

Verification against current source shows this premise is **factually incorrect on one point**: `conf.d/` is a real, git-tracked directory in this repository (`conf.d/github-mcp`, `conf.d/cicd-mcp`, `conf.d/git-mcp`, `conf.d/web-search-mcp`), and `conf.d/github-mcp` does define `GITHUB_TOKEN=""` exactly as the doc describes. The doc's one-line reference is not stale or fabricated.

However, verification also surfaces a **real, confirmed gap** the issue's underlying concern still points at:
- No code path anywhere in this repository (`deploy/setup_services.sh`, `deploy/start_agent.sh`, `scripts/agent/http_lifecycle.py`'s subprocess-spawn `env=dict(os.environ)` logic, or the `github`/`cicd` `service_init.py` modules) sources/reads `conf.d/*` files. `service_init.py` only reads `os.environ.get("GITHUB_TOKEN", ...)` from whatever the parent process's environment already contains.
- `conf.d/github-mcp` (and `conf.d/cicd-mcp`, `conf.d/web-search-mcp`) each contain a comment instructing the operator to run `python3 scripts/agent.py --reload-mcp <name>` after editing the file. No `scripts/agent.py` file exists (the CLI entrypoint is `scripts/agent/__main__.py`, invoked as `python -m agent`), and no `--reload-mcp` flag exists anywhere in the codebase — this instruction is stale/broken.
- A prior implementation record (`implementations/done/20260711-214727_cicd_mcp_server_github_token_config.md`, Assumption/Procedure step 2) already flagged the exact same open question when wiring up `cicd-mcp`'s token: it explicitly left "confirm by reading how `github_token` is resolved... at implementation time" and "systemd unit env file / `.env` loaded by the process manager" as unresolved, non-repo-local mechanisms — i.e. this was never actually settled, only deferred.

## Problem
`docs/02_deployment-part1.md` §2.3 tells a deployer to "set `GITHUB_TOKEN` in `conf.d/github-mcp`" but never explains how a value placed in that file actually reaches the running agent/MCP-server process's environment. Nothing in this repository sources `conf.d/*` automatically (no OpenRC/systemd unit, no `EnvironmentFile=`-equivalent, no Python loader). A deployer who edits `conf.d/github-mcp` and expects `GITHUB_TOKEN` to take effect (e.g. via the documented `--reload-mcp` command) will find the reload command doesn't exist, and may have no reason to suspect the file needs to be manually `source`d or exported into the shell/service environment before the agent process starts.

## Reason for change
Leaving this undocumented risks the exact failure mode the original issue warned about: a deployer follows the documented procedure, `GITHUB_TOKEN` never actually reaches the running process, and GitHub-dependent features (`github-mcp`, `cicd-mcp`) silently continue operating at the unauthenticated 60 req/hr rate limit (or fail outright for `cicd-mcp`, which requires a token for all 4 tools) with no clear error pointing back to the setup step.

## Implementation intent
Do not invent or assert an env-loading mechanism that isn't confirmed. Two possible outcomes exist depending on what the actual production deployment does (per the issue's own instruction, this must be confirmed with the document author/operator or by tracing a live deployment before writing the fix):
1. If production actually sources `conf.d/<name>` into the environment via some external mechanism (e.g. an OpenRC service wrapper, a systemd `EnvironmentFile=` directive, or a manual `source`/`export` step in an onboarding runbook not present in this repo) — document that mechanism explicitly in §2.3, replacing the current single unexplained line.
2. If no such mechanism exists yet in production — correct §2.3 to state plainly that the operator must manually export `GITHUB_TOKEN` (e.g. `source conf.d/github-mcp && export GITHUB_TOKEN` before starting the agent process, or set it directly in the shell/service environment) rather than implying an automatic pickup.

Either way, also fix the stale `python3 scripts/agent.py --reload-mcp <name>` comment inside `conf.d/github-mcp`, `conf.d/cicd-mcp`, and `conf.d/web-search-mcp` to reference a command that actually exists (or remove the reload claim if no such reload path exists yet), since this is a second, independently-confirmed inaccuracy discovered while investigating the issue.
