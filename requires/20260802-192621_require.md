## Background
The source issue (`issues/20260802-080020_rag_unused_dto_investigation_and_consolidation.md`) originally
flagged four DTOs/dataclass groups as confirmed-unused-via-grep across `docs/03_rag_04_01`, `04_03`, `04_04`,
and `04_05`, asking for a design-owner decision (forward-looking placeholder vs. dead code) and a single
consolidated record instead of four scattered mentions.

Re-verification against the current repo state (2026-08-02) shows two of the four items are **already fully
resolved** by prior work and no longer need action:

- `AuditLogRecord`/`ApprovalDecision` (`04_03`): resolved as NC-005
  (`docs/00_governance_07_needs-confirmation-inventory.md` §NC-005). Both classes were deleted from
  `scripts/rag/models_audit.py` (commit `556490796`); `docs/03_rag_04_03_dto-models_audit.md` already carries
  an explicit `**Status**: deleted` line. Confirmed via grep: no `AuditLogRecord`/`ApprovalDecision` symbols
  remain anywhere under `scripts/`.
- `PipelineRunResult.result_source` (`04_05`): resolved as NC-006. The field was removed from
  `scripts/rag/types.py` entirely (commit `556490796`); `PipelineRunResult` has no `result_source` field
  today. The name `result_source` still exists in the codebase, but only as an unrelated, actively-used field
  on a different class, `SearchDiagnostics.result_source` (`scripts/rag/models_result.py:102`), which NC-002
  separately confirmed is not dead code. `docs/03_rag_04_04_dto-models_config.md` and
  `docs/03_rag_04_05_dto-types.md` already document this resolution.

The remaining two items are still open and still match the issue's original description:

- **`RegisteredDocument`** (`scripts/rag/models_data.py:62`, doc `04_01`): grep confirms zero references
  outside its own definition. Unlike the other three DTOs, `docs/03_rag_04_01_dto-models_data.md` does not
  even mention it as possibly-unused today — it is silently absent from the doc's field-by-field description,
  and no entry in `docs/00_governance_07_needs-confirmation-inventory.md` tracks it. The forward-vs-dead
  question for this DTO has never been recorded anywhere.
- **`models_config.py` dataclasses** (`MqeConfig`, `FusionConfig`, `RerankConfig`, `SearchConfig`,
  `ChunkSplitterConfig`, `IngesterConfig`, `PipelineConfig`, doc `04_04`): grep confirms none of these are
  imported or instantiated outside their own definition file. `docs/03_rag_04_04_dto-models_config.md` already
  documents this grep evidence in detail (an "実装上の補足" section), including the observation that
  `ConfigLoader().load("xxx.toml")` returns raw `dict`s consumed via `cfg.get("key", default)` in
  `scripts/rag/ingestion/chunk_splitter.py` / `ingester.py`, bypassing these dataclasses entirely — and that
  `shared/types.py`'s `RagConfig` Protocol docstring describes `rag.models_config.*` as the intended file-format
  DTOs for ingestion TOML. However, the doc stops short of a decision: it records the grep evidence but never
  states whether this is (a) a not-yet-wired-up future validation layer that should be kept, or (b) a stale
  scaffold that should be deleted. No NC entry and no `03_rag_90` entry exists for this open question.

`docs/03_rag_90_inconsistencies_and_known_issues.md` currently has no populated entries at all (only
frontmatter and a migration note) — it documents an entry format (`Type / Impact / Description / Safe
interpretation / Recommended action / Source`) but the file body has zero instances of it. This is the
designated consolidation target per the original issue's "Target Files" scope.

## Problem
Two genuinely-still-unresolved DTO groups (`RegisteredDocument`, `04_04` config dataclasses) each have an
undetermined forward-looking-vs-dead-code status that cannot be settled from code or docs alone, and the
information that does exist about them (grep evidence, in `04_04`'s case) is not recorded in a discoverable,
consolidated known-issues location. `RegisteredDocument` has no record of the question at all.

## Reason for change
Per the source issue: scattering the open question across multiple files makes it hard to track and resolve,
and a design-owner decision is required before any future cleanup or removal work can be safely undertaken.
Consolidating now (with the two already-resolved items correctly dropped from scope) keeps the tracking
document accurate and avoids re-litigating settled questions.

## Implementation intent
- For each of the two still-open DTO groups, seek an explicit design/implementation-owner decision on
  whether it is an intentional forward-looking placeholder (keep) or removable dead code (candidate for a
  future, separate deletion issue).
- Where a decision cannot be obtained, register the item as an explicit open Needs-Confirmation entry rather
  than guessing — per the source issue's own "AI Implementation Instruction".
- Record both outcomes as entries in `docs/03_rag_90_inconsistencies_and_known_issues.md`, using the file's
  documented entry format (`Type / Impact / Description / Safe interpretation / Recommended action / Source`).
- Replace the scattered per-file notes in `04_01` and `04_04` with a short reference to the consolidated
  `03_rag_90` entry (do not delete the underlying grep evidence/field tables — just stop repeating the open
  question in place).
- Do not touch `04_03` or `04_05` beyond what is already there — both are already correctly marked resolved
  and are out of scope for this requirement.
