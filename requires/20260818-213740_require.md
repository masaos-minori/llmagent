# Remove dead MCP-degraded-reason bookkeeping in McpServerHealthRegistry

## Priority
Medium

## Target files
- `scripts/shared/mcp_health.py` (`McpServerHealthRegistry.record_degraded()`, `get_degraded_reason()`, `_degraded_reasons` field, and their use inside `record_success()`)
- `scripts/agent/commands/cmd_mcp.py` (`_write_servers_in_state()`, the sole caller of `get_degraded_reason()`)
- `tests/shared/test_mcp_health_degraded.py`
- `tests/agent/commands/test_cmd_mcp.py` (assertions that mock `get_degraded_reason`)

## Background
Source issue `issues/20260817_03_issue.md` ("[TECH-DEBT] Remove or justify unreachable dead code paths") flagged three members as unreachable: `route_resolver`'s unused constructor inputs, `McpServerHealthRegistry.record_degraded()` / `get_degraded_reason()`, and `RETENTION_DAYS`.

Re-verification against the current codebase (2026-08-18) shows two of the three items are no longer applicable:
- `ToolRouteResolver.__init__()` in `scripts/shared/route_resolver.py` already carries explicit "kept for X" justification notes in its docstring for `server_configs` (backward compatibility, not read/stored), `discovery_map` (feeds the currently-unreachable `_log_routing_coverage()` diagnostic), and `known_tools` (no production caller today, kept for a future coverage-visibility caller). This already satisfies the issue's own acceptable resolution ("annotate each as a deliberate extension point with a short note").
- `RETENTION_DAYS` (`scripts/agent/memory/enums.py`) now has a real consumer: `scripts/agent/memory/jsonl_store.py::read_active()` calls `RETENTION_DAYS.get(source_key)` to drive per-source-type memory expiry filtering. It is not dead.

The third item is still valid: `McpServerHealthRegistry.record_degraded(server_key, reason=None)` (`scripts/shared/mcp_health.py:54`) has no production caller anywhere in `scripts/` — grepping the whole tree shows only unit tests invoke it. Because nothing ever writes to `self._degraded_reasons`, `get_degraded_reason()` (`scripts/shared/mcp_health.py:84`) always returns `None` in production. `get_degraded_reason()` itself is NOT dead code by the narrow definition (it IS called, from `cmd_mcp.py:163` inside `_write_servers_in_state()`), but the data path feeding it is: the caller's `reason_str = f": {reason}" if reason else ""` line always evaluates to an empty string in real runs, so the "degraded reason" ever shown to a user via `mcp status` is permanently blank. This is exactly the "misleading reader" hazard the original issue described — a watchdog-era mechanism whose writer was removed but whose reader and storage still ship as if it were live.

## Problem
`McpServerHealthRegistry` maintains a `_degraded_reasons: dict[str, str]` bookkeeping dict and a `record_degraded()` writer method that no production code path calls. The corresponding reader, `get_degraded_reason()`, is wired into the `mcp status` command's degraded-server display but can only ever return `None` today, making that part of the CLI output permanently vestigial while looking functional. This costs reviewer attention and risks a future contributor assuming the mechanism is live and building on it.

## Reason for change
Per the issue's stated intent: eliminate members that cannot execute so the MCP health contract reflects only what the system actually does, unless a concrete caller is reinstated. No watchdog or other component currently sets a degraded reason, so keeping the writer/reader/storage triplet around is unjustified dead weight.

## Implementation intent
Resolve this the same way the issue allows for other items: either (a) remove `record_degraded()`, `get_degraded_reason()`, and the `_degraded_reasons` dict (including its clearing in `record_success()`), and simplify `cmd_mcp.py::_write_servers_in_state()` to drop the now-pointless reason lookup/format, or (b) if a near-term caller (e.g., a reinstated watchdog, or a probe in `mcp_status.py`) is planned, wire in that concrete caller now instead of leaving the mechanism inert, and add a short docstring note explaining why it is kept per the issue's own fallback option. Prefer (a) unless there is a concrete, already-planned caller; do not invent a speculative one.

## Implementation instructions
1. Confirm no other caller of `record_degraded()` exists beyond `tests/shared/test_mcp_health_degraded.py` (re-grep at implementation time in case other work landed first).
2. If removing (preferred path, absent a concrete reinstated caller):
   - Delete `record_degraded()` and `get_degraded_reason()` from `scripts/shared/mcp_health.py`.
   - Delete the `_degraded_reasons` field and its initialization in `__init__`, and its clearing line in `record_success()`.
   - Update `scripts/agent/commands/cmd_mcp.py::_write_servers_in_state()` to remove the `reason`/`reason_str` lookup and the `{reason_str}` interpolation, since it will always be empty; keep the rest of the label/server-key output unchanged.
   - Remove `tests/shared/test_mcp_health_degraded.py` (or the subset of tests that exercise only the removed writer/reader pair) and update `tests/agent/commands/test_cmd_mcp.py` to stop mocking `get_degraded_reason` and instead assert the plain `[DEGRADED] {key}` line without a reason suffix.
   - Update `scripts/shared/mcp_health.py`'s module/class docstrings if they reference the degraded-reason mechanism, so documentation matches the reduced surface.
3. If instead reinstating a caller: implement the concrete call site that invokes `record_degraded()` with a real reason at the point a degraded probe occurs, and leave the reader/storage in place; add a one-line docstring justification only if any residual unused parameter remains.
4. Do not touch `route_resolver.py`'s constructor parameters or `RETENTION_DAYS` — both are already resolved per the Background section; re-touching them is out of scope for this requirement.
5. Do not touch `tool_cache.ToolResultCache` — explicitly out of scope per the source issue.
