# Clarify WAL TRUNCATE checkpoint failure behavior in docs/01_overview-arch-03-features.md

## Priority
Medium

## Target files
- `docs/01_overview-arch-03-features.md` (session-end diagnostic save section, currently ~lines 62-70)

## Background
`docs/01_overview-arch-03-features.md` documents the session-end diagnostic save
sequence performed in the REPL loop's `finally` block: (1) save session diagnostics
to `DiagnosticStore`, (2) persist session memory, (3) run a WAL TRUNCATE checkpoint on
`session.sqlite` before closing the connection. The doc states that a WAL TRUNCATE
checkpoint is executed but does not describe what happens if that checkpoint fails —
whether the process still exits cleanly, and what state the WAL file is left in for the
next startup.

## Problem
An operator who encounters a failed WAL checkpoint (e.g. in logs) has no documented
guidance on whether this is safe (process exits, no data loss) or whether it signals a
risk that needs attention. The doc is silent on failure-path behavior.

## Reason for change
This is a recovery/failure-understanding gap. Per `rules/coding.md` §"Documentation
notes — Current behavior classification", an undocumented behavior gap must be
classified before being written up; source investigation below confirms this is an
"Accepted current specification" case (the behavior is correct/intentional and already
implemented with a safety net), so it should be written as plain prose, not as an
unlabeled "Current behavior" callout or an issue.

## Implementation intent
Extend the existing session-end diagnostic save description in
`docs/01_overview-arch-03-features.md` with a short, factual note on WAL TRUNCATE
checkpoint failure behavior, based on the verified source behavior below. No source
code changes are implied or required — this is a documentation-only clarification of
already-implemented, already-safe behavior.

### Verified source behavior (investigated in `scripts/agent/repl.py`, class members
`_wal_checkpoint_sync`, `_wal_backup_sync`, `_close_resources`)

- `_wal_checkpoint_sync` (repl.py:263-323) first attempts a PASSIVE checkpoint; if that
  is slow (>5s) or raises `sqlite3.Error`, it falls back to a TRUNCATE checkpoint with up
  to 3 attempts and exponential backoff (1s, 2s). If all 3 TRUNCATE attempts raise
  `sqlite3.Error`, the method logs an error and returns `(False, errors)` — it does not
  raise.
- `_close_resources` (repl.py:400-468), invoked from `run()`'s `finally` block
  (repl.py:700-803), calls `_wal_checkpoint_sync` via `loop.run_in_executor` under a
  30s timeout (`_WAL_CHECKPOINT_TIMEOUT_S`). A timeout or `sqlite3.Error` here is also
  only appended to a local `errors` list, never re-raised.
- If the checkpoint did not succeed (`truncated_or_ok is False` — covers TRUNCATE
  failure, exception, and timeout), `_close_resources` calls `_wal_backup_sync`
  (repl.py:341-398) under a 10s timeout. This copies the `session.sqlite-wal` file to a
  timestamped backup path (`{db_path}-wal-backup-{session_tag}-{unix_time}`) next to the
  DB file, guarded by an `allowed_root` path check and a backup-directory
  writability check. This backup step is best-effort: its own failures are likewise only
  logged and appended to `errors`, never raised.
- After the checkpoint/backup attempts, `_close_resources` continues to shut down
  services (`svc.lifecycle.shutdown_all()`, `svc.http.aclose()`) unconditionally,
  independent of whether the checkpoint or backup succeeded. All collected errors are
  logged as a single summary at the end (repl.py:466-468) but never raised — so
  **the process always exits cleanly regardless of WAL TRUNCATE checkpoint outcome**.
  Because `_close_resources` runs inside `finally` (not inside the WAL-checkpoint `try`
  itself), no exception from checkpoint/backup can prevent this cleanup or process exit.
- **WAL file state on next startup**: SQLite's WAL semantics mean that a failed
  checkpoint leaves all committed transactions durably recorded in the (now larger,
  un-truncated) `-wal` file. No committed data is lost — the next process to open the
  database (via `SQLiteHelper("session").open(...)`) will read committed frames from the
  WAL as needed and SQLite will attempt its own checkpoint opportunistically on
  subsequent writes/opens. In addition to the underlying no-data-loss guarantee, this
  codebase adds a defense-in-depth WAL file backup step described above, which is not
  currently documented at all.
- Conclusion: **this is a confirmable, verified, and already-safe behavior** — not a
  bug and not something requiring a Needs Confirmation entry. It falls under the
  "Accepted current specification" classification in `rules/coding.md`.

## Implementation instructions
1. In `docs/01_overview-arch-03-features.md`, in the "セッション終了時の診断保存"
   subsection (item 3, WAL TRUNCATE checkpoint), add one or two sentences (in the
   existing Japanese prose style of that section, consistent with surrounding
   `(根拠: ...)` citation convention) stating:
   - If the WAL TRUNCATE checkpoint fails (after PASSIVE checkpoint and 3 TRUNCATE
     retries with backoff), the process still exits cleanly; no exception propagates
     from `_close_resources`.
   - On failure, the WAL file (`session.sqlite-wal`) is additionally backed up to a
     timestamped path via `_wal_backup_sync` as a defense-in-depth measure (best-effort;
     failures here are also only logged).
   - On the next startup, SQLite resumes with the enlarged (un-truncated) WAL file; no
     data loss is expected because WAL retains all committed transactions, but operators
     should treat repeated checkpoint failures as worth monitoring (e.g. growing WAL
     file size).
   - Cite `agent/repl.py` (`_wal_checkpoint_sync`, `_wal_backup_sync`,
     `_close_resources`) as the source, consistent with the doc's existing `(根拠: ...)`
     citation style.
