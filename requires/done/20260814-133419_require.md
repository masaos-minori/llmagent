# Add ast-grep constraint to prevent git.exc import false positive recurrence

## Priority
Low

## Target files
- `rules/coding.md` — add constraint check pattern
- `.pre-commit-config.yaml` — optionally wire the constraint as a pre-commit hook
- Any future file that adds `import git` and references `git.exc.<Name>` without `import git.exc`

## Background
Discovered while running the requirement-to-plan workflow for `requires/20260813-141541_require.md` (plan: `plans/20260813-185356_plan.md`), which fixes the 2 currently-known call sites of the `git.exc.*` pyright `reportAttributeAccessIssue` false positive by adding an explicit `import git.exc` alongside the existing `import git` at each site. The requirement's Background section already flags this as "a repeated pattern (same root cause at 2+ call sites), not an isolated typo."

## Problem
The fix is purely import-shape, applied by hand at each of the 2 known call sites. Neither `scripts/shared/git_helper.py` nor `scripts/mcp_servers/git/git_service.py` currently includes `import git.exc` despite referencing `git.exc.*`. There is no lint rule, `ast-grep` pattern, or pre-commit hook that would catch a future call site added via `import git` followed by `git.exc.<Name>` without the accompanying `import git.exc`. A contributor who copy-pastes the old (pre-fix) pattern from git history, another project, or an LLM-generated snippet would silently reintroduce the same pyright false positive, and it would only surface the next time someone runs `pyright` broadly and has to re-diagnose a root cause that is already fully understood today.

## Reason for change
This is a structurally cheap gap to close (a single `ast-grep`/`rg` pattern could flag `import git` co-occurring with `git.exc.` but not `import git.exc` in the same file), but doing so is out of scope for `plans/20260813-185356_plan.md`, whose acceptance criteria are scoped to the 2 currently-known call sites and explicitly exclude adding new tooling/stub dependencies. Leaving it unfiled would mean the recurrence risk is undocumented once the current fix lands.

## Implementation intent
Add a repo-local constraint check that flags any file matching `import git` where `git\.exc\.` appears in the body but `import git.exc` does not. Wire it into `.pre-commit-config.yaml` as a low-cost hook.

## Implementation instructions
1. Add a constraint check pattern alongside the existing `ast-grep` one-liners in `rules/coding.md` §Constraint checks:
   - Pattern: `rg -l "git\.exc\." scripts/ | xargs -I{} sh -c 'grep -q "^import git.exc" {} || echo {}'`
   - Verify/refine the exact command before wiring it in.
2. Wire the constraint into `.pre-commit-config.yaml` as a low-cost hook, mirroring how `check-suppression-justification` is wired in per `rules/coding.md`.
3. Scope this as its own small requirement/plan since it adds a new constraint-check pattern rather than touching `git_helper.py`/`git_service.py` again.

## Acceptance criteria
- A constraint check exists that detects any file with `git.exc.` usage but missing `import git.exc`.
- The constraint check is either documented in `rules/coding.md` and/or wired into `.pre-commit-config.yaml`.
- No regression in CI — the constraint should pass on the current codebase after the existing fixes land.

## Tests
