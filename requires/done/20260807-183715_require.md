# Reduce template-memo-style detail in docs/06_eventbus_90_inconsistencies_and_known_issues.md

## Priority
Medium

## Target files
`docs/06_eventbus_90_inconsistencies_and_known_issues.md`

## Background
This chapter is the canonical source for known issues and deferred items (per `memo-doc-eventbus-review.md` §「章間の正本ルール」: 既知問題・保留事項 = `06_eventbus_90_inconsistencies_and_known_issues`), but a Known Issues section that degrades into a bug-list-with-metadata-fields loses its value as an operational reference, per this memo's explicit prohibition (§「禁止事項」: Known Issues を単なるバグ一覧にすること).

Note: `memo-doc-eventbus-review.md` has been deleted since this issue was created, but the issue's claims remain valid based on independent verification against the source codebase.

## Problem
The known-issues chapter contains the full 17-field issue template, unverified metadata fields (Owner / First Found / Target / Related), Statement A/B-style migration memos, detailed implementation file/test names, and a plain schema-vs-implementation-difference table — all of which violate the design-doc reduction policy and reduce the chapter's value as an operational reference.

## Reason for change
A Known Issues section that becomes a bug-list-with-metadata-fields loses its value as an operational reference. The chapter should focus on operational meaning, not metadata templates.

## Implementation intent
Restructure each entry to explain what the issue means, why it matters, what to watch for operationally, and the criteria for deciding whether/how to address it — not a metadata template or diff memo.

## Implementation instructions
1. Read `memo-doc-eventbus-review.md` §「06_eventbus_90_inconsistencies_and_known_issues」 if available, or use the guidance below.
2. Keep: the meaning of each known issue, why it is a problem, operational cautions, fix-decision criteria, the reasoning behind each deferred item, the operational impact of Agent integration being unimplemented, the operational impact of ack-offset monotonicity not being guaranteed.
3. Replace the full 17-field issue template, unverified metadata fields (Owner / First Found / Target / Related), Statement A/B-style migration memos, detailed implementation file/test names, and plain schema-vs-implementation-difference table with concise operational summaries.
4. Verify each entry against current code per `rules/coding.md` §「Documentation notes — "Current behavior" classification」 whether the discrepancy still applies before keeping or deleting it. Classify every entry using the five-way classification: Accepted current specification / Implementation fix required / Documentation fix required / Issue already tracked / Obsolete and removable.
5. The note that `promote_to_dlq()` is not on the production path may be kept, but only briefly as an implementation detail (this chapter is the destination for that relocated note from `06_eventbus_02_04_dlq-background-loop`, per that issue).
6. When in doubt whether a detail is operationally-critical, keep it. Mark unclear rationale as `Needs Confirmation`.
7. If a new "Implementation fix required" item is discovered, file it as a separate issue rather than implementing a fix.
8. Manually check internal Markdown links after editing.

## Acceptance criteria
- The chapter follows the standard template from `memo-doc-eventbus-review.md` §「修正後の章構成テンプレート」 where applicable to a known-issues chapter.
- No entry uses the full 17-field template or unverified metadata fields; each entry states operational meaning instead.
- Every entry is classified per `rules/coding.md`'s five-way classification (Accepted current specification / Implementation fix required / Documentation fix required / Issue already tracked / Obsolete and removable) before being kept, cross-referenced, or deleted.
- The Agent-integration-unimplemented and ack-offset-non-monotonicity impact statements remain explicit.
