# Make sensitive field filtering configurable in DiagnosticStore

## Priority
High

## Target files
- scripts/agent/diagnostic_store.py
- scripts/agent/config_dataclasses.py

## Background
During adversarial review of the agent startup process, we traced the full diagnostic store flow through diagnostic_store.py. The DiagnosticStore stores data in session_diagnostics table and handles encryption/retention settings via DiagnosticsConfig. The _filter_sensitive_fields() method redacts artifacts and rag_stage_outcomes, but there's no evidence of comprehensive field-level validation against the DiagnosticsConfig schema. If new fields are added to diagnostics without updating _filter_sensitive_fields(), they could leak sensitive information.

## Problem
The list of sensitive fields (`_SENSITIVE_FIELDS`) is hardcoded as a tuple of strings ("artifacts", "rag_stage_outcomes") in diagnostic_store.py. There is no mechanism to configure which fields should be filtered based on DiagnosticsConfig or any other configuration source. When new diagnostic fields are added that may contain sensitive data (e.g., API keys, tokens, credentials), they will not be filtered unless a developer manually updates `_SENSITIVE_FIELDS`. This creates a latent security risk where sensitive data could be persisted unredacted.

Additionally, while `_SENSITIVE_PATTERNS` provides regex-based secret detection as a secondary safeguard, it only raises an exception when encryption is disabled — it does not redact the matched content, leaving the raw secret in the stored diagnostic row.

## Reason for change
The current approach relies on developers remembering to update a hardcoded list whenever a new sensitive field is introduced. A configurable approach would ensure that sensitive field filtering keeps pace with the evolving set of diagnostic fields without requiring manual code changes.

## Implementation intent
Make the list of sensitive fields configurable via DiagnosticsConfig. Add a new field to DiagnosticsConfig that specifies which payload keys should be filtered. Update _filter_sensitive_fields() to merge the configured fields with the existing hardcoded list, ensuring backward compatibility.

## Implementation instructions
1. In `scripts/agent/config_dataclasses.py`, add a new field to DiagnosticsConfig:
   ```python
   # Payload keys treated as sensitive and filtered by _filter_sensitive_fields().
   # Defaults include "artifacts" and "rag_stage_outcomes"; additional keys
   # may be specified here without modifying diagnostic_store.py.
   sensitive_fields: frozenset[str] = frozenset(("artifacts", "rag_stage_outcomes"))
   ```

2. In `scripts/agent/diagnostic_store.py`, modify `_filter_sensitive_fields()`:
   - Load DiagnosticsConfig via `_load_diagnostics_config()`
   - Merge configured sensitive fields with the hardcoded list
   - Apply filtering to all merged fields

3. Update the docstring of `_filter_sensitive_fields()` to reflect that the field list is now configurable.

4. Update the module-level comment above `_SENSITIVE_FIELDS` to note that the list is augmented by DiagnosticsConfig.

## Acceptance criteria
- [ ] All sensitive fields are filtered regardless of how many exist
- [ ] Adding new fields to diagnostics doesn't require manual updates to _filter_sensitive_fields()
- [ ] No regressions in normal operation when registry is available
- [ ] Backward compatibility: existing configurations without the new field still work correctly

## Tests

- Integration test verifying diagnostic output during startup/shutdown shows filtered values
- Test verifying that DiagnosticsConfig.sensitive_fields defaults to the original hardcoded list when not specified

## Documentation Impact
If DiagnosticsConfig is extended, update documentation to reflect the new state.

## Out of Scope

- Adding retry logic for health checks
