## Background
The tool-execution layer currently has two separate execution engines, selected by a
single config flag, `execute_all_tool_calls()` in `scripts/agent/tool_runner.py:526-530`:

```python
if not ctx.cfg.tool.serial_tool_calls:
    results = await _execute_with_dag(ctx, approved_calls, turn)
else:
    results = await _execute_standard(ctx, approved_calls, turn)
```

`_execute_standard()` (`tool_runner.py:423-503`) uses the static `is_side_effect()`
helper (imported at line 26, called at line 434) to decide whether to downgrade the
whole batch to fully serial. `_execute_with_dag()` (`tool_runner.py:315-420`) instead
uses `ToolSpec`/`build_execution_groups()` in `scripts/agent/tool_scheduler.py`. The
module docstring in `tool_scheduler.py:11-22` explicitly documents these as "two
distinct, intentionally-separate serialization mechanisms" that "are not unified
today" — this is acknowledged, not accidental, technical debt.

Verified against current source on 2026-08-13 (commit `4dcd7bee4`, which refactored
unrelated helpers in `tool_runner.py` and made no scheduling-logic changes — confirmed
via `git show 4dcd7bee4 -- scripts/agent/tool_runner.py`). All defects below were
independently re-confirmed by reading `tool_scheduler.py` and `tool_runner.py` in
full, including the tests that currently assert the buggy behavior as expected:

1. **Scope-less writes run concurrently.** `write_first` (built at
   `tool_scheduler.py:99-100`) is scheduled as `ScheduledBatch(groups=[write_first],
   serialize_flags=[False])` (`tool_scheduler.py:122-123`). Since `serialize=False`,
   `_run_group_calls()` (`tool_runner.py:98-112`) executes all calls in that group via
   `asyncio.gather`, i.e., multiple no-scope **write** tools run concurrently with each
   other. Locked in by `test_write_first_group_is_gathered_concurrently`
   (`tests/agent/test_tool_scheduler.py:293-305`) and
   `test_write_first_batch_has_serialize_false`
   (`tests/agent/test_tool_scheduler_serialization.py:93-101`).
2. **`requires_serial` calls lose their original position.** The build loop
   (`tool_scheduler.py:89-102`) unconditionally appends any `requires_serial` call to a
   `serial_barrier` bucket first, and `groups` emits all `serial_barrier` entries before
   resource/write/parallel groups (`tool_scheduler.py:104-112`), regardless of the
   call's original index. Locked in by `test_serial_tool_precedes_parallel_tools`
   (`tests/agent/test_tool_scheduler.py:61-72`), which asserts the serial group is
   `groups[0]` even when the serial call appeared second in the input.
3. **Reads never conflict with writes on the same resource.**
   `tool_scheduler.py:95-102` only routes `is_write=True` calls with a scope into
   `resource_groups`; every read (`is_write=False`) always goes to `parallel`,
   irrespective of its `resource_scope`. `resource_groups` and `parallel` are combined
   into one `ScheduledBatch` executed together via `asyncio.gather`
   (`tool_scheduler.py:125-135`, executed at `tool_runner.py:366-371`), so a read
   against a resource a concurrent write is touching is never serialized against it.
4. **Metadata is effectively keyed by tool name, not call.** `ToolSpec.call_id` exists
   (`scripts/shared/tool_spec.py:26`) but is hard-coded to `""` when the metadata map is
   built (`tool_runner.py:73`, `call_id=""`). The default resource scope is the tool's
   own name (`_default_scope = name if _is_write else ""`, `tool_runner.py:71`), and
   `resource_groups` (`tool_scheduler.py:85,98`) is keyed on that scope string — i.e.
   per-tool-name, not per-call. Two calls to the same tool with different arguments
   cannot be scheduled with different scopes. (This overlaps with, and depends on, the
   call-level `ToolSpec`/resource-scope work already filed in
   `requires/20260813-140532_require.md`.)
5. **`groups` and `serialize_flags` are separate parallel arrays that can desync.**
   `ScheduledBatch` (`tool_scheduler.py:48-55`) defines `groups: list[list[dict]]` and
   `serialize_flags: list[bool]  # parallel to groups` as two independently-built lists
   with no structural guarantee of matching length; `zip()` at `tool_runner.py:366-371`
   silently truncates on any mismatch instead of erroring.
6. **The scheduler returns two execution-group representations; the runner uses only
   one.** `build_execution_groups()` returns `(groups, metadata)`, where
   `metadata.concurrent_groups` is a second, independent execution-group list
   (`tool_scheduler.py:70-141`). `_execute_with_dag()` captures the flat `groups` return
   value into `_groups` (underscore-prefixed, explicitly unused, `tool_runner.py:330`)
   and only ever iterates `metadata.concurrent_groups` (`tool_runner.py:359-372`). Tests
   confirm this by uniformly naming the flat return `_groups`
   (e.g. `tests/agent/test_tool_scheduler_serialization.py:37,50,63`).
7. **Serialization events fire for one-call groups with no real concurrency
   prevented.** The `serial_barrier` events loop (`tool_scheduler.py:143-154`)
   unconditionally emits a `_SerializationEvent(tools_count=1, ...)` for every
   `requires_serial` tool, even when it is the only call in the batch. Locked in by
   `test_serial_barrier_event_fields`
   (`tests/agent/test_tool_scheduler_serialization.py:112-120`).
8. **`requires_serial` events hard-code `is_write=True`.** `tool_scheduler.py:146-153`
   sets `is_write=True` in the `_SerializationEvent` unconditionally, never consulting
   the tool's actual `meta.is_write`. `test_serial_barrier_event_fields`
   (`tests/agent/test_tool_scheduler_serialization.py:112-120`) exercises a
   `requires_serial=True` spec whose `is_write` defaults to `False` (per the `_spec`
   helper signature) and still asserts `evt.is_write is True` — proving the bug is
   test-locked, not merely untested.
9. `ToolConfig.serial_tool_calls` (`scripts/agent/config_dataclasses.py:161`) carries
   only the comment `# When True, tool calls execute one by one instead of
   asyncio.gather()` — it documents only the `_execute_standard()` behavior and says
   nothing about the flag switching the entire scheduler implementation.

This issue (filed as Issue 03 in a three-issue dependency chain) depends on the
call-level `ToolSpec`/resource-scope/schema-2.0 work in
`requires/20260813-140532_require.md` (source: `issues/done/20260807_21_issue.md`) and
the fail-closed tool-call-preparation work in
`requires/20260813-140801_require.md` (source: `issues/done/20260807_22_issue.md`),
because the DAG planner defined here must receive only already-prepared, already
call-ID-scoped tool calls.

## Problem
There are two tool-execution engines with different, disagreeing safety rules, gated
by one boolean config flag (`serial_tool_calls`). Changing that flag changes not only
concurrency but also which source of truth governs write safety. Independently of the
duplication, the currently-active DAG scheduler (`build_execution_groups()`) has eight
concrete correctness defects (enumerated above): scope-less writes run concurrently
with each other, `requires_serial` calls are hoisted out of their original position
instead of acting as true barriers, reads are never checked against same-resource
writes, scheduling metadata is effectively tool-name-keyed rather than call-ID-keyed,
the scheduler's two return values (`groups` and `metadata.concurrent_groups`) can
diverge from each other with the runner blindly using only the second, and
serialization-audit events both over-fire (single-call groups) and misreport
(`is_write` hard-coded to `True`) the actual scheduling decision.

## Reason for change
Concurrent tool execution safety cannot rely on a scheduler whose write-conflict
detection and audit trail are demonstrably wrong, nor on two independent execution
engines whose safety guarantees differ. The current defects create realistic
correctness failures — for example, two scope-less writes (e.g. two shell commands
each performing an unscoped file write) executing concurrently via `write_first`, or a
directory read racing a descendant-path write because reads never enter conflict
detection. Because several of the current tests assert this buggy behavior as
*expected*, the defects will persist and regress silently unless the scheduler is
replaced and the tests rewritten to assert the corrected behavior.

## Implementation intent
Establish one deterministic DAG execution planner that is the sole execution path for
every prepared, approved tool-call batch. Treat `serial_tool_calls=True` as a
"force-serial" planning mode applied to the same DAG planner — not a switch to a
different engine. Represent a call's original-order position, per-call resource
scopes (via the `ToolSpec.resource_scopes` shape from
`requires/20260813-140532_require.md`), write status, and serial-barrier requirement as
first-class planner inputs keyed by `call_id`. Build phases by walking calls in
original order, closing the current normal phase whenever a `requires_serial` call is
encountered, executing that call alone as its own phase, and resuming normal
conflict-aware batching afterward. Within a normal phase, treat any overlapping
resource scope (including filesystem ancestor/descendant paths) as a conflict for
read/write, write/read, and write/write pairs, and only read/read pairs as safely
concurrent; a state-changing call with no resolvable scope must use a fixed
`global:write` scope that conflicts with every other call in the same phase (no more
"gather everything with no scope" bucket). Replace the two parallel arrays
(`groups`/`serialize_flags`) and the two return values (`groups`, `metadata`) with a
single execution-plan object whose groups are bound to their own execution mode, so a
group can never execute in a mode its metadata doesn't describe. Emit serialization
events only when concurrency was actually prevented, with an explicit reason code and
the call's *real* `is_write` value. After execution, always restore results to
original call order before any history/session/output/failure-accounting use. This is
a deterministic greedy planner — do not pursue maximum graph optimization.

## Implementation instructions

1. **Remove `_execute_standard()`.** Delete it from `scripts/agent/tool_runner.py`
   (currently lines 423-503) and the `serial_tool_calls` branch in
   `execute_all_tool_calls()` (currently lines 526-530). Every approved batch must go
   through the (renamed/replaced) DAG execution path unconditionally.

2. **Update `ToolConfig.serial_tool_calls` documentation**
   (`scripts/agent/config_dataclasses.py:161`) to describe the new, single-engine
   semantics, e.g.:
   ```python
   # When True, the DAG scheduler executes all prepared and approved tool calls
   # sequentially in original call order. The DAG remains the sole execution path.
   serial_tool_calls: bool = False
   ```

3. **Add a `force_serial` planner input.** Pass
   `force_serial = ctx.cfg.tool.serial_tool_calls` into the planner (replacing today's
   branch-selection use of the flag). When `force_serial=True`, the planner must emit
   one sequential phase per call, in original order, using the same plan/audit
   structure as normal DAG execution, recording reason `forced_serial` for each
   resulting serialization event.

4. **Implement true serial barriers.** Rewrite the phase-building loop in
   `build_execution_groups()` (currently `tool_scheduler.py:89-112`) so a
   `requires_serial=True` call stays at its original position: iterate calls in
   original order; accumulate consecutive non-serial calls into the current normal
   phase; when a serial call is reached, close the current normal phase (planning it
   under normal conflict rules), execute the serial call alone as its own phase, then
   start a new normal phase for subsequent calls. Do not collect serial calls into a
   leading bucket (removes the `serial_barrier`-first behavior at
   `tool_scheduler.py:104-112`).

5. **Key all planner metadata by `call_id`, not tool name.** Stop hard-coding
   `call_id=""` (`tool_runner.py:73`) and stop defaulting `resource_scope` to the tool
   name (`_default_scope = name if _is_write else ""`, `tool_runner.py:71`). The
   planner's input must be `call_specs: dict[str, ToolSpec]` keyed by each call's real
   `call_id`. If a prepared call ID has no entry in `call_specs`, the planner must
   raise — never silently default to a read-only/no-conflict `ToolSpec`.

6. **Include reads in conflict detection.** Within a normal phase, compare every pair
   of calls' resolved `resource_scopes` (per `ToolSpec.resource_scopes` from
   `requires/20260813-140532_require.md`): read/read may run concurrently; read/write,
   write/read, and write/write must serialize when scopes overlap. Scope overlap
   includes equal filesystem paths and ancestor/descendant relationships (matches the
   scope-comparison contract already required by
   `requires/20260813-140532_require.md`).

7. **Remove the `write_first` bucket.** Delete the current `write_first` collection
   (`tool_scheduler.py:99-100`) and its `serialize_flags=[False]` batch
   (`tool_scheduler.py:122-123`). A state-changing call with no resolved scope must
   already carry `resource_scopes=("global:write",)` (per
   `requires/20260813-140532_require.md`'s `resolve_resource_scopes()` contract), and
   `global:write` must conflict with every other call in the same normal phase, forcing
   full serialization among scope-less writes instead of concurrent execution via
   `asyncio.gather`.

8. **Replace parallel arrays with bound plan objects.** Replace
   `ScheduledBatch(groups: list[list[dict]], serialize_flags: list[bool])` with
   dataclasses that bind execution mode directly to its calls, e.g.:
   ```python
   @dataclass(frozen=True)
   class ScheduledGroup:
       calls: tuple[ToolSpec, ...]
       sequential: bool
       reason: str = ""

   @dataclass(frozen=True)
   class ScheduledBatch:
       groups: tuple[ScheduledGroup, ...]

   @dataclass(frozen=True)
   class ExecutionPlan:
       batches: tuple[ScheduledBatch, ...]
       serialization_events: tuple[SerializationEvent, ...]
   ```
   Equivalent names are acceptable provided execution mode cannot become detached from
   its group.

9. **Return one execution-plan object.** `build_execution_groups()` (or its
   replacement) must return a single `ExecutionPlan`, not the current `(groups,
   metadata)` pair with `metadata.concurrent_groups` as a second representation. Update
   `_execute_with_dag()` (`tool_runner.py:315-420`) to consume only this one structure —
   remove the currently-unused `_groups` flat list (`tool_runner.py:330`).

10. **Correct serialization events.** Emit a serialization event only when concurrency
    was actually prevented (i.e., the group had more than one call, or a barrier
    displaced calls that would otherwise have run together). Use explicit reason codes:
    `forced_serial`, `requires_serial`, `resource_read_write_conflict`,
    `resource_write_write_conflict`, `global_write_scope`. Each event must record the
    triggering call ID, tool name, the call's actual `is_write` (never hard-coded to
    `True`), the relevant resource scopes, the number of affected calls, and the
    scheduling decision. Do not emit an event for a one-call group with no competitor,
    and do not report `parallel` mode when the plan executed sequentially.

11. **Preserve final result order.** After executing an `ExecutionPlan` (which may run
    groups concurrently within a phase), sort collected results by original call
    position before they reach conversation-history updates, session persistence,
    user-visible output, or failure-key accounting.

12. **Rewrite the tests that currently assert the defects as correct.** Update or
    remove `test_write_first_group_is_gathered_concurrently`
    (`tests/agent/test_tool_scheduler.py:293-305`),
    `test_write_first_batch_has_serialize_false`
    (`tests/agent/test_tool_scheduler_serialization.py:93-101`),
    `test_serial_tool_precedes_parallel_tools`
    (`tests/agent/test_tool_scheduler.py:61-72`), and
    `test_serial_barrier_event_fields`
    (`tests/agent/test_tool_scheduler_serialization.py:112-120`) so they assert the
    corrected behavior instead of the current bug.

## Acceptance criteria
- `_execute_standard()` is removed from `scripts/agent/tool_runner.py`.
- Every approved tool-call batch executes through the single DAG execution-plan path.
- `serial_tool_calls=True` executes all calls sequentially in original order via the
  same DAG plan/audit structure used for normal execution.
- A `requires_serial` call remains at its original position, dividing the calls before
  it and after it into separate normal phases.
- No scope-less state-changing call can execute concurrently with another
  state-changing call (the `write_first`-with-`serialize=False` bug is gone).
- Same-scope read/write and write/write pairs serialize; same-scope read/read pairs
  may run concurrently.
- Different-scope state-changing calls may run concurrently when no other constraint
  applies.
- Planner metadata (and its input contract) is keyed by `call_id`, not tool name; a
  missing `ToolSpec` for a prepared call ID causes the planner to fail, not to default
  to a synthetic read-only spec.
- The scheduler returns exactly one `ExecutionPlan`-shaped object; there is no second,
  independently-consumed group representation.
- A group's execution mode (`sequential`/concurrent) cannot become detached from its
  calls — `groups`/`serialize_flags` parallel-array structure is removed.
- Serialization events are emitted only when concurrency was actually prevented, use
  the explicit reason codes listed above, and record the call's real `is_write` value.
- Final tool-call results are restored to original call order before being used for
  history updates, session persistence, output, or failure accounting.

## Tests
- Force-serial mode (`serial_tool_calls=True`) preserves original call order end to
  end.
- One `requires_serial` barrier correctly separates two normal phases (calls before and
  after are batched independently, not hoisted to the front).
- Multiple `requires_serial` barriers in one batch each divide their own phase
  boundary.
- A read-only tool marked `requires_serial` produces a serialization event with
  `is_write=False`.
- A state-changing call with no resolvable scope (`global:write`) runs alone in its
  phase relative to any other state-changing call in the same phase.
- Same-scope read and write calls serialize; same-scope write and write calls
  serialize; same-scope read and read calls execute concurrently.
- Different-scope state-changing calls may execute concurrently when no other
  constraint applies.
- A parent-directory read and a descendant-path write serialize (ancestor/descendant
  scope overlap).
- A one-call group does not emit a serialization/conflict event.
- A prepared call ID missing from the planner's `call_specs` input raises a planning
  error rather than defaulting silently.
- Results from a batch containing concurrently-executed calls are restored to original
  call order in the final output.
- Audit/serialization-event scheduling-decision fields match the actual execution mode
  used (no `parallel` reported for a sequential execution).
- Regression tests updated to assert the corrected `write_first`/`serial_barrier`/
  `is_write` behavior in place of the four tests currently locking in the old defects
  (see Implementation instructions #12).
