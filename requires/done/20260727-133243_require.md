# Add application-level liveness re-check to HTTP MCP server reuse path

## Priority

Medium

## Target Files

- `scripts/agent/http_lifecycle.py:148-157` — `verify_running()` only checks OS-level process liveness via `proc.poll()`
- `scripts/agent/factory.py:114-148` — `_ServerLifecycleRouter.ensure_ready()` short-circuits based solely on `verify_running()`'s result

## Background

`HttpServerLifecycleManager` manages HTTP-transport MCP servers started as subprocesses.
On initial startup, `start()` (`scripts/agent/http_lifecycle.py:200-295`) polls the
server's `/health` endpoint until it responds `200 OK` or a startup timeout elapses,
confirming the process is both alive at the OS level and responsive at the application
(HTTP) level.

After startup, `ensure_ready()` (`scripts/agent/factory.py:114-148`) is the path used to
decide whether a server needs to be (re)started before handling a request. It calls
`verify_running(server_key)`, and only proceeds to call `start()` when that returns
`False`.

## Problem

`verify_running()` (`scripts/agent/http_lifecycle.py:148-157`) determines "running" purely
from `proc.poll() is not None` (OS process exit status):

```python
def verify_running(self, server_key: str) -> bool:
    """Return True if the HTTP subprocess server is running, False if missing or exited."""
    proc = self._http_procs.get(server_key)
    if proc is None or proc.poll() is not None:
        logger.warning(
            "Lifecycle: HTTP subprocess %r is not running; it should have been started at agent init",
            server_key,
        )
        return False
    return True
```

It never performs an HTTP request to confirm the server is actually responsive.
`ensure_ready()` uses this result as the sole gate for reuse vs. restart:

```python
if not self._http_mgr.verify_running(server_key):
    ...
    await self._http_mgr.start(server_key, cfg)
    ...
```

If `verify_running()` returns `True`, `ensure_ready()` returns immediately without any
further check, and `start()` — the only place with an HTTP `/health` poll
(`scripts/agent/http_lifecycle.py:258-295`) — is never invoked in this path, since
`start()` itself is a no-op whenever the process is still alive
(`scripts/agent/http_lifecycle.py:211-217`).

Consequence: an OS process that is alive but has hung or deadlocked at the application
layer (e.g., stuck event loop, deadlocked handler, exhausted worker threads) will
continue to be reported as "running" indefinitely. It is never detected by the lifecycle
layer and never triggers automatic recovery (restart). The problem only becomes visible
when a caller's tool-invocation timeout eventually fires, well after the underlying
server has stopped functioning.

## Reason for Change

Process-management logic should not treat "OS process alive" as equivalent to "server is
usable." Silently reusing a hung server produces confusing downstream failures (tool call
timeouts with no clear root cause) and prevents automatic self-healing that the codebase
already partially implements via cooldown/restart logic in `_ServerLifecycleRouter`. Since
the health-check plumbing (`httpx` client, `/health` URL derivation) already exists in
`start()`, extending it to periodic reuse-time checks is a small, well-contained change
that closes an observability and reliability gap.

## Implementation Intent

Add a lightweight, rate-limited application-level liveness check to the reuse path so
that a hung-but-alive HTTP MCP server is detected and can trigger a restart, without
imposing an HTTP round-trip cost on every single `ensure_ready()` call.

Suggested approach (subject to design confirmation during planning):
- Track a "last verified at" monotonic timestamp per `server_key` in
  `HttpServerLifecycleManager`.
- In `verify_running()` (or a new method called from `ensure_ready()`), when the OS-level
  check passes AND more than a configurable interval (e.g. a few seconds to tens of
  seconds) has elapsed since the last successful `/health` check, perform a short-timeout
  HTTP GET to `/health`. Treat a non-200 response or a request exception as "not running."
  Otherwise, skip the HTTP check and return the OS-level result (to avoid adding latency
  to every request path).
- On detecting an unhealthy-but-alive process, ensure the existing restart/cooldown path
  in `_ServerLifecycleRouter.ensure_ready()` is triggered (this may require terminating
  the stale process first, since `start()` treats an alive process as already-started and
  will not perform a fresh health poll on it).
- Keep the check bounded by a short timeout so a truly hung server does not block
  `ensure_ready()` for long.

## Implementation Instructions

1. In `scripts/agent/http_lifecycle.py`, add a per-`server_key` "last health-checked at"
   timestamp store (e.g. `self._last_health_check: dict[str, float]`), initialized/cleared
   alongside `_http_procs` in `start()` and cleanup paths (`stop`, `shutdown_all`, etc.).
2. Add a configurable re-check interval (e.g. a class-level constant or a field sourced
   from `McpServerConfig`, consistent with how `startup_timeout_sec` is already
   configured).
3. Modify `verify_running()` (or introduce an async sibling, e.g.
   `verify_running_async()`, if an async HTTP call cannot be made from the current
   synchronous signature) so that when the OS-level check passes and the re-check
   interval has elapsed, it performs a short-timeout GET to `{cfg.url}/health` and returns
   `False` if the request fails or does not return `200 OK`.
4. Update `_ServerLifecycleRouter.ensure_ready()` in `scripts/agent/factory.py` to call
   the (possibly now-async) liveness check and to correctly restart the subprocess when it
   reports unhealthy — including terminating the stale-but-alive process first if
   necessary, since `start()` is a no-op for processes that are still alive.
5. Ensure the added HTTP check has a short bounded timeout (e.g. 1-2 seconds) so that a
   hung server does not stall `ensure_ready()` callers.
6. Add/update logging so a transition from "OS-alive but app-unhealthy" to "restarting"
   is clearly distinguishable in logs from a plain process-exit restart.

## Acceptance Criteria

- [ ] A HTTP MCP server whose OS process is alive but whose `/health` endpoint stops
      responding (or returns non-200) is detected within the configured re-check interval
      and is no longer reported as "running" by the liveness check used in
      `ensure_ready()`.
- [ ] Detection of an app-level-unhealthy server triggers the existing restart/cooldown
      path in `_ServerLifecycleRouter`, resulting in a fresh subprocess being started.
- [ ] The added liveness check does not perform an HTTP request on every single
      `ensure_ready()` call — it is rate-limited by the re-check interval to avoid adding
      per-request latency overhead.
- [ ] A truly hung server (health request never returns) does not block `ensure_ready()`
      beyond the configured short timeout.
- [ ] Existing behavior for a normally-running, healthy server is unchanged (no spurious
      restarts).
- [ ] Existing behavior for an OS-exited process (immediate restart) is unchanged.

## Tests

- Unit test for `verify_running()` (or its async replacement) simulating: (a) OS process
  alive + `/health` returns 200 -> `True`; (b) OS process alive + `/health` returns
  non-200 or raises -> `False`; (c) OS process alive + re-check interval not yet elapsed
  -> `True` without an HTTP call being made (verify via mock call count).
- Unit/integration test for `_ServerLifecycleRouter.ensure_ready()` verifying that when
  the liveness check reports unhealthy, the stale process is terminated and `start()` is
  invoked to launch a replacement.
- Regression test confirming no additional HTTP calls are made for rapid successive
  `ensure_ready()` calls within the re-check interval.
