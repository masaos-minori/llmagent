# Clarify events.py "no delivery mechanism" note by naming the actual delivery module

## Priority
Medium

## Target files
- `docs/01_overview-files-04-shared-part2.md` (the `events.py` line in the file tree listing, currently annotated "配送機構なし" / "no delivery mechanism")

## Background
`docs/01_overview-files-04-shared-part2.md` lists `scripts/shared/events.py` with the
annotation "ArtifactEvent / RetryEvent TypedDict — ライフサイクル/成果物通知の型定義
(配送機構なし)" ("...type definitions for lifecycle/artifact notifications (no delivery
mechanism)"). The note correctly states that `events.py` has no delivery mechanism of its
own, but it does not say which component actually performs event delivery, leaving readers
to guess or assume delivery does not exist anywhere in the system.

## Problem
A reader encountering "(no delivery mechanism)" next to `events.py` cannot tell whether:
(a) no delivery mechanism exists anywhere in the codebase, or
(b) delivery is handled elsewhere and `events.py` is deliberately scoped to type
definitions only.
Source inspection confirms it is case (b): `scripts/shared/events.py`'s own module
docstring states "It has no delivery system, no event bus, and no consumers. It exists
solely as a type annotation..." — and a real delivery mechanism exists at
`scripts/eventbus/broker.py`, whose `EventBroker` class implements `subscribe()`,
`unsubscribe()`, and `publish()` (in-memory pub/sub with per-subscriber queues and topic
filtering; `publish()` fans out an event dict to matching subscribers and returns the
delivered count). The doc's current wording omits this connection, so the constraint is
only half-explained.

## Reason for change
This is an easy-to-misunderstand gap: `events.py` and the eventbus broker are in different
directories (`scripts/shared/` vs `scripts/eventbus/`), so nothing in the doc currently
points a reader from one to the other. Adding a single clarifying sentence closes this gap
with minimal documentation surface area, per the issue's explicit scope (a pointer sentence,
not a full architecture writeup).

## Implementation intent
Add one short clarifying sentence/annotation to the `events.py` doc entry (or immediately
adjacent to it) in `docs/01_overview-files-04-shared-part2.md`, naming
`scripts/eventbus/broker.py` (specifically its `EventBroker.publish()` fan-out logic) as the
component that actually performs event delivery. Keep the existing "(no delivery mechanism)"
qualifier on `events.py` itself — do not remove or weaken it, since it remains factually
correct for that specific file. Do not expand this into a broader description of the
eventbus subsystem (routes, DLQ, offsets, etc.) — that is out of scope here.

1. Open `docs/01_overview-files-04-shared-part2.md` and locate the `events.py` line
   (currently: `events.py  # ArtifactEvent / RetryEvent TypedDict — ライフサイクル/成果物通知の型定義 (配送機構なし)`).
2. Add a clarifying sentence naming `scripts/eventbus/broker.py` as the actual delivery
   owner — for example (English, matching the requirement's own working language; adapt to
