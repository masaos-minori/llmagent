# Requirement: Dynamic Health Check Timeout Based on Startup Timeout Configuration

## Priority

Medium — hardcoded 5-second timeout can cause false failures for servers with longer startup times

## Target Files

- `scripts/agent/http_lifecycle.py` (line 329)

## Background

The health check HTTP client uses a hardcoded 5-second timeout:

```python
async with httpx.AsyncClient(timeout=httpx.Timeout(timeout=5.0)) as client:
```

This timeout applies to each individual health check request, not the overall startup window. The overall startup window is controlled by `cfg.startup_timeout_sec`, which may be significantly larger (e.g., 30 seconds).

## Problem

If an MCP server takes more than 5 seconds to respond to `/health` during startup (even though it is starting normally), the health check fails due to the short timeout. This causes unnecessary startup failure even though the server will eventually become healthy within the configured startup timeout window.

## Reason for Change

Align the health check request timeout with the server's actual startup characteristics to reduce false negatives during startup.

## Implementation Intent

Make the health check request timeout configurable and proportional to the overall startup timeout, rather than using a hardcoded value.

## Implementation Instructions

**Option A — Proportional timeout:**
- Set the health check request timeout to a fraction of `cfg.startup_timeout_sec` (e.g., `min(cfg.startup_timeout_sec / 10, 15.0)`)
- Ensures reasonable timeout for both fast-starting and slow-starting servers
- Cap at a maximum (e.g., 15 seconds) to prevent unreasonably long timeouts

**Option B — Separate configuration parameter:**
- Add a new configuration field `health_check_request_timeout_sec` to `McpServerConfig`
- Default to 10 seconds if not specified
- Allows operators to tune independently of startup timeout

**Option C — Simple increase:**
- Increase the hardcoded timeout from 5.0 to 10.0 or 15.0 seconds
- Simpler but less flexible

Option A is recommended because it automatically adapts to the configured startup timeout without requiring additional configuration.

## Acceptance Criteria

- [ ] Health check request timeout is no longer hardcoded to 5 seconds
- [ ] Timeout adapts based on `cfg.startup_timeout_sec` or is explicitly configurable
- [ ] Servers that take up to the configured startup timeout to respond are not falsely rejected
- [ ] No regression in behavior for servers that respond quickly

## Tests

- Integration test verifying health check succeeds when server responds within startup timeout but after 5 seconds
- Unit test verifying timeout calculation logic
