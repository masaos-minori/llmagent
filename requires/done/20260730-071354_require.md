# Require: Rationalize the RAG result source and diagnostics model

## Priority

Medium

## Target files

- `scripts/rag/models_result.py`
- `scripts/rag/pipeline.py`
- `scripts/rag/http_augment.py`

## Background

PipelineRunResult includes result_source, and SearchDiagnostics also includes result_source and HTTP result fields.

## Problem

There is no clear single source of truth for result_source. It is also too coarse-grained to distinguish important RAG result paths such as:

- remote service
- local pipeline
- semantic cache
- refiner result
- raw chunk fallback
- remote empty
- local empty

This makes diagnostics incomplete and can make stale-cache or fallback behavior difficult to understand.

## Reason for change

The intent is to create a consistent and source-aware diagnostics model.

## Implementation intent

### Decide whether result_source should live in PipelineRunResult, SearchDiagnostics, or both

### If both are kept, define which one is authoritative

### Extend ResultSource or introduce a new enum that can represent:

- remote
- remote_empty
- local
- cache
- refiner
- raw_chunks
- fallback
- empty

### Set result_source consistently in:

- HTTP remote success
- HTTP remote empty
- HTTP fallback
- semantic cache hit
- local pipeline result
- refiner success
- raw chunk fallback
- local empty result

### Expose semantic_cache_size and semantic_cache_generation in get_diagnostics()

### Add cache hit/miss counters if feasible

## Acceptance criteria

- [ ] Every augment path has a clear result source.
- [ ] get_diagnostics() exposes result_source and relevant cache diagnostics.
- [ ] result_source is no longer stale or unused.
- [ ] Remote empty and fallback are distinguishable.
- [ ] Cache hits and local search output are distinguishable.
