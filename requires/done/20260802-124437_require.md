# Differentiate duplicate H1 headings in docs/02_deployment-part1.md and part2.md

## Priority
Medium

## Target files
- `docs/02_deployment-part1.md`
- `docs/02_deployment-part2.md`

## Background
`docs/02_deployment-part1.md` and `docs/02_deployment-part2.md` are a split pair covering
deployment. Both files currently use the identical H1 heading `# 導入手順・デプロイ`
(confirmed at line 14 of each file as of this review). Part1 covers package installation,
Python/uv setup, llama.cpp build, model acquisition, and service registration (sections
"Embedding: multilingual-E5-small" and "2. サービス設定"). Part2 covers DB initialization,
the deployment checklist, and failure modes (sections "3. DB 初期化" through "3.3
失敗モード").

## Problem
Because both files share the exact same H1 text, any tooling that concatenates or
generates a unified/merged view of the two files (or of the full doc set) would produce
two identical top-level headings back to back, which is ambiguous for navigation, anchors,
and any heading-based table-of-contents generation.

## Reason for change
Identical H1s across a split-file pair is a structural risk specifically for tooling that
builds a combined view (e.g. a documentation index or merge script) — the headings should
each reflect the distinct scope of their file's content instead of being indistinguishable
duplicates.

## Implementation intent
Give each file an H1 that reflects its actual content scope, without altering the
underlying content, section numbering, or split boundary:
- part1: something reflecting environment/build setup and service startup (e.g.
  "環境構築・起動" or an equivalent phrase covering packages, Python env, llama.cpp build,
  model acquisition, and service registration).
- part2: something reflecting DB initialization and failure modes (e.g.
  "DB初期化・失敗モード" or an equivalent phrase covering DB schema setup, the deployment
  checklist, and failure-mode handling).

The exact wording is not prescribed beyond distinguishing the two files' scope — the next
phase (planning) should pick wording consistent with existing heading style in this doc
set and should not otherwise restructure the files.

## Implementation instructions
1. Update the H1 (line 14) in `docs/02_deployment-part1.md` from `# 導入手順・デプロイ` to
   a heading reflecting environment setup / build / startup scope.
2. Update the H1 (line 14) in `docs/02_deployment-part2.md` from `# 導入手順・デプロイ` to
   a heading reflecting DB initialization / failure-mode scope.
3. Do not change the `source` frontmatter field in either file as part of this change (see
   "Note on frontmatter `source` field" below — this is intentionally out of scope).
4. Do not change any other content, section numbering, or the part1/part2 split boundary.
5. Check for any cross-references to the old H1 text (e.g. links using the heading as
   anchor text) in other docs under `docs/` and update them if they exist, so links are not
   broken by the heading rename.

## Note on frontmatter `source` field (scope correction from the source issue)
The source issue additionally claimed that `docs/02_deployment-part2.md`'s frontmatter
`source` field (`source: - 02_deployment-part1.md`) is an incorrect self-reference /
copy-paste artifact that should be corrected or removed. This claim was checked against
current source and found **not applicable**: the same pattern — both halves of a
split-file pair listing the **part1** filename as `source`, including part1 listing its
own filename as its `source` — is the established, repeated convention used throughout
`docs/`. Confirmed identical pattern in at least three other split pairs:
- `docs/03_rag_02_02_ingestion_pipeline-crawler-part1.md` / `-part2.md`
  (`source: - 03_rag_02_02_ingestion_pipeline-crawler-part1.md` in both)
- `docs/03_rag_02_03_ingestion_pipeline-chunksplitter-part1.md` / `-part2.md`
  (`source: - 03_rag_02_03_ingestion_pipeline-chunksplitter-part1.md` in both)
- `docs/05_agent_02_runtime-architecture-part1.md` / `-part2.md`
  (`source: - 05_agent_02_runtime-architecture-part1.md` in both)

No tooling in `scripts/` (checked `scripts/mcp_servers/mdq/parser.py`, the only doc-parsing
frontmatter reader found) reads or depends on the frontmatter `source` field — it only
reads `tags`. Since `docs/02_deployment-part2.md`'s `source` value matches the repo-wide
convention exactly, changing it here would make this pair inconsistent with every other
split pair rather than fixing a genuine error. This requirement therefore covers only the
H1 heading fix; the frontmatter `source` field should be left unchanged. If the project
later decides the repo-wide `source` convention itself should change, that would need to
be a separate, repo-wide requirement covering all split pairs consistently, not a
single-file fix here.
