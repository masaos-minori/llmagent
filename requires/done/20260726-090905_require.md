# WAL checkpoint on shutdown can stall the event loop with no application-level timeout

## Priority

Medium

## Target files

- `scripts/agent/repl.py` — `SessionRunner._close_resources()` (currently lines 245-336), specifically:
  - lines 256-258: PASSIVE checkpoint attempt (`db.checkpoint("PASSIVE")`)
  - lines 259-293: exception-triggered fallback to TRUNCATE checkpoint with retry/backoff
  - lines 294-314: WAL file backup path generation and copy when TRUNCATE fallback does not succeed
- `scripts/db/helper.py` — `SQLiteHelper.checkpoint()` (lines 269-283) and `apply_connection_pragmas()` (around line 36, sets `PRAGMA busy_timeout`)

## Background

`SessionRunner._close_resources()` runs during shutdown (invoked via plain `await self._close_resources()` from two `finally` blocks, at `repl.py:526` and `repl.py:615`, with no timeout wrapper on the call). It performs a WAL checkpoint before closing the session's SQLite connection: it first tries `PASSIVE` mode, and on `sqlite3.Error` falls back to `TRUNCATE` mode with up to 3 retries (exponential backoff via `asyncio.sleep`), and if that also fails, copies the WAL file to a backup path before giving up.

`SQLiteHelper` sets `PRAGMA busy_timeout=30000` (30s, `helper.py` `_DEFAULT_BUSY_TIMEOUT_MS`) and opens the connection with `sqlite3.connect(..., timeout=30)` (`helper.py`, `sqlite_timeout` default 30s). Both of these bound how long any single SQLite operation will wait for a lock, but neither is applied as an overall timeout on `_close_resources()` as a whole, and `checkpoint()` itself (`helper.py:269-283`) adds no additional timeout logic.

## Problem

An issue report (`issues/20260726_18_issue.md`) claimed that the PASSIVE checkpoint on shutdown has no timeout and could block shutdown indefinitely, with escalating fallback to TRUNCATE and then a WAL file backup. Source verification confirms the general shape of this code path but corrects two details:

1. **Fallback trigger**: TRUNCATE fallback only runs when the PASSIVE checkpoint raises `sqlite3.Error` (`repl.py:259`). It does not run when PASSIVE completes without error but leaves unwritten frames (`busy` count > 0) — `checkpoint()` never inspects that value, so a PASSIVE checkpoint that silently fails to fully checkpoint the WAL is logged as a success (`repl.py:258`) and no fallback is triggered at all.
2. **Bound on blocking, not literally infinite**: `busy_timeout=30000` and `sqlite3.connect(timeout=30)` mean any single blocking SQLite call (the PASSIVE checkpoint call itself, and each of the up to 3 TRUNCATE attempts) is bounded to roughly 30 seconds before SQLite raises `SQLITE_BUSY`. However, there is no overall/application-level timeout across the whole `_close_resources()` checkpoint sequence, so worst case the sequence can still block the event loop for a large multiple of that (up to ~30s for PASSIVE + up to 3 × 30s for TRUNCATE retries + ~7s of backoff sleep ≈ 2 minutes), all executed as synchronous, blocking `sqlite3` calls directly inside an `async def` with no `run_in_executor`/`asyncio.wait_for` offload. During this window the event loop cannot process cancellation, signals, or other shutdown work, which functions as a de facto indefinite/uncontrolled stall from the caller's perspective even though it is not mathematically unbounded.

Additionally, `db_path = db.execute("PRAGMA database_list").fetchone()[1]` (`repl.py:297-299`) reads column index 1, which is the database **name** (e.g. `"main"`), not the file path (`PRAGMA database_list` returns `(seq, name, file)`). This means the WAL backup path construction at lines 300-306 is built from the wrong value and the subsequent `shutil.copy2(wal_file, wal_backup_path)` (line 307) will generally fail or produce a bogus path, silently defeating the WAL-backup-of-last-resort safety net. This is a related, pre-existing bug in the same code path and should be fixed alongside the timeout work since it affects the same lines the issue flags.

## Reason for change

Shutdown-time work that can synchronously block the event loop for up to ~2 minutes, with no configurable ceiling and no cancellation path, is a real availability/robustness risk (e.g., delayed process exit under supervisors with SIGKILL escalation, delayed release of other resources in the same `finally` block, poor operator experience). The existing per-call `busy_timeout` mitigates literal infinite blocking but does not cap the aggregate time, and does not address the fact that the escalation path (PASSIVE -> TRUNCATE -> backup) is itself unbounded in wall-clock terms. Separately, the WAL backup fallback is currently non-functional due to the wrong `PRAGMA database_list` column being read, which should be corrected so the last-resort safety net actually works when needed.

## Implementation intent

Bound the total time `_close_resources()` can spend on the WAL checkpoint sequence, and make the fallback logic in `repl.py` more faithful to the intended escalation semantics:

- Add an explicit, configurable overall timeout around the checkpoint sequence (PASSIVE attempt + TRUNCATE retries), e.g. via `asyncio.wait_for` around an `await loop.run_in_executor(None, ...)` call so the blocking SQLite work does not block the event loop directly and can be time-bounded and cancelled.
- On overall timeout expiry, proceed straight to the WAL backup path (or abandon cleanly with a logged error) rather than continuing to retry.
- Fix `db_path = db.execute("PRAGMA database_list").fetchone()[1]` to read the correct column (index 2, the file path) so the WAL backup logic actually operates on a valid path.
- Preserve existing logging/error-collection behavior (the `errors` list surfaced at the end of `_close_resources()`).

## Implementation instructions

1. In `scripts/agent/repl.py`, wrap the blocking checkpoint work (currently lines 251-319) so it runs off the event loop (e.g. `await loop.run_in_executor(None, _do_checkpoint, ...)`) and is bounded by `asyncio.wait_for(..., timeout=<configurable seconds>)`.
2. Introduce a configurable overall timeout value (e.g. a constructor/config parameter or module-level constant, consistent with how `sqlite_timeout` / `sqlite_busy_timeout_ms` are configured in `scripts/db/helper.py`) rather than hardcoding a magic number.
3. On `asyncio.TimeoutError` from the wrapped call, log an error, record it in the `errors` list (consistent with existing entries like `"wal_checkpoint_truncate"`), and proceed to attempt the WAL backup step so a slow/stuck checkpoint doesn't skip the safety net.
4. Fix the `PRAGMA database_list` column index bug: change `.fetchone()[1]` to `.fetchone()[2]` at `repl.py:297-299` (or use named access) so `db_path` is the actual database file path, not its name.
5. Do not change the existing PASSIVE -> TRUNCATE -> backup escalation order or its retry count/backoff for TRUNCATE; only add the overall time bound and fix the path bug.
6. Keep behavior on non-WAL journal modes (the `else` branch at `repl.py:315-316`) unchanged.

## Acceptance criteria

- [ ] The full WAL checkpoint sequence in `_close_resources()` is bounded by a configurable overall timeout and no longer runs the blocking `sqlite3` calls directly on the event loop.
- [ ] When the overall timeout is exceeded, the WAL backup step is still attempted, and the timeout is logged and recorded in the `errors` list.
- [ ] `db_path` is derived from the correct `PRAGMA database_list` column (the file path, not the database name), and the WAL backup copy (`shutil.copy2`) succeeds when a WAL file is present at that path.
- [ ] Existing successful-path behavior (fast PASSIVE checkpoint success, fast TRUNCATE fallback success) is unchanged in terms of logging and control flow.
- [ ] `_close_resources()` no longer has an unbounded/large worst-case blocking window (previously up to ~2 minutes with no ceiling); the new ceiling is explicit and documented.

## Tests

- Unit test: simulate a checkpoint operation that hangs/blocks past the configured overall timeout (e.g. via a mock that sleeps or blocks a lock); verify `_close_resources()` returns within the timeout bound, logs an `asyncio.TimeoutError`/timeout condition, records it in `errors`, and still attempts the WAL backup step.
- Unit test: verify `db_path` is correctly extracted from a mocked `PRAGMA database_list` result (asserting the file-path column is used, not the name column), and that `shutil.copy2` is called with a valid source WAL file path.
