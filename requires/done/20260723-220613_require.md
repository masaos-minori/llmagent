## Title

Include sqlite3.Error class name in session start error messages

## Priority

High

## Target files

- scripts/agent/repl.py

## Background

When `ctx.session.start()` raises a `sqlite3.Error`, the error message displayed to the user does not distinguish between different types of SQLite errors (e.g., `OperationalError` for "database is locked", `DatabaseError` for I/O errors). This makes root cause analysis difficult.

## Problem

`repl.py:444-449` catches `sqlite3.Error` and displays a generic message: `"Database unavailable during session start: {e}". The message includes the raw exception string `{e}` which may be cryptic (e.g., "database is locked") but does not explicitly state the error type. Users cannot easily determine whether the issue is a lock contention problem, an I/O error, or something else.

## Reason for change

Including the error class name (`e.__class__.__name__`) in the message helps users and operators quickly identify the type of SQLite error and take appropriate action (e.g., retrying for lock contention vs. checking disk space for I/O errors).

## Implementation intent

Modify the error message to include the sqlite3.Error subclass name, making the error more actionable.

## Implementation instructions

Change the code from:

```python
# Before (line ~445):
except sqlite3.Error as e:
    self._view.write_fatal(
        f"Database unavailable during session start: {e}. Check DB connectivity or run: bash deploy/init_db.sh"
    )
    raise RuntimeError(f"Database unavailable: {e}") from None
```

To:

```python
# After:
except sqlite3.Error as e:
    err_type = e.__class__.__name__
    self._view.write_fatal(
        f"Database unavailable during session start ({err_type}): {e}. Check DB connectivity or run: bash deploy/init_db.sh"
    )
    raise RuntimeError(f"Database unavailable ({err_type}): {e}") from None
```

## Acceptance criteria

1. Error message includes the sqlite3.Error subclass name (e.g., "OperationalError", "DatabaseError").
2. Existing behavior for "no such table" RuntimeError path is unchanged.
3. No mypy errors introduced by the change.
4. All existing tests pass without modification.
