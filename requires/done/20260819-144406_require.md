## Background
Source issue `issues/20260819_02_issue.md` ("Replace permissive RAG payload handling
with strict crawl and chunk contracts") describes a permissive JSON-boundary contract
for the RAG ingestion pipeline (crawl -> chunk-splitter -> ingester -> store) that
tolerates missing/malformed fields via defaulting and coercion.

## Problem
The RAG ingestion pipeline (crawl artifact -> chunk-splitter -> chunk artifact ->
ingester -> store) currently accepts malformed or incomplete current-format JSON
artifacts as if they were valid, because the JSON-reading boundary
(`read_json_file()`/`_read_chunk_json_raw()` in `pipeline_utils.py`, plus
`_validate_artifact(..., strict=False)` and `_normalize_chunk_index()` in
`ingester.py`), the `ChunkDocument` DTO, and the `chunk_insert()` signatures in both
the `DocumentStore` protocol and its SQLite implementation all default or coerce
mandatory current-format fields instead of rejecting the payload:

- Missing `lang` silently becomes `"en"`, which can misclassify Japanese content.
- Missing/invalid `chunk_index` silently becomes `0` (via two independently-defined
  fallback code paths — `_get_int_with_default()` in `pipeline_utils.py` and
  `_normalize_chunk_index()` in `ingester.py`), which can create duplicate chunk
  indexes.
- Missing `chunk_type`/`source_file` silently become `""`, which defers detection to
  database constraints and silently loses source traceability.
- A string `chunk_index` (e.g. `"1"`) is silently coerced via bare `int()` instead of
  being rejected as a type error.
- `_validate_artifact(..., strict=False)` allows a payload through while skipping the
  `schema_version`/`created_by` checks entirely.
- Crawler output does not consistently emit `etag`/`last_modified` keys at all, so a
  strict reader that requires the keys to be present (with `null` allowed as the
  value) cannot yet be written against current crawler output without a crawler
  change first.
- Crawler and chunk-splitter artifacts are read through overlapping,
  near-duplicate permissive TypedDicts (`ChunkJsonRaw`, `CrawlPayload`,
  `CrawlFilePayload`, `ChunkOutputPayload`) rather than one strict schema per
  artifact type, even though the two artifact types have different validity rules
  (e.g. a crawler payload may have empty `content` only when `code_blocks` is
  non-empty; a chunk payload's `content` must always be non-empty).

## Reason for change
There is no legacy data to support and no omission should be allowed for
current-format artifacts. Continuing to default/coerce mandatory fields lets
malformed artifacts silently propagate through chunking, embedding, and storage
until a database constraint eventually — and much later — surfaces the problem, by
which point source traceability (`source_file`) or chunk ordering (`chunk_index`) may
already be lost or corrupted. Validation belongs at the JSON boundary, before any
downstream processing, and the two artifact types (crawl vs. chunk) are different
enough in their validity rules that they should not continue to share (or
near-duplicate) a single permissive type.

## Implementation intent
Create two independent, artifact-specific strict schemas — one for crawler output,
one for chunk-splitter output — and reject any payload that does not exactly satisfy
its schema, before chunking, embedding, or database access. The implementation must
distinguish a missing key from a present key whose value is legitimately `null`
(`etag`, `last_modified`, `normalized_content` are mandatory keys but nullable
values; no other mandatory field may be `null`, defaulted, or coerced).

Crawler payloads must support code-only local Python files: empty `content` is valid
only when `code_blocks` contains at least one string. Chunk payload `content` must
always be non-empty. Unknown fields are rejected under one explicit policy applied
consistently to both payload types (rejecting unknown fields is the preferred
policy under the no-omission/no-legacy intent).

## Implementation instructions
1. In `scripts/rag/ingestion/pipeline_utils.py`:
   - Replace `ChunkJsonRaw` (currently `pipeline_utils.py:19-39`) with two separate
     strict payload types: `CrawlJsonPayload` and `ChunkJsonPayload`, each declaring
     exactly its required-keys list (see Required Crawl Payload / Required Chunk
     Payload below) with no `NotRequired` fields except where the issue explicitly
     allows a nullable-but-mandatory value (`etag`, `last_modified`,
     `normalized_content`).
   - Implement `read_crawl_json(path) -> CrawlDocument` and `read_chunk_json(path) ->
     ChunkDocument`, each performing full key-presence, type, and allowed-value
     validation before returning a DTO. Raise on any violation (missing key, wrong
     type, disallowed value, unknown key) rather than defaulting/coercing.
   - Remove `read_json_file()` and `_read_chunk_json_raw()` (`pipeline_utils.py:72-
     100` and `:42-69`) once no production caller remains — replace their callers
     with the new strict readers.
   - Remove `_get_str_with_default()` (`pipeline_utils.py:115-118`) and
     `_get_int_with_default()` (`pipeline_utils.py:121-129`); no replacement default-
     filling helper should be introduced.

## Required Crawl Payload
- `schema_version` (must equal `"1"`)
- `artifact_type` (must equal `"crawl"`)
- `created_by` (must equal `"crawler"`)
- `url`
- `title`
- `lang` (must be `"ja"` or `"en"`)
- `fetched_at`
- `content` (may be empty only if `code_blocks` is non-empty)
- `code_blocks` (must be `list[str]`)
- `etag` (mandatory key, value may be `null`)
- `last_modified` (mandatory key, value may be `null`)

## Required Chunk Payload
- `schema_version` (must equal `"1"`)
- `artifact_type` (must equal `"chunk"`)
- `created_by` (must equal `"chunk_splitter"`)
- `url`
- `title`
- `lang`
- `fetched_at`
- `etag` (mandatory key, value may be `null`)
- `last_modified` (mandatory key, value may be `null`)
- `source_file` (non-empty string)
- `chunking_strategy` (must be `"text"` or `"heading"`)
- `chunk_index` (non-negative JSON integer; `bool` explicitly rejected)
- `chunk_type` (must be `"text"` or `"code"`)
- `content` (non-empty string)
- `normalized_content` (mandatory key, value may be `null`)

## Acceptance criteria
- Crawler and chunk artifacts have separate types (`CrawlJsonPayload`/
  `ChunkJsonPayload`), separate DTOs (`CrawlDocument`/`ChunkDocument`), and separate
  readers (`read_crawl_json()`/`read_chunk_json()`), replacing `ChunkJsonRaw`,
  `CrawlPayload`, `CrawlFilePayload`, and `ChunkOutputPayload`.
- `chunk_splitter.py` accepts only crawler artifacts as input.
- `ingester.py` accepts only chunk artifacts as input.
- Missing mandatory keys (per the Required Crawl/Chunk Payload lists) are rejected,
  not defaulted.
- Invalid value types are rejected without coercion (e.g. a string `chunk_index` is
  rejected, not coerced via `int()`).
- `chunk_index="1"`, `chunk_index=true`, and negative `chunk_index` values are all
  explicitly rejected.
- No mandatory field is ever replaced with `""`, `0`, `"en"`, `[]`, or `"text"` as a
  silent default.
- `etag`, `last_modified`, and `normalized_content` remain valid as mandatory keys
  with `null` values.
- Crawler output always includes `etag` and `last_modified` keys (using `null` when
  unavailable) — `crawler.py:339-342`'s conditional-insertion pattern is removed.
- Python source crawler payloads with code-only content (empty `content`, non-empty
  `code_blocks`) successfully produce code chunks.
- `DocumentStore.chunk_insert()` and `SQLiteDocumentStore.chunk_insert()` signatures
  match — both require `chunk_type` and `source_file` with no default value.
- `read_json_file()`, `_read_chunk_json_raw()`, `_get_str_with_default()`,
  `_get_int_with_default()`, `_normalize_chunk_index()`, and
  `_validate_artifact(..., strict=False)` no longer exist or are no longer reachable
  in production code paths.
- `RegisteredDocument` is removed, confirmed by a fresh repository-wide `rg` re-check
  immediately before removal showing no caller.
- All affected tests pass.
