# Record and resolve the open decision on whether `resolve_approval` should reject halted-task approvals

## Priority
Medium

## Target files
- `scripts/agent/workflow/approval_ops.py` (`resolve_approval`, lines 45-67) — docstring update now; guard implementation only if a decision authorizes it
- `scripts/agent/commands/cmd_workflow.py` (`_cmd_approve`, `_cmd_reject`) — reference only; both call `resolve_approval` today with no task-status check; changed only if a decision authorizes a guard
- `tests/agent/test_approval_task_persistence.py` — reference only, explicitly out of scope for this requirement (see Background)

## Background
The source issue (`issues/20260804-135244_unknowns.md`) was filed while converting
`requires/done/20260804-131007_require.md` into `plans/done/20260804-135114_plan.md`. It flags that
`resolve_approval()` in `scripts/agent/workflow/approval_ops.py` checks only the approval row's own
status (`not found` / `already resolved`) and never looks at the associated task's status. Verified
against current source: the function (lines 45-67) issues a single `SELECT status FROM approvals`
lookup and never queries the `tasks` table. `scripts/agent/commands/cmd_workflow.py`'s `_cmd_approve`
and `_cmd_reject` (verified at their current line ranges) likewise call `resolve_approval` directly
with no task-status check beforehand. Resolving an approval for a task already marked `"halted"`
(via `update_task_status(db, task_id, "halted")`) therefore succeeds today exactly as it would for a
`"running"` task.

`tests/agent/test_approval_task_persistence.py::TestHaltedTaskStatusRejection::test_halted_task_prevents_resume`
currently asserts the opposite (`pytest.raises(RuntimeError)`), and the test file's collection is
separately broken by two pre-existing import errors (`TurnContext` does not exist in
`agent.context`; `update_task_status` is not defined in `agent.workflow.approval_ops`, it lives in
`agent.workflow.task_ops`) — both verified still present against current source. A separate,
already-approved plan, `plans/done/20260804-104315_plan.md`, already authorizes fixing those import
errors and rewriting `test_halted_task_prevents_resume` to assert the true (no-exception) current
outcome; that fix has not yet been applied to the test file (verified: the file still has both
broken imports) but is tracked through its own pipeline stage and is **not** part of this
requirement's scope — this requirement must not duplicate or interfere with it.

What remains genuinely unresolved, and is the actual subject of this requirement, is the underlying
product question the source issue raises: is the current no-check behavior in `resolve_approval`
intentional/acceptable, or a gap that should be closed with an explicit guard? This is a
maintainer/product decision, not something derivable from source code alone. The repository already
has precedent for handling exactly this situation without guessing at an answer: see
`requires/done/20260802-192621_require.md`, which — facing a similar "cannot be settled from code or
docs alone" design decision — directed attempting to obtain an explicit decision, and falling back to
recording the item as an explicit open, undecided item (rather than inferring intent) when no
decision channel was available. This requirement follows the same pattern.

## Problem
`resolve_approval` silently allows approval resolution for halted tasks, and there is currently no
documentation anywhere in the source (docstring, comment, or design doc) stating whether this is
deliberate or an oversight. Left as-is, a future reader or automated agent could either (a) wrongly
assume rejection is already enforced, or (b) "fix" the gap unilaterally without authorization, given
the blast radius the source issue already scoped: `scripts/agent/workflow/approval_ops.py`,
`scripts/agent/commands/cmd_workflow.py`, and 15+ existing `resolve_approval(...)` call sites across
`tests/agent/test_approval_task_persistence.py`, `tests/agent/workflow/test_approval_ops.py`,
`tests/agent/workflow/test_workflow_state_store.py`, `tests/agent/workflow/test_workflow_engine.py`,
and `tests/agent/workflow/test_approval_race_condition.py`.

## Reason for change
The source issue is explicitly marked `Blocking: True` against closing
`requires/done/20260804-131007_require.md`'s underlying question, and it was written specifically
because "no live maintainer is available in the document-only planning cycle that produced this
issue." Making the gap explicit now — regardless of which way the eventual decision goes — prevents
the ambiguity from being silently forgotten or silently "resolved" by inference.

  `resolve_approval` (or its `cmd_workflow.py` callers) reject approval resolution when the
  associated task's status is `"halted"`?"

  a documented, known characteristic pending a product decision (cross-reference the source issue by
  filename in the note).
- Either path is a valid, complete resolution of this requirement; do not block indefinitely waiting
  for a decision that may never arrive in this document-only pipeline.
