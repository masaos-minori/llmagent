# Confirm and hoist `_to_call_tool_response`'s local `CallToolResponse` import to module level

## Priority
Low

## Target files
- `scripts/mcp_servers/dispatch.py` (`_to_call_tool_response`)
- `scripts/mcp_servers/models.py` (imported symbol's source module)

## Background
`scripts/mcp_servers/dispatch.py`'s `_to_call_tool_response` function imports `CallToolResponse` locally inside the function body (line 38), even though a `TYPE_CHECKING`-only module-level import of the same symbol exists for the type annotation (line 16). Static analysis found no currently-live import cycle that would require the local import, but the local import was added deliberately (in commit `89b26343a`, at the same time as the `TYPE_CHECKING` import), not left over from before it — suggesting possible intent that should be confirmed before removing it.

## Problem
Redundant local import in `_to_call_tool_response` that may indicate an unconfirmed historical reason for keeping it. If no valid reason exists, hoisting it to module level would simplify the code and reduce import overhead.

## Reason for change
`dispatch.py` is imported by every MCP server; redundant local imports add cognitive load and potential runtime overhead. The local import's deliberate placement alongside the `TYPE_CHECKING` import warrants investigation rather than silent removal.

## Implementation intent
Add a test that imports `mcp_servers.dispatch` before `mcp_servers.models` has been imported anywhere else in the process (fresh subprocess), to prove no import-time cycle exists. Before proceeding, read `git show 89b26343a` to understand why the local import was added alongside the `TYPE_CHECKING` import. If the test passes and no valid reason for the local import is found, hoist the import to module level and remove the redundant `TYPE_CHECKING` guard (or keep both if there's a reason not visible today).

## Implementation instructions
1. Read `git show 89b26343a` to understand the original rationale for the local import alongside the `TYPE_CHECKING` import.
2. Add a fresh-subprocess import-order test proving `import mcp_servers.dispatch` alone (without `mcp_servers.models` already loaded) does not raise `ImportError`.
3. If the test passes AND no valid reason for the local import is found in the commit history:
   - Hoist `from mcp_servers.models import CallToolResponse` to module level (remove the local import from `_to_call_tool_response`).
   - Remove the `TYPE_CHECKING`-only import since it's no longer needed separately.
4. If the test fails OR a valid reason for the local import is found: document why the local import is required and close this issue as "confirmed intentional, no change."

## Acceptance criteria
- Either: the import is hoisted to module level and the new import-order test passes, or
- The local import is confirmed intentional (documented in a code comment referencing this issue) and no change is made.

## Tests
New fresh-subprocess import-order test (see Required Changes); full `tests/mcp_servers/` regression run if the import is moved.
