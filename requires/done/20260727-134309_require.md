# Clarify and document the distance metric used by the `memories_vec` KNN search

## Priority

Medium

## Target Files

- `scripts/agent/memory/retriever.py:151-187` — `VectorRetriever.knn_search` method; negates `mv.distance` into `MemoryHit.score` without stating the underlying metric
- `scripts/db/schema_sql.py:134-137` — `memories_vec` virtual table (`vec0`) definition; no `distance_metric` clause specified
- `docs/05_agent_12_04_memory-module-ref-retrieval-and-injection.md:66` — documents `knn_search` and explicitly marks the metric as "Needs confirmation" (NC-004)
- `docs/00_governance_07_needs-confirmation-inventory.md` (NC-004 entry) — tracks this open question

## Background

- `VectorRetriever.knn_search` (`scripts/agent/memory/retriever.py:151-187`) runs a KNN query against the `memories_vec` sqlite-vec virtual table, ordering by `mv.distance` ascending (nearest first), then negates the distance into `MemoryHit.score` with the comment "Negate distance: MemoryHit.score convention is higher-is-better" (line 185).
- The `memories_vec` table is created in `scripts/db/schema_sql.py:134-137` as:
  ```sql
  CREATE VIRTUAL TABLE IF NOT EXISTS memories_vec USING vec0(
      memory_id TEXT PRIMARY KEY,
      embedding float[DIMS]
  );
  ```
  No `distance_metric=...` clause is present. The sibling `chunks_vec` table (RAG pipeline, `schema_sql.py:47-50`) is defined the same way.
- A repo-wide search for `distance_metric` returns zero hits. There is no embedding-normalization logic in `scripts/agent/memory/embedding_client.py` that would make L2 and cosine distance provably equivalent.
- The only nearby mention of "cosine" is an unenforced docstring in `scripts/db/store_impl.py:39` ("Search for k nearest neighbors by cosine distance.") on the analogous `chunks_vec` search path — this is a comment, not an actual `vec0` configuration, and does not apply to `memories_vec`.
- `sqlite-vec`'s `vec0` module defaults to L2 (Euclidean) distance when no `distance_metric` is specified, but this default is never stated anywhere in this repo's source.

## Problem

- The actual distance metric behind `MemoryHit.score` (via `mv.distance`) cannot be determined from the `scripts/agent/memory` module alone, nor from the `memories_vec` table definition in `scripts/db/schema_sql.py`, since no `distance_metric` is explicitly declared.
- This was independently re-verified against current source on 2026-07-27 and the ambiguity still exists — the issue has not been resolved by any subsequent code change.
- Downstream consumers of `MemoryHit.score` (ranking, thresholding, evaluation of memory-search quality) implicitly assume a metric (e.g., cosine similarity semantics) that is not guaranteed by the schema.

## Reason for Change

- Without an explicit, verifiable distance metric, engineers and future maintainers risk misinterpreting `MemoryHit.score` — e.g., assuming bounded cosine similarity (`[-1, 1]`) when the actual value is a negated unbounded L2 distance, which would corrupt any logic that thresholds or normalizes scores.
- Making the metric explicit in the schema (or verifying and documenting the current implicit default) removes an unresolved "Needs confirmation" item and gives the memory module discoverable, self-contained behavior.

## Implementation Intent

- Investigate the actual behavior of the `memories_vec` `vec0` virtual table to determine, with certainty, which distance metric it currently uses at runtime (not just from static source reading, since `vec0` may apply an undocumented-in-repo default).
- Based on the investigation outcome, decide whether to (a) make the metric explicit and intentional in the schema definition (e.g., add `distance_metric=cosine` or `distance_metric=L2` to the `CREATE VIRTUAL TABLE` statement in `schema_sql.py`), and/or (b) update the documentation to state the confirmed metric, removing the NC-004 "Needs confirmation" marker.
- This requirement covers the investigation and the schema/code-level clarification; documentation updates (`docs/*.md`) should follow in a later phase per the standard workflow, once the investigation's factual conclusion is available.

## Implementation Instructions

1. Determine the installed `sqlite-vec` version used by this project (check `requirements.txt` / `pyproject.toml` / lockfile) and consult that version's documentation or source for the default `distance_metric` applied by `vec0` when the clause is omitted.
2. Empirically verify the default by writing a small isolated test/script: insert a few known vectors into a `vec0` table created without `distance_metric`, query with `MATCH`, and confirm whether `distance` values match L2 (Euclidean) or cosine distance formulas computed independently (e.g., using numpy) for the same vectors.
3. Cross-check whether embeddings inserted into `memories_vec` (via the embedding client / ingestion path in `scripts/agent/memory/`) are normalized to unit length before insertion. If they are, L2 distance and cosine distance become monotonically related, which would materially affect the ranking-interpretation risk described in the Problem section — document this finding either way.
4. Based on the confirmed metric, update `scripts/db/schema_sql.py:134-137` to add an explicit `distance_metric=...` clause to the `memories_vec` `CREATE VIRTUAL TABLE` statement, so the metric is discoverable directly from the schema rather than relying on an undocumented extension default. Apply the same clarification to `chunks_vec` (`schema_sql.py:47-50`) if it shares the same ambiguity.
5. Update the comment at `scripts/agent/memory/retriever.py:185` ("Negate distance...") to name the confirmed metric explicitly, so the module is self-contained per NC-004's original concern.
6. Do not edit `docs/*.md` files as part of this requirement's implementation; a follow-up documentation-update step (outside this workflow phase) should update `docs/05_agent_12_04_memory-module-ref-retrieval-and-injection.md:66` and clear the NC-004 entry in `docs/00_governance_07_needs-confirmation-inventory.md` once the schema change lands.
