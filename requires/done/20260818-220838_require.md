# Complete the EventBus ACK/NACK, Offset-Precedence, Persistence-Reconciliation, and Production Authentication Contract

## Priority
High

## Background

`docs/06_eventbus_*.md` already documents a large part of the EventBus contract: the delivery
guarantee (at-least-once, `docs/06_eventbus_04_dlq_offsets_and_delivery_semantics.md`), per-topic
ordering, consumer-offset non-monotonicity (registered as known issue `EVENTBUS-001` in
`docs/06_eventbus_90_inconsistencies_and_known_issues.md`), JSONL's role as a secondary/non-
authoritative archive vs SQLite as the authoritative store (`docs/06_eventbus_03_persistence_schema_and_replay.md`,
`docs/06_eventbus_02_05_failure-behavior-summary.md`), publish idempotency, and replay pagination
format.

However, verification against the current implementation
(`scripts/eventbus/ack_route.py`, `scripts/eventbus/db.py`, `scripts/eventbus/subscribe_route.py`,
`scripts/eventbus/config.py`) shows four areas that the existing documentation set does not cover
and that remain functionally undefined or unimplemented:

1. The full ACK/NACK interaction matrix and consumer-identity handling.
2. Precedence between an explicit `since_seq` and a stored consumer offset.
3. Reconciliation and monitoring procedures for partial-persistence scenarios.
4. A production authentication/authorization model — none exists today beyond a loopback-bind
   check.

## Problem

1. **ACK/NACK matrix is incomplete.** `ack_event()` in `scripts/eventbus/db.py` is idempotent
   (`UPDATE ... WHERE acked_at IS NULL`, distinguishing found/newly-acked/already-acked), but
   `nack_event()` unconditionally increments `delivery_failure_count` on every call with no
   idempotency check — duplicate NACKs are not defined as a distinct case anywhere. Neither route
   checks whether an event was already NACKed before ACK (`ack_event` succeeds regardless of
   `delivery_failure_count`/`dlq_at`) or already ACKed before NACK (`nack_event` succeeds
   regardless of `acked_at`), so "ACK after NACK" and "NACK after ACK" have no documented or
   enforced semantics. There is also no consumer registry (`schema.sql` has no consumer/event
   ownership column) — `ack_route.py`'s `consumer_id` is only used to write an offset file, never
   validated against who is allowed to ack/nack a given event — so "consumer mismatch" is neither
   detected nor documented as intentionally unenforced.

2. **`since_seq` vs. stored offset precedence is ambiguous.** In
   `scripts/eventbus/subscribe_route.py`, `start_seq = since_seq; if consumer_id and start_seq == 0: start_seq = read_offset(...)`.
   This makes an explicit `since_seq=0` (client wants full replay) indistinguishable from an
   omitted `since_seq` (client wants resume-from-offset) whenever `consumer_id` is also supplied.
   No document among the 06_eventbus_* set states this precedence rule or its edge case.

3. **No reconciliation procedure exists for partial-persistence failures.** Docs state that a
   JSONL append failure after a successful SQLite commit still returns HTTP 200 with a WARNING log
   (`scripts/eventbus/publish_route.py`), but no document defines how an operator detects or
   repairs SQLite/JSONL divergence after such a failure, nor what metrics/alerts should exist to
   surface it (task items 17–18 of the source issue remain open).

4. **No production authentication/authorization model exists.** `scripts/eventbus/config.py` only
   validates that the bind host is not a public/wildcard address unless `allow_public_bind=true`;
   there is no bearer token, mTLS, reverse-proxy, or per-consumer authorization support anywhere in
   `scripts/eventbus/`, and no `Authorization`/token handling in any route file. No
   project-level OpenAPI document exists to reflect a security model. This is a real, currently
   un-selected design decision, not a documentation gap alone.

## Reason for change

Without resolving these four points, clients still cannot safely implement: (a) correct handling
of concurrent/duplicate ACK and NACK calls or event ownership across consumers, (b) predictable
resume-vs-replay behavior when both `since_seq` and `consumer_id` are supplied, (c) operational
recovery from silent SQLite/JSONL divergence, and (d) any production deployment that is reachable
outside of loopback. Each of these directly affects workflow-execution correctness, auditability,
and safe production exposure, as stated in the source issue.

## Implementation intent

This is a documentation-and-design requirement, not a code-behavior-change requirement (no source
files are to be modified in this phase). The next phase should:

- Extend the existing EventBus documentation set (most naturally
  `docs/06_eventbus_02_02_subscribe-ack.md`, `docs/06_eventbus_02_03_nack-health-dlq.md`, and
  `docs/06_eventbus_90_inconsistencies_and_known_issues.md`) with the missing ACK/NACK transition
  table and consumer-identity policy, explicitly stating which transitions are enforced by code
  today versus merely documented as client responsibility.
- Add an explicit precedence rule for `since_seq` vs. stored consumer offset to
  `docs/06_eventbus_02_02_subscribe-ack.md` (or a new section), including the `since_seq=0`
  ambiguity, and decide whether this is a documentation-only clarification or requires a
  sentinel-value code fix (e.g., `since_seq=-1`/absent vs. `0`) — if a code fix is judged
  necessary, it must be scoped as a separate follow-up implementation requirement, not bundled into
  this documentation phase.
- Define a reconciliation procedure and minimum required logs/metrics/alerts for SQLite/JSONL
  divergence, to be added to `docs/06_eventbus_03_persistence_schema_and_replay.md` and/or
  `docs/06_eventbus_90_inconsistencies_and_known_issues.md`.
- Select one production authentication/authorization model (per the source issue's evaluated
  options: loopback-only binding, static bearer token, rotatable service token, mutual TLS,
  reverse-proxy authentication, per-consumer authorization) and document it, including
  unauthorized/forbidden response definitions, local-development exceptions, secret
  provisioning/rotation, and how production config validation should reject an insecure
  configuration. Note that selecting/implementing this model may itself be EventBus
  implementation work and, per `AGENTS.md` Global Rule 8, must not be implemented directly — only
  the decision and its documentation belong to this requirement; a subsequent phase must route any
  actual code change through the process that rule permits.

## Implementation instructions

1. Add a full ACK/NACK state-transition table (first ACK, duplicate ACK, first NACK, duplicate
   NACK, ACK-after-NACK, NACK-after-ACK, unknown event ID, concurrent ACK/NACK, consumer mismatch)
   to the EventBus docs, each row stating: current code behavior (verified against
   `scripts/eventbus/db.py::ack_event/nack_event` and `scripts/eventbus/ack_route.py`), HTTP status
   code, response body, and persistence side effect. Explicitly mark "consumer mismatch" as
   currently undetected/unenforced (no consumer-ownership column exists) rather than silently
   omitting it.
2. Document the `since_seq` / stored-offset precedence rule and the `since_seq=0` ambiguity in
   `docs/06_eventbus_02_02_subscribe-ack.md`, cross-referencing
   `scripts/eventbus/subscribe_route.py` line-level behavior.
3. Document "unknown or mismatched consumer" behavior for both `/subscribe` (offset read) and
   `/events/{event_id}/ack` (offset write): today any `consumer_id` string is accepted with no
   registry check, and this should be stated as a deliberate limitation or flagged as a required
   follow-up.
4. Add a reconciliation section describing: how to detect SQLite/JSONL divergence (e.g., comparing
   max `seq` in SQLite vs. last line in `events.jsonl`), what log fields already exist to support
   this (`scripts/eventbus/publish_route.py`'s WARNING log), and what additional metrics/alerts
   (if any) are recommended.
5. Add a new "Known Issue" entry (or extend `EVENTBUS-001`'s neighbors) in
   `docs/06_eventbus_90_inconsistencies_and_known_issues.md` for "no production authentication
   model" alongside the existing offset-monotonicity entry, so it is tracked with the same rigor.
6. Produce a short design note selecting one authentication/authorization model from the six
   options in the source issue, with rationale, and describing unauthorized (401) vs. forbidden
   (403) response shapes, local-dev bypass conditions, and secret rotation expectations. This note
   is documentation only in this phase — it is the input to a future implementation requirement.
7. Do not modify any file under `scripts/`, `docs/*.md`, or elsewhere as part of this phase; only
   `requires/` and `issues/done/` may be touched by this workflow step. The next phase (design/plan)
   is responsible for actually editing `docs/06_eventbus_*.md`.

## Acceptance criteria

- [ ] A complete ACK/NACK transition table exists covering all nine scenarios listed in
      Implementation instructions #1, each with an HTTP status, response body, and persistence
      side effect, verified against current code.
- [ ] Consumer-mismatch/unknown-consumer behavior is explicitly documented as unenforced (or a
      follow-up requirement is raised to enforce it).
- [ ] `since_seq` vs. stored-offset precedence, including the `since_seq=0` ambiguity, is
      documented with a stated resolution (documentation-only clarification, or a flagged
      follow-up code-fix requirement).
- [ ] A reconciliation procedure and required logs/metrics/alerts for SQLite/JSONL divergence are
      documented.
- [ ] One production authentication/authorization model is selected and documented, with
      unauthorized/forbidden responses, local-dev exceptions, and secret rotation expectations.
- [ ] The "no production authentication model" gap is registered as a known issue with the same
      rigor as `EVENTBUS-001`.
- [ ] No file under `scripts/` was modified as part of satisfying this requirement in the current
      phase.

## Tests

- This phase is documentation/design only; no automated tests are produced here.
- The resulting documentation must specify, for a later test-writing phase, concrete test cases
  for: each ACK/NACK transition, `since_seq=0`-with-`consumer_id` vs. `since_seq` omitted, and
  (once an auth model is implemented) unauthorized/forbidden access attempts — so that a future
  implementation/test phase can directly convert these into pytest cases.
