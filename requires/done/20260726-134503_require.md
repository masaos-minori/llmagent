# Add guard tests for approval resolution race condition

## Priority

## Background

A race condition exists between checking pending approvals and resolving them during /approve command execution. Multiple concurrent requests could resolve the same approval simultaneously. The sequence is: count_pending_approvals → find_approval_by_id → resolve_approval. Between steps 1 and 2, another process could resolve the same approval, causing step 3 to attempt re-resolution of an already-resolved approval. In SQLite WAL mode, transaction consistency across different connections isn't guaranteed. Additionally, when find_approval_by_id returns None or status != "pending", it's unclear whether the approval was already resolved or doesn't exist.

## Problem

Double approval possible in concurrent environments, especially with parallel API access.

## Reason for Change

Establish behavioral baseline through guard tests before any refactoring of these components.

## Implementation Intent

Create comprehensive guard tests covering:
- Concurrent approval resolution detection
- Optimistic locking verification
