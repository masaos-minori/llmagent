# Document the absence of a retention/cleanup policy for `rag-src/registered/` files

## Priority
Low

## Target files
`docs/01_overview-files-02-rag.md` (~lines 27-34, the file-structure tree showing `registered/`)

## Background
`docs/01_overview-files-02-rag.md` documents the `rag-src/` directory layout, including
`registered/`, which the comment describes as "DB 投入済みファイル (ingester.py が移動)"
(files moved here by `ingester.py` once ingested into the DB). This naming convention
communicates a state transition (chunk → registered) but says nothing about how long
files remain in `registered/` or whether/how they are ever cleaned up.

## Problem
A reader relying on this document to make disk-usage or operational decisions (e.g.
"can we safely clear out `registered/`? does it grow unbounded?") cannot answer that
question from this document alone, and — per verification below — cannot answer it from
any other current documentation either, because no such policy exists in the codebase.

## Reason for change
Leaving an operationally relevant gap (unbounded disk growth potential) silently
undocumented risks an operator either deleting files that are still needed or assuming a
cleanup job exists when none does. Making the gap explicit lets a reader immediately
know to treat `registered/` disk usage as a manual/operational concern rather than
searching further documentation for a non-existent policy.

## Verification performed (for the next phase's reference — no further search needed)
- Searched all `docs/03_rag_*.md` files for any statement of a retention, cleanup, TTL,
  purge, or disk-usage policy for the `registered/` directory or the files inside it.
  Every hit for "registered" in that directory relates to a different concept: DB-row
  deletion order (`chunks_vec` → `documents` cascade), URL/document dedup ("already
  registered"), or the CLI `--force` re-ingest flag. None describe removing files from
  the `rag-src/registered/` directory on disk.
- Searched all of `docs/*.md` (not just `03_rag_*`) for TTL/cron/purge/retention/cleanup
  keywords. All matches that mention actual retention policies belong to unrelated
  subsystems: agent session DB retention (`purge_old_sessions`, `sqlite_retention_max_age_days`,
  `memory_retention_days`), the `session_diagnostics` table's `retention_days` config, and
  the in-memory `ToolExecutor`/`ToolResultCache` TTL caches. None apply to `rag-src/registered/`.
- Searched `scripts/rag/ingestion/ingester.py` (the module that writes into
  `registered/`) and grepped all of `scripts/` for other "registered" references. The
  only code touching `_registered_dir` is `_move_to_registered()` /
  `_route_chunk_files()`, which move files **into** `registered/`. No code anywhere
  deletes, expires, or otherwise cleans up files already inside `registered/`.
- Conclusion: there is no retention/cleanup policy for `rag-src/registered/` anywhere in
  current docs or code — files accumulate there indefinitely with no automated or
  documented manual cleanup process. This is a genuine documentation gap, not something
  merely missing a cross-reference.

## Implementation intent

Confirmation" style note directly to `docs/01_overview-files-02-rag.md` next to the
`registered/` file-structure entry, stating plainly that the retention/cleanup policy for
this directory is unconfirmed/undocumented within the scope of this file. Do not invent
or imply a policy that doesn't exist, and do not implement any actual cleanup mechanism —
this is documentation-only.
