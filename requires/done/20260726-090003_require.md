# Unconditional double-invocation of tool approval checks

## Priority

Medium

## Target Files

- `scripts/agent/tool_runner.py` — `_run_approval_gate()` (line ~457/474-489)
- `scripts/agent/repository_gateway.py` — `RepositoryGateway._gate_write()` (line ~106)
- `scripts/agent/tool_approval.py` — `run_approval_checks()` (line ~190-202), specifically the unused `skip_in_workflow_mode` parameter

## Background

`run_approval_checks()` in `tool_approval.py` is the single, shared implementation of interactive per-tool approval. It is invoked from two independent call sites for the same tool call:

1. `tool_runner.py:457` calls `_run_approval_gate(ctx, tool_calls)` (defined at `tool_runner.py:474-489`), which in turn calls `run_approval_checks(ctx, tool_calls)` at batch level, before any tool in the batch is executed.
2. For any tool call classified as a write/risky operation (`risk != RiskLevel.NONE`), `RepositoryGateway._gate_write()` (`repository_gateway.py:81-123`) calls `run_approval_checks(ctx, [tool_call_dict])` again at `repository_gateway.py:106`, per call, during actual execution.

Because `factory.py:499-509` always constructs and attaches a non-None `RepositoryGateway` to the agent context, every risky tool call goes through both gates. Neither call site passes `skip_in_workflow_mode=True`, and there is no shared state between the two call sites to suppress the second check once the first has approved a call.

An originating issue (`issues/20260726_14_issue.md`) described this as a workflow-mode-specific problem: it claimed that `tool_approval.py:200-202` skips approval "in workflow mode" while `repository_gateway.py`'s gate runs "independently," causing a bypass/mismatch specific to workflow mode.

## Problem

Investigation of current source shows the issue's framing is not accurate, but a related, broader problem is real:

- `run_approval_checks()` has one implementation only; there is no separate `_run_approval_checks()` function as the issue implies. Both `tool_runner.py:457` (via `_run_approval_gate`) and `repository_gateway.py:106` (via `_gate_write`) call this same function.
- The skip condition at `tool_approval.py:200-202` (`if skip_in_workflow_mode: ... return tool_calls, []`) is real, but `skip_in_workflow_mode` defaults to `False` and is **never passed as `True` by any caller** in the codebase (verified by grep across `scripts/agent/`). It is effectively dead code today — there is no active workflow-mode wiring, so there is no scenario where one gate skips due to workflow mode while the other does not.
- The docstring of `_run_approval_gate()` (`tool_runner.py:480-482`) asserts: "When the workflow definition sets require_approval=true, workflow-level approval gates are inserted between execute and verify stages. In this case, per-tool approval is skipped during the execute stage to avoid double-prompting." This describes intended behavior that is not implemented: `_run_approval_gate` always calls `run_approval_checks` with the default `skip_in_workflow_mode=False`, regardless of workflow mode.
- The actual, verified defect: for **every** risky/write tool call, in **every** mode (not only workflow mode), `run_approval_checks()` runs twice — once at the batch level in `tool_runner._run_approval_gate` and once at the per-call level in `repository_gateway._gate_write` — resulting in two separate interactive approval prompts for the same logical tool call, with no deduplication between the two call sites.

## Reason for Change

Double-prompting a user (or a scripted approver) for the same tool call is confusing, wastes interaction cycles, and risks divergent outcomes if the two prompts are answered differently (e.g., approved in the batch gate but denied in the gateway gate, or vice versa). The existing `skip_in_workflow_mode` parameter and the docstring in `tool_runner.py` indicate that avoiding double-prompting was an explicit design goal that was never completed — the wiring to activate the skip is missing. This gap should be closed so behavior matches the documented intent, and so redundant prompting does not occur in any mode, not just workflow mode.

## Implementation Intent

Ensure `run_approval_checks()` is invoked at most once per logical tool call for a given execution path. Either:

- (a) Wire up `skip_in_workflow_mode` (or an equivalent signal) end-to-end so that once approval has been granted for a tool call at the batch level in `tool_runner._run_approval_gate`, `repository_gateway._gate_write()` does not re-run `run_approval_checks()` for the same call; or
- (b) Establish a single authoritative gate location (e.g., make the gateway's per-call check authoritative and have `tool_runner._run_approval_gate` a no-op/pass-through, or vice versa), removing the redundant call site entirely.

Correct the stale docstring in `tool_runner.py:474-489` to reflect whichever behavior is actually implemented after the fix.

## Implementation Instructions

1. Decide on a single approval-gate ownership model (batch-level in `tool_runner.py` vs. per-call in `repository_gateway.py`) and document the decision in code comments/docstrings.
2. If keeping both call sites, thread an "already approved" signal (e.g., a set of approved tool-call IDs stored on `ctx` or passed through the call chain) from `_run_approval_gate` into `RepositoryGateway._gate_write`, and have `_gate_write` skip `run_approval_checks()` for tool calls already present in that approved set.
3. If eliminating a call site instead, remove the now-redundant call to `run_approval_checks()` from `repository_gateway._gate_write()` (or from `tool_runner._run_approval_gate`), ensuring the remaining call site still covers all tool-call types currently gated by both (write tools invoked directly through the gateway outside the batch path, if any).
4. Update the docstring of `_run_approval_gate()` in `tool_runner.py:474-489` so it accurately describes the implemented behavior (remove or correct the claim about workflow-mode skipping if `skip_in_workflow_mode` is not the mechanism used).
5. If `skip_in_workflow_mode` ends up unused after the fix, remove the dead parameter from `run_approval_checks()`'s signature in `tool_approval.py`; if it becomes the chosen mechanism, ensure it is actually set to `True` by the appropriate caller(s).

## Acceptance Criteria

- [ ] For a single risky/write tool call, `run_approval_checks()` (or its effective approval logic) executes at most once per logical call, in all modes (workflow mode and non-workflow mode).
- [ ] No user-facing duplicate interactive approval prompt occurs for the same tool call.
- [ ] `tool_runner.py`'s `_run_approval_gate()` docstring accurately reflects the implemented skip/dedup behavior.
- [ ] The `skip_in_workflow_mode` parameter in `tool_approval.run_approval_checks()` is either actively wired up by a real caller or removed if unused.
- [ ] Existing approval-denial behavior (a denied tool call is not executed) continues to work correctly after the change.

## Tests

- Unit test: simulate a risky tool call going through `tool_runner._run_approval_gate` followed by `repository_gateway._gate_write`; assert the underlying approval-check function is invoked exactly once for that call.
- Unit test: verify a denied tool call at the batch-level gate never reaches `repository_gateway._gate_write`'s execution path.
- Unit test (if dedup approach chosen): verify a tool call approved at the batch level is not re-prompted at the gateway level, using a mocked/stubbed interactive approval function to count invocations.
- Regression test: verify normal (single-gate) tool calls that bypass the batch gate (if any exist) are still correctly gated exactly once.
