# Pin MCP server subprocess startup to avoid implicit `uv run` dependency resolution

## Priority

Low

## Target Files

- `config/agent.toml:299,311,320,329,338,347,364,373,382,394` — all `[mcp_servers.<key>]` sections define `cmd = ["uv", "run", "--directory", "/opt/llm", "python", ...]`
- `scripts/agent/http_lifecycle.py:222,230-231` — `HttpServerLifecycleManager.start()` launches `cfg.cmd` verbatim via `subprocess.Popen`

## Background

Every `[mcp_servers.<key>]` entry in `config/agent.toml` (`shell`, `git`, `web_search`, `file_delete`, `file_write`, `file_read`, `github`, `cicd`, `rag_pipeline`, `mdq`) uses the same `cmd` pattern:

```toml
cmd = ["uv", "run", "--directory", "/opt/llm", "python", "/opt/llm/scripts/mcp_servers/<name>/<name>_server.py"]
```

`HttpServerLifecycleManager.start()` (`scripts/agent/http_lifecycle.py:222-231`) passes this `cmd` list directly to `subprocess.Popen` with no additional flags or environment guard.

By default, `uv run` checks the invoking project's `pyproject.toml` / `uv.lock` for consistency on every invocation and will transparently resolve and sync dependencies (installing/upgrading packages in the project's venv) if it decides the environment is out of date. This happens on every MCP server subprocess start, not just at deploy time.

## Problem

Because none of the `cmd` entries pass a flag that disables this behavior (e.g. `--frozen` or `--no-sync`), each MCP server startup can trigger implicit dependency resolution/sync against `/opt/llm/pyproject.toml` and `/opt/llm/uv.lock`. If write access to those files (or to the project venv) is not tightly restricted in the deployment environment, this means:

- MCP server startup time is not deterministic (dependency resolution/sync can run unexpectedly).
- The effective dependency set for a running MCP server could silently drift between restarts if `pyproject.toml`/`uv.lock` are writable, without any corresponding code change being reviewed or deployed.

This is not a pure application bug — it depends on production file permissions — but the codebase currently provides no defense-in-depth against it: nothing in `config/agent.toml` or `scripts/agent/http_lifecycle.py` constrains `uv run` to a strictly locked, non-resolving invocation.

## Reason for Change

Startup commands for security- and correctness-sensitive subprocesses (MCP servers with roles like `file_write`, `file_delete`, `execute`) should be deterministic regardless of external file-permission configuration. Adding an explicit "do not resolve/sync dependencies at runtime" flag to `uv run` removes this class of risk at the config level, independent of whatever permissions are (or are not) correctly set in a given deployment, and makes the intended behavior self-documenting in `config/agent.toml`.

## Implementation Intent

Make all MCP server `cmd` entries in `config/agent.toml` invoke `uv run` in a mode that never performs implicit dependency resolution or environment sync at startup (e.g. `uv run --frozen ...` or `uv run --no-sync ...`), so that:
- Startup fails fast and loudly if the locked environment is not already prepared, instead of silently mutating it.
- No production write-permission assumption is required for correct, deterministic MCP server startup.

## Implementation Instructions

1. Confirm which `uv run` flag best fits the deployment model (`--frozen` to skip lockfile freshness checks and use the lockfile as-is without updating it, vs `--no-sync` to skip environment sync and assume the venv is already prepared) — coordinate with deploy tooling under `/opt/llm` (see `deploy` skill / deployment scripts) to ensure the venv is prepared ahead of time (e.g. during deploy, not at MCP server start).
2. Update the `cmd` array in every `[mcp_servers.<key>]` section of `config/agent.toml` (lines 299, 311, 320, 329, 338, 347, 364, 373, 382, 394) to insert the chosen flag immediately after `"run"`, e.g. `["uv", "run", "--frozen", "--directory", "/opt/llm", "python", ...]`.
3. Verify `HttpServerLifecycleManager.start()` in `scripts/agent/http_lifecycle.py` requires no changes since it forwards `cfg.cmd` verbatim; confirm no other code path (tests, docs examples) hardcodes the old `cmd` shape and would need updating in lockstep.
4. Add or update deployment documentation/runbook notes (outside `docs/*.md` scope of this requirement — flag as a follow-up) describing that the venv/lockfile at `/opt/llm` must be fully synced before MCP servers are started, since runtime sync is now disabled.
5. Manually verify (or add a smoke test) that an MCP server still starts successfully with the new flag when the `/opt/llm` venv is already in sync, and fails with a clear error if the lockfile/venv is stale — confirming the fail-fast behavior works as intended.

## Acceptance Criteria

- [ ] MCP servers still start successfully in a correctly-prepared deployment (synced venv/lockfile).
- [ ] Starting an MCP server against a deliberately stale lockfile/venv now fails fast with a clear error instead of silently resolving/syncing dependencies.
