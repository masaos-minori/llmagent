# Restructure docs/01_overview-files-04-shared-part2.md: replace stale manual file tree, document 3 missing files, add cache/health-gate design rationale, confirm drift-verification failure behavior

## Priority
High

## Target files
- `docs/01_overview-files-04-shared-part2.md` (primary target; ~lines 26-71 contain the manual file tree)

## Background
`docs/01_overview-files-04-shared-part2.md` documents `scripts/shared/` via a manually-maintained
ASCII file tree with one-line per-file descriptions (section "## 3. ファイル構成", lines ~26-71).
Manual trees of this kind drift from source over time because nothing enforces that new files in
`scripts/shared/` get added to the doc. This issue was raised as part of a broader documentation
review (`docs_review_overview_architecture.md` §2/§3/§6A/§6B) that flagged this specific file tree
as a maintenance-cost-not-justified pattern with confirmed, already-manifested drift.

## Problem
Verification against current source (`ls scripts/shared/` compared to the doc's tree) confirms:

1. **Missing files (confirmed drift).** Three files exist in `scripts/shared/` but are absent from
   the doc's file tree: `config_utils.py`, `runtime_tool.py`, `runtime_tool_registry.py`. All three
   are current, non-experimental production modules (not dead code, not `__pycache__`).
2. **Design rationale gap.** The doc's entries for `tool_cache.py`, `mcp_health.py`, and
   `tool_transport_invoker.py` already have one-line class/type summaries (e.g. "LRU キャッシュ +
   TTL"), but no *design-intent* prose explaining the TTL-cache staleness/duplicate-call tradeoff
   or why tool dispatch is health-gated. Source inspection additionally reveals a fact the doc does
   not state: `tool_cache.py`'s `ToolResultCache` is **not currently used** by `ToolExecutor` —
   `ToolExecutor` maintains its own internal cache (`shared/tool_executor.py` `_execute_with_cache()`
   / `_store_and_evict()`) with stampede protection that `ToolResultCache` lacks. `ToolResultCache`
   is a standalone utility for a future caller, not the canonical cache — the doc's current wording
   could mislead a reader into thinking it is the active cache.
3. **Drift-verification failure behavior undocumented.** The doc does not state whether a detected
   routing-drift mismatch blocks startup or only warns.

## Reason for change
- The missing-file gap is confirmed, present-day drift, not a hypothetical risk.
- `runtime_tool_registry.py` is confirmed (via source reading of
  `scripts/shared/runtime_tool_registry.py` and `scripts/shared/route_resolver.py`) to be the
  **sole routing authority**: `route_resolver.py`'s module docstring and
  `ToolRouteResolver.resolve()` state "`RuntimeToolRegistry` ... is the sole routing authority ...
  `ToolRegistry` is no longer consulted here." This is directly relevant to the separately-tracked
  arch-03 tool-routing-priority documentation error — leaving `runtime_tool_registry.py`
  undocumented here risks compounding that confusion, since a reader of this file-structure doc has
  no way to learn that routing authority moved away from `ToolRegistry`/`tool_registry.py` to
  `RuntimeToolRegistry`.
- The cache/health-gate design tradeoffs (staleness risk vs. reduced duplicate calls; health-gating
  dispatch by server health) are useful context currently missing, and the doc's silence on
  `ToolResultCache` being unused-by-ToolExecutor is actively misleading, not merely incomplete.
- Operators reading a startup/runtime drift warning need to know today, without reading source,
  whether it means "informational" or "the process will refuse to start" — this is now a confirmed,
  documentable fact (see Implementation instructions below), not an open question.

## Implementation intent
Replace the manually-maintained file tree with a short pointer to `scripts/shared/` as the
authoritative file listing (i.e., stop duplicating `ls scripts/shared/` in prose). Retain (or fold
into prose) any information the tree currently carries that is not recoverable by just listing the
directory: notably the one-line per-file responsibility descriptions, since those add value beyond
a bare `ls`. Add the 3 missing files with their responsibility. Add a short design-rationale
paragraph for the cache/health-gate cluster. State the confirmed drift-verification failure
behavior as fact, citing the controlling config flags.

## Implementation instructions
1. **Remove the ASCII file tree** (~lines 26-71 of `docs/01_overview-files-04-shared-part2.md`).
   Replace it with a pointer directing the reader to `scripts/shared/` for the current, authoritative
   file list (e.g. "see `scripts/shared/` for the current file list"), while preserving the
   responsibility-description content in a form that doesn't require re-deriving it from source
   (a flat or lightly-grouped list is acceptable; an ASCII tree diagram is not required).

2. **Add the 3 missing files** with a one-line responsibility description each, based on source
   read during this requirement's investigation:
   - `config_utils.py` — Typed config value accessors (e.g. `get_str()`) for reading typed values
     out of raw config dicts (TOML/JSON-loaded), raising `ValueError` on type mismatch.
   - `runtime_tool.py` — Defines `RuntimeTool` (frozen dataclass: normalized runtime tool metadata:
     name, server_key, server_url, description, input_schema, is_write, requires_serial,
     resource_scope, agent_safety_tier, requires_approval, enabled_for_llm, capabilities, etc.) and
     `build_runtime_tool()` safe-default construction. Also defines `AgentSafetyTier` (a `Literal`
     that intentionally duplicates, rather than imports, `agent.tool_policy`'s tier vocabulary, to
     respect the `shared`-is-leaf import-layer contract).
   - `runtime_tool_registry.py` — Defines `RuntimeToolRegistry`, an in-memory `{name: RuntimeTool}`
     registry populated by `McpToolDiscoveryService.discover_all()` at startup and wired into
     `ToolExecutor` via `set_runtime_registry()`. **This is the sole routing authority** consulted
     by `shared.route_resolver.ToolRouteResolver.resolve()` — `shared.tool_registry.ToolRegistry`
     is no longer consulted for routing (it remains in use only as drift-detection input; see
     `tool_registry.py`'s own module docstring). The doc entry should flag this routing-authority
     role explicitly, since it is directly relevant to the tool-routing-priority question tracked
     separately in the arch-03 critical fix issue (do not resolve that issue here — only note the
     connection, per this requirement's scope).

3. **Add a short (1-2 sentence) design-rationale paragraph** covering `tool_cache.py`,
   `mcp_health.py`, `tool_transport_invoker.py` as a cluster:
   - State the TTL-cache tradeoff: caching tool results for a bounded TTL reduces duplicate
     upstream calls at the cost of bounded staleness risk.
   - State that dispatch is health-gated: `McpServerHealthRegistry` tracks per-server health
     (HEALTHY/DEGRADED/UNAVAILABLE/HALF_OPEN) so `ToolTransportInvoker`/`ToolExecutor` can avoid
     dispatching to servers known to be failing.
   - Explicitly note that `tool_cache.py`'s `ToolResultCache` is a standalone utility **not
     currently wired into `ToolExecutor`** (which has its own internal cache in
     `tool_executor.py`) — do not let the doc imply `ToolResultCache` is the active/canonical cache.

4. **Document the drift-verification failure behavior as confirmed fact** (this requirement's
   investigation determined it fully — do not mark as "Needs Confirmation"). There are two
   independent drift checks, each with its own gating:
   - **Config-drift** (`shared.tool_routing_validation.validate_routing_against_config()`, invoked
     from `scripts/agent/repl_health.py::check_routing_drift()` during startup): mismatches are
     logged as warnings and returned; the check only **raises `RuntimeError`** (which
     `scripts/agent/startup.py` treats as a pipeline-fatal outcome, aborting startup) when
     `ctx.cfg.tool.routing_drift_strict` is `True`. Default behavior is warn-only.
   - **Live-drift** (`shared.tool_routing_validation.validate_routing_against_live()`, invoked from
     `scripts/agent/services/mcp_tool_discovery.py`'s `_build_drift_findings()`): mismatches are
     surfaced as `StartupCheckOutcome`s whose severity is `FATAL` (blocks startup — `startup.py`
     raises `RuntimeError("Startup validation failed: ...")` when any pipeline outcome is FATAL) if
     `_is_fatal_severity()` is true, i.e. `tool_definitions_strict` config is `True` **or**
     `security_profile == PRODUCTION`; otherwise the outcome is `WARNING` (does not block).
   - As a secondary, related fact worth one line: duplicate tool-ownership findings (a tool name
     claimed by more than one server) are always `FATAL` regardless of strict mode or security
     profile — noted in `mcp_tool_discovery.py`'s module docstring.
   Summarize this in prose (config-drift: warn unless `routing_drift_strict`; live-drift: warn
   unless strict tool definitions or production profile; duplicate ownership: always fatal). Do not
   go into implementation-procedure-level detail — this is a documentation summary, not a
   reproduction of the source.
