## Background
The issue's premise is that the project has "switched to a Qwen3 1024-dimensional fixed embedding design" and that stale E5/384 references now need cleanup. Verification against current source shows this premise is **not yet true**: no code path in this repository currently references Qwen3 as an embedding model, and every location listed above still actively implements the E5-era design — `"passage: "`/`"query: "` prefixes are prepended in `ingester.py` and `llm_client.py`, `embedding_client.py` still carries a `query_prefix` field and a hard `embed_dim` dimension check defaulting to 384, and both `config/agent.toml` and `config/ingester.toml` set `embedding_dims`/`memory_embed_dim` to `384` as the live, load-bearing configuration value (not merely a comment).

Four other requirement documents already exist that specify the actual functional migration this cleanup depends on:
- `requires/20260802-070234_require.md` — fix the embedding dimension contract to a Qwen3 1024-dimensional constant; removes `DbConfig.embedding_dims`, `MemoryConfig.memory_embed_dim`, `_check_embedding_dimensions()`.
- `requires/20260802-070538_require.md` — normalize embedding request paths for Qwen3 raw-text embeddings; removes `query_prefix`, `embed_dim`, `DIMENSION_MISMATCH` from `EmbeddingClientConfig`/`_fetch_embedding`/`types.py`, normalizes prefixes in `ingester.py`/`llm_client.py`.
- `requires/20260802-071152_require.md` — integration verification after the functional migration in 070538 lands.
- `requires/20260802-070909_require.md` — chunk-size adjustments referencing the Qwen3 embedding migration as context (not a source of stale-doc references itself).

As of this assessment, none of the above have been implemented in source — only their requirement documents exist. This cleanup issue (06) is explicitly sequenced by its own text to happen "after the implementation changes," so it cannot be correctly executed yet: removing the E5/384 comments now, while the code still performs E5-style prefixing and 384-dimension validation, would make the documentation describe a design the code does not yet implement — the opposite of the issue's stated goal.

## Problem
Once the functional migration described in the four requirement documents above is implemented, the following will become genuinely stale and must be removed/updated:
- Hard-coded `384` defaults and config values (`embedding_dims`, `memory_embed_dim`, `embed_dim`) that no longer match the actual (1024) embedding dimension.
- `E5 passage prefix` / `E5 query prefix` / `query_prefix` field and its use in request construction.
- Docstrings and inline comments describing 384-dimensional output and E5 prefix behavior.

Until that migration lands, these are accurate descriptions of current behavior, not stale leftovers.

## Reason for change
Once the Qwen3 migration (tracked in the four requirement documents above) is implemented, leftover 384/E5/`query_prefix`/`embed_dim` comments, docstrings, and config defaults will mislead future developers into believing the old E5/384 design is still in effect, or into reintroducing E5-style assumptions (e.g., re-adding a prefix, or re-adding a 384 default) when touching this code later.

## Implementation intent
Treat this as a follow-up documentation/comment cleanup pass that runs only after — and in the same change set or immediately following — the functional migration requirements (`20260802-070234`, `20260802-070538`, `20260802-071152`) are implemented. Do not attempt to strip these comments/defaults independently beforehand, since they still describe real behavior. Once the functional code no longer uses E5 prefixes or a 384 dimension:
- Remove or update remaining stale prose (docstrings, inline comments, config file comments) that reference 384, E5, `query_prefix`, or `embed_dim` to describe Qwen3 embedding, 1024-dimensional fixed embedding, and raw-text embedding input.
- Do not reintroduce a hard-coded numeric default in prose or code where the functional requirements already specify removing the configurable/default value entirely (see `20260802-070234_require.md`, which calls for a 1024 code constant, not a configurable default).
