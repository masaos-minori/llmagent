# Fix documentation claiming a nonexistent `_FORBIDDEN_KEYS` fail-fast mechanism for `workflow_mode`

## Priority

Medium

## Target Files

- `docs/01_overview-arch-02-pipelines.md:66` — asserts `workflow_mode` is rejected via `_FORBIDDEN_KEYS` in `build_agent_config()`, raising `ConfigLoadError`
- `docs/05_agent_03_03_turn-processing-flow-workflow-engine-part1.md:109` — cross-references the same unverified claim ("`workflow_mode`が設定キーとして存在しないこと")
- `docs/05_agent_08_01_configuration-loading-agent-config-part2.md:43` — states `workflow_mode`/`workflow_require_approval` "are not valid keys" without describing the actual (non-)enforcement
- `scripts/agent/config_builders.py` — `build_agent_config()` (lines 450-501): no `_FORBIDDEN_KEYS` check exists; confirmed no builder reads or rejects `workflow_mode`
- `tests/test_config_dataclasses.py:178-186` — only verifies `AgentConfig` has no `workflow_mode` attribute; does not verify any config-load rejection behavior

## Background

`docs/01_overview-arch-02-pipelines.md` documents the agent's mandatory-workflow design and claims a specific fail-fast safety guarantee: if a config file sets the key `workflow_mode`, `build_agent_config()` detects it via a `_FORBIDDEN_KEYS` list and aborts startup with `ConfigLoadError`. This claim is repeated/cross-referenced from two other docs (`05_agent_03_03_...` and `05_agent_08_01_...`).

## Problem

Investigation confirms the claimed mechanism does not exist in the current codebase:

- `grep -rn "_FORBIDDEN_KEYS" scripts/ tests/` returns no matches anywhere in the codebase.
- `build_agent_config()` in `scripts/agent/config_builders.py` (lines 450-501) was read in full: it calls `ProductionConfigValidator().validate(...)`, several `_build_*_config(cfg)` helpers, and boolean/string getters, but never inspects the config dict for a `workflow_mode` key, and never raises `ConfigLoadError`.
- No builder function (e.g. `_build_llm_config`) reads or rejects `workflow_mode`; if present in a config file, it is silently ignored — no error, no warning, no code path is affected.
- `tests/test_config_dataclasses.py:178-186` (`test_agent_config_has_no_workflow_mode_field`, `test_agent_config_has_no_workflow_require_approval_field`) only assert that the `AgentConfig` dataclass instance lacks a `workflow_mode`/`workflow_require_approval` attribute. Neither test loads a config dict containing `workflow_mode` through `build_agent_config()` to check for a raised error — so the documented "reject at load time" behavior is untested and, per the source read above, unimplemented.
- The only related enforcement mechanism found in the repository is `tools/check_no_compat.py` (backed by `tests/test_check_no_compat.py`), a CI static-analysis grep over source-code/doc text for compat-leftover patterns (including a `workflow_mode field reference` pattern). This is fundamentally different from what the docs describe: it scans source text at CI time for developer-written code patterns, not runtime user config-file values, and it raises CI lint findings, not `ConfigLoadError` at agent startup.
- A separate unrelated field `workflow_mode: str = ""` exists in `scripts/agent/services/models.py:118` inside `ContextStateView` (a status/display view dataclass), which has no connection to config loading or `AgentConfig`.

## Reason for Change

The documentation makes a specific, falsifiable, testable claim about runtime safety behavior (fail-fast rejection of a config key) that does not hold. This creates a gap between documented audit/safety guarantees and actual system behavior: an operator relying on this doc could believe that setting `workflow_mode` in a config file is guaranteed to be caught and rejected at startup, when in reality it is silently ignored with no error and no log message. This is a documentation-accuracy defect that should be corrected to prevent misplaced confidence in a safety guarantee that isn't implemented, and/or to close the gap by implementing the guarantee if it was originally intended.

## Implementation Intent

Resolve the discrepancy by choosing one of two paths (decision should be made after checking `git log -p -- scripts/agent/config_builders.py docs/01_overview-arch-02-pipelines.md` and related history to determine if `_FORBIDDEN_KEYS` was ever implemented and later removed, or if it was purely aspirational/planned but never built):

1. **Documentation-only fix (default/minimum)**: Correct `docs/01_overview-arch-02-pipelines.md:66` (and the two cross-referencing docs) to accurately describe current behavior — `workflow_mode` is not a recognized/read config key anywhere in `build_agent_config()` or its builder functions; setting it in a config file has no effect and produces no error. Remove or rephrase the `_FORBIDDEN_KEYS`/`ConfigLoadError` claim. Optionally mention the actual, unrelated CI-time static check (`tools/check_no_compat.py`) as a separate, weaker guardrail against developers reintroducing `workflow_mode` handling in source code — but must not conflate it with runtime config-file validation.
2. **Implementation fix (if intended as a real safety guarantee)**: Add an actual forbidden-key check in `build_agent_config()` (or `load_config()`) that raises `ConfigLoadError` when `workflow_mode` (and any other keys documented as forbidden) appear in the loaded config dict, then update `tests/test_config_dataclasses.py` (or a more appropriate test module) with a test that loads a config dict containing `workflow_mode` through `build_agent_config()` and asserts `ConfigLoadError` is raised.

This requirement does not mandate which path to take — that decision belongs to whoever picks up the resulting work plan, informed by the git-history check above. Given this is a doc/implementation-fork decision, the work-plan phase must record which path was chosen and why.
