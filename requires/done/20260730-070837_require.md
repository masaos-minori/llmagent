# Require: Clarify MCP startup validation responsibilities and severity model

## Priority

High

## Target files

- `agent/startup.py`
- `agent/repl_health.py`
- `agent/services/mcp_tool_discovery.py`
- `agent/shared/health_models.py`

## Background

The startup pipeline runs multiple checks, including:

- Security audit
- Embedding dimension validation
- Service readiness
- MCP tool discovery
- Routing drift checks
- Routing safety tier checks
- RAG consistency checks

Several of these touch MCP behavior, but they represent different validation layers.

## Problem

Startup validation output can be difficult to interpret because multiple checks may appear related to MCP availability or tool readiness.

Examples:

- `check_readiness()` sounds broad, but it primarily checks LLM and embedding service readiness.
- `MCP tool discovery` validates `/v1/tools` and builds `RuntimeToolRegistry`.
- `routing_drift` compares configuration/static expectations against discovered tools.
- `routing_safety_tiers` checks safety tier declarations.
- Security audit checks auth, sandbox, and allowlist posture.

Without clear separation, operators cannot easily determine whether a startup problem is caused by LLM/Embed health, MCP discovery, metadata quality, routing drift, or security configuration.

## Reason for change

Make startup validation results actionable by separating responsibilities and documenting severity rules.

## Implementation intent

### Define startup check responsibilities

Document the responsibility of each startup check.

Recommended definitions:

- `LLM/Embed readiness`
  - Checks LLM and embedding service availability.
  - Does not represent MCP tool readiness.

- `MCP tool discovery / registry build`
  - Fetches `/v1/tools`.
  - Validates MCP tool entries.
  - Builds `RuntimeToolRegistry`.

- `MCP routing drift`
  - Compares configured/static expectations with live discovery results.

- `MCP safety tier validation`
  - Checks whether tools have appropriate safety tier metadata or configuration.

- `Security audit`
  - Checks auth token, sandbox, allowlist, and production hardening.

### Improve startup summary labels

Use clearer labels in startup output.

Suggested label changes:

- `Service readiness` -> `LLM/Embed readiness`
- `Tool discovery` -> `MCP tool discovery / registry build`
- `Routing drift` -> `MCP routing drift`
- `Routing safety tiers` -> `MCP safety tier validation`

### Define severity behavior

Document severity rules for:

- local mode
- production mode
- `tool_definitions_strict=true`
- routing drift strict mode

Recommended rules:

- Duplicate tool names are always fatal.
- Required MCP metadata violations are fatal in production or strict mode.
- Missing optional metadata may be warning-only in local mode.
- Security hardening violations are fatal in production.
- Local mode may continue with warnings when affected tools are hidden or unavailable.

### Reduce duplicate reporting

If the same MCP issue appears in multiple startup checks, make sure each message adds distinct information.

Avoid reporting the same root cause under multiple labels without clarification.

## Acceptance criteria

- [ ] Startup validation responsibilities are documented.
- [ ] `check_readiness()` is clearly identified as LLM/Embed readiness, not full MCP readiness.
- [ ] MCP tool discovery and registry build are clearly identified.
- [ ] Routing drift and safety tier checks are documented as distinct validation layers.
- [ ] Startup summary labels are clear and operator-friendly.
- [ ] Production/local/strict severity behavior is documented.
- [ ] Duplicate or overlapping startup messages are reduced or clarified.

## Tests

- Add a test confirming startup output correctly identifies LLM/Embed readiness vs MCP readiness.
- Add a test confirming startup labels match the new naming convention.
- Add a test confirming severity rules differ between local and production modes.
- Add a test confirming duplicate MCP issues are not reported redundantly.
