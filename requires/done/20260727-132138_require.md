# Fix disabled subprocess-terminate fallback in StartupOrchestrator startup failure path

## Priority

High

## Target Files

- `scripts/agent/startup.py:62-89` — `StartupOrchestrator.run()` discards the return value of `_start_servers()` and never populates `self._spawned_subprocesses`
- `scripts/agent/startup.py:128-167` — `_start_servers()` correctly accumulates spawned processes in a local `spawned` list but the caller ignores it
- `scripts/agent/repl.py:736-751` — `AgentREPL.run()` relies on `_spawned_subprocesses` (both the success-path return value and the exception-path instance attribute) to terminate orphaned subprocesses; this fallback is currently a no-op because the list is always empty

## Background

`StartupOrchestrator` spawns MCP HTTP subprocess servers during agent startup
(`_start_servers()`). If a later startup step fails, the code is designed to clean up any
already-spawned subprocesses through two independent mechanisms:

1. `lifecycle.shutdown_all()`, which tracks HTTP subprocesses internally via
   `_ServerLifecycleRouter._http_procs`.
2. A caller-side fallback in `repl.py` that directly calls `proc.terminate()` on every
   process in `_spawned_subprocesses` (checking both the return value from `run()` and the
   `startup._spawned_subprocesses` instance attribute), intended to catch cases where
   mechanism (1) itself fails.

## Problem

Mechanism (2) is permanently disabled:

- `self._spawned_subprocesses: list[subprocess.Popen] = []` is initialized in `run()`
  (`scripts/agent/startup.py:66`) but is never appended to anywhere in the codebase
  (verified via `grep -n "_spawned_subprocesses" -r scripts/agent/startup.py
  scripts/agent/repl.py` — only the declaration and read sites appear, no `.append()`).
- `_start_servers()` builds a correct local `spawned` list and returns it
  (`scripts/agent/startup.py:128-167`), but `run()` calls `await
  self._start_servers()` without capturing the return value (line 68), so the list is
  discarded immediately.
- On the success path, `run()` unconditionally returns `[]` as the third tuple element
  (`scripts/agent/startup.py:89`, `return self._cmds, self._orchestrator, []`), regardless
  of how many subprocesses were actually spawned.
- Consequently, in `repl.py`, `_spawned_subprocesses` (success path) and
  `startup._spawned_subprocesses` (exception path) are always empty, so the `for proc in
  all_procs: ... proc.terminate()` loop at `scripts/agent/repl.py:749-751` never terminates
  anything.
- The only functioning cleanup path today is `lifecycle.shutdown_all()`
  (`scripts/agent/startup.py:74-84`). If that call raises, the exception is only logged
  (`scripts/agent/startup.py:78-82`) and not re-raised, and there is no other mechanism to
  stop the orphaned subprocesses — the intended defense-in-depth fallback is dead code.

## Reason for Change

This is a resource-leak / process-orphaning defect. If `lifecycle.shutdown_all()` fails for
any reason during a startup rollback (e.g. an exception while iterating its internal
subprocess dict, a bug in its own shutdown logic, or an unexpected error), the previously
spawned MCP HTTP subprocess servers will keep running as orphans with no supervising
process, since the designed fallback path is inert. This is worse in production security
profiles (`SecurityProfile.PRODUCTION`), where subprocess startup failures are treated as
fatal and trigger the rollback path most often. Fixing this restores the intended
defense-in-depth guarantee at effectively zero cost, since the plumbing already exists —
only the wiring is missing.

## Implementation Intent

Make `_spawned_subprocesses` actually reflect the processes spawned during the current
`run()` call, in both the success and exception paths, so the `repl.py` fallback loop can
do real work when needed:

- Capture the return value of `_start_servers()` and store it in
  `self._spawned_subprocesses` immediately, so it is populated before any subsequent
  startup step (health check, service check, approval recovery, prompt setup) can fail.
- Return the actual spawned-process list from `run()` on the success path instead of a
  hardcoded `[]`, so callers see accurate data on both success and failure.
- Do not change the behavior of `lifecycle.shutdown_all()` itself, and do not change which
  processes get spawned — this is strictly a bug fix to the tracking/propagation of already
  correct data.

## Implementation Instructions

1. In `scripts/agent/startup.py`, in `StartupOrchestrator.run()`, change line 68 from
   `await self._start_servers()` to capture and store the result, e.g.:
   `self._spawned_subprocesses = await self._start_servers()`
   (keep the existing `self._spawned_subprocesses: list[subprocess.Popen] = []`
   initialization on line 66 as the pre-call default, in case `_start_servers()` itself
   raises before returning).
2. In the same method, change the success-path return statement (currently
   `return self._cmds, self._orchestrator, []  # empty list on success` at line 89) to
   return the real list: `return self._cmds, self._orchestrator,
   self._spawned_subprocesses`.
3. Verify no other caller of `StartupOrchestrator.run()` or `_start_servers()` depends on
   the previous (always-empty / discarded) behavior. `scripts/agent/repl.py:739` already
   expects a real list and needs no changes.
4. Do not modify `scripts/agent/repl.py`'s termination loop logic (lines 744-751) — it is
   already correct and will start working once the underlying data is populated.
5. Add a regression test (see Tests section) that injects a failure in
   `lifecycle.shutdown_all()` and asserts that the `repl.py`-side fallback terminates the
   spawned subprocesses.

## Acceptance Criteria

- [ ] `StartupOrchestrator._spawned_subprocesses` contains every `subprocess.Popen` object
      returned by `_start_servers()` immediately after that call, regardless of what
      happens afterward.
- [ ] `StartupOrchestrator.run()` returns the actual spawned-process list (not a hardcoded
      `[]`) on the success path.
- [ ] When a later startup step raises after subprocesses were spawned, and
      `lifecycle.shutdown_all()` also raises (or is unavailable), the `repl.py` fallback
      loop successfully calls `.terminate()` on each still-running spawned subprocess.
- [ ] Existing successful-startup behavior (server spawning, health checks, service
      recovery) is unchanged.

## Tests

- Add/extend a unit test for `StartupOrchestrator.run()` (or `_start_servers()` /
  `run()` integration) that: spawns fake subprocess(es) via a stubbed
  `lifecycle.start_http_subprocess`, forces a failure in a later step (e.g.
  `_verify_mcp_health`), forces `lifecycle.shutdown_all()` to raise, and asserts that
  `run()`'s exception path leaves `self._spawned_subprocesses` populated with the fake
  processes (not empty).
- Add a test around `scripts/agent/repl.py`'s startup call site (or an equivalent
  integration test) that verifies, given the above failure scenario, `proc.terminate()` is
  actually invoked on each spawned fake process by the `finally` block's fallback loop.
- Add/confirm a success-path test asserting `run()`'s third return value equals the list of
  processes actually spawned by `_start_servers()` (not an empty list) when startup
  succeeds.
