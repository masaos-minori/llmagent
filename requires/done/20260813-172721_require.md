# Extract shared console-processor-attach helper in otel_tracer.py without changing log wording

## Priority
Low

## Target files
- `scripts/shared/otel_tracer.py` (`_attach_console_exporter`, `_attach_otlp_exporter`)
- `tests/shared/test_otel_tracer.py`

## Background
`scripts/shared/otel_tracer.py` builds a private OpenTelemetry `TracerProvider` and attaches
either a `ConsoleSpanExporter`-backed processor or an OTLP-backed processor depending on
whether `otlp_endpoint` is set and whether the OTLP exporter package is importable.

Verified against current source (2026-08-13): both `_attach_console_exporter` (lines 100-104)
and the OTLP-unavailable fallback branch inside `_attach_otlp_exporter` (lines 107-115) contain
the same two-line pattern:

```python
processor = _ConsoleProcessor()
provider.add_span_processor(processor)
```

immediately followed by a log call — but the log call differs at each site:
- `_attach_console_exporter`: `logger.info("OTel tracer configured: ConsoleSpanExporter service=%s", service_name)`
- `_attach_otlp_exporter` fallback: `logger.warning("opentelemetry-exporter-otlp not installed; falling back to ConsoleSpanExporter")`

`tests/shared/test_otel_tracer.py` was checked for existing characterization coverage of these
two log calls. It asserts the warning texts for the two "dependency not installed" fallback
paths (`test_build_tracer_falls_back_to_noop_when_sdk_unavailable`,
`test_falls_back_to_console_when_otlp_unavailable`), but it does **not** import or directly test
`_attach_console_exporter`, and there is no assertion anywhere in the file for the exact info-level
text `"OTel tracer configured: ConsoleSpanExporter service=%s"` logged by `_attach_console_exporter`,
nor for the exact warning text logged inside `_attach_otlp_exporter`'s fallback branch
(`"opentelemetry-exporter-otlp not installed; falling back to ConsoleSpanExporter"`) — the existing
test only checks that a warning was logged and `caplog.text` contains a substring, not that this
specific call site's wording is locked as a characterization test tied to the refactor described
below. The gap noted in the source issue therefore still applies.

## Problem
The "create `_ConsoleProcessor`, call `add_span_processor`" pattern is duplicated verbatim across
two call sites with no shared helper, and there is no characterization test that pins the exact
log text/level at either site. This makes it unsafe to extract a shared helper later: doing so
naively would either duplicate the divergent log call inside the helper (defeating the purpose of
extraction) or require parameterizing the log message/level, which risks silently changing visible
log output if done without a locking test first.

## Reason for change
Reducing duplication is desirable, but only if it is provably behavior-preserving. Without a
characterization test asserting the exact log text and level at both call sites, a future refactor
of this duplication could silently change operator-visible log output (message wording or level),
which is a regression risk in a module used for tracing/observability configuration.

## Implementation intent
1. First, add characterization tests that lock the exact current log text and level produced by
   `_attach_console_exporter` and by the fallback branch inside `_attach_otlp_exporter`, using
   `caplog`. These tests must fail if either log message's text or level changes.
2. Only after the characterization tests are in place and passing, extract a shared private
   helper (e.g. `_attach_console_processor_with_log(provider, level, message, *args)` or similar)
   that performs the `_ConsoleProcessor()` + `add_span_processor()` steps and the log call, with the
   log level and full message text passed in as explicit arguments from each call site — not
   inferred or hardcoded inside the helper. This keeps the byte-for-byte wording and level at each
   site intact while removing the structural duplication.
3. Do not change the fallback decision logic (when console vs. OTLP is used, or when OTLP
   fallback to console happens) — only the shared code structure for attaching a console
   processor and logging that fact.

## Implementation instructions
- In `scripts/shared/otel_tracer.py`:
  - Add a private helper function that takes the `provider`, a `logging` level (or a bound
    `logger.info` / `logger.warning` callable), and the message template plus its format
    arguments, and performs: construct `_ConsoleProcessor()`, call
    `provider.add_span_processor(processor)`, then perform the log call with the exact level and
    message/args passed in.
  - Update `_attach_console_exporter` to call this helper, passing `logging.INFO` (or
    `logger.info`) and the exact existing message `"OTel tracer configured: ConsoleSpanExporter service=%s"`
    with `service_name` as the format argument.
  - Update the fallback branch inside `_attach_otlp_exporter` to call this helper, passing
    `logging.WARNING` (or `logger.warning`) and the exact existing message
    `"opentelemetry-exporter-otlp not installed; falling back to ConsoleSpanExporter"` (no format
    arguments).
  - Preserve the current return behavior of both functions (both currently return `None`
    implicitly).
- In `tests/shared/test_otel_tracer.py`:
  - Add a test that imports/calls `_attach_console_exporter` directly against a `_FakeProvider`
    (already defined in the file) and asserts, via `caplog.at_level(logging.INFO, logger="shared.otel_tracer")`,
    that the log text is exactly `"OTel tracer configured: ConsoleSpanExporter service=svc"` (or
    equivalent exact-match assertion, not just a substring `in` check if feasible) and that the
    provider received one `_ConsoleProcessor` instance.
  - Add or extend a test for `_attach_otlp_exporter`'s fallback branch asserting the exact warning
    text `"opentelemetry-exporter-otlp not installed; falling back to ConsoleSpanExporter"` (this
    is close to what `test_falls_back_to_console_when_otlp_unavailable` already checks via
    substring — tighten it to an exact match, or add a companion exact-match assertion, so the
    refactor is provably behavior-preserving).
  - Run these characterization tests before making any production-code change, confirm they pass
    against current (pre-refactor) behavior, then perform the extraction and re-run the full suite
    to confirm the same assertions still pass unchanged.

## Acceptance criteria
- Log message text and level at both call sites (`_attach_console_exporter`'s info log and
  `_attach_otlp_exporter`'s fallback warning log) remain byte-identical to current behavior after
  the refactor.
- No change to which processor/exporter is attached under which condition (console vs. OTLP vs.
  OTLP-unavailable-fallback-to-console).
- The duplicated "create `_ConsoleProcessor`, add_span_processor" code is expressed through a
  single shared helper called from both sites.
- `tests/shared/test_otel_tracer.py` contains characterization tests that would fail if the log
  text or level at either site changed.

## Tests
- Run the full `tests/shared/test_otel_tracer.py` suite before and after the change; all existing
  tests must continue to pass unchanged.
- New/updated tests must assert exact log text (not just substring containment where feasible) and
  log level via `caplog` for both call sites.
- No other test files are expected to require changes for this refactor.
