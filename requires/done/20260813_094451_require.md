# Make RAG consistency diagnostics complete and non-silent

## Priority
Medium

## Target files
- `scripts/db/rag_consistency.py`
- `scripts/db/models.py`
- Consistency tests

## Background
Current RAG consistency diagnostics rely on comparing total counts between FTS (Full Text Search) tables and the `chunks` table. This approach fails to detect individual row mismatches if the errors cancel each other out (e.g., one missing FTS row and one orphan FTS row). Additionally, URL-level diagnostics use broad exception handling that silences errors, potentially masking underlying issues.

## Problem
1. Aggregate count subtraction doesn't detect specific row-level discrepancies (gaps vs orphans).
2. Silent error handling in URL-level diagnostics can lead to false "clean" reports.
3. Difficulties in identifying the exact cause of inconsistencies due to lack of detailed reporting.

## Reason for change
To provide more reliable and actionable RAG consistency reports by detecting specific row mismatches and ensuring diagnostic failures are explicitly reported rather than silenced.

## Implementation intent
Refactor consistency diagnostics to use set-based comparisons (row-ID difference) to identify specific missing or orphaned records. Improve error handling in diagnostic queries to prevent silent failures and ensure that any unrun check prevents a "clean" status.

## Implementation instructions
1. Refactor `rag_consistency.py` to use set difference operations on Row IDs to identify:
   - Chunks missing from FTS.
   - FTS rows without corresponding chunks.
2. Implement collection of affected identifiers (e.g., chunk IDs) from these set difference results.
3. Replace broad `except Exception: pass` blocks in URL-level diagnostic queries with specific, scoped database exception handling.
4. Add a mechanism to record diagnostic errors (either in the report or via a new field in `models.py`) so that a failed check prevents a "clean" status.
5. Update diagnostic reporting to log the failing query category and exception details.
6. Ensure orphan vector diagnostics use chunk IDs as the primary identifier rather than attempting unreliable URL reconstruction.

## Acceptance criteria
- Discrepancies like one missing FTS row and one orphan FTS row are correctly identified even if totals match.
- Failed URL-level diagnostic checks are explicitly visible in the report and prevent a "clean" status.
- Diagnostics remain strictly read-only.
- Orphan vector diagnostics accurately report problematic IDs without claiming unavailable URLs.

## Tests
- Test case: equal-count gap/orphan cancellation (ensure they are detected separately).
- Test case: URL-level SQL failure (ensure it's reported).
- Test case: orphan vector without a matching chunk.
- Verify normal consistent database returns a clean report.
