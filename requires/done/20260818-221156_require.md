## Background
Security controls for this system already exist and are individually documented, but they are scattered across the Agent, MCP, RAG, deployment, and operations documentation sets. Verified evidence of fragmentation:

- MCP allowlists, auth profiles/sandboxing, and fail-open/fail-closed/risk-tier behavior live in a 5-part series: `docs/04_mcp_05_01` through `04_mcp_05_05`. `docs/04_mcp_00_document-guide.md` itself labels this series "セキュリティモデル(5分割)" ("security model, split into 5 parts") — an explicit, standing acknowledgment that even the MCP-only security model is fragmented.
- Path/repo jailing and command allowlists for file-write/file-delete/shell tools are documented in `04_mcp_04_02_file-write-file-delete-shell.md`, separately from the mdq-specific path-traversal/symlink-traversal coverage in `04_mcp_04_04_mdq.md` and `04_mcp_05_05_mdq-enforcement-and-lockdown.md`. Explicit path-traversal/symlink-traversal language currently exists only for the mdq tool, not uniformly for file-write, file-delete, git, github, or shell tools.
- Tool approval gating (agent-side) is documented separately in `05_agent_06_01`, `05_agent_06_02`, and `05_agent_08_04_configuration-mcp-approval-obs.md`.
- Production fail-closed enforcement (`security_profile=production`, `audit_security_defaults()`) is documented in `04_mcp_05_02_auth-profiles-and-sandboxing.md`, `04_mcp_06_16_pre-production-fail-open-checklist.md`, and `04_mcp_06_17_local-to-production-auth-migration.md`.
- Audit logging is documented in `04_mcp_02_03_audit-logging-and-errors.md`, `04_mcp_06_07_reading-audit-logs.md`, and `05_agent_10_02_operations-and-observability-audit-and-otel.md`.
- RAG content sanitization (prompt-injection defense) is documented in `03_rag_03_05_query_pipeline-augment-stages.md` (`sanitize_document()`) and `03_rag_04_02_dto-models_result.md` (`was_sanitized`, `patterns_detected`).
- Overall fail-open/fail-closed behavior is summarized separately again in `05_failure_modes_and_operational_readiness.md`.

No file in `docs/` or `rules/` is scoped as a cross-cutting security architecture, trust-boundary, or threat-model document. `docs/00_index.md` has no such entry, and no existing doc covers Agent, MCP, RAG, deployment, and operations security together in one place.

## Problem
There is no single system-wide security architecture document defining trust boundaries, protected assets, the threat model, authentication/authorization requirements per externally reachable API, secret lifecycle (provisioning/storage/rotation/revocation), log redaction rules, audit retention, prompt-injection responsibility boundaries, or local-vs-production behavioral differences.

There is also no single common policy document for high-risk MCP tools (file-write, file-delete, shell, git, github, CI/CD, database maintenance) that consolidates allowed paths/repos, command allowlists, argument validation, path-traversal prevention, symlink-traversal prevention, approval requirements mapped to risk tiers, audit fields, production restrictions, and failure behavior. The closest existing artifact — the MCP `04_mcp_05_0x` series — is itself explicitly split into 5 files, excludes Agent- and RAG-side controls, and only names path-traversal/symlink-traversal protection for the mdq tool, not uniformly across all high-risk tools.

This fragmentation creates a real risk: an implementation AI or engineer changing one component's security control (e.g., a new MCP tool's allowlist, or a new approval gate) may not recognize its impact on the system-wide security posture, because no document states the full model in one place, and no single policy is authoritative for what all high-risk tools must satisfy.

## Reason for change
The system already performs high-impact actions (file modification/deletion, shell execution, git/GitHub operations, CI/CD execution, database maintenance, workflow approval/execution) and is actively growing (recent MCP/RAG/eventbus refactors per the `git log`). Without one authoritative trust-and-authorization model and one common high-risk-tool policy, inconsistent tool-level controls can permit path traversal, symlink traversal, command-allowlist bypass, unauthorized repository access, or execution without required approval as new tools/servers are added. Consolidating now — while the underlying controls already largely exist and are individually correct — is lower risk than doing so after further fragmentation accumulates.

## Implementation intent
Produce a small set of new, cross-cutting documentation artifacts (not a code change) that:
1. Define one system security architecture: trust boundaries (with a diagram), protected assets, threat model, per-API authentication/authorization requirements, secret lifecycle, log redaction rules, audit retention, prompt-injection responsibility boundaries, and explicit local-vs-production / fail-open-vs-fail-closed behavior — synthesizing what is already true today from the scattered sources listed above, not inventing new behavior.
2. Define one common policy for high-risk MCP tools (file-write, file-delete, shell, git, github, CI/CD, DB maintenance): allowed paths/repos, command allowlists, argument validation, path-traversal and symlink-traversal prevention (generalizing the mdq-specific pattern to all applicable tools), approval requirements mapped to risk tiers, audit fields, production restrictions, and failure behavior — with tool-specific exceptions documented separately (not merged into the common policy body).
3. Update the existing scattered docs (the 5-part MCP series, agent approval docs, audit docs, RAG sanitization docs, failure-modes doc) to reference the new consolidated documents as the canonical source, rather than duplicating the policy inline. Do not delete or merge the existing detailed docs — they remain the implementation-level detail; the new docs are the cross-cutting index/policy layer above them.
4. Add the new document(s) to `docs/00_index.md`'s task-to-document mapping so future tasks touching security-relevant tools are routed to read them.

This is a documentation-consolidation effort. It should not change any runtime behavior, code, or existing detailed docs' technical content — only add new cross-cutting documents and add cross-references from existing docs to them.
