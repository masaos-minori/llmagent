## Background
The `05_agent_*.md` document set mixes design/operational judgment with content that is mechanically derivable from code. A review (`memo-doc-agent-review.md`) identified what to keep vs. remove per chapter.

## Problem
The memory chapter carries full dataclass/enum/store-API lists, retriever/ingestion/extraction function lists, and scoring-formula detail that belongs in code.

## Reason for change
This chapter should serve as the canonical source for memory-layer design intent only. Dataclass/enum/store-API lists and scoring formulas increase staleness risk without adding decision value.

## Implementation intent
Keep this chapter as the canonical source for memory-layer design intent. Remove dataclass/enum/store-API lists, retriever/ingestion/extraction function lists, per-source-type mechanical field tables, and scoring-formula detail. Delegate the formula/constants to code.

1. Read all eight files in full.
2. Identify sections containing: memory dataclass/enum/store-API lists, retriever/ingestion/extraction function lists, per-source-type mechanical field tables, scoring-formula detail and constant tables.
3. Remove or compress those sections while preserving: why the memory layer is optional, the operational meaning of hybrid / fts-only / degraded / disabled modes, the relationship between JSONL and SQLite storage, the fallback policy when embedding is unavailable, memory injection's effect on answer quality and associated cautions, the memory-vs-RAG responsibility boundary.
