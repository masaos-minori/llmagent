# Fix: orphaned MCP subprocess when `_start_servers()` fails mid-loop in `StartupOrchestrator.run()`

## Priority
Critical

## Target files
- `scripts/agent/startup.py` (`StartupOrchestrator.run()`, lines 67-94; `_start_servers()`, lines 133-204)
- `scripts/agent/repl.py` (`AgentREPL.run()` cleanup logic, lines 829-842)
- `scripts/agent/factory.py` (`_ServerLifecycleRouter`, line 52; `shutdown_all()`, lines 167-172 — reference only)
- `scripts/agent/http_lifecycle.py` (`HttpServerLifecycleManager`, line 53; `_http_procs`, line 76; `shutdown_all()`, lines 495-534 — reference only)

## Background
`StartupOrchestrator.run()` (`scripts/agent/startup.py:67-94`) starts configured MCP servers and,
on any failure during setup, is intended to roll back already-started subprocesses via
`lifecycle.shutdown_all()`. The rollback is currently gated by a local flag,
`_servers_started`, which is set `True` only after `_start_servers()` returns successfully:

```python
async def run(self) -> tuple[CommandRegistry, Orchestrator, list[subprocess.Popen]]:
    self._initialize()
    _servers_started = False
    self._spawned_subprocesses: list[subprocess.Popen] = []
    try:
        self._spawned_subprocesses = await self._start_servers()
        _servers_started = True
        await self._verify_mcp_health()
        ...
    except Exception as setup_err:
        if _servers_started:
            try:
                await self._ctx.services_required.lifecycle.shutdown_all()
            except Exception as shutdown_err:
                logger.error(...)
        raise setup_err
```

`_start_servers()` (`scripts/agent/startup.py:133-204`) starts multiple MCP servers one at a time
in a loop, accumulating successfully-started `subprocess.Popen` objects into a purely local list
(`spawned`) that is only returned at line 204 if the whole loop completes. If the 2nd or later
server fails to start — in particular under `SecurityProfile.PRODUCTION`, where a retry failure
raises `RuntimeError` immediately (`scripts/agent/startup.py:189-195`):

```python
except (OSError, RuntimeError) as retry_err:
    if ctx.cfg.mcp.security_profile == SecurityProfile.PRODUCTION:
        msg = f"{OutputTag.FATAL} MCP subprocess {key!r} failed to start after retry: {retry_err}"
        masked_msg = _mask_secrets(msg)
        logger.error(masked_msg)
        raise RuntimeError(masked_msg) from retry_err
```

— then `_start_servers()` never reaches its `return spawned` statement, and the exception
propagates out with the local `spawned` list (containing the already-started, earlier server's
`Popen`) discarded.

Meanwhile, the earlier server's subprocess is *not* lost from the system's own bookkeeping: it is
already registered in `scripts/agent/factory.py`'s `_ServerLifecycleRouter` (line 52), which
delegates to `HttpServerLifecycleManager` (`scripts/agent/http_lifecycle.py:53`), whose
`_http_procs` dict (`http_lifecycle.py:76`) is populated as soon as `start()` succeeds
(`http_lifecycle.py:409`) — independent of whether `_start_servers()` itself later raises.

The caller, `scripts/agent/repl.py`'s `AgentREPL.run()` (method starts at line 743; relevant
try/except at lines 829-842), does not rescue this either:

```python
startup = StartupOrchestrator(self._ctx, self._view)
_spawned_subprocesses: list[subprocess.Popen] = []
try:
    self._cmds, self._orchestrator, _spawned_subprocesses = await startup.run()
except Exception as e:
    self._view.write_fatal(f"Startup failed: {e}")
    # Terminate any subprocesses started during partial (failed) startup.
    all_procs = _spawned_subprocesses
    if hasattr(startup, "_spawned_subprocesses"):
        all_procs = list(all_procs) + list(startup._spawned_subprocesses)
    for proc in all_procs:
        if proc.poll() is None:
            proc.terminate()
    raise
```

`repl.py` does attempt a fallback via `startup._spawned_subprocesses` (an instance attribute
initialized to `[]` at `startup.py:71`, before `_start_servers()` is called, and only overwritten
at `startup.py:73` if that call returns without raising). In the failure mode described above, the
assignment at line 73 never completes, so `startup._spawned_subprocesses` remains `[]` — identical
to the local `_spawned_subprocesses` in `repl.py`. `all_procs` is therefore empty, and
`proc.terminate()` is never called on the earlier server's process.

## Problem
When `_start_servers()` raises partway through starting multiple configured MCP servers (e.g. the
2nd server fails a retry under `SecurityProfile.PRODUCTION`), the already-started 1st server's
subprocess is left running with no code path that terminates it:
- `StartupOrchestrator.run()`'s except block skips `lifecycle.shutdown_all()` because
  `_servers_started` is still `False` (it is only set `True` after `_start_servers()` returns
  normally, which never happens on this path).
- `AgentREPL.run()`'s cleanup loop iterates an empty `all_procs` list, since neither
  `_spawned_subprocesses` (unassigned, because `startup.run()` raised before the tuple assignment)
  nor `startup._spawned_subprocesses` (still `[]`, because `_start_servers()` never returned) hold
  a reference to the orphaned process.

The result is an orphaned MCP subprocess that outlives the failed startup attempt, with no
supervising code aware of its existence.

## Reason for change
This is a resource-lifecycle correctness bug with operational impact: every partial MCP startup
failure involving 2+ configured servers leaks a subprocess, which accumulates over repeated
failed/retried startups (e.g. during deployment troubleshooting or flaky server configs) and can
exhaust process/port/resource limits. `HttpServerLifecycleManager.shutdown_all()` is already
designed to safely no-op on an empty `_http_procs` dict, and safely handles being called more than
once, so fixing the gating condition in `StartupOrchestrator.run()` carries low risk of
regressions or double-shutdown side effects.

## Implementation intent
Change the rollback trigger in `StartupOrchestrator.run()` from "did `_start_servers()` return
normally" to "was an attempt made to start at least one MCP subprocess" (or equivalently, make the
`except` block call `lifecycle.shutdown_all()` unconditionally, since `lifecycle` is already fully
constructed by `_initialize()` before `_start_servers()` is ever invoked, and `shutdown_all()` is
safe to call even when zero subprocesses were started). Additionally, where practical, make
`_start_servers()` surface the list of subprocesses it managed to start before raising, so callers
retain an accurate record even independent of the `lifecycle` object's own bookkeeping.

## Implementation instructions
1. In `scripts/agent/startup.py`, `StartupOrchestrator.run()`: remove the gating of
   `lifecycle.shutdown_all()` on the `_servers_started` flag being `True` only after
   `_start_servers()` returns. Either:
   - (a) set `_servers_started = True` (or equivalent) before calling `_start_servers()`, since
     `lifecycle` is already initialized by `_initialize()` at that point and is safe to shut down
     unconditionally on any subsequent exception; or
   - (b) remove the flag/conditional and call `lifecycle.shutdown_all()` unconditionally inside the
     `except Exception as setup_err:` block.
2. In `scripts/agent/startup.py`, `_start_servers()` (lines 133-204): ensure the list of
   subprocesses started so far is preserved and accessible to the caller even when the function
   raises mid-loop — for example, update `self._spawned_subprocesses` (or an equivalent
   caller-visible attribute) incrementally as each subprocess is spawned, rather than only via the
   `return spawned` statement at the end of the function. This keeps `startup._spawned_subprocesses`
   accurate for `repl.py`'s fallback cleanup path even when `_start_servers()` does not return
   normally.
3. In `scripts/agent/repl.py`, `AgentREPL.run()` (lines 829-842): re-verify the existing
   `hasattr(startup, "_spawned_subprocesses")` fallback still behaves correctly once step 2 makes
   that attribute populated incrementally; adjust only if the incremental-update approach in step 2
   changes the attribute's shape or timing. Do not perform unrelated refactoring of this method.
4. Confirm `HttpServerLifecycleManager.shutdown_all()` (`scripts/agent/http_lifecycle.py:495-534`)
   remains safe to call when `_http_procs` is empty or when some processes are already terminated,
   and safe to call more than once (relevant if both the new unconditional `shutdown_all()` call in
   `run()` and any pre-existing call path could both fire) — do not modify
   `http_lifecycle.py`'s own start/stop logic; verification only, per the issue's stated out-of-scope
   note.
5. Do not modify `scripts/agent/factory.py`'s `_ServerLifecycleRouter` or
   `scripts/agent/http_lifecycle.py`'s subprocess start/stop logic — those are out of scope.
6. Keep the change scoped to `StartupOrchestrator.run()`, `_start_servers()`, and their direct
   caller relationship in `repl.py`; do not perform unrelated refactoring.

## Acceptance criteria
- With 2 or more MCP servers configured, when the 2nd (or later) server fails to start (including
  the `SecurityProfile.PRODUCTION` retry-failure path that raises `RuntimeError` immediately), the
  1st server's already-started subprocess is reliably terminated (verified via
  `lifecycle.shutdown_all()` being invoked, or via the process no longer running).
- This holds for both `SecurityProfile.PRODUCTION` and non-production security profiles.
- `lifecycle.shutdown_all()` being called unconditionally (including when zero subprocesses were
  started, or when it may be invoked more than once across `run()` and `repl.py`'s fallback) causes
  no errors or unhandled exceptions.
- No unrelated behavior of `StartupOrchestrator`, `AgentREPL`, `_ServerLifecycleRouter`, or
  `HttpServerLifecycleManager` changes.

## Tests
Add to `tests/agent/test_startup.py` (or the equivalent existing test file covering

  failure path), verifying that the 1st server's `Popen`-equivalent mock receives a `terminate()`

- Cover both `SecurityProfile.PRODUCTION` and a non-production profile in this scenario.
- Optionally, a regression test confirming `lifecycle.shutdown_all()` is a safe no-op when called
  with zero started subprocesses (startup fails before any server starts).
