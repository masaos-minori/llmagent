## Background
`requires/done/20260818-224947_require.md` identified a contradiction: the doc says
`tool_definitions` findings are never FATAL (always downgraded to WARNING), while
`scripts/agent/services/mcp_tool_discovery.py` implements a unified severity scheme
(`is_fatal = strict or security_profile == PRODUCTION`) that applies to
`tool_definitions` findings the same as drift and malformed-capabilities findings. That
requirement explicitly framed this as a decision point (Option A: doc is right, fix the
code; Option B: code is right, fix the doc) and permitted inferring intent from in-repo
design history when a stakeholder decision is not obtainable.

`plans/20260819-184236_plan.md` (Design section) selected Option B based on two pieces of
in-repo evidence in `scripts/agent/services/mcp_tool_discovery.py`: the module docstring
(lines 33-35, "Unified severity scheme (drift, tool-definitions, malformed-capabilities)")
and the `_check_tool_definitions_finding()` docstring (lines 389-395, framing the current
behavior as a deliberate fix — "this resolves the old quirk where strict-mode drift
detection was silently downgraded to 'skipped'"). No operations/product-owner sign-off was
sought in that workflow cycle. `issues/done/20260819-184236_risks.md` recorded this as a
non-blocking traceability risk and suggested an optional confirmation step before or during
implementation.

## Problem
The plan that will drive the next implementation phase commits to Option B (doc changed to
match code) purely from inferred design intent, without an explicit operations/product-owner
statement that FATAL-on-production for `tool_definitions` mismatches is the desired
operational policy. If that inference is wrong, implementing Option B would formally codify,
in documentation, a startup-abort behavior that silently reverses a previously documented
"never blocks startup" guarantee — a behavior operators may not expect. `rules/coding.md`'s
"Explicit sign-off gates" section requires that when a later sub-task is gated behind
explicit sign-off before implementation, the required sign-off channel must be documented in
the follow-up issue/plan entry; this has not yet been done for `plans/20260819-184236_plan.md`.

## Reason for change
Adding an explicit, low-cost confirmation checkpoint before implementing the doc-and-test
change avoids two asymmetric failure modes: (a) skipping confirmation and later discovering
Option A was actually intended, which would require reverting a merged doc change and
re-running the test-writing work under Option A instead; versus (b) a short delay to get a
one-line confirmation from whoever owns the operational policy. Given the change alters a
previously documented "always continue" guarantee into a "may abort startup" behavior, the
asymmetry favors confirming first per `rules/coding.md`'s sign-off gate guidance.

## Implementation intent
Record a sign-off gate on `plans/20260819-184236_plan.md` (the preferred channel per
`rules/coding.md`) before executing that plan's Phase 1 (doc edit) and Phase 2 (test
coverage). Do not implement any source code, doc, or test change under this requirement
directly — this requirement only establishes the confirmation gate and the two
already-specified fallback paths (Option B as planned, or Option A as specified in
`requires/done/20260818-224947_require.md`'s Implementation intent section). Whichever
option is confirmed becomes the one actually implemented in the next phase.

## Implementation instructions

   section — hard-code `StartupCheckStatus.WARNING` in both branches of
