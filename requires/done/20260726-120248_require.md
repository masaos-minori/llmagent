## Background

pyright reports 29 errors across 12 files. mypy passes all checks. The discrepancy stems from pyright's stricter type narrowing and inability to resolve certain dynamic imports. Two categories emerge:

1. **True type mismatches**: FastAPI Protocol incompatibility in `attach_auth_middleware()` calls
2. **False positives**: GitPython dynamic module attribute access (`git.exc`) that pyright cannot resolve

## Problem

```bash
$ uv run pyright scripts/
29 errors, 12 files
```

Two dominant patterns:

**Pattern A — FastAPI Protocol mismatch:**
```python
def attach_auth_middleware(app: _FastAPIApp, token: str) -> None:
    ...

attach_auth_middleware(app, ...)  # app is FastAPI, not _FastAPIApp
```

`_FastAPIApp.middleware` expects `(type_: str) -> ...` but FastAPI defines it as `(middleware_type: str) -> ...`. Parameter name mismatch causes pyright rejection.

**Pattern B — GitPython dynamic attribute:**
```python
except git.exc.InvalidGitRepositoryError:  # pyright: "exc" is not a known attribute
except git.exc.GitError:                  # pyright: "exc" is not a known attribute
```

`git.exc` is dynamically created by GitPython at import time; pyright cannot resolve it statically.

## Reason for Change

Reduce pyright error count to improve developer experience and CI signal quality. Even though CI gates on mypy only, pyright errors indicate real type safety gaps that could cause issues if CI is ever switched.

## Implementation Intent

Classify each of the 29 errors into one of three categories:

1. **True mismatch** — Fix by adding appropriate casts or updating type annotations
2. **False positive** — Add `# type: ignore[rule]` comments with justification
3. **Stubs needed** — Add or update type stubs for third-party libraries

Specific actions identified so far:
- Add `cast(_FastAPIApp, app)` before `attach_auth_middleware()` calls (same pattern used in mdq_server.py:368)
- Add `# type: ignore[attr-defined]` for `git.exc` accesses in git_helper.py
