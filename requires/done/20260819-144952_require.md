# Enforce URL-group atomicity and strict RAG database constraints

## Priority

Medium

## Target files

- `scripts/rag/ingestion/ingester.py`
- `scripts/db/schema_sql.py`
- `tests/db/test_create_schema.py`
- `tests/db/test_db_maintenance.py`

## Background

Source issue `issues/20260819_04_issue.md` ("Enforce URL-group atomicity and strict RAG
database constraints") describes two related gaps in the RAG ingestion pipeline: (1) the
ingester does not validate that all chunks in a URL group describe the same document
version before mutating the database, and swallows constraint violations instead of
rolling back; (2) the RAG DDL still provides defaults for columns the application layer
is expected to always supply explicitly, which lets other write paths bypass the strict
contract at the database boundary.

Verified directly against current source (`scripts/rag/ingestion/ingester.py`,
`scripts/db/schema_sql.py`):

- `_insert_chunks_batch()` (lines 516-548) wraps the per-chunk INSERT into `chunks`/
  `chunks_vec` (lines 527-545) in:
  ```python
  except sqlite3.IntegrityError:
      pass
  ```
  (lines 546-547). The failure is neither re-raised, rolled back, nor reflected in the
  returned `inserted` count adjustment — the loop simply continues to the next chunk.
  There is no transaction/rollback logic inside this function itself; commit is handled
  elsewhere (`_commit_url_transaction`, line 648), so a swallowed `IntegrityError` here
  can produce a partially-inserted, silently-truncated URL group.
- `ingest_url_group()` (lines 190-230) sorts `chunk_files` by filename stem (line 202,
  not by `chunk_index`) and reads only `chunk_files[0]` into `first_data` (line 203).
  Lines 212-217 then take `title`, `lang`, `etag`, `last_modified`, `fetched_at`, and
  `chunking_strategy` solely from `first_data`, with no loop that checks the remaining
  chunk files in the group agree on these values (or on `url`, `source_file`,
  `schema_version`, `artifact_type`, `created_by`, which are read per-chunk elsewhere,
  e.g. `_validate_artifact` line 378, but never cross-checked against a group baseline).
  A URL group whose files disagree on any of these fields is therefore silently
  collapsed onto the first file's values today.
- `_normalize_chunk_index()` (lines 358-366) only coerces `chunk_index` to `int`,
  defaulting to `0` on `ValueError`/`TypeError`. No duplicate-index or
  contiguous-from-zero check exists anywhere in the ingester. Today, a duplicate
  `chunk_index` within a group would only surface as the `IntegrityError` that
  `_insert_chunks_batch()` currently swallows (via the `UNIQUE(doc_id, chunk_index)`
  constraint at `schema_sql.py` line 46) — i.e. the one enforcement mechanism that
  exists is exactly the one being silently discarded.
- `_route_chunk_files()` (lines 768-824) already routes failed files to a
  `failed_dir = self._chunk_dir.parent / "failed"` (line 775), writing `.error.json`
  metadata via `_write_error_metadata()` (lines 826-851) before moving each file to
  `retry/` or `failed/` depending on the failure reason (lines 811-814). This routing
  mechanism already exists and is called from `ingest_url_group()` (lines 259/264); the
  gap is only that constraint failures inside `_insert_chunks_batch()` do not currently
  reach this routing path because they are swallowed before propagating.
- `scripts/db/schema_sql.py` (lines 27-50) currently defines:
  - `documents.fetched_at` (line 32): `TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%SZ', 'now'))`
  - `documents.chunking_strategy` (line 35): `TEXT NOT NULL DEFAULT 'text'`
  - `documents.etag` (line 33): `TEXT` (nullable, no default)
  - `documents.last_modified` (line 34): `TEXT` (nullable, no default)
  - `chunks.chunk_type` (line 44): `TEXT NOT NULL DEFAULT 'text'`
  - `chunks.source_file` (line 45): `TEXT NOT NULL DEFAULT ''`
  - `chunks.normalized_content` (line 43): `TEXT` (nullable, no default)
- `tests/db/test_create_schema.py` and `tests/db/test_db_maintenance.py` both exist and
  are the current schema/DB-maintenance test targets named in the issue's validation
  command.

All factual claims in the issue are confirmed against current source; the issue is fully
applicable and not already resolved.

This issue's own "Dependencies" section names two prerequisites, both already converted
into requirement documents:
- `requires/done/20260819-144406_require.md` ("Replace permissive RAG payload handling with
  strict crawl and chunk contracts") — establishes strict, mandatory-field crawl/chunk
  JSON contracts (`read_crawl_json()`/`read_chunk_json()`, non-defaulted `ChunkDocument`
  fields including `chunk_type`, `source_file`, `chunking_strategy`) that this
  requirement's URL-group validation logic and DDL tightening build on.
- `requires/done/20260819-144649_require.md` ("Make fetched_at mandatory end to end and remove
  timestamp compatibility behavior") — makes `fetched_at` a mandatory, non-null `str`
  through every layer including `scripts/db/schema_sql.py`, and separately calls for
  removing the `documents.fetched_at` `DEFAULT` clause as part of that end-to-end
  mandatory-field change.

This requirement is not a duplicate of either dependency: those two establish that the
*application-level* contracts (JSON readers, DTOs, store signatures) are strict and that
`fetched_at` specifically is mandatory end to end. This requirement additionally (a)
adds URL-group cross-chunk consistency validation and atomic rollback inside the
ingester — a control-flow concern neither dependency addresses — and (b) extends the
database-level no-default enforcement to `chunking_strategy`, `chunk_type`, and
`source_file` in addition to `fetched_at`, and requires `_insert_chunks_batch()` to stop
swallowing `sqlite3.IntegrityError`. Implementation of this requirement should be
sequenced after the two dependencies land, since it assumes their strict, non-defaulted
DTO/reader contracts are already in place when it adds group-level validation on top.

## Problem

- `_insert_chunks_batch()` (`ingester.py:516-548`) catches `sqlite3.IntegrityError` and
  discards it (`except sqlite3.IntegrityError: pass`, lines 546-547) instead of
  propagating it, so a duplicate `chunk_index` or other constraint violation can produce
  a partially-inserted URL group that is reported as if it succeeded.
- `ingest_url_group()` (`ingester.py:190-230`) derives all document-level metadata
  (`title`, `lang`, `etag`, `last_modified`, `fetched_at`, `chunking_strategy`, and
  implicitly `url`, `source_file`, `schema_version`, `artifact_type`, `created_by`) from
  only the first chunk file in the group (sorted by filename stem, not `chunk_index`),
  with no check that the remaining files in the group agree. A mixed-version group (e.g.
  one file re-crawled with a different `fetched_at` or `title` mixed into an otherwise
  stale group) is silently ingested as if it were a single consistent document.
- No duplicate-`chunk_index` or contiguity check exists before embedding/insertion; the
  only mechanism that would catch a duplicate index today (the `UNIQUE(doc_id,
  chunk_index)` constraint) is rendered ineffective by the swallowed
  `IntegrityError`.
- `scripts/db/schema_sql.py` still defines `DEFAULT` values for `documents.fetched_at`
  (line 32), `documents.chunking_strategy` (line 35), `chunks.chunk_type` (line 44), and
  `chunks.source_file` (line 45). Once the application layer is made strict (per the two
  dependency requirements), these DDL defaults become the only remaining way a write
  path could omit a mandatory field and have SQLite silently substitute a value instead
  of failing.

## Reason for change

Ingestion is intended to be atomic per URL: either a complete, internally-consistent
document and all of its chunks are committed, or none of it is. Silently accepting a
metadata-inconsistent group, or silently discarding a constraint violation mid-batch,
both violate that intent and can leave the database in a state that looks like a
successful ingest but is actually incomplete or self-contradictory. Once the JSON
readers, DTOs, and store signatures are strict (per the two dependency requirements),
retaining DDL-level defaults for the same mandatory fields would leave a bypass at the
database boundary that undermines the no-omission contract those changes establish —
any future or overlooked write path could still insert incomplete rows without
triggering an error. No legacy data or write path depends on these defaults, so there is
no compatibility reason to keep them, and no migration is needed since the database can
be recreated directly from the stricter DDL.

## Implementation intent

Treat each URL group as one immutable, atomic ingestion unit. Before embedding or any
database mutation, validate every chunk file in the group: metadata fields must match
across the group, and `chunk_index` values must be free of duplicates (with a documented
decision on whether contiguity-from-zero is also required). Any validation failure or
database constraint failure must cause the entire URL's transaction to roll back with no
partial commit, and the affected files must be routed to `failed/` (via the existing
`_route_chunk_files()` mechanism) with error metadata explaining the failure. Success
counters must exclude every row that was part of a rolled-back or failed group.

In parallel, tighten `scripts/db/schema_sql.py` so the schema enforces the same
no-omission contract: remove the `DEFAULT` clauses from `documents.fetched_at`,
`documents.chunking_strategy`, `chunks.chunk_type`, and `chunks.source_file`, while
keeping all four `NOT NULL` and leaving `etag`, `last_modified`, and
`normalized_content` nullable and default-free as they already are. Since no legacy data
must be preserved, recreate `rag.sqlite` from the stricter DDL rather than writing an
incremental migration.

## Acceptance criteria

- Inconsistent group metadata (any of the checked fields differing across chunk files in
  the same URL group) causes the complete URL group to fail before any database
  mutation.
- Duplicate `chunk_index` values within a group are detected and rejected before
  embedding or database insertion.
- `_insert_chunks_batch()` no longer catches `sqlite3.IntegrityError` silently; any
  database integrity error rolls back the entire URL transaction with no partial commit.
- Failed URL groups (validation or integrity failure) are routed to `failed/` via
  `_route_chunk_files()` with error metadata identifying the specific failure.
- Success/inserted counters exclude all rows from rolled-back or failed groups.
- `documents.fetched_at`, `documents.chunking_strategy`, `chunks.chunk_type`, and
  `chunks.source_file` have no `DEFAULT` clause and remain `NOT NULL`; omitting any of
  them in an INSERT causes the INSERT to fail.
- `documents.etag`, `documents.last_modified`, and `chunks.normalized_content` remain
  nullable with no default (unchanged).
- The ingester and `SQLiteDocumentStore` supply all four mandatory values explicitly on
  every INSERT/UPSERT path.
- A newly created `rag.sqlite` (recreated from the stricter DDL, no migration) passes all
  schema and ingestion tests.
- Full RAG ingestion of a valid, consistent URL group succeeds with no hidden partial
  inserts.
