# Fix inaccurate "setup_services.sh initializes the LLM services" description in docs/02_deployment-part1.md §2.3

## Priority
High

## Target files
- `docs/02_deployment-part1.md` (§2.3 "Registering and starting LLM services", around line 104)

## Background
`docs/02_deployment-part1.md` §2.3 opens with the sentence "`deploy/setup_services.sh` initializes the LLM services." This is read by operators as the authoritative description of what the deploy script does when bringing up embed-llm and agent-llm.

## Problem
The sentence is factually inaccurate:
- In `deploy/setup_services.sh`, the two LLM-related sections (currently lines 74-77 and 79-83) each only run `for svc in embed-llm agent-llm; do echo "  起動: ${svc}"; done` — this prints a message per service name but starts no actual process. No process launch, no PID capture, nothing analogous to the Event Bus block (lines 85-90), which does `python -m eventbus.app ... &` and captures `$!`.
- `config/agent.toml` shows `embed_url = "http://192.168.11.238:8081"` (line 10) and `llm_url = "http://192.168.11.197:8080"` (line 22) — separate host IP addresses, not localhost. embed-llm and agent-llm are therefore external services running on different hosts, entirely outside what `setup_services.sh` (which only runs local `curl 127.0.0.1:...` health checks) can start or manage.
- The doc's own example block (current lines 113-120) instructs the reader to run `setup_services.sh` and then curl `127.0.0.1:8081` / `127.0.0.1:8080` for health — reinforcing the false impression that these are local processes the script started, when they are actually remote services that must already be running on their own hosts.

## Reason for change
This is a confirmed implementation/documentation mismatch. A reader would reasonably conclude that running `setup_services.sh` starts the LLM services, when in fact it does not — those services must be started and managed separately on different hosts. In production, this misunderstanding could result in going live with the LLM servers never actually started, since nothing in the deploy pipeline actually starts them.

## Implementation intent
Correct the opening description of §2.3 (and the immediately following health-check example, if it perpetuates the same false impression) to accurately state:
1. What `setup_services.sh` actually does regarding "LLM services": it only echoes per-service names in a loop — it does not start embed-llm or agent-llm processes. (It does perform workflow artifact/schema pre-flight checks, and it does start the Event Bus subprocess and print MCP-server auto-start reminders — these parts are already accurately described elsewhere in the doc and should not be changed.)
2. That embed-llm and agent-llm are external services running on separate hosts, per `embed_url`/`llm_url` in `config/agent.toml`, and that starting/operating those services is outside the scope of this deployment pipeline.

Do not add or change any actual process-starting logic in `setup_services.sh` — this is documentation-only, describing current (echo-only) reality.
