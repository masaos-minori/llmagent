# Make MCP server health timeout configurable instead of hardcoded

## Priority
High

## Target files
- scripts/agent/http_lifecycle.py
- scripts/agent/services/mcp_tool_discovery.py
- scripts/agent/services/mcp_status.py
- scripts/agent/config_dataclasses.py

## Background
During adversarial review of the agent startup process, we traced the full MCP tool discovery flow through mcp_tool_discovery.py. The service fetches /v1/tools endpoints from HTTP-transport MCP servers, validates tool shape, normalizes to RuntimeTool instances, detects cross-server duplicates, and validates against static ToolRegistry for drift. However, there's no evidence of comprehensive timeout handling for edge cases where MCP servers might take longer than expected to respond.

## Problem
The current `MCPSERVER_HEALTH_TIMEOUT` constant in http_lifecycle.py is hardcoded to 5.0 seconds. This creates several issues:

1. **No configurability**: Different MCP servers may have different response time characteristics. A slow but healthy server could be incorrectly marked as unreachable.
2. **Network variability**: In production environments, network latency can vary significantly. A fixed 5-second timeout may be too aggressive for some deployments.
3. **No per-server configuration**: Some servers might need longer timeouts while others don't. The current approach treats all servers identically.
4. **Hardcoded dependency**: Both `mcp_tool_discovery.py` and `mcp_status.py` import the same constant, making it difficult to customize behavior per use case.

## Reason for change
Making the timeout configurable allows operators to adjust based on their deployment environment and server characteristics. This improves reliability and reduces false positives in server health detection.

## Implementation intent
Add a configurable timeout field to the McpServerConfig dataclass so each server can specify its own timeout. Fall back to a sensible default (currently 5.0) when not specified. Update both `mcp_tool_discovery.py` and `mcp_status.py` to use the per-server timeout instead of the global constant.

## Implementation instructions
1. Add a new optional field to `McpServerConfig` in `config_dataclasses.py`:
   ```python
   # Timeout in seconds for health checks and tool discovery requests.
   # Defaults to 5.0 if not specified.
   health_timeout: float | None = None
   ```

2. Create a helper function to resolve the effective timeout:
   ```python
   def get_effective_health_timeout(cfg: McpServerConfig) -> float:
       """Return the effective health timeout for this server, using the configured value or the default."""
       if cfg.health_timeout is not None:
           return cfg.health_timeout
       # Default fallback — keep in sync with the constant in http_lifecycle.py
       return 5.0
   ```

3. Update `mcp_tool_discovery.py` to use the per-server timeout:
   ```python
   resp = await self._ctx.services_required.http.get(
       f"{cfg.url}/v1/tools",
       timeout=httpx.Timeout(timeout=get_effective_health_timeout(cfg)),
   )
   ```

4. Update `mcp_status.py` similarly to use the per-server timeout.

5. Keep `MCPSERVER_HEALTH_TIMEOUT` in http_lifecycle.py as the documented default value for reference.

## Acceptance criteria
- [ ] Each MCP server can specify its own health timeout via config
- [ ] Servers without explicit timeout still use the default of 5.0 seconds
- [ ] No regressions in normal operation when registry is available
