## Background
`issues/20260817_09_issue.md` grouped five open questions that each need an owner
decision before any further code or doc change, so they can be reviewed together. A
read-only verification pass against the current repository (2026-08-18) re-checked
every claim in the issue against source:

1. **git-mcp vs github-mcp write-guard asymmetry** — confirmed still present.
   `GitSecurityGuards._check_write()` (`git_security.py:41-45`) is a single global
   `read_only: bool` switch: if `False`, every write tool (`git_add`, `git_commit`,
   `git_checkout`, `git_pull`, `git_push`) is allowed unconditionally. There is no
   per-branch protection, path denylist, file-size cap, or audit log anywhere in
   `scripts/mcp_servers/git/`. By contrast, `GitHubSecurityGuards`
   (`service_security.py`) enforces `_assert_allowed_repo` (fail-closed on empty
   allowlist), `_assert_allowed_path` (glob denylist), `_assert_max_file_size`,
   `_assert_allowed_branch` (protected-branch glob patterns via
   `_resolve_and_check_branch`), `allow_force_push` gating rebase merges
   (`service_pull_requests.py:158-160`), and `_write_github_audit_log`. `git_push`
   in `git_service.py:225-235` can push directly to any branch (e.g. `main`) with
   no protected-branch check at all, while the equivalent GitHub write path is
   branch-gated. `read_only` defaults to `true` (`git_models.py:29`) and is
   enforced again at dispatch in `git_server.py:77-78`, but once an operator sets
   `read_only=false`, no finer-grained control exists at all. This is a real,
   currently-existing asymmetry, not a resolved item. It is already flagged
   in-repo as an open, unconfirmed design question — `docs/04_mcp_04_05_git.md:89`
   states verbatim: "git_checkout/git_pull/git_push を他の書き込みツールと区別する
   追加ガード（例: 保護ブランチ・force push 制限）は実装されていない...
   [Needs Confirmation: この非対称性が意図的な設計判断なのか...不明であり、
   担当者の決定が必要である。]" A prior issue,
   `issues/done/20260802-075026_mcp_git_write_tools_guard_asymmetry.md`, already
   asked for exactly this confirmation; its outcome was only to add the
   "Needs Confirmation" note above to the doc, not to record an actual decision —
   so the ambiguity remains genuinely open today, and this requirement supersedes
   that prior issue's unfinished follow-through.

2. **Workflow approval gate default-disabled** — confirmed still present.
   `WorkflowDef.require_approval: bool = False` (`workflow/models.py:93`) and
   `workflow_loader.py:136` both default to `False` when a workflow definition
   omits the field, and the shipped operational config explicitly sets it to
   `false` too (`config/workflows/default.json:25`). No approval gate is inserted
   between execute and verify (`workflow_engine.py:143`) unless a workflow
   definition explicitly opts in. Already flagged as an open, unconfirmed question
   in `docs/05_agent_03_03_turn-processing-flow-workflow-engine.md:92,272`: "...
   本番デプロイのデフォルト設定では承認ゲートは発火しない...(Needs Confirmation /
   未決事項)".

3. **`cfg.diagnostics.*` not reloadable via `/reload`** — confirmed still present.
   `DiagnosticsConfig` (`config_dataclasses.py:383-396`) declares `encryption_key`,
   `retention_days`, and `sensitive_fields`. `ConfigReloadService`
   (`config_reload.py`) has dedicated apply/reload methods for LLM, tool, RAG,
   approval, memory, SSE, and MCP-security fields, but no method reads or writes
   any `ctx.cfg.diagnostics.*` field anywhere in the file — `diagnostics` is not
   mentioned once, and it is absent from `_detect_startup_only()`
   (lines 431-445) too, so it is not even reported to the operator as a
   startup-only/skipped field. A change to `[diagnostics]` in `agent.toml` only
   takes effect after a full restart, with no visible signal that this section is
   excluded from `/reload`. Already noted as a plain fact (without stated intent)
   in `docs/05_agent_08_01_configuration-loading-agent-config.md:34,114`:
   "`diagnostics.*`は`/reload`未対応".

4. **`RagPipelineConfig` code defaults vs. `config/rag_pipeline_mcp_server.toml`
   divergence** — confirmed still present, with concrete diffs. Comparing
   `RagPipelineConfig` dataclass defaults (`rag_pipeline_models.py:40-65`) against
   the operational TOML (`config/rag_pipeline_mcp_server.toml`):
   - `top_k_search`: code default `5` vs. TOML `20`
   - `top_k_rerank`: code default `10` vs. TOML `15`
   - `rag_min_score`: code default `0.0` vs. TOML `2.0`
   - `semantic_cache_max_size`: code default `128` vs. TOML `100`
   - `refiner_max_chars_per_chunk`: code default `800` vs. TOML `300`
   - `use_semantic_cache`: TOML does not set this key at all, so it silently
     resolves to the code default (`False`)

   Five fields have materially different values between the dataclass default and
   the file that is actually loaded in production, and one field is silently
   absent from the TOML entirely. Because `from_dict()` always falls back to the
   dataclass default when a TOML key is missing, nothing currently forces these
   two sources to agree, so "the TOML is the source of truth" cannot be assumed
   safely — simplifying/trimming the TOML on that assumption could silently
   change production RAG search/rerank behavior.

5. **RAG-003 / RAG-004 unused DTOs** — re-verified individually; the two items no
   longer have the same status:
   - **RAG-003** (`RegisteredDocument` in `scripts/rag/models_data.py:62-68`) is
     still open and accurate: grep across the repo shows zero imports or
     instantiations of `RegisteredDocument` outside its own definition.
   - **RAG-004** as originally described (`MqeConfig`, `FusionConfig`,
     `RerankConfig`, `SearchConfig`, `ChunkSplitterConfig`, `IngesterConfig`,
     `PipelineConfig` in `scripts/rag/models_config.py`) is now **stale and no
     longer applicable**: none of those seven dataclasses exist in
     `scripts/rag/models_config.py` any more. The file was refactored down to a
     single `RagConfigImpl` dataclass, which *is* actively used
     (`scripts/rag/pipeline.py:41,121,180` and by
     `tests/rag/test_rag_pipeline_stage.py`, `tests/agent/test_rag_get_cfg.py`).
     The "keep vs. remove" question RAG-004 posed no longer has a subject — the
     unused classes it referred to are gone, replaced by a used one. RAG-004 is
     therefore excluded from this requirement's scope; `docs/03_rag_04_04_dto-models_config.md`
     and the RAG-004 entry in `docs/03_rag_90_inconsistencies_and_known_issues.md`
     are now themselves stale (still describing the seven removed dataclasses) —
     that documentation drift is a separate documentation-hygiene concern, not an
     open design decision, and is out of scope here.

## Problem
Four genuinely open, currently-reproducible ambiguities (write-guard asymmetry
between git-mcp and github-mcp; workflow approval gate default; `cfg.diagnostics.*`
reload exclusion; `RagPipelineConfig` code-vs-TOML divergence) and one genuinely
open unused-DTO question (RAG-003) currently have no recorded owner decision. Each
carries a real risk if acted on by assumption:
- Treating the git-mcp/github-mcp asymmetry as "fine" without a decision risks an
  unreviewed gap (git-mcp write path can push to `main` with no protection); treating
  it as "must fix" without a decision risks scope creep or breaking an intentionally
  simpler local-git tool.
- Leaving the workflow approval gate default undecided means nobody has confirmed
  whether `require_approval: bool = False` matches the intended safety posture, or
  whether it should default to `True` (safer default, opt-out) instead.
- The `cfg.diagnostics.*` reload gap has no recorded intent — it could be a
  deliberate startup-only design (e.g., because `encryption_key` should not rotate
  live) or a simple oversight.
- The `RagPipelineConfig` divergence means nobody has confirmed whether the
  dataclass defaults or the TOML values are the intended production behavior,
  making any future "simplify the TOML by dropping redundant keys" change unsafe
  without first knowing which values are canonical.
- `RegisteredDocument` (RAG-003) has sat unused with no recorded keep/remove
  decision.

## Reason for change
Without a recorded decision, any future engineer (human or AI) touching these areas
is forced to either guess intent or re-investigate from scratch. Recording the
decision now, while the evidence has just been freshly verified, is cheap;
re-discovering it later after further drift (as already happened with RAG-004,
which changed shape entirely since it was first raised) is not. This also unblocks
whichever follow-up issues are actually needed — right now no follow-up exists for
any of these four decisions.

## Implementation intent
For each of the five items below, record an explicit decision and, where the
decision requires code or config change, open a dedicated follow-up issue (using
the existing `issues/` workflow) referencing this requirement and the verified
evidence above. Do not implement the eventual fix here — this requirement is scoped
to decision-recording and follow-up issue creation only, consistent with the
original issue's intent ("Convert ambiguous items into recorded decisions").

1. **git-mcp / github-mcp write-guard asymmetry**: decide whether git-mcp's
   coarse-grained `read_only` guard is an intentional simplification (local git,
   trusted operator, no PR/branch-protection concept needed) or a gap that should
   gain an equivalent to github-mcp's `protected_branches` / path-denylist /
   audit-log controls. Record the decision and, if a gap, open a follow-up issue
   scoped to adding the missing guard(s) to `scripts/mcp_servers/git/`.
2. **Workflow approval gate default**: decide whether `require_approval` should
   keep defaulting to `False` (opt-in gate) or switch to `True` (opt-out, safer
   default). Record the decision and, if a change is warranted, open a follow-up
   issue scoped to changing the default in `workflow/models.py` and
   `workflow_loader.py` plus updating any workflow definition that silently relied
   on the old default.
3. **`cfg.diagnostics.*` reload exclusion**: decide whether this is intentional
   (e.g., encryption-key rotation mid-session is unsafe) or a missing feature.
   Record the decision and, if a feature gap, open a follow-up issue scoped to
   adding `diagnostics` handling to `ConfigReloadService`, consistent with how
   other config sections are handled there.
4. **`RagPipelineConfig` defaults vs. TOML**: decide which source is canonical —
   either the dataclass defaults should be updated to match the operational TOML
   (making the TOML the single source of truth), or the TOML should be corrected
   to match intended dataclass defaults, or both should be explicitly documented
   as intentionally different (e.g., "TOML values are the tuned production
   values; dataclass defaults are safe fallbacks for missing keys only"). Record
   the decision and open a follow-up issue to reconcile the five diverging fields
   and the one silently-defaulted field (`use_semantic_cache`) listed in the
   Background section.
5. **RAG-003**: decide whether `RegisteredDocument` is a forward-looking
   placeholder to keep or dead code to remove. Record the decision and, if
   removal, open a follow-up issue to delete it and update
   `docs/03_rag_04_01_dto-models_data.md` accordingly.
