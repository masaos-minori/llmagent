# Simplify docs/01_overview-files-05-config.md file listing; add config-split criteria and allowlist-change rule; establish canonical MCP port/name table

## Priority
High

## Target files
- `docs/01_overview-files-05-config.md` (primary edit target, ~lines 22-46)

## Background
`docs/01_overview-files-05-config.md` §3 currently contains a manually-maintained ASCII tree listing of `config/` files with inline port annotations (lines 26-46). Verification against the current `config/` directory confirms this listing has already drifted: `config/doc_quality_rules.json` exists on disk but is absent from the documented listing. This confirms the issue's drift-risk concern is not hypothetical.

Separately, per the broader documentation-review effort (`docs_review_overview_architecture.md` §1/§2/§4), MCP server port numbers are currently duplicated across at least `01_overview-arch-01-process.md`, `01_overview-files-03-scripts-part5.md`, and this file (and, independently observed during verification, also `04_mcp_01_system_overview.md` and `04_mcp_01_tool_ownership_matrix.md`, which currently agree with this file's numbers). One further file, `04_mcp_02_service_boundaries.md`, was found to carry a *different, inconsistent* port mapping (e.g. it lists `rag-pipeline-mcp` as port 8005 and `file-mcp` as 8004) — this is evidence supporting the canonical-source rationale but is explicitly out of scope for this requirement (no separate issue currently tracks it; do not fix it here).

A config-split criteria (what belongs in `agent.toml` vs. an individual MCP server's own TOML file) was investigated and found to already exist, just not in this file: `docs/04_mcp_06_02_configuration-file-inventory.md` documents a "プロセス分離方針" (process separation policy) with two layers — Layer 1 (`config/agent.toml`, read only by the agent process: `[mcp_servers.*]` transport config, `tool_definitions`, `tool_safety_tiers`, `security_profile`) and Layer 2 (`config/*_mcp_server.toml`, each server's own local application settings, enforced at runtime via `ConfigLoader.restrict_to(own_config_file)` / `ConfigPermissionError`). This is derivable and citable — it does not need to be treated as a Needs Confirmation item.

No existing doc was found stating an operational change-management rule for allowlist edits (e.g. `file_read_mcp_server.toml` `allowed_dirs`, `shell_mcp_server.toml` `command_allowlist`) — only descriptive references to what allowlists do and their fail-open/fail-closed defaults (`04_mcp_05_01_access-control-and-allowlists.md`, `04_mcp_06_10_settings-with-high-operational-impact.md`). This rule is genuinely new content to add, not something to source from elsewhere.

## Problem
1. The file listing in `docs/01_overview-files-05-config.md` is stale (confirmed: missing `config/doc_quality_rules.json`) and will keep drifting because it is manually maintained by hand rather than pointing at the implementation tree.
2. The document does not explain the agent.toml vs. per-server-TOML split, even though that criteria already exists in `04_mcp_06_02_configuration-file-inventory.md` and is not referenced from this file.
3. The document does not state an operational rule for changing allowlist values safely, despite these being security-sensitive (fail-open/fail-closed behavior documented in `04_mcp_05_01_access-control-and-allowlists.md`).
4. This file is not yet established as the single canonical source for the MCP server name/port mapping, even though it is a natural candidate and other files currently repeat the same numbers independently.

## Reason for change
- Confirmed drift (missing `doc_quality_rules.json`) demonstrates the manual listing is already unreliable and will keep costing review effort to keep in sync.
- Allowlist changes are security-sensitive: getting the change process wrong risks unintentionally permitting file or command execution. This is operational knowledge that should not have to be reverse-engineered from code.
- Port-number duplication across multiple docs risks drift between them (already independently confirmed as a concern in the arch-01 server-count issue referenced by this issue).

## Implementation intent
- Replace the manually-maintained ASCII file listing (lines ~26-46) with a short pointer to `config/` as the source of truth for the current file list (implementation-tree pointer style), rather than re-enumerating every file by hand.
- Add a concise config-split criteria section that states the two-layer policy, sourced from and cross-referenced to `04_mcp_06_02_configuration-file-inventory.md` (do not restate it in a way that could drift independently — link to it as the detailed source, summarize only the decision rule here: transport/agent-wide/tool-safety settings that only the agent process reads go in `agent.toml`; a given MCP server's own runtime/application settings, including its own allowlists, go in that server's `config/<key>_mcp_server.toml`).
- Add an operational rule paragraph for allowlist changes, along the lines suggested in the issue (allowed-directory / allowed-command changes must go through code review and be kept consistent with `conf.d/` settings, since loosening them carelessly risks permitting unintended file or command execution).
- Add (or reformat existing content into) an explicit MCP server name ↔ port mapping table in this file, marked as canonical, so that other documents can reference it instead of repeating the numbers.
