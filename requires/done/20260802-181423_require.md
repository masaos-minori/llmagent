## Background
`issues/20260802-080020_rag_02_04_method_name_and_table_cleanup.md` originally reported two
problems in `docs/03_rag_02_04` (parts 1+2): (1) a method-name error where
`delete_existing_document()` was claimed to not exist and should be `delete_document(url: str)`,
and (2) verbatim, code-derived tables (Dataclass table, public-methods table in part1;
updated-DB-tables table and structured-logging-field table in part2) that mechanically
transcribe source instead of documenting design intent.

Re-verification against current source found that claim (1) no longer applies: it was
already fixed by commit `6cfb24c10` ("feat: add RAG docs consistency checker and fix
confirmed drift"). Current `docs/03_rag_02_04_ingestion_pipeline-ingester-part1.md`
§4.2.1 (lines 78-79, "影響を受けるコードパス") already correctly distinguishes the two
distinct `DocumentManager` classes and their methods:
- `DocumentManager.delete_existing_document()` in `scripts/rag/ingestion/document_manager.py`
  (confirmed present at line 116 of that file) — the ingestion-pipeline delete path.
- `DocumentManager.delete_document(url)` in `scripts/mcp_servers/rag_pipeline/document_manager.py`
  (confirmed present at line 62 of that file, signature `def delete_document(self, url: str) -> bool`)
  — the MCP-tool (`rag_delete_document`) delete path.

Both methods exist in their respective files and both are already correctly cited with the
correct file path in the current doc. No method-name fix is needed. `docs_review_rag.md`'s
"Needs confirmation" entry on this point is stale and pre-dates the `6cfb24c10` fix.

Claim (2) was re-verified and still applies: the verbatim tables are still present in the
current docs:
- part1 lines 39-43: "Dataclass" table for `IngestUrlResult`.
- part1 lines 45-53: "公開メソッド" (public methods) table for `RagIngester`.
- part2 lines 53-60: "4.5 更新されるDBテーブル" (updated DB tables) table.
- part2 lines 79-83: "4.7 ロギング" structured-field-by-log-level table.

## Problem
`docs/03_rag_02_04` parts 1 and 2 contain tables that are mechanical, field-by-field
transcriptions of source code (dataclass fields, method signatures, DB table
operations, structured logging fields). This code-derived detail provides no
design-intent value beyond what reading the source directly would show, and it drifts
out of sync whenever the underlying code changes (as evidenced by the already-fixed but
previously-stale method-name reference nearby in the same file).

## Reason for change
Removing verbatim, code-derived tables and replacing them with a pointer to the
implementation source / Reference API keeps the documentation focused on design intent
(e.g. the deletion-order invariant, `embedding_dims` validation) and removes a
maintenance burden that produces no long-term value: these tables must otherwise be kept
in lockstep with source changes indefinitely.

No method-name change is required in this pass — that part of the original issue is
already resolved in current source and must not be reintroduced or "fixed again."
