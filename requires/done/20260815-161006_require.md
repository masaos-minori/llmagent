# Enhance ToolLoopGuard cycle detection beyond exact fingerprint matching

## Priority
Medium

## Target files
- scripts/agent/tool_loop_guard.py
- scripts/agent/llm_turn_runner.py
- scripts/agent/config_dataclasses.py

## Background
During adversarial review of the agent startup process, we traced the full turn orchestration flow through orchestrator.py → llm_turn_runner.py → tool_loop_guard.py. The ToolLoopGuard handles duplicate call detection, cycle detection, retry suppression, and consecutive error limiting. However, the current cycle detection logic only catches exact repetitions of the same round-level tool fingerprint. It does not detect patterns where different tool calls are made each time but no progress is being made toward a solution.

## Problem
The current `check_cycle()` method in ToolLoopGuard detects cycles by comparing round-level fingerprints (sorted tool call name+argument pairs hashed via MD5). This approach works when the LLM repeats the exact same sequence of tool calls, but fails to detect patterns where:

1. The LLM makes different tool calls each time but none make progress (e.g., trying different approaches to the same problem without advancing)
2. The LLM oscillates between two or more sets of tool calls without converging
3. The LLM makes valid-looking tool calls that all succeed but don't advance toward the goal

While `max_tool_turns=5` prevents true infinite loops, these undetected patterns waste turns and may cause premature termination with unhelpful results. The current guards only trigger after 5 turns of wasted effort rather than detecting the pattern earlier.

## Reason for change
Enhancing cycle detection to recognize partial progress patterns would allow earlier intervention and better user experience. Instead of waiting for the LLM to exhaust all allowed turns, the system could detect stagnation patterns and prompt the LLM to provide a final answer sooner.

## Implementation intent
Add a secondary cycle detection mechanism that tracks whether tool calls are making progress over multiple rounds. This could use:
- Tracking unique tool names called per round and detecting when the same subset of tools is repeatedly invoked without new tools being introduced
- Measuring semantic similarity of tool call arguments across rounds to detect near-duplicate patterns
- Adding a configuration option for a "progress window" that measures how many distinct tool names have been used recently

## Implementation instructions
1. In `scripts/agent/tool_loop_guard.py`, add a new `_check_progress_stagnation()` method:
   - Track unique tool names per round in `TurnLoopState`
   - Compare recent rounds' tool name sets against historical patterns
   - Return an exit message when stagnation is detected (different tools but no new capabilities being exercised)

2. Update `check_all()` to also call the new stagnation check

3. Consider adding a new config field to `ToolConfig` in `config_dataclasses.py`:
   ```python
   # Number of recent rounds to consider for progress stagnation detection.
   # When the same subset of tool names appears in N consecutive rounds
   # without any new tool being introduced, treat it as stagnation.
   progress_stagnation_window: int = 3
   ```

4. Document the new guard behavior in the class docstring

## Acceptance criteria
- [ ] Cycle detection prevents infinite loops under all conditions
- [ ] Stagnation patterns (different tools, no progress) are detected earlier than max_tool_turns
- [ ] No regressions in normal operation when registry is available
- [ ] New config field has sensible default

## Tests
- Unit test for `check_cycle()` with various fingerprint combinations including near-duplicate patterns
- Unit test for new stagnation detection with different tool sequences that show no progress
- Integration test verifying guard behavior during extended tool-call loops

## Documentation Impact

## Out of Scope

- Adding retry logic for health checks
