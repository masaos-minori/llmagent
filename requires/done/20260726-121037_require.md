## Background

The `_migrate` function in `eventbus/db.py` handles schema migration from an older version that had a `retry_count` column to the current schema with `delivery_failure_count` and `dlq_requeue_count` columns. This entire migration code path is untested.

## Problem

**Needs confirmation resolved (verified against current `scripts/eventbus/db.py:76-113` on
2026-08-23):** the code below has diverged from the snippet originally filed in this
requirement — the current `_migrate` uses a try/except idempotent-column pattern instead of
a `PRAGMA table_info` existence check, and also creates two indexes. The requirement is
updated to match:

```python
def _migrate(conn: sqlite3.Connection) -> None:
    for col in ("delivery_failure_count", "dlq_requeue_count"):
        try:
            conn.execute(
                f"ALTER TABLE events ADD COLUMN {col} INTEGER NOT NULL DEFAULT 0"
            )
        except sqlite3.OperationalError as exc:
            if exc.args and "duplicate column name" in exc.args[0]:
                pass  # column already exists
            else:
                raise
    try:
        conn.execute("ALTER TABLE events DROP COLUMN retry_count")
    except sqlite3.OperationalError as exc:
        if exc.args and "no such column" in exc.args[0].lower():
            pass  # already dropped, or table created fresh without it
        else:
            raise
    for idx in (
        "idx_events_dlq_at ON events(dlq_at)",
        "idx_events_dlq_seq ON events(dlq_at, seq)",
    ):
        conn.execute(f"CREATE INDEX IF NOT EXISTS {idx}")
```

No test verifies:
1. Migration succeeds when `retry_count` column exists
2. New columns are correctly added
3. Existing data is preserved after migration
4. Exception during migration does not corrupt the database
5. Calling `_migrate()` a second time on an already-migrated database is a no-op (idempotency
   of the try/except duplicate-column and no-such-column branches — not covered by the
   original filing, added because the current implementation's correctness depends on it)

## Reason for Change

This component was classified as High-risk-refactor because migration code is untested. Without guard tests, any change to the migration logic could silently break existing databases.

## Implementation Intent

Create `tests/eventbus/test_eventbus_db_migration.py` (placed alongside the other
`tests/eventbus/test_eventbus_*.py` files, not directly under `tests/`) with:

1. `test_migrate_adds_new_columns`: Create DB with `retry_count` column, run `_migrate()`, verify `delivery_failure_count` and `dlq_requeue_count` exist
2. `test_migrate_preserves_data`: Insert rows before migration, verify they survive migration unchanged
3. `test_migrate_is_idempotent`: Run `_migrate()` twice on the same connection; the second call must not raise and must leave the schema/data unchanged
