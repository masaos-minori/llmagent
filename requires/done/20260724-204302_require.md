# StartupOrchestrator.run() failure causes HTTP client leak

## Priority

Critical

## Target Files

- `scripts/agent/repl.py` — AgentREPL.run(), _run_repl_loop(), _close_resources()
- `scripts/agent/startup.py` — StartupOrchestrator.run(), _start_servers()

## Background

AgentREPL.run() calls StartupOrchestrator.run() during startup. If startup fails, the REPL loop is never entered, and its finally block (which closes resources including the HTTP client) is skipped.

## Problem

In `repl.py:506-512`:

```python
startup = StartupOrchestrator(self._ctx, self._view)
try:
    self._cmds, self._orchestrator = await startup.run()
except Exception as e:
    self._view.write_fatal(f"Startup failed: {e}")
    raise
await self._run_repl_loop()
```

When `StartupOrchestrator.run()` raises an exception, `_run_repl_loop()` is never called. Its finally block (line ~472-475) contains `await self._close_resources()`, which closes `svc.http`. This resource cleanup is therefore conditional on successful startup.

Additionally, if `StartupOrchestrator._start_servers()` has spawned MCP subprocesses before failing, those processes are also leaked because no cleanup path exists for partial-start failures.

## Reason for Change

Resource leaks on startup failure cause:
- Accumulated open HTTP connections across restart attempts
- Zombie MCP subprocesses consuming system resources
- Unpredictable behavior on subsequent startup attempts

## Implementation Intent

Ensure all resources acquired during the startup phase are released regardless of whether startup succeeds or fails. The fix must be minimal and localized to the startup path only.

## Implementation Instructions

### Option A (Recommended): Move resource close to AgentREPL.run() finally

1. Add a finally block in `AgentREPL.run()` that calls `_close_resources()` unconditionally.
2. Refactor `_close_resources()` to handle the case where `self._ctx.services` is None (partial startup).
3. Ensure subprocess cleanup is included in the finally block.

### Option B: Explicit cleanup in the except handler

1. In the `except Exception` handler at line 509, call `_close_resources()` before re-raising.
2. Also add a finally block to catch cases where the except handler itself raises.

Option A is preferred because it covers both success and failure paths uniformly.

## Acceptance Criteria

- [ ] StartupOrchestrator.run() raises an exception and HTTP client is closed
- [ ] MCP subprocesses spawned during startup are terminated on failure
- [ ] Resource cleanup runs unconditionally (not dependent on startup success)
- [ ] No new exceptions introduced by the cleanup logic

## Tests

- Unit test: mock `StartupOrchestrator.run()` to raise; verify `_close_resources()` is called
- Integration test: simulate MCP subprocess spawn followed by startup failure; verify subprocess termination
