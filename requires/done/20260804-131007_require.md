# Decide whether `resolve_approval` should reject approvals for halted tasks

## Priority

Medium

## Target files

- `scripts/agent/workflow/approval_ops.py` (reference/candidate change — `resolve_approval`, lines
  45-67)
- `scripts/agent/commands/cmd_workflow.py` (reference/candidate change — `_cmd_approve` /
  `_cmd_reject`)
- `tests/agent/test_approval_task_persistence.py` (reference — `TestHaltedTaskStatusRejection`,
  lines ~145-164)

## Background

While planning the fix for `tests/agent/test_approval_task_persistence.py`
(originating from `requires/done/20260804-094909_require.md`, developed into
`plans/done/20260804-104315_plan.md`), reading `resolve_approval()`'s full body in
`scripts/agent/workflow/approval_ops.py` (lines 45-67) confirmed it only checks the *approval*
row's own status (`not found` / `already resolved`) — it never queries or checks the associated
task's status. Resolving an approval for a task that has already been marked `"halted"` (via
`update_task_status(db, task_id, "halted")`) therefore succeeds today exactly as if the task were
still `"running"`. This was re-verified directly against the current source as part of this
requirement's assessment: `resolve_approval` (lines 45-67) still contains only two SQL statements
against the `approvals` table, with no reference to the `tasks` table or `task_id` status.

`tests/agent/test_approval_task_persistence.py::TestHaltedTaskStatusRejection::test_halted_task_prevents_resume`
currently asserts the opposite (`pytest.raises(RuntimeError)`) — an invented contract that does not
match `resolve_approval`'s real behavior, and fails as written. The plan built from the prior
requirement (`plans/done/20260804-104315_plan.md`) directs correcting this test to assert the true
outcome (no exception; approval resolves normally), rather than adding a task-status check to
`resolve_approval` itself, since production-code changes were explicitly out of scope for that
document-only test-fix cycle. As of this writing, that test-fix has not yet been applied to the
test file — `test_halted_task_prevents_resume` still asserts `pytest.raises(RuntimeError)` — so the
gap described below has not yet materialized in the test suite, but is scheduled to once the
approved test-fix plan is implemented.

## Problem

Once the test is corrected to assert the true (no-check) behavior, the codebase will have **zero
automated coverage** flagging the fact that a halted task's pending approval can still be resolved.
This may be an intentional current limitation, or it may be a genuine product gap — the answer is
not decidable from source code alone and requires a maintainer/product decision.

Evidence (re-verified against current source):
- `scripts/agent/workflow/approval_ops.py:45-67` — `resolve_approval()` body: two `SELECT`/`UPDATE`
  statements against the `approvals` table only; no reference to the `tasks` table or `task_id`'s
  current status anywhere in the function.
- `tests/agent/test_approval_task_persistence.py` — `test_running_task_allows_resume` (in the same
  `TestHaltedTaskStatusRejection` class group) already establishes, for a `"running"` task, that
  `resolve_approval` succeeds without any status check — confirming the halted-task case is
  symmetric (no differentiation by task status at all).
- `scripts/agent/commands/cmd_workflow.py` — `_cmd_approve` (line 116) and `_cmd_reject` (line 172)
  both call `resolve_approval` directly with no halted-task check beforehand; the gap is not
  compensated for at the command-handler layer either.

## Reason for change

Without an explicit maintainer decision, the loss of test coverage for this behavior would go
unnoticed, and no one would be accountable for either (a) confirming the current behavior is
intentional, or (b) authorizing a production-code fix. Filing this as a requirement makes the
decision visible and actionable rather than letting it silently disappear along with the test
rewrite.

## Implementation intent

This requirement does not mandate a specific code change. It requires a maintainer/product
decision between two options, and defines the minimal follow-up work for each:

1. **Halted-task rejection is desired behavior.** Add a task-status check inside
   `resolve_approval` (or in the `_cmd_approve`/`_cmd_reject` command handlers in
   `cmd_workflow.py`, before calling `resolve_approval`) that rejects resolution when the
   associated task's status is `"halted"`. Restore dedicated test coverage for this behavior
   (e.g., re-instating an equivalent of `test_halted_task_prevents_resume` that asserts
   `pytest.raises(RuntimeError)` against the *new*, intentional guard).
2. **Current behavior is acceptable** (e.g., halting a task is an independent, orthogonal state
   that should not block approval resolution). No code change is needed. The corrected test's
   docstring (per `plans/done/20260804-104315_plan.md`) should remain the documented
   characterization of this known gap, and this requirement can be closed as "working as
   intended" with no further action.

## Implementation instructions

- A maintainer must first choose option 1 or option 2 above.
- If option 1 is chosen: this requirement should be superseded by a new, separate requirement
  document that authorizes the production-code change (a task-status check in `resolve_approval`
  and/or the `cmd_workflow.py` command handlers) together with its own test coverage. Do not add
  the check silently as a side effect of processing this document.
- If option 2 is chosen: no code or test changes are needed beyond what
  `plans/done/20260804-104315_plan.md` already specifies for the test docstring. Close this
  requirement without further action.
- Under no circumstances should the task-status check be added to `resolve_approval` without an
  explicit requirement authorizing that specific production-code change.

## Acceptance criteria

- A maintainer/product decision is recorded (either as a follow-up requirement authorizing a
  `resolve_approval` guard, or as an explicit "working as intended" closure).
- If a guard is authorized and implemented, `resolve_approval` (or the relevant command handler)
  rejects approval resolution for tasks with status `"halted"`, and a test equivalent to
  `test_halted_task_prevents_resume` passes against that new, intentional behavior.
- If no guard is authorized, the known-gap characterization in
  `test_halted_task_prevents_resume`'s docstring (per `plans/done/20260804-104315_plan.md`) remains
  accurate and in place.

## Tests

- No new tests are required by this document itself; it only requires a decision.
- If option 1 (add the guard) is subsequently authorized, that follow-up requirement must specify
  a corresponding automated test asserting the halted-task rejection behavior.
