# Resolve NC-005: Determine Whether AuditLogRecord/ApprovalDecision in scripts/rag/models_audit.py Are Dead Code

Low

## Target Files

- `docs/00_governance_07_needs-confirmation-inventory.md` (NC-005 entry, ~line 106-111) — inventory entry tracking this open question

## Background

`docs/03_rag_04_03_dto-models_audit.md` documents two dataclasses in `scripts/rag/models_audit.py`:
`AuditLogRecord` (an immutable audit log entry for tool execution) and `ApprovalDecision` (an
immutable record of an approval decision). The doc states these appear to implement "RAG pipeline
tool execution audit/approval workflow DTOs," but notes this description does not match current
usage.

Note on naming: the issue file (`issues/20260727_17_issue.md`) and the governance inventory entry
`docs/00_governance_07_needs-confirmation-inventory.md` (NC-005) refer to these classes as
`RagAuditRequest`/`RagAuditResponse`. This name does not exist anywhere in the codebase (verified
via repo-wide grep). The actual class names, confirmed by reading
`scripts/rag/models_audit.py` and `docs/03_rag_04_03_dto-models_audit.md`, are `AuditLogRecord`
and `ApprovalDecision`. This appears to be a naming inconsistency already present in the governance
inventory document, not a new problem introduced by this issue. The substantive open question
(dead code vs. forward-looking definition) is unaffected and still applies to the real classes.

## Problem

- `AuditLogRecord` and `ApprovalDecision` in `scripts/rag/models_audit.py` are not imported by any
  file under `scripts/` (verified via `grep -rn "from rag.models_audit\|rag\.models_audit\."` and
  `grep -rn "ApprovalDecisionEvent"` across the repo — zero references to either class name from
  any consumer).
- The real, actively used approval/audit workflow lives in a separate implementation under
  `scripts/agent/` (`scripts/agent/shared/models.py` defines `ApprovalDecisionEvent`;
  `scripts/agent/tool_audit.py` and `scripts/agent/tool_approval.py` implement the actual
  tool-execution audit/approval logic). This is unrelated to `scripts/rag/models_audit.py`.
- `git log --oneline -- scripts/rag/models_audit.py` shows only formatting/refactor commits since
  the file was split out of `rag/models.py` (`f6a3d2db`); no commit has ever added a consumer.
- It remains unknown from the code and git history alone whether these two classes were
  intentionally pre-declared for a planned RAG-side audit feature, or are leftover dead code from
  an incomplete refactor.

## Reason for Change

Unused, unreferenced DTOs create ongoing maintenance burden (they must be kept in sync with any
future audit/approval schema changes without ever being exercised or tested) and mislead readers
of the RAG module into believing an audit/approval integration exists there. Resolving the
ambiguity — by either removing the dead code or documenting a concrete forward-looking rationale —
removes this confusion and lets the "Needs confirmation" item in the governance inventory be
closed.

## Implementation Intent

This is an investigation-and-decision task, not a code fix. The eventual outcome (delete the
classes, or keep them with a documented rationale) is a decision for a maintainer/code owner with
project context, not something derivable purely from static analysis. This requirement covers the
investigation steps needed to reach that decision and, separately, the documentation updates that
should follow once the decision is made (documentation updates are out of scope for the current
document-only workflow phase and must be done in a later phase).
