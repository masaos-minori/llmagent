# Fix `ToolTransportInvoker.__init__` to honor `call_timeout_sec=0` as "no timeout" and remove the dead `hasattr` check

## Priority
Medium

## Target files
- `scripts/shared/tool_transport_invoker.py` (`ToolTransportInvoker.__init__`)
- `tests/shared/test_tool_transport_invoker.py`

## Background
Verified against current source (2026-08-13):

- `scripts/shared/tool_transport_invoker.py:54-58` computes the per-server timeout as:
  ```python
  timeout_sec = (
      cfg.call_timeout_sec
      if hasattr(cfg, "call_timeout_sec") and cfg.call_timeout_sec
      else 60.0
  )
  ```
- `McpServerConfig.call_timeout_sec` (`scripts/shared/mcp_config.py:55`) is a dataclass field
  `call_timeout_sec: float = 60.0  # per-call timeout for HttpTransport; 0 = no timeout` — always
  present on any `McpServerConfig` instance, so `hasattr(cfg, "call_timeout_sec")` is always
  `True`. This makes the `hasattr` check dead code.
- The field-level comment at `mcp_config.py:55` explicitly documents `0 = no timeout` as the
  intended contract.
- `McpServerConfig.__post_init__` (`mcp_config.py:113-115`) validates `call_timeout_sec >= 0` (not
  `> 0`), meaning `0` is an explicitly accepted, validated value, not an invalid input to reject.
  `tests/shared/test_mcp_config_validation.py:75-76` confirms `call_timeout_sec=0` constructs
  successfully (`assert cfg.call_timeout_sec == 0`); only negative values raise.
- `HttpTransport.__init__`/call path (`scripts/shared/http_transport.py:35,42,104`) already
  implements "0 = no timeout" correctly on its own side:
  `timeout = httpx.Timeout(self._timeout) if self._timeout > 0 else None` — passing `0` through
  to `HttpTransport` correctly disables the httpx timeout.
- Because `0` is falsy in Python, `ToolTransportInvoker.__init__`'s truthy check
  (`... and cfg.call_timeout_sec`) evaluates to `False` when `call_timeout_sec == 0`, so the
  `else 60.0` branch fires and silently overrides the caller's "no timeout" request with the
  default `60.0` before `HttpTransport` ever sees the value. `HttpTransport`'s own correct
  0-means-no-timeout handling is unreachable through this path.
- No current config file in `config/` sets `call_timeout_sec` at all (repo-wide `rg` confirms
  only `mcp_config.py:218`'s loader default and `scripts/agent/services/config_reload.py:50`
  reference the key), so this is a currently latent bug: no shipped config exercises the `0` path
  today, but the field is a validated, publicly settable config value and the bug will silently
  reappear the moment anyone sets `call_timeout_sec: 0` in a server's `config/*.toml` block.
- `tests/shared/test_tool_transport_invoker.py` (8 existing tests) has no test referencing
  `call_timeout_sec` or timeout resolution at all — the `0`, positive, and default-unset cases are
  all currently untested at this layer.
- Found during a behavior-preserving refactor cycle on `tool_transport_invoker.py` (2026-08-13);
  not fixed then because it is a behavior change, out of scope for that zero-behavior-change
  refactor.

## Problem
`ToolTransportInvoker.__init__` does not honor `call_timeout_sec=0` as "no timeout," contradicting
both the field's own documented contract (`mcp_config.py:55`) and the downstream `HttpTransport`
class's already-correct handling of the same value. A user or future config author who sets
`call_timeout_sec: 0` in a server config, expecting the timeout to be disabled (per the
documented contract and per `HttpTransport`'s correct behavior), will instead silently get the
default `60.0` second timeout with no error or warning. Additionally, the `hasattr(cfg,
"call_timeout_sec")` check is unreachable dead code since the field is a non-optional dataclass
attribute with a class-level default, always present on any constructed `McpServerConfig`.

## Reason for change
The evidence collected in Background makes the intended contract unambiguous: "0 means no
timeout" is the correct, intended, and already-partially-implemented (on the `HttpTransport` side)
behavior — not a rejected or unsupported input. `McpServerConfig.__post_init__` validates `>= 0`
(not `> 0`), the field comment says so directly, and `HttpTransport` already special-cases `0`
correctly. Leaving `ToolTransportInvoker.__init__` as-is means the only class positioned to pass
this value through is the one that silently breaks it, making the documented "0 = no timeout"
contract false in practice for any caller that goes through `ToolTransportInvoker`. This is
currently latent (no shipped config sets `0`) but should be fixed proactively before any config or
caller relies on the documented behavior and hits a silent, hard-to-diagnose 60-second timeout
instead of "no timeout."

## Implementation intent
Fix `ToolTransportInvoker.__init__` to pass `cfg.call_timeout_sec` straight through to
`HttpTransport` unchanged, removing both the dead `hasattr` guard and the truthy-fallback-to-60.0
logic entirely. `McpServerConfig.call_timeout_sec` already guarantees a value is always present
(defaulting to `60.0` at the dataclass/config-loader level when unset — see `mcp_config.py:55` and
`mcp_config.py:218`), so `ToolTransportInvoker` needs no fallback logic of its own: it only needs
to forward the already-resolved field value. This lets `HttpTransport`'s existing, correct
`self._timeout > 0` check be the single place that decides "no timeout" vs. "timed out," rather
than have `ToolTransportInvoker` pre-empt that decision with its own conflicting truthy check.

## Implementation instructions
1. Read `scripts/shared/tool_transport_invoker.py:54-58` (the block being changed),
   `scripts/shared/mcp_config.py:50-60` and `:113-115` (field definition and validation), and
   `scripts/shared/http_transport.py:35,42,104` (the downstream consumer of `timeout_sec`) before
   making any change, to confirm no other logic branches on `timeout_sec` between these two
   points.
2. Per this project's refactor discipline, add characterization test(s) locking down the current
   (buggy) behavior first, then update them to lock in the fixed behavior — do not skip straight
   to the fix without a test capturing the before/after.
3. In `ToolTransportInvoker.__init__`, replace:
   ```python
   timeout_sec = (
       cfg.call_timeout_sec
       if hasattr(cfg, "call_timeout_sec") and cfg.call_timeout_sec
       else 60.0
   )
   ```
   with a direct assignment, e.g.:
   ```python
   timeout_sec = cfg.call_timeout_sec
   ```
   (or inline `cfg.call_timeout_sec` directly into the `HttpTransport(...)` call if that reads
   more cleanly with the surrounding loop) — the goal is removing both the dead `hasattr` branch
   and the truthy-vs-zero mismatch, not preserving any part of the old expression shape.
4. Do not add a new fallback default inside `ToolTransportInvoker` — the default-when-unset case is
   already fully handled upstream by `McpServerConfig`'s dataclass default (`60.0`) and by the
   config loader (`mcp_config.py:218`, `float(v.get("call_timeout_sec", 60.0))`). Adding a second
   default here would be redundant and could drift from the upstream default over time.
5. Do not modify `HttpTransport`'s own timeout handling (`scripts/shared/http_transport.py`) — it
   is already correct and out of scope for this change.
6. Do not modify any other timeout/retry/health-check logic in `ToolTransportInvoker` or elsewhere
   in this class.
7. No `docs/*.md` changes are required: `call_timeout_sec: 0`'s "no timeout" contract is already
   documented at the field level (`mcp_config.py:55`'s comment); this change makes the code match
   existing documentation rather than introducing new documented behavior. Confirm during
   implementation whether any `docs/` file describing `config/agent.toml`'s per-server keys
   contradicts this contract — if one does, that is a separate documentation-fix-required item to
   raise, not part of this requirement's scope.

## Acceptance criteria
- `ToolTransportInvoker.__init__` no longer contains a `hasattr(cfg, "call_timeout_sec")` check.
- Constructing `ToolTransportInvoker` with a server config where `call_timeout_sec=0` results in
  the corresponding `HttpTransport` instance being constructed with `timeout_sec=0` (not `60.0`),
  and, per `HttpTransport`'s existing logic, the resulting httpx timeout is `None` (no timeout).
- Constructing `ToolTransportInvoker` with a positive `call_timeout_sec` (e.g. `30.0`) still
  results in that exact value being passed through to `HttpTransport` unchanged.
- Constructing `ToolTransportInvoker` with a config using the dataclass default (`call_timeout_sec`
  unset by the caller, i.e. `60.0`) still results in `60.0` being passed through — the
  default-when-unset behavior is unchanged, just no longer implemented redundantly in
  `ToolTransportInvoker`.
- `ruff` and `mypy` pass on the changed file.
- The full `tests/shared/` suite passes, including the existing 8 tests in
  `tests/shared/test_tool_transport_invoker.py` (unchanged assertions for anything unrelated to
  timeout resolution).
