## Background
Issue `issues/20260818_07_issue.md` requested a broad reconciliation of specifications, runtime references, and issue state across Overview, Deployment, RAG, Agent, Shared/DB, and operations documents. Verification against the current repository shows the documentation set already has a substantial governance layer (`docs/00_governance_01..08`) defining canonical-source rules, a Known-Issues template, a deprecated-items registry, and a Needs-Confirmation inventory process, plus CI workflows (`.github/workflows/{overview,deployment,agent,mcp,governance,rag}-docs-consistency.yml`) and tooling (`tools/check_docs_consistency.py`, `tools/audit_docs.py`, `tools/check_doc_quality.py`). Several of the issue's original concerns are therefore already resolved in practice:
- CLI deprecated-command references (`/note`, `/ingest`, `/debug audit`, `/db *`) are documented with explicit replacements in `docs/05_agent_07_07_cli-and-commands-migration-notes.md` and `docs/00_governance_05_deprecated-items.md`.
- The three-vs-four-database ambiguity does not exist in the current docs: `docs/90_shared_04_01_db_architecture_and_schema-overview-and-config.md:35` states plainly "Four DB files exist: rag.sqlite, session.sqlite, workflow.sqlite, eventbus.sqlite" with per-DB config keys, tables, and rationale for separation; `docs/02_deployment.md` also lists `eventbus.sqlite` with path, config key, and backup applicability ("Yes").

However, targeted checks found that a subset of the issue's concerns is still concretely present in the current documentation and is not covered by existing CI/tooling.

## Reason for change
- Conflicting model/GGUF filenames across authoritative-looking documents risk an operator loading the wrong LLM or embedding model, or misconfiguring `model-path` during deployment, with no automated check to catch the mismatch before or after a docs change.
- An unarchived, all-resolved Needs-Confirmation inventory makes it hard for a reader (human or AI) to tell at a glance whether any item is still open, defeating the purpose of the inventory as an actionable tracker.
- A duplicated metadata field with two different dates is a direct data-integrity defect in a document whose stated purpose is trustworthy tracking; it also demonstrates that no validation currently enforces the single-value-per-field rule implied by the inventory's own field definitions.
- Known Issues documents remaining unmigrated after a formal migration plan was written and merged represents unfinished, stalled governance work; leaving five areas in divergent formats undermines the cross-area consistency the plan itself sets out to achieve.

## Implementation intent
- Establish one canonical location (e.g. `docs/02_deployment.md` or a new single "active models" table referenced by the others) as the single source of truth for active LLM/embedding model filenames and dimensions; convert all other mentions (`01_overview-files-01-build.md`, `03_rag_05_1-configuration-reference.md`) into either an identical restatement or an explicit cross-reference/link to the canonical entry, removing conflicting filenames.
- Add a lightweight consistency check (extending `tools/check_docs_consistency.py` / `tools/_docs_consistency_lib.py`) that extracts `.gguf` filenames and `embedding_dims` values referenced across docs and fails when the same logical model slot (LLM vs. embedding) resolves to different filenames/dimensions across documents.
- Restructure `docs/00_governance_07_needs-confirmation-inventory.md` to split resolved entries into a clearly separated archive section (or a separate archive document linked from it), keeping only genuinely open/deferred items in the active "Inventory Items" section, while preserving every original NC ID, question, evidence, and resolution text verbatim.
- Fix the NC-005 duplicate `Last Reviewed` field by keeping a single, correct value (use the most recent/most specific date, e.g. `2026-07-29`, and remove the stale duplicate) and add note about the correction only if the project's evidence-label convention requires it.
- **CORRECTED (see Problem 4 above):** No Known-Issues document migration is needed — it already happened on 2026-07-23 (commit `7b04065ce`) and the Agent area's entries were already fully resolved and removed afterward. Instead, update `docs/00_governance_08_known-issues-migration-plan.md` to record that the migration was executed (date, commit, per-area outcome), rather than leaving it framed as an unexecuted plan.
