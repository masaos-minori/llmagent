# Correct override-mode failure-behavior description in the MDQ/RAG boundary doc

## Priority
Medium

## Target files
- `docs/04_mcp_05_04_mdq-rag-boundary.md` (routing policy table, "ルーティング方針" section, row 3 of the availability-fallback table)

## Background
`docs/04_mcp_05_04_mdq-rag-boundary.md` documents an "オーバーライドモード" (override mode) for
choosing between MDQ and RAG tool routing, and includes a table row stating:

> オーバーライドモードで、強制指定したサーバーが利用不可 | エラーを返す
> (Override mode, forced server unavailable → returns error)

A prior chunk-level doc review flagged that it is unconfirmed whether a failure during
override-mode execution returns an error to the caller or falls back to different
behavior, and asked for this to be traced against actual code and tests.

## Problem
Investigation of the current codebase shows the doc's row is misleading about the
underlying mechanism, even though its stated end-user-visible outcome ("returns an
error") happens to be correct:

- There is no "override mode" code path that forces tool routing to a specific server
  and separately checks that server's availability. The only thing in code called an
  "override" is `resolve_mode()` in `scripts/agent/mdq_rag_classifier.py` (lines 45-52),
  which lets a configured `config_mode` (`mdq`/`rag`, not `auto`) take precedence over the
  query-heuristic classifier. This override only decides which one-line system-prompt
  hint (`_mode_hint`) is injected before an LLM turn, in
  `scripts/agent/mode_classification.py:classify_and_inject_mode()` (lines 47-70). It does
  not intercept, force, or wrap actual MCP tool execution, and it has no distinct
  "forced server unavailable" check of its own.
- Actual tool execution is a completely separate, mode-agnostic path: tool calls are
  routed purely by tool name via `ToolRouteResolver`/`RuntimeToolRegistry`
  (`scripts/shared/route_resolver.py`), invoked through
  `ToolTransportInvoker.invoke()` (`scripts/shared/tool_transport_invoker.py`,
  around lines 178-213). When the resolved server (e.g. rag-pipeline-mcp) fails
  mid-call, `invoke()` catches `TransportError` and converts it via
  `_record_transport_error()` (lines 149-168) into
  `ToolCallResult(is_error=True, error_type="transport", ...)`, which propagates
  unchanged through `execute_one_tool_call()`
  (`scripts/agent/tool_runner.py`, lines ~183-238) back to the caller as an error tool
  result. There is no fallback branch to MDQ, and no swallowing, anywhere in this chain
  — for any tool, whether or not a config-mode override was in effect.
- No test file (`tests/test_mode_classification.py`, `tests/test_mdq_rag_boundary.py`,
  `tests/test_route_resolver.py`, `tests/test_tool_runner.py`, or others found via search)
  asserts anything about an "override mode, forced server unavailable" scenario as a
  distinct case; `tests/test_mode_classification.py::test_config_override_takes_precedence_over_query_content`
  only tests hint-selection precedence, not tool-execution failure behavior.

## Reason for change
Callers implementing error handling around RAG calls need documentation that reflects
the real mechanism, not one that implies a dedicated "forced-routing + availability
check" code path exists when it does not. Leaving the current wording risks a reader
believing there is override-mode-specific failure logic to configure or rely on, when
the actual guarantee ("tool-call failures return an error, no fallback") is a generic
property of the tool-execution layer that applies uniformly, independent of mode.

## Implementation intent
Rewrite the affected table row (and any adjoining prose that refers to "override mode"
having its own failure/unavailability handling) in
`docs/04_mcp_05_04_mdq-rag-boundary.md` to state the confirmed, code-traced behavior
precisely, per `rules/coding.md`'s "Documentation notes — Current behavior
classification" guidance (this is a "Documentation fix required" case — the doc's
wording is inaccurate about the mechanism, not the code that's buggy). Do not change any
implementation behavior as part of this requirement.

## Implementation instructions
1. In `docs/04_mcp_05_04_mdq-rag-boundary.md`, under "ルーティング方針" → the availability
   fallback table (rows currently covering MDQ unavailable / RAG unavailable / override
   mode forced-server unavailable), revise the third row so it no longer implies a
   distinct "override mode" availability check exists. State instead, as confirmed fact:
   - "Override mode" (`config_mode` set to `mdq` or `rag` instead of `auto`) only changes
     which routing hint is injected into the system prompt before an LLM turn
     (`scripts/agent/mdq_rag_classifier.py:resolve_mode()`,
     `scripts/agent/mode_classification.py:classify_and_inject_mode()`); it does not
     force or wrap actual tool execution.
   - Any tool call — to rag-pipeline-mcp or any other MCP server, regardless of whether
     an override/config-mode was active — that fails mid-execution is surfaced as an
     error result to the caller (`ToolCallResult(is_error=True, error_type="transport")`
     via `scripts/shared/tool_transport_invoker.py`), with no fallback to a different
     server or mode anywhere in that path.
2. Ensure the row/prose no longer suggests "override mode" itself performs a pre-call
   availability check separate from generic tool-execution error handling; if the doc
   wants to keep a row about pre-call unavailability, phrase it as applying to the
   generic tool-routing layer rather than as an "override mode"-specific behavior.
3. Cite the specific code locations above (file + function/line range) inline or in a
   footnote if the doc's style elsewhere does so (check neighboring sections'
   convention before adding new citation style).
4. Do not mark this as an open "Needs Confirmation" item — the investigation is
   conclusive: mid-execution rag-pipeline-mcp failures return an error with no
   fallback, and this holds regardless of override/config-mode.
5. Do not modify `scripts/agent/mdq_rag_classifier.py`,
   `scripts/agent/mode_classification.py`, `scripts/shared/tool_transport_invoker.py`, or
   any other source file — this requirement is documentation-only.

## Acceptance criteria

  (b) a mid-execution failure of a tool call (including rag-pipeline-mcp) returns an
  error to the caller with no fallback, independent of override/config-mode.
- The doc no longer describes "override mode" as having its own dedicated
  forced-routing availability check distinct from generic tool-execution error
  handling.
- No source code, tests, or other `docs/*.md` files are modified.
