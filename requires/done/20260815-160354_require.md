# Replace UNKNOWN fallback with UNAVAILABLE in _resolve_health_state()

## Priority
Medium

## Target files
- scripts/agent/services/mcp_status.py
- scripts/shared/mcp_health.py

## Background
During adversarial review of the agent startup process, we traced the full startup sequence through factory.py → build_agent_context() → AgentContext assembly. The McpStatusService probes all MCP servers and formats status table, but _resolve_health_state() has a fallback to UNKNOWN when registry is None. This means that during startup/shutdown phases where the registry might not be fully initialized, the service will report UNKNOWN instead of a more informative state like "unavailable" or "initializing".

## Problem
When McpServerHealthRegistry is None (e.g., during startup or shutdown), _resolve_health_state() returns McpServerHealthState.UNKNOWN. UNKNOWN is semantically ambiguous — it does not distinguish between "the registry exists but cannot determine the state" and "the registry itself is unavailable". During initialization and teardown phases, this ambiguity causes the status table to display "UNKNOWN" for all servers, making it impossible to tell whether the problem is with individual servers or with the registry itself.

## Reason for change
The UNKNOWN state is intended for cases where the registry exists but cannot determine the state of a specific server. When the registry is None entirely, the correct semantic is that no server is available — UNAVAILABLE is the appropriate state.

## Implementation intent
Replace the UNKNOWN fallback in _resolve_health_state() with UNAVAILABLE when registry is None. No new states are needed; McpServerHealthState.UNAVAILABLE already exists and correctly expresses "no registry available".

## Implementation instructions
1. In `scripts/agent/services/mcp_status.py`, modify `_resolve_health_state()`:
   - Change line 52 from `return McpServerHealthState.UNKNOWN` to `return McpServerHealthState.UNAVAILABLE`
2. Update the docstring on line 49 from "falling back to UNKNOWN" to "falling back to UNAVAILABLE"
3. Verify no other callers depend on UNKNOWN being returned specifically for the None-registry case

## Acceptance criteria

- [ ] The new state clearly indicates the registry is unavailable rather than just unknown
