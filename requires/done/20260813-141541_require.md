# Resolve pyright `reportAttributeAccessIssue` on `git.exc.*` across GitPython call sites

## Priority
Low

## Target files
- `scripts/shared/git_helper.py`
- `scripts/mcp_servers/git/git_service.py`
- Any other file matching `rg "git\.exc\." scripts/` at implementation time (repo currently
  has exactly these two files; a fresh grep is still required before implementing, in case new
  call sites were added since this requirement was written)

## Background
`scripts/shared/git_helper.py` and `scripts/mcp_servers/git/git_service.py` both catch
GitPython exceptions via attribute access through the top-level `git` module
(`git.exc.InvalidGitRepositoryError`, `git.exc.GitError`) after doing a plain `import git`.
GitPython's installed package (`gitpython` 3.1.50, confirmed in `uv.lock`) ships `py.typed`
but does not declare `exc` as a typed attribute of the top-level `git` package — the
`git/__init__.py` module only does `from git.exc import (...)` for individual exception
classes, it never does `import git.exc` itself, so pyright has no static declaration that
`git.exc` is a valid attribute path on `git`.

## Problem
Running `uv run pyright scripts/shared/git_helper.py scripts/mcp_servers/git/git_service.py`
currently reports 3 `reportAttributeAccessIssue` errors, confirmed reproducing today
(2026-08-13):
- `scripts/shared/git_helper.py:56:16` — `except git.exc.InvalidGitRepositoryError:`
- `scripts/shared/git_helper.py:62:16` — `except git.exc.GitError as e:`
- `scripts/mcp_servers/git/git_service.py:65:20` — `_GIT_ERRORS = (git.exc.GitError, ...)`

No `types-GitPython`-style stub package is present in `pyproject.toml` or `uv.lock`. This is
a repeated pattern (same root cause at 2+ call sites), not an isolated typo, so it should be
fixed consistently rather than patched ad hoc.

## Reason for change
This is a pre-existing static-analysis gap noted during a prior behavior-preserving refactor
of `scripts/shared/git_helper.py` (2026-08-13) and deliberately deferred because the fix
touches more than one file and needed a single, consistent resolution. Leaving it unresolved
means every future `pyright` run on these files reports noise that masks genuinely new
errors, and any new call site added by copy-paste will silently inherit the same false
positive instead of a clean pattern to copy.

## Implementation intent
Root cause: `git/__init__.py` never executes `import git.exc` (only `from git.exc import X`),
so pyright cannot statically resolve `git.exc` as an attribute of the `git` module object,
even though it works fine at runtime. The fix is therefore an import-shape change at each call
site, not a stub or suppression:

- Replace the implicit access pattern with an explicit `import git.exc` (in addition to, or
  instead of, the existing `import git`) in each file that currently writes `git.exc.<Name>`.
  After this explicit import, pyright resolves `git.exc` directly rather than through
  attribute access on `git`, resolving the error without a stub dependency or a suppression.
- Do not change which exception classes are caught, their order, or any control flow —
  this is purely an import/reference-shape change.
- Only fall back to a `# type: ignore[reportAttributeAccessIssue]` (or
  `# type: ignore[attr-defined]` if mypy is the driving checker for that line) with an inline
  justification if the explicit `import git.exc` approach is verified not to resolve the
  pyright error at one or more sites — do not use it as the default resolution.
- Apply the same resolution shape at every call site found by `rg "git\.exc\." scripts/`; do
  not use a different technique per file.

## Implementation instructions
1. Run `rg "git\.exc\." scripts/` first to enumerate every call site (currently
   `scripts/shared/git_helper.py:56`, `scripts/shared/git_helper.py:62`, and
   `scripts/mcp_servers/git/git_service.py:65`) before making any change, in case new sites
   exist by the time this is implemented.
2. In `scripts/shared/git_helper.py`, the existing `import git` is a lazy, function-local
   import (line 39, guarded for optional gitpython availability) — add `import git.exc`
   alongside it (or replace the reference to import `git.exc` directly) so the two
   `except git.exc.*` clauses at lines 56 and 62 resolve.
3. In `scripts/mcp_servers/git/git_service.py`, `import git` is a top-level module import
   (line 19) — add `import git.exc` at the top level so line 65's
   `_GIT_ERRORS = (git.exc.GitError, OSError, ValueError)` resolves.
4. Re-run `uv run pyright scripts/shared/git_helper.py scripts/mcp_servers/git/git_service.py`
   and confirm 0 errors related to `git.exc`.
5. Re-run `uv run mypy scripts/shared/git_helper.py scripts/mcp_servers/git/git_service.py` to
   confirm no new mypy errors were introduced by the import change.
6. If the explicit-import approach does not fully resolve pyright's error at any site, add a
   `# type: ignore[reportAttributeAccessIssue]` there with an inline justification per
   `rules/coding.md`'s suppression-governance rule, and note in the commit/PR why the
   import-based fix did not work at that site.
