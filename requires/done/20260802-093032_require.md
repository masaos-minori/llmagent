## Problem
The `scripts/eventbus/` block in `docs/01_overview-files-06-misc.md` is a plain directory-tree
listing of 15 files with one-line Japanese descriptions each. It does not explain how a failed
message delivery is detected, how it is moved to the dead-letter queue, or how it can be
recovered/replayed. A reader must currently cross-reference multiple source files
(`ack_route.py`, `db.py`, `dlq.py`, `dlq_route.py`, `offsets.py`, `replay_route.py`) to
reconstruct this flow themselves.

## Reason for change
Documenting only filenames forces every reader who needs to understand delivery-failure
handling (e.g. for operations, incident response, or onboarding) to read the eventbus source
directly. A short recovery-flow description directly in the overview doc removes that burden
and matches the doc's purpose as a file-structure *and* behavior overview (the `conf.d/`
security-default annotations set this precedent already).

## Implementation intent
Keep the existing per-file directory tree (do not delete it — it still serves as a file-location
reference), and add a short prose paragraph immediately after it (or replace the flat one-line
comments with a paragraph, whichever reads better in context) that walks through the verified
failure -> DLQ -> recovery path in the actual code, correcting the source issue's simplified
description where it was inaccurate (see below).

## Implementation instructions
Verified flow (confirmed by direct source reading on 2026-08-02; use these exact mechanics,
not the issue's shorthand, since the issue's "DLQ -> replay via replay_route.py" phrasing is an
oversimplification):

1. **Failure detection**: when a subscriber nacks an event, `ack_route.py` calls into
   `db.py`'s failure-count update, which increments `delivery_failure_count` for that
   `event_id` (`UPDATE events SET delivery_failure_count = delivery_failure_count + 1 ...`).
2. **Promotion to DLQ**: `dlq.py`'s `promote_to_dlq()` selects events whose
   `delivery_failure_count >= max_retry` (and not yet in the DLQ, i.e. `dlq_at IS NULL`),
   marks them with a `dlq_at` timestamp, and writes a `DlqEventRecord` for each.
3. **DLQ inspection and recovery — this is the corrected part**: the DLQ is inspected and
   recovered via `dlq_route.py`'s two endpoints, **not** `replay_route.py`:
   - `dlq_list` (paginated `GET`) lists dead-lettered events (`count_dlq` / `fetch_dlq` in
     `db.py`).
   - `dlq_requeue` (`POST`, by `event_id`) calls `requeue_event()` in `db.py` to put a
     dead-lettered event back into the active queue; it returns 409 if the event exists but
     is not currently in the DLQ, and 404 if the event does not exist at all.
4. **Separate mechanism — consumer replay/catch-up**: `offsets.py` persists each consumer's
   last-committed sequence offset to disk (`read_offset` / `write_offset`), and
   `replay_route.py`'s `replay` endpoint streams (SSE or JSON) all events with
   `seq > since_seq`. This is a general consumer catch-up/replay-from-offset mechanism for
   any consumer reconnecting or resuming — it is not DLQ-specific and is not how
   dead-lettered events are recovered.
5. Write a short paragraph (a few sentences, in the doc's existing Japanese style, consistent
   with the rest of the section) capturing points 1-4 above, placed after the eventbus file
   tree in `docs/01_overview-files-06-misc.md`. Keep the file tree itself intact as a
   file-location reference; the new paragraph supplements it rather than replacing the whole
   list.
6. Do not modify `conf.d/`-related content in this pass — it is already correct as of commit
   `f680273e0` and out of scope for this requirement.
7. Do not modify any eventbus source code (`scripts/eventbus/*.py`) — per AGENTS.md Global
   Rule 8, no eventbus-related code implementation is in scope here; this is a documentation
   change only.
