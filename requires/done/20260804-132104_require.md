# Fix: RAG consistency check swallows exception details with no log trace

## Priority
Medium

## Target files
- `scripts/agent/startup.py` (`StartupOrchestrator._check_services()`, RAG consistency check block, lines 348-359)

## Background
`StartupOrchestrator._check_services()` (`scripts/agent/startup.py:271-371`) runs six startup
checks in sequence (security_audit, readiness, mcp_tool_discovery, routing_drift,
routing_safety_tiers, rag_consistency), each wrapped in its own `try`/`except`. The RAG
consistency check (lines 348-359) currently reads:

```python
# 6. RAG consistency
try:
    rag_check = RagMaintenanceService().consistency()
    if rag_check.is_consistent:
        pipeline.add_ok("rag_consistency")
    else:
        for issue in rag_check.issues:
            pipeline.add_warning(
                "rag_consistency", f"[RAG] Consistency issue: {issue}"
            )
except Exception:  # noqa: BLE001
    pipeline.add_skipped("rag_consistency", "RAG consistency check skipped")
```

The other five `except` blocks in the same method all bind the caught exception to a name
(`as exc`) and interpolate its string representation into the message passed to
`pipeline.add_fatal(...)` / `pipeline.add_warning(...)`, e.g.:

```python
except Exception as exc:  # noqa: BLE001
    pipeline.add_fatal("readiness", f"Readiness check failed: {exc}")
```
```python
except Exception as exc:  # noqa: BLE001
    pipeline.add_warning("routing_drift", f"Routing drift check failed: {exc}")
```

The RAG block is the only one of the six that does not bind the exception (`except Exception:`,
no `as exc`) and produces a fixed string, `"RAG consistency check skipped"`, with zero information
about what failed.

## Problem
Verified against current source (`scripts/agent/startup.py:348-359`): when
`RagMaintenanceService().consistency()` raises, the exception is caught, discarded, and replaced
with a hardcoded message via `pipeline.add_skipped("rag_consistency", "RAG consistency check
skipped")`. No exception class name, message, or traceback is captured anywhere.

Precise verification of the downstream path also confirms the asymmetry is real, though the
mechanism differs slightly from a plain "other blocks call `logger.*` directly" description:
- None of the six `except` blocks in `_check_services()` call `logger.warning`/`logger.error`
  directly at the point of catching. Instead, they pass a message (with or without `{exc}`
  interpolated) to `pipeline.add_fatal(...)` / `add_warning(...)` / `add_skipped(...)`.
- `_display_pipeline_results()` (`scripts/agent/startup.py:373-383`) prints every WARNING/FATAL/
  SKIPPED outcome's message to the console via `self._view.write_warning(...)` /
  `write_fatal(...)`, which are thin `print(...)` wrappers (`scripts/agent/cli_view.py:185-191`) —
  not routed to the log file.
- Only outcomes that escalate to FATAL are additionally written to the log file, via
  `logger.error("FATAL pipeline outcomes: %s", ...)` at `scripts/agent/startup.py:367-370`, and
  only if `pipeline.has_fatal` is true.
- `_report_readiness()`'s final `logger.info("Readiness summary: %s", ...)` call
  (`scripts/agent/startup.py:513`) logs only aggregate pass/fail/warning *counts* per check name,
  never the individual exception messages.

The net effect: for every other check, if its exception is caught and turned into a FATAL outcome
(readiness, mcp_tool_discovery, security_audit's `RuntimeError` path), the exception text reaches
the log file via the aggregated FATAL log line. Even for the two blocks that only ever produce a
WARNING on exception (routing_drift, routing_safety_tiers), the exception text at least reaches
the console output and is visible to whoever is watching startup. For RAG consistency, the
exception is caught by `except Exception:` (unbound) and only ever produces a SKIPPED outcome with
a hardcoded string — so there is no path, in the log file or on the console, by which the actual
exception (DB corruption, schema mismatch, permission error, unexpected bug, etc.) becomes visible
to an operator. This matches `rules/coding.md`'s "Suppression governance" concern about swallowed
errors: the broad `except Exception:` itself is an intentional, acceptable design choice (per the
issue's own constraint), but discarding the exception's content entirely is not.

## Reason for change
When `RagMaintenanceService().consistency()` fails at startup for any reason, the current code
guarantees the operator learns nothing about the cause beyond "RAG consistency check skipped."
Diagnosing an actual failure (corrupted SQLite DB, missing permissions, schema drift, an
unanticipated bug in the maintenance service) currently requires reproducing the failure under a
debugger, since neither the startup log file nor the console output retains any exception detail.
Every sibling check in the same method retains at least the exception's string form somewhere
visible; RAG consistency should not be a silent outlier.

## Implementation intent
Bind the caught exception (`except Exception as exc:`) and include its content in both the log
output and the `pipeline.add_skipped(...)` message, bringing this block in line with the pattern
already used by the other five checks in `_check_services()`. Keep the broad `except Exception`
catch itself unchanged — do not narrow it — since it is a deliberate choice to avoid aborting the
whole startup sequence over a non-critical maintenance check.

## Implementation instructions
1. In `scripts/agent/startup.py`, change the RAG consistency `except` clause (line 358) from
   `except Exception:  # noqa: BLE001` to `except Exception as exc:  # noqa: BLE001 — ...`, adding
   an inline justification per `rules/coding.md`'s Suppression governance rule explaining why the
   broad `except Exception` is intentionally retained here (e.g. a non-critical maintenance check
   must not abort startup).
2. Add a `logger.warning(...)` (or `logger.error(...)`, at the author's discretion — the issue
   accepts either depending on assessed severity) call inside the `except` block that logs the
   exception, e.g. `logger.warning("RAG consistency check failed: %s", exc)`, using `%s`-style
   lazy formatting consistent with other `logger.*` calls in this file.
3. Update the `pipeline.add_skipped(...)` call to include a concise reference to `exc` in its
   message string, e.g. `pipeline.add_skipped("rag_consistency", f"RAG consistency check skipped:
   {exc}")`, so the failure reason is also visible via the console output path
   (`_display_pipeline_results()` → `write_warning(...)`), consistent with how the other WARNING/
   FATAL outcomes in this method surface their exception text.
4. Do not change the exception type caught (keep the broad `Exception`), do not change control
   flow (the check must remain non-fatal — `add_skipped`, not `add_fatal`), and do not modify
   `RagMaintenanceService.consistency()` itself or any other check in `_check_services()`.

## Acceptance criteria
