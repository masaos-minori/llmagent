# Use RuntimeToolRegistry for LLM-facing tool definitions

## Priority
Medium

## Target files
- `scripts/agent/llm_turn_runner.py` — `_filter_disabled_tool_definitions()` and its call site in `_stream_llm()`
- `scripts/shared/runtime_tool_registry.py` — `RuntimeToolRegistry.llm_tool_definitions()`

## Background
Discovered while running the requirement-to-plan workflow for `requires/20260813-140801_require.md`, during the audit of every remaining `ctx.cfg.tool.tool_definitions` reference under `scripts/agent/`. The sibling requirements' acceptance criteria and implementation instructions are scoped to the call-execution path (`_validate_tool_args()`, `_build_tool_meta()`, approval ordering) and do not mention `llm_turn_runner.py`'s tool-list construction.

## Problem
- `_filter_disabled_tool_definitions()` sources `tool_definitions` from `ctx.cfg.tool.tool_definitions` (static config list) and only removes entries whose name is known to the registry but not currently `enabled_for_llm`. It does not add or correct anything from the registry; the base content (schema, description) for every tool still comes from the static config list.
- If a tool is registered live (via `/v1/tools` discovery) but was never added to `ctx.cfg.tool.tool_definitions` (or the static entry has a stale/incorrect schema), the LLM either never sees that tool as callable, or sees a schema that has drifted from what `RuntimeToolRegistry`/`RuntimeTool.input_schema` actually validates against at call time — a second source of truth for tool shape, parallel to the one the sibling requirements are removing for tool execution.
- `RuntimeToolRegistry.llm_tool_definitions()` already exists and returns the correct LLM-facing shape derived from live discovery, but is currently used only as a name-visibility filter, not as the source of tool content.

## Reason for change
Once the execution path treats `RuntimeToolRegistry` as the sole runtime authority for tool metadata, leaving the LLM-payload construction on a separate static source undermines that guarantee in a way that's easy to miss: a reader auditing `ctx.cfg.tool.tool_definitions` usages after those requirements ship could reasonably (and incorrectly) conclude the field is fully inert at runtime, when it is still load-bearing for what tools the LLM is told it can call.

## Implementation intent
Change `_filter_disabled_tool_definitions()` (or its call site) to build the LLM payload directly from `registry.llm_tool_definitions()` when the registry is available, keeping `ctx.cfg.tool.tool_definitions` only as the fallback for the case the registry is `None`/empty (mirroring the existing early-return in `_filter_disabled_tool_definitions()` when `registry is None`).

## Implementation instructions
1. In `_filter_disabled_tool_definitions()`, when `registry is not None`, use `registry.llm_tool_definitions()` as the base list instead of `tool_definitions` parameter.
2. Keep the existing early-return path when `registry is None` (falls back to `ctx.cfg.tool.tool_definitions`).
3. Remove the `known_names` intersection logic — since the base list now comes from the registry, all entries are already valid tool names. Only keep the `visible_names` filter to exclude tools marked `enabled_for_llm=False`.
4. Simplify the loop: iterate over `registry.llm_tool_definitions()` directly, keeping only entries whose `name` is in `visible_names`.
5. Update the call site in `_stream_llm()` to pass only `registry` (remove `ctx.cfg.tool.tool_definitions` argument).
6. Add a regression test asserting that a tool present in `RuntimeToolRegistry` but absent from `ctx.cfg.tool.tool_definitions` is still offered to the LLM once this is fixed (currently it would not be, since the static list is the starting point).
7. Scope this as its own requirement/plan — it changes what tools the LLM is offered mid-session, which is a user-visible behavior change distinct from the fail-closed execution-path work.

## Acceptance criteria
- `_filter_disabled_tool_definitions()` no longer takes `tool_definitions: list[dict[str, Any]]` as a parameter sourced from `ctx.cfg.tool.tool_definitions`.
- When `registry is not None`, the LLM payload is built entirely from `registry.llm_tool_definitions()`.
- When `registry is None`, the fallback to `ctx.cfg.tool.tool_definitions` is preserved.
- A tool registered live via `/v1/tools` discovery but absent from `ctx.cfg.tool.tool_definitions` appears in the LLM payload.
- The `known_names` intersection logic is removed — all entries from `registry.llm_tool_definitions()` are valid tool names.
- Existing tests pass; new regression test covers the live-registered-tool scenario.

## Tests
- Regression test: tool present in `RuntimeToolRegistry` but absent from `ctx.cfg.tool.tool_definitions` is offered to the LLM.
- Verify `_filter_disabled_tool_definitions()` returns correct shape from `registry.llm_tool_definitions()` when registry is available.
- Verify fallback behavior when registry is `None`.
