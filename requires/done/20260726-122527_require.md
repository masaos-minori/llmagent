**FAIL-2 does not match current reality and is corrected below.** The original claim was
"1 failed test (schema_version missing) in `test_mcp_tool_discovery.py`, caused by
`rag_pipeline_server.py` missing `schema_version` from `/v1/tools`." Verification found:
- `schema_version` does not appear anywhere in `scripts/mcp_servers/rag_pipeline/
  rag_pipeline_server.py` — this specific claim cannot be corroborated as a live issue
  and appears to have referred to a since-changed or since-fixed code path.
- Running the test file at its current path
  (`tests/agent/services/test_mcp_tool_discovery.py`) today shows **2 different**
  failures, both in `TestDiscoverAllUnreachableServers`:
  `test_non_200_status_marks_server_unreachable` and
  `test_invalid_json_body_marks_server_unreachable`. Root cause (traced in this review):
  the `_make_ctx()` test helper (line 65-75) builds `ctx = MagicMock()` and only
  explicitly sets `ctx.cfg.mcp.mcp_servers` and `ctx.cfg.mcp.security_profile`. It never
  sets `ctx.cfg.tool.tool_definitions_strict`. `McpToolDiscoveryService._is_strict()`
  calls `getattr(self._ctx.cfg.tool, "tool_definitions_strict", False)` — but because
  `ctx.cfg.tool` is itself a `MagicMock`, accessing `.tool_definitions_strict` on it
  auto-vivifies a new `MagicMock` rather than raising `AttributeError`, so `getattr`'s
  `False` default is never used. `bool(MagicMock())` evaluates to `True`, so
  `_is_strict()` returns `True` for every test using `_make_ctx()`'s default, which makes
  `_is_fatal_severity()` also `True`, which escalates the `tool_definitions`-related
  finding from `WARNING` to `FATAL` — exactly the two assertions these two tests make
  and fail on. This is a test-fixture gap, not a production code defect.

## Problem

`tests/agent/services/test_mcp_tool_discovery.py::_make_ctx()` does not configure
`ctx.cfg.tool.tool_definitions_strict`, so every test built via this helper silently runs
with `_is_strict() == True` (via `MagicMock` auto-vivification + truthy `bool()`) instead
of the intended default-off strict mode. Two tests in `TestDiscoverAllUnreachableServers`
assert `WARNING`-severity behavior that only holds when `_is_strict()` is `False`, so they
fail under the fixture's actual (accidental) `True` value.

## Reason for Change

An accidentally-strict test fixture silently changes the severity-escalation behavior
under test for every test built via `_make_ctx()`, not just the 2 that currently fail —
any future test asserting WARNING-vs-FATAL behavior through this helper is at risk of the
same silent flip. Fixing the fixture once removes the risk for the whole file, not just
the 2 known failures.

## Implementation Intent

Add an explicit `ctx.cfg.tool.tool_definitions_strict = False` (or a `strict` parameter to
`_make_ctx()`, defaulting to `False`) to the helper, matching how it already parametrizes
`security_profile`.

## Implementation Instructions

1. In `tests/agent/services/test_mcp_tool_discovery.py::_make_ctx()`, add a
   `tool_definitions_strict: bool = False` parameter and set
   `ctx.cfg.tool.tool_definitions_strict = tool_definitions_strict` inside the function
   body, mirroring the existing `security_profile` parameter.
2. Re-run the full file: `uv run pytest tests/agent/services/test_mcp_tool_discovery.py -v`
   — confirm the 2 previously-failing tests now pass and no other test in the file
   regresses (i.e., no test in the file was relying on the accidental `True` default).
3. If any other test in the file turns out to depend on the accidental `strict=True`
   default, pass `tool_definitions_strict=True` explicitly at that call site rather than
   changing the helper's default back — the default should reflect the common case
   (default AgentContext config, not strict mode).
