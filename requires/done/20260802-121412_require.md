# Simplify startup/health-check command listing in docs/02_deployment-part1.md §2.3

## Priority
Low

## Target files
- `docs/02_deployment-part1.md` (§2.3 "Registering and starting LLM services", currently the
  code block at lines ~113-119, within the section spanning lines ~102-124)
- A operations runbook location to receive the relocated commands (none currently exists as a
  general-purpose destination — see Background)

## Background
`docs/02_deployment-part1.md` §2.3 is a deployment/design narrative section. Verified against
current content (read 2026-08-02): the section still contains a verbatim command block:

```bash
bash deploy/setup_services.sh

curl -s http://127.0.0.1:8081/health   # embed-llm
curl -s http://127.0.0.1:8080/health   # agent-llm

bash deploy/start_agent.sh
```

This matches the issue's description exactly (the issue's cited line range, ~133-140, is
slightly off from the current file's actual line numbers, ~113-119, but the content and
substance are unchanged — the issue is not obsolete). The prose immediately above the block
already explains the purpose of `setup_services.sh` (workflow pre-flight checks), but the
curl health-check commands and the two `bash` invocations are listed verbatim with no
accompanying statement of *why* health-check verification happens at this point in the
sequence.

A repository search for an existing "operations runbook" (運用Runbook) found none. The only
runbook-like content is:
- `docs/05_agent_10_04_operations-and-observability-validation-and-troubleshooting-part1.md`
  §"Workflow Deployment Runbook" — scoped narrowly to workflow-definition/schema validation
  failure modes and recovery commands (missing `default.json`, invalid JSON, schema version
  mismatch, etc.). It does not cover general service startup or health-check verification and
  is not a natural fit for this content.
- `implementations/done/20260710-155645_operator_workflow_deployment_runbook.md` — a completed
  implementation-procedure document under `implementations/done/`, i.e. a historical planning
  artifact, not a live user-facing runbook.

This is consistent with the related issue `deploy_simplify_os_provisioning_steps` (already
processed; see `requires/20260802-121203_require.md`), which independently found no existing
OS-provisioning/setup runbook either. That sibling requirement proposes creating a new
provisioning runbook for one-time OS/build setup content. This issue's content is different in
kind — it is an operational verification step performed after every service (re)start, not a
one-time provisioning step — so it may or may not belong in the same destination document as
the sibling requirement's provisioning runbook. This requirement does not mandate reusing that
same file; it leaves the choice (new dedicated operations runbook vs. extending an existing
runbook-like doc) to the next phase, since no ready-made destination currently exists for
either.

## Problem
Verbatim startup and health-check commands are embedded inline in a deployment *design*
document. This buries the design intent (why health-check verification happens at this point
in the startup sequence, and what it is meant to confirm) under command-line detail that is
runbook-level content: it changes independently of design intent (ports, endpoints, exact
invocation syntax may change) and, left in two places, creates a second location that must be
kept in sync.

## Reason for change
Keeping command-level detail in the design narrative forces every future command change (e.g.
a health-check port change) to touch a design document instead of an operations runbook, and
increases the risk that the design document silently goes stale relative to the ports/commands
actually in use.

## Implementation intent
- Replace the verbatim command block in `docs/02_deployment-part1.md` §2.3 with a prose
  statement of the health-check step's purpose and target (per the issue's proposed wording:
  "サービス起動後、embed-llm/agent-llmそれぞれについてヘルスチェックエンドポイントへの疎通を
  確認する。具体的なコマンド例は運用Runbookを参照。"), keeping the design-relevant surrounding
  prose (the "Workflow pre-flight responsibilities" bullet list) untouched.
- Relocate the exact command examples (the `bash deploy/setup_services.sh` /
  `curl -s http://127.0.0.1:8081/health` / `curl -s http://127.0.0.1:8080/health` /
  `bash deploy/start_agent.sh` sequence) to an operations runbook, identifying or creating the
  appropriate destination — do not lose the exact commands in the process.
- Do not change the actual startup/health-check procedure, ports, or endpoints — this is a
  documentation relocation only.
