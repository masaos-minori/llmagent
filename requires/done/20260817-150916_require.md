# Clarify 0-vs-missing semantics for `browser_*` config fields in `web_search_models.py`

## Priority
Low

## Target files
- `scripts/mcp_servers/web_search/web_search_models.py` (`WebSearchConfig.from_dict`, `browser_max_response_kb`, `browser_timeout_sec` fields)

## Background
`scripts/mcp_servers/web_search/web_search_models.py`'s `WebSearchConfig.from_dict` parses `browser_max_response_kb`/`browser_timeout_sec` (and similar) via an `int(d.get(key) or default)` idiom. Because `0` is falsy in Python, a TOML value of `browser_max_response_kb = 0` would silently fall back to the default (e.g. 256) rather than being treated as an explicit, intentional zero.

## Problem
`0` is falsy in Python, so `d.get(key) or default` treats `0` the same as `None` — both fall back to the default. This means an explicit `browser_max_response_kb = 0` in TOML is silently ignored and replaced with the default value.

## Reason for change
Correctness: ensure that explicit `0` values in TOML configs are honored as intended overrides, not silently converted to defaults. This is a real behavior change visible to ops/TOML authors.

## Implementation intent
Decide whether `0` should be treated as a valid, explicit override (requiring `d.get(key) is None` rather than falsy-check) or whether `0` is genuinely never a sensible value for these fields (in which case the current behavior may be intentional and this issue can be closed as "no action"). If changing: replace the `or default` idiom with an explicit `is None` check for these two fields specifically (do not blanket-change every `or default` usage in this file without the same per-field review).

## Implementation instructions
### Phase 1: Investigate downstream impact
1. Check how `browser_max_response_kb=0`/`browser_timeout_sec=0` would behave downstream in `search_provider.py`'s `fetch_browser` before deciding whether `0` is a meaningful override.
2. Determine whether `timeout_sec=0` means "no timeout" or "instant timeout" in the consuming code.

### Phase 2: Decide and implement
**Option A: Honor `0` as explicit override (recommended)**
1. Change `int(d.get(key) or default)` to `int(d.get(key)) if d.get(key) is not None else default` for the affected fields only.
2. Add a characterization test asserting `browser_max_response_kb: 0` in the source dict produces `0` in the resulting config, not the default.

**Option B: Leave as-is (if `0` is genuinely never a sensible value)**
1. Close this issue as "no action, confirmed intentional."
2. Document why `0` is intentionally mapped to the default.

## Acceptance criteria
Either:
- Explicit `0` values for the affected fields are honored as `0` (code changed, new test added); or
- The current behavior is confirmed intentional and documented, with no code change.
- All other `WebSearchConfig` fields' current fallback behavior is unchanged.
