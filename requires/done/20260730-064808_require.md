# Require: Consolidate workflow task status ownership in WorkflowEngine

## Priority

High

## Target files

- `scripts/agent/orchestrator.py`
- `scripts/agent/workflow/workflow_engine.py`
- `scripts/agent/workflow/state_store.py`
- `scripts/agent/workflow/approval_ops.py`
- `scripts/agent/commands/cmd_workflow.py`
- `scripts/agent/startup.py`
- `scripts/agent/context.py`

## Background

`WorkflowEngine.run()` updates task status during workflow execution, marking tasks as `running`, `completed`, `failed`, `halted`, or `pending_approval`. The orchestrator currently also updates task status in a `finally` block based on `error_kind`, creating duplicate status ownership.

## Problem

Duplicate task status ownership can corrupt workflow state:

- `WorkflowEngine` sets task status to `pending_approval`, then the orchestrator `finally` block overwrites it as `completed`.
- `WorkflowEngine` sets task status to `halted`, then the orchestrator overwrites it as `failed` or `completed`.

This makes workflow recovery, audit, and approval handling unreliable.

## Reason for change

Make `WorkflowEngine` the single owner of workflow task status transitions. The orchestrator may read workflow status but should not unconditionally write final task status.

## Implementation intent

### 1. Remove unconditional task status update from orchestrator

Remove or significantly restrict logic similar to:

    if error_kind is not None:
        store.update_task_status(task.task_id, "failed")
    else:
        store.update_task_status(task.task_id, "completed")

### 2. If a fallback update is required, guard it by current status

If the status must be corrected defensively, only update when the current status is still transitional.

Allowed transitional states: `pending`, `running`

Do not overwrite terminal or suspended states: `pending_approval`, `completed`, `failed`, `halted`

### 3. Treat workflow.sqlite as the source of truth

Approval-related state should be derived from workflow storage:

- `tasks.status = pending_approval`
- `approvals.status = pending`

In-memory fields such as `ctx.workflow.approval_pending` should be treated as cache or display state only.

### 4. Synchronize ctx state from DB when needed

When blocking a turn due to pending approval, prefer checking workflow storage or a StateStore query. If both DB state and in-memory state exist, DB state wins.

## Acceptance criteria

- [ ] The orchestrator no longer overwrites `pending_approval`
- [ ] The orchestrator no longer overwrites `halted`
- [ ] Workflow task status transition ownership is documented as belonging to `WorkflowEngine`
- [ ] Pending approval detection uses workflow storage as the source of truth
- [ ] In-memory approval state is treated as derived/cache state
- [ ] `/approve` and `/reject` keep DB and context state synchronized
- [ ] Restart recovery can identify pending approvals from workflow storage

## Tests

- Workflow pending approval is not overwritten as completed
- Workflow halted task is not overwritten as completed
- Workflow failed task remains failed
- Normal completed task is marked completed by `WorkflowEngine`
- Pending approval survives process restart
- DB state wins over stale `ctx.workflow.approval_pending`
