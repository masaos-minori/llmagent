# Improve LifecycleState transition error messages with valid targets

## Priority
Low

## Target files
- scripts/agent/lifecycle.py

## Background
During adversarial review of the agent startup process, we traced the full lifecycle management flow through lifecycle.py. The LifecycleState transitions from STARTING → RUNNING/FAILED/STOPPED with valid transition guards. However, there's no evidence of comprehensive error handling for edge cases where an invalid transition might occur due to race conditions or unexpected state changes.

## Problem
The current `assert_valid_transition()` function raises a `ValueError` with the message `"Invalid lifecycle transition: {from_state!r} -> {to_state!r}"`. This is insufficient for debugging because:

1. **No valid targets listed**: The error message doesn't indicate what states ARE valid from the source state, making it hard to understand why the transition failed
2. **Ambiguous root cause**: Without knowing valid transitions, developers must look up the enum documentation to understand what went wrong
3. **Debugging friction**: In production environments, operators need immediate visibility into what's expected

For example, if a developer sees `"Invalid lifecycle transition: <LifecycleState.FAILED: 'failed'> -> <LifecycleState.RUNNING: 'running'>"`, they can't immediately tell whether RUNNING is a valid target from FAILED without consulting the enum docstring.

## Reason for change
Including valid target states in the error message would make debugging faster and reduce the cognitive load required to understand transition failures.

## Implementation intent
Modify `assert_valid_transition()` to include the list of valid target states in the error message. For example:
```python
raise ValueError(
    f"Invalid lifecycle transition: {from_state!r} -> {to_state!r}. "
    f"Valid targets from {from_state!r}: {', '.join(t.name for t in valid_targets)}"
)
```

## Implementation instructions
1. Modify `assert_valid_transition()` in `lifecycle.py` to include valid target states in the error message
2. Use the existing `_VALID_TRANSITIONS` dictionary to extract valid targets
3. Format the valid targets as readable names (e.g., "STARTING, FAILED") rather than enum values
4. Keep the original error format intact for backward compatibility
