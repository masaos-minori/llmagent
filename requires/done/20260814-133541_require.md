# Define grace-period duration for LlmTransportErrorHandler.resolve_retryable deprecation

## Priority
Medium

## Target files
- `scripts/shared/llm_transport_errors.py` — `LlmTransportErrorHandler.resolve_retryable()`
- `tests/shared/test_llm_transport_errors.py` — `TestResolveRetryable` test class
- `rules/coding.md` — optionally add repo-wide deprecation policy

## Background
`requires/done/20260813-172533_require.md` (implementation intent, sub-task 1) directs adding a `DeprecationWarning` to `LlmTransportErrorHandler.resolve_retryable` in `scripts/shared/llm_transport_errors.py` "for a grace period" before outright removal "in a later change." The requirement does not state how long that grace period is, nor what event (elapsed time, a release tag, a second explicit sign-off) triggers the follow-up removal change. Without a defined trigger, the deprecated method plus its dedicated `TestResolveRetryable` test class in `tests/shared/test_llm_transport_errors.py` could be left in the "warns but still present" state indefinitely, which is exactly the kind of stale-dead-code state this requirement was raised to eliminate.

No repository-wide policy document (`rules/coding.md`, `rules/toolchain.md`) defines a standard deprecation-to-removal interval (e.g., "one release", "30 days", "next major version").

## Problem
The grace period for deprecating `LlmTransportErrorHandler.resolve_retryable` lacks a defined duration or trigger condition. Without this, the deprecated method and its test class could remain indefinitely after the warning is added.

## Reason for change
To ensure the deprecation follows through to removal within a predictable timeframe, preventing stale-dead-code accumulation.

## Implementation intent
When implementing sub-task 1 (adding the `DeprecationWarning`), define a concrete removal trigger — e.g., "remove once this warning has shipped in one deploy cycle with zero new callers appearing in `rg` checks" — and record that decision either as a code comment near the `warnings.warn` call or as a follow-up issue with a target date/condition.

Recommended approach: adopt a repo-wide default ("deprecated symbols are removed the next time `plans/` touches the same file for an unrelated reason, provided a zero-caller `rg` re-check still holds") and document it in `rules/coding.md`. This avoids ad-hoc decisions per deprecation and ensures consistency across all future deprecations.

## Implementation instructions
1. Add `DeprecationWarning` to `LlmTransportErrorHandler.resolve_retryable()` per the existing requirement.
2. In the same change, add a code comment near the `warnings.warn` call specifying the removal trigger using the repo-wide default: "Remove this method the next time `plans/` touches this file for an unrelated reason, provided a zero-caller `rg` re-check still holds."
3. Update `rules/coding.md` with the standard deprecation-to-removal interval if not already documented.
4. Create a follow-up issue or plan entry tracking the removal with the defined trigger condition.

## Acceptance criteria
- `DeprecationWarning` is emitted when `resolve_retryable` is called.
- A concrete removal trigger is documented (either as a code comment or separate issue).
- The trigger is actionable and verifiable (e.g., "zero new callers after one deploy cycle").
- No regression in existing behavior — the method still functions while emitting the warning.

## Tests
- Verify `DeprecationWarning` is emitted when `resolve_retryable` is called.
- Existing `TestResolveRetryable` tests continue to pass (method remains callable during grace period).
- Confirm zero new callers via `rg` check at the time of removal.
