# Document the confirmed reload/restart requirement for RuntimeToolRegistry availability state in docs/04_mcp_03_06

## Priority
Medium

## Target files
- `docs/04_mcp_03_06_tool-runtime-availability-metadata.md` (primary — add confirmed finding)
- Cross-reference only (no edit expected): `docs/04_mcp_06_17_local-to-production-auth-migration.md`

## Background
`docs/04_mcp_03_06_tool-runtime-availability-metadata.md` documents the `/v1/tools` endpoint and
the `config_dependent` / `enabled` / `disabled_reason` runtime-availability model, and states that
`/v1/tools` is the primary source used to construct `RuntimeToolRegistry`. It further says: "Any
changes to tool availability (e.g., due to health degradation, config reload) will be reflected in
subsequent `/v1/tools` responses and will cause `RuntimeToolRegistry` to be updated accordingly."
This sentence implies a live-updating path that source inspection shows does not exist.

Separately, `docs/04_mcp_06_17_local-to-production-auth-migration.md` §"`/reload`とフル再起動の違い"
already documents that `/reload` never modifies `[mcp_servers.*]` connection definitions (URL, auth
token, transport, command, env) — a full agent process restart is required for those. That
constraint is scoped narrowly to MCP server *connection* definitions, not to
`RuntimeToolRegistry`'s `enabled`/`disabled_reason` availability snapshot, which is a distinct
mechanism covered only in 03_06.

## Problem
03_06 does not state whether editing `config/agent.toml` (or per-server config such as
`config/file_read_mcp_server.toml`, `config/git_mcp_server.toml`) and then running `/reload`
actually rebuilds `RuntimeToolRegistry`'s availability state, or whether a full process restart is
required. Source investigation (read-only, this cycle) confirms the actual behavior:

- `/reload` is handled by `_ConfigMixin._cmd_reload()` in
  `scripts/agent/commands/cmd_config.py:37`, which calls `ConfigLoader().load_all()` then
  `ConfigReloadService(ctx).apply_config_dict(new_cfg)`
  (`scripts/agent/services/config_reload.py:113`).
- The only touchpoint `apply_config_dict` has with `RuntimeToolRegistry` is calling
  `runtime_tools.apply_policy(tier_map, allowed_tools)` (`config_reload.py:195-202`).
  `RuntimeToolRegistry.apply_policy()` (`scripts/shared/runtime_tool_registry.py:168-195`) only
  re-derives `agent_safety_tier`, `requires_approval`, and re-ANDs `enabled_for_llm` using
  `tool_safety_tiers`/`allowed_tools` from `[approval]`/`[tool]` in `agent.toml`. It never touches
  `raw_definition`, `disabled_reason`, or `status`, and never calls `discover_all()` or re-fetches
  `/v1/tools`.
- `RuntimeToolRegistry` is populated exactly once, via
  `McpToolDiscoveryService(ctx).discover_all()` at `scripts/agent/startup.py:329-333` —
  startup-only; this is never invoked from `/reload`.
- Per-server availability-driving config (`allowed_dirs`, `read_only`, `command_allowlist`, etc.)
  lives in separate per-server TOML files (e.g. `config/file_read_mcp_server.toml`,
  `config/git_mcp_server.toml`), not in `agent.toml`. Each server loads its own config once into a
  module-level `_cfg` at process start (e.g. `FileReadConfig.load()` in `read_server.py:71`,
  `GitConfig.load()` in `git_server.py:49`); no reload/watch mechanism for these was found
  (`grep -rl reload scripts/mcp_servers/` returned nothing relevant).

Conclusion: `/reload` does **not** rebuild or refresh `RuntimeToolRegistry`'s `enabled` /
`disabled_reason` availability snapshot under any condition. It only patches
tier/allowlist-derived fields (`agent_safety_tier`, `requires_approval`, `enabled_for_llm`'s
policy-AND) on already-registered `RuntimeTool` objects in place. Reflecting any change to tool
availability metadata in `RuntimeToolRegistry` — whether the change originates from `agent.toml`
policy fields or from a per-server config file — requires a full agent process restart (so that
`discover_all()` re-runs). Picking up an MCP server's own `allowed_dirs`/`read_only`/etc. change
additionally requires restarting that server process, since its `_cfg` is also fixed at import
time with no hot-reload path.

## Reason for change
03_06's current wording ("will cause `RuntimeToolRegistry` to be updated accordingly") reads as an
assertion of live-updating behavior that does not match the source. An operator who edits config
and runs `/reload` expecting the availability snapshot (`enabled`/`disabled_reason`,
`/mcp status`'s `DISABLED_REASON` column) to refresh would be operating on stale state without
realizing it — a real operational risk. This is the same category of risk 06_17 already documents
for `[mcp_servers.*]` changes, but 03_06 currently makes no equivalent statement for
`RuntimeToolRegistry`'s own availability-metadata rebuild, and its existing sentence about
config-reload actually contradicts the confirmed behavior.

## Implementation intent
Correct and extend 03_06's "`/v1/tools` as RuntimeToolRegistry Source" section (and/or add a short
new subsection) to state, as confirmed fact:
- `/reload` never rebuilds `RuntimeToolRegistry`'s discovery-derived state
  (`raw_definition`/`disabled_reason`/`status`, and hence `/mcp status`'s `DISABLED_REASON`
  column); only a full agent process restart re-runs `discover_all()` and refreshes it.
- `/reload` does live-apply `[approval].tool_safety_tiers` / `[tool].allowed_tools` policy fields
  via `RuntimeToolRegistry.apply_policy()` — this is a distinct, narrower mechanism that must not
  be conflated with a full availability-metadata rebuild.
- Per-server config files (e.g. `allowed_dirs`, `read_only`, `command_allowlist`) are not part of
  `agent.toml` and have no reload path at all; changing them requires restarting the affected MCP
  server process (in addition to restarting the agent, if `RuntimeToolRegistry` should reflect the
  change).
- Add a cross-reference to 06_17's `/reload`-vs-restart section, noting that this restart
  requirement is a separate, broader mechanism than (and not fully covered by) 06_17's
  `[mcp_servers.*]`-only scoping statement.

This is documentation-only; do not implement a hot-reload mechanism for `RuntimeToolRegistry`, and
do not modify `cmd_config.py`, `config_reload.py`, `runtime_tool_registry.py`, `startup.py`, or any
per-server config-loading code.

## Implementation instructions

   RuntimeToolRegistry Source": replace or amend the sentence "Any changes to tool availability
   (e.g., due to health degradation, config reload) will be reflected in subsequent `/v1/tools`
   responses and will cause `RuntimeToolRegistry` to be updated accordingly" — this currently
   overstates config-reload's effect. State plainly that `RuntimeToolRegistry` is populated once at
   agent startup via `McpToolDiscoveryService.discover_all()`
   (`scripts/agent/startup.py:329-333`), and that neither `/reload` nor a live-health-check path
   causes it to be rebuilt from a fresh `/v1/tools` fetch.

   - `/reload` (`_ConfigMixin._cmd_reload()`, `scripts/agent/commands/cmd_config.py:37`) calls
     `ConfigReloadService.apply_config_dict()` (`scripts/agent/services/config_reload.py:113`),
     whose only `RuntimeToolRegistry` touchpoint is `apply_policy()`
     (`scripts/shared/runtime_tool_registry.py:168-195`), which re-derives
     `agent_safety_tier`/`requires_approval`/policy-derived `enabled_for_llm` only — it never

   - Per-server config files driving `enabled`/`disabled_reason` computation (e.g.

## Acceptance criteria
- `docs/04_mcp_03_06_tool-runtime-availability-metadata.md` states, as confirmed fact (not as an
  open question), that `/reload` does not rebuild `RuntimeToolRegistry`'s discovery-derived
  `enabled`/`disabled_reason` state, and that a full agent process restart is required for that
  state to reflect config changes (agent-side or per-server).
- The overstated sentence in "`/v1/tools` as RuntimeToolRegistry Source" implying config-reload
  causes `RuntimeToolRegistry` to update is corrected or removed.
- The doc cross-references 06_17's `/reload`-vs-restart section and clarifies the two are related
  but scoped differently ([mcp_servers.*] connection definitions vs. RuntimeToolRegistry's
  availability snapshot).
- No source file is modified; no other `docs/*.md` file is modified.

## Tests
Documentation-only change; no automated tests required. If desired as an optional strengthening

change until the agent process (and the MCP server process) are restarted.
