# Title: [REQ] Define EventBus Operational Lifecycle and Establish Canonical API Schemas
# Priority: Medium
# Target files: scripts/eventbus/**/*.py, docs/eventbus/*.md, OpenAPI spec
# Background: EventBus operational policies (retention, capacity, DLQ, consumers) and API documentation are currently incomplete or subject to manual duplication/drift.
# Problem: 
# 1. Unclear policies on event retention, replay availability, purging, and database maintenance.
# 2. Undefined Dead Letter Queue (DLQ) lifecycle and consumer management (creation, expiration, slow-consumer recovery).
# 3. Manual API documentation may diverge from actual FastAPI/Pydantic implementations.
# Reason for change: To ensure reliable long-term operation (preventing unbounded growth or stale consumers) and maintain accurate, automated API documentation.
# Implementation intent: Formalize the full EventBus operational lifecycle and establish executable OpenAPI schemas as the single source of truth for APIs.
# Implementation instructions:
# 1. **Retention and Capacity Management**: Define policies for event retention, replay availability, purging, and database size/maintenance (WAL, VACUUM, disk space alerts).
# 2. **DLQ and Consumer Lifecycle**: Define DLQ retention, deletion, and requeue logic. Define consumer-ID lifecycles (creation, ownership, expiration, cleanup) and implement slow-consumer detection/recovery mechanisms.
# 3. **API Schema Authority**: Designate FastAPI's OpenAPI specification as the canonical source for all EventBus endpoints. Implement generation or validation of Markdown documentation from these schemas.
# 4. **Automated Validation**: Integrate schema drift detection into the CI pipeline to catch discrepancies between code and documentation.
# 5. **Observability**: Define and document required health metrics and alerting for EventBus operations.
# Acceptance criteria:
# - Retention, replay, purge, and capacity policies are explicitly documented.
# - DLQ and consumer-ID lifecycles are fully defined and implemented.
# - Slow-consumer detection and recovery procedures are established.
# - All EventBus APIs are fully described in the OpenAPI specification.
# - Markdown API documentation is synchronized with the OpenAPI spec.
# - CI detects any drift between the API implementation and its documentation.
# - Health metrics and alerting requirements are clearly defined.
# Tests:
# - Verification of purge and replay boundary conditions.
# - Testing of DLQ requeue behavior.
# - Simulation of consumer expiration and cleanup.
# - Validation of API payload compliance against schemas.
# - Comparison of OpenAPI spec with documented endpoints.
