# Reduce cyclomatic complexity of `LlmSseStreamHandler.stream_once`

## Priority
Medium

## Target files
- `scripts/shared/llm_sse_stream.py` (`LlmSseStreamHandler.stream_once`)
- `tests/shared/test_llm_sse_stream.py`

## Background
`scripts/shared/llm_sse_stream.py` implements `LlmSseStreamHandler`, the static-method class
responsible for driving a single SSE connection attempt against the LLM chat-completion
endpoint: opening the HTTP stream, reading chunks via `read_next_chunk`, feeding them to
`RobustSSEParser`, extracting `finish_reason`/content/tool-call deltas via
`LlmSseHelpers.process_sse_payloads`, and translating transport failures into
`LLMTransportError`.

This was found during a prior behavior-preserving refactor cycle on this file (2026-08-13).
Other complexity/duplication findings from that cycle were addressed at the time, but this
one was deliberately deferred because it touches the core per-chunk read/parse/finish-reason
loop, and the refactor cycle's constraint was "do not change streaming/timeout/heartbeat
behavior even incidentally." Extracting this loop body safely requires its own dedicated
behavior-lock cycle with new characterization tests, which was out of scope for that pass.

## Problem
`radon cc scripts/shared/llm_sse_stream.py -s` currently reports:

```
M 47:4 LlmSseStreamHandler.stream_once - C (12)
C 21:0 LlmSseStreamHandler - B (6)
M 25:4 LlmSseStreamHandler.read_next_chunk - A (3)
M 135:4 LlmSseStreamHandler._handle_status - A (2)
M 143:4 LlmSseStreamHandler._build_payload - A (2)
```

`stream_once` (lines 47-130) is grade C (score 12), the highest in the module and the only
method above grade A. The complexity is concentrated in its `while True` per-chunk loop
(lines 84-115), which interleaves:
- reading the next chunk and detecting stream exhaustion (`read_next_chunk`)
- raising `LLMTransportError(kind="PREMATURE_EOF", ...)` when the stream ends without a
  prior `is_done` or `finish_reason`
- feeding the chunk to `RobustSSEParser.feed`, accumulating `stat_parse_errors_ref`
- calling `LlmSseHelpers.process_sse_payloads` and updating `finish_reason`
- two independent `break` conditions (`exhausted` with no error, and `is_done`)

Confirmed still true in current source: `stream_once` spans `scripts/shared/llm_sse_stream.py:47-130`,
and `tests/shared/test_llm_sse_stream.py` currently has exactly 24 `def test_` functions, matching
the issue's baseline. `mutmut` is listed in `pyproject.toml` dev dependencies but is not currently
installed in this environment (`which mutmut` fails), so mutation testing scoped to the extracted
path is not yet available and must be deferred per the issue's own fallback instruction.

## Reason for change
A grade-C method concentrates several independent failure/exit conditions
(premature EOF, malformed-chunk exhaustion, finish-reason completion) in one function body,
making it harder to reason about and to safely modify in the future without an accidental
behavior change. Extracting the loop body into a named helper with an explicit contract
reduces this risk and documents the exit conditions for future maintainers, provided the
extraction is proven behavior-preserving by tests written before the change.

## Implementation intent
Extract the per-chunk processing loop body of `stream_once` (the code currently inside the
`while True:` block, lines approximately 85-115) into a well-named private static helper on
`LlmSseStreamHandler` (e.g. `_process_next_chunk` or similar), preserving exactly:
- the order of the `exhausted` / `is_done` / `finish_reason` checks
- the exact conditions under which `PREMATURE_EOF` is raised
  (`exhausted and not is_done and finish_reason is None`)
- the exact conditions under which the loop `break`s (on non-error `exhausted`, and on
  `is_done`)
- the exact heartbeat-timeout propagation from `read_next_chunk` (unchanged — this issue
  only touches `stream_once`'s loop body, not `read_next_chunk` itself)

Do not change `llm_reconnect.py` or `llm_retry.py` behavior, and do not change heartbeat
timeout values or retry classification anywhere.

This must follow `skills/python-refactoring/workflow.md` Phase 2: write new characterization
tests for exhaustion / finish_reason / premature-EOF edge cases (pinning current behavior)
*before* performing the extraction, not after.

## Implementation instructions
1. Before any code change, add characterization tests to `tests/shared/test_llm_sse_stream.py`
   (or confirm existing tests already cover) each of these edge-case combinations for
   `stream_once`:
   - stream exhausts with `finish_reason` already set (clean completion, no error) — the
     `break` on `exhausted` when `is_done` or `finish_reason is not None` must not raise.
   - stream exhausts with `is_done=True` from the parser but `finish_reason` still `None`.
   - stream exhausts with both `is_done=False` and `finish_reason=None` — must raise
     `LLMTransportError(kind="PREMATURE_EOF", ...)` with `partial_text` set from accumulated
     `content_parts`.
   - `is_done=True` returned by `parser.feed` on a chunk that also carries a `finish_reason`
     — loop must break immediately after processing that chunk.
   - multiple chunks processed before either exit condition is hit (loop continues correctly).
   - `stat_parse_errors_ref` accumulation across multiple chunks, including the reset of
     `parser.stat_parse_errors` to 0 after each accumulation.
2. Run the full existing suite and new characterization tests, confirm all pass against the
   current, unextracted implementation (establishes the behavior lock).
3. Extract the loop body into a private static helper with an explicit docstring describing
   its inputs (parser, byte_iter, url, timeout/retry flags, mutable accumulators) and outputs
   (updated `finish_reason`, whether to break, whether to raise). Keep control-flow order
   identical; a mechanical extraction (e.g. returning a small result/break-signal object or
   raising directly from the helper) is acceptable as long as observable behavior is
   byte-for-byte identical.
4. Re-run `radon cc scripts/shared/llm_sse_stream.py -s` and confirm `stream_once` is now
   grade B or better.
5. If `mutmut` becomes available in this environment during implementation, run it scoped to
   the extracted helper's path and confirm 0 surviving mutants; if it remains unavailable,
   perform a manual branch-by-branch review per `skills/DESIGN.md` §Tool availability guard
   and explicitly document that fallback (which condition was reviewed manually and why) in
   the implementation report.
