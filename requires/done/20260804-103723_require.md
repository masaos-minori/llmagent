# Correct the stale "cosine distance" docstring in `SQLiteVectorStore.vec_search` (`chunks_vec` is explicitly L2)

## Background
The source issue (`issues/20260804-103043_unknowns.md`) was written as a follow-up "unknown" from
`plans/done/20260727-145945_plan.md` (UNK-02). At the time it was written, `chunks_vec`'s
`CREATE VIRTUAL TABLE ... USING vec0(...)` statement in `scripts/db/schema_sql.py` had no explicit
`distance_metric=` clause, so its runtime metric was ambiguous by source inspection alone, and
`scripts/db/store_impl.py:39`'s docstring — "Search for k nearest neighbors by cosine distance." —
could not be confirmed right or wrong without an empirical `sqlite-vec` test (the issue proposed
adapting `scratchpad/test_vec0_distance.py`, which had already empirically confirmed L2 for the
sibling `memories_vec` table).

Verification against the current source tree during this cycle found that the ambiguity described
in the issue has since been resolved by a later, unrelated commit:
- `git log` shows commit `556490796` ("fix: resolve NC-001 through NC-021 needs-confirmation
  items", NC-004) added an explicit `distance_metric=L2` clause to **both** `memories_vec` and
  `chunks_vec` in `scripts/db/schema_sql.py`, in the same change. `scripts/db/schema_sql.py:47-51`
  now reads:
  ```
  CREATE VIRTUAL TABLE IF NOT EXISTS chunks_vec USING vec0(
      chunk_id  INTEGER PRIMARY KEY,
      embedding float[DIMS],
      distance_metric=L2
  );
  ```
  This is an explicit declaration, not an implicit default — it settles the question the issue
  raised without requiring an empirical `sqlite-vec` extension test.
- The same commit updated `scripts/agent/memory/retriever.py`'s comment to say "Negate L2
  (Euclidean) distance" (confirmed present at line 185), consistent with the `memories_vec` side of
  NC-004.
- `scripts/rag/repository.py:144` already carries a docstring that independently and correctly
  states the `chunks_vec` search path's metric: "Retrieve top_k chunks by L2-distance KNN (smaller
  distance = higher similarity)." This corroborates L2 from a second source-level location in the
  same codebase.
- No normalization step exists between embedding generation and `chunks_vec` insertion:
  `scripts/rag/ingestion/ingester.py:448` inserts the raw embedding bytes directly
  (`INSERT INTO chunks_vec (chunk_id, embedding) VALUES (?, ?)`), with no call to `cosine_sim` or
  any normalization helper in that path. (`rag/utils.py`'s `cosine_sim` is used elsewhere, in
  `rag/cache.py:61`, for an unrelated embedding-cache dedup check — not in the `chunks_vec` search
  path.)
- No committed empirical test exists for this: `scratchpad/` does not currently exist in the
  repository (the `test_vec0_distance.py` script the issue references was left in an ephemeral,
  non-committed location per the plan's own note), and `tests/db/test_db_store_impl.py`'s
  `vec_search` tests only exercise a mocked DB layer — they assert delegation, not actual distance
  values, so they do not resolve the metric question either.

Given the explicit `distance_metric=L2` clause plus the corroborating `repository.py:144` docstring
and the absence of any normalization step, `chunks_vec`'s runtime metric is L2 — confirmed at the
source level, with no need for the empirical extension test the issue proposed. However, this means
`scripts/db/store_impl.py:39`'s "cosine distance" docstring is now a confirmed, not merely
suspected, inaccuracy, and it directly contradicts `repository.py:144` within the same codebase.
The issue is not fully resolved — the schema ambiguity it flagged is gone, but the docstring defect
it anticipated fixing is still present and unaddressed.

## Problem
`scripts/db/store_impl.py:39`, in `SQLiteVectorStore.vec_search`'s docstring, states:
```python
def vec_search(self, embedding: bytes, k: int) -> list[tuple[int, float]]:
    """Search for k nearest neighbors by cosine distance."""
```
This is factually wrong. `chunks_vec` is declared with an explicit `distance_metric=L2` clause
(`scripts/db/schema_sql.py:50`), and `scripts/rag/repository.py:144` — documenting the same
underlying `chunks_vec` query path — correctly states "L2-distance KNN". A maintainer reading
`store_impl.py:39` in isolation would be misled into believing `chunks_vec` returns cosine-distance
values (range roughly [0, 2], 0 = identical direction regardless of magnitude) when it actually
returns L2/Euclidean distances (unbounded, magnitude-sensitive), which could lead to incorrect
downstream assumptions about score ranges, thresholding, or ranking behavior for anything consuming
`vec_search`'s returned `(chunk_id, distance)` pairs.

## Reason for change
Leaving a self-contradictory pair of docstrings in the codebase (`store_impl.py:39` says cosine;
`repository.py:144` says L2, for the same table) is a maintainability hazard: it invites a future
reader or agent to "fix" the wrong side, or to write code that assumes cosine-distance value ranges
where L2 actually applies. Now that the schema explicitly commits to L2 (via NC-004), correcting the
docstring is a small, low-risk, purely-documentation fix with no ambiguity left to resolve first.

## Implementation intent
Update the one-line docstring in `SQLiteVectorStore.vec_search` to accurately describe the L2
distance metric that `chunks_vec` actually uses, matching the wording style already used in
`repository.py:144`. This is a comment/docstring-only change — no behavior, SQL, or schema change is
needed or in scope, since the explicit `distance_metric=L2` clause already correctly reflects
runtime behavior.
