# Clarify shell-mcp sandbox enforcement responsibility split in docs/04_mcp_04_02

## Priority
High

## Target files
- `docs/04_mcp_04_02_file-write-file-delete-shell.md` (shell-mcp section, "セキュリティ注記" / "本番環境での強制" callout block, approx. lines 122-129 as of this writing)

## Background
`docs/04_mcp_04_02_file-write-file-delete-shell.md` documents shell-mcp's sandboxing behavior,
including a security note that `sandbox_backend` defaults to `"none"` and that production mode
rejects this combination by raising a `RuntimeError` at startup ("エージェントは起動時に
`RuntimeError` を発生させる"). This wording already gestures at "the agent" being involved, but
it does not name the specific mechanism, nor does it state which component (shell-mcp vs. the
Agent) actually owns the enforcement check. This leaves the security-relevant responsibility
boundary implicit rather than explicit.

## Problem
An implementer or operator reading the current doc could reasonably (but incorrectly) conclude
that shell-mcp itself refuses to run unsandboxed in production, since the note is phrased close
to shell-mcp's own configuration description. In fact, verified against current source:

- **shell-mcp itself performs no production-awareness check.** `scripts/mcp_servers/shell/shell_models.py`
  (`ShellConfig`) defaults `shell_sandbox_backend` to `"none"` and loads whatever value is set in
  `config/shell_mcp_server.toml` with no validation tied to any notion of "production."
  `scripts/mcp_servers/shell/service_static_helpers.py::init_sandbox()` only raises if
  `backend == "firejail"` and the `firejail` binary is missing; it does **not** raise or warn when
  `backend == "none"`. `scripts/mcp_servers/shell/shell_service.py::ShellService.__init__` calls
  `init_sandbox()` and otherwise just uses the configured backend as-is. shell-mcp has no
  `security_profile` / production concept anywhere in its own code path.
- **The actual "reject `sandbox_backend=none` in production" enforcement lives entirely in the
  Agent layer**, specifically `scripts/agent/repl_health.py::audit_security_defaults()`. This
  function is invoked from `scripts/agent/startup.py` (around line 297) during Agent process
  startup, with `production_mode = (ctx.cfg.mcp.security_profile == SecurityProfile.PRODUCTION)`
  (read from `agent.toml`). It loads shell config via
  `agent/security_audit_config.py::load_shell_audit_config()` and, if
  `shell_cfg.sandbox_backend == "none"` while `production_mode` is `True`, raises
  `RuntimeError("Production mode requires shell sandbox. ...")`, which prevents the Agent process
  from starting.
- Consequence: if shell-mcp is ever started or reached independently of the Agent's own startup
  path (i.e., without `agent/startup.py::audit_security_defaults()` having run and passed), there
  is **no enforcement anywhere** that blocks an unsandboxed shell-mcp instance from executing
  commands, even in what an operator might consider a "production" deployment.

This is a security-relevant responsibility-boundary gap in the documentation, not a code defect:
the code behavior is intentional and correctly split by layer, but the doc does not make the
split explicit enough to prevent a wrong mental model.

## Reason for change
Per `rules/coding.md`'s "Current behavior" classification, this gap is a "Documentation fix
required" case: the underlying code split (Agent enforces; shell-mcp does not self-enforce) is
correct and intentional, but the doc's wording does not clearly attribute enforcement to the
correct layer. Leaving it unclear risks an implementer assuming shell-mcp is self-defending when
it is not, which could lead to running shell-mcp in a context where the Agent-side gate is
bypassed or absent, with no compensating control.

## Implementation intent
Extend the existing "本番環境での強制" (Production enforcement) callout in the shell-mcp section
of `docs/04_mcp_04_02_file-write-file-delete-shell.md` to explicitly state the responsibility
split between the two layers, naming the concrete enforcement mechanism, without altering any
other part of the document's structure or the file-write-mcp / file-delete-mcp sections.

## Implementation instructions
1. Locate the existing security note block in `docs/04_mcp_04_02_file-write-file-delete-shell.md`
   under the shell-mcp section (the block starting with "**セキュリティ注記 — サンドボックスは
   デフォルトで無効:**" and including "**本番環境での強制:**").
2. Add explicit language stating:
   - shell-mcp itself does not perform any production-mode check and does not enforce a safe
     sandbox default; it simply executes with whatever `sandbox_backend` is configured in
     `config/shell_mcp_server.toml` (default `"none"`).
   - Production-environment enforcement (rejecting `sandbox_backend = "none"` when
     `security_profile = "production"`) is performed by the Agent layer, specifically
     `scripts/agent/repl_health.py::audit_security_defaults()`, invoked from
     `scripts/agent/startup.py` during Agent process startup. On violation it raises
     `RuntimeError`, which prevents the Agent from starting — it does not modify or restart
     shell-mcp itself.
   - As a consequence, this enforcement only applies when shell-mcp is started as part of the
     Agent's managed startup path; running shell-mcp independently of that path bypasses the
     check entirely.
3. Keep the addition in the same style/register as the existing callout (Japanese prose,
   `>`-blockquote formatting matching the surrounding note), and keep it scoped to the shell-mcp
   section only — do not touch file-write-mcp or file-delete-mcp sections.
4. Do not change any code; this is a documentation-only change to `docs/04_mcp_04_02_file-write-file-delete-shell.md`.

## Acceptance criteria
- The shell-mcp section of `docs/04_mcp_04_02_file-write-file-delete-shell.md` explicitly states
  that shell-mcp itself does not enforce a safe sandbox default in production.
- The doc explicitly names `scripts/agent/repl_health.py` (`audit_security_defaults`) as the
  component performing production-mode enforcement, and states that it is invoked from Agent
  startup (`scripts/agent/startup.py`).
- The doc communicates that this enforcement is bypassed if shell-mcp runs outside the Agent's
  managed startup path.
- No other section of the file, and no source code, is modified.
