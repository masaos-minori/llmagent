# Require: Document residual risk of abandoned executor thread on WAL-checkpoint timeout

## Priority

Low

## Target files

- `scripts/agent/repl.py` (`AgentREPL._close_resources()`, `_wal_checkpoint_sync()`, `_wal_backup_sync()`)
- `scripts/agent/http_lifecycle.py` (precedent reference)

## Background

The WAL-checkpoint sequence in `AgentREPL._close_resources()` is wrapped in `loop.run_in_executor(None, self._wal_checkpoint_sync)` bounded by `asyncio.wait_for(..., timeout=self._WAL_CHECKPOINT_TIMEOUT_S)`. If the underlying blocking SQLite/OS call does not return before the timeout, the worker thread is not cancelled and remains as a live, non-daemon `ThreadPoolExecutor` worker.

## Problem

If a genuine OS/filesystem-level I/O stall occurs (hung disk, stalled network filesystem), the `_wal_checkpoint_sync()` or `_wal_backup_sync()` worker thread could be abandoned indefinitely, delaying interpreter shutdown. This is the same class of risk documented in `http_lifecycle.py:95-103` (`_wait_exited`).

## Reason for change

Track this residual risk explicitly rather than letting it go unrecorded. The plan proceeds with `run_in_executor` + `wait_for` because the requirement doc explicitly directs this approach and the risk window is narrower than the `proc.wait()` case it fixes.

## Implementation intent

No immediate implementation change required. Document the risk and establish monitoring criteria for when it becomes actionable.

## Implementation instructions

No code changes required at this time. Monitor for:

- Process shutdown latency correlated with WAL checkpoint timeouts in production
- Supervisor SIGKILL events timing that suggests worker threads are preventing clean exit

If observed in practice, consider a poll-based alternative similar to `http_lifecycle.py`'s `_wait_exited()` pattern.

## Acceptance criteria

- [ ] Risk is documented and tracked
- [ ] `_WAL_CHECKPOINT_TIMEOUT_S` / `_WAL_BACKUP_TIMEOUT_S` values are kept comfortably below process supervisor's SIGTERM->SIGKILL grace period
