## Background

`docs/05_agent_04_03_state-and-persistence-platform-databases.md` documents the workflow persistence API. Its entry for `request_approval` carries an explicit "Needs confirmation" note (lines 109-110) stating that the `workflow_id` argument "is believed to be used, like `StateStore.create_task`'s, to identify multi-workflow versions, but the details of its use are unconfirmed." This is tracked as NC-008 in the project's Needs-Confirmation inventory (`docs/00_governance_07_needs-confirmation-inventory.md`), with Priority: High and Blocking: Yes, because multi-workflow routing mistakes could misdirect approvals to the wrong task — an area also touched by the approval-restore ordering bug in `issues/20260727_01_issue.md` (now `issues/done/20260727_01_issue.md`).

## Problem

The current documentation leaves `workflow_id`'s actual purpose unconfirmed, which risks:
- Future maintainers assuming `workflow_id` is used to disambiguate/route pending approvals between concurrent workflows, when in fact no lookup function in `approval_ops.py` filters by `workflow_id` (all lookups filter by `task_id` and/or `session_id` only — see `get_latest_approval`, `find_pending_approval_by_session`, `find_latest_pending_approval`, `find_approval_by_id`, `find_all_pending_approvals`).
- The NC-008 item remaining open in the Needs-Confirmation inventory past its "Next sprint" resolution target, keeping a Blocking:Yes item unresolved.

Investigation of the current source confirms the following facts (traced end-to-end):
1. `workflow_id` is generated as a fresh `str(uuid.uuid4())` in `orchestrator.py::_init_workflow_task` each time a *new* task is created for a turn (`scripts/agent/orchestrator.py:330-341`). It is therefore effectively a per-task-instance identifier, not a "workflow type/version" label (that role is already covered by the separate `workflow_version` field).
2. When an existing task is resumed after an approval gate (`existing_task_id` supplied), the same `workflow_id` is reused (`task.workflow_id or str(uuid.uuid4())`, `scripts/agent/orchestrator.py:341`) — so `workflow_id` persists for the lifetime of one task/turn, including retries and resumption, but a new turn starts a new `workflow_id`.
3. `request_approval` (`scripts/agent/workflow/approval_ops.py:12-36`) simply stores the caller-supplied `workflow_id` on the `approvals` row; it never uses it to look up or disambiguate anything.
4. Every approval-lookup function in `approval_ops.py` selects by `task_id` and/or `session_id` + status — none filters by `workflow_id`. Routing/disambiguation of pending approvals is therefore performed via `task_id`/`session_id`, not `workflow_id`.
5. `workflow_id` is propagated identically into `record_artifact` (`artifact_ops.py`) and `begin_stage_if_new` (`idempotency_ops.py`), and into OTel span attributes (`workflow_engine.py:137,160,234,254`, `tool_audit.py:58,79,191`) — i.e., it functions purely as a correlation/observability tag threaded through tracing and audit records for a given task/turn.
6. `StateStore.get_workflow_count(session_id)` (`state_store.py:209-216`) counts `COUNT(DISTINCT workflow_id)` for a session — a diagnostic metric of how many distinct workflow instances (turns) have run in that session over time, displayed via `repl.py:181`. It is historical/cumulative, not a concurrency indicator: `AgentContext.workflow` (`scripts/agent/context.py:191-200`) holds a single `current_task_id`/`workflow_id` pair, confirming only one workflow is active per session at a time — there is no concurrent multi-workflow execution in the current design.

In short: `workflow_id` is a per-task-instance correlation ID for audit/tracing and per-session workflow-instance counting, not a routing/filter key used anywhere to disambiguate between multiple simultaneously pending approvals or tasks.

## Reason for Change

NC-008 is marked Blocking:Yes with Priority:High in the Needs-Confirmation inventory. The investigation above provides a definitive, source-traced answer, so the open question should be closed: the documentation should be updated to state the confirmed behavior (removing the "Needs confirmation" hedge) and the inventory entry should be marked resolved. This removes ambiguity for future contributors reasoning about approval routing correctness, and is directly relevant to the approval-restore correctness concerns raised in the related issue `issues/done/20260727_01_issue.md`.
