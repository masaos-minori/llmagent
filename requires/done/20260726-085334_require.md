# Schema validation for tool call arguments is implemented but never invoked

## Priority

High

## Target Files

- `scripts/agent/tool_runner.py` — `execute_one_tool_call()` (lines 113–165; `orjson.loads(args_str)` at line 132)
- `scripts/agent/tool_arg_validator.py` — `validate_tool_arguments()` (existing, unused in production)
- `scripts/agent/repository_gateway.py` — `RepositoryGateway.execute()` (lines ~76–79, READ passthrough) and `_gate_write()` (lines 81–123)

## Background

A prior requirement (`requires/done/20260725_01_require.md`) and its associated plan/implementation-procedure (`plans/done/20260725-134727_plan.md`, `implementations/done/20260725-152507_tool_runner.md`) called for adding schema-based validation of LLM-generated tool call arguments before they reach MCP servers. That work produced `scripts/agent/tool_arg_validator.py`, which defines `validate_tool_arguments(tool_name, args, input_schema, allow_extra_fields=False) -> ValidationResult` (checks required fields, rejects unexpected fields, and runs `jsonschema` type validation, falling back to lenient/accept-all when no schema is available). This module was added in commit `299964b14` but the integration step described in its own design (and in its own module docstring: "Validation location: execute_one_tool_call() after orjson.loads(), before calling executor") was never applied to `tool_runner.py`.

## Problem

`execute_one_tool_call()` in `scripts/agent/tool_runner.py` parses the LLM-generated tool call arguments with `orjson.loads(args_str)` at line 132, and only catches `orjson.JSONDecodeError` (lines 133–136). The parsed `args` dict is then passed straight to `ctx.services_required.gateway.execute(ctx, name, args)` or `ctx.services_required.tools.execute(name, args)` (lines 138–141) with no schema check at all.

Verified against current source:

- `validate_tool_arguments(` has **zero production call sites** anywhere in `scripts/agent/` or `scripts/shared/` — it is called only from `tests/test_tool_arg_validator.py`. It is currently dead code.
- `RepositoryGateway.execute()` (`scripts/agent/repository_gateway.py`) routes `OperationType.READ` tool calls straight to `self._executor.execute(tool_name, args)` with no validation of any kind.
- `RepositoryGateway._gate_write()` (same file, lines 81–123), which handles WRITE-classified tool calls, does **not** call `validate_tool_arguments()` either. It only calls `check_preflight()` (policy check) and `classify_risk()` / `run_approval_checks()` (human-approval gating for risky operations) — none of which perform JSON-schema validation of argument shape/types.

This corrects the original issue text (`issues/20260726_12_issue.md`), which stated that schema validation happens in `_gate_write()` at line 90 for write tools, and that only READ tools are unvalidated. That claim does not hold: no tool call — read or write — currently receives schema validation. The gap is broader than originally reported.

A `RuntimeToolRegistry` keyed by tool name (holding each tool's `input_schema`) is already reachable from `tool_runner.py` via `ctx.services_required.runtime_tools` (an `AppServices` field populated at startup by `agent/startup.py` from `McpToolDiscoveryService`), but it can be `None` if not wired for a given run, so any integration must handle that case.

## Reason for Change

LLM-generated tool call arguments are untrusted input. Without schema enforcement, malformed or unexpected fields (e.g., an out-of-scope `path`, an unexpected boolean flag enabling a side effect, a wrong type) reach MCP server executors unchecked, for both read and write tool calls. Read tools are not risk-free: a schema violation on a read tool (e.g. a path argument escaping the intended scope, or an unexpected parameter altering behavior) can still cause information disclosure or unintended error-driven behavior. The validation logic to close this gap already exists and is tested in isolation (`tests/test_tool_arg_validator.py`), but delivers no protection because it is never wired into the execution path.

## Implementation Intent

Wire the existing `validate_tool_arguments()` into `execute_one_tool_call()` so that every tool call — read and write alike — is validated against its tool's `input_schema` immediately after JSON parsing and before any execution or gateway dispatch. Preserve the existing lenient-fallback behavior (skip validation when no schema is available) so tools with incomplete MCP definitions are not blocked. On validation failure, return a graceful error result (matching the existing error-result shape used elsewhere in `tool_runner.py`/`repository_gateway.py`) instead of raising, and log a warning with the tool name and rejection reason — do not let a validation failure crash the session.

## Implementation Instructions

1. In `scripts/agent/tool_runner.py::execute_one_tool_call()`, after the existing `orjson.loads(args_str)` block (line 132–136) and before the dispatch to `ctx.services_required.gateway.execute(...)` / `ctx.services_required.tools.execute(...)` (lines 138–141):
   - Look up the tool's schema via `ctx.services_required.runtime_tools` (an `AppServices.runtime_tools: RuntimeToolRegistry | None`). Guard for `None` (registry not wired) and for the tool name not being registered (e.g. `KeyError` from `registry.get(name)`) — in either case, fall through to lenient behavior (skip validation) rather than failing the call.
   - When a `RuntimeTool` is found, call `validate_tool_arguments(tool_name=name, args=args, input_schema=runtime_tool.input_schema, allow_extra_fields=runtime_tool.allow_extra_fields)` (or the equivalent current field name if `allow_extra_fields` does not already exist on `RuntimeTool` — confirm at implementation time and add the field if missing, defaulting to `False`).
   - On `ValidationResult.success is False`: log a warning (tool name + `result.reason`) and return/produce an error result through the same result path the function already uses for other execution errors (matching `text/is_error/x_request_id` handling further down in the function), without calling the executor or gateway.
2. Apply this check uniformly for both the gateway path and the direct `ctx.services_required.tools.execute(...)` path — do not special-case read vs. write; validation must run before either branch.
3. Do not duplicate or move validation into `repository_gateway.py`. Keep `_gate_write()`'s existing policy/approval responsibilities (`check_preflight`, `classify_risk`, `run_approval_checks`) unchanged — schema validation is orthogonal and belongs at the single chokepoint in `tool_runner.py` so both read and write paths get it identically.
4. Ensure audit logging (`audit_tool_exec`, currently called after execution) still fires appropriately for rejected calls, or add an equivalent audit entry for validation rejections, consistent with how `repository_gateway.py::_gate_write()` logs `gateway.policy_denied` / `gateway.approval_denied` for its own rejections.

## Acceptance Criteria

- [ ] `validate_tool_arguments()` has at least one production call site in `scripts/agent/tool_runner.py`, executed for every tool call (read and write) after JSON parsing and before executor/gateway dispatch.
- [ ] A tool call with arguments missing a required field, or containing an unexpected extra field (schema present, `allow_extra_fields=False`), is rejected before reaching the executor/gateway and returns a graceful error result — the session does not crash.
- [ ] A tool call for a tool with no registered schema (`runtime_tools` registry `None`, or tool not found in registry) still executes normally (lenient fallback preserved).
- [ ] A tool call with valid arguments matching its schema executes normally, unaffected by the new check.
- [ ] Rejections are logged with the tool name and validation reason.
- [ ] `_gate_write()` in `repository_gateway.py` is unchanged in responsibility (policy/approval only); no duplicate validation logic is introduced there.
