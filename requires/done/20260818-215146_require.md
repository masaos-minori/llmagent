# Config dataclass cleanup: unwired fields, duplicate definitions, validation gaps, default mismatch

## Priority
Low

## Target files
- `scripts/agent/config_dataclasses.py`
- `scripts/agent/config_builders.py`
- `scripts/agent/services/config_validators.py`
- `scripts/agent/factory.py`
- `scripts/agent/startup.py` (reader of `agent_memory_max_startup_snippets`)
- `scripts/agent/memory/injection.py` (`InjectionPolicy.min_importance` default)
- `docs/*.md` sections documenting `ToolConfig.progress_stagnation_window`,
  `memory_max_inject_semantic`, `memory_max_inject_episodic`,
  `memory_min_importance` (doc updates are coupled to the code changes below
  but are out of scope for this document-only requirement; flag for a
  follow-up doc pass once implementation lands)

## Background
`config_dataclasses.py`, `config_builders.py`, `config_validators.py`, and
`factory.py` together define and populate the agent's configuration surface.
Several inconsistencies have accumulated across these files: a config field
that looks tunable from toml but can never actually be changed at runtime, a
setting duplicated across two dataclasses where only one copy is wired, a
validated-field convention that one field silently violates, a validation
split between dataclass and build-path layers that behaves differently
depending on construction path, a default-value mismatch between two
related classes, and a hardcoded pair of LLM parameters that breaks the
pattern used by every other LLM call in the codebase.

## Problem
Verification against current source (branch `master`, as of this task)
confirms five distinct, still-reproducing problems:

> implementation already resolved items 2 and 3 below (confirmed against

> 5, concluding "no change needed" because `factory.py` always passes the
> explicit `MemoryConfig` value. Items 1, 4, and 6 were left unaddressed
> (item 1 was explicitly marked out-of-scope; items 4 and 6 were marked

> items 1, 4, and 6, revisits item 5 as a deliberate strengthening beyond
> the prior "no change needed" call (aligning the default itself, not just
> the runtime-injected value, to prevent drift for any future direct
> construction), and treats items 2 and 3 as already satisfied — no further
> action.

1. **`AgentConfig.agent_memory_max_startup_snippets` is unwired from
   config, not literally dead.** It is declared at
   `config_dataclasses.py:434` (line drifted from `432` at requirement-write
   time) with default `10`, and it IS read at
   `startup.py:637` to truncate memory snippets injected into the initial
   system prompt. However, neither `config_builders.py` nor `factory.py`
   nor `config_reload.py` ever assigns it from parsed toml (no
   `_get_int_or_default(cfg, "agent_memory_max_startup_snippets", ...)`
   call exists anywhere). The field therefore always evaluates to its
   hardcoded default of `10` regardless of what an operator puts in
   config — it looks configurable but functionally is not. **Correction to
   the original issue**: the issue describes this field as "dead" with "no
   build wiring and no reader"; the "no reader" half is inaccurate — the
   field is read and has real runtime effect, it is simply impossible to
   override from config. The fix should treat this as an unwired-config
   bug (wire it into the build path so it becomes genuinely configurable,
   or remove the field and inline the literal `10` at its call site in
   `startup.py` if a config knob is not actually wanted), not as removing
   an inert field.

2. **[ALREADY RESOLVED — verified against current source 2026-08-19, no
   action needed]** `security_lockdown_enabled` was previously duplicated
   across `MCPConfig` (`config_dataclasses.py:268`) and `AgentConfig`. The
   prior implementation cycle
   (`implementations/done/20260818-213448_config_cleanup.py.md`, Part A)
   already removed the field and its docstring entry from `AgentConfig`.
   Current source confirms: `security_lockdown_enabled` appears exactly
   once in `config_dataclasses.py` (on `MCPConfig`, line 268); `AgentConfig`
   has no such field; `config_builders.py`'s `build_agent_config` wires the
   parsed toml value only into `MCPConfig(...)` (no corresponding
   `AgentConfig(...)` kwarg exists to wire, since the field is gone). All
   runtime call sites (e.g. `repl_health.py:504-507`, `config_reload.py`)
   read only `ctx.cfg.mcp.security_lockdown_enabled`. Retained here for
   traceability only.

3. **[ALREADY RESOLVED — verified against current source 2026-08-19, no
   action needed]** `ToolConfig.progress_stagnation_window` previously
   lacked validation. The prior implementation cycle
   (`implementations/done/20260818-213448_config_cleanup.py.md`, Part B)
   already added `validate_progress_stagnation_window()` to
   `config_validators.py` and wired it into `ToolConfig.__post_init__` as
   `_v_tool_psw`. Current source confirms: `config_validators.py:155-159`
   defines `validate_progress_stagnation_window` (raises when
   `progress_stagnation_window < 0`); `config_dataclasses.py:222` calls
   `_v_tool_psw(self)` inside `ToolConfig.__post_init__`
   (`config_dataclasses.py:215-222`), alongside the five pre-existing
   sibling validators. The field is declared at
   `config_dataclasses.py:181`. Retained here for traceability only.

4. **[Confirmed still reproducing, action required]** `MemoryConfig`
   validation is split between dataclass and build-path
   layers, so direct construction skips half the checks.
   `MemoryConfig.__post_init__` (`config_dataclasses.py:253-257`, line
   drifted from `249-253`) validates
   only `memory_fts_limit`, `memory_rrf_k`, and `memory_recency_days`.
   `memory_max_inject_semantic`, `memory_max_inject_episodic`,
   `memory_embed_timeout_sec`, and `memory_retention_days` are validated
   only in `config_builders.py:332-360`, inside `_build_memory_config`, as
   part of parsing raw toml. Constructing `MemoryConfig(...)` directly
   (e.g. in a test, or any future code path that bypasses
   `_build_memory_config`) enforces none of the four build-path checks.

5. **[Confirmed still reproducing at the default-value level; action
   required per this requirement, superseding the prior cycle's "no change
   needed" call — see re-verification note above]**
   `InjectionPolicy.min_importance` default (`0.5`,
   `scripts/agent/memory/injection.py:31`) differs from
   `MemoryConfig.memory_min_importance` default (`0.3`,
   `config_dataclasses.py:233`, line drifted from `229`). In production,
   `factory.py:_build_injection_service` (lines 456-461) always passes
   `ctx.cfg.memory.memory_min_importance` into the `InjectionPolicy`
   constructor, so the differing defaults never actually conflict in the
   real build path — the mismatch only bites when `InjectionPolicy()` is
   constructed directly without going through the factory (e.g. tests),
   producing a different default than production actually uses.

6. **[Confirmed still reproducing, action required]** Compression LLM
   parameters are hardcoded while equivalent parameters
   elsewhere are configurable. `factory.py:43-44` defines
   `_COMPRESS_TEMPERATURE: float = 0.3` and
   `_COMPRESS_MAX_TOKENS: int = 300` as fixed module constants (confirmed
   at these exact line numbers), used at
   `factory.py:319-336` (`_build_history_manager`, line drifted from
   `325-336`) for the `HistoryManager`
   conversation-compression LLM call. By contrast, the main LLM call
   (`_build_llm_client`, `factory.py:266-292`, line drifted from
   `279-293`) sources `temperature` and
   `max_tokens` from `LLMConfig` (`llm_temperature`, `llm_max_tokens`), and
   the title-generation call has its own configurable
   `title_llm_temperature` / `title_llm_max_tokens` fields
   (`config_dataclasses.py:110-111`, line drifted from `107-108`).
   Compression is the one LLM
   parameterized call path that breaks this pattern.

## Reason for change
These are latent correctness and maintainability hazards: an operator
setting a config value that silently has no effect (item 1), a security
flag whose authoritative source is ambiguous to a reader unfamiliar with
the build path (item 2), an unvalidated field that can carry a negative
value into loop-guard logic (item 3), validation that depends on
construction path rather than being an invariant of the type (item 4), a
default that misleads anyone constructing `InjectionPolicy` directly in
tests or future code (item 5), and an asymmetry that makes compression the
only LLM call not tunable via config (item 6). None of these are urgent
correctness bugs in the current production path (all six are still
"latent" — production behavior today is fixed/predictable because the
factory path papers over the gaps), but each adds a bit of surprise for
future readers/maintainers and the fixes are small, contained, and best
done together since they share the same four files.

## Implementation intent
For each item, choose between "wire it correctly" and "remove it," and make
this decision explicit before implementing, rather than leaving the
inconsistency in place:
- Item 1: either wire `agent_memory_max_startup_snippets` into
  `_build_agent_config`-equivalent build path so it is genuinely
  configurable from toml, or remove the field from `AgentConfig` and
  replace its use in `startup.py:637` with the literal default value,
  documenting that startup snippet truncation is intentionally fixed.
- Item 2: keep exactly one authoritative `security_lockdown_enabled` field.
  Preferred approach: remove it from `AgentConfig` (since no code currently
  reads `AgentConfig.security_lockdown_enabled`) and confirm no reader
  regresses; alternative is to wire the build path to set both from the
  same parsed value and document why two copies exist.
- Item 3: add a `progress_stagnation_window >= 0` validator in
  `config_validators.py` following the existing pattern (see
  `validate_tool_cycle_detect_window`) and call it from
  `ToolConfig.__post_init__`, or remove the field if it turns out to be
  otherwise unused (it is used in `tool_loop_guard.py`, so removal is
  unlikely to be the right call — validation is expected).
- Item 4: move the four build-path-only checks
  (`memory_max_inject_semantic >= 0`, `memory_max_inject_episodic >= 0`,
  `memory_embed_timeout_sec > 0`, `memory_retention_days >= 1`) into
  `MemoryConfig.__post_init__` via new validator functions in
  `config_validators.py`, following the same pattern as
  `_v_mem_fts`/`_v_mem_rrf`/`_v_mem_rec`, so `MemoryConfig` enforces its own
  invariants regardless of construction path. Build-path code in
  `config_builders.py` can keep raising `ConfigReloadValidationError` for a
  config-reload-specific error type/message if that distinction matters
  operationally, but should not be the sole enforcement point.
- Item 5: change `InjectionPolicy.min_importance` default in
  `scripts/agent/memory/injection.py:31` from `0.5` to `0.3` to match
  `MemoryConfig.memory_min_importance`, so direct construction and the
  factory-built path agree.
- Item 6: decide whether compression LLM parameters should be promoted to
  `LLMConfig` fields (e.g. `llm_compress_temperature`,
  `llm_compress_max_tokens`, following the `title_llm_*` naming
  convention) or remain intentionally fixed. If promoted, wire them through
  `config_builders.py` with sensible defaults matching the current
  hardcoded values (`0.3`, `300`) so behavior is unchanged unless an
  operator overrides them. If kept fixed, add a code comment in
  `factory.py` explaining why compression parameters are not
  configurable (already partially present at `factory.py:43-44`; expand it
  to explicitly state the decision, not just what the constants are).

## Implementation instructions
1. In `config_dataclasses.py`, resolve items 1, 2, 3, 4, 5 per the intent
   above: remove or wire `agent_memory_max_startup_snippets`; remove or
   properly wire the duplicate `security_lockdown_enabled` on
   `AgentConfig`; add validation call for `progress_stagnation_window` in
   `ToolConfig.__post_init__`; add validation calls for the four
   currently-build-path-only `MemoryConfig` fields in
   `MemoryConfig.__post_init__`.
2. In `config_validators.py`, add the new validator functions needed by
   step 1 (`progress_stagnation_window` and the four `MemoryConfig`
   fields), following the existing naming/signature convention (e.g.
   `_v_tool_*`, `_v_mem_*` prefixes and the public
   `validate_tool_cycle_detect_window`-style names).
3. In `config_builders.py`, remove now-redundant inline validation for the
   four `MemoryConfig` fields if it is fully superseded by
   `__post_init__` (or keep it only if a distinct
   `ConfigReloadValidationError` type/message is operationally required —
   document the reason inline if so); remove the toml-read/wiring
   dead-ends left over from item 1/2 changes.
4. In `factory.py`, update `_build_injection_service` if item 5's default
   change affects any assumptions there (it should not, since the factory
   always passes the explicit `MemoryConfig` value); implement the item 6
   decision (promote to config or document as fixed).
5. In `scripts/agent/memory/injection.py`, update
   `InjectionPolicy.min_importance` default per item 5.
6. In `scripts/agent/startup.py`, update the use of
   `agent_memory_max_startup_snippets` per the item 1 decision (keep
   reading from config if wired, or replace with a literal/constant if the
   field is removed).
7. Search `scripts/` and `docs/` for every other reference to each
   changed/removed field name before finalizing, to avoid leaving stale
   readers or writers.
8. Defer `docs/*.md` updates to a follow-up documentation pass once the
   code changes are implemented and reviewed — do not bundle doc edits
   into this same change if it complicates review; if convenient to do in

   `memory_min_importance` are the effective memory-injection limits.

## Acceptance criteria
- `agent_memory_max_startup_snippets` is either genuinely configurable end
  to end (toml -> build path -> `AgentConfig` -> `startup.py` read) or
  removed with its call site replaced by a documented literal; no
  half-wired state remains.
- Exactly one `security_lockdown_enabled` field is authoritative; all
  readers reference it; the unused/unwired copy is removed or the
  duplication is explicitly documented and both copies are proven to stay
  in sync.
- A negative `progress_stagnation_window` raises `ValueError` from
  `ToolConfig.__post_init__`, matching the pattern used by
  `tool_cycle_detect_window` and the other validated window fields.
- Constructing `MemoryConfig(...)` directly (bypassing
  `_build_memory_config`) enforces the same invariants for
  `memory_max_inject_semantic`, `memory_max_inject_episodic`,
  `memory_embed_timeout_sec`, and `memory_retention_days` as the build
  path currently does, via `__post_init__`.
- `InjectionPolicy.min_importance` default equals
  `MemoryConfig.memory_min_importance` default (`0.3`).
- Compression LLM parameters (`_COMPRESS_TEMPERATURE`,
  `_COMPRESS_MAX_TOKENS`) are either exposed as configurable `LLMConfig`
  fields with defaults preserving current behavior, or explicitly
  documented in `factory.py` as an intentionally fixed design decision.
- No existing test regresses; `ruff`, `mypy`, and `bandit` checks defined
  in `rules/coding.md` pass on all changed files.
