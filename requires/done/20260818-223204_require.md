# Remove legacy backward-compatibility arguments and unreachable diagnostic path from ToolRouteResolver

## Priority
High

## Target files
- `scripts/shared/route_resolver.py`
- `scripts/shared/tool_executor.py`
- Tests that exercise the removed surface (see Implementation instructions), including but not
  limited to:
  - `tests/shared/test_route_resolver.py`
  - `tests/agent/services/test_runtime_tool_routing_integration.py`
  - `tests/shared/test_rag_tools_consistency.py`
  - `tests/docs/test_github_config_consistency.py`
  - `tests/integration/test_agent_mcp_integration.py`
  - `tests/integration/test_rag_turn_integration.py`

## Background
`ToolRouteResolver.resolve()` has already migrated to using `RuntimeToolRegistry` (populated from
live `/v1/tools` discovery) as the sole routing authority. `ToolRegistry`/static config-based
routing is no longer consulted by `resolve()`. Despite this migration, the constructor still
carries a `server_configs` positional argument, a `discovery_map` keyword argument, and a
`known_tools` keyword argument that only exist to preserve the pre-migration call signature.

## Problem
Verified directly against current source (`scripts/shared/route_resolver.py`,
`scripts/shared/tool_executor.py`, `scripts/agent/factory.py`):

- `ToolRouteResolver.__init__`'s `server_configs` parameter is stored nowhere and read nowhere;
  the docstring itself states "not read or stored — routing never consults per-server config."
- `discovery_map` is stored on `self._discovery_map` but the only reader is
  `_log_routing_coverage()`, which itself only runs when `known_tools` is passed to `__init__`.
- `_log_routing_coverage()` never executes in production: `scripts/agent/factory.py`'s
  `_build_tool_executor()` constructs `ToolExecutor` without a `discovery_map` argument, and
  `ToolExecutor.__init__` (`scripts/shared/tool_executor.py:72-74`) constructs
  `ToolRouteResolver(server_configs, discovery_map=discovery_map or {})` without ever passing
  `known_tools`. No production code path passes `known_tools` to `ToolRouteResolver` anywhere in
  `scripts/`.
- `tool_executor.py` passes `server_configs` straight through to the resolver even though the
  resolver never reads it; `ToolExecutor` also independently keeps `self._server_configs` for its
  own legitimate use in `_check_startup_mode()`, which is unrelated to the resolver and must be
  preserved.

This is dead/misleading API surface: an unread constructor argument and a diagnostic method that
cannot be reached in production. It invites future maintainers to mistake the compatibility
argument for a real routing input.

## Reason for change
The routing-authority migration to `RuntimeToolRegistry` is complete and stable. Leaving unread
arguments and unreachable diagnostic code in place increases the chance a future change
mistakenly treats `server_configs`/`discovery_map` as live routing inputs, and adds noise to the
public constructor signature of a shared, security-relevant routing component.

## Implementation intent
Make the resolver's constructor reflect only what `resolve()` actually consults
(`runtime_registry`, `warn_on_missing`, `strict_mode`). Remove the compatibility-only parameters
and the diagnostic method that depends on them, then update the one production caller
(`ToolExecutor.__init__`) to stop passing them. Do not touch `ToolExecutor`'s own
`server_configs`/`_server_configs` usage for `_check_startup_mode()` — that is independent of the
resolver and must keep working unchanged.

## Implementation instructions
1. In `scripts/shared/route_resolver.py`:
   - Remove the `server_configs` parameter from `ToolRouteResolver.__init__`.
   - Remove the `discovery_map` and `known_tools` parameters from `ToolRouteResolver.__init__`,
     and remove the `self._discovery_map` attribute.
   - Remove the `_log_routing_coverage()` method entirely.
   - Update the class/method docstrings to drop references to the removed parameters and to the
     removed diagnostic method.
   - Leave `build_discovery_map()` (the free function) untouched — it is unrelated production
     logic used for drift validation, not part of this cleanup.
2. In `scripts/shared/tool_executor.py`:
   - Update the `ToolRouteResolver(...)` construction call (around line 72-74) to stop passing
     `server_configs` and `discovery_map`.
   - Remove the `discovery_map` parameter from `ToolExecutor.__init__` since its only use was to
     forward to the resolver.
   - Do NOT remove `server_configs` from `ToolExecutor.__init__`, and do NOT remove
     `self._server_configs` — both are required by `_check_startup_mode()`.
3. Update all call sites/tests that construct `ToolRouteResolver` with `server_configs`,
   `discovery_map`, or `known_tools`, or that assert on `_log_routing_coverage()` behavior. These
   tests are validating the removed compatibility surface itself, so they must be updated to the
   new constructor signature or removed if they test only the deleted behavior (e.g., the
   `known_tools`/`_log_routing_coverage` coverage tests in
   `tests/agent/services/test_runtime_tool_routing_integration.py` and
   `tests/shared/test_route_resolver.py`, and the `discovery_map=...` construction calls in
   `tests/shared/test_rag_tools_consistency.py`, `tests/docs/test_github_config_consistency.py`,
   `tests/integration/test_agent_mcp_integration.py`, and
   `tests/integration/test_rag_turn_integration.py`). Preserve test intent for routing behavior
   that is still relevant (e.g., `RuntimeToolRegistry`-based resolution, strict_mode, warn-on-
   missing) — only drop assertions specific to the removed compatibility arguments.
4. Search the full repository (not just the files listed above) for any other
   `ToolRouteResolver(` or `ToolExecutor(...discovery_map=` call sites that may have been missed.

## Acceptance criteria
- `ToolRouteResolver.__init__`'s signature no longer contains `server_configs`, `discovery_map`,
  or `known_tools`.
- `ToolRouteResolver` has no `_log_routing_coverage` method and no `_discovery_map` attribute.
- `ToolExecutor.__init__` no longer has a `discovery_map` parameter and no longer passes
  `server_configs`/`discovery_map` to `ToolRouteResolver`.
- `ToolExecutor.__init__` still accepts `server_configs` and still sets `self._server_configs`,
  and `_check_startup_mode()` still works unchanged (startup_mode=none detection is unaffected).
- No remaining reference to the removed parameters/method anywhere in `scripts/` or `tests/`
  (grep confirms no hits for `_log_routing_coverage`, and no `ToolRouteResolver(` call site still
  passes `server_configs=`/positional server_configs, `discovery_map=`, or `known_tools=`).
- Full test suite passes (`uv run pytest`), with tests for the removed compatibility surface
  either deleted or rewritten against the new constructor signature, and all still-relevant
  routing behavior (RuntimeToolRegistry resolution, strict_mode, warn_on_missing) still covered.
