# Cache stampede protection can cause cascading failures

## Priority

Medium

## Target Files

- `scripts/shared/tool_executor.py` — `_execute_with_stampede_protection()`, `_raw_execute()`

## Background

The `_execute_with_stampede_protection()` method prevents stampede effects by sharing an inflight future among concurrent callers requesting the same cached tool result. If the first caller's execution fails, all waiters receive the exception.

## Problem

In `tool_executor.py:164-195`:

```python
async def _execute_with_stampede_protection(
    self, cache_key: str, tool_name: str, args: dict[str, Any]
) -> ToolCallResult:
    inflight = self._inflight.get(cache_key)
    if inflight is not None and not inflight.done():
        return await inflight
    ...
    try:
        result = await self._raw_execute(tool_name, args)
    except Exception as exc:
        if not inflight.done():
            inflight.set_exception(exc)
        raise
    else:
        if not inflight.done():
            inflight.set_result(result)
        return result
```

When `_raw_execute()` raises a TransportError, `inflight.set_exception(exc)` propagates the exception to all waiting requests. This is intentional behavior but means that a transient network failure causes all concurrent requests for the same cached key to fail simultaneously. Additionally, `_record_transport_error()` records the failure in the server health registry, potentially affecting other tool calls on the same server.

## Reason for Change

A single transient failure affects all concurrent callers of the same cache key, even though some might have succeeded if their requests were processed independently. This amplifies the blast radius of temporary network issues and can cause cascading failures across multiple tools on the same MCP server.

## Implementation Intent

Decouple stampede protection from error propagation. Allow individual waiters to retry independently when the shared request fails, rather than forcing all waiters to receive the same exception. Add retry logic for transient errors.

## Implementation Instructions

1. Modify `_execute_with_stampede_protection()` to not propagate exceptions to waiters. Instead, remove the failed inflight future and allow each waiter to make its own independent call.
2. Add a retry mechanism for TransportError that respects the server's health state.
3. When the shared request fails, log a warning but do not set an exception on the inflight future.
4. Ensure the inflight future is cleaned up before allowing retries.

## Acceptance Criteria

- [ ] Transient failures affect only the initiating request, not concurrent waiters
- [ ] Retry mechanism exists for TransportError with backoff
- [ ] Server health registry updates are delayed for transient errors
- [ ] Concurrent requests for the same cache key can succeed independently
