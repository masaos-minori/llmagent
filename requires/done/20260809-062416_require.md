# Refactor RAG ingestion into an atomic URL-level transaction

## Priority
High

## Target files
- `scripts/rag/ingestion/ingester.py`
- `scripts/rag/ingestion/document_manager.py`
- `scripts/db/helper.py`
- relevant ingestion tests

## Background
The current RAG ingestion flow processes URLs through independent database connections and per-chunk commits. When parsing, embedding, or storage fails partway through, the previous searchable document can be lost and the replacement remains incomplete. The current `(chunk_ok, embed_ok)` result tuple cannot reliably distinguish parse, validation, embedding, and storage failures.

## Problem
Data integrity risk: partial ingestion leaves the system in an inconsistent state where either the old document is deleted but the new one is incomplete, or vice versa. Failure modes are ambiguous due to the binary `(chunk_ok, embed_ok)` result format.

## Reason for change
Without atomic URL-level transactions, forced re-ingestion failures can corrupt the searchable corpus. This affects reliability of the entire RAG pipeline when documents need to be updated.

## Implementation intent
Treat one URL and its complete chunk set as the smallest commit unit. Keep HTTP embedding calls parallel where useful, but perform all canonical database changes through one connection and one transaction after every chunk has been prepared successfully.

## Implementation instructions
1. Parse and validate the complete URL group before changing the database.
2. Generate all embeddings before deleting or replacing an existing document.
2b. After starting the transaction (step 6), delete the existing document within the transaction boundary — not before it.
3. Keep HTTP embedding calls parallelizable, but remove database access and commits from embedding workers.
4. Introduce an immutable `PreparedChunk` DTO containing all validated values required for insertion. Define fields as follows:
   ```python
   @dataclasses.dataclass(frozen=True)
   class PreparedChunk:
       doc_id: int
       chunk_index: int
       content: str
       normalized_content: str | None
       embedding_blob: bytes  # float32 BLOB already converted via floats_to_blob()
       chunk_type: str
       source_file: str
   ```
5. Replace `(chunk_ok, embed_ok)` with explicit failure reason enumeration. Define as follows:
   ```python
   class IngestionFailureReason(str, Enum):
       PARSE_FAILED = "parse_failed"
       VALIDATION_FAILED = "validation_failed"
       EMBEDDING_FAILED = "embedding_failed"
       STORAGE_FAILED = "storage_failed"
   ```
6. Use `SQLiteHelper.begin_immediate()` for one URL-level transaction.
7. Inside the transaction, delete the existing vector rows and document, insert the replacement document, then insert all chunks and vectors.
8. Roll back the entire URL update if any database operation fails.
9. Move the complete URL group to `registered/` only after a successful commit. Commit success means all chunks in the URL group were prepared without failure.
10. Route retries at URL-group level rather than moving individual failed chunks away from a partially committed document.
11. Preserve the previous searchable document when forced re-ingestion fails.
12. Invalidate the semantic cache only when at least one URL-level corpus transaction commits successfully.
13. Add `rag_pipeline_service_url` as a constructor parameter of `RagIngester.__init__`, cache it, and use it for cache invalidation instead of calling `ConfigLoader().load("ingester.toml")` at the end of `ingest_all()`.

## Acceptance criteria
- A failed forced re-ingestion leaves the previous document, chunks, FTS rows, and vectors unchanged.
- A successful URL ingestion commits the document, every chunk, FTS trigger updates, and every vector as one unit.
- No worker opens a database connection or commits an individual chunk.
- A URL group with one failed preparation does not modify the database.
- Files are moved to `registered/` only after commit.
- All-skipped and all-failed runs do not invalidate the cache.
- Cache invalidation occurs only when at least one URL-group commits successfully; each group's commit status is tracked independently.
- Failure logs and metadata identify parse, validation, embedding, or storage failure unambiguously.
