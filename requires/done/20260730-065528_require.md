# Require: Define first-class readiness and status behavior for `persistent` MCP servers

## Priority

High

## Target files

- `scripts/shared/mcp_config.py`
- `scripts/agent/startup.py`
- `scripts/agent/repl_health.py`
- `scripts/agent/services/mcp_status.py`
- `scripts/agent/services/mcp_tool_discovery.py`
- MCP operations documentation

## Background

`persistent` startup mode represents an externally managed HTTP MCP server. For persistent servers, the Agent should not start, stop, restart, manage PID/process group, or assume subprocess ownership. Instead, the Agent should validate persistent servers through HTTP-level checks.

## Problem

Subprocess and persistent servers have different operational responsibilities. For subprocess servers, the Agent owns the lifecycle. For persistent servers, the Agent can only observe and validate `/health`, `/v1/tools`, auth behavior, schema compatibility, tool metadata quality, and runtime registry inclusion. If this distinction is not explicit, persistent servers may appear unhealthy or unmanaged even when they are correctly managed externally.

## Reason for change

Make `persistent` a first-class supported startup mode with clear readiness and status semantics.

## Implementation intent

### 1. Define ownership semantics

Document that persistent servers are externally managed.

For persistent servers:

- `managed=False` is normal.
- PID and PGID are normally unavailable.
- Agent lifecycle state should not imply subprocess ownership.
- Restart guidance should point to the external service manager.

### 2. Define persistent readiness

Persistent readiness should be based on:

- `/health` reachable
- `/health` parseable
- `ready=true` or acceptable degraded state
- `/v1/tools` discovery success
- compatible schema version
- valid tool metadata
- successful auth
- RuntimeToolRegistry registration

### 3. Define production and local behavior

Recommended production behavior:

- Required persistent server unreachable -> fatal
- Auth failure -> fatal
- Invalid `/v1/tools` schema -> fatal
- Required metadata missing -> fatal
- Duplicate tool name -> fatal

Recommended local behavior:

- Unreachable persistent server -> warning or degraded
- Tools from unreachable server -> unavailable or hidden from LLM
- REPL may continue when safe

### 4. Update status display

For persistent servers, `/mcp status` should show:

- startup mode as `persistent`
- process management as `external`
- no PID/PGID or `external`
- health state
- discovery state
- operator action guidance

Do not treat `managed=False` as an error for persistent servers.

### 5. Update runbook guidance

Add operational guidance for persistent failure cases:

- External service not running
- Auth token mismatch
- `/health` returns 503
- `/v1/tools` schema invalid
- Tool metadata invalid
- Upstream dependency degraded

## Acceptance criteria

- [ ] `persistent` startup mode is documented as officially supported
- [ ] Persistent servers are not treated as missing managed subprocesses
- [ ] Persistent readiness is based on `/health` and `/v1/tools` validation
- [ ] Production/local behavior is documented
- [ ] `/mcp status` distinguishes persistent from subprocess servers
- [ ] `managed=False` is normal for persistent servers
- [ ] Operator messages for persistent failures point to external-service recovery

## Tests

- Verify persistent server startup mode loads without subprocess errors
- Verify `/mcp status` shows `persistent` and `external` for persistent servers
- Verify production fatal behavior for required persistent server failures
- Verify local warning/degraded behavior for unreachable persistent servers
- Verify runbook guidance covers persistent failure scenarios
