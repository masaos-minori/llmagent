# Separate session-not-found vs no-messages error paths in restore_session

## Priority
Medium

## Target files
- scripts/agent/services/session_restore.py
- scripts/agent/session_message_repo.py
- scripts/agent/services/exceptions.py

## Background
During adversarial review of the agent startup process, we traced the full session restoration flow through session_restore.py. The restore_session() method rebuilds history, switches session ID, and resets stats. However, there's no evidence of comprehensive error handling for edge cases where the session might exist but have no messages, or where the session might be corrupted.

## Problem
The current `restore_session()` method raises `SessionNotFoundError` with the message `"Session {session_id} not found or has no messages."`. This is ambiguous because:

1. `fetch_messages()` in session_message_repo.py returns an empty list when no messages exist for a session, without distinguishing between "session doesn't exist" and "session exists but has no messages"
2. The caller cannot tell which condition triggered the error
3. Users cannot take appropriate action based on the specific failure mode

## Reason for change
Distinguishing these two failure modes allows more precise error reporting and enables callers to handle each case differently (e.g., creating a new session vs. informing the user that the restored session has no history).

## Implementation intent
Add a way to distinguish between "session not found" and "no messages" in the fetch operation. Options include:
- Adding a boolean flag to indicate whether the session was found
- Returning a tuple/list with both the messages and a status indicator
- Using a sentinel value instead of an empty list

## Implementation instructions
1. Modify `fetch_messages()` in `session_message_repo.py` to return a tuple `(messages: list[LLMMessage], session_found: bool)` where `session_found` indicates whether the session exists in the database
2. Update all call sites of `fetch_messages()` to handle the new return type
3. Update `restore_session()` in `session_restore.py` to use the new return type and provide distinct error messages for each case
4. Consider adding a new exception class `SessionNoMessagesError` in `services/exceptions.py` for the no-messages case

## Acceptance criteria
- [ ] Error messages clearly distinguish between "session not found" and "session has no messages"
- [ ] All call sites of `fetch_messages()` are updated to handle the new return type
- [ ] No regressions in normal operation when registry is available

## Tests
- Unit test for `fetch_messages()` with various session states
- Integration test verifying diagnostic output during startup/shutdown

## Documentation Impact
If DiagnosticsConfig is extended, update documentation to reflect the new state.

## Out of Scope
- Changing the registry initialization order
- Adding retry logic for health checks

## AI Implementation Instruction
Modify only _filter_sensitive_fields() in diagnostic_store.py. Add a new state to McpAvailability enum if needed. Update the fallback logic to use the new state instead of UNKNOWN when registry is None.
