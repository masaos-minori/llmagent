# Approval task ID persists across turns without validation

## Priority

Medium

## Target Files

- `scripts/agent/commands/cmd_workflow.py` — `_cmd_approve()`, `_cmd_reject()`
- `scripts/agent/orchestrator.py` — `_init_workflow_task()`

## Background

After approving a workflow step via `/approve`, the approved task ID is stored in `ctx.turn.pending_approval_task_id`. This value is used in the next turn to restore the associated task.

## Problem

In `cmd_workflow.py:124-129`:

```python
self._ctx.turn.pending_approval_id = None
self._ctx.workflow.approval_pending = False
self._ctx.turn.pending_approval_task_id = task_id
```

Similarly in `_cmd_reject()` (`cmd_workflow.py:175-177`):

```python
self._ctx.turn.pending_approval_id = None
self._ctx.workflow.approval_pending = False
self._ctx.turn.pending_approval_task_id = task_id
```

The `pending_approval_task_id` is used in the next turn by `_init_workflow_task()`:

```python
(workflow_id, task,) = self._init_workflow_task(
    ctx, session_id, ctx.turn.pending_approval_task_id, store
)
```

However, if the user approves another approval after this, `task_id` is overwritten. The original approval's associated task may not be correctly restored. Additionally, when `_init_workflow_task()` receives an `existing_task_id`, it retrieves the task via `get_task_by_id()`, but even if the retrieved task has status "halted", processing continues without error.

## Reason for Change

When multiple approvals exist, the pending task ID can be silently overwritten, causing the wrong task to be restored in the next turn. Tasks with halted status are processed without validation, potentially causing unexpected behavior.

## Implementation Intent

Validate existing values before overwriting `pending_approval_task_id`. Clear the field immediately after use. Add status validation for restored tasks.

## Implementation Instructions

1. Before setting `pending_approval_task_id`, check if a non-None value already exists. If so, log a warning indicating which task ID would be overwritten.
2. After `_init_workflow_task()` uses the value, clear `pending_approval_task_id` to prevent accidental reuse.
3. In `_init_workflow_task()`, validate the retrieved task's status. If "halted", raise an error or return a specific error message instead of proceeding.
4. Consider using a queue-based approach for pending task IDs to support multiple concurrent approvals.

## Acceptance Criteria

- [ ] Warning logged when `pending_approval_task_id` would be overwritten
- [ ] `pending_approval_task_id` cleared after use
- [ ] Halted tasks rejected with error when restored
- [ ] Multiple concurrent approvals handled correctly

## Tests

- Unit test: approve two approvals in sequence; verify second approval logs warning about overwrite
- Integration test: approve approval then reject another; verify correct task restoration for both
- Stress test: rapid successive approvals; verify no task ID corruption
