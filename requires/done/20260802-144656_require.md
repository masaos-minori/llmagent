# Fix docs/04_mcp_06_13 watchdog inaccuracies: degraded_reason contradiction and nonexistent config/log strings

## Priority
Medium

## Target files
- `docs/04_mcp_06_13_watchdog-health-reasons-scheduling-part1.md`
- `docs/04_mcp_06_13_watchdog-health-reasons-scheduling-part2.md`
- Cross-referenced against `docs/04_mcp_06_12_watchdog-configuration-monitoring.md` (do not modify this file; it is confirmed accurate)

## Background
`docs/04_mcp_06_13-part1` (lines 49–70) describes `record_failure(reason=...)` and
`record_degraded()` as if degraded-reason recording is an active, working mechanism.
`docs/04_mcp_06_12` (lines 47–56) states the opposite: `McpServerHealthRegistry.record_degraded()`
has zero call sites in current `scripts/` and is dead code, and `get_degraded_reason()` will
therefore always return `None`. These two docs directly contradict each other about the same
mechanism.

Separately, `docs/04_mcp_06_13-part2` (lines 18–68) documents a config option
`repeated_tool_error_threshold`, a `[debug]`-prefixed log line format, and grep patterns
`error_type=tool` / `error_type=transport` (logfmt-style) as the way to monitor tool/transport
errors. None of these strings exist in current source.

## Problem
Both parts of `06_13` describe mechanisms and strings that do not match current source, verified
as follows:

**Degraded-reason recording (part1):**
- `scripts/shared/mcp_health.py:37` — `record_failure(self, server_key: str) -> McpServerHealthState`
  takes **no `reason` parameter**. The doc's `registry.record_failure(reason=str(body_reason))`
  would raise `TypeError` if executed.
- `scripts/shared/mcp_health.py:54` — `record_degraded(self, server_key: str, reason: str | None = None) -> None`
  is the only method that accepts `reason=`, but it has **zero call sites** anywhere in `scripts/`
  (confirmed by grep) — it is dead code.
- `record_failure(server_key)` (no `reason`) is actually called from
  `scripts/shared/tool_executor.py:115` and `scripts/shared/tool_transport_invoker.py:157`.
- `get_degraded_reason(key)` is called from `scripts/agent/commands/cmd_mcp.py:189` and `:202`,
  but since `record_degraded()` never runs, it always returns `None`.
- Conclusion: `docs/04_mcp_06_12` is accurate; `docs/04_mcp_06_13-part1` is wrong on two counts
  (invents a nonexistent `reason` kwarg on `record_failure`, and presents the dead
  `record_degraded()` path as active).

**Nonexistent config/log strings (part2):**
- `repeated_tool_error_threshold`: zero hits in `scripts/`. This was a real constructor parameter
  on `ToolExecutor` that was found to be dead (stored but never read) and deliberately removed —
  see `implementations/done/20260711-171622_tool_executor_remove_unused_error_threshold.md`.
- `[debug]` log prefix: zero hits anywhere in `scripts/`.
- Logfmt-style `error_type=tool` / `error_type=transport` (as grep-able plain text tokens): zero
  hits. No `structlog`-based logfmt output exists in `scripts/` (`rules/coding.md` explicitly lists
  "temporary structlog debug calls" only as something never to commit, i.e. structlog is not the
  production logging mechanism).
- The real mechanisms are two separate, unconnected pieces:
  1. **Per-server error counters, no threshold/warning** — `scripts/shared/tool_transport_invoker.py`:
     - `self.stat_tool_errors: dict[str, int] = {}` (line 38) and
       `self.stat_transport_errors: dict[str, int] = {}` (line 39), incremented in
       `_record_success()` (tool errors, lines 144–147) and `_record_transport_error()`
       (transport errors, lines 153–154). **No threshold check and no "repeated tool errors"
       warning log exists** tied to these counters.
     - Transport failures are logged via plain stdlib `logging` at line 158–160:
       `logger.warning("transport failure for %r: %s (state=%s)", server_key, e, state.value)` —
       not JSON, not logfmt.
  2. **Structured JSON audit log with an `error_type` field** — `scripts/agent/tool_audit.py`,
     function `audit_tool_exec(ctx, tool_name, args, is_error, mcp_request_id, error_type="", artifact_uri=None, source="") -> None`
     (line 159), which builds a `ToolExecEvent` and emits it via
     `ctx.services_required.audit_logger.info(_json_dumps(dataclasses.asdict(evt)))` (line 195),
     where `_json_dumps` is `scripts/shared/json_utils.py:23`
     (`orjson.dumps(obj, option=orjson.OPT_SORT_KEYS)`, decoded to `str`).
     `ToolExecEvent` (`scripts/agent/shared/models.py:44-61`) has these relevant fields:
     - `"event": "tool_exec"` (literal, top-level)
     - `"is_error": bool`
     - `"error_type": str` — one of `"transport"`, `"tool"`, or `""` (empty on success)
     - plus `task_id`, `tool`, `operation_type`, `resource_scope`, `mcp_request_id`, `args_preview`,
       `ts`, `source`, `workflow_id`, `session_id`, `artifact_uri`
     The real greppable/jq-able JSON tokens are `"error_type":"tool"` and
     `"error_type":"transport"` (as JSON key/value pairs, sorted keys via orjson), with
     `"event":"tool_exec"` identifying the log line — never a `key=value` logfmt token and never
     prefixed by `[debug]`.

## Reason for change
An operator following `06_13-part2`'s documented grep patterns
(`grep "error_type=tool" agent.log`, `grep "repeated tool errors" agent.log`,
`grep "error_type=transport" agent.log`) would get zero matches against real log output, because
the actual logs are structured JSON, not logfmt, and no threshold-triggered warning exists at all.
Anyone reading `06_13-part1` in isolation would believe degraded-reason recording is an active,
working feature when it is confirmed dead code with zero call sites. Both are confirmed factual
inaccuracies per `rules/coding.md`'s "Current behavior" classification table — this is a
"Documentation fix required" case (the doc itself is wrong; do not patch code to match the doc).

## Implementation intent
Rewrite `06_13-part1`'s degraded-reason description to match `06_12`'s confirmed-accurate
account: state plainly that `record_degraded()` / reason-carrying failure recording exists in
source but has no call sites and is not exercised (dead code), and that `record_failure()` (the
method actually called in `scripts/`) takes no `reason` parameter. Cross-reference `06_12` rather
than duplicating the full explanation.

Rewrite `06_13-part2`'s config/log-string references to describe the two real, separate
mechanisms found in source: the unconnected `stat_tool_errors`/`stat_transport_errors` counters
in `ToolTransportInvoker` (no threshold, no warning log), and the actual structured JSON audit
event (`ToolExecEvent`, `event=tool_exec`, `error_type` field) emitted by `audit_tool_exec()`.
Replace the logfmt-style grep examples with JSON-appropriate lookups (e.g. `grep` for the raw
JSON substring, or `jq` filters against the `error_type` / `event` fields), scoped to whatever log
file `audit_logger` actually writes to. Do not invent a working threshold-warning mechanism that
does not exist — accurately reflect that no such warning currently fires.
