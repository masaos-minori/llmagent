# Fix Qwen3 embedding dimension contract as a 1024-dimensional code constant

## Priority

High

## Target files

- `scripts/db/store_protocols.py` — `get_embedding_dims()` (line 27-30) currently returns `build_db_config().embedding_dims`.
- `scripts/db/config.py` — `DbConfig.embedding_dims: int = 384` field (line 32), validated in `__post_init__` (line 46-47), and read in `build_db_config()` via `embedding_dims=int(cfg.get("embedding_dims", 384))` (line 82).
- `config/agent.toml` — `embedding_dims = 384` (line 17) and `memory_embed_dim = 384` (line 88).
- `config/ingester.toml` — `embedding_dims = 384` (line 18).
- `scripts/db/create_schema.py` and `scripts/db/schema_sql.py` — `create_rag_schema()` / `create_session_schema()` call `get_embedding_dims()` and pass `dims` into `build_rag_schema_sql(dims)` / `build_session_schema_sql(dims)`, which substitute the `DIMS` placeholder into the `chunks_vec.embedding float[DIMS]` and `memories_vec.embedding float[DIMS]` virtual table DDL. This path already flows through `get_embedding_dims()`, so it needs no structural change once that function returns the constant.

Removing the key from `agent.toml` (as the issue instructs) does not remove this fallback — it silently keeps producing `384`.
- `scripts/agent/factory.py` (lines 371, 421-427) — passes `ctx.cfg.memory.memory_embed_dim` into `MemoryStore(embed_dim=...)` and `EmbeddingClientConfig(embed_dim=...)`. Both would keep receiving the stale `384` default from `config_builders.py` even after the DB layer is fixed to `1024`.
- `scripts/rag/ingestion/ingester.py` (line 70, `self._expected_dims = int(cfg.get("embedding_dims", 384))`; docstring at line 226-229) — reads `embedding_dims` from ingester config independently of `db/store_protocols.py`. The `_expected_dims` removal is covered by `20260802-070538_require.md` (E5→Qwen3 raw-text migration). Do not remove the code-level read here; coordinate so the config key is removed exactly once.

## Background

The system is mid-migration from a 384-dimensional embedding model (`multilingual-E5-small`, per `docs/01_overview-files-01-build.md` and `docs/01_overview-arch-01-process.md`) to a 1024-dimensional Qwen3 embedding model (`Qwen3-Embedding-0.6B-Q8_0.gguf`). This migration is tracked across a series of sibling issues in `issues/` (`20260731_02` through `20260731_06`), covering raw-text request normalization, chunk-splitting quality, integration verification, and stale-documentation cleanup. This requirement covers only the first step: replacing the currently-configurable `embedding_dims` value with a fixed 1024 code constant.

Verified against current source:
- `DbConfig.embedding_dims` exists in `scripts/db/config.py` and defaults to `384`.
- `build_db_config()` reads `embedding_dims` from `agent.toml` (default `384`).
- `get_embedding_dims()` in `scripts/db/store_protocols.py` returns `build_db_config().embedding_dims`.
- `config/agent.toml` contains both `embedding_dims = 384` and `memory_embed_dim = 384`.
- `config/ingester.toml` contains `embedding_dims = 384`.
- Vector table DDL (`chunks_vec`, `memories_vec` in `scripts/db/schema_sql.py`) is parameterized by a `DIMS` placeholder filled in from `get_embedding_dims()` at schema-creation time, so a single source-of-truth constant is sufficient to fix both tables.

This confirms every factual claim in the source issue still holds in current source.

## Problem

Embedding dimensionality is currently a runtime configuration value (TOML-driven), not an implementation invariant, even though the system supports exactly one embedding model (Qwen3, 1024 dimensions). This creates a live risk that `chunks_vec` or `memories_vec` gets created with `float[384]` (or any other value an operator puts in a TOML file) instead of the only dimension the system actually supports, `float[1024]`. In addition, a startup consistency check (`scripts/agent/startup.py::_check_embedding_dimensions()`) and a separate memory-layer configuration path (`MemoryConfig.memory_embed_dim`, built in `scripts/agent/config_builders.py`) currently rely on independently-configurable 384-defaulted values that are not addressed by the source issue's file list, and will either break (`AttributeError`) or silently retain a stale `384` fallback if the DB-layer change is made in isolation.

## Reason for change

Configuration drift between `db/config.py`, `agent.toml`, `ingester.toml`, and the memory-layer config has already produced two independently-configurable "384" defaults (`embedding_dims` and `memory_embed_dim`) protected only by a startup equality check. Making 1024 a compile-time constant removes this class of drift entirely, and doing it now (before the rest of the Qwen3 migration issues land) prevents new code from reintroducing a configurable dimension.

## Implementation intent

Introduce a single named constant (e.g. `QWEN3_EMBEDDING_DIMS = 1024`) in the DB layer that all embedding-dimension consumers reference, directly or transitively, instead of reading a dimension value from any TOML file. `get_embedding_dims()` becomes the one function that returns this constant; everything that today reads `embedding_dims` or `memory_embed_dim` from config should either be removed (if it duplicates the constant) or redirected to call `get_embedding_dims()` (if it needs the value). Do not implement any migration of existing vector data — old `rag.sqlite` / `session.sqlite` files are expected to be recreated, not migrated.

## Implementation instructions

1. Define `QWEN3_EMBEDDING_DIMS = 1024` as a module-level constant in `scripts/db/store_protocols.py` (or another appropriate shared location in the `db/` layer — the next phase should choose based on avoiding import cycles with `db/config.py`).
2. Update `get_embedding_dims()` in `scripts/db/store_protocols.py` to return the constant directly, no longer calling `build_db_config().embedding_dims`. Keep `get_embedding_bytes()` deriving from `get_embedding_dims()` unchanged in behavior. Update the module docstring (line 13-14) which still says "return configured dimension count (default 384)".
3. Update `scripts/db/config.py`:
   - Remove the `embedding_dims` field from `DbConfig` (line 32).
   - Remove the associated `__post_init__` validation (lines 46-47) — no longer applicable once dimension is a constant, not user input.
   - Remove `embedding_dims=int(cfg.get("embedding_dims", 384))` from `build_db_config()` (line 82).
4. Update `config/agent.toml`: remove `embedding_dims = 384` (line 17) and `memory_embed_dim = 384` (line 88).
5. Update `config/ingester.toml`: remove `embedding_dims = 384` (line 18). The code-level read of `embedding_dims` in `scripts/rag/ingestion/ingester.py` (line 70, `self._expected_dims`) is handled by `20260802-070538_require.md` — coordinate so the config key is removed exactly once.
6. Remove the startup consistency check in `scripts/agent/startup.py::_check_embedding_dimensions()` (lines 270-286): it currently calls `build_db_config().embedding_dims`, which will no longer exist. Since dimension is now a fixed constant and cannot mismatch on the DB side, remove the check entirely. No replacement check is needed because `QWEN3_EMBEDDING_DIMS` is a compile-time invariant — no runtime path can produce a mismatch.

7. Remove `MemoryConfig.memory_embed_dim` (`scripts/agent/config_dataclasses.py` line 221, built in `scripts/agent/config_builders.py` lines 339-344/376, consumed in `scripts/agent/factory.py` lines 371 and 421-427): since `memory_embed_dim` is being removed from `agent.toml`, the code-level default of `384` in `config_builders.py` must not silently persist as the value passed to `MemoryStore(embed_dim=...)` and `EmbeddingClientConfig(embed_dim=...)`. Remove the field and its plumbing, sourcing `1024` from `get_embedding_dims()` at the call sites in `factory.py`. This merges cleanly with `issues/20260731_02_issue.md`'s planned removal of `EmbeddingClientConfig.embed_dim` — both are handled in the same change set.
8. Ensure schema creation (`scripts/db/create_schema.py`, `scripts/db/schema_sql.py`) continues to call `get_embedding_dims()` for the `DIMS` placeholder in `chunks_vec` and `memories_vec` DDL — no structural change needed here since it already flows through the function being fixed, but confirm no other hard-coded `384` remains nearby.
9. Recreate both vector databases (`rag.sqlite`, `session.sqlite`) using the fixed schema so `chunks_vec.embedding` and `memories_vec.embedding` are created as `float[1024]`. Do not implement or write any migration path from the old 384-dimensional data — existing vectors are expected to be discarded and re-ingested.

## Acceptance criteria

- `get_embedding_dims()` always returns `1024`, with no code path that reads it from a TOML file.
- No TOML file under `config/` contains `embedding_dims`.
- No TOML file under `config/` contains `memory_embed_dim`.
- `DbConfig` (in `scripts/db/config.py`) no longer has an `embedding_dims` field.
- `scripts/agent/startup.py::_check_embedding_dimensions()` is removed entirely — the agent starts without an `AttributeError`.
- `MemoryConfig.memory_embed_dim` is removed; no remaining code path passes an embed-dimension value derived from config into `MemoryStore` / `EmbeddingClientConfig`.
- A newly created `rag.sqlite` creates `chunks_vec.embedding float[1024]`.
- A newly created `session.sqlite` creates `memories_vec.embedding float[1024]`.
- No migration from old vector data is implemented.
