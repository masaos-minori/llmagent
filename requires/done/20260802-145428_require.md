# Correct docs/04_mcp_08_tool_capability_naming_convention.md: browser_fetch's capabilities=("web_fetch",) is test-fixture-only, not production

## Priority
Medium

## Target files
- `docs/04_mcp_08_tool_capability_naming_convention.md` (lines 84-91: "具体例" / "現在採用しているツール" and "ステータス" sections)

## Background
`docs/04_mcp_08_tool_capability_naming_convention.md` documents a proposed capability-naming
convention for MCP tools (`{domain}.{action}` strings, e.g. `filesystem.read`). It further
claims, under "現在採用しているツール" (tools currently adopting this), that `browser_fetch`
(from `web_search-mcp`) has adopted `capabilities=("web_fetch",)` in implementation, and its
"ステータス" section states this convention "was first adopted in implementation because
web_search-mcp's browser_fetch declared the web_fetch capability."

An issue (`issues/20260802-075026_mcp_browser_fetch_capabilities_prod_vs_test.md`) raised
suspicion that this documented value does not actually exist in production code and may only
be present in a test fixture.

## Problem
Verification against current source confirms the suspicion:

- Production tool definition `scripts/mcp_servers/web_search/web_search_tools.py` (`TOOL_LIST`)
  defines the `browser_fetch` tool entry (lines 39-65) with keys `name`, `description`,
  `inputSchema`, `status: "production"`, and `config_dependent: True` — there is **no
  `capabilities` key at all** for `browser_fetch` in this production definition.
- `scripts/agent/services/mcp_tool_discovery.py` (lines ~274-278, ~328) shows that when a
  discovered tool entry has no `capabilities` key, the discovery service tolerates the
  absence and the resulting `RuntimeTool.capabilities` defaults to an empty tuple `()`
  (confirmed also by `scripts/shared/runtime_tool.py` lines 79-109: `capabilities` defaults
  to `()` when not explicitly supplied).
- The **only** place in the repository where `capabilities=("web_fetch",)` literally appears
  is `tests/test_runtime_tool_routing_integration.py` line 84, inside
  `_make_runtime_registry()`, a test helper that manually constructs a `RuntimeTool` via
  `build_runtime_tool(...)` for the purpose of exercising routing logic in isolation. This
  value is **not** derived from `web_search_tools.py`'s `TOOL_LIST` or any production
  discovery path — it is hardcoded test fixture data.
- A `grep` across `scripts/` and `tests/` for `capabilities` confirms every other production
  occurrence (`scripts/agent/config_builders.py`, `scripts/agent/services/mcp_tool_discovery.py`,
  `scripts/shared/runtime_tool.py`) relates to the generic capability *mechanism*, not to any
  concrete `browser_fetch` value.

Therefore, in actual production behavior today, `browser_fetch`'s runtime `capabilities` value
is the **empty tuple `()`** (the default, since no server declares a `capabilities` key for
this tool) — not `("web_fetch",)`. The documentation's claim that this convention has been
"adopted in implementation" by `browser_fetch` is factually incorrect as of current source.

(Supporting observation, not in scope to act on beyond noting it: the literal string
`"web_fetch"` also does not match the document's own naming-convention regex
`^[a-z][a-z0-9_]*(\.[a-z][a-z0-9_]*)+$`, which requires at least one dot-separated segment —
further evidence this was never a real adopted value, just an illustrative/test string that
leaked into the doc.)

## Reason for change
Per `rules/coding.md` §"Documentation notes — Current behavior classification", a doc note
describing a gap between documented and actual behavior must be classified before being
written. This case is a **"Documentation fix required"** classification: the doc itself is
wrong (it asserts implementation adoption that does not exist in production code). Leaving
it uncorrected risks an implementer building a tool-capability-aware integration around a
value (`("web_fetch",)`) that will never actually be returned by the `browser_fetch` tool in
production, causing silent integration/routing failures for any logic that branches on this
capability string.

## Implementation intent
Correct `docs/04_mcp_08_tool_capability_naming_convention.md` so it accurately reflects that:
1. The capability-naming convention itself remains a valid, optional, proposed standard
   (no change needed to that part of the doc).
2. `browser_fetch` has **not** actually adopted this convention in production — no MCP tool
   in the current codebase declares a `capabilities` value that matches the documented naming
   convention. The document must not claim otherwise.
3. Either remove the "現在採用しているツール" (currently adopted) claim and the
   corresponding "ステータス" sentence entirely (since there is no real adopter), or
   explicitly relabel it to state that `capabilities=("web_fetch",)` exists only as an
   illustrative/test-fixture value in `tests/test_runtime_tool_routing_integration.py` and
   is not present in any production `TOOL_LIST` or discovery response.
Do not change any production or test code — this is a documentation-only correction, per the
issue's explicit "Out of Scope" note.
