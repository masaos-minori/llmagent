# Reduce diff-memo-style detail in docs/05_agent_90_inconsistencies_and_known_issues.md

## Priority
Medium

## Target files
- `docs/05_agent_90_inconsistencies_and_known_issues.md`

## Background
The `05_agent_*.md` document set mixes design/operational judgment with content that is mechanically derivable from code. A review (`memo-doc-agent-review.md`) identified what to keep vs. remove per chapter.

## Problem
This chapter is the canonical source for known issues and unresolved items, but a Known Issues section that degrades into a plain bug list or diff memo loses its value as an operational/decision reference.

## Reason for change
Each entry must explain: what the issue means, why it is a problem, what operators should watch for, and the criteria for deciding whether/how to fix it — not just "diff observed at file X line Y."

## Implementation intent
Restructure each entry to have operational meaning. Remove bare code-diff memos and "confirmed at file:line" notes with no operational framing. Classify every entry per the five-way classification before keeping, cross-referencing, fixing, or deleting.

## Implementation instructions
1. Read the target file in full.
2. For each entry, identify: bare code-diff memos, "confirmed at file X line Y" notes with no operational meaning, plain implementation-visible enumerations.
3. Remove or compress those sections while preserving: the meaning of each known issue, why it is a problem, operational cautions, fix-decision criteria, the classification of items as removed/migrated/needs-confirmation, and the reasoning behind each Needs Confirmation entry.
4. Before removing any entry, verify against current code whether the discrepancy still applies; do not delete a note without this verification.
5. Cross-reference actual bug-track issues under `issues/` where an "Implementation fix required" classification applies, rather than duplicating the description inline.
6. Restructure remaining content to follow the template: Purpose / Design Intent / Responsibility Boundary / Key Constraints / Operational Notes / Known Limitations / Related Docs.
7. Ensure every entry is classified per the five-way classification (Accepted current specification / Implementation fix required / Documentation fix required / Issue already tracked / Obsolete and removable).
8. If a new "Implementation fix required" item is discovered, file it as a separate issue under `issues/` rather than only noting it here.
9. If a design rationale cannot be recovered from the current text, mark it `Needs Confirmation` rather than guessing.
10. Run `python tools/check_agent_docs_consistency.py` after editing (includes the obsolete diagnostics/event-name reference check relevant to this chapter).
