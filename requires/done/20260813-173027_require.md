# Type the `server_tool_lists` tool-descriptor shape in `route_resolver.build_discovery_map`

## Priority
Medium

## Target files
- `scripts/shared/route_resolver.py` (`build_discovery_map`)
- `tests/shared/test_route_resolver.py` (`TestBuildDiscoveryMap`, lines ~237-311)
- `tests/shared/test_routing_duplicate_ownership.py` (module-level tests)
- `tests/shared/test_tool_registry.py` (`test_duplicate_live_ownership_detected`, ~line 243)

## Background
`scripts/shared/route_resolver.py::build_discovery_map` has the signature:

```python
def build_discovery_map(
    server_tool_lists: dict[str, list[dict[str, Any]]],
) -> tuple[dict[str, str], dict[str, list[str]]]:
```

`skills/DESIGN.md`'s Pythonic safety constraints state: "Avoid raw `dict[str, Any]` for core
domain data — use `dataclasses`, Pydantic models, or `TypedDict`." The inner
`dict[str, Any]` here represents a tool descriptor (one entry from a server's tool list) and is
exactly this kind of domain data, so the raw-`dict[str, Any]` parameter type is a genuine gap
against that rule.

Verified against current source (2026-08-13):
- The function body only ever reads one key from each tool descriptor: `tool.get("name")`
  (line 41), which it validates with `isinstance(name, str) or not name` before using it — so the
  function's own runtime contract requires nothing beyond an optional `name` field.
- **Correction to the issue's caller claim**: `build_discovery_map` is **not** currently called
  from `scripts/shared/tool_executor.py` or any other production code path. A repo-wide search
  (`rg "build_discovery_map" scripts/ tests/`, excluding `__pycache__`) shows the only callers are
  three test modules:
  - `tests/shared/test_route_resolver.py` (class `TestBuildDiscoveryMap`)
  - `tests/shared/test_routing_duplicate_ownership.py` (module-level tests)
  - `tests/shared/test_tool_registry.py` (`test_duplicate_live_ownership_detected`)

  — three files, not the four the issue states. `ToolExecutor.__init__` in `tool_executor.py`
  does accept a *different* `discovery_map: dict[str, str] | None` parameter (the *output* shape
  of `build_discovery_map`'s first return value), but nothing in the current codebase actually
  calls `build_discovery_map` to produce that argument; `route_resolver.py`'s own docstrings
  (`ToolRouteResolver.__init__`'s `discovery_map` arg doc, and `_log_routing_coverage`'s docstring)
  confirm this data is validation-only metadata that today has no production producer or consumer
  wired end-to-end. This does not make the function dead code to remove (out of scope here, and a
  separate concern) — it remains a public, directly-tested function, so its parameter type is
  still worth fixing. The fix below only needs to touch `route_resolver.py` and its three test
  importers; `tool_executor.py` does not need to change.
- Existing test fixtures pass tool-descriptor literals with two properties the new `TypedDict`
  must accommodate:
  1. Some literals include an extra `server_key` key that `build_discovery_map` ignores (outer
     dict key is authoritative), e.g. `test_route_resolver.py`'s
     `test_normal_path`/`test_duplicate_tool_first_wins` and `test_tool_registry.py`'s
     `test_duplicate_live_ownership_detected` all pass
     `{"name": "read_file", "server_key": "file_read"}`.
  2. `test_route_resolver.py::TestBuildDiscoveryMap::test_empty_tool_name_skipped` deliberately
     passes malformed entries — `{"name": "", "server_key": "file_read"}` and
     `{"name": None, "server_key": "file_read"}` — to exercise the function's own defensive
     `isinstance(name, str) or not name` skip logic. A `TypedDict` with `name: str` would make
     `{"name": None, ...}` a static type error at that call site even though it is intentionally
     testing runtime behavior, not a caller mistake.
- No existing `TypedDict` for an MCP tool descriptor already exists to reuse. `scripts/shared/tool_spec.py`
  defines `ToolSpec`, a `dataclass` for execution-DAG metadata (call id, args, resource scope) —
  a different concept (an approved *call*, not a discovered tool descriptor) and not a fit to
  extend. `scripts/shared/types.py` already holds several small `TypedDict`s for LLM/tool-call
  wire shapes (`ToolCallDict`, `ToolCallFunction`, etc.) and is the closest existing precedent for
  where a small, dict-shaped domain type belongs in this codebase.

## Problem
`build_discovery_map`'s public signature exposes `dict[str, Any]` for a value that is
domain data (a tool descriptor), which weakens static-analysis coverage for a shape that has a
known, narrow contract (an optional `name` field, with any other keys ignored by this function).
This is exactly the pattern `skills/DESIGN.md` asks reviewers to avoid for core domain data.

## Reason for change
Typing the parameter closes a real, currently-flagged gap against the repo's documented
type-safety rule (`skills/DESIGN.md`) without requiring a runtime behavior change, since
`TypedDict` is a static-only construct. Doing this now (as a small, scoped change) is preferable
to leaving `dict[str, Any]` in place indefinitely; the change was deliberately deferred out of an
unrelated refactor cycle specifically so it could go through this issue → requirement → plan
process rather than being folded into an unrelated diff.

## Implementation intent
1. Define a `TypedDict` describing one tool descriptor entry as consumed by `build_discovery_map`,
   with a `name` field. Since other callers' fixtures attach an extra, ignored `server_key` key,
   make the `TypedDict` tolerant of that key rather than forcing every fixture literal to drop it
   (either by including `server_key` as an optional field on the type, or by another mechanism
   that avoids widespread fixture edits) — pick whichever keeps the diff smallest and most
   accurate to actual usage.
2. Update `build_discovery_map`'s signature to use
   `dict[str, list[ThatTypedDict]]` instead of `dict[str, list[dict[str, Any]]]`.
3. For the one test literal that intentionally passes an invalid `name` (`None`) to test the
   defensive skip path (`test_empty_tool_name_skipped`), do not weaken the `TypedDict`'s `name`
   field to accept `None` just to satisfy this one line — that would defeat the point of typing
   the field. Instead, add a narrow, explained `# type: ignore[...]` (or equivalent scoped
   suppression) on that specific literal, with a comment noting it is deliberately testing
   malformed input, not a typo.
4. This is a static-typing-only change: `build_discovery_map`'s runtime logic, its
   `isinstance`/truthiness guard on `name`, its return value shape, and `ToolRouteResolver`'s
   routing/resolution logic must all remain byte-for-byte unchanged.

## Implementation instructions
- In `scripts/shared/route_resolver.py`:
  - Add a `TypedDict` (e.g. `class ToolDescriptor(TypedDict, total=False):` or similar — name and
    exact field set at the implementer's discretion, but it must be based on rereading every call
    site's literals before finalizing, per the issue's original instruction) with at least a
    `name` field. Use `total=False` (or `NotRequired`) for any field that is not present in every
    fixture literal, so existing literals that omit `server_key` (e.g. in
    `test_routing_duplicate_ownership.py`, which only ever passes `{"name": "..."}"`) remain valid.
  - Change the `server_tool_lists` parameter's annotation from `dict[str, list[dict[str, Any]]]`
    to `dict[str, list[<NewTypedDict>]]`.
  - Remove the now-unused `Any` import only if nothing else in the file still needs it (check
    before removing).
  - Do not change the function body's logic (`tool.get("name")`, the `isinstance`/truthiness
    check, the warning log call, or the returned `route_map`/`duplicates` shapes).
- In the three test files that construct `server_tool_lists` literals
  (`tests/shared/test_route_resolver.py`, `tests/shared/test_routing_duplicate_ownership.py`,
  `tests/shared/test_tool_registry.py`):
  - Re-run mypy/pyright after the signature change and fix any newly-surfaced type errors on the
    literal dicts passed to `build_discovery_map`.
  - For `test_route_resolver.py::TestBuildDiscoveryMap::test_empty_tool_name_skipped`'s two
    malformed literals (`{"name": "", ...}` and `{"name": None, ...}`), keep the runtime
    assertions unchanged; add a scoped type-ignore comment on the `None` literal specifically
    (empty-string `""` is a valid `str` and needs no suppression) explaining it deliberately tests
    the function's defensive skip path.
  - Do not add new required keys to any fixture literal; if any literal is discovered to be
    genuinely missing a field the chosen `TypedDict` would require, stop and report rather than
    inventing a value (per the issue's original instruction).
- Do not modify `scripts/shared/tool_executor.py` — it does not call `build_discovery_map` (see
  Background) and is out of scope for this change.
- Do not modify `ToolRouteResolver`'s routing/resolution logic or the discovery-map *return*
  value shape (`tuple[dict[str, str], dict[str, list[str]]]`), per the issue's original
  out-of-scope note.
