# Add guard tests for orchestrator.py before refactoring

## Priority

High

## Target Files

- `scripts/agent/orchestrator.py` — High-risk-refactor
- `test_orchestrator.py` — MagicMock full usage

## Background

The orchestrator.py module exceeds 500 lines with deep nesting, scattered state mutations, and tight coupling to DB/WorkflowEngine. Tests use MagicMock exclusively (70-80 items), providing zero real integration verification.

## Problem

No regression detection mechanism. Any refactoring risks breaking behavior without detection due to lack of real integration tests.

## Reason for Change

Establish behavioral baseline through guard tests before any refactoring of this component.

## Implementation Intent

Create integration tests using real DB/WorkflowEngine connections to verify actual behavior rather than mocked interfaces.

## Implementation Instructions

1. Create `tests/integration/test_orchestrator_integration.py` with tests for:
   - Turn execution: Test a complete turn from message input to response output
   - Tool call flow: Test tool discovery, validation, execution, and result processing
   - Approval workflow: Test the approval flow with real database interactions
   - Error handling: Test error scenarios (tool failures, network timeouts, etc.)
2. Use SQLite in-memory database for testing
3. Use real WorkflowEngine instead of mocks
4. Run tests to confirm no regressions
5. Proceed with refactoring only after guard tests pass

## Acceptance Criteria

- [ ] Guard tests added for turn execution, tool call flow, and approval workflow
- [ ] All guard tests pass against current codebase
- [ ] No regressions introduced during guard test addition
