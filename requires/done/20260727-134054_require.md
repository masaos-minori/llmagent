# Fix DocumentManager._update_etag hardcoding doc_id=0 instead of the existing document's ID

## Priority

High

## Target Files

- `scripts/rag/ingestion/document_manager.py:61` — `handle_existing_document` calls `self._update_etag(etag, last_modified, fetched_at)` without threading `existing_doc_id` through
- `scripts/rag/ingestion/document_manager.py:94-101` — `_update_etag` does not accept a `doc_id` parameter and constructs `ETagManager(self._db, 0)` with a hardcoded literal `0`
- `scripts/rag/ingestion/etag_manager.py:14-17,63-76` — `ETagManager.__init__` stores `doc_id` and all SQL (`_update_with_freshness`, `_update_null_fill`) filters `WHERE doc_id = ?` using that stored value

## Background

- `docs/03_rag_02_06_ingestion_pipeline-supporting-components.md` (ETagManager section, "境界条件") documents this as a "Needs confirmation" item: `ETagManager` only issues SQL against the `doc_id` it was constructed with, and the caller is responsible for passing the correct one. The doc notes that `DocumentManager`'s ETag update path passes a fixed `0` instead of `existing_doc_id`, and flags this as a possible bug requiring confirmation.
- This requirement is generated from issue `issues/20260727_15_issue.md` (NC-003), sourced from the inventory `docs/00_governance_07_needs-confirmation-inventory.md` (Priority: High, Blocking: Yes).
- Source-code verification for this cycle confirmed the documented suspicion is accurate and still present in current `master`:
  - `ingester.py:374` calls `doc_mgr.handle_existing_document(url, existing_doc_id, force, etag, last_modified, fetched_at, ...)`, so the real `existing_doc_id` is available at the call site.
  - `document_manager.py:46-62` (`handle_existing_document`) receives `existing_doc_id` as a parameter but only forwards it to `_handle_existing_file` (the `file://` branch, line 60). On the non-file skip path it calls `self._update_etag(etag, last_modified, fetched_at)` (line 61) — `existing_doc_id` is dropped entirely.
  - `_update_etag` (lines 94-101) has no `doc_id` parameter in its signature and hardcodes `ETagManager(self._db, 0).update(...)`.
  - `ETagManager` (`etag_manager.py`) issues `UPDATE documents SET ... WHERE doc_id = ?` using whatever `doc_id` it was constructed with — here always `0`.

## Problem

For any non-`file://` URL that is re-ingested without `force=True` (the "skip and refresh ETag" path), the ETag/Last-Modified refresh SQL runs `WHERE doc_id = 0`. Because `documents.doc_id` is an autoincrement primary key starting at 1, this `UPDATE` matches zero rows for essentially all real documents. As a result:
- The stored `etag`/`last_modified`/`fetched_at` values for the existing document are never actually refreshed on the skip path, even though the code logs `"skip-path etag updated for doc_id=%d"` (with `doc_id=0`), which is misleading — it reports success for an update that silently affected 0 rows.
- Over repeated ingestion runs, stale ETag/Last-Modified values persist on the real document row, which can affect any future conditional-fetch or freshness/staleness logic that relies on those columns being current, and produces misleading log output.

## Reason for Change

- The current behavior is very likely an unintentional bug (a parameter that exists at the call site is silently dropped one level down), not a deliberate design choice — nothing in the surrounding code or docs justifies always targeting `doc_id=0`.
- Fixing it removes the documented "Needs confirmation" ambiguity in `docs/03_rag_02_06_ingestion_pipeline-supporting-components.md` and `docs/03_rag_02_05_ingestion_pipeline-document-manager.md`, and restores the intended ETag-refresh behavior for the skip path.
- Left unfixed, RAG document freshness metadata for the skip path silently drifts from reality, and any future feature that trusts `documents.etag`/`documents.last_modified`/`documents.fetched_at` for existing (non-file) documents will operate on stale data.

## Implementation Intent

- Thread the real `existing_doc_id` from `handle_existing_document` through `_update_etag` into the `ETagManager` construction, so the ETag/Last-Modified update SQL targets the correct row.
- Keep the existing staleness-guard and null-fill behavior of `ETagManager` unchanged — only the `doc_id` value used to construct it needs to be corrected at the `DocumentManager` call site.
- Update the log message in `_log_updated` implicitly becomes accurate once the correct `doc_id` is passed (no change needed inside `etag_manager.py` itself, since it already logs whatever `doc_id` it was given).
