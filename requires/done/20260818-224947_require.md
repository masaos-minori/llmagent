# Resolve tool_definitions FATAL/WARNING severity contradiction between docs and implementation

## Priority
High

## Target files
- `scripts/agent/services/mcp_tool_discovery.py` (`_is_fatal_severity()`, `_check_tool_definitions_finding()`)
- `docs/05_agent_10_01_operations-and-observability-startup-and-health.md` (startup severity mapping section, "運用上の注意")
- `tests/agent/services/test_mcp_tool_discovery.py` (severity coverage for `tool_definitions`)

## Background
`docs/05_agent_10_01_operations-and-observability-startup-and-health.md` states, under "運用上の注意":

> `tool_definitions` は strict モードでも FATAL にはならない — 常に WARNING にダウングレードされる。

This has been verified as still present in the doc at the time of this requirement.

## Problem
The implementation in `scripts/agent/services/mcp_tool_discovery.py` does not match this claim. The module docstring (lines ~33-35) explicitly states a "Unified severity scheme (drift, tool-definitions, malformed-capabilities): `is_fatal = strict or (security_profile == PRODUCTION)`."

`_is_fatal_severity()` (verified at lines ~345-358) implements exactly that:
```python
def _is_fatal_severity(self) -> bool:
    return self._is_strict() or (
        self._ctx.cfg.mcp.security_profile == SecurityProfile.PRODUCTION
    )
```

`_check_tool_definitions_finding()` (verified at lines ~388-417) uses `_is_fatal_severity()` to decide between `StartupCheckStatus.FATAL` and `StartupCheckStatus.WARNING` for `tool_definitions` findings, both for the `has_issues` branch and for the `RuntimeError` exception-handling branch.

`StartupOrchestrator._check_services()` in `scripts/agent/startup.py` (verified at line ~369) treats any `FATAL` outcome from `mcp_tool_discovery` findings (which include `tool_definitions` findings) as `pipeline.add_fatal(...)`, and a FATAL pipeline outcome aborts startup (`RuntimeError` raised after all checks complete, per the severity table in the same doc).

Net effect: with `security_profile=PRODUCTION`, a `tool_definitions` mismatch is FATAL and blocks startup regardless of `tool_definitions_strict`, directly contradicting the doc's unconditional "never FATAL, always downgraded to WARNING" claim.

No existing test locks the production + `tool_definitions_strict=False` + tool_definitions-mismatch case to either FATAL or WARNING:
- `TestUnifiedSeverity.test_severity_unified_for_duplicates` (verified at `tests/agent/services/test_mcp_tool_discovery.py` ~line 1368) only parametrizes and asserts FATAL for **duplicate-tool-name** findings, not `tool_definitions` findings.
- `test_tool_definitions_check_surfaces_as_outcome_not_exception` (verified at ~line 1428) only covers the non-strict/default-profile (effectively LOCAL) case, asserting WARNING; it does not cover PRODUCTION or strict=True.

## Reason for change
Operators currently cannot trust either the doc or a passing test suite to know what actually happens in production when `tool_definitions` drifts. The module docstring's own framing ("this resolves the old quirk where strict-mode drift detection was silently downgraded to skipped by an unrelated exception handler") suggests the FATAL-in-production behavior may be an intentional design decision that was never reflected back into the doc — but this cannot be confirmed without an explicit decision, since the doc was also never updated to match. Leaving this unresolved risks an operator being blindsided by an unexpected production startup failure while trusting a doc that says it can't happen.

## Implementation intent
This requirement is a **decision point**, not a prescribed fix. The next phase must first obtain (or make and record) a decision on the intended policy, then align doc and code to that decision. Two mutually exclusive resolution paths are possible; only one should be implemented:

**Option A — doc is correct ("tool_definitions never FATAL"):**
Exclude `tool_definitions` findings from the unified `_is_fatal_severity()` scheme. `_check_tool_definitions_finding()` should always return `StartupCheckStatus.WARNING` for both the `has_issues` branch and the `RuntimeError`-caught branch, regardless of `strict` or `security_profile`. The module docstring's "Unified severity scheme" note must be updated to state that `tool_definitions` is the WARNING-only exception, parallel to how duplicate-tool findings are already documented as the FATAL-only exception.

**Option B — implementation is correct (unified scheme applies to tool_definitions too):**
Update `docs/05_agent_10_01_operations-and-observability-startup-and-health.md`'s "運用上の注意" bullet for `tool_definitions` to state that it follows the unified severity scheme (FATAL when `strict` or `security_profile == PRODUCTION`, WARNING otherwise), matching the wording style already used for `mcp_tool_discovery`'s own bullet in the same list.

## Implementation instructions
1. Determine the intended policy for `tool_definitions` severity (via product/operations decision, or by inferring authoritative intent from related design history if a stakeholder decision is not obtainable in this workflow — but the decision and its rationale must be explicitly recorded in the plan/implementation output).
2. If Option A is chosen: modify `_check_tool_definitions_finding()` in `scripts/agent/services/mcp_tool_discovery.py` so both the `has_issues` branch and the `except RuntimeError` branch hard-code `StartupCheckStatus.WARNING` (do not call `_is_fatal_severity()` for this path). Update the module docstring's severity-scheme note accordingly.
3. If Option B is chosen: edit the `tool_definitions` bullet in `docs/05_agent_10_01_operations-and-observability-startup-and-health.md`'s "起動時検証の重大度マッピング" / "運用上の注意" section to describe the unified strict-or-production FATAL behavior instead of "常に WARNING にダウングレードされる".
4. Regardless of option chosen, add or extend tests in `tests/agent/services/test_mcp_tool_discovery.py` to explicitly assert the resulting behavior for `tool_definitions` findings across the `(strict, security_profile)` matrix — mirroring the existing `TestUnifiedSeverity.test_severity_unified_for_duplicates` parametrization pattern but targeting `tool_definitions` findings specifically (both the `has_issues` path and the `RuntimeError`-caught path), so the production + non-strict case is no longer untested.
5. Do not change duplicate-tool-name or drift-finding severity behavior; this requirement is scoped to `tool_definitions` only.

## Acceptance criteria
- The doc's `tool_definitions` severity description and the implementation's actual behavior are consistent with each other (whichever option is chosen).
- The behavior for `security_profile=PRODUCTION` with `tool_definitions_strict=False` and a `tool_definitions` mismatch is unambiguously defined as either FATAL or WARNING, and is asserted by a test.
- The behavior for `tool_definitions_strict=True` with a `tool_definitions` mismatch is also asserted by a test (in addition to the production case).
- All existing tests continue to pass.
- The module docstring in `scripts/agent/services/mcp_tool_discovery.py` no longer overstates or misstates which finding types are covered by the unified severity scheme.

## Tests
- Extend `tests/agent/services/test_mcp_tool_discovery.py` with parametrized coverage of `(strict, security_profile) -> expected_status` for `tool_definitions` findings, covering at minimum: `(False, LOCAL)`, `(False, PRODUCTION)`, `(True, LOCAL)`, `(True, PRODUCTION)`.
- Ensure both code paths that can produce a `tool_definitions` finding are covered: the `has_issues` result path and the `except RuntimeError` exception-surfacing path (the latter already has a partial test at `test_tool_definitions_check_surfaces_as_outcome_not_exception` that should be extended or parametrized rather than duplicated).
- Run the full existing test suite for this module to confirm no regressions from whichever option is implemented.
