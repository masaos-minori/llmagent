# Group SearchDiagnostics field table by local vs. HTTP-integration origin in docs/03_rag_04_02_dto-models_result.md

## Priority
Low

## Target files

## Background
`docs/03_rag_04_02_dto-models_result.md` documents the DTOs in `scripts/rag/models_result.py`. The `SearchDiagnostics` dataclass (lines 94-106 of that file) has 8 fields, split by an in-code comment into two conceptual groups:

```python
@dataclass(frozen=True)
class SearchDiagnostics:
    """Diagnostic information about a search operation."""

    embed_ok: int = 0
    embed_failed: int = 0
    fts_errors: int = 0
    # Remote mode fields (new):
    result_source: ResultSource = ResultSource.LOCAL
    http_result_kind: HttpResultKind = HttpResultKind.NOT_USED
    remote_status_code: int | None = None
    remote_latency_ms: float | None = None
    fallback_reason: str | None = None
```

The doc's "実装意図 (Implementation note)" section already correctly explains this split in prose: `embed_ok` / `embed_failed` / `fts_errors` are local-execution-origin counters, while `result_source`, `http_result_kind`, `remote_status_code`, `remote_latency_ms`, and `fallback_reason` were added later for the HTTP RAG service integration ("Remote mode fields (new)" per the source comment). However, the actual Markdown field table above that note still lists all 8 fields flat, in a single parallel list, with no visual or structural grouping.

## Problem
Verified against the current source (`scripts/rag/models_result.py:94-106`) and the current doc (`docs/03_rag_04_02_dto-models_result.md`): the issue's premise still holds. The `SearchDiagnostics` field table is a single flat table of 8 rows. A reader scanning only the table (not the prose note below it) cannot tell which fields are always populated during local execution versus which are meaningful only when the request was delegated to the remote HTTP RAG service. This is a genuine gap between what the table shows and what the prose (and source comment) already know.

## Reason for change
Without grouping, a reader inspecting `SearchDiagnostics` values in a purely local (non-HTTP) run may wrongly expect `result_source`, `http_result_kind`, `remote_status_code`, `remote_latency_ms`, or `fallback_reason` to carry meaningful non-default data, or may not realize `embed_ok`/`embed_failed`/`fts_errors` are the only fields guaranteed to reflect real local-execution activity. Making the origin/applicability grouping visible directly in the table (not just buried in prose below it) reduces this misreading risk.

## Implementation intent
Split the existing single `SearchDiagnostics` field table in `docs/03_rag_04_02_dto-models_result.md` into two clearly labeled groups, in field-declaration order, matching the dataclass's own grouping (confirmed via the `# Remote mode fields (new):` source comment and the doc's existing implementation note):

1. **Local-execution counters** (always populated, present regardless of HTTP/remote mode):
   - `embed_ok`
   - `embed_failed`
   - `fts_errors`

2. **HTTP-integration-added fields** (meaningful only when the search was delegated to / attempted against the remote HTTP RAG service; carry default/inert values in a pure local-only run):
   - `result_source`
   - `http_result_kind`
   - `remote_status_code`
   - `remote_latency_ms`
   - `fallback_reason`

Note: the issue text loosely described the second group as "`http_result_kind`, `remote_*` fields" (3-4 fields), but the actual dataclass source comment (`# Remote mode fields (new):`) covers 5 fields — it also includes `result_source` and `fallback_reason`. `result_source` classifies where the result came from (remote/local/fallback) and is only interesting once remote mode exists; `fallback_reason` is set by `scripts/rag/pipeline.py` and `scripts/rag/http_augment.py` specifically to record why an in-process fallback occurred after an HTTP attempt — both belong in the HTTP-integration group, not the local group. This grouping determination (3 local / 5 HTTP-integration) should be used, overriding the issue's narrower description, since it is directly backed by the source code comment.

Do not change the dataclass in `scripts/rag/models_result.py` — this is documentation-only, as explicitly scoped by the issue.
