## Background
`docs/04_mcp_03_01_dispatch-and-routing.md` (line 212) states: "config の `tool_names` は
ルーティングの入力ではない; あくまでドリフト検証用のメタデータである" (config's `tool_names` is not
a routing input; it is drift-validation metadata only). A companion requirement
(`requires/20260802-143623_require.md`, from a separate issue) already addresses propagating this
fact to `docs/04_mcp_06_03`. This requirement addresses propagating the same fact to the two other
files identified in the current issue: `docs/04_mcp_01_system_overview.md` and
`docs/04_mcp_06_09_mcp-failure-diagnosis.md`.

## Problem
Verified against current file content:
- `docs/04_mcp_01_system_overview.md` lines 118-129 contain the Major Components table that
  distinguishes `ToolRouteResolver`, `RuntimeToolRegistry` ("唯一のルーティング権威"), and
  `ToolRegistry` ("ルーティングには使われない" — for tool definitions/ownership drift detection).
  This table (and the surrounding narrative at line 30) never mentions `config/agent.toml`'s
  `tool_names` field or clarifies that it is not a routing input. A reader who only reads this file
  could reasonably (but wrongly) assume `tool_names` participates in routing, since the file
  discusses routing authority in detail without ruling it out.
- `docs/04_mcp_06_09_mcp-failure-diagnosis.md` lines 99-113 document the
  `McpServerHealthRegistry` circuit breaker (`record_failure()`, `is_unavailable()`,
  `HALF_OPEN`/`UNAVAILABLE`/`HEALTHY` transitions, threshold/cooldown defaults). This section never
  mentions `tool_names` and has no note ruling out its involvement in circuit-breaker state or
  dispatch gating.

Both omissions are confirmed still present as of this review (re-grepped both files for
`tool_names`, `RuntimeToolRegistry`, `ToolRouteResolver`, `ToolRegistry`, and circuit-breaker
section content — no match for the clarifying fact in either file).

## Reason for change
This is one of the most easily-misunderstood facts in the MCP domain: the
RuntimeToolRegistry/ToolRegistry/ToolRouteResolver distinction in `01_system_overview.md` is
already flagged as the most confusing part of the domain, and a reader who studies that section (or
the circuit-breaker section in `06_09`) without also reading `03_01` has no cue that `tool_names`
is excluded from routing. Adding the same one-sentence fact to both files closes that gap so a
reader arriving at any of the four related files (`03_01`, `06_03`, `01_system_overview`, `06_09`)
reaches the correct understanding.

## Implementation intent
Add one clarifying sentence to each of the two target files, at the point where a reader would most
plausibly (but wrongly) infer `tool_names` affects routing or circuit-breaker behavior:
- In `01_system_overview.md`, place the note directly adjacent to (or as an additional note under)
  the Major Components table's `RuntimeToolRegistry`/`ToolRegistry`/`ToolRouteResolver` rows, so it
  reads naturally as part of that routing-authority explanation.
- In `06_09`, place the note directly adjacent to (at the end of) the
  "Tool実行層のcircuit breaker（`McpServerHealthRegistry`）" section, so it reads naturally as a
  boundary clarification on what does/doesn't affect circuit-breaker state.

Word both notes consistently with `docs/04_mcp_03_01` line 212 and with the equivalent note being
added to `docs/04_mcp_06_03` per `requires/20260802-143623_require.md`, so all cross-references
agree verbatim or near-verbatim. Do not restructure the RuntimeToolRegistry/ToolRegistry/
ToolRouteResolver explanation or the circuit-breaker state machine itself — only add the
cross-referencing fact.
