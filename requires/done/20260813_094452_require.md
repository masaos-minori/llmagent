# Harden repository input handling and FTS observability

## Priority
Medium

## Target files
- `scripts/rag/repository.py`
- Search diagnostics models if structured fields are added
- Repository and SearchStage tests

## Background
Current repository methods pass `top_k` directly to SQL without validation, which can lead to invalid inputs. Additionally, tokenless FTS queries are represented as `MATCH '""'`, and there is a hardcoded 20-token limit that truncates input silently, making it difficult for callers to diagnose why retrieval quality might be degrading due to excessive query length.

## Problem
1. Lack of explicit validation for `top_k` allows potentially invalid values to reach the database layer.
2. Silent truncation of FTS queries beyond 20 tokens makes it hard to debug why certain terms are ignored during retrieval.
3. Empty or whitespace-only queries still trigger SQL execution instead of returning early.

## Reason for change
To make repository boundaries explicit and predictable, ensuring that invalid inputs are caught early and that silent behaviors (like truncation) are observable through diagnostics.

## Implementation intent
Introduce validation for `top_k` inputs, implement early exit for empty/whitespace-only queries, and add observability into the tokenization/truncation process during FTS query construction.

## Implementation instructions
1. Implement a shared validator for `top_k` inputs to ensure they are non-boolean integers greater than zero.
2. Update `_build_fts_query()` to return an empty normalized query string when no usable tokens remain after processing.
3. In `fts_search()`, check if the constructed FTS query is empty and return `[]` immediately without executing SQL.
4. Add logging or diagnostic metadata to record the original FTS token count, the number of tokens actually used, and whether truncation occurred.
5. Ensure that Japanese and English tokenization behavior remains unchanged for non-empty queries.

## Acceptance criteria
- Zero, negative, boolean, and non-integer `top_k` values fail before reaching the SQL layer.
- Whitespace-only and punctuation-only FTS queries return `[]` without triggering SQL syntax errors.
- Queries exceeding the 20-token limit expose truncation information via logs or diagnostics.
- Normal search results remain behaviorally identical to current implementation.

## Tests
- Test with invalid `top_k` values (zero, negative, boolean, non-integer).
- Test with valid `top_k` values.
- Test with empty and punctuation-only queries.
- Test with Japanese and English non-empty queries.
- Test with queries containing exactly 19, 20, and 21 tokens to verify truncation reporting.
