# Publish ChunkSplitter output atomically with a completion manifest

## Priority
High

## Target files
- `scripts/rag/ingestion/chunk_splitter.py`
- `scripts/rag/ingestion/pipeline_utils.py`

## Background
Currently, `ChunkSplitter` uses the existence of `{stem}-0000.json` as a sentinel to determine if a source file has been processed. This approach is prone to errors if a write operation fails partially or if regeneration produces fewer chunks than previously existing.

## Problem
The current implementation lacks atomicity and verifiable completion:
- A partial write can leave behind some chunk files without a proper way to know it was incomplete, except by checking for `-0000.json`.
- If a new generation results in fewer chunks, old higher-numbered chunks might remain, leading to inconsistent state.
- There is no verifiable proof that all intended chunks were successfully written and validated before marking the process as complete.

## Reason for change
To ensure data integrity during the RAG ingestion pipeline by making the output of `ChunkSplitter` atomic and verifiable via a dedicated manifest file.

## Implementation intent
Replace the sentinel chunk file with a formal manifest file that contains metadata about the completed set of chunks. Use a temporary directory for writing chunks and only move them to their final destination and create the manifest once all chunks are verified.

## Implementation instructions
1. Modify `ChunkSplitter.process_file` to use a temporary directory within the `chunk_dir` for writing new chunks.
2. Implement a manifest creation step that writes a JSON manifest containing `schema_version`, `artifact_type`, `source_file`, `chunk_count`, and other relevant metadata.
3. Update `is_already_processed` in `pipeline_utils.py` to check for the existence of this manifest instead of the `-0000.json` file.
4. Ensure that upon successful completion, the temporary chunks are moved to their final location and the manifest is created atomically (or as close as possible).
5. Add logic to remove any existing chunks and manifests for the same source file before starting a new processing run (unless `force` is used).
6. Update integration tests to verify atomic replacement and manifest validation.

## Acceptance criteria
- A crash during chunk writing does not leave behind a partial set of chunks that appear complete.
- Regeneration resulting in fewer chunks correctly replaces the previous set and its manifest.
- Processing is skipped if a valid manifest already exists for the source file.
- Manifest is created only after all chunks are successfully written.

## Tests
- Test partial write failure (ensure no manifest is created and no stale chunks are left).
- Test ten-to-six regeneration (ensure exactly six chunks and one manifest exist).
- Test unchanged source/config skip (verify manifest usage).
- Test manifest corruption handling.
