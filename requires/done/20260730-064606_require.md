# Require: Final-answer fallback for LLM tool loop guard

## Priority

High

## Target files

- `scripts/agent/llm_turn_runner.py`
- `scripts/agent/tool_loop_guard.py`
- `scripts/agent/turn_result.py`
- `scripts/agent/orchestrator.py`
- `scripts/agent/message_schema.py`
- `scripts/shared/llm_client.py`

## Background

When ToolLoopGuard detects repeated, cyclic, or retrying tool calls, the agent currently terminates the LLM turn as a failure. This differs from tool approval denial, where the denial is added to the conversation as a tool message, allowing the LLM to continue and respond appropriately.

## Problem

The current behavior has several issues:

- The LLM does not know why its tool loop was stopped.
- The LLM does not receive an instruction to answer with already available information.
- The turn may end with a guard message instead of a useful final answer.
- Unexecuted assistant tool calls may be persisted if guard checks happen after the assistant tool-call message is appended to history.

## Reason for change

Convert ToolLoopGuard from a hard stop into a controlled final-answer fallback, giving the LLM one more opportunity to produce an answer using only the information already available in the conversation.

## Implementation intent

Implement a final-answer-only fallback mechanism when ToolLoopGuard triggers:

1. The LLM returns tool calls.
2. ToolLoopGuard checks the proposed tool calls **before** they are persisted.
3. If the guard triggers:
   - Do not persist the unexecuted assistant tool-call message.
   - Add a temporary system message instructing the LLM not to call tools again.
   - Call the LLM once more without tool definitions.
   - If the LLM returns a final answer, continue normally.
   - If the LLM returns tool calls again, fail safely.
4. Keep diagnostic records for guard events.

## Implementation instructions

### 1. Add final-answer-only streaming method

Add `_stream_llm_final_answer()` to `LLMTurnRunner`:
- Call the LLM with an empty tool definition list (`tool_defs=[]`).
- Use the same conversation history.
- Preserve workflow context metadata for tracing.
- Return the normal LLM response object.

### 2. Add guard finalization handler

Add `_finalize_after_guard()` helper method:
- Inject a temporary system message with trusted source for ephemeral system messages.
- Request a final answer without tools.
- Return `TurnResult(action="continue")` if a normal answer is produced.
- Return `TurnResult(action="fail", error_kind="tool_loop_guard")` if the LLM still returns tool calls.

### 3. Move ToolLoopGuard checks before persistence

Guard checks must happen before:
- `ctx.conv.append_message(message)`
- `ctx.session.save(..., tool_calls=...)`

This prevents unexecuted assistant tool calls from being stored in the normal conversation history or session database.

### 4. Use ephemeral system message

Add a temporary system message:

> [ToolLoopGuard] Repeated or cyclic tool use was detected. Do not call tools again. Produce the best possible final answer using only the information already available in the conversation.

### 5. Normalize failure reason handling

When `TurnResult.action != "continue"`, derive `error_kind` from:

    error_kind = result.error_kind or result.reason or result.action

## Acceptance criteria

- [ ] ToolLoopGuard no longer immediately fails the turn in the common case
- [ ] A final-answer-only LLM call is attempted once after guard activation
- [ ] The final-answer call does not include tool definitions
- [ ] If the LLM returns normal content, the turn returns `TurnResult(action="continue")`
- [ ] If the LLM returns tool calls again, the turn returns `TurnResult(action="fail")`
- [ ] Unexecuted assistant tool-call messages are not persisted to conversation history or session storage
- [ ] Guard events remain available in diagnostics
- [ ] `TurnResult.reason` is not lost when deriving audit or error metadata

## Tests

- Duplicate tool call triggers final-answer fallback
- Cyclic tool-call pattern triggers final-answer fallback
- Retry of a previously failed tool call triggers final-answer fallback
- Final-answer call is made with no tool definitions
- Final-answer response with no tool calls succeeds
- Final-answer response with tool calls fails safely
- Unexecuted assistant tool calls are not persisted
- Guard diagnostics are still written
