# Requirement: Staggered Startup for MCP Server Health Checks

## Priority

Medium — burst load on health endpoints could trigger false restart loops under certain conditions

## Target Files

- `scripts/agent/http_lifecycle.py` (lines 326-364)
- `scripts/agent/startup.py` (lines 143-169)

## Background

When multiple HTTP subprocess MCP servers start simultaneously, each polls its own `/health` endpoint every 0.5 seconds. All servers begin polling at approximately the same time, creating a burst of concurrent health check requests.

## Problem

Concurrent health check requests from multiple servers create a burst load on their respective `/health` endpoints. If any endpoint has slow response times or connection limits, this burst could cause transient failures that trigger unnecessary restart attempts.

## Reason for Change

Staggering startup reduces the probability of cascading failures due to health endpoint overload during the critical startup window.

## Implementation Intent

Add configurable startup delay between consecutive MCP server starts to reduce burst load on health endpoints.

## Implementation Instructions

**Option A — Configurable stagger delay:**
- Add a new configuration parameter `startup_stagger_delay_sec` (default: 1.0) to `McpServerConfig`
- In `_start_servers()`, track the last successful startup time and apply stagger delay before starting the next server
- Log the stagger delay applied for observability

**Option B — Fixed stagger delay:**
- Hard-code a fixed stagger delay (e.g., 1 second) between consecutive server startups
- Simpler but less flexible

Option A is recommended because it allows operators to tune the stagger based on their deployment characteristics.

## Acceptance Criteria

- [ ] Consecutive MCP server startups are separated by at least the configured stagger delay
- [ ] Default stagger delay is reasonable (1-2 seconds recommended)
- [ ] Stagger delay can be disabled or set to zero if needed
- [ ] Logging includes stagger information for debugging
- [ ] No regression in startup time for single-server deployments

## Tests

- Integration test verifying stagger delay is applied between consecutive server startups
- Integration test verifying no stagger when only one server exists
