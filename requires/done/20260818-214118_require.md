# Implement `enabled`/`disabled_reason` on web-search-mcp and github-mcp `/v1/tools`

## Priority
Low

## Target files
- `scripts/mcp_servers/web_search/web_search_server.py`
- `scripts/mcp_servers/github/github_server.py`
- `scripts/mcp_servers/server.py` (optional: shared annotation helper, see Implementation intent)
- `docs/04_mcp_90_inconsistencies_and_known_issues.md` (MCP-002 entry, update in a later docs pass, not in this requirement's code change)
- `docs/04_mcp_03_06_tool-runtime-availability-metadata.md`, `docs/04_mcp_04_01_web-search-file-read-github.md` (documentation follow-up, not in scope for this requirement's code change)

## Background
`docs/04_mcp_03_06_tool-runtime-availability-metadata.md` and `docs/04_mcp_90_inconsistencies_and_known_issues.md`
(entry MCP-002) define a runtime-availability contract for MCP tool discovery: each tool in a
server's `/v1/tools` response should carry `enabled` (bool) and `disabled_reason` (string) fields,
computed per-request from the server's current config state, with the invariant
`enabled=True <-> disabled_reason == ""`.

Verified current implementation state (2026-08-18, read directly from source):
- `scripts/mcp_servers/git/git_server.py` and the three file servers
  (`scripts/mcp_servers/file/{read,write,delete}_server.py`, via
  `scripts/mcp_servers/file/common.py::availability_flags()`) already implement this contract on
  `/v1/tools` and gate `/v1/call_tool` accordingly.
- `scripts/mcp_servers/shell/shell_server.py` and `scripts/mcp_servers/cicd/cicd_server.py` do not
  implement it, but this is a **documented, intentional scope exclusion** (requirement 15; see
  `docs/04_mcp_03_06_tool-runtime-availability-metadata.md` section 3 and
  `docs/04_mcp_04_03_rag-pipeline-and-cicd.md`). Not a gap to close here.
- `scripts/mcp_servers/rag_pipeline/rag_pipeline_server.py` and `scripts/mcp_servers/mdq/mdq_server.py`
  have no `config_dependent: True` tools at all (checked their `TOOL_LIST` sources), so the
  enabled/disabled_reason contract does not apply to them.
- `scripts/mcp_servers/web_search/web_search_server.py` has one `config_dependent: True` tool
  (`browser_fetch`) but its `/v1/tools` handler (`list_tools()`) calls the generic
  `build_tools_response()`, which never adds `enabled`/`disabled_reason`. This is a real,
  undocumented-as-deferred gap.
- `scripts/mcp_servers/github/github_server.py` has multiple `config_dependent: True` tools (all of
  them, per `scripts/mcp_servers/github/tools_*.py`) but its `/v1/tools` handler also calls the
  generic `build_tools_response()` with no availability annotation. `docs/04_mcp_04_01_...md` line
  ~166 describes this as pending future work ("要件15/16の実装次第"), not an intentional exclusion
  — i.e. still an open gap.

**Correction to the source issue (`issues/20260817_04_issue.md`):** the issue states "only
web-search-mcp implements `enabled`/`disabled_reason`; the other servers omit them." This is
backwards. Source inspection shows git-mcp and the three file servers *are* the ones that
implement it; web-search-mcp is one of the servers that *lacks* it. This requirement is scoped to
the two servers verified to actually lack the contract without a documented deferral:
web-search-mcp and github-mcp.

The other independent point in the source issue (MCP-001: `include_disabled` query parameter and
`disabled_code` structured field on `/v1/tools`) is excluded from this requirement. It is already
tracked as an intentionally deferred, evaluated design decision — see
`docs/04_mcp_90_inconsistencies_and_known_issues.md` (MCP-001, "Resolution Notes: 意図的に延期") and
`docs/04_mcp_03_06_tool-runtime-availability-metadata.md` ("Future / deferred design options",
"Status: unimplemented, no immediate action required"). No further action is needed for MCP-001.

## Problem
`web-search-mcp` and `github-mcp` each have at least one tool whose usability depends on server
config (`browser_fetch` depends on `browser_allowed_domains`; every github-mcp tool depends on
`_GITHUB_TOKEN`/`GitHubConfig`), but their `/v1/tools` responses never surface `enabled` or
`disabled_reason`. Callers and operators cannot distinguish "tool exists and is currently unusable
due to config" from "tool exists and is usable" on these two servers, even though the same concept
is already surfaced correctly by git-mcp and the file servers. This breaks the uniformity that
`RuntimeToolRegistry`/`/mcp status` (`DISABLED_REASON` column) and any client-side tooling built
against the documented contract expect across servers.

## Reason for change
- The contract is already defined and already implemented correctly on 4 of the servers where it
  applies; web-search-mcp and github-mcp are outliers, not intentionally-scoped exceptions.
- `docs/04_mcp_90_inconsistencies_and_known_issues.md` MCP-002 already carries an explicit
  "Recommended Action" to close this gap and remove the tracking entry once done.
- Leaving it open means `/mcp status` and any RuntimeToolRegistry-based tooling continue to show
  misleading/absent disabled-reason data for two servers whose tools are, in practice, frequently
  config-gated (missing GitHub token; empty/misconfigured browser domain allowlist).

## Implementation intent
Follow the existing pattern used by `git_server.py` (`_git_tool_availability()` +
`_annotate_tool()`) and `file/common.py` (`availability_flags()`), rather than inventing a new
shape:
- For **web-search-mcp**: gate `browser_fetch` on whether `_cfg.browser_allowed_domains` is
  non-empty (mirroring the fail-closed semantics already enforced at dispatch time in
  `search_provider.py::_check_domain()` — an empty allowlist means every domain is rejected).
  `search_web` has no `config_dependent` flag and should report `enabled=True`,
  `disabled_reason=""` unconditionally.
- For **github-mcp**: gate all tools on whether `_GITHUB_TOKEN`/`GitHubConfig` indicates a usable
  token, mirroring the check already used by the `/health` endpoint
  (`if not _GITHUB_TOKEN: deps["github_token"] = "not_set"`). Reuse that same signal rather than
  adding a second, possibly-diverging check.
- In both cases, wire the same availability check into `/v1/call_tool` so disabled tools are
  rejected server-side before dispatch, consistent with git-mcp's
  `CallToolResponse(result=f"Tool disabled: {reason}", is_error=True)` behavior.
- Consider whether the now-3x-duplicated "compute (enabled, reason) then merge into each tool dict"
  shape in git/file/(new) web-search/(new) github warrants a small shared helper in
  `scripts/mcp_servers/server.py` alongside `build_tools_response()`, to avoid a 5th bespoke
  copy if a future server needs the same treatment. This is a judgment call for the implementer,
  not a requirement.
- Do not touch `shell_server.py`, `cicd_server.py`, `rag_pipeline_server.py`, or `mdq_server.py` —
  out of scope per the Background section above.

## Implementation instructions
1. In `scripts/mcp_servers/web_search/web_search_server.py`, add an availability check function
   analogous to `_git_tool_availability()` that returns `(enabled, disabled_reason)` for a given
   tool name, using `_cfg.browser_allowed_domains` for `browser_fetch` and always-enabled for
   `search_web`. Use the standard reason string form already established elsewhere (e.g.
   `"browser_allowed_domains is empty"`, consistent with `"allowed_dirs is empty"` /
   `"allowed_repo_paths is empty"`).
2. Replace the `build_tools_response(TOOL_LIST, "web_search")` call in `list_tools()` with a
   response that merges `enabled`/`disabled_reason` into each tool dict alongside `server_key`.
3. In the `/v1/call_tool` handler (or equivalent dispatch entry point) for web-search-mcp, reject
   calls to a disabled tool before dispatch, returning
   `CallToolResponse(result=f"Tool disabled: {reason}", is_error=True)`.
4. In `scripts/mcp_servers/github/github_server.py`, add an equivalent availability check based on
   `_GITHUB_TOKEN` (or the underlying `GitHubConfig` field it derives from), applied uniformly to
   all tools in `TOOL_LIST` (all are `config_dependent: True` today).
5. Replace the `build_tools_response(TOOL_LIST, "github")` call in `list_tools()` with the
   annotated version, and add the equivalent server-side dispatch gate in the call-tool handler.
6. Do not change `MCP_TOOL_SCHEMA_VERSION` unless the new fields require a version bump per its
   existing versioning contract in `scripts/mcp_servers/server.py` — check that docstring before
   deciding.
7. This requirement covers source code only. Documentation updates (removing/updating the MCP-002
   entry in `docs/04_mcp_90_inconsistencies_and_known_issues.md`, updating
   `docs/04_mcp_03_06_tool-runtime-availability-metadata.md` and
   `docs/04_mcp_04_01_web-search-file-read-github.md`) are expected as part of closing this out,
   but happen in the documentation phase, not as part of this code requirement.

## Acceptance criteria
- `GET /v1/tools` on web-search-mcp returns `enabled`/`disabled_reason` for every tool, with
  `browser_fetch` reporting `enabled=false` / a non-empty reason when
  `browser_allowed_domains` is empty, and `enabled=true` / `""` otherwise; `search_web` always
  reports `enabled=true` / `""`.
- `GET /v1/tools` on github-mcp returns `enabled`/`disabled_reason` for every tool, consistent with
  the same signal already used by `/health`'s `github_token` dependency check.
- `POST /v1/call_tool` on both servers rejects a disabled tool with
  `CallToolResponse(result="Tool disabled: <reason>", is_error=True)` before reaching the
  dispatch table, matching git-mcp's existing behavior.
- `enabled=True <-> disabled_reason == ""` holds for every tool on both servers (no case where
  `enabled=false` pairs with an empty reason string, or vice versa).
- No behavior change to shell-mcp, cicd-mcp, rag-pipeline-mcp, or mdq-mcp `/v1/tools` responses.

## Tests
- Add/extend tests analogous to `tests/mcp_servers/git/test_tools_endpoint.py` for both
  web-search-mcp and github-mcp: assert `/v1/tools` includes `enabled`/`disabled_reason` per tool
  under both a "config present" and "config absent/empty" fixture.
- Add a call-tool test for each server confirming a disabled tool is rejected with
  `is_error=True` and the expected reason string, without reaching the underlying service/dispatch
  table (i.e. assert the underlying handler/service method is not invoked).
- Confirm existing tests for shell-mcp, cicd-mcp, rag-pipeline-mcp, and mdq-mcp `/v1/tools`
  continue to pass unchanged (no `enabled`/`disabled_reason` expected there).
