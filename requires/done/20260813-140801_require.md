# Enforce Fail-Closed Tool-Call Preparation Before Approval and Remove the `tool_definitions` Runtime Fallback

## Priority
High

## Background
`RuntimeToolRegistry` is the runtime authority for live MCP tool metadata (discovered
from `/v1/tools`). `ctx.cfg.tool.tool_definitions` is a separate, static, config-driven
list intended only for startup drift validation and test fixtures.

Verified against current source (2026-08-13):

- `tool_runner.py::_validate_tool_args()` (lines 141-155) calls
  `registry.get(name)` and explicitly catches `KeyError` (line 154) with a comment
  "Fall through to gateway fallback" (line 155).
- On that fallthrough, it loops over `ctx.cfg.tool.tool_definitions` (lines 158-172),
  matching `td.get("name")` and `td.get("inputSchema")` — top-level keys.
- This is structurally inconsistent with the *other* `tool_definitions` consumer in the
  same file: `_build_tool_meta()` (lines 60-79) reads `td.get("function", {})` and then
  `fn.get("name")` — an OpenAI-style nested shape. The same config list is read with two
  incompatible shapes by two different fallback paths in the same module.
- If the tool is absent from **both** the registry and `tool_definitions`,
  `_validate_tool_args()` returns `None` (line 173), which `execute_one_tool_call()`
  (line 202) treats as "no validation error" — i.e. an unknown, unvalidated tool is
  allowed to proceed to execution. This is a genuine fail-open path, not a hypothetical
  one.
- `execute_all_tool_calls()` (lines 506-537) calls `_run_approval_gate()` (line 524)
  **before** any call reaches `execute_one_tool_call()` (via `_execute_with_dag()` /
  `_execute_standard()`, lines 526-530). `execute_one_tool_call()` (lines 194-201) is
  where `orjson.loads()` parsing and `_validate_tool_args()` both happen. This confirms
  the issue's claim that argument parsing and validation currently run **after**
  approval, not before it.
- `_build_tool_meta()` (lines 60-79), called from `_execute_with_dag()` (lines 325-326),
  still derives DAG scheduling metadata from `ctx.cfg.tool.tool_definitions` using the
  static `is_side_effect()` helper and `SHELL_TOOLS` name set.

This issue (H-02 / M-06) depends on the schema-2.0 metadata and per-call `ToolSpec`
work already filed as `requires/20260813-140532_require.md` (source issue
`issues/done/20260807_21_issue.md`, "Issue 01" in the dependency chain below) and must
be completed before the standard-execution-path removal tracked in
`issues/20260807_23_issue.md` ("Issue 03"), because the DAG planner must receive only
already-prepared, already-validated calls.

## Problem
1. An unregistered tool name that also has no matching `tool_definitions` entry is
   currently **not rejected** — `_validate_tool_args()` returns `None` and the call
   proceeds to `RepositoryGateway`/`ToolExecutor`.
2. The `tool_definitions` fallback in `_validate_tool_args()` and the `tool_definitions`
   read in `_build_tool_meta()` disagree on shape (top-level `name`/`inputSchema` vs.
   nested `function.name`), so a stale or malformed static entry can be silently
   ignored or misread by one path while accepted by the other.
3. Argument JSON parsing (`orjson.loads`) and schema validation happen inside
   `execute_one_tool_call()`, which only runs after `_run_approval_gate()` has already
   approved the call — malformed JSON, non-object arguments, and unknown tools are
   discovered too late, after the call has already been through approval.
4. `tool_definitions` can still repair or override missing live registry metadata
   (write classification, schema) via the fallback loop, recreating a second source of
   truth for execution-relevant properties that `RuntimeToolRegistry` is supposed to
   own exclusively.
5. There is no regression test proving a tool absent from `RuntimeToolRegistry` fails
   even when a matching static `tool_definitions` entry exists.

## Reason for change
Live `/v1/tools` discovery and `RuntimeToolRegistry` are meant to be the sole runtime
authority for tool execution metadata (per the architecture already established by
`requires/20260813-140532_require.md`). As long as `_validate_tool_args()` retains a
`tool_definitions` fallback and a silent-success path for unregistered tools, that
authority is not enforced: a stale, incomplete, or malformed static definition can make
an unavailable or incompletely-discovered tool executable, and validation happening
after approval means invalid calls consume an approval decision before they are known
to be well-formed.

## Implementation intent
Introduce an explicit, fail-closed preparation phase that runs for every tool call
before it is sent to approval: parse the call ID and function name, parse the
arguments JSON exactly once, require the result to be a JSON object, resolve the tool
through `RuntimeToolRegistry` only, validate arguments against
`RuntimeTool.input_schema`, resolve resource scopes, and build a call-level `ToolSpec`.
Represent each successfully-prepared call explicitly (e.g. a `PreparedToolCall`
dataclass carrying `call_id`, `name`, `args`, `spec`, and the original call dict) so
downstream execution reuses the already-parsed arguments instead of re-parsing them.
A call that fails preparation becomes a synthetic tool-error result and never reaches
approval, DAG planning, `RepositoryGateway`, or `ToolExecutor`; other calls in the same
batch continue independently. Remove the `KeyError`-catch-and-fall-through branch and
the `tool_definitions` loop from `_validate_tool_args()` entirely. Keep
`ctx.cfg.tool.tool_definitions` only for startup drift validation
(`agent/repl_health.py::_check_tool_definitions`) and test fixtures; update its
docstring/comment in `config_dataclasses.py` to state plainly that it is not a runtime
source or fallback for routing, argument validation, scheduling, approval, or
execution.

## Implementation instructions
1. Add a preparation function/module (e.g. `scripts/agent/tool_preparation.py`) invoked
   from `execute_all_tool_calls()` **before** `_run_approval_gate()` (currently line
   524). For each raw tool call: validate the call object and call ID; read the
   function name; call `orjson.loads()` on `arguments` exactly once; reject non-dict
   results; require `ctx.services_required.runtime_tools` to be initialized; resolve
   the tool via `registry.get(name)`; validate parsed args against
   `RuntimeTool.input_schema` via `validate_tool_arguments()`
   (`agent/tool_arg_validator.py`); resolve resource scopes; build a `ToolSpec`.
2. Represent successfully prepared calls as an explicit `PreparedToolCall`
   (`call_id`, `name`, `args`, `spec`, `original_call`) or an equivalent structure, so
   `execute_one_tool_call()` no longer calls `orjson.loads()` on `func.get("arguments")`
   itself (currently lines 193-199) — it must consume already-parsed `args` from the
   prepared call.
3. Use distinct, machine-readable preparation-error kinds: `configuration` (registry not
   initialized), `unknown_tool` (registry `get()` raises `KeyError`), `validation`
   (malformed JSON or non-object arguments), `schema` (invalid/unavailable live
   `input_schema`), `metadata` (incomplete live execution metadata or failed scope
   resolution). Convert each into a synthetic `ToolCallResult` (reuse the existing
   `_reject_validation()` pattern at `tool_runner.py:115-125`) rather than raising out of
   the batch loop.
4. In `_validate_tool_args()` (`tool_runner.py:128-173`), delete the `except KeyError:
   pass` fallthrough (line 154-155) and the entire `tool_definitions` loop (lines
   157-172). An unregistered tool must now be rejected during preparation, before this
   function is ever reached for that call — after this change, `_validate_tool_args()`
   itself becomes redundant with the new preparation phase and should be removed (its
   logic subsumed by preparation) rather than left as unreachable dead code.
5. Route `_run_approval_gate()` (`tool_runner.py:541-556`) to accept only prepared
   calls; preparation failures must be converted to their own tool-error results and
   excluded from the approval batch, not silently denied by the approval path.
6. Preserve original call order when merging preparation errors, approval denials, and
   execution results back into `_collect_tool_result_msgs()` (`tool_runner.py:234-263`).
7. Remove `_build_tool_meta()` (`tool_runner.py:60-79`) and its call site in
   `_execute_with_dag()` (currently lines 325-326) if the sibling requirement
   (`requires/20260813-140532_require.md`) has not already done so by the time this is
   implemented; otherwise verify it is already gone and only the `_validate_tool_args()`
   fallback (this requirement's primary target) remains to be removed.
8. Update the `tool_definitions` field docstring/comment in
   `config_dataclasses.py` (line 194) to state it is compatibility-only: used for
   startup drift validation (`agent/repl_health.py::_check_tool_definitions`) and test
   fixtures, never a runtime source or fallback for routing, argument validation,
   scheduling, approval, or execution.
9. Audit remaining references to `ctx.cfg.tool.tool_definitions` /

## Acceptance criteria
- An unregistered tool name fails during preparation, before approval, even when a
  matching entry exists in `ctx.cfg.tool.tool_definitions`.
- Malformed argument JSON and non-object parsed arguments fail during preparation,
  before approval.
- `_validate_tool_args()` no longer contains a `KeyError` catch that falls through to
  `ctx.cfg.tool.tool_definitions`, and no longer reads `ctx.cfg.tool.tool_definitions`
  at all.
- Runtime argument validation uses only `RuntimeTool.input_schema` resolved from
  `RuntimeToolRegistry`.
- `execute_one_tool_call()` reuses already-parsed arguments from the prepared call and
  does not call `orjson.loads()` on the raw arguments string a second time.
- No invalid call reaches `_run_approval_gate()`, DAG planning, `RepositoryGateway`, or
  `ToolExecutor`.
- A batch containing one invalid and one valid call still executes the valid call; the
  invalid call surfaces as a tool-error result in its original position.
- Preparation failures do not affect MCP server health/diagnostics tracking.
- `ctx.cfg.tool.tool_definitions`'s docstring/comment states it is compatibility-only
  (startup drift validation and test fixtures), matching actual code behavior after
  this change.
- Startup drift validation (`agent/repl_health.py::_check_tool_definitions`) continues
  to function unchanged.

## Tests
- `RuntimeToolRegistry` not initialized (`ctx.services_required.runtime_tools is None`)
  → preparation fails with a `configuration`-kind result, no approval call is made.
- Tool name absent from `RuntimeToolRegistry` but present in `ctx.cfg.tool.tool_definitions`
  → call is rejected (regression guard for the primary fix); assert
  `RepositoryGateway.execute` / `ToolExecutor.execute` are not called for this call.
- Malformed JSON in `arguments` → rejected before approval.
- `arguments` decodes to a list, string, number, boolean, or null → rejected before
  approval (non-object check).
- Arguments violate `RuntimeTool.input_schema` → rejected with a `schema`/`validation`
  reason.
- One invalid call and one valid call in the same `tool_calls` batch → the valid call
  executes normally; the invalid call becomes a synthetic error result; both preserve
  original order in the final tool messages.
- Approval mock/spy: assert it is invoked only with prepared calls, never with a call
  that failed preparation.
- `grep -n "tool_definitions" scripts/agent/tool_runner.py` after the change shows no
  remaining reference inside `_validate_tool_args()` (function removed or fallback
  deleted).
- Existing `tests/agent/test_tool_runner.py`, `tests/agent/test_tool_arg_validator.py`,
  and `tests/agent/test_tool_approval_*.py` pass unmodified in behavior for already-valid
  calls (no behavior change for the happy path).
