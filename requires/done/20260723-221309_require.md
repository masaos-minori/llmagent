## Title

Improve error message for tool calls during MCP subprocess cooldown

## Priority

Medium

## Target files

- scripts/agent/factory.py

## Background

When a tool is called and the corresponding MCP subprocess is in cooldown (within 30 seconds of a previous failure), `ensure_ready()` silently returns without starting the server. The caller then fails with a generic error.

## Problem

`factory.py:126-127`: When `_in_cooldown()` returns True, `ensure_ready()` returns without any indication to the caller that the server is temporarily unavailable due to cooldown. The subsequent tool execution fails with a vague error like "tool not available" or "connection refused".

## Reason for change

Users need to understand why a tool call failed. A message indicating that the server is restarting would be much more actionable than a generic "not available" error.

## Implementation intent

Modify `ensure_ready()` to raise a specific exception when the server is in cooldown, allowing the caller to display a meaningful message.

## Implementation instructions

Change the code from:

```python
# Before (factory.py ~line 126):
if self._in_cooldown(server_key):
    return
```

To:

```python
# After:
if self._in_cooldown(server_key):
    remaining = _COOLDOWN_SECONDS - (time.monotonic() - self._failed_starts[server_key])
    raise ServerCooldownError(
        f"MCP server {server_key!r} is restarting. Try again in {remaining:.0f}s"
    )
```

Define `ServerCooldownError` as a custom exception class:

```python
class ServerCooldownError(RuntimeError):
    """Raised when a tool call is attempted while an MCP server is in cooldown."""
```

Alternatively, use a sentinel value instead of raising an exception:

```python
# Return a special result object instead of raising
if self._in_cooldown(server_key):
    remaining = _COOLDOWN_SECONDS - (time.monotonic() - self._failed_starts[server_key])
    return CooldownResult(server_key=server_key, remaining_seconds=remaining)
```

The exception approach is preferred because it makes the failure explicit at the call site.

## Acceptance criteria

1. When a tool is called during cooldown, the error message includes the server name and estimated restart time.
2. Existing behavior for non-cooldown cases is unchanged.
3. No mypy errors introduced by the change.
4. All existing tests pass without modification.

## Tests

1. Test: Tool call during cooldown displays informative message
   - Simulate a server in cooldown
   - Call a tool requiring that server
   - Verify error message contains server name and remaining time

2. Test: Tool call after cooldown expires works normally
   - Wait until cooldown expires
   - Call a tool requiring that server
   - Verify server starts and tool executes successfully

3. Test: Non-MCP servers unaffected
   - Call a tool requiring a non-subprocess MCP server
   - Verify no cooldown logic applies
