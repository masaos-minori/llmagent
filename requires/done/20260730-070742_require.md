# Require: Unify `/v1/tools` validation around `McpToolDiscoveryService`

## Priority

High

## Target files

- `agent/services/mcp_tool_discovery.py`
- `agent/repl_health.py`
- `agent/startup.py`
- `shared/runtime_tool.py`
- `shared/runtime_tool_registry.py`

## Background

The codebase currently has two different `/v1/tools` validation paths.

The first path is in `repl_health.py`. It performs lightweight name-only validation through functions such as `_validate_tools_response()`, `_collect_server_tool_names()`, and `_check_tool_definitions()`.

The second path is `McpToolDiscoveryService`. It fetches `/v1/tools`, validates richer tool entry shape, normalizes tools into `RuntimeTool`, builds `RuntimeToolRegistry`, detects duplicate tool names, and reports startup findings.

Runtime routing depends on `RuntimeToolRegistry`, so `/v1/tools` validation should be aligned with the registry-building path.

## Problem

Keeping two independent `/v1/tools` validation paths can cause inconsistent startup and runtime behavior.

Examples:

- A tool response may pass name-only validation but fail rich metadata validation.
- Startup validation may report one view of available tools while runtime routing uses another.
- Tool metadata issues may be missed by the lightweight path.
- Duplicate tool ownership may be handled differently across validation paths.
- Multiple `/v1/tools` fetches during startup may observe different states.

## Reason for change

Treat `/v1/tools` as the runtime tool contract, not merely a list of tool names.

`McpToolDiscoveryService` should be the canonical place for:

- Fetching `/v1/tools`
- Validating tool entries
- Normalizing tool metadata
- Building `RuntimeToolRegistry`
- Detecting duplicate tool names
- Reporting startup validation findings

## Implementation intent

### Define validation ownership

Document that `McpToolDiscoveryService` is the authoritative `/v1/tools` validation path.

It should own:

- `/v1/tools` fetch
- Tool entry validation
- Tool metadata validation
- `RuntimeTool` normalization
- `RuntimeToolRegistry` construction
- Duplicate tool name detection
- Startup validation findings

### Refactor or reclassify `repl_health.py` checks

Review the following functions:

- `_validate_tools_response()`
- `_collect_server_tool_names()`
- `_check_tool_definitions()`

Choose one of the following approaches:

- Remove the name-only validation path.
- Convert it into a wrapper around `McpToolDiscoveryService`.
- Keep it only as a clearly named quick shape check.

If retained, it must be explicitly documented as non-authoritative.

### Align tool definition checks

Tool definition mismatch checks should use the same effective live tool set that is used to build `RuntimeToolRegistry`.

Avoid reporting one tool set in startup validation while routing uses another.

### Preserve duplicate tool safety behavior

Duplicate tool names must remain fatal and excluded from the registry.

Do not introduce first-wins routing behavior.

## Acceptance criteria

- [ ] `McpToolDiscoveryService` is documented as the canonical `/v1/tools` validation path.
- [ ] `repl_health.py` name-only validation is removed, wrapped, or clearly marked as non-authoritative.
- [ ] Startup validation does not treat name-only validation as the source of truth.
- [ ] Runtime routing and startup validation are aligned around `RuntimeToolRegistry`.
- [ ] Duplicate tool names remain excluded from the registry and reported as fatal.
- [ ] Documentation clearly separates quick shape checks from registry-building validation.

## Tests

- Add a test confirming duplicate tool name detection remains consistent between startup and runtime.
- Add a test confirming tool metadata validation is performed by `McpToolDiscoveryService`.
