# Title
Extract gate-chain helper and merge invoke/record-result pattern between ToolExecutor and ToolTransportInvoker

## Priority
Low

## Target files
- `scripts/shared/tool_executor.py`
- `scripts/shared/tool_transport_invoker.py`
- `tests/shared/test_tool_executor_order.py` (must keep passing unchanged; may gain new characterization assertions)
- New characterization test file(s) under `tests/shared/` for the merged invoke/record-result helper (exact filename left to implementation; e.g. `tests/shared/test_tool_transport_invoker_merge.py`)

Out of scope for this requirement (see Background): the "typed args DTO" item from the source

## Background
Verified against current source (2026-08-13):
- `ToolExecutor._raw_execute` (`scripts/shared/tool_executor.py:109-145`) calls, in order:
  `self._check_startup_mode(server_key)` → `self._check_health(server_key)` →
  `await self._ensure_lifecycle_ready(server_key)` → transport resolution/call. This exact order
  is pinned by `tests/shared/test_tool_executor_order.py::test_transport_success_full_path`
  (line 159): `assert call_order == ["resolve", "health", "lifecycle", "transport"]`.
- `ToolExecutor._raw_execute` (`tool_executor.py:140-145`) and `ToolTransportInvoker.invoke()`
  (`scripts/shared/tool_transport_invoker.py:175-207`) contain a byte-for-byte identical
  try/except block:
  ```python
  try:
      result = await self._execute_with_semaphore(transport, tool_name, args, sem)
      self._record_success(server_key, result)
      return result
  except TransportError as e:
      return self._record_transport_error(server_key, e)
  ```
- `ToolExecutor` is the only class in `scripts/` that subclasses `ToolTransportInvoker`
  (`tool_executor.py:47`) — there are no other subclasses to account for in a blast-radius
  review.
- This is the same file pair covered by `docs/*` special-case guidance for MCP routing paths
  (`prompts/04_refactor.md` Special Cases): both files sit on the tool-call gate/transport path,
  so any structural change must preserve exact gate order and error-recording semantics, not just
  "equivalent" behavior.

This requirement document covers items 1 ("gate-chain helper") and 2 ("invoke-with-gates merge")
from `issues/20260813-133041_tool_executor_structural_followups.md`. Item 3 ("typed args DTO")
is explicitly excluded: the source issue itself says item 3 "touches every call site across
`scripts/agent/`" and must not be started "without first producing a `requires/` document given
its cross-cutting scope" — that scoping work has not been done, and bundling it here would mean
prescribing a cross-cutting migration without the dedicated blast-radius review it needs. Item 3
should be raised as its own future issue/requirement when someone is ready to scope it.

## Problem
1. The gate-check sequence in `ToolExecutor._raw_execute` (`_check_startup_mode` /
   `_check_health` / `_ensure_lifecycle_ready` / transport call) is inlined directly in that
   method. There is currently no reusable "gate chain" abstraction, so any future subclass or
   sibling execution path that needs the same ordered gate checks would have to duplicate the
   sequence by hand, risking an accidental reordering (which `test_transport_success_full_path`
   would catch only if that duplicate path is also covered by an equivalent order-locking test).
2. `ToolTransportInvoker.invoke()` and `ToolExecutor._raw_execute()` duplicate the exact same
   try/except + `_record_success`/`_record_transport_error` block. Any future change to error
   recording (e.g. adding a new exception type to catch, or changing what gets recorded) must be
   applied in both places by hand, and nothing currently enforces that the two stay in sync.

## Reason for change
Both duplications were identified during recent behavior-preserving refactor cycles on these two
files (2026-08-13) but were deliberately not folded into those cycles, because this file pair's
special-case sensitivity (MCP routing/gate-order path) means a structural change here needs its
own dedicated characterization-test-first cycle rather than being mixed into an already-scoped,
single-file, zero-behavior-change refactor. This requirement gives that dedicated cycle a
concrete scope. Deduplicating now (while there is exactly one subclass, `ToolExecutor`, and one
order-locking test to extend) is lower-risk than deferring further, since every additional caller
or test added later increases the blast radius of the eventual merge.

## Implementation intent
Two related but separately verifiable extractions, both confined to
`scripts/shared/tool_executor.py` and `scripts/shared/tool_transport_invoker.py`:

1. **Gate-chain helper**: Extract the ordered sequence `_check_startup_mode` → `_check_health` →
   `_ensure_lifecycle_ready` (as called from `_raw_execute`) into a single helper method (e.g.
   `_run_gate_chain(server_key)`), called before transport resolution. The helper must preserve
   the exact call order and exact exception/return behavior of each gate check — this is a pure
   extraction, not a reordering or a behavior change.
2. **Invoke/record-result merge**: Factor the shared try/except + `_record_success` /
   `_record_transport_error` block out of `ToolTransportInvoker.invoke()` and
   `ToolExecutor._raw_execute()` into one shared method on `ToolTransportInvoker` (e.g.
   `_invoke_and_record(server_key, transport, tool_name, args, sem)`), with `ToolExecutor`
   calling the inherited version after running its gate chain rather than reimplementing the
   try/except locally. Since `ToolExecutor` is the sole subclass today, this is a same-file
   merge, not a fan-out change — but the merged method must remain override-safe (do not make it
   `final`/private in a way that would block a legitimate future subclass override).

Do both extractions as pure refactors: no change to gate order, no change to which exceptions are
caught, no change to what gets recorded via `_record_success`/`_record_transport_error`, no change
to public method signatures of `ToolExecutor` or `ToolTransportInvoker`.

## Acceptance criteria
- `ToolExecutor._raw_execute` no longer inlines the three gate checks directly; they are called
  through a single extracted gate-chain helper, and the call order remains exactly
  `_check_startup_mode` → `_check_health` → `_ensure_lifecycle_ready` → transport call.
- `tests/shared/test_tool_executor_order.py` passes in full with no assertion changes to
  `test_transport_success_full_path`'s expected order list.
- The try/except + `_record_success`/`_record_transport_error` block that currently exists
  independently in both `ToolTransportInvoker.invoke()` and `ToolExecutor._raw_execute()` is
  consolidated into one method, with `ToolExecutor` calling the inherited version.
- The new characterization test(s) added in Implementation instructions step 4 pass both before
  (pinning current behavior) and after (confirming the merge preserved it) the merge.
- No public method signature on `ToolExecutor` or `ToolTransportInvoker` changes.
- No file under `scripts/agent/` is modified.
- `ruff`, `mypy`, and the full `tests/shared/` suite pass after the change.
