# Consolidate legacy-compatibility paths in RAG/DB schema and eventbus config

## Priority
Low

## Target files
- `scripts/rag/maintenance.py` (`COALESCE(normalized_content, content)` in `rebuild_fts`)
- `scripts/agent/services/rag_maintenance_service.py` (same `COALESCE(normalized_content, content)` pattern)
- `scripts/rag/ingestion/etag_manager.py` (`COALESCE(etag, ?)` fallback update)
- `scripts/mcp_servers/mdq/db_schema.py` (`_migrate_legacy_chunks_schema`: auto-detect old `chunks` schema and `DROP TABLE`/`DROP TRIGGER` it)
- `scripts/eventbus/config.py` (`_REMOVED_CONFIG_KEYS`, `load_config`: startup-failure guard for stale `poll_interval_ms`/`offset_checkpoint_interval` keys)
- `scripts/db/create_schema.py` (`create_rag_schema`, `create_session_schema`, `create_workflow_schema`, `create_eventbus_schema`)
- `scripts/db/schema_sql.py` (`apply_workflow_migrations`, and RAG/session schema DDL definitions)

## Background
The RAG/DB/eventbus layer carries several backward-compatibility mechanisms that exist to tolerate old data shapes or old schemas from earlier versions of the system:
- `COALESCE(normalized_content, content)` and `COALESCE(etag, ?)` null-fill fallbacks accommodate legacy chunk rows or non-Japanese chunks where `normalized_content`/`etag` may be null.
- `mdq.sqlite` auto-detects a legacy `chunks` schema (an `id` INTEGER PK column) at startup and silently `DROP`s and rebuilds the table and its FTS index/triggers.
- The eventbus config loader hard-fails startup if the TOML config still contains the removed `poll_interval_ms` or `offset_checkpoint_interval` keys.
- Among the SQLite databases, only `workflow.sqlite` has an incremental migration mechanism (`apply_workflow_migrations` in `scripts/db/schema_sql.py`); RAG and session schemas (`create_rag_schema`, `create_session_schema`) are created via plain `CREATE TABLE IF NOT EXISTS` DDL with no migration path — any schema change there relies on manual re-indexing/re-creation rather than migration.

## Problem
These compatibility paths were verified against current code and are still present and unresolved:
1. It has not been decided whether the `COALESCE` null-fill fallbacks are still needed, or whether they can be narrowed now that a re-index is an acceptable operational step.
2. The `mdq.sqlite` legacy-schema auto-DROP-and-recreate runs unconditionally and silently at startup, which is a data-loss risk with no explicit operator confirmation step or documented procedure.
3. It is unclear whether the eventbus removed-key startup-failure guard should remain permanently or be retired now that the deprecation window has likely passed.
4. Migration strategy is inconsistent across the three SQLite databases: `workflow.sqlite` has real incremental migrations, while RAG/session schemas have none, and this asymmetry is undocumented — engineers have no stated policy to follow when the RAG or session schema changes.

## Reason for change
Undocumented, inconsistent, and silently-destructive compatibility/migration behavior increases operational risk (unexpected data loss on `mdq.sqlite` schema mismatch) and increases maintenance cost (engineers must independently discover the DB-specific migration story before making schema changes). Making an explicit keep/reduce/remove decision for each path, and writing down one migration policy, removes ambiguity for future schema-changing work in this subsystem.

## Implementation intent
For each compatibility path, make and document an explicit decision (keep as-is, reduce/narrow, or remove) rather than defaulting to "leave in place" or "delete without evaluation":
- Evaluate whether the `COALESCE` fallbacks can be dropped given that a full re-index is available as a recovery path, and either keep them with a documented rationale or remove them and add an explicit backfill/re-index step.
- Decide whether `mdq.sqlite`'s silent auto-DROP-and-recreate should be replaced by an explicit, operator-confirmed migration step (e.g., requiring a flag, a warning-then-abort path, or a documented manual command) given its data-loss risk, or kept as-is with the risk explicitly documented.
- Decide whether the eventbus removed-config-key startup guard should stay permanently (defense against silently-ignored stale config) or be retired, and document the decision.
- Write down a single stated policy for how schema changes are handled per database (RAG, session, eventbus, workflow), addressing the current asymmetry — either extend incremental migrations to RAG/session schemas or explicitly document why recreate-on-change is acceptable for those databases.

Do not prescribe specific code changes beyond what each decision requires; this is a policy/design pass, not a mandate to remove every compatibility path.

## Implementation instructions
1. For `COALESCE(normalized_content, content)` (`scripts/rag/maintenance.py`, `scripts/agent/services/rag_maintenance_service.py`) and `COALESCE(etag, ?)` (`scripts/rag/ingestion/etag_manager.py`): assess whether legacy null rows can still occur in current ingestion paths; record the keep/reduce/remove decision and, if removing, add the corresponding backfill/re-index instructions.
2. For `_migrate_legacy_chunks_schema` in `scripts/mcp_servers/mdq/db_schema.py`: decide whether the automatic silent `DROP`/rebuild should require explicit operator action (e.g., a CLI flag, an environment variable, or a pre-flight warning with abort-by-default), and implement that decision or document why the current silent behavior is acceptable.
3. For `_REMOVED_CONFIG_KEYS` in `scripts/eventbus/config.py`: decide whether to keep, relax (warn instead of fail), or remove the guard; implement or document the decision.
4. Compare `create_workflow_schema` (uses `apply_workflow_migrations`) against `create_rag_schema`/`create_session_schema` (plain DDL, no migration) in `scripts/db/create_schema.py` and `scripts/db/schema_sql.py`; write the chosen migration policy for each database type, and apply it (either add a migration mechanism to RAG/session schemas consistent with the workflow one, or explicitly document — in code comments/docstrings — why those databases intentionally use recreate-only).
5. Ensure any behavior change (e.g., new operator confirmation gate on `mdq.sqlite` migration) is covered by tests.

## Acceptance criteria
- Each of the four compatibility/migration paths above has an explicit keep/reduce/remove decision reflected in the code (or an explicit code comment/docstring recording "keep, because ...").
- The `mdq.sqlite` data-loss-risk path (auto-DROP-and-recreate) has an explicit, documented handling (either an operator confirmation mechanism or a clearly documented rationale for why silent recreation remains acceptable).
- A single documented migration policy exists that explains, per database (RAG, session, eventbus config, workflow), whether incremental migration or recreate-on-change is used and why.
- All existing tests pass; no unrelated behavior changes are introduced.

## Tests
- Run the full existing test suite (`uv run pytest`) to confirm no regressions.
- If the `mdq.sqlite` legacy-migration behavior changes (e.g., gains a confirmation step), add/update tests covering both the legacy-schema-detected path and the no-legacy-schema path.
- If any `COALESCE` fallback is removed, add/update tests verifying the corresponding backfill/re-index step produces correct data.
- If the eventbus removed-key guard changes, add/update tests covering config files that do and do not contain the removed keys.
