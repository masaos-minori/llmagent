# Consolidate `_on_*_error` exception handlers and add exception chaining in `mcp_servers/file/common.py`

## Priority
Low

## Target files
- `scripts/mcp_servers/file/common.py` (`_on_auth_error`, `_on_not_found`, `_on_validation_error`, `resolve_safe`, `check_size_limit`)

## Background
Two related deferred ideas from `scripts/mcp_servers/file/common.py`'s 2026-08-14 refactor cycle:
1. `_on_auth_error`/`_on_not_found`/`_on_validation_error` are three structurally identical one-line async exception handlers (differ only by an HTTP status-code literal).
2. `resolve_safe`'s and `check_size_limit`'s `except OSError:` blocks re-raise as `FileValidationError` without `from e` exception chaining, losing the original traceback.

## Problem
1. Three nearly-identical exception handler functions create unnecessary duplication.
2. Two `OSError` → `FileValidationError` re-raises lose the original exception context via missing `__cause__`.

## Reason for change
Duplication removal reduces cognitive load. Exception chaining improves debugging by preserving the original error context. Both were identified during the refactor cycle but deferred due to potential side effects (handler identity changes, traceback rendering changes).

## Implementation intent
For (1): search `docs/`, logging call sites, and `check-mcp-docs` output for any reliance on these handlers' `__name__` before consolidating; if none found, extract a `_make_error_handler(status_code: int) -> Callable` factory. For (2): confirm no test asserts on `__cause__` or traceback text, and confirm no log-scraping tooling parses tracebacks, before adding `from e`.

## Implementation instructions
### Part A: Handler consolidation
1. Search `docs/`, logging call sites, and `check-mcp-docs` output for any reliance on `_on_auth_error`/`_on_not_found`/`_on_validation_error` handler `__name__` values.
2. If no dependency found:
   - Extract a shared factory function: `_make_error_handler(status_code: int) -> Callable[[Request, Exception], Awaitable[JSONResponse]]`.
   - Replace the three handlers with closures produced by the factory.
   - Re-verify FastAPI still registers/dispatches correctly.
3. If a dependency exists: document why each handler must remain separate and close this part of the issue.

### Part B: Exception chaining
1. Confirm no test asserts on `__cause__` or traceback text in `tests/mcp_servers/file/test_file_common.py`.
2. Add `from e` to both `OSError` re-raise sites:
   - `resolve_safe`: `raise FileValidationError("Invalid path") from e`
   - `check_size_limit`: `raise FileValidationError(str(e)) from e`
3. Run `tests/mcp_servers/file/test_file_common.py` to verify no regressions.

## Acceptance criteria
- All 3 exception-handler behaviors (status code, response body) are unchanged for callers.
- `resolve_safe`/`check_size_limit`'s raised `FileValidationError` instances have `__cause__` set to the original `OSError` (if that change is made).
- `tests/mcp_servers/file/test_file_common.py`'s 38 existing tests pass unchanged.
