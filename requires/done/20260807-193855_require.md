## Background
This chapter is the canonical source for the design intent behind shared types and Protocols (per `memo-doc-shared-review.md` §「章間の正本ルール」: 共通型とProtocolの設計意図 = `90_shared_02_types_and_protocols`). Per the memo's explicit note for this chapter: what matters is not the shape of the type, but why it lives in shared/ and which boundary it protects.

Note: `memo-doc-shared-review.md` exists and its guidance for this chapter remains valid based on independent verification against the source codebase.

## Problem
The types-and-protocols chapters contain exhaustive field-level detail that contradicts the memo's instruction to focus on design intent rather than type shape. Specifically:

- Full field definition of `LLMMessage` (core-types.md lines 61-73)
- Full field lists for DTOs like `ToolCallResult` (part1.md lines 47-63)
- Signatures for `ActionResult`/`ToolSpec`/`CacheEntry` (part1.md lines 76-86, 96-105, 116-129)
- dataclass definitions for `RawHit`/`MergedHit`/`RankedHit` (core-types.md lines 133-167)
- `ToolCallFunction`-family TypedDict listings (core-types.md lines 80-91, table format)
- Full field list of `ShellPolicy` (part2.md lines 94-110)
- Full tool frozenset name enumeration (reference.md lines 46-57)
- Pydantic definitions for `CallToolRequest`/`Response` (reference.md lines 67-74)
- Textbook-style Protocol/TypedDict/dataclass comparison table (reference.md lines 83-89)

Additionally, the current docs do not follow the standard template from `memo-doc-shared-review.md` §「修正後の章構成テンプレート」 — they use a different structure (numbered sections with type-by-type descriptions rather than the proposed purpose/design-intent/boundary/constraints format). This makes the cleanup task more substantial than just removing field lists; it requires restructuring the entire chapter organization.

## Reason for change
The document violates the design-doc reduction policy established in `memo-doc-shared-review.md`. Detail should be redirected to the source files rather than deleted, ensuring no loss of information for readers who need it.

## Implementation intent
Keep this chapter focused on: why common types live in shared/, why LLM DTOs are separated so they can be imported without `LLMClient`, the Protocol/TypedDict/dataclass usage policy, why `RagConfig` is a structural Protocol rather than `AgentConfig`, that `ArtifactEvent` is a data definition only (not an event bus), that `ShellPolicy` separates policy values from the shell MCP implementation, the design intent behind `RuntimeTool`/`RuntimeToolRegistry` heading toward being the canonical runtime metadata source, and the shared-is-leaf constraint (shared/ must not import agent's enums/config classes).

## Implementation instructions
1. Read `memo-doc-shared-review.md` §「90_shared_02_types_and_protocols」 including its 注意 note: describe why a type exists in shared/ and what boundary it protects, not its field shape.
2. Keep the reasoning listed above intact even where the surrounding field-level detail is trimmed.
3. Replace full DTO/dataclass/Protocol field lists and textbook-style type-comparison tables with cross-references to the appropriate source files.
4. Point to `scripts/shared/types.py` and other type-defining modules for exact implementation detail rather than transcribing them.
5. When in doubt whether a detail is operationally-critical, keep it. Mark unclear rationale as `Needs Confirmation`.
6. Manually check internal Markdown links after editing.

## Acceptance criteria
- All four files follow the standard template from `memo-doc-shared-review.md` §「修正後の章構成テンプレート」 where applicable.
- No full DTO/dataclass/Protocol field list or textbook-style type-comparison table remains.
- Each type's "why it's in shared/, what boundary it protects" rationale remains explicit.
