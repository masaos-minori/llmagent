# Replace manual file listing in docs/01_overview-files-04-shared-part1.md with an implementation-tree pointer, and document the confirmed 3-DB split rationale

## Priority
Medium

## Target files
- `docs/01_overview-files-04-shared-part1.md` (primary — file listing at lines ~24-47, DB description at lines ~28-31)

## Background
`docs/01_overview-files-04-shared-part1.md` documents the deployed `/opt/llm/` directory structure. Its file-listing block (lines 24-47) manually enumerates every file under `scripts/db/` (not `scripts/shared/` — see verification note below), plus the `db/` directory holding the three SQLite files. This pattern of manually-maintained file listings has been shown elsewhere in this doc set to drift out of sync with actual source over time, even though — as verified below — this particular listing is still accurate today.

Separately, the doc states (lines 28-31) that persistent state is split across `rag.sqlite`, `session.sqlite`, and `workflow.sqlite`, but gives no rationale for why three separate database files were chosen over one. This is flagged as the single most important "source of truth" fact in the file, so leaving the rationale undocumented risks a future consolidation decision being made without the original design constraint in view.

### Verification performed (Step 2 of issue-to-require)
- The file listing at lines 32-47 enumerates `scripts/db/` (13 entries: `__init__.py`, `create_schema.py`, `schema_sql.py`, `helper.py`, `maintenance.py`, `config.py`, `models.py`, `store.py`, `store_protocols.py`, `store_impl.py`, `rag_consistency.py`, `rotation.py`, `recovery.py`). Compared against the current contents of `scripts/db/` (via `ls`), this list is a complete and accurate 1:1 match with no additions, removals, or renames. Note: the issue's framing referenced `scripts/shared/`, but the actual doc content at these line numbers documents `scripts/db/` — `scripts/shared/` is the subject of the companion file `docs/01_overview-files-04-shared-part2.md`. The drift-risk concern (accurate today, manually maintained, no enforcement) applies identically to `scripts/db/`.
- The 3-DB split rationale was investigated via git commit history (not guessed). Commits `73bd9bb08`, `65cc81110`, and `fa703f346` (June 2026, "Metadata DB / Workflow / Idempotency implementation plan") explicitly record the design reasoning when `workflow.sqlite` was added as a database independent from the pre-existing `rag.sqlite`/`session.sqlite` pair:
  - `73bd9bb08`: "workflow.sqlite is independent from session.sqlite/rag.sqlite (avoids lock contention; WAL mode enforced)"
  - `fa703f346`: "SQLite lock contention: workflow.sqlite is independent DB + WAL mode + asyncio single-thread → no concurrent writes possible → removed [as an open risk]"
  - This is corroborated by `docs/90_shared_04_03_db_architecture_and_schema-migration-and-scaling.md`, which documents that `rag.sqlite`/`session.sqlite`/`eventbus.sqlite` are architecturally independent (no shared incremental-migration mechanism, separate recreation procedures).
  - **This confirms the rationale exactly as speculated in the issue's example sentence: the split avoids lock contention between databases with different write frequencies/patterns (session state changes every turn, workflow state changes per task-tracking event, RAG index changes only during ingestion).**
  - Scope limit on the evidence: the recorded rationale explicitly covers separating `workflow.sqlite` from `{rag,session}.sqlite`. No commit was found stating an explicit rationale for the original `rag.sqlite` vs `session.sqlite` split (that split predates the workflow.sqlite design commits and was not accompanied by a recorded design note). The lock-contention principle is the best-evidenced explanation and is architecturally consistent with the rag/session split too, but this specific pairwise rationale is inferred by the same design logic rather than directly quoted from a commit message for that pair.

## Problem
1. The file listing at lines 32-47 duplicates information (`scripts/db/` contents) that is better sourced from the implementation tree itself, creating an ongoing manual-maintenance burden and drift risk consistent with other reviewed sections of this doc set — even though currently accurate.
2. The rationale for the 3-DB split (lines 28-31) is not documented in `docs/01_overview-files-04-shared-part1.md`, despite this document itself calling it out as key "source of truth" information. Readers cannot tell whether the split is an intentional constraint (e.g., avoiding lock contention) or an accident of history, risking an uninformed future consolidation.

## Reason for change
The maintenance cost/drift-risk pattern of manual file listings has already been established elsewhere in this doc set as not worth carrying forward. Now that the 3-DB split rationale has been positively confirmed via commit history (rather than needing to be flagged as unconfirmed), it should be captured in the doc before that historical context is lost or a consolidation is proposed without it.
