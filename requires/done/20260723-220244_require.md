## Title

Fix _http_procs cleanup on MCP subprocess startup failure

## Priority

Critical

## Target files

- scripts/agent/http_lifecycle.py
- scripts/agent/startup.py

## Background

When an HTTP MCP subprocess fails during startup, the StartupOrchestrator.rollback path calls lifecycle.shutdown_all() which only shuts down already-successful servers. The failing server's state in HttpServerLifecycleManager is not fully cleaned up.

## Problem

After verifying the current source code, the issue description needs correction:

1. **http_lifecycle.py:263-280 ("exited early" path)**: `proc.poll() is not None` detects process termination, but `_terminate_with_timeout()` is NOT called. However, since `proc.poll() is not None`, the process has already exited — this is not a true orphan process.

2. **http_lifecycle.py:295-306 ("timeout" path)**: `_terminate_with_timeout(proc, server_key)` IS called here, so no orphan process occurs in this path.

3. **Common issue in both paths**: `_http_procs[server_key]` is NOT removed after the exception. The process entry remains in the dict even though the process is no longer running.

4. **stderr file leak**: Both paths call `fh.close()`, so stderr file handles are properly closed. No file descriptor leak exists.

## Reason for change

Stale entries in `_http_procs` cause incorrect behavior in subsequent operations:
- `ensure_ready()` checks `self._http_procs.get(server_key)` to determine if a subprocess is running. A stale entry makes it believe the process is still alive when it is not.
- Subsequent restart attempts will skip starting a new process because `existing = self._http_procs.get(server_key)` returns a stale Popen object whose `poll()` result may be unpredictable.
- The stale entry prevents proper cleanup during shutdown.

## Implementation intent

Ensure all internal state (`_http_procs`, `_http_pgids`) is cleaned up consistently on any startup failure, regardless of which error path triggers.

## Implementation instructions

### Option A: Fix in http_lifecycle.py:start()

Add `_http_procs.pop(server_key, None)` and `_http_pgids.pop(server_key, None)` before raising `HttpStartupError` in both error paths:

```python
# In "exited early" path (~line 280):
raise HttpStartupError(failure)

# Before raise, add:
self._http_procs.pop(server_key, None)
self._http_pgids.pop(server_key, None)

# In "timeout" path (~line 306):
raise HttpStartupError(timeout_failure)

# Before raise, add:
self._http_procs.pop(server_key, None)
self._http_pgids.pop(server_key, None)
```

### Option B: Use finally block

Wrap the health-poll loop in a try-finally to ensure cleanup happens regardless of how the loop exits:

```python
try:
    while time.monotonic() < deadline:
        ...
finally:
    self._http_procs.pop(server_key, None)
    self._http_pgids.pop(server_key, None)
```

Option A is preferred for clarity and minimal diff.

## Acceptance criteria

1. After MCP subprocess startup failure, `_http_procs[server_key]` must be empty.
2. After MCP subprocess startup failure, `_http_pgids[server_key]` must be empty.
3. After MCP subprocess startup failure, `_stderr_files[server_key]` must be empty.
4. After MCP subprocess startup failure, `_stderr_log_paths[server_key]` must be empty.
5. Subsequent `ensure_ready()` call must correctly detect the missing subprocess and attempt to start it again.
6. All existing tests pass without modification.
