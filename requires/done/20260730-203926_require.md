# Requirement: Consistent Error Handling for MCP Server Health Checks

## Priority

Low — inconsistency exists but has limited practical impact; both paths ultimately fail the same way on persistent failures

## Target Files

- `scripts/agent/startup.py` (lines 143-169, 171-217)

## Background

The startup sequence includes two phases that verify MCP server health:
1. `_start_servers()` — starts HTTP subprocess MCP servers and performs initial health checks
2. `_verify_mcp_health()` — post-startup health verification after all servers are started

## Problem

`_start_servers()` does not retry on health check failure, while `_verify_mcp_health()` retries once after a 1-second delay. This inconsistency means transient failures during startup cause immediate fatal errors, while the same failures during post-startup verification get a grace period.

## Reason for Change

Inconsistent error handling between related code paths makes debugging confusing and creates different behavior depending on which phase a transient failure occurs in.

## Implementation Intent

Align the retry behavior across both methods to ensure consistent handling of transient health check failures.

## Implementation Instructions

Choose one approach:

**Option A — Add retry to `_start_servers()`:**
- Add a single retry attempt to `_start_servers()` matching the pattern in `_verify_mcp_health()`
- Retry after 1 second delay before failing
- Log at INFO level on first attempt, WARNING level on retry

**Option B — Remove retry from `_verify_mcp_health()` and document intent:**
- Remove the retry logic from `_verify_mcp_health()`
- Document why strict behavior is desired during startup vs. post-startup
- Ensure both methods have identical retry semantics (zero retries)

Option A is recommended because it reduces false negatives during startup when servers may take slightly longer to respond.

## Acceptance Criteria

- [ ] Both `_start_servers()` and `_verify_mcp_health()` use the same retry policy
- [ ] Retry delay is configurable or documented as a constant
- [ ] Logging levels are consistent between the two methods
- [ ] No regression in existing behavior for persistent failures

## Tests

- Unit test verifying retry behavior in `_start_servers()` matches `_verify_mcp_health()`
- Integration test verifying both methods behave identically under transient network failure
