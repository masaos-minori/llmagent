# WAL checkpoint failure on shutdown risks data loss

## Priority

High

## Target Files

- `scripts/agent/repl.py` — AgentREPL._close_resources()

## Background

During graceful shutdown, `_close_resources()` performs a WAL checkpoint before closing the session database connection. If the checkpoint fails, the error is logged as a warning and the connection is closed without checkpointing.

## Problem

In `repl.py:261-271`:

```python
try:
    with SQLiteHelper("session").open(write_mode=True) as db:
        wal_mode = db.execute("PRAGMA journal_mode").fetchone()[0]
        if wal_mode.lower() == "wal":
            db.checkpoint("TRUNCATE")
            logger.info("WAL checkpoint completed on shutdown")
        else:
            logger.debug("WAL checkpoint skipped: journal mode is %r", wal_mode)
except sqlite3.Error as e:
    errors.append(("wal_checkpoint", f"{type(e).__name__}: {e}"))
    logger.warning("WAL checkpoint failed on shutdown: %s", e)
```

When `db.checkpoint("TRUNCATE")` raises `sqlite3.Error`, the context manager closes the connection without completing the checkpoint. Any unflushed WAL pages are lost.

## Reason for Change

Data loss during shutdown is unacceptable for a system that persists conversation history, tool call results, and workflow state. A WAL checkpoint failure should be treated as a serious condition requiring remediation.

## Implementation Intent

Ensure WAL checkpoint failure does not result in silent data loss. Add retry logic with exponential backoff, or escalate the failure to an error level with explicit user notification.

## Implementation Instructions

1. Add a retry loop around `db.checkpoint("TRUNCATE")` with up to 3 attempts and exponential backoff (1s, 2s, 4s).
2. After retries are exhausted, change the log level from WARNING to ERROR.
3. Optionally, copy the WAL file to a backup location before closing the connection, so the data can be recovered manually.
4. Consider adding a `PRAGMA wal_checkpoint(PASSIVE)` before attempting `TRUNCATE` — PASSIVE may succeed where TRUNCATE fails because it does not require exclusive access.

## Acceptance Criteria

- [ ] WAL checkpoint failure triggers retry with backoff
- [ ] Data is not silently lost when checkpoint fails after retries
- [ ] Error is escalated to ERROR log level if all retries fail
- [ ] Session connection is properly closed regardless of checkpoint outcome

## Tests

- Unit test: mock `db.checkpoint()` to raise; verify retry count and eventual error logging
- Integration test: simulate WAL checkpoint failure by holding a lock; verify WAL data preservation
