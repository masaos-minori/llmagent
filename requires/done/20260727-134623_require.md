## Background

`PipelineRunResult` (declared in `scripts/rag/types.py`) has a `result_source: str | None = None`
field. A separate, similarly named field exists on `SearchDiagnostics`
(`scripts/rag/models_result.py:102`, typed as `ResultSource` enum), which *is* actively set at
`scripts/rag/pipeline.py:484/489/494` (`ResultSource.REMOTE` / `ResultSource.FALLBACK`) and is
covered by tests (`tests/test_rag_http_mode.py`, `tests/test_pipeline_http_result_kind.py`).

An earlier revision of the docs incorrectly attributed the "set via `dataclasses.replace()`"
behavior to `PipelineRunResult.result_source`; that description has since been corrected in the
docs to clarify the two fields are distinct. However, the underlying question the correction left
open — whether `PipelineRunResult.result_source` itself is genuinely dead code — was flagged as
"Needs confirmation" and never resolved.

Git history shows `PipelineRunResult.result_source` was introduced in commit `342d828728b9a3`
("feat: implement config validator, pipeline HTTP result kinds, and plugin hooks protocol",
2026-06-24) alongside `PipelineHttpResultKind` and plugin hooks work, but no commit since has ever
assigned a non-default value to it.

## Problem

Verification against current source confirms the issue's claim:

- `grep -rn "PipelineRunResult(" --include="*.py" .` shows the field is only ever constructed via
  keyword arguments in `scripts/rag/pipeline.py:347` and in test fixtures
  (`tests/test_agent_rag.py`, `tests/test_pipeline_http_result_kind.py`,
  `tests/test_rag_http_mode.py`, `tests/test_rag_pipeline.py`, `tests/test_rag_refiner.py`,
  `tests/test_rag_quality_regression.py`) — none of these pass `result_source=`.
- `grep -rn "\.result_source" --include="*.py" .` (excluding test files) returns no matches outside
  the field declaration itself — no code path reads `PipelineRunResult.result_source` anywhere.
- The sole production constructor, `scripts/rag/pipeline.py:347`, omits `result_source`, so it is
  always `None` in practice.

The field is confirmed dead: it is declared, never written by any code path, and never read by any
code path. This creates ongoing risk of confusion with the actively-used
`SearchDiagnostics.result_source` (`ResultSource` enum) field of a similar name.

## Reason for Change

The docs explicitly mark this as an open "Needs confirmation" item
(`docs/03_rag_03_06_query_pipeline-helpers-and-cache-part2.md:120`) requiring implementer
confirmation on whether the field is planned for future use (e.g. a plugin hook consumer) or should
be removed as residual dead code. Leaving it unresolved perpetuates maintenance confusion between
two similarly-named `result_source` fields on different classes. This requirement resolves the open
question so a concrete implementation decision (remove vs. retain-with-justification) can be made in
a follow-on plan/implementation cycle.

## Implementation Intent

Investigate whether `PipelineRunResult.result_source` was intended to be wired into any planned
feature (in particular the plugin hooks protocol / `PipelineHttpResultKind` work introduced in the
same commit that added the field), and reach a decision:

- If no future use is identified: remove the field from `PipelineRunResult` (and any references in
  tests/fixtures that pass it, if not already omitted) as dead code.
- If a legitimate future use is identified (e.g. a documented plugin extension point): keep the
  field but add an inline code comment in `scripts/rag/types.py` explaining its intended future
  consumer, and update the docs to remove the "Needs confirmation" label in favor of that
  explanation.

Note: per the issue-to-requirement workflow's document-only phase constraints, this requirement
document does not itself modify `docs/*.md` or source code — those changes belong to the downstream
plan/implementation phases.
