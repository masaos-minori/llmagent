# Add nosec annotations for bandit B608 false positives

## Priority

High

## Target Files

- `scripts/eventbus/db.py:210` — IN clause with placeholder generation
- `scripts/eventbus/subscribe_route.py:51` — same pattern
- `scripts/mcp_servers/mdq/db_grep.py:70` — WHERE clause assembly with params binding
- `scripts/mcp_servers/mdq/health_check.py:35` — STALE_SQL_CONDITION constant
- `scripts/mcp_servers/mdq/mdq_service.py:209` — where_clauses fragment + params
- `scripts/mcp_servers/mdq/mdq_service.py:340` — STALE_SQL_CONDITION constant

## Background

bandit reports B608 (SQL injection via string query construction) issues in the eventbus
and mdq modules. All are false positives: values are always bound via `?` placeholders,
never concatenated into SQL strings.

**Needs confirmation resolved (verified 2026-08-23):** running `uv run bandit -r scripts/
-c pyproject.toml` now shows exactly 6 unannotated B608 findings, not 8. The two
`scripts/mcp_servers/mdq/search.py` locations originally filed here
(`_build_search_where()` fixed fragment + params, at the requirement's line 145 and 156)
already carry `# nosec B608 — where_clause built only from static predicate fragments in
_build_search_where(); all values bound via params` and are excluded from this
requirement's scope. The two `mdq_service.py` line numbers also shifted (205→209,
327→340) since the requirement was filed; the Target Files list above uses current line
numbers. `db.py:195`→`210` and `subscribe_route.py:47`→`51` shifted for the same reason.

## Problem

```bash
$ uv run bandit -r scripts/ -c pyproject.toml
Issue: [B608:hardcoded_sql_expressions] Possible SQL injection vector through string-based query construction.
```

The db layer already has correct nosec annotations (`scripts/db/maintenance.py:169`,
`scripts/db/store_impl.py:259`) using the format `# nosec B608 — <justification>` — note
this uses an em dash (U+2014, `—`), not a hyphen. The eventbus and mdq layers have
identical query patterns but the 6 locations above lack annotations.
`tools/check_suppression_justification.py` enforces the em-dash-delimited format for
every `# nosec` in `scripts/` — a hyphen-delimited annotation fails this check.

## Reason for Change

Without nosec annotations, CI fails on bandit even though there is no actual
vulnerability. This creates noise and reduces signal quality.

## Implementation Intent

Add `# nosec B608 — <justification>` annotations (em dash, matching the db-layer format
and `tools/check_suppression_justification.py`'s requirement) to all 6 locations.

## Implementation Instructions

For each location, add a comment after the SQL string expression:

```python
# Before:
cursor.execute(f"SELECT * FROM events WHERE topic IN ({','.join('?' for _ in topics)})", params)

# After:
cursor.execute(f"SELECT * FROM events WHERE topic IN ({','.join('?' for _ in topics)})", params)  # nosec B608 — all values bound via ? placeholders
```

Justifications by category:
- eventbus (2): "all values bound via ? placeholders"
- mdq db_grep (1): "WHERE clause built from fixed column names; values bound via params"
- mdq health_check (1): "STALE_SQL_CONDITION is a fixed string constant"
- mdq mdq_service (2): "where_clauses fragments from fixed constants; values bound via params"

After adding annotations, verify:
1. `uv run bandit -r scripts/ -c pyproject.toml` exits with medium/high issue count = 0
2. `uv run python tools/check_suppression_justification.py scripts/eventbus/db.py
   scripts/eventbus/subscribe_route.py scripts/mcp_servers/mdq/db_grep.py
   scripts/mcp_servers/mdq/health_check.py scripts/mcp_servers/mdq/mdq_service.py`
   reports no missing-justification violations
