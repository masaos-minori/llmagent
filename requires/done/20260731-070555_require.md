# Requirement: Add Exclusive Locking to Stale Attempt Recovery

## Priority

High

## Target Files

- `scripts/agent/workflow/state_store.py`

## Background

When multiple processes or threads execute `recover_stale_attempts()` simultaneously, the same stale attempt can be recovered multiple times because there is no exclusive locking mechanism.

## Problem

In `state_store.py`:

```python
cursor.execute("""
    SELECT id, workflow_id FROM workflow_attempts
    WHERE status = 'running'
    AND updated_at < ?
""", (stale_threshold.isoformat(),))
rows = cursor.fetchall()

for row in rows:
    await self._recover_attempt(row['id'])
```

This means:

1. Process A reads stale attempts (e.g., IDs 1, 2, 3)
2. Process B reads the same stale attempts (IDs 1, 2, 3) — before either has recovered them
3. Both processes attempt to recover the same attempts
4. Result: duplicate execution, database inconsistency

## Reason for Change

Duplicate recovery causes resource waste, potential data corruption, and unpredictable behavior. Only one process should recover a given stale attempt.

## Implementation Intent

Add exclusive locking to prevent concurrent processes from recovering the same stale attempt. Use SQLite's `FOR UPDATE SKIP LOCKED` clause as the primary approach, with Redis distributed lock as an alternative for multi-database scenarios.

## Implementation Instructions

### Step 1: Add `FOR UPDATE SKIP LOCKED` to the query

```python
async def recover_stale_attempts(self):
    """Recover stale workflow attempts with exclusive locking."""
    grace_period = timedelta(seconds=30)
    stale_threshold = datetime.now() - grace_period
    
    # Fetch only one stale attempt at a time, skipping locked ones
    cursor = self.db.execute("""
        SELECT id, workflow_id FROM workflow_attempts
        WHERE status = 'running'
        AND updated_at < ?
        ORDER BY created_at ASC
        LIMIT 1
        FOR UPDATE SKIP LOCKED
    """, (stale_threshold.isoformat(),))
    
    row = cursor.fetchone()
    
    if row:
        logger.info(f"Recovering stale attempt {row['id']}")
        await self._recover_attempt(row['id'])
        return True  # Successfully recovered one attempt
    
    return False  # No stale attempts available
```

### Step 2: Retry loop for continuous recovery

Since only one attempt is recovered per call, add a retry loop:

```python
async def recover_all_stale_attempts(self):
    """Continuously recover stale attempts until none remain."""
    while True:
        recovered = await self.recover_stale_attempts()
        if not recovered:
            break
```

### Alternative: Redis distributed lock (if needed for multi-database)

If the system uses multiple databases or requires cross-process coordination beyond SQLite's scope:

```python
import aioredis

async def recover_stale_attempts(self):
    lock_key = f"stale_attempt_recovery:{self.workflow_id}"
    lock = await aioredis.Lock(lock_key, timeout=30)
    
    if not await lock.acquire(blocking=False):
        logger.debug("Another process holds the lock, skipping")
        return False
    
    try:
        # ... existing recovery logic
    finally:
        await lock.release()
```

### Recommendation

SQLite's `FOR UPDATE SKIP LOCKED` is sufficient for single-database scenarios. The Redis approach is overkill unless cross-database coordination is required.

## Acceptance Criteria

1. Concurrent processes never recover the same stale attempt
2. All stale attempts are eventually recovered when multiple processes run concurrently
3. Normal recovery operation is unaffected — no regression
