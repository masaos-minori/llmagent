# Clarify and document the read path for JSONL-archived memory

## Priority

Medium

## Target Files

- `docs/05_agent_04_03_state-and-persistence-platform-databases.md:54` — "Needs confirmation" note about the archived-memory read path
- `scripts/agent/memory/jsonl_store.py` — `JsonlMemoryStore` (`read_all`, `read_active`, `count_all`) — the archive read API
- `scripts/agent/memory/import_ops.py` — `import_from_jsonl()` — imports archive entries back into SQLite `memories`/`memories_fts`/`memories_vec`
- `scripts/agent/commands/memory_rebuild_ops.py` — `MemoryRebuildOps.rebuild()` — the `/memory rebuild` command that exposes the read/import path to operators
- `docs/00_governance_07_needs-confirmation-inventory.md` (NC-007 entry) — inventory record to be closed once documentation is updated

## Background

`agent/memory/jsonl_store.py`'s `JsonlMemoryStore` appends every `MemoryEntry` write to a
non-authoritative, append-only JSONL file for backup/audit purposes (SQLite via `MemoryStore`
remains the source of truth). `docs/05_agent_04_03_state-and-persistence-platform-databases.md:54`
flags the read path for this archive as "Needs confirmation" (tracked as NC-007 in
`docs/00_governance_07_needs-confirmation-inventory.md`), stating that whether archived data can
be read back after write is unverified.

## Problem

Investigation of the current source shows the read path already exists and is fully wired in,
but this is not reflected in the documentation:

- `JsonlMemoryStore.read_all()` deserializes every line back into a `MemoryEntry`, raising
  `JsonlFormatError` on the first malformed line (`scripts/agent/memory/jsonl_store.py:72-89`).
- `JsonlMemoryStore.read_active()` layers per-source-type retention filtering on top of
  `read_all()` (`scripts/agent/memory/jsonl_store.py:91-111`), but has no caller anywhere in
  `scripts/` outside of tests — it is currently dead/unused code from a production-path
  perspective.
- `JsonlMemoryStore.count_all()` is used operationally by `/memory rebuild` and
  `/memory check-consistency` (`scripts/agent/commands/memory_rebuild_ops.py:46,130`) to report
  the archive's record count.
- `agent/memory/import_ops.py:import_from_jsonl()` calls `read_all()` and re-inserts every entry
  into SQLite (`memories`/`memories_fts`/`memories_vec`), after clearing those tables. This is the
  concrete, tested, end-user-facing read path: it is invoked via the `/memory rebuild` command
  (`scripts/agent/commands/memory_rebuild_ops.py:38-96`), which supports a dry-run mode (default)
  and a `--confirm` mode that performs the actual re-import.
- The module docstring in `jsonl_store.py:10-11` already states the intended usage: "Use
  `read_all()` for audit, export, or one-time import. Do not use it to rebuild authoritative
  state — use `MemoryStore` directly or restore from a SQLite backup." This intent is not
  reflected in the referenced doc section.
- Test coverage exists for the full round trip: `tests/test_regression_jsonl_config.py`,
  `tests/test_memory_jsonl.py`, `tests/test_jsonl_store.py`, and `tests/test_memory_consistency.py`
  (via `count_all()`) all exercise write-then-read behavior.

So the underlying open question ("does read-after-write work, and what is the path?") has a
verifiable, existing answer in code; the doc simply has not been updated to state it, and the
"Needs confirmation" marker was never removed.

## Reason for Change

Leaving an accurate, already-implemented read path marked "Needs confirmation" in the
documentation is misleading: it implies a possible functionality gap or data-loss risk that does
not exist, and it leaves NC-007 open in the governance inventory indefinitely. Closing this out
keeps `docs/05_agent_04_03_state-and-persistence-platform-databases.md` and the NC inventory
accurate, and gives future readers (and future NC audits) a concrete pointer (`/memory rebuild`,
`import_from_jsonl`) instead of an open question.

Separately, `read_active()` having no production caller is worth flagging during the
investigation (see Implementation Instructions) so a decision can be made on whether it is
intentionally reserved for a future retention-aware read flow or should be removed — but this
determination is out of scope for the doc-only fix itself and should be captured as a follow-up
note rather than blocking the documentation update.
