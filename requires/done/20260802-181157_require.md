## Background
`docs/03_rag_02_03_ingestion_pipeline-chunksplitter-part1.md` §3.1 currently contains a
"モジュールレベルの定数" (module-level constants) table (lines 37-43, listing
`MIN_HEADING_LINES_FOR_MARKDOWN` and `MARKDOWN_HEADING_RE`) and a "公開メソッド"
(public methods) table (lines 59-65, listing `__init__`, `process_all`, `process_file`
with full signatures). These are verbatim transcriptions of
`scripts/rag/ingestion/chunk_splitter.py` content, confirmed still present as of this
review. `docs/03_rag_02_03_ingestion_pipeline-chunksplitter-part2.md` §3.3's CLI-argument
table (line 65) describes `--force` as "既存チャンクを再生成する（センチネルチェックを上書き）".

This mirrors a project-wide documentation-review finding
(`docs_review_rag.md` §1 "コード説明に寄りすぎている領域", §2 削除候補 item 2, §6B) that
constant/method tables without selection rationale are mechanical code transcription
that belongs in code comments / Reference API docs, not in narrative design docs.

## Problem
1. Part1's constant table and public-methods table duplicate what is already in the
   source code (`scripts/rag/ingestion/chunk_splitter.py`), without adding any design
   rationale — a maintenance burden with no offsetting value, and prone to drifting out
   of sync with the code (as flagged generally in `docs_review_rag.md`).
2. Part2's `--force` description, while already a single table cell, is part of a CLI
   table that the issue asks to compress to a fixed, simpler wording that avoids the
   internal implementation detail ("センチネルチェックを上書き" → "センチネルチェックを無視し").
3. `MIN_HEADING_LINES_FOR_MARKDOWN=2`'s rationale (experimental tuning vs. arbitrary
   convention) has never been documented anywhere in the repo, leaving future
   implementers unable to judge whether the threshold can safely be changed.

## Reason for change
Mechanical tables add no design information beyond what a code reader already gets from
`chunk_splitter.py`, and they must be kept in sync with the code by hand, which has
already drifted for similar tables elsewhere per `docs_review_rag.md`. Trimming these
tables reduces duplication and maintenance surface. Separately, threshold constants such
as `MIN_HEADING_LINES_FOR_MARKDOWN` are the kind of design-relevant value that *is* worth
keeping in prose, so its rationale (or the explicit absence of one) should be recorded
once, here, rather than left silently undocumented.

## Finding: MIN_HEADING_LINES_FOR_MARKDOWN=2 rationale (investigated, unconfirmable)
Investigated via `git log --all -S "MIN_HEADING_LINES_FOR_MARKDOWN"` and `git log --all -p
--follow -- scripts/ChunkSplitter.py` / `scripts/rag/ingestion/chunk_splitter.py`:
- The named constant `MIN_HEADING_LINES_FOR_MARKDOWN = 2` was introduced in commit
  `16c27288b` ("refactor: eliminate magic values in scripts/ (PLR2004)"), which only
  extracted an already-hardcoded literal `2` into a named constant — it did not change
  the threshold value or add rationale.
- The literal `>= 2` heuristic itself (with only the inline comment "Treat as Markdown
  when at least two heading lines are found") is present unchanged in the very first
  commit of this repository (`6b56ecfa1`, "Initial commit: LLM agent REPL with RAG, MCP
  servers, and plugin architecture"), at `scripts/chunk_splitter.py`. There is no
  pre-initial-commit history available in this repository, and no design/plan document
  (searched `plans/`, `docs_review_rag.md`, and design-note commits such as `adc463b30`)
  records why `2` specifically was chosen over `1` or `3`.
- Conclusion: the rationale is genuinely unconfirmable from repository history — this is
  not a case of insufficient investigation. Document it as an explicit
  **Needs Confirmation** item (per `rules/coding.md`'s "Documentation notes" classification:
  this is a case where the discrepancy is "the rationale was never recorded", closest to
  the project's existing `docs_review_rag.md` §6B "Needs confirmation" pattern — confirm
  with the original author if determinable, otherwise leave as an explicitly tracked open
  item rather than inventing a rationale).
