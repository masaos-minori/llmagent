# DiagnosticStore: configurable sensitive_fields, decrypt-on-fetch, and accurate docstring

## Priority
Medium

## Target files
- `scripts/agent/config_builders.py` (`_build_diagnostics_config()`)
- `scripts/agent/diagnostic_store.py` (`DiagnosticStore._load_diagnostics_config()`, `DiagnosticStore.fetch()`, `DiagnosticStore._filter_sensitive_fields()`)
- `scripts/agent/config_dataclasses.py` (`DiagnosticsConfig` — reference only; no field changes required)
- `docs/05_agent_08_04_configuration-mcp-approval-obs.md` (DiagnosticsConfig section)

## Background
`DiagnosticsConfig` already declares a `sensitive_fields: frozenset[str]` field (default
`{"artifacts", "rag_stage_outcomes"}`) intended to let operators extend the set of payload
keys redacted by `DiagnosticStore._filter_sensitive_fields()`. `DiagnosticStore.save()` also
supports an `encrypt=True` path that Fernet-encrypts row content when an `encryption_key` is
configured.

## Problem
Three related defects were verified against the current source:

1. **`sensitive_fields` is not wired to config.** Both `_build_diagnostics_config()` in
   `scripts/agent/config_builders.py` (lines 431-439) and
   `DiagnosticStore._load_diagnostics_config()` in `scripts/agent/diagnostic_store.py`
   (lines 43-59) construct `DiagnosticsConfig` passing only `encryption_key` and
   `retention_days`. `sensitive_fields` is never read from the `[diagnostics]` table in
   `agent.toml`, so it always resolves to the dataclass default. An operator who adds a
   `sensitive_fields` entry to `agent.toml` gets no redaction of that field and no error or
   warning — a silent data-hygiene gap.
2. **Encrypted rows cannot be read back.** `DiagnosticStore.save()` Fernet-encrypts content
   when `encrypt=True` and a key is configured, but `DiagnosticStore.fetch()` (lines
   166-175) returns row content verbatim with no decrypt step. Any row saved with
   `encrypt=True` comes back as raw ciphertext. This is latent today because all current
   callers (`save_serialization_event`, `save_partial_completion`, `save_transport_failure`)
   use `encrypt=False`, but it becomes an active defect the moment any caller sets
   `encrypt=True`.
3. **Docstring overstates behavior.** `_filter_sensitive_fields()`'s docstring (lines 61-72)
   states "The set of sensitive fields is loaded from DiagnosticsConfig and merged with the
   hardcoded defaults" — true of the code path in isolation, but misleading given defect (1):
   the configured value can never differ from the default in practice today.
4. **Design doc is incomplete.** `docs/05_agent_08_04_configuration-mcp-approval-obs.md`
   documents `encryption_key` and `retention_days` for `DiagnosticsConfig` (lines 87-88, 124)
   but omits `sensitive_fields` entirely.

## Reason for change
This is a data-hygiene and observability-correctness risk: operators configuring redaction
via `agent.toml` currently get silent no-ops, and any future adoption of encrypted
diagnostics storage would silently produce unreadable data. Fixing both wiring gaps now
(before any caller sets `encrypt=True`) avoids a production incident and aligns documented
behavior with actual behavior.

## Implementation intent
- Read `sensitive_fields` from the `[diagnostics]` table in both `_build_diagnostics_config()`
  and `DiagnosticStore._load_diagnostics_config()`, preserving union-with-defaults semantics
  (configured values are additive to `_SENSITIVE_FIELDS`, not a replacement) — this matches
  the union logic already implemented inside `_filter_sensitive_fields()`.
- Resolve the fetch/decrypt gap using one of two acceptable options, chosen based on what
  best fits the existing encryption design in `diagnostic_store.py`:
  - **Option A (decrypt):** `fetch()` decrypts each row's content with the configured Fernet
    key when the content appears to be Fernet-encrypted, returning plaintext to callers.
  - **Option B (explicit marker):** `fetch()` (or `save()`) tags encrypted rows so they are
    never silently treated as plaintext JSON by downstream readers — e.g. a wrapper field or
    sentinel indicating "content is encrypted, not decodable via this path."
  Either option must eliminate the current silent failure mode (ciphertext handed to callers
  expecting plaintext/JSON).
- Update `_filter_sensitive_fields()`'s docstring to describe the corrected, working
  behavior once (1) is fixed.
- Add `sensitive_fields` to the DiagnosticsConfig section of
  `docs/05_agent_08_04_configuration-mcp-approval-obs.md`, describing its purpose (additive
  redaction field list) without embedding the concrete default value in the doc.

## Implementation instructions
1. In `scripts/agent/config_builders.py::_build_diagnostics_config()`, read
   `diagnostics_raw.get("sensitive_fields", ...)` from the `[diagnostics]` table (list of
   strings in TOML) and pass it to `DiagnosticsConfig(sensitive_fields=...)`, unioned with
   the dataclass default rather than overriding it outright — keep behavior consistent with
   how `_filter_sensitive_fields()` currently unions `_SENSITIVE_FIELDS` with the config
   value.
2. Apply the same fix to `DiagnosticStore._load_diagnostics_config()` in
   `scripts/agent/diagnostic_store.py` so both config-construction paths behave identically.
3. Decide and implement Option A or Option B for `DiagnosticStore.fetch()`:
   - If Option A: detect Fernet-encrypted content (e.g. try/except around `Fernet(key).decrypt(...)`,
     or a stored marker distinguishing encrypted vs. plaintext rows) and decrypt using the
     configured `encryption_key` before returning; handle the case where the key is
     missing/rotated (row cannot be decrypted) explicitly rather than raising an unhandled
     exception into callers.
   - If Option B: add an explicit indicator (e.g. an `encrypted: bool` key in the returned
     dict, or a content prefix/sentinel) so any caller can distinguish encrypted rows from
     plaintext ones and choose not to parse ciphertext as JSON.
4. Update the `_filter_sensitive_fields()` docstring in `scripts/agent/diagnostic_store.py`
   to state plainly that the sensitive-field set is the union of the hardcoded defaults and
   whatever `sensitive_fields` is configured in `agent.toml`'s `[diagnostics]` table (now
   that this is actually true).
5. Update `docs/05_agent_08_04_configuration-mcp-approval-obs.md`'s DiagnosticsConfig
   section to document `sensitive_fields` alongside `encryption_key` and `retention_days`,
   describing purpose only (additive/union redaction field list), not the concrete default
   values.

## Acceptance criteria
- Setting `sensitive_fields = ["some_field"]` under `[diagnostics]` in `agent.toml` causes
  `_filter_sensitive_fields()` to redact `some_field` (in addition to the hardcoded
  defaults) when its payload value is a list.
- A diagnostic row saved via `DiagnosticStore.save(..., encrypt=True)` with a configured
  `encryption_key` is, when read back via `fetch()`, either (a) returned as decrypted
  plaintext matching the original content (Option A), or (b) clearly and unambiguously
  flagged as encrypted/not-decodable so no caller can mistake ciphertext for plaintext JSON
  (Option B).
- `_filter_sensitive_fields()`'s docstring accurately describes the fixed behavior with no
  discrepancy between documented and actual behavior.
- `docs/05_agent_08_04_configuration-mcp-approval-obs.md` lists `sensitive_fields` for
  `DiagnosticsConfig` without embedding its concrete default value.

  (Option B) — never raw, unflagged ciphertext.
- Existing tests in `tests/agent/test_diagnostic_store.py` and
  `tests/agent/test_config_builders.py` must continue to pass unmodified in behavior
  expectations aside from the additions above.
