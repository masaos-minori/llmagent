# Fix bare-name vs prefixed-name MCP file convention error across docs/04_mcp_06_14, 06_15, and 07

## Priority
High

## Target files
- `docs/04_mcp_06_14_new-tool-registration-procedure.md`
- `docs/04_mcp_06_15_new-mcp-server-addition-checklist.md`
- `docs/04_mcp_07_tool_schema_export_policy.md`

## Background
MCP server implementation files in this codebase follow the `<name>_server.py` /
`<name>_tools.py` naming convention (e.g. `git_server.py`/`git_tools.py`,
`cicd_server.py`/`cicd_tools.py`, `mdq_server.py`/`mdq_tools.py`,
`github_server.py`/`github_tools.py`), confirmed by inspecting
`scripts/mcp_servers/*/` directly. No bare `server.py` or `tools.py` file exists
anywhere under `scripts/mcp_servers/`. The `file/` subdirectory follows the same
prefixed pattern using its sub-role name instead of the directory name
(`read_server.py`/`read_tools.py`, `write_server.py`/`write_tools.py`,
`delete_server.py`/`delete_tools.py`).

## Problem
Three documentation files describe MCP server implementation files using the bare
names `server.py` / `tools.py`, which do not match the actual convention:

- `docs/04_mcp_06_14_new-tool-registration-procedure.md:52` — table row referencing
  "所有元のMCPサーバー(`mcp_servers/<name>/server.py`)".
- `docs/04_mcp_06_15_new-mcp-server-addition-checklist.md:20` — checklist item
  referencing "`scripts/mcp_servers/<name>/server.py`を作成する".
- `docs/04_mcp_07_tool_schema_export_policy.md` — bare names appear repeatedly:
  - Line 18: generic policy statement referencing `mcp_servers/<name>/tools.py`.
  - Line 25: factually wrong concrete reference, "`mcp_servers/github/tools.py`を参照"
    (the actual file is `github_tools.py`).
  - Lines 31-36: the migration-history list gives bare-name paths for git, mdq,
    rag_pipeline, shell, cicd, and web_search (e.g.
    "`scripts/mcp_servers/git/tools.py`, `scripts/mcp_servers/git/server.py`"),
    all of which are wrong — the real files are `git_tools.py`/`git_server.py`, etc.
  - Lines 54-56: further prose references to generic `tools.py`/`server.py` in
    describing per-server behavior.

`docs/04_mcp_07_tool_schema_export_policy.md` additionally contradicts itself: its
"注記" at lines 41-43 states that bare-name files were a historical/transitional
state, already superseded by the `<server>_tools.py`/`<server>_server.py`
convention, and points to a tracking issue (`issues/20260719-193357_risks.md`) for
"現状と対応". That referenced issue file does not exist anywhere in the repo
(verified — not in `issues/` or `issues/done/`), so the note points to a dead
reference. Meanwhile the rest of the same document (lines 18, 25, 31-39, 54-56)
presents bare names as if they were still current/accurate file paths, directly
contradicting its own historical-note framing.

A developer or AI agent following any of these three documents when adding a new
MCP server or tool would create incorrectly named files (`server.py`/`tools.py`
instead of `<name>_server.py`/`<name>_tools.py`), diverging from the established
convention used by every existing MCP server in the codebase.

## Reason for change
This is a confirmed factual error, verified directly against
`scripts/mcp_servers/*/` source, propagated across three documentation files with
one file (`04_mcp_07`) actively self-contradictory. Per `rules/coding.md`
"Documentation notes — Current behavior classification", a discrepancy of this
kind where the doc itself is simply wrong (stale example/reference) falls under
"Documentation fix required": fix the doc directly and remove the stale note once
the surrounding text is accurate, rather than leaving a partial historical caveat
next to inconsistent bare-name text.

## Implementation intent
Rewrite all bare-name (`server.py`/`tools.py`) references in the three target
files to use the actual `<name>_server.py`/`<name>_tools.py` convention (or the
correct sub-role-prefixed name for the `file/` subdirectory cases:
`read_server.py`/`read_tools.py`, `write_server.py`/`write_tools.py`,
`delete_server.py`/`delete_tools.py`). In `04_mcp_07`, resolve the
self-contradiction by removing the outdated bare-name text and its associated
historical/tracking note entirely — do not leave both the "historical" framing
and the bare-name body text coexisting. The dead reference to
`issues/20260719-193357_risks.md` should be removed along with the note (do not
replace it with a new reference unless a valid replacement is identified during
implementation).
