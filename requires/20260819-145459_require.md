## Background

Source issue `issues/20260819_06_issue.md` ("[Low] Replace compatibility tests and align
documentation with the strict contracts") asks for two related follow-up actions once the
strict-contract implementation work in this workstream lands: (1) delete tests that assert
acceptance of removed compatibility formats and replace them with explicit rejection tests
plus current-format end-to-end tests, and (2) update MCP/RAG/DTO/Store-Protocol/database
documentation so it describes only the current strict contracts, with historical entries
clearly marked as unsupported rather than as available aliases or migration paths.

This is a follow-up/cleanup issue for the entire workstream, not a duplicate of any single
implementation requirement. It depends on all of the following, already converted into
requirement documents:

- `requires/20260819-144011_require.md` — MCP Schema 2.0 discovery strict validation
  (`schema_version`, `inputSchema` field naming).
- `requires/20260818-223204_require.md` — `ToolRouteResolver` compatibility-argument removal
  (pre-existing requirement).
- `requires/20260819-144406_require.md` — strict crawl/chunk contracts (mandatory fields,
  `artifact_type` matching).
- `requires/20260819-144649_require.md` — `fetched_at` mandatory end to end, removal of
  timestamp fallback/null-fill behavior.
- `requires/20260819-144952_require.md` — URL-group atomicity and strict RAG database
  constraints (DDL default removal).
- `requires/20260819-145251_require.md` — removal of duplicate document-management code and
  regeneration of RAG runtime data under the strict contracts.

## Problem

- Multiple test modules across MCP routing/discovery and RAG ingestion currently assert
  **acceptance** of formats and behaviors that the dependency requirements will make invalid:
  missing `schema_version` (`test_mcp_tool_discovery.py`), `input_schema`/legacy
  `resource_scope`, missing RAG mandatory fields, timestamp fallback/null-fill, `chunk_index`
  coercion to zero (`test_ingester.py`), and legacy `ToolRouteResolver` constructor inputs
  (`test_route_resolver.py`, plus other files listed under Target files). Left in place, these
  tests force the implementation to keep the removed compatibility behavior just to keep the
  suite green, defeating the strict-contract work.
- Current documentation (`docs/04_mcp_02_01_endpoints-and-transport.md`,
  `docs/90_shared_03_02_runtime_and_execution-tool-executor-and-infrastructure.md`, and
  others in scope) describes `input_schema`, legacy `resource_scope`, and
  backward-compatibility constructor parameters as currently supported, which will mislead
  maintainers and AI implementation agents into treating removed compatibility paths as still
  available.
- No corresponding rejection tests exist yet for the formats being removed, so once the
  dependency requirements are implemented there is no automated guard against a future
  regression silently reintroducing compatibility acceptance.

## Reason for change

Because no legacy data exists and no migration is performed anywhere in this workstream, the
repository must describe and test only the current MCP Schema 2.0 and strict RAG contracts.
Tests that assert acceptance of legacy aliases, missing fields, timestamp fallbacks, or
implicit type coercion actively pin the obsolete behavior in place; documentation that still
describes those paths as supported (rather than as removed history) actively misleads future
implementation work, including AI agents following this repository's own document-workflow
pipeline. This must be done as a distinct follow-up step because it can only be completed
correctly once the strict contracts it tests and documents actually exist in the
implementation.

## Implementation intent

Sequence this work strictly after all six dependency requirements listed in Background are
implemented and merged. Then, for each compatibility-acceptance test identified (per the
issue's Implementation Tasks and Scope lists), delete it and add an explicit rejection test
covering the same input under the new strict validation, plus a current-format end-to-end
test exercising the corresponding success path. For each documentation area in scope, update
the text to describe only the fields, formats, and behaviors the implementation actually
accepts — mandatory keys documented separately from nullable ones, `fetched_at` documented in
its canonical UTC form, `inputSchema`/`resource_scope_kind`/`resource_scope_keys` as the only
supported MCP fields — and remove migration guidance and compatibility-period language.
Historical facts may remain only in `docs/00_governance_05_deprecated-items.md` (or an
equivalent already-designated historical section), phrased so they cannot be read as
currently-supported aliases. Do not preserve any compatibility behavior solely to avoid
rewriting a test or a doc paragraph.
