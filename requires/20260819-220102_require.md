# Record and track the accepted risk of session.sqlite having no incremental migration mechanism

## Priority
Low

## Target files
- `scripts/db/schema_sql.py` (`_SESSION_SCHEMA_TEMPLATE`, lines 85-144; `_WORKFLOW_MIGRATIONS` /
  `apply_workflow_migrations`, lines 252-294 area, for cross-reference only)

## Background
`plans/20260819-183436_plan.md` (Design §5, "Migration policy across the four databases")
verified and documented the current migration-mechanism asymmetry across the four
project databases:

- `workflow.sqlite` — incremental migrations via `_WORKFLOW_MIGRATIONS` (a list of
  `(id, ALTER TABLE ...)` tuples) and `apply_workflow_migrations`
  (`scripts/db/schema_sql.py:252-294`, confirmed present in current source).
- `rag.sqlite` — recreate-only (`CREATE TABLE/VIRTUAL TABLE IF NOT EXISTS`
  `_RAG_SCHEMA_TEMPLATE`), acceptable because its rows are derived and reindexable from
  source documents.
- `eventbus.sqlite` — recreate-only; out of scope to change (eventbus implementation
  changes are prohibited by AGENTS.md Global Rule 8).
- `session.sqlite` — recreate-only (`_SESSION_SCHEMA_TEMPLATE`,
  `scripts/db/schema_sql.py:85-144`, confirmed present in current source, no
  `apply_*_migrations`-style function exists for it). Its tables (`sessions`, `messages`,
  `memories`, `memory_links`, `session_diagnostics`) hold conversation history and
  semantic/episodic memory — data that is not trivially re-derivable the way a RAG index
  is by re-crawling source documents.

That plan's Design §5 explicitly kept this asymmetry as-is ("intentionally kept, not
extended") and its Phase 1 implementation step calls for adding a "Migration policy"
docstring section to `scripts/db/schema_sql.py` recording the general per-database
policy. Verified against current source: that docstring section does not exist yet
(`scripts/db/schema_sql.py`'s module docstring, lines 1-16, has no such section as of
this writing), because the plan has not yet progressed through
`prompts/02_plan-to-implementation-procedure.md` / `prompts/03_implementation.md`.

That same plan's Risks section, however, explicitly flagged that the general policy
statement does not fully resolve `session.sqlite`'s specific situation — because its
data is not reindexable like RAG's — and filed `issues/20260819-183436_risks.md` for a
maintainer decision on whether `session.sqlite` should be reclassified as needing
incremental migration ahead of any concrete schema-change need. That issue offered three
options: (1) proactively extend the `workflow.sqlite`-style incremental migration
mechanism to `session.sqlite` now, (2) explicitly document the recreate-only gap and its
consequences, or (3) defer the decision until a concrete `session.sqlite` schema change
is actually proposed.

## Problem
There is currently no `apply_*_migrations`-style incremental migration path for
`session.sqlite`, unlike `workflow.sqlite`. If a future change needs to add or alter a
column on `sessions`, `messages`, `memories`, `memory_links`, or `session_diagnostics`,
the only mechanism available today (`CREATE TABLE IF NOT EXISTS`) does not alter existing
tables at all. A genuine schema change would require either a manual one-off migration
script written at that time, or accepting data loss on recreate — and neither is
currently documented as the intended procedure specifically for `session.sqlite`
(as distinct from the general, already-documented RAG/session/workflow asymmetry).

This gap was identified as a real risk, not a speculative one, but resolving it by
proactively building a migration mechanism today would itself be speculative work: no
concrete `session.sqlite` schema change is currently pending, and
`skills/require-to-plan/workflow.md` Step 9 directs against including steps not required
by a stated, current goal.

## Reason for change
Leaving this risk unrecorded as a distinct, trackable item (separate from the general
migration-policy note that `plans/20260819-183436_plan.md` will add) risks the gap being
silently forgotten until a `session.sqlite` schema change is actually proposed under time
pressure, at which point the migration-vs-recreate-vs-data-loss decision would have to be
made ad hoc. Recording the decision now — to defer, not to ignore — ensures the next
concrete `session.sqlite` schema-change proposal is required to explicitly re-visit this
question rather than defaulting silently to a lossy recreate.

## Implementation intent
Adopt resolution path 3 from `issues/20260819-183436_risks.md`: defer the
migration-mechanism-vs-recreate decision for `session.sqlite` until the first concrete
`session.sqlite` schema change is actually proposed, and make that decision explicitly as
part of that future requirement/plan cycle — rather than building an
`apply_workflow_migrations`-style mechanism for `session.sqlite` speculatively today.

This requirement is document-only: it does not mandate implementing an incremental
migration mechanism, and does not mandate a specific choice among options 1-3 for the
eventual schema change — it only mandates that the deferred risk is written down in a
durable, discoverable place (source code) so a future schema-change requirement is
prompted to address it rather than silently repeating the plan's general RAG/session
policy note without considering `session.sqlite`'s non-reindexable data.

Coordinate with `plans/20260819-183436_plan.md` Phase 1 (the "Migration policy"
docstring section to be added to `scripts/db/schema_sql.py`'s module docstring): whichever
lands first should add the general per-database policy note; this requirement's
implementation adds a `session.sqlite`-specific follow-up note next to
`_SESSION_SCHEMA_TEMPLATE` referencing that general note and the deferred decision,
without duplicating the general policy text.

## Implementation instructions
1. Verify at implementation time whether `plans/20260819-183436_plan.md` Phase 1's
   "Migration policy" docstring section has already been added to
   `scripts/db/schema_sql.py`'s module docstring. If it has, reference it by name in the
   new note instead of restating it. If it has not, this requirement's implementation
   should still proceed independently — do not block on that plan landing first.
2. Add a short comment/docstring note directly above `_SESSION_SCHEMA_TEMPLATE`
   (`scripts/db/schema_sql.py`, currently starting at line 85) stating:
   - `session.sqlite` currently uses recreate-only DDL (`CREATE TABLE IF NOT EXISTS`),
     with no incremental migration mechanism (unlike `workflow.sqlite`'s
     `_WORKFLOW_MIGRATIONS` / `apply_workflow_migrations`).
   - Unlike `rag.sqlite`, `session.sqlite`'s data (conversation history,
     semantic/episodic memory) is not trivially re-derivable from an external source.
   - This gap is a known, accepted risk (see `issues/done/20260819-183436_risks.md` and
     this requirement) — the migration-mechanism-vs-recreate decision is deliberately
     deferred until a concrete `session.sqlite` schema change is proposed, at which point
     that proposal's requirement/plan must explicitly address how existing conversation
     and memory data is preserved (either by adding an incremental migration mechanism at
     that time, or by an explicit export/reimport step) rather than silently defaulting to
     a lossy recreate.
3. Do not add a migration mechanism, `apply_session_migrations` function, or any schema
   version tracking table for `session.sqlite` as part of this requirement — that would be
   speculative work not required by any currently pending schema change.
4. Do not modify `_SESSION_SCHEMA_TEMPLATE`'s DDL content itself, and do not modify
   `_WORKFLOW_MIGRATIONS` or `apply_workflow_migrations`.
