## Background
Issue `issues/20260818_07_issue.md` requested a broad reconciliation of specifications, runtime references, and issue state across Overview, Deployment, RAG, Agent, Shared/DB, and operations documents. Verification against the current repository shows the documentation set already has a substantial governance layer (`docs/00_governance_01..08`) defining canonical-source rules, a Known-Issues template, a deprecated-items registry, and a Needs-Confirmation inventory process, plus CI workflows (`.github/workflows/{overview,deployment,agent,mcp,governance,rag}-docs-consistency.yml`) and tooling (`tools/check_docs_consistency.py`, `tools/audit_docs.py`, `tools/check_doc_quality.py`). Several of the issue's original concerns are therefore already resolved in practice:
- CLI deprecated-command references (`/note`, `/ingest`, `/debug audit`, `/db *`) are documented with explicit replacements in `docs/05_agent_07_07_cli-and-commands-migration-notes.md` and `docs/00_governance_05_deprecated-items.md`.
- The three-vs-four-database ambiguity does not exist in the current docs: `docs/90_shared_04_01_db_architecture_and_schema-overview-and-config.md:35` states plainly "Four DB files exist: rag.sqlite, session.sqlite, workflow.sqlite, eventbus.sqlite" with per-DB config keys, tables, and rationale for separation; `docs/02_deployment.md` also lists `eventbus.sqlite` with path, config key, and backup applicability ("Yes").

However, targeted checks found that a subset of the issue's concerns is still concretely present in the current documentation and is not covered by existing CI/tooling.

## Problem
1. **Model/GGUF/embedding-dimension references conflict across documents for what is claimed to be the same active deployment:**
   - `docs/01_overview-files-01-build.md:31-32` lists the active LLM as `Qwen3.6-Instruct-Q4_K_M.gguf` and the active embedding model as `multilingual-E5-small.gguf` (384 dims).
   - `docs/02_deployment.md:47-49` lists the embedding model as `multilingual-e5-small-Q8_0.gguf` and two different LLMs, `gemma-4-e4b-it-Q4_K_M.gguf` and `Qwopus3.6-35B-A3B-v1-MTP-Q4_K_M.gguf`.
   - `docs/03_rag_05_1-configuration-reference.md:68` ties `embedding_dims=384` to model name `all-MiniLM-L6-v2`, a third distinct embedding-model name for the same dimension slot.
   - There is no single canonical document identified as authoritative for the active model filenames, and `tools/check_docs_consistency.py` / `tools/_docs_consistency_lib.py` contain no check for GGUF filenames, model names, or embedding dimension consistency (confirmed via source grep — zero matches for "gguf", "model", or "embedding_dims").

2. **Needs-Confirmation inventory has no active/resolved separation despite the governance doc defining one.** `docs/00_governance_07_needs-confirmation-inventory.md` defines an "Inventory Items" section intended to hold active items, but all 17 entries (NC-001 through NC-017) currently carry `Status: resolved`. None have been moved to an archive; the document mixes fully-resolved historical entries with the section meant to track active unconfirmed items, contrary to the issue's task of separating active Needs-Confirmation items from resolved history.

3. **Duplicate metadata field present in the inventory itself.** Entry NC-005 in `docs/00_governance_07_needs-confirmation-inventory.md` (lines ~130-131) contains two `**Last Reviewed**` fields with different, conflicting dates (`2026-07-29` and `2026-07-22`), which is exactly the "duplicate issue metadata fields" defect category called out in the source issue.

4. **Per-area Known Issues documents remain unmigrated to the common template.** `docs/00_governance_08_known-issues-migration-plan.md` is explicitly scoped as a plan only ("Excluded: Actually modifying any existing Known Issues documents during this planning phase"). The five target documents (`03_rag_90`, `04_mcp_90`, `05_agent_90`, `06_eventbus_90`, `90_shared_90`) still use divergent, area-specific formats (Japanese vs. English headers, table-based vs. prose, inconsistent severity/status fields) as documented in the plan's own "Current Format Summary" section. The actual migration described by the plan has not been executed.

## Reason for change
- Conflicting model/GGUF filenames across authoritative-looking documents risk an operator loading the wrong LLM or embedding model, or misconfiguring `model-path` during deployment, with no automated check to catch the mismatch before or after a docs change.
- An unarchived, all-resolved Needs-Confirmation inventory makes it hard for a reader (human or AI) to tell at a glance whether any item is still open, defeating the purpose of the inventory as an actionable tracker.
- A duplicated metadata field with two different dates is a direct data-integrity defect in a document whose stated purpose is trustworthy tracking; it also demonstrates that no validation currently enforces the single-value-per-field rule implied by the inventory's own field definitions.
- Known Issues documents remaining unmigrated after a formal migration plan was written and merged represents unfinished, stalled governance work; leaving five areas in divergent formats undermines the cross-area consistency the plan itself sets out to achieve.

## Implementation intent
- Establish one canonical location (e.g. `docs/02_deployment.md` or a new single "active models" table referenced by the others) as the single source of truth for active LLM/embedding model filenames and dimensions; convert all other mentions (`01_overview-files-01-build.md`, `03_rag_05_1-configuration-reference.md`) into either an identical restatement or an explicit cross-reference/link to the canonical entry, removing conflicting filenames.
- Add a lightweight consistency check (extending `tools/check_docs_consistency.py` / `tools/_docs_consistency_lib.py`) that extracts `.gguf` filenames and `embedding_dims` values referenced across docs and fails when the same logical model slot (LLM vs. embedding) resolves to different filenames/dimensions across documents.
- Restructure `docs/00_governance_07_needs-confirmation-inventory.md` to split resolved entries into a clearly separated archive section (or a separate archive document linked from it), keeping only genuinely open/deferred items in the active "Inventory Items" section, while preserving every original NC ID, question, evidence, and resolution text verbatim.
- Fix the NC-005 duplicate `Last Reviewed` field by keeping a single, correct value (use the most recent/most specific date, e.g. `2026-07-29`, and remove the stale duplicate) and add note about the correction only if the project's evidence-label convention requires it.
- Execute the migration described in `docs/00_governance_08_known-issues-migration-plan.md` for at least the first area in its "Suggested Migration Order" (Agent), converting `docs/05_agent_90_inconsistencies_and_known_issues.md` to the common template from `docs/00_governance_04_known-issues-template.md` while preserving all existing entry IDs and content; treat the remaining four areas as follow-up work rather than doing all of them in one pass, per the migration plan's own "migrate one area at a time" policy.

## Implementation instructions
1. Read the three model-reference documents (`01_overview-files-01-build.md`, `02_deployment.md`, `03_rag_05_1-configuration-reference.md`) in full and determine, from the actual deployment scripts under `deploy/` and configuration in `config/`, which model filenames are truly current; do not assume either doc is correct without checking `deploy/*.sh` and `config/*.toml`.

4. In `docs/00_governance_07_needs-confirmation-inventory.md`, add an "Archived (Resolved) Items" section (or a separate `docs/00_governance_07b_needs-confirmation-archive.md` linked from the main doc — choose whichever keeps the existing doc's structure simplest) and move all `Status: resolved` entries there verbatim, leaving the "Inventory Items" section containing only entries that are `open`, `investigating`, or `deferred` (currently zero, since all 17 are resolved — state this explicitly if the active section ends up empty rather than leaving it ambiguous).
5. Fix NC-005's duplicate `Last Reviewed` line, keeping one authoritative date.
6. Pick the Agent area (`docs/05_agent_90_inconsistencies_and_known_issues.md`) as the first per-area Known Issues migration target; rewrite its entries using the 17-field template from `docs/00_governance_04_known-issues-template.md`, preserving every original ID, and add a migration note (date + "migrated from prior format") per entry as required by `docs/00_governance_08_known-issues-migration-plan.md`'s Migration Policy.
