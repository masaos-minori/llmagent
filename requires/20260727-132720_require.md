# Fix AgentREPL.run() finally block terminating successfully-started MCP subprocesses

## Priority

High

## Target Files

- `scripts/agent/repl.py:736-752` — `AgentREPL.run()`'s `finally` block unconditionally terminates spawned subprocesses, even when `startup.run()` completed successfully
- `scripts/agent/startup.py:62-89` — `StartupOrchestrator.run()`, the source of the `_spawned_subprocesses` data the `finally` block consumes (see also `requires/20260727-132138_require.md`, which fixes the currently-empty tracking of this list)

## Background

`AgentREPL.run()` wraps the call to `StartupOrchestrator.run()` in a `try`/`except`/`finally`:

```python
startup = StartupOrchestrator(self._ctx, self._view)
_spawned_subprocesses: list[subprocess.Popen] = []
try:
    self._cmds, self._orchestrator, _spawned_subprocesses = await startup.run()
except Exception as e:
    self._view.write_fatal(f"Startup failed: {e}")
    raise
finally:
    # Terminate any subprocesses started during partial startup
    # Check both local variable (success path) and instance variable (exception path)
    all_procs = _spawned_subprocesses
    if hasattr(startup, "_spawned_subprocesses"):
        all_procs = list(all_procs) + list(startup._spawned_subprocesses)
    for proc in all_procs:
        if proc.poll() is None:
            proc.terminate()
    await self._close_resources()
```

The comment states the intent is to "terminate any subprocesses started during **partial**
startup" — i.e. cleanup only when startup fails partway through. However, a Python
`finally` block always executes, regardless of whether the `try` block raised or returned
normally. There is currently a separate, already-documented bug (`requires/20260727-132138_require.md`,
sourced from `issues/20260727_02_issue.md`) where `StartupOrchestrator.run()` always returns
an empty list on the success path (`scripts/agent/startup.py:89`,
`return self._cmds, self._orchestrator, []  # empty list on success`) and never populates
`self._spawned_subprocesses` with real processes on either path. Because of that bug,
`all_procs` in `repl.py`'s `finally` block is always empty today, so this design flaw has no
observable effect yet.

## Problem

The `finally` block's termination loop is not actually conditioned on startup having failed
— it runs identically whether `try` succeeded or raised. Today this is masked only because
the sibling bug keeps `all_procs` empty in both cases. If `requires/20260727-132138_require.md`
is implemented in isolation — making `StartupOrchestrator.run()` correctly return the real
spawned-process list on the success path — then, immediately after a **fully successful**
startup, `AgentREPL.run()`'s `finally` block will iterate over the just-spawned MCP HTTP
subprocesses and call `proc.terminate()` on each one still running. This kills every
successfully started MCP HTTP subprocess server right after the agent finishes starting up,
breaking all HTTP-subprocess-mode MCP tools for the rest of the session.

This is a latent design defect masked by a currently-tracked bug: fixing one without the
other produces a new, more severe regression (total loss of MCP subprocess functionality on
every successful startup) instead of fixing anything.

## Reason for Change

The two issues (`issues/20260727_02_issue.md` / `requires/20260727-132138_require.md`, and
this one) must be resolved together, or resolving the tracking bug alone will silently break
every session that uses HTTP-subprocess-mode MCP servers. The `finally` block needs to
distinguish "startup succeeded" from "startup failed" and only terminate spawned subprocesses
in the failure case, matching the behavior the existing comment already describes but the
code does not implement.

## Implementation Intent

Restrict subprocess termination in `AgentREPL.run()` to the startup-failure path only, so
that:

- On successful startup, spawned MCP subprocesses are left running and are not touched by
  this cleanup logic at all.
- On startup failure (the `except` branch), the existing termination behavior — terminating
  any subprocess from either `_spawned_subprocesses` (return value) or
  `startup._spawned_subprocesses` (instance attribute) that is still running — is preserved
  exactly as today, once `requires/20260727-132138_require.md` makes that data accurate.
- `self._close_resources()` continues to run on every path (success and failure), since it is
  unrelated cleanup and not part of this defect.

## Implementation Instructions

1. In `scripts/agent/repl.py`, move the subprocess-termination loop out of `finally` and into
   the `except` block (or otherwise gate it on a flag set only when an exception was caught),
   for example:

   ```python
   startup = StartupOrchestrator(self._ctx, self._view)
   _spawned_subprocesses: list[subprocess.Popen] = []
   try:
       self._cmds, self._orchestrator, _spawned_subprocesses = await startup.run()
   except Exception as e:
       self._view.write_fatal(f"Startup failed: {e}")
       # Terminate any subprocesses started during partial startup
       all_procs = _spawned_subprocesses
       if hasattr(startup, "_spawned_subprocesses"):
           all_procs = list(all_procs) + list(startup._spawned_subprocesses)
       for proc in all_procs:
           if proc.poll() is None:
               proc.terminate()
       raise
   finally:
       await self._close_resources()
   ```
2. Keep the dedup/union logic between `_spawned_subprocesses` (local variable, success-path
   return value) and `startup._spawned_subprocesses` (instance attribute, exception-path
   state) unchanged — only the placement (except-only vs. always-on) is being fixed.
3. Do not change `StartupOrchestrator.run()` or `_start_servers()` in this change; the data
   plumbing fix for `_spawned_subprocesses` is scoped to
   `requires/20260727-132138_require.md` and should land together with (or before) this
   change, since this fix alone has no observable effect until that data is populated, and
   that fix alone (without this one) causes the regression described above.
4. Update the stale comment ("Terminate any subprocesses started during partial startup") if
   needed so it accurately reflects that this code now only runs on the failure path.
5. Confirm no other exit path from `AgentREPL.run()` between `startup.run()` and the end of
   the method needs equivalent subprocess cleanup on success (i.e. that leaving spawned
   subprocesses running after a successful startup is indeed the correct, intended
   behavior — subprocesses are expected to live for the duration of the session and be
   cleaned up later via normal shutdown/`lifecycle.shutdown_all()`, not by this
   startup-specific fallback).

## Acceptance Criteria

- [ ] When `startup.run()` completes successfully, no subprocess in the returned
      `_spawned_subprocesses` list (nor in `startup._spawned_subprocesses`) is terminated by
      `AgentREPL.run()`.
- [ ] When `startup.run()` raises, every still-running subprocess present in either
      `_spawned_subprocesses` or `startup._spawned_subprocesses` is terminated, exactly as
      before this change.
- [ ] `self._close_resources()` is still awaited on both the success and failure paths.
- [ ] This change is landed together with (or after) the fix in
      `requires/20260727-132138_require.md`, so that the two are never applied independently
      in a way that reintroduces either bug.

## Tests

- Add a unit/integration test for `AgentREPL.run()` (or the equivalent startup call site)
  that: stubs `StartupOrchestrator.run()` to succeed and return a list containing a live fake
  `subprocess.Popen`-like object (`poll()` returns `None`), then asserts `.terminate()` is
  **not** called on it after `run()` returns/proceeds to the REPL loop.
- Add a companion test that stubs `StartupOrchestrator.run()` to raise after populating
  `startup._spawned_subprocesses` with a live fake process, and asserts `.terminate()` **is**
  called on it in that case (regression test preserving current failure-path behavior).
- Run both this test and the tests added for `requires/20260727-132138_require.md` together
  to confirm the combined behavior: successful startup keeps subprocesses alive, and failed
  startup still cleans them up.
