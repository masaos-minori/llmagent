# Deprecate or consolidate `LlmTransportErrorHandler.resolve_retryable` (dead code, duplicated classification logic)

## Priority
Medium

## Target files
- `scripts/shared/llm_transport_errors.py` (`LlmTransportErrorHandler.resolve_retryable`)
- `scripts/shared/llm_reconnect.py` (`LlmReconnectHandler.resolve_retryable`, `LlmReconnectHandler._evaluate_stream_error`)
- `tests/shared/test_llm_transport_errors.py`
- `tests/shared/test_llm_reconnect.py`

## Background
`scripts/shared/llm_transport_errors.py` defines `LlmTransportErrorHandler`, a static-method
class that translates HTTP/stream failures into `LLMTransportError`. Its
`raise_http_status_error` and `translate_stream_error` methods are actively called from
`scripts/shared/llm_sse_stream.py` (`LlmSseStreamHandler.stream_once`, lines 125 and 140). A
third method, `resolve_retryable` (lines 60-74), classifies whether an `LLMTransportError`
should be retried based on `e.kind` (`HEARTBEAT_TIMEOUT` / `MALFORMED_SSE_FRAME` / fallback to
`e.retryable`) and threads a `heartbeat_timeout_counter` through its return tuple
`(effective_retryable, updated_heartbeat_timeout_counter)`.

`scripts/shared/llm_reconnect.py` (`LlmReconnectHandler`) independently implements the same
three-branch classification rule twice, split across two methods:
- `resolve_retryable` (lines 24-35) — bare-`bool` return, no counter.
- `_evaluate_stream_error` (lines 37-64) — calls `LlmReconnectHandler.resolve_retryable`
  internally (line 55), then separately increments `heartbeat_timeout_count` and mutates
  `e.stat_heartbeat_timeouts` when `e.kind == "HEARTBEAT_TIMEOUT"` (lines 60-62), and folds in
  an additional `has_partial` check (line 63) before deciding `should_retry`.
  `_evaluate_stream_error` is the one actually called from `LlmReconnectHandler.stream` (line
  115), the production reconnect loop.

## Problem
Verified against current source (2026-08-13):
- `LlmTransportErrorHandler.resolve_retryable` has zero callers anywhere in `scripts/`
  (`rg "LlmTransportErrorHandler" scripts/` shows only the class definition and the two other
  methods being called from `llm_sse_stream.py`; `resolve_retryable` itself is never invoked
  outside `tests/shared/test_llm_transport_errors.py`). It is dead production code, exercised
  only by its own dedicated unit tests (`TestResolveRetryable` in that test file).
- The three-branch classification logic it implements
  (`HEARTBEAT_TIMEOUT` -> flag / `MALFORMED_SSE_FRAME` -> flag / fallback -> `e.retryable`) is
  duplicated verbatim in `LlmReconnectHandler.resolve_retryable`
  (`scripts/shared/llm_reconnect.py:24-35`), which *is* live production code, reached via
  `_evaluate_stream_error` from the active reconnect loop in `LlmReconnectHandler.stream`.
- The one structural difference between the two `resolve_retryable` implementations is exactly
  as the source issue described: `LlmTransportErrorHandler`'s version threads a
  `heartbeat_timeout_counter` through its return value and increments it inline on
  `HEARTBEAT_TIMEOUT`; `LlmReconnectHandler`'s version returns a bare `bool`, and its caller
  (`_evaluate_stream_error`) increments the counter and mutates
  `e.stat_heartbeat_timeouts` separately.
- One correction to the source issue: it described the duplicate as living inside
  `_evaluate_stream_error` itself. In current source, the duplicate three-branch rule has
  since been factored out into `LlmReconnectHandler.resolve_retryable`, a separate method that
  `_evaluate_stream_error` calls. The underlying duplication (two independently-defined
  copies of the same classification rule, one dead, one live) is unchanged and still applies —
  only the exact line locus shifted.

## Reason for change
Keeping dead code around (`LlmTransportErrorHandler.resolve_retryable`) with its own
maintained test suite creates false signal about what is actually exercised in production and
is extra surface a future editor must reason about when changing retry-classification
semantics. Having the same three-branch rule live independently in two files is a duplication
risk: a future change to the retry policy (e.g. adding a new `LLMErrorKind`) could be applied
to one copy and silently missed in the other, producing inconsistent retry behavior between
whichever call path uses which copy.

## Implementation intent
Treat this as two independently schedulable sub-tasks, per the source issue's own risk
classification — do not require both to land in the same change:

1. **Dead-code removal path (lower risk).** Confirm `LlmTransportErrorHandler.resolve_retryable`
   still has zero callers in `scripts/` at implementation time (re-run the `rg` check below).
   Add a `warnings.warn(..., DeprecationWarning, stacklevel=2)` at the top of the method body
   for a grace period, per this project's "retain deprecated aliases" convention
   (`skills/python-refactoring/SKILL.md`), before outright removal in a later change. Do not
   remove the method and its tests in the same change that adds the deprecation warning unless
   a maintainer explicitly confirms an immediate removal is acceptable for this genuinely-dead
   method.
2. **Cross-file consolidation path (higher risk — needs explicit sign-off before
   implementation).** Design one shared three-branch classification helper (its natural home is
   `LlmTransportErrorHandler.resolve_retryable`'s counter-threading signature, since
   `LlmReconnectHandler._evaluate_stream_error` already needs the counter value for
   `e.stat_heartbeat_timeouts`) that both `LlmReconnectHandler.resolve_retryable` and any
   future caller can use without re-implementing the branch logic. Update
   `LlmReconnectHandler._evaluate_stream_error` to call the shared helper instead of
   `LlmReconnectHandler.resolve_retryable`, reconciling the counter-threading difference so that
   `_evaluate_stream_error`'s existing behavior (increment counter, mutate
   `e.stat_heartbeat_timeouts`, combine with the `has_partial` check) is preserved exactly.

Do not change `LlmReconnectHandler.stream`'s reconnect/backoff/heartbeat semantics as an
incidental side effect of either sub-task.

## Implementation instructions
1. Before making any change, re-run `rg "resolve_retryable" scripts/ tests/` and
   `rg "LlmTransportErrorHandler" scripts/` across the whole repo to reconfirm the zero-caller
   claim for `LlmTransportErrorHandler.resolve_retryable`; do not assume this requirement
   document's snapshot is still accurate.
2. For sub-task 1: add the `DeprecationWarning` to
   `LlmTransportErrorHandler.resolve_retryable` in `scripts/shared/llm_transport_errors.py`,
   referencing the intended replacement in the warning message. Keep
   `tests/shared/test_llm_transport_errors.py`'s `TestResolveRetryable` tests passing (wrap
   assertions with `pytest.warns(DeprecationWarning)` as needed) — do not delete this test
   class in the same change unless the method itself is being removed.
3. For sub-task 2 (separate change, requires sign-off first): extract the shared three-branch
   helper, point `LlmReconnectHandler.resolve_retryable` (or `_evaluate_stream_error` directly)
   at it, and add/adjust characterization tests so both
   `tests/shared/test_llm_transport_errors.py` and `tests/shared/test_llm_reconnect.py` continue
   to assert the same externally-observable outcomes as today for every `LLMErrorKind` /
   flag / counter combination currently covered.
4. Do not touch `LlmSseStreamHandler.stream_once`'s calls to `raise_http_status_error` /
   `translate_stream_error`, or any heartbeat/retry constant, in either sub-task.

## Acceptance criteria
- No behavior change to `LlmReconnectHandler.stream`'s existing retry/heartbeat semantics.
- Sub-task 1: `LlmTransportErrorHandler.resolve_retryable` either emits a `DeprecationWarning`
  (grace-period state) or is removed entirely with its dedicated tests removed in the same
  change — not left silently as-is once this requirement is implemented.
- Sub-task 2 (if undertaken): the three-branch classification rule exists in exactly one place
  in source, with both `LlmTransportErrorHandler`-side and `LlmReconnectHandler`-side behavior
  unchanged from a caller's perspective (identical retry decisions and counter values for every
  input combination exercised by the existing tests).
- `tests/shared/test_llm_reconnect.py` and `tests/shared/test_llm_transport_errors.py` pass
  (adjusted for the deprecation warning / consolidation as applicable) with unchanged outcomes
  for every case not directly affected by the change.
