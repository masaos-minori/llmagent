# Fix HttpTransport retrying non-retryable HTTP statuses and losing HTTPStatusError context

## Priority
High

## Target files
- `scripts/shared/http_transport.py` (`HttpTransport.call`)
- `tests/shared/test_tool_executor.py`
- `tests/shared/test_tool_executor_routing.py`

## Background
`HttpTransport.call()` posts to `/v1/call_tool` on an MCP HTTP server. It maintains a
retryable-status set `_RETRYABLE_STATUS = frozenset({429, 502, 503, 504})` intended to
distinguish transient failures (worth retrying) from non-retryable failures (should fail
fast). A similar retryable-status pattern already exists in `scripts/shared/llm_retry.py`
via `_TRANSIENT_HTTP_STATUS_CODES = frozenset({429, 503})` and `_is_transient_http_error()`.

## Problem
Verified against current source (2026-08-13): in `HttpTransport.call()`
(`scripts/shared/http_transport.py`, lines ~106-146), the retry loop checks
`resp.status_code in self._RETRYABLE_STATUS` only in the success path *before*
`resp.raise_for_status()` is called. When `raise_for_status()` raises `httpx.HTTPStatusError`
(for any non-2xx status, including ones outside `_RETRYABLE_STATUS` such as 400/404/500),
the `except httpx.HTTPStatusError as e:` handler (lines 133-139) does not check the status
code at all — it always sets `last_exc` and falls through to the next loop iteration,
retrying the request up to `_RETRY_MAX` (3) times regardless of whether the status was
retryable.

After the loop exhausts all attempts, the `for...else` clause (lines 142-145) raises a
generic `TransportError` with the message `"[Retry exhausted] tool=... url=... after N
attempts"`, which drops the actual `HTTPStatusError` type and status code that caused the
failure.

Confirmed by running both tests at HEAD:
```
uv run pytest tests/shared/test_tool_executor.py::TestHttpTransportRetry::test_non_retryable_http_status_not_retried tests/shared/test_tool_executor_routing.py::TestHttpTransportErrors::test_http_status_error_raises_transport_error -v
```
Both FAIL:
- `test_non_retryable_http_status_not_retried`: a 500 response causes `call_count == 3`
  (asserts `== 1`) — the request is retried 3 times despite 500 not being in
  `_RETRYABLE_STATUS`.
- `test_http_status_error_raises_transport_error`: the raised message is
  `"[Retry exhausted] tool=my_tool url=http://127.0.0.1:8000 after 3 attempts"`, which does
  not contain `"HTTPStatusError"` (asserted via `assert "HTTPStatusError" in
  str(exc_info.value)`).

This is a correctness bug, not an accepted specification: the code's own
`_RETRYABLE_STATUS` set already documents the intended retry policy, but the
`HTTPStatusError` exception path ignores it entirely.

## Reason for change
Callers depending on `tool_executor.py` / `tool_transport_invoker.py` retry semantics
currently retry requests that should fail fast (e.g. 400 Bad Request), wasting time/attempts
and potentially causing unwanted side effects on non-idempotent calls. Additionally, error
messages surfaced to logs/audits for HTTP failures lose the actual failure reason (status
code, exception type), making incident diagnosis harder.

## Implementation intent
Classify `httpx.HTTPStatusError` by `e.response.status_code` against `_RETRYABLE_STATUS`
inside the `except httpx.HTTPStatusError` handler:
- If the status code is in `_RETRYABLE_STATUS`, keep the existing retry behavior (loop to
  next attempt, same backoff/attempt-count semantics as today — do not touch the backoff
  formula).
- If the status code is NOT in `_RETRYABLE_STATUS`, raise a `TransportError` immediately
  (fail fast), without consuming further retry attempts.

Ensure the final exception message — for both the "non-retryable, immediate" path and the
"retry exhausted" path — includes the originating exception type (`HTTPStatusError`) and/or
status code, so context is not lost. The existing `_transport_error()` helper already builds
messages with a `[Prefix]` tag; reuse or extend it to raise directly for the non-retryable
case and to carry the last `HTTPStatusError`'s detail into the retry-exhausted message rather
than the current generic `"[Retry exhausted]..."` string.

Do not restructure the overall retry loop's control flow, backoff timing, or attempt-count
logic beyond what is needed to add this status-code branch. Do not change
`tool_executor.py` / `tool_transport_invoker.py` call sites unless their behavior actually
depends on the exact old message format (verify before touching).

## Implementation instructions
1. Read `scripts/shared/http_transport.py::HttpTransport.call` (and `_transport_error`) and
   the two failing tests in full before changing anything.
2. In the `except httpx.HTTPStatusError as e:` block (currently lines 133-139), branch on
   `e.response.status_code in self._RETRYABLE_STATUS`:
   - Retryable: keep current behavior (set `last_exc` via `_transport_error(...,
     break_flag=False, health_check=False)` and continue the loop).
   - Non-retryable: call `_transport_error(..., break_flag=True, health_check=False)` (or
     equivalent) to raise immediately, short-circuiting further attempts.
3. Update the `for...else` "retry exhausted" branch (currently lines 142-145) so its message
   incorporates the last caught exception's context (e.g. include `last_exc`'s message, or
   the last `HTTPStatusError`'s status code/type) instead of the current bare
   `"[Retry exhausted] tool=... url=... after N attempts"` string. Preserve the
   `TransportError` type and the general "retry exhausted after N attempts" framing — just
   stop discarding the underlying cause.
4. Keep `_RETRYABLE_STATUS = frozenset({429, 502, 503, 504})` as-is (do not change which
   statuses are retryable) unless investigation shows the test suite expects a different
   set — check for any other tests asserting specific status codes as retryable/non-retryable
   before finalizing the set.
5. Run the full targeted test file pair before and after the change to confirm only the
   two named tests flip from fail to pass, and no other test in those files regresses:
   `uv run pytest tests/shared/test_tool_executor.py tests/shared/test_tool_executor_routing.py -v`
