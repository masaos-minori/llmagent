# Fix failure-mode table symptom-column log-string mismatch in docs/02_deployment-part2.md

## Priority
Medium

## Target files
- `docs/02_deployment-part2.md` (§3.3 失敗モード table, lines ~54-60)

## Background
`docs/02_deployment-part2.md` §3.3 contains a "失敗モード" (failure mode) table whose 症状 (symptom)
column lists `[FATAL] ...` strings styled as inline code, in a table format that reads as
grep-able, exact log output. Operators facing a deployment failure would reasonably copy these
strings verbatim into `grep` against deployment logs.

## Problem
Verification against current source confirms 4 of the 5 table rows do not match the actual log
strings emitted by the deploy scripts. Re-verified via `grep -n "FATAL" deploy/deploy.sh
deploy/init_db.sh deploy/setup_services.sh` on 2026-08-02:

| Table row (current, §3.3) | Actual log string (verified in source) | Source location |
|---|---|---|
| `` `[FATAL] Missing required workflow definition` `` | `[FATAL] Missing required workflow definition: config/workflows/default.json` | `deploy/deploy.sh:18` |
| `` `[FATAL] Invalid workflow definition` `` | `[FATAL] Workflow definition failed validation; aborting deployment.` | `deploy/deploy.sh:26` |
| `` `[FATAL] Checksum does not match source` `` | `[FATAL] Deployed workflow definition checksum does not match source; deployment corrupted.` | `deploy/deploy.sh:110` |
| `` `[FATAL] Schema is missing or incomplete` `` | `[FATAL] Workflow database schema is missing or incomplete.` | `deploy/init_db.sh:50`, `deploy/setup_services.sh:35`, `deploy/setup_services.sh:50` |
| `` `[FATAL] Schema version mismatch` `` | `[FATAL] Workflow schema version mismatch: expected ${EXPECTED_SCHEMA_VERSION}, found ${ACTUAL_SCHEMA_VERSION:-<none>}.` | `deploy/setup_services.sh:62` |

Row 1 (`Missing required workflow definition`) is a true prefix/substring of its actual log line,
so it is grep-safe as-is and does not need changing. Rows 2-5 are not substrings of their actual
log lines (different wording and/or different capitalization mid-sentence), so a literal `grep -F`
for the table's current text against deployment logs returns zero matches for all four.

Note for context: `setup_services.sh` also emits two additional `[FATAL]` lines not currently
represented in the table at all —
`[FATAL] Missing required workflow definition: ${WORKFLOW_JSON}` (line 23) and
`[FATAL] Deployed workflow definition failed validation: ${WORKFLOW_JSON}` (line 29) — and
`deploy.sh` emits `[FATAL] Deployed workflow definition missing after copy: ${DEPLOY_CONFIG}/workflows/default.json`
(line 116). Adding rows for these is optional/out of scope per the source issue; only fixing the
existing 4 mismatched rows is required.

## Reason for change
This is a confirmed factual error with direct operational impact: an operator grepping logs for
the table's exact strings during an incident gets zero matches for 4 of 5 failure modes, delaying
root-cause identification exactly when speed matters most. The table's code-block/inline-code
styling implies these are literal, exact strings, which is misleading in its current state.

## Implementation intent
Choose exactly one of the following two approaches (do not mix both):
1. **Preferred: exact-string synchronization.** Replace each mismatched symptom-column entry with
   the corresponding actual, verified log string (see table above), so the column is truly
   grep-able.
2. **Alternative: explicit non-literal-summary disclaimer.** If exact-string synchronization is
   judged too fragile to maintain long-term (e.g., strings likely to drift again as scripts
   change), instead leave the table's summarized wording but add an explicit note stating the
   symptom column is a summary label, not a literal grep target, and point readers to the actual
   scripts (or to keeping the table synced) for exact strings.

## Implementation instructions
- Open `docs/02_deployment-part2.md` §3.3 (the 失敗モード table, currently lines 54-60).
- If choosing approach 1 (exact-string sync):
  - Replace the symptom column text for the "Invalid workflow definition" row with
    `[FATAL] Workflow definition failed validation; aborting deployment.`
  - Replace the symptom column text for the "Checksum does not match source" row with
    `[FATAL] Deployed workflow definition checksum does not match source; deployment corrupted.`
  - Replace the symptom column text for the "Schema is missing or incomplete" row with
    `[FATAL] Workflow database schema is missing or incomplete.`
  - Replace the symptom column text for the "Schema version mismatch" row with
    `[FATAL] Workflow schema version mismatch: expected <X>, found <Y>.` (using placeholder
    notation consistent with the doc's existing style, since the actual values are shell
    variables `${EXPECTED_SCHEMA_VERSION}` / `${ACTUAL_SCHEMA_VERSION:-<none>}`).
  - Leave the "Missing required workflow definition" row's symptom text unchanged (it is already
    a valid grep-safe prefix of the real log line).
  - Keep the 失敗スクリプト (failing script) and 対処法 (remedy) columns as-is unless they become
    inaccurate after the symptom-text change.
- If choosing approach 2 (disclaimer): add a short note directly above or below the table (in
  Japanese, consistent with surrounding doc language) stating that the 症状 column contains
  summary labels, not literal grep-target strings, and referencing the actual scripts
  (`deploy.sh`, `init_db.sh`, `setup_services.sh`) as the source of truth for exact wording.
- Do not modify `deploy/deploy.sh`, `deploy/init_db.sh`, or `deploy/setup_services.sh` — this is a
  documentation-only change.
- Do not add new failure-mode rows for the additional `[FATAL]` strings noted in Background unless
  doing so is trivial and low-risk; it is not required for this requirement to be satisfied.
