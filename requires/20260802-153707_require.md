# Document the confirmed reason `restart_recommended` always returns False in docs/04_mcp_02_02

## Priority
Medium

## Target files
- `docs/04_mcp_02_02_startup-modes-and-health.md` (primary — the `restart_recommended` semantics subsection, roughly lines 31-64 in the current file, plus the two example JSON bodies around lines 66-92)

## Background
`docs/04_mcp_02_02_startup-modes-and-health.md` documents the standard `/health` response
schema shared by all MCP servers. Its "標準的な `/health` レスポンスのセマンティクス"
subsection already states, as a code-verified fact, that `restart_recommended` always
returns `False` across all 10 MCP servers and the `MCPServer.health()` base implementation,
and that no code path exists anywhere in the codebase that returns `True` (the note is
explicitly marked "Explicit in code"). What the doc does not state is *why* this is the
case — i.e., whether it is a partially-implemented placeholder awaiting future work, or an
intentional/expected end-state.

Investigation for this requirement (source: issue
`issues/20260802-075026_mcp_restart_recommended_always_false_reason.md`) traced the
history of this field and found a confirmed, code- and history-backed reason (see
"Reason for change" below) — this is not a case that needs to fall back to a "Needs
confirmation" placeholder.

## Problem
1. The reason for the always-`False` behavior is undocumented, so a reader cannot tell
   whether to expect this to change in a future release (unimplemented feature) or to treat
   it as permanent (intentional design), per the issue's concern.
2. Separately (found during verification, in scope because it lives in the same subsection
   this requirement touches): the same subsection currently describes `restart_recommended`
   and `operator_action_required` using present-tense language that assumes an active
   "ウォッチドッグ" (watchdog) consumer — e.g. "…をウォッチドッグに伝える" (line 41) and
   "ウォッチドッグは WARNING をログに記録するが" (line 45) — while the very same document,
   a few lines below (line 64), states that the MCP watchdog (the only automatic-restart
   consumer of this field) was removed on 2026-07-16. The present-tense watchdog framing
   inside the semantics subsection is stale relative to that later note and is part of why
   the "why is it always False" reasoning is unclear to a reader: the doc still frames the
   field around a consumer that no longer exists.

## Reason for change
Verified via code and commit history — confirmed, not a Needs-Confirmation case:

- `restart_recommended` was designed to signal the MCP watchdog (a background task that
  periodically polled every server's `/health` endpoint and auto-restarted subprocess-mode
  servers on failure) whether a process restart could resolve a given failure. This is
  documented in `scripts/mcp_servers/server.py`'s `health()` docstring ("restart_recommended:
  True signals the watchdog that a process restart may resolve the failure; False means
  restart will not help").
- The field was hardcoded to `False` from the moment it was introduced
  (`scripts/mcp_servers/health_response.py::make_health_response()` and
  `MCPServer.health()` in `scripts/mcp_servers/server.py`, commit `7ffa728ac`) — no server's
  `/health` implementation was ever wired to compute a real `True` case. This is because
  every dependency-failure mode any of the 10 servers currently detects (missing config
  value, missing binary in `PATH`, missing credential/token, filesystem misconfiguration —
  see the "サーバー固有のヘルスレスポンスフィールド" table in the same doc) is a category
  that a process restart inherently cannot fix; these require operator action, not restart.
  There was accordingly never a concrete failure case that needed `restart_recommended=True`.
- The MCP watchdog — the only intended consumer that would have acted on a `True` value —
  was deliberately removed on 2026-07-16/17 per explicit user request (commit `6bc329cb7`,
  "feat: remove MCP watchdog (background health-poll + auto-restart loop)", driven by
  `requires/done/20260716_20_require.md`). That removal requirement's Non-goals section
  explicitly states the `/health` endpoint and its response fields (including
  `restart_recommended`) must NOT be removed — they were kept for `McpStatusService.probe_all()`
  / `/mcp status` display purposes (see `docs/04_mcp_06_12_watchdog-configuration-monitoring.md`,
  "Not affected" section, which explicitly lists `restart_recommended` as retained).
- Net effect, confirmed: `restart_recommended` is not an unimplemented placeholder awaiting
  future work, and it is also not simply "intentionally never offered" from day one — it is
  a field whose only real consumer (the watchdog) was deliberately removed, while the field
  itself was deliberately retained in the schema for informational display in `/mcp status`.
  No further design intent exists to make any server compute a `True` value, since (a) no
  current failure category would warrant it, and (b) no code path acts on it even if a
  server did emit `True`, beyond a text label in `/mcp status`'s `health_reason` column
  (per this same doc's "`/mcp status` での解釈" bullet, already documented).
