# Undocumented, non-configurable background-task failure threshold

## Priority

Medium

## Target Files

- `scripts/agent/orchestrator.py:51` — `BG_FAILURE_THRESHOLD: int = 5` (module-level constant)
- `scripts/agent/orchestrator.py:580-615` — `_discard_and_log()`, the `add_done_callback` handler that increments/resets `self._consecutive_bg_failures` and checks it against `BG_FAILURE_THRESHOLD` (the `>=` check is at line 600)
- `scripts/agent/orchestrator.py:129` — `self._consecutive_bg_failures: int = 0` initialization
- `scripts/agent/orchestrator.py:572-577` — the first-turn background task creation site (`ctx.stats.stat_turns == 1` guard, `on_first_turn` callback, `add_done_callback(self._discard_and_log)`)
- `scripts/agent/startup.py:122` — wiring of `on_first_turn=self._cmds._generate_session_title`, confirming the only background task type currently feeding this counter is session-title generation

## Background

`orchestrator.py` runs a single "first-turn" background task per turn-1 event: session title generation (`_generate_session_title`, wired via `startup.py:122`). Its completion callback, `_discard_and_log` (`orchestrator.py:580-615`), maintains `self._consecutive_bg_failures`, an instance-level counter:

- Reset to `0` on success (line 614) or on `asyncio.CancelledError` (line 586, treated as neutral, not a failure).
- Incremented by 1 on any other exception (line 588).
- At count `== 1`: logged as `logger.warning` and surfaced to the user via `self._on_error` (lines 589-599).
- At count `>= BG_FAILURE_THRESHOLD` (5): logged as `logger.error` instead of `logger.warning` (lines 600-605).
- Otherwise (counts 2-4): logged as `logger.warning` (lines 606-611).

The background task is created only inside `_append_user_message`, guarded by `ctx.stats.stat_turns == 1` (line 573). `Orchestrator` is constructed exactly once per process (`startup.py:117`, called once from `StartupOrchestrator.run()`), and is reused — not recreated — across `/clear` (`conversation_service.clear_conversation`) and `/session load` (`session_restore.py:46`), both of which call `reset_session_stats()` and reset `ctx.stats.stat_turns` to `0`. Since the next user message increments `stat_turns` back to `1`, each `/clear` or `/session load` re-arms the first-turn background task on the *same* `Orchestrator` instance, and `_consecutive_bg_failures` persists and accumulates across these resets (it is never reset by `/clear`/`/session load` themselves — only by a background-task success or cancellation).

## Problem

The original issue's framing overstates both the mechanism and the impact. Verified facts:

1. **The threshold's only observable effect is a log-level change**, from `logger.warning` to `logger.error` (lines 600-605 vs. 606-611). There is no circuit breaker, no disabling of the background task, no additional user-facing notification, and no other behavioral consequence tied to `BG_FAILURE_THRESHOLD`. The claim that reaching 5 failures causes the system to be "misidentified as critically broken" is not accurate — nothing downstream reads or reacts to the `logger.error` call differently than any other log-level entry.
2. **The counter is not "shared across all background task types."** As currently wired, there is exactly one background task type in the whole file that feeds `_consecutive_bg_failures` (session-title generation via `on_first_turn`). No other `asyncio.create_task(...)` call in `orchestrator.py` attaches `_discard_and_log`. The counter is a plain, un-keyed `int`, not a dict — so if a second background task type were added in the future without its own counter, it would incorrectly share this one — but that is a latent design risk, not a current bug.
3. **"5 consecutive failures" does not mean 5 rapid retries of one call.** The background task fires at most once per `stat_turns == 1` event and is never retried by the counter's own logic. Reaching the threshold requires the *first-turn task itself* to fail 5 separate times with zero intervening successes, across 5 separate `/clear` or `/session load` cycles within the lifetime of one `Orchestrator` (process). This is a real, reachable scenario (confirmed: `Orchestrator` is a long-lived singleton, and neither `/clear` nor `/session load` resets `_consecutive_bg_failures`), but it is a narrower and less severe scenario than the issue's phrasing ("5回の失敗が累積すると重大な障害として記録される") implies.
4. A single success already fully resets the counter (line 614), and cancellation is already excluded from counting as failure (line 586). This existing logic already partially addresses "transient failure" noise — a lone transient failure is forgotten as soon as one success occurs. However, there is genuinely **no distinction between transient errors (e.g., network timeouts) and persistent/programming errors** — all non-cancellation exceptions are counted identically, and the threshold value (5) is a hardcoded magic number with no comment explaining its rationale or its actual effect (log-level only).
5. There is no backoff, retry, or transient-error classification logic anywhere in the background-task failure path.

## Reason for Change

The code today is functionally reasonable (a rare failure streak only changes a log line's severity, which is low-risk), but it is under-documented in a way that invites future misreadings identical to the one in the source issue: a reader/maintainer seeing `BG_FAILURE_THRESHOLD` and an `elif >= threshold: logger.error(...)` branch could reasonably assume this triggers meaningful failure handling (e.g., alerting, circuit-breaking) when it does not, and could misjudge how "5 consecutive failures" actually accumulates (across session resets, not rapid retries). Additionally, the hardcoded, uncommented `5` gives operators no way to tune sensitivity, and no guidance exists for what should happen if a second background task type is added later (it would silently share this counter). Clarifying the code and closing these documentation/configurability gaps prevents both future misdiagnosis of log output and accidental counter-sharing bugs as the codebase grows.

## Implementation Intent

Without changing the existing, low-risk behavior (log-level escalation only, reset-on-success, reset-on-cancellation), improve the clarity and maintainability of this failure-counting logic:

1. Add an explanatory comment/docstring at `_discard_and_log` (and/or near `BG_FAILURE_THRESHOLD`'s definition) stating precisely: what this counter tracks (currently: session-title-generation first-turn task only), that reaching the threshold only changes log severity (no circuit-breaking or task-disabling effect), that the counter resets on success or cancellation, and that it can accumulate across `/clear` and `/session load` cycles within the same process because `Orchestrator` is a long-lived singleton.
2. Evaluate whether `BG_FAILURE_THRESHOLD` should be sourced from existing configuration (e.g., `ctx.cfg`) rather than being a hardcoded module constant, so operators can tune log-escalation sensitivity without a code change. If configurability is deemed out of scope, at minimum retain it as a named constant with the clarifying comment from item 1.
3. Guard against future counter-sharing bugs: if a second background task type is ever wired to `_discard_and_log` (or a similar callback), it must use its own counter rather than sharing `_consecutive_bg_failures`. Document this expectation inline (a comment is sufficient; no new task type exists today, so no functional change is required for this item).
