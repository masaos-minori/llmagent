# Remove duplicate document-management code and regenerate RAG runtime data

## Priority

Medium

## Target files

- `scripts/rag/ingestion/document_manager.py`
- `tests/rag/ingestion/test_ingestion_freshness.py`
- Runtime data at the paths configured in `config/crawler.toml`, `config/chunk_splitter.toml`,
  `config/ingester.toml` (`rag_src_dir`, currently `/opt/llm/rag-src`) and
  `config/ingester.toml`, `config/rag_pipeline_mcp_server.toml`, `config/agent.toml`
  (`rag_db_path`, currently `/opt/llm/db/rag.sqlite`)
- Related operational documentation describing the regeneration procedure

## Background

Source issue `issues/20260819_05_issue.md` ("Remove duplicate document-management code and
regenerate RAG runtime data") describes two related cleanup actions: (1) removing a dead,
duplicate file-URL handling helper in `DocumentManager`, and (2) deleting and regenerating
RAG runtime artifacts once the strict-contract implementation issues have landed.

Verified directly against current source (`scripts/rag/ingestion/document_manager.py`):

- `handle_existing_document()` (lines 48-102) is the active decision path. For file URLs
  (`is_file_url(url)` true), it fetches the stored `etag`/`last_modified`, calls
  `self._is_file_unchanged(...)` (a SHA-256 comparison; see docstring at line 151 — "Return
  True when the file SHA-256 hash is unchanged") to decide skip (unchanged) vs. replace
  (changed), and logs "file:// unchanged (sha256 match)" or "file:// changed — auto
  re-ingesting" (lines 68-89). For non-file URLs it compares `etag`/`last_modified` directly.
- `_handle_existing_file()` (lines 104-132) duplicates the file-URL branch: it fetches the
  same stored `etag`/`last_modified`, calls the same `self._is_file_unchanged(...)` SHA-256
  comparison, logs the identical two messages, and returns a plain `bool` (`True` = unchanged)
  instead of the tuple `handle_existing_document()` returns.
- A repository-wide search for calls to `_handle_existing_file(` (excluding `__pycache__`,
  `.git`, and the generated `mutants/` mutation-testing tree) found **zero current callers**.
  The only occurrences are the method's own definition (line 104) and its duplicate inside
  `mutants/scripts/rag/ingestion/document_manager.py` (a generated artifact, not source that
  is imported or invoked by application code). `_handle_existing_file()` is dead code.
- `_is_file_unchanged` (static method, line 145) is called from `handle_existing_document()`
  (line 75) and from `_handle_existing_file()` (line 118), and is exercised directly by
  `tests/rag/ingestion/test_ingestion_freshness.py` (lines 20, 25, 30, 35, 40, 43). Removing
  `_handle_existing_file()` does not affect `_is_file_unchanged` itself or its existing test
  coverage, since `handle_existing_document()` retains its own call to it.
- The `rag-src/chunk/`, `rag-src/registered/`, `rag-src/retry/`, `rag-src/failed/` directories
  and `rag.sqlite` do not exist under the repository root — they are runtime/operational
  artifacts. `config/crawler.toml`, `config/chunk_splitter.toml`, and `config/ingester.toml`
  set `rag_src_dir = "/opt/llm/rag-src"`; `config/ingester.toml`,
  `config/rag_pipeline_mcp_server.toml`, and `config/agent.toml` set
  `rag_db_path = "/opt/llm/db/rag.sqlite"`. The regeneration steps in this requirement
  therefore apply to the deployed `/opt/llm/` runtime environment, not to repository-tracked
  paths — regeneration is an operational/deployment action, distinct from the code change to
  `document_manager.py`.

All factual claims in the issue are confirmed against current source; the code-duplication
finding is fully applicable and not yet resolved (`_handle_existing_file()` still exists as
dead code today).

This issue's own "Dependencies" section names three prerequisites, all already converted into
requirement documents:

- `requires/20260819-144406_require.md` ("Replace permissive RAG payload handling with strict
  crawl and chunk contracts") — strict, mandatory-field crawl/chunk JSON contracts that the
  regenerated runtime data (chunk files under `rag-src/chunk/`) must conform to.
- `requires/20260819-144649_require.md` ("Make fetched_at mandatory end to end and remove
  timestamp compatibility behavior") — makes `fetched_at` mandatory through every layer; the
  regenerated crawler payloads, chunk files, and database rows in this requirement must carry
  a mandatory, consistent `fetched_at`.
- `requires/20260819-144952_require.md` ("Enforce URL-group atomicity and strict RAG database
  constraints") — URL-group cross-chunk validation, atomic rollback, and DDL default removal
  that the recreated `rag.sqlite` in this requirement must be built from.

This requirement is not a duplicate of any of the three: those establish the strict
application-level and database-level contracts; this requirement (a) removes a specific
dead-code duplication in `DocumentManager` unrelated to those contracts, and (b) performs the
one-time operational cleanup and regeneration of runtime data (chunk files, `registered/`,
`retry/`, `failed/`, `rag.sqlite`) under those contracts once they are implemented.
Implementation of the regeneration half of this requirement must be sequenced strictly after
all three dependencies land, since regenerating data under the old permissive contracts would
immediately violate the new strict contracts.

## Problem

- `scripts/rag/ingestion/document_manager.py` contains two implementations of the same
  file-URL SHA-256 skip-vs-replace decision: the active one inside
  `handle_existing_document()` (lines 68-89) and the unused `_handle_existing_file()` (lines
  104-132). Both call `self._is_file_unchanged(...)` and log the same messages, but
  `_handle_existing_file()` has no caller anywhere in `scripts/` or `tests/`. Keeping both
  increases maintenance cost and risks a future fix being applied to only one path.
- Any RAG runtime data (chunk files under `rag-src/chunk/`, `registered/`, `retry/`,
  `failed/`, and `rag.sqlite`) generated before the strict crawl/chunk contracts, mandatory
  `fetched_at`, and strict database constraints (the three dependency requirements) were
  implemented does not conform to those contracts and cannot be trusted or migrated forward;
  it must be deleted and regenerated from current sources instead.

## Reason for change

`handle_existing_document()` is confirmed as the single active decision path exercised by
callers; `_handle_existing_file()` duplicates its file-URL logic with zero callers, so
removing it eliminates a dead-code maintenance hazard without touching any live behavior.
Once the three dependency requirements make the crawl/chunk JSON contracts, `fetched_at`, and
database constraints strict, any pre-existing runtime data generated under the old permissive
rules is invalid under the new contracts by definition. No legacy data needs to be preserved
and no migration path is in scope, so the only correct operational action is deletion followed
by a full, deterministic regeneration run (Crawler -> ChunkSplitter -> Ingester -> consistency
check) against current sources.

## Implementation intent

Keep exactly one authoritative file-URL decision path in `handle_existing_document()`:
matching SHA-256 values skip re-ingestion, differing values trigger replacement. Remove the
unused `_handle_existing_file()` method entirely; do not change `_is_file_unchanged()` or the
call inside `handle_existing_document()`. Preserve or add focused regression tests covering
both the skip (SHA-256 match) and replace (SHA-256 mismatch) outcomes through
`handle_existing_document()`.

Separately, after all three dependency requirements are implemented and deployed, perform a
one-time operational regeneration of RAG runtime data: stop ingestion processes, remove
generated chunk files and clear `registered/`, `retry/`, and `failed/` under the configured
`rag_src_dir`, delete the existing `rag.sqlite` at the configured `rag_db_path`, recreate the
database from the strict DDL, and re-run Crawler, ChunkSplitter, and Ingester against the
current source set, followed by the RAG consistency check. This is operational cleanup and
regeneration, not data migration — no legacy-format reading, conversion, or compatibility
logic is in scope.

- `_handle_existing_file()` no longer exists in `scripts/rag/ingestion/document_manager.py`.
- `handle_existing_document()` remains the only implementation of the file-URL SHA-256
  skip/replace decision; its behavior is unchanged.
- Matching SHA-256 values continue to skip re-ingestion; differing values continue to
  trigger replacement, verified via tests against `handle_existing_document()`.
- `rg -n "_handle_existing_file"` over `scripts/` and `tests/` (excluding `mutants/`) returns
  no matches after the change.
- No generated chunk files predating the strict-contract changes remain under the configured
  `rag_src_dir`; `registered/`, `retry/`, and `failed/` are cleared.
- The database at the configured `rag_db_path` is recreated from the current strict DDL.
- A full Crawler -> ChunkSplitter -> Ingester run against the current source set completes
  successfully.
- The RAG consistency check reports no issues after regeneration.
- Sampled `fetched_at` values match across crawler payloads, chunk files, and database rows.
