# Catch WorkflowTimeoutError in Orchestrator to prevent uncontrolled propagation to the REPL loop

## Priority

Medium

## Target Files

- `scripts/agent/orchestrator.py:291-294` — `_handle_workflow_engine()` exception handling
- `scripts/agent/workflow/workflow_engine.py:81-82` — `WorkflowTimeoutError` definition
- `scripts/agent/workflow/workflow_engine.py:148-150` — `WorkflowEngine.run()` catches `WorkflowHaltError`/`WorkflowTimeoutError` together and re-raises
- `scripts/agent/workflow/workflow_engine.py:272-284` — `_run_stage_with_retry()` raises `WorkflowTimeoutError` on stage timeout
- `scripts/agent/repl.py:462-502` (`_repl_loop`), `575-591` (`_dispatch_line`), `617-649` (`_run_repl_loop`) — call chain the exception propagates to if uncaught

## Background

`WorkflowEngine.run()` wraps each stage (`plan`/`execute`/`verify`) via `_run_stage_with_retry()`, which calls the stage function with `asyncio.wait_for(fn(), timeout=timeout)`. When a stage exceeds its `timeout_sec`, `asyncio.wait_for` raises `TimeoutError`, which `_run_stage_with_retry()` converts into `WorkflowTimeoutError` (`workflow_engine.py:282-284`) and re-raises. `WorkflowEngine.run()` catches this alongside `WorkflowHaltError` at line 148, marks the task `halted`, and re-raises it further up to the caller, `Orchestrator._handle_workflow_engine()`.

## Problem

`Orchestrator._handle_workflow_engine()` (`orchestrator.py:290-294`) only has `except` clauses for `WorkflowPendingApprovalError` and `WorkflowHaltError`:

```python
except WorkflowPendingApprovalError as exc:
    self._handle_workflow_approval_pending(exc, session_id)
except WorkflowHaltError as exc:
    self._handle_workflow_halt(exc)
```

`WorkflowTimeoutError` is defined as `class WorkflowTimeoutError(Exception)` (`workflow_engine.py:81-82`) — it is not a subclass of `WorkflowHaltError` — so neither `except` clause matches it. The exception passes through the `finally` block (which updates task status and closes the store) and re-raises out of `_handle_workflow_engine()`, out of `handle_turn()` (`orchestrator.py:190-233`, which has no try/except around the call), into `Orchestrator.handle_turn()`'s caller.

Verified by tracing the call chain in `scripts/agent/repl.py`:
- `_dispatch_line()` (line 589) calls `await self._orchestrator.handle_turn(line)` with no try/except wrapping it.
- `_repl_loop()` (lines 487-497) wraps `_dispatch_line()` in `asyncio.wait_for(...)` but only catches `TimeoutError` (asyncio/builtin timeout, unrelated to `WorkflowTimeoutError`, which subclasses `Exception` directly, not `TimeoutError`) — so it does not catch `WorkflowTimeoutError`.
- `_run_repl_loop()` (lines 617-649) wraps `_repl_loop()` in a `try/except RuntimeError` — `WorkflowTimeoutError` is not a `RuntimeError`, so it is not caught here either.

No layer in this call chain catches `WorkflowTimeoutError`. A stage timeout during a live turn will propagate all the way out of `_run_repl_loop()`, terminating the REPL loop with an unhandled exception instead of being reported to the user as a recoverable workflow error (the way `WorkflowHaltError` is via `_handle_workflow_halt()`).

## Reason for Change

A single stage timeout (a transient condition — e.g. slow LLM response, slow tool call, slow verification step) should not be allowed to crash the entire interactive REPL session. `WorkflowHaltError` already has a defined recovery path (`_handle_workflow_halt()`); `WorkflowTimeoutError` needs the same kind of controlled handling so timeouts are reported to the user and the session continues, rather than the process crashing or exiting unexpectedly mid-session.

## Implementation Intent

Add explicit handling for `WorkflowTimeoutError` in `Orchestrator._handle_workflow_engine()`, mirroring the existing `WorkflowHaltError` path (or intentionally reusing it, if a timeout should be treated identically to a halt from the user's perspective). Ensure the user receives a clear, actionable message and the turn ends cleanly without leaving `handle_turn()` via an uncaught exception.

## Implementation Instructions

1. In `scripts/agent/orchestrator.py`, add an `except WorkflowTimeoutError as exc:` clause to `_handle_workflow_engine()` (alongside the existing `except WorkflowPendingApprovalError` and `except WorkflowHaltError` clauses, around line 291-294). Import `WorkflowTimeoutError` from `scripts/agent/workflow/workflow_engine.py` at the top of `orchestrator.py` (it currently imports `WorkflowHaltError` at line 45 — add `WorkflowTimeoutError` next to it).
2. Implement a handler (e.g. `_handle_workflow_timeout(self, exc: WorkflowTimeoutError) -> None`) that reports the timeout to the user via the existing error/warning notification mechanism (`self._on_error` or equivalent, consistent with how `_handle_workflow_halt()` reports `WorkflowHaltError`), and ends the turn without re-raising.
3. Confirm the `finally` block in `_handle_workflow_engine()` (lines 295-307) still runs correctly for the timeout path (task status update, `_deactivate_workflow`, `store.close()`) — it already executes for any exception since it is a `finally`, so no change should be needed there, but verify no double-close or state-corruption issue when combined with the new `except` clause.
4. Double check whether `WorkflowEngine.run()` should keep treating `WorkflowTimeoutError` the same as `WorkflowHaltError` (marking the task `halted` — `workflow_engine.py:148-150`) or whether it warrants its own task status (e.g. `timed_out`) for observability. This is a judgment call for the implementer; if introduced, ensure `StateStore.update_task_status()` accepts the new status value.

## Acceptance Criteria

- [ ] `Orchestrator._handle_workflow_engine()` has an explicit `except WorkflowTimeoutError` clause that does not allow the exception to propagate past `handle_turn()`.
- [ ] A stage timeout during a turn results in a user-visible error/warning message and the REPL loop continues to accept the next input, instead of crashing or exiting.
- [ ] No regression to existing `WorkflowHaltError` and `WorkflowPendingApprovalError` handling behavior.

## Tests

- If feasible, add a REPL-level test driving `_dispatch_line()`/`_repl_loop()` with a stubbed orchestrator that raises `WorkflowTimeoutError`, asserting the loop continues to the next input rather than terminating.
