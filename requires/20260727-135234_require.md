## Background

- The issue (`issues/20260727_21_issue.md`, sourced from NC-009 in
  `docs/00_governance_07_needs-confirmation-inventory.md`) is titled around a
  "`RagPipelineConfig.run` field" whose explicit-setter is unknown.
- Investigation during this workflow cycle found that **no field named `run`
  exists anywhere on `RagPipelineConfig`** (`scripts/mcp_servers/rag_pipeline/rag_pipeline_models.py:36-64`
  lists all fields; there is no `run`). The NC-009 inventory entry's own
  "Section" label (`§RagPipelineConfig.run field`) does not match the actual
  section title in `docs/03_rag_04_05_dto-types.md`, which is "実装上の補足"
  (Implementation notes) discussing the **`PipelineRunResult.result_source`**
  field (`scripts/rag/types.py:44`), not a `RagPipelineConfig.run` field.
- The real open question, as written in the doc body (line 48), is: does any
  code path other than `RagPipeline.run()` (e.g. plugins) construct a
  `PipelineRunResult` and explicitly pass `result_source`?
- Investigation during this cycle also found:
  - `grep -rn "PipelineRunResult(" --include="*.py"` across the repo shows
    exactly one production construction site: `scripts/rag/pipeline.py:347`,
    inside `RagPipeline.run()`. It does not pass `result_source`, so the
    default (`None`, per `scripts/rag/types.py:44`) is always used. All other
    matches are in `tests/*.py` mocks, not production call paths.
  - The plugin extension point that `run()` used to expose after reranking
    (`get_pipeline_post_stages()` / `run_pipeline_stages()`, imported from
    `shared.plugin_registry`) was removed per
    `implementations/done/20260717-224428_rag_pipeline_py_plugin_removal.md`
    (dated 2026-07-17, before NC-009's last-reviewed date of 2026-07-22).
    `plugin_registry.py` no longer exists in the repo (`find` returns no
    match), and `scripts/rag/pipeline.py` has zero remaining references to
    "plugin"/"Plugin" (confirmed by grep).
  - Therefore, in the current codebase there is no "other path (plugins,
    etc.)" that could set `result_source` — the plugin mechanism referenced by
    the original doc note no longer exists.

## Problem

- `docs/03_rag_04_05_dto-types.md:48` still carries a `[Needs confirmation]`
  tag asking whether other call paths set `result_source`, even though the
  underlying mechanism (plugins) that would have provided such a path was
  removed over a week before NC-009's last review date. The open question is
  answerable now but has not been closed.
- Separately, the NC-009 inventory entry
  (`docs/00_governance_07_needs-confirmation-inventory.md:163-164`) mislabels
  the target as "`§RagPipelineConfig.run field`" / "run field", which does not
  exist in the code (`RagPipelineConfig` has no `run` field) and does not
  match the actual doc section title. This is a traceability defect: anyone
  following NC-009's "Section" pointer to investigate a `RagPipelineConfig.run`
  field will not find one, and may misdiagnose the issue as already invalid
  rather than recognizing it refers to `PipelineRunResult.result_source`.

## Reason for Change

- Leaving a resolvable `[Needs confirmation]` marker in place understates the
  actual (now-verifiable) behavior of `PipelineRunResult.result_source` and
  keeps NC-009 open in the governance inventory indefinitely, even though the
  investigation this cycle already produced a confirmed answer via direct code
  read (not inference).
- The mislabeled "Section"/title in NC-009 is a documentation-accuracy defect
  independent of the underlying question; it should be corrected regardless of
  how the `result_source` question is resolved, so future readers can locate
  the correct field.
