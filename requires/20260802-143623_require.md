# Fix field-count claim, add tool_names-routing note, and document role's actual usage in docs/04_mcp_06_03

## Background
`docs/04_mcp_06_03_mcpserverconfig-fields-agenttoml-mcp_servers.md` documents the fields of
`[mcp_servers.*]` in `config/agent.toml`, backed by the `McpServerConfig` dataclass in
`scripts/shared/mcp_config.py`. The doc currently states (line 21): "以下の4つのフィールドのみが
agent.toml に含まれる" (only the following 4 fields are included), listing only `startup_mode`,
`transport`, `url`, and `cmd`. It separately documents `key` as a 5th, non-TOML, auto-derived
field.

## Problem
Verified against the current `McpServerConfig` dataclass (`scripts/shared/mcp_config.py:48-71`),
the "4 fields only" claim is stale. The dataclass now has **14 total fields**, of which **13 are
TOML-settable** (read via `v.get(...)` in `_build_single_server()`,
`scripts/shared/mcp_config.py:168-198`) and 1 (`key`) is auto-derived from the `[mcp_servers.<key>]`
section name, matching the doc's own existing treatment of `key` as a non-TOML field.

TOML-settable fields not currently documented in this file:
- `call_timeout_sec: float = 60.0` — per-call timeout for HttpTransport; 0 = no timeout
- `startup_timeout_sec: int = 30` — subprocess startup health-poll timeout in seconds
- `tool_names: list[str] = []` — deploy allow-list; validated against the tool registry but is
  NOT a routing input (see below)
- `auth_token: str = ""` — Bearer token sent by `ToolExecutor`
- `role: str = ""` — human-readable role label (see confirmed usage below)
- `env: dict[str, str] = {}` — extra env vars for subprocess mode
- `startup_stagger_delay_sec: float = 0.0` — stagger delay between consecutive server starts
- `max_stderr_log_size_mb: float = 100.0` — max stderr log size in MB before rotation
- `max_stderr_log_files: int = 3` — number of rotated stderr log files to keep

Full current field list (14 total): `transport`, `url`, `startup_mode`, `call_timeout_sec`,
`startup_timeout_sec`, `tool_names`, `auth_token`, `role`, `cmd`, `env`, `key` (auto-derived, not a
TOML key), `startup_stagger_delay_sec`, `max_stderr_log_size_mb`, `max_stderr_log_files`.

Note: the issue that prompted this requirement estimated 10 fields; the verified current count is
14 (13 TOML-settable + `key`). The field count has drifted further since the issue was filed —
implement against the 14/13 count confirmed above, not the issue's original estimate, and re-verify
against `scripts/shared/mcp_config.py` at implementation time in case it has changed again.

Separately, `docs/04_mcp_03_01_dispatch-and-routing.md` (line 212) states: "config の `tool_names`
はルーティングの入力ではない; あくまでドリフト検証用のメタデータである" (config's `tool_names` is
not a routing input; it is drift-validation metadata only). This fact is currently absent from
`docs/04_mcp_06_03`, which is a cross-file inconsistency: a reader of `04_mcp_06_03` alone (which
does not currently mention `tool_names` at all) has no way to know this. Additionally,
`docs/04_mcp_03_01` line 214 already cross-references `04_mcp_06_03` for "TOML examples of the 3
tool_names states (omitted / empty list / configured)" — but `04_mcp_06_03` currently contains no
`tool_names` content at all, so that cross-reference is presently dangling/unfulfilled from
`04_mcp_06_03`'s side.

Regarding `role`: code search (`grep -rn "\.role\b" scripts/`) confirms `role` is **not unused**.
It is read from config and actively used for **display purposes only**:
- `scripts/agent/services/mcp_status.py:116` and `:189` — `role=cfg.role or ""` populates the
  `role` field of `McpProbeResult` when building `/mcp status` probe results.
- `scripts/agent/commands/cmd_mcp.py:44-52` — the `ROLE` column of the `/mcp status` table renders
  `r.role` (with an optional `[sb:<sandbox_backend>]` suffix).

`role` is confirmed to be an operator-facing, human-readable label shown in the `/mcp status`
command output. It is not read anywhere in routing/dispatch code (`route_resolver.py`,
`tool_routing_validation.py`, `tool_executor.py`) — its only consumer is the status-display path
above. This resolves the issue's "unconfirmed usage" concern with a definite answer, so no "Needs
Confirmation" placeholder is needed for `role`.

## Reason for change
The field-count claim is a confirmed factual error that would cause readers to underestimate
configurable options (missing `auth_token`, `role`, `call_timeout_sec`, `startup_timeout_sec`,
`tool_names`, `env`, and 3 more fields entirely). The missing tool_names-routing fact creates a
cross-file inconsistency with `04_mcp_03_01` that could lead a reader of `04_mcp_06_03` alone to
wrongly assume `tool_names` participates in routing decisions. The dangling cross-reference from
`04_mcp_03_01` to `04_mcp_06_03` for tool_names TOML examples should be resolved once
`04_mcp_06_03` documents `tool_names`. `role`'s usage, now confirmed via code, should be recorded
accurately instead of being left ambiguous.
