# Startup banner tool count should reflect RuntimeToolRegistry, not the static tool_definitions list

## Priority
Low

## Target files
- `scripts/agent/repl.py` (`AgentREPL._n_tools` property, ~line 114-117)
- `docs/05_agent_07_02_cli-and-commands-cliview.md` (§起動バナー, ~line 42-44)

## Background
The interactive REPL prints a startup banner (`AgentREPL._print_startup_banner()` ->
`CLIView.write_startup_banner()`) showing session id, chunk count, tool count, memory
mode, and workflow status. The tool count is currently sourced from
`AgentREPL._n_tools`:

```python
@property
def _n_tools(self) -> int:
    """Number of tools available (from config/tools_definitions.toml)."""
    return len(self._ctx.cfg.tool.tool_definitions)
```

`self._ctx.cfg.tool.tool_definitions` is a static list loaded from
`config/tools_definitions.toml` at config-build time. The actual runtime-authoritative
tool set lives in `RuntimeToolRegistry` (`scripts/shared/runtime_tool_registry.py`),
populated by `McpToolDiscoveryService.discover_all()` during startup and stored at
`ctx.services_required.runtime_tools`. `RuntimeToolRegistry` already excludes tools
belonging to unavailable/degraded MCP servers at construction time, and its
`llm_tool_definitions()` method further filters to tools with `enabled_for_llm=True`
(i.e. tools actually exposed to the LLM's tool-calling surface). This is the exact
pattern already used by `LLMTurnRunner._filter_disabled_tool_definitions()` in
`scripts/agent/llm_turn_runner.py` (~line 207-223), which prefers
`registry.llm_tool_definitions()` and falls back to `ctx.cfg.tool.tool_definitions` only
when `ctx.services_required.runtime_tools` is `None`.

## Problem
`_n_tools` counts the static config list, which can diverge from the live,
discovery-filtered tool set. When MCP discovery excludes a tool (e.g. a schema-2.0
contract failure, an unavailable/degraded server, or a tool with `enabled_for_llm=False`),
the static list still counts it, so the banner overstates the number of tools actually
callable by the agent in that session. This has been verified directly against the
current source: `_n_tools` at `scripts/agent/repl.py:115-117` still reads
`len(self._ctx.cfg.tool.tool_definitions)` and has no reference to
`RuntimeToolRegistry`.

Verified startup ordering: `AgentREPL.run()` awaits `StartupOrchestrator.run()` (which
performs MCP discovery and sets `ctx.services_required.runtime_tools`) before calling
`_run_repl_loop()`, which calls `_print_startup_banner()`. So by the time the banner is
printed, the runtime registry is already populated for a normal successful startup —
sourcing the count from it is feasible without reordering startup.

The design doc `docs/05_agent_07_02_cli-and-commands-cliview.md` (§起動バナー) merely
states that the banner shows "ツール数" (tool count) without qualifying its source; once
the behavior changes to reflect the runtime-authoritative count, this line should note
that the count is the live/runtime-available tool count, not the static config count.

## Reason for change
An operator-facing number that silently overstates capability is misleading: it can lead
an operator to believe more tools are callable than actually are, which matters when
debugging why the agent is not using an expected tool. Aligning the displayed count with
the runtime-authoritative source removes this mismatch, using a pattern already
established and tested elsewhere in the codebase (`_filter_disabled_tool_definitions`).

## Implementation intent
Change `AgentREPL._n_tools` to prefer the count of tools reported by
`ctx.services_required.runtime_tools.llm_tool_definitions()` (the LLM-callable, live,
discovery-filtered set) when the registry has been populated, falling back to the
current static `len(self._ctx.cfg.tool.tool_definitions)` behavior only when
`runtime_tools` is `None` (e.g. discovery not yet run, or a degraded/partial startup
path that still reaches the banner). This mirrors the existing fallback pattern in
`LLMTurnRunner._filter_disabled_tool_definitions()` rather than inventing a new one.

Do not touch the other two call sites that already compute
`len(ctx.cfg.tool.tool_definitions)` for different, explicitly-labeled displays
(`CommandRegistry._cmd_help` in `scripts/agent/commands/registry.py:99`, and
`_cmd_mcp_status` in `scripts/agent/commands/cmd_mcp.py:172`, which prints
`"Tools  N (from config/tools_definitions.toml)"`) — those are intentionally
config-sourced and explicitly labeled as such, and are out of scope for this issue.

## Implementation instructions
1. In `scripts/agent/repl.py`, update the `_n_tools` property:
   - Read `registry = self._ctx.services_required.runtime_tools` (or the equivalent
     accessor already used elsewhere in this file/class for `services_required`).
   - If `registry` is not `None`, return `len(registry.llm_tool_definitions())`.
   - Otherwise, return `len(self._ctx.cfg.tool.tool_definitions)` (unchanged fallback
     behavior).
   - Update the property's docstring to describe the new runtime-first behavior and the
     fallback condition.
2. In `docs/05_agent_07_02_cli-and-commands-cliview.md`, update the §起動バナー
   description of `write_startup_banner()`'s tool count to state that the count reflects
   the live/runtime-available (discovery-filtered, LLM-enabled) tool set, with a fallback
   to the static config count when the runtime registry has not been populated.
3. Do not modify `CommandRegistry._cmd_help` or `_cmd_mcp_status` — they remain sourced
   from the static config list and are explicitly labeled as such in their own output.

## Acceptance criteria
- `AgentREPL._n_tools` returns `len(runtime_tools.llm_tool_definitions())` whenever
  `ctx.services_required.runtime_tools` is populated (the normal startup path).
- `AgentREPL._n_tools` falls back to the current static `len(tool_definitions)` behavior
  only when the runtime registry is `None`.
- The startup banner's displayed tool count matches the number of tools actually
  enabled for LLM tool-calling in that session (i.e. excludes tools from
  unavailable/degraded servers and tools with `enabled_for_llm=False`).
- `docs/05_agent_07_02_cli-and-commands-cliview.md` §起動バナー accurately describes the
  corrected source and fallback behavior of the tool count.
- The two other, differently-labeled call sites (`_cmd_help`, `_cmd_mcp_status`) are left
  unchanged.

## Tests
- Add/extend a unit test for `AgentREPL._n_tools` (or its exercising path, e.g. the
  existing startup-banner test in `tests/agent/`) covering:
  - `runtime_tools` populated with a mix of `enabled_for_llm=True/False` tools ->
    `_n_tools` equals only the enabled-for-llm count.
  - `runtime_tools` populated with tools whose owning server is in
    `unavailable_servers`/`degraded_servers` -> those tools are excluded from the count
    (already guaranteed by `RuntimeToolRegistry` construction, but assert the count
    reflects it end-to-end through `_n_tools`).

    `len(ctx.cfg.tool.tool_definitions)`, matching current behavior exactly (regression
    guard).

  banner/startup-focused test file).
