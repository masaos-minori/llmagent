## Background
`docs/00_governance_01_documentation-governance.md` already defines the seven document classes (Governance, Guide, Specification, Reference, Operations, Note, Known Issues) and update/review rules, but its own "Non-Goals" section explicitly excludes "document formatting conventions within Specification documents." Only one class (Known Issues) has an actual template document (`docs/00_governance_04_known-issues-template.md`); the other six classes have no template, no defined Front Matter beyond the ad-hoc `title/category/tags/related` seen in existing files, and no defined required/optional section list.

Separately, a repository-wide search found no `docs/*.md` file uses Mermaid (`grep -rl '```mermaid' docs/` returns zero matches), while 10 files still use Unicode box-drawing ASCII diagrams (`┌ └ │ ├`), which are fragile under concatenation/reflow.

A search for the literal deferral phrase "詳細はソースコードを参照してください" ("see source code for details") found it in exactly 3 files, 11 occurrences, all lacking any accompanying statement of responsibility, side effects, failure behavior, or concurrency/security notes for the constants/methods being deferred.

## Problem
1. Six of seven document classes (all but Known Issues) have no template, so new documents in those classes are written ad hoc with inconsistent structure, front matter, and evidence conventions.
2. Three files (`chunksplitter`, `shared-utilities`, `rag-pipeline-class`) have sections that only say "see source code for details" without stating the responsibility, inputs/outputs, side effects, failure behavior, or concurrency constraints a reader needs for design-level understanding.
3. Ten files use ASCII box-drawing diagrams instead of Mermaid, which are harder to review as diffs and can visually break during concatenation or narrow rendering.

## Reason for change
This is documentation-only maintenance debt: it does not block any feature work, but the lack of templates makes new documents inconsistent to write and review, and the ASCII diagrams are a known source of rendering breakage. Addressing it now, while the doc set is being actively maintained (see recent `docs/00_governance_*` additions), is cheaper than retrofitting later once more documents accumulate without templates.

## Implementation intent
- Extend the existing governance framework (`docs/00_governance_01_documentation-governance.md` already lists the seven classes) by adding one template reference document that gives each of the six untemplated classes: required Front Matter fields, a required-section list, an optional-section list, and the evidence/related-document conventions already established by `00_governance_02_canonical-source-rule.md` and `00_governance_03_evidence-labels.md`. Follow the structure/style already used by `00_governance_04_known-issues-template.md` as the model for the new template document.
- For the 3 files with bare "see source code" deferrals, add a short minimum-behavioral-contract block (Responsibility, Input contract, Output contract, Side effects, Failure behavior, Idempotency, Concurrency constraints, Security boundary — include only the fields relevant to each section) directly above or in place of the bare deferral sentence. Do not restate the full API surface — keep pointing to source code for exhaustive signatures.
- For the 10 files with ASCII box-drawing diagrams, convert each diagram to an equivalent Mermaid diagram (flowchart/graph as appropriate), and retain a short plain-text description near the diagram as an accessible text alternative (a sentence or short list summarizing the flow, not a duplicate ASCII diagram).
- Do not create new diagrams for flows that do not currently have one (e.g. RAG ingestion/query pipeline overview, workflow engine, EventBus recovery use numbered-list/inline-arrow notation today, not box diagrams) — that would be new documentation content beyond the scope of "converting existing diagrams," and is explicitly out of scope for this requirement.
- This entire requirement is documentation-only. No source code changes. Where a target touches EventBus-related documentation, restrict work strictly to reading/describing existing behavior — do not add or change any EventBus implementation logic (see AGENTS.md Global Rule 8). In this requirement, no EventBus file requires changes (its docs currently contain no ASCII diagrams and no bare source-code-only deferrals), so this constraint is precautionary only.

## Implementation instructions
1. Create a new governance document (suggested path: `docs/00_governance_09_document-templates.md`) that:
   - Lists the six classes needing a template: Governance, Guide, Specification, Reference, Operations, Note.
   - For each class, defines: required Front Matter fields (title, category, tags, related, and any class-specific fields), a required-sections list, an optional-sections list, and one line on how evidence/citation conventions (per `00_governance_03_evidence-labels.md`) apply.
   - Cross-links from `docs/00_governance_01_documentation-governance.md`'s "Related Governance Documents" list and its Non-Goals section should be updated to point to the new template document instead of excluding formatting conventions outright (the exclusion should be narrowed or removed since it is now addressed).
2. In each of the 3 target files with "詳細はソースコードを参照してください" occurrences, add a minimum behavioral contract immediately adjacent to each occurrence, using only the fields applicable to that section (e.g. a constants-list section needs no "Concurrency constraints"; a public-method section may need Side effects and Failure behavior).
3. For each of the 10 files with box-drawing ASCII diagrams, replace the fenced ASCII diagram with a ```mermaid fenced block expressing the same relationships, and add/keep one short paragraph of plain-text description immediately before or after the diagram.
4. After conversion, verify every new Mermaid block renders correctly on GitHub (visually check via a GitHub preview, PR view, or an equivalent Mermaid-compatible renderer) before considering the task complete.
