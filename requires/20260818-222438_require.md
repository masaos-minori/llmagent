# Document EventBus operational-lifecycle gaps as explicit known issues

## Priority

Medium

## Target files

- `docs/06_eventbus_90_inconsistencies_and_known_issues.md` (primary — add new known-gap entries)
- `docs/06_eventbus_03_persistence_schema_and_replay.md` (retention/capacity cross-reference)
- `docs/06_eventbus_05_06_dlq-operations.md` (DLQ file retention cross-reference)
- `docs/06_eventbus_05_04_consumer-id-stability.md` (consumer-ID lifecycle cross-reference)
- `docs/06_eventbus_02_03_nack-health-dlq.md` and `docs/06_eventbus_05_05_delivery-operations.md` (slow-consumer detection/recovery cross-reference)
- `docs/06_eventbus_06_02_reference-api-route-handlers.md` (API schema gap cross-reference)
- No changes to any file under `scripts/eventbus/` — see "Reason for change" below.

## Background

`docs/06_eventbus_*.md` already comprehensively documents the EventBus system as it is
currently implemented (system overview, publish/replay, subscribe/ack, nack/health/DLQ,
DLQ background loop, persistence schema, config, consumer-ID stability, delivery
operations, DLQ operations, and a reference API section). A dedicated
`06_eventbus_90_inconsistencies_and_known_issues.md` file already exists and follows an
established pattern of recording open items (`EVENTBUS-001` through `EVENTBUS-007`),
including a "保留中" (deferred) section for functionality that is intentionally not
implemented (Agent integration, `EVENTBUS-005`/`006`/`007`).

Verification against the current source in `scripts/eventbus/` (`db.py`, `dlq.py`,
`broker.py`, `config.py`, and all `*_route.py` files) confirms the issue's core factual
claims are still accurate today:

- No retention, purge, or `VACUUM` logic exists anywhere in `scripts/eventbus/db.py`
  (no `DELETE FROM events`, no `VACUUM` call, no size/disk-space checks).
- DLQ JSON files written by `scripts/eventbus/dlq.py` (`_atomic_write`) are never deleted
  or expired by any code path; `os.unlink` is used only to clean up a temp file after a
  failed atomic write.
- Consumer-ID handling (`docs/06_eventbus_05_04_consumer-id-stability.md`) documents that
  IDs are client-supplied with no server-side collision detection, but there is no
  expiration, ownership, or offset-cleanup logic in `scripts/eventbus/offsets.py`.
- Slow-consumer *detection* exists and is documented (`EventBroker.slow_consumer_count()`
  in `scripts/eventbus/broker.py`, surfaced via `degraded_reasons` in
  `scripts/eventbus/health_route.py`), but there is no slow-consumer *recovery* mechanism
  (no disconnect/backpressure/reset logic) anywhere in the codebase, and no recovery
  sequence diagram exists in the docs.
- No Pydantic request/response models exist in any `scripts/eventbus/*_route.py` file
  (`grep` for `BaseModel`/`response_model` returns nothing); routes take a raw
  Starlette `request` and hand-parse JSON, so the FastAPI-generated OpenAPI schema is not
  a meaningful canonical contract today.
- Unlike other subsystems, there is no `eventbus-docs-consistency.yml` workflow under
  `.github/workflows/` (compare with `agent-docs-consistency.yml`,
  `mcp-docs-consistency.yml`, `rag-docs-consistency.yml`,
  `deployment-docs-consistency.yml`, `governance-docs-consistency.yml`), so no CI job
  detects EventBus API/doc drift.

So the issue's factual premise is not stale: retention, purge, DB-capacity/WAL
maintenance, DLQ-file expiry, consumer-ID expiration/reuse, slow-consumer recovery, and
canonical OpenAPI schemas/CI drift detection are all genuinely undefined and unimplemented
today.

## Problem

`AGENTS.md` Global Rule 8 states: "eventbus に関連する実装は絶対にしないこと
（デバッグ・調査は可）" — EventBus implementation is categorically forbidden project-wide;
only debugging/investigation is allowed. `routing.md` reinforces this: "Event Bus debug /
investigation only — implementation forbidden, see AGENTS.md Global Rule 8".

Most of the original issue's numbered tasks (retention/purge routines, `VACUUM`
scheduling, low-disk handling, DLQ file expiry, consumer-ID expiration/cleanup,
slow-consumer recovery logic, Pydantic request/response models, and a CI schema-drift
job) require writing or modifying code under `scripts/eventbus/` and/or
`.github/workflows/`. Under the current project-wide policy, none of that code can be
implemented. Converting the issue into a requirement that asks for those implementations
would produce a requirement that can never legally be executed in this repository as
currently governed.

## Reason for change

The operational risk described in the issue (unbounded DB/DLQ growth, stale consumers,
replay ambiguity, undocumented slow-consumer behavior, doc drift against the real API) is
real and currently invisible to anyone reading the EventBus docs, because none of these
gaps are recorded anywhere. The existing
`docs/06_eventbus_90_inconsistencies_and_known_issues.md` file already has a working
convention for exactly this situation — recording known gaps and explicitly deferred
functionality (see `EVENTBUS-005`/`006`/`007`) without requiring new code. Applying that
same convention to the operational-lifecycle and API-schema gaps keeps the risk visible
and traceable while staying fully within the documentation-only constraint imposed by
Global Rule 8.

## Implementation intent

Extend `docs/06_eventbus_90_inconsistencies_and_known_issues.md` with new numbered entries
(continuing the `EVENTBUS-NNN` numbering scheme) that state, for each area below, the
current behavior and the fact that no policy/mechanism exists yet — mirroring the
tone and format already used for `EVENTBUS-001` through `EVENTBUS-007`:

1. Retention / replay availability: no retention window is defined; all events persist
   indefinitely in SQLite (and in the JSONL archive) unless the operator manually
   intervenes.
2. Purge and consumer-offset protection: no purge mechanism exists; therefore there is no
   consumer-offset protection to describe.
3. Database capacity / WAL maintenance / VACUUM / low-disk behavior / metrics / alerts:
   none are implemented; `PRAGMA journal_mode=WAL` is set but no explicit checkpoint,
   `VACUUM`, or disk-space check exists.
4. DLQ file retention: DLQ JSON files under `{deadletter_dir}` are never deleted or
   expired by any code path.
5. Consumer-ID expiration / reuse / offset cleanup: consumer IDs and their offsets persist
   indefinitely with no expiration or cleanup; document this as an explicit gap distinct
   from the already-documented lack of collision detection.
6. Slow-consumer recovery: detection exists and is documented, but no automatic or manual
   recovery procedure or sequence diagram exists; state this explicitly as deferred and
   note that any recovery design work is blocked pending a policy change to Global Rule 8.
7. API schema canonicity: no Pydantic models or `response_model` annotations exist on any
   EventBus route; the OpenAPI schema FastAPI would generate today does not reflect a
   deliberately designed contract. Treat "make OpenAPI canonical," "generate/validate
   Markdown against OpenAPI," and "CI schema-drift detection" as blocked/deferred for the
   same reason as item 6.

Do not add any new code, configuration, or CI workflow. Do not modify anything under
`scripts/eventbus/` or `.github/workflows/`. Every new entry must be phrased as
documenting an existing gap, not as a design proposal or implementation spec.

## Implementation instructions

1. Open `docs/06_eventbus_90_inconsistencies_and_known_issues.md` and add new entries
   `EVENTBUS-008` through `EVENTBUS-011` (or renumber to avoid collision with any entries
   added by other in-flight work) under a section consistent with the existing
   "ドキュメント対応のみ" / "保留中" structure, covering the seven areas listed in
   "Implementation intent" (items 1–3 can be grouped as one entry on retention/capacity,
   item 4 as one entry on DLQ file retention, item 5 as one entry on consumer-ID
   lifecycle, item 6 as one entry on slow-consumer recovery, item 7 as one entry on API
   schema canonicity).
2. Each new entry must include: an ID, a severity/status tag (matching the existing
   `(Medium/open)`, `(Low/deferred)` style), a one-to-two sentence description of the
   current (absent) behavior, and — where applicable — an explicit note that resolving it
   requires code changes currently forbidden by `AGENTS.md` Global Rule 8.
3. Add a short cross-reference line (one sentence, pointing to the relevant new
   `EVENTBUS-0NN` entry) in each of: `06_eventbus_03_persistence_schema_and_replay.md`
   (retention/capacity), `06_eventbus_05_06_dlq-operations.md` (DLQ file retention),
   `06_eventbus_05_04_consumer-id-stability.md` (consumer-ID lifecycle),
   `06_eventbus_02_03_nack-health-dlq.md` or `06_eventbus_05_05_delivery-operations.md`
   (slow-consumer recovery), and `06_eventbus_06_02_reference-api-route-handlers.md` (API
   schema canonicity). Use the existing "Related Documents" footer convention already
   present in each file rather than introducing a new cross-reference style.
4. Do not touch any `.py` file, any file under `.github/workflows/`, or any other `docs/`
   file outside the EventBus set (`docs/06_eventbus_*.md`).
5. Keep entries factual and traceable to the current source (cite file names, e.g.
   `scripts/eventbus/dlq.py`, `scripts/eventbus/broker.py`) the way existing entries in the
   known-issues file already do.
