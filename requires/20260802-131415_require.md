# State the single-host vs. multi-host deployment premise explicitly in documentation

## Priority
Medium

## Target files
- `docs/02_deployment-part1.md`
- `docs/02_deployment-part2.md`
- `docs/01_overview-arch-01-process.md` (primary candidate for canonical placement — see Implementation intent)
- `docs/01_overview.md` (index page; only a cross-reference/link would be added here, not the statement itself)

## Background
The deployment guide is split across `docs/02_deployment-part1.md` and `docs/02_deployment-part2.md`. Neither file states whether the guide assumes:
- a single-host-complete setup (Agent + MCP servers + LLM services all on one machine), or
- a multi-host configuration where `embed-llm` and `agent-llm` run on separate, externally-managed hosts.

Verification against current sources confirms the underlying facts the issue is based on:
- `config/agent.toml` sets `embed_url = "http://192.168.11.238:8081"` and `llm_url = "http://192.168.11.197:8080"` — two different IPs, i.e. two different hosts in this example configuration.
- `docs/01_overview-arch-01-process.md` (line 88) already notes: "`agent-llm`/`embed-llm` の実際の接続先は `config/agent.toml` の `llm.llm_url` / `rag.embed_url` で個別ホスト・ポートとして設定するものであり…稼働環境によっては別ホスト・別ポートを指す場合がある" — i.e. this file already acknowledges LLM services may live on separate hosts, but it does not frame this as an explicit deployment-topology premise, and does not cross-reference the deployment guide.
- `docs/02_deployment-part1.md` §2.3 ("Registering and starting LLM services") shows the reader running `curl -s http://127.0.0.1:8081/health` and `curl -s http://127.0.0.1:8080/health` for embed-llm and agent-llm — i.e. the guide's own worked example uses `127.0.0.1` (localhost), which reads as a same-host setup and is not reconciled anywhere with the separate-host reality shown in `config/agent.toml`.
- A grep for single-host/multi-host/separate-host terminology (`単一ホスト`, `複数ホスト`, `multi-host`, `single-host`, `別ホスト`, `外部サービス`, etc.) across `docs/01_overview.md`, `docs/02_deployment-part1.md`, and `docs/02_deployment-part2.md` returns no matches — confirming the premise is genuinely absent from all three files today.
- `docs/01_overview.md` itself is now a pure index/table-of-contents page (front matter `related:` lists sub-documents; body is just a file table) — it does not contain narrative architecture content itself. The narrative process/architecture content that the issue's original candidate location implied now lives in `docs/01_overview-arch-01-process.md`, which is linked from `01_overview.md`'s index and already discusses process topology, per-process config isolation, and the embed-llm/agent-llm host question (see line 88 above). This is a structural change since the issue was filed and should inform where the premise statement is actually added.

This issue is not resolved: no file currently states the premise. It is actionable, not vague — the issue names the exact statement text and the exact candidate files.

## Problem
A reader of the deployment guide who reads only `02_deployment-part1.md` and `02_deployment-part2.md` cannot determine the overall deployment topology assumption. Part1's own worked example (`127.0.0.1` health checks) implies same-host, while the real configuration example (`config/agent.toml`) shows separate hosts, and the one file that already hints at "may be a separate host" (`01_overview-arch-01-process.md`) neither states this as a documented premise nor is cross-referenced from the deployment guide. This is foundational context both deployment files implicitly depend on without declaring, and it is currently self-contradictory in tone across the docs set.

## Reason for change
Without an explicit, single canonical statement of this premise, readers combining the deployment docs can reasonably reach opposite conclusions about topology depending on which passage they read first (the `127.0.0.1` example vs. the separate-IP config example vs. the "may be a separate host" hint). Declaring the premise once, in one canonical place, and cross-referencing it removes this ambiguity and prevents future duplication/contradiction as these docs are edited independently.

## Implementation intent
Establish exactly one canonical location for the single-host-vs-multi-host deployment premise, and make every other related file reference it rather than restate or omit it.

Recommended canonical location: `docs/01_overview-arch-01-process.md`, because:
- It already documents process/config topology and already contains the closest existing statement on this subject (line 88, on `embed_url`/`llm_url` potentially pointing to separate hosts).
- `docs/01_overview.md` is now index-only and is not a suitable home for narrative content; it would only carry a link into the file that owns the premise (or into `02_deployment-part1.md`, whichever is chosen as canonical).
- `docs/02_deployment-part1.md` §2.3 is the deployment-guide passage most directly affected (it is the one whose own worked example currently implies same-host), making it the natural cross-reference point rather than the natural owner, since the overview/architecture layer is the more logical home for a premise about system topology.

If, per the issue's own fallback instruction, author confirmation on placement cannot be obtained, default to placing the statement in whichever of part1/part2 most directly depends on it — i.e. `docs/02_deployment-part1.md` §2.3 — and mark the placement as provisional pending author confirmation, exactly as the issue specifies. Do not treat the recommendation above as mandatory if the next phase's author-confirmation step selects a different file; the acceptance criteria only require a single canonical location plus cross-references, not this specific file.
