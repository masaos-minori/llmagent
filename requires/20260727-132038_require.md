# Fix startup approval recovery to restore the most recent pending approval, not the oldest

## Priority

High

## Target Files

- `scripts/agent/startup.py:506-540` — `_recover_pending_approvals()` selects `results[-1]` from a `DESC`-ordered list, which is the oldest pending approval, not the most recent as the surrounding comment and log message claim.
- `scripts/agent/workflow/approval_ops.py:191-204` — `find_all_pending_approvals()` returns rows `ORDER BY a.created_at DESC, a.rowid DESC` (newest first); referenced here only to confirm the sort order that `startup.py` relies on. No change to this function is required unless the implementer chooses the "flip the query to ASC" fix path described below.

## Background

`StartupOrchestrator._recover_pending_approvals()` restores workflow approval-pending state after a process restart. When multiple tasks are left in `pending_approval` status across a restart, this method is supposed to surface the most recently created pending approval to the user via `ctx.turn.pending_approval_id` and the startup warning message.

`find_all_pending_approvals()` in `scripts/agent/workflow/approval_ops.py` queries pending approvals with `ORDER BY a.created_at DESC, a.rowid DESC`, meaning `results[0]` is the newest and `results[-1]` is the oldest.

## Problem

In `scripts/agent/startup.py:518-519`:

```python
# Recover the most recent pending approval first
task_id, approval = results[-1]
```

The comment states the intent is to recover the most recent pending approval, but because `results` is ordered newest-first (`DESC`), indexing `[-1]` actually selects the **oldest** pending approval. This is a direct contradiction between stated intent and implementation.

Consequence: when a restart occurs with multiple tasks stuck in `pending_approval`, the REPL sets `ctx.turn.pending_approval_id` to the oldest approval and presents it to the user as "last". A user running `/approve <id>` or `/reject <id>` based on this prompt could be acting on the wrong (stale) approval request instead of the actual most recent one.

There is no existing test that pins down the expected ordering behavior of `_recover_pending_approvals()`, so this defect does not currently cause any test failures (verified: no test in the repository currently asserts on selecting the newest vs. oldest pending approval during recovery).

## Reason for Change

Workflow approval gates are a mandatory execution path (see ADR-Workflow-Mandatory, `docs/05_agent_03_03_turn-processing-flow-workflow-engine-part1.md`). Presenting the wrong pending approval to the user creates a risk of approving or rejecting the wrong task, which can have real side effects on task execution. The fix is small and localized but has high correctness impact given the safety-critical nature of the approval gate.

## Implementation Intent

Make the implementation match the stated intent: recover and surface the **most recent** (newest by `created_at`, tie-broken by `rowid`) pending approval when multiple pending approvals exist after a restart.

Two equivalent fix paths are acceptable; choose whichever keeps the code clearest:

1. Change `scripts/agent/startup.py:519` from `results[-1]` to `results[0]` (since `results` is already `DESC`-ordered, `results[0]` is the newest). This is the minimal, most localized fix and requires no change to `approval_ops.py`.
2. Alternatively, change the query's `ORDER BY` in `find_all_pending_approvals()` to `ASC` and keep `results[-1]` in `startup.py`, updating the docstring on `find_all_pending_approvals()` accordingly. This is less localized since it changes the semantics of a shared helper function and its docstring ("ordered by creation time descending").

Prefer option 1 unless another caller of `find_all_pending_approvals()` depends on descending order (verify no other caller before choosing option 2).

## Implementation Instructions

1. Check all call sites of `find_all_pending_approvals()` (e.g. via grep across `scripts/agent/`) to confirm whether any other caller depends on the current `DESC` ordering.
2. If no other caller depends on `DESC` ordering being consumed via `results[-1]`, apply the minimal fix: change `scripts/agent/startup.py:519` from `task_id, approval = results[-1]` to `task_id, approval = results[0]`.
3. Update the comment on `scripts/agent/startup.py:518` if needed so it still accurately describes the selection (it already says "Recover the most recent pending approval first", which will now be correct).
4. Double-check the log/warning messages at `scripts/agent/startup.py:529-540` still correctly describe the selected approval as the most recent one; no wording change should be needed if the fix in step 2 is applied, but verify no logic there also assumes reverse indexing.
5. Add a regression test that creates multiple pending approvals with different `created_at` timestamps and asserts that `_recover_pending_approvals()` (or the underlying selection logic) picks the one with the latest `created_at` — see the Tests section below.

## Acceptance Criteria

- [ ] After a restart with two or more tasks in `pending_approval` status, `_recover_pending_approvals()` sets `ctx.turn.pending_approval_id` / `ctx.turn.pending_approval_task_id` to the approval with the latest `created_at` (ties broken by highest `rowid`).
- [ ] The comment and log/warning text in `scripts/agent/startup.py` accurately describe the approval actually selected (no "most recent" claim paired with oldest-item selection).
- [ ] A test exists that fails against the old (`results[-1]` with `DESC` ordering) behavior and passes against the fixed behavior.
- [ ] No other caller of `find_all_pending_approvals()` is broken by the chosen fix (verified by grep/tests).
