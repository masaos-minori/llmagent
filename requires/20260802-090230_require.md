# Correct the tool-routing priority description in docs/01_overview-arch-03-features.md

## Priority
High

## Target files
- `docs/01_overview-arch-03-features.md` (the "ツールルーティング" subsection, ~lines 54-56)

## Background
`docs/01_overview-arch-03-features.md` documents implemented features and their
implementation locations for readers/implementers who need a quick, accurate map of
runtime behavior. The "ツールルーティング" (tool routing) note currently describes a
two-stage fallback routing mechanism attributed to `shared/route_resolver.py`. This was
flagged as the single most severe finding in the Overview/Architecture domain review,
because it is a confirmed factual error about a core runtime mechanism, not speculation.

## Problem
The current doc text (verified present at lines 54-56 as of this writing) reads:

> `shared/route_resolver.py` がツール名をサーバキーに解決する。ルーティング優先順位は
> (1) 起動時の `/v1/tools` live discovery マップ、(2) `shared/tool_registry.py` の
> 静的レジストリ。設定 `tool_names` はルーティングには使用せず、ドリフト検証用のメタ
> データのみ。(根拠: `shared/route_resolver.py`)

This describes routing as a two-stage fallback: (1) the live discovery map, then (2) the
static `tool_registry.py` registry. This directly contradicts the actual, current
implementation and its own module docstring in `scripts/shared/route_resolver.py`,
re-verified during this requirement-writing pass. The current module docstring (lines
2-13 of `scripts/shared/route_resolver.py`) reads verbatim:

```
shared/route_resolver.py

Tool-name to server-key resolution for ToolExecutor.

`RuntimeToolRegistry` (populated from live `/v1/tools` discovery via
`ToolExecutor.set_runtime_registry()`) is the sole routing authority. When a tool is not
found there, `resolve()` either raises `ValueError` immediately (strict_mode) or logs a
warning and then raises. `ToolRegistry` is no longer consulted here.

Config `tool_names` is NOT a routing input; it is drift validation metadata only.
Live /v1/tools discovery is used for startup validation only, not routing.
```

The `ToolRouteResolver` class docstring (line 60) reiterates: "Map tool_name → server_key
using RuntimeToolRegistry as the sole routing authority." The implementation confirms
this: `resolve()` (lines 102-115) calls only `_lookup_runtime_registry()`, which in turn
only consults `self._runtime_registry` (a `RuntimeToolRegistry` instance, lines 117-121).
The `discovery_map` constructor argument is documented (lines 81-83) as "used only by the
currently-unreachable `_log_routing_coverage()` diagnostic, never by `resolve()`."
`tool_registry.py`/`ToolRegistry` is not imported, referenced, or consulted anywhere in
`route_resolver.py`. There is no two-stage fallback in the current implementation: there
is exactly one routing authority (`RuntimeToolRegistry`), and no fallback to a static
registry.

An implementer debugging a routing-related incident who trusts the current doc text will
look for a fallback path to `tool_registry.py` that does not exist, leading to
misdiagnosis of the actual routing behavior.

## Reason for change
The doc's routing-priority description is factually wrong about a core runtime mechanism
and is the highest-priority correction identified in the Overview/Architecture domain
review. Per `rules/coding.md`'s "Current behavior" classification, this is a
"Documentation fix required" case (the doc itself is wrong; the code is correct and
already documents itself accurately) — fix the doc directly rather than filing an
implementation issue.

## Implementation intent
Replace the two-stage fallback description in `docs/01_overview-arch-03-features.md`
with wording that matches `route_resolver.py`'s current, actual, documented behavior:
`RuntimeToolRegistry` is the sole routing authority; the live `/v1/tools` discovery map
is validation-only and is never consulted by `resolve()`; the static registry
(`tool_registry.py`) is not consulted for routing at all; and the `tool_names` config
value is used only for drift validation, not routing. Do not introduce new claims beyond
what `route_resolver.py`'s docstring and implementation currently state. Preserve the
existing "(根拠: `shared/route_resolver.py`)" citation convention used throughout the
surrounding doc section.
