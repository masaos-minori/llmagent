# Split the conflated Agent-layer / MCP-server-layer allowlist warning descriptions in docs/04_mcp_*.md

## Priority
Medium

## Target files
- `docs/04_mcp_05_01_access-control-and-allowlists.md` (primary — cicd-mcp `workflow_allowlist` section, lines ~202-225)
- `docs/04_mcp_05_03_fail-open-fail-closed-and-risk-tiers.md` (line ~45, cicd-mcp row; line ~43, shell-mcp row — same conflation pattern, needs same split or a cross-reference)
- `docs/04_mcp_05_05_mdq-enforcement-and-lockdown.md` (line ~172, cicd-mcp; lines ~235-237, shell-mcp — same pattern)
- Any other `docs/04_mcp_*.md` file found on further audit to describe a single "startup warning" for an allowlist that is actually produced independently by both `scripts/agent/repl_health.py` and a `scripts/mcp_servers/<server>/*.py` module (not fixed in this requirement — file follow-up issues instead, per the source issue's "Out of Scope").

## Background
`docs/04_mcp_05_01_access-control-and-allowlists.md` documents cicd-mcp's `workflow_allowlist` fail-closed behavior. It states: "`workflow_allowlist` が空の場合、起動時に以下の警告が出力される: `DENY-ALL detected: cicd.workflow_allowlist is empty. cicd-mcp will reject ALL workflow trigger requests.`" This is written as a single, unified "at startup" warning.

In reality there are two independent warning mechanisms, confirmed against current source:

1. **Agent layer** — `scripts/agent/repl_health.py`, function `audit_security_defaults()` (trigger check ~line 631, log/return ~lines 638-639). Runs once at agent REPL startup, in the agent process, regardless of whether the cicd-mcp server is even running. It reloads the cicd config itself via `load_cicd_audit_config()` and checks `cicd_cfg is not None and not cicd_cfg.workflow_allowlist and not lockdown`. On trigger it calls `logger.warning(msg)` on the agent's own logger and appends the message to a `warnings: list[str]` that callers surface as REPL startup output. Exact message: `"DENY-ALL detected: cicd.workflow_allowlist is empty. cicd-mcp will reject ALL workflow trigger requests. Verify this is intentional or add allowed workflows to cicd_mcp_server.toml."`

2. **cicd-mcp's own layer** — `scripts/mcp_servers/cicd/service_guards.py`, `CiCdGuards.__init__` (trigger ~line 39, log ~lines 40-41). Fires when the `CiCdGuards`/`CiCdService` mixin is constructed inside the cicd-mcp **server process**, checking `if not self._workflow_allowlist:` against the value injected into its own constructor (not a re-read of the agent's config path). It logs via `logger.warning(...)` on the module's own logger (`mcp_servers.cicd.service_guards`) as a pure side effect inside the server process's log stream — there is no return value. Exact message: `"cicd-mcp: workflow_allowlist is empty — all workflow triggers will be denied"`.

These are genuinely independent: different processes (agent REPL vs. cicd-mcp server process), different config-read paths, different logger namespaces, different message text, and different output destinations (agent warnings list surfaced at REPL start vs. server-process log stream only). Neither mechanism calls the other.

Note also that `service_guards.py` has a third, distinct mechanism — `_assert_allowed_workflow()` (~lines 60-72), which raises `CicdAuthorizationError` per-call at request time. This is runtime enforcement, not a startup warning, and is out of scope for this requirement's "warning" framing, but should not be conflated with the two warnings either if the rewritten section touches it.

The project's own docs already show the correct pattern elsewhere: `docs/04_mcp_05_01_access-control-and-allowlists.md:116` (github-mcp `protected_branches` section) explicitly states "agent 層の承認と github-mcp 側の `protected_branches` は独立した別レイヤーである" (the agent-layer approval and github-mcp's own `protected_branches` are independent, separate layers). The cicd-mcp `workflow_allowlist` section should follow this same documented pattern.

A spot-check of two other `docs/04_mcp_*.md` files that reference the same cicd-mcp warning (`04_mcp_05_03_fail-open-fail-closed-and-risk-tiers.md` and `04_mcp_05_05_mdq-enforcement-and-lockdown.md`) found the identical conflation for **shell-mcp**: both docs describe only the agent-layer warning (`repl_health.py`, message `"DENY-ALL detected: shell.command_allowlist is empty..."`), with no mention that `scripts/mcp_servers/shell/shell_service.py`'s `build_service()` (~lines 333-340) independently logs its own, differently-worded warnings inside the shell-mcp server process (`"command_allowlist is empty — all commands will be rejected"`, and a second one for `shell_cwd_allowed_dirs`). This is the same two-layer pattern, undocumented the same way, for a different server/allowlist pair.

## Problem
`docs/04_mcp_05_01_access-control-and-allowlists.md`'s cicd-mcp `workflow_allowlist` section presents two independent warnings (Agent-layer `repl_health.py` and cicd-mcp-layer `service_guards.py`) as if they were a single unified "startup warning." An operator investigating an incident who is unaware of this split could check only one location (e.g. only the agent REPL output, or only the cicd-mcp server log) and miss the other, delaying root-cause identification — especially since the two mechanisms have different trigger conditions (agent process running vs. cicd-mcp server process running) and can, in principle, diverge (e.g. agent-layer warning suppressed by `lockdown` while the server-layer warning is not, or vice versa).

The same conflation pattern exists for the shell-mcp `command_allowlist` (and `shell_cwd_allowed_dirs`) warnings in `04_mcp_05_03` and `04_mcp_05_05`, which reference the same `05_01` doc.

## Reason for change
Documentation accuracy directly affects incident-response speed. The doc should describe each warning mechanism's real trigger condition and real output destination so an operator (or an AI agent debugging on the operator's behalf) knows exactly where to look for each. The project has an established, correct precedent for this exact kind of distinction (github-mcp `protected_branches`, `05_01` line 116) that the cicd-mcp section should be brought in line with.

## Implementation intent
Rewrite the cicd-mcp `workflow_allowlist` warning description in `docs/04_mcp_05_01_access-control-and-allowlists.md` (lines ~221-222 and any related row/summary elsewhere in the same doc) to present two explicit, separately labeled items instead of one merged statement, following the same "independent separate layer" framing already used for github-mcp `protected_branches` at line 116. Do not merge or reconcile the two mechanisms' wording — describe each as it actually behaves in source. Then perform (or explicitly hand off via follow-up issue, per the source issue's Out-of-Scope instruction) the same treatment for the shell-mcp instances found in `04_mcp_05_03` and `04_mcp_05_05`.

This requirement is documentation-only; it does not request any source code change to `repl_health.py` or `service_guards.py`.

## Implementation instructions

   - Which layer/process produces it (Agent REPL process / cicd-mcp server process)
   - The exact trigger condition (agent: `cicd_cfg is not None and not cicd_cfg.workflow_allowlist and not lockdown` in `repl_health.py::audit_security_defaults()`; server: `not self._workflow_allowlist` in `service_guards.py::CiCdGuards.__init__`)
   - The exact output destination (agent: `logger.warning` + returned in `warnings: list[str]` surfaced at REPL startup; server: `logger.warning` on the `mcp_servers.cicd.service_guards` logger, server-process log stream only)

2. Follow the phrasing pattern already used at `docs/04_mcp_05_01_access-control-and-allowlists.md:116` for github-mcp `protected_branches` ("independent separate layer") so the doc is internally consistent.
