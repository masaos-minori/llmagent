## Background

A prior governance effort already produced most of the infrastructure this area needs:

- `docs/00_governance_03_evidence-labels.md` defines the 7 evidence labels, usage conditions, examples, and the "ambiguous case" handling policy.
- `docs/00_governance_04_known-issues-template.md` defines a common 17-field Known Issue entry template plus Status/Type/Severity/Owner/Area vocabularies.
- `docs/00_governance_07_needs-confirmation-inventory.md` defines a 15-field inventory entry format and an extraction process, and already lists NC-001 through NC-017, all currently marked `Status: resolved`.
- `docs/00_governance_08_known-issues-migration-plan.md` is a *planning* document only — it explicitly excludes performing the actual migration ("Excluded: Actually modifying any existing Known Issues documents during this planning phase").

Despite this, verification against the current repository shows the underlying problems the original issue raised are still present in three specific ways.

## Problem

1. **No generic evidence block.** `00_governance_03_evidence-labels.md` only defines a structured field set (Question/Evidence/Impact/Required Action/Target Document/Review Timing) for the "Needs confirmation" label. There is no standard evidence block (source module/doc, symbol/section, test identifier, verification date, notes) usable for the other six evidence labels (Explicit in code, Strongly implied by code, Documentation only, Deprecated, Verified by test, Operationally observed).

2. **Unregistered active uncertainty markers exist.** A repo-wide scan (`grep -rn "Needs Confirmation\|要確認\|未確認" docs/`) finds live markers in area documents that do not correspond to any entry in `00_governance_07_needs-confirmation-inventory.md` (which currently only covers NC-001–NC-017, all already resolved). Confirmed examples:
   - `docs/04_mcp_04_05_git.md:89` — whether the write-guard asymmetry between `git_checkout`/`git_pull`/`git_push` and other write tools is an intentional design decision.
   - `docs/05_agent_03_03_turn-processing-flow-workflow-engine.md:92,272` — whether `require_approval` defaulting to `False` in production is intended.
   - `docs/03_rag_02_03_ingestion_pipeline-chunksplitter.md:39,115` — rationale for `MIN_HEADING_LINES_FOR_MARKDOWN = 2` is unconfirmed.
   - `docs/03_rag_02_08_ingestion_pipeline-shared.md:135` — no recorded basis for a hardcoded value of `20`.
   - `docs/03_rag_02_09_ingestion_pipeline-shared-utilities.md:47` — rationale for `MIN_TEXT_LENGTH_FOR_DETECTION = 100` is unconfirmed.
   - `docs/90_shared_04_03_db_architecture_and_schema-migration-and-scaling.md:93,96,109` — three `(要確認)` markers about hardware-dependent thresholds.
   - `docs/01_overview-files-02-rag.md:31` — retention/cleanup policy for `registered/` is unconfirmed.
   - `docs/04_mcp_00_document-guide.md:159` — a "未確認事項" (unconfirmed items) section not linked to the central inventory.

   These statements have no inventory ID and no bidirectional link to `00_governance_07`, so they can remain unresolved indefinitely without an owner, contrary to the inventory document's stated purpose.

3. **Known Issues formats remain inconsistent across areas, and one area's migration note is inaccurate:**
   - `docs/04_mcp_90_inconsistencies_and_known_issues.md` — fully migrated; contains a migration note and both entries (MCP-001, MCP-002) use all 17 template fields. Use as the reference example.
   - `docs/03_rag_90_inconsistencies_and_known_issues.md` — entries (RAG-003, RAG-004) already contain content matching essentially all 17 template fields, but the document has no migration note declaring template adoption (unlike MCP/Shared-DB).
   - `docs/90_shared_90_inconsistencies_and_known_issues.md` — carries a migration note claiming "Destination format: common template (17 fields)", but the single entry (SHARED-001) is written as a single narrative paragraph with only Status/Severity/Type mentioned inline; it does not actually contain the 17 discrete fields (no ID/Title/Area/Owner/First Found/Target/Related/Summary/Current Description/Observed Implementation/Recommended Action/Resolution Notes as separate fields). The note and the content disagree.
   - `docs/05_agent_90_inconsistencies_and_known_issues.md` — uses an entirely different scheme (a "5段階分類": Accepted current specification / Implementation fix required / Documentation fix required / Issue already tracked / Obsolete and removable) with no individual entries currently open ("現時点でオープンな項目はない"). This is not the common template and there is no discussion of whether this divergence is an intentional area-specific choice or a pending migration.
   - `docs/06_eventbus_90_inconsistencies_and_known_issues.md` — uses Japanese section headers ("対応が必要な項目", "ドキュメントのみで対応する項目", "保留中", "スキーマと実装の差異") with individual `EVENTBUS-NNN` entries that carry only inline `(Severity/Status)` — no Type, Owner, Source, Target, Related, or separate Current Description/Observed Implementation/Recommended Action fields.

   This means comparison, filtering, and automated validation across areas is still not possible, which is exactly the consequence the original issue warned about.

## Reason for change

- The governance scaffolding (evidence labels, common template, NC inventory format, migration plan) is already in place and should not be redefined from scratch; doing so would duplicate existing, correct work.
- However, the actual application of that scaffolding is incomplete and, in the Shared/DB case, self-contradictory (a migration note asserting compliance that the entry does not satisfy). Leaving this unaddressed means the stated risk in the original issue — unreliable comparison, filtering, and validation across areas — persists in practice, even though the framework exists on paper.
- New "Needs Confirmation" markers have accumulated in area docs since the inventory was last populated (all 17 current inventory entries are already resolved), so the inventory has drifted out of sync with the live documentation set.

## Implementation intent

- Do not re-author the evidence-label taxonomy, the common Known-Issues template, or the NC inventory format — extend them.
- Add a generic, reusable evidence-block sub-template to `00_governance_03_evidence-labels.md` for use with any of the 7 evidence labels (not just Needs confirmation), with one example per label type.
- Re-run the Needs-Confirmation extraction process already documented in `00_governance_07_needs-confirmation-inventory.md` against the current `docs/` tree, and add inventory entries (continuing the `NC-###` sequence) for every currently active, unregistered marker found. Link each source statement back to its new inventory ID (per the existing document's stated goal of bidirectional linking).
- Bring the five area Known-Issues documents into actual conformance with the common template, following the already-fully-migrated MCP document as the reference model:
  - Reformat `90_shared_90_inconsistencies_and_known_issues.md`'s SHARED-001 entry into the discrete 17-field format so its content matches its existing migration note.
  - Add a migration note to `03_rag_90_inconsistencies_and_known_issues.md` documenting that its entries already conform (or perform the light reformatting needed to make them conform).
  - Convert `06_eventbus_90_inconsistencies_and_known_issues.md`'s section/table-based entries into individual 17-field entries, preserving existing `EVENTBUS-NNN` IDs.
  - For `05_agent_90_inconsistencies_and_known_issues.md`, either migrate its 5-tier scheme into the common template (if there is content to migrate) or explicitly document why the area intentionally uses a different scheme instead of silently diverging — this determination belongs to the next phase (plan/implementation), not this requirement.
- Preserve all existing entry IDs and issue substance in every migrated document; do not resolve any Known Issue or Needs-Confirmation item as part of this work.

## Implementation instructions

1. In `00_governance_03_evidence-labels.md`, add a "Standard Evidence Block" section defining a reusable field set (Evidence label, Source module or document, Symbol or section, Test identifier, Verification date, Notes), with one worked example per of the 7 label types. Prefer symbol/config-key/test references over line numbers, consistent with the existing document's spirit.
2. Re-run the extraction process in `00_governance_07_needs-confirmation-inventory.md` §Extraction Process against the full `docs/` tree. For every active (i.e., not already superseded/resolved) marker not currently represented by an inventory entry — including but not limited to the eight locations listed under Problem #2 — add a new `NC-###` entry with all 15 fields populated, and add a back-reference (inventory ID) at the marker's location in the source document only if the source document itself is in scope for this requirement; otherwise note in the inventory entry that the source-side link is deferred to the relevant area's own document-maintenance work.
3. For each of the five area Known-Issues documents, compare current structure against `00_governance_04_known-issues-template.md`'s 17 fields and:
   - `04_mcp_90...` — no action needed (already compliant); confirm during review.
   - `03_rag_90...` — add a migration note (matching MCP's/Shared's note format) and confirm/adjust field names so all 17 fields are explicitly present per entry.
   - `90_shared_90...` — rewrite SHARED-001 into explicit 17 discrete fields, preserving all existing content/decisions; the ID must remain `SHARED-001`.
   - `06_eventbus_90...` — convert each table/section item into an individual entry using the full field set, preserving all existing `EVENTBUS-NNN` IDs and content; do not merge or drop the "保留中" (deferred) or "スキーマと実装の差異" items — represent them as entries with `Status: deferred` or equivalent rather than dropping them.
   - `05_agent_90...` — determine whether the 5-tier scheme should migrate to the common template or remain a documented exception; record the decision explicitly in the document (this decision is part of this requirement's scope since the original issue asked to "distinguish confirmed design decisions from active defects").
4. Add a migration note to any document that did not previously have one, following the existing note format used in the MCP and Shared/DB documents (date, source format, destination format, notes on content preservation).
5. Do not modify source code or any file outside `docs/` and `requires/`.
