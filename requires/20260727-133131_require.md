# Terminate spawned MCP subprocess before dropping tracking on getpgid() failure

## Priority

High

## Target Files

- `scripts/agent/http_lifecycle.py:242-255` — `HttpServerLifecycleManager.start()`, `except OSError` branch after `os.getpgid(proc.pid)`
- `scripts/agent/http_lifecycle.py:345-398` — `HttpServerLifecycleManager.shutdown_all()`, enumerates cleanup targets from `_http_procs.keys()`

## Background

`HttpServerLifecycleManager.start()` spawns an HTTP MCP server subprocess via
`subprocess.Popen(..., start_new_session=True)` and then calls
`os.getpgid(proc.pid)` to record the process group id for later
`os.killpg()`-based termination in `_terminate_with_timeout()` (line 111).

`shutdown_all()` (lines 345-398) enumerates all subprocesses to clean up
solely from `self._http_procs.keys()` (line 370). Any process not present in
that dict is invisible to shutdown and never terminated.

## Problem

In `start()` (lines 242-255), if `os.getpgid(proc.pid)` raises `OSError`, the
`except` branch logs a warning that says "cleaning up", closes the stderr
file handle, and pops the server key from `_stderr_files`, `_stderr_log_paths`,
`_http_procs`, and `_http_pgids` — but it never calls `proc.terminate()` or
`proc.kill()`. If the underlying OS process is actually still alive (e.g.
`getpgid()` failing for a permission or transient reason rather than because
the process already exited), it is now completely untracked: not in
`_http_procs`, so `shutdown_all()` (line 370: `keys = list(self._http_procs.keys())`)
will never find and terminate it. The process is orphaned for the lifetime of
the parent, with no mechanism to reap it.

This is confirmed as reproducing in the current source (verified against
`scripts/agent/http_lifecycle.py` at the cited line ranges).

## Reason for Change

An orphaned MCP subprocess is a resource leak (holds ports, file descriptors,
memory) and a potential security/stability concern (an unmanaged process
outliving the agent). The code's own log message ("cleaning up") indicates
the intent was to terminate the process, but the implementation only removes
it from internal bookkeeping. This is the same class of orphaned-subprocess
symptom already tracked in `issues/done/20260727_02_issue.md` and
`issues/done/20260727_06_issue.md` (per this issue's Classification note),
but from a distinct code path, so it must be fixed independently.

## Implementation Intent

Before discarding tracking state in the `except OSError` branch of `start()`,
ensure the spawned process is actually terminated (or killed if it does not
respond to a terminate signal within a bounded timeout), so no live process
is left running unmanaged regardless of why `getpgid()` failed.

## Implementation Instructions

1. In `scripts/agent/http_lifecycle.py`, inside `HttpServerLifecycleManager.start()`,
   in the `except OSError:` branch handling `os.getpgid(proc.pid)` failure
   (current lines 244-255):
   - Before popping `server_key` out of `_http_procs`/`_http_pgids`, attempt to
     terminate the process directly on the `proc` handle (since no pgid was
     recorded, `_terminate_with_timeout()`'s pgid-based path is unavailable —
     use `proc.terminate()`, wait with the existing `_wait_exited()` helper
     (line ~90s) under a bounded timeout, and escalate to `proc.kill()` if it
     does not exit in time), mirroring the terminate/escalate pattern already
     used in `_terminate_with_timeout()` (lines 111-146) but operating on
     `proc` directly since `_http_pgids[server_key]` was never set for this
     process.
   - Only after the termination attempt (successful or not) proceed with
     closing the stderr file handle and popping the bookkeeping dicts, so
     tracking is never dropped while the process might still be alive.
   - Keep the existing warning log, and add a follow-up log line reporting
     whether termination succeeded, timed out, or the process had already
     exited.
2. Do not change the happy path (`getpgid()` succeeds) or any other branch of
   `start()`.
3. Do not change `shutdown_all()`'s enumeration logic — the fix belongs in
   `start()` so no process ever reaches a state of being alive but absent
   from `_http_procs`.

## Acceptance Criteria

- [ ] When `os.getpgid(proc.pid)` raises `OSError` in `start()` and the
      spawned process is still alive, the process is terminated (or killed
      after a bounded timeout) before its tracking entries are removed from
      `_http_procs`/`_http_pgids`/`_stderr_files`/`_stderr_log_paths`.
- [ ] No new orphaned process remains after `start()` returns from this
      branch, verified via a test that injects a `getpgid()` failure with a
      real (or fake, in-test) subprocess and confirms the process exits.
- [ ] Existing behavior for the success path of `start()` and for
      `shutdown_all()`/`restart()` is unchanged.
