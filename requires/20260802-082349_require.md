# Clarify relationship between Resolution Workflow and Conflict Resolution Rule in docs/00_governance_02

## Priority
Medium

## Target files
- `docs/00_governance_02_canonical-source-rule.md`

## Background
`docs/00_governance_02_canonical-source-rule.md` currently defines two separate step-by-step
procedures for handling conflicts:
- **Conflict Resolution Rule** (lines 25-32, 4 steps): identify area(s), determine if the
  same area applies (consult document-guide), check cross-area supersession by dependency
  direction, and register a Known Issue if unresolved.
- **Resolution Workflow** (lines 53-61, 5 steps): detect the conflict, classify the conflict
  type, apply the appropriate resolution rule, update affected documents/code, and record the
  resolution in Known Issues.

These two sections overlap substantially (both end in registering/recording a Known Issue,
both involve identifying/classifying the conflict) but the document does not state how they
relate to each other or to the third rule in the same document, **Code vs Document Conflict
Rule** (lines 34-42).

## Problem
A reader of `docs/00_governance_02_canonical-source-rule.md` cannot tell from the text alone
whether:
- Resolution Workflow supersedes Conflict Resolution Rule (i.e. replaces it),
- Resolution Workflow wraps/encompasses Conflict Resolution Rule and Code vs Document Conflict
  Rule (i.e. Resolution Workflow is the overall process and the other two are sub-procedures
  invoked from within it), or
- The two are simply duplicated/redundant content that should be merged.

This ambiguity means a reader resolving an actual conflict does not know which procedure to
follow, or whether to follow both in sequence.

## Reason for change
Without an explicit statement of the relationship, the governance document fails at its stated
purpose (defining canonical rules for resolving conflicts) because it leaves the resolution
process itself ambiguous. This was flagged in a documentation review
(`docs_review_governance.md` §3, summarization candidate item 2) and confirmed still present
in the current file as of this review (verified 2026-08-02: both sections exist unchanged,
with no cross-referencing or relationship statement between them).

## Implementation intent
Add a short introductory statement at the start of the "Resolution Workflow" section
(immediately after the `## Resolution Workflow` heading, before its numbered list) clarifying
that Resolution Workflow is the overall, ordered process that incorporates the individual
rules defined earlier in the same document — Conflict Resolution Rule, Code vs Document
Conflict Rule, and Known Issues Registration Rule — as steps within it (e.g., step 2
"Classify the conflict type" invokes Code vs Document Conflict Rule's five categories or
Conflict Resolution Rule's area-based logic; step 3 "Apply the appropriate resolution rule"
executes whichever specific rule the classification pointed to; step 5 "Record the
resolution" invokes Known Issues Registration Rule's criteria).

This is a documentation-fix-required case per `rules/coding.md` §"Documentation notes —
Current behavior classification": the doc's own content is ambiguous/incomplete, not a
code/doc mismatch, so the fix is a direct edit to the doc — no code changes are implied.

## Implementation instructions
1. In `docs/00_governance_02_canonical-source-rule.md`, edit only the `## Resolution
   Workflow` section (do not restructure or renumber the existing 5-step list, and do not
   edit `## Conflict Resolution Rule`, `## Code vs Document Conflict Rule`, or `## Known
   Issues Registration Rule`).
2. Insert one to two introductory sentences directly under the `## Resolution Workflow`
   heading, before the "From detection to record-keeping:" line (or replacing/extending it),
   stating explicitly that this workflow is the overall ordered process that integrates the
   three preceding rules — Conflict Resolution Rule, Code vs Document Conflict Rule, and
   Known Issues Registration Rule — each invoked at the appropriate step.
3. Do not merge, delete, or reorder the two step lists themselves; only add the clarifying
   statement.
4. If, during implementation, the intended relationship turns out to be ambiguous even after
   re-reading the surrounding document (e.g. it is unclear whether Resolution Workflow is
   meant to wrap all three rules or only some), do not guess: register the ambiguity as a
   "Needs Confirmation" entry in `docs/00_governance_07_needs-confirmation-inventory.md`
   instead of writing an unsupported relationship statement, per the issue's original AI
   Implementation Instruction.

## Acceptance criteria
