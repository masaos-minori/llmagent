## Background
The source issue (`issues/20260802-080020_rag_01_part2_crawl_limits_and_stage_table_dedup.md`)
reported two problems in `docs/03_rag_01_system_overview-part2.md`:
1. Crawl depth stated as "up to 6 hops" and page count as "up to 500 pages," diverging from
   `config/crawler.toml` (`max_depth = 3`, `max_pages = 200`).
2. The "query pipeline stage table" and "MCP server responsibility table" in the same file
   duplicate content that is canonically owned by `docs/03_rag_03_01_query_pipeline-overview.md`,
   down to class names and the `rrf_k` default value.

Re-verification during this requirement's drafting (2026-08-02) found that **item 1 is already
fixed**: commit `6cfb24c10` ("feat: add RAG docs consistency checker and fix confirmed drift",
2026-07-30) corrected the crawl depth/page-count text in
`docs/03_rag_01_system_overview-part2.md` (lines 99-100) to read:
- クロール深度: "運用値は3(開始URLから最大3ホップ、`config/crawler.toml`の`max_depth`)。コード側フォールバック値とは異なるため、参照時は運用設定ファイルの値を優先する"
- クロールページ数上限: "運用値は200(サイトあたり最大200ページ、`config/crawler.toml`の`max_pages`)。500はコードのフォールバック値であり運用値ではない"

This matches the current `config/crawler.toml` (`max_depth = 3`, `max_pages = 200`) and is
consistent with `docs/03_rag_02_02_ingestion_pipeline-crawler-part1.md` (lines 99-100 of that
file state the same 3-hop / 200-page operational values). **No further change is needed for the
crawl depth/page-count numbers** — this requirement is scoped only to item 2, the remaining
unresolved part of the issue.

## Problem
`docs/03_rag_01_system_overview-part2.md` still contains two tables that duplicate content
canonically owned elsewhere, creating two sources of truth that must be kept in sync manually:

- The "クエリパイプライン" stage table (lines 62-68, columns: ステージ / クラス / 機能) repeats
  the same 5 stage class names (`MqeStage`, `SearchStage`, `FusionStage`, `RerankStage`,
  `AugmentStage`) and the same `rrf_k` default value (60) and rerank/dedup mechanics that are
  already documented in `docs/03_rag_03_01_query_pipeline-overview.md` §1 (the
  `RagPipeline.augment(query)` flow diagram) and its child detail files
  (`03_rag_03_02` through `03_rag_03_05`).
- The "MCPサーバーの責務分担" table (lines 105-111, 3 rows: `rag_pipeline_server.py`,
  `rag_pipeline_service.py`, `scripts/rag/pipeline.py`) restates file responsibilities that
  overlap with the "呼び出し元" / "MCP サーバー呼び出しパス" sections of
  `docs/03_rag_03_01_query_pipeline-overview.md`.

## Reason for change
Duplicated detail across `part2` and the canonical `03_01` doc doubles the maintenance burden:
any future change to stage class names, the `rrf_k` default, or MCP file responsibilities
requires editing two files instead of one, and the two already drifted apart once before (this
is the same class of drift that commit `6cfb24c10` had to fix for other duplicated details in
this document set).

## Implementation intent
Compress both tables in `docs/03_rag_01_system_overview-part2.md` down to a short, high-level
summary with no class names, no specific config default values, and no per-file responsibility
detail — and defer all such detail to the canonical documents via an explicit cross-reference.
`part2` should describe *that* the pipeline has 5 stages and *that* an MCP layer exists, not
*how* each stage or file works internally.
