# Move OS-provisioning/build instructions out of docs/02_deployment-part1.md into a dedicated provisioning runbook

## Priority
Low

## Target files
- `docs/02_deployment-part1.md` (§1.1 "Gentoo Linux パッケージ導入", §1.3 "llama.cpp のビルド")
- A new or existing provisioning/setup runbook location (none currently exists — see Background)

## Background
`docs/02_deployment-part1.md` is a deployment/design narrative document. Verified against
current content (read 2026-08-02):
- §1.1 contains the Gentoo package list and `emerge --ask ...` command, plus a note that
  Python's `sqlite3` module may lack load-extension support and needs a USE-flag adjustment
  (`echo 'dev-lang/python sqlite' >> /etc/portage/package.use/python` + re-`emerge`).
- §1.3 contains the llama.cpp build instructions: `git clone`, `cmake -B build ...`, and
  `cmake --build build ...`.

Both sections still match the issue's description exactly — the content has not changed
since the issue was filed and the issue is not obsolete.

A search of the repository (`docs/`, `deploy/`, `rules/env.md`, top-level READMEs) found
**no existing OS-provisioning/setup runbook**. The only other "runbook" in the repo is an
unrelated operator troubleshooting runbook for workflow-deployment failure recovery
(`docs/05_agent_10_04_operations-and-observability-validation-and-troubleshooting-part1.md`
§"Workflow Deployment Runbook"), which is not a suitable home for OS-package/build
provisioning steps. `rules/env.md` currently points readers to
`docs/02_deployment-part1.md` for "導入手順・依存パッケージ・llama.cpp ビルド" and would need
its pointer updated (or left pointing at part1's new reference line) if this content moves.

## Problem
Pure OS-provisioning instructions (Gentoo package list, `emerge` invocation, llama.cpp
`git clone`/`cmake` build commands) are embedded inline in a deployment *design* document.
These instructions carry no design rationale, go stale independently of the document's
narrative purpose (OS package names/versions and llama.cpp build flags change over time),
and crowd out the one line in §1.1 that IS a design decision: the sqlite3 load-extension
USE-flag requirement, which is directly tied to the sqlite-vec adoption decision described
elsewhere in the deployment docs.

## Reason for change
Provisioning-level instructions don't convey design judgment and are better suited to a
dedicated setup/provisioning runbook that can evolve independently (e.g., on OS/package/
llama.cpp version bumps) without touching the design narrative. No such runbook currently
exists, so this change also establishes that location for future provisioning content.

## Implementation intent
- Relocate the OS-package-list/`emerge` instructions (§1.1) and the llama.cpp `git clone`/
  `cmake` build instructions (§1.3) from `docs/02_deployment-part1.md` into a dedicated
  provisioning/setup runbook, created since none exists yet.
- Leave a short reference pointer in `part1` at each relocated section, directing the
  reader to the new runbook.
- Do not relocate the sqlite3 USE-flag design note — it stays in `part1`'s main text
  exactly where it currently sits (immediately following the package list in §1.1), since
  it documents a design decision (load-extension support required for sqlite-vec), not
  mere provisioning.
- Do not change any actual provisioning command, package name, version, or build flag —
  this is a documentation relocation only.

## Implementation instructions
1. Confirm no provisioning/setup runbook already exists before creating one (re-verify at
   implementation time in case the repo has changed since this requirement was written).
2. Choose or create a provisioning runbook location consistent with the existing `docs/`
   numbering/naming convention used by `02_deployment-part1.md` / `02_deployment-part2.md`
   (e.g. a new file in the `docs/02_deployment*` family, or another location if a better
   fit is identified) — the exact filename/location is left to the implementation/planning
   phase to decide.
3. Move §1.1's package list and `emerge --ask ...` command, and §1.3's `git clone`/
   `cmake -B build ...`/`cmake --build build ...` commands, into the new runbook verbatim
   (no command changes).
4. In `part1`, replace the moved content with a short reference pointer to the new runbook
   location, keeping section numbering/headings intact for anything not moved.
5. Keep the sqlite3 USE-flag note (the `> Python の sqlite3 モジュールが...` blockquote and
   its two commands) in `part1`'s §1.1 main text, unmoved, immediately after the package-list
   reference pointer, since it is a design note tied to the sqlite-vec decision.
6. Update `rules/env.md`'s pointer to `docs/02_deployment-part1.md` for "導入手順・依存パッケージ・
   llama.cpp ビルド" if the moved content changes which document owns that information (this
   falls within docs/*.md-adjacent housekeeping the next phase should account for, though
   `rules/env.md` itself is outside `docs/*.md`).
7. Run the repo's docs consistency check (e.g. `python -m tools.check_docs_consistency`,
   if present) after the move to confirm no broken cross-references.

## Acceptance criteria
- `docs/02_deployment-part1.md` no longer contains the full Gentoo package list/`emerge`
  command (§1.1) or the llama.cpp `git clone`/`cmake` build commands (§1.3) inline.
- `part1` contains a reference pointer to the new provisioning runbook in place of each
  relocated section.
- The sqlite3 USE-flag design note remains in `part1`'s §1.1 main text, unchanged and in
  its current position relative to the (now-pointer-replaced) package list.
- The new provisioning runbook contains the relocated content, unmodified in substance
  (commands/package names/versions unchanged).
- No other section of `part1` (§1.2, §1.4, §2.x) is altered beyond what's needed for the
  relocation and reference pointers.
