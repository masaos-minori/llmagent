# Fix `test_config_reload_security_profile.py` collection error caused by stale `apply_config_changes` reference

## Priority
High

## Target files
- `tests/agent/services/test_config_reload_security_profile.py` (to be modified)
- `scripts/agent/services/config_reload.py` (reference only, not expected to change)
- `tests/agent/services/test_config_reload.py` (reference only — established mocking pattern to follow)

## Background
`tests/agent/services/test_config_reload_security_profile.py` imports
`apply_config_changes` from `agent.services.config_reload` and calls it as
`await apply_config_changes(ctx, new_cfg)` in four test methods (lines 68, 80, 92, 104).
No such symbol exists in `scripts/agent/services/config_reload.py` — confirmed by grep and by
running `PYTHONPATH=scripts pytest tests/agent/services/test_config_reload_security_profile.py -v`,
which fails at collection with:
```
ImportError: cannot import name 'apply_config_changes' from 'agent.services.config_reload'
```
All four tests in the file therefore never run, leaving the security-profile fallback behavior
(invalid/empty/numeric-string `security_profile` values preserving the current value; valid values
being applied) with zero test coverage.

## Problem
The source issue assumed the fix would be a simple rename — swap the import/call sites to
`apply_config_dict(ctx, new_cfg)` — on the theory that `apply_config_dict()` is a drop-in,
same-shape replacement. Verification against the current `config_reload.py` shows this is only
partially true, and a naive rename would still fail at runtime (not at collection, but inside the
test body):

1. **Not a standalone function.** `apply_config_dict()` is an *instance method* of
   `ConfigReloadService` (`scripts/agent/services/config_reload.py:113`), constructed as
   `ConfigReloadService(ctx)`. There is no module-level `apply_config_dict(ctx, new_cfg)` callable.
2. **Not async.** `apply_config_dict()` has signature
   `def apply_config_dict(self, new_cfg: dict[str, Any]) -> ConfigReloadOutcome` — it is
   synchronous and takes only `new_cfg` (the context is bound via `self._ctx` at construction
   time). The test's `await ...` calls must become plain calls.
3. **The test's mock context is missing `services_required`.** `apply_config_dict()`
   internally calls `self._sync_services(new_cfg)`, which reads
   `ctx.services_required.llm`, `.hist_mgr`, `.tools`, `.runtime_tools` (and, when an MCP server
   is removed, `ctx.services_required.lifecycle`). The test's current mock,
   `type("MockContext", (), {"cfg": cfg})()`, only sets `cfg` — calling `ConfigReloadService(ctx)`
   with this object and then `.apply_config_dict(new_cfg)` would raise `AttributeError` on
   `ctx.services_required`, because a bare `type(...)` instance has no such attribute (unlike the
   real `AgentContext`, whose `services_required` is a property that raises a descriptive
   `RuntimeError` only when `self.services` is `None`).
   The sibling test file `tests/agent/services/test_config_reload.py` already solves this same
   problem for the same class: it builds `ctx = MagicMock()`, sets the specific `ctx.cfg.*` fields
   the code path under test reads, sets `ctx.services_required.llm = None` (etc.) for the services
   it needs to be absent, and passes `ctx` to `ConfigReloadService(ctx)`. This is the established,
   working pattern in this codebase for testing `ConfigReloadService` and should be reused rather
   than reinvented.

`apply_config_dict()` does take a raw `dict` (matching how `new_cfg` is already built in the test),
so the specific concern flagged in the issue's "AI Implementation Instruction" — that
`apply_config_dict()` might expect a config object instead of a dict, forcing a restructure of how
`new_cfg` is built — does **not** apply. No restructuring of `new_cfg` construction is needed.

## Reason for change
The four tests in this file are the only coverage for `security_profile` reload fallback behavior
(silently preserving the current value on invalid/empty/non-enum input, applying valid values).
Because the module fails to import, `pytest` cannot even collect the file, so this behavior has no
executable regression protection today. Fixing only the import without also fixing the
call-shape mismatches (sync vs. async, method vs. function, missing `services_required` stub)
would just trade a collection-time `ImportError` for a runtime `AttributeError`/`TypeError` inside
each test body — leaving the underlying acceptance criterion ("all tests in the file pass")
unmet.

## Implementation intent
- Replace `from agent.services.config_reload import apply_config_changes` with
  `from agent.services.config_reload import ConfigReloadService`.
- Construct a `ConfigReloadService` instance per test (or via a fixture, following the pattern in
  `tests/agent/services/test_config_reload.py`) and call the synchronous
  `svc.apply_config_dict(new_cfg)` in place of `await apply_config_changes(ctx, new_cfg)`.
  Remove `await` and the `pytest.mark.asyncio` markers from the four affected test methods if they
  no longer await anything (confirm no other awaited call remains in each test body first).
- Extend `_make_ctx()` (or introduce an equivalent per-test setup) so the mock context has a
  usable `services_required` — the simplest fix consistent with existing conventions is building
  `ctx` as `MagicMock()` with `ctx.cfg` explicitly set to the real `AgentConfig` instance produced
  by the current dict-based construction (so `AgentConfig(**merged)` values are preserved exactly
  as today), and setting `ctx.services_required.llm = None`,
  `.hist_mgr = None`, `.tools = None`, `.runtime_tools = None` — mirroring
  `tests/agent/services/test_config_reload.py`'s fixture, since these tests only exercise the
  `security_profile` fallback path in `_reload_approval_settings()`/`_reload_approval_config()`,
  not live service syncing.
- Do not add a new `apply_config_changes` alias or any other backwards-compat shim to
  `scripts/agent/services/config_reload.py` — fix the test only, per the project's no-shims
  refactoring convention (also stated explicitly in the source issue).
- Do not rewrite the security-profile assertions themselves (lines checking
  `ctx.cfg.mcp.security_profile`) — only the import, construction, and call sites need to change.
