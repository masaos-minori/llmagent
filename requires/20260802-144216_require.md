# Deduplicate repeated health-probe explanatory note in docs/04_mcp_06_06_verification-methods.md

## Priority
Low

## Target files
- `docs/04_mcp_06_06_verification-methods.md` (section `## ヘルスプローブレスポンスの例`, lines ~49-133)

## Background
`docs/04_mcp_06_06_verification-methods.md` documents how to verify MCP server health via
curl-based health probes. Its "ヘルスプローブレスポンスの例" section shows one healthy
base-response example followed by five per-server "degraded" examples (shell-mcp:8009,
rag-pipeline-mcp:8010, github-mcp:8006, mdq-mcp:8013, git-mcp:8014).

## Problem
Each of the five degraded examples ends with the identical explanatory sentence, verbatim:

> `/mcp status` の `health_reason` に `operator_action_required` として反映される（表示のみ；自動的な再起動は行われない）。

This sentence carries no server-specific information — it is the same statement about how
`/mcp status` surfaces `operator_action_required`, repeated five times. This was confirmed
still present in the current file (verified by reading the file directly; the repetition is
unchanged since the issue was filed). Each of the five server-specific details (port,
dependency key, error message, `details` payload) was cross-checked against the current
source (`scripts/mcp_servers/shell/shell_server.py`, `.../rag_pipeline/rag_pipeline_server.py`,
`.../github/github_server.py`, `.../mdq/health_check.py`, `.../git/git_server.py`, and the
service URLs in `config/agent.toml`) and all match the doc exactly — no drift was found, so
no endpoint/port/dependency-key correction is needed alongside the dedup.

## Reason for change
The repeated note is a maintenance burden that grows with every additional MCP server added
to this section, and repeating it five times adds no design information beyond the first
occurrence. Consolidating it reduces doc size and the risk that future edits update the note
in some copies but not others.

## Implementation intent
State the common explanatory note once (e.g., immediately above or below the five examples,
or as a single sentence introducing the "degraded" examples as a group), then present the
per-server specific detail (port, dependency key, error message) compactly — e.g. as a
table with columns such as Server / Port / `dependencies` key / error message / `details`
payload — rather than five nearly-identical full curl+JSON blocks. Retain at least one full
worked curl+JSON example (recommend keeping the existing healthy base-response example, plus
one full degraded example such as shell-mcp) so a concrete illustration of the request/response
shape remains for readers unfamiliar with the format.
