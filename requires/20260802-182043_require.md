## Background
`docs/03_rag_03_02_query_pipeline-rag-pipeline-class-part1.md` and `part2.md` document the
`RagPipeline` class (`scripts/rag/pipeline.py`). Part1 currently contains three tables that are
verbatim, mechanical transcriptions of the class's signatures/attributes:
- "コンストラクタ" (constructor parameters), part1 lines 41-47
- "公開属性" (public attributes), part1 lines 61-70
- "公開メソッド" (public methods), part1 lines 73-81

Part2 currently contains an "HTTP RAGリクエストの詳細" table (part2 lines 108-114: endpoint,
request body shape, max attempt count, retry backoff) that is likewise a mechanical transcription
readable directly from `scripts/rag/pipeline_service.py` / `scripts/rag/http_augment.py`.

These four tables add no design/rationale value beyond what reading the source directly provides,
and increase maintenance burden (any signature change requires a doc update to avoid drift).

## Problem
The four tables listed above should be removed as pure transcription noise. However, part1's
constructor table's `module_cfg` row carries non-mechanical, valuable information — that
`module_cfg` bypasses `load_all()` / `agent.toml` (the agent-process config path) and falls back
to internal module config resolution when `None` — which must not be lost when the table is
deleted.

Verification note (important correction to the original issue): the issue asked to "add" design
rationale explaining why the MCP adapter hardcodes `rag_service_url=""` to prevent infinite HTTP
delegation loops. Checking current `docs/03_rag_03_02...part2.md` (line 49, inside the "HTTPモード
(`rag_service_url`)" table, row "無限委譲の防止") shows this rationale is **already present**:
"MCPアダプタは `rag_service_url=""` をハードコードしているため、インプロセスの `augment()` が
再度委譲することはない。" This was independently confirmed against
`scripts/mcp_servers/rag_pipeline/rag_pipeline_models.py:119`, which hardcodes
`rag_service_url=""` with the inline comment `# prevent HTTP loop when augment() is called
in-process`, and against `tests/test_rag_pipeline_mcp_service.py` (`test_rag_service_url_always_empty`,
asserting `adapter.rag_service_url == ""` specifically to prevent an HTTP loop in the MCP
process). So the rationale-addition part of the original issue is already satisfied by the
current doc content; the remaining, still-open work is only the table removal (this row is in a
different table from the one being removed, so removing the "HTTP RAGリクエストの詳細" table does
not affect it).

The `http_result_kind` classification table (part2 lines 86-91) and its "`remote_empty` is a
success, not a fallback" note (part2 lines 93-96) are confirmed accurate against
`scripts/rag/pipeline_service.py`, `scripts/rag/http_augment.py`, and `scripts/rag/pipeline.py`,
and must be kept as-is — they are not in scope for removal.

## Reason for change
Mechanical signature/attribute/method tables duplicate the source of truth (the code itself) and
drift silently when the code changes without a doc update. Removing them reduces maintenance
surface. The `module_cfg` bypass behavior and the `http_result_kind`/`remote_empty` semantics are
genuinely valuable non-obvious design notes and must survive the cleanup.
