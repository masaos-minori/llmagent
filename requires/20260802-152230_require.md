# Document the design rationale for git-mcp's write-tool guard asymmetry vs. github-mcp

## Priority
Medium

## Target files
- `docs/04_mcp_04_05_git.md` (git-mcp documentation — primary target)
- Read-only reference for comparison: `docs/04_mcp_04_01_web-search-file-read-github.md`, `docs/04_mcp_05_01_access-control-and-allowlists.md`
- Read-only reference for verification: `scripts/mcp_servers/git/git_security.py`, `scripts/mcp_servers/git/git_service.py`, `scripts/mcp_servers/github/service_security.py`, `config/git_mcp_server.toml`, `config/github_mcp_server.toml`

## Background
github-mcp's write tools are protected by several layered guards implemented in
`scripts/mcp_servers/github/service_security.py`: an `allowed_repos` allowlist
(fail-closed), a `path_denylist` for file writes, a `max_file_size_kb` cap, a
`protected_branches` check (with default-branch resolution via the API), and an
audit-log writer. These are documented in
`docs/04_mcp_04_01_web-search-file-read-github.md` (guard-config table).

git-mcp's write tools (`git_add`, `git_commit`, `git_checkout`, `git_pull`,
`git_push`) only pass through two guards in `scripts/mcp_servers/git/git_security.py`:
an `allowed_repo_paths` path-prefix allowlist and a global `read_only` flag. There is
no protected-branch check, no path denylist, no file-size cap, no force-push
restriction, and no per-tool differentiation for the more dangerous operations
(`git_checkout` / `git_pull` / `git_push`) — all five write tools share one
common guard path (`_WRITE_TOOLS` in `git_service.py`).

`docs/04_mcp_04_05_git.md` (line 89, "実装上の補足" section) already states this
asymmetry as a fact: "書き込み系5ツール...を他の書き込みツールと区別する追加ガード
（例: 保護ブランチ・force push 制限）は実装されていない。(Explicit in code)". This
sentence records *that* the guards are absent, but not *why* — it does not say
whether this is an accepted, intentional design decision (e.g., "local git
operations are the user's own responsibility, unlike GitHub operations which act
on a shared remote repository") or an unimplemented safety feature that is still
pending.

A related historical requirement, `requires/done/20260606_03_require.md` ("Git /
GitHub の危険操作ガードと artifact flow 整備"), proposed defining protected-branch,
force-push-ban, and allowed-repository policy for *both* Git and GitHub MCP
together. Only github-mcp appears to have received these guards in the current
codebase — git-mcp did not, and no document explains whether that was a deliberate
scope narrowing or an incomplete rollout.

## Problem
The current documentation records the guard gap as a neutral fact ("not
implemented") without attaching any design rationale. Per `rules/coding.md`'s
"Current behavior" classification rule, an undifferentiated gap note like this
must be resolved into one of five categories (accepted spec / implementation fix
required / documentation fix required / issue already tracked / obsolete) rather
than left as an unlabeled gap. Today it is none of these — it is an open question.
This creates risk in both directions: if the gap is actually a safety oversight,
it may sit unaddressed indefinitely because it reads as "known and presumably
fine"; if it is intentional, engineers or reviewers unaware of the rationale may
keep re-flagging it as an apparent regression or oversight.

## Reason for change
This is a documentation/design-classification gap, not a code defect, so it does
not require new guard logic to fix. It does require someone able to confirm design
intent (the responsible author/team) to state, on the record, why git-mcp's
posture differs from github-mcp's — or to confirm that no such decision was ever
made, in which case the gap should be tracked as pending implementation work
instead of documented as accepted.

## Implementation intent
Do not invent a rationale. The available context (issue file, current docs, prior
requirement `20260606_03`) does not contain enough information to determine
whether the asymmetry is (a) an accepted design decision under a
"local-git-operations-are-user-risk" premise, or (b) unfinished work stemming from
the 20260606 requirement's guard-parity intent, which was applied to github-mcp
but not carried through to git-mcp. Because this cannot be resolved from source
alone, the next phase must either:
1. Obtain an explicit confirmation from the responsible design owner/team on which
   interpretation is correct, and then document that confirmed answer directly in
   `docs/04_mcp_04_05_git.md` next to the existing line-89 gap note, replacing the
   bare "not implemented" statement with the confirmed rationale; or
2. If no such confirmation can be obtained during this workflow, register the item
   explicitly as a "Needs Confirmation" note in the document (clearly labeled, not
   asserted as either accepted-spec or implementation-required) and escalate for
   human decision, per `rules/coding.md`'s guidance that ambiguous "Current
   behavior" gaps default to being tracked rather than silently left ambiguous.

## Implementation instructions
- Attempt to determine or confirm the design intent behind git-mcp's narrower
  guard set. Sources to check/consult, in order:
  - Any commit messages, PR descriptions, or design notes near the introduction of
    `git_security.py` / `service_security.py` that discuss scope decisions.
  - Whether `requires/done/20260606_03_require.md`'s "Git / GitHub" scope was
    later narrowed to github-mcp only in a subsequent plan/implementation
    document (search `plans/`, `implementations/`, `implementations/done/` for
    references to git-mcp protected-branch or force-push guards).
  - If no such trail exists and no human owner is reachable within this
    workflow's scope, treat the intent as unconfirmed.
- If intent is confirmed as intentional (accepted risk-acceptance decision):
  - Update `docs/04_mcp_04_05_git.md`'s "実装上の補足" section (near line 89) to
    replace/augment the current bare "not implemented" sentence with an explicit
    statement of the accepted rationale (e.g., local git operations act on the
    user's own local working copy and are considered the user's responsibility to
    manage, unlike github-mcp write tools which act on a shared remote
    repository/branch that other collaborators depend on).
  - Do not remove the existing "(Explicit in code)" factual note — augment it with
    the rationale, keeping the factual/rationale distinction clear.
- If intent is confirmed as an unimplemented safety gap (not intentional):
  - Do not implement the guards as part of this requirement (out of scope, per the
    source issue).
  - Instead, file a separate follow-up issue under `issues/` describing the
    concrete guard parity work needed (protected-branch check, force-push
    restriction, path denylist, file-size cap for git-mcp write tools), and
    cross-reference it from `docs/04_mcp_04_05_git.md`'s line-89 note per the
    "Issue already tracked" classification in `rules/coding.md`.
- If intent cannot be confirmed within this workflow (no accessible design owner,
  no conclusive historical trail): update `docs/04_mcp_04_05_git.md` to add an
  explicit, clearly labeled "Needs Confirmation" note next to the existing line-89
  gap statement, stating that whether this asymmetry is intentional or an
  unimplemented gap is unresolved and requires a decision from the responsible
  owner. Do not assert either interpretation as fact in this case.
- In all cases, do not modify `scripts/mcp_servers/git/` guard logic, `git_security.py`,
  `git_service.py`, or `config/git_mcp_server.toml` as part of this requirement —
  this requirement is documentation-scoped only; any guard implementation is out of
  scope and must go through a separate issue/requirement cycle.

- The existing factual "(Explicit in code)" statement at/near line 89 remains

- No changes are made to git-mcp or github-mcp source code, configuration, or
