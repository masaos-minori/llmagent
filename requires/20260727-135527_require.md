## Background

- `DiagnosticStore` (in `scripts/agent/diagnostic_store.py`) defines a method `save_loop_guard_hint(session_id, reason, turn_count)` that persists a diagnostic row with `kind="loop_guard_hint"`.
- The actual tool loop guard logic, in `scripts/agent/tool_loop_guard.py`, implements its own private helper `_save_guard_hint` which calls `ctx.diagnostics.save(ctx.session.session_id, "guard_hint", json_dumps(payload))` directly — using `kind="guard_hint"`, not `kind="loop_guard_hint"`, and not going through `DiagnosticStore.save_loop_guard_hint` at all.
- A repository-wide search (`grep -rn "save_loop_guard_hint" --include="*.py"`) confirms the only caller of `save_loop_guard_hint` is the unit test `tests/test_diagnostic_store.py::test_save_loop_guard_hint`; there is no production call site.
- This discrepancy was already flagged as a documentation "Needs confirmation" item (NC-012) in `docs/00_governance_07_needs-confirmation-inventory.md` and described in `docs/05_agent_10_05_operations-and-observability-monitoring.md:92`.

## Problem

- `save_loop_guard_hint` is effectively dead production code: it exists, is tested in isolation, but is never invoked by any real code path.
- The `kind` value it would produce (`loop_guard_hint`) never actually appears in the diagnostics table in practice, since the real tool loop guard writes `kind="guard_hint"` via a different, private code path.
- This creates two risks:
  1. **Confusion for maintainers/operators**: anyone reading `DiagnosticStore`'s public API or querying diagnostics by `kind="loop_guard_hint"` (e.g. for monitoring/alerting) will get no results, while the actual data lives under `kind="guard_hint"`.
  2. **Maintenance burden**: the unused method and its dedicated test must be kept in sync with the real save-path's payload shape even though they are never exercised together, increasing the chance of silent drift.

## Reason for Change

- The current state is confirmed by source inspection (not just documentation claim): `save_loop_guard_hint` has zero production callers, while `tool_loop_guard.py` independently persists loop-guard diagnostics under a different `kind` string using a different call path.
- Leaving this unresolved keeps the NC-012 "Needs confirmation" item open indefinitely and leaves misleading/inconsistent public API surface in `DiagnosticStore`.

## Implementation Intent

- Decide and implement one of two resolutions for `DiagnosticStore.save_loop_guard_hint`:
  1. **Remove it** (along with its dedicated test) as dead code, since `tool_loop_guard.py` already has its own working save path (`_save_guard_hint` / `kind="guard_hint"`); or
  2. **Wire it in**: refactor `tool_loop_guard.py`'s `_save_guard_hint` to call `DiagnosticStore.save_loop_guard_hint` instead of `ctx.diagnostics.save(..., "guard_hint", ...)` directly — but note this would change the persisted `kind` value from `guard_hint` to `loop_guard_hint`, which is a behavior change that must be checked against any downstream consumers (dashboards, alert queries, other tests) that filter on `kind="guard_hint"`.
- This requirement document only requires investigating and deciding between the two options and implementing the chosen one; it does not mandate a specific outcome. Once code is fixed, update the two affected documentation sections (`docs/05_agent_10_05_operations-and-observability-monitoring.md` and the NC-012 entry in `docs/00_governance_07_needs-confirmation-inventory.md`) to remove the "Needs confirmation" label and record the resolution — but that documentation update is out of scope for this document-only workflow phase and should happen in the implementation phase.
