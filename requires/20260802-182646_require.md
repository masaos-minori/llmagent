# Simplify verbatim method/SQL tables in docs/03_rag_03_06 parts 1 and 2

## Priority
Medium

## Target files
- `docs/03_rag_03_06_query_pipeline-helpers-and-cache-part1.md`
- `docs/03_rag_03_06_query_pipeline-helpers-and-cache-part2.md`

## Background
The source issue (`issues/20260802-080020_rag_03_06_cleanup_and_cache_freshness_restart_timing.md`)
raised two concerns about `docs/03_rag_03_06_query_pipeline-helpers-and-cache-part1.md` /
`-part2.md`: (1) both files transcribe `SemanticCache` / `RagRepository` / `RagScorer` / `RagLLM`
methods and raw SQL queries verbatim in tables, and (2) the CLI-ingest cache-freshness section
allegedly lacked the specific detail that a running query process's `SemanticCache` requires a
restart or explicit `invalidate()` call to pick up a CLI re-ingest.

Verification against the current repo state (as of 2026-08-02) found the two concerns are no
longer equally valid:

- **Concern 2 (cache-freshness restart detail) is already resolved.** The current
  `part1.md` §"CLI インジェスト後のキャッシュ鮮度" (lines 60-62) already states, in detail, that
  `rag_delete_document` only invalidates the cache of the calling MCP process; that CLI ingestion
  runs in a separate process with no access to that in-memory cache; and that the rag-pipeline-mcp
  service (or agent/subprocess-mode MCP server) must be restarted for immediate query freshness
  after CLI ingest, since this is not automatic. This is at least as specific as, and arguably more
  detailed than, the exact wording the issue proposed adding. No further edit is needed here.
- **Concern 1 (verbatim tables) is still valid and unresolved.** Both files still contain full
  mechanical transcriptions of source code:
  - `part1.md` lines 39-46: a full method/property table for `SemanticCache`
    (`lookup`, `put`, `prune`, `size`, `invalidate`, `generation`) with signatures and descriptions.
  - `part2.md` lines 36-39: a raw SQL table for `RagRepository.vector_search` / `fts_search`.
  - `part2.md` lines 44-46, 52-54: tables of Japanese-FTS5 tokenization constants and the
    `tokenize_pos_filter` signature.
  - `part2.md` lines 58-61: a full public-method table for `RagRepository`
    (`vector_search`, `fts_search`) plus a bullet list of module-level wrapper functions.
  - `part2.md` lines 72-74: a method table for `RagScorer.rrf_merge`.
  - `part2.md` lines 90-95, 99-102: method tables for `RagLLM` (`expand_queries`,
    `cross_encoder_rerank`, `summarize_tool_result`, `refine_context`) and module-level functions
    (`get_embedding`, `summarize_tool_result`).

  Also verified: unlike the `05_agent_*` and `06_eventbus_*` doc categories, there is no
  `03_rag_*_reference-api*.md` document for RAG (confirmed via `docs/03_rag_00_document-guide.md`
  and a repo-wide search for "Reference API" / "リファレンスAPI"). So a cleaned-up section should
  point readers to the source file path directly (as the existing `RagLLM` sub-section in
  `part2.md` §7.3 already does — "実装は以下にある… `scripts/rag/llm_client.py`"), not to a
  reference-API doc that doesn't exist.

## Problem
Two of the classes/helpers documented in `docs/03_rag_03_06` parts 1 and 2 are described with
full mechanical tables of method signatures and raw SQL text, duplicating what's already
authoritative in `scripts/rag/cache.py` and `scripts/rag/repository.py`. This transcription adds
maintenance burden (the doc silently drifts whenever a signature or query changes) without adding
interpretive value beyond what the source already states.

## Reason for change
Per this repo's documentation conventions, docs should carry design intent and non-obvious
behavior, not restate code. Verbatim tables are the kind of content the `docs_review_rag.md`
review flagged as "要約候補" (summarization candidates) precisely because they add no
information not already in source, while increasing the chance of drift.

## Implementation intent
For each affected sub-section, replace the full method/SQL table with a short prose summary of
the class's/function group's responsibility (one to two sentences), any design judgment worth
keeping (e.g. why `RagRepository` centralizes all SQL, why Sudachi is lazy-loaded, the FTS5
token-count constant if it reflects a real operational limit worth calling out), and a pointer to
the source file (e.g. `scripts/rag/repository.py`) for exact signatures — following the pattern
already used for the `RagLLM` sub-section in `part2.md` §7.3. Do not remove genuinely
non-obvious behavioral notes (e.g. the "混同注意" `result_source` note in `part2.md` — out of
scope, tracked in a separate issue; the "テストで確認されている挙動" note under `SemanticCache`
in `part1.md`, which documents `invalidate()`'s tested behavior and is a judgment call, not a
mechanical transcription — keep or fold into prose, do not delete outright).

   stating: `SemanticCache` provides `lookup()`/`put()` (implementing `CacheService`), FIFO
   `prune()`-on-put eviction, a `size` property, and `invalidate()` (bumps a `generation` counter
   and clears all entries atomically under a lock) plus a `generation` property for observability.
   Point to `scripts/rag/cache.py` for exact signatures. Preserve the existing
   "テストで確認されている挙動" sentence (or an equivalent one) describing `invalidate()`'s
   tested effect, since it is a verified behavioral claim, not a mechanical transcription.
2. Do **not** modify the "CLI インジェスト後のキャッシュ鮮度" section (`part1.md` lines 60-62) —
   it already contains the restart/invalidation detail the source issue asked for and has been
   verified accurate against `scripts/rag/cache.py`'s `invalidate()` implementation (see
   Background). Leave it as-is.
3. In `part2.md` §7.1 (`RagRepository`), replace the SQL-query table (lines 36-39) and the
   public-method table (lines 58-61) with prose: one sentence on `RagRepository`'s responsibility

5. In `part2.md` §7.2 (`RagScorer`) and §7.3 (`RagLLM`), replace the remaining method tables
