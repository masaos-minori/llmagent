# Normalize chunk generation to preserve original text and normalized search text

## Priority
High

## Target files
- `scripts/rag/ingestion/chunk_english.py`
- `scripts/rag/ingestion/chunk_japanese.py`
- `scripts/rag/ingestion/chunk_splitter.py`

## Background
The SQLite schema (`scripts/db/schema_sql.py`) separates original readable content from search-normalized text on the `chunks` table:

- `chunks.content` — original text, intended for LLM context.
- `chunks.normalized_content` — search-normalized text.

The FTS5 sync triggers (`chunks_ai`, `chunks_ad`, `chunks_au` in `scripts/db/schema_sql.py`) index `COALESCE(normalized_content, content)`, i.e. they prefer `normalized_content` when present and fall back to `content` otherwise.

For this contract to work correctly, chunk generation must produce both values independently: the original text must be preserved verbatim for LLM/embedding use, while a separately normalized version must be produced for FTS5 search quality. Verified against current source, the three chunkers do not consistently honor this contract:

1. **English chunking** (`scripts/rag/ingestion/chunk_english.py`): `_chunk_english()` (lines 26-31) returns `list[str]`, where each entry has already had stopwords removed via `_filter_stopwords_en()`. The original, unfiltered text is never retained or returned, so `content` ends up storing stopword-filtered text instead of the original readable text.

2. **Japanese chunking** (`scripts/rag/ingestion/chunk_japanese.py`): `_merge_ja_sentence_pairs()` (lines 77-100) declares a local `result: list[tuple[str, str]] = []` but the loop bodies (`_emit_and_start_new`, line 109; `_merge_tail_into_last`, lines 126-133) append to `self._result` instead of the local `result`. As a result, the local `result` returned by the method is populated only when the final trailing buffer meets `_min_chunk` (lines 96-97) — every chunk emitted mid-loop via `_emit_and_start_new` is written to `self._result` and never returned. `self._result` is also never reset per call, so it can carry stale state across invocations. This is a functional bug: `_chunk_japanese()` effectively drops all but at most the last chunk of a Japanese document.

3. **Markdown heading chunking** (`scripts/rag/ingestion/chunk_splitter.py`): `_chunk_markdown_by_heading()` (lines 188-205) returns `list[str]` (original section text only). In `_build_text_triples()` (lines 244-256), markdown chunks are always emitted as `("text", c, "")` (line 251) — `normalized_content` is hard-coded to the empty string, so markdown-sourced chunks never get FTS5-normalized text regardless of language.

## Problem
Chunk generation does not consistently produce the `(original, normalized)` pair required by the `chunks.content` / `chunks.normalized_content` schema and the FTS5 `COALESCE` trigger design:

- English chunks lose the original readable text (only the stopword-filtered form survives).
- Japanese chunks lose most chunks entirely due to the `self._result` / local `result` state-splitting bug in `_merge_ja_sentence_pairs()`.
- Markdown heading chunks never populate `normalized_content`, regardless of the section's language.

## Reason for change
This breaks the intended separation between LLM-facing content and FTS5-facing normalized search text:

- English `chunks.content` currently stores degraded (stopword-stripped) text instead of the original text needed for LLM context and embeddings.
- Japanese `chunks.content` is affected by a state-management bug that silently discards most chunks produced from a document, which directly harms both LLM context and FTS5 search recall/completeness for Japanese documents.
- Markdown-sourced chunks (which use `.md` / `.markdown` / `.mdx` heading-based chunking unconditionally, per `_is_markdown_source()`) never benefit from normalized search text, weakening FTS5 search quality for markdown-heavy sources (e.g. docs).

## Implementation intent
Make the chunk contract language-independent and consistent across all three chunk sources (English, Japanese, Markdown), so that every text-chunking path yields `(original, normalized)` pairs, and `chunk_splitter.py`'s payload-building step writes `content = original` and `normalized_content = normalized or None` uniformly regardless of source.

Key behavioral intents:
- LLM context (`content`) always uses original, unmodified text.
- FTS5 (`normalized_content`) always prefers normalized text when available (falls back to `content` via the existing DB trigger `COALESCE` when normalized text is absent/None).
- Embedding generation uses original `content`, not normalized text.
- Japanese chunk merging must use a single, consistent state-holding mechanism (local variable, not split between instance and local state) so no chunks are silently dropped.

## Implementation instructions
1. **`chunk_english.py`**:
   - Change `_chunk_english()` to return `list[tuple[str, str]]` instead of `list[str]`.
   - Preserve the original (pre-stopword-removal) merged/split text as the first tuple element.
   - Compute the stopword-filtered text (via `_filter_stopwords_en()`) as the second tuple element (normalized text).
   - Apply the `_min_chunk` length filter based on the original text's length (the current filter is based on the filtered text — decide and document which length governs filtering, consistent with Japanese chunking's use of original-text length in `_merge_ja_sentence_pairs`).
   - Update call sites of `_chunk_english()` accordingly (including its use inside `_chunk_markdown_by_heading()`'s oversized-section fallback in `chunk_splitter.py`).

2. **`chunk_japanese.py`**:
   - Keep the public contract of `_chunk_japanese()` returning `list[tuple[str, str]]`.
   - Remove the `_result` instance attribute entirely (delete its declaration at the mixin class level and all references in `_emit_and_start_new()` and `_merge_tail_into_last()`).
   - Fix `_merge_ja_sentence_pairs()` so the local `result` list declared inside the method is the single source of truth: `_emit_and_start_new()` and `_merge_tail_into_last()` must append to / mutate this local `result` (e.g. by passing it as a parameter or restructuring these as inline logic within `_merge_ja_sentence_pairs()`), not a `self.` attribute.
   - Ensure no state persists across separate calls to `_merge_ja_sentence_pairs()` / `_chunk_japanese()` beyond what is explicitly reset at the start of each call (`_orig_buf`, `_norm_buf`).

3. **`chunk_splitter.py`**:
   - Change `_chunk_markdown_by_heading()` to return `list[tuple[str, str]]`.
   - For each markdown section, keep the original markdown section text (including heading) as `content`.
   - For the normalized text: detect language per section (or reuse the document-level `lang` field already available via `ChunkDocument`) and generate Sudachi-normalized text (via the Japanese mixin's normalization helper, e.g. `_normalize_ja_sentence`) for Japanese sections, or English-normalized text (via the English mixin's stopword-filter helper) for English sections.
   - When a section exceeds `_md_snippet_max_chars` and falls back to `_chunk_english()` (line 204), propagate that helper's now-tuple output directly instead of wrapping it in `("text", c, "")`.
   - Update `_build_text_triples()` (lines 244-256) so the markdown branch consumes `(original, normalized)` tuples from `_chunk_markdown_by_heading()` instead of hard-coding `norm=""`.
   - Confirm `_build_chunk_payload()` (line 303-321) continues to write `content = chunk_content` (original) and `normalized_content = norm_content or None` — this part of the contract already matches the requirement and should not need to change, but must be re-verified once the upstream chunkers change their return shapes.

4. Update all call sites and any local type annotations affected by the `list[str]` → `list[tuple[str, str]]` signature changes (e.g. `_build_text_triples()`, `_build_code_triples()` is unaffected since code chunking is out of scope).

## Acceptance criteria
- `_chunk_english()` returns `list[tuple[str, str]]` where the first element is original readable text and the second is stopword-filtered normalized text.
- `_chunk_japanese()` returns `list[tuple[str, str]]` with all chunks correctly emitted (no chunks silently dropped due to state-handling bugs), and no longer references `self._result` anywhere in the module.
- `_merge_ja_sentence_pairs()` uses only a local `result` variable for chunk accumulation; the `_result` instance attribute is removed from the class.
- `_chunk_markdown_by_heading()` returns `list[tuple[str, str]]`, producing non-empty `normalized_content` for markdown sections (Sudachi-normalized for Japanese sections, English-normalized for English sections), while preserving the original markdown section text (with heading) as `content`.
- `chunking_strategy = "heading"` is preserved for markdown-sourced documents.
- `chunk_splitter.py`'s `_build_chunk_payload()` continues to write `content = original` and `normalized_content = normalized or None` for every chunk_type/source combination.
- `chunks.content` remains suitable as-is for LLM context and embedding generation (original text, not stopword-filtered or otherwise altered).
- `chunks.normalized_content` remains suitable for FTS5 indexing (normalized/stopword-filtered form, or `None` to trigger the existing `COALESCE(normalized_content, content)` fallback).

## Tests
- Add/update unit tests for `_chunk_english()` verifying the returned tuples: first element matches original paragraph/sentence text (before stopword removal), second element matches the stopword-filtered form.
- Add/update unit tests for `_chunk_japanese()` / `_merge_ja_sentence_pairs()` specifically covering the multi-chunk case (input long enough to require more than one `_emit_and_start_new()` call) to confirm all chunks are present in the returned list — this is a regression test for the current state-splitting bug.
- Add/update unit tests for `_chunk_markdown_by_heading()` confirming both a Japanese-content markdown section and an English-content markdown section produce non-empty `normalized_content`, and that the original section text (with heading, unmodified) is preserved as `content`.
- Add/update an ingestion-pipeline-level test (e.g. in `tests/test_rag_ingestion_pipeline.py` or `tests/test_ingester.py`, whichever already covers chunk_splitter output) verifying that written chunk JSON files have `content` equal to original text and `normalized_content` populated (or `None`) as expected for each of the three source types (English text, Japanese text, Markdown).
- Run the full existing test suite (`uv run pytest`) to ensure no regressions in dependent modules (`ingester.py`, `repository.py`, `models_data.py`, and FTS-related tests such as `tests/test_fts_japanese.py`, `tests/test_fts_sync.py`, `tests/test_fts_fallback.py`).
