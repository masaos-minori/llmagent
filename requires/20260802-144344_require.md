# Clarify that `fail_closed` in docs/04_mcp_06_10 is a general design term, not a literal config key

## Priority
Low

## Target files
- docs/04_mcp_06_10_settings-with-high-operational-impact.md

## Background
`docs/04_mcp_06_10_settings-with-high-operational-impact.md` contains a table titled "Settings with High Operational Impact" listing literal configuration keys (`allowed_dirs`, `command_allowlist`, `repo_allowlist`, `allowed_repo_paths`, `read_only`, `tool_definitions_strict`, etc.) alongside their operational effect. Row 19 of that table reads:

```
| `allowed_repos` = `[]` + `fail_closed` | すべてのGitHub書き込みが拒否される |
```

Because every other cell in the first column is a literal, verifiable config key rendered in backticks, presenting `` `fail_closed` `` in the same style strongly implies it is also a literal config key name, parallel to `allowed_repos`.

## Problem
`fail_closed` (with underscore, formatted as code) is not an actual configuration key anywhere in the codebase. Verification performed:

- `grep -rn "fail_closed" config/*.toml` → no matches. None of the `.toml` config files (`config/github_mcp_server.toml`, `config/git_mcp_server.toml`, `config/cicd_mcp_server.toml`, `config/web_search_mcp_server.toml`) define a `fail_closed` key.
- `grep -rn "fail_closed" scripts/agent/config_dataclasses.py` → no dataclass field is named `fail_closed`. The relevant GitHub-write-related field is `approval_github_allowed_repos` (comment: "empty = deny all (fail-closed)"); the GitHub MCP server's own field is `allowed_repos` (in `config/github_mcp_server.toml`, comment: "Empty list = deny all (fail-closed)").
- Every other occurrence of the string across the repo (`scripts/mcp_servers/**`, `scripts/agent/repl_health.py`, `tests/**`, `docs/04_mcp_05_03_fail-open-fail-closed-and-risk-tiers.md`) uses the hyphenated form "fail-closed" as a descriptive/design-policy adjective (e.g., "empty allowlist = deny all (fail-closed)"), never as a literal identifier that is set, read, or parsed from config.
- `scripts/agent/repl_health.py` even uses `fail_closed_empty` as an internal Python variable name (a list of setting names that are "fail-closed when empty"), which is unrelated to any config schema key — it is local bookkeeping, not a documented config option.

Conclusion: `fail_closed` is a general design/behavior term (fail-closed policy: deny access when an allowlist is empty), not a configuration key. Only `allowed_repos` is the real, literal config key that triggers this behavior when empty. The doc's current phrasing conflates the two, which could mislead a developer into searching for a nonexistent `fail_closed` setting.

## Reason for change
Ambiguous documentation wastes developer time (searching for a config key that does not exist) and risks under-documenting the real key if a reader assumes `fail_closed` is already the full story. This is a low-risk, quick documentation fix that removes a clear source of confusion identified during the MCP docs review (source: `docs_review_mcp.md` §"Needs confirmation: fail_closedという語が設定キーか一般用語か(06_10)").

## Implementation intent
Edit the affected table row (and only that row / its immediate context) in `docs/04_mcp_06_10_settings-with-high-operational-impact.md` so it no longer presents `fail_closed` as if it were a literal config key formatted identically to real keys. Either:
- Reword the row to reference only the real key (`allowed_repos`) and describe the fail-closed *behavior* in prose (not as a second backticked key), or
- Keep the row similar but add an explicit disambiguating note (inline or as a table footnote) stating that "fail_closed" here refers to the general fail-closed design policy described in `docs/04_mcp_05_03_fail-open-fail-closed-and-risk-tiers.md`, not a literal configuration key.

Do not invent or rename any configuration key. Do not touch any other row in the table unless the same ambiguity is present there (verify before touching).

   `| \`allowed_repos\` = \`[]\` + \`fail_closed\` | すべてのGitHub書き込みが拒否される |`
2. Rewrite the first column so `fail_closed` is not rendered as a second literal key in backticks next to `allowed_repos`. Suggested phrasing direction (adjust to match the document's existing tone/style, in Japanese as the rest of the doc is written):

   or add a short parenthetical / footnote clarifying: "`fail_closed`はここでは設定キー名ではなく、`allowed_repos`が空の場合に全拒否とする一般的な設計方針（fail-closedポリシー）を指す。" with a cross-reference to `docs/04_mcp_05_03_fail-open-fail-closed-and-risk-tiers.md`.

5. This is a documentation-only change. Do not modify any source code, config files, or other `docs/*.md` files.
