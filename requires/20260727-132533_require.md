# Fix Orchestrator finally block overwriting pending_approval/halted task status with completed

## Priority

High

## Target Files

- `scripts/agent/orchestrator.py:291-307` — `Orchestrator._handle_workflow_engine()` `finally` block unconditionally writes `completed`/`failed` based only on `error_kind`
- `scripts/agent/workflow/workflow_engine.py:126-154` — `WorkflowEngine.run()`, reference for correct status transitions (`pending_approval`, `halted`, `failed`, `completed`)
- `scripts/agent/workflow/approval_ops.py:191-204` — `find_all_pending_approvals()`, depends on `tasks.status = 'pending_approval'` staying intact

## Background

`WorkflowEngine.run()` (`scripts/agent/workflow/workflow_engine.py:126-154`) manages task status transitions per exception type:

- On `WorkflowPendingApprovalError`: `_gate_approval()` (`workflow_engine.py:156-187`) already calls `store.update_task_status(task_id, "pending_approval")` before raising. `run()` re-raises without touching status (`except WorkflowPendingApprovalError: raise`, line 146-147).
- On `(WorkflowHaltError, WorkflowTimeoutError)`: `run()` calls `update_task_status(task_id, "halted")` then re-raises (line 148-150).
- On any other `Exception`: `run()` calls `update_task_status(task_id, "failed")` then re-raises (line 151-153).
- On normal completion: `update_task_status(task_id, "completed")` (line 154).

The caller, `Orchestrator._handle_workflow_engine()` (`scripts/agent/orchestrator.py`), catches these exceptions at lines 291-294:

```python
except WorkflowPendingApprovalError as exc:
    self._handle_workflow_approval_pending(exc, session_id)
except WorkflowHaltError as exc:
    self._handle_workflow_halt(exc)
finally:
    try:
        _task = task
        if _task is not None and _task.task_id:
            if error_kind is not None:
                store.update_task_status(_task.task_id, "failed")
            else:
                store.update_task_status(_task.task_id, "completed")
    except Exception as e:
        logger.warning("Failed to update task status on engine exit: %s", e)
    self._deactivate_workflow(ctx)
    store.close()
```

`error_kind` is a local variable set only inside `execute_fn` (via `self._process_turn()`), used to distinguish success/failure of the turn's LLM processing. It has no relationship to `WorkflowPendingApprovalError` or `WorkflowHaltError`, both of which are raised by the engine itself (from `_gate_approval` or stage retry exhaustion) independent of `execute_fn`'s outcome. `_handle_workflow_approval_pending()` and `_handle_workflow_halt()` (verified at `orchestrator.py:372-412`) do not update task status themselves — they only log, emit audit events, and reset `ctx.workflow` state.

## Problem

When a turn completes its `execute` stage normally (so `error_kind` stays `None`) and then hits the approval gate, `WorkflowPendingApprovalError` is caught at line 291 without any status write. Control falls into `finally`, where `error_kind is None` is true, so `store.update_task_status(_task.task_id, "completed")` runs unconditionally — overwriting the `pending_approval` status that `_gate_approval()` had just set moments earlier.

The same happens for `WorkflowHaltError`: `_handle_workflow_halt()` does not write status, so `finally` overwrites the previously-set `halted` status back to `completed`.

Confirmed impact:
- `find_all_pending_approvals()` (`scripts/agent/workflow/approval_ops.py:191-204`) filters on `WHERE t.status = 'pending_approval' AND a.status = 'pending'`. Once the task's status is silently rewritten to `completed`, this task is invisible to that query, breaking `StartupOrchestrator._recover_pending_approvals()` after a process restart.
- Halted tasks are recorded as `completed`, corrupting audit trails and violating the auditability/recoverability requirements referenced by ADR-Workflow-Mandatory (`docs/05_agent_03_03_turn-processing-flow-workflow-engine-part1.md`).
- No existing test in `tests/test_orchestrator.py` guards against this overwrite.

## Reason for Change

Silent DB state corruption on a Critical-severity path (approval/halt bookkeeping) undermines the workflow engine's core guarantee that task status accurately reflects its suspension/termination reason. This must be fixed to keep approval recovery and audit logs correct.

## Implementation Intent

Make the `finally` block in `Orchestrator._handle_workflow_engine()` status-transition-aware: it must only write `completed`/`failed` when the engine actually finished in one of those two terminal states from the `execute_fn`/`verify_fn` path. It must NOT overwrite a status that `WorkflowEngine` (via `_gate_approval` or its own except-blocks) already set to `pending_approval` or `halted`.

Preferred approach: track which exception (if any) terminated the workflow run, and skip the `finally` status write entirely when the run ended via `WorkflowPendingApprovalError` or `WorkflowHaltError` (since those cases already have the correct terminal status written by the engine). Only perform the `error_kind`-based `completed`/`failed` write when neither of those two engine-level exceptions occurred.

## Implementation Instructions

1. In `scripts/agent/orchestrator.py`, inside `_handle_workflow_engine()`, introduce a flag (e.g. `engine_status_handled: bool = False`) initialized before the `try` block alongside `error_kind`/`is_partial`/`task`.
2. Set `engine_status_handled = True` inside both the `except WorkflowPendingApprovalError as exc:` branch and the `except WorkflowHaltError as exc:` branch (lines ~291-294), since in both cases `WorkflowEngine` has already persisted the correct terminal status (`pending_approval` or `halted`) before raising.
3. In the `finally` block (lines ~295-307), guard the existing `store.update_task_status(...)` call so it only runs when `engine_status_handled` is `False`:
   ```python
   finally:
       try:
           _task = task
           if _task is not None and _task.task_id and not engine_status_handled:
               if error_kind is not None:
                   store.update_task_status(_task.task_id, "failed")
               else:
                   store.update_task_status(_task.task_id, "completed")
       except Exception as e:
           logger.warning("Failed to update task status on engine exit: %s", e)
       self._deactivate_workflow(ctx)
       store.close()
   ```
4. Do not change the behavior for the case where `await engine.run(...)` raises any other exception not caught by the two `except` clauses (it propagates out of `_handle_workflow_engine()` entirely — confirm this is intentional/unchanged and out of scope for this fix; the `finally` block still runs for cleanup, but `engine_status_handled` stays `False` since only the two named `except` clauses are affected).
5. Add a short comment above the flag or the guarded write explaining why: "WorkflowEngine already persisted the correct terminal status (pending_approval/halted) before raising; do not overwrite it here."

## Acceptance Criteria

- [ ] When `WorkflowEngine.run()` raises `WorkflowPendingApprovalError` during a normal (non-error) turn, the task's DB status remains `pending_approval` after `_handle_workflow_engine()` returns — it is not overwritten to `completed`.
- [ ] When `WorkflowEngine.run()` raises `WorkflowHaltError` (or `WorkflowTimeoutError` propagated as halted), the task's DB status remains `halted` after `_handle_workflow_engine()` returns — it is not overwritten to `completed`.
- [ ] Normal successful completion (no exception) still results in `completed` status being written.
- [ ] A turn where `error_kind` is set (execute stage failure) still results in `failed` status being written, when the engine did not itself raise `WorkflowPendingApprovalError`/`WorkflowHaltError`.
- [ ] `find_all_pending_approvals()` continues to return tasks correctly after a pending-approval turn (regression check that the fix does not break the query's assumptions).

## Tests

  - Simulate `WorkflowEngine.run()` raising `WorkflowPendingApprovalError` after the store already has status `pending_approval` for the task; assert the task's final status queried from the store is still `pending_approval`, not `completed`.
  - Simulate `WorkflowEngine.run()` raising `WorkflowHaltError` after the store already has status `halted`; assert the final status is still `halted`.
  - Simulate normal completion; assert final status is `completed`.
  - Simulate `error_kind` being set (execute failure) with no engine-level exception; assert final status is `failed`.
- Optionally add a regression test around `find_all_pending_approvals()` (`scripts/agent/workflow/approval_ops.py`) confirming a task left in `pending_approval` state via `_handle_workflow_engine()` is returned by the query.
