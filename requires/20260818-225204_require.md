# Unify FAIL/WARN/OK classification in StartupOrchestrator._report_readiness Readiness Summary

## Priority
Medium

## Target files
- `scripts/agent/startup.py` (`StartupOrchestrator._report_readiness`, `StartupOrchestrator._check_services`)
- Test file(s) covering `scripts/agent/startup.py` (e.g. `tests/agent/test_startup.py` or the existing test module for this class — confirm actual path during implementation)

## Background
`_report_readiness()` prints a 4-line "Readiness Summary" after startup checks complete: Security audit, Service readiness, Tool discovery, RAG consistency. Each line is built from per-source counts of `OK` / `FATAL` / `WARNING` / `SKIPPED` outcomes accumulated in a `StartupValidationResult` (see `scripts/agent/shared/health_models.py`). Outcomes are recorded independently in `_check_services()`: warnings and fatals are always appended when they occur, but whether an explicit `OK` outcome is *also* appended (`pipeline.add_ok(...)`) differs by check:
- `security_audit` (lines ~340-350): `pipeline.add_ok("security_audit")` is called unconditionally after processing warnings, unless `audit_security_defaults` raises `RuntimeError`. So `security_ok` is truthy whenever no exception occurred, **even if warnings were recorded**.
- `readiness` (lines ~352-362): `pipeline.add_ok("readiness")` is called only `if not result.has_issues` (no warnings AND no errors). If a warning-only result occurs, `add_ok` is skipped, so `mcp_ok` is falsy even though `mcp_fail == 0`.
- `mcp_tool_discovery` (lines ~364-388): `pipeline.add_ok("mcp_tool_discovery")` is called only `if not discovery.findings and not discovery.unreachable`. A warning-only finding skips `add_ok`, so `tool_disc_ok` is falsy even though `tool_disc_fail == 0`.
- `rag_consistency` (lines ~410-424): `pipeline.add_ok("rag_consistency")` is called only if `rag_check.is_consistent`; warning-only results skip it, and the display line already uses `'OK' if rag_ok else 'WARN'` (no `FAIL`).

The display code at lines ~524-537 renders each line as:
```python
f"  Security audit: {'OK' if security_ok else 'FAIL'} ({security_fail} fatal, {security_warn} warnings)"
f"  Service readiness: {'OK' if mcp_ok else 'FAIL'} ({mcp_fail} fatal, {mcp_warn} warnings, {mcp_skip} skipped)"
f"  Tool discovery: {'OK' if tool_disc_ok else 'FAIL'} ({tool_disc_fail} fatal, {tool_disc_warn} warnings, {tool_disc_skip} skipped)"
f"  RAG consistency: {'OK' if rag_ok else 'WARN'} ({rag_fail} fatal, {rag_warn} warnings)"
```

## Problem
Verified against the current source (2026-08-18):
- **Confirmed bug** — for the "Service readiness" line and the "Tool discovery" line, a warning-only outcome (fatal count == 0, warning count > 0) produces `mcp_ok == 0` / `tool_disc_ok == 0` respectively, so the display shows **"FAIL"** alongside `(0 fatal, N warnings, ...)`. This is self-contradictory (a line reading "FAIL" while itself reporting `0 fatal`) and can cause an operator to believe startup failed when it actually completed and the session is running normally.
- **Correction to the source issue's claim**: the issue text asserts that the `security_audit` line exhibits the identical bug (its example shows `Security audit: FAIL (0 fatal, 1 warnings)`). This is **not accurate for the current code**: `pipeline.add_ok("security_audit")` is called unconditionally in the non-exception path, so `security_ok` is truthy whenever warnings occur without an exception, and the line currently renders `OK (0 fatal, 1 warnings)`, not `FAIL`. There is no reproducible "false FAIL" for `security_audit` today. There is, however, a related (milder) inconsistency worth fixing at the same time: because `security_ok` is always true in the non-exception path, the security_audit line can never show anything but `OK` or `FAIL`(on exception) — it never renders `WARN` even when warnings are present, unlike the RAG line, which undercuts the goal of a uniform, trustworthy summary.
- The `rag_consistency` line already avoids the false-FAIL problem (it uses `WARN`, not `FAIL`, when `rag_ok` is falsy), but its classification is likewise driven by an "OK only if zero issues" flag rather than by the fatal count, so it is inconsistent in mechanism with the other three lines even though its current output happens to be safe.
- Net effect: 4 lines use 3 different ad hoc mechanisms to decide OK/WARN/FAIL, 2 of which (`readiness`, `mcp_tool_discovery`) currently produce a misleading "FAIL" for a non-fatal, warning-only state.

## Reason for change
An operator scanning the Readiness Summary should be able to trust that "FAIL" means startup actually raised a fatal condition (which, per `_check_services()`, would already have raised `RuntimeError` and aborted startup via `pipeline.has_fatal`), and that "WARN" means startup continued but something needs attention. The current mixed logic breaks that guarantee for 2 of the 4 lines, creating false-alarm risk and eroding trust in the summary as a fast triage tool.

## Implementation intent
Base each of the 4 summary lines purely on the counted `FATAL` and `WARNING` outcomes for its source (which are always recorded reliably, regardless of whether `add_ok` was also called), rather than on a separately-maintained "ok" flag/counter. Apply one shared 3-tier rule uniformly:
- `FAIL` if fatal count > 0
- else `WARN` if warning count > 0
- else `OK`

This can be implemented as a small shared helper (e.g. a local function or static method taking `fail_count, warn_count` and returning the label string) used by all four lines, to guarantee the same rule is applied everywhere and to prevent future drift. The `add_ok` calls in `_check_services()` may remain as-is (they are otherwise harmless bookkeeping) but the `_report_readiness` display must no longer depend on the presence/absence of an `OK` outcome to decide between `OK` and `FAIL`/`WARN`.

## Implementation instructions
1. In `scripts/agent/startup.py`, add a small helper (module-level function or private method on `StartupOrchestrator`, whichever fits the existing style) that takes `fatal_count: int, warning_count: int` and returns `"FAIL"` / `"WARN"` / `"OK"` per the 3-tier rule above.
2. Update all four `lines.append(...)` f-strings in `_report_readiness` (security_audit, readiness/"Service readiness", mcp_tool_discovery/"Tool discovery", rag_consistency/"RAG consistency") to call this helper with each source's `*_fail` and `*_warn` counts instead of using `'OK' if xxx_ok else 'FAIL'` / `'OK' if rag_ok else 'WARN'`.
3. The `*_ok` local variables (`mcp_ok`, `rag_ok`, `security_ok`, `tool_disc_ok`) become unused for display purposes once the helper is wired in; remove them if nothing else references them, to avoid dead code and satisfy lint.
4. Do not change the fatal-vs-non-fatal semantics of `_check_services()` itself (i.e. do not change what triggers `pipeline.add_fatal` / `has_fatal` / the `RuntimeError` startup-abort path) — this task is limited to the summary line rendering.

## Acceptance criteria
- When a source has `fatal == 0` and `warning > 0`, its Readiness Summary line renders `WARN`, never `FAIL`, for all four lines (Security audit, Service readiness, Tool discovery, RAG consistency).
- When a source has `fatal > 0`, its line renders `FAIL` regardless of warning count.
- When a source has `fatal == 0` and `warning == 0`, its line renders `OK`.
- All four lines use one identical, shared classification rule (verifiable by code inspection — a single helper/function is the sole place implementing the 3-tier logic).
- No change to whether startup itself raises/aborts on fatal outcomes (`pipeline.has_fatal` behavior in `_check_services` is untouched).
- Existing tests continue to pass; `ruff`/`mypy` clean (no unused-variable warnings from removed `*_ok` locals).

## Tests

  - fatal=0, warning>0 → `WARN` (this is the regression case for `readiness` and `mcp_tool_discovery`, and the new-behavior case for `security_audit`)
  - fatal>0, warning=0 → `FAIL`
