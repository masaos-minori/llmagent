# Fix: startup sequence ignores SIGINT/SIGTERM until it completes

## Priority
High

## Target files
- `scripts/agent/startup.py` (`StartupOrchestrator.__init__()`, `run()` lines 67-94, `_start_servers()` lines 133-204, `_verify_mcp_health()` lines 206-252)
- `scripts/agent/repl.py` (`AgentREPL.run()`, signal handler registration lines 743-829; `_repl_loop()`, shutdown-race pattern lines 520-598)
- `scripts/agent/http_lifecycle.py` (`HttpServerLifecycleManager.start()`, health-check polling loop lines 408-451, if the polling loop itself is made cancellable)

## Background
`AgentREPL.run()` (`scripts/agent/repl.py:743-829`) registers SIGTERM/SIGINT handlers via
`loop.add_signal_handler()` before invoking the startup sequence:

```python
loop = asyncio.get_running_loop()
self._shutdown_event = asyncio.Event()

def _sigterm_handler() -> None:
    self._ctx.conv.shutdown_requested = True
    if self._shutdown_event is not None:
        self._shutdown_event.set()
    ...

for sig in (signal.SIGTERM, signal.SIGINT):
    try:
        loop.add_signal_handler(sig, _sigterm_handler)
    ...

startup = StartupOrchestrator(self._ctx, self._view)
...
self._cmds, self._orchestrator, _spawned_subprocesses = await startup.run()
```

Because `loop.add_signal_handler()` intercepts the signal at the event-loop level, `SIGINT` no
longer raises `KeyboardInterrupt` — it only invokes `_sigterm_handler()`, which sets
`self._ctx.conv.shutdown_requested = True` and `self._shutdown_event.set()`.

Verified against current source: `grep -n "shutdown_event\|shutdown_requested"
scripts/agent/startup.py` returns zero matches. Neither `StartupOrchestrator.run()`,
`_start_servers()`, nor `_verify_mcp_health()` reference `shutdown_event` or
`shutdown_requested` anywhere, and `StartupOrchestrator.__init__(self, ctx: AgentContext, view:
CLIView)` (constructor) has no parameter through which a shutdown signal could be passed in.
`AgentREPL.run()` constructs it as `StartupOrchestrator(self._ctx, self._view)`
(`scripts/agent/repl.py:829`) — no `shutdown_event` is wired through.

`_start_servers()` (`scripts/agent/startup.py:133-204`) awaits
`ctx.services_required.lifecycle.start_http_subprocess(key, cfg)` per configured HTTP subprocess
MCP server, which in turn (`scripts/agent/http_lifecycle.py:408-451`, inside
`HttpServerLifecycleManager.start()`) polls `/health` every 0.5s
(`await asyncio.sleep(0.5)` at line 448) until `cfg.startup_timeout_sec` elapses. On a first-attempt
failure, `_start_servers()` retries after `HEALTH_CHECK_RETRY_DELAY_SEC = 1.0` second
(`scripts/agent/startup.py:44`, sleep at line ~174). `_verify_mcp_health()`
(`scripts/agent/startup.py:206-252`) performs a similar retry-with-delay pattern against each
server's `/health` endpoint. None of these `await asyncio.sleep(...)` or
`await client.get(...)` calls are raced against `shutdown_event`, so once a signal handler sets the
flags, the awaiting coroutine is not interrupted — it only completes (or fails) on its own
schedule.

With multiple configured servers, each having a multi-second-to-multi-ten-second
`startup_timeout_sec`, the aggregate startup sequence can block for minutes. During this window,
`_sigterm_handler()` only sets flags; nothing in the startup path checks them, so the process does
not react to Ctrl-C or `SIGTERM` at all until `startup.run()` returns (success or failure) and
control reaches `_repl_loop()`, which is the first place `shutdown_event`/`shutdown_requested` are
actually consulted (`scripts/agent/repl.py:538-598`, using `asyncio.wait({dispatch_task,
shutdown_task}, return_when=asyncio.FIRST_COMPLETED)`).

This issue is related to `issues/done/20260804-120001_startup_mcp_subprocess_orphan_on_partial_failure.md`
(requirement: `requires/20260804-131707_require.md`), which fixes orphaned MCP subprocesses left
behind when `_start_servers()` fails partway through. Forcing operators to `SIGKILL` a hung startup
sequence (because graceful signals do nothing) bypasses `AgentREPL.run()`'s and
`StartupOrchestrator.run()`'s cleanup paths entirely, so `lifecycle.shutdown_all()` is never
called — the two issues compound each other and are best addressed together.

## Problem
`StartupOrchestrator`'s startup sequence has no mechanism to observe a shutdown request. If the
operator sends `SIGINT`/`SIGTERM` while startup is blocked on a slow/unresponsive MCP subprocess
health check, the signal is silently absorbed by `_sigterm_handler()` (flags are set but nothing
reads them) and the process continues waiting up to the full configured timeout(s) across all
configured servers, with no way to abort short of `SIGKILL`.

## Reason for change
This is an operability/reliability gap: a hung or slow startup should be interruptible the same
way the REPL's main loop already is. Without this fix, the only way to abort a stuck startup is
`SIGKILL`, which skips graceful cleanup and — per the related orphan-subprocess issue — can leave
MCP subprocesses running unsupervised. The REPL already has a proven pattern for this
(`asyncio.wait(..., return_when=FIRST_COMPLETED)` racing a task against `shutdown_event.wait()` in
`_repl_loop()`), so this is an extension of an existing, tested design, not a new cancellation
model.

## Implementation intent
Thread the existing `asyncio.Event` shutdown signal (already created in `AgentREPL.run()` as
`self._shutdown_event`) into `StartupOrchestrator`, and check it at the startup sequence's major
wait points — before/inside the per-server startup loop in `_start_servers()`, inside the
health-check retry delay, and inside `_verify_mcp_health()`'s retry delay — so that a shutdown
request interrupts the startup sequence promptly instead of after it completes. On interruption,
ensure already-started subprocesses are cleaned up via `lifecycle.shutdown_all()` before
propagating the abort, reusing the same rollback path that
`issues/done/20260804-120001_startup_mcp_subprocess_orphan_on_partial_failure.md` /
`requires/20260804-131707_require.md` hardens for the ordinary failure case.

## Implementation instructions
1. In `scripts/agent/startup.py`, add a `shutdown_event: asyncio.Event | None = None` parameter to
   `StartupOrchestrator.__init__()` and store it (e.g. `self._shutdown_event`).
2. In `scripts/agent/repl.py`'s `AgentREPL.run()` (around line 829), pass
   `self._shutdown_event` into the `StartupOrchestrator(...)` constructor call so the same event
   used by `_repl_loop()`'s signal handling is shared with the startup phase.
3. In `_start_servers()` (`scripts/agent/startup.py:133-204`): before each per-server startup
   attempt (top of the `for key, cfg in ctx.cfg.mcp.mcp_servers.items():` loop) and around the
   `await asyncio.sleep(HEALTH_CHECK_RETRY_DELAY_SEC)` retry delay, race the in-progress wait
   against `self._shutdown_event.wait()` using the same `asyncio.wait(...,
   return_when=asyncio.FIRST_COMPLETED)` pattern already used in `_repl_loop()`
   (`scripts/agent/repl.py:538-556`). If the shutdown wait completes first, stop starting further
   servers and proceed to cleanup.
4. In `_verify_mcp_health()` (`scripts/agent/startup.py:206-252`): apply the same race to the
   per-server health-check retry delay (`await asyncio.sleep(HEALTH_CHECK_RETRY_DELAY_SEC)`).
5. On a shutdown-triggered interruption in either method, ensure
   `ctx.services_required.lifecycle.shutdown_all()` is invoked for any subprocesses started so far
   before the interruption is surfaced to `run()`'s caller (coordinate with the fix in
   `requires/20260804-131707_require.md`, which already changes the rollback gating in
   `StartupOrchestrator.run()`'s `except` block — do not introduce a second, divergent rollback
   path).
6. Do not modify `HttpServerLifecycleManager.start()`'s internal 0.5s health-check polling loop
   (`scripts/agent/http_lifecycle.py:408-451`) unless needed for interruption at that finer
   granularity; if left unmodified, document that a shutdown request is honored between
   `start_http_subprocess()` calls (i.e. per-server, not mid-poll) as an accepted latency bound —
   confirm this is acceptable given per-server `startup_timeout_sec` values, or extend the
   polling loop itself to also race against `shutdown_event` if finer-grained interruption is
   required.
7. Do not introduce a new cancellation abstraction — reuse the
   `asyncio.wait(..., return_when=FIRST_COMPLETED)` task-race pattern already established in
   `_repl_loop()`.
8. Out of scope (per the source issue): shutdown handling for `_repl_loop()` itself is already
   implemented and must not be changed by this work.

## Acceptance criteria
- Reproducing a non-responsive (or very slow) MCP subprocess health check and sending
  SIGINT/SIGTERM during the startup sequence causes the process to move to safe termination within
  a few seconds, instead of blocking until the full `startup_timeout_sec` (and any retries) elapse.
- Any subprocesses already started before the shutdown request is honored are terminated via
  `lifecycle.shutdown_all()` (no orphaned processes), consistent with
  `requires/20260804-131707_require.md`.
- Normal (successful) startup sequences show no regression: no added delay, no change in behavior
  when no shutdown signal is received.
- No new cancellation model is introduced; the fix reuses the existing
  `asyncio.wait(..., return_when=FIRST_COMPLETED)` pattern from `_repl_loop()`.
