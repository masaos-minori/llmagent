# Race condition in approval resolution

## Priority

Medium

## Target Files

- `scripts/agent/commands/cmd_workflow.py` — `_cmd_approve()`, `_cmd_reject()`
- `scripts/agent/workflow/approval_ops.py` — `resolve_approval()`, `find_approval_by_id()`

## Background

The `/approve` and `/reject` commands resolve pending workflow approvals by checking if an approval exists and then resolving it. The check and resolution steps are separate operations.

## Problem

In `cmd_workflow.py:93-129`:

```python
def _cmd_approve(self, ctx: CommandContext, *args: str) -> CommandResult:
    count = count_pending_approvals(store._db)
    ...
    approval = find_approval_by_id(store._db, explicit_id)
    if approval is None or approval.status != "pending":
        return CommandResult(error="...")
    resolve_approval(store._db, approval.approval_id, "approved", reason)
```

Between step 1 (checking pending approvals) and step 3 (resolving the approval), another process could resolve the same approval concurrently. In SQLite WAL mode, transaction consistency across different connections is not guaranteed. Additionally, when `find_approval_by_id()` returns None or non-pending status, it is impossible to distinguish between an already-resolved approval and a nonexistent one.

## Reason for Change

Concurrent approval resolution can lead to double-resolution of the same approval, causing inconsistent workflow state. This is particularly problematic in environments where multiple clients can interact with the system simultaneously.

## Implementation Intent

Make approval resolution atomic by wrapping the check-and-resolve operation in a single transaction. Use optimistic locking or conditional updates to prevent double-resolution.

## Implementation Instructions

1. Modify `resolve_approval()` to use `UPDATE ... WHERE status='pending'` instead of unconditional update.
2. Check the number of affected rows after the update. If zero, return a specific error indicating the approval was already resolved.
3. Wrap the entire check-and-resolve flow in a single database transaction.
4. Return distinct error messages for "not found" vs "already resolved" states.

## Acceptance Criteria

- [ ] Approval resolution uses conditional update (WHERE status='pending')
- [ ] Double-resolution prevented via row count check
- [ ] Distinct error messages for "not found" vs "already resolved"
- [ ] Entire flow runs within a single transaction
