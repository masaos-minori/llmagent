# Prevent oversized chunks during text and code chunk merging

## Priority
Medium

## Target files
- `scripts/rag/ingestion/chunk_utils.py`
- `scripts/rag/ingestion/chunk_splitter.py`
- `scripts/rag/ingestion/chunk_english.py`

## Background
The RAG ingestion pipeline (`Crawler.py` → `ChunkSplitter.py` → `RagIngester.py`) merges
text and code items into chunks bounded by `min_chunk` / `max_chunk` (configured in
`chunk_splitter.toml`). Chunk size directly affects embedding and retrieval quality
(especially after the Qwen3 embedding migration referenced in the issue): oversized
chunks reduce retrieval precision and destabilize ranking even though the model itself
can technically accept longer context.

Verified against current source:

- `merge_text_items()` in `scripts/rag/ingestion/chunk_utils.py` (lines 36-43): when an
  incoming `item` alone does not fit within `max_chunk` and the current `buf` is below
  `min_chunk`, the function falls into `buf = item` (line 43) with no splitting. A
  single oversized item is carried through unsplit and can be appended to `result`
  as-is. This function is called directly from `_chunk_code()` in
  `scripts/rag/ingestion/chunk_splitter.py` (lines 209-219), where code blocks are
  produced by splitting only at blank lines (`re.split(r"\n{2,}", ...)`); a code block
  with no internal blank line (e.g. one long function) that exceeds `max_chunk` is
  passed to `merge_text_items()` and is never split further.
- `_split_sentences_en()` in `scripts/rag/ingestion/chunk_english.py` (lines 67-81) is
  the last-resort fallback for an oversized paragraph, but its own docstring states
  "Oversized sentences are kept as-is" — a single sentence longer than `max_chunk` is
  appended to `chunks` unsplit, with no character-length fallback.
- `start_next_buf()` in `scripts/rag/ingestion/chunk_utils.py` (lines 12-17), used by
  both `merge_text_items()` and `chunk_english.py`'s `_flush_and_merge()`, builds
  `overlap + sep + next_item` without checking the result against `max_chunk`. The
  resulting buffer is only bounds-checked against `max_chunk` on the *next* loop
  iteration (when the next item is considered), not immediately after construction, so
  a buffer already near `max_chunk` plus overlap can end up larger than `max_chunk` when
  it is finally emitted. The existing test
  `tests/test_chunk_utils.py::TestMergeTextItems::test_overlap_carries_tail` only
  asserts chunks stay under `max_chunk + overlap + separator` slack (`<= 12` for
  `max_chunk=8`), confirming this is current, unresolved behavior rather than a strict
  `max_chunk` guarantee.

## Problem
Oversized chunks can be produced in two independent ways:
1. A single oversized text/code item bypasses splitting entirely (no fallback exists
   for splitting a lone item that is itself larger than `max_chunk`).
2. A conforming chunk can be pushed over `max_chunk` after `chunk_overlap` is
   prepended, because the overlap-augmented buffer is not re-validated against
   `max_chunk` at the point of construction.

## Reason for change
This is not required for Qwen3 compatibility per se (Qwen3 tolerates longer context),
but fixing it improves retrieval precision and ranking stability for the embedding
pipeline going forward, and closes a known correctness gap that current tests already
hint at (the `<= 12` slack tolerance in `test_overlap_carries_tail`) but do not fully
close.

## Implementation intent
- Introduce oversized-item handling at the point items are merged, rather than only at
  paragraph level:
  - For text (English path in `chunk_english.py`): when a paragraph or sentence itself
    exceeds `max_chunk`, split it further — sentence boundaries first, then fall back
    to fixed-length character splitting for any remaining oversized fragment (e.g. a
    single run-on sentence).
  - For code (`_chunk_code()` in `chunk_splitter.py`, backed by `merge_text_items()` in
    `chunk_utils.py`): when a blank-line-delimited block itself exceeds `max_chunk`,
    split it further — by structural boundaries (e.g. line boundaries, or other
    reasonable code-aware boundary) first, then fall back to fixed-length
    character-length splitting.
  - This oversized-item handling can live in `chunk_utils.py` as a shared helper (so
    both the code path and any caller of `merge_text_items()` benefit), with
    language-specific splitting strategies supplied by `chunk_english.py` /
    `chunk_splitter.py` as needed.
- Fix `start_next_buf()` (or its call sites) so that the overlap-augmented buffer is
  validated against `max_chunk` at construction time, not only on the next iteration's
  size check — e.g. by truncating/re-splitting when `overlap + sep + next_item` alone
  would exceed `max_chunk`.
- Preserve existing short-tail merge behavior (merging a final under-`min_chunk`
  remainder into the previous chunk) in both `merge_text_items()` and
  `_merge_paragraphs_en()` — do not regress this behavior while adding the
  oversized-item handling.
- Keep the fix scoped to the English/code chunking paths named in the issue
  (`chunk_utils.py`, `chunk_splitter.py`, `chunk_english.py`). Note for awareness only:
  `scripts/rag/ingestion/chunk_japanese.py`'s `_merge_ja_sentence_pairs()` has an
  analogous unbounded-sentence gap, but it is out of scope for this requirement since
  the source issue does not list it as a target file.

## Implementation instructions
1. In `chunk_utils.py`, add a helper (or extend `merge_text_items()`) that, given a
   single item longer than `max_chunk`, splits it into pieces `<= max_chunk` using a
   pluggable "fine splitter" strategy, falling back to plain character-length slicing
   when the fine splitter cannot bring a piece under `max_chunk`. Wire this in wherever
   `merge_text_items()` currently does `buf = item` for an oversized item.
2. In `chunk_splitter.py`, supply a code-aware fine splitter for `_chunk_code()` (e.g.
   split an oversized block by single newlines or other structural markers before
   falling back to character slicing), and pass it into the updated
   `merge_text_items()` call.
3. In `chunk_english.py`, ensure `_split_sentences_en()` (or a new step invoked after
   it) applies character-length splitting to any sentence still longer than
   `max_chunk` after sentence-boundary splitting, so no chunk emitted by
   `_chunk_english()` can exceed `max_chunk`.
4. Fix `start_next_buf()` so the buffer it returns is re-validated (and truncated/
   re-split as needed) against `max_chunk`, accounting for `chunk_overlap` and `sep`
   length, in both its `chunk_utils.py` and `chunk_english.py` call sites.
5. Do not change `chunk_japanese.py`, `docs/*.md`, or configuration defaults as part of
   this change unless a later phase explicitly extends scope.

## Acceptance criteria
- No single text chunk produced by `_chunk_english()` (via `merge_text_items()` /
  `_merge_paragraphs_en()` / `_split_sentences_en()`) exceeds `max_chunk`, including
  chunks derived from a single oversized paragraph or sentence.
- No single code chunk produced by `_chunk_code()` (via `merge_text_items()`) exceeds
  `max_chunk`, including chunks derived from a single oversized blank-line-delimited
  block.
- Chunks produced with `chunk_overlap > 0` do not exceed `max_chunk` as a result of the
  overlap prefix being added.
- Existing short-tail merge behavior (small trailing remainder merged into the
  previous chunk instead of discarded or left as a separate undersized chunk) still
  functions for both text and code paths.
- Normal-sized (non-oversized) input continues to produce the same chunking result as
  before the change.

## Tests
- Extend `tests/test_chunk_utils.py` (`TestMergeTextItems`) with cases where a single
  item exceeds `max_chunk` (with and without internal splittable boundaries) and assert
  every returned chunk's length is `<= max_chunk`.
- Add/extend overlap-specific tests in `tests/test_chunk_utils.py` asserting that
  `start_next_buf()` output and downstream merged chunks never exceed `max_chunk`
  (tightening the current `test_overlap_carries_tail` slack tolerance).
- Add tests in `tests/test_chunk_splitter.py` (or a new focused test module) for
  `_chunk_code()` with a single oversized code block (no internal blank lines),
  asserting all resulting chunks are `<= max_chunk`.
- Add tests exercising `_chunk_english()` / `_split_sentences_en()` with a single
  run-on sentence exceeding `max_chunk`, asserting the result is split and each chunk
  is `<= max_chunk`.
- Run the full existing suite for the touched modules (`tests/test_chunk_utils.py`,
  `tests/test_chunk_splitter.py`, `tests/test_mdq_get_chunk_behavior.py`) to confirm no
  regression in existing passing behavior.
