# Deduplicate SearchDiagnostics field table in docs/03_rag_03_03 against docs/03_rag_04_02, and record confirmed HTTP-mode `last_fetch_result` staleness finding

## Priority
Medium

## Target files
- `docs/03_rag_03_03_query_pipeline-context-and-diagnostics.md` (edit target)
- `docs/03_rag_04_02_dto-models_result.md` (reference only — canonical DTO field source, not edited by this requirement)

## Background
`docs/03_rag_03_03_query_pipeline-context-and-diagnostics.md` documents three things in its
section 4: the `PipelineContext` dataclass (§4, from `scripts/rag/stage.py`), the
`SearchDiagnostics` dataclass (§4.2, from `scripts/rag/models_result.py`), and the
`get_diagnostics()` return dict (§4.3, from `scripts/rag/pipeline.py:548`). The source issue
claimed all three field tables duplicate `docs/03_rag_04_02_dto-models_result.md`, which is the
canonical DTO reference for `scripts/rag/models_result.py`.

Verification against current source found this claim is only partially correct:
- **`SearchDiagnostics` (§4.2)**: genuinely duplicated. `docs/03_rag_04_02_dto-models_result.md`
  (lines 88-99) already documents the exact same 8 fields (`embed_ok`, `embed_failed`,
  `fts_errors`, `result_source`, `http_result_kind`, `remote_status_code`, `remote_latency_ms`,
  `fallback_reason`) with the same types and defaults.
- **`PipelineContext` (§4)**: NOT present in `04_02`. `04_02` documents `scripts/rag/models_result.py`
  DTOs only; `PipelineContext` is defined in `scripts/rag/stage.py` and has no field table
  anywhere else in the docs tree (confirmed via `grep -rl "PipelineContext" docs/*.md` — it
  appears only in `03_03` and other `03_rag_03_0x` pipeline-stage docs that reference it in
  prose, not as a field table).
- **`get_diagnostics()` return dict (§4.3)**: also NOT present in `04_02`. It documents the
  return value of a `RagPipeline` method (`scripts/rag/pipeline.py:548`), not a DTO class, and
  has no duplicate elsewhere.

So the actionable deduplication is narrower than the issue's literal wording: only the
`SearchDiagnostics` table should be removed and replaced with a cross-reference. The
`PipelineContext` and `get_diagnostics()` tables must be kept — they are not duplicated
anywhere, and removing them (as the issue's "Required Changes" wording literally suggests)
would delete unique documentation content with nothing to replace it, since `04_02` doesn't
cover either of them.

Separately, the issue asks whether `call_rag_service()`'s docstring claim — that
`set_fetch_result` is defined but never called — means HTTP-mode `fetch_result` is genuinely
never updated. A full call-graph trace was completed (see Implementation intent below) and the
claim is **confirmed**, with an additional practical consequence beyond what the docstring
states.

## Problem
1. `docs/03_rag_03_03_query_pipeline-context-and-diagnostics.md` §4.2 transcribes the
   `SearchDiagnostics` field table verbatim from `docs/03_rag_04_02_dto-models_result.md`
   (lines 88-99 there), creating a second source of truth that must be kept in sync manually
   whenever `SearchDiagnostics` fields change.
2. The doc does not state whether `get_diagnostics()["fetch_result"]` can go stale when the
   pipeline runs in HTTP mode, even though the underlying behavior (confirmed below) means an
   operator reading `fetch_result` during a successful HTTP-mode call is looking at leftover
   data from a previous in-process run, not data reflecting the current call.

## Reason for change
The `SearchDiagnostics` duplication doubles maintenance effort against the canonical `04_02`
DTO document — any future field change (add/remove/rename/retype) must be applied in two
places or the docs silently diverge. The `fetch_result` staleness behavior is confirmed to be
real (not merely a documented forward-compatibility placeholder), and it bears on incident
diagnostics reliability: an operator using `get_diagnostics()["fetch_result"]` to investigate
an HTTP-mode RAG call could be misled by data left over from a different call.

### Call-graph trace finding (confirmed, not inconclusive)
Traced `set_fetch_result` across its full call chain:
- `scripts/rag/pipeline_service.py:42-171` — `call_rag_service()`'s entire body was read in
  full (both the retry loop and post-loop exhausted-retries path). `set_fetch_result` is
  **never invoked** anywhere in the function; only `_set_fallback_reason(set_fallback_reason,
  ...)` is called, on the 4xx path (line ~144-147), the JSON-parse-error path (line ~157), and
  the retries-exhausted path (line ~167-169). This confirms the docstring's claim at face
  value: the callback is accepted as a parameter but dead in this function.
- `scripts/rag/http_augment.py:44-99` — `HttpAugment.__init__` stores the callback as
  `self._set_fetch_result` (line 56) and `HttpAugment.run()` passes
  `set_fetch_result=lambda fr: self._set_fetch_result(fr)` into `call_rag_service()` (line 69).
  Since `call_rag_service()` never calls it, this wrapper is also never invoked.
- `scripts/rag/pipeline.py:470-511` — `RagPipeline._run_http_augment()` constructs `HttpAugment`
  with `set_fetch_result=lambda fr: setattr(self, "last_fetch_result", fr)` (line 481). Because
  the callback chain above never fires, **this setattr never runs during a successful or
  failed-but-fallback-eligible HTTP call.**
- `scripts/rag/pipeline.py:336` — the only place `self.last_fetch_result` is actually assigned
  is inside `RagPipeline.run()`, unconditionally, after the full in-process
  MQE→Search→Fusion→Rerank→Augment stage sequence completes.
- `scripts/rag/pipeline.py:408-414` (`augment()`) — when `rag_service_url` is configured and
  `_run_http_augment()` returns a non-`None` result (HTTP success, including valid empty `""`),
  `augment()` returns immediately at line 413-414 **without calling `self.run()`**. `run()` is
  only reached when the HTTP call fails/exhausts retries (returns `None`) and the code falls
  through to the in-process fallback path.

**Confirmed conclusion**: In HTTP mode, `self.last_fetch_result` is updated **only when the
HTTP call fails and the in-process pipeline runs as a fallback** (via `run()`'s line-336
assignment) — never through the `set_fetch_result` callback plumbing, which is entirely dead
code end-to-end. Consequently, whenever an HTTP-mode call **succeeds** (remote non-empty or
remote empty), `get_diagnostics()["fetch_result"]` reflects whatever `last_fetch_result` held
from a previous call (or `None` if no in-process run has ever occurred yet on that
`RagPipeline` instance) — it does not reflect the just-completed HTTP call at all, because the
HTTP path has no `hits`/`min_score_applied` data of its own to populate a `TwoStageFetchResult`
with. This is a genuine, non-hypothetical staleness gap, not a remote edge case.

   list, types, and defaults are documented in `docs/03_rag_04_02_dto-models_result.md` (link
   to it), and that this section instead covers only the fields' HTTP-mode
   boundary-condition/ownership behavior.
2. Do not touch the `PipelineContext` table (§4) or the `get_diagnostics()` table (§4.3) — leave
   them as-is; they are not duplicates.
3. Keep the "境界条件 (Boundary and ownership)" subsection on `http_result_kind`'s dual
   definition exactly as-is (content and line references already re-verified as accurate).
4. Add a note (near the `fetch_result` row in the `get_diagnostics()` table, or near
   `PipelineContext.search_diagnostics`) stating plainly, per the classification in
   `rules/coding.md`, that in HTTP mode `last_fetch_result` (and therefore
   `get_diagnostics()["fetch_result"]`) is updated only on the in-process fallback path, and is
   stale/unrelated to the current call whenever the HTTP call itself succeeds — with a
   pointer to `scripts/rag/pipeline.py:336`, `:408-414`, and `:470-511`, and
   `scripts/rag/pipeline_service.py:42-171` as the evidence trail. Since this is a real gap
   rather than accepted behavior, do not label it "Needs Confirmation" — state it as a known,
   confirmed limitation, and note (in one sentence) that whether to fix it (e.g., populate
   `fetch_result` from the HTTP result, or clear it before HTTP calls) is an implementation
   decision out of scope for this documentation change.
5. Do not modify `docs/03_rag_04_02_dto-models_result.md`, any other `docs/*.md` file, or any
   file under `scripts/` — this requirement is documentation-only for `03_03`.
