## Background

`config/agent.toml` currently sets `startup_mode = "subprocess"` for all 10 configured `[mcp_servers.*]` entries (verified directly in the file). `StartupMode` (`scripts/shared/mcp_config.py`) defines three enum values: `none`, `persistent`, `subprocess`.

Several documents correctly describe today's configuration as all-subprocess:
- `docs/01_overview-arch-02-pipelines.md:81` — "現行の `config/agent.toml` は全 MCP サーバに `startup_mode = "subprocess"` を明示指定している(persistent はスキーマ上存在するが未使用)"
- `docs/02_deployment.md:90,113` — "MCP servers (ports 8004-8014) auto-start as agent-managed subprocesses on agent startup."

But `docs/04_mcp_01_system_overview.md`'s "Server Catalog" table (lines 71-80) lists every one of the same 10 servers with 起動モード = `persistent` — the opposite claim. The five per-server catalog docs (`04_mcp_04_01` through `04_mcp_04_05`) repeat `**起動モード:** persistent（HTTP）` for each server individually, propagating the same wrong claim into 10+ separate locations. This is a live, currently-reproducing contradiction, not a historical/stale issue — verified by direct comparison against `config/agent.toml` on 2026-08-18.

Separately, `docs/04_mcp_01_tool_ownership_matrix.md` already has a working generated-and-guarded inventory section (produced by `tools/gen_reference_table.py --type mcp`, drift-checked by `check_port_drift`/`check_tool_name_drift` in `tools/check_docs_consistency.py --domain mcp`), but it only covers Server / Port / Tool Count / Tool Names — it does not include startup mode, health-check mode, enabled state, or security tier, so there is no generated source of truth that would have caught the persistent/subprocess contradiction above.

Additionally, `.github/workflows/mcp-docs-consistency.yml` runs `python tools/check_mcp_docs_consistency.py`, a script that no longer exists (it was consolidated into `tools/check_docs_consistency.py --domain mcp` per that file's own docstring). This workflow currently fails outright rather than performing any consistency check, so CI is not actually gating MCP docs drift today.

## Problem

1. Documentation for MCP server startup mode is self-contradictory: the dedicated MCP overview and all five per-server catalog docs assert `persistent` for every server, while the top-level overview, deployment docs, and the actual configuration assert `subprocess`. An operator or agent reading only the MCP-specific docs would draw the wrong conclusion about process ownership, health-check behavior, and failure-recovery expectations (manual restart vs. automatic subprocess retry via `ensure_ready()`).
2. The generated MCP inventory (`docs/04_mcp_01_tool_ownership_matrix.md`) does not carry startup mode, health-check mode, enabled state, or security tier, so there is no mechanically-derived, drift-checked value that could have prevented (1) or would catch future recurrences.
3. No drift check exists (unlike `check_port_drift` / `check_tool_name_drift`) that compares documented per-server startup mode against `config/agent.toml`.
4. `.github/workflows/mcp-docs-consistency.yml` invokes a nonexistent script, so the CI job intended to catch exactly this kind of drift is broken and provides no actual protection.

## Reason for change

Startup mode determines process ownership, health-check behavior, tool-discovery timing, routing availability, and — critically — whether local fail-open or production fail-closed behavior applies on server failure. Wrong documentation here can cause an operator to double-start a server, skip starting a required one, treat an unreachable server as routable, or apply the wrong failure-recovery procedure (expecting automatic subprocess retry when the doc says "persistent, manual restart," or vice versa). The contradiction is live in the docs today, not merely historical, and the CI safety net meant to catch this class of drift is currently non-functional.

## Implementation intent

- Establish `docs/04_mcp_02_02_startup-modes-and-health.md` (or another single canonical doc, to be decided in planning) as the one place that defines the semantics of `none` / `persistent` / `subprocess`, including process ownership, health-check behavior, tool-discovery behavior, routing availability, and local vs. production failure behavior for each mode.
- Correct the per-server startup-mode claims in `04_mcp_01_system_overview.md`'s Server Catalog table and in the five `04_mcp_04_0*` catalog docs so they match `config/agent.toml`'s actual configured values (currently all `subprocess`), rather than re-deriving or reinterpreting the mode semantics in each location.
- Extend the existing generated-inventory mechanism (`tools/gen_reference_table.py` + the guarded section in `04_mcp_01_tool_ownership_matrix.md`) to also emit startup mode and health-check mode per server, sourced directly from `config/agent.toml`; include enabled state and security tier only if a config-level source of truth for them actually exists (verify during planning — no `enabled` or `security_tier` field was found on `McpServerConfig` as of this writing).
- Add a startup-mode drift check to `tools/check_docs_consistency.py` (mcp domain), parallel in structure to the existing `check_port_drift` / `check_tool_name_drift`, that flags any per-server startup-mode claim in the docs that disagrees with `config/agent.toml`.
- Fix `.github/workflows/mcp-docs-consistency.yml` to invoke the current script (`tools/check_docs_consistency.py --domain mcp`) instead of the removed `tools/check_mcp_docs_consistency.py`, so CI actually runs and can catch this class of drift going forward.
- Explicitly mark any remaining hand-written example/illustrative startup-mode tables (if kept for pedagogical purposes) as non-canonical, distinct from the generated inventory.
