# Fix stale RAG tool names and dedupe MDQ/RAG boundary criteria in docs/04_mcp_05_04 and docs/04_mcp_04_04

## Priority
High

## Target files
- `docs/04_mcp_05_04_mdq-rag-boundary.md` (primary — stale tool names + becomes canonical boundary doc)
- `docs/04_mcp_04_04_mdq.md` (secondary — dedupe boundary criteria table)

## Background
`docs/04_mcp_05_04_mdq-rag-boundary.md` is the designated canonical document for the MDQ-vs-RAG
decision boundary (its own header states "正典の場所" — canonical location, consolidated from a
now-deleted `04_mcp_07_mdq_rag_boundary.md`). Its "RAG を使用する場面" section (around line 63)
lists the RAG tool set as:

```
ツール: ingest, search, get_document, delete_document, list_documents（rag-pipeline-mcp 経由）
```

These five names do not exist anywhere in the current `rag-pipeline-mcp` implementation.

Separately, `docs/04_mcp_04_04_mdq.md` contains its own "MDQ FTS5 対 RAG の判断基準" table
(around lines 105-111) that restates the same MDQ-vs-RAG decision guidance found in `05_04`,
even though `04_04` already has a one-line cross-reference to `05_04` immediately below the table
(line 115: "MDQ 対 RAG の境界の詳細な定義については、[04_mcp_05 §MDQ vs RAG Boundary]... を参照").
The table itself is redundant given that reference already exists.

## Problem
1. **Stale tool names (confirmed factual error).** Verified against
   `scripts/mcp_servers/rag_pipeline/rag_pipeline_tools.py` (`TOOL_LIST`) and
   `scripts/mcp_servers/rag_pipeline/rag_pipeline_server.py` (FastAPI route definitions): the
   actual, current tool names exposed by `rag-pipeline-mcp` are:
   - `rag_run_pipeline` — runs the full pipeline (MQE→Search→RRF→Rerank→Dedup→Augment);
     production status.
   - `rag_debug_pipeline` — same full pipeline, additionally returns intermediate stage outputs
     (`queries`, `merged_hits`, `reranked_hits`, `elapsed`) for debugging; production status.
   - `rag_list_documents` — lists indexed documents in the production RAG store.
   - `rag_delete_document` — deletes a document and its chunks by URL.

   None of `ingest`, `search`, `get_document`, `delete_document`, `list_documents` exist as tool
   names. (`delete_document`/`list_documents` are close to but distinct from the real
   `rag_delete_document`/`rag_list_documents` — the `rag_` prefix is missing throughout, and
   `ingest`/`search`/`get_document` have no equivalent tool at all.) A sibling file,
   `docs/04_mcp_05_03_fail-open-fail-closed-and-risk-tiers.md` (line 85), already references the
   correct name `rag_run_pipeline`, confirming `05_04` alone was left stale after a prior rename.

2. **No standalone search-only tool exists.** Confirmed via source inspection
   (`scripts/mcp_servers/rag_pipeline/rag_pipeline_models.py`, `build_rag_cfg_adapter()`, line
   ~118): `use_search=True` is hardcoded with the comment "always True in MCP mode; checked in
   augment()" — search is a mandatory, non-optional stage of the pipeline, not something that can
   be invoked in isolation. Both `rag_run_pipeline` and `rag_debug_pipeline` always execute the
   entire MQE→Search→RRF→Rerank→Dedup→Augment sequence; there is no request parameter (no `mode`,
   `search_only`, or equivalent field on `RagRunRequest`) to run search alone. The closest
   available approximation is `rag_debug_pipeline`, whose response (`RagDebugResponse` in
   `rag_pipeline_models.py`) exposes `merged_hits` (post-RRF-merge hits, closest to raw search
   results) and `reranked_hits` as a byproduct of a full pipeline run — not a dedicated search-only
   call. This is a fully determined fact, not an open question requiring "Needs Confirmation"
   marking.

3. **Duplicated decision criteria.** The MDQ-vs-RAG boundary/decision criteria are authored twice
   in different forms — the full criteria + data-ownership table in `05_04`, and a shorter
   "MDQ FTS5 対 RAG の判断基準" table in `04_04` — creating a maintenance hazard where only one
   copy gets updated when the underlying facts change (as happened here: `05_04`'s RAG tool names
   went stale while other doc updates presumably touched `04_04` or `05_03`).

## Reason for change
An AI or human implementer following `05_04` as written would attempt to call nonexistent tools
(`ingest`, `search`, `get_document`, `delete_document`, `list_documents`), which will fail against
the actual `rag-pipeline-mcp` server. This is a confirmed, reproducible factual error in a document
that explicitly claims canonical status for this exact topic. The duplication across `04_04` and
`05_04` is a root cause of exactly this kind of staleness and should be eliminated now rather than
left to recur.

## Implementation intent
- In `05_04`, replace the stale RAG tool list with the four verified current tool names, and add a
  short, explicit note that no standalone search-only tool/mode exists today — search is always
  executed as an inseparable stage of `rag_run_pipeline`/`rag_debug_pipeline`, with
  `rag_debug_pipeline`'s `merged_hits`/`reranked_hits` fields being the closest available way to
  inspect search-stage results (as a debug byproduct, not a dedicated search call).
- Consolidate the MDQ-vs-RAG decision criteria so `05_04` remains the single canonical source: keep
  `05_04`'s full criteria and data-ownership table as-is (no stale content found there beyond the
  tool names), and reduce `04_04`'s duplicate table to a one-line reference pointing at `05_04`
  (do not just add another reference alongside the existing table — remove/replace the table
  itself, since `04_04` already has a working cross-reference line directly below it).
- Do not implement a search-only RAG tool or change any pipeline behavior — this is a
  documentation-only correction reflecting current reality.
