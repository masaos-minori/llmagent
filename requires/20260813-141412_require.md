# Consolidate duplicated ratio-based token-estimation logic in `context_view.py` with `shared/token_estimation.py`

## Priority
Medium

## Target files
- `scripts/agent/services/context_view.py`
- `scripts/shared/token_estimation.py`

## Background
`scripts/shared/token_estimation.py` defines the canonical character-to-token ratio
constants (`RATIO_TEXT = 4.0`, `RATIO_TOOL_CALL = 2.5`, `RATIO_SYSTEM = 3.5`) and helper
functions (`estimate_tokens_for_text`, `estimate_tokens_for_assistant_with_tool_calls`,
`estimate_tokens`) used to estimate LLM token usage from message content.

`scripts/agent/services/context_view.py`'s `_token_breakdown` function (lines 93-133)
independently defines local constants `_RATIO_TEXT = 4.0`, `_RATIO_TOOL_CALL = 2.5`,
`_RATIO_SYSTEM = 3.5` and reimplements the same `int(len(text) / ratio)` /
`int(tool_call_serialized_length(tc) / ratio)` arithmetic to build a three-bucket
breakdown (`system`, `history`, `tool_messages`) for context-budget display.

This was found during a behavior-preserving refactor cycle on
`scripts/shared/token_estimation.py` (2026-08-13) but was out of scope there because
`context_view.py` lives outside `scripts/shared/` and that refactor's scope was limited
to one file at a time.

## Problem
The ratio values and per-character arithmetic are maintained in two places. A future
tuning of a ratio constant (e.g. adjusting `RATIO_TEXT` for a new model family) applied
to `shared/token_estimation.py` would silently not propagate to `context_view.py`,
producing inconsistent token estimates between the two call sites with no test or lint
signal to catch the drift.

Verification performed for this requirement (2026-08-13): direct comparison of both
implementations' source confirms the three ratio values are currently identical
(4.0 / 2.5 / 3.5) and the per-item arithmetic is identical
(`int(len(text) / ratio)` for text/system, `int(tool_call_serialized_length(tc) / ratio)`
for tool calls). A manual side-by-side run over a representative message list (system +
user + assistant-with-tool-call + tool-result + assistant-text) produced matching total
token counts (115 in both), confirming there is currently **no** behavioral divergence
between the two implementations. This is a pure duplication-removal case, not a
correctness bug.

## Reason for change
Two independently-maintained copies of the same formula are a maintenance and
correctness risk: nothing prevents them from diverging in the future, and any change to
one is easy to forget to apply to the other. Consolidating onto a single source of
truth removes that risk without changing current behavior.

## Implementation intent
Have `context_view.py` import and reuse `scripts/shared/token_estimation.py`'s ratio
constants (`RATIO_TEXT`, `RATIO_TOOL_CALL`, `RATIO_SYSTEM`) instead of redefining private
local constants (`_RATIO_TEXT`, `_RATIO_TOOL_CALL`, `_RATIO_SYSTEM`) inside
`_token_breakdown`. Where it fits cleanly without changing `_token_breakdown`'s existing
three-bucket (`system` / `history` / `tool_messages`) output shape, also reuse
`estimate_tokens_for_text` for the per-item division; do not force a reuse that would
require restructuring `_token_breakdown`'s bucket semantics (its buckets differ from
`shared.token_estimation.estimate_tokens`'s `text`/`tool_calls`/`system` breakdown keys
— e.g. `context_view.py` buckets "tool" role text into `tool_messages`, while
`shared.token_estimation.estimate_tokens` buckets it into `text`). Constant reuse alone
fully addresses the drift risk described in Problem; deeper function-level reuse is a
nice-to-have, not a requirement.

## Implementation instructions
1. In `scripts/agent/services/context_view.py`, add an import of `RATIO_TEXT`,
   `RATIO_TOOL_CALL`, `RATIO_SYSTEM` from `shared.token_estimation` (module-level import,
   grouped with the existing `from shared...` imports at the top of the file).
2. Remove the local constant definitions `_RATIO_TEXT: float = 4.0`,
   `_RATIO_TOOL_CALL: float = 2.5`, `_RATIO_SYSTEM: float = 3.5` from inside
   `_token_breakdown` (lines 108-110).
3. Replace all four usages of `_RATIO_TEXT`, `_RATIO_TOOL_CALL`, `_RATIO_SYSTEM` inside
   `_token_breakdown` (lines 119, 122, 124, 127, 131) with the imported
   `RATIO_TEXT`/`RATIO_TOOL_CALL`/`RATIO_SYSTEM` names.
4. Do not change any arithmetic, bucket assignment, or the function's return shape —
   this is a pure identifier substitution plus an import, not a logic change.
5. Optionally (not required): if `estimate_tokens_for_text` can be called in place of the
   inline `int(len(text) / ratio)` expressions without changing which bucket
   (`sys_tokens`/`hist_tokens`/`tool_tokens`) a value lands in, do so for further
   deduplication. Skip this if it would require restructuring `_token_breakdown`'s
   control flow.
6. Do not change the numeric ratio values themselves — that is a behavior change out of
   scope for this requirement.
7. Re-run the equivalence check (comparable to the manual verification described in
   Problem) after the change to confirm output is byte-for-byte identical to before the
   change for the same inputs.

## Acceptance criteria
- `scripts/agent/services/context_view.py` no longer defines `_RATIO_TEXT`,
  `_RATIO_TOOL_CALL`, or `_RATIO_SYSTEM`; it imports the equivalent names from
  `shared.token_estimation`.
- `_token_breakdown`'s per-category output (`token_system`, `token_history`,
  `token_tool_messages`) is byte-for-byte unchanged for existing test inputs and for the
  representative message list used during verification.
- No change to `scripts/shared/token_estimation.py`'s public constants or function
  signatures (this requirement only adds consumers, it does not change that module's
  contract) unless a follow-up need to export something not already exported is
  discovered, in which case the addition must be purely additive.
- `ruff` and `mypy` pass on both changed files with no new suppressions.
