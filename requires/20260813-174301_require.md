# Document the repo-wide convention that a module-level `logger` may be declared ahead of first use

## Priority
Low

## Target files
- `rules/coding.md` (add the convention note)
- Reference-only, no change required, but re-verify at implementation time:
  - `scripts/shared/token_estimation.py`
  - `scripts/shared/llm_client.py`
  - `scripts/shared/llm_sse_stream.py`
  - `scripts/shared/mcp_config.py`
  - `scripts/shared/tool_registry.py`

## Background
Verified against current source (2026-08-13):

- Five modules under `scripts/shared/` declare a module-level `logger = logging.getLogger(__name__)`
  that is never invoked anywhere else in the same file (confirmed via `rg -n "logger" <file>` per
  file — the declaration line is the only occurrence in each): `token_estimation.py:10`,
  `llm_client.py:25`, `llm_sse_stream.py:18`, `mcp_config.py:22`, `tool_registry.py:36`. No other
  module imports `logger` from any of these five files either, so the declarations are genuinely
  unreferenced, not consumed elsewhere.
- `uv run vulture scripts/shared/ --min-confidence 60 | grep -i logger` does not flag any of these
  five declarations — vulture treats a bare module-level attribute assignment like
  `logger = logging.getLogger(__name__)` as potentially used elsewhere and does not report it the
  way it reports unused local variables, functions, or classes. Vulture is therefore not a reliable
  signal for this specific pattern; the `rg`-based manual check above is authoritative.
- This is not an isolated occurrence: at least 11 other `scripts/shared/*.py` modules
  (`config_loader.py`, `git_helper.py`, `http_transport.py`, `llm_reconnect.py`, `llm_retry.py`,
  `mcp_health.py`, `otel_tracer.py`, `route_resolver.py`, `token_counter.py`, `tool_executor.py`,
  `tool_transport_invoker.py`) declare the identical `logger = logging.getLogger(__name__)` pattern
  and *do* call `logger.*` at least once. Across `scripts/shared/`, declaring a module-level logger
  at the top of the file is close to a universal pattern; the five files above are simply the subset
  that have not yet grown a call site.
- No written policy on this exists anywhere in the repo today. `rules/coding.md` (121 lines, checked
  in full) has no mention of "logger" at all. `CLAUDE.md` has no logger mentions. `docs/` describes
  how the `Logger` class is used in various modules but never states a convention about declaring an
  as-yet-unused module-level logger, and never mentions vulture/dead-code linting in connection with
  loggers.
- Found during a behavior-preserving refactor cycle on `scripts/shared/token_estimation.py`
  (2026-08-13). Not removed there because the pattern recurs across many sibling modules, which is
  evidence of an established repo convention rather than file-local dead code, but this had not been
  confirmed against any written rule.

## Problem
The repo has a de facto but undocumented convention: every module under `scripts/shared/` declares a
module-level `logger`, and a subset of those declarations currently have no call site in their file.
Because the convention is unwritten, each future refactor cycle that touches one of these five files
(or discovers a similar case elsewhere) has to independently re-decide whether the unused `logger` is
intentional boilerplate or removable dead code, at risk of one file's declaration being deleted while
an untouched sibling module keeps the identical pattern — producing an inconsistent codebase and
wasted repeat investigation of the exact question this requirement settles once.

## Reason for change
The evidence favors treating this as an intentional, low-cost convention rather than dead code to
delete:
- The pattern is the norm, not the exception: 11 of 16 `scripts/shared/*.py` modules that declare a
  module-level logger already call it; the 5 in question are simply modules that have not yet needed
  a log call, not modules where the declaration was a one-off mistake.
- A single `logger = logging.getLogger(__name__)` line is effectively zero-risk and zero-maintenance:
  it does not execute any logging I/O until a call site is added, so its presence carries no runtime
  cost or correctness risk.
- Removing it now only to have the very next feature or bug-fix in that same file need a logger again
  means each affected file would re-add the identical boilerplate line later, and the codebase would
  cycle between "removed for cleanliness" and "re-added for use" with no net benefit — pure churn.
- Codifying the decision in `rules/coding.md` (the project's single source of truth for shared
  conventions, per its own header) removes the ambiguity for future refactor cycles and reviewers,
  so this exact question is not re-litigated per file each time it resurfaces.

## Implementation intent
Adopt Option A from the source issue: confirm the module-level "logger declared ahead of first use"
pattern is an accepted, intentional convention across `scripts/shared/`, and add a short, explicit
note to `rules/coding.md` stating this so future refactor or dead-code-removal passes recognize it as
accepted and do not re-flag it file by file. Do not remove any of the five currently-unused logger
declarations — this requirement is documentation-only (a `rules/coding.md` addition); no
`scripts/shared/*.py` file content changes as part of this requirement.

## Implementation instructions
1. Open `rules/coding.md` and add a new short subsection (a natural location is near the "Key library
   choices" or "Documentation notes" sections, or as its own small section — follow the existing
   heading style, e.g. `##`-level with a short table or bullet list, consistent with the rest of the
   file).
2. State the convention explicitly, in English, along these lines (adapt wording to match the file's
   existing tone, do not copy verbatim if it reads awkwardly in context):
   - Every module under `scripts/shared/` may declare `logger = logging.getLogger(__name__)` at
     module level even before the module has a call site for it; this is accepted, intentional
     boilerplate anticipating near-future use, not dead code.
   - Dead-code tools (`vulture`, manual review, refactor cycles) should not flag or remove an unused
     module-level `logger` declaration on this basis alone.
   - This convention applies specifically to the `logger = logging.getLogger(__name__)` declaration
     pattern; it does not exempt other unused module-level names (imports, constants, functions) from
     normal dead-code review — scope the note narrowly to loggers.
3. Do not modify any of the five files listed in Target files, and do not modify any other
   `scripts/*.py` file — this requirement's only content change is the `rules/coding.md` addition.
4. Do not modify any `docs/*.md` file — the convention belongs in `rules/coding.md` (a coding
   convention, not user-facing behavior documentation).
5. Keep the added note concise (a few lines / a short bullet list) — this is a policy clarification,
   not a new section requiring extensive elaboration.

## Acceptance criteria
- `rules/coding.md` contains an explicit, unambiguous statement that a module-level
  `logger = logging.getLogger(__name__)` declared ahead of its first call site is an accepted
  convention in `scripts/shared/` (and, by the same reasoning, elsewhere `logging.getLogger` is used
  the same way), not dead code to be removed on sight.
- No `scripts/shared/*.py` file is modified as part of this requirement; the five currently-unused
  logger declarations remain exactly as they are.
- No `docs/*.md` file is modified.
- A future reviewer or automated refactor pass reading `rules/coding.md` alone (without re-deriving
  the reasoning in this requirement's Background section) can determine that an unused module-level
  `logger` in `scripts/shared/` does not need to be flagged or removed.
