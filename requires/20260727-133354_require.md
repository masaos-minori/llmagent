# Add allowlist/denylist validation for MCP server subprocess env vars

## Priority

Low

## Target Files

- `scripts/agent/http_lifecycle.py:224-226` — `HttpServerLifecycleManager.start()` merges `cfg.env` into the subprocess environment with no key/value filtering
- `scripts/shared/mcp_config.py:110-119` (`McpServerConfig._validate_cross_fields()`) — only validates that `env` is `dict[str, str]`, never inspects key names for dangerous entries
- `config/shell_mcp_server.toml:33-38` — reference: existing `env_allowlist` / `env_denylist` pattern already used for shell-exec request env

## Background

`HttpServerLifecycleManager.start()` launches MCP server subprocesses configured under `[mcp_servers.<key>]` in `config/agent.toml`-family files. It builds the subprocess environment by merging the full parent process environment with `cfg.env`:

```python
env = None
if cfg.env:
    env = {**os.environ, **cfg.env}
```

`McpServerConfig._validate_cross_fields()` in `scripts/shared/mcp_config.py` validates `env` only for type shape (`dict[str, str]`); it does not check whether keys are sensitive/dangerous (e.g. `LD_PRELOAD`, `LD_LIBRARY_PATH`, `PYTHONPATH`).

A parallel mechanism already exists for shell-exec requests: `config/shell_mcp_server.toml` defines `env_allowlist` (permitted keys; when non-empty, only listed keys pass) and `env_denylist` (glob patterns removed when `env_allowlist` is empty, e.g. `["LD_PRELOAD", "LD_LIBRARY_PATH", "PYTHONPATH"]`). No equivalent control exists for the MCP server startup env path.

## Problem

There is a design inconsistency: the shell-exec request path protects against dangerous env var overrides via an allow/deny list, but the MCP server subprocess startup path (`HttpServerLifecycleManager.start()` / `McpServerConfig`) has no equivalent check. `cfg.env` values from `config/agent.toml` are merged into the subprocess env unconditionally, so any key (including `LD_PRELOAD`, `LD_LIBRARY_PATH`, `PYTHONPATH`, etc.) can silently override the inherited parent environment for that subprocess.

Risk is limited in practice because `cfg.env`/`cfg.cmd` originate from admin-controlled configuration files, not untrusted user input. However, the lack of a corresponding safeguard is a consistency gap versus the precedent already set in `shell_mcp_server.toml`.

## Reason for Change

Bring the MCP server startup env-merge path in line with the existing defense-in-depth pattern used for shell-exec env handling, so that a misconfigured or compromised `config/agent.toml` entry cannot silently inject dangerous env vars (e.g. `LD_PRELOAD`) into an MCP server subprocess. This also removes the current inconsistency between the two config surfaces, making the codebase's security posture uniform and self-documenting.

## Implementation Intent

Add an allowlist/denylist validation step for `McpServerConfig.env`, mirroring the `env_allowlist` / `env_denylist` mechanism already defined in `config/shell_mcp_server.toml`, either by:
- reusing the same denylist of dangerous glob patterns (`LD_PRELOAD`, `LD_LIBRARY_PATH`, `PYTHONPATH`, and similar loader/interpreter-hijacking variables) as a default denylist applied in `McpServerConfig._validate_cross_fields()`, or
- introducing an equivalent `env_denylist`/`env_allowlist` config option scoped to `[mcp_servers.<key>]` and enforcing it at config-build time in `scripts/shared/mcp_config.py`.

If, after implementation review, the team decides no additional validation is warranted (because `cfg.env`/`cfg.cmd` are strictly admin-controlled), that decision must be recorded as an explicit code comment near `McpServerConfig._validate_cross_fields()` and `HttpServerLifecycleManager.start()` explaining why the shell-exec denylist precedent does not apply here, so the inconsistency is documented rather than silent.

## Implementation Instructions

1. Decide on an approach: (a) hardcode a shared denylist of dangerous env var name patterns reused from `config/shell_mcp_server.toml`'s `env_denylist` default (`LD_PRELOAD`, `LD_LIBRARY_PATH`, `PYTHONPATH`), or (b) add a configurable denylist/allowlist for MCP server env, consistent in shape with the shell_mcp_server.toml precedent.
2. If validation is added: extend `McpServerConfig._validate_cross_fields()` in `scripts/shared/mcp_config.py` (near the existing loop at lines 115-119 that checks `env` is `dict[str, str]`) to reject or filter keys matching the denylist glob patterns, raising a `ValueError` with a clear message identifying the offending key.
3. Ensure `HttpServerLifecycleManager.start()` in `scripts/agent/http_lifecycle.py` (lines 224-226) continues to work unchanged if validation is enforced earlier at config-load time; do not duplicate filtering logic in both places — pick one enforcement point (prefer config validation, since it fails fast at startup rather than at subprocess-spawn time).
4. If the team instead decides no validation is needed, add an explicit comment at `scripts/shared/mcp_config.py`'s `_validate_cross_fields()` and at `scripts/agent/http_lifecycle.py:224-226` stating the rationale (admin-controlled config, no untrusted input path) and referencing this requirement/issue for future readers.
5. Update or add unit tests covering the chosen behavior (see Tests section).

## Acceptance Criteria

- [ ] Either: `McpServerConfig` construction/validation rejects (or filters) `env` entries whose keys match a denylist of dangerous variable names (at minimum `LD_PRELOAD`, `LD_LIBRARY_PATH`, `PYTHONPATH`), with a clear error message; or an explicit code comment documents the deliberate decision not to add such validation, placed at both `scripts/shared/mcp_config.py` (`_validate_cross_fields`) and `scripts/agent/http_lifecycle.py` (`start()`).
- [ ] No change to legitimate, non-denylisted `cfg.env` behavior — existing valid MCP server configs continue to start subprocesses unaffected.
- [ ] The chosen behavior is consistent with (or explicitly justified as differing from) the `env_allowlist`/`env_denylist` precedent in `config/shell_mcp_server.toml`.

## Tests

- Add a unit test in the `scripts/shared/mcp_config.py` test suite verifying that an `McpServerConfig` with `env={"LD_PRELOAD": "/tmp/evil.so"}` (or equivalent denylisted key) either raises `ValueError` at validation time, or is filtered out before subprocess launch — whichever approach is chosen.
- Add/keep a regression test confirming that non-denylisted `env` entries (e.g. `{"MY_APP_TOKEN": "abc"}`) continue to validate successfully and are passed through to `HttpServerLifecycleManager.start()` unchanged.
- If the "document only, no validation" path is chosen instead, no new test is required, but confirm existing tests around `_validate_cross_fields()` still pass unchanged.
