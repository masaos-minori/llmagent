# Unknown Follow-up Issue Template (Canonical)

Use this exact Markdown structure for `issues/{timestamp}_unknowns.md` (or its
zero-padded-sequence variant) generated by `skills/issue-to-plan/workflow.md` Step 6,
when a Plan's Unknown is `BLOCKING: True` or otherwise requires standalone tracking
beyond the Plan's inline Unknowns table. This is a GitHub Issue Markdown document —
one issue per section when more than one Unknown is filed together — not a
`templates/issue.md`-shaped Issue.

```markdown
# Unresolved blocking unknown: <one-line summary>

## Summary
Briefly describe what remains unresolved and why it matters for the Plan.

## Evidence Missing
What investigation was attempted, and what could not be confirmed.

## Resolution Path
Concrete steps needed to resolve this Unknown.

## Blocking Impact
- **Blocking for:** the Requirement(s)/task(s) this blocks.
- **Not blocking for:** what can proceed independently of this Unknown.

## Related
- Plan: `{path to the Plan this Unknown was raised in}`
- Source issue: `{path to the Issue that produced the Plan}`

## Traceability
- Workflow phase: issue-to-plan
- Source issue: `{path}`
- Source plan: `{path}`
- Generated at: {timestamp from date +%Y%m%d-%H%M%S}
```

## Field notes

- Cite the source Plan's Unknown by its `ID` (e.g. `UNK-02`) inside `Summary` or
  `Resolution Path` rather than re-quoting the Plan's full Unknown Description text —
  see `skills/issue-to-plan/workflow.md` Step 6.
- The `Traceability` fields here are a deliberately narrower subset of
  `templates/traceability.md`'s full field list (no `Source requirement`, `Source
  implementation procedure`, or `Related target files`) — this document traces back to
  exactly one Issue and one Plan, never to a target file set.
- `Blocking Impact` distinguishes what this Unknown blocks from what it does not —
  never state only one side.
