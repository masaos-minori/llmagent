# MCP Protocol and Transport: Endpoints and Transport

## Purpose

To document the shared MCP protocol. It covers HTTP formats, common types, authentication, response truncation, audit logs, and error formats.

---

## Common Endpoints (All Servers)

| Endpoint | Method | Description |
|---|---|---|
| `/v1/call_tool` | POST | Execute a named tool |
| `/v1/tools` | GET | List available tools and descriptions |
| `/health` | GET | Health check |

All servers expose these endpoints. The `/health` response varies by server (see [Server-specific health](./mcp_02_02_startup-modes-and-health.md)).

Beyond these three, each server retains only non-execution diagnostics. The file-read server additionally exposes `GET /list_allowed_directories`, a diagnostic that returns resolved allowlist paths; it is retained as a sensitive diagnostic whose final disposition awaits a maintainer decision. No operation-specific execution route remains on any server — every tool runs through the single `POST /v1/call_tool` path below.

## HTTP Transport: `/v1/call_tool`

### Request

``` http
POST /v1/call_tool
Content-Type: application/json
Authorization: Bearer <token>   (auth_token is mandatory and non-empty for every MCP server, which refuses to start without it; see attach_auth_middleware() below)
X-Session-Id: <session_id>      (injected by ToolExecutor)

{"name": "tool_name", "args": {"key": "value"}}
```

`X-Session-Id` is set during agent startup via `ToolTransportInvoker.set_session_id()` and refreshed whenever the agent's active session id changes (session restore, new-session clear). It is injected into all POST requests by `HttpTransport.call()`. If a session-id change is not followed by a refresh, tool calls keep the previous session's id and server-side audit attribution is wrong for the rest of the run.

`X-Request-Id` is injected as a UUID in the response headers by the server's authentication middleware. A 401 rejection response is returned without the header.

Every MCP server registers that middleware and enforces the `Authorization` header (see `mcp_06_14_mcp-authentication-setup.md`).

### Correlation Keys

| Key | Type | Generated by | Appears in |
|---|---|---|---|
| `X-Session-Id` | HTTP request header | Agent (`ToolTransportInvoker.set_session_id()`) | Transport logs, server audit log (`session_id` field) |
| `X-Request-Id` | HTTP response header | Server auth middleware (UUID) | Transport logs, server audit log (`request_id` field), `ToolCallResult.request_id` |
| `server_key` | Log field | Agent router (`ToolRouteResolver`) | Agent dispatch logs, `ToolCallResult` |
| `tool_name` | Log field | Agent router | Agent logs, server audit log |

> For information on how to trace a single tool call across agent dispatch, transport, and MCP server logs, see [mcp_03 End-to-End Tool Call Tracing](./mcp_03_03_transport-and-health.md#end-to-end-tool-call-tracing).

### Response

```json
{"result": "<formatted text>", "is_error": false}
```

`is_error=true` indicates a tool-level error. Even in case of a tool error, the HTTP status remains 200. HTTP 4xx/5xx indicate transport-level errors.

### Idempotency Key for Side-Effecting Calls

`POST /v1/call_tool` is the single execution path for every tool. Side-effecting calls (operations that mutate state) must carry an `X-Idempotency-Key` request header. The shared request boundary rejects a keyless side-effecting call before dispatch; read-only keyless calls stay allowed. The set of side-effecting tools is defined centrally rather than per-server, so the same header requirement applies to every server.

## Request and Response Models

`CallToolRequest` (`name`, `args`) and `CallToolResponse` (`result`, `is_error`) are shared by all MCP servers so that the request/response structure is identical across servers. Definitions: `scripts/mcp_servers/models.py`.

## HTTP Tool List: `/v1/tools`

### Current fields

These fields are currently supported by the discovery service:

#### Top-level response fields

- `schema_version` — top-level discovery-time metadata (returned by all servers)

#### Per-tool fields

- `name` — per-tool identifier
- `description` — per-tool description
- `inputSchema` — per-tool schema (required; `input_schema` is not accepted)
- `status` — per-tool status
- `server_key` — server key injected by `build_tools_response()`
- `enabled` — maps to RuntimeTool.enabled_for_llm (returned by every MCP server; see [Tool Runtime Availability Metadata](./mcp_03_06_tool-runtime-availability-metadata.md))
- `disabled_reason` — reason when disabled (returned by every MCP server)
- `is_write` — whether the tool performs writes (schema-2.0, **required** — a missing/invalid value rejects the tool entry, see [mcp_03_02_tool-registry.md](./mcp_03_02_tool-registry.md))
- `requires_serial` — whether the tool requires serial execution (schema-2.0, **required**)
- `resource_scope_kind` / `resource_scope_keys` — declared scope kind (e.g. `"filesystem"`, `"git_repo"`) and the argument keys whose values feed the resolved per-call scope (schema-2.0, **required**); resolved into `ToolSpec.resource_scopes` at call time by `shared/resource_scope.py::resolve_resource_scopes()`
- `capabilities` — optional capability flags (per-tool)
- `config_dependent` — whether the tool depends on configuration state

### Query parameters and deferred fields

`GET /v1/tools` accepts `include_disabled` (default `false`; disabled tools are omitted unless `true`) and `disabled_code` (compared against `disabled_reason`).

Not implemented:

- Top-level `capabilities` — not returned by `build_tools_response()`

Called at startup to verify that configured tool names match live server tools.
In case of mismatch → the `RuntimeError` is surfaced as a `FATAL` startup finding and startup is aborted; there is no toggle.

## Call-State Control Endpoints

Two control paths are served alongside the tool paths. They are evidence paths for the Agent: a control path never runs a tool handler.

| Path | Method | Caller | Returns |
|---|---|---|---|
| `/v1/call_state/{key}` | GET | the Agent, with the control Bearer token | one call-state record |
| `/v1/call_state/{key}/reconcile` | POST | the Agent, with the control Bearer token | one reconcile decision |

`{key}` is the logical call id the caller already holds; it is checked against the same closed key pattern the ledger accepts, so a value that cannot be a ledger key is refused before any lookup. Control requests carry `X-Request-Id` like any other request on a server. Authorization posture: [mcp_05_01](./mcp_05_01_access-control-and-allowlists.md); logging rules: [mcp_02_03](./mcp_02_03_audit-logging-and-errors.md).

### Call-state response fields

| Field | Meaning |
|---|---|
| `key` | logical call id |
| `ledger_status` | the row state the mapping table covers: `pending`, `completed`, `failed`, `interrupted` |
| `agent_state` | the state the shared mapping table gives for `ledger_status` and `lease_live` |
| `attempt_number`, `lease_live`, `lease_expires_epoch` | attempt and lease facts |
| `result_class`, `result_code`, `result_size_bytes`, `result_sha256`, `external_ref` | result availability facts, recorded at terminal finalization: the stored result for a completed call, the error class with `replay_unavailable` for a failed call |
| `reconciliation_required` | true when the state needs an operator decision |
| `error_code` | stable code, see Error codes |

Every field is a closed-vocabulary value or an opaque identifier. No response carries raw arguments, credentials, signed URLs, raw exceptions, or internal paths, and no response carries evidence text.

### Result classes

| Class | Meaning |
|---|---|
| `complete` | the stored result is available in full |
| `secure_reference` | the result is represented by an opaque external reference |
| `redacted_preview` | only a redacted preview is stored; `result_sha256` and `result_size_bytes` still describe the full result |
| `replay_unavailable` | no result facts can be reported beyond the error class, so the caller must not re-run the tool |

`result_sha256` and `result_size_bytes` always describe the full serialized result, whatever the class.

### Reconcile decisions and outcomes

Decisions: `reused_completed` (a completed call is reported as it is and is never mutated by a control path), `reconciled` (a stale pending row was moved through the existing reconciliation path), `operator_review`, `refused`.

Outcomes: `evidence_found`, `no_evidence`, `ambiguous`, `unverifiable`, plus `none` when no reconciler ran. Only `evidence_found` and `no_evidence` move a row; `ambiguous` and `unverifiable` report that operator review is needed and leave the row as it is. A decision carries a digest of its evidence, never the evidence itself.

### Error codes

`none`, `unknown_key`, `lease_live`, `attempts_exhausted`, `not_reconcilable`, `reconciler_failed`, `handler_failed`, `store_unavailable`. A value that cannot be a ledger key is reported as `invalid_key`.

### Failure behavior

| Situation | Result |
|---|---|
| Unknown key | 404 `unknown_key` |
| Live lease | 409, `refused` with `lease_live` |
| Attempts exhausted | 409, `refused` with `attempts_exhausted` and operator review |
| Control path with an empty control token | 401 |
| Control token set but no validated dedup configuration | 503 `store_unavailable` |
| A key that cannot be a ledger key | 422 `invalid_key` |
| Method mismatch on a control path | 405 `invalid_key` |

On the Agent side, any control problem — an unconfigured or empty control token, an unreachable server, a failed request, or a payload outside these vocabularies — establishes nothing: the caller keeps the outcome it would have had without the control read, and no handler is run.

## MCPServer Base Class (`scripts/mcp_servers/server.py`)

All MCP servers inherit from `MCPServer`. Subclasses declare their identity (`server_name`, `server_version`, loopback `http_host`, `http_port`, `app_module`, tool definitions) and implement `dispatch(name, args) -> DispatchResult`, which is abstract. Port numbers are owned by `config/agent.toml`.

Contracts owned by the base class:

- **Health**: `health()` returns `(health_dict, http_status)`; HTTP 200 if `ready=True`, 503 if `ready=False`. The health dict carries `status` (`ok` / `degraded`), `ready`, `liveness`, `restart_recommended`, `operator_action_required`, `dependencies`, and `details`. The base implementation always reports `ok` / ready; every MCP server overrides it and builds its response with `make_health_response(deps, details)` (`mcp_servers/health_response.py`). See [mcp_02_02](./mcp_02_02_startup-modes-and-health.md) for details.
- **Loopback-only binding**: `run_http()` raises `ValueError` before binding if `http_host` is not `"127.0.0.1"` or `"::1"`. Every internal MCP server binds to loopback only, with no override. The bound socket address is verified to be loopback again immediately after startup (defense-in-depth, independent of the pre-bind check).
- **Authentication**: `attach_auth_middleware(app, token)` rejects requests without a matching `Authorization: Bearer <token>` header with HTTP 401. An empty `token` is also fail-closed in the middleware: every request gets 401 and no accept-all opt-out exists (Explicit in code — scripts/mcp_servers/server.py `attach_auth_middleware`). Every MCP server additionally refuses to start with an empty `auth_token` (`require_auth_token()`), and `McpServerConfig` construction-time validation and `agent.startup_validation`'s "MCP authentication check" reject it before the agent calls a server.
- **Tool listing**: every server's `/v1/tools` handler annotates its own `TOOL_LIST` and passes it to `build_tools_response()`.
- **Control paths**: the control API middleware is registered after the tool-auth middleware, so it runs first and control paths are answered there and never reach tool authentication. Control paths use a separate control credential, and their response vocabulary is the shared call-state contract rather than a per-server shape. A server whose control token is empty keeps serving tool paths with its own token; only the control paths are closed.
- **Truncation**: oversized responses are truncated by the base class; the result carries total and visible byte counts so the truncation is observable.
