# MCP Protocol and Transport: Endpoints and Transport

## Purpose

To document the shared MCP protocol. It covers HTTP formats, common types, authentication, response truncation, audit logs, and error formats.

---

## Common Endpoints (All Servers)

| Endpoint | Method | Description |
|---|---|---|
| `/v1/call_tool` | POST | Execute a named tool |
| `/v1/tools` | GET | List available tools and descriptions |
| `/health` | GET | Health check |

All servers expose these endpoints. The `/health` response varies by server (see [Server-specific health](./mcp_02_02_startup-modes-and-health.md)).

---

## HTTP Transport: `/v1/call_tool`

### Request

``` http
POST /v1/call_tool
Content-Type: application/json
Authorization: Bearer <token>   (auth_token is mandatory and non-empty for every MCP server, which refuses to start without it; see attach_auth_middleware() below)
X-Session-Id: <session_id>      (injected by ToolExecutor)

{"name": "tool_name", "args": {"key": "value"}}
```

`X-Session-Id` is set during agent startup via `ToolTransportInvoker.set_session_id()` and is injected into all POST requests by `HttpTransport.call()`.

`X-Request-Id` is injected as a UUID in the response headers by the server's authentication middleware.

Every MCP server registers that middleware and enforces the `Authorization` header (see `mcp_06_14_mcp-authentication-setup.md`).

### Correlation Keys

| Key | Type | Generated by | Appears in |
|---|---|---|---|
| `X-Session-Id` | HTTP request header | Agent (`ToolTransportInvoker.set_session_id()`) | Transport logs, server audit log (`session_id` field) |
| `X-Request-Id` | HTTP response header | Server auth middleware (UUID) | Transport logs, server audit log (`request_id` field), `ToolCallResult.request_id` |
| `server_key` | Log field | Agent router (`ToolRouteResolver`) | Agent dispatch logs, `ToolCallResult` |
| `tool_name` | Log field | Agent router | Agent logs, server audit log |

> For information on how to trace a single tool call across agent dispatch, transport, and MCP server logs, see [mcp_03 End-to-End Tool Call Tracing](./mcp_03_03_transport-and-health.md#end-to-end-tool-call-tracing).

### Response

```json
{"result": "<formatted text>", "is_error": false}
```

`is_error=true` indicates a tool-level error. Even in case of a tool error, the HTTP status remains 200. HTTP 4xx/5xx indicate transport-level errors.

## Request and Response Models

`CallToolRequest` (`name`, `args`) and `CallToolResponse` (`result`, `is_error`) are shared by all MCP servers so that the request/response structure is identical across servers. Definitions: `scripts/mcp_servers/models.py`.

## HTTP Tool List: `/v1/tools`

### Current fields

These fields are currently supported by the discovery service:

#### Top-level response fields

- `schema_version` — top-level discovery-time metadata (returned by all servers)

#### Per-tool fields

- `name` — per-tool identifier
- `description` — per-tool description
- `inputSchema` — per-tool schema (required; `input_schema` is not accepted)
- `status` — per-tool status
- `server_key` — server key injected by `build_tools_response()`
- `enabled` — maps to RuntimeTool.enabled_for_llm (returned by every MCP server; see [Tool Runtime Availability Metadata](./mcp_03_06_tool-runtime-availability-metadata.md))
- `disabled_reason` — reason when disabled (returned by every MCP server)
- `is_write` — whether the tool performs writes (schema-2.0, **required** — a missing/invalid value rejects the tool entry, see [mcp_03_02_tool-registry.md](./mcp_03_02_tool-registry.md))
- `requires_serial` — whether the tool requires serial execution (schema-2.0, **required**)
- `resource_scope_kind` / `resource_scope_keys` — declared scope kind (e.g. `"filesystem"`, `"git_repo"`) and the argument keys whose values feed the resolved per-call scope (schema-2.0, **required**); resolved into `ToolSpec.resource_scopes` at call time by `shared/resource_scope.py::resolve_resource_scopes()`
- `capabilities` — optional capability flags (per-tool)
- `config_dependent` — whether the tool depends on configuration state

### Query parameters and deferred fields

`GET /v1/tools` accepts `include_disabled` (default `false`; disabled tools are omitted unless `true`) and `disabled_code` (compared against `disabled_reason`).

Not implemented:

- Top-level `capabilities` — not returned by `build_tools_response()`

Called at startup to verify that configured tool names match live server tools.
In case of mismatch → warning log; if `tool_definitions_strict=True` → `RuntimeError`.

## MCPServer Base Class (`scripts/mcp_servers/server.py`)

All MCP servers inherit from `MCPServer`. Subclasses declare their identity (`server_name`, `server_version`, loopback `http_host`, `http_port`, `app_module`, tool definitions) and implement `dispatch(name, args) -> DispatchResult`, which is abstract. Port numbers are owned by `config/agent.toml`.

Contracts owned by the base class:

- **Health**: `health()` returns `(health_dict, http_status)`; HTTP 200 if `ready=True`, 503 if `ready=False`. The health dict carries `status` (`ok` / `degraded`), `ready`, `liveness`, `restart_recommended`, `operator_action_required`, `dependencies`, and `details`. The base implementation always reports `ok` / ready; every MCP server overrides it and builds its response with `make_health_response(deps, details)` (`mcp_servers/health_response.py`). See [mcp_02_02](./mcp_02_02_startup-modes-and-health.md) for details.
- **Loopback-only binding**: `run_http()` raises `ValueError` before binding if `http_host` is not `"127.0.0.1"` or `"::1"`. Every internal MCP server binds to loopback only, with no override. The bound socket address is verified to be loopback again immediately after startup (defense-in-depth, independent of the pre-bind check).
- **Authentication**: `attach_auth_middleware(app, token)` rejects requests without a matching `Authorization: Bearer <token>` header with HTTP 401. With an empty `token` the middleware alone would accept all requests, a fallback that exists only for standalone testing: every MCP server refuses to start with an empty `auth_token`, and `McpServerConfig` construction-time validation and `agent.startup_validation`'s "MCP authentication check" also reject it before the agent calls a server.
- **Tool listing**: every server's `/v1/tools` handler annotates its own `TOOL_LIST` and passes it to `build_tools_response()`.
- **Truncation**: oversized responses are truncated by the base class; the result carries total and visible byte counts so the truncation is observable.
