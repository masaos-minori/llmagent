# RAG index consistency checks

The RAG index requires synchronization between the following three tables:
- `chunks` — The primary chunk records.
- `chunks_fts` — FTS5 full-text search index (generated by SQLite triggers).
- `chunks_vec` — Vector embedding index.

## Startup Warnings

On every agent startup, a RAG consistency check is performed via `check_rag_consistency()` (3 COUNT queries, read-only, high performance). If an inconsistency is detected, a warning is printed to the console.

```text
[RAG] Consistency issue: fts_gap=3 (3 chunks missing from FTS index)
```

If the index is healthy, no warning is shown (`logger.info("RAG consistency: OK")` is logged instead).

## `/session rag-rebuild-fts` Command

The `/session rag-rebuild-fts` command rebuilds `chunks_fts` from the base `chunks` table.

**Rebuild Rules:** Rebuilding indexes `COALESCE(normalized_content, content)`. This is identical to the FTS5 trigger (`chunks_ai`).

- **Japanese chunks:** If `normalized_content` (already normalized with Sudachi) exists, it is indexed.
- **English/Code chunks:** Since `normalized_content` is NULL, FTS5 falls back directly to `content`.
- **DO NOT manually edit `chunks_fts`** — this is a derived index maintained by triggers or the rebuild process.

**When to use:**
- When `fts_gap > 0` (missing FTS entries) is detected by `/session rag-consistency`.
- When `fts_orphan_count > 0` (extra FTS entries, risk of data loss) is detected.
- To verify FTS index integrity after large ingestions.

**Repair Decision Flow:**

| Issue | Fix |
|---|---|
| `fts_gap > 0` | Run `/session rag-rebuild-fts` — Rebuilds from `chunks` because FTS entries are missing. |
| `fts_orphan_count > 0` | Run `/session rag-rebuild-fts` — Removes extra entries in FTS (risk of data loss; urgent action required). |

## `/session rag-consistency` Command

The `/session rag-consistency` command displays numerical counts and then shows an OK status or a summary of errors.

```yaml
  chunks: 1042  fts: 1042  vec: 1042  fts_gap: 0  orphan_vec: 0  fts_orphan: 0
RAG consistency: OK (chunks/FTS/vec in sync)
```

If there is an inconsistency:

```yaml
  chunks: 1042  fts: 1039  vec: 1042  fts_gap: 3  orphan_vec: 0  fts_orphan: 0
RAG consistency: FAIL
Consistency issue: [WARNING] FTS gap detected (chunks=1042, fts=1039, gap=3). Affected doc_ids: [1, 2, 3]. Run '/session rag-rebuild-fts' to repair.
```

## Threshold Policy

This check uses a **strict zero** threshold. That is, if any of `fts_gap`, `fts_orphan_count`, or `orphan_vec_count` is non-zero, an inconsistency is reported. Configurable thresholds (e.g., allowing `fts_gap <= 5`) are not implemented. Whether a policy for partial "OK" results is needed **requires verification**.

## Fixing Inconsistencies

Use `/session rag-consistency` to detect issues. The report includes identifiers for affected `chunk_id`/URLs (up to 10 each), allowing operators to respond without manual DB investigation.

**Repair Decision Flow:**

| Issue | Fix |
|---|---|
| `fts_gap > 0` | Run `/session rag-rebuild-fts` — Rebuilds from `chunks` because FTS entries are missing. |
| `fts_orphan_count > 0` | Run `/session rag-rebuild-fts` — Removes extra entries in FTS (risk of data loss; urgent action required). |
| `orphan_vec_count > 0` | Run `ingester.py --force` for the affected URL — For rows in `chunks_vec` that have no corresponding row in `chunks`. |
| `vec != chunks` | Run `ingester.py --force` for the affected URL |

Run `/session rag-rebuild-fts` to re-sync `chunks_fts` from the `chunks` table.
