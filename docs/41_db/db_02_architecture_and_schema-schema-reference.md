## 5. rag.sqlite Schema

`documents` holds document metadata (unique `url`, `lang` constrained to ja/en, fetch/cache validators, chunking strategy); `chunks` holds chunk content keyed by `chunk_id`, with `doc_id` referencing `documents` `ON DELETE CASCADE`. Column definitions: `db/schema_sql.py` (`_RAG_SCHEMA_TEMPLATE`). Timestamp columns use the Z-suffix format (see Timestamp Format Policy); `fetched_at` is always supplied by callers.

### `chunks_fts` (FTS5 virtual table)

FTS5 virtual table for full-text search on chunk content, indexing `COALESCE(normalized_content, content)`. It is a derived index of `chunks`, synchronized automatically by AFTER INSERT/UPDATE/DELETE triggers on `chunks`. IMPORTANT: Do not manually synchronize chunks_fts after INSERT/UPDATE/DELETE — triggers handle it automatically.

### `chunks_vec` (sqlite-vec virtual table)

sqlite-vec virtual table for vector similarity search. Stores float32 little-endian embeddings keyed by `chunk_id`; the dimension is `scripts/db/store_protocols.py::get_embedding_dims()`, a fixed code-level constant (not a config key). `chunks_vec` has no foreign key to `chunks`; rows are written and deleted explicitly by the ingestion and deletion paths, and the `chunks_vec_ad` trigger (AFTER DELETE ON chunks) deletes the matching row as a backstop, including when the delete comes from the `documents` cascade.

## 6. session.sqlite Schema

`session.sqlite` holds `sessions` (including `undo_floor_message_id`, the `/undo` compression boundary: the last `messages` row ID written by the latest compression, 0 when never compressed), `messages` (FK to `sessions` `ON DELETE CASCADE`), `memories` (semantic/episodic long-term memory, PK UUID v4), `memories_fts` (FTS5 BM25 index over content/summary/tags), `memories_vec` (sqlite-vec KNN index; dimension from the fixed `get_embedding_dims()` constant, see section 5; written only when `embed_enabled=True`), `memory_links` (many-to-many deduplication table, composite PK, no FK, `INSERT OR IGNORE`) and `session_diagnostics` (system-level events kept apart from conversation messages because of different lifecycle and query patterns; FK to `sessions` `ON DELETE CASCADE`). Column definitions: `db/schema_sql.py`.

`memories.session_id` records the source session of a memory for provenance.
It does not establish ownership and intentionally has no foreign-key constraint
to `sessions`. The value is retained after the source session is deleted. The constraint is omitted so that session deletion and retention never cascade into long-term memory, and so that a memory may outlive its source session; adding a foreign key or linking the two deletions requires an ADR.

## 7. workflow.sqlite Schema

Initialized by `create_workflow_schema()`, used by `agent/workflow/state_store.py`. Task and tool-state tables (tasks, attempts, processed_events, artifacts, tool_call_state) are created with `CREATE TABLE IF NOT EXISTS` (DDL in `scripts/db/schema_sql.py`). `tasks.status` accepts only `pending`, `running`, `completed`, `failed`, `halted` and `attempts.status` only `running`, `completed`, `failed`: every write is validated by the workflow ops helpers before SQL runs, and fresh databases additionally carry matching CHECK constraints (the pattern already established for `tool_call_state.state`). `check_workflow_schema()` (agent startup) accepts only databases that carry the current required tables and columns and no legacy migration markers, and the deploy pre-flight rejects `schema_migrations` or `workflow_schema_version` outright; such a legacy database must be archived and recreated by the operator. Recovery: recreate the workflow database ([db_07 section 11](db_07_api_and_operations-recovery-and-reference.md#11-db-recreation-procedure)).

Each `tasks` row carries a `task_nonce`: a globally unique opaque identifier (UUID4) generated by `create_task()`; it is never derived from caller-supplied fields. The `tasks.task_nonce` UNIQUE constraint is a backstop, not an identity or deduplication mechanism. Task identity is `task_id`: task reuse across a retained `workflow.sqlite` is by `task_id` (`get_task_by_id`), so a second `create_task()` call with identical arguments produces a new row — task-request deduplication does not exist. Stage re-execution is prevented by the event key in `processed_events`, not by the task nonce. `session_id` is the text form of the chat session id of the turn that created the task. End-of-session diagnostics count a session's tasks, workflows, execute attempts, and artifacts by this column, and a task created without a started session stores an empty string and is not counted. `turn_number` is recorded metadata only: it is a process-local counter (`agent/conversation_state_manager.py`). Neither value is part of task identity. A new session against a retained file always receives fresh, unique nonces.

`processed_events` rows are pruned on two paths, both at agent startup (`agent/workflow/state_store.py`). `StateStore.recover_stale_attempts()` deletes the rows of the (`task_id`, `stage_id`) pair of every attempt it marks failed, so a resumed stage re-executes instead of being skipped forever. `StateStore.purge_finished_workflow_events()` then deletes rows whose task is terminal (`completed`/`failed`/`halted`) with `updated_at` past the fixed 30-day `_EVENT_RETENTION_SEC` horizon. The `tasks` and `attempts` rows themselves are never pruned; the `ON DELETE CASCADE` foreign key on `processed_events.task_id` is available but no code path deletes `tasks` rows.

## 7a. eventbus.sqlite Schema

Independent persistence domain per [ADR-008](../10_adr/adr_02_05_008_db-sqlite-4db-separation.md) INV-04: `eventbus.sqlite` is the system of record for Event, Offset, Delivery, and DLQ state. Schema source: `scripts/eventbus/schema.sql` is the only DDL definition; `scripts/db/schema_sql.py::build_eventbus_schema_sql()` reads that file for the bootstrap via `create_schema()`, and the service creates the schema from the same file when the `events` table is missing (Decision Target `eventbus.persistence-schema.bootstrap-ddl`). ## 7b. Timestamp Format Policy

SQLite DEFAULT timestamps use strftime('%Y-%m-%dT%H:%M:%SZ', 'now') (Z suffix). Event Bus Python-side timestamps use `now_iso()` in `scripts/eventbus/json_utils.py`, which also produces the Z suffix. Python-side timestamps for workflow tables without a DEFAULT use datetime.now(UTC).isoformat(), which produces a +00:00 suffix. Consumers comparing timestamps across these sources MUST NOT assume a single suffix form.
