## 5. rag.sqlite Schema

`documents` holds document metadata (unique `url`, `lang` constrained to ja/en, fetch/cache validators, chunking strategy); `chunks` holds chunk content keyed by `chunk_id`, with `doc_id` referencing `documents` `ON DELETE CASCADE`. Column definitions: `db/schema_sql.py` (`_RAG_SCHEMA_TEMPLATE`). Timestamp columns use the Z-suffix format (see Timestamp Format Policy); `fetched_at` is always supplied by callers.

### `chunks_fts` (FTS5 virtual table)

FTS5 virtual table for full-text search on chunk content, indexing `COALESCE(normalized_content, content)`. It is a derived index of `chunks`, synchronized automatically by AFTER INSERT/UPDATE/DELETE triggers on `chunks`. IMPORTANT: Do not manually synchronize chunks_fts after INSERT/UPDATE/DELETE — triggers handle it automatically.

### `chunks_vec` (sqlite-vec virtual table)

sqlite-vec virtual table for vector similarity search. Stores float32 little-endian embeddings keyed by `chunk_id`; the dimension is `scripts/db/store_protocols.py::get_embedding_dims()`, a fixed code-level constant (not a config key). `chunks_vec` has no foreign key to `chunks`; rows are written and deleted explicitly by the ingestion and deletion paths, and the `chunks_vec_ad` trigger (AFTER DELETE ON chunks) deletes the matching row as a backstop, including when the delete comes from the `documents` cascade.

## 6. session.sqlite Schema

`session.sqlite` holds `sessions` (including `undo_floor_message_id`, the `/undo` compression boundary: the last `messages` row ID written by the latest compression, 0 when never compressed), `messages` (FK to `sessions` `ON DELETE CASCADE`), `memories` (semantic/episodic long-term memory, PK UUID v4), `memories_fts` (FTS5 BM25 index over content/summary/tags), `memories_vec` (sqlite-vec KNN index; dimension from the fixed `get_embedding_dims()` constant, see section 5; written only when `embed_enabled=True`), `memory_links` (many-to-many deduplication table, composite PK, no FK, `INSERT OR IGNORE`) and `session_diagnostics` (system-level events kept apart from conversation messages because of different lifecycle and query patterns; FK to `sessions` `ON DELETE CASCADE`). Column definitions: `db/schema_sql.py`.

`memories.session_id` records the source session of a memory for provenance.
It does not establish ownership and intentionally has no foreign-key constraint
to `sessions`. The value is retained after the source session is deleted. The constraint is omitted so that session deletion and retention never cascade into long-term memory, and so that a memory may outlive its source session; adding a foreign key or linking the two deletions requires an ADR.

## 7. workflow.sqlite Schema

Initialized by `create_workflow_schema()`, used by `agent/workflow/state_store.py`. Task tables (tasks, attempts, processed_events, artifacts) are created with `CREATE TABLE IF NOT EXISTS` (DDL in `scripts/db/schema_sql.py`). `workflow_schema_version` is an append-only log whose current version is the latest row; `create_workflow_schema()` records the `WORKFLOW_SCHEMA_VERSION` constant only when the log is empty and refuses to record over a different latest version (idempotent at the current version). Schema version mismatch: check_workflow_schema() (agent startup) and deploy/pre-flight both compare latest version against WORKFLOW_SCHEMA_VERSION constant, fail with [FATAL]/RuntimeError naming both versions if mismatch (includes case where no row exists yet). Recovery: recreate the workflow database ([db_07 section 11](db_07_api_and_operations-recovery-and-reference.md#11-db-recreation-procedure)).

Each `tasks` row carries an `idempotency_key` that is a globally unique opaque identifier (UUID4) generated by `create_task()`; it is never derived from caller-supplied fields. The `tasks.idempotency_key` UNIQUE constraint is a backstop against a future key-derivation regression, not the identity mechanism. `session_id` and `turn_number` are recorded metadata only; `turn_number` is a process-local counter (`agent/conversation_state_manager.py`) and is not part of task identity. Task reuse across a retained `workflow.sqlite` is by `task_id` (`get_task_by_id`), not by this key; a new session against a retained file always receives fresh, unique keys.

## 7a. eventbus.sqlite Schema

Independent persistence domain per [ADR-008](../10_adr/adr_02_05_008_db-sqlite-4db-separation.md) INV-04: `eventbus.sqlite` is the system of record for Event, Offset, Delivery, and DLQ state. Schema source: `scripts/eventbus/schema.sql` is the only DDL definition; `scripts/db/schema_sql.py::build_eventbus_schema_sql()` reads that file for the bootstrap via `create_schema()`, and the service creates the schema from the same file when the `events` table is missing (Decision Target `eventbus.persistence-schema.bootstrap-ddl`). Table/column detail: [eventbus_06_persistence_schema_and_replay.md](../24_eventbus/eventbus_06_persistence_schema_and_replay.md).

## 7b. Timestamp Format Policy

SQLite DEFAULT timestamps use strftime('%Y-%m-%dT%H:%M:%SZ', 'now') (Z suffix). Event Bus Python-side timestamps use `now_iso()` in `scripts/eventbus/json_utils.py`, which also produces the Z suffix. Python-side timestamps for workflow tables without a DEFAULT use datetime.now(UTC).isoformat(), which produces a +00:00 suffix. Consumers comparing timestamps across these sources MUST NOT assume a single suffix form.
