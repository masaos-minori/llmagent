# MCP Server Catalog: git-mcp

## git-mcp (Port 8014)

**Purpose:** Local git repository operations with two-stage safety guards.
**Startup Mode:** persistent (HTTP)
**Configuration:** `config/git_mcp_server.toml`
**Authentication:** No GITHUB_TOKEN required; uses local git credentials

**Tools:**

All tools require configuration (`config_dependent: true`).

Git server's `enabled`/`disabled_reason` calculation: If `allowed_repo_paths` is empty, it is prioritized for disabling (reason `"allowed_repo_paths is empty"`). Otherwise, if `read_only=true`, only write tools are disabled (reason `"read_only=true"`). See [04_mcp_03_06_tool-runtime-availability-metadata.md](04_mcp_03_06_tool-runtime-availability-metadata.md) for details.

### Availability metadata

The git-mcp server provides availability metadata through `/v1/tools`:

- `enabled`: Indicates whether the tool is available for LLM use
- `disabled_reason`: Provides the reason when the tool is disabled

#### Precedence rules

When multiple conditions could disable the tool, the following precedence applies:

1. If `allowed_repo_paths` is empty → tool is disabled regardless of other settings
2. If `read_only=true` and the operation requires write access → tool is disabled

This means `allowed_repo_paths is empty` takes precedence over `read_only=true`.

#### Disabled call behavior

When a disabled tool is called via `/v1/call_tool`, the response includes the concrete reason:

```
Tool disabled: <reason>
```

This matches the documented contract — no deviation exists between the documentation and implementation.

| Tool | Tier | read_only Guard | dry_run | config_dependent |
|---|---|---|---|---|
| `git_status` | READ_ONLY | — | — | yes |
| `git_log` | READ_ONLY | — | — | yes |
| `git_diff` | READ_ONLY | — | — | yes |
| `git_branch` | READ_ONLY | — | — | yes |
| `git_show` | READ_ONLY | — | — | yes |
| `git_add` | WRITE_SAFE | Blocked if read_only=true | yes | yes |
| `git_commit` | WRITE_SAFE | Blocked | yes | yes |
| `git_checkout` | WRITE_DANGEROUS | Blocked | yes | yes |
| `git_pull` | WRITE_DANGEROUS | Blocked | yes | yes |
| `git_push` | WRITE_DANGEROUS | Blocked | yes | yes |

The "Tier" column does not exist within the `scripts/mcp_servers/git/` directory itself; its values originate from `[tool_safety_tiers]` in `config/agent.toml` (the agent layer's authorization policy settings). The git-mcp server implementation does not internally determine or maintain tiers. (Explicit in code)

**Health:** If git is found: `{"status":"ok","ready":true,"liveness":true,"restart_recommended":false,"operator_action_required":false,"dependencies":{},"details":{}}`; if not found: `{"status":"degraded","ready":false,"dependencies":{"git":"git not found in PATH"/"check failed"}}` — returns HTTP 200 when ready, and 503 when degraded.
**Configuration:**

| Key | Default | Notes |
|---|---|---|
| `allowed_repo_paths` | `[]` | fail-closed; empty = reject all; paths are resolved via `Path.resolve()` |
| `read_only` | `true` | Unless explicitly set to false, all write tools return `[DENIED]` |
| `max_log_entries` | `50` | Limit on `git_log` entries |
| `auth_token` | `""` | Bearer token for MCP server call authentication |

**Note (2026-07-13):** `audit_log_path` was removed from `config/git_mcp_server.toml`. It was an unused key that caused no effect, but leaving it could lead to incorrect expectations that "git operations are logged to this path". While the `GitConfig.audit_log_path` field itself (default "") remains in `git_models.py`, the key being absent from config works normally.

**Note:** `git_show` is truncated at 8000 characters. The `inputSchema` for `git_log` defaults to `max_entries=20`; the default for the config's `max_log_entries` is `50`.

### Implementation Notes

- The `GitConfig.audit_log_path` field (removed from config above) is not referenced or written to anywhere in `GitService`/`server.py`. Actual call logs are output as JSON lines by `server.py::call_tool` via `mcp_servers.audit._audit_log` using the standard `logging.getLogger(__name__)` (module logger); there is no implementation for writing directly to a specified path. Unlike `github-mcp` (`service_security.py`), `shell-mcp` (`service.py`), or `file-delete-mcp` (`delete_service.py`), which have dedicated logic to open and append to `audit_log_path`, `git-mcp` lacks equivalent implementation. (Explicit in code)
- All five write tools (`git_add`/`git_commit`/`git_checkout`/`git_pull`/`git_push`) use a common path through `GitService`'s repository validation, checking `allowed_repo_paths` before passing through the write guard determined by the `_WRITE_TOOLS` frozenset (`service.py`). There are no additional guards distinguishing `git_checkout`/`git_pull`/`git_push` from other write tools (e.g., protected branch or force push restrictions). (Explicit in code) [Needs Confirmation: It is unclear whether this asymmetry is an intentional design decision (e.g., assuming local git operations are the user's responsibility) or a missing security feature compared to GitHub MCP; this requires a decision from the owner.]
- `git_commit` throws `GitServiceError("nothing staged to commit")` if `dry_run=false` and there are no staged changes. Other write tools do not have this type of "pre-execution condition check." (Explicit in code)
- Since repositories are opened with `search_parent_directories=False` using `git.Repo`, `repo_path` must point to the repository root (the directory containing `.git`); providing a subdirectory results in a `GitServiceError` wrapping a `git.InvalidGitRepositoryError`. (Explicit in code)

## Write protection policy

See also: `00_security_02_high-risk-tool-common-policy.md` Layered protection model for the general framework this section instantiates.

### Purpose

Agent-side approval confirms user intent; it does not verify that a `git_checkout`/`git_pull`/`git_push` call is technically safe. Git MCP MUST enforce its own technical constraints independently of Agent-side approval. Today it only partially does so — this section states current behavior plainly and separates it from target policy.

### Common guard (implemented)

`GitSecurityGuards` (mixin on `GitService`) enforces, for every write tool: repository-path authorization against `allowed_repo_paths` (resolved via `Path.resolve()` before comparison, so symlink- and traversal-based escapes are rejected) and `read_only` rejection. Both checks run before dispatch to the tool handler, for all five write tools uniformly (Explicit in code).

### Command-specific guard status: not implemented

No guard distinguishes `git_checkout`/`git_pull`/`git_push` from the other write tools or from each other. Concretely, none of the following exist: Dirty-Worktree rejection, Detached-HEAD control, Forced-Checkout rejection, protected-branch enforcement, Force-Push blocking, pull-strategy enforcement, or remote/ref value validation. `branch` and `remote` are passed through to GitPython as unvalidated strings.

**Confirmed exploitable consequence:** because `branch`/`remote` are unvalidated, passing a value such as `"--force"` in the `branch` field is interpreted by the underlying `git` CLI as an option rather than a ref name. This was reproduced in a sandboxed two-clone test environment: `git_checkout` with `branch="--force"` discards uncommitted worktree changes without warning, and `git_push` with `branch="--force"` performs a forced update that overwrites a diverged remote branch. The absence of a `force` parameter in the tool's input schema is not an effective mitigation — the same effect is reachable through the existing `branch`/`remote` fields. This is tracked as an open Known Issue (see `04_mcp_90_inconsistencies_and_known_issues.md`), not a designed exception.

### `git_checkout` policy

- **Current:** no Dirty-Worktree check (git's own failure, if any, is the only guard); no Detached-HEAD control; no distinction between branch checkout and path checkout; no Forced-Checkout rejection (see exploitable consequence above); no submodule-side-effect handling.
- **Target:** Dirty Worktree SHOULD be rejected unless a documented safe exception applies; Forced Checkout MUST be rejected; Detached HEAD SHOULD be rejected unless explicitly permitted; the approval preview SHOULD identify the current branch, target ref, and affected worktree state.

### `git_pull` policy

- **Current:** remote and branch are forwarded to `repo.git.pull()` with no allowlist beyond "non-empty" (branch is not even checked for non-empty); pull strategy (fast-forward-only vs. merge vs. rebase) is not set by Git MCP and is entirely determined by the ambient `git` configuration of the repository/environment; no Dirty-Worktree pre-check; conflict handling is whatever `git`'s own failure produces, wrapped into `GitServiceError`.
- **Target:** pull SHOULD use an explicit, fast-forward-only strategy for unattended execution; merge/rebase MUST require separately documented policy; Dirty Worktree MUST cause rejection; conflicts MUST NOT be reported as success.

### `git_push` policy

- **Current:** no protected-branch check (Git MCP has no `protected_branches` concept — that setting exists only in GitHub MCP's `GitHubConfig`, not in `GitConfig`); no technical Force-Push block (see exploitable consequence above); no ref-deletion, mirror-push, or multiple-ref distinctions (the schema does not expose them, but nothing rejects a `remote`/`branch` value crafted to request them via option injection); upstream/remote is not validated against an allowlist beyond non-empty.
- **Target:** Force Push MUST be blocked by the normal `git_push` operation; protected branches MUST reject direct push unless a separately approved policy allows it; remote and destination ref MUST be resolved and validated explicitly; a push rejected by the remote MUST NOT be reported as success. If Force Push is ever required operationally, it MUST be a separate, more strongly authorized administrative capability — not an option of the normal `git_push` tool.

### Protected branch authority

Git MCP has no protected-branch policy source today. GitHub MCP's `protected_branches` is a distinct, unrelated setting and MUST NOT be assumed to apply to local Git MCP operations. Until a Git MCP protected-branch policy is designed, production use SHOULD treat any branch as pushable/checkout-able by any caller with repository-path access, which is the current fail-open reality for this specific control.

### Approval level (current gap)

`git_checkout`/`git_pull`/`git_push` are tiered `WRITE_DANGEROUS`, which the risk-tier table describes as requiring full-word `yes` confirmation. In the current `agent.toml::approval_risk_rules`, only tools with an explicit `"high"` override actually get that prompt; `git_checkout`/`git_pull`/`git_push` have no such override and fall back to `RiskLevel.MEDIUM` (`y/N` single-character approval) — see `04_mcp_05_03_fail-open-fail-closed-and-risk-tiers.md`. This is a documentation/behavior mismatch in the approval layer, separate from the MCP-side guard gaps above.

### Structured rejection codes (current)

Git MCP returns free-form strings, not stable codes: `[DENIED] git-mcp is configured with read_only=true` (read-only) and repository-path rejection via `GitServiceError`. There is no rejection category for protected-branch, force-push, dirty-worktree, or detached-HEAD, because none of those checks exist yet to reject anything.

### Postcondition verification: not implemented

None of `format_checkout()`/`format_pull()`/`format_push()` re-check the resulting branch/HEAD, detect unresolved merge conflicts, or re-fetch remote state after a push. Success is inferred solely from the absence of a `GitCommandError`.

### Audit

Every `/v1/call_tool` invocation is recorded via the shared `_audit_log()` helper (tool name, outcome, timestamp, session/request id). **Needs confirmation:** the call site passes `req.args.get("repo", "")` as the audit `target`, but Git MCP's own input schema uses the key `repo_path`, not `repo` — read from code, this looks like the audit `target` field is always empty for git-mcp calls; this has not been confirmed by capturing a live log line. Pre-operation and post-operation git state (branch, HEAD, conflict status) are not part of the audit record regardless. `audit_log_path` in `GitConfig` is present but unused — no code path writes to it (see the 2026-07-13 note above, which remains accurate).
