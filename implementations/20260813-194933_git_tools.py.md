## Goal

Add the schema-2.0 per-tool metadata contract to all 10 tool entries in
`scripts/mcp_servers/git/git_tools.py`'s `TOOL_LIST`, marking the 5 read tools
(`git_status`, `git_log`, `git_diff`, `git_branch`, `git_show`) read-only and the 5
write tools (`git_add`, `git_commit`, `git_checkout`, `git_pull`, `git_push`)
state-changing, with every entry scoped `resource_scope_kind="git_repo"`,
`resource_scope_keys=["repo_path"]`.

## Scope

In scope: the 10 dict literals inside `TOOL_LIST` (lines 15-260+, confirmed entries:
`git_status` 17-31, `git_log` 33-57, `git_diff` 59-83, `git_branch` 85-99, `git_show`
101-120, `git_add` 122-146, `git_commit` 148-168, `git_checkout` 170-198, `git_pull`
200-229, `git_push` 231-260). Out of scope: the `McpTool`/`McpToolProperty`/
`McpInputSchema` type-alias definitions (lines 11-13) and any change to the actual git
subprocess invocation logic elsewhere in the git-mcp server.

## Assumptions

- None of the 10 entries currently declare any of the 4 new fields (confirmed:
  `rg "is_write|requires_serial|resource_scope"` on this file returns no hits) — fully
  missing on all 10.
- All 10 entries require `repo_path` in their `inputSchema["required"]` (confirmed by
  reading each entry: every one lists `"repo_path"` as the first/only-common required
  property), matching the plan's uniform `resource_scope_keys=["repo_path"]`.
- `requires_serial` is not specified per-tool by the plan's Affected-areas row for this
  file (only "reads read-only; writes state-changing; all scoped git_repo/repo_path"
  is stated); this document assumes `requires_serial=False` uniformly across all 10
  entries, since the plan's Design section relies on the new scope-overlap conflict
  graph (same `repo_path` scope string colliding) to serialize concurrent writes to the
  same repository, rather than a blanket global barrier per tool. `requires_serial=True`
  is reserved elsewhere in the plan (e.g. `shell_tools.py`, out of scope here) for
  tools needing a barrier regardless of scope.
- Read tools' descriptions ("Show the working tree status...", "Show commit
  history...", "Show diff...", "List all local branches...", "Show the content of a
  commit...") confirm no mutation; write tools' descriptions explicitly state
  "Requires read_only=false in config" for `git_add`/`git_commit`/`git_checkout`/
  `git_pull`/`git_push`, confirming they are the mutating half.

## Design decisions

- 5 read entries: `is_write=False`, `requires_serial=False`,
  `resource_scope_kind="git_repo"`, `resource_scope_keys=["repo_path"]`.
- 5 write entries: `is_write=True`, `requires_serial=False`,
  `resource_scope_kind="git_repo"`, `resource_scope_keys=["repo_path"]`.
- Every entry uses the exact same `resource_scope_keys=["repo_path"]` regardless of
  read/write status — the distinguishing factor between read and write tools is
  `is_write`, not the scope shape, since all 10 tools operate on exactly one repository
  path each (no dual-scope case like file `move_file` exists in this module).
- `dry_run`-capable write tools (`git_add`, `git_commit`, `git_checkout`, `git_pull`,
  `git_push` all support a `dry_run` boolean per their `inputSchema`) still get
  `is_write=True` unconditionally — `dry_run` is a runtime argument value, not a
  schema-level distinction; the schema declares the tool's *capability* to write, and
  per-call scope resolution (in `resource_scope.py`, out of scope here) is where
  argument-level nuance would be handled if ever needed, not in this static
  `TOOL_LIST`.

## Alternatives considered

Considered giving `dry_run=True`-supporting write tools a conditional/dynamic
`is_write` — rejected: `TOOL_LIST` entries are static schema declarations evaluated
once at import time, not per-call; the plan's contract is explicitly a static
per-tool-name declaration (`TOOL_LIST` entries), and per-call dry-run nuance is not
part of this plan's scope (confirmed: the plan's Out-of-Scope section limits this
work to declaring metadata, not call-level dry-run-aware overrides).

## Implementation

### Target file: `scripts/mcp_servers/git/git_tools.py`

### Procedure

1. For each of the 5 read entries (`git_status` 17-31, `git_log` 33-57, `git_diff`
   59-83, `git_branch` 85-99, `git_show` 101-120), add 4 keys after each entry's
   `"config_dependent": True,` line: `"is_write": False,`, `"requires_serial": False,`,
   `"resource_scope_kind": "git_repo",`, `"resource_scope_keys": ["repo_path"],`.
2. For each of the 5 write entries (`git_add` 122-146, `git_commit` 148-168,
   `git_checkout` 170-198, `git_pull` 200-229, `git_push` 231-260), add the same 4
   keys but with `"is_write": True,` instead of `False`.
3. Leave `inputSchema`, `status`, and `config_dependent` (all currently `True` for
   every entry in this module) unchanged.

### Method

Direct literal-dict edits, one insertion per entry (10 total), no new imports/helpers.

### Details

- Example — `git_status` (lines 17-31) currently ends:
  ```python
  "required": ["repo_path"],
      },
      "status": "production",
      "config_dependent": True,
  },
  ```
  becomes:
  ```python
  "required": ["repo_path"],
      },
      "status": "production",
      "config_dependent": True,
      "is_write": False,
      "requires_serial": False,
      "resource_scope_kind": "git_repo",
      "resource_scope_keys": ["repo_path"],
  },
  ```
- `git_log`, `git_diff`, `git_branch`, `git_show` each receive the identical
  read-only 4-key block (only `is_write=False` differs by category, not by tool).
- Example — `git_add` (lines 122-146) currently ends:
  ```python
  "required": ["repo_path", "paths"],
      },
      "status": "production",
      "config_dependent": True,
  },
  ```
  becomes:
  ```python
  "required": ["repo_path", "paths"],
      },
      "status": "production",
      "config_dependent": True,
      "is_write": True,
      "requires_serial": False,
      "resource_scope_kind": "git_repo",
      "resource_scope_keys": ["repo_path"],
  },
  ```
- `git_commit`, `git_checkout`, `git_pull`, `git_push` each receive the identical
  write 4-key block.

## Compatibility considerations

Additive-only; `tests/mcp_servers/test_tool_schema.py`'s `_SCHEM_MODULES` list already
includes `mcp_servers.git.git_tools` and its two parametrized tests only assert
presence/type of `name`/`description`/`inputSchema`/`status`/`config_dependent` and
absence of `requires_config` — unaffected by 4 new keys. No consumer of this module's
`McpTool` type alias is affected (it is a plain `dict[str, Any]` alias, unconstrained).

## Security considerations

Correctly distinguishing `is_write=True` for `git_add`/`git_commit`/`git_checkout`/
`git_pull`/`git_push` (all of which already gate on `read_only=false` in server
config per their own descriptions) from the 5 read-only tools is itself a security-
relevant clarification: it gives the future scheduler and discovery validator
accurate metadata to serialize concurrent writes to the same `repo_path` and to
reject any tool addition that omits this declaration (via
`test_tool_schema_contract.py`). This file makes no change to the existing
`read_only=false` config gate itself — that enforcement lives in the git-mcp server's
dispatch logic, not in `TOOL_LIST`.

## Rollback considerations
