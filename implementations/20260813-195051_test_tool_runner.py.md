## Design decisions

- **Delete `TestBuildToolMeta` outright, don't adapt it.** `_build_tool_meta()` is
  deleted from production code per the paired implementation doc; a test class for a
  deleted function has no target to test. Its individual test methods (asserting on
  `resource_scope`/`is_write`/`requires_serial` derivation for specific tool names like
  `trigger_workflow`, `rag_delete_document`, `index_paths`/`refresh_index`,
  `git_commit`) are not simply discarded, though — per the plan's Risk mitigation
  ("port every existing scenario... as regression fixtures"), each scenario's *intent*
  (e.g. "a known write tool without explicit metadata still gets `is_write=True`") is
  re-expressed as a test of `ctx.services_required.runtime_tools.tool_spec_for_call()`'s
  behavior for the same tool names, where that registry method's own test file
  (`tests/shared/test_runtime_tool_registry.py`, a different target file/agent) is the
  more natural home — this doc's `test_tool_runner.py` update instead focuses its
  ported coverage on `_execute_with_dag()`'s *use* of the per-call spec (i.e., that it
  correctly builds a call-id-keyed dict and passes it to `build_execution_groups()`),
  not on re-testing scope-resolution logic that now lives in a different module.
- **`TestExecuteWithDag` gets new fixtures, not a rewritten fixture-building style.** The
  existing class already mocks `ctx.services_required` extensively (implied by the file's
  heavy `unittest.mock` usage) — this doc's update adds a `runtime_tools` attribute to
  that existing mock context object with a `tool_spec_for_call` side effect/return value
  per test case, keeping the established mocking idiom in this file rather than
  introducing a new fixture style (e.g. a `pytest.fixture`-based approach) that would be
  inconsistent with the rest of the 1080-line file.
- **`TestExecuteStandardSerialization` tests both branches of the new fallback.** Per
  the Design/UNK-02 resolution in the plan, add (or update) at least two cases: (1) a
  registered tool with `is_write=True` in the mock registry triggers serial execution;
  (2) an unregistered tool name (mock registry's `.get()` raises `KeyError`) also
  triggers serial execution via the `True` fallback — this directly encodes the
  conservative-fallback behavior the plan's Design section specifies, and is the single
  most behaviorally significant new case in this file since it changes an actual runtime
  decision (not just an internal data shape).
- **Regression grep test lives as a plain `subprocess`/`Path.read_text()`-based
  assertion, not a `pytest` marker or lint-config change.** The plan's Implementation
  steps specify it literally: "expect no code change, only a regression test (`grep -n
  "_build_tool_meta" scripts/agent/tool_runner.py` returns nothing; `grep -n
  "SHELL_TOOLS" scripts/agent/tool_runner.py` returns nothing) added to
  `tests/agent/test_tool_runner.py`." Implement as a small test function reading the
  source file's text (via `pathlib.Path(...).read_text()`, resolved relative to the
  repo root the same way other tests in this repo resolve source paths, or via a simple
  substring check) and asserting the two strings are absent — no need for an actual
  `grep` subprocess call, which would be slower and add a shell dependency to the test.

## Alternatives considered

- Keeping `TestBuildToolMeta` but redirecting its calls to whatever replaces
  `_build_tool_meta()` line-for-line. Rejected: the plan calls for deleting
  `_build_tool_meta()` entirely with no direct replacement function of the same
  signature — the new flow is a call-id-keyed dict built inline in `_execute_with_dag()`,
  not a standalone importable helper with the same shape, so there is no drop-in target
  for these tests to redirect to.
- Testing the new `tool_spec_for_call()`-based flow only at the `_execute_with_dag()`
  integration level (skipping any unit-level assertion on the call-id-keyed dict shape
  itself). Rejected: per the plan's Risk mitigation emphasis on regression safety for
  this exact area, at least one test should assert the constructed `tool_meta` dict is
  keyed by `tc["id"]` (not tool name) and passed to `build_execution_groups()` in that
  shape, since this is the crux of the correctness change this plan introduces.
