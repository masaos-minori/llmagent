## Goal

Add a config/token-map preflight to `deploy/load_env.sh` that builds the EventBus token maps via the existing `auth._populate_token_maps()` and cross-checks them against `load_config()` before startup, so a broken config or an unbuildable token map aborts before the service starts, while keeping `require_env_vars` as the presence gate (`REQ-005`).

## Scope

- Modify `deploy/load_env.sh` only: add a new preflight function that loads config, populates token maps, and cross-checks them; wire its call into the sourcing consumer (`deploy/setup_services.sh`) before the EventBus launch.
- Do not modify `scripts/eventbus/auth.py`, `scripts/eventbus/config.py`, `scripts/eventbus/app.py`, or the `/health` contract here — the preflight reuses the already-correct `load_config()` and `_populate_token_maps()` (`REQ-005`, `REQ-002`).

## Assumptions

- `scripts/eventbus/auth.py::_populate_token_maps()` (line 97) builds `_TOKEN_PRINCIPAL_MAP` from a config object and raises `ValueError` when `consumer_token` is configured without `consumer_authorization`; it is called from `scripts/eventbus/app.py`'s lifespan (line 74) on every real startup.
- `scripts/eventbus/config.py::load_config()` is the authoritative config loader; the preflight reuses it unchanged.
- `deploy/load_env.sh::require_env_vars` (lines 69-106) checks variable presence only; it does not validate that the loaded config can build its token maps, which is the gap this preflight closes.

## Design decisions

- **A new shell function wraps a `uv run` python preflight.** The preflight runs one `python -c` under the same `uv run` harness used elsewhere in the deploy scripts: it calls `load_config()`, then `_populate_token_maps()`, then asserts the built `_TOKEN_PRINCIPAL_MAP` is consistent with `load_config()`. Any raised error (for example the `consumer_token`-without-`consumer_authorization` `ValueError`) or any map/config mismatch prints `[FATAL]` and exits 1.
- **Keep `require_env_vars` as the presence gate.** Presence of the environment variables is still enforced by `require_env_vars` (lines 69-106); the new preflight adds a second, deeper layer that validates the config actually resolves. The two gates are sequential, not replacing.
- **Cross-check by fingerprint, not by raw token.** The comparison reads the non-secret token fingerprints stored on each `Principal` rather than the raw token values, so the preflight never logs secrets while still proving every configured token produced exactly one principal.

## Alternatives considered

- **Call `_populate_token_maps()` from inside `require_env_vars`.** Rejected: `require_env_vars` is a generic presence gate parameterized by label and rerun command; folding a config-specific python call into it breaks its reuse and its shellcheck isolation.
- **Reproduce the token-map logic in bash.** Rejected: the map is a Python data structure owned by `auth.py`; re-deriving it in shell would drift from the runtime and defeat the purpose of reusing `_populate_token_maps()`.

Add a new `preflight_eventbus_tokens` (new) function after `require_env_vars` (after line 106) that runs a `uv run` python one-liner: call `load_config()`, then `_populate_token_maps()`, then compare the resulting `_TOKEN_PRINCIPAL_MAP` fingerprints against the configured tokens, aborting on any mismatch or raised error.
3. Call the new `preflight_eventbus_tokens` (new) function from `deploy/setup_services.sh` after `require_env_vars` and before the EventBus background launch, so a broken config aborts before the process starts.

### Method

- The new function takes no arguments; it resolves the config path from the same `${EVENTBUS_CONFIG}` variable the launch block uses and passes it to the python one-liner via an environment variable or argument.
- The python one-liner imports `load_config` from `eventbus.config` and `_populate_token_maps` from `eventbus.auth`, mirrors the lifespan ordering at `scripts/eventbus/app.py` line 74 (`load_config()` then `_populate_token_maps()`), and after population iterates the configured token fields to confirm each produced a principal whose fingerprint matches `_populate_token_maps()` output. A `ValueError` propagates and the shell wrapper turns a non-zero exit into a `[FATAL]` message.
- Keep `require_env_vars` (lines 69-106) exactly as-is; the preflight is additive and runs after it.

### Details

- The cross-check compares non-secret fingerprints (`Principal.token_fingerprint`), computed by `_populate_token_maps()` via SHA-256 prefix, so raw token values are never printed or compared in the clear.
- A duplicate token (two config fields sharing one value) yields a single principal with merged roles; the preflight treats a configured token absent from the map as a mismatch and aborts.
- `parse_env_file` (lines 15-54) and `collect_required_env_vars` (lines 57-65) are untouched; the preflight depends on their output being already exported into the environment.

## Compatibility considerations

- `load_env.sh` is a sourcing-only library; adding one function and one call site does not change the behavior of `parse_env_file` or `require_env_vars`.
- The preflight runs once per `setup_services.sh` invocation, before the EventBus launch, so it adds startup latency equal to a single `uv run` invocation.

## Security considerations

- Fail-closed: a broken config or unbuildable token map aborts before the service starts. The cross-check reads only non-secret fingerprints; raw token values are never logged.

## Rollback considerations

- Remove the new `preflight_eventbus_tokens` (new) function and its call site in `setup_services.sh` (or `git checkout` the parent commit); `parse_env_file`, `collect_required_env_vars`, and `require_env_vars` are unchanged.
