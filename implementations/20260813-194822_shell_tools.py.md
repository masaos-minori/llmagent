## Goal

Add the schema-2.0 tool-metadata contract to the single `shell_run` entry in
`scripts/mcp_servers/shell/shell_tools.py::TOOL_LIST`, marking it as a
write/serial/process-scoped tool so `McpToolDiscoveryService` can register it
under the new required-field contract.

  `TOOL_LIST` entry, `shell_run`, currently with only `name`, `description`,
  `inputSchema`, `status`, and `config_dependent` — no `is_write`,
  `requires_serial`, or `resource_scope*` fields exist today. This is a
  fresh add of all 4 fields, not a backfill.
- `implementations/done/20260718-090034_shell_tools.py.md` exists from a
  prior cycle dated 2026-07-18, predating this plan (2026-08-13). Confirmed
  by grep that `resource_scope_kind`/`resource_scope_keys` do not appear
  anywhere in `scripts/` or `tests/` today — that prior doc is unrelated to
  this plan's 4-field contract (most plausibly it added the
  `config_dependent` field or something equally unrelated). Coincidental
  filename match, not this plan's change.
- Per the plan's Affected-areas row for this file (verbatim):
  "`is_write=True`, `requires_serial=True`, `resource_scope_kind="process"`,
  `resource_scope_keys=[]`" — taken as the exact target values for this
  implementation, not re-derived independently.
- `shell_run` executes an arbitrary allowlisted shell command; its "resource"
  is the shared process/execution environment, not any single argument value
  (its arguments — `command`, `argv`, `cwd`, `env`, etc. — describe *how* to
  run the command, not a resource to scope conflicts against by value). This
  is why `resource_scope_keys=[]` (empty, fixed scope) rather than e.g.
  `resource_scope_keys=["cwd"]`.

## Design decisions

- `is_write=True`: a shell command is presumed to have side effects on the
  host (file writes, process spawning, network calls) — the same
  conservative posture the plan's Design section applies elsewhere ("favor
  conservative correctness").
- `requires_serial=True`: shell commands are serialized globally rather than
  scoped-and-parallelized, since two arbitrary shell invocations could
  contend for unpredictable shared resources (files, ports, subprocesses)
  that no static argument-derived scope could safely capture. This matches
  the plan's `resource_scope_kind="process"` choice — a single fixed kind
  covering "the process/OS environment" as one indivisible resource, rather
  than attempting per-command scoping.
- `resource_scope_keys=[]`: no argument is treated as a scope key; the scope
  is the fixed value the plan's Design section's scope-string catalogue
  implies (`"process:global"`), which `resolve_resource_scopes()` (a
  different file, not written here) will resolve to regardless of arguments.
- Field placement: appended after the existing `"config_dependent": True,`
  line, preserving all existing keys/order.

## Alternatives considered

- Scoping by `cwd` (`resource_scope_keys=["cwd"]`) to allow concurrent shell
  commands in different working directories: rejected — the plan's own
  Affected-areas row specifies `resource_scope_keys=[]` explicitly for this
  file, and `cwd` does not capture all of a shell command's side-effect
  surface (a command can affect resources outside its `cwd`, e.g. via
  absolute paths, network calls, or environment mutation), so per-`cwd`
  scoping would risk under-serializing genuinely conflicting commands.
- Treating `shell_run` as `requires_serial=False` with a broad
  `resource_scope_kind="process"`/`resource_scope_keys=[]` (letting the
  conflict-graph's write-vs-write edge do the serialization implicitly since
  every `shell_run` call would share the same fixed scope): considered
  equivalent in outcome to `requires_serial=True` for a single-tool server,
  but `requires_serial=True` is more explicit about the global-barrier intent
  the plan's Affected-areas row states verbatim, so it is used directly
  rather than relying on scope-collision to produce the same effect
  indirectly.

## Compatibility considerations

- Additive-only dict-literal change; no signature or import changes.
- `McpToolDiscoveryService`'s current optional-field type-check
  (`if field_name in entry`) already accepts this shape today; the change
  becomes load-bearing once the sibling doc for `mcp_tool_discovery.py` makes
  the 4 fields required — without this change, `shell_run` would then be
  excluded from the registry entirely, removing shell execution from the
  LLM-visible tool surface.

## Security considerations

- This is the single highest-risk tool in the entire schema-2.0 rollout
  (arbitrary sandboxed shell execution). Declaring `is_write=True`/
  `requires_serial=True` here ensures the scheduler never runs `shell_run`
  concurrently with itself or with other write-tagged calls once
  `tool_scheduler.py`'s conflict-graph rework (a different file, not written
  here) consumes this metadata — closing a gap where, before this change, an
  unregistered-metadata `shell_run` could have been silently defaulted to
  `is_write=False` by `build_runtime_tool()`'s current defaulting behavior.
- No change to the actual allowlist/sandbox enforcement (`argv[0]` allowlist,
  `cwd` restriction) — those remain the load-bearing security controls;
  this doc only adds scheduling metadata.

## Rollback considerations

- Revert is a pure removal of the 4 appended keys; no persisted state or
  data migration involved.
