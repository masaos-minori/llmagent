# Implementation procedure: scripts/agent/repl.py

## Goal

Bound `AgentREPL._close_resources()`'s blocking WAL-checkpoint sequence (PASSIVE
checkpoint -> TRUNCATE retries -> WAL file backup) with a timeout by running it off the
event loop via `loop.run_in_executor(None, ...)` + `asyncio.wait_for(..., timeout=...)`,
and fix the `PRAGMA database_list` column-index bug (`fetchone()[1]` -> `fetchone()[2]`)
so the WAL backup safety net copies the correct database file.

## Scope

    (`_WAL_CHECKPOINT_TIMEOUT_S: float = 30.0`, `_WAL_BACKUP_TIMEOUT_S: float = 10.0`).
  - Extract `_wal_checkpoint_sync()` from the current PASSIVE/TRUNCATE logic
    (`repl.py:251-293`), changing `await asyncio.sleep(2**attempt)` to

- Default values `_WAL_CHECKPOINT_TIMEOUT_S = 30.0`, `_WAL_BACKUP_TIMEOUT_S = 10.0`
  match the plan's stated rationale (roughly one `busy_timeout`'s worth of extra wait);
  not derived from measured production shutdown-latency data.
- Two independent `SQLiteHelper("session")` connections (one per stage) is safe — SQLite
  supports multiple independent connections to the same WAL-mode database file, and a
  `sqlite3.Connection` opened on one thread cannot safely be handed to another
  (`check_same_thread=True` default, confirmed via `scripts/db/helper.py`'s `_connect()`
  not overriding it), so each helper must open its own connection inside the function
  run by the executor, not share one opened on the event-loop thread.
- Confirmed against current source: `scripts/agent/repl.py:245-336` matches the plan's
  described shape exactly (try block at line 251, PASSIVE at 257, TRUNCATE retry loop
  at 266-293, backup block with the `[1]` bug at 297-299, `else` skip branch at
  315-316). `tests/test_repl.py:423-469` confirms `TestCloseResourcesWALCheckpoint`
  contains exactly the 3 named tests
  (`test_passive_checkpoint_called_first_when_wal_mode`,
  `test_truncate_checkpoint_falls_back_on_passive_failure`,
  `test_checkpoint_skipped_when_not_wal_mode`), each patching `agent.repl.SQLiteHelper`
  and asserting on `mock_db.checkpoint` call args.

## Design decisions

- Split the current single try/except block into two independently-executed,
  independently-timed-out synchronous helpers (`_wal_checkpoint_sync`,
  `_wal_backup_sync`) rather than wrapping the whole existing block in one
  `run_in_executor` + `wait_for` call — a single wrapped call would mean a
  checkpoint-side timeout abandons the not-yet-reached backup step too, defeating the
  requirement that the backup is "still attempted" on overall timeout.
- Use `except TimeoutError` (not `asyncio.TimeoutError`) to catch `asyncio.wait_for`'s
  timeout — on Python >= 3.11, `asyncio.TimeoutError` is an alias of the builtin, and
  this repo requires Python >= 3.13 (`pyproject.toml`); matches existing usage
  elsewhere in the file (`repl.py:365`).
- `not truncated_or_ok` (rather than a separate timeout flag) gates whether the backup
  stage runs: it stays `False` both when TRUNCATE genuinely exhausts its 3 retries and
  when the checkpoint stage times out before completing, so both cases correctly fall
  through to the backup attempt with no extra branching.
- Keep the `errors` list's existing tuple shape (`(name, "ExcType: message")`) for the
  two new failure modes (`wal_checkpoint_timeout`, `wal_backup_timeout`), consistent
  with existing entries like `wal_checkpoint_truncate`.

## Alternatives considered

- Wrapping the entire existing block (connection open -> checkpoint -> backup) in a
  single `run_in_executor` + `wait_for` call: rejected — a checkpoint-stage timeout
  would abandon the backup step, which the requirement explicitly disallows.
  Documented in the plan's Design section 2.
- Passing the timeout via `AgentREPL.__init__` as a constructor parameter or through
  `AgentConfig`/`agent.toml`: rejected for this change's size — `AgentREPL()` is
  constructed with zero arguments at its two call sites
  (`scripts/agent/__main__.py:14`, `scripts/agent/repl.py:632`), and plumbing a new
  config source through would be an out-of-scope, larger change; a class attribute is
  also required for `_make_bare_repl()`'s `__new__`-based test construction to work
  without touching `__init__` (see Assumptions).
- Fixing the `PRAGMA database_list` bug by replacing the whole query with
  `SQLiteHelper.DB_PATH` (an existing property exposing `self._db_path` directly,
  `helper.py:112-115`), avoiding the PRAGMA query and the column-index bug class
  entirely: not adopted — the requirement doc's Tests section expects verification via
  a mocked `PRAGMA database_list` result, so the literal index fix (`[1]` -> `[2]`) is
  used to stay faithful to the specified test surface. Noted as a lower-risk follow-up
  only, not part of this change.

### Method

- Synchronous-code extraction (two new private methods) plus an async-wrapper
  rewrite using `loop.run_in_executor(None, ...)` + `asyncio.wait_for(...)` — a
  standard sync/async boundary pattern already used elsewhere in this file
  (`repl.py:365`). No new dependencies; `asyncio`, `sqlite3`, `shutil`, `os`, `time`
  are already imported in `repl.py`.

### Details

`_close_resources()` shape after the change (illustrative, not final production code —
see the plan's Design section 2 in `plans/done/20260726-095135_plan.md` for the full
reference implementation):

```python
async def _close_resources(self) -> None:
    self._view.write_history()
    errors: list[tuple[str, str]] = []
    loop = asyncio.get_running_loop()

    truncated_or_ok = False
    try:
        truncated_or_ok, checkpoint_errors = await asyncio.wait_for(
            loop.run_in_executor(None, self._wal_checkpoint_sync),
            timeout=self._WAL_CHECKPOINT_TIMEOUT_S,
        )
        errors.extend(checkpoint_errors)
    except TimeoutError:
        errors.append(("wal_checkpoint_timeout", f"TimeoutError: exceeded {self._WAL_CHECKPOINT_TIMEOUT_S}s"))
    except sqlite3.Error as e:
        errors.append(("wal_checkpoint", f"{type(e).__name__}: {e}"))

    if not truncated_or_ok:
        try:
            _wal_backup_path, backup_errors = await asyncio.wait_for(
                loop.run_in_executor(None, self._wal_backup_sync),
                timeout=self._WAL_BACKUP_TIMEOUT_S,
            )
            errors.extend(backup_errors)
        except TimeoutError:
            errors.append(("wal_backup_timeout", f"TimeoutError: exceeded {self._WAL_BACKUP_TIMEOUT_S}s"))
    # ... unchanged tail: svc.lifecycle.shutdown_all(); svc.http.aclose(); errors summary log
```

`PRAGMA database_list` returns rows shaped `(seq, name, file)`; `.fetchone()[2]` is the
file-path column (`.fetchone()[1]` was the database-name column, e.g. `"main"`).

## Compatibility considerations

- `_close_resources()` is called from exactly two `finally` blocks in the same file
  (`repl.py:526`, `repl.py:615`), both as plain `await self._close_resources()`; no
  external caller exists elsewhere in the repo (`grep -rn "_close_resources"
  scripts/`). The method's external signature (`async def _close_resources(self) ->
  None`) is unchanged, so no caller-side update is needed.
- The `errors` list's existing entry shape (`(name, "ExcType: message")` tuples) is
  preserved; new entries (`wal_checkpoint_timeout`, `wal_backup_timeout`) are additive
  and consumed by the same unchanged final summary log.
- `scripts/db/helper.py` (`SQLiteHelper`) is unchanged; both stages continue to use its
  existing public `open(write_mode=True)` / `checkpoint(...)` / `execute(...)` contract.

## Security considerations

- N/A — no new external input, no secrets, no network exposure; the backup file path
  is derived from an existing, already-trusted local DB path (`self._db_path` via
  `PRAGMA database_list`), and the column-index fix only changes which existing,
  non-sensitive column is read.

## Rollback considerations

- Single self-contained change confined to one production file
  (`scripts/agent/repl.py`) and one test file (`tests/test_repl.py`); revert by
  reverting the commit. No schema, config, or data migration is involved — the two new
  class attributes and the two new private helper methods carry no persistent state, so
  rollback has no cleanup burden.
- If the timeout values (`30.0`s / `10.0`s) prove wrong in production, they are
  trivially tunable in place (class-attribute edit) without further design work or a
  rollback of the executor-wrapping structure itself.
