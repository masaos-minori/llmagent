## Goal

Promote `check_compat_shims.py --check-removed-names` from opt-in to default-on in the CI
backward-compatibility job (`.github/workflows/backward-compat-check.yml`) now that the corpus is
confirmed compliant, preserving its report-only-until-compliant guard (never hard-fail CI while
residual non-compliance may exist), and mark GV-017 `Existing`. The detector itself is read-only.

## Scope

- **In-Scope**:
  - Re-run `--check-removed-names` across the corpus to re-confirm zero reintroductions.
  - Wire `--check-removed-names` into the CI backward-compatibility job so it runs by default.
  - Preserve the report-only guard: keep the check `Warning`-level; do not make it a hard CI
    failure while residual non-compliance may exist.
  - Update the GV-017 matrix row to `Existing` and clear its Follow-up note.
- **Out-of-Scope**:
  - Changing the detection patterns (`_REMOVED_NAME_PATTERNS`, `_HISTORICAL_CONTEXT_MARKERS`).
  - Modifying other `check_compat_shims.py` options or its exit-code logic.
  - Adding the check to the pre-commit hook (pre-commit does not currently wire this tool; see
    UNK-02).

## Assumptions

- The corpus is already compliant (verified: `uv run python tools/check_compat_shims.py
  --check-removed-names` reports "All checks passed", zero findings) — so promoting does not trip
  the report-only guard.
- The natural promotion point is the CI backward-compatibility job
  (`backward-compat-check.yml`), which already runs the bare invocation and triggers on
  `docs/**/*.md`.
- The check is `Warning`-level and non-blocking, consistent with GV-017's existing gate.

## Design decisions

- Promotion is a CI-config change only; the detector stays read-only.
- Add `--check-removed-names` to the existing bare invocation so the removed-name check runs by
  default. The job's `paths:` triggers already cover `docs/**/*.md`, so reintroductions in docs are
  caught on the next PR.
- Do not modify the detector's exit logic; the report-only guard's purpose (avoid failing CI during
  the non-compliant transition) is satisfied because the corpus is compliant.

## Alternatives considered

- Modifying the detector to distinguish severity in its exit code — rejected: REQ-004 forbids
  changing the detector; the guard is preserved by keeping the corpus compliant and reverting the
  promotion if residual non-compliance is later found.

## Implementation

`.github/workflows/backward-compat-check.yml`

### Procedure

1. Read the existing backward-compatibility job to locate the bare invocation
   (`python tools/check_compat_shims.py`, currently without any flag).
2. Confirm the job's `paths:` triggers cover `docs/**/*.md` (they do).
3. Add `--check-removed-names` to the bare invocation:
   `python tools/check_compat_shims.py --check-removed-names`.
4. Do not touch `check_compat_shims.py` (REQ-004).

### Method

- **Promote in place.** Edit the existing invocation line to append `--check-removed-names`; do not
  add a new step or a new job. The job's `paths:` triggers already cover `docs/**/*.md`.
- **Preserve the guard (UNK-01, REQ-003).** Leave the detector's exit logic unchanged. Because the
  corpus is compliant (zero findings), there is no residual non-compliance to trip the gate;
  promoting is safe. If residual non-compliance is later discovered, revert the promotion (restore
  the opt-in default) rather than modifying the detector. Document this in-code/PR.
- **Detection basis (UNK-03).** Use `_REMOVED_NAME_PATTERNS` / `_HISTORICAL_CONTEXT_MARKERS` as-is
  (read-only); the promotion covers all registered patterns, not just the four slash-commands.
