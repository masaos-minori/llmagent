## Design decisions

- **Heading level and nesting position**: `##### Deletion-First Evaluation` and
  `##### ADR Requirement` are both `#####`-level subsections, siblings of the other
  existing `#####` subsections under their parent `####` Step (Step 6 and Step 10
  respectively) — matching the precedent set by all four sibling documents' identical
  treatment of their own inserted subsections.
- **`##### ADR Requirement` placement inside Step 10**: the Plan's Implementation
  intent says "before the existing per-file report bullet list." Step 10's current body
  opens with the sentence "Keep diffs minimal. For each file, report:" immediately
  followed by the bullet list. This document places `##### ADR Requirement`
  immediately after the `#### Step 10: Report results` heading and before that lead
  sentence, rather than between the lead sentence and the bullet list — this keeps the
  lead sentence attached to the list it introduces, while still satisfying "before the
  existing per-file report bullet list" (the subsection precedes both the sentence and
  the list it governs).
- **Path C completion sub-list placement inside the Completion gate paragraph**: the
  Plan's Implementation intent says "append ... to the existing `**Completion gate.**`
  paragraph." The existing paragraph's structure is: opening sentence -> ten bullets ->
  closing sentence ("If any item is not satisfied, do not report the task as
  complete."). This document appends the new `**Path C completion requirements**`
  sub-list after the ten existing bullets and before that closing sentence, so the
  closing sentence's "any item" continues to cover both the original ten and the new
  items collectively, rather than only the original ten.
- **Reporting items cross-reference in-file subsection headings, not sibling Plan
  paths**: consistent with the design choice already established by
  `implementations/20260826-160025_01_prompts_04_refactor.md.md` (citing the in-file
  `##### Discovery Vocabulary` subsection rather than `plans/20260826-151739_plan.md`),
  this document's seven new Step 10 items and the Path C completion sub-list cite the
  four sibling documents' actual inserted subsection headings (`##### Technical Debt
  Discovery`, `##### Responsibility Analysis`, `##### Documentation Drift Detection`,
  `##### Architecture Baseline (Path C)`, `##### Path C: Architecture Comparison
  Validation`, `##### Path C: Architectural Refactoring`, `##### Discovery
  Vocabulary`) rather than the plan file paths the Plan's own Requirements cite — an AI
  executing `prompts/04_refactor.md` at refactor time needs a durable, in-file anchor,
  not a reference to a Plan that will be archived to `plans/done/`.
- **ADR reconciliation reuses the governance document's exact wording** (`REQ-006`):
  the inserted `##### ADR Requirement` text quotes
  `docs/00_governance_01_documentation-policy.md`'s canonical header order verbatim
  (re-verified accurate, see Assumptions) rather than restating the Plan's own
  fourteen-field reconciliation table inline — the reconciliation table's role is to
  justify the Design decision here, not to be copied into the prompt file itself; the
  prompt file only needs the operative rule (`REQ-008`), not the full mapping.
- **Discrepancy handling follows `skills/DESIGN.md` "No implementation counts"**: both
  count discrepancies found during verification (Completion gate bullets, Path C
  completion items — see Assumptions) are resolved by naming items rather than
  asserting a count in the inserted text, so the inserted prompt content stays correct
  regardless of which count is "right."

## Alternatives considered

- Making either new subsection a new, separately numbered Step (e.g. "Step 6.5" or
  "Step 10.5") was rejected: it would violate `REQ-019`'s "no renumbering of existing
  Steps," and the Plan's Design section confirms no step renumbering is needed.
- Restating the Plan's full fourteen-field ADR reconciliation table inside
  `prompts/04_refactor.md` was considered, to make the mapping self-contained in the
  prompt file; rejected per `REQ-008` ("does not invent a new storage convention") and
  `skills/DESIGN.md` "Avoid implementation-reference duplication" — the operative rule
  (use the existing convention, do not invent a new one) is what the AI executing the
  workflow needs; the field-by-field justification belongs in the Plan/Design record,
  not in the reusable prompt text.
- Citing the four sibling Plans' file paths (as the Plan's own Requirements literally
  do) instead of the four sibling documents' actual inserted heading names was
  considered, for fidelity to the Plan's exact wording; rejected in favor of the
  in-file-anchor design already established by issue 02's document (see Design
  decisions) — plan files are archived to `plans/done/` after implementation, so citing
  them from inside a durable prompt file would go stale.
- Picking one of the two conflicting counts (nine vs. ten Completion gate bullets;
  twelve vs. thirteen Path C completion items) as "the correct one" and asserting it in
  the inserted text was considered; rejected in favor of naming the items instead,
  per `skills/DESIGN.md` "No implementation counts" — this avoids introducing a new,
  possibly also-wrong count into the prompt file.

### Details

Insert exactly this text at insertion point 1 (start of Step 6's body, before the
`libcst` bullet list):

```markdown
##### Deletion-First Evaluation

Applies only when the planned transformation would introduce a new class, protocol,
adapter, facade, manager, service, or registry — not for every Step 6 transformation. A
pure rename, an extraction into an existing module, or a type-annotation change does not
require this evaluation. This evaluation and its justification requirement apply
identically to Path A, Path B, and Path C — unlike Step 3/4's existing Path-gated
tooling-depth clauses, this is not Path-gated, because the underlying design question
(does this change need a new abstraction) is independent of blast radius.

Before introducing a new class, protocol, adapter, facade, manager, service, or
registry, evaluate the following seven steps in order and stop at the first step that
resolves the change — the first step that applies settles the question; do not
separately justify skipping the later steps once an earlier one applies:

1. Can the responsibility be removed?
2. Can the state or side effect be removed?
3. Can duplicate paths be consolidated?
4. Can the code be simplified?
5. Can responsibility move to an existing boundary?
6. Can logic be extracted?
7. Is a new abstraction required?

If step 7 is reached, the new abstraction requires a justification with exactly these
seven fields, recorded in the Step 10 report (see `##### ADR Requirement` for when the
new abstraction also requires an ADR):
- The problem being solved
- Why removal or simplification is insufficient
- Ownership
- Lifecycle
- Dependency direction
- Callers
- Test boundary

A new abstraction with an incomplete justification must not be transformed in this
Step — record it as a Proposal (`##### Discovery Vocabulary`) instead, consistent with
Step 2's existing "if behavior change is anything other than none, stop, record as
proposal" pattern.
```

Insert exactly this text at insertion point 2 (start of Step 10's body, before "Keep
diffs minimal. For each file, report:"):

```markdown
##### ADR Requirement

An ADR is mandatory when the change is classified Path C (see `##### Path C:
Architectural Refactoring`). An ADR is optional, but permitted, for Path B when the
change records an important trade-off — a judgment call made by the AI executing this
workflow when choosing to write one; no further gating criteria are defined here.

ADR content produced by this Requirement follows the repository's existing convention —
`adr-template.md`'s section structure, standardized by
`docs/00_governance_01_documentation-policy.md` "ADR Section Header Standardization"
(canonical header order: Context [Problem, Constraints], Assumptions, Decision,
Rationale, Alternatives Considered, Consequences [Positive/Negative], Invariants,
Verification, Migration, Implementation Notes, Known Deviations, Review Triggers,
Approval, Related Documents, Change History, Completion Checklist), plus the `Status`
field governed by that same document's "ADR Status Definitions"
(`Proposed`/`Accepted`/`Rejected`/`Deprecated`/`Superseded`) — not a separate,
purpose-built field list. This never invents a new storage convention, location, or
template; any suggested field with no direct equivalent in the existing convention is
folded into its nearest existing section rather than added as a new top-level header.

`prompts/04_refactor.md`'s existing Core Rule ("Do not edit documentation unless
explicitly instructed") governs where this ADR content is written: Step 10 always
produces the ADR content, in the reconciled shape above, inline in the report as a
draft. Creating the file under `docs/adr/ADR-{next-number}-{slug}.md` and registering it
in `docs/adr-index.md`'s existing "ADR List" table and dependency graph happens only
when the user explicitly instructs a documentation update — this Requirement does not
relax or reinterpret the existing Core Rule, it states how the new ADR obligation
operates within it.
```
