## Design decisions
- **A new, separate step** (`Run Front Matter schema compliance check
  (report-only)`), added after the existing `Run dependency graph cycle check`
  step — matches this workflow's own established one-step-per-tool convention
  (two existing steps, one per tool), and gives an independently-visible
  pass/fail-or-report signal in the GitHub Actions UI distinct from the other
  two checks.
- **`continue-on-error: true`** on the new step (not on the whole job) — this
  is the standard GitHub Actions mechanism for a report-only step: the step
  still runs and its output is visible, but a non-zero exit does not fail the
  job or block merge, exactly matching REQ-003's "marked non-blocking" language
  and this Plan's own Implementation intent.
- **`tools/check_docs_structure.py` and `schemas/doc_front_matter.json` are
  added to both `push.paths` and `pull_request.paths`**, mirroring this
  workflow's own existing convention (`tools/check_needs_confirmation_inventory.py`
  and `tools/check_dependency_graph_cycles.py` are both already listed
  alongside `docs/**/*.md`) — without this, a change to the tool's schema
  logic or to the schema file itself would not trigger this workflow, since
  neither path matches the existing `docs/**/*.md` glob. This is not
  explicitly required by REQ-003's own wording, but is a direct, minimal
  application of a pattern already established twice in the same file by
  earlier, already-implemented Plans.
- **The step's `run:` command matches the Plan's own Implementation intent
  exactly**: `python tools/check_docs_structure.py docs/*.md docs/adr/*.md
  --schema schemas/doc_front_matter.json` — no `set -euo pipefail`-driven
  early exit is needed beyond what the existing two steps already establish as
  this file's convention, which this step also follows for consistency (a
  report-only step still benefits from `set -e` failing fast within the step
  itself on a genuine tool crash, distinct from `continue-on-error`'s job-level
  effect on a non-zero *exit code* specifically).

## Alternatives considered
- **Combine this step into the existing "Run Needs Confirmation inventory
  checks" or "Run dependency graph cycle check" step's `run:` block** —
  rejected: those steps are both currently Blocking (no `continue-on-error`);
  combining a report-only check into a blocking step's script would either
  make the whole step non-blocking (silently weakening the other two checks)
  or require awkward in-script exit-code suppression that `continue-on-error`
  already handles cleanly at the step level.
- **Omit the `paths:` trigger additions, relying only on `docs/**/*.md`** —
  considered, rejected (see Design decisions): this would leave a fix to the
  schema-validation logic itself, or a change to the schema file, silently
  untested by this workflow — the same reasoning already applied twice before
  in this exact file for the two existing tool-specific `paths:` entries.
