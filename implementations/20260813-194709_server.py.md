## Goal

Define, on the shared MCP server base module `scripts/mcp_servers/server.py`, an
explicit, named schema-2.0 per-tool metadata contract (`is_write: bool`,
`requires_serial: bool`, `resource_scope_kind: str`, `resource_scope_keys: list[str]`)
that is clearly distinguished from the existing envelope-level
`MCP_TOOL_SCHEMA_VERSION` constant, so that every one of the 10 MCP servers built on
this base class has one documented, canonical place describing what the 4 new fields
mean and how they relate to the envelope schema version already advertised at
`/v1/tools`.

## Scope

In scope: `scripts/mcp_servers/server.py` only — adding a module-level constant
naming/enumerating the schema-2.0 field set (for later import by the shared contract
validator described in `scripts/shared/resource_scope.py`, owned by a different
implementation procedure) and a clarifying docstring passage next to
`MCP_TOOL_SCHEMA_VERSION` (line 35) and inside `build_tools_response()`'s docstring
(lines 194-199). Out of scope: any change to the 10 individual `TOOL_LIST` modules
(covered by their own docs in this batch), any change to `MCPServer.list_tools()`,
`list_tools_with_server_key()`, or `health()`, and any change to
`scripts/shared/resource_scope.py`/`mcp_tool_contract.py` itself (owned elsewhere per
the plan).

## Assumptions

- The plan's Affected-areas row for this file describes the change as "Define/clarify
  a per-tool schema-2.0 contract distinct from the envelope-level
  `MCP_TOOL_SCHEMA_VERSION`" — read literally, this is a documentation/constant-naming
  change to this file, not a runtime-validation change (validation logic lives in the
  new `scripts/shared/resource_scope.py` module per the plan's Phase 1).
- `scripts/shared/resource_scope.py` does not exist yet in this repo (confirmed:
  `ls scripts/shared/resource_scope.py` → not found) and is a different agent's
  assigned file; this document only prepares `server.py` to be a stable import target
  for that module's validator function name list, without creating a circular or
  premature dependency.

## Design decisions

- Add a single frozen constant, e.g. `TOOL_SCHEMA_V2_FIELDS: tuple[str, ...] = ("is_write", "requires_serial", "resource_scope_kind", "resource_scope_keys")`, directly below `MCP_TOOL_SCHEMA_VERSION` (after line 35), so both schema concepts live next to each other with one glance distinguishing "envelope schema version" from "per-tool metadata field names."
- Do not rename or bump `MCP_TOOL_SCHEMA_VERSION` itself — the plan's Out-of-Scope section does not list an envelope version bump, and no consumer of `/v1/tools` is changing its expectations of the envelope shape in this plan.
- Keep `MCPServer` (the class, lines 104-191) untouched — it has no per-tool field today and the plan does not ask this base class to validate anything at runtime; validation is the new `resource_scope.py` module's job.

## Alternatives considered

- Adding a `validate_schema_v2(tool: dict) -> list[str]` function directly in
  `server.py` was considered, but rejected: the plan explicitly places the shared
  contract validator in `scripts/shared/resource_scope.py` (leaf-layer, no
  `mcp_servers` import), and `scripts/shared/` cannot import from `mcp_servers/` nor
  vice-versa without violating the `shared-is-leaf` `.importlinter` contract noted in
  the plan's Design section — keeping the field-name constant in `server.py` (which
  `mcp_servers` code is allowed to define) and letting `resource_scope.py` define its
  own equivalent constant/validation independently avoids a layering violation.

## Implementation

### Target file: `scripts/mcp_servers/server.py`

### Procedure

1. Insert a new module-level constant `TOOL_SCHEMA_V2_FIELDS` immediately after the
   existing `MCP_TOOL_SCHEMA_VERSION: str = "1.0"` line (line 35), with a docstring
   comment explaining it lists the 4 required per-tool schema-2.0 fields distinct from
   the envelope version above it.
2. Expand the comment above `MCP_TOOL_SCHEMA_VERSION` (lines 33-34) to explicitly
   cross-reference the new constant, so a reader hitting either one is pointed at the
   other.
3. Expand `build_tools_response()`'s docstring (lines 194-199) with one sentence
   noting that `schema_version` in its returned dict describes the *envelope* shape
   only; per-tool `is_write`/`requires_serial`/`resource_scope_kind`/
   `resource_scope_keys` are a separate, per-entry contract validated by each server's
   own `TOOL_LIST` (not by `build_tools_response()` itself).
4. No changes to `MCPServer`, `_FastAPIApp`, `TruncationResult`, or
   `_truncate_with_meta()`.

### Method

Purely additive: one new constant plus two docstring/comment expansions. No existing
symbol is renamed, no existing behavior changes, no new import is added (the constant
is a plain `tuple[str, ...]` literal, no dependency on the not-yet-created
`resource_scope.py`).

### Details

- Current line 33-35 reads:
  ```
  # Schema version advertised in each server's /v1/tools response; bump when the
  # tool-schema shape changes in a way that matters to Agent-side discovery/validation.
  MCP_TOOL_SCHEMA_VERSION: str = "1.0"
  ```
  New content inserted directly below line 35:
  ```
  # Per-tool schema-2.0 metadata field names (distinct from the envelope version
  # above): every TOOL_LIST entry across all 10 MCP servers must declare these 4
  # fields. See scripts/shared/resource_scope.py for the validator that enforces this.
  TOOL_SCHEMA_V2_FIELDS: tuple[str, ...] = (
      "is_write",
      "requires_serial",
      "resource_scope_kind",
      "resource_scope_keys",
  )
  ```
- `build_tools_response()` (current lines 194-203) keeps its existing return shape
  (`{"schema_version": ..., "tools": [...]}`) unchanged — only its docstring gains the
  clarifying sentence described above; no field is added to the returned dict by this
  file, since the per-tool fields already ride inside each tool dict passed in via
  `tools`.

Trivial: revert the single hunk adding `TOOL_SCHEMA_V2_FIELDS` and the two docstring
edits. No other file depends on `TOOL_SCHEMA_V2_FIELDS` existing until the
`resource_scope.py` validator and the new `tests/mcp_servers/test_tool_schema_contract.py`
are implemented (both tracked as separate target files in the plan), so rollback of
this file alone cannot break anything else already merged from this same plan.
