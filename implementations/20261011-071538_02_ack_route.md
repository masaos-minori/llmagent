# Implementation Procedure: scripts/eventbus/ack_route.py

## Goal

Make NACK handling atomic by moving the -2 state determination into the same lock acquisition and transaction as the NACK increment. Also remove the stale `events.acked_at` 409 branch.

## Scope

- `scripts/eventbus/ack_route.py`: Modify `_nack_and_promote()` to return -2 state atomically; remove the `events.acked_at` 409 branch (lines 174-176).

## Assumptions

- The existing `_nack_and_promote()` function returns -2 when the event should be rejected (already ACKed).
- The separate `run_with_db_lock(_nack_and_promote)` call after the NACK increment is the root cause of the race condition.
- The `events.acked_at` column has been dropped from the `events` table via migration.

## Design decisions

- Merge the -2 state check into the same `run_with_db_lock` call as the NACK increment, so the state determination and the NACK are atomic.
- Remove the `events.acked_at` 409 branch since the column no longer exists in the `events` table.

## Alternatives considered

1. Keep separate lock acquisitions but add a retry mechanism — rejected because it adds complexity without solving the fundamental race condition.
2. Use a single lock for both operations — chosen approach, simpler and correct.

## Implementation

### Target file

`scripts/eventbus/ack_route.py`

### Procedure

1. Identify the separate `run_with_db_lock` calls in the NACK handler (around lines 174-198).
2. Merge the -2 state determination into the same `run_with_db_lock` call as the NACK increment.
3. Remove the `events.acked_at` 409 branch (lines 174-176).

### Method

Modify the NACK handler to perform both the NACK increment and the -2 state check under a single lock acquisition.

### Details

1. **Merge -2 state check into NACK lock (REQ-003)**:
   - Current code (line 192): `failure_count, promoted = await run_with_db_lock(_nack_and_promote)`
   - The -2 state check runs under a separate lock acquisition after `_nack_and_promote()` returns -2.
   - Change: Move the -2 state determination into the same `run_with_db_lock` call. The `_nack_and_promote` function should return the -2 state as part of its result, and the caller should check it immediately without a second lock acquisition.
   - Specifically, modify the NACK handler to:
     ```python
     # Before: separate lock acquisition for -2 check
     failure_count, promoted = await run_with_db_lock(_nack_and_promote)
     if failure_count == -2:
         # -2 state check under separate lock — race condition
         ...
     
     # After: single lock acquisition
     result = await run_with_db_lock(_nack_and_promote)
     if result.state == -2:
         # -2 state check under same lock — atomic
         ...
     ```

2. **Remove `events.acked_at` 409 branch (REQ-004)**:
   - Current code (lines 174-176): Reads `events.acked_at` to determine 409 response.
   - Since `events.acked_at` has been dropped from the `events` table, this branch is stale.
   - Remove the entire 409 branch that reads `events.acked_at`.

## Compatibility considerations

- The change modifies the NACK handler's control flow. Existing callers expect the same return values (failure_count, promoted).
- The removal of the `events.acked_at` 409 branch means that NACKs for already-ACKed events will no longer return 409 from this specific branch. The per-consumer ACK check (REQ-001/REQ-003) should still handle this case.

## Security considerations

- No security implications. The change affects internal state management only.

## Rollback considerations

- If the merge causes issues, revert to separate lock acquisitions.
- If the `events.acked_at` removal causes issues, restore the 409 branch temporarily until the migration is confirmed.
