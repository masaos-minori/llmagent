# Implementation: `cmd_workflow.py` — Warn on `pending_approval_task_id` Overwrite

## Goal

Prevent silent overwriting of `ctx.turn.pending_approval_task_id` by logging a warning
whenever `_cmd_approve()` (and, if applicable, `_cmd_reject()`) would replace an
already-set value with a new one.

## Scope

**In scope:**
- `scripts/agent/commands/cmd_workflow.py::_cmd_approve()` (assignment at line 126).
- `scripts/agent/commands/cmd_workflow.py::_cmd_reject()` — verify whether it needs the
  same guard (see Details: it currently does not assign `pending_approval_task_id` at all).

**Out of scope:**
- `orchestrator.py::_init_workflow_task()` halted-task validation (separate implementation doc).
- `startup.py` recovery-path overwrite protection (separate implementation doc).
- Queue-based multi-approval handling (deferred per plan).

## Assumptions

- `self._ctx.turn.pending_approval_task_id` is the single field used to hand off the task
  ID to `orchestrator.py::_handle_workflow_engine` (confirmed: `orchestrator.py:222`).
- Overwrite should only warn, not block — approving a new task while one is already
  pending is a symptom to surface, not a state the command should refuse to reach (per
  plan's Assumption 1: single field is sufficient for now).
- A module-level `logger = logging.getLogger(__name__)` (or equivalent) already exists in
  `cmd_workflow.py` for use by the new warning call — confirmed by existing `logging`
  usage pattern in `orchestrator.py`/`startup.py`; verify at edit time and import if absent.

## Design decisions

- Log at `warning` level (not error) — an overwrite is anomalous but not necessarily fatal,
  consistent with existing overwrite-adjacent warnings in `startup.py`/`orchestrator.py`.
- Keep the check inline in `_cmd_approve()` rather than extracting a helper — a single
  call site does not justify a new abstraction (YAGNI, per `skills/python-design/SKILL.md`).
- Warn using the old and new task IDs so an operator can correlate which approval got
  dropped.

## Alternatives considered

- **Raise instead of warn**: rejected — would block legitimate approval flows without a
  queue-based design to fall back on (queue is explicitly deferred, per plan Out-of-Scope).
- **Extract a shared `_set_pending_approval_task_id()` helper reused by `_cmd_approve`,
  `_cmd_reject`, and `startup.py`**: rejected for this doc — `_cmd_reject` does not
  currently set this field at all, and `startup.py` is a separate module/procedure; keeping
  each site's fix local avoids coupling unrelated implementation docs.

## Implementation

### Target file

`scripts/agent/commands/cmd_workflow.py`

### Procedure

1. In `_cmd_approve()`, immediately before the existing line
   `self._ctx.turn.pending_approval_task_id = task_id` (line 126), add a check:
   ```python
   if self._ctx.turn.pending_approval_task_id is not None:
       logger.warning(
           "Overwriting pending_approval_task_id %s with %s",
           self._ctx.turn.pending_approval_task_id,
           task_id,
       )
   self._ctx.turn.pending_approval_task_id = task_id
   ```
2. In `_cmd_reject()` (lines 131-177): confirm this function does not assign
   `pending_approval_task_id` anywhere (verified: it only clears `pending_approval_id` and
   `approval_pending`, and marks the task `"halted"` via `update_task_status` at line 167).
   No overwrite guard is applicable here since there is no assignment to guard. Document
   this as a no-op finding in the PR/commit description rather than adding a check that has
   no effect.
3. Add a module-level logger if `cmd_workflow.py` does not already import/define one; reuse
   the existing logger otherwise.

### Method

Direct in-place edit: one new `if` guard plus one `logger.warning` call at the single
assignment site in `_cmd_approve()`. No new function, parameter, or class.

### Details

- Confirmed by direct read (`scripts/agent/commands/cmd_workflow.py:83-177`): `_cmd_approve`
  sets `pending_approval_task_id = task_id` unconditionally at line 126; `_cmd_reject` never
  references `pending_approval_task_id`.
- Use `%s`-style lazy formatting for `logger.warning`, consistent with `orchestrator.py`.
- Keep the added block under 120 chars per line.
- No new imports beyond `logging` if not already present.

## Compatibility considerations

- Purely additive (a new warning log line); no change to return values, control flow, or
  the `pending_approval_task_id` value ultimately stored — existing callers unaffected.
- No public API/CLI surface change.

## Security considerations

- Warning message includes task IDs only (already-internal identifiers, not secrets); no
  new sensitive-data exposure in logs.

## Rollback considerations

- Single-file, single-guard change — revert by removing the `if` block; no data migration
  or state cleanup required since no persisted state is touched.
