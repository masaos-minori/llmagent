## Design decisions

- **Delete `_execute_standard()` outright rather than keep it as a fallback.** The plan's
  Goal explicitly names the two disagreeing engines (`_execute_standard()` gated by
  `is_side_effect()`/`SHELL_TOOLS`, `_execute_with_dag()` gated by
  `ToolSpec`/`build_execution_groups()`) as the problem to remove; `force_serial`
  (a planner *input*) replaces `serial_tool_calls`' role as a branch *selector*, so no
  second engine is needed to express "run everything serially."
- **`force_serial=ctx.cfg.tool.serial_tool_calls` passed straight through, no local
  branching in `tool_runner.py`.** Today's `if not ctx.cfg.tool.serial_tool_calls:
  ... else: ...` (lines 526-530) picks between two functions; the new code calls
  `_execute_with_dag(ctx, approved_calls, turn, force_serial=ctx.cfg.tool.serial_tool_calls)`
  unconditionally — the branch moves inside `build_execution_groups()`'s phase-building
  algorithm (paired `tool_scheduler.py` doc), where `force_serial=True` short-circuits to
  one sequential phase per call.
- **Build `call_specs` inline in `_execute_with_dag()`, not via a new helper.** Mirrors
  the sibling Issue-02 doc's decision for the same call site: the plan's Implementation
  steps describe this as a direct replacement of the `_build_tool_meta()` call with a
  per-call construction, sourced from `PreparedToolCall.spec` — no new named helper is
  introduced.
- **Keep `results.sort(key=lambda r: call_order.get(r[0], 0))` (current line 373)
  unchanged.** Per the plan's Design section: "this mechanism is correct and is
  retained unchanged; only the loop that produces `results` (over `ExecutionPlan.batches`
  instead of `metadata.concurrent_groups`) changes." `call_order` (current line 357,
  `{tc["id"]: i for i, tc in enumerate(approved_calls)}`) already keys by `call_id`, so
  it needs no change either.
- **Remove only the two named imports that become unused.** `from shared.tool_constants
  import SHELL_TOOLS` (line 25) is deleted entirely — nothing else in this file uses
  `SHELL_TOOLS` once `_execute_standard()` and `_build_tool_meta()` are gone (confirmed
  via `rg -n "SHELL_TOOLS" scripts/agent/tool_runner.py`: two hits today, both inside the
  two functions being deleted). `is_side_effect` is dropped from the
  `shared.tool_executor_helpers` import (line 26) while `tool_hash_key` stays (used
  elsewhere in the file for cache-key computation, unrelated to scheduling).

## Alternatives considered

- Keeping `_build_tool_meta()`/`_execute_standard()` as thin deprecated wrappers for
  backward compatibility. Rejected: the plan's Implementation steps explicitly say
  "delete `_execute_standard()`" and "delete `_build_tool_meta()` if Issue 02 has not
  already removed it" — no caller outside this module and its own test file uses either
  (confirmed via `rg -n "_build_tool_meta\|_execute_standard"` across `scripts/` and
  `tests/` during fact-gathering for this doc).
- Catching a missing-`call_id` error from `call_specs` construction and synthesizing a
  conservative default `ToolSpec` inside `_execute_with_dag()`. Rejected: this
  reproduces exactly the "unsafe silent default" the plan's Goal names as one of the
  eight defects to eliminate; the failure must propagate as a scheduling failure
  (surfacing from `build_execution_groups()`), not be swallowed at the call site.
