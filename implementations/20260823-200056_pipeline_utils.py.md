## Goal
In `scripts/rag/ingestion/pipeline_utils.py`: widen `ChunkJsonRaw.fetched_at` from
optional (`NotRequired[str | None]`) to a mandatory, non-null `str`, and change
`read_json_file()` to read `fetched_at` from the raw dict and pass it unchanged into
`ChunkDocument(...)`, raising `ChunkFormatError` when the key is missing, `None`, or an
empty string — no default/fallback value is ever substituted.

## Scope
- In scope: `scripts/rag/ingestion/pipeline_utils.py` only — the `ChunkJsonRaw` TypedDict
  definition and the `read_json_file()` function body.
- Out of scope: `scripts/rag/models_data.py`'s `ChunkDocument.fetched_at` field addition
  (own implementation document; this file's change depends on it existing first, since
  `ChunkDocument(...)` must accept a `fetched_at` keyword argument);
  `scripts/rag/ingestion/chunk_splitter.py` and `scripts/rag/ingestion/ingester.py`
  (own implementation documents; both import symbols from this file but their bodies are
  out of scope here); `crawler.py`'s generation logic.

## Assumptions
- `ChunkJsonRaw.fetched_at` is currently declared `NotRequired[str | None]` and is not
  read anywhere in `read_json_file()`'s body today — confirmed by reading the full file;
  `ChunkDocument(...)` is constructed there without a `fetched_at` argument, so this
  file's change is additive to the constructor call, not a rename.
- `scripts/rag/models_data.py`'s `ChunkDocument` gains a mandatory `fetched_at: str`
  field (positioned before the first field carrying a default, `code_blocks`) in its own,
  separate implementation step; this file's `read_json_file()` edit must land no earlier
  than that field exists, or the `ChunkDocument(...)` call will raise `TypeError` for an
  unexpected keyword argument on the old dataclass shape.
- No on-disk `rag-src/*.json` fixture needs to remain readable without a `fetched_at`
  key after this change (per the source plan's Assumptions: no legacy-data compatibility
  constraint is claimed).

## Design decisions
- Read `fetched_at` with direct-key access validated up front (`data.get("fetched_at")`
  then an explicit non-empty-`str` check), not via a new `_get_str_with_default()`-style
  helper — the existing `_get_str_with_default()` helper's entire purpose is to supply a
  default, which is precisely the behavior this field must not have.
- Raise `ChunkFormatError` for a missing, `None`, or empty-string `fetched_at`, matching
  the exception type `read_json_file()` already raises for a fully unreadable file — no
  new exception class is introduced for this field.
- Validate `fetched_at` inside `read_json_file()` itself (alongside the existing
  `url`/`content` presence checks that already live in `_read_chunk_json_raw()`), not by
  widening `_read_chunk_json_raw()`'s early-return contract — keeps the "which check
  raises vs. returns `None`" split exactly as it exists today for `url`/`content`.

## Alternatives considered
- Reusing `_get_str()` (returns `str | None`, no raising) and letting a `None` flow into
  `ChunkDocument(fetched_at=None)` — rejected: `ChunkDocument.fetched_at` becomes
  mandatory `str` with no default, so a `None` value would only be caught later by
  `mypy`/dataclass typing, not at the point of malformed input; raising immediately in
  `read_json_file()` gives a precise, attributable error at the source file boundary.
- Extending `_get_str_with_default()` with a "raise instead of default" flag — rejected
  as unnecessary indirection for a single one-off mandatory field; a direct explicit
  check reads clearer and avoids changing a shared helper's contract for every other
  caller of `_get_str_with_default()`.

## Implementation
### Target file
`scripts/rag/ingestion/pipeline_utils.py`

### Procedure
1. In `ChunkJsonRaw`, change the `fetched_at` field from `fetched_at:
   NotRequired[str | None]` to `fetched_at: str` (mandatory, no `NotRequired`, no `| None`).
2. In `read_json_file()`, after the existing `data is None` failure check and before
   constructing `ChunkDocument(...)`, read `fetched_at = data.get("fetched_at")` and
   validate it is a non-empty `str`; if not, raise `ChunkFormatError` with a message
   naming the file path and the reason (missing key vs. wrong type vs. empty string).
3. Pass `fetched_at=fetched_at` into the `ChunkDocument(...)` constructor call, alongside
   the existing `url`, `title`, `lang`, `content`, etc. keyword arguments.
4. Leave `_read_chunk_json_raw()`, `_get_str()`, `_get_list()`,
   `_get_str_with_default()`, `_get_int_with_default()` unchanged — none of them are the
   right shape for a raise-on-absence mandatory field, per Design decisions above.

### Method
- Straight-line addition to the existing `read_json_file()` function body; no new
  function, no new class, no control-flow restructuring beyond one new validation
  branch.

### Details
- Place the `fetched_at` validation immediately after the `data is None` check at the top
  of `read_json_file()`, before the `title = _get_str(...)` line, so the function fails
  fast on the most fundamental missing-input case first (consistent with how `url`/
  `content` are already validated first, inside `_read_chunk_json_raw()`).
- The `ChunkFormatError` message should distinguish "missing key" from "empty/whitespace
  string" from "wrong type" if practical (mirrors the level of detail already given by
  `_read_chunk_json_raw()`'s existing `logger.warning` messages for `url`/`content`), but
  a single combined message naming the field and path is acceptable if that distinction
  adds no debugging value in practice — implementer's judgment, not a design fork that
  changes calling code.
- Do not add a `_get_str_required()`-style new shared helper unless a second caller needs
  identical raise-on-absence semantics in this file; at present only `fetched_at` needs
  it, so an inline check keeps the diff minimal (YAGNI, matches this file's existing
  mix of small single-purpose helpers rather than one generalized helper).

## Compatibility considerations
- Breaking change by design: any on-disk `rag-src/*.json` (crawl) or
  `rag-src/chunk/*.json` (chunk) file lacking a `fetched_at` key, or carrying `null`/an
  empty string for it, will now raise `ChunkFormatError` from `read_json_file()` instead
  of silently producing a `ChunkDocument` with no `fetched_at` at all — matches the
  source plan's explicit "no legacy-data compatibility constraint" assumption.
- `chunk_splitter.py`'s `_read_source_data()` already catches `ChunkFormatError` around
  its call to `read_json_file()` and treats it as a per-file skip (logs and returns
  `None`), so a malformed/legacy source file causes that one file to be skipped, not a
  batch-wide crash — no new exception handling is required in that caller for this
  change to be safe.

## Security considerations
N/A: no new external input surface — `fetched_at` is read from the same locally-written,
already-trusted JSON file (`orjson.loads` on disk content) that `url`/`content` are
already read from; only the validation strictness changes, not the trust boundary.

## Rollback considerations
- Revert this file's `ChunkJsonRaw`/`read_json_file()` diff together with
  `scripts/rag/models_data.py`'s `ChunkDocument.fetched_at` field addition as one atomic
  unit — reverting only this file while `ChunkDocument.fetched_at` remains mandatory
  would make `ChunkDocument(...)` fail at call time for lack of the argument; reverting
  only `models_data.py` while this file still passes `fetched_at=...` would raise
  `TypeError: unexpected keyword argument`.
- No schema/data migration is involved in this file's own change, so rollback is a pure
  code revert with no cleanup step.
