# Implementation Procedure: docs/05_agent_08_*_configuration*.md

## Goal

Reduce `docs/05_agent_08_*_configuration*.md` documents to canonical sources for configuration ownership and reload boundaries by removing exhaustive field/default-value tables, while preserving operational judgments about configuration management.

## Scope

**In-Scope**:
- Restructure all 5 files in `docs/05_agent_08_*_configuration*.md` to preserve: which files own which settings, the Hot-reloadable / Restart-required / Startup-only judgment criteria, strict-mode settings required in production, the danger of an empty `allowed_tools` list, the operational meaning of `tool_safety_tiers`, the config-drift detection approach, what operators must do after a config change.
- Remove: full mechanical field lists per config, exhaustive default-value tables, dataclass-structure explanations, plain "this field is this type" statements.
- **CRITICAL**: Never drop operational judgment during trimming. After trimming, explicitly re-verify: all operational judgments (hot-reloadable vs restart-required vs startup-only classification, strict-mode requirements, empty `allowed_tools` danger, `tool_safety_tiers` meaning, config-drift detection, operator actions after config change) still state their reasoning and operational caveat.
- When in doubt about whether a detail is operational judgment, keep it and mark for human review rather than deleting.
- Replace exhaustive default-value tables with pointers to `config/agent.toml` / the relevant dataclass for exact values.
- Rephrase operational concepts as judgments (why), not just mechanical descriptions.
- Reformat using the template: Purpose / Design Intent / Responsibility Boundary / Key Constraints / Operational Notes / Known Limitations / Related Docs.
- Mark unrecoverable design rationales as `Needs Confirmation`.

**Out-of-Scope**:
- Modifying other documents in the `05_agent_*.md` set.
- Adding new content beyond what exists in the current documents.
- Changing the doc set directory structure.

## Assumptions

1. The `memo-doc-agent-review.md` referenced in acceptance criteria existed during the original review but may have been moved or deleted since then.
2. `tools/check_agent_docs_consistency.py` is available and functional for post-edit verification.
3. `config/agent.toml` exists and serves as the authoritative source for configuration values.
4. All 5 target files form a coherent logical unit (loading + LLM/RAG + tools/memory + MCP/approval/observability).

## Design decisions

- Configuration documentation should answer "what can I change" and "how does the system react," not "which dataclass field maps to which TOML key."
- Exhaustive field listings and default-value tables are visible in code and add no operational value.
- Canonical Source Rule applies: when a fact is mechanically derivable from code, point to the source rather than transcribing it.
- Unrecoverable design rationales must be explicitly marked `Needs Confirmation` rather than silently dropped.
- Operational judgment must never be silently dropped — when in doubt, keep and mark for human review.

## Alternatives considered

- Keep current format: violates the principle that mechanical inventories should not be maintained manually.
- Replace with auto-generated API reference: would reduce maintenance burden but loses human-curated narrative. Not pursued without explicit request.
