## Goal

Wire the new fail-closed preparation phase (`scripts/agent/tool_preparation.py`, see its
own doc) into `scripts/agent/tool_runner.py`'s execution pipeline: delete
`_validate_tool_args()` and `_build_tool_meta()` entirely, change
`execute_one_tool_call()` to accept an already-prepared call instead of parsing JSON and
validating itself, and change `execute_all_tool_calls()` to run preparation before
`_run_approval_gate()`, merging preparation failures back into the final ordered result
list alongside approval denials and execution results.

## Scope

In scope, all within `scripts/agent/tool_runner.py`:
- Delete `_validate_tool_args()` (current lines 128-173, including its `except KeyError:
  pass` fallthrough and the `ctx.cfg.tool.tool_definitions` gateway-fallback loop at
  lines 157-172).
- Delete `_build_tool_meta()` (current lines 60-79) and its now-unused imports
  (`from shared.tool_constants import SHELL_TOOLS`, and `is_side_effect` from `from
  shared.tool_executor_helpers import is_side_effect, tool_hash_key` — keep
  `tool_hash_key`, it is used elsewhere for cache-key computation).
- Change `execute_one_tool_call()` (current lines 176-231) to accept a `PreparedToolCall`
  instead of a raw `tc: dict`, dropping its own `orjson.loads()` (lines 194-199) and the
  `_validate_tool_args()` call (line 201).
- Change `execute_all_tool_calls()` (current lines 506-538) to call `prepare_tool_calls()`
  first, pass only prepared calls into `_run_approval_gate()`, and merge preparation
  failures back into original order alongside approval denials and execution results.

## Design decisions

- **Preparation runs once, at the very top of `execute_all_tool_calls()`, before the
  approval gate.** Today's flow is `_run_approval_gate()` →
  `_execute_with_dag()`/`_execute_standard()` → `_collect_tool_result_msgs()`. Inserting
  preparation as step 0 means `_run_approval_gate()` (and therefore
  `run_approval_checks()`) only ever sees calls that already parsed and validated
  cleanly — the plan's core "fail before approval" requirement.
- **`approved_calls` becomes `list[PreparedToolCall]` throughout, not `list[dict]`.**
  Every downstream function that today takes `approved_calls: list[dict]`
  (`_execute_with_dag`, `_execute_standard`, `execute_one_tool_call`) is updated in the
  same step to consume the new type — a partial migration (some functions still expecting
  raw dicts) would silently break at the call boundary rather than fail a type check, so
  all four are changed together.
- **`_execute_standard()`'s side-effect check is left on `is_side_effect()`/
  `SHELL_TOOLS`, only its iteration target changes.** The plan's Scope explicitly lists
  what to remove (`_validate_tool_args()`, `_build_tool_meta()`) and does not name
  `_execute_standard()`'s check as a removal target; changing its semantics here would be
  scope creep beyond this plan's acceptance criteria (that is the sibling plan's concern,
  tracked separately in `plans/done/20260813-183049_plan.md` and its own implementation
  docs — this doc does not assume that sibling work has landed, and grounds only against
  the current tree, where `is_side_effect`/`SHELL_TOOLS` are still present and used).
- **Preparation failures are merged back via the existing `call_order` pattern**, reusing
  `{tc["id"]: i for i, tc in enumerate(tool_calls)}` (already used at
  `tool_runner.py:357`/`373` inside `_execute_with_dag()`) at the
  `execute_all_tool_calls()` level so the final `tool_msgs` list preserves original batch
  order across prep-failures, denials, and successful executions.

## Alternatives considered

- Running preparation inside `_run_approval_gate()` itself rather than in
  `execute_all_tool_calls()`. Rejected: `_run_approval_gate()`'s docstring
  (`scripts/agent/tool_runner.py:541-552`) states it is "the sole per-tool-call approval
  gate for the batch" — folding preparation into it would blur that single
  responsibility and make preparation failures harder to distinguish from approval
  denials in the merge step. Keeping them as two distinct phases in
  `execute_all_tool_calls()` matches the plan's "preparation, then approval" ordering
  literally.
- Keeping `_validate_tool_args()` as a thin deprecated wrapper around
  `validate_tool_arguments()` for backward compatibility. Rejected: the plan's goal is
  explicitly to remove the `except KeyError: pass` fallthrough and the
  `tool_definitions` loop that make it unsafe; a wrapper that still exists but is unused
  by the production path would leave dead code and an easy-to-reintroduce fallback,
  contrary to the plan's Goal.

## Security considerations

- This is the change that closes the plan's named vulnerability: today, an unregistered
  tool name that happens to match a stale `ctx.cfg.tool.tool_definitions` entry is
  silently accepted by `_validate_tool_args()`'s fallback loop and proceeds all the way
  to `RepositoryGateway`/`ToolExecutor`. After this change, `_validate_tool_args()` no
  longer exists, and the equivalent registry-miss case is rejected in preparation before
  `_run_approval_gate()` is ever called — a call that fails preparation cannot reach
  approval, DAG planning, or execution under any code path in this file.
- Removing `_build_tool_meta()`'s reliance on `ctx.cfg.tool.tool_definitions` for DAG
  scheduling metadata means a call's `resource_scope`/`requires_serial`/`is_write` are
  now always derived from the live `RuntimeToolRegistry` (via `pc.spec`), not from a
  static config value that could drift from the actual registered tool's real
  capabilities.

## Rollback considerations

- This file's changes are interdependent with `tool_preparation.py` (new import) and
  `tool_approval.py` (signature change) — reverting requires reverting all three in the
  same commit/PR, or `execute_all_tool_calls()` will fail to import
  `PreparedToolCall`/`prepare_tool_calls`.
- No persisted state or schema change; rollback is a source-only `git revert` of the
  combined commit.
- If only this file's revert is needed while keeping `tool_preparation.py` present but
  unused, that is safe (an unused new module has no runtime effect), but the reverse
  (reverting `tool_preparation.py` while keeping this file's changes) is not — this file
  would fail to import.
