## Goal
Implement `tools/generate_workitem.py`'s three rendering modes (issue, plan,
implementation-procedure), each extracting the current fenced skeleton from its
template file and writing it with placeholder text preserved verbatim (REQ-001,
REQ-002, REQ-003, REQ-004).

## Scope
- In scope: CLI argument parsing (`--kind`, `--id`, `--title`, `--source-plan`,
  `--target-file-path`); fenced-skeleton extraction from `templates/issue.md` /
  `templates/plan.md` / `templates/implementation-procedure.md`; per-kind output
  filename computation; collision rejection against the target directory and its
  `done/` counterpart; `--source-plan` existence validation.
- Out of scope: generating substantive field content (Summary, Problem, Decision
  Details, Traceability values); modifying `templates/issue.md`, `templates/plan.md`,
  or `templates/implementation-procedure.md`.

## Assumptions
- Dev-only tooling, outside the production deploy scope (absent from
  `deploy/deploy.sh` and `rules/env.md`'s deployment description).
- "Placeholder text" means each template field's current instructional prose,
  reproduced verbatim — not an empty string.
- `--id`/`--title` (issue mode) and `--target-file-path` (implementation-procedure
  mode) are supplied by the invoking caller; the tool does not infer them from
  repository content.

## Design decisions
- Extract text strictly between the fenced ` ```markdown ... ``` ` block's opening
  and closing marker in each template file, and write it unchanged — never a
  hardcoded copy of field names — so the tool tracks whatever the templates
  currently define (confirmed: each template's skeleton lives inside exactly one
  such fenced block — `templates/issue.md` lines 10-69, `templates/plan.md` lines
  8-157, `templates/implementation-procedure.md` lines 19-77, verified against
  current file content).
- Filename computation is one function per kind, not one generic formatter — the
  three naming rules differ in structure (id+slug vs. none vs. seq+path-slug).
- Collision policy is a hard reject, not the zero-pad auto-increment
  `templates/plan.md` Step 5 defines for the `issue-to-plan` workflow's own
  plan-generation step — the issue's Required Changes explicitly calls for reject
  behavior.

## Alternatives considered
- Three separate scripts (`generate_issue.py` / `generate_plan.py` /
  `generate_implementation_procedure.py`), matching the existing one-script-per-
  purpose convention elsewhere in `tools/`: rejected for now per the source issue's
  explicit default (single script + `--kind`); the three render/filename functions
  are kept internally separated per kind so a future split remains a mechanical
  extraction.
- Auto-increment on filename collision (mirroring `templates/plan.md` Step 5):
  rejected — the issue's Required Changes explicitly states reject-only behavior.

## Implementation
### Target file
`tools/generate_workitem.py`

### Procedure
1. Parse CLI arguments: `--kind {issue,plan,implementation-procedure}` (required),
   `--id`, `--title` (issue mode), `--source-plan`, `--target-file-path`
   (implementation-procedure mode).
2. Read the template file for the selected kind and extract the text strictly
   between the first ` ```markdown ` fence and its matching closing ` ``` ` marker.
3. Compute the output filename for the selected kind (see Method below).
4. In implementation-procedure mode, validate `--source-plan` exists; if not,
   print an error and exit non-zero without writing (REQ-004).
5. Check the computed output path for collision against its target directory and
   the directory's `done/` counterpart; if either exists, print an error and exit
   non-zero without writing (REQ-003).
6. Write the extracted skeleton verbatim to the computed output path.

### Method
Single-entry-point CLI script using `argparse`, following
`tools/generate_reference_table.py`'s `ArgumentParser` + `choices`-constrained
option structure as a consistency reference. Filename computation:
- issue: `{timestamp}_{id}_{slug}.md` in `issues/` (per
  `skills/issue-creator/SKILL.md` Issue Filename Generation) — `{slug}` is `--title`
  lowercased with spaces replaced by dashes.
- plan: `{timestamp}_plan.md` in `plans/` (per `templates/plan.md` Step 5).
- implementation-procedure: `{timestamp}_{seq}_{target_file_slug}.md` in
  `implementations/`, where `target_file_slug` is `--target-file-path` with `/` and
  any non-alphanumeric/`_`/`-`/`.` character replaced by `_` (per
  `skills/plan-to-implementation-procedure/workflow.md` Workflow position). `seq` is
  not independently derivable by this tool from a single `--target-file-path`
  invocation; accept it as a required companion value the caller supplies
  alongside `--target-file-path` when invoking implementation-procedure mode.
- `{timestamp}` is generated by the script itself at invocation time
  (`YYYYMMDD-HHmmss`), independent of any caller-supplied value.

### Details
- Template extraction: locate the first line matching ` ```markdown ` and the next
  line thereafter matching exactly ` ``` `; the extracted skeleton is every line
  strictly between them (exclusive of the fence markers themselves).
- Each mode's writer creates parent directories only if the target directory
  already exists per the Plan's `Implementation Target Files` evidence (`issues/`,
  `plans/`, `implementations/` all currently exist) — the tool does not create a
  top-level work-item directory that does not already exist.
- Exit codes: `0` on success: `1` on any validation failure (missing
  `--source-plan`, filename collision, unreadable template file).
