`scripts/mcp_servers/web_search/web_search_tools.py::TOOL_LIST`
(`search_web`, `browser_fetch`), marking both as read-only, non-serial,

## Design decisions

- Both `search_web` and `browser_fetch` get `is_write=False`,
  `requires_serial=False`, `resource_scope_kind=""`, `resource_scope_keys=[]`
  — no argument on either tool (`query`/`max_results` on `search_web`;
  `url`/`max_response_kb` on `browser_fetch`) identifies a mutable resource;
  both are read-only fetches against external, non-shared-store targets (the
  web itself), so there is no meaningful scope to serialize against, matching
  `browser_fetch`'s own description: "read-only; no JavaScript execution, no
  interactive actions."
- Field placement: appended after `"status": "production",` on
  `search_web`, and after `"config_dependent": True,` on `browser_fetch`
  (preserving existing key order on both).

## Alternatives considered

- Scoping `browser_fetch` by its `url` argument's host
  (`resource_scope_kind="web_host"`, `resource_scope_keys=["url"]`): rejected
  — the plan's Affected-areas row explicitly states `resource_scope_kind=""`
  (unscoped) for both tools, and since both are read-only, no scheduling
  conflict-graph edge would ever form for them regardless of scope value
  (per the plan's Design: "Read/read pairs are never edges"), so host-level
  scoping would add metadata with no observable scheduling effect.
- Treating `browser_fetch` as write-like because it performs an outbound
  network fetch: rejected — the tool's own description explicitly
  self-identifies as read-only, and the plan's Affected-areas row classifies
  it as read-only alongside `search_web`.

## Implementation

### Target file: `scripts/mcp_servers/web_search/web_search_tools.py`

### Procedure

1. Read the current 2-entry `TOOL_LIST` in full (already done for this doc —
   confirmed no schema-2.0 fields present on either entry).
2. Append 4 keys to `search_web`'s dict after `"status": "production",`
   (line 37).
3. Append the same 4 keys to `browser_fetch`'s dict after
   `"config_dependent": True,` (line 64).
4. Leave `inputSchema`, `description`, and `required` unchanged on both.

### Method

## Compatibility considerations

- Additive-only dict-literal change; no import/signature changes.
- `tests/agent/services/test_runtime_tool_routing_integration.py`'s
  `_make_runtime_registry()` helper currently builds a `browser_fetch`
  `RuntimeTool` fixture directly via `build_runtime_tool(..., resource_scope="",
  ...)` (the *current* singular-field signature) rather than reading this
  file's `TOOL_LIST`; this doc's change to `TOOL_LIST` does not by itself
  require that fixture to change, but once `build_runtime_tool()`'s signature
  is renamed to `resource_scope_kind`/`resource_scope_keys` (a different
  file's change, per the plan's Phase 1), that fixture's construction call
  needs updating too — tracked in the sibling doc for that test file, not
  here.
- Becomes load-bearing once `mcp_tool_discovery.py`'s validator requires all
  4 fields — without this change, both `search_web` and `browser_fetch`
  would be excluded from the registry, removing web search/fetch from the
  LLM-visible tool surface.

## Security considerations

- No change to the domain allowlist enforcement (`browser_fetch`'s "Host
  must be in the configured domain allowlist") or `search_web`'s external
  search provider integration — this doc is metadata-only.
- Marking both tools non-serial/unscoped is consistent with their read-only,
  externally-directed nature; no serialization requirement is lost by this
  classification since neither tool ever mutates local or shared state.

## Rollback considerations

- Revert is a pure removal of the 4 appended keys per entry; no persisted
  state or data migration involved.
