## Goal

Change `run_approval_checks()` in `scripts/agent/tool_approval.py` to accept
already-prepared tool calls (`list[PreparedToolCall]`, with already-parsed `args`)
instead of raw `tc: dict` values, removing its own independent `orjson.loads()` /
`except orjson.JSONDecodeError` fallback (current lines 200-208) — once the new
preparation phase (`scripts/agent/tool_preparation.py`) runs first, this function never
receives an unparsed call, so the lenient "invalid JSON → empty dict" path becomes dead
and inconsistent with the plan's fail-closed guarantee.

## Scope

In scope: `scripts/agent/tool_approval.py`'s `run_approval_checks()` (current lines
187-219) only — its parameter type, its body's JSON-handling block, and its return
type's element type (`list[dict]` → `list[PreparedToolCall]` for the approved side;
`denied_ids: list[str]` unchanged).

Out of scope: `check_approval()` (lines 123-184) — its signature
`(ctx, tool_name: str, args: dict[str, Any]) -> bool` is unchanged; it already takes
already-parsed `args`, so `run_approval_checks()` passing `pc.args` instead of
`args_preview` requires no change on `check_approval()`'s side. `_build_preview_with_dry_run()`,
`_prompt_user_approval()`, and the preflight/risk helpers imported from `tool_policy.py`
are unaffected.

## Assumptions

- `scripts/agent/tool_runner.py:554` (`from agent.tool_approval import
  run_approval_checks`, inside `_run_approval_gate()`) is the only call site of
  `run_approval_checks()` (confirmed via `grep -rn "run_approval_checks"` across
  `scripts/` — one production hit, in `tool_runner.py`; test hits only in
  `tests/agent/test_tool_approval_preflight.py`), so this signature change has exactly
  one production caller to update, covered by the `tool_runner.py` doc in this set.
- `PreparedToolCall` (from the new `scripts/agent/tool_preparation.py`) exposes `call_id:
  str`, `name: str`, `args: dict[str, Any]` directly — `run_approval_checks()` reads
  `pc.call_id`/`pc.name`/`pc.args` rather than `tc["id"]`/`tc["function"]["name"]`/a
  freshly-decoded `args_preview`.

## Design decisions

- **Drop the `orjson.loads`/`except orjson.JSONDecodeError` block entirely rather than
  keeping it as defensive redundancy.** Once preparation guarantees `pc.args` is already
  a valid `dict` (enforced upstream, before this function is ever called), re-parsing or
  re-validating here would be dead code that could mask a real upstream bug (e.g., if a
  future caller mistakenly bypasses preparation) by silently falling back to `{}` instead
  of surfacing a type error.
- **No new exception raised for a hypothetical raw-dict caller.** The plan's Risks
  section (mitigation for the removed-fallback risk) suggests "a type-level guard
  (`PreparedToolCall` as the sole accepted parameter type)" — this is satisfied by the
  parameter type annotation itself (`tool_calls: list[PreparedToolCall]`); no runtime
  `isinstance` check is added, consistent with this codebase's existing style of relying
  on type annotations + mypy rather than runtime guards for internal call contracts (no
  other function in this file performs a runtime type check on its parameters).
- **`approved_calls` returned by `run_approval_checks()` is `list[PreparedToolCall]`,
  not `list[dict]`**, so `tool_runner.py`'s `_run_approval_gate()` and the functions it
  feeds (`_execute_with_dag()`, `_execute_standard()`) consume `PreparedToolCall`
  end-to-end with no intermediate re-wrapping.

## Alternatives considered

- Keeping the `orjson.loads`/`except` block as a no-op safety net (parse `pc.args` again
  even though it is already a `dict`, just in case). Rejected: `pc.args` is typed
  `dict[str, Any]`, not `str`; there is nothing to re-parse — `orjson.loads()` on an
  already-decoded dict would be a type error, not a redundant no-op, so keeping the
  block is not merely unnecessary, it is incorrect after the type change.
- Adding a runtime `isinstance(pc, PreparedToolCall)` assertion at the top of
  `run_approval_checks()`. Rejected: no other function in this module or
  `tool_runner.py` performs runtime type assertions on its own parameters; the type
  annotation plus mypy checking (per `rules/toolchain.md`'s validation sequence) is the
  established enforcement mechanism in this codebase.

## Compatibility considerations

- `check_approval()` is unchanged and remains independently callable with a plain
  `(ctx, tool_name, args)` triple — any test or future caller that constructs its own
  `args` dict directly (bypassing `run_approval_checks()`/preparation entirely) is
  unaffected by this doc.
- `run_approval_checks()`'s return type's first element changes from `list[dict]` to
  `list[PreparedToolCall]` — the sole production caller (`tool_runner.py`'s
  `_run_approval_gate()`) is updated in the same change (see that file's doc); any test
  that asserts on the returned `approved_calls`' shape (e.g. indexing
  `approved[0]["function"]["name"]`) must be updated to `approved[0].name` — covered by
  the `tests/agent/test_tool_approval_preflight.py` doc in this set, the only test file
  that calls `run_approval_checks()` directly.

## Security considerations

- Removing the lenient "invalid JSON → empty dict, continue anyway" fallback closes a
  second (now redundant, since preparation already rejects malformed JSON) path where a
  malformed tool call could still reach `check_approval()` with fabricated empty
  arguments rather than being rejected outright. After this change, that path simply
  cannot occur — a malformed call never reaches this function at all.

  caller) and `tool_preparation.py` (the type it now depends on) — see the
  `tool_runner.py` doc's Rollback section for the combined-revert note.
- No persisted state; rollback is source-only.
