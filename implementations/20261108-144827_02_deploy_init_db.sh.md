## Goal
Extend the hardcoded `REQUIRED_WORKFLOW_TABLES` list in `deploy/init_db.sh` to include
`tool_call_state` so the deploy pre-flight refuses the same gap-shaped databases the Python
startup gate will refuse (`REQ-002`), and pin shell/Python list equality with a new test.

## Scope
**Release unit**: wfaudit003-full (Phase 1)

- Covers Plan `plans/20261108-084006_wfaudit003_schema-gate-table-gap.md` row 2 only:
  `deploy/init_db.sh` (L46), plus the new list-parity test file.
- The mirrored list is table-presence only (matching the script's existing loop); column-level
  requirements stay owned by the Python gate (procedure `144827_01`).

## Assumptions
- Procedure `144827_01` (Python gate entry) lands in the same release unit; the parity test fails
  until both lists agree, which is the intended pin.
- The deployed copy under `/opt/llm/deploy/` is refreshed by `deploy.sh` sync; no manual edit of
  the deployed file is part of this procedure.

## Design decisions
- Keep the shell gate as a presence-only mirror: the script loops table names via `sqlite3`
  (`deploy/init_db.sh` L46-60); adding per-table `PRAGMA table_info` checks to shell would
  duplicate gate semantics outside the Python source of truth. The Python gate performs the
  column-level refusal.
- The parity test parses the shell constant textually instead of executing the script, so it runs
  in CI without deploy paths or services (`rules/env.md` deploy root is absent in dev checkout
  parts of the suite).

## Alternatives considered
- Sourcing the shell list from Python at deploy time (single physical list): rejected by the plan
  Design section — it couples the pre-flight script to the venv.
- Having `init_db.sh` call `check_workflow_schema()` directly for the workflow DB: rejected for
  this change; the existing presence loop and legacy-marker loop are the established shape of the
  script, and the eventbus fingerprint block shows the Python-bridge pattern is reserved for
  fingerprint-only checks.

## Implementation
### Target file
`deploy/init_db.sh` — `REQUIRED_WORKFLOW_TABLES` assignment (L46).

### Procedure
Append `tool_call_state` to the space-separated list. No loop or message changes.

### Method
Change L46 from:

```bash
REQUIRED_WORKFLOW_TABLES="tasks attempts processed_events artifacts"
```

to:

```bash
REQUIRED_WORKFLOW_TABLES="tasks attempts processed_events artifacts tool_call_state"
```

### Details
- The existing loop (L48-54) and the `[FATAL]`/`Missing table(s):` messages (L56-59) then cover
  `tool_call_state` automatically; the OK line (L61) prints the extended list.
- The parity test (new file `tests/deploy/test_required_workflow_tables_parity.py`, see Validation
  plan) reads this constant plus the one in `deploy/setup_services.sh` (procedure `144827_03`) and
  compares against `agent.services.workflow_schema.REQUIRED_WORKFLOW_TABLES` keys.

## Compatibility considerations
- Deployed databases created by `create_workflow_schema()` already contain `tool_call_state`, so a
  current production `workflow.sqlite` passes the extended pre-flight unchanged (plan `UNK-01`
  probe still gates rollout before deploy).
- The script remains read-only: it only runs `SELECT` queries against `sqlite_master`.

## Security considerations
- No new attack surface; the sqlite3 invocations use the same query shape as the existing entries.

## Rollback considerations
- Reverting L46 restores prior pre-flight behavior; revert together with the Python gate entry and
  `setup_services.sh` mirror (procedures 01, 03) or the parity test fails — which is the pin
  working as designed.
