## Goal
- Record an explicit decision for `git_checkout`/`git_pull`/`git_push`'s approval
  tier in `config/agent.toml` (REQ-006).

## Scope
- In scope: three new lines in `config/agent.toml`'s `[approval_risk_rules]`
  section.
- Out of scope: `[tool_safety_tiers]` (the `WRITE_DANGEROUS` classification itself),
  `agent/tool_policy.py` logic.

## Assumptions
- Pending UNK-01 sign-off; this document assumes the Plan's default (raise to the
  full-word-`yes` tier). Do not implement before sign-off is recorded per
  `rules/coding.md` Explicit sign-off gates, on `plans/20260825-095817_plan.md`.

## Design decisions
- `_TIER_TO_RISK` maps `WRITE_DANGEROUS` to `RiskLevel.MEDIUM` (`y/N` prompt).
  `approval_risk_rules` entries are checked first in `classify_risk()` and override
  the tier default when present.
- Add, matching the existing `delete_file`/`shell_run`/`github_push_files` pattern:
  ```
  git_checkout = "high"
  git_pull = "high"
  git_push = "high"
  ```
- `RiskLevel` values are `none`/`medium`/`high` (`tool_enums.py::RiskLevel`); match
  existing entries' exact spelling.

## Alternatives considered
- Explicitly affirming the current `y/N` tier as intended (UNK-01's other option) —
  in that case, this document's code change does not apply; only a decision record
  (e.g. a comment in `config/agent.toml`) would be added instead. Adopt this
  alternative if sign-off says "keep MEDIUM."

## Implementation
### Target file
`config/agent.toml`

### Procedure
1. Open the `[approval_risk_rules]` section (where `delete_file = "high"` etc. are
   listed).
2. Add the three `git_*` lines near the existing `github_delete_file = "high"` etc.
3. Leave `[tool_safety_tiers]`'s `git_checkout`/`git_pull`/`git_push` entries
   (`= "WRITE_DANGEROUS"`) unchanged — only the approval override is added, not the
   tier classification.

### Method
- Plain TOML line additions. No code change; takes effect on service restart since
  `agent/tool_policy.py` reads `cfg.approval.approval_risk_rules` at call time.

### Details
- After this change, `classify_risk()`'s Priority 1 check
  (`raw_rule = cfg.approval.approval_risk_rules.get(tool_name)`) resolves
  `base = RiskLevel.HIGH` for these three tools.
- `RiskLevel.HIGH` short-circuits further escalation logic (e.g.
  `_special_case_risk()`/`_escalate_for_path()`), so `HIGH` is the final resolved
  value.
- `tool_approval.py`'s `RiskLevel.HIGH` branch (full-word `"yes"` confirmation) then
  applies.

## Compatibility considerations
- A non-interactive/automated caller currently relying on the `y/N` prompt could
  break if it does not also handle the full-word-`yes` prompt (see Risks below and
  the Plan's Risk section).
- `docs/04_mcp_05_03_fail-open-fail-closed-and-risk-tiers.md`'s cross-reference to
  `04_mcp_04_05_git.md` Approval level should be checked for consistency after this
  change (separate follow-up, not this document's scope).

## Security considerations
- The change only raises the risk classification; it introduces no privilege
  reduction or bypass.
- All three tools already belong to `GIT_WRITE_TOOLS`; this change is independent of
  `git_service.py`'s separate ref-safety/protected-branch validation layer.

## Rollback considerations
- Removing the three lines immediately restores the prior `y/N` behavior. No code
  change, so rollback requires only a config change and restart.
