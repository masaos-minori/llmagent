## Goal
- Create `tools/amend_plan.py`: append one target file to a Frozen Plan in `plans/` consistently, re-check the four Plan Freeze criteria for the new row, and print the results of the structure, path-audit, and overlap checks (`REQ-001`, `REQ-002`, `REQ-003`).

## Scope
- In scope: the new tool module. Out of scope: removing or reordering rows, changing requirements, generating the new row's procedure, the tests (seq 02), and registration (seq 06 to 08).

## Assumptions
- Step 3a verification (2026-11-02): no tool amends a Plan today; `tools/check_workitem_structure.py`, `tools/audit_plan_target_paths.py`, and `tools/check_plan_target_overlaps.py` exist and only check. The Plan layout the tool edits (target table, `Freeze status` line, `Affected areas`, `Implementation steps`, `### Requirement Traceability`, `### Work Items Created`, `Related target files` line) was confirmed in `templates/plan.md` and the current Plan.
- Plan A10 (added in Step 3a): `tools/audit_plan_target_paths.py` reads the second cell (`Change Responsibility`) for a creation hint, so for a path that does not exist the tool writes `New file:` at the start of that cell.
- Plan A11 (added in Step 3a): `tools/check_plan_target_overlaps.py` reads only the first token after `**Freeze status**:`. The tool changes that token only on failure (`Frozen` to `Draft`) and places dated amendment lines on their own lines after the existing note. That checker takes no plan argument and prints repository-wide findings, so the tool prints only the lines that name the amended Plan.
- Plan A2 to A5: the log is the dated line in the `Freeze status` note; an `Affected areas` row is added; the `Work Items Created` row is added only with `--procedure`; the class is stated by the caller and recorded, never decided by the tool.
- Overlap (Step 2): no other Frozen Plan creates this file.

## Design decisions
- Pure functions over the Plan text: parse sections, build the intended edits, apply them to an in-memory copy, and write once (temp file, then replace) only on a real run, so any refusal leaves the Plan unchanged.
- Each edit is located by its own `## ` or `### ` heading or its own line prefix, never by a global search for a path string, so a similar path earlier in the file is not touched (`REQ-002`).

## Alternatives considered
- A dedicated amendment-log section in the Plan: rejected (Plan A2), it would change `templates/plan.md` and two checkers.
- The tool classifying the amendment: rejected (Plan A5), the owner's policy is pending.

## Implementation
### Target file
`tools/amend_plan.py` (new)

### Procedure
1. Create the module with a docstring (purpose, usage, exit codes) and a `main(argv)` entry point using `argparse`: positional plan path; required `--file`, `--responsibility`, `--reason`, `--requirement`, `--evidence`, `--tests`, `--step`, `--class` (`fallout` or `scope`); optional `--procedure` and `--dry-run`.
2. Refusals first, each printing the reason, exiting 1, writing nothing: the path is not under `plans/` (a `plans/done/` Plan is refused), the Plan is missing or lacks a required section, the file is already an `Implementation Target Files` or `Reference Files` row, or the same amendment line already exists.
3. Build the edits in order: row appended after the last row of the target table; `Freeze status` line `Amended {date} ({class}): added {path} — {reason}`; Requirement Traceability row; path appended to `Related target files`; `Affected areas` row; a checkbox appended to step N; a `Work Items Created` row when `--procedure` is given (otherwise report it as skipped).
4. Freeze re-check on the new row: the path exists, or the row is `New file` with an existing parent directory; reason non-empty; evidence non-empty; the requirement ID is defined in the Plan's `Requirements`. All pass: row `Verified`, `Frozen` kept. Otherwise row `Needs confirmation`, first Freeze token set to `Draft`, failed criterion named in the output.
5. Dry run prints each edit as a before and after excerpt plus the checks it would run and writes nothing. A real run writes once, then runs the three checks and prints their results.

### Method
- Split sections on line-start `## ` and `### ` headings; a table edit works on the contiguous `|` lines of the named table and inserts after its last data row; cell text escapes `|`.
- Date from the standard library; step N located by its `N. **` list item inside `## Implementation steps`, the new checkbox placed after that item's last `- [ ]` line with the same indentation.
- Requirement Traceability row: requirement ID, `Amendment {date}: {reason}`, the path, `Phase {N}`, the acceptance criteria that cite the requirement (or `N/A: none cites {REQ}`), the `--tests` text, `Confirmed by repository evidence`.
- Run the three checks with `subprocess.run` over a fixed argv list built from `sys.executable` (no shell); a `# nosec` needs the rule code plus an em-dash justification (`tools/check_suppression_justification.py`).

### Details
- Exit codes: 0 success (including a dry run and a reported `Draft` outcome), 1 refusal or failed check, 2 usage error. The tool edits only the named Plan and never creates the procedure document.

## Compatibility considerations
- Additive new tool. A Plan lacking a required section is refused, not guessed at.

## Security considerations
- Fixed-argv subprocess calls, no shell, no network. Writes only the named `plans/*.md` file; the `plans/` prefix check runs before any read-modify-write.

## Rollback considerations
- Delete the new file (single path) or revert the commit. A Plan edited by mistake is restored with `git checkout` of that one path, since all edits land in one write.

## Completion criteria
- Dry run prints every edit and changes nothing (AC-1); a file already a target or reference row is refused with the reason (AC-2); edits are section-scoped and the row is appended last (AC-3); a failed criterion leaves the Plan `Draft` and names it, a passing row keeps `Frozen` (AC-4); lint, type, and security checks are clean.

## Out of Scope
- Removing or reordering rows, requirement changes, generating the procedure for the new row, editing any real Plan, and the approval policy text.
