## Goal

Reduce `scripts/rag/ingestion/ingester.py` to ~100 lines of pure orchestration glue code by delegating all extracted concerns to the 7 new modules created in Rows B–H. Preserve `RagIngester` as the public API facade.

## Scope

- Modify `scripts/rag/ingestion/ingester.py`: remove methods delegated to extracted modules, replace calls with delegate invocations
- Add test file `tests/test_ingester_orchestrator.py` for the reduced orchestrator
- Verify cyclomatic complexity of `ingest_all` and `ingest_url_group` ≤ B(3)
- Verify no import errors across the project after refactoring

## Assumptions

- Rows B–H have been implemented first (per Phases 1–7); their extracted classes exist and expose the expected public APIs
- `RagIngester`'s public interface (`ingest_all`, `ingest_url_group`) must remain unchanged
- Existing callers import via `from rag.ingestion.ingester import RagIngester` — this path must continue to work

## Design decisions

- **Thin facade pattern**: RagIngester becomes a composition of 7 concern classes; remains the single public class
- **Dependency injection**: extracted components receive dependencies (config, db_path, etc.) via constructor — no global state access
- **Constants relocation**: constants moved to appropriate concern classes during earlier phases
- **Import consolidation**: inline imports removed where possible

## Alternatives considered

- Keep some methods in RagIngester and only extract the most complex ones — rejected because it leaves residual complexity hotspots
- Merge multiple concerns into fewer classes — rejected because it defeats the purpose of separation of concerns
- Use a service locator instead of DI — rejected because it introduces hidden coupling

6. Ensure `RagIngester` line count < 200

### Method

Extract each concern class using Deletion-First approach:
- Write the new class/module first (before deleting from RagIngester)
- Verify the new class works in isolation (unit tests pass)
- Then delete the old code from RagIngester
- Finally update RagIngester to delegate to the new class

## Security considerations

- Path validation in `_is_db_path_allowed` must be preserved — prevents WAL files outside allowed directories
- Error handling in resource shutdown must not leak sensitive information (DB paths, config values)
- Signal handler cleanup must not leave dangling references that prevent GC
- HTTP client must be closed properly when RagIngester is garbage collected

## Rollback considerations

- If any extracted class fails validation, revert to monolithic RagIngester:
  1. Delete newly created modules
  2. Restore original `ingester.py` from git
  3. Update `__init__.py` to remove new exports
- Each row is independently reversible — partial rollback is possible by keeping the original `ingester.py` as a reference
