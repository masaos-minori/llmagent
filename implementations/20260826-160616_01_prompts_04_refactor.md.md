## Goal

Add an eight-field Architecture Baseline (`REQ-001`-`REQ-004`, purpose: capture the
structural "before" state of a Path C change) to the end of `prompts/04_refactor.md`'s
`#### Step 4: Behavior lock`, and an eight-item Architecture Comparison Validation set

architectural refactoring is verifiable structurally, not only behaviorally, without
weakening the existing Behavior Lock, public API, exception, or side-effect guarantees
(`REQ-008`).

## Design decisions

- **Heading level and nesting position**: `##### Architecture Baseline (Path C)` and
  `##### Path C: Architecture Comparison Validation` are both `#####`-level
  subsections, siblings of the other existing `#####` subsections under their parent
  `####` Step (Step 4 and Step 7 respectively) — matching the Plan's own Validation
  plan instruction and the precedent set by both sibling documents' identical treatment
  of their own inserted subsections.
- **Field-to-mechanism mapping reuses existing tooling wherever possible** (`REQ-002`):
  five of the eight Architecture Baseline fields map to an already-established
  repository tool or check (dependency direction: `pydeps`/`import-linter`; state
  ownership: reuse of Step 5's "Global mutable state" inventory item; configuration
  dependencies: `rg` against `config/*.toml`/`config_loader.py`; routing or
  registration: the `rg "ToolRouteResolver\|tool_names"` command; deployment
  references: reuse of Step 3's existing `deploy.sh` check). The remaining three
  (module ownership, entry points, lifecycle ownership) have no established repository
  command and are stated as explicit manual-capture fields (`UNK-01`-`UNK-03`) rather
  than left silently unspecified — per the Plan's own resolution path.
- **Step 7 items are pure before/after comparisons, not a new discovery mechanism**
  (`REQ-006`): each of the eight comparison items is defined as "the same capture
  method from the Architecture Baseline, run again after Step 6 Transformation,
  compared against the value recorded before it" — consistent with Step 7's existing
  character (it validates against baselines established earlier in the workflow, e.g.
  Step 5's side-effect inventory recheck). "Migration validation" and "rollback
  validation" are tied to concepts owned by issue 02's document (atomic migration
  group; the rollback-strategy item of its seven-item pre-implementation checklist)
  rather than redefined here.
- **Reporting-vocabulary reuse, not duplication** (`REQ-007`): Step 7 already defines a
  complete `Not run`/`Blocked` reporting rule for its Conditional validation list. This
  document's eight new items reuse that rule rather than introducing a second one —
  the same design discipline both sibling documents applied to "Proposal" and to the
  atomic-migration-group concept. The text explicitly states that only evidence
  availability, not requiredness, may be `Not run`/`Blocked` for these eight items,
  since they are mandatory-when-Path-C-applies, unlike the genuinely-optional
  Conditional validation list they borrow vocabulary from.
- **Path-C-only scoping stated explicitly at both insertion points** (`REQ-004`): each
  new subsection opens with a sentence stating it applies only when Path C, so Path A/B
  behavior is unaffected — required by the issue's own Out-of-Scope item "Changing Path
  A or Path B validation depth."

## Alternatives considered

- Making either new subsection a new, separately numbered Step (e.g. "Step 4.5" or
  "Step 7.5") was rejected: it would violate `REQ-008`'s "no renumbering of existing
  Steps," and the Plan's Design section explicitly confirms no step renumbering is
  needed.
- Defining a second, Path-C-specific `Pass`/`Fail`/`Not run`/`Blocked` reporting
  vocabulary distinct from Step 7's existing Conditional-validation rule was
  considered, to make the eight items' mandatory-when-applicable status more visually
  distinct from the genuinely-optional Conditional list; rejected because `REQ-007`
  explicitly requires reuse, and a second vocabulary would itself be the kind of
  duplication the Plan's Risks section warns against — the mandatory/optional
  distinction is instead carried by one explicit sentence rather than by a parallel
  vocabulary.
- Placing the Architecture Baseline subsection earlier in Step 4 (e.g. immediately
  after the coverage/`mutmut` bullets, before the manifest list) was considered, to
  keep "baseline-capture" content together; rejected in favor of the Plan's own Design
  instruction to append after all of Step 4's existing content, including whichever
  Path C depth bullet issue 02's document may already have added — this keeps the
  insertion point stable regardless of implementation order between this document and
  issue 02's.
- Fixing issue 02's open Plan Gap (the Path classification framing sentences not
  mentioning Path C) as part of this document was considered, since it is adjacent to
  this document's Path-C-scoped content; rejected — it is a change to `##### Path
  classification` text that neither this Plan's `Implementation steps` nor issue 02's
  Plan authorizes, so per `workflow.md` Step 3 it is reported as a cross-reference
  (see Assumptions) rather than silently implemented.

```markdown
##### Architecture Baseline (Path C)

Applies only when the change is classified Path C (see `##### Path C: Architectural
Refactoring`). Path A and Path B proceed through this Step exactly as today, unaffected.

Before any Path C transformation begins (Step 6), capture all eight of the following
fields:

- **Module ownership**: no established repository command exists for this field
  (verified: no `CODEOWNERS` file, no ownership-registry document, no documented
  ownership-check command anywhere in `rules/`, `routing.md`, or `skills/`). Capture
  manually by direct code inspection, using `rules/env.md` Architecture's six-layer
  diagram (`scripts/{agent,db,eventbus,mcp_servers,rag,shared}/`) as the default
  ownership unit (the owning layer/module directory).
- **Dependency direction**: run `pydeps` (import graph) and `import-linter`/
  `lint-imports` against `.importlinter`'s contracts — the same tools this Step already
  runs at Path B/C depth — cross-checked against `rules/env.md` Architecture's layer
  diagram.
- **Entry points**: no single established repository command covers all entry-point
  types. Capture manually via `rg "if __name__ == .__main__.":` plus direct inspection
  of `config/agent.toml` service definitions and the relevant MCP server class's
  `http_port` class variable (`scripts/mcp_servers/server.py`-derived modules).
- **Lifecycle ownership**: no established repository command exists for this field
  beyond module-naming convention. Capture manually via `rg` for class names containing
  `Lifecycle` and for `start`/`stop`/`shutdown` method definitions in the affected
  module.
- **State ownership**: reuse this Step's sibling Step 5's existing side-effect
  inventory "Global mutable state" item as the baseline record for this field; do not
  define a second, separate capture method.
- **Configuration dependencies**: `rg` against `config/*.toml` and
  `shared/config_loader.py` usages, consistent with `rules/env.md`'s statement that
  `config/agent.toml` is the configuration SSOT.
- **Routing or registration**: `rg "ToolRouteResolver\|tool_names" scripts/shared/` —
  the exact command already named in `skills/python-refactoring/workflow.md` Special
  Cases and cross-referenced by this file's own Special Cases section.
- **Deployment references**: reuse Step 3's existing "referenced in `deploy.sh`" check
  verbatim; do not define a second deploy-reference check.

Module ownership, entry points, and lifecycle ownership are manual-capture fields with
no established repository tooling — record them explicitly as such rather than
applying an inconsistent ad hoc method across runs.

Do not start a Path C transformation (Step 6) if any required Architecture Baseline
field is missing or its capture is incomplete.
```

Insert exactly this text at insertion point 2 (end of Step 7, before `#### Step 8:

```markdown
##### Path C: Architecture Comparison Validation

Applies only when the change is classified Path C. These eight items are mandatory
checks for Path C — not optional the way the Conditional validation list above is; only
their evidence availability, not their requiredness, may be `Not run`/`Blocked`.

For each item, re-run the same capture method recorded in the Architecture Baseline
(Step 4) after Step 6 Transformation, and compare the result against the baseline
recorded before transformation:

- **Before-and-after dependency comparison** — compares the dependency direction field.
- **Architecture-boundary comparison** — compares the dependency direction field,
  cross-checked against `.importlinter` contracts and `rules/env.md`'s layer diagram.
- **Ownership validation** — compares the module ownership and state ownership fields.
- **Migration validation** — verifies every declared atomic migration group member (see
  `##### Path C: Architectural Refactoring`) was transformed and no partial-migration
  state remains.
- **Rollback validation** — verifies the rollback strategy declared in that same
  subsection's pre-implementation checklist is actually exercisable, not merely stated.
- **Route, tool, or plugin registration comparison** — compares the routing or
  registration field.
- **Configuration and deployment comparison** — compares the configuration
  dependencies and deployment references fields.
- **Removed-symbol reference check** — a repository-wide (not target-file-scoped) `rg`
  search for old symbol names, extending Step 6's "no legacy symbol names remain" rule
  and Step 9's equivalent check beyond the target file or migration group to the whole
  repository.

Report each item as one of `Pass`, `Fail`, `Not run`, or `Blocked`, reusing the
Conditional validation reporting rule above verbatim in spirit: report why an item was
not run, use a repository-defined alternative when available, do not report a skipped
item as passed, report `Blocked` only if the missing check is required to prove
behavior preservation, and otherwise record it as `Not run`.
```
