## Assumptions
- `drift_report()` treats a mapping entry that is not a routing checker as an error, so these rows must land in the same change as the row 01 mapping entries (Step 3a, checked against current code).
- Step 3a: `check_adr_reference` appears only inside the Notes cell of the `check_adr_authority` row; `_parse_routing_run_cells` reads Run cells only, so a new row is required.
- Step 3a: `check_workitem_traceability` has no routing row; its Run cell must include `--active-only` to give the id the gate and the hook have.
- Overlap (Step 2): `routing.md` is also targeted by the Plans filed from `flowimp001`, `flowimp003`, `flowimp004`, `flowimp010`, and `flowimp011`. Judged compatible: `flowimp004` adds an entry to the "Conditional load" list (a different section); the others add their own rows to the same "When to run which tool" table, so the edits are row-additive and do not contradict each other. Whichever lands later rebases.

## Design decisions
- Place the rows together, after the `check_docs_japanese` row at the end of the table, one row per checker, Notes cell stating the hook id and that the same check runs in pre-commit.
- Run cells use the `uv run python tools/<name>.py` form like every other row.

## Alternatives considered
- Reuse existing Notes wording style; a one-line blanket row naming all seven was rejected because `_parse_routing_run_cells` derives one id per row.

- A work item under `issues/`, `plans/`, or `implementations/` was added or changed | `uv run python tools/check_workitem_traceability.py --active-only` | hook `workitem-traceability`; archived items are excluded.
- Verify each Situation and Notes sentence against the checker's own docstring before writing it, and keep every Run cell free of `|` characters.
