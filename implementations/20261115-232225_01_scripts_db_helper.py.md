## Assumptions
- Verification finding (2026-11-15, re-verified against post-004 code): `open` (`:280-333`) already wraps only `_configure_connection` in `try/except Exception` (`:316-326`) and closes the connection only on the `read_only` branch (`:321-325`); the write path leaks on any post-connect failure. REQ-001 closes exactly this hole: teardown on all modes while keeping the read-only residue cleanup (`_cleanup_read_only_residue`, Plan 004 REQ-006) on the ro failure path.
- `self.conn` is assigned only at `:329` on the success path, so `helper.conn is None` after any failed open holds without extra work.
- `except BaseException` is ruff-clean in this repo (BLE001 does not flag it; precedents `scripts/agent/tool_runner.py:550`, `scripts/agent/startup_component_init.py:50`) — no noqa needed.
- Double `close()` is a no-op, so removing `_load_vec_extension`'s `conn.close()` (`:258`) is safe; the visible outcome (exception type, `helper.conn is None`) is unchanged for the frozen test `tests/db/test_sqlite_helper.py:358-369`.
- Overlap judgment: `helper.py` is also a Plan 006 target (row `begin_immediate` deprecation), but that row touches `:382` only — disjoint from this document's `open`/prepare region; batch order 005 → 006 (memo2.md sequencing) keeps the edits conflict-free.

## Design decisions
- Single-owner teardown via an extracted `_prepare_connection` (new) carrying the `try/except BaseException` handler: `open` is already B(9); inlining the widened handler would push it further, extraction also lowers `open`'s CC (Plan Design, complexity-control bullet).
- Guard first: the `load_vec is True and not self._vec_so` check runs before the re-open close and before `_connect`, so a doomed open neither closes a live connection nor creates one (REQ-004 "before any connection is created"). `load_vec=None` keeps `_default_load_vec` behavior verbatim, so the frozen default-skip tests (`:338-356`, `:371-395`) stay green.
- Re-open close reuses `self.close()` (already resets `self.conn = None` and runs residue cleanup) rather than a raw `conn.close()`, keeping one teardown site on the success-side lifecycle too.

## Alternatives considered
- Per-callee cleanup in every callee of `open`: rejected in Plan Design — any future callee re-introduces the leak class.
- Refusing non-reuse re-open with `RuntimeError`: rejected (Plan Design) — in-repo callers never treat a second `open()` as an error; close-with-debug-log preserves their behavior (UNK-01, non-blocking).

### Procedure

2. Remove `conn.close()` from `_load_vec_extension` (`:258`); keep the `OperationalError` log-and-raise and the `ValueError` guard (`:249-252`) as-is (REQ-002: `open`'s handler is the single teardown owner; an `AttributeError` from `enable_load_extension` (`:254`) now propagates with the connection closed by `open`).
3. Re-open close: in `open`, immediately after the reuse short-circuit (`:310-311`), insert the guard `if self.conn is not None:` → debug log ("closing previous connection on re-open") + `self.close()` (REQ-003; `reuse_connection=True` semantics unchanged — short-circuit precedes it).
4. Explicit-`load_vec` guard at the top of `open` (before step 3): `if load_vec is True and not self._vec_so: raise ValueError("load_vec=True requested but sqlite_vec_so is not configured")` (REQ-004). `is True` keeps the instance-default path (`load_vec=None`) untouched.
5. Update the `open` docstring: explicit `load_vec=True` must load or fail; a non-reuse `open()` closes a previously open connection (Issue: docstring-only documentation).
