## Goal

Retire `scripts/agent/tool_runner.py`'s name-keyed, statically-derived tool scheduling
metadata (`_build_tool_meta()`, its `is_side_effect()`/`SHELL_TOOLS` imports, and
`_execute_standard()`'s static `is_side_effect()` side-effect check) and replace it with
a call-id-keyed flow sourced from `ctx.services_required.runtime_tools` (a
`RuntimeToolRegistry`), the plan's single scheduling-metadata authority. This makes
`_execute_with_dag()` build a `dict[str, ToolSpec]` keyed by each approved call's `tc["id"]`
via `tool_spec_for_call(tc["id"], name, args)`, and makes `_execute_standard()`'s
batch-downgrade check derive `is_write` from the same registry instead of the static
frozenset/function pair.

## Assumptions

- `ctx.services_required.runtime_tools` is populated (non-`None`) before any tool call
  reaches `execute_all_tool_calls()`/`_execute_with_dag()` — per the plan's Assumptions
  section, confirmed by `scripts/agent/startup.py:367`
  (`ctx.services_required.runtime_tools = discovery.registry`) running before
  `_validate_tool_args()` (tool_runner.py:141) already depends on the same registry being
  present. Falsifiable if a call path exists where tool execution runs before discovery
  completes.
- `RuntimeToolRegistry.tool_spec_for_call(call_id, name, args)` (implemented, currently
  unused, at `scripts/shared/runtime_tool_registry.py:156-164`) and `ToolSpec.resource_scopes`
  (plural, replacing today's singular `resource_scope`) are delivered by other target
  files in this same plan cycle (`scripts/shared/tool_spec.py`,
  `scripts/shared/runtime_tool_registry.py`, `scripts/shared/resource_scope.py`) — this
  doc depends on their contracts as already specified in the plan's Scope/Design
  sections, not on re-deriving them here.
- `RuntimeToolRegistry.get(name)` raising `KeyError` for an unregistered tool name is the
  correct fail-closed signal for both `_execute_with_dag()` (propagated through
  `tool_spec_for_call()` and into `build_execution_groups()`, per the plan's Design
  section) and `_execute_standard()`'s new `is_write` lookup (caught locally, falling
  back to `True`, per UNK-02's resolution) — these are two different handling strategies
  for the same underlying `KeyError`, deliberately, because the DAG path treats a missing
  spec as a scheduling failure while the non-DAG path treats an unregistered tool as
  conservatively side-effecting.

## Design decisions

- **Call-id keying, not name keying, in `_execute_with_dag()`.** Two approved calls in
  the same batch can invoke the same tool name (e.g. two `write_file` calls on different
  paths); a name-keyed `dict[str, ToolSpec]` cannot distinguish their per-call `args`
  (and therefore their per-call `resource_scopes`), which is exactly the bug the plan's
  Design section identifies in the current `_build_tool_meta()`/`build_execution_groups()`
  pairing. Keying by `tc["id"]` (unique per call within a batch) is the only shape that
  lets each call carry its own resolved scopes into the scheduler.
- **Build the `dict[str, ToolSpec]` in `_execute_with_dag()`, not in a new helper.** The
  plan's Implementation steps describe this as a direct replacement of the
  `_build_tool_meta(tool_definitions)` call with an inline per-call loop calling
  `tool_spec_for_call()` — there is no indication a new named helper is wanted, and
  introducing one would add an indirection layer the plan doesn't call for. Keep the
  per-call spec construction as a simple loop building the dict directly at the current
  call site (lines 325-326).
- **Let `tool_spec_for_call()`'s `KeyError` propagate out of `_execute_with_dag()`
  uncaught.** The plan's Design section states a call with no registry entry "raises
  `KeyError` from `.get()` today — the scheduler must propagate this as a scheduling
  failure rather than swallow it." `_execute_with_dag()` itself does not need a
  try/except around the per-call `tool_spec_for_call()` calls; the failure surfaces
  either at spec-build time (`KeyError` from `.get()` inside `tool_spec_for_call()`) or,
  once `scripts/agent/tool_scheduler.py` is reworked, as its dedicated
  `MissingToolSpecError` when a call-id is absent from the passed-in `tool_meta` map —
  either way, `_execute_with_dag()` does not add its own catch/default here, preserving
  the fail-closed intent end to end.
- **`_execute_standard()`'s replacement checks `ctx.services_required.runtime_tools`
  directly, not a new wrapper.** Per the Design section's literal resolution of UNK-02:
  `(ctx.services_required.runtime_tools.get(name).is_write if registered else True)`.
  "Registered" is determined by calling `.get(name)` and catching `KeyError` locally (the
  registry has no separate `is_registered()`/`__contains__` — confirmed by the
  `RuntimeToolRegistry` methods read for this doc: `get()` is the only lookup and it
  raises `KeyError` on a miss), falling back to `True` on the exception. This keeps
  `_execute_standard()`'s batch-level downgrade mechanism conceptually distinct from
  `ToolSpec.requires_serial`'s per-call DAG barrier, exactly as
  `tool_scheduler.py`'s module docstring (read in full for the sibling doc in this set)
  requires — `_execute_standard()` still makes its own decision, just from a different
  metadata source.
- **Remove only the two named imports that become unused, not the whole import
  statement.** `from shared.tool_constants import SHELL_TOOLS` (line 25) is deleted
  entirely (nothing else in the file uses `SHELL_TOOLS`). `from shared.tool_executor_helpers
  import is_side_effect, tool_hash_key` (line 26) keeps `tool_hash_key` (used elsewhere in
  the file for cache-key computation, unrelated to scheduling) and drops only
  `is_side_effect` from the same `import` statement.

## Alternatives considered

- Keeping `_build_tool_meta()` as a thin wrapper around the new per-call flow (for
  backward compatibility with existing callers/tests). Rejected: the plan's
  Implementation steps explicitly say "delete `_build_tool_meta()` itself," and its
  existing tests (`TestBuildToolMeta` in `tests/agent/test_tool_runner.py`) are being
  removed/replaced as part of this same plan (see the paired test doc), so no caller
  outside this module needs it to remain.
- Catching `tool_spec_for_call()`'s `KeyError` inside `_execute_with_dag()` and
  synthesizing a conservative default `ToolSpec` (mirroring today's silent-default
  behavior). Rejected: this exactly reproduces the "unsafe silent default" the plan's
  Goal names as one of the four disagreeing metadata sources to eliminate; the plan
  requires the failure to propagate as a scheduling failure, not be swallowed at this
  layer.

## Security considerations

- The new `_execute_standard()` fallback (`True` for unregistered tools) is
  fail-closed/conservative — an unrecognized tool is now treated as side-effecting,
  triggering serial execution rather than silently running concurrently. This reduces
  risk of an undiscovered or misconfigured tool racing against other calls in the same
  batch.
- Propagating `tool_spec_for_call()`'s `KeyError` (rather than swallowing it into a
  synthetic default) prevents a tool call with no registry entry from silently being
  scheduled as if it were read-only/unscoped — closing the exact silent-default gap the
  plan's Goal names as a security-relevant scheduling-correctness issue.

## Rollback considerations

- The change is confined to one file's internals (`tool_runner.py`) plus its test file;
  reverting this doc's edits (restore `_build_tool_meta()`, the two imports, the
  name-keyed `tool_meta` build in `_execute_with_dag()`, and the static
  `is_side_effect()` check in `_execute_standard()`) is a straightforward `git revert` of
  this commit, independent of the `tool_scheduler.py` rework, *provided* the scheduler
  rework's signature change (call-id-keyed `tool_meta` parameter) is rolled back in the
  same revert — the two files' changes are interdependent (this file's `tool_meta` shape
  must match what `build_execution_groups()` expects), so they should land and roll back
  together, not independently.
- No data migration, schema change, or persisted-state change is introduced — rollback
  risk is limited to source-code behavior, not stored data.
