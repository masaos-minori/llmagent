# Implementation procedure: scripts/agent/tool_runner.py (approval-gate docstring correction)

## Goal

Correct the stale docstring on `tool_runner._run_approval_gate()` (which
currently describes an unimplemented `skip_in_workflow_mode`-based skip
during the execute stage) to state plainly that this function is the
sole per-tool-call approval gate for the batch, and add a regression test
proving `run_approval_checks` (via the interactive prompt it drives) is
invoked exactly once per risky tool call end-to-end.

Note: two other implementation procedure docs already exist for
`tool_runner.py` in this batch
(`implementations/20260726-100351_tool_runner.py.md` and
`implementations/20260726-101046_tool_runner.py.md`) but cover unrelated
topics — tool-argument schema validation and conversation-history message
validation, respectively. This doc is a distinct item, for the
approval-gate docstring and its regression test, and is not yet
implemented.

## Scope

- In scope:
  - `scripts/agent/tool_runner.py::_run_approval_gate()` — docstring-only
    edit (lines ~480-482 currently). No functional change to this
    function's body.
  - `tests/test_tool_runner.py` — add one new regression test asserting
    `run_approval_checks` (or the interactive prompt path it drives) is
    invoked exactly once for a risky tool call across a full
    `execute_all_tool_calls()` run, with a real (non-mocked-away)
    `RepositoryGateway` wired in as `ctx.services_required.gateway`.
- Out of scope:
  - `RepositoryGateway._gate_write()`'s redundant-call removal and its
    module/method docstrings — covered by the `repository_gateway.py`
    doc (`implementations/20260726-101359_repository_gateway.py.md`).
  - `tool_approval.run_approval_checks()`'s `skip_in_workflow_mode`
    parameter removal — covered by the `tool_approval.py` doc
    (`implementations/20260726-101440_tool_approval.py.md`).
  - Any other `tool_runner.py` change (tool-argument validation,
    conversation-history validation) — covered by the two pre-existing
    docs noted above.
  - `docs/*.md` updates (document-only phase; not permitted in this cycle).

## Assumptions

1. `_run_approval_gate()`'s body (delegating straight to
   `tool_approval.run_approval_checks(ctx, tool_calls)`, currently lines
   484-489) is already correct and requires no functional change — only
   its docstring is stale.
2. The companion changes in `repository_gateway.py` (removing the
   redundant `_gate_write()` approval call) and `tool_approval.py`
   (removing `skip_in_workflow_mode`) land together with this change,
   since the new regression test's "exactly once" assertion depends on
   `RepositoryGateway._gate_write()` no longer calling
   `run_approval_checks()` a second time.
3. `RepositoryGateway` can be constructed directly in a test with a
   mocked-out low-level executor (`AsyncMock`) and a permissive/mocked
   `cfg`, so it counts as "real (non-mocked-away)" for the purposes of
   proving the single-invocation invariant through both layers
   (`tool_runner` batch gate + `RepositoryGateway.execute()`).

## Design decisions

- Fix only the docstring, not the implementation: `_run_approval_gate()`
  already behaves correctly (single call to `run_approval_checks()` per
  batch); the defect being corrected is purely that its comment describes
  a workflow-mode skip feature that was never implemented for this
  function. Rewriting the docstring to state the actual, simpler
  contract avoids misleading future readers.
- Add the regression test at the `tool_runner.py` level (not in
  `test_repository_gateway.py` or `test_tool_approval_paths.py`) because
  it needs to exercise both layers together
  (`execute_all_tool_calls()` → `_run_approval_gate()` →
  `RepositoryGateway.execute()` → `_gate_write()`) to prove the
  end-to-end "exactly once" property that the source plan's fix depends on.

## Alternatives considered

- **Leave the docstring as-is and only rely on code comments elsewhere
  (e.g. on `RepositoryGateway`) to document the single-gate model**:
  rejected — `_run_approval_gate()` is the actual gate implementation and
  its own docstring is the most direct place a future reader would look;
  leaving it stale would actively contradict the corrected
  `repository_gateway.py` docstrings.
- **Add the regression test as a unit test with `RepositoryGateway`
  fully mocked out (`ctx.services_required.gateway = AsyncMock()`)**:
  rejected — this would only prove `run_approval_checks` is called once
  at the batch level, not that no second call happens deeper inside a
  real gateway's `_gate_write()`; using a real `RepositoryGateway`
  instance (with only its low-level `ToolExecutor` and the interactive
  prompt mocked) is necessary to pin the actual defect being fixed.

## Implementation

### Target file

`scripts/agent/tool_runner.py` (plus `tests/test_tool_runner.py`)

### Procedure

1. In `_run_approval_gate()` (currently lines 474-489), replace the
   docstring body:
   ```
   When the workflow definition sets require_approval=true, workflow-level approval
   gates are inserted between execute and verify stages. In this case, per-tool
   approval is skipped during the execute stage to avoid double-prompting.
   ```
   with text stating this is the single approval gate for the batch —
   approved calls proceed to execution (including through
   `RepositoryGateway`) without any further approval check performed
   anywhere downstream.
2. No change to the function body (`from agent.tool_approval import
   run_approval_checks` local import, the `await run_approval_checks(ctx,
   tool_calls)` call, and the `return result` line all stay as-is).
3. In `tests/test_tool_runner.py`, add a new test (e.g.
   `test_run_approval_checks_invoked_exactly_once_through_gateway`) that:
   - Constructs a real `RepositoryGateway` (from
     `agent.repository_gateway`) with an `AsyncMock` low-level
     `ToolExecutor` and a `cfg` permissive enough to classify the tool as
     write/risky (reusing patterns from `test_repository_gateway.py`'s
     `_make_gateway`/`_make_ctx` helpers or constructing inline).
   - Sets `ctx.services_required.gateway` to this real gateway instance
     (instead of the `None` default used by most existing
     `tool_runner.py` tests, which bypasses the gateway entirely).
   - Patches only the interactive layer — either
     `agent.tool_approval._prompt_user_approval` or
     `asyncio.to_thread` — with a `MagicMock`/`AsyncMock` that records
     call count and returns an approval (`"y"`/`True`).
   - Calls `execute_all_tool_calls(ctx, [write_call], 0)` with one
     risky/write tool call.
   - Asserts the patched interactive-approval mock was awaited/called
     exactly once (`assert_awaited_once()` /
     `assert_called_once()`), directly pinning the "no double prompt"
     invariant end-to-end.

### Method

Docstring-text replacement (no code logic change) plus one additive
integration-style test that wires a real `RepositoryGateway` into the
existing `tool_runner.py` test harness pattern.

### Details

- The new test must not mock away `RepositoryGateway.execute()` itself —
  doing so would make the assertion vacuous (it would only prove
  `_run_approval_gate()` calls `run_approval_checks()` once, not that
  `_gate_write()` doesn't call it again).
- If `check_preflight()`/policy classification would otherwise reject the
  chosen test tool/args, patch only `agent.repository_gateway.check_preflight`
  and `agent.repository_gateway.classify_operation_type` as needed (per
  existing `test_repository_gateway.py` patterns) — `classify_risk` is no
  longer called by `_gate_write()` after the companion change lands, so
  it does not need patching here.

## Compatibility considerations

- Docstring-only change to `_run_approval_gate()` — no signature or
  behavior change, no caller impact.
- The new test is additive; it does not modify or remove any existing
  test behavior in `test_tool_runner.py`.

## Security considerations

- The new regression test directly pins the security-relevant invariant
  that motivated the source plan: exactly one interactive approval
  prompt per risky tool call, in every mode. This test will fail loudly
  if a future change reintroduces a second approval call path (e.g. if
  `RepositoryGateway._gate_write()` regains an independent approval
  check), surfacing the regression at test time rather than as a
  silent UX defect (double-prompting) or a silent security gap (a path
  that skips approval entirely).

## Rollback considerations

- Revert is a docstring-text change plus removal of one additive test —
  no functional code, no data migration, no persisted state involved.
  Reverting does not affect any other test's behavior.

## Validation plan

- `mypy scripts/agent/` — no new errors (docstring-only change).
- `pytest tests/test_tool_runner.py -q` — all pass, including the new
  single-invocation regression test.
- Full-suite run (`pytest -q`) validated jointly with the
  `repository_gateway.py` and `tool_approval.py` docs — the new
  regression test's "exactly once" assertion is only meaningful once
  those two companion changes have also landed (otherwise
  `_gate_write()`'s still-present redundant call would make the count
  two, and the test should fail until all three changes are applied
  together).
- Manual smoke check (optional, per source plan): run the agent REPL,
  trigger one write tool call requiring approval, confirm exactly one
  interactive prompt appears.
