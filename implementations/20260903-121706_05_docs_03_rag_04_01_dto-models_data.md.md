definitions (`REQ-006`, `REQ-010`), correctly stating which fields may be `None` at the
DTO level and why (`REQ-009`) — the current "Required fields" bullet incorrectly
groups `title` with truly-required fields.

## Design decisions
- Distinguish two separate nullability boundaries, since they are not identical and
  conflating them is the root cause of the current inaccuracy: (1) DTO-level typing —
  what `ChunkDocument`'s dataclass fields accept in Python (`str` vs. `str | None`),
  and (2) JSON-input-level classification — what the parsing readers
  (`read_crawl_json()`/`read_chunk_json()`) accept from the raw JSON payload before
  constructing the DTO (documented in the canonical table, row 2 of this Plan). `title`
  is the clearest case: JSON-input-level it is Nullable (`_validate_nullable_str`), but
  DTO-level it is always `str`, because both readers do `title or ""` before
  constructing `ChunkDocument` — stating only one boundary would be incomplete.
- Keep this document's job strictly to the DTO-level boundary (its actual subject,
  `scripts/rag/models_data.py`) and link to row 2's document for the JSON-input-level
  table, rather than duplicating that table here — consistent with `REQ-011`'s
  single-canonical-source intent even though this row's Requirements do not cite
  `REQ-011` directly.

## Alternatives considered
- State only DTO-level types without mentioning the JSON-input-level distinction:
  rejected — this is what produced the current inaccurate "title: Required" bullet;
  omitting the distinction would leave the same ambiguity for `title` unresolved.
- Duplicate the full canonical table from row 2 here instead of linking: rejected —
  this document's own evidence (`models_data.py`) only supports DTO-level claims, not
  the JSON-parsing validator behavior documented in row 2's table.

```
### ChunkDocument — Chunk data passed between pipeline stages
DTO-level field types (`scripts/rag/models_data.py:31-47`):
- `url`, `title`, `lang`, `content`, `chunking_strategy`, `chunk_index`,
  `source_file`, `chunk_type`, `fetched_at` are non-`Optional` (`str`/`int`);
  `code_blocks` defaults to `[]` (never `None`).
- `etag`, `last_modified`, `normalized_content` are `str | None` (default `None`) —
  the only three fields that may be `None` at this DTO level. `etag`/`last_modified`
  represent optional upstream metadata not always available at crawl/chunk time;
  `normalized_content` is Japanese-only Sudachi normalization, always `None` for
  crawl artifacts, English chunks, and code chunks.
- `title` is always a `str` at this DTO level, defaulting to `""` — both
  `read_crawl_json()` and `read_chunk_json()` convert an explicit JSON `null` to `""`
  (`title or ""`) before constructing `ChunkDocument`. This differs from the
  JSON-input-level classification (see below), where `title` is Nullable.
- `chunking_strategy`/`source_file`/`chunk_type` are always non-`None` `str` here;
  crawl artifacts always set them to `"text"`/`""`/`""` respectively (crawl-stage
  values do not exist yet); chunk artifacts allow `source_file`/`chunk_type` to be
  explicit (possibly empty) strings and require `chunking_strategy` to be a
  non-empty string, with no code-enforced closed value set for either.

For the JSON-input-level Required/Nullable/Conditional classification (what the
parsing readers accept from the raw payload before DTO construction — not identical
to the DTO-level typing above), see the canonical table in
[03_rag_02_03_ingestion_pipeline-chunksplitter.md](03_rag_02_03_ingestion_pipeline-chunksplitter.md).
```
