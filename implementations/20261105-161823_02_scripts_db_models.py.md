## Goal

Remove the `write_smoke_test_ok` field from `SessionConsistencyReport` so the frozen
dataclass no longer advertises a write smoke test that this release unit deletes. The
read-only health flags (`session_diagnostics_readable`, `read_smoke_test_ok`) and the
failure flag (`diagnostic_errors`) remain.

## Scope
**Release unit**: session report contract removal

## Assumptions

- This field removal lands together with the three wiring edits that form one release
  unit (Phases 1-3): `scripts/db/session_consistency.py` (seq 01) stops setting the
  kwarg, `scripts/db/recovery_verification.py` (seq 03) stops triggering on it, and the
  two test modules (seq 04/05) stop asserting it. Until all four land, any remaining
  reference is a broken compile or a dataclass-construction error; keep them in one
  commit.
- Every in-repo consumer of `write_smoke_test_ok` is one of those files plus the two
  test modules (confirmed by `tools/scan_change_consumers.py --seed write_smoke_test_ok`
  and a repo-wide grep). No external/dashboard/config consumer exists. See UNK-01.
- `SessionConsistencyReport` is a `@dataclass(frozen=True)`; removing a field with a
  default (`bool | None = None`) does not change the position of any later field, so no
  positional construction breaks.

## Design decisions

- Delete the field rather than repurpose it: the field's sole meaning was "the write
  smoke test passed", and the issue mandates removing the write test. A leftover bool
  with no setter would be dead state.

## Alternatives considered

- Repurposing `write_smoke_test_ok` as a generic capability flag versus deleting it.
  Chose deletion: the plan's Implementation Intent is explicit that the existing
  read-only probes replace the write probe, and a repurposed flag would carry no
  source of truth.
