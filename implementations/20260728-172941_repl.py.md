## Goal

Restrict the subprocess-termination loop in `AgentREPL.run()` (`scripts/agent/repl.py`)
to the startup-failure (`except`) path only, so that a successful `StartupOrchestrator.run()`
no longer has its just-spawned MCP HTTP subprocesses terminated by the `finally` block,
while `self._close_resources()` continues to run on every path.

## Scope

**In-Scope:**
- `scripts/agent/repl.py` — `AgentREPL.run()`, lines 736-752:
  - Move the subprocess-termination loop (`all_procs = ...` / `for proc in all_procs: ...
    proc.terminate()`) from the unconditional `finally` block into the `except` block,
    before the existing `raise`.
  - Keep `await self._close_resources()` running unconditionally via `finally`.
  - Update the stale comment ("Terminate any subprocesses started during partial
    startup") to reflect that this code now only executes on the failure path.
- New/extended unit tests in `tests/test_repl.py`:
  - A test that stubs `StartupOrchestrator.run()` to succeed and return a list
    containing a live fake `Popen`-like object (`poll()` returns `None`), and asserts
    `.terminate()` is **not** called on it.
  - A companion test that stubs `StartupOrchestrator.run()` to raise after populating
    `startup._spawned_subprocesses` with a live fake process, and asserts `.terminate()`
    **is** called on it.
- Coordinating this change with `plans/20260727-142046_plan.md` (the sibling plan for
  `requires/20260727-132138_require.md`, which fixes `StartupOrchestrator` so
  `_spawned_subprocesses` is actually populated) so both land together.

**Out-of-Scope:**
- `scripts/agent/startup.py` — no code changes. `StartupOrchestrator.run()` /
  `_start_servers()` tracking fix is scoped entirely to
  `requires/20260727-132138_require.md` / `plans/20260727-142046_plan.md`.
- Any change to `lifecycle.shutdown_all()` or `_ServerLifecycleRouter` internals.
- Any change to `_close_resources()` (`scripts/agent/repl.py:390-458`) itself, or to the
  separate, already-correct call to it at the end of `_run_repl_loop()`
  (`scripts/agent/repl.py:646-649`), which performs the normal end-of-session
  `lifecycle.shutdown_all()` cleanup for subprocesses left running after a successful
  startup.
- Any change to signal-handling logic elsewhere in `run()` (lines 660-734).

## Assumptions

1. `scripts/agent/repl.py:736-752` currently reads (verified by direct read):
   ```python
   startup = StartupOrchestrator(self._ctx, self._view)
   _spawned_subprocesses: list[subprocess.Popen] = []
   try:
       self._cmds, self._orchestrator, _spawned_subprocesses = await startup.run()
   except Exception as e:
       self._view.write_fatal(f"Startup failed: {e}")
       raise
   finally:
       # Terminate any subprocesses started during partial startup
       all_procs = _spawned_subprocesses
       if hasattr(startup, "_spawned_subprocesses"):
           all_procs = list(all_procs) + list(startup._spawned_subprocesses)
       for proc in all_procs:
           if proc.poll() is None:
               proc.terminate()
       await self._close_resources()
   ```
   — the termination loop runs unconditionally regardless of `try` outcome, matching the
   requirement's description exactly.
2. This defect is currently masked and has no observable effect today, because
   `requires/20260727-132138_require.md` (already converted to
   `plans/20260727-142046_plan.md`) documents that `StartupOrchestrator.run()` always
   returns `[]` on the success path and never populates `self._spawned_subprocesses`
   — verified by reading `scripts/agent/startup.py:62-89` directly: line 89 is
   `return self._cmds, self._orchestrator, []  # empty list on success`, and
   `self._spawned_subprocesses` is initialized at line 66 but never appended to.
   Consequently `all_procs` in `repl.py` is always empty today, so today's tests pass
   whether or not the loop is gated.
3. **This plan MUST land together with (or immediately alongside)
   `plans/20260727-142046_plan.md`.** If `plans/20260727-142046_plan.md`'s fix (making
   `StartupOrchestrator.run()` return the real spawned-process list on success) is
   deployed without this plan's fix, `all_procs` becomes non-empty on successful
   startups too, and the current unconditional `finally` loop will call
   `proc.terminate()` on every just-spawned, healthy MCP HTTP subprocess immediately
   after a fully successful startup — breaking all HTTP-subprocess-mode MCP tools for
   the rest of the session. This is the exact regression both requirement documents
   warn about. The two implementation procedures must be sequenced so this plan's fix
   is never live in production without the sibling plan's fix also being live (this
   plan's fix landing first, alone, is safe; the sibling plan's fix landing first,
   alone, is not).
4. No other exit path between `startup.run()` and the end of `AgentREPL.run()` needs
   equivalent subprocess cleanup on the success path. Verified by reading
   `scripts/agent/repl.py:617-649` (`_run_repl_loop()`): its own `finally` block already
   calls `await self._close_resources()` at normal session end
   (`scripts/agent/repl.py:390-458`), which calls `await svc.lifecycle.shutdown_all()`
   (`scripts/agent/repl.py:445`) — the standard, intended mechanism for terminating
   long-lived MCP HTTP subprocesses when the session actually ends. Leaving
   successfully-spawned subprocesses running after `run()`'s startup phase is therefore
   the correct, intended behavior, not an oversight. This resolves Implementation
   Instruction #5 in the requirement.
5. Existing tests in `tests/test_repl.py` that patch `agent.startup.StartupOrchestrator`
   (lines 466-469, 492-495, 831-837) either return an explicit empty list (`[]`) as the
   third tuple element on the success path, or raise before any subprocess list is
   populated on the failure path; combined with `MagicMock.__iter__`'s default
   (`iter([])`) covering the unconfigured `startup._spawned_subprocesses` attribute
   access via `hasattr`/`list(...)`, none of these tests assert on or are sensitive to
   which branch (`except` vs. unconditional `finally`) runs the termination loop, so
   moving the loop into `except` does not break them.

## Design decisions

- Move the termination loop from `finally` into `except` before `raise`.
- Keep `_close_resources()` in `finally` — it runs unconditionally on all paths.
- Update the comment to clarify the loop only runs on failure.
- Add two new tests: one asserting `.terminate()` is NOT called on success, one asserting
  it IS called on failure.

## Alternatives considered

- Wrap the entire `try`/`except`/`finally` in an outer `if not startup_failed:` guard.
  Rejected — would require duplicating `_close_resources()` or adding a flag variable;
  moving the loop into `except` is simpler and more localized.
- Use a context manager to track startup success/failure. Rejected — over-engineered for
  a single conditional; a simple `except` placement achieves the same result with less
  complexity.

Exception path behavior:
- On success: `_close_resources()` runs in `finally`; subprocess-termination loop does NOT run.
- On failure: both the subprocess-termination loop AND `_close_resources()` run.
