## Goal

Add a precise, example-grounded docs/ content policy to `skills/DESIGN.md` Shared
Vocabulary: five categories of implementation-detail content `docs/*.md` documents
should not contain, and five categories of design-intent content they should
contain instead (REQ-001, REQ-002, REQ-003, REQ-004).

## Scope

- In-scope: adding two new named subsections to `skills/DESIGN.md` Shared
  Vocabulary, placed after "No implementation counts" and before "Out-of-scope
  paths".
- Out-of-scope: any other section of `skills/DESIGN.md`; any file under
  `docs/`; `rules/env.md`'s own content (referenced, not edited).

## Assumptions

- The two new subsections extend the existing "Avoid implementation-reference
  duplication" / "No source-code line numbers" / "No concrete configuration
  values" / "No implementation counts" group directly, since they are
  topically the same kind of principle (content policy for
  generated/reviewed documentation).
- A short, explicitly-labeled illustrative port number inside a worked example
  is not a violation of the new "literal port number" remove-category — this
  mirrors the existing "No concrete configuration values" principle's own
  worked-example exemption (`skills/DESIGN.md`, confirmed present) and
  requires no new carve-out text of its own.

## Design decisions

Two clearly-marked, symmetric five-item lists (remove-categories,
retain-categories) rather than a new, disconnected policy section — keeps the
"avoid implementation detail / retain design intent" framing consistent
across all of Shared Vocabulary's related rules. Each category gets a
one-sentence definition plus a short example.

## Alternatives considered

A single combined list without the remove/retain split — rejected: the Plan's
Acceptance criteria (AC-1, AC-2) require both category sets to be separately,
explicitly stated so a follow-up detection tool can target only the
remove-categories without also matching retain-category content.

### Method

Direct `Edit` insertion of two new `###`-level subsections between the
confirmed existing headings. No code changes; no test file.

### Details

Five remove-categories to define (source: Plan `plans/done/20260905-101850_plan.md`
Requirements REQ-001, each grounded in a concrete example from that Plan's
Problem section):
- Full file tree with per-file descriptions — example: an ASCII tree
  (`├─`, `│`, `└─`) with one-line descriptions per entry.
- Per-file one-line description embedded in a tree or table (same example
  class as above, called out separately since a table without a full tree can
  still exhibit it).
- Class/function/method signature-and-description index table — example: a
  `| Function | Signature | Description |` table.
- Implementation-location mapping statement ("this behavior is implemented in
  `{file}`") — example: an inline comment naming which `.py` performs an
  action.
- Literal port number in a heading, table, or prose — example: a section
  heading stating "(Port NNNN)".

Five retain-categories to define (source: Plan REQ-002):
- Component responsibility (Agent, MCP, RAG, EventBus, Shared/DB).
- State each component owns.
- Allowed dependency direction.
- Reason for process separation.
- Reason for per-process configuration separation.
- Design boundaries requiring joint consideration on change.

Cross-reference target for dependency-direction content: `rules/env.md`
Architecture (per REQ-004) — do not restate the layer/dependency content
itself here, only point to it.
