## Goal

Rework `scripts/agent/tool_scheduler.py::build_execution_groups()` from a
tool-*name*-keyed, single-scope-string grouping algorithm (with a silent all-`False`
default on a lookup miss) to a call-*id*-keyed algorithm that consumes
`ToolSpec.resource_scopes` (plural, multi-valued) and groups write-relevant calls via a
conflict graph — an edge between two calls when at least one is `is_write=True` and any
pair of their `resource_scopes` overlaps (exact match, or ancestor/descendant for
`"filesystem:"`-prefixed scopes) — taking connected components as the serialized
resource groups, and raising a dedicated exception when a call's id has no entry in the
passed-in metadata map instead of silently defaulting.

## Scope

In scope: `scripts/agent/tool_scheduler.py` only —
- `build_execution_groups()`'s signature (`tool_meta: dict[str, ToolSpec]` re-keyed from
  tool name to `call_id`) and its full body (current lines 70-189);
- a new dedicated exception (e.g. `MissingToolSpecError`) raised when a call's `call_id`
  has no entry in `tool_meta`;
- the connected-component conflict-graph construction replacing the current
  `resource_groups: dict[str, list[dict]]` exact-string-keyed grouping (current lines
  85, 97-98, 107-108);
- `_SerializationEvent.resource_scope: str` (current line 42) becoming
  plural/multi-valued to carry the new `resource_scopes` shape into serialization-event
  reporting, and its two construction sites (current lines 146-154 for the serial
  barrier, 156-167 for resource-scope conflicts) updated accordingly;
- the module docstring (current lines 1-23), updated only to reflect the new grouping
  mechanism's description — its stated distinction between the `is_side_effect()`
  batch-level downgrade and `ToolSpec.requires_serial`'s per-call DAG barrier is
  preserved unchanged, per the plan's explicit instruction to keep that distinction.

Out of scope: `scripts/agent/tool_runner.py`'s caller-side changes (separate target
file, separate doc in this set — that doc covers building the call-id-keyed dict passed
into this function), `scripts/shared/tool_spec.py`/`resource_scope.py`/
`runtime_tool_registry.py` (owned by other target files), and any MCP server `TOOL_LIST`
changes.

## Assumptions

- `ToolSpec.resource_scopes: tuple[str, ...]` (plural, replacing today's
  `resource_scope: str = ""`) is delivered by the sibling `scripts/shared/tool_spec.py`
  change in this same plan cycle; this doc's grouping algorithm consumes that field as
  already specified in the plan's Design section, not re-deriving its shape.
- Every scope string is kind-prefixed (e.g. `"filesystem:/a"`, `"git_repo:/a"`), per the
  plan's Design section — this doc's conflict predicate relies on that invariant to
  special-case only the `"filesystem:"` prefix for ancestor/descendant overlap and use
  plain string equality for every other kind, without itself needing to validate the
  invariant (validation is the new shared contract validator's job, a different target
  file).
- `scripts/shared/resource_scope.py`'s ancestor/descendant overlap predicate (per the
  plan's Scope: "an overlap/conflict predicate for ancestor/descendant filesystem
  paths") is available for `tool_scheduler.py` to import, OR this file implements its
  own local `_scopes_conflict()` mirroring that predicate — the plan's Implementation
  steps place `_scopes_conflict(a, b)` inside `scripts/shared/resource_scope.py` (Phase 1
  step 1), so this doc assumes `tool_scheduler.py` imports and reuses that shared
  predicate rather than re-implementing it, to avoid two divergent definitions of
  "conflict." (`scripts/agent/tool_scheduler.py` importing from `scripts/shared/` is
  layering-compatible per `.importlinter`'s `shared-is-leaf` contract, since `agent` may
  import `shared`, only the reverse is forbidden.)
- Read/read pairs are never edges in the conflict graph (per UNK-05's resolution) — this
  doc's algorithm does not need to build any graph structure for read-only calls at all;
  they can be filtered out before graph construction exactly as today's `parallel`
  bucket does.

## Design decisions

- **Conflict graph + connected components, not pairwise nested loops with early exit.**
  The plan's Design section specifies this exact algorithm shape: "builds a conflict
  graph over the write-relevant calls in a batch... and takes connected components as
  the serialized resource groups." Connected components (not, say, a union-find over all
  calls including reads) is the right granularity because a resource group must include
  every call transitively connected through overlapping scopes — e.g. call A conflicts
  with B (shared path), B conflicts with C (a different shared path with A but not B) —
  A, B, and C must all serialize together even though A and C's own scopes don't
  directly overlap. A simple pairwise check without transitive closure would
  under-serialize this case.
- **Only write-relevant calls enter the graph.** Per UNK-05's resolution, an edge exists
  only when *at least one* side of a pair `is_write=True`; a read-only call with no
  writer counterpart in its scope neighborhood never needs a graph node. This preserves
  today's `parallel` bucket for calls that have no write conflict, keeping the trailing
  parallel group's behavior recognizable to the ported tests.
  - Concretely: build the graph only over calls where `is_write=True` OR at least one
    other call's scope overlaps a read call's scope AND that other call is a writer —
    i.e. a read call *can* be pulled into a resource group if a concurrent write call in
    the same batch has an overlapping scope (this is required for the plan's stated
    "a directory read must conflict with a descendant-path write despite unequal scope
    strings" scenario in the Design section). The simplest implementation: build the
    candidate node set as "every call with at least one non-empty `resource_scopes`
    entry," then add an edge between any two candidate calls where at least one is
    `is_write=True` and their scopes overlap; a read call with resource_scopes that
    never overlaps any writer's scopes ends up as an isolated single-node component and
    is treated the same as `parallel` (single-call components with `is_write=False` fold
    into the trailing parallel group rather than becoming their own serialized group of
    one, to avoid needlessly serializing an isolated read).
- **`requires_serial` barrier and write-tools-without-scope write-first bucket stay
  unchanged.** Per the plan's Design section: "preserving the existing `requires_serial`
  global-barrier and write-tools-without-scope write-first buckets unchanged." These two
  buckets are evaluated *before* the conflict graph is built (same as today's ordering,
  where `serial_barrier`/`write_first` are separated out in the same `for tc in
  tool_calls` loop before `resource_groups` is populated) — only the middle
  "same-scope" bucket becomes the graph-based multi-scope logic; the loop's overall
  four-bucket shape (serial barrier, resource-scope conflict groups, write-first,
  parallel) is preserved.
- **Raise `MissingToolSpecError` (new, dedicated exception), not `KeyError`.** The plan's
  Implementation steps explicitly call for "a dedicated exception (e.g.
  `MissingToolSpecError`)... instead of the current silent all-`False` default." A
  dedicated exception (subclassing `Exception`, defined in this module, exported for
  `tool_runner.py`/tests to catch or assert on) gives callers and tests a specific,
  greppable failure mode distinct from any other `KeyError` that might occur elsewhere in
  the call stack (e.g. inside `tool_spec_for_call()`'s own `.get()` lookup on the tool
  *name*, which is a different failure — "tool name not registered" — from "this
  specific call_id's spec is missing from the map passed into this function," which
  should not normally happen if the caller built `tool_meta` correctly, but is checked
  defensively per the plan's "raise, don't default" acceptance criterion).
- **`_SerializationEvent.resource_scope` becomes multi-valued.** Since a resource group
  under the new algorithm can span calls whose `resource_scopes` tuples don't share a
  single common string (e.g. `move_file`'s two scopes each independently conflicting
  with different other calls in the same connected component), a single `resource_scope:
  str` field can no longer represent "the scope that triggered this event" precisely.
  Rename/retype to `resource_scopes: tuple[str, ...]` (or keep the field name
  `resource_scope` but change its type to a tuple/list — this doc recommends renaming to
  `resource_scopes` for consistency with `ToolSpec.resource_scopes`, since both describe
  the same underlying multi-scope concept) holding the union of scopes observed across
  the group's calls, for diagnostic/audit purposes (`ctx.stats.stat_serialization_events`
  in `tool_runner.py` consumes this field — see the paired `tool_runner.py` doc's
  Compatibility section).

## Alternatives considered

- Keeping single-scope-string exact-match dict-keying (`resource_groups: dict[str,
  list[dict]]`) and simply iterating each call's `resource_scopes` tuple to insert it
  into multiple dict buckets (one per scope string), then merging any buckets that share
  a call. Rejected: this is effectively a manual, less-general reimplementation of
  connected components (merging buckets that share a member *is* union-find), without
  the transitive-closure correctness the plan's Design section explicitly asks for
  (ancestor/descendant overlap can link two calls whose scope strings are never
  literally equal, so exact-match dict keys alone cannot express that relationship —
  reachability search dict keys would still be needed).
- Silently keeping the current default-`False`-on-miss behavior for backward
  compatibility with any external caller that doesn't yet pass complete `tool_meta`.
  Rejected: this is exactly the "unsafe silent default" the plan's Goal names as one of
  the four disagreeing metadata sources being eliminated, and the plan's Implementation
  steps explicitly require raising instead.

## Implementation

### Target file: `scripts/agent/tool_scheduler.py`

### Procedure

1. Update the module docstring (current lines 1-23): describe the new call-id keying and
   multi-scope conflict-graph grouping in the "Groups tool calls so that..." bullet list
   (current lines 5-9), while leaving the "NOTE — two distinct, intentionally-separate
   serialization mechanisms" section (current lines 11-22) conceptually unchanged — only
   update its cross-reference if the exact phrase "same non-empty resource_scope" (line
   7) needs updating to "overlapping resource_scopes" for accuracy; the distinction
   between `ToolSpec.requires_serial` and `is_side_effect()`'s batch-level downgrade
   itself is not touched.
2. Add `class MissingToolSpecError(Exception):` (or similar name) near the top of the
   module, after the existing dataclasses or before `build_execution_groups()`, with a
   docstring stating it is raised when a tool call's `call_id` has no corresponding entry
   in the `tool_meta` map passed to `build_execution_groups()`.
3. Change `build_execution_groups()`'s signature: `tool_meta: dict[str, ToolSpec]  #
   tool_name -> ToolSpec` (current line 72's comment) becomes `tool_meta: dict[str,
   ToolSpec]  # call_id -> ToolSpec`.
4. Replace the per-call lookup (current lines 89-91: `name = tc["function"]["name"]` /
   `meta = tool_meta.get(name)`) with a lookup by `tc["id"]`; on a miss, raise
   `MissingToolSpecError(f"No ToolSpec for call_id={tc['id']!r} (tool={tc['function']['name']!r})")`
   instead of falling through with `meta = None` (which today silently produces
   `scope=""`, `is_write=False` via the `if meta is not None else` fallbacks at current
   lines 95-96).
5. Replace the single-scope bucketing (current lines 97-98: `if scope and is_write:
   resource_groups.setdefault(scope, []).append(tc)`) with the conflict-graph
   construction described in Design: build nodes for every call with at least one
   non-empty `resource_scopes` entry, add edges per the overlap predicate (reusing
   `scripts/shared/resource_scope.py`'s conflict predicate, per Assumptions), compute
   connected components, and treat each multi-node component (or any single-node
   component where the sole call `is_write=True`) as one serialized resource group in
   place of today's `resource_groups.values()`.
6. Update the two `_SerializationEvent`-construction sites (current lines 143-154 for the
   serial barrier — unchanged in shape, just confirms the field rename doesn't affect it
   since `resource_scope=""`/unset for that event kind — and current lines 156-167 for
   resource-scope conflicts) to populate the renamed/retyped `resource_scopes` field with
   the union of scopes observed in that connected component.
7. Keep the `write_first`/`parallel` bucket logic (current lines 99-102, 109-112,
   122-123, 132-134) and the `concurrent_groups`/`ScheduledBatch` construction (current
   lines 114-141) structurally unchanged — only the source of `resource_groups`'s
   iteration (now connected components instead of a scope-string-keyed dict) changes; the
   loop that builds `groups`/`cgr` from `resource_groups.values()` continues to work
   unchanged as long as the connected-component step still produces an iterable of
   `list[dict]` groups in the same shape.

  the return value, only how they build the `tool_meta` argument passed in (covered by
  the paired `tool_runner.py` doc).
- `_SerializationEvent.resource_scope`'s rename/retype to `resource_scopes` is a breaking

- Any external caller passing a name-keyed `tool_meta` dict (built via the now-deleted

  direct consumers," not incrementally.

## Security considerations

- Raising `MissingToolSpecError` instead of silently defaulting to an all-`False`
  synthetic spec closes a fail-open gap: today, a scheduling bug that produces a
  name-mismatch (e.g. a typo, or a tool renamed in one place but not another) silently
  treats the affected call as read-only/unscoped, potentially letting a write-tool call
  run concurrently with conflicting writes. The new behavior fails the batch loudly
  instead, which is the more conservative, security-relevant direction the plan's Goal
  requires ("fail-closed... metadata flow").
- The ancestor/descendant filesystem-scope conflict predicate is itself a
  security-relevant boundary: an under-broad predicate (missing a real overlap) could
  let two conflicting filesystem writes run concurrently; an over-broad one only costs
  performance (unnecessary serialization). Per the plan's Risk section, this asymmetry
  argues for erring toward over-serialization when the predicate's correctness is in
  doubt — this doc's Design section notes the predicate itself is owned by
  `scripts/shared/resource_scope.py` (a different target file), not reimplemented here.

## Rollback considerations

- This file's changes are tightly coupled to `scripts/agent/tool_runner.py`'s caller-side
  changes (the `tool_meta` dict's key space and the `ToolSpec.resource_scopes` field
  shape) — reverting this file's rework without reverting `tool_runner.py`'s matching
  change would break `_execute_with_dag()` immediately (name-keyed calls into a
  call-id-keyed function, or vice versa). The two files must be reverted together, as
  noted symmetrically in the paired `tool_runner.py` doc.
- No persisted state or schema change is introduced; rollback is a pure source-code
  revert with no data-migration concern.
- Given the plan's Risk section explicitly flags this rework as "genuine algorithmic
  redesign... raising correctness risk," a staged rollback path (e.g. feature-flagging
  the new grouping behind a config toggle) was considered but is not specified by the
  plan and is not introduced here — the plan's stated mitigation is pre-merge regression
  test coverage (porting every existing scenario), not a runtime toggle; this doc follows
  that mitigation strategy rather than inventing a new one.
