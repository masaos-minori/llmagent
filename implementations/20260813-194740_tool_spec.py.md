## Goal

Replace `ToolSpec`'s singular `resource_scope: str = ""` field with a plural
`resource_scopes: tuple[str, ...] = ()` field, so a single approved tool call can carry
multiple independently-conflicting resource scopes (e.g. `move_file`'s source and
destination), which the (separately-updated) scheduler's conflict-graph grouping needs.

## Scope

In scope: `scripts/shared/tool_spec.py` only — the `ToolSpec` dataclass field and its
docstring. Out of scope: `RuntimeTool.resource_scope_kind`/`resource_scope_keys`
(separate target file `runtime_tool.py`), `resolve_resource_scopes()` (separate target
file `resource_scope.py`), and `runtime_tool_registry.py::_build_tool_spec()`'s
population of the new field (separate target file `runtime_tool_registry.py`, though its
doc's output must match this field's exact name/type).

## Assumptions

- `resource_scopes=()` (empty tuple) is the correct default, mirroring the existing
  `resource_scope: str = ""` empty-string default's "no scope" meaning — an empty tuple
  is the natural plural analog of an empty string here.
- 7 importers reference `shared.tool_spec` repo-wide (per the plan's Affected-areas
  table); this doc only covers the definition site.
- No other `ToolSpec` field changes — `call_id`, `name`, `args`, `requires_serial`,
  `is_write` are unaffected by this plan for this file.

## Design decisions

- **Tuple, not list.** Consistent with `RuntimeTool.capabilities: tuple[str, ...]` and
  the new `RuntimeTool.resource_scope_keys: tuple[str, ...]` (per the companion
  `runtime_tool.py` doc) — keeps `ToolSpec` (also `@dataclass(frozen=True)`) fully
  hashable/immutable, and keeps the plural-scope shape consistent across both dataclasses
  in this data-model layer.
- **Field renamed to plural (`resource_scopes`), not just retyped.** Signals at the call
  site (`spec.resource_scopes`) that the value can hold more than one entry, avoiding a
  silent behavior change where old code iterating `spec.resource_scope` as if it were
  still a single string would now iterate characters of... actually this would be a hard
  `AttributeError` either way since the type changes; the rename makes the break obvious
  at read-time rather than producing a type mismatch under the old name.
- **No default-factory needed.** Unlike `args: dict[str, Any] = field(default_factory=dict)`
  (mutable default, needs `field(default_factory=...)`), `()` is an immutable empty tuple
  literal and safe to use directly as a dataclass field default without `field(...)`.

## Alternatives considered

Keeping the field name `resource_scope` but changing its type to `tuple[str, ...]`
(retype without rename). Rejected: the plan's Affected-areas table explicitly specifies
the plural name `resource_scopes`, and keeping the singular name while holding a tuple
would read confusingly at every call site (`spec.resource_scope` reading like a single
value when it can hold several).

## Implementation

### Target file: `scripts/shared/tool_spec.py`

### Procedure

1. In the `ToolSpec` dataclass (lines 13–31), replace the field
   `resource_scope: str = ""` (currently line 29) with
   `resource_scopes: tuple[str, ...] = ()`, keeping its current position between `args`
   (line 28) and `requires_serial` (line 30).
2. Update the class docstring's `Fields:` list (currently line 21:
   `resource_scope: Resource path/branch string for conflict detection ("" if none)`) to:
   `resource_scopes: Tuple of kind-prefixed resource-scope strings for conflict
   detection (empty tuple if none; see shared.resource_scope for the string shape).`

### Method

Direct in-place field rename via `Edit` on the two lines identified above (field
declaration + docstring line); this file has no other references to `resource_scope` to
update (it is an 18-line dataclass module with no helper functions).

### Details

- Current field: `resource_scope: str = ""` at line 29, immediately following
  `args: dict[str, Any] = field(default_factory=dict)` (line 28) and immediately
  preceding `requires_serial: bool = False` (line 30). Field order is preserved in the
  replacement.
- The module has no `field(default_factory=...)` requirement for the new field since
  `tuple[str, ...] = ()` is an immutable literal default, safe directly on a
  `@dataclass(frozen=True)` (confirmed: the class decorator at line 13 is
  `@dataclass(frozen=True)`, same as `RuntimeTool`).
- No import changes needed — `from dataclasses import dataclass, field` (line 9) and
  `from typing import Any` (line 10) already cover everything the new field needs (no
  new type needs importing since `tuple[str, ...]` uses only builtins under
  `from __future__ import annotations`, already present at line 7).

## Compatibility considerations

Same atomic-rename requirement as `runtime_tool.py`: no back-compat alias is introduced.
Any code still constructing `ToolSpec(resource_scope=...)` or reading `.resource_scope`
breaks at that call site; per the plan's Risk mitigation this must land in the same
commit as `runtime_tool_registry.py::_build_tool_spec()`'s update (which is the sole
in-scope producer of `ToolSpec` instances with a populated scope field).
