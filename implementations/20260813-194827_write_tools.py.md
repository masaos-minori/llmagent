## Goal

Add the schema-2.0 per-tool metadata contract to all 4 tool entries in
`scripts/mcp_servers/file/write_tools.py`'s `TOOL_LIST` (`write_file`, `edit_file`,
`create_directory`, `move_file`), marking each `is_write=True`,
`requires_serial=False` (default), `resource_scope_kind="filesystem"`, and giving
`move_file` its distinct dual-key `resource_scope_keys=["source", "destination"]` per
the plan.

## Scope

In scope: the 4 dict literals inside `TOOL_LIST` (lines 11-118) —
`write_file` (13-35), `edit_file` (37-73), `create_directory` (75-93),
`move_file` (95-117). Out of scope: the `dry_run` handling logic elsewhere in the
file-write-mcp server implementation (not in this schema module), and any change to
`inputSchema` property definitions themselves (the 4 new fields are sibling keys to
`inputSchema`, not nested inside it).

## Assumptions

- None of the 4 entries currently declare any of the 4 new fields (confirmed: `rg
  "is_write|requires_serial|resource_scope"` on this file returns no hits) — fully
  missing on all 4, not a partial-backfill case.
- The plan's per-server table states only `move_file` needs the dual
  `["source","destination"]` key list; the other 3 single-path write tools
  (`write_file`, `edit_file`, `create_directory`) each use `resource_scope_keys=["path"]`,
  consistent with their single `path` property (confirmed present in each entry's
  `inputSchema["properties"]`, e.g. line 18-21 for `write_file`).
- `requires_serial` is not specified per-tool in the plan's Affected-areas row for this
  file (only `is_write` and the scope fields are called out); this document assumes
  `requires_serial=False` for all 4 entries, consistent with the plan's Design section
  stating the new conflict-graph groups writes into serialized components based on
  *scope overlap*, not a blanket per-tool serial flag — `requires_serial=True` is
  reserved (per the plan's shell_tools.py row, out of scope here) for tools needing a
  global barrier regardless of scope, which none of these 4 filesystem writes require.

## Design decisions

- `write_file`, `edit_file`, `create_directory`: `is_write=True`,
  `requires_serial=False`, `resource_scope_kind="filesystem"`,
  `resource_scope_keys=["path"]`.
- `move_file`: `is_write=True`, `requires_serial=False`,
  `resource_scope_kind="filesystem"`, `resource_scope_keys=["source", "destination"]`
  — per the plan's explicit instruction, since `move_file` mutates two distinct
  filesystem locations and both must independently participate in scope-conflict
  detection (per the plan's Design section on `resolve_resource_scopes()` producing
  multiple scopes per call).
- Field ordering: insert after `config_dependent` in each entry, matching the
  convention used for `read_tools.py`.

## Alternatives considered

Considered giving `move_file` a single combined scope key (e.g.
`resource_scope_keys=["source"]` only, treating destination as incidental) — rejected
because the plan's Design section explicitly requires both `source` and `destination`
to independently conflict with unrelated concurrent calls (e.g. a `write_file` on the
destination path must serialize against an in-flight `move_file` targeting that same
destination), which a single-key scope would miss.

## Implementation

### Target file: `scripts/mcp_servers/file/write_tools.py`

### Procedure

1. In the `write_file` entry (lines 13-35), add 4 keys after
   `"config_dependent": False,` (line 34): `"is_write": True,`,
   `"requires_serial": False,`, `"resource_scope_kind": "filesystem",`,

Direct literal-dict edits — one small insertion per entry, no new imports, no helper
functions needed (module has no `_input_schema()` helper; this module builds
`inputSchema` inline as raw dicts already).

## Compatibility considerations

Additive-only; existing consumers (`build_tools_response()`, dispatch logic in the
file-write-mcp server, `tests/mcp_servers/test_tool_schema.py`'s parametrized checks
over this module) see 4 extra keys per entry and no removed/renamed key. No behavior
change to the actual write/edit/move/create operations themselves — this file only
holds tool *schema* dicts, not implementation logic.

## Security considerations

`is_write=True` on all 4 entries correctly documents that these tools mutate the
filesystem — this is metadata consumed downstream by the scheduler/discovery
validator, not a new enforcement point in this file itself. No new security surface is
introduced here; existing path-safety checks in the write-tool implementation
(elsewhere in the file-write-mcp server) are unaffected. `move_file`'s dual scope keys
make the future scheduler correctly serialize concurrent calls touching either its
source or destination path, which is a *safety improvement* over today's single-scope
model once wired up by the (separately-owned) scheduler changes — but that wiring is
out of scope for this document.

## Rollback considerations

Trivial: revert the 4 additive blocks (one per entry). No other file in this specific
document's scope depends on these fields yet.
