## Goal

In `scripts/db/schema_sql.py`: remove the `DEFAULT` clause from four columns in
the `rag.sqlite` DDL template — `documents.fetched_at`, `documents.chunking_strategy`,
`chunks.chunk_type`, and `chunks.source_file` — while keeping each column's
existing `NOT NULL` constraint (and, where present, `CHECK` constraint) intact.
This removes the silent-substitution path that let an INSERT omitting one of
these four columns succeed with a database-supplied default instead of failing,
supporting the plan's atomicity goal ("either a complete document and all its
chunks are committed, or none of it is, with no silently-substituted default").

## Scope

- In scope: the `documents` and `chunks` table definitions inside
  `_RAG_SCHEMA_TEMPLATE` (consumed by `build_rag_schema_sql(dims)`) — only the
  `DEFAULT` clause on `fetched_at`, `chunking_strategy`, `chunk_type`, and
  `source_file`. `documents.etag`, `documents.last_modified`, and
  `chunks.normalized_content` are explicitly unchanged (they remain nullable
  with no `DEFAULT`).
- Out of scope: all other tables in this file (`sessions`, `messages`,
  `memories`, `memory_links`, `sync_log`, `tasks`, `task_stages`, `task_metrics`,
  `task_artifacts`, `task_events`, `schema_migrations`, the eventbus `events`
  table) — none of their `DEFAULT` clauses are named by this plan; confirmed by
  direct read that the plan's Scope section names exactly these four columns
  and no others in this file.
- Out of scope: `CHECK`/`NOT NULL` constraints themselves — confirmed present
  today (`chunk_index >= 0`, `chunk_type IN ('text', 'code')`,
  `length(content) > 0`, `lang IN ('ja', 'en')`) and unaffected by this change
  per the plan's Assumptions.
- Out of scope: `scripts/db/store_impl.py`'s `doc_upsert()` and
  `scripts/rag/ingestion/ingester.py`'s `ingest_url_group()` — separate target
  files (the latter covered by the sibling document
  `implementations/20260823-201317_ingester.py.md` in this batch; the former is
  a distinct target file not assigned to this batch).

## Assumptions

- Confirmed by direct read: today's DDL text is
  `fetched_at TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%SZ', 'now'))`,
  `chunking_strategy TEXT NOT NULL DEFAULT 'text'`,
  `chunk_type TEXT NOT NULL DEFAULT 'text'`, and
  `source_file TEXT NOT NULL DEFAULT ''` — all four already carry `NOT NULL`
  today, so removing only the `DEFAULT` clause (leaving `NOT NULL`) is a
  minimal, additive-strictness edit with no other constraint text to touch.
- Confirmed by direct read of `scripts/rag/ingestion/ingester.py`: its
  `_insert_document()` has a two-branch fallback — when `fetched_at is None` it
  falls into a `cursor2` branch that omits `fetched_at` from the INSERT column
  list entirely, currently relying on this column's `DEFAULT`. That branch is
  scheduled for removal by the dependency plan `plans/done/20260820-095054_plan.md`
  (fetched_at made mandatory end-to-end). **Re-verify before implementing**:
  run `rg -n "cursor2" scripts/rag/ingestion/ingester.py` — if the `cursor2`
  branch still exists when this document is executed, removing
  `fetched_at`'s `DEFAULT` here will make that branch raise
  `sqlite3.IntegrityError` on any call path that reaches it with `fetched_at is
  None`, which is exactly the sequencing hazard the source plan's Assumptions
  section warns about ("this plan's ingester.py/schema_sql.py changes must land
  after" the two dependency plans).
- Confirmed by direct read: `_insert_chunks_batch()` and `_insert_document()`
  in `ingester.py` already include `chunk_type`/`source_file` and
  `chunking_strategy` explicitly in every INSERT column list on their normal
  (non-fallback) path — so for those two columns, on the paths already in
  regular use, removing the `DEFAULT` is not expected to change today's
  observed behavior; the fallback `cursor2` branch above is the one path where
  `fetched_at`'s `DEFAULT` is presently load-bearing.
- Per the source plan's Scope section, `scripts/db/store_impl.py`'s
  `doc_upsert()` INSERT branch currently omits `fetched_at`/`chunking_strategy`
  from its column list entirely, relying on these two `DEFAULT` clauses. That
  file is a separate target file (not in this batch's assignment) whose own
  procedure must add explicit values before this schema change lands in the
  same deployment, per the plan's Implementation steps (Phase 2 updates
  `store_impl.py` after Phase 1 removes the schema defaults). The plan notes
  `doc_upsert()` has zero production callers today (only exercised by
  `tests/db/test_db_store_impl.py`), so the practical exposure during any
  Phase 1→2 gap is test-only, not production.

## Design decisions

- Edit only the `DEFAULT` clause text of the four named columns in place;
  do not restructure the `CREATE TABLE` statements, reorder columns, or touch
  any `CHECK`/`UNIQUE`/`REFERENCES` clause — the plan explicitly scopes this
  file's change to "remove `DEFAULT` from ... keep all four `NOT NULL`."
- No schema-version bump or migration path is added for this change (per the
  plan's Design step 7): `rag.sqlite` uses `CREATE TABLE IF NOT EXISTS` DDL, so
  an already-existing database file will not pick up the stricter constraint
  without deleting the file and re-running `create_rag_schema()`. This is a
  recreate-not-migrate change, consistent with how this schema is already
  managed.

## Alternatives considered

- Replacing the removed `DEFAULT` with an application-level constant passed
  explicitly by every caller while leaving the DDL `DEFAULT` in place as a
  redundant safety net — rejected: a surviving DDL `DEFAULT` would keep the
  exact silent-substitution path this plan exists to close; the plan's Goal is
  explicit about eliminating "silently-substituted database default," not just
  making callers supply a value optionally.
- Adding a new `CHECK` constraint instead of removing `DEFAULT` (e.g.
  `CHECK (chunk_type <> '')`) — rejected: `NOT NULL` plus removing `DEFAULT`
  already forces every INSERT to supply a non-null value explicitly, which is
  the exact and only behavior the plan specifies; an additional `CHECK` is not
  requested and would go beyond this plan's stated scope.

   `source_file TEXT NOT NULL DEFAULT ''` to `source_file TEXT NOT NULL`.

   `chunks.normalized_content` untouched (no `DEFAULT` today, remain nullable).

   (the plan's own Phase 5 verification command, scoped to this file) and
   confirm zero matches remain.

### Method

Pure text edit to a SQL DDL string template — four `DEFAULT` clauses deleted,
nothing else in the template restructured. No Python logic in this module
(`build_rag_schema_sql`, `build_session_schema_sql`, `build_workflow_schema_sql`,
`build_eventbus_schema_sql`, `apply_workflow_migrations`) changes shape or
signature.

### Details

- `_RAG_SCHEMA_TEMPLATE` is a module-level string substituted with the `DIMS`
  placeholder by `build_rag_schema_sql(dims)`; this change only edits the
  literal SQL text, not the substitution mechanism.
- Confirm after editing that the `documents` table's final column
  (`chunking_strategy`) still has no trailing comma before the closing `);`
  and that the `chunks` table's `UNIQUE (doc_id, chunk_index)` and its three
  `CHECK (...)` lines are untouched and still comma-separated correctly from
  the edited `chunk_type`/`source_file` lines above them.

## Compatibility considerations

- `create_schema.py` and the plan's Affected areas table cite 6 other call
  sites importing `build_rag_schema_sql()`/`schema_sql.py` — none of them are
  expected to need code changes from this edit alone, since `NOT NULL` was
  already present; only INSERT paths that previously omitted one of the four
  columns (the `ingester.py` `cursor2` fallback and `store_impl.py`'s
  `doc_upsert()`) are affected, and both are covered by their own dependency
  plan / sibling target-file procedure, not by this file's edit itself.
- Because the DDL uses `CREATE TABLE IF NOT EXISTS`, any already-existing
  `rag.sqlite` file in a dev/staging/production environment will silently keep
  its old, `DEFAULT`-bearing schema until that file is deleted and
  `create_rag_schema()` is re-run — this is a deployment-time action item, not
  a code compatibility issue, per the plan's Design step 7 and Implementation
  Phase 5.

## Security considerations

N/A: this is a stricter-constraint DDL change on a local SQLite schema with no
new external input surface, no new query construction, and no change to how
untrusted input reaches these columns — it only removes a database-level
fallback value, tightening rather than loosening data integrity.

## Rollback considerations

- This change is Phase 1 in the source plan's Implementation steps and is
  explicitly called "independently revertable" there — it can be reverted as
  its own commit (re-adding the four `DEFAULT` clauses) without needing to
  revert `store_impl.py`'s Phase 2 changes or `ingester.py`'s Phase 3/4 changes
  in the same action, though a revert here should be paired with confirming
  whether `store_impl.py`'s `doc_upsert()` (once updated in Phase 2 to supply
  explicit values) still functions correctly against the reverted, looser
  schema — it would, since supplying an explicit value is always valid whether
  or not a `DEFAULT` also exists.
- If reverted, any `rag.sqlite` file created under the stricter schema in the
  interim keeps its stricter constraints until recreated; reverting this file
  alone does not retroactively loosen an already-created database file.
