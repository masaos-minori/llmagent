## Goal

Replace `build_execution_groups()` in `scripts/agent/tool_scheduler.py` (current lines
70-189) — the four-bucket `serial_barrier`/`resource_groups`/`write_first`/`parallel`
grouping keyed by tool *name* — with a single phase-building DAG planner keyed by
`call_id`, that treats `requires_serial` as an in-place barrier (not a leading bucket),

`global:write` scope, and returns one `ExecutionPlan` (bound `ScheduledGroup`/
`ScheduledBatch` dataclasses plus public `SerializationEvent`s) instead of today's
`tuple[list[list[dict]], _GroupMetadata]`.

## Design decisions

- **In-place barrier, not a leading bucket, for `requires_serial`.** Today's
  `serial_barrier` list (current lines 84, 92-94, 105-106, 120-121, 143-154) is collected
  first and always emitted before every other group, which silently reorders a serial
  tool that appeared *after* other calls in `tool_calls`. The new algorithm walks calls
  in original order and closes/reopens `current_phase` around each serial call in place,
  per the plan's phase-building algorithm step 2.
- **`global:write` scope replaces the no-scope write-first bucket.** Today's `write_first`
  bucket (current lines 86, 99-100, 109-112, 122-123, 132-134, 169-179) treats every
  scopeless write tool as belonging to one shared bucket by construction, without ever
  checking whether two scopeless writes actually conflict with each other or with a
  scoped write — this is one of the plan's cited defects ("scope-less writes racing each
  other"). Assigning `("global:write",)` as the resolved scope (per Issue 01's
  `resolve_resource_scopes()` contract, consumed not reimplemented here) lets the same
  conflict-graph machinery serialize scopeless writes against each other and against any
  other write, instead of a hand-rolled separate bucket.
- **Union-find over conflict pairs, one sequential `ScheduledGroup` per connected
  component with `len > 1`.** Per the plan's Design section point 5: within each phase,
  build a conflict graph where an edge exists when either side `is_write=True` and their
  `resource_scopes` overlap; read/read pairs never conflict. This is the same
  transitive-closure requirement noted by the sibling `tool_scheduler.py` doc for Issue
  01 (a chain A-B-C must all serialize together even if A and C don't directly overlap).
- **Raise on a missing `call_id`, never synthesize a default `ToolSpec`.** Replaces the
  current `meta = tool_meta.get(name)` / `if meta is not None else` fallback pattern
  (current lines 91, 95-96) that silently treats an unmatched call as read-only/unscoped
  — exactly the "fail-open" gap the plan's Goal names.
- **`force_serial` replaces branch selection at the call site, it does not live inside
  the old four-bucket logic.** When `force_serial=True`, skip phase-building/conflict-
  graph construction entirely and emit one single-call sequential phase per call in
  original order, reason `forced_serial` — this is what lets
  `ctx.cfg.tool.serial_tool_calls` become a planner *input* instead of selecting between
  two whole execution engines in `tool_runner.py`.

## Alternatives considered

- Keeping `_GroupMetadata`/`ScheduledBatch`'s current `list`-based, two-return-value
  shape (`(groups, metadata)`) and only patching the four-bucket logic in place.
  Rejected: the plan explicitly names this shape as one of the eight defects ("a
  metadata-vs-return-value split the runner only half-uses... desyncable parallel
  arrays") — `groups: list[list[dict]]` and `metadata.concurrent_groups` can drift apart
  since nothing binds them together; the new bound dataclasses (`ScheduledGroup`,
  `ExecutionPlan`) make that drift structurally impossible.
- Manual pairwise dict-keyed bucketing (iterate each call's scopes into per-scope
  buckets, then merge buckets that share a member) instead of an explicit conflict graph
  with connected components. Rejected for the same reason the sibling Issue-01 doc
  rejects it: merging buckets that share a member *is* union-find, done manually and
  without the ancestor/descendant transitive-closure correctness an explicit graph gives
  for free.

     `is_write=True` and scopes overlap via the shared predicate; read/read never
     conflicts), compute connected components via union-find, emit one sequential
     `ScheduledGroup` per component with `len > 1` and one concurrent `ScheduledGroup`

## Security considerations

- Raising on a missing `call_id` instead of silently defaulting to an unscoped/read-only
  `ToolSpec` closes a fail-open gap: a scheduling bug (mismatched id, a tool renamed in
  one place but not another) previously let the affected call run concurrently with
  conflicting writes undetected; the new behavior fails the batch loudly, matching the
  plan's stated "fail-closed... metadata flow" direction.
- The scope-overlap conflict predicate is a security-relevant boundary — an under-broad
  predicate risks two conflicting filesystem writes running concurrently; per the
  sibling Issue-01 doc's Security considerations, this doc errs toward the shared,
  single-source predicate in `scripts/shared/resource_scope.py` rather than a local
  reimplementation, to avoid two divergent definitions of "conflict."
