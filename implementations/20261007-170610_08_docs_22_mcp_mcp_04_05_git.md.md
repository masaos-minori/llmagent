### Method

#### Step 1 — "Command-specific guard status" (line 117)

Replace the ref-validation sentence. Current text describes
`_validate_ref()` rejecting only a leading `-` for `git_log`/`git_diff`/`git_show`/
`git_checkout`/`git_pull`/`git_push` (`branch` and `remote`), and states remote names
are not matched against a pattern. Rewrite to:

- Write tools (`git_checkout`, `git_pull`, `git_push`) validate `branch`/`remote`
  against an allow-list equivalent to `git check-ref-format --branch`: reject `+`, `:`,
  `^`, `~`, `?`, `*`, `[`, backslash, `..`, `@{`, whitespace, control characters,
  values starting with `refs/`, and `HEAD`; `remote` against a conservative
  `[A-Za-z0-9._-]+` pattern.
- Read tools (`git_log` `branch`, `git_diff` `commit`, `git_show` `ref`) retain the
  option-injection-only check; the allow-list does not apply to them (so
  `git_show`'s default `ref="HEAD"` and tag refs are not regressed).

Keep the statement that `git_status`/`git_branch`/`git_add`/`git_commit` take no ref
argument.

#### Step 2 — `git_push` Current bullet (line 131)

Replace "`_is_safe_ref()`" / "option-injection-shaped `branch`/`remote` values are
already rejected" with the allow-list: `branch`/`remote` are rejected by the
`git check-ref-format --branch`-equivalent allow-list before any GitPython call. Keep
the Force-Push-not-reachable-via-`--force` observation (no `force` field exists).

#### Step 3 — "Protected branch authority" (lines 136-141)

Rewrite the two-bullet "enforced in two places with different subjects" description to
the destination-based model:

- One authoritative Stage 3 check (`WriteProtectionPipeline.verify_authorization()`,
  now taking `tool_name`/`requested_branch`/`protected_branches`/`active_ref`) compares
  the operation **destination** — `req.branch` for `git_pull`/`git_push`, the switch
  target for `git_checkout`, current HEAD for `git_add`/`git_commit` — against
  `GitConfig.protected_branches`, normalized case-insensitively. It is the single
  authoritative check: a protected destination is rejected even if the pre-pipeline
  check is bypassed.
- The pre-pipeline `GitService._validate_protected()` is retained as an early-rejection
  layer (defense in depth), comparing the same destination.
- Consequence: `git_checkout` away from a protected branch (target = unprotected) is
  allowed; only checkout *into* a protected branch is rejected. Report the actually
  rejected branch name (no longer hard-coded `'main'`).
- Note `git_pull`/`git_push` now require a non-empty `branch` (REQ-004), so the old
  "empty branch rejected" contradiction is gone.

Retain the final paragraph distinguishing git-mcp `protected_branches` from GitHub
MCP's `protected_branches`.

#### Step 4 — "Structured rejection codes" (line 149)

Update the protected-branch and option-injection entries:

- Option-injection: `_validate_ref()`/`_is_safe_ref()` → the write-tool allow-list for
  `branch`/`remote` (read tools retain the option-injection check).
- Protected-branch: report the actually-rejected branch name instead of a hard-coded
  `'main'`.
