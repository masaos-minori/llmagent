## Goal

Give `RecoveryResult.action` a distinct value for the wrong-domain rejection case so
callers can tell it apart from `no_backup`/`bad_backup` (REQ-002).

## Scope

`RecoveryResult`'s docstring/comment (the field itself is already a plain `str`, so no
type change is needed). Out of scope: any other field on `RecoveryResult`, and any
other dataclass in this file.

## Assumptions

`action: str` (confirmed via `grep -n "class RecoveryResult" -A 6
scripts/db/models.py`, showing `action: str` with no enum/Literal constraint) — this
is an open string field, not a closed enum, so adding a new value used elsewhere
(`scripts/db/recovery.py`) requires no change to this field's type or validation.

## Design decisions

Since `action` is already an untyped `str` field, the only design decision is whether
to leave it fully open (current behavior, no change needed to the field declaration
itself) or introduce a `Literal`/enum of allowed values. Per the Plan's Scope
("Reason for Modification: Add new `RecoveryResult.action` value for wrong-domain
scenario"), this document's job is to make the new value's meaning discoverable —
add it to the class docstring's enumeration of known action values, without narrowing
the field's type (narrowing to `Literal[...]` would be a larger, unrequested type
change affecting every existing caller that constructs a `RecoveryResult`).

## Alternatives considered

- Converting `action` to a `Literal[...]` or `StrEnum` — rejected: out of scope per
  the Plan (`Reason for change`/`Risks` sections discuss the new value as an additive
  string, and note "no change to `os.replace()`... beyond the pre-check", with no
  mention of a type-level enum migration); the Plan's own Risk mitigation states
  "since `action` is a string field" as the reason existing callers are safe, implying
  the string-field design is intentionally preserved, not migrated.
