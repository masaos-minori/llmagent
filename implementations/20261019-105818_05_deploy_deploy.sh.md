## Goal
Make the deploy check binary freshness, use the staged swap when binaries come from a separate build directory, and record the deployed revision (`REQ-005`).

## Scope
- The binary placement block and the end of this script; the `scripts/`, `config/`, `tests/`, and `docs/` synchronization stays as it is.

## Assumptions
- `tools/manage_binaries.py` exists and is run with `python3` from the repository checkout (this script already runs from the repository root).
- `DEPLOY_STRICT_BINARIES` (new) is unset by default, so existing deploys keep working.

## Design decisions
- Integrity failures stop the deploy (`set -e` with the tool's exit code); stale or unknown binaries only warn unless `DEPLOY_STRICT_BINARIES=1` (new).
- Keep the existing per-binary existence check as the first guard.

## Alternatives considered
Failing on stale binaries by default was rejected: existing production binaries have no build info yet (Plan UNK-03).

## Implementation
### Target file
`deploy/deploy.sh`

### Procedure
1. After the existence loop over `BINARY_NAMES`, when `BUILD_OUTPUT_DIR` differs from the deploy bin directory, run the tool's `swap` instead of the per-file `cp`.
2. Run `check --bin-dir "${DEPLOY_BIN}" --rev auto --repo "${REPO_ROOT}"`, adding `--strict` when `DEPLOY_STRICT_BINARIES` (new) is `1`.
3. Before the closing message, run `record-revision --root /opt/llm --rev auto --repo "${REPO_ROOT}"`.
4. Print the check result so the operator sees stale or unknown binaries.

### Method
- Edit the block under the "バイナリ + 辞書配置" comment: keep `BUILD_OUTPUT_DIR`, `BINARY_NAMES`, the `realpath` same-file guard, and the dictionary handling; replace the `cp` with the tool call only for the separate-directory case.
- Call the tool as `python3 "${REPO_ROOT}/tools/manage_binaries.py" ...`.

### Details
- The next-steps text at the end can mention `deploy/build_binaries.sh` for stale binaries.
- Do not change the config copy list in this procedure.
