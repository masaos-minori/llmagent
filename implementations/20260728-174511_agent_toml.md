## Goal

Every `[mcp_servers.<key>]` `cmd` entry in `config/agent.toml` invokes `uv run --no-sync` instead of bare `uv run`, so MCP server subprocess startup never performs implicit dependency resolution/sync against `/opt/llm/pyproject.toml`/`uv.lock`, and instead fails fast if the deployed venv is not already prepared.

## Scope

**In-Scope:**
- Insert `--no-sync` immediately after `"run"` in the `cmd` array of all 10 `[mcp_servers.<key>]` sections in `config/agent.toml` (lines 299, 311, 320, 329, 338, 347, 364, 373, 382, 394).
- Add/extend a config-level test asserting each subprocess-mode `cmd` list contains `--no-sync`.
- Manual/smoke verification that an MCP server still starts successfully with the new flag against the existing synced dev venv.

**Out-of-Scope:**
- Any change to `scripts/agent/http_lifecycle.py` — `HttpServerLifecycleManager.start()` already forwards `cfg.cmd` verbatim.
- Any change to `scripts/shared/mcp_config.py` — `cmd` is stored as a plain `list[str]`; no schema change required.
- Updating deployment runbook notes describing that the venv/lockfile must be fully synced before MCP servers start — explicitly out of scope for this document-only planning phase.
- Adding a code-level guard that rejects a missing `--no-sync` flag — only the `cmd` array change plus a test are needed.

## Assumptions

1. `--no-sync` (not `--frozen`) is the correct flag per the deployment model — confirmed by codebase precedent: `uv run --no-sync <cmd>` is the established pattern used throughout this repo whenever the intent is "assume the venv is already prepared, do not sync/resolve at invocation time."
2. The production venv at `/opt/llm` is synced via `uv sync --dev --system-certs` as a distinct deploy step, documented in `docs/02_deployment-part1.md:35`.
3. No other code path outside `config/agent.toml` hardcodes the pre-change `["uv", "run", "--directory", ...]` shape at a fixed index other than `cmd[-1]` — confirmed by grep: only `tests/test_mcp_server_cmd_paths.py` inspects `cmd`, and it only reads `cmd[-1]`.
4. The 10 `[mcp_servers.<key>]` sections currently at lines 299, 311, 320, 329, 338, 347, 364, 373, 382, 394 are the complete and only set of `startup_mode = "subprocess"` entries in `config/agent.toml`.

## Design decisions

- Use `--no-sync` flag (not `--frozen`) — matches this repo's existing convention for "assume venv already prepared" invocations.
- Insert `--no-sync` at index 2 of the `cmd` array: `["uv", "run", "--no-sync", "--directory", "/opt/llm", "python", ...]`.
- Extend `tests/test_mcp_server_cmd_paths.py` with an assertion that every subprocess-mode `server_cfg.cmd` contains `"--no-sync"` at index 2.

## Alternatives considered

- Use `--frozen` instead of `--no-sync`. Rejected — `--frozen` would still allow silent environment mutation (installing missing packages to match a possibly-stale lockfile) without erroring, which does not satisfy the requirement's "fail fast and loudly" goal as cleanly as `--no-sync`.
- Add a Python assertion/guard that rejects a missing `--no-sync` flag. Rejected — the requirement only asks for the `cmd` array change plus a test, not runtime enforcement.

```python
# New test — tests/test_mcp_server_cmd_paths.py
def test_subprocess_cmds_have_no_sync_flag():
    """Every subprocess-mode MCP server cmd should contain '--no-sync'."""
    cfg = build_agent_config()
    for key, server_cfg in cfg.agent.mcp_servers.items():
        if server_cfg.startup_mode == "subprocess":
            # Assert --no-sync is at index 2: ["uv", "run", "--no-sync", ...]
            assert "--no-sync" in server_cfg.cmd, \
                f"{key}: subprocess cmd missing --no-sync flag: {server_cfg.cmd}"
```

## Compatibility considerations

- All 10 MCP servers (`shell`, `git`, `web_search`, `file_delete`, `file_write`, `file_read`, `github`, `cicd`, `rag_pipeline`, `mdq`) are affected identically; this includes security-sensitive roles (`file_write`, `file_delete`, `execute`).
- `scripts/agent/http_lifecycle.py::HttpServerLifecycleManager.start()` consumes `cfg.cmd` verbatim via `subprocess.Popen` — no code change needed there.
- `scripts/shared/mcp_config.py::McpServerConfig`/`_build_single_server` parse `cmd` as an untyped `list[str]` — no schema validation of flag content exists today, so no parser change required.

## Security considerations

This change strengthens the security posture by preventing MCP server subprocesses from silently mutating their environment during startup. It ensures that any dependency mismatch is caught at startup rather than silently resolved, which could introduce unexpected behavior or dependencies.

## Rollback considerations

- Simple revert: remove `--no-sync` from all 10 `cmd` arrays in `config/agent.toml`.
- Low blast radius: only affects the `cmd` array values consumed by `HttpServerLifecycleManager.start()`.

## Risks

- Choosing `--no-sync` over `--frozen` could be wrong if the actual deploy tooling does not guarantee `uv sync` runs before every MCP-server-affecting deploy → Mitigation: `docs/02_deployment-part1.md:35` already documents `uv sync --dev --system-certs` as a required deploy step; Implementation Step 3 files a follow-up to make this precondition explicit in the deployment runbook specifically in the context of MCP server startup.
- `config/agent.toml` has high churn (55 commits, including a prior bug fix for stale `cmd` paths in commit `18287eb2`) — a future edit to these `cmd` arrays could silently drop the `--no-sync` flag → Mitigation: the new test added in Phase 2 acts as a regression guard, run on every `pytest` invocation and CI.
- Manual verification (Phase 3, simulating a stale venv) may not be reproducible in an automated CI environment → Mitigation: document the manually-observed error text in the implementation procedure so a future automated test can assert against it if the deploy tooling later exposes a way to simulate this in CI.
