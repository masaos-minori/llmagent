## Assumptions

- `execute_one_tool_call()`'s return shape (`tc_id, name, args, full_text, is_error,
  llm_text`) is unchanged (per the `tool_runner.py` doc), so every existing assertion of
  the form `_, name, args, text, is_error, llm_text = result` in this file needs no
  change to its *unpacking* shape — only to how the input `tc`/`pc` value is constructed
  before the call.
- `_execute_with_dag()`'s current tests build `tool_meta` manually in some cases and via
  `_build_tool_meta()` in others (confirmed: `TestExecuteWithDag`'s early tests call
  `_build_tool_meta()` directly to build the dict passed alongside `approved_calls`) —
  after this plan, tests that constructed `tool_meta` via `_build_tool_meta()` must
  instead construct each `PreparedToolCall.spec` directly (a `ToolSpec` literal) and let
  `_execute_with_dag()` build its own `tool_meta` dict internally from
  `{pc.name: pc.spec for pc in approved_calls}`, per that file's doc — tests no longer
  pass `tool_meta` as a separate argument at all if `_execute_with_dag()`'s signature
  itself doesn't take one (confirmed: it doesn't; `tool_meta` is entirely
  internally-derived).

## Design decisions

- **Delete `TestExecuteOneToolCallValidation` from this file rather than leaving a
  stub.** Its four scenarios test `_validate_tool_args()`'s specific lenient-fallback
  semantics, which this plan removes entirely; the equivalent (but now fail-closed, not
  lenient) scenarios belong in `test_tool_preparation.py`. Leaving a renamed-but-similar
  class here testing `execute_one_tool_call()` for validation behavior it no longer
  performs would misdescribe the function under test.
- **Add one `_pc()` helper rather than inlining `PreparedToolCall(...)` construction at
  every call site.** ~15 call sites currently construct `tc` dicts directly (per `grep -c
  "execute_one_tool_call" tests/agent/test_tool_runner.py` → 15 hits); a shared helper
  keeps the diff smaller and consistent with the file's existing `_cfg()`/`_tc()`-style
  helper convention (confirmed present at the top of this file today).
- **Keep `TestExecuteWithDag`'s and `TestExecuteStandardSerialization`'s scenario
  *names* and *assertions* unchanged where the underlying behavior is unchanged** —
  only the input construction (`tc` dict → `PreparedToolCall`) changes; this keeps the
  diff reviewable as "same tests, adapted inputs" rather than a full rewrite, and makes
  it easy to confirm no behavioral coverage was silently dropped.

## Alternatives considered

- Rewriting this file from scratch given the scope of changes. Rejected: the plan's
  Risks section explicitly names this as high-likelihood risk ("1080 lines... changing
  both functions' contracts in the same phase risks a large, error-prone test rewrite")
  and mitigates it by keeping the 6-tuple return shape unchanged and updating
  incrementally, running the suite after each edit — a full rewrite would discard that
  mitigation and risk losing coverage silently.
- Keeping `_build_tool_meta()`'s tests but pointing them at a new equivalent function.
  Rejected: no equivalent function is introduced (its logic is subsumed into
  `RuntimeToolRegistry.tool_spec_for_call()`, already tested in
  `scripts/shared/`'s own test suite per the plan's Out-of-Scope section, which
  explicitly excludes re-testing the shared-layer plumbing here).

       name: str,
       args: dict[str, Any],
       call_id: str = "call_1",

   ) -> PreparedToolCall:
       return PreparedToolCall(
           call_id=call_id,
           name=name,
           args=args,
