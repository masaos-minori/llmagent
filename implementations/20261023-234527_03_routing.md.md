## Goal

Add a pointer to the new `run_validation_gates.py` entry point in `routing.md`'s "When to run which tool" table, so the routing table's own selection logic points at the executable one-command form that runs the gates a given diff needs. (`REQ-008`)

## Scope

- **In-Scope**: add one row to the "When to run which tool" table in `routing.md` only.
- **Out-of-Scope**: implementing the tool (seq 01 of the plan's sibling row), registering it in `tools/TOOL_DESCRIPTIONS.md` (seq 02), or adding the `rules/toolchain.md` pointer (seq 04).

## Assumptions

- The table's rows follow the shape `| Situation | Run | Notes |`, where `Run` names the exact command to execute.
- `run_validation_gates.py` is invoked as `uv run python tools/run_validation_gates.py` (matching every other row in the table).
- `check_skills_references.py` validates backtick-quoted `rules/`/`skills/`/`templates/`/`AGENTS.md`/`routing.md` references resolve to existing files; the new row must not introduce a dangling reference.

## Design decisions

- **Add one row near the other `tools/`-change rows.** Place the new row immediately after the `check_tool_descriptions_sync.py` row (line 96), grouping the two `tools/`-adjacent gate runners together and keeping the table's tool-oriented ordering intact.

## Alternatives considered

- Adding a whole new subsection for the orchestrator: rejected — the "When to run which tool" table is the canonical home for "which command to run for this situation", and a new section would fragment discoverability.
