# Implementation Procedure: Refactor pipeline.py — separation of concerns

## Goal

Extract five concern groupings from `RagPipeline` into separate modules/classes and reduce it to a thin sequencer (REQ-001 through REQ-006).

## Scope

- Modify `scripts/rag/pipeline.py`: extract MQE stage logic, search stage logic, fusion stage logic, rerank stage logic, HTTP augment + refiner logic into dedicated modules/classes
- Consolidate duplicated retry-once-with-delay helper used across `_run_stage` and `_run_http_augment`
- Reduce `RagPipeline` to thin sequencer wiring components together in `run()`

## Assumptions

- Constructor-injection/delegation pattern used in `orchestrator.py` and `ingester.py` splits is acceptable as a reference
- Five concern groupings listed under Implementation Intent are reasonable boundaries for extracted modules
- Existing `scripts/rag/stages/*.py` files may need to become proper stage implementations rather than staying as stubs
- Consolidated per-stage status helper should be parameterized by stage name and return OK/FATAL/WARNING/SKIPPED counts

## Design decisions

- Extract each concern into a separate module/class following constructor-injection/delegation pattern
- `RagPipeline.run()` remains a thin sequencer calling into components in same order as today
- Preserve public return contract (`PipelineRunResult`) and exception behavior
- Consolidate retry-once-with-delay logic into shared helper

## Alternatives considered

- Single monolithic refactor vs phased extraction: phased approach reduces risk of interface breakage
- Inline status helpers vs consolidated parameterized helper: consolidated helper reduces duplication but requires careful API design
