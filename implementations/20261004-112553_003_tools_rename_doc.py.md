## Goal
Make `tools/rename_doc.py` rewrite front matter `related:` entries when a document is renamed (REQ-002: keep the single source of cross-references valid across renames).

## Scope
- In: scanning front matter `related:` entries in `scan_file`, producing rewrites for them, and the docstring and report wording.
- Out: Markdown link rewriting behavior, title rewriting, prose-mention reporting for non-front-matter text.

## Assumptions
- Basenames are unique under `docs/`, so a bare front matter entry equal to the old basename refers to the renamed file.
- Existing entries are unquoted; quoted or otherwise unusual entries fail closed.
- Verified: `scan_file` today reports a bare front matter filename as a non-link prose mention, so the new handling must mark those spans as handled.

## Design decisions
- Reuse `PlannedRewrite`, `UnresolvedLink`, `classify_style`, `compute_new_target`, and the rightmost-first span application so apply semantics do not change.
- Preserve each entry's existing style: a bare entry becomes the new basename; a `../` entry becomes the relative path from the referencing file.
- Fail closed: an entry that resolves to the old path but is neither style is reported as unresolved and not rewritten.

## Alternatives considered
- Reparse and re-emit front matter with a YAML library: rejected; would reformat unrelated keys.
- Leave front matter entries to the structure checker's front matter link validation (in `tools/check_docs_structure.py`) to detect: rejected; detection without repair leaves renames half-done.

## Implementation
### Target file
`tools/rename_doc.py`

### Procedure
1. In `scan_file`, find the front matter block and the `related:` block item lines.
2. For each item, match it to the old path (bare: basename equals the old basename; `../` style: resolves to the old path), classify style, and build a `PlannedRewrite` with the item's text span.
3. Add those spans to the handled spans so the prose scan does not also report them.
4. Update the module docstring (scope now includes front matter `related:` entries) and the report heading text.

### Method
- Item lines match `^\s+-\s+<entry>\s*$`; only the entry text span is replaced.
- An entry resolving to the old path with another shape (quoted, sub-path) goes to `unresolved_links` with a reason and no rewrite.
- The old-path file's own front matter entries (self-reference) follow the existing `actual_file` handling in `main()`.
- No change to `main()` flow other than wording.

### Details
- Front matter spans do not overlap Markdown link spans, so `apply_rewrites_to_content`'s rightmost-first order still holds.
- Both `--dry-run` (default) and `--apply` behavior stay as documented; the dry-run report lists the new rewrites.
- Do not touch body Related sections (they are being removed by the migration rows).

## Compatibility considerations
- Existing link and prose behavior is unchanged except that bare front matter entries are no longer reported as prose mentions.
- CLI arguments are unchanged.

## Security considerations
- Scope stays restricted to `docs/` (`ensure_within_docs` checks are unchanged); no new subprocess use.

## Rollback considerations
- Revert the commit; renames then behave as before and the structure checker's front matter link validation flags stale entries.

- Unsupported shapes are reported and nothing is written for them.
- Those entries are not reported a second time as prose mentions.
- Ruff, mypy, bandit, and the tool's tests pass.

## Out of scope
- Rewriting body prose, titles, or non-`docs/` files.
- Any change to how Markdown links are rewritten.
