## Goal
Add a logical-verification result field/type to `scripts/db/models.py`, distinguishable
from `RecoveryResult`'s existing physical-outcome fields (REQ-001).

## Scope
- In scope: `RecoveryResult` (lines 123-129) — add one new field carrying a
  logical-verification outcome (pass/fail + detail), or a nested result type if a
  single bool+str pair is insufficient to also carry which domain (RAG/Session) was
  checked.
- Out of scope: `success`/`action`/`detail`/`dry_run` — unchanged in meaning; any other
  class in this file (e.g. `DbCondition`, confirmed present but not read in full this
  cycle — not implicated by this row's change).

## Assumptions
- A single additional field (e.g. `logical_ok: bool | None = None`, `None` meaning "no
  logical check applicable/run") is sufficient — Design decisions below explains why a
  separate nested dataclass was considered and not chosen, unless implementation-time
  investigation finds `detail` cannot cleanly carry both physical and logical messages
  in one string (in which case a second `logical_detail: str | None = None` field is
  the minimal addition, not a full nested type).

## Design decisions
- Add plain field(s) to the existing frozen dataclass rather than introducing a nested
  result type (e.g. `LogicalVerificationResult`) — `RecoveryResult` is already a flat,
  frozen dataclass with 4 fields; a 5th/6th field keeps every existing construction
  site (`RecoveryResult(success=..., action=..., ...)`) working with only additive
  keyword arguments, no signature-breaking change. A nested type would be justified
  only if the logical outcome needed its own multi-field report shape mirroring
  `RagConsistencyReport`'s structure — not required here, since seq 01 only needs a
  pass/fail flag plus a short summarized detail string, per REQ-002's own "pass/fail +
  detail" wording.

## Alternatives considered
- A nested `LogicalVerificationResult` dataclass (mirroring
  `RagConsistencyResult`/`RagConsistencyReport`'s existing shape in
  `scripts/agent/services/models.py`): rejected for this row — that existing type
  belongs to a different, unrelated feature (`RagMaintenanceService.consistency()`,
  confirmed via `rg` to have no relation to the recovery path this Plan modifies); a
  flat field addition here is simpler and sufficient for REQ-001's stated need.
