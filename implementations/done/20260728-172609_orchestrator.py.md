## Goal

Stop `Orchestrator._handle_workflow_engine()`'s `finally` block from overwriting a task's DB status back to `completed`/`failed` when `WorkflowEngine.run()` already persisted a terminal `pending_approval` or `halted` status before raising.

## Scope

**In-Scope:**
- `scripts/agent/orchestrator.py` — `_handle_workflow_engine()`: add an `engine_status_handled: bool` flag, set it `True` in the `except WorkflowPendingApprovalError` and `except WorkflowHaltError` branches, and guard the `finally` block's `store.update_task_status(...)` call on `not engine_status_handled`.
- Widen the second `except` clause from `except WorkflowHaltError as exc:` to `except (WorkflowHaltError, WorkflowTimeoutError) as exc:` (see UNK-01) so a bare `WorkflowTimeoutError` re-raised by `WorkflowEngine.run()` (which already stamped `"halted"`) is also protected from being overwritten to `"completed"`.
- Update `_handle_workflow_halt()`'s type hint from `exc: WorkflowHaltError` to `exc: WorkflowHaltError | WorkflowTimeoutError` to match the widened except clause.
- Add `WorkflowTimeoutError` to the import list from `agent.workflow` in `scripts/agent/orchestrator.py`.
- `tests/test_orchestrator.py` — add/extend tests covering `_handle_workflow_engine()`'s status-preservation behavior for `pending_approval`, `halted` (via both `WorkflowHaltError` and `WorkflowTimeoutError`), `completed`, and `failed` outcomes.

**Out-of-Scope:**
- Any change to `scripts/agent/workflow/workflow_engine.py` — its `run()` method (lines 126-154) and `_gate_approval()` (lines 156-187) already set the correct terminal statuses before raising; no changes needed there. Read-only reference for this plan.
- Any change to `scripts/agent/workflow/approval_ops.py` — `find_all_pending_approvals()` is only a regression-check target, not a modification target.
- Any change to task status semantics beyond preventing the overwrite (e.g. no new status values, no schema changes).
- Handling of any other exception type not caught by the two (now widened to three) named except clauses — those continue to propagate uncaught out of `_handle_workflow_engine()` unchanged; the `finally` block still runs cleanup (`_deactivate_workflow`, `store.close()`) for them, and per the source requirement this remains intentional/unchanged.

## Assumptions

1. `store = StateStore()` (orchestrator.py line 241) is the same class whose `update_task_status()` method (`scripts/agent/workflow/state_store.py:90`) performs `UPDATE tasks SET status=?, ... WHERE task_id=?` — confirmed by direct read.
2. `ctx` passed into `_handle_workflow_engine()` and `self._ctx` used inside `_handle_workflow_approval_pending()`/`_handle_workflow_halt()` reference the same `AgentContext` object at runtime (both handlers use `self._ctx` rather than a passed-in `ctx` param), so mutations there are visible to the caller's `ctx`. This is standard for this codebase's single-context-per-turn design and does not need further verification for this bug fix, since the fix only touches status-write control flow, not context mutation.
3. `error_kind` remaining `None` when an engine-level exception (`WorkflowPendingApprovalError`/`WorkflowHaltError`/`WorkflowTimeoutError`) fires before or during the execute stage is expected and unrelated to this fix's correctness — the fix's guard (`engine_status_handled`) is orthogonal to `error_kind`.
4. No other caller of `store.update_task_status()` races with `_handle_workflow_engine()`'s `finally` block for the same `task_id` within a single turn (single-threaded async turn processing per session).

## Design decisions

- Use a boolean flag (`engine_status_handled`) initialized to `False` alongside `error_kind`/`is_partial`/`task` before the `try` block. Set to `True` in both exception branches that indicate the engine already persisted the correct terminal status. Guard the `finally` block's status write on `not engine_status_handled`.
- Widen `except WorkflowHaltError` to `except (WorkflowHaltError, WorkflowTimeoutError)` to satisfy the Acceptance Criteria's explicit "or WorkflowTimeoutError" clause, consistent with how `workflow_engine.py` itself treats the two exceptions as equivalent for status purposes.

## Alternatives considered

- Initialize `engine_status_handled` inside the `try` block after `store = StateStore()`. Rejected — flag must be available in the `finally` block regardless of where `store` assignment fails; placing it alongside `error_kind`/`is_partial`/`task` ensures availability in all paths.
- Check the stored status value directly in the `finally` block instead of using a flag. Rejected — would require an extra DB round-trip and introduces race conditions if another process updates the status concurrently; the flag approach is simpler and avoids this.
