## Goal
Implement `tools/rename_doc.py`, a script that renames a `docs/*.md` file (including
`docs/adr/*.md`) via `git mv` and rewrites every Markdown-link path across `docs/`
pointing at the old path, preserving each referencing file's link style (REQ-001,
REQ-002, REQ-003, REQ-004, REQ-005, REQ-006).

## Scope
- In scope: `git mv <old-path> <new-path>`; scanning `docs/` (including `docs/adr/`)
  for `[text](path)` links resolving to `old-path` and rewriting only the path
  portion, preserving each file's existing prefix style (bare vs. `../`-prefixed);
  opt-in `--old-title`/`--new-title` adjacent link-text rewrite; reporting (not
  modifying) non-link prose mentions; `--dry-run` (default) / `--apply` modes;
  write-scope restriction to `docs/` only.
- Out of scope: renaming/restructuring `scripts/*.py` (that is
  `rename_mcp_modules.py`'s scope); automatically resolving non-link prose
  mentions; renaming an ADR's numeric ID or updating `docs/adr-index.md`'s ID
  column/plain-text `ADR-NNN` mentions (UNK-03 — file-path-only renaming, current
  ADR number preserved).

## Assumptions
- Dev-only tooling, outside the production deploy scope (absent from
  `deploy/deploy.sh` and `rules/env.md`'s deployment description).
- "Markdown link" for REQ-002/REQ-004's scope means the `[text](path)` inline-link
  form only — reference-style `[text][ref]` / `[ref]: path` links were not
  observed in the inspected ADR files and are not separately required.
- The old path is matched by exact relative-path resolution against each
  referencing file's own directory, not by filename-only matching, since two
  different `docs/` files could plausibly share a basename in a large tree.

## Design decisions
- Enforce the `docs/`-only write restriction (REQ-006) by resolving both
  `old-path`/`new-path` and every candidate rewrite target to an absolute path and
  confirming containment under the repository's `docs/` directory before any
  write — rejecting (non-zero exit, no write) on containment failure. This
  directly defends against a `..`-traversal argument, not merely trusting the
  caller-supplied path.
- Preserve each referencing file's existing link-prefix convention on rewrite
  (bare filename vs. `../`-prefixed) rather than normalizing to one form —
  confirmed necessary: `docs/adr/ADR-005-rag-source-derived-index-relationships.md`
  and `docs/adr/ADR-009-rag-ft5-text-separation.md` both use the bare-filename
  convention (e.g. `[RAG Data Model](03_rag_04_01_dto-models_data.md)`), while
  `docs/adr/ADR-012-git-mcp-server-side-write-enforcement.md` uses a
  `../`-prefixed convention (`[MCP Server Catalog: git-mcp](../04_mcp_04_05_git.md)`)
  for structurally similar cross-references — the repository is not consistent
  on this point.
- Non-link-prose reporting (REQ-004) is a hard behavioral boundary: after
  extracting every Markdown link span on a line, any remaining occurrence of the
  old filename outside those spans is collected into the report and never
  written, in both `--dry-run` and `--apply` modes.
- Title-rewrite (REQ-003) is gated on both `--old-title` and `--new-title` being
  supplied together — supplying only one is a usage error (non-zero exit), not a
  partial rewrite.
- `--dry-run` is the default (matching `tools/fix_docstring_paths.py` and
  `tools/fix_docs_section_marks.py`'s existing convention); `--apply` is required
  to write.

## Alternatives considered
- Normalizing every rewritten link to one canonical prefix style: rejected — the
  repository's own ADR files demonstrate two conventions in current use; forcing
  one style would create unrelated diff noise in every referencing file touched.
- Auto-resolving plain-prose mentions of the old filename: rejected per the
  issue's own Constraints — plain prose is reported only, never modified,
  distinct from Markdown-link path rewriting.
- Renaming an ADR's numeric ID together with its file path: rejected for this
  Plan's scope (UNK-03) — deferred to a future, separately-scoped extension if
  requested by an owner decision.

## Implementation
### Target file
`tools/rename_doc.py`

### Procedure
1. Parse CLI arguments: `<old-path> <new-path>` (positional), `--old-title`,
   `--new-title` (optional pair), `--dry-run` (default) / `--apply`.
2. Resolve `old-path`/`new-path` to absolute paths and confirm both lie under the
   repository's `docs/` directory; reject (non-zero exit, no write) if either
   does not.
3. Scan every `docs/*.md` file (including `docs/adr/*.md`) for `[text](path)`
   Markdown links; for each, resolve `path` relative to the containing file's
   directory and compare against the resolved `old-path`.
4. For each matching link: compute the new path string using the same prefix
   convention (bare vs. `../`-prefixed) the original link already used, and
   record a planned rewrite (old link string -> new link string) for that file.
5. If `--old-title`/`--new-title` are both supplied: for each planned link
   rewrite, check whether the link's adjacent text duplicates `--old-title`; if
   so, also record a text rewrite to `--new-title`.
6. For each file scanned, after extracting all Markdown-link spans on each line,
   check whether any remaining occurrence of the old filename (outside those
   spans) exists; record each as a non-link-prose finding (report only, never
   rewritten).
7. In `--dry-run` mode (default): print the planned `git mv`, every planned link/
   title rewrite, and every non-link-prose finding, without performing the move
   or writing any file.
8. In `--apply` mode: perform `git mv <old-path> <new-path>` first, then write
   every planned link/title rewrite to its referencing file, then print the same
   report as `--dry-run` plus confirmation the writes occurred. Non-link-prose
   findings are still reported, never written, in `--apply` mode too.

### Method
Argparse-based CLI script (`main()` entry point), `pathlib.Path`-based repo-root
and `docs/`-containment resolution, plain-function structure (link-scanner,
per-file rewriter, title-rewrite helper, prose-mention detector) — following
`tools/fix_docstring_paths.py`/`tools/fix_docs_section_marks.py`'s established
`--dry-run`-default/`--apply`-to-write CLI shape. `git mv` invoked via
`subprocess.run(["git", "mv", str(old_path), str(new_path)], shell=False,
check=True)` or the repository's existing GitPython pattern
(`scripts/shared/git_helper.py`'s lazy `import git`) — either is acceptable per
this Plan; the choice is an implementation-procedure-level decision, not
prescribed further here since the Plan's Reference Files cite
`tools/rename_mcp_modules.py` only as a structural/CLI reference, not for its
specific move mechanism (that tool renames Python modules, not files via `git
mv`).

### Details
- Link path parsing: split the matched `(path)` portion on the first `#` to
  preserve any trailing anchor fragment unchanged when rewriting only the path
  segment (UNK-02).
- Link matcher must fail closed on any link path it cannot confidently classify
  as either the bare-filename or `../`-prefixed style — report it rather than
  guess a rewrite (per the Plan's Risks mitigation).
- The `docs/`-containment check applies to every file the scanner considers
  writing to, not only the `git mv` source/destination — a link-rewrite target
  file must also resolve under `docs/` before any write.
- Exit codes: `0` on success (dry-run report or completed apply); `1` on any
  validation failure (containment failure, malformed CLI arguments, `git mv`
  failure).

## Rollback considerations
New file only; rollback is deleting `tools/rename_doc.py`. Any rename it performs
via `--apply` is itself a Git rename — reversible with a normal `git mv` back, or
`git revert`/`git reset` on the commit that recorded it, same as any other Git
rename. `--dry-run` mode performs no write at all, so it carries no rollback
concern.
