## Goal

Define `ServerCooldownError` custom exception and raise it from `ensure_ready()` when a tool call is attempted during MCP subprocess cooldown.

## Scope

**In-Scope**:
- Define `ServerCooldownError(RuntimeError)` custom exception class
- Raise `ServerCooldownError` from `ensure_ready()` when server is in cooldown

**Out-of-Scope**:
- Modifying cooldown logic itself
- Changing `_COOLDOWN_SECONDS` duration
- Adding new configuration options
- Updating callers to handle the exception (covered in separate documents)

## Assumptions

1. Raising an exception (rather than returning a sentinel value) makes the failure explicit at the call site.
2. `ServerCooldownError(RuntimeError)` will be caught by existing `except (OSError, RuntimeError)` handlers in callers.

## Design decisions

- **Subclass `RuntimeError`**: Ensures compatibility with existing exception handlers that catch `RuntimeError`. Callers don't need to add new exception types.
- **Include remaining time in error message**: Provides actionable information to users about when they can retry.
- **Place constant `_COOLDOWN_SECONDS` at module level**: Already exists at line 45 of factory.py — reuse it rather than duplicating the value.

## Alternatives considered

- **Return sentinel object instead of raising**: Would require changing all callers to check for sentinel values. Chose exception approach because it makes the failure explicit at the call site.
- **Raise generic `RuntimeError`**: Less informative — users wouldn't know this is specifically a cooldown issue. Chose custom exception for clarity.
- **Use `TimeoutError` subclass**: Semantically closer but doesn't fit the asyncio timeout pattern. Chose `RuntimeError` for broader compatibility.
