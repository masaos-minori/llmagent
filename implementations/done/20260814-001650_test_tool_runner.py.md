## Design decisions

- **Rewrite `TestExecuteStandardSerialization` in place, keep its class name.** All
  three of its tests exercise `serial_tool_calls=True` through the public
  `execute_all_tool_calls()` entry point and assert on `ctx.stats.stat_serialization_events`/
  `ctx.diagnostics.save_serialization_event` — this observable surface does not change
  under the rework (both `_execute_standard()` and the new `force_serial`-driven
  `_execute_with_dag()` populate the same `ctx.stats`/`ctx.diagnostics` sinks), only the
  `serial_reason` value and the fields present on the `round_event` dict change. Keeping
  the class name and test names (only updating bodies/comment) makes the diff show
  "same behavior, corrected mechanism," matching how the plan frames this as swapping
  the underlying engine while preserving the outward contract of the diagnostic events.
- **`test_no_side_effect_no_serialization_event` becomes the direct regression lock for
  "no event when concurrency wasn't actually prevented."** Today this test passes
  because a read-only call never triggers `_execute_standard()`'s `is_side_effect()`
  check; under the new path, it must pass because a single read-only call under
  `force_serial=True` still produces exactly one single-call phase with no *other* call
  to conflict with — the plan's Design section states events fire "only when
  concurrency was actually prevented," and a batch of one call never prevents anything.
  This doc keeps the test's assertion (`stat_serialization_events == []`) but updates
  its docstring to explain *why* under the new mechanism, since the old explanation
  ("no side effect detected") no longer applies once `is_side_effect()` is gone from
  this path.
- **New final-order-restoration test targets the specific defect named in the plan's
  Goal** ("results.sort... is retained unchanged; only the loop that produces results...
  changes") — this is exactly the kind of regression a naive rewrite of the
  `ExecutionPlan.batches` iteration could silently break (e.g. by forgetting to carry
  `tc["id"]` through into whatever `ScheduledGroup.calls` ends up holding), so it
  deserves its own explicit test rather than relying on existing tests that happen not
  to exercise out-of-order completion.

## Alternatives considered

- Deleting `TestExecuteStandardSerialization` entirely on the theory that
  `_execute_standard()` no longer exists, so nothing in this class name applies.
  Rejected: the class's *behavioral* contract (serial_tool_calls=True still serializes,
  still records an event with a specific reason, still calls diagnostics) is exactly
  what this plan requires to be preserved through the new mechanism — deleting the
  class would lose that regression coverage rather than update it. The plan's own
  Assumptions section explicitly frames `serial_tool_calls` as feeding `force_serial`
  "instead of branch-selection use," implying continuity of observable behavior, not
  removal.
- Testing `force_serial` only at the `tool_scheduler.py` unit level (covered by the
  paired `test_tool_scheduler.py` doc) and skipping an end-to-end test here. Rejected:
  the plan's Affected-areas table explicitly lists this file's needed addition as
  "Add/adjust tests for the single execution path, `force_serial`, final-order
  restoration" — an end-to-end test through `execute_all_tool_calls()` is what proves
  `ctx.cfg.tool.serial_tool_calls` actually reaches the planner as `force_serial`, which
  a scheduler-only unit test cannot demonstrate on its own.
