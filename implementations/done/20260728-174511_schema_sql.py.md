## Goal

Confirm the distance metric actually used by the `memories_vec` (and `chunks_vec`) `vec0` virtual tables through empirical testing, make it explicit in `scripts/db/schema_sql.py`, and update the "Negate distance" comment in `scripts/agent/memory/retriever.py` to name the confirmed metric — resolving NC-004 at the code/schema level without touching `docs/*.md`.

## Scope

**In-Scope:**
- Empirical + source-level confirmation of the default `vec0` distance metric used by `memories_vec` (already completed during this planning cycle — resolved to L2/Euclidean)
- Add explicit `distance_metric=L2` clause to `memories_vec` `CREATE VIRTUAL TABLE` statement in `scripts/db/schema_sql.py:134-137`
- Add the same explicit clause to `chunks_vec` (`scripts/db/schema_sql.py:47-50`) if its runtime behavior is confirmed to match (conditional on UNK-02 resolution)

- Note in code comments and the eventual commit message: embeddings are not normalized before insertion, so L2 ranking is magnitude-sensitive

- Correcting the "cosine distance" docstring at `scripts/db/store_impl.py:39` unless UNK-02 resolves to confirm `chunks_vec` also defaults to L2 (tracked as a conditional follow-up)

## Assumptions

1. The production sqlite-vec build at `/opt/llm/sqlite-vec/vec0.so` (VERSION `0.1.10-alpha.4`) is representative of what runs in all environments that exercise `memories_vec`/`chunks_vec`.
2. The `distance_metric=` clause syntax parsed at `sqlite-vec.c:3066` in the installed build is stable/supported syntax for this version and will not error when added to the `CREATE VIRTUAL TABLE` statement.
3. Because the confirmed default (L2) already matches what the schema silently used before, adding the explicit clause is a no-op with respect to search result ordering — no ranking regression is expected.
4. `chunks_vec`'s runtime default is also L2 (same `vec0` module, same missing clause, same binary) even though this was not separately empirically re-tested in this cycle — see UNK-02.

## Risks

- The `distance_metric=L2` clause syntax may not be accepted by the specific installed build (0.1.10-alpha.4) if its syntax diverges from upstream → Mitigation: Verify the clause against `sqlite-vec.c:3066`'s parsing logic before editing `schema_sql.py`, during Phase 1.
- No sqlite-vec version is pinned in `requirements.txt`/`pyproject.toml`/`uv.lock`, so a CI or contributor environment could load a different `sqlite-vec` build than the production `/opt/llm/sqlite-vec/vec0.so` tested here → Mitigation: Keep the new test gated behind the existing `@pytest.mark.skipif(not _VEC_AVAILABLE, ...)` pattern so it degrades gracefully.
- Embeddings inserted into `memories_vec` are not normalized to unit length, so L2-based `MemoryHit.score` is magnitude-sensitive and may not match a naive "cosine similarity" mental model held by downstream consumers → Mitigation: This plan does not change embeddings or scoring; it only documents the confirmed metric in the comment so future consumers are aware of the magnitude sensitivity.
- Changing `chunks_vec` without empirically confirming its runtime metric (UNK-02) could introduce an incorrect `distance_metric=` clause that silently changes RAG search ordering → Mitigation: Treat `chunks_vec` as conditional/optional in this plan; only proceed with it in the implementation phase if UNK-02's empirical test confirms L2.
