# Implementation Procedure: Phase 7 — Test Updates

## Goal

Add tests for atomicity scenarios (forced re-ingestion with embedding failure, database failure during replacement, partial preparation failure, successful replacement), add tests for cache invalidation edge cases (all-skipped run, all-failed run, partial success), and update existing tests to work with new `PreparedChunk` / `IngestionFailureReason` API.

## Scope

### In-Scope
- Add test: forced re-ingestion with embedding failure — verify previous document preserved
- Add test: database failure during replacement — verify rollback
- Add test: partial preparation failure — verify no DB modification
- Add test: successful replacement — verify all chunks committed atomically
- Add test: all-skipped run — verify cache NOT invalidated
- Add test: all-failed run — verify cache NOT invalidated
- Add test: cache invalidation on partial success — verify cache invalidated only once
- Update existing tests to work with new `PreparedChunk` / `IngestionFailureReason` API

### Out-of-Scope
- Changes to cache invalidation logic beyond using cached URL
- Database schema changes
- Changes to `_commit_url_transaction()` (Phase 3)

## Assumptions

1. Current test suite uses `pytest` with `unittest.mock` for mocking (confirmed by inspecting existing tests)
2. `SQLiteHelper` can be mocked to simulate failures (confirmed by inspecting existing tests)
3. `PreparedChunk` objects can be compared via `isinstance()` checks in assertions
4. `IngestionFailureReason` values are comparable with string literals via `StrEnum` (confirmed by Python 3.11+ behavior)

## Design decisions

- Tests use `pytest.fixture` for shared setup (DB instance, mock HTTP client)
- Atomicity tests verify both success and failure paths
- Cache invalidation tests verify timing — cache should only be invalidated when at least one URL group succeeds
- Partial success scenario: if ANY chunk fails during preparation, entire URL group rolled back — no partial commits possible

## Alternatives considered

- Using integration tests for all scenarios: rejected because they're slower and harder to isolate failures
- Using property-based testing: rejected because it adds complexity without significant benefit for this domain
- Testing only success paths: rejected because failure paths are critical for atomicity guarantee

```python
def test_forced_reingest_with_embedding_failure(mock_db, mock_http_client, mock_doc_mgr):
    """Verify previous document preserved when re-ingestion fails."""
    # Setup: existing document exists
    mock_doc_mgr.handle_existing_document.return_value = (123, False)
    
    # Setup: first chunk succeeds, second fails
    prepared_chunks = [
        PreparedChunk(doc_id=123, chunk_index=0, content="chunk1", 
                     normalized_content="chunk1", embedding_blob=b"\x00\x01", 
                     chunk_type="text", source_file="file.txt"),
    ]
    
    # Setup: second chunk fails
    mock_http_client.post.side_effect = [
        {"embedding": [0.1] * 768},  # First chunk succeeds
        Exception("Embedding failed"),  # Second chunk fails
    ]
    
    # Execute
    ingester = RagIngester(
        rag_pipeline_service_url="http://localhost:8000",
        max_workers=2,
        http_client=mock_http_client,
    )
    
    result = ingester.ingest_url_group("http://example.com", force=True)
    
    # Verify: previous document preserved
    assert result.n_success == 1
    assert result.n_failed == 1
    assert result.failure_reason == IngestionFailureReason.EMBEDDING_FAILED
    
    # Verify: rollback happened — no new data inserted
    assert not db.execute.called_after_begin_immediate
```

### Details

**File locations**: 
- `tests/rag/ingestion/test_rag_ingester.py` — unit tests for atomicity scenarios
- `tests/integration/test_ingestion_e2e.py` — integration tests for end-to-end atomicity

**Key changes**:
1. Add atomicity test fixtures (mock DB, HTTP client, DocumentManager)
2. Add 4 new atomicity tests (forced re-ingest failure, DB failure, partial failure, successful replacement)
3. Add 3 cache invalidation tests (all-skipped, all-failed, partial success)
4. Update existing tests to work with new `PreparedChunk` / `IngestionFailureReason` API

**Critical insight**: Tests must verify BOTH success and failure paths. The atomicity guarantee is meaningless without testing the failure cases — if ANY chunk fails, the ENTIRE URL group should be rolled back.

**Thread safety**: Since workers no longer hold DB connections, there's no risk of connection conflicts. The main thread handles all DB writes sequentially.

**Memory consideration**: `PreparedChunk.embedding_blob` stores raw bytes — memory pressure for large documents is acceptable since URLs are processed sequentially; memory is freed after commit.

## Compatibility considerations

- Existing callers of `_embed_and_store()` expect `(bool, bool)` tuple — must be updated in Phase 4
- Test mocks that patch `_embed_and_store()` must return `PreparedChunk | IngestionFailureReason` instead
- `n_embed_failed` field semantics change: from "individual chunk embedding failure count" to "URL-group-level embedding failure indicator" (all-or-nothing due to atomicity)
