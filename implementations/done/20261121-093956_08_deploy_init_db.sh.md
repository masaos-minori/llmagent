## Goal

Make `deploy/init_db.sh` deterministically initialize the dedup store (identity row, `user_version` stamp, installation marker) through the shared loader path at deploy time, and document the operator-resolution step (REQ-005, REQ-007, REQ-011; AC-5, AC-10).

- Row 01 provides the loader/creation path (`load_dedup_config` + store open creating identity, stamp, marker in one sequence); the script only invokes it and verifies creation.
- `deploy.sh` already copies `config/mcp_dedup.toml` (verified: deploy.sh:153-154 file-level copy); no deploy.sh change is in this Plan's scope.
- Existing `tests/deploy/` gate tests must keep passing. Executed 2026-11-21: the fallout was confirmed and the Plan amended — `tests/deploy/test_init_db_schema_gate.py` and `tests/deploy/test_init_db_eventbus_schema.py` are now target rows; the schema-gate driver's `_write_config` gained a `config/mcp_dedup.toml` rewrite (the eventbus driver already rewrote every `config/*.toml`), and two sandboxed dedup tests were added to the schema-gate suite.

## Design decisions
- Initialize via a short `uv run python -c` (or module `__main__`) invocation against `LLMAGENT_CONFIG_DIR`/`/opt/llm/config/mcp_dedup.toml` rather than raw `sqlite3` DDL in the shell — the script must not duplicate canonical DDL (ADR-008 schema authority).
- The script's sandbox contract (honors `DEPLOY_SCRIPTS`/`DEPLOY_DB`/`LLMAGENT_CONFIG_DIR`, as the existing schema-gate tests rely on) extends to the dedup step.

## Alternatives considered
- Lazy first-use creation only: rejected by REQ-011 — deploy must prove creation deterministically, and first initialization is the only state where creation is legal.

## Implementation
### Target file
`deploy/init_db.sh`
### Procedure
Add a dedup-store initialization step after the existing database init/gate steps, plus a documented operator-resolution comment.
### Method
1. Add an init step that opens (and thereby creates, when first initialization) the dedup store through the shared loader with the resolved config; fail the script if the state is anything but `first_initialization` or `healthy` (e.g. `legacy_or_unverified` on an old pre-change file must abort with the archive-and-recreate message).
2. Verify after creation: store file exists, `PRAGMA user_version = 1`, `store_meta` row present, marker file present.
3. Add a comment block (and `usage`/echo text) pointing operators to the db_08 runbook (row 18) for `lost`/`replaced`/`schema_mismatch` resolution; the resolution operation itself is a manual store-API call, not an automated script step.
### Details
- `deploy/init_db.sh` contains no dedup/mcp references today (verified 2026-11-21); it already hosts the workflow schema fingerprint gate, so the new step follows the same gate/abort idiom.
- Executed 2026-11-21: the step runs an inline `uv run python` heredoc (no new helper tool; the procedure's earlier draft reference to a `tools/normalize_path.py` helper was a hallucination — no such tool exists or is needed; the store path comes from the loader, not from shell path arithmetic). It verifies `PRAGMA user_version = 1`, a `store_meta` identity row, and the `.mcp_dedup_installed` marker, and aborts with the archive-and-recreate/operator-runbook message on any refused open.
- Follow-up fix uncovered by the sandbox test: `DedupStore.__init__` previously executed `PRAGMA journal_mode = WAL` before start-state classification, which rewrites the database header of a legacy store it is about to refuse. The pragma now runs only after `_classify_or_create()` succeeds, so refused opens are strictly read-only (ADR-008 fail-closed). Healthy and first-initialization stores still end in WAL mode.

## Compatibility considerations
- A pre-existing pre-change store file causes an explicit abort (legacy gate), never a silent mutation (ADR-008: the software never mutates/archives/deletes databases; the operator does).

## Security considerations
- Deterministic creation at deploy time removes the race where the first tool call under load creates the store mid-dispatch.
