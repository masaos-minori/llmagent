## Goal

Add the schema-2.0 per-tool metadata contract to all 4 entries in
`scripts/mcp_servers/github/tools_file.py`'s `TOOL_LIST`, marking
`github_get_file_contents` read-only and `github_create_or_update_file`,
`github_push_files`, `github_delete_file` state-changing, all scoped
`resource_scope_kind="github_repo"`, `resource_scope_keys=["owner","repo"]`.

## Scope

In scope: the 4 dict literals inside `TOOL_LIST` (lines 9-140) —
`github_get_file_contents` (11-37), `github_create_or_update_file` (39-70),
`github_push_files` (72-110), `github_delete_file` (112-139). Out of scope: the
GitHub API client/auth logic elsewhere in the github-mcp server.

## Assumptions

- None of the 4 entries currently declare any of the 4 new fields (confirmed:
  `rg "is_write|requires_serial|resource_scope"` on this file returns no hits) —
  fully missing on all 4.
- All 4 entries require both `owner` and `repo` in their `inputSchema` (confirmed by
  reading each entry's `required` list: `["owner","repo","path"]`,
  `["owner","repo","path","content","message"]`, `["owner","repo","branch","files","message"]`,
  `["owner","repo","path","message","sha"]` respectively), so
  `resource_scope_keys=["owner","repo"]` is valid for all 4 (unlike the two
  cross-repository search tools handled in `tools_repository.py`'s document, none of
  this module's tools lack owner/repo).
- Only `github_get_file_contents` is read-only — confirmed by description ("Retrieve
  the contents of a specific file...") vs. the other 3 ("Create or update a file...",
  "Push multiple files as a single commit...", "Delete a file...").

## Design decisions

- `github_get_file_contents`: `is_write=False`, `requires_serial=False`,
  `resource_scope_kind="github_repo"`, `resource_scope_keys=["owner", "repo"]`.
- `github_create_or_update_file`, `github_push_files`, `github_delete_file`:
  `is_write=True`, `requires_serial=False`, `resource_scope_kind="github_repo"`,
  `resource_scope_keys=["owner", "repo"]` — per the plan's instruction that all
  mutating calls in the GitHub modules get repository-level scope. `path` (the
  specific file touched) is deliberately not added to `resource_scope_keys` — the
  plan's per-module instruction specifies repository-level scope only (`["owner",
  "repo"]`), not file-level, for these 4 modules (contrast with the file-server's
  `move_file`, which the plan explicitly calls out for dual-key file-level scope);
  this document follows the plan's literal instruction rather than introducing a
  finer-grained scope not specified there.

## Alternatives considered

Considered adding `path` as a third scope key for `github_create_or_update_file`/
`github_delete_file` (both operate on one file path) for finer-grained conflict
detection than whole-repository — rejected: the plan's explicit per-module
instruction for all 4 GitHub tool modules is uniformly repository-level
(`["owner","repo"]`), and `github_push_files` operates on a list of files (no single
`path` key exists in its schema — it has `files` instead), so a uniform
`["owner","repo"]` across the module is both what the plan specifies and the only
shape common to all 3 write tools without a special-case for `github_push_files`.

## Security considerations

Correctly marking the 3 mutating file operations `is_write=True` with repository-level
scope lets the future scheduler serialize concurrent file mutations against the same
`owner`/`repo` (e.g. two `github_create_or_update_file` calls, or a `github_push_files`
racing a `github_delete_file`, on the same repository). Repository-level (not
file-level) granularity is a conservative choice consistent with the plan's directive
to "favor conservative correctness" — it may over-serialize two file-disjoint writes
to the same repo, which is safe (just less parallel) rather than under-serializing.

## Rollback considerations
