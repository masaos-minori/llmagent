## Goal

Add the schema-2.0 per-tool metadata contract to all 5 entries in
`scripts/mcp_servers/github/tools_issues.py`'s `TOOL_LIST`, marking
`github_create_issue` and `github_add_issue_comment` state-changing (scoped
`resource_scope_kind="github_repo"`, `resource_scope_keys=["owner","repo"]`), the
repo-addressable reads (`github_list_issues`, `github_get_issue`) similarly scoped
but read-only, and the cross-repository `github_search_issues` unscoped.

## Scope

In scope: the 5 dict literals inside `TOOL_LIST` (lines 9-125) —
`github_list_issues` (11-30), `github_get_issue` (32-47), `github_create_issue`
(49-78), `github_search_issues` (80-101), `github_add_issue_comment` (103-124). Out
of scope: the GitHub API client/auth logic elsewhere in the github-mcp server.

## Assumptions

- None of the 5 entries currently declare any of the 4 new fields (confirmed:
  `rg "is_write|requires_serial|resource_scope"` on this file returns no hits) —
  fully missing on all 5.
- `github_list_issues`, `github_get_issue`, `github_create_issue`,
  `github_add_issue_comment` all require both `owner` and `repo` (confirmed by each
  entry's `required` list) — scope-eligible.
- `github_search_issues` (80-101) has only `query`/`per_page` properties, no
  `owner`/`repo` (confirmed by reading the entry) — it is a keyword search "across
  all of GitHub" per its own description, matching the same cross-repository-search
  pattern as `tools_repository.py`'s `github_search_repositories`/`github_search_code`,
  so it is treated as unscoped for the same reason (no resolvable per-repository
  scope key exists in its schema).
- Only `github_create_issue` and `github_add_issue_comment` mutate state — confirmed
  by description ("Create an issue...", "Post a comment...") vs. the other 3
  ("Retrieve the list of issues...", "Retrieve a specific issue...", "Keyword
  search...").

## Design decisions

- `github_create_issue`, `github_add_issue_comment`: `is_write=True`,
  `requires_serial=False`, `resource_scope_kind="github_repo"`,
  `resource_scope_keys=["owner", "repo"]`.
- `github_list_issues`, `github_get_issue`: `is_write=False`,
  `requires_serial=False`, `resource_scope_kind="github_repo"`,
  `resource_scope_keys=["owner", "repo"]` — scoped for descriptive accuracy even
  though read/read never becomes a conflict-graph edge (UNK-05 resolution).
- `github_search_issues`: `is_write=False`, `requires_serial=False`,
  `resource_scope_kind=""`, `resource_scope_keys=[]` — unscoped, consistent with the
  cross-repository-search precedent established for `tools_repository.py`'s two
  search tools and the plan's `web_search_tools.py` row.

## Alternatives considered

Considered scoping `github_add_issue_comment` additionally by `issue_number` (it
targets one specific issue, not the whole repo) — rejected: the plan's per-module
instruction is uniformly repository-level (`["owner","repo"]") across all 4 GitHub
tool modules; introducing issue-level granularity here alone would be inconsistent
with the plan's stated scope and is not requested by it.

### Method

Direct literal-dict edits, one insertion per entry (5 total), no new imports/helpers.

### Details

- `github_list_issues` currently ends (lines 25-30):
  ```python

      },

  ```

- `github_create_issue` (`required": ["owner", "repo", "title"]`) gets the
  write-scoped block (`is_write=True`).
- `github_search_issues` (`required": ["query"]`) gets the unscoped block
  (`resource_scope_kind=""`, `resource_scope_keys=[]`).
- `github_add_issue_comment` (`required": ["owner", "repo", "issue_number", "body"]`)
  gets the write-scoped block.

## Compatibility considerations

Additive-only. No existing test parametrizes over `mcp_servers.github.tools_issues`

## Security considerations

Correctly marking `github_create_issue`/`github_add_issue_comment` as `is_write=True`
with repository-level scope lets the future scheduler serialize concurrent issue
mutations against the same repository. Leaving `github_search_issues` unscoped
(rather than an invalid `owner`/`repo` scope it has no matching schema property for)
avoids a validator rejection.

## Rollback considerations

Trivial: revert the 5 additive blocks. No other file depends on these fields yet.
