## Goal

Update `rules/coding.md` with a standard deprecation-to-removal interval policy. This establishes a repo-wide convention ensuring deprecated symbols are removed within a predictable timeframe.

## Scope

- Add a new subsection under "Mandatory conventions" or as a standalone section titled "Deprecation policy" in `rules/coding.md`.

### Out-of-Scope

## Assumptions

- The zero-production-caller status for `LlmTransportErrorHandler.resolve_retryable` confirmed via `rg` on 2026-08-14 still holds at implementation time.
- No repo-wide policy currently defines a standard deprecation-to-removal interval (verified: `rules/coding.md` contains no such policy).
- The recommended approach — repo-wide default ("deprecated symbols are removed the next time `plans/` touches the same file for an unrelated reason, provided a zero-caller `rg` re-check still holds") — is acceptable to maintainers.

## Design decisions

- Place the deprecation policy as a standalone section titled "Deprecation policy", consistent with the existing structure of `rules/coding.md` (Mandatory conventions is a table-only section; a new subsection cannot be added beneath it).
- Use English-only comments consistent with the project's coding conventions.
- The policy text is concise and actionable, specifying exactly when deprecated symbols should be removed.

## Alternatives considered

- **Fixed-duration policy**: Could define a fixed duration (e.g., "30 days", "next major version"), but this would require a separate mechanism to track elapsed time since deprecation, which does not exist in this repo.
- **Separate policy document**: Could create a separate `rules/deprecation-policy.md`, but the requirement specifies adding it to `rules/coding.md` alongside other mandatory conventions.
- **Inline docstring annotation**: Could add the removal trigger to the method's docstring, but the requirement explicitly specifies placing it near the `warnings.warn` call.

## Implementation

### Target file

`rules/coding.md`

### Procedure

1. Open `rules/coding.md` and locate the "Mandatory conventions" section (lines 3-14).
2. After the "Mandatory conventions" section (after line 14), add a new top-level section titled "Deprecation policy".
3. The new section should appear as:

```markdown
## Deprecation policy

Deprecated symbols are removed the next time `plans/` touches the corresponding file for an
unrelated reason, provided a zero-caller `rg` re-check still holds. This applies to all
future deprecations unless a different interval is explicitly documented in the deprecation
comment itself.
```

4. Verify the formatting is correct by running `uv run ruff format rules/coding.md`.

### Method

The deprecation policy establishes a repo-wide convention for removing deprecated symbols. It ties removal to natural maintenance opportunities (when someone else is already touching the file for an unrelated reason) rather than arbitrary time-based deadlines. The zero-caller `rg` re-check provides a safety gate — removal only proceeds if no new callers have appeared.

This approach is consistent with the repo's existing practice of using `plans/` entries as implementation tracking artifacts, and avoids adding new tooling or infrastructure.

### Details

- The policy spans three lines to keep each line under 120 characters (consistent with the project's max line length rule).
- The policy uses lowercase "rg" (not "RG") to match the project's convention of using lowercase tool names in comments.
- The policy includes an escape hatch: "unless a different interval is explicitly documented in the deprecation comment itself" — allowing for exceptions when justified.
- The policy is placed as a top-level section after "Mandatory conventions" to emphasize its importance and ensure visibility during code review.
