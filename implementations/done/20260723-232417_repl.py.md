## Goal

Fix inconsistent signal handler installation when `add_signal_handler()` fails on Windows by making each signal handler registration independent.

## Scope

**In-Scope**:
- Replace try/except wrapping both `add_signal_handler()` calls with per-signal try/except logic

**Out-of-Scope**:
- Adding new signal handlers
- Modifying `_sigterm_handler()` behavior
- Adding configuration options

## Assumptions

1. `signal.SIGTERM` and `signal.SIGINT` are always available on all platforms.
2. The lambda `lambda *_: _sigterm_handler()` correctly ignores signal arguments (which it does not need).
3. `import signal as _signal` inside the except block works correctly on Windows.

## Design decisions

- **Per-signal try/except**: Each signal handler is registered independently — if one fails, the other still gets installed. This prevents partial failure where only SIGTERM would be registered.
- **Move `import signal as _signal` outside the try/except**: Eliminates the need for conditional import inside except block. Since `signal` is a stdlib module, there's no risk of circular import at module level.
- **Use `loop.add_signal_handler()` preferred path**: On Unix-like systems, `add_signal_handler()` is preferred because it integrates with asyncio's event loop. Only fall back to `signal.signal()` on Windows where `add_signal_handler()` raises `NotImplementedError`.

## Alternatives considered

- **Keep single try/except with fallback**: Simpler but has the partial failure bug — if SIGTERM succeeds and SIGINT fails, only SIGTERM is registered. Rejected due to inconsistency.
- **Always use `signal.signal()` regardless of platform**: Would work everywhere but loses asyncio integration benefits on Unix. Chose platform-aware approach.
- **Check `sys.platform` before choosing handler method**: Adds complexity and potential for bugs. Chose exception-based detection instead.
