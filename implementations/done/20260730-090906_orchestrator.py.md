## Goal

Convert ToolLoopGuard from a hard turn-failure into a controlled final-answer fallback: when the guard detects repeated/cyclic/retrying tool calls, inject a temporary system message and call the LLM once more without tool definitions, allowing the LLM to produce a final answer using only information already available in the conversation.

## Scope

**In-Scope:**
- Normalize `error_kind` derivation when `TurnResult.action != "continue"`

**Out-of-Scope:**
- Changes to existing guard detection logic (cycle/dedup/retry/error_limit checks remain unchanged)
- Changes to `ToolLoopGuard.check_error_limit()` behavior
- Changes to diagnostic recording beyond what is required by the new flow
- Changes to MCP server configurations or deploy scripts

## Assumptions

1. The ephemeral system message injected by the guard should use the same ephemeral-key filtering mechanism (`_ephemeral`) already used by command handlers, so it will be cleaned up automatically between turns.
2. `LLMClient.stream()` accepts an empty `tool_defs=[]` and produces a non-tool-calls response — this is the standard OpenAI-compatible API behavior.
3. The temporary system message content defined in the requirement doc is sufficient; no additional wording refinement is needed.
4. A single final-answer attempt is enough — if the LLM still returns tool calls, the turn fails safely without further retries.

## Design decisions

- **Error_kind normalization**: Derive `error_kind` from `result.error_kind or result.reason or result.action` in `Orchestrator._handle_llm_turn()` to ensure consistent error metadata downstream.

## Alternatives considered

- **Keep existing error_kind derivation**: Could keep the existing behavior where `error_kind` is derived from `result.error_kind` alone. Rejected because it would cause inconsistency when `result.error_kind` is None but `result.reason` or `result.action` provides the error context.
