## Goal

Decouple stampede protection from error propagation so that transient failures affect only the initiating request, not concurrent waiters. Add retry logic for transient errors while preserving cache consistency.

## Scope

- Modify `_execute_with_stampede_protection()` to not propagate exceptions to waiters
- Remove failed inflight future and allow each waiter to make independent calls
- Add retry mechanism for TransportError with exponential backoff
- Delay server health registry updates for transient errors

## Assumptions

- Retry attempts should use exponential backoff starting at 1 second
- Maximum retry attempts should be configurable (default: 3)
- Server health registry updates should be delayed by 5 seconds after transient error
- Concurrent waiters should be allowed to retry independently without waiting for original request completion

## Design decisions

- **Independent waiter retry**: When a TransportError occurs, remove the inflight future and allow each waiter to make its own attempt. This prevents all waiters from failing due to one transient error.
- **Exponential backoff retry**: Use 1s, 2s, 4s backoff for up to 3 retries. This balances between rapid recovery and avoiding overwhelming a recovering server.
- **Delayed health registry update**: Defer server health status updates by 5 seconds for transient errors. If the request succeeds within this window, cancel the health update. This prevents premature server marking as unhealthy.
- **Cache consistency during retry**: Mark cache entries as "pending_retry" during retry window to prevent stale reads.

## Alternatives considered

- **Propagate exception to all waiters**: Would fail all concurrent requests on any error. Too aggressive for transient failures. Rejected due to poor availability.
- **Circuit breaker pattern**: More sophisticated than simple retry but adds complexity. Exponential backoff sufficient for most transient failure scenarios.
- **Immediate health registry update**: Would mark servers unhealthy immediately on first error. Too aggressive; transient errors don't indicate persistent problems.
- **Global retry pool**: Share retry attempts among waiters. Complex coordination overhead. Independent retries simpler and more resilient.

   ```python
   async def _execute_with_stampede_protection(self, cache_key, ...):
       # ... existing inflight check logic ...
       
       try:
           result = await self._raw_execute(...)
           
           # Success: cancel any pending health registry update
           await self.server_health_registry.cancel_transient_update(cache_key)
           
           return result
           
       except TransportError as e:
           # Transient error: do NOT propagate to waiters
           logger.warning(f"Stampede protection: transient error for {cache_key}, allowing retries")
           
           # Remove inflight future to allow independent retries
           self._inflight.pop(cache_key, None)
           
           # Delay server health registry update
           await self.server_health_registry.defer_transient_update(cache_key, delay=5)
           
           # Attempt retry with exponential backoff
           return await self._retry_with_backoff(cache_key, ...)
   
   async def _retry_with_backoff(self, cache_key, ..., max_retries=3):
       """Retry with exponential backoff for transient errors."""
       last_exception = None
       for attempt in range(max_retries):
           try:
               # Check server health before retrying
               if not await self.server_health_registry.is_server_healthy(cache_key):
                   logger.warning(f"Server unhealthy for {cache_key}, skipping retry {attempt + 1}")
                   break
               
               result = await self._raw_execute(...)
               
               # Success: cancel pending health update
               await self.server_health_registry.cancel_transient_update(cache_key)
               return result
               
           except TransportError as e:
               last_exception = e
               if attempt < max_retries - 1:
                   backoff_time = 2 ** attempt  # 1, 2, 4 seconds
                   logger.info(f"Retry {attempt + 1}/{max_retries} for {cache_key} after {backoff_time}s")
                   await asyncio.sleep(backoff_time)
               else:
                   logger.error(f"All {max_retries} retries exhausted for {cache_key}: {e}")
       
       raise last_exception
   ```

## Compatibility considerations

- **Retry behavior change**: Existing callers expecting immediate failure on TransportError will now see delayed results. May affect timeout-sensitive workflows.
- **Health registry timing**: Servers may remain marked healthy longer during transient issues. Monitor for false negatives.
- **Cache status field addition**: New cache status values require schema migration if cache is persisted.

## Security considerations

- **Denial of service**: Retry mechanism could amplify load on recovering servers. Max retry limit mitigates this.
- **Stale data exposure**: Cache entries marked "pending_retry" must not serve stale data. Verify cache read paths respect this status.
- **Server health manipulation**: Ensure server health status cannot be manipulated by untrusted parties.

## Rollback considerations

- **Quick rollback**: Remove retry logic and revert to immediate exception propagation
- **Data impact**: No database changes; rollback does not affect persisted state
- **Configurable mode**: Consider adding environment variable to toggle retry behavior without code changes
