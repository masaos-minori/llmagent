# Implementation: `startup.py` — Warn on `pending_approval_task_id` Overwrite During Recovery

## Goal

Apply the same overwrite-protection warning used in `cmd_workflow.py::_cmd_approve()` to
`startup.py::_recover_pending_approvals()`, since this recovery path also assigns
`ctx.turn.pending_approval_task_id` unconditionally and can silently clobber a value set
earlier in the same session.

## Scope

**In scope:**
- `scripts/agent/startup.py::_recover_pending_approvals()`, the assignment
  `ctx.turn.pending_approval_task_id = task_id` (line 522).

**Out of scope:**
- `cmd_workflow.py::_cmd_approve()` overwrite warning (separate implementation doc; same
  pattern, different call site).
- `orchestrator.py::_init_workflow_task()` halted-task rejection (separate implementation
  doc).
- Any other part of `_recover_pending_approvals()` (approval-ID recovery, warning-message
  text) — already fixed by a prior implementation
  (`implementations/done/20260711-172521_startup_pending_approval_recovery_fix.md`), which
  added this exact assignment; this doc only adds the overwrite guard around it.
- `find_all_pending_approvals()` / `StateStore` query logic.

## Assumptions

- `_recover_pending_approvals()` runs once during agent startup, before any turn is
  processed, so in the normal case `ctx.turn.pending_approval_task_id` is still `None`
  at this point (fresh `AgentContext`/`TurnState`). An overwrite here would only occur if
  the field were already populated by some other startup-order interaction — this is
  exactly the "unknown" the plan flags (`UNK-02`), resolved here as: no confirmed active
  overwrite path exists today, but the guard is added defensively, matching the plan's
  explicit instruction to "apply same overwrite check in startup.py if needed" and the
  general principle "prevent silent overwriting" stated in the Goal.
- Consistent with `cmd_workflow.py`'s guard (see its implementation doc), a warning (not an
  exception) is the correct response — recovery must not fail startup.

## Design decisions

- Mirror the `cmd_workflow.py::_cmd_approve()` guard exactly (same log level, same
  before/after task-ID fields) for consistency across the two call sites that assign this
  field, per plan Risk 3 ("Add same overwrite protection to startup recovery path").
- Place the check immediately before the existing assignment at line 522, inside
  `_recover_pending_approvals()`, not in a shared helper — two call sites do not yet
  justify extracting a shared utility (YAGNI); revisit if a third site appears.

## Alternatives considered

- **Extract a shared `_warn_if_overwriting_pending_task(ctx, new_task_id)` helper used by
  both `cmd_workflow.py` and `startup.py`**: rejected for this cycle — the two modules
  belong to different layers of the same package (`agent.commands` vs `agent`) and each
  implementation doc here is scoped file-by-file per the workflow; introducing a shared
  helper across two separate procedure docs would create a hidden ordering dependency
  between them. Revisit as a follow-up refactor if a third overwrite site emerges.
- **Skip the check entirely since recovery runs before any turn**: rejected — the plan
  explicitly calls out this path as an open question (`UNK-02`) and instructs adding the
  same protection "if needed"; adding a low-cost defensive warning is cheaper than leaving
  the gap unaddressed, and matches the Goal's stated intent to prevent silent overwrites
  everywhere the field is assigned.

## Implementation

### Target file

`scripts/agent/startup.py`

### Procedure

1. In `_recover_pending_approvals()`, immediately before
   `ctx.turn.pending_approval_task_id = task_id` (line 522), add:
   ```python
   if ctx.turn.pending_approval_task_id is not None:
       logger.warning(
           "Overwriting pending_approval_task_id %s with %s during recovery",
           ctx.turn.pending_approval_task_id,
           task_id,
       )
   ```
2. No change to the existing `logger.warning(...)` call at lines 523-529 (recovered-count
   summary) or the `self._view.write_warning(...)` call at lines 530-534.

### Method

Direct in-place edit: one new `if` guard inserted before the existing assignment. No new
function, parameter, or import (module already uses `logger` at this call site, confirmed
`scripts/agent/startup.py:523`).

### Details

- Confirmed by direct read (`scripts/agent/startup.py:506-534`): the assignment at line 522
  is unconditional; no existing check for a pre-existing value.
- Keep new lines under 120 chars.
- Do not alter the message text/format of the two existing warnings in this function —
  those were already fixed by `implementations/done/20260711-172521_startup_pending_approval_recovery_fix.md`.

## Compatibility considerations

- No change to `AgentContext`/`TurnState` schema.
