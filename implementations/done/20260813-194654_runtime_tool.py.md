## Goal

Replace `RuntimeTool`'s singular `resource_scope: str` field (and the matching
`build_runtime_tool()` parameter) with two fields, `resource_scope_kind: str` and
`resource_scope_keys: tuple[str, ...]`, so a `RuntimeTool` declares *how* to compute a
call's resource scope (kind + which argument keys matter) rather than a single static
scope value baked in at discovery time.

## Scope

In scope: `scripts/shared/runtime_tool.py` only — the `RuntimeTool` dataclass field, the
`build_runtime_tool()` parameter/default/passthrough, and both the class and function
docstrings. Out of scope: `ToolSpec.resource_scope`/`resource_scopes` (separate target
file `tool_spec.py`), `resolve_resource_scopes()` itself (separate target file
`resource_scope.py`), and any call site outside this file (e.g.
`runtime_tool_registry.py::_build_tool_spec()`, MCP server `TOOL_LIST` population) —
those are covered by their own docs in this set or by later plan phases.

## Assumptions

- `resource_scope_kind=""` is the correct "unscoped" sentinel (mirrors the existing
  `resource_scope: str = ""`-default convention already used for other string fields in
  this same file, e.g. no direct precedent field but consistent with `description: str
  = ""`-style defaults elsewhere in the codebase).
  `resource_scope_keys=()` is the correct default for "no keys declared."
- No other field on `RuntimeTool` or `build_runtime_tool()` needs to change — this is a
  narrow one-field-becomes-two-fields split, not a broader schema change (the other three
  schema-2.0 fields, `is_write`/`requires_serial`, already exist; the fourth,
  `resource_scope`, is exactly the field being split here).
- 11 importers reference `shared.runtime_tool` repo-wide (per the plan's Affected-areas
  table); this doc only covers the definition site, not each importer — importer fixups
  belong to whichever doc/phase owns each importer file.

## Design decisions

- **Two fields, not one composite.** `resource_scope_kind: str` and
  `resource_scope_keys: tuple[str, ...]` are separate fields (not, say, a single
  `tuple[str, str, ...]` or a small dataclass) because `resource_scope_kind` is set once
  per tool (a classification) while `resource_scope_keys` is a list of argument-key
  names — keeping them as two plainly-typed fields matches the plan's Design section
  wording verbatim (`resource_scope_kind: str` + `resource_scope_keys: tuple[str, ...]`)
  and keeps `resolve_resource_scopes(tool, args)` (in the new `resource_scope.py`) able to
  destructure both without needing a third intermediate type.
- **Tuple, not list, for `resource_scope_keys`.** Matches `capabilities: tuple[str, ...]`,
  the existing tuple-typed field convention on this same frozen dataclass — keeps the
  whole dataclass hashable/immutable-safe.
- **No validation logic added here.** This file only holds the shape; the plan's shared
  contract validator (`validate_tool_schema_v2()`, in `resource_scope.py`) is the
  validation boundary, not `build_runtime_tool()`. `build_runtime_tool()` continues to
  apply only *safe defaults* for omitted fields, not correctness checks.

## Alternatives considered

Keeping `resource_scope: str` and adding a second `resource_scope_keys` field alongside
it (instead of renaming/splitting). Rejected: the plan's Affected-areas table and
Implementation steps both specify a straight replacement (`resource_scope: str` →
`resource_scope_kind: str` + `resource_scope_keys: tuple[str, ...]`), and keeping the old
field would leave two competing scope representations on the same dataclass, defeating
the plan's stated goal of eliminating disagreeing scheduling-metadata sources.

## Compatibility considerations

Any caller still passing `resource_scope=` as a keyword argument to `build_runtime_tool()`
or reading `.resource_scope` on a `RuntimeTool` instance breaks immediately (no
deprecated-alias shim is introduced — the plan's Risk section explicitly calls for an
atomic, not incremental, rename across `shared/` + `runtime_tool_registry.py` + all
direct consumers). This doc's scope is limited to the definition site; the plan's Risk
mitigation (re-run `rg "\.resource_scope\b" scripts/ tests/` after the full rename) is
the mechanism that catches any missed caller — this doc does not implement that repo-wide
sweep itself.
