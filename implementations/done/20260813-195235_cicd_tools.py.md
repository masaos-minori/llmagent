## Goal

Add the schema-2.0 per-tool metadata contract to all 4 entries in
`scripts/mcp_servers/cicd/cicd_tools.py`'s `TOOL_LIST`: `trigger_workflow` marked
state-changing with `resource_scope_kind="cicd_workflow"`,
`resource_scope_keys=["repo","workflow","ref"]` per the plan, and the 3 status/run/log
read tools marked read-only with a scope built from whichever identifying keys each
one's own schema actually has.

## Scope

In scope: the 4 dict literals inside `TOOL_LIST` (lines 11-119) — `trigger_workflow`
(13-47), `get_workflow_runs` (49-73), `get_workflow_status` (75-95),
`get_workflow_logs` (97-118). Out of scope: the actual GitHub Actions API dispatch/
polling logic elsewhere in the cicd-mcp server, and the `repo_allowlist` config gate
referenced in `trigger_workflow`'s description.

## Assumptions

- None of the 4 entries currently declare any of the 4 new fields (confirmed:
  `rg "is_write|requires_serial|resource_scope"` on this file returns no hits) —
  fully missing on all 4.
- `trigger_workflow` requires `repo` and `workflow`, with `ref` as an optional
  property (present in `inputSchema["properties"]` but not `required`) — confirmed
  by reading lines 19-44; the plan's exact instruction is
  `resource_scope_keys=["repo","workflow","ref"]`, which this document follows
  literally even though `ref` is optional at the JSON-Schema level (the future
  `resolve_resource_scopes()` in `scripts/shared/resource_scope.py`, not this file,
  is responsible for handling a missing optional key at call time, e.g. falling back
  to a default `ref` value or omitting it from the resolved scope string).
- `get_workflow_runs` requires `repo` and `workflow` (no `run_id`, no `ref`) —
  confirmed by its `required` list (line 69).
- `get_workflow_status` and `get_workflow_logs` both require `repo` and `run_id` (no
  `workflow`, no `ref`) — confirmed by their `required` lists (lines 91, 113).
- The plan's per-module row states only `trigger_workflow`'s exact scope-key triple;
  it does not specify scope keys for the 3 read tools beyond "status/run/log reads
  read-only." This document therefore makes an explicit, grounded design choice for
  the reads' scope keys (see Design decisions) rather than leaving them unscoped,
  since all 3 reads do have a `repo`-identifying argument available and declaring it
  keeps the schema meaningfully descriptive — but this choice should be flagged to
  the plan owner/reviewer as an implementer decision, not a literal plan quote, for
  these 3 specific tools.

## Design decisions

- `trigger_workflow`: `is_write=True`, `requires_serial=False`,
  `resource_scope_kind="cicd_workflow"`, `resource_scope_keys=["repo", "workflow", "ref"]`
  — verbatim per the plan's per-module row.
- `get_workflow_runs`: `is_write=False`, `requires_serial=False`,
  `resource_scope_kind="cicd_workflow"`, `resource_scope_keys=["repo", "workflow"]` —
  uses the 2 identifying keys actually present in its own schema (no `run_id`/`ref`
  property exists to include).
- `get_workflow_status`, `get_workflow_logs`: `is_write=False`,
  `requires_serial=False`, `resource_scope_kind="cicd_workflow"`,
  `resource_scope_keys=["repo", "run_id"]` — uses the 2 identifying keys actually
  present in each of their own schemas.
- `requires_serial=False` on all 4, including `trigger_workflow` — the plan's
  per-module row does not call for a global barrier on this tool (that treatment is
  reserved for `shell_tools.py` elsewhere in the plan); scope-based conflict
  detection (two `trigger_workflow` calls on the same `repo`/`workflow`/`ref` triple)
  is deemed sufficient.

## Alternatives considered

Considered leaving the 3 read tools unscoped (`resource_scope_kind=""`,
`resource_scope_keys=[]`), mirroring the GitHub modules' cross-repository search
tools — rejected: unlike those search tools, all 3 CI/CD reads do have a `repo`
property (and either `workflow` or `run_id`) in their schema, so a meaningful
`"cicd_workflow"`-kind scope is resolvable; declaring it (even though read/read pairs
never become conflict-graph edges) keeps the schema consistent with how the GitHub
modules scoped their own repo-addressable reads.

## Security considerations

Correctly marking `trigger_workflow` as `is_write=True` documents that it can
dispatch a real GitHub Actions run (subject to the existing `repo_allowlist` config
gate, unchanged by this file). Scoping it by `repo`/`workflow`/`ref` lets the future
scheduler serialize concurrent dispatches targeting the same workflow+ref, avoiding a
race where two dispatches with different `inputs` land on the same ref
simultaneously. This file makes no change to the `repo_allowlist` enforcement itself.

## Rollback considerations

Trivial: revert the 4 additive blocks. No other file depends on these fields yet.
