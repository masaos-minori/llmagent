# Implementation procedure: scripts/agent/llm_turn_runner.py

## Goal

Route `llm_turn_runner.py`'s two assistant-message append sites — the
tool-call branch in the main turn loop and `_finalize_answer_text()` — through
`ConversationState.append_message()`.

## Scope

- In scope:
  - Main turn loop, tool-call branch (currently L95):
    `ctx.conv.history.append(message)`, where `message` is the streamed LLM
    response's assistant message (with `tool_calls` set).
  - `_finalize_answer_text()` (currently L199-203):
    `ctx.conv.history.append(message)`, the done-turn assistant message.
- Out of scope: `execute_all_tool_calls()` (covered by the `tool_runner.py`
  procedure doc), `_stream_llm()`/`LlmReconnectHandler` streaming-accumulation
  internals in `shared/llm_client.py`.

## Assumptions

- Both `message` dicts originate from `response.message` (turn-loop branch,
  L88) or the equivalent finalize-path value — both are constructed in-repo by
  the streaming accumulation logic (`shared/llm_client.py` /
  `LlmReconnectHandler`) from typed deltas, not passed through arbitrary
  provider JSON (plan Assumption 3). They therefore already contain only
  `role`/`content`/`tool_calls`, matching `ROLE_KEY_WHITELIST["assistant"] =
  {"role", "content", "tool_calls"}` (confirmed, `message_schema.py`).
- Confirmed by direct read (`scripts/agent/llm_turn_runner.py:88-99` and
  `199-203`): no ephemeral keys are ever present on these messages; no
  `source` is needed at either call site.

## Design decisions

- Turn-loop tool-call branch (L95): replace `ctx.conv.history.append(message)`
  with `ctx.conv.append_message(message)`, no `source`.
- `_finalize_answer_text()` (L202): replace `ctx.conv.history.append(message)`
  with `ctx.conv.append_message(message)`, no `source`.
- No sanitization is expected in either case given Assumption 3/the confirmed
  key set — this item's value is closing the audit gap and providing a
  regression guard (via the new test in Validation plan) against a future
  change to the streaming accumulation logic silently starting to pass through
  raw provider fields.

## Alternatives considered

- **Skip this file since messages are always well-formed today.** Rejected:
  the requirement's goal is that *every* history-construction call site is
  validated, not just the ones handling untrusted input today — this closes
  the gap and creates a regression guard for future streaming-logic changes
  (plan Risk: "Routing llm_turn_runner.py's streamed assistant messages
  through strict validation could reject/strip a legitimate provider-specific
  field if the LLM client's accumulation logic ever changes").

## Implementation

### Target file

`scripts/agent/llm_turn_runner.py`

### Procedure

1. In the main turn loop (currently L95), replace
   `ctx.conv.history.append(message)` with `ctx.conv.append_message(message)`.
2. In `_finalize_answer_text()` (currently L202), replace
   `ctx.conv.history.append(message)` with `ctx.conv.append_message(message)`.

### Method

Two independent one-line substitutions; no change to `response.message`
construction, `finish_reason`/`has_tool_calls` branching (L88-93), or the
subsequent `ctx.session.save(...)` / `execute_all_tool_calls(...)` calls
(L96-115).

### Details

- Both call sites are `self`-methods on the turn-runner class holding `ctx`;
  no new import needed.
- `_finalize_answer_text()` is only reached when `finish_reason != "tool_calls"`
  or `not has_tool_calls` (L91-92); the turn-loop append (L95) is only reached
  on the opposite branch — the two call sites are mutually exclusive per turn
  iteration, not both hit for the same `message`.

## Compatibility considerations

- No behavior change expected: both message shapes already fully satisfy
  `ROLE_KEY_WHITELIST["assistant"]`, so validation always succeeds and the
  stored message is byte-identical to what raw `.append()` would have stored.
- `ctx.session.save("assistant", ..., tool_calls=...)` (L96-99, DB persistence)
  is unrelated to `ctx.conv.history` and untouched by this item.

## Security considerations

- Closes the two `llm_turn_runner.py`-owned gaps named in the requirement.
- Provides an early-warning mechanism (via `append_message()`'s `warning` log
  on sanitization) if a future change to the LLM streaming client ever starts
  passing through raw provider JSON with unexpected fields — this is the
  concrete plan Risk this item mitigates.

## Rollback considerations

- Both substitutions are independent single-line reverts with no data
  migration, since stored message shape is unchanged for well-formed input.

## Validation plan

- Extend `tests/test_llm_turn_runner.py` with a regression test confirming
  assistant messages (both the tool-call branch and the finalize-answer
  branch) still land in `ctx.conv.history` unchanged after routing through
  `append_message()`.
- `pytest tests/test_llm_turn_runner.py -q` — all pass.
- `pytest -k "llm_turn_runner" -q` — all pass (per plan's Regression tests
  row).
- `ruff check scripts/agent/llm_turn_runner.py`, `mypy

## Out of scope

- `execute_all_tool_calls()` and any `tool_runner.py` history mutation
  (covered by the `tool_runner.py` procedure doc).
- `shared/llm_client.py` / `LlmReconnectHandler` streaming-accumulation
  internals.
