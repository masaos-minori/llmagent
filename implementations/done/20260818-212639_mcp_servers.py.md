Part B — Update `build_tools_response()`:

```python
def build_tools_response(
    tools: Sequence[McpTool],
    server_key: str,
    include_disabled: bool = False,
    disabled_code: str | None = None,
) -> dict[str, Any]:
    """Build the /v1/tools response with optional visibility filtering."""
    filtered = tools
    
    # Filter out disabled tools unless explicitly requested
    if not include_disabled:
        filtered = [t for t in filtered if t.get("enabled", True)]
    
    # Further filter by disabled_code if specified
    if disabled_code is not None:
        filtered = [t for t in filtered if t.get("disabled_reason") == disabled_code or t.get("enabled", True)]
    
    return {
        "tools": [tool for tool in filtered],
    }
```

### Details

- `McpTool` is a TypedDict (not BaseModel) because existing callers use dict literals, not model instantiation.
- `McpToolProperty` is a TypedDict for the property key/value annotations used by `git_tools.py` and `cicd_tools.py`.
- Filtering happens after tool collection but before serialization — minimal impact on existing code paths.
- `disabled_code` filter includes both matching disabled tools AND all enabled tools — ensures operators can see which tools are available alongside those with specific failure modes.

## Compatibility considerations

- Adding `enabled`/`disabled_reason` fields to `McpTool` is backward compatible — Pydantic allows extra fields by default unless `extra="forbid"` is set.
- Default `enabled=True` means existing clients see no change in tool availability.
- New `include_disabled`/`disabled_code` params are optional — existing callers work unchanged.
- Disabled tools are excluded from the default response — clients that don't request them won't see them.

## Security considerations

- Visibility filtering does not affect authentication/authorization — disabled tools may still be callable via `/v1/call_tool` if the caller has permission.
- `disabled_code` values are informational only — no security boundary enforcement.
