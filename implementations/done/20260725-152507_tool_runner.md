## Goal

Add schema-based validation for LLM-generated tool call arguments before they reach MCP servers. Reject tool calls that contain unexpected or invalid fields according to the MCP tool definition's inputSchema, preventing argument injection attacks.

## Scope

- Add argument validation in `scripts/agent/tool_runner.py` after `orjson.loads(args_str)` parsing
- Validate against MCP tool inputSchema stored in `RuntimeTool.input_schema`
- Reject tool calls with extra fields not defined in the schema
- Log warnings for rejected tool calls with details about which fields were rejected
- Graceful handling of validation failures (no session crash)
- Optional custom validation rules per tool via RuntimeTool field extension

## Assumptions

- RuntimeTool.input_schema contains valid JSON Schema format compatible with standard validators
- The validation should happen at the tool_runner layer, not in tool_executor, because it needs access to the specific tool's schema
- Extra fields should be rejected by default (strict mode); allowing extra fields can be opt-in per tool
- Validation errors should be logged but not crash the session; the tool call should be returned as an error result

## Design decisions

- **Validation location**: Place validation in `execute_one_tool_call()` after `orjson.loads()`, before calling `tool_executor.execute()`. This ensures all tool calls pass through validation regardless of how they originate.
- **Strict mode by default**: Reject extra fields by default (`allow_extra_fields=False`). This provides defense-in-depth against argument injection. Tools that need extra fields can opt-in via `allow_extra_fields=True`.
- **Validation result object**: Use a dedicated `ValidationResult` class instead of raising exceptions. This allows clean separation between validation logic and execution flow, and enables detailed error reporting.
- **Fallback to lenient mode**: When schema is missing or malformed, fall back to lenient mode (accept all fields). This prevents blocking legitimate tool calls due to incomplete MCP tool definitions.

## Alternatives considered

- **Raise exception on validation failure**: Would require try/catch in every caller and risk session crashes. Chose ValidationResult pattern instead for graceful degradation.
- **Validate in tool_executor**: Would require passing schema information to executor layer. Placing validation in tool_runner keeps schema-aware logic closer to where tool calls are dispatched.
- **Use pydantic models**: Pydantic would provide rich validation but adds dependency weight. JSON Schema validation via `jsonschema` library is more aligned with MCP tool definition format.
- **Log-only mode first**: Could start with logging-only mode and switch to reject later. However, implementing reject mode from the start avoids rework and the fallback-to-lenient mitigates breakage risk.

## Compatibility considerations

- **Backward compatibility**: Fallback to lenient mode when schema is missing/malformed prevents breaking existing tools
- **MCP server compatibility**: Some MCP servers may have incomplete schemas; lenient fallback handles this gracefully
- **Existing tool behavior**: Strict mode may cause previously silent failures to become visible; monitor during rollout

## Security considerations

- **Argument injection prevention**: Primary security goal of this change
- **Schema tampering**: Ensure RuntimeTool.input_schema cannot be modified by untrusted sources
- **Denial of service**: Lenient fallback prevents attackers from exploiting malformed schemas to block all tool calls
- **Information disclosure**: Validation error messages should not expose internal schema details to LLM

## Rollback considerations

- **Quick rollback**: Remove validation import and bypass call in execute_one_tool_call()
- **Data impact**: No database changes; rollback does not affect persisted state
- **Configurable mode**: Consider adding environment variable to toggle strict/lenient mode without code changes
