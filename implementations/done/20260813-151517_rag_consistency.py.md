## Goal

Refactor `scripts/db/rag_consistency.py` to compute set-based diffs independently of aggregate count thresholds, eliminating blind spots where equal-count gap/orphan cancellation hides discrepancies.

## Scope

**In-Scope:**
- Move EXCEPT query computations outside of `fts_gap > 0` / `orphan_vec_count > 0` conditionals in `_collect_affected_identifiers()`.
- Always collect affected identifiers from set-based diffs regardless of aggregate count values.
- Keep aggregate counts as supplementary information.

**Out-of-Scope:**
- Adding new fields to `RagConsistencyReport` (handled in separate document).
- Modifying source code behavior beyond diagnostic improvements.
- Updating documentation (`docs/*.md`).

## Assumptions

- SQLite 3.35+ is available (already required for vec0), supporting EXCEPT queries.
- LIMIT 10 on EXCEPT queries prevents unbounded memory usage for large tables.
- Existing callers of `check_rag_consistency()` accept the updated report structure without breaking.

## Design decisions

- **Unconditional diff computation**: Compute set-based diffs always, even when aggregate counts show zero discrepancy. This eliminates the blind spot where gaps and orphans cancel each other out.
- **Keep aggregate counts**: Aggregate counts remain as supplementary information for quick diagnostics without running expensive EXCEPT queries.
- **LIMIT 10 preserved**: Maintain existing LIMIT 10 on all EXCEPT queries to prevent memory blow-up.

## Alternatives considered

- **Conditional computation based on heuristic threshold**: Would reintroduce the same blind spot. Rejected.
- **Full enumeration without LIMIT**: Too slow for large databases. Rejected.
- **Separate diagnostic mode flag**: Adds complexity for marginal benefit. Rejected.

### Details

- Both EXCEPT queries now run unconditionally. When there are no discrepancies, they return empty result sets, and the corresponding identifier tuples become `None` via the `if rows else None` pattern.
- Empty result sets produce empty tuples `()`, which differ from `None`. The downstream code in `summarize_issues()` checks `if report.affected_chunk_ids:` etc., so empty tuples will be treated as falsy (correct behavior).
- Performance impact: For consistent databases, two additional EXCEPT queries execute per check. These are typically fast for moderate-sized tables; profile if needed.

## Compatibility considerations

- Return value change: When no discrepancy exists, `affected_chunk_ids` changes from `None` (when `fts_gap == 0`) to `None` (empty result → `None` via `if rows else None`). Semantically identical.
- When discrepancy exists, behavior is unchanged — identifiers are collected the same way.
- No API contract change to `check_rag_consistency()` signature.

## Security considerations

N/A — read-only SQL queries only. No user input involved.

## Rollback considerations

- Simple revert: restore the `if fts_gap > 0:` and `if orphan_vec_count > 0:` guards.
- No data migration or schema change involved.
- No backward compatibility risk since `None` vs empty tuple distinction is handled by truthiness checks in `summarize_issues()`.
