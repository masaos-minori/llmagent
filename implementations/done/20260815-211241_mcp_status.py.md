# Implementation Procedure: Replace UNKNOWN fallback with UNAVAILABLE in _resolve_health_state()

## Goal

Replace the UNKNOWN fallback in `_resolve_health_state()` with UNAVAILABLE when the registry is None, providing clearer semantics during startup/shutdown phases.

## Scope

- `scripts/agent/services/mcp_status.py`: `_resolve_health_state()` function only
- Docstring update referencing the fallback state

## Assumptions

1. `McpServerHealthState.UNAVAILABLE` semantically means "server unavailable due to health probe failures" (`mcp_health.py:43`), NOT "registry doesn't exist"
2. The status table display logic can handle UNAVAILABLE state properly
3. No other code depends on UNKNOWN being returned specifically for the None-registry case

## Design decisions

- Change the single return value in the None-registry branch from `UNKNOWN` to `UNAVAILABLE`
- Keep the function signature unchanged; this is a pure semantic change within an existing code path
- Update the docstring to reflect the new fallback state name

## Alternatives considered

- Adding a new `NO_REGISTRY` state to distinguish "registry doesn't exist" from "health probe failure" — rejected because it would require changes across multiple files (enum definition, status table rendering, all callers) and adds complexity for marginal benefit
- Keeping UNKNOWN — rejected because it misrepresents the actual condition

## Implementation

### Target file

`scripts/agent/services/mcp_status.py`

### Procedure

1. Read `scripts/agent/services/mcp_status.py` to confirm the current UNKNOWN fallback location (line 52)
2. Read `scripts/shared/mcp_health.py` to verify `McpServerHealthState.UNAVAILABLE` exists and its meaning
3. Search for all callers of `_resolve_health_state()` to ensure they don't depend on UNKNOWN
4. Modify the return statement on line 52 from `McpServerHealthState.UNKNOWN` to `McpServerHealthState.UNAVAILABLE`
5. Update the docstring on line 49 from "falling back to UNKNOWN" to "falling back to UNAVAILABLE"
6. Verify no other callers depend on UNKNOWN being returned specifically for the None-registry case
7. Run tests to ensure no regressions

### Method

Single-line change in the None-registry guard branch.

### Details

```python
# Before (line 49, 52):
def _resolve_health_state(ctx: AgentContext, key: str) -> McpServerHealthState:
    """Get the health state for a server, falling back to UNKNOWN."""
    registry = ctx.services_required.health_registry
    if registry is None:
        return McpServerHealthState.UNKNOWN
    return cast(McpServerHealthState, registry.get_state(key))

# After:
def _resolve_health_state(ctx: AgentContext, key: str) -> McpServerHealthState:
    """Get the health state for a server, falling back to UNAVAILABLE."""
    registry = ctx.services_required.health_registry
    if registry is None:
        return McpServerHealthState.UNAVAILABLE
    return cast(McpServerHealthState, registry.get_state(key))
```

## Compatibility considerations

- Callers that compare against `McpServerHealthState.UNKNOWN` will see different values after this change
- The status table display must already support UNAVAILABLE (it does, per mcp_health.py line 43)
- No API contract change; the function signature remains identical

## Security considerations

N/A — no security impact. This is a semantic improvement to error reporting.

## Rollback considerations

Reverting is straightforward: restore the original `UNKNOWN` return value and docstring text.

## Validation plan

- Integration test: status table display during startup/shutdown shows UNAVAILABLE for all servers
- Manual verification: grep confirms no other code depends on UNKNOWN for the None-registry case

## Out of scope

- Changes to status table rendering logic
- Changes to any caller of `_resolve_health_state()` beyond what is necessary for this semantic change
