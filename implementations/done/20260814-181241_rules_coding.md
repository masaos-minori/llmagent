# Implementation Procedure: Add git.exc Import Guard Constraint to rules/coding.md

## Goal

Add a constraint check pattern in `rules/coding.md` §Constraint checks that flags any file matching `import git` where `git\.exc\.` appears in the body but `import git.exc` does not. This prevents future contributors from silently reintroducing the pyright `reportAttributeAccessIssue` false positive on `git.exc.<Name>` attribute access.

## Scope

### In-Scope
- Add the constraint check one-liner to `rules/coding.md` §Constraint checks section (alongside the existing ast-grep one-liners).

### Out-of-Scope
- Adding a `types-GitPython`-style stub package to `pyproject.toml`/`uv.lock`.
- Any change to which exception types are caught, their order, or control flow.
- Any change to runtime behavior, log messages, or the `RepoInfoResult`/`GitServiceError` contracts.
- `# type: ignore` suppression — only a fallback if the import-based fix is proven not to resolve the error at a given site.
- Any file outside the constraint-check mechanism itself (the constraint applies to all future files, not just the 2 current ones).
- Pre-commit wiring — handled in Phase 3.

## Assumptions

- Phase 1 (sibling fix) has been implemented: both `scripts/shared/git_helper.py` and `scripts/mcp_servers/git/git_service.py` currently include `import git.exc`.
- `ast-grep` is available in the dev environment (already used for other constraint checks per `rules/coding.md`).
- The constraint check is low-cost enough to run on every commit without noticeable CI latency — a single `rg` + `grep` pipeline over `scripts/` takes <1 second.
- No database schema change and no new MCP server are involved; this is a pure tooling/process addition.

## Design decisions

- Use `rg` (ripgrep) instead of `ast-grep` for this specific constraint because the pattern requires checking two independent conditions across a file (`git.exc.` usage AND absence of `import git.exc`), which is more naturally expressed as a shell pipeline than an ast-grep pattern.
- Place the constraint alongside the existing ast-grep one-liners in the same §Constraint checks section, maintaining consistency with the project's existing constraint check style.
- The constraint uses `! grep -q` (negated grep) to flag files that DON'T contain `import git.exc`, rather than trying to express the negative condition in a single regex.

## Alternatives considered

- **ast-grep pattern**: Could use `ast-grep --pattern 'import git' --lang python scripts/ | while read f; do grep -qv "import git\.exc" "$f" && echo "$f"; done` but this would require ast-grep to be installed and adds complexity for a simple two-condition check.
- **Shell script file**: Could extract the constraint into a standalone script in `tools/` directory, but the plan explicitly states this is a low-cost one-liner suitable for inline documentation.
- **Pre-commit-only enforcement**: Could skip the documentation step and only wire into pre-commit, but the §Constraint checks section serves as human-readable documentation for developers who want to manually verify before committing.

## Implementation

### Target file

`rules/coding.md`

### Procedure

1. Open `rules/coding.md` and locate the "Constraint checks (run before every commit)" section (lines 51-62).
2. After the last existing constraint check (after line 62, after the `json.load()` check), add a new constraint check block following the same format as the existing ones.
3. The new constraint should appear as:

```bash
# git.exc import guard — requires explicit `import git.exc` alongside `import git`
rg -l "git\.exc\." scripts/ | while read f; do ! grep -q "import git\.exc" "$f" && echo "$f"; done
```

4. Verify the constraint passes on the current codebase by running the command manually.

### Method

The constraint works by:
1. `rg -l "git\.exc\." scripts/` — find all files in `scripts/` that contain `git.exc.` (list mode, output filenames only).
2. For each file found, `! grep -q "import git\.exc" "$f"` — check if the file does NOT contain `import git.exc` anywhere in it.
3. If the negated grep succeeds (meaning `import git.exc` is absent), `echo "$f"` outputs the filename to stdout, indicating a violation.

This approach catches the common copy-paste scenario where a developer adds `git.exc.<Name>` references without also adding the required `import git.exc` statement.

### Details

- The constraint uses `rg -l` (list mode) instead of `rg` with `-n` (line numbers) because we only care about whether the file violates the constraint, not which specific line does.
- The `! grep -q` pattern is used instead of `grep -v` because `grep -v "^import git\.exc"` would only match lines that don't start with `import git.exc`, which could still miss the case where `import git.exc` appears elsewhere in the file.
- The constraint is scoped to `scripts/` only, consistent with the existing constraint checks in this section.
- The comment follows the project convention of using English-only comments and log messages.
