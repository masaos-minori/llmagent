## Goal

Convert ToolLoopGuard from a hard turn-failure into a controlled final-answer fallback: when the guard detects repeated/cyclic/retrying tool calls, inject a temporary system message and call the LLM once more without tool definitions, allowing the LLM to produce a final answer using only information already available in the conversation.

## Scope

**In-Scope:**
- Add `GUARD_HINT` constant to `tool_loop_guard.py` — the ephemeral system message text defined in the requirement
- Determine trusted source for guard-injected messages: either add a new entry to `TRUSTED_SOURCES` in `message_schema.py` (e.g., `"loop_guard": {"_ephemeral"}`) or reuse an existing one. If adding new entry, update `is_trusted_source()` and `get_allowed_ephemeral_keys()` accordingly.

**Out-of-Scope:**
- Changes to existing guard detection logic (cycle/dedup/retry/error_limit checks remain unchanged)
- Changes to `ToolLoopGuard.check_error_limit()` behavior
- Changes to diagnostic recording beyond what is required by the new flow
- Changes to MCP server configurations or deploy scripts

## Assumptions

1. The ephemeral system message injected by the guard should use the same ephemeral-key filtering mechanism (`_ephemeral`) already used by command handlers, so it will be cleaned up automatically between turns.
2. `LLMClient.stream()` accepts an empty `tool_defs=[]` and produces a non-tool-calls response — this is the standard OpenAI-compatible API behavior.
3. The temporary system message content defined in the requirement doc is sufficient; no additional wording refinement is needed.
4. A single final-answer attempt is enough — if the LLM still returns tool calls, the turn fails safely without further retries.

## Design decisions

- **Ephemeral message via trusted source**: Reuse the existing `_ephemeral` key filtering mechanism rather than adding a separate bypass. If `"loop_guard"` is not in `TRUSTED_SOURCES`, add it.
- **Single retry policy**: One final-answer attempt only. No exponential backoff or multiple retries — the second failure is the safe fallback.

## Alternatives considered

- **Add new ephemeral key type**: Could create a new `_guard` ephemeral key type. Rejected because reusing `_ephemeral` is simpler and consistent with existing patterns.
- **Bypass schema validation**: Could bypass schema validation for guard messages. Rejected because it would weaken security guarantees.

## Compatibility considerations

- Adding a new entry to `TRUSTED_SOURCES` may affect downstream consumers that rely on the trusted sources list
- The ephemeral message injection requires the trusted source to be properly configured in `message_schema.py`

## Security considerations

- Ephemeral message injection must pass schema validation — validate message schema before appending; log warning if injection fails and fall back to the current hard-stop behavior
- The temporary system message must not contain user data or sensitive information

## Rollback considerations

- If ephemeral message injection fails, fall back to the current hard-stop behavior
- Removing the new entry from `TRUSTED_SOURCES` will disable guard message injection
