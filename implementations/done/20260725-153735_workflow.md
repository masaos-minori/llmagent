## Goal

Prevent silent overwrites of `pending_approval_task_id` and add validation for restored task status. Ensure that when multiple approvals exist, each approval's associated task is correctly restored and halted tasks are rejected with proper error messages.

## Scope

- Log warning before overwriting `pending_approval_task_id` if non-None value exists
- Clear `pending_approval_task_id` immediately after use by `_init_workflow_task()`
- Validate retrieved task status in `_init_workflow_task()`; reject halted tasks with error
- Add support for queue-based pending task IDs to handle multiple concurrent approvals

## Assumptions

- Warnings should be logged at INFO level with task ID details redacted
- Halted tasks should be rejected with a specific error message indicating the task was halted
- Queue-based approach should maintain FIFO ordering for pending approvals
- Existing callers of `_init_workflow_task()` can handle the new RuntimeError with specific error message

## Design decisions

- **Queue-based pending task tracking**: Replace single `pending_approval_task_id` with `deque` queue. This allows handling multiple concurrent approvals without losing task references.
- **Strict halted task rejection**: Tasks with "halted" status cannot be restored. This prevents orphaned or cancelled workflows from being inadvertently resumed.
- **Immediate cleanup after use**: Clear `pending_approval_task_id` (or pop from queue) immediately after successful task retrieval. Prevents stale references.
- **Redacted task IDs in logs**: Task IDs should not be exposed in INFO-level logs. Use partial IDs or hash values instead.

## Alternatives considered

- **Single pending task ID with overwrite warning**: Simpler but doesn't solve the core problem of lost task references when multiple approvals exist. Rejected due to incomplete solution.
- **Optimistic locking on task status**: Would add version column and check version on restore. More robust but requires schema change (out of scope).
- **Reject all non-"active" tasks**: Could reject any task not in "active" status. However, this might be too aggressive; "halted" is specifically problematic while other states may be valid.
- **asyncio.Queue vs collections.deque**: asyncio.Queue provides async-safety but adds complexity. Simple deque sufficient since operations are within event loop context.

       """Initialize workflow task with validation."""
       # Get task from queue
       task_id = self._pop_pending_task_id()
       if task_id is None:
           return None

       task = await get_task_by_id(task_id)

           logger.warning(f"Task {task_id[:8]}... not found")
           return None

       if task.status == "halted":
           raise RuntimeError(f"Cannot restore halted task {task_id}")
       
       # Clear pending_approval_task_id after successful retrieval
       # (already popped from queue above)
       
       return task
   
   def _pop_pending_task_id(self) -> Optional[str]:
       """Pop next pending task ID from queue."""
       if hasattr(self, 'pending_approval_queue') and self.pending_approval_queue:
           return self.pending_approval_queue.popleft()
       return None

## Compatibility considerations

- **Breaking change**: Rejecting halted tasks will cause failures for workflows expecting halted task restoration. Document this behavior clearly.
- **Queue vs single value**: Callers expecting `ctx.turn.pending_approval_task_id` will need updates to use queue methods instead.
- **Log format change**: Task ID redaction changes log output format. May affect log parsing tools.

## Security considerations

- **Task ID exposure**: Redact task IDs in INFO-level logs to prevent information disclosure
- **Workflow hijacking**: Strict halted task rejection prevents attackers from resuming cancelled workflows
- **Denial of service**: Queue overflow protection needed if many approvals accumulate

## Rollback considerations

- **Quick rollback**: Remove queue logic and revert to single pending_approval_task_id
- **Data impact**: No database changes; rollback does not affect persisted state
- **Configurable mode**: Consider adding environment variable to toggle strict/lenient halted task handling without code changes
