# Implementation Procedure — `scripts/db/models.py`

## Goal

Add the final active-database state to `RecoveryResult` in
`scripts/db/models.py` (`REQ-006`): one additive, machine-readable field naming
which database state is active after a recovery (`restored`,
`preserved_original` (new), `non_serviceable` (new)), so the CLI and operators are told the
truthful active state instead of inferring it from `action`.

## Scope
**Release unit**: contract activation

## Assumptions

- `RecoveryResult` (current L160-L168) is a frozen dataclass shared across
  `scripts/db/__init__.py`, `scripts/db/rotation.py`, and the service layer
  (`scripts/agent/services/db_maintenance_service.py`,
  `scripts/agent/services/models.py`). The addition MUST stay additive so all
  these stay import-compatible.
- `logical_ok: bool | None = None` (current L168) is populated to `True`/`False`
  on every restore path by `scripts/db/recovery.py` (seq 02); this Plan keeps the
  field definition and its `None` default for non-restore results (vacuum,
  `no_backup`, …), which never run logical verification.
- Cross-plan: `sessmoke001` is already implemented (batch `20261105-161823`,
  archived in `implementations/done/`): the write-smoke field no longer exists in
  `SessionConsistencyReport` (current L172+), a different dataclass. This Plan
  touches only `RecoveryResult`; no interaction. (Verified 2026-11-05.)

## Design decisions

- Add one optional field `active_db_state: str | None = None` after `logical_ok`.
  Values: `restored` (candidate verified and activated), `preserved_original` (new)
  (verification failed before activation; live DB untouched),
  `non_serviceable` (new) (post-activation failure and rollback failed).
- Keep the field optional so positional/keyword construction at existing call
  sites is unaffected.

## Alternatives considered

- Carrying the state in `action` + `detail` was rejected (see `UNK-06`): a
  dedicated field is machine-readable and unambiguous for consumers.

## Compatibility considerations

- Additive optional field with a default; existing constructors and consumers are
  unchanged. `lint-imports` unaffected.
- `scripts/agent/commands/db_session_ops.py` (consumes `result.logical_ok`,
  current L80-L84) prints a truthful line with no consumer change; it may also
  render `active_db_state` (new) if desired (optional, out of scope here).

### Method

```python
@dataclass(frozen=True)
class RecoveryResult:
    """Structured result of a corruption recovery attempt.

    active_db_state names the database state that is actually active after the
    attempt: "restored", "preserved_original", or "non_serviceable".
    """

    success: bool
    action: str  # e.g. "no_backup", "bad_backup", "backup_wrong_domain", "logical_verify_failed", "verification_unavailable", ...
    detail: str | None = None
    dry_run: bool = False
    logical_ok: bool | None = None
    active_db_state: str | None = None   # (new): "restored" | "preserved_original" | "non_serviceable"
```

Coordinate the value strings with `scripts/db/recovery.py` (seq 02), which sets
them.

### Details

The field is additive and optional; existing `RecoveryResult(...)` calls that do
not pass it keep working. `logical_ok` population is owned by seq 02; this file
only declares the field. Do not rename `active_db_state` (new) once chosen, as
`scripts/db/recovery.py` sets it.
