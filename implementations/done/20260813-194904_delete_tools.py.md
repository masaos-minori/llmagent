## Goal

Add the schema-2.0 per-tool metadata contract to both tool entries in
`scripts/mcp_servers/file/delete_tools.py`'s `TOOL_LIST` (`delete_file`,
`delete_directory`): `is_write=True`, `requires_serial=False`,
`resource_scope_kind="filesystem"`, `resource_scope_keys=["path"]`.

## Scope

In scope: the 2 dict literals inside `TOOL_LIST` (lines 11-55, exact end not yet
confirmed past line 55 in the read excerpt but the module's second entry closes the
list per its own bracket). Out of scope: any change to the recursive-delete logic

server.

## Assumptions

- Neither entry currently declares any of the 4 new fields (confirmed:
  `rg "is_write|requires_serial|resource_scope"` on this file returns no hits) — fully
  missing on both, not a partial-backfill case.
- Both tools operate on a single `path` argument (confirmed: both entries'
  `inputSchema["properties"]` contain only `path` plus boolean flags — `dry_run` for
  `delete_file`, `recursive`+`dry_run` for `delete_directory` — no second path-like
  argument), so `resource_scope_keys=["path"]` applies uniformly to both, matching the
  plan's per-server table (`resource_scope_keys=["path"]`).

## Design decisions

- Both entries: `is_write=True` (deletion is inherently mutating),
  `requires_serial=False` (scope-based conflict detection in the future scheduler
  handles serialization against overlapping paths; no blanket global barrier is
  warranted for a single-path delete), `resource_scope_kind="filesystem"`,
  `resource_scope_keys=["path"]`.
- `delete_directory`'s `recursive=True` mode is not given any different scope
  treatment (e.g. no attempt to enumerate descendant paths into
  `resource_scope_keys`) — the ancestor/descendant overlap detection for
  `"filesystem:"`-kind scopes is handled generically by the future
  `resource_scope.py` conflict predicate (per the plan's Design section, using
  `PurePosixPath.is_relative_to()`), so a single `path` key pointing at the directory
  root is sufficient for the conflict graph to catch overlaps with any
  path underneath it.

## Security considerations

`is_write=True` correctly documents that both tools are destructive (file/directory
deletion). No new security surface introduced — this file holds schema dicts only, not
the actual deletion logic (permission checks, recursive-delete guards) implemented
elsewhere in the file-delete-mcp server. Accurate `is_write` metadata is a
precondition for the future scheduler to correctly serialize deletes against
concurrent reads/writes on overlapping paths, which is a safety improvement once the
(separately-owned) scheduler rework consumes it.
