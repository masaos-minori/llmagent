## Goal

Make Windows signal handler integration-safe by scheduling the signal callback through the asyncio event loop instead of calling it directly from the OS signal handler thread.

## Scope

**In**: `scripts/agent/repl.py` (AgentREPL.run())
**Out**: Changes to signal handling, other async resource access patterns

## Assumptions

1. Only `_sigterm_handler()` needs to be made integration-safe — it's the only handler registered in the fallback path
2. `loop.call_soon_threadsafe()` is available on all supported Python versions (3.7+)
3. No other code paths need similar treatment in this scope

## Design decisions

- Replace the direct `_signal.signal(sig, lambda *_: _sigterm_handler())` call with one that schedules the handler via `loop.call_soon_threadsafe(_sigterm_handler)`
- This ensures the handler runs on the event loop's next iteration rather than interrupting async operations mid-execution
- Add comment explaining why this approach is used on Windows

## Alternatives considered

- **Keep direct call but add threading lock around shared state**: Would add unnecessary complexity; `call_soon_threadsafe()` is simpler and more idiomatic
- **Use asyncio.Queue to communicate signals**: Over-engineered; `call_soon_threadsafe()` is designed exactly for this purpose
- **Remove Windows support entirely**: Not viable; must maintain cross-platform compatibility

Change to:

```python
import signal as _signal

for sig in (signal.SIGTERM, signal.SIGINT):
    try:
        loop.add_signal_handler(sig, _sigterm_handler)
    except NotImplementedError:
        # On Windows, register a process-wide handler that schedules the
        # callback on the event loop via call_soon_threadsafe(). This prevents
        # the handler from interrupting async operations mid-execution.
        _signal.signal(sig, lambda *_: loop.call_soon_threadsafe(_sigterm_handler))
```

Key points:
- Changed the lambda to use `loop.call_soon_threadsafe(_sigterm_handler)` instead of calling `_sigterm_handler()` directly
- Added comment explaining why this approach is used on Windows
- Same behavior as before — shutdown is still triggered on SIGTERM/SIGINT
- Thread-safe because `call_soon_threadsafe()` is designed for cross-thread event loop interaction

### Method

Extract ownership of signal handler lifecycle into the REPL class itself (`AgentREPL`). Use `call_soon_threadsafe()` to schedule the signal callback on the event loop instead of executing it directly from the OS signal handler thread.

### Details

The core issue is that on Windows, `add_signal_handler()` raises `NotImplementedError`, so the fallback registers a process-wide signal handler via `_signal.signal()`. This handler runs in the OS signal handler thread, which can interrupt async operations mid-execution — potentially causing race conditions with asyncio primitives like Events.

By using `loop.call_soon_threadsafe(_sigterm_handler)`:
- The signal handler immediately returns control to the OS signal handler thread
- The actual callback execution is scheduled on the event loop's next iteration
- No risk of interrupting async operations — the event loop handles synchronization
- Thread-safe because `call_soon_threadsafe()` is specifically designed for cross-thread event loop interaction

The `_sigterm_handler()` function only does three things: sets `self._ctx.conv.shutdown_requested`, calls `self._shutdown_event.set()`, and logs. All three are thread-safe individually, but the combination could cause issues if an async operation is in progress between them. Scheduling via `call_soon_threadsafe()` eliminates this risk entirely.
