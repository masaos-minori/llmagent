## Goal

`CrawlFilePayload`, `ChunkOutputPayload`, and `ChunkMetadata`, and thread
`ChunkDocument.fetched_at` through `_extract_chunk_metadata()` so that every
per-chunk output file written for one crawl record carries the identical, unmodified
`fetched_at` value.

## Assumptions
- `CrawlFilePayload`, `ChunkOutputPayload`, and `ChunkMetadata` currently have no
  `fetched_at` field at all — confirmed by reading the full file; this is a pure addition
  to all three TypedDicts, not a widen-from-optional change (unlike `pipeline_utils.py`'s
  `ChunkJsonRaw.fetched_at`, which already exists as `NotRequired[str | None]`).
- `_extract_chunk_metadata()` builds the `ChunkMetadata` dict solely from attributes of
  the `ChunkDocument` instance (`data.url`, `data.title`, `data.lang`, `data.etag`,
  `data.last_modified`) plus two locally-computed values (`src_path.name`,
  `chunking_strategy`) — confirmed by reading the function body; `data.fetched_at` will
  be available on that same `ChunkDocument` instance once `models_data.py`'s field
  addition (separate implementation document) lands, requiring no new parameter or
  data-flow change to this function's signature.
- `_build_chunk_payload()` already spreads `**metadata` (the `ChunkMetadata` dict)
  directly into the returned payload dict — confirmed by reading the function body — so
  adding `fetched_at` to `ChunkMetadata` and populating it in `_extract_chunk_metadata()`
  is sufficient to make every chunk file's JSON output carry the field; no edit to
  `_build_chunk_payload()` itself is needed.
- `CrawlFilePayload` is used only as a type-annotation possibility (currently in
  `_is_markdown_source(self, data: ChunkDocument | ChunkJsonRaw) -> bool`'s import list
  and module-level definition) and is not the runtime input to `_read_source_data()`
  today — `read_json_file()` returns a `ChunkDocument`, not a `CrawlFilePayload` — so
  adding `fetched_at` to `CrawlFilePayload` is a type-shape correctness fix (documenting
  what a crawl JSON file actually contains) rather than a change that affects any live
  parsing path in this file.
- All chunk files derived from one crawl record must carry the identical `fetched_at`
  value (per the source plan's Design section item 2: "no re-derivation") — this is
  already the natural consequence of `_extract_chunk_metadata()` being called exactly
  once per `_write_chunk_files()` invocation, with the resulting single `ChunkMetadata`
  dict spread into every per-chunk payload in the loop.

## Design decisions
- Add `fetched_at: str` (mandatory, not `NotRequired`) to `ChunkMetadata` despite that
  TypedDict being declared `total=False` for spreading purposes — `total=False` controls
  whether the *class* requires all keys at construction/type-check time for dict-literal
  assignment, but does not prevent an individual field from being annotated as `str`
  (non-`NotRequired`) to signal "always populated by `_extract_chunk_metadata()`, if
  present"; this mirrors how `url`/`title`/`lang` are already annotated `str` (not
  `str | None`) in the current `ChunkMetadata` despite the class being `total=False`.
- Populate `fetched_at` in `_extract_chunk_metadata()` via direct attribute access
  (`data.fetched_at`), not via a new default/fallback — matches the source plan's
  "propagate unchanged" design principle applied identically in every other layer of the
  pipeline.
- Keep `CrawlFilePayload` and `ChunkOutputPayload` as-is structurally (only adding the
  one field) rather than restructuring them — no other change to this file is authorized
  by the source plan beyond the `fetched_at` addition.

## Alternatives considered
- Passing `fetched_at` as a separate explicit parameter to `_extract_chunk_metadata()`
  instead of reading it off the `ChunkDocument` instance already passed as `data` —
  rejected: `_extract_chunk_metadata(self, data: ChunkDocument, ...)` already receives
  the full `ChunkDocument`, and every other propagated field (`url`, `title`, `lang`,
  `etag`, `last_modified`) is read the same way; a separate parameter would be redundant
  and inconsistent with the existing pattern.
- Re-deriving `fetched_at` per chunk file (e.g. from `src_path` mtime at write time) —
  rejected outright: this is exactly the re-derivation the source plan's Design section
  explicitly forbids; the whole point of threading the field through `ChunkMetadata` is
  that every chunk from one crawl record shares one canonical value.

## Implementation
### Target file
`scripts/rag/ingestion/chunk_splitter.py`

### Procedure
1. In `CrawlFilePayload`, add `fetched_at: str` (mandatory, alongside the existing
   `url`, `title`, `lang`, `content`, `code_blocks` mandatory fields; not grouped with
   the `NotRequired` `etag`/`last_modified` fields).
2. In `ChunkOutputPayload`, add `fetched_at: str` (mandatory, alongside `url`, `title`,
   `lang`, `source_file`, `chunk_index`, `chunk_type`, `content`; not grouped with the
   `NotRequired` `normalized_content` field).
3. In `ChunkMetadata`, add `fetched_at: str` alongside the existing `url`, `title`,
   `lang`, `source_file`, `chunking_strategy` fields (i.e. the group of fields not typed
   `| None`).
4. In `_extract_chunk_metadata()`, add `"fetched_at": data.fetched_at` to the returned
   dict literal, alongside the existing `"url": data.url`, `"title": data.title`, etc.
   entries.

### Method
- Pure additive field declarations in three TypedDicts plus one new dict-literal entry
  in an existing function; no new function, no new class, no control-flow change.

### Details
- Do not add `fetched_at` handling to `_build_chunk_payload()` — it already spreads
  `**metadata` (the updated `ChunkMetadata`) into its return value, so the new field
  flows through automatically once `_extract_chunk_metadata()` populates it.
- Do not touch `_is_markdown_source()`'s `ChunkDocument | ChunkJsonRaw` union or any
  other change to that method — the source plan's Out-of-Scope section explicitly
  excludes reworking that union (it is in scope of the sibling
  `plans/20260820-094150_plan.md` instead); this document's changes to
  `CrawlFilePayload`/`ChunkOutputPayload`/`ChunkMetadata` are additive field declarations
  only and do not touch that method's signature or body.
- Field placement within each TypedDict body should group `fetched_at` with the other
  mandatory (non-`NotRequired`, non-`| None`) fields, for readability consistency with
  the existing declaration order — this is a style preference, not a functional
  requirement (TypedDict field order has no runtime effect).

## Compatibility considerations
- Breaking change by design: any on-disk `rag-src/*.json` crawl file lacking a
  `fetched_at` key will already be rejected earlier, at `read_json_file()` (see that
  file's own implementation document) — this file's own change (adding the field to
  three TypedDict *type annotations*) has no independent runtime enforcement effect by
  itself; enforcement happens upstream. This file's role is limited to making the type
  shapes accurate and ensuring the already-validated value is threaded through to every
  chunk output file.
- Every `rag-src/chunk/{stem}-{idx:04d}.json` file written after this change will
  contain a `fetched_at` key it previously lacked entirely — downstream consumers
  (`ingester.py`, own implementation document) must be updated in the same overall
  change to read it as mandatory, per the source plan's Phase 2 sequencing.
