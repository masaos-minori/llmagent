# Implementation procedure: scripts/agent/tool_runner.py (message-history validation)

## Goal

Route `tool_runner.py`'s two `ctx.conv.history` mutation sites —
`_collect_tool_result_msgs()`'s per-result append and
`execute_all_tool_calls()`'s denied-call extend — through the new
`ConversationState.append_message()` / `extend_messages()` helpers.

Note: two other implementation procedure docs already exist for
`tool_runner.py` in this batch
(`implementations/20260726-100319_runtime_tool.py.md` and
`implementations/20260726-100351_tool_runner.py.md`) but cover an unrelated
topic — wiring `validate_tool_arguments()` into `execute_one_tool_call()` for
tool *argument* schema validation. This doc is a distinct item, for
conversation-*history* message validation, and is not yet implemented.

## Scope

- In scope:
  - `_collect_tool_result_msgs()` (L168-195): the
    `ctx.conv.history.append({"role": "tool", "tool_call_id": tc_id, "content":
    llm_text})` call (currently L193).
  - `execute_all_tool_calls()` (L439-471): the
    `ctx.conv.history.extend(denied_history)` call (currently L469), where
    `denied_history` comes from `_build_denied_messages(denied_ids)` (L492+).
- Out of scope: any change to `_build_denied_messages()`'s message-construction
  logic itself, `_run_approval_gate()`, or the tool-argument-validation work
  covered by the two same-day companion docs named above.

## Assumptions

- Both messages constructed here use `role: "tool"` with `tool_call_id` and
  `content` only — this exactly matches `ROLE_KEY_WHITELIST["tool"] = {"role",
  "content", "tool_call_id"}` (confirmed, `message_schema.py`), so no
  sanitization will occur for either site; this is a pure plumbing change with
  no behavior change expected.
- No `source` is required for either call site — tool-role messages carry no
  ephemeral keys, so the default `source=""` path applies.

## Design decisions

- `_collect_tool_result_msgs()`: single-message append → use
  `ctx.conv.append_message({"role": "tool", "tool_call_id": tc_id, "content":
  llm_text})`, no `source`.
- `execute_all_tool_calls()`: bulk extend of `denied_history` → use
  `ctx.conv.extend_messages(denied_history)`, no `source`. `extend_messages()`
  is preferred over calling `append_message()` in a loop at the call site,
  since `extend_messages()` already implements that loop centrally (per the
  `context.py` procedure doc).

## Alternatives considered

- **Use `replace_history()` for the denied-messages extend.** Rejected:
  `replace_history()` clears history first, which is wrong here —
  `execute_all_tool_calls()` is appending additional denied-tool-result
  messages onto existing turn history, not replacing it. `extend_messages()`
  is the correct primitive.

## Implementation

### Target file

`scripts/agent/tool_runner.py`

### Procedure

1. In `_collect_tool_result_msgs()` (currently L193), replace
   `ctx.conv.history.append({"role": "tool", "tool_call_id": tc_id, "content":
   llm_text})` with `ctx.conv.append_message({"role": "tool", "tool_call_id":
   tc_id, "content": llm_text})`.
2. In `execute_all_tool_calls()` (currently L469), replace
   `ctx.conv.history.extend(denied_history)` with
   `ctx.conv.extend_messages(denied_history)`.

### Method

Two independent one-line substitutions within the same file; no change to
`_build_denied_messages()`'s return shape or to the surrounding
approval-gate/dispatch control flow (L455-471).

### Details

- `_collect_tool_result_msgs()` is called from `execute_all_tool_calls()`
  (L467) before the denied-messages extend (L469) — order of these two
  history mutations is unchanged by this item.
- No new import needed in `tool_runner.py` — both calls go through
  `ctx.conv.*`, which is already accessed throughout this file via `ctx:
  AgentContext`.

## Compatibility considerations

- No behavior change expected: both message shapes already fully satisfy
  `ROLE_KEY_WHITELIST["tool"]`, so validation always succeeds and the stored
  message is identical to what raw `.append()`/`.extend()` would have stored.
- `ctx.session.save_many(tool_msgs)` (L471, DB persistence of the same
  `tool_msgs` list built alongside history) is unrelated to `ctx.conv.history`
  and is untouched by this item.

## Security considerations

- Closes the two `tool_runner.py`-owned gaps named in the requirement: tool
  results and denied-call messages now flow through the same validated append
  path as the rest of the codebase, so a future change to either function
  cannot silently bypass validation.
- Tool-role messages have no ephemeral-key surface today (`ROLE_KEY_WHITELIST`
  has no ephemeral entries for `"tool"`), so there is no meaningful new
  attack-surface reduction here beyond consistency — this item's value is
  closing the audit gap, not fixing an active vulnerability in this specific
  file.

## Rollback considerations

- Both substitutions are independent single-line reverts with no data
  migration, since stored message shape is unchanged for both call sites.
