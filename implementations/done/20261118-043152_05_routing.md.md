## Assumptions

- `routing.md` currently has no row naming either tool (verified 20261118 with `rg -n "audit_plan_target_paths|sync_plan_workitem_status" routing.md`); the audit is reachable today only through `tools/amend_plan.py`'s post-run printout and the reconciliation tool only through the `Superseded` branch of `skills/code-implementation/workflow.md` (Plan Background).
- The drift check derives each row's checker id from its Run cell (`_checker_id_from_cell`) and requires exact two-way parity with `ROUTING_GATES` (verified 20261118), so the Run cells must mirror the seq 02 mapping argv.
- A row is not a hook: neither new tool needs a `.pre-commit-config.yaml` entry; the drift check's hook comparison is unaffected.

## Design decisions

- Run cells use single-token runtime placeholders (`<plan>`), and the Why cell states that the gate check never auto-selects the tool, matching the patternless manual mappings (Plan Decision 2; precedent: the `amend_plan` row's placeholder note). A multi-token placeholder like `[plans/*.md ...]` would break id parity: `_checker_id_from_cell` splits the Run cell on whitespace, so the cell side would derive `audit_plan_target_paths:[plans/*.md` against the gate side's `audit_plan_target_paths:[plans/*.md ...]` (corrected 20261118 by adversarial re-verification).
- Both rows are inserted after the `check_plan_target_overlaps.py` row (line 129 at revalidation time), keeping the Plan-tool cluster together; row order is not semantic for the drift check (it parses every data row).

## Alternatives considered

- One combined row naming both tools: rejected — drift parses one Run cell per row and each tool needs its own trigger and id.
