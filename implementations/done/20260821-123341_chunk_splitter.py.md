## Goal
In `scripts/rag/ingestion/chunk_splitter.py`: remove `CrawlFilePayload` and
`ChunkOutputPayload`; read crawl artifacts only via `read_crawl_json()`; write chunk
artifacts via `ChunkJsonPayload`/`ChunkDocument`; update `_is_markdown_source()`'s
signature.

## Scope
- In scope: `scripts/rag/ingestion/chunk_splitter.py` only.
- Out of scope: `pipeline_utils.py`'s reader/writer implementations themselves (own
  document); test file updates (own documents).

## Assumptions
- `_read_source_data()` (line 223-229) is the sole caller of `read_json_file()`
  (soon `read_crawl_json()`) and always returns `ChunkDocument | None` — confirmed by
  reading the full file. Both call sites of `_is_markdown_source()` (line 147 inside
  `process_file()`, and line 250 inside `_build_text_triples()`) pass a `ChunkDocument`
  (`chunk_doc`/`data` typed as `ChunkDocument` at both sites), never a raw dict —
  confirmed by reading the surrounding function signatures. The `ChunkJsonRaw` branch
  in `_is_markdown_source(self, data: ChunkDocument | ChunkJsonRaw)` is therefore dead
  code today; per the plan's own note ("confirm via the surrounding call sites at
  implementation time"), this confirms the raw-dict branch can be dropped entirely
  rather than updated to `ChunkDocument | ChunkJsonPayload`.
- `CrawlFilePayload` (lines 43-51) is defined but only used as a type-annotation
  possibility in `_is_markdown_source`'s union — same dead-code status as above,
  *for this file's own production call sites*.
- **Caveat found during adversarial review:** `tests/rag/ingestion/test_chunk_splitter.py`
  calls `splitter._is_markdown_source({"url": ...})` directly with **plain dicts** (not
  `ChunkDocument` instances) in all 6 of its tests — so narrowing this method's
  signature to `ChunkDocument`-only is only safe if that test file is updated in the
  same change to construct `ChunkDocument(...)` instances instead of raw dicts. This is
  consistent with the plan's own Affected-areas note for that test file ("Update to
  construct/consume `CrawlJsonPayload`/`CrawlDocument`..."), so no plan correction is
  needed here — just flagging the dependency explicitly for implementation-order
  purposes: land this file's signature narrowing together with (not before)
  `test_chunk_splitter.py`'s fixture update. See that file's own implementation
  document.

## Design decisions
- Simplify `_is_markdown_source(self, data: ChunkDocument) -> bool` to take only
  `ChunkDocument` (drop the `| ChunkJsonRaw` / `| ChunkJsonPayload` union entirely),
  since no caller ever passes a raw dict. This is a narrower, more precise signature
  than the plan's suggested `ChunkDocument | ChunkJsonPayload` alternative, justified by
  the call-site check above.
- `ChunkOutputPayload` (lines 55-66) is replaced by constructing `ChunkJsonPayload`
  dict literals directly in `_build_chunk_payload()` (or by importing the
  `ChunkJsonPayload` TypedDict as the return-type annotation there).

## Alternatives considered
- Keeping `ChunkJsonPayload` in the `_is_markdown_source` union for defensive
  future-proofing — rejected: this file's own call sites are the actual constraint, and
  the plan explicitly says to confirm and simplify rather than speculatively widen the
  signature (matches `rules/coding.md`'s general no-speculative-generalization stance
  applied elsewhere in this plan).

## Implementation
### Target file
`scripts/rag/ingestion/chunk_splitter.py`

### Procedure
1. Remove `class CrawlFilePayload(TypedDict)` (lines 43-51) and
   `class ChunkOutputPayload(TypedDict)` (lines 55-66).
2. Change the import block (currently `from rag.ingestion.pipeline_utils import
   ChunkJsonRaw, collect_source_files, is_already_processed, read_json_file`, lines
   23-28) to `from rag.ingestion.pipeline_utils import collect_source_files,
   is_already_processed, read_crawl_json`.
3. In `_read_source_data()` (lines 223-229): call `read_crawl_json(src_path)` instead
   of `read_json_file(src_path)`; keep the `except (FileNotFoundError,
   ChunkFormatError)` handling unchanged (both old and new readers raise
   `ChunkFormatError`).
4. Change `_is_markdown_source(self, data: ChunkDocument | ChunkJsonRaw) -> bool` (line
   165) to `_is_markdown_source(self, data: ChunkDocument) -> bool`; remove the
   `isinstance(data, ChunkDocument)` branching inside the method body (lines 171,
   178-180) since the parameter is now always a `ChunkDocument` — use direct attribute
   access (`data.url`, `data.content`).
5. In `_build_chunk_payload()` (lines 303-321): keep constructing the returned
   `dict[str, object]` literal, but ensure every mandatory `ChunkJsonPayload` key is
   present with the right nullability (`etag`, `last_modified`, `normalized_content`
   always present, `None` when unavailable) — this already matches the current
   `**metadata, "chunk_index": idx, "chunk_type": chunk_type, "content": chunk_content,
   "normalized_content": norm_content or None` construction; only the type annotation
   changes from implicit `dict[str, object]` to `ChunkJsonPayload`.

### Method
- Pure signature/import edits plus one dead-branch removal inside
  `_is_markdown_source()`; no new control flow beyond what already exists.

### Details
- `ChunkMetadata` (TypedDict, `total=False`, lines 69-83) is a separate, still-needed
  type used for `**metadata` spreading in `_build_chunk_payload()` — not in scope for
  removal; it is not `CrawlFilePayload`/`ChunkOutputPayload`.
- `process_file()` (lines 129-149) and `_write_chunk_files()`/`_extract_chunk_metadata()`
  (lines 262-301) are unaffected beyond the type-annotation change flowing through from
  `ChunkDocument`'s field removal of defaults (see `models_data.py`'s implementation
  document) — no logic change needed there since these methods already read from a
  `ChunkDocument` instance via attribute access.
- **CORRECTION:** `_build_chunk_payload()`'s return type annotation must NOT be changed
  to `ChunkJsonPayload` because the payload includes `schema_version`, `artifact_type`,
  and `created_by` fields (spread via `**metadata`) that are absent from
  `ChunkJsonPayload`'s TypedDict definition in `pipeline_utils.py` (lines 35-48). Keep
  the return type as `dict[str, object]` — the TypedDict does not cover the full output
  shape.
- **CORRECTION:** `_read_source_data()` calls `read_crawl_json(src_path)` which returns
  `Any` (a dict), NOT `ChunkDocument`. After step 3, the variable `chunk_doc` in
  `process_file()` will hold a dict, not a `ChunkDocument` instance. The callers
  (`_is_markdown_source(chunk_doc)` and `logger.info(extra={"url": chunk_doc.url})`)
  will fail at runtime because dicts do not support `.url` attribute access. The fix:
  either (a) convert the dict to a `ChunkDocument` after reading, or (b) update
  `read_crawl_json()` to return `ChunkDocument` instead of `Any`. Option (b) is preferred
  and requires updating `pipeline_utils.py` to construct `ChunkDocument(url=url, ...)` from
  the validated dict fields.

## Compatibility considerations
- Any crawl JSON file that previously passed the permissive `_read_chunk_json_raw()`
  path but would fail the new `read_crawl_json()`'s exact-key-set/type checks will now
  raise `ChunkFormatError`, causing `process_file()`'s caller (`process_all()`, which
  already catches `(OSError, RuntimeError, ValueError)` around `process_file()`) to log
  and skip that file rather than crash the batch — `ChunkFormatError` is a `ValueError`
  subclass, so this existing catch already covers it; no new exception handling is
  needed in `process_all()`.
