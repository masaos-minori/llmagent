## Goal
- Give `attach_auth_middleware` an opt-in, keyword-only switch that admits requests to exactly the health path from a loopback client without the Bearer token, while every other request keeps strict token validation and the default behavior is unchanged (`REQ-001`, `REQ-002`, `REQ-003`).

## Scope
- The function `attach_auth_middleware` (signature, docstring, and its middleware closure) and one new private module-level helper in `scripts/mcp_servers/server.py`. The other functions, the server runner, and every caller are untouched here (the web-search caller is procedure 02).

## Assumptions
- Under the real server the request exposes the peer address as the client attribute, a pair of host and port; under the framework test client the default host is the plain string testclient, not an IP address, and the client attribute can be absent. Both must be treated as not loopback.
- All MCP servers bind to loopback only (the runner verifies the bound socket address after start), so a loopback-scoped admission adds no external exposure.
- The Python version is 3.13, where the standard IP-address object reports IPv4-mapped IPv6 loopback addresses as loopback.
- The new parameter is additive and defaults to disabled, so existing callers behave exactly as before.

## Design decisions
- Keyword-only parameter exempt_health_on_loopback (new), default false, so no positional call can set it by accident.
- The admission is by exact path equality with the health path and by loopback client only; any other path, including one that merely starts with the health path, still needs the correct token. It does not depend on which token the client presents, because the agent's health poll presents the main token, which is not the browser token.
- A private helper `_is_loopback_client` (new) takes the request and returns false when the client attribute is missing or its host does not parse as an IP address; otherwise it returns the IP object's loopback flag. Keeping it separate makes it unit-testable and keeps the closure small.
- The request-id header is still attached to an admitted response, and the 401 path is unchanged.

## Alternatives considered
- Exempting the health path on every client address: rejected, it would expose health details if a server ever bound a non-loopback address.
- Making the health checker send the browser token, or aligning the server credential with the main token: rejected in the Plan Design (wider blast radius in high-churn shared code).

## Compatibility considerations
- Backward compatible: callers that do not pass the new parameter behave exactly as before (git, rag-pipeline, cicd, and the mdq caller keep strict validation).

## Security considerations
- The only new admission is the exact health path from a loopback client; protected routes keep the constant-time token comparison and still require the token from a loopback client. The risk that a non-loopback bind would expose health details is mitigated by the runner's post-start loopback verification; the dependence on loopback-only binding is recorded in the Plan assumptions.
- A forwarded-address header cannot grant access: a peer on loopback is already loopback, and a changed client address can only make a request non-loopback.
