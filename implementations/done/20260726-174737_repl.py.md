## Goal

Log a warning in `AgentREPL._persist_session_diagnostics()` when sensitive fields
(`artifacts`, `rag_stage_outcomes`) would be persisted but are filtered out by
`DiagnosticStore`, so operators can see that redaction occurred rather than silently
losing data.

## Scope

**In-Scope:**
- In `_persist_session_diagnostics()` (`scripts/agent/repl.py`), before/around the
  `self._diagnostic_store.save(...)` call, detect whether `summary["artifacts"]` or
  `summary["rag_stage_outcomes"]` is non-empty and log a warning noting that these fields
  will be filtered before persistence.

**Out-of-Scope:**
- The actual filtering/redaction logic itself (implemented in `DiagnosticStore`, tracked in
  `implementations/20260726-174644_diagnostic_store.py.md`).
- Any other diagnostic collection logic in `_persist_session_diagnostics()` (latency
  summary, workflow/task counts, RAG query count) — unchanged.
- The unrelated SIGTERM/service-cleanup fix
  (`implementations/20260726-171517_repl.py.md`) and WAL backup path-traversal fix
  (`implementations/20260726-172953_repl.py.md`) already tracked for `repl.py` — neither
  touches `_persist_session_diagnostics()` or diagnostics content, confirmed by reading
  both documents' Goal/Scope sections.

## Assumptions

1. "Sensitive" is scoped to exactly the two fields `DiagnosticStore` redacts —
   `artifacts` and `rag_stage_outcomes` — so the warning condition here must mirror that
   set exactly, not be independently defined (avoids drift between what `repl.py` warns
   about and what `diagnostic_store.py` actually filters).
2. The warning is logged once per `_persist_session_diagnostics()` call (session end), not
   per individual artifact/outcome item, consistent with the method's existing
   once-per-session logging style (e.g. `logger.debug("Failed to persist session
   diagnostics", ...)` at line 246).
3. This change does not require `encrypt=True` to be passed to `save()` — filtering happens
   unconditionally in `DiagnosticStore.save()` (per the companion document), so the warning
   here is informational regardless of the encryption flag.

## Design decisions

- Compute the warning condition from the already-built `summary` dict (lines 204-233)
  rather than re-deriving `artifacts`/`rag_stage_outcomes` separately, to avoid duplicating
  the emptiness check against a second source of truth.
- Log at `logger.warning` (not `debug`) since this is meant to be operator-visible per the
  plan's "Log warnings when sensitive data would be persisted but is filtered out"
  requirement, distinct from the existing `logger.debug` failure-path logging in this
  method.
- Keep the check inline in `_persist_session_diagnostics()` rather than pushing it into
  `DiagnosticStore.save()`, since the plan explicitly assigns this responsibility to
  `repl.py` (Affected Files table: "`repl.py` — `_persist_session_diagnostics()`: add
  warning logging for filtered data") — `DiagnosticStore` doing its own filtering already
  logs at its own layer if warranted (see companion document); this avoids two components
  both trying to own the same log line.

## Alternatives considered

- Have `DiagnosticStore.save()` return a flag/count indicating what was redacted, and have
  `repl.py` log based on that return value — rejected for this document: `save()` currently
  returns `None` and changing its return type is a larger, more invasive contract change
  than checking the pre-save `summary` dict directly in `repl.py`; simpler inline check is
  sufficient for a log-only requirement.
- Logging at `debug` level to match the surrounding method's existing style — rejected: the
  plan explicitly calls for visibility ("Log warnings..."), and `debug` would make it
  invisible in default-configured deployments.

## Compatibility considerations

- Purely additive logging; no change to `_persist_session_diagnostics()`'s control flow,
  return value (`None`), or the `save()` call's arguments/content.

## Security considerations

- The warning message logs only counts (`len(...)`), not the actual artifact URIs or RAG
  outcome contents — consistent with not leaking sensitive data into logs while still
  surfacing that redaction occurred.
- No new external input or trust boundary; operates on data already fully computed
  in-process.

## Rollback considerations

- Single added `if`/`logger.warning` block; revert via `git checkout` or a targeted revert
  commit on `scripts/agent/repl.py`.
- No persisted-state or schema impact; rollback simply removes the log line with no other
  effect.
