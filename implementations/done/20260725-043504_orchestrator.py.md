## Goal

Ensure the allowed_tools override is scoped to the turn lifecycle and always restored, regardless of where exceptions occur within the turn processing pipeline.

## Scope

**In**: `scripts/agent/orchestrator.py` (Orchestrator._process_turn())
**Out**: Changes to tool policy enforcement, other configuration overrides

## Assumptions

1. Only `_process_turn()` modifies `ctx.cfg.tool.allowed_tools` per turn
2. Concurrent turns do not share the same `ctx.cfg.tool.allowed_tools` reference
3. The context manager approach (Option A) is preferred over instance variable approach (Option B)

## Design decisions

- Extract the allowed_tools override/restore logic into a context manager method `_tool_override()`
- This makes the scoping explicit and ensures the finally block always runs, even if an exception occurs during the yield
- Replace the try/finally in `_process_turn()` with `with self._tool_override(self._allowed_tools):`

## Alternatives considered

- **Keep try/finally but use instance variable for original value**: Would require tracking state across multiple methods; context manager is cleaner
- **Use a decorator instead of context manager**: Would be more complex; context manager is simpler and more Pythonic
- **Add assertions around concurrent access**: Would catch bugs but doesn't solve the root cause; context manager prevents it entirely

### Procedure

#### Step A: Add _tool_override context manager

Add after `_process_turn()` definition (or near other helper methods):

```python
@contextmanager
def _tool_override(self, allowed: list[str] | None):
    """Temporarily override allowed_tools for the duration of a turn."""
    original = self._ctx.cfg.tool.allowed_tools
    if allowed is not None:
        self._ctx.cfg.tool.allowed_tools = allowed
    try:
        yield
    finally:
        self._ctx.cfg.tool.allowed_tools = original
```

Key points:
- Uses `contextmanager` decorator from `contextlib`
- Saves original value before any modification
- Restores original value in finally block — guaranteed to run even on exception
- Handles None case — doesn't modify if no override specified

### Method

Extract ownership of tool override lifecycle into the orchestrator itself (`Orchestrator`). Use a context manager to make the scoping explicit and guarantee restoration via Python's finally semantics.

### Details

The core issue is that the allowed_tools override is managed manually via try/finally in `_process_turn()`, which has two problems:
1. If an exception occurs between the assignment and the finally block, the finally still runs — but this is fragile because it relies on the developer remembering to put the restore in the right place
2. The intent is implicit — readers must trace through the try/finally to understand the scope

By using a context manager:
- The scope is explicit — anything inside the `with` block is scoped to the override
- Restoration is guaranteed by Python's finally semantics — no chance of forgetting
- The code is more readable — the `with` statement clearly indicates temporary modification

The context manager handles both cases:
- When `allowed` is not None: saves original, sets override, yields, restores original
- When `allowed` is None: saves original, yields without modification, restores original (no-op)
