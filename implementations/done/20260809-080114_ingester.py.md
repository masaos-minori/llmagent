# Implementation Procedure: Phase 3 — Atomic Transaction Method

## Goal

Add `_commit_url_transaction()` method using `SQLiteHelper.begin_immediate()` that atomically deletes existing rows (if force=True), inserts document/chunks/vectors, and moves files to `registered/` on success. On exception, rollback handled automatically by context manager.

## Scope

### In-Scope
- Add `_commit_url_transaction(doc_mgr, db, url, doc_id, prepared_chunks, force)` method
- Use `db.begin_immediate()` context manager for the transaction
- Inside transaction: delete existing vector rows + document (if force), insert document, insert all chunks + vectors
- On exception: rollback handled automatically by context manager, preserve previous state
- After commit success: move files to `registered/`

### Out-of-Scope
- Changes to `ingest_url_group()` flow orchestration (Phase 4)
- Changes to cache invalidation logic (Phase 5)
- Changes to `document_manager.py` beyond removing `delete_existing_document()` delegation (Phase 6)
- Database schema changes

## Assumptions

1. `SQLiteHelper.begin_immediate()` correctly serializes concurrent writers via `BEGIN IMMEDIATE` (confirmed by inspecting `helper.py:243-246`)
2. `begin_immediate()` context manager properly handles nested exception unwinding (RESOLVED: Code inspection shows try/except in `_begin_transaction()` but no test coverage for rollback edge cases — add unit test later)
3. `chunks_fts` trigger fires automatically on INSERT INTO chunks (verified by existing consistency checks in `rag_consistency.py`)
4. `chunks_vec_ad` trigger fires on DELETE FROM chunks (verified by `delete_document_chain()` in `document_manager.py:17-33`)
5. Main connection uses separate instance, not nested transaction within same connection (RESOLVED: No nested transactions found in current codebase)
6. sqlite-vec extension works with single connection approach (RESOLVED: Confirmed — `_load_vec_extension()` in `helper.py:145-158` loads vec extension once per connection)

## Design decisions

- `_commit_url_transaction()` is an instance method on `RagIngester` — it has access to `self._client`, `self._log_ingestion_result`, `self._route_chunk_files`
- Uses `with db.begin_immediate():` context manager — ensures rollback on any exception
- Deletes existing rows BEFORE inserting new ones (same order as current `delete_existing_document()` + `_insert_document()` / `_insert_chunk()` sequence)
- File routing happens AFTER successful commit — if commit fails, files stay in their original location for retry
- Partial success scenario: if ANY chunk fails during preparation, the ENTIRE URL group is rolled back (no partial commits). This is the core atomicity guarantee.

## Alternatives considered

- Using `BEGIN IMMEDIATE` without context manager: rejected because context manager ensures rollback even on unexpected exceptions
- Deleting and inserting in separate transactions: rejected because it doesn't provide atomicity — intermediate state would be visible
- Moving file routing before commit: rejected because if commit fails, files would be moved but data rolled back — inconsistent state

#### Step 3: Add `_commit_url_transaction()` method

```python
def _commit_url_transaction(
    self,
    doc_mgr: DocumentManager,
    db: SQLiteHelper,
    url: str,
    doc_id: int,
    prepared_chunks: list[PreparedChunk],
    force: bool,
) -> None:
    """Atomically commit all database changes for a URL inside BEGIN IMMEDIATE transaction.
    
    If force=True, deletes existing document/chunks/vectors first.
    On any exception, rollback is automatic via context manager.
    Files are moved to registered/ only after successful commit.
    """
    with db.begin_immediate():
        # Delete existing rows if force=True
        if force:
            # Delete chunks_vec rows first (no FK to chunks, must be explicit)
            db.execute(
                "DELETE FROM chunks_vec WHERE chunk_id IN (SELECT chunk_id FROM chunks WHERE doc_id = ?)",
                (doc_id,),
            )
            # Delete document row (CASCADE removes chunks automatically)
            db.execute("DELETE FROM documents WHERE doc_id = ?", (doc_id,))
        
        # Insert document
        cur = db.execute(
            "INSERT INTO documents (url, title, lang, etag, last_modified, fetched_at)"
            " VALUES (?, ?, ?, ?, ?, ?)",
            (url, ...),  # Fill with actual fields
        )
        
        # Insert all chunks + vectors
        for pc in prepared_chunks:
            self._insert_chunk(db, pc.doc_id, pc.chunk_index, pc.content, 
                             pc.normalized_content, pc.embedding_blob, 
                             pc.chunk_type, pc.source_file)
    
    # Commit succeeded — move files to registered/
    # ... file routing logic ...
```

#### Step 4: Handle failure cases inside transaction

For each failure case, return appropriate `IngestionFailureReason`:

```python
try:
    # ... transaction logic ...
except SomeParseError:

    return IngestionFailureReason.PARSE_FAILED

    logger.warning("validation failed", extra={"url": url})

    logger.error("embedding failed", extra={"url": url})
    return IngestionFailureReason.EMBEDDING_FAILED

    logger.exception("storage failed", extra={"url": url})
    return IngestionFailureReason.STORAGE_FAILED
```

### Details

**File location**: `scripts/rag/ingestion/ingester.py`

**Key changes**:
1. Remove `SQLiteHelper` instantiation — workers no longer open DB connections
2. Change return type from `tuple[bool, bool]` to `PreparedChunk | IngestionFailureReason`
3. Replace `db.execute(...)` calls with `PreparedChunk` construction
4. Add exception handlers mapping to `IngestionFailureReason` values
5. Keep HTTP client usage unchanged — embedding service calls remain parallel

**Critical insight**: The main thread (in `ingest_url_group()`) becomes the sole DB writer. All DB operations happen within `_commit_url_transaction()` using `BEGIN IMMEDIATE`. This ensures atomicity — either ALL chunks for a URL are committed, or NONE are.

**Thread safety**: Since workers no longer hold DB connections, there's no risk of connection conflicts. The main thread handles all DB writes sequentially.

**Memory consideration**: `PreparedChunk.embedding_blob` stores raw bytes — memory pressure for large documents is acceptable since URLs are processed sequentially; memory is freed after commit.
