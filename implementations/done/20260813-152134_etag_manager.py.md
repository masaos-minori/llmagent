## Goal

Align ETag freshness handling with transaction ownership by removing internal commits and using proper datetime comparison instead of fragile lexical string comparison.

## Scope

**In-Scope:**
- Remove `self._db.commit()` calls from `_update_with_freshness()` and `_update_null_fill()`.
- Refactor `_is_stale_update()` to use timezone-aware UTC datetime parsing instead of lexical string comparison.
- Add explicit error handling for invalid/malformed timestamp strings.
- Update tests to verify rollback behavior and datetime comparison correctness.

**Out-of-Scope:**
- Modifying source code behavior beyond diagnostic improvements.
- Updating documentation (`docs/*.md`).
- Changing the core ingestion or pipeline orchestration logic.

## Assumptions

- Callers of `ETagManager.update()` will manage their own transactions (including commit/rollback).
- **Verified assumption**: `document_manager.py` calls `ETagManager.update()` within an outer transaction (confirmed by inspecting caller code).
- Timezone-aware UTC datetimes are available via Python's standard library (`datetime.timezone.utc`).
- Invalid timestamps should be treated as non-stale (conservative fallback).

## Design decisions

- **Remove internal commits**: Transaction ownership belongs to callers. Internal commits break atomicity across multiple operations.
- **Datetime parsing over lexical comparison**: ISO-8601 strings with mixed timezone formats (e.g., `Z` vs `+09:00`) produce incorrect results under lexical comparison. Use `datetime.fromisoformat()` for correct comparison.
- **Conservative fallback for invalid timestamps**: Treat invalid timestamps as non-stale rather than rejecting the update — prevents false negatives on edge cases.

## Alternatives considered

- **Keep internal commits but add a `transaction_owner` flag**: Adds complexity without solving the root problem (who owns the transaction?). Rejected.
- **Use `time.strptime()` instead of `fromisoformat()`**: Less robust for timezone handling. Rejected.
- **Reject updates on invalid timestamps**: Too aggressive; could block valid updates. Rejected in favor of conservative fallback.

### Details

- Both methods now rely on caller-managed transactions. If the caller fails to commit, changes remain uncommitted and visible only within the current transaction scope.
- `datetime.fromisoformat()` handles ISO-8601 variants including `Z` suffix and timezone offsets like `+09:00`.
- The `.replace("Z", "+00:00")` call normalizes the `Z` suffix before parsing.
- Invalid timestamps are logged and treated as non-stale — the update proceeds conservatively.
