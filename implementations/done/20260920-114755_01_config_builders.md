# Implementation Procedure: Refactor config_builders.py — eliminate _extract_fields anti-pattern

## Goal

Eliminate the `_extract_*_fields` → dict → spread anti-pattern in `scripts/agent/config_builders.py`, replace `{**...}` spreading with explicit keyword arguments, move inline validation to dataclass `__post_init__`, remove `sys.exit(1)`, and extract module-level imports. REQ-001, REQ-002, REQ-004, REQ-005, REQ-006.

## Scope

Modify exactly one file: `scripts/agent/config_builders.py`. No other file modification targets — `scripts/agent/config_dataclasses.py` and `scripts/agent/constants.py` are reference files only (confirmed no changes needed).

## Assumptions

- All 9 dataclasses already have `__post_init__` methods that can absorb inline validation (confirmed via evidence review).
- The public API boundary (`build_agent_config()`, `load_config()`, `ConfigLoadError`) remains unchanged.
- `constants.py` IS the canonical source for `_DEFAULT_*` tables (confirmed by docstring at line 7-10). Defaults currently duplicated in `_extract_*_fields` extractors should be consolidated to `constants.py` where possible, or moved to dataclass field defaults where they are domain-specific.
- The tier check in `_extract_approval_tool_fields` (lines 406–411) and dry-run validation in `_extract_approval_tool_fields` (lines 399–402) can safely move to `ApprovalConfig.__post_init__` since it already calls `_v_app_tier(self)`.

## Design decisions

1. **Path A classification**: This task affects ≤ 3 files, no public interface changes, no DB schema changes → limited to direct-verification inspection only.
2. **Default consolidation strategy**: Move defaults from `_extract_*_fields` extractors to their respective dataclass field defaults where domain-appropriate. For cross-domain defaults (approval-related), keep them in `constants.py` as `_DEFAULT_*` tables.
3. **Validation migration**: Move inline validation from `_extract_approval_tool_fields` (tier check) and `_build_approval_config` (dry-run validation) to `ApprovalConfig.__post_init__`. Use existing validator functions from `agent.services.config_validators` where available.
4. **Import extraction**: Move `from shared.tool_registry import get_registry` from `_resolve_config_source_and_registry` (line 464) to module-level import alongside other shared imports.
5. **Error handling**: Replace `sys.exit(1)` in `_run_production_validation` with raising `ConfigReloadValidationError` or returning error results tuple.

## Alternatives considered

1. **Keep `_extract_*_fields` but rename to `_get_*_field`**: Would reduce dict-spreading but retain the indirect pattern. Rejected because the fundamental anti-pattern (indirect field mapping) would remain.
2. **Inline validation in builder instead of `__post_init__`**: Would avoid dataclass dependency but violate REQ-004 which requires validation in `__post_init__` or dedicated validators.
3. **Remove `sys.exit(1)` and return None**: Would change the caller contract. Better to raise an exception so callers can handle it consistently.

## Compatibility considerations

- Public API boundary (`build_agent_config()`, `load_config()`, `ConfigLoadError`) remains unchanged.

- Module-level import of `shared.tool_registry` may cause circular import issues — test import order; use lazy import pattern if circular dependency detected.
- Inline validation moved to `__post_init__` may change error timing (validation now happens at construction time vs. build time) — verify that `ConfigReloadValidationError` is raised consistently in both paths.

## Security considerations

- Tier validation logic preserved in `__post_init__` via `_v_app_tier`.
- Dry-run tool filtering preserved in builder before dataclass construction.
- Production config validation errors now propagate as exceptions instead of terminating the process — ensure calling code handles this appropriately.
