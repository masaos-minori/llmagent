## Assumptions
- **Blocking discovery carried forward from row 01**: `tools/check_canonical_source_conflicts.py`
  currently exits 0 with zero findings against the real registry — not because the
  registry is clean, but because its fallback TOML parser cannot read the actual
  `[[canonical_sources]]` array-of-tables structure at all, and
  `tools/check_canonical_source_registry.py` (the tool it is supposed to wrap,
  `M-01-04`) does not exist yet either. Wiring this tool into CI as a blocking step
  **before** row 01's schema reconciliation lands would add a blocking check that
  always passes regardless of actual registry state — a false sense of enforcement,
  not real enforcement. This row's own Phase 0 gate (below) reflects that ordering
  requirement explicitly, going beyond the Plan's own stated Phase 0 (which only
  gates on `M-01-04` existing, not on row 01's schema fix landing on top of it).
- The workflow file's existing two patterns (plain blocking step; `continue-on-error:
  true` report-only step) are both directly reusable — no new CI mechanism is
  needed.

## Design decisions
- Add the new step as **blocking** (no `continue-on-error`), matching REQ-010's
  explicit requirement and the existing "Run Needs Confirmation inventory checks"/
  "Run dependency graph cycle check" pattern — not the report-only Front Matter
  pattern, which REQ-010 explicitly says not to follow for this tool.
- Place it between those two existing blocking steps and the report-only Front
  Matter step, per the Plan's own Design section ("after the existing
  `check_dependency_graph_cycles.py` step, before the report-only front-matter
  step").

## Alternatives considered
- Wire the step now with `continue-on-error: true` as an interim measure until row
  01 lands, then tighten to blocking later: rejected — REQ-010 explicitly requires
  a blocking step, and Design section's Risk mitigation for `GV-016` ("no
  unimplemented auto-checks documented as implemented") argues against any
  interim state that could be mistaken for real enforcement — better to defer this
  row entirely (Blocker Log) than land a weakened version that Phase 3's own next
  step (seq 06, Matrix update) might then prematurely mark "Existing" against.
