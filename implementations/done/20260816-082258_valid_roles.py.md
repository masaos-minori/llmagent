# Implementation Procedure: Make SessionMessageRepository._VALID_ROLES configurable

## Goal

Make `_VALID_ROLES` extensible so that new role types can be added without modifying `session_message_repo.py`, while preserving backward compatibility with the existing hardcoded default set {"user", "assistant", "tool", "system"}.

## Scope

- Add a `MessageRoleConfig` dataclass to `scripts/agent/config_dataclasses.py`
- Integrate it into `AgentConfig` as a new field
- Modify `SessionMessageRepository` to accept an optional roles source (config, callable, or fallback to default)
- Update docstrings and add tests
- No changes to DB schema, fetch logic, or message serialization

## Assumptions

1. The project already has a well-established configuration pattern via `AgentConfig` composition in `config_dataclasses.py`
2. The four usages of `_VALID_ROLES` in `session_message_repo.py` (save, save_many, replace_messages) should all respect the configured roles
3. Backward compatibility means: when no custom roles are provided, behavior must remain identical to current (default set = {"user", "assistant", "tool", "system"})
4. The `LLMMessage` TypedDict in `shared/types.py` uses `Literal["user", "assistant", "tool", "system"]` — extending it would require coordination across layers

## Unknowns

1. Will any downstream consumers (e.g., MCP servers, external tools) send non-standard roles? If not, the benefit of configurability may be limited.
2. Should the `LLMMessage` TypedDict Literal type also be extended, or kept separate from the runtime validation set?
3. Does the `strict_mode` flag semantics change if invalid roles come from a trusted config source vs. untrusted input?
4. Are there any existing TOML config files that could serve as a natural home for role definitions?

## Design decisions

- Add `MessageRoleConfig` dataclass with `allowed_roles: frozenset[str]` field defaulting to `frozenset({"user", "assistant", "tool", "system"})`
- Compose into `AgentConfig` as `messages: MessageRoleConfig = field(default_factory=MessageRoleConfig)`
- `SessionMessageRepository.__init__` gains optional `roles_source: frozenset[str] | None = None` parameter
- Module-level `_VALID_ROLES` renamed to `_DEFAULT_VALID_ROLES` and used only as fallback
- Avoid circular imports by keeping injection point simple (frozenset parameter, not config object)

## Alternatives considered

1. **Use a callback/function instead of frozenset**: Would allow dynamic role computation but adds complexity. Frozenset is simpler and sufficient for most use cases.
2. **Add roles to existing config section**: Could add to an existing config section rather than creating a new one. But roles are conceptually distinct from other config concerns.
3. **Keep module-level constant and add subclass**: Subclass `SessionMessageRepository` with different `_VALID_ROLES`. But this creates inheritance complexity and doesn't solve the root problem of needing multiple configurations simultaneously.

## Compatibility considerations

- Adding optional field to `AgentConfig` is backward-compatible
- Renaming `_VALID_ROLES` to `_DEFAULT_VALID_ROLES` is internal — no external API contract
- If any code catches `ValueError` from the helper, it could conflict with other ValueError uses
- Extending roles beyond the four standard ones breaks the `LLMMessage.role` Literal type in `shared/types.py`

## Security considerations

N/A — no security implications. Only changes configuration handling.

## Rollback considerations

- Revert `MessageRoleConfig` dataclass addition
- Remove `messages` field from `AgentConfig`
- Restore `_VALID_ROLES` name in `session_message_repo.py`
- Remove `roles_source` parameter from `SessionMessageRepository.__init__`
- No database or config changes to revert

## Validation plan

- Unit test: `test_custom_roles_injection` — verify save/save_many/replace_messages reject roles outside the custom set
- Unit test: `test_default_roles_fallback` — verify no regression when `roles_source=None`
- Unit test: `test_strict_mode_with_custom_roles` — verify strict mode raises correctly for custom invalid roles
- Integration test: verify `AgentConfig.messages.allowed_roles` is properly composed and accessible
- Run full existing test suite (`uv run pytest`) to confirm no regressions
- Manual check: verify no other callers depend on `_VALID_ROLES` being exactly `{"user", "assistant", "tool", "system"}`

## Out of scope

- Changes to `LLMMessage` TypedDict Literal type in `shared/types.py`
- Changes to how roles are validated in other parts of the system
- Changes to TOML schema documentation (separate concern)
- Changes to message serialization format

def test_custom_roles_injection():
    repo = SessionMessageRepository(session_id=1, roles_source=frozenset({"custom_role"}))
    assert repo.get_valid_roles() == frozenset({"custom_role"})
    # Invalid role should be rejected
    with pytest.raises(RuntimeError):
