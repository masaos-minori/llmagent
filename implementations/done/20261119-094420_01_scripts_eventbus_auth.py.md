## Assumptions
- Behavior is unchanged for REQ-001 and REQ-002: the dedicated `admin_token` block already overwrote the entry that the per-role loop wrote, so the final principal map is identical (verified in Step 3a by reading `_build_principal_map`).
- In `resolve_principal`, `request.app.state.config` is read only to feed `get_auth_token`, so the local `config` variable goes with it (verified in Step 3a).
- `get_auth_token` has no caller other than `resolve_principal`; the generated reference table and the manifest mention it and are regenerated by the seq 08 and seq 09 documents (verified in Step 3a).
- The name `attach_request_id_middleware` (new) is a judgment call recorded in the Plan; no symbol with that name exists.
- The `_fingerprint` nested helper and the duplicate `hashlib` import in this file belong to the EventBus task supervision issue and MUST NOT be touched here.

## Design decisions
- Delete the `admin_token` pair from `_PER_ROLE_TOKEN_FIELDS` and keep the dedicated control-plane block as the only build of that principal.
- Delete `get_auth_token` instead of keeping it: nothing calls it, and the Current-Specification-Only policy forbids dead fallbacks.
- Rename only the EventBus function; the nested `_request_id_middleware` keeps its name.

## Alternatives considered
- Merge the `auth_token` and `admin_token` blocks into one loop over the control-plane tokens: rejected, it widens the change beyond the Plan and touches more of the function than REQ-001 needs.
- Keep `get_auth_token` for tests: rejected, no test references it.
- Keep a deprecated alias for the old function name: rejected, aliases are forbidden by the Current-Specification-Only policy and every caller is in the Plan.
