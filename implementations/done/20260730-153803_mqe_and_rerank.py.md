## Goal

Make the RAG pipeline resilient to LLM-side failures by adding explicit fallback paths: MQE failure falls back to original query; rerank failure falls back to RRF-ranked results.

## Scope

**In-Scope:**
- Add MQE failure fallback: when expand_queries() raises, set ctx.queries = [ctx.query]
- Add rerank failure fallback: when cross_encoder_rerank() raises, use ctx.merged directly
- Update stage status reporting to distinguish disabled vs failed-with-fallback
- Ensure AugmentStage always receives usable reranked hits when search and fusion succeed
- Add comprehensive tests for both fallback scenarios

**Out-of-Scope:**
- Changes to SQLite schema
- Changes to embedding service
- Changes to RRF fusion logic
- Changes to augment formatting

## Assumptions

1. MQE fallback uses the original query unchanged — no attempt to retry or modify the query.
2. Rerank fallback applies deduplicate_chunks() + rag_top_k slicing to ctx.merged (same as _rerank_fallback()).
3. Fallback reasons are recorded as distinct strings: "mqe_exception" and "rerank_exception".
4. Both fallbacks should be logged at INFO level for observability.
5. The fallback behavior should apply only on LLM exceptions, not on configuration errors.

## Design decisions

- **Exception-specific fallback**: Catch specific LLM exception types (not bare `except Exception`) to avoid masking unrelated errors. Use RagLLM exception types defined in llm_client.py.
- **MQE fallback simplicity**: Use the original query unchanged rather than attempting retries or modifications. This avoids cascading failures.
- **Rerank fallback preserves ordering**: Apply deduplicate_chunks() + rag_top_k slicing to ctx.merged, maintaining RRF ranking order without relevance scoring.
- **Status distinction**: Return "fallback" status (distinct from "disabled") so operators can distinguish intentional feature disablement from runtime failures.

## Alternatives considered

- **Catch bare `Exception`**: Could catch all exceptions instead of specific LLM types. Rejected because it would mask unrelated errors (e.g., configuration errors).
- **Retry before fallback**: Could retry the LLM call once before falling back. Rejected because LLM failures are typically transient and retrying wastes time; the fallback provides immediate resilience.
- **Raise instead of fallback**: Could propagate the exception up the pipeline. Rejected because the pipeline should continue operating with degraded quality rather than failing entirely.

## Implementation

### Target files

`scripts/rag/stages/mqe.py`, `scripts/rag/stages/rerank.py`, `scripts/rag/pipeline.py`

### Procedure

#### Phase 1: Add MQE failure fallback

1. In `MqeStage.run()`, locate the `_run_mqe()` call.
2. Wrap the call in try/except to catch LLM exceptions:
   ```python
   # Before:
   ctx.queries = self._run_mqe(ctx)
   
   # After:
   try:
       ctx.queries = self._run_mqe(ctx)
   except RagLLMError as e:
       logger.info(f"MQE failed ({e}), using original query as fallback")
       ctx.queries = [ctx.query]
       result.fallback_reason = "mqe_exception"
   ```

3. On exception, set `ctx.queries = [ctx.query]` (original query fallback).
4. Log INFO message: "MQE failed, using original query as fallback".
5. Record fallback reason "mqe_exception" in StageResult.

#### Phase 2: Add rerank failure fallback

1. In `RerankStage.run()`, locate the `_rerank()` call.
2. Wrap the call in try/except to catch LLM exceptions:
   ```python
   # Before:
   ctx.reranked = self._rerank(ctx)
   
   # After:
   try:
       ctx.reranked = self._rerank(ctx)
   except RagLLMError as e:
       logger.info(f"Rerank failed ({e}), using RRF-ranked results as fallback")
       # Compute fallback from ctx.merged
       top_k = cfg.rag_top_k if hasattr(cfg, 'rag_top_k') else DEFAULT_TOP_K
       ctx.reranked = deduplicate_chunks(ctx.merged[:top_k])
       result.fallback_reason = "rerank_exception"
   ```

3. On exception, compute fallback from `ctx.merged`: slice to cfg.rag_top_k, then deduplicate_chunks().
4. Set `ctx.reranked` to the deduplicated merged results.
5. Log INFO message: "Rerank failed, using RRF-ranked results as fallback".
6. Record fallback reason "rerank_exception" in StageResult.

#### Phase 3: Update stage status reporting

1. Modify `_mqe_status()` in `pipeline.py` to return "fallback" with reason "mqe_exception" when MQE failed but fallback was applied:
   ```python
   def _mqe_status(self) -> Dict[str, Any]:
       if not self.use_mqe:
           return {"status": "disabled", "reason": "use_mqe=False"}
       if getattr(self, '_mqe_failed', False):
           return {"status": "fallback", "reason": "mqe_exception"}
       return {"status": "ok"}
   ```

2. Modify `_rerank_status()` similarly:
   ```python
   def _rerank_status(self) -> Dict[str, Any]:
       if not self.use_rerank:
           return {"status": "disabled", "reason": "use_rerank=False"}
       if getattr(self, '_rerank_failed', False):
           return {"status": "fallback", "reason": "rerank_exception"}
       return {"status": "ok"}
   ```

3. Keep existing "use_mqe=False" / "use_rerank=False" fallback reasons unchanged.

## Compatibility considerations

- Existing successful pipeline flow is unchanged — only failure paths are affected.
- Test assertions expecting "failure" status for LLM exceptions need updating to "fallback".
- Operators monitoring stage status will see "fallback" instead of "failure" — update any dashboards/alerts accordingly.
- The fallback behavior applies only on LLM exceptions, not on configuration errors — preserving existing error handling for config issues.

## Security considerations

- No new secrets or credentials introduced.
- Logging includes exception messages — ensure no sensitive data leaks through log output (e.g., API keys embedded in LLM responses).
- Fallback queries/results do not introduce new attack surfaces.

## Rollback considerations

- Removing the try/except blocks restores the previous hard-failure behavior.
- Reverting the status reporting changes removes the "fallback" distinction.
- The fallback logic is additive — removing it does not affect any other pipeline components.
