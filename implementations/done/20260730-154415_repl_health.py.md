## Goal

Connect MCP `/health` schema, probe model, and status interpretation so the Agent can consistently interpret and display dependency failures, readiness state, restart recommendations, and operator-action requirements.

## Scope

**In-Scope:**
- Update /mcp status in repl_health.py to show interpreted health fields
- Update startup summary to include health interpretation results
- Update operational logs to log dependency failures and parse failures

**Out-of-Scope:**
- Changes to MCP transport layer (SSE/HTTP)
- Changes to MCP authentication protocol itself
- Changes to make_health_response() in mcp_servers
- Changes to health_models.py (covered by separate implementation procedure)

## Assumptions

1. The common /health schema from make_health_response() is stable and will not change frequently.
2. Parse failures should never crash the Agent — they should be logged and surfaced as warnings.
3. The interpretation helpers defined in health_models.py are available for use.

## Design decisions

- **Truncated details**: Truncate details summary to first N characters rather than dumping full JSON to avoid excessive output.
- **Dual status display**: Show both self-reported status (from /health) and Agent-observed status (from registry) side-by-side for clarity.
- **Parse failure visibility**: Surface parse_failure_reason in /mcp status output so operators know when the Agent couldn't interpret the health response.

## Alternatives considered

- **Full JSON dump of details**: Could show complete details object. Rejected because it produces excessive output when details contains large JSON objects.
- **Separate /mcp subcommands**: Could create separate /mcp health and /mcp status commands. Rejected because a single command with clear sections is more discoverable.

### Procedure

#### Phase 5: Surface useful status information

1. Update /mcp status command in `repl_health.py` to show interpreted health fields:
   ```python
   async def _handle_mcp_status(self, ...) -> None:
       # For each MCP server, show:
       # - Self-reported status vs Agent observed status
       # - Dependency failures (summarized)
       # - Details summary (truncated, not full JSON dump)
       # - Restart recommendation
       # - Operator action requirement
       
       for server_name, result in sorted(probe_results.items()):
           # Display Agent-observed health
           print(f"[{server_name}]")
           
           # Display self-reported health via interpretation
           try:
               interpretation = interpret_health_body(result.body)
               
               # Status comparison
               print(f"  Self-reported: {interpretation.self_reported_status}")
               print(f"  Agent observed: {'reachable' if result.reachable else 'unreachable'}")
               
               # Ready state
               print(f"  Ready: {interpretation.ready}")
               
               # Dependency failures
               if interpretation.dependency_summary:
                   print(f"  Dependencies:")
                   for dep in interpretation.dependency_summary:
                       print(f"    - {dep}")
               
               # Details summary (truncated)
               if interpretation.details_summary:
                   max_detail_len = 200
                   detail_text = "; ".join(interpretation.details_summary)
                   if len(detail_text) > max_detail_len:
                       detail_text = detail_text[:max_detail_len] + "..."
                   print(f"  Details: {detail_text}")
               
               # Action items
               if interpretation.restart_recommended:
                   print(f"  [!] Restart recommended")
               if interpretation.operator_action_required:
                   print(f"  [!] Operator action required")
                   
               # Parse failure
               if interpretation.parse_failure_reason:
                   print(f"  [!] Parse failure: {interpretation.parse_failure_reason}")
           except Exception as e:
               print(f"  [!] Interpretation error: {e}")
   ```

2. Update startup summary to include health interpretation results:
   ```python
   # During startup, after probing MCP servers:
   for server_name, result in sorted(probe_results.items()):
       try:
           interpretation = interpret_health_body(result.body)
           if not interpretation.ready or interpretation.restart_recommended:
               logger.warning(
                   f"MCP server '{server_name}' health: "
                   f"ready={interpretation.ready}, "
                   f"restart_recommended={interpretation.restart_recommended}"
               )
       except Exception:
           # Non-crashing on parse failure
           logger.debug(f"Failed to interpret health for '{server_name}': {e}")
   ```

3. Update operational logs to log dependency failures and parse failures:
   ```python
   # When processing health probe results:
   for server_name, result in probe_results.items():
       try:
           interpretation = interpret_health_body(result.body)
           if interpretation.dependency_summary:
               logger.warning(
                   f"MCP server '{server_name}' has dependency failures: "
                   f"{', '.join(interpretation.dependency_summary)}"
               )
           if interpretation.parse_failure_reason:
               logger.warning(
                   f"MCP server '{server_name}' health parse failure: "
                   f"{interpretation.parse_failure_reason}"
               )
       except Exception as e:
           logger.debug(f"Failed to process health for '{server_name}': {e}")
   ```

## Compatibility considerations

- The updated /mcp status output format changes what operators see — ensure any automated parsing of /mcp status output is updated accordingly.
- Startup summary changes add warning-level logging for unhealthy MCP servers — existing monitoring/alerting based on these logs may trigger new alerts.
- Parse failure handling remains non-crashing — preserving existing resilience behavior.

## Security considerations

- No security implications from this change — the interpretation helpers only read and format existing health data.
- Details truncation prevents potential information leakage through excessively long detail outputs.

## Rollback considerations

- Removing the interpretation logic from /mcp status reverts to displaying raw McpHealthProbeResult fields.
- Removing the startup summary changes eliminates the new warning-level logging for unhealthy MCP servers.
- The parse failure handling is additive — removing it does not affect other functionality.
