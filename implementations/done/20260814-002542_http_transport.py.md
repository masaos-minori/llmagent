# Implementation Procedure: scripts/shared/http_transport.py

## Goal

Make `HttpTransport.call()` stop retrying HTTP status codes that are not in
`_RETRYABLE_STATUS`, and make the "retry exhausted" failure message retain
the last caught exception's context (type/status code) instead of a bare
`"[Retry exhausted] ..."` string.

## Scope

In scope:
- `HttpTransport.call`'s `except httpx.HTTPStatusError as e:` block
  (currently `scripts/shared/http_transport.py:133-139`).
- The `for...else` "retry exhausted" branch (currently
  `scripts/shared/http_transport.py:142-145`).

Out of scope (per plan, verified unchanged by this procedure):
- `_RETRYABLE_STATUS = frozenset({429, 502, 503, 504})` (line 69) — membership
  unchanged.
- The `resp.status_code in self._RETRYABLE_STATUS` pre-check at line 114 and
  its `continue`-based retry path (lines 114-125) — unchanged.
- Backoff formula (`2 ** (self._RETRY_MAX - attempt - 1)`, line 115),
  `_RETRY_MAX` (line 70), and `_transport_error()`'s signature (lines 72-89).

## Assumptions

- Grounded by reading `scripts/shared/http_transport.py:60-147` directly
  (current source, not just the plan's line-number references, which match
  but are worth re-confirming immediately before editing per the plan's own
  Phase 1 step).
- Structural nuance not spelled out in the plan's Design section: because
  the retryable-status pre-check at line 114 already `continue`s (skipping
  `resp.raise_for_status()` at line 126) whenever `resp.status_code in
  self._RETRYABLE_STATUS`, `resp.raise_for_status()` — and therefore the
  `except httpx.HTTPStatusError` handler — can only ever fire for a status
  code that is *not* in `_RETRYABLE_STATUS`. In other words, every
  `HTTPStatusError` reaching the handler at lines 133-139 is, by
  construction, already non-retryable today. The plan's prescribed
  `e.response.status_code in self._RETRYABLE_STATUS` branch inside the
  handler is therefore always-false in the current call graph — but it is
  kept per the plan's explicit design (mirrors the `TimeoutException`
  handler's idiom, stays correct if the pre-check at line 114 is ever
  restructured) rather than special-cased away as dead code, since removing
  it would silently change behavior if line 114's pre-check logic is later
  edited independently of this handler.
- No production code parses the `TransportError` message text (verified via
  the plan's UNK-01 resolution: `tool_executor.py:144` and
  `tool_transport_invoker.py:206` catch by type only) — so enriching the
  exhausted-retry message string is safe.

## Design decisions

- Mirror the existing `except httpx.TimeoutException` idiom (lines 129-132):
  call `self._transport_error(...)` with `break_flag=True` to raise
  immediately, rather than introducing a new control-flow shape (e.g. a
  `raise` statement or a new helper).
- Keep `health_check=False` on the `HTTPStatusError` branch exactly as today
  (no behavior change to the health-check suffix).
- Thread `last_exc` into the retry-exhausted message via simple f-string
  interpolation (`{last_exc}`) rather than restructuring the message format,
  to keep the "Retry exhausted" / "after N attempts" substrings intact for
  the two tests that assert on them
  (`test_retries_exhausted_returns_error`,
  `test_http_503_retry_exhaustion_is_transport_error`).

## Alternatives considered

N/A — plan specifies the approach (mirror the `TimeoutException` idiom); no
other design was evaluated.

## Implementation

### Target file

`scripts/shared/http_transport.py`

### Procedure

1. In the `except httpx.HTTPStatusError as e:` block (lines 133-139), branch
   on `e.response.status_code in self._RETRYABLE_STATUS`:
   - True → keep today's call exactly as-is (no `break_flag`).
   - False → same `_transport_error(...)` call, adding `break_flag=True`.
2. In the `for...else` branch (lines 142-145), interpolate `last_exc` into
   the raised message.

### Method

Single `if`/`else` added inside the existing `except httpx.HTTPStatusError`
block; one f-string edit in the `else` clause of the `for` loop. No new
imports, no new helper functions, no change to `_transport_error()`'s
signature.

### Details

Current code (lines 133-145):

```python
            except httpx.HTTPStatusError as e:
                last_exc = self._transport_error(
                    name,
                    "[HTTPStatusError]",
                    f"status={e.response.status_code} response={e.response.text[:300]!r}",
                    health_check=False,
                )
            except (httpx.RequestError, ValueError) as e:
                last_exc = self._transport_error(name, f"[{type(e).__name__}]", str(e))
        else:
            msg = f"[Retry exhausted] tool={name} url={self._base_url} after {self._RETRY_MAX} attempts"
            logger.error(msg)
            raise TransportError(msg)
        raise last_exc or TransportError(f"call failed: {name}")
```

Target code:

```python
            except httpx.HTTPStatusError as e:
                last_exc = self._transport_error(
                    name,
                    "[HTTPStatusError]",
                    f"status={e.response.status_code} response={e.response.text[:300]!r}",
                    break_flag=e.response.status_code not in self._RETRYABLE_STATUS,
                    health_check=False,
                )
            except (httpx.RequestError, ValueError) as e:
                last_exc = self._transport_error(name, f"[{type(e).__name__}]", str(e))
        else:
            msg = (
                f"[Retry exhausted] tool={name} url={self._base_url} "
                f"after {self._RETRY_MAX} attempts: {last_exc}"
            )
            logger.error(msg)
            raise TransportError(msg)
        raise last_exc or TransportError(f"call failed: {name}")
```

Note: `break_flag=e.response.status_code not in self._RETRYABLE_STATUS`
expresses the same branch as an explicit `if`/`else` in one line, consistent
with `_transport_error`'s existing `break_flag: bool = False` keyword-only
parameter. Either this inline form or an explicit `if e.response.status_code
in self._RETRYABLE_STATUS: ... else: ...` with two separate
`_transport_error(...)` calls satisfies the plan; the inline form avoids
duplicating the `_transport_error(...)` call's other three arguments.

## Compatibility considerations

- `TransportError` remains a plain `Exception` subclass with only a message
  — no signature change. Callers that catch by type
  (`tool_executor.py:144`, `tool_transport_invoker.py:206`) are unaffected.
- Retryable statuses (429/502/503/504) are unreachable by this handler today
  (see Assumptions) — no observable behavior change for them either way.
- Message text changes (adding `last_exc` detail to the retry-exhausted
  message) are additive/substring-preserving, not a format break, per the
  plan's Risks section (both consumers of that message use substring
  containment, not exact match).

## Security considerations

- No new user-controlled data enters the message beyond what
  `_transport_error` already logs (`e.response.text[:300]`, already
  truncated); no new logging of secrets/headers introduced.
- `bandit scripts/shared/http_transport.py` reported zero findings before
  this change (per plan's Design section); this change adds no new
  I/O, deserialization, or subprocess calls, so the baseline is expected to
  hold.

## Rollback considerations

- Single-method, single-file change with no new imports or cross-file
  dependency; revert by restoring the two edited blocks (`except
  httpx.HTTPStatusError` handler and the `for...else` message) to the
