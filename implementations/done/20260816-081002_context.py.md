# Implementation Procedure: Add asyncio.Lock to ConversationState.history access

## Goal

Make the asyncio single-threaded assumption explicit for ConversationState.history access by adding a class-level asyncio.Lock, and convert the three history mutation methods (append_message, extend_messages, replace_history) from synchronous to async.

## Scope

- `scripts/agent/context.py`: ConversationState class only

## Assumptions

1. asyncio is single-threaded; coroutines do not interleave except at await points
2. All history mutations within a single turn execute sequentially without yielding
3. Background tasks spawned during a turn may access history after await points, creating potential interleaving windows
4. The existing TurnState._lock pattern is the preferred approach for similar mutable state
5. Adding a Lock will not change runtime behavior under normal operation, only make the assumption explicit

## Design decisions

- Follow jsonl_store.py pattern for lazy lock initialization: `_history_lock: asyncio.Lock | None = None` field + `_ensure_lock` property
- Convert all three methods to async with `async with self._ensure_lock:` wrapping
- Class-level lock shared across instances (following TurnState._lock pattern)
- Document the asyncio assumption in class docstring

## Alternatives considered

1. **Document-only approach (Option B)**: Add class-level docstring explaining asyncio single-threaded model. Minimal risk, no API change. But does not enforce the invariant.
2. **Separate locks per method**: Would allow finer-grained concurrency but adds complexity and memory overhead. Not needed since history mutations are always sequential within a turn.
3. **Eager lock creation**: Creates asyncio.Lock at dataclass construction time. Fails if event loop hasn't started yet. Lazy initialization required.

New class:
```python
@dataclass
class ConversationState:
    """Per-session conversation fields.

    History access is synchronized via asyncio.Lock. The asyncio single-threaded
    model means coroutines do not interleave except at await points. If concurrent
    access ever becomes possible (e.g., multi-loop), locking must be added here.
    """

    _history_lock: asyncio.Lock | None = None
    history: list[LLMMessage] = field(default_factory=list)
    llm_url: str = ""
    debug_mode: bool = False
    plan_mode: bool = False
    system_prompt_name: str = "default"
    system_prompt_content: str = ""
    shutdown_requested: bool = False
    is_processing: bool = False
    memory_disabled: bool = False
    memory_warning_shown: bool = False

    @property
    def _ensure_lock(self) -> asyncio.Lock:
        if self._history_lock is None:
            self._history_lock = asyncio.Lock()
        return self._history_lock

    async def append_message(self, msg: LLMMessage, *, source: str = "") -> None:
        async with self._ensure_lock:
            check_view: dict[str, Any] = dict(msg, source=source) if source else dict(msg)
            result = validate_message(check_view)
            if result.success:
                self.history.append(msg)
                return
            role = msg.get("role", "<unknown>")
            logger.warning(
                "Sanitizing invalid message (role=%s, source=%s): %s",
                role,
                source or "<none>",
                result.reason,
            )
            sanitized = _sanitize_message(msg, source=source)
            if sanitized is None:
                logger.error(
                    "Dropping message after sanitization removed required fields (role=%s)",
                    role,
                )
                return
            self.history.append(sanitized)

    async def extend_messages(self, msgs: list[LLMMessage], *, source: str = "") -> None:
        async with self._ensure_lock:
            for msg in msgs:
                await self.append_message(msg, source=source)

    async def replace_history(self, msgs: list[LLMMessage], *, source: str = "") -> None:
        async with self._ensure_lock:
            self.history = []
            for msg in msgs:
                await self.append_message(msg, source=source)
```

Note on nested lock acquisition: `extend_messages` and `replace_history` acquire the lock first, then call `append_message` which also tries to acquire the same lock. Since asyncio.Lock is not reentrant, this would cause a deadlock. Solution: extract the inner body of `append_message` into a private `_append_message_locked` method that does NOT acquire the lock, and have both the public `append_message` and the callers (`extend_messages`, `replace_history`) decide which variant to call based on whether the lock is already held.

Alternative approach to avoid nested lock issue:
```python
async def append_message(self, msg: LLMMessage, *, source: str = "") -> None:
    async with self._ensure_lock:
        await self._append_message_locked(msg, source=source)

async def _append_message_locked(self, msg: LLMMessage, *, source: str = "") -> None:
    """Append a validated message. Caller MUST hold the lock."""
    check_view: dict[str, Any] = dict(msg, source=source) if source else dict(msg)
    result = validate_message(check_view)
    if result.success:
        self.history.append(msg)
        return
    role = msg.get("role", "<unknown>")
    logger.warning(...)
    sanitized = _sanitize_message(msg, source=source)
    if sanitized is None:
        logger.error(...)
        return
    self.history.append(sanitized)

async def extend_messages(self, msgs: list[LLMMessage], *, source: str = "") -> None:
    async with self._ensure_lock:
        for msg in msgs:
            await self._append_message_locked(msg, source=source)

async def replace_history(self, msgs: list[LLMMessage], *, source: str = "") -> None:
    async with self._ensure_lock:
        self.history = []
        for msg in msgs:
            await self._append_message_locked(msg, source=source)
```

This avoids the deadlock by having `append_message` acquire the lock and delegate to `_append_message_locked` (which assumes the lock is held). Callers like `extend_messages` and `replace_history` acquire the lock themselves and call `_append_message_locked` directly.
