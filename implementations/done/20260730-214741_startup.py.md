# Implementation Procedure: Consistent Error Handling for MCP Server Health Checks

## Goal

Align retry behavior between `_start_servers()` and `_verify_mcp_health()` so both use identical retry semantics with configurable delay.

## Scope

**In-Scope:**
- Add single-retry logic to `_start_servers()` matching `_verify_mcp_health()` pattern
- Extract retry delay as a constant or configurable parameter
- Ensure logging levels are consistent between the two methods

**Out-of-Scope:**
- Adding more than one retry attempt
- Changing the post-startup health check retry logic in `_verify_mcp_health()`
- Modifying the health check timeout value

## Assumptions

1. A single retry is sufficient for transient failures during startup
2. Both methods should share the same retry delay value to avoid inconsistency
3. The existing retry in `_verify_mcp_health()` is correct and should not be removed

## Design decisions

- Retry delay extracted as module-level constant `HEALTH_CHECK_RETRY_DELAY_SEC = 1.0` near line 16 of startup.py
- Retry logic mirrors `_verify_mcp_health()` exactly: re-create httpx.AsyncClient, re-send request, raise RuntimeError on second failure
- Logging levels match `_verify_mcp_health()`: INFO on first attempt failure, WARNING on retry attempt failure

## Alternatives considered

- Configurable retry count instead of fixed single retry → rejected; plan scope limits to one retry
- Shared helper method for retry logic → deferred; adds complexity without clear benefit for single retry
- Making retry delay configurable via config → deferred; low priority given current usage

   - Ensure the retry follows the same pattern as `_verify_mcp_health()`: re-create httpx.AsyncClient, re-send request, raise RuntimeError on second failure

## Compatibility considerations
