## Goal

Add `scripts/shared/resource_scope.py`, a new pure `shared/`-layer module providing
`resolve_resource_scopes(tool, args)` — the single place that turns a `RuntimeTool`'s
declared `resource_scope_kind`/`resource_scope_keys` plus a call's actual arguments into
a tuple of kind-prefixed scope strings — and an internal `_scopes_conflict(a, b)`
overlap predicate used later by `scripts/agent/tool_scheduler.py`'s conflict-graph
grouping. Also add the shared schema-2.0 contract validator
(`validate_tool_schema_v2(entry)`) in this same module, per the plan's explicit
"fold into resource_scope.py" instruction.

## Scope

In scope: creating `scripts/shared/resource_scope.py` with `resolve_resource_scopes()`,
`_scopes_conflict()`, and `validate_tool_schema_v2()`. Out of scope: wiring this module
into `runtime_tool_registry.py::_build_tool_spec()` (covered by the
`runtime_tool_registry.py` doc in this same set) and wiring the conflict predicate into
`scripts/agent/tool_scheduler.py` (a separate, not-assigned-to-this-doc-set target file).

## Assumptions

- `RuntimeTool` already carries `resource_scope_kind: str` and
  `resource_scope_keys: tuple[str, ...]` by the time this module is written (per the
  `runtime_tool.py` doc in this set) — this module imports `RuntimeTool` for its type
  signature only, and must not be implemented in an order that requires the old
  `resource_scope: str` field.
- `args` is always a plain `Mapping[str, Any]` (parsed tool-call arguments), never an
  `AgentContext` or config dataclass — required by the `shared-is-leaf` `.importlinter`
  contract, which forbids this module from importing `agent`, `mcp_servers`, `rag`, or
  `db`.
- The known `resource_scope_kind` vocabulary is a small fixed set:
  `""` (unscoped), `"filesystem"`, `"git_repo"`, `"github_repo"`, `"cicd_workflow"`,
  `"rag_store"`, `"mdq_store"`, `"process"` — enumerated from the plan's Design section
  scope-string examples and the Affected-areas table's per-server kind assignments.

## Design decisions

- **Pure function, no registry/agent dependency.** `resolve_resource_scopes(tool, args)`
  takes only a `RuntimeTool` and a `Mapping[str, Any]`; it does not look anything up in
  `RuntimeToolRegistry` or any config object, keeping it independently unit-testable and
  compliant with `shared-is-leaf`.
- **Kind-prefixed scope strings resolve UNK-05.** Every returned scope string has the
  shape `f"{resource_scope_kind}:{normalized_value}"`. This makes cross-kind string
  equality collisions structurally impossible, so `_scopes_conflict()` only needs a
  special case for the `"filesystem:"` prefix (ancestor/descendant via
  `PurePosixPath.is_relative_to()`); every other kind is plain string equality.
- **Multi-key tools produce multi-scope tuples.** `resource_scope_keys` is iterated in
  declared order; each key present in `args` contributes one scope string. This is what
  gives `move_file` (`resource_scope_keys=["source", "destination"]`) two independent
  scopes in its returned tuple, per the plan's Phase 1 test list.
- **Fail-closed fallback, not fail-open.** If `tool.is_write` is `True` and none of
  `resource_scope_keys` resolves to a present, non-empty `args` value, the function
  returns `("global:write",)` — never an empty tuple and never the bare tool name. Only
  a non-write tool with no resolvable keys returns `()` (unscoped read).
- **Validator lives in this module, not a separate file.** `validate_tool_schema_v2()`
  is added here rather than in a new `scripts/shared/mcp_tool_contract.py`, to avoid an
  extra leaf-layer file for a single small function; see Alternatives considered.

## Alternatives considered

- A separate `scripts/shared/mcp_tool_contract.py` module for
  `validate_tool_schema_v2()`, keeping "resolve scopes" and "validate contract" as two
  files. Rejected: the plan explicitly leaves the choice open and this doc set commits
  to the single-file option to avoid proliferating tiny `shared/` leaf modules; the
  validator is small (a handful of field checks) and shares no state with
  `resolve_resource_scopes()`, but colocating it keeps all schema-2.0-contract logic
  discoverable from one import.

## Implementation

### Target file: `scripts/shared/resource_scope.py` (new)

### Procedure

1. Create the file with a module docstring stating its purpose and the `shared-is-leaf`
   import restriction (no `agent`/`mcp_servers`/`rag`/`db` imports), mirroring the style
   of the "Import-layer design decisions" docstring section already present in
   `scripts/shared/runtime_tool_registry.py`.
2. Add imports: `from __future__ import annotations`; `from collections.abc import
   Mapping`; `from pathlib import PurePosixPath`; `from typing import Any`; `from
   shared.runtime_tool import RuntimeTool` (type-only use).
3. Define a module-level constant, e.g. `_KNOWN_SCOPE_KINDS = frozenset({"", "filesystem",
   "git_repo", "github_repo", "cicd_workflow", "rag_store", "mdq_store", "process"})`,
   used by both a scope-string builder and `validate_tool_schema_v2()`.
4. Implement `resolve_resource_scopes(tool: RuntimeTool, args: Mapping[str, Any]) ->
   tuple[str, ...]`:
   - If `tool.resource_scope_kind` is falsy (`""`), return `()` immediately (unscoped).
   - Otherwise, for each key in `tool.resource_scope_keys`, look up `args.get(key)`; skip
     keys absent or empty; for present keys build `f"{tool.resource_scope_kind}:{value}"`
     (normalizing filesystem-like values, e.g. via `str(PurePosixPath(value))` only for
     the `"filesystem"`/`"git_repo"` kinds — other kinds use the raw string value, e.g.
     `github_repo` composing `"owner/repo"` from two keys, `cicd_workflow` composing
     `"repo:workflow:ref"` from three).
   - Collect all resolved scope strings into a tuple, preserving `resource_scope_keys`
     order.
   - If the resulting tuple is empty and `tool.is_write` is `True`, return
     `("global:write",)` as the fail-closed fallback.
   - Otherwise return the (possibly empty) tuple.
5. Implement `_scopes_conflict(a: str, b: str) -> bool`:
   - If `a == b`, return `True`.
   - If both start with `"filesystem:"`, strip the prefix from each, build
     `PurePosixPath` from each remainder, and return `True` if either
     `.is_relative_to()` the other (covers ancestor/descendant in both directions).
   - Otherwise return `False` (different kinds, or same kind but different non-filesystem
     value, never conflict).
6. Implement `validate_tool_schema_v2(entry: dict[str, Any]) -> list[str]`:
   - Return a list of human-readable problem strings; empty list means the entry is
     valid.
   - Check `entry.get("name")` is a non-empty `str`; else append a "name" problem.
   - Check `entry.get("inputSchema")` is a non-empty `dict` with a `"properties"` key
     that is itself a `dict`; else append an "inputSchema" problem.
   - Check `entry.get("is_write")` and `entry.get("requires_serial")` are both present
     and are `bool` (not merely falsy/truthy — reject `None`, `int`, `str`); else append
     one problem per missing/mistyped field.
   - Check `entry.get("resource_scope_kind", "")` is in `_KNOWN_SCOPE_KINDS`; else append
     a problem naming the offending kind.
   - Check `entry.get("resource_scope_keys", [])` is a `list[str]`, and each listed key
     string is present in `entry["inputSchema"]["properties"]` (when `inputSchema` was
     itself valid); else append a problem per missing/mistyped key.

### Method

Write the module as straight-line pure functions with no shared mutable state; no
classes needed since the plan's Design section describes only free functions
(`resolve_resource_scopes()`, `_scopes_conflict()`) plus the validator. Match the
existing `shared/` module docstring convention (see `runtime_tool_registry.py`'s
"Import-layer design decisions" section) by explicitly documenting the no-`agent`-import
constraint at the top of the file so a future contributor does not "fix" it by adding
the import back.

### Details

- File path: `scripts/shared/resource_scope.py` (new, ~90–120 lines including
  docstrings).
- Public surface: `resolve_resource_scopes(tool: RuntimeTool, args: Mapping[str, Any]) ->
  tuple[str, ...]`, `validate_tool_schema_v2(entry: dict[str, Any]) -> list[str]`.
  Private: `_scopes_conflict(a: str, b: str) -> bool` (leading underscore since it is
  consumed by `tool_scheduler.py` in a later, unassigned step but has no committed public
  contract yet in this doc set).
- No dataclasses; all functions take/return plain built-in types per the leaf-layer
  contract.
- `PurePosixPath` (not `Path`) is used deliberately — scope strings are logical resource
  identifiers, not filesystem paths to be resolved against the local OS, and
  `PurePosixPath` avoids accidental platform-dependent path semantics in `is_relative_to`
  comparisons.

## Compatibility considerations

This is a brand-new file with no existing importers, so there is no backward-compatible
shape to preserve. Its only forward-compatibility concern is that
`runtime_tool_registry.py::_build_tool_spec()` (updated in a companion doc) will import
`resolve_resource_scopes` from this module — the function name and two-positional-arg
signature (`tool`, `args`) must match what that doc specifies.

## Security considerations

- The fail-closed `("global:write",)` fallback is the security-relevant design point:
  an under-specified write tool must never resolve to an empty scope tuple, which would
  let the scheduler treat it as freely parallelizable. This module must never special-case
  its way around that fallback.
- `validate_tool_schema_v2()` is the last line of defense before an incomplete or
  malformed tool declaration reaches the registry; it must reject rather than
  coerce/default any missing required field, matching the plan's "fail-closed" goal.

## Rollback considerations

Deleting `scripts/shared/resource_scope.py` is safe in isolation only after reverting its
sole planned caller (`runtime_tool_registry.py::_build_tool_spec()`); until that caller
exists, this file can be added or removed independently with no other code change,
consistent with the plan's Phase 1 note that this module is "independently
revertable/testable."
