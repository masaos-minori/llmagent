## Goal

Unify `[DENIED]`/`read_only=true` guard-denial message formatting into a structured error-code scheme across `git_security.py`'s guard implementations and `git_service.py`'s 10 handlers, enabling MCP clients to handle denials programmatically rather than relying on fragile string parsing.

## Scope

### In-Scope
- Designing the target structured shape (or deciding not to change)
- Rewriting characterization tests for every guard-denial message
- Updating `_check_repo_path`/`_check_write` and all 10 `git_*` handlers to use the new shape

### Out-of-Scope
- Extending to `scripts/mcp_servers/file/*_service.py`'s analogous guards (requires separate scoping decision)
- Changing which conditions trigger a denial (only the message format changes)

## Assumptions

- A maintainer-approved target shape exists and is documented before implementation begins
- The current denial conditions remain unchanged — only the message/response shape changes
- MCP clients currently parse the `[DENIED]` prefix; any new shape must be explicitly communicated as a breaking change
- The `RepoValidationResult.error_message` field will transition from `str` to a structured type (e.g., `dict` or Pydantic model)

## Design decisions

- Use a two-part structured response: machine-parseable error code + human-readable message
- Keep the human-readable message alongside the error code for backward compatibility during migration
- Require explicit sign-off on the target shape before implementation — this is a breaking change for MCP clients
- Start with git-only scope unless repo-wide extension is explicitly requested

## Alternatives considered

- Leave `[DENIED]` string format as-is — rejected because it forces MCP clients to parse strings fragilely
- Return only an error code without a human-readable message — rejected because operators need readable output
- Add a new `is_denied` boolean flag alongside the existing string — rejected because it doesn't solve the core problem of programmatic handling

## Compatibility considerations

- Breaking change for MCP clients that parse the `[DENIED]` prefix or `read_only=true` substring
- `RepoValidationResult.error_message` type change from `str` to structured type may break other consumers
- Must coordinate migration with any downstream MCP clients

## Security considerations

- None identified — this is a refactoring of error reporting, no security-sensitive code paths involved

## Rollback considerations

- Revert the diff; no data loss or service impact
- MCP clients may need coordinated migration due to breaking change

### Method

Refactoring — replace fragile string-based denial messages with a structured error-code scheme.

# In scripts/mcp_servers/git/git_models.py (new types):

from enum import StrEnum
from pydantic import BaseModel

class GitDenialCode(StrEnum):
    REPO_PATH_NOT_ALLOWED = "repo_path_not_allowed"
    WRITE_DENIED_READONLY = "write_denied_readonly"
    WRITE_DENIED_MAX_BYTES = "write_denied_max_bytes"

class GitDenialResponse(BaseModel):
    """Structured denial response for MCP clients."""
    code: GitDenialCode
    message: str  # Human-readable message for operators
    
    def __str__(self) -> str:
        """Backward-compatible string representation for legacy clients."""
        return f"[DENIED] {self.message}"

# In scripts/mcp_servers/git/git_security.py:

# BEFORE:
def _check_repo_path(self, target: str) -> tuple[bool, str]:
    """Check if target path is within any allowed repo."""
    p = PurePosixPath(target)
    for allowed in self.allowed_repos:
        try:
            p.relative_to(allowed)
            return True, ""
        except ValueError:
            continue
    return False, "[DENIED] Path not in allowed repos"

def _check_write(self, target: str) -> tuple[bool, str]:
    """Check if write operation is allowed."""
    if self.read_only:
        return False, "[DENIED] read_only=true"
    ...

# AFTER:
def _check_repo_path(self, target: str) -> tuple[bool, GitDenialResponse | None]:
    """Check if target path is within any allowed repo."""
    p = PurePosixPath(target)
    for allowed in self.allowed_repos:
        try:
            p.relative_to(allowed)
            return True, None
        except ValueError:
            continue
    return False, GitDenialResponse(
        code=GitDenialCode.REPO_PATH_NOT_ALLOWED,
        message=f"Path '{target}' not in allowed repos",
    )

def _check_write(self, target: str) -> tuple[bool, GitDenialResponse | None]:
    """Check if write operation is allowed."""
    if self.read_only:
        return False, GitDenialResponse(
            code=GitDenialCode.WRITE_DENIED_READONLY,
            message="Write denied: server is read-only",
        )
    ...

# In scripts/mcp_servers/git/git_service.py (handler update):

# BEFORE:
def _handle_git_status(self, params: dict[str, Any]) -> dict[str, Any]:
    allowed, msg = self.security._check_repo_path(params["repo_path"])
    if not allowed:
        return {"error": msg}
    ...

# AFTER:
def _handle_git_status(self, params: dict[str, Any]) -> dict[str, Any]:
    allowed, denial = self.security._check_repo_path(params["repo_path"])
    if not allowed:
        assert denial is not None
        return {
            "error": str(denial),  # Backward-compatible for legacy clients
            "denial_code": denial.code.value,  # New: programmatic access
        }
    ...

# In tests/mcp_servers/git/test_mcp_git.py (characterization test rewrite):

# BEFORE:
def test_check_repo_path_denial():
    result = security._check_repo_path("/etc/passwd")
    assert result == (False, "[DENIED] Path not in allowed repos")

# AFTER:
def test_check_repo_path_denial():
    allowed, denial = security._check_repo_path("/etc/passwd")
    assert allowed is False
    assert denial is not None
    assert denial.code == GitDenialCode.REPO_PATH_NOT_ALLOWED
    assert denial.message == "Path '/etc/passwd' not in allowed repos"
    assert str(denial) == "[DENIED] Path '/etc/passwd' not in allowed repos"
