# Implementation Procedure: docs/05_agent_01_system-overview.md

## Goal

Reduce `docs/05_agent_01_system-overview.md` to a canonical source for overall scope and top-level execution model by removing mechanical inventories and pushing component-level detail to owning chapters.

## Scope

**In-Scope**:
- Restructure `docs/05_agent_01_system-overview.md` to preserve: Agent's purpose, in-scope/out-of-scope boundaries, overall execution model, reason WorkflowEngine is always traversed, RAG/MCP/Embedding out-of-scope boundary, high-level responsibilities of major components.
- Remove: detailed entry-point call sequences, mechanical class/file correspondence tables, prompt literal strings, history-filename details, exhaustive slash-command enumerations.
- Replace overlapping content with pointers to owning chapters (e.g., slash commands → `05_agent_07_*`).
- Reformat using the template: Purpose / Design Intent / Responsibility Boundary / Key Constraints / Operational Notes / Known Limitations / Related Docs.
- Mark unrecoverable design rationales as `Needs Confirmation`.

**Out-of-Scope**:
- Modifying other documents in the `05_agent_*.md` set.
- Adding new content beyond what exists in the current document.
- Changing the doc set directory structure.

## Assumptions

1. The `memo-doc-agent-review.md` referenced in acceptance criteria exists and contains a valid chapter structure template.
2. `tools/check_agent_docs_consistency.py` is available and functional for post-edit verification.
3. All mechanical content being removed is indeed duplicatable via code search (no unique facts will be lost).
4. The canonical command chapter (`05_agent_07_*`) exists and can be used for cross-references.

## Design decisions

- System overview should answer "what does this agent do" and "how does it fit into the broader system," not "which class maps to which file."
- Component-level detail belongs in owning chapters; this chapter provides only the high-level map.
- Canonical Source Rule applies: when a fact is mechanically derivable from code, point to the source rather than transcribing it.
- Unrecoverable design rationales must be explicitly marked `Needs Confirmation` rather than silently dropped.

## Alternatives considered

- Keep current format: violates the principle that mechanical inventories should not be maintained manually.
- Replace with auto-generated component diagram: would reduce maintenance burden but loses human-curated narrative. Not pursued without explicit request.

## Implementation

### Target file

`docs/05_agent_01_system-overview.md`

### Procedure

#### Phase 1: Preparation

1. Confirm `memo-doc-agent-review.md` exists and locate it (search repo root and subdirectories).
2. Read `docs/05_agent_01_system-overview.md` in full.
3. Identify sections containing:
   - Entry-point call sequences (detailed step-by-step invocation chains)
   - Class/file correspondence tables (mechanical mappings between classes and files)
   - Prompt literal strings (actual prompt text embedded in documentation)
   - History-filename details (specific filename patterns)
   - Exhaustive slash-command enumerations (complete lists of all commands)

#### Phase 2: Core Logic Implementation

4. For each identified mechanical section:
   - If the content is an entry-point call sequence: replace with a pointer to the owning chapter or "see code search" statement.
   - If the content is a class/file correspondence table: remove entirely; this is mechanical mapping visible in code.
   - If the content includes prompt literal strings: remove unless the string itself carries operational meaning (rare).
   - If the content is history-filename details: remove; filenames are discoverable via code search.
   - If the content is an exhaustive slash-command enumeration: replace with a pointer to `05_agent_07_*` (canonical command chapter).
5. Preserve the following content:
   - Agent's purpose statement
   - In-scope/out-of-scope boundaries
   - Overall execution model (high-level flow description)
   - Reason WorkflowEngine is always traversed (operational judgment)
   - RAG/MCP/Embedding out-of-scope boundary
   - High-level responsibilities of major components (not per-class detail)
6. Mark any unrecoverable design rationale as `Needs Confirmation`.
7. Reformat remaining content using the standard template:
   ```
   ## Purpose
   ## Design Intent
   ## Responsibility Boundary
   ## Key Constraints
   ## Operational Notes
   ## Known Limitations
   ## Related Docs
   ```

#### Phase 3: Deployment & Verification

8. Run `python tools/check_agent_docs_consistency.py` to confirm no broken internal links or removed-file references.
9. Manually verify that the document still serves its navigation purpose after restructuring.
