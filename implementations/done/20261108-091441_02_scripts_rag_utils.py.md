# Implementation procedure: `scripts/rag/utils.py` — typed float32-range rejection in `floats_to_blob`

## Goal
Make `floats_to_blob` reject out-of-range elements with a typed `ValueError` via an explicit range check, and correct its docstring's inaccurate claim that out-of-range values raise `struct.error` (`REQ-002`: typed pack validation at the shared utility boundary).

## Scope
**Release unit**: ragvec001-full

- Add the float32-range check to `_validate_float_list` and fix the `floats_to_blob` docstring.
- Companion test file `tests/rag/test_rag_utils.py` gets the out-of-range and boundary-magnitude cases.

## Assumptions
- Gated: `issues/20261107-050701_adrrag001_rag-fallback-failure-policy.md` phase all - prose dependency on an open issue; the Plan's own Scope records "Related, no order required".
- The float32 upper bound constant is decided here as `_FLOAT32_MAX = 3.4028234663852886e38` (float32 max magnitude), matching the sibling document for `scripts/rag/llm_client.py`; each module keeps its own copy (no cross-boundary private-symbol import).

## Design decisions
- The range check belongs in `_validate_float_list` (the existing validation helper) rather than around `struct.pack`: validation stays one place, and the exception raised is the typed `ValueError` with the element index, consistent with the helper's other checks (DESIGN: validate at boundaries, typed over untyped failures).
- The residual `except struct.error` wrapper and its log line stay: they remain the last-resort pack guard for causes other than element range.

## Alternatives considered
- Let `struct.error` propagate for out-of-range values and only fix the docstring: rejected — `struct.pack('<f', 1e300)` actually raises `OverflowError` today (verified live), so neither current behavior matches the docstring, and an untyped pack crash keeps the pipeline escape the Plan is fixing.

## Implementation
### Target file
`scripts/rag/utils.py`

### Procedure
1. Add a module-level constant `_FLOAT32_MAX` (new) near the existing module constants, with a one-line comment naming it as the float32 maximum magnitude.
2. In `_validate_float_list`, after the existing `not math.isfinite(v)` branch, raise `ValueError` when `abs(v) > _FLOAT32_MAX`, message naming the offending index and value.
3. Correct the `floats_to_blob` docstring: `Raises ValueError` now lists out-of-range values; the `Raises struct.error` line no longer claims out-of-range is its example (state "residual packing failure").

### Method
- New branch in the element loop: `if abs(v) > _FLOAT32_MAX:` → `raise ValueError(f"floats_to_blob: element {i} is out of float32 range ({v!r})")`.
- `math` and `struct` are already imported in this module; no import changes.

### Details
- Current state (verified at HEAD `eb19564fe`): the docstring line reads `Raises struct.error if packing fails (e.g. value out of float32 range)`; `_validate_float_list` checks `isinstance`/non-empty/`math.isfinite` only; `1e300` passes validation and `struct.pack` raises `OverflowError`, which the wrapper (catches `struct.error` only) does not catch.
- Callers verified unchanged: `scripts/rag/repository.py` `vector_search` and the `scripts/rag/ingestion/embedding.py` `embed_and_store` pack call site — the ingestion pack step now surfaces a typed `ValueError` instead of `OverflowError` even though ingestion response validation is out of scope (Plan Design, secondary effect).
