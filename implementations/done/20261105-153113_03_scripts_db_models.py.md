## Goal

Add an explicit verification-status contract to `RagConsistencyReport` so a dimension whose
probe failed or returned an unknown value is expressed as "not verified" instead of being
indistinguishable from a healthy zero. The change is purely additive: every existing numeric
field keeps its meaning.

## Scope
**Release unit**: N/A: not part of a release unit

## Assumptions

- The field is populated by the orchestrator (`scripts/db/rag_consistency.py`, seq 01/02)
  from the per-probe error markers it already records; this module only declares the field.
- Existing constructions of `RagConsistencyReport` use keyword arguments (see
  `tests/db/test_rag_consistency.py`, seq 05). Any new field MUST carry a default so those
  constructions keep compiling; a required field would break them.
- Consumers branch on the new field: `scripts/db/recovery_verification.py` (seq 04) treats an
  unverified dimension as a verification failure.
- Severity stays numeric (`fatal_count`, `degraded_count`, `findings`); the status field is
  orthogonal to severity. See UNK-02.

## Design decisions

- Add per-dimension unverified flags rather than a single opaque boolean, so a consumer can
  report WHICH dimension failed (FK / embedding / schema). Each defaults to `False`, keeping
  the change additive and backward compatible.
- Express "unverified" as explicit booleans rather than overloading a numeric count, so
  `is_consistent` aggregation (which reads numeric counts) is unaffected and the status is
  never mistaken for a healthy zero (REQ-002).

## Alternatives considered

- A single `verification_status: str` enum (`"verified"` / `"unverified"`) versus
  per-dimension flags. Chose per-dimension flags: AC-003 requires each check to report
  independently, and consumers (recovery drill, recovery verification) benefit from knowing
  which dimension is unverified. A single aggregate flag loses that granularity.
- Deriving unverified from `diagnostic_errors` at consumption time versus declaring explicit
  fields. Chose explicit fields: the plan's REQ-001 calls for the unavailable-extension
  state to appear in the report contract itself, not be inferred downstream, and it makes the
  contract self-documenting.

### Procedure
1. Open `RagConsistencyReport` (`scripts/db/models.py` L96-L152) and add three unverified

   - `embedding_unverified: bool = False`
   - `schema_unverified: bool = False`
2. Give every new field a `False` default so all existing keyword-argument constructions keep
   working.
3. Document each field with a one-line comment noting it is set by the orchestrator when the
   corresponding probe raises `sqlite3.Error` (see `scripts/db/rag_consistency.py`, seq 01).
4. Confirm the dataclass remains frozen-compatible and that no field ordering breaks positional
   construction (the report is always built with keyword arguments in
   `check_rag_consistency`).

### Method
Declarative dataclass-field addition. No logic, no new method. The orchestrator sets the flags
during report assembly; this module only defines the contract.

### Details
- Current `RagConsistencyReport` holds numeric counts and `issues`/`findings` only; there is
  no way to say "this dimension was not verified." The three new flags fill exactly that gap.
- The flags are independent of `fatal_count`/`degraded_count`, which are derived from
  `findings` (L130-L145). An unverified dimension does not itself create a FATAL finding here;
  the consumer (seq 04) decides how to treat it. This keeps the numeric severity contract
  stable while adding the status dimension.
- `diagnostic_errors` (L150-L152) already captures probe errors; the new flags are a structured,
  per-dimension projection of that signal. Keep both: `diagnostic_errors` for the raw message,
  the flags for machine-readable branching.
