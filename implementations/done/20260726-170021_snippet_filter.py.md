## Goal

Wire the existing `scripts/agent/memory/snippet_filter.py` module (PII redaction +
length truncation) into the memory snippet build pipeline so injected memory
snippets cannot leak PII or exceed a configurable length, and log a warning
whenever a snippet is filtered or truncated.

## Scope

**In-Scope**:
- Call `snippet_filter.filter_pii()` and `snippet_filter.truncate_snippet()` on each
  snippet text produced by `MemoryInjectionService._build_snippets_from_hits`
  (and, for consistency, `_build_snippets_from_entries`) in
  `scripts/agent/memory/injection.py`.
- Add a `max_snippet_length: int = 500` field to `InjectionPolicy`
  (`scripts/agent/memory/injection.py`) and pass it to `truncate_snippet()`.
- Log a warning when `FilteredSnippet.was_filtered` or `TruncatedSnippet.was_truncated`
  is `True`.

**Out-of-Scope** (per source plan):
- Adding new PII patterns to `snippet_filter.py`.
- Changing `InjectionPolicy` defaults beyond the new snippet length field.
- Modifying `HybridRetriever` search logic.
- The orchestrator.py priority-marker change (Affected-Areas row 1) and the general
  injection.py wiring row (Affected-Areas row 2) are tracked as separate items in the
  source plan; matching implementation-procedure documents for `orchestrator.py` and
  `injection.py` already exist under `implementations/done/`, so per the dedup rule
  those two rows are treated as already covered and are not re-documented here. This
  document exists specifically because no `implementations/*snippet_filter.py*` document
  exists yet.

## Assumptions

1. `snippet_filter.py` (`scripts/agent/memory/snippet_filter.py`, 72 lines) is complete
   and has zero current callers — confirmed by reading the file: it exports
   `filter_pii(text) -> FilteredSnippet` and `truncate_snippet(text, max_length=500) -> TruncatedSnippet`,
   both pure functions with no side effects.
2. `FilteredSnippet.text` is never `None` in the current implementation (per its
   docstring), so no "reject snippet entirely" branch is needed yet.
3. Existing callers of `on_user_prompt()` / `on_session_start()` do not depend on
   unfiltered snippet content (per source plan Assumption 4).
4. `_build_snippets_from_hits` and `_build_snippets_from_entries` are the only two
   snippet-construction sites in `injection.py`; filtering/truncation should apply to
   both for consistency, though the source plan's Implementation Steps only mention
   `_build_snippets_from_hits` explicitly.

## Design decisions

- Apply `filter_pii()` then `truncate_snippet()` in that order (redact PII first, then
  truncate) so redaction markers are never cut off mid-token by truncation.
- Keep `filter_pii`/`truncate_snippet` calls inline in the snippet-building loop rather
  than introducing a new abstraction layer — the functions are already pure and
  side-effect-free, so no wrapper class is justified (YAGNI).
- Add `max_snippet_length` to the existing frozen `InjectionPolicy` dataclass rather
  than a new config object, to keep all injection tuning in one place.

## Alternatives considered

- **Filter/truncate at the `MemorySnippet` model layer instead of in `injection.py`**:
  rejected — would couple `models.py` to the filtering policy and apply to snippets
  built via `_build_snippets_from_entries` and `_build_snippets_from_hits` alike
  without an obvious extension point; keeping it in the service that owns policy
  (`InjectionPolicy`) is simpler.
- **Make PII filtering configurable/toggleable via a policy flag**: rejected as
  out-of-scope per source plan (no new `InjectionPolicy` fields beyond max length).

## Implementation

### Target file

- Primary: `scripts/agent/memory/injection.py`
- Consumed module (no changes): `scripts/agent/memory/snippet_filter.py`

### Procedure

1. Import `filter_pii` and `truncate_snippet` from `agent.memory.snippet_filter` at the
   top of `injection.py`.
2. Add `max_snippet_length: int = 500` to `InjectionPolicy` (line ~25-32).
3. In `_build_snippets_from_hits` (line ~93-108) and `_build_snippets_from_entries`
   (line ~75-91), after computing `snippet_text`, apply:
   - `filtered = filter_pii(snippet_text)`; use `filtered.text`.
   - `truncated = truncate_snippet(filtered.text, self._policy.max_snippet_length)`;
     use `truncated.text` as the final snippet text.
4. After each call, if `filtered.was_filtered` or `truncated.was_truncated` is `True`,
   emit a `logger.warning(...)` call.

### Method

- Direct, minimal edit of the two snippet-building helper methods; no new classes.
- Reuse the existing `logger = logging.getLogger(__name__)` already defined at module
  level (line 21) for the new warning calls.

### Details

- Current `_build_snippets_from_hits` body (lines 93-108):
  ```python
  def _build_snippets_from_hits(
      self, hits: Sequence[MemoryHit], prefix: str, source: str
  ) -> list[MemorySnippet]:
      snippets: list[MemorySnippet] = []
      for hit in hits:
          snippet_text = (
              hit.entry.summary if hit.entry.summary else hit.entry.content[:100]
          )
          snippets.append(
              MemorySnippet(
                  text=f"{prefix} {snippet_text}",
                  source=source,
              )
          )
      return snippets
  ```
  Insert the `filter_pii` / `truncate_snippet` calls between computing `snippet_text`
  and building the `f"{prefix} {snippet_text}"` string; log a warning with a snippet
  count (per source plan Phase 3) when filtering occurred, and with the original
  length (per source plan Phase 3) when truncation occurred.
- `_build_snippets_from_entries` (lines 75-91) has the identical `snippet_text`
  pattern (`entry.summary if entry.summary else entry.content[:100]`) and should
  receive the same treatment for consistency, even though the source plan's
  Implementation Steps text only names `_build_snippets_from_hits`.
- `InjectionPolicy` (lines 24-32) currently has no length-related field; add
  `max_snippet_length: int = 500` alongside the existing `max_semantic`,
  `max_episodic`, `min_importance` fields.
- `snippet_filter.filter_pii(text: str) -> FilteredSnippet` and
  `snippet_filter.truncate_snippet(text: str, max_length: int = 500) -> TruncatedSnippet`
  (both defined in `scripts/agent/memory/snippet_filter.py`, lines 46-72) require no
  changes — only import and call.

## Compatibility considerations

- `MemorySnippet.text` remains a `str`; filtering/truncation only changes its content,
  not its type or the `MemorySnippet` dataclass shape — no downstream consumer
  (`orchestrator.py::_handle_memory_injection`) needs to change.
- Default `max_snippet_length=500` is strictly larger than the current unconditional
  `content[:100]` fallback, so existing short snippets are unaffected; only summaries/
  content longer than 500 chars will now be truncated (previously untruncated).
- No public constructor signature changes to `InjectionPolicy` beyond adding a field
  with a default, so existing call sites that construct `InjectionPolicy(...)` without
  the new field keep working.

## Security considerations

- This change is itself a security control (PII redaction before LLM context
  injection); no new attack surface is introduced since `filter_pii`/`truncate_snippet`
  are pure, regex-based, non-networked functions.
- Regex-based PII detection can false-positive (e.g. `API_KEY` pattern matching
  long non-secret base64-like tokens) or false-negative; per source plan this is an
  accepted limitation for this stage (no ML-based detection).
- Warning logs must not themselves re-emit the raw (unfiltered) snippet text —
  log only counts/lengths, never the original content, to avoid defeating the
  redaction via logs.

## Rollback considerations

- Single-file, additive change (new import, one new dataclass field with a default,
  two call sites augmented) — revertible with `git revert` of the one commit with no
  schema/data migration involved.
- No persisted state changes (no DB schema, no config file changes) — rollback is a
  pure code revert.
