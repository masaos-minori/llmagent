## Goal

Ensure WAL checkpoint failure does not result in silent data loss during shutdown by adding retry logic with exponential backoff.

## Scope

**In**: `scripts/agent/repl.py` (AgentREPL._close_resources())
**Out**: Changes to SQLiteHelper.checkpoint(), other database operations

## Assumptions

1. `SQLiteHelper.checkpoint()` can fail due to busy timeouts or exclusive access requirements
2. Exponential backoff with 3 attempts (1s, 2s, 4s) provides sufficient recovery window
3. PASSIVE checkpoint mode may succeed where TRUNCATE fails because it doesn't require exclusive access

## Design decisions

- Try PASSIVE mode first, then TRUNCATE — PASSIVE is more reliable during shutdown as it doesn't require exclusive access
- Use per-mode retry (3 attempts per mode) rather than global retry — allows switching strategies between modes
- Log ERROR-level after all modes exhausted — distinguishes from transient failures that are retried

## Alternatives considered

- **Retry only TRUNCATE mode**: Would miss the opportunity to use PASSIVE which is more reliable during shutdown; PASSIVE should be tried first
- **Use a single global retry counter across modes**: Would complicate the logic unnecessarily; per-mode retry aligns better with the strategy-switch intent
- **Add a separate error callback for checkpoint failures**: Over-engineered; existing `errors` list mechanism is sufficient

Change to:

```python
        # WAL checkpoint before closing connections
        try:
            with SQLiteHelper("session").open(write_mode=True) as db:
                wal_mode = db.execute("PRAGMA journal_mode").fetchone()[0]
                if wal_mode.lower() == "wal":
                    checkpoint_succeeded = False
                    for attempt, mode in enumerate(["PASSIVE", "TRUNCATE"], start=1):
                        try:
                            db.checkpoint(mode)
                            logger.info("WAL checkpoint (%s) completed on shutdown", mode)
                            checkpoint_succeeded = True
                            break
                        except sqlite3.Error as e:
                            if attempt < 3:
                                import time as _time
                                _time.sleep(min(2 ** (attempt - 1), 4))
                                logger.warning(
                                    "WAL checkpoint (%s) attempt %d failed: %s; retrying...",
                                    mode, attempt, e,
                                )
                            else:
                                logger.error(
                                    "WAL checkpoint (%s) failed after %d attempts: %s",
                                    mode, attempt, e,
                                )
                    if not checkpoint_succeeded:
                        errors.append(
                            ("wal_checkpoint",
                             f"WAL checkpoint failed after exhausting PASSIVE/TRUNCATE modes"),
                        )
                else:
                    logger.debug("WAL checkpoint skipped: journal mode is %r", wal_mode)
        except sqlite3.Error as e:
            errors.append(("wal_checkpoint", f"{type(e).__name__}: {e}"))
            logger.warning("WAL checkpoint failed on shutdown: %s", e)
```

Key points:
- Tries PASSIVE mode first, falls back to TRUNCATE if PASSIVE fails
- Each mode gets up to 3 attempts with exponential backoff (1s, 2s, 4s)
- After all modes exhausted, logs ERROR-level message instead of WARNING
- Error appended to `errors` list for summary logging at end of `_close_resources()`
- Connection always closed via context manager regardless of checkpoint outcome

### Method

Extract ownership of WAL checkpoint reliability into the caller (`_close_resources`). Use nested try/except with per-mode retry and exponential backoff to handle transient failures gracefully.

### Details

The core issue is that WAL checkpoint during shutdown can fail due to concurrent access from other connections, resulting in silent data loss. The current code makes a single attempt with TRUNCATE mode, which requires exclusive access to the WAL file.

By adding PASSIVE mode first (which waits for a checkpointer without requiring exclusive access) and implementing per-mode retry with exponential backoff, we achieve:
- Higher success rate — two different checkpoint strategies increase recovery probability
- Graceful degradation — each mode retries independently before moving to the next
- Proper error escalation — ERROR-level logging when all strategies exhausted
- No connection leak — context manager ensures cleanup regardless of outcome
