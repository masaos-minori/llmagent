## Goal
- Correct `docs/04_mcp_04_05_git.md` §Protected branch authority (and the related
  "Current:" bullet just above it) to describe the implemented
  `GitConfig.protected_branches` policy instead of claiming no policy source exists
  (REQ-003).

## Scope
- In scope: `docs/04_mcp_04_05_git.md`'s `### git_push policy` "Current:" bullet and
  the `### Protected branch authority` section body.
- No code change.

## Assumptions
- `GitConfig.protected_branches` (`scripts/mcp_servers/git/git_models.py`),
  `GitSecurityGuards._check_protected_branch()`, and
  `GitService._validate_protected()` (`git_security.py`/`git_service.py`) are
  unchanged by this document (`Explicit in code`).
- `config/git_mcp_server.toml` currently has no `protected_branches` key set, so
  `GitConfig`'s default (empty list) applies (`Explicit in code`).

## Design decisions
- Separate two distinct facts clearly: the enforcement *mechanism* is implemented,
  but the *current shipped configuration* leaves it empty (so nothing is actually
  protected today) — do not conflate "not implemented" with "not configured."
- Contrast with GitHub MCP's `protected_branches` (`config/github_mcp_server.toml`,
  glob-capable, e.g. `"release/*"`): Git MCP's check is exact-match only, not glob —
  state this as a distinct setting/semantics, not as "unrelated."
- Document the existing gap that `_validate_protected()` skips the check entirely
  when `branch` is empty.

## Alternatives considered
- Deleting §Protected branch authority and merging its content into `git_push
  policy` — rejected; other documentation
  (`04_mcp_05_03_fail-open-fail-closed-and-risk-tiers.md`) cross-references this
  section by name, so its heading is kept stable.
