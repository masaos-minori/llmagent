## Goal

Ensure repository input handling and FTS observability are complete and predictable: verify `_validate_top_k()` covers all invalid input cases, verify empty query early-exit works correctly, and verify FTS truncation logging provides sufficient diagnostic information. Optionally add structured truncation metadata to `RagHit` types.

## Scope

**In-Scope:**
- Verify `_validate_top_k()` handles all invalid input cases (zero, negative, boolean, non-integer, float).
- Verify empty query early-exit returns consistent results.
- Verify truncation logging provides sufficient diagnostic information.
- Run existing tests to confirm behavioral identity.
- **Optional**: Add `truncated: bool` field to `RawHit`, `MergedHit`, `RankedHit` if callers need structured truncation metadata.

**Out-of-Scope:**
- Modifying source code behavior beyond diagnostic improvements.
- Updating documentation (`docs/*.md`).
- Changing the core ingestion or pipeline orchestration logic.

## Assumptions

- Existing callers of `fts_search()` don't need structured truncation metadata (current logger output is sufficient).
- `_validate_top_k()` already covers all required validation cases.
- Empty query early-exit is sufficient for preventing SQL errors.

## Design decisions

- **Verification-first approach**: Since the existing implementation already addresses the core requirements, prioritize verification over new features.
- **Optional enhancement path**: If callers need structured truncation metadata, add `truncated: bool` field to all three `RagHit` variants (`RawHit`, `MergedHit`, `RankedHit`) and propagate from `_build_fts_query()`.

## Alternatives considered

- **Add truncation metadata unconditionally**: Would change the public API contract for all callers. Rejected as too broad.
- **Use a separate response wrapper**: Adds complexity for marginal benefit. Rejected.
- **Keep log-only approach**: Satisfies current requirement ("expose truncation information via logs or diagnostics"). Preferred default.
