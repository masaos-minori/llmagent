## Goal

Make the distinction between Workflow approval and Tool approval explicit through configuration and documentation, eliminating ambiguity about which approval mechanism `/approve` and `/reject` apply to.

## Scope

**In-Scope:**
- Add explicit `"require_approval": false` to `config/workflows/default.json`

**Out-of-Scope:**
- Changes to Workflow approval logic itself
- Changes to Tool approval logic itself
- Changes to the interaction between the two approval mechanisms beyond documentation

## Assumptions

1. The intended default for `require_approval` is `false` (no workflow-level approval gate), matching the current implicit behavior.
2. Tool approval denial already appears as a tool message in conversation history — this behavior is correct and does not need code changes.
3. Documentation updates should follow the existing doc structure; new docs should reference existing ones rather than duplicating content.

## Design decisions

- **Explicit config over implicit default**: Add `require_approval: false` explicitly to `default.json` rather than relying on the dataclass default. This makes the intent clear and prevents behavioral regression if defaults change.
- **Consistent terminology**: Use "Workflow approval" and "Tool approval" consistently throughout all documents; avoid standalone "approval" without qualifier.

## Alternatives considered

- **Rely on dataclass default**: Could keep `require_approval` absent from `default.json` and rely on the dataclass default (`False`). Rejected because it creates ambiguity about whether the absence means "not set" or "explicitly disabled".
- **Add `require_approval: true` by default**: Could enable Workflow approval by default. Rejected because the current implicit behavior is `false` and changing it would be a breaking change.

#### Phase 1: Explicitly configure workflow approval

1. Add `"require_approval": false` to `config/workflows/default.json`:
   ```json
   {
       "stages": [...],
       "require_approval": false
   }
   ```
   - Place at the same level as the `stages` key, consistent with the schema
   - If the schema expects it elsewhere (e.g., within each stage), place it there instead

### Method

### Details

1. `config/workflows/default.json` update:
   - Add `"require_approval": false` at the top level (consistent with schema)
   - If the schema expects it within each stage entry, add it to each stage instead
   - Verify the JSON remains valid after the edit
