# Implementation Procedure: Update docs/adr-index.md to reflect ADR-004 revision

## Goal

Update `docs/adr-index.md` to eliminate stale references to ADR-004's pre-revision state, including outdated invariant descriptions that reference removed Local-mode concepts.

## Scope

- **In-Scope**: Updating ADR List entry for ADR-004, rewriting Invariant Verification Matrix rows INV-010 through INV-022 that reference ADR-004, deciding whether to consolidate overlapping invariant rows.
- **Out-of-Scope**: Modifying ADR-004 itself, changing the Invariant Verification Matrix structure for other ADRs' rows, resolving circular dependency notes (CDR-1/CDR-2/CDR-3).

## Assumptions

- The ADR List entry for ADR-004 has already been updated (title and status are correct per current adr-index.md).
- The cross-ADR Invariant Verification Matrix's INV-010/011/019/020/021/022 numbering is independent from ADR-004's own INV-01–INV-10 numbering.
- Existing INV IDs should be preserved rather than renumbered (per repository practice).

## Design decisions

- INV-011 must be rewritten to use ADR-004's unified terminology: "Fail-Fast" applies only to startup-time safety/integrity failures; "Fail-Closed" applies only to runtime safety/integrity failures. The distinction between "Fail-Fast at startup" and "Fail-Closed at execution" is preserved but must be expressed in the revised ADR-004's own wording.
- INV-021 must reference Decision #12 ("component criticality undefined → do not assume non-required") instead of the nonexistent "undefined component criticality" concept.
- INV-019 and INV-020 remain distinct: required-component unavailability prevents startup; non-required component availability failure permits partial availability.
- INV-022 remains distinct: fallback prohibition tied to ADR-010 as sole authority.

## Alternatives considered

- Consolidating INV-010 and INV-011 into a single row if they overlap significantly after rewriting. Decision: keep separate unless their descriptions become identical post-rewrite.
- Renumbering INV IDs after consolidation. Decision: preserve existing INV IDs per repository practice.

### Details

**INV-010 rewrite**: Current description states "The system uses a single common failure-handling policy across all environments; environment names do not weaken safety, validation, authentication, authorization, approval, routing, or data-integrity controls." This maps to ADR-004 Decision #1 (single common policy) and Decision #3 (environment names do not change any requirements). Verification Status needs re-checking against current code.

**INV-011 rewrite**: Current description contains stale language: "Fail-Fast at startup / Fail-Closed at execution" and "required/non-required branch." Per ADR-004:
- Decision #14 defines startup Fail-Fast conditions (Workflow definition missing/invalid, required DB connection failure, RuntimeToolRegistry initialization failure, Tool ownership duplication, required MCP server unavailable, auth/authorization/allowlist/safety-tier/config-isolation/approval-control establishment failures, environment setting validation failure, inability to determine component criticality on which startup continuation depends).
- Decision #15 defines execution Fail-Closed conditions (unknown tool, disabled tool, unavailable tool, tool ownership ambiguity, invalid tool arguments, missing required approval, authentication or authorization failure, resource scope validation failure, allowlist validation failure, unable to verify execution prerequisites, unable to determine safe execution destination, request targeting disabled non-required component).
- Decision #14 explicitly states: "Not every dependency failure stops startup. Availability failures where the target component is explicitly classified as non-required may permit startup continuation per Decision #7." This replaces the stale "required/non-required branch" concept.
- The revised wording should express: safety/integrity failures are Fail-Fast at startup or Fail-Closed at execution, never converted to partial availability. The specific list of failure types should follow Decision #14/Decision #15 enumeration.

**INV-019 re-verification**: Current verification status is "**Not verified** — no dedicated test exercises the `is_required` branch in `scripts/agent/services/mcp_tool_discovery.py`; see ADR-004 Known Deviations." This claim was confirmed via grep in the previous session. No additional evidence found. Status remains unchanged.

**INV-020 re-verification**: Current verification status is "**Not verified** — no dedicated test; only a generic warnings-do-not-abort mechanism test exists (`test_warnings_only_no_raise`), not a scenario test tied to component-criticality classification." This claim was confirmed via grep in the previous session. No additional evidence found. Status remains unchanged.

**INV-021 rewrite**: Current description references "Undefined component criticality does not permit startup continuation." Per ADR-004 Decision #12: "コンポーネントの必須性が未定義または判定不能な場合: 当該コンポーネントを非必須であると仮定しない。未定義の分類を起動継続の根拠として用いない。これを未解決の設計上または設定上の誤りとして扱う。該当する場合は、現行のKnown Issueを記録または参照する。" The invariant should reference Decision #12's actual requirement: unknown component criticality must not be assumed non-required; it must not serve as grounds for startup continuation.

**INV-022 re-verification**: Current verification status is "Confirmed (existing ADR-004 Verification test: no fallback occurs outside ADR-010-defined conditions); no test yet for the general prohibition." This claim was confirmed via grep in the previous session. No additional evidence found. Status remains unchanged.

**Consolidation decision**: After verifying each invariant row's content against the revised ADR-004:
- INV-010 covers the single-common-policy invariant (Decision #1 + Decision #3).
- INV-011 covers the Fail-Fast/Fail-Closed boundary invariant (Decision #14 + Decision #15).
- These are distinct concerns and should remain separate unless their descriptions become identical after rewriting.
