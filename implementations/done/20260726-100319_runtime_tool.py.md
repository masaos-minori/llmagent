# Implementation procedure: scripts/shared/runtime_tool.py

## Goal

Add a new `allow_extra_fields: bool = False` field to the `RuntimeTool` dataclass and
the corresponding parameter/resolution logic to `build_runtime_tool()`, so that
`_validate_tool_args()` (added in `tool_runner.py`, see companion procedure doc for
that file) has a per-tool flag to pass through to `validate_tool_arguments()`.

## Scope

- In scope: `RuntimeTool` dataclass field + docstring; `build_runtime_tool()` parameter
  + safe-default resolution + docstring.
- Out of scope: populating `allow_extra_fields` from any MCP server tool advertisement
  (no such source field exists today); changing the sole production call site
  `scripts/agent/services/mcp_tool_discovery.py::_dedupe_and_build()` (it uses keyword
  args and does not pass this field, so it picks up the new default automatically —
  verify only, no edit).

## Assumptions

- `RuntimeTool` is `@dataclass(frozen=True)` with no `kw_only=True` (confirmed,
  `scripts/shared/runtime_tool.py:25`); all 14 existing fields are non-defaulted
  positional/keyword fields. Appending one new defaulted field after `capabilities`
  (the last existing field) is a valid dataclass field order (defaulted fields must
  trail non-defaulted ones — satisfied since it is the very last field).
- All known construction sites (`build_runtime_tool()`, and direct `RuntimeTool(...)`
  calls in `tests/test_cmd_mcp.py` ~line 530/546) use keyword arguments exclusively, so
  a new trailing defaulted field cannot break them.

## Design decisions

- Add the field as a plain `bool` with dataclass-level default `False`, matching the
  style of other boolean fields on this dataclass (`is_write`, `requires_serial`,
  `requires_approval`, `enabled_for_llm`) which are also plain (non-Optional) `bool`.
- In `build_runtime_tool()`, accept `allow_extra_fields: bool | None = None` (matching
  the existing "tri-state input, resolved boolean output" pattern used for
  `is_write`/`requires_serial`/etc.), and resolve `None` -> `False` — the same
  safe-default pattern already used for every other boolean flag in this function.
- Default to `False` (strict/reject-extra-fields) rather than `True`, per the plan's
  explicit design intent: today no MCP server advertises an "allow extra fields" flag,
  so conservative (strict) validation is the correct default for every currently
  discovered tool.

## Alternatives considered

- Making the new field `Optional[bool]` with a `None` sentinel on the dataclass itself
  (instead of resolving to a concrete `bool` in `build_runtime_tool()`): rejected —
  inconsistent with how every other boolean field on `RuntimeTool` is modeled (concrete
  `bool`, resolution happens once at construction time in `build_runtime_tool()`).
- Sourcing `allow_extra_fields` from `raw_definition` at discovery time in this same
  change: rejected — out of scope per the plan; no server currently advertises this,
  and doing so here would conflate a dataclass-shape change with a discovery-behavior
  change.

## Implementation

### Target file

`scripts/shared/runtime_tool.py`

### Procedure

1. Add `allow_extra_fields: bool` as a new field on the `RuntimeTool` dataclass,
   placed immediately after the existing `capabilities: tuple[str, ...]` field (last
   field, per dataclass field-ordering rule for defaulted fields).
2. Add a new docstring line under the `Fields:` block: `allow_extra_fields: True when
   unexpected/unschemad argument fields should be tolerated instead of rejected by
   validate_tool_arguments().`
3. In `build_runtime_tool()`:
   - Add parameter `allow_extra_fields: bool | None = None` after the existing
     `capabilities: tuple[str, ...] | None = None` parameter.
   - Add resolution line: `resolved_allow_extra_fields = (allow_extra_fields if
     allow_extra_fields is not None else False)`, placed alongside the other
     `resolved_*` lines (after `resolved_capabilities`).
   - Add `allow_extra_fields=resolved_allow_extra_fields` to the `return RuntimeTool(...)`
     call's keyword arguments (last line, after `capabilities=resolved_capabilities`).
   - Add one line to the "Safe-default rules" docstring block: `allow_extra_fields
     defaults to False — extra/unschemad fields are rejected unless a tool explicitly
     opts in.`
4. Run `tests/shared/test_runtime_tool.py` and `tests/shared/test_runtime_tool_registry.py`
   to confirm no existing construction breaks (per plan Implementation step 1).

Direct, minimal dataclass/function edit — no new abstractions, no new imports needed

## Compatibility considerations

- Backward compatible: new field is trailing and defaulted at both the dataclass and
  `build_runtime_tool()` levels; all existing all-keyword construction sites continue
  to work unchanged.
- No change to any other module's import of `RuntimeTool` or `build_runtime_tool`.

## Security considerations

- Default (`False` / strict) is the conservative choice — it does not loosen any
  existing validation behavior for any currently-discovered tool, since no tool sets
  this field explicitly today.

## Rollback considerations

- Single-file, additive-only change (new field + new parameter, both defaulted). Revert
  is a straightforward removal of the added lines; no data migration, no persisted
  state, no config-key involvement.
