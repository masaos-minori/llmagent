# Implementation Procedure: Enhance ToolLoopGuard cycle detection with progress stagnation

## Goal

Enhance cycle detection to recognize partial progress patterns, allowing earlier intervention and better user experience instead of waiting for the LLM to exhaust all allowed turns.

## Scope

- `scripts/agent/tool_loop_guard.py`: Add `_check_progress_stagnation()` method
- `scripts/agent/config_dataclasses.py`: Add `progress_stagnation_window` field to ToolConfig
- Class docstring update documenting new guard behavior

## Assumptions

1. `max_tool_turns=5` prevents true infinite loops but doesn't detect stagnation patterns
2. Tracking unique tool names per round can identify stagnation patterns
3. A configuration option for a "progress window" can measure how many distinct tool names have been used recently
4. `check_cycle()` currently detects exact fingerprint matches only (line 133-141 in tool_loop_guard.py)

## Design decisions

- Add `_check_progress_stagnation()` method to ToolLoopGuard class
- Track unique tool names per round in TurnLoopState
- Compare recent rounds' tool name sets against historical patterns
- Return exit message when stagnation detected (different tools but no new capabilities exercised)
- Add `progress_stagnation_window` config field to ToolConfig
- Update `check_all()` to call the new stagnation check before dedup/retry checks

## Alternatives considered

- Using argument similarity in addition to tool names — rejected because it adds complexity and may produce false positives for legitimate repeated tool usage patterns
- Detecting stagnation based on turn count alone — rejected because it doesn't account for varying tool usage patterns
- Adding a new `NO_PROGRESS` state to the enum — rejected because it would require changes across multiple files
