## Goal

Convert ToolLoopGuard from a hard turn-failure into a controlled final-answer fallback: when the guard detects repeated/cyclic/retrying tool calls, inject a temporary system message and call the LLM once more without tool definitions, allowing the LLM to produce a final answer using only information already available in the conversation.

## Scope

**In-Scope:**
- Add `_stream_llm_final_answer()` method to `LLMTurnRunner` — LLM call with `tool_defs=[]`
- Add `_finalize_after_guard()` method to `LLMTurnRunner` — guard-triggered final answer flow
- Move ToolLoopGuard check before assistant message persistence in `LLMTurnRunner.run()`
- Use ephemeral system message with trusted source for guard injection
- Normalize `error_kind` derivation when `TurnResult.action != "continue"`

**Out-of-Scope:**
- Changes to existing guard detection logic (cycle/dedup/retry/error_limit checks remain unchanged)
- Changes to `ToolLoopGuard.check_error_limit()` behavior
- Changes to diagnostic recording beyond what is required by the new flow
- Changes to MCP server configurations or deploy scripts

## Assumptions

1. The ephemeral system message injected by the guard should use the same ephemeral-key filtering mechanism (`_ephemeral`) already used by command handlers, so it will be cleaned up automatically between turns.
2. `LLMClient.stream()` accepts an empty `tool_defs=[]` and produces a non-tool-calls response — this is the standard OpenAI-compatible API behavior.
3. The temporary system message content defined in the requirement doc is sufficient; no additional wording refinement is needed.
4. A single final-answer attempt is enough — if the LLM still returns tool calls, the turn fails safely without further retries.

## Design decisions

- **Final-answer-only streaming**: Call `ctx.services_required.llm.stream(llm_url, ctx.conv.history, [])` with empty `tool_defs` instead of modifying the existing stream loop. This isolates the new flow from the normal execution path.
- **Ephemeral message via trusted source**: Reuse the existing `_ephemeral` key filtering mechanism rather than adding a separate bypass. If `"loop_guard"` is not in `TRUSTED_SOURCES`, add it.
- **Single retry policy**: One final-answer attempt only. No exponential backoff or multiple retries — the second failure is the safe fallback.
- **Error_kind normalization**: Derive `error_kind` from `result.error_kind or result.reason or result.action` in `Orchestrator._handle_llm_turn()` to ensure consistent error metadata downstream.

## Alternatives considered

- **Modify existing stream loop**: Could extend the current stream loop to handle the final-answer case inline. Rejected because it would increase complexity and risk of regressions in the core loop.
- **Add new LLM client method**: Could create a dedicated `stream_without_tools()` method on `LLMClient`. Rejected because `tool_defs=[]` is already supported by the OpenAI-compatible API; no new client method needed.
- **Persist unexecuted assistant message then fail**: Could persist the original assistant message and then fail. Rejected because it would leak unexecuted tool-call messages into session storage.

1. Add `_stream_llm_final_answer()` method to `LLMTurnRunner`:

   ```python
   async def _stream_llm_final_answer(self) -> Any:
       """Call LLM with empty tool_defs to get a final answer."""
       # Use _span_ctx("final_answer") for tracing
       return await self.ctx.services_required.llm.stream(
           self.llm_url,
           self.ctx.conv.history,
           [],  # tool_defs=[]
       )
   ```

   ```python
       """Handle final-answer fallback after ToolLoopGuard triggers."""

       # Call _stream_llm_final_answer() to get a final answer
   ```

#### Phase 4: Move ToolLoopGuard checks before persistence

3. In `LLMTurnRunner.run()`, reorder the inner loop body:
   - Before: persist assistant message → check guard → execute tools
   - After: check guard → (if triggered, run final-answer fallback) → else persist → execute tools
4. When guard triggers and final-answer fallback succeeds: do NOT persist the original unexecuted assistant tool-call message
5. When guard triggers and final-answer fallback fails: do NOT persist the original unexecuted assistant tool-call message; return `TurnResult(action="fail")`

### Method

- Add two new methods: `_stream_llm_final_answer()` and `_finalize_after_guard()`
- Refactor `run()` inner loop to move guard check before persistence

### Details

1. `_stream_llm_final_answer()`:
   - Call `ctx.services_required.llm.stream(llm_url, ctx.conv.history, [])` with empty `tool_defs`
   - Preserve workflow context metadata for tracing (use `_span_ctx("final_answer")`)
   - Return the normal LLM response object

2. `_finalize_after_guard()`:
   - Create ephemeral system message with text instructing LLM not to call tools again
   - Determine trusted source: either add `"loop_guard": {"_ephemeral"}` to `TRUSTED_SOURCES` in `message_schema.py` or reuse existing `"cmd_handler"` source
   - Append the ephemeral message to `ctx.conv.history`
   - Call `_stream_llm_final_answer()` to get a final answer
   - Check `finish_reason` of the response:
     - If `finish_reason != "tool_calls"`: parse the answer text, append via `_finalize_answer_text()`, return `TurnResult(action="continue", answer=answer)`
     - If `finish_reason == "tool_calls"`: return `TurnResult(action="fail", answer=msg, reason="tool_loop_guard")`

## Compatibility considerations

- Downstream consumers of `TurnResult(action="fail")` with `reason="tool_loop_guard"` may need to handle the new `error_kind` derivation change
- The ephemeral message injection requires the trusted source to be properly configured in `message_schema.py`

## Security considerations

- Ephemeral message injection must pass schema validation — validate message schema before appending; log warning if injection fails and fall back to the current hard-stop behavior
- The temporary system message must not contain user data or sensitive information

## Rollback considerations

- If the final-answer fallback causes unexpected behavior, revert the reorder of guard check before persistence
- If ephemeral message injection fails, fall back to the current hard-stop behavior
- Ensure `error_kind` is explicitly set to `"tool_loop_guard"` in the new code paths to avoid breaking existing consumers
