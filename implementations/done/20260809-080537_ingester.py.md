# Implementation Procedure: Phase 4 — Update Main Ingestion Methods

## Goal

Update `ingest_url_group()` to collect `PreparedChunk` results from workers, then call `_commit_url_transaction()`. Remove `db.commit()` call before `_ingest_chunk_files()`. Update `_log_ingestion_result()` and `_route_chunk_files()` to use `IngestionFailureReason` values.

## Scope

### In-Scope
- Modify `ingest_url_group()` to collect `PreparedChunk | IngestionFailureReason` results from workers
- Remove `db.commit()` call before `_ingest_chunk_files()` — transaction handles commit
- Update `_log_ingestion_result()` to use `IngestionFailureReason` values instead of `(chunk_ok, embed_ok)` tuple checks
- Update `_route_chunk_files()` to use `IngestionFailureReason` for routing decisions
- Handle partial success scenario — if ANY chunk fails during preparation, entire URL group rolled back

### Out-of-Scope
- Changes to cache invalidation logic (Phase 5)
- Changes to `document_manager.py` beyond removing `delete_existing_document()` delegation (Phase 6)
- Database schema changes

## Assumptions

1. `ThreadPoolExecutor` shutdown waits for all workers to complete before proceeding (confirmed by Python stdlib docs)
2. `PreparedChunk` objects can be safely collected into a list without memory pressure (acceptable since URLs processed sequentially; memory freed after commit)
3. `IngestionFailureReason` values are comparable with string literals via `StrEnum` (confirmed by Python 3.11+ behavior)
4. sqlite-vec extension works with single connection approach (RESOLVED: Confirmed — `_load_vec_extension()` in `helper.py:145-158` loads vec extension once per connection)

## Design decisions

- `ingest_url_group()` collects results from ALL workers first, then decides whether to proceed with commit based on whether ANY failed
- If ANY worker returns `IngestionFailureReason`, the ENTIRE URL group is rolled back — no partial commits possible
- `_log_ingestion_result()` uses `IngestionFailureReason` values directly instead of checking `(chunk_ok, embed_ok)` tuple semantics
- `_route_chunk_files()` routes files based on `IngestionFailureReason` value, not boolean flags
- File routing happens AFTER successful commit — if commit fails, files stay in their original location for retry

## Alternatives considered

- Processing each chunk individually (one-by-one): rejected because it doesn't solve the atomicity problem — partial commits still possible
- Using a shared queue between workers and main thread: rejected because it adds complexity without solving the fundamental inconsistency problem
- Returning a dict instead of `PreparedChunk`: rejected because dataclass provides type safety and IDE support

#### Step 2: Modify `ingest_url_group()` to collect `PreparedChunk` results

Change the result collection loop:
```python
with ThreadPoolExecutor(max_workers=self._max_workers) as executor:
    futures = {
        executor.submit(self._embed_and_store, doc_id, path): path
        for path in paths
    }
    prepared_chunks: list[PreparedChunk] = []
    failure_reason: IngestionFailureReason | None = None
    
    for future in concurrent.futures.as_completed(futures):
        result = future.result()
        if isinstance(result, PreparedChunk):
            prepared_chunks.append(result)
        else:
            # result is IngestionFailureReason
            failure_reason = result
            break  # Stop processing — abort early on failure
```

Key points:
- Collect results into `prepared_chunks` list
- If ANY result is `IngestionFailureReason`, set `failure_reason` and break early
- No more `(chunk_ok, embed_ok)` tuple unpacking

### Details

**File locations**: `scripts/rag/ingestion/ingester.py`

**Key changes**:
1. Replace `(chunk_ok, embed_ok)` tuple unpacking with `isinstance(result, PreparedChunk)` check
2. Remove `db.commit()` before chunk processing
3. Add `_commit_url_transaction()` call after collecting all results
4. Update `_log_ingestion_result()` to use `IngestionFailureReason` values
5. Update `_route_chunk_files()` to use `IngestionFailureReason` for routing decisions
6. Handle partial success scenario — if ANY chunk fails, entire URL group rolled back

**Critical insight**: The main thread becomes the sole DB writer. All DB operations happen within `_commit_url_transaction()` using `BEGIN IMMEDIATE`. This ensures atomicity — either ALL chunks for a URL are committed, or NONE are.

**Thread safety**: Since workers no longer hold DB connections, there's no risk of connection conflicts. The main thread handles all DB writes sequentially.

**Memory consideration**: `PreparedChunk.embedding_blob` stores raw bytes — memory pressure for large documents is acceptable since URLs are processed sequentially; memory is freed after commit.
