# Implementation: BLE001 triage batch (multiple files) — Phase 2: triage net-new BLE001 findings

## Goal

Once `BLE001` is active in `pyproject.toml`'s `select` list (Phase 1), triage every
newly-surfaced "blind except" finding across `scripts/` and `tests/`: narrow the except
clause to a specific exception type where feasible, or add a justified
`# noqa: BLE001 — <specific reason>` following the codebase's existing justification
style.

## Scope

**In-Scope:**
- All net-new (currently unsuppressed) `BLE001` findings surfaced by
  `uv run ruff check --select BLE001 scripts/ tests/` after Phase 1 lands.
- Per-site review: narrow the `except` clause where feasible; otherwise add a specific,
  em-dash-justified `# noqa: BLE001` comment.
- Re-running the `rules/coding.md` suppression-governance `rg` checks to confirm every
  `BLE001`/`PLC0415` noqa (old and new) carries a justification.
- Running `tox -e lint` to confirm no regressions after triage.

**Out-of-Scope:**
- The 23 files/sites that already carry a pre-existing, previously-reviewed
  `# noqa: BLE001` comment (per the plan: "already reviewed in the prior cycle,
  `plans/20260806-105228_plan.md`" — not re-litigated here), notably
  `scripts/agent/startup.py`'s 5 existing noqa comments.
- `PLC0415` findings — explicitly out of scope for the whole plan (separate, much larger
  effort).
- Any behavior change beyond exception-handling specificity (no new features, no
  refactors unrelated to the blind-except pattern).

## Design decisions

- Defer exact scoping to Phase 2 execution time (post-Phase-1) rather than freezing a
  file list now — the plan itself explicitly avoids enumerating this list to prevent
  staleness; this procedure document follows the same discipline.
- Prefer narrowing the `except` clause to a specific exception type over adding
  `# noqa: BLE001` wherever feasible — only fall back to a justified noqa when the
  code path genuinely needs to catch a broad exception (e.g. a top-level error boundary
  that must not crash the process), per the plan's Implementation Steps Phase 2 wording.

## Alternatives considered

- Blanket-suppress all net-new findings with an unjustified or generically-worded
  `# noqa: BLE001` — rejected: the plan explicitly mitigates this risk ("do not
  bulk-suppress with a blanket noqa") and requires per-site review.
- Enumerate today's snapshot list as the final, authoritative scope — rejected: the
  snapshot was taken with `--select BLE001` overriding the *current* (pre-Phase-1)
  config, so it may shift slightly once `pyproject.toml`'s actual `select` list changes
  and interacts with any per-file `# noqa` already present; the plan requires
  regeneration post-Phase-1, and this document defers to that requirement rather than
  risking a stale enumeration.

### Procedure
1. Confirm Phase 1 (`pyproject.toml` BLE001 activation) has landed.
2. Re-run `uv run ruff check --select BLE001 scripts/ tests/` to get the authoritative,
   current finding list.
3. Cross-reference against the 23 already-reviewed, already-justified
   `# noqa: BLE001` sites from `plans/done/20260806-105228_plan.md` — exclude those from
   re-triage.
4. For each remaining (net-new) finding: read the surrounding function to decide between
   (a) narrowing the `except` clause to a specific exception type, or (b) adding
   `# noqa: BLE001 — <specific reason>` matching the codebase's existing justification
   style (e.g. "must not abort", "classification fallback").
5. Re-run the suppression-governance `rg` checks from `rules/coding.md` (as corrected by
   the Phase 1 `rules/coding.md` procedure) to confirm every `BLE001` noqa now carries a
   justification.
6. Run `tox -e lint` to confirm no regressions.
7. Do not implement yet — this is a document-only phase; the actual per-file edits happen
   at `prompts/03_implementation.md` time. Given the number of files involved, the
   implementer may choose to further decompose this batch into smaller sub-batches or
   per-file procedures at that time, consistent with `prompts/02`'s "file-level
   implementation procedure" norm — this document intentionally defers that
   decomposition rather than guessing at a stale file list now.

### Method

inline noqa comment addition) — no automated codemod; each site requires human judgment
about the correct exception type or justification.

## Compatibility considerations

- Exception-handling behavior changes only where an `except` clause is narrowed — this
  changes which exception types are caught at that site. Each narrowing must be verified
  against the corresponding test file (e.g. `tests/agent/test_startup.py`,
  `tests/agent/test_startup_consistency.py` for `scripts/agent/startup.py`) to confirm no
  intended-to-be-caught exception type is newly missed.
- No suppression-only (`noqa`-only) change alters runtime behavior.

## Security considerations

- Narrowing overly-broad `except Exception:`/`except BaseException:` clauses generally
  *improves* the security/reliability posture (avoids silently swallowing unexpected
  errors) — no negative security implication expected; verify no narrowing accidentally
  drops a legitimate error-handling path relied on for graceful degradation.

## Rollback considerations

- Each site's edit (narrowed except clause or added noqa comment) is independently
  revertable (single-line/single-block diff); no cross-file migration or shared state.
- Recommend committing Phase 2 triage separately from Phase 1 (per the plan's phased
  design), so a problematic narrowing at one site can be reverted without touching the
  `pyproject.toml`/`rules/coding.md` Phase 1 commit.
