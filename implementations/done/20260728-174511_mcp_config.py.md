## Goal

Add a denylist-based validation for `McpServerConfig.env` in `scripts/shared/mcp_config.py`, mirroring the existing `env_denylist` pattern in `config/shell_mcp_server.toml`, so that dangerous env var keys (`LD_PRELOAD`, `LD_LIBRARY_PATH`, `PYTHONPATH`) cannot be silently merged into an MCP server subprocess environment via `config/agent.toml`.

## Scope

**In-Scope:**
- Extend `McpServerConfig._validate_cross_fields()` in `scripts/shared/mcp_config.py` (the existing `env` type-check loop at lines 115-119) to also reject keys matching a denylist of dangerous glob patterns, raising `ValueError` with a message identifying the offending key.
- Hardcode the denylist as a module-level constant reusing the same default values as `config/shell_mcp_server.toml`'s `env_denylist` (`LD_PRELOAD`, `LD_LIBRARY_PATH`, `PYTHONPATH`), matched via `fnmatch.fnmatch` (consistent with `scripts/mcp_servers/shell/shell_service.py::_filter_env`).
- Add a short code comment at `HttpServerLifecycleManager.start()` (`scripts/agent/http_lifecycle.py:224-226`) noting that env is validated upstream at config-load time in `McpServerConfig`, so no duplicate filtering is needed there.
- Add unit tests in `tests/test_mcp_config_validation.py` covering: a denylisted key raises `ValueError`; a non-denylisted key continues to validate successfully.

**Out-of-Scope:**
- Adding a new configurable `env_allowlist`/`env_denylist` TOML option scoped to `[mcp_servers.<key>]` — approach (a), a hardcoded shared denylist, is chosen instead since it is the smaller, immediately-testable change and no current `config/agent.toml` entry defines `env`, so there is no configurability need yet.
- Any change to `scripts/mcp_servers/shell/shell_service.py` or `config/shell_mcp_server.toml` (the precedent, left untouched).
- Any change to `HttpServerLifecycleManager.start()`'s env-merge logic itself (`env = {**os.environ, **cfg.env}` stays unchanged; only a documentation comment is added).
- Runtime/behavioral changes to MCP server startup for any currently configured server (none define `env` today).

## Assumptions

1. `cfg.env`/`cfg.cmd` in `config/agent.toml`-family files are admin-controlled, not derived from untrusted runtime input.
2. Rejecting (raising `ValueError`) rather than silently filtering is preferred — fail-fast at config-load beats silent filtering that could mask a misconfiguration.
3. No currently deployed `[mcp_servers.<key>]` section in `config/agent.toml` sets `env`, so this change has zero behavioral impact on existing valid configs.
4. The denylist only needs to match the three key names cited in the requirement plus glob-pattern support for consistency with the shell precedent; no additional dangerous keys are added speculatively.

## Design decisions

- Add module-level constant `_ENV_KEY_DENYLIST: tuple[str, ...] = ("LD_PRELOAD", "LD_LIBRARY_PATH", "PYTHONPATH")` near top-level imports/constants in `mcp_config.py`.
- Use `fnmatch.fnmatch(k, p)` for each `(k, p)` pair in the denylist, consistent with `shell_service.py::_filter_env`.
- Raise `ValueError(f"{key_prefix}: env key {k!r} matches denylisted pattern; dangerous loader/interpreter env vars are not permitted")` when a key matches.
- Add one-line comment above `env = None` in `http_lifecycle.py:224` documenting that env filtering happens upstream at `McpServerConfig` construction.

## Alternatives considered

- Configurable `env_denylist` field in `McpServerConfig` (TOML option). Rejected — keeps the change contained to the two target files named in the requirement; can be promoted later if needed.
- Silent filtering instead of rejection. Rejected — fail-fast at config-load is preferred per the requirement's stated preference.
