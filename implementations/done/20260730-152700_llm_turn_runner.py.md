## Goal

Convert ToolLoopGuard from a hard turn-failure into a controlled final-answer fallback: when the guard detects repeated/cyclic/retrying tool calls, inject a temporary system message and call the LLM once more without tool definitions, allowing the LLM to produce a final answer using only information already available in the conversation.

## Scope

**In-Scope:**
- Add `_stream_llm_final_answer()` method to `LLMTurnRunner` — LLM call with `tool_defs=[]`
- Add `_finalize_after_guard()` method to `LLMTurnRunner` — guard-triggered final answer flow
- Move ToolLoopGuard check before assistant message persistence in `LLMTurnRunner.run()`
- Use ephemeral system message with trusted source for guard injection
- Normalize `error_kind` derivation when `TurnResult.action != "continue"`

**Out-of-Scope:**
- Changes to existing guard detection logic (cycle/dedup/retry/error_limit checks remain unchanged)
- Changes to `ToolLoopGuard.check_error_limit()` behavior
- Changes to diagnostic recording beyond what is required by the new flow
- Changes to MCP server configurations or deploy scripts

## Assumptions

1. The ephemeral system message injected by the guard should use the same ephemeral-key filtering mechanism (`_ephemeral`) already used by command handlers, so it will be cleaned up automatically between turns.
2. `LLMClient.stream()` accepts an empty `tool_defs=[]` and produces a non-tool-calls response — this is the standard OpenAI-compatible API behavior.
3. The temporary system message content defined in the requirement doc is sufficient; no additional wording refinement is needed.
4. A single final-answer attempt is enough — if the LLM still returns tool calls, the turn fails safely without further retries.

## Design decisions

- Use ephemeral system message (not a regular system message) for guard-injected hint to avoid polluting conversation history.
- Perform guard check before persisting the assistant message to prevent unexecuted tool-call messages from leaking into session storage.
- Single final-answer attempt only — if the LLM still returns tool calls, treat as hard failure. This avoids infinite retry loops.
- Derive `error_kind` from `result.error_kind or result.reason or result.action` for robustness in downstream consumers.

## Alternatives considered

- **Retry with tools after guard trigger**: Would allow another tool-call attempt but risks repeating the same loop. Rejected in favor of simpler single-attempt approach.
- **Add new ephemeral source ID vs reuse existing**: Adding a dedicated `"loop_guard"` source provides clearer audit trail but adds maintenance overhead. Reuse of `"cmd_handler"` is acceptable if scope is limited.
- **Persist assistant message then override**: Would keep existing persistence logic but risks inconsistent state. Rejected in favor of pre-persistence guard check.

```python
async def _stream_llm_final_answer(self, ctx: TurnContext) -> Any:
    """Call LLM with no tool definitions to get a final text answer."""
    span_ctx = self._span_ctx("final_answer")
    try:
        response = await ctx.services_required.llm.stream(
            ctx.conv.history,
            [],  # tool_defs=[] — no tools available
        )
        return response
    except Exception as e:
        logger.warning(
            f"Final-answer LLM call failed: {e}",
            exc_info=True,
        )
        raise
```

3. Preserve workflow context metadata via `_span_ctx("final_answer")` for tracing.

### Phase 2: Add guard finalization handler

1. Add `_finalize_after_guard()` method to `LLMTurnRunner`:

```python
def _finalize_after_guard(self, ctx: TurnContext, guard_result: GuardResult) -> TurnResult:
    """Handle the final-answer fallback after ToolLoopGuard triggered."""
    # Inject temporary system message with trusted source
    # TODO: Determine trusted source — either add "loop_guard" to TRUSTED_SOURCES
    # in message_schema.py or reuse existing "cmd_handler" source.
    ephemeral_msg = Message(
        role="system",
        content=GUARD_HINT,
        source="loop_guard",  # or "cmd_handler" depending on decision above
        ephemeral_keys={"_ephemeral"},
    )
    ctx.conv.history.append(ephemeral_msg)

    # Call LLM without tools
    try:
        response = self._stream_llm_final_answer(ctx)
    except Exception as e:
        logger.warning(f"Final-answer stream failed, returning hard fail: {e}")
        return TurnResult(
            action="fail",
            reason="tool_loop_guard",
            answer=f"Tool loop detected. Error during final answer: {e}",
        )

    # Parse response
    finish_reason = getattr(response, "finish_reason", None)
    if finish_reason != "tool_calls":
        # LLM produced text answer — append and continue
        answer_text = response.content if hasattr(response, "content") else str(response)
        assistant_msg = Message(role="assistant", content=answer_text)
        ctx.conv.history.append(assistant_msg)
        return TurnResult(action="continue", answer=answer_text)
    else:
        # LLM still returned tool calls — hard fail
        return TurnResult(
            action="fail",
            reason="tool_loop_guard",
            answer="Tool loop detected. Final answer attempt also returned tool calls.",
        )
```

### Phase 3: Move ToolLoopGuard checks before persistence

1. In `LLMTurnRunner.run()`, locate the inner loop body where:
   - Assistant message is persisted → guard check → tools executed
   
2. Reorder to:
   - Guard check → (if triggered, run final-answer fallback) → else persist assistant message → execute tools

3. Pseudocode for the reordered inner loop:

```python
# BEFORE guard check (original order):
# ctx.session.save(..., tool_calls=...)  # persist assistant message
# guard_result = self.guard.check(...)
# if guard_result.triggered:
#     return TurnResult(action="fail", reason="tool_loop_guard")
# ... execute tools ...

# AFTER reordering:
guard_result = self.guard.check(...)
if guard_result.triggered:
    return self._finalize_after_guard(ctx, guard_result)
# Only persist if guard did NOT trigger
ctx.session.save(..., tool_calls=...)
... execute tools ...
```

4. When guard triggers and final-answer fallback succeeds: do NOT persist the original unexecuted assistant tool-call message.
5. When guard triggers and final-answer fallback fails: do NOT persist the original unexecuted assistant tool-call message; return `TurnResult(action="fail")`.

## Compatibility considerations

- Downstream consumers of `TurnResult(action="fail")` with `reason="tool_loop_guard"` may see a change in `error_kind` derivation. Ensure callers handle both old and new values.
- If `GUARD_HINT` constant is added to `tool_loop_guard.py`, verify it does not conflict with any existing constants in that module.
- The ephemeral message injection requires either a new trusted source entry or reuse of an existing one in `message_schema.py`. Validate against existing schema enforcement.

## Security considerations

- The ephemeral system message must use a trusted source to pass schema validation. Untrusted sources would cause injection failures.
- No new secrets or credentials are introduced. The guard hint is a static string.
- The final-answer LLM call uses the same LLM client as other calls — no privilege escalation risk.

## Rollback considerations

- If the final-answer fallback causes issues, revert the guard check ordering in `run()` to restore the original hard-stop behavior.
- Removing the `_finalize_after_guard()` method and `_stream_llm_final_answer()` method restores the previous behavior entirely.
- The `GUARD_HINT` constant can be removed from `tool_loop_guard.py` without side effects.
