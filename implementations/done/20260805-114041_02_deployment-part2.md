# Implementation Procedure: docs/02_deployment-part2.md — Failure Mode Symptom Sync

## Goal
- Ensure the "症状" (symptom) column of the failure-mode table in `docs/02_deployment-part2.md`
  §3.3 exactly matches the `[FATAL]` log strings emitted by `deploy/deploy.sh`,
  `deploy/init_db.sh`, and `deploy/setup_services.sh`, so operators can `grep` the table
  text directly against live logs.

## Scope
- In scope: the four symptom-column cells in the §3.3 failure-mode table
  (`docs/02_deployment-part2.md`, lines 56-60 as of this writing).
- Out of scope: the "失敗スクリプト" (script) and "対処法" (remedy) columns; any change to
  `deploy/*.sh`; adding/removing table rows; any other document.

## Assumptions
- The four target log strings in the plan are copied verbatim from the deployment scripts
  (verified below — see Details).
- **Observation (not an assumption to verify, a confirmed fact as of 2026-08-05):** the live
  content of `docs/02_deployment-part2.md` lines 57-60 already contains the exact four
  strings the plan proposes. Grep evidence:
  - `docs/02_deployment-part2.md:57` → `` `[FATAL] Workflow definition failed validation; aborting deployment.` ``
  - `docs/02_deployment-part2.md:58` → `` `[FATAL] Deployed workflow definition checksum does not match source; deployment corrupted.` ``
  - `docs/02_deployment-part2.md:59` → `` `[FATAL] Workflow database schema is missing or incomplete.` ``
  - `docs/02_deployment-part2.md:60` → `` `[FATAL] Workflow schema version mismatch: expected <X>, found <Y>.` ``
  - This means the described edit is likely already a no-op against current `master`. The
    implementer must diff current content against the plan's four target strings before
    editing (see Procedure step 1) rather than assume the change is still pending.

## Design decisions
- Treat this as a single-file, single-table documentation edit — no new abstraction, no
  script changes. (per `skills/python-design` guidance: keep the design no larger than the
  problem requires.)
- Source of truth for each symptom string is the literal `echo "[FATAL] ..."` line in the
  corresponding `deploy/*.sh` script, not paraphrase — this preserves grep-ability, the
  stated goal of the plan.
- Re-verify the live file state before editing, since documentation and source can drift in
  either direction between plan authoring and implementation.

## Alternatives considered
- Auto-generate the failure-mode table from the scripts at build time — rejected as
  out-of-scope; plan explicitly scopes this to a manual doc edit, and no build-time doc
  generation mechanism exists in this repo.
- Leave the table paraphrased ("human readable") instead of verbatim log strings — rejected
  because the plan's Goal is explicitly grep-ability, which requires exact string match.
