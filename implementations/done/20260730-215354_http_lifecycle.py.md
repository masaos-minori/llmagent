# Implementation Procedure: Dynamic Health Check Timeout Based on Startup Timeout Configuration

## Goal

Make the health check request timeout configurable and proportional to the overall startup timeout, eliminating the hardcoded 5-second value that causes false failures for slow-starting servers.

## Scope

**In-Scope:**
- Replace hardcoded `timeout=5.0` in health check client creation with a computed value
- Compute timeout as a fraction of `cfg.startup_timeout_sec` capped at a maximum

**Out-of-Scope:**
- Changing the health check polling interval (0.5 seconds)
- Changing the re-check interval for ongoing health monitoring
- Adding jitter or exponential backoff to the timeout calculation

## Assumptions

1. A fraction of 1/10 of the startup timeout provides reasonable per-request timeout while allowing retries within the overall window
2. Maximum timeout of 15 seconds prevents unreasonably long individual requests
3. Minimum timeout of 3 seconds ensures the timeout isn't too aggressive for fast-starting servers

## Design decisions

- Timeout formula: `min(max(cfg.startup_timeout_sec // 10, 3.0), 15.0)`
- Fraction: 1/10 of startup timeout allows ~10 retry attempts within the overall window
- Minimum: 3.0 seconds prevents timeouts from being too aggressive
- Maximum: 15.0 seconds prevents unreasonably long individual requests

## Alternatives considered

- Fixed 10-second timeout → rejected; still fails for servers with >10s startup
- Fully configurable per-server timeout → deferred; adds config complexity without clear benefit
- Exponential backoff between retries → deferred; low priority given current usage

### Method

Add helper method to `HttpServerLifecycleManager`:

```python
def _compute_health_check_timeout(self, startup_timeout_sec: int) -> float:
    """Compute health check request timeout based on startup timeout.
    
    Returns a timeout value proportional to startup_timeout_sec, bounded
    by [3.0, 15.0] seconds.
    """
    return min(max(startup_timeout_sec // 10, 3.0), 15.0)
```

## Compatibility considerations

- No API changes; internal method signature unchanged
- Existing single-server deployments may see improved reliability for slow-starting servers
- Multi-server deployments unaffected unless they have servers with startup_timeout_sec > 50

## Security considerations

- No new secrets or sensitive data exposed through log messages
- Timeout computation uses only configuration values already available

## Rollback considerations

- Simple rollback: revert to original hardcoded timeout values
- No data migration or schema changes required
- If regression detected, set `startup_timeout_sec` to small value to reduce computed timeout
