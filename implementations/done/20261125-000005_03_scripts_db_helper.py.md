## Goal

Make every write path in the db helper consult the gate before it executes a write statement, so a write that starts after shutdown begins is refused rather than committed (REQ-004: writes stop when shutdown starts; REQ-005: the refusal lives in the db layer; AC-2: no write succeeds after the gate closes).

## Scope
**Release unit**: R2-write-gate (Phase 2)

- In scope: the write entry points of `scripts/db/helper.py` and the read paths that must stay unaffected.
- Out of scope: the gate itself (row 2), the package exports (row 4), and closing the gate (row 5).

## Assumptions

- The write statements are reached through a small number of entry points in `scripts/db/helper.py`, so the check belongs at those entry points rather than at each call site.
- Reads must keep working after the gate closes: the snapshot and checkpoint steps read while writes are refused (REQ-006, REQ-008).
- Verified against source 2026-11-25 (execution): the first assumption holds — no `scripts/` module reaches the connection behind the helper (`grep -rn "\.conn\.execute" scripts/` is empty), so the nine entry points cover every write. The second needs a precision the procedure did not state: `execute` is also the read path for 22 literal `SELECT` call sites in `scripts/`, so gating it unconditionally would refuse reads the Plan requires to keep working. The guard is therefore statement-aware (Implementation step 4), which is what makes the Plan's "Read-only paths are never gated" (`plans/done/20261124-095950_cliplc004_bounded-shutdown-machine.md:78`) hold for `execute` too.
- Size budget: `scripts/db/helper.py` was 21518 B against the 24576 B gate. Measured after the change: 23961 B (guard methods, nine call sites, and the docstring lines that explain them), 615 B of headroom, no baseline entry needed. Later rows must not grow this file further without splitting it or recording a baseline entry.

## Design decisions

- Check inside the helper, not in the callers: the import contract allows only `agent -> db`, so a db-layer check is the only place that covers every caller, and a caller-side check would leave a second path to the same connection.
- The check is a single call to the gate's write check at the top of each write entry point; no write function gains a new parameter, so no caller signature changes.
- Compatibility impact: callers that write during shutdown now receive `WriteGateClosed` (new); callers during normal operation are unaffected.

## Alternatives considered

- wrap every write in the authorized context by default — rejected: that would make the gate advisory, which is the failure mode the Plan's Problem section describes.

## Implementation
### Target file
`scripts/db/helper.py`

### Procedure
1. Import the gate and the statement classifier from `scripts/db/write_gate.py` (row 2): `get_write_gate`, `is_write_statement`.
2. Add one private guard, `_ensure_write_allowed(operation)`, that calls the gate's `check_write(operation)` and lets `WriteGateClosed` (new) propagate unchanged.
3. Call the guard from the nine write entry points the Plan lists (`plans/done/20261124-095950_cliplc004_bounded-shutdown-machine.md:78`): `open(write_mode=True)`, `execute`, `executemany`, `executescript`, `commit`, `_begin_transaction` (which both `begin_immediate` and `begin_exclusive` go through), `checkpoint`, and `vacuum`.
4. Gate a statement entry point only when the statement is a write: `execute` and `executemany` consult `is_write_statement(sql)` first; `executescript` is always gated (a script commits implicitly, so its statements cannot be classified reliably); `commit` is gated only when `conn.in_transaction` is true, which is SQLite's own answer to whether a write is being made durable.
5. Leave the read paths untouched: `fetchall`, `health_check`, `interrupt_when`, `close`, and `open()` without `write_mode` gain no check (REQ-006, REQ-008).

### Method
- Guard at the boundary: the check happens before any statement is prepared, so a refused write never allocates a cursor or opens a transaction.
- No exception is caught inside the helper: the caller decides whether a refused write is fatal, and the gate has already counted it.

### Details
- The helper does not decide which steps are authorized: it only asks the gate whether this write may proceed, which keeps the authorization decision in the shutdown coordinator (row 5).
- `interrupt_when` (`scripts/db/helper.py:158-184`) is the interrupt entry point the settle step uses (row 5); this row does not change its behavior, and an interrupted statement is a distinct outcome from a refused write.

## Compatibility considerations

- No public signature changes in the helper; the new behavior is a raised exception on a path that previously succeeded.
- Callers that legitimately write during shutdown must run inside the authorized context (row 5), otherwise they fail loudly.

## Security considerations

- The propagated exception carries the gate state and step name only, no SQL text or path (REQ-013).

## Rollback considerations

- Revert this row's commit alone: the gate module stays unused and inert, so removing the checks restores today's behavior exactly.
