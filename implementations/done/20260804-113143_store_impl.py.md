## Assumptions
- `chunks_vec`'s runtime distance metric is L2, confirmed by `distance_metric=L2` in
  `scripts/db/schema_sql.py`'s `CREATE VIRTUAL TABLE ... USING vec0(...)` statement for
  `chunks_vec` (added by commit `556490796`).
- No normalization step between embedding generation and `chunks_vec` insertion makes
  L2 and cosine equivalent — confirmed by reading `vec_insert` (lines 30-36), which inserts
  raw embedding bytes directly with no call to `cosine_sim` or any normalization helper.
- `tests/db/test_db_store_impl.py::test_vec_search_*` (5 tests, lines 301-341) assert
  delegation against a mocked DB layer only; they do not assert on docstring text or actual
  distance values, so this change cannot regress them.

## Design decisions
- Single string-literal edit only; no new abstraction, no signature change, no test file
  edit. The existing `vec_search` contract (`(embedding: bytes, k: int) -> list[tuple[int, float]]`)
  is unaffected — this is a documentation-accuracy fix, not a behavioral change.
- Wording style follows the existing sibling docstring at `scripts/rag/repository.py:144`
  (`"""Retrieve top_k chunks by L2-distance KNN (smaller distance = higher similarity)."""`)
  for consistency across the codebase, per the plan's Design section.

- Also updating `schema_sql.py`/`repository.py` "for consistency" — explicitly rejected;
  both are already correct and the plan marks them read-only/must-not-change (scope creep
