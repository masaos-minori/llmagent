# Implementation: `orchestrator.py` — Reject Halted Tasks in `_init_workflow_task()`

## Goal

Ensure `_init_workflow_task()` never resumes a task whose persisted status is `"halted"`
when restoring from a previously stored `pending_approval_task_id` (or any other
`existing_task_id` caller), since halted tasks require explicit user action rather than
automatic restoration.

## Scope

**In scope:**
- `scripts/agent/orchestrator.py::_init_workflow_task()`, the `existing_task_id is not
  None` branch (lines 315-320).

**Out of scope:**
- `cmd_workflow.py` overwrite-warning fix (separate implementation doc).
- `startup.py` overwrite-protection fix (separate implementation doc).
- Changing `TaskRecord.status` values or the state machine in `workflow_engine.py`.
- Handling of statuses other than `"halted"` (e.g. `"completed"`, `"failed"`) — out of
  scope per plan; only halted-task rejection is required.

## Assumptions

- Valid `TaskRecord.status` values are `pending | running | pending_approval | completed |
  failed | halted` (confirmed: `scripts/agent/workflow/models.py:20`).
- A task reaches `"halted"` via `update_task_status(..., "halted")`, called from
  `cmd_workflow.py::_cmd_reject()` (line 167) and `workflow_engine.py` (lines 149, 186) —
  i.e. halted is a deliberate terminal/suspended state, not a transient one.
- Raising `RuntimeError` on a halted task is consistent with the existing "not found" case
  in the same branch (`raise RuntimeError(f"Task {existing_task_id} not found")`, line 318),
  so callers of `_init_workflow_task()` already have to handle a `RuntimeError` from this
  method.
- `WorkflowEngine`/`_handle_workflow_engine()` has no fallback path that expects a halted
  task to be silently substituted with a new one; a raised `RuntimeError` propagates up to
  the caller of `_handle_workflow_engine()`, which is expected to report the error to the
  user (existing `except` handling only catches `WorkflowPendingApprovalError` and
  `WorkflowHaltError` at lines 262-265 — a bare `RuntimeError` will propagate further; this
  is an existing behavior for the "not found" case too, so no new failure mode is
  introduced).

## Design decisions

- Perform the status check immediately after `get_task_by_id()` returns a non-`None`
  result, colocated with the existing "not found" check, so both invalid-task conditions
  are handled in one place.
- Reuse `RuntimeError` (not a new exception type) for consistency with the adjacent
  "not found" branch — introducing a dedicated exception class is not justified for a
  single new condition (YAGNI).
- Fail closed: any halted task is rejected regardless of caller (there is currently only
  one caller path — via `ctx.turn.pending_approval_task_id` from `_handle_workflow_engine`
  — but the check belongs at the shared retrieval point, not the caller).

## Alternatives considered

- **Silently create a new task instead of raising**: rejected — this would hide the halted
  state and violate the requirement that halted tasks require explicit user action.
- **Check status in the caller (`_handle_workflow_engine`) instead of
  `_init_workflow_task`**: rejected — `_init_workflow_task` is the single point that fetches
  the `TaskRecord`; checking there avoids duplicating the fetch-then-validate pattern if a
  second caller is added later.
- **Introduce a dedicated `HaltedTaskError` exception**: deferred — no current caller
  distinguishes "not found" from "halted" programmatically; a plain `RuntimeError` with a
  descriptive message is sufficient until such a need arises.

## Implementation

### Target file

`scripts/agent/orchestrator.py`

### Procedure

1. In `_init_workflow_task()`'s `else` branch (existing_task_id path, lines 315-320),
   after the existing "not found" check, add a status check:
   ```python
   else:
       _fetched = get_task_by_id(store._db, existing_task_id)
       if _fetched is None:
           raise RuntimeError(f"Task {existing_task_id} not found")
       if _fetched.status == "halted":
           raise RuntimeError(
               f"Task {existing_task_id} is halted and cannot be automatically resumed"
           )
       task = _fetched
       workflow_id = task.workflow_id or str(uuid.uuid4())
   ```
2. No change to the `existing_task_id is None` (new-task) branch.

### Method

Direct in-place edit: one new `if` guard raising `RuntimeError`, inserted between the
existing `None` check and the `task = _fetched` assignment. No new function, parameter,
or import required (`RuntimeError` is a builtin).

### Details

- Confirmed by direct read (`scripts/agent/orchestrator.py:280-324`): the `else` branch has
  exactly one existing validation (`_fetched is None`); no status check currently exists.
- Keep the new line under 120 chars.
- No change to the `try/finally` `store.close()` handling — the new `raise` occurs inside
  the existing `try` block, so `finally: if close_store: store.close()` still runs.

## Compatibility considerations

- Backward-incompatible in one specific case: a caller that previously resumed a halted
  task via a stale `existing_task_id` will now get a `RuntimeError` instead of silently
  reusing the halted `TaskRecord`. Per plan Risk 1, this is the intended behavior change;
  no migration path is defined for callers relying on the old silent-resume behavior since
  none is known to exist in this codebase (only path currently supplying
  `existing_task_id` is `ctx.turn.pending_approval_task_id`, which is cleared to `None`
  immediately after use per `orchestrator.py:225`, and only ever set by `_cmd_approve`,
  never after a reject/halt).
- No change to the `existing_task_id is None` (fresh task) path.

## Security considerations

- N/A — no new external input, no change to authorization/trust boundaries; task IDs are
  already-internal identifiers sourced from `ctx.turn.pending_approval_task_id`.

## Rollback considerations

- Single-file, single-guard change — revert by removing the new `if` block. No persisted
  data or schema change; rollback is a pure code revert.
