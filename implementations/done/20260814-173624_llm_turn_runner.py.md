# Implementation Procedure: Shift LLM-Facing Tool List Construction to RuntimeToolRegistry

## Goal

Change `_filter_disabled_tool_definitions()` in `scripts/agent/llm_turn_runner.py` to build the LLM-facing tool list directly from `RuntimeToolRegistry.llm_tool_definitions()` instead of from `ctx.cfg.tool.tool_definitions` (static config). This eliminates the second source of truth for tool shape between the call-execution path (which treats the registry as sole authority per the sibling fail-closed requirement) and the LLM-payload construction path.

## Scope

### In-Scope
- Change `_filter_disabled_tool_definitions()` (`scripts/agent/llm_turn_runner.py:207-223`) to use `registry.llm_tool_definitions()` as the base list when `registry is not None`.
- Remove the `known_names` intersection logic — since the base list now comes from the registry, all entries are already valid tool names. Only keep the `visible_names` filter to exclude tools marked `enabled_for_llm=False`.
- Simplify the loop: iterate over `registry.llm_tool_definitions()` directly, keeping only entries whose `name` is in `visible_names`.
- Update the call site in `_stream_llm()` (`scripts/agent/llm_turn_runner.py:282`) to pass only `registry` (remove `ctx.cfg.tool.tool_definitions` argument).
- Keep the existing early-return path when `registry is None` (falls back to `ctx.cfg.tool.tool_definitions`).
- Add a regression test asserting that a tool present in `RuntimeToolRegistry` but absent from `ctx.cfg.tool.tool_definitions` is still offered to the LLM once this is fixed.

### Out-of-Scope
- Any change to `ctx.cfg.tool.tool_definitions` itself — the field stays as a compatibility/test-fixture value (same rationale as the sibling fail-closed requirement).
- Any change to `repl_health.py::_check_tool_definitions()` / `check_tool_definitions_runtime()` — startup drift validation must keep working unchanged.
- Any change to `config_reload.py`'s hot-reload of `cfg.tool.tool_definitions` — it only replaces the static field value; after this change nothing downstream reads that field for execution, so reloading remains harmless.
- Display/count-only call sites (`repl.py:117`, `commands/registry.py:99`, `commands/cmd_mcp.py:172`) — verified read-only `len(...)` uses.
- Any change to `RuntimeToolRegistry.llm_tool_definitions()` itself — its output shape is already correct for the LLM payload (`{"name", "description", "parameters"}`), no modification needed.
- Any `docs/*.md` edits (out of scope for this document-only planning phase).

## Assumptions

- `ctx.services_required.runtime_tools` (`RuntimeToolRegistry`) is populated before any LLM stream call in normal operation (confirmed: constructed by `McpToolDiscoveryService.discover_all()` at startup and wired via `factory.py`; the `None` check in the current code handles the rare case where it isn't).
- `RuntimeToolRegistry.llm_tool_definitions()` returns the correct LLM-facing shape derived from live discovery (`{"name", "description", "parameters"}` keys matching the LLM client contract) — confirmed by reading `scripts/shared/runtime_tool_registry.py:112-126`.
- Import-layer direction permits `scripts/agent/llm_turn_runner.py` to import from `scripts/shared/runtime_tool_registry.py` (same layer dependency pattern already exists today via `ctx.services_required.runtime_tools`).
- No database schema change and no new MCP server are involved; this is a pure in-process control-flow refactor within the existing agent REPL/turn-runner process.
- The 3 test scenarios listed in the requirement's "Tests" section are the acceptance bar for this change.

## Design decisions

- **Simplified passthrough**: Since `visible_names` contains exactly the names returned by `llm_tool_definitions()`, the check `td["name"] in visible_names` is always True for every entry in the iteration. The simplified version collapses to a direct return of `registry.llm_tool_definitions()`. However, the requirement's implementation instructions say "iterate over `registry.llm_tool_definitions()` directly, keeping only entries whose `name` is in `visible_names`." Keeping the filtering step makes the intent explicit and provides a safety net if the method is later extended to accept a custom base list.
- **Bug fix side effect**: The current `_filter_disabled_tool_definitions()` logic has an inverted condition (`name not in known_names or name in visible_names`). Switching to the registry as the base list implicitly fixes this bug — using the registry as the base list eliminates this class of error entirely.

## Alternatives considered

- **Keep `known_names` intersection**: Would require fixing the inverted condition (`name in known_names and name in visible_names`) separately. Not worth the complexity since the registry-as-base-list approach eliminates the need for `known_names` entirely.
- **Collapse to direct return**: The simplest possible implementation — just return `registry.llm_tool_definitions()` when registry is available. Rejected because the requirement explicitly says to keep the filtering step for clarity and future extensibility.
- **Add `types-GitPython` stub**: Out of scope — unrelated to this change.

**New method body:**
```python
def _filter_disabled_tool_definitions(self) -> list[dict[str, Any]]:
    """Return LLM-facing tool definitions from the registry, excluding disabled tools."""
    ctx = self._ctx
    registry = ctx.services_required.runtime_tools
    if registry is None:
        return ctx.cfg.tool.tool_definitions
    visible_names = {td["name"] for td in registry.llm_tool_definitions()}
    result: list[dict[str, Any]] = []
    for td in registry.llm_tool_definitions():
        if td["name"] in visible_names:
            result.append(td)
    return result
```

Note: The `visible_names` check is technically redundant (every entry from `llm_tool_definitions()` is already in `visible_names`), making the loop body trivially true for every iteration. However, keeping it makes the filtering intent explicit and provides a safety net if the method is later extended to accept a custom base list. Document this redundancy in a brief comment.

### Details

**Current state (lines 207-223):**
```python
def _filter_disabled_tool_definitions(
    self, tool_definitions: list[dict[str, Any]]
) -> list[dict[str, Any]]:
    """Exclude MCP tools marked as disabled_for_llm=False from the LLM payload."""
    ctx = self._ctx
    registry = ctx.services_required.runtime_tools
    if registry is None:
        return tool_definitions
    visible_names = {td["name"] for td in registry.llm_tool_definitions()}
    known_names = {tool.name for tool in registry.all_tools()}
    result: list[dict[str, Any]] = []
    for td in tool_definitions:
        fn = td.get("function") if isinstance(td, dict) else None
        name = fn.get("name") if isinstance(fn, dict) else None
        if name is None or name not in known_names or name in visible_names:
            result.append(td)
    return result
```

**Key changes:**
1. Remove `tool_definitions` parameter from signature
2. Replace `for td in tool_definitions:` with `for td in registry.llm_tool_definitions():`
3. Remove `known_names` computation
4. Simplify the inclusion condition: `if name is None or name not in known_names or name in visible_names` → `if td["name"] in visible_names`
5. Remove `fn`/`name` extraction since we now iterate over dicts directly from `llm_tool_definitions()` which already have `"name"` key
6. Update docstring to reflect new behavior
7. Update call site in `_stream_llm()` line 282
