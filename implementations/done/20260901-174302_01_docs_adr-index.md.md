### Details

**INV-011 (REQ-001):**
Current description: "Safety or integrity failures (auth, allowlist, safety-tier, secrets, Config Isolation, approval-control establishment, RuntimeToolRegistry init, duplicate tool ownership) are Fail-Fast at startup / Fail-Closed at execution, and are never converted into partial availability"

Replace with terminology consistent with revised ADR-004:
- Replace "Fail-Fast at startup / Fail-Closed at execution" with explicit Decision #14 / Decision #15 references.
- Remove "required/non-required branch" concept (ADR-004 Decision #1 eliminated environment-based branching).
- Updated description: "Safety or integrity failures (auth, allowlist, safety-tier, secrets, Config Isolation, approval-control establishment, RuntimeToolRegistry init, duplicate tool ownership) are Fail-Fast at startup (Decision #14) or Fail-Closed at execution (Decision #15), and are never converted into partial availability"
- Verification status: Confirmed in code structure — `scripts/agent/startup.py` routes these checks through unconditional FATAL paths; no environment-dependent branching found.

**INV-019 (REQ-002):**
Current status: "**Not verified** — no dedicated test exercises the `is_required` branch in `scripts/agent/services/mcp_tool_discovery.py`; see ADR-004 Known Deviations"

Code inspection result: Lines 134-145 of `mcp_tool_discovery.py` show the `is_required` logic uses `cfg.required_in_production` or `cfg.required_in_local` based on security profile. However, this classification depends on environment-specific fields (`required_in_production`/`required_in_local`), which contradicts ADR-004 Decision #1 (single common policy, no environment-based distinction). The Known Deviation in ADR-004 confirms this gap.

Updated status: **Needs confirmation** — code structure shows an `is_required` branch exists but it relies on environment-dependent fields (`required_in_production`/`required_in_local`) that conflict with the unified policy. Without a dedicated test exercising this path, verification cannot be confirmed.

**INV-020 (REQ-003):**
Current status: "**Not verified** — no dedicated test; only a generic warnings-do-not-abort mechanism test exists (`test_warnings_only_no_raise`), not a scenario test tied to component-criticality classification"

Code inspection result: Same `is_required` logic in `mcp_tool_discovery.py` lines 134-145 handles both required and non-required cases. The WARNING status assignment at line 145 corresponds to the non-required path. However, no dedicated test covers this classification.

Updated status: **Needs confirmation** — same reasoning as INV-019. The code path exists but lacks dedicated test coverage.

**INV-021 (REQ-004):**
Current description: "Undefined component criticality does not permit startup continuation"

ADR-004 Decision #12 states: "コンポーネントの必須性が未定義または判定不能な場合: 当該コンポーネントを非必須であると仮定しない。未定義の分類を起動継続の根拠として用いない。これを未解決の設計上または設定上の誤りとして扱う。該当する場合は、現行のKnown Issueを記録または参照する。"

The current invariant description conflates two concepts: (a) "undefined component criticality" and (b) "does not permit startup continuation." Decision #12 says: do NOT assume non-required for undefined criticality; treat it as an unresolved design/configuration error. It does NOT say "do not permit startup continuation" — it says "do not use undefined classification as grounds for startup continuation."

Updated description: "Component criticality that is undefined or undeterminable must not be assumed to be non-required; it must be treated as an unresolved design or configuration error (ADR-004 Decision #12)"
Verification status: Needs confirmation — current code has no distinct "undefined" classification state; `required_in_production`/`required_in_local` are booleans defaulting to `True`, so this invariant is not currently enforceable as a separate branch (as noted in ADR-004 Known Deviations).

**INV-022 (REQ-005):**
Current status: "Confirmed (existing ADR-004 Verification test: no fallback occurs outside ADR-010-defined conditions); no test yet for the general prohibition"

Re-verification: ADR-004 Group 10 (Fallback boundary) Decision #25-27 restricts Fallback to cases where another Accepted ADR explicitly defines it. ADR-010 is the sole exception. Code inspection of `http_augment.py` showed fallback on 4xx/parse errors (noted in INV-015 as potentially violated by CI-003), but this is a different concern from INV-022 which specifically addresses RAG fallback authority.

Updated status: **Needs confirmation** — while the ADR-004 Verification section notes no fallback outside ADR-010-defined conditions, there is no dedicated test for the general prohibition (INV-022 itself). The existing verification is structural/code-inspection based, not tested.
