# Implementation Procedure: Add SQL Constraints to chunks Table

## Goal

Add four database-level constraints to the `chunks` table in `_RAG_SCHEMA_TEMPLATE`:
- `UNIQUE (doc_id, chunk_index)` — semantic uniqueness per document
- `CHECK (chunk_index >= 0)` — reject negative indices
- `CHECK (chunk_type IN ('text', 'code'))` — restrict chunk type values
- `CHECK (length(content) > 0)` — reject empty content strings

## Scope

- **In scope**: Modify `_RAG_SCHEMA_TEMPLATE` in `scripts/db/schema_sql.py` only.
- **Out of scope**: Database migration of existing data, test updates, config changes.

## Assumptions

- Schema DDL is applied via `create_schema.py` which recreates the database from scratch.
- **Verified assumption**: Existing databases are not migrated; new databases will use the updated schema. Confirm with stakeholder before applying to production environments.
- The `chunk_id` primary key does not imply `(doc_id, chunk_index)` uniqueness — two chunks in the same document cannot share an index.

## Design decisions

- All constraints are added inline in the `CREATE TABLE` statement rather than as separate `ALTER TABLE` statements. This keeps the template self-contained and avoids migration complexity.
- SQLite's `length()` function returns the number of characters, not bytes — appropriate for TEXT columns.

## Alternatives considered

- Separate `ALTER TABLE ADD CONSTRAINT` statements: rejected because they require migration of existing data and complicate rollback.
- Application-layer validation only: rejected because database-level constraints provide defense-in-depth against malformed data regardless of application failures.

### Method

### Details

Current `chunks` table definition (lines 37–46):

```sql
    CREATE TABLE IF NOT EXISTS chunks (
        chunk_id           INTEGER PRIMARY KEY AUTOINCREMENT,
        doc_id             INTEGER NOT NULL
                           REFERENCES documents(doc_id) ON DELETE CASCADE,
        chunk_index        INTEGER NOT NULL,
        content            TEXT    NOT NULL,
        normalized_content TEXT,
        chunk_type         TEXT    NOT NULL DEFAULT 'text',
        source_file        TEXT    NOT NULL DEFAULT ''
    );
```

Modified `chunks` table definition:

```sql
    CREATE TABLE IF NOT EXISTS chunks (
        chunk_id           INTEGER PRIMARY KEY AUTOINCREMENT,
        doc_id             INTEGER NOT NULL
                           REFERENCES documents(doc_id) ON DELETE CASCADE,
        chunk_index        INTEGER NOT NULL,
        content            TEXT    NOT NULL,
        normalized_content TEXT,
        chunk_type         TEXT    NOT NULL DEFAULT 'text',
        source_file        TEXT    NOT NULL DEFAULT '',
        UNIQUE (doc_id, chunk_index),
        CHECK (chunk_index >= 0),
        CHECK (chunk_type IN ('text', 'code')),
        CHECK (length(content) > 0)
    );
```

Key points:
- `UNIQUE (doc_id, chunk_index)` is a table-level constraint (not a column constraint) since it spans two columns.
- `CHECK (chunk_type IN ('text', 'code'))` replaces the implicit assumption that `chunk_type` defaults to `'text'` — now only valid values are accepted.
- `CHECK (length(content) > 0)` catches empty strings that `NOT NULL` alone would allow.
- Trailing comma before the first table-level constraint (`source_file` line) is required by SQL syntax.

## Compatibility considerations

- New databases: all constraints apply immediately upon creation via `create_schema.py`.
- Existing databases: not affected (schema recreation required anyway per plan scope).
- Ingestion pipeline: must ensure `chunk_index >= 0`, `chunk_type` in `('text', 'code')`, and `content` is non-empty before insertion. These are already enforced by the ingestion layer.

## Security considerations

N/A — constraints do not introduce security surface area. They reduce attack surface by rejecting malformed input at the database level.

## Rollback considerations

- To roll back, revert the `_RAG_SCHEMA_TEMPLATE` string to its original form.
- If new databases were created with the constraints, they must be dropped and recreated without them.
- No data loss risk: constraints only affect new rows; existing data is unaffected.
