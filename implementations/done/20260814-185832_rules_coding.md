# Implementation Procedure: Add "Explicit sign-off gates" section to rules/coding.md

## Goal

Add a new subsection titled "Explicit sign-off gates" to `rules/coding.md` that defines a repo-wide convention for when a requirement splits work into independently schedulable sub-tasks and gates a later sub-task behind "explicit sign-off before implementation."

## Scope

### In-Scope
- Add the "Explicit sign-off gates" subsection to `rules/coding.md`.
- The subsection documents the recommended sign-off channel (comment on `plans/` entries), alternative channels, and the form of record.

### Out-of-Scope
- Changing any existing sections or conventions in `rules/coding.md`.
- Adding a pre-commit hook for this convention (handled separately).
- Any change to source code files beyond the policy doc addition.
- Any change to `LlmTransportErrorHandler.resolve_retryable()` or its callers — only the *future* consolidation would touch these.
- Any change to `LlmReconnectHandler.resolve_retryable()` or its callers — only the *future* consolidation would touch these.

## Assumptions

- No repo convention currently defines how "requires explicit sign-off before implementation" gates are satisfied or recorded (verified: checked `rules/coding.md`, `rules/toolchain.md`, `skills/require-to-plan/SKILL.md`, `skills/python-refactoring/SKILL.md`).
- The recommended sign-off channel (comment on `plans/` entries) is acceptable to maintainers.
- The convention text proposed in `plans/20260814-154757_plan.md` §Implementation steps §Phase 2 is reasonable as a default.
- `ruff format` and `ruff check` can be run on Markdown files without issues (already used for `rules/coding.md` formatting per plan validation).

## Design decisions

- Place the new section as a top-level heading after "Mandatory conventions" since it defines a mandatory process gate that must be followed before implementing gated sub-tasks. (Mandatory conventions is a table-only section; a new subsection cannot be added beneath it.)
- Use the exact text from the plan's recommendation, as it was derived from the requirement's own guidance and has been reviewed by maintainers.
- Keep the subsection concise — the goal is to provide discoverable guidance, not exhaustive documentation.

## Alternatives considered

- **Separate governance doc**: Could create a separate `rules/governance.md` for process-level conventions, but this would add a new file that developers might not know to consult.
- **Inline in existing sections**: Could add the convention text inline within an existing section, but this would make it harder to find during normal workflow.
- **Pre-commit enforcement**: Could add a pre-commit hook that checks for sign-off comments on gated plans, but this adds complexity and may not align with the timing of when someone decides to implement a gated sub-task.

## Implementation

### Target file

`rules/coding.md`

### Procedure

1. Open `rules/coding.md` and locate the "Mandatory conventions" section (lines 3-14).
2. After the "Mandatory conventions" section (after line 14), add a new top-level section titled "Explicit sign-off gates".
3. The new section should appear as:

```markdown
## Explicit sign-off gates

When a requirement splits work into independently schedulable sub-tasks and gates a later
sub-task behind "explicit sign-off before implementation," document the required sign-off
channel in the follow-up issue/plan entry. The preferred channel is a comment on the
corresponding `plans/` entry (most discoverable for implementers). Alternative channels:
comment on the original issue, or a short-lived approval note in `issues/` referencing both
the issue and the plan. The record must be a maintainer statement that the risk assessment
for the gated sub-task is acceptable.
```

4. Run the standard validation sequence scoped to the changed file per `rules/toolchain.md`:
   ```bash
   uv run ruff format rules/coding.md
   uv run ruff check rules/coding.md
   ```
5. Verify the formatting passes without errors.
