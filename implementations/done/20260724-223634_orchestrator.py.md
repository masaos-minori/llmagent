## Goal

Surface first-turn background task exceptions to the user immediately, regardless of whether subsequent tasks also fail.

## Scope

**In**: `scripts/agent/orchestrator.py` (Orchestrator._discard_and_log())
**Out**: Changes to LLMTurnRunner, other background task handling paths

## Assumptions

1. `_on_first_turn` runs as an asyncio background task and may raise during initialization
2. `_on_error` callback exists in Orchestrator and can be used to notify the user
3. First-turn failures have high impact on session behavior and should be surfaced immediately

## Design decisions

- Call `self._on_error(exc)` only when `self._consecutive_bg_failures == 1` and the exception is NOT `asyncio.CancelledError` — ensures first-turn failure is surfaced exactly once
- Wrap `_on_error` call in try/except to prevent notification masking the original exception
- No additional degraded-state flag needed — `_on_error` itself signals the issue to the user

## Alternatives considered

- Set a separate `is_degraded` flag on `ctx.conv`: adds state complexity; `_on_error` already surfaces the issue visually
- Always call `_on_error` regardless of failure count: would produce duplicate notifications on consecutive failures
- Suppress `_on_error` for specific exception types beyond CancelledError: too prescriptive; caller should decide what constitutes a user-facing error

## Implementation

### Target file

`scripts/agent/orchestrator.py`

### Procedure

1. In `Orchestrator._discard_and_log()`, when `self._consecutive_bg_failures == 1` and the exception is NOT `asyncio.CancelledError`, add a call to `self._on_error(exc)` to surface the error to the user.
2. Ensure the notification is idempotent — only emit once per unique first-turn failure. The existing counter already prevents re-notification on consecutive failures from the same source.
3. Optionally set `ctx.conv.is_processing = False` or similar flag to indicate the session is in a degraded state after first-turn failure.
4. Verify no duplicate notifications occur if the same task fails multiple times.

Key points:
- `_on_error` called only on first non-CancelledError failure (`_consecutive_bg_failures == 1`)
- `_on_error` call wrapped in try/except to prevent notification failure from masking the original exception
- No change to logging behavior — warning/error logs remain as-is

## Compatibility considerations

- No API changes — internal callback invocation only
- Existing callers of `_discard_and_log` unaffected (it's only called by asyncio task done callbacks)
- `_on_error` signature unchanged — caller decides how to display the error

## Security considerations

- No security impact — error notification only
- `_on_error` exception caught and logged — prevents denial-of-service via broken notification handler

## Rollback considerations

- If `_on_error` causes issues for specific callers, revert by removing the notification block
- No data loss risk — only visual/user-facing change
