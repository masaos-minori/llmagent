## Goal

Add `rag_pipeline_service_url: str` parameter to `RagIngester.__init__()`, cache it as `self._rag_pipeline_service_url`, and update `ingest_all()` to use cached URL for cache invalidation instead of reloading config.

## Scope

### Out-of-Scope

## Assumptions

1. Current `RagIngester.__init__()` accepts `rag_pipeline_service_url` as a parameter (confirmed by inspecting current code)
2. `ingest_all()` currently reloads config to get the service URL for cache invalidation (confirmed by inspecting current code)
3. Cache invalidation timing changes — previously happened after all URL groups regardless of success (confirmed by inspecting current code)

## Design decisions

- `rag_pipeline_service_url` is passed to constructor — avoids repeated config reloads during ingestion
- Cached URL used for cache invalidation — eliminates race condition where config might change between URL processing and cache invalidation
- Cache invalidation happens only when at least one URL group commits successfully (new behavior)

## Alternatives considered

- Passing URL via method parameters: rejected because it adds unnecessary complexity to every method call
- Using a shared config object: rejected because it doesn't solve the race condition problem — config could still change between reads
- Invalidating cache after ALL URL groups regardless of success: rejected because it wastes resources on failed ingestions

### Details

**File location**: `scripts/rag/ingestion/ingester.py`

**Key changes**:
1. Verify `rag_pipeline_service_url` is stored in constructor
2. Replace config reload in `ingest_all()` with cached URL
3. Add conditional cache invalidation — only invalidate if at least one URL group succeeded

**Critical insight**: By caching the URL in the constructor, we eliminate the race condition where config might change between URL processing and cache invalidation. This is especially important for distributed systems where config updates can propagate asynchronously.

**Thread safety**: Since workers no longer hold DB connections, there's no risk of connection conflicts. The main thread handles all DB writes sequentially.

**Memory consideration**: `PreparedChunk.embedding_blob` stores raw bytes — memory pressure for large documents is acceptable since URLs are processed sequentially; memory is freed after commit.
