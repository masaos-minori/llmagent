## Goal

Replace numeric ingestion sentinels (`n_failed = -1`) with explicit URL statuses using `IngestionFailureReason.UNEXPECTED_FAILURE` to improve code clarity, maintainable aggregations, and type safety.

## Scope

**In-Scope:**
- Add `UNEXPECTED_FAILURE` to `IngestionFailureReason` enum.
- Ensure all `n_failed` and `n_success` values are non-negative.
- Replace `n_failed = -1` sentinel usage with appropriate `status` assignment and `n_failed = 0`.
- Update `ingest_all()` aggregation logic to use the new status and non-negative counts.
- Update logging to include the explicit status.
- Update tests to reflect the changes.

**Out-of-Scope:**
- Modifying source code behavior beyond diagnostic improvements.
- Updating documentation (`docs/*.md`).
- Changing the core ingestion or pipeline orchestration logic.

## Assumptions

- The existing `failure_reason` field in `IngestUrlResult` is sufficient for encoding status information.
- Callers of `ingest_all()` will handle the new `UNEXPECTED_FAILURE` status appropriately.
- Negative integers are not a valid representation of discrete error states.

## Design decisions

- **Add `UNEXPECTED_FAILURE` to enum**: Replaces the `-1` sentinel with an explicit, typed indicator.
- **Set `n_failed = 0` alongside the new status**: Prevents confusion between "zero failures" and "unknown failures".
- **Update `_process_url_groups()` exception handler**: Only catches `(OSError, RuntimeError, ValueError, sqlite3.OperationalError)` — these are the specific exceptions handled in the current code.

## Alternatives considered

- **Keep `-1` sentinel but add docstring warning**: Adds cognitive overhead without solving the root problem. Rejected.
- **Use `None` for `n_failed` when unknown**: Breaks downstream consumers expecting integer types. Rejected.
- **Add separate `is_unexpected_failure` boolean flag**: Redundant with `failure_reason`; adds unnecessary complexity. Rejected.
