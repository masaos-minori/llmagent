## Goal

Add the schema-2.0 per-tool metadata contract — `is_write=False`,
`requires_serial=False`, `resource_scope_kind="filesystem"`,
`resource_scope_keys=["path"]` — to all 9 tool entries in
`scripts/mcp_servers/file/read_tools.py`'s `TOOL_LIST`, so the file-read-mcp server's
tools carry explicit, machine-checkable scheduling metadata instead of relying on the
name-keyed/static classification sources this plan retires.

## Scope

In scope: the 9 dict literals inside `TOOL_LIST` (lines 48-112) — `list_directory`,
`list_directory_with_sizes`, `directory_tree`, `read_text_file`, `read_media_file`,
`read_multiple_files`, `search_files`, `grep_files`, `get_file_info`. Out of scope:
`_input_schema()` (lines ~1-45, the Pydantic-to-JSON-Schema helper) and the Pydantic
request models it wraps (`ListDirectoryRequest`, etc., defined elsewhere in this
module or imported) — none of the 4 new fields need to appear inside `inputSchema`
itself, only as sibling keys on each tool dict alongside `status`/`config_dependent`.

## Assumptions

- All 9 entries currently have `"status": "production"` and `"config_dependent": False`
  as their only trailing metadata keys (confirmed by reading lines 48-112) — none of
  the 4 new schema-2.0 fields exist on any entry today, so this is a pure addition, not
  a migration of pre-existing partial fields.
- Every read tool operates on a single filesystem path argument named `path` in its
  Pydantic request model / resulting `inputSchema["properties"]` (per the plan's
  Affected-areas row: `resource_scope_keys=["path"]` for all 9). This assumption is
  grounded in the tool names/descriptions read (e.g. `read_text_file` "Read file
  contents...", `list_directory` "Return immediate entries of the specified
  directory") all being single-path operations; `read_multiple_files` accepts multiple
  paths internally but the plan's per-server table specifies a uniform
  `["path"]` for this module, which this document follows literally without second-
  guessing the plan.
- A future shared validator (`scripts/shared/resource_scope.py`, not yet created —
  confirmed absent by `ls`) will check that each name in `resource_scope_keys` exists
  in the tool's own `inputSchema["properties"]`; this document does not itself verify
  that `read_multiple_files`'s actual Pydantic model exposes a property literally named
  `path` (vs. e.g. `paths`) — flagged here so the implementer double-checks
  `ReadMultipleFilesRequest`'s field name before committing `["path"]` verbatim for
  that one entry, and adjusts to the model's actual field name if it differs.

## Design decisions

- All 9 entries get identical `is_write=False`/`requires_serial=False` — this module
  is exclusively read operations (no entry description implies mutation), matching the
  plan's per-server table exactly.
- Field ordering within each dict: insert the 4 new keys after `config_dependent` (the
  current last key) to minimize diff noise against the existing `name`/`description`/
  `inputSchema`/`status`/`config_dependent` block.

## Alternatives considered

N/A — the plan specifies this module's fields precisely (uniform read-only,
`resource_scope_kind="filesystem"`, `resource_scope_keys=["path"]`); no alternative
scoping was considered.

## Implementation

### Target file: `scripts/mcp_servers/file/read_tools.py`

### Procedure

1. For each of the 9 dicts in `TOOL_LIST` (lines 48-112), add 4 keys after
   `"config_dependent": False,`:
   `"is_write": False,`, `"requires_serial": False,`,
   `"resource_scope_kind": "filesystem",`, `"resource_scope_keys": ["path"],`.
2. Re-run `_input_schema()` mentally (no code change needed there) to confirm each
   Pydantic model backing these 9 entries does expose a `path`-named property in its
   `inputSchema["properties"]` — spot-check `ReadMultipleFilesRequest` specifically per
   the Assumptions note above, since "multiple files" suggests a plural field; adjust
   `resource_scope_keys` for that one entry only if its actual property is not named
   `path`.
3. Leave `_input_schema()`, imports, and all Pydantic model definitions untouched.

### Method

Direct literal-dict edits, one `Edit` per entry (or one `replace_all`-safe multi-hunk
edit) inserting the same 4-line block after each entry's `"config_dependent": False,`
line. No new imports, no new helper function — the values are static literals.

### Details

- `TOOL_LIST` starts at line 48 (`TOOL_LIST: list[dict[str, Any]] = [`) and ends at
  line 112 (closing `]`), with entries at:
  `list_directory` (50-55), `list_directory_with_sizes` (56-62),
  `directory_tree` (63-69), `read_text_file` (70-76), `read_media_file` (77-83),
  `read_multiple_files` (84-90), `search_files` (91-97), `grep_files` (98-104),

## Compatibility considerations

Additive-only change to dict literals returned by `TOOL_LIST`; any code currently
iterating tool dicts with `for k, v in tool.items()` or similar sees 4 extra keys but
no removed/renamed key. `build_tools_response()` in `server.py` (`{**t, "server_key":
server_key}`) passes the extra keys through unchanged. The pre-existing
`tests/mcp_servers/test_tool_schema.py::test_static_schema_required_fields` and
`test_config_dependent_field_present_and_requires_config_absent` (which parametrize
over this exact module) only assert presence/type of `name`/`description`/
`inputSchema`/`status`/`config_dependent` and absence of `requires_config` — none of
these assertions are broken by adding 4 new keys.

## Security considerations

None — these are read-only tools (`is_write=False` documents existing behavior; no
behavior changes). Declaring `resource_scope_kind="filesystem"` with
`resource_scope_keys=["path"]` is metadata only in this file; the actual scope-string
resolution and any path-traversal protection remain the responsibility of
`scripts/shared/resource_scope.py` (not this file) and the existing runtime path
validation inside the tool implementations (not part of `TOOL_LIST`).

## Rollback considerations

Trivial: revert the 9 additive 4-line blocks. No other already-changed file in this
plan reads these fields yet from this specific module until
`mcp_tool_discovery.py`'s validator (a different target file) starts requiring them —
until that lands, an incomplete rollback here only means the fields are simply absent
again, matching today's state, with no partial-migration hazard.
