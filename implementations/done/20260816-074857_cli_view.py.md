# Implementation Procedure: Mitigate CLIView Writer Protocol partial test double risk

## Goal

Prevent AttributeError at runtime when test doubles implement only a subset of Writer Protocol methods, by making the protocol compatible with partial implementations.

## Scope

- `scripts/agent/cli_view.py`: Writer Protocol definition and CLIView implementation
- Any existing test doubles that use Writer Protocol
- Protocol usage sites that call Writer methods

## Assumptions

1. Test doubles are created by developers who may only care about the methods they need to mock
2. `@runtime_checkable` enforcement is currently relied upon as a safety check
3. Default implementations should be no-op (do nothing) rather than raise errors
4. The Reader Protocol does not have the same risk (only 1 method)

## Design decisions

- Create an abstract base class `WriterBase` with no-op implementations of all 10 Writer methods
- Make `Writer` Protocol inherit from `WriterBase` (Protocol + ABC pattern)
- Make `CLIView` inherit from `WriterBase` instead of implementing methods independently
- Use `abc.ABCMeta` metaclass to prevent direct instantiation of `WriterBase`
- Partial test doubles automatically satisfy the protocol via inheritance
- `isinstance(obj, Writer)` works correctly for partial implementations
- No silent failures — calling an unimplemented method still raises AttributeError with a clear message

## Alternatives considered

1. **Approach B: Use `typing.Protocol` with `__getattr__` fallback** — Would add a `__getattr__` to the Protocol that raises a descriptive error only when an unimplemented method is actually called. Keeps the Protocol pure but provides better diagnostics. Rejected because it requires modifying every Protocol usage site.

2. **Add `typing.Optional` to method signatures** — Would mark optional methods but doesn't solve the `isinstance` check problem. Rejected because it changes the contract in a way that's harder to reason about.

3. **Use `abc.ABC` with default implementations directly on the Protocol** — Python allows this since 3.8. This is what we're choosing.

## Compatibility considerations

- Adding a base class changes the MRO (method resolution order). If multiple inheritance is used elsewhere, this could cause subtle issues.
- If `@runtime_checkable` is relied upon for strict checking, Approach A weakens that guarantee. However, the trade-off is worth preventing silent AttributeErrors.
- Existing test doubles that do NOT inherit from `WriterBase` will still fail `isinstance` checks, but they will also get better error messages when calling unimplemented methods.
- If the Protocol is used outside of tests (e.g., for structural typing in production), the no-op defaults could mask bugs.

## Security considerations

N/A — no security implications. Only changes error message formatting.

## Rollback considerations

- Remove `WriterBase` class and revert `Writer` Protocol to original definition
- Revert `CLIView` to not inherit from `WriterBase`
- No database or config changes to revert

## Validation plan

- **Unit test**: Create a partial Writer test double inheriting from `WriterBase` with only `write_token` overridden, verify `isinstance(partial, Writer)` returns True
- **Unit test**: Verify that calling an unimplemented method on a partial double raises AttributeError with a clear message
- **Unit test**: Verify `CLIView` instance satisfies `isinstance(view, Writer)`
- **Integration test**: Verify normal operation with full CLIView writer still works
- **Manual**: Check that no existing tests break after the change

## Out of scope

- Changes to Reader Protocol (only 1 method, low risk)
- Changes to CLIView's internal logic beyond adding inheritance
- Changes to how Writer Protocol is consumed outside of `cli_view.py`
- Integration tests for lifecycle transitions (only unit tests for Writer Protocol)
