## Goal

Make approval resolution atomic by preventing double-resolution of the same approval through conditional updates and transaction isolation. Ensure that concurrent `/approve` or `/reject` commands cannot resolve the same approval twice, which would cause inconsistent workflow state.

## Scope

- Modify `resolve_approval()` to use conditional update (`WHERE status='pending'`) instead of unconditional update
- Check affected row count after update; return specific error if zero rows affected (already resolved)
- Wrap check-and-resolve flow in single database transaction where possible
- Return distinct error messages for "not found" vs "already resolved" states
- Update `_cmd_approve()` and `_cmd_reject()` to handle new error cases

## Assumptions

- SQLite WAL mode provides sufficient transaction isolation for this fix
- The `rowcount` attribute on cursor objects accurately reflects affected rows after UPDATE
- Concurrent access will be limited to multiple REPL sessions or API clients, not within a single process
- Existing callers of `resolve_approval()` can handle the new RuntimeError with specific error message

## Design decisions

- **Conditional update over SELECT-then-UPDATE**: Use `WHERE status='pending'` clause directly in UPDATE statement rather than checking status first. This eliminates race window between read and write.
- **Rowcount-based detection**: Check cursor.rowcount after UPDATE to determine if approval was actually updated. Zero rows means it was already resolved.
- **Separate error types**: Distinguish "not found" (approval doesn't exist) from "already resolved" (approval exists but not pending). These require different UI responses.
- **Statement-level atomicity**: Rely on SQLite's statement-level atomicity for the conditional UPDATE. This avoids complexity of managing transactions across separate connections.

## Alternatives considered

- **Optimistic locking with version column**: Would add version column to approvals table and check version in WHERE clause. More robust but requires schema change (out of scope).
- **SELECT-then-UPDATE pattern**: Check approval status with SELECT before UPDATE. Creates race condition window between the two statements. Rejected due to TOCTOU vulnerability.
- **Database-level advisory locks**: Use SQLite advisory lock functions. Complex and not portable. Conditional UPDATE achieves same goal more simply.
- **Application-level locking**: Implement Redis-style lock in memory. Requires external dependency and doesn't work across processes.

   ```python
   def resolve_approval(approval_id: str, status: str, reason: Optional[str] = None) -> ApprovalResult:
       # ... existing setup ...
       
       # Conditional update instead of unconditional
       sql = """
           UPDATE approvals 
           SET status = ?, reason = ?, resolved_at = ?
           WHERE approval_id = ? AND status = 'pending'
       """
       cursor.execute(sql, (status, reason, datetime.now().isoformat(), approval_id))
       
       # Check rowcount
       if cursor.rowcount == 0:
           # Check if approval exists but is not pending
           cursor.execute("SELECT status FROM approvals WHERE approval_id = ?", (approval_id,))
           row = cursor.fetchone()
           if row is None:
               raise RuntimeError(f"Approval {approval_id} not found")
           else:
               raise RuntimeError(f"Approval {approval_id} already resolved")
       
       db.commit()
       return ApprovalResult(success=True, approval_id=approval_id)
   ```

4. Create `ApprovalResult` dataclass if not exists:

5. Update `_cmd_approve()` in `cmd_workflow.py`:
   ```python
   async def _cmd_approve(...):
       try:
           result = await resolve_approval(...)

       except RuntimeError as e:
           if "already resolved" in str(e):
               return f"This approval has already been resolved."
           elif "not found" in str(e):
               return f"Approval {approval_id} not found."
   ```

## Compatibility considerations

- **Breaking change**: Code that relied on idempotent approval resolution will now receive errors. Need to document this change.
- **Error message format**: New RuntimeError messages must be parsed by callers. Consider using custom exception class for better type safety.
- **SQLite version compatibility**: cursor.rowcount behavior should be consistent across SQLite versions, but verify during testing.

## Security considerations

- **Race condition prevention**: Primary security goal is preventing double-resolution attacks
- **Information disclosure**: Error messages should not expose internal state details beyond what's necessary
- **Privilege escalation**: Ensure only authorized users can approve/reject workflows

## Rollback considerations

- **Quick rollback**: Revert to unconditional UPDATE by removing `AND status='pending'` clause
- **Data impact**: No database changes; rollback does not affect persisted state
- **Migration**: No migration needed since schema unchanged
