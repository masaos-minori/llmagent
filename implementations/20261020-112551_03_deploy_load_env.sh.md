## Goal
Create `deploy/load_env.sh` as a sourcing-only shell library that holds the `.env` parsing and required-variable
gate semantics already proven in `deploy/start_agent.sh`, so `deploy/setup_services.sh` (seq 04) can gate on the
Event Bus configuration without a second copy of the logic and without `/opt/llm` hardcoding.

## Scope
- New file `deploy/load_env.sh` (new) with three functions: `parse_env_file` (new), `collect_required_env_vars` (new),
  `require_env_vars` (new).
- No change to `deploy/start_agent.sh` (it keeps its inline copy; Plan Out-of-Scope).
- No `set -euo pipefail` in the library: the library is sourced, and options are the sourcing script's
  responsibility.

## Assumptions
- `deploy/start_agent.sh` lines 36-69, 72-80 and 112-135 are the semantics to reproduce; they are already
  exercised in production and are lifted with only the two documented changes below.
- The caller defines `REPO_ROOT` and, when an `.env` file exists, `ENV_FILE`, before calling `require_env_vars` (new);
  the library reads both through `${VAR:-}` so it stays safe under a caller running `set -u`.
- `deploy/setup_services.sh` line 12 already sets `set -euo pipefail`, so the library's `[[ ... ]] && continue`
  patterns must stay inside a loop or a tested context (the same shape `deploy/start_agent.sh` uses).
- Names written with the (new) marker are the functions this procedure creates in the new file; two of them keep
  the exact names and bodies they have in `deploy/start_agent.sh`, which the tool's scoped-path rule cannot read
  because it only resolves `.py` and `.md` citations.

## Design decisions
- Sourced library, not an executable: the gate must be able to export variables into the caller's shell, which a
  subprocess cannot do.
- `parse_env_file` (new) keeps the permission warning inside the function (it is a property of the file being parsed,
  and every caller should get it) instead of inline in each caller as `deploy/start_agent.sh` lines 90-94 do.
- `require_env_vars "<label>" "<re-run command>" <config files...>`: the label and the re-run command are
  parameters because the agent gate says "MCP auth" and re-runs `start_agent.sh`, while the Event Bus gate says
  "Event Bus" and re-runs `setup_services.sh`. Reproducing the messages exactly is what `AC-2` checks.
- `collect_required_env_vars` (new) is shared as written: its `{ grep ... || true; }` guard is what keeps a no-match
  from aborting a function under `set -e`/`pipefail`.
- No `/opt/llm` default path anywhere in the library: paths come from arguments or caller variables, which is
  what lets `tests/deploy/test_load_env_gate.py` (seq 06) run the gate against `tmp_path` fixtures.

## Alternatives considered
- Put the gate in a Python helper: rejected because the gate must abort the shell script before the service is
  launched, and a Python call cannot export variables into the caller's environment.
- Change `deploy/start_agent.sh` to source this library in the same commit: rejected by the Plan (Out-of-Scope)
  to avoid changing the agent startup path in this task; `UNK-02` records the consolidation follow-up.
- Inline the gate again in `setup_services.sh`: rejected — it duplicates the parser and is the drift risk the
  Plan lists under Risks.

### Details
Header and function shape (the lifted bodies are copied from the cited line ranges, not retyped):

```bash
#!/bin/bash
# load_env.sh
# .env パースと必須環境変数ゲートを共有する sourcing 専用ライブラリ。
# 単体では実行しない（set -euo pipefail は sourcing 側で設定する）。
#
# 使用例:
#   source "${REPO_ROOT}/deploy/load_env.sh"
#   parse_env_file "${ENV_FILE}"
#   require_env_vars "Event Bus" "bash deploy/setup_services.sh" "${CONFIG_FILES[@]}"
```

`require_env_vars` (new) body (new):

```bash
require_env_vars() {
    local label="$1"
    local rerun_command="$2"
    shift 2
    local -a config_files=("$@")
    local -a missing=()
    local var

    while IFS= read -r var; do
        [[ -z "${var}" ]] && continue
        if [[ -z "${!var+x}" || -z "${!var}" ]]; then
            missing+=("${var}")
        fi
    done < <(collect_required_env_vars "${config_files[@]}")

    if (( ${#missing[@]} > 0 )); then
        local env_file_hint="${ENV_FILE:-}"
        local repo_root_hint="${REPO_ROOT:-}"
        echo "" >&2
        echo "[FATAL] ${#missing[@]} required ${label} environment variable(s) not set or empty:" >&2
        printf '  - %s\n' "${missing[@]}" >&2
        echo "" >&2
        if [[ -n "${env_file_hint}" ]]; then
            echo "Set them in ${env_file_hint} (or your shell), e.g.:" >&2
        elif [[ -n "${repo_root_hint}" ]]; then
            echo "Create ${repo_root_hint}/.env with these variables, e.g.:" >&2
        else
            echo "Set them in your environment or a .env file, e.g.:" >&2
        fi
        for var in "${missing[@]}"; do
            printf '  %s="$(openssl rand -hex 32)"\n' "${var}" >&2
        done
        echo "Then re-run: ${rerun_command}" >&2
        exit 1
    fi
}
```

## Compatibility considerations
- `deploy/start_agent.sh` is untouched, so the agent startup path and its messages are unchanged this cycle.
- The gate semantics are the same unset-or-empty test (`[[ -z "${!var+x}" || -z "${!var}" ]]`) the agent gate
  uses, so an operator who already runs the agent gate sees identical behavior for the Event Bus.
- `tests/deploy/test_load_env_gate.py` (seq 06) is the only test that executes this file; no production caller
  exists until seq 04 lands.

## Security considerations
- Parsing stays parse-only: no `eval`, no `source` of the `.env` file, no command substitution, and unsafe lines
  are skipped with a warning instead of being executed.
- Already-exported variables are never overridden, so an operator can keep a secret out of the file.
- The permission warning travels with the parser, so a `.env` with mode other than 600 or 400 is reported on
  every code path.
- Missing variables are reported by name only; no value is ever printed.

## Rollback considerations
Single-target removal: `git rm deploy/load_env.sh` (or revert the commit that adds it). seq 04 must be reverted
together with it if the library is removed, because `setup_services.sh` sources it.
