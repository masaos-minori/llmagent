## Goal

Declare the four shutdown keys in the shipped configuration file with their defaults, so the production validator sees them in the file it validates and operators can change the deadline without editing code (REQ-002: one configurable global deadline; REQ-011: configurable second-signal behavior; AC-1).

- Out of scope: the dataclass fields (row 17), the builder (row 18), and documenting the keys (row 48).

## Assumptions

- The flat scalar keys live in the block at `config/agent.toml:28-35`, where `pending_timeout_minutes` (`config/agent.toml:31`) and `approval_grant_ttl_seconds` (`config/agent.toml:35`) already sit with a short explanatory comment each.
- The file is copied to the production path by `deploy/deploy.sh:152`, so a key added here reaches production without a separate deploy change.
- The production validator derives its accepted key set from `AgentConfig` (row 17), so declaring a key the dataclass does not know would be an error, and this row lands after row 17.

## Design decisions

- Declare all four keys explicitly with the same values as the dataclass defaults, rather than omitting them: an operator-visible default is what makes the deadline configurable in practice, and the validator reads this file in the integration test.
- Keep each comment to two lines, in the style of the neighboring keys, so the 5-consecutive-comment-line rule enforced by `tools/check_config_comment_length.py` stays satisfied.
- Compatibility impact: none for existing keys; the file gains four entries.

## Alternatives considered

- declare only the deadline and leave the other three implicit — rejected: the settle window and the confirm window are the numbers an operator must reason about together when the total deadline changes.
