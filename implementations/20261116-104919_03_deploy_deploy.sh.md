## Goal

Verify that `deploy/deploy.sh` already satisfies `REQ-004` — it rejects a bin directory where
one of the ten `mcp_<server>` names (or the agent) is missing or mismatched before deploy
proceeds — and make only the minimal, necessary change. The current script already lists all
eleven names in `BINARY_NAMES`, rejects a missing name in a pre-check loop before any copy
step, and routes the remote-build swap through `tools/manage_binaries.py` checksum verification
plus a freshness `check`; this row confirms that coverage rather than adding speculative logic.

## Assumptions

- `deploy/deploy.sh` is run from the repository root (`REPO_ROOT` is derived from the script
  location, `deploy/deploy.sh:15`), so every `${REPO_ROOT}/...` reference resolves.
- The eleven names in `BINARY_NAMES` already match the output names of
  `deploy/build_binaries.sh` `ENTRIES` (agent + ten MCP servers), so no list update is needed.
- A "mismatched" name means the installed file's checksum differs from its recorded build info;
  that is caught by `manage_binaries.py` swap/check, not by the existence pre-check.

## Design decisions

- **Confirm existing coverage; do not expand it.** The Plan anticipated "update the binary list
  and verification" (`plans/20261115-193516_buildperf001_mcp-multidist-binary.md`), but the
  current code already carries that update. The change here is therefore a verification/locking
  step, not a new feature. Adding checks beyond what exists would widen the blast radius of a
  deploy script with no corresponding requirement.

## Alternatives considered

- **Adding a checksum pass to the existence pre-check (lines 94-100).** Rejected as unnecessary
  for the local-build path: when `BUILD_OUTPUT_DIR` equals `DEPLOY_BIN` the swap is skipped and
  the binaries are freshly built in place, so a checksum mismatch cannot occur there. The
  mismatch case applies to remote builds, where the swap already verifies checksums.
- **Promoting the freshness `check` to an early, always-fail gate.** Rejected: the strictness
  gate (`DEPLOY_STRICT_BINARIES`) and the end-of-script `FRESHNESS_RC` evaluation are the
  existing, intentional contract; moving them changes deploy ordering and warning semantics
  outside `REQ-004`.

### Method

### Details

- The pre-check iterates `"${BINARY_NAMES[@]}"` against `${BUILD_OUTPUT_DIR}/${b}`, so it validates
  whatever directory the build wrote to, local or remote.
- For local builds (`BUILD_OUTPUT_DIR` == `DEPLOY_BIN`), the swap is skipped (line 104), which is
  correct: the binaries were just built into the destination, so there is nothing to verify or
  move. Freshness still runs via the `check` call.
- The freshness `check` compares the build commit against the deployed revision
  (`record-revision` at lines 210-211), so a binary that predates a sibling's change is flagged;
  strictness is opt-in via `DEPLOY_STRICT_BINARIES=1`.
