## Goal
- Remove `SemanticCache` as a runtime capability from the RAG pipeline and delete every
  call site, protocol method, and HTTP endpoint that exists only to invalidate it, so
  local RAG always executes retrieval against the currently visible committed RAG
  database state.

## Priority
High

## Scope
- **In-Scope**:
  - Remove `SemanticCache`/`CacheService`/`CacheEntry` and their construction/usage from
    `scripts/rag/pipeline.py`.
  - Remove `RagPipeline.invalidate_cache()` and the `invalidate_cache()` method from the
    `RagPipelineLike` protocol and `RagPipelineMCPService`.
  - Remove the `/rag_invalidate_cache` HTTP endpoint and its handler.
  - Remove `CacheInvalidator` (`scripts/rag/ingestion/cache_invalidation.py`) and its
    caller in `scripts/rag/ingestion/ingester.py`.
  - Delete `scripts/rag/cache.py` and `CacheEntry` once zero remaining callers are
    confirmed.
  - Update/remove tests made obsolete by the deletion; add regression coverage proving
    committed document changes are visible without cache invalidation or restart.
- **Out-of-Scope**:
  - Removing the `use_semantic_cache`/`semantic_cache_threshold`/`semantic_cache_max_size`

  - Removing `embed_url` (still required by local vector retrieval and the Agent memory
    embedding path).
  - The `scripts/agent` statistics field `stat_semantic_cache_hits` (see Unknowns UNK-02).

## Background
`scripts/rag/cache.py` implements `SemanticCache` and `CacheEntry`. `scripts/rag/pipeline.py`
imports, constructs, and calls `lookup()`/`put()`/`invalidate_cache()` on it.
`scripts/mcp_servers/rag_pipeline/rag_pipeline_service.py` exposes `invalidate_cache()` and
calls it from document deletion; `rag_pipeline_server.py` exposes the
`/rag_invalidate_cache` HTTP endpoint. `scripts/rag/ingestion/cache_invalidation.py`'s
`CacheInvalidator` is a confirmed active caller of that endpoint, invoked from
`scripts/rag/ingestion/ingester.py` after ingestion completes.

## Problem
The in-process `SemanticCache` cannot observe corpus changes committed by other
processes, has no TTL, and does not use its generation value to validate entry
freshness. Its behavior is spread across the RAG pipeline, the RAG MCP service
protocol, document deletion, the ingestion pipeline's post-ingestion invalidation call,
and a direct HTTP invalidation endpoint. Removing only the cache lookup from the
pipeline would leave invalid method contracts, stale call sites, and a public endpoint
for a feature that no longer exists.

## Reason for change
A cache with no cross-process invalidation and no TTL can serve stale results after
another process commits document changes, contradicting the freshness guarantee RAG
retrieval is expected to provide.

## Implementation intent
Remove query-result caching as a runtime capability and make local RAG execute
retrieval for every query against the currently visible committed RAG database state.
Remove cache invalidation as an API and an operational concept, including the ingestion
pipeline's post-ingestion invalidation call. Preserve `embed_url` because it remains
required by local vector retrieval and the Agent memory embedding path. Delete the
cache-lookup embedding request in `RagPipeline.augment()` entirely rather than leaving
a dead `if self._cfg.use_semantic_cache and ...` branch — the `use_semantic_cache`
config field itself is left in place (its removal is `semcacheconfig`'s
responsibility), but no production code path may read it after this Plan lands.

## Design
`RagPipeline.augment()` currently branches on `self._cfg.use_semantic_cache` at two
points: before retrieval (embedding the query and calling `semantic_cache.lookup()`,
returning early on a hit) and after retrieval (calling `semantic_cache.put()` to store
the formatted context block). Both branches, and the embedding call that exists only to
feed the cache lookup, are removed entirely rather than left as a dead `if` guarded by
a config flag that this Plan does not remove — the flag itself remains defined (see
Assumptions) purely so `semcacheconfig` can remove it independently without racing this
Plan, but no code path in this Plan's target files may read it after REQ-001 lands.

`RagPipelineLike.invalidate_cache()` exists solely to let
`RagPipelineMCPService.fmt_delete_document()` clear stale cache entries after a
document delete; once the cache is gone, the protocol method, its implementation, the
call site, and its log message are all removed together (REQ-002) — there is no
partial state where the protocol method exists without a backing cache.

`/rag_invalidate_cache` (REQ-003) and `CacheInvalidator` (REQ-004) are two independent
callers of the same underlying capability (`RagPipelineMCPService.invalidate_cache()`
via HTTP): the endpoint is the direct exposure, `CacheInvalidator` is the ingestion
pipeline's HTTP client for that endpoint. Both are removed in the same Plan since
leaving either one would mean shipping a dead code path (an endpoint with no
meaningful effect, or a client that 404s).

`scripts/rag/cache.py` and `CacheEntry` (REQ-005) are deleted last, after REQ-001
through REQ-004 remove every confirmed caller — deleting them first would break
`scripts/rag/pipeline.py`'s import before that import itself is removed.

Test cleanup (REQ-006) includes three files discovered by this Plan's own
repository-wide search (`tests/rag/test_pipeline_http_result_kind.py`,
`tests/rag/test_rag_http_mode.py`, `tests/rag/test_pipeline_refiner_fallback_counters.py`)
that stub `pipeline.semantic_cache = MagicMock()` / `cfg.use_semantic_cache = False` in
fixture setup. These lines do not currently fail (Python allows assigning arbitrary
attributes to a `MagicMock`-backed test double), but they reference a removed concept
and are cleaned up per the originating issue's "Remove imports, mocks, fixtures, and
helper methods made unused by the deletion" instruction.
