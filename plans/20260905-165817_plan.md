## Goal
- Implement deterministic, CI-blocking validation for the Canonical Source Registry's semantic rules (duplicate/missing/ambiguous/stale canonical-source mappings), reusing existing documentation-validation infrastructure wherever it already covers the need.

## Priority
Medium

## Scope
- **In-Scope**: a new semantic validator (`tools/check_canonical_source_conflicts.py`) that wraps `M-01-04`'s `tools/check_canonical_source_registry.py` (schema/structural checks) and adds the additional semantic rules this Issue requires (duplicate ADR identifier — implementing the already-tracked-but-missing `GV-003`; multiple canonical Specifications for the same target/claim-type; area-guide-vs-registry contradiction, scoped to targets the registry currently defines; legacy universal-precedence-language reintroduction, reusing `check_compat_shims.py`'s historical-context helper); deterministic `CANONICAL-NNN`-prefixed error output with target/claim-type/source/expected-condition fields; unit tests per rule; integration tests against a temporary registry and temporary doc tree; wiring the new tool into `.github/workflows/governance-docs-consistency.yml` as a blocking step; updating the Governance Verification Matrix only once that CI wiring is in place.
- **Out-of-Scope**: resolving the content of any existing conflict this validator finds; automatically rewriting canonical documents to fix a detected violation (report only); inferring that code complies with an ADR merely because both are registered; fully implementing the area-guide-vs-registry check beyond the one registry entry `M-01-04` populated (complete coverage depends on `M-01-06`'s migration, not yet in scope).
- **Constraint**: keep registry schema validation (`tools/check_canonical_source_registry.py`, `M-01-04`) separate from this Plan's semantic validation; reuse `tools/check_docs_structure.py`, `tools/check_docs_quality.py`, and existing ADR validators (`check_adr_invariant_matrix.py`, `check_adr_reference.py`, `check_compat_shims.py`) wherever they already cover a need, rather than introducing an overlapping validator (source Issue's Constraints section).

## Background
The Governance Verification Matrix already identifies duplicate canonical declarations (`GV-011`, `GV-012`), missing canonical references (`GV-013`), and unique-ADR-ID enforcement (`GV-003`) as incomplete ("Missing") or manual-only checks — none of them is currently automated against the new registry-based model `M-01-04` introduced.

## Problem
A registry with no enforcement is only as reliable as manual review — the exact failure mode the target-based model (`M-01-02`) and registry (`M-01-04`) were introduced to replace; without deterministic validation, invalid, ambiguous, missing, or stale canonical-source mappings can be merged undetected.

## Reason for change
Confirmed via Read: `tools/check_docs_structure.py` has no ADR-ID-duplicate logic (matching `GV-003`'s own "Missing" status), `tools/check_docs_quality.py`'s only duplicate check is `duplicate_heading_numbers` (unrelated), and neither `check_adr_invariant_matrix.py` nor `check_adr_reference.py` validates canonical-source conflicts — so this functionality does not yet exist anywhere in the repository and must be added, per the source Issue's own instruction to verify no existing tool already owns it.

## Implementation intent
Add one new tool, `tools/check_canonical_source_conflicts.py`, that (a) invokes `M-01-04`'s registry validator and re-emits its findings under this Plan's deterministic `CANONICAL-NNN` rule-ID format, (b) adds the additional semantic checks this Issue requires that no existing tool covers, delegating to `check_compat_shims.py`'s `_is_historical_context()` helper for the legacy-language-reintroduction check rather than duplicating it, and (c) extends `tools/check_docs_structure.py` directly for the one check that is squarely that tool's existing responsibility (`GV-003` Unique ADR ID) rather than reimplementing it in the new tool. Wire the new tool into the existing `governance-docs-consistency.yml` CI workflow as a blocking step, and update the Governance Verification Matrix's status only once that wiring is confirmed active.

## Design
`tools/check_canonical_source_conflicts.py` is a thin orchestration layer: it imports and calls `tools/check_canonical_source_registry.py`'s existing validation functions (not re-implementing them), converts their findings into this Plan's `CANONICAL-NNN` rule-ID format (matching the source Issue's own example error format: rule ID, `Target:`, `Claim type:`, `Sources:`/`Source:`, `Expected:`), and adds the genuinely new checks (`REQ-002`, `REQ-003`, `REQ-005`, `REQ-006`, `REQ-007`) that do not exist in any current tool. `GV-003` (duplicate ADR ID) is implemented directly in `tools/check_docs_structure.py` instead — that tool already owns ADR/document structural validation (see its existing `GV-002`, `GV-006`, `GV-007` rows in the Governance Verification Matrix), so a duplicate-ID check belongs there, not duplicated into the new tool; `check_canonical_source_conflicts.py` calls it and re-emits its result as `CANONICAL-007` for a consistent rule-ID namespace in this Plan's own output.

Rule-ID allocation (all under the `CANONICAL-` prefix the source Issue's example already uses): `CANONICAL-001` duplicate canonical source; `CANONICAL-002` missing source (wraps `M-01-04`); `CANONICAL-003` unknown target format (wraps `M-01-04`); `CANONICAL-004` unknown claim type (wraps `M-01-04`); `CANONICAL-005` Draft normative source (wraps `M-01-04`); `CANONICAL-006` Proposed ADR as Accepted source (wraps `M-01-04`); `CANONICAL-007` duplicate ADR ID (wraps the new `check_docs_structure.py` check); `CANONICAL-008` multiple canonical Specifications; `CANONICAL-009` registry schema violation (wraps `M-01-04`); `CANONICAL-010` area guide contradicting registry; `CANONICAL-011` legacy universal-precedence reintroduction. The five Warnings use a separate `CANONICAL-W-NNN` sub-namespace, kept visibly distinct from blocking errors in output (`REQ-007`, AC8).

CI wiring adds one new blocking step to `.github/workflows/governance-docs-consistency.yml` (after the existing `check_dependency_graph_cycles.py` step, before the report-only front-matter step), and adds `tools/check_canonical_source_conflicts.py`, `tools/check_canonical_source_registry.py`, and `config/documentation_canonical_sources.toml` to the workflow's `paths:` trigger list so the check runs whenever any of them change.
