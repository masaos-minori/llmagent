## Background
The source Issue (`issues/20260821_02_issue.md`) was written against an earlier
snapshot of the codebase in which Git MCP had no branch-level guard at all, the
approval layer silently downgraded `git_checkout`/`git_pull`/`git_push` to a `y/N`
prompt, and the security docs mis-described both. Since that snapshot, an
already-archived Plan (`plans/done/20260825-095817_plan.md`, REQ-003/REQ-006) and prior
unlogged work implemented `GitConfig.protected_branches` +
`GitSecurityGuards._check_protected_branch()` (wired into all three write handlers),
added ref-safety validation (`_is_safe_ref()`/`_validate_ref()`, rejecting
option-injection-shaped `branch`/`remote` values), and raised
`git_checkout`/`git_pull`/`git_push` to the `"high"` approval tier in
`config/agent.toml::approval_risk_rules`. `docs/04_mcp_90_inconsistencies_and_known_issues.md`
`MCP-004` even records this as `Status: resolved`, with a note that
`04_mcp_05_03_fail-open-fail-closed-and-risk-tiers.md`'s stale caveat "should be removed
the next time that document is touched" — this Plan is that next touch.

## Problem
Re-verifying every factual claim in the Issue against current source (2026-08-26) shows:
- **Issue claim "server layer has no branch/force guard"** — **false now**.
  `GitSecurityGuards.__init__` (`git_security.py:23-32`) takes `protected_branches`;
  `_check_protected_branch()` (`git_security.py:54-58`) enforces it; `GitService`
  (`git_service.py`) calls `_validate_protected()` in `git_checkout`, `git_pull`, and
  `git_push` (lines 237, 255, 276) before dispatch. Tested by
  `tests/mcp_servers/git/test_git_security_compliance.py::test_check_protected_branch`,
  `test_git_checkout_protected_branch`, `test_git_push_protected_branch`,
  `test_git_pull_protected_branch`. `branch`/`remote` option-injection is also already
  rejected via `_is_safe_ref()`/`_validate_ref()`, tested by `test_is_safe_ref`. Force-Push
  has no guard because it has nothing to guard: `GitPushRequest` (`git_models.py:177-185`)
  exposes no `force` field and `format_output.py` never passes `--force`.
- **Issue claim "agent approval enforces only single-character y/N"** — **false now**.
  `config/agent.toml::approval_risk_rules` (lines 201-203) sets
  `git_checkout = "high"`, `git_pull = "high"`, `git_push = "high"`. `classify_risk()`
  (`tool_policy.py:137-171`) checks `approval_risk_rules` first (Priority 1), before the
  `tool_safety_tiers` → `_TIER_TO_RISK` fallback that would otherwise yield `MEDIUM`.
  Tested by
  `tests/agent/test_tool_policy_comprehensive.py::test_git_checkout_pull_push_resolve_to_high_risk`.
- **Issue claim "escalation list omits git"** — **false now**. Same `approval_risk_rules`
  entries above are the escalation list the Issue says is missing them.
- **Issue claim "branch protection intent silently ignored for git" (via
  `_escalate_for_github_branch()` only firing for `github_`-prefixed tools)** — **still
  technically true but no longer consequential**: that specific branch-conditional
  escalation path indeed skips git tools, but it is now redundant — `git_checkout`/
  `git_pull`/`git_push` already get the unconditional `"high"` override for *every*
  branch, not only protected ones, so no branch ever reaches only `MEDIUM`. No fix
  needed; documented here as a verified non-issue rather than silently dropped.
- **Issue claim "the security document is false" (00_security_02 claims
  `protected_branches`/`force_push_blocked` exist for Git MCP; NC-018 pointer is
  broken)** — **the specific quoted claim no longer exists**, but the document is
  *still* wrong, in the opposite direction: `00_security_02_high-risk-tool-common-policy.md`
  line 187 currently states "Git MCP: has no protected-branch policy and no technical
  Force Push block" — which is now false for the protected-branch half, since
  `GitConfig.protected_branches` is enforced. The `NC-018` pointer the Issue complains
  about does not appear anywhere in `00_security_02` today; the correctly-scoped
  replacement, `NC-019` in `docs/00_governance_03_issue-and-uncertainty-management.md`,
  already exists (`Status: open`, `Last Reviewed: 2026-08-21`) and needs no further
  action from this Plan.

## Reason for change
Operators and future implementers read these documents to judge what protection Git MCP
actually provides. Right now the documents disagree with each other and with the code:
some sections correctly describe the implemented protected-branch guard, others still
claim it does not exist, and the ownership matrix still reports a uniform risk tier that
no longer matches the config. Left uncorrected, this actively misleads in both
directions — understating protection in some places, and (if read superficially)
appearing to overstate it if an operator does not also notice the empty
`protected_branches` list means it isn't switched on for the real repo. Fixing the
config activation without fixing the docs (or vice versa) would leave the mismatch
in place either way.

## Implementation intent
Two independent groups of changes, each individually revertable: (1) five
documentation corrections that align every claim about Git MCP branch/approval
protection with the code that already exists and is already tested, replacing false
"not implemented" claims with accurate descriptions and cross-references to the
existing tests, while explicitly leaving the still-open Dirty-Worktree/Detached-HEAD/
postcondition items (`GIT-001` and its companion) untouched and cross-referenced, not
re-described as fixed; and (2) one config-only change that activates the existing,
tested `protected_branches` guard for the real repository by setting it in
`config/git_mcp_server.toml`, mirroring the branch list already declared in
`config/agent.toml::approval_high_risk_branches`. No new module, class, or public
interface is introduced.
