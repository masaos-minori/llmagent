# Make replay pagination validated, snapshot-consistent, and bounded

## Goal

Make the `/replay` endpoint a stable API contract: restrict the `format` parameter to the closed set `sse`/`json` so unsupported values return a validation error (422) and OpenAPI documents only the supported values; combine the `_fetch()` and `_count()` calls into a single `run_with_db_lock()`-wrapped closure so each JSON response's `total` and `items` represent one internally consistent database snapshot; keep ordering deterministic by `seq`.

## Priority
Medium

## Scope
- **In-Scope**: Restricting `format` to `sse`/`json` using FastAPI's `Literal`/enum support; returning validation errors for unsupported values; combining `_fetch()`/`_count()` into a single locked closure; documenting paging behavior when offset exceeds available result set and while new events are published.
- **Out-of-Scope**: Batch-bounded initial subscription replay and capacity limits (EB-M05). Authentication/authorization for the replay endpoint.

## Background

Confirmed by direct read of `scripts/eventbus/app.py` line 130 (`fmt: str = Query(default="sse", alias="format")`) and `scripts/eventbus/replay_route.py` lines 26-63: no `Literal["sse", "json"]`/regex constraint exists on `fmt`, and OpenAPI therefore cannot list a restricted enum for it either. `_fetch()` (line 38) and `_count()` (line 47) are separate closures each independently wrapped in `await run_with_db_lock(...)` (lines 41, 49) — the lock (`scripts/eventbus/db.py`'s module-level `_db_lock`) is acquired and released twice, not held across both reads, so no read-transaction/lock scope spans the two queries together.

## Problem

- An unsupported `format` value (anything other than `json`) is silently accepted and served as SSE rather than rejected with a validation error, and OpenAPI cannot document the actual supported values because the parameter has no closed type.
- Between the `_fetch()` and `_count()` calls in the JSON-format path, a concurrent `/publish` can insert a new row — the returned `items` list is a snapshot *before* that insert while `total` may reflect *after* it (or vice versa, depending on interleaving), so the response's `total`/`items` do not necessarily describe the same database state.

## Reason for change

Make replay a stable API contract. Inputs must be strictly validated, ordering must be deterministic, and a JSON page must describe one consistent database snapshot.

## Implementation intent

Restrict `format` to the closed set `sse`/`json` using FastAPI's `Literal`/enum support so unsupported values return a validation error (422) and OpenAPI documents only the supported values. In `replay_route.py`, fetch total count and page items under one lock acquisition and one read (e.g. a single `run_with_db_lock()` call that runs both queries inside the same closure, so they execute back-to-back while the lock is held, rather than two separate lock-acquire/release round trips). Keep ordering stable by `seq` (already the case via `fetch_events_since()`'s `ORDER BY seq`, confirmed in `db.py` line 215 — preserve this).

## Requirements

- `REQ-001`: Restrict `format` to the closed set `sse` and `json`.
- `REQ-002`: Return a validation error for unsupported values and expose the enum in OpenAPI.
- `REQ-003`: Fetch total count and page items under one lock and one read (combine `_fetch()`/`_count()` into a single `run_with_db_lock()`-wrapped closure).
- `REQ-004`: Document paging behavior when offset exceeds the available result set and while new events are published.
- `REQ-005`: Verify ordering remains deterministic by `seq` after the change.

## Design

### Architecture analysis

The `/replay` endpoint currently has two execution paths:
1. **SSE path**: Fetches all matching events (no pagination limit enforcement beyond `limit`/`offset`), streams them via SSE.
2. **JSON path**: Fetches paginated items (`_fetch()`) and total count (`_count()`) separately, returns `{total, items}`.

The critical issue is in the JSON path: the two separate `run_with_db_lock()` calls mean the lock is acquired and released twice, allowing a concurrent `/publish` to insert a row between the two reads. This makes `total` and `items` potentially inconsistent.

### Dependency graphing

```
FastAPI routing ──► replay() ──► _fetch() ──► fetch_events_since(db, ...)
   │                    │              └──► run_with_db_lock(_fetch)
   │                    │
   └──► get_db()        │
                         │
   FastAPI routing ──► replay() ──► _count() ──► conn.execute("SELECT COUNT(*) ...")
   │                    │              └──► run_with_db_lock(_count)
   └──► get_db()        │
```

After refactoring, the JSON path becomes:
```
FastAPI routing ──► replay() ──► combined_fetch_and_count() ──► [fetch_events_since + SELECT COUNT(*)]
   │                    │              └──► single run_with_db_lock(combined_fetch_and_count)
   └──► get_db()        │
```

Key dependencies:
- `app.py` must pass `Literal["sse", "json"]` type to FastAPI for automatic validation.
- `replay_route.py` must combine the two closures into one.
- Both `app.py` and `replay_route.py` must agree on the `fmt` parameter type.

### Historical analysis

- The `/replay` endpoint was designed with two separate DB reads for the JSON path — this was likely intentional to avoid holding the lock longer than necessary, but it creates a race condition.
- No prior attempt to add format validation exists — this is the first effort.
- The `ORDER BY seq` in `db.py:215` has been stable since inception — no ordering regression risk.

### Operational dependency inspection

- Adding `Literal["sse", "json"]` to the query parameter will cause FastAPI to reject unsupported values with HTTP 422 automatically — no manual validation needed.
- Combining `_fetch()`/`_count()` into a single closure means the DB lock is held for slightly longer (two queries instead of one), but this is acceptable since SQLite handles concurrent readers well.
- The `limit`/`offset` bounds (1–1000) are already enforced by FastAPI's `ge(1, le=1000)` — no change needed there.

### Design decisions

1. **Format validation (REQ-001)**: Use `Literal["sse", "json"]` type annotation on the `fmt` query parameter in both `app.py` and `replay_route.py`. If FastAPI doesn't support Literal on query params, fall back to a custom `Enum` class.

2. **Snapshot consistency (REQ-003)**: Combine `_fetch()` and `_count()` into a single closure that executes both queries inside the same `run_with_db_lock()` call. This ensures the lock is held across both reads, preventing interleaving with `/publish`.

3. **Precedence of defaults**: Keep `default="sse"` for backward compatibility. If a client sends `?format=json`, they get a JSON response; otherwise, SSE streaming.

4. **Documentation update (REQ-004)**: Document the following in `docs/06_eventbus_06_reference-api.md`:
   - The `format` parameter accepts only `sse` or `json` (returns 422 for other values).
   - JSON responses provide snapshot-consistent `total` and `items` for each page.
   - When offset exceeds available results, `items` is empty but `total` reflects the remaining count.

## Risks

- **Risk**: FastAPI may not properly validate `Literal["sse", "json"]` on query parameters — if so, need to use a custom Enum class instead. → **Mitigation**: Test with FastAPI's built-in validation after implementation; if Literal fails, switch to Enum.
- **Risk**: Combining `_fetch()`/`_count()` into a single closure increases the time the DB lock is held, which could impact concurrent operations under high load. → **Mitigation**: The two queries are simple (one SELECT with LIMIT/OFFSET, one SELECT COUNT(*)) — the additional lock hold time is negligible (< 1ms for typical datasets).
- **Risk**: Existing clients may send unsupported format values expecting SSE fallback — these will now receive 422 errors. → **Mitigation**: Document the breaking change clearly; the 422 error is more helpful than silent SSE fallback.
