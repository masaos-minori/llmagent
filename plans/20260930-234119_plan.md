## Goal
Contain turn-execution exceptions that currently escape the agent REPL loop and crash the interactive session, so that an unexpected per-turn error is reported to the operator and the REPL remains usable for the next command.

## Priority
Medium

## Scope
- **In-Scope**: Add a per-turn exception safety net in `scripts/agent/repl_input_loop.py` around the turn-dispatch await. Add a regression test in `tests/agent/test_repl_error_handling.py`.
- **Out-of-Scope**: Startup `session.start()` exception translation in `run()`; input-coroutine cancellation on the shutdown-during-input path (tracked separately as `repl002`); `WorkflowEngine` internals; shutdown racing, multiline continuation, and command routing outside the turn-dispatch path.

## Background
Found during an adversarial review of `scripts/agent/repl_input_loop.py` covering agent REPL operation processing. User input flows `ReplInputLoop._dispatch_line` -> `Orchestrator.handle_turn` -> `WorkflowEngineAdapter.execute_turn` -> `WorkflowEngine`. Each layer has its own error handling, but every layer narrows the set of caught exception types rather than widening it, so the effective containment is the intersection of those narrow sets.

## Problem
- `scripts/agent/repl_input_loop.py:_repl_loop` awaits the dispatch task and catches only `TimeoutError` locally (`except TimeoutError`).
- `scripts/agent/repl_input_loop.py:run()` wraps `await self._repl_loop()` in `try/except RuntimeError` only, writing a fatal message and re-raising.
- `scripts/agent/workflow_engine_adapter.py:execute_turn` catches only `WorkflowPendingApprovalError`, `WorkflowHaltError`, and `WorkflowTimeoutError`; other exceptions are re-raised by `WorkflowEngine.run()`.
- `scripts/agent/repl.py:run()` calls `self._input_loop.run(...)` with no surrounding `try/except`, and `main()` runs it directly under `asyncio.run(...)`.

Result: a turn that raises any exception other than `RuntimeError` (or `TimeoutError`) is never surfaced through `view.write_fatal`/`write_warning`; it reaches `asyncio.run()` and ends the whole session.

## Reason for change
A single unexpected per-turn error currently costs the entire interactive session. Turn-level failures (a bad LLM response, an unhandled tool error, a transient transport fault) should be reported to the operator and the REPL should remain usable for the next command. Containment scoped to one exception type is fragile: adding any new exception type in the turn path silently removes REPL resilience with no warning.

## Implementation intent
Add a per-turn exception safety net so that an exception escaping `handle_turn`/`_dispatch_line` is surfaced through the CLI view and the loop continues (unless a shutdown was requested). Prefer containing it in `_repl_loop` around the dispatch await, or in `run()` around `_repl_loop()`, without disturbing the existing shutdown-racing logic or the current `RuntimeError` fatal-write path. If the fix belongs in `WorkflowEngineAdapter.execute_turn`, convert unexpected exceptions into an error response/error_kind rather than letting them propagate, and document that contract. Keep the change minimal and localized to the turn-dispatch path.

## Requirements
- `REQ-001`: In `scripts/agent/repl_input_loop.py`, wrap the turn-dispatch await so a non-`RuntimeError`, non-`TimeoutError` exception escaping `handle_turn`/`_dispatch_line` is caught, surfaced through the CLI view (`write_fatal`/`write_warning`), and does not abort the loop when no shutdown was requested.
- `REQ-002`: Add a regression test asserting that `handle_turn` raising a non-`RuntimeError` exception leaves the REPL responsive (waits for the next input) instead of propagating out of the loop.

## Design
The current architecture narrows exception containment at every layer: `_repl_loop` catches only `TimeoutError`, `run()` catches only `RuntimeError`, and `execute_turn` handles only three workflow errors. The effective containment is their intersection, which excludes every other exception type.

Preferred design: contain the exception at the REPL layer, where the operator-facing surface lives. Wrap the turn-dispatch await in `_repl_loop` with a `try/except` that catches a broad base `Exception` (not `BaseException`, never `asyncio.CancelledError`), writes it through the view, and continues the loop unless `shutdown_requested` is set. `TimeoutError` keeps its existing shutdown-race handling; `RuntimeError` keeps its existing fatal-write-and-reraise path in `run()`. The new handler sits alongside these without collapsing into them.

Fallback design: if implementation determines adapter-side containment is cleaner, convert unexpected exceptions in `WorkflowEngineAdapter.execute_turn` into an error response/error_kind and document that contract — but do not remove or weaken the existing `WorkflowPendingApprovalError`/`WorkflowHaltError`/`WorkflowTimeoutError` handling.

Because `_repl_loop` already has cyclomatic complexity D (radon score 28), the added branch must stay minimal; extract a small helper method if the branch grows beyond a few lines.

## Risks
- **Risk**: A broad `try/except Exception` around the dispatch await could swallow exceptions the loop intentionally relies on propagating (e.g. `CancelledError`, or a fatal signal), masking real failures. → **Mitigation**: Re-raise `asyncio.CancelledError` explicitly; preserve the existing `TimeoutError` shutdown-race path and the `RuntimeError` fatal-write-and-reraise path in `run()`; scope the new handler to the turn-dispatch await only, never the surrounding shutdown logic.
- **Risk**: `_repl_loop` already has cyclomatic complexity D (radon score 28); adding branches risks pushing it further and reducing maintainability. → **Mitigation**: Keep the added branch minimal; extract a small named helper method if it grows beyond a few lines; validate with `uv run radon cc scripts/agent/repl_input_loop.py -s` before finishing.
- **Risk**: The fix contains the symptom at the loop layer while the root cause (an unhandled exception type escaping `execute_turn`) persists downstream. → **Mitigation**: Record UNK-01 and, during implementation, trace which exception types escape; if adapter-side containment is cleaner for a specific recurring type, address it as a follow-up rather than blocking this change.
