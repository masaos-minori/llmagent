## Goal
Contain turn-execution exceptions that currently escape the agent REPL loop and crash the interactive session, so that an unexpected per-turn error is reported to the operator and the REPL remains usable for the next command.

## Priority
Medium

## Scope
- **In-Scope**: Add a per-turn exception safety net in `scripts/agent/repl_input_loop.py` around the turn-dispatch await. Add a regression test in `tests/agent/test_repl_error_handling.py`.
- **Out-of-Scope**: Startup `session.start()` exception translation in `run()`; input-coroutine cancellation on the shutdown-during-input path (tracked separately as `repl002`); `WorkflowEngine` internals; shutdown racing, multiline continuation, and command routing outside the turn-dispatch path.

## Background
Found during an adversarial review of `scripts/agent/repl_input_loop.py` covering agent REPL operation processing. User input flows `ReplInputLoop._dispatch_line` -> `Orchestrator.handle_turn` -> `WorkflowEngineAdapter.execute_turn` -> `WorkflowEngine`. Each layer has its own error handling: `_repl_loop` catches only `TimeoutError`, `run()` catches only `RuntimeError`, `execute_turn` handles only three workflow errors (`WorkflowPendingApprovalError`, `WorkflowHaltError`, `WorkflowTimeoutError`). `WorkflowEngine.run()` has a broad `except Exception` clause that catches all exceptions, marks the task as "failed", and re-raises them. The effective containment gap is not simply the intersection of narrow sets — it is that the engine catches everything but does not surface it to the operator (the engine re-raises after marking failed), while the REPL layer catches nothing except `RuntimeError`/`TimeoutError`.

## Problem
- `scripts/agent/repl_input_loop.py:_repl_loop` awaits the dispatch task and catches only `TimeoutError` locally (`except TimeoutError` at lines 280 and 288). Exceptions from `dispatch_task.result()` (lines 249, 257) propagate out unhandled.
- `scripts/agent/repl_input_loop.py:run()` wraps `await self._repl_loop()` in `try/except RuntimeError` only (line 103), writing a fatal message and re-raising.
- `scripts/agent/workflow_engine_adapter.py:execute_turn` catches only `WorkflowPendingApprovalError`, `WorkflowHaltError`, and `WorkflowTimeoutError`; other exceptions propagate out after `WorkflowEngine.run()` marks the task as "failed" via its `except Exception` clause (line 155-157) and re-raises.
- `scripts/agent/repl.py:run()` calls `self._input_loop.run(...)` with no surrounding `try/except`, and `main()` runs it directly under `asyncio.run(...)`.

Result: a turn that raises any exception other than `RuntimeError` (or `TimeoutError`) is never surfaced through `view.write_fatal`/`write_warning`; it reaches `asyncio.run()` and ends the whole session. Note: `WorkflowEngine.run()` catches these exceptions internally (marks task as "failed") and re-raises them — the engine itself does not swallow exceptions; the containment gap is purely at the REPL layer where non-`RuntimeError`/non-`TimeoutError` exceptions escape without operator notification.

## Reason for change
A single unexpected per-turn error currently costs the entire interactive session. Turn-level failures (a bad LLM response, an unhandled tool error, a transient transport fault) should be reported to the operator and the REPL should remain usable for the next command. Containment scoped to one exception type is fragile: adding any new exception type in the turn path silently removes REPL resilience with no warning.

## Implementation intent
Add a per-turn exception safety net so that an exception escaping `handle_turn`/`_dispatch_line` is surfaced through the CLI view and the loop continues (unless a shutdown was requested). Prefer containing it in `_repl_loop` around the dispatch await, or in `run()` around `_repl_loop()`, without disturbing the existing shutdown-racing logic or the current `RuntimeError` fatal-write path. If the fix belongs in `WorkflowEngineAdapter.execute_turn`, convert unexpected exceptions into an error response/error_kind rather than letting them propagate, and document that contract. Keep the change minimal and localized to the turn-dispatch path.

## Requirements
- `REQ-001`: In `scripts/agent/repl_input_loop.py`, wrap the turn-dispatch await so a non-`RuntimeError`, non-`TimeoutError`, non-`CancelledError` exception escaping `handle_turn`/`_dispatch_line` is caught, surfaced through the CLI view (`write_warning` for turn-level failures), and does not abort the loop when no shutdown was requested.
- `REQ-002`: Add a regression test asserting that `handle_turn` raising a non-`RuntimeError` exception leaves the REPL responsive (waits for the next input) instead of propagating out of the loop.

## Design
The current architecture has a two-tier containment gap: `WorkflowEngine.run()` catches all exceptions via `except Exception` (line 155-157) and marks the task as "failed", then re-raises; the REPL layer catches only `RuntimeError`/`TimeoutError`. The effective containment gap is that the engine handles the exception internally (task status updated) and re-raises, but neither the engine nor the REPL surfaces it to the operator.

Preferred design: contain the exception at the REPL layer, where the operator-facing surface lives. Wrap the turn-dispatch await in `_repl_loop` with a `try/except Exception` guard that re-raises `asyncio.CancelledError`, writes the error through the view, and continues the loop unless `shutdown_requested` is set. `TimeoutError` keeps its existing shutdown-race handling; `RuntimeError` keeps its existing fatal-write-and-reraise path in `run()`. The new handler sits alongside these without collapsing into them.

**Hard requirement**: Because `_repl_loop` already has cyclomatic complexity D (radon score 28), the added branch MUST stay minimal. Extract a small named helper method if the branch grows beyond a few lines — this is mandatory, not optional. Validate with `uv run radon cc scripts/agent/repl_input_loop.py -s` before finishing.

Fallback design: if implementation determines adapter-side containment is cleaner, convert unexpected exceptions in `WorkflowEngineAdapter.execute_turn` into an error response/error_kind and document that contract. This requires changes to `execute_turn` to set `error_kind` on unexpected exceptions (currently only `WorkflowPendingApprovalError`/`WorkflowHaltError`/`WorkflowTimeoutError` are handled specially) and to the orchestrator's `_execute_turn` to check for error conditions before passing the result tuple along. Do not remove or weaken the existing `WorkflowPendingApprovalError`/`WorkflowHaltError`/`WorkflowTimeoutError` handling.

## Risks
- **Risk**: A broad `try/except Exception` around the dispatch await could swallow exceptions the loop intentionally relies on propagating (e.g. `CancelledError`, or a fatal signal), masking real failures. → **Mitigation**: Re-raise `asyncio.CancelledError` explicitly; preserve the existing `TimeoutError` shutdown-race path and the `RuntimeError` fatal-write-and-reraise path in `run()`; scope the new handler to the turn-dispatch await only, never the surrounding shutdown logic.
- **Risk**: `_repl_loop` already has cyclomatic complexity D (radon score 28); adding branches risks pushing it further and reducing maintainability. → **Mitigation**: Keep the added branch minimal; extract a small named helper method if it grows beyond a few lines; validate with `uv run radon cc scripts/agent/repl_input_loop.py -s` before finishing. Enforce AC-4 (complexity ≤ 30).
- **Risk**: The fix contains the symptom at the loop layer while the root cause (an unhandled exception type escaping `execute_turn`) persists downstream. → **Mitigation**: Record UNK-01 and, during implementation, trace which exception types escape; if adapter-side containment is cleaner for a specific recurring type, address it as a follow-up rather than blocking this change.
- **Risk**: Surfacing the error at the REPL loop while `WorkflowEngine.run()` has already marked the task as "failed" creates a confusing state for the operator (task status says "failed" but the REPL continues). → **Mitigation**: Document this inconsistency in the implementation notes; consider whether surfacing the error through a callback mechanism from the engine would be cleaner, but do not block this change on that resolution.
- **Risk**: `sqlite3.Error` from `ctx.session.save()` in `orchestrator.py:_execute_turn` line 107 and tool execution exceptions from `execute_all_tool_calls()` in `tool_runner.py` are NOT caught anywhere in the turn path — these are concrete examples of the gap identified in UNK-01, not just theoretical possibilities. → **Mitigation**: The loop-layer fix addresses all of these uniformly via the broad `try/except Exception`; no need to enumerate each type individually.
