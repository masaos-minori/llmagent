# Plan: Make `TURN_LIMIT_HINT` report the omitted result's size and the configured limit

## Goal

When `_apply_turn_char_limit()` in `scripts/agent/tool_runner.py` replaces an
over-budget tool result with a hint, the hint text seen by the LLM must state the
omitted result's actual size (character count and line count) and the configured
per-turn limit, instead of the current fixed generic sentence — giving the LLM
concrete signal to decide whether to retry narrower, request a summary, or move on.

## Scope

**In scope:**
- Convert `TURN_LIMIT_HINT` in `scripts/agent/tool_result_formatter.py` (currently a
  plain string constant, line 13) into a small function that accepts the omitted
  result's char count, line count, and the configured limit, and renders a concise
  hint string containing all three values.
- Update `_apply_turn_char_limit()` in `scripts/agent/tool_runner.py` (lines 231-245)
  to compute `omitted_chars = len(llm_text)` and `omitted_lines =
  len(llm_text.splitlines())` and pass them, plus `limit`, into the new hint function
  instead of returning the static constant.
- Update the import at `scripts/agent/tool_runner.py:33-36` to import the new function
  name instead of the old constant name.
- Preserve the existing `logger.info(...)` call (lines 238-242) and its current
  message/values unchanged.
- Add unit tests in `tests/test_tool_result_formatter.py` (new hint-function output for
  representative cases: empty text, single-line, multi-line, exact boundary) and in
  `tests/test_tool_runner.py` (`_apply_turn_char_limit()` end-to-end: over-limit
  returns dynamic hint containing correct numbers; under-limit returns `llm_text`
  unchanged).

**Out of scope:**
- Any change to the limit-detection condition
  (`limit > 0 and (turn_chars + len(llm_text)) > limit`) — it must trigger under
  exactly the same condition as before.
- Any change to `_collect_tool_result_msgs`'s turn-budget accounting
  (`turn_chars += len(llm_text)` at `tool_runner.py:192`) — it keeps accumulating the
  length of whatever `_apply_turn_char_limit` returns, same as today.
- Any change to how tool results are persisted, displayed, or logged elsewhere in
  `tool_runner.py` (e.g. `_log_and_emit_tool_call`, `_emit_tool_result`).
- `docs/*.md` updates — out of scope for this document-only planning phase.

## Design

**Decision: convert `TURN_LIMIT_HINT` from a string constant into a function,
`turn_limit_hint(omitted_chars: int, omitted_lines: int, limit: int) -> str`, defined
in `scripts/agent/tool_result_formatter.py`, and have `_apply_turn_char_limit()` call
it with the values it already computes.**

A format-string approach (e.g. `TURN_LIMIT_HINT_TEMPLATE = "...{omitted_chars}..."`
plus a manual `.format(...)` call at the use site) was considered but rejected in
favor of a small function: a function gives a typed, self-documenting call signature
(`turn_limit_hint(chars, lines, limit)`) enforced by the caller, whereas a bare
template string leaves the keys/format spec implicit and easier to typo at the call
site with no static check. Since there is exactly one call site (confirmed by U2),
the function approach costs nothing extra while being safer to extend later (e.g. if
a fourth value needs to be added).

**Exact new hint format:**

```python
def turn_limit_hint(omitted_chars: int, omitted_lines: int, limit: int) -> str:
    """Build the hint shown to the LLM in place of a tool result dropped for
    exceeding the per-turn char limit.

    Reports the omitted result's size (so the LLM can gauge how much was cut)
    without including the omitted content itself.
    """
    return (
        f"[Result omitted: per-turn tool result limit reached. "
        f"Omitted result: {omitted_chars} chars, {omitted_lines} lines. "
        f"Configured per-turn limit: {limit} chars.]"
    )
```

Example rendering: `[Result omitted: per-turn tool result limit reached. Omitted
result: 8412 chars, 137 lines. Configured per-turn limit: 4000 chars.]`

This keeps the same bracketed, single-sentence-family style as the original hint
(`"[Result omitted: per-turn tool result limit reached.]"`), so the LLM sees a
familiar prefix, with the size/limit facts appended concisely — no omitted content is
included, satisfying Implementation Instruction #4 of the requirement doc.

**`_apply_turn_char_limit()` after the change:**

```python
def _apply_turn_char_limit(
    llm_text: str,
    turn_chars: int,
    limit: int,
) -> str:
    """Apply per-turn char limit; return hint if exceeded."""
    if limit > 0 and (turn_chars + len(llm_text)) > limit:
        omitted_chars = len(llm_text)
        omitted_lines = len(llm_text.splitlines())
        logger.info(
            "Per-turn tool result limit reached: %s chars > %s; result replaced with hint",
            turn_chars + omitted_chars,
            limit,
        )
        return turn_limit_hint(omitted_chars, omitted_lines, limit)
    return llm_text
```

Notes on this design:
- The `logger.info(...)` call is untouched byte-for-byte (same message, same
  `turn_chars + len(llm_text)` cumulative value, same `limit`) — Acceptance
  Criterion 3 ("existing internal logging behavior... preserved") is satisfied by
  construction, not by re-deriving the log line from the new per-result numbers.
- `omitted_chars` is deliberately `len(llm_text)` (the size of *this* result), not the
  cumulative `turn_chars + len(llm_text)` used in the log line — seeing this result's
  own size is what tells the LLM how much of *this specific* tool call's output was
  cut (Assumption 4).
- The triggering condition (`limit > 0 and (turn_chars + len(llm_text)) > limit`) is
  untouched, so Acceptance Criterion 2 ("still correctly triggers replacement under
  the same condition") is satisfied by construction.
- The `hint: str = TURN_LIMIT_HINT` local variable is removed since the new call
  already returns a `str`; no behavior change, just one fewer intermediate binding.

## Risks

- **Risk:** Renaming `TURN_LIMIT_HINT` to `turn_limit_hint` (constant → function,
  case change) is a breaking rename if any external caller was missed by the grep.
  **Likelihood:** low — U2's repo-wide grep across `scripts/` and `tests/` found
  exactly the two expected references, and Implementation Step 1 re-confirms this
  immediately before editing.
  **Mitigation:** Step 1's grep re-check, plus running `lint-imports` and the full
  `pytest -q` suite (which would surface an `ImportError` from any missed call site)
  before considering the change complete.
- **Risk:** The new hint text is longer than the original; if some downstream code
  path (e.g. history size accounting, a display truncation routine) assumes the hint
  is a short fixed string, a longer dynamic hint could interact unexpectedly with
  other length-based logic.
  **Likelihood:** low — the hint replaces `llm_text` for the same tool-result slot,
  and `turn_chars += len(llm_text)` (line 192, unchanged) already generically handles
  a replaced string of any length; no other code path inspects the hint's exact
  length or content.
  **Mitigation:** the full `pytest -q` run in Implementation Step 6 covers any
  existing integration tests that exercise `_collect_tool_result_msgs` end-to-end;
  Implementation Steps 4-5's new tests explicitly assert on the hint's *content*
  correctness, not merely its presence, so a regression here would surface directly.
- **Risk:** `llm_text.splitlines()` on inputs containing unusual line-terminator
  characters (e.g. `\r`, `\v`, `\x1c`-`\x1e`, Unicode line/paragraph separators) counts
  more "lines" than a naive `\n`-count would, potentially reporting a line count that
  looks surprising for content that appears single-line when rendered in a terminal.
  **Likelihood:** low — this only affects the cosmetic line-count number in the hint,
  not any control-flow or correctness property; tool results are typically JSON,
  shell output, or file content, where `splitlines()`'s broader definition is either
  irrelevant or arguably more accurate.
  **Mitigation:** none needed structurally — the requirement doc itself names
  `llm_text.splitlines()` as the intended line-count idiom (Problem section), so this
  is accepted as consistent with the requirement's own design intent; no further
  action taken.

No risk identified above is unmitigated/blocking, so no `issues/*_risks.md` file is
required for this plan.
