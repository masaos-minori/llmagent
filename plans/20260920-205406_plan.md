## Goal
- Fix false-positive detection in `check_docs_content_policy.py` where `_ERROR_HEADING_RE` and `_CONFIG_HEADING_RE` headings within a fixed 10-line window cause unrelated tables/bullet-lists to be flagged after edits shrink line distances between sections.

## Scope

- **Out-of-Scope**: The two already-applied workarounds in `docs/05_agent_05_llm-and-streaming.md` and `docs/06_eventbus_05_configuration-and-operations.md`; `check_docs_content_policy.py`'s other detection functions (`check_full_json_example`, `check_literal_port_number`, etc.); reverting or redoing the two affected docs files.

## Background
The window-based heuristic was documented in `check_error_handling_table()`'s own docstring as "Flag a table under an Error/Exception/Error Handling heading ... independent of a nearby heading" — deliberately heading-proximity-based rather than requiring structural nesting. This design was exercised extensively during a 2026-09-20 batch that removed mechanically-derivable tables/lists across 22 `docs/*.md` files (`implementations/done/20260920-16*.md`), two of which triggered this side effect.

## Problem
Two confirmed cases show that removing a flagged table/list can shrink the line-distance to an adjacent, unrelated section enough to pull it into the window, producing a new false-positive finding purely as a side effect of fixing an earlier one:

1. **`docs/05_agent_05_llm-and-streaming.md`**: Removing the "Partial Completion Persistence Rules" and "Error Type Design" tables left the retained `### Error Type Design` heading directly above an unrelated `### Runtime Parameter Generation` table. The removal shortened the line-distance between the two enough that `_ERROR_HEADING_RE` (matching the literal word "Error" at the start of a heading) now found `### Error Type Design` within `_HEADINGS_WINDOW` of the unrelated table, flagging it as a new `error-handling table` finding. Worked around by renaming the heading to `### LLMTransportError Kind Categories` (the first word no longer matches `_ERROR_HEADING_RE`).

2. **`docs/06_eventbus_05_configuration-and-operations.md`**: Replacing 8 of 20 `Configuration Fields` bullets with a one-sentence pointer pulled the 12 untouched bullets — including `publisher_token`/`consumer_token`, explicitly protected as security-relevant content by the source Plan — into the `_HEADINGS_WINDOW` of the `### Configuration Fields` heading, producing new `config-file inventory correspondence entry` findings for content that was correctly *not* flagged before the edit. Worked around by expanding the pointer paragraph with additional prose until the remaining bullets fell outside the 10-line window.

## Reason for change
A checker whose own remediation can trigger a new, unrelated false positive creates a whack-a-mole editing loop and forces workarounds (heading renames, padded prose) that exist only to satisfy the tool rather than to improve document quality — the opposite of `skills/DESIGN.md` Docs content policy's intent. This also means the *order* in which findings are fixed within a file can change the total mechanical-content removed depending on which sections end up within `_HEADINGS_WINDOW` of which heading, which is not decidable from reading the flagged finding alone.

## Implementation intent
Scope the heading-window check to the same Markdown section (bounded by the next heading of equal-or-higher level), not merely bounded by line-count. A table 6 lines under `### Error Type Design` is far more likely to belong to that section than one 6 lines under a heading that is itself followed by a different `###` heading before the table. Section-scoping fully replaces `_HEADINGS_WINDOW` for these two functions — no combination of section-scoped + line-count is needed because section boundaries provide strictly stronger semantics than a fixed line count.

## Design
### Section-scoping approach (Path A: small task, ≤3 files)

Both `check_error_handling_table()` and `check_config_file_inventory_table()` currently scan backward up to `_HEADINGS_WINDOW` (10) lines from a table row looking for a matching heading. The fix replaces this fixed-line-count search with section-aware scoping:

**Algorithm:**
1. When a table row is found (line starting with `|` followed by a table separator row), start scanning backward.
2. For each line going upward, check if it matches the relevant heading regex (`_ERROR_HEADING_RE` or `_CONFIG_HEADING_RE`).
3. **Before checking the heading regex**, first check if the current line is a Markdown heading of equal-or-higher level (i.e., has fewer or equal `#` characters) than the one we're looking for. If yes, stop scanning — the table belongs to a different section.
4. Only if no such higher-level heading is encountered during the scan, apply the original heading regex check.

**Section boundary detection:**
A Markdown heading of equal-or-higher level is detected by counting leading `#` characters. Since `_ERROR_HEADING_RE` and `_CONFIG_HEADING_RE` both match `^#{1,6}`, any line matching `^#{1,6}\s+` that has `<=` the number of `#` characters as the target heading constitutes a section boundary.

For example, if searching for a `###` heading match and encountering a `##` heading while scanning backward, the scan stops — they are in different sections.

**Simplified approach:** Instead of counting `#` characters, use a simpler rule: any line matching `^#{1,6}\s+` that does NOT match the target heading regex constitutes a section boundary. This works because:
- If the line matches the target heading regex, it's the heading we want — flag the table.
- If the line does NOT match the target heading regex but IS a heading, it's a different section — stop scanning.
- If the line is not a heading, continue scanning.

This avoids needing to know the exact `#` count of the target heading upfront.

**Edge case: heading at the exact position of the table header.** The current code checks `for j in range(max(0, i - _HEADINGS_WINDOW), idx)` where `idx` is the table header row index. With section-scoping, the loop becomes:
```python
for j in range(idx - 1, max(-1, idx - _HEADINGS_WINDOW), -1):
    line = doc.lines[j]
    # If this line is a heading that doesn't match our target regex, stop
    if _SECTION_BOUNDARY_HEADING_RE.search(line):
        break
    if _TARGET_HEADING_RE.search(line):
        has_target_heading = True
        break
```
Where `_SECTION_BOUNDARY_HEADING_RE = re.compile(r"^#{1,6}\s+")` matches any Markdown heading.

## Risks
- **Risk**: Section-scoping could miss legitimate detections where a table is genuinely under a matching heading but separated by prose content (not another heading) within the window. → **Mitigation**: The existing `_HEADINGS_WINDOW` value of 10 already handles prose-separated cases. Section-scoping adds a stricter constraint (no intervening heading) but does not remove the ability to detect tables under headings — it simply prevents cross-section false positives. Any table genuinely under a matching heading will have no intervening heading between them, so detection still works.
- **Risk**: Edge case where a heading appears within 10 lines but is not the intended target (e.g., a heading about "Error" in a different context like "Error Type Categories"). → **Mitigation**: This is exactly what section-scoping solves — if there's a different heading between the table and the error-related heading, they're in different sections. The heading regex itself remains unchanged, so headings that genuinely introduce error-handling content are still matched.
