# Plan: Consolidate legacy-compatibility paths in RAG/DB schema and eventbus config

## Goal

Make and document an explicit keep/reduce/remove decision for each of the four
identified compatibility/migration paths (RAG `COALESCE` fallbacks, `etag`
null-fill, `mdq.sqlite` legacy-schema auto-recreate, eventbus removed-config-key
guard), and write down a single migration policy that explains, per database
(RAG, session, eventbus, workflow), whether incremental migration or
recreate-on-change is used and why — without changing eventbus implementation
(decision-recording only, per AGENTS.md Global Rule 8) and without removing any
compatibility path that current evidence shows is still actively needed.

## Design

### 1. `COALESCE(normalized_content, content)` — Decision: **KEEP**

Evidence (`scripts/rag/ingestion/ingester.py:508,535`; `scripts/mcp_servers/mdq/indexer.py`)
shows `normalized_content` is deliberately left `NULL`/empty for non-Japanese
chunks by the *current*, non-legacy ingestion path (`normalized_content or None`
is passed on every insert, not just for old rows). This is not dead
legacy-compatibility debt — it is the live contract for how English content is
stored. The RAG schema (`scripts/db/schema_sql.py`) declares `normalized_content
TEXT` nullable (no `NOT NULL DEFAULT`), and the `chunks_ai`/`chunks_ad`/`chunks_au`
triggers already apply the same `COALESCE` at insert/update time — `rebuild_fts`
in `maintenance.py` and `rag_maintenance_service.py` exist to keep the FTS index
consistent with that same rule when the trigger-driven state must be
regenerated in bulk. Removing the `COALESCE` would break FTS search for every
English chunk. Decision: keep as-is; add a one-line code comment in both
`rebuild_fts` methods stating this is a deliberate, permanent rule (not
transitional) so future readers do not attempt to remove it as "legacy."

### 2. `COALESCE(etag, ?)` / `COALESCE(last_modified, ?)` — Decision: **KEEP**

`etag_manager.py`'s `_update_null_fill` is invoked specifically on the branch
where `new_fetched_at is None` (see `update()`), i.e. when the caller has no
freshness signal at all. In that case the method must not blindly overwrite a
previously-known `etag`/`last_modified` with a fetch that carries no comparable
timestamp — the `COALESCE` here encodes "never regress a known value with an
unknown one," which is a correctness rule, not a legacy shim. Decision: keep
as-is; add a one-line comment above `_update_null_fill` making this rule
explicit.

### 3. `_migrate_legacy_chunks_schema` (`scripts/mcp_servers/mdq/db_schema.py`) — Decision: **REDUCE (add operator confirmation)**

Current behavior: `create_production_tables` unconditionally calls
`_migrate_legacy_chunks_schema` on every startup; that function unconditionally
checks `PRAGMA table_info(chunks)` and — only when it detects the legacy `id`
column — silently `DROP`s `chunks`, `chunks_fts`, and the three sync triggers,
with no backup and no operator confirmation, before `_create_chunks_table`
recreates the table empty. Because the legacy `chunks` table's data (`content`,
`doc_id`, etc.) is destroyed rather than migrated, any process restart against
a not-yet-migrated `mdq.sqlite` silently loses the indexed corpus (recoverable
only by re-indexing from source Markdown, which is possible but unannounced).

Decision: require an explicit operator opt-in before the destructive path
executes. Add an `MDQ_ALLOW_LEGACY_SCHEMA_MIGRATION` environment variable
(default unset/`false`): when the legacy schema is detected and the variable is
not set to a truthy value, log an ERROR describing the detected legacy schema,
the destructive action that would be taken, and the env var needed to proceed,
then raise `RuntimeError` to abort startup rather than silently dropping data.
When the variable is set, proceed with the existing drop-and-recreate behavior
(logged at its current INFO level, unchanged) and no re-index is triggered
automatically — re-indexing remains a separate, existing operational step.
This preserves today's default confirmation-free experience for the common
case (no legacy schema detected → no behavior change at all) while turning the
one data-loss branch from silent to explicit.

### 4. `_REMOVED_CONFIG_KEYS` (`scripts/eventbus/config.py`) — Decision: **KEEP, documentation only — no code change in this workflow**

Per AGENTS.md Global Rule 8 ("eventbus に関連する実装は絶対にしないこと"),
no code change to `scripts/eventbus/` may be made by this or any future
agent-driven implementation pass without a rule change; only debugging and
investigation are permitted there. This plan therefore records the decision as
**keep the hard-fail guard** — rationale: `load_config` is called once at
process startup (`scripts/eventbus/config.py:72`), so the cost of a hard
failure is a refused startup with a precise, actionable error message ("delete
them from {path}"), which is strictly safer than a "warn and continue" relax
that risks masking a stale config silently running with defaults the operator
did not intend. There is no evidence (UNK-02) that retiring the guard is
operationally necessary, and hard-fail-at-startup carries no ongoing runtime
cost. The decision is recorded here as **keep permanently**, with the
implementation of that decision (i.e., leaving the code exactly as-is) requiring
zero action. A follow-up issue is filed (see Implementation steps §4) purely to
carry this decision into the historical record with an explicit
"implementation prohibited" annotation, in case a future rule change ever
revisits Global Rule 8.

### 5. Migration policy across the four databases

Current state (verified against `scripts/db/create_schema.py` and
`scripts/db/schema_sql.py`):

| Database | Mechanism | Where |
|---|---|---|
| `workflow.sqlite` | Incremental: `_WORKFLOW_MIGRATIONS` list of `(id, ALTER TABLE ...)` tuples applied idempotently by `apply_workflow_migrations`, tracked via `workflow_schema_version` table | `schema_sql.py:252-294`, `create_schema.py:51-61,80-90` |
| `rag.sqlite` | Recreate-only: `CREATE TABLE/VIRTUAL TABLE IF NOT EXISTS` in `_RAG_SCHEMA_TEMPLATE`; no migration list | `schema_sql.py:26-83` |
| `session.sqlite` | Recreate-only: same pattern as RAG in `_SESSION_SCHEMA_TEMPLATE` | `schema_sql.py:85-144` |
| `eventbus.sqlite` | Recreate-only: `_EVENTBUS_SCHEMA`, no migration list (out of scope to change — Global Rule 8; documenting existing state only) | `schema_sql.py:221-244` |

Decision: this asymmetry is **intentionally kept**, not extended, in this
plan. `workflow.sqlite` needed incremental migration because its rows
(`tasks`, `attempts`) are long-lived, operationally significant records that
must survive a schema change in place; `rag.sqlite` and `session.sqlite` are
derived/rebuildable indexes and conversation logs respectively, both already
covered by an existing recreate/reindex operational story (`create_rag_schema`
already runs on top of `IF NOT EXISTS` DDL, and full reindex is the documented
recovery path referenced by this same requirement's background section).
Extending `apply_workflow_migrations`-style migrations to RAG/session now,
with no schema change currently pending for either, would be speculative
work forbidden by `skills/require-to-plan/workflow.md` Step 9 ("do not include
speculative steps — only steps required by the stated goal"). The policy to
write down (in `schema_sql.py`) is: *use the `apply_workflow_migrations`
pattern for any database whose rows are non-reindexable operational state
(currently only `workflow.sqlite`); use recreate-on-change (`IF NOT EXISTS`
DDL, no migration list) for any database whose contents can be safely
regenerated from an upstream source (currently `rag.sqlite` via re-index,
`session.sqlite` has no such property but has no history of in-place column
additions to date — flagged as a documentation gap, not a code gap, addressed
by writing the policy explicitly rather than silently continuing to have no
stated policy)*.

## Risks

- **Risk**: The new `MDQ_ALLOW_LEGACY_SCHEMA_MIGRATION` gate could break an
  existing automated deployment that currently relies on the silent
  auto-migration succeeding without any env var set (likelihood: low —
  `rg` found no reference to this behavior in `deploy/` or `tools/`).
  → **Mitigation**: default-unset behavior only changes outcome when a legacy
  schema is actually detected (i.e., only on an old `mdq.sqlite` that has never
  been migrated); a freshly-created or already-migrated DB is unaffected.
  Document the env var in the function's docstring and in the raised error
  message so any operator who hits it has a one-line fix.
- **Risk**: Adding comments/docstrings near `COALESCE` usages could be
  mistaken later for a TODO to remove them, defeating the purpose of recording
  "keep" (likelihood: low). → **Mitigation**: word the comments as explicit
  permanent-rule statements ("not legacy compatibility"), not as a decision
  still open for reconsideration.
- **Risk**: The eventbus decision issue could later be misread as authorizing
  implementation (likelihood: low, but consequential given Global Rule 8).
  → **Mitigation**: the issue file header explicitly states "IMPLEMENTATION
  PROHIBITED" and cites Global Rule 8 by name, per the task's own instruction.
- **Risk**: Recreate-on-change policy for `session.sqlite` is described as a
  "documentation gap, not a code gap" (Design §5) but `session.sqlite` holds
  conversation history that is not trivially re-derivable like a RAG index
  (likelihood: medium — a future in-place column addition to `messages`/
  `memories` would currently have no migration path and could force a lossy
  recreate). → **Mitigation**: not fully resolved in this plan; filed as a
  risk issue (see below) rather than silently accepted, since it cannot be
  mitigated without either implementing a migration mechanism now (out of
  scope — no pending schema change to justify it) or accepting the gap
  (a judgment call beyond this plan's decision authority).

This last risk is not mitigable within this plan's scope (Design §5 explicitly
excludes speculative migration-mechanism work with no pending schema change),
so it is filed as `issues/20260819-183436_risks.md` for a maintainer decision
on whether `session.sqlite` should be reclassified as needing incremental
migration ahead of any concrete schema-change need.
