# Plan: Replace compatibility tests and align documentation with the strict contracts

## Goal

Once the six dependency strict-contract requirements land, delete every remaining test
that asserts acceptance of a removed MCP/RAG compatibility format and replace it with an
explicit rejection test, and rewrite the MCP/RAG/tool-routing documentation that still
describes `input_schema`, legacy singular `resource_scope`, or backward-compatibility
constructor parameters as currently supported — so no test or doc in the repository
still pins or documents behavior the strict-contract work removed.

## Design

No production code, module, or interface changes in this plan's own remaining scope —
all production-code and test-editing work for the strict-contract behavior itself is
already assigned to the five dependency plans listed under Out-of-Scope. This plan's
design is limited to:
1. Documentation correction: replace "supported alias" framing with "removed, only the
   strict field is supported" framing in the four files identified above, matching the
   exact field names (`inputSchema`, `resource_scope_kind`, `resource_scope_keys`) the
   implementation enforces once the dependencies land.
2. A gated final-verification checklist run once all six dependencies are merged,
   re-running the source requirement's own `rg` validation search and rejection-coverage
   checklist against the then-current repository state, and adding any single missing
   rejection test found at that time (expected to be zero or near-zero given the
   dependency plans' own coverage, per Assumption A1/UNK-01).

## Risks

- **Risk**: This plan is executed before all six dependency plans actually land in
  `scripts/`, causing Phase 2/3 doc and verification work to describe behavior that
  does not yet exist in code (likelihood: medium, given five separate dependency plans
  must each independently reach `plans/done/` first) → **Mitigation**: Phase 1's gate
  step is mandatory and blocking; do not begin Phase 2 until the gate passes and is
  re-verified against the actual merged `scripts/` state, not against the dependency
  plans' text alone.
- **Risk**: One or more of the five dependency plans is revised during its own
  implementation (e.g. a different rejection-test shape than what this plan's
  Out-of-Scope section describes today), leaving a gap this plan did not anticipate
  (likelihood: low-medium) → **Mitigation**: Phase 1's re-verification step and Phase 3's
  gap-fill step exist specifically to catch and close any such gap before declaring the
  source requirement's acceptance criteria met.
- **Risk**: `docs/00_governance_05_deprecated-items.md`'s new entries are added with
  wording that could be misread as "still available as an alias" rather than clearly
  historical (likelihood: low) → **Mitigation**: follow the existing entries' phrasing
  pattern exactly (e.g. "Removed; X is now required") and apply the source
  requirement's own acceptance criterion — "cannot be read as available aliases or
  migration paths" — as the explicit review bar before finalizing Phase 2.
