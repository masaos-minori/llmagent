## Goal
- Build one startup state machine so `RuntimeToolRegistry` publication only completes after server eligibility (`StartupMode`), discovery results, required-tool schemas, and fatal findings have all been validated, and so a disabled (`StartupMode.NONE`) server can never be probed, transported to, routed to, or exposed to the LLM.

## Priority
High

## Scope
- **In-Scope**:
  - Excluding `StartupMode.NONE` servers from `/v1/tools` discovery, transport construction, routing, and LLM-facing tool definitions.
  - Enforcing the startup-mode reject check at the shared MCP invocation boundary (`ToolTransportInvoker`/`ToolExecutor`).
  - Escalating malformed/missing required-server tool entries to FATAL.
  - Reordering registry build/publish so it happens off-path and only after all fatal-eligible checks pass.
  - Adding a registry-readiness gate that blocks tool execution and LLM tool-definition generation until publication completes.
  - Mode-matrix, required/optional-server, duplicate-tool, startup-order, and concurrent-access regression tests.
- **Out-of-Scope**:
  - `mcpagent05`'s invocation-gate unification implementation itself (only the shared boundary this Plan touches must remain reconcilable with it — see Dependencies).
  - `mcpagent08`'s duplicate-tool ownership/routing policy implementation itself (duplicate detection in `mcp_tool_discovery.py` already exists and is only referenced, not redesigned, here).
  - Config-reload-time registry mutation (`scripts/agent/services/config_reload.py`'s `apply_policy()` path) — that is `mcpagent04`'s (runtime-policy-reload-reversibility) scope; this Plan's atomicity guarantee covers startup-time publication only (see Risks).
  - Any MCP server business logic unrelated to the startup/discovery/registry-publication path.

## Background
N/A: covered by Summary — this Issue is a direct code-level finding across the MCP startup/discovery/registry path, not derived from a prior design decision document.

## Problem
Adversarial verification (Step 2) confirmed every claim in the Issue's Problem statement against current source:
- `McpToolDiscoveryService.discover_all()` (`scripts/agent/services/mcp_tool_discovery.py`) iterates `ctx.cfg.mcp.mcp_servers.items()` and skips a server only when `cfg.transport != TransportType.HTTP or not cfg.url` — it does **not** check `cfg.startup_mode`, so a `StartupMode.NONE` server with an HTTP transport and a configured URL is fetched over the network during discovery. The same gap exists a second time in `agent.services.tool_validation._collect_server_tool_names()` (used by `_check_tool_definitions()`), which is not in the Issue's original Target Files list — see Design for this correction.
- `RuntimeToolRegistry.__init__` (`scripts/shared/runtime_tool_registry.py`) excludes a tool only when its `server_key` is in `unavailable_servers` (servers that failed discovery) — there is no equivalent exclusion for a disabled (`startup_mode=NONE`) server's tools, so a disabled server that still answers `/v1/tools` would have its tools registered and exposed via `llm_tool_definitions()`.
- `ToolTransportInvoker.__init__` (`scripts/shared/tool_transport_invoker.py`) builds an `HttpTransport` for every entry in `server_configs` unconditionally — a disabled server still gets a live transport object.
- `ToolTransportInvoker.invoke()` (the base class's public method) has no startup-mode check at all. Only `ToolExecutor._raw_execute()` (via `_run_gate_chain()` → `_check_startup_mode()`) rejects `StartupMode.NONE`. Because `ToolExecutor` subclasses `ToolTransportInvoker` and inherits `invoke()` unmodified, a caller holding a `ToolExecutor` (or `ToolTransportInvoker`) reference can call `.invoke(server_key, ...)` directly and bypass the startup-mode gate — confirming the Issue's hedged claim ("may allow bypassing"). `rg` found no production call site of `.invoke(` today (only `tests/shared/test_tool_transport_invoker.py` and `tests/shared/test_tool_transport_invoker_merge.py` call it) — this is a latent, not currently-exploited, gap.
- `McpToolDiscoveryService._validate_and_normalize_entry()`'s docstring and code confirm every per-tool schema violation is a WARNING ("Schema errors are per-tool WARNING findings, not FATAL"), regardless of the owning server's `McpServerConfig.required` flag — confirming "malformed required-server tool entries may not be treated as fatal." There is also no existing check that every `tool_name` declared in a required server's `McpServerConfig.tool_names` was actually discovered — "verify every required tool is discovered and has a valid schema" is unimplemented, not merely under-tested.
- Adversarial verification **narrows** one Issue claim: "A FATAL startup finding is not guaranteed to convert into a startup failure before the agent begins accepting requests" is only partially true today. `StartupValidationPipeline.check_services()` (`scripts/agent/startup_validation.py`) aggregates FATAL findings into `pipeline.has_fatal`; `StartupOrchestrator._check_services()` (`scripts/agent/startup.py`) raises `RuntimeError` when `has_fatal` is true; `AgentREPL.run()` (`scripts/agent/repl.py`) re-raises that exception and never reaches `self._input_loop.run(...)` — so a FATAL finding **does** currently prevent request acceptance through this path. The real gap is narrower and more concrete: inside `check_services()`, `ctx.services_required.runtime_tools = discovery.registry` and `ctx.services_required.tools.set_runtime_registry(discovery.registry)` are executed immediately after `discover_all()` returns — before the pipeline's own fatal-aggregation step (which runs after routing-drift/safety-tier/RAG checks later in the same method) and before `_check_services()`'s `has_fatal` check. The registry is wired into live service state before its own fatal-worthiness (or a later check's fatal-worthiness) is known; the current single-threaded sequential `await` chain has no concurrent reader in that window today, but nothing in the code structure prevents one, and the Issue's stated intent (build off-path, publish atomically) is a real, unimplemented gap, not a false claim.
- The two "Unknown" items in the Issue's Target Files are resolved by repository evidence: `scripts/agent/startup.py` exists as a single file (no `scripts/agent/startup/` directory), and the registry-wiring code that must change lives specifically in `scripts/agent/startup_validation.py` (a `startup_*.py` sibling), not `startup.py` itself. `tests/agent/test_startup.py` exists and is the correct test target (no `tests/test_agent_startup.py` exists anywhere under `tests/`).

## Reason for change
Disabled-server exclusion, fatal discovery handling, required-tool validation, and policy-before-publication are parts of one startup state machine. Implementing them separately could publish a partially valid registry, expose disabled tools, or allow the agent to accept work after a fatal discovery result.

## Implementation intent
Build and publish `RuntimeToolRegistry` only after server eligibility (`StartupMode`), discovery results, required-tool schemas, fatal findings, and active policy have all been validated successfully; the agent remains unavailable until the complete registry is safe to expose. Concretely:
1. Filter every discovery loop (`mcp_tool_discovery.py`, `tool_validation.py`) on `cfg.startup_mode != StartupMode.NONE` in addition to the existing transport/URL check.
2. Stop constructing `HttpTransport` instances for `StartupMode.NONE` servers in `ToolTransportInvoker.__init__`.
3. Give `ToolTransportInvoker` its own `server_configs`/`startup_mode` awareness and move the startup-mode reject check into `invoke()` itself (the method both `ToolExecutor.execute()` and any direct caller ultimately route through) rather than only in `ToolExecutor`'s subclass-only gate chain — this keeps a single shared invocation boundary, consistent with `mcpagent05`'s framing of this same boundary (see Dependencies), rather than hiding `invoke()` behind a rename.
4. Extend `RuntimeToolRegistry`'s exclusion mechanism (currently `unavailable_servers`-only) to also exclude disabled-server tools from `all_tools()`/`resolve()`/`llm_tool_definitions()`, while allowing `diagnostics()` to still surface them (marked disabled, not executable) — this is the concrete answer to "define whether disabled servers participate in drift diagnostics without becoming routable."
5. Add a `required`-aware escalation in `mcp_tool_discovery.py`: a malformed or missing tool entry belonging to a `required=True` server becomes FATAL; the same finding for an optional server stays WARNING.
6. Add a new required-tool-presence check: after discovery, for every required server's configured `tool_names`, confirm each name was actually discovered (present in the built registry) — missing means FATAL.
7. Restructure `StartupValidationPipeline.check_services()` so discovery builds the registry, evaluates it, and only calls `ctx.services_required.tools.set_runtime_registry(...)` / assigns `ctx.services_required.runtime_tools` after the method has finished evaluating every fatal-eligible check with no FATAL outcome recorded so far for the registry-affecting checks (mcp_tool_discovery, duplicate-tool, required-tool). On a FATAL outcome, the previous/empty registry state is not replaced.
8. Add an explicit registry-readiness gate on `AppServices` (`scripts/agent/context.py`) that `ToolExecutor`'s gate chain and the LLM-tool-definition read path can both observe, so execution is blocked while publication is in progress — defense-in-depth for the ordering restructured in step 7, and the concrete mechanism for "prevent tool execution while registry initialization is incomplete."

## Requirements
- `REQ-001`: Exclude `StartupMode.NONE` servers from live `/v1/tools` discovery in both `McpToolDiscoveryService.discover_all()` and `agent.services.tool_validation._collect_server_tool_names()`.
- `REQ-002`: Do not construct an `HttpTransport` for a `StartupMode.NONE` server in `ToolTransportInvoker.__init__`.
- `REQ-003`: Extend `RuntimeToolRegistry`'s exclusion mechanism to exclude disabled-server tools from `all_tools()`, `resolve()`, `get()`, and `llm_tool_definitions()`.
- `REQ-004`: Enforce the startup-mode reject check at the shared invocation boundary (`ToolTransportInvoker.invoke()`), so both `ToolExecutor.execute()`'s name-based path and any direct server-key `invoke()` call reject `StartupMode.NONE` identically.
- `REQ-005`: Let `RuntimeToolRegistry.diagnostics()` continue to report a disabled server's tools (marked disabled) without them being routable/executable/LLM-visible (the REQ-003 exclusion must not remove them from `diagnostics()`).
- `REQ-006`: Add a mode-matrix test suite (`StartupMode.NONE` / `PERSISTENT` / `SUBPROCESS`) covering discovery inclusion/exclusion, transport creation, and invocation gating.
- `REQ-007`: Add regression coverage protecting the existing FATAL-to-startup-failure conversion (`pipeline.has_fatal` → `RuntimeError` → `AgentREPL.run()` re-raise → input loop never starts) against future refactors.
- `REQ-008`: Escalate a malformed required-server tool entry to FATAL in `McpToolDiscoveryService._validate_and_normalize_entry()` (via its caller) when the owning server's `McpServerConfig.required` is `True`; keep it WARNING for optional servers.
- `REQ-009`: Add a required-tool-presence check: every `tool_name` declared in a required server's `McpServerConfig.tool_names` must be discovered with a valid schema, or the startup is FATAL.
- `REQ-010`: Add regression coverage confirming optional-server discovery failures (unreachable, malformed) remain WARNING-only and never become executable/routable.
- `REQ-011`: Restructure `StartupValidationPipeline.check_services()` (and its `startup.py` caller) so the discovered registry is built off-path and is only wired into `AppServices.runtime_tools` / `ToolExecutor.set_runtime_registry()` after all fatal-eligible checks affecting the registry have been evaluated with no FATAL outcome.
- `REQ-012`: Add a registry-readiness gate on `AppServices` (`scripts/agent/context.py`) that `ToolExecutor`'s gate chain checks before dispatch, so no tool execution or LLM-facing tool-definition generation can use a registry whose publication is incomplete.
- `REQ-013`: Add startup-order and concurrent-access regression tests verifying the discovery → validation → policy application → executor wiring → LLM-definition publication → request-acceptance ordering, and that a reader never observes a partially-published registry.

## Acceptance criteria
- No network request is sent to a disabled server during discovery or tool execution. (`REQ-001`, `REQ-002`)
- No disabled-server tool appears in routing or LLM-facing definitions. (`REQ-003`)
- Both name-based execution and any server-key invocation path reject disabled servers. (`REQ-004`)
- Diagnostics can report disabled servers without making them executable. (`REQ-005`)
- The process does not enter the ready state when any fatal finding exists. (`REQ-007`, `REQ-011`)
- Duplicate tool ownership always prevents startup. (`REQ-011`, `REQ-013` — protects the existing always-FATAL duplicate-tool behavior in `mcp_tool_discovery.py`)
- A required server with an invalid or missing required tool prevents startup. (`REQ-008`, `REQ-009`)
- Optional-server degradation is reported without exposing unavailable tools. (`REQ-010`)
- No request can execute a tool before policy application completes. (`REQ-012`)
- No disallowed tool is exposed to the LLM during startup or reload. (`REQ-012` for startup; reload is out-of-scope — see Risks)
- Fatal discovery findings prevent registry publication. (`REQ-011`)
- Registry replacement is atomic for readers. (`REQ-011`, `REQ-013`)

## Design
The current startup call chain is `AgentREPL.run()` → `StartupOrchestrator.run()` → (`ComponentInitializer.initialize()`, `McpServerStarter.start_servers()`, `McpServerStarter.verify_health()`, `StartupValidationPipeline.check_services()`, `ApprovalRecovery.recover()`, `PromptSetup.setup_prompt()`) → `AgentREPL._input_loop.run()`. `check_services()` already aggregates FATAL findings into a `StartupValidationResult` that `StartupOrchestrator._check_services()` turns into a `RuntimeError`, which `repl.py` re-raises before the input loop starts — this part of the state machine already works and must not regress (REQ-007).

The concrete defect this Plan fixes is registry **publication timing**, not fatal-detection: `check_services()` wires the freshly-discovered registry into live `AppServices` state (`ctx.services_required.runtime_tools`, `ToolExecutor.set_runtime_registry()`) immediately after `discover_all()` returns, several checks before the method's own fatal-aggregation. The fix is to defer that wiring to the end of `check_services()`, conditioned on no FATAL outcome having been recorded for any registry-affecting check (mcp_tool_discovery, duplicate-tool, required-tool-presence), and to add an explicit readiness flag on `AppServices` (REQ-012) that `ToolExecutor`'s gate chain consults, so that even a future code path that reorders checks again fails closed rather than silently exposing an unvalidated registry.

`StartupMode.NONE` exclusion must be applied at four independent points, because none of them currently derive from a single shared filter: the discovery loop (`mcp_tool_discovery.py`, `tool_validation.py`), transport construction (`tool_transport_invoker.py`), the registry's own tool-inclusion logic (`runtime_tool_registry.py`), and the invocation boundary (`invoke()`). `McpServerConfig.is_disabled` (already defined in `mcp_config.py`, unmodified by this Plan) is the single predicate all four call sites should share, to avoid four independent re-derivations of "is this server disabled" drifting apart over time.

`RuntimeToolRegistry.diagnostics()` must keep surfacing a disabled server's tools (REQ-005) because it already reads from `self._tools` (the post-exclusion dict) for the `/mcp status` command — the design decision is that a disabled server's tools should be visible in this diagnostic view (marked disabled, e.g. via a `disabled_reason` derived from `startup_mode`) without being present in `all_tools()`/`resolve()`/`llm_tool_definitions()`. This requires `RuntimeToolRegistry` to track disabled-server tools in a form `diagnostics()` can still read even though `resolve()`/`get()`/`all_tools()` must not return them — the implementation-procedure phase should choose between a second internal dict (mirroring `_unavailable_servers`'s existing pattern) or a per-tool "disabled" marker, whichever more cleanly reuses the existing `unavailable_servers`-style exclusion the class already has.

## Risks

- **Risk**: This Plan's atomicity guarantee (REQ-011/013) covers startup publication only; `config_reload.py`'s `apply_policy()` mutates the same `RuntimeToolRegistry` object at runtime without the same guarantee, so a config-reload race is not closed by this Plan. → **Mitigation**: documented as UNK-02 and as an explicit Out-of-Scope item; flagged for `mcpagent04` to confirm ownership when it reaches planning.
- **Risk**: Required-tool-presence and required-tool-schema FATAL escalation (REQ-008/009) could turn a previously-WARNING-only production deployment into one that fails to start, if a currently-deployed required server has a malformed or missing tool today. → **Mitigation**: this is the Issue's explicit intent (Acceptance Criteria: "A required server with an invalid or missing required tool prevents startup"); implementation must run the new checks against current `config/*_mcp_server.toml` data before merge to confirm no currently-required server would newly fail startup, and report the outcome as part of the implementation phase's validation.
