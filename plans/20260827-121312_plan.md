## Background

end-to-end (see git history of this file for the original Goal/Requirements). Before
this Plan's `UNK-01` (stampede-protection disposition) could be resolved and
implementation could begin, an independent Plan
(`plans/done/20260826-120000_plan.md`, from `issues/done/20260826_delete_tool_executor_cache_issue.md`)
was drafted and implemented in parallel, landing on `origin/master` as commit
`fa659963d` and merged into this branch (`eebf2bada`) on 2026-08-27.

Re-verification against current source (2026-08-27, post-merge) found the parallel
implementation:
- **Completed**: removed `ToolExecutor._cache`, `_execute_with_cache()`,
  `_store_and_evict()`, `stat_cache_hits`, `clear_cache()`, `apply_config()`
  entirely, the `cache_ttl`/`cache_max_size` constructor parameters, and the
  `CacheEntry` import — confirmed via `rg -n
  "cache_ttl|cache_max_size|stat_cache_hits|CacheEntry|clear_cache"

  resolving this Plan's `UNK-01` in the *opposite* direction from this Plan's
  proposed default ("keep it"). `execute()` now calls `_raw_execute()` directly with
  no `is_side_effect()` branch at all (confirmed via `grep -n "def execute" -A5
  scripts/shared/tool_executor.py`) — the side-effecting-tool cache-bypass
  distinction this Plan's Out-of-Scope asked to preserve is moot now that there is

  `_safe()` before `getattr()` is ever called — a test-double divergence from the real
  `ToolExecutor` instance used in production. **This regression was fixed directly in
  this same plan-to-implementation-procedure cycle** (2026-08-27, before this Plan
  document was finalized): removed the dead `cache_hits` field from `StatsViewModel`
  (`agent/commands/models.py`) and its two consumers in `cmd_config_stats.py` (the
  `_safe(...)` read and the `Cache hits` render line) — this was the correct fix per
  this Plan's own original `REQ-007`, which the parallel implementation never
  completed.

## Problem
Two concrete gaps remain after the parallel implementation and this cycle's direct
fix, both confirmed by direct repository re-verification (2026-08-27):
1. `ToolConfig` (`scripts/agent/config_dataclasses.py`) still declares
   `tool_cache_ttl: float = 300.0` (line 176) and `tool_cache_max_size: int = 200`
   (line 178), and still imports and calls `validate_tool_cache_max_size` as
   `_v_tool_cms` (lines 91, 235) — both fields are now write-only dead
   configuration: nothing reads them since `ToolExecutor` no longer accepts a
   `cache_ttl`/`cache_max_size` constructor argument (confirmed via `rg -n
   "tool_cache_ttl|tool_cache_max_size" scripts/agent/factory.py` returning no
   matches).
2. `scripts/agent/config_builders.py` (lines 277-278, 308-309) still reads
   `tool_cache_ttl`/`tool_cache_max_size` from raw TOML config and passes them into
   `ToolConfig` construction — the loader half of the same dead configuration.

## Reason for change
Leaving `ToolConfig.tool_cache_ttl`/`tool_cache_max_size` in place after their sole
consumer (`ToolExecutor`'s constructor) was removed makes the config appear
tunable to an operator or future contributor when it no longer has any effect —
the same class of documentation/config-drift problem
`issues/done/20260825_docs_tool_cache_removal_stale_docs_issue.md` was filed to
prevent for `docs/*.md`, now manifesting in the config schema itself. The orphaned
`validate_tool_cache_max_size` validator compounds this: it validates a field that
does nothing, giving a false impression that the value is meaningfully enforced.

## Implementation intent
Remove the two dead fields from `ToolConfig` and their TOML-loading plumbing in the
same change as removing the now-purposeless `validate_tool_cache_max_size`
validator, mirroring the field/validator/plumbing split already used elsewhere in
this config module. No behavior change results — nothing currently reads these
values in any way that affects running behavior (their only effect was setting
`ToolExecutor` constructor arguments that no longer exist).

## Design
`REQ-001`/`REQ-002`/`REQ-003` must land together in one change: `REQ-001` removes
`ToolConfig`'s fields and its validator wiring; `REQ-003` removes the validator
function `REQ-001`'s import pointed at; `REQ-002` removes the loader-side plumbing
that populates the fields `REQ-001` deletes. Landing any one without the others
leaves a dangling import (`REQ-001` without `REQ-003`) or an unused local variable
(`REQ-002`'s `tool_cache_ttl`/`tool_cache_max_size` locals, if `REQ-001` hasn't
removed the field they're passed into).

`REQ-004` (the `cmd_config_stats.py` fix) is already complete and independent of
`REQ-001`–`REQ-003` — it addresses a different file pair with no shared symbol.

This Plan does not re-open `UNK-01` (stampede protection) or propose any change to
`ToolExecutor` itself — that decision was made by the parallel implementation and is
accepted as-is (see Background, Assumptions).
