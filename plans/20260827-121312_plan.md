## Goal
- Remove `ToolExecutor`'s internal TTL+LRU tool-result cache (`_cache`,
  `_execute_with_cache`, `_store_and_evict`, `stat_cache_hits`, `clear_cache()`, the
  `cache_ttl`/`cache_max_size` constructor parameters, and `apply_config(cache_ttl=...)`)
  end-to-end — from `ToolExecutor` itself through its config surface, its production
  call sites, and its test suite — so `execute()` always re-executes non-side-effecting
  tools instead of returning a cached result, unblocking the three already-`Blocked`
  follow-up Plans that depend on this cache no longer existing.

## Priority
Medium

## Scope
- **In-Scope**:
  - `ToolExecutor`'s cache storage/lookup/eviction logic and the `cache_ttl`/
    `cache_max_size` configuration surface, end-to-end (source, config, production call
    sites, tests).
  - Resolving the stampede-protection disposition (keep vs. remove) as part of this
    Plan's Design, since it directly determines how `execute()` must be rewritten.
  - The `Cache hits` `/stats` line in `cmd_config_stats.py`.
- **Out-of-Scope**:
  - Wiring in or unifying with `ToolResultCache` (`scripts/shared/tool_cache.py`) — that
    is `issues/done/20260821_09_issue.md`'s separate, narrower scope (unify or
    document, not remove). This Plan removes `ToolExecutor`'s own cache outright and
    does not touch `ToolResultCache`.
  - Any change to `is_side_effect()` or the side-effecting-tool bypass logic.
  - Implementing the three follow-up issues' own scopes
    (`cfgreload_toolexecutor_cache_wiring`, `config_validators_dead_cache_validator`,
    `docs_tool_cache_removal_stale_docs`) — this Plan only removes the prerequisite
    cache; their own Plans (already drafted and `Blocked`) cover their specific
    follow-up work and are expected to proceed once this Plan lands.
  - Any change to `_raw_execute()`'s own execution/transport logic beyond how it is
    reached.
  - The 14 documentation files covered by
    `issues/done/20260825_docs_tool_cache_removal_stale_docs_issue.md` — documentation
    is out of scope for this document-only (`issue-to-plan`) phase in general, and that
    issue's own Plan already covers this Plan's target docs.

## Reason for change
Three already-filed follow-up issues (and their corresponding Plans, all currently
`Blocked`) depend on this cache no longer existing before they can proceed. Landing
this removal unblocks all three. Per `issues/done/20260821_09_issue.md`, it also
resolves the two-cache-implementations ambiguity in the removed cache's own favor.

No independent functional/performance motivation for removing tool-result caching
itself was found during investigation (in `issues/`, `requires/`, or `plans/`,
including `done/` subdirectories, as of 2026-08-27) beyond the three follow-up issues'
shared precondition — this is recorded rather than invented (see Assumptions).

## Implementation intent
Remove the cache storage, lookup, and eviction logic from `ToolExecutor` entirely — do
not replace it with a different cache implementation (do not redirect to
`ToolResultCache`). Resolve the stampede-protection question explicitly as part of this
Plan's Design (see below) rather than leaving it for implementation time. Remove the
`cache_ttl`/`cache_max_size` configuration surface and the `Cache hits` stat output
end-to-end across every layer identified in Problem above, not just at the
`ToolExecutor` boundary.

## Design
### Task-size classification: Path B
This Issue affects 9 distinct production/config files plus 10 test files (well beyond
Path A's ≤3-file threshold) and changes `ToolExecutor`'s public constructor signature
and `apply_config()`'s public signature — both public/runtime-facing interface
changes. Per `skills/issue-to-plan/SKILL.md` Routing, this mandates Path B: full
architecture, dependency graphing, historical, and operational analysis was performed
(see Affected areas and the sections below), not only direct verification.

### Architecture analysis
`rg "^from|^import" scripts/shared/tool_executor.py` (2026-08-27) shows

(`http_transport`, `json_utils`, `mcp_config`, `route_resolver`, `tool_cache`,

### Operational dependency inspection
`ToolExecutor` is constructed once per agent process (`factory.py`) as an in-process
object, not a separate service with its own port/socket — `lsof`-based inspection
(designed for MCP servers/DB locks) does not apply here. No live process lock or
external dependency is at risk from this change; the change is confined to
in-process Python object construction and method bodies.

### Stampede-protection disposition (resolves UNK-01's default, pending maintainer confirmation)
`_execute_with_stampede_protection()` shares an inflight `asyncio.Future` per
`cache_key` across concurrent callers via `self._inflight` — a dict entirely separate
from `self._cache`. It never reads or writes the cache being removed. Its purpose
(preventing duplicate concurrent executions of the same tool+args) is orthogonal to
whether results are cached afterward: even with no cache at all, two concurrent
identical calls arriving at the same instant would otherwise both dispatch to the MCP
server unnecessarily, which is exactly the "stampede" this mechanism prevents.

This Plan's Design therefore defaults to **keeping** `_execute_with_stampede_protection()`
as an independent concurrency guard, with `execute()` calling it directly (via a
renamed or refactored entry point that no longer implies caching) instead of routing
through the now-removed `_execute_with_cache()`. This contradicts
`issues/done/20260825_docs_tool_cache_removal_stale_docs_issue.md`'s stated assumption
that "stampede protection removed" is the end state — see `UNK-01` (Blocking) for the
required maintainer confirmation before implementation proceeds. If the maintainer
instead confirms stampede protection should be removed too, `REQ-002` and `REQ-008`
must be revised accordingly (remove `_execute_with_stampede_protection()` and its
`self._inflight` state instead of preserving them), and this Design section's
conclusion must be corrected in place.
