# Plan — Implement missing guard layers for high-risk tool categories (MCP-006)

## Goal
Close Known Issue MCP-006 by bringing every high-risk MCP server's Layered protection
layer coverage into conformance with `security_02_high-risk-tool-common-policy.md` —
either implement the missing command-specific guards, postcondition verification, and
audit before/after + approval correlation, or document each layer as not applicable in
that tool's own document — then remove the MCP-006 entry from `governance_03_issue-and-uncertainty-management.md`.

## Priority
Medium

## Scope
- **In-Scope**: Per-category re-audit of the five Layered protection layers for git, mdq, file-write, file-delete, shell, github; implementing the minimal missing layer or documenting it as not applicable; updating each tool's own document with its current layer coverage; updating the audit-record schema doc; removing the MCP-006 ledger entry once every category is resolved.
- **Out-of-Scope**: Redesigning the five-layer model or its layer definitions; changing the common guard layer (allowlist + read-only/write gating); adding new high-risk tool categories; non-high-risk MCP servers; reworking approval-execution flow outside the five layers.

## Background
The Layered protection model (`security_02_high-risk-tool-common-policy.md`) defines five
layers: Agent approval, Common per-server guard, Command-specific guard, Postcondition
verification, Audit. Every high-risk server implements the common guard, but coverage of
the remaining four layers is uneven. This is registered as Known Issue MCP-006 in
`governance_03_issue-and-uncertainty-management.md` Part 1 (Area: MCP, Status: open,
Severity: Medium, Type: design-gap). The Known Issue Registration Rule in
`governance_01_documentation-policy.md` requires the discrepancy stay tracked until
resolved, so this plan resolves it.

## Problem
Per MCP-006's observed-implementation row (verified against current source):
- Postcondition verification exists only in `scripts/mcp_servers/git/repository_state.py`; other categories lack a comparable check.
- Audit records carry no approval correlation across servers. Before/after state is captured only by `git-mcp` (`_serialize_state` pre/post repository-state conditions emitted in `git_server.py`); the other servers omit it or write it unstructured. `file-write-mcp` writes no audit record at all; `file-delete-mcp` writes an audit log but without before/after or correlation.
- Command-specific guards exist for git (ref/remote/protected-branch), mdq (path/symlink), file-delete (recursive-root rejection), shell (command allowlist/cwd/env). file-write and github have none beyond the common guard and configured denylists.
- github ships `github_service_security.py` with command-specific guards (`_clamp_per_page`, `_assert_allowed_repo`, `_assert_allowed_path`, `_assert_allowed_branch`) and a configurable audit log (`_write_github_audit_log`), but the log format `{ts} op={op} {fields}` carries no before/after state or approval correlation.

## Reason for change
Leaving MCP-006 open keeps the policy describing an unimplemented gap and leaves a
defense-in-depth hole: partial/unintended results are not post-verified and audit records
cannot be tied to the approving call. Resolving it either restores the missing layer or
formally documents why it does not apply — the resolution path the Known Issue template
prescribes.

## Implementation intent
Work per category. For each of git, mdq, file-write, file-delete, shell, github, decide
for every Layered protection layer whether to (a) implement the missing layer, or (b)
record in that tool's own document that the layer is not applicable. Prefer the minimal
change that achieves conformance. Reuse the git `repository_state.py` postcondition pattern
only where it generalizes (it does not verify checkout and its TOCTOU re-check is a
documented no-op, so fill those gaps rather than copying it wholesale). Add audit
before/after state plus approval correlation where a server currently omits them. Do not
redesign the common guard or the five-layer model. Once every category is either
implemented or documented-as-not-applicable, remove the MCP-006 entry.

## Requirements
- `REQ-001`: Re-derive each category's actual current five-layer coverage from live source before deciding implemented vs. not-applicable (never trust MCP-006's V22-01 snapshot).
- `REQ-002`: For each category, every command-specific guard is either implemented or documented as not applicable.
- `REQ-003`: For each category, postcondition verification is either implemented (reusing the git pattern where it generalizes, filling its checkout + TOCTOU gaps) or documented as not applicable.

- `REQ-007`: `security_02_high-risk-tool-common-policy.md` no longer describes an open coverage gap, and the MCP-006 entry is removed from `governance_03_issue-and-uncertainty-management.md` once every category is resolved.

## Design

verification (Step 2) confirmed the issue's claims against current source: MCP-006's
observed-implementation row matches live code (postcondition in git only; audit records
lack before/after/correlation; file-write writes no audit; github has guards + a
before/after-less audit log). The re-audit (REQ-001) is the first implementation step and

than forced server-side.

## Risks
- **Risk**: The re-audit (UNK-01) shows some layer needs substantial new implementation, so MCP-006 cannot be fully closed in this cycle. → **Mitigation**: Scope the heavy implementation as a follow-up; do NOT remove the MCP-006 entry until every category resolves implemented-or-N/A; document the residual as a new tracked item if needed.
- **Risk**: Adding audit before/after state changes the audit format and breaks consumers parsing the `{ts} op={op} {fields}` shape. → **Mitigation**: Extend (add fields) rather than rewrite; update `mcp_02_03_audit-logging-and-errors.md`; check audit consumers before changing format.
- **Risk**: Filling git's checkout postcondition or TOCTOU re-check changes checkout timing/behavior. → **Mitigation**: Keep the change scoped to post-operation state verification; regression-test the existing dry-run/detached-head paths.
- **Risk**: `file-write-mcp` audit write failure could break startup or a call. → **Mitigation**: Mirror `file-delete`'s audit-failure-is-logged-never-raised behavior.
