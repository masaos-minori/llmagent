# Plan: Write manual operator recovery runbook for workflow.sqlite / eventbus.sqlite

## Goal
Document the manual operator recovery procedure for `workflow.sqlite` and `eventbus.sqlite`, including confirming actual backup coverage before writing the runbook.

## Priority
Medium

## Scope
- **In-Scope**: Confirm backup coverage for workflow/eventbus via `rotate_all_dbs()`; write Operations runbook section describing manual recovery steps; cross-reference from ADR-008 Related Documents.
- **Out-of-Scope**: Implement new automatic backup/recovery code; change ADR-008's recovery policy itself.

## Background
ADR-008 (post-merge, 2026-08-31) Decision Details #20 / INV-18 establishes that `workflow.sqlite` and `eventbus.sqlite` corruption recovery is a manual operator action — automatic restoration is prohibited. No document currently describes what that manual recovery procedure actually consists of. The issue text claims "`rotate_all_dbs()` currently excludes both" but investigation of `scripts/db/rotation.py` shows this claim is incorrect: `rotate_all_dbs()` (line 72-78) explicitly archives all four databases including workflow and eventbus (lines 76-77: `wf_dest = rotate_workflow_db(archive_dir)` and `eb_dest = rotate_eventbus_db(archive_dir)`).

## Problem
The only Operations-facing statement about workflow/eventbus recovery today is the error detail string returned by the API (`action="no_recovery_allowed"`); there is no step-by-step procedure (e.g., what backup exists, how to validate a candidate, how to manually apply it, what to do if no backup exists).

## Reason for change
A documented policy without an accompanying runbook leaves operators unable to act when the documented scenario (workflow/eventbus corruption) actually occurs, defeating the purpose of documenting the policy at all.

## Implementation intent
Write an Operations runbook section describing the manual recovery procedure for `workflow.sqlite` and `eventbus.sqlite`. Since `rotate_all_dbs()` does archive these two databases (confirmed by reading `scripts/db/rotation.py` lines 76-77), the runbook can describe concrete restore steps rather than stating "no backup exists." However, the runbook must still address the case where backups have been rotated away beyond the operator's retention window.

## Requirements
- `REQ-001`: Runbook MUST accurately reflect current backup coverage (confirmed: `rotate_all_dbs()` archives all four databases including workflow/eventbus).
- `REQ-002`: Runbook MUST NOT contradict ADR-008's decision that automatic restoration is prohibited for workflow/eventbus domains.
- `REQ-003`: Runbook MUST cover: locating available backups, validating a candidate, applying it manually, and handling the case where no valid backup exists.
- `REQ-004`: ADR-008's Related Documents MUST reference the new/updated runbook section.

The runbook will follow this structure:
1. **Precondition check**: Confirm which backups exist in `/opt/llm/db/archive/` for workflow/eventbus
2. **Validate candidate**: Use SQLite integrity check on the archived copy
3. **Apply restore**: Copy validated archive over the corrupted live database
4. **Post-restore verification**: Re-run integrity check on restored database
5. **No backup available**: Data-loss acknowledgment / escalation path

Key finding from investigation: the issue text incorrectly states "`rotate_all_dbs()` currently excludes both" — the actual code confirms all four databases are archived (scripts/db/rotation.py lines 76-77).
