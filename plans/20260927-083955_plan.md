## Background
Three sibling implementation-procedure documents (`implementations/done/20260912-150000_01_scripts_eventbus_dlq_route_py.md`, `..._03_tests_eventbus_test_eventbus_dlq_py.md`, `..._04_tests_eventbus_test_eventbus_requeue_edge_cases_py.md`) all identically state: "The `dlq_imminent` field is no longer included since the original event's `delivery_failure_count` is no longer relevant after redelivery" — confirming its removal from the requeue response was a deliberate, cross-documented design decision. Separately, commit `933b4340` ("feat(eventbus): migrate to lineage model for DLQ redelivery", 2026-09-12) both migrated `dlq_route.py` to the lineage model (`redeliver_event()`, returning `new_event_id`) and added a `redelivered_from`-existence check "as a concurrency guard" in `redeliver_event()`, intended (per its docstring) "to prevent duplicate redeliveries" from "two concurrent requests" racing on the same `dlq_at IS NOT NULL` check. However, this same guard also unconditionally blocks any *later, sequential, legitimate* re-redeliver of an original event_id that failed again and was re-promoted back into DLQ — exactly the scenario `test_repeated_requeue_increments_dlq_requeue_count` exercises. An earlier version of this same test was recorded as passing (`✓`) in `implementations/done/20260630-112000_eventbus_dlq_requeue_path_unification.md` (2026-06-30, predating the Sept-12 guard), suggesting the guard's later addition may have introduced this regression as an unintended side effect of solving the narrower concurrency race.

## Problem
- `test_requeue_event_at_max_retry_then_re_promoted`: `KeyError: 'dlq_imminent'` — the field was deliberately removed from the response (per the 3 corroborating implementation-procedure docs); this test's assertion was never removed to match.
- `test_requeue_returns_dlq_imminent_when_delivery_failure_count_gte_max_retry`: same `KeyError: 'dlq_imminent'`, same confirmed cause.
- `test_repeated_requeue_increments_dlq_requeue_count`: the second requeue call (on the same original `event_id`, after `sweep_orphans` re-promotes it to DLQ) returns 409 instead of the test's expected 200, because `redeliver_event()`'s `redelivered_from`-existence guard treats "this original event_id was ever redelivered before" as permanently disqualifying — even though the event has legitimately re-entered DLQ since then via `sweep_orphans`.

## Reason for change
The `dlq_imminent` fix is a confirmed, low-risk test-staleness cleanup. The repeated-requeue fix is potentially a real production limitation: if the concurrency guard is meant only to prevent two *simultaneous* redeliver requests from double-inserting, but instead permanently forbids all *future* redelivers of an original event_id after the first, that would incorrectly block a legitimate retry-queue workflow (an event that fails again after its first redeliver and needs to be redelivered a second time) — a correctness/reliability concern for the DLQ's core retry semantics, not merely a test issue.

## Implementation intent
For `dlq_imminent`: remove the 2 stale assertions, consistent with the already-executed, cross-documented removal decision — no further confirmation needed given 3 independent corroborating documents. For the repeated-requeue guard: first determine whether `redeliver_event()`'s guard can be narrowed to only block genuinely-concurrent races (e.g. by checking for an existing *un-acked, still-in-DLQ-or-active* descendant rather than any descendant ever) without reintroducing the race it was added to prevent; if a narrower guard is feasible and consistent with the guard's own stated concurrency-only intent, fix `redeliver_event()`. If investigation shows the permanent block is in fact intentional beyond just the race (e.g. a business rule limiting redelivery attempts per lineage chain root), instead correct the test's scenario to operate on the newly-returned `new_event_id` for each subsequent requeue rather than the original `event_id`.
