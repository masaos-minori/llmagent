## Background
NC-036 asked whether `call_rag_service()`'s parse-error-triggers-fallback behavior was an intentional refinement of ADR-010 Decision #9, or an unintended deviation, citing the test `test_json_parse_error_calls_set_fallback_reason` as evidence the deviation was actively defended. A 2026-09-27 deep-dive found this is already resolved in code: commit `ba82419b` ("fix(pipeline_service): return empty string instead of None on JSON parse errors per ADR-010 Decision #9; update docstring and test") and commit `4ee51b8d` ("fix: remove spurious _set_fallback_reason call on JSON parse error (ADR-010 INV-07 compliance)", 2026-09-25) both directly fixed this.

This Plan's own Step 3 verification independently confirmed every claim: both cited commits exist with the stated messages and touch `scripts/rag/pipeline_service.py`; the current `except ValueError` branch (lines 175-181) returns `"", None, 0.0` and does not call `_set_fallback_reason` — unlike the sibling HTTP-client-error branches (lines 152-169), which return `None` and do call `_set_fallback_reason`, confirming the `ValueError` branch's return contract is now materially different (an empty-string result, not a fallback trigger) and its "falling back to in-process" log wording is stale; the test cited in NC-036 no longer exists under that name — it was renamed to `test_json_parse_error_does_not_call_set_fallback_reason` (line 240) and now asserts `len(reasons) == 0`, the opposite of what NC-036 describes.

## Problem
