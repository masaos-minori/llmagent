## Goal
Give operators accurate visibility into `/reload`'s handling of `diagnostics.*` config
fields by adding a distinct reporting category for them (they are already live —
re-read from disk on every `DiagnosticStore.save()`/`fetch()` call, independent of
`/reload` — so classifying them as `[STARTUP-ONLY]` would be factually wrong), and
correct two stale documentation notes left over from a prior, already-implemented fix
to the write-only-encryption problem this issue also describes.

## Priority
Medium

## Scope
- **In-Scope**:
  - Add a new `ConfigReloadOutcome` category (distinct from `applied` / `skipped` /
    `startup_only`) that reports `diagnostics.*` fields as always-live/config-file-driven
    when `/reload` detects they changed on disk.
  - Add a detector method in `scripts/agent/services/config_reload.py`, analogous to

    `diagnostics.retention_days` / `diagnostics.sensitive_fields`.

  - Add unit tests for the new detector and a characterization-test update for the new

## Background
The source Issue (`issues/20260821_06_issue.md`) bundles two diagnostics-subsystem
gaps under one title: M-6 (write-only encryption — `fetch()` allegedly never decrypts)
and M-8 (`diagnostics.*` config changes silently dropped by `/reload`). Both were
originally documented as "Known Limitations" in
`docs/05_agent_09_01_data-layer-session-db.md` and
`docs/05_agent_08_04_configuration-mcp-approval-obs.md` respectively, which is what the
Issue's References field cites.

## Problem
Re-verifying both claims against current source (2026-08-26) found:
- **M-6 claim is now false.** `scripts/agent/diagnostic_store.py`'s `fetch()` (lines
  174-206) already decrypts Fernet-encrypted content, wrapped in a try/except that
  leaves ciphertext as-is and logs a warning on failure. This was implemented by
  `plans/done/20260818-170728_plan.md` ("Complete the DiagnosticStore diagnostics fix
  by ... implementing decryption in `fetch()`"), which is already merged and archived.
  That plan's Documentation Impact was explicitly "None", so the two doc files that
  described the write-only-encryption limitation were never updated — they are stale,
  not the code.
- **M-8 claim is true, but its root cause is different from what the Issue assumes.**
  `scripts/agent/services/config_reload.py`'s `_detect_startup_only()` (lines 431-444)
  only compares `use_memory_layer` and `routing_drift_strict` against `ctx.cfg`; no
  code path in `config_reload.py` references `encryption_key`, `retention_days`, or
  `sensitive_fields`. However, `DiagnosticStore._load_diagnostics_config()` (lines
  43-65) does not read `ctx.cfg.diagnostics` at all — it calls
  `ConfigLoader().load("agent.toml")` directly, fresh, on every single `save()` and
  `fetch()` call. `AgentConfig.diagnostics` (built by `_build_diagnostics_config()` in
  `scripts/agent/config_builders.py:424`) is constructed at startup but has zero
  runtime readers (`rg "cfg\.diagnostics\b"` across `scripts/` returns no hits outside
  its own construction). So `diagnostics.*` config is not "startup-only" (a restart is
  never required — the very next diagnostic write/read already picks up whatever is on
  disk) and it needs no `/reload` action either — it was never wired through `ctx.cfg`
  to begin with. The actual defect is narrower than the Issue describes: `/reload`'s
  report gives the operator zero acknowledgment of `diagnostics.*` fields one way or
  the other, so an operator who edits `agent.toml`'s `[diagnostics]` table and runs
  `/reload` cannot tell from the output whether anything happened.

## Reason for change
An operator-facing `/reload` command that silently says nothing about a config section
the operator just edited is a transparency gap regardless of whether the underlying
behavior is already correct. Classifying `diagnostics.*` as `[STARTUP-ONLY]` (the
Issue's suggested fix) would introduce a new, incorrect claim (that a restart is
needed) in place of the current silence. The stale "fetch() doesn't decrypt" doc notes
are an independent problem: they actively mislead anyone reading the docs about
already-fixed code.

## Implementation intent
Add a new, correctly-labeled reporting category to `ConfigReloadOutcome` for fields
that are live via their own independent config read path rather than via `ctx.cfg` +
`/reload`'s sync methods. Populate it with a diff-based detector mirroring
`_detect_startup_only()`'s existing pattern (compare fresh `new_cfg` values against the
`ctx.cfg.diagnostics` snapshot taken at startup, report names that differ), so the
change follows the same shape already used for `startup_only` and is trivially
reviewable against it. Render the new category in `_cmd_reload()` with wording that
tells the operator the setting is already effective without restart or explicit
`/reload` support. Separately, correct the two stale doc notes now that their
underlying code/behavior claims have been re-verified.

## Design
`ConfigReloadOutcome` currently has five fields: `applied`, `needs_restart`, `skipped`,
`source_files`, `startup_only`. `_detect_startup_only()` is the only existing
"differs-from-running-cfg" detector and follows this shape: read a value out of
`new_cfg` via a typed getter (`_get_bool`/`_get_str`/etc.), compare it against the
corresponding `ctx.cfg.<subsystem>.<field>` attribute, append the field name to a
`list[str]` if they differ. `_detect_diagnostics_live_fields()` follows the identical
shape, scoped to `new_cfg["diagnostics"]` (a nested dict, confirmed via
`config/agent.toml`'s `[diagnostics]` table and `_build_diagnostics_config()`'s use of
`_get_dict(cfg, "diagnostics")`) compared against `ctx.cfg.diagnostics`'s three fields.
The only semantic difference from `_detect_startup_only()` is the label attached to the
result (`always_live` instead of `startup_only`) and the fact that, unlike
`use_memory_layer`/`routing_drift_strict`, `ctx.cfg.diagnostics` is never read by any
runtime code path — it exists solely as the last-startup snapshot this detector diffs
against. This is intentionally not "fixed" by wiring `ctx.cfg.diagnostics` into
`DiagnosticStore` (out-of-scope): `DiagnosticStore`'s direct-from-disk read is already
strictly more current than anything `/reload` could push into `ctx.cfg`, so changing
that ownership model would be a regression in freshness, not an improvement.

`_cmd_reload()`'s existing branch structure is:
```
if not result.applied and not result.needs_restart:
    if result.startup_only: ... "startup-only settings cannot apply without restart"
    else: "No changes detected."
elif result.needs_restart: ...
else: "Config reloaded — all changes applied"
```
`REQ-003` adds `result.always_live` as a third condition in the initial `if`/`elif`
chain (rendered similarly to `startup_only` but with distinct wording), and the "No
changes detected." branch must additionally require `not result.always_live` — a
`diagnostics.*`-only edit currently would otherwise be a false "No changes detected."
after `REQ-002` starts populating `always_live` (before `REQ-002`, this branch was
correct only by omission, since nothing populated any diagnostics-related list at all).

`radon cc scripts/agent/commands/cmd_config.py -s -n C` currently reports `_cmd_reload`
at complexity grade C (11) — the pre-existing baseline. `REQ-003` adds one more
condition and one more `_write_item_list()` call; implementers should keep the
branching additive (reuse the existing `if result.<category>:` + `_write_item_list()`
pattern already used for `applied`/`skipped`/`startup_only`) rather than introducing
new nested branching, to avoid pushing complexity meaningfully higher than the current
baseline.
