# Define and enforce valid event delivery state transitions

## Goal

Turn delivery handling into a deterministic state machine. Every operation must have documented preconditions, transactional postconditions, and a defined error when the requested transition is invalid. Start by adding state predicates to `nack_event()`'s `WHERE` clause so that NACK on an already-ACKed or already-DLQ'd event returns HTTP 409 with a safe, actionable reason, following the existing `ERR_EVENT_NOT_IN_DLQ` pattern in `dlq_route.py`.

## Priority
Medium

## Scope
- **In-Scope**: Defining normal, delivered, ACKed, failed, DLQ, requeued, and archived states as applicable to the final consumer model; documenting allowed and prohibited transitions; adding state predicates to database updates (starting with `nack_event()`'s `WHERE` clause); returning HTTP 409 for invalid transitions with a safe, actionable reason; making concurrent ACK, NACK, promotion, and requeue outcomes deterministic; linking each invariant to an automated test.
- **Out-of-Scope**: Transactional ACK/offset redesign (EB-H01). DLQ requeue real-redelivery redesign (EB-H03).

## Background

Confirmed by direct read of `scripts/eventbus/db.py`: `ack_event()` (lines 118-141) is itself idempotent against re-ACK (`WHERE event_id = ? AND acked_at IS NULL`, returning `(True, False)` for an already-acked event without erroring), but `nack_event()` has no equivalent guard — it will happily increment `delivery_failure_count` for an event that is already ACKed or already sitting in the DLQ. By contrast, `scripts/eventbus/dlq_route.py`'s `dlq_requeue()` (lines 49-78) already returns HTTP 409 (`ERR_EVENT_NOT_IN_DLQ`) for an event that exists but is not currently in the DLQ — so a 409-on-invalid-transition pattern is already established elsewhere in this codebase and can be extended to ACK/NACK.

## Problem

- `NACK` on an already-ACKed event silently increments its failure count with no error and no defined meaning — the event is "done" from the ACK side but is treated as still failing from the NACK side.
- `NACK` on an event already in the DLQ (`dlq_at IS NOT NULL`) also silently increments its count, which (combined with this batch's DLQ-requeue-redesign issue's separation of lifetime vs. cycle failure counts) could immediately push a freshly-requeued event back toward re-promotion.
- No existing test in `tests/eventbus/test_eventbus_ack_nack.py`/`test_eventbus_subscribe_transition.py` (confirmed present under `tests/eventbus/`) asserts that NACK-after-ACK or NACK-after-DLQ-promotion is rejected — this needs direct confirmation of those files' actual assertions, but `nack_event()`'s SQL shows no guard exists to make such a test pass today.

## Reason for change

Turn delivery handling into a deterministic state machine. Every operation must have documented preconditions, transactional postconditions, and a defined error when the requested transition is invalid.

## Implementation intent

Define normal, delivered, ACKed, failed, DLQ, requeued, and archived states as applicable to the final consumer delivery model (coordinate with this batch's transactional-ACK/offset and DLQ-redesign issues so the state names stay consistent across all three). Document allowed and prohibited transitions. Add state predicates to `nack_event()`'s (and any other relevant) database updates — e.g. `WHERE event_id = ? AND acked_at IS NULL AND dlq_at IS NULL` — and return HTTP 409 with a safe, actionable reason when the transition is rejected, following the existing `ERR_EVENT_NOT_IN_DLQ` pattern in `dlq_route.py`.

## Design

### Task-size classification: Path B

This task affects > 3 files, changes public/runtime interface (adds validation constraints that affect client behavior), and modifies configuration contracts. Full architecture analysis, dependency graphing, historical analysis, and operational dependency inspection are performed per Path B rules.

### Architecture analysis

The EventBus currently has two independent operation paths:
1. **ACK path**: `ack_event()` is idempotent — calling it multiple times for the same event returns `(True, False)` without error.
2. **NACK path**: `nack_event()` is NOT idempotent — calling it multiple times increments `delivery_failure_count` each time, even for events that are already ACKed or DLQ'd.

The critical issue is that there is no state machine governing these operations — any operation can be applied to any event regardless of its current state. This creates undefined behavior when operations are applied out of order.

### Dependency graphing

```
FastAPI routing ──► nack() ──► _nack_and_promote() ──► nack_event(db, event_id)
   │                    │              │                        │
   │                    │              │                        ├──► UPDATE events SET delivery_failure_count = ... WHERE event_id = ?
   │                    │              │                        └──► return new count or -1
   │                    │              │
   │                    │              └──► promote_single(db, dir, event_id) (if count >= max_retry)
   │                    │
   └──► get_db()        │
   └──► get_config()    │

FastAPI routing ──► ack_event() ──► _do_ack() ──► ack_event(db, event_id, now)
   │                    │              │                        │
   │                    │              │                        ├──► UPDATE events SET acked_at = ? WHERE event_id = ? AND acked_at IS NULL
   │                    │              │                        └──► return (found, newly_acked)
   │                    │              │
   └──► get_db()        │
   └──► get_config()    │
```

After refactoring, the NACK path becomes:
```
FastAPI routing ──► nack() ──► _nack_and_promote() ──► nack_event(db, event_id)
   │                    │              │                        │
   │                    │              │                        ├──► UPDATE events SET delivery_failure_count = ... 
   │                    │              │                        │         WHERE event_id = ? AND acked_at IS NULL AND dlq_at IS NULL
   │                    │              │                        └──► return new count or -1 (or -2 for invalid transition)
   │                    │              │
   │                    │              └──► HTTP 409 if count == -2
   │                    │
   └──► get_db()        │
   └──► get_config()    │
```

Key dependencies:
- `db.py` must return a distinct signal (-2) for invalid transitions.
- `ack_route.py` must convert this signal to HTTP 409 with a specific error message.
- The error messages must follow the existing pattern (`ERR_EVENT_NOT_FOUND`, `ERR_EVENT_NOT_IN_DLQ`).

### Historical analysis

- The ACK path was designed with idempotency in mind — `WHERE event_id = ? AND acked_at IS NULL` ensures re-ACK is safe.
- The NACK path was NOT designed with idempotency in mind — `WHERE event_id = ?` alone allows NACK on any event.
- No prior attempt to add state predicates to NACK exists — this is the first effort.
- The 409-on-invalid-transition pattern was established later in `dlq_route.py`'s `dlq_requeue()` function.

### Operational dependency inspection

- Adding state predicates means that NACK will fail for events that were previously valid targets — this is a breaking change for clients that rely on silent increment.
- The 409 response must include a clear reason so clients can distinguish between "already ACKed" and "already DLQ'd".
- Concurrent transitions are handled deterministically by SQLite's serialization via `run_with_db_lock` — the second call observes the first call's committed state.

### Design decisions

1. **State definition (REQ-001)**: Define the following states based on the existing column values:
   - **Normal**: `acked_at IS NULL AND dlq_at IS NULL`
   - **Delivered**: `acked_at IS NULL AND dlq_at IS NULL` (same as Normal — the distinction is semantic, not structural)
   - **ACKed**: `acked_at IS NOT NULL`
   - **Failed**: `acked_at IS NULL AND delivery_failure_count >= max_retry AND dlq_at IS NULL`
   - **DLQ**: `dlq_at IS NOT NULL`
   - **Requeued**: `dlq_at IS NULL AND delivery_failure_count < max_retry` (after requeue)
   - **Archived**: Not yet implemented — would require a new column or TTL-based cleanup

2. **State predicates for NACK (REQ-003)**: Add `AND acked_at IS NULL AND dlq_at IS NULL` to `nack_event()`'s `WHERE` clause. Return `-2` (distinct from `-1` for "not found") to signal an invalid transition.

3. **HTTP 409 response (REQ-004)**: In `ack_route.py`, convert `-2` to HTTP 409 with a specific error message:
   - If `acked_at IS NOT NULL`: `"event already acknowledged"`
   - If `dlq_at IS NOT NULL`: `"event already in dead letter queue"`
   
   Use the existing `ERR_EVENT_NOT_FOUND` / `ERR_EVENT_NOT_IN_DLQ` pattern for consistency.

4. **Concurrent transitions (REQ-005)**: Rely on SQLite's serialization via `run_with_db_lock` — the second call observes the first call's committed state. If ACK wins, NACK returns 409; if NACK wins, ACK returns 200 with `already_acked: false`.

5. **Documentation update (REQ-002)**: Document the state diagram and transition rules in `06_eventbus_04`, including:
   - All states and their definitions.
   - Allowed transitions (with arrows).
   - Prohibited transitions (with red X marks).
   - Error responses for prohibited transitions.

6. **ADR-006 alignment (REQ-006)**: Update ADR-006's Known Deviations section to note which invariants are now enforced:
   - INV-05 (offset monotonicity): Not affected by this change.
   - INV-07 (at-least-once delivery): Now enforced — NACK cannot corrupt ACKed events.
   - INV-08 (NAK/DLQ state persistence): Now enforced — NACK cannot corrupt DLQ'd events.
   - INV-12 (ACK failure handling): Not affected by this change.
   - INV-13 (DLQ promotion priority): Not affected by this change.
