# Make the REPL Exit Bracket Own Session Persistence on Every Path, with One Component Deciding Whether Anything Is Written

**Plan ID**: 20261022-071052
**Source Issue**: issues/20261021-093421_shutdown002-session-persistence-skipped-on-startup-failure.md
**Generated**: 2026-10-22 07:10 JST

## Goal

Make the REPL's exit sequence one explicit, total bracket: the session persist
step is reached on every exit path, runs before resource shutdown, and one
component decides whether anything is written for the session that does or does
not exist. A failed startup then produces a stated skip instead of an accident,
and a persistence failure can no longer replace the error the process was
already exiting with.

## Priority

- **Primary goal**: move the persist call into the single `finally` of
  `AgentREPL.run()` (`scripts/agent/repl.py:161-162`) ahead of
  `close_resources()`, so the step is reached on the startup-failure,
  startup-interrupt, input-loop-error and normal-exit paths alike.
- **Must be resolved first**: the write-or-skip decision, and where it lives.
  This Plan's answer is: write nothing when no session was started, and own that
  decision inside `SessionPersister`, keyed on `ctx.session.session_id`. The
  step is still *reached* on every path; only the write is conditional.
- **Secondary goals**: delete the `persister_callback` indirection
  (`scripts/agent/repl_input_loop.py:76-82`, `:111-115`); contain persistence
  failures so they are reported as non-fatal and cannot replace a propagating
  exception; make one error raised inside the input loop produce one
  operator-facing line (`repl_input_loop.py:89-91` and `:108-110` print the same
  error twice today).
- **Out of scope**: the *content* of what is persisted — the `session_summary`
  payload fields (`scripts/agent/session_persister.py:111-134`) and the memory
  extraction rules — which is memory/turn scope, not exit-path scope;
  `close_resources()`'s internals (`shutdown001`, `plans/20261022-043330_plan.md`);
  signal and shutdown-event ownership (`repl001`, `plans/20261022-030840_plan.md`);
  stdin reads (`repl002`); `TestCloseResourcesWALCheckpoint`
  (`tests/agent/test_repl.py:879-1030`, owned by `shutdown001`); the
  WAL-timeout bullet at `docs/23_agent/agent_10_01_operations-and-observability-startup-and-health.md:144`
  and item 3 (`docs/01_overview/overview_01_03-arch-features.md:67`), both owned
  by `shutdown001`; moving `TestPersistSessionDiagnostics`
  (`tests/agent/test_repl.py:472-610`) into the new mirror test file, which this
  Plan records as a work item instead of performing.

## Background

The source issue claims persistence is reached only through the input loop. That
is true at HEAD, and it is verifiable in three lines: `_persist_after_loop`
(`scripts/agent/repl.py:105-108`) is passed as the second argument of
`ReplInputLoop.run()` (`repl.py:157-160`), and only that method's `finally`
(`scripts/agent/repl_input_loop.py:111-115`) calls it. `AgentREPL.run()`'s own
`finally` (`repl.py:161-162`) calls `close_resources()` and nothing else.

Two corrections to how the issue framed the consequence, both established by
reading HEAD:

- A startup failure is not a quiet exit. `except StartupInterrupted`
  (`repl.py:134-139`) and `except Exception` (`:140-142`) each write a message
  and `raise`; `run()` returns `None`, so the exception escapes through the
  `finally` and out of `asyncio.run(AgentREPL().run())` (`repl.py:170-172`).
  `close_resources()` is the only cleanup that runs.
- **No in-memory session state can exist on that path to be lost.** `ctx.session`
  is a bare `AgentSession()` (`scripts/agent/context.py:332`); `session_id` is
  assigned only at `scripts/agent/session.py:148`, reachable only from
  `repl_input_loop.py:88`; `AgentSession.replace_messages` (`session.py:80-84`)
  and `AgentSession.save_diagnostic` (`session.py:89-93`) already skip silently in
  exactly that state; and per-event diagnostics are inserted inline at their own
  call sites (`scripts/agent/llm_turn_runner.py:154`, `:161`, `:170`;
  `scripts/agent/tool_runner.py:132`; `scripts/agent/tool_run_recorder.py:108`;
  `scripts/agent/tool_loop_guard.py:141`; `scripts/agent/session.py:94`) rather
  than deferred to the persist step. The persist step writes exactly two things:
  a `kind="session_summary"` row (`session_persister.py:111-149`) and a
  `memory.on_session_stop(...)` call (`:174-178`), and
  `MemoryIngestionService.on_session_stop` returns immediately when history yields
  no entries (`scripts/agent/memory/ingestion.py:87-89`).

So the defect this Plan fixes is not lost data. It is that the exit sequence is
defined by *which code path unwound*, and that the two observable symptoms of
that shape are real and measured.

Measured with throwaway probes (`/tmp/opencode/shutdown002_probe.py`,
`/tmp/opencode/shutdown002_probe2.py`; deliberately not added to the
repository), against temporary databases under `.venv`:

| Measurement | Result |
|---|---|
| Input loop entered, `session.start()` raises `SchemaMissingError` | the same `[fatal] Session schema missing. Run: bash deploy/init_db.sh to initialize the database.` line printed **twice** (`repl_input_loop.py:90` then `:109`) |
| Same run, persist `finally` raises | the re-raised session-start error is **replaced** in the traceback by `TypeError: Object of type MagicMock is not JSON serializable` from the persist body |
| `DiagnosticStore.save(session_id=None, kind="session_summary", …)` against a real `session_diagnostics` table | row `(1, None, 'session_summary')` committed; the column is a nullable FK (`scripts/db/schema_sql.py:140-147`) so nothing rejects it |
| Live `/opt/llm/db/session.sqlite` `session_diagnostics` | 6 rows, all `session_summary`, **0** with a null `session_id` |

The last two rows together say why the null-session case is latent rather than
visible today: in practice `session.start()` fails only when the whole schema is
missing, and then the persist `INSERT` raises `sqlite3.OperationalError`, is
caught at `session_persister.py:150`, and writes a **third** operator-facing line
(`:152`). A null-`session_id` summary row is what the same code writes when the
table exists and the session start failed for a different reason.

## Problem

One session has two cleanup owners with different reachability. `close_resources()`
runs on every exit path; the persist step runs only when the input loop was
entered. Neither the asymmetry nor the reason for it is stated in code or docs,
and the nesting has three concrete effects: a persist exception replaces the
error the process was already reporting, the same input-loop error is printed
twice, and the persist step can write a `session_summary` row for a session that
was never created.

## Reason for Change

- The behavior is currently asserted by nothing. `tests/agent/test_repl.py:505-512`
  (`test_handles_none_session_id`) is the closest case and contains **no
  assertion**; it also patches `agent.wal_checkpoint_manager.SQLiteHelper`
  (`:511`), which `SessionPersister` never calls, so the patch intercepts
  nothing. `TestRunResourceCleanup` (`tests/agent/test_repl.py:1423-1490`) is the
  ordering test the issue asks for and already records cleanup calls in a list —
  its three assertions (`:1459`, `:1474`, `:1490`) name `close_resources` only,
  which is the current behavior encoded as intent. `TestRunSqliteErrorMessage`
  (`:736-807`) asserts `assert len(fatal_calls) >= 1` (`:772`) — a weakened
  assertion that tolerates the duplicate report this Plan removes. The 18
  `mock_persister = AsyncMock()` fixtures (`:150`, `:159`, …, `:435`) are passed
  as an argument and asserted on zero times.
- The indirection has no remaining reason. `grep -rn "persister_callback" scripts/`
  returns only its own three lines (`repl_input_loop.py:79`, `:112`, `:113`), and
  `grep -rn "_persist_after_loop" tests/` returns nothing. The parameter's
  signature is a three-way union (`Callable[[], None] | Callable[[], Coroutine] |
  None`, `repl_input_loop.py:76-82`) plus a runtime `asyncio.iscoroutine` branch
  (`:113-115`) to accommodate one value that is always the same bound coroutine
  method.
- The docs state the boundary this Plan changes, in both directions.
  `docs/01_overview/overview_01_03-arch-features.md:65` says persistence happens
  "After the REPL input loop ends".
  `docs/23_agent/agent_10_01_operations-and-observability-startup-and-health.md:76`
  says cleanup runs "when the interactive session ends or when startup fails or is
  interrupted" and lists four steps (`:78-81`), none of which is persistence. One
  of those two sentences is wrong about every path, and today both are defensible
  because they describe different owners.
- `SessionPersister.persist_session_diagnostics` is already the most complex
  function on this path — radon C (18) — and its outer guard
  (`session_persister.py:154`) accepts only `(OSError, sqlite3.Error)` while the
  inner one (`:150`) accepts `(RuntimeError, sqlite3.Error)`, so a defect in the
  payload-building body (`:52-142`) is not contained at all. That is the shape
  the measured `TypeError` escaped through.

## Implementation Intent

Put the ordering in one function and the write-or-skip decision in one component,
without changing what is persisted, what `close_resources()` does, or which
component performs each step.

**Naming and concept boundaries**
- Rename `AgentREPL._persist_after_loop` (`repl.py:105-108`) to
  `_persist_session_state`. The old name states a position in a control flow that
  will no longer exist, and `grep -rn "_persist_after_loop" tests/` shows no test
  depends on it. The only external mention is the prose this Plan corrects
  (`overview_01_03-arch-features.md:65`).
- Keep the names `SessionPersister`, `persist_session_memories`,
  `persist_session_diagnostics`, `ReplInputLoop.run`, `AgentREPL.run`,
  `ResourceShutdownCoordinator.close_resources`. `ReplInputLoop.run` loses one
  parameter; no other signature changes.
- Add no new class, no new module, and no shutdown "policy" object. The bracket is
  a `try/finally` in the function that already has one.

**What each component owns after this Plan**
- `AgentREPL.run()`: the order of the exit sequence, and nothing else.
- `SessionPersister`: whether session state is written, and how a persistence
  failure is reported.
- `ReplInputLoop`: the input loop only.
- `ResourceShutdownCoordinator`: the resource steps (unchanged; owned by
  `shutdown001`).

## Requirements

- REQ-001: the persist step is reached on every exit path of `AgentREPL.run()`,
  from one `finally`, before `close_resources()`. Today it is reached only when
  `ReplInputLoop.run()` was entered (`repl_input_loop.py:111-115`).
- REQ-002: `ReplInputLoop.run()` owns no persistence step. The
  `persister_callback` parameter (`repl_input_loop.py:76-82`), its `finally`
  (`:111-115`) and the `asyncio.iscoroutine` branch are removed; the method keeps
  its remaining parameter and every other statement as written.
- REQ-003: the decision to write or skip session state is made in exactly one
  place — `SessionPersister` — and is keyed on `ctx.session.session_id`, the only
  session-existence state the code has (`scripts/agent/session.py:148` is the
  sole assignment). A skip performs no `DiagnosticStore.save` call and no
  `memory.on_session_stop` call, and records its reason in the log.
- REQ-004: a persistence failure is reported through the existing non-fatal
  channel (`scripts/agent/cli_view.py` `write_warning`, `:57`, `:209`, with
  `OutputTag.NON_FATAL`) and never replaces the exception the process was already
  propagating. A `finally` body that raises replaces the in-flight exception —
  measured above — so the bracket's persist call is guarded.
- REQ-005: that containment covers the whole persist step, not only its DB call.
  `session_persister.py:154` currently guards `(OSError, sqlite3.Error)` while the
  payload-building body above it is unguarded.
- REQ-006: the session persist step writes no `session_diagnostics` row with a
  null `session_id`. Store-level behavior is deliberately different and stays:
  `DiagnosticStore.save(session_id=None, …)` must keep working, because
  `tests/agent/test_regression_diagnostic_persist.py:114-123` asserts it as
  intended behavior.
- REQ-007: one error raised inside `ReplInputLoop.run()` produces exactly one
  operator-facing line for that error. `SchemaMissingError` is a `RuntimeError`
  (`session.py:19`), so the inner handler (`repl_input_loop.py:89-91`) and the
  outer `except RuntimeError` (`:108-110`) both report it; the `sqlite3.Error`
  handler (`:95-101`) is converted into a `RuntimeError` and reported twice for
  the same reason.
- REQ-008: the order *inside* `close_resources()` is unchanged: checkpoint,
  backup, `lifecycle.shutdown_all()`, `http.aclose()`
  (`agent_10_01_*:78-81`, `scripts/agent/resource_shutdown_coordinator.py:64-151`).
  This Plan changes only the step that precedes it.
- REQ-009: the decision and the order are stated where a reader will hit them
  first: the `repl.py` comment that currently explains the nesting
  (`repl.py:124-126`), `AgentREPL._persist_session_state`'s docstring, and
  `SessionPersister`'s module and method docstrings (`session_persister.py:2-9`,
  `:50-51`, `:157-158`).
- REQ-010: the normal-exit path is behaviorally unchanged. Both persist methods
  still run, in the same order, with the same payload, before any resource is
  closed. The ordering requirement is not incidental: persistence reads
  `ctx.services.llm` / `ctx.services.hist_mgr` (`session_persister.py:54`, `:56`)
  and calls `ctx.services.memory` (`:174`), all of which `close_resources()`
  releases at `agent_10_01_*:80-81`.
- REQ-011: the tests assert the documented behavior — "no session DB write and no
  memory-ingestion call happened for a session that does not exist" — not the
  number of mock calls the fixture itself arranged.

## Assumptions

  different claims, and only the first is required. The evidence is that no value
  the persist step reads or writes can exist without a `sessions` row; the

## Design

**The invariant this Plan installs**
`AgentREPL.run()` has exactly one exit bracket, in a fixed order: persist session
state, then close resources. No step in that bracket is reachable from a nested
`finally` owned by another component. The order is not stylistic: the persist step
reads `ctx.services.llm`, `ctx.services.hist_mgr` (`session_persister.py:54`,
`:56`) and calls `ctx.services.memory` (`:174`), and `close_resources()` releases
`lifecycle` and `http` (`agent_10_01_*:80-81`); persisting after close would read
and use clients that have been closed. The bracket's *reachability* is total; the
*write* inside the persist step is conditional and owned by `SessionPersister`.

**Why the decision belongs to `SessionPersister`**
It is a policy about when session state is meaningful, and the component that
performs the writes is the only place that knows which values depend on a
`sessions` row. The file already encodes that dependency twice, at `:72` and
`:97`; REQ-003 makes it one stated gate at the top instead of two silent partial
gates in the middle. `AgentREPL` keeps ordering only, which is what its class
docstring (`repl.py:63-69`) already claims it does. Keeping the decision in
`AgentREPL` would make any future non-REPL caller of the persister re-derive it.

**Why the gate is not a change to `DiagnosticStore`**
The store's acceptance of `session_id=None` is deliberate and tested
(`tests/agent/test_regression_diagnostic_persist.py:114-123`), and it is used for
real by `session.py:94` and the turn-level recorders after a session exists. The
new rule is "the session-level persist step does not write for a session that was
never started" — a rule about the caller, above a store whose contract stays as
recorded (REQ-006).

**Why the current tests pass**
Three mechanisms, all local: `assert len(fatal_calls) >= 1` tolerates the
duplicate report; `test_handles_none_session_id` has no assertion at all, so any
behavior passes it; and the 18 `mock_persister` fixtures record nothing. The only
test that observes the bracket, `TestRunResourceCleanup` (`:1423-1490`), encodes
today's answer — `calls == ["close_resources"]` on the startup-failure path —
as its expected value. That is why AC-1's evidence is a changed expected list and
AC-3's evidence is a row count, and why REQ-011 exists: an assertion that cannot
fail and an expected value copied from the implementation are the same defect.

**Verification surface**
A test is a regression test for this defect only if it fails when the gate is
removed, when the persist call is removed from `run()`'s `finally`, or when the
duplicate report is restored. Those three mutations are the phase gates. A test that
only counts calls a fixture arranged does not qualify.

## Risks

  call sites use. Mitigation: the parameter has no other caller (`grep` above), no
  test asserts on it, and `F841` forces the unused fixtures to be deleted in the

  without an id, turning a loud null-`session_id` write into a silent skip.

- Strengthening `assert len(fatal_calls) >= 1` to `== 1` (`tests/agent/test_repl.py:772`)
  can expose a second report this Plan has not enumerated in some other path.
  Mitigation: Phase 3 runs `tests/agent/test_repl.py` and

### Requirement Traceability
- REQ-001 → Phase 1 → AC-1, AC-2: the defect is that one cleanup step is reached
  from one path, so the first phase changes only where the step is called. Nothing
  about what is persisted moves with it.
- REQ-002 → Phase 1 → AC-5: the indirection is the mechanism that made the reach
  path-dependent, and it has no other user; removing it in the same phase as the
  move prevents a dangling parameter that would invite the nesting back.
- REQ-003 → Phase 2 → AC-3: the write-or-skip decision must exist before the step
  becomes unconditional, otherwise Phase 1 would turn a stated absence on the
  startup path into a null-`session_id` write — the measured `(1, None,
  'session_summary')` row.
- REQ-004 and REQ-005 → Phase 1 and Phase 2 → AC-4: the bracket only becomes safe
  to make unconditional once a failure inside it cannot replace the exception the
  process is reporting; the measured `TypeError` replacing `SchemaMissingError` is
  the evidence, and the two guards at `session_persister.py:150` / `:154` are the
  gap.
- REQ-006 → Phase 2 → AC-3, AC-7: the store-level null contract is real and
  tested, so the boundary between store and session persist step has to be drawn
  explicitly rather than inherited.
- REQ-007 → Phase 3 → AC-6: the double report is the visible symptom of the same
  ownership problem, but it is separable from the bracket and is the one requirement
  whose design choice is not yet settled (UNK-01).
- REQ-008 and REQ-009 → Phase 3 → AC-8, AC-9: the order is documented behavior in
  two documents that currently disagree, and `shutdown001` owns two of the four
  regions involved, so the documentation pass is last and ordered against it.
- REQ-010 → Phase 1 → AC-7: the unchanged files are the regression surface for the
  move; `test_repl_error_handling.py:20` and `TestPersistSessionDiagnostics` pass
  through the gate because their sessions exist.
- REQ-011 → all phases → AC-1, AC-3, AC-6: three of this area's existing tests
  cannot fail, and the one that can fails only for today's answer; without the
  mutation gates the Plan could be implemented and the defect survive.
