## Goal

Decouple stampede protection from error propagation so that transient failures affect only the initiating request, allowing concurrent waiters to retry independently.

## Scope

**In-Scope:**
- Modify `_execute_with_stampede_protection()` to not propagate exceptions to waiters
- Remove failed inflight future and allow each waiter to make its own independent call
- Add retry mechanism for TransportError with backoff
- Delay server health registry updates for transient errors

**Out-of-Scope:**
- Modifying cache TTL or eviction logic
- Changing side-effect tool caching behavior (already bypasses cache)
- Adding new configuration options beyond what's needed for retry parameters

## Assumptions

1. Each waiter should have its own chance to succeed — if the first attempt fails due to a transient error, subsequent attempts may succeed
2. Retry count should be bounded to prevent infinite loops
3. TransportError is the primary transient error category that warrants retry
4. The existing `_record_transport_error()` call in `_raw_execute()` should be deferred until after all retries are exhausted

## Risks

- **Risk**: Retry logic increases latency for legitimate failures → Mitigation: Bound retries to 3 attempts; use short initial backoff (1s); only apply to TransportError
- **Risk**: Removing inflight future without setting a result could leave waiters hanging → Mitigation: Always set either result or error state before removing inflight future
- **Risk**: Delayed health registry updates slow down server failure detection → Mitigation: Update health registry after final retry failure; log warning at each retry attempt
