# Plan: Close remaining ConfigLoader/MCPServer fail-closed gaps (REQ-003 through REQ-006)

## Goal
Implement the four unactioned requirements (REQ-003 through REQ-006) from H-02 to close remaining Config Isolation fail-closed gaps: falsy `own_config_file` bypass, unknown-top-level-key rejection, ADR documentation updates, and corresponding test coverage.

High

## Scope

## Background
The original H-02 issue (`issues/done/20260902-101452_h02_config_loader_fail_closed_gap.md`) requested six fixes (REQ-001 through REQ-006) for ConfigLoader's fail-closed guarantee. Its resulting plan (`plans/done/20260902-191443_plan.md`) generated 13 implementation procedure documents (`implementations/done/20260902-220059_01` through `_13`), and every one of them is scoped to REQ-001 and/or REQ-002 only — none target REQ-003, REQ-004, REQ-005, or REQ-006. Direct reads of the current code and docs confirm REQ-001/REQ-002 are correctly implemented, but REQ-003 through REQ-006 were never implemented at all; no implementation procedure was ever generated for them. The original Plan's own `## Execution Status` table still reads a single placeholder row with `Status: Pending`, never updated to reflect even the REQ-001/002 work that did land — this Plan's bookkeeping does not distinguish "done" from "not done" per requirement.

## Problem
- `scripts/mcp_servers/server.py::MCPServer.run_http()` still guards `restrict_to()` with a bare `if self.own_config_file:` (no `else`/fail-closed branch) — a falsy `own_config_file` silently skips Config Isolation restriction (REQ-003 unmet).
- `scripts/shared/production_config_validator.py` has no general unknown-top-level-key rejection — only the narrower `tool_safety_tiers`-specific bidirectional check (`_check_missing_tool_safety_tiers`/`_check_unknown_tool_safety_tiers`) exists (REQ-004 unmet).
- `docs/adr/ADR-002-config-isolation.md` has no per-process required-file/required-key/empty-allowed-key table (REQ-005 unmet; confirmed absent by direct read).
- `docs/adr/ADR-004-environment-failure-handling-policy.md`'s INV-07 row still reads "Needs confirmation" (REQ-006 unmet; confirmed by direct read at the row citing INV-06/INV-07).

## Reason for change
These are the same security-relevant fail-closed gaps the original H-02 issue identified: Config Isolation can still be silently bypassed by a falsy `own_config_file`, no config loader rejects unknown/mistyped top-level keys, and two ADRs' own Verification sections still record "Needs confirmation"/missing documentation for exactly this scenario class. REQ-001/002 landing does not close these remaining gaps — they require independent implementation work that the original Plan never generated procedures for.

## Implementation intent
Carry forward REQ-003 through REQ-006 exactly as specified in the original H-02 issue's Implementation Intent and Required Changes sections — this issue does not redesign that scope, it re-files the portion of it that was never actioned. Use `dataclasses.fields()` introspection to derive valid config keys dynamically rather than hardcoding them. Treat REQ-001/REQ-002 as already satisfied and out of scope here.

- `REQ-004`: `ProductionConfigValidator` rejects unknown/mistyped top-level config keys during production config loading, with valid keys derived from `scripts/agent/config_dataclasses.py` via `dataclasses.fields()` introspection.

## Design
This is a Path B task (> 3 files affected, runtime interface changes). Architecture analysis shows the affected modules span two layers: runtime server behavior (server.py) and production config validation (production_config_validator.py), plus documentation updates (ADR-002, ADR-004). Dependency graphing reveals that Config Isolation enforcement flows from MCPServer.startup → ConfigLoader.load_all() → restrict_to(), and any bypass at the MCPServer level cannot be recovered downstream. Historical analysis shows the original H-02 Plan never generated procedures for REQ-003–006, indicating they were overlooked during initial scoping. Operational dependency inspection confirms no running processes hold locks on these files.

The design approach uses dynamic key discovery: `dataclasses.fields()` introspection on all sub-config classes derives the valid key set at runtime, avoiding hardcoding. The fail-closed branch in MCPServer.run_http() raises immediately on falsy own_config_file, consistent with the strict=True default established by REQ-001.
