## Goal
- Make configuration loading a single typed transaction: startup and `/reload` accept and reject exactly the same values, startup-only fields never reach live state, every live-service change is staged so a failed commit rolls the applied changes back in reverse order, and every MCP server-definition change stays pending until the owning process restarts.

## Priority
High

## Scope
- **In-Scope**:
  - One strict typed field-validation layer shared by the startup config builders and the reload candidate phase.
  - Strict MCP server-definition parsing (`cmd`, `env`, booleans, numeric fields, `url`, `role`, unknown-key rejection) used identically at startup and on the reload classification path.
  - Startup-only (`hot_reloadable=False`) field filtering during candidate preparation, and removal of those fields from live service sync.
  - Reload staging with snapshot, prepare, commit, reverse-order rollback, and the outcome states `prepared`, `committed`, `rolled_back`, `degraded`.
  - Prepare and restore APIs on the live services the reload mutates (`LlmHotConfigHandler`, `HistoryManager`, `RuntimeToolRegistry`), and fail-before-commit for anything not reversible.
  - MCP definition add, change, and remove classified as restart-required, with no live lifecycle, config, or registry mutation, and pending changes displayed by `/mcp status`.
  - Unknown-key rejection on the reload path, including fields removed or moved by the `agent.toml` reduction work.
  - Removal of the duplicate and dead reload code found during verification, with its tests retargeted.
  - Documentation and generated-manifest updates for the new behavior.
- **Out-of-Scope**:
  - MCP launch security and credentials (`issues/20261119-145304_cliplc006_mcp-launch-spec-credentials.md`).
  - MCP health and capability state (`issues/20261119-145306_cliplc008_mcp-health-capability.md`).
  - API field cleanup (`issues/20261119-145311_cliplc013_api-field-cleanup.md`), which this Plan unblocks.
  - Pruning of removed `agent.toml` fields and the effective-config snapshot test, kept in `issues/20261120-114213_agentcfg005_system-prompt-snapshot.md`.
  - Any change to an ADR decision or invariant: none is required (see `Design`), and no approval record is written.
- **Dependencies**:

## Problem
- Startup and reload validate the same field with different rules, so a value rejected at startup can be accepted by `/reload` and applied to a running process.
- Fields declared startup-only are written into live configuration and live services, and the report claims they were applied.
- The commit phase mutates `ctx.cfg`, the conversation prompt, MCP lifecycle tracking, and three live services in sequence with no snapshot and no rollback, so a failure in the middle leaves a half-applied configuration.
- A removed MCP server is untracked live while its process keeps running, and reload never mutates the live MCP definition, so the CLI report does not describe live state.
- Malformed MCP definitions and removed configuration keys are accepted or silently ignored, and the outcome model cannot express prepared, committed, rolled-back, or degraded state.

## Reason for Change
- Correctness of the configuration transaction: an accepted `/reload` must mean every reported change is live, and a failed `/reload` must mean nothing changed.
- cliplc006 (MCP launch specification) and cliplc008 (MCP health and capability state) build on a strict configuration model, and cliplc013 (API field cleanup) needs the outcome model this Plan introduces.

## Implementation Intent
- Route both paths through one typed parser: `/reload` builds its candidate configuration with `build_agent_config(cfg_override=...)`, which already runs `ProductionConfigValidator`, so reload validates exactly what startup validates and the candidate phase works on typed `AgentConfig` sections instead of raw dictionary values.
- Add the missing type rules to the field registry so every registered field has a declared type and validator used by both paths, and filter `hot_reloadable=False` fields while building candidates so they never enter `ctx.cfg` or `ServiceSyncer`.
- Wrap the commit in a reload transaction that snapshots the affected configuration sections and conversation state, asks each live service to prepare, commits only after every prepare succeeds, and on failure replays the recorded undo tokens in reverse order; anything not reversible stays gated before any live mutation.
- Classify added, changed, and removed MCP server definitions as restart-required only: no lifecycle call, no live `ctx.cfg.mcp` write, no `RuntimeToolRegistry` write, recorded in a pending state the CLI displays.
- Make a removed or moved field an unknown key on both paths, and delete it from the registry, the startup-only classification, and service sync in the same change.

## Requirements
- REQ-001: One strict typed field-validation layer, defined in the leaf layer and used by both the startup config builders and the reload candidate phase, enforcing field type before value range: `bool` fields reject non-bool, numeric fields reject `bool` and strings, string fields reject non-string, and list fields require a list or tuple of the declared element type.
- REQ-002: `/reload` runs the same production validation startup runs, including unknown-key rejection, before any candidate is built, so a removed or moved key is an error and never silently ignored.
- REQ-003: Candidate preparation filters `hot_reloadable=False` fields out of the sections it prepares and out of `ServiceSyncer`, reports them only as pending restart, and leaves `ctx.cfg`, `ctx.conv`, and every live service unchanged by them.
- REQ-004: MCP server definitions parse through one strict parser used by startup and by the reload classification path: `cmd` is a non-empty list or tuple of non-empty strings; `env` is a mapping of `str` to `str`; `required`, `enabled`, and `auto_start` are `bool`; `startup_timeout_sec` and `max_stderr_log_files` are `int`; `call_timeout_sec`, `startup_stagger_delay_sec`, and `max_stderr_log_size_mb` are `float` and reject `bool`; `url`, `role`, and `auth_token` are `str`; keys outside the declared MCP key set are rejected.
- REQ-005: The reload commit is a staged transaction with the outcome states `prepared`, `committed`, `rolled_back`, and `degraded`, recorded on `ConfigReloadOutcome` and reported by `/reload`.
- REQ-006: `LlmHotConfigHandler`, `HistoryManager`, and `RuntimeToolRegistry` expose snapshot and restore operations; the commit applies prepared changes only after every prepare succeeds, and a commit failure replays the undo tokens in reverse order.
- REQ-007: A service that cannot be made reversible stays behind a fail-before-commit gate; the MCP lifecycle is gated this way and the outcome records which path applied.
- REQ-008: Added, changed, and removed MCP server definitions are classified `needs_restart` only; `/reload` performs no lifecycle call, no write to live `ctx.cfg.mcp`, and no write to `RuntimeToolRegistry`; lifecycle, discovery, posture, and registry state change only after restart and rediscovery.
- REQ-009: Pending MCP definition changes and pending startup-only fields are recorded in a pending-restart state that `/mcp status` and `/config show` display as distinct from live rows.
- REQ-010: A field removed or moved out of `agent.toml` is rejected as an unknown key on both paths and is absent from `CONFIG_FIELD_REGISTRY`, the startup-only classification, and `ServiceSyncer` in the same change.
- REQ-011: Field-level errors are stable and redacted: they name the field path and the violated rule and never include the raw value; `/reload` reports validation, commit, and rollback failures through one error family rather than an uncaught `TypeError`.
- REQ-012: When a rollback step itself fails, the outcome is `degraded`, the CLI names the services left inconsistent and requires a restart, and a later `/reload` in the same process is refused until restart.
- REQ-013: Dead and duplicate reload code is removed and its tests retargeted to the surviving path: `ConfigReloadService._classify_mcp_server_changes`, `config_section_reload.reload_validated_section`, `config_section_reload.reload_direct_fields`, `config_section_reload.prepare_direct_section`, `config_section_reload.apply_direct_section`, the unused `ConfigReloadService._sync_services` parameters, and the unused `ServiceSyncer.__init__` parameters.
- REQ-014: Documentation and generated artifacts state the new contract: startup-only versus hot-reload behavior, the four reload outcome states, and MCP server-definition changes as restart-required.

## Acceptance Criteria
- AC-1: A value table run through the startup builder and through `/reload` produces identical accept and reject results, including every value listed in `Design` as newly rejected.
- AC-2: A `/reload` whose payload contains only startup-only fields leaves `ctx.cfg`, `ctx.conv`, `HistoryManager`, `RuntimeToolRegistry`, and MCP lifecycle state byte-for-byte unchanged, and reports each field as pending restart.
- AC-3: For every injectable commit failure at any stage, all reversible services are restored to their snapshot values and the applied changes are undone in reverse application order.
- AC-4: A `/reload` that removes, adds, or changes an MCP server definition starts, stops, or re-registers nothing: no lifecycle call, no live `ctx.cfg.mcp` write, no `RuntimeToolRegistry` write, and no orphaned process.
- AC-5: The CLI outcome names the stage and matches the live state: `prepared`, `committed`, `rolled_back`, or `degraded`, with pending changes visible in `/mcp status` and `/config show`, and no raw configuration value in any error message.
- AC-6: A field removed or moved out of `agent.toml` is rejected as an unknown key by both startup and `/reload`, and is absent from `CONFIG_FIELD_REGISTRY`, the startup-only classification, and `ServiceSyncer`.

## Design
The change replaces three separate code paths that today validate, mutate, and report configuration independently: the startup builder, the reload candidate phase, and the reload commit phase. After the change there is one validation path, one mutation path, and one report.

### Parity model (REQ-001, REQ-002; OD-01, OD-04)
- `scripts/shared/config_field_types.py` owns the strict primitives. `agent/services/typed_validators.py` delegates to them, `agent/config_section_builders.py` and `agent/config_builders.py` keep using `typed_validators`, and `agent/services/config_validators.py` composes the same primitives with its range rules. There is no second implementation of a type rule anywhere in the configuration layer.
- `ConfigFieldRegistry` gains a declared `field_type` and an `allow_empty` flag, so the registry, not the caller, decides what a field accepts. Entries with `validator_fn=None` acquire the validator implied by their declared type.
- `/reload` obtains its candidate by calling `build_agent_config(cfg_override=loaded_dict)`, the same function startup uses with no override. Production validation, unknown-key rejection, and typed section assembly therefore apply to a reload payload exactly as they apply to a file-loaded configuration. The candidate phase then works on typed `AgentConfig` sections and compares them against live values to determine what changed.
- Because a candidate is a complete `AgentConfig`, a value that startup rejects can never reach the commit phase: AC-1 holds by construction rather than by two rule sets kept in sync.

### Transaction model (REQ-005, REQ-006, REQ-007, REQ-012; OD-05, OD-06)
`ReloadTransaction` in `scripts/agent/services/config_reload_transaction.py` owns four stages:
1. `snapshot()`: copy the values of every `ctx.cfg` section the payload touches, the conversation prompt content, and the policy state of `RuntimeToolRegistry`, `HistoryManager`, and the llm hot-config handler. Section values are written back into the same section objects, because the live services hold references to those instances (see `Assumptions`).
2. `prepare()`: build the typed candidates and ask each live service for the change it will apply, keeping the change in the transaction rather than in the service. Prepare performs no live mutation. A prepare failure aborts with `stage=prepared` and nothing applied.
3. `commit()`: run the applied steps in a fixed order and record an `UndoToken` for each applied step. The order is: configuration section values, conversation prompt content, `RuntimeToolRegistry` policy, `HistoryManager` limits and derived selection policy, llm hot-config values. Commit runs only after every prepare succeeded.
4. `rollback()`: replay the recorded undo tokens in reverse application order. A rollback step that itself raises does not stop the rollback; the remaining tokens are still replayed and the outcome becomes `degraded`, naming the services left inconsistent, requiring a restart, and setting the guard that makes `PendingConfigState` refuse a later `/reload` in the same process.
- `ConfigReloadOutcome.stage` is one of `prepared` (validated, nothing applied, including the no-change case and the pending-only case), `committed` (all applied steps live), `rolled_back` (a commit failure was fully undone), `degraded` (a rollback failure left live state inconsistent).
- Fail-before-commit is the path for anything not reversible. The MCP lifecycle is the one such path in this Plan, and the outcome records `prepared` with a pending record rather than pretending a live effect.

### Pending-restart model (REQ-003, REQ-008, REQ-009; OD-02, OD-03)
- `PendingConfigState` in `scripts/agent/services/config_pending_state.py` records pending MCP definition changes (`added`, `changed`, `removed`, per server key and field) and pending startup-only fields (per section and field), each with the reason: `startup_only` or `mcp_definition_requires_restart`.
- Startup-only fields are filtered while candidates are built, so they never enter a section candidate, never reach `ServiceSyncer`, and therefore cannot reach `HistoryManager`. `classify_startup_only_fields` compares the candidate payload against live values before any mutation, which is what makes the report truthful today's version is not.
- MCP add, change, and remove produce pending records only. `/reload` no longer calls `cleanup_server_resources`, no longer writes live `ctx.cfg.mcp`, and no longer touches `RuntimeToolRegistry`. Removed-server process termination belongs to the restart path, where the owning process is stopped by definition; removing the live tracking-only cleanup is what removes the orphan-process risk in AC-4.
- `/mcp status` keeps its live probe rows and adds a separate pending section rendered by a helper extracted from `_cmd_mcp_status`, which also brings that function below the radon complexity gate. `/config show` gains the same separation for startup-only fields.
- Restart-time state is unchanged code: `startup_validation`, `startup_mcp_starter`, and the discovery and posture services already build lifecycle, discovery, posture, and registry state from the parsed definitions at startup, which satisfies "rebuild after restart and rediscovery" without a new mechanism.

### Newly rejected inputs (Constraint: stricter parsing changes accepted inputs)
Startup accepts none of these today; `/reload` or the MCP parser accepts them today and will reject them after this Plan. The list is what a maintainer must review before enforcement, and no repository configuration file contains any of them:
- MCP server table: `cmd` as a plain string (today split into single characters); `cmd` containing an empty string; an empty `cmd` sequence; `required`, `enabled`, or `auto_start` given as `"false"`, `"true"`, `0`, or `1`; `startup_timeout_sec` or `max_stderr_log_files` given as a string or a boolean; `call_timeout_sec`, `startup_stagger_delay_sec`, or `max_stderr_log_size_mb` given as a boolean; `role` given as a number; `url` given as a number (today it fails later as an `AttributeError` inside `urlparse`); any key outside the declared MCP key set (today dropped in silence).
- Reload payload: `llm_url`, `memory_embed_url`, or any string field given as a number or boolean; `llm_max_tokens`, `http_timeout`, `memory_max_pinned`, `context_compress_turns`, `tool_max_tool_turns`, `tool_result_max_llm_chars`, or `memory_min_importance` given as a string or a boolean; `llm_temperature` or `retry_base_delay` given as a boolean; `memory_local_only`, `serial_tool_calls`, or `memory_embed_enabled` given as a number or string; `plan_blocked_tools`, `allowed_tools`, `disabled_tools`, or `masked_fields` given as a non-sequence; a removed or moved key such as `tool_safety_tiers` or `approval_risk_rules` in a reload payload (today silently ignored).
