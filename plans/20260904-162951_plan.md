## Goal
- Make protected-branch and ref authorization actually take effect on the code path
  that live MCP tool calls travel (`POST /v1/call_tool` → `RepositoryState.snapshot()` →
  `WriteProtectionPipeline.run()`), for `git_checkout`, `git_pull`, and `git_push` —
  the only three write tools this path currently dispatches.

## Priority
High

## Scope
- **In-Scope**: fixing `RepositoryState.snapshot()`'s placeholder protected-branch
  check and hard-coded `ref_valid`; adding the currently-missing Stage 3
  (authorization) call inside `WriteProtectionPipeline.run()`; injecting
  `GitConfig.protected_branches` into the live path; introducing a structured
  operation-target model for checkout/pull/push; ref/branch normalization and
  rejection rules; HTTP-level regression tests for the live path.
- **Out-of-Scope**: `WriteProtectionPipeline`'s stage ordering/postcondition
  verification beyond adding the missing Stage 3 call (`gitpipeline`);
  detached-HEAD/dry-run precondition behavior (`gitdryrun`); unifying
  `GitService`'s dead-code dispatch table with the live `call_tool` path
  (`gitdispatch`); repository-path containment/audit (`gitpathaudit`); remote
  authorization/concurrency (`gitremote`); deleting the ~60 unused placeholder
  methods this Plan's investigation found in `RepositoryState`/`WriteProtectionPipeline`
  (`gitcleanup`); making `git_add`/`git_commit` reachable via `call_tool` (currently
  not dispatched at all via the live path — `gitdispatch` scope, see Unknowns).

## Background
`docs/adr/ADR-012-git-mcp-server-side-write-enforcement.md` and
`issues/done/20260902-094746_h01_git_mcp_write_protection_status_contradiction.md`
concluded write-protection guards are implemented and tested, covering
`GitService._validate_protected()` (`scripts/mcp_servers/git/git_service.py`, backed
by `test_check_protected_branch`). This Plan's Step 3 investigation found that
conclusion describes a **dead-code path**: `GitMCPServer.dispatch()`
(`scripts/mcp_servers/git/git_server.py:266`), which routes to
`GitService.get_dispatch_table()`, has zero external callers repository-wide
(confirmed via `rg "\.dispatch\("` across `scripts/mcp_servers/`) — the base
`MCPServer` class defines no `/v1/call_tool` route itself, and no code elsewhere
invokes `GitMCPServer.dispatch()`. The route that actually serves
`POST /v1/call_tool` is defined directly in `git_server.py` (line 144) and, for
`git_checkout`/`git_pull`/`git_push`, builds a `RepositoryState` snapshot and runs it
through `WriteProtectionPipeline` — a separate implementation from `GitService` that
`test_git_security_compliance.py` (all 184 existing git-mcp tests, confirmed passing)
does not exercise: every existing test instantiates `GitService` directly, none use
`TestClient` against `POST /v1/call_tool`.

## Problem
Two independent, compounding gaps make protected-branch/ref authorization a no-op on
the live path:
1. `RepositoryState.snapshot()`'s `protected_branch=_is_protected_branch(repo)`
   (`repository_state.py:108`) always evaluates `False` — the module-level
   `_is_protected_branch(repo: git.Repo) -> bool` function (line 752) is a hard-coded
   placeholder that never reads `GitConfig.protected_branches`, and `ref_valid=True`
   (line 109) is never actually validated.
2. **New finding, not previously documented**: even if (1) were fixed,
   `WriteProtectionPipeline.run()` (`repository_state.py:510-531`) never calls
   `RepositoryState.verify_authorization()` — the method that reads
   `protected_branch`/`ref_valid` (lines 78-84) — despite the class's own docstring
   stating "Stages 1-3 (repo path validation, write guard, authorization) are handled
   before pipeline construction." `run()` only executes Stage 5 (preconditions), Stage
   6 (the git operation itself), and Stage 7 (postcondition, itself a placeholder
   always returning `True`). Authorization is not merely broken — it is never invoked
   at all on the live path.
`config/git_mcp_server.toml` already sets `protected_branches = ["main", "master",
"release"]`, but this value reaches neither `_is_protected_branch()` nor any call in
the live pipeline.

## Reason for Change
This combines protected-branch resolution, checkout/pull/push target resolution, and
ref validation because they share the same operation-target model and must land
together — fixing only the placeholder function without also wiring the missing
Stage 3 call would leave authorization silently unreachable, and fixing only the
Stage 3 call without correcting the placeholder would enforce a check that always
passes.

## Implementation intent
Add the missing `verify_authorization()` call to `WriteProtectionPipeline.run()` as an
explicit Stage 3, before Stage 5. Replace `_is_protected_branch()`'s placeholder body
with a real check against `GitConfig.protected_branches`, injected by threading
`protected_branches` through `RepositoryState.snapshot()`'s signature (default `[]` to
preserve existing direct-snapshot call sites in tests) from `git_server.py`'s existing
module-level `_cfg`. Replace `ref_valid=True` with a real check reusing the existing
`_is_safe_ref`-style option-like-ref rejection, extended to reject empty/malformed
values where not semantically valid for the given tool. Introduce a small
operation-target resolution step ahead of `snapshot()` for each of checkout/pull/push
that determines the actual destination branch/local source/remote destination ref
before authorization runs, normalizing `main` and `refs/heads/main` to the same
comparison form.

## Design
This Plan's Step 3 investigation overturned the prior `h01` conclusion
("write-protection guards are implemented and tested") by tracing the actual HTTP
request path rather than trusting `GitService`'s test coverage: `POST /v1/call_tool`
(the only route the base `MCPServer` class does not itself provide, and the only one
`uvicorn` actually serves for this server) builds a `RepositoryState` via `snapshot()`
and runs it through `WriteProtectionPipeline`, entirely bypassing `GitService`.
`GitMCPServer.dispatch()` — the method that would route through `GitService` — has no
caller anywhere in the codebase.

Two independent defects compound on this live path: the protected-branch placeholder
(known, per the issue) and the missing Stage 3 call in `WriteProtectionPipeline.run()`
(new finding). Both must be fixed together — fixing either alone leaves protection
non-functional. This Plan adds Stage 3 as an explicit early step in `run()`, calling
`RepositoryState.verify_authorization()` (which already correctly reads
`protected_branch`/`ref_valid` — that logic was never wrong, only unreached) before
Stage 5's precondition checks.

`protected_branches` reaches `_is_protected_branch()` by threading it through
`RepositoryState.snapshot()`'s signature as a new parameter, defaulting to `[]` so
existing test call sites that construct a `RepositoryState` without caring about
protection continue to work unchanged. `git_server.py` supplies the real value from
its already-existing module-level `_cfg.protected_branches`, following the same
pattern already used for `_cfg.allow_detached_head`.

The operation-target model (REQ-005) is scoped narrowly to what checkout/pull/push
need: checkout's destination is `req.branch` itself (already explicit); pull's target
is the resolved local branch (current branch if `req.branch` is empty) and the
selected remote; push's target is the local source (current branch if `req.branch` is
empty) and the remote destination ref. This avoids introducing a new class/abstraction
per the Deletion-First spirit — it is resolved as plain function logic within
`repository_state.py`, not a new object.

`GitService._validate_protected()` is left unmodified: it is unreachable dead code on
the live path, and this issue's own Constraints prohibit introducing a second
authorization mechanism — the fix belongs entirely in the path that actually serves
requests. Whether `GitService`'s dispatch table is later deleted or merged is
`gitdispatch`'s decision (UNK-01), not this Plan's.
