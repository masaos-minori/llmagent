# Plan: Resolve pyright `reportAttributeAccessIssue` on `git.exc.*` across GitPython call sites

## Goal

Eliminate the 3 pyright `reportAttributeAccessIssue` false positives on `git.exc.<Name>`
attribute access in `scripts/shared/git_helper.py` and
`scripts/mcp_servers/git/git_service.py`, by adding an explicit `import git.exc` at each
call site, without changing any exception-handling behavior. This removes static-analysis
noise that currently masks genuinely new pyright errors on these two files and gives future
copy-paste call sites a clean import pattern instead of the current false-positive-prone one.

## Design

This is a static-analysis-only, import-shape change with no architectural implication:

- **Layering**: `git_helper.py` lives in `scripts/shared/` (shared utility layer, consumed
  by `/context` display code) and `git_service.py` lives in `scripts/mcp_servers/git/`
  (MCP server layer, dispatches git tool calls). Both already depend on the third-party
  `gitpython` package (`import git`); adding `import git.exc` is a same-package,
  finer-grained import of an already-imported dependency — it introduces no new edge in the
  import graph and cannot violate any `lint-imports` contract (contracts govern
  intra-project module boundaries, not stdlib/third-party submodule imports).
- **Root cause**: confirmed via `uv.lock` that the installed `gitpython` is 3.1.50, whose
  `git/__init__.py` only does `from git.exc import (...)` for individual exception classes
  (never `import git.exc`), so pyright has no static declaration that `git.exc` is a valid
  attribute path reachable through the `git` module object — even though it resolves fine at
  runtime via Python's dynamic attribute lookup once the submodule has been imported anywhere
  in the process. Adding an explicit `import git.exc` at each call site makes `git.exc` a
  directly-imported name in that module's namespace, which pyright resolves statically. This
  was verified empirically (see UNK-01 resolution above): a probe file with the same shapes
  produces 0 pyright errors and 0 mypy errors with the explicit import, versus the 3 current
  errors without it.
- **Placement of the new import**:
  - In `git_helper.py`, `import git` is a lazy, function-local import inside
    `get_repo_info()` (guarded by `except ImportError` for environments without gitpython
    installed). `import git.exc` must be added in the same lazy, function-local scope
    (immediately after or alongside the existing `import git` line) to preserve the
    "fast startup when gitpython is unused" property documented in the module's docstring —
    a top-level `import git.exc` here would defeat that guard.
  - In `git_service.py`, `import git` is already a top-level, unconditional import (this
    module is only loaded when the git MCP server is active, so there is no lazy-import
    concern here). `import git.exc` should be added at the top level, next to it.
- **No new suppressions**: per `rules/coding.md`'s suppression-governance rule, `# type:
  ignore` / `# nosec` require inline justification and should not be the default fix. Since
  the probe confirms the import-based fix fully resolves the issue, no suppression is needed
  anywhere in this change.

## Risks

- **Risk**: The explicit `import git.exc` could be flagged by ruff as a redundant/unused
  import if ruff's unused-import detection doesn't recognize the submodule-attribute-access
  usage pattern in `git_service.py` (where only `git.exc.GitError` is referenced, not `git`
  alone, on some code paths). → **Mitigation**: `git` is still directly used elsewhere in
  both files (`git.Repo(...)` in both), so ruff will not flag either import as unused; this
  was structurally verified by reading both files in full (see Design section). Likelihood: low.
- **Risk**: A future contributor could copy the *old* `import git` (without `import git.exc`)
  pattern to a new call site, reintroducing the same pyright false positive elsewhere. →
  **Mitigation**: this is a known-recurring pattern per the requirement's Background
  ("repeated pattern ... not an isolated typo"); no code-level guard fully prevents future
  copy-paste of the old pattern within this plan's scope. Filed as a follow-up issue (see
  below) since it is a process/documentation gap, not something this plan's 2-file change can
  close on its own. Likelihood: medium.
- **Risk**: `gitpython`'s `git/__init__.py` shape could change in a future version bump (e.g.
  if `git.exc` becomes a formally re-exported/typed attribute), making this fix's rationale
  stale. → **Mitigation**: out of scope for this plan (no dependency bump is part of this
  change); the fix is harmless either way — an explicit `import git.exc` remains valid and a
  no-op even if the top-level package later re-exports it. Likelihood: low.
