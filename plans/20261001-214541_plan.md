# Plan: Recover all pending approvals on startup instead of only the most recent

## Goal
Fix `ApprovalRecovery.recover()` so that when multiple pending approvals exist from a prior session, every pending approval is surfaced for resolution rather than silently orphaning all but the newest one. Implements REQ-001 (short purpose: enumerate all pending approvals), REQ-002 (short purpose: define deterministic order/resolution flow), REQ-003 (short purpose: add tests covering multi-pending recovery).

## Priority
Medium

## Scope
- **In-Scope**: Modifying `ApprovalRecovery.recover()` to surface all pending approvals; defining a deterministic order/resolution flow; adding regression tests for multi-pending recovery.
- **Out-of-Scope**: Changing how approvals are requested or resolved during a live session; altering the approval table schema; fixing the TTL inconsistency claim (debunked as false positive in Adversarial Verification).

## Background
`find_all_pending_approvals()` (`scripts/agent/workflow/approval_ops.py`) joins `tasks` and `approvals`, filtering `tasks.status = 'pending_approval' AND approvals.status = 'pending'`, excluding expired entries (24h TTL), ordered by creation descending. Recovery runs during startup (`StartupOrchestrator._recover_pending_approvals()`).

## Problem
`recover()` takes `results[0]`, sets `ctx.workflow.approval_pending = True`, and points `ctx.turn.pending_approval_id` / `pending_approval_task_id` at just that one record. It logs `"Recovered %d pending approval(s); showing last: task=%s approval=%s reason=%s"` (with `%d` format string) but only wires up the latest. Any additional pending approvals stay in the workflow DB in a `pending_approval` state that the current session does not expose or resolve.

## Reason for change
On restart after a crash/shutdown with multiple in-flight approval gates, users are told a count exists but can act on only one. The remainder linger until they expire, then vanish unresolved -- potentially leaving tasks stuck in `pending_approval`.

## Implementation intent
Clarify the intended model: (a) at most one approval may be pending at a time (in which case `find_all_pending_approvals()` returning many is itself suspicious and should be investigated), or (b) multiple approvals can legitimately be pending (in which case recovery must enumerate and let the user resolve each, or queue them). Implement the confirmed model without changing the underlying approval lifecycle.

## Requirements
- `REQ-001`: Enumerate all pending approvals from `find_all_pending_approvals()` and wire up each for resolution (not just `results[0]`).
- `REQ-002`: Define a deterministic order/resolution flow for multi-pending approvals (e.g., FIFO by creation time, or allow `/approve`/`/reject` commands to accept an approval_id argument).
- `REQ-003`: Add regression tests covering multi-pending recovery cases, including assertions that non-wired-up approvals are accounted for (not just that the latest is shown).

## Design
- **Approach**: Iterate over all results from `find_all_pending_approvals()` in `recover()`, setting `ctx.workflow.approval_pending = True` and wiring up each approval's `task_id` and `approval_id` to the context. For the UI layer, emit a warning listing all pending approvals with their IDs and reasons, and instruct the user to use `/approve <approval_id>` or `/reject <approval_id>` for each.
- **Ordering**: Use the existing `ORDER BY a.created_at DESC, a.rowid DESC` from `find_all_pending_approvals()` as the deterministic order — oldest first (reverse of the query result order) so the user resolves approvals in chronological order.
- **State management**: Since `ctx.turn.pending_approval_id` and `ctx.turn.pending_approval_task_id` are single-value fields, the design choice is: (a) surface all approvals in the warning message and let the user resolve them one-by-one via `/approve`/`/reject` commands (minimal change), or (b) add a queue mechanism to track remaining approvals (larger change). Approach (a) is preferred unless the issue confirms that multiple simultaneous approvals are expected.

## Risks
- **Risk**: Multiple pending approvals could cause confusion if the user cannot easily identify which approval corresponds to which task. → **Mitigation**: Warning message includes task_id, approval_id, and reason for each pending approval.
- **Risk**: The single-value fields `ctx.turn.pending_approval_id` and `ctx.turn.pending_approval_task_id` cannot hold multiple values simultaneously. → **Mitigation**: These fields represent the "currently active" approval being presented to the user; the user resolves them one-by-one via `/approve`/`/reject` commands. Other pending approvals remain in the DB until resolved or expired.
