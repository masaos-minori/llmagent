# Plan: EventBus out-of-order ACK skips lower-seq events on resume

## Goal
- Ensure reconnecting consumers re-deliver unacked events even when ACKs arrive out of order, preserving the at-least-once delivery guarantee stated in ADR-006.

## Priority
High

## Scope
- **In-Scope**: Add low-water-mark query for resume position; add index on `consumer_delivery(acked_at)`; update subscribe route to use new resume position; add regression test; update documentation.
- **Out-of-Scope**: Changes to ACK semantics for ordered delivery; changes to consumer-side ordering discipline.

## Background
The EventBus component uses a high-water-mark offset to track acknowledged events. On reconnect, it resumes from `seq > offset`. When ACKs arrive out of order (e.g., ACK(seq=10) before ACK(seq=5)), the offset advances past seq=5, causing it to be skipped on reconnect. This violates the at-least-once baseline stated in ADR-006.

## Problem
When ACK(seq=10) arrives before ACK(seq=5):
- Offset becomes 10
- On reconnect: `start_seq = 10`, so seq=5 is never re-delivered
- Confirmed by reading `delivery_repo.py::ack_event_for_consumer()` and `subscribe_route.py::subscribe()`

ADR-006 states at-least-once delivery (losses not tolerated), which conflicts with the current high-water-mark-only resume logic under out-of-order ACK conditions.

## Reason for change
Without this fix, unacked events are silently lost during reconnect after out-of-order ACKs. Monitoring systems cannot detect or alert on event loss. Consumers cannot implement targeted recovery logic based on missing events.

## Implementation intent
On reconnect, compute the resume position as `max(lowest_unacked_seq, stored_offset)`. This ensures already-acked events above the lowest unacked are skipped (fast-forward) while unacked events below the stored offset are re-delivered (no loss).

## Design
### Current Behavior (Verified Against Source)

1. **Offset is a high-water mark** — `delivery_repo.py::ack_event_for_consumer()`:
   ```sql
   INSERT INTO consumer_offsets(...) VALUES (?, ?)
   ON CONFLICT(consumer_id) DO UPDATE SET
     offset = excluded.offset
   WHERE excluded.offset > consumer_offsets.offset
   ```
   The offset only advances when the new value exceeds the current one. Confirmed.

2. **Resume position derived only from offset** — `subscribe_route.py::subscribe()`:
   ```python
   start_seq = get_consumer_offset(db, consumer_id)
   ```
   Reconnect resumes from `seq > offset`. Confirmed.

3. **Out-of-order ACK causes skip** — If ACK(seq=10) arrives before ACK(seq=5):
   - Offset becomes 10
   - On reconnect: `start_seq = 10`, so seq=5 is never re-delivered
   - Confirmed by reading `delivery_repo.py::ack_event_for_consumer()` and `subscribe_route.py::subscribe()`

4. **ADR-006 states at-least-once (losses not tolerated)** — Confirmed.

5. **No test coverage for out-of-order ACK scenario** — grep across all test files found zero matches for out-of-order ACK patterns. Confirmed.

### Design Decision: Option B

**Rationale:**
- Option A (ordered ACK as consumer obligation) contradicts the at-least-once baseline stated in ADR-006. Consumers cannot reliably ACK in strict seq order under network partition or broker reordering.
- Option B preserves the at-least-once guarantee without requiring consumer-side ordering discipline.
- The existing high-water-mark offset remains useful for fast-forwarding already-acked events; the new logic adds a low-water-mark fallback below it.

### Resume Position Computation (Option B)

On reconnect, compute the resume position as:

```
resume_position = max(lowest_unacked_seq, stored_offset)
```

Where:
- `lowest_unacked_seq` = minimum `seq` among events where `consumer_delivery.acked_at IS NULL` AND `seq <= stored_offset`
- `stored_offset` = current value of `consumer_offsets.offset`

This ensures:
- Already-acked events above the lowest unacked are skipped (fast-forward)
- Unacked events below the stored offset are re-delivered (no loss)
- Events above the stored offset are delivered normally (unchanged)

### SQL Query for Lowest Unacked Seq

```sql
SELECT MIN(e.seq) FROM events e
LEFT JOIN consumer_delivery cd ON e.event_id = cd.event_id
  AND cd.consumer_id = ?
WHERE (cd.acked_at IS NULL OR cd.event_id IS NULL)
  AND e.seq <= ?
```

This requires an index on `consumer_delivery(consumer_id, acked_at)` for efficiency. Without it, the query degrades to a full table scan per reconnect.

Note: The LEFT JOIN condition `(cd.acked_at IS NULL OR cd.event_id IS NULL)` correctly handles two cases:
- `cd.event_id IS NULL`: events with NO `consumer_delivery` record (never attempted for this consumer) — treated as unacked
- `cd.acked_at IS NULL`: events where delivery was attempted but not yet acked

### Clarification Needed

The plan's resume position computation (`max(lowest_unacked_seq, stored_offset)`) does not account for the `since_seq` parameter from the Last-Event-ID header. The actual resume position computation in `subscribe_route.py` uses:
```python
start_seq = since_seq
if consumer_id and start_seq == 0:
    start_seq = get_consumer_offset(db, consumer_id)
if start_seq == 0 and last_event_id is not None:
    start_seq = last_event_id + 1
```

This means the low-water-mark logic should be applied AFTER the `since_seq` determination, not as a replacement for it. The fix should compute `resume_position = max(since_seq, lowest_unacked_seq)` rather than replacing the entire resume position logic.


### Step 2: Add resume position computation function

**File**: `scripts/eventbus/delivery_repo.py`

Add a new function `get_resume_position(conn, consumer_id)`:

```python
def get_resume_position(conn: sqlite3.Connection, consumer_id: str) -> int:
    """Compute the resume position for a reconnecting consumer.

    Returns the maximum of:
      - The stored offset (high-water mark of acknowledged seq values)
      - The lowest unacked seq among events with seq <= stored offset

    This ensures no unacked event is skipped on reconnect while still
    allowing fast-forward past already-acked events.
    """
    # Get stored offset
    row = conn.execute(
        "SELECT offset FROM consumer_offsets WHERE consumer_id = ?",
        (consumer_id,),
    ).fetchone()
    if row is None:
        return 0  # No offset yet — start from beginning

    stored_offset = int(row["offset"])

    # Find lowest unacked seq <= stored_offset
    row = conn.execute(
        "SELECT MIN(e.seq) FROM events e "
        "JOIN consumer_delivery cd ON e.event_id = cd.event_id "
        "WHERE cd.consumer_id = ? "
        "AND cd.acked_at IS NULL "
        "AND e.seq <= ?",
        (consumer_id, stored_offset),
    ).fetchone()

    lowest_unacked = int(row[0]) if row and row[0] else stored_offset

    return max(lowest_unacked, stored_offset)
```
