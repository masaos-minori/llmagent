## Architecture Analysis

### Current Behavior (Verified Against Source)

1. **Offset is a high-water mark** — `delivery_repo.py` line 182-189:
   ```sql
   INSERT INTO consumer_offsets(...) VALUES (?, ?)
   ON CONFLICT(consumer_id) DO UPDATE SET
     offset = excluded.offset
   WHERE excluded.offset > consumer_offsets.offset
   ```
   The offset only advances when the new value exceeds the current one. Confirmed.

2. **Resume position derived only from offset** — `subscribe_route.py` line 126:
   ```python
   start_seq = get_consumer_offset(db, consumer_id)
   ```
   Reconnect resumes from `seq > offset`. Confirmed.

3. **Out-of-order ACK causes skip** — If ACK(seq=10) arrives before ACK(seq=5):
   - Offset becomes 10
   - On reconnect: `start_seq = 10`, so seq=5 is never re-delivered
   - Confirmed by reading `delivery_repo.py::ack_event_for_consumer()` and `subscribe_route.py::subscribe()`

4. **ADR-006 states at-least-once (losses not tolerated)** — ADR-006 line 362:
   > "With out-of-order ACKs, an unacknowledged lower seq is skipped when a consumer resumes, which is in tension with the at-least-once baseline"
   Confirmed.

5. **No test coverage for out-of-order ACK scenario** — grep across all test files found zero matches for out-of-order ACK patterns. Confirmed.

### Design Decision: Option B

**Rationale:**
- Option A (ordered ACK as consumer obligation) contradicts the at-least-once baseline stated in ADR-006. Consumers cannot reliably ACK in strict seq order under network partition or broker reordering.
- Option B preserves the at-least-once guarantee without requiring consumer-side ordering discipline.
- The existing high-water-mark offset remains useful for fast-forwarding already-acked events; the new logic adds a low-water-mark fallback below it.

### Resume Position Computation (Option B)

On reconnect, compute the resume position as:

```
resume_position = max(lowest_unacked_seq, stored_offset)
```

Where:
- `lowest_unacked_seq` = minimum `seq` among events where `consumer_delivery.acked_at IS NULL` AND `seq <= stored_offset`
- `stored_offset` = current value of `consumer_offsets.offset`

This ensures:
- Already-acked events above the lowest unacked are skipped (fast-forward)
- Unacked events below the stored offset are re-delivered (no loss)
- Events above the stored offset are delivered normally (unchanged)

### SQL Query for Lowest Unacked Seq

```sql
SELECT MIN(e.seq) FROM events e
JOIN consumer_delivery cd ON e.event_id = cd.event_id
WHERE cd.consumer_id = ?
  AND cd.acked_at IS NULL
  AND e.seq <= (SELECT offset FROM consumer_offsets WHERE consumer_id = ?)
```

This requires an index on `consumer_delivery(acked_at)` for efficiency. Without it, the query degrades to a full table scan per reconnect.

## Implementation Steps

### Step 1: Add index on consumer_delivery(acked_at)

**File**: `scripts/eventbus/schema.sql`

Add after the `consumer_delivery` table definition:
```sql
CREATE INDEX IF NOT EXISTS idx_consumer_delivery_unacked
  ON consumer_delivery(consumer_id, acked_at);
```

**Rationale**: The low-water-mark query filters on `(consumer_id, acked_at IS NULL)`. An index on `(consumer_id, acked_at)` enables efficient lookup of unacked rows per consumer.

### Step 2: Add resume position computation function

**File**: `scripts/eventbus/delivery_repo.py`

Add a new function `get_resume_position(conn, consumer_id)`:

```python
def get_resume_position(conn: sqlite3.Connection, consumer_id: str) -> int:
    """Compute the resume position for a reconnecting consumer.

    Returns the maximum of:
      - The stored offset (high-water mark of acknowledged seq values)
      - The lowest unacked seq among events with seq <= stored offset

    This ensures no unacked event is skipped on reconnect while still
    allowing fast-forward past already-acked events.
    """
    # Get stored offset
    row = conn.execute(
        "SELECT offset FROM consumer_offsets WHERE consumer_id = ?",
        (consumer_id,),
    ).fetchone()
    if row is None:
        return 0  # No offset yet — start from beginning

    stored_offset = int(row["offset"])

    # Find lowest unacked seq <= stored_offset
    row = conn.execute(
        "SELECT MIN(e.seq) FROM events e "
        "JOIN consumer_delivery cd ON e.event_id = cd.event_id "
        "WHERE cd.consumer_id = ? "
        "AND cd.acked_at IS NULL "
        "AND e.seq <= ?",
        (consumer_id, stored_offset),
    ).fetchone()

    lowest_unacked = int(row[0]) if row and row[0] else stored_offset

    return max(lowest_unacked, stored_offset)
```

```python
def test_out_of_order_ack_no_skip_on_reconnect(
    client: TestClient, tmp_path: Path
) -> None:
    """ACK a higher seq before a lower seq → reconnect must not skip the lower seq."""
    from eventbus import app as eb_app
    from eventbus.db import insert_event
    from eventbus.delivery_repo import (
        ack_event_for_consumer,
        get_resume_position,
    )

    db = eb_app.app.state.db

    # Publish three events
    seq1, _, _ = insert_event(
        db, "evt-oof-1", "t", json.dumps({"data": "1"}), "p", "2026-10-04T00:00:00Z"
    )
    seq2, _, _ = insert_event(
        db, "evt-oof-2", "t", json.dumps({"data": "2"}), "p", "2026-10-04T00:00:00Z"
    )
    seq3, _, _ = insert_event(
        db, "evt-oof-3", "t", json.dumps({"data": "3"}), "p", "2026-10-04T00:00:00Z"
    )
    assert seq1 < seq2 < seq3

    # ACK out of order: ack seq3 before seq2
    _, newly_acked_c, _ = ack_event_for_consumer(
        db, "evt-oof-3", "oof-consumer", "2026-10-04T00:00:00Z"
    )
    assert newly_acked_c
    _, newly_acked_b, _ = ack_event_for_consumer(
        db, "evt-oof-2", "oof-consumer", "2026-10-04T00:00:00Z"
    )
    assert newly_acked_b

    # Verify offset jumped to seq3 (high-water mark)
    offset = get_consumer_offset(db, "oof-consumer")
    assert offset == seq3

    # Compute resume position — should be seq2 (lowest unacked <= offset)
    resume_pos = get_resume_position(db, "oof-consumer")
    assert resume_pos == seq2

    # Verify: reconnect would deliver seq2 and seq3 (not seq1 since it's acked)
    # Note: seq1 was never acked, so it should also be included
    # Actually: seq1 has no consumer_delivery record, so it won't appear in the join
    # We need to handle this case separately
```

## Risks

| Risk | Mitigation |
|---|---|
| LEFT JOIN changes semantics for events never attempted for this consumer | Explicitly document: events with no consumer_delivery record are treated as unacked and will be re-delivered on reconnect |
| Performance degradation on large datasets due to new query | Index on `consumer_delivery(consumer_id, acked_at)` bounds the scan to the consumer's delivery records only |
| Duplicate delivery of events between `lowest_unacked_seq` and `stored_offset` | Duplicates are tolerated by the at-least-once baseline; consumers must handle idempotency |
| Backward compatibility with existing consumers | Existing consumers that ACK in order see no behavior change (lowest_unacked_seq = stored_offset + 1 when all events up to offset are acked) |

## Assumptions

1. At-least-once delivery (losses not tolerated) is the correct baseline — confirmed by ADR-006.
