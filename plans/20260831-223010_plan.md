# Plan: Separate repl_health.py into Five Concern Classes

## Goal
- Split `scripts/agent/repl_health.py` (666 lines, 13 functions/classes) into five focused modules, each owning one concern: MCP service health checks, tool-definition validation, workflow schema validation, routing-drift validation, and security-defaults auditing. Reduce coupling between startup pipeline imports and health-check logic.

## Priority
High

## Scope
- **In-Scope**: Refactor `repl_health.py` into five modules under `scripts/agent/services/`; update import sites (`startup.py`, `mcp_status.py`, `mcp_tool_discovery.py`); migrate test files to match new module layout
- **Out-of-Scope**: Changes to `shared/` models/types used by repl_health; changes to `agent/lifecycle.py`; changes to `agent/orchestrator.py` beyond existing patterns

## Background
`repl_health.py` has grown to 666 lines mixing five distinct concerns:
1. MCP service health probing (`_probe_mcp_health_detail`, `check_service_health`)
2. Tool-definition runtime validation (`_validate_tools_response`, `_collect_server_tool_names`, `_check_tool_definitions`, `check_tool_definitions_runtime`)
3. Workflow schema validation (`check_workflow_definition`, `SchemaCheckResult`, `check_workflow_schema`)
4. Routing-drift validation (`check_routing_drift`, `check_routing_safety_tiers`)
5. Security-defaults auditing (`audit_security_defaults`, `_load_audit_config_or_warn`)

This mirrors the `orchestrator.py` decomposition (commit `25eb40b56`) which split 1,500+ lines into six concern classes. The same pattern applies here: separate concerns into `scripts/agent/services/` where other services already live.

## Problem
The monolithic `repl_health.py` creates import cycles (e.g., lazy import in `startup.py:324`), makes it hard to locate specific health-check logic, and violates single-responsibility — each function touches unrelated domain knowledge.

## Reason for change
The file has accumulated 19 commits since its creation, growing from ~200 lines to 666. The import cycle workaround in `startup.py:324` ("lazy import: avoids a module-level import cycle") confirms architectural tension. Other services in `scripts/agent/services/` follow the same concern-separation pattern already established by the orchestrator decomposition.

## Implementation intent
Extract each concern into its own module under `scripts/agent/services/`, following the existing pattern from `scripts/agent/services/mcp_status.py` and `scripts/agent/services/mcp_tool_discovery.py`. Keep public API surface backward-compatible during migration: re-export old names from `repl_health.py` as aliases until all callers are updated. Update import sites incrementally. Migrate tests to import from new locations.

## Requirements
- `REQ-001`: Each extracted module must own exactly one concern with no cross-concern dependencies
- `REQ-002`: Public API must remain backward-compatible during migration (old names re-exported from `repl_health.py`)
- `REQ-003`: All existing tests must pass after migration
- `REQ-004`: No new import cycles introduced
- `REQ-005`: Startup pipeline must work identically after migration

## Design

### Module layout
Following the existing pattern established by `scripts/agent/services/mcp_status.py` and `scripts/agent/services/mcp_tool_discovery.py`:

```
scripts/agent/services/
├── mcp_health.py          # MCP service health checks
│   ├── _probe_mcp_health_detail(ctx) -> McpHealthProbeResult
│   ├── check_service_health(ctx) -> HealthCheckResult
│   └── check_readiness(ctx, production_mode=False) -> HealthCheckResult
├── tool_validation.py     # Tool-definition runtime validation
│   ├── _validate_tools_response(response) -> list[str]
│   ├── _collect_server_tool_names(ctx) -> tuple[set[str], list[str]]
│   ├── _check_tool_definitions(ctx) -> list[str]
│   └── check_tool_definitions_runtime(ctx) -> HealthCheckResult
├── workflow_schema.py     # Workflow schema validation
│   ├── SchemaCheckResult (dataclass)
│   ├── check_workflow_definition(workflows_dir) -> None
│   └── check_workflow_schema(db_path) -> SchemaCheckResult
├── routing_drift.py       # Routing-drift validation
│   ├── check_routing_drift(ctx, strict=False) -> list[str]
│   └── check_routing_safety_tiers(ctx) -> list[str]
└── security_audit.py      # Security-defaults auditing
    ├── _load_audit_config_or_warn[T](...) -> T | None
    └── audit_security_defaults(...) -> list[str]
```

### Migration strategy
1. **Create new modules** with extracted code, keeping original function signatures and behavior
2. **Update import sites** one at a time: `mcp_status.py`, `mcp_tool_discovery.py`, then `startup.py`
3. **Keep backward-compatible re-exports** in `repl_health.py` during transition
4. **Migrate tests** to import from new locations
5. **Remove old re-exports** once all callers updated

### Import compatibility layer
During migration, `repl_health.py` becomes:
```python
"""Backward-compatibility re-exports for repl_health consumers."""
from agent.services.mcp_health import _probe_mcp_health_detail, check_service_health, check_readiness
from agent.services.tool_validation import ...
# etc.
```

This ensures no caller breaks until they are explicitly updated.
