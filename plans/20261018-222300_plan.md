# Plan Output Template (Canonical)

## Goal
Add a pre-bind, fail-closed security-posture gate to `mdq-mcp` so it refuses to bind HTTP when its posture is invalid, matching every sibling MCP server.

## Priority
Medium

## Scope
- **In-Scope**:
  - Build the MDQ security posture once at module import, reusing `build_mdq_posture()` / `validate_mdq_security()`.
  - Add `_enforce_posture_gate()` to `mdq_server.py` that raises `SystemExit(1)` when the posture is not validated, and call it in `__main__` before `server.run_http()`.
  - Extract the dependency-collection logic currently inside `check_health()` into a reusable helper shared by `/health` and the import-time posture build.
  - Add `test_mdq_health_posture.py` asserting the fail-closed startup gate, mirroring the sibling servers.
- **Out-of-Scope**:
  - Changing how MDQ computes or publishes its security posture on `/health`.
  - Modifying any other MCP server's `_enforce_posture_gate()`.
  - Changing `MCPServer.run_http()`.
  - Altering the module-level empty-token guard or the per-request `allowed_dirs` authorization.
  - Any documentation update (see Documentation Impact).

## Background
Every MCP server except `mdq-mcp` defines `_enforce_posture_gate()` and calls it in its `__main__` before `MCPServer.run_http()`. The gate reads a module-level `SecurityPosture` and exits the process before binding when `validated` is false, logging the failed check ids and reason codes. Each sibling ships a `test_*_health_posture.py` that asserts this fail-closed startup. `mdq-mcp` has no such gate: its `__main__` calls only `server.run_http()`, and its only startup guard is a module-level check that rejects an empty Bearer token. Its full security posture is computed by `check_health()` and published on the `/health` endpoint only.

## Problem
`mdq_server.py`'s `__main__` binds HTTP before any misconfiguration (missing DB, schema error, empty `allowed_dirs`, etc.) is detected; the misconfiguration is discovered only on the next `/health` probe, after the server is already accepting connections. Every other MCP server refuses to bind instead. The gap is a deviation from the shared MCP startup contract described by ADR-003 (Static Availability) and ADR-004 (fail-closed).

## Reason for change
The missing gate is a contract inconsistency with all sibling servers and leaves an unnecessary bind-before-detect window. Closing it restores parity and fails closed on misconfiguration before listening, like its peers.

## Implementation intent
Bring `mdq-mcp` in line with the other servers: compute its security posture once at import (as siblings do), expose it via a module-level `_security_posture`, add `_enforce_posture_gate()` that reads `.validated` and raises `SystemExit(1)` when invalid, and call the gate in `__main__` before `run_http()`. The posture is built by reusing the existing `build_mdq_posture()` / `validate_mdq_security()` machinery; no new posture definition is introduced. Because MDQ's posture depends on runtime dependency state (db presence, schema, index stats) that `check_health()` currently gathers inline, that collection is extracted into a reusable helper shared by `/health` and the import-time build.

## Requirements
- `REQ-001`: The MDQ entry point validates its security posture as a fail-closed gate before binding HTTP and exits non-zero (`SystemExit(1)`) when the posture is not validated, mirroring the sibling servers.
- `REQ-002`: The MDQ security posture is computed once at module import via `build_mdq_posture()` / `validate_mdq_security()`, exposed as a module-level `_security_posture` readable as `.validated`.
- `REQ-003`: The dependency-collection logic currently inside `check_health()` is extracted into a reusable helper shared by `/health` and the import-time posture build, with no behavior change to `/health`.
- `REQ-004`: A `test_mdq_health_posture.py` asserts the gate passes on a validated posture and fails closed (`SystemExit(1)`, logging failed check ids and reason codes) on an invalid posture, mirroring the sibling tests.
- `REQ-005`: The module-level empty-token guard, the per-request `allowed_dirs` authorization, and every other MCP server's gate are unchanged.

## Design
Path A (small task): affects 3 files, no public/runtime interface change, no database schema change. The posture is built once at import like the siblings, exposing a module-level `_security_posture`; the gate reads `.validated`. Because MDQ's posture depends on runtime dependency state that `check_health()` currently gathers inline, that collection is extracted into a reusable helper in `health_check.py` (kept there, not moved to `mdq_security_validation.py`, to respect the `mcp_servers → db, shared` import layer). The helper returns `(mdq_cfg, db_file_present, schema_error, schema_checked, index_stats)`; `check_health()` and the import-time build both consume it, so `/health` behavior is unchanged. The gate runs only in `__main__`, so importing the module in tests does not trigger `SystemExit`. `run_startup_validation()` never raises, so the import-time build cannot crash the module.

- **Risk**: Building the posture at import connects to the DB or reads config earlier than today. → **Mitigation**: `MdqService` already connects to the DB and creates tables at import (`_service = MdqService()`), so no new side effect is introduced; `run_startup_validation()` never raises, and the gate runs only in `__main__`, so importing the module in tests does not trigger `SystemExit`.
- **Risk**: A fresh install with an empty DB could be misread as an invalid posture. → **Mitigation**: `_index_check` returns OK when documents and FTS rows are both zero, so a fresh install yields a validated posture; `validated` reflects config validity, not index population.
- **Risk**: A malformed config could raise during the import-time build. → **Mitigation**: The posture build is independent of `_service` construction and never raises; keep the two paths separate.
