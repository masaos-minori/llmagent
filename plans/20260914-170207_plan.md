# Plan: Correct subscription replay boundaries, batching, and reconnect semantics

## Goal

Establish a deterministic replay algorithm for EventBus subscriptions that eliminates duplicated or lost events across reconnects by replacing offset-based pagination with keyset pagination, defining a shared resume-position convention, and ensuring safe replay-to-live handoff.

## Priority
High

## Scope
- **In-Scope**: Replay/reconnect boundary logic in `scripts/eventbus/subscribe_route.py`, its resume-position calculation, and associated tests
- **Out-of-Scope**: Unrelated route handlers, producer-side changes, consumer-side acknowledgment logic, SSE transport-level behavior

## Background
The EventBus subscription endpoint (`/subscribe`) replays historical events from SQLite before switching to live broker delivery. The current implementation has three interrelated problems: offset-based pagination can emit duplicates or skip events, the replay-to-live handoff is not guaranteed to avoid gaps or overlaps, and three resume-position inputs (`since_seq`, consumer offsets, Last-Event-ID) lack a unified boundary convention.

## Problem
An unfiltered subscription's historical replay relies on offset-based pagination without a defined deterministic order, risking duplicated or skipped events. The replay-to-live handoff point lacks guarantees against gaps or overlaps. Three resume inputs (`since_seq`, consumer offsets, Last-Event-ID) are interpreted independently rather than through a shared boundary convention, causing inconsistent sequence resolution across reconnects.

## Reason for change
These tasks share the same replay-position model and subscription loop. Implementing them separately would risk inconsistent sequence semantics and duplicate fixes.

## Implementation intent
Create one deterministic replay algorithm that terminates, preserves sequence continuity, and transitions safely to live delivery. Centralize resume-position calculation behind one testable function so `since_seq`, consumer offsets, and Last-Event-ID all resolve through the same boundary convention.

## Requirements
- `REQ-001`: Replace offset-based pagination with keyset pagination based on the last emitted sequence number in the unfiltered replay query.
- `REQ-002`: Capture a replay ceiling at subscription start so events published during replay are handled by the live-delivery path.
- `REQ-003`: Define resume positions consistently as either the last successfully processed sequence number or the next sequence to read; set the Last-Event-ID-derived boundary so the next sequence is included.
- `REQ-004`: Align `since_seq`, consumer offsets, and Last-Event-ID semantics under one shared convention.
- `REQ-005`: Document the precedence rule for conflicting resume inputs.
- `REQ-006`: Centralize resume-position calculation in a testable function.
- `REQ-007`: Ensure the replay loop terminates and transitions to live broker delivery.
- `REQ-008`: Ensure deterministic ordering in the replay query (ORDER BY seq).
- `REQ-009`: Update active EventBus design documents (`docs/eventbus`) to describe the replay boundary/precedence convention after implementation evidence is available.
- `REQ-010`: No event is lost or duplicated across reconnect boundaries.

## Design

### Keyset Pagination Replacement (REQ-001)
Replace the offset-based replay query:
```sql
SELECT ... FROM events WHERE seq > ? ORDER BY seq LIMIT ? OFFSET ?
```
With keyset pagination using the last emitted sequence number:
```sql
SELECT ... FROM events WHERE seq > ? AND seq <= ? ORDER BY seq LIMIT ?
```
Where `?` placeholders are `(start_seq, replay_ceil + batch_size, batch_size)`. This eliminates the OFFSET clause entirely, ensuring deterministic ordering regardless of concurrent inserts.

The replay loop becomes:
1. Query: `WHERE seq > start_seq AND seq <= replay_ceil + batch_size ORDER BY seq LIMIT batch_size`
2. Emit events, updating `replay_ceil` for each emitted event
3. If fewer than `batch_size` rows returned, break (end of data)
4. Otherwise, set `start_seq = replay_ceil + 1` and continue

### Replay Ceiling Capture (REQ-002)
Capture `replay_ceil = start_seq - 1` at subscription start (before entering the replay loop). This represents the highest sequence number that should be covered by replay. Any event with `seq > replay_ceil` will be handled by the live-delivery path.

This ensures:
- Events published between the final replay batch and live path startup are caught by the live path
- No event falls through the gap between replay and live phases

### Resume Position Convention (REQ-003, REQ-004)
Define two semantic types for resume positions:
- **Last processed**: The sequence number of the last successfully received event (inclusive)
- **Next to read**: The sequence number of the next event to receive (exclusive)

Each resume input maps to one type:
- `since_seq`: Next to read (current semantics preserved)
- Consumer offset: Last processed (stored as the acknowledged sequence)
- Last-Event-ID: Last processed (browser sends the last seen event ID; we add 1 to get next to read)

The unified calculation function resolves all three inputs to a single "next to read" value.

### Precedence Rule (REQ-005)
When multiple resume inputs are provided:
1. `since_seq` takes priority if non-zero
2. Consumer offset is used only when `since_seq == 0` and `consumer_id` is present
3. Last-Event-ID is the fallback when both `since_seq == 0` and no consumer offset exists

This precedence is deterministic and documented.

### Centralized Resume-Position Calculation (REQ-006)
Extract resume-position resolution into a standalone function:
```python
def resolve_resume_position(
    since_seq: int,
    consumer_id: str,
    last_event_id: int | None,
    db: sqlite3.Connection,
    max_seq: int,
) -> tuple[int, str]:
    """Resolve resume position from multiple inputs.
    
    Returns:
        Tuple of (start_seq, source) where source indicates which input was used.
    """
```

### Replay Loop Termination (REQ-007)
The replay loop terminates when:
1. A partial batch is returned (fewer rows than `batch_size`)
2. Zero rows are returned (no more data)
3. `start_seq > replay_ceil` (all replayed data consumed)

After termination, the live-delivery phase begins immediately.

### Deterministic Ordering (REQ-008)
Maintain `ORDER BY seq` in the replay query. With keyset pagination, this guarantees consistent ordering even under concurrent inserts.
