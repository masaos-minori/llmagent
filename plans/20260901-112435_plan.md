## Background
An ADR's own Known Deviations section and the area's canonical Known Issues document both
describe the same underlying gaps by Known Issue ID, but nothing currently checks that their
Status fields agree. This session's ADR-008/ADR-012 work found multiple cases where they had
drifted apart, each caught only by an agent manually cross-checking code, tests, and both
documents by hand.

## Problem
(Evidence: Explicit in issue, confirmed by repository inspection) No existing tool in `tools/`
cross-references an ADR's Known Deviations section against the corresponding canonical Known
Issues document's Status field for the same Known Issue ID. `tools/check_docs_consistency.py`
does not reference `docs/adr/` at all (confirmed: no `adr` match in that file's source other
than an unrelated `--skip schemadrift` example), and `tools/check_needs_confirmation_inventory.py`
checks Needs-Confirmation markers against a single central inventory, not ADR-vs-Known-Issues
Status agreement.

## Reason for change
Without this check, an ADR can silently drift out of sync with the canonical Known Issues
record in either direction, and the only way to catch it currently is an agent noticing during
unrelated work, as happened repeatedly this session. Adversarial verification against the
current repository (see Design) confirms this gap is still live today: `docs/04_mcp_90_inconsistencies_and_known_issues.md`'s `MCP-004` entry now shows
`Status: resolved`, but `docs/adr/ADR-012-git-mcp-server-side-write-enforcement.md`'s Known
Deviations section still lists `MCP-004` as an active (`**Known Issue**:`, not `**Resolved**:`)
deviation — a genuine, currently-uncorrected disagreement, not a stale example from the
Issue's original session.

## Implementation intent
Reuse `tools/_docs_consistency_lib.py`'s `DocFile`/`Issue`/`discover_md_files`/`report_and_exit`
helpers, following the same shape as `tools/check_needs_confirmation_inventory.py` (parse
per-ID entries out of one document type, parse ID references out of other documents, cross-check,
report `Issue` objects). Two new pieces of parsing logic are needed that no existing tool
provides: (1) extracting `### <ID>: <Title>` entries and their Status field from a canonical
Known Issues document, tolerant of the multiple structural entry formats actually observed
(see Design); (2) extracting Known Issue ID tokens from an ADR's `## Known Deviations` section
and its `## Related Documents` → `### Known Issues` subsection, anchored narrowly enough to avoid
false positives from ADR prose that merely mentions an ID-shaped string (see Design and Risks).

## Design
Follow the shape of `tools/check_needs_confirmation_inventory.py` (the closest existing analog):
parse per-ID entries out of one document family, parse ID references out of a second document
family, cross-check, emit `Issue` objects, and finish with `report_and_exit`. Two pieces of new
parsing logic are required, both grounded in structural findings from this Plan's own
verification (not assumed):

1. **Canonical-doc Status extraction (REQ-001)**: a per-document parser that walks
   `### <ID>: <title>` boundaries (reusing `discover_md_files` to get `DocFile.lines`) and
   extracts each entry's Status using two alternate patterns tried in order: the bullet-list
   form `^- \*\*Status\*\*:\s*(\S+)` (matches `04_mcp_90`, `05_agent_90`, and `90_shared_90`'s
   `CI-*` entries), falling back to the inline-prose form `Status:\s*([a-zA-Z ]+?)\s*/` (matches
   `90_shared_90`'s `SHARED-*` entries). An entry with neither form present is treated as
   unparseable and skipped with a note, not silently ignored.
2. **ADR-side ID extraction (REQ-002)**: restricted to two locations only — the `## Known
   Deviations` section's bullets (any bold label, e.g. `**Known Issue**:`, `**Resolved**:`)
   and the `## Related Documents` → `### Known Issues` subsection's parenthetical ID mentions.
   A candidate ID token must match `[A-Z]+-\d+` and be immediately followed by whitespace, an
   em-dash, or end-of-line — this lookahead is the specific fix for the
   `ADR-004-D1-profile-config-model-still-present` false-match case found during verification
   (a naive `[A-Z]+-\d+` match without this lookahead would incorrectly extract `ADR-004` as a
   candidate ID). A bullet whose first token after the label does not match this pattern (e.g.
   ADR-005's backtick-led `sqlite-vec` bullet) contributes no ID and is not reported as anything,
   per the Issue's own false-positive-avoidance constraint.
3. **ADR-side status signal (REQ-004, UNK-03)**: a bullet is "resolved-like" only when its label
   is literally `**Resolved**:`; every other Known-Deviations bullet is "open-like" — this mirrors
   the Issue's own example ("an ADR's Known Deviations already removed an entry as resolved"),
   i.e. the absence of an active-deviation bullet for a given ID is the same "resolved-like"
   signal from the ADR's side as an explicit `**Resolved**:` label.
4. **Cross-document resolution (REQ-003)**: resolve every extracted ID against the union of all
   `discover_md_files(DOCS_DIR, prefix="")` results filtered to filenames ending in
   `_90_inconsistencies_and_known_issues.md`, not a hardcoded three-path list — required by the
   `EVENTBUS-008` evidence (AC-4).

No change to `tools/_docs_consistency_lib.py` is needed — `check_needs_confirmation_inventory.py`
already establishes the precedent that a new checker defines its own local per-ID parsing rather
than extending the shared lib, and this Plan follows the same pattern to keep the file count at
three (Path A).

## Risks
- **Risk**: A canonical Known Issues document introduces a fourth Status-field structural
  format not covered by REQ-001's two patterns (bullet-list, inline-prose), silently producing
  an "unparseable" skip rather than a mismatch report. → **Mitigation**: the live-repository
  Acceptance Criteria (AC-1..AC-4) exercise real content from all documents in scope, giving
  early signal; the "unparseable, skipped, noted" behavior (Design item 1) fails visibly rather
  than silently misclassifying.
- **Risk**: The false-positive-avoidance token-anchoring rule (REQ-002) is itself imperfect for
  an ID-shaped free-text mention not yet observed in the repository. → **Mitigation**: scope is
  explicitly narrowed to the `## Known Deviations` bullets and `## Related Documents` → `###
  Known Issues` subsection only (never whole-document prose), per the Issue's own constraint;
  AC-7 pins the one concrete false-positive case found during verification as a regression test.
- **Risk**: Extending cross-document resolution beyond the Issue's three named documents (REQ-003)
  could be read as scope creep beyond the literal Required Changes text. → **Mitigation**: the
  Issue's own wording is "at least" those three, and the Issue's Implementation Intent already
  describes the mechanism generically ("each area's canonical
  `docs/{area}_90_inconsistencies_and_known_issues.md`"); omitting this would produce a proven,
  reproducible false-positive (`EVENTBUS-008`, AC-4) that directly contradicts the Issue's own
  Constraints ("avoid false positives").
- **Risk**: `docs/adr/ADR-008-sqlite-4db-separation.md`'s Known Deviations section is currently
  written in Japanese, which does not affect ID-token extraction (the ID and label tokens are
  ASCII/English regardless) but is a pre-existing, separate documentation-language drift
  (`skills/DESIGN.md` Output language) discovered during verification. → **Mitigation**: out of
  scope for this Plan (source/docs are not modified by this workflow phase); noted here only so
  a future documentation pass is aware of it.
- **Risk**: `docs/03_rag_90_inconsistencies_and_known_issues.md` defines no `### <ID>` headings
  at all, so every RAG-area ID an ADR references (`DESIGN-1`, `DESIGN-2`) will always report as
  dangling until that document adopts the heading convention — a pre-existing documentation gap,
  not a defect introduced by this tool. → **Mitigation**: this is the intended, correct behavior
  per REQ-005 and is pinned as AC-3, not treated as a bug to fix in this Plan.
