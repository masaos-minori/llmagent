## Goal
Add an optional `class` front-matter field (enum of the 7 documented document
classes) to `schemas/doc_front_matter.json`, extend the shared schema-loading
helper and `tools/manage_frontmatter.py` to support it, and resolve the
already-tracked `NC-032` (`additionalProperties` strict-vs-permissive) in the same
change.

## Priority
Medium

## Scope
- **In-Scope**: the optional `class` schema property; an explicit, documented
  `additionalProperties` decision resolving `NC-032`; a new
  `tools/manage_frontmatter.py` subcommand that classifies documents in
  dry-run/report mode; documenting the new field; removing `NC-032` from the
  active inventory; unit tests.
- **Out-of-Scope**: actually classifying all existing documents (a separate,
  larger bulk-classification effort); extending `check_docs_structure.py`'s
  `check_schema_compliance` to enforce the new `class` enum (not requested by the
  source issue's Acceptance Criteria, which only requires no regression — see
  Risks).

## Background
Confirmed by reading `schemas/doc_front_matter.json`: `required` lists exactly
`title`/`area`/`tags`/`related` (line 5); no `class` property exists;
`additionalProperties: true` (line 6) is the current permissive setting `NC-032`
(`docs/00_governance_03_issue-and-uncertainty-management.md:722-748`) tracks as an
open question. Confirmed: `docs/00_governance_01_documentation-policy.md`'s
Document Classification (lines 44-52) defines exactly 7 classes (Governance,
Guide, Specification, Reference, Operations, Note, Known Issues). Confirmed:
`tools/_front_matter_schema.py` is the shared, single-source-of-truth loader both
`tools/manage_frontmatter.py` (line 39, 209) and `tools/check_docs_structure.py`
(lines 23, 249) already use for `required_fields`/`area_enum`/`status_enum` — its
own docstring states its purpose is to avoid "each tool hardcoding its own copy."
Its `FrontMatterSchema` dataclass currently has no `class_enum` field, so it must
be extended for the new `class` property to flow through this same
single-source-of-truth path rather than a third hardcoded copy of the 7-class
list (alongside the policy doc and the JSON schema). Confirmed:
`NC-032`'s own Evidence notes that some `docs/*.md` files (e.g. RAG documents)
already use non-required extension keys (e.g. `source:`) under the current
permissive setting, and its Required Action calls for "a survey of which
documents currently use non-required front-matter keys, before ... CI-enforcement
implementation begins" — no such survey has been completed (confirmed: no
tracking issue or plan references this survey).

## Problem
Any automated process that needs to act only on Reference-class (or any
specific-class) documents currently has no mechanical way to identify a
document's class; it requires reading each document's content.

## Reason for change
Both the mechanical-content check work and any Reference-class migration benefit
from selecting "all `class: Reference` documents" without manual classification.
Resolving `NC-032` alongside this change avoids a second schema edit shortly
after this one, and adding a new known property is the natural point to also
decide whether to close off unknown ones.

## Implementation intent
Add `class` as an optional enum field to `schemas/doc_front_matter.json` with the
7 documented values. Extend `tools/_front_matter_schema.py`'s `FrontMatterSchema`
with a `class_enum` field (mirroring `area_enum`/`status_enum`) so the schema
remains the single source of truth. Add a new `tools/manage_frontmatter.py`
subcommand (`classify`) that infers `class` where confidently derivable and
reports the rest as ambiguous, following `add-missing`'s existing
never-guess/report-ambiguous pattern (confirmed at
`tools/manage_frontmatter.py:224-231`). Decide `additionalProperties` explicitly
in the same schema edit (see Design for the recommended decision and its
rationale), resolving `NC-032`.

## Assumptions
- **Recommended `additionalProperties` decision (`REQ-002`)**: keep
  `additionalProperties: true` (unchanged from its current value), now as an
  explicit, documented decision rather than an unexamined default — reason:
  `NC-032`'s own Evidence confirms area-specific extension keys (e.g. `source:`
  in RAG documents) are already in legitimate active use, and its own Required
  Action states that flipping to `false` requires a completed survey of which
  documents use non-required keys first; no such survey has been done (confirmed
  above). Setting `false` now would immediately break schema validation for
  every file using an undocumented extension key, per `NC-032`'s own stated
  Impact. This recommendation resolves `NC-032` as "decided permissive, with
  survey-then-revisit as a distinct, separately-tracked follow-up if desired" —
  the accountable party may override this recommendation before
  `plan-to-implementation-procedure` proceeds (see `rules/coding.md` "Explicit
  sign-off gates"; the sign-off channel is a comment on this Plan).
- `classify`'s inference heuristics ("existing area-guide/heading conventions")
  are limited to signals already used elsewhere in the repo (e.g. a document-guide
  file's own stated class, or a filename/heading pattern matching one of the 7
  class names) — exact heuristic rules are an implementation-time design choice
  within `REQ-004`'s "never guess, report ambiguous" constraint, not fixed by
  this Plan.
- No `--fix` write mode is added for `classify` in this issue's scope — the
  source issue's Acceptance Criteria only requires dry-run/report mode ("runs ...
  in a dry-run/report mode ... without modifying any file"); a future
  bulk-classification issue (explicitly Out of Scope here) would add the write
  path.

## Risks
- **Risk**: `check_docs_structure.py`'s `check_schema_compliance` does not
  validate the new `class` enum (only `area`/`status` are hardcoded, confirmed at
  lines 115-130) — a document could carry an invalid `class` value and no
  automated check would catch it, undermining `REQ-001`'s "rejects an invalid
  one" criterion for anything beyond raw JSON Schema validation. →
  **Mitigation**: `REQ-001`'s Acceptance Criterion is satisfied at the JSON
  Schema level (a schema-validating tool/library rejects an invalid enum value);
  extending `check_schema_compliance` with a `class_enum` check mirroring its
  existing `area_enum`/`status_enum` blocks is explicitly out of this Plan's
  scope (not requested by the source issue) but is a natural, low-effort
  follow-up — noted here rather than silently assumed.
- **Risk**: The accountable party disagrees with this Plan's recommended
  `additionalProperties: true` decision (Assumptions) and prefers `false` with an
  immediate audit. → **Mitigation**: the sign-off channel (a comment on this
  Plan) is the point to override before `plan-to-implementation-procedure`
  proceeds, per `rules/coding.md` "Explicit sign-off gates."
