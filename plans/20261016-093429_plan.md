## Goal
- Make a pinned semantic memory reach every new session regardless of `min_importance`, as `docs/23_agent/agent_11_01_memory-overview-and-modes.md` states, and lock that behavior with tests at the real retriever/SQLite boundary.

## Priority
Medium

## Scope
- **In-Scope**: change the session-start query so pinned semantic memories bypass the importance threshold; add tests for pinned/unpinned handling at the retriever level and through `MemoryInjectionService.on_session_start()` with a real retriever over an in-memory SQLite.
- **Out-of-Scope**: `/memory` subcommands, pin limit, `rebuild` replay and JSONL change events (mem001); retrieval scoring and `on_user_prompt` injection; injecting pinned episodic memories; the `max_semantic` cap versus `memory_max_pinned`; production deployment.

## Background

The one uncovered item is M-1-4, a test that a pinned memory is injected at the next session start. Checking it showed that the code does not match the documented behavior.

## Problem
- `HybridRetriever.top_semantic()` in `scripts/agent/memory/retriever.py` selects `WHERE memory_type = 'semantic' AND importance >= ?` for every row and only orders by `pinned DESC`. A pinned memory whose importance is below `min_importance` is therefore not returned, while `agent_11_01` states pinned entries are always injected regardless of the importance threshold.
- No test sets `pinned=True` on the session-start path: `tests/agent/memory/test_memory_layer.py` `TestOnSessionStart` mocks the retriever, and `TestTopSemantic` in `tests/agent/memory/test_memory_retriever.py` has only `test_pinned_entry_ordered_first` (a pinned row at importance 0.5 with no `min_importance` and no `limit` pressure), so no test covers a pinned row below the threshold or session-start injection of a pinned row.
- Default `memory_min_importance` is 0.5 in `config/agent.toml` (0.3 in the dataclass), so a low-importance pin is a realistic case.

## Reason for change
Pin is only meaningful if a pinned memory reliably reaches the next session. The current query silently drops a pinned memory below the threshold, and nothing would catch a regression in this path.

## Implementation intent
- Keep the change inside the single SQL predicate of `top_semantic()`: a row qualifies when it meets the threshold or is pinned. Ordering, branch filter, `memory_type`, and `LIMIT` stay as they are.
- Put the new tests next to the existing `TestTopSemantic` tests, which already run against a real in-memory SQLite, instead of adding more mock-based tests.
- Do not touch `MemoryInjectionService`; its behavior is unchanged and is exercised end to end by one new test.

## Requirements
- `REQ-001`: `top_semantic()` returns a pinned semantic memory even when its importance is below `min_importance`; an unpinned memory below the threshold is still excluded.
- `REQ-002`: Tests at the retriever level cover a pinned memory above the threshold, a pinned memory below the threshold, an unpinned memory below the threshold, and pinned memories being returned before unpinned ones within `limit`.
- `REQ-003`: A test drives `MemoryInjectionService.on_session_start()` with a real `HybridRetriever` over a temporary SQLite and shows that a pinned low-importance memory appears in the returned snippets.
