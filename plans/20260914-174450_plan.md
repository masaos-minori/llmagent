# Plan: Define publish durability, recovery, and operational observability

## Goal

Make post-commit partial failures observable and recoverable without changing the documented publish success criterion (database commit) unintentionally.

## Priority
Medium

## Scope
- **In-Scope**: Publish-path durability/observability — declaring canonical store, adding metrics for JSONL append and broker notification failures, documenting recovery procedures
- **Out-of-Scope**: Unrelated broker or subscribe logic changes beyond what recovery/metric additions require

## Background
Both the JSONL append and the live broker notification happen after the database commit in the publish path, but partial failures in either step after that commit are not currently observable or documented as recoverable, risking silent data/notification loss without changing the documented publish-success criterion.

## Problem
It is not documented (or verified) whether SQLite or the JSONL file is the canonical event store; if JSONL append fails after a successful database commit, there is currently no metric or health signal surfacing that failure, nor a defined reconciliation/rebuild mechanism if JSONL turns out to be derived data. Similarly, if the live broker notification fails after a successful commit, there is no metric for that failure, and it is not verified that subscribers can still recover the missed notification through SQLite-backed replay.

## Reason for change
JSONL append and broker notification both occur after database commit. Their failure handling depends on the same canonical-store and recovery decision.

## Implementation intent
Make post-commit partial failures observable and recoverable without changing the documented publish success criterion (database commit) unintentionally.

## Requirements
- `REQ-001`: Declare SQLite or JSONL as the canonical event store.
- `REQ-002`: Add a metric or health signal for JSONL append failures.
- `REQ-003`: Provide a deterministic reconciliation or rebuild mechanism if JSONL is derived data.
- `REQ-004`: Document behavior for disk-full and permission failures.
- `REQ-005`: Add a metric for committed events whose live broker notification failed.
- `REQ-006`: Verify that subscribers can recover missed notifications through SQLite replay.
- `REQ-007`: Document why database commit success remains the publish success criterion.

## Design

### Canonical Store Declaration (REQ-001, REQ-007)
Current state in `publish_route.py`:
```python
# Line 54: Database commit happens here
seq, inserted, status = await run_with_db_lock(_insert)

# Lines 61-73: Post-commit JSONL append (derived data?)
if inserted:
    try:
        cfg = get_config(request)
        path = Path(cfg.storage_dir) / "events.jsonl"
        line = json_dumps({**body, "seq": seq}) + "\n"
        with path.open("a", encoding="utf-8") as f:
            f.write(line)
            f.flush()
            os.fsync(f.fileno())
    except OSError as exc:
        logger.warning(
            "eventbus: JSONL append failed (event still committed): %s", exc
        )

# Lines 75-88: Post-commit broker notification (real-time delivery)
if inserted:
    event_dict = {...}
    try:
        n = broker.publish(event_dict)
        logger.debug("publish notify broker delivered=%d seq=%d", n, seq)
    except Exception:
        logger.exception("publish broker notify error seq=%d", seq)
```

The function returns at line 91 **after** both post-commit operations have been attempted. The publish success criterion is the database commit (line 54), not the post-commit operations.

**Decision**: Declare SQLite as the canonical event store. Rationale:
1. The database commit is the publish success criterion — if the DB commit succeeds, the event is considered published
2. JSONL is derived data — it's appended after the DB commit and can be rebuilt from SQLite
3. Broker notification is real-time delivery — it's a side effect of publishing, not part of the durable record

This means:
- If JSONL append fails after DB commit: the event is still published; JSONL will need reconciliation
- If broker notification fails after DB commit: the event is still published; subscribers can recover via SQLite replay

### Deterministic Reconciliation Mechanism (REQ-003)
If SQLite is the canonical store and JSONL is derived, provide a deterministic rebuild mechanism:

```python
# In scripts/eventbus/reconcile.py (new file):
"""Reconcile JSONL events against SQLite canonical store."""

import logging
from pathlib import Path

logger = logging.getLogger(__name__)

def reconcile_jsonl(db_path: str, jsonl_path: str) -> dict[str, int]:
    """Rebuild JSONL from SQLite canonical store.
    
    Returns {
        "reconciled": <int>,   # events written to JSONL
        "skipped": <int>,       # events already present in JSONL
        "errors": <int>,        # errors encountered
    }
    """
    import sqlite3
    
    conn = sqlite3.connect(db_path)
    cursor = conn.execute(
        "SELECT seq, event_id, topic, payload, producer, published_at "
        "FROM events ORDER BY seq"
    )
    
    jsonl_dir = Path(jsonl_path).parent
    jsonl_dir.mkdir(parents=True, exist_ok=True)
    
    reconciled = 0
    skipped = 0
    errors = 0
    
    # Read existing JSONL lines into a set for comparison
    existing_lines = set()
    if Path(jsonl_path).exists():
        with open(jsonl_path, "r", encoding="utf-8") as f:
            existing_lines = set(f.readlines())
    
    with open(jsonl_path, "w", encoding="utf-8") as f:
        for row in cursor.fetchall():
            event_data = {
                "seq": row[0],
                "event_id": row[1],
                "topic": row[2],
                "payload": row[3],
                "producer": row[4],
                "published_at": row[5],
            }
            line = json_dumps(event_data) + "\n"
            
            if line in existing_lines:
                skipped += 1
            else:
                f.write(line)
                reconciled += 1
    
    conn.close()
    return {"reconciled": reconciled, "skipped": skipped, "errors": errors}
```

### Disk-Full and Permission Failure Behavior (REQ-004)
Document the following behaviors:

**Disk-full scenario**:
- DB commit succeeds → event is published (canonical store updated)
- JSONL append fails with `OSError` → metric incremented, warning logged
- Broker notification may succeed or fail independently → metric incremented if failed
- Subscriber can recover via SQLite replay

**Permission failure scenario**:
- Same as disk-full — DB commit succeeds, JSONL append fails
- No retry attempt (idempotent by nature — JSONL append is append-only)
- Reconciliation mechanism can restore JSONL when permissions are restored

### Documentation Structure (REQ-001, REQ-003, REQ-004, REQ-007)
Create `docs/eventbus/08_publish_durability.md` documenting:

**Canonical Store**: SQLite is the canonical event store. JSONL is derived data that can be rebuilt from SQLite.

**Publish Success Criterion**: A publish operation succeeds when the database commit completes successfully. Post-commit operations (JSONL append, broker notification) are best-effort side effects.

**Failure Scenarios**:
- JSONL append failure: Event is still published; JSONL will need reconciliation
- Broker notification failure: Event is still published; subscribers can recover via SQLite replay
- Both failures can occur simultaneously; each is independently observable via Prometheus metrics

**Recovery Procedure**: Run `scripts/eventbus/reconcile.py` to rebuild JSONL from SQLite.
