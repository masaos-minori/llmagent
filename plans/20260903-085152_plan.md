## Goal
- Align the `docs/03_rag_*.md` Specification set with current strict-reader behavior
  (`read_crawl_json()` / `read_chunk_json()`, both raising `ChunkFormatError` on
  missing/invalid fields), removing the obsolete `read_json_file()` fallback
  description from current specifications and consolidating the artifact field
  contract into one canonical, cross-linked document.

## Priority
High

## Scope
- **In-Scope**: the `docs/03_rag_*.md` files listed in Implementation Target Files
  below; updating field-classification tables (Required/Nullable/Conditional);
  relocating legacy `read_json_file()` fallback description to a historical section;
  consolidating duplicated field tables to one canonical document with cross-links.
- **Out-of-Scope**: removing `read_json_file()` from `scripts/rag/ingestion/
  pipeline_utils.py`; any test file changes; artifact migration/regeneration of
  stored artifacts; making `schema_version`/`artifact_type`/`created_by` mandatory.

## Background
The strict-reader migration (`read_crawl_json()`/`read_chunk_json()`) is already
implemented; code-side documentation (docstrings) was addressed by
`issues/done/20260819_02_issue.md`. That issue's Documentation Impact excluded the
`docs/03_rag_*.md` Specification set, which this Plan covers.

## Problem
`docs/03_rag_02_08_ingestion_pipeline-shared.md` still documents `read_json_file()`'s
lenient fallback behavior (`lang` default `"en"`, `chunk_index` default `0`,
empty-string fallback for `source_file`/`chunk_type`) as a currently-relevant reader,
via a "Field Mapping for `read_json_file`" table (repository evidence: lines 62 and
66 of that file). Required/Nullable/Conditional field classification is inconsistent
across the Specification set, and crawler-artifact fields are not clearly separated
from chunk-artifact fields.

## Reason for change
Ambiguity between current strict-reader behavior and former lenient-reader behavior
risks obsolete parsing assumptions being reintroduced, or new artifact producers
relying on outdated fallback documentation.

## Implementation intent
Establish `docs/03_rag_02_08_ingestion_pipeline-shared.md` as the canonical source of
the `read_json_file()` legacy description, relocated to a clearly marked historical
section, and treat `docs/03_rag_02_03_ingestion_pipeline-chunksplitter.md` (or a
single other document selected during implementation) as the canonical location for
the full crawl/chunk artifact-field contract table, with other documents linking to
it rather than duplicating it. Update `docs/03_rag_02_02_ingestion_pipeline-crawler.md`,
`-chunksplitter.md`, `-ingester.md`, `-shared.md`, `04_01_dto-models_data.md`,
`05_4-error-handling-reference.md`, and `05_5-constraints-reference.md` to state the
canonical reader per artifact type, the `ChunkFormatError` failure mode, and the
Required/Nullable/Conditional classification per field, sourced from
`scripts/rag/ingestion/pipeline_utils.py`'s `read_crawl_json()`/`read_chunk_json()`
validation helpers (`_validate_str`, `_validate_str_or_empty`, `_validate_nullable_str`,
`_validate_int_non_negative`) and `scripts/rag/models_data.py`'s `ChunkDocument`.

## Requirements
- `REQ-001`: Remove descriptions presenting `read_json_file()` as a supported
  production reader from current specifications; relocate its fallback-behavior
  description to a clearly marked historical/Migration section.
- `REQ-002`: Document `read_crawl_json()` as the canonical reader for crawler
  artifacts, and state that `ChunkSplitter` uses it.
- `REQ-003`: Document `read_chunk_json()` as the canonical reader for chunk
  artifacts, and state that `RagIngester` uses it.
- `REQ-004`: Document that missing required fields and invalid types raise
  `ChunkFormatError` (exact-key-set check plus per-field type/value validation).
- `REQ-005`: Document `chunk_index` as a non-negative integer, explicitly rejecting
  `bool` before the `int` check (no implicit conversion from strings or booleans).
- `REQ-006`: Separate crawler-artifact fields from chunk-artifact fields (crawl:
  8 required keys without `normalized_content`/`chunk_index`/`source_file`/
  `chunk_type`/`chunking_strategy`; chunk: 13 required keys plus those five), and
  classify each field as Required, Nullable, or Conditional, consistently across
  documents.
- `REQ-007`: Distinguish missing keys (rejected by the exact-key-set check),
  explicit `null` (accepted only for fields validated via `_validate_nullable_str`:
  `title`, `etag`, `last_modified`, `normalized_content`), and empty string values
  (accepted only for fields validated via `_validate_str_or_empty`: `content` in
  crawl artifacts, `source_file`/`chunk_type` in chunk artifacts).
- `REQ-008`: Document the non-empty requirement for `url` (both artifact types) and
  `content` (chunk artifacts only — crawl artifacts allow empty `content` when
  `code_blocks` is non-empty), and state `lang`'s current validation (`_validate_str`:
  any non-empty string is accepted; there is no parse-time enforcement of the `en`/
  `ja` value set defined by `LanguageCode` — see `UNK-01`).
- `REQ-009`: Document that `etag`, `last_modified` (both artifact types), and
  `normalized_content` (chunk artifacts only) may be `null`, because they represent
  optional upstream metadata not always available at crawl/chunk time.
- `REQ-010`: Document that `title` defaults to `""` when `null` (both artifact
  types); that crawl artifacts always set `source_file`/`chunk_type` to `""` and
  `chunking_strategy` to `"text"` (crawl-stage values do not exist yet), while chunk
  artifacts allow `source_file`/`chunk_type` to be explicit (possibly empty) strings
  and require `chunking_strategy` to be a non-empty string with no enforced closed
  value set in code (see `UNK-02`).
- `REQ-011`: Select one canonical document for the complete artifact-field contract;
  replace duplicated field tables elsewhere with links to it.
- `REQ-012`: Document the resolution of the `read_json_file()`/strict-reader gap in
  `docs/03_rag_90_inconsistencies_and_known_issues.md` (see `UNK-03` — no existing
  Known Issue entry on this topic was found; this may require adding a new resolved
  entry rather than updating an existing one).
