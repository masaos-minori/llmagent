## Background
`issues/20260902-094746_h01_git_mcp_write_protection_status_contradiction.md` documents that
Git MCP's write-protection status is stale/contradictory across `NC-019`, `MCP-003`, and
`ADR-012`, even though the underlying guards (protected-branch enforcement, `branch`/`remote`
option-injection rejection, Dirty-Worktree/Detached-HEAD checks, postcondition verification, and
the empty-`branch` protected-branch bypass fix) are all implemented and covered by tests. Three
duplicate unexecuted plans existed proposing to fix `MCP-003`'s status in
`docs/04_mcp_90_inconsistencies_and_known_issues.md`; the most complete one,
`plans/20260901-223706_plan.md`, was kept (the other two deleted). That plan's own Scope
explicitly excludes `NC-019` and any change to `ADR-012`, so the Issue's `NC-019`/`ADR-012`
portion remains unaddressed. This plan is the follow-on referenced in the Issue's Acceptance
Criteria ("`plans/20260901-223706_plan.md` is extended ... or a follow-on plan is added").

During this plan's own Step 3 inspection (adversarial verification against current source), two
findings beyond the Issue's original text were confirmed:
- `docs/04_mcp_04_05_git.md` line 93 carries `NC-019`'s literal inline marker text
  (`[Needs Confirmation: It is unclear whether this asymmetry is an intentional design decision
  ...]`). Per `routing.md`'s tool-usage table ("Needs confirmation marker ... resolved ... →
  remove the inline marker from the source doc"), and confirmed directly by reading
  `tools/check_needs_confirmation_inventory.py::check_untracked_inline_markers()`, removing
  `NC-019` from the inventory without also removing this marker leaves an orphaned marker with
  no inventory entry, which that check flags as a `WARNING`. Removing the marker is therefore a
  required, mechanical consequence of resolving `NC-019` — not a scope expansion into the
  broader staleness already deferred by the prior `NC-019` issue's Background.
- `docs/adr/ADR-012-git-mcp-server-side-write-enforcement.md` contains two more references to the
  same fixed empty-`branch` bypass beyond the `MCP-003` bullet the Issue named: the Manual Review
  section (line 190: "...has not been fixed; review before relying on...") and an unlabeled
  "Known Issue" bullet in Known Deviations (lines 205-209, with `Type`/`Summary`/`Impact`/
  `Resolution Target` sub-fields) — both describe `_validate_protected()` as still skipping the
  check on an empty `branch`, which `Verified by test` evidence (commit `800aea33e`;
  `scripts/mcp_servers/git/git_service.py::_validate_protected()`; the two
  `test_git_..._with_empty_branch_returns_denied` tests) confirms is no longer true. All three
  `ADR-012` references describe the same underlying, now-fixed gap and are corrected together in
  this plan.

## Problem
`NC-019`'s stale `open` entry, its stale source-doc marker, and three stale references to the
same fixed bug inside `ADR-012` all continue to assert that a confirmed, already-fixed
protected-branch bypass remains open, which is exactly the security-relevant
documentation/code mismatch `issues/20260902-094746_h01...` was filed to correct.

## Reason for change
Per the Issue's Reason for Change: an operator or reviewer consulting `NC-019`, the `ADR-012`
Known Deviations list, or `04_mcp_04_05_git.md`'s inline marker would incorrectly conclude a
confirmed exploitable gap is still open, when commit `800aea33e` and its regression tests already
closed it. Leaving the orphaned marker in `04_mcp_04_05_git.md` after removing `NC-019` from the
inventory would also introduce a new, tool-detectable inconsistency
(`check_needs_confirmation_inventory.py`'s untracked-marker `WARNING`).

## Implementation intent
Apply the governance doc's literal Needs-Confirmation lifecycle rule (full removal on
resolution, not a `resolved` status marker — that status value does not exist in that document's
Status Values list) to `NC-019`. Remove only the literal marker text tied to `NC-019` from
`04_mcp_04_05_git.md`, leaving its surrounding, separately-flagged staleness untouched. In
`ADR-012`, convert all three stale references to the fixed empty-`branch` bypass into `Resolved`
entries, following the exact format of the existing `- **Resolved**: MCP-005 — ...` bullet
already in the same Known Deviations list — do not invent a new resolved-item format.
