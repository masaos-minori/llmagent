# Plan: Make the Empty-Result Tool Loop Guard Reach the Results It Guards

**Plan ID**: 20261022-092413
**Source Issue**: issues/20261021-093421_tool001_empty-result-loop-guard-is-never-wired.md
**Generated**: 2026-10-22 09:24 JST

## Goal

Make the one object that decides whether a tool loop stops the same object that sees the tool
results. `ToolLoopGuard.check_empty_result_repeat()`
(`scripts/agent/tool_loop_guard.py:169-189`) is consumed at two places and always returns `None`,
because the only producer of its counts sits behind `getattr(ctx, "guard", None)`
(`scripts/agent/tool_runner.py:201`) and nothing ever assigned that attribute. This Plan replaces
the attribute lookup with an explicit parameter that starts where the guard already lives
(`LLMTurnRunner._guard`, `scripts/agent/llm_turn_runner.py:98`, `:125`, `:129`) and ends at the
function that produces a tool result (`execute_one_tool_call`, `scripts/agent/tool_runner.py:147-184`).
After this Plan, enabling `tool.tool_empty_result_max_repeats` is enough to make the documented
protection work; leaving it at the shipped default keeps today's behavior exactly.

## Priority

- **Primary goal**: remove a dependency that no code could satisfy. `grep -rn "ctx\.guard" scripts/
  tests/` matches only the `getattr` read site, and `scripts/agent/context.py` contains no `guard`
  name at all, so the recording block at `scripts/agent/tool_runner.py:209-210` is unreachable and
  `_empty_result_counts` (`scripts/agent/tool_loop_guard.py:107`) is permanently empty.
- **Must be decided first**: where a result is recorded. This Plan's answer is *at production* —
  inside `execute_one_tool_call`, immediately after the result exists — because that is the only
  location that covers both execution paths (`RepositoryGateway.execute`,
  `scripts/agent/tool_runner.py:105-107` and the gateway-bypass path at `:108-119`) and both
  scheduling shapes (sequential group loop at `:69-73`, gathered concurrent group at `:74`).
  Recording at the batch collector (`_collect_tool_result_msgs`, `:187-222`) is the shape that made
  the feature unfixable in place, and `tool002` needs per-call visibility.
- **Secondary goals**: the false state-ownership claim in the class docstring
  (`scripts/agent/tool_loop_guard.py:88-89` versus `:107`); the generated API signature table that
  states both entry points' parameter lists (`docs/23_agent/agent_13_reference-api-generated.md:184-185`);
  making the existing turn-level option testable at all.
- **Out of scope**: *when* the guard is checked (`tool002`, per-call detection and mid-batch
  interruption); whether failed or preparation-failed results are recordable and what "empty" means
  for a non-string output (`tool003`, `tool004`); the batch-order merge at
  `scripts/agent/tool_runner.py:381-385`; tool result masking (`tool005`); the other four guards and
  all thresholds; the `message` parameter of `check_empty_result_repeat` (`:169`), which is unused
  but exists so `check_all` (`:365-374`) calls every guard with one uniform signature.

## Background

`LlmTurnExecutor.handle_llm_turn()` builds a fresh `ToolLoopGuard` per LLM turn
(`scripts/agent/llm_turn_executor.py:83`) and hands it to `LLMTurnRunner` (`:84-88`). Inside the
inner tool loop (`scripts/agent/llm_turn_runner.py:83-130`) the runner:

- checks the cycle/stagnation/empty-result/dedup/retry guards through `check_all` before execution
  (`:98-105`, `scripts/agent/tool_loop_guard.py:356-375`);
- executes the round through `execute_all_tool_calls(ctx, message["tool_calls"], turn,
  out_failed_keys=state.failed_calls)` (`:115-120`);
- then checks the empty-result guard (`:125`) and the consecutive-error guard (`:129`), turning a hit
  into `TurnResult(action="fail", answer=msg, reason="empty_result_repeat")` (`:126-128`).

The empty-result half is the only guard whose input comes from *tool output* rather than from the
assistant message. Its producer is `record_tool_result` (`scripts/agent/tool_loop_guard.py:156-167`),
and its only call site is `scripts/agent/tool_runner.py:210`, guarded by the `getattr` at `:201`. The
consecutive-error guard shows the contrast: its state is threaded explicitly
(`out_failed_keys=state.failed_calls`, `scripts/agent/llm_turn_runner.py:119`, consumed at
`scripts/agent/tool_runner.py:225-237`), so it works. The guard object itself was never threaded.

## Problem

The option is documented, configured, reported at startup, and inert.

- `scripts/agent/tool_runner.py:200-201` reads `guard = getattr(ctx, "guard", None)`; no code assigns
  `guard` on `AgentContext`, so `:209-210` never runs.
- `check_empty_result_repeat` therefore sees an empty `_empty_result_counts` from both consumers:
  `scripts/agent/llm_turn_runner.py:125` and `check_all` (`scripts/agent/tool_loop_guard.py:371`).
- The startup self-report runs unconditionally at guard construction
  (`scripts/agent/tool_loop_guard.py:36`, `:96-103`, `:109-123`) and asserts a protection state that
  the wiring cannot back up for any configuration above 0.
- The dead half has no test: `tests/agent/test_tool_loop_guard.py` (34 tests) never calls
  `record_tool_result` or `check_empty_result_repeat`, and no test in `tests/agent/` asserts that a
  guard reaches `tool_runner`. Every existing turn test replaces the entry point with a mock
  (`tests/agent/test_llm_turn_runner.py:397`, `:436`, `:485`, `:518`, `:583`;
  `tests/agent/test_orchestrator.py:899`, `:970`), so a missing dependency inside it is invisible.
- Ordering consequence: `check_all` runs before execution (`scripts/agent/llm_turn_runner.py:98`
  versus `:115`), so its empty-result arm can only ever read counts recorded by an earlier round. The
  only place that can act on the current round is `:125` — and that is exactly the boundary a
  per-call detection change (`tool002`) needs recording to have already happened below.

## Reason for Change

A tool that returns `""` repeatedly is the pattern this guard exists to stop, and today the only
remaining protections are the error-count, dedup, cycle, and retry checks
(`docs/23_agent/agent_03_02_turn-processing-flow-llm-tool-loop.md:33` lists it as a stop condition
that can fire). An empty output is not an error, so `update_errors`
(`scripts/agent/tool_loop_guard.py:379-389`) resets the error counter, and a call with new arguments
is not a dedup or cycle hit — such a loop can consume the whole `max_tool_turns` budget and the
operator gets a "maximum tool turns reached" answer (`scripts/agent/llm_turn_runner.py:132-137`)
instead of the specific `empty_result_repeat` answer the guard was written to produce.

## Implementation Intent

State the dependency where the dependency already exists. `LLMTurnRunner` holds the guard; it passes
it to the one function it already calls with turn-scoped state. Inside `scripts/agent/tool_runner.py`
that parameter is threaded to the function that produces a result, and the recording call moves there.
No mutable state is added to `AgentContext`, and no new state is added anywhere else: the counts stay
in the per-turn guard instance that already holds them.

## Design

### Why a required parameter and not a context attribute

`AgentContext` is built once per session (`scripts/agent/factory.py`) and the guard is built once per
LLM turn (`scripts/agent/llm_turn_executor.py:83`). Putting the guard on the context would store
turn-scoped state on a session-scoped object and would need a reset step at the start of every turn —
a second lifetime problem in place of the first one. It is also what `skills/DESIGN.md` Shared
Vocabulary and the issue's own Constraint rule out. The threaded parameter is the same shape the
working guard already uses for its turn state: `out_failed_keys=state.failed_calls`
(`scripts/agent/llm_turn_runner.py:119` → `scripts/agent/tool_runner.py:236-237`).

The parameter is required, not `Optional`. An optional guard would reproduce the failure mode this
issue is about: a call site that silently does no recording. The cost is explicit and bounded — 31
test call sites updated, and mypy becomes the enforcement mechanism (AC-1).

### Why recording moves to `execute_one_tool_call`

`execute_one_tool_call` (`scripts/agent/tool_runner.py:147-184`) is the single function through which
every approved call passes, after approval (`_run_approval_gate`, `:394-409`), after preparation
(`prepare_tool_calls`, `:369`), and after the result exists. Recording there:

- covers both execution paths in one place (`:105-107` and `:108-119`), which recording in
  `RepositoryGateway` would not (the bypass path exists for tests, `:96-103`);
- is independent of batch shape, so a sequential group's calls are recorded one by one
  (`:69-73`) and a gathered group's calls are each recorded by their own task (`:74`) — which is what
  `tool002`'s per-call check needs;
- is independent of the merge and re-sort that happens afterwards
  (`scripts/agent/tool_runner.py:381-385`), which is `tool003`'s ordering concern.

`_record_transport_failure` (`:180`) is the model for this position: a per-result observation, made
once, at the place the result exists. The recording call is placed immediately after it.

### What deliberately does not change

The two check sites, the thresholds, the option semantics, the hint text
(`EMPTY_RESULT_REPEAT_HINT`, `scripts/agent/tool_loop_guard.py:67-70`), the `guard_hint` diagnostic
write (`:141`), the `TurnResult` shape, the `check_all` order (`:365-374`), and the batch collection
order. Keeping those fixed is what makes the change auditable as "wiring only" and keeps
`docs/23_agent/agent_03_02_turn-processing-flow-llm-tool-loop.md:33-110` accurate without editing it.

The unused `message` parameter of `check_empty_result_repeat` (`:169`) is kept. It is part of the
uniform signature `check_all` uses to call every guard (`:365-374`); removing it from one guard would
be an unrelated cleanup and would not make the feature more correct.

### Sequencing with the other tool issues

`tool001` (this Plan) owns *whether the guard sees results*. `tool002` owns *when a trip is acted on*
(per-call checks in sequential groups, per-batch checks for concurrent groups, and the synthesized tool
messages for any call that is then skipped). `tool003` owns *which results count* (failed and
preparation-failed results, and the strict `tc["id"]` index at `:383`). `tool004` owns the
classification boundaries. Implementing this Plan first is the order the source issue's Dependencies
section asks for, and it is the only order in which the later plans change rules instead of plumbing.
`tool002`'s future mid-batch stop is not added here: it changes how many tool messages a round
produces, which is a different decision with its own test surface.

## Risks

- **Risk**: blast radius of changing two public signatures — measured before implementation per
  `rules/toolchain.md:3-28`: `execute_all_tool_calls` appears in 4 test files (19 call sites, 7
  mock-patch sites) and `execute_one_tool_call` in 3 test files (12 call sites, 3 mock-patch sites),
  i.e. 31 references across 5 test files, above the "~20 references" recording threshold.
  **Mitigation**: the count is recorded here, in this Plan, before implementation; Phase 3 enumerates
  each file and call-site count, and mypy is used to produce the list rather than a failing test run.
- **Risk**: `scripts/agent/tool_runner.py` is 858 bytes below the 16384 B ceiling and five parameter
  additions plus one recording call consume part of that headroom. **Mitigation**: keep the threading to
  one typed parameter per function and no new helper; measure after Phase 1 (`check_module_size.py
  --top 5`); if it fails, open a separate module-split work item rather than growing this Plan (UNK-02).
- **Risk**: recording at production time makes the guard's state change *during* a round, so a later
  `check_all` call in the same round (`scripts/agent/llm_turn_runner.py:98`) can see counts produced by
  the previous round's execution instead of an empty map — a behavior that was previously unreachable.
  **Mitigation**: this is the intended fix, and it is asserted explicitly: the no-leak-across-turns case
  proves counts are scoped to one LLM turn, while AC-2 proves within-turn visibility. `tool002` decides
  whether an in-round trip acts immediately; until then the only consumer that acts is the existing one
  at `:125`, which already reports `reason="empty_result_repeat"`.
- **Risk**: the new turn-level test drives the real executor and a real `ToolLoopGuard`, which is the
  slowest kind of agent test and could become flaky if it uses wall-clock bounds. **Mitigation**: no
  time bounds are asserted; the stub tool is synchronous-fast, `max_tool_turns` is set to the minimum
  that reaches the threshold, and the assertions are on `TurnResult` fields and the `guard_hint` row.
- **Risk**: adding a required parameter to a function three test files patch with `AsyncMock` could
  hide the wiring in exactly those tests. **Mitigation**: the mock-patch tests are not the acceptance
  surface; AC-6 and AC-7 run through the unmocked path, and `check_mock_patch_targets.py` keeps the
  patch targets valid.
