## Goal
- Use one canonical `GitServiceError` definition and eliminate the dead, duplicated
  `RepoValidationResult` shims from the live and near-live Git MCP code paths, so an
  `isinstance` check can never silently miss a semantically-identical-but-different
  Python class.

## Priority
Medium

## Scope
- **In-Scope**: removing the unused duplicate `GitServiceError` in `git_models.py`;
  classifying every `RepoValidationResult` usage (active/test-only/obsolete);
  migrating test-only callers off the deprecated shim; removing
  `repository_state.py`'s `RepoValidationResult`; a test proving exception identity
  cannot bypass the registered FastAPI handler.
- **Out-of-Scope**: protected-branch/ref authorization content (`gitauth`); the
  write-protection pipeline's stage ordering (`gitpipeline`); placeholder-method
  removal in `repository_state.py` beyond the error/validation types this issue
  names (`gitcleanup`) — the ~60 other dead methods `gitauth`'s Plan found are not
  touched here; `git_service.py`'s `RepoValidationResult` removal, which this Plan
  defers to `gitdispatch`'s implementation (see Design) rather than acting
  unilaterally on a type that Plan's own change may need to replace.

## Background
Investigation confirmed `GitServiceError` is defined twice — `errors.py:10` and
`git_models.py:73` — but this Plan's Step 3 re-confirmation (per the issue's own AI
Implementation Instruction) found `git_models.py`'s copy has **zero** references
anywhere, including within `git_models.py` itself: every actual `raise
GitServiceError(...)`/`except GitServiceError`/`@app.exception_handler(GitServiceError)`
site across `repository_state.py`, `format_output.py`, `git_server.py`, and
`git_service.py` already imports from `errors.py`. The duplicate is inert, not a
live isinstance-mismatch risk today — but remains a latent risk for any future code
that imports from `git_models.py` instead.

`RepoValidationResult` is more complex than the issue's Background states: it is
independently defined **twice**, not once — `repository_state.py:34` ("Local shim for
legacy callers... New code should use RepositoryState directly") and, separately,
`git_service.py:56` (its own distinct class, also carrying a deprecation warning).
These are two different Python classes with the same name. Tracing every usage:
- `repository_state.py`'s `RepoValidationResult` is referenced by
  `RepositoryState.validate_repo()` (line 210, called only by
  `tests/mcp_servers/git/test_repository_state.py` lines 161/217 — test-only, no
  production caller) and by `RepositoryState._validate_repo()`/
  `WriteProtectionPipeline._validate_repo()` (lines 396, 699 — both confirmed dead
  code by `gitauth`'s Plan's investigation this session: neither class's ~60-method
  surface, including these, has any external caller). It is also exported via
  `__all__` (line 746).
- `git_service.py`'s `RepoValidationResult` is referenced only by
  `GitService._validate_repo()` (lines 108-120), which `_run_tool()` calls — itself
  confirmed dead code (`GitService`'s dispatch table has zero external callers, per
  `gitauth`'s Plan).
Neither `RepoValidationResult` definition has an active production caller today: the
live `POST /v1/call_tool` path (`git_server.py`) never imports or references
`RepoValidationResult` — its rejection path uses a plain `tuple[bool, str, str]` from
`_resolve_repo_path()`.

## Problem
Two independent `GitServiceError` classes and two independent `RepoValidationResult`
classes create the exact risk the issue names: a handler written against one class
would silently fail to catch or match an instance of the other. Today this is latent
(no live caller uses the non-canonical copies), but the duplication itself is the
defect — a future change routing traffic through the currently-dead paths (e.g.
`gitdispatch`'s Plan) could make the risk live without anyone having removed the
duplicate that would then matter.

## Reason for Change
An exception-identity mismatch turning a caught-and-handled failure into an
unhandled one is exactly the kind of defect that is invisible until the wrong code
path becomes reachable — consolidating to one definition of each type now, while it
is still low-risk to do so, prevents that failure mode from ever activating.

## Implementation intent
Delete `git_models.py`'s unused duplicate `GitServiceError` — no caller migration
needed, since none exists. For `RepoValidationResult`: migrate
`test_repository_state.py`'s two test-only callers of `RepositoryState.validate_repo()`
to assert against `RepositoryState`'s own fields directly (per the shim's own
docstring), then remove `repository_state.py`'s `RepoValidationResult` class,
`validate_repo()`, and the two dead `_validate_repo()` methods that return it (the
latter already in scope for removal as unreachable code, consistent with this
Plan's narrow error/validation-type framing rather than `gitcleanup`'s broader
placeholder sweep). Leave `git_service.py`'s `RepoValidationResult` and
`GitService._validate_repo()` untouched — not because they are exempt from the
issue's concern, but because `gitdispatch`'s Plan (already Frozen) proposes making
`GitService._run_tool()` live, and that Plan's own implementation is the correct
place to decide `_run_tool()`'s replacement return type, not a unilateral removal
here that could conflict with it.

## Design
This Plan's investigation revised the issue's own Background in one respect: the
issue describes `RepoValidationResult` as a single shim "still referenced in
git_service.py, repository_state.py, and tests" — this Plan found it is actually
*two independent class definitions*, not one shared shim referenced from multiple
files, which changes the correct remediation from "migrate references to one shim"
to "eliminate one dead-code copy now, defer the other to the Plan that would make it
live." This distinction matters for `gitdispatch`'s Plan (already Frozen,
`plans/20260904-191458_plan.md`): that Plan's REQ-002 proposes routing live traffic
through `GitService.get_dispatch_table()`/`_run_tool()`, which returns
`git_service.py`'s `RepoValidationResult`. If this Plan removed that class
unilaterally, `gitdispatch`'s implementation would need to either restore an
equivalent type or redesign its return-value handling as an unplanned side effect —
better to leave that decision to whichever Plan actually makes the code path live.

`repository_state.py`'s `RepoValidationResult` and its 3 usage sites, by contrast,
are safe to remove now: none of `gitauth`, `gitpipeline`, `gitdryrun`, or `gitremote`'s
Plans (all already Frozen this session) touch `RepositoryState.validate_repo()`,
`RepositoryState._validate_repo()`, or `WriteProtectionPipeline._validate_repo()` —
they all operate on different methods within the same file (`verify_authorization()`,
`verify_postcondition()`, `verify_preconditions()`, remote/lock additions
respectively). Removing these three dead methods here does not conflict with any of
those Plans' scoped edits.
