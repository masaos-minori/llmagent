## Background
The Issue's cited Note (`docs/03_rag_03_03_query_pipeline-context-and-diagnostics.md:85`)
is quoted accurately: "In HTTP mode, `fetch_result` might contain stale values from
the previous in-process execution rather than the current call's result. This is
because `RagPipeline._run_http_augment()` does not call `self.run()` upon an HTTP
success."

**Re-verified 2026-09-13** (this cycle, against the current repository state): this
claim does not hold. Tracing the actual data flow for `RagPipeline.last_fetch_result`
on an HTTP-mode success:
1. `RagPipeline.__init__` (`pipeline.py:119`) constructs its `AugmentRefiner` with
   `set_fetch_result=lambda fr: setattr(self, "last_fetch_result", fr)` — a callback
   that directly writes to the `RagPipeline` instance's own `last_fetch_result`
   attribute, bypassing any need for `self.run()` to be called
2. On HTTP success, `AugmentRefiner._forward_fetch_result()` (`augment.py:102-110`)
   is invoked (wired as `HttpAugment`'s `set_fetch_result` callback,
   `augment.py:79`); when `selected_hits` is non-empty, it constructs a
   `TwoStageFetchResult` and calls `self._set_fetch_result(fetch_result)` — which is
   exactly the `RagPipeline.__init__`-supplied callback from step 1
3. This means `RagPipeline.last_fetch_result` is updated **before**
   `RagPipeline.augment()`'s HTTP-mode branch (`pipeline.py:298-301`) even runs its
   own (separate) `fetch_result = getattr(self._augment_refiner, "last_fetch_result",
   None)` check

Separately, `AugmentRefiner.last_fetch_result` (the property `augment()`'s
line 299 reads via `getattr`) is backed by `AugmentRefiner._last_fetch_result`
(`augment.py:66`), which is initialized to `None` in `__init__` and **never
reassigned anywhere in the class** (confirmed via `grep -n "_last_fetch_result"
scripts/rag/augment.py` — only the `__init__` initialization and the property
getter exist). So `augment()`'s lines 298-301 always read `None` from
`self._augment_refiner.last_fetch_result` and never actually update
`self.last_fetch_result` a second time — this code path is effectively dead/inert,
though harmless, since the real update already happened via the callback in step 2
above.

The one genuine staleness condition: `_forward_fetch_result()`
(`augment.py:102-110`) only calls the update callback `if selected_hits:` — when
`selected_hits` is empty (HTTP call succeeded but returned zero hits), the callback
is never invoked, and `RagPipeline.last_fetch_result` retains whatever value it held
from a prior call. This is a real (if narrow) staleness condition, but it is
unrelated to the Issue's stated cause (`self.run()` not being called) — it is
purely about the empty-hits case in the callback-based update path.

No existing test directly exercises `last_fetch_result` staleness/freshness in HTTP
mode (checked `tests/rag/test_rag_http_mode.py`,
`tests/rag/test_pipeline_http_result_kind.py`,
`tests/rag/test_pipeline_refiner_fallback_counters.py`,
`tests/rag/test_fusion_mode_diagnostics.py` — all set `pipeline.last_fetch_result =
None` as a fixture reset, none assert on its post-HTTP-success value).

## Problem
The documented Note describes a staleness cause and mechanism (`self.run()` not
being called) that does not match the actual code — `last_fetch_result` is updated
via a direct callback mechanism the Note does not mention, and the mechanism the Note
does cite (`RagPipeline.augment()`'s own re-check of `self._augment_refiner.last_fetch_result`)
is dead code that never actually performs an update. This risks readers
investigating or "fixing" a staleness problem that, as described, does not exist,
while missing the one narrow case (empty `selected_hits`) where staleness genuinely
occurs.

## Reason for change
Correct the Note to describe the actual, current `last_fetch_result` update
mechanism (the `AugmentRefiner`→`RagPipeline` callback) and its one genuine
staleness condition (empty `selected_hits`), so the documentation matches the
current implementation rather than an outdated understanding of it.

## Implementation intent
Rewrite the Note at
`docs/03_rag_03_03_query_pipeline-context-and-diagnostics.md:85` to state: (1)
`last_fetch_result` is updated via a callback (`AugmentRefiner._forward_fetch_result()`
→ the `RagPipeline.__init__`-supplied `set_fetch_result` callback) at the point
`HttpAugment` reports fetch hits, not via `self.run()`; (2) the one genuine
staleness condition is when the HTTP call succeeds but returns zero hits
(`selected_hits` empty), in which case the callback is not invoked and
`last_fetch_result` retains its prior value.
