## Goal
Reduce complexity of `ConfigReloadService.apply_config_dict()` by extracting its six distinct responsibilities into smaller, focused private methods, improving readability and testability without changing public behavior.

## Priority
Low

## Scope
- **In-Scope**: Extracting private methods from `apply_config_dict()`, updating docstrings, fixing pre-existing test failures
- **Out-of-Scope**: Changes to `config_field_registry.py`, `config_validators.py`, `config_section_reload.py`, `config_service_sync.py`, `config_outcome_classification.py`; adding new features or changing public APIs

## Background
`ConfigReloadService` was previously part of `_ConfigMixin` in `scripts/agent/commands/cmd_config.py`. The migration extracted config handling into dedicated modules (`config_section_reload.py`, `config_outcome_classification.py`, `config_service_sync.py`). However, `apply_config_dict()` itself remains monolithic with multiple concerns mixed together.

## Problem
`apply_config_dict()` (~44 lines) performs six distinct operations:
1. Section-based reload via `reload_validated_section` (lines 97-100) — returns `list[str]` of changed fields
2. Direct field reload via `reload_direct_fields` (lines 101-104) — returns `dict[str, ...]` of changed fields
3. Direct field updates for `system_prompt_tool`, `allowed_tools`, `masked_fields` (lines 105-110)
4. MCP server change classification + lifecycle cleanup (lines 111-121)
5. Service sync via `_sync_services()` (delegates to `ServiceSyncer.sync_all()`) (lines 122-129)
6. Outcome classification for startup-only and diagnostics fields (lines 130-131)

Operations 1 and 2 use different mechanisms: Operation 1 (`reload_validated_section`) performs validated reload via `dataclasses.replace` + validators, while Operation 2 (`reload_direct_fields`) performs direct field update via `setattr`. Both append section names to `outcome.applied`, but their mechanisms differ. Operations 5 and 6 produce unrelated result types: Operation 5 returns `ConfigReloadOutcome` (wrapping `ServiceSyncResult` internally), Operation 6 returns `list[str]`. This violates the Single Responsibility Principle and makes the method hard to follow, test, and modify. Additionally, 14 existing tests fail due to CONFIG_FIELD_REGISTRY import issues.

## Reason for change
Maintainability risk: the method's size and mixed concerns make it difficult to add new configuration sections or modify existing ones without risking unintended side effects. Note: this refactoring does NOT fix the 14 pre-existing test failures caused by `_diff_mcp_server_config` import path changes; those are separate issues outside the scope of this refactor.

## Implementation intent
Extract each of the six responsibilities into separate private methods on `ConfigReloadService`:
- `_apply_validated_sections(self, ctx, new_cfg)` — section-based reload via `reload_validated_section` (operation 1 only)
- `_apply_direct_reloads(self, ctx, new_cfg)` — direct field reload via `reload_direct_fields` (operation 2 only)
- `_apply_direct_fields(self, new_cfg)` — direct field updates (operation 3)
- `_handle_mcp_changes(self, ctx, new_cfg)` — MCP classification + lifecycle cleanup (operation 4)
- `_sync_services(self, new_cfg, ctx)` — service sync (operation 5)
- `_classify_outcomes(self, new_cfg)` — outcome classification (operation 6)

Each extracted method returns its own result type rather than mutating a shared `ConfigReloadOutcome` passed in — this avoids shared mutable state and makes each method independently testable. The orchestrator merges results after all calls. The key design decision is that each method returns its own result type rather than forcing all results through a common `ConfigReloadOutcome` intermediate — the orchestrator (`apply_config_dict`) merges them.

## Design
The refactoring follows the Extract Method pattern (Fowler). Each extracted private method receives the minimal parameters needed to perform its single responsibility. The `apply_config_dict()` method becomes a thin orchestrator that calls these methods sequentially and merges their results.

Key design decisions:
- Each extracted method returns its own result type rather than mutating a shared `ConfigReloadOutcome` passed in — this avoids shared mutable state and makes each method independently testable. The orchestrator merges results after all calls.
- Operations 1 and 2 are kept as separate methods because they use fundamentally different mechanisms: Operation 1 uses `reload_validated_section` (validated via `dataclasses.replace` + validators), Operation 2 uses `reload_direct_fields` (direct `setattr`). Forcing them into one method would require an artificial common return type.
- Operations 5 and 6 are kept as separate methods because they produce unrelated result types: Operation 5 returns `ConfigReloadOutcome` (wrapping `ServiceSyncResult` internally), Operation 6 returns `list[str]`. Merging them would obscure which fields come from which operation.
- The `_classify_mcp_server_changes` helper already exists and delegates to `classify_mcp_server_changes` from `config_outcome_classification`; it remains unchanged
- The `_sync_services` method already exists and delegates to `ServiceSyncer.sync_all()`; it remains unchanged
- The `ConfigReloadOutcome` dataclass is used only by the orchestrator to collect final results — no new types introduced
