## Background
Commit `5e568520` (2026-09-18) replaced the eventbus's old `_TOKEN_CONSUMER_MAP` design with a `_TOKEN_PRINCIPAL_MAP` + `Principal`-based model across `ack_nack`, `crash_ack`, `subscribe`, and `ack_endpoint` test fixtures. `scripts/eventbus/ack_route.py`'s `_do_ack` contains an explicit, well-commented design: `ack_event_for_consumer()`'s `INSERT OR IGNORE` into `consumer_delivery` has no FK enforcement against `events`, so `found` (not `newly_acked`) is deliberately used as "the authoritative existence check" for the 404 response — and no separate "was this delivered before ack" gate exists; an ack atomically creates the delivery+ack record. `test_eventbus_ack_endpoint.py::test_ack_event_principal_ownership_validation`'s own inline comment (line 217) still references `_principal.allowed_consumer_ids is populated from _TOKEN_CONSUMER_MAP` — the map name that commit `5e568520` replaced — indicating this test's expectations were not fully reconciled with that refactor.

## Problem
Confirmed via live `--tb=long`/`--tb=short` reruns:
- **Not-found → 404 vs expected 409** (2 tests): `ack_route.py`'s `_do_ack` explicitly raises 404 when `found` is `False` (nonexistent event), per its own inline design comment; the tests expect 409.
- **No prior delivery → 200 vs expected 409** (3 tests): `_do_ack`/nack's shared path has no separate delivery-existed-before-ack gate — an ack/nack call itself creates the delivery record; the tests expect a 409 rejection that no code path currently implements or (per the design comment) is intended to implement.
- **Wrong consumer_id → 200 vs expected 403/409** (3 tests): both `require_consumer_identity` (FastAPI dependency, `scripts/eventbus/auth.py`) and `_do_ack`'s own inline check (`scripts/eventbus/ack_route.py`) contain logic that should reject `consumer_id not in principal.allowed_consumer_ids` with 403 — confirmed via Read that the test fixture (`principal_client`) correctly re-populates `_TOKEN_PRINCIPAL_MAP["consumer-token"].allowed_consumer_ids = frozenset({"consumer-A"})` before each test (verified empirically via a standalone `_populate_token_maps` invocation) — yet the observed response is 200 in all 3 files, meaning the ownership check is not being reached or not evaluating as expected at request time. The precise mechanism was not fully pinned down within this planning cycle's evidence-gathering (see Unknowns).

## Reason for change
The first two clusters (5 tests) look like stale test expectations from before the `_TOKEN_PRINCIPAL_MAP` refactor, based on strong in-code evidence (explicit design comments, a fossil reference to the old map name) — but this Plan does not assume that conclusion without first checking whether a Requirement/spec document defines the intended contract (see Implementation intent). The third cluster (3 tests) is potentially a real authorization-bypass regression across all three ack/nack/crash-recovery endpoints — high priority given its security nature — and must be root-caused, not assumed away, before any test is changed to match current (possibly broken) behavior.
