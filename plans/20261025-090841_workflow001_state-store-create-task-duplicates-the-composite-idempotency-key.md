## Problem
Two functions write `tasks` rows with different key rules. `task_ops.create_task()` uses a UUID4; `StateStore.create_task()` still composes `"{session_id}:{turn_number}"` when both values are given. `session_id` is the literal `""` in the live path (`orchestrator.py` passes `""` to `execute_turn`, checked in Step 3) and `turn_number` is a process-local counter, so the composite key repeats across processes against a retained `workflow.sqlite` and would raise `sqlite3.IntegrityError` on the UNIQUE constraint. The wrapper is uncalled today, but `StateStore` is a documented public class, so the collision is one added call away, and no test covers the wrapper, so nothing detects the divergence. The closed plan's scope guard is file-scoped (`task_ops.py` only) and cannot see this copy.

## Reason for Change
The closed plan's intent is that the composite form no longer exists in the task-write path. Leaving a second copy keeps the removed defect reachable. The fix is one method body and one test.

## Implementation Intent
Delegate to the existing function rather than patch the branch inline. This leaves one `INSERT` for task rows (removing the duplicated SQL), keeps the signature and `TaskRecord` return type, and makes the key rule a single definition. The cost is one in-package import (`state_store` to `task_ops`), which stays inside `agent.workflow` and introduces no cycle.
