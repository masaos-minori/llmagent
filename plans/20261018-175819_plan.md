# Plan: Automate Needs Confirmation review-metadata consistency checks (GV-008)

## Goal

field-groups defined for Needs Confirmation items — adding `Last Reviewed`, `Priority`, and
Status/Blocking consistency on top of the already-checked `Assigned To` and
`Resolution Target` — then mark GV-008 fully automated in the governance documentation matrix.

## Background
`docs/00_governance/governance_04_documentation-checks.md` maps rule GV-008
("Needs Confirmation assignment, review metadata, priority, and resolution target") to the
enforcement tool `check_needs_confirmation_inventory.py`. The matrix records its status as
`Partial` because the tool currently checks only two of the four field-groups
(`Assigned To`, `Resolution Target`); the other two (`Last Reviewed`, `Priority`, and
Status/Blocking consistency) are manual review.

## Problem
The three unchecked field-groups can drift without detection: a Needs Confirmation item may
carry a stale or missing `Last Reviewed`, an invalid `Priority`, or a dangling `Blocking`
reference, and the automated tool would report no issue.

## Reason for change
Governance_04 lists a follow-up to automate the remaining field-groups. Automating them
removes the manual-review burden and closes the detection gap for GV-008.

## Implementation intent
Follow the existing `check_*` pattern already in the tool: each new check takes the parsed
entries, returns a list of `Issue` with `severity="WARNING"`, and is aggregated in `main()`.
Because the current `NcEntry` and parser only expose five fields, first extend both to carry
`last_reviewed`, `priority`, and `blocking`, then add the three checks that consume them. Do
not invent field values; every allowed value must trace to `governance_03`.

## Requirements
- `REQ-001`: For every active Needs Confirmation entry, `Last Reviewed` is present and a
  well-formed ISO `YYYY-MM-DD` date. Missing or malformed values produce a WARNING.
- `REQ-002`: `Priority` is one of the values defined by `governance_03`'s Priority Values
  section; any other value produces a WARNING.
- `REQ-003`: When `Blocking` is set, it references a valid Needs Confirmation id that exists
  among the corpus entries; when unset, no dangling blocking reference remains. Invalid or
  dangling references produce a WARNING.
- `REQ-004`: The GV-008 matrix row status changes from `Partial` to `Existing` and its

## Design
The tool aggregates findings from several `check_*` functions in `main()`. Each new check
follows that shape: `(entries: list[NcEntry]) -> list[Issue]` with `severity="WARNING"`.

1. **Parser/dataclass extension.** `NcEntry` currently stores only `nc_id`, `source_file`,
   `status`, `assigned_to`, `resolution_target`. Add `last_reviewed`, `priority`, and
   `blocking` attributes and extend `_parse_inventory_entries` to read the corresponding
   `**Field:**` markers from each inventory entry. Guard against absent markers (treat as
   `None`) so existing entries without those fields do not raise.
2. **REQ-001 (`Last Reviewed`).** Flag entries where `last_reviewed` is `None` or not a
   parseable ISO `YYYY-MM-DD` date. Do not enforce recency (UNK-01).
3. **REQ-002 (`Priority`).** Compare `priority` against the `governance_03` Priority Values
   enum (`High`, `Medium`, `Low`), case-insensitively. Flag anything else.
4. **REQ-003 (`Blocking`).** Resolve `blocking` against the set of real NC ids in the corpus.
   If set and not found, flag it (UNK-02 correction: this is about the `Blocking` field, not a
   `Blocked` status).
5. **Wiring.** Register the three checks in `main()` alongside the existing ones so their
   WARNING findings flow through the existing aggregation and reporting path.

No public interface, CLI argument, or exit-code contract changes. Severity stays `WARNING` to
preserve the existing "warnings → exit 0, ERROR → non-zero" behavior verified by
`TestExitCodeBehavior`.

  **Mitigation**: Implement around the actual `Blocking` field and record the correction in
