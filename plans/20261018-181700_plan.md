# Plan: Automate audit of auto-checks documented as implemented (GV-014)

## Goal
Build a new checker that cross-references every auto-check documented as `Auto` against an
actual runnable script under `tools/` or `scripts/`, flagging documented-but-absent or
name-drifted entries, then mark GV-014 `Existing`. Keep the check non-blocking and
`Warning`-level.

## Priority
Medium

## Scope
- **In-Scope**:
  - Parse documented auto-check tool references from the authoritative documents.
  - Verify each reference resolves to an existing, runnable script under `tools/` or
    `scripts/` (discovered dynamically, not hardcoded).
  - Flag documented-but-absent or name-drifted entries.
  - Add unit tests with documented-but-missing and valid entries.
  - Update the GV-014 matrix row to `Existing` and clear its follow-up note.
- **Out-of-Scope**:
  - Changing which documents are authoritative sources of auto-check claims.
  - Adding new auto-checks.

## Background
`governance_04_documentation-checks.md` maps GV-014 ("No unimplemented auto-checks documented
as implemented") to human review on a periodic basis, status `Partial`, with the follow-up
"Automate auto-check implementation audit (currently manual)". Auto-checks are recorded as
`Method = Auto` in the Governance Verification Matrix and listed as automated in `routing.md`'s
tool table.

## Problem
A checker can be documented as "Auto" while no corresponding runnable script exists, or its
documented name has drifted from the actual tool filename. Implementers then believe enforcement
exists when it does not, and manual review only catches this between sweeps.

## Reason for change
GV-014 is a periodic `Warning` gate. Automating the audit keeps documentation honest about what
is actually enforced and removes reliance on periodic manual sweeps.

## Implementation intent
Build a checker that parses documents enumerating auto-checks (the GV matrix `Method = Auto`
cells, `routing.md` tool entries) and verifies each referenced tool resolves to an existing,
runnable script under `tools/` or `scripts/`. Flag documented-but-absent or name-drifted
entries. Keep the check non-blocking and `Warning`-level.

## Requirements
- `REQ-001`: The checker parses documented auto-check tool references from the authoritative
  documents (`governance_04_documentation-checks.md` `Method = Auto` cells and `routing.md`

## Design
New standalone CLI following the `tools/check_*.py` convention (argparse, `Issue` results,
`Warning`/`ERROR` severities).

1. **Parse authoritative sources.** Extract tool references from:
   - `governance_04` matrix rows where the method column is `Auto` — capture the backtick-quoted
     tool token in that row.
   - `routing.md` tool-table rows — capture backtick-quoted `tools/...`/`scripts/...` paths.
2. **Discover tools dynamically.** List files under `tools/` and `scripts/` at runtime; build a
   set of basenames and full relative paths (do not hardcode).
3. **Resolve and flag (UNK-02).** For each documented token, resolve by basename (or relative
   path). If no match exists, flag at `Warning` (documented-but-absent). If only a close
   candidate exists, emit a non-blocking drift hint (UNK-03). Exclude non-path tokens and known
   alternative invocation names to avoid false positives.
4. **Report.** `Warning`-only; preserve the non-blocking contract.

No change to how checks are invoked; no change to the authoritative documents' structure.

## Risks
- **Risk**: False positives from differently-named invocations (pre-commit hooks, CI jobs). →
  **Mitigation**: Exclude non-path tokens and maintain a small allowlist of known alternative
  names (UNK-02); tune against the current corpus.
- **Risk**: Ambiguous authoritative source set. → **Mitigation**: Fix the input set to
  `governance_04` `Method = Auto` cells + `routing.md` tool table; document it (UNK-01).
- **Risk**: Fuzzy drift detection may itself false-positive. → **Mitigation**: Report drift as a
  non-blocking hint, not a failure (UNK-03).
