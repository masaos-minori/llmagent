## Goal
Provide one command that runs the validation gates a change needs before commit, chosen from the changed files, and prints a single pass/fail summary — implementing `rules/toolchain.md` "Standard validation sequence" and the applicable rows of `routing.md` "When to run which tool", so neither has to be reassembled by hand each session.

## Priority
Medium

## Scope
- **In-Scope**: inventory every gate from `rules/toolchain.md`, the `routing.md` table, `.pre-commit-config.yaml`, and `.github/workflows/ci.yml` and record which gate runs where; define the path-to-gate mapping and the execution order; add `tools/run_validation_gates.py` that maps changed paths (from `git diff` against a base, staged plus unstaged) to the existing checkers/commands and runs them in the documented order, calling the existing commands rather than reimplementing them; implement a fast mode (changed-file gates only) and a full mode (adds full `pytest` and `diff-cover`); emit one summary with per-gate result and the exact failing command using the canonical `Pass`/`Fail`/`Partial`/`Not available`/`Blocked` vocabulary; add a drift check/test that fails when a checker named in `routing.md` has no mapping entry; register the tool in `tools/TOOL_DESCRIPTIONS.md` and reference it from `routing.md` and `rules/toolchain.md`.
- **Out-of-Scope**: adding, removing, or changing any gate or its thresholds; changing `.github/workflows/ci.yml` or `.pre-commit-config.yaml` hook sets (read-only for the inventory unless the plan decides otherwise); auto-fixing findings; committing or pushing (`skills/git-commit-and-sync` keeps that role); wiring the tool as a pre-push hook or skill step (left to the plan as an open decision).

## Background
`rules/toolchain.md` "Standard validation sequence" (verified, lines 30-104) lists a 9-step ordered sequence: (1) ruff format+lint, (2) mypy (+ pyright alternate), (3) import-linter (`lint-imports`), (4) ast-grep, (5) bandit, (6) pytest, (7) diff-cover, (8) pre-commit `run --all-files`, (9) `git diff` review. `routing.md` "When to run which tool" (verified, lines 80-117) lists 29 path-keyed conditional checkers keyed to what changed (docs, DB schema, module size, Needs confirmation markers, tools/ changes, skills, workitems, ADRs, Japanese prose, and so on). `AGENTS.md` Global Rule 9 makes running the applicable ones mandatory.

The gates are currently spread across four places, all verified:
- `.pre-commit-config.yaml` runs a subset as hooks (ruff, ruff-format, mypy, docs-consistency, tool-descriptions-sync, check-compat-shims, check-suppression-justification, git-exc-import-guard, adr-invariant-matrix, adr-reference-scoped, adr-structure, skills-references, docs-japanese, known-deviation-sync, metadata-field-policy, plan-target-overlaps, conftest-integrity, workitem-traceability, mock-patch-targets, check-docstrings, check-module-size). It does **not** run `bandit`, `lint-imports`, `pytest`, or `diff-cover` (`Strongly implied by code`: only hook ids were read, not each hook's `entry`; confirmed by the id list).
- `.github/workflows/ci.yml` runs the `lint` job (ruff, mypy, bandit, `lint-imports`, DB separation, reference-table drift, docstrings, module size, `pre-commit run --all-files`) and the `test` job (`pytest` + `diff-cover` with `--fail-under=90`).
- `tox.ini` defines `envlist = lint, typecheck, tests` only.
- No `Makefile` or `justfile` exists; `.claude/settings.local.json` holds permissions only.

`d388529d1` ("raise the module size gate from 16384 B to 20480 B") is a recent example of a gate enforced in both pre-commit and CI. `ast-grep` (toolchain step 4) is present in `rules/toolchain.md` but absent from both pre-commit and CI, so it is a local-only gate today.

Repository tools already cover the individual operations (`Explicit in code`, per `tools/TOOL_DESCRIPTIONS.md`): each `tools/check_*.py` and the `lint-imports`/`bandit`/`pytest`/`diff-cover` invocations exist and are callable. No tool runs the whole selection as one entry point (`Needs confirmation`: judged from `routing.md` and the tool list, not from reading every tool body).

## Problem
No single place answers "what must I run for this diff". The author or agent has to read `rules/toolchain.md`, scan the routing table against the changed paths, and run each command. Gates that are not pre-commit hooks (`bandit`, `lint-imports`, `pytest`, `diff-cover`) are skipped locally and fail only in CI. The same selection effort is repeated every session.

## Reason for Change
Local feedback before commit is cheaper than a red CI run, and the rule set already exists in prose, so the only missing piece is an executable form. This also supports `AGENTS.md` Global Rule 7 (extract an operation performed repeatedly into a `tools/` script).

## Implementation Intent
Add one tool under `tools/` that maps changed paths (from `git diff` against a base, staged plus unstaged) to the existing checkers and commands and runs them in the documented order. It must call the existing commands, not reimplement their checks, and must not duplicate what pre-commit already runs beyond a single `pre-commit run` step. The mapping is data (a table in the tool, or a TOML under `config/` if the repository convention allows), kept next to `routing.md` semantics so drift is detectable. It reports each gate with the canonical `Pass`/`Fail`/`Partial`/`Not available`/`Blocked` vocabulary from `rules/ai-execution.md` Repository Tool Usage item 11. Whether to also wire it as a pre-push hook or a skill step is left to the plan.

## Design
**Architecture.** `tools/` scripts are not under `scripts/`, so the import-layer contract does not constrain them. `run_validation_gates.py` is a thin orchestrator: it discovers changed files, looks up the mapping data, and shells out to the existing commands via subprocess, calling them rather than reimplementing their checks. It imports nothing from `scripts/`.

**Two-source mapping.** The tool serves two documents with different shapes: `rules/toolchain.md` gives a linear 9-step order (used by full mode and as the canonical run), and `routing.md` gives ~29 path-keyed conditional checkers (used by fast mode to select only what the changed files trigger). Both feed one embedded data structure keyed by path-pattern → gate, where each gate records its canonical command and which source it belongs to. This keeps a single run coherent: fast mode selects a subset of the same gates the full mode would run.

**Source-of-truth discipline.** `rules/toolchain.md` stays the canonical command list. The tool's embedded commands mirror it; they are not independently editable elsewhere. `REQ-006`'s drift test fails when a `routing.md` checker has no mapping entry, so `routing.md` cannot advance ahead of the tool silently. The AI Implementation Instruction's stop-and-report-on-contradiction guard applies if the inventory and `rules/toolchain.md` ever disagree (UNK-04).

**Vocabulary.** Result classification uses the `Pass`/`Fail`/`Partial`/`Not available`/`Blocked` vocabulary from `rules/ai-execution.md` Repository Tool Usage item 11; a skipped or unavailable gate is reported as `Not available`/skipped, never as `Pass`.

**Modes.** Fast mode runs only the gates selected by the changed files. Full mode runs the same selection plus the full `pytest` suite and `diff-cover --fail-under=90`, gated behind an explicit flag so fast mode stays cheap (resolves UNK-02).

**Local-only gates.** `ast-grep` (toolchain step 4) is included even though it is not a pre-commit hook or a CI job; the tool makes the local-only coverage explicit rather than hiding it.

**Operational dependency.** `workitem001` (`20261023-173429`) also adds a `tools/` entry and edits `tools/TOOL_DESCRIPTIONS.md`; both plans touch the same file, so their implementation commits should be coordinated (sequential or combined) to avoid a merge conflict on `tools/TOOL_DESCRIPTIONS.md`. This is an implementation-order concern, not a plan blocker.
