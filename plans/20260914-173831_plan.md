# Plan: Make DLQ promotion and requeue atomic, locked, and documented

## Goal

Guarantee deterministic and auditable DLQ transitions under concurrent execution by moving the relevant reads/writes under the shared database lock, and document the requeue API's contract precisely enough to update or retire `EVENTBUS-002` per the documentation policy.

## Priority
Medium

## Scope
- **In-Scope**: DLQ requeue atomicity (shared-lock fix), requeue API contract documentation, EVENTBUS-002 resolution
- **Out-of-Scope**: Background recovery sweep changes beyond what the shared-lock fix requires, unrelated replay/publish logic changes

## Background
Immediate DLQ promotion, the background recovery sweep, and requeue locking currently form one lifecycle whose concurrency behavior is not guaranteed atomic; this issue moves the requeue path's redelivery/sequence-lookup/failure-state inspection under the shared database lock and documents the requeue API's response contract, superseding `EVENTBUS-002`'s undocumented-pagination note where applicable.

## Problem
The DLQ requeue request path does not currently guarantee that redelivery, new-sequence lookup, and failure-state inspection all occur under one shared lock/transaction, so concurrent requeue attempts risk a non-deterministic outcome (e.g. more than one successful redelivery, or an incorrect returned sequence). Separately, the requeue API's request parameters, defaults, bounds, ordering, and response fields are not fully documented, and `EVENTBUS-002`'s pagination-format note may already be stale or partially overlapping with this gap.

## Reason for change
Immediate promotion, recovery sweep, requeue locking, and concurrency behavior form one DLQ lifecycle.

## Implementation intent
Guarantee deterministic and auditable DLQ transitions under concurrent execution by moving the relevant reads/writes under the shared database lock, and document the requeue API's contract precisely enough to update or retire `EVENTBUS-002` per the documentation policy.

## Design

### Shared-Lock Fix for Redelivery + Sequence Lookup (REQ-001, REQ-002)
Current state in `dlq_requeue()`:
```python
# Line 69: Under lock
success, new_event_id = await run_with_db_lock(_redeliver)
if success:
    # Lines 78-83: OUTSIDE lock — GAP!
    row = db.execute("SELECT seq FROM events WHERE event_id = ?", (new_event_id,)).fetchone()
    if row is not None:
        resp["new_seq"] = int(row[0])
```

The gap between line 69 (under lock) and lines 78-83 (outside lock) means:
1. Another concurrent operation could modify the database between lock release and seq lookup
2. The seq lookup could fail or return stale data
3. The response could include an incorrect `new_seq` value

**Decision**: Extend `redeliver_event()` to return `(success, new_event_id, new_seq)` where `new_seq` is computed atomically within the same transaction.

```python
# In db.py:
def redeliver_event(
    conn: sqlite3.Connection,
    event_id: str,
    now: str | None = None,
) -> tuple[bool, str | None, int | None]:
    """Redeliver a dead-lettered event by inserting a new row with lineage.

    Returns (success, new_event_id, new_seq):
      - (True, new_event_id, new_seq)   = event found and redelivered
      - (False, None, None)             = event not found in DLQ or already redelivered
    """
    # ... existing concurrency guard logic (unchanged) ...
    
    ts = now if now is not None else "strftime('%Y-%m-%dT%H:%M:%SZ', 'now')"
    new_event_id = uuid.uuid4().hex
    
    # Insert new row and get its seq in one operation
    cur = conn.execute(
        f"INSERT INTO events ({_COL_EVENT_ID}, topic, payload, producer, published_at, {_COL_DELIVERY_FAILURE_COUNT}, {_COL_CYCLE_FAILURE_COUNT}, redelivered_from) "
        f"VALUES (?, ?, ?, ?, {ts}, ?, 0, ?)",
        (new_event_id, topic, payload, producer, delivery_failure_count, event_id),
    )
    new_seq = int(cur.lastrowid) if cur.lastrowid else None
    
    conn.commit()
    return (True, new_event_id, new_seq)
```

This eliminates the need for a separate seq lookup outside the lock. The `lastrowid` gives us the sequence number atomically at insert time.

For the error path, also move the failure-state inspection under the lock:
```python
# In dlq_route.py:
async def dlq_requeue(...):
    db = get_db(request)
    
    def _redeliver_and_inspect():
        success, new_event_id, new_seq = redeliver_event(db, event_id)
        if not success:
            # Inspect failure state under lock
            row = db.execute(
                "SELECT dlq_at FROM events WHERE event_id = ?", (event_id,)
            ).fetchone()
            if row is not None:
                return (False, ERR_EVENT_NOT_IN_DLQ, 409)
            return (False, ERR_EVENT_NOT_FOUND, 404)
        return (True, new_event_id, new_seq)
    
    result = await run_with_db_lock(_redeliver_and_inspect)
    if isinstance(result, tuple) and len(result) == 3:
        _, detail, status_code = result
        raise HTTPException(status_code=status_code, detail=detail)
    
    success, new_event_id, new_seq = result
    if success:
        logger.info("dlq redelivered event_id=%s -> %s", event_id, new_event_id)
        resp = {
            "event_id": event_id,
            "requeued": True,
            "new_event_id": new_event_id,
            "new_seq": new_seq,
        }
        return resp
```

### API Contract Documentation (REQ-004, REQ-005)
Create `docs/eventbus/07_operations-dlq-requeue.md` documenting the requeue API:

**Request**:
- Endpoint: `POST /dlq/requeue`
- Query parameter: `event_id` (required, string) — the original event ID to requeue
- No default values — `event_id` is mandatory
- No bounds validation beyond type checking (handled by FastAPI)

**Response (HTTP 200)**:
```json
{
    "event_id": "<original event ID>",
    "requeued": true,
    "new_event_id": "<UUID v4 hex>",
    "new_seq": <integer>
}
```

**Response (HTTP 409)**:
```json
{
    "error": "Event not in DLQ"
}
```

**Response (HTTP 404)**:
```json
{
    "error": "Event not found"
}
```

**Empty-result behavior**: If no events are in DLQ, `/dlq/list` returns `{total: 0, items: []}` — documented separately in DLQ list endpoint docs.

**Invalid-parameter behavior**: Missing `event_id` query parameter returns HTTP 422 (FastAPI validation). Empty `event_id` (`?event_id=`) returns HTTP 404 (not found).
