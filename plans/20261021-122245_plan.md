## Design
This is a document-driven, Path A decision with a conditional automation branch. The live corpus has 0 findings, so a new gate is feasible without remediation. The critical constraint is the missing `--strict`: the checker is report-only by default and always exits 0 on warnings. Therefore:
- A **warning gate** (non-blocking) can be wired immediately (routing row, pre-commit, or CI) with no tool change.
- A **blocking gate** requires adding `--strict` to the checker, which violates the "do not modify the checker" constraint without explicit owner sign-off per `rules/coding.md`'s explicit sign-off gates. The plan routes a blocking-gate decision through that gate.
The `--strict` documentation drift (docstring, `TOOL_DESCRIPTIONS.md`, issue text) is a separate, low-severity defect that should be corrected in the same change (REQ-004) regardless of the automation decision.
