# Plan: Remove redundant unconditional sleep in close_resources settlement block

## Goal
Eliminate the unconditional 10-second `_GRACEFUL_TIMEOUT_S` delay on every process shutdown in `ResourceShutdownCoordinator.close_resources()`, restoring prompt shutdown timing for healthy cases while preserving the timeout error path for genuinely unsettled operations.

## Priority
Medium

## Scope
- **In-Scope**: Removing or making conditional the settlement block sleep in `scripts/agent/resource_shutdown_coordinator.py`; updating the class docstring to reflect the corrected behavior; adding tests for both healthy and timeout paths.
- **Out-of-Scope**: Changing `_GRACEFUL_TIMEOUT_S`'s value (10.0); task-cancellation-ordering logic (lines 60-104), tracked separately; WAL checkpoint/backup changes; service lifecycle shutdown changes.

## Background
The prior implementation procedure (`implementations/done/20260904-102208_01_scripts_agent_resource_shutdown_coordinator_py.md`) replaced `asyncio.sleep(0)` with `asyncio.sleep(_GRACEFUL_TIMEOUT_S)` to satisfy REQ-RSC002-1 (timeout actually fires when operations don't settle). However, this introduced a regression against REQ-RSC002-3 (no regression in shutdown timing for healthy cases): the settlement block now unconditionally waits `_GRACEFUL_TIMEOUT_S` seconds on every shutdown, even though `pending_tasks` are already awaited to completion earlier in the same method at line 81 via `asyncio.gather(*pending_tasks, return_exceptions=True)`.

## Problem
Every shutdown — healthy or not — unconditionally blocks for `_GRACEFUL_TIMEOUT_S` (10) seconds in the settlement block (lines 140-158), even though the tasks it might be "waiting for" were already awaited to completion earlier in the same method. This directly violates REQ-RSC002-3 ("No regression in shutdown timing for healthy cases").

## Reason for change
An unconditional 10-second delay on every process shutdown is an operational cost (slower restarts, slower deploys, slower test teardown wherever this path runs) introduced specifically to fix a no-op timeout check — but the fix traded "timeout never fires" for "shutdown always takes the full timeout," which the original issue's own acceptance criterion (REQ-RSC002-3) explicitly prohibited.

## Implementation intent
Remove the redundant unconditional sleep, or make the settlement wait conditional on genuinely unresolved state (if any exists beyond what line 81's `gather()` already resolved). Since `pending_tasks` are already fully awaited by that `gather()` call, the settlement block likely has no remaining state to wait for at all — confirm this and, if so, remove the block (or reduce it to purely defensive error handling with no artificial delay) rather than inventing a new condition to gate it on.

## Requirements
- `REQ-001`: A healthy shutdown (all tasks already settled via the earlier `gather()`) completes without an unconditional additional `_GRACEFUL_TIMEOUT_S`-second wait.
- `REQ-002`: A shutdown where something is genuinely still unsettled still triggers the timeout error path and is collected in `errors`.
- `REQ-003`: `ResourceShutdownCoordinator`'s docstring accurately describes the resulting settlement behavior.
- `REQ-004`: No regression in existing `resource_shutdown_coordinator.py` tests.

## Design
### Analysis summary
- **Path classification**: Path A (Small Task) — affects ≤ 3 files, no public interface changes, no database schema changes.
- **Target file dependencies**: `scripts/agent/resource_shutdown_coordinator.py` imports `asyncio`, `logging`, `CLIView`, and TYPE_CHECKING references to `AgentContext` and `WalCheckpointManager`. No runtime-facing interface changes.
- **Callers**: `scripts/agent/repl.py` creates `ResourceShutdownCoordinator` and calls `close_resources()` in the run() finally block. No caller depends on the 10s delay being present.
- **Evidence verification**: Confirmed via `rg -n "_GRACEFUL_TIMEOUT_S|asyncio.gather|asyncio.sleep" scripts/agent/resource_shutdown_coordinator.py` that lines 144-147 contain the unconditional `asyncio.sleep(_GRACEFUL_TIMEOUT_S)` call wrapped in `asyncio.wait_for(..., timeout=_GRACEFUL_TIMEOUT_S)`. The `TimeoutError` handler at lines 148-155 would never fire because `asyncio.sleep()` itself cannot exceed its own timeout argument.

### Design decision
The settlement block (lines 140-158) serves no functional purpose given that `pending_tasks` are already awaited to completion at line 81. The `TimeoutError` branch can never trigger because `asyncio.sleep(_GRACEFUL_TIMEOUT_S)` will complete normally within `_GRACEFUL_TIMEOUT_S` seconds regardless of task state. The correct resolution is to remove the entire settlement block.

If future investigation reveals that some state outside `pending_tasks` requires a settlement period, the replacement would be a conditional wait using `asyncio.wait_for()` with a dynamic timeout based on actual pending work, capped at `_GRACEFUL_TIMEOUT_S` as a ceiling — not as a fixed floor. However, the current evidence suggests no such state exists.
