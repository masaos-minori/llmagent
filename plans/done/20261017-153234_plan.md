# Plan — Make retry-suppression and empty-result defaults observable

## Goal
Make the effective on/off state of the ToolLoopGuard retry-suppression and
empty-result-repeat guards observable at startup, and document the `> 0` / `<= 0`
config semantics. Add a single concise startup diagnostic that reports whether each
guard is enabled for the resolved config, and document the semantics on the config
fields and in the Known Limitations section. Do NOT change defaults or gating logic.

## Priority
Medium

## Scope
- **In-Scope**: Adding a one-time startup diagnostic that logs the effective on/off
  state of retry suppression (`tool_error_retry_max > 0`) and empty-result repeat
  detection (`tool_empty_result_max_repeats > 0`); documenting the `> 0` enables /
  `<= 0` disables semantics on the two `ToolConfig` fields and in the Known
  Limitations bullet; adding a regression test that the diagnostic reflects the
  configured state for both on and off cases and that defaults are unchanged.
- **Out-of-Scope**: Changing the default values (`tool_error_retry_max=1`,
  `tool_empty_result_max_repeats=0`); enabling empty-result detection by default;
  modifying any guard gating logic, cycle-detection algorithm, or thresholds; other
  guards (dedup, cycle, stagnation, consecutive-error).

## Background
`scripts/agent/tool_loop_guard.py` gates two per-turn guards on their config:

```python
def record_tool_result(self, tool_name, result):
    if ctx.cfg.tool.tool_empty_result_max_repeats <= 0:
        return   # empty-result detection OFF
    ...

def check_empty_result_repeat(self, message):
    if ctx.cfg.tool.tool_empty_result_max_repeats <= 0:
        return None
    ...

def check_retry_suppression(...):
    if ctx.cfg.tool.tool_error_retry_max <= 0:
        return None   # retry suppression OFF
    ...
```

Defaults (`scripts/agent/config_dataclasses.py`): `tool_error_retry_max = 1` (on),
`tool_empty_result_max_repeats = 0` (off).
`docs/23_agent/agent_03_02_...llm-tool-loop.md` Known Limitations lists:
"Retry suppression is only effective if `tool_error_retry_max > 0`. Empty result
repeat detection is only effective if `tool_empty_result_max_repeats > 0`."

`ToolLoopGuard` is instantiated per turn in
`scripts/agent/llm_turn_executor.py:80` (`guard = ToolLoopGuard(self._ctx)`); its
`check_all()` is called from `LLMTurnRunner.run()`. It holds no session-lifecycle
hook of its own.

## Problem
Both guards are effectively invisible to operators: when disabled there is no startup
indication, so an operator cannot tell whether retry/empty-result protection is active.
Empty-result detection is off by default with no signal, so a loop of empty results
can spin undetected unless explicitly enabled. The `> 0` enables / `<= 0` disables
semantics are documented only in a Known Limitations bullet, not near the config
fields themselves.

## Reason for change
Ambiguous, silent configuration behavior makes it easy to ship without the intended
protection and hard to diagnose why a guard did not fire. Making the effective state
observable and documenting the semantics reduces misconfiguration and improves
debuggability. This is observability + documentation only; runtime behavior is
unchanged.

## Implementation intent
Add a startup-time diagnostic that reports the effective on/off state of both guards
for the resolved config, and document the `> 0` / `<= 0` semantics on the config
fields and in the Known Limitations section. Name the boundary: only add reporting +
docs; do NOT touch the `<= 0` gating or the defaults.

Two equivalent mechanisms satisfy the emit; implement one:
- **(a) Module-once flag in the guard constructor (recommended):** Add a method
  `ToolLoopGuard.report_effective_state()` that reads the two config values and emits
  one concise `logger.info`/`logger.warn` line. Call it from `__init__` guarded by a
  module-level `_STARTUP_REPORTED` boolean so it fires exactly once per process (the
  guard is constructed per turn, so an unguarded constructor call would spam every
  turn).
- **(b) Emit from the startup sequence:** Locate a genuine one-time session-start hook
  in the startup path and call `report_effective_state()` there. Prefer (a) unless a
  clean, already-once startup hook is confirmed (see UNK-02).

## Requirements

## Assumptions
- A module-level `_STARTUP_REPORTED` flag is acceptable for the "once per process"
  guarantee; it resets on process restart (which is the intended "startup" semantic).
- `logger.info`/`logger.warning` from `tool_loop_guard.__name__` is sufficient for the
  operator-facing signal; no new output channel required.
- The off case for empty-result detection (default off) may warrant `warning` level to
  surface that protection is absent; the on case uses `info`.

## Design
Path B (touches 4 files: 2 code, 1 test, 1 doc). Adversarial verification (Step 2)
confirmed the issue's claims against current source: `tool_loop_guard.py` gates
empty-result detection at lines 126 and 139 on
`cfg.tool.tool_empty_result_max_repeats <= 0` and retry suppression at line 308 on
`cfg.tool.tool_error_retry_max <= 0`; defaults are
`tool_error_retry_max=1` (line 172) and `tool_empty_result_max_repeats=0` (line 176)
in `config_dataclasses.py`; the Known Limitations bullets exist at doc lines 117-118.
The guard is constructed per turn (`llm_turn_executor.py:80`), so a naive constructor
emit would fire every turn — the plan uses a module-level `_STARTUP_REPORTED` flag to
guarantee one emission per process (UNK-01). The one genuine open question is WHERE the
diagnostic belongs (a real startup hook vs. the module-once flag) and whether the off
case should be `warning`; both are non-blocking design preferences. No architecture,
interface, schema, or module-boundary change; runtime behavior is frozen (REQ-007).

## Risks
- **Risk**: Emitting in `__init__` without a once-flag spams a log line every turn. →
  **Mitigation**: Module-level `_STARTUP_REPORTED` flag (REQ-002).

  **Mitigation**: Keep the flag inside the guard method so relocation is a one-line
  caller change.
- **Risk**: Logging-unavailable crashes startup. → **Mitigation**: try/except around
  the log call (REQ-003).
- **Risk**: Accidentally altering a default or threshold. → **Mitigation**: REQ-004
  regression test + existing gating tests remain green (REQ-007).
