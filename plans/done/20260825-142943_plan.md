## Background
本Planは `issues/20260825_cfgreload_toolexecutor_cache_wiring_issue.md`(`plans/20260825-142436_plan.md`)・`issues/20260825_config_validators_dead_cache_validator_issue.md`(`plans/20260825-142646_plan.md`)と同じ、未作成の前提変更(`ToolExecutor` キャッシュ削除)に依存していた。

**前提は解消された**: `issues/done/20260826_delete_tool_executor_cache_issue.md` / `plans/done/20260826-120000_plan.md` により、`ToolExecutor` のキャッシュ機構は2026-08-27時点で完全に削除され、`origin/master` にマージ済み。

**本サイクルの敵対的検証(2026-08-27)で判明した追加事実**:
- 広域grep(`stampede\|_execute_with_cache\|ToolExecutor.*cache\|cache.*ToolExecutor\|stat_cache_hits\|Cache hits\|tool_cache_ttl\|tool_cache_max_size`)を再実行した結果、本Planが確定した14ファイルのリストに変動はない(UNK-02解消、ドリフトなし)。
- キャッシュだけでなく `_execute_with_stampede_protection()`(stampede protection、inflight future共有)自体も別実装で完全に削除されている(`self._inflight` も含めて消滅) — 本Planの元々のImplementation intentが想定していた「stampede protection廃止」という記述はそのまま正しい記述になる。
- `execute()` の現在の実際のフローは `ToolExecutor.execute()` → `_raw_execute()`(`resolve server_key` → `_run_gate_chain()`[startup_mode gate → health gate] → `_ensure_lifecycle_ready()` → transport resolution → semaphore付き `_invoke_and_record()`)であり、キャッシュ・stampede protectionのステップは一切ない。各ファイルの書き換え文言はこの正確なフローに合わせる。
- **既存の実装手順書 `implementations/20260825-224356_11_docs_tool_cache_removal.md` を発見** — 14ファイルすべてを1つの文書にまとめた形式(このワークフローの「1 target file = 1 document」原則に反する)で、`Source plan` は本Planを正しく参照しているが、Execution StatusはBlockedのまま未実装。実際に14ファイルの記述を再確認した結果(Problem参照)、いずれも古い記述のまま変更されていないことを確認した。したがって「Not implemented」として扱い、本サイクルで正式なテンプレート形式(1ファイル1文書)で14個の実装手順書を新規生成する。同文書の各ファイルごとの調査内容(具体的な行番号・現在の文言)は正確であることを確認済みであり、参考情報として活用する。

## Problem

## Reason for change
これらのドキュメントを削除済みの挙動を記述したまま放置すると、人間の保守者・ドキュメントを読むAIエージェントの双方に、Tool結果が引き続きキャッシュされていると誤解させる。

## Implementation intent
前提となるキャッシュ削除が着地した時点で、上記14ファイルの該当セクションを削除または書き換え、「Tool結果はもうキャッシュされず、同一の同時呼び出しはそれぞれMCPサーバーへ到達する(stampede protection廃止)」という実態を反映する。`skills/DESIGN.md` の「実装詳細への言及重複を避ける」原則に従い、コード行レベルの詳細ではなく振る舞い/意図のレベルで記述する。
