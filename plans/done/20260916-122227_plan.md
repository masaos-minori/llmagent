## Goal
- Make `RuntimeToolRegistry.apply_policy()` recompute LLM-facing tool visibility from an immutable discovery-time baseline plus the current policy on every call (so a disabled tool becomes re-enabled the moment a later policy allows it again), apply that recomputation as a single atomic registry replacement, and close two confirmed direct-executor call sites that currently bypass mandatory `allowed_tools` preflight enforcement.

## Problem
Adversarial verification (Step 2) checked every claim in the Issue's Problem statement against current source, confirmed the core defect, and found two additional bypass call sites the Issue did not name:

- **Confirmed: cumulative mutation blocks re-enable.** `RuntimeToolRegistry.apply_policy()` computes `enabled_for_llm=enabled and tool.enabled_for_llm` — ANDing the newly-computed `enabled` decision with the tool's *current* (already policy-mutated) `enabled_for_llm` value, not with a fixed discovery-time baseline. Once a tool is disabled by one `apply_policy()` call, its `enabled_for_llm` becomes `False`; a later call that recomputes `enabled=True` (e.g. the tool is back in `allowed_tools`) still ANDs against the now-`False` stored value and stays `False` forever. This exactly matches the Issue's claim and is reproducible by calling `apply_policy()` twice in sequence (verified by direct reading of `scripts/shared/runtime_tool_registry.py`; no existing test exercises this two-call sequence — `tests/shared/test_runtime_tool_registry.py`'s `apply_policy` tests are all single-call).
- **Confirmed: no immutable discovery-time baseline exists.** `RuntimeTool` (`scripts/shared/runtime_tool.py`) has exactly one `enabled_for_llm: bool` field; there is no separate, policy-untouched field recording the tool's original discovery-time visibility. `apply_policy()` has no other source of truth to recompute from.
- **Narrowed: routing does not consult `enabled_for_llm` at all, in either direction.** `RuntimeToolRegistry.resolve()` returns a `server_key` for any registered tool name regardless of `enabled_for_llm` — this is confirmed, but it is by design (routing answers "does this name exist," not "is it currently LLM-visible"); the actual risk is not routing itself but whether every path that turns a resolved route into an executed call also independently checks `allowed_tools`.
- **Confirmed and extended: execution-path enforcement is not mandatory at every direct executor/invoker call site.** The primary orchestration path (`agent.tool_runner.execute_all_tool_calls()` → `agent.tool_runner._run_approval_gate()` → `agent.tool_approval.run_approval_checks()` → `agent.tool_approval.check_approval()` → `agent.tool_policy.check_preflight()`) already enforces `cfg.tool.allowed_tools` for every tool call before it reaches `RepositoryGateway`/`ToolExecutor`, contrary to what the Issue's Target File list implies — `scripts/shared/tool_executor.py` and `scripts/agent/tool_runner.py` do not need behavioral changes; they already gate correctly through this path (see Design). The genuine gap is two call sites the Issue did not name, both of which call `ToolExecutor.execute()` directly, entirely outside `execute_all_tool_calls()`'s gate:
  - `_cmd_diff()` in `scripts/agent/commands/cmd_context.py` calls `await ctx.services.tools.execute("git_diff", ...)` directly from the `/diff` slash command, with no `check_preflight()` call anywhere in the path.
  - `_execute_mdq()` in `scripts/agent/commands/cmd_mdq.py` calls `await tools.execute(tool_name, tool_args)` directly from every `/mdq` subcommand handler, with no `check_preflight()` call anywhere in the path.
  A policy that removes `git_diff` or an MDQ tool name from `cfg.tool.allowed_tools` does not prevent either slash command from executing it — this is the concrete, reproducible instance of the Issue's hedged claim ("a tool hidden from the LLM could still be executable if called by name through a path that bypasses the preflight check").
- **Confirmed but narrowed: atomicity.** `apply_policy()`'s current per-entry mutation loop (`for name, tool in list(self._tools.items()): self._tools[name] = dataclasses.replace(...)`) contains no `await`, so within the current single-threaded asyncio process no concurrent coroutine can observe a torn intermediate state *during* one `apply_policy()` call — the practical exposure today is narrower than "any concurrent reader can see a torn registry." The Issue's Acceptance Criterion is still a real, unimplemented guarantee: nothing in the code structure prevents a future change (an `await` inside the loop, or a second thread) from reintroducing tearing, and the current per-entry-reassignment style does not make the "old-or-new, never partial" invariant explicit or structurally enforced. A single atomic dict-reference swap closes this permanently rather than relying on the absence of `await` as an implicit guarantee.
- **Cross-checked against related Plans/Issues, no contradiction found**: `plans/20260916-114735_plan.md` (mcpagent01, already generated) explicitly scopes its own atomicity guarantee to startup-time publication only and flags (`UNK-02`) that config-reload-time `apply_policy()` atomicity is `mcpagent04`'s (this Issue's) scope to confirm — this Plan is the confirmation and the owner of that mechanism. `issues/20260914-103159_mcpagent05_mcp-lifecycle-invocation-gate-unification.md` (still unprocessed) targets `ToolTransportInvoker`/`ToolExecutor`'s shared gate-chain ordering, not `RuntimeToolRegistry.apply_policy()` or the two command-layer bypass sites this Plan fixes — no overlap. `docs/00_governance_03_issue-and-uncertainty-management.md`'s existing CI entry for ADR-003 Decision #14 explicitly says "Re-evaluate if `mcpagent04` introduces behavioral changes" — this Plan does, and schedules that doc update as its final implementation step, consistent with the Issue's own Documentation Impact instruction ("only after executable verification is available").

## Reason for change
Runtime policy currently mutates effective visibility cumulatively, making disabled tools impossible to re-enable via a later reload. Two direct-executor call sites (`/diff`, `/mdq`) can still execute a tool by name without ever checking `allowed_tools`, so presentation policy (what the LLM sees) and execution policy (what can actually run) can diverge silently.

## Implementation intent
Give `RuntimeTool` an immutable discovery-time LLM-visibility field; make `apply_policy()` recompute `enabled_for_llm` from that field and the complete current policy on every call, applying the result as one atomic dict swap; and add the missing `check_preflight()` call at the two confirmed bypass sites so `allowed_tools` is enforced identically everywhere a tool can be executed by name.

## Design
1. **Immutable base value (`REQ-001`)**: `RuntimeTool` (frozen dataclass) gains a new field recording discovery-time LLM visibility, resolved once at construction and never written to again. Because `RuntimeTool` is frozen and several call sites construct it directly (not only via `build_runtime_tool()`), the field must have a safe default that requires no edits to those call sites — a `None`-sentinel default resolved in `__post_init__` via `object.__setattr__` to mirror the `enabled_for_llm` value actually passed at construction is the smallest, most backward-compatible mechanism (see UNK-01). `build_runtime_tool()` gains a matching optional parameter for explicit override, following its existing `_or_default()` convention.
2. **Recompute-from-base (`REQ-002`)**: `apply_policy()`'s per-tool formula changes from `enabled = (not allowed_tools or name in allowed_tools); enabled_for_llm = enabled and tool.enabled_for_llm` to `enabled_for_llm = tool.<immutable base field> and (not allowed_tools or name in allowed_tools)`. `dataclasses.replace()` continues to be used per tool to build the updated instance (it already preserves any field not explicitly passed, so the immutable base field carries forward unchanged automatically); only the source of the AND's left-hand operand changes, from the tool's current mutable state to its immutable base.
3. **Atomic replacement (`REQ-003`)**: `apply_policy()` changes from `for name, tool in list(self._tools.items()): self._tools[name] = dataclasses.replace(...)` (per-entry reassignment into the live `self._tools` dict) to building a complete new `dict[str, RuntimeTool]` locally, then assigning `self._tools = new_tools` once, after the loop completes. This makes the "old-or-new, never partial" guarantee structural rather than an implicit consequence of the loop containing no `await` — and is a `dict`-swap, not a new `RuntimeToolRegistry` instance, so `apply_policy()`'s existing signature/callers (`config_reload.py`) are unaffected.
4. **Preflight-bypass fix (`REQ-004`, `REQ-005`)**: `check_preflight()` cannot be called from `scripts/shared/tool_executor.py` (the `shared` layer must not import from `agent`, per the enforced import-layer contract — confirmed by this Plan's `lint-imports` run, which found only one pre-existing, unrelated violation elsewhere). The fix must therefore live at the `agent`-layer call sites that currently skip it: `_cmd_diff()` and `_execute_mdq()`, both of which already have `ctx`/`ctx.cfg` in scope and can call `agent.tool_policy.check_preflight()` directly (both files already sit in the `agent` layer, so no new import-layer exception is introduced). On `PolicyViolationError`, each method reports a denial message (reusing the exception's own text, per UNK-02) instead of executing. `PolicyViolationError`'s existing message format (e.g. `f"{tool_name}: not in allowed_tools for this session"`) does not echo tool arguments, so no credential/payload exposure is introduced by surfacing it in `_cmd_diff()`/`_execute_mdq()`'s denial output — consistent with the Issue's AI Implementation Instruction ("logs and tool results do not expose credentials, payloads, raw response bodies, or sensitive configuration").
5. **Test strategy**: registry-level tests (`REQ-006`–`REQ-008`) exercise the corrected formula and atomicity directly against `RuntimeToolRegistry`/`RuntimeTool`; a cross-layer test (`REQ-009`) confirms `check_preflight()` and `apply_policy()` agree for the same `allowed_tools` value; command-layer tests (`REQ-010`, `REQ-011`) exercise the two fixed bypass sites end-to-end. The existing `tests/agent/services/test_config_reload.py` E2E test is regression-run, not modified, since its fixture exercises a single `apply_policy()` call (unaffected by the reversibility fix) and does not assert anything about internal `dict` identity (unaffected by the atomic-swap change).

## Risks
- **Risk**: The `__post_init__`-resolution approach for the new immutable `RuntimeTool` field (UNK-01) could interact unexpectedly with the 5 direct-construction call sites that bypass `build_runtime_tool()`, if any of them rely on strict positional field ordering. → **Mitigation**: implementation phase adds the new field only as a keyword-defaultable field after `allow_extra_fields` (the dataclass's current last field), preserving positional compatibility for any call site using positional args, and runs the full test suite for all 5 affected files before considering Phase 1 complete.
- **Risk**: Rewriting `apply_policy()`'s mutation strategy (REQ-002/REQ-003) changes behavior relied on by `tests/agent/services/test_config_reload.py`'s existing E2E test, even though hand-tracing suggests no assertion is affected. → **Mitigation**: Phase 1's last step explicitly runs this test as a named regression check before Phase 2 begins; any failure pauses implementation and is reported rather than silently patched.
- **Risk**: `mcpagent05` (still unprocessed) may later restructure `ToolExecutor`/`ToolTransportInvoker`'s shared gate chain in a way that changes where `allowed_tools` enforcement conceptually lives, potentially duplicating or conflicting with this Plan's command-layer fix. → **Mitigation**: this Plan's fix is scoped to two specific `agent`-layer call sites, not the shared invocation boundary itself, so it composes independently of whatever `mcpagent05` changes at the `ToolExecutor`/`ToolTransportInvoker` layer; coordinate ordering if both land in the same session.
- **Risk**: The two pre-existing findings noted during this Plan's baseline (the `import-linter` violation and the unused `OutputTag` import) could be mistaken for regressions introduced by this Plan's diff if not called out explicitly during implementation-phase validation. → **Mitigation**: both are recorded here as pre-existing and out of scope; the implementation phase should re-confirm neither finding's line count changed as part of this Plan's diff before reporting validation results.
