## Goal
- Remove the duplicated stderr-log-path bookkeeping and the repeated cleanup/raise
  code blocks in `HttpServerLifecycleManager` (`scripts/agent/http_lifecycle.py`) so
  the server-key -> log-path mapping has a single owner (`StderrLogManager`) and the
  three-way-duplicated failure-cleanup sequences in `_create_and_validate_proc` and
  `_health_poll_until_ready` each live in one place, without changing any public
  behavior of `HttpServerLifecycleManager`.

## Background
`http_lifecycle.py` is a composition facade produced by an earlier module-split
refactor (`issues/done/20260915-102515_refactor_http_lifecycle_module_split.md`) and
most recently had a dead-code/duplication pass in
`issues/done/20260919-115306_refactor_002_consolidate_remaining_http_lifecycle_duplication_and_dead_code.md`
(commit `8020c683`), which removed the unused `ProcessSnapshotProvider` module and
delegated `shutdown_all()` to `ShutdownCoordinator`. That pass did not touch the
stderr-path duplication or the repeated cleanup blocks this Plan addresses.

## Problem
Confirmed by reading `scripts/agent/http_lifecycle.py`,
`scripts/agent/http_lifecycle_stderr_log_manager.py`, and
`scripts/agent/http_lifecycle_shutdown_coordinator.py`, and by
`uv run radon cc scripts/agent/http_lifecycle.py -s -n B`:

1. **Duplicated state / encapsulation break** — `HttpServerLifecycleManager.__init__`
   declares `self._stderr_log_paths: dict[str, str] = {}` (`http_lifecycle.py:87`).
   `_open_stderr_log` (`http_lifecycle.py:90-96`) populates it by reading
   `self._stderr_log_manager._log_paths` — a private attribute of the collaborator
   `StderrLogManager` (`http_lifecycle_stderr_log_manager.py:30`) — instead of a
   public accessor (confirmed: `StderrLogManager` currently exposes no such accessor;
   only `open_log`, `read_tail`, `rotate_log`). The two dicts are kept in sync
   manually via **six** independent call sites, not five as the source Issue stated:
   the five `.pop(server_key, None)` sites in `http_lifecycle.py:176, 278, 305, 331,
   476`, **plus** one bulk `manager._stderr_log_paths.clear()` call in
   `ShutdownCoordinator.shutdown_all()` (`http_lifecycle_shutdown_coordinator.py:132`)
   that the source Issue's Target Files or Areas section omitted entirely.
2. **Repeated cleanup blocks** — `_create_and_validate_proc`
   (`http_lifecycle.py:244-336`, radon complexity B(9)) repeats the same
   "close stderr handle, pop `_stderr_files`, pop `_stderr_log_paths`" sequence in
   three separate failure branches (lines 275-278, 302-306, 327-334).
   `_health_poll_until_ready` (`http_lifecycle.py:338-423`, radon complexity B(6))
   repeats the same "cleanup resources, pop `_http_procs`, pop `_http_pgids`, build
   `StartupFailure`, raise `HttpStartupError`" sequence across its early-exit,
   shutdown-requested, and timeout branches (lines 372-387, 399-410, 412-423).
   `_read_stderr_for_cleanup` (`http_lifecycle.py:167-169`) is a pure one-line
   passthrough to `_read_stderr_tail` (`http_lifecycle.py:98-110`) with no added
   behavior.

## Reason for change
The duplicated `_stderr_log_paths` state and its six independent write/pop/clear
sites are a maintenance risk: a future change to any of the three files that touch it
can forget one site and leave `_stderr_log_paths` out of sync with
`StderrLogManager`'s own bookkeeping, silently corrupting `get_process_info`/
`get_process_snapshot` output (`http_lifecycle.py:193` reads `_stderr_log_paths`
directly) with no test pinpointing the cause. This Plan's own Step 2/3 verification
already found one such gap the source Issue missed (`ShutdownCoordinator`'s direct
`.clear()` call), which is itself evidence for the risk being described. The repeated
cleanup-and-raise blocks in `_health_poll_until_ready` and `_create_and_validate_proc`
are the direct cause of their radon B-grade complexity and make the three failure
branches harder to verify stay behaviorally identical as the file evolves.

## Implementation intent
Give `StderrLogManager` sole ownership of the server-key -> log-path mapping: add
`get_log_path(server_key) -> str | None` (read), `forget(server_key) -> None` (remove
one entry — replaces the five `.pop()` sites), and `clear() -> None` (remove all
entries — replaces `ShutdownCoordinator`'s bulk `.clear()` call), mirroring the two
existing removal patterns exactly so every current call site has a direct
replacement. Remove `HttpServerLifecycleManager._stderr_log_paths` entirely once every
read site is routed through `get_log_path()`. Extract the repeated
"read-stderr-tail, drop tracked process/pgid entries, build-and-raise
`HttpStartupError`" sequence in `_health_poll_until_ready` into one private helper
used by all three branches, and the repeated stderr-handle-and-tracking cleanup in
`_create_and_validate_proc`'s three failure paths into one private helper. Remove
`_read_stderr_for_cleanup` and call `_read_stderr_tail` directly from
`_cleanup_server_resources`. Preserve the existing public behavior of `start`,
`restart`, `shutdown_all`, `get_process_info`, `get_process_snapshot`, and
`list_processes` exactly — this is an internal-structure change only.

## Design
Ownership consolidation: `StderrLogManager` becomes the sole owner of the
server-key -> log-path mapping. `HttpServerLifecycleManager` keeps its own
`_stderr_log_manager: StderrLogManager` instance (already present,
`http_lifecycle.py:80`) and calls `self._stderr_log_manager.get_log_path(server_key)`
wherever it currently reads `self._stderr_log_paths.get(server_key, ...)`
(`http_lifecycle.py:100, 193`), and `self._stderr_log_manager.forget(server_key)`
wherever it currently does `self._stderr_log_paths.pop(server_key, None)`
(`http_lifecycle.py:176, 278, 305, 331, 476`). `ShutdownCoordinator.shutdown_all()`
calls `manager._stderr_log_manager.clear()` in place of its current
`manager._stderr_log_paths.clear()` (`http_lifecycle_shutdown_coordinator.py:132`).
`HttpServerLifecycleManager._stderr_log_paths` and its `__init__` declaration
(`http_lifecycle.py:87`) are deleted once no read site remains.

Cleanup-helper extraction: `_health_poll_until_ready`'s three failure branches
(early-exit, shutdown-requested, timeout) each currently do: read stderr tail via
`_cleanup_server_resources`, pop `_http_procs`/`_http_pgids`, construct a
`StartupFailure` with a branch-specific `reason`, and raise `HttpStartupError`. A new
private helper takes the `server_key` and a `reason: str` string, performs the shared
cleanup, and raises — collapsing three ~15-line blocks into three single-line calls
plus the branch-specific condition. `_create_and_validate_proc`'s three failure
branches (validation `ValueError`, `Popen` `Exception`, `getpgid` `OSError`) currently
each do: close `stderr_fh`, pop `_stderr_files`, and (per the ownership consolidation
above) call `_stderr_log_manager.forget()`. A new private helper takes the
`server_key` and `stderr_fh`, performs this shared cleanup, and is called from all
three branches before each branch's own distinct re-raise/log statement.

## Risks
- **Risk**: `http_lifecycle.py` is a high-churn (45 commits total, 9 in the last 30
  days), single-effective-author composition facade sitting on the MCP subprocess
  startup/shutdown path — a mistake here has a broad blast radius across every HTTP
  MCP server's lifecycle. → **Mitigation**: no public method signature changes
  (Scope/Implementation intent), full targeted + full-suite pytest run, and
  diff-cover ≥90% before considering the change done.
- **Risk**: a private-attribute call site outside the three files identified here is
  missed, the same way the source Issue missed `ShutdownCoordinator`'s call site. →
  **Mitigation**: `AC-1`/`AC-2` require an `rg` sweep for `_log_paths` and
  `_stderr_log_paths` across all of `scripts/` (not just the target files) before
  the change is considered complete, so a missed site fails the acceptance check
  rather than surfacing later as a runtime bug.
- **Risk**: the Mock-based `test_http_lifecycle_shutdown_coordinator.py` test could be
  updated in a way that makes it pass vacuously (e.g. asserting a mock was called
  without asserting what it was called with), silently losing coverage of the actual
  clear-on-shutdown behavior. → **Mitigation**: the updated assertion must check the
  mocked `StderrLogManager.clear()` call happened (not just that some attribute is
  empty), per Implementation step 2's explicit instruction.
