# Work Plan: Enhance ToolLoopGuard cycle detection beyond exact fingerprint matching

## Goal
Enhance cycle detection to recognize partial progress patterns, allowing earlier intervention and better user experience instead of waiting for the LLM to exhaust all allowed turns.

## Scope
- Modify `scripts/agent/tool_loop_guard.py` to add `_check_progress_stagnation()` method
- Update `check_all()` to also call the new stagnation check
- Consider adding a new config field to `ToolConfig` in `config_dataclasses.py`
- Document the new guard behavior in the class docstring

## Assumptions
1. `max_tool_turns=5` prevents true infinite loops but doesn't detect stagnation patterns
2. Tracking unique tool names per round can identify stagnation patterns
3. A configuration option for a "progress window" can measure how many distinct tool names have been used recently

## Unknowns
1. Does `check_cycle()` correctly detect exact fingerprint matches? Need to verify implementation.
2. What is the maximum number of tool calls per round? Affects how many unique tool names we track.
3. Should stagnation detection use tool names only, or also consider argument similarity?

## Affected areas
- scripts/agent/tool_loop_guard.py
- scripts/agent/llm_turn_runner.py
- scripts/agent/config_dataclasses.py
- Cycle detection components

## Design
The current `check_cycle()` method detects cycles by comparing round-level fingerprints (sorted tool call name+argument pairs hashed via MD5). This should be enhanced to track unique tool names per round and detect when the same subset of tools is repeatedly invoked without new tools being introduced.

## Implementation steps
1. Read `scripts/agent/tool_loop_guard.py` and identify the exact location of `check_cycle()`
2. Add a new `_check_progress_stagnation()` method that tracks unique tool names per round in `TurnLoopState`
3. Compare recent rounds' tool name sets against historical patterns
4. Return an exit message when stagnation is detected (different tools but no new capabilities being exercised)
5. Update `check_all()` to also call the new stagnation check
6. Consider adding a new config field to `ToolConfig` in `config_dataclasses.py`:
   ```python
   # Number of recent rounds to consider for progress stagnation detection.
   # When the same subset of tool names appears in N consecutive rounds
   # without any new tool being introduced, treat it as stagnation.
   progress_stagnation_window: int = 3
   ```
7. Document the new guard behavior in the class docstring
8. Run tests to ensure no regressions

## Validation plan
- Unit test for `check_cycle()` with exact fingerprint matches at threshold boundary
- Unit test for new stagnation detection with different tool sequences that show no progress
- Integration test verifying guard behavior during extended tool-call loops

## Risks
1. Stagnation detection may produce false positives for legitimate repeated tool usage patterns
2. Adding progress_stagnation_window config field requires updating ToolConfig schema
3. Existing tests may not cover stagnation scenarios, requiring new test cases
