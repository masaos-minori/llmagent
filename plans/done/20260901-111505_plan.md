## Goal
- Add `tools/rename_doc.py`, a script that renames a `docs/*.md` file (including
  `docs/adr/*.md`) via `git mv` and rewrites every Markdown-link path across `docs/`
  that points at the old path, in one pass, so the manual grep-then-hand-edit cycle
  currently used for every documentation rename is no longer required.

## Priority
Medium

## Scope
- **In-Scope**:
  - `tools/rename_doc.py <old-path> <new-path>`: performs the move via `git mv`, then
    finds and rewrites every Markdown-link path (`[text](path)` form) across `docs/`
    that resolves to `old-path`, preserving each referencing file's existing
    relative-link convention (with vs. without a `../` prefix).
  - `--old-title "..." --new-title "..."` opt-in flag: when both are given, also
    rewrites link text adjacent to a rewritten link path that duplicates the old
    title. Never inferred automatically.
  - Reporting (not modifying) any reference to the old filename that is not inside a
    Markdown link (plain prose mention).
  - `--dry-run` (default) / `--apply` mode, consistent with `fix_docstring_paths.py`
    and `fix_docs_section_marks.py`'s existing convention.
  - `tools/TOOL_DESCRIPTIONS.md` entry for the new tool, in the same
    "ドキュメント構造検証・整形補助スクリプト" table as `rename_mcp_modules.py`.
  - `tests/tools/test_rename_doc.py`.
- **Out-of-Scope**:
  - Renaming or restructuring `scripts/*.py` files (`rename_mcp_modules.py`'s existing
    scope).
  - Automatically resolving non-link prose mentions of the old filename.
  - Renaming an ADR's numeric ID (e.g. `ADR-004` -> a different number) or updating
    `docs/adr-index.md`'s ID column / plain-text `ADR-NNN` mentions — per the Issue's
    Unresolved Questions, this needs a separate owner decision; this Plan implements
    file-path-only renaming (current ADR number preserved).
  - The four other tools proposed alongside this one in the same session
    (`tool002_generate_workitem_scaffold`, `tool003_check_workitem_traceability`,
    `tool004_manage_workitem_stage_transitions`, and the pending `tool006` Known
    Deviation/Known Issue sync check) — tracked as separate issues, not touched here.
- **Dependencies**: N/A: none (per Issue's Dependencies field — this Plan does not
  depend on any other issue, plan, or external work, and nothing else is recorded as
  depending on it).

## Background
This session renamed `docs/adr/ADR-004-*.md` twice (Evidence: Explicit in issue — this
is a description of prior session activity, not an independently checkable repository
claim), each time manually finding and fixing referencing files via `grep -rl` followed
by individual `Edit`/`sed` calls, including updating link text that duplicated the
document's old title. The same manual sequence was used for the ADR-011/ADR-013
deletions and ADR-003/ADR-008 consolidation earlier in the same session.
`tools/TOOL_DESCRIPTIONS.md` documents a `rename_*` naming convention
(Evidence: Confirmed by repository evidence — `tools/TOOL_DESCRIPTIONS.md` line 5:
"`merge_part_files.py`/`rename_*` = 個別操作") for exactly this class of "rename and fix
up every reference" operation, applied today only to `rename_mcp_modules.py` (Python
module renames under `mcp_servers/`), not to `docs/*.md` files.

## Problem
(Evidence: Confirmed by repository evidence) `tools/rename_doc.py` does not exist

## Reason for change
A dedicated tool removes the repetitive, error-prone grep-then-hand-edit cycle for doc
renames and reduces the risk of missing a reference — which would otherwise surface
later as a broken link caught only by `tools/check_docs_structure.py`, or not caught at
all if the stale reference is plain prose rather than a Markdown link.

## Implementation intent
Add `tools/rename_doc.py <old-path> <new-path>` with three responsibilities, run in
this order: (1) `git mv <old-path> <new-path>`; (2) scan `docs/` (including
`docs/adr/`) for Markdown links (`[text](path)`) whose path resolves to `old-path`
(accounting for both the bare-filename convention observed in
`docs/adr/ADR-004-environment-failure-handling-policy.md`,
`docs/adr/ADR-005-rag-source-derived-index-relationships.md`, and
`docs/adr/ADR-009-rag-ft5-text-separation.md` — e.g. `[RAG Data Model]
(03_rag_04_01_dto-models_data.md)` with no `docs/` or `../` prefix — and the `../`-prefixed
convention observed in `docs/adr/ADR-012-git-mcp-server-side-write-enforcement.md`,
e.g. `[MCP Server Catalog: git-mcp](../04_mcp_04_05_git.md)`; confirmed by repository
evidence that this repository is not consistent on this point, per Issue's AI
Implementation Instruction) and rewrite only the path portion, preserving each file's
existing prefix style; (3) when `--old-title`/`--new-title` are both supplied, also
rewrite link text adjacent to a rewritten link that duplicates the old title; (4)
report every non-link plain-prose mention of the old filename found during the scan,
without modifying it. Default to `--dry-run` (reports planned changes without writing);
require an explicit `--apply` flag to write, per `fix_docstring_paths.py` and
`fix_docs_section_marks.py`'s existing convention in this `tools/` directory
(Evidence: Confirmed by repository evidence — both files' module docstrings state this
`--dry-run`-default / `--apply`-to-write behavior).

- Task-size classification (`skills/issue-to-plan/SKILL.md` Routing): **Path A (Small
  Task)** — affects 3 files (`tools/rename_doc.py`, `tools/TOOL_DESCRIPTIONS.md`,
  `tests/tools/test_rename_doc.py`), no public/runtime-facing interface change (a
  dev-only CLI script, not part of the running agent/MCP/RAG services), no database
  schema change. Consistent with this session's precedent for new `tools/` scripts of
  the same shape (`plans/20260901-105731_plan.md` for `tool002`,
  `plans/20260901-110301_plan.md` for `tool003`, both classified Path A for ≤3-file
  tool additions with the identical script+`TOOL_DESCRIPTIONS.md`+test-file structure).
  Per Routing, this skips architecture/dependency/historical/operational analysis; the
  validation-quality baseline below is still established.
- Scope-restriction enforcement (REQ-006): the tool must resolve and validate that both
  the `git mv` target and every rewrite candidate lie under `docs/` before writing,
  rather than trusting caller-supplied paths — this is the concrete mechanism behind
  the Issue's Constraint "do not modify files outside `docs/`".
- Link-path rewrite preserves per-file style (REQ-002): rather than normalizing every
  link to one canonical relative-path form, the rewriter computes the new path using
  the same prefix convention (`../` or bare) the original matched link already used in
  its source file — confirmed necessary because `docs/adr/ADR-004-*.md`/`ADR-005-*.md`/
  `ADR-009-*.md` use bare filenames while `docs/adr/ADR-012-*.md` uses `../`-prefixed
  paths for structurally similar cross-references, per Reference Files above.
- Non-link-prose reporting (REQ-004) is a hard behavioral boundary, not a "best
  effort" heuristic: the scan pass, having already extracted every Markdown link on a
  line, checks whether any remaining occurrence of the old filename exists outside
  those spans; each such occurrence is collected into the report and never written,
  in both `--dry-run` and `--apply` modes.
- Title-rewrite (REQ-003) is gated by both flags being present together — supplying
  only one of `--old-title`/`--new-title` is a usage error, not a partial rewrite,
  since a title rewrite with only one side known cannot be applied safely.

## Risks
- **Risk**: The bare-filename vs. `../`-prefixed link convention split (confirmed
  across ADR-004/005/009 vs. ADR-012) is not fully characterized — a link style not
  covered by the observed samples could be mis-rewritten or silently skipped.
  **Mitigation**: fixture tests (T1) must include at least one bare-filename and one
  `../`-prefixed referencing file; the matcher must fail closed (report, do not guess)
  on any link path it cannot confidently classify into one of the two known styles.
- **Risk**: A future `docs/*.md` reference form not covered by REQ-002's `[text](path)`
  scope (e.g. reference-style `[ref]: path` definitions, per UNK-01) could go
  unrewritten, producing a broken link caught only later by
  `tools/check_docs_structure.py`. **Mitigation**: document the tool's exact matched-
  link-form scope in its `--help` text and `tools/TOOL_DESCRIPTIONS.md` entry, so a gap
  is visible rather than assumed comprehensive; extend the matcher in a follow-up issue
  if such a form is found in practice.
- **Risk**: Scope-restriction to `docs/` (REQ-006) could be bypassed by a caller
  supplying a path that only appears to be under `docs/` (e.g. via `..` traversal in
  the CLI argument). **Mitigation**: resolve both the `old-path`/`new-path` arguments
  and every candidate file to an absolute path and confirm containment under the
  repository's `docs/` directory before any write, rejecting (non-zero exit, no write)
  if containment fails.
