## Goal
- Stop `tools/stale_detector.py` from reporting `symbol_missing` for four kinds of names that can never appear in a `.py` file but are cited correctly (built-in and dunder names, lint rule codes, sibling-procedure numbers, documentation chapter ids), and for configuration keys that exist as keys in the repository's configuration files, while a genuinely stale Python symbol is still reported.

## Priority
Medium

## Scope
- **In-Scope**:
  - Recognition rules applied only at the point where a symbol is about to be reported missing (absent from the target or scoped file and from every `.py` file):
    - built-in names (`builtins` module) and names written between double underscores;
    - lint and type-checker rule codes (one to four capital letters followed by two to four digits);
    - sibling-procedure numbers (an underscore followed only by digits);
    - documentation chapter ids (a lowercase word followed by one or more underscore-digit groups) that are a prefix of an existing `docs/` file name;
    - configuration keys: a token that appears in key position (TOML or ini assignment, table header, shell assignment, JSON key, `CREATE TABLE` name) in `config/`, `conf.d/`, `schemas/`, `deploy/`, `init.d/`, `pyproject.toml`, or `tox.ini`. A mention inside a comment is not a key.
  - A positive and a negative test per class, built from the exact tokens measured, and cached lookups so runtime does not noticeably increase.
  - The `stale_detector.py` entry of `tools/TOOL_DESCRIPTIONS.md`.
- **Out-of-Scope**:
  - Searching `docs/`, `plans/`, `issues/`, `implementations/`, or comments for the existence of a name (they keep the names of removed code and would hide genuine staleness).
  - Names a procedure creates (the `(new)` marker, stale001) and new target files (stale002, done).
  - Widening which line-leading imports are checked (stale001 UNK-02), a reusable measurement tool, a warning-level verdict, and a note in `templates/implementation-procedure.md` (authors need take no action; see `UNK-02`).
  - The abort-on-any-mismatch policy, archived procedures under `implementations/done/`, and the `.claude/worktrees/` copy of the tool.

## Background
- `skills/code-implementation/workflow.md` Step 3 aborts a procedure on any `tools/stale_detector.py` mismatch and forbids correcting the procedure and continuing.
- `_check_symbol_refs` in `tools/stale_detector.py` checks every backticked, identifier-shaped token with a symbol shape (underscore-prefixed, containing a capital letter, or containing an underscore) against the target or scoped file, then against every `.py` file through `_symbol_present_somewhere`; a token absent from all of them is reported `symbol_missing`.
- stale001 (`plans/done/20261012-132739_plan.md`) and stale002 (`plans/done/20261012-173651_plan.md`) are implemented and pushed; they handled prose imports, names a procedure creates, and new target files, and left `UNK-03` (other false-positive classes) open.
- Issue `issues/done/20261012-172959_stale003_stop-flagging-non-python-names-as-missing.md` records the five classes. Re-measurement for this Plan corrected its figures for two of them (see Problem).

## Problem
Re-measured on the current repository over 6060 archived procedures (`implementations/done/*.md`): every backticked token with the detector's identifier shape that appears in no tracked `.py` file, classified by why. Only classes independent of repository history are counted (a token removed later is genuinely stale and cannot be told apart in an archived procedure).
- **Built-in and dunder names (confirmed)**: 6 tokens in 15 procedures (`DeprecationWarning`, `MemoryError`, `StopIteration`, `__slots__`, `__init_subclass__`, `__subclasscheck__`). `LookupError` was reported in practice while no `.py` used it and passes today only because `scripts/agent/startup_prompt_setup.py` names it, so these names pass or fail by accident.
- **Rule codes (confirmed)**: 3 tokens in 7 procedures (`RUF100`, `F841`, `I001`).
- **Sibling-procedure numbers (confirmed)**: 9 tokens (`_01` to `_10`) in 20 procedures; `_02` was reported in practice.
- **Documentation chapter ids (corrected)**: the Issue states they are prefixes of existing `docs/` file names. Only 43 of the 58 measured tokens are (for example `agent_04` for `docs/23_agent/agent_04_01_...md`, `governance_04`), in 55 procedures. The other 15 (for example `agent_90`, `agent_17`, `shared_05`, `user_1`) match no file name and no text in `docs/` today: they cite chapters that were renamed or removed, so they are genuinely stale and keep being reported.
- **Configuration keys (corrected, the largest correction)**: the Issue counted 27 tokens in 111 procedures, using a word-anywhere search of the configuration directories. Of those, only 7 tokens in 11 procedures appear in key position (`asyncio_mode` in `pyproject.toml`; `BING_API_KEY` and `BRAVE_API_KEY` in `conf.d/`; `SOURCE_SHA256`, `DEPLOYED_SHA256`, `DEPLOY_SCRIPTS`, `MISSING_TABLES` in `deploy/` scripts). The other 20 tokens (102 procedures) appear only in comments or values: for example `healthcheck_mode` and `HealthcheckMode` in `config/agent.toml` comments that say the setting was removed, `concurrency_limit`, `enable_refresh`, `embedding_model`, `vector_table` in a `config/mdq_mcp_server.toml` comment that says they have moved, and `tool_results`, which the Issue called a table created in `deploy/init_db.sh` but which appears only in an expected-tables comment there and in no schema. Those are genuinely stale or unverifiable and must keep being reported; a word-anywhere search would hide them, including Python names mentioned in comments such as `_validate_artifact`, `get_document`, `sqlite_helper`, and `rag_llm`.
- **Union**: 108 of 6060 procedures (1.8%) cite at least one name of the corrected five classes, against 215 (3.6%) in the Issue.
- **Excluded (confirmed)**: `line_out_of_bounds` findings concern files that were split or shortened after implementation (genuine staleness); the large remaining group of absent tokens (about 1690 procedures) is dominated by created names (the `(new)` marker) and removed names.
- Evidence classes: the rule shapes are `Explicit in code` (the shape filter in `_check_symbol_refs`); the counts are `Measured`.

## Reason for change
- Each false abort costs a person an exception decision for a correct procedure; at 1.8% of procedures the gate teaches authors to avoid citing rule codes, built-ins, and doc ids, or to bypass it.
- Each rule is deterministic and independent of repository history, and each is narrow enough that it cannot hide a stale Python symbol.

## Implementation intent
- Narrow and additive: a token is exempted only after it is already known to be absent from the target, the scoped file, and every `.py` file, so no existing verdict changes except where one of the five classes was the reason for a `symbol_missing`.
- One private predicate, `_is_non_python_name`, called at the report point of `_check_symbol_refs`, so that function gains one decision point at most. The predicate holds the rules as small, separately testable functions or constants.
- Documentation ids are matched by file-name prefix, not by a broad pattern. Configuration keys are matched by key position, not by word occurrence. Comments never count.
- Lookups that read the file system (the `docs/` file names and the configuration keys) are built lazily, once per run, and cached next to the existing symbol-presence cache.
- Keep the detector regex-based and dependency-free.

## Requirements
- `REQ-001`: A built-in name (including `LookupError` and `DeprecationWarning`), a dunder name, a rule code, and a sibling-procedure number are not reported `symbol_missing`.
- `REQ-002`: A documentation chapter id that is a prefix of an existing `docs/` file name is not reported; a similar token that matches no file name is still reported.
- `REQ-003`: A token that appears in key position in the listed configuration locations is not reported; the same token appearing only in a comment there, or absent from them and from every `.py`, is still reported.
- `REQ-004`: Each class has a positive and a negative test built from the measured tokens, and a genuinely stale Python symbol (a snake_case, CamelCase, or underscore-prefixed name absent from every `.py` and from the configuration keys) is still reported. The 82 existing detector tests pass unchanged.
- `REQ-005`: The `stale_detector.py` entry of `tools/TOOL_DESCRIPTIONS.md` lists what is recognized.
- `REQ-006`: Re-running the measurement shows no token of the five classes among the reported `symbol_missing` findings, and detector verdicts on a sample of archived procedures change only where such a token was the reason.

## Assumptions
- A token that is absent from the target, the scoped file, and every `.py` file, and is a built-in name, a dunder name, a rule-code shape, or a sibling number, is never a Python symbol the procedure expects to find in code; the shapes are fixed (one to four capital letters then two to four digits; an underscore then digits only).
- The `docs/` tree keeps chapter ids as the leading part of file names (verified for the 43 matched ids); an id is accepted only when a file name starts with the id followed by an underscore or a dot.
- Key position can be recognized with line-based regular expressions for the listed formats (TOML and ini assignments and table headers, shell assignments, JSON keys, `CREATE TABLE`) without a parser; a value inside a string, an array, or a comment is not a key.
- Recognizing a configuration key does not imply the key is still honored by code; the rule only means the name exists as a key in the repository, which is the same level of evidence as presence in a `.py` file.
- Reading the small configuration files once per run does not noticeably slow the detector (the five locations total under 250 KB).

## Design
- Path A (3 target files, no public interface change, no schema change): direct verification only. `tools/stale_detector.py` imports only the standard library. The detector is called by the `code-implementation` workflow text and its tests only; no hook or CI job runs it.
- Validation quality baseline for `tools/stale_detector.py`: radon grade C for `_check_symbol_refs` (17), B for `from_procedure` (9) and `_check_line_refs` (10); vulture and bandit report nothing; 82 detector tests pass before any change.
- Hook point: in `_check_symbol_refs`, at the existing `if not _symbol_present_somewhere(...)` branch, call `_is_non_python_name(sym, source_dir, caches)` before `add_mismatch`. A name present in the target, the scoped file, or any `.py` never reaches it, so no existing verdict changes for found names.
- `_is_non_python_name` order (cheapest first, no I/O until needed): built-in or dunder; rule-code shape; sibling-number shape; documentation id (shape check first, then the lazily built set of `docs/` file names); configuration key (lazily built set of keys). Each rule is a small function or compiled pattern so it can be tested alone.
- Configuration keys: one cached set built from the listed locations by reading each file once and, line by line, skipping comment lines and extracting keys with a few anchored patterns (assignment at line start, table header, JSON key, `CREATE TABLE` name). Files that cannot be decoded are skipped. The sets live in a small cache object passed alongside the existing symbol-presence cache, created per `_check_symbol_refs` call, so a run reads each location at most once.
- Mismatch type and message stay `symbol_missing`; no schema change.

## Risks
- **Risk**: A rule hides a genuinely stale Python symbol (for example a removed class named like a rule code) → **Mitigation**: rules run only after the name is absent from every `.py`; shapes are fixed and narrow; each class has a negative test; documentation and comments are never searched.
- **Risk**: A comment-only configuration mention is accepted as a key (the Issue's word-anywhere rule would have hidden `healthcheck_mode`, `tool_results`, and Python names in comments) → **Mitigation**: comment lines are skipped and only key positions count; tests assert that a comment-only mention is still reported.
- **Risk**: Key extraction misses a format or accepts a value as a key → **Mitigation**: limited to the formats present in the five locations; tests cover each; a miss only leaves today's behavior (reported), not a hidden stale name.
- **Risk**: Runtime grows because the detector reads configuration and `docs/` listings per procedure → **Mitigation**: lazy construction on first need, cached per call; measured against the current per-procedure time.
- **Risk**: The figures drift or are overstated again → **Mitigation**: acceptance re-runs the measurement (`AC-7`); the Issue's overstated counts are corrected here in Problem.
