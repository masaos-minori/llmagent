# Plan: Complete Evidence Block Standardization, Needs-Confirmation Re-scan, and Known-Issues Template Migration

## Goal

Extend the existing governance scaffolding (evidence labels, common Known-Issues template,
Needs-Confirmation inventory) without redefining it: add a generic evidence-block sub-template
usable by all 7 evidence labels, register every currently active/unregistered "Needs
Confirmation"/"要確認"/"未確認" marker in `docs/` into the NC inventory, and bring the five
area Known-Issues documents (Agent, MCP, RAG, EventBus, Shared/DB) into actual conformance
with the 17-field common template or an explicitly documented, intentional deviation.

## Scope

**In scope:**
- Add a "Standard Evidence Block" section to `docs/00_governance_03_evidence-labels.md`
  (reusable field set + one worked example per of the 7 evidence labels).
- Re-run the NC extraction process against the current `docs/` tree and add new `NC-###`
  entries (continuing from `NC-017`) to `docs/00_governance_07_needs-confirmation-inventory.md`
  for every active, unregistered marker, including the 8 locations named in the requirement.
- Reformat `docs/90_shared_90_inconsistencies_and_known_issues.md`'s `SHARED-001` into
  discrete 17-field format (ID preserved).
- Add/rewrite the migration note in `docs/03_rag_90_inconsistencies_and_known_issues.md` so
  it explicitly declares source/destination-format template compliance (see Unknowns —
  the existing "Migration Note" heading there is a different kind of note and must not be
  mistaken for the format-compliance note required here).
- Convert `docs/06_eventbus_90_inconsistencies_and_known_issues.md`'s section/table entries
  (EVENTBUS-001..007) into individual 17-field entries, preserving IDs and the "保留中"/
  "スキーマと実装の差異" content (as `Status: deferred` or equivalent — not dropped).
- For `docs/05_agent_90_inconsistencies_and_known_issues.md`, decide and document explicitly
  whether the 5-tier scheme migrates to the common template or remains an intentional,
  documented exception.
- Confirm `docs/04_mcp_90_inconsistencies_and_known_issues.md` needs no structural change
  (reference example) during review.
- Add back-references from the 8 confirmed source-marker locations to their new NC-### IDs,
  where the source document is itself in scope for this requirement; otherwise note the
  deferred link in the inventory entry.

**Out of scope:**
- Resolving/closing any existing Known Issue or NC item, or altering their substance.
- Modifying anything outside `docs/` and `requires/` (no source code, no `scripts/`).
- Re-defining the evidence-label taxonomy, the 17-field template, or the NC inventory's
  15-field format — only extending/applying them.
- Acting on the `decisions/20260819_*.md` files' "Follow-up Actions" (e.g., updating
  `rag_pipeline_models.py` defaults) — those are implementation-code changes for a
  different workflow cycle, not this documentation-only plan.

## Design

1. **Standard Evidence Block** (`00_governance_03_evidence-labels.md`): insert a new
   `## Standard Evidence Block` section after the existing "Needs Confirmation Required
   Fields" section, defining fields: Evidence label, Source module or document, Symbol or
   section, Test identifier, Verification date, Notes. Follow with 7 subsections (one per
   label: Explicit in code, Strongly implied by code, Documentation only, Needs
   confirmation, Deprecated, Verified by test, Operationally observed), each showing a
   filled-in example using a real symbol/doc reference already present in the repo (e.g.,
   reuse the `/reload` and `PREMATURE_EOF` examples already in the document where they fit
   a label, to avoid fabricating new unverified claims).
2. **NC inventory re-scan** (`00_governance_07_needs-confirmation-inventory.md`): for each
   of the 8 confirmed marker locations, add one `NC-###` entry (starting `NC-018`) with all
   15 fields (ID, Source File, Section, Line Number, Question, Evidence, Impact, Required
   Action, Status=open, Assigned To=Unassigned, Last Reviewed=today, Priority, Related NC,
   Resolution Target, Blocking). Use `Related NC` to link the two `90_shared_04_03...`
   entries if investigation confirms they share a root cause (hardware-dependent thresholds).
3. **Back-references**: for each of the 8 source documents (all are within `docs/`, hence
   in scope per instruction #2's "if the source document itself is in scope for this
   requirement"), append the assigned `NC-###` ID inline next to the existing marker text
   (e.g., `(Needs Confirmation: see NC-018)`), without altering the substance of the
   surrounding claim.
4. **SHARED-001 rewrite**: convert the existing single-paragraph entry into the 17 discrete
   fields per the template, preserving the ID and all decision content (Status: open,
   Severity: High, Type: implementation-bug, the DatabaseError-catching recommendation,
   etc.) — no information may be dropped, only restructured.
5. **RAG migration note**: add a new subsection (e.g., `## Template Migration Note`,
   distinct from the existing 2026-08-06 "Migration Note") stating: migration date, source
   format (already-conformant ad hoc bullet fields), destination format (common template,
   17 fields), and a field-by-field confirmation that RAG-003/RAG-004 satisfy all 17 fields
   (they currently do, per Step A verification — no field reformatting needed, only the
   declarative note is missing).
6. **EventBus conversion**: convert EVENTBUS-001 through EVENTBUS-007 into 17-field entries.
   Preserve the Japanese section groupings as informative subheadings if desired, but each
   ID becomes its own entry block. EVENTBUS-005/006/007 (currently a single combined
   "保留中" mention for three IDs) get separated into three individual entries, each
   `Status: deferred`, `Type: design-gap` (or `operational-gap`), preserving the "Agent
   統合は意図的に未実装" rationale. The "スキーマと実装の差異" section's 4 field names
   (`acked_at`, `delivery_failure_count`, `dlq_requeue_count`, `dlq_at`) are documentation
   only (all in active use, no discrepancy) — represent as either a closing note or a single
   informational entry, not a Known Issue, since no inconsistency exists there.
7. **Agent doc decision**: record explicitly in
   `docs/05_agent_90_inconsistencies_and_known_issues.md` that the 5-tier scheme is kept as
   an intentional, documented area-specific exception (rationale: it separates "confirmed
   design decision" from "active defect" at a granularity the common template's Status/Type
   fields do not directly express, and the document currently has zero open entries to
   migrate) — add this rationale as prose in the existing "Design Intent"/"Key Constraints"
   section rather than restructuring the whole document.
8. **MCP doc**: no content change; implementer confirms during review that MCP-001/MCP-002
   already satisfy all 17 fields (verified true in this plan's Step A read).

## Risks

- **Risk**: Adding back-references inside area documents (e.g., `docs/04_mcp_04_05_git.md`)
  could be read as "modifying documentation" beyond the NC inventory itself, creating scope
  ambiguity with instruction #2's "only if the source document itself is in scope."
  (Likelihood: low — all 8 locations are named explicitly in the requirement's Target
  files list as in-scope.) → **Mitigation**: keep each back-reference a minimal, non-
  substantive inline addition (e.g., append `(see NC-018)`) that does not alter the
  underlying claim, consistent with instruction #2 and the "no substance altered" acceptance
  criterion.
- **Risk**: Misreading `docs/03_rag_90_inconsistencies_and_known_issues.md`'s existing
  "Migration Note" as already satisfying the acceptance criterion, causing the required
  format-compliance note to be skipped. (Likelihood: medium — confirmed as a real trap
  during this plan's verification.) → **Mitigation**: explicitly flagged in Unknowns/
  Assumptions above; implementation step 3 requires adding a distinctly-labeled note.
- **Risk**: Treating `decisions/20260819_git_mcp_write_guard_asymmetry.md` or
  `decisions/20260819_workflow_approval_gate_default_state.md` as resolving the
  corresponding NC candidates, silently closing them as "already decided" rather than
  registering them as open. (Likelihood: medium — same-day decision files with closely
  related titles are an easy false match.) → **Mitigation**: documented in Assumptions
  with the specific mechanism-level distinction; NC-### entries for these two markers must
  be drafted from the actual doc question, `Status: open`.
- **Risk**: EventBus conversion accidentally drops the "保留中"/"スキーマと実装の差異"
  narrative framing that explains *why* EVENTBUS-005/006/007 are deferred and why the 4
  schema fields are not an inconsistency. (Likelihood: low.) → **Mitigation**: implementation
  step explicitly requires preserving this content in the `Recommended Action`/`Resolution
  Notes`/`Current Description` fields rather than deleting the prose.
- **Risk**: Requirement's acceptance criterion "All currently active markers... have a
  corresponding entry" could expand scope if a fresh `grep` at implementation time finds
  markers beyond the 8 named ones (docs change over time). (Likelihood: low-medium.)
  → **Mitigation**: implementation step 2 explicitly re-runs the grep scan before finalizing
  the NC-### entry list, rather than assuming the 8 named locations are exhaustive.
