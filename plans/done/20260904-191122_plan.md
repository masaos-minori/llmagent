## Goal
- Make `RepositoryState.verify_preconditions()` actually evaluate `dry_run` and
  `allow_detached_head` instead of silently ignoring both, so configuration,
  documentation, and runtime behavior agree.

## Priority
High

## Scope
- **In-Scope**: adding `dry_run`/`allow_detached_head` parameters to
  `verify_preconditions()`; threading both values from the live `POST /v1/call_tool`
  path into Stage 5; defining detached-HEAD permission scope across
  checkout/pull/push; correcting the precondition method's docstring/error text;
  adding a documented `allow_detached_head` example to `config/git_mcp_server.toml`.
- **Out-of-Scope**: GIT-001's already-resolved dirty-worktree/detached-HEAD scenario
  (do not re-open); protected-branch/ref authorization content (`gitauth`); the
  write-protection pipeline's stage ordering/Stage 3/Stage 7 work (`gitpipeline`) —
  this Plan touches the same `verify_preconditions()`/`run()` area and coordinates
  with, not duplicates, that Plan's changes (see Design).

## Background
`issues/done/20260823_git_dirty_worktree_detached_head_issue.md` (GIT-001) resolved
the dirty-worktree/detached-HEAD *check itself* existing. This Plan's Step 3
investigation re-confirmed (per the issue's own instruction) that
`RepositoryState.verify_preconditions(self, command: str)`
(`scripts/mcp_servers/git/repository_state.py:139-155`) still takes only a `command:
str` parameter — no `dry_run`, no `allow_detached_head` — despite its own docstring
stating "dirty-worktree and detached-HEAD guards apply only to write commands when
dry_run is False" and its own error message telling the caller to "set
allow_detached_head=true in git_mcp_server.toml". Neither claim is implemented: the
method unconditionally rejects dirty worktree and detached HEAD regardless of
`dry_run`, and never reads `allow_detached_head` at all. `config/git_mcp_server.toml`
does not even contain an `allow_detached_head` line (confirmed by direct read) — the
setting exists only as a `GitConfig` field default (`False`) and is threaded to
`format_checkout()`'s *postcondition* check (`git_server.py:243`,
`format_output.py:123,142`), never to this *precondition* check.

## Problem
Because `verify_preconditions()` cannot observe `dry_run`, a dry-run preview request
against a dirty or detached-HEAD repository is rejected identically to a real write
request — defeating dry-run's purpose as a non-mutating preview. Because it cannot
observe `allow_detached_head`, setting `allow_detached_head=true` has no effect on
Stage 5: the operation is rejected before Stage 6 ever runs, so
`format_checkout()`'s already-wired `allow_detached_head` parameter (used only in its
own postcondition check) never gets a chance to matter — checkout can never proceed
past Stage 5 while detached, regardless of configuration.

## Reason for Change
GIT-001 addressed the dirty-worktree/detached-HEAD scenario existing at all; this
issue closes the structural gap GIT-001 did not scope — the precondition method's
inability to observe the two inputs (`dry_run`, `allow_detached_head`) its own
docstring and error message already claim to honor.

## Implementation intent
Add `dry_run: bool` and `allow_detached_head: bool` parameters to
`verify_preconditions()`. When `dry_run=True`, skip the dirty-worktree and
detached-HEAD checks (matching the existing docstring's claim) while keeping
authorization active (Stage 3, once `gitauth`'s fix lands — this Plan does not modify
Stage 3 itself). When `dry_run=False`, evaluate `allow_detached_head`: permit detached
HEAD only when explicitly configured, applied uniformly across
checkout/pull/push consistent with `GitService`'s existing (dead-code but
representative) convention (`git_service.py:308,338,366`, which applies the same
`is_detached_head and not self._allow_detached_head` check to all three). Thread both
values from `git_server.py`'s live `call_tool` path (`req.dry_run`, module-level
`_cfg.allow_detached_head`) into `WriteProtectionPipeline.run()` and on to Stage 5.

## Design
This Plan, `gitauth`, and `gitpipeline` all touch
`scripts/mcp_servers/git/repository_state.py`'s `WriteProtectionPipeline.run()`/
`RepositoryState` — three Plans filed alongside the same originating issue set,
coordinated by each Plan's own Dependencies section rather than merged into one. This
Plan's own change is scoped narrowly to Stage 5 (`verify_preconditions()`'s
signature and body) and the values threaded into it; it does not touch Stage 3
(`gitauth`'s scope), Stage 7 or `record_stage()` (`gitpipeline`'s scope). An
implementer landing all three should expect three coordinated diffs to
`repository_state.py`/`git_server.py` — this Plan's Risks section flags the
coordination requirement explicitly rather than assuming a single-Plan
implementation order.

`allow_detached_head`'s scope (UNK-01) is resolved by following `GitService`'s
existing, if dead-code, convention of applying the same check uniformly to
checkout/pull/push — chosen for consistency with the one prior implementation of this
exact policy in this codebase, absent an explicit narrower instruction in the issue
text. This is a genuine judgment call, recorded as such rather than silently decided.

Dry-run's non-mutation guarantee (REQ-009) is not re-implemented by this Plan —
`format_checkout()`/`format_pull()`/`format_push()` already early-return before any
mutating Git call when `req.dry_run` is true (confirmed by direct read in an earlier
cycle this session). This Plan's contribution is narrower: ensuring the *precondition
stage* does not incorrectly reject a dry-run preview before it ever reaches those
already-safe branches.

## Risks
- **Risk**: This Plan, `gitauth`, and `gitpipeline` all modify the same
  `WriteProtectionPipeline.run()` method and `RepositoryState` class — implementing
  them independently without coordination could produce merge conflicts or an
  incomplete combination of the three fixes → **Mitigation**: each Plan's Design
  section scopes its own change narrowly (this Plan: Stage 5 only) and names the
  other two Plans explicitly; an implementer should review all three Implementation
  Target Files tables together before editing `repository_state.py`.
- **Risk**: Applying `allow_detached_head` uniformly to pull/push (REQ-004, UNK-01)
  could be the wrong scope if a maintainer intended checkout-only → **Mitigation**:
  documented as a judgment call with its rationale (following `GitService`'s existing
  convention); easy to narrow later without re-touching the dry-run logic.
- **Risk**: Skipping preconditions entirely during dry-run could allow a dry-run
  request to reach Stage 6 in a state real execution never would (e.g. previewing a
  push while detached) → **Mitigation**: dry-run branches in `format_output.py`
  already perform read-only operations (`git fetch --dry-run`, no `git push`/`git
  checkout` mutation) regardless of repository state, so this is a preview-accuracy
  question, not a safety one — the operation still cannot mutate anything.
