## Goal
- Make two operator-visibility signals in the agent startup reporting path accurate: render a skipped RAG consistency check distinctly from a warning-bearing check, and stop labeling a user-initiated startup shutdown (`StartupInterrupted`) as "Startup failed".

## Priority
Low

## Scope
- **In-Scope**:
  - Add the RAG `SKIPPED` count to the RAG consistency line in `ReadinessReporter.report_readiness()` so a skipped check is distinguishable from a warning-bearing check.
  - Distinguish `StartupInterrupted` from other startup failures in `AgentREPL.run()` when composing the user-facing message, so an intentional shutdown is not labeled "Startup failed".
  - Preserve the `except Exception` re-raise and the outer `finally` resource-cleanup in `repl.py` unchanged.
  - Add regression tests for both changes.
- **Out-of-Scope**:
  - Any change to the validation pipeline itself or the RAG classification behavior (see `issues/20261016-133921_startup001_...`).
  - Changing what is reported for the other three checks (security audit, service readiness, tool discovery) or their counts.
  - Refactoring the readiness summary layout beyond adding the skipped indicator.
  - Changing startup control flow, rollback, or signal-handling/shutdown semantics.

## Background
The startup pipeline is the fail-fast gate for service health. `ReadinessReporter.report_readiness()` prints a per-service summary. Readiness, tool discovery, and (partly) security show OK/FAIL with fatal/warning/skipped counts, but the RAG line omits the skipped count. When the RAG check is skipped (timeout or any exception, see `StartupValidationPipeline.check_services()`), `ok` is false, so the line renders as "WARN" with zero fatal and zero warnings and no indication that the check did not actually run. Separately, `AgentREPL.run()` wraps `StartupOrchestrator.run()` and, on any exception, writes `f"Startup failed: {e}"`. `StartupInterrupted` (raised when a SIGINT/SIGTERM shutdown request fires during startup, `class StartupInterrupted(RuntimeError)` in `startup.py`) is a normal, expected exit, not a failure, but it flows through the same `except Exception` branch and is reported identically.

## Problem
An operator scanning the startup banner cannot tell whether "RAG consistency: WARN" means the check found problems or was never completed. And a clean user-initiated shutdown during startup is displayed as a failure, which is misleading in logs and interactive sessions.

## Reason for change
These are low-risk reporting-accuracy improvements. They cost little to fix and remove two sources of operator confusion during startup triage. Neither changes startup behavior or the fail-fast security gate.

## Implementation intent
- In `ReadinessReporter.report_readiness()`, include the RAG skipped count so a skipped RAG check is not rendered as a bare "WARN". Reuse the existing `{count} skipped` count-column pattern used by the readiness and tool-discovery lines for consistency.
- In `AgentREPL.run()`, branch on `StartupInterrupted` before the generic `except Exception` handler and emit a shutdown/interrupt-appropriate (non-fatal) message, so an intentional shutdown is not labeled "Startup failed". Preserve the re-raise and the `finally` resource cleanup.

## Requirements
- `REQ-001`: Add the RAG `SKIPPED` count to the RAG consistency line in `ReadinessReporter.report_readiness()` so a skipped check is distinguishable from a warning-bearing check.
