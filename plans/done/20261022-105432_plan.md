# Answer Every Declared Tool Call Id, Whether the Round Completed or Not

`_run_group_calls()`; no such break exists at HEAD (`scripts/agent/tool_runner.py:63-74` contains no

## Goal

Make one tool round answer every `tool_call` id it declared. Today `LLMTurnRunner.run()` appends and
persists the assistant message (`scripts/agent/llm_turn_runner.py:107-112`), and then
`execute_all_tool_calls()` produces tool rows only from the results it managed to collect
(`scripts/agent/tool_runner.py:387-391`): if any call raises, the whole round's results — including
calls that already ran and already applied side effects — are discarded, and the persisted assistant
`tool_calls` block stands with zero answers. That block is sent to the provider unchanged on the next
turn (`llm_turn_runner.py:292-296`, `scripts/shared/llm_sse_stream.py:206`).

This Plan changes two things, both inside the round:

1. The round records each result at the point the result exists, in a map it owns and keys by
   `tool_call_id`, and at the end of the round — normal or exceptional — it synthesizes one tool
   result for every declared id that map does not hold, and writes all of them through the existing
   single `save_many()` call.
2. A guard trip that can be observed from results already in that map stops the remaining calls of a
   sequential group and the remaining batches of the plan, and those skipped ids are answered by the
   same synthesis. This is the mid-round half that `plans/20261022-092413_plan.md:372-381` defers to
   `tool002`.

Nothing above the round changes. The assistant message stays persisted, exceptions keep propagating,
the turn loop's two guard check sites stay where they are, and `TurnResult` is unchanged.

## Priority

- Severity: High. The defect is stored state, not a transient error: it survives the turn that caused
  it, and every later request for that session carries it.
- User-visible impact: Yes. A tool failure that today prints an error and continues turns the session
  into one whose next request contains an unanswered `tool_calls` block. Whether the provider rejects
  it or answers as if the tool returned nothing is not known at HEAD (UNK-01); what is known is that
  nothing in this repository repairs it (`scripts/agent/context.py:124-151` adds messages only, and
  `scripts/agent/history.py:147-154` counts serialized `tool_calls` but never removes a dangling one).
- blast-radius: Medium. One function's internal structure (`execute_all_tool_calls` and the two
  engines it calls), one new pure module, and one extracted predicate in `ToolLoopGuard`. No public
  signature changes, no config key changes, no storage schema change.
- Blocking dependencies: **implementation order only, for Phase 2.** Phase 2 observes the trip through
  the guard instance `LLMTurnRunner` already owns, reached through the explicit parameter
  `plans/20261022-092413_plan.md` Phase 1 adds to `execute_all_tool_calls` and
  `execute_one_tool_call`; that plan also deletes the `getattr(ctx, "guard", None)` read
  (`scripts/agent/tool_runner.py:200-201`) this Plan would otherwise have to read. The tool001 plan
  states this order itself (`:374-379`: "Implementing this Plan first is the order the source issue's
  Dependencies section asks for"). Phase 1 needs no guard and can land independently.

## Scope

- `ToolRunner`'s round (`execute_all_tool_calls`, `scripts/agent/tool_runner.py:347-391`) owns one
  map `collected: dict[str, tuple]`, keyed by `tool_call_id`, for one invocation, and passes it to
  `_execute_with_dag()` (`:301`), `_run_plan_batches()` (`:274`), and `_run_group_calls()` (`:63`).
- Each result is recorded into that map at the point it exists, in both group shapes: the sequential
  loop (`:69-73`) and the gathered call site (`:74`), by a per-call wrapper that records before it
  returns. Recording at production is the position the tool001 plan chose for the same reason
  (`plans/20261022-092413_plan.md:26-31`): it is the only position that covers both group shapes and
  both execution paths.
- The declared id set is read from the `tool_calls` argument before preparation or execution, so a
  failure in preparation, approval, planning, or execution cannot move it.
- A completion step runs once per round, on normal completion and on an escaping exception
  alike: `missing = declared ids − collected ids − already-answered ids`, one synthesized tool result
  per missing id, then the existing `ctx.conv.extend_messages()` + `ctx.session.save_many()` path
  (`:389-391`). The synthesized rows do not pass through `_update_stats_for_result()` (`:225-237`) or
  `record_tool_result()`.
- Mid-round observation: the count scan inside `check_empty_result_repeat()`
  (`scripts/agent/tool_loop_guard.py:169-189`) is extracted into a non-recording predicate; the
  sequential group consults it after each recorded result, `_run_plan_batches()` consults it after
  each completed batch, and a trip ends the round's remaining work. `check_empty_result_repeat()`
  keeps its recording behavior, so the turn-level check at `llm_turn_runner.py:125` remains the one
  place that writes `guard_hint` and produces the fail `TurnResult`.
- Unchanged: the assistant persist (`llm_turn_runner.py:107-112`); the two turn-level check sites
  (`:98-105`, `:122-130`); `check_all()` and its four detectors and thresholds; the `_reject()` /
  `_PrepFailure` shapes in `scripts/agent/tool_preparation.py:37-73`; `_build_denied_messages()`
  (`tool_runner.py:412-428`); the original-order merge (`:383-385`); one `save_many()` per round.
- Out of scope: `asyncio.gather` without `return_exceptions=True` (`tool_runner.py:74`, `:291-296`) —
  `tool003`; the `KeyError` from `tc["id"]` at `:383` and `_is_empty_result()`'s non-`str` branches
  (`tool_loop_guard.py:146-154`) — `tool004`; result masking — `tool005`; whether a trip should
  change the answer text the user sees; repairing history already stored; the `persist_as_assistant`

## Problem

1. `execute_all_tool_calls()` knows the full declared set (`:349`) but produces rows only from the
   results it received (`:387` → `_collect_tool_result_msgs` iterates `results`, `:202-221`). An id
   with no result tuple is invisible to the function that could answer it.
2. Results are collected after execution, so a failure is not partial: `:375-377` must return before
   `:387` or `:391` runs. Any side effect the completed calls applied stays applied and unrecorded.
3. `asyncio.gather` without `return_exceptions=True` (`:74`, `:291-296`) raises on the first failure
   and cancels siblings, so even with a `try` around the call, the completed results of that group
   are not obtainable from the returned value.
4. Nothing downstream repairs it. `handle_llm_turn` has no `except` (`llm_turn_executor.py:89-102`);
   `run()` has no `except` around the round (`:115-120`); `_handle_llm_error()` (`:141-196`) only
   handles a failure of the LLM call itself and returns `persist_as_assistant=False`
   (`turn_result.py:29`), so it never touches this state.
5. The next turn replays the orphan: `fetch_messages` returns it in `message_id` order
   (`session_message_repo.py:219`) and `llm_sse_stream.py:206` sends it unchanged. With
   `execute` configured `retryable: true, max_attempts: 3` (`config/workflows/default.json`) the same
   turn is retried and appends a second assistant message on top of the orphan — cross-attempt
   duplication is `turn002`; this issue is pairing inside one round.
6. The failure is recorded but the history is not. `workflow_engine_adapter.py:189-198` writes the
   `turn_end` diagnostic, `scripts/agent/workflow/workflow_engine.py:236-244` records the failed
   attempt, `:129-131` marks the task failed. A diagnostic explains the stop to the operator and not
   to the model.
7. No detector reports the state. `scripts/db/session_consistency.py:27-32` counts messages whose
   *session* is missing, not `tool_calls` without results.
8. No test asserts the pairing. `tests/agent/test_llm_turn_runner.py` replaces
   `agent.llm_turn_runner.execute_all_tool_calls` with a mock in every tool-round test (`:397`,
   `:436`, `:485`, `:518`, `:583`); `tests/agent/test_agent_repl_tool_exec.py:377` stubs
   `ctx.session.save_many = MagicMock()`; `tests/agent/test_tool_runner.py` asserts that the
   exceptions are raised (`TestExecutorUnavailableGuard`, `:1155-1166`) and never what history or the
   `session_messages` table contain afterwards.

## Reason for Change

- The invariant is already the design of every other path in the same function: preparation failures
  become answered result tuples (`tool_preparation.py:51-73`), denied calls become tool messages
  (`tool_runner.py:412-428`), and a single call is answered by `execute_one_tool_call` (`:147-184`).
  Only the failure path leaves ids unanswered, and only because it returns early.
- The issue's own decision is recorded and this Plan implements it: synthesize, do not delete
  (`issues/…tool002…md:94-99`) — deleting the assistant message erases what the model asked for,
  cannot undo the side effects that already happened, and collides with the per-attempt retry
  semantics `turn002` owns.
- `docs/23_agent/agent_03_02_turn-processing-flow-llm-tool-loop.md:78` currently states "The original
  unexecuted assistant message is not persisted." That is true only of the guard fallback at
  `llm_turn_runner.py:242`-`_finalize_after_guard`, and reads as the opposite of `:107-112`. The
  tool-execution document has a `### Result Reflection in History` section
  (`docs/23_agent/agent_06_01_tool-execution-and-approval-execution.md:68-70`) that describes only
  which method appends results, and never states the guarantee.
- This is the half the tool001 plan makes possible: once a result is recorded at the point it exists
  (`plans/20261022-092413_plan.md:26-31`, `:374-381`), "which ids are still unanswered" becomes a
  question a round can answer about itself.

## Implementation Intent

| Aspect | Intent |
|---|---|
| Data owner | One round owns `collected`, keyed by `tool_call_id`, created in `execute_all_tool_calls()` and threaded to the engines. It is the round's single source of truth for "answered". |
| Public contract | `execute_all_tool_calls(ctx, tool_calls, turn, out_failed_keys)` keeps its return type `None` and raises exactly what it raises today. `_run_group_calls`, `_run_plan_batches`, `_execute_with_dag`, `_collect_tool_result_msgs` are private and change internally only. `execute_one_tool_call` keeps returning the same 6-tuple; the recording happens in the round's per-call wrapper, not inside it, so the tool001 plan's call-site migration (`plans/20261022-092413_plan.md:182-184`) is not re-opened. |
| Pairing rule | Stated by id, not adjacency: for every id the assistant message declared and that reached the round, one persisted row with `role='tool'` and that `tool_call_id` exists when the round ends. Adjacency cannot express it — the read order is `message_id` (`session_message_repo.py:219`) and the tool rows are written in a batch after the assistant row. |
| Side effects | One `save_many()` per round. No `ctx.stats` change and no `out_failed_keys` change from a synthesized row. No new `session_diagnostics` kind, no new `ctx.stats` counter, no new config key. |
| Control flow | The round's completion step never swallows an exception: it writes the missing rows, then the original exception propagates. `_finalize_after_guard`, `check_all`, `update_errors`, `check_error_limit` and both `TurnResult` shapes are untouched. |
| Configuration | No threshold or default changes. `tool_empty_result_max_repeats` keeps `<= 0` meaning disabled: with the shipped default (`scripts/agent/config_dataclasses.py:178`, key absent from `config/`) Phase 2's predicate returns "no trip" exactly as `check_empty_result_repeat` does today (`tool_loop_guard.py:172-173`). |
| Module shape | The synthesis is a new pure module. `tool_runner.py` is 15526 B and `tool_loop_guard.py` 15827 B against the 16384 B gate in `tools/check_module_size.py`, with no baseline recorded for either. |
| Rejected shapes | (a) deleting the pending assistant message — rejected by the issue and by DR-004; (b) moving the assistant write into the round's transaction — `save` and `save_many` are two commits today and merging them holds a write open across a hung MCP call (the issue's answered question, `:100-105`); (c) repairing at read time — the tool001 plan's DEFER-002; at HEAD there is no result to re-pair, so a read-side rule cannot produce one; (d) `except` clauses inside each engine — each engine would need its own synthesis and ordering, and the `KeyError` at `:383` happens outside all of them. |

## Requirements

- REQ-001: When `execute_all_tool_calls()` finishes — by returning or by raising — every declared
  `tool_call_id` that reached the round has exactly one entry in `ctx.conv.history` and exactly one
  persisted `session_messages` row with `role='tool'` and that `tool_call_id`. Source: issue AC-1 and
  Summary; Verification `:41-43`.
- REQ-002: Each executed result is recorded in `collected` at the point it exists, in the sequential
  group path and in the gathered path, so a later failure cannot discard a completed call. Source:
  Verification `:41-43`; tool001 plan `:26-31`.
- REQ-003: The declared id set is taken from the `tool_calls` argument before preparation, approval,
  planning, or execution. Source: `tool_runner.py:349`, `:369`, `:372`, `:375`, `:383`.
- REQ-004: A synthesized row states that the call was not executed, drawn from a closed two-member
  set: the round stopped by a guard observation, or the round did not complete. It is not an empty
  result and not a copy of `format_error_payload()` output. Source: issue Required Changes bullet 1
  ("marked as an error"); Constraints bullet 2 ("reuse that shape instead of inventing a second one").
- REQ-005: A synthesized row does not change `ctx.stats`, does not add to `out_failed_keys`, and does
  not call `record_tool_result()`. Source: `_update_stats_for_result` (`tool_runner.py:225-237`) feeds
  `update_errors` (`llm_turn_runner.py:122`) and `check_retry` (`tool_loop_guard.py:326-354`); a
  synthesized row would make the next round's decisions depend on calls that never ran.
- REQ-006: A trip observed mid-round ends the round's remaining work: no further call of that
  sequential group is executed, and no further batch of the plan is dispatched. Those ids are answered
  by REQ-001. Source: tool001 plan `:374-376`; issue question 8.
- REQ-007: Exactly one `guard_hint` write and one log line per trip. The mid-round observation
  records nothing; `check_empty_result_repeat()` keeps the recording at its existing site. Source:
  `tool_loop_guard.py:128-141`, `:181-:188`; `docs/23_agent/agent_03_02_turn-processing-flow-llm-tool-loop.md:80-86`;
  tool001 plan `:362-366`.
- REQ-008: Control flow is unchanged. The exception that a failing round raises today still propagates
  from `execute_all_tool_calls()`; `llm_turn_runner.py:107-112` and `:122-130` are not edited; the
  function's return type stays `None`. Source: issue AC-3 as a constraint on scope;
  `tests/agent/test_tool_runner.py:1155-1166`.
- REQ-009: Rows keep the existing original-batch order, synthesized rows included. Source:
  `tool_runner.py:383-385`; `tests/agent/test_tool_runner.py:1034` (the order contract).
- REQ-010: Existing answered paths are never synthesized twice: preparation failures
  (`tool_preparation.py:51-73`, merged at `:384`), approval denials (`:388-390`, `:412-428`), and
  results of executed calls. Source: issue Constraints bullet 2, AC-3.
- REQ-011: A declared call with no `id` is not pairable and the existing `KeyError` at `:383` is not
  duplicated, moved, or masked. Source: issue Out of Scope / Dependencies (`tool004`).
- REQ-012: Exactly one `save_many()` call per round, at the existing site. Source: `:391`.
- REQ-013: The synthesis is pure — no `agent.*`, `shared.*`, `services.*` or `workflow_engine.*`
  import — and neither modified module exceeds `tools/check_module_size.py`'s ceiling. Source:
  `skills/DESIGN.md` Shared Vocabulary.

## Design

### The round, and the one thing that changes

```
execute_all_tool_calls(ctx, tool_calls, turn, out_failed_keys)      -> None   (unchanged contract)
  declared_ids = ids in tool_calls, in order, before anything else          # REQ-003
  collected: dict[str, tuple] = {}                                          # owned by this call
  try:
      prepared, prep_failures = prepare_tool_calls(...)                     # unchanged
      approved, denied_ids   = _run_approval_gate(...)                      # unchanged
      stopped = await _execute_with_dag(ctx, approved, collected, ...)
          └ _run_plan_batches(ctx, plan, pc_by_id, collected)
                for each batch:
                    await asyncio.gather(_run_group_calls(group, serialize, ctx, collected) …)
                        sequential: for pc in group:
                                        res = await _recorded_call(ctx, pc, collected)   # REQ-002
                                        if guard_scan(): break               # REQ-006, records nothing
                        gathered:   await asyncio.gather(*(_recorded_call(ctx, pc, collected) …))
                    if guard_scan(): break                                  # batch boundary
      # normal completion: collected holds every executed call; the scan may have stopped the round
  # exceptional completion: collected still holds every call that finished first  # REQ-002
  rows, msgs = pair_round_results(declared_ids, prep_ids, denied_ids, collected, reason)   # REQ-001
  tool_msgs = await _collect_tool_result_msgs(ctx, ordered_real_results, turn, out_failed_keys)
  append msgs; extend history; tool_msgs.extend(denied_msgs); ctx.session.save_many(tool_msgs)  # REQ-012
  raise   # only when the round raised                                                             # REQ-008
```

The shape that makes both halves the same mechanism is that `collected` is written at the point a
result exists. A failure and a skipped call then become the same observable fact — a declared id that
is not in the map — and one code path answers both.

| ID | Decision | Alternatives considered | Reason | Consequence |
|---|---|---|---|---|
| DR-001 | The round owns a `collected` map keyed by `tool_call_id`, filled at the production point, and the pairing is `declared − answered`. | (a) `except` clauses inside each engine — the `KeyError` at `:383` and a `save_many` failure sit outside every engine, and three engines would each need ordering; (b) returning the missing ids to the turn loop and letting `llm_turn_runner.py:115-120` write them — the runner does not know which ids the planner executed, and the tool001 plan already rejected an `out_partial_results`-style parameter; (c) a `set` of skipped ids maintained alongside the result lists — a second source of truth that can drift from the rows actually written; (d) comparing against rows read back from the DB — a read inside the write path re-deriving state the process already holds. | `execute_all_tool_calls` is the only function that holds the declared set for a round (`:349`), and `tool_call_id` is already the key every write path uses (`:221`, `:427`, `session_message_repo.py:91-104`). | A later `tool001` mid-round decision or a `tool003` change adds a call site or a payload, not a new owner. |

## Risks

- **The synthesis can answer a call that actually ran.** If a real result exists but was not recorded
  (a path this Plan did not cover), a synthesized row replaces a real payload. Mitigated by recording at
  the production point in both group shapes (REQ-002) and by `TestCompletedResultsSurviveAFailure`;
  UNK-02 bounds the residual to the `gather`-cancellation window, which `tool003` removes.
- **A synthesized row could be read as a tool result by a later guard.** It is excluded from
  `record_tool_result()`, `_update_stats_for_result()`, and `out_failed_keys` by construction (REQ-005),
  and `TestSynthesizedRowsDoNotTouchGuardStateOrStats` asserts the three of them together.
- **`tool_runner.py` crosses the 16384 B gate while the map is threaded.** 858 B of headroom, no
  baseline recorded. Mitigated by keeping the pairing logic in a separate module (DR-003) and measuring
  at the end of Phase 1 (UNK-05). If it fails, the completion step moves into
  `scripts/agent/tool_result_pairing.py`; do not add a baseline and do not widen this Plan
  (`rules/toolchain.md`).
- **Phase 2 lands before the tool001 plan does.** Then there is no guard to consult and the mid-round
  stop has nothing to observe; a `getattr(ctx, "guard", None)` fallback would re-introduce the state the
  tool001 plan deletes. Mitigated by the stated order (Priority, DR-006) and by Phase 1 being complete
  on its own — if the order is broken, Phase 2 is deferred and Phase 1 still delivers AC-1.
- **Doc drift.** `agent_03_02:78` is corrected here; `plans/20261022-092413_plan.md` edits `:33` and
  `:110` of the same file. `tools/check_docs_consistency.py` and `tools/check_docs_content_policy.py`
  are run at Phase 3, and the two sections are disjoint.
- **Provider interpretation is unknown.** A row stating "not executed" might be treated as a real tool
  result by some providers (UNK-01). The payload names the reason explicitly; the alternative — an
  unanswered `tool_calls` block — is already known to be an invalid request shape.
- **Existing tests assert the raise, and the completion step runs before it.** If the pairing write
  itself raises (`session_message_repo.py:89-91`), the original error is replaced. Mitigated by
  keeping the pairing write in the same position as the existing `save_many` (no new failure surface
  earlier than today) and by AC-3 keeping the existing raise assertions unchanged; UNK-04 records the
  divergence this path can still leave.
