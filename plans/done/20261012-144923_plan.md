## Goal
- Make the startup routing-drift check fail visibly and predictably when the check itself breaks: an unexpected failure (any exception other than the drift's own `RuntimeError`) becomes FATAL when `routing_drift_strict` is true and a recorded WARNING when it is false, instead of a log line with an empty result, so a broken check is never reported as a clean one.

## Priority
Medium

## Scope
- **In-Scope**:
  - Stop `check_routing_drift()` in `scripts/agent/services/routing_drift.py` from swallowing unexpected exceptions; let them propagate to its caller.
  - In `StartupValidationPipeline.check_services()` (`scripts/agent/startup_validation.py`), classify an unexpected drift-check failure by `routing_drift_strict` (FATAL when strict, WARNING otherwise); treat unreadable strictness as strict; keep the `RuntimeError` to FATAL mapping.
  - Tests for the new policy at function and pipeline level.
  - Document the policy in the three places that state routing-drift severity.
- **Out-of-Scope**:
  - The safety-tier block (`# 5b`), the RAG-consistency and readiness blocks, and the drift findings themselves.
  - The `repl_health.py` backward-compatibility re-export.
  - `ADR-004` text (it does not mention drift-check crashes; INV-07 covers Safety Tier, not drift).
  - The inline policy comment's rationale beyond what is needed to state the rule.

## Background
- `StartupValidationPipeline.check_services()` block `# 5` maps `RuntimeError` to `add_fatal()` and every other exception to `add_warning()` (`scripts/agent/startup_validation.py:113-116`); block `# 5b` maps every exception to `add_fatal()` (Fail-Closed per INV-07).
- Issue `issues/20261012-124829_start003_startup-routing-drift-check-downgrades-failures-to-warnings-while-safety-tier-check-stays-fail-closed.md` asks for an explicit, consistent policy for a drift-check crash and leaves the choice open.
- Decision recorded with the user on 2026-10-12: the policy depends on `routing_drift_strict` (fatal when strict, warning when not).

## Problem
Verified against current source (`Confirmed by repository evidence`):
- **Correction to the Issue (where the fail-open is)**: the Issue says a non-`RuntimeError` raised inside `check_routing_drift()` reaches the `except Exception` in block `# 5` and becomes a warning. It does not. `check_routing_drift()` has its own `except Exception` that logs a warning and returns `[]` (`scripts/agent/services/routing_drift.py:40-42`, added in `a74d0ed82`), so the exception never leaves the function. The caller's handler in block `# 5` is reachable only for failures outside that inner `try` (the deferred import at the top of the function, or reading `ctx.cfg.tool.routing_drift_strict`).
- **Consequence**: for the realistic crashes (a malformed server config, a registry error), the pipeline records no outcome at all; the only trace is one line in `agent.log`. Startup proceeds as if the check had passed, even when `routing_drift_strict` is true, which `ProductionConfigValidator` requires in production.
- **Existing policy text**: block `# 5` already carries a comment stating the downgrade ("unexpected routing-drift check failures are downgraded to a warning rather than allowed to abort startup"). So the Issue's "without an explicit documented decision" is only partly true: the downgrade is stated, its rationale is not, and the user-facing docs say nothing about a crash of the check.
- **Documented severity today**: `routing_drift_strict` true gives FATAL, false gives WARNING (`docs/22_mcp/mcp_06_09_startup-validation-behavior-tool_definitions_strict.md`, `docs/23_agent/agent_08_03_configuration-tools-memory.md`). No document covers an unexpected failure of the check itself. `docs/10_adr/adr_02_004_environment-failure-handling-policy.md` INV-07 lists Safety Tier but not drift; ADR-003 limits the static registry to diagnostic use (drift validation), so a crashed drift check does not by itself bypass runtime routing.
- **Exception types (Issue Unresolved Question 2)**: `check_routing_drift()` can fail through `validate_routing_against_config` (registry resolution, per-server `tool_names` access, `validate_tool_names_match`) and through `ctx.cfg.mcp.mcp_servers`; all are non-`RuntimeError` in practice. The policy chosen applies to every exception other than `RuntimeError`, so the exact list does not need to be enumerated.
- **No test pins the current behavior**: the only tests of the function are the three strict-mode cases in `tests/agent/test_startup_mcp_starter.py`; the pipeline tests mock `check_routing_drift` and do not cover an exception. Other callers: `scripts/agent/repl_health.py` re-exports the name only.

## Reason for change
- Routing drift is a startup safety diagnostic whose strict mode the project requires in production. A check that silently reports nothing when it crashes defeats that guarantee, and its severity differs between the drift block and the adjacent safety-tier block without a stated rule.
- Making severity follow the strictness the operator already configured keeps the documented semantics (strict means unknown or drifted is FATAL; non-strict means WARNING) and adds no new setting.

## Implementation intent
- Let unexpected exceptions propagate out of `check_routing_drift()` and decide their severity in one place, the pipeline block, next to the existing `RuntimeError` mapping.
- Treat "strictness cannot be read" as strict, so an unreadable setting fails closed.
- Keep `check_services()` from growing: put the strict/non-strict choice in a small helper.
- Do not change the findings, the `RuntimeError` message, or the safety-tier block.

## Requirements
- `REQ-001`: `check_routing_drift()` no longer catches unexpected exceptions; any exception other than the strict-mode `RuntimeError` propagates, and its docstring states this.
- `REQ-002`: In block `# 5`, a non-`RuntimeError` failure is recorded as a FATAL outcome when `routing_drift_strict` is true and as a WARNING outcome when it is false; an unreadable setting is treated as strict.
- `REQ-003`: The `RuntimeError` to FATAL mapping, the drift findings (warnings), and the safety-tier block (`# 5b`) behave exactly as before.
- `REQ-004`: Tests cover REQ-001 to REQ-003 at function level and pipeline level.
- `REQ-005`: The three documents that state routing-drift severity state the rule for an unexpected failure of the check itself.
- `REQ-006`: The existing tests, lint, types, and the full suite pass with no new failures.
