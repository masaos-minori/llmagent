## Background
ADR-012（Status: Proposed）Decision #5 は、`git_checkout`/`git_pull` が Dirty Worktree・Detached HEAD の状態を検出し、安全な例外（dry_run 等）がない限り実行を拒否することを求めている。この差異は ADR-012 自身の Known Deviations に `GIT-001` として既に登録済みである。

## Problem
- `scripts/mcp_servers/git/git_service.py` の `git_checkout()`（line 224-238）/`git_pull()`（line 240-254付近）は `_validate_ref()`（ref安全性）と `_validate_protected()`（保護ブランチ）のみを呼び出しており、Dirty Worktree・Detached HEAD の検査は一切ない。
- `scripts/mcp_servers/git/format_output.py:format_status()`（line 28-40）は `repo.is_dirty(untracked_files=True)` を使うが、これは `git_status`（読み取り専用ツール）の表示専用であり、書き込みゲートには使われていない。issue の記載と一致。
- `git_checkout`/`git_pull` は既に `dry_run` 引数を受け付けており（`GitCheckoutRequest`/`GitPullRequest`）、`format_checkout()`/`format_pull()`（`format_output.py:118-147`）を確認した結果、`dry_run=True` 時は `git_checkout` は分岐先で実際の `checkout`/`create_head` を一切呼ばず、`git_pull` は `git fetch --dry-run` のみを実行し、いずれも作業ツリーを変更しない。これは Decision #5 が言う「文書化された安全な例外」の実装として既に存在する仕組みであり、新規の例外設計は不要と判断した。
- `GitConfig`（`scripts/mcp_servers/git/git_models.py:24-52`）には `protected_branches` という既存のポリシー配列パターンがあり、これに倣って Detached HEAD 許可ポリシーを追加できることを確認した。

## Reason for change
Dirty Worktree での `git_checkout`/`git_pull` 実行は、未コミットの変更を失わせる可能性がある High Severity の Git MCP セキュリティギャップである。ADR-012 は既にこの差異を GIT-001 として認識しているが未実装のまま残っている。

## Implementation intent
`GitSecurityGuards._check_dirty_worktree(repo)` / `_check_detached_head(repo, cfg)` を追加し、`git_checkout`/`git_pull` ハンドラ内で、`req.dry_run` が `False` の場合にのみ呼び出す。Detached HEAD の許可は `GitConfig.allow_detached_head`（デフォルト `False`）で制御する。

## Requirements
- `REQ-001`: `scripts/mcp_servers/git/git_security.py` に `_check_dirty_worktree(self, repo: git.Repo) -> tuple[bool, str]` を追加する。`repo.is_dirty(untracked_files=True)` が `True` の場合、拒否メッセージを返す。
- `REQ-002`: 同ファイルに `_check_detached_head(self, repo: git.Repo) -> tuple[bool, str]` を追加する。`repo.head.is_detached` が `True` かつ `self._cfg.allow_detached_head` が `False` の場合、拒否メッセージを返す。
- `REQ-003`: `scripts/mcp_servers/git/git_models.py:GitConfig` に `allow_detached_head: bool = False` フィールドを追加し、`from_dict()` で `protected_branches` と同様にパースする。
- `REQ-004`: `scripts/mcp_servers/git/git_service.py` の `git_checkout()`/`git_pull()` ハンドラで、`req.dry_run` が `False` の場合に限り、リポジトリを開いた直後（`op` 実行前）に `_check_dirty_worktree()`/`_check_detached_head()` を呼び出す。両チェックとも既存の `_validate_ref()`/`_validate_protected()` と同じ「エラーメッセージがあれば即座に return」パターンに従う。
- `REQ-005`: `tests/mcp_servers/git/test_git_security_compliance.py`（または適切な既存テストファイル）に、(a) Dirty Worktree で `git_checkout`/`git_pull` が拒否される、(b) Detached HEAD かつ `allow_detached_head=False` で拒否される、(c) `allow_detached_head=True` なら許可される、(d) `dry_run=True` なら Dirty/Detached であっても拒否されない、の4パターンのテストを追加する。

## Acceptance criteria
- AC-01（REQ-001,REQ-004対応）: Dirty Worktree 状態のリポジトリに対する `git_checkout`/`git_pull`（`dry_run=False`）が拒否メッセージを返すことをテストで確認できる。
- AC-02（REQ-002,REQ-003,REQ-004対応）: Detached HEAD 状態かつ `allow_detached_head=False`（デフォルト）のリポジトリに対する `git_checkout`/`git_pull`（`dry_run=False`）が拒否メッセージを返すことをテストで確認できる。
- AC-03（REQ-003対応）: `allow_detached_head=True` を設定した場合、Detached HEAD でも拒否されないことをテストで確認できる。
- AC-04（REQ-004対応）: `dry_run=True` の場合、Dirty Worktree/Detached HEAD であっても拒否されず、従来どおりのプレビュー動作を維持することをテストで確認できる（回帰防止）。

## Design
- `_check_dirty_worktree`/`_check_detached_head` は `_check_protected_branch` と同じ `tuple[bool, str]` 戻り値パターンに従う（`(True, "")` で許可、`(False, "[DENIED] ...")` で拒否）。
- `git_checkout`/`git_pull` ハンドラでの呼び出し順序: 既存の `_validate_ref()` → `_validate_protected()` の後、`_run_tool()` 呼び出し前に `if not req.dry_run:` ブロックで `_check_dirty_worktree()`/`_check_detached_head()` を追加する。リポジトリを開く必要があるため、`_run_tool()` 内部（`self._open_repo(repo_path)` 実行後）に呼び出し位置を置くか、ハンドラ側で先に repo を開いて両チェックを行ってから `_run_tool()` に委譲する形にするかは実装時に確定する（既存の `_run_tool()` のリポジトリオープンとの重複を避けるため、実装手順書作成時に `_run_tool()` のシグネチャ拡張を検討する）。
- `GitConfig.allow_detached_head` のデフォルトは `False`（Decision #5 の「明示的に許可されない限り拒否」に合わせる）。

## Risks
- **Risk**: `_run_tool()` の共通経路にチェックを混入させると `git_add`/`git_commit`/`git_push` まで誤ってブロックする → **Mitigation**: Design節で明記した通り、チェック呼び出しは `git_checkout`/`git_pull` ハンドラに限定し、共有の `_validate_repo()`/`_run_tool()` 本体は変更しない。
- **Risk**: `dry_run` を安全な例外として扱う設計判断が、将来 ADR-012 が Accepted になる際に「明示的に文書化された例外」として正式に ADR 本文へ追記されていないと指摘される可能性 → **Mitigation**: 実装完了後、ADR-012 の Known Deviations `GIT-001` を解決済みとして更新し、`dry_run` を安全な例外として採用した旨を記録する。
