## 1. Goal

Add filtering policies for memory snippets before they are injected as system messages into the LLM context. Prevent prompt injection attacks where the LLM could manipulate its own context by generating queries designed to retrieve specific snippets. Limit snippet length and mark system message priority lower than user messages.

## 2. Scope

### In-Scope
- Add PII/credential filtering layer for memory snippets before injection
- Implement maximum snippet length limit (500 characters per snippet)
- Add priority marker to system message indicating lower priority than user messages
- Log warnings when snippets are filtered or truncated

### Out-of-Scope
- Changes to memory retrieval logic
- Changes to memory storage schema
- Changes to conversation history management
- Database migration for existing records

## 3. Assumptions

- PII detection can use regex-based patterns for common formats (email, phone, credit card, etc.)
- The 500-character limit per snippet is acceptable for balancing context relevance vs. injection risk
- System message priority marking should use a standard format compatible with existing LLM providers
- Warnings should be logged at INFO level with snippet details redacted

## 8. Risks & Mitigations

- **Risk**: PII detection may have false positives, rejecting legitimate snippets. → **Mitigation**: Start with logging-only mode (warn but don't reject), then switch to reject mode after validation period. Provide configuration option to adjust sensitivity.
- **Risk**: Custom PII patterns may miss some sensitive data types. → **Mitigation**: Use established patterns from existing security libraries; document known limitations.
- **Risk**: Truncating snippets may remove important context. → **Mitigation**: Keep snippet prefix intact (e.g., "[Semantic memory]") even when truncating content; log which snippets were truncated.
