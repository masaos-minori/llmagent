# Plan — Catch jsonschema.SchemaError in tool argument type validation

## Goal
Make `_check_type_validation()` in `scripts/agent/tool_arg_validator.py` robust against
both `jsonschema.ValidationError` and `jsonschema.SchemaError` so a malformed MCP input
schema is reported as a validation failure instead of crashing the tool execution path.

## Priority
Medium

## Scope
- **In-Scope**: Adding a `SchemaError` (and defensive base `JSONSchemaError`) catch to
  `_check_type_validation()` that returns a failed `ValidationResult` with a
  schema-specific reason; adding a unit test for the malformed-schema path; updating the
  Known Limitations bullet in `docs/23_agent/agent_06_01_...execution.md`.
- **Out-of-Scope**: Changing the `ValidationError` branch or any other validation step
  (required-fields, extra-fields, custom-validator); changing how valid schemas are
  validated; broadening the catch to bare `Exception`; modifying the JSON Schema library
  version.

## Background
Tool arguments are validated against each MCP server's declared `input_schema` before
execution. The type-check step delegates to `jsonschema.validate()` inside
`_check_type_validation()`. Per `docs/23_agent/agent_06_01_...execution.md` Known
Limitations, structurally invalid schemas from MCP servers may raise
`jsonschema.SchemaError`, which that function does not catch.

## Problem
`_check_type_validation()` wraps only `jsonschema.ValidationError`:

```python
try:
    jsonschema.validate(instance=args, schema=input_schema)
except jsonschema.ValidationError as e:   # SchemaError is NOT caught here
    return ValidationResult(success=False, reason=...)
return ValidationResult(success=True)
```

`jsonschema.SchemaError` (raised when the schema itself is malformed, e.g. invalid JSON
Schema syntax/keywords) is a distinct exception hierarchy from `ValidationError`. When an
MCP server ships a broken schema, `validate()` raises `SchemaError`, which escapes
`_check_type_validation()` and the surrounding validation call chain, turning a
recoverable "bad schema" condition into an unhandled exception in the tool execution path.

## Reason for change
A broken or malicious MCP server can crash the tool execution path by shipping a malformed
schema rather than being rejected like any other type mismatch. This is a
defense-in-depth and reliability gap: schema validity is a precondition that should fail
closed with a reported validation error, not an uncaught exception.

## Implementation intent
Wrap the `jsonschema.validate()` call in `_check_type_validation()` to also catch
`jsonschema.SchemaError` (and, defensively, the base
`jsonschema.exceptions.JSONSchemaError`) and convert them to a
`ValidationResult(success=False, ...)` with a clear reason. Keep the existing
`ValidationError` handling unchanged. Use a distinct reason string for schema errors (e.g.
"Invalid input schema for {tool_name}: {e.message}") so operators can tell it apart from a
value type mismatch. Do not alter the required-fields, extra-fields, or custom-validator
steps.

## Requirements
- `REQ-001`: `_check_type_validation()` catches `jsonschema.SchemaError` in addition to
  `jsonschema.ValidationError` and returns a failed `ValidationResult`.
- `REQ-002`: A distinct, schema-specific reason string distinguishes `SchemaError` from a
  value type mismatch; the existing `ValidationError` message format is preserved.
- `REQ-003`: A unit test feeds a deliberately malformed schema and asserts the validation
  returns `success=False` instead of raising.
- `REQ-004`: Valid schemas and ordinary type mismatches keep their current behavior.
- `REQ-005`: The Known Limitations bullet in `docs/23_agent/agent_06_01_...execution.md`
  reflects that structurally invalid schemas are now handled (or moved to a resolved note).

## Design
Path A (affects ≤ 3 files; no public/runtime interface change; no DB schema change).
Adversarial verification (Step 2) confirmed the issue's claims against current source:
`_check_type_validation()` (lines 184-195) catches only `jsonschema.ValidationError`;
`validate_tool_arguments()` calls it without a try/except, so `SchemaError` propagates to
the outer caller `tool_preparation.py`. One nuance found: `validate_tool_arguments()`'s
docstring claims malformed schemas fall back to lenient mode, but the type-validation path
does not actually implement that — the gap is real. Preserve the `ValidationError`
message format; order except clauses most-specific first (see UNK-01).
