## Background
Per this session's earlier full-suite investigation, these 4 tests were observed failing in the ~2700-test full-suite run but passing when re-run individually via `pytest --lf`. This planning cycle re-confirmed the pattern: 2 separate reruns of the 3 affected files together each showed exactly 1 of the 3 mcp_servers/cicd/shell tests failing (a different one each time), while `test_eventbus_publish.py`'s 2 tests passed in the recheck; running the failing shell-endpoint test in complete isolation passed reliably (`1 passed`) — confirming the failure is genuinely context/order-dependent, not a fluke of a single bad run.

## Problem
- `tests/eventbus/test_eventbus_publish.py::test_jsonl_append_failure_increments_metric`, `::test_broker_notify_failure_increments_metric`: intermittently fail in a full-suite/multi-file context.
- `tests/mcp_servers/cicd/test_cicd_server_endpoints.py::TestCallToolEndpoint::test_dispatches_known_tool_and_audit_logs`, `tests/mcp_servers/shell/test_shell_server_endpoints.py::TestCallToolEndpoint::test_dispatches_known_tool_and_audit_logs`: same intermittent pattern — confirmed via this cycle's reruns that each fails only sometimes, and passes reliably when run alone.

## Reason for change
Flaky tests erode confidence in full-suite/CI signal and can mask genuine regressions or cause false-failure noise. This session's earlier investigation (`eb005`) already found one concrete instance of this general failure class (a shared, process-global Prometheus `REGISTRY` causing order-dependent counter-value assertions) — these 4 tests may share a similar shared-global-state cause (e.g. an audit-log call counter, a cached FastAPI app/registry object, or similar module-level mutable state not reset between tests), but the exact mechanism for these specific 4 tests was not pinned down within this planning cycle's evidence-gathering.

## Implementation intent
Per `skills/python-test-and-fix/SKILL.md` Path D (Flaky Test Investigation): reproduce each failure deterministically by running the affected test alongside progressively larger neighboring test sets (starting from its own file, then its own directory, then the two mcp_servers directories together) to narrow down which other test(s) leave behind state that causes the failure. Look specifically for shared mutable state: a module-level counter/registry not reset between tests (the `eb005` pattern), a cached `TestClient`/FastAPI `app` instance whose state carries over, or an audit-log mock/spy whose call count accumulates across tests. Fix by adding proper per-test isolation (a fixture that resets the identified shared state) rather than reordering tests or adding retries.
