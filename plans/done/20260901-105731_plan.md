## Goal
- Add `tools/generate_workitem.py`, a scaffolding script that generates a correctly-named,
  correctly-structured skeleton file for the three work-item document kinds (`issues/*.md`,
  `plans/*.md`, `implementations/*.md`), removing manual timestamp computation and manual
  template field-order transcription as sources of naming/structure drift.

## Priority
Medium

## Scope
- **In-Scope**:
  - `tools/generate_workitem.py`: a single script with a `--kind {issue,plan,implementation-procedure}`
    flag that renders the canonical fenced skeleton from `templates/issue.md`, `templates/plan.md`,
    or `templates/implementation-procedure.md` respectively, with placeholder text only (no
    invented substantive content).
  - Filename computation matching each workflow's exact naming convention (issue, plan,
    implementation-procedure).
  - Collision rejection (refuse to overwrite an existing file in the target directory or its
    `done/` counterpart).
  - `Source plan` path existence validation for implementation-procedure mode.
  - `tools/TOOL_DESCRIPTIONS.md` entry for the new tool.
  - `tests/tools/test_generate_workitem.py`.
- **Out-of-Scope**:
  - Generating substantive field content (Summary, Problem, Decision Details, Traceability
    values, etc.) — the tool emits placeholder text only.
  - Modifying `templates/issue.md`, `templates/plan.md`, or `templates/implementation-procedure.md`.
  - The four other tools proposed alongside this one in the same session (traceability
    checking, stage-transition automation, document renaming, Known Deviation/Known Issue sync
    checking) — tracked as separate issues, not touched here.

## Background
`skills/issue-creator`'s Issue Filename Generation section, `skills/issue-to-plan`'s Output
format section, and `skills/plan-to-implementation-procedure`'s Output format section each
define a naming convention and a canonical template file. All three are currently produced by
an agent or human typing the boilerplate structure out by hand each time, which risks
field-order drift from the canonical templates and timestamp/slug typos. `AGENTS.md` Global
Rule 7 (script an operation once it is repeated three or more times) applies, since this pattern
was repeated across a single session's work (Evidence: Explicit in issue).

## Problem
(Evidence: Confirmed by repository evidence) `tools/TOOL_DESCRIPTIONS.md` documents an
established `generate_*` naming convention for tools that produce new content
(`generate_reference_table.py`, `generate_mcp_inventory.py`, both listed under its
"リファレンス自動生成スクリプト" table), but no existing tool generates a new work-item
document from `templates/issue.md` / `templates/plan.md` / `templates/implementation-procedure.md`.
Confirmed absent: `tools/generate_workitem.py` does not exist in the repository (`ls
tools/generate_workitem.py` — not found); `tests/tools/test_generate_workitem.py` does not exist
either (confirmed via directory listing).

## Reason for change
A scaffolding tool removes the two most error-prone manual steps (timestamp computation and
template field-order reproduction) from every issue/plan/implementation-procedure creation, and
guarantees the naming convention that `skills/issue-to-plan` Step 1.5's duplicate detection and
`skills/plan-to-implementation-procedure`'s `{timestamp}_{seq}_{target_file_slug}.md` naming
depend on.

## Implementation intent
Add `tools/generate_workitem.py` with a `--kind {issue,plan,implementation-procedure}` flag
(single script, per the issue's stated default — see Unknowns UNK-01). Each mode parses the
target template's canonical skeleton — confirmed to live inside a single fenced ` ```markdown
... ``` ` code block in all three template files (`templates/issue.md` lines 10-69,
`templates/plan.md` lines 8-157, `templates/implementation-procedure.md` lines 19-77; the
surrounding prose in each file, e.g. "Field notes" / "Notes on filling...", is explanatory and
must not be copied into the generated skeleton) — and writes it verbatim (placeholder text
unchanged) to the correctly-named output path. For `issue`, accept `--id` and `--title` and emit
`issues/{timestamp}_{id}_{slug}.md`. For `plan`, emit `plans/{timestamp}_plan.md`. For
`implementation-procedure`, accept `--source-plan` and `--target-file-path` and emit
`implementations/{timestamp}_{seq}_{target_file_slug}.md`, computing `target_file_slug` from
`target_file_path` (not `target_file_name`) exactly as `skills/plan-to-implementation-procedure/workflow.md`
Workflow position defines it. The tool only creates the skeleton file — it does not decide
content.

## Requirements
- `REQ-001`: Implement `tools/generate_workitem.py`'s three rendering modes (issue, plan,
  implementation-procedure), each extracting the current fenced skeleton from its template file
  and writing it with placeholder text preserved verbatim — no invented substantive content.
- `REQ-002`: Compute the output filename per each mode's exact naming convention: issue ->
  `{timestamp}_{id}_{slug}.md` in `issues/` (per `skills/issue-creator/SKILL.md` Issue Filename
  Generation); plan -> `{timestamp}_plan.md` in `plans/` (per `templates/plan.md` Step 5 filename
  rule); implementation-procedure -> `{timestamp}_{seq}_{target_file_slug}.md` in
  `implementations/`, with `target_file_slug` derived from `target_file_path` (per
  `skills/plan-to-implementation-procedure/workflow.md` Workflow position).
- `REQ-003`: Refuse (non-zero exit, no write) when the computed output path already exists in
  the target directory or its `done/` counterpart, rather than overwriting or auto-incrementing.
- `REQ-004`: For implementation-procedure mode, validate that the given `--source-plan` path
  exists before generating the output file; refuse (non-zero exit, no write) if it does not.
- `REQ-005`: Document `tools/generate_workitem.py` in `tools/TOOL_DESCRIPTIONS.md`, consistent
  with the file's established `generate_*` table, so `tools/check_tool_descriptions_sync.py`
  passes.
- `REQ-006`: Add `tests/tools/test_generate_workitem.py` covering: filename-generation
  correctness for each of the three kinds, field-order correctness against current template
  content, collision rejection, and missing-source-path rejection.

## Design
- Task-size classification (`skills/issue-to-plan/SKILL.md` Routing): **Path A (Small Task)** —
  affects 3 files (`tools/generate_workitem.py`, `tools/TOOL_DESCRIPTIONS.md`,
  `tests/tools/test_generate_workitem.py`), no public/runtime-facing interface change (a
  dev-only CLI script, not part of the running agent/MCP/RAG services), no database schema
  change. Consistent with prior precedent in this repository for new `tools/` scripts of similar
  size (e.g. `plans/done/20260707-105310_plan.md`, `plans/done/20260712-163137_plan.md`, both
  classified Path A for ≤3-file tool additions). Per Routing, this skips
  architecture/dependency/historical/operational analysis; the validation-quality baseline below
  is still established.
- Rendering approach: each template's canonical skeleton lives inside exactly one fenced
  ` ```markdown ... ``` ` block (confirmed via `grep` line numbers cited in Implementation
  intent above). The tool extracts text strictly between that fence's opening and closing marker
  and writes it unchanged — this is what keeps the tool's output from drifting off the canonical
  template (per the issue's Constraints: "the tool must track whatever those templates currently
  define, not fork a parallel copy of the field list").
- Filename computation is implemented as one function per kind, mirroring the three naming rules
  cited in Reference Files, rather than one generic formatter — the three rules differ in
  structure (id+slug vs. none vs. seq+path-slug) and forcing a shared formatter would obscure
  each rule's source-of-truth reference.
- Collision policy (REQ-003) is a hard reject, not the zero-pad auto-increment that
  `templates/plan.md` Step 5 defines for the `issue-to-plan` *workflow's own* plan-generation
  step. This is a deliberate, evidence-based divergence — the issue's Required Changes explicitly
  states "reject ... rather than silently overwriting," and does not ask for auto-increment. See
  Risks below for the mitigation on this divergence.

## Risks
- **Risk**: The tool's hard reject-on-collision policy (REQ-003) diverges from
  `templates/plan.md` Step 5's zero-pad auto-increment convention used by the `issue-to-plan`
  *workflow itself* when generating a plan document, which could read as an inconsistency to a
  future maintainer. **Mitigation**: state the reject-only behavior explicitly in the tool's
  `--help` text and its `tools/TOOL_DESCRIPTIONS.md` entry; do not have `skills/issue-to-plan`
  delegate its own zero-pad step to this tool unless a future issue explicitly updates
  `workflow.md` to do so.
- **Risk**: `templates/issue.md` / `templates/plan.md` / `templates/implementation-procedure.md`
  field order can change independently after this tool ships, silently desyncing the generated
  skeleton from the canonical template. **Mitigation**: parse the fenced block directly at each
  invocation (never a hardcoded copy of field names), and add a test (part of REQ-006/T2)
  asserting the rendered skeleton's field headings match the template's current field headings.
- **Risk**: The single-script-with-`--kind` design (UNK-01's adopted default) may not match a
  future owner decision favoring three separate scripts, requiring a later split.
  **Mitigation**: keep the three render/filename functions internally separated per kind (see
  Design) so a future split is a mechanical extraction, not a rewrite.
