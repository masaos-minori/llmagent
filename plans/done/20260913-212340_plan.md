## Background
The Issue's cited claim
(`docs/03_rag_01_system_overview.md:52`: "Agent turn invokes
`RagPipeline.augment(query)` via MCP HTTP; RagPipeline executes MQE → Search →
RRF → Rerank → Augment stages; KNN + BM25 search operates over SQLite (rag.db).")
and the adjacent "Owned State" line (line 53: "RagPipeline owns the query
execution lifecycle; SQLite (rag.db) owns the vector store layer.") are confirmed
accurate as quoted.

**Re-verified 2026-09-13** (this cycle): the Issue's premise that no rationale
exists for this ownership needed correction — unlike sibling issues this cycle
(`183021`, `183024`, `183025`) where empirical/design rationale was genuinely
absent, here the rationale exists but is spread across separate documents this
overview section does not reference:
- `rules/env.md`'s layered-architecture rule (6-layer structure enforced by
  `.importlinter`: `shared → db → rag/mcp_servers → agent`, `eventbus` fully
  independent) establishes *why* query-execution logic lives in the `rag` layer
  (it is the layer positioned to depend on `db` for storage access) — a
  structural, repository-wide constraint, not specific to `RagPipeline` alone
- `docs/adr/ADR-005-rag-source-derived-index-relationships.md` establishes the
  canonical-source/derived-index relationship (`documents`/`chunks` as source of
  truth, `chunks_fts`/`chunks_vec` as rebuildable derived indexes) — directly
  relevant to *why* SQLite is positioned as the vector-store layer's owner (it
  hosts both the canonical source and the derived index in one place, under one
  consistency model)
- `docs/adr/ADR-010-rag-fallback.md` documents the in-process fallback model
  (why `RagPipeline` handles both the primary HTTP-delegated path and the
  in-process fallback path itself) — directly relevant to *why*
  `RagPipeline` owns the full query-execution lifecycle rather than delegating
  parts of it elsewhere

Points 3 and 4 of the Issue's Recommended Action (how ownership affects
modification rights; known exceptions to the ownership rules) are **not**
answered by any of these documents or elsewhere in the repository (confirmed via
targeted review of `rules/env.md`, `ADR-005`, `ADR-010`, and a repository-wide
`grep` for "modification rights"/"ownership exception" — no match). Unlike points
1-2, these describe process/governance conventions this repository has not
documented, not facts this cycle's investigation could locate.

## Problem
A reader of the "Owned State" line has no way to discover that its rationale is
already recorded, in `rules/env.md`'s architecture rule and two specific ADRs,
because none of them is cross-referenced from this line — and no way to know that
modification-rights/exception guidance genuinely doesn't exist yet, rather than
just being unlinked.

## Reason for change
Add cross-references to the ADRs/rule that already answer "why does this
ownership exist" so a reader is directed to the actual rationale, and state
plainly that modification-rights/exception guidance is not recorded, so the
reader does not keep searching for it.

## Implementation intent
Add, immediately after the Query Pipeline's "Owned State" line (line 53): (1) a
cross-reference to `rules/env.md`'s layered-architecture rule as the structural
basis for `rag`-layer ownership; (2) a cross-reference to `ADR-005` for the
SQLite canonical-source/derived-index rationale; (3) a cross-reference to
`ADR-010` for why `RagPipeline` owns the full execution lifecycle including
fallback; (4) a brief note that modification-rights implications and known
exceptions to this ownership model are not separately documented anywhere in this
repository as of this cycle's search.
