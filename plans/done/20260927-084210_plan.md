## Goal
Fix two unrelated, single-test failures in the MCP file server's read path: a genuine production bug where directory validation incorrectly applies the file-content byte-size limit to a directory's filesystem `stat()` size (raising a spurious `FileValidationError`), and a test-mocking fragility where a `Path.stat` call-counting scheme no longer triggers `get_file_info`'s intended `OSError`-to-`FileValidationError` conversion.

## Priority
Medium

## Scope
- **In-Scope**:
  - Fix `scripts/mcp_servers/file/read_security.py::ReadSecurityGuards._validate_file` so the `expected_type="dir"` branch does not apply `_check_size_limit` (the file-content max-read-bytes check) to a directory's `stat().st_size`.
  - Fix `tests/mcp_servers/file/test_read_service.py::TestGetFileInfo::test_get_file_info_os_error_raises_file_validation_error`'s `Path.stat` call-counting mock so it reliably fails on `get_file_info`'s own explicit `stat()` call.
- **Out-of-Scope**: Any other failing test from the full-suite investigation (tracked separately).

## Background
`ReadSecurityGuards._validate_file` (`scripts/mcp_servers/file/read_security.py:53-66`) resolves a path, validates it is a file or directory per `expected_type`, then unconditionally calls `self._check_size_limit(target)` — which calls `target.stat().st_size` and compares it against `self._max_read_bytes` (a limit meant for file *content* size). For a directory, `stat().st_size` reflects filesystem block/inode accounting (commonly 4096 bytes on ext4 for a directory entry), which is unrelated to "how much data would be read" and can trivially exceed a small configured `max_read_bytes` even for an empty directory. `tests/mcp_servers/file/test_get_file_info_os_error_raises_file_validation_error` separately verifies `read_business.py::get_file_info`'s `try: st = target.stat() except OSError: raise FileValidationError(...)` branch, using a `Path.stat` monkeypatch that counts calls on the target path and raises only from the second call onward (to let `target.exists()`'s own internal `stat()` call succeed first) — but the test currently observes no exception at all, indicating the call-counting assumption no longer matches the actual number/identity of `stat()` calls `get_file_info` (or the surrounding resolution/existence-check path) makes.

## Problem
- `test_validates_existing_directory`: `_validate_file(str(sub), expected_type="dir")` raises `FileValidationError: File size exceeds the limit (1024 bytes): 4096 bytes` — confirmed via traceback to originate from `_check_size_limit` being called for a directory target.
- `test_get_file_info_os_error_raises_file_validation_error`: `Failed: DID NOT RAISE <class 'mcp_servers.file.common.FileValidationError'>` — `get_file_info`'s own try/except around `target.stat()` (confirmed correct via Read, `read_business.py:287-307`) is never actually reached with a failing `stat()` call under the test's current mock, for a reason not fully pinned down within this planning cycle (see Unknowns).

## Reason for change
The directory-validation bug is a genuine correctness defect: any directory read/listing operation whose `stat()`-reported size exceeds the configured file-content byte limit would incorrectly fail, even though no file content is actually being read. The `get_file_info` test fix restores real coverage of the `OSError`-to-`FileValidationError` conversion path, which is currently unverified (the test passes-by-vacuously-not-raising only because `pytest.raises` requires an exception, so the failure here means the test never actually failed for the right reason previously either — worth confirming during implementation whether this test has ever passed as intended).

## Implementation intent
For the directory-validation bug: skip `_check_size_limit` entirely when `expected_type == "dir"` in `_validate_file` (returning a sentinel size, e.g. `0`, or restructure the return type if callers rely on a meaningful size for directories — confirm via Read of all `_validate_file(..., expected_type="dir")` call sites before deciding the exact return-value contract). For the mocking fragility: add temporary print/call-tracing to `boom()` to observe the actual sequence and identity of `Path.stat` calls during a repro run, then adjust the call-counting condition (or switch to a more robust technique, e.g. patching `read_business.get_file_info`'s specific call site rather than global `Path.stat`) so the intended `OSError` reliably surfaces from `get_file_info`'s own explicit `stat()` call.
