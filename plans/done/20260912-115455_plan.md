- Decide whether `/dlq/{event_id}/requeue` should use in-place requeue (same `event_id`, cleared `dlq_at`) or lineage-based requeue (new `event_id`, `redelivered_from` pointing to original), then align production code and tests to that single model.

## Background
`redeliver_event()` and the `redelivered_from`/`cycle_failure_count` schema columns were added in a separate, earlier commit (concurrent eventbus work landed via rebase during this session — see `scripts/eventbus/db.py` history), apparently in anticipation of moving DLQ requeue to the lineage model, but the route (`dlq_route.py::dlq_requeue()`) was never switched over to call it — it still calls the older `requeue_event()`. `test_eventbus_concurrent.py` was updated (in commit `8d915f7c6`) to assert the lineage-model response shape, but the other DLQ test files were not updated to match, and `redeliver_event()` itself was not yet wired into the route or given the concurrency guard it needs to satisfy the "only one redeliver succeeds" requirement.

## Problem
`/dlq/{event_id}/requeue`'s intended semantics are ambiguous in the current codebase: the route implementation, and 5 out of 6 currently-passing DLQ-requeue tests, assume in-place requeue; 1 test (added most recently) assumes the lineage model. Whichever direction is chosen, the losing side's tests need rewriting, not just the production code.

## Reason for change
`test_eventbus_concurrent.py::TestConcurrentDlqRequeue::test_concurrent_dlq_requeue` currently fails and will keep failing until this is resolved one way or the other.

## Implementation intent
Decide whether DLQ requeue should be in-place (current route behavior) or lineage-based (new event_id per redeliver, matching `redeliver_event()` and the schema support already in place), then:
- If in-place is correct: update `test_concurrent_dlq_requeue` to drop the `new_event_id`/`new_seq` assertions and match the in-place response shape, and consider removing or repurposing the now-dead `redeliver_event()` function.
- If lineage is correct: wire `dlq_route.py::dlq_requeue()` to `redeliver_event()` (adding a `redelivered_from`-based idempotency guard, since the original row's `dlq_at` is deliberately left set), and rewrite the 5 in-place-model tests listed above (in `test_eventbus_dlq.py` and `test_eventbus_requeue_edge_cases.py`) to match.

## Design
### Decision Point: In-place vs Lineage Model

The core design decision is which requeue model to adopt as the single truth for `/dlq/{event_id}/requeue`. Both models have valid arguments:

**In-place model (current route behavior):**
- Pros: Simpler semantics — the same event is "requeued" into the active queue; no new event_id to track; aligns with existing test coverage (5 out of 6 tests).
- Cons: Loses audit trail — no way to distinguish between the original delivery attempt and a requeued attempt; harder to debug delivery issues.

**Lineage model (new event_id per redeliver):**
- Pros: Full audit trail — each delivery attempt is a distinct row with `redelivered_from` pointing to the original; supports retry counting via `cycle_failure_count`; aligns with the schema support already in place.
- Cons: More complex — requires updating the route to call `redeliver_event()`, adding a concurrency guard, and rewriting 5 test files; breaks backward compatibility with callers expecting the same `event_id`.

### Lineage Model Concurrency Guard Strategy

When the lineage model is chosen, `redeliver_event()` needs a correct concurrency guard. The current implementation uses a conditional-update on the original row (`WHERE event_id = ? AND dlq_at IS NOT NULL`) followed by an INSERT of a new row. This approach has a race condition: two concurrent requests could both see `dlq_at IS NOT NULL` and both insert new rows.

A proper guard requires checking whether a `redelivered_from` entry already exists for this original event_id. Since SQLite doesn't support atomic UPSERT-like operations natively without careful transaction handling, the guard should:
1. Begin a transaction
2. Check if `SELECT 1 FROM events WHERE redelivered_from = ?` returns any rows
3. If yes, return `(False, None)` — already redelivered
4. If no, proceed with the conditional UPDATE + INSERT as currently implemented
5. Commit the transaction

This ensures only one redeliver succeeds per original event, satisfying the requirement stated in `test_concurrent_dlq_requeue`.
