## Background
The Issue's cited claim
(`docs/03_rag_05_4-error-handling-reference.md:79`: "The actual exception classes
defined in `scripts/rag/exceptions.py` are 7 types ... `RagRerankError` and
`RagPipelineError` are not included here ... The exception hierarchy is not unified
under a single base class across the entire rag layer.") is confirmed accurate.

**Re-verified 2026-09-13** (this cycle): confirmed the fragmentation's origin via
`git log -S` on each exception class:
- `RagLayerError` and its 6 subclasses (`exceptions.py`) were introduced in
  `afbfe2915 refactor(rag): Phase 1-3 — backward-compat removal, foundation files,
  dataclass migration`
- `RagRerankError` (and its sibling `RagExpansionError`, also not under
  `RagLayerError`) was introduced in `b20e136d8 refactor(rag): split llm.py
  (413→42+260+245 lines) into prompts + client`
- `RagPipelineError` was introduced in `e4152f361 refactor(rag): pipeline/stages
  fail-fast — remove expand_queries_safe, except Exception fallbacks, add
  RagPipelineError`

These are three independent refactoring efforts at different times, each addressing
a different concern (foundational error types, a file-splitting refactor, and a
fail-fast behavior change) — none of them referenced or extended the others'
exception hierarchy. The fragmentation is a byproduct of independently-scoped
refactors, not a deliberate architectural decision, and no design document or ADR
records a rationale for keeping them separate (confirmed: no `docs/adr/*.md` file
references any of these four exception classes).

The Issue's claim that the note is not "clearly connected to the main error
handling tables" is only partially accurate: the `RagPipeline` table (lines 66-73)
does reference `RagRerankError` directly (line 73), and the Implementation Notes
bullet about it (line 77) explains how it's caught — so a connection exists for
that one exception. The disconnection is broader: `RagLayerError` and its 6
subclasses (`exceptions.py`) are not referenced in the `RagPipeline`/`RagIngester`
tables at all, since they are actually raised elsewhere (ingestion validation code,
per `pipeline_utils.py`), making the "7 types" bullet read as an aside rather than
something tied to a specific table row.

## Problem
A reader of the Implementation Notes learns that the exception hierarchy is
fragmented but not why, and has no indication of whether unification is planned,
rejected, or simply never considered — leaving the fragmentation's status
ambiguous.

## Reason for change
Add the fragmentation's actual cause (three independent, unrelated refactors) and a
brief forward-looking note (what unification would require, without committing to
a schedule) to the existing Implementation Notes bullet, so a reader understands
this is an artifact of incremental refactoring history rather than an unexplained
gap or an active area of confusion.

   project to a future migration; a full migration plan would need its own
   Issue→Plan cycle once someone decides to pursue it
