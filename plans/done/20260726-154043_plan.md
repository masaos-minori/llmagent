## Goal

Eliminate the race condition in workflow approval resolution by making the check-and-resolve operation atomic using conditional SQL updates and immediate-mode transactions.

## Scope

**In-Scope:**
- Modify `resolve_approval()` to use conditional UPDATE with `WHERE status='pending'`
- Add row-count verification after conditional UPDATE to detect double-resolution
- Wrap `_cmd_approve()` and `_cmd_reject()` flows in `BEGIN IMMEDIATE` transactions
- Return distinct error messages for "not found" vs "already resolved" states

**Out-of-Scope:**
- Modifying other workflow operations (request_approval, get_latest_approval, etc.)
- Adding new database columns or indexes
- Changing approval audit logging behavior
- Modifying per-tool interactive approval (tool_approval.run_approval_checks)

## Assumptions

1. SQLite `rowcount` attribute accurately reflects the number of rows modified by an UPDATE statement
2. `BEGIN IMMEDIATE` provides sufficient serialization for concurrent writer scenarios
3. The existing `RuntimeError` raised by `resolve_approval()` is used as the sole error mechanism for approval failures
4. Both `_cmd_approve()` and `_cmd_reject()` share the same approval resolution path via `resolve_approval()`

## Risks

- **Risk**: `BEGIN IMMEDIATE` could cause contention under high concurrency → Mitigation: IMMEDIATE lock only held briefly (single UPDATE); accept minor latency increase over double-resolution risk
- **Risk**: SQLite `rowcount` may not reflect affected rows on some platforms → Mitigation: Test `rowcount` behavior explicitly before deploying; fallback to COUNT query if needed
- **Risk**: Error message changes break downstream consumers (e.g., REPL output parsing) → Mitigation: Keep RuntimeError string format similar; document the change
