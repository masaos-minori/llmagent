# Batch subscription replay and define EventBus capacity limits

## Goal

Turn initial-replay into a bounded, observable operation. Replay must never monopolize memory or the global database lock, and operators must be able to observe contention before it becomes an outage.

## Priority
Medium

## Scope
- **In-Scope**: Defining supported publish rate, subscriber count, retained-event count, replay size, and latency objectives based on representative load testing; reading initial replay in bounded, configurable batches (e.g. fetch and yield in chunks rather than one `.fetchall()`); preserving register-before-replay ordering without losing or duplicating events published during replay; instrumenting database-lock wait time, query duration, replay backlog, and batch progress; deciding from measurements whether separate read connections or a connection manager are required.
- **Out-of-Scope**: `/replay` endpoint's own pagination/snapshot-consistency issue (EB-M04). Centralizing the currently-hardcoded operational thresholds (`_SLOW_CONSUMER_THRESHOLD`, queue `maxsize`, health's `500` backlog threshold) into validated configuration — tracked separately in this batch.

## Background

Confirmed by direct read: `subscribe_route.py`'s `_fetch_replay()` executes one unbounded query inside `run_with_db_lock()` (line 64), and `scripts/eventbus/route_helpers.py`'s `run_with_db_lock()` (lines 66-75) wraps every DB-touching route (`publish_route.py`, `ack_route.py`, `dlq_route.py`, `replay_route.py`, `health_route.py`) in the same `asyncio.to_thread(_locked)` pattern, all contending for the same `_db_lock`. `scripts/eventbus/config.py`'s `EventBusConfig` dataclass has no field for replay batch size, subscriber count, retained-event count, or publish rate — confirmed by direct read of its field list (lines 36-42).

## Problem

- A reconnecting consumer with a far-behind offset causes `_fetch_replay()` to load potentially the entire event history into memory in one `.fetchall()` call, and to hold the shared lock for that call's full duration — during which every other route (`publish`, `ack`, `nack`, `dlq`, `health`) is blocked waiting on the same lock.
- No operating envelope (publish rate, subscriber count, retained-event count, replay size, latency objectives) is defined or enforced anywhere, so there is no evidence-based basis for deciding when the system is approaching its limits versus operating normally.
- `health_route.py`'s `max_queue_depth() >= 500` threshold (line 51) and `broker.py`'s `_SLOW_CONSUMER_THRESHOLD = 100` (line 12) are the only capacity-adjacent signals that exist today, and neither is derived from a documented capacity model — they are hardcoded values with no stated rationale (tracked separately in this batch as the operational-thresholds issue).

## Reason for change

Bound resource use and establish an evidence-based operating envelope. Initial replay must not monopolize memory or the global database lock, and operators must be able to observe contention before it becomes an outage.

## Implementation intent

Read initial replay in bounded, configurable batches (e.g. fetch and yield in chunks rather than one `.fetchall()`), releasing and reacquiring `_db_lock` between batches so other routes are not blocked for the full replay duration. Preserve the existing register-before-replay ordering (`subscribe_route.py` already subscribes to the broker before starting replay, at line 39, specifically to avoid losing events published during replay — keep this property while batching). Define supported publish rate, subscriber count, retained-event count, replay size, and latency objectives based on representative load testing, and decide from measurements whether the current single-connection/single-lock model needs separate read connections or a connection manager.

### Architecture analysis

The EventBus currently has two independent operation paths:
1. **Replay path**: `subscribe_route.py`'s `_fetch_replay()` executes one unbounded query inside `run_with_db_lock()`.
2. **Live delivery path**: After replay completes, live events are streamed from the broker queue.

The critical issue is that there is no bound on the replay path — a reconnecting consumer with a far-behind offset can cause the entire event history to be loaded into memory in one `.fetchall()` call, holding the shared lock for the full duration.

### Dependency graphing

```
FastAPI routing ──► subscribe() ──► _sse_gen() ──► _fetch_replay() ──► db.execute().fetchall()
   │                    │              │                        │
   │                    │              │                        ├──► SELECT seq, event_id, topic, payload, producer, published_at FROM events WHERE seq > ? ORDER BY seq
   │                    │              │                        └──► return list of rows
   │                    │              │
   └──► get_broker()    │
   └──► get_db()        │
   └──► get_config()    │
```

After refactoring, the flow becomes:
```
FastAPI routing ──► subscribe() ──► _sse_gen() ──► _fetch_replay_batched() ──► db.execute().fetchmany(BATCH_SIZE)
   │                    │              │                        │
   │                    │              │                        ├──► SELECT seq, event_id, topic, payload, producer, published_at FROM events WHERE seq > ? ORDER BY seq LIMIT BATCH_SIZE OFFSET offset
   │                    │              │                        └──► yield rows, release lock between batches
   │                    │              │
   └──► get_broker()    │
   └──► get_db()        │
   └──► get_config()    │
```

Key dependencies:
- `subscribe_route.py` must iterate over batches instead of fetching all at once.
- `config.py` must provide a `replay_batch_size` field.
- `route_helpers.py` must track lock wait time for instrumentation.
- `db.py` must provide hooks for lock wait time tracking.

### Historical analysis

- The replay path was designed for simplicity — one query, one fetch, one yield loop.
- No prior attempt to add batching to replay exists — this is the first effort.
- The single-connection/single-lock model was chosen for simplicity and correctness — adding separate read connections would require careful consideration of transaction isolation.

### Operational dependency inspection

- Adding batching means that replay will take longer overall (multiple lock acquisitions/releases), but each individual lock acquisition will be shorter — this is a trade-off between throughput and latency.
- The instrumented lock wait time will help operators detect contention before it becomes an outage.
- The capacity limits derived from load testing will inform future scaling decisions.

### Design decisions

1. **Batch size (REQ-002)**: Add a `replay_batch_size` field to `EventBusConfig` with a default value TBD from load testing. The batch size should be small enough to keep individual lock acquisitions short (e.g., 100-1000 events).

2. **Register-before-replay preservation (REQ-003)**: Preserve the existing register-before-replay ordering exactly — the broker subscription must be registered before starting replay, and the `replay_ceil` duplicate-discard logic must continue to work correctly under batching.

3. **Instrumentation (REQ-004)**: Add the following instrumentation:
   - Database-lock wait time: Track how long each route waits for the lock.
   - Query duration: Track how long each DB query takes.
   - Replay backlog: Track how many events are remaining in the replay.
   - Batch progress: Track which batch is being processed.

4. **Capacity limits (REQ-001)**: Define the following capacity limits based on representative load testing:
   - Supported publish rate (events/sec).
   - Subscriber count (concurrent subscribers).
   - Retained-event count (max events retained in SQLite).
   - Replay size (max events replayed in a single session).
   - Latency objectives (p95/p99 latency for publish/ACK operations).

5. **Connection pooling decision (REQ-005)**: Decide from measurements whether separate read connections or a connection manager are required — do not implement speculatively.

6. **Documentation update (REQ-006)**: Document the batched-replay design, the measured capacity limits, and the test methodology used to derive them in `06_eventbus_05`.

## Risks

- **Risk**: Batched replay may increase overall replay time due to multiple lock acquisitions/releases. → **Mitigation**: Keep individual lock acquisitions short by using appropriate batch sizes; monitor lock wait times to ensure other routes are not starved.
- **Risk**: The capacity limits derived from load testing may not generalize across different deployment environments. → **Mitigation**: Document the test methodology clearly so operators can validate limits in their own environment.
- **Risk**: The instrumentation hooks may have performance overhead. → **Mitigation**: Use lightweight timing mechanisms (e.g., `time.monotonic()`) and avoid expensive logging during hot paths.
