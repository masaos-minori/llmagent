## Goal
- Persist a `/undo` compression boundary (`sessions.undo_floor_message_id`) so that conversation turns existing at the last compression (automatic, `/compact`, or fallback truncation) cannot be undone, while turns added after compression remain undoable, and restore the boundary across `/session load`.

## Priority
Medium

## Scope
- **In-Scope**:
  - Add `sessions.undo_floor_message_id INTEGER NOT NULL DEFAULT 0` to the session.sqlite schema (recreation approach; confirmed by user 2026-10-14).
  - Update the boundary atomically with the snapshot rewrite in `SessionMessageRepository.replace_messages()` and expose it through `AgentSession`.
  - Add in-memory `ctx.conv.undo_floor` (index into `ctx.conv.history`; 0 = no boundary) with set/reset lifecycle.
  - Restore the boundary on `/session load` by converting the stored boundary row ID into a history index.
  - Rework `undo_service.undo_last_turn()` and `AgentSession.undo_last_turn()` to gate deletions at the boundary, never mutate when nothing is undoable, and delete in the DB before touching history.
  - Show the compression-boundary message when blocked; keep the current message when never compressed; remove the summary-warning branch.
  - Delete `AgentSession.delete_last_turn()` (no production caller) and its tests.
  - Add unit/integration tests for each acceptance criterion and a schema test for the new column/default.
  - Regenerate `docs/23_agent/agent_13_reference-api-generated.md`.
- **Out-of-Scope**:
  - Adding an incremental migration mechanism to `session.sqlite` (would change db_03 policy; separate proposal).
  - Making compression preserve original messages.
  - Memory/session responsibility changes tracked separately.
  - Production deployment and the actual recreation of the production `session.sqlite`.

## Background
The `/undo` compression boundary behavior was specified on 2026-10-14 (option A: store the boundary in `sessions`) and is already reflected in docs: `agent_07_03`, `agent_07_07`, `agent_04_01`, `agent_04_02`, `agent_09_01`, `db_02` section 6, `deployment_01` (Upgrade note). AGENT-008 was removed from `governance_03`. No ADR is required because no ADR decision changes. The code does not implement it yet, so the docs currently describe the target behavior.

## Problem
- Compression rewrites the stored snapshot through `SessionMessageRepository.replace_messages()`; the summary (`[Conversation summary]`, `role=system`) replaces older messages.
- `scripts/agent/services/undo_service.py` `undo_last_turn()` finds the last `role='user'` message in `ctx.conv.history` with no knowledge of compression, and only returns a warning when the removed range contains a summary.
- It trims `ctx.conv.history` before calling `ctx.session.undo_last_turn()`, so a DB failure leaves history and DB inconsistent.
- `AgentSession.delete_last_turn()` (deletes at most the last 2 rows) has no production caller in `scripts/`.

## Reason for change
After compression, the undoable range is unclear and a summary can be destroyed. A persisted boundary makes the range defined, survives `/session load`, and lets the DB itself refuse to delete rows at or before the boundary.

## Implementation intent
- Add `sessions.undo_floor_message_id INTEGER NOT NULL DEFAULT 0` (0 = never compressed). The boundary is a `messages.message_id` (an `INTEGER PRIMARY KEY AUTOINCREMENT` exists, so the premise holds).
- Update the boundary in the same transaction as the snapshot rewrite: boundary = max `message_id` of the session after the rewrite.
- Keep an in-memory `ctx.conv.undo_floor` (index into `ctx.conv.history`; 0 = no boundary), updated after a successful snapshot write, reset on `/clear`, and derived from row IDs on `/session load`.
- `/undo`: search for the last user message only at or after the floor; if none, change nothing (history and DB) and report why. Delete in the DB first, restricted to `message_id` greater than the stored boundary, then change history through a verified method.
- Remove `delete_last_turn()` (no caller) instead of keeping a compatibility copy.
- Keep the existing stripping of preceding `_memory_injected` / `_ephemeral` markers in `undo_service`.

## Design
- **Schema (recreation, confirmed).** Add `undo_floor_message_id INTEGER NOT NULL DEFAULT 0` to the `sessions` table in `_SESSION_SCHEMA_TEMPLATE`. Because `session.sqlite` has no incremental migration mechanism and the recreation approach was confirmed on 2026-10-14, the column exists only in newly recreated DBs; production recreation is out of scope. Default 0 means "never compressed", matching the `message_id` domain (`INTEGER PRIMARY KEY AUTOINCREMENT`).
- **Atomic boundary update.** `SessionMessageRepository.replace_messages()` already runs DELETE + INSERT in one transaction. Extend it to `UPDATE sessions SET undo_floor_message_id = (SELECT MAX(message_id) FROM messages WHERE session_id = ?) WHERE session_id = ?` in that same transaction, after the INSERT. The early `if not messages: return` is preserved; the boundary is updated only when a snapshot is actually written. Both compression callers (`conversation_state_manager.handle_history_compression`, `cmd_rag_export._cmd_compact`) call `ctx.session.replace_messages()`, so they share one boundary-updating path.
- **Facade surface.** `AgentSession.replace_messages()` returns the boundary `message_id | None`; callers set `ctx.conv.undo_floor` after a successful write.
- **In-memory floor lifecycle.** `ConversationState.undo_floor: int = 0` (index into `history`; 0 = no boundary). Set after a successful snapshot write in the compression callers; reset to 0 in `clear_conversation()` for both `/clear` and `/clear new` (new session starts uncompressed).
- **Restore conversion.** `fetch_messages()` additionally returns the stored `undo_floor_message_id`. `restore_session()` converts the boundary row ID into a history index by matching role/content within the restored history (robust to ephemeral/memory-injected rows that may be absent), and sets `ctx.conv.undo_floor`.
- **DB-first, boundary-gated undo.** `undo_service.undo_last_turn()` now: (1) searches the last user message only at index >= `ctx.conv.undo_floor`; if none, raises a block signal and changes nothing; (2) calls `session.undo_last_turn()`, which deletes in the DB first, restricted to `message_id > sessions.undo_floor_message_id` read from the DB, then reports rows deleted; (3) trims `ctx.conv.history` only after the DB delete succeeds. This ordering guarantees a failed DB delete leaves history unchanged.
- **DB-level enforcement independent of in-memory floor.** `AgentSession.undo_last_turn()` always includes `AND message_id > undo_floor_message_id` in the DELETE, so rows at or before the boundary are never deleted even when `ctx.conv.undo_floor` is forced to 0.
- **Result shape.** `UndoResult` drops the summary-warning semantics; it carries a block indicator/reason so `_cmd_undo` can print the compression-boundary message. Never-compressed sessions keep the existing success message.
- **Removal.** `AgentSession.delete_last_turn()` has no production caller; delete it and its tests. No compatibility shim.

## Risks
- **Risk**: Removing `AgentSession.delete_last_turn()` breaks a caller outside `scripts/` (tests, docs, or an external consumer) that the in-repo grep cannot see. → **Mitigation**: Grep the whole repo for `delete_last_turn` before deleting; REQ-008 asserts zero references in code, tests, and docs; no compatibility shim is added (constraint), so any surviving reference fails the grep and halts the step.
- **Risk**: Changing `SessionMessageRepository.fetch_messages()` from a 2-tuple `(messages, session_found)` to include the boundary breaks every existing caller (`session.py` facade, `session_restore.restore_session`). → **Mitigation**: Enumerate all callers via `rg "from <module> import|import <module>"` and `rg "\.fetch_messages\("` before the change; update each caller in the same step; add a test asserting the new return shape.
- **Risk**: The boundary UPDATE must land in the same transaction as the snapshot rewrite; if it runs in a separate statement, a crash between INSERT and UPDATE leaves a rewritten snapshot with a stale boundary. → **Mitigation**: Emit the `UPDATE sessions SET undo_floor_message_id = (SELECT MAX(message_id) ...) ` as the final statement inside the existing single transaction; the acceptance criterion "a failure inside the snapshot rewrite changes neither snapshot nor boundary" verifies atomicity.
- **Risk**: On `/session load`, deriving `ctx.conv.undo_floor` from a row count is wrong because `_ephemeral` / `_memory_injected` messages can exist in history without a DB row (constraint). → **Mitigation**: Convert the stored boundary row ID into a history index by matching role/content within the restored history (robust to ephemeral/memory-injected rows); see UNK-02 resolution path and `message_schema.py` as a Reference File.
- **Risk**: An incorrect or zero in-memory `ctx.conv.undo_floor` could over-delete if it were authoritative. → **Mitigation**: The DB-level `AND message_id > undo_floor_message_id` filter in `AgentSession.undo_last_turn()` is authoritative; the in-memory floor is only a convenience gate, so a forced-zero floor still cannot delete at-or-before the boundary (acceptance criterion).
- **Risk**: Tests open the production `session.sqlite` and corrupt it. → **Mitigation**: All tests run against the sandbox config using patched `build_db_config` and a fake `SQLiteHelper` backed by in-memory SQLite, following the existing isolation pattern in `tests/agent/test_agent_session.py`; never touch `/opt/llm`.
- **Risk**: Production `session.sqlite` recreation (out of scope here) loses sessions, messages, and diagnostics. → **Mitigation**: Out of scope for this Plan; the lossy recreation and memory recovery from JSONL are documented in `deployment_01` (Upgrade note) as a separate deployment task; this Plan only adds the column to newly recreated DBs.
- **Risk**: `undo_service.undo_last_turn()` trimming history before the DB delete reintroduces the history/DB inconsistency the issue reports. → **Mitigation**: Enforce DB-first ordering in the reworked service — delete in the DB via `session.undo_last_turn()`, then trim history only after the delete succeeds; a failed DB delete leaves history unchanged (acceptance criterion).
