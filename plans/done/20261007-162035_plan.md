## Goal
- Make git-mcp reject force-push ref forms through the `branch` argument and evaluate the protected-branch rule against the branch an operation actually changes (the destination), so protected branches cannot be force-updated via the branch argument while a still can leave a protected branch.

## Priority
High

## Scope
- **In-Scope**:
  - Replacing the reject-list ref validator with an allow-list validator equivalent to `git check-ref-format --branch` for the write-operation `branch`/`remote` arguments.
  - Routing the protected-branch decision to the operation destination: argument branch for `git_pull`/`git_push`, switch target for `git_checkout`, current HEAD for `git_add`/`git_commit`.
  - Limiting the Stage 3 "HEAD is protected" rejection to `git_add`/`git_commit` so `git_checkout` can leave a protected branch.
  - Making `branch` required (non-empty) in the `git_pull`/`git_push` JSON schemas and Pydantic models, fixing their descriptions, and removing the unreachable `or state.active_branch` in `format_push()`.
  - Passing `protected_branches`, `requested_branch`, and `active_ref` to `WriteProtectionPipeline.run()` so the Stage 5b re-check and the checkout postcondition receive their inputs.
  - Taking a single `RepositoryState.snapshot()` in the server and passing it down.
  - Reporting the actually-rejected branch name in protected-branch errors.
  - Removing the duplicated compatibility guards (`_check_repo_path`, `_is_safe_ref`, `_check_protected_branch`) and `RepoValidationResult`.
  - Adding the rejection tests first, then the fix; updating ADR-012, the ADR index INV-01..INV-04 verification status, and the git-mcp catalog doc.
- **Out-of-Scope**:
  - Audit record and error-path changes (tracked in the separate git-mcp audit/error-path issue).
  - Moving blocking git work off the event loop (separate issue).
  - Idempotency cache changes.
  - Changing read-only tool behavior beyond avoiding regression.
  - Force-Push as an administrative capability (ADR-012 Decision Details #3).

## Background
Source: local investigation notes (memo1.md, ISSUE-02), consolidating MCP-004 (raised from Low to High), MCP-002, and two earlier findings. ADR-012 makes server-side protection of protected branches its central control; its Rationale states that removing a force option from the schema is not a control if the branch argument can reach the same effect. The git-mcp catalog doc `docs/22_mcp/mcp_04_05_git.md` documents the current partial guard under "Command-specific guard status: partially implemented" and "Protected branch authority".

## Problem
- `_validate_ref()` in `GitService` rejects only values starting with `-` and values containing NUL or newline (`scripts/mcp_servers/git/git_service.py`, `_validate_ref`). Values like `+main`, `feature:main`, `HEAD:main`, `refs/heads/main` pass both `_validate_ref()` and `_validate_protected()` and reach `format_push()`, which runs `git push <remote> -- <branch>`; arguments after `--` are still parsed by GitPython as refspecs, so `+main` force-updates the remote main.
- Protected-branch checking exists in two places with different subjects: `GitService._validate_protected()` compares the branch *argument* by exact string match, while `RepositoryState.verify_authorization()` (Stage 3) checks the *current HEAD*.
- When HEAD is on a protected branch, Stage 3 rejects every write tool including `git_checkout`, so the tool cannot leave the protected branch.
- `git_pull`/`git_push` schemas make `branch` optional (empty = current branch), but `_validate_protected("")` always rejects an empty branch, and the Pydantic models default `branch` to `""` — a contract contradiction (MCP-002).
- `WriteProtectionPipeline.run()` already accepts `protected_branches`/`requested_branch`/`active_ref` parameters but `GitService._run_tool()` never passes them, so the Stage 5b re-check uses stale/empty inputs and part of the checkout postcondition does not run.
- `RepositoryState.snapshot()` is taken three to four times per dispatched write call (`_run_tool` once, plus a re-check and a post-state snapshot inside `WriteProtectionPipeline.run()`, plus one refresh snapshot in `format_checkout()`), letting the audited state drift from the state used for the decision.
- The protected-branch error message hard-codes `'main'` (`GitService._check_protected_branch()`); the real rejected branch is never reported.

## Reason for change
- Force-pushing a protected branch is the exact threat ADR-012 exists to prevent, and it is currently reachable through the `branch` argument.
- The check inspects the wrong subject: it does not protect the destination, yet it blocks the harmless escape from a protected branch.
- A schema default that always fails is a contract contradiction that teaches the LLM wrong calling patterns.
- The TOCTOU re-check was built but receives no inputs, so it provides no protection.
- Repeated snapshots let the audited state differ from the state used for the decision.

## Implementation intent
- One consistent model: the caller names the branch to modify, and the protected-branch decision is made against that destination. Refs are accepted only as simple branch names via an allow-list, not by rejecting known-bad characters. From a protected branch, read operations and checkout to an unprotected branch remain possible.

## Requirements
- `REQ-001`: `git_pull`/`git_push`/`git_checkout` MUST reject a `branch` argument that is not a simple branch name, using an allow-list equivalent to `git check-ref-format --branch`: reject `+`, `:`, `^`, `~`, `?`, `*`, `[`, backslash, `..`, `@{`, whitespace, control characters, values starting with `refs/`, and `HEAD`; `git_pull`/`git_push` MUST also validate the `remote` name against a conservative pattern. (`scripts/mcp_servers/git/git_service.py`) — Acceptance 1. The existing `_validate_ref()` calls on the READ tools (`git_log` `branch`, `git_diff` `commit`, `git_show` `ref`) MUST be left on the current option-injection-only check — the allow-list applies to write-operation `branch`/`remote` arguments only, so `git_show`'s default `ref="HEAD"` and tag refs are not regressed.
- `REQ-002`: The protected-branch decision MUST be evaluated against the operation destination by the authoritative Stage 3 check (`WriteProtectionPipeline.verify_authorization()`): the argument branch for `git_pull`/`git_push`, the switch target for `git_checkout`, and the current HEAD for `git_add`/`git_commit`, with names normalized before comparison. The pre-pipeline `_validate_protected()` is retained as an early-rejection layer (defense in depth) but the Stage 3 check alone must reject a protected destination even if the pre-pipeline check is bypassed. (`scripts/mcp_servers/git/git_service.py`, `scripts/mcp_servers/git/repository_state.py`) — Acceptance 1, 2
- `REQ-003`: Because Stage 3 evaluates the *destination*, `git_checkout` away from a protected branch (target = unprotected branch) is allowed; only checkout *into* a protected branch is rejected. (`scripts/mcp_servers/git/repository_state.py`) — Acceptance 2
- `REQ-004`: `branch` MUST be required (non-empty) in the `git_pull`/`git_push` JSON schemas (`git_tools.py`) and Pydantic models (`git_models.py`), their descriptions MUST be corrected, and the unreachable `or state.active_branch` fallback in `format_push()` MUST be removed. (`scripts/mcp_servers/git/git_tools.py`, `scripts/mcp_servers/git/git_models.py`, `scripts/mcp_servers/git/format_output.py`) — Acceptance 3
- `REQ-005`: `GitService._run_tool()` MUST pass `protected_branches`, `requested_branch`, and `active_ref` to `WriteProtectionPipeline.run()` so the Stage 5b re-check and the checkout postcondition receive their inputs. (`scripts/mcp_servers/git/git_service.py`, `scripts/mcp_servers/git/repository_state.py`) — Acceptance 4
- `REQ-006`: Exactly one `RepositoryState.snapshot()` MUST be taken per dispatched call in `_run_tool()` and passed down to the pipeline; the two in-pipeline snapshots (the Stage 5b re-check and the post-state snapshot in `WriteProtectionPipeline.run()`) MUST be removed. (`scripts/mcp_servers/git/git_service.py`, `scripts/mcp_servers/git/repository_state.py`)

## Design
Path B (affects > 3 files, changes runtime-facing service contracts). Analysis depth per `workflow-path-b.md`: architecture, dependency graphing, historical, operational — none surfaced a blocking finding; the git-mcp module is self-contained and its tests are co-located.

**Ref validation model.** Replace `GitService._validate_ref()` reject-list with an allow-list helper `_validate_ref_allowlist(ref)` returning `(ok, message)`. A ref is accepted only if it matches a simple-branch-name pattern and contains none of the rejected tokens (`+`, `:`, `^`, `~`, `?`, `*`, `[`, backslash, `..`, `@{`, whitespace, control chars) and does not start with `refs/` or equal `HEAD`. `remote` is validated against a conservative `[A-Za-z0-9._-]+` pattern. This helper is used for the write-operation `branch`/`remote` arguments. Read-tool ref args keep the current minimal option-injection check; extending the allow-list to read tools is explicitly deferred because `git_show` defaults `ref` to `HEAD`, which the allow-list would reject, and the constraint forbids read-tool regression.

**Destination-based protected-branch decision.** One normalized comparison: normalize both the configured list and the target name to `refs/heads/<name>` (lowercase) via the existing `_normalize_branch_name()`. For `git_pull`/`git_push` the target is `req.branch`; for `git_checkout` the target is the switch target; for `git_add`/`git_commit` the target is the current HEAD. `_validate_protected()` is kept as the pre-pipeline destination check for pull/push/checkout; the Stage 3 check covers commit/add.

**Stage 3 scoping.** `verify_authorization()` gains the operation context (tool name, `requested_branch`, `active_ref`, `protected_branches`) and evaluates protection against the *destination*: `requested_branch` when present (pull/push/checkout) or the current HEAD otherwise (commit/add). This makes Stage 3 the single authoritative protected-branch check (satisfying "rejected at Stage 3 even when the pre-pipeline check is bypassed") while allowing checkout away from a protected branch (target = unprotected branch is not protected). The pre-pipeline `_validate_protected()` is retained as an early-rejection layer. INV-03 holds for all tools: checkout *into* a protected branch is rejected because its destination is protected.

**Pipeline inputs.** `GitService._run_tool()` already builds `RepositoryState`; pass `self._protected_branches`, the per-tool `requested_branch`, and `active_ref` into `WriteProtectionPipeline.run()`. The Stage 5b re-check and `verify_postcondition()` then operate on real inputs.

**Single snapshot.** Take one `RepositoryState.snapshot()` in `_run_tool()` and remove the two in-pipeline snapshot calls (`run()` lines 342 and 367), passing the same `state` through. The Stage 5b re-check keeps comparing `is_detached_head` (a property) rather than `active_branch`, consistent with the existing comment about test doubles.

**Branch required.** `git_pull`/`git_push` schemas set `branch` in `required` and drop `default: ""`; the Pydantic models set `branch: str = Field(..., ...)`. `format_push()` no longer needs `req.branch or state.active_branch` since `req.branch` is always present.

**Duplicated guards.** `_is_safe_ref()` and `_check_protected_branch()` in `GitService` have zero callers (confirmed via `rg`) and are removed. `RepoValidationResult` is referenced only inside `git_service.py` and is removed together with a rewrite of `_validate_repo()` (which currently returns `RepoValidationResult` and is consumed by `_run_tool`). `_check_repo_path()` is NOT removed: it has active test callers (`TestCheckRepoPath` in `test_mcp_git.py`, and the compliance suite), so removal would break those tests; its redundancy with `_is_within_allowed_paths()` is a reconciliation question (retain, or fold into `_is_within_allowed_paths()` with a test update) flagged as `Needs confirmation`. `GitSecurityGuards` in `git_security.py` is already off the request path and is left as a reference file.

## Risks
- **Risk**: Changing `verify_authorization()` and `WriteProtectionPipeline.run()` signatures breaks many existing tests (the `test_repository_state.py` suite references `verify_authorization` ~17 times and constructs snapshots directly). → **Mitigation**: Update those tests in the same change (REQ-003, REQ-005 test rows); measure blast radius up front with `rg -c '\bverify_authorization\b' tests/` and `rg -c 'RepositoryState.snapshot' tests/` and budget the test updates as part of this unit.
- **Risk**: Making `branch` required in `git_pull`/`git_push` changes the public MCP contract; any caller relying on the empty-branch default will now fail schema validation. → **Mitigation**: The Issue requires this (MCP-002); update affected tests and document the new required field in the catalog doc. No backward-compat shim (repository policy).
- **Risk**: An over-strict allow-list could reject legitimate simple branch names containing characters like `-` or `.`. → **Mitigation**: Model the allow-list on `git check-ref-format --branch` and validate against a live temporary repository (Test 2) before finalizing; keep the reject set to the Issue's enumerated tokens plus the structural rules.
- **Risk**: Removing guards/`RepoValidationResult` could break callers. `_is_safe_ref` and `_check_protected_branch` are dead on the request path (zero production callers) but DO have test callers in `tests/mcp_servers/git/test_git_security_compliance.py` (`test_is_safe_ref` lines 49-53, `test_check_protected_branch` lines 55-62); a `rg` limited to `scripts/` misses these. `RepoValidationResult` is referenced only inside `git_service.py`. `_check_repo_path()` has active test callers (`TestCheckRepoPath`, compliance suite) — removing it would break ~14 test sites. → **Mitigation**: Resolve UNK-03 first (scope decision): either retain `_is_safe_ref`/`_check_protected_branch` (like `_check_repo_path`, because they are tested) and remove only `RepoValidationResult` (with a `_validate_repo()` rewrite), or remove them together with the two test methods in `test_git_security_compliance.py` (which adds that test file to scope). Run the full git-mcp test suite in Step 10 and fix any breakage.
- **Risk**: UNK-01 — real GitPython `git push -- <form>` behavior may differ from the Issue assumption. → **Mitigation**: Confirm against a temporary repository during implementation; stop and report per the Issue's AI instruction if it differs.
