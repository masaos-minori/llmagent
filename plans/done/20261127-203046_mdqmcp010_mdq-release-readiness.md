# Finalize MDQ fence semantics, production criteria, test classification, and response-model cleanup

## Goal
- Lock the Markdown feature subset the MDQ parser actually supports, so the tool descriptions state it and golden tests pin it; define measurable production-readiness criteria for mdq-mcp and add a reproducible benchmark harness that can measure them; classify the 38 MDQ test modules (35 at the evidence revision, 3 added by the rebase) as contract or characterization so CI can separate authoritative assertions from recorded behavior; and remove the response models that no production code produces.

## Priority
Low

## Scope
- **In-Scope**:
  - The fence-content decision applied as the plan default: fenced content stays excluded from the searchable section body, the parser docstring states it, and the `search_docs` and `grep_docs` descriptions state the supported feature subset.
  - Golden tests for Python, JSON, shell, and Mermaid fences, and for the search exclusion of fence-only content.
  - Production-readiness criteria for integrity, security, observability, performance, and recovery, expressed as measurable conditions, plus the process for changing a tool's status.
  - A benchmark harness that measures p50/p95/p99 for search, grep, index, refresh, and rebuild across chunk count, database size, chunk length, and concurrency, and prints a report.
  - Test-taxonomy markers on every MDQ test module, the requirement citation for each contract module, and the MDQ area added to the taxonomy checker's classified areas.
  - Removal of the response models with no producer, including the empty `IndexMetadata` placeholder, and a guard test that fails when a model in `mdq_models.py` has no production consumer.
  - Documentation for the fence decision, the production criteria and measured scale, the status-change process, and the `disabled_reason` fallback semantics.
- **Out-of-Scope**:
  - Behavior changes owned by the mdqmcp001 through mdqmcp009 plans: this Plan changes no parser, result, error, schema, or scope behavior.
  - Changing any tool's `status` value: the criteria are defined, the status stays as declared until the thresholds are agreed.
  - Adding `status` validation to `validate_tool_schema_v2()`: the closed-vocabulary gap is recorded, not fixed here.
  - Changing the `disabled_reason` fallback in `scripts/shared/runtime_tool_registry.py`: the semantics are documented, the pinned tests are not touched.

  - Any ADR decision change (an ADR change needs a maintainer approval record; this Plan does not write or simulate one).

## Problem
The parser's supported subset is documented but not stated by the tools a client discovers, and nothing pins it. Production status is asserted without criteria, and the status field has no closed vocabulary or change process. The CI taxonomy gate cannot judge MDQ because no MDQ module is classified. Nine response models declare shapes no production code produces, which reads as a contract.

## Reason for Change
These are the last MDQ items and the only ones that can be settled without changing behavior: they lock the semantics the earlier plans define, make the production claim evidence-based, and remove a false contract before the implementation procedures are generated. Doing them before the behavior contracts settle would cause drift, as the issue states.

## Implementation Intent
Keep the documented fence semantics and pin them with golden tests rather than changing them. Define the production criteria as measurable conditions that existing contract tests already satisfy for integrity, security, and observability, and leave the numeric performance thresholds and the recovery measurement to the owner. Classify every MDQ module by whether its assertions trace to a requirement source, and let the checker's classified-area list cover MDQ. Delete the models that have no producer and add a guard that keeps the module free of them.

## Requirements
- `REQ-001`: The fence-content decision is stated in one place and pinned: `parser.py`'s feature list states that fenced content is excluded from the section body, `search_docs` and `grep_docs` descriptions state the supported feature subset, and golden tests for Python, JSON, shell, and Mermaid fences pin both the heading rule and the search exclusion. No parser behavior changes.
- `REQ-002`: Production status for mdq-mcp is defined by measurable criteria for integrity, security, observability, performance, and recovery, and the process for changing a tool's status is documented. A reproducible benchmark harness measures p50, p95, and p99 for search, grep, index, refresh, and rebuild by chunk count, database size, chunk length, and concurrency, and prints a report. No tool's status value changes until the thresholds are agreed.
- `REQ-003`: Every MDQ test module carries exactly one taxonomy marker, each contract module carries a requirement citation, and `tools/check_test_taxonomy.py` classifies `tests/mcp_servers/mdq` as a classified area.
- `REQ-004`: Every model in `scripts/mcp_servers/mdq/mdq_models.py` has a production consumer. The 9 unreferenced response models and the empty `IndexMetadata` placeholder are removed, and a guard test fails when a model in the module has no consumer in `scripts/`.
- `REQ-005`: Documentation records the fence decision, the production criteria and the measured scale, the status-change process, and the `disabled_reason` fallback semantics, in the documents named by `docs/00_index.md`'s task mapping.

## Design
- Fence semantics are not changed. The parser already excludes fence content from the section body, the docs already state it, and one test already asserts it. The Plan closes three gaps: the parser's own feature list does not state the exclusion, the tool descriptions state no feature subset, and no golden test pins the four fence languages. Keeping the behavior is the plan default because changing it would be a behavior change, which the issue excludes.
- Production criteria are expressed as measurable conditions rather than as a status vocabulary change. Integrity, security, and observability are already covered by contract modules (`test_mdq_foreign_keys.py`, `test_mdq_path_jail.py` and `test_auth.py`, `test_mdq_health_posture.py`), so the criterion for those areas is that the module passes. Performance and recovery need numbers the owner has not agreed, so the Plan defines the measurement shape (p50/p95/p99 by chunk count, database size, chunk length, and concurrency) and leaves the thresholds as an Unknown. Alternatives considered: (a) mark the write tools `beta` until the thresholds are met — rejected, it changes a declared status value with no agreed process and contradicts `tests/mcp_servers/mdq/test_mdq_metadata_consistency.py`, which pins `production` for all 7 tools; (b) add a closed status vocabulary to `validate_tool_schema_v2()` — rejected here, it changes the schema-2.1 contract and needs the contract owner (UNK-04).
- The benchmark harness measures and reports; it asserts nothing until the thresholds exist. It is classified as `characterization` because it records observed measurements with no requirement source, and it flips to `contract` when the thresholds are agreed. It is marked `benchmark`, which requires the marker registration in `pyproject.toml`. Under CI's `-n logical` run the plugin disables itself, so the harness is an on-demand measurement, not a CI gate (UNK-07).
- Test classification follows the governance rule: a module is `contract` when its assertions trace to a requirement source and carry the citation. 16 of the 35 MDQ modules are contract (security and authorization, error taxonomy, tool metadata and schema, routing and layer consistency, foreign keys, the RAG boundary, health posture, config degradation, and the search count and limit rules); the other 19 are characterization. The citation names `REQ-003` because the MDQ canonical doc is not a registry-registered source (Assumptions). No MDQ module is added to `tools/test_taxonomy_baseline.txt`, because the baseline is for modules that cannot be classified, and every MDQ module can be. ## Risks
- **Risk**: the golden tests lock the fence exclusion, so if the owner decides fenced content should be searchable the tests must be flipped and the parser changes → **Mitigation**: the decision is recorded as an Unknown; the tests assert the documented semantics, and a flip is a behavior change owned by another plan, not by this one.
- **Risk**: adding `tests/mcp_servers/mdq` to `CLASSIFIED_AREAS` makes CI fail for any MDQ module without a marker → **Mitigation**: the markers land in the same commit as the classified-area change (declared as a release unit); the baseline stays free of MDQ entries.
- **Risk**: the harness produces no measurements under CI's `-n logical` run, so a printed report could be read as evidence of the measured scale → **Mitigation**: the harness asserts nothing, the docs record the measured scale only from a run made outside xdist, and the CI question is recorded as an Unknown.
- **Risk**: removing the response models deletes shapes a downstream consumer could import dynamically → **Mitigation**: no reference exists in `scripts/`, `tests/`, or `docs/` at the evidence revision, and the guard test fails if a definition without a consumer is added.
- **Risk**: the 7 citation additions change test docstrings only, but a citation naming `REQ-003` points at the classification requirement rather than at the contract's own normative source, because the MDQ canonical doc is not registry-registered → **Mitigation**: the citation form is recorded as an assumption; if the owner registers the MDQ doc in the Canonical Source Registry, the citations can be repointed without changing the classification. The 16 contract modules that already carry an accepted citation are not changed by this Plan.
- **Risk**: the production criteria for recovery cannot be measured, so the documented criteria would read as satisfied when they are not → **Mitigation**: the criteria section records recovery as unmeasured with the reason, and no tool's status is justified by it (UNK-05).
- **Risk**: this Plan consumes documents that open plans also modify → **Mitigation**: ordering recorded in the `Depends on` bullets; the Plan adds sections rather than restating claims owned by another plan.
