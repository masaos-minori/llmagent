## Goal
Refactor `scripts/agent/factory.py` to reduce complexity by splitting `_ServerLifecycleRouter`, removing dead code, standardizing builder function patterns, and improving type safety — all while preserving the `LifecycleManagerProtocol` contract and public behavior.

## Priority
Medium

## Scope
- **In-Scope**:
  - Remove unused `_COOLDOWN_TIMEOUT_SEC` constant
  - Split `_ServerLifecycleRouter` into two classes (coordinator + subprocess manager)
  - Replace private `_http_procs` access with existing `verify_running()` call
  - Standardize builder function return types (single typed values instead of tuples)
  - Fix `object` type annotations in memory builders with proper generics
  - Update affected tests for new class architecture
  - Update module docstrings to reflect new architecture
- **Out-of-Scope**:
  - Refactoring `HttpServerLifecycleManager` itself (already well-separated)

  - Adding new features or changing service initialization order
  - Refactoring memory layer builders beyond type annotation fixes
  - Modifying `docs/*.md` files

## Background
`factory.py` is the central assembly point for AgentContext services. It contains `_ServerLifecycleRouter` (~200 lines, 16 methods covering 6 distinct responsibilities), seven `_build_*` helper functions, and the main `build_agent_context()` orchestrator. The module has accumulated complexity through incremental additions without architectural review. Adversarial validation confirmed all five claims in the Issue: dead code, SRP violation, inconsistent builder patterns, god function, and private attribute access.

## Problem
The module has five concrete problems:
- Dead constant `_COOLDOWN_TIMEOUT_SEC` is defined but never referenced anywhere in the codebase.
- `_ServerLifecycleRouter` violates SRP: it manages lifecycle states, cooldown logic, subprocess coordination, process snapshots, resource cleanup, and config filtering — six distinct responsibilities in one class.
- Builder functions have inconsistent return patterns: some return tuples (`_build_llm_client`, `_build_tool_executor`, `_build_history_manager`), others return single values. Memory builders use `object` type annotations instead of proper generics.
- `build_agent_context()` is a god function that sequentially wires all services without clear responsibility boundaries.
- `_ServerLifecycleRouter` accesses private attributes (`self._http_mgr._http_procs`) from outside its owning module, breaking encapsulation — though `HttpServerLifecycleManager` already exposes a public `verify_running()` method serving this purpose.

## Reason for change
This refactor reduces cognitive load for future contributors, eliminates dead code that confuses readers, and makes the service assembly pipeline more testable by isolating each builder into a clearly bounded unit. No behavioral change is required — this is purely structural.

## Implementation intent
Apply these changes in order, each preserving public behavior:

1. **Remove dead code**: Delete `_COOLDOWN_TIMEOUT_SEC`. Keep `_COOLDOWN_SECONDS` as the sole cooldown constant.

2. **Split `_ServerLifecycleRouter`**: Extract subprocess lifecycle methods (`ensure_ready`, `start_http_subprocess`, `restart`, `shutdown_idle`) into a new `_SubprocessLifecycleManager` class. Keep state/cooldown logic in `_ServerLifecycleRouter` as a coordinator. Both implement `LifecycleManagerProtocol`.

3. **Replace private attribute access**: In `_ServerLifecycleRouter.start_http_subprocess()`, replace `self._http_mgr._http_procs.get(server_key)` with `self._http_mgr.verify_running(server_key)` — `HttpServerLifecycleManager` already exposes this public method.

4. **Standardize builder patterns**: Each `_build_*` function should return a single typed value (not a tuple). For multi-return builders (`_build_llm_client`, `_build_tool_executor`, `_build_history_manager`), introduce named dataclasses for multi-value returns.

5. **Fix memory builder type annotations**: Replace `object` type annotations in `_build_embedding_client`, `_build_jsonl_store` with proper generic bounds.

6. **Update tests**: Tests currently instantiate `_ServerLifecycleRouter` directly and inject mocks via `router._http_mgr`. After the split, tests must work with the new architecture where `_SubprocessLifecycleManager` owns subprocess operations.

## Design
### Architecture decisions

1. **Two-class split for `_ServerLifecycleRouter`**: Extract subprocess lifecycle methods into `_SubprocessLifecycleManager`. Keep state/cooldown logic in `_ServerLifecycleRouter` as coordinator. Both implement `LifecycleManagerProtocol`.

   Rationale: The issue identifies six distinct responsibilities in `_ServerLifecycleRouter`. Subprocess operations (`ensure_ready`, `start_http_subprocess`, `restart`, `shutdown_idle`) are conceptually separate from state management (`_set_state`, `get_transport_state`) and cooldown logic (`_in_cooldown`). The coordinator delegates subprocess operations to `_SubprocessLifecycleManager`, which owns the actual subprocess lifecycle.

2. **Use existing `verify_running()` method**: Replace private `_http_procs` access with `self._http_mgr.verify_running(server_key)` — no new method needed.

   Rationale: Adversarial validation confirmed `HttpServerLifecycleManager` already has a public `verify_running(server_key: str) -> bool` method at line 134 that does exactly what the proposed `is_running()` would do. Adding a new method would be redundant.

3. **Dataclass wrappers for multi-return builders**: Introduce named dataclasses for `_build_llm_client`, `_build_tool_executor`, `_build_history_manager` instead of returning tuples.

   Rationale: Tuple returns make it impossible to track which caller consumes which element. Dataclasses provide explicit field names and improve type safety. Example:
   ```python
   @dataclass
   class LlmClientResult:
       http: httpx.AsyncClient
       llm: LLMClient
   ```

4. **Generic type bounds for memory builders**: Replace `object` with `TypeVar` constraints where possible.

   Rationale: `_build_retriever[T]` already uses generics properly. Other builders like `_build_embedding_client` and `_build_jsonl_store` return `-> object` which loses type information. Use `TypeVar` with appropriate constraints or keep `object` only where the return type is truly dynamic (depends on injected class parameter).

### Protocol design

The Issue's Implementation Intent #2 states both classes should implement `LifecycleManagerProtocol`. However, this creates a question: should `_SubprocessLifecycleManager` have its own protocol, or should both share `LifecycleManagerProtocol`?

If both share `LifecycleManagerProtocol`:
- `_SubprocessLifecycleManager` must implement all 9 methods of the protocol
- Some methods (e.g., `cleanup_server_resources`, `get_process_snapshot`) are not relevant to subprocess-only management
- The coordinator pattern becomes less clear

Alternative: create a narrower `_SubprocessLifecycleProtocol` that only includes subprocess-relevant methods, and have `_ServerLifecycleRouter` delegate to it.

This is an open architectural decision (UNK-01) that should be resolved during implementation.
