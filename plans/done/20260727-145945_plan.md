## Assumptions

1. The production sqlite-vec build at `/opt/llm/sqlite-vec/vec0.so` (VERSION `0.1.10-alpha.4`) is representative of what runs in all environments that exercise `memories_vec`/`chunks_vec` (dev/test may use a different pip-installed `sqlite-vec` if present, but no such package is currently pinned in `requirements.txt`/`pyproject.toml`/`uv.lock`).
2. The `distance_metric=` clause syntax parsed at `sqlite-vec.c:3066` in the installed build is stable/supported syntax for this version and will not error when added to the `CREATE VIRTUAL TABLE` statement.
3. Because the confirmed default (L2) already matches what the schema silently used before, adding the explicit clause is a no-op with respect to search result ordering — no ranking regression is expected.
4. `chunks_vec`'s runtime default is also L2 (same `vec0` module, same missing clause, same binary) even though this was not separately empirically re-tested in this cycle (only source-confirmed by symmetry) — see UNK-02.

## Risks

- **Risk**: The `distance_metric=L2` clause syntax may not be accepted by the specific installed build (`0.1.10-alpha.4`, a custom source build newer than pip's 0.1.9) if its syntax diverges from upstream → **Mitigation**: Verify the clause against `sqlite-vec.c:3066`'s parsing logic (or run a quick isolated `CREATE VIRTUAL TABLE` smoke test with the clause, mirroring `scratchpad/test_vec0_distance.py`) before editing `schema_sql.py`, during Phase 1
- **Risk**: No sqlite-vec version is pinned in `requirements.txt`/`pyproject.toml`/`uv.lock`, so a CI or contributor environment could load a different `sqlite-vec` build than the production `/opt/llm/sqlite-vec/vec0.so` tested here, with a different default or clause syntax → **Mitigation**: Keep the new test gated behind the existing `@pytest.mark.skipif(not _VEC_AVAILABLE, ...)` pattern so it degrades gracefully; flag the missing version pin as a separate, out-of-scope follow-up (not fixed by this plan)
- **Risk**: Embeddings inserted into `memories_vec` are not normalized to unit length (confirmed via `scripts/agent/memory/mapper.py:35-44` and `embedding_client.py`), so L2-based `MemoryHit.score` is magnitude-sensitive and may not match a naive "cosine similarity" mental model held by downstream consumers → **Mitigation**: This plan does not change embeddings or scoring; it only documents the confirmed metric in the comment (Implementation Step in Phase 2) so future consumers are aware of the magnitude sensitivity — normalization itself is explicitly out-of-scope and should be raised as a separate requirement if downstream ranking correctness becomes a problem
- **Risk**: Changing `chunks_vec` without empirically confirming its runtime metric (UNK-02) could introduce an incorrect `distance_metric=` clause that silently changes RAG search ordering → **Mitigation**: Treat `chunks_vec` as conditional/optional in this plan; only proceed with it in the implementation phase if UNK-02's empirical test (Phase 1) confirms L2, otherwise defer `chunks_vec` to a separate follow-up requirement
