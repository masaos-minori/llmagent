## Background
This Plan follows the same Implementation-Notes classification review that
produced the ADR-004, ADR-006, and 13-ADR file-list Plans earlier this session.
This issue is a judgment-call item: whether ADR-007's Circuit Breaker Note
should be promoted to an Invariant depends on a repository-wide fact (does
other code depend on the specific state names) that the issue's own drafting
explicitly deferred to implementation time.

## Problem
`docs/adr/ADR-007-http-mcp-adoption-and-stdio-non-support.md`'s `## Implementation
Notes` (current line 338, re-confirmed at Plan creation — this line survived
this session's earlier common-pattern file-list cleanup, which explicitly
preserved it) states "Circuit Breaker: 5-state（HEALTHY → DEGRADED →
UNAVAILABLE → HALF_OPEN → HEALTHY）" while `## Invariants`' `INV-07` only
requires that a Circuit Breaker exist in the shared Transport layer, without
naming the state model. The source issue's central open question — whether
other code depends on the specific state names — is resolved by this Plan's
own investigation (see Design): confirmed yes, four files outside the defining
module reference specific `McpServerHealthState` members directly.

## Reason for change
Per this review's own promotion criterion ("複数実装が同じ制約を守る必要がある"),
a state model that four other files pattern-match against by name
(`McpServerHealthState.DEGRADED`, `.UNAVAILABLE`, `.HALF_OPEN`) is a
cross-implementation constraint: a future refactor renaming or reordering these
states would silently break every one of those callers, with nothing in
`## Invariants` to flag the violation. The source issue's own Constraint
("do not invent a new Invariant... unless the investigation shows it")
is satisfied by this Plan's evidence, not overridden by it.

## Implementation intent
Add a new Invariant describing the actual current state machine accurately
(not the ADR's own "5-state" framing, which double-counts `HEALTHY` as both
the cycle's start and end while never mentioning the real, distinct — but
unused — fifth enum member, `UNKNOWN`; see Design). Add a Verification entry
and a new test, since none currently exists for this state machine's
transitions specifically. Add the corresponding `docs/adr-index.md` row.
Condense the Implementation Notes line into a pointer now that the detail is
promoted.

- **The promotion criterion is met — recorded per the source issue's explicit
  request**: `grep -rn "HEALTHY\|DEGRADED\|UNAVAILABLE\|HALF_OPEN" scripts/`
  found `McpServerHealthState` members referenced in 4 files outside
  `scripts/shared/mcp_health.py`: `scripts/agent/startup_reporter.py`
  (`.DEGRADED`), `scripts/agent/services/mcp_status.py` (`.UNAVAILABLE`),
  `scripts/agent/commands/cmd_mcp.py` (`.DEGRADED`, `.UNAVAILABLE`), and

  source issue's own stated threshold ("more than one component depends on the
  specific names/transitions") — promotion is warranted, not a default
  assumption.
- **The ADR's own "5-state" phrase is imprecise, verified by reading the
  actual enum**: `McpServerHealthState` (`scripts/shared/mcp_health.py:11-18`)
  has 5 *members* (`HEALTHY`, `DEGRADED`, `UNAVAILABLE`, `HALF_OPEN`,
  `UNKNOWN`), but the ADR's "5-state（HEALTHY → DEGRADED → UNAVAILABLE →
  HALF_OPEN → HEALTHY）" lists only 4 *distinct* names, counting `HEALTHY`
  twice (as the cycle's start and end) — it never mentions the real fifth
  member, `UNKNOWN`, which is itself confirmed dead code (`UNK-01`). The new
  Invariant's wording (`REQ-001`) describes the 4 live, actually-transitioned
  states and their real transition rules (read from
  `McpServerHealthRegistry.record_failure()`/`record_success()`/
  `is_unavailable()` in full) rather than copying the ADR's own imprecise
  "5-state" framing forward into a first-class Invariant.
- **No existing test covers the state machine itself**: `tests/agent/test_agent_factory.py`
  and `tests/shared/test_tool_transport_invoker.py` both reference
  `McpServerHealthRegistry`, but only to confirm that `record_failure()`/
  `record_success()` are *called* by the code under test (via
  `MagicMock(wraps=registry.record_failure)`), not that the registry's own
  internal transition logic (threshold counting, cooldown timing, `HALF_OPEN`
  trial semantics) is correct. Per the source issue's own Testing
  Expectations ("add one only if none exists"), `REQ-003` adds a new,
  dedicated test file.
- **Global Invariant ID assignment**: consistent with the `INV-023`–`INV-027`
  precedent already established this session, the new row uses the next
  global sequential ID, `INV-028` (current maximum `INV-027`, confirmed via
  `grep` at Plan creation time — re-verify at implementation time in case
  another change landed a row since).

  first-class Invariant — a worse outcome than leaving it in Implementation
