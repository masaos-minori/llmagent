property its comments claim to enforce.

## Background
Commit `c433c3c68` added per-call idempotency handling to the MCP transport layer (REQ-005,
REQ-006): one UUID is emitted per logical call, sent as the `X-Idempotency-Key` header on
every retry, and write-tool post-send retries were intended to be gated on key presence.
The server side deduplicates via `_duplicate_cache` keyed on `(idempotency_key, tool name,
normalized-args hash)` with a 1h TTL and oldest-first eviction past a fixed entry count.

## Problem
In `HttpTransport.call`, `idempotency_key` is assigned once as `str(uuid.uuid4())`, which is
always a non-empty string. The write guard is written as
`if name in _WRITE_TOOLS and not idempotency_key:`. Because `idempotency_key` is never
empty, `not idempotency_key` is always `False`, so the `raise ... break_flag=True` branch is
unreachable. Control always falls through to the non-breaking `_transport_error(...)` call,
which discards its return value and lets the retry loop continue. Write tools are therefore
retried on a non-timeout `httpx.RequestError`, exactly like read tools.
(`httpx.TimeoutException`, a `RequestError` subclass, is caught earlier and breaks without
retry.) The guard that was supposed to stop blind write retries never runs. This has been
true since the guard was introduced in commit `c433c3c68` — the key is always sent, so the
guard was unreachable from its inception.

## Reason for change
The guard documents a safety property (REQ-006: a write must not be retried without a
server-side dedup key) that the code does not actually enforce. Anyone reading
`http_transport.py` concludes that writes are protected from double execution by this guard;
that conclusion is wrong. The defect is therefore a misleading comment plus dead code, not an
active vulnerability: because the key is always sent, `_duplicate_cache` deduplicates every
write for this transport, so server-side deduplication is the real (and always-engaged)
backstop. The residual question — whether the dedup cache's TTL/eviction could allow a
double execution for a retry arriving after eviction — is open (see Unknowns), not an
established current hazard. The maintenance risk is that future edits may rely on a
client-side backstop that does not exist and make the write path blindly retriable.

## Implementation intent
Adopt option (b): the design is intentionally "key always present, always safe to retry," so
replace the dead branch with an explicit comment stating that writes are always retried on a
non-timeout `httpx.RequestError` and that safety rests on the always-active server-side
`_duplicate_cache`, plus a test asserting writes are retried, so the behavior is deliberate
rather than accidental. Do not adopt option (a) (emitting the key only for write tools) — it
is ruled out by the Constraint that forbids altering the `X-Idempotency-Key` header contract;
only elimination of the dead branch is viable. Do not leave a `raise` branch that cannot be
reached.

## Design
The change is behavior-preserving: the removed branch was provably unreachable because
`idempotency_key` is always a non-empty string, so removing it cannot change observable
behavior. The plan therefore focuses on (1) removing dead code, (2) correcting the
misleading comment, and (3) pinning the behavior with a test.

- **Option (a) rejection**: emitting the key only for write tools would change the
  `X-Idempotency-Key` header contract that `_duplicate_cache` relies on for all-tool
  deduplication, so it is rejected. Only option (b) (eliminate the dead branch) is viable.
- **Test strategy**: mock `httpx.AsyncClient.post` to raise exceptions and count calls;
  assert 3 attempts for a non-timeout `httpx.RequestError` (write and read) and 1 attempt
  for a `httpx.TimeoutException`. Follow the existing conventions in
  `tests/shared/test_tool_transport_invoker.py` (`MagicMock(spec=httpx.AsyncClient)`).
- **Preservation**: the single-per-call key generation and the `X-Idempotency-Key` header
  assignment are untouched.
