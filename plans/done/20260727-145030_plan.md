## Goal

Every `[mcp_servers.<key>]` `cmd` entry in `config/agent.toml` invokes `uv run --no-sync` instead of bare `uv run`, so MCP server subprocess startup never performs implicit dependency resolution/sync against `/opt/llm/pyproject.toml`/`uv.lock`, and instead fails fast if the deployed venv is not already prepared.

## Scope

**In-Scope:**
- Insert `--no-sync` immediately after `"run"` in the `cmd` array of all 10 `[mcp_servers.<key>]` sections in `config/agent.toml` (`shell`, `git`, `web_search`, `file_delete`, `file_write`, `file_read`, `github`, `cicd`, `rag_pipeline`, `mdq`) — currently at lines 299, 311, 320, 329, 338, 347, 364, 373, 382, 394.
- Add/extend a config-level test asserting each subprocess-mode `cmd` list contains `--no-sync` (e.g. extend `tests/test_mcp_server_cmd_paths.py` or add a sibling assertion in `tests/test_mcp_config.py`).
- Manual/smoke verification that an MCP server (e.g. `shell`) still starts successfully with the new flag against the existing synced dev venv, per Acceptance Criteria.

**Out-of-Scope:**
- Any change to `scripts/agent/http_lifecycle.py` (`HttpServerLifecycleManager.start()` already forwards `cfg.cmd` verbatim — confirmed by reading the source; no change needed).
- Any change to `scripts/shared/mcp_config.py` (`McpServerConfig`/`_build_single_server`) — `cmd` is stored as a plain `list[str]`; no schema change required.
- Updating `docs/*.md` deployment runbook notes describing that the venv/lockfile must be fully synced before MCP servers start — explicitly out of scope for this document-only requirement-to-plan phase (flagged as a required follow-up implementation step; see Risks).
- Choosing/adding a code-level guard (e.g. Python assertion) that rejects a missing `--no-sync` flag — the requirement only asks for the `cmd` array change plus a test, not runtime enforcement.

## Assumptions

1. `--no-sync` (not `--frozen`) is the correct flag per the deployment model — confirmed by codebase precedent: `uv run --no-sync <cmd>` is the established pattern used throughout this repo's own validation/test commands (e.g. `plans/done/20260629-144035_plan.md`, `plans/done/20260629-143407_plan.md`, `implementations/done/20260629-174553_agent_mandatory_tool_approval_enforcement.md`) whenever the intent is "assume the venv is already prepared, do not sync/resolve at invocation time." `--frozen` would still allow silent environment mutation (installing missing packages to match a possibly-stale lockfile) without erroring, which does not satisfy the requirement's "fail fast and loudly ... instead of silently mutating it" goal as cleanly as `--no-sync`.
2. The production venv at `/opt/llm` is synced via `uv sync --dev --system-certs` as a distinct deploy step, documented in `docs/02_deployment-part1.md:35` — this confirms the venv-preparation precondition is already met by the existing deploy flow, independent of MCP server startup. `--no-sync` at MCP-server-start time is therefore safe under normal deploy procedure.
3. No other code path outside `config/agent.toml` hardcodes the pre-change `["uv", "run", "--directory", ...]` shape at a fixed index other than `cmd[-1]` (the script path) — confirmed by grep: only `tests/test_mcp_server_cmd_paths.py` inspects `cmd`, and it only reads `cmd[-1]`, so inserting `--no-sync` after `"run"` does not break it.
4. The 10 `[mcp_servers.<key>]` sections currently at lines 299, 311, 320, 329, 338, 347, 364, 373, 382, 394 are the complete and only set of `startup_mode = "subprocess"` entries in `config/agent.toml` — confirmed by grep count (10 matches for `startup_mode = "subprocess"`, all preceded by the 10 named `[mcp_servers.*]` headers listed in the requirement).

## Risks

- **Risk**: Choosing `--no-sync` over `--frozen` could be wrong if the actual deploy tooling does not guarantee `uv sync` runs before every MCP-server-affecting deploy → **Mitigation**: `docs/02_deployment-part1.md:35` already documents `uv sync --dev --system-certs` as a required deploy step; Implementation Step 3 (Phase 3) files a follow-up to make this precondition explicit in the deployment runbook specifically in the context of MCP server startup, closing the gap between "documented" and "operationally guaranteed."
- **Risk**: `config/agent.toml` has high churn (55 commits, including a prior bug fix for stale `cmd` paths in commit `18287eb2`) — a future edit to these `cmd` arrays could silently drop the `--no-sync` flag → **Mitigation**: the new test added in Phase 2 (`tests/test_mcp_server_cmd_paths.py` extension) acts as a regression guard, run on every `pytest` invocation and CI.
- **Risk**: Manual verification (Phase 3, simulating a stale venv) may not be reproducible in an automated CI environment, leaving Acceptance Criteria item 3 ("fails fast with a clear error") without an automated regression test → **Mitigation**: document the manually-observed error text in the implementation procedure so a future automated test can assert against it if the deploy tooling later exposes a way to simulate this in CI; treated as a known coverage gap, not a blocker for this change.
- **Risk**: Documentation follow-up (runbook note update) could be forgotten since it is explicitly out-of-scope for this plan and not tracked as a hard gate → **Mitigation**: Implementation Step 3 (Phase 3) explicitly calls out filing a follow-up requirement/issue for it, making it a tracked action item rather than an implicit assumption.
