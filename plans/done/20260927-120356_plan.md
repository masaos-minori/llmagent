## Problem
No code path exists anywhere in `scripts/agent/` that calls Event Bus. Confirmed via `rg` across `scripts/agent/`: zero references to `eventbus`/`EventBus`. Event Bus's server side already exposes a working `/publish` endpoint (`scripts/eventbus/publish_route.py::publish()`, wired into `scripts/eventbus/app.py`).

## Reason for change
Without this integration, Agent-driven workflows cannot publish events to Event Bus's durable, ordered event log; the only current workaround is direct MCP tool calls, which bypasses Event Bus entirely.

## Implementation intent
Add a small, dedicated HTTP client module under `scripts/agent/`, following the existing pattern already used for other Agent-side service clients (`scripts/agent/memory/embedding_client.py`: a dataclass config, `httpx.AsyncClient`, retry handling). The client wraps the existing `/publish` endpoint only — no new transport, no new server-side code.

## Design
Follow the existing Agent-side HTTP-client convention (`scripts/agent/memory/embedding_client.py`): a dataclass holding connection config (`publish_url`, `timeout`, auth token), an `httpx.AsyncClient`-based publish method, and a typed result/error rather than a raised exception on failure — this keeps the new client consistent with how the Agent already handles other external HTTP dependencies (RAG embedding service) and avoids introducing a second error-handling convention.

No Python-level import boundary is crossed: `.importlinter`'s `eventbus-is-isolated` contract forbids `eventbus` importing from `agent` (the reverse direction), not `agent` calling `eventbus` over HTTP — confirmed via reading `.importlinter`. The existing "Broken contracts" output (`shared.production_config_validator -> agent.config_dataclasses`/`agent.tool_policy`) is a pre-existing, unrelated violation not touched by this Plan.
