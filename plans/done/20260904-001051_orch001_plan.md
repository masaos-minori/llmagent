# Plan: Add workflow loader fallback mode to Orchestrator.__init__

## Goal
- Allow REPL startup without a valid workflow definition by providing a fallback mode with limited functionality

## Priority
Low

## Scope
- **In-Scope**: Add fallback mode for missing workflow definitions; disable workflow commands or load a built-in default; update CLI argument parsing if a new flag is introduced
- **Out-of-Scope**: Adding new workflow formats; changing the workflow validation logic

## Background
Workflow definitions are loaded at REPL startup time. Missing workflow files cause hard crashes with no recovery path.

## Problem
No graceful degradation: users cannot start the REPL without a workflow definition, even if they want to use basic REPL functionality.

## Reason for change
Deployment reliability: the REPL should have a minimum viable mode that works without workflows, allowing users to interact with the system even if workflow features are unavailable.

## Implementation intent
Add a --no-workflow flag that skips workflow loading and disables workflow-dependent commands. Choose the approach that matches the project's operational philosophy — whether workflows are required or optional.

## Requirements
- `REQ-ORCH001-1`: REPL starts without a workflow definition (in fallback mode)
- `REQ-ORCH001-2`: Workflow-dependent commands are disabled or show appropriate error
- `REQ-ORCH001-3`: Normal workflow loading continues to work unchanged

## Design
1. In Orchestrator.__init__, catch WorkflowLoadError/FileNotFoundError and set _workflow_def = None instead of raising
2. Set a flag _fallback_mode = True when workflow loading fails
3. Pass None to WorkflowEngine only if it accepts None (verify contract first)
4. In workflow-dependent methods, check _fallback_mode and return early with appropriate message
5. If CLI flag needed, add --no-workflow to argparse and pass to Orchestrator
