## Goal
- Fix `retry_once_with_delay` so that a second failed attempt to start an HTTP subprocess MCP server re-raises a clean, catchable error instead of an `AttributeError` caused by misusing `HttpStartupError`'s constructor, so a persistently misconfigured server is routed through the required/non-required decision matrix (disable vs. fatal `RuntimeError`) instead of aborting startup for every remaining MCP server.

## Priority
High

## Scope
- **In-Scope**:
  - Rework the second-attempt re-raise in `scripts/agent/shared/retry_helper.py` so it is safe for every exception type raised by the subprocess-start path, including custom exceptions whose constructor does not accept a plain message string.
  - Add a regression test in `tests/agent/test_retry_helper.py` covering a custom `RuntimeError` subclass with a non-string constructor raised on both attempts.
- **Out-of-Scope**:
  - Changes to command validation, subprocess launch, health polling, or process termination.

  - Reworking the broader startup retry/discovery flow beyond the retry-helper re-raise.

## Background
`scripts/agent/startup_mcp_starter.py::McpServerStarter.start_servers` starts each HTTP/subprocess MCP server once, then wraps a second attempt in `retry_once_with_delay` (`scripts/agent/shared/retry_helper.py`). On the second failure the helper executes `raise type(retry_err)(masked_msg) from retry_err`, where `masked_msg` is a plain `str`. `HttpStartupError` (`scripts/agent/http_lifecycle_errors.py`) is a `RuntimeError` whose `__init__(self, failure: StartupFailure)` stores `failure` and then reads `failure.reason` when calling `super().__init__()`. The command-validation path raises `HttpStartupError(StartupFailure(...))` (`scripts/agent/http_lifecycle.py::_create_and_validate_proc`).

## Problem
Verified against the code on 2026-10-16:
- `HttpStartupError.__init__` requires a `StartupFailure` and accesses `failure.reason`. Passing a `str` (what `retry_once_with_delay` does on its re-raise line) sets `self.failure = "<str>"` and then evaluates `"<str>".reason`, which raises `AttributeError`.
- `start_servers` catches `(OSError, RuntimeError, TimeoutError, ConnectionRefusedError, ConnectionResetError, BrokenPipeError)`. `HttpStartupError` is a `RuntimeError` and is caught on the first attempt, but the `AttributeError` raised on the second attempt is NOT in that tuple, so it propagates uncaught out of `start_servers`.
- Consequence: a server that fails both attempts crashes the entire startup loop before any later server is started. The two post-retry branches in `start_servers` (disable non-required servers via `disable_server`, or raise a fatal `RuntimeError` for required servers) are never reached, so neither the required nor the non-required decision matrix is applied.

## Reason for change
A single server with a permanent misconfiguration (bad command, missing dependency, etc.) currently takes down startup of all other MCP servers with an unrelated `AttributeError`, hiding the real cause and breaking the required/non-required failure policy.

## Implementation intent
Rework the retry helper's second-attempt re-raise so it is safe for every exception type raised by the subprocess-start path, including custom exceptions whose constructor does not accept a message string. Prefer reconstructing the original exception from its stored payload (e.g. re-raise `HttpStartupError(failure)` using the captured `StartupFailure`) over `type(err)(str_message)`, or fall back to preserving the type and chaining a new exception without invoking the original constructor. Keep the fatal prefix and secret masking.

## Requirements
- `REQ-001`: On second failure, `retry_once_with_delay` MUST re-raise an exception whose construction does not depend on the original exception's constructor accepting a plain message string.
- `REQ-002`: For an exception exposing a reconstructable payload (e.g. `HttpStartupError.failure`), the re-raised exception MUST reconstruct the original type from that payload.
- `REQ-003`: For standard exceptions (`TimeoutError`, `ConnectionRefusedError`, `RuntimeError`), the re-raised exception MUST preserve the original type and carry the masked fatal message.
- `REQ-004`: For any other exotic constructor, the re-raised exception MUST preserve the original type, chain the original error, and MUST NOT raise `AttributeError`.
- `REQ-005`: The re-raised message MUST retain the `fatal_prefix` and secret masking (`_mask_secrets`).
- `REQ-006`: A regression test MUST assert that a custom `RuntimeError` subclass with a non-string constructor raised on both attempts does not raise `AttributeError` and propagates as the custom type.

## Design
Path A (small task): affects ≤ 3 files, no public/runtime interface change, no DB schema. Architecture/dependency/historical/operational analysis was skipped per `skills/issue-to-plan/SKILL.md` Routing; the points below come from Step 3 direct verification.

- **Root cause.** `scripts/agent/shared/retry_helper.py` line 60 executes `raise type(retry_err)(masked_msg) from retry_err`. When `retry_err` is an `HttpStartupError`, `type(retry_err)` is `HttpStartupError`, whose `__init__(self, failure: StartupFailure)` stores `failure` and then calls `super().__init__(failure.reason)`. Passing `masked_msg` (a `str`) sets `self.failure = "<str>"` and then evaluates `"<str>".reason`, raising `AttributeError`.
- **Why it escapes.** `start_servers` (`scripts/agent/startup_mcp_starter.py`) catches `(OSError, RuntimeError, TimeoutError, ConnectionRefusedError, ConnectionResetError, BrokenPipeError)` on the first attempt (lines 88-95). `HttpStartupError` is a `RuntimeError`, so it is caught on the first attempt and triggers the retry. On the second attempt the `AttributeError` is not in that tuple, so it propagates uncaught out of `start_servers`.
- **Unreachable decision matrix.** The post-retry branches (disable non-required via `disable_server` at line 116, or raise fatal `RuntimeError` for required at line 120) live at lines 110-122 and are never reached because the `AttributeError` escapes before the retry result is handled.
- **Callers.** Exactly two, confirmed by a single `rg`: (1) `start_servers` line 103 passes `lambda: self._start_http_subprocess_once(key, cfg)`, which can raise `HttpStartupError` through the command-validation path; (2) `verify_health` line 173 passes `lambda: self._verify_single_health(...)`, which raises a plain `RuntimeError(f"HTTP {resp.status_code}")` that accepts a message string and is therefore unaffected.
- **Fix approach.** Rework the re-raise into a small private helper that (a) reconstructs the original type from a known payload when the exception exposes one (e.g. `type(err)(err.failure)` for `HttpStartupError`), (b) falls back to `type(err)(message)` for standard exceptions, and (c) falls back further to preserving the type and chaining without invoking the constructor for any exotic constructor. Preserve `fatal_prefix` + `_mask_secrets` and chain `from retry_err`. Do not modify `HttpStartupError` (no defensive shim).
- **Design trade-off to resolve in implementation.** Coupling payload reconstruction to a specific attribute name (`failure`) introduces a soft dependency on `HttpStartupError` internals inside a shared helper. Prefer a guarded `getattr(err, "failure", None)` check (optional, non-coupling when absent) over an `isinstance` check; the general fallback still works if the attribute name changes. This is a plan-level note for the implementation phase, not a frozen requirement.

## Risks
- **Risk**: Over-generalizing the fallback could alter the exception type for a caller relying on the exact type. → **Mitigation**: prefer payload reconstruction and standard `type(err)(message)`; only fall back for exotic constructors; the regression test pins standard-type preservation (`REQ-003`).
- **Risk**: Coupling payload reconstruction to the `failure` attribute name creates a hidden dependency on `HttpStartupError` internals inside a shared helper. → **Mitigation**: guard with `getattr(err, "failure", None)` (non-coupling when absent) and keep the general fallback; document the assumption in the helper docstring. See the Design trade-off note.
- **Risk**: Changing a shared helper affects both callers. → **Mitigation**: confirmed exactly two callers; `verify_health` uses plain `RuntimeError` and is unaffected; targeted then full `pytest`.
- **Risk**: The `__new__`-based fallback may not initialize state for all exception subclasses. → **Mitigation**: fallback is reached only when `type(err)(message)` fails; document it; the regression test covers the primary custom-constructor case.
