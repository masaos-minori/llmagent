# Plan: Fix `TestMergeOrder` to match `ConfigLoader.load()`'s documented flat-merge behavior

## Goal
`PYTHONPATH=scripts pytest tests/shared/test_config_loader.py -v` collects and passes 100% (all
classes, including the 4-test `TestMergeOrder` class), while `scripts/shared/config_loader.py`'s
`load()`/`load_all()` production logic remains byte-for-byte unchanged and no other test class in
the file regresses.

## Assumptions
1. No production call site passes multiple filenames to `ConfigLoader.load()`.
   Verified by re-running the requirement's own audit: `grep -rn "\.load(" scripts --include=*.py |
   grep -v load_all` — every `ConfigLoader().load(...)` / `<Config>.load()` call site passes exactly
   one filename (or none, via a wrapper `classmethod`). Two non-`ConfigLoader` matches
   (`scripts/agent/workflow/validate.py:24`, `scripts/agent/orchestrator.py:179`) belong to an
   unrelated `WorkflowLoader.load()` API and do not affect this conclusion.
2. `ConfigLoader.load_all()` (`scripts/shared/config_loader.py:68-94`) always iterates over the
   module-level constant `_BASE_CONFIG_FILES` (line 28), currently `("agent.toml",)` — a **single**
   filename — and takes no filename arguments itself. Verified by reading the method body directly:
   `for name in _BASE_CONFIG_FILES:` with no parameter to override it.
3. Because `_BASE_CONFIG_FILES` currently has only one entry, `load_all()`'s one-level-deep dict
   merge branch (`if isinstance(val, dict) and isinstance(merged.get(key), dict): merged[key] =
   {**merged[key], **val}`) is unreachable via a normal, unpatched `load_all()` call in the current
   codebase — `merged` is always empty when the (only) file is processed, so the "already a dict at
   this key" branch condition can never be true. Verified via `git log -p` on `config_loader.py`,
   which shows `_BASE_CONFIG_FILES` used to hold multiple entries (commit history includes MCP
   server config filenames) before commit `c9af99019` ("consolidate agent config into single
   agent.toml") reduced it to one. To exercise the real merge-across-files branch through the real
   method, a test must monkeypatch `_BASE_CONFIG_FILES` to (temporarily) contain 2+ filenames — see
   UNK-01.
4. `monkeypatch.setattr("<module>", "<CONSTANT>", <value>)` on a private module-level constant is an
   established pattern in this test suite, not a novel technique being introduced here. Verified:
   `tests/eventbus_helpers.py:29` does exactly this
   (`monkeypatch.setattr(eb_app, "_ENVELOPE_SCHEMA_PATH", schema_path)`) for a comparable
   underscore-prefixed module constant.
5. `test_first_file_values_preserved_when_no_overlap` requires no change. Verified by running
   `PYTHONPATH=scripts pytest tests/shared/test_config_loader.py::TestMergeOrder -v` against the
   current, unmodified file: it is the one test (of four) that already **passes** — its two files
   define disjoint top-level keys (`[section]` vs `[other]`), so `load()`'s flat `dict.update()`
   naturally preserves both without any merge-depth dependency.
6. `_filter_meta_keys()` (`config_loader.py:147-150`) strips only **top-level** keys starting with
   `_`; it does not recurse into nested tables. Verified directly by reading its one-line
   comprehension (`{k: v for k, v in data.items() if not k.startswith("_")}` — `data.items()` is the
   top-level dict only) and confirmed empirically: loading
   `'[section]\nfoo = 1\n_bar = 2\n'` / `'[section]\nbaz = 3\n_qux = 4\n'` through the current,
   unmodified `load()` yields `{'section': {'baz': 3, '_qux': 4}}` — `_qux` (nested inside
   `[section]`) survives; it is never filtered. The current test's assertions
   (`"_qux" not in result["section"]`) were asserting behavior `_filter_meta_keys()` never
   implements, independent of the flat/nested merge-depth question the source requirement
   addressed.

## Design

No architectural change; no production code touched. This is a characterization-test repair that
aligns `TestMergeOrder` with the two methods' actually-documented, actually-verified behaviors,
correcting three distinct defects (only one of which — the flat-vs-nested merge-depth mismatch —
was identified by the source requirement; UNK-02 and UNK-03 above are additional, independently
verified defects found during this plan's source analysis).

- **`test_later_file_overrides_earlier`** — keep `load()`. Fixtures unchanged
  (`a.toml`: `[section]\nfoo=1\nbar=2`; `b.toml`: `[section]\nfoo=3\nbaz=4`). Assertions:
  `result["section"]["foo"] == 3`, `result["section"]["baz"] == 4`,
  `"bar" not in result["section"]` (explicitly documents that `b.toml`'s `[section]` table wholly
  replaces `a.toml`'s under `dict.update()`, per Assumption 1/the requirement's chosen resolution).

- **`test_first_file_values_preserved_when_no_overlap`** — unchanged (Assumption 5).

- **`test_nested_dict_merge`** — rewrite to call `load_all()` via the UNK-01 monkeypatch, with the
  UNK-02 TOML nesting fix:
  ```python
  def test_nested_dict_merge(
      self, tmp_path: Path, monkeypatch: pytest.MonkeyPatch
  ) -> None:
      """load_all() merges dict-valued keys one level deep across files
      (see config_loader.py's load_all() docstring)."""
      (tmp_path / "a.toml").write_text(
          '[mcp_servers.server_a]\nurl = "http://localhost:1"\n'
      )
      (tmp_path / "b.toml").write_text(
          '[mcp_servers.server_b]\nurl = "http://localhost:2"\n'
      )
      monkeypatch.setattr(
          "shared.config_loader._BASE_CONFIG_FILES", ("a.toml", "b.toml")
      )
      loader = ConfigLoader(config_dir=tmp_path)
      result = loader.load_all()
      assert result["mcp_servers"]["server_a"]["url"] == "http://localhost:1"
      assert result["mcp_servers"]["server_b"]["url"] == "http://localhost:2"
  ```
  Prototyped end-to-end against the real, unmodified `scripts/shared/config_loader.py` module
  (module attribute mutated directly, not via pytest, for the prototype) and confirmed it produces
  `{'mcp_servers': {'server_a': {...}, 'server_b': {...}}}` — both assertions pass.

- **`test_meta_keys_filtered_from_both_files`** — keep `load()`, redesign fixture per UNK-03/
  Assumption 6:
  ```python
  def test_meta_keys_filtered_from_both_files(self, tmp_path: Path) -> None:
      """Top-level keys starting with '_' are filtered from both files independently."""
      (tmp_path / "a.toml").write_text('_meta = "from_a"\n[section]\nfoo = 1\n')
      (tmp_path / "b.toml").write_text('_meta = "from_b"\n[section]\nbar = 2\n')
      loader = ConfigLoader(config_dir=tmp_path)
      result = loader.load("a.toml", "b.toml")
      assert "_meta" not in result
      assert result["section"] == {"bar": 2}
      assert "foo" not in result["section"]
  ```
  This exercises the real, top-level-only `_filter_meta_keys()` behavior (both files' `_meta` keys
  are gone), while also staying consistent with `load()`'s flat-overwrite semantics (`b.toml`'s
  `[section]` wholly replaces `a.toml`'s, so `foo` does not survive) — one assertion set now
  correctly documents both mechanisms instead of asserting a nested-filtering behavior that does
  not exist.

## Risks

- **R1 — Partial/inconsistent mechanical edit** (e.g. forgetting to add the `monkeypatch` fixture
  parameter, or leaving the old `load("a.toml", "b.toml")` call in `test_nested_dict_merge` instead
  of switching to `load_all()`). Likelihood: Low. Mitigation: **addressed in-plan** — Implementation
  step 2's checkpoint runs the single test in isolation before moving to the next; step 4's full-file
  run is the final backstop.
- **R2 — Monkeypatching a private module constant (`_BASE_CONFIG_FILES`) couples the test to an
  internal implementation detail; a future refactor that renames or removes this constant (e.g. if
  `load_all()` is ever given an explicit filenames parameter) would silently break this one test's
  ability to exercise the merge branch, even though `load_all()` itself would still work correctly.**
  Likelihood: Low (the constant has existed under this name since `load_all()`'s introduction and
  is also referenced by `scripts/agent/commands/cmd_config.py`, so it is not purely a test-internal
  name). Mitigation: **addressed in-plan** — the docstring/comment on `test_nested_dict_merge`
  explicitly states *why* the monkeypatch is needed (single-entry `_BASE_CONFIG_FILES` in current
  production config), so a future maintainer who breaks this test understands the coupling
  immediately rather than being confused by an opaque failure. No issue filed — this is a normal,
  documented test-design tradeoff, not a defect.
- **R3 — `tests/shared/test_shared_boundary_conditions.py::TestDictMergeConflictResolution::
  test_different_subsections_in_load_all_merged` does not actually call `loader.load_all()` at
  all.** Its own in-line comment admits this ("We need to manually combine since load_all only
  loads `_BASE_CONFIG_FILES`") — it re-implements the one-level-deep merge algorithm by hand inside
  the test body and asserts against that hand-rolled copy, not against `load_all()`'s real code path
  (`config_loader.py:82-93`). This means a real regression in `load_all()`'s merge logic would not
  be caught by that test today — only by the newly-fixed `test_nested_dict_merge` in this plan
  (which, per UNK-01's resolution, does call the real method via monkeypatching
  `_BASE_CONFIG_FILES`). Likelihood: Medium (this gap already exists today, independent of this
  fix, and was found only as a side effect of investigating UNK-01). Mitigation: **filed as a
  separate follow-up risk issue** (see `issues/`) recommending that
  `test_different_subsections_in_load_all_merged` be rewritten using the same
  `monkeypatch.setattr("shared.config_loader._BASE_CONFIG_FILES", ...)` technique this plan
  introduces, so it exercises the real method instead of a hand-rolled copy. Out of scope for this
  plan because that file is not named in the source requirement's Target files list, and touching
  it here would be scope creep.
