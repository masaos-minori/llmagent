**DB schema**: `approvals.task_id` is `NOT NULL REFERENCES tasks(task_id) ON DELETE CASCADE`
(`scripts/db/schema_sql.py:199-209`), so in the real schema every approval row has a corresponding
task row. Note for the follow-up: SQLite only enforces `REFERENCES` when
`PRAGMA foreign_keys = ON` is set per-connection; some test helpers construct the DB via raw
`sqlite3.connect()` without setting this pragma (e.g. `tests/agent/test_approval_task_persistence.py`'s
`_make_db`), so an orphaned `approval.task_id` with no matching `tasks` row is possible in test
setups even though not possible under the enforced schema in normal application use. Any future
guard implementation must define behavior for a missing task row (treat as non-halted / raise / etc.).

## Design

No design change in this cycle. For the record (to inform the eventual follow-up decision):

- **Where the guard could live**: either inside `resolve_approval()` itself (single choke point,
  covers any future caller) or in the `cmd_workflow.py` command handlers only (narrower, leaves
  `resolve_approval` a pure DB-status-transition function). `resolve_approval` is currently called
  directly, without a task-status check, from both `_cmd_approve` and `_cmd_reject` — a
  handler-level check would need to be duplicated in both places unless factored into a shared
  helper.
- **Current `resolve_approval` contract** (verified against `scripts/agent/workflow/approval_ops.py`
  lines 45-67): raises `RuntimeError` only if (a) the approval row does not exist, or (b) the
  approval's own `status != "pending"`. It performs no query against the `tasks` table at all.
- **`WorkflowEngine._gate_approval`** (`scripts/agent/workflow/workflow_engine.py`, lines 156-181)
  already reads `existing.status` (the approval's status, not the task's) to decide resume/halt
  behavior when the workflow itself re-checks an approval — this is a different code path from
  `resolve_approval` and is unaffected by either option.

## Risks

- **Risk**: The decision is deferred indefinitely, leaving the known coverage gap (once
  `plans/done/20260804-104315_plan.md`'s test-fix lands) undocumented as "accepted" or "to be fixed."
  Likelihood: medium.
  **Mitigation**: Filed as `issues/20260804-135244_unknowns.md` with both options and their
  acceptance criteria spelled out, so the gap stays visible in the issue backlog rather than
  disappearing silently with the test rewrite.
- **Risk**: If option 1 is later authorized, adding a task-status check to `resolve_approval`
  could break existing tests that call it without an associated `"running"`/non-halted task
  (~15+ call sites across 4 test files, per Affected Areas). Likelihood: medium.
  **Mitigation**: The follow-up requirement (Phase 3 above) must explicitly require an audit of all
  existing `resolve_approval` call sites' task-status fixtures before merging the guard, not just
  the addition of new positive tests.
- **Risk**: If option 1 is later authorized, a guard implemented as a `tasks` JOIN could mishandle
  orphaned `approval.task_id` values that have no matching `tasks` row (possible in test doubles
  that build schema via raw `sqlite3.connect()` without `PRAGMA foreign_keys = ON`, even though the
  real schema enforces the FK). Likelihood: low.
  **Mitigation**: The follow-up requirement must define explicit behavior for "no matching task
  row found" (e.g., treat as non-halted and proceed, consistent with the FK guarantee in
  production) and add a test for that case.

All risks above have mitigations recorded in this plan; none required filing a separate
`issues/{timestamp}_risks.md` (the one blocking item — the decision itself — is already filed as
an Unknown, not a Risk).
