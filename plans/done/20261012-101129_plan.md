## Background
- Under the per-consumer model the NACK path no longer writes the events-level counters; promotion uses `consumer_delivery_failure_count` (ADR-006 INV-13; `eventbus_05` Inline Promotion Path and Background Loop Promotion).
- `plans/done/20261012-093531_plan.md` found this drift in `eventbus_03_dlq_operations.md` and recorded it as out of scope there.
- Repository evidence (`Explicit in code`): the background sweep query joins `consumer_delivery` and filters on `consumer_delivery_failure_count`; the inline path in the NACK route compares the nacking consumer's per-consumer count with `max_retry`; no statement in `scripts/eventbus` updates the events-level counters on NACK.

## Problem
- The document says inline promotion is triggered when `POST /nack` raises `delivery_failure_count` to `max_retry`, and that the sweep searches events where `delivery_failure_count >= max_retry AND dlq_at IS NULL`; that condition cannot become true under the per-consumer model.
- An operator would look at the wrong counter when diagnosing a promotion, and the orphaned-events explanation is built on that condition.

## Reason for change
- Documentation/code mismatch on correctness-relevant operational behavior, in a document that contradicts `eventbus_05` and ADR-006.

## Implementation intent
- Rewrite only the passages that state the promotion condition so they describe per-consumer gating, keep the description of the two paths, the shared promotion routine and the `dlq_at IS NULL` guard, and refer to `eventbus_05` for the exact rule instead of restating it. Describe behavior, not line numbers or counts.

- `REQ-002`: The DLQ Background Sweep section describes the sweep as selecting events by the per-consumer failure count with `dlq_at IS NULL`, and its orphaned-events explanation does not rely on the events-level counter.
