## Goal

Prevent double-resolution of workflow approvals by making the check-and-resolve operation atomic via conditional SQL updates and transaction isolation.

## Scope

**In-Scope**:
- Modify `resolve_approval()` to use conditional UPDATE with `WHERE status='pending'`
- Return affected row count to distinguish "already resolved" from "not found"
- Wrap `_cmd_approve()` and `_cmd_reject()` in `begin_immediate()` transaction
- Update error handling in `_cmd_approve()` and `_cmd_reject()` for distinct error messages

**Out-of-Scope**:
- Changes to other workflow operations (request, get_latest, etc.)
- Changes to per-tool interactive approval (`tool_approval.run_approval_checks`)
- Changes to recovery logic (`_recover_pending_approvals`)

## Assumptions

1. SQLite WAL mode supports concurrent readers with serialized writes — `BEGIN IMMEDIATE` provides sufficient isolation for single-writer scenarios
2. `db.fetchall()` returns empty list when no rows match — consistent across all callers
3. Existing callers of `resolve_approval()` expect `RuntimeError` on failure — they handle both "not found" and "already resolved" cases identically

UNK-02: Resolved — SQLite always reads committed data. Within a single connection, uncommitted changes are visible only within the same transaction. Since we use `begin_immediate()` wrapping the entire flow, the SELECT inside the transaction will see the current state.

## Implementation Steps

1. **Phase 1: Modify resolve_approval() to return affected row count**
   - Change `resolve_approval()` signature to return `bool` (True = success, False = already resolved)
   - Replace unconditional UPDATE with `UPDATE ... WHERE status='pending' AND approval_id=?`
   - Return True if affected_rows > 0, False otherwise
   - Remove "already resolved" RuntimeError; keep "not found" RuntimeError

2. **Phase 2: Update callers to handle distinct error states**
   - In `_cmd_approve()`: after `resolve_approval()`, check return value; if False, show "already resolved" message
   - In `_cmd_reject()`: same pattern
   - Wrap both command methods in `store.begin_immediate()` context manager

3. **Phase 3: Add tests**
   - Test: conditional update prevents double-resolution
   - Test: distinct error messages for "not found" vs "already resolved"
   - Test: transaction isolation works correctly
