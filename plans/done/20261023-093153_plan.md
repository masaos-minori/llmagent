# Implementation Plan: Workflow task idempotency key is not restart-safe

## Goal

Make `agent.workflow.task_ops.create_task()` generate a per-insert unique `idempotency_key` so that
creating a task for a session/turn that already has a task row no longer violates the
`tasks.idempotency_key UNIQUE` constraint.

## Priority

High (blocks normal operation after a failed turn)

## Scope

Workflow task creation only (`scripts/agent/workflow/task_ops.py`, `scripts/agent/workflow/state_store.py`)
plus their tests. The adapter's resume path (`workflow_task_id` → `get_task_by_id`) is unchanged.

## Task Size

Path A

Path A Basis: 1 behavior change (key derivation) in 2 files, 2 test files. No signature, schema,
data-model, or dependency change. No import-cycle or public-interface impact.

## Background

`create_task()` at `scripts/agent/workflow/task_ops.py:13` derives the key from the caller-supplied
session and turn when both are non-`None` (`task_ops.py:21-24`):

```python
if session_id is not None and turn_number is not None:
    idempotency_key = f"{session_id}:{turn_number}"
else:
    idempotency_key = str(uuid.uuid4())
```

`tasks.idempotency_key` is `TEXT UNIQUE NOT NULL` (`scripts/db/schema_sql.py:178`).
The only production caller is `WorkflowEngineAdapter._init_workflow_task()`
(`scripts/agent/workflow_engine_adapter.py:269-275`), which passes `turn_number=ctx.stats.stat_turns`
and creates a new task only when `agent_state["workflow_task_id"]` is absent. When a task exists and
the state carries `workflow_task_id`, `create_resumed_task()` (`task_ops.py:62`) is used, which already
generates `str(uuid.uuid4())`.

The same composite derivation is duplicated in `StateStore.create_task()` (`scripts/agent/workflow/state_store.py:55-59`),
which has no callers found in `scripts/` or `tests/`.

## Problem

A task row created for a turn stays in the database even when the turn fails, while
`agent_state["turn_number"]` and `agent_state["workflow_task_id"]` are only updated by
`ConversationStateManager` after a successful turn (`scripts/agent/conversation_state_manager.py:101-111`).
The next turn therefore recomputes the same `turn_number` and calls `create_task()` again, producing the
identical composite key. The `INSERT` raises `sqlite3.IntegrityError`, which is not caught on this path
(`_init_workflow_task()` has no `try`/`except`; only `WorkflowEngine.execute()` at
`workflow_engine_adapter.py:289` is wrapped), so the whole workflow path is discarded and the turn falls
back to the legacy path.

Verified against HEAD `064e77fd9` with an in-memory reproduction of `create_task()`:

```text
run1 first key: :0            status: success
run2 first insert raised: IntegrityError: UNIQUE constraint failed: tasks.idempotency_key
[ADAPTER] Workflow engine failed, falling back to legacy
```

Issue correction: the reported key format is accurate, but the observed first-turn key is `":0"`, not
`":1"`. `ctx.stats.stat_turns` (`scripts/agent/shared/context.py:223`, default `0`) is incremented only
after a successful turn (`conversation_state_manager.py:111`), so the first task created in a process
carries the value `0`. Also, `get_task_by_idempotency_key()` has no production caller — only
`tests/agent/workflow/test_workflow_state_store.py:20,80-85` and
`tests/agent/workflow/test_workflow_engine.py:94,125,142,296`.
The legacy paths in the issue (`scripts/agent/workflow_state_store.py`, commit `7b80c8d`) do not exist at
HEAD; the corresponding code is `scripts/agent/workflow/task_ops.py`.

## Reason for Change

Fix a restart-unsafe key derivation that turns a normal retry after a failed turn into a database
constraint violation and a silent fallback to the legacy path.

## Implementation Intent

- Decision (user-confirmed): `create_task()` always generates `idempotency_key = str(uuid.uuid4())`.
  The `(session_id, turn_number)` composite derivation is removed.
- `session_id` and `turn_number` remain stored as task columns and are kept as parameters. Signatures
  are not changed.
- The only resume mechanism stays the persisted `agent_state["workflow_task_id"]` →
  `get_task_by_id()` path already implemented at `workflow_engine_adapter.py:253-264`. No adapter change.
- `StateStore.create_task()` (`state_store.py:55-59`) drops the same composite branch so no second copy
  of the defective derivation remains. Not merged into `task_ops.create_task()` in this plan
  (AGENTS.md rule 5: no unrelated refactoring).
- Consequence accepted: multiple `tasks` rows can exist for the same `(session_id, turn_number)`. Nothing
  in `scripts/` queries tasks by composite key (`get_task_by_idempotency_key()` is unused in production),
  so no query semantics change.
- The `UNIQUE NOT NULL` constraint on `tasks.idempotency_key` and `WORKFLOW_SCHEMA_VERSION` are not
  changed.

## Requirements

- REQ-001: `agent.workflow.task_ops.create_task()` generates `idempotency_key` as `str(uuid.uuid4())`
  for every call, regardless of `session_id`/`turn_number`.
  - Acceptance: two calls with identical `(session_id, turn_number)` both insert successfully and return
    distinct `idempotency_key` values.
  - Priority: High, Dependencies: none
- REQ-002: `StateStore.create_task()` no longer derives `f"{session_id}:{turn_number}"` and generates
  `str(uuid.uuid4())`.
  - Acceptance: no composite-key derivation remains anywhere in `scripts/agent/workflow/`.
  - Priority: Medium, Dependencies: REQ-001 (same shape)
- REQ-003: Signatures of `create_task()`, `create_resumed_task()`, and `StateStore.create_task()` and the
  `tasks` schema are unchanged; `session_id`, `turn_number`, `workflow_version`, `workflow_id` continue to
  be stored.
  - Acceptance: existing caller `workflow_engine_adapter.py:269-275` compiles and behaves unchanged.
  - Priority: High, Dependencies: REQ-001
- REQ-004: Existing tests that assert the composite format are migrated to the new contract.
  - Acceptance: `tests/agent/workflow/test_workflow_state_store.py:73` no longer asserts
    `"sess1:1"`; `test_idempotency_key_unique` (`:75-78`) asserts repeated creates for the same
    session/turn succeed with distinct keys; `test_get_by_idempotency_key` (`:80-85`) looks up the key
    returned by `create_task()`.
  - Priority: High, Dependencies: REQ-001
- REQ-005: Tests that look up tasks by the literal composite key are migrated to `get_task_by_id()` using
  the task id returned by `WorkflowRunResult.task_id` or by `create_task()`.
  - Acceptance: `tests/agent/workflow/test_workflow_engine.py:94,125,142,296` no longer use literal
    `"s:1"`, and those tests pass.
  - Priority: High, Dependencies: REQ-001
- REQ-006: Add a regression test that reproduces the restart scenario: a task row exists for
  `(session, turn)` and a new task is created for the same `(session, turn)` without raising.
  - Acceptance: the test fails with `IntegrityError` before the change and passes after it.
  - Priority: High, Dependencies: REQ-001, REQ-004

## Design

- What changes: the value written into `tasks.idempotency_key` becomes a per-insert UUID.
- What must not change: function signatures, `TaskRecord`, `tasks` DDL, `WORKFLOW_SCHEMA_VERSION`, the
  adapter's create-vs-resume decision, `WorkflowEngine` stage execution.
- What is intentionally deferred: removing or delegating `StateStore.create_task()`; adding a
  `(session_id, turn_number)` query.
- What is allowed only after a decision: unifying the two `create_task` implementations.
