## Design
**Format reconciliation is the central constraint.** Both governance checkers recognize a Part 2
entry only via a `#### NC-XXXX` heading plus `- **Field:**` bullets; they do not parse markdown
tables. The current Part 2 uses a six-column table (`NC-001`–`NC-004`) that neither parser reads
— hence conformance passes vacuously while the marker-checker still flags `rag_05_5`. Registering
a tracked source therefore *requires* a bullet-format `NC-040` block. Two consequences:

- **Field count.** `check_issue_inventory_conformance.py` counts `- **Field:**` bullets and
  requires exactly 15 for Part 2 (the `#### ` heading itself does not count). All fifteen
  documented fields must therefore be emitted as bullets, including `- **ID:** NC-040` (this
  matches the Part 1 convention, e.g. `DESIGN-2`). Do **not** replicate the historical
  `NC-021`–`NC-024` omission of the ID bullet (14 bullets) — that fails the current checker.
- **Mixed formats.** Adding a bullet-format block alongside the existing table leaves Part 2 in
  two formats. Leave the table as-is (converting it is a larger, riskier change and out of
  scope). Recommend a dedicated follow-up to unify Part 2's format — see Risks.

**Why the `ETagManager` half is dropped.** No inline marker exists in `rag_02_06` and the
distinction is implemented in code (`InvalidIncomingTimestampError` + `InvalidStoredTimestampError`,
both `ValueError` subclasses). The Extraction Process populates entries from source markers; there
is nothing to extract, and inventing an entry would violate it. The question remains tracked via
`etagexc01`.

**Referential integrity.** Set `Related NC: None`. `Resolution Target` is free-form and is not
validated by either checker, so it may reference an owner decision or an optional follow-up
without needing an existing heading to resolve against.
