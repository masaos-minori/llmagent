0-failure result regardless of execution order or `pytest-randomly` seed, by
fixing the specific test-isolation gaps that cause 3 independent
self-contained ordering bugs plus one cross-class state leak — replacing the
Issue's own (partially incorrect) single-cause theory with a
per-cluster-verified fix plan.

## Background
Reproduced directly against the current repository state (2026-09-20,
`uv run pytest tests/mcp_servers/git/test_git_security_compliance.py -q`):
14 failures with `--randomly-seed=1` and 14 failures with `-p no:randomly`
(declaration order) — matching the Issue's own claim of "13-14 failures"
exactly, confirming the problem is still live and unresolved despite the
partial fix attempts recorded in the Issue's own "Work Status" section.

**Adversarial Verification correction to the Issue's Root Cause Analysis**:
the Issue attributes the failures to `TestLiveCallToolAuthorization` leaking
`protected_branches` state into other classes via the `_cfg`/`_service`
dual-copy gap ("Blocking Factors" #1). Isolation testing disproves this as
the primary or sole mechanism:
- `uv run pytest ... -k "TestLiveCallToolAuthorization"` (this class alone,
  no other class in the run) still produces 6 failures — proving a
  self-contained, within-class ordering bug independent of any cross-class
  leak. The class's own tests already restore `_cfg.protected_branches`
  symmetrically (verified via `rg`); the actual defect is elsewhere within
  this class and is not yet pinned to a specific attribute.
- `uv run pytest ... -k "TestDryRunAndDetachedHeadLivePath"` (alone)
  produces 2 failures — a second, independent self-contained bug in a class
  the Issue's Root Cause Analysis did not implicate as a source, only as a
  victim.
- `uv run pytest ... -k "TestNewlyReachableToolsViaHTTP"` (alone) produces 2
  failures (`test_newly_reachable_write_tool_denied_under_dirty_worktree`,
  both parametrizations) — notable because this class already uses the
  "enabled" fixture (`copy.deepcopy` snapshot-after-setup, restore via
  `__dict__.update()` in a `finally`) that the Issue's abandoned
  investigation added specifically to fix this class of bug. Each
  parametrized test gets its own fresh `tmp_path`-based repo directory, and
  the fixture's own `_cfg`/`_service` restore is verified symmetric — so
  this residual failure is caused by a state channel other than `_cfg`/
  `_service`, not yet identified (see Unknowns).
- `uv run pytest ... -k "TestNewlyReachableToolsViaHTTP or
  TestRemoteAuthorizationViaHTTP or TestGitServiceErrorHandlerIdentity"`
  (excluding both `TestLiveCallToolAuthorization` and
  `TestDryRunAndDetachedHeadLivePath`) still produces 6 failures: the same 2
  self-contained `TestNewlyReachableToolsViaHTTP` failures, plus 3 in
  `TestRemoteAuthorizationViaHTTP` and 1 in `TestGitServiceErrorHandlerIdentity`
  that do NOT occur when those two classes run alone (`4 passed`/`1 passed`
  respectively, 0 failures each) — proving `TestNewlyReachableToolsViaHTTP`
  is the source of a genuine cross-class leak into these two otherwise-clean
  classes.
- Total accounted for: 6 (`TestLiveCallToolAuthorization`, self-contained) +
  2 (`TestDryRunAndDetachedHeadLivePath`, self-contained) + 2
  (`TestNewlyReachableToolsViaHTTP`, self-contained) + 3
  (`TestRemoteAuthorizationViaHTTP`, cross-class victim of
  `TestNewlyReachableToolsViaHTTP`) + 1 (`TestGitServiceErrorHandlerIdentity`,
  same cross-class victim) = 14, matching the full-file failure count
  exactly with no residual unexplained failures.
- Also confirmed: `_cfg.protected_branches`'s true shipped default (via
  `config/git_mcp_server.toml`) is `['main', 'master', 'release']`, not
  empty — relevant baseline fact for whichever attribute-level fix each
  cluster below turns out to need.

The Issue's own "Work Status" log shows a prior investigation attempted an
`isolate_git_server_state` autouse fixture (replacing all manual

## Problem
Three independent, self-contained test-ordering bugs exist within
`TestLiveCallToolAuthorization`, `TestDryRunAndDetachedHeadLivePath`, and
`TestNewlyReachableToolsViaHTTP` respectively (each reproducible with that
one class running alone), and `TestNewlyReachableToolsViaHTTP`'s own bug (or
a related state channel) additionally leaks into `TestRemoteAuthorizationViaHTTP`
and `TestGitServiceErrorHandlerIdentity`, which have no defect of their own.
The exact attribute or state channel responsible for each of the 3
self-contained bugs has not yet been pinned down (see Unknowns) — only the
class-level location and failure count have been verified.

## Reason for change
Same as the Issue: an order-dependent test file provides unreliable CI
signal, already observed producing both 13 and 14 failures with different
exact members across different orderings, risking either a masked real
regression or wasted investigation time on a phantom failure. The prior
investigation's abandonment in a "Blocked" state (Issue's own "Work Status")
means this risk is still fully live in the current repository.

## Implementation intent
For each of the 3 self-contained-bug classes, first re-run the class alone
under `-s`/targeted `print`/`pytest --lf`-style bisection (as this Plan's
own Background section did) to narrow the failing pair or trio of tests
within the class, then inspect exactly what state differs between a passing
solo run and the failing in-sequence run for those specific tests — do not
assume the cause is `_cfg`/`_service` drift without first checking it, since
`TestNewlyReachableToolsViaHTTP`'s already-fixed-looking `enabled` fixture
proves that assumption can be wrong. Once each cluster's actual leaking
state is identified, apply either (a) a corrected per-test save/restore, or
(b) a fixture-based snapshot/restore for that class — following the
Issue's own Implementation Intent's preference for (b) when the attribute
count is large enough to make manual `try/finally` error-prone, which this
Plan's own evidence (`TestLiveCallToolAuthorization`'s 5-6 attributes across
11 tests) suggests is already the case for at least that class. For
`TestNewlyReachableToolsViaHTTP` specifically, since its existing `_cfg`/
`_service` fixture already appears symmetric, the audit must explicitly
extend beyond `_cfg`/`_service` (see Unknowns UNK-01) before concluding what
fix is needed. Do not skip or `xfail` any of these tests as a workaround,
per the Issue's own instruction.

## Design
This Plan deliberately does not prescribe a single uniform fix shape across
all 3 clusters, per Assumptions above — the Issue's own abandoned attempt at
a single file-wide `isolate_git_server_state` autouse fixture did not
resolve the failures and left an unexplained "teardown ordering issue"
(UNK-03). Instead, this Plan's Implementation steps direct per-cluster
bisection first (reusing this Plan's own Background methodology: run the
one affected class alone via `-k "<ClassName>"`, then narrow to the
smallest failing test pair/subset), then a fix scoped to what that
bisection actually finds:
- `TestLiveCallToolAuthorization` and `TestDryRunAndDetachedHeadLivePath`
  both currently use ad hoc per-test `try/finally` save/restore blocks
  (verified via `rg` — see Background). If bisection confirms the leak is a
  `_cfg`/`_service` attribute after all (just one this Plan's direct read
  did not catch), replacing the per-test blocks with a class-scoped fixture
  modeled on `TestNewlyReachableToolsViaHTTP`'s existing `enabled` pattern
  (snapshot the full `_cfg.__dict__`/`_service.__dict__` once, after any
  fixture-level setup, restore via `.update()` in a `finally`) is preferred
  over continuing manual enumeration, per the Issue's own Implementation
  Intent — 5-6 attributes across many tests already makes manual
  `try/finally` error-prone (this Plan's own evidence).
- `TestNewlyReachableToolsViaHTTP` already uses that same fixture pattern
  and still has both a self-contained bug and a cross-class leak — so its
  fix cannot be "adopt the enabled-fixture pattern" (already present).
  Bisection here must look beyond `_cfg`/`_service` (UNK-01) before any fix
  is chosen; widening the same fixture's snapshot/restore to cover whatever
  channel is found (rather than inventing a second, different mechanism) is
  preferred once identified, to keep the file's isolation strategy
  consistent across classes.
- `TestRemoteAuthorizationViaHTTP` and `TestGitServiceErrorHandlerIdentity`
  need no fix of their own (they pass cleanly in isolation) — REQ-003's fix
  to `TestNewlyReachableToolsViaHTTP`'s leak source is expected to resolve
  their failures as a side effect, per AC-2's explicit re-verification
  requirement rather than an assumption.

## Risks
- **Risk**: A cluster's bisection (Phase 1) finds no clean single-attribute
  cause and the leak is genuinely diffuse/probabilistic (e.g. object
  identity/aliasing rather than a value drift) → **Mitigation**: fall back
  to the class-scoped fixture pattern (full `__dict__` deep-copy
  snapshot/restore) uniformly for that class even without a fully pinned
  single-line cause — this pattern already works for 2 of the 3 classes
  that use it (`TestRemoteAuthorizationViaHTTP`,
  `TestGitServiceErrorHandlerIdentity`), so it is a reasonable structural
  fallback distinct from the abandoned file-wide autouse attempt.
- **Risk**: Fixing one cluster changes shared module import/collection
  order enough to reveal a previously-masked 4th failure → **Mitigation**:
  Phase 3's full-file, multi-seed re-run (AC-3) is mandatory after all 3
  clusters are fixed, specifically to catch this before declaring the Plan
  complete.
- **Risk**: The exact same "autouse fixture teardown ordering issue" that
  blocked the prior investigation (UNK-03) recurs if a fixture-based fix is
  chosen → **Mitigation**: verify fixture teardown order explicitly (e.g.
  `pytest --setup-show`) for any newly introduced fixture before relying on
  it, per Design.
