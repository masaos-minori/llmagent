# Plan: Refactor ConfigReloadService — eliminate duplicate validation logic and field collection duplication

## Goal
Consolidate `scripts/agent/services/config_reload.py`'s duplicated field collection and dual-validation pattern into a single unified flow, parameterize repetitive reload methods, replace magic strings with constants, and reduce AgentContext coupling — enabling independent unit testing of each concern without full context mocking.

## Priority
Medium

## Scope
- **In-Scope**: Consolidate `_collect_request_values()` and `_apply_llm_prompt_params()` into single `_collect_field_changes()` method; remove `_validate_request()` pre-validation; extract parameterized `_reload_section()` helper; replace magic strings with named constants; reduce AgentContext coupling in `_sync_services()`
- **Out-of-Scope**: MCP server lifecycle management changes; adding new validators; changing `ConfigReloadOutcome` field types or adding/removing fields; modifying `AgentContext` or `services_required` interfaces; performance optimization beyond what refactor naturally achieves

## Background
After extracting `HttpServerLifecycleManager` from `lifecycle.py`, similar splits were completed for `orchestrator.py`, `repl.py`, `ingester.py`, and `pipeline.py`. However, `config_reload.py` remains at 645 lines with two independent paths for identical data: `_collect_request_values()` collects `http_timeout`, `context_token_limit`, `embed_url`, `use_semantic_cache`, `max_tool_turns`, `tool_result_max_llm_chars`; then `_apply_llm_prompt_params()` collects `llm_temperature`, `llm_max_tokens`, `llm_url`, `web_search_url`, `embed_url`, `http_timeout`, `max_tool_turns`, `tool_result_max_llm_chars`, `tool_definitions`, `system_prompt_tool`, `system_prompts`. Overlap on `http_timeout`, `embed_url`, `max_tool_turns`, `tool_result_max_llm_chars` means the same request values flow through two separate methods without coordination. Additionally, `_validate_request()` validates `http_timeout` via `validate_llm_http_timeout()` and `context_token_limit` via `validate_llm_context_token_limit()`, while `_apply_rag_tool_params()` validates temperature, max_tokens, context_char_limit, etc. — different validator sets for overlapping fields.

## Problem
`ConfigReloadService.apply_config_dict()` calls `_validate_request()` which validates LLM/RAG/Tool fields BEFORE applying changes, but then calls `_apply_rag_tool_params()` which ALSO collects and validates the same fields AFTER — using different validator sets. Additionally, `_collect_request_values()` and `_apply_llm_prompt_params()` both collect `embed_url`, `http_timeout`, `max_tool_turns`, and `tool_result_max_llm_chars` from the same request payload into separate change dicts, creating two independent paths for identical data. Tight coupling to AgentContext makes unit testing difficult without full context mocking. Six private reload methods follow identical patterns that could be parameterized. Magic strings scattered throughout make maintenance error-prone.

## Reason for change
- Dual-validation pattern creates inconsistent coverage: pre-validation (`_validate_request`) and post-application validation (`_apply_rag_tool_params`) use different validator sets for overlapping fields, making it easy to miss validators or add redundant ones
- Field collection duplication means the same request values flow through two separate methods without coordination — a future change could modify one path without updating the other
- `_sync_services()` accesses `ctx.services_required.llm`, `ctx.services_required.hist_mgr`, `ctx.services_required.runtime_tools` directly — requires full AgentContext mock for unit testing
- Six private reload methods (`_reload_approval_config`, `_reload_tool_allowlist`, `_reload_memory_runtime`, `_reload_security_profile`, plus two others) follow identical patterns that could be parameterized
- Magic strings like `"context_char_limit"` at line 404, `"http_timeout"` at line 228/498, `"system_prompt_tool"` at line 301/509 are used in multiple places without centralization

## Implementation intent
Consolidate the concerns above into a single unified flow, following the constructor-injection/delegation pattern already used for the `orchestrator.py` and `ingester.py` splits. Suggested approach:

- **Unified field collector** — owns `_collect_field_changes()` replacing both `_collect_request_values()` and `_apply_llm_prompt_params()`, populating one set of change dicts (`llm_changes`, `rag_changes`, `tool_changes`)
- **Post-application validator** — moves all validation to after application, not before; removes `_validate_request()` entirely
- **Parameterized reload helper** — extracts common pattern from `_reload_approval_config`, `_reload_tool_allowlist`, `_reload_memory_runtime`, `_reload_security_profile` into a single `_reload_section(ctx, new_cfg, section_name, field_mappings)` method
- **Magic string constants** — replaces all magic strings with module-level named constants
- **Decoupled service sync** — passes only required service instances instead of accessing `ctx.services_required.*` directly

## Design
### Architecture Analysis
`ConfigReloadService` has two independent paths for identical data: `_collect_request_values()` collects `http_timeout`, `context_token_limit`, `embed_url`, `use_semantic_cache`, `max_tool_turns`, `tool_result_max_llm_chars`; then `_apply_llm_prompt_params()` collects `llm_temperature`, `llm_max_tokens`, `llm_url`, `web_search_url`, `embed_url`, `http_timeout`, `max_tool_turns`, `tool_result_max_llm_chars`, `tool_definitions`, `system_prompt_tool`, `system_prompts`. Overlap on `http_timeout`, `embed_url`, `max_tool_turns`, `tool_result_max_llm_chars` means the same request values flow through two separate methods without coordination. Additionally, `_validate_request()` validates `http_timeout` via `validate_llm_http_timeout()` and `context_token_limit` via `validate_llm_context_token_limit()`, while `_apply_rag_tool_params()` validates temperature, max_tokens, context_char_limit, etc. — different validator sets for overlapping fields.

### Dependency Graph
- **Caller**: `AgentContext.reload_config()` delegates to `ConfigReloadService.apply_config()`
- **Callee**: `config_validators.py` provides validation functions; `models.py` defines `ConfigReloadRequest`, `ConfigReloadOutcome`
- **Dependencies**: `AgentContext` (tight coupling), `dataclasses.replace()`, `_get_float`, `_get_int`, `_get_str`, `_get_list_nonempty`, `_get_dict_nonempty`

### Historical Analysis
The file has had 12 commits modifying it over time, indicating moderate churn. Recent commits include SSE resilience improvements, MCP server config diffing, and validation consolidation. This suggests changes should be carefully tested.

### Operational Dependency Inspection
No external processes hold locks on this file during normal operation. The service manages configuration state but does not hold persistent OS-level locks itself.

### Design Decisions
1. **Unified field collector**: Replace `_collect_request_values()` and `_apply_llm_prompt_params()` with single `_collect_field_changes()` that populates one set of change dicts (`llm_changes`, `rag_changes`, `tool_changes`)
2. **Post-application validation**: Move all validation to after application, not before — removes `_validate_request()` entirely
3. **Parameterized reload helper**: Extract common pattern from `_reload_approval_config`, `_reload_tool_allowlist`, `_reload_memory_runtime`, `_reload_security_profile` into `_reload_section(ctx, new_cfg, section_name, field_mappings)`
4. **Magic string constants**: Define module-level constants like `FIELD_HTTP_TIMEOUT = "http_timeout"`, `FIELD_CONTEXT_CHAR_LIMIT = "context_char_limit"`, `FIELD_SYSTEM_PROMPT_TOOL = "system_prompt_tool"`
5. **Decoupled service sync**: Pass only required service instances to `_sync_services()` instead of accessing `ctx.services_required.*` directly
