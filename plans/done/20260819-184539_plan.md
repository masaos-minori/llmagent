# Plan: Unify FAIL/WARN/OK classification in StartupOrchestrator._report_readiness

## Goal
Make the four Readiness Summary lines in `StartupOrchestrator._report_readiness`
(`scripts/agent/startup.py`) derive their `FAIL` / `WARN` / `OK` label from a single
shared 3-tier rule based purely on each source's fatal/warning counts, eliminating the
current self-contradictory "FAIL (0 fatal, ...)" output for the `readiness` and
`mcp_tool_discovery` sources.

## Scope

### In scope
- Add one shared classification helper (module-level function or private method on
  `StartupOrchestrator`) taking `fatal_count: int, warning_count: int` and returning
  `"FAIL"` / `"WARN"` / `"OK"`.
- Rewire the four `lines.append(...)` f-strings in `_report_readiness`
  (`scripts/agent/startup.py`, currently lines 526-537) to call the helper with each
  source's already-computed `*_fail` / `*_warn` counts instead of using the `*_ok`
  boolean-ish variables.
- Remove the four now-unused `*_ok` local variables (`security_ok`, `mcp_ok`,
  `tool_disc_ok`, `rag_ok`) if nothing else in the method references them.
- Add unit tests in `tests/agent/test_startup.py` covering the 4 sources x 4
  fatal/warning combinations for the rendered summary line (or for the extracted
  helper directly, per the requirement's stated test preference).

### Out of scope
- Any change to `_check_services()`'s fatal/warning/ok recording logic, `add_ok`
  call sites, `pipeline.has_fatal`, or the `RuntimeError` startup-abort path.
- Any change to `StartupValidationResult` / `StartupCheckStatus`
  (`scripts/agent/shared/health_models.py`) — reference only.
- Any change to the `Unreachable servers:` / `Degraded servers:` / unavailable-server
  lines that follow the 4 main summary lines in `_report_readiness` (lines 538+).
- Any change to `_display_pipeline_results` (the per-outcome WARNING/FATAL/SKIPPED
  console output emitted before the summary).

## Design
Add a single helper implementing the 3-tier rule (fatal > 0 -> `FAIL`; else
warning > 0 -> `WARN`; else `OK`):

```python
@staticmethod
def _classify_summary_status(fatal_count: int, warning_count: int) -> str:
    """Classify a readiness-summary source into FAIL/WARN/OK.

    FAIL if any fatal outcome was recorded, WARN if only warnings were
    recorded, OK otherwise. This is the single shared rule used by every
    line of the Readiness Summary so all four sources are judged the same
    way, regardless of whether an explicit `add_ok(...)` outcome was also
    recorded for that source.
    """
    if fatal_count > 0:
        return "FAIL"
    if warning_count > 0:
        return "WARN"
    return "OK"
```

Rewire the 4 lines (current lines 526-537) from:

```python
lines.append(
    f"  Security audit: {'OK' if security_ok else 'FAIL'} ({security_fail} fatal, {security_warn} warnings)"
)
lines.append(
    f"  Service readiness: {'OK' if mcp_ok else 'FAIL'} ({mcp_fail} fatal, {mcp_warn} warnings, {mcp_skip} skipped)"
)
lines.append(
    f"  Tool discovery: {'OK' if tool_disc_ok else 'FAIL'} ({tool_disc_fail} fatal, {tool_disc_warn} warnings, {tool_disc_skip} skipped)"
)
lines.append(
    f"  RAG consistency: {'OK' if rag_ok else 'WARN'} ({rag_fail} fatal, {rag_warn} warnings)"
)
```

to:

```python
lines.append(
    f"  Security audit: {self._classify_summary_status(security_fail, security_warn)} "
    f"({security_fail} fatal, {security_warn} warnings)"
)
lines.append(
    f"  Service readiness: {self._classify_summary_status(mcp_fail, mcp_warn)} "
    f"({mcp_fail} fatal, {mcp_warn} warnings, {mcp_skip} skipped)"
)
lines.append(
    f"  Tool discovery: {self._classify_summary_status(tool_disc_fail, tool_disc_warn)} "
    f"({tool_disc_fail} fatal, {tool_disc_warn} warnings, {tool_disc_skip} skipped)"
)
lines.append(
    f"  RAG consistency: {self._classify_summary_status(rag_fail, rag_warn)} "
    f"({rag_fail} fatal, {rag_warn} warnings)"
)
```

Then delete the now-dead `security_ok`, `mcp_ok`, `tool_disc_ok`, `rag_ok`
assignments (current lines 452-456, 472-476, 487-491, 502-506 — the `_ok` sum
blocks only; the corresponding `_fail`/`_warn`/`_skip` sum blocks are still
needed and stay).

This keeps `_check_services()` and `StartupValidationResult` completely untouched
(per the requirement's explicit constraint #4), and confines the fix to
presentation logic in `_report_readiness`, satisfying the "one shared rule, single
place" acceptance criterion by construction (there is exactly one method
implementing the tiering, called 4 times).

## Risks
- **Risk**: Removing the `*_ok` sum-block computations might be mistaken for also
  needing to remove the `add_ok(...)` call sites in `_check_services()`, silently
  widening the change beyond the stated scope.
  → **Mitigation**: Implementation step 2 explicitly limits removal to the 4 local
  variables in `_report_readiness`; the plan explicitly states (`Scope > Out of
  scope`) that `_check_services()` and its `add_ok` calls are untouched. Reviewer
  should diff-check that no line in `_check_services()` changed.
- **Risk**: A future contributor could bypass the shared helper by hand-inlining the
  3-tier logic again in a 5th line added later (e.g. a new summary row), silently
  reintroducing the drift this fix removes.
  → **Mitigation**: Name the helper clearly (`_classify_summary_status`) and add a
  docstring stating it is the single source of truth for this classification, per
  Design section above; acceptance criteria in the requirement already call for
  verifiability "by code inspection."
- **Risk (low)**: Test additions to `tests/agent/test_startup.py` could collide
  with an already-large file (1300+ lines) making review harder.
  → **Mitigation**: Group the new tests in one clearly-named class/section placed
  near the existing `_check_services`-outcome tests (lines ~934-1270) for
  discoverability, rather than scattering them.
