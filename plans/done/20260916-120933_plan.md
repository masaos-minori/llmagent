## Goal
- Make production tool-safety validation fail closed: remove the broad
  exception-to-`None` fallback in tool-set resolution so a registry failure
  produces an actionable validation error instead of silently skipping
  safety-critical checks, and enforce one canonical, enum-backed
  security-profile model (`shared.mcp_config.SecurityProfile`) so an unknown
  profile value is rejected rather than silently accepted.

## Priority
High

## Scope
- **In-Scope**:
  - `scripts/shared/production_config_validator.py`'s tool-set resolution
    (`_resolve_known_tools()`) and its unused `security_profile` argument.
  - The two runtime call sites that invoke `ProductionConfigValidator.validate()`
    during agent startup: `scripts/agent/config_builders.py::build_agent_config()`
    and `scripts/agent/services/security_audit.py::audit_security_defaults()`.
  - Tests that currently encode the old fail-open/skip-on-registry-failure and
    unvalidated-profile behavior as correct, and new tests for the fail-closed
    replacement behavior.
  - Recording the fix's resolution in `docs/adr/ADR-004-environment-failure-handling-policy.md`'s
    `## Known Deviations` section, once implementation is verified.
- **Out-of-Scope**:
  - Unrelated refactoring of `scripts/agent/services/security_audit.py::audit_security_defaults()`
    beyond removing its duplicate known-tools fallback (its pre-existing high
    cyclomatic complexity, radon grade E, is not addressed here).
  - Fixing the pre-existing `lint-imports` `shared-is-leaf` contract violation
    (`shared.production_config_validator` importing `agent.tool_policy` /
    `agent.config_dataclasses`) — confirmed pre-existing and unrelated to this
    Plan's scope (see Risks).
  - Adding new `SecurityProfile` enum members — the canonical profile set is
    confirmed to already be exactly `{PRODUCTION}` (see Design); this Plan
    enforces that existing model, it does not redesign it.
  - `scripts/agent/startup.py` and other `scripts/agent/startup_*.py` files not
    named above — confirmed by repository evidence to not call
    `ProductionConfigValidator` directly (see Unknowns UNK-01).

## Background
`docs/adr/ADR-004-environment-failure-handling-policy.md` establishes fail-closed
environment-failure handling as an architectural requirement, and its
2026-09-04 revision already removed `SecurityProfile.LOCAL`, leaving a single
`SecurityProfile.PRODUCTION` member so that production-grade validation is
unconditional across all environments. This Plan applies that same
already-adopted fail-closed principle to the one remaining gap: production
tool-safety validation's own internal fallback and its currently-unused
`security_profile` parameter.

## Problem
`scripts/shared/production_config_validator.py::_resolve_known_tools()` catches
any exception from `shared.tool_registry.get_registry()` and returns `None`,
which causes the tool-safety-tier checks to be silently skipped rather than
reported as a validation error. `scripts/agent/services/security_audit.py::audit_security_defaults()`
independently duplicates the same broad-except-to-`None` pattern around its own
`get_registry()` call. Separately, `ProductionConfigValidator.validate()`
accepts a `security_profile: SecurityProfile | str` argument that is never
referenced anywhere in the method body (confirmed by `vulture`, 100%
confidence: "unused variable 'security_profile'"), so no profile value —
including one that does not exist in the `SecurityProfile` enum (e.g. the
legacy `"local"` string still used by several existing tests) — is ever
validated or rejected.

## Reason for change
Security-profile inconsistency and registry-unavailable validation skipping
affect the same production safety decision. The validator cannot apply
profile-specific guarantees if profiles are undefined or if the authoritative
tool set is unavailable and silently ignored. Repository evidence confirms
both gaps are real and currently present, not already resolved by an earlier
change.

## Implementation intent
Convert the internal registry-resolution fallback from "silently skip on any
exception" to "resolve explicitly, and surface a resolution failure as an
actionable entry in `ConfigValidationResult.errors`" — while continuing to
honor a `known_tools` value a caller supplies explicitly (including an empty
set) exactly as before. Inject the authoritative tool set explicitly from both
runtime call sites (`config_builders.py`, `security_audit.py`) rather than
relying on the validator's internal best-effort path. Add explicit
`SecurityProfile` coercion/rejection to `validate()`'s `security_profile`
argument so an unsupported value fails during configuration construction
instead of being silently ignored. Reconcile the existing tests that currently
assert the old fail-open behavior as correct.

## Requirements
- `REQ-001`: Remove the broad exception-to-`None` fallback in production
  tool-set resolution; a registry resolution failure on the default/`None`
  path must produce an actionable entry in `ConfigValidationResult.errors`
  instead of silently skipping the tool-safety-tier checks. Catch only
  documented, specific exception types for which a recovery path is actually
  defined (e.g. `ImportError` for a registry-module import failure,
  `ValueError` for a duplicate-registration failure raised by
  `ToolRegistry.register()`) — not a bare `except Exception`. This applies
  identically to the internal fallback in `production_config_validator.py`
  and to `security_audit.py`'s independent, duplicate fallback.
- `REQ-002`: Inject the authoritative known-tool set explicitly from both

  `security_audit.py::audit_security_defaults()`) rather than omitting

- `REQ-003`: Enforce one canonical, enum-backed security-profile model in

## Design
`_resolve_known_tools(known_tools)`'s contract changes from "return the
caller-supplied set, else best-effort-resolve from the registry, else `None`
on any error (silently skip the two tier checks)" to "return the
caller-supplied set unchanged when provided (including an empty set); when not
provided, resolve from `shared.tool_registry.get_registry()` and, on failure,
surface that failure as an entry in the enclosing `ConfigValidationResult.errors`
rather than silently returning `None`." This preserves the existing,
explicit-injection contract every current test already exercises
(`known_tools={...}` passed directly) while closing the only path that
silently skips validation — the internal default-resolution fallback.

`ProductionConfigValidator.validate()`'s `security_profile` argument goes from
entirely unused (confirmed by `vulture`) to being coerced against
`shared.mcp_config.SecurityProfile` (mirroring the existing
`MCPConfig.security_profile` post-init coercion precedent in
`config_dataclasses.py`) and rejected — recorded as a validation error — when
the value is not a defined enum member. Because the canonical profile set is
already exactly `{PRODUCTION}` (per ADR-004's 2026-09-04 revision), and no
existing check in `validate()` branches on `security_profile` today, REQ-004
is satisfied by confirming (via the new parameterized tests) that this
remains true after REQ-003's change — no relaxation branch is introduced.

Both runtime call sites (`config_builders.py::build_agent_config()` and
`security_audit.py::audit_security_defaults()`) are updated to resolve
`known_tools` explicitly via the same registry call, rather than one omitting
it entirely and the other maintaining its own independent, duplicate
best-effort fallback — eliminating the second copy of the anti-pattern this
Issue targets.

**Path classification: Path B** (per `skills/issue-to-plan/SKILL.md` Routing).
Criteria met: affects more than 3 files (6 Implementation Target Files), and
changes the runtime behavior of a broadly-referenced production-validation
entry point (`ProductionConfigValidator`, referenced by 14 test files per the
blast-radius measurement in Affected areas) in a way existing callers/tests
currently rely on (several tests assert the old fail-open/unvalidated-profile
behavior as correct and must be rewritten). Full architecture, dependency,
historical, and operational-dependency analysis was performed (see Reference
Files, Affected areas, and Risks R-1/R-2 for the concrete findings: the
pre-existing `lint-imports` `shared-is-leaf` violation, the >10-file blast
radius, and the two independent call sites requiring coordinated changes).
