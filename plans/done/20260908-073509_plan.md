# Plan: Add RAG read smoke test to post-restore logical verification

## Goal
Add a read smoke test to RAG post-restore verification, mirroring session's existing `_check_read_smoke_test` pattern, so that RAG's logical verification demonstrates actual read capability rather than relying solely on structural count checks.

## Priority
Medium

## Scope
- **In-Scope**: Add `_check_read_smoke_test` helper to `rag_consistency.py`; add `read_smoke_test_ok` field to `RagConsistencyReport`; wire result into `is_consistent()`; add failing smoke test scenario to `test_db_recovery.py`.
- **Out-of-Scope**: Adding a RAG write smoke test (unless H-07-01 explicitly permits mutation during RAG verification); modifying `session_consistency.py`; altering WAL/SHM handling paths; changing `recovery.py` control flow beyond consuming the new report field.

## Background
Post-restore verification in `scripts/db/recovery.py` (`_run_logical_verification`) re-runs physical integrity checking and domain-specific logical consistency checks for both `rag` and `session` targets after a restore. Session's consistency report already includes a read smoke test and a write smoke test (`_check_read_smoke_test`/`_check_write_smoke_test` in `scripts/db/session_consistency.py`, confirmed at lines 56-72 and 75-100 respectively). `scripts/db/rag_consistency.py` has no equivalent smoke-test function — confirmed via `rg -n "^def |smoke" scripts/db/rag_consistency.py`, which lists only `_collect_basic_counts`, `_collect_document_checks`, `_safe_url_count_query`, `_collect_url_counts_and_mismatches`, `_collect_affected_identifiers`, `check_rag_consistency`, `is_consistent`, and `summarize_issues` — RAG's post-restore verification checks table/index/relationship counts but never actually executes a read query representative of application usage.

Issue H-07-07 (already implemented per `issues/done/20260903-110305_h0707_add-rag-session-recovery-verification.md`) required "Read-only search smoke test succeeds" as one of the RAG verification requirements. The count-based checks (`fts_gap`, orphan counts, etc.) can all report zero/healthy while a structural issue outside what they measure (e.g. a broken FTS query due to a subtly wrong virtual-table configuration) still causes an actual search query to fail — the counts alone do not prove the database is usable for its actual read path the way `session`'s `_check_read_smoke_test` proves session/message reads work.

## Problem
`recover_corruption()`'s success predicate for `rag` currently depends only on structural counts, not on demonstrating that a representative read (matching what `session` already does) succeeds — this is a narrower guarantee than what the domain policy intends and than what `session` already provides for its own domain.

## Reason for change
`recover_corruption()`'s success predicate for `rag` currently depends only on structural counts, not on demonstrating that a representative read succeeds — this is a narrower guarantee than what the domain policy intends and than what `session` already provides for its own domain.

## Implementation intent
Add a `_check_read_smoke_test(db: SQLiteHelper) -> bool` helper to `scripts/db/rag_consistency.py`, mirroring `session_consistency.py`'s `_check_read_smoke_test` shape exactly (try/except around representative `SELECT COUNT(*)`-style read queries, boolean result) rather than inventing a different shape for RAG. Add `read_smoke_test_ok: bool = False` to `RagConsistencyReport`, mirroring `SessionConsistencyReport.read_smoke_test_ok`. Fold the new field into `is_consistent()`'s aggregate boolean. Do not touch `scripts/db/recovery.py`'s control flow — `_run_logical_verification()` already dispatches to `check_rag_consistency`/`is_consistent` generically, so a failing smoke test propagates to `action="logical_verify_failed"` without any change there.

## Requirements
- `REQ-001`: `RagConsistencyReport` includes a read-smoke-test result (`read_smoke_test_ok` field), mirroring `SessionConsistencyReport`'s existing field.
- `REQ-002`: `is_consistent()` for RAG returns `False` when the smoke test fails, even if all count-based checks are healthy.
- `REQ-003`: A failing RAG smoke test causes `recover_corruption()` to return `action="logical_verify_failed"`, consistent with the existing count-based failure paths.
- `REQ-004`: Existing RAG consistency tests (`test_recover_rag_fts_gap`, `test_recover_rag_missing_table`, `test_recover_rag_fts_orphan`, `test_recover_rag_vector_orphan`) continue to pass unchanged.
