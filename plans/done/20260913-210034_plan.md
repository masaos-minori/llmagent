## Problem
The existing "Generating Freshness Data" subsection fully documents *what* each
component does and their contract, but does not explain *why* calculation and
decision-making are split across two components — a reader might wonder whether
this split is deliberate architecture or incidental, without an explicit rationale.

## Reason for change
Add the missing design rationale to the existing subsection, completing the
Issue's 4-point request without duplicating the 3 points already well-documented
there.

## Implementation intent
Append one short paragraph to the end of the "Generating Freshness Data (Note on
Responsibility Boundaries)" subsection (after line 88's log-message note) stating:
`crawl_file()`/`CrawlPersister.save()` (I/O and metadata calculation) and
`DocumentManager._is_file_unchanged()` (business-logic decision) are deliberately
separated so each can be tested independently (calculation logic without a
database, decision logic without file I/O) and so the freshness-decision policy can
evolve (e.g. changing the skip/re-ingest rule) without touching crawl-time file
reading.
