# Plan: Fix logical contradiction in RAG parse error handling (ADR-010 compliance)

## Goal
Remove the spurious `_set_fallback_reason` call in the `ValueError` handler of `call_rag_service()`, aligning observability with actual system behavior — no fallback occurs on JSON parse errors per ADR-010 INV-07.

## Priority
Medium

## Scope
- **In-Scope**: Removing `_set_fallback_reason` call in `scripts/rag/pipeline_service.py`; updating the corresponding unit test in `tests/rag/test_rag_pipeline_service.py`
- **Out-of-Scope**: Changing the actual fallback policy, modifying other error handlers (4xx/5xx), changing the return contract of `call_rag_service()`

## Background
ADR-010 INV-07 states: "解析エラーはログに記録し、空結果として扱う" (log parse errors and treat them as empty results). The `call_rag_service()` docstring (lines 85-87) documents that JSON parse errors return `""` (empty string) — a valid empty result, NOT a failure that triggers fallback. However, the implementation calls `_set_fallback_reason` even though no fallback occurs.

## Problem
In `scripts/rag/pipeline_service.py`, the `ValueError` exception handler (line 175-182) calls `_set_fallback_reason(set_fallback_reason, f"http_parse_error: {e}")` before returning `("", None, 0.0)`. The return value `""` correctly prevents fallback, but the fallback reason callback fires anyway, producing misleading observability data — a "fallback reason" is logged for events that did not result in a fallback.

## Reason for change
Reporting a fallback reason without a fallback is a semantic error in the logging/metrics logic. To align the implementation strictly with ADR-010 and ensure observability metrics/logs accurately reflect system behavior.

## Implementation intent
Remove the call to `_set_fallback_reason` within the `ValueError` exception block in `scripts/rag/pipeline_service.py`. Rename and update the existing test `test_json_parse_error_calls_set_fallback_reason` → `test_json_parse_error_does_not_call_set_fallback_reason` to assert that the fallback reason callback is NOT invoked upon receiving malformed JSON.

## Requirements
- `REQ-001`: On JSON parse error, `call_rag_service` returns `("", None, 0.0)` — no fallback triggered
- `REQ-002`: No fallback reason is passed to the `set_fallback_reason` callback on JSON parse error
- `REQ-003`: Automated tests pass after the change

## Design
The fix is minimal and surgical: remove the single `_set_fallback_reason` call in the
`ValueError` handler. The return value `("", None, 0.0)` already correctly signals
"valid empty result, no fallback" per the docstring contract. No additional state
management or callback coordination is needed because the callback is purely
observational — its purpose is to record WHY a fallback occurred, and no fallback
occurred in this case.

The existing test `test_json_parse_error_calls_set_fallback_reason` encodes the buggy
behavior (asserting `len(reasons) == 1`). This test must be renamed to
`test_json_parse_error_does_not_call_set_fallback_reason` and corrected to assert
`len(reasons) == 0`, since the callback should not fire when no fallback occurs.

Caller analysis (`scripts/rag/http_augment.py:104-152`): The sole caller collects
fallback reasons into a local `http_fallback_reasons` list. On parse error, even with
the current bug, the collected reason is never propagated externally because
`result=""` causes line 128 to set `fallback_reason=None` and line 139's guard prevents
outer `_set_fallback_reason` invocation. Therefore the fix has zero observable impact on
callers — only internal observability consistency improves.

Task-size classification: Path A (affects ≤ 3 files, no public interface changes, no
database schema changes). Architecture analysis, dependency graphing, historical
analysis, and operational dependency inspection are skipped per routing rules.
