## Goal
- Define and implement deterministic routing from a detected canonical-source discrepancy to exactly one destination (Known Issue, Configuration Drift, Needs Confirmation, Canonical Source Conflict, or a documentation-correction task), so a conflict can never be silently suppressed or duplicated across inventories.

## Priority
Medium

## Scope
- **In-Scope**: documenting the 8 required routing rules in `docs/00_governance_01_documentation-policy.md`; adding a new "Part 3: Canonical Source Conflict" tracking section (Entry Template with the 12 required fields, Status Values, Severity/Blocking definitions, Resolution rule) to `docs/00_governance_03_issue-and-uncertainty-management.md`, following that document's existing Known Issues/Needs Confirmation pattern; defining Configuration Drift's own record location in the same document (currently named only once, in the Decision Target Canonical Source Matrix, with no tracking template); extending `docs/00_governance_01_documentation-policy.md`'s existing Merge Conditions to state severity/blocking behavior for Canonical Source Conflicts explicitly; registering the new routing/duplicate-detection logic in `M-01-05`'s validator (`tools/check_canonical_source_conflicts.py`) and its tests; updating the Governance Verification Matrix.
- **Out-of-Scope**: resolving any existing discrepancy this Plan's own routing rules would apply to; introducing a new external issue tracker (none is required — the existing `docs/00_governance_03_issue-and-uncertainty-management.md` lifecycle is reused); changing application runtime behavior; creating dedicated Known Issue/Needs Confirmation/PR templates as standalone files (confirmed, per `M-01-01`'s prior verification, that these are inline sections of `docs/00_governance_03_issue-and-uncertainty-management.md`, not separate files, and no PR template exists anywhere in the repository — see Reference Files).
- **Constraint**: do not permit the same discrepancy to be independently active in more than one inventory (Known Issues, Needs Confirmation, Configuration Drift, Canonical Source Conflict) simultaneously — cross-reference instead of duplicating (source Issue's Constraints section).

## Background
`M-01-01` through `M-01-06` establish how to identify a canonical source and detect a conflict, but not what happens after detection — a discrepancy may represent an implementation bug, an intentional but undocumented deviation, configuration drift, missing design ownership, or unresolved intent, and without explicit routing rules the same discrepancy could be duplicated across inventories or incorrectly resolved by editing a non-canonical document.

## Problem
Selecting a canonical source does not by itself resolve a discrepancy; without a deterministic destination, a detected conflict risks silent suppression or duplicate tracking.

## Reason for change
This is the final `M-01` issue that connects the canonical-source model (`M-01-01`-`M-01-06`) to the repository's existing issue-and-uncertainty lifecycle — without it, `M-01-05`'s validator can detect a conflict but has nowhere deterministic to route it.

## Implementation intent
Add the 8 routing rules and the 5 resolution rules as normative text in the governance documents, add the missing "Canonical Source Conflict" tracking category (reusing the existing Known Issues/Needs Confirmation template pattern) and a minimal Configuration Drift record location, and extend `M-01-05`'s validator to classify each finding into exactly one of the 5 destination categories with the 12 required record fields, using cross-references (never duplication) when a discrepancy is already tracked.

## Design
**Routing rules placement**: the 8 routing rules are added to `docs/00_governance_01_documentation-policy.md` immediately after `M-01-02`'s six-step resolution sequence (in "## Canonical Source Precedence"), since routing is the natural next step after that sequence's own final step ("record unresolved differences through the designated conflict workflow") — this section is exactly that "designated conflict workflow."

**Part 3: Canonical Source Conflict** (new section in `docs/00_governance_03_issue-and-uncertainty-management.md`, following "Part 1: Known Issues"'s existing pattern): Entry Template with the 12 required fields (Conflict ID `CSC-{NNN}`, Decision target, Claim type, Canonical source, Conflicting source or evidence, Conflict category, Impact, Severity [`High`/`Medium`/`Low`, reusing Known Issues' existing Severity Values], Blocking status [`Blocking`/`Non-blocking`], Required action, Owner [reusing Known Issues' existing Owner Values], Validation evidence); Status Values (`open`/`investigating`/`resolved`, where `resolved` means exactly one normative source remains and the entry is then removed per the Current-Specification-Only Policy, matching Known Issues' own Lifecycle wording).

**Part 4: Configuration Drift** (new, minimal section, same document): a lighter template (Drift ID `CD-{NNN}`, Decision target, Deployed value description, Approved operational value description, Severity, Status) — deliberately smaller than Part 3's template since Configuration Drift concerns exactly one dimension (deployed-vs-approved value), not the fuller canonical-source-conflict shape.

**Duplicate-active-record prevention** (`REQ-002`'s Constraint): each new Part 3/Part 4 entry's template includes a `Related` field (matching Known Issues' existing `Related` field) that cross-references any existing Known Issue/Needs Confirmation/Configuration Drift/Canonical Source Conflict entry for the same underlying discrepancy — `tools/check_canonical_source_conflicts.py`'s extension (`REQ-008`) checks this field before creating a new entry recommendation, refusing to recommend a second independent entry for a discrepancy it can already match against an existing one by decision-target-and-claim-type.

**Validator extension** (`tools/check_canonical_source_conflicts.py`): each finding `M-01-05`'s existing checks already produce is now additionally classified into exactly one of the 5 destinations (Known Issue / Configuration Drift / Needs Confirmation / Canonical Source Conflict / documentation-correction task) per this Plan's `REQ-001` routing rules, and the finding's output gains the 12 required record fields where the destination is Canonical Source Conflict (a lighter field set for the other 4 destinations, matching each one's own existing/newly-added template).
