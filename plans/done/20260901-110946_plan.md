## Goal
- Add `tools/manage_workitem_stage.py`, a CLI with subcommands `close-issue`, `close-plan`,
  and `close-implementation`, that performs the archival `git mv` for each workflow stage
  transition and blocks `close-implementation` when the target file's own Execution Status
  table still has a `Pending` row (unless overridden with `--force --reason`).

## Priority
Medium

## Background
This session performed several `git mv` stage-transition operations by hand and manually
edited Execution Status tables while doing so. `skills/issue-to-plan`'s Core Execution Rules
state the archival move to `issues/done/` is gated on validation, not approval, and "MUST NOT
be skipped" — currently enforced only by an agent remembering to do it, not by tooling.

## Problem
`skills/issue-to-plan` Step 10 and `skills/plan-to-implementation-procedure` Step 4 each
require a `git mv` of the processed file into its `done/` counterpart once validation passes.
An implementation procedure's own Execution Status table is hand-edited to mark steps
Completed/Pending. This is currently done by directly editing files and running `git mv` by
hand, with no tool enforcing that the move only happens after gating validation, or that the
Execution Status table stays consistent with the actual move.

## Reason for change
A dedicated stage-transition tool turns a multi-step manual process (validate → `git mv` →
verify) into one command, reducing the chance of a skipped move (a fully-processed
issue/plan/implementation left outside its `done/` directory) or an inconsistency between an
Execution Status table's `Pending` rows and an archival move that already happened.

## Implementation intent
Implement `tools/manage_workitem_stage.py` as a single-file CLI with three subcommands,
following the existing `argparse` subcommand pattern used by `tools/manage_frontmatter.py`
(`add-missing` / `dedupe-lists`). Each subcommand takes a path argument and performs the
move via `git mv` semantics (GitPython, matching the repo's established
`scripts/shared/git_helper.py` / `scripts/mcp_servers/git/git_service.py` usage of the
`gitpython` dependency already in `pyproject.toml`) rather than a plain filesystem rename —
so the workflow's own "use `git mv` only, no fallback" rule (`rules/workflow-lifecycle.md`
Archival Move) is enforced by the tool itself, not left to agent discipline. Only
`close-implementation` inspects file content (the Execution Status table, per
`templates/execution-status.md`'s canonical structure) to decide whether to block; the other
two subcommands perform an unconditional move once the source exists and the destination
does not.

## Requirements
- `REQ-001`: `close-issue <issue-path>` moves `issues/{file}.md` to `issues/done/{file}.md`
  using `git mv` (or the moral equivalent preserving history), refusing if source is missing
  or destination already exists.
- `REQ-002`: `close-plan <plan-path>` moves `plans/{file}.md` to `plans/done/{file}.md` with
  the same move semantics and refusal conditions as `REQ-001`.
- `REQ-003`: `close-implementation <implementation-path>` moves
  `implementations/{file}.md` to `implementations/done/{file}.md`, but first parses the
  target file's `### Execution Status` table (`templates/execution-status.md` structure) and
  refuses the move if any row's `Status` column is `Pending`, printing which row(s) are
  blocking.
- `REQ-004`: `close-implementation`'s block in `REQ-003` can be overridden by passing both
  `--force` and a required `--reason "..."`; when overridden, the move proceeds and the
  supplied reason is included in the printed result.
- `REQ-005`: The tool does not edit the substantive content of the file being moved beyond
  the move itself — `close-implementation` only reads Execution Status rows to decide
  whether to block; it does not fill in, correct, or rewrite any row.
- `REQ-006`: Every subcommand prints a clear success or failure result, including the
  resulting path, and exits non-zero on failure (missing source, existing destination,
  blocked-and-not-forced, or a `git mv` failure).
- `REQ-007`: `tools/TOOL_DESCRIPTIONS.md` documents the new tool consistently with its
  existing per-tool entry format, and `tools/check_tool_descriptions_sync.py` passes after
  the addition.
- `REQ-008`: `tests/tools/test_manage_workitem_stage.py` covers, using a temporary git
  repository fixture (not the live repository): a successful move for each of the three
  subcommands; a blocked move due to a `Pending` Execution Status row; and a forced move via
  `--force --reason`.

## Design
`manage_workitem_stage.py` follows the established `tools/manage_frontmatter.py` shape: one
`argparse` parser with subcommands, each subcommand backed by its own `cmd_*` function
importable for direct unit testing (mirroring `tests/tools/test_manage_frontmatter.py`'s
`from tools.manage_frontmatter import cmd_add_missing` pattern). `close-issue` and
`close-plan` share a single move helper (source path → destination path under the sibling
`done/` directory, refusing on missing source or existing destination) since their behavior
is otherwise identical apart from the directory pair — `close-implementation` layers the
Execution Status parse-and-block check on top of the same move helper before invoking it.
Execution Status parsing reads only the `### Execution Status` Markdown table (per
`templates/execution-status.md`) using a simple line-based table parser (Markdown table row
splitting), not a general Markdown parser dependency — consistent with this repo's existing
tools, none of which pull in a Markdown-table-parsing library for this kind of check. The
move itself uses GitPython (`import git`, lazily, matching `scripts/shared/git_helper.py`'s
pattern) rather than `subprocess` invocation of the `git` CLI, keeping the dependency surface
consistent with the rest of the repo's git-touching code — the exact GitPython call is
UNK-02, to resolve at the implementation-procedure stage.

## Risks
- **Risk**: A `git mv` performed via GitPython on a file with uncommitted local
  modifications could behave unexpectedly (e.g. refuse, or stage a modified+renamed file) →
  **Mitigation**: the shared move helper checks the source file's git status before moving
  and surfaces a clear error rather than silently proceeding; covered by REQ-006's
  failure-result requirement.
- **Risk**: A hand-written line-based Execution Status table parser could misparse a
  malformed or reordered table (e.g. extra columns, missing header separator) and either
  wrongly block or wrongly allow a move → **Mitigation**: REQ-008's test coverage includes a
  well-formed fixture table; a follow-up hardening pass (not blocking this Plan) can add
  malformed-table test cases once the parser's real-world failure modes are observed.
- **Risk**: Duplicating file-move logic across three subcommands instead of true code reuse
  could let `close-issue`/`close-plan`/`close-implementation` drift apart over time →
  **Mitigation**: the Design section specifies one shared move helper used by all three, not
  three independent implementations.
