## Goal
Add a per-session message count to the `/session list` output, add the missing roundtrip
test (a listed ID loads and deletes successfully), and complete documentation of the data
subcommands — finalizing the already-implemented `/session list` command so it fully matches
its specification.

## Priority
Medium

## Scope
- **In-Scope**:
  - Add `message_count` to each row returned by `AgentSession.list_sessions()` via a
    `LEFT JOIN` on the `messages` table grouped by `session_id`.
  - Extend the frozen `SessionRow` dataclass with a `message_count` field and pass it
    through `_session_list`, then render it as a new table column.
  - Add a unit test for `list_sessions()` including the message count.
  - Add a roundtrip command test: take an ID printed by `/session list` and assert
    `/session load` and `/session delete` both succeed for it.
  - Update the Session Category doc to list the data subcommands (`list`, `load`, `rename`,
    `delete`) alongside the maintenance subcommands.
  - Verify/correct the session lifecycle reference in the persistence doc.
- **Out-of-Scope**: reimplementing `/session list` or any subcommand; changing
  `/session load` or `/session delete` semantics; adding columns beyond the message count;
  reintroducing `SQLiteSessionStore`.

## Background
The `/session list [n]` command lists recent sessions via `AgentSession.list_sessions()`,
queried through `SQLiteHelper("session")` against `session.sqlite`. It is dispatched in
`scripts/agent/commands/cmd_session.py` (`_cmd_session`, `sub == "list"` ->
`_session_list`) and its help text already advertises `list [n]`.

The originating requirement specified five items:
- production-path listing returning newest-first with ID, title, created date, and message
  count (no `SQLiteSessionStore`)
- a `list [n]` subcommand (default 20, mark the current session)
- `list` in the `/session` help text
- a test that a listed ID works with `/session load` and `/session delete`
- doc updates (Session Category, session lifecycle)

Investigation confirms the `list [n]` subcommand and help text are done, and the stated
completion condition (find past session IDs within the REPL and use them for `load` and
`delete`) is already met. Only the message-count column, the roundtrip test, and full doc
coverage remain.

## Problem
The `/session list` output omits the message count that the specification requires, so a
user cannot gauge a session's size from the REPL before loading it. In addition, no test
verifies the list -> load/delete contract, and the docs under-document the data
subcommands (they currently enumerate only the maintenance subcommands).

## Reason for change
Without the message count, triaging which sessions are large before loading is guesswork.
Without a roundtrip test, a regression in the list -> load/delete contract would go
undetected. The docs currently list only maintenance subcommands, so readers miss the data
subcommands (`list`, `load`, `rename`, `delete`).

## Implementation intent
Extend the existing `list_sessions()` result and `_session_list()` display to include a
per-session message count, computed with a `LEFT JOIN` on the `messages` table grouped by
`session_id`. Preserve newest-first ordering, the `is_current` marker, the default limit
of 20, and title truncation. Add a roundtrip test. Update the docs. Do not reintroduce
`SQLiteSessionStore`.

`_session_list` renders rows via the frozen `SessionRow` dataclass in
`scripts/agent/services/models.py`; `message_count` MUST flow through that dataclass
(which has a single construction site in `_session_list`) rather than being read ad hoc in
the render loop.

## Design
- **Architecture**: The change stays within the `agent` layer. `list_sessions()` opens
  `SQLiteHelper("session")` and runs a single read query against `session.sqlite`; adding a
  `LEFT JOIN` introduces no new imports. `lint-imports` reports 6 contracts, 0 broken, so
  there is no import-boundary risk.
- **Data flow**: `list_sessions()` returns one dict per session carrying a new
  `message_count` key -> `_session_list` maps each dict to the (extended) frozen
  `SessionRow` dataclass -> the table renderer emits the new column. `message_count` flows
  through `SessionRow` rather than being read ad hoc in the render loop.
- **Counting semantics**: `COUNT(m.message_id)` over
  `LEFT JOIN messages m ON m.session_id = s.session_id`, grouped by `s.session_id`, so
  zero-message sessions still appear with count `0`.
- **Ordering**: preserved as `ORDER BY session_id DESC`. `session_id` is an AUTOINCREMENT
  key, so this is strictly newest-first; no chronological sort is required.
- **Limit guard**: non-positive limits remain guarded (SQLite `LIMIT -1` returns all rows).
