## Background
The Issue's cited claim
(`docs/03_rag_02_03_ingestion_pipeline-chunksplitter.md:273-274`: "Crawl artifacts
do not carry `normalized_content` / `chunk_index` / `source_file` / `chunk_type` /
`chunking_strategy` as input keys — `read_crawl_json()` sets these internally
rather than reading them") is confirmed accurate, and is already clearly stated
(lines 273-277), not "buried" as the Issue suggests.

**Re-verified 2026-09-13** (this cycle): confirmed there is exactly **one**
cross-field validation rule in this document's scope — crawl artifacts' `content`
(line 265: "empty string allowed only when `code_blocks` is non-empty (cross-field
rule)"), enforced at `pipeline_utils.py:141-145`
(`if not content and not code_blocks: raise ChunkFormatError(...)`). Chunk
artifacts' `content` field explicitly has no such exception (line 284: "no
cross-field exception here, unlike crawl artifacts"). No other cross-field
dependency exists among either artifact type's fields (confirmed by reading both
full field tables, lines 260-295, and their validators,
`pipeline_utils.py:100-230`).

The rule's rationale, while not stated as a comment at the validation site itself,
is traceable to a specific upstream behavior: `CrawlPersister.save()`
(`crawl_persister.py:69-77`, confirmed during a sibling issue's investigation this
same cycle) stores `.py` files with `content=""` and the actual source in
`code_blocks=[content]` ("Python files are stored as code blocks so the code
chunker applies"). This is the only crawl-artifact producer confirmed to produce an
empty `content` with non-empty `code_blocks` — the cross-field rule exists to allow
this specific, legitimate empty-content case while still rejecting a payload that
is empty in both fields (which would indicate a genuinely broken/incomplete crawl
result).

## Problem
The single existing cross-field rule is stated in a table cell (line 265) without
a dedicated explanation of its rationale or example payloads, making it easy to
overlook when adding a new field or reviewing validation logic — though it is not,
contrary to the Issue's framing, one of several undocumented rules; it is the only
one, and its "what" is already documented, just not its "why" or worked examples.

## Reason for change
Add a dedicated subsection consolidating the rule, its rationale (traced to `.py`
file handling), and example payloads, so a developer can find the complete picture
in one place rather than needing to separately locate the table cell, the
validator code, and the upstream producer that motivates the exception.

## Implementation intent
Add a "Cross-Field Validation Rules" subsection after the crawl/chunk artifact
tables (after line 299) stating: (1) the single confirmed rule — crawl artifacts'
`content` may be empty only if `code_blocks` is non-empty; (2) its rationale —
traced to `CrawlPersister.save()`'s `.py`-file handling, which stores source code
in `code_blocks` with `content=""`; (3) that chunk artifacts have no equivalent
exception; (4) one valid example (`.py` file: `content=""`, `code_blocks=["def
foo(): ..."]`) and one invalid example (`content=""`, `code_blocks=[]` → rejected).
