# Plan: Resolve tool_definitions FATAL/WARNING severity contradiction between docs and implementation

## Goal
Make the documented severity behavior of `tool_definitions` startup findings in
`docs/05_agent_10_01_operations-and-observability-startup-and-health.md` consistent with the
actual behavior implemented in `scripts/agent/services/mcp_tool_discovery.py`, and lock that
behavior down with tests across the full `(strict, security_profile)` matrix.

## Scope

**In scope:**
- Decide and record the intended severity policy for `tool_definitions` findings (Option A vs
  Option B, see Design).
- Update `docs/05_agent_10_01_operations-and-observability-startup-and-health.md`'s
  "運用上の注意" / "起動時検証の重大度マッピング" section for the `tool_definitions` bullet
  (Option B) OR update `_check_tool_definitions_finding()` and the module docstring in
  `scripts/agent/services/mcp_tool_discovery.py` (Option A) — whichever option is chosen.
- Add parametrized test coverage in `tests/agent/services/test_mcp_tool_discovery.py` for
  `tool_definitions` findings across `(strict, security_profile)`, covering both the
  `has_issues` branch and the `except RuntimeError` branch.

**Out of scope:**
- Duplicate-tool-name severity behavior (already correctly documented and tested as
  always-FATAL; must not change).
- Drift-finding (`routing_drift_live` / `_build_drift_findings`) severity behavior (already
  covered by `TestDriftFindings`; must not change).
- `malformed-capabilities` finding behavior (already covered by
  `test_malformed_capabilities_produces_warning_not_fatal`; must not change — note this
  existing test's name asserts WARNING-only for malformed-capabilities, which is a *separate*
  finding type from `tool_definitions` and is not touched by this plan).
- Any change to `mcp_tool_discovery`'s own top-level failure severity (doc line 64: "本番/
  ローカル問わず FATAL" — this is about the *service call itself* failing, not about
  `tool_definitions` findings, and is out of scope).
- Any actual code/doc/test edit during this planning cycle (this plan document is the only
  output of this workflow phase).

## Design

### Evidence gathered
- `scripts/agent/services/mcp_tool_discovery.py:33-35` (module docstring): "Unified severity
  scheme (drift, tool-definitions, malformed-capabilities): `is_fatal = strict or
  (security_profile == PRODUCTION)`. Duplicate-tool findings are the one exception to this
  scheme — they are always FATAL." This explicitly lists `tool-definitions` as a member of the
  unified scheme, on equal footing with drift and malformed-capabilities, with only duplicates
  called out as the exception.
- `_check_tool_definitions_finding()` docstring (lines 389-395): describes converting
  `RuntimeError` into a `StartupCheckOutcome` with "the unified severity" and frames this as a
  deliberate fix for an "old quirk where strict-mode drift detection was silently downgraded to
  'skipped' by an unrelated exception handler" — language describing an intentional
  improvement, not an accidental regression.
- The actual code in both branches of `_check_tool_definitions_finding()` (lines 400-404 and
  411-416) calls `_is_fatal_severity()` uniformly, exactly matching the docstring's stated
  intent. There is no separate, tool_definitions-specific carve-out anywhere in this file.
- `scripts/agent/startup.py:371-375` treats any `FATAL` status from any `mcp_tool_discovery`
  finding uniformly — no per-finding-type exception exists at the call site either.
- The doc's line 63 claim ("常に WARNING にダウングレードされる") has no corresponding
  carve-out in the code and appears to simply predate the unified-scheme refactor, while line
  64 (about `mcp_tool_discovery`'s own top-level failure) is unrelated and unaffected.
- No test currently locks in either behavior for the production + non-strict case (confirmed:
  `TestUnifiedSeverity.test_severity_unified_for_duplicates` at line 1368 parametrizes only
  duplicate findings; `test_tool_definitions_check_surfaces_as_outcome_not_exception` at line
  1428 uses `_make_ctx(...)`'s default `security_profile=SecurityProfile.LOCAL` and
  `tool_definitions_strict=False` only — confirmed via `_make_ctx`'s signature at line 61-65 —
  so PRODUCTION and strict=True are both untested for this finding type).

### Decision: Option B is chosen (implementation is correct; doc must be updated)

Rationale: the module docstring's own words are the strongest available signal of intent in
this repo, and they unambiguously group `tool_definitions` into the unified scheme alongside
drift and malformed-capabilities — this is not incidental phrasing, it is a design note added
specifically to explain why the FATAL/WARNING decision is centralized in
`_is_fatal_severity()`. The `_check_tool_definitions_finding()` docstring further frames the
current behavior as a bug fix ("resolves the old quirk"), meaning a return to
"tool_definitions is never FATAL" (Option A) would re-introduce the very quirk the code was
written to eliminate: an operator running in `security_profile=PRODUCTION` with
`tool_definitions_strict=True` would have a tool-definition mismatch silently downgraded to a
non-blocking WARNING, which is precisely the failure mode the docstring says was already fixed
once. Per the workflow's fallback rule ("infer authoritative intent from related design
history if a stakeholder decision is not obtainable"), this in-repo documentation is treated as
the authoritative intent, and no external stakeholder input is required to proceed.

Consequently, the doc is the artifact that is wrong, not the code. Option B's edit is a pure
documentation correction: update the `tool_definitions` bullet in
`docs/05_agent_10_01_operations-and-observability-startup-and-health.md` (line 63) to state
that `tool_definitions` follows the same unified severity scheme as `drift` and
`malformed-capabilities` (FATAL when `strict` or `security_profile == PRODUCTION`, WARNING
otherwise), phrased in parallel with the `mcp_tool_discovery` bullet immediately below it
(line 64) for stylistic consistency.

### Option A (rejected, recorded for traceability)
Exclude `tool_definitions` from the unified scheme by hard-coding
`StartupCheckStatus.WARNING` in both branches of `_check_tool_definitions_finding()`, and
narrow the module docstring's "Unified severity scheme" line to drop `tool-definitions` from
the list (parallel to how duplicates are already called out as the FATAL-only exception).
Rejected because it contradicts the explicit, deliberate-sounding docstring evidence at lines
33-35 and 389-395, and because it would resurrect the exact bug the code comments say was
already fixed. This option remains implementable if a future stakeholder decision overrides
the in-repo evidence relied on here (see Risks).

## Risks
- **Risk**: The Option B decision was inferred from in-repo docstring evidence rather than an
  explicit stakeholder/product-owner sign-off; if the actual intended policy is Option A, this
  plan's implementation phase would ship the wrong fix (a doc change that further entrenches
  an unintended production-FATAL behavior). Likelihood: low (the docstring evidence is direct
  and specific, not circumstantial) but impact would be operational (unexpected startup
  failures in production for operators who trusted the old doc wording).
  **Mitigation**: The Design section records both options and the rejected alternative in
  full, and the requirement document itself frames this as an explicitly revisable decision
  point. If a stakeholder later disagrees, Option A's steps are already specified in the
  requirement's "Implementation intent" section and can be substituted without re-analysis.
  Tracked as a recorded, non-blocking risk (see `issues/20260819-184236_risks.md`).
- **Risk**: Doc-only wording drift in the future (someone edits `_is_fatal_severity()` again
  without updating the doc) could re-create the same contradiction this plan fixes.
  Likelihood: medium (this has already happened once). Impact: low-medium (same class of
  operator confusion as the current issue, not a new failure mode).
  **Mitigation**: Recommend (for the implementation phase, not this planning cycle) adding a
  code comment near `_is_fatal_severity()` cross-referencing the doc section name
  ("運用上の注意 / 起動時検証の重大度マッピング") so future edits are more likely to trigger a
  doc check. This is a suggestion for the implementation phase; not itself an action of this
  plan.
- **Risk**: The new parametrized tests could be written in a way that only exercises the
  `has_issues`/`RuntimeError` branches in isolation and misses an interaction where both a
  `tool_definitions` issue and a duplicate/drift finding occur in the same `discover_all()`
  call, potentially masking a status-aggregation bug. Likelihood: low (existing tests already
  isolate finding types successfully). Impact: low.
  **Mitigation**: Implementation phase should keep at least one existing multi-finding test
  (if any) unchanged as a regression guard; no new combined-finding test is mandated by the
  requirement's acceptance criteria, so this is noted but not escalated to a blocking issue.
