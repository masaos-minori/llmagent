## Goal
- Make the server-side audit records (`mcp_tool_exec`) and application log lines of shell, git, github, cicd, rag-pipeline and web-search MCP servers reach a log file, and make the documentation state where each server's records actually go.

## Priority
Medium

## Scope
- **In-Scope**: Give the six server modules the shared file-backed `Logger` used by the other four servers; keep the existing tests working through a propagation fixture; add a test that every server's audit logger is enabled and writes to a file; correct the audit and log documentation; correct the git audit documentation.
- **Out-of-Scope**: Changing the audit record schema or error-type vocabulary; Agent-side `tool_exec` auditing; log rotation and retention; creating a shared server-side `audit.log` sink (verification showed none exists and none is needed); making an unopenable log file fatal (UNK-01); the other MCP startup issues.

## Background
`mcp_servers/audit.py::_audit_log()` serializes one JSON-lines record and calls `server_logger.info(...)`. file-read, file-write, file-delete and mdq create `shared.logger.Logger(__name__, "/opt/llm/logs/<name>.log")`, which attaches a file and a stream handler and sets INFO. The six servers above create `logging.getLogger(__name__)` instead, and `MCPServer.run_http()` configures only the `uvicorn.*` loggers. The documentation says `mcp_tool_exec` records land in a shared `<log_dir>/audit.log` and that servers write `<server>-mcp.log` application logs.

## Problem
After building the `uvicorn.Config` that `run_http()` creates and importing each server module, the module logger of shell, git, github, cicd, rag_pipeline and web_search reported INFO disabled and zero handlers, while the other four reported INFO enabled with two handlers. Every `_audit_log(logger, ...)` call and `call_tool` log line of the six servers is therefore dropped. Verification refined the picture: no server-side code writes `audit.log` (only the Agent does, for `tool_exec`), so even working servers write `mcp_tool_exec` to their own application log; only five `Logger(...)` sites exist, so the documented `shell-mcp.log`, `github-mcp.log`, `git-mcp.log`, `cicd-mcp.log` and `rag-mcp.log` do not exist; the Agent-side Layer 1 record and the dedicated shell, github and file-delete audit files remain. `GitConfig.audit_log_path` is documented as unused.

## Reason for Change
Audit records exist to reconstruct who did what through write-capable tools. The gap is invisible: tests pass, the documentation claims a shared audit log, and no error is raised.

## Implementation Intent
Follow the pattern the four working servers already use: each server module creates a shared `Logger` writing its own application log, and the audit records go there. Do not invent a new shared sink. Keep `shared.logger.Logger`'s existing behavior (stderr fallback when a file cannot be opened) and keep tests able to capture the server loggers.

## Requirements
- `REQ-001`: The six server modules create their module `logger` with `shared.logger.Logger(__name__, "/opt/llm/logs/<name>.log")` using the names `shell-mcp.log`, `git-mcp.log`, `github-mcp.log`, `cicd-mcp.log`, `rag-mcp.log` (as documented) and `web-search-mcp.log`, so INFO is enabled and handlers are attached after import.
- `REQ-002`: Type annotations that name `logging.Logger` for these loggers accept the shared `Logger` (git's `_audit_log_safe`), keeping `mypy` clean.
- `REQ-003`: Existing tests that read the server loggers through `caplog` keep working through a test fixture that restores propagation to the root logger for these six loggers.
- `REQ-004`: A test proves that for all ten server modules the audit logger has INFO enabled and a handler, and that a `_audit_log` call writes one parseable record to a file under a temporary log directory.
- `REQ-005`: The documentation states, per server, where `mcp_tool_exec` records and application logs are written (each server's own application log; `audit.log` is the Agent's), without claiming a shared server-side `audit.log`.

## Design
Path B (more than three files; start-time behavior change). Architecture analysis: `lint-imports` reports all 6 contracts kept; `shared.logger` is in the leaf layer already imported by four sibling servers, so no new dependency edge appears. The change mirrors file-read, file-write, file-delete and mdq: a module-level `Logger(__name__, "/opt/llm/logs/<name>.log")`. `Logger` attaches a file and a stream handler, sets INFO, redacts bearer tokens, and falls back to stderr if the file cannot be opened. It sets `propagate = False`, which makes `caplog` blind to these loggers; a worktree experiment that switched the six servers produced 37 failures in 12 test files for exactly that reason, so a single autouse fixture in a new `tests/mcp_servers/conftest.py` restores propagation for the six loggers instead of editing 12 files. `web_search_service.py` already opens `web-search-mcp.log` with its own `Logger`; two handlers on one file are acceptable and the file stays the documented one. Historical analysis (30 days): server modules 2-6 commits each; the MCP documents 4-33 commits (`mcp_04_05_git.md` is the highest, so keep its edit minimal and rebase before committing). Operational dependency: production runs binaries, so a deploy rebuilds them and the log directory `/opt/llm/logs` must be writable by the server user (it already is for the four working servers).
