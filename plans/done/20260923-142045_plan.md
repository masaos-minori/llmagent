## Goal
Change `tools/check_docs_structure.py`'s cross-reference resolution (front-matter
`related`/`source` entries and body Markdown links) from directory-relative resolution
to a repository-wide basename lookup, and make its default file-discovery glob
recursive, so the tool keeps working correctly once the planned `docs/` folder
reorganization moves files into area subfolders without renaming them.

## Priority
High

## Scope
- **In-Scope**: `tools/check_docs_structure.py`'s `check_related_links()`,
  `check_links()`, and `main()`'s default glob; new/extended unit test coverage in
  `tests/tools/test_check_docs_structure.py` for cross-directory resolution, missing-
  file detection, already-path-qualified references, and recursive default discovery.
- **Out-of-Scope**: physically moving any file under `docs/`; removing or shortening
  any filename prefix; `tools/_docs_consistency_lib.py`'s prefix-based, non-recursive
  `discover_md_files()`; any hardcoded `docs/<file>.md` path constant in any other tool;
  any CI workflow change (including the `governance-docs-consistency.yml` gap
  identified in Risks below — tracked there, not fixed here); updating
  `tools/TOOL_DESCRIPTIONS.md` (see Documentation Impact).

## Background
A separate investigation (2026-09-23) evaluated reorganizing `docs/` into 11 area-based
subfolders (`00_governance/`, `01_overview/`, `10_adr/`, `21_rag/`, `22_mcp/`,
`23_agent/`, `24_eventbus/`, `40_shared/`, `41_db/`, `90_deployment/`, `91_security/`)
while keeping every existing filename unchanged (no prefix removal, no renaming). That
investigation produced 16 issues (`docsreorg01`-`docsreorg16`) breaking the work into a
prerequisite-tooling phase, per-area physical-move issues, and a final validation
sweep. This Plan covers `docsreorg01`, the first prerequisite: every per-area move
issue explicitly depends on it.

## Problem
`tools/check_docs_structure.py`'s `check_related_links()` (lines 176-194) and
`check_links()` (lines 143-152) both resolve a referenced filename as
`(path.parent / entry).resolve()` — relative to the *referencing* file's own directory,
not a repository-wide search. Re-measured against the current `docs/` tree (2026-09-23,
188 files, confirmed globally unique basenames — zero duplicates): of 645 front-matter
`related`/`source` entries, 58 already cross what would become a folder boundary under
the planned reorg; of 811 body Markdown links, 240 do. Moving files into the planned
subfolders would make all 298 of these references resolve to a non-existent path and
start failing `check_docs_structure.py`, even though the referenced files still exist.

(Note: the source Issue's Problem section cited 650 front-matter entries and 1
pre-existing broken reference; re-verification found the current counts are 645
entries / 0 pre-existing broken — a concurrent, unrelated fix already landed for that
one broken reference. The cross-folder counts driving this Plan, 58 and 240, are
unchanged.)

Additionally, `main()`'s default glob pattern is `docs/*.md` (line 241) — non-recursive
— so running the tool with no arguments already misses files under `docs/adr/`,
`docs/eventbus/`, and `docs/databases/` today, before any reorg move happens.

## Reason for change
The planned folder reorganization explicitly keeps every filename unchanged and moves
files only. Every filename in `docs/**/*.md` is currently globally unique (verified: 0
duplicate basenames across all 188 files today), so a global basename lookup is
unambiguous and safe to adopt now, before any files move. Doing this first avoids
manually rewriting 298 relative-path references by hand once files relocate, and keeps
`check_docs_structure.py` passing throughout the migration. This Plan is a hard
dependency of every one of the 11 per-area physical-move issues already filed.

## Implementation intent
Build one basename → path index by scanning `docs/**/*.md` once per `main()`
invocation, and thread it through `validate_file()` into `check_related_links()` and
`check_links()` so both resolve a reference by looking it up in the index instead of
via `path.parent`-relative resolution. Preserve the existing behavior of reporting a
"references missing file" / "broken link" issue when a referenced basename is not in
the index. Preserve correct resolution for references that already include a relative
directory component (`adr/ADR-010-rag-fallback.md`,
`../00_governance_01_documentation-policy.md` — both already in use today, confirmed by
Reference Files below) by falling back to the existing `path.parent`-relative check
when the bare-basename lookup does not apply, rather than replacing that check outright.
Add a hard failure (not a silent pick-one) if the index construction ever finds two
files sharing a basename, since the whole reorg's continued safety depends on that
uniqueness holding. Change `main()`'s default glob from `docs/*.md` to `docs/**/*.md`.

## Requirements
- `REQ-001`: Build a single repository-wide basename → path index by scanning

- `REQ-002`: `check_related_links()` resolves each `related`/`source` entry via the

- `REQ-003`: `check_links()` resolves each body Markdown link target the same way as

  the tool fails loudly (non-zero exit, explicit error message naming both paths) —
  it must not silently resolve to the first match found.
- `REQ-005`: `main()`'s default glob pattern changes from `docs/*.md` to `docs/**/*.md`.
- `REQ-006`: Add unit test coverage in `tests/tools/test_check_docs_structure.py` for:
  (a) cross-directory bare-filename resolution succeeding, (b) a genuinely missing
  filename still being reported, (c) a reference that already includes a relative
  directory component still resolving correctly, and (d) the new default glob covering
  a file in a subdirectory.

## Design
Add a private module-level helper, e.g. `_build_basename_index(root: Path) -> dict[str, Path]`,
called once at the top of `main()` after argument parsing (always scanning
`docs/**/*.md` regardless of the caller's own glob arguments, since the index must
cover every file that could be a valid cross-reference target, not only the files being
validated in this run). Thread the resulting index through `validate_file()` as a new
required parameter, and from there into `check_related_links()` and `check_links()`
(both already take `path` and `content`; add `basename_index: dict[str, Path]` as a
third parameter to each).

Resolution logic per reference, in order:
1. If the entry contains a path separator or starts with `.` (an existing directory-
   qualified reference like `adr/ADR-010-rag-fallback.md` or
   `../00_governance_01_documentation-policy.md`), resolve it via the existing
   `(path.parent / entry).resolve()` check first — preserves current behavior for the
   references confirmed in Reference Files above.
2. Otherwise (a bare filename), look it up in `basename_index` by `Path(entry).name`.
   Report "missing file" / "broken link" if absent from the index.

Index construction: build `basename_index` by iterating `Path("docs").rglob("*.md")`
once; if a basename is seen twice, do not silently keep the first — raise (or record
and report, then exit non-zero from `main()`) a clear "duplicate basename: '{name}'
found at both {path1} and {path2}" error before any check even runs, satisfying REQ-004
without deferring the failure into individual per-file check output.

This keeps `check_related_links()`/`check_links()`'s existing structure and signatures
mostly intact (one added parameter each), avoids introducing a class or new module, and
localizes the whole change to `tools/check_docs_structure.py`.

No production code, schema, or `docs/*.md` content change — this Plan is
tooling-internal-logic-only.

**Known limitation carried over from the source Issue (not solved by this Plan)**:
this change only makes the automated checker tolerate a bare-filename cross-folder
reference. It does not fix how the same bare-filename link renders for a human reading
the file directly on GitHub or in a plain Markdown viewer — those follow the literal
relative path and will 404 once the referencing and referenced files move into
different folders during the physical-move issues. This Plan accepts that trade-off
(keeping the automated safety net green without a large manual link-rewrite across the
whole `docs/` tree) rather than silently claiming to preserve human-facing link
click-through across folders.

  address it as part of `docsreorg16`'s final validation sweep.
- **Risk**: threading a new required parameter through `validate_file()`,
  `check_related_links()`, and `check_links()` could be missed at one call site,
  silently reverting to old behavior for that path → **Mitigation**: `validate_file()`
  has exactly one production call site (`main()` line 253) and two test call sites,
  both already confirmed via `rg`; update all three in the same change and let the
  existing tests (which call `validate_file()` directly) catch a missed/incorrect
  signature update immediately as a `TypeError`.
- **Risk**: the duplicate-basename hard-failure (REQ-004) could itself be triggered by
  a legitimate future addition to `docs/` if two areas independently pick the same
  filename → **Mitigation**: this is the intended, correct behavior per this Plan's
  Implementation intent (fail loudly rather than silently mis-resolve) — the resolution
  is for the newly-added file to be renamed, not for this check to be weakened.
