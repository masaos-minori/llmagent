# Plan: Enforce consumer and topic authorization across subscribe, ACK, and NACK

## Goal

Apply one fail-closed consumer authorization model to subscription and all consumer-scoped state changes (ACK, NACK), built on the principal introduced in `eventbus02`, eliminating bypass paths where a consumer could act on another consumer's events or an unauthorized topic could be subscribed to.

## Priority
High

## Scope
- **In-Scope**: Consumer/topic authorization in ACK, NACK, and subscribe paths — enforcing principal ownership of consumer IDs, verifying event delivery before ACK/NACK acceptance, canonicalizing topic authorization parameters
- **Out-of-Scope**: Unrelated DB/broker logic beyond what fail-closed authorization requires, EVENTBUS-008 governance entry correction (belongs to `eventbus10`)

## Background
Consumer identity, topic permissions, ACK ownership, and NACK ownership currently lack one fail-closed authorization model across the subscribe/ACK/NACK paths. The consumer ACK endpoint has a consumer-less fallback path, neither ACK nor NACK mandatorily validates that the requesting principal owns the `consumer_id` it is acting as, and there is no single canonical topic list shared between the endpoint and its authorization dependency.

## Problem
The consumer ACK endpoint currently has (or is at risk of having) a consumer-less fallback path, and neither the ACK nor NACK endpoint mandatorily validates that the requesting principal owns the `consumer_id` it is acting as, nor that the event was actually delivered to that consumer before accepting the ACK/NACK. Topic authorization for subscriptions is similarly not guaranteed to fail closed when identity resolution is missing, and there is no single canonical topic list/parameter name shared between the endpoint and its authorization dependency.

## Reason for change
Consumer identity, topic permissions, ACK ownership, and NACK ownership are interdependent. Separate changes could leave bypass paths or contradictory state transitions.

## Implementation intent
Apply one fail-closed consumer authorization model to subscription and all consumer-scoped state changes, built on the principal introduced in `eventbus02`.

## Requirements
- `REQ-001`: Pass the authenticated principal or equivalent authorization context through all ACK layers.
- `REQ-002`: Validate that the requested consumer ID belongs to the principal.

- `REQ-005`: Remove the consumer-less fallback from the consumer API.

## Design

### Principal Ownership Validation (REQ-001, REQ-002, REQ-008)
The authenticated principal carries `allowed_consumer_ids` (from `eventbus02`). Both ACK and NACK endpoints must validate:
```python
if consumer_id and principal.allowed_consumer_ids and consumer_id not in principal.allowed_consumer_ids:
    raise HTTPException(status_code=403, detail=f"Forbidden: consumer_id '{consumer_id}' not allowed")
```

This check applies regardless of whether the principal has a configured consumer ID restriction — if the principal has no restriction (`allowed_consumer_ids` is empty), any consumer ID is permitted. If the principal has a restriction, only listed consumer IDs are allowed.

### Event Delivery Verification Before ACK/NACK (REQ-003, REQ-009)
Before accepting an ACK or NACK, verify the event was actually delivered to the requesting consumer:
```python
# For ACK:
row = conn.execute(
    "SELECT acked_at FROM consumer_delivery WHERE consumer_id = ? AND event_id = ?",
    (consumer_id, event_id),
).fetchone()
if row is None:
    # Event not delivered to this consumer — reject
    raise HTTPException(status_code=409, detail="Event not delivered to this consumer")
```

For NACK, similar verification — but NACK can also apply to events that were delivered but failed processing. The distinction: ACK requires prior successful delivery acknowledgment; NACK requires either prior delivery or prior failure.

### Mandatory consumer_id for ACK Endpoint (REQ-004, REQ-005, REQ-013)
Remove the consumer-less fallback path in `_do_ack()`:
```python
# Current (to be removed):
if consumer_id:
    found, newly_acked, seq = ack_event_for_consumer(db, event_id, consumer_id, now)
else:
    found, newly_acked = _ack_event_plain(db, event_id, now)
    return (found, newly_acked, None)
```

Replace with mandatory consumer_id:
```python
# New:
if not consumer_id:
    raise HTTPException(status_code=400, detail="consumer_id is required for consumer ACK")
found, newly_acked, seq = ack_event_for_consumer(db, event_id, consumer_id, now)
```

The consumer-less fallback allows anonymous consumers to ACK events without tracking per-consumer state — this is a security gap. The mandatory consumer_id ensures all consumer-scoped operations are attributable.

### Required consumer_id for NACK Endpoint (REQ-007)
Add `consumer_id` as a required query parameter to the NACK endpoint:
```python
async def nack(
    request: Request,
    event_id: str = Query(default=""),
    consumer_id: str = Query(...),  # Required — no default
    _role: Role | None = None,
    _identity: dict[str, Any] | None = None,
) -> dict[str, Any]:
```

NACK without a consumer ID is ambiguous — who is nacking? The operation must be attributable to a specific consumer.

### Consumer Failure / Retry Counter Semantics (REQ-010)
**Decision**: Consumer-specific failures should be tracked separately from the global `delivery_failure_count`. Two counters:
- `delivery_failure_count` (global, event-level): used for DLQ promotion threshold
- `consumer_delivery_failure_count` (per-consumer): used for consumer-specific retry decisions

The NACK handler should:
1. Increment the consumer-specific failure count atomically with the global count
2. Use the global count for DLQ promotion (existing behavior preserved)
3. Optionally expose the consumer-specific count in the response for observability

If the current code's single-counter approach is sufficient for the operational model, document this decision explicitly rather than introducing unnecessary complexity.

### Unrestricted, Deny-All, Explicit Allowlist States (REQ-011)
Represent these three states distinctly in the Principal model:
- **Unrestricted**: `allowed_consumer_ids` is `None` — any consumer ID is permitted
- **Deny-all**: `allowed_consumer_ids` is an empty frozenset `{}` — no consumer ID is permitted
- **Explicit allowlist**: `allowed_consumer_ids` is a non-empty frozenset — only listed consumer IDs are permitted

This matches the convention already established in `_populate_token_maps()` where empty sets mean "no restriction" — but we need to distinguish "no entry in the map" (unrestricted) from "empty entry in the map" (deny-all).

### Fail-Closed for Unregistered Tokens (REQ-012)
When a token has no authorization entry (not in `_TOKEN_ROLE_MAP`, `_TOKEN_CONSUMER_MAP`, or `_TOKEN_TOPIC_MAP`), fail closed:
- Reject at the authentication layer (HTTP 401) — no principal can be resolved
- This is already partially handled by `resolve_principal()` returning 401 for unknown tokens

### Empty Consumer ID Semantics (REQ-013)
**Decision**: Empty consumer ID is rejected with HTTP 400 for both ACK and NACK endpoints. An empty string is not a valid consumer identifier — it represents an anonymous/unattributable identity which contradicts the fail-closed authorization model.

### Canonical Topic Parameter (REQ-014, REQ-016)
Use one parameter name consistently across the subscribe endpoint and its authorization dependency:
- Subscribe endpoint: `topic: list[str] = Query(default=[])`
- Authorization dependency: `topics: list[str] | None = None`

**Decision**: Standardize on `topics` as the canonical parameter name. Update the subscribe endpoint to use `topics` instead of `topic`, and update `require_consumer_identity` to accept `topics` consistently.

### Pass Only Authorized Topics to Subscription Handler (REQ-016)
After resolving the principal, filter the requested topics against `principal.allowed_topics`:
```python
if principal.allowed_topics is not None:
    # Filter to authorized topics only
    authorized_topics = [t for t in requested_topics if t in principal.allowed_topics]
    unauthorized = set(requested_topics) - set(authorized_topics)
    if unauthorized:
        raise HTTPException(
            status_code=403,
            detail=f"Forbidden: topics {unauthorized} not allowed",
        )
    requested_topics = authorized_topics
```

A mixed list containing any unauthorized topic is rejected entirely (fail-closed), not silently filtered.

### Empty Topic List Semantics (REQ-017)
**Decision**: An empty topic list means "all topics" — this is the current behavior and should be preserved. However, only principals with unrestricted access (or explicit wildcard permission) may subscribe to all topics. Principals with topic restrictions must specify at least one topic.

### Fail-Closed When Identity Resolution Missing (REQ-015)
If identity resolution fails at any point (missing principal, missing authorization context), the request is rejected before reaching any consumer-scoped state mutation. This is enforced by:
1. Authentication layer rejecting unknown tokens (HTTP 401)
2. Authorization dependencies requiring a valid principal
3. Consumer ownership checks rejecting unauthorized consumer IDs
