## 1. Goal

Add schema-based validation for LLM-generated tool call arguments before they reach MCP servers. Reject tool calls that contain unexpected or invalid fields according to the MCP tool definition's inputSchema, preventing argument injection attacks.

## 2. Scope

### In-Scope
- Add argument validation in `scripts/agent/tool_runner.py` after `orjson.loads(args_str)` parsing
- Validate against MCP tool inputSchema stored in `RuntimeTool.input_schema`
- Reject tool calls with extra fields not defined in the schema
- Log warnings for rejected tool calls with details about which fields were rejected
- Graceful handling of validation failures (no session crash)
- Optional custom validation rules per tool via RuntimeTool field extension

### Out-of-Scope
- Modifying existing MCP tool schemas
- Adding new MCP servers
- Database schema changes
- Changes to cache stampede protection logic
- Changes to transport error handling

## 3. Assumptions

- RuntimeTool.input_schema contains valid JSON Schema format compatible with standard validators
- The validation should happen at the tool_runner layer, not in tool_executor, because it needs access to the specific tool's schema
- Extra fields should be rejected by default (strict mode); allowing extra fields can be opt-in per tool
- Validation errors should be logged but not crash the session; the tool call should be returned as an error result

## 8. Risks & Mitigations

- **Risk**: Strict mode validation may break existing LLM behavior if the LLM has been sending extra fields that were previously ignored. → **Mitigation**: Start with logging-only mode (warn but don't reject), then switch to reject mode after validation period.
- **Risk**: Some MCP tools may have incomplete or incorrect inputSchemas. → **Mitigation**: Fallback to lenient mode when schema is missing or malformed, log warning.
- **Risk**: Type validation may be too strict for some tools. → **Mitigation**: Make type validation optional per-tool, default to schema-defined types only for critical tools.
