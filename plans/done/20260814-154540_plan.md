## Design

**How this fits the existing architecture**: This plan operates at the policy level rather than the code level. The deprecation warning addition (`plans/20260813-190710_plan.md`) handles the code-side change. This plan adds the governance layer — a defined grace period and repo-wide convention — ensuring the deprecation follows through to removal within a predictable timeframe.

**Policy design rationale**: The requirement recommends adopting a repo-wide default ("deprecated symbols are removed the next time `plans/` touches the same file for an unrelated reason, provided a zero-caller `rg` re-check still holds"). This approach has several advantages:
1. It avoids arbitrary time-based deadlines that may not align with release cycles.
2. It ties removal to natural maintenance opportunities (when someone else is already touching the file).
3. The zero-caller `rg` re-check provides a safety gate — removal only proceeds if no new callers have appeared.
4. It is consistent with the repo's existing practice of using `plans/` entries as implementation tracking artifacts.

**Why not a fixed-duration policy**: A fixed-duration policy (e.g., "30 days", "next major version") would require a separate mechanism to track elapsed time since deprecation, which does not exist in this repo. The `plans/`-based approach leverages existing infrastructure without adding new tooling.
