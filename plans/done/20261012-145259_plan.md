## Integration note

Two independent `issue-to-plan` cycles were produced for the same root issue
(`start001`):

- `plans/20261012-133954_plan.md` — proposed removing `close_resources()` from the
  startup `finally` and calling it once **after** the input loop (no `finally` around
  the loop).
- `plans/20261012-140942_plan.md` — restructured `run()` to **one outer `finally`**
  wrapping startup, the post-startup memory warning, and the input loop.

This document consolidates both into a single plan. The session-wide `finally` approach
(`140942`) is canonical because it runs cleanup exactly once on every exit path
(normal exit, startup failure, interrupt, loop exception) while never running ahead of
the loop, satisfying the Issue's constraint against dropping cleanup on the failure path.
The simpler no-`finally` approach (`133954`) matches the Issue's literal text but drops
cleanup for a `ComponentInitializer.initialize()` failure and a startup interrupt, which
the Issue forbids; it is recorded here as a rejected alternative.

**Implementation is complete** (commit `9d54033be`); this document is a consolidated
record, not a forward-looking plan. All Execution Status rows are `Completed`.

## Goal

Make `AgentREPL.run()` release session resources exactly once per run, after the REPL
input loop ends (or when startup fails or is interrupted), never before the input loop on
a successful startup.

## Priority

High

## Scope

- **In-Scope**:
  - Restructure `AgentREPL.run()` in `scripts/agent/repl.py` so
    `ResourceShutdownCoordinator.close_resources()` is called once, from a single
    `finally` that wraps startup, the post-startup warning, and the input loop.
  - Spy-based tests in `tests/agent/test_repl.py` for the call order and the call count on

  - Update the "Resource Cleanup on Shutdown" section of

- **Out-of-Scope**:

  - Any change to `StartupOrchestrator.run()` or its rollback (`scripts/agent/startup.py`).
  - Lazy rebuild of the HTTP client or MCP servers as a workaround.
  - Making `lifecycle.shutdown_all()` idempotent: on the failure path it is already called
    twice today (startup rollback, then `close_resources()`), and that does not change.

## Background

- `AgentREPL.run()` wraps `startup.run()` in `try/except/finally`; the `finally` calls
  `self._shutdown.close_resources()` (`scripts/agent/repl.py:129-130`, added in commit
  `26dc21eff6`, 2026-08-31). A `finally` also runs on success.
- Issue
  `issues/20261012-124806_start001_startup-failure-cleanup-handler-closes-shared-http-client-before-the-repl-session-begins.md`
  reports that this closes the shared HTTP client and stops all MCP servers before the
  input loop starts.

## Problem

Verified against current source (`Confirmed by repository evidence`):

- **Order on success (confirmed by run)**: a probe that patched `StartupOrchestrator` to
  succeed and recorded the calls saw `['close_resources', 'input_loop.run']`. The failure
  path saw `['close_resources']`, the fatal message written, and the exception re-raised.
- **Effect**: `close_resources()` ends with `lifecycle.shutdown_all()` and
  `http.aclose()` (`scripts/agent/resource_shutdown_coordinator.py`). The shared
  `httpx.AsyncClient` is built once in `scripts/agent/factory.py:423`; the other
  `AsyncClient` uses in `scripts/agent/` are local `async with` clients, so nothing
  rebuilds it. A closed client raises
  `RuntimeError: Cannot send a request, as the client has been closed.` (confirmed by run),
  so the first LLM request after startup fails.
- **No cleanup after the session**: `close_resources()` is called only from `repl.py:130`.
  The input loop's own `finally` runs `_persist_after_loop` (session memories and
  diagnostics) and nothing else, so normal exit performs no resource cleanup today.
- **Correction to the Issue (new finding)**: the Issue's Required Changes remove
  `close_resources()` from the startup `finally` and rely on `StartupOrchestrator.run()`'s
  rollback for the failure path. That rollback does not cover everything
  `close_resources()` covers: it only wraps the steps inside its `try` (server start,
  health, service checks, approval recovery, prompt setup) and only calls
  `lifecycle.shutdown_all()`. A failure in `ComponentInitializer.initialize()` is
  deliberately not rolled back
  (`tests/agent/test_startup_rollback.py::test_no_rollback_on_initialize_failure`), the
  closing `RuntimeError` after the `try` is not covered either, and the rollback does not
  close the HTTP client, checkpoint the WAL, or write history. Dropping `close_resources()`
  from the failure path would violate the Issue's own constraint ("do not drop cleanup on
  the failure path"). `close_resources()` today also runs for `BaseException` during
  startup (for example an interrupt), which a plain `except Exception` would skip.
- **Other conclusions of the Issue**: Unresolved Question 1 (does anything reconnect the
  client) is answered: no. Question 2 (is production broken or masked) cannot be observed
  from the repository; the code path is a defect regardless (see `UNK-01`).

## Reason for change

- On every successful startup the agent loses its LLM client and MCP servers before the
  first prompt, and on normal exit nothing is cleaned up. Both break normal operation.
- Moving the call without keeping a cleanup guard on every exit path would trade one
  defect for another (leaked HTTP client and WAL state after failed or interrupted
  startup).

## Implementation intent

- Run cleanup in one `finally` whose body is the whole session: startup, the
  post-startup warning, and the input loop. Then cleanup runs exactly once on normal exit,
  startup failure, interruption, and an exception from the loop, and never before the loop
  on success.
- Keep the inner `except Exception` that writes the fatal message and re-raises, unchanged.
- Do not touch `close_resources()` or `StartupOrchestrator.run()`; change only where
  `close_resources()` is invoked.

## Requirements

- `REQ-001`: On a successful startup, `close_resources()` is not called before
  `input_loop.run()` starts.
- `REQ-002`: `close_resources()` is called exactly once per `run()` on every exit path
  (normal exit, startup failure, exception raised by the input loop), after the input loop
  on the success path.
- `REQ-003`: A startup failure still writes the fatal view message and re-raises the
  original exception; `StartupOrchestrator.run()` and `close_resources()` are unchanged.
- `REQ-004`: Spy-based tests (recording call order, not an `AsyncMock` that hides the call)
  cover `REQ-001` to `REQ-003`.
- `REQ-005`: The agent startup and health document states that cleanup runs when the
  session ends, or when startup fails or is interrupted, not during startup.
- `REQ-006`: The existing tests, lint, types, and the full suite pass with no new
  failures.

## Assumptions

- A single outer `finally` is acceptable for the whole session: the persister callback
  already runs in the input loop's own `finally`, so session data is persisted before
  resources close.
- Calling `lifecycle.shutdown_all()` twice on the failure path (startup rollback, then
  `close_resources()`) is existing behavior and is safe today; this plan does not change
  it.
- Exceptions raised by the post-startup memory-warning code should also trigger cleanup;
  including them in the outer `try` is consistent with "exactly once on every exit path".
- The `_spawned_subprocesses` return value remains an unused assignment in `run()`
  (pre-existing dead assignment); subprocess termination is delegated to
  `lifecycle.shutdown_all()`, not done directly by `repl.py`.

## Design

- Path A (3 files, no public or runtime-facing interface change, no schema change). Direct
  verification: `repl.py` imports `ResourceShutdownCoordinator`, `StartupOrchestrator`,
  `ReplInputLoop` and others, all read; `agent.repl` is imported by
  `scripts/agent/__init__.py`, `scripts/agent/__main__.py`, `tests/agent/test_repl.py`,
  `tests/agent/test_signal_handler_race.py` and
  `tests/agent/commands/test_command_registry_consistency.py`.
- Shape of the change in `run()`:
  - the signal setup stays as it is; then one `try:` begins;
  - inside it, the existing startup `try/except Exception` keeps `write_fatal` and `raise`,
    with its own `finally` removed;
  - then the memory-disabled warning and `await self._input_loop.run(...)` stay in the same
    outer `try`;
  - one `finally:` at the outer level calls `await self._shutdown.close_resources()`.
- Rejected alternative (the Issue's literal text, i.e. plan `133954`): remove the call from
  the `finally` and add one after the loop. It drops cleanup for a failure in
  `initialize()` and for an interrupt during startup, which the Issue's own constraints
  forbid.
- Validation quality baseline (`scripts/agent/repl.py`): radon reports `run()` at grade
  `A(4)`; vulture reports nothing; bandit reports 42 Low / 10 Medium / 0 High. These are
  the recorded pre-change baseline and are unchanged after the fix. `tests/agent/test_repl.py`
  and `tests/agent/test_startup_rollback.py` pass; the full suite passes
  (`8257 passed, 20 skipped`; `pre-commit` all hooks pass).

## Risks

- **Risk**: Cleanup now also runs when the post-startup warning code or the loop raises,
  which could mask the original exception if `close_resources()` itself raises →
  **Mitigation**: `close_resources()` records and logs its own errors and does not raise on
  checkpoint, backup, task, or service failures; a test covers the loop-exception path and
  checks the original exception is the one raised.
- **Risk**: A test relied on cleanup happening before the loop → **Mitigation**: the
  validation step runs the importing test files (`UNK-02`); a failure is reported, not
  worked around.
- **Risk**: Production still uses the old build until redeployed → **Mitigation**: the
  plan's last step points to the `deploy` skill; deployment itself is outside this plan.
