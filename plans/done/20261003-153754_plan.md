# Plan: Clarify ToolRouteResolver strict_mode documentation

## Goal
Clarify the `strict_mode` behavior in `ToolRouteResolver` documentation to prevent future confusion during code reviews and refactoring.

## Priority
Medium

## Scope
- **In-Scope**: Updating the class-level docstring of `ToolRouteResolver` to clarify the `strict_mode` behavior; ensuring consistency between class-level and parameter-level documentation.
- **Out-of-Scope**: Changing the retry logic itself; modifying other transport layers; changing error handling behavior.

## Background
`scripts/shared/route_resolver.py` line 27-31:
```python
class ToolRouteResolver:
    """Map tool_name → server_key using RuntimeToolRegistry as the sole routing authority.

    RuntimeToolRegistry is populated from live /v1/tools discovery. Raises ValueError
    when the tool is not found there.
    """
```

The class-level docstring says "Raises ValueError when the tool is not found there", which implies that `ValueError` is raised regardless of `strict_mode`. However, the parameter-level docstring (lines 43-52) correctly explains that "both `strict_mode=True` and `strict_mode=False` always raise `ValueError` on an unresolved tool — the difference is in error-message wording only."

The issue claims there's a documentation mismatch, but upon closer inspection, the parameter-level docstring is accurate. The class-level docstring could be improved to clarify the `strict_mode` behavior.

## Problem
The class-level docstring doesn't mention the `strict_mode` behavior, which could lead to confusion during code reviews and refactoring. Developers may assume that `strict_mode=False` means `ValueError` is not raised.

## Reason for change
Documentation clarity improvement. Ensuring consistent documentation across all levels prevents misinterpretation during code reviews and refactoring.

## Implementation intent
Update the class-level docstring of `ToolRouteResolver` to clarify the `strict_mode` behavior, ensuring consistency with the parameter-level docstring.

## Requirements
- REQ-001: Class-level docstring accurately reflects the `strict_mode` behavior
- REQ-002: Documentation remains consistent with parameter-level docstring
- REQ-003: Existing tests pass after the change
