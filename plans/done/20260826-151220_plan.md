## Background
`config/agent.toml` and `config/ingester.toml` each carried an `embedding_dims`
(and, for `agent.toml`, a `memory_embed_dim`) key defaulting to `384`, matching a
`multilingual-E5-small` embedding model. A source-evidenced migration (tracked in
`requires/done/20260802-070234_require.md`, `plans/done/20260802-102150_plan.md`, and
`implementations/done/20260802-122033_embedding_dimension_constant.md`, with regression
coverage in `tests/db/test_embedding_dimension.py`) removed both keys from both TOML
files and replaced the runtime lookup with a fixed code-level constant
(`QWEN3_EMBEDDING_DIMS = 1024` in `scripts/db/store_protocols.py::get_embedding_dims()`).
A sibling requirement filed the same day
(`requires/done/20260802-071922_require.md`, "Remove stale 384/E5 documentation once the
Qwen3 embedding migration lands") explicitly deferred the documentation cleanup because,
at verification time, the code migration had not yet landed — and no Plan was ever
generated from that requirement, so the cleanup never happened even after the migration
did land later the same day. Numerous docs written or left standing since then still
describe the pre-migration, config-driven `384` design as current.

Separately, `docs/01_overview-arch-01-process.md`'s service/port/model table names the
port-8080 chat LLM as `Qwen3.6-Instruct-Q4_K_M`, while `docs/02_deployment.md` §1.4 — the
already-established canonical model table (see Reason for change) — lists two different
chat-LLM filenames, `gemma-4-e4b-it` and `Qwopus3.6-35B-A3B-v1`, for the same role.

## Problem
Two independent, currently-live documentation inconsistencies:
1. **Embedding dimension.** At least eleven `docs/*.md` files state that
   `embedding_dims`/`memory_embed_dim` is a configurable key in `config/agent.toml` or
   `config/ingester.toml` defaulting to `384`; a troubleshooting note computes an
   expected BLOB byte count from that assumption. Repository evidence (config file
   contents plus the migration trail above) confirms neither key exists in either TOML
   file, and the dimension is instead a fixed code constant. One of these docs also
   reproduces a `DbConfig` dataclass code block with an `embedding_dims: int = 384`
   field that does not exist in the actual `DbConfig` dataclass, and another describes
   an `AgentConfig.memory.memory_embed_dim` field that was removed in the same
   migration.
2. **Chat-LLM name.** `docs/01_overview-arch-01-process.md` and the canonical model
   table in `docs/02_deployment.md` §1.4 name different filenames for the same chat-LLM
   role, and the canonical table itself lists two different filenames for that one role.
   Which (if any) is the actual currently-running filename cannot be determined from
   `deploy/*.sh` or `config/*.toml` (both are free of `.gguf` references; the LLM runs
   on an external host not tracked in this repository) — this is the same blocking gap
   already on file as `UNK-01` in `plans/done/20260819-174858_plan.md`.

## Reason for change
Config-drift documentation misleads an operator or an AI coding agent touching this
area into believing `embedding_dims`/`memory_embed_dim` can still be tuned via TOML, or
into recomputing a `1536`-byte expectation that no longer matches the code's actual
BLOB-size contract — either mistake would produce a real vector-insertion error if acted
on. `docs/02_deployment.md` §1.4 was already made canonical for model filenames by a
prior, fully-implemented plan (`plans/done/20260819-174858_plan.md`; see its
implementation in `implementations/done/20260820-133953_model_references_docs.md.md`),
which updated `docs/01_overview-files-01-build.md` and
`docs/03_rag_05_1-configuration-reference.md` to cross-reference it instead of
restating filenames — but that plan's target-file list did not include
`docs/01_overview-arch-01-process.md`, so its chat-LLM name conflict with the now-canonical
table was never resolved and remains live today.

## Implementation intent
Apply the same "cross-reference the canonical table instead of restating a literal
name" pattern already established and implemented for
`docs/01_overview-files-01-build.md`/`docs/03_rag_05_1-configuration-reference.md` to
`docs/01_overview-arch-01-process.md`'s chat-LLM and embed-LLM table rows. For the
embedding-dimension family of docs, replace each "configurable via `config/*.toml`,
default 384" claim with a statement that the dimension is a fixed code-level constant,
and point to `scripts/db/store_protocols.py` (`get_embedding_dims()` /
`QWEN3_EMBEDDING_DIMS`) as the single source of truth, rather than restating a specific
number independently in each of eleven files (so a future constant change requires
updating one code location, not eleven docs). Remove the two fabricated field
references outright rather than trying to reconcile them to a new number.

## Design
Two independent fix patterns, chosen to match precedent already established and
implemented in this repository rather than inventing a new convention:

1. **Chat/embed-LLM name rows (`REQ-001`, `REQ-002`).** `docs/02_deployment.md` §1.4 is
   already annotated as the canonical model-reference table by
   `plans/done/20260819-174858_plan.md`'s implementation. Extend the same
   cross-reference treatment already applied to `docs/01_overview-files-01-build.md`
   and `docs/03_rag_05_1-configuration-reference.md` to
   `docs/01_overview-arch-01-process.md`'s service table, replacing its Model column
   values for the `agent-llm` and `embed-llm` rows with a link to
   `docs/02_deployment.md#14-llm--how-to-get-models` (or the section's current anchor)
   instead of restating filenames that can drift out of sync. This does not resolve
   `UNK-01` (which literal filename is actually correct) — it only removes the
   structural duplication that let two docs silently diverge.
   **Note (plan-to-implementation-procedure adversarial verification, 2026-08-27)**:
   re-reading `docs/02_deployment.md` §1.4's actual table found the embed-LLM model
   name itself (`multilingual-e5-small`) does NOT actually conflict with
   `docs/01_overview-arch-01-process.md`'s `multilingual-E5-small` (only
   capitalization differs, not a real drift) — REQ-002's cross-reference of the
   *model name* is a preventive/consistency measure, not a correction of an
   existing name conflict; the actual, confirmed conflict for embed-llm is only the
   "384D" dimension claim (REQ-002's other half). The chat-LLM row (REQ-001) is the
   one with a genuine three-way name conflict (`Qwen3.6-Instruct-Q4_K_M` in
   `01_overview-arch-01-process.md` vs. two different names,
   `gemma-4-e4b-it`/`Qwopus3.6-35B-A3B-v1`, in `02_deployment.md` §1.4 itself).
2. **Embedding-dimension config-key claims (`REQ-003`, `REQ-004`).** Repository
   evidence (`config/agent.toml`, `config/ingester.toml` file contents; the migration
   trail in `requires/done/20260802-070234_require.md` and
   `implementations/done/20260802-122033_embedding_dimension_constant.md`;
   `tests/db/test_embedding_dimension.py`) confirms the dimension is now a fixed
   code-level constant, not a TOML key. Each affected doc's "via `config/*.toml`,
   default 384" framing is rewritten to instead name
   `scripts/db/store_protocols.py::get_embedding_dims()` as the single source of
   truth. This mirrors the existing "point to one canonical source instead of
   restating a value in N places" convention from pattern 1, applied to a code
   constant instead of a config value. Fabricated field reproductions
   (`DbConfig.embedding_dims`, `AgentConfig.memory.memory_embed_dim`) are deleted
   outright since no rewording of a nonexistent field is meaningful.

No `scripts/` or `config/` file is touched — both fix patterns are documentation-only
corrections of claims about existing, unchanged source-code and config-file behavior.
