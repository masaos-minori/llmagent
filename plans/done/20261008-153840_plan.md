# Plan: Fix MCP subprocess startup and health check handling

## Goal

Align MCP server startup and health check logic with ADR-004 Group 7: `required=false` servers that fail to start must be disabled without aborting the Agent, the `/health` authentication policy must be resolved consistently between Agent and servers, and degraded-but-live 503 responses must not abort startup.

## Priority

Medium

## Scope

- **In-Scope**:

  - `scripts/shared/mcp_config.py`: `McpServerConfig.required` field usage
  - `scripts/agent/shared/retry_helper.py`: retry-once-with-delay behavior for non-required servers
  - `config/agent.toml`: server configuration with `required` field
  - `scripts/mcp_servers/health_response.py`: `/health` response structure (read-only reference)

- **Out-of-Scope**:
  - Health endpoint changes of unrelated servers
  - Circuit-breaker behavior
  - Changes to `scripts/agent/http_lifecycle.py` beyond what is needed for the `/health` auth policy

## Background

ADR-004 Group 7 specifies that a failing `required=false` server is disabled and startup continues. The current implementation contradicts this: `start_servers()` and `verify_health()` never consult `cfg.required`, so a `required=false` server that fails to start stops the whole Agent after retries. Additionally, `verify_health()` calls `/health` without an Authorization header while the MCP auth middleware requires authentication on all paths including `/health`. A 503 from `/health` (degraded, e.g., rag-pipeline with `embed_url` unset) is treated as a startup failure.

## Problem

1. `start_servers()` and `verify_health()` never consult `cfg.required`; a `required=false` server that fails to start stops the whole Agent after retries.
2. `verify_health()` calls `/health` without an Authorization header, while the MCP auth middleware requires authentication on all paths including `/health`, so servers with an `auth_token` should answer 401.
3. A 503 from `/health` (degraded, e.g., rag-pipeline with `embed_url` unset) is treated as a startup failure.

## Reason for change

1. The implementation contradicts ADR-004 Group 7.
2. If health checks and authentication do not mesh, correctly configured servers fail to start; conversely, if startup currently succeeds, authentication may be disabled somewhere. Either case needs resolution.
3. Not distinguishing degraded from down lets a non-essential feature stop the entire Agent.

## Implementation intent

Decide startup outcome by "required or not" and "down or degraded", consistent with ADR-004. Choose a single `/health` authentication policy and align both sides. Parse the 503 body; when `liveness=true` and degraded, treat it as "started, partially available".

## Requirements

- `REQ-001`: On startup or health failure, check `cfg.required`; for `required=false`, disable the server (`is_disabled`, removed from routing), log WARNING, and continue.
- `REQ-002`: The Agent sends Bearer token in `/health` requests when the server has `auth_token` set (Option B: authenticate all endpoints).
- `REQ-003`: Parse the 503 body; when `liveness=true` and degraded, treat it as "started, partially available" rather than a startup failure.
- `REQ-004`: Required servers must still fail startup when down (no weakening of required-server behavior).
- `REQ-005`: Do not weaken authentication to make the check pass.

## Design

### Decision Matrix

The startup/health decision logic follows a 2-axis matrix per ADR-004 Group 7:

| | Down (not reachable) | Degraded (503, liveness=true) |
|---|---|---|
| **required=true** | Abort startup (FATAL) | Abort startup (FATAL) |
| **required=false** | Disable server, continue (WARNING) | Continue (INFO) |

### `/health` Authentication Policy

Option B: Agent sends Bearer token on `/health` requests when `cfg.auth_token` is set. This is consistent with ADR-007 "authenticate all endpoints". The Agent must include the Authorization header in all `/health` requests where the server has `auth_token` configured.

### 503 Body Parsing

When a 503 is received, parse the JSON body:
- If `liveness=true` and `status=degraded`: treat as "started, partially available" — log INFO, continue.
- If `liveness=false` or `status` indicates down: treat as down — apply the decision matrix based on `cfg.required`.

### Implementation Approach

1. In `start_servers()`: after subprocess start failure, check `cfg.required`. For `required=false`, call a new method to disable the server and continue.
2. In `verify_health()`: add Bearer token to the request, parse 503 body, apply decision matrix.
3. In `http_lifecycle_health_checker.py`: add Bearer token support to `verify_running_async()` and `startup_poll()`.
