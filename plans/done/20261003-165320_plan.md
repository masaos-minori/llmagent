## Goal
Harden `shared/http_transport.py::HttpTransport.call()` so a malformed `/v1/call_tool` response fails on the first attempt instead of being retried deterministically, and the unreachable trailing `raise` is removed so every exit path is explicit.

## Priority
Low

## Scope
- **In-Scope**: Make `ValueError` from `_parse_http_response()` fail fast (raise `TransportError`) instead of looping; remove the unreachable trailing `raise last_exc or TransportError(...)` so each non-retryable path has exactly one explicit failure exit; collapse the fragile `for...else` into a clear structure while preserving retryable-status looping; add a regression test asserting a malformed body fails after exactly one `post` call.
- **Out-of-Scope**: Changing the retryable-status set `{429,502,503,504}`; changing the retry count (3) or the `2**attempt` backoff schedule; changing the retry-exhaustion message wording; adding client-side response-size limits or new schema validation beyond the current checks; refactoring other methods in `http_transport.py`.

## Background
`call()` is the single HTTP entry point for every MCP tool invocation. It retries on a fixed set of retryable status codes (`{429,502,503,504}`, `http_transport.py:73`) up to `_RETRY_MAX=3` attempts (`:74`) with `2**attempt` exponential backoff (`:130`), and classifies other failures via a `for...else` construct (`:120-167`): timeout and non-retryable `HTTPStatusError` raise inside their `except` block, retryable statuses `continue`, and the loop's `else` clause raises a retry-exhaustion message on completion.

## Problem
Two related control-flow weaknesses exist in `call()`:

1. A malformed response (`result` missing/non-str, `is_error` non-bool, or invalid JSON) raises `ValueError` inside `_parse_http_response()` (`:61-67`). That `ValueError` is caught by `except (httpx.RequestError, ValueError)` at `:161-162`, which sets `last_exc` WITHOUT `break_flag=True` and neither `continue`s nor `raise`s — so the loop simply iterates again and re-issues the request. Because a malformed body is deterministic, all three attempts fail identically, wasting network round-trips for a failure that can never succeed on retry.
2. The final `raise last_exc or TransportError(f"call failed: {name}")` (`:167`) is unreachable. Every iteration either returns (success), raises inside an `except` block (timeout / non-retryable status), `continue`s (retryable status), or falls through to the `for...else` clause, which already raises the exhaustion message. Nothing ever reaches the trailing statement, and `last_exc` is effectively a dead variable (always overwritten, never read before the `else` raises).

Repository evidence additionally shows the `HTTPStatusError` branch's retryable handling (`:156,159-160`) is dead in practice: retryable statuses are filtered by the `if resp.status_code in self._RETRYABLE_STATUS` check at `:128` before `resp.raise_for_status()` at `:142`, so that `except` branch only ever observes non-retryable statuses and always raises.

## Reason for change
The malformed-response retry adds latency with zero recovery value on every persistent server misconfiguration or schema mismatch, and the fragile `for...else` + shadowed `last_exc` pattern is a footgun: a future edit that introduces another `break_flag=False` path would expect `last_exc` to surface but would instead be swallowed by the `else` clause, producing confusing "call failed" errors instead of the real cause.

## Implementation intent
Make non-transient failures fail fast and make exit paths explicit. On a `ValueError` from response parsing, raise immediately rather than looping. Collapse the `for...else` + trailing-raise into a clear structure where retryable statuses loop and every other failure resolves to a single, well-defined error. Preserve the current retryable-status set, the `2**attempt` exponential backoff, the retry-exhaustion message wording, and the distinction between `transport` and `tool` error surfaces downstream.

## Design
Task-size classification: **Path A**. Rationale against `skills/issue-to-plan/SKILL.md` Routing: the change touches one production source file (`http_transport.py`) plus behavior-locking/regression test files, introduces no public or runtime-facing interface change (`call()` keeps its signature and return/raise contract), and touches no database schema. Path B's architecture/dependency/historical/operational analysis is therefore not applied; the validation-quality baseline (bandit) is still established per Path A (already clean across the shared modules).

Central design decision — split `ValueError` from `httpx.RequestError`: the current `except (httpx.RequestError, ValueError)` handler is rewritten so `ValueError` raises immediately (fail fast, non-transient) while `httpx.RequestError` stays in a returning handler that preserves the existing retry-via-exhaustion behavior (REQ-001, REQ-003). This is the minimal interpretation of the issue's scope and avoids changing latency characteristics for potentially-transient network errors. UNK-01 records the open question of whether RequestError should later fail fast.

Structural change: replace the `for...else` + trailing `raise last_exc or TransportError(...)` with an explicit structure where retryable statuses `continue` and every non-retryable failure raises inside its handler; the loop's exhaustion raise becomes the single retryable-exhaustion exit. The confirmed-dead `HTTPStatusError` retryable check (`:156,159-160`) is removed as part of the collapse (behavior identical, since retryable statuses are filtered before `raise_for_status`).
