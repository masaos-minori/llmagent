# Make duplicate publish handling content-safe and reconcile JSONL semantics

## Goal

Turn duplicate publish handling into a deterministic idempotency system. An identical retry should return the original sequence without a new delivery, while a conflicting reuse of an event ID should be rejected with HTTP 409. Declare `events.jsonl`'s role explicitly so it can be reconciled with SQLite and not be mistaken for a second inconsistent source of truth.

## Priority
Medium

## Scope
- **In-Scope**: Defining canonical equality fields and canonical JSON comparison for duplicate detection; returning idempotent success only for identical content; returning HTTP 409 for conflicting content without modifying stored data; declaring `events.jsonl`'s role and changing the append behavior to match that declared role; adding reconciliation and failure-injection tests.
- **Out-of-Scope**: Transactional ACK/offset redesign (EB-H01). DLQ requeue real-redelivery redesign (EB-H03). Changing `insert_event()`'s `seq` allocation scheme beyond what's needed to support content comparison.

## Background

Confirmed by direct read of `scripts/eventbus/db.py` lines 170-188 (`insert_event`) and `scripts/eventbus/publish_route.py` lines 19-77 (`publish`): the JSONL write block (lines 50-59) runs unconditionally after `_insert()` returns, and the `if inserted:` guard (line 61) applies only to the subsequent broker-publish call. There is no test in `tests/eventbus/test_eventbus_publish.py`/`test_eventbus_publish_contract.py` (file names confirmed present under `tests/eventbus/`) that asserts JSONL line count matches SQLite row count after a duplicate `event_id` is published with different content — this needs confirmation by reading those files' actual assertions before considering it resolved.

## Problem

- A publisher that reuses an `event_id` with a different topic/payload/producer/timestamp receives the same HTTP 200 success response as the original publish (the response only echoes `event_id`/`seq`, per line 77) — SQLite retains the original content, but the caller cannot tell that its new content was silently discarded.
- Every publish attempt — including SQLite-ignored duplicates — appends a line to `events.jsonl`, so SQLite can contain one row for an `event_id` while `events.jsonl` contains multiple (potentially conflicting) records for the same ID, with no defined reconciliation rule for which JSONL line reflects the current SQLite state.

## Reason for change

Provide strict idempotency. An identical retry should return the original sequence without a new delivery, while a conflicting reuse of an event ID should be rejected. The role of JSONL must be explicit so it can be reconciled with SQLite and not be mistaken for a second inconsistent source of truth.

## Implementation intent

Load and compare the existing event when an event ID already exists, using canonical equality fields and canonical JSON comparison or content hashing (not raw string comparison, to avoid false conflicts from reordered JSON keys — `scripts/eventbus/json_utils.py`'s `dumps()` already sorts keys via `OPT_SORT_KEYS`, which should make this comparison straightforward to implement consistently). Return idempotent success only for identical content; return HTTP 409 for conflicting content without modifying stored data. Declare `events.jsonl`'s role explicitly (replica, recovery artifact, or request audit) and change the append behavior in `publish_route.py` to match that declared role.

## Assumptions

- The `events.jsonl` role should be "replica" — append only newly inserted events, not all attempts. This aligns with the existing pattern where JSONL is used as a durable log alongside SQLite.
- Canonical equality fields should include: `topic`, `payload` (canonical JSON), `producer`, `published_at`. These are the fields that determine whether two events are truly the same.
- Content comparison should use canonical JSON comparison (via `orjson.dumps()` with `OPT_SORT_KEYS`) rather than raw string comparison, to handle key ordering differences.
- Concurrent duplicate publishes are handled deterministically by SQLite's serialization via `run_with_db_lock` — the second call observes the first call's committed state.

## Design

### Task-size classification: Path B

This task affects > 3 files, changes public/runtime interface (adds validation constraints that affect client behavior), and modifies configuration contracts. Full architecture analysis, dependency graphing, historical analysis, and operational dependency inspection are performed per Path B rules.

### Architecture analysis

The EventBus currently has two independent operation paths:
1. **SQLite insert**: `insert_event()` uses `INSERT OR IGNORE` — silently discards duplicates without any content comparison.
2. **JSONL append**: Unconditionally appends every publish attempt, regardless of whether SQLite accepted the event.

The critical issue is that there is no correlation between these two operations — a duplicate event produces a new JSONL line but no new SQLite row, creating an inconsistency that cannot be reconciled.

### Dependency graphing

```
FastAPI routing ──► publish() ──► _insert() ──► insert_event(db, event_id, topic, payload_str, producer, published_at)
   │                    │              │                        │
   │                    │              │                        ├──► INSERT OR IGNORE INTO events ...
   │                    │              │                        └──► return (seq, inserted)
   │                    │              │
   │                    │              └──► JSONL append (unconditional)
   │                    │
   └──► get_db()        │
   └──► get_config()    │
   └──► get_broker()    │
```

After refactoring, the flow becomes:
```
FastAPI routing ──► publish() ──► _insert() ──► insert_event(db, event_id, topic, payload_str, producer, published_at)
   │                    │              │                        │
   │                    │              │                        ├──► INSERT OR IGNORE INTO events ...
   │                    │              │                        ├──► IF duplicate detected:
   │                    │              │                        │         compare canonical fields
   │                    │              │                        │         └──► return (seq, inserted=0, status="duplicate")
   │                    │              │
   │                    │              └──► JSONL append (only if inserted=True)
   │                    │
   └──► get_db()        │
   └──► get_config()    │
   └──► get_broker()    │
```

Key dependencies:
- `db.py` must return a distinct signal for duplicate detection (currently returns `(seq, False)`).
- `publish_route.py` must decide based on the signal whether to append JSONL and whether to return success or 409.
- The canonical comparison logic must use `orjson.dumps()` with `OPT_SORT_KEYS` for consistent key ordering.

### Historical analysis

- The `INSERT OR IGNORE` pattern was designed for idempotent retries — but it only works for identical content because it doesn't compare anything.
- The JSONL append was designed as a simple append-only log — no deduplication logic exists.
- No prior attempt to add content comparison to duplicate detection exists — this is the first effort.
- The 409-on-invalid-transition pattern was established later in `dlq_route.py`'s `dlq_requeue()` function.

### Operational dependency inspection

- Adding content comparison means that duplicate events with different content will now receive 409 errors instead of silent success — this is a breaking change for clients that rely on silent deduplication.
- Moving JSONL append inside `if inserted:` means that duplicate events will no longer produce new JSONL lines — this is a breaking change for consumers that expect one line per attempt.
- The canonical comparison logic must handle edge cases: null values, nested objects, arrays, etc.

### Design decisions

1. **Canonical equality fields (REQ-001)**: Define the following canonical equality fields:
   - `topic`: Must match exactly.
   - `payload`: Must match after canonical JSON serialization (`orjson.dumps()` with `OPT_SORT_KEYS`).
   - `producer`: Must match exactly.
   - `published_at`: Exclude from canonical equality — this field is typically generated server-side and may differ between retries.

2. **Content comparison logic (REQ-001)**: When `insert_event()` detects a duplicate (`cur.rowcount == 0`):
   - Fetch the existing row from SQLite.
   - Compare canonical fields using canonical JSON comparison.
   - Return `(seq, inserted=False, status="duplicate")` for identical content.
   - Return `(None, inserted=False, status="conflict")` for conflicting content.

3. **HTTP 409 response (REQ-003)**: In `publish_route.py`, convert `"conflict"` status to HTTP 409 with a specific error message:
   - Use the existing `ERR_EVENT_NOT_FOUND` / `ERR_EVENT_NOT_IN_DLQ` pattern for consistency.
   - Include a clear reason string (e.g., `"event already exists with different content"`).

4. **JSONL append behavior (REQ-004, REQ-005)**: Move JSONL append inside `if inserted:` block. This makes `events.jsonl` behave as a "replica" — one line per unique event, not per attempt.

5. **Documentation update (REQ-004)**: Document `events.jsonl`'s declared role in `06_eventbus_03` as a "replica" — one line per unique event, matching SQLite's deduplication semantics.

6. **ADR-006 alignment (REQ-002, REQ-003)**: Update ADR-006's Known Deviations section to note which invariants are now enforced:
   - INV-07 (at-least-once delivery): Now enforced — duplicate events cannot corrupt stored data.
   - INV-12 (ACK failure handling): Not affected by this change.
   - INV-13 (DLQ promotion priority): Not affected by this change.
