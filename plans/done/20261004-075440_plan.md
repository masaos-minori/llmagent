# Plan: Tighten CommandValidator python3 allowlist prefix to a bounded interpreter match

## Goal
Close the `CommandValidator.validate()` allowlist bypass in which any resolved basename beginning with the literal prefix `python3` was accepted, so that only genuine Python interpreter basenames (`python3` and `python3.<version>`) pass while crafted names such as `python3evil` or `python3-config` are rejected.

## Priority
Medium

## Scope
- **In-Scope**:
  - Modify `scripts/agent/http_lifecycle_command_validator.py` to replace the open `startswith("python3")` exception with a bounded interpreter-basename match.
  - Update `tests/agent/test_http_lifecycle_command_validator.py` to cover the new rejection and accepted interpreter variants.
- **Out-of-Scope**:
  - Changing the primary command allowlist contents (`node`, `uvx`, `python`, etc.).
  - Reworking symlink-resolution, regular-file, or PATH-lookup checks.
  - Any change to env-filtering (`filter_env`) or subprocess launch logic.

## Background
HTTP subprocess MCP servers are launched by `HttpServerLifecycleManager._create_and_validate_proc()`, which delegates command validation to `CommandValidator.validate()` in `scripts/agent/http_lifecycle_command_validator.py`. The method performs a four-check allowlist: PATH lookup via `shutil.which()`, symlink resolution via `os.path.realpath()`, regular-file verification, and basename allowlist against `{node, npm, npx, uvx, python, pipx, uvicorn}`. The interpreter exception was added to admit versioned interpreters (`python3.11`, `python3.12`) that are not in the primary allowlist.

## Problem
The allowlist check in `CommandValidator.validate()` uses `base_name.startswith("python3")` as an open exception. Because `shutil.which()` resolves through PATH, an attacker who places a file named e.g. `python3foo` (or a symlink resolving to one) in a PATH directory makes `validate()` return its absolute path, and the caller then launches it via `subprocess.Popen()`. This defeats the basename allowlist, which is the last control before arbitrary code execution.

## Reason for change
As written, the `startswith("python3")` branch matches unrelated executables (`python3-config`, `python3-distutils`, `python3evil`) in addition to real interpreters. The allowlist is the final security boundary before process launch, so the exception must be narrowed to genuine interpreter basenames without broadening the primary allowlist.

## Implementation intent
Introduce a bounded, compiled regular expression that matches only `python3` plus an optional dotted numeric version suffix, and use `re.fullmatch()` against the resolved basename in place of the open `startswith()` check. Keep the primary allowlist membership test unchanged and leave the public signature of `validate()` untouched. Apply the same narrowing to the test layer: reject crafted names deterministically and assert bounded acceptance of real interpreter variants.

## Requirements
- `REQ-001`: Replace the open `base_name.startswith("python3")` exception in `CommandValidator.validate()` with a bounded interpreter-basename match that accepts bare `python3` and `python3.<version>` while rejecting crafted names such as `python3evil` and `python3-config`.
- `REQ-002`: Add unit tests proving that a crafted non-interpreter basename (`python3evil`) is rejected with `HttpStartupError`, and that `python3`, `python3.11`, and `python3.12` still validate successfully; update the existing unbounded-prefix test accordingly.
- `REQ-003`: Preserve behavior for the primary allowlist (`node`, `uvx`, `python`, etc.) so existing validated commands continue to pass and no existing test regresses.
- `REQ-004`: Do not change the public signature of `validate(server_key: str, cmd_name: str) -> str`.

The fix narrows the interpreter exception to a bounded match. Rationale for the pattern shape: the issue's illustrative `python3\.?\d+` requires a digit after `python3`, which would reject bare `python3`; however `python3` is not in the primary allowlist and existing tests require it to validate successfully, so the pattern must accept both bare `python3` and `python3.<digits>`. The chosen form is `python3(?:\.\d+)?` applied with `re.fullmatch()`, which rejects `python3evil`, `python3-config`, and `python3distutils` while accepting `python3`, `python3.11`, and `python3.12`. The compiled pattern lives at module scope; `validate()` keeps its signature and combines the primary allowlist membership test with the interpreter match using logical OR.

- **Risk**: Over-tightening rejects a legitimately installed interpreter variant used by admin config (a basename outside `python3` / `python3.<NN>`). → **Mitigation**: Pattern accepts only `python3` and `python3.<digits>`; any other variant fails closed with a clear `HttpStartupError` at startup instead of executing silently, so a mismatch is observable rather than a silent security gap.
