# Plan: Read stdin on an owned daemon reader thread so an abandoned read cannot hold the REPL process open

## Goal
- Make every interactive prompt read in the agent go through one small, explicitly owned read primitive that performs the blocking `input()` call on a daemon thread it controls, so that cancelling a read — or leaving it pending when the REPL loop exits — no longer holds `asyncio.run()` or the interpreter's exit path open. Process exit time must become a property of the shutdown path, not of keyboard activity.

## Priority
Medium

## Scope
- **In-Scope**: a new `scripts/agent/stdin_reader.py` that owns the blocking stdin read (one request-driven daemon thread, `loop.call_soon_threadsafe` result bridge, no join/shutdown hook); replacing the default-executor reads in `scripts/agent/repl_input_loop.py:144` and `:191`; replacing the private `ThreadPoolExecutor` in `scripts/agent/cli_view.py:112`, `:285-291` (and deleting `CLIView.__del__` and the `concurrent.futures` import); replacing the `asyncio.to_thread(input, ...)` reads in `scripts/agent/tool_approval.py:125`, `:128` (and deleting that module's now-unused `import asyncio`); the tests that prove the exit property and the unchanged prompt semantics; correction of the two documents that describe the current executor-thread behavior.
- **Out-of-Scope**: which signal interrupts what, and the single shutdown-event ownership (`repl001`, already planned at `plans/20261022-030840_plan.md`); the value of any timeout (`_GRACEFUL_TIMEOUT_S` 10.0, `_INPUT_TIMEOUT_S` 30); the unused duplicate at `scripts/agent/resource_shutdown_coordinator.py:29`; `scripts/agent/commands/memory_data_ops.py:48`'s synchronous `input(prompt)` on the event-loop thread; `scripts/agent/startup_validation.py:163-171`'s default-executor use for a non-stdin call; MCP subprocess and HTTP client teardown (`shutdown003`); the unused `loop` parameter of `CLIView.read_multiline` and the `Reader` protocol; the REPL fixture redesign (`repl003`).

## Background
The REPL reads stdin on the event loop's default executor. `_read_input` does it in both of its branches — `loop.run_in_executor(None, lambda: input("> "))` at `scripts/agent/repl_input_loop.py:144` (the shutdown-event branch, which `repl001` makes reachable) and at `:191` (the branch that runs today). `CLIView.read_multiline` owns a second, private pool (`scripts/agent/cli_view.py:112`, `:285-289`, created lazily at `:286-288`) reached from `_read_input` at `:197`. `tool_approval` prompts through `asyncio.to_thread(input, ...)` (`:125`, `:128`), and `asyncio.to_thread` is `loop.run_in_executor(None, ...)` (`/usr/lib/python3.14/asyncio/threads.py`).

Every one of those paths ends in a `concurrent.futures` pool worker, and a pool worker that is inside `input()` cannot be cancelled or joined away: `_WorkItem.run` calls `future.set_running_or_notify_cancel()` and a running item is not cancelled, and `concurrent.futures.thread._python_exit` puts the queue sentinel and then `t.join()`s every thread registered in `_threads_queues` (`/usr/lib/python3.14/concurrent/futures/thread.py:23-31`). `asyncio.run()` also joins the default executor before returning — `Runner.close()` calls `loop.shutdown_default_executor(constants.THREAD_JOIN_TIMEOUT)` (`/usr/lib/python3.14/asyncio/runners.py:75`) with `THREAD_JOIN_TIMEOUT = 300` (`/usr/lib/python3.14/asyncio/constants.py:34`). This repository already documents the same effect for a different resource in `tests/eventbus/test_eventbus_shutdown.py:1-20`, and already carries a regression test whose stated purpose is to avoid leaking a non-daemon pool worker (`tests/agent/test_lifecycle.py:1040-1057`).

The two mitigations that exist today bound only part of the problem: `_INPUT_TIMEOUT_S = 30` (`cli_view.py:24`, applied at `:290-292`) guards only the continuation read, and even there the timeout bounds only the *awaiting* side — the worker stays blocked (`test_repl.py:645-660` documents this by keeping its stub blocked and releasing it in `finally`).

## Problem
Verified against HEAD `84cf9b580`, and measured in this environment (`.venv`, Python 3.14.7; the blocked read is a 6.0 s sleep so no keyboard is needed; `/tmp/opencode/repl002_probe.py`, `/tmp/opencode/repl002_probe2.py`, `/tmp/opencode/repl002_probe3.py`, `/tmp/opencode/repl002_drive.py`).

- The issue's mechanism is confirmed at both live call sites and in the interpreter: cancelling the tracking `Future` does not stop a started worker, and the interpreter then joins it at exit. Measured process-exit times:

| Mechanism for the read | `asyncio.run()` returns | Process exits |
|---|---|---|
| `run_in_executor(None, ...)` + cancel (current code) | held for the whole blocked read | 6.09 s |
| private `ThreadPoolExecutor(max_workers=1)` + `shutdown(wait=False, cancel_futures=True)` | 0.20 s | 6.09 s |
| `ThreadPoolExecutor` subclass whose worker threads are daemon | 0.25 s | 6.10 s |
| `sys.stdin.close()` to unblock the blocked worker | n/a | 6.09 s (the worker is not unblocked) |
| plain daemon `threading.Thread` + `loop.call_soon_threadsafe` result bridge | 0.20 s | 0.29 s |

- The issue's own `Implementation Intent` first option is therefore wrong: no `concurrent.futures` executor satisfies the Acceptance Criteria, because `_python_exit` joins every pool worker regardless of its daemon flag. Only a reading thread that is not a pool worker and is a daemon thread satisfies them (measured 0.29 s exit with the reader still blocked).
- Two live stdin paths are missing from the issue's `Target Files or Areas` and share the same defect: `CLIView.read_multiline` (`cli_view.py:267-300`) and `_prompt_user_approval` (`tool_approval.py:121-129`). The issue's Acceptance Criterion "the default loop executor is not used for stdin reads" is not satisfiable while either remains.
- The issue's `AI Implementation Instruction` ("keep the change inside `repl_input_loop.py` plus the `main()`/`run()` shutdown path") is a gap against this tree: `scripts/agent/repl.py` needs no change for this issue (`main()` at `:170-172` and `run()`'s `finally` are correct as they stand; the exit-bound property comes from the thread's daemon flag, not from the shutdown path), while `cli_view.py` and `tool_approval.py` do. This Plan follows the verified tree and records the deviation here rather than in the code.
- The observable behavior that must survive is well defined and already tested: `"> "` / `"... "` prompts (`agent_07_05:36`, `:44`), EOF (Ctrl-D) → `_read_input` returns `None` and the loop exits (`repl_input_loop.py:183-185`, `:192-194`, `test_repl.py:674-680`), Ctrl-C while waiting for input → the same exit path (`_InputAborted` sentinel, `repl_input_loop.py:24-31`, `:145-146`, `:186-188`), continuation joining and its stop conditions (`test_cli_view.py:96-140`), the 30 s continuation bound surfacing as `KeyboardInterrupt` (`cli_view.py:293-295`, currently untested), and `check_approval` prompting exactly once per tool call (`tool_approval.py:186`) with `EOFError` propagating through `tool_runner.py:409` to `_repl_loop`'s per-turn handler (`repl_input_loop.py:128-134`) — there is no re-prompt loop anywhere.
- The reason no existing test sees the defect: every REPL input test stubs at a boundary above the mechanism (`_read_input` as an `AsyncMock`, `view.read_multiline` as an `AsyncMock`, `asyncio.to_thread` as an `AsyncMock`), and the tests that do drive the real read (`test_repl.py:640-706`) stub `builtins.input` and assert only the return value, never the thread or the process.

## Reason for Change
`repl001` starts cancelling the input read on signals; if the abandoned read still holds the interpreter, that fix changes where the REPL *stops waiting* without changing when the process *exits*, and an operator at an idle prompt still has only a force-kill available — which skips WAL checkpoint, session persistence and MCP termination (`repl.py:161-162`, `repl_input_loop.py:111-115`, and MCP servers are started with `start_new_session: True`, `http_lifecycle_subprocess_launcher.py:99`). The issue also states the dependency plainly: pairs with `repl001`, review together.

## Implementation Intent
Introduce one module that owns the blocking stdin read as a request-driven daemon thread, and route all three prompt call sites through it. Nothing about the prompts, the cancellation structure, the shutdown race, or the timeout values changes: the change is which thread performs the blocking call and how its result is handed back to the event loop, so that nothing in the shutdown path ever has to wait for it.

## Requirements
- `REQ-001`: a new module `scripts/agent/stdin_reader.py` owns the read primitive. It exposes one class that, on first use, starts exactly one `threading.Thread` with `daemon=True` and performs the blocking prompt call on that thread, and delivers the result to the awaiting coroutine through `loop.call_soon_threadsafe` on the loop captured from the awaiting coroutine (`asyncio.get_running_loop()` at request time). The primitive uses no `concurrent.futures` executor, no `asyncio.to_thread`, and no `run_in_executor`; it has no `close()`, `shutdown()`, `join()` or `atexit` hook, because joining it is exactly the cost this Plan removes.
- `REQ-002`: the primitive is request-driven and serves one outstanding request per instance. The worker waits on a `threading.Event` (blocked wait, no polling, no sleep loop, no busy wait — the issue's "may hold stdin but must not spin" constraint), performs exactly one read per request, and never pre-reads a line the caller has not requested. A second concurrent request on the same instance raises `RuntimeError` instead of being silently queued, so an overlap that the current call sequence does not produce cannot become a silent hang.
- `REQ-003`: cancellation and delivery rules are stated in code: cancelling the awaiting task cancels the request future (which `await` already does) and the worker's completed read is applied only to a future that is not `done()`; if the originating future is done, the line is delivered to the newest pending request on that instance, and if there is none it is discarded. Delivery to a closed loop is a no-op: the `RuntimeError` from `call_soon_threadsafe` is caught at the delivery point. No line is read speculatively and no abandoned line is replayed to a later process.
- `REQ-004`: exceptions raised by the read are captured in the worker and stored as the future's exception, so `EOFError` and `KeyboardInterrupt` reach the awaiting call site as ordinary, retrievable exceptions and the worker thread continues serving. The caught tuple is explicit — `(Exception, KeyboardInterrupt, SystemExit)` — matching what `concurrent.futures` delivers today and what `_input_task` already expects (`repl_input_loop.py:145`); no blind `except Exception`, and no suppression comment. The `_InputAborted` sentinel and its stated reason (`repl_input_loop.py:24-31`) keep their role, because the new bridge stores exceptions instead of raising them into loop callbacks.
- `REQ-005`: each owner holds its own reader instance and no instance is shared between owners: `ReplInputLoop` creates one, `CLIView` creates one, `tool_approval.py` keeps one module-level lazily created instance (it has no component to own it). A reader instance is used only from the event loop that issues its requests.
- `REQ-006`: `_read_input`'s two read calls (`scripts/agent/repl_input_loop.py:144`, `:191`) call that instance instead of `loop.run_in_executor(None, ...)`, with the same `"> "` prompt and the same `lambda: input("> ")` semantics. Everything around them stays as written: `_input_task`, `_InputAborted`, `_shutdown_watcher`, `input_coro.cancel()`, `_abort_input()`, `_input_coro` tracking, the `None`-fallback branch (`:189-194`), `_read_input`'s `(self, loop)` signature, `_repl_loop`'s race structure, and `_GRACEFUL_TIMEOUT_S` (`:55`).
- `REQ-007`: `CLIView.read_multiline` reads continuation lines through its own reader instance with the same `"... "` prompt and the same stop conditions (no trailing backslash, empty line, EOF, Ctrl-C). `CLIView.__init__` no longer creates an input executor (`:112`), the private pool and its lazy creation are removed (`:285-289`), `CLIView.__del__` (`:114-118`) and `import concurrent.futures` (`:13`) are deleted, and `read_multiline`'s public signature (`:267-269`) and the `Reader` protocol (`:74-84`) stay byte-identical — including the currently unused `loop` parameter, which this Plan does not remove.
- `REQ-008`: the 30 s bound keeps its value (`_INPUT_TIMEOUT_S = 30`, `cli_view.py:24`) and keeps producing `logger.warning("Multiline input timed out")` followed by `raise KeyboardInterrupt` (`:293-295`); only the docstring's stated rationale ("the default ThreadPoolExecutor is saturated") is corrected to describe what the code now bounds. No timeout value anywhere is retuned, per the issue's instruction.
- `REQ-009`: `_prompt_user_approval` reads its answer through a single private seam in `scripts/agent/tool_approval.py` that calls the module's reader instance; the prompts (`"  Execute? [yes/no]: "`, `"  Execute? [y/N]: "`), the `"yes"`/`"y"` matching, `check_approval`'s exactly-one-prompt-per-tool-call shape (`:186`), the audit calls, and the `EOFError` propagation path are unchanged. Because `asyncio` is used in that module only for `to_thread` (`:11`, `:125`, `:128`), the import is removed in the same step.
- `REQ-010`: `docs/23_agent/agent_07_05_cli-and-commands-repl-io.md` records how a pending stdin read is released at shutdown and that process exit is bounded by the shutdown path rather than by keyboard input, and `docs/23_agent/agent_10_06_operations-and-observability-rag-diagnostics-and-memory.md:65`'s claim that the stdin-read "executor thread … terminates upon process exit" is replaced with the reader-thread behavior. Each corrected sentence names behavior a named test asserts.
- `REQ-011`: unchanged: `scripts/agent/repl.py`, `scripts/agent/signal_handler.py` and its non-POSIX fallback, `_GRACEFUL_TIMEOUT_S` in both files, `ctx.conv.shutdown_requested`, `ReadResult` values, `ReplInputLoop.run()`'s signature, `/exit`, tab completion and history setup (`cli_view.py:100-160`), `memory_data_ops.py:48`'s synchronous `input(prompt)`, `startup_validation.py:163-171`, `_read_input`'s call sites in tests, and the `Reader` protocol. No new third-party dependency: only `threading` (stdlib) is added.

## Assumptions
- At most one stdin read is outstanding at a time in production: `_read_input` awaits its read before `read_multiline` is called (`repl_input_loop.py:196-198`), and `_prompt_user_approval` runs only during a dispatch (`tool_runner.py:409`), when no prompt read is in flight. The `RuntimeError` guard in `REQ-002` is what makes a violated assumption visible rather than a hang.
- Calling `input()` from a daemon thread is equivalent, for terminal behavior, to calling it from the executor threads the code uses today: both are non-main threads, and `readline`'s history/completion state is process-global (`cli_view.py:100-160`). The mechanism change is the thread's daemon flag and ownership, not the read function or the prompts.
- A daemon thread killed at interpreter exit loses nothing that must be flushed: `input()` writes only its prompt and produces no result the caller still wants after the caller stopped waiting.
- `loop.call_soon_threadsafe()` is available on the loop implementations this project runs (Linux `SelectorEventLoop`, `deploy/start_agent.sh`) and on Windows event loops; no `loop.add_reader()`/`add_pipeReader` is used, so the non-POSIX path is untouched.
- The existing race structure in `_read_input` is the intended one (its own comments at `:168`, `:271-273`), so this Plan rewires only what it awaits, not how it decides.
- `check_approval`'s single-prompt-per-call shape and `EOFError` propagating to `_surface_turn_error` are current behavior worth preserving, verified by reading `tool_approval.py:186` and `tool_runner.py:409` rather than assumed.

## Design
Path B: one mechanism defect shared by three call sites (all stdin reads are performed by a `concurrent.futures` pool worker that neither cancellation nor `asyncio.run()` can release), corrected by one new module and three rewirings, with an observable behavior change only at process exit. Classification evidence: the measurements in `Problem` separate the mechanisms that satisfy the issue's Acceptance Criteria from those that do not, and the tree shows a second and third instance of the same defect (`cli_view.py`, `tool_approval.py`) that the issue's target list did not name.

Design decisions:
- A plain daemon `threading.Thread`, not any `concurrent.futures` executor. Measured: a private pool returns the loop in 0.20 s but the process in 6.09 s, and a pool subclass whose workers are daemon still waits 6.10 s, because `_python_exit` joins every entry of `_threads_queues` regardless of the daemon flag (`/usr/lib/python3.14/concurrent/futures/thread.py:23-31`). The issue's first option is therefore excluded by measurement, not by preference.
- A reader thread, not `loop.add_reader(sys.stdin, …)`. A non-thread design would need a readable fd, would bypass `readline` (losing tab completion and history for the prompt), would break `input()`'s EOF/Ctrl-C behavior, and `add_reader` is not supported on Windows event loops — which the issue's "must not regress the Windows path" constraint rules out. `http_lifecycle_process_terminator.py:105-113`'s poll-with-`asyncio.sleep` precedent is the right *intent* (no joinable worker) but cannot be applied to a blocking `readline`-backed call, which cannot be decomposed into polls.
- Request-driven, never speculative. The worker performs a read only when a request exists, because eager pre-reading would consume a line the caller may never ask for (the continuation loop, `_should_exit`, and the EOF path all depend on reading exactly when asked). Rejected alternative: a background thread that always reads and pushes into a queue — simpler code, but it would steal input the REPL has not requested and would make `/exit` handling depend on queue contents.
- Instance ownership, not a process-wide singleton. Rejected: one global reader. It would make test order matter (a read abandoned by one test would block the next test's request for the full duration of its stub), and two owners sharing one instance would need a cross-instance lock that the event-loop thread would have to block on while a worker waits for a keystroke — converting this Plan's fix back into a wait. Each owner holding its own instance costs at most one additional daemon thread and keeps each component's lifecycle local (`REQ-005`). The one-request-per-instance guard makes the "only one read is outstanding in practice" assumption fail loudly if it ever stops holding.
- Loop capture per request, from `asyncio.get_running_loop()`. Rejected: binding the reader to one loop object. The suite creates a fresh loop per test (`tests/test_cli_view.py:103-140`, `test_repl.py` fixtures), and a reader bound to the first loop would deliver into a closed loop. Per-request capture also means a reader instance is only ever used from the loop that issued the request (`REQ-005`).
- Exceptions are delivered as stored future exceptions, and the caught tuple is explicit. `concurrent.futures` already stores `BaseException` in the item's future today, so `EOFError`, `KeyboardInterrupt` and `SystemExit` all reach `_input_task` now (`repl_input_loop.py:145` catches the latter two); the new bridge must reproduce that without raising through loop callbacks, which is exactly why `_InputAborted` exists (`repl_input_loop.py:24-31`). A `try/except Exception` only would drop `KeyboardInterrupt` and silently change the Ctrl-C contract.
- Abandoned-line policy: deliver to the newest pending request, otherwise discard. Both are defensible; delivering to a live request avoids silently swallowing keystrokes the user already typed after a timeout, and discarding is what makes a closed-loop case harmless. The policy is stated in code and pinned by `TestCancelledRequestDelivery` (`AC-4`), and its interactive consequence is UNK-01's measurement, not a claim.
- Preserve every observable, change only the thread. Prompts, EOF and Ctrl-C mapping, continuation stop conditions, the 30 s bound's value and its `KeyboardInterrupt` mapping, `check_approval`'s single prompt and `EOFError` propagation, `_read_input`'s signature, `_repl_loop`'s race, `Reader`, and `read_multiline`'s currently unused `loop` parameter all stay (`REQ-006`..`REQ-009`, `REQ-011`). Two temptations this Plan explicitly declines: tuning a timeout the issue forbids tuning, and removing dead-but-public API (`Reader`, `read_multiline`'s `loop`) that this change does not make dead.
- Cross-plan overlaps recorded deliberately: `repl_input_loop.py` and `agent_07_05_*.md` are shared with `plans/20261022-030840_plan.md` in disjoint regions with a fixed order (repl001 first, so the `:144` branch is live before this Plan rewires it); `plans/20261022-024105_plan.md` (doc001) must be implemented before this Plan's Phase 2 or its prompt-literal evidence re-derived (Notes, WI-01); `tests/agent/test_repl.py` is expected to be repl003's target later.
- Coverage gate: per `rules/toolchain.md`, changed-line coverage at the 90% threshold is required; the new module is the most thoroughly covered file in this Plan because its unit tests drive it directly through an injected read function.

## Risks
- **Risk**: A daemon reader thread holds stdin while the process exits, so a terminal could be left in an unexpected `readline` state (the question the issue itself leaves open). → **Mitigation**: the exit property is measured (`AC-1`), the terminal-state claim is UNK-01 with an explicit interactive check as an implementation step, and the docs do not claim it is safe before that check is done (AC-9).
- **Risk**: Re-pointing 25 patch targets in `test_tool_approval_preflight.py` could hide an approval-behavior regression if a substitution is applied mechanically to a case whose real intent was "no prompt happened at all" (`:805`). → **Mitigation**: the suite's expectations and parameterizations are unchanged (`Tests`), `:805`'s assertion is re-pointed to the same seam rather than deleted, and the whole approval suite plus the `EOFError` propagation case run in the validation plan (AC-6).
- **Risk**: Two reader instances (input loop and view) could both be active if a future change overlaps reads, and stdin ownership would become ambiguous. → **Mitigation**: `REQ-002`'s `RuntimeError` guard makes an overlap inside one instance visible, the single-read-at-a-time property is stated as an assumption with its call-sequence evidence, and the design records why a process-wide singleton was not chosen so the next change does not assume one exists.
- **Risk**: A line typed for a cancelled read can be delivered to the next request, so an answer could appear against a prompt the user did not see. → **Mitigation**: the delivery rule is explicit and pinned by `TestCancelledRequestDelivery`; the reachable case is only a read abandoned by a timeout or a cancellation, after which the loop exits, and UNK-01 records the interactive check.
- **Risk**: `_read_input` and `read_multiline` already carry the timeout and cancellation shapes that `cv001` added; rewiring could re-introduce the hang `cv001` fixed. → **Mitigation**: the 30 s bound and its `KeyboardInterrupt` mapping are kept and newly tested (`REQ-008`, `AC-4`), and `cv001`'s issue is listed in `Reference Files` so the implementer sees why the bound exists.
- **Risk**: The change touches a file already near the size and complexity ceiling (`repl_input_loop.py` 13224 B, `_repl_loop` D (29)). → **Mitigation**: no new branch is added to `_read_input` (two call replacements only), all guard logic lives in the new module, and `check_module_size.py` plus `radon cc` run in the validation plan with "may only stay or improve" thresholds.
- **Risk**: Cross-plan collision with repl001 (`repl_input_loop.py`, `agent_07_05_*.md`) and doc001 (its `REQ-005` evidence cites the prompt literals this Plan moves). → **Mitigation**: disjoint regions, the fixed order repl001 → this Plan, the doc001 ordering note in `Notes`, and `check_plan_target_overlaps.py` in the validation plan (WI-01).
- **Risk**: The plan asserts "the default loop executor is not used for stdin reads", but the loop's default executor is still used elsewhere in the process (DB offloads, `startup_validation.py`). → **Mitigation**: `AC-2`'s assertion is scoped to the three stdin modules with a loop spy during reads, and the remaining non-stdin uses are named in Scope and `Reference Files` so the claim cannot be read as a global statement.
