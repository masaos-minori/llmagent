# Work Plan: Make SessionMessageRepository._VALID_ROLES configurable

## Goal
Make `_VALID_ROLES` extensible so that new role types can be added without modifying `session_message_repo.py`, while preserving backward compatibility with the existing hardcoded default set {"user", "assistant", "tool", "system"}.

## Scope
- Add a `MessageRoleConfig` dataclass to `scripts/agent/config_dataclasses.py`
- Integrate it into `AgentConfig` as a new field
- Modify `SessionMessageRepository` to accept an optional roles source (config, callable, or fallback to default)
- Update docstrings and add tests
- No changes to DB schema, fetch logic, or message serialization

## Assumptions
1. The project already has a well-established configuration pattern via `AgentConfig` composition in `config_dataclasses.py`
2. The four usages of `_VALID_ROLES` in `session_message_repo.py` (save, save_many, replace_messages) should all respect the configured roles
3. Backward compatibility means: when no custom roles are provided, behavior must remain identical to current (default set = {"user", "assistant", "tool", "system"})
4. The `LLMMessage` TypedDict in `shared/types.py` uses `Literal["user", "assistant", "tool", "system"]` — extending it would require coordination across layers

## Unknowns
1. Will any downstream consumers (e.g., MCP servers, external tools) send non-standard roles? If not, the benefit of configurability may be limited.
2. Should the `LLMMessage` TypedDict Literal type also be extended, or kept separate from the runtime validation set?
3. Does the `strict_mode` flag semantics change if invalid roles come from a trusted config source vs. untrusted input?
4. Are there any existing TOML config files that could serve as a natural home for role definitions?

## Affected areas
- scripts/agent/session_message_repo.py — use injected roles instead of module-level constant
- scripts/agent/config_dataclasses.py — add MessageRoleConfig + integrate into AgentConfig
- tests/agent/test_session_message_repo.py — tests for custom roles
- scripts/shared/types.py — consider updating LLMMessage Literal type (optional, out-of-scope for Phase 1)

## Design
The approach follows the existing pattern in this codebase: define a dataclass in `config_dataclasses.py`, compose it into `AgentConfig`, and inject it where needed.

```python
@dataclass
class MessageRoleConfig:
    """Valid message roles for SessionMessageRepository."""
    allowed_roles: frozenset[str] = field(default_factory=lambda: frozenset({"user", "assistant", "tool", "system"}))

@dataclass
class AgentConfig:
    # ... existing fields ...
    messages: MessageRoleConfig = field(default_factory=MessageRoleConfig)
```

`SessionMessageRepository.__init__` gains an optional `roles_source` parameter:
- If provided: use it directly as the valid roles set
- If None: fall back to the module-level `_DEFAULT_VALID_ROLES` constant
- The module-level `_VALID_ROLES` becomes `_DEFAULT_VALID_ROLES` and is only used as the fallback

This avoids circular imports (session_message_repo doesn't import config_dataclasses at module level) and keeps the injection point explicit.

## Implementation steps
1. Add `MessageRoleConfig` dataclass to `scripts/agent/config_dataclasses.py` after `DiagnosticsConfig`
2. Add `messages: MessageRoleConfig = field(default_factory=MessageRoleConfig)` to `AgentConfig`
3. Rename `_VALID_ROLES` to `_DEFAULT_VALID_ROLES` in `session_message_repo.py`
4. Add `roles_source: frozenset[str] | None = None` parameter to `SessionMessageRepository.__init__`
5. In `__init__`, resolve effective roles: `self._valid_roles = roles_source if roles_source is not None else _DEFAULT_VALID_ROLES`
6. Replace all references to `_VALID_ROLES` with `self._valid_roles` in save(), save_many(), replace_messages()
7. Add `get_valid_roles()` method to `SessionMessageRepository` for introspection
8. Update docstrings on `__init__` and affected methods
9. Write unit tests for custom roles injection
10. Verify no regressions by running existing test suite

## Validation plan
- Unit test: `test_custom_roles_injection` — verify save/save_many/replace_messages reject roles outside the custom set
- Unit test: `test_default_roles_fallback` — verify no regression when `roles_source=None`
- Unit test: `test_strict_mode_with_custom_roles` — verify strict mode raises correctly for custom invalid roles
- Integration test: verify `AgentConfig.messages.allowed_roles` is properly composed and accessible
- Run full existing test suite (`uv run pytest`) to confirm no regressions
- Manual check: verify no other callers depend on `_VALID_ROLES` being exactly `{"user", "assistant", "tool", "system"}`

## Risks
1. **Circular import**: If `SessionMessageRepository` needs to access `AgentConfig` at runtime, importing `config_dataclasses` inside `__init__` could cause issues. Mitigation: use lazy import or keep injection point simple (frozenset parameter).
2. **Type consistency**: Extending roles beyond the four standard ones breaks the `LLMMessage.role` Literal type in `shared/types.py`. This requires cross-layer coordination.
3. **Config loading order**: If `AgentConfig` is built before `SessionMessageRepository` is instantiated, the config must be available at construction time.
4. **Backward compatibility**: If any existing code passes unexpected values to `roles_source`, the default fallback behavior must still match current behavior.
