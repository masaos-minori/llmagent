## Goal
Fix `tests/eventbus/test_eventbus_route_helpers_metrics.py::TestRunWithDbLockMetrics`'s 2 order-dependent flaky failures: a genuine `int()`-vs-`float()` parsing bug when reading a Prometheus counter's text-exposition value, and a lack of per-test isolation for the shared, process-global default `prometheus_client` `REGISTRY` that both tests read from.

## Priority
Medium

## Scope
- **In-Scope**:
  - Fix `test_lock_contention_counter_increments_on_slow_acquire`'s metric-value parsing (`int(lines_after[-1].split(" ")[-1])`) to correctly parse Prometheus's float-formatted counter values (e.g. `"1.0"`).
  - Add per-test isolation for the Prometheus metrics this file reads (`eventbus_db_lock_wait_time_seconds`, `eventbus_db_lock_contention_total`), so results do not depend on what other tests in the same pytest session already observed via the shared default `REGISTRY`.
- **Out-of-Scope**:
  - `scripts/eventbus/route_helpers.py`'s `_db_lock_wait_time`/`_db_lock_contention` metric definitions and `run_with_db_lock`'s `.observe()`/`.inc()` calls — confirmed correct and already unconditionally invoked on every call.
  - Any other eventbus test file's own use of these same metric names (if any) — out of scope for this Plan; only this file's own 2 tests are fixed here.

## Background
Both tests import `from prometheus_client import REGISTRY, generate_latest` and read the process-global default `REGISTRY` (the same singleton `scripts/eventbus/route_helpers.py`'s `Histogram`/`Counter` objects register themselves to at import time). Since this registry is never reset between tests (or between test files, within one pytest process), whether `test_lock_contention_counter_increments_on_slow_acquire` observes a `"0.0"` or `"N.0"` (N ≥ 1) counter value depends on test execution order (`pytest-randomly` reorders tests per run, confirmed via `Using --randomly-seed=...` in the test output) — and once the value is non-zero, `int("1.0")` raises `ValueError: invalid literal for int() with base 10: '1.0'`, since Prometheus's text exposition format always renders Counter/Histogram values with a decimal point.

## Problem
Confirmed via 4 consecutive `uv run pytest tests/eventbus/test_eventbus_route_helpers_metrics.py -q` reruns, producing 4 different pass/fail combinations (`3 passed`; `2 failed, 1 passed`; `1 failed, 2 passed`; `3 passed`):
- `test_lock_contention_counter_increments_on_slow_acquire`: `int(lines_after[-1].split(" ")[-1])` raises `ValueError` whenever the shared counter's already-accumulated value is non-zero (formatted as e.g. `"1.0"`), which happens whenever an earlier test (in this file or elsewhere in the same session) already incremented `eventbus_db_lock_contention_total`.
- `test_lock_wait_time_metric_observed`: `assert len(lines) > 0` intermittently fails despite `run_with_db_lock`'s `_db_lock_wait_time.observe(lock_wait)` being unconditional (confirmed via Read, `scripts/eventbus/route_helpers.py:148`) — the exact ordering/isolation interaction causing this specific intermittent failure was not fully pinned down within this planning cycle (see Unknowns).

## Reason for change
A flaky test in the full suite undermines confidence in CI signal and can mask genuine regressions in DB-lock-contention observability. The `int()`/`float()` bug is a clear, deterministic defect independent of the flakiness once triggered.

## Implementation intent
Fix the parsing bug by using `float()` instead of `int()` (Prometheus counter/histogram sample values are always floats in the text exposition format) — compare as `float(...) >= 0` per the test's own already-lenient intent ("Counter may or may not have incremented... just verify it's a valid number"). Separately, add isolation so both tests observe only their own call's effect: either capture each metric's value immediately before the test's `run_with_db_lock` calls and assert on the *delta* (after − before) rather than the raw cumulative value, or use a fresh, test-scoped `CollectorRegistry` if `run_with_db_lock`'s metrics can be parameterized to register there instead of the global default (confirm feasibility at implementation time — this may require making `route_helpers.py`'s metrics registry-configurable, which would expand this Plan's target files; prefer the before/after-delta approach first since it requires no production change).

## Requirements
- `REQ-001`: Fix `test_lock_contention_counter_increments_on_slow_acquire`'s counter-value parsing to use `float()` instead of `int()`.
- `REQ-002`: Make both tests' assertions independent of accumulated state from other tests in the same session (before/after delta, or equivalent isolation).
