# Plan: Extract gate-chain helper and merge invoke/record-result pattern between ToolExecutor and ToolTransportInvoker

## Goal
Remove two structural duplications on the MCP tool-call gate/transport path, as pure
behavior-preserving refactors:
1. Extract the ordered gate-check sequence (`_check_startup_mode` → `_check_health` →
   `_ensure_lifecycle_ready`) currently inlined in `ToolExecutor._raw_execute`
   (`scripts/shared/tool_executor.py:109-145`) into a single reusable helper method.
2. Merge the byte-for-byte identical try/except + `_record_success`/`_record_transport_error`
   block that exists independently in both `ToolTransportInvoker.invoke()`
   (`scripts/shared/tool_transport_invoker.py:202-207`) and `ToolExecutor._raw_execute`
   (`scripts/shared/tool_executor.py:140-145`) into one shared method on
   `ToolTransportInvoker`, with `ToolExecutor` calling the inherited version.

This closes items 1 and 2 of `issues/done/20260813-133041_tool_executor_structural_followups.md`
without touching item 3 (typed args DTO), which remains explicitly out of scope for its own
future requirement.

## Scope

### In-Scope
- `scripts/shared/tool_executor.py`: extract `_run_gate_chain(server_key)` (or equivalent name)
  from `_raw_execute`, preserving exact call order and exact exception/return behavior of each
  gate check; change `_raw_execute` to call the inherited merged invoke/record method instead of
  reimplementing the try/except locally.
- `scripts/shared/tool_transport_invoker.py`: extract `_invoke_and_record(server_key, transport,
  tool_name, args, sem)` (or equivalent name) from `invoke()`'s tail try/except block, keeping it
  override-safe (no `@final`, no name-mangled double-underscore).
- `tests/shared/test_tool_executor_order.py`: must keep passing unchanged, in particular
  `test_transport_success_full_path`'s `call_order == ["resolve", "health", "lifecycle",
  "transport"]` assertion; may gain new characterization assertions for gate early-exit behavior
  if a gap is found (see Unknowns/Design).
- A new characterization test file under `tests/shared/` (e.g.
  `tests/shared/test_tool_transport_invoker_merge.py`) written and passing against the
  **pre-merge** code first, pinning `invoke()`'s current success path (`_record_success` called
  once with correct args) and `TransportError` path (`_record_transport_error` called once with
  correct args, its return value propagated), then re-verified unchanged after the merge.

### Out-of-Scope
- Item 3 of the source issue ("typed args DTO") and any file under `scripts/agent/`
  (`factory.py`, `tool_runner.py`, `repl.py`, `context.py`, `repository_gateway.py`,
  `commands/cmd_mdq.py`) — confirmed by `rg` (Affected areas below) that none of these call
  `.invoke(` or `_raw_execute` directly, so this internal restructuring needs no changes there.
- `invoke()`'s own lifecycle-handling block (`tool_transport_invoker.py:185-191`, which catches
  only `ServerCooldownError`) — this is a separate code path from `ToolExecutor`'s
  `_ensure_lifecycle_ready` (which catches `OSError`/`RuntimeError` and calls
  `self._health_registry.record_failure`); the two are not being unified, only the tail
  try/except+record block is shared (see Design, and Risks).
- The semaphore ensure/get step (`self._ensure_semaphores()` then `(self._semaphores or
  {}).get(server_key)`) — this stays duplicated at each call site, matching the requirement's
  suggested `_invoke_and_record(..., sem)` signature, which takes `sem` as an already-resolved
  parameter rather than resolving it internally.
- No public method signature change on `ToolExecutor` or `ToolTransportInvoker`.
- No new/removed file under `scripts/` (no `deploy/deploy.sh` line change needed) and no new MCP
  server (no MCP service map update needed).

## Assumptions
- "Behavior-preserving" is verified primarily by (a) the existing order-locking test
  `tests/shared/test_tool_executor_order.py::test_transport_success_full_path` and (b) a new
  characterization test for `invoke()`'s success/error recording, per the requirement's own
  Implementation instructions — no additional test infrastructure is needed beyond what's named
  in the requirement.
- The existing `tests/shared/test_tool_transport_invoker.py` (pre-existing, not modified by this
  plan) already exercises `invoke()`'s observable side effects (stat counters, health-registry
  calls) for both success and `TransportError` paths; the new characterization test file adds
  direct assertions on `_record_success`/`_record_transport_error` call counts/arguments (mocked),
  which is a narrower, complementary pin specifically for the merge, not a replacement.
- `ToolExecutor` remains the sole subclass of `ToolTransportInvoker` in `scripts/` (confirmed by
  `rg`, Affected areas below), so this is a same-file-pair merge with no fan-out to other
  subclasses to account for.

## Design
Both files sit in the `shared` layer. `ToolExecutor` (`scripts/shared/tool_executor.py:47`)
subclasses `ToolTransportInvoker` (`scripts/shared/tool_transport_invoker.py:25`); this is a
same-package, same-layer inheritance relationship (`shared` importing from `shared`), so no
import-linter boundary is crossed by adding a new protected method to either class —
`PYTHONPATH=scripts uv run lint-imports` currently only reports pre-existing, unrelated
`eventbus → shared`/`db` violations, none touching `tool_executor.py`/`tool_transport_invoker.py`.

Current call sequence (verified by direct read, matches the requirement's Background exactly):
- `ToolExecutor._raw_execute` (`tool_executor.py:109-145`): resolves `server_key` via
  `self._resolver.resolve(tool_name)`, then in order — `_check_startup_mode(server_key)` →
  `_check_health(server_key)` (inherited from `ToolTransportInvoker`) →
  `await self._ensure_lifecycle_ready(server_key)` (executor-specific override, catches
  `OSError`/`RuntimeError`, calls `self._health_registry.record_failure`) → resolves transport →
  `self._ensure_semaphores()` + get `sem` → try/except block (lines 140-145) calling
  `_execute_with_semaphore`, then `_record_success`/`_record_transport_error` (both inherited from
  `ToolTransportInvoker`).
- `ToolTransportInvoker.invoke()` (`tool_transport_invoker.py:175-207`): `_check_health` →
  lifecycle block (lines 185-191, inlined, catches only `ServerCooldownError`, no
  `record_failure` call — this is intentionally a *different* lifecycle path from
  `ToolExecutor._ensure_lifecycle_ready` and is not touched by this refactor) → resolve transport
  → `_ensure_semaphores()` + get `sem` → try/except block (lines 202-207), byte-for-byte identical
  to `_raw_execute`'s.

Target design:
1. `_run_gate_chain(self, server_key: str) -> ToolCallResult | None` on `ToolExecutor`, calling
   `_check_startup_mode` → `_check_health` → `await self._ensure_lifecycle_ready`, returning the
   first non-`None` error result (short-circuiting exactly as today) or `None` if all gates pass.
   `_raw_execute` calls this once before transport resolution, replacing the three separate
   inline checks with one call plus one `if err := ...: return err`-style short-circuit.
2. `_invoke_and_record(self, server_key, transport, tool_name, args, sem) -> ToolCallResult` on
   `ToolTransportInvoker`, containing exactly the current try/except body (`_execute_with_semaphore`
   → `_record_success` → return; `except TransportError as e: return self._record_transport_error`).
   `invoke()` calls it after its own (unchanged) lifecycle block; `ToolExecutor._raw_execute` calls
   the *inherited* version after its gate chain, instead of reimplementing the block.
3. Layering: no new imports needed for either extraction (both helpers use only names already
   imported in their respective files). No import-linter contract change required.

## Risks

- **Risk**: The order-locking test's `_make_executor()` helper builds `ToolExecutor` via
  `__new__` and directly patches private attributes/mocks, so it could still report a passing
  `call_order` even if the gate-chain extraction subtly changes production wiring in a way the
  mock-based helper doesn't observe. → **Mitigation**: also run the broader
  `tests/shared/test_tool_executor_routing.py` and `tests/shared/test_tool_executor.py` suites
  (already mandated in Implementation steps Phase 3), which construct `ToolExecutor` through more
  realistic paths and exercise the same gates from a second angle. Likelihood: low.
- **Risk**: A future implementer conflates `invoke()`'s own lifecycle-handling block (catches only
  `ServerCooldownError`, no `record_failure`) with `ToolExecutor._ensure_lifecycle_ready` (catches
  `OSError`/`RuntimeError`, calls `record_failure`) while doing the merge, and accidentally unifies
  them — a silent behavior change beyond this requirement's scope. → **Mitigation**: Design and
  Implementation steps above explicitly call out that `invoke()`'s lifecycle block is untouched;
  only the tail try/except+record block is shared. Likelihood: medium (the two blocks look
  superficially similar, which is exactly why this note is called out explicitly).
- **Risk**: The merged `_invoke_and_record` is made `@final`, name-mangled, or otherwise
  non-overridable, silently violating the acceptance criterion that it "remain override-safe."
  → **Mitigation**: Implementation steps specify a normal single-underscore instance method with
  no `@final` decorator; this is a one-line naming/decorator choice to get right during the edit,
  not a structural risk. Likelihood: low.
- **Risk**: This file pair has high recent churn (12 + 7 commits in the last 30 days) and an
  effectively single-author bus factor, so a concurrent unrelated change could conflict with this
  refactor if timed poorly. → **Mitigation**: keep the two extractions as separate, independently
  revertable commits (per Implementation steps), and run the full `tests/shared/` suite
  immediately before finalizing to catch any interleaving issue early. Likelihood: low (single
  active contributor reduces the chance of an uncoordinated concurrent edit).
