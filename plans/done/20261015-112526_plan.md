# Plan — Move MCP security validation to per-server self-validation + posture contract

## Goal
- Replace the Agent's startup security audit (which reads each MCP server's config
  file) with per-server self-validation plus a versioned, non-secret Security Posture
  contract that each server exposes and the Agent validates.
- Remove the Agent's cross-config read so the orchestrator stays restricted to
  `agent.toml` (REQ-001), cross-server isolation holds, and fail-closed is preserved.
- Gate Tool Discovery and RuntimeToolRegistry registration on a validated posture
  contract instead of on static tool enablement.

## Priority
High

## Scope

### In-Scope
- Common platform in `scripts/shared/security/`: Security Validation result DTO with
  reason-code vocabulary, security policy version, posture-contract version, non-secret
  config fingerprint, common startup-validation flow, non-secret logging/diagnostics.
- Security Posture contract (versioned, non-secret) exposed on each server's `/health`.
- Per-server self-validation for Shell, Git, GitHub, CI/CD, File Read/Write/Delete,
  RAG Pipeline, MDQ, and any other HTTP MCP server the Agent uses.
- Agent-side posture validator, failure classification (Availability/Safety/Integrity),
  Tool Discovery gating, RuntimeToolRegistry construction gated on posture.
- Shadow Validation harness to run the old audit and new self-validation in parallel
  during migration.
- Canonicalization: remove the old audit, its loaders, the single import-linter
  exception, and update dependent callers/tests.
- Docs: ADR-002, ADR-003, ADR-004, ADR-007, ADR-014, ADR index / invariant matrix.

### Out-of-Scope
- stdio transport adoption.
- External network exposure of MCP servers.
- mTLS, PKI, remote attestation, binary signing, SBOM, provenance.
- RuntimeToolRegistry Hot Rediscovery.
- Changing the authentication mechanism between Agent and server.
- Changing tool approval policy.
- Comprehensive OS-user / container / service-management changes.
- Large-scale reorganization of server config keys.
- embed-llm readiness (separate, already addressed).
- Any change that becomes necessary belongs to a separate design change, not this plan.

## Background
- ADR-002 Decision #7 permits one exception: the Agent reads shell/git/github/cicd
  configs at startup via `agent/security_audit_config.py` loaders, narrowed to frozen
  audit DTOs holding only security-posture fields. `.importlinter` encodes this as the
  single `agent-mcp-config-models` contract (one `ignore_imports` grant for
  `agent.security_audit_config` -> the four MCP config models).
- This conflicts with the orchestrator's restriction to `agent.toml` (REQ-001,
  `scripts/agent/context.py:308` `ConfigLoader.restrict_to("agent.toml")`; asserted in
  `tests/agent/test_context.py`). Satisfying REQ-001, cross-server isolation
  (`tests/agent/test_config_permission_cross_server.py`), and fail-closed
  (`tests/agent/test_audit_security_failures.py`) inside one restricted process is
  impossible; widening the allowlist weakens REQ-001.
- Each MCP server calls `ConfigLoader.restrict_to(self.own_config_file)` in
  `MCPServer.run_http()` (`scripts/mcp_servers/server.py:240`), so it reads and can
  validate its own config fully. The precondition for self-validation exists today.
- ADR-002 Review Triggers name the direction: each server can enforce the audited
  settings at its own startup, after which the audit moves out of the Agent.

## Problem
The Agent is the single process that reads every MCP server's config at startup. That
read is required to fail under REQ-001 restriction, yet the audit needs it — an
unsatisfiable triangle inside one process. The current resolution grows ADR-002's
exception (narrowed DTOs) rather than removing the cross-config read.

## Reason for change
Per `memo2.md` (MCP Server自己セキュリティ検証 移行作業指示書, 2026-10-15; the file is no longer
present in the repository, so its content is carried forward through the source issue),
ownership of security validation must follow per-process config ownership (ADR-002): each server
validates itself; the Agent validates only a standardized contract. This shrinks ADR-002's
exception instead of growing it and makes the architecture self-consistent.

## Implementation intent
- Put the common platform (DTO, contract schema, startup flow) in `scripts/shared/security/`
  (new package under the existing `scripts/shared/` leaf layer; importable by both `agent`
  and `mcp_servers`).
- Each server extends its existing partial security logic into a full self-validation that
  returns the common result DTO and exposes a non-secret posture on `/health`.
- The Agent validates the posture contract (schema, version, server key, required-check
  results, fingerprint presence, health/tool-discovery identity match), classifies
  failures, and gates discovery/registration.
- During migration, run the old audit and the new self-validation in parallel (Shadow
  Validation) and compare results without emitting raw config values; only after
  equivalence switch canonical and remove the old audit.

## Requirements

### Phase A — Common platform
- `REQ-001`: The common Security Validation result DTO carries check ID, check status, reason code,
  security policy version, posture-contract version, ready state, and a non-secret
  config fingerprint.
  It is the single type servers return and the Agent consumes.
- `REQ-002`: The Security Posture contract is versioned and non-secret (server key, policy
  version, check results, fingerprint; never Secret, raw allowlist, sensitive path, or
  config body) and is published on each server's `/health`. Liveness, Readiness, and
  Security Posture remain distinct concepts; the initial integration adds posture
  minimally into the existing `/health`.
- `REQ-003`: All servers share one startup ordering: Config Load -> Schema Validation ->
  Common Security Validation -> Server-Specific Security Validation -> Dependency
  Validation -> Tool Capability Consistency Validation -> Runtime State Installation ->
  HTTP Bind -> Ready. A server that fails validation does not bind HTTP or return Ready.
- `REQ-004`: Non-secret logging/diagnostics are standardized (reason codes, no Secret in
  logs/exceptions/diagnostics; existing message masking preserved).

### Phase B — Per-server self-validation (one requirement per server)
- `REQ-005` Shell: enforce own-config-only, sandbox backend present, command allowlist
  non-empty; verify published tools vs. sandbox/allowlist; expose posture.
- `REQ-006` Git: repo allowlist, protected branch, force-push disabled, dirty worktree /
  detached HEAD checks; expose posture.
- `REQ-007` GitHub: repo/branch allowlists, destructive-op guard, wildcard-range and
  merge/push/delete constraints, external API token presence; expose posture.
- `REQ-008` CI/CD: workflow allowlist, ref guard, input validation; expose posture.
- `REQ-009` File Read/Write/Delete: path boundary / symlink-escape guard, atomic write,
  recursive-delete limits; expose posture.
- `REQ-010` RAG Pipeline: db/index/allowed-dir checks; expose posture.
- `REQ-011` MDQ: db/index/allowed-dir and auth checks; expose posture.
- `REQ-015` Web Search (added 2026-10-16 by user decision resolving `UNK-04`): browser allowlist
  deny-all semantics, result-count bounds, outbound timeout and response-size bounds; expose posture.
  This requirement exists because `REQ-012`/`REQ-014` posture gating applies to every HTTP-transport
  server in `config/agent.toml`, and `config/agent.toml:375-383` registers `web_search` as one; without
  a self-validation row its posture would be missing and `search_web`/`browser_fetch` would be excluded
  from the registry.

### Phase C — Agent-side posture validation and gating
- `REQ-012`: The Agent validates the posture contract (schema, contract version, server
  key, required-check presence/results, policy-version compatibility, fingerprint presence,
  health/tool-discovery identity match). The Agent holds no real allowlist values, paths,
  sandbox internals, server secrets, or server config models.
- `REQ-013`: Failures are classified Availability vs Safety vs Integrity. Missing/unreachable
  required server = Availability (abort); unreachable non-required server = Availability
  (partial availability only when conditions met). Invalid posture schema, unsupported
  contract version, server-key mismatch, missing/failing required check, `validated=false`
  = Integrity/Safety (abort). A non-required server never converts a Safety/Integrity
  failure into partial availability.
- `REQ-014`: Tool Discovery and RuntimeToolRegistry registration occur only when
  `ready=true` and `security.validated=true`. No Hot Rediscovery.

### Phase D — Migration and canonicalization
- `REQ-016`: Shadow Validation runs the old audit and new self-validation in parallel and
  compares results (MATCH_PASS / MATCH_FAIL / AGENT_ONLY_FAIL / SERVER_ONLY_FAIL /
  CHECKSET_MISMATCH / CONTRACT_ERROR) without emitting raw config values.
- `REQ-017`: After equivalence, make the new way canonical: remove the old audit, its
  loaders, the single import-linter exception, and update dependent callers/tests. No
  implicit runtime fallback to the old audit; rollback to a known-good version instead.

### Phase E — Documentation
- `REQ-018`: ADR-002 removes the cross-config-read exception, adds the per-server
  self-validation decision, and makes "Agent does not read server config" and "posture has
  no Secret" invariants. ADR index / invariant matrix updated.
- `REQ-019`: ADR-003 aligns to posture-gated `/v1/tools`, no registration of failing
  servers, self-validation failure distinguished from static tool disable, no Hot
  Rediscovery.
- `REQ-020`: ADR-004 aligns to posture failures as Safety/Integrity, non-required servers
  still abort, unreachable separated from unsafe, subprocess exception retained.
- `REQ-021`: ADR-007 aligns to posture contract on `/health`, readiness conditions, auth
  requirement, no Tool Discovery before validation, HTTP-only.
- `REQ-022`: ADR-014 aligns so the server owns its validation, the Agent validates only the
  common contract, and the Agent does not replicate server-specific safety.

## Design
- **Ownership follows process config ownership (ADR-002).** Each server reads only its own
  config and validates itself fail-closed before binding HTTP. The Agent stops reading
  `*_mcp_server.toml` and importing MCP config models; it validates only the standardized
  contract. This removes the single cross-config read that conflicts with REQ-001.
- **Common platform in `scripts/shared/security/`.** The result DTO, contract schema, and
  startup flow live in the shared leaf layer, importable by both `agent` (Agent -> shared
  is allowed) and `mcp_servers` (mcp_servers -> shared is allowed). No new import-linter
  layer is introduced. Where an existing ADR carries an explicit exception, a common
  check is expressed as `not_applicable` or a dedicated check ID rather than silently
  skipped.
- **Posture contract is versioned and non-secret.** It carries server key, policy version,
  check results, and a non-secret config fingerprint (sha256 over a normalized, non-secret
  view of the config). It never carries Secret, raw allowlist, sensitive path, or config
  body. Tool Discovery and Tool Call are permitted only when `ready=true` and
  `security.validated=true`.
- **Check statuses are `OK`, `FAILED`, `NOT_APPLICABLE`, and a non-fatal `WARNING`.** A
  `WARNING` check records a finding the old Agent audit reported as a warning (for example
  `github.allow_force_push=true`) without flipping `validated`, so a server that today starts
  with a warning keeps starting after migration. Only `FAILED` blocks Ready. A check is never
  silently omitted: an inapplicable check is reported as `NOT_APPLICABLE`.
- **Startup ordering is uniform.** Config Load -> Schema Validation -> Common Security
  Validation -> Server-Specific Security Validation -> Dependency Validation -> Tool
  Capability Consistency Validation -> Runtime State Installation -> HTTP Bind -> Ready.
  Validation failure blocks HTTP bind and Ready.
- **Failure classification.** Availability (missing/unreachable server) vs Safety/Integrity
  (invalid posture, bad version, key mismatch, failing required check, `validated=false`).
  A non-required server never converts a Safety/Integrity failure into partial availability.
- **Migration by Shadow Validation.** Old audit and new self-validation run in parallel;
  results compared (MATCH_PASS/MATCH_FAIL/AGENT_ONLY_FAIL/SERVER_ONLY_FAIL/CHECKSET_MISMATCH/
  CONTRACT_ERROR) without emitting raw config values. No implicit runtime fallback to the
  old audit; rollback to a known-good version instead.
- **Invariants.** Existing INV-01..INV-04 retained. Add: every server validates its own
  config before ready (INV-05); a failing server exposes no Tool Discovery or Tool calls
  (INV-06); the Agent does not read server configs or import their models (INV-07); the
  Agent discovers a server only after validating its posture contract (INV-08); posture
  contains no Secret or raw sensitive value (INV-09).

## Risks
- **Risk**: A server's self-validation diverges from the old audit during migration, hiding
  a misconfig. → **Mitigation**: Shadow Validation must show MATCH_PASS/MATCH_FAIL before
  canonicalization; any CHECKSET_MISMATCH blocks the switch.
- **Risk**: Removing the import-linter exception breaks an undiscovered import. →
  **Mitigation**: `lint-imports` is a mandatory gate in Phase 4; the sole importer is
  `security_audit.py` (verified).
- **Risk**: Extending `/health` changes the payload consumed by existing monitoring. →
  **Mitigation**: Posture fields are additive; switch conditions require health-response
  compatibility with existing monitoring.
- **Risk**: Non-required server converts a Safety failure into partial availability. →
  **Mitigation**: INV-06 / AC-007 enforced by a dedicated failure-classification test.
- **Risk**: `deploy.sh` drift between repo and `/opt/llm`. → **Mitigation**: new shared
  modules are rsynced by `deploy.sh`; no `deploy.sh` edit needed for Python files; verify
  parity after deploy.
- **Risk**: Self-declaration gives no third-party assurance; the trust anchor is the
  managed MCP server binary, not the posture contract itself. → **Mitigation**: document
  this limitation explicitly; rely on the managed-binary supply chain; treat the posture
  contract as a self-declaration, not a cryptographic attestation.
- **Risk**: A uniform "empty allowlist is `FAILED`" rule applied to Web Search would make
  the shipped deny-all `browser_allowed_domains = []` refuse to bind. → **Mitigation**:
  row `51` reports `server.browser_allowlist` as `NOT_APPLICABLE` when empty and `WARNING`
  for a malformed entry, because an empty web allowlist disables `browser_fetch` instead of
  widening access; `tests/mcp_servers/cicd/test_mcp_server_health_status.py:19-31` pins the
  shipped-config `ready=true` outcome.
