# Work Plan: Make sensitive field filtering configurable in DiagnosticStore

## Goal
Make the list of sensitive fields configurable via DiagnosticsConfig, ensuring sensitive field filtering keeps pace with the evolving set of diagnostic fields without requiring manual code changes.

## Scope
- Modify `scripts/agent/config_dataclasses.py` to add `sensitive_fields` field to DiagnosticsConfig
- Modify `scripts/agent/diagnostic_store.py` to load and merge configured sensitive fields
- Update docstrings and module comments

## Assumptions
1. DiagnosticsConfig can accept a new field without breaking existing configurations
2. The hardcoded list `("artifacts", "rag_stage_outcomes")` should remain as default values
3. Merging configured fields with hardcoded list ensures backward compatibility

## Unknowns
1. Does DiagnosticsConfig have a mechanism to specify default values for new fields?
2. Are there other callers of `_filter_sensitive_fields()` that depend on the hardcoded list?
3. Configured sensitive fields should merge with (not replace) the hardcoded defaults for backward compatibility. Should operators be able to remove fields from the default list? If so, a separate `remove_fields` config would be needed.

## Affected areas
- scripts/agent/diagnostic_store.py
- scripts/agent/config_dataclasses.py
- Sensitive field filtering components

## Design
The current `_filter_sensitive_fields()` method uses a hardcoded list of sensitive fields. This should be changed to load the list from DiagnosticsConfig, merging configured fields with the hardcoded list for backward compatibility.

## Implementation steps
1. Read `scripts/agent/config_dataclasses.py` and identify the DiagnosticsConfig class
2. Add a new field `sensitive_fields: frozenset[str] = frozenset(("artifacts", "rag_stage_outcomes"))` to DiagnosticsConfig
3. Read `scripts/agent/diagnostic_store.py` and identify the exact location of `_filter_sensitive_fields()`
4. Modify `_filter_sensitive_fields()` to load DiagnosticsConfig via `_load_diagnostics_config()`
5. Merge configured sensitive fields with the hardcoded list
6. Apply filtering to all merged fields
7. Update the docstring of `_filter_sensitive_fields()` to reflect that the field list is now configurable
8. Update the module-level comment above `_SENSITIVE_FIELDS` to note that the list is augmented by DiagnosticsConfig
9. Run tests to ensure no regressions

## Validation plan
- Unit test for `_filter_sensitive_fields()` with various field combinations including newly added sensitive fields
- Integration test verifying diagnostic output during startup/shutdown shows filtered values
- Test verifying that DiagnosticsConfig.sensitive_fields defaults to the original hardcoded list when not specified

## Risks
1. If DiagnosticsConfig cannot accept a new field without breaking existing configurations, this change could cause issues
2. If other code depends on the hardcoded list being used, changing to a configurable list could break behavior
3. _SENSITIVE_PATTERNS raises an exception when encryption is disabled — adding new patterns could affect error handling paths
