# Plan: Fix ToolTransportInvoker _maybe_semaphore type annotation mismatch

## Goal
Fix the type annotation mismatch in `ToolTransportInvoker._maybe_semaphore()` where the return type is declared as `contextlib.AbstractAsyncContextManager[None]` but `contextlib.nullcontext()` is returned when `sem` is `None`.

## Priority
Critical

## Scope
- **In-Scope**: Fixing the type annotation mismatch in `ToolTransportInvoker._maybe_semaphore()`; adding comments explaining the design decision; updating related documentation if needed.
- **Out-of-Scope**: Changing the retry logic itself; modifying other transport layers; changing error handling behavior.

## Background
`scripts/shared/tool_transport_invoker.py` line 100-106:
```python
@staticmethod
def _maybe_semaphore(
    sem: asyncio.Semaphore | None,
) -> contextlib.AbstractAsyncContextManager[None]:
    """Return the semaphore as an async context manager, or nullcontext if None."""
    if sem is not None:
        return sem
    return contextlib.nullcontext()
```

The return type annotation declares `contextlib.AbstractAsyncContextManager[None]`, but `contextlib.nullcontext()` is NOT an async context manager — it's a synchronous context manager. In Python 3.7+, using `nullcontext` with `async with` works because `nullcontext` doesn't have `__aenter__`/`__aexit__` methods, so Python falls back to the sync version. However, type checkers will complain about the type mismatch.

## Problem
1. Type annotation mismatch: `contextlib.nullcontext()` does not implement `AbstractAsyncContextManager`
2. Code review confusion: The intent of semaphore release is unclear when `nullcontext` is used
3. Type checker warnings may hide real type mismatches

## Reason for change
Type safety improvement. Eliminating type annotation mismatches ensures that type checkers can catch real errors and prevents confusion during code reviews.

## Implementation intent
Either:
1. Use `contextlib.nullcontext()` explicitly and update the return type annotation to reflect that both sync and async context managers are valid returns
2. Create a custom async context manager that wraps `nullcontext` and implements `AbstractAsyncContextManager`

Approach 1 is preferred as it's simpler and more maintainable.

## Design
Path A classification applies: direct verification inspection only, no architecture/dependency/historical/operational analysis.

Two possible approaches:
1. **Update return type annotation**: Replace `contextlib.AbstractAsyncContextManager[None]` with a union type that includes both `asyncio.Semaphore` and `contextlib.nullcontext`:
   ```python
   def _maybe_semaphore(
       sem: asyncio.Semaphore | None,
   ) -> asyncio.Semaphore | contextlib.nullcontext:
   ```
   However, this is not valid Python syntax.

2. **Use Protocol-based approach**: Define a Protocol that both `asyncio.Semaphore` and `nullcontext` satisfy:
   ```python
   @runtime_checkable
   class AsyncContextManagerLike(Protocol):
       async def __aenter__(self) -> None: ...
       async def __aexit__(self, exc_type, exc_val, exc_tb) -> bool | None: ...
   
   def _maybe_semaphore(
       sem: asyncio.Semaphore | None,
   ) -> AsyncContextManagerLike:
       if sem is not None:
           return sem
       return contextlib.nullcontext()
   ```
   This approach is more complex but provides better type safety.

3. **Simplest approach**: Keep the current implementation but add a comment explaining why `nullcontext` is safe to use with `async with`:
   ```python
   # Note: contextlib.nullcontext is safe to use with `async with` even though
   # it's not an AbstractAsyncContextManager. Python 3.7+ falls back to the
   # sync context manager protocol when __aenter__/__aexit__ are missing.
   ```

Approach 3 is preferred as it's simplest and most maintainable.
