## Background
Config reload replaces `RuntimeToolRegistry._tools` via `apply_policy()`
(`scripts/shared/runtime_tool_registry.py:150-175`). REQ-002
(`docs/00_governance_03_issue-and-uncertainty-management.md:518-527`, confirmed via
Read) was filed to track whether this swap is atomic, and remains `Status: open`.

## Problem
Step 3 investigation (adversarial verification against current source) found the
Issue's central factual claim — "the current implementation ... directly assigns
`self._tools = new_tools`, creating a non-atomic transition window" — mischaracterizes
the existing code. Reading `apply_policy()` in full:

```python
def apply_policy(
    self,
    tier_map: Mapping[str, AgentSafetyTier],
    allowed_tools: Sequence[str] = (),
) -> None:
    new_tools: dict[str, RuntimeTool] = {}
    for name, tool in list(self._tools.items()):
        ...
        new_tools[name] = dataclasses.replace(tool, ...)
    self._tools = new_tools
```

The loop builds the entire replacement state into a local variable (`new_tools`)
without ever touching `self._tools` until the single assignment on the last line. This
already is the "build complete new registry state without modifying the existing one,
then atomically swap references" pattern the Issue's Implementation Intent describes
as the desired fix. Two consequences follow directly from this structure, both already
true today:
1. **Rollback on failure**: if any iteration of the loop raises (e.g. a future,
   currently-hypothetical failure in `dataclasses.replace()`), the exception
   propagates before `self._tools = new_tools` executes, so `self._tools` still holds
   the original, unmodified dict — no explicit rollback code is needed because the
   mutation is deferred to the very last statement.
2. **No partially-swapped state is observable**: under CPython, a bare attribute
   assignment (`self._tools = new_tools`) is a single bytecode-level reference swap
   protected by the GIL — any concurrent reader calling `resolve()`/`get()`/
   `all_tools()` (all of which read `self._tools` fresh on each call) sees either the
   complete pre-swap dict or the complete post-swap dict, never a mix.

`git blame` confirms this exact build-then-swap structure was introduced by commit
`520c9b39f9` ("feat: tool policy comprehensive tests and mdq command improvements",
2026-09-17) — the same commit that implemented REQ-001's fix, three days before this
Issue was filed. `tests/shared/test_runtime_tool_registry.py`'s existing
`test_atomic_single_swap_identity_change` (lines 257-263, confirmed via Read) already
asserts `id(reg._tools)` changes exactly once per `apply_policy()` call — direct
evidence the swap is a single-reference replacement, not an in-place mutation.

What is still missing: no test exercises the rollback-on-exception path (nothing in
the existing test suite raises mid-loop and checks `self._tools` afterward), and no
test observes the registry from a second thread during `apply_policy()` to confirm no
mixed-state read is possible. REQ-002's governance entry was never updated to reflect
the 2026-09-17 fix.

## Reason for change
Leaving REQ-002 `open` after the underlying atomic-swap structure was already
implemented creates the same governance drift as REQ-001: the tracked risk (mixed-state
routing during reload) reads as unaddressed, and the "build-then-swap gives rollback
and atomicity for free" property has no regression test pinning it against a future
refactor that might, for example, mutate `self._tools` in place inside the loop.

## Implementation intent
Add two regression tests that directly exercise the properties the Issue's Acceptance
Criteria describe (no mixed-state routing; rollback leaves original state intact),
grounded in the already-correct build-then-swap structure, then close REQ-002's
governance entry with a citation to the new evidence — no behavior change to
`apply_policy()` itself, since its atomicity already follows from CPython's reference-
assignment semantics.

## Design
The atomic-swap design was already made and implemented in commit `520c9b39f9`
(build into a local dict across the loop, single reference-swap assignment at the
end); this Plan does not change that design. The two new tests make explicit,
in code, the two guarantees that structure already provides implicitly: (1) an
exception during build never reaches the swap statement, so `self._tools` is
untouched on failure, and (2) because the swap is a single reference rebind, any
concurrent read sees a complete, self-consistent registry state — never a partial
mix of old and new tool entries. Both properties are consequences of ordinary Python
semantics (deferred mutation via a local variable; GIL-atomic attribute assignment),
not of any concurrency primitive, so no lock, `threading.Lock`, or compare-and-swap
mechanism is added — consistent with the Issue's own "single-process assumption
holds" exclusion of distributed locking.

`scripts/shared/config_loader.py` is excluded as a target file for the same reason
established in REQ-001's Plan (`plans/20260920-203022_plan.md`): it contains no
`RuntimeToolRegistry`/`apply_policy` reference; the real reload call site is
`scripts/agent/services/config_reload.py`'s `_sync_services()`, which needs no change
since the atomicity guarantee lives entirely inside `apply_policy()`.

## Risks
- **Risk**: A threading-based test (REQ-002) could be flaky under CI load or on a
  slower machine, since it depends on the GIL yielding between the reader and writer
  threads during the window of the test → **Mitigation**: use a tight loop with a high
  iteration count (e.g. thousands of `apply_policy()` calls) rather than a single
  timed race, so the test's statistical power to catch a hypothetical regression stays
  high even if any individual iteration's scheduling is unpredictable; document the
  CPython-GIL dependency in the test docstring (see UNK-02).
- **Risk**: Marking REQ-002 `resolved` could be seen as retroactively validating an
  unreviewed 2026-09-17 change → **Mitigation**: same as REQ-001's Plan — the
  Resolution note cites the exact commit SHA and the new tests, making the claim
  independently checkable.
