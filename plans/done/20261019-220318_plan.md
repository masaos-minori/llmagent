## Goal
- Make agent shutdown of MCP server subprocesses complete in bounded time (one termination timeout, not the sum over servers) and leave no MCP server process behind after a normal or interrupted shutdown.

## Priority
Medium

## Scope
- **In-Scope**:
  - Fix the termination wait so a server that exits promptly on SIGTERM is recognised as exited instead of being waited on until the SIGKILL escalation.
  - Terminate all managed servers concurrently, with every server signalled before any wait begins.
  - Tests for both behaviors, and the lifecycle documentation of shutdown.
- **Out-of-Scope**:
  - Setting `timeout_graceful_shutdown` or any other change in `scripts/mcp_servers/server.py` (the Issue's hypothesis was refuted, see Problem).
  - The `cicd` `http_error` display, the unreachable remote `embed-llm`, startup order and health-check logic, and the binary build and deploy procedures.
  - Cleaning up processes that are already orphaned (an operator action).

## Background
- Observed on 2026-10-19 after deploying rebuilt binaries: two agent runs with piped input under a `timeout 100` wrapper left 14 MCP server processes (7 servers, two processes each) re-parented to PID 611 and ports 8004, 8005, 8007, 8008, 8010, 8012, 8013 in LISTEN. The log showed `Escalated to SIGKILL for process group` for only the first two servers (`shell`, `git`); the other seven were never signalled. An older `mcp_mdq` from an earlier session also still held port 8013.
- The shutdown path is the `finally` of the REPL session, which closes resources and calls the lifecycle `shutdown_all`; the HTTP lifecycle manager delegates to the shutdown coordinator, which delegates to the process terminator.

## Problem
- Confirmed by source: the shutdown coordinator terminates servers one at a time, each with a 30 second bound, so ten servers take up to about 300 seconds, and any outer deadline or interruption leaves the servers not yet reached running.
- Confirmed by experiment (2026-10-19, scratch scripts outside the repository): the Issue's hypothesis that uvicorn waits for keep-alive connections is not supported. A uvicorn server with an open idle keep-alive client exits in 0.2 seconds on SIGTERM, with or without `timeout_graceful_shutdown`.
- Confirmed by experiment and source: the terminator waits for exit by polling `os.killpg(pgid, 0)` and never reaps the child. A process that has exited but is not yet reaped (a zombie) keeps the group "alive" for that probe; in the experiment the probe raised `ProcessLookupError` only after `poll()` reaped the child. The wait loop contains no `poll()` call, so a server that exits at once on SIGTERM is still waited on for the full 30 seconds and then SIGKILLed. This matches the log (two servers each escalated after the full bound). Whether it explains every delay on the deployed binaries (launcher plus child) is Unknown UNK-01.
- Orphaned servers keep their ports, so a later start can fail the port check or talk to a stale server from an older binary.

## Reason for Change
- Operational reliability: leftover servers can silently serve old code after a redeploy, which undermines the deploy verification.
- Shutdown time is unpredictable and grows with the number of servers.

## Implementation Intent
- Keep the responsibility split: the terminator owns signalling and the exit check, the coordinator owns ordering and the overall bound.
- Fix the root cause at the smallest scope: reap the child while waiting so exit is detected immediately; then make the coordinator signal every server first and wait for all of them together.
- Preserve the SIGTERM then SIGKILL escalation, process-group signalling, the SIGINT absorption during shutdown, and the tracking-entry behavior on termination failure.
- The terminator is also used by the startup-failure paths; the fix must keep their behavior (they benefit from the same correct exit detection).

## Requirements
- `REQ-001`: The terminator's wait for exit MUST detect an exited, unreaped child (reap it, for example through `poll()`) so a server that exits on SIGTERM returns without waiting for the timeout.
- `REQ-002`: The shutdown coordinator MUST terminate all managed servers concurrently so total shutdown time is bounded by one termination timeout plus a small margin.
- `REQ-003`: Every managed server's process group MUST receive the termination signal before any wait begins, so an interruption or an outer deadline during shutdown cannot leave an unsignalled server.
- `REQ-004`: A server that ignores SIGTERM MUST still be removed by SIGKILL within the bound, and the tracking-entry behavior on a termination failure MUST be unchanged.
- `REQ-005`: Tests MUST cover REQ-001 to REQ-004, including a regression test that fails on the current terminator.
- `REQ-006`: The lifecycle documentation MUST describe the shutdown behavior (concurrent termination, bound, and exit detection).
- `REQ-007`: After the change is deployed, a normal `/exit` MUST leave no `/opt/llm/bin/mcp_*` process and no listener on ports 8004 to 8014.

## Design
- Path B (more than 3 target files). Architecture: `lint-imports` reports 6 contracts kept; the change stays inside `scripts/agent/` and adds no import, so no layer contract is affected. Dependency graphing: the terminator has three callers (shutdown coordinator, health checker, subprocess launcher) plus the manager's restart path; the coordinator has one caller. Historical: four commits in 30 days each for the two source files, single author. Operational: the production agent binary embeds `scripts/agent/`, so the fix reaches production only after a rebuild; no process holds a lock relevant to the change.
- Root cause (revised from the Issue): the wait loop never reaps the child, so the group liveness probe stays true for a zombie. The Issue's uvicorn graceful-shutdown hypothesis is not supported by the experiment, and `scripts/mcp_servers/server.py` is therefore not a target.
- Order of work: the regression test first (observe it fail), then the terminator fix, then the coordinator change with its tests, then the documentation, then deploy and verification.
- Coordinator design direction: send the termination signal to every group before awaiting anything, then await all terminations together under the existing bound; keep the pop-before-terminate tracking and the failure branch (entry retained). Exact mechanics are left to the implementation procedure.
- Quality baseline (2026-10-19): `radon cc` grades `terminate_with_timeout` C (18) and `shutdown_all` C (12), so the change should not raise them; `vulture` reports only the two unused signal-handler parameters (existing); `bandit` reports only the existing `subprocess` import and `assert` notes (no Medium or High).

## Risks
- **Risk**: Reaping in the wait loop changes behavior for the other callers of the terminator (startup failure and restart). → **Mitigation**: `Popen.poll()` is idempotent; run the caller regression tests listed in the Validation plan and keep the escalation path unchanged.
- **Risk**: Concurrent termination interleaves with the SIGINT absorption and the per-entry tracking, losing a tracking entry on failure. → **Mitigation**: Keep pop-before-terminate and the retained entry on failure, and test the failure branch with several servers.
- **Risk**: The reap fix does not cover the onefile launcher plus child pair on the deployed binaries (UNK-01). → **Mitigation**: The SIGKILL escalation still bounds the time; the AC-006 check detects a remaining delay and a follow-up issue is filed.
- **Risk**: A real-subprocess test is slow or flaky. → **Mitigation**: Use a short `sleep`-based child and tight timeouts; keep it deterministic by asserting on the exit status, not on wall-clock thresholds alone.
- **Risk**: The agent binary stays stale after the source change. → **Mitigation**: The deploy step rebuilds the stale `agent` binary and checks freshness with `tools/manage_binaries.py check`.
