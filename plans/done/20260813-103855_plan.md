## 6. Design
### Core Problem
The current implementation computes set-based diffs (using `EXCEPT`) only when aggregate counts indicate a discrepancy. This creates a blind spot: if `chunks == fts` but some chunks are missing from FTS and some orphan FTS entries exist, neither the aggregate counts nor the set-based diffs will detect the problem.

### Solution: Unconditional Set-Based Diff Computation
Compute set-based diffs independently of aggregate count thresholds:

```python
# Always compute these diffs regardless of aggregate counts
fts_missing_from_chunks = db.execute(
    "SELECT id FROM chunks_fts_docsize EXCEPT SELECT chunk_id FROM chunks"
).fetchall()

fts_missing_in_fts = db.execute(
    "SELECT chunk_id FROM chunks EXCEPT SELECT id FROM chunks_fts_docsize"
).fetchall()
```

Then populate `affected_chunk_ids`, `affected_orphan_chunk_ids`, etc. based on these unconditional diffs.

### Updated `is_consistent()` Logic
Add a check for the case where both `fts_gap > 0` AND `fts_orphan_count > 0` simultaneously (shouldn't happen with pure aggregate counts, but could occur if set-based diffs reveal hidden issues):

```python
def is_consistent(report: RagConsistencyReport) -> bool:
    consistent: bool = (
        # ... existing checks ...
        and not report.diagnostic_errors
        and (report.fts_gap == 0 or report.fts_orphan_count == 0)  # mutual exclusion
    )
    return consistent
```

Actually, a better approach: add a new field `fts_mixed_discrepancy` to indicate when both types of discrepancies coexist.

### Diagnostic Error Tracking Enhancement
Currently, `diagnostic_errors` tracks SQL execution failures. Enhance to also track:
- Cases where set-based diffs were computed but aggregate counts didn't match
- Specific query categories that failed during diagnostic execution

- **Risk**: Adding `failed_queries` field may change serialization format. → **Mitigation**: Use `None` as default; ensure backward compatibility.
