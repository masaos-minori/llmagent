## Goal
- Bring the git MCP tests back in line with the current git MCP behavior so the full suite is green again, by fixing each failing test according to the contract the recent upstream change deliberately altered, and by removing the order dependence of the tests that fail only inside a full run.

## Priority
High

## Scope
- **In-Scope**: the four git MCP test modules that contain the failing tests; diagnosing and removing the shared state that makes two tests order-dependent.
- **Out-of-Scope**: changing git MCP production code (unless diagnosis proves a defect, which is then reported as an additional target); the audit-record emission design; EventBus changes; the other tracked pre-existing problems.

## Background
Six git MCP tests fail on the current upstream head after the change "complete git-mcp audit record emission gaps fix (REQ-005 through REQ-010)". Five failures reproduce in a clean checkout of that commit alone; one test fails only inside the full run. Root causes were traced in this plan's verification.

## Problem
- Stale fixture after the requirement that the format functions take a mandatory config: one push test patches the removed config loader while the service under test has no config, so the push operation's assertion fails and surfaces as an empty "git_push failed" error.
- Stale expectations after the removal of the push stdout-rejection branch: one formatter test and two repository-state tests assert that a rejection or error marker in push output makes the call fail; both detection points were removed on purpose. A rejected push normally exits non-zero and GitPython raises, which the service reports as an error, so the removed substring checks were not the only safety net; this should be confirmed by a test.
- Order dependence: two tests in the git security compliance module pass alone and fail inside the full run (and the dry-run test passed in one subset run while failing in another), so state leaks between tests; the upstream commit already touched this module's isolation.

## Reason for change
A red suite hides new failures and blocks the post-sync validation required before every push.

## Implementation intent
- Update tests to the new contract rather than weaken them: inject an authorized config into the service for the push test; replace the three marker tests with tests of the new behavior (a rejected push raising a command error becomes a service error; a clean push result is returned as is).
- Find the leaking shared state by running the module and the full run in different orders, then fix the fixture or monkeypatch scope.

## Requirements
- `REQ-001`: The dry-run push test builds the service with an authorized remote configuration instead of patching the removed loader, and passes.
- `REQ-002`: The three push-rejection tests are rewritten to the post-change contract (a failing push is reported through the execution-error path; output text alone does not fail the call), after the owner confirms that the removal was intended.
- `REQ-003`: The two order-dependent tests pass in isolation and in a full run, with the leaking state identified and removed.
- `REQ-004`: The full suite (excluding the separately tracked EventBus transition module) passes in two consecutive runs; lint, format, and type checks report no new findings.
