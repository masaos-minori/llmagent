## Goal
- Correct `HttpTransport.call()`'s retry backoff so delays increase across retry attempts (1s, then 2s, for `_RETRY_MAX=3`) and are only slept when another attempt will follow, and ensure MCP HTTP transport error diagnostics never expose raw response bodies while still recording safe, correlatable fields (status code, request ID, server key, tool name, sanitized error code) — including applying the project's existing secret-redaction mechanism to the two `shared/` modules that currently bypass it.

## Problem
Confirmed by direct inspection of `scripts/shared/http_transport.py`:
- Line 115: `wait_sec = 2 ** (self._RETRY_MAX - attempt - 1)  # 4, 2, 1` — with `_RETRY_MAX = 3`, this produces delays of 4s (attempt 0), 2s (attempt 1), 1s (attempt 2): decreasing, not increasing.
- The `for attempt in range(self._RETRY_MAX):` loop (lines 106-150) contains no `break` statement, so its `else:` clause (lines 143-150, the "Retry exhausted" diagnostic) always executes once the loop completes normally. Because attempt 2 (the final, non-retried attempt) still executes the `await asyncio.sleep(wait_sec)` at line 124 when the response status is retryable, a sleep occurs after the last attempt even though no further retry follows it — confirmed via `tests/shared/test_tool_executor.py::test_retry_delay_values_via_sleep_mock` (lines 225-254), which currently asserts exactly 3 sleep calls (`[4, 2, 1]`), one per attempt including the last.
- Line 137: `f"status={e.response.status_code} response={e.response.text[:300]!r}"` embeds up to 300 characters of the raw HTTP response body into the `TransportError` message. This message becomes `ToolCallResult.output` via `ToolTransportInvoker._record_transport_error()` → `_error_result(server_key, str(e), error_type="transport")` (`scripts/shared/tool_transport_invoker.py` lines 148-158, 106-120) — confirming the Issue's claim that raw response bodies may reach `ToolCallResult.output`.
- Both `scripts/shared/http_transport.py` (line 15) and `scripts/shared/tool_transport_invoker.py` (line 22) declare `logger = logging.getLogger(__name__)` directly, per this codebase's own convention for library modules (`scripts/shared/logger.py`'s module docstring: "Library modules should use: `logger = logging.getLogger(__name__)`"). `shared.logger`'s `_RedactionFilter` (lines 41-52) is only ever attached via `Logger._configure_logger()` (`self._logger.addFilter(_RedactionFilter())`, line 145) to a `Logger`-wrapped instance. Because Python `logging.Logger.callHandlers()` invokes only each ancestor *handler's* own filters during propagation — not the ancestor *logger* object's filters — a `Logger`-level filter on one named logger (e.g. an entry-point's `"agent"` logger) never applies to records originating from an unrelated logger such as `"shared.http_transport"` or `"shared.tool_transport_invoker"`, confirmed by `grep`: neither file imports `shared.logger.Logger`, and no root-level `logging.basicConfig()`/filter installs redaction globally (only `scripts/db/create_schema.py` calls `logging.basicConfig(level=logging.INFO)`, with no filter argument). This confirms the Issue's hedged claim ("secret-redaction may not be applied to server-provided fields before logging").

## Reason for change
Retry timing and error reporting share the same HTTP failure loop in `HttpTransport.call()`. The current backoff decreases from 4 to 2 to 1 seconds and sleeps after the final attempt, while raw error bodies may be logged or returned, and the two modules that log these diagnostics bypass the project's own secret-redaction mechanism. Correcting only one aspect would retain either unnecessary latency, information exposure, or an unredacted logging path.

## Implementation intent
Rework the retry loop in `HttpTransport.call()` to compute delay from the number of retries already performed (increasing: `2 ** attempt_index` across the retries that actually occur) and to sleep only when the loop will continue to another attempt; track the last retryable HTTP status seen so the exhaustion diagnostic can report it without the raw body; replace the `e.response.text[:300]!r` fragment with only status code, request ID (when present), and the existing sanitized exception-type prefix. Add a small public helper in `scripts/shared/logger.py` (alongside the existing `register_secret()`) that attaches `_RedactionFilter` to an arbitrary `logging.Logger` instance, and call it from both `http_transport.py`'s and `tool_transport_invoker.py`'s module-level logger initialization; register the transport's auth token as a secret the same way `scripts/shared/mcp_config.py` already does. Update the two retry tests whose current assertions encode the old (buggy) behavior, and add new tests proving secrets/sensitive fragments are not leaked.

## Design
The retry loop in `HttpTransport.call()` iterates `attempt in range(self._RETRY_MAX)` (0, 1, 2 for `_RETRY_MAX=3`). The corrected design computes the wait from the number of retries *already performed* (i.e. `attempt`, zero-indexed) rather than the number *remaining*, and only sleeps when `attempt < self._RETRY_MAX - 1` (i.e. another attempt will follow): `wait_sec = 2 ** attempt` for `attempt in {0, 1}` yields delays `1, 2` — matching the Issue's stated target exactly, and skips the sleep entirely on `attempt == 2` (the final attempt), which currently sleeps unnecessarily due to the `for...else` structure having no `break`. A `last_retryable_status: int | None` variable is set on every retryable-status branch iteration and threaded into the `else:` clause's "Retry exhausted" message, replacing the `last_exc`-only diagnostic with an explicit status field pulled from the *response*, not from an exception message string. The `except httpx.HTTPStatusError` branch's `detail` string switches from `f"status={e.response.status_code} response={e.response.text[:300]!r}"` to `f"status={e.response.status_code} request_id={e.response.headers.get('x-request-id', '')!r}"` — dropping the raw body while retaining exactly the fields the Issue's Required Changes name (status code, request ID, and the existing tool/server_key/exception-type-prefix fields already present in the surrounding message format).

For redaction, `scripts/shared/logger.py` gains a small function (name to be finalized per UNK-01) that performs `target_logger.addFilter(_RedactionFilter())`, callable without constructing a full `Logger` wrapper (which requires a `log_file` argument unsuited to library modules, per this file's own module docstring). `http_transport.py` and `tool_transport_invoker.py` each call this helper once, immediately after their existing `logger = logging.getLogger(__name__)` line, and `HttpTransport.__init__` additionally calls `register_secret(self._auth_token)` when a token is configured, mirroring `mcp_config.py:283`'s existing call site. This is a targeted, additive change: it does not alter `shared/`'s leaf position in `.importlinter`'s dependency hierarchy, does not change any public method signature, and does not touch `ToolCallResult`/`TransportErrorInfo`'s schema.
