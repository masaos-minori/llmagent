# Fix DbCondition.UNKNOWN treated identically to CORRUPTION in recover_corruption()

## Goal
Ensure `recover_corruption()` distinguishes `DbCondition.UNKNOWN` from `DbCondition.CORRUPTION`, preserving the target database and requiring operator intervention instead of triggering automatic backup-restore.

## Priority
High

## Scope
- **In-Scope**: Adding explicit `UNKNOWN` handling in `recover_corruption()`, updating its docstring, adding tests, updating ADR-008 Known Deviations
- **Out-of-Scope**: Changing `_classify_error()` logic, changing CORRUPTION branch behavior for rag/session, changing workflow/eventbus no_recovery_allowed path

## Background
ADR-008 (post ADR-011 merge, 2026-08-31) INV-17 requires that Unknown or unclassifiable integrity-check failures preserve the target database and require operator intervention rather than triggering automatic restoration. Confirmed during the ADR-011 → ADR-008 merge by reading `scripts/db/recovery.py` in full: `_classify_error()` returns `DbCondition.UNKNOWN` for exceptions that are neither `sqlite3.OperationalError` (lock/permission) nor `sqlite3.DatabaseError`/`ValueError` (corruption), but `recover_corruption()`'s branch `if condition in (LOCK_CONTENTION, PERMISSION_FAILURE, INVALID_FORMAT)` does not include `UNKNOWN`, so execution falls through to the "CORRUPTION or UNKNOWN" comment and attempts `_restore_from_backup()` for `rag`/`session` targets exactly as it would for confirmed corruption.

## Problem
An Unknown or unclassifiable integrity-check failure on `rag.sqlite` or `session.sqlite` is not distinguished from confirmed corruption and can trigger an automatic backup restore, contradicting ADR-008 INV-17.

## Reason for change
The ADR-008 invariant exists specifically because an automatic action taken on a failure of unknown cause is riskier than requiring operator judgment — an ambiguous failure (e.g., a transient I/O error the classifier does not recognize) should not silently trigger a backup restore that could discard legitimate current data.

## Implementation intent
Add an explicit `UNKNOWN` branch in `recover_corruption()` that returns a result equivalent to `no_recovery_allowed` — preserving the target database and reporting that operator intervention is required — mirroring the behavior already implemented for `workflow`/`eventbus` targets, without changing the existing (already-decided) `CORRUPTION` branch's restore behavior for `rag`/`session`.

## Requirements
- `REQ-001`: `recover_corruption()` MUST distinguish `DbCondition.UNKNOWN` from `DbCondition.CORRUPTION` and NOT trigger automatic backup-restore for UNKNOWN conditions on `rag`/`session` targets.
- `REQ-002`: `recover_corruption()` MUST return a result whose `action` clearly communicates "preserved, operator intervention required" for Unknown outcomes.
- `REQ-003`: `recover_corruption()`'s docstring `action` value list MUST reflect the new outcome for Unknown.
- `REQ-004`: ADR-008's Known Deviations entry for this gap MUST be updated to reflect the fix.
- `REQ-005`: Tests MUST assert that an Unknown classification does not call `_restore_from_backup()` and leaves the target database unmodified.

## Design
Path A classification: affects ≤ 3 production files (recovery.py core logic + 2 test files), no public interface changes, no schema changes.

Design decision: Use a new `action` value `"unknown_preserved"` for the UNKNOWN case, following the pattern of `no_recovery_allowed` for workflow/eventbus. This makes the outcome self-describing rather than reusing `"error"` which conflates UNKNOWN with other error types.

The fix is minimal: insert an additional check between the existing early-return branch (line 204-214) and the "CORRUPTION or UNKNOWN" fallthrough (line 216):

```python
if condition == DbCondition.UNKNOWN:
    return RecoveryResult(
        success=False,
        action="unknown_preserved",
        detail=f"Unknown integrity failure: {detail}",
        dry_run=dry_run,
    )
```

This approach:
1. Does not modify `_classify_error()` (per issue constraint)
2. Does not change CORRUPTION branch behavior (per issue constraint)
3. Does not change workflow/eventbus no_recovery_allowed path (per issue constraint)
4. Preserves the target database by returning before `_restore_from_backup()` is reached
5. Clearly communicates the outcome via the `action` field
