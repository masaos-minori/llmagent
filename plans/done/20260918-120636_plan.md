## Goal
- Close the automated-test-coverage gap for ADR invariants tracked in `docs/adr-index.md`'s
  "ADR Invariant Verification Matrix", correcting the Matrix's Verification Status cells
  where adversarial verification found they are already stale (an automated test already
  exists but was never cited, or the underlying "violation" was already resolved
  elsewhere), and authoring new tests only where a genuine gap remains.

## Priority
Medium

## Background
The source Issue (`issues/20260914-112456_qa01_adr-invariant-automated-test-coverage.md`)
correctly identified that `docs/adr-index.md`'s Matrix and `tools/check_adr_invariant_matrix.py`
already exist and function correctly, and that its own scope is adding missing test
coverage, not building new infrastructure. However, this Plan's adversarial verification
(Step 2/3) found the Issue's list of "invariants lacking automated coverage" is
significantly stale: of the 12 invariants the Issue lists (INV-003, INV-005, INV-006,
INV-007, INV-008, INV-009, INV-010, INV-011, INV-012, INV-013, INV-014, INV-015), 6
already have a dedicated, passing automated test that the Matrix simply never cites
(INV-003, INV-006, INV-007, INV-008, INV-014), and a 6th (INV-015) is not actually a
violation at all — it was already investigated and resolved as a non-issue in
`docs/00_governance_03_issue-and-uncertainty-management.md`'s `CI-004` entry
(resolved 2026-09-14), yet `docs/adr-index.md`'s INV-015 row still reads "**Potentially
violated**" and cites a mismatched "Known Issue CI-003" (an unrelated config-reload
entry — the actually-relevant entry is `CI-004`). The Issue's Background also states the
Matrix documents "22 invariants (INV-001 through INV-022)"; the current Matrix has since
grown to INV-028, though this does not affect the 12-item list's individual accuracy.
Separately, `CI-004`'s own resolution note flags a narrower, still-open discrepancy
(ADR-010 Decision #9 vs. `call_rag_service()`'s `ValueError` handling) that was never
filed as its own tracked item — this Plan files it (see Unknowns) rather than leaving it
to be rediscovered later.

## Reason for change
An invariant confirmed only by code inspection has no regression protection. Separately,
a Matrix row that understates existing coverage ("no test yet" when a test already
exists) risks a future contributor duplicating test work, and a Matrix row that
misclassifies an already-resolved finding as "Potentially violated" (INV-015) risks
future effort being spent chasing a fix for a non-existent bug, or waiting indefinitely
on a dependency (`ragsvc01`) that will never produce the expected change.

## Design
This Plan makes no production-code change — it is scoped entirely to test authoring and
`docs/adr-index.md` citation corrections. Two design points from Step 3's inspection:

- `scripts/shared/mcp_config.py`'s `TransportType` `StrEnum` contains only `HTTP = "http"`
  — INV-006 ("no stdio transport usage") is structurally guaranteed at the config-parsing
  layer (any `transport="stdio"` value raises `ValueError` on enum coercion), which is
  exactly what `tests/shared/test_mcp_config.py::test_stdio_transport_rejected` already
  exercises. This is why REQ-002 is a citation fix, not new test authoring.
- INV-015's correction (REQ-006) does not touch `scripts/rag/pipeline_service.py` or
  `scripts/rag/http_augment.py` at all — `CI-004`'s resolution already established that
  the current 4xx-triggers-fallback code is ADR-010-compliant. The only remaining,
  distinct discrepancy (Decision #9 / parse-error handling) is deliberately routed to
  UNK-03 rather than folded into REQ-006, since fixing it would be a behavior change
  requiring its own Issue → Plan cycle, not something this test-coverage Plan should
  decide unilaterally.

  treated as final.

  only, may not actually exercise the real startup FATAL-path code in
  `scripts/agent/startup.py`, giving false confidence in the invariant. →
  **Mitigation**: prefer integration-style assertions against the real startup
  validation pipeline over mocked unit assertions, per `ADR-004`'s own "Startup
  Validation" Type classification for these two invariants (see UNK-02).
- **Risk**: Authoring a new test for one of the 6 genuine gaps (REQ-007 through
  REQ-012) could reveal that the invariant is actually violated in current code (as
  already happened once, historically, for INV-015 before its resolution) — carried
  forward from the source Issue's own `AI Implementation Instruction` constraint. →
  **Mitigation**: if a new test fails against current code, stop and report the finding
  as a separate Issue rather than weakening the test or the invariant's stated behavior
  to make it pass (see Scope Out-of-Scope and Acceptance criteria).
- **Risk**: A future, unrelated edit to `docs/adr-index.md` could silently reintroduce a
  stale Verification Status cell — the same failure mode this Plan corrects for INV-003/
  006/007/008/014/015. → **Mitigation**: `tools/check_adr_invariant_matrix.py` already
  verifies cited pytest node id existence going forward, but does not verify the cited
  test's assertion still matches the invariant text; no full mitigation exists for that
  narrower gap — out of scope for this Plan (a checker enhancement, if wanted, is a
  separate Issue).
