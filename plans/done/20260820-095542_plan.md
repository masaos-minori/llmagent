# Plan: Enforce URL-group atomicity and strict RAG database constraints

## Goal

Make RAG ingestion atomic per URL — a URL group either commits as one complete,
internally-consistent document with all its chunks, or fails entirely with no
partial write and no silently-substituted database default — by adding
cross-chunk group validation and duplicate-`chunk_index` detection before
embedding/mutation in `ingest_url_group()`, making `_insert_chunks_batch()`
propagate `sqlite3.IntegrityError` instead of swallowing it, and removing the
`DEFAULT` clauses for `documents.fetched_at`, `documents.chunking_strategy`,
`chunks.chunk_type`, and `chunks.source_file` in `scripts/db/schema_sql.py`.

## Assumptions

- **Sequencing**: this plan's `ingester.py`/`schema_sql.py` changes must land
  after `plans/20260820-094150_plan.md` (from
  `requires/done/20260819-144406_require.md`) and
  `plans/20260820-095054_plan.md` (from
  `requires/done/20260819-144649_require.md`). By the time this plan is
  implemented, `_normalize_chunk_index()` and `_validate_artifact()` (cited by
  line number in the source requirement, verified accurate against the
  current pre-dependency codebase) will already have been removed by
  `plans/20260820-094150_plan.md`, and `_read_chunk_json()` will route through
  its new strict `read_chunk_json()` reader. This plan's cross-chunk
  validation and duplicate-index check must be designed against that
  post-dependency shape of `ingester.py`, not literally re-add logic the
  dependency plan already removes. Falsifiable: re-check
  `scripts/rag/ingestion/ingester.py` for `_normalize_chunk_index` /
  `_validate_artifact` at implementation time; if either still exists, the
  dependency has not landed yet and this plan is blocked.
- **Contiguous-from-zero is enforced** (resolves the requirement's explicitly
  deferred decision). Reasoning: the requirement's own "Reason for change"
  states ingestion must be atomic — "either a complete ... document and all
  of its chunks are committed, or none of it is." A gap in `chunk_index`
  (e.g. 0, 1, 3) most plausibly indicates a missing/lost chunk file between
  splitting and ingestion — exactly the kind of silent incompleteness this
  requirement exists to catch. Enforcing contiguity-from-zero is therefore
  the choice consistent with the stated goal; a merely-unique-but-gapped set
  would defeat the atomicity intent. Falsifiable: if implementation-time
  discovery shows `chunk_splitter.py` legitimately produces sparse indices
  (e.g. filtered-out chunks that intentionally skip a number) this assumption
  is wrong and must be revisited — not observed in `chunk_splitter.py` during
  this analysis, but that file was not read in this cycle (see UNK-01).
- The four target columns' `CHECK` constraints (`chunk_type IN ('text',
  'code')`, `chunk_index >= 0`, `length(content) > 0`, `lang IN ('ja','en')`)
  already exist in `schema_sql.py` today and are unaffected by this plan —
  only `DEFAULT` clauses are removed, `NOT NULL`/`CHECK` stay as-is.

## Design

1. **Group validation, added to `ingest_url_group()` before
   `_get_or_create_document()`/`_prepare_chunks()`**: read every file in
   `chunk_files` (not just `chunk_files[0]`) via `_read_chunk_json()`. For
   each of `url`, `title`, `lang`, `fetched_at`, `etag`, `last_modified`,
   `source_file`, `chunking_strategy`, `schema_version`, `artifact_type`,
   `created_by`, compare the value from every file against `chunk_files[0]`'s
   value; any mismatch fails the whole group before any embedding call or DB
   read. Collect all `chunk_index` values from the same read pass; reject the
   group if any duplicate exists or if the sorted set is not exactly
   `range(len(chunk_files))` (contiguous-from-zero, per Assumptions).
2. **Failure routing**: on validation failure, call `_route_chunk_files([],
   [(p, "group_validation_failed: <detail>") for p in chunk_files])` (mirrors
   the existing failure path at line 264 today) so every file in the group —
   not just the mismatched one — is written to `failed/` with
   `_write_error_metadata()` explaining the group-level reason, and return
   `self._validation_failure_result(url, chunk_files)`.
3. **`_insert_chunks_batch()`**: delete the `except sqlite3.IntegrityError:
   pass` block so the exception propagates out of the function. Because
   `_commit_url_transaction()` already wraps this call inside
   `db.begin_immediate()` (a context manager), an uncaught exception
   propagating through it triggers the existing transaction-rollback behavior
   of that context manager (verify this rollback-on-exception behavior in
   `SQLiteHelper.begin_immediate()` at implementation time — not read in this
   cycle since it is outside this plan's target-file list, but is the
   mechanism this design step depends on).
4. **`_process_url_groups()`** already catches `sqlite3.OperationalError` per
   URL group and continues to the next group (line 733 today) — add
   `sqlite3.IntegrityError` to that exception tuple so a propagated integrity
   failure from one URL group does not abort the entire batch run; log via
   the existing `logger.exception(...)` call and mark that group's result as
   failed (0 success) rather than crashing `_process_url_groups()`.
5. **`schema_sql.py`**: remove the 4 `DEFAULT` clauses; no `CHECK`/`NOT NULL`
   change.
6. **`doc_upsert()`**: add `fetched_at: str` and `chunking_strategy: str`
   parameters (mandatory, no default, consistent with UNK-02's resolution);
   include both in the INSERT column list.
   **Internal contradiction found and corrected during implementation-procedure
   review**: this step originally said the `ON CONFLICT` branch "keeps its
   existing `fetched_at = strftime(...)` recompute-on-update behavior." That
   directly contradicts both (a) this plan's own UNK-02 resolution
   (caller-supplied `fetched_at`, no internal `datetime.now()`/`strftime`
   computation) and (b) sibling plan `plans/done/20260820-095054_plan.md`'s
   explicit decision for this same method
   (`ON CONFLICT ... DO UPDATE SET fetched_at = excluded.fetched_at` —
   see `implementations/20260823-200056_store_impl.py.md`), whose entire
   purpose is making `fetched_at` a single canonical value that propagates
   unchanged rather than being recomputed anywhere. **Corrected**: the
   `ON CONFLICT` branch sets `fetched_at = excluded.fetched_at` (caller-supplied
   value, overwritten like the other columns), not a `strftime(...)` recompute.
   `chunking_strategy = excluded.chunking_strategy` (overwrite with the
   caller-supplied value, like `title`/`lang`/`etag`/`last_modified`) —
   `chunking_strategy` is not a "first-seen" timestamp, so there is no reason
   to special-case it away from the other overwritten columns.
7. **DB recreation**: no migration; `rag.sqlite` is recreated by deleting the
   file and re-running `create_rag_schema()` (idempotent, `IF NOT EXISTS`
   DDL — confirmed by reading `scripts/db/create_schema.py`, which means an
   existing `rag.sqlite` file would NOT pick up the DDL change without
   deletion first).

## Risks

- **Risk**: `_normalize_chunk_index()`/`_validate_artifact()` may not yet be
  removed at the time this plan is implemented if the two dependency plans
  (`plans/20260820-094150_plan.md`, `plans/20260820-095054_plan.md`) have not
  landed, causing this plan's new validation logic to be built against a
  soon-to-change API surface (likelihood: medium — both are still open plans,
  not yet implemented) → **Mitigation**: Phase 3's first step is an explicit
  re-check for their absence before writing the group-validation code;
  treat a positive re-check (methods still present) as a hard stop, not a
  soft warning.
- **Risk**: `SQLiteHelper.begin_immediate()`'s rollback-on-exception behavior
  is assumed, not verified in this cycle (out of this plan's target-file
  list) — if it does not roll back automatically on an uncaught exception,
  simply removing the `except sqlite3.IntegrityError: pass` block would leave
  a partial commit instead of fixing it (likelihood: low — context-manager
  rollback-on-exception is the conventional pattern, but unverified)
  → **Mitigation**: Phase 4 must open and read `db/helper.py`'s
  `begin_immediate()` implementation before removing the swallow, and add the
  no-partial-commit test as a blocking check before merging this phase.
- **Risk**: `RagIngester._insert_chunk()` (singular) is left with the
  now-inconsistent `chunk_type: str = ""` / `source_file: str = ""` defaults
  since it is out-of-scope dead code; if a future change resurrects a caller
  for it without noticing the DDL no longer defaults these columns, it would
  fail immediately at runtime (likelihood: low — zero current callers)
  → **Mitigation**: none needed for this plan; flag for removal in a future
  dead-code pass (`vulture` once available) rather than fixing here, since
  fixing/removing it is outside this requirement's stated scope.
- **Risk**: `tests/db/test_db_maintenance.py` and `tests/db/test_db_store_impl.py`
  each maintain a private inline schema copy that has already drifted from
  `schema_sql.py` (missing `chunking_strategy` column, missing `CHECK`
  constraints, different NULL-ability) — updating only the 4 `DEFAULT`
  clauses in `schema_sql.py` without also correcting these fixtures would
  leave the acceptance criteria unverified by the test suite even though
  `schema_sql.py` itself is correct (likelihood: high — confirmed by direct
  read, not speculative) → **Mitigation**: Phases 1-2 explicitly include
  updating both fixtures; do not treat `schema_sql.py`'s change alone as
  sufficient for this requirement's acceptance criteria.
- **Risk**: `ingester.py` is the highest-churn, effectively single-author file
  in scope (5 commits/30d, ~98% one author across name-casing variants) —
  a mistake in the group-validation ordering (e.g. reading all group files
  before `_get_or_create_document()`) could silently reintroduce a partial-DB
  read before validation completes (likelihood: low-medium) → **Mitigation**:
  implement Phase 3 as its own independently-revertable commit, separate from
  Phase 4's `IntegrityError` change, with the "before any DB read" ordering
  covered by a dedicated mock-based test asserting `_get_or_create_document`/
  `_prepare_chunks` are not called when group validation fails.
