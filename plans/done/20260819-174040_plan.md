## Goal

Add two new cross-cutting documentation artifacts — a system security architecture
document and a high-risk MCP tool common policy document — that consolidate the
security posture already scattered across the Agent/MCP/RAG/operations doc sets, and
add cross-references from the existing scattered docs plus `docs/00_index.md` to these
new documents, without changing any code or any existing doc's technical content.

## Scope

**In-Scope:**
- Create `docs/00_security_01_architecture-and-trust-boundaries.md`: trust-boundary
  diagram (Agent -> LLM -> MCP -> target resource, plus RAG ingestion path), protected
  assets, threat model, per-externally-reachable-API authN/authZ requirements, secret
  lifecycle (provisioning/storage/rotation/revocation), log-redaction rules, audit
  retention, local-vs-production behavior, fail-open-vs-fail-closed behavior, and
  prompt-injection responsibility boundaries — synthesized from existing docs only.
- Create `docs/00_security_02_high-risk-tool-common-policy.md`: one common policy for
  file-write, file-delete, shell, git, github, cicd, and DB-maintenance-class MCP
  tools — allowed paths/repos, command allowlists, argument validation, path-traversal
  prevention, symlink-traversal prevention (generalized from the mdq-only doc pattern to
  all filesystem-touching high-risk tools), approval requirements mapped explicitly to
  risk tiers, audit fields, production restrictions, failure behavior — structured so
  each tool-specific doc can layer only its exceptions on top.
- Add cross-references (a short "See also: canonical cross-cutting doc" pointer, not
  inline duplication) from the 19 existing scattered docs listed in Affected Areas to
  the two new documents.
- Add new "タスク別ドキュメント参照" row(s) to `docs/00_index.md` routing security/
  approval/audit/high-risk-tool tasks to the two new documents.
- Add both new files to the `related:`/"Related Documents" lists of the files they
  cross-reference, consistent with existing doc-set convention.

**Out-of-Scope:**
- Any change to `scripts/` or other code — this is documentation-only.
- Any change to the technical content of the 19 existing scattered docs beyond adding a
  cross-reference pointer.
- Re-verifying or re-implementing `scripts/shared/security/` (already delivered by
  `plans/done/20260818-184804_plan.md` / `implementations/done/20260818-214148_unified_security.py.md`
  under the same source issue — that code-side deliverable is complete and out of scope here).
- Deleting, merging, or renumbering any existing doc file.
- Adding a diagram-rendering pipeline; the trust-boundary diagram is a plain Markdown
  code block (ASCII/mermaid-in-code-fence acceptable, no external tooling).

## Assumptions

- The new docs' numbering follows the `00_governance_NN_*` precedent (cross-cutting,
  numbered under `00_`) rather than the domain-scoped `0X_<domain>_NN_*` pattern, because
  the content spans Agent + MCP + RAG + operations and does not belong to one domain
  (falsifiable: confirmed by inspecting `docs/00_governance_01..10_*.md` — these already
  establish `00_` as the cross-cutting/meta prefix, distinct from `00_index.md` and
  `01_overview.md`).
- File-write and file-delete MCP tools already perform `Path.resolve()`-based path
  jailing at the code level (confirmed: `scripts/mcp_servers/file/write_service.py`,
  `delete_service.py`, `common.py`, `read_security.py` reference `resolve()`/
  `allowed_dirs`), but no existing doc names this behavior with "path-traversal" /
  "symlink-traversal" terminology outside the mdq docs — so the new common-policy doc is
  describing already-true code behavior in doc form, not inventing new behavior.
- `docs/04_mcp_00_document-guide.md`'s File Index table and "セキュリティモデル(5分割)"
  label are left unchanged in wording; only a pointer to the new architecture/policy
  docs is added, since the requirement's Implementation intent explicitly says "reference
  the new consolidated architecture doc" rather than rewrite the label.
- Git/GitHub/CI/CD/DB-maintenance tool docs (`04_mcp_04_05_git.md`,
  `04_mcp_04_01_web-search-file-read-github.md`, `04_mcp_04_03_rag-pipeline-and-cicd.md`)
  are not in the requirement's explicit Target files list and are therefore not required
  to receive a cross-reference in this plan, even though they are high-risk-tool docs —
  flagged as a Risk below rather than silently added to scope.

## Design

- **Numbering**: `00_security_01_architecture-and-trust-boundaries.md` and
  `00_security_02_high-risk-tool-common-policy.md`, mirroring the existing
  `00_governance_NN_*` cross-cutting prefix. Front matter (`title`, `category: security`,
  `tags`, `related`) follows the same YAML block convention seen in
  `04_mcp_05_01_access-control-and-allowlists.md` and `00_governance_01_documentation-governance.md`.
- **`00_security_01` structure** (sections, each synthesizing named source docs, no new
  claims):
  1. Purpose / how to use this doc
  2. Trust-boundary diagram: `Agent -> LLM -> MCP -> target resource` plus the RAG
     ingestion path as a second boundary-crossing arrow into the same diagram (plain
     fenced-code ASCII diagram — no external rendering dependency)
  3. Protected assets (filesystem under `allowed_dirs`, git repos, GitHub repos, CI/CD
     workflows, DB files, audit logs, secrets)
  4. Threat model (untrusted LLM output, untrusted RAG-ingested content, compromised
     tool arguments, path/symlink escape, command-allowlist bypass, unauthorized
     repo/workflow access, execution without approval)
  5. Per-externally-reachable-API authN/authZ table (one row per MCP server: file-read/
     write/delete, shell, git, github, cicd, mdq, rag-pipeline — sourced from
     `04_mcp_05_01`/`04_mcp_05_02`)
  6. Secret lifecycle (provisioning/storage/rotation/revocation) — sourced from
     `04_mcp_06_17_local-to-production-auth-migration.md`
  7. Log redaction rules — sourced from `04_mcp_02_03_audit-logging-and-errors.md`
  8. Audit retention — sourced from `04_mcp_06_07_reading-audit-logs.md` and
     `05_agent_10_02_operations-and-observability-audit-and-otel.md`
  9. Local-vs-production behavior — sourced from `04_mcp_06_16_pre-production-fail-open-checklist.md`
     and `04_mcp_05_03_fail-open-fail-closed-and-risk-tiers.md` §起動時のAudit
  10. Fail-open-vs-fail-closed behavior — table reproduced/linked from `04_mcp_05_03`
      §Fail-Open 対 Fail-Closed の要約, cross-referenced (not duplicated verbatim) with
      `05_failure_modes_and_operational_readiness.md`
  11. Prompt-injection responsibility boundaries — sourced from `03_rag_03_05` (`sanitize_document()`)
      and `03_rag_04_02` (`was_sanitized`, `patterns_detected`), stating which layer
      (RAG ingestion vs Agent vs MCP) is responsible at each boundary crossing
- **`00_security_02` structure**:
  1. Purpose / scope (which tools this policy governs: file-write, file-delete, shell,
     git, github, cicd, DB maintenance — mdq included as the reference implementation
     of traversal prevention)
  2. Allowed paths/repos — common shape (`allowed_dirs`/`allowed_repo_paths`/`allowed_repos`,
     all fail-closed on empty) — sourced from `04_mcp_05_01`
  3. Command allowlists — sourced from `04_mcp_05_01` §コマンドAllowlist
  4. Argument validation — pointer to `agent/tool_arg_validator.py::validate_tool_arguments()`
     per `05_agent_06_01`
  5. Path-traversal prevention (common statement: all filesystem-touching tools resolve
     paths via `Path.resolve()` before comparison against the allowlist root) —
     generalizes the language currently found only in `04_mcp_04_04_mdq.md` /
     `04_mcp_05_05_mdq-enforcement-and-lockdown.md`
  6. Symlink-traversal prevention (same generalization — `Path.resolve()` follows and
     normalizes symlinks before the allowlist check)
  7. Approval requirements mapped explicitly to risk tiers — reproduces the
     `READ_ONLY` / `WRITE_SAFE` / `WRITE_DANGEROUS` / `ADMIN` table from
     `04_mcp_05_03` §リスクティア分類 as the authoritative approval-to-tier mapping,
     cross-linked with `05_agent_06_01`/`05_agent_06_02` for the approval-execution flow
  8. Audit fields — sourced from `04_mcp_02_03`
  9. Production restrictions — sourced from `04_mcp_06_16`
  10. Failure behavior — fail-closed-by-default statement, cross-linked to
      `00_security_01` §Fail-open-vs-fail-closed
  11. Tool-specific exceptions — explicit statement that exceptions live in each tool's
      own doc (e.g. github's `protected_branches`/`path_denylist` are fail-open by
      design, documented in `04_mcp_05_01`), not merged into this policy body, per the
      requirement's Implementation intent #2 and Acceptance criteria "documented
      separately from the common policy body, with clear references"
- **Cross-reference pattern**: each of the 19 existing docs gets one short addition —
  either a new bullet under an existing "Related Documents" section, or (where no such
  section fits contextually, e.g. mid-body table sections) a one-line "See also:
  `00_security_0X_...md` for the cross-cutting canonical policy" note placed adjacent to
  the most relevant existing heading. No existing sentence is deleted or reworded.
- **`docs/00_index.md` change**: add rows to "タスク別ドキュメント参照" §MCP and a new
  row under a security-focused scope, e.g.:
  `| System security architecture / trust boundaries / threat model | `00_security_01_architecture-and-trust-boundaries.md` |`
  `| High-risk MCP tool policy (path/repo allowlists, traversal prevention, approval-to-risk-tier mapping) | `00_security_02_high-risk-tool-common-policy.md` |`
  placed near the existing "MCP security model (allowlist / denylist / fail-closed)" row
  (line 113) without altering that row.

## Risks

- **Risk**: The two new consolidated docs could drift from the underlying 19 detailed
  docs over time if a future change updates one side only (Likelihood: medium) →
  **Mitigation**: each new doc's front matter `related:` list and body cross-references
  point bidirectionally, and `uv run check-mcp-docs` catches broken links on future CI
  runs; no automated content-drift check exists beyond that, so this is accepted
  residual risk, not eliminated.
- **Risk**: git/github/cicd/db-maintenance-specific docs (`04_mcp_04_05_git.md`,
  `04_mcp_04_01_web-search-file-read-github.md`, `04_mcp_04_03_rag-pipeline-and-cicd.md`)
  are high-risk-tool docs but are absent from the requirement's Target files list, so
  they will not receive a cross-reference in this cycle even though the new
  `00_security_02` doc's scope statement names git/github/cicd as governed tools
  (Likelihood: high — acceptance criterion "each existing tool-specific doc... can
  reference it" is not fully met for these three files) → **Mitigation**: file a
  follow-up issue recommending a narrow follow-on requirement to add the same
  cross-reference to these three docs; do not silently expand this plan's scope beyond
  the requirement's explicit Target files list.
- **Risk**: The new `00_security_02` doc's "path-traversal/symlink-traversal prevention
  is generalized to file-write/file-delete/shell" claim is a documentation synthesis of
  existing code behavior (`Path.resolve()` usage confirmed in
  `scripts/mcp_servers/file/write_service.py`, `delete_service.py`, `common.py`), but
  this plan did not exhaustively read every line of those service files or the shell-mcp
  server's cwd-jailing code (Likelihood: low-medium — the requirement's own Tests
  section flags this as needing "a follow-on review/verification pass") →
  **Mitigation**: Phase 3's verification step explicitly re-checks this against the
  `rg` evidence above before publishing; if a discrepancy is found, correct the new doc
  text (not the code) since this phase is documentation-only, and file a code-review
  issue if the actual enforcement is found to be weaker than assumed.
