## Goal
- Make the live Git MCP dispatch path (`POST /v1/call_tool`) actually enforce
  `allowed_repo_paths` containment (it currently does not check it at all), reject
  sibling/symlink-escaped/invalid paths before creating a repository snapshot, and
  make rejection-path audit logging safe against a secondary exception.

## Priority
High

## Scope
- **In-Scope**: adding path-component-aware `allowed_repo_paths` containment
  enforcement to the live dispatch path; symlink-escape and invalid-path rejection
  before `RepositoryState.snapshot()` is called; fixing the rejection-path audit call
  that currently snapshots an unvalidated path; redacted vs. canonical audit target
  fields; coordinating with `gitdispatch`'s Plan so its proposed routing through
  `GitService` does not make `GitService._validate_repo()`'s vulnerable
  string-prefix check live.
- **Out-of-Scope**: protected-branch/ref authorization content (`gitauth`); the
  write-protection pipeline's stage ordering (`gitpipeline`); remote authorization/
  concurrency (`gitremote`); dispatch unification itself (`gitdispatch`, already
  Frozen as `plans/20260904-191458_plan.md`) — this Plan only ensures that Plan's
  eventual implementation does not reintroduce the string-prefix vulnerability this
  Plan fixes.

## Background
`issues/done/20260816-160000_git_security_path_is_relative_to.md` was expected to
have replaced raw string-prefix path comparison with `Path.is_relative_to()`. This
Plan's Step 3 investigation (per the issue's own AI Implementation Instruction: `rg
"is_relative_to|snapshot\("`) found **zero** matches for `is_relative_to` anywhere
under `scripts/mcp_servers/git/` — that prior fix is not present in the current
codebase in the form the issue describes. Direct inspection of the actual containment
logic found:
- **Live path** (`git_server.py`'s `POST /v1/call_tool`, confirmed this session by
  `gitauth`'s Plan to be the only route FastAPI serves): calls
  `_resolve_repo_path(repo_path)` (`git_security.py:14-27`) — a module-level function
  that only canonicalizes the path (`Path(repo_path).resolve()`) and checks it is
  non-empty and resolvable. **It never compares the resolved path against
  `_cfg.allowed_repo_paths` at all.** `GitSecurityGuards._check_repo_path()`
  (`git_security.py:45-57`) likewise only calls `_resolve_repo_path()` and returns
  `True` unconditionally on success — its own docstring says "Allowlist check is
  delegated to subclasses," but the live path never reaches a subclass that performs
  one.
- **`GitService`** (dead code per `gitauth`'s Plan, but relevant to `gitdispatch`'s
  Plan — see Design): contains **two different** containment checks. `_validate_repo()`
  (`git_service.py:108-120`, the one actually called by `_run_tool()`) uses
  `req_repo_path.startswith(p)` — raw string-prefix matching, vulnerable to a sibling
  path like `/allowed-repo-evil` matching an allowed `/allowed-repo` root, and
  performs no path canonicalization at all before comparing. `_check_repo_path()`
  (`git_service.py:140-159`, explicitly commented "Backward-compatible guards (used
  by tests)") implements the *correct* path-component-aware check via
  `PurePosixPath(normalized).relative_to(PurePosixPath(allowed))`, but is not called
  by any live or dead-code dispatch path — it exists only for test compatibility.
- The rejection-path audit call in `git_server.py` (`call_tool`, line 169) calls
  `RepositoryState.snapshot(repo_path)` — the raw, unresolved input — inside the
  `_audit_log(...)` call built for the case where `_resolve_repo_path()` already
  failed. `RepositoryState.snapshot()` opens a `git.Repo` unconditionally
  (`repository_state.py:88`), which raises `git.InvalidGitRepositoryError`/
  `git.NoSuchPathError` for a non-existent or non-repository path — exactly the case
  this rejection branch exists to handle, confirming the issue's concern structurally.

## Problem
The live dispatch path enforces no repository-path allowlist whatsoever — worse than
the issue's own stated concern (raw string-prefix matching being spoofable by a
sibling path). Any resolvable filesystem path reaching `POST /v1/call_tool` proceeds
to `RepositoryState.snapshot()` and full tool execution regardless of
`allowed_repo_paths`'s configured value. Separately, the rejection-path audit call
can itself raise a secondary exception by attempting to open a `git.Repo` at a path
already known to have failed resolution, which would surface as an unhandled 500
response instead of the intended rejection message.

## Reason for Change
A path-containment gap on the only route that actually serves requests, and a
rejection-path exception that can turn a security control into undefined behavior at
exactly the moment it should fail closed, are both live, exploitable gaps — not
theoretical ones.

## Implementation intent
Add path-component-aware `allowed_repo_paths` containment enforcement
(`PurePosixPath.relative_to()`-style, reusing the logic `GitService._check_repo_path()`
already has correct but unreachable) to the live dispatch path in `git_security.py`,
called from `git_server.py` before any `RepositoryState.snapshot()`. Reject missing,
inaccessible, non-repository, symlink-escaped, and unauthorized paths at that single
point. Fix the rejection-path audit call to never snapshot an unresolved/unvalidated
path. Record the raw requested value only in a redacted audit field; use the
canonical resolved path as the audit target only once containment succeeds. Fix
`GitService._validate_repo()`'s vulnerable `startswith()` check to use the same
correct containment logic, so `gitdispatch`'s Plan (which proposes routing live
traffic through `GitService.get_dispatch_table()`) does not reintroduce this
vulnerability once it lands.

## Requirements
- `REQ-001`: Add path-component-aware `allowed_repo_paths` containment checking to
  the live dispatch path — currently entirely absent, not merely string-prefix-based.
- `REQ-002`: Use `PurePosixPath.relative_to()`-style component-aware containment
  (reusing `GitService._check_repo_path()`'s existing correct logic) rather than raw
  string-prefix matching, rejecting a sibling path like `/allowed-repo-evil` for an
  `/allowed-repo` root.
- `REQ-003`: Reject missing, inaccessible, non-repository, symlink-escaped, and
  unauthorized paths before any `RepositoryState.snapshot()` call.
- `REQ-004`: Fix `call_tool`'s rejection-path audit call
  (`_audit_log(..., pre_condition=_serialize_state(RepositoryState.snapshot(repo_path)), ...)`)
  so it does not attempt to snapshot a path that has already failed
  resolution/authorization — use `None`/an empty pre-condition, or a
  snapshot-independent description, for this branch.
- `REQ-005`: Record the untrusted requested value only in a safely redacted audit
  field; use the canonical resolved path as the authoritative audit `target` only
  after successful containment authorization.
- `REQ-006`: Ensure an exception during audit-log construction/emission cannot
  replace or mask the original validation response — wrap the audit call so its
  failure is logged but does not propagate past the already-determined rejection or
  success response.
- `REQ-007`: Fix `GitService._validate_repo()`'s `req_repo_path.startswith(p)` check
  to use the same component-aware containment as REQ-002, so `gitdispatch`'s Plan
  (`plans/20260904-191458_plan.md`, already Frozen, proposing to route live traffic
  through `GitService.get_dispatch_table()`/`_run_tool()`) does not make this
  vulnerable check live once implemented.

## Design
This Plan's central finding — the live dispatch path enforces no repository-path
allowlist at all — is more severe than the issue's own stated concern (raw
string-prefix matching). The issue's Background cites a prior fix
(`is_relative_to()` adoption) that this Plan's investigation could not find any trace
of in current code; rather than assume that issue's premise, this Plan treats the
current, directly-observed state as ground truth (per `AGENTS.md` Policy: base
answers only on the given context, not on prior issue text once evidence
contradicts it) and implements containment fresh, reusing
`GitService._check_repo_path()`'s already-correct (if unreachable) logic as the
template.

REQ-007 is included because of a specific interaction with `gitdispatch`'s Plan
(already Frozen, `plans/20260904-191458_plan.md`): that Plan proposes routing live
`POST /v1/call_tool` traffic through `GitService.get_dispatch_table()`, which calls
`_run_tool()`, which calls `_validate_repo()` — the method with the vulnerable
`startswith()` check. Without REQ-007, implementing `gitdispatch`'s Plan after this
one would silently reintroduce the sibling-path vulnerability this Plan fixes on the
current live path, just relocated to a different (soon-to-be-live) code path. Fixing
both call sites now, regardless of implementation order between this Plan and
`gitdispatch`, closes that gap either way.
