## Background
`tools/check_docs_content_policy.py` already exists, is already registered in
`tools/TOOL_DESCRIPTIONS.md`, and already implements 11 check functions covering
most of `skills/DESIGN.md`'s "Docs content policy — remove" categories. Running it
(`uv run python tools/check_docs_content_policy.py`) currently reports 30 warnings
across the `docs/` tree — confirmed live and working — but it does not flag
`docs/03_rag_02_03_ingestion_pipeline-chunksplitter.md` at all, despite that file's
confirmed TypedDict field table, CLI argument table, error-handling table, and full
JSON payload example (companion Issue `docref01`). Reading the tool's source
confirms why: `check_index_table`/`check_field_type_table`'s header regexes do not
match a `| TypedDict | Purpose |` header; `check_cli_command_enumeration` only
inspects fenced `bash` blocks, not Markdown tables, so it never sees
`| Argument | Description | Default |`; no existing function inspects an
Error/Exception-heading table; and no existing function flags a full JSON payload
example at all. Separately, `routing.md`'s "When to run which tool" table
(confirmed via direct inspection, lines 82-84) lists `check_docs_quality.py`,
`check_docs_structure.py`, and `check_docs_consistency.py` for a `docs/*.md` edit,
but has no row for `check_docs_content_policy.py` at all.

## Problem
Two independent, compounding gaps mean the implementation-detail content this Plan
and the companion Issue care about is neither reliably detected nor discoverable as a
check to run: (1) the existing detector's patterns miss four content shapes that
occur in practice, and (2) the checks that do exist are not listed in the routing
table an implementer is expected to consult before finishing a `docs/*.md` edit.

## Reason for change
Without the four new detectors, `check_docs_content_policy.py` gives a false sense of
coverage — it reports 30 findings but silently misses the exact file the companion
Issue confirmed by hand. Without the `routing.md` registration, an implementer
following the routing table's own stated process has no way to know this tool exists
at all.

## Implementation intent
Extend `tools/check_docs_content_policy.py` in place, matching its existing style
exactly: one `check_*(files: list[DocFile]) -> list[Issue]` function per category,
guarded-block awareness via the existing `_is_guard_start`/`_is_guard_end` helpers, a
conservative minimum-rows/lines threshold (mirroring `_MIN_MECHANICAL_TABLE_ROWS`/
`_MIN_CLI_BLOCKS`) so a short illustrative example is not flagged, and an `Issue`
message citing the relevant `skills/DESIGN.md` category. Wire all four new functions
into `main()` alongside the existing 11. Add a corresponding positive-detection and
negative-non-detection test pair for each new function in
`tests/tools/test_check_docs_content_policy.py`, matching that file's existing
one-test-per-category pattern (a `_doc()`-built fixture, an assertion on
`len(issues)` and message substring). Correct `tools/TOOL_DESCRIPTIONS.md`'s two
existing entries, which currently describe only skills/DESIGN.md's original five
named categories — already stale relative to the module's actual 11-function (soon
15-function) check set. Add the missing `routing.md` row using the same "Situation" /
"Run" / "Notes" shape as the adjacent `check_docs_quality.py`/`check_docs_structure.py`
rows.

## Design
This is a Path A (small task) Plan: 4 target files, no public/runtime-facing
interface change, no database schema change — so architecture/dependency/historical/
operational analysis (Path B) is skipped per `skills/issue-to-plan/SKILL.md`
Routing. Direct verification (Step 3) confirmed: `tools/check_docs_content_policy.py`
has exactly one importer (`tests/tools/test_check_docs_content_policy.py`) and one
internal dependency (`tools/_docs_consistency_lib.py` for `Issue`/`report_and_exit`),
so the new functions carry no wider blast radius than the file itself and its
existing test file. The four new functions are designed as pure additions —
independent `check_*` functions appended to the module and wired into `main()` — with
no change to any of the 11 existing functions' logic, matching the existing module's
established one-function-per-category shape rather than introducing a different
internal architecture (e.g. a single generic pattern-matching engine), consistent
with `skills/DESIGN.md` File Split Rule's "shared normalization" principle (this
module is already the single canonical home for this policy's detection logic; a new
file would fragment it).

  flagging legitimate short illustrative examples elsewhere in `docs/`. →
  **Mitigation**: same full-tree smoke-test review as above; err toward a higher
  threshold initially, consistent with the existing module's conservative bias.
