# Plan: Audit BLE/PLC0415 noqa suppressions and add automated suppression-justification enforcement

## Goal
Resolve, with verified ruff evidence, whether `# noqa: BLE001` / `# noqa: PLC0415` suppressions
across the repo suppress anything real under the project's current ruff `select` list; bring the
`select` list and/or noqa codes into a documented, consistent state; and add an automated
pre-commit check that fails when a `# noqa`, `# type: ignore`, or `# nosec` comment lacks the
em-dash inline justification required by `rules/coding.md` §Suppression governance.

## Scope

### In-Scope
- Add `BLE001` to `pyproject.toml`'s `[tool.ruff.lint]` `select` list (bounded blast radius,
  verified below).
- Explicitly document, in `pyproject.toml` and `rules/coding.md`, the decision to **not** add
  `PLC0415`/`PLC` to `select` (disproportionate blast radius, verified below) as an intentional,
  evidence-based exception rather than an oversight.
- Triage the ~39 net-new `BLE001` findings surfaced once `BLE001` is selected (narrow the except
  clause or add a justified `# noqa: BLE001 — <reason>`).
- Add a new `tools/check_suppression_justification.py` check (module pattern matching existing
  `tools/check_no_compat.py`) that fails when a `# noqa`, `# type: ignore`, or `# nosec` comment
  lacks a rule/error code and an em-dash-delimited justification, with a baseline allowlist for
  today's pre-existing non-compliant lines (matching `tools/check_no_compat.py`'s
  `DEFAULT_ALLOWLIST` pattern) so only new/modified violations block a commit.
- Add a matching test file `tests/tools/test_check_suppression_justification.py`.
- Wire the new check into `.pre-commit-config.yaml` as a `local` hook, following the
  `no-compat-stubs` entry pattern.
- Fix the asymmetry in `rules/coding.md` §Suppression governance's own documented `rg` examples
  (today only the `nosec` example checks for the em-dash; the `noqa` and `type: ignore` examples
  only check for a rule/error code) so the documented convention and the automated check agree.
- Update `rules/coding.md` §Suppression governance to reference the new automated check in place
  of "run before every commit."

### Out-of-Scope
- Adding `PLC0415`/`PLC` (or any other new rule family beyond `BLE001`) to `select` — the measured
  blast radius (~1193 net-new findings) makes this a separate, much larger effort; not part of
  this plan.
- Bulk-remediating the ~330 pre-existing suppression comments that already lack an em-dash
  justification (77 `BLE001`/`PLC0415` noqa + 244 `type: ignore` + some `nosec`) — these are
  grandfathered via the new check's baseline allowlist, not individually fixed here.
- Enabling `RUF100` (`unused-noqa`) or any other `RUF` rule in `select` — discovered as a candidate
  during this audit (see Assumptions), but its own blast radius (167 findings across multiple rule
  codes, not just `BLE001`/`PLC0415`) makes it a separate decision.
- Any change to `tox.ini`'s `lint` environment scope (`scripts/` only) — not required by the chosen
  design (the new check is wired via pre-commit, not tox).
- Any change to `scripts/` runtime behavior beyond the `BLE001` exception-handling triage in
  Phase 2.
- `docs/*.md` updates (out of scope for this document-only phase per workflow constraints).

## Assumptions
1. Ruff (`uv run ruff`, resolved version 0.15.16 via `uv run ruff --version`) is the only lint tool
   in the toolchain that can act on `BLE001`/`PLC0415` — confirmed: `tox.ini`'s `lint` env runs only
   `ruff format --check` and `ruff check`; no pylint/flake8 is configured anywhere.
2. `BLE001` is the only rule in ruff's `BLE` (flake8-blind-except) category — confirmed by
   measurement: `--select BLE` and `--select BLE001` both report 62 findings against
   `scripts/ tests/`, so selecting the family vs. the exact code is equivalent; the plan selects
   the exact code `"BLE001"` for minimal, explicit footprint.
3. `PLC0415` findings dominate the `PLC` family in this codebase — confirmed by measurement:
   `--select PLC` (whole family) reports 1194 findings vs. 1193 implied for `PLC0415` alone
   (1255 combined `BLE,PLC0415` minus 62 `BLE`) — i.e., other `PLC` rules contribute negligibly.
4. `tools/` modules (dev-tooling / CI checks) are not deploy-impacted — confirmed:
   `grep -n "tools/" deploy/deploy.sh` returns no matches, and existing `tools/check_*.py` modules
   (e.g. `check_no_compat.py`, `check_tool_descriptions_sync.py`) are wired only via
   `.pre-commit-config.yaml` / `pyproject.toml [project.scripts]`, never via `deploy/deploy.sh`.
5. A diff-scoped (changed-lines-only) enforcement approach was considered as an alternative to a
   baseline allowlist, but the allowlist approach is preferred because it exactly matches an
   existing, working precedent in this codebase (`tools/check_no_compat.py`'s
   `DEFAULT_ALLOWLIST`/`--allowlist`), whereas no diff-scoped pre-commit hook precedent exists here
   (`diff-cover` is a separate, coverage-specific tool run manually via `tox`/CI, not pre-commit).

## Risks & Mitigations

- **Risk**: Enabling `PLC0415` (or the full `PLC` family) would surface ~1193 new lint findings
  across the codebase, far beyond a reviewable single-plan increment.
  → **Mitigation**: explicitly do not enable `PLC0415`/`PLC` in this plan; document the decision
  and its evidence in `pyproject.toml` and `rules/coding.md` as an intentional exception. Any future
  desire to enable it should be filed as its own dedicated, large-scope requirement.

- **Risk**: Enabling `BLE001` surfaces ~39 net-new "blind except" call sites requiring individual
  triage, some in high-complexity/high-churn files (`scripts/agent/startup.py`: radon grade F,
  53-commit history).
  → **Mitigation**: triage in a dedicated Phase 2 step with per-site review (narrow the exception
  or add a specific justified noqa); do not bulk-suppress with a blanket noqa; leave
  `startup.py`'s 5 pre-existing, already-justified `BLE001` noqa comments untouched (already
  reviewed in the prior cycle).

- **Risk**: An unconditional, repo-wide enforcement hook would fail immediately on ≥330
  pre-existing non-compliant suppression comments (77 noqa + 244 type:ignore + up to 14 nosec),
  blocking all future commits until a large historical remediation is done first.
  → **Mitigation**: ship the new hook with a baseline allowlist (mirroring
  `tools/check_no_compat.py`'s `DEFAULT_ALLOWLIST`/`--allowlist` pattern) so only new or modified
  unjustified suppressions fail the check; full historical remediation of the allowlisted lines is
  an optional, separate follow-up, not a blocker for enabling the hook now.

- **Risk**: `rules/coding.md`'s own documented `rg` examples for `noqa`/`type: ignore` do not
  actually test for the em-dash (only the `nosec` example does) — building the new automated check
  to match those examples verbatim would silently perpetuate the same gap the requirement is
  trying to close.
  → **Mitigation**: design `tools/check_suppression_justification.py` to require the em-dash
  uniformly across all three suppression kinds, and correct `rules/coding.md`'s `rg` examples to
  match, in the same Phase 1 commit.

- **Risk**: The new `tools/check_suppression_justification.py` itself could introduce false
  positives on legitimate non-ASCII dash usage or multi-line noqa comments (e.g. the parenthesized
  multi-line import style seen in `scripts/agent/commands/cmd_config.py`), causing hook failures
  unrelated to actual missing justifications.
  → **Mitigation**: the accompanying test file (`tests/tools/test_check_suppression_justification.py`)
  must include a case exercising the multi-line/parenthesized-import noqa style already present in
  the codebase (e.g. `scripts/agent/commands/cmd_config.py` lines 43-45) before the hook is wired
  into `.pre-commit-config.yaml`.

All risks above have mitigations stated directly in this plan; no `issues/*_risks.md` file is
filed (Step 6 skipped per workflow instructions).
