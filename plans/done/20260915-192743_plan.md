## Goal
Add a new, narrowly-scoped lint tool (`tools/check_adr_structure.py`) that
mechanically detects two ADR structural drift patterns this session's manual
review found — a missing `## Known Deviations` heading, and an
`## Implementation Notes` file/symbol list that has silently diverged from
`### Implementation References` — register it in the same pre-commit pipeline
as its sibling `check_adr_*.py` tools, and document it per this project's
existing conventions, without attempting to automate the four-way semantic
classification this session's review actually required human judgment for.

## Priority
Medium

## Scope
- **In-Scope**:
  - A new script, `tools/check_adr_structure.py` (a new sibling to
    `check_adr_reference.py`/`check_adr_invariant_matrix.py`, not an extension
    of either — see Design for why).
  - Check (a): every `docs/adr/*.md` file contains a `## Known Deviations`
    heading (ERROR severity, matching this file's sibling checks'
    established severity for a structural absence).
  - Check (b): for each ADR, extract file/symbol references (backtick-quoted
    `scripts/...`/`tests/...` paths) under `## Implementation Notes` and under
    `### Implementation References`; flag (WARNING severity, per the source
    issue's own explicit wording) any reference present in Notes but absent
    from References — skip an ADR entirely for this check if Notes contains no
    such backtick-quoted path at all (the now-common post-cleanup state, not a
    violation).
  - A new test file, `tests/tools/test_check_adr_structure.py`, following
    `tests/tools/test_check_adr_reference.py`'s direct-function-call pattern.
  - Register the new hook in `.pre-commit-config.yaml`, matching the existing
    `adr-invariant-matrix`/`adr-reference-scoped` entries' format.
  - Document the new check in `docs/00_governance_04_documentation-checks.md`
    (a new numbered entry under `## Automated Checks`) and
    `tools/TOOL_DESCRIPTIONS.md` (both its summary table and its detailed
    table, matching sibling `check_adr_*.py` entries).
  - Fix `docs/adr/ADR-002-config-isolation.md`'s own missing `## Known
    Deviations` heading — confirmed during this Plan's evidence-gathering to
    be the one ADR that would immediately fail the new check (a X issue),
    which would make the new pre-commit hook block every future commit
    repository-wide starting from the moment it is enabled. This is a
    structural fix (add the standard heading with the project's own
    zero-deviations placeholder text, per `ADR-003`'s exact precedent), not a
    semantic-classification judgment call — squarely still in this issue's own
    stated scope, not the excluded four-way classification.
- **Out-of-Scope**:
  - Automating the four-way semantic classification (delete / promote /
    Known Issue / Needs Confirmation) — explicitly ruled out by the source
    issue's own Constraint.
  - Fixing `tools/check_docs_structure.py`'s `ModuleNotFoundError: No module
    named 'yaml'` — the source issue's own text already marked this as
    unrelated and out of scope regardless. This Plan's own evidence-gathering
    found the underlying condition is *not* actually resolved at the
    dependency-declaration level: `pyyaml` is present in the current dev venv
    only as a *transitive* dependency of `bandit`/`pre-commit`/`schemathesis`
    (confirmed via `uv pip show pyyaml` → `Required-by: bandit, pre-commit,
    schemathesis`; no direct `pyyaml` entry exists in `pyproject.toml`), not
    as a direct project dependency backing `check_docs_structure.py`'s own
    `import yaml`. The error does not reproduce *today, in this environment*,
    but a leaner environment (e.g. one installing only this project's own
    declared dependencies) could still hit it. Left out of scope per the
    source issue's own instruction — recorded accurately here, not silently
    reported as "resolved."
  - Any ADR content fix beyond `ADR-002`'s missing heading (see Reason for
    change below for why that one exception is made) — all other structural
    findings from this session's review (ADR-004's Known Deviations, the
    13-ADR list-duplication cleanup, ADR-006/007's prose reclassification)
    were already implemented by separate, already-completed Plans earlier this
    session.
  - Restructuring `docs/00_governance_04_documentation-checks.md`'s existing,
    already-inconsistent entry numbering (entries 9–14 live under `## Manual
    Checks` while numbered lower than entry 15, an `## Automated Checks`
    entry) — a pre-existing quirk, not introduced or required to be fixed
    here; the new entry is simply appended as the next available number.

## Background
This issue follows the same Implementation-Notes classification review that
produced the ADR-004, 13-ADR file-list, ADR-006, and ADR-007 Plans earlier this
session — all four are now implemented and committed. This issue is the
review's own meta-conclusion: which parts of that manual audit are worth
automating going forward, and which are not.

## Problem
This session's manual audit found two ADR structural drift patterns with no
existing detector:
1. `docs/adr/ADR-004-*.md` was missing `## Known Deviations` — already fixed
   by `plans/done/20260915-145322_plan.md`. Confirmed during this Plan's own
   evidence-gathering (`grep -c "^## Known Deviations" docs/adr/*.md`) that
   ADR-004 now has exactly one occurrence — but **`docs/adr/ADR-002-config-isolation.md`
   has zero** (its `### CI-001` Known Issue entry lives directly inside
   `## Implementation Notes` with no separate heading — already noted as
   `UNK-01` in `plans/done/20260915-154020_plan.md` and as `UNK-02` in
   `plans/done/20260915-190322_plan.md`, but never itself fixed). The source
   issue's own Acceptance Criteria #1 ("flags ADR-004's missing heading")
   is now stale — the tool, once built, would instead flag ADR-002.
2. All 13 ADRs' Implementation Notes file/class/config/test list duplicated
   their own Implementation References — already fixed by
   `plans/done/20260915-154020_plan.md`. Confirmed during this Plan's
   evidence-gathering that this pattern no longer exists in the current tree
   (every affected ADR's Notes section now either has no backtick-quoted
   path at all, or only a short pointer). Check (b), once built, would
   currently find zero drift — its value is prospective (catching a *future*
   re-introduction of this pattern after a rename), not retrospective.
3. `tools/check_docs_structure.py`'s previously-reported `ModuleNotFoundError:
   No module named 'yaml'` does not reproduce in the current dev environment
   (confirmed by running it directly), but this is fragile, not fixed:
   `pyyaml` is present only as a *transitive* dependency of
   `bandit`/`pre-commit`/`schemathesis` (confirmed via `uv pip show pyyaml`),
   with no direct entry in `pyproject.toml` backing `check_docs_structure.py`'s
   own `import yaml`. Unrelated to this issue's own scope either way, per the
   source issue's own text.

## Reason for change
The source issue's own reasoning stands independent of whether the *specific*
instances it found are still present: "a future ADR author can easily forget
the Known Deviations heading, or let an Implementation Notes list drift out of
sync... with nothing currently flagging either." This Plan's own evidence
confirms check (a) still has exactly one live violation today (`ADR-002`) and
check (b) has zero — meaning the tool's prospective, drift-prevention value is
the actual justification now, not a backlog of findings to surface. `ADR-002`'s
gap is fixed as part of this same Plan specifically so that landing the new
pre-commit hook does not immediately block every future commit on a pre-existing,
unrelated condition — the same pattern this repository already uses for
`check_compat_shims.py`'s `--check-removed-names` flag (kept out of the default
blocking invocation until its one known finding was resolved), applied here by
fixing the finding instead of deferring the hook.

## Implementation intent
Add `tools/check_adr_structure.py` as a new sibling script (not an extension of
`check_adr_reference.py`, whose own docstring explicitly frames itself as
scoped to "matrix-named files only" — a narrower mandate than "every ADR file,"
which is what checks (a) and (b) both require). Reuse
`tools/_docs_consistency_lib.py`'s `Issue`/`report_and_exit` helpers and match
`check_adr_reference.py`'s CLI conventions (`--format json`) exactly, per the
source issue's own AI Implementation Instruction. Register it in
`.pre-commit-config.yaml` alongside its siblings. Document it in both
`docs/00_governance_04_documentation-checks.md` and `tools/TOOL_DESCRIPTIONS.md`.
Fix `ADR-002`'s missing heading so the new hook does not break CI on landing.

## Design
This is a Path B task (6 target files, exceeding Path A's ≤3-file threshold) —
though, being a self-contained `tools/` script addition with a closely-mirrored
sibling precedent, the standard Path B architecture/dependency-graphing
tooling (`grimp`/`pyan3`/`import-linter`/`pydeps`, aimed at `scripts/`-level
import graphs) does not meaningfully apply: a new `tools/*.py` script has no
import-graph relationship to `scripts/`, and `routing.md`'s own "Adding a new
tool" section already carves this class of change out of the standard
`python-implementation` validation sequence. The "concrete list of N files"
Path B's dependency-graphing step calls for is the 6-row Implementation Target
Files table above, produced by direct investigation (reading every sibling
tool/test/config/doc file this addition must match), not generated tooling.
Historical analysis (git churn, author count) is recorded in Affected areas.

- **The source issue's own Acceptance Criteria #1 is stale — verified, not
  assumed**: it expects the tool to flag `ADR-004`'s missing heading and the
  13-ADR duplication pattern. Both are already fixed by this session's own
  prior Plans. Per `rules/ai-execution.md` Adversarial Verification, this
  Plan re-checked current state directly (`grep -c "^## Known Deviations"
  docs/adr/*.md` across all 13 files) rather than trusting the issue's
  snapshot, and found the *actual* current violation is `ADR-002`, not
  `ADR-004` — recorded in Problem/Reason for change, not silently
  reconciled.
- **New sibling script, not an in-place extension**: `check_adr_reference.py`'s
  own docstring states its scope is intentionally narrow — "a smaller,
  well-scoped 'ADR-vs-code' audit rather than a repository-wide mandate...
  scoped to matrix-named files only." Checks (a) and (b) both need to examine
  *every* ADR file unconditionally, a broader mandate that doesn't fit that
  stated scope — this resolves the source issue's own Unresolved Question via
  the cited tool's own text, not a guess.
- **Fixing ADR-002 is the safest path to a landable pre-commit hook**: this
  repository already has a working precedent for the alternative (defer the
  hook's default-blocking invocation until a known finding resolves —
  `check_compat_shims.py`'s `--check-removed-names` flag, documented in its
  own `tools/TOOL_DESCRIPTIONS.md` entry) — but since `ADR-002`'s fix is a
  trivial, one-line-heading, mechanical addition (not the excluded semantic
  classification), fixing it directly is simpler than introducing a
  flag-gated, non-default hook variant for what would otherwise be a
  permanent carve-out.
- **Check (b)'s "skip if Notes has no path" rule is load-bearing, not
  incidental**: without it, every one of the 13 already-cleaned ADRs (whose
  Notes sections now read only a one-line pointer, or nothing at all beyond
  preserved caveats) would falsely appear to have "lost" every file/symbol
  Notes used to list — the source issue's own Implementation Intent explicitly
  anticipates this ("Implementation Notes may legitimately have zero list
  content after the companion cleanup issue is implemented").
