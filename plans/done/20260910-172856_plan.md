## Goal
- Fix the wrong mock-patch target in `tests/agent/test_diagnostic_store.py` so this
  test file exercises the fake in-memory `_FakeSQLiteHelper` instead of the real
  production `/opt/llm/db/session.sqlite` database, stopping further test-data
  pollution of that production file.

## Priority
High

## Scope
- **In-Scope**: replacing every `patch("db.helper.SQLiteHelper", ...)` occurrence in
  `tests/agent/test_diagnostic_store.py` with `patch("agent.diagnostic_store.SQLiteHelper", ...)`;
  verifying via `pytest` and a before/after production row-count check that the fix
  actually stops writes to the real database.
- **Out-of-Scope**: cleaning up rows already written into the real
  `/opt/llm/db/session.sqlite` by past test runs; any change to
  `scripts/db/config.py` or `config/agent.toml`'s `session_db_path`; auditing other
  test files for the same wrong-mock-target pattern; the optional `DiagnosticStore`
  path-injection hardening (constructor parameter) mentioned in the issue's
  Implementation Intent as a secondary, non-required recommendation (see Unknowns,
  `UNK-01`).

## Background
`scripts/agent/diagnostic_store.py` does `from db.helper import SQLiteHelper`
(confirmed: line 17), which binds the name `SQLiteHelper` into
`agent.diagnostic_store`'s own module namespace. Every `SQLiteHelper(...)`
construction inside `DiagnosticStore` (confirmed at `scripts/agent/diagnostic_store.py`
lines 121, 176, 188) therefore looks up the name via that local binding at call time,
not via `db.helper`. Every one of the 29 `patch(...)` call sites in
`tests/agent/test_diagnostic_store.py` targets `"db.helper.SQLiteHelper"` — the
*origin* module where `SQLiteHelper` is defined — instead of
`"agent.diagnostic_store.SQLiteHelper"`, the name as it is actually looked up at call
time. This is the standard wrong-mock-target bug: patching where a symbol is defined
does not affect a module that already did `from X import Y`.

## Problem
Because the patch never takes effect, `DiagnosticStore.save()`/`fetch()`/
`save_serialization_event()` fall through to the real `SQLiteHelper("session")`
construction path. `scripts/db/config.py::build_db_config()` reads
`config/agent.toml`, which sets `session_db_path = "/opt/llm/db/session.sqlite"`
(confirmed: `config/agent.toml` line 8) — a real file that exists and is used by the
running agent. `DiagnosticStore.__init__(self, session_id: int | None = None)`
(confirmed: `scripts/agent/diagnostic_store.py` line 39) takes no path-override
parameter, so there is no supported way to redirect it to a test path other than
mocking the correct import site — which this test file fails to do. The test file's
own `_FakeSQLiteHelper` + `fake_db` fixture (confirmed: lines 34-75) is the only
isolation attempt present, and it never engages because of the wrong patch target
above. No `tests/agent/conftest.py` exists (confirmed), and `tests/conftest.py` has
no diagnostics/session-DB autouse fixture that would otherwise catch this.

A read-only query against the real database during this Plan's own analysis
(`sqlite3 -readonly /opt/llm/db/session.sqlite "select count(*) from
session_diagnostics"`) returned 1018 rows, further grown from the 922 rows recorded
at the time the issue was filed — confirming the pollution is ongoing and the
defect remains live as of this Plan's generation.

## Reason for change
This is a data-integrity defect, not merely a broken test: every local or CI run of
`tests/agent/test_diagnostic_store.py` silently grows a real production database
file, pollutes it with non-production data, and makes the recorded diagnostics
history unreliable for its actual operational purpose. It also makes a large share of
this file's 34 test methods (issue estimate: 22-25) permanently fail regardless of
the code under test, since they assert on row counts that can never be exactly 1 in a
table that already has hundreds of unrelated rows.

## Implementation intent
Change every `patch("db.helper.SQLiteHelper", ...)` call in
`tests/agent/test_diagnostic_store.py` to `patch("agent.diagnostic_store.SQLiteHelper", ...)`
— the import-site convention — so the existing `_FakeSQLiteHelper`/`fake_db` fixture
actually engages and tests run against an isolated in-memory fake, not the real
database. No change to `scripts/agent/diagnostic_store.py`, `scripts/db/config.py`,
or `config/agent.toml` is required for this fix. The optional path-injection
hardening mentioned in the issue is deliberately excluded from this Plan's scope (see
`UNK-01`).

## Requirements

## Design
Root cause: Python's `unittest.mock.patch` must target the name as it is looked up at
call time in the module under test, not the module where the symbol was originally
defined. `scripts/agent/diagnostic_store.py` executes `from db.helper import
SQLiteHelper` at import time, which creates a new local binding
`agent.diagnostic_store.SQLiteHelper` that is independent of `db.helper.SQLiteHelper`
from that point on. Patching `db.helper.SQLiteHelper` therefore has no effect on code
that already imported the name via `from ... import ...`; the correct target is the
consuming module's own binding, i.e. `agent.diagnostic_store.SQLiteHelper`.

Fix approach: a mechanical string replacement of the patch target across all 29 call
sites in `tests/agent/test_diagnostic_store.py`. No change to `DiagnosticStore` or its
callers is needed — the existing `_FakeSQLiteHelper`/`fake_db` fixture already
implements the correct fake surface (`open()`, `execute()`, `fetchall()`, `commit()`,
context-manager protocol); it simply never gets substituted in today because the
patch never engages.

  and growing, confirmed via read-only query during this Plan's analysis) is
  commingled with genuine production diagnostics and cannot be cleanly separated
  after the fact → **Mitigation**: explicitly out of scope per the issue's own
  Constraints; this Plan does not attempt cleanup, only stops further pollution going
  forward.
- **Risk**: `radon`/`bandit` baselines (run in place of the DB-touching diff-cover
