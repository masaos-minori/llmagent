# Plan: Refactor pipeline.py — separation of concerns

## Goal
Split `scripts/rag/pipeline.py`'s `RagPipeline` class into focused modules to separate its five combined concerns and eliminate duplicated retry-once-with-delay logic.

## Priority
Medium

## Scope
- **In-Scope**: Extract five concern groupings into separate modules/classes; consolidate duplicated retry-once-with-delay helper; reduce `RagPipeline` to thin sequencer; reorganize affected test files
- **Out-of-Scope**: Changing pipeline stage order; changing timeout/retry values; adding new stages; modifying `scripts/mcp_servers/rag_pipeline/` internals; performance optimization

## Background
The module docstring states this file was "Extracted from agent/repl.py so that AgentREPL contains only input loop, command dispatch, and output display logic." After that extraction, `RagPipeline` accumulated the full RAG pipeline orchestration in one class rather than being split further. Similar splits were already completed for `scripts/agent/orchestrator.py`, `scripts/agent/repl.py`, and `scripts/rag/ingestion/ingester.py`.

## Problem
`RagPipeline` exceeds the 400-line threshold defined in `skills/DESIGN.md` File Split Rule trigger condition (672 lines) and combines at least five distinct concerns: MQE quality estimation, search execution, RRF fusion, reranking, and HTTP augmentation with context refinement.

**Correction (2026-09-04 audit)**: the "duplicated retry-once-with-delay logic across
`_run_stage` and `_run_http_augment`" claim under Reason for change does not hold —
inspection of `scripts/rag/pipeline.py` immediately before this Plan's generation
(commit `f3a569331`) shows neither method contained any retry/delay logic at that time.
The five-concern-extraction goal itself was accurate and has been fully implemented
(see Execution Status); only this one sub-claim was stale at authoring time, and no
retry consolidation was needed or performed.

## Reason for change
- `_get_stage_status`, `_mqe_status`, `_search_status`, `_fusion_status`, `_rerank_status` together account for roughly half the file and mix per-stage status reporting with formatting/aggregation logic
- `_run_stage` and `_run_http_augment` duplicate retry-once-with-delay logic across different methods
- Stage diagnostics and last_stage_results tracking are functionally unrelated to core pipeline orchestration but currently require reviewing the same 672-line file
- HTTP augmentation and context refinement are functionally unrelated to stage orchestration but currently require reviewing the same file

## Implementation intent
Extract the five concerns into separate modules/classes following the constructor-injection/delegation pattern used in `orchestrator.py` and `ingester.py` splits. Suggested grouping:
- **MQE stage** — owns `_mqe_status`, `_run_mqe`
- **Search stage** — owns `_search_status`, `_run_search`
- **Fusion stage** — owns `_fusion_status`, `_run_fusion`
- **Rerank stage** — owns `_rerank_status`, `_run_rerank`
- **HTTP augment + refiner** — owns `_run_http_augment`, `_run_refiner`, `_map_http_result_kind`

`RagPipeline.run()` should remain a thin sequencer calling into these components in the same order as today, preserving its public return contract (`PipelineRunResult`) and exception behavior.

## Design
### Architecture decisions (Path B analysis)

**Import graph**: `pipeline.py` imports from 15+ modules across rag/, rag/stages/, rag/repository/, shared/. Extracted modules will each have narrower import dependencies aligned to their concern.

**Caller/callee relationships**: `scripts/mcp_servers/rag_pipeline/rag_pipeline_service.py` consumes `RagPipeline`. Multiple test files also instantiate `RagPipeline` directly. This limits blast radius but requires careful interface preservation.

**Historical churn**: Recent commits touch pipeline.py for formatting, comments, fusion stage changes, diagnostics, and stage-level observability — moderate churn indicating active maintenance.

**Test coverage**: Eight test files exist with extensive coverage. Behavior-lock tests are critical for preserving pipeline stage order semantics.

**Dependency graph**: 
- Direct callers: `scripts/mcp_servers/rag_pipeline/rag_pipeline_service.py`, multiple test files
- Dependencies: `SQLiteHelper`, `SemanticCache`, `HttpAugment`, `_map_http_result_kind`, `RagLLM`, `get_embedding`, `RagConfigImpl`, `TwoStageFetchResult`, `HttpResultKind`, `SearchDiagnostics`, `RefineResult`, `refine_context`, `PipelineContext`, `PipelineStage`, `StageResult`, `PipelineRunResult`, `RagConfigValidator`, `build_embed_url`, `build_llm_url`, `RagConfig`

**Operational constraints**: Pipeline stage order must be preserved (MQE → Search → Fusion → Rerank → Augment → Refine). `RagPipelineError` raise conditions must be preserved. HTTP mode selection logic must be preserved.
