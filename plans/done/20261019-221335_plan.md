## Goal
- Route a database (`sqlite3.Error`) failure raised by `AgentSession.set_title` inside `SessionTitleService.generate` through the same `SessionTitleGenerationError` that the LLM-title fallback consumes, so a DB write failure degrades gracefully to the input-based title instead of escaping uncaught.

## Priority
Low

## Scope
- **In-Scope**:
  - Add an `except (sqlite3.Error)` clause to `SessionTitleService.generate` in `scripts/agent/services/session_title.py` that converts the `sqlite3.Error` into `SessionTitleGenerationError`, chained with `from e`, placed before the existing generic `(RuntimeError, OSError)` handler.
  - Add a regression test to `tests/agent/services/test_session_title.py` asserting that a `sqlite3.Error` raised by `set_title` surfaces as `SessionTitleGenerationError`.
- **Out-of-Scope**:
  - Changing the fallback title logic in `SessionTitleGen.generate` (`scripts/agent/commands/session_title.py`).
  - Changing `AgentSession.set_title` itself (`scripts/agent/session.py`) — including its `title[:SESSION_TITLE_MAX_CHARS]` storage cap (that is Issue sess002) or its `sqlite3.Error` propagation.
  - Changing which failures are considered retryable; only ensuring DB errors funnel through `SessionTitleGenerationError`.

## Background
`SessionTitleService.generate` calls the chat LLM, then persists the produced title via `AgentSession.set_title`. `set_title` performs DB writes and can raise `sqlite3.Error`. `SessionTitleGen.generate` (the command-layer generator, `scripts/agent/commands/session_title.py`) treats any `SessionTitleGenerationError` as a trigger for a local fallback title and wraps its own `set_title` call in a broad, logged `except`.

## Problem
In `SessionTitleService.generate`, the `set_title` call sits inside a `try` whose `except` clauses catch `SessionTitleGenerationError`, `httpx` errors, `ValueError`, and `(RuntimeError, OSError)`. `sqlite3.Error` matches none of these — its MRO is `sqlite3.Error -> Exception -> BaseException -> object`, so it is not a subclass of `RuntimeError`, `OSError`, or `ValueError` — and a DB failure while persisting the LLM-generated title escapes `generate` unconverted. `SessionTitleGen` only falls back on `SessionTitleGenerationError`, so the raw `sqlite3.Error` bypasses the fallback entirely instead of degrading gracefully to the input-based title.

## Reason for Change
The fallback is meant to be the safety net for any title-generation failure. The primary path currently has weaker error handling than the fallback: HTTP/parse failures degrade gracefully, but a DB write failure does not. Making `set_title` failures convert to `SessionTitleGenerationError` restores a single, consistent failure contract across the primary and fallback paths.

## Implementation Intent
Convert the `sqlite3.Error` raised by `set_title` inside `SessionTitleService.generate` into `SessionTitleGenerationError`. Add an explicit `except (sqlite3.Error)` clause before the generic handlers (or extend the final generic handler to include it), chaining the cause with `from e`. Do not change which failures are considered retryable; only ensure DB errors funnel through the same `SessionTitleGenerationError` that the fallback consumes.

- `REQ-001`: In `scripts/agent/services/session_title.py`, add an `except (sqlite3.Error)` clause to `SessionTitleService.generate` that raises `SessionTitleGenerationError` chained from the caught error (`... from e`), placed before the generic `(RuntimeError, OSError)` handler so it is reached before the generic branch.
- `REQ-002`: Preserve the existing re-raise ordering — `SessionTitleGenerationError` re-raised first, then network (`httpx`), then parse (`ValueError`), then DB (`sqlite3.Error`), then generic. No already-handled failure type may stop being handled or change its wrapping message shape.

## Design
- **Where: `SessionTitleService.generate`'s existing `try` (resolves UNK-02).** The method already funnels every failure type through `SessionTitleGenerationError` except `sqlite3.Error`. Adding an `except (sqlite3.Error)` clause completes that funnel. The clause is placed immediately before the generic `(RuntimeError, OSError)` handler (line 67) so it is reached before the generic branch and reads as a distinct, intentional DB-error case.
- **Why a dedicated clause rather than extending the generic handler.** `sqlite3.Error` is not a `RuntimeError`/`OSError`, so the generic handler never caught it; adding `sqlite3.Error` to that tuple would work but muddies the generic handler's "unexpected runtime errors" meaning. A dedicated clause documents intent and mirrors the existing per-type clauses (`httpx`, `ValueError`).
- **Ordering is safe.** `SessionTitleGenerationError` is a `RuntimeError` subclass (`exceptions.py` line 13) but is re-raised first (`except SessionTitleGenerationError: raise`, line 61), so it never shadows the new clause. `sqlite3.Error` is unrelated to `httpx`, `ValueError`, `RuntimeError`, and `OSError`, so no two clauses overlap. The resulting order is: `SessionTitleGenerationError` → `httpx` → `ValueError` → `sqlite3.Error` → `(RuntimeError, OSError)`.
- **Cause chaining.** Raise `SessionTitleGenerationError(<message>) from e` so the original `sqlite3.Error` is preserved in `__cause__`, matching the style of the surrounding clauses (`from e`).
- **Minimal surface.** The change is confined to one method in one source file plus one regression test. No signature, interface, schema, or deploy change; `set_title`'s behavior and propagation are untouched.
