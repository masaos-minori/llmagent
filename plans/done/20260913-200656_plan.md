# Consolidate duplicate SIGINT-absorb handler between HttpServerLifecycleManager and ShutdownCoordinator

## Goal
Eliminate the duplicate `_absorb_sigint_during_shutdown` implementation between
`HttpServerLifecycleManager` (`http_lifecycle.py`) and `ShutdownCoordinator`
(`http_lifecycle_shutdown_coordinator.py`) by extracting it to a single
module-level function in `http_lifecycle_shutdown_coordinator.py`, with both classes
exposing it as a `staticmethod` alias so existing call sites and tests keep working
unchanged.

## Priority
High

## Scope
- **In-Scope**: Extracting `_absorb_sigint_during_shutdown`'s body to one
  module-level function; making both `HttpServerLifecycleManager` and
  `ShutdownCoordinator`'s existing `_absorb_sigint_during_shutdown` attribute an alias
  (`staticmethod`) to that shared function, so `manager._absorb_sigint_during_shutdown`
  and `ShutdownCoordinator._absorb_sigint_during_shutdown` continue to exist and
  resolve to the same underlying function
- **Out-of-Scope**: Consolidating the two classes' actual shutdown *logic*
  (`HttpServerLifecycleManager.shutdown_all()`'s `_terminate_with_timeout`-based
  per-process termination vs. `ShutdownCoordinator.shutdown_all()`'s
  SIGTERM→timeout→SIGKILL process-group escalation) — see Background; removing
  `ShutdownCoordinator.shutdown_all()` as dead code (a separate cleanup, not part of
  this fix); changing the SIGTERM→SIGKILL escalation timing; any change to
  `HttpServerLifecycleManager`'s public API surface

## Background
Both `HttpServerLifecycleManager._absorb_sigint_during_shutdown`
(`http_lifecycle.py:528-538`) and `ShutdownCoordinator._absorb_sigint_during_shutdown`
(`http_lifecycle_shutdown_coordinator.py:55-60`) are identical `@staticmethod`s
(same body, same log message `"Lifecycle: SIGINT received during shutdown_all();
ignoring until cleanup completes"`), each installed via `signal.signal(signal.SIGINT,
...)` inside their own class's `shutdown_all()` (`http_lifecycle.py:540-589`;
`http_lifecycle_shutdown_coordinator.py:63-133`). Confirmed by direct inspection.

**Re-verified 2026-09-13** (this cycle, against the current repository state) —
two findings beyond the Issue's own description:

1. **`ShutdownCoordinator.shutdown_all()` is unreachable dead code.** Repository-wide
   search (`rg "shutdown_all"` across `scripts/` and `tests/`) found only
   `HttpServerLifecycleManager.shutdown_all()` actually invoked in production code
   (`factory.py:171`: `await self._http_mgr.shutdown_all()`). No call site invokes
   `ShutdownCoordinator.shutdown_all(manager)` anywhere, and no test file exercises
   `ShutdownCoordinator` directly (`tests/agent/test_resource_shutdown_coordinator.py`
   tests an unrelated class, `ResourceShutdownCoordinator`, from a different module).
   `HttpServerLifecycleManager.__init__` (`http_lifecycle.py:87`) already holds a
   `ShutdownCoordinator` instance as `self._shutdown_coordinator`, but
   `shutdown_all()` never reads it — this dependency is wired but never used.
2. **The two `shutdown_all()` implementations' actual termination logic differs,
   not just the SIGINT handler.** `HttpServerLifecycleManager.shutdown_all()` calls
   `self._terminate_with_timeout()` (`http_lifecycle.py:132-162`, using
   `_do_pgid_terminated()`) per process; `ShutdownCoordinator.shutdown_all()`
   implements its own separate SIGTERM→wait→SIGKILL loop
   (`http_lifecycle_shutdown_coordinator.py:81-127`) using `_kill_pg()`/
   `_kill_pg_force()`. Both achieve process-group-aware graceful-then-forceful
   termination, via two independent implementations — this is a second, larger form
   of duplication than the Issue's stated scope (SIGINT handler only).

Given finding 2, delegating `HttpServerLifecycleManager.shutdown_all()` entirely to
`ShutdownCoordinator.shutdown_all()` (the Issue's suggested approach) would silently
switch the actually-used termination code path to one that is currently untested and
unused in production — a materially larger behavior change than "remove a duplicate
SIGINT handler." This Plan narrows scope to exactly the SIGINT-handler duplication
(the Issue's literal problem statement and its "Duplicate ... SIGINT handler" title),
leaving the two termination-logic implementations' consolidation as a separate,
follow-on concern.

Existing tests directly assert on `HttpServerLifecycleManager._absorb_sigint_during_shutdown`'s
identity and presence: `tests/agent/test_http_lifecycle_integration.py`'s
`test_absorb_sigint_handler_exists` (`hasattr` check, line 49; monkeypatches the
attribute via `patch.object`, lines 55-58) and `test_shutdown_all_installs_guard_handler`
(line 89: `assert installed_handler is manager._absorb_sigint_during_shutdown` — an
identity check, not just an equality check). This constrains the extraction: the
attribute name and its resolution via `self._absorb_sigint_during_shutdown` must keep
working identically, which a `staticmethod` alias satisfies (the alias attribute
still exists on the class and yields the same underlying function object each access).

## Problem
The identical `_absorb_sigint_during_shutdown` static method exists in two places
with byte-for-byte identical code and log message text. Any future change to the
handler's behavior or log message must be applied in both locations; missing one
creates silently inconsistent SIGINT-absorption behavior and indistinguishable log
output between the two shutdown code paths (even though only one path is currently
reachable in production — see Background finding 1).

## Reason for change
Remove the literal code duplication of `_absorb_sigint_during_shutdown` by extracting
it to a single module-level function, so any future change to its behavior or log
message needs to happen in exactly one place — without touching the two classes'
independent (and differently-implemented) shutdown/termination logic, which is a
separate, larger concern (see Background finding 2).

## Implementation intent
1. In `http_lifecycle_shutdown_coordinator.py`, define a module-level function
   `_absorb_sigint_during_shutdown(signum: int, frame: object) -> None` with the
   existing shared body (the log message), placed alongside the existing
   module-level helpers (`_get_pgid`, `_kill_pg`, `_kill_pg_force`)
2. In `ShutdownCoordinator`, replace the class's own
   `_absorb_sigint_during_shutdown` method body with
   `_absorb_sigint_during_shutdown = staticmethod(_absorb_sigint_during_shutdown)`
   (a direct alias to the new module-level function), preserving the attribute's
   existence and identity
3. In `http_lifecycle.py`, import the module-level function from
   `http_lifecycle_shutdown_coordinator` and set
   `HttpServerLifecycleManager._absorb_sigint_during_shutdown = staticmethod(...)`
   the same way, replacing its own duplicate method body
4. No change to either class's `shutdown_all()` method body beyond this — the
   `signal.signal(signal.SIGINT, self._absorb_sigint_during_shutdown)` /
   `signal.signal(signal.SIGINT, ShutdownCoordinator._absorb_sigint_during_shutdown)`
   call sites are unchanged, since the attribute they reference still resolves to a
   callable with the same signature and behavior

## Design
This task is classified as **Path A** (small task): affects 2 files, no public
interface changes (both classes' public method signatures are unchanged; only a
private attribute's implementation is now shared), no database schema changes.

This cycle's re-verification found the Issue's core duplication claim accurate, but
also found the duplication is embedded in a larger, unaddressed structural
duplication (two parallel, independently-implemented termination code paths, one of
which — `ShutdownCoordinator.shutdown_all()` — is entirely unreachable in production).
Fully adopting the Issue's suggested fix (delegate `HttpServerLifecycleManager.shutdown_all()`
to `ShutdownCoordinator` entirely) would silently switch production behavior to the
currently-unused, untested code path — a materially larger and riskier change than
what the Issue's title and Problem section describe. This Plan is scoped narrowly to
the literal SIGINT-handler duplication, tracking the larger termination-logic
consolidation question as a non-blocking Unknown for a separate decision.

Key design decisions:
1. Use a `staticmethod` alias (`ClassName._absorb_sigint_during_shutdown =
   staticmethod(shared_func)`) rather than simply deleting one class's method and
   redirecting call sites to import the module-level function directly — this
   preserves `hasattr(HttpServerLifecycleManager, "_absorb_sigint_during_shutdown")`
   and the identity-check assertion in `test_shutdown_all_installs_guard_handler`
   without modifying any existing test
2. Place the shared module-level function in `http_lifecycle_shutdown_coordinator.py`
   (not `http_lifecycle_errors.py`, which the Issue's Implementation Intent also
   suggested) — `http_lifecycle_errors.py`'s stated purpose is "Exceptions and
   dataclasses for HTTP subprocess MCP server startup failures," semantically
   unrelated to a shutdown signal handler; `http_lifecycle_shutdown_coordinator.py`
   already hosts semantically related module-level helpers (`_get_pgid`, `_kill_pg`,
   `_kill_pg_force`) and `http_lifecycle.py` already imports from it, so no new import
   edge or circular-import risk is introduced
3. Do not consolidate the two `shutdown_all()` termination-logic implementations —
   that is Background finding 2's separate, larger concern (tracked as UNK-01), which
   this Plan's narrower scope (matching the Issue's literal title) does not require
