# Implementation Plan: `turn_end` audit events are duplicated on success and missing on failure

## Goal

- Emit exactly one `turn_end` audit event per user turn, on every exit path: success, soft LLM
  error, workflow halt, an exception that escapes the engine, and cancellation.
- Make `turn_end.elapsed_ms` measure the turn instead of the process uptime, and keep the turn's own
  `task_id` and `workflow_id` in the event.
- Put the turn bracket in one owner (`Orchestrator._execute_turn`) and the turn-event builder in one
  owner (`AuditEventEmitter`), and clear turn and workflow state on every exit path.
- Delete the second, unreachable copy of the turn-end event and the `TurnState` fields that nothing
  in `scripts/` produces or consumes.

## Priority

High

## Background

`audit.log` is the operational record of the agent: each turn writes `turn_start`, `workflow_start`,
`stage_completed`, `tool_exec`, and `turn_end`. `docs/23_agent/agent_10_02_operations-and-observability-audit-and-otel.md:32`
states that two lifecycle events bracket each turn, and `:56` states that `turn_end` carries
`workflow_id` — the only field in the whole log that joins a turn to the workflow task rows written
by the engine (`audit_workflow_start` / `audit_stage_completed` stamp `task_id` with the *workflow*
task id, `turn_*` / `tool_*` with the *turn* id; see `tool_audit.py:50`, `:75`, `:161` and
`audit_event_emitter.py:83`). The issue `turn004` is the reason the other turn-lifecycle issues
(`turn002`, `turn003`) can be measured at all: if `turn_end` is duplicated on success and absent on
failure, then turn counts, latency, and failure rates read out of `audit.log` are all wrong.

Two components implement the same lifecycle today. `AuditEventEmitter` is built by
`Orchestrator.__init__` (`orchestrator.py:71-72`, wired with the view hooks from
`startup_component_init.py:79-82`) and is called by `_execute_turn`. `WorkflowEngineAdapter` carries
its own private copy of the same builder (`workflow_engine_adapter.py:206-258`) and calls it from the
`verify` stage (`:178-183`). The adapter's copy is the one that runs first, so it wins the turn id
and the workflow id, and the caller's copy then writes a second event with an empty id.

Corrections to the issue's claims, established against current source:

1. "If `_process_turn` raises … no `turn_end` event at all" is true only when the exception escapes
   `execute_turn` (case G) or the turn is cancelled (case E). A stage failure configured
   `retryable: true` in `config/workflows/default.json` becomes a halt, which `_handle_workflow_halt`
   (`:186-188`, `:311-321`) converts into a normal return, so today the caller does emit one event
   (measured cases B and F). Two of the five paths are missing the event, not "the exception paths".
2. The second event's empty `task_id` is not only caused by the id being cleared at `:385`. The
   `task_id` argument of `build_turn_end_event` (`audit_event_emitter.py:107-113`) is never read:
   the dict takes `task_id` from `build_turn_end_metadata(ctx)`, which reads
   `ctx.turn.current_turn_id or ""` (`:94`). The adapter's copy has the same dead parameter
   (`workflow_engine_adapter.py:210-228`).
3. The issue's `Dependencies` section says this work "shares the `execute_turn(...)` signature with
   `turn001`; change the signature once". That dependency does not exist: `execute_turn` already
   takes `turn_started_at` (`workflow_engine_adapter.py:131-137`), and the frozen turn001 Plan
   (`plans/20261023-084918_plan.md`, REQ-009 and its target-row notes) keeps both the signature and
   the `""` session id unchanged. This Plan changes only the *value* passed at `orchestrator.py:168`.
4. The issue's acceptance list asks for a non-empty `task_id` but does not mention `workflow_id`,
   which is the harder constraint. `turn_end` carries a real `workflow_id` today only inside the
   adapter's `verify`-stage event, because `_deactivate_workflow` (`:199`, `:305-309`) and
   `_handle_workflow_halt` (`:317-319`) clear `ctx.workflow.*` before any caller-side emit runs. Any
   bracket placed outside the adapter therefore emits `workflow_id=""` unless the teardown moves with
   it. probe9 measures that moving the teardown keeps `workflow_id` set on all five paths.
5. The "Dead state" claim is confirmed, and is slightly wider than the issue states:
   `TurnState.last_error_kind` (`context.py:199-202`) appears nowhere outside its declaration;
   `tool_calls` (`:196`), `turn_count` (`:197`), `_lock` (`:198`), `add_tool_call` and
   `get_tool_calls` (`:204-216`) have no producer or consumer in `scripts/` and are used only by
   `tests/agent/test_context.py:23-36`. `current_turn_id` (`:194`) and `background_tasks` (`:195`)
   are live (written by `audit_event_emitter.py:76`, `:145` and `tool_runner.py:84`; read by
   `tool_audit.py:50`, `:75`, `:161` and `audit_event_emitter.py:94`).
6. No test pins the adapter's duplicate emission: `_handle_turn_end`, `_build_turn_end_event` and
   their siblings appear in no test file, and `test_orchestrator.py:537-560`, `:564-590`, `:718` and
   `tests/integration/test_orchestrator_integration.py:313-340` inspect only
   `audit_logger.info.called` / the last call payload. No test asserts an event count or an
   `elapsed_ms` value, which is why the defect has stayed invisible: it matches the issue's
   expectation that "deleting the second emitter must not break any test".

## Reason for Change

- Every latency or failure-rate reading taken from `audit.log` is currently wrong by construction:
  success paths are counted twice, failure and cancellation paths are not counted at all, and
  `elapsed_ms` is process uptime in every event that uses it.
- A cancelled or failed turn leaves `ctx.turn.current_turn_id` set, so the next turn's
  `tool_exec` / `tool_approval` rows can be stamped with a *previous* turn's id
  (`tool_audit.py:50`, `:75`, `:161`, `tool_runner.py:84`) until the next `emit_turn_start`
  overwrites it (`audit_event_emitter.py:76`).
- `agent_10_02:32` and `:56` document behavior the code does not produce, and
  `agent_02_runtime-architecture.md:102` attributes the lifecycle events to the Orchestrator while
  the first event is actually written by the adapter. Two implementations of the same event are the
  mechanism of the defect; the issue asks for one owner.

## Implementation Intent

- Make `Orchestrator._execute_turn` the single turn bracket: start the clock, emit `turn_start`, run
  the adapter, and in a `finally` emit `turn_end` and deactivate the workflow. Catch
  `BaseException` (not `Exception`) only to record what escaped, then let it propagate unchanged.
- Make `AuditEventEmitter` the single builder of `turn_start` / `turn_end`; delete the adapter's copy
  and the stage hook that called it.
- Move the workflow teardown to the bracket so the event can still carry `workflow_id`, and keep the
  teardown unconditional even if the audit write fails.
- Delete the state fields and the test that no production code uses, rather than inventing producers
  for them.
- Keep every existing event key, the `execute_turn` return tuple, the adapter's public method set,
  and the workflow definition unchanged.

## Requirements

- `REQ-001`: `_execute_turn` captures one monotonic turn start (`time.perf_counter()`) before
  `emit_turn_start()` and passes it to `execute_turn(line, turn_started_at, "")`, replacing the two
  `0.0` literals at `orchestrator.py:168` and `:171`. `import time` is added to the stdlib import
  group (`rules/coding.md`). The `session_id` argument stays `""`.
- `REQ-002`: `_execute_turn` brackets the adapter call in `try` / `except BaseException` / `finally`.
  The `finally` emits `turn_end` and then deactivates the workflow, so both run on success, halt,
  escaped exception, and cancellation. The caught exception is never swallowed.
- `REQ-003`: when an exception escapes `execute_turn`, `error_kind` is
  `getattr(exc, "kind", None) or type(exc).__name__` and `is_partial` is
  `bool(getattr(exc, "partial_text", ""))`. No new audit event type is introduced.
- `REQ-004`: the `turn_end` write inside the `finally` is best-effort: a failing emit is reported at
  `logger.error` with the turn id and never prevents the teardown and never replaces the exception
  already in flight.
- `REQ-005`: `WorkflowEngineAdapter._handle_turn_end` (`:369-385`) is deleted and the `verify` stage
  callback (`:178-183`) no longer performs turn-end work. The `verify` stage itself stays in
  `config/workflows/default.json` and stays a required stage (`workflow_loader.py:49`), so its
  callback becomes a documented no-op returning `None`.
- `REQ-006`: the four now-unreachable private turn-end helpers in the adapter
  (`:206-208`, `:210-228`, `:230-239`, `:241-...`) are deleted; `AuditEventEmitter`'s public
  equivalents become the only implementations.
- `REQ-007`: the adapter stops clearing turn/workflow state on turn exit: the `finally` no longer
  calls `_deactivate_workflow` (`:199`), and `_handle_workflow_halt` (`:311-321`) keeps its
  `logger.error` and `on_error` call but no longer assigns `ctx.workflow.*` (`:317-319`). The
  teardown moves to the bracket through the existing public `deactivate_workflow(ctx)` alias
  (`:113-118`), which stays a thin delegate to `_deactivate_workflow` (`:305-309`).
- `REQ-008`: `AuditEventEmitter.emit_turn_end` (`:127-145`) keeps its signature, event keys,
  `on_turn_end` hook, and `ctx.turn.current_turn_id = None` clearing; the unused `task_id` parameter
  of `build_turn_end_event` (`:107-113`) is removed and its single call site (`:139-141`) updated.
- `REQ-009`: `TurnState` (`context.py:193-216`) declares only `current_turn_id` and
  `background_tasks`; `tool_calls`, `_lock`, `last_error_kind`, `turn_count`, `add_tool_call` and
  `get_tool_calls` are deleted. `import asyncio` stays (`background_tasks: set[asyncio.Task[Any]]`).
- `REQ-010`: `tests/agent/test_context.py::test_turn_state_concurrency` (`:23-36`) is deleted,
  together with the imports it alone required (`import asyncio` at `:1`, `TurnState` in the
  `agent.context` import at `:4`).
- `REQ-011`: `audit_stage_completed`'s `elapsed_ms` (`workflow_engine_adapter.py:167`) keeps its
  existing meaning — time from turn entry to stage completion — and units, and now receives a real
  start through `turn_started_at`.
- `REQ-012`: the four documents named in `Documentation Impact` state the single bracket, the
  one-event-per-turn rule, the `error_kind` vocabulary for failure paths, and that historical
  `elapsed_ms` values are not reliable.

## Design

### The hidden coupling: `turn_end.workflow_id`

`turn_end` is the only audit event that links a turn to the engine's task rows.
`audit_workflow_start` and `audit_stage_completed` stamp `task_id` with the *workflow* task id;
`turn_start`, `turn_end`, and every `tool_*` event stamp it with the *turn* id
(`audit_event_emitter.py:83`, `tool_audit.py:50`, `:75`, `:161`). The join is
`turn_end.workflow_id`, which `agent_10_02:56` documents. Both turn-end builders read
`ctx.workflow.workflow_id` at event-build time (`workflow_engine_adapter.py:237`,
`audit_event_emitter.py:94-99`), and today the adapter's copy runs *before* its own teardown at
`:199` / `:317-319`, which is the only reason that field is ever non-empty.

Therefore the location of the bracket and the location of the teardown must move together. Options
considered, with the measured consequence:

- `DR-001` (chosen, user decision): the bracket lives in `_execute_turn` and the teardown moves with
  it, through the adapter's public `deactivate_workflow(ctx)` alias (`:113-118`), executed after the
  emit. probe9 measures `task_id` set, `workflow_id` set, real `elapsed_ms`, derived `error_kind` and
  a cleared turn id on all five paths, with exactly one event each. Rejected side effect: it amends
  the frozen turn003 Plan's statement that `_handle_workflow_halt` is not edited (see `DR-006`).
- `DR-002` (rejected): the bracket lives in `_execute_turn` and the teardown stays in the adapter.
  One event per turn, but `workflow_id` is always `""`, which contradicts `agent_10_02:56` and
  removes the only turn↔workflow join from the log.
- `DR-003` (rejected): emit inside the adapter's `finally` before `_deactivate_workflow` and delete
  the caller's `emit_turn_end`. Fields are preserved, but `turn_start` would belong to the caller and
  `turn_end` to the adapter — the split that produced this defect — and it would require injecting the
  emitter and both view hooks into the adapter, adding a dependency in the opposite direction.

### The bracket shape

```python
async def _execute_turn(self, line):
    """Run one turn: one turn_start, one turn_end on every exit path."""
    ctx = self._ctx
    turn_started_at = time.perf_counter()
    answer, error_kind, is_partial = "", None, False
    await self._audit_emitter.emit_turn_start()
    try:
        answer, error_kind, is_partial = await self._workflow_adapter.execute_turn(
            line, turn_started_at, ""
        )
    except BaseException as exc:  # noqa: BLE001 — the bracket must close on every exit path, including CancelledError; the exception is re-raised by Python after this clause
        error_kind = getattr(exc, "kind", None) or type(exc).__name__
        is_partial = bool(getattr(exc, "partial_text", ""))
    finally:
        try:
            await self._audit_emitter.emit_turn_end(
                line, answer, turn_started_at, error_kind, is_partial
            )
        except Exception as exc:  # noqa: BLE001 — a failed audit write must not skip the teardown nor mask the exception in flight
            logger.error("Failed to emit turn_end audit event: task_id=%s: %s", ctx.turn.current_turn_id, exc)
        self._workflow_adapter.deactivate_workflow(ctx)
```

- `except BaseException` is required because `asyncio.CancelledError` derives from `BaseException`;
  `except Exception` would leave case E unrecorded (measured: `workflow_engine.py:129` has the same
  limitation, which is why turn003 handles cancellation in the adapter's `finally`).
- The measured radon complexity of this body is `A` (`/tmp/opencode/cc_probe.py`), so
  `radon cc -s -n C scripts/agent/orchestrator.py` stays empty and the split of `_process_turn`
  stays turn002's work.
- Emit first, then deactivate: the event needs the turn id and the workflow id, and
  `emit_turn_end`'s own clearing (`audit_event_emitter.py:145`) is what makes the id empty
  afterwards. `deactivate_workflow` is the last statement so no earlier failure can skip it.
- The adapter keeps its `finally` status block (`:190-198`, turn003's shape) and its
  `_owns_state_store` close (`:200-202`); only the `_deactivate_workflow` call leaves it.

### `error_kind` for paths the adapter never returned from

- `DR-004` (chosen): derive from the caught exception, keep the event type as `turn_end`. A
  `kind`-carrying exception keeps its structured value (matching `llm_turn_executor.py:114`),
  everything else falls back to the class name. A failed turn is then distinguishable inside the
  existing vocabulary: `error_kind` non-null plus the absence of a `completed` status in `tasks`.
- `DR-005` (rejected): a separate `turn_failed` event. It answers the same question but adds a value
  to the event vocabulary that the issue explicitly asks not to add, and every consumer of
  `agent_10_02` / `agent_10_03` would need the new vocabulary in the same change.
- `DR-006` (rejected): leave `error_kind=None` on failure paths and rely on the DB. The audit log
  would then still not distinguish "clean turn" from "turn that blew up", which is the question the
  issue asks.
