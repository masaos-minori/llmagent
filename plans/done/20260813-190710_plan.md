# Plan: Deprecate dead `LlmTransportErrorHandler.resolve_retryable`; document (gated) consolidation with `LlmReconnectHandler`

## Goal

Eliminate the false signal created by keeping a fully dead method
(`LlmTransportErrorHandler.resolve_retryable` in `scripts/shared/llm_transport_errors.py`) alive
with its own maintained test suite, while the same three-branch retry-classification rule
(`HEARTBEAT_TIMEOUT` -> flag / `MALFORMED_SSE_FRAME` -> flag / fallback -> `e.retryable`) is
independently re-implemented, live, in `LlmReconnectHandler.resolve_retryable`
(`scripts/shared/llm_reconnect.py`). This plan executes the requirement's lower-risk sub-task now
(mark the dead method deprecated) and documents — but does not implement — the higher-risk
cross-file consolidation sub-task, which the requirement explicitly gates behind sign-off not yet
obtained.

## Scope

### In-Scope
- Re-verify (immediately before implementation) that `LlmTransportErrorHandler.resolve_retryable`
  still has zero production callers, via `rg "resolve_retryable" scripts/ tests/` and

## Design

**How this fits the existing architecture**: `LlmTransportErrorHandler` and `LlmReconnectHandler`
are both static-method utility classes under `scripts/shared/`, sitting at the same architectural
layer (transport/error-translation helpers consumed by the SSE streaming stack:
`llm_sse_stream.py` -> `llm_reconnect.py` -> `llm_client.py`). Adding a `DeprecationWarning` inside
`LlmTransportErrorHandler.resolve_retryable` is a leaf-level, non-structural change: the method
keeps its existing signature (`(e, heartbeat_timeout_retry, malformed_chunk_retry,
heartbeat_timeout_counter) -> tuple[bool, int]`) and branch logic exactly as-is, so no import
boundary, layering rule, or `lint-imports` contract is touched — `resolve_retryable` does not
import from or get imported by any new module as part of this change.

**Doc impact check**: `docs/01_overview-files-04-shared-part2.md` (lines 26, 29) and
`docs/01_overview-files-03-scripts-part1.md` (line 39) mention `llm_transport_errors.py` /
`llm_reconnect.py` only at the module/class level ("`llm_transport_errors.py` —
LlmTransportErrorHandler"); `docs/05_agent_05_llm-and-streaming-part1.md` (line 66) documents
`LlmReconnectHandler.stream`'s reconnect behavior at the public-method level. None of these
describe `resolve_retryable`'s internal branch logic or call it out as a distinct behavior, and
this plan does not change `resolve_retryable`'s observable behavior (same return value; only adds
a warning side-effect) — no `docs/*.md` update is required for sub-task 1.

**Why sub-task 2 is documented, not implemented, here**: the requirement's own risk
classification splits dead-code removal (low risk, this plan's scope) from cross-file
consolidation (higher risk, explicit-sign-off-gated). Implementing the consolidation without
sign-off would violate the requirement's own "Implementation intent" §2 gate. The natural design
for that future work, per the requirement, is to make `LlmTransportErrorHandler.resolve_retryable`'s
counter-threading signature (`tuple[bool, int]`) the shared helper's shape — since
`_evaluate_stream_error` already needs the counter for `e.stat_heartbeat_timeouts` — and have
`LlmReconnectHandler.resolve_retryable` (or `_evaluate_stream_error` directly) call it instead of
re-implementing the three branches. That design is recorded here for the future plan that will
implement sub-task 2 once UNK-02 (sign-off) is resolved.

**Aside (out of scope, noted for hygiene)**: `uv run vulture scripts/shared/llm_reconnect.py
--min-confidence 80` flags `stat_parse_errors_ref` (line 82, a parameter of
`LlmReconnectHandler.stream`) as unused. Confirmed via `rg "stat_parse_errors_ref" scripts/ tests/`
and reading `scripts/shared/llm_client.py`: this parameter is accepted by `stream()` but never
forwarded to `LlmSseStreamHandler.stream_once` (which does have a working
`stat_parse_errors_ref` parameter), and `llm_client.py` doesn't pass it — `stream()` obtains parse
error counts from its return tuple instead. This is a pre-existing, unrelated finding from the
2026-07-03 module-split refactor (`05a4fdab4`), not connected to the `resolve_retryable`
requirement's target files or behavior. Not filed as a separate issue per this plan's scope
restriction (issues limited to this plan's own Unknowns/Risks); left as a note for a future,
separately-scoped cleanup pass over `llm_reconnect.py`.

## Risks

- **Risk**: The `DeprecationWarning` message could be missed by a future contributor who calls
  `LlmTransportErrorHandler.resolve_retryable` from new code without noticing the warning in test
  output. → **Mitigation**: The warning message explicitly names the live replacement
  (`LlmReconnectHandler.resolve_retryable`); combined with the zero-caller `rg` re-check in Phase 1
  of every future change touching this file, a new caller would be caught before merge. Likelihood: low.
- **Risk**: Wrapping the 4 existing `TestResolveRetryable` assertions in `pytest.warns(...)` could
  accidentally narrow or change what each test asserts if the `with` block is scoped incorrectly
  (e.g., assertions outside the `with` block would still pass even if no warning fired, silently
  weakening the new coverage). → **Mitigation**: Keep the `resolve_retryable(...)` call itself
  inside the `with pytest.warns(DeprecationWarning):` block for each of the 4 tests, and add the
  dedicated warning-fires test as a second, independent check that isn't tied to the return-value
  assertions. Likelihood: low.
- **Risk**: A future removal change (after the grace period) could delete
  `LlmTransportErrorHandler.resolve_retryable` and `TestResolveRetryable` without re-confirming
  zero callers, if the `rg` re-check habit isn't followed. → **Mitigation**: This plan's Phase 1
  step and the requirement's own Implementation instructions §1 both call for re-running the `rg`
  check immediately before any change to this method; the same instruction should be copied into
  the future removal plan. Likelihood: low (tracked via UNK-01, filed as
  `issues/20260813-190848_unknowns.md` — not fully mitigable within this plan alone since the
  removal change is out of this plan's scope).
