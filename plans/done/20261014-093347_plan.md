# Plan: Mask alternate secret shapes in the agent secret masker

## Goal
Extend `agent.secrets_masker._mask_secrets()` to also mask `Authorization: Bearer <token>` and related bearer-header secret shapes, while preserving the existing `key=value` masking and the function's public contract (replace secrets in a string, never raise, stay cheap).

  - Add unit tests for the new shapes plus regression coverage for the existing `key=value` shapes.
  - Update the secret-masking section in `docs/23_agent/agent_10_01_operations-and-observability-startup-and-health.md` to state the final set of masked forms and remove the limitation note.
- **Out-of-Scope**:

  - Reusing or modifying `scripts/shared/logger.py`'s shared redaction registry (`register_secret` / `attach_redaction_filter`) — its public API and other callers must not change.

## Background
`_mask_secrets()` is applied to MCP subprocess output that the Agent reports on startup failure (`scripts/agent/http_lifecycle.py`, `scripts/agent/startup_mcp_starter.py`). The ledger entry `AGENT-006` records the shape-recognition gap as `open` / `Medium` / `design-gap`. Source `scripts/agent/secrets_masker.py`, target `docs/23_agent/agent_10_01_operations-and-observability-startup-and-health.md`.

`issues/done/20261004-160514_secmask001_secrets-masker-leaves-short-secret-values-unmasked.md` (`secmask001`) addressed a different defect in the same module (the value-leak half) and left the shape-recognition gap open as an unresolved question. `AGENT-006` tracks exactly that deferred gap, which remains open.

## Problem
The three `SECRET_PATTERNS` in `scripts/agent/secrets_masker.py` each require a `<key>\s*=\s<value>` structure. Real subprocess output frequently carries credentials in other shapes — an `Authorization: Bearer <token>` header line, a JSON field `"api_key": "..."`, or a bare token on its own line. None of these match, so they are logged in clear text. Masking is best-effort, but the current matcher gives a false sense of protection: it masks `key=value` secrets and silently passes everything else through.

## Reason for change
The masking path is security-sensitive (it exists precisely to keep credentials out of logs and startup-error reports). A shape it does not recognize leaks directly. The value-leak half of the problem is now fixed by `secmask001`; the recognition half is still open and should not be left as an unanswered question.

## Implementation intent
Extend `SECRET_PATTERNS` (pattern-extension resolution path) rather than route through the shared log-redaction registry. Rationale: both call sites pass opaque strings (`_mask_secrets(stderr_full[:500])`, `_mask_secrets(str(e))`); the registry (`register_secret`/`attach_redaction_filter`) redacts pre-known values via a `logging.Filter`, which does not fit a pure string→string masker operating on arbitrary text, and wiring it in would risk changing call-site behavior. The final masked set is:
- Existing `key=value` forms unchanged (`password`/`passwd`/`pwd`, `api_key`/`apikey`, `secret`/`token`).
- `Authorization: <scheme> <token>` header (scheme-generic, case-insensitive).
- Standalone `Bearer <token>` (case-insensitive), covering bearer tokens that appear without an `Authorization:` prefix.

## Design
Resolution path: **pattern extension** in `SECRET_PATTERNS`. Both call sites (`http_lifecycle.py:420`, `startup_mcp_starter.py:100`) pass opaque strings through `_mask_secrets()`, which keeps its pure string→string contract. The shared registry (`scripts/shared/logger.py`) redacts pre-known values via a `logging.Filter` and would require extracting values before masking — incompatible with the current contract and would risk changing call-site behavior.

Final masked set (case-insensitive):
1. `key=value` — unchanged (`password`/`passwd`/`pwd`, `api_key`/`apikey`, `secret`/`token`).
2. `Authorization: <scheme> <token>` — e.g. `Authorization: Bearer <token>`, `Authorization: Basic <token>`.
3. Standalone `Bearer <token>` — bearer tokens appearing without an `Authorization:` prefix.

Candidate patterns (added after the existing three, preserving the `group(1) + "***MASKED***"` replacement convention):
```python
re.compile(r"(?i)(Authorization:\s*\S+\s+)(\S+)"),  # Authorization: <scheme> <token>
re.compile(r"(?i)(Bearer\s+)(\S+)"),                 # standalone Bearer <token>
```
Both patterns use non-overlapping quantifiers (`\S+` followed by `\s+`/`\S+`), so there is no catastrophic-backtracking risk. Applying them sequentially is safe even if one pattern's output feeds the other: the token is always replaced by `***MASKED***` (a `\S+`), so neither pattern can re-expose a real token.

Out of scope by decision: JSON `"key": "value"` and bare hex/base64 tokens produce too many false positives to justify; they are recorded as out-of-scope, not as future requirements.

- **Risk**: Regex catastrophic backtracking on adversarial input (the masker runs on every log line). → **Mitigation**: patterns use only non-nested `\S+`/`\s+` quantifiers with a hard separator; covered by the existing `test_arbitrary_text_never_raises` case plus new bearer cases.
- **Risk**: Regressing the `secmask001` value-leak fix (same file/tests/doc). → **Mitigation**: existing `key=value` regression cases are retained unchanged; the new patterns are additive only.
