## Goal
Make `deploy/setup_services.sh` classify the remote `embed-llm` / `agent-llm` health result the way the agent's own startup pipeline classifies it — `agent-llm` (required) stays fatal, `embed-llm` (optional) becomes a non-fatal warning by default, with a documented `LLM_GATE_STRICT=1` switch that restores the current abort — so that an unreachable embedding service no longer blocks the Event Bus, and make the script's final summary state which services were started and which were skipped/degraded.

## Priority
High

## Background
- Found on 2026-10-19 while trying to start the Event Bus (`127.0.0.1:8015`) on the production host.
- `deploy/setup_services.sh` lines 76-129 implement a health gate before the Event Bus block (lines 132-137): it reads `embed_url` and `llm_url` from `config/agent.toml`, retries `GET /health` on both (`LLM_HEALTH_RETRIES="${LLM_HEALTH_RETRIES:-30}"`, line 82, five-second interval, line 83), and exits with `[FATAL] LLM services did not become ready within ${LLM_HEALTH_RETRIES} attempts (~$((LLM_HEALTH_RETRIES * LLM_HEALTH_INTERVAL))s).` (lines 122-127), or `[FATAL] LLM base URL(s) not configured in config/agent.toml (embed_url/llm_url).` (lines 100-103).
- The gate treats both services symmetrically (line 114: both must return HTTP 200), so either being down aborts the whole script under `set -euo pipefail` (line 12).
- Measured on 2026-10-19: `embed_url = "http://192.168.11.238:8081"` (unreachable) while `llm_url = "http://192.168.11.197:8080"` returns healthy. The gate waits 30 attempts (~150 s) then aborts. `/opt/llm/llama.cpp` exists but the embedding server's command/model are not in this repository; `setup_services.sh` line 76 states these are remote services the repository only health-checks.
- The same condition is non-fatal for the agent: `scripts/agent/services/mcp_health.py::check_service_health` classifies `("llm", ..., required=True)` and `("embed-llm", ..., required=False)` (lines 294-319), so an unreachable `embed-llm` becomes a `logger.warning` + non-fatal `ServiceWarning`, while an unreachable `llm` becomes a fatal error. The production startup log on 2026-10-19 20:00 recorded `WARNING [check_service_health] [non-fatal] embed-llm unreachable ...` and still completed startup.
- `config/agent.toml` declares no Event Bus URL or token, and `deploy/start_agent.sh` does not start the Event Bus; `setup_services.sh` is the only path that starts it. `/opt/llm/logs/eventbus.log` does not exist, so that path has never completed.

## Problem
- One unavailable remote service makes the whole service-setup script fail, including the part that does not depend on it: `set -euo pipefail` (line 12) means the Event Bus lines (132-137) are never reached.
- The two deployment entry points disagree about the severity of the same condition: `setup_services.sh` treats an unreachable `embed-llm` as fatal, while the agent (`check_service_health` + `startup_validation.py` / `startup_reporter.py`) treats it as a warning. An operator who follows the documented order gets a hard stop, then finds the agent starts anyway.
- The failure message does not say that the Event Bus was left unstarted, and the retry loop prints only `embed-llm=---, agent-llm=200` style progress lines, which does not distinguish "service down" from "wrong health path".
- Related observability gap (recorded by the issue as a separate follow-up, out of scope here): `scripts/mcp_servers/rag_pipeline/rag_pipeline_server.py::_check_health_deps` (lines 208-220) only records `embed_url` as "not configured" when the key is missing or not a string; a configured-but-unreachable `embed_url` passes the rag_pipeline `/health` check. This gate is therefore the only place in the deployment path that notices an embedding-service outage — which is exactly why making it non-fatal must still surface the condition clearly.

## Reason for Change
- Deployment failure: the documented service startup sequence cannot complete on the current host state.
- Consistency: one host condition has two different severities across two `deploy/` entry points.
- Operability: the abort hides which services were started and which were skipped, and burns ~150 s before reporting it.
- Correctness of the health story: the component that should surface an embedding outage (`rag_pipeline` `/health`) does not, and the component that does notice stops the deployment instead of degrading.

## Implementation Intent
- Keep the health probe (it is the deployment path's only embedding-outage check) but classify it the way `check_service_health` does: `agent-llm` (required) stays fatal; `embed-llm` (optional) becomes a non-fatal warning the operator can opt into as fatal. Concretely: report both statuses, continue to the Event Bus block, and make strict behavior an explicit, documented switch (`LLM_GATE_STRICT=1`), with the current abort kept as the strict-mode behavior.
- Report what was started and what was skipped in the script's final summary, so an operator can tell that the Event Bus is up while `embed-llm` is down.
- Keep the fail-closed parts intact: the workflow definition and schema pre-flight checks (lines 20-70) stay fatal and in their current order.
- Record the rag_pipeline observability gap as a separate follow-up rather than fixing the MCP health contract inside this issue.

## Design
Path A (≤3 modification-target files; no new module, no public/library API or endpoint change, no DB schema). The design below is grounded in Step 3's direct verification.

**Severity classification (core).** The current gate (lines 111-127) waits until BOTH `embed-llm` and `agent-llm` return HTTP 200, then aborts if either did not. Replace the single `ready` flag with per-service readiness flags (`EMBED_OK`, `LLM_OK`) recorded as soon as each returns 200, and record the last status/error for each. Then decide severity per service, mirroring `check_service_health`:
- `agent-llm` (required): if not ready → fatal.
- `embed-llm` (optional): if not ready → warning by default; fatal only when `LLM_GATE_STRICT=1`.

This makes the script's semantics identical to the agent's: `agent-llm` down always aborts; `embed-llm` down degrades unless the operator opts into strict mode. When both are ready the script proceeds exactly as today.

**Strict switch.** `LLM_GATE_STRICT="${LLM_GATE_STRICT:-0}"`. In strict mode the `agent-llm`-not-ready branch and the `embed-llm`-not-ready branch both emit the existing `[FATAL] LLM services did not become ready within ${LLM_HEALTH_RETRIES} attempts (~$((LLM_HEALTH_RETRIES * LLM_HEALTH_INTERVAL))s).` message (lines 123-125) and `exit 1`, reproducing the current behavior exactly for either-or.

**Summary (REQ-004).** After the Event Bus block, print a structured summary listing each service as started or skipped/degraded with the reason (e.g. `embed-llm (<url>): UNREACHABLE — degraded, non-fatal` / `Event Bus (:8015, PID <pid>): started`). This replaces the current implicit flow and directly addresses the "message does not say the Event Bus was left unstarted" problem.

**Control-flow under `set -euo pipefail`.** Preserve `set -euo pipefail` (constraint). All new conditionals use explicit `if` tests (safe under `set -e`); the `curl` calls keep their `|| true`. Real failures are never silenced — the script still exits non-zero for a required-service outage or a pre-flight failure.

**Cross-dependency (Issue `ebsec001`).** Making the gate non-fatal lets the script REACH the Event Bus block, but the block currently uses bare `python -m eventbus.app` (line 134, `PYTHONPATH` set on line 133), which dies with `ModuleNotFoundError` without FastAPI. Actually starting the service is `ebsec001`'s responsibility (change to `uv run "${UV_PROD_FLAGS[@]}"`). This issue only makes the script reach and launch the block; its script-level test stubs `python` so it needs no FastAPI. The two fixes are independent per the issue's stated dependency.

**Adversarial verification (corrected understanding vs. the issue's literal wording).**
- The issue says "Move or reorder the script so the Event Bus is started before the script can abort." The Plan does NOT reorder: making the abort conditional (non-fatal for the optional service) means the Event Bus block is reached by falling through, with no reordering required. Reordering was offered by the issue as one option ("for example"), not a requirement.
- The issue's AC "starts it, exits 0" implicitly depends on `ebsec001` fixing the bare-`python` start; this Plan documents that dependency rather than implementing it.
- The issue references `start_agent.sh` as treating embed-llm as non-fatal, but `start_agent.sh` contains no health-check logic at all. The actual non-fatal classification lives in `scripts/agent/services/mcp_health.py::check_service_health`; that is the reference to align with, not `start_agent.sh` (which is cited only to confirm it does not start the Event Bus).
