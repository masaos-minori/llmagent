## Goal
- Establish EventBus as a fail-closed security boundary by adding authentication middleware, a publisher/consumer/operator/monitoring authorization model bound to caller identity, audit logging of authorization failures and privileged actions, and fail-closed configuration-key validation — while leaving the already-strict loopback-only bind enforcement untouched.

## Priority
High

## Scope
- **In-Scope**:
  - A new ADR recording the authentication mechanism and authorization model decision.
  - Bearer-token authentication middleware for the EventBus FastAPI app, implemented locally within `scripts/eventbus/` (the `eventbus-is-isolated` import-linter contract forbids importing `scripts/shared/` or `scripts/mcp_servers/`).
  - A publisher/consumer/operator/monitoring permission model, with authenticated identity bound to allowed `consumer_id`s and topics.
  - Operator-only authorization for DLQ administration (`/dlq`, `/dlq/{event_id}/requeue`) and privileged replay (`/replay`).
  - Structured audit logging of authorization failures and privileged actions, with no secret values recorded.
  - Fail-closed rejection of unknown, missing, and incorrectly-typed EventBus configuration keys in `load_config()` (`scripts/eventbus/config.py`) — implemented locally, not via `scripts/shared/config_loader.py`'s `ConfigLoader` (see Design/Assumptions).
  - Regression test confirming the existing loopback-only bind rejection is unchanged.
  - Positive/negative authorization tests for every route category.
  - `docs/00_security_01_architecture-and-trust-boundaries.md` update documenting the new model as canonical.
- **Out-of-Scope**:
  - Re-implementing or weakening loopback-only binding (`EventBusConfig.__post_init__`, `_LoopbackVerifyingServer`) — already implemented; this Plan only adds a regression test confirming it (REQ-007).
  - Transactional ACK/offset redesign, backpressure handling, and DLQ requeue redesign — each tracked by a separate Issue/Plan in this batch (`eb_h01`, `eb_h02`, `eb_h03`).
  - Migrating EventBus configuration loading to `scripts/shared/config_loader.py`'s `ConfigLoader` — architecturally prohibited (see Design).
  - Correcting the stale `CI-001` status/Recommended-Action text in `docs/00_governance_03_issue-and-uncertainty-management.md` (it currently contradicts `ADR-002`'s own embedded note that CI-001 was already resolved via a local-invariant approach) — flagged as a Risk, not fixed by this Plan (out of scope: it is a pre-existing documentation inconsistency unrelated to this Issue's stated Target Files).
  - Choosing between static bearer token / rotatable service token / mutual TLS / reverse-proxy authentication as an open research question — this Plan's REQ-001 resolves it to static bearer token, grounded in the existing `attach_auth_middleware()` precedent (`scripts/mcp_servers/server.py`) and the `EVENTBUS-008` Known Issue's own recommendation, and records that decision in the new ADR; it is not left as a discretionary later choice.

## Background
No route in `scripts/eventbus/` authenticates or authorizes callers (`Confirmed by repository evidence`: `rg` across `app.py`, `publish_route.py`, `subscribe_route.py`, `ack_route.py`, `dlq_route.py`, `replay_route.py` finds no auth-related code; the only "auth" hits are a log message and a `ValueError` message about the absence of authentication). `EventBusConfig.__post_init__` (`scripts/eventbus/config.py` lines 44-54) already raises `ValueError` for any `host` other than `127.0.0.1`/`::1`, and `app.py`'s `_main()` (lines 203-219) adds a post-startup `_LoopbackVerifyingServer` socket check as defense-in-depth — both confirmed by direct read, matching the Issue's citation. `load_config()` (`config.py` lines 60-80) uses a bespoke `tomllib.load()` call, rejects only a fixed, hardcoded set of removed keys (`_REMOVED_CONFIG_KEYS`), and reads only the enumerated required keys via `data["..."]`/`data.get("host", ...)` — any other key present in the TOML file is silently ignored, and no key's type is validated before being passed into the `EventBusConfig` dataclass.

Dependencies: N/A: none (per Issue) — this Plan has no dependency on other Issues, Plans, or external work, and nothing else depends on it.

This gap is already tracked as `EVENTBUS-008` (No Production Authentication Model for Event Bus HTTP API, High severity, open) and `CI-001` (EventBus process reads configuration directly instead of using ConfigLoader, High severity, open) in `docs/00_governance_03_issue-and-uncertainty-management.md`. `EVENTBUS-008`'s own Recommended Action already suggests "Implement static bearer-token validation in the Event Bus process; add auth middleware to route handlers" — this Plan adopts that mechanism (see Design).

## Problem
- No authentication middleware exists — every route accepts unauthenticated requests.
- No authorization model exists — a caller can act as any `consumer_id`, access any topic, administer the DLQ, and trigger replay, all without any permission check.
- `load_config()` bypasses fail-closed validation for anything beyond the fixed removed-key list: an unknown key is silently ignored, and no key's type is checked before being handed to `EventBusConfig`.

## Reason for change
Establish EventBus as a fail-closed security boundary, additive to (not a replacement for) the already-strict loopback-only binding: authentication must identify the caller, authorization must limit actions/topics/consumer IDs, and configuration behavior must reject anything unexpected rather than silently accept it.

## Implementation intent
Record the authentication/authorization design decision in a new ADR first (this Plan resolves the mechanism choice to a static Bearer token, per Design below, so the ADR documents rather than re-opens that decision). Implement the middleware and permission model as new, self-contained modules inside `scripts/eventbus/` — the `eventbus-is-isolated` import-linter contract forbids depending on `scripts/shared/` or `scripts/mcp_servers/`, so the existing `scripts/mcp_servers/server.py::attach_auth_middleware()` and `scripts/mcp_servers/audit.py::AuditRecord` patterns are mirrored conceptually but reimplemented locally, not imported. Harden `load_config()` in place (reject unknown keys, validate each required key's type) rather than migrating to `ConfigLoader`, which the same import-linter contract prohibits and which `ADR-002` already resolved via a documented local-invariant exception. Update the security architecture doc last, once the implementation is complete and testable.

## Design
Authentication mechanism: static Bearer token, mirroring the existing `scripts/mcp_servers/server.py::attach_auth_middleware()` pattern — a FastAPI `@app.middleware("http")` function that checks `request.headers.get("Authorization", "")` against a configured token and returns `401` on mismatch. This is reimplemented locally in a new `scripts/eventbus/auth.py`, not imported, because the `.importlinter` `eventbus-is-isolated` contract (confirmed `KEPT` via `PYTHONPATH=scripts uv run lint-imports`) forbids `eventbus` from importing `mcp_servers` or `shared`. The token itself is added as a new required key to `config/eventbus.toml` (validated by `REQ-005`'s stricter `load_config()`), following the existing `auth_token = "${ENV:...}"` convention already used by every `*_mcp_server.toml` file.

Authorization model: four roles — publisher, consumer, operator, monitoring — each granted a fixed subset of routes. A consumer's authenticated identity is bound to the `consumer_id` it is permitted to use and the topics it may subscribe to (closing the gap where any caller could currently act as any `consumer_id`). Operator permission gates DLQ administration and privileged replay (scope per `UNK-01`/the `REQ-001` ADR). Monitoring permission is read-only (health/metrics-style access); this Plan does not add a new monitoring-only route, so it is defined in the ADR for completeness but has no corresponding code change in this Plan's `Implementation Target Files`.

Configuration hardening: `load_config()` is extended with a local, non-shared type/unknown-key check (an explicit allow-list of the 7 known keys — `port`, `db_path`, `storage_dir`, `offsets_dir`, `deadletter_dir`, `max_retry`, `host` — plus the new `auth_token` — with a per-key `isinstance` check) rather than reusing `scripts/shared/config_utils.py::get_typed()`, which `eventbus` cannot import. This mirrors `rules/coding.md`'s Type-coercion policy intent (reject wrong types, don't silently coerce) without violating the isolation contract.

Audit logging: a new `scripts/eventbus/audit.py`, mirroring `scripts/mcp_servers/audit.py::AuditRecord`'s structured-fields style (event/source/ts/session-or-consumer-id/tool-or-route/target), emitting one record per authorization failure and per privileged action (DLQ admin, replay), with the `Authorization` header's token value never included in any logged field.

`ConfigLoader` migration: explicitly not pursued. `ADR-002-config-isolation.md`'s own embedded `CI-001` Known Issue note (lines 363-375) already documents and accepts this exact exception — "EventBus cannot import ConfigLoader (`.importlinter` `eventbus-is-isolated` contract). Resolved via a local invariant instead" — so `REQ-001`'s ADR only needs to reference this existing resolution, not re-litigate it.
