## Goal
- Make `POST /nack` reject, with HTTP 409 `event already acknowledged`, a NACK sent by a consumer that has already ACKed the same event, without changing any failure counter and without allowing DLQ promotion — so the implemented behavior matches the documented state machine (ACKed is terminal for NACK).

## Priority
High

## Scope
- **In-Scope**:
  - Per-consumer "already ACKed" check in `nack_event()` (keyed on `consumer_delivery.acked_at` for the requesting `consumer_id`), evaluated atomically with the counter UPDATE.
  - HTTP 409 mapping in the `nack` route so the per-consumer case returns `event already acknowledged`.
  - Regression tests (unit, route-level, DLQ-promotion, second-consumer semantics).
  - Updating the three EventBus documents and the one ADR-006 bullet so they state the final behavior and drop the pointers to the source Issue.
- **Out-of-Scope**:
  - Redesigning the per-consumer delivery model or offsets; changing ACK semantics.
  - Setting `events.acked_at` from the per-consumer ACK path.
  - An idempotency guard for duplicate NACK (separately known).
  - The deleted-event race on the 409 path (tracked as EVENTBUS-011).
  - Choosing the alternative option (keep behavior and change the documents/ADR-006).

## Background
`ack_event_for_consumer()` records an ACK only in `consumer_delivery` and `consumer_offsets`; it never sets `events.acked_at`. The consumer-less `ack_event()`, which does set `events.acked_at`, is not called by any route. `nack_event()` rejects a NACK only when `events.acked_at` or `events.dlq_at` is set. EventBus documents (`eventbus_03`, `eventbus_06`, `eventbus_15`) and ADR-006 define an ACKed event as non-NACKable (HTTP 409), and currently carry a pointer to the source Issue where they describe the gap.

## Problem
Verified against current source (Step 3):
- ACK then NACK by the same consumer passes the `WHERE ... acked_at IS NULL AND dlq_at IS NULL` guard in `nack_event()`, so `delivery_failure_count`, `cycle_failure_count` and `events.consumer_delivery_failure_count` are incremented and the route returns HTTP 200.
- Repeated NACKs after an ACK can reach `cfg.max_retry` and promote an already-processed event to the DLQ through `promote_single()` in `_nack_and_promote()`.
- The `nack` route maps the invalid-transition sentinel to a 409 detail by re-reading only `events.acked_at`/`events.dlq_at`; for a per-consumer ACK both are NULL, so even if `nack_event()` rejected the request the route would return `invalid NACK transition`, not `event already acknowledged`.
- Correction to the Issue's wording: the "consumer failure counter" is the event-level column `events.consumer_delivery_failure_count`, not a per-consumer counter.

## Reason for change
The documented API contract and the implemented behavior disagree on a state transition that affects delivery correctness: spurious failure counts and possible DLQ promotion of events that consumers have already processed.

## Implementation intent
Adopt the Issue's recommended option: reject the NACK when the requesting consumer has already ACKed the event. Implement the check inside the existing UPDATE statement of `nack_event()` (a `NOT EXISTS` subquery on `consumer_delivery`), so the check and the counter update are one atomic statement and no counter can change on rejection. Return the existing invalid-transition sentinel and teach the route to report `event already acknowledged` when the per-consumer ACK exists. Leave the `consumer_id is None` path of `nack_event()` unchanged.

## Requirements
- `REQ-001`: A NACK from consumer C for event E, when C has already ACKed E, returns HTTP 409 with detail `event already acknowledged`, and `delivery_failure_count`, `cycle_failure_count` and `consumer_delivery_failure_count` of E are unchanged.
- `REQ-002`: The already-ACKed determination uses the per-consumer delivery state (`consumer_delivery.acked_at` for the requesting `consumer_id`) and is evaluated atomically with the counter update in `nack_event()`; the `consumer_id is None` path keeps its current events-level-only behavior.

## Design
Path B classification (more than 3 files affected).
- **Architecture**: `delivery_repo.py` is the delivery layer; `ack_route.py` is the HTTP route that calls it through the `eventbus.db` facade. Dependencies are unchanged: no new imports and no new cross-package edges. `lint-imports` reports a pre-existing broken contract unrelated to EventBus (`shared.production_config_validator -> agent.tool_policy`); it is not caused by this Plan.
- **Dependency graph**: `nack_event()` is called only by `ack_route.py` (through `eventbus.db`) and by tests; `eventbus.db` re-exports it. Four production/test-code files plus three documents and one ADR change in total.
- **Historical**: `ack_route.py` and `test_eventbus_ack_nack.py` are high-churn (15 and 14 commits in 30 days); keep edits small and localized. All files have a single effective author.
- **Operational**: no dependency upgrade and no new service dependency; `pip-audit` is not applicable. SQLite schema is unchanged, so no data migration or lock coordination is needed; the change runs inside the existing `run_with_db_lock` serialization.
- **Atomicity choice**: put the per-consumer check in the UPDATE itself (`NOT EXISTS` subquery bound to `consumer_id`) rather than a separate SELECT, so the check and the counter increment cannot interleave with a concurrent ACK. When the UPDATE matches no row, the existing follow-up SELECT distinguishes not-found (-1) from invalid transition (-2).
- **Route mapping**: on the -2 result the route first looks up `consumer_delivery.acked_at` for the requesting consumer and raises `ERR_EVENT_ALREADY_ACKED`; only then falls back to the existing `events.acked_at` / `events.dlq_at` inspection. This keeps the DLQ 409 and the fallback `invalid NACK transition` branches intact.
- **Validation baseline** (Step 5): radon — `nack_event` B(6), `ack_event_for_consumer` B(8), route `nack` C(13); vulture — no findings at confidence 80 for both source files; bandit — pre-existing Low 1 / Medium 1, High 0 for both files (not caused by this Plan); diff-cover baseline is recorded at the start of implementation and must reach the threshold in `rules/toolchain.md` Completion checklist.
