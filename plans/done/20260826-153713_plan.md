## Goal
Add a "Documentation Drift Detection" subsection to `prompts/04_refactor.md`'s Step 3
(Preparation) that compares implementation evidence against seven named document
sources (`routing.md`, `AGENTS.md`, README, design documents, coding and toolchain
rules, configuration specifications, deployment definitions), records each drift as an
evidence-based Finding with a defined record schema, and reuses — rather than
duplicates — `rules/coding.md`'s existing five-category "Current behavior"
classification as the disposition space for confidently-resolved findings, adding two
pre-classification confidence states (`Unverified`, `Ambiguous Source of Truth`) for
findings whose evidence does not yet support choosing one of the five.

N/A: not specified in issue

## Scope
- **In-Scope**:
  - Add a `##### Documentation Drift Detection` subsection under
    `#### Step 3: Preparation` in `prompts/04_refactor.md`.
  - Compare relevant implementation details against: `routing.md`, `AGENTS.md`,
    README, design documents, coding and toolchain rules, configuration
    specifications, deployment definitions.
  - Define the Drift Finding record schema: document, implementation evidence, drift
    description, confidence, possible source of truth, suggested follow-up.
  - Reuse `rules/coding.md`'s existing five-category "Current behavior" classification
    (Accepted current specification / Implementation fix required / Documentation fix
    required / Issue already tracked / Obsolete and removable) as the disposition a
    confidently-resolved Drift Finding is routed to, instead of defining a second,
    parallel classification system.
  - Add two pre-classification confidence states — `Unverified` and `Ambiguous Source
    of Truth` — for a Drift Finding whose evidence does not yet support choosing one
    of the five `rules/coding.md` categories.
  - State explicitly that a Drift Finding classified `Ambiguous Source of Truth` must
    not be auto-resolved via `rules/coding.md`'s "ambiguous cases default to
    Implementation fix required" rule — that default is calibrated for authoring a
    `docs/*.md` note about an already-known gap, not for a drift-detection process
    spanning a wider, more consequential document set (deployment definitions,
    toolchain rules, etc.); an `Ambiguous Source of Truth` finding requires maintainer
    confirmation before it is routed into one of the five categories.
  - State that Drift Finding discovery does not modify `docs/*.md`, `routing.md`,
    `AGENTS.md`, README, or any other document — documentation changes remain opt-in,
    surfaced only via the unified Proposal mechanism (per issue 01's Plan,
    `plans/20260826-151739_plan.md`), never applied automatically.
- **Out-of-Scope** (explicit in issue, plus carried forward from sibling Plans):
  - Automatic documentation updates.
  - Repository-wide documentation audits (this subsection runs during a refactor's
    Step 3 on the target file's relevant document references, not as a standalone
    audit tool).
  - Architecture Smell detection.
  - Deprecated analysis.
  - Path C classification and its checklist (issue 02, `plans/20260826-152429_plan.md`).
  - Architecture Baseline / Path C validation (issue 03,
    `plans/20260826-153056_plan.md`).
  - Redefining or relaxing `rules/coding.md`'s five-category classification — this
    Plan reuses it as-is; any change to that table is out of scope here.

## Design
- **Path A/B classification of this Plan**: Path A. Single target file
  (`prompts/04_refactor.md`, per the issue's `## Files to Change`), no public/runtime
  interface change, no database schema change. Per `skills/issue-to-plan/SKILL.md`
  Routing, this is determined by the three Path A criteria alone; content size does
  not change the classification. Direct verification performed: `routing.md`
  references `prompts/04_refactor.md` by name only (no Step-number cross-reference to
  update); no file under `docs/` references this file at all.
- **Step 3 confirmed as the correct insertion point**: the issue's Tasks say "Extend
  Step 3 with Documentation Drift Detection." Direct inspection of the current
  `prompts/04_refactor.md` confirms `#### Step 3: Preparation` currently covers `rg`
  symbol search, a `deploy.sh` reference check, and Path A/B-gated `pydeps`/
  `import-linter`/`ast-grep` depth, producing an impact scope table — no Technical Debt
  Discovery, Responsibility Analysis, or Documentation Drift Detection subsection
  exists yet in the file on disk (issues 01-03's Plans are pending approval, not yet
  implemented). This step sits before Step 4 (Behavior Lock) and well before Step 6
  (Transformation) — the correct place to record drift findings before any
  code-locking or transformation work begins.
- **Relationship to issue 01's Plan (`plans/20260826-151739_plan.md`)**: that Plan
  defines the Discovery Vocabulary (Finding/Candidate/Proposal/Approved
  Change/Blocked/Not Applicable) and appends Technical Debt Discovery then
  Responsibility Analysis to the end of Step 3. This Plan's Documentation Drift
  Detection is a third, independent discovery mechanism under the same Step —
  it reuses issue 01's unified Proposal format for any suggested documentation change
  (REQ-007) and is ordered to append after Responsibility Analysis (REQ-001) so the
  final subsection order inside Step 3 is deterministic regardless of implementation
  sequence. Unlike issue 03's Plan (which depends on issue 02's Path C classification),
  this Plan has no hard dependency on issues 01-03: Documentation Drift Detection
  applies uniformly across Path A/B/C refactors and does not reference Path
  classification at all — confirmed by the issue's Tasks list, which never mentions
  Path A/B/C.
- **Reuse decision — the key design choice for this Plan**: `rules/coding.md`'s
  "Documentation notes — 'Current behavior' classification" table already defines a
  five-category disposition (Accepted current specification / Implementation fix
  required / Documentation fix required / Issue already tracked / Obsolete and
  removable) for a `docs/*.md` note describing a known gap. The issue's requested
  `Unverified` / `Ambiguous Source of Truth` classification substantially overlaps
  with this: both are about deciding what a discovered discrepancy means. Rather than
  defining a second, competing classification, this Plan makes Documentation Drift
  Detection's output feed directly into `rules/coding.md`'s existing table:
  `Unverified` and `Ambiguous Source of Truth` are pre-classification confidence
  states used only while evidence is still insufficient to select one of the five
  categories; once evidence is sufficient, the Drift Finding's "possible source of
  truth" / "suggested follow-up" fields are populated using the five-category table
  directly (REQ-004). The one explicit divergence (REQ-006): `rules/coding.md`'s
  "ambiguous cases default to Implementation fix required" auto-resolution is
  intentionally NOT applied to `Ambiguous Source of Truth` Drift Findings, because that
  default was calibrated for authoring a single `docs/*.md` note (where filing an
  issue is cheap and reversible), while Documentation Drift Detection spans a wider,
  more consequential document set (deployment definitions, toolchain rules, routing)
  where auto-deciding could misdirect a refactor — matching the issue's own Intent
  ("without automatically deciding whether the code or document is authoritative").
  This divergence is scoped narrowly to this one subsection and does not alter
  `rules/coding.md`'s table for any other caller.
- **Duplicate-check performed** (see Report): searched `plans/` and `plans/done/` for
  an existing documentation-drift-detection framework targeting
  `prompts/04_refactor.md` or elsewhere. Two `plans/done/` matches

  (issue 01) and `plans/20260826-153056_plan.md` (issue 03) both explicitly list
  "documentation-drift detection" under Out-of-Scope, reserved for issue 04 — confirming
  no sibling Plan already covers this. No existing Plan defines the
  document/evidence/drift-description/confidence/source-of-truth/follow-up record
  schema. This confirms no duplicate exists; this Plan proceeds as new work.
