## Background
The Issue's cited claim
(`docs/03_rag_03_02_query_pipeline-rag-pipeline-class.md:46,84`:
"`invalidate_cache()` is intended to be called only after corpus changes ...")
is quoted accurately from the document (the text is duplicated verbatim at both
line 46 and line 84, within this file's `## 2.`/`## 2a.` duplicate sections).

**Re-verified 2026-09-13** (this cycle): `invalidate_cache()` does not exist
anywhere in the current codebase. A repository-wide search (`rg
"invalidate_cache" scripts/ tests/`) found it only in
`tests/rag/test_rag_pipeline_no_cache_freshness.py`, which **asserts its
absence** three times (`assert hasattr(pipeline, "invalidate_cache") is False`,
lines 92, 113, 137) — its removal is deliberately verified, not an oversight. This
traces to the same semantic cache removal already confirmed during a sibling
issue's investigation this cycle (`282b08f38 req-005: remove SemanticCache from
RAG pipeline and MCP server`, `09093016d feat(rag): remove semantic cache
configuration fields and references`).

A further, code-level instance of the same staleness was found in
`scripts/rag/pipeline.py` itself: `RagPipeline.augment()`'s own docstring lists
"2. Semantic cache: cached string (final) or None (fallback)" as a live fallback
step (line 267) and states "May update semantic cache on successful augment" as a
side effect (line 284) — but `augment()`'s actual fallback chain (already
confirmed during a sibling issue's investigation this same cycle,
`183020`/`plans/20260913-210928_plan.md`) has only 4 steps (HTTP mode, Search
Pipeline, Refiner, Raw Chunks) — no semantic-cache step exists in the executed
code. Additionally, line 95 carries an orphaned comment ("In-memory
nearest-neighbour cache; threshold/max_size read from cfg") immediately followed
by a blank line and then unrelated config-resolution code — a leftover from the
removed cache's initialization code, with no corresponding attribute or logic
remaining beside it.

## Problem
1. `docs/03_rag_03_02_query_pipeline-rag-pipeline-class.md` documents
   `invalidate_cache()` — a method verified not to exist — as a caller
   responsibility, misleading a reader into looking for a method that was removed
2. `scripts/rag/pipeline.py`'s own `augment()` docstring lists a "Semantic cache"
   fallback step that does not execute in the current implementation, and carries
   an orphaned comment referencing removed cache initialization — both stale
   artifacts of the same removal, inside the source code itself

## Reason for change
Correct both the documentation and the source-code docstring/comment to state
the semantic cache (including `invalidate_cache()`) was removed, matching the
confirmed current implementation and the dedicated test verifying its absence.

## Implementation intent
1. Replace both duplicate mentions of `invalidate_cache()`
   (`docs/03_rag_03_02_query_pipeline-rag-pipeline-class.md:46,84`) with a note
   stating the semantic cache (and `invalidate_cache()` with it) was removed,
   citing the removal commits and the test verifying its absence
2. Remove the "2. Semantic cache: ..." line from `augment()`'s docstring
   (`pipeline.py:267`) and renumber the remaining fallback steps
3. Remove "May update semantic cache on successful augment"
   (`pipeline.py:284`) from the Side effects list
4. Remove the orphaned comment (`pipeline.py:95`)
