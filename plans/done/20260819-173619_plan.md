## Design

1. **ACK/NACK transition table.** One table with columns: Scenario | Current
   code behavior (verified) | HTTP status | Response body | Persistence
   side effect. Populate all nine rows from the verified code:
   - First ACK → `ack_event` returns `(True, True)` → 200, `{event_id,
     acked: true, seq}`, sets `acked_at`, writes offset if `consumer_id` set.
   - Duplicate ACK → `ack_event` returns `(True, False)` → 200,
     `{event_id, acked: true, already_acked: true}`, no further write, no
     offset re-write (offset write only happens on `newly_acked`).
   - First NACK → `nack_event` increments `delivery_failure_count` from 0
     to 1 (or higher) → 200, `{event_id, delivery_failure_count}`, promotes
     to DLQ if `>= max_retry`.
   - Duplicate NACK → `nack_event` has **no idempotency guard**; every call
     unconditionally increments `delivery_failure_count` again → 200 each
     time, side effect: counter keeps incrementing, DLQ promotion can
     trigger on a later duplicate call. Document explicitly as "not
     idempotent by design today" (Documentation notes classification:
     "Implementation fix required" is the honest classification per
     `rules/coding.md`, but implementing that fix is out of scope here —
     file it as a follow-up requirement pointer, do not silently write it
     up as accepted spec).
   - ACK after NACK → `ack_event`'s `WHERE acked_at IS NULL` still matches
     (NACK never sets `acked_at`) → 200, ack succeeds, `delivery_failure_count`
     stays at whatever NACK left it; document that a NACKed-then-ACKed
     event is treated as a normal ack with no reconciliation of the prior
     failure count.
   - NACK after ACK → `nack_event` has no `acked_at` check → 200, NACK
     "succeeds" (increments `delivery_failure_count`) even though the event
     is already acked; document as currently unenforced/undefined-by-design,
     mirroring the requirement's own framing.
   - Unknown event ID (ACK) → `ack_event` returns `(False, False)` → 404,
     `ERR_EVENT_NOT_FOUND`. (NACK) → `nack_event` returns `-1` → 404,
     `ERR_EVENT_NOT_FOUND`.
   - Concurrent ACK/NACK → both run through `run_with_db_lock`, which
     serializes them at the DB-access layer; document as "no true race — the
     lock enforces a total order, and the second call observes the first
     call's already-committed state," resolving UNK-01 above.
   - Consumer mismatch → no consumer/event ownership column exists;
     `consumer_id` is accepted as any string and used only for
     `write_offset`/`read_offset`; document as explicitly unenforced (per
     Implementation instructions #1/#3), not silently omitted.
2. **`since_seq`/offset precedence.** Quote the exact logic from
   `subscribe_route.py` lines 32-34 (`start_seq = since_seq; if consumer_id
   and start_seq == 0: start_seq = read_offset(...)`) and state the rule
   in prose: an explicit `since_seq=0` and an omitted `since_seq` (which
   defaults to `0` per the `Query(default=0)` declaration) are
   indistinguishable once `consumer_id` is supplied — both resolve to
   "read from stored offset," so a client that wants a genuine full replay
   while also passing `consumer_id` cannot currently express that intent.
   State the resolution as: documentation-only clarification for this
   phase, with a flagged follow-up: *if* a sentinel value fix
   (`since_seq=-1` meaning "no override, use stored offset" vs. `since_seq=0`
   meaning "start from the beginning") is later judged necessary, it must be
   filed as a separate implementation requirement — this plan does not
   schedule that code change.
3. **Reconciliation procedure.** Document: (a) detection — compare `SELECT
   MAX(seq) FROM events` in SQLite against the `seq` field of the last line
   of `events.jsonl`; a gap indicates a JSONL append failure occurred; (b)
   existing signal — `publish_route.py`'s `logger.warning("eventbus: JSONL
   append failed (event still committed): %s", exc)` (line 59) is the only
   log emitted today, with no metric/alert; (c) recommended additions (as
   documentation-only recommendations, not implemented here): a counter
   metric on this WARNING path and an operator runbook step to re-derive
   missing JSONL lines from SQLite (SQLite is authoritative per
   `docs/06_eventbus_02_05_failure-behavior-summary.md`), so JSONL can be
   backfilled without data loss.
4. **Auth/authz design note.** A short new subsection (in
   `docs/06_eventbus_90_inconsistencies_and_known_issues.md`, alongside the
   new Known Issue entry, or as a dedicated block) selecting one of the six
   options. Recommend **static bearer token validated by the EventBus
   process itself**, with a documented upgrade path to a rotatable service
   token, because: it requires no new infrastructure (no reverse proxy or
   mTLS cert management dependency), is enforceable directly in
   `scripts/eventbus/config.py`'s existing validation pattern (rejecting
   `allow_public_bind=true` without a configured token, mirroring the
   existing public-bind check), and is the minimum viable step up from
   today's "loopback-only, no auth" state. Document: 401 (missing/absent
   `Authorization` header) vs. 403 (well-formed but wrong/revoked token)
   response body shapes; a `EVENTBUS_LOCAL_DEV=1`-style bypass restricted to
   loopback bind (mirroring the existing `allow_public_bind` gate) as the
   local-dev exception; and secret rotation as "operator replaces the
   configured token value and restarts the process" (no hot-reload) for a
   first iteration, with rotation-without-restart flagged as a future
   enhancement, not part of this design note's minimum bar. This selection
   and its rationale are documentation only — implementing token validation
   in `scripts/eventbus/config.py` or the route handlers is explicitly
   deferred to a future implementation requirement per Global Rule 8.
5. **Known Issue entry.** Add, in the "対応が必要な項目" section next to
   `EVENTBUS-001` (same severity tier — High/open), an entry such as
   "EVENTBUS-008: No production authentication model" with the same
   two-line style used by the existing entries (what's missing, current
   mitigation state, whether a server-side fix is planned). This keeps the
   new gap tracked with identical rigor to `EVENTBUS-001`, as required by
   the requirement's acceptance criteria.
6. **Future test-case list.** Add a short list (in whichever doc file has
   the transition table, or as a shared note) enumerating the concrete
   pytest cases a later phase should write: one per ACK/NACK transition row,
   one for `since_seq=0`+`consumer_id` vs. omitted `since_seq`, and
   (once implemented) one each for a missing/invalid `Authorization` header.

## Risks

- **Risk**: The ACK/NACK transition table, once written down formally,
  makes the `nack_event` non-idempotency and the "NACK after ACK succeeds"
  behavior look like an approved specification rather than a bug, because
  writing it as prose can blur the "documented current behavior" vs.
  "acceptable forever" distinction (Likelihood: medium).
  → **Mitigation**: Per `rules/coding.md`'s "Current behavior" classification
  table, classify the non-idempotent-NACK and NACK-after-ACK rows as
  "Implementation fix required," not "Accepted current specification" —
  and add an explicit one-line pointer in the doc that a future
  implementation requirement, not this plan, would file the corresponding
  code fix. This is written into Design §1 above and must survive into the
  final doc text.
- **Risk**: The auth-model selection (static bearer token) could be
  overridden or second-guessed once an actual implementation phase starts,
  wasting the design-note effort (Likelihood: low-medium, per UNK-03).
  → **Mitigation**: Write the note with recorded rationale and explicitly
  rejected alternatives (mTLS, reverse proxy, etc.) so a future deviation is
  a deliberate, visible decision rather than a silent one.
- **Risk**: This plan could be perceived as re-doing work already covered
  by `plans/done/20260818-184640_plan.md` (same source issue), causing
  confusion about which plan is authoritative (Likelihood: medium — this is
  the exact duplicate pattern flagged by prior workflow cycles).
  → **Mitigation**: The Scope section above explicitly states this plan
  supersedes only the documentation subset of the earlier plan (whose docs
  steps were never executed, verified by direct read of all four target
  docs) and explicitly excludes the earlier plan's blocked
  code-implementation steps. No `issues/{timestamp}_risks.md` is filed for
  this risk since it is fully mitigated by the Scope section's explicit
  boundary statement — it is not left unmitigated.
- **Risk**: A future reader implements the bearer-token auth model directly
  in `scripts/eventbus/config.py` by citing this plan's Design §4 as
  authorization to do so, violating Global Rule 8 (Likelihood: low, but
  high impact if it happens).
  → **Mitigation**: Design §4 and the Scope's Out-of-Scope list both state
  explicitly, in two separate places, that implementation is deferred to a
  future requirement and is not authorized by this plan.

All risks above are mitigated within this plan; no `issues/{timestamp}_risks.md`
file is required.
