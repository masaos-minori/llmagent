## Goal
- Make the `/memory` command behave as `docs/23_agent/agent_07_10_cli-and-commands-slash-commands-memory-other.md` specifies for `list`, `delete`, and `prune` (confirmation before destructive operations, the documented arguments and defaults), align the command registry and the chapter so the `GV-023` contract check passes for `/memory` without an exemption, and close Known Issue `AGENT-013`.

## Priority
Medium

## Scope
- **In-Scope**:
  - `list`: arguments `[n] [--type semantic|episodic] [--pinned] [--query <text>]`, default 20 and at most 200, short IDs in the output; the positional `semantic|episodic`, `--source`, and `--branch` forms are removed.
  - `delete` and `prune`: a `y/N` confirmation before any change (anything but `y` changes nothing); `prune` takes `[--days <n>]` and rejects a non-integer or non-positive value instead of silently using the default.
  - `prune` selects and deletes by `updated_at` instead of `created_at`, as the chapter says ("not updated for n days"), and its confirmation and dry-run counts exclude pinned memories (decided with the requester on 2026-10-16).
  - Update the `/memory` entry of the command registry so its usages are exactly the documented forms.
  - Align the `/memory` chapter wording with the registry rendering where the documented forms differ only in notation (`unpin`, `rebuild`).
  - Remove the `/memory` entry from `_CONTRACT_EXEMPT_COMMANDS`, update the `GV-023` description, and remove `AGENT-013` from the Active Items.
  - Update and add tests for the above.
- **Out-of-Scope**:
  - The JSONL change events, replay, `rebuild`, `reindex`, `pin` limit, and `status` behavior, which are implemented and covered by earlier work (`plans/done/20261015-074949_plan.md`).
  - The undocumented `--dry-run` flag of `delete` and `prune`, which stays as it is (see UNK-02).
  - Making `/memory` asynchronous (see UNK-04), the dead `memory_search` and `memory_show` handlers, and `cmd_memory.py` dispatch.
  - Any compatibility shim for the removed `list` arguments.

## Problem
Verified against the code on 2026-10-16:
- `MemoryDataOps.memory_list` (`scripts/agent/commands/memory_data_ops.py`) accepts a positional `semantic|episodic`, `--source`, `--branch`, `--pinned`, and a limit with default 10; it has no `--type` or `--query`, no maximum, and prints full 36-character IDs. The chapter specifies `[n] [--type …] [--pinned] [--query <text>]`, default 20, at most 200, short IDs.
- `memory_delete` and `memory_prune` act immediately: neither the handlers nor `cmd_memory.py` contain a confirmation (the only `y/N` prompt in the agent is the tool approval in `tool_approval.py`); the module docstring of `cmd_memory.py` says "after confirmation". The chapter specifies a `y/N` confirmation for both.
- `memory_prune` takes a positional day count and falls back to the default when it is not an integer; the chapter specifies `[--days <n>]`.
- The `/memory` registry entry (`command_defs_list.py`) renders `list [semantic|episodic] [--source …] [--branch <branch>] [limit]`, `pin <id>`, `unpin <id>`, `delete <id>`, `prune [days]`, and `rebuild [--confirm] [--allow-loss]`. With the exemption removed, `check_command_contracts` reports 11 errors (6 registered usages not documented, 5 documented forms not registered).
- `prune` decides by age of `created_at` (`SQLiteMemoryDeleteStore.delete_memories_before` and `collect_prunable_ids` in `scripts/db/store_impl.py`), while the chapter says memories "not updated for `n` days"; a recently updated old memory is deleted today. `pin` and `unpin` also set `updated_at` (`pin_ops.py`).
- `count_ops.count_prunable` (used by the current `--dry-run`) counts rows without `AND pinned = 0`, so it overstates what `prune` deletes; the actual deletion excludes pinned memories.
- `AGENT-013` is open in `governance_03`; `tools/check_docs_consistency.py` exempts `/memory` (`_CONTRACT_EXEMPT_COMMANDS = {"/memory": "AGENT-013"}`); the `GV-023` row in `governance_04` states the exemption.
- Already satisfied (verified): dispatch of `status|list|delete|pin|unpin|prune|reindex|rebuild`, `/memory` without arguments running `status`, the disabled-layer message, short-ID resolution (minimum 8 characters, ambiguous and unknown IDs), the pin limit message, pinned memories excluded from `prune` (`pinned = 0` in the SQL), and `rebuild` flags.

## Reason for change
Without a confirmation, a mistyped `/memory delete` or `/memory prune` destroys long-term memory immediately, and the chapter promises otherwise. The contract check is also skipped for `/memory`, so the document and the command can drift unnoticed.

## Implementation intent
- Add a small confirmation helper to `MemoryDataOps` that asks `[y/N]`, treats EOF or any answer other than `y`/`yes` as no, and use it in `memory_delete` and `memory_prune` before the change.
- Rework the argument parsing of `memory_list` and `memory_prune` to the documented forms with explicit validation errors, moving the parsing into small helpers so the high-complexity `memory_list` does not grow.
- Express `--query` through the existing FTS retriever and apply `--type` and `--pinned` to its hits; print the first 8 characters of each ID.
- Update the registry entry to the documented forms, and adjust the chapter only where the notation differs from what the registry can render.
- Take the count shown in the prompt and in `--dry-run` from `collect_prunable_ids` (pinned excluded) instead of `count_prunable`, and switch both queries of the delete store to `updated_at`.
- Then remove the exemption, close `AGENT-013`, and update the `GV-023` text.

## Design
Path B (10 target files, a public command contract change). Architecture analysis: `memory_data_ops.py` is imported by `cmd_memory.py` only; `command_defs_list.py` is read by the registry, the help output, and `tools/check_docs_consistency.py`; no new imports cross a layer (`lint-imports`: 6 contracts kept). Baseline: `memory_list` cyclomatic complexity D (26), so the new argument parsing goes into small helper functions (a list-options parser and a confirmation helper) instead of growing it; `memory_delete` and `memory_prune` are B (9). The confirmation helper prints a prompt, reads one line with `input`, and returns true only for `y` or `yes`; EOF and any other answer return false. `memory_prune` counts the prunable entries first (the existing counter) and shows the count in the prompt. `memory_list` resolves `--query` through the retriever, applies `--type` and `--pinned`, truncates to `n`, and prints the first 8 characters of each ID. The registry entry is rewritten with the documented usages; the chapter is adjusted for notation only. The exemption table in the checker becomes empty and a test pins that.

## Risks
- **Risk**: Removing `--source`, `--branch`, and the positional type from `list` breaks existing users of those forms. → **Mitigation**: the chapter never documented them, and the decision to follow the documents was made with the requester; the tests assert the rejection.
- **Risk**: Pruning by `updated_at` changes which memories are deleted (fewer: a memory touched by an update, pin, or unpin is retained). → **Mitigation**: this follows the chapter and is the safer direction; the test pins both a recent-update retention case and an old-update deletion case.
- **Risk**: A synchronous `input()` stalls the event loop during a confirmation (UNK-04). → **Mitigation**: the prompt is short and interactive only; revisit with an asynchronous handler if background tasks suffer.
