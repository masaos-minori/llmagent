## Goal
Make the `now_iso` and `now_iso_raw` tests in `tests/shared/test_json_utils.py` independent of the wall clock, so a second boundary or UTC midnight falling inside a test can no longer fail CI, without changing any production code.

## Priority
Medium

## Scope
- **In-Scope**:
  - `tests/shared/test_json_utils.py`: rewrite the three clock-boundary-sensitive tests (`test_now_iso_consistent_across_calls_same_second`, `test_now_iso_raw_consistent_across_calls_same_second`, `test_now_iso_date_changes_at_midnight`) against a frozen clock, add explicit boundary tests, and replace the two 1.1 s real sleeps with frozen-clock advances. (`tests/shared/test_json_utils.py`)
- **Out-of-Scope**:
  - Changing `shared.json_utils.now_iso` / `now_iso_raw`, `scripts/eventbus/json_utils.py`, or any caller.
  - Auditing the rest of the suite for other time-dependent tests (a separate issue if found).
  - CI configuration, test retries, or quarantining tests.
  - Adding a dependency (`freezegun` is already a dev dependency).

## Background
- CI run `39406860045` (commit `df00f7e2b`) failed with one failure out of 9662 tests: `tests/shared/test_json_utils.py::TestNowIso::test_now_iso_consistent_across_calls_same_second` raised `assert '2026-10-20T10:22:49Z' == '2026-10-20T10:22:50Z'`. The next run (`e8d7d96b9`) passed in full; the commits in between changed only `deploy/` shell scripts and a CI workflow.
- `now_iso()` formats `datetime.now(UTC)` as `%Y-%m-%dT%H:%M:%SZ`, so it has one-second resolution; `now_iso_raw()` returns `isoformat()` with microseconds.
- Related history: `issues/done/20260927-075303_test002_flaky-tests-observed-in-full-suite-run.md` covered other flaky tests and does not mention `json_utils`. No open issue under `issues/` touches this file.

## Problem
- `test_now_iso_consistent_across_calls_same_second` calls `now_iso()`, sleeps 10 ms, calls it again, and asserts equality. A second boundary inside that 10 ms window fails it (about 1 run in 100, derived from the sleep length against the one-second resolution, not measured).
- `test_now_iso_raw_consistent_across_calls_same_second` has the same shape on the first 19 characters of `now_iso_raw()`.
- `test_now_iso_date_changes_at_midnight` compares the date of a `now_iso()` result with a date read from a separate clock call, so UTC midnight between the two calls fails it. Its name also promises a rollover check that its body does not perform.
- All three were reproduced deterministically with a frozen clock during planning (see Design), so the exposure of the two unobserved tests is demonstrated, not assumed.

## Reason for Change
- A red CI run costs a re-run and hides real failures. The fix is small, local to one test file, and uses a library the repository already declares and already uses in tests (`tests/tools/test_check_workitem_traceability.py`).

## Implementation Intent
- Verify the intended properties against a controlled clock instead of the real one: within one frozen second two calls are equal; across a second boundary they differ; the date rolls over at midnight. Use `freeze_time` as a context manager so the clock is restored when each test ends.
- Keep format-only tests unchanged, since they do not depend on the clock value.
- Do not change `now_iso`, `now_iso_raw`, or documented behavior.

## Requirements
- `REQ-001`: `test_now_iso_consistent_across_calls_same_second` no longer depends on real elapsed time or a second boundary, and a new boundary test asserts that two `now_iso()` calls on either side of a second boundary differ. (`tests/shared/test_json_utils.py`)
- `REQ-002`: `test_now_iso_raw_consistent_across_calls_same_second` is made deterministic the same way, and a new boundary test asserts the 19-character prefix of `now_iso_raw()` differs across a second boundary. (`tests/shared/test_json_utils.py`)
- `REQ-003`: `test_now_iso_date_changes_at_midnight` is rewritten to assert the date from a frozen instant just before UTC midnight and from the instant after it, so it actually checks the rollover and cannot straddle midnight. (`tests/shared/test_json_utils.py`)
- `REQ-004`: `test_now_iso_time_changes_over_time` and `test_now_iso_raw_time_changes_over_time` advance a frozen clock instead of sleeping 1.1 s, preserving their intent that the value follows the clock. (`tests/shared/test_json_utils.py`)

## Design
Path A (one modification-target file; no public/runtime interface change; no database schema). The design is grounded in Step 3's direct verification and a planning probe.

**Why a frozen clock.** The properties under test belong to `now_iso`'s format and truncation, not to elapsed time. A frozen clock lets the tests state them exactly: calls within one frozen second return the same string; advancing past a second boundary changes it; advancing past midnight changes the date.

**Probe result (planning, not committed).** With `freeze_time("2026-10-20 10:22:49.995")`:
- advancing 2 ms keeps `now_iso()` equal; advancing a further 10 ms crosses into `…:50Z` and makes it differ;
- the old test shape (read, advance 10 ms, read, assert equal) fails, matching the CI failure text;
- the `now_iso_raw` 19-character prefix differs across the same boundary;
- at `23:59:59.999`, a `now_iso()` result and a later `datetime.now(UTC)` read give different dates after a 2 ms advance, reproducing the midnight shape.

This also shows `freeze_time` reaches `shared.json_utils`, which does `from datetime import UTC, datetime`.

**Test shape.** Use `with freeze_time(<start>) as frozen:` and `frozen.tick(delta=timedelta(...))` inside each test, so the clock is restored on exit and no test can leak a frozen clock into another. For the same-second tests choose a start well inside a second (for example `.100`) so they stay deterministic; add separate boundary tests that start at `.995`. Keep the existing test names where the name still states a true property; the midnight test's name now matches its body because it checks the rollover.

**Time-changes tests.** `test_now_iso_time_changes_over_time` and its raw twin are not flaky (a 1.1 s sleep always crosses a second); replacing the sleeps with `frozen.tick(delta=1.1 s)` preserves the intent and removes about 2.2 s of real waiting from every run, as the issue asks to decide.

**Deploy.** No file under `scripts/` or `config/` changes, so no deployment step applies.

**Adversarial verification (corrected understanding vs. the issue's wording).**
- The issue states the three tests share a cause "by construction"; the probe turned that into a deterministic reproduction for each, so the Plan treats the two unobserved tests as confirmed exposures.
- The issue lists the two 1.1 s sleeps as "decide"; the Plan decides to replace them (REQ-004) because the intent is preserved and the saving is certain, while stating they are not a flakiness source.
- The issue's baseline claim "runs no slower than before" is made concrete: the baseline is 160 tests in 3.66 s, of which the four sleeps account for about 2.2 s plus 0.02 s.

## Risks
- **Risk**: A frozen clock leaks into other tests if applied with a decorator, module-level fixture, or an unclosed `start()`. → **Mitigation**: use `with freeze_time(...)` context managers inside each test so the real clock is restored on exit; the 20-run loop and the full suite would expose a leak.
- **Risk**: Rewriting the tests weakens what they assert. → **Mitigation**: keep the intended property for each (equality within a second, difference across one, date rollover) and add explicit boundary tests, so coverage of the behavior increases.
- **Risk**: `freeze_time` fails to reach `shared.json_utils` because it imports `datetime` by name. → **Mitigation**: verified in a planning probe that it does; the new tests assert on the frozen values, so a regression would fail immediately.
- **Risk**: Other time-dependent tests elsewhere in the suite remain flaky. → **Mitigation**: out of scope here; file a separate issue if found, rather than widening this change.
