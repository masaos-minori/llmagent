# Plan: Config dataclass cleanup (remaining items) — unwired field, validation gap, hardcoded LLM params

## Goal
Close the three config-cleanup gaps that a prior cycle on the same source
issue (`issues/20260817_07_issue.md`) left unaddressed —
`agent_memory_max_startup_snippets` unwired from toml (item 1),
`MemoryConfig` validation split across construction paths (item 4), and
hardcoded compression LLM parameters (item 6) — and additionally align
`InjectionPolicy.min_importance`'s default with `MemoryConfig`'s (item 5),
strengthening beyond the prior cycle's "no change needed" call so direct
construction and the factory-built path agree by default, not just at
runtime.

## Scope

**In-Scope:**

## Design
For each remaining item, this plan adopts the requirement's recommended
direction:

- **Item 1 — wire, not remove.** `agent_memory_max_startup_snippets` is
  actively read at `startup.py:637` with real runtime effect (memory
  snippet truncation at session start). The requirement frames "wire" vs
  "remove" as the open decision; this plan wires it, because the field is
  not dead — it is a legitimate operator-tunable knob that is currently
  impossible to override. Wiring means adding one
  `_get_int_or_default(cfg, "agent_memory_max_startup_snippets", 10)` call
  in `config_builders.py::build_agent_config` and passing it into the
  `AgentConfig(...)` constructor call, mirroring how every other
  `AgentConfig`-level scalar (e.g. `otel_enabled`, `structured_log`) is
  already built and passed as a local variable before the `return
  AgentConfig(...)` statement.

- **Item 4 — move validation into `__post_init__`, keep build-path errors
  only if operationally distinct.** Add four new validator functions to
  `config_validators.py` (`validate_memory_max_inject_semantic`,
  `validate_memory_max_inject_episodic`, `validate_memory_embed_timeout_sec`,
  `validate_memory_retention_days`), each following the existing
  `validate_memory_fts_limit`-style signature (`cfg: MemoryConfig`, single
  `ValueError` raise with an f-string message matching the *exact* wording
  already used in `config_builders.py`'s `ConfigReloadValidationError`
  raises, so the error message an operator sees does not change even
  though the exception type does for the build path — no, exception type
  is decided next). Call all four from `MemoryConfig.__post_init__`
  alongside `_v_mem_fts`/`_v_mem_rrf`/`_v_mem_rec`. In `config_builders.py`,
  remove the four inline `if ... < 0: raise ConfigReloadValidationError(...)`
  blocks in `_build_memory_config` since `MemoryConfig(...)` construction
  (which `_build_memory_config` still performs) now raises `ValueError` via
  `__post_init__` for the same conditions — per the source requirement's
  Implementation instructions §3, a distinct `ConfigReloadValidationError`
  type is only worth keeping if reload-specific error handling depends on
  catching that exact type; grep confirms `config_reload.py` catches
  `ConfigReloadValidationError` broadly around the whole reload build call
  (not per-field), so a `ValueError` from `MemoryConfig.__post_init__`
  during a reload-triggered `_build_memory_config` call will surface as an
  uncaught `ValueError` unless the reload path's catch clause is widened.
  This plan's implementation step therefore keeps `_build_memory_config`
  wrapping its call to `MemoryConfig(...)` (or the reload caller's existing
  try/except) so a `ValueError` raised from `__post_init__` is re-raised as
  `ConfigReloadValidationError` for reload callers, preserving the reload
  path's existing error contract while making `MemoryConfig`'s own
  invariants self-enforcing regardless of construction path.

- **Item 5 — align the default, superseding the prior "no change needed"
  call.** The prior implementation cycle concluded no change was needed
  because `factory.py` always passes the explicit value. This plan's
  source requirement explicitly asks for the default itself to be
  corrected (`0.5` -> `0.3`) so that any *direct* construction of
  `InjectionPolicy()` (tests, future code) matches production behavior by
  default rather than only when routed through the factory. This is a
  one-line default change with no behavioral impact on the current
  factory-built path (unchanged: factory always overrides the default).

- **Item 6 — promote to `LLMConfig`, following the `title_llm_*`
  pattern.** Add `llm_compress_temperature: float = 0.3` and
  `llm_compress_max_tokens: int = 300` to `LLMConfig`, wired through
  `_build_llm_config` exactly like `title_llm_temperature` /
  `title_llm_max_tokens` (same `_get_float_or_default` /
  `_get_int_or_default` calls, same defaults preserving current hardcoded
  behavior). `factory.py::_build_history_manager` reads
  `ctx.cfg.llm.llm_compress_temperature` /
  `ctx.cfg.llm.llm_compress_max_tokens` instead of the module constants;
  the module constants `_COMPRESS_TEMPERATURE` / `_COMPRESS_MAX_TOKENS` at
  `factory.py:43-44` are removed (no longer referenced) rather than kept
  as an unused fallback, since `LLMConfig`'s own field defaults now serve
  that role. No new validators are added for the two new fields, matching
  the unvalidated `title_llm_*` sibling fields already in `LLMConfig`.

## Risks
- **Risk**: Removing the inline `ConfigReloadValidationError` raises in
  `_build_memory_config` (item 4) could silently change the exception
  type surfaced to `/reload` callers if the reload path's error handling
  specifically matches on `ConfigReloadValidationError` rather than a
  broader `Exception`/`ValueError` catch (likelihood: medium — this is
  exactly the kind of behavior change the source requirement's Acceptance
  criteria warns against: "No existing test regresses"). **Mitigation**:
  before removing the inline raises, grep
  `config_reload.py`/`repl_health.py`/related test files for
  `except ConfigReloadValidationError` to confirm the catch is broad
  enough (e.g. wraps the whole `build_agent_config` call) that a
  `ValueError` from `MemoryConfig.__post_init__` is still caught and
  reported the same way; if the catch is narrow, either widen it or wrap
  the `_build_memory_config` call site to convert `ValueError` ->
  `ConfigReloadValidationError` explicitly, as noted in Design/Implementation
  step 3.
- **Risk**: Wiring `agent_memory_max_startup_snippets` (item 1) changes
  behavior for any operator whose toml already sets this key expecting it
  to be silently ignored (likelihood: low — a key that has always been
  inert is unlikely to be deliberately set to a non-default value in
  production config, but cannot be ruled out without checking deployed
  `config/agent.toml`). **Mitigation**: grep
  `config/agent.toml` and any `config/*.toml.example` files for
  `agent_memory_max_startup_snippets` before implementing; if present with
  a non-default value, flag to the maintainer for explicit confirmation
  that the newly-effective value is intended.
- **Risk**: Removing now-unused `_COMPRESS_TEMPERATURE` /
  `_COMPRESS_MAX_TOKENS` module constants (item 6) could break an external
  test or doc that imports them directly (likelihood: low). **Mitigation**:
  Phase 6's stale-reference sweep (`rg "_COMPRESS_TEMPERATURE|_COMPRESS_MAX_TOKENS"`)
  covers `scripts/` and `docs/`; extend the same grep to `tests/` before
  removing the constants.
- **Risk**: This plan's scope determination (items 2/3 already resolved,
  items 1/4/5/6 remaining) rests on this cycle's source-reading; if a
  *third*, still-more-recent cycle already addressed items 1, 4, or 6
  between this plan's authoring and its implementation, the plan could
  become partially redundant again (likelihood: low given no other
  `requires/`, `plans/`, or `implementations/` file currently references
  `issues/20260817_07_issue.md` beyond the two cycles already found in
  this session). **Mitigation**: re-run `grep -rl "20260817_07"
  requires/done/*.md plans/done/*.md implementations/done/*.md` at the
  start of the implementation phase to catch any newer cycle before
  starting work.
