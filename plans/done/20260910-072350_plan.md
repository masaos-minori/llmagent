# Centralize and validate EventBus operational thresholds

## Goal

Centralize the three hardcoded EventBus operational thresholds (slow-consumer threshold, subscriber queue capacity, and backlog health threshold) into `EventBusConfig` with validated relationships between them, so tuning requires editing one source rather than three separate modules. Preserve today's hardcoded values as defaults so behavior is unchanged unless an operator explicitly reconfigures them.

## Priority
Low

## Scope
- **In-Scope**: Adding `slow_consumer_threshold`, `subscriber_queue_maxsize`, and `backlog_health_threshold` fields to `EventBusConfig` with safe defaults matching today's hardcoded values; validating relationships in `__post_init__`; updating callers (`broker.py`, `health_route.py`) to read thresholds from config instead of module-level constants; updating documentation.
- **Out-of-Scope**: Deriving threshold values from load-test measurement (EB-M05). Backpressure disconnect behavior itself (EB-H02). Changing the DLQ sweep interval (`_DLQ_INTERVAL = 60.0` in `app.py`) — this is already centralized in one place per the issue's own analysis.

## Background

Confirmed by direct read: `EventBusConfig` (`config.py` lines 29-54) has fields for `port`, `db_path`, `storage_dir`, `offsets_dir`, `deadletter_dir`, `max_retry`, and `host` only — none of the three thresholds above are represented. There is no `_DLQ_INTERVAL`-style constant review needed for the sweep interval, since `app.py`'s `_DLQ_INTERVAL = 60.0` (line 52) is already a single named module constant (not duplicated elsewhere) — memo4.md's "DLQ sweep interval" mention refers to this constant, which is arguably already centralized in one place, though not yet in validated configuration.

## Problem

Tuning any of these values today requires editing source in three different files with no single place that validates their relationships are sensible (e.g. nothing currently prevents setting the slow-consumer threshold above the queue's own `maxsize`, which would make the health check's slow-consumer branch unreachable in practice). This makes tuning inconsistent and can produce misleading health status if the values drift out of a sane relationship.

## Reason for change

Create one validated source of truth for operational thresholds. Values that affect capacity and alerting should be configurable where necessary, have safe defaults, and fail validation when their relationships are invalid.

## Implementation intent

Inventory all hardcoded EventBus operational thresholds (`_SLOW_CONSUMER_THRESHOLD`, queue `maxsize`, health's backlog threshold, and the already-single-instance `_DLQ_INTERVAL`). Move the tunable ones into `EventBusConfig` with documented rationale and safe defaults matching today's hardcoded values (so behavior is unchanged unless an operator explicitly reconfigures them). Validate relationships such as slow-consumer threshold being below queue capacity, and backlog threshold not exceeding queue capacity, in `EventBusConfig.__post_init__` alongside the existing `port`/`max_retry`/`host` validations.

## Requirements

- `REQ-001`: Add `slow_consumer_threshold`, `subscriber_queue_maxsize`, and `backlog_health_threshold` fields to `EventBusConfig` with defaults matching today's hardcoded values (100, 1000, 500 respectively).
- `REQ-002`: Validate relationships in `EventBusConfig.__post_init__`: slow-consumer threshold < queue capacity, backlog threshold <= queue capacity.
- `REQ-003`: Update `broker.py` to read `slow_consumer_threshold` and `subscriber_queue_maxsize` from config instead of using module-level constants.
- `REQ-004`: Update `health_route.py` to read `backlog_health_threshold` from config instead of the hardcoded value.
- `REQ-005`: Update `docs/06_eventbus_05_configuration-and-operations.md` to document each threshold's rationale, default, and validated relationship to the others.

## Design

### Task-size classification: Path B

This task affects > 3 files, changes public/runtime interface (adds config fields that affect `EventBroker` construction), and modifies configuration contracts. Full architecture analysis, dependency graphing, historical analysis, and operational dependency inspection are performed per Path B rules.

### Architecture analysis

The EventBus has two layers of configuration:
1. **Startup configuration** (`EventBusConfig` + TOML): loaded at process startup, validates port/retry/host constraints.
2. **Runtime constants** (module-level in `broker.py`, inline in `health_route.py`): not configurable, not validated against each other.

This plan moves layer 2 into layer 1, making runtime constants derive from startup configuration. This eliminates the inconsistency gap where values could drift out of sane relationships.

### Dependency graphing

```
app.py ──► load_config() ──► EventBusConfig (new: threshold fields)
   │                              │
   ├─► EventBroker(├──► broker.py (reads config for threshold values)
   ├─► _dlq_loop()                  (reads config for queue maxsize)
   └─► health_check() ──► health_route.py (reads config for backlog threshold)
```

Key dependency: `EventBroker` must receive config (or its derived values) to replace hardcoded constants. Currently `EventBroker.__init__` takes no parameters — this is a breaking change to the internal API.

### Historical analysis

- `_SLOW_CONSUMER_THRESHOLD = 100` was introduced as a module-level constant with no documented rationale.
- `asyncio.Queue(maxsize=1000)` was set without documentation of why 1000 was chosen.
- `max_queue_depth >= 500` in health checks has no documented relationship to the 1000 queue size.
- No prior attempt to centralize these values exists — this is the first consolidation effort.

### Operational dependency inspection

- Adding config fields requires updating the TOML config file (either manually or via migration).
- Changing `EventBroker.__init__` signature affects all call sites in `app.py`.
- The DLQ sweep interval (`_DLQ_INTERVAL = 60.0`) is explicitly out of scope per the issue.
- Backpressure disconnect behavior (EB-H02) depends on queue overflow detection — this change does not alter the overflow mechanism itself, only how the threshold is configured.

### Design decisions

1. **Config field addition (REQ-001)**: Add three new fields to `EventBusConfig`:
   - `slow_consumer_threshold: int = 100`
   - `subscriber_queue_maxsize: int = 1000`
   - `backlog_health_threshold: int = 500`
   
   These match today's hardcoded values exactly. The dataclass is frozen=True, so defaults are settable only through `__post_init__` or field defaults.

2. **Relationship validation (REQ-002)**: In `__post_init__`, after existing validations:
   - `slow_consumer_threshold < subscriber_queue_maxsize` (strictly less — a consumer at exactly the queue capacity is not yet "slow")
   - `backlog_health_threshold <= subscriber_queue_maxsize` (at most equal — a backlog equal to queue capacity is the worst case)
   
   Raise `ValueError` with actionable messages naming both conflicting values.

3. **Broker refactoring (REQ-003)**: Since `EventBroker.__init__` currently takes no parameters, add a `config: EventBusConfig` parameter. Replace:
   - `_SLOW_CONSUMER_THRESHOLD` usage → `self._slow_consumer_threshold = config.slow_consumer_threshold`
   - `asyncio.Queue(maxsize=1000)` → `asyncio.Queue(maxsize=config.subscriber_queue_maxsize)`
   
   Update `app.py`'s `EventBroker()` call to pass `cfg`.

4. **Health route refactoring (REQ-004)**: Replace the inline `500` literal with a config-derived value. Two options:
   - Pass config to the health check function (requires changing the FastAPI dependency injection)
   - Store the threshold on the broker (preferred — `broker.backlog_health_threshold`), since the broker already knows its own queue sizes
   
   Option 2 avoids changing the health endpoint's dependency injection contract.

5. **Documentation update (REQ-005)**: Update `docs/06_eventbus_05_configuration-and-operations.md`:
   - Add the three new fields to the Configuration Fields section
   - Document the validation rules between them
   - Update the Delivery Operations section to state thresholds are now config-driven

## Risks

- **Risk**: Changing `EventBroker.__init__` signature breaks any external callers beyond `app.py`. → **Mitigation**: Verify all call sites before merging; `EventBroker` is an internal class (no public API contract), but confirm no third-party code imports it directly.
- **Risk**: Existing TOML configs lack the new threshold fields, causing `load_config()` to fail. → **Mitigation**: Use `data.get("field", default_value)` pattern in `load_config()` so missing fields fall back to safe defaults.
- **Risk**: The validation order in `__post_init__` matters — if one validation fails, subsequent validations may raise confusing errors. → **Mitigation**: Validate in dependency order: queue capacity first, then slow-consumer threshold against it, then backlog threshold against it.
