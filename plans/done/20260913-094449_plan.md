  request to it regardless of the caller's token.

N/A: covered by Problem.

## Problem
`_ROUTE_ROLE_MAP` maps a path prefix to the role(s) allowed to call it, and
`require_role`'s `_check_role` resolves the caller's role by checking
`request.url.path.startswith(route_path)` against each key in map order. The map
defines `/ack` as a key, but the endpoint's actual route is
`/events/{event_id}/ack` (`scripts/eventbus/app.py`'s `ack_event` handler) —
`/events/...` never starts with `/ack`, so no entry matches and the fallback
`raise HTTPException(status_code=403, detail="Forbidden: unknown route")` fires
unconditionally.

## Reason for change
Confirmed by repository evidence: running `tests/eventbus/test_eventbus_ack_endpoint.py`
and `tests/eventbus/test_eventbus_ack_nack.py` shows every request to
`/events/{event_id}/ack` returning 403 even with a valid, correctly-scoped consumer
token — the ack endpoint is unusable end-to-end in the current codebase, not only in
tests.

## Implementation intent
Add a `_ROUTE_ROLE_MAP` entry whose key matches `/events/{event_id}/ack`'s path prefix
(`/events`), mapped to `Role.CONSUMER`, without changing the existing prefix-match
lookup mechanism (`_check_role`'s in-order `startswith` scan) itself.

## Requirements
- `REQ-001`: `_ROUTE_ROLE_MAP` in `scripts/eventbus/auth.py` must include an entry
  that matches `/events/{event_id}/ack`'s path prefix, mapped to `Role.CONSUMER`,
  without altering the roles or matching behavior of any existing entry.

## Design
`_ROUTE_ROLE_MAP` is a plain `dict[str, set[Role]]` scanned in definition order by
`_check_role` via `path.startswith(route_path)`. The fix adds one new key
(`"/events"`, or another prefix uniquely matching `/events/{event_id}/ack` without
colliding with an unrelated existing prefix) mapped to `{Role.CONSUMER}`. No change to
`_check_role`'s scan logic, to any other entry's role, or to any route handler is
required — this is a data-only fix to close a mapping gap.
