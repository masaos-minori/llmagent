## Goal
- Eliminate the shutdown-time race between `scripts/eventbus/app.py`'s `_dlq_loop`
  background sweep and `lifespan()`'s `db.close()` call, so the Event Bus process
  never crashes with a Segmentation Fault during shutdown.

## Problem
`lifespan()` starts `app.state.dlq_task = asyncio.create_task(_dlq_loop(app))` on
startup. `_dlq_loop()` calls `sweep_orphans()` via `run_with_db_lock()`, which runs the
actual work through `asyncio.to_thread()` (`scripts/eventbus/route_helpers.py`). On
shutdown, `lifespan()` calls `app.state.dlq_task.cancel()`, awaits it, then immediately
calls `app.state.db.close()`.

`asyncio.Task.cancel()` only delivers `CancelledError` at the next `await` point inside
the coroutine — it cannot stop a `concurrent.futures.Future` that is already running in
a worker thread (a well-known `asyncio.to_thread`/executor limitation). If `_dlq_loop`'s
background thread is mid-execution of `sweep_orphans()` -> `_shared_promote()`
(`scripts/eventbus/dlq.py`) when shutdown begins, `await app.state.dlq_task` can return
(via `CancelledError`) while that thread is still running — and the very next line,
`app.state.db.close()`, closes the SQLite connection out from under it.

## Reason for change
Confirmed by repository evidence: a `pytest tests/eventbus/` run produced `Fatal Python
error: Segmentation fault`, with the crashing thread's stack at the moment of the crash
showing `scripts/eventbus/dlq.py:50 in _shared_promote` (a `db.execute(...)` call) ->
`sweep_orphans` -> `app.py:110 in _sweep` -> `route_helpers.py:99 in _locked`, while a
second thread's stack simultaneously showed `starlette/testclient.py:713 in __exit__`
(the `TestClient` context-manager exit, which triggers `lifespan` shutdown) inside a
test fixture's teardown. This is a process crash — it is not caught by any `except`
clause and takes down the entire interpreter. It would crash the live Event Bus service
the same way in production, not only in a test run.

## Implementation intent
Ensure shutdown genuinely waits for any in-flight `run_with_db_lock`-wrapped work to
finish (not just for the wrapping asyncio coroutine to observe cancellation) before
closing the database connection. `code-implementation` should choose the specific
mechanism (see Design below for the candidates identified during planning) with a
bounded wait so a stuck thread cannot hang shutdown forever.

## Requirements
- `REQ-001`: `app.state.db.close()` must not execute while any `run_with_db_lock`
  invocation started by `_dlq_loop` is still running in its worker thread.
- `REQ-002`: The shutdown sequence must not block indefinitely if a sweep thread is
  stuck — it must have a bounded wait (with a defined, logged fallback behavior if
  the bound is exceeded).

## Design
Candidate mechanisms identified during planning, for `code-implementation` to choose
between (not prescribed here, since each has different trade-offs):
- Have `_dlq_loop` track its own in-flight `run_with_db_lock` call (e.g. hold a
  reference to the underlying thread/future) and have `lifespan()`'s shutdown path
  wait on that reference specifically, with a timeout, before calling `db.close()`.
- Route `db.close()` itself through `get_db_lock()` (the same lock `run_with_db_lock`
  already uses to guard concurrent DB access) so `close()` cannot proceed while a
  sweep holds the lock — bounded by adding a timeout to the lock acquisition used for
  shutdown specifically, so a stuck sweep cannot hang shutdown forever.
- Give `_dlq_loop` a cooperative shutdown signal checked between sweep iterations, in
  addition to (not instead of) whichever of the above ensures the *currently running*
  sweep (not just the *next* one) finishes before `db.close()`.

Whichever mechanism is chosen must satisfy REQ-001 (wait for actual thread completion,
not just coroutine cancellation) and REQ-002 (bounded wait, not indefinite blocking).

- **Risk**: A fix that serializes shutdown on the sweep lock could hang indefinitely
  if the sweep itself is stuck (e.g. on a corrupted DB file) → **Mitigation**: bound
  the wait with a timeout (REQ-002) and log/report when the bound is exceeded rather
  than blocking forever.
- **Risk**: This is a timing-dependent bug; a single passing test run after the fix is
  not strong evidence it is actually resolved → **Mitigation**: require repeated runs
  (AC-1) and a deliberately-forced regression test (AC-2), not just an ordinary pass.
