# Plan: make the turn-task idempotency key globally unique so restarts cannot fail the first turn

## Goal
- Remove the cross-process collision in `tasks.idempotency_key`: today `create_task()` builds `f"{session_id}:{turn_number}"` from the literal `""` the orchestrator passes and a process-local counter, so the first turn of a new REPL run against a retained `workflow.sqlite` aborts with `sqlite3.IntegrityError`.
- Encode a stated uniqueness scope instead of a derived one: `idempotency_key` becomes a globally unique opaque identifier (UUID4) generated in `create_task()`, and `turn_number` is documented as informational metadata rather than identity.

## Priority
High

  - `tests/agent/workflow/test_workflow_state_store.py`: update `TestCreateTask` / `TestUpdateTaskStatus` to the new key semantics and add the cross-restart regression case (same `(session_id, turn_number)` inserted twice, no `IntegrityError`).
  - `tests/agent/workflow/test_workflow_engine.py`: replace the four literal `"s:1"` idempotency-key lookups (`:94`, `:125`, `:142`, `:296`) with the record's returned `task.idempotency_key`.
  - `docs/41_db/db_02_architecture_and_schema-schema-reference.md` §7 and `docs/23_agent/agent_04_03_state-and-persistence-platform-databases.md`: document what the task idempotency key means, its uniqueness scope, and how a retained `workflow.sqlite` interacts with a new session.

## Background
The issue (`issues/20261021-093421_turn001_task-idempotency-key-collides-across-restarts.md`, Priority High) was re-verified against the current HEAD `064e77fd9` after the repository was rebased onto the remastered `origin/master`; every structural claim still holds at new paths and line numbers:

- `Orchestrator._execute_turn` calls `self._workflow_adapter.execute_turn(line, 0.0, "")` (`scripts/agent/orchestrator.py:167-169`); no other production `execute_turn(` call site exists (grep over `scripts/agent/` matches only the adapter definition and this call).
- `WorkflowEngineAdapter.execute_turn` passes `session_id` to `_init_workflow_task` (`workflow_engine_adapter.py:149`) and `_init_workflow_task` calls `create_task(..., session_id=session_id, turn_number=ctx.stats.stat_turns, ...)` (`:269-275`, the counter at `:272`).
- `create_task` takes the composite branch whenever both values are not `None` (`scripts/agent/workflow/task_ops.py:21-24`); `""` is not `None`, so the composite key is always taken on the production path. The `uuid4` branch exists only for `None` inputs.
- `tasks.idempotency_key TEXT UNIQUE NOT NULL` (`scripts/db/schema_sql.py:178`).
- `ctx.stats.stat_turns` is process-local: `RuntimeStats.stat_turns` defaults to `0` (`scripts/agent/context.py:223`), the only increment site is `conversation_state_manager.append_user_message` (`scripts/agent/conversation_state_manager.py:111`), and nothing restores it from any database.
- Nothing on this path catches `IntegrityError` (the only `IntegrityError` catch under `scripts/` is `scripts/agent/memory/ingestion.py:215`).
- `get_task_by_idempotency_key` is defined (`task_ops.py:93`, wrapper `state_store.py:124`) but has **no production caller**; the only lookups are in tests (`tests/agent/workflow/test_workflow_state_store.py`, `tests/agent/workflow/test_workflow_engine.py`). Resume-by-existing-task uses `get_task_by_id` instead (`workflow_engine_adapter.py:279`).

Two corrections to the issue text found during verification (defect class unchanged):

- The first turn of a run inserts `":0"`, not `":1"`: `append_user_message` increments `stat_turns` inside the execute stage, which runs **after** `_init_workflow_task`. Probe output at HEAD: `run1 first key: :0`.
- The issue's operational note (empty `tasks` table, `workflow_schema_version` = 2) is environment state from 2026-10-21 and was not re-checked against `/opt/llm`; it is irrelevant to the code-level defect and is tracked as `UNK-01`.

## Problem
`scripts/agent/workflow/task_ops.py:21-24`:

```python
if session_id is not None and turn_number is not None:
    idempotency_key = f"{session_id}:{turn_number}"
else:
    idempotency_key = str(uuid.uuid4())
```

The composite branch is key-derived from two inputs that together are not unique across process runs: `session_id` is the constant `""` on the only production path, and `turn_number` restarts at `0` in every process. A probe at HEAD `064e77fd9` (temporary file under `/tmp/opencode/`, removed after the run) built the real workflow schema and called the real `create_task`:

```text
run1 first key: :0
run2 first insert raised: IntegrityError : UNIQUE constraint failed: tasks.idempotency_key
uuid-branch key parses as uuid: True
composite lookup used by tests works: True
```

So the second process run against a retained `workflow.sqlite` fails at its first turn. `_init_workflow_task` does not catch the error, `execute_turn`'s `try` block (`workflow_engine_adapter.py:148-152`) does not handle `sqlite3.Error`, and the turn aborts before any stage runs — no answer, no audit trail for the turn body.

The composite key has no consumer either: nothing in production looks a task up by idempotency key (`get_task_by_idempotency_key` callers are tests only), and task reuse across a restart is done by `task_id` (`existing_task_id` path, `workflow_engine_adapter.py:279-287`). The key today therefore only produces the constraint violation it was supposed to prevent.

## Reason for Change
A data-retention-dependent failure that kills the first turn after any restart is indistinguishable from a startup bug for the user, and the repository's contract for this area (issue `Constraints`) requires existing `workflow.sqlite` content to survive rather than be deleted. The identity choice must be fixed at the source, not masked by catching the error at the call site (issue `AI Implementation Instruction`).

## Implementation Intent
Make the key globally unique and say so. `create_task()` generates `idempotency_key = str(uuid.uuid4())` unconditionally — the same mechanism the `None` branch already uses and the only mechanism in the codebase that is unique across runs without new state. `turn_number` stays a recorded column but its docstring role changes to informational metadata with explicitly process-local semantics. The uniqueness scope, the collision outcome (cannot occur by construction; the UNIQUE constraint remains as the backstop), and the relationship between a retained `workflow.sqlite` and a new session are stated in the docstring and the two documents named in Scope.

## Design
**Why a global key, not a fixed composite scope.** The composite key fails because both of its inputs fail to be run-unique: `session_id` is a constant `""` (the caller never passes a real id) and `stat_turns` is process-local. Making the scope correct would require two new pieces of state the codebase does not have — a real session identifier at the `execute_turn` boundary and a persisted, per-session turn counter — and would still need collision resolution for genuine replays. The user decision for this plan (Option B) instead aligns the key with what the system actually uses: `task_id` already carries resume identity (`existing_task_id` / `get_task_by_id`), stage-level duplicate detection lives in `idempotency_ops.py` (`processed_events`), and nothing reads tasks by idempotency key. A UUID4 key therefore makes the constraint inert (backstop) and removes the failure class with a two-line behavior change in the one function that owns key creation. Option A (session-scoped key + DB-seeded counter) and Option C (composite with uuid fallback) were considered and rejected: A adds new persisted state and touches the orchestrator/adapter contracts for a lookup no consumer performs; C keeps a mislabeling key ("same logical turn") across restarts while still relying on uuid fallbacks to avoid the crash.

**Scope statement in code.** The `create_task()` docstring becomes the single statement of the scope: "idempotency_key is a globally unique identifier for this task row (UUID4); it is never derived from caller-supplied fields. `session_id` and `turn_number` are recorded metadata; `turn_number` is a process-local counter (`agent/conversation_state_manager.py`) and is not part of task identity." The existing first line (`"Create a new task record."`) is preserved verbatim to avoid drift in the generated API table (`AC-5`); the scope text starts on the second line.

**What stays.** `execute_turn` / `_init_workflow_task` / `create_task` signatures, the INSERT statement and column list, the UNIQUE constraint, `WORKFLOW_SCHEMA_VERSION`, the resume path, `get_task_by_idempotency_key` and its `state_store` wrapper, and every existing status/stage assertion. No `try/except` is added anywhere (`REQ-006`): the class of collision is removed by construction, and the constraint stays as the backstop against any future key-derivation regression (the mutation test `T-4` pins this).

**Compatibility with retained data.** Old rows (e.g. key `":0"`) keep their values; nothing migrates, because the plan changes only generation, not interpretation. `T-3` proves the mixed-format case: a raw-SQL row with an old composite key and a new task row coexist and remain readable through both lookup functions.
