## Goal
- `/reload` が `LLMConfig`/`RAGConfig`/`ToolConfig` の各フィールドを更新する際、起動時(`__post_init__`)と同じバリデータを再実行し、範囲外の値を拒否する。

## Priority
High

## Scope
- **In-Scope**:
  - `scripts/agent/services/config_reload.py`: `cfg.llm`/`cfg.rag`/`cfg.tool` を直接 `setattr` で変更している箇所を、変更差分を辞書に集約した上で `dataclasses.replace()` により再構築する方式に変更する(サブconfigごとに1回の `dataclasses.replace()` 呼び出しへ集約)
- **Out-of-Scope**:
  - `config_validators.py` の個々の `validate_*` 関数の内容変更(別issue `issues/20260825_config_validators_duplicate_range_checks_issue.md` で対応)

  - 新規バリデーションルールの追加

## Background
`scripts/agent/config_dataclasses.py` は複数のconfig dataclassに `__post_init__` を定義しており、`config_validators.py` の `validate_*` 関数を呼び出している。`ConfigReloadService` は既に構築済みのdataclassインスタンスのフィールドを直接 `setattr` で変更するため、`__post_init__` もバリデータも再実行されない。

## Problem
現在のソースを再確認した結果:
- `cfg.llm`/`cfg.rag`/`cfg.tool` への `setattr` 呼び出しは、`_apply_llm_context_params`・`_apply_tool_params`・`_apply_rag_params`・`_apply_llm_retry_params`・`_apply_llm_prompt_params`・`_apply_sse_reload_params` の複数の関数にまたがって分散している(grep で26箇所確認)。
- `LLMConfig.__post_init__`(line 139-149)、`RAGConfig.__post_init__`(line 165-169)、`ToolConfig.__post_init__`(line 230-237)は、いずれも `validate_*` 関数の呼び出しのみで構成されており、キャッシュ生成・リソースオープン・可変共有状態の初期化などの副作用を一切持たないことを確認した。これにより `dataclasses.replace()` によるこれら3サブconfigの再構築は安全であると判断できる(issue が Option A/B の判断を Plan 生成時に委ねていた Unresolved Question はこれで解決)。
- `validate_*` 関数はすべて `ValueError` を送出する(`config_validators.py` 内で確認)。`ConfigReloadValidationError`(`scripts/agent/services/exceptions.py:17`、`ValueError` のサブクラス)は既に `config_reload.py`・`config_builders.py`・`typed_validators.py` で使われており、`config_builders.py:374` には「`ConfigReloadValidationError` へ変換してリロード経路のエラーハンドリングに使う」という既存パターンが存在する。
- **[REVISED 2026-08-25: adversarial review]** `_apply_llm_prompt_params`・`_apply_sse_reload_params` は `_apply_rag_tool_params()` の子として呼ばれていない。実際の呼び出しグラフ(`config_reload.py:120-135`, `apply_config_dict()`)は `self._apply_rag_tool_params(ctx, new_cfg)`(121行目、内部で `_apply_llm_context_params`・`_apply_tool_params`・`_apply_rag_params`・`_apply_llm_retry_params` の4関数を呼ぶ)→ `_reload_approval_settings`・`masked_fields` 直接代入・`_classify_mcp_server_changes`(122-133行目)→ `self._apply_llm_prompt_params(ctx, new_cfg)`(134行目)→ `self._apply_sse_reload_params(ctx, new_cfg)`(135行目)→ `self._sync_services(new_cfg)`(136行目)の順。つまり `_apply_llm_prompt_params`/`_apply_sse_reload_params` は `_apply_rag_tool_params()` が完了した**後**に、`apply_config_dict()` から独立に呼ばれる。Design で提案されている「`_apply_rag_tool_params()` の末尾で1回だけ `dataclasses.replace()` する」設計のままでは、後から実行される2関数の変更差分を反映できない(またはその2関数のためだけに追加でもう一度 `dataclasses.replace()` を呼ぶ必要が生じ、AC-01が要求する「失敗時は全サブconfigが変更前のまま」という単一トランザクション性が壊れる)。Design/Implementation intent/REQ-004/Implementation steps を、辞書を `apply_config_dict()` レベルで生成し6ヘルパー全てに引き渡し、`_apply_sse_reload_params()` 完了後・`_sync_services()` 呼び出し前(136行目の直前)の1箇所でのみ3サブconfigの `dataclasses.replace()` を行う設計に修正する(詳細は Design 参照)。
- **[REVISED 2026-08-25: adversarial review]** `_apply_llm_prompt_params()`(339-382行目)は `_apply_str(new_cfg, "web_search_url", lambda v: setattr(cfg.rag, "web_search_url", v))`(354行目)を含むが、`web_search_url` は `RAGConfig`(`config_dataclasses.py:153-169`)に定義されたフィールドではない(`config_dataclasses.py` 全体を grep してもフィールド宣言はゼロ件、`_build_rag_config()`(`config_builders.py:249-271`)も `RAGConfig(...)` 構築時にこの引数を渡していない)。現在は素の `setattr()` のためインスタンス属性として動的に生えるだけで動くが、これを `rag_changes` 辞書に含めて `dataclasses.replace(cfg.rag, **rag_changes)` に渡すと `TypeError: __init__() got an unexpected keyword argument 'web_search_url'` が発生し、これは `ValueError` のサブクラスではないため計画の `except ValueError` では捕捉できず、`/reload` がリロード全体で未処理例外を送出して落ちる(現状の「サイレントに受け入れる」よりも悪化する退行)。`web_search_url` は `RAGConfig.__post_init__` のどの `validate_*` にも対応しない(バリデータが存在しない)フィールド外属性であり、本Planの目的(バリデータの再実行)の対象外でもあるため、`rag_changes` から明示的に除外し、現状通り直接 `setattr(ctx.cfg.rag, "web_search_url", v)` で即時適用する(他のrag変更の適用順序に対して非トランザクション的に扱われる点は、現状の `masked_fields` 直接代入と同じ扱いとして許容する)。**追記**: この事象は既に `issues/done/20260825_cfgreload_web_search_url_ghost_attribute_issue.md` として個別に issue 化されており、対応する未処理の sibling plan `plans/20260825-142600_plan.md`(Goal: 消費者が皆無であることを確認した上で `_apply_llm_prompt_params()` から `web_search_url` の diff-apply行を削除する)が存在する。142600 が本Planより先に実装されればこの行自体が削除され本Planの除外対応は不要になり、本Planが先に実装されれば142600は単に直接 `setattr` の1行を削除するだけで、いずれの順序でも競合しない。

## Reason for change
起動時に拒否される値が `/reload` では黙って受け入れられてしまう、起動時とリロード時の不変条件の不一致を解消する。

## Implementation intent
`_apply_llm_context_params`・`_apply_llm_retry_params`・`_apply_llm_prompt_params`・`_apply_sse_reload_params`(`cfg.llm` を変更する箇所)、`_apply_tool_params`・`_apply_llm_prompt_params`(`cfg.tool` を変更する箇所)、`_apply_rag_params`・`_apply_llm_prompt_params`(`cfg.rag` を変更する箇所)を、直接 `setattr` する代わりに変更差分を `dict[str, Any]` に集約するよう変更する。**[REVISED 2026-08-25: adversarial review]** `_apply_rag_tool_params()` は `_apply_llm_prompt_params`/`_apply_sse_reload_params` の親関数ではない(Problem参照)ため、`llm_changes`/`tool_changes`/`rag_changes` の3辞書は `apply_config_dict()`(呼び出し元の最上位)で生成し、`_apply_rag_tool_params()` 経由の4ヘルパーと、`apply_config_dict()` から直接呼ばれる `_apply_llm_prompt_params`・`_apply_sse_reload_params` の両方に明示的な引数として引き渡す。`dataclasses.replace(cfg.llm, **llm_changes)` 等の呼び出しは `apply_config_dict()` 内、`_apply_sse_reload_params()` 完了後・`_sync_services()` 呼び出し前の1箇所にのみ置き、llm/rag/tool それぞれ1回ずつ呼び出して `ctx.cfg.llm` 等を新しいインスタンスに差し替える(6ヘルパー全ての変更を集約した後に1回で差し替えることで、AC-01が要求する単一トランザクション性を保つ)。`web_search_url`(`RAGConfig` の非宣言フィールド)は `rag_changes` に含めず、現状通り直接 `setattr` で即時適用する。`ValueError`(`__post_init__` 内のバリデータ由来)を捕捉し `ConfigReloadValidationError` として再送出し、失敗時は `ctx.cfg` を変更前の状態のまま保持する(部分適用を防ぐため、辞書への集約は行うが実際の差し替えは全フィールド収集後に1回で行う)。

## Design
各 `_apply_*` ヘルパーは、現在の `lambda v: setattr(cfg.llm, "field", v)` パターンを `lambda v: changes["field"] = v` 相当(辞書への書き込み)に置き換える。ヘルパーは呼び出し元(`_apply_rag_tool_params`)と辞書を共有するか、辞書を返す形にリファクタリングする(実装時にどちらが既存コード構造に自然に馴染むか判断する)。`_apply_rag_tool_params()` の末尾:
```
if llm_changes:
    try:
        cfg.llm = dataclasses.replace(cfg.llm, **llm_changes)
    except ValueError as e:
        raise ConfigReloadValidationError(str(e)) from e
```
を llm/tool/rag それぞれについて行う。3サブconfigの検証順序(どれを先に検証するか)は、既存の呼び出し順序(llm context → tool → rag → llm retry → llm prompt → sse)から自然に導かれる完了順とし、恣意的な順序変更はしない。

**[REVISED 2026-08-25: adversarial review]** 上記コード例の設置場所を訂正する。`_apply_rag_tool_params()`(`config_reload.py:213-223`)は `_apply_llm_prompt_params`(334行目で呼ばれるのではなく134行目で呼ばれる)・`_apply_sse_reload_params`(135行目)の親関数ではなく、これら2関数は `apply_config_dict()` から `_apply_rag_tool_params()` 完了後に独立して呼ばれる(Problem参照)。したがって:
- `llm_changes: dict[str, Any] = {}`・`tool_changes: dict[str, Any] = {}`・`rag_changes: dict[str, Any] = {}` は `apply_config_dict()` の冒頭(121行目の `self._apply_rag_tool_params(ctx, new_cfg)` 呼び出しより前)で生成する。
- `_apply_rag_tool_params(ctx, new_cfg, llm_changes, tool_changes, rag_changes)` に3辞書を引き渡し、内部で呼ぶ `_apply_llm_context_params`・`_apply_llm_retry_params`(llm_changes へ書き込み)、`_apply_tool_params`(tool_changes へ書き込み)、`_apply_rag_params`(rag_changes へ書き込み)にもそれぞれ引き渡す。
- `apply_config_dict()` から直接呼ばれる `_apply_llm_prompt_params(ctx, new_cfg, llm_changes, tool_changes, rag_changes)`・`_apply_sse_reload_params(ctx, new_cfg, llm_changes)` にも同じ3辞書(該当するもの)を引き渡す。`_apply_llm_prompt_params()` 内の `web_search_url` の設定(354行目)は `rag_changes` に含めず、`setattr(ctx.cfg.rag, "web_search_url", v)` の直接代入のまま残す(`RAGConfig` の非宣言フィールドのため — Problem参照)。
- 上記コード例の `if llm_changes: try: cfg.llm = dataclasses.replace(...)` ブロック(llm/tool/rag 各1回)は、`_apply_sse_reload_params()` の呼び出し(135行目)が完了した直後・`self._sync_services(new_cfg)`(136行目)呼び出しの直前という、`apply_config_dict()` 内の1箇所に置く。これにより6ヘルパー全ての変更が集約された後に初めて `dataclasses.replace()` が走り、AC-01が要求する単一トランザクション性(失敗時は3サブconfig全てが変更前のまま)が保たれる。
