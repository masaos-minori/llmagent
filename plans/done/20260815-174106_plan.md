# Work Plan: Replace UNKNOWN fallback with UNAVAILABLE in _resolve_health_state()

## Goal
Replace the UNKNOWN fallback in `_resolve_health_state()` with UNAVAILABLE when the registry is None, providing clearer semantics during startup/shutdown phases.

## Scope
- Modify `_resolve_health_state()` in `scripts/agent/services/mcp_status.py`
- Update docstring reference from UNKNOWN to UNAVAILABLE
- Verify no other callers depend on UNKNOWN being returned specifically for the None-registry case

## Assumptions
1. McpServerHealthState.UNAVAILABLE semantically means "server unavailable due to health probe failures" (mcp_health.py:43), NOT "registry doesn't exist"
2. The status table display logic can handle UNAVAILABLE state properly
3. No other code depends on UNKNOWN being returned specifically for the None-registry case

## Unknowns
1. Should we add a new state like NO_REGISTRY or keep UNKNOWN for the "registry doesn't exist" case instead of using UNAVAILABLE?
2. Are there other callers of `_resolve_health_state()` that expect UNKNOWN for the None-registry case?
3. Will the status table display logic render UNAVAILABLE correctly?

## Affected areas
- scripts/agent/services/mcp_status.py
- scripts/shared/mcp_health.py
- Status table display components

## Design
The current `_resolve_health_state()` method returns McpServerHealthState.UNKNOWN when registry is None. This should be changed to return McpServerHealthState.UNAVAILABLE instead, which better represents "no registry available" rather than "unknown state".

## Implementation steps
1. Read `scripts/agent/services/mcp_status.py` and identify the exact location of the UNKNOWN fallback
2. Read `scripts/shared/mcp_health.py` to verify McpServerHealthState.UNAVAILABLE exists and its meaning
3. Search for other callers of `_resolve_health_state()` to ensure they don't depend on UNKNOWN
4. Modify the return statement from `McpServerHealthState.UNKNOWN` to `McpServerHealthState.UNAVAILABLE`
5. Update the docstring on line 49 from "falling back to UNKNOWN" to "falling back to UNAVAILABLE"
6. Verify no other callers depend on UNKNOWN being returned specifically for the None-registry case
7. Run tests to ensure no regressions

## Validation plan
- Unit test for `_resolve_health_state()` with registry=None verifying UNAVAILABLE is returned
- Integration test verifying status table display during startup/shutdown shows UNAVAILABLE for all servers
- Manual verification that no other code depends on UNKNOWN for the None-registry case

## Risks
1. Using UNAVAILABLE for "registry doesn't exist" conflates with "server unavailable due to health probe failures" — consider adding NO_REGISTRY state
2. If other code depends on UNKNOWN for the None-registry case, changing to UNAVAILABLE could break behavior
3. Status table display logic may not handle UNAVAILABLE correctly
