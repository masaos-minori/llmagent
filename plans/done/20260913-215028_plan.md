# Plan: Consolidate duplicate SIGTERM→SIGKILL escalation logic into ProcessTerminator

## Goal
Consolidate the SIGTERM→SIGKILL process termination escalation logic currently duplicated across three locations into a single authoritative implementation in `ProcessTerminator.terminate_with_timeout`.

## Priority
High

## Scope
- **In-Scope**: Remove SIGTERM→SIGKILL escalation logic from `HttpServerLifecycleManager._terminate_with_timeout` and `ShutdownCoordinator.shutdown_all`; delegate both to `ProcessTerminator.terminate_with_timeout`
- **Out-of-Scope**: Refactoring the entire shutdown flow, adding new error handling paths, changing the SIGTERM→SIGKILL escalation timing algorithm

## Background
The SIGTERM→SIGKILL escalation pattern appears in three separate places:

1. `HttpServerLifecycleManager._terminate_with_timeout()` (http_lifecycle.py:132-157): Uses `_do_pgid_terminated()` with pgid-based os.killpg() fallback to proc-level signals.
2. `ProcessTerminator.terminate_with_timeout()` (http_lifecycle_process_terminator.py:125-206): Implements its own SIGTERM→SIGKILL escalation with pgid tracking.
3. `ShutdownCoordinator.shutdown_all()` (http_lifecycle_shutdown_coordinator.py:63-133): Implements its own SIGTERM→SIGKILL escalation with pgid lookup.

Each has slightly different timeout values (RESTART_TERMINATE_TIMEOUT_SEC=3.0s, TERMINATE_TIMEOUT_SEC=5.0s, _SHUTDOWN_TIMEOUT_SEC=30.0s), different poll intervals (0.05s vs 0.1s), and different error handling strategies.

Evidence verified against source:
- `http_lifecycle.py:132-157`: `_terminate_with_timeout` — uses `_do_pgid_terminated` with force=True escalation
- `http_lifecycle.py:164-191`: `_do_pgid_terminated` — pgid-based signal sending with fallback
- `http_lifecycle_process_terminator.py:125-206`: `terminate_with_timeout` — own escalation implementation
- `http_lifecycle_shutdown_coordinator.py:63-133`: `shutdown_all` — own escalation with asyncio.get_event_loop().time()

## Problem
Three independent implementations of the same core operation create:

1. **Inconsistent timeouts**: Different methods use different default timeouts (3.0s, 5.0s, 30.0s), leading to unpredictable shutdown behavior depending on which entry point is used.
2. **Divergent error handling**: One uses `os.killpg()` with fallback to `proc.terminate()/proc.kill()`, another checks `proc.poll()` before signaling, another uses `asyncio.get_event_loop().time()` instead of `time.monotonic()`.
3. **Maintenance burden**: Any fix to the escalation logic must be applied in three places; missing one creates inconsistent behavior.
4. **Potential for resource leaks**: If one path fails to terminate a process group while another succeeds, orphaned child processes may remain.

## Reason for change
Duplicate process termination logic violates DRY and introduces subtle differences in shutdown behavior. A process that exits within 3 seconds under one path may survive until 30 seconds under another, creating operational unpredictability.

## Implementation intent
Make `ProcessTerminator` the sole authority for SIGTERM→SIGKILL escalation. Have `HttpServerLifecycleManager._terminate_with_timeout` and `ShutdownCoordinator.shutdown_all` delegate to `self._process_terminator.terminate_with_timeout(proc, server_key, timeout)` instead of implementing their own escalation. The timeout parameter should be configurable per-call site but share the same underlying escalation mechanism.

## Design
The consolidation approach:

### 1. `HttpServerLifecycleManager._terminate_with_timeout` (http_lifecycle.py:132-157)

Before:
```python
async def _terminate_with_timeout(self, proc, server_key, timeout=RESTART_TERMINATE_TIMEOUT_SEC):
    if proc.poll() is not None:
        return
    used_pgid = await self._do_pgid_terminated(
        self._http_pgids.get(server_key), proc, force=False
    )
    if await self._wait_exited(proc, timeout):
        if not used_pgid:
            logger.warning(...)
        return
    logger.warning("force-killing %r", server_key)
    await self._do_pgid_terminated(
        self._http_pgids.get(server_key), proc, force=True
    )
    ...
```

After:
```python
async def _terminate_with_timeout(self, proc, server_key, timeout=RESTART_TERMINATE_TIMEOUT_SEC):
    if proc.poll() is not None:
        return
    await self._process_terminator.terminate_with_timeout(proc, server_key, timeout)
```

Remove `_do_pgid_terminated` method entirely (lines 164-191) since it becomes unused.

### 2. `ShutdownCoordinator.shutdown_all` (http_lifecycle_shutdown_coordinator.py:63-133)

Before: Inline SIGTERM→SIGKILL loop with `asyncio.get_event_loop().time()`, `_kill_pg`, `_kill_pg_force`.

After: Delegate to `ProcessTerminator.terminate_with_timeout`:
```python
@staticmethod
async def shutdown_all(manager, terminator=None):
    ...
    for server_key, proc in list(procs.items()):
        if proc is None:
            continue
        terminator = terminator or manager._process_terminator
        await terminator.terminate_with_timeout(proc, server_key, _SHUTDOWN_TIMEOUT_SEC)
    ...
```

Add optional `terminator` parameter for testability and dependency injection.

### 3. `ProcessTerminator.terminate_with_timeout` (unchanged)

Remains the single source of truth. No behavioral changes needed.

## Risks
- **Risk**: Removing `_do_pgid_terminated` could break callers that depend on its return value (whether pgid-based termination was used) → **Mitigation**: The caller (`_terminate_with_timeout`) only uses the return value for a warning log message about orphaned children; this information is now implicit in `ProcessTerminator.terminate_with_timeout`'s own logging
- **Risk**: `ShutdownCoordinator.shutdown_all` is a static method — adding a `terminator` parameter changes its signature → **Mitigation**: Make the parameter optional with a default that resolves from `manager._process_terminator`; callers passing `None` get the manager's terminator automatically
- **Risk**: Different poll intervals (0.05s vs 0.1s) between implementations may cause subtle timing differences → **Mitigation**: After consolidation, all callers use `ProcessTerminator`'s interval (0.1s); document this as a known behavioral change
