# Plan: Document reload vs. restart requirements for RuntimeToolRegistry availability

## Goal
Correct misinformation in `docs/04_mcp_03_06_tool-runtime-availability-metadata.md` regarding how configuration reloads affect `RuntimeToolRegistry`'s availability state, and clarify the different restart requirements for agent-level vs. per-server configurations.

## Design
We need to distinguish between two distinct mechanisms:
1. **Policy Application (Hot-reloadable)**: `/reload` can apply safety policies (like `agent_safety_tier` or `requires_approval`) to already-registered tools.
2. **Availability Metadata Rebuild (Requires Restart)**: The core metadata derived from `/v1/tools` (like `enabled`, `disabled_reason`, and `status`) is only refreshed during agent startup when `discover_all()` is called.

Furthermore, we must clarify that per-server configuration changes (e.g., `allowed_dirs`) require restarting the specific MCP server process in addition to the agent.

## Implementation steps
1. **Read `docs/04_mcp_03_06_tool-runtime-availability-metadata.md`** to identify exact locations for edits.
2. **Update "`/v1/tools` as RuntimeToolRegistry Source" section**:
   - Replace or amend the incorrect sentence: "Any changes to tool availability (e.g., due to health degradation, config reload) will be reflected in subsequent `/v1/tools` responses and will cause `RuntimeToolRegistry` to be updated accordingly."
   - State clearly that `RuntimeToolRegistry` is populated once at agent startup via `McpToolDiscoveryService.discover_all()` and that neither `/reload` nor a live-health-check path triggers a rebuild of the registry from a fresh `/v1/tools` fetch.
3. **Add a new subsection: "Reload vs. restart for RuntimeToolRegistry"**:
   - Explain that `/reload` (`_ConfigMixin._cmd_reload()`) uses `ConfigReloadService.apply_config_dict()` to call `RuntimeToolRegistry.apply_policy()`.
   - Clarify that `apply_policy()` only updates policy-derived fields (e.g., `agent_safety_tier`, `requires_approval`, `enabled_for_llm`) and does *not* touch `raw_definition`, `disabled_reason`, or `status`.
   - State that a full agent process restart is required for `RuntimeToolRegistry`'s discovery-derived state (including `/mcp status`'s `DISABLED_REASON` column) to reflect config changes.
   - Note that per-server config files (e.g., `allowed_dirs` in `file_read_mcp_server.toml`) require restarting the MCP server process itself to be picked up.
4. **Add a cross-reference**:
   - Link to `docs/04_mcp_06_17_local-to-production-auth-migration.md#reload-とフル再起動の違い` (or equivalent anchor).
   - Explicitly note that while 06_17 discusses restarts for `[mcp_servers.*]` connection definitions, this note covers the broader requirement for refreshing the `RuntimeToolRegistry` availability snapshot.
5. **Verification**:
   - Manual verification that all claims match the findings in the requirement and the source code logic described.
