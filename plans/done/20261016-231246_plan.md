## Problem
- The central guarantees of ADR-004 (safety and integrity failures are Fail-Fast at startup or Fail-Closed at runtime and are never downgraded to partial availability; Fallback exists only where an Accepted ADR defines it) are not proved for every listed failure class.

- Startup Fail-Fast and runtime Fail-Closed behavior are listed together in one `Partial` row, so a gap in one cannot be seen apart from the other.

## Reason for change
The ADR is Accepted and other ADRs depend on it. Its main guarantees should have evidence a gate can check, or an explicit and reasoned manual-review basis, so the status shown in the ADR and the ADR Index matches what is actually verified.

## Design

This is a documentation-status and test-coverage task. No production code changes are
planned; every requirement is satisfied by adding tests and by editing status/evidence
text only. The one exception is REQ-004, whose deliverable is a recorded decision, not
code.

### Failure-class-to-phase mapping

ADR-004 guarantees split into two phases:

- **Fail-Fast (startup):** the class fails during startup validation and aborts startup
  (for example authentication, authorization, Allowlist, Safety Tier, Config Isolation,
  approval-control establishment, RuntimeToolRegistry initialization, duplicate tool
  ownership, required DB connection).
- **Fail-Closed (runtime):** the class is rejected on the execution path rather than at
  startup.

Phase 1 maps each listed class to the startup-validation symbol that enforces it
(for example `ProductionConfigValidator.validate()` behind Config Isolation and the
strict-default checks, the MCP `required`/auth enforcement behind startup discovery, and
the tool-registry ownership check behind duplicate ownership), and to the existing test
that already covers it. The map is the matrix in REQ-001. The distinction between
Fail-Fast and Fail-Closed is recorded per cell; the current ADR lists both together in
one `Partial` row, which is the gap this separates.

### Automatability gate

A class is added to the test set only when its Fail-Fast or Fail-Closed outcome is
reachable through configuration-isolated fixtures without changing production code and
without opening a production DB. Classes that cannot be reached this way stay manual,
with the reason recorded in the matrix and the ADR Manual Review subsection. This is the
constraint from the issue, applied as the filter between REQ-001 (map all classes) and
REQ-002 (test the automatable ones).

### Partial-availability check (REQ-003)

The check asserts that a safety or integrity failure produces either a startup abort or a
runtime rejection, never a continued partial-availability state, for each matrix class.
Where a class cannot be exercised automatically, the reason is documented instead.

### Fallback-audit decision (REQ-004)

The ADR Manual Review already records why a pattern-based fallback detector would produce
unmanageable false positives. The decision framework: if a bounded registry of permitted
fallbacks can be defined against Accepted ADRs with acceptable false-positive cost,
implement it; otherwise record the manual-release-review decision with its rationale.
This stays within the matrix scope and does not touch ADR-010's policy.

### Preservation guard

All edits to `adr_02_004_environment-failure-handling-policy.md` and `adr_01_index.md`
are limited to status and evidence text. `tools/check_adr_preservation.py` is the gate:
it reports ERROR when a Decision, Invariant, reference, or failure policy text changes,
so REQ-005 and REQ-006 cannot silently alter a protected field.
