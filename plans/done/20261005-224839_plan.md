## Goal
Restore the `"tool"` `error_type` classification for HTTP tool-level errors in `ToolCallResult.from_transport()` so that tool errors are counted by `stat_tool_errors`, match the audit/diagnostics consumers, and agree with the documentation — reverting the regression introduced by commit `3526dcc44`.

## Priority
High

## Scope
- **In-Scope**:
  - Restore `error_type="tool" if is_error else ""` in `ToolCallResult.from_transport()` (`scripts/shared/transport_dto.py`).
  - Update `from_transport()`'s docstring to describe it builds a tool-level result from a successful transport response.
  - Add a new unit test file `tests/shared/test_transport_dto.py` pinning `from_transport()` behavior.
  - Verify the three integration tests pass and no new failures appear in the regression command.
- **Out-of-Scope**:
  - Changing the `error_type` vocabulary ("transport" | "tool" | "").
  - Changing `server_key` handling (`from_transport()` keeps `server_key=""`; the `dataclasses.replace(parsed, server_key=self._server_key)` override in `HttpTransport.call()` stays).
  - Changing the transport error path (`_error_result(..., error_type="transport")`, `_record_transport_error()`, `_handle_lifecycle_error()`).
  - Changing retry logic or health tracking in `HttpTransport` / `ToolTransportInvoker`.
  - Modifying any existing test or documentation file.
  - Renaming or re-scoping `from_transport()`; redesigning `ToolCallResult`.

## Background
- Commit `3526dcc44` changed `ToolCallResult.from_transport()` in `scripts/shared/transport_dto.py` from `error_type="tool" if is_error else ""` to `error_type="transport" if is_error else ""` (`git show 3526dcc44 -- scripts/shared/transport_dto.py` confirms a one-line change bundled into a gate-chain-unification / HTTP-hardening commit whose message does not mention this change).
- The change originated from `issues/done/20261003-152247_transport_dto_default_server_key.md` and procedure `implementations/done/20261003-180548_01_scripts_shared_transport_dto_py.md`. That procedure's premise ("`from_transport()` is specifically for transport-layer results, so `transport` is the correct default") is wrong: no caller overrides `error_type`, and the only caller needs `"tool"`.
- The `error_type` field comment documents the vocabulary: `"transport" | "tool" | ""` (empty on success).
- `docs/22_mcp/mcp_03_03_transport-and-health.md` states tool-level errors (`error_type == "tool"`) are treated as successful transport calls, trigger `record_success()` and increment `stat_tool_errors`; transport errors become `error_type="transport"`.

## Problem
- `ToolCallResult.from_transport()` labels every error result `"transport"`. Its only caller, `HttpTransport._parse_http_response()` (`scripts/shared/http_transport.py:82`), uses it for HTTP 200 responses carrying `is_error: true` — i.e. tool-level errors.
- `ToolTransportInvoker._record_success()` (`scripts/shared/tool_transport_invoker.py:154`) increments `stat_tool_errors` only when `result.error_type == "tool"`. With `"transport"`, HTTP tool errors increment neither `stat_tool_errors` nor `stat_transport_errors` (the latter is incremented only in `_record_transport_error()`, reached only via `TransportError`) — these errors are counted nowhere.
- Downstream consumers read the wrong value: the `tool_exec` audit log (`scripts/agent/tool_runner.py:152`) and `save_transport_failure` diagnostics (`tool_runner.py:159-162`, which now fire for tool errors, writing bogus "transport failure" records). Audit logs and the doc-described grep recipes (`mcp_06_07`, `mcp_06_08`, `mcp_06_13`) misclassify these errors.
- Health state is NOT affected (`_record_success()` still calls `record_success()` regardless of `error_type`).
- Three integration tests fail on master with `assert 'transport' == 'tool'`: `test_agent_mcp_integration.py::test_a05_http_tool_error_increments_stat`, `test_robustness_chaos.py::test_3b2_multiple_error_types_in_same_turn`, `test_robustness_chaos.py::test_3b3_partial_batch_failure`. (Reproduced by execution this session.)
- `tool_cache.py:63` recomputes `"tool"` for cached errors, so a cache-replayed HTTP error already says `"tool"` while the live result says `"transport"` — an internal inconsistency.

## Reason for change
Correctness and observability regression: tool-level errors are misclassified, `stat_tool_errors` is no longer incremented, and the code contradicts `mcp_03_03`. Three integration tests fail on master.

## Implementation intent
Two options were considered; Option A is recommended.
- **Option A (recommended)**: restore `error_type="tool" if is_error else ""` in `from_transport()` and fix its docstring. One-line behavioral change; the single caller needs no change. Restores the pre-`3526dcc44` state the docs and tests were written against.
- **Option B**: keep `"transport"` as the default and override in `HttpTransport._parse_http_response()` (or `call()`) with `dataclasses.replace(..., error_type="tool" if is_error else "")`. Keeps the previous issue's "default is transport" intent but leaves a constructor whose default is wrong for its only use and adds an override every future caller must remember.

Both options yield identical runtime behavior for the audit log, diagnostics, and `stat_tool_errors`; they differ only in where the classification lives. No retry, health, or scheduler logic reads `error_type`, so neither has additional side effects. The owner decides; this Plan encodes Option A.

Tests must not be changed; the three failing tests already encode the expected behavior.

## Design
**Option A (encoded).** `from_transport()` is used by exactly one caller for HTTP 200 `is_error: true` bodies, which are tool-level errors per the docs, the invoker counter, and the three tests. A constructor default of `"transport"` that every caller must override is a trap; restoring `"tool"` makes the default correct for the only use and matches the pre-`3526dcc44` state.

**Why the change is safe.** `error_type` is read only by `tool_runner.py` (audit log line 152, diagnostics lines 159-162) and `ToolTransportInvoker._record_success()` (counter line 154). No retry logic, scheduler, or health registry reads it; MCP-server-side and eventbus `error_type` fields are unrelated vocabularies. Health state is unaffected because `_record_success()` calls `record_success()` regardless of `error_type`. Both options produce identical runtime behavior; A localizes the classification in the DTO constructor rather than the caller.

**Validation quality baseline (this session):** `radon cc scripts/shared/transport_dto.py` → `from_transport` complexity A(2); `bandit -r scripts/shared/transport_dto.py` → 0 issues. Low-risk change.
