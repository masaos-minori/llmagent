## Goal
Reduce `scripts/rag/pipeline.py`'s complexity (587 lines) by extracting config resolution, diagnostics formatting, stage lifecycle management, and DB connection handling into four dedicated modules, and by decoupling `AugmentRefiner` construction and consolidating duplicated search logic — while preserving `RagPipeline`'s exact public API.

## Priority
Medium

## Scope
- **In-Scope**: Extracting `resolve_rag_config()` into `rag/config_resolution.py`; creating a `PipelineDiagnostics` dataclass in `rag/diagnostics.py` and using it internally in `get_diagnostics()` (return type stays `dict`); extracting the stage-execution loop into a `RagPipelineStageLifecycle` class in `rag/stage_lifecycle.py`; making `AugmentRefiner` an optional constructor parameter with lambda callbacks removed; introducing a `RagDatabaseConnection` context manager in `rag/db_connection.py`; consolidating `search_queries()`'s duplicated embedding-fetch-and-search logic with `SearchStage`'s existing `_search_all_queries` helper; updating the two test files that directly assign `RagPipeline`'s private SQLite/refiner attributes; adding a test file per new module.
- **Out-of-Scope**: Adding new pipeline stages or modifying existing stage behavior; changing the RAG pipeline algorithm order (MQE → search → RRF → rerank); modifying `AugmentRefiner`'s internal logic or its HTTP/refiner delegation; caching layers or performance optimizations beyond what the refactor enables; migrating to a different database abstraction layer; fixing the 3 pre-existing, unrelated test failures in `tests/rag/test_rag_pipeline_no_cache_freshness.py` (see Assumptions).

## Background
`scripts/rag/pipeline.py` was originally a thin orchestrator wrapping MQE → search → RRF → rerank stages (confirmed: the module docstring's "Module layout" comment at line 12 still describes four related files: `repository.py`, `llm_client.py`, `pipeline_service.py`, `pipeline_refiner.py`). Over time it accumulated additional responsibilities: `resolve_rag_config()` (confirmed at line 63, a standalone 115-line configuration-resolution function with its own defaults/validation/fallback logic and no dependency on pipeline orchestration), `get_diagnostics()` (confirmed at line 521, constructing a flat dict duplicating fields already available on typed result objects), and tight `AugmentRefiner` coupling in `__init__` (confirmed at line 192: `AugmentRefiner` is constructed with two lambda callbacks, `set_fetch_result` and `set_fallback_reason`, that bypass type safety).

## Problem
`pipeline.py` violates single-responsibility in four confirmed ways:
1. **Config resolution** (`resolve_rag_config()`, line 63) is coupled to pipeline internals despite having no pipeline-orchestration dependency.
2. **Diagnostics formatting** (`get_diagnostics()`, line 521, cyclomatic complexity C/18 per `radon` — the highest in the file) constructs a flat dict with hardcoded keys duplicating `PipelineRunResult`/`SearchDiagnostics` fields.
3. **Tight `AugmentRefiner` coupling** (`__init__`, line 192) uses lambda callbacks and stores 4 SQLite-related attributes (`_rag_db_path`, `_sqlite_vec_so`, `_sqlite_timeout`, `_sqlite_busy_timeout_ms`) that are only used in `augment()` (line 425), which constructs a `SQLiteHelper` inline rather than through a managed factory/context manager.
4. **Duplicated search logic**: `search_queries()` (line 299) and `SearchStage`'s `_search_all_queries` helper (`scripts/rag/stages/search.py:26`) run nearly identical embedding-fetch-and-search loops (confirmed by direct comparison of both implementations).

## Reason for change
- **Maintainability risk**: `pipeline.py` has been modified in 84 commits (`git log --oneline --diff-filter=M -- scripts/rag/pipeline.py`), confirming it is a high-churn file where large, undifferentiated changes carry elevated regression risk.
- **Testability degradation**: unit-testing `RagPipeline.__init__` currently requires mocking HTTP clients, LLM instances, and callback lambdas simultaneously.
- **Type safety erosion**: `get_diagnostics()` returns raw dicts; callers get no static type checking on diagnostic fields.
- **Duplication**: confirmed duplication between `search_queries()` and `SearchStage`'s helper increases the chance the two drift out of sync.

## Implementation intent
Extract the four concerns into dedicated modules while preserving `RagPipeline`'s exact public API (`run`, `augment`, `get_diagnostics`, `search_queries`, `rerank_candidates` all keep their current signatures — required both by the source Issue's Constraints and confirmed necessary because `scripts/mcp_servers/rag_pipeline/rag_pipeline_service.py`, the only production caller, uses `augment()` and would break on a signature change):

1. Move `resolve_rag_config()` to `rag/config_resolution.py` verbatim; `pipeline.py` imports it.
2. Create `PipelineDiagnostics` in `rag/diagnostics.py` mirroring `get_diagnostics()`'s current dict keys exactly (no cumulative counters — see Design decision below); `get_diagnostics()` builds one internally via `PipelineDiagnostics.from_run_result(...)` and converts it back to a `dict` before returning, so its `-> dict` return type is unchanged.
3. Extract the stage-creation-and-execution loop from `run()` into `RagPipelineStageLifecycle` in `rag/stage_lifecycle.py`; `run()` becomes a thin delegator.
4. Make `AugmentRefiner` an optional constructor parameter (default `None`); if not provided, `augment()` constructs one internally. Remove the `set_fetch_result`/`set_fallback_reason` lambda callbacks — use direct attribute assignment after construction instead.
5. Introduce `RagDatabaseConnection` in `rag/db_connection.py`, wrapping the `SQLiteHelper(...).open(row_factory=True)`/close lifecycle currently inlined in `augment()` (line 468-478).
6. Consolidate `search_queries()`'s loop with `stages/search.py`'s `_search_all_queries` helper — `search_queries()` keeps its exact public signature (a hard constraint; see Design decision on the Issue's own Unresolved Question #2) but delegates its internal work to the shared helper instead of duplicating it.

## Design
### Analysis summary
- **Path classification**: Path B (creates 4 new modules; affects 12 target files).
- **Architecture analysis**: `PYTHONPATH=scripts uv run lint-imports` confirms the `rag must not import from agent or mcp_servers` contract is currently `KEPT`; the 4 new modules must preserve this (only import from `db`/`shared`, per `.importlinter`'s documented dependency hierarchy: `rag → db, shared`). An unrelated, pre-existing contract violation (`shared` → `agent`) was found and is out of scope (see Assumptions).
- **Dependency graphing**: `rg -n "RagPipeline\(" scripts/` confirms `scripts/mcp_servers/rag_pipeline/rag_pipeline_service.py` is `RagPipeline`'s only production caller, using only the public `augment()` method. Of the ~13 test files importing `RagPipeline` (`rg -n "from rag.pipeline import" scripts/ tests/`), only 2 directly access the private attributes this refactor moves (confirmed by grepping for `resolve_rag_config|get_diagnostics|_rag_db_path|_sqlite_vec_so|_sqlite_timeout|_sqlite_busy_timeout_ms|_augment_refiner` across all of them) — these 2 are REQ-007's target files; the other ~11 (4 asserting only on `get_diagnostics()`'s dict keys, plus others using only public methods) require no change.
- **Historical analysis**: `git log --oneline --diff-filter=M -- scripts/rag/pipeline.py` returns 84 commits — a high-churn file; implementation steps must stay small and independently revertable (see Risks).
- **Validation quality baseline**: `uv run radon cc scripts/rag/pipeline.py -s` ranks `get_diagnostics` (C, complexity 18) and `resolve_rag_config` (C, complexity 17) as the file's two most complex functions — directly corroborating the Issue's extraction targets. `uv run vulture scripts/rag/ --min-confidence 80` found no dead code in `pipeline.py` itself. `uv run bandit scripts/rag/pipeline.py -c pyproject.toml` found 1 pre-existing Low-severity finding, unrelated to this refactor. Coverage baseline: `uv run coverage report --include="*/rag/pipeline.py"` shows 71% (140/197 statements covered).

### Design decisions
1. **`search_queries()` stays public with its exact signature** (resolves the Issue's own Unresolved Question #2: "Does `search_queries()` need to remain a public method...?"). The Issue's Constraints ("All public method signatures on `RagPipeline` must remain unchanged") and Required Changes ("Preserve backward compatibility: ... `search_queries` ... retain their signatures") settle this in favor of keeping it — only its internal duplication with `stages/search.py`'s `_search_all_queries` helper is consolidated (REQ-006), the method itself is not removed or replaced.
2. **`PipelineDiagnostics` excludes cumulative counters** (resolves the Issue's Unresolved Question #3). Direct reading of `get_diagnostics()`'s current implementation confirms its returned dict does NOT include the cumulative `self.stat_search_embed_failed`/`self.stat_search_fts_errors` counters — only `self.last_search_diagnostics`'s per-run `embed_ok`/`embed_failed`/`fts_errors`/`degraded` fields are included, under the `search_diagnostics` key. `PipelineDiagnostics` must match this exactly to preserve `get_diagnostics()`'s current dict shape (a Constraint, not an option).
3. **`get_diagnostics()`'s return type stays `dict`**, per the Issue's backward-compatibility Constraint on `RagPipeline`'s public method signatures. `PipelineDiagnostics.from_run_result(...)` builds the typed object internally; `get_diagnostics()` converts it back to a `dict` with the identical key set (e.g. via a `PipelineDiagnostics.to_dict()` method) before returning.
4. **`RagPipelineStageLifecycle` accepts `RagConfigImpl`, not `RagConfig`** (resolves the Issue's Unresolved Question #1): `self._cfg` is assigned from `resolve_rag_config()`'s return value, which is already `RagConfigImpl` — passing the already-resolved concrete type avoids an unnecessary cast in the extracted class.

## Risks
- **Risk**: `pipeline.py` is a high-churn file (84 modifying commits); performing this multi-module extraction as one large change increases merge-conflict and regression risk. → **Mitigation**: implement in the 6 small, independently-testable phases above (config resolution → diagnostics → DB connection → stage lifecycle → `AugmentRefiner`/`search_queries`), running the relevant test subset after each phase rather than only at the end.

- **Risk**: `get_diagnostics()`'s dict shape must remain byte-for-byte identical for the 4 read-only test files that assert on specific dict keys. → **Mitigation**: `PipelineDiagnostics`'s field set is derived directly from the current implementation's dict keys (Design decision #2), and Phase 3 explicitly re-runs those 4 files' tests before the phase is considered complete.
- **Risk**: The 3 pre-existing failing tests in `tests/rag/test_rag_pipeline_no_cache_freshness.py` (referencing the already-removed `_ModuleConfig`) could be mistaken for a new regression introduced by this Plan. → **Mitigation**: documented in Assumptions as pre-existing and out of scope; each phase's validation confirms these 3 still fail for the same `_ModuleConfig`-related reason (not a new reason), rather than expecting them to pass.
