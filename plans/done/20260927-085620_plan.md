## Goal
Fix 3 `tests/agent/test_orchestrator.py` tests that all share one confirmed root cause: `Orchestrator.__init__` eagerly constructs a real `WorkflowEngine(...)` instance (`scripts/agent/orchestrator.py:162`) and passes it into `WorkflowEngineAdapter`, which stores it as a fixed `self._workflow_engine` reference (`scripts/agent/workflow_engine_adapter.py:82`) — so any test that patches `agent.workflow_engine_adapter.WorkflowEngine` *after* already constructing the `Orchestrator` has no effect, and the real engine's own retry/halt logic runs instead of the test's intended mock.

## Priority
Medium

## Scope
- **In-Scope**: Restructure all 3 affected tests so the `WorkflowEngine` mock (where one is used) is applied *before* the `Orchestrator`/`_make_orchestrator` call constructs the adapter, or the real engine's retry behavior is otherwise neutralized for the one test that doesn't attempt a mock at all.
- **Out-of-Scope**: `scripts/agent/orchestrator.py`'s eager `WorkflowEngine` construction and `WorkflowEngineAdapter`'s fixed-reference storage — both are normal, unremarkable production wiring; no evidence this needs to become lazier or injectable differently for production use. `agent001`'s `ToolLoopGuard.check_all()` signature failures in the same file — distinct, already-tracked root cause, confirmed unrelated to this one.

## Background
`Orchestrator.__init__` (`scripts/agent/orchestrator.py:162`) constructs `WorkflowEngine(...)` directly and passes it to `WorkflowEngineAdapter.__init__`, which stores it as `self._workflow_engine = workflow_engine` (`scripts/agent/workflow_engine_adapter.py:82`) — a one-time binding, not re-resolved per call. `execute_turn` (`scripts/agent/workflow_engine_adapter.py:144-215`) then calls `self._workflow_engine.run(...)` using this already-bound reference. Two of the three failing tests call `patch("agent.workflow_engine_adapter.WorkflowEngine", return_value=mock_engine_instance)` as a context manager wrapped only around the `await orch.handle_turn(...)` call — but `orch` (via `_make_orchestrator(ctx)`) was already constructed *before* entering that `with` block, so the real `WorkflowEngine` was already instantiated and bound; the patch has no effect on the already-existing `orch._workflow_adapter._workflow_engine`. The third test doesn't attempt to patch `WorkflowEngine` at all, so it directly exercises the real engine's stage-retry logic (`scripts/agent/workflow/workflow_engine.py`, confirmed via the captured log "Task test-task-id: execute attempt 1 failed, retrying in 1s") — which retries a failing `execute` stage, eventually converts a persistent failure into a `WorkflowHaltError`, which `execute_turn`'s own `except (WorkflowHaltError, WorkflowTimeoutError)` block (lines ~199-201) deliberately swallows (`engine_status_handled = True; self._handle_workflow_halt(exc)`) rather than re-raising — so `orch.handle_turn(...)` returns normally instead of ever propagating the test's injected `RuntimeError`.

## Problem
- `test_handle_turn_calls_workflow_engine_run_once`: `mock_engine_instance.run.assert_called_once()` fails (`Called 0 times`) — the real engine's `run()` was called instead, since the mock was installed too late.
- `test_handle_turn_returns_normally_on_genuine_workflow_timeout`: `assert on_error.call_count == 1` fails (`0 == 1`) — same late-mock-installation cause; the real engine's `run()` ran (not `mock_engine.run` with its `WorkflowTimeoutError` side effect), so `_on_error` was never invoked with the intended timeout error.
- `test_original_config_restored_even_on_error`: `Failed: DID NOT RAISE RuntimeError` — the real `WorkflowEngine`'s retry-then-halt logic converts the test's injected `RuntimeError` into a `WorkflowHaltError` that `execute_turn` itself swallows, so `handle_turn` returns normally instead of letting `RuntimeError` propagate.

## Reason for change
All three are confirmed test-construction-ordering/isolation gaps, not production defects: the eager, fixed-reference `WorkflowEngine` wiring is ordinary production design; the tests simply patch (or fail to patch) it at the wrong point in the test's own setup sequence. Fixing them restores real coverage of: the "engine is always invoked" invariant, timeout-driven `_on_error` dispatch, and config-restoration-on-error behavior.

## Implementation intent
For the two mock-based tests, move the `Orchestrator`/`_make_orchestrator(ctx, ...)` construction *inside* the `with patch("agent.workflow_engine_adapter.WorkflowEngine", return_value=mock_engine_instance):` block (or an equivalent earlier-scoped patch), so the mock is in effect when `Orchestrator.__init__` runs and constructs its `WorkflowEngineAdapter`. For the third test, either apply the same real-`WorkflowEngine`-avoidance pattern (construct `Orchestrator` inside a `WorkflowEngine` patch that raises/propagates the injected error without retrying) or explicitly configure a `retry_policy`/workflow definition with `max_attempts=1` so the first failure halts immediately — then further confirm whether `execute_turn`'s swallowing of `WorkflowHaltError` is itself intended to always convert to a non-raising outcome (in which case this test's expectation of a raised `RuntimeError` needs re-examination against that swallowing behavior, not just a retry-count fix — see Unknowns).
