## Goal
Add an operator-triggered `/session rag-rebuild-vec` command that invokes the already-existing `RagMaintenanceService.rebuild_vec()` method, closing the gap where `chunks_vec` rows orphaned by out-of-band deletions (bypassing `ADR-005`'s deletion-order mitigation) can be detected by `check_rag_consistency()` but never actually removed.

## Priority
Low

## Scope
- **In-Scope**: Register a new `/session rag-rebuild-vec` subcommand in `cmd_session.py` that calls `RagMaintenanceService.rebuild_vec()` and reports the result, following the exact pattern already used by `rag-rebuild-fts`; add corresponding tests; update `RAG-005`'s governance entry once verified.
- **Out-of-Scope**: Migrating to a vector store with FK constraint support; changing `ADR-005`'s deletion-order invariant; adding a new detection/identification method (the existing `check_rag_consistency()` orphan detection is reused, not duplicated — see Design); adding a *scheduled/periodic* trigger distinct from the operator-invoked command (see Unknowns).

## Background
`docs/00_governance_03_issue-and-uncertainty-management.md` `RAG-005` ("sqlite-vec does not enforce foreign key constraints on embedding vectors", Status: open, Severity: Low) tracks this gap as "a known, accepted architectural limitation mitigated by deletion ordering, not an active defect being worked." `docs/adr/ADR-005-rag-source-derived-index-relationships.md` establishes the correct deletion order (delete `chunks_vec` before `documents`) as the primary mitigation. The source Issue (`issues/20260914-105248_ragsvc03_orphaned-vector-periodic-cleanup.md`) requested implementing a periodic-cleanup mitigation for the residual case where that order is bypassed (crash mid-deletion, or a direct DB operation outside the normal path).

## Problem
The Issue's original claim was: "no function in `scripts/rag/` or `scripts/db/` actually deletes the orphaned `chunks_vec` rows the check detects," and "`scripts/rag/maintenance.py` (`RagMaintenanceService`) currently implements only `rebuild_fts()`, with no equivalent orphan-vector cleanup method."

**Corrected understanding (Step 2 adversarial verification against current source):**
- The Issue's cited class name/location (`scripts/rag/maintenance.py`'s `RagMaintenanceService`) does not match current source: `scripts/rag/maintenance.py` defines `RagDbMaintenanceService` (`rotate()`, `rebuild_fts()`, `vacuum()`), a *different* class from `scripts/agent/services/rag_maintenance_service.py`'s `RagMaintenanceService` (`stats_rag()`, `rebuild_fts()`, `consistency()`, `recover()`, `rebuild_vec()`, `reconcile_url()`).
- `RagMaintenanceService.rebuild_vec()` (`scripts/agent/services/rag_maintenance_service.py`, lines 66-78) already exists and already removes orphaned `chunks_vec` rows as a side effect of its full-rebuild approach (`DELETE FROM chunks_vec` followed by re-inserting from `chunks WHERE embedding IS NOT NULL` — any row in `chunks_vec` with no matching/valid source is necessarily dropped and not re-inserted).
- However, `rebuild_vec()` has **no caller anywhere in the codebase** (confirmed via `grep -rn "rebuild_vec" scripts/` restricted to non-test, non-memory-module call sites) — it is dead code from a caller-reachability standpoint, unlike `rebuild_fts()`, which is wired to the `/session rag-rebuild-fts` command (`cmd_session.py` `_rag_rebuild_fts()`, dispatch table entries at lines 214-215).
- Therefore the actual gap is narrower and different from the Issue's framing: the cleanup *logic* already exists; what is missing is an **invocation path** (an operator command), not a new cleanup method reusing `check_rag_consistency()`'s detection logic as the Issue's `Implementation Intent` specified.

## Reason for change
Per `RAG-005`'s own stated Impact, an unbounded orphan count degrades vector index size/search performance over time when the deletion-order mitigation is bypassed. `rebuild_vec()` already exists to correct this, but with no command wiring it, an operator has no supported way to invoke it — the correction path exists in code but is unreachable in practice, which is functionally equivalent to the Issue's stated problem (orphans accumulate with no operational remedy), just for a different root cause than originally stated.

## Implementation intent
Add a `/session rag-rebuild-vec` subcommand to `cmd_session.py`'s `_SessionMixin`, mirroring `_rag_rebuild_fts()`'s existing structure exactly (call the service method, print a success message, register in the dispatch table and help text). Do not add a new orphan-cleanup method or reimplement detection — `RagMaintenanceService.rebuild_vec()` already reuses `chunks`/`chunks_vec` state directly and needs no change. Do not add a scheduled/periodic trigger in this Plan (see Unknowns, UNK-01) — only the operator-invoked path, matching `rebuild_fts()`'s existing operational pattern per the Issue's own fallback guidance ("confirm which invocation model fits this codebase's existing maintenance patterns... before adding a new one").
