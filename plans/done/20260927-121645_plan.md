## Background
NC-037 asked whether the current MCP-server-unreachable retry behavior is an intentional simplicity choice or a pending configurable Retry Policy. Issue `issues/20260927-115931_nc037_confirm-whether-a-configurable-mcp-health-check-retry-policy-was-intended.md` found the situation more nuanced than NC-037's original framing: `scripts/agent/services/mcp_health.py` performs a single check with no retry; `scripts/agent/http_lifecycle_health_checker.py::HealthChecker.startup_poll()` implements a configurable retry loop but has zero callers anywhere in `scripts/`/`tests/`.

## Problem
This Plan completed the trace the Issue left open: `rg -n "asyncio.sleep|for attempt|range(.*retr|max_retries" scripts/agent/services/mcp_tool_discovery.py scripts/agent/startup_validation.py scripts/agent/startup_reporter.py scripts/agent/commands/cmd_mcp.py` returns zero matches across all four additional MCP-unreachable-handling-adjacent files (confirmed via `rg -l "unreachable"` first identifying them as relevant, then checking each for retry logic). `scripts/agent/services/mcp_tool_discovery.py`'s `fetch_tools()` (the actual MCP-unreachable detection path used during Agent startup, distinct from `mcp_health.py`'s RAG/embed-LLM-service check) also performs a single attempt with no retry, escalating an unreachable finding directly (`_escalate_unreachable_findings()`). Across every MCP-server-unreachable-handling code path this Plan traced, the uniformly-exercised behavior is "single check, no retry" — the only retry logic anywhere in this area is the orphaned, zero-caller `startup_poll()`.

## Reason for change
The trace is now complete enough to present the owner with an accurate picture: a configurable retry utility exists in the codebase but is not wired into any of the paths that actually handle MCP-server-unreachable conditions today. This is either a deliberate choice (single-check simplicity was the intended policy; `startup_poll()` was built for a different, more general purpose or abandoned) or a genuine gap (retry was intended everywhere and never finished wiring). Only the owner can rule which.

## Implementation intent
Present the completed trace to the owner and record their ruling directly in ADR-004's Implementation Notes, replacing NC-037's stale "single fixed-delay retry" framing with the corrected "no retry on any currently-exercised path; a configurable retry utility exists unused" framing.
