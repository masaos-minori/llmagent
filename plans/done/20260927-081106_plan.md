## Background
`ToolLoopGuard.check_all()` originally took 4 positional arguments after `self`: `(seen_calls, round_fingerprints, failed_calls, message)`. Commit `24e9e9b3` ("feat(agent): implement progress stagnation detection in ToolLoopGuard", 2026-09-20) inserted a new required `round_tool_names: list[frozenset[str]]` parameter between `round_fingerprints` and `failed_calls` — becoming `(seen_calls, round_fingerprints, round_tool_names, failed_calls, message)` — and updated both of `check_all`'s files (`scripts/agent/tool_loop_guard.py`, `scripts/agent/llm_turn_runner.py`) accordingly. That commit touched no test file (confirmed via `git show --stat 24e9e9b3`), so every existing test call site still uses the old 4-argument form. Positionally, each old call's `failed_calls` argument now lands in the `round_tool_names` slot, its `message` argument now lands in the `failed_calls` slot, and the actual `message` parameter is left unsupplied — producing the observed `TypeError`.

## Reason for change
The production code and its one real caller (`scripts/agent/llm_turn_runner.py`) are already correct and consistent with each other (confirmed by Read); only the tests are stale. This is a pure test-side regression from an incomplete follow-up to a legitimate feature commit — leaving it unfixed means 12 tests provide zero coverage of the tool-loop-guard's dedup/cycle/stagnation/retry safety mechanism (a loop-prevention safety feature) via any of these 5 call sites.

## Implementation intent
For each of the 12 failing tests' `check_all(...)` call(s), insert a `round_tool_names` argument in the correct (3rd) position. Default to `[]` for every call, since none of the 12 failing tests assert on progress-stagnation behavior (that behavior is exercised by `tool_loop_guard.py`'s own dedicated stagnation tests, not these 12) — passing `[]` preserves each test's original dedup/cycle/retry-focused intent without introducing stagnation-detection side effects it did not previously exercise. Do not touch production code.
