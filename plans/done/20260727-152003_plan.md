## Goal

Resolve NC-010 and NC-014 by deciding, and specifying, what `tools/gen_rag_reference.py`
should do now that `docs/03_rag_05_configuration_and_operations.md` (its `OPS_DOC`
write target) no longer exists post-split, so that the `AUTO-GENERATED` guard blocks in
`docs/03_rag_05_7-rag-index-consistency-checks.md` and
`docs/03_rag_05_8-rag-mcp-internal-operations-direct-db-access.md` stop implying an
automation that does not run, and the tool itself stops being effectively dead code on
its write path.

## Scope

**In-Scope:**
- Decide the policy for each of the two content types the tool generates:
  - `generate_cli_help()` output (crawler / chunk_splitter / ingester `--help` text)
  - `generate_config_table()` output (keys from `config/crawler.toml`,
    `config/chunk_splitter.toml`, `config/ingester.toml`)
- Update `tools/gen_rag_reference.py` (`OPS_DOC` constant, `main()` write logic) to match
  the decided policy, keeping the existing `GUARD_START`/`GUARD_END` find/replace
  mechanism.
- Resolve both guard blocks consistently:
  - `docs/03_rag_05_8-rag-mcp-internal-operations-direct-db-access.md:84-115` (CLI help)
  - `docs/03_rag_05_7-rag-index-consistency-checks.md:94-96` onward (config table)
- Cover both requirements (`requires/20260727-135407_require.md` NC-010 and
  `requires/20260727-135740_require.md` NC-014) under one coordinated design, since both
  are the same `OPS_DOC` root cause manifesting in two files.

**Out-of-Scope:**
- Actually editing `docs/*.md` content or the `Needs confirmation` prose (NC-010/NC-014
  entries in `docs/00_governance_07_needs-confirmation-inventory.md`) — that happens in a
  later documentation-editing workflow phase, per the requirement's own Implementation
  Instructions §5 note. This plan only specifies what that later edit should say.
  Note: `docs/03_rag_05_1-configuration-reference.md` is read-only reference evidence in
  this plan, not an edit target.
- Restructuring `config/*.toml` files or adding description metadata to TOML keys.
- Changing `check_rag_consistency()` / `/db consistency` behavior (unrelated to this
  tooling fix).
- Making `gen_rag_reference.py` part of CI/pre-commit (not requested; out of scope unless
  a future requirement asks for it).

## Implementation Steps

**Policy decision (recommended, grounded in the evidence above; grounds the steps below):**

1. **CLI-help section — automate it.** Replace the single `OPS_DOC` constant with two
   named targets:
   ```python
   CLI_HELP_DOC = Path("docs/03_rag_05_8-rag-mcp-internal-operations-direct-db-access.md")
   ```
   Keep writing the `generate_cli_help()` guarded block
   (`<!-- AUTO-GENERATED: gen_rag_reference.py cli-help -->` /
   `<!-- END AUTO-GENERATED -->`) into this file — content already matches current
   `argparse` definitions (verified statically, UNK-01), so this section can resume being
   genuinely auto-generated. No file relocation to `03_rag_05_2-execution-guide.md`: that
   file's existing content is prose-style runnable examples (not raw `--help` dumps) and
   should not be overwritten by a guard block.
2. **Config-table section — do not automate; adopt manual maintenance as policy.**
   `docs/03_rag_05_1-configuration-reference.md` is already the higher-quality,
   hand-maintained source of truth (per-key descriptions the generator cannot produce).
   Do not add a second, lower-quality auto-generated config table anywhere. Concretely:
   - Remove `generate_config_table()`'s role as a write target: `main()` no longer writes
     a config-table guarded block to any doc file.
   - Optionally retain `generate_config_table()` as a `--dry-run`-only diagnostic (e.g. to
     let a human eyeball whether `03_rag_05_1-configuration-reference.md` has drifted from
     `config/*.toml`), but its output is never written into a doc file automatically.
   - Delete the existing (stale, duplicate) config-table `AUTO-GENERATED` block from
     `docs/03_rag_05_7-rag-index-consistency-checks.md` in the follow-up documentation
     phase, since it duplicates `03_rag_05_1` and its own prose already says `03_rag_05_1`
     is authoritative.
3. Use distinct guard-marker comment text per section
   (`gen_rag_reference.py cli-help` vs. leaving no config-table marker at all) so a future
   run cannot accidentally match the wrong block via a shared literal
   `<!-- AUTO-GENERATED: gen_rag_reference.py config -->` string.
4. This resolves NC-010 and NC-014 identically: both were the same root cause
   (`OPS_DOC` pointing at a deleted file); the fix removes the config-table guard/target
   from the tool entirely rather than repointing it a second time, and NC-014's block is
   deleted rather than kept.

## Risks

- **Risk**: Retargeting `CLI_HELP_DOC` at `docs/03_rag_05_8-...md` still requires a
  guard-marker text change in that doc file, which is technically a `docs/*.md` edit —
  → **Mitigation**: That edit belongs to the implementation phase (`03_implementation.md`),
  not this planning phase; this plan only specifies the marker text so it stays
  consistent with the tool code change. No `docs/*.md` file is edited during this
  planning workflow run.
- **Risk**: Dropping automated config-table generation entirely could let
  `docs/03_rag_05_1-configuration-reference.md` silently drift from `config/*.toml` over
  time with no automated check → **Mitigation**: keep `generate_config_table()` available
  under `--dry-run` specifically so a human can periodically diff its raw key list against
  `03_rag_05_1`'s tables; consider a future lightweight test (e.g. a `tests/` assertion
  that every TOML key in `config/{crawler,chunk_splitter,ingester}.toml` appears somewhere
  in `03_rag_05_1-configuration-reference.md`) as a follow-up requirement — out of scope
  for this plan but worth filing separately.
- **Risk**: This plan's environment could not execute the three ingestion scripts'
  `--help` live (missing `bs4`/`rag`/`db` deps, no network to install them in this
  sandbox), so CLI-help freshness (UNK-01) was verified by static source comparison only,
  not by running the actual command → **Mitigation**: Implementation Phase 3 step above
  requires running `python tools/gen_rag_reference.py --dry-run` for real in an
  environment with dependencies installed (`uv sync --dev --system-certs`) before
  considering the change complete; if live `--help` output differs from the static
  reading, the guarded block will simply pick up the correct live text automatically once
  the tool runs.
- **Risk**: Treating NC-010 and NC-014 as one coordinated change (per this plan and the
  NC-014 requirement's own instruction not to implement independently) means the
  `requires/20260727-135740_require.md` cycle, when processed, must recognize this plan
  already covers it rather than generating a second, possibly divergent plan →
  **Mitigation**: this plan's Scope and Traceability sections explicitly list
  `requires/20260727-135740_require.md` as covered; the next workflow phase
  (`02_plan_to_implementation_procedure.md`) should treat both source requirements as
  satisfied by this single plan document.
