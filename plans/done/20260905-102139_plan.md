## Goal
- Build a new automated check that scans `docs/*.md` for the five
  implementation-detail categories the docs content policy prohibits, register
  it in `docs/00_governance_04_documentation-checks.md` as a report-only
  (Warning) check, and run it once against the current corpus to produce a
  concrete violation inventory for follow-up content-migration work.

## Priority
Medium

## Scope
- **In-Scope**: implementing the detection logic as a new dedicated script
  (`tools/check_docs_content_policy.py`); registering it in
  `docs/00_governance_04_documentation-checks.md`'s Automated Checks section
  and Governance Verification Matrix as report-only (Warning); unit tests for
  the detection logic; one run against the current `docs/*.md` corpus with
  its output recorded as this Plan's completion evidence; registering the new
  script in `tools/TOOL_DESCRIPTIONS.md` (required whenever a file is added to
  `tools/`, per `routing.md` "When to run which tool").
- **Out-of-Scope**: rewriting `docs/01_overview-files-*.md` or any other
  flagged document to comply with the policy; defining the content policy
  itself (tracked in the sibling `docscope1` Plan this one depends on);
  deciding `check_port_drift()`/`check_port_range_claim()`'s fate under the
  new policy (tracked separately — `docscope3`); editing `rules/env.md`.

## Background
This Plan depends on the docs/ design-intent content policy being defined
first — Plan `plans/20260905-101850_plan.md` (source issue
`issues/done/20260903-200135_docscope1_define-design-intent-content-policy.md`),
which adds the five remove-category definitions to `skills/DESIGN.md` Shared
Vocabulary this detection logic implements pattern/heuristic matching
against. That Plan is Frozen but not yet implemented as of this Plan's
creation (confirmed: `skills/DESIGN.md` does not yet contain the new
subsections) — this Plan's Implementation steps are gated on that
precondition (see Risks).

`docs/00_governance_04_documentation-checks.md`'s Governance Verification
Matrix already has a precedent for landing a corpus-wide check as report-only
first: `GV-020` (removed-name reintroduction detection, confirmed at line 290:
`Chk | Auto | check_compat_shims.py --check-removed-names | PR | Warning |
Partial | Implement the context-aware ... detection case; promote to
default-on once the corpus is compliant`). This Plan follows the same
rollout pattern, since the current corpus has known, extensive violations
(the entire `01_overview-files-*` series, among others — confirmed present:
`docs/01_overview-files-01-build.md`, `docs/01_overview-files-02-rag.md`,
`docs/01_overview-files-06-misc.md`) that a day-one hard gate would turn into
a blocking failure for unrelated PRs.

## Problem
There is currently no automated way to find every instance of the five
remove-categories across `docs/*.md`. A manual one-time sweep would also
leave no regression guard — a future document could reintroduce a file tree,
an index table, or a port number with nothing to catch it, the same gap
`GV-020` was created to close for reintroduced removed-names. The known
violation sites are already large enough to matter: at least 6 dedicated
file-tree documents (`docs/01_overview-files-01-build.md` through
`docs/01_overview-files-06-misc.md`) and 6 additional files confirmed to
contain index tables or literal port numbers (`docs/03_rag_02_08_ingestion_pipeline-shared.md`,
`docs/03_rag_02_05_ingestion_pipeline-document-manager.md`,
`docs/03_rag_02_07_ingestion_pipeline-utils.md`,
`docs/04_mcp_02_01_endpoints-and-transport.md`,
`docs/04_mcp_03_02_tool-registry.md`,
`docs/04_mcp_04_02_file-write-file-delete-shell.md` — all confirmed present
during the sibling `docscope1` Plan's Step 3 inspection).

## Reason for Change
Per `AGENTS.md` Global Rule 7 ("If you perform the same operation three or
more times, extract it into a Python script... and reuse it"), a violation
category recurring across 10+ files already crosses this repository's own
stated threshold for tooling. Building the detection logic once, as a
registered check, also gives the corpus a permanent regression guard instead
of a single manual pass that immediately goes stale.

**Added during this Plan's post-Freeze skill/tool cross-check (2026-09-05)**:
`routing.md`'s "When to run which tool" table states "A file was added to or
removed from `tools/` → run `check_tool_descriptions_sync.py` — Update
`tools/TOOL_DESCRIPTIONS.md` in the same change — do not leave a tool
undocumented." This Plan's new file (`tools/check_docs_content_policy.py`)
falls squarely under that rule; the original version of this Plan omitted
`tools/TOOL_DESCRIPTIONS.md` from Implementation Target Files, which would
have surfaced as an "additional target file discovery" `Blocked` condition
during `plan-to-implementation-procedure` (`rules/workflow-lifecycle.md`
Revalidation) — corrected here instead, before that phase begins.

## Implementation intent
Implement the detection logic as a new dedicated script
(`tools/check_docs_content_policy.py`) rather than extending
`tools/check_docs_quality.py` — that file is already 549 lines, past
`skills/DESIGN.md` File Split Rule's 400-line trigger, and adding five new
independent detection responsibilities (one per remove-category) would push
it further past that threshold while adding a distinct responsibility group
(content-policy scanning) alongside its existing core-check group. The new
script follows the existing `Issue`-object reporting convention already used
by `tools/check_docs_quality.py`/`tools/check_docs_structure.py` (confirmed:
`@dataclass(frozen=True) class Issue` at `tools/check_docs_quality.py` line
44). Land the check as report-only (Warning), matching `GV-020`'s own
rollout precedent, and register it in
`docs/00_governance_04_documentation-checks.md`'s Automated Checks list (as a
new numbered entry after the existing 8) and Governance Verification Matrix
(next available `GV-*` ID after `GV-020`, re-checked for collision
immediately before insertion — see Risks). After implementation, run the new
check against the current `docs/*.md` corpus once and record its output
(file + violated category) — this becomes the scoping input for whichever
follow-up issue(s) perform the actual content rewrites; this Plan does not
attempt those rewrites.

**Shared-library reuse decision (added during this Plan's post-Freeze
skill/tool cross-check, 2026-09-05)**: `tools/_docs_consistency_lib.py`
already defines an `Issue`/`DocFile` pair structurally identical to
`check_docs_quality.py`'s own (`file`, `line_no`, `severity`, `message`),
reused by five existing scripts (`check_dependency_graph_cycles.py`,
`check_needs_confirmation_inventory.py`, `check_known_deviation_sync.py`,
`check_adr_invariant_matrix.py`, `check_adr_reference.py`) — this Plan's
Design must not add a *third*, independently-defined copy of the same shape
without considering that library first, per `AGENTS.md` Global Rule 7. Two
sub-decisions follow:
- **`Issue` dataclass**: import it from `tools/_docs_consistency_lib.py`
  rather than redefining it a third time — the shape is identical and this
  avoids a needless third copy.
- **File discovery**: do NOT reuse `_docs_consistency_lib.py`'s
  `discover_md_files(docs_dir, *, prefix: str)` — it globs
  non-recursively (`docs_dir.glob(f"{prefix}*.md")`) and requires a
  domain-specific `prefix`, so it cannot see files under `docs/adr/` or
  `docs/databases/` (confirmed both exist via `find docs -mindepth 1
  -maxdepth 1 -type d`). Since this check must scan the full `docs/*.md`
  corpus including subdirectories, follow `check_docs_quality.py`'s own
  `discover_md_files(docs_dir)` shape instead (`docs_dir.rglob("*.md")`,
  no `prefix` parameter) — implemented locally in the new script, not
  imported, since `check_docs_quality.py` does not currently expose it as a
  reusable public helper either.

## Design
This Plan introduces one new standalone CLI script following the repository's
existing `tools/check_*.py` pattern (a single-responsibility, independently
invokable script with its own sibling test file — the same shape as
`check_docs_structure.py`/`test_check_docs_structure.py`), not a new
subsystem or package boundary.

**Path A/B classification — corrected 2026-09-05 (post-Freeze skill/tool
cross-check)**: originally classified Path A (3 files). Adding
`tools/TOOL_DESCRIPTIONS.md` (REQ-008, required by `routing.md`'s new-file
registration rule — see Reason for Change) brings the count to 4 files,
exceeding Path A's "≤ 3 files" threshold per `skills/issue-to-plan/SKILL.md`
Routing. Reclassified **Path B**. The four required analyses, performed
during this correction:

### Architecture analysis
`tools/check_docs_content_policy.py` is a leaf script with no importers of
its own besides its test file; it imports `Issue` from
`tools/_docs_consistency_lib.py` (existing shared dependency, already
imported by 5 other `tools/check_*.py` scripts — no new dependency direction
introduced) and implements its own file discovery rather than importing
`check_docs_quality.py`'s (that function is not exposed as a reusable
public helper there). No circular-import risk: `tools/_docs_consistency_lib.py`
has no `__main__` and imports nothing from any `check_*.py` script (confirmed
by its own docstring: "Not a check script itself — has no `__main__` entry
point").

### Dependency graphing
Concrete file list requiring changes (matches Implementation Target Files
exactly, 4 files): `tools/check_docs_content_policy.py` (new),
`tests/tools/test_check_docs_content_policy.py` (new),
`docs/00_governance_04_documentation-checks.md` (edit, 2 locations: Automated
Checks list + Governance Verification Matrix), `tools/TOOL_DESCRIPTIONS.md`
(edit, 1 new entry). No other file requires modification — confirmed via
`grep -rn "check_docs_content_policy"` returning zero pre-existing
references (it is a wholly new tool name).

### Historical analysis
`docs/00_governance_04_documentation-checks.md`: 8 commits (30d churn, per
Affected areas). `tools/TOOL_DESCRIPTIONS.md`: not independently measured —
it is a low-risk, append-only registry file with no behavioral content; its
own churn is driven entirely by how often new `tools/` files are added, not
by this Plan's specific change.

### Operational dependency inspection
Not applicable — this Plan touches no MCP server, database, or long-running
process; `tools/check_docs_content_policy.py` is a stateless, read-only CLI
script invoked on demand (matching every other `tools/check_*.py` script's
operational profile).

**Design decision (unchanged by reclassification)**: no
public/runtime-facing interface change (the new script is an independent CLI
entry point, not a change to any existing module's interface), no database
schema change — Path B applies solely because of the file-count threshold,
not because of interface or schema risk. Direct verification (Step 3, and
re-verification during this correction) confirmed the Issue's cited evidence
(`GV-020` precedent, `check_docs_quality.py`'s size and `Issue` convention,
the 12 confirmed violation-example files (6 file-tree documents + 6
index-table/port-number files, per Problem), and `routing.md`'s
`TOOL_DESCRIPTIONS.md` registration rule) all hold against current source.
The core design decision remains a new dedicated script rather than
extending `check_docs_quality.py`, justified by that file's existing size
(549 lines, past the 400-line File Split Rule trigger) — adding a fifth
independent detection responsibility there would compound rather than
relieve that existing size pressure.
