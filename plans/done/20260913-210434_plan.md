## Background
The Issue's cited claim
(`docs/03_rag_02_03_ingestion_pipeline-chunksplitter.md:186`: "URLs ending in
`.md`, `.markdown`, or `.mdx` always use heading chunking regardless of
`md_index_enable`. For other files, heuristic detection ... is used only if
`md_index_enable=true`.") is confirmed accurate against
`_is_markdown_source()` (`scripts/rag/ingestion/chunk_splitter.py:137-156`):
extension-matched URLs (line 146) return `True` unconditionally, before
`self._md_index_enable` (line 148) is even checked.

**Re-verified 2026-09-13** (this cycle): two of the Issue's four requested points
could not be answered from available evidence, and a third point's premise does
not hold:
1. **No historical rationale is recorded.** `git log --all -S "always use heading
   chunking"` and `-S "md_index_enable"` on `chunk_splitter.py` both trace this
   behavior to `ee035ff5e`/`c0b578e82` ("feat: Markdown ingest standardization —
   production code changes"). Both commits' full messages contain no rationale —
   only "(continuation of previous commit — pre-commit stash restored unstaged
   files)". No code comment in `_is_markdown_source()` explains *why* extension
   takes unconditional precedence over the heuristic path, only *that* it does.
2. **No override exists for URL-based `.md`/`.markdown`/`.mdx` detection.**
   `_is_markdown_source()`'s extension check (line 146) returns unconditionally
   before `md_index_enable` is read (line 148) — there is no configuration key,
   flag, or code path that suppresses heading chunking for a `.md`-extension URL.
   `md_index_enable` only gates the *heuristic* detection path (content-based
   heading-line counting) used for non-`.md`-extension sources. The Issue's
   Recommended Action's 3rd request ("How to override the behavior for non-URL
   sources") presumes an override mechanism exists; none does, for any source
   whose URL carries one of these three extensions (including local `file://`
   sources — `str.endswith()` matches the extension regardless of the `file://`
   scheme prefix, confirmed by inspecting `WebCrawler.crawl_file()`'s URL
   construction, `crawl_persister.py:62`: `f"file://{path.resolve()}"`).
3. **The rule's likely technical motivation can be stated without overreaching.**
   An extension-based check is deterministic and requires no content inspection
   (unlike the heuristic path's line-counting), so it is plausible the extension
   rule exists for reliability on sources already known to be Markdown. This is
   offered as a *plausible technical rationale inferred from the code's structure*,
   explicitly distinguished from a *historical* rationale (point 1), which is not
   recorded anywhere.

## Problem
A reader of the current documentation could reasonably assume `md_index_enable`
provides some way to change how `.md`/`.markdown`/`.mdx` URLs are chunked (the
Issue's own Recommended Action reflects this assumption) — but no such override
exists. Separately, a reader has no way to know whether the extension-based rule's
historical rationale is simply undocumented here, or genuinely unrecorded anywhere
in the project's history.

## Reason for change
State the two confirmed facts plainly — no historical rationale is on record, and
no override exists for extension-matched sources — so a reader does not spend time
searching for a configuration option that isn't there, or assume documentation
gaps that are actually gaps in the project's own history.

## Implementation intent
Add a short note near the existing Markdown source detection description stating:
(1) the extension-based rule's historical rationale is not recorded in code
comments or commit history (citing the traced commits as the earliest evidence
found); (2) `md_index_enable` does not override extension-based detection for
`.md`/`.markdown`/`.mdx` URLs (including local `file://` sources) — it only
affects heuristic detection for other file types; (3) a plausible technical
rationale (determinism vs. content-based heuristics), explicitly labeled as
inferred, not historical.
