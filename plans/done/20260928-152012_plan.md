NC-021 originally asked whether `_classify_error()` should be extended to produce `INVALID_FORMAT`, or whether the enum value/branch should be removed as dead code. `docs/10_adr/ADR-008-sqlite-4db-separation.md` Decision Details #14 already settles that question in favor of keeping the enum and dispatch branch (physical-recovery must classify DB state across all six `DbCondition` values, `INVALID_FORMAT` included). A 2026-09-27 deep-dive investigation found the remaining, narrower question — whether test coverage is needed for the unreachable branch — is a coverage gap, not an open design question: a unit test for the classification mapping already exists, but the recovery flow's own dispatch has integration-level tests for its sibling conditions `LOCK_CONTENTION`/`PERMISSION_FAILURE` but not for `INVALID_FORMAT`.

## Problem
`recover_corruption()`'s dispatch branch for `DbCondition.INVALID_FORMAT` (`scripts/db/recovery.py:429-432`) has no integration-level test, unlike its two sibling conditions in the same `if` clause — an inconsistent coverage gap.

## Reason for change
Closing this gap removes the last open item blocking NC-021's removal from `docs/00_governance/governance_03_issue-and-uncertainty-management.md`'s Needs Confirmation inventory, and brings the three sibling `DbCondition` branches to equal test coverage.

## Implementation intent
