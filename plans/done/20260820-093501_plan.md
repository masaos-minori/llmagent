# Plan: Enforce strict MCP Schema 2.0 validation in tool discovery

## Goal

Make `McpToolDiscoveryService` reject, instead of silently tolerating, three legacy/absent
forms in `/v1/tools` responses — a missing or unsupported `schema_version`, a snake_case
`input_schema` fallback in place of `inputSchema`, and a legacy singular `resource_scope`
field — so a genuine server-side schema regression surfaces as a discovery-time WARNING
finding rather than being silently accepted.

## Scope

**In-Scope:**
- `scripts/agent/services/mcp_tool_discovery.py`:
  - `_fetch_server_tools`: require `schema_version` present and equal to the currently
    supported version; reject (via the existing `_warning_fetch_result(...)` whole-server
    path) otherwise.
  - `_validate_and_normalize_entry`: read only `entry.get("inputSchema")` (no
    `input_schema` fallback); reject entries carrying a legacy singular `resource_scope`
    key outright instead of merely type-checking it when present.
  - `_dedupe_and_build`: read only `entry.get("inputSchema")` (no fallback) — entries
    reaching this method already passed validation, so this is a same-key-only lookup.
  - Docstrings/comments describing the current tolerant behavior (module docstring,
    `_fetch_server_tools` docstring, `_validate_and_normalize_entry` docstring).
  - A new module-level constant for "the currently supported schema version".
- `tests/agent/services/test_mcp_tool_discovery.py`:
  - Replace `test_missing_schema_version_tolerated` with a rejection test.
  - Add a companion test for an unsupported (non-matching) `schema_version` value.
  - Replace `test_resource_scope_type_checked_when_present_synthetic` with a rejection
    test (both the previously-"rejected-because-wrong-type" and previously-"accepted-
    because-right-type" halves must now assert rejection, since presence alone is now
    disqualifying).
  - Add a new test asserting a `input_schema`-only (no `inputSchema`) entry is rejected.

## Assumptions

- A1: The value the production servers emit for `MCP_TOOL_SCHEMA_VERSION` is `"1.0"`
  (verified: `scripts/mcp_servers/server.py:39` and mirrored identically in the four
  per-family server modules). The new client-side "currently supported version" constant
  must equal this literal, not `"2.0"`. Falsifiable by re-reading
  `scripts/mcp_servers/server.py:39` at implementation time — if any server's value has
  since diverged, the constant must track the actual emitted value, not a hardcoded guess.
- A2: No new shared module is required to hold the schema-version constant. The
  requirement text explicitly leaves this to implementer judgment ("either satisfies this
  requirement"); since the Target files list does not include a new `scripts/shared/*.py`
  module and creating one would add a `deploy/deploy.sh` copy-list entry and cross-module
  import for a single-file concern, this plan chooses a local module-level constant in
  `mcp_tool_discovery.py` (e.g. `_SUPPORTED_SCHEMA_VERSION`) with an inline comment
  pointing at `scripts/mcp_servers/server.py:MCP_TOOL_SCHEMA_VERSION` as the source of
  truth. Falsifiable: if a future requirement needs the same constant from multiple
  client-side modules, centralizing it becomes justified and this decision should be
  revisited.
- A3: A `resource_scope` key present on an entry should be a hard rejection (WARNING
  finding via `_warning_entry`), not merely "no longer type-checked but silently ignored".
  Basis: the require doc's Implementation instructions step 2 explicitly asks for a
  replacement test "asserting that an entry carrying the legacy singular `resource_scope`
  field is rejected (or at minimum no longer accepted as valid)", and the Acceptance
  criteria states entries carrying it "no longer silently pass through as if compatible."
  Silently dropping the type-check without adding a rejection would leave such entries
  passing through un-flagged, which does not satisfy "no longer silently pass through."
  This is the interpretation this plan adopts; it is a design decision, not a re-reading
  of ambiguous requirement text as fact.
- A4: `scripts/agent/startup.py` requires no change (see Scope: Out-of-Scope) because it
  only aggregates `StartupCheckOutcome.status`/`.message` from `mcp_tool_discovery`
  findings without branching on which specific validation rule produced a WARNING.
  Falsifiable by re-reading `scripts/agent/startup.py` lines 371-385, 505-541 at
  implementation time.

## Design

1. **Schema-version constant.** Add, near `_REQUIRED_SCHEMA_V2_FIELDS` in
   `mcp_tool_discovery.py`:
   ```python
   # The schema_version value production MCP servers currently emit
   # (scripts/mcp_servers/server.py:MCP_TOOL_SCHEMA_VERSION). Kept as a local literal
   # rather than a shared import: this is the only client-side consumer that needs it.
   _SUPPORTED_SCHEMA_VERSION = "1.0"
   ```
   (See Assumption A2 for why this is local rather than centralized.)

2. **`_fetch_server_tools` (schema_version enforcement).** Replace the current
   debug-log-only block:
   ```python
   schema_version = body.get("schema_version")
   if schema_version is not None:
       logger.debug(...)
   ```
   with a hard check that routes through the existing `_warning_fetch_result(...)` path
   (the same mechanism used for non-200 / invalid-JSON / malformed-shape), so a missing
   or mismatched `schema_version` marks the whole server unreachable/excluded with one
   WARNING finding — not a per-tool rejection:
   ```python
   schema_version = body.get("schema_version")
   if schema_version != _SUPPORTED_SCHEMA_VERSION:
       return _warning_fetch_result(
           f"{key}: /v1/tools schema_version {schema_version!r} unsupported "
           f"(expected {_SUPPORTED_SCHEMA_VERSION!r})"
       )
   ```
   This naturally covers both "missing" (`None != "1.0"`) and "wrong value" cases with one
   branch, matching the acceptance criteria's two separate test cases with one code path.

3. **`_validate_and_normalize_entry` (inputSchema, resource_scope).**
   - Change `input_schema = entry.get("inputSchema", entry.get("input_schema"))` to
     `input_schema = entry.get("inputSchema")`.
   - Remove `("resource_scope", str)` from the optional-field type-check tuple.
   - Add an explicit rejection immediately before or after that loop:
     ```python
     if "resource_scope" in entry:
         return _warning_entry(
             f"{server_key}: tool {name!r} carries legacy 'resource_scope' field "
             "(use resource_scope_kind/resource_scope_keys)"
         )
     ```
   - Update the method's docstring (currently: "Optional `status`/`resource_scope`
     (legacy singular)/`enabled`/`capabilities` remain type-checked only if present") to
     state that `resource_scope` is now a hard-rejection field, not a tolerated one.

4. **`_dedupe_and_build` (inputSchema only).** Change
   `entry.get("inputSchema", entry.get("input_schema"))` to `entry.get("inputSchema")`.
   No new rejection here — entries reaching this method already passed validation.

5. **Docstring/comment sweep.** Update the module docstring (lines 6-14 currently
   describe reading "optional `schema_version`/`capabilities` keys" — `schema_version` is
   no longer merely optional/logged, it is now enforced) and the `_fetch_server_tools`
   docstring to reflect strict rejection instead of tolerant logging.

## Risks

- **Risk**: The chosen literal `"1.0"` for `_SUPPORTED_SCHEMA_VERSION` drifts from
  `MCP_TOOL_SCHEMA_VERSION` if the latter is bumped in `scripts/mcp_servers/server.py`
  without updating the client-side constant, silently reintroducing the exact
  "reject every real server" failure mode the require doc explicitly warns against.
  → **Mitigation**: the constant carries an inline comment pointing at the
  server-side source of truth; the new `test_unsupported_schema_version_rejected` test
  (Implementation Steps Phase 2) exercises the mismatch path, so a future drift would
  be caught as an unexpected *acceptance* failure in `TestToolsEndpointSchemaVersion`
  (which already asserts real servers' `schema_version == MCP_TOOL_SCHEMA_VERSION`) if
  the two values ever diverge in a way that breaks discovery in practice — likelihood:
  low; a follow-up requirement to centralize the constant (Assumption A2) would remove
  this risk entirely if judged worthwhile later.
- **Risk**: Making `resource_scope` presence a hard rejection (Assumption A3) is an
  interpretation of ambiguous requirement text, not an explicit instruction — a reviewer
  could reasonably prefer the weaker "stop tolerating, but don't hard-reject" reading.
  → **Mitigation**: both readings satisfy the require doc's literal acceptance criteria
  ("rejection tests must exist either way"); this plan documents the choice and rationale
  in Assumption A3 so it is visible for review before implementation, and the
  implementation step is small/isolated (one `if` block) so switching interpretations
  later is a low-cost, independently revertable change.
- **Risk**: Concurrent/sequential application of this plan and
  `plans/done/20260819-184236_plan.md` (both touch `mcp_tool_discovery.py`, though disjoint
  methods — `_fetch_server_tools`/`_validate_and_normalize_entry`/`_dedupe_and_build`
  here vs. `_check_tool_definitions_finding()` there) could produce line-shift merge
  friction if implemented in parallel branches.
  → **Mitigation**: implement sequentially (whichever plan reaches `implementations/`
  first should land first); the two touch disjoint methods so a textual conflict, if
  any, is mechanical to resolve.
- **Risk**: Removing the `resource_scope` type-check tolerance could reject a tool entry
  from a non-listed/future MCP server that still emits the legacy field, if such a
  server exists but was not part of the five reference-only servers checked.
  → **Mitigation**: the WARNING (not FATAL by default) severity for entry-level
  rejections is unchanged — an affected server's tool is excluded from the registry with
  a clear, actionable message rather than crashing discovery; `security_profile`/`strict`
  still control FATAL escalation exactly as today for other entry-level rejections.
