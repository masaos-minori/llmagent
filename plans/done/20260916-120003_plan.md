## Problem
`_special_case_risk()` in `scripts/agent/tool_policy.py` (confirmed at line 138)
checks `cmd.startswith(p) for p in cfg.approval.approval_shell_safe_prefixes`
against a configured safe-prefix list before returning `RiskLevel.NONE`. This does
not establish real executable identity: `str.startswith()` matches on raw
characters, not token boundaries, so a safe prefix (e.g. `"cat"`) also matches an
unrelated command that merely begins with the same characters (e.g.
`"category_dump_secrets"`), and it performs no validation of the arguments that
follow the matched prefix.

**Adversarial-verification correction to the Issue's stated exploit scenario**
(Issue Problem section, `"cat /etc/passwd; rm -rf /"`): confirmed by repository
evidence that this scenario does not execute as described. `rg -n "shell=True"
scripts/ tests/` returns no matches anywhere in the repository, and
`scripts/mcp_servers/shell/shell_service.py::_check_command()` /
`scripts/mcp_servers/shell/subprocess_runner.py::run_subprocess()` show the actual
executed command always goes through `asyncio.create_subprocess_exec(*argv, ...)`
with `argv` either caller-supplied or `shlex.split(req.command)` — never a real
shell. `shlex.split("cat /etc/passwd; rm -rf /")` yields the literal token list
`["cat", "/etc/passwd;", "rm", "-rf", "/"]`, which the OS executes as a single `cat`
invocation with those tokens as filename arguments — `rm` never runs as a separate
process. Shell metacharacters (`;`, `&&`, `|`, backticks, `$()`, redirection) are
therefore not interpreted as compound-command operators anywhere in the current
execution path.

The real, confirmed gap is narrower than the Issue's exploit scenario but still a
genuine security defect:
1. **Prefix collision without a token boundary** (confirmed): `cmd.startswith(p)`
   allows any command string that merely starts with the same characters as an
   approved prefix, including a longer, unrelated executable name.
2. **No argument/path constraint for approval-free shell commands** (confirmed):
   `classify_risk()`'s control flow (`scripts/agent/tool_policy.py` lines 178-186)
   returns `_special_case_risk()`'s result for `shell_run` before
   `_escalate_for_path()` is ever reached, and `"command"` is not a member of
   `cfg.approval.approval_resource_keys["path_keys"]` (confirmed in
   `config/agent.toml` `[approval_resource_keys]`) even if it were reached. So a
   safe-prefix command such as `cat /etc/shadow` or `find / -name id_rsa` is
   classified `RiskLevel.NONE` today with no protected-path or `allowed_root` check
   applied at all — a defect independent of shell metacharacters.
3. **Forward-compatibility gap** (defense-in-depth, not currently exploitable): the
   classifier itself performs no rejection of shell metacharacters/control
   operators. Should a future change introduce a real shell-interpreting execution
   path (`shell=True`, a different exec tool, or a change to `_check_command()`),
   today's classifier would misclassify a compound command sharing a safe prefix as
   `RiskLevel.NONE` with no additional guard. Failing closed on metacharacters now
   removes this latent risk before it can be exploited.

## Reason for change
Shell approval currently relies on raw command-prefix matching that does not
establish executable identity or apply any argument/path constraint, and would
misclassify a future or alternate execution path that does interpret shell
metacharacters. This issue is an independent security boundary and is deliberately
scoped apart from the MCP startup work in `mcpagent01`.

## Implementation intent
Replace the raw-string `startswith()` check with a parsed-command authorization
path inside `_special_case_risk()`'s `shell_run` branch:
1. Tokenize the raw `command` string with `shlex.split()`; a `ValueError` (e.g.
   unbalanced quotes) or empty result fails closed to `RiskLevel.HIGH`.
2. Before token-level matching, scan the *raw* command string for shell
   metacharacters/control operators (`;`, `&&`, `||`, `&`, `|`, `` ` ``, `$(`, `<(`,
   `>(`, `>`, `>>`, `<`, newline) — any match fails closed to `RiskLevel.HIGH`
   regardless of prefix match, since `shlex.split()` alone cannot detect these as
   operators (they become literal tokens, not real syntax — see Problem's
   correction above).
3. Match the parsed leading token(s) against each configured
   `approval_shell_safe_prefixes` entry by exact token-sequence equality on
   `os.path.basename(argv[0])` (and, for a multi-word configured entry such as
   `"git log"`, exact equality of the corresponding leading tokens) — never a
   substring/prefix comparison over the raw line.
4. Only on a matching executable/subcommand: extract every remaining non-flag
   (positional, path-like) token and route it through the same checks
   `_escalate_for_path()` and `check_allowed_root()` already apply to other tools'
   path arguments, reusing `cfg.approval.approval_protected_paths` and
   `cfg.approval.allowed_root` — no new config keys.
5. Document the `cat`/`find`/`grep` NONE-eligibility decision (Design below) and
   implement any additional unsafe-flag denylist the decision requires.

## Design
The current design conflates two distinct concerns under one raw-string check in
`_special_case_risk()`: (1) whether `shell_run` may proceed *without* human
approval (agent-side risk classification, this Plan's scope), and (2) whether the
command is *permitted to execute at all* (the shell-mcp server's own
`command_allowlist` in `shell_service.py::_check_command()`, out of this Plan's
scope, already parsed and token-exact). This Plan brings (1) into parity with the
parsing discipline already used by (2): `shlex.split()` plus exact-token matching
on `os.path.basename(argv[0])`, rather than duplicating a new parser.

The classifier gains three layered checks, evaluated in order inside the
`shell_run` branch of `_special_case_risk()`:
1. **Metacharacter fail-closed** (REQ-002) — a raw-string scan for shell control
   operators, run first and unconditionally, since `shlex.split()` cannot detect
   them (it only tokenizes; see Problem's correction).
2. **Parsed identity match** (REQ-001) — `shlex.split()` the command (fail closed on
   `ValueError`/empty), then require the leading token(s) to equal, not merely
   start with, a configured safe entry's tokens.
3. **Path/argument constraint** (REQ-003, REQ-004) — for a matched
   entry, route every remaining positional token through the existing
   `approval_protected_paths`/`allowed_root` checks (previously never reached for
   `shell_run` — see Problem, point 2) and a per-executable unsafe-flag denylist for
   `cat`/`find`/`grep`-class commands.

`_special_case_risk()`'s cyclomatic complexity is already grade B (radon: 9) and
`classify_risk()` grade C (13) at baseline (`uv run radon cc
scripts/agent/tool_policy.py -s`, confirmed before this change). Implementing the
three layered checks as small, separately named helper functions (rather than
inlining all logic into `_special_case_risk()`) keeps each function at or below
grade B and keeps `classify_risk()`'s own complexity unchanged, since it only calls
`_special_case_risk()` as before.

No new `config/*.toml` key is introduced: `approval_shell_safe_prefixes` keeps its
existing `list[str]` type and default values (`config/agent.toml`,
`scripts/agent/config_dataclasses.py`) — only its runtime interpretation changes
from "raw string prefix" to "exact leading-token sequence."

## Risks
- **Risk**: A configured multi-word safe-prefix entry (e.g. `"git log"`) is
  misparsed by the new exact-token matcher if it is not tokenized with the same
  `shlex`-based rules as the incoming command, silently narrowing or widening what
  is treated as safe. → **Mitigation**: tokenize both the configured entry and the
  incoming command with `shlex.split()` before comparison, and add a regression
  test asserting each existing `approval_shell_safe_prefixes` default value
  (`config/agent.toml`) still matches its intended safe invocation post-change.
- **Risk**: Reassessing `cat`/`find`/`grep` (REQ-004) to sometimes return
  `RiskLevel.HIGH` where they previously returned `NONE` could increase approval
  prompts for legitimate, frequently-used read-only commands, degrading agent
  usability. → **Mitigation**: scope the new HIGH-escalation strictly to
  protected-path/`allowed_root`/unsafe-flag violations (REQ-003, REQ-004), not to
  every invocation, and validate against the existing test fixtures in
  `tests/agent/test_tool_policy_comprehensive.py` to confirm common safe
  invocations remain `NONE`.
- **Risk**: `scripts/agent/tool_policy.py` and `scripts/agent/config_dataclasses.py`
  both show a single effective author across their commit history (high bus
  factor), increasing review risk for a security-boundary change. →
  **Mitigation**: keep the diff small and evidence-grounded per this Plan's
  Implementation steps; rely on the adversarial test suite (REQ-005) as an
  independent, executable check rather than solely on code review.
- **Risk**: The pre-existing `lint-imports` violation
  (`shared.production_config_validator` importing `agent.tool_policy`) could mask
  a real regression if this Plan's change to `tool_policy.py` is misread as the
  cause of a lint-imports failure during implementation. → **Mitigation**:
  `Documentation Impact`/`Assumptions` above record this as pre-existing and
  unrelated; implementation should re-run `lint-imports` before this Plan's
  changes to reconfirm the same single violation, then treat any *additional*
  broken contract as caused by this Plan's own changes.
