# Plan

## Goal
Remove the incremental migration mechanism of `workflow.sqlite` (the migration list, its apply function, and its call in the schema bootstrap) so that the workflow schema bootstrap is create-only plus schema-version recording, and make sure a database older than the supported baseline is rejected rather than silently stamped with the current version.

## Priority
Medium

## Scope
- **In-Scope**:
  - Delete `_WORKFLOW_MIGRATIONS` and `apply_workflow_migrations()` from `scripts/db/schema_sql.py`, and the call plus import in `scripts/db/create_schema.py`.
  - Make `tools/check_db_separation.py` read only the base workflow DDL.
  - Remove or rewrite every test that depends on the removed symbols while keeping base-DDL and version-record tests.
  - Make `create_workflow_schema()` refuse to record the current version over a database whose latest recorded version differs (REQ-007).
  - Update the documentation and operator messages that describe or advertise in-place workflow migration.
- **Out-of-Scope**:
  - EventBus migrations, the MDQ legacy rebuild, and the legacy offset import (separate removal issues).
  - Changing the workflow schema, the value of `WORKFLOW_SCHEMA_VERSION`, or the startup check logic.
  - Backup, restore, or rollback tooling.
  - `docs/00_governance/governance_02_documentation-metadata.md` Glossary example that names `apply_workflow_migrations()` (see UNK-04).

## Background
The database design document (Supported Upgrade Baseline) states that the minimum supported source schema of `workflow.sqlite` is the current release schema, and classifies every migration as removable, each removed by its own change. A read-only inspection of the single host `/opt/llm` on 2026-10-21 recorded version `1.1.0`, equal to `WORKFLOW_SCHEMA_VERSION` in `scripts/db/schema_sql.py`. Verified against current source: the base workflow DDL already contains every column the migrations add and defines no `approvals` table, so all seven migration entries are no-ops on a fresh database; `create_workflow_schema()` runs the base DDL, then the migrations, then records the version.

## Problem
The migration list and `apply_workflow_migrations()` run on every workflow schema bootstrap and serve no supported database. Adversarial verification of the Issue found three additional facts the Issue does not account for:
- Removing the migrations alone would leave `create_workflow_schema()` stamping the current version over an older database. `_record_workflow_schema_version` inserts the current version whenever the latest recorded version differs, and `REQUIRED_WORKFLOW_TABLES` in `scripts/agent/services/workflow_schema.py` does not list the columns the migrations added (`attempts.error_kind`, `attempts.error_detail`, `artifacts.workflow_id`, `artifacts.attempt_number`, `processed_events.workflow_id`). An old database could therefore pass the startup check after `deploy/init_db.sh` ran against it.
- Operator-facing text still advertises migration: `scripts/agent/services/workflow_schema.py` ("Run create_workflow_schema() to migrate."), `deploy/setup_services.sh` ("Run deploy/init_db.sh to migrate the workflow schema"), `docs/90_deployment/deployment_01_deployment.md` (init responsibilities, backup rationale, and the `[FATAL]` recovery row "Apply migrations via init_db.sh"), and `docs/41_db/db_02_architecture_and_schema-schema-reference.md` (recovery wording).
- `docs/10_adr/adr_02_05_008_db-sqlite-4db-separation.md` names `apply_workflow_migrations()` in the `schema-repair` definition, so the Issue's acceptance command (`rg` over `docs`) cannot return no match without an ADR reference edit.

## Reason for Change
A migration that runs on every bootstrap can fail or alter data on a database it was never meant to touch (one entry rewrites task rows). Removing it makes the bootstrap match the owner-approved baseline; the version-guard keeps "recreate, not migrate" enforceable.

## Implementation Intent
Delete the mechanism and keep the base DDL and the version constant unchanged. Replace the implicit upgrade-by-stamping behavior with an explicit refusal: when the version log already holds a latest version different from `WORKFLOW_SCHEMA_VERSION`, `create_workflow_schema()` raises a clear error telling the operator to recreate the database, instead of recording the current version. First-run and same-version runs stay idempotent. Update every doc and message that describes migration, as intent and constraints only, leaving no history of the removal.

## Design
- Path B (more than three files; runtime schema bootstrap on the startup/deploy path).
- Evidence: all seven list entries are no-ops on a fresh database because the base DDL already holds the added columns and defines no `approvals` table; `create_workflow_schema()` applies base DDL, migrations, then the version record; `check_workflow_schema()` checks required tables/columns then the version, but its required-column list omits the migration-added columns.
- Guard design (REQ-005): inspect the version log before recording; no row or equal latest version proceeds; any other latest version raises. The startup check is not changed, so an unprepared old database is still caught there for the columns and version it already checks.
- Docs follow the Current-Specification-Only policy: the removal is described as the current bootstrap behavior, with no history sentence.
- Related removal issues (EventBus, MDQ, offset import) edit overlapping files (`scripts/db/schema_sql.py`, `tools/check_db_separation.py`, `tests/db/test_create_schema.py`, `db_03`, `deployment_01`); apply them one after another and re-read each file before editing.
