# Plan — Enable approval dry-run previews for GitHub tools

## Goal
Make approval dry-run previews work for GitHub mutation tools so approvers see real
dry-run output instead of static text. Currently a high-risk GitHub tool that requires
approval shows only a static preview because dry-run enrichment is gated behind two
checks that GitHub tools fail.

## Priority
Medium

## Scope
- **In-Scope**: Enabling dry-run preview enrichment for GitHub mutation tools that
  actually support a `dry_run` parameter. This means adding those tools to BOTH gating
  sets — the hardcoded capability set `_KNOWN_DRY_RUN_CAPABLE_TOOLS` in
  `scripts/agent/tool_approval.py` AND the default allowlist `_DEFAULT_DRY_RUN_TOOLS` in
  `scripts/agent/constants.py` — plus a regression test.
- **Out-of-Scope**: Read-only GitHub tools (they lack a `dry_run` field and are
  auto-approved, so they never reach the dry-run path); any change to the dry-run
  execution mechanism itself; changing how `approval_dry_run_tools` is read from config;
  other MCP servers' tools; deriving capability dynamically from the tool registry.

## Background
`_build_preview_with_dry_run()` in `scripts/agent/tool_approval.py` enriches the
approval preview with actual dry-run output, but only when the tool passes two gates:

```python
if (
    tool_name not in ctx.cfg.approval.approval_dry_run_tools   # gate 1: config allowlist
    or ctx.services_required.tools is None
):
    return preview   # static preview only; dry-run path dormant
if not _is_dry_run_capable(tool_name):   # gate 2: hardcoded capability set
    logger.warning("Tool %s does not support dry_run; using static preview", tool_name)
    return preview
# ... execute(tool_name, {**args, "dry_run": True}) and append dry-run text
```

`_DEFAULT_DRY_RUN_TOOLS` in `scripts/agent/constants.py` defaults to
`[write_file, edit_file, create_directory, delete_file, delete_directory, move_file]` —
no GitHub tools. `_KNOWN_DRY_RUN_CAPABLE_TOOLS` in `tool_approval.py` is the same six
names. Neither contains any `github_*` tool.

GitHub request models declare `dry_run: bool` fields and `github_service_dispatch.py`
implements `_execute_with_dry_run` (returns a `{preview, dry_run: true}` payload when
`dry_run=True`). So enabling dry-run previews for GitHub tools is technically feasible.

## Problem
When a high-risk GitHub tool requires approval, the preview shows only static text
without executing a dry run, because GitHub tools are absent from BOTH gating sets.
Approvers cannot see what the operation will do before approving.

## Reason for change
Approval previews are the operator's only chance to inspect a high-risk mutation before
it executes. Omitting dry-run output for GitHub tools degrades that visibility for a
whole class of write operations (file edits, issue/PR creation, branch creation).

## Implementation intent
Add the GitHub mutation tools that genuinely support `dry_run` to BOTH gating sets so
the dry-run path is reachable, then add a regression test. Two equivalent mechanisms
satisfy this; implement one:

- **(a) Extend both hardcoded name lists (recommended):** Append the dry-run-capable
  GitHub tool names to `_KNOWN_DRY_RUN_CAPABLE_TOOLS` (tool_approval.py) and to
  `_DEFAULT_DRY_RUN_TOOLS` (constants.py). Keep the existing six entries verbatim.
  This makes dry-run previews work out of the box for all users.
- **(b) Capability gate only + documented config:** Fix only gate 2
  (`_KNOWN_DRY_RUN_CAPABLE_TOOLS`) and document that operators must add GitHub tools to
  their `approval_dry_run_tools` config. Lower blast radius (does not change the global
  default) but does not work out of the box.

Recommended set (GitHub mutation tools that declare a `dry_run` field):
`github_create_or_update_file`, `github_push_files`, `github_delete_file`,
`github_create_issue`, `github_add_issue_comment`, `github_create_pull_request`,
`github_update_pull_request`, `github_merge_pull_request`, `github_create_branch`.

## Requirements
- `REQ-001`: A dry-run-capable GitHub tool in `approval_dry_run_tools` produces a
  preview that includes the dry-run output (not static text only).
- `REQ-002`: Both gating sets include the dry-run-capable GitHub tools, so neither gate
  blocks the dry-run path for them.
- `REQ-003`: The existing six default dry-run tools keep masking/preview behavior
  unchanged (regression).
- `REQ-004`: Read-only GitHub tools are NOT added (they lack `dry_run` and are
  auto-approved).
- `REQ-005`: A regression test asserts a GitHub tool triggers dry-run execution before
  the approval prompt.

## Design
Path A (affects ≤ 3 files; no public/runtime interface change; no DB schema change).
Adversarial verification (Step 2) confirmed the issue's claims against current source:
`_build_preview_with_dry_run` (tool_approval.py lines 70-109) enforces TWO gates —
config allowlist (line 82) and hardcoded capability (line 86 via `_is_dry_run_capable`).
The issue states only the config allowlist; fixing gate 1 alone is insufficient because
`_KNOWN_DRY_RUN_CAPABLE_TOOLS` (lines 53-61) also excludes every `github_*` tool. Both
lists must be updated. GitHub tools genuinely support `dry_run`: request models declare
`dry_run: bool` and `github_service_dispatch.py::_execute_with_dry_run` (lines 83-121)
produces preview output. Scope is limited to the nine GitHub mutation tools that declare
`dry_run` (`github_create_or_update_file`, `github_push_files`, `github_delete_file`,
`github_create_issue`, `github_add_issue_comment`, `github_create_pull_request`,
`github_update_pull_request`, `github_merge_pull_request`, `github_create_branch`);
read-only GitHub tools lack the field and are auto-approved (never reach the gate).
Risk mitigation: Pydantic GitHub models do not forbid extra fields, so a
dry_run-incompatible tool passed `dry_run=True` would silently execute for real — hence
strict scoping (UNK-01). GitHub mutation tools route through approval
(`tool_policy.py::_GITHUB_MUTATION_TOOLS`, `_escalate_for_github_branch`), confirming
they reach the dry-run path. Existing `TestCheckApprovalDryRun` (test_tool_approval_preflight.py
lines 447-568) provides the mockable harness for the regression test.
