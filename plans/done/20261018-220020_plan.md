## Background
`scripts/agent/startup_mcp_starter.py` `McpServerStarter.start_servers` iterates the configured subprocess HTTP MCP servers and, for each, attempts a single start then a single retry via `retry_once_with_delay`. On the second failure it branches on `cfg.required`: `required=true` raises a fatal `RuntimeError`; `required=false` calls `disable_server` (set `startup_mode=NONE`, clear `tool_names`) and continues. `disable_server` is defined in the same module and is called only from that branch.

Meanwhile `scripts/shared/mcp_config.py` `McpServerConfig.__post_init__` runs `_validate_cross_fields` -> `_validate_startup_requirements`, which raises `ValueError` when `startup_mode==SUBPROCESS` and `required` is falsy. `_build_mcp_servers` builds every server through this constructor, so no valid runtime `McpServerConfig` can carry `required=false` on a subprocess server. Every subprocess server therefore has `required=true`.

The rejection is intentional and correct (fail closed: a subprocess server that fails to spawn cannot degrade gracefully). The problem is that the startup module still contains the now-impossible graceful path alongside it.

## Problem
Two related defects:

1. Dead code. The `if not cfg.required:` branch in `start_servers` and the entire `disable_server` method can never execute against a real configuration. They exist as if non-required subprocess servers were supported, but the config layer forbids them.
2. Contradictory documentation. The guard comment in `mcp_config.py` states that "the spawn path ignores `required`, so a non-required subprocess server would still abort startup on a spawn failure." The actual spawn path (`start_servers`) does NOT ignore `required` — it branches on it and disables-and-continues for non-required servers. A maintainer reading either side would form an incorrect mental model: the comment suggests the startup code does not honor `required`, while the startup code suggests non-required subprocess servers are handled.

Neither defect causes a runtime fault today. Both are maintenance hazards: a future author who trusts `start_servers` may add logic that depends on the graceful-disable path, and one who trusts the comment may assume the spawn path fails open.

## Reason for change
The divergence is latent now but will surface on the next edit to this path. Removing the dead path and reconciling the comment eliminates a trap and makes the code agree with the documented constraint.

## Implementation intent
Treat this as a cleanup that removes unreachable code and fixes the contradictory comment. Do not change any startup runtime behavior: all subprocess servers remain `required=true` and fail closed on spawn failure. ## Design
Path A (small task): affects 2 files, no public or runtime-facing interface change, no database schema change. This is a behavior-preserving cleanup.

The graceful-disable path is dead for two independent reasons, both confirmed against current source:
1. Config-level: `McpServerConfig` rejects `required=false` for `startup_mode=subprocess`, so no runtime subprocess server can be non-required.
2. Control-flow level: `retry_once_with_delay` re-raises on second failure rather than returning `None`, so the `else` branch that consults `cfg.required` is only reachable when the retry itself returns `None` (a process that neither starts nor raises). Even then `cfg.required` is always `true` for subprocess servers, so the branch always takes the fatal-raise path.

Removing the branch and `disable_server` collapses the two-post-retry-branch structure to a single fatal raise, which is the only behavior any real configuration can exhibit. The comment rewrite makes the guard comment describe the actual mechanism (disallow non-required subprocess servers; spawn failures fail closed) instead of the false claim that the spawn path ignores `required`.
