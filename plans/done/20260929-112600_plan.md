## Background
Filed as `issues/20260929-111108_eventbus001_ack-endpoint-authorization-bypassed-when-principal-allowed_consumer_ids-is-none.md`, which described this as a possible production authorization bypass: an ACK request for a `consumer_id` the principal does not own returns `200` instead of `403`/`409`, with a debug log showing `_principal.allowed_consumer_ids=None` at the check site despite the test fixture setting `allowed_consumer_ids=frozenset({"consumer-A"})`.

Deeper investigation during this planning cycle (adversarial verification of the Issue's claims, per `rules/ai-execution.md`) traced the full request path and found the root cause is **not** a production authorization defect:

- `scripts/eventbus/app.py`'s `ack_event()` route depends on `require_role(Role.CONSUMER)` (for `_principal`) and `require_consumer_identity` (for `_identity`), both of which depend on `scripts/eventbus/auth.py::resolve_principal()`, which correctly reads `allowed_consumer_ids` from `_TOKEN_PRINCIPAL_MAP`.
- `scripts/eventbus/app.py`'s `lifespan()` (lines ~68-74) calls `_populate_token_maps(app.state.config)` on FastAPI startup, which does `_TOKEN_PRINCIPAL_MAP.clear()` and repopulates every token's `Principal` fresh from config.
- The `principal_client` fixture (`tests/eventbus/test_eventbus_ack_endpoint.py:44-81`) calls `_populate_token_maps(cfg)` and then overrides `consumer-token`'s `allowed_consumer_ids` to `frozenset({"consumer-A"})` at lines 66-76 — **before** entering `with TestClient(eb_app.app) as c:` (line ~82, outside the excerpt above but confirmed by direct read). Entering `TestClient(...)` triggers FastAPI's `lifespan` startup event, which re-runs `_populate_token_maps()` and wipes out the fixture's override, resetting `consumer-token`'s `allowed_consumer_ids` back to `None` (the default "any consumer_id" value) before any test request is made.
- This means the request-time `_principal.allowed_consumer_ids=None` observed in the failing test's debug log is explained entirely by this fixture-ordering issue — the actual production auth-resolution code (`resolve_principal`, `require_consumer_identity`, `ack_route.py`'s inline check) is not implicated. A real deployment calls `_populate_token_maps()` exactly once at real startup from real config, with no later override to be wiped out.

This corrects the originating Issue's "Reason for Change" framing (production security risk) — see Reason for change below for the corrected framing.

## Problem
`principal_client`'s custom `Principal` override for `consumer-token` (`tests/eventbus/test_eventbus_ack_endpoint.py:70-76`) is applied before `TestClient(eb_app.app)` triggers the app's `lifespan` startup handler, which unconditionally re-populates `_TOKEN_PRINCIPAL_MAP` from config and discards the override. `TestAckEndpoint::test_ack_event_principal_ownership_validation` therefore exercises a principal with no consumer restriction, so the ownership check it means to test never triggers, and the ACK request succeeds with `200` instead of the expected `403`/`409`.

## Reason for change
The test currently gives a false signal: it reads as verifying a security-relevant authorization boundary (consumer ID ownership on ACK) but, due to the fixture bug, does not actually exercise that boundary at all. Fixing the fixture restores real test coverage for this authorization check going forward — it not being caught until now means a future regression in `resolve_principal`/`require_consumer_identity`'s actual ownership logic would also go undetected. This is a testability/test-integrity fix, not a response to an active production vulnerability.

## Implementation intent
Move the `_TOKEN_PRINCIPAL_MAP["consumer-token"]` override block in the `principal_client` fixture to after `with TestClient(eb_app.app) as c:` has been entered (i.e., after `lifespan` startup has already run and repopulated the map once), so the override is the last write to that entry before any test issues a request through `c`. Update the fixture's inline comment, which currently attributes the override's effect to `_TOKEN_CONSUMER_MAP` (a scheme `scripts/eventbus/auth.py`'s own comment says has been replaced by the current role-based `_TOKEN_PRINCIPAL_MAP` resolution), to reference the mechanism actually in effect.

## Requirements

- `REQ-002`: Correct the fixture's stale `_TOKEN_CONSUMER_MAP` comment reference to describe the current `_TOKEN_PRINCIPAL_MAP`-based mechanism.
