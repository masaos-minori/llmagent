# Plan: Fix EventBus Role-Based Authorization Gap

## Goal
- Fix the EventBus route-role authorization gap where `require_role` and `require_consumer_identity` FastAPI dependencies are wired on delegated-to functions that are never invoked through FastAPI's dependency-injection system, causing all authorization checks to be bypassed. Additionally, address the `require_consumer_identity` return-type mismatch (`None` vs expected `dict`) and populate `_TOKEN_CONSUMER_MAP`/`_TOKEN_TOPIC_MAP` from configuration.

## Priority
High

## Scope
- **In-Scope**: Fix the authorization wiring gap so that role-based and consumer-identity checks actually execute; resolve the `require_consumer_identity` return-type contract mismatch; add configuration support for per-role/per-consumer token mapping; update affected tests.
- **Out-of-Scope**: Changing the Bearer-token presence/validity check itself (`verify_bearer_token`, `attach_auth_middleware`); any other MCP server's `attach_auth_middleware` usage; adding new MCP servers; database schema changes beyond what is necessary for the authorization mechanism.

## Background
The EventBus service defines a route-role access-control boundary via `_ROUTE_ROLE_MAP` in `scripts/eventbus/auth.py`: only `Role.OPERATOR` callers should reach `/dlq`, `/dlq/requeue`, `/replay`; only `Role.PUBLISHER` should reach `/publish`; only `Role.CONSUMER` should reach `/subscribe`, `/ack`, `/nack`. However, none of this is enforced because the authorization dependencies are declared on the wrong layer of the call chain.

## Problem
`scripts/eventbus/app.py` registers FastAPI routes (`@app.get("/dlq")`, `@app.get("/subscribe")`, etc.) whose handler functions delegate to real logic in `scripts/eventbus/dlq_route.py`, `subscribe_route.py`, `ack_route.py`, and `replay_route.py` via plain `await` calls. Those delegated-to functions carry `Depends(require_role(...))` / `Depends(require_consumer_identity)` parameters — not the `@app.get/post`-registered wrapper functions. Because FastAPI resolves dependencies only for registered route handlers, the delegated-to functions' `Depends(...)`-defaulted parameters are never resolved by FastAPI at all. When called as plain functions, Python uses each parameter's literal default value — the un-evaluated `Depends(...)` marker object itself — so the authorization function bodies never run.

Independently, `require_role`'s own check compares the endpoint's hardcoded `role` argument against `_ROUTE_ROLE_MAP[path]` — it never inspects the caller's token to determine what role the caller holds. There is no code anywhere that maps a caller's Bearer token to a `Role`.

`require_consumer_identity` compounds this: its return type is `None` (nothing is returned on success), but `subscribe_route.py`'s `subscribe()` does `_identity.get("topics", set())` on its result, assuming a `dict`. Even if FastAPI did resolve this dependency correctly, the call would raise `AttributeError: 'NoneType' object has no attribute 'get'`.

Finally, `scripts/eventbus/auth.py`'s module-level `_TOKEN_CONSUMER_MAP` and `_TOKEN_TOPIC_MAP` dicts are initialized empty and are never populated from `EventBusConfig`, any config file, or any other source.

## Reason for change
This is security-sensitive: the route-role map documents an intended access-control boundary but none of it is enforced. Any caller with the single shared `auth_token` currently has full access to every endpoint. This also crashes tests whenever a test actually reaches the code path that depends on `require_consumer_identity`.

## Implementation intent
Re-architect the authorization mechanism so that:
1. Role-based and consumer-identity checks are actually executed for every request
2. A caller's role is determined from their Bearer token (per-role tokens in config)
3. `require_consumer_identity` returns a proper identity dict matching its callers' expectations
4. `_TOKEN_CONSUMER_MAP`/`_TOKEN_TOPIC_MAP` are populated from configuration at startup

## Requirements
- `REQ-001`: All route-role authorization checks must execute for every request — `require_role` and `require_consumer_identity` must be declared on the FastAPI route handlers registered in `app.py` (or called explicitly within them), not on delegated-to functions that are never resolved by FastAPI's DI.
- `REQ-002`: A caller's role must be determined from their Bearer token. Each configured token maps to a specific role, and the authorization check verifies the caller's token grants the required role for the requested endpoint.
- `REQ-003`: `require_consumer_identity` must return a dict-like object with a `topics` key containing a set of permitted topics, matching the contract expected by `subscribe_route.py`'s `subscribe()` function.
- `REQ-004`: `_TOKEN_CONSUMER_MAP` and `_TOKEN_TOPIC_MAP` must be populated from `EventBusConfig` at startup, not left as empty dicts.
- `REQ-005`: The existing single-shared-token deployment model must not break unless a migration path is designed (config files, deployment docs, operational tooling currently assume one `auth_token`).

## Design
### Authorization Architecture Decision
The fix requires moving authorization from the delegated-to route functions to the FastAPI route handlers registered in `app.py`. Two approaches are viable:

**Approach A: Declare dependencies on wrapper functions**
Move `Depends(require_role(...))` declarations from the delegated-to functions to the `@app.get/post`-registered wrapper functions in `app.py`. This makes FastAPI's DI system resolve the dependencies correctly. The delegated-to functions would receive resolved role/consumer-identity values as regular parameters.

**Approach B: Explicit invocation within wrappers**
Keep the delegated-to functions unchanged (remove their `Depends(...)` defaults) and have the wrapper functions explicitly call `require_role()` / `require_consumer_identity()` as plain awaited functions before delegating. This avoids relying on FastAPI's DI entirely.

Approach A is preferred because it aligns with FastAPI's idiomatic usage pattern and keeps authorization logic declarative. Approach B would require duplicating authorization logic in each wrapper function.

### Token-to-Role Mapping
Since the current single-shared-token model makes role determination impossible, the fix introduces per-role tokens in the EventBus TOML config. Each configured token maps to a specific role, and the authorization check verifies the caller's token against the required role for the requested endpoint.

### `require_consumer_identity` Return Type Fix
`require_consumer_identity` must return a dict-like object with a `topics` key containing a set of permitted topics. The fix changes the return type from `None` to `dict[str, Any]` and ensures the returned dict always contains the `topics` key.
