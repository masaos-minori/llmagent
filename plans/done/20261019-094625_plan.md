## Goal
- Make Memory vector storage and KNN search work on the real `session.sqlite` connection by adopting Session Vector: amend ADR-008 (and every document restating its scope) so sqlite-vec is loaded for the two databases that own a vec0 table (`rag.sqlite`, `session.sqlite`), make `SQLiteHelper("session")` load it by default, make the Memory KNN query valid for vec0, and verify it with tests that run against a real vec-enabled session database.

## Priority
High

## Background
- Origin: review memo1.md V26-05, reproduced on 2026-10-19. The owner decided option 1 (adopt Session Vector by amending ADR-008) with connection fix (b) (change the helper default for `session`), and asked for the issue and this plan.
- ADR-008 states sqlite-vec is loaded only into `rag.sqlite` (Constraints, Decision 9, INV-08). Its own Reconsideration Conditions list "sqlite-vec is needed in a database other than `rag.sqlite`" as a trigger for revisiting the ADR, so an amendment is the sanctioned path.
- The Memory schema places `memories_vec` (vec0) in `session.sqlite`; `tools/check_db_separation.py` already registers it as a session-owned vec table.
- Session and Memory are a logical responsibility split inside one physical database; this plan does not change that.

## Problem
- Reproduced with the real `SQLiteHelper("session")` path on a temporary database: with `load_vec` unset, `INSERT`, `COUNT`, and KNN `MATCH` on `memories_vec` raise `sqlite3.OperationalError: no such module: vec0`; with `load_vec=True`, `COUNT` and KNN succeed.
- Cause: the helper sets `_default_load_vec = (resolved == "rag")`, and the only runtime `load_vec=True` is in schema creation. Every Memory call site opens `SQLiteHelper("session")` without `load_vec`.
- Effects:
  - Retrieval with an embedding catches the `OperationalError`, logs a WARNING, and returns FTS-only results on every call, so hybrid retrieval never happens and the failure is silent.
  - Writes with an embedding (`add`, `upsert`) call `_write_vec` inside `begin_immediate()`; the `OperationalError` propagates out of the write function, and the ingestion persist helper does not catch it, so a write whose embedding was fetched successfully fails.
- Second defect, found while verifying this plan (2026-10-19) by running the Memory code against a real vec-enabled session database with the helper default simulated as fixed: write, replace, delete, and `count_vec` then succeed, but `VectorRetriever.knn_search` still fails with `sqlite3.OperationalError: A LIMIT or 'k = ?' constraint is required on vec0 knn queries`. The query joins `memories_vec` to `memories` and applies `LIMIT` outside the join, which vec0 does not accept. A query that wraps the KNN in a subquery with `k = ?` and joins afterward returned the expected rows. Fixing the connection alone therefore does not make hybrid retrieval work.
- Tests mask it: unit tests create `memories_vec` as a plain table, the integration fixtures swallow the schema exception, and the retriever test uses an in-memory database without vec.

## Reason for change
- Correctness: a documented Memory feature (hybrid retrieval, vec index maintenance, `reindex --vec`, `rebuild`) cannot work on the production connection, and part of the failure is silent.
- Documentation and tooling conflict: the normative rule ("RAG only") contradicts the implemented and checked schema ownership, and the check tool currently pins the defect (it fails if the helper default stops being `resolved == "rag"`).
- The owner has made the design decision, so the conflict can now be resolved in one coordinated change.

## Implementation intent
- Resolve the design once, in the ADR, then make the helper, the check tool, the documents, and the tests express that single rule.
- Rule: sqlite-vec is loaded by default for each database that owns a vec0 table (`rag`, `session`) and for no other target; an explicit `load_vec` argument still overrides the default, and an explicit `db_path` keeps its current derivation from `sqlite_vec_so`.
- Fix the connection in one place (the helper default) rather than adding `load_vec=True` at Memory call sites, so `LOAD_VEC_SANCTIONED` does not grow.
- Keep the check tool as the enforcement point: change what it pins, not whether it pins.
- Prove the fix with a failing-first real-DB test, then the helper change.

## Design
- Path B (more than 3 files; changes a runtime-facing helper default). Analyses run: architecture (`lint-imports`: 6 contracts kept, 0 broken), dependency graphing (44 `session` target usages in `scripts/`; `scripts/db/create_schema.py` is the only explicit `load_vec=True`), historical (churn per file above; single author), operational (no deployment performed by this plan). `radon` shows low complexity for `scripts/db/helper.py`; `bandit` reports only informational `nosec` notices.
- Decision: change the default in the helper, not the Memory call sites. One edit covers `write_ops`, `retriever`, `count_ops`, `rebuild_ops`, `import_ops`, and `store`, and keeps `LOAD_VEC_SANCTIONED` unchanged.
- The helper default becomes membership in the set of databases that own a vec0 table. The check tool's `VEC_TABLES` inventory already records that set; the plan keeps the two descriptions of the set consistent rather than introducing a second source of truth.
- Retriever fix: wrap the KNN in a subquery bounded by `k = ?` and join `memories` afterward, keeping the type and branch filters on the outer query. This is the smallest change that vec0 accepts; the return shape, score convention (negated L2 distance), and RRF merge are untouched. Existing tests mock `knn_search`, so none depend on the SQL text.
- Failure behavior: the existing helper semantics are kept for `session` (load only when `sqlite_vec_so` is configured; a load error raises). This is parity with `rag`, not new behavior; UNK-01 records the alternative.
- ADR handling: INV-08 and Decision 9 are rewritten from "only `rag.sqlite`" to "databases that own a vec0 table: `rag.sqlite` and `session.sqlite`". The Reconsideration Conditions bullet is the trigger that justifies the amendment and is left as history. `tools/check_adr_preservation.py` will flag INV-08; see UNK-03.
- Test design: the real-DB test file creates the schema through the same path production uses (`build_session_schema_sql` with the extension loaded) and then opens the connection with default arguments, so a regression in the default fails the test.

## Risks
- **Risk**: Loading the extension on every session connection adds open latency or fails where the `.so` is missing. → **Mitigation**: Same semantics as `rag` (loaded only when `sqlite_vec_so` is configured); measure in Phase 2 (UNK-02); tests use `sqlite_vec_so=""` or an explicit `db_path`, which keep their current default.
- **Risk**: The ADR INV-08 rewrite is blocked by `tools/check_adr_preservation.py` or the pre-commit hook. → **Mitigation**: The amendment is recorded in the Approval Record and the commit message; if the hook blocks the commit, stop and report rather than bypassing it (UNK-03).
- **Risk**: Widening the helper default weakens the separation rule for other targets. → **Mitigation**: The check tool keeps rejecting an extension load for `workflow` and `eventbus`, with tests (REQ-004).
- **Risk**: Existing tests that open session connections with a mocked or missing extension start failing after the default change. → **Mitigation**: Run the full suite in Phase 2; `tests/db/test_create_schema.py` already patches `_load_vec_extension`, and tests using an explicit `db_path` with empty `sqlite_vec_so` keep default `False`.
- **Risk**: A real-DB test depends on a development-machine file. → **Mitigation**: Skip explicitly with a reason when `/opt/llm/sqlite-vec/vec0.so` is absent, matching the existing pattern in `tests/agent/memory/test_memory_retriever.py`.

- **Risk**: With the KNN bound applied before the type and branch filters, fewer than `limit` rows can come back when many nearest rows are filtered out. → **Mitigation**: Use the existing candidate limit as `k`, record the behavior in the real-DB test, and treat a larger over-fetch as a follow-up (UNK-05).
