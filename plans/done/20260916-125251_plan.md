## Goal
- Make process-level configuration ownership enforcement, loader/exception
  documentation, validation-result typing, and Agent/RAG configuration-shape
  consumption consistent across `scripts/shared/config_loader.py`,
  `scripts/shared/config_errors.py`, `scripts/shared/config_validator.py`, and
  `scripts/shared/production_config_validator.py`, so that: (1) the Agent
  process enforces `ConfigLoader.restrict_to()` unconditionally, matching
  every other process entry point; (2) the allowed-file set cannot be
  broadened after initialization except through an explicit test-only reset;
  (3) loader documentation lists every exception type it can raise; (4) only
  one `ConfigValidationResult` type exists; (5) RAG/production config
  consumers agree on one canonical (flat) configuration shape; and (6) valid
  top-level configuration keys are derived from one explicit schema source
  instead of a function mixing dataclass introspection with an ad hoc manual
  list.

## Priority
Medium

## Problem
Adversarial verification against current source (Step 2/3) found:
- `scripts/agent/context.py`'s `AgentContext.__init__` only calls
  `ConfigLoader.restrict_to("agent.toml")` when the `AGENT_RESTRICT_CONFIG`
  environment variable is set (`if os.environ.get("AGENT_RESTRICT_CONFIG"):
  ConfigLoader.restrict_to("agent.toml")`). `deploy/start_agent.sh` (the
  actual production startup script) never sets this variable. Every other
  process entry point in the repository calls `restrict_to()`
  unconditionally or fails closed: `scripts/rag/ingestion/crawler.py`,
  `ingester.py`, and `chunk_splitter.py` call it unconditionally at their
  `if __name__ == "__main__":` block; `scripts/mcp_servers/server.py::run_http()`
  raises `ConfigPermissionError` if `own_config_file` is falsy. The Agent
  process is the sole exception — confirming the Issue's claim that
  `restrict_to()` initialization is not mandatory before production
  configuration loading.
- `docs/adr/ADR-002-config-isolation.md`'s CI-001 Known Deviation entry
  states "Agent-side, `ConfigLoader.restrict_to("agent.toml")` was added to
  `AgentContext.__init__`" with `Status: Resolved (2026-08-25)` — this
  documentation is stale relative to the current, still-conditional code
  (confirmed by `implementations/done/20260825-174354_01_scripts_agent_context.py.md`,
  which shows the `AGENT_RESTRICT_CONFIG` guard was deliberately added for
  test isolation, not removed later).
- `ConfigLoader.restrict_to()` currently allows the allowed-file set to be
  broadened or changed after initialization (`tests/shared/test_config_loader.py::
  test_multiple_restrict_calls_last_wins` documents "last call wins" as
  today's intended behavior) — confirming the Issue's claim.
- `ConfigLoader.load()`'s docstring ("raises ValueError on missing/parse
  error") does not mention `ConfigPermissionError` (a `RuntimeError`
  subclass, not a `ValueError`) or `ConfigReadError` — confirming this part
  of the Issue's exception-documentation claim.
- **Correction to the Issue's claim**: `ConfigLoader.load_all()`'s
  strict-default documentation is already accurate in current source
  (`strict: If True (default), raise ConfigMissingError for any missing
  required config file...`) and matches the actual `strict: bool = True`
  default. `docs/00_governance_03_issue-and-uncertainty-management.md`
  (CI-005 entry) confirms this exact docstring/behavior mismatch was already
  corrected on 2026-09-14, predating this Issue. No further action is
  required for this specific sub-claim (see Assumptions).
- `ConfigValidationResult` is defined twice: `scripts/shared/config_validator.py`
  (fields without default factories, plus an `ok` property) and
  `scripts/shared/production_config_validator.py` (both fields default to
  `field(default_factory=list)`, no `ok` property) — confirming the Issue's
  claim. `ProductionConfigValidator.validate_unknown_tool_safety_tiers()`
  relies on the `warnings` field's default factory
  (`ConfigValidationResult(errors=errors)`, omitting `warnings`) — a
  compatibility constraint for REQ-004 (see Risks R-3).
- `RagConfigValidator._extract_rag_section()`'s docstring claims it
  normalizes "nested `{"rag": {...}}` (agent.toml) and flat `{...}` (MCP
  module_cfg) shapes," but `config/agent.toml` has no `[rag]` table — its RAG
  keys (e.g. `embed_url`) are flat top-level keys, confirmed by direct
  inspection. All three production call sites
  (`scripts/rag/config_resolution.py`, `scripts/mcp_servers/rag_pipeline/
  rag_pipeline_models.py`, `scripts/agent/config_builders.py::_build_rag_config()`)
  pass flat dicts; the nested `{"rag": {...}}` branch is exercised only by
  `tests/shared/test_config_validator.py`, never by a production caller
  (confirmed by `rg '"rag":\s*\{'`). This refines the Issue's "differently-
  shaped" claim: the practical inconsistency is a stale docstring and an
  untested-in-production dead branch, not divergent production behavior.
- `ProductionConfigValidator._get_valid_production_keys()` combines dataclass
  field introspection over 9 sub-config classes with three separate blocks of
  manually-added keys (`agent_memory_max_startup_snippets`;
  `system_prompt_tool`/`security_profile`; `diagnostics`; and 11 DB/RAG
  subsystem path keys) — confirming the Issue's "mixed dataclass
  introspection and manual additions" claim by direct reading of the
  function body.
- No test currently loads `config/agent.toml` (the real production file) and
  runs it through `RagConfigValidator`/`ProductionConfigValidator`
  end-to-end (confirmed by `rg` across `tests/shared/`) — confirming the
  Issue's "add integration tests using the actual production configuration
  shape" gap. Running both validators against the real file manually during
  this Plan's analysis produced zero errors/warnings from either validator,
  confirming REQ-005's flat-shape canonicalization is compatible with the
  current production configuration.

## Reason for change
Process file restrictions, loader exception documentation, duplicated
validation result types, and inconsistent configuration-shape handling all
affect the same configuration-authority boundary that
`docs/adr/ADR-002-config-isolation.md` already governs; repository evidence
confirms each sub-claim is real (except the already-corrected `load_all()`
docstring sub-claim) and unresolved by any other in-flight Plan.

## Implementation intent
Make the Agent process's config-isolation enforcement structurally identical
to every other process's (unconditional `restrict_to()`), close the
allowed-file-set broadening gap with an explicit test-only reset mechanism,
document the loader's full exception contract, consolidate the duplicate
`ConfigValidationResult` into one canonical definition (preserving both
fields' default factories for backward compatibility), standardize RAG
configuration consumption on the flat shape actually used in production, and
replace the ad hoc valid-key derivation with one explicit, named schema
source that `ProductionConfigValidator` reads from — without redesigning
`AgentConfig` or introducing a new schema-validation library.

## Requirements
- `REQ-001`: The Agent process MUST call `ConfigLoader.restrict_to("agent.toml")`
  unconditionally in `AgentContext.__init__`, before `build_agent_config()`
  runs — removing the `AGENT_RESTRICT_CONFIG` environment-variable gate — so
  that production configuration cannot be loaded by the Agent process before
  process-level restriction is established, matching every other process
  entry point.
- `REQ-002`: `ConfigLoader.restrict_to()` MUST reject a later call that would
  change the already-established allowed-file set, except through a new,
  explicit, dedicated test-only reset mechanism (a public classmethod, not a
  direct write to the private `_allowed_files` attribute).
- `REQ-003`: `ConfigLoader.load()`'s (and, where applicable, `load_all()`'s)
  docstrings MUST document every exception type the method can raise,
  including `ConfigPermissionError` (a policy/permission failure, not a
  `ValueError`) and `ConfigReadError`.
- `REQ-004`: The two duplicate `ConfigValidationResult` dataclasses
  (`scripts/shared/config_validator.py`,
  `scripts/shared/production_config_validator.py`) MUST be unified into one
  canonical definition, hosted in `scripts/shared/config_validator.py` and
  imported by `production_config_validator.py`, preserving the `ok` property
  and `field(default_factory=list)` defaults on both `errors` and `warnings`
  fields (required by `validate_unknown_tool_safety_tiers()`'s
  single-argument construction — see Risks R-3).
- `REQ-005`: `RagConfigValidator` MUST consume one canonical (flat)
  configuration shape; the nested `{"rag": {...}}` special case in
  `_extract_rag_section()`, exercised only by test fixtures and no production
  caller, MUST be removed, and its docstring corrected.
- `REQ-006`: `ProductionConfigValidator`'s valid-top-level-key set MUST be
  derived from one explicit, named canonical schema source instead of a
  function that mixes 9-dataclass field introspection with three separate
  inline manual-addition blocks — without changing which keys are valid.
- `REQ-007`: Add integration test(s) that load the actual `config/agent.toml`
  production file via `ConfigLoader().load_all()` and assert both
  `RagConfigValidator` and `ProductionConfigValidator` accept it with zero
  errors.
- `REQ-008`: Once REQ-001 is implemented and verified, correct
  `docs/adr/ADR-002-config-isolation.md`'s CI-001 Known Deviation entry so it
  accurately reflects unconditional Agent-process enforcement (no
  environment-variable gate), per the Issue's own Documentation Impact
  instruction ("update ... only after executable verification is available").

## Acceptance criteria
- AC-1 (REQ-001): Production configuration cannot be loaded by the Agent
  process before `ConfigLoader.restrict_to("agent.toml")` has been called —
  enforced unconditionally, not gated behind an opt-in environment variable.
- AC-2 (REQ-002): The restriction set cannot be broadened or changed after
  initialization except through an explicit, dedicated test-only reset
  mechanism.
- AC-3 (REQ-003): Loader documentation (`load()`/`load_all()` docstrings)
  lists every exception type raised, including `ConfigPermissionError` and
  `ConfigReadError`.
- AC-4 (REQ-004, REQ-005): RAG and production validators consume the same
  canonical `ConfigValidationResult` type and the same canonical (flat)
  configuration shape.
- AC-5 (REQ-006): Unknown top-level keys are rejected using one canonical,
  explicit schema source, not a function mixing two independent derivation
  mechanisms.
- AC-6 (REQ-007): An integration test loads the actual production
  `config/agent.toml` and confirms both validators accept it with zero
  errors.
- AC-7 (REQ-008): `docs/adr/ADR-002-config-isolation.md`'s CI-001 entry
  accurately reflects unconditional Agent-process enforcement after REQ-001
  lands.

## Design
**REQ-001/REQ-002 (`config_loader.py`, `context.py`)**: `AgentContext.__init__`
drops the `AGENT_RESTRICT_CONFIG` guard and calls
`ConfigLoader.restrict_to("agent.toml")` unconditionally, mirroring
`crawler.py`/`ingester.py`/`chunk_splitter.py`'s existing unconditional
calls and `server.py`'s fail-closed pattern. Because `_allowed_files` is a
process-wide class attribute, this makes every pytest process that
constructs an `AgentContext()` restricted for the remainder of that process
unless reset — `tests/conftest.py` gains an autouse fixture that calls the
new test-only reset classmethod after every test, replacing the
file-scoped, ad hoc resets currently duplicated in
`tests/shared/test_config_loader.py` and
`tests/agent/test_config_permission_cross_server.py` (those files may keep
their own fixtures; the new global one is a safety net for every other test
file that was not previously resetting state at all). `restrict_to()` itself
gains a check: if `_allowed_files` is already set to a set different from
the one requested, it raises rather than silently overwriting — except when
invoked through the new reset path, which clears `_allowed_files` back to
`None` first.

**REQ-004 (`config_validator.py`, `production_config_validator.py`)**: The
canonical `ConfigValidationResult` moves to (or is confirmed to remain in)
`scripts/shared/config_validator.py`, keeping the `ok` property and adding
`field(default_factory=list)` to both `errors` and `warnings` — the default
factory is required because `production_config_validator.py`'s
`validate_unknown_tool_safety_tiers()` constructs
`ConfigValidationResult(errors=errors)` without `warnings=`.
`production_config_validator.py` imports this class instead of defining its
own; both layers already only reference `.errors`/`.warnings`/`.ok`, so no
call site changes beyond the import.

**REQ-005 (`config_validator.py`)**: `_extract_rag_section()` drops the
`cfg["rag"] if "rag" in cfg else cfg` branch in favor of always treating the
input as flat, matching all three production call sites; its docstring is
corrected to describe the single flat shape.

**REQ-006 (`production_config_validator.py`, `config_dataclasses.py`)**:
`config_dataclasses.py` exposes one named tuple/list of the 9 sub-config
classes (the schema root); `_get_valid_production_keys()` iterates that
import instead of a hardcoded inline list, and its remaining manual
additions are consolidated into one named constant (rather than three
separate `.add()`/`.update()` blocks with scattered comments) — combined
with the schema-root fields in one place. The resulting valid-key set is
unchanged (T-7).

**REQ-007**: New integration test(s) call `ConfigLoader().load_all()`
against the real `config/` directory (no monkeypatched `config_dir`) and run
the result through both validators, asserting zero errors — this is the
concrete evidence artifact this Plan's own manual verification (Problem
section) becomes a permanent regression test for.

**REQ-008**: Documentation-only correction to ADR-002's CI-001 entry, gated
on REQ-001's tests passing.
