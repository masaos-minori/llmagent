## 1. Goal

Protect sensitive diagnostic data by filtering redacting fields before persistence. Add optional encryption and automatic retention policies to reduce exposure risk.

## 2. Scope

### In-Scope
- Define and implement filter that removes or redacts sensitive fields from diagnostic summary
- Add optional encryption layer using configurable key for diagnostic data storage
- Implement retention policy that automatically deletes records older than configurable period
- Log warnings when sensitive data is filtered out

### Out-of-Scope
- Changes to artifact URI generation logic
- Changes to RAG query result collection
- Changes to database schema
- Changes to HTTP client lifecycle

## 3. Assumptions

- Sensitive fields should be redacted (not removed) to preserve data structure integrity
- Encryption key should be loaded from environment variable or configuration file
- Retention policy default should be 30 days
- Redaction should replace values with "[REDACTED]" while preserving field names
- Encryption should use AES-256-GCM for authenticated encryption

## 8. Risks & Mitigations

- **Risk**: Encryption key management complexity may introduce operational burden. → **Mitigation**: Provide clear documentation for key rotation procedures; support key derivation from passphrase.
- **Risk**: Retention policy deletion may cause data loss if misconfigured. → **Mitigation**: Require explicit confirmation for retention periods shorter than 7 days; log all deletions for audit.
- **Risk**: Redaction may break downstream analysis tools expecting original data format. → **Mitigation**: Provide configuration option to disable redaction during transition period; document breaking changes in release notes.
