# Run Turn-Entry Work Once Per Turn, Not Once Per Execute Stage Attempt

**Plan ID**: 20261023-102728
**Source Issue**: issues/20261021-093421_turn002_execute-stage-retry-duplicates-user-messages.md
**Generated**: 2026-10-23 10:27 JST
**Task Size**: Path B. One production file changes, but the change moves a responsibility across the
`workflow_engine_adapter` ↔ `workflow_engine` retry boundary, contradicts two documented stage
contracts, and needs a test strategy that does not exist today (no test has ever forced an
adapter-level stage retry). Path A conditions are not met: the change is not internal-only, existing
tests do not cover the boundary, and the direction required a user decision.

## Goal

Make one user turn perform its input preparation once, no matter how many times the workflow engine
retries the `execute` stage.

Today `WorkflowTurnExecutor.execute_turn()` registers `_process_turn()` as the `execute` stage callback
(`scripts/agent/workflow_engine_adapter.py:161-166`), and `_process_turn()` does two different kinds of
work in one body: turn-entry preparation — clear the previous turn's ephemeral messages (`:332`), inject
memory (`:333`), classify the turn mode (`:334`), append the user message (`:335`), compress history
(`:336`) — and the per-attempt LLM/tool execution (`:338-344`). The `execute` stage is
`retryable: true` with `max_attempts: 3` (`config/workflows/default.json:11-14`, `:21-24`), and the
engine re-invokes the whole callback on any exception (`scripts/agent/workflow/workflow_engine.py:149-153`).
So a retried turn appends the user message once per attempt, increments `stat_turns` once per attempt,
runs memory injection and mode classification once per attempt, and writes one `kind='user'` row into
`session.sqlite` per attempt.

This Plan changes one thing:

1. Turn-entry preparation becomes an explicit once-per-turn step that `execute_turn()` runs after task
   activation and before `engine.run()`. The `execute` stage keeps only LLM/tool execution, its error
   classification, assistant persistence, and its own `audit_stage_completed` call.

Nothing else changes. `execute_turn()`'s signature and `(answer, error_kind, is_partial)` return, the
zero-argument `StageCallback` shape (`workflow_engine.py:28`), the `try` / `except` / `finally` structure
that updates task status and closes stores (`workflow_engine_adapter.py:186-202`), the `verify` stage
(`:178-183`), and the engine itself are untouched.

## Priority

- Severity: Medium-High. The defect writes durable state: a retried turn leaves multiple user messages
  in `session.sqlite` and multiple entries in the conversation history that every later request for that
  session replays (`scripts/agent/session_message_repo.py:219` orders by `message_id`, and the history is
  sent to the provider unchanged). It also inflates `ctx.stats.stat_turns`, which is the counter the
  turn001 plan had to stop deriving task keys from (`plans/20261023-093153_plan.md` REQ-002).
- User-visible impact: latent today, not observed. `workflow.sqlite` has 0 `tasks` rows and an empty
  `attempts` table, no duplicated `kind='user'` content was found in the live `session.sqlite` files, and
  no agent process is running (`pgrep -af agent.main` empty). The trigger is an exception escaping
  `_process_turn`, not an ordinary LLM failure (see Problem item 5).
- Blast radius: Medium. One production module's internals (`execute_turn`, `_process_turn`), two test
  files with 7 existing call sites, and two documentation chapters whose text states the opposite of the
  new boundary. No public signature change, no schema change, no config change.
- Blocking dependencies: none. `plans/20261023-093153_plan.md` (turn001, `scripts/db/workflow/task_ops.py`,
  `scripts/agent/workflow/state_store.py`) and `plans/20261023-072425_plan.md` (tool005, masking) share no
  target file with this Plan. The four plans that touch `scripts/agent/tool_runner.py`
  (`plans/20261022-092413_plan.md`, `plans/20261022-105432_plan.md`, `plans/20261023-004538_plan.md`,
  `plans/20261023-023815_plan.md`) are independent: this Plan does not modify `tool_runner.py`.

## Problem

1. One method carries two lifetimes. `_process_turn()` (`workflow_engine_adapter.py:323-356`) is both the
   once-per-turn preparation and the per-attempt stage body, and it is registered whole as the retryable
   `execute` callback (`:161-166`).
2. The engine re-runs the whole body. `_run_stage_with_retry()` re-invokes the callback after any
   non-timeout exception until `max_attempts` (`workflow_engine.py:149-167`), so each entry effect is
   applied once per attempt.
3. The duplicated effects are durable, not just in-memory: `conversation_state_manager.py:110` appends a
   user message to the history, `:119` writes a `kind='user'` row, `:111` advances `stat_turns`, and
   `:112-118` can spawn the first-turn background task again.
4. Memory injection and mode classification are also re-run (`:333`, `:334`), which means a mode decision
   is recomputed per attempt and `ctx.cfg.tool.allowed_tools` is mutated per attempt
   (`mode_classification.py:289`).
5. The trigger is narrower than the issue states, and one trigger is deterministic: when
   `ctx.turn.current_turn_id` is empty, `attempt_id=""` makes `LLMTurnRunner.run()` raise `RuntimeError`
   (`llm_turn_runner.py:73-78`) on every attempt, so entry work runs three times for one input.
6. Entry failures lose their identity. Today `HistoryCompressionError` and store errors are retried inside
   the stage and, after exhaustion, surface as `WorkflowHaltError` (`workflow_engine.py:156-167`), which
   the adapter treats as a workflow halt (`workflow_engine_adapter.py:186-188`, `:311-321`). A fix that
   moves entry work out must not silently change that outcome.
7. No test exercises it. `grep` over `tests/` for `_process_turn` finds only return-contract call sites
   (`tests/agent/test_orchestrator.py:1167`, `:1491`, `:1529-1530`, `:1909`, `:2038`, `:2082`;
   `tests/integration/test_orchestrator_integration.py:665`, `:706-707`). Engine tests assert attempt
   records, not effect idempotency (`tests/agent/workflow/test_workflow_engine.py:111`, `:131`, `:210`,
   `:240`, `:261`, `:301`).
8. The documentation states the current (defective) contract as intended behavior:
   `docs/23_agent/agent_03_03_turn-processing-flow-workflow-engine.md:79` lists memory injection and mode
   classification under the `execute` stage, and `docs/23_agent/agent_03_01_turn-processing-flow-overview.md:104-113`
   states that `classify_and_inject_mode()` runs in the same stage as the user message append.

## Reason for Change

- The user decision for this issue is recorded: Option A — run turn-entry work exactly once before
  `engine.run()`. (2026-10-23, question "turn002 の実装方向の承認".)
- The once-per-turn boundary already exists in this class: `_init_workflow_task()` and
  `_activate_workflow()` run once before the engine (`:146-152`). Placing preparation next to them keeps
  one mechanism per lifetime instead of adding a third.
- `ConversationStateManager`'s methods are already written as once-per-turn operations — `append_user_message`
  increments the turn counter and spawns the first-turn task (`:111-118`) — so calling them per attempt is
  inconsistent with their own owner. Keeping them unmodified and fixing the call site preserves the
  single-source-of-truth intent recorded by `7b80c8d`.
- The duplicated user message is the input the model re-reads on every later request; unlike a duplicated
  task row it cannot be reconciled by any later read path (`session_message_repo.py:219`,
  `scripts/agent/context.py:124-151` only move messages, `scripts/agent/history.py:147-154` counts
  serialized content and never removes one).
- The turn001 plan removed the `stat_turns`-derived task key, which removed the *collision* this issue
  could cause but not the duplicated increment. This Plan is the remaining half.

## Design

### The turn, and the one thing that changes

```
execute_turn(line, turn_started_at, session_id, existing_task_id=None, ...)   (unchanged contract)
  try:
      task = _init_workflow_task(...)                       # unchanged, :146-151
      _activate_workflow(ctx, task)                         # unchanged, :152  (sets current_task_id)
      with tool_override(self._allowed_tools):              # REQ-004: one scope for both halves
          prepare_turn_input(line, ctx)                     # NEW once-per-turn step  :332-336
            clear_previous_turn_ephemeral_messages()
            handle_memory_injection(line)
            classify_and_inject_mode(line, ctx)             # assigns allowed_tools, still in force below
            append_user_message(line)                       # history + stat_turns + session.save("user")
            handle_history_compression()
          await engine.run(task, plan_fn, execute_fn, verify_fn)     # unchanged, :185
              plan_fn    -> None                                              # unchanged
              execute_fn -> await run_llm_stage(...)          # :338-354 + audit_stage_completed :167-176
              verify_fn  -> _handle_turn_end(...)                             # unchanged
  except (WorkflowHaltError, WorkflowTimeoutError): _handle_workflow_halt(...)   # unchanged, :186-188
  finally: task status update / _deactivate_workflow / close                  # unchanged, :189-202
  return answer, error_kind, is_partial                                      # unchanged
```

The reason one split is enough: every value entry work produces is already read from `ctx`, and the stage's
identity (`workflow_id`, `task_id`, `stage_id`, `attempt_id`) is already read from `ctx` (`:340-343`). No
value needs to cross the new boundary as an argument, which is also forced by the engine's zero-argument
`StageCallback` (`workflow_engine.py:28`).

  UNK-02 keeps the residual visible.
- **Entry failures lose retry coverage.** `HistoryCompressionError` and store errors are retried today because
  they are inside the stage. Mitigated by AC-5 asserting the preserved outcome and by UNK-01 being resolved
  before Phase 2. If a dependency is found, the response is a separate bounded retry inside the owning
  component, not moving entry work back into the stage.
- **Entry work leaves the 120 s stage timeout.** A slow memory search or compression call can now extend a
  turn outside the stage timeout that observability assumes. Mitigated by `TestEntryWorkOutsideStageTimeout`
  and by the documentation row stating the change; the components keep their own bounds
  (`history.py:202-229`).
- **`workflow_engine_adapter.py` crosses the 16384 B gate.** 1586 B of headroom and no baseline. Mitigated by
  keeping the split to two methods with no duplicated plumbing and measuring after Phase 2 (UNK-04); if it
  fails, the preparation helper moves to a private module under `scripts/agent/` rather than adding a
  baseline (`rules/toolchain.md`).
- **Test migration weakens an existing invariant.** The payload-composition and cross-turn-boundary tests at
  `tests/agent/test_orchestrator.py:1496-1533` are the closest to the changed code. Mitigated by AC-7 and by
  migrating call sites only: if an assertion must change, keep the old call unchanged and record it as an
  open question instead of editing the assertion.

  the loader; the existing tests at `:394-399` restore the real `WorkflowEngine` and `create_task` to reach the
  real engine. A new test that does not restore them would exercise no retry. Mitigated by asserting an
  `attempts` row count greater than 1 inside the idempotency test itself.
- **Doc drift between two chapters.** `agent_03_01:121` delegates turn-flow detail to `agent_03_03`; the two
  passages must agree. Mitigated by Phase 3 ordering (the stage chapter first) and
  `check_docs_consistency.py --domain agent`.
