# Plan: Improve HttpTransport asyncio.sleep cancellation handling during retries

## Goal
Improve cancellation responsiveness during retry waits in `HttpTransport.call()`, so that tasks cancelled while sleeping are not blocked until the full sleep duration elapses.

## Priority
Medium

## Scope
- **In-Scope**: Improving cancellation handling in `HttpTransport.call()` during retry waits; updating documentation if needed.
- **Out-of-Scope**: Changing the retry logic itself (number of retries, backoff strategy); modifying other transport layers; changing error handling behavior.

## Background
`scripts/shared/http_transport.py` line 139-140:
```python
if attempt < self._RETRY_MAX - 1:
    await asyncio.sleep(wait_sec)
```

When `attempt < self._RETRY_MAX - 1`, the code sleeps for `wait_sec` seconds (which is `2**attempt`). For `attempt=0`, `wait_sec=1`; for `attempt=1`, `wait_sec=2`.

Currently, when a task is cancelled while sleeping, the `CancelledError` is raised only after the sleep completes. This means that even if the task is cancelled, the caller must wait until the sleep finishes before receiving the cancellation notification.

## Problem
When a task is cancelled during a retry wait, the cancellation is not immediately propagated. The task remains blocked until the sleep completes, reducing responsiveness.

## Reason for change
Improving cancellation responsiveness ensures that long-running operations can be terminated promptly when no longer needed, improving system responsiveness and resource utilization.

## Implementation intent
Either:
1. Use `asyncio.wait_for(asyncio.sleep(wait_sec), timeout=...)` to add a timeout to the sleep, allowing cancellation to propagate sooner
2. Use `asyncio.shield()` to protect the sleep from cancellation while still allowing the task to be cancelled after the sleep completes

Approach 1 is preferred as it provides immediate cancellation propagation.

- REQ-002: Retry logic remains unchanged (same number of retries, same backoff strategy)
- REQ-003: Existing tests pass after the change

Two possible approaches:
1. **Use `asyncio.wait_for()`**: Replace `await asyncio.sleep(wait_sec)` with `await asyncio.wait_for(asyncio.sleep(wait_sec), timeout=...)`. This adds a timeout to the sleep, allowing cancellation to propagate sooner. However, this approach doesn't actually help with cancellation propagation — `wait_for` also doesn't interrupt the underlying coroutine on cancellation.
2. **Use `asyncio.shield()`**: Wrap the sleep in `asyncio.shield()` to protect it from cancellation while still allowing the task to be cancelled after the sleep completes. This approach doesn't improve cancellation propagation either.

Actually, neither approach directly solves the cancellation propagation problem. The correct approach is to check for cancellation before sleeping:
```python
if attempt < self._RETRY_MAX - 1:
    try:
        await asyncio.sleep(wait_sec)
    except asyncio.CancelledError:
        # Re-raise cancellation immediately
        raise
    continue
```

However, this is already the default behavior of `asyncio.sleep()` — it raises `CancelledError` when the task is cancelled. So the issue's claim may be incorrect.

So the issue's claim that "キャンセル例外が `sleep` から送出されない" is actually incorrect. The cancellation exception IS raised from `sleep`.

However, there is a subtle issue here. If the task is cancelled while sleeping, the `CancelledError` is raised, but the sleep coroutine itself is not interrupted. This means that the sleep coroutine continues to run in the background, consuming resources.
