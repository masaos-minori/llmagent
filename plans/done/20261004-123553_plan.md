# Plan: Merged — Tighten CommandValidator python3 allowlist AND strip dangerous env vars via filter_env

**Merges:** Plans 075440 (Tighten CommandValidator python3 allowlist prefix) + 081743 (filter_env strips inherited loader/interpreter env vars)

## Goal
Close two security gaps in HTTP subprocess MCP server launch:
1. Replace the open `startswith("python3")` exception in `CommandValidator.validate()` with a bounded interpreter-basename match (`python3(?:\.\d+)?`) so crafted names like `python3evil` or `python3-config` are rejected.
2. Strip dangerous loader/interpreter environment variables (`LD_PRELOAD`, `LD_LIBRARY_PATH`, `PYTHONPATH`) from the inherited environment in `CommandValidator.filter_env()` using the canonical denylist from `shared.mcp_config`.

## Priority
Medium

## Scope
- **In-Scope**:
  - Modify `scripts/agent/http_lifecycle_command_validator.py`: replace `startswith("python3")` with bounded regex; add `_ENV_KEY_DENYLIST` import and apply it in `filter_env()`.
  - Update `tests/agent/test_http_lifecycle_command_validator.py`: rewrite unbounded-prefix test; add negative/positive interpreter tests; add `TestCommandValidatorFilterEnv` class.
- **Out-of-Scope**:
  - Changing the primary command allowlist contents (`node`, `uvx`, `python`, etc.).
  - Adding other env vars (`TZ`, `PYTHONHASHSEED`, `PYTHONHOME`, `PYTHONSTARTUP`) to the denylist — evaluate separately.
  - Any change to subprocess launch logic beyond validation/env filtering.

## Background
HTTP subprocess MCP servers are launched by `HttpServerLifecycleManager._create_and_validate_proc()`, which delegates command validation to `CommandValidator.validate()` and builds the child environment via `env = self._command_validator.filter_env(cfg.env)` in `scripts/agent/http_lifecycle.py`.

Two independent security issues exist:
1. The allowlist check in `CommandValidator.validate()` uses `base_name.startswith("python3")` as an open exception, matching unrelated executables (`python3-config`, `python3-distutils`, `python3evil`).
2. `filter_env()` seeds its result with the full parent environment (`dict(os.environ)`) but only filters config-supplied keys against `_protected_env_vars`. Inherited values such as `LD_PRELOAD`, `LD_LIBRARY_PATH`, and `PYTHONPATH` pass through unchanged when they originate from the agent process. Separately, `scripts/shared/mcp_config.py` defines `_ENV_KEY_DENYLIST = ("LD_PRELOAD", "LD_LIBRARY_PATH", "PYTHONPATH")` and enforces it only when building config (`_validate_env`), never on the runtime env-passing path.

## Problem
Both issues widen the attack surface before arbitrary code execution:
- The allowlist bypass allows crafted executable basenames to pass validation.
- Inherited loader/interpreter env vars enable shared-library hijacking and module injection in subprocesses.

## Reason for change
The allowlist is the final security boundary before process launch, so the interpreter exception must be narrowed to genuine interpreter basenames. The defense-in-depth denylist at the config layer does not cover the runtime env-passing path — since these subprocesses are arbitrary-code-execution sinks, uncontrolled inheritance of ELF/preload and Python-path variables materially widens the attack surface.

## Implementation intent
1. Introduce a bounded, compiled regex `python3(?:\.\d+)?` applied with `re.fullmatch()` against the resolved basename in place of the open `startswith()` check. Keep the primary allowlist membership test unchanged.
2. Import the canonical `_ENV_KEY_DENYLIST` from `shared.mcp_config` into the validator and apply it after seeding `result = dict(os.environ)` in `filter_env()`, eliminating drift between the config and runtime layers.

### Part 1: Bounded interpreter match (Plan 075440)
The fix narrows the interpreter exception to a bounded match. Rationale for the pattern shape: the issue's illustrative `python3\.?\d+` requires a digit after `python3`, which would reject bare `python3`; however `python3` is not in the primary allowlist and existing tests require it to validate successfully, so the pattern must accept both bare `python3` and `python3.<digits>`. The chosen form is `python3(?:\.\d+)?` applied with `re.fullmatch()`, which rejects `python3evil`, `python3-config`, and `python3distutils` while accepting `python3`, `python3.11`, and `python3.12`. The compiled pattern lives at module scope; `validate()` keeps its signature and combines the primary allowlist membership test with the interpreter match using logical OR.

### Part 2: Denylist stripping in filter_env (Plan 081743)
The change narrows only what `filter_env()` drops from the inherited environment. The canonical `_ENV_KEY_DENYLIST` stays owned by `shared.mcp_config`; the validator imports it (allowed by the `agent → shared` import layer) and applies the same `fnmatch` semantics, eliminating drift between the config and runtime layers. `filter_env()` keeps its signature and return contract (`dict[str, str] | None`), returning `None` for `None` input as before.

## Risks
- **Risk**: Over-tightening rejects a legitimately installed interpreter variant used by admin config (a basename outside `python3` / `python3.<NN>`). → **Mitigation**: Pattern accepts only `python3` and `python3.<digits>`; any other variant fails closed with a clear `HttpStartupError` at startup instead of executing silently, so a mismatch is observable rather than a silent security gap. See UNK-01.
- **Risk**: Existing test `test_python3_prefix_allows_python3x` encodes the old unbounded behavior and could mask the intent change. → **Mitigation**: Rewrite that test in Phase 3 to assert bounded acceptance; it currently exercises only real binaries so it may still pass, but its contract claim is incorrect and must be corrected.
- **Risk**: Importing `shared.mcp_config` into the validator adds a cross-layer dependency that may pull heavy transitive config imports into the subprocess validation hot path. → **Mitigation**: Confirm `lint-imports` passes (UNK-03); if the transitive cost is significant, introduce a lightweight shared constants module holding the denylist and import that instead.
- **Risk**: Stripping `PYTHONPATH` may break legitimately configured venv-based Python subprocess launches. → **Mitigation**: Behavior mirrors the existing config-layer denylist (which already excludes `PYTHONPATH`) and fails closed; resolve `PYTHONPATH` acceptability with the reviewer (UNK-02). Document the unsupported case per the issue constraint.
