# Plan: Missing operational guidance for rag-src/registered/ file lifecycle

## Goal
Define the retention period, deletion trigger, and deletion ownership for chunk files moved to `rag-src/registered/` after successful ingestion, and update related documentation to reflect the policy.

## Priority
Low

## Scope
- **In-Scope**: Document retention/deletion policy for `rag-src/registered/` files, update File Lifecycle table in ingestion pipeline overview, replace `(retention TBD)` placeholder in system overview, update Known Issue entry status
- **Out-of-Scope**: Implementing a cron infrastructure (requires separate design decision), changes to the FileRouter's routing logic, changes to the ingestion pipeline's core functionality, changes to the FTS indexing process, changes to the chunk storage format

## Background
After successful ingestion, chunk files are **moved** (via `shutil.move()`) to `rag-src/registered/` by `FileRouter.route()` in `scripts/rag/ingestion/file_routing.py`. The File Lifecycle table in the ingestion pipeline overview documents creation but not deletion of these files. This creates uncertainty about how long files persist and who is responsible for cleanup. Additionally, there is no cron job or scheduled task for cleanup — the project has no automated maintenance mechanism for this directory.

## Problem
No deletion logic exists in `scripts/rag/ingestion/ingester.py` or `file_routing.py`. The `rag-src/registered/` directory may grow unbounded over time, and files may be deleted ad hoc without traceability if this gap is not tracked.

## Reason for change
Without defined lifecycle management, the `rag-src/registered/` directory becomes a source of disk space growth and operational confusion. A clear policy prevents both issues.

## Implementation intent
1. Determine whether files should be retained indefinitely, deleted after a fixed period, or cleaned up by a separate process
2. Define the deletion trigger (e.g., periodic cron job, on-ingestion cleanup of older files) and ownership (which component/process is responsible)
3. Document the policy in the ingestion pipeline documentation and update the Known Issue entry

## Design
This is primarily a documentation task. The policy definition does not require code changes right now because:

1. **Retention policy**: Since files are MOVED (not copied) to `rag-src/registered/`, they are no longer available at the source location. The retention question is whether to keep them indefinitely for audit/debug purposes or delete them after a configurable period. Given that the ingestion pipeline already logs results and error metadata is written for failed chunks, indefinite retention provides diminishing returns.

2. **Cleanup mechanism**: Implementing a cron infrastructure is explicitly out of scope (per issue constraint). The immediate action is to define the policy; implementation of automated cleanup requires a separate design decision. Options include:
   - Operator intervention (manual cleanup)
   - Periodic task integrated into existing scheduling (if/when cron infrastructure is added)
   - On-ingestion cleanup triggered by `RagIngester` itself (would require code change)

3. **Documentation-first approach**: Defining the policy in documentation allows stakeholders to review and agree on the retention period without requiring code changes. This aligns with the issue's AI Implementation Instruction: "Do not implement any cleanup mechanism until the retention policy is defined."
