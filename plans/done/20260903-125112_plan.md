## Background
A repository-wide re-survey at Plan time (the source Issue's own "AI Implementation
Instruction" requires re-running this check, since concurrent work may have shifted
the corpus) found, via `uv run python tools/check_docs_structure.py docs/*.md
docs/adr/*.md`:
- 4 files match `grep -l "^category:"`, and **none of the 4 is a simple, isolated
  key rename** — corrected 2026-09-03 during a separate tooling-improvement task's
  investigation, which found this Plan's original 2-file "pure rename" bucket was
  itself factually wrong (see below). All 4 need some form of structural repair:
  - `docs/04_mcp_05_03_fail-open-fail-closed-and-risk-tiers.md` and
    `docs/04_mcp_03_03_transport-and-health.md` have **no opening `---` fence at
    all** — their `category:` line sits in an unfenced pseudo-YAML block that
    `tools/check_docs_structure.py` does not recognize as front matter, so they are
    correctly counted among the 43 "missing Front Matter" files below (full
    front-matter-block construction, not a rename).
  - `docs/01_overview-files-03-scripts.md` and `docs/01_overview-files-04-shared.md`
    **have an opening `---` fence but no closing `---`** — confirmed via
    `content.find("\n---", 3)` returning `-1` for both files (`check_docs_structure.py`
    independently reports the same: `"Front Matter opening '---' has no closing
    '---'"`). This Plan's own original Implementation Target Files rows for these 2
    files incorrectly stated "front matter otherwise valid" — a factual error in
    this Plan itself, not merely in the source Issue, corrected here. These files
    need a **manual repair** (add a closing `---` immediately before the first body
    line — `# File Structure`-style H1 heading — preserving the existing
    `title`/`tags`/`related` content unchanged) combined with the `category:`→`area:`
    rename, in the same edit. Neither `tools/manage_frontmatter.py add-missing --fix`
    (only handles files with zero front matter) nor its `rename-category-to-area
    --fix` subcommand (requires an already-`---`-terminated block; by design it
    detects this exact case and declines to touch the file, per the "never guess
    ambiguous metadata" principle both tools follow) can safely automate this —
    it is deliberately left for manual `Edit`, matching the source Issue's own
    caution against guessing.
- 43 files currently have no front matter block recognized at all (one more than the
  Issue's investigation-time count of 42 — re-confirmed at Plan time via direct tool
  run).
- 11 ADR files (`docs/adr/ADR-001` through `ADR-010`, plus `ADR-012`) already have
  valid front matter with `title`/`area`/`related` present, but are missing the
  `tags` field — a category the source Issue's Required Changes/Target Files section
  did not enumerate, even though the Issue's own Acceptance Criteria ("every file...
  has a front matter block containing title, area, tags, and related") requires
  fixing them. This Plan adds them as `REQ-003` to satisfy the Issue's own stated
  Acceptance Criteria.
- `tools/manage_frontmatter.py add-missing --fix` only globs `docs/*.md`
  (`DOCS_DIR.glob("*.md")`, non-recursive) — it never reaches `docs/adr/*.md`, and
  even for a `docs/*.md` root file with an existing-but-incomplete front matter
  block, it only *reports* missing fields (`total_issues`), it does not add them.
  The tool can therefore automate only the 43-file "missing entirely" bucket; the 2
  fence repairs and 11 ADR `tags` additions require manual `Edit`.
- **Resolved 2026-09-03**: `tools/manage_frontmatter.py`'s `extract_area_from_filename()`
  previously had no mapping for the `06_eventbus` prefix that this repository's 5
  real EventBus documents actually use (`docs/06_eventbus_00_document-guide.md`
  through `_04_...`) — its `AREA_PREFIX_MAP` instead had stale entries `"06_config"`
  → `operations` and `"91_eventbus"` → `eventbus`, matching zero real files. This was
  fixed in a separate tooling-improvement task (not this Plan's own scope):
  `AREA_PREFIX_MAP` now maps `"06_eventbus"` → `"eventbus"` directly, and the dead
  `"06_config"`/`"91_eventbus"` entries were removed. Re-verified at this Plan's
  correction time: `extract_area_from_filename("06_eventbus_00_document-guide.md")`
  now returns `"eventbus"` correctly — `docs/06_eventbus_00_document-guide.md` no
  longer needs a manual override (see `REQ-004`, now a verification step rather than
  a workaround).

## Problem
56 files across the corpus do not carry a compliant front-matter block under
`docmeta01`'s finalized schema (2 needing a manual unterminated-fence repair plus
key rename, 43 entirely missing — 2 of which also carry a stray `category:` line
inside an unfenced block, 11 missing one field). The tool intended to automate part
of this migration previously had a confirmed area-inference gap for the
`06_eventbus` filename convention (now fixed — see Background) that would have
silently mis-tagged one of this Plan's own target files if trusted without review;
this Plan's mandatory manual-review requirement (`REQ-002`) would have caught it
regardless, but the underlying tool gap is now closed at the source.

## Reason for change
Once `docmeta01` establishes the canonical schema, the document corpus must actually
comply for that schema to have practical effect, rather than becoming aspirational
guidance like the "Recommended Additional Fields" section it replaces.

## Implementation intent
Prefer `tools/manage_frontmatter.py add-missing --fix` over a new ad hoc script for
the 43 missing-front-matter files, per `rules/ai-execution.md` Repository Tool
Usage — but manually review and correct every inferred `title`/`area`/`tags` value
against the document's actual content before accepting it (per the source Issue's
own AI Implementation Instruction). Verify (not override — the underlying inference
bug is fixed, see Background) that `docs/06_eventbus_00_document-guide.md`'s `area`
comes out as `eventbus`. Perform the 2 unterminated-front-matter repairs
(`category:`→`area:` rename combined with adding the missing closing `---`,
preserving existing content) and the 11 ADR `tags:` additions via manual `Edit`,
since no current tool can safely automate either case (see Background). Do not begin
any of this until `docmeta01`'s Plan (`plans/20260903-124425_plan.md`) has been
implemented — this Plan's `area` enum and required-field set are not authoritative
until that Plan's `docs/00_governance_02_documentation-metadata.md` rewrite lands
(see Implementation steps Phase 0).
