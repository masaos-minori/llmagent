# Plan: Record the accepted risk of session.sqlite having no incremental migration mechanism

## Goal

Add a discoverable, `session.sqlite`-specific comment/docstring note directly above
`_SESSION_SCHEMA_TEMPLATE` in `scripts/db/schema_sql.py` that documents the current
recreate-only mechanism, the non-reindexable nature of `session.sqlite`'s data
(conversation history, semantic/episodic memory), and the explicit deferral of the
migration-mechanism-vs-recreate decision to the next concrete `session.sqlite`
schema-change proposal — with no executable behavior change.

## Design

- Location: the note is inserted as a comment block immediately preceding the
  `_SESSION_SCHEMA_TEMPLATE: str = """` line (currently line 85 in
  `scripts/db/schema_sql.py`).
- Content (three points, per requirement Implementation instructions §2):
  1. `session.sqlite` currently uses recreate-only DDL (`CREATE TABLE IF NOT EXISTS`),
     with no incremental migration mechanism (unlike `workflow.sqlite`'s
     `_WORKFLOW_MIGRATIONS` / `apply_workflow_migrations`).
  2. Unlike `rag.sqlite`, `session.sqlite`'s data (conversation history,
     semantic/episodic memory) is not trivially re-derivable from an external source.
  3. This gap is a known, accepted risk (cross-reference
     `issues/done/20260819-183436_risks.md` and the source requirement) — the
     migration-mechanism-vs-recreate decision is deliberately deferred until a concrete
     `session.sqlite` schema change is proposed, at which point that proposal's
     requirement/plan must explicitly address how existing conversation and memory data
     is preserved (incremental migration mechanism, or an explicit export/reimport step)
     rather than silently defaulting to a lossy recreate.
- If `plans/20260819-183436_plan.md`'s general "Migration policy" docstring section
  (module-level, near the top of `scripts/db/schema_sql.py`) has already landed by
  implementation time, the new note references it by name (e.g. "see the module
  docstring's Migration policy section for the general per-database policy") instead of
  restating the general RAG/session/workflow/eventbus comparison table.
- No function signatures, DDL statements, or runtime logic are touched. This is a
  documentation-only change embedded in source code (per `rules/coding.md`'s
  "Documentation notes" classification, this qualifies as recording an already-decided,
  accepted risk — not a new "Implementation fix required" issue, since no code defect
  exists; it is a deliberate, tracked deferral).

  address it explicitly. This is a documentation-wording risk, not a code risk; no

  forward as residual risk for the next `session.sqlite` schema-change cycle to inherit.
  Likelihood: low — the note is explicit and requires no source-of-truth cross-reference
  the reader must chase further.
