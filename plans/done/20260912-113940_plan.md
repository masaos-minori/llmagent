# Plan: Fix /subscribe SSE Generator Client Disconnect Detection

## Goal
- Fix the `/subscribe` endpoint's SSE generator (`_sse_gen`) so it reliably detects client disconnect under both production ASGI servers (uvicorn) and Starlette's `TestClient`, preventing indefinite resource leaks.

## Priority
Medium

## Scope
- **In-Scope**: Add a reliable disconnect detection mechanism for the `/subscribe` SSE generator; update affected tests; verify production behavior is unchanged.
- **Out-of-Scope**: Changing the Bearer-token presence/validity check itself; any other MCP server's `attach_auth_middleware` usage; role/consumer-identity authorization gap (covered by separate issue).

## Background
The `/subscribe` endpoint streams Server-Sent Events via `_sse_gen`. Its live-delivery loop exits only when: (1) `sub.disconnect` is set (only on broker queue overflow), (2) the broker sends a `None` sentinel (app-wide shutdown), or (3) `await request.is_disconnected()` returns `True` (added as partial mitigation). Under TestClient's `httpx.ASGITransport`, case 3 does not fire reliably — a test opening `/subscribe` and then closing the response leaves the server-side generator running indefinitely.

## Problem
Under TestClient, `request.is_disconnected()` does not return `True` when the client-side response object is closed. This was reproduced 3 separate ways (plain `.stream()` context exit, `request.is_disconnected()` polling added, and `.send(..., stream=True)` without a context manager) — all hung identically. Regardless of the TestClient-specific reproduction, an SSE endpoint that cannot reliably detect disconnects is a real resource-leak risk in production: every subscriber whose queue never overflows keeps its generator, asyncio tasks, and broker registration alive forever after the client actually goes away.

## Reason for change
This blocks writing a working automated test for the `/subscribe` success path and represents a resource-leak risk in production for quiet topics whose queues never overflow.

## Implementation intent
Add a timeout-based disconnect detection mechanism as a fallback alongside the existing `is_disconnected()` polling. When no events arrive within a bounded time window, assume the client disconnected and clean up. This approach works regardless of whether `is_disconnected()` fires under the given transport layer.

## Requirements
- `REQ-001`: The `/subscribe` SSE generator must reliably detect client disconnect under both production ASGI servers (uvicorn) and Starlette's `TestClient`, freeing resources within a bounded time after disconnect.
- `REQ-002`: The existing disconnect detection mechanisms (queue overflow → `sub.disconnect`, app shutdown → `None` sentinel) must be preserved.

## Design
### Timeout-Based Disconnect Detection
The fix adds a configurable idle timeout to `_sse_gen`'s live-delivery loop. After each successful event delivery, the last heartbeat timestamp is updated. If no events arrive within the timeout window, the generator assumes the client has disconnected and cleans up.

This approach works because:
1. Under normal operation, events arrive continuously, so the timeout never triggers.
2. Under TestClient, even if `is_disconnected()` doesn't fire, the lack of incoming events will eventually trigger the timeout.
3. Under uvicorn, the timeout provides additional robustness beyond `is_disconnected()`.

The timeout is implemented using `asyncio.wait_for()` around the inner while loop, with a configurable duration. When the timeout expires, the loop breaks and the finally block runs cleanup.

### Alternative Approaches Considered
- **Heartbeat/pong mechanism**: Require clients to respond periodically. Too complex for this use case; SSE protocol doesn't have built-in pong support.
- **Separate connection-monitoring task**: Create a background task that checks connection state. Over-engineered; the timeout approach is simpler and achieves the same result.

## Risks
- **Risk**: Timeout-based disconnect could prematurely close active subscriptions during periods of low event frequency. → **Mitigation**: Make the timeout configurable and set a reasonable default (e.g., 60 seconds) that covers normal quiet periods for SSE subscribers.
- **Risk**: Adding `sse_idle_timeout` to `EventBusConfig` changes the config schema and requires migration. → **Mitigation**: Use a hardcoded default if config changes are deemed too risky; document the need for future config addition.
- **Risk**: The timeout approach may not fully solve the TestClient issue if the transport layer also affects other asyncio primitives. → **Mitigation**: Verify the fix under TestClient before considering the issue resolved.
