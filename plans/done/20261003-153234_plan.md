# Plan: Fix HttpTransport retry exhaustion losing original exception context

## Goal
Restore the original exception context when `HttpTransport.call()` exhausts all retries, so that debugging and incident investigation can identify the root cause of transport failures.

## Priority
High

## Scope
- **In-Scope**: Fixing the exception context loss in `HttpTransport.call()` when all retries are exhausted; updating related documentation if needed.
- **Out-of-Scope**: Changing the retry logic itself (number of retries, backoff strategy); adding new error types; modifying other transport layers.

## Background
`scripts/shared/http_transport.py` line 163-167:
```python
else:
    msg = self._build_exhaustion_message(name, last_retryable_status)
    logger.error(msg)
    raise TransportError(msg)
raise last_exc or TransportError(f"call failed: {name}")
```

When all retries fail, `_build_exhaustion_message` generates a new `TransportError` message and raises it. However, the final `raise last_exc or TransportError(...)` is never reached because the `for...else` block already raised an exception.

Currently, Python's exception chaining (`raise ... from ...`) preserves the original exception information, but wrapping it in a new exception loses this chain.

## Problem
When retries are exhausted, the original exception stack trace is lost. This makes debugging difficult and hinders incident investigation in production environments.

## Reason for change
The checker's exit status affects CI/CD pipelines and automated verification workflows. If warnings should block verification, the exit code must reflect that. If warnings are informational only, exit 0 is correct. A decision is needed to avoid ambiguity in downstream consumers.

## Implementation intent
Fix the exception context loss by either:
1. Removing the `raise TransportError(msg)` from the `for...else` block and always using `raise last_exc`
2. Using `raise TransportError(msg) from last_exc` to explicitly preserve the exception chain

## Requirements
- REQ-001: Original exception context is preserved when retries are exhausted
- REQ-002: Retry exhaustion messages still include diagnostic information (tool name, status code)
- REQ-003: Existing tests pass after the change

## Design
Path A classification applies: direct verification inspection only, no architecture/dependency/historical/operational analysis.

Two possible approaches:
1. **Remove the `for...else` raise**: Remove `raise TransportError(msg)` from the `for...else` block and always use `raise last_exc or TransportError(...)`. This restores the original exception chain but loses the diagnostic message from `_build_exhaustion_message()`.
2. **Use explicit exception chaining**: Replace `raise TransportError(msg)` with `raise TransportError(msg) from last_exc`. This preserves both the diagnostic message and the original exception chain.

Approach 2 is preferred as it preserves both pieces of information.
