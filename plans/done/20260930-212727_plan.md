## Background
`ADR-004-environment-failure-handling-policy.md` defines two cross-cutting invariants:
- INV-15: Fallbackは、他のAccepted ADRが明示的に定義する場合に限り許可される。
- INV-16: ADR-010は、承認済みRAG Fallbackの権威であり続ける。

Its Verification Matrix lists exactly one Integration-test row for both invariants ("ADR-010で定義される場面以外でFallbackが発生しないこと", `Blocking: Yes`), but the recorded Status is `Needs confirmation (not individually re-run in this task)`. Every other row in the same matrix cites a specific test file and class; this row cites none. No existing issue, plan, or implementation procedure in the repository targets INV-15 or INV-16 specifically (confirmed by repository-wide search).

This is the same class of gap as the (now-resolved) `CI-014` family: an ADR marks a Blocking invariant but the tracking document records the verification status as unconfirmed. Left as-is, a future change could introduce a fallback path outside ADR-010's defined scope without being caught by any test or documented review step.

## Design

**Task-size classification: Path A.** The change affects ≤ 3 files, introduces no public or
runtime-facing interface change, and touches no database schema. The breadth of the
repository-wide fallback search does not change this impact-based classification; it only
feeds REQ-001's enumeration. Path A skips architecture/dependency/historical/operational
analysis, so `Affected areas` marks Churn/Bus Factor/Blast Radius as `N/A`.

**Why a single automated test cannot fully cover INV-15/INV-16.** The invariant asserts
"no fallback anywhere outside ADR-010's scope." Enforcing this automatically requires
classifying every `fallback` occurrence in the codebase as either (a) an ADR-010-sanctioned
RAG fallback or (b) an ADR-004-scope fallback requiring an Accepted ADR. The word "fallback"
appears 221 times across `scripts/` (110 in `scripts/rag/` for ADR-010-sanctioned RAG fallback;
111 outside `scripts/rag/`). Of the 111 non-RAG occurrences, the overwhelming majority are
defensive patterns (bare-except fallthrough, default-value substitution, `_or_default`) that
are NOT ADR-004-scope fallbacks. Any pattern-based automated detector would produce
unmanageable false positives, so the whole-codebase assertion cannot be robustly asserted by
one test. This mirrors the `CI-014` family's original problem and its resolution lesson:
cross-area ADR-invariant verification ultimately needs an accountable owner plus documented
review, not just a test.

**The hybrid mechanism (recommended).** Split coverage along what is mechanically
verifiable versus what requires judgment:
- *Mechanically verifiable subset* — the existing tests (`test_401_no_fallback`,
  `test_403_no_fallback`, `test_json_parse_error_does_not_call_set_fallback_reason`) pin
  `call_rag_service()`'s contract only: 401/403 make one request, record an
  `http_auth_error:` reason and return `None`; a JSON parse error returns `""` with no
  reason. They do not assert that in-process RAG is skipped, and they do not touch
  `ResultSource.FALLBACK`. In fact `RagPipeline` runs in-process search whenever
  `run_http_augment()` returns `None`, including for 401/403 (`http_augment.py` only skips
  forwarding the stage-level fallback reason, and `augment.py` still sets
  `ResultSource.FALLBACK`). REQ-002 therefore cites them as a contract pin, not as proof of
  "no fallback", and grounds the citation with `check_adr_invariant_matrix.py`.
- *Whole-codebase assertion* — "no other ADR-004-scope fallback exists" requires enumerating
  and classifying every path, which is a review activity. REQ-003 documents a Manual Review
  checklist item with re-review cadence and an owner reference.
- *Regression guard (confirmed; resolves UNK-01)* — REQ-005 adds a narrow test locking the
  ADR-010 marker (`ResultSource.FALLBACK`) to the sanctioned RAG
  augment path, so the single allowed fallback cannot silently relocate. It guards against
  regressions in the one automatable spot; it does not claim to cover the full invariant.

**Matrix Status update.** The row's Status becomes a precise hybrid statement rather than a
single value: the covered subset (the `call_rag_service()` contract) is `Confirmed` by existing tests, and the cross-cutting
remainder is covered by a documented Manual Review with a cadence — satisfying the issue's
requirement that the marker no longer be a bare `Needs confirmation`.
