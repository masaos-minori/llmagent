## Goal
Give `rag-pipeline-mcp` `/health` a real reachability signal for `embed_url`: a configured-but-unreachable embedding service is reported as a distinct `"unreachable"` dependency state (HTTP 503, `ready: false`, `liveness: true`) instead of only reporting the key as absent, so an embedding outage is visible in the MCP health layer rather than invisible while the two embedding tools fail at call time.

Medium

## Background
- Found on 2026-10-19 while investigating why `deploy/setup_services.sh` aborts on an unreachable `embed-llm` (`http://192.168.11.238:8081`, `All connection attempts failed`) even though the rest of the stack is healthy. `192.168.11.238` is this host's own `enp3s0` address.
- `scripts/mcp_servers/rag_pipeline/rag_pipeline_server.py::_check_health_deps` (lines 208-220) loads `rag_pipeline_mcp_server.toml` and records `deps["embed_url"] = "not configured"` only when the value is falsy or not a `str`. It issues no request and never observes the service.
- `GET /health` (lines 223-231) passes those deps to `scripts/mcp_servers/health_response.py::make_health_response` (lines 26-57), where `ready = len(deps) == 0 and (security is None or security.validated)` (line 43); any non-empty `deps` yields HTTP 503 with `status: "degraded"`, `ready: false`, `operator_action_required: true`.
- `scripts/mcp_servers/rag_pipeline/rag_pipeline_security.py` is presence-only by design (docstring lines 36-38: "validation cannot issue an outbound request or touch a database"); check id `server.embed_url_configured` (line 46). `tests/mcp_servers/rag_pipeline/test_rag_pipeline_health_posture.py` includes it (`_RAG_CHECK_IDS`, lines 23-31).
- Tool availability uses the same presence-only signal: `rag_pipeline_server.py::_rag_pipeline_tool_availability` (lines 125-131) disables `rag_run_pipeline` and `rag_debug_pipeline` only when `cfg.embed_url` is empty (`"embed_url is not configured"`), so with the key configured the tools stay enabled and fail only inside `call_tool`.
- The documented contract matches the code, so this is a contract extension rather than a code-versus-doc defect: `docs/22_mcp/mcp_04_03_rag-pipeline-and-cicd.md:46`, `docs/22_mcp/mcp_02_02_startup-modes-and-health.md:112`, `docs/21_rag/rag_01_system_overview.md:141,145-146`, `docs/22_mcp/mcp_06_04_verification-methods.md:24` all define `dependencies.embed_url` as `"not configured"` / `"check failed"` only. (The issue cites line numbers 64/166/153-157/84 for these; the content claims are accurate but the current locations differ — see Adversarial verification.)
- Measured on 2026-10-19: `embed_url = "http://192.168.11.238:8081"` (set in `config/rag_pipeline_mcp_server.toml:10`) is configured and the service is unreachable, while `llm_url = "http://192.168.11.197:8080"` is healthy. With that configuration `rag-pipeline-mcp` `/health` returns `status: "ok"`, `ready: true`, `dependencies: {}`, HTTP 200.
- Sibling precedent shows the pattern is available: `mdq` records real observed state in its health input (`scripts/mcp_servers/mdq/health_check.py::_collect_dependencies` → db file presence, schema error, index stats, fed into `build_mdq_posture`); `file/common.py::_build_health_deps` (line 194) stats local allowed_dirs. No MCP server probes a remote URL in its health input today (a search for `_check_health_deps` / `health_deps` finds only `rag_pipeline_server.py` and `file/common.py:194`, and no `httpx` use in any `*security*.py` or `*health*.py` MCP module). This therefore introduces a new health-probe pattern and must be scoped deliberately.

## Problem
- The only embedding-dependent MCP server cannot distinguish "configured" from "working": with a configured-but-unreachable `embed_url` it answers `200 ok / ready: true` for the whole duration of an embedding outage while the two embedding tools fail at call time.
- Monitoring gap: an operator following `docs/22_mcp/mcp_06_04_verification-methods.md:24` (curl `/health`, read `dependencies.embed_url`) sees a healthy server during an embedding outage.
- Consistency: `mdq` reports observed dependency state while `rag_pipeline` reports configured-only state, even though embedding availability is the rag-pipeline server's single hard runtime dependency.
- Safety of the current signal: the outage is currently visible only as one non-fatal agent warning plus a hard abort in `setup_services.sh` (Issue `ebops002`). Once that gate is made non-fatal, nothing in the MCP health layer would report the outage at all — this issue supplies the replacement signal.

## Reason for Change
- Production reliability: the only embedding-dependent MCP server cannot distinguish "configured" from "working", which is exactly the state an operator needs during an outage.
- Public API behavior: `/health` is the documented readiness surface for MCP servers, and its `ready` claim is currently weaker than operators reasonably read it.
- Consistency: `mdq` reports observed dependency state while `rag_pipeline` reports configured-only state.
- The replacement-signal timing: `ebops002` removes the only current outage signal (the aborting gate); this issue supplies the durable replacement.

## Implementation Intent
- Keep the presence check (`"not configured"`) exactly as it is, and add a distinct second state for reachability, e.g. `deps["embed_url"] = "unreachable"`, so the two failure modes stay distinguishable in the response body and in tests.
- Keep the posture check presence-only. `rag_pipeline_security.py:36-38` is a deliberate design property (startup validation must not issue outbound requests); changing startup behavior is not part of this issue.
- Put the probe in the health path only, with a hard request timeout and a short-lived cache, so `/health` stays fast and does not multiply load on the embedding service. Derive the probe URL from the configured base (mirroring how the agent strips the path to `{scheme}://{netloc}/health` in `mcp_health.py:303-307`); reuse `build_embed_url` from `scripts/shared/llm_client.py` only if the chosen endpoint is the embeddings endpoint rather than `<base>/health`.
- Respect the import contract `mcp_servers must not import from agent` (`lint-imports`, 6 contracts, all KEPT): the probe helper lives in `scripts/mcp_servers/rag_pipeline/` and may import from `shared` (permitted), never from `agent`.
- Make the probe injectable (transport or callable parameter) so tests need no network, and keep the default path bounded by an explicit timeout constant.
- Preserve the agent's tolerance: `make_health_response` keeps `restart_recommended: false` and `liveness: true`, and the agent already treats a `503` with `liveness: true` as degraded-but-live (`scripts/agent/http_lifecycle_health_checker.py::is_degraded_but_live`, lines 79-96), so a remote outage degrades the server without causing a restart loop. Verify this against existing agent tests rather than assuming it.

## Design
Path B (>3 modification-target files; new module; public `/health` interface change). The design below is grounded in Step 3/Step 5 analysis.

**New dependency state (core).** `_check_health_deps` currently returns `{}` when `embed_url` is a non-empty string. Extend it to a three-state model:
- absent / non-string → `"not configured"` (unchanged),
- config load error → `"check failed"` (unchanged, returned early before any probe),
- configured but reachability probe fails → `"unreachable"` (new).

The probe runs only on the success path (config loaded and `embed_url` a non-empty string), so the config-failure branch (`deps["config"] = "check failed"`) is unaffected and its characterization test (`test_rag_pipeline_server_endpoints.py:162-176`) still expects exactly `{"config": "check failed"}` with no probe.

**Probe module (`rag_pipeline_health_probe.py`).** A new module inside the `rag_pipeline` package exposing a single entry point, e.g. `async def probe_embed_reachable(embed_url, *, caller=None, timeout=...) -> "reachable" | "unreachable"`. Design points:
- Injectability: accept an optional `caller` (an `httpx.AsyncClient`-like `.get` or a callable) so tests supply a stub; default to a real bounded `httpx.AsyncClient`.
- Bounded: explicit timeout constant (default 2.0 s, matching `mcp_health.py:307`); the request must not block longer than the timeout even on DNS stalls (`httpx.Timeout` covers connect/read).
- URL derivation: probe `<base>/health` via GET by default (mirrors the agent's own probe and needs no payload); reuse `build_embed_url` only if the embeddings endpoint is chosen (UNK-01).
- Import direction: import from `shared.llm_client` (permitted); never from `agent`. `lint-imports` gates this.

**Cache.** A short-TTL cache keyed by the embed base, storing `(state, monotonic_timestamp)`. On each probe call: if a fresh entry exists, return it without issuing a request; otherwise probe and store. Exposed for tests (reset + call counter). TTL default ~5-10 s (UNK-02).

**Wiring into `GET /health`.** `_check_health_deps` calls the probe lazily (local import, matching the existing lazy `ConfigLoader` import) after the presence check passes. The probe result becomes a `deps` entry; `make_health_response` is called unchanged, so the response shape (`liveness:true`, `restart_recommended:false`, 503, `ready:false`) is preserved (REQ-003).

**Test-suite impact (important).** The shipped `config/rag_pipeline_mcp_server.toml:10` sets `embed_url="http://192.168.11.238:8081"`, which the test isolation root copies in. An un-stubbed probe would therefore hit an unreachable IP during the existing `/health`-reading tests. Resolution: the probe is injectable; update `test_rag_pipeline_health_posture.py` and `test_rag_pipeline_server_endpoints.py` to stub it, keeping those tests network-free and deterministic. `test_health_returns_503_when_the_posture_is_not_validated` (which asserts `dependencies == {}`) stubs the probe so its posture-driven 503 is unaffected.

**Cross-dependency (Issue `ebops002`).** `ebops002` removes the only current outage signal (the aborting LLM gate); this issue supplies the durable replacement signal in the MCP health layer. Each is independently implementable and reviewable; the deployment story is complete only with both.

## Risks
- **Risk**: `/health` now issues an outbound HTTP request, adding latency and a hard dependency on the embedding service's availability to the health surface. → **Mitigation**: explicit short timeout (default 2.0 s, bounded even on DNS stalls via `httpx.Timeout`), short-TTL cache so repeated polls issue at most one probe, injectable transport for tests; worst-case latency asserted in a test with a hanging transport (AC-004, AC-005).
- **Risk**: The shipped `config/rag_pipeline_mcp_server.toml` sets an unreachable `embed_url`, so an un-stubbed probe would hit a real network during existing `/health` tests, making them slow/nondeterministic or changing `dependencies`. → **Mitigation**: probe is injectable; update the existing `/health`-reading tests in `test_rag_pipeline_health_posture.py` and `test_rag_pipeline_server_endpoints.py` to stub it, keeping them network-free and deterministic (AC-003, AC-006).
- **Risk**: Making `/health` report `degraded` could change how the agent's startup poll treats the server (restart loop or fatal). → **Mitigation**: keep `liveness: true` and `restart_recommended: false` (unchanged `make_health_response` shape); the agent's `is_degraded_but_live` treats such a `503` as ready; verify `tests/agent/test_http_lifecycle_health_check.py` stays green (REQ-003).
- **Risk**: The probe helper imports across a package boundary and violates `mcp_servers must not import from agent`. → **Mitigation**: place the module inside `scripts/mcp_servers/rag_pipeline/` (or `shared`), import from `shared` only, and gate with `lint-imports` (6 contracts, currently all KEPT).
- **Risk**: Doc/code drift breaks `check_docs_consistency.py` if the four documents are not updated together with the code. → **Mitigation**: update all four documents in the same commit as the code (REQ-005); the checker is part of the validation plan (AC-007).
