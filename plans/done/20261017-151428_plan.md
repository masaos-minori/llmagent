# Plan — Surface startup rollback failures beyond a log line

## Goal
Make a failure of `lifecycle.shutdown_all()` during startup rollback observable at a
level that reliably reaches the operator: when rollback fails, emit an operator-visible
message via the existing CLI view output channel in addition to the existing
`logger.error(...)`, while preserving the re-raise of the original startup exception.

## Priority
Medium

## Scope
- **In-Scope**: Adding an operator-visible emit to the rollback-failure branch of
  `StartupOrchestrator.run()` (`scripts/agent/startup.py`) that reuses the existing view
  output channel (bypassing the logger), without altering the `raise setup_err`. Adding
  a regression test asserting the operator-visible signal plus preserved re-raise.
  Updating the Known Limitations bullet in
  `docs/23_agent/agent_10_01_...startup-and-health.md`.
- **Out-of-Scope**: Changing what `shutdown_all()` does or which resources it shuts down;
  other shutdown paths (`ResourceShutdownCoordinator.close_resources`); normal
  (non-failure) startup logging; the success path; the original `setup_err` handling.

## Background
`scripts/agent/startup.py` `StartupOrchestrator.run()` wraps the startup sequence in a
try/except:

```python
except Exception as setup_err:
    try:
        await self._ctx.services_required.lifecycle.shutdown_all()
    except Exception as shutdown_err:
        logger.error(
            "CRITICAL: Startup rollback FAILED — subprocesses may be orphaned: %s",
            shutdown_err,
        )
    raise setup_err
```

`docs/23_agent/agent_10_01_...startup-and-health.md` Known Limitations states: "A
failure of the rollback `shutdown_all()` during startup failure is only logged; the
original startup exception is re-raised and nothing is shown on the console for the
rollback failure."

## Problem
When rollback fails, the only signal is a `logger.error` line. Depending on the logging
configuration that line may not reach the operator's console/stderr, and it is
immediately followed by the re-raised `setup_err`, which can obscure the rollback
failure. Orphaned subprocesses are a real operational hazard (leaked children, open
ports, dangling handles), and the operator has no guaranteed console-visible indication
that rollback failed.

## Reason for change
Rollback failure during startup is a critical operational condition (possible orphaned
subprocesses). Relying solely on a logger line that may not reach the console risks
silently leaving orphaned processes. The failure should be surfaced in a way that
reliably reaches the operator.

## Implementation intent
When the rollback fails, emit an operator-visible message in addition to (not instead
of) the existing `logger.error`. Reuse the process-level CLI view output channel that
the REPL already uses for critical startup messages, so it reaches the console
regardless of logger level config. Preserve the re-raise of `setup_err` so the original
failure is not masked. Name the boundary: only the rollback-failure branch changes;
normal startup success and normal error paths are untouched.

Two equivalent channels satisfy this; implement one:
- **(a) `self._view.write_fatal(msg)` (recommended):** The established channel for
  critical startup messages — `startup_reporter.py` uses it for FATAL pipeline outcomes
  and `repl.py` uses it for `"Startup failed: ..."`. Semantically matches a CRITICAL
  rollback failure and reaches the console.
- **(b) `self._view.write_stderr(text)`:** Writes directly to process stderr via the
  output port. Guaranteed process-level stderr.

Construct the message to reference the rollback failure and (optionally) the shutdown
error, without duplicating the `logger.error` wording in a way that confuses log
aggregation.

## Requirements
- `REQ-001`: On `shutdown_all()` failure, an operator-visible message is emitted via the

- `REQ-002`: The final `raise setup_err` is unchanged; the original startup error is

## Design
Path A (affects ≤ 3 files; no public/runtime interface change; no DB schema change).
Adversarial verification (Step 2) confirmed the issue's claims against current source:
the rollback-failure branch (`startup.py` lines 76-85) records the failure only via
`logger.error` and then re-raises `setup_err`; the Known Limitations bullet (doc line
144) states exactly this. `StartupOrchestrator` holds `self._view` (a `CLIView`,
constructor lines 51-56), which exposes operator-output channels `write_fatal`
(cli_view.py 209-213) and `write_stderr` (cli_view.py 263-265); both are used for
critical startup messages elsewhere (`startup_reporter.py:65`, `repl.py:141`). The
existing test `test_startup_rollback.py::test_rollback_shutdown_failure_preserves_original_error`
already drives the rollback-failure path with a `MagicMock` view, so the fix is directly
assertable via `view.write_fatal`/`write_stderr`. The named boundary: only the
rollback-failure branch changes; `raise setup_err` and the success path are untouched.
The one genuine open question (UNK-01) is which channel most reliably reaches the
console across deployment modes; `write_fatal` is recommended as primary.

## Risks
- **Risk**: The chosen channel does not reach the console in some deployment mode
  (UNK-01). → **Mitigation**: Confirm both `write_fatal` and `write_stderr` routing per
  mode before coding; prefer the one verified to reach the operator.

  asserts exact call counts on the view). → **Mitigation**: Only `test_rollback_*`
  exercises this branch with a MagicMock view; verify the full rollback suite passes.
- **Risk**: Duplicate/confusing output in log aggregation. → **Mitigation**: Keep the
  console message concise and distinct from the logger line's structured detail.
