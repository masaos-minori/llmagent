# Work Plan: Enhance Observability of Memory Initialization Failures

## Status: REVISED

This plan has been revised following a code review to avoid breaking changes. The previous approach of failing startup on FATAL errors was rejected to preserve the agent's ability to operate without memory (graceful degradation).

## Goal

Improve observability of memory initialization failures by classifying exceptions and using appropriate log levels, while maintaining existing graceful degradation behavior.

## Scope

- Modify `scripts/agent/startup.py` to classify exceptions during memory initialization.
- Implement differentiated logging based on the exception type.
- Ensure no new state variables (e.g., `memory_retry_pending`) are introduced unless a clear retry mechanism is defined.

## Assumptions

1. Graceful degradation is mandatory: The agent must always start even if memory services fail.
2. Logging is the primary tool for improving observability in this phase.
3. `ctx.conv.memory_disabled` remains the standard way to signal memory unavailability.

## Affected Areas

- `scripts/agent/startup.py` — Core logic change for exception handling and logging.
- `tests/test_startup.py` — New test coverage for classification and logging.

## Design

### Approach: Classify exceptions for enhanced logging

Instead of changing the control flow (which would break the agent), we will categorize the error to provide better diagnostic information in the logs.

```python
import sqlite3
import logging

logger = logging.getLogger(__name__)

def _classify_memory_failure(exc: Exception) -> str:
    """Classify memory initialization failure for logging purposes."""
    if isinstance(exc, (sqlite3.Error, OSError)):
        return "DATABASE_OR_IO"
    elif isinstance(exc, (TimeoutError, ConnectionError)): # Add relevant network errors
        return "NETWORK_TRANSIENT"
    else:
        return "UNKNOWN"

# In startup.py (_setup_prompt):
try:
    memory_snippets = ctx.services_required.memory.on_session_start(
        ctx.session.session_id,
    )
    # ... (existing snippet processing) ...
except Exception as exc:
    ctx.conv.memory_disabled = True
    category = _classify_memory_failure(exc)
    
    if category == "DATABASE_OR_IO":
        logger.error(
            "Memory injection failed (CRITICAL): %s; continuing without memory",
            exc,
        )
    elif category == "NETWORK_TRANSIENT":
        logger.warning(
            "Memory injection failed (TRANSIENT): %s; continuing without memory",
            exc,
        )
    else:
        logger.info(
            "Memory injection failed (UNKNOWN): %s; continuing without memory",
            exc,
        )
    
    self._view.write_warning(
        f"{OutputTag.NON_FATAL} Memory injection failed ({category}): {exc}"
    )
```

### Implementation Steps

#### Step 1: Add `_classify_memory_failure()` function

Add the helper function to `startup.py`.

#### Step 2: Update `_setup_prompt` error handling

Replace the current generic `except Exception` block with the categorized logging logic.

#### Step 3: Add tests

- Test `DATABASE_OR_IO` triggers `logger.error`.
- Test `NETWORK_TRANSIENT` triggers `logger.warning`.
- Test other exceptions trigger `logger.info`.
- Verify `ctx.conv.memory_disabled` is always set to `True`.
- Verify that no exception is raised to the caller (ensuring startup continues).

## Validation Plan

1. Unit tests: Verify each exception type triggers the correct log level and category.
2. Integration tests: Simulate DB and Network failures to ensure the agent still starts successfully.
3. Manual testing: Verify the warning message shown to the user includes the error category.

## Risks

| Risk | Mitigation |
|------|------------|
| Over-classification of errors | Keep the classification simple and conservative. |
| Log spamming | Use appropriate log levels (INFO vs ERROR) to prevent noise. |
