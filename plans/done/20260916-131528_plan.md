## Background
Filed as the last issue in the `mcpagent01`–`mcpagent09` batch, intended to run after the batch's functional issues stabilize behavior, since several of its originally proposed corrections describe a target state (e.g. "duplicates are always fatal", "tests assert `TransportError`") that depends on other issues' code changes actually landing.

## Problem
Adversarial verification (Step 2) against current source found:
- Two of the Issue's six wording claims were **already true** in current source, not defects: `scripts/shared/route_resolver.py`'s module docstring already states `RuntimeToolRegistry`/live discovery is "the sole routing authority" and that config `tool_names` is "NOT a routing input; it is drift validation metadata only" (near-identical wording exists in `scripts/shared/tool_registry.py`'s module docstring). No correction needed for these two.
- Two of the Issue's claims are **confirmed defects owned by other Plans**, not by this one: `tests/shared/test_tool_executor.py::test_retries_exhausted_returns_error` (line 56) does assert generic `pytest.raises(Exception)` with no `TransportError`-specific name — but `plans/20260916-124248_plan.md` (mcpagent06) REQ-009 already targets this exact fix. `scripts/shared/route_resolver.py::build_discovery_map()` (lines 33-62) does implement first-wins-with-a-warning for duplicate tool names, contradicting `scripts/agent/services/mcp_tool_discovery.py`'s already-correct exclude-and-always-FATAL policy (module docstring, lines 27-38) — but `plans/20260916-130526_plan.md` (mcpagent08) REQ-001 already removes `build_discovery_map()` entirely, not just its wording.
- One claim's underlying premise is **false, refining the required action**: `ToolRouteResolver.__init__`'s `strict_mode` parameter does not change "only error wording" (the Issue's own stated condition for renaming/removing it) — when `strict_mode=True`, `resolve()` calls `_raise_strict_error()` (a `NoReturn` path) before ever reaching the `warn_on_missing` check, so `strict_mode=True` also suppresses the warning log that `warn_on_missing=True` would otherwise emit. Both configurations always raise `ValueError` on an unresolved tool (confirmed: the only production construction site, `scripts/shared/tool_executor.py:54`, uses no `strict_mode` argument; the sole `strict_mode=True` call site is `tests/agent/services/test_runtime_tool_routing_integration.py::test_strict_mode_error_message_mentions_runtime_registry`, whose own docstring already frames the difference as message-only). Because the Issue's stated condition for renaming/removing the parameter does not hold, and because a full rename/removal is itself an interface change beyond this Issue's declared "documentation/wording correction, not a behavior change" scope, this Plan instead documents both effects precisely.
- One claim is **confirmed and requires no refinement**: `scripts/agent/config_dataclasses.py`'s `AgentConfig` class docstring (line 433) states "Composes 8 domain-specific sub-configs", while the same file's module docstring (line 16) states 9, and the class itself declares exactly 9 sub-config fields (`llm`, `rag`, `tool`, `memory`, `mcp`, `approval`, `obs`, `diagnostics`, `messages`). This resolves the Issue's own Unresolved Question: the correct current count is 9, confirmed directly against the dataclass fields, not assumed.
- One claim is **confirmed and scope-expanded by new evidence**: searching `docs/*.md` for the same count (not in the Issue's original Target Files list) found three additional, independent, and even-more-stale occurrences of "7 sub-configs"/"7 sub-configurations": `docs/agent_13_reference-api.md:229`, `docs/agent_01_system-overview.md:52`, `docs/agent_02_runtime-architecture.md:110`. A fourth doc, `docs/adr/ADR-002-config-isolation.md:82`, already correctly states 9 and names all nine sub-configs — confirming 9 is the correct, stable count independently of `config_dataclasses.py`.
- One claim is **confirmed as stated**: `scripts/shared/config_validator.py::RagConfigValidator._check_removed_semantic_cache_keys()`'s validation message reads "...see issues/done/20260902-150339_semcacherm_... and issues/20260902-150341_semcachedocs_...)" — both references are truncated with a literal `...` instead of the full slug, and the second additionally omits the `done/` path segment (the actual file is `issues/done/20260902-150341_semcachedocs_replace_semanticcache_tests_and_docs_with_no_cache_design.md`, confirmed to exist at that path via `ls`).
