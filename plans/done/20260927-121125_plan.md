## Goal
Add a dynamic, admin-authenticated Event Bus API for updating `consumer_authorization`/`topic_authorization` at runtime, plus an Agent-side client for it, closing Known Issue EVENTBUS-007.

## Priority
Low

## Scope
- **In-Scope**: A new Event Bus `/admin/topics/authorization` endpoint (ADMIN-role-gated) that updates the in-memory `consumer_authorization`/`topic_authorization` maps derived from `EventBusConfig`; an Agent-side client for it; removal of EVENTBUS-007 from the Known Issues inventory once verified.
- **Out-of-Scope**: Publish (EVENTBUS-005) and SSE subscribe (EVENTBUS-006), tracked as separate Plans; changing the existing static config-file-based authorization model (it remains valid as the startup-time source; this Plan adds a runtime override on top of it, per the owner's decision below); any topic-as-first-class-entity model (create/list/rename topics) — the owner's decision (see Background) scoped this Plan to dynamic authorization updates only, not a broader topic-entity system.

## Background
`docs/00_governance/governance_03_issue-and-uncertainty-management.md`'s EVENTBUS-007 records that Agent→EventBus topic management integration is intentionally unimplemented. Issue `issues/20260927-115652_eventbus007_implement-agent-eventbus-topic-management-integration.md` found that Event Bus has no server-side concept of a manageable "topic" entity — `topic` is a free-form string field on events, used only for subscription filtering (`scripts/eventbus/broker.py::_Subscriber.topics`) and static per-consumer authorization (`consumer_authorization`/`topic_authorization` in `scripts/eventbus/config.py`, loaded once at startup). The issue's Unresolved Question (what "topic management" concretely means) was escalated to the user, who ruled: implement a dynamic authorization-config update API, with a matching Agent-side client.

## Problem
**Correction (found during `plan-to-implementation-procedure` Step 3a adversarial verification, not caught at Plan-writing time)**: `consumer_authorization`/`topic_authorization` are not merely "static until restart" as originally framed — they currently have **no runtime effect at all**. `scripts/eventbus/auth.py::_populate_token_maps()` (line 92) never reads `config.consumer_authorization`/`config.topic_authorization`; it only sets every token's `Principal.allowed_consumer_ids`/`allowed_topics` to `None` (unrestricted), for the shared `auth_token`, every per-role token, and `admin_token` alike. `_CONSUMER_ID_ALLOWLIST` (`auth.py` line 60) is declared but has zero writes anywhere in the codebase. The enforcement code that would consult these restrictions (`require_consumer_identity()`, `auth.py` lines 238-293) is real and functional, but is never triggered because no `Principal` is ever constructed with non-`None` restrictions. In short: `consumer_authorization`/`topic_authorization` are validated at config-load time (`EventBusConfig.__post_init__()`) but never wired to the Principal/enforcement layer — this is missing foundational wiring, not an existing runtime mechanism that merely needs a dynamic-update API layered on top. `scripts/agent/` has zero references to `eventbus`/`EventBus` (confirmed via `rg`), so no Agent-side client exists either.

## Reason for change
Per the owner's ruling: administrative workflows should be able to update consumer/topic authorization without a full Event Bus restart, and the Agent should be able to drive this automatically rather than requiring a manual config edit.

## Implementation intent
Add a new `POST /admin/topics/authorization` endpoint to Event Bus, gated by the already-declared (but currently unused) `Role.ADMIN` route prefix `/admin/*` in `scripts/eventbus/auth.py`'s `_ROUTE_ROLE_MAP`. The endpoint updates `app.state.config.consumer_authorization`/`topic_authorization` in memory and re-runs `scripts/eventbus/auth.py::_populate_token_maps()` (or an equivalent targeted update) so the change takes effect immediately, without requiring the static config file or a restart. Add a thin Agent-side client for this endpoint, following the same conventions as the EVENTBUS-005/006 clients.

## Design
The existing `_ROUTE_ROLE_MAP`'s `/admin/*` → `Role.ADMIN` entry (confirmed at `scripts/eventbus/auth.py` line 55) is a forward-declared, currently-unconsumed prefix — no `/admin/` route exists in `app.py` yet (confirmed via `grep`). This Plan's endpoint is the first consumer of that prefix, so it should not need a new authorization mechanism, only a new route registered under it.

`app.state.config` (confirmed at `app.py` line 67) already holds the live, mutable `EventBusConfig` instance for the running process — the new endpoint mutates this object's `consumer_authorization`/`topic_authorization` fields directly, then re-invokes an extended `_populate_token_maps()` that additionally sets each per-role token's `Principal.allowed_consumer_ids`/`allowed_topics` from those fields (the wiring that does not currently exist — confirmed via full Read, see corrected Problem section). `_CONSUMER_ID_ALLOWLIST` (`auth.py` line 60) is a separate, currently-dead declared variable with zero writes anywhere — this Plan does not populate it, since the actual enforcement path reads `Principal.allowed_consumer_ids`/`allowed_topics` (lines 238-293), not `_CONSUMER_ID_ALLOWLIST`.

Request validation (REQ-003) reuses `EventBusConfig.__post_init__()`'s existing type checks for these two fields (confirmed via Read) rather than duplicating a second, independently-worded validation — either by constructing a scratch `EventBusConfig`-like check, or by extracting the existing per-field validation into a reusable function during implementation (an implementation-time decision, not this Plan's concern).

Path A/B classification: **Path B** (creates a new module, and changes a runtime-facing interface — a new HTTP endpoint) — full architecture/dependency/historical/operational analysis performed:
- Architecture: read `scripts/eventbus/auth.py`'s `_ROUTE_ROLE_MAP` and `Role` enum; confirmed the `/admin/*` prefix's existing declaration; `.importlinter` re-checked (no relevant contract change).
- Dependency graphing: identified `app.py` as the single route-registration point; identified `_populate_token_maps()` as the config→runtime-state derivation function this endpoint must invoke.
- Historical analysis: `scripts/eventbus/` under active development (same finding as the EVENTBUS-005/006 Plans).
- Operational dependency inspection: this endpoint mutates in-process state only (no new port, no new external process, no DB schema change) — `lsof`-based process/port inspection is not applicable; confirmed no DB migration is implied (`consumer_authorization`/`topic_authorization` are config-object fields, not persisted DB columns, confirmed via `scripts/eventbus/schema.sql` containing no matching column names).

## Risks
- **Risk**: Extending `_populate_token_maps()` to consult `consumer_authorization`/`topic_authorization` inadvertently narrows an existing token's access (e.g. the shared `auth_token` or `admin_token`, which must remain unrestricted) → **Mitigation**: the integration test (Validation plan) specifically checks that `auth_token`/`admin_token`-holding callers remain unrestricted after the extension, not only that per-role tokens gain the intended restriction.
- **Risk**: The new admin endpoint becomes a privilege-escalation surface if `Role.ADMIN` gating is misapplied → **Mitigation**: AC-2 explicitly tests rejection of non-ADMIN-token requests before this Plan is considered complete; `bandit` static security scan is part of the validation plan.
- **Risk**: An invalid authorization update request corrupts in-memory config state before validation catches it → **Mitigation**: REQ-003 requires validating and constructing the new authorization maps in a local variable first, only assigning to `app.state.config` after validation passes (an implementation-time detail to enforce during `code-implementation`).
