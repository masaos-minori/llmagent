# Note that RAG constraint values' rationale is unrecorded and recommend empirical verification for tuning

## Goal
Add a note after `docs/03_rag_01_system_overview.md`'s Constraints table stating
that no rationale (empirical basis, trade-off analysis) for these specific values
is recorded in code, config, or ADRs, and that tuning any of them should be
verified empirically (search quality/performance testing) rather than assumed —
without inventing a rationale or quality-impact analysis that does not exist.

  (2) tuning guidance requires empirical verification, which this documentation

- **Out-of-Scope**: Fabricating a rationale, quality-impact analysis, or tuning

  inventing content to fill it); running actual experiments/benchmarks to

  documentation-only fix); writing new ADRs to retroactively justify these values

## Background
The Issue's cited claim
(`docs/03_rag_01_system_overview.md`, Constraints table entries like "Language
Detection: CJK ratio ≥ 0.10 → `ja`; otherwise `en`; fallback to hint if < 100
chars") is confirmed accurate — these values are listed with only a source file
citation, no rationale or impact explanation.

**Re-verified 2026-09-13** (this cycle): searched for any recorded rationale for
each of the 6 constraint values and found none:
- No ADR references any of the specific values or their surrounding concepts
  (confirmed via `grep -rl` across `docs/adr/` for "CJK ratio", "chunk_overlap",
  "min_chunk", "max_chunk", "max_depth", "max_pages" — no match)
- The originating code itself carries no rationale comment: the CJK ratio
  threshold (`scripts/rag/ingestion/crawler_utils.py:26`,
  `_CJK_RATIO_THRESHOLD: float = 0.1`) has only a one-line description comment
  ("CJK character ratio threshold above which text is classified as Japanese"),
  not a justification for why `0.1` specifically; `config/chunk_splitter.toml`'s
  `min_chunk`/`max_chunk`/`chunk_overlap` values carry no comments at all beyond
  the file-level header

The Issue's Recommended Action requests documenting "why each constraint value was
chosen (empirical basis, trade-offs)" and "how changing each value affects search
quality/performance" — neither can be answered from available evidence. These
questions require actual empirical work (running the pipeline with varied values
and measuring retrieval quality) that this documentation-fix cycle cannot perform;
answering them with plausible-sounding but unverified claims would misrepresent
speculation as established fact.

## Problem
An operator consulting the Constraints table for tuning guidance has no way to
know whether the absence of rationale/impact information is a documentation gap
(fixable by writing it down) or a genuine absence of recorded knowledge (requiring
new empirical work before it can be documented) — the current table is silent on
this distinction.

## Reason for change
State plainly that no rationale for these specific values is recorded anywhere,
and that tuning should be verified empirically rather than assumed to have a
documented basis — so an operator does not spend time searching for
non-existent design documentation, and knows any tuning decision needs its own
verification.

verify the change against actual retrieval quality/performance for the intended
use case rather than assuming a known-good adjustment — this documentation set
does not currently provide quality-impact guidance for any of them.
