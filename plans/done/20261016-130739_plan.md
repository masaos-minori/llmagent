## Goal
- Make the Deployment chapter's database inventory include `mdq.sqlite`, stating only what the DB documents, ADR-008, and the code already establish, so Deployment, DB, and ADR documents describe the same persistent databases.

## Priority
Medium

## Scope
- **In-Scope**:
  - Add `mdq.sqlite` to the Deployment DB inventory (owner, config source, derived-store classification) in `docs/90_deployment/deployment_01_deployment.md` section 3.0.
  - State in the Deployment chapter how `mdq.sqlite` is initialized (not by `init_db.sh`; created when the MDQ service starts), its recovery stance as ADR-008 defines it, and the health-check behavior that reports it.
  - Add a hand-written note immediately after the generated DB Path Reference block that names the `mdq.sqlite` path source (`db_path` in `config/mdq_mcp_server.toml`); the generator and the generated block stay unchanged.

  - Any change to `tools/generate_reference_table.py`, `mdq.sqlite` behavior, `recover_corruption()`, `rotate_all_dbs()`, or `deploy/*.sh`.

  - The `/memory` contract (mem001), ADR-004 verification (issue adr004), and high-risk MCP protection layers.

## Background
Source: finding V24-03, with the residual of V24-04, in `memo1.md` (design document review of 2026-10-16). Verified on 2026-10-16: `docs/41_db/db_08_active_databases.md` already lists `mdq.sqlite` (owner, config source, schema authority, busy timeout, lifecycle); `docs/10_adr/adr_02_008_sqlite-4db-separation.md` already states under "Derived Stores Outside the Four Domains" (line 131) that it is a derived store owned by `mdq-mcp`, rebuilt by `index_paths` and `refresh_index`, and not backed up or restored by `recover_corruption()` or `rotate_all_dbs()`; `docs/41_db/db_03_architecture_and_schema-migration-and-scaling.md` section 8d records the legacy-schema detection run at every MDQ service start.

## Problem
- `docs/90_deployment/deployment_01_deployment.md` section 3.0 (lines 253-266) lists only `rag.sqlite`, `session.sqlite`, `workflow.sqlite`, and `eventbus.sqlite`; the auto-generated DB Path Reference (lines 321-332) lists the same four, because `tools/generate_reference_table.py` reads only `scripts/db/config.py` and `config/agent.toml`.
- `mdq.sqlite` is not mentioned anywhere in the Deployment chapter. Its path is `db_path = "/opt/llm/db/mdq.sqlite"` in `config/mdq_mcp_server.toml`, which `deploy/deploy.sh` copies (line 140) while it also runs `mkdir -p /opt/llm/db` (line 55); `deploy/init_db.sh` does not create `mdq.sqlite`.
- `create_production_tables()` (`scripts/mcp_servers/mdq/db_schema.py`) creates the parent directory and the tables when the MDQ service starts, and unconditionally drops and recreates `chunks` when it detects a legacy schema (data loss, db_03 section 8d); `scripts/mcp_servers/mdq/health_check.py` reports a missing DB file (`db_file`) and schema problems as degraded.
- Operators reading only the Deployment chapter get none of this, and ADR-008 does not point to db_03 section 8d for the migration responsibility.

## Reason for change
A persistent database absent from the Deployment inventory can be left out of provisioning, recovery planning, and post-deploy checks. The facts already exist in the DB and ADR documents; the Deployment chapter should state its part and agree with them.
