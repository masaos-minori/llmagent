## Goal
Fix 3 tests in `tests/eventbus/test_eventbus_ack_nack.py` that compare `nack_event()`'s `NackResult` return value against a bare tuple (`== (1, 1)`, `== (2, 2)`, `== (-1, -1)`), which fails because `NackResult` is a `@dataclass(frozen=True)` (not a `NamedTuple`), so its default `__eq__` does not compare equal to a plain tuple.

- **Out-of-Scope**: `scripts/eventbus/delivery_repo.py`'s `NackResult` definition itself — already a well-documented, intentional `frozen` dataclass with a clear docstring explaining its two fields' sentinel values; no evidence it should instead be a `NamedTuple`. `eb001`'s status-code failures in the same file — distinct root cause, tracked separately.

## Background
`NackResult` (`scripts/eventbus/delivery_repo.py:24`) is defined as `@dataclass(frozen=True)` with two fields, `delivery_failure_count: int | Literal[-1]` and `cycle_failure_count: int | Literal[-2]`. A dataclass's generated `__eq__` compares only against instances of the exact same class (or subclass) by default — comparing it to a bare `tuple` returns `NotImplemented`, and since `tuple.__eq__` likewise cannot compare against a non-tuple `NackResult`, Python falls back to `False`. `tests/eventbus/test_eventbus_ack_nack.py::TestNackEvent`'s 3 affected tests predate this (or were never updated to this) type and still compare the return value to a bare 2-tuple.

## Problem
- `test_nack_event_increments_failure_count` (line 364): `assert result == (1, 1)`.
- `test_nack_event_increments_again` (lines 390, 393): `assert result1 == (1, 1)` / `assert result2 == (2, 2)`.
- `test_nack_event_not_found` (line 406): `assert result == (-1, -1)`.

All 4 fail with `assert NackResult(delivery_failure_count=N, cycle_failure_count=M) == (N, M)` → `False`.

## Reason for change
These 3 tests currently provide no effective verification of `nack_event()`'s return value (they fail before their assertion can pass in any circumstance) — restoring correct, type-matched comparisons restores real coverage of the nack-count-increment and not-found-sentinel behavior these tests are meant to verify.

## Implementation intent
Replace each bare-tuple comparison with either an equivalent `NackResult(...)` instance comparison (preserves the single-assertion style) or two separate field assertions (`result.delivery_failure_count == N` / `result.cycle_failure_count == M`) — either is acceptable since `test_nack_event_increments_failure_count`/`test_nack_event_increments_again` already separately assert the underlying DB row's `delivery_failure_count`/`cycle_failure_count` columns immediately after, so the `NackResult`-level assertion mainly re-confirms the function's direct return value.
