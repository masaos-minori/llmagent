## Goal
- Add an explicit maximum correction-and-recheck cycle count to
  `skills/issue-to-plan/workflow.md`, so the workflow stops and reports `Blocked` with a
  summary of remaining unresolved issues instead of patching a Plan indefinitely across
  repeated Step 2 adversarial-verification / Step 8 completeness-check cycles.

## Background
`skills/issue-to-plan/workflow.md` Step 2 (lines 142-146) instructs that an adversarial-
verification finding must be written into the Plan as a correction, and Step 8 (lines
355-357) instructs that `Pass`/`Completed` must not be reported while any requirement
information is unmapped, untraceable, or `Implementation Target Files` is not `Frozen` —
implying a correction is needed and the relevant check is presumably re-run. Directly
re-reading both sections confirms the source issue's claim: neither states, nor does any
other part of `workflow.md`, how many correction-and-recheck cycles are tolerated for a
single Issue before the workflow must stop and escalate instead of continuing to patch.
`grep -n "correction cycle\|correction-and-recheck\|N consecutive" workflow.md` returns no
matches, confirming this gap still exists as of this Plan's generation.

Three related but distinct workflow-gap issues from the same review batch (`itp003`,
`itp004`, `itp005`) already have their own Plans (`plans/20260901-214951_plan.md`,
`plans/20260901-215116_plan.md`, `plans/20260901-215253_plan.md`), none yet executed
(`## Execution Status` shows `Pending` in each). `itp003`'s Plan itself leaves the exact
numeric retry bound as an open Unknown (`UNK-01`: "Whether 3 (matching `AGENTS.md`'s
general Attempt Limit) or a different number is the right bound... left to implementation
planning, but the chosen number must be stated explicitly either way") — this Plan follows
the same convention for its own bound, rather than inventing a number `itp003`'s own Plan
declined to commit to.

## Problem
A Plan correction made to satisfy one check (e.g. Step 8 completeness) can introduce or
reveal an inconsistency elsewhere in the same document (e.g. correcting a Requirement's
scope may invalidate an Acceptance criterion that referenced the old scope, which the next
completeness check would then flag). Nothing in `workflow.md` currently bounds how many
times this correct-then-recheck cycle may repeat for a single Issue.

## Reason for change
Without a stated bound, a Plan could accumulate an unbounded sequence of patch-on-patch
corrections in a single cycle with no signal that the Issue or Plan structure itself — not
any individual field's content — may be the actual problem.

## Implementation intent
Add a short, explicit correction-cycle bound near Step 2 and Step 8 (the two points where a
correction can be triggered), stating: the maximum number of consecutive correction-and-
recheck cycles tolerated for the same Plan; that once exceeded without reaching a clean
`Pass`, the workflow must stop and report `Blocked: Plan requires more than N correction
cycles — {summary of remaining issues}` rather than continuing to patch; and that this
report must summarize all remaining unresolved issues, not just the last one encountered
before stopping. State explicitly whether N is the same value as `AGENTS.md`'s general
3-attempt Attempt Limit or a distinct, workflow-specific value — leaving the exact number
open as a shared Unknown with `itp003` (see Unknowns), consistent with that Plan's own
treatment of the same open question, rather than deciding it unilaterally here.

## Requirements
- `REQ-001`: `workflow.md` states an explicit maximum number of correction-and-recheck
  cycles tolerated for a single Issue's Plan (near Step 2 and/or Step 8), after which the
  workflow must stop and report `Blocked` instead of continuing to patch.
- `REQ-002`: `workflow.md` specifies that the `Blocked` report in this case must contain a
  summary of all remaining unresolved issues, not only the last one encountered.
- `REQ-003`: `workflow.md` states explicitly whether this bound is the same value as
  `AGENTS.md`'s general 3-attempt Attempt Limit or a distinct, workflow-specific bound —
  stated as a cross-reference, not silently assumed.
