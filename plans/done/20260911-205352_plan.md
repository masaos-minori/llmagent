## Goal
Wire HTTP-mode RAG augment (`RagPipeline.augment()` when `rag_service_url` is
configured) to actually populate `RagPipeline.last_fetch_result` from the RAG
service's `selected_hits` response field, matching the in-process path's existing
behavior and the field's documented contract.

## Priority
Medium

## Scope
- **In-Scope**: Parse `selected_hits` from `call_rag_service()`'s HTTP response;
  construct a `TwoStageFetchResult` from it (gated on non-empty hits, using
  config-derived `min_score_applied`/`max_chunks_per_doc`); route it through the
  `set_fetch_result` callback chain to `RagPipeline.last_fetch_result`; correct the
  3 currently-skipped tests in `tests/agent/commands/test_agent_rag.py` (their
  bodies assert the wrong type — see Design) and one test each in
  `tests/rag/test_augment_refiner.py` / `tests/rag/test_augment_integration.py`
  whose assertion describes the exact string-based behavior being replaced.
- **Out-of-Scope**: Any change to in-process (non-HTTP) pipeline fetch-result
  behavior (`scripts/rag/stage_lifecycle.py`, untouched); the RAG service's own
  response schema (already emits `selected_hits`, confirmed — see Design);
  deduplicating `tests/rag/test_augment_integration.py` and
  `tests/rag/test_augment_refiner.py` (discovered to be byte-identical duplicate
  files — see Assumptions; both are edited identically here, not merged).
- **Dependencies**: N/A: none.

## Background
`RagPipeline.last_fetch_result` is typed `TwoStageFetchResult | None` and
documented (`augment()`'s docstring "Side effects" section) as updated both by the
in-process path and "when HTTP stage is used." The in-process path
(`scripts/rag/stage_lifecycle.py:136`) does construct and assign a real
`TwoStageFetchResult`. HTTP mode never has: `call_rag_service()`
(`scripts/rag/pipeline_service.py`) only reads the `"result"` string field from the
RAG service's JSON response and never reads `selected_hits` at all, despite the RAG
service itself already returning that field (confirmed server-side, see Design).

Git history clarifies how this gap arose: commit `cd59f3792` ("refactor(augment):
simplify set_fetch_result callback to str...", 2026-09-02) changed
`set_fetch_result`'s type annotation from `Callable[[TwoStageFetchResult], None]`
to `Callable[[str], None]` across `pipeline_service.py`/`http_augment.py`/
`augment.py`, and added a new call site in `HttpAugment.run()`
(`self._set_fetch_result(result)`, passing the augmented context *string*) to keep
the (now-unused) callback invoked with something. However, even before that commit,
`call_rag_service()` never parsed `selected_hits` or called the callback with a
real `TwoStageFetchResult` — the actual client-side wiring gap this issue fixes
was never implemented at any point in this file's history, not merely regressed.

## Problem
No code in `scripts/rag/pipeline_service.py`, `scripts/rag/http_augment.py`, or
`scripts/rag/augment.py` reads a `selected_hits` key from the RAG service's JSON
response, and no `TwoStageFetchResult` is ever constructed for the HTTP-mode path:
- `call_rag_service()` reads only `"result"`; `_set_fetch_result()` is defined but
  never called from within that file.
- `RagPipeline.__init__` constructs its `AugmentRefiner` without a
  `set_fetch_result` callback, so `AugmentRefiner._set_fetch_result` is a no-op.
- `HttpAugment.run()` currently calls `self._set_fetch_result(result)` with the
  augmented context *string* (line 120-121) — a call site added by the same
  refactor that flattened the type to `str`; this must be removed, not preserved,
  since it conflicts with `last_fetch_result`'s actual type contract (confirmed:
  `PipelineDiagnostics.to_dict()`, `scripts/rag/diagnostics.py:99-106`, calls
  `fetch.hits`/`fetch.min_score_applied` on `self.fetch_result` — a plain string
  would raise `AttributeError` there).
- The 3 currently-skipped tests in `tests/agent/commands/test_agent_rag.py`
  (`TestAugmentHttpMode::test_stores_selected_hits_in_last_fetch_result`,
  `::test_does_not_overwrite_last_fetch_result_when_hits_empty`,
  `::test_missing_selected_hits_key_does_not_raise`) already mock a
  `selected_hits` field in the response and are named for the intended behavior,
  but as currently written, all three assert `pipeline.last_fetch_result` equals a
  plain *string* — the same wrong type contract, not what their own names describe.
  A fourth test, `test_set_fetch_result_callback_called_with_result` (present
  identically in both `tests/rag/test_augment_refiner.py` and
  `tests/rag/test_augment_integration.py` — see Assumptions), currently asserts
  the callback is called with the string result; this describes exactly the
  behavior being replaced and must be corrected, or it will start failing once the
  erroneous string call site is removed.

## Reason for change
Any caller relying on `last_fetch_result` after an HTTP-mode augment (`get_diagnostics()`,
two-stage-fetch consumers referenced in `stage_lifecycle.py`'s own comment, e.g.
`REPLAgent._run_turn`) currently gets stale or `None` data with no error surfaced,
silently degrading downstream behavior whenever the RAG service is used instead of
the in-process pipeline. This directly contradicts `augment()`'s own documented
contract.

## Implementation intent
Parse `selected_hits` in `call_rag_service()` and invoke its (currently dead)
`_set_fetch_result()` helper with the raw hit-dict list whenever the response body
was successfully parsed (both the empty-`"result"` and non-empty-`"result"` success
paths — `selected_hits` and `result` vary independently in the response). Thread
this raw list up through `HttpAugment` unchanged (pure pass-through, as it already
does structurally). In `AugmentRefiner` — the first layer with access to `RagConfig`
— wrap the callback: construct a `TwoStageFetchResult(hits=selected_hits,
min_score_applied=self._cfg.rag_min_score, max_chunks_per_doc=self._cfg.max_chunks_per_doc)`
and forward it to `AugmentRefiner`'s own `set_fetch_result` callback, but only when
`selected_hits` is non-empty — this single check is what implements "do not
overwrite `last_fetch_result` when hits are empty/absent." Wire `RagPipeline.__init__`
to pass a real callback into `AugmentRefiner(...)` that assigns
`self.last_fetch_result`. Remove `HttpAugment.run()`'s now-incorrect direct
`self._set_fetch_result(result)` call.

## Design
Investigation (Step 2/3, Path B full analysis) established the following, in order:

1. **The 3 target tests are currently skipped, not failing** (`@pytest.mark.skip`,
   citing this exact issue) — reproduced via
   `uv run pytest tests/agent/commands/test_agent_rag.py::TestAugmentHttpMode -v -rs`
   (2 passed, 3 skipped).
2. **The client-side wiring gap is real and confirmed**: `call_rag_service()`
   (`pipeline_service.py:134-135`) reads only `body.get("result")`; no code path
   reads `selected_hits`. `RagPipeline.__init__` (`pipeline.py:115-121`) constructs
   `AugmentRefiner` without a `set_fetch_result` kwarg.
3. **The server-side already emits `selected_hits`** — resolves the issue's own
   Unresolved Question. `scripts/mcp_servers/rag_pipeline/rag_pipeline_models.py:215`
   declares `selected_hits: list[dict[str, Any]] = Field(...)` on the response
   model; `rag_pipeline_service.py:150-190`'s `_build_selected_hits()` populates it
   from `pipeline.last_fetch_result.hits` (the server's own `RagPipeline` instance
   runs in-process, so its own `last_fetch_result` is already correctly populated
   via the existing in-process path — this bug is specific to a *client* of the
   service, not the service itself). `tests/mcp_servers/rag_pipeline/test_rag_pipeline_server_endpoints.py:99`
   confirms the real response body's top-level key is literally `selected_hits`.
4. **The existing skipped tests' own assertions are wrong**, independent of the
   issue's description — a second adversarial-verification finding beyond what the
   issue itself flagged. All 3 currently assert `pipeline.last_fetch_result == "<a
   string>"`. This cannot be the correct target behavior:
   `pipeline.py:85` types `last_fetch_result: TwoStageFetchResult | None`, and
   `diagnostics.py:99-106`'s `PipelineDiagnostics.to_dict()` calls
   `fetch.hits`/`fetch.min_score_applied` on it — a plain string would raise
   `AttributeError` there. These 3 tests must be corrected (not merely un-skipped)
   as part of this fix, per `rules/ai-execution.md` Adversarial Verification: write
   the corrected understanding into this Plan rather than the issue's original
   framing (which assumed un-skipping alone would suffice).
5. **A 4th test needs correction for the same reason**, discovered only via
   dependency graphing beyond the issue's own listed Target Files:
   `test_set_fetch_result_callback_called_with_result` (identical in
   `tests/rag/test_augment_refiner.py` and `tests/rag/test_augment_integration.py`
   — confirmed byte-identical duplicate files, see Assumptions) currently asserts
   the callback receives the augmented context string, matching the exact
   behavior being removed (`http_augment.py`'s incorrect direct call site).
6. **Root cause traced via git history, not merely inferred**: commit `cd59f3792`
   (2026-09-02, "refactor(augment): simplify set_fetch_result callback to str...")
   changed the callback's type from `Callable[[TwoStageFetchResult], None]` to
   `Callable[[str], None]` across all 3 production files, and added the (now
   incorrect) direct string call in `HttpAugment.run()`. However,
   `git show cd59f3792^:scripts/rag/pipeline_service.py` shows `call_rag_service()`
   never called the callback even before that commit — the actual `selected_hits`
   parsing this issue adds was never implemented at any point, so this is new
   wiring work, not a pure revert.
7. **Fix design**: `call_rag_service()` gains `selected_hits` parsing and calls its
   own (currently dead) `_set_fetch_result()` helper with the raw hit-dict list on
   every successfully-parsed response (both `""`-result and non-empty-result
   paths) — retyped to `Callable[[list[dict[str, Any]]], None]`. `HttpAugment`
   passes this straight through unchanged (already does so structurally) except
