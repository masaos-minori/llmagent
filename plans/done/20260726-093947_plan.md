# Plan: Document `BG_FAILURE_THRESHOLD` semantics and defer configurability

## Goal

Close the documentation gap around `BG_FAILURE_THRESHOLD` in `scripts/agent/orchestrator.py`
— clarifying that it only changes a log level, that it currently tracks a single
background-task type, and that it can accumulate across `/clear`/`/session load` cycles
— while making and justifying a concrete, evidence-based decision to defer moving it into
the config system, without changing any existing runtime behavior.

## Scope

**In scope:**
- Add a clarifying comment/docstring block directly above `BG_FAILURE_THRESHOLD`
  (`scripts/agent/orchestrator.py:51`) stating: its only effect is a
  `logger.error` vs. `logger.warning` choice in `_discard_and_log`; it currently applies
  only to the first-turn session-title-generation background task; and it is reset by a
  background-task success or `asyncio.CancelledError`, not by `/clear` or `/session load`.
- Expand `_discard_and_log`'s docstring (`scripts/agent/orchestrator.py:580-614`) to state
  the cross-session accumulation semantics precisely (can span multiple `/clear`/
  `/session load` cycles within one process lifetime because `Orchestrator` is a
  long-lived singleton), so a future reader does not need to cross-reference
  `startup.py`, `conversation_service.py`, and `session_restore.py` to re-derive this.
- Add a short comment near `self._consecutive_bg_failures: int = 0`
  (`scripts/agent/orchestrator.py:129`) noting it is scoped to a single background-task
  type today and must not be reused for a second task type without giving that type its
  own counter.
- Make and document a concrete decision on configurability (see Design): **defer**
  moving `BG_FAILURE_THRESHOLD` into the config system for this change; retain it as a
  named module constant, with the clarifying comment from the first bullet fully
  satisfying the requirement doc's fallback instruction ("if configurability is deemed
  out of scope, at minimum retain it as a named constant with the clarifying comment").
- Add/adjust unit tests to lock in current behavior (log-level thresholds, reset
  semantics) so the documentation change cannot silently drift from the code it describes.

**Out of scope:**
- Moving `BG_FAILURE_THRESHOLD` into `AgentConfig`/`config/agent.toml` — evaluated and
  explicitly deferred (see Design for justification); not implemented in this change.
- Any change to reset-on-success (`orchestrator.py:614`), reset-on-cancellation
  (`orchestrator.py:586`), the first-failure user notification
  (`orchestrator.py:589-599`), or the `stat_turns == 1` gating (`orchestrator.py:573`).
- Any change to `startup.py`'s `on_first_turn` wiring.
- Adding a second background-task type or a keyed/dict-based failure counter — no such
  task type exists today; only a documentation comment guarding against future misuse
  is added.
- `docs/*.md` updates — out of scope for this document-only planning phase.

## Design

**Decision: Retain `BG_FAILURE_THRESHOLD` as a named module constant with a clarifying
comment; defer moving it into the config system (`ctx.cfg`/`AgentConfig`) for this
change.**

Justification, weighing the evidence gathered in Unknowns/U3 against the requirement
doc's own severity assessment:

1. **The requirement doc's own "Problem" analysis downgrades urgency.** It explicitly
   states the threshold's only observable effect is a log-level change (no
   circuit-breaker, no task-disabling, no other downstream consequence), that the
   scenario reaching the threshold is narrow (5 separate `/clear`/`/session load`
   cycles with zero intervening successes on one background-task type), and that "the
   code today is functionally reasonable... under-documented" rather than broken. A
   configurability knob for a value whose only effect is a log line's severity, for a
   narrow and already-partially-mitigated scenario (reset-on-success, cancellation
   excluded), does not carry proportionate operator value today.
2. **Configurability would cost 5 files, not ≤3.** U3 confirms end-to-end wiring
   requires touching `config/agent.toml`, `scripts/agent/config_dataclasses.py`,
   `scripts/agent/services/config_validators.py`, `scripts/agent/config_builders.py`,
   and `scripts/agent/orchestrator.py`. Per `skills/python-issue-to-plan/SKILL.md`'s
   Path A/B classification, this pushes the task from Small (≤3 files, no
   interface/schema changes) into Large (>3 files), which is disproportionate scope
   for a change whose only functional effect (per point 1) is a log level. The
   documentation-only path keeps the change to exactly 1 production file
   (`orchestrator.py`) plus tests.
3. **A real, copyable precedent exists if this is revisited.**
   `ToolConfig.tool_error_max_consecutive` (`config_dataclasses.py:168`) is
   structurally identical to what `BG_FAILURE_THRESHOLD` would become as a config
   field, and its validator (`config_validators.py`) and builder
   (`config_builders.py`) wiring is a directly copyable template. Recording this
   precedent in the constant's own comment means a future change that does need
   operator-tunable sensitivity (e.g., if a second background-task type is added and
   shared-counter concerns in Implementation Intent item 3 become live) has a clear,
   low-ambiguity path forward, without this change having to speculatively build it
   now ("no new task type exists today, so no functional change is required" — quoting
   the requirement doc's own item 3 framing, applied here to configurability too).
4. **This satisfies the requirement doc's explicit fallback clause verbatim**:
   "If configurability is deemed out of scope, at minimum retain it as a named constant
   with the clarifying comment from item 1" (Implementation Instructions #2/#3). The
   decision is documented here, in the constant's own comment (Implementation Step 2),
   and is not left ambiguous or silently skipped.
5. **What changes vs. what does not:** Only comments/docstrings change in
   `orchestrator.py`; `BG_FAILURE_THRESHOLD`'s value (5), its type, and every branch of
   `_discard_and_log`'s log-level logic are byte-for-byte unchanged. Tests are added to
   pin this behavior so the documentation cannot silently drift out of sync with the
   code in the future.

## Risks

- **Risk:** Deferring configurability could be seen as not fully satisfying the
  requirement doc's Acceptance Criteria item "A decision is made and implemented (or
  explicitly documented as deferred)."
  **Likelihood:** low — the criterion explicitly permits "documented as deferred" as a
  valid outcome.
  **Mitigation:** Design section above documents the decision and its justification in
  full, referencing concrete file-count evidence (U3); the constant's own comment
  (Implementation Step 2) restates the deferral and points to the precedent
  (`tool_error_max_consecutive`) for future reversal, so the decision is discoverable
  both in the plan and in the code itself.
- **Risk:** Adding new unit tests for `_discard_and_log`'s log-level branching could
  be brittle if it asserts on `caplog`/mock call arguments tied to exact log message
  text, which could break if the docstring/comment changes in Steps 2-4 are
  accidentally placed such that they alter runtime string formatting (they should not,
  since only comments/docstrings are touched, not the f-strings passed to `logger.*`).
  **Likelihood:** low.
  **Mitigation:** Implementation Step 6's diff check explicitly confirms only
  comments/docstrings changed before running tests; tests should assert on log *level*
  (`logger.warning` vs `logger.error` call site, e.g. via `caplog.records[i].levelname`)
  rather than exact message text where practical, to reduce coupling to wording.
- **Risk:** A future contributor adds a second background-task type and, missing the
  new scoping comment (Step 4), reuses `_consecutive_bg_failures` anyway, silently
  conflating two unrelated failure streams (the exact latent risk the requirement doc
  flags in its Problem section item 2).
  **Likelihood:** medium over time, since nothing enforces the comment's guidance in
  code today (documentation-only mitigation, not a structural guard).
  **Mitigation:** the comment (Step 4) is the requirement doc's own accepted mitigation
  for this risk ("a comment is sufficient; no new task type exists today, so no
  functional change is required for this item" — Implementation Intent item 3). No
  structural enforcement (e.g., a keyed dict counter) is added in this change since no
  second task type exists yet; this residual risk is accepted and documented rather
  than escalated to `issues/*_risks.md`, consistent with the requirement doc's own
  scoping.

No risk identified above is unmitigated/blocking, so no `issues/*_risks.md` file is
required for this plan.
