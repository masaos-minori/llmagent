## Goal

Ensure WAL checkpoint failure does not result in silent data loss during shutdown.

## Scope

**In**: `scripts/agent/repl.py` (AgentREPL._close_resources())
**Out**: Changes to SQLiteHelper internals, other database maintenance operations

## Assumptions

1. `db.checkpoint("TRUNCATE")` can fail due to exclusive access requirements
2. `PRAGMA wal_checkpoint(PASSIVE)` may succeed where `TRUNCATE` fails because it doesn't require exclusive access
3. `SQLiteHelper("session").open(write_mode=True)` creates a new connection each time

## Implementation Steps

1. Before attempting `db.checkpoint("TRUNCATE")`, first try `db.checkpoint("PASSIVE")` at line 264. If PASSIVE succeeds, log and skip TRUNCATE.
2. If PASSIVE fails, wrap `db.checkpoint("TRUNCATE")` in a retry loop with up to 3 attempts and exponential backoff (1s, 2s, 4s).
3. After retries are exhausted, change the log level from WARNING to ERROR at line 29-30.
4. Before closing the connection in the finally block, copy the WAL file (`{db_name}-wal`) to a backup location so data can be recovered manually.
5. Ensure the session connection is properly closed regardless of checkpoint outcome.

## Risks

| Risk | Likelihood | Mitigation |
|---|---|---|
| Exponential backoff delays shutdown unnecessarily | med | Cap total retry time to 7 seconds; use asyncio.sleep instead of time.sleep |

| PASSIVE checkpoint leaves unflushed WAL pages | low | Document that PASSIVE is a best-effort fallback; TRUNCATE remains preferred |
