# Plan

## Goal
Remove the MDQ service's startup branch that detects the legacy `chunks` table shape and unconditionally drops and recreates it, so that `create_production_tables()` is create-only and a store older than the supported baseline is recovered by deleting the file and re-indexing, as the design documents already describe.

## Priority
Low

## Scope
- **In-Scope**:
  - Delete `_migrate_legacy_chunks_schema()` and its call in `scripts/mcp_servers/mdq/db_schema.py`, and update the docstrings that mention legacy migration there and in `scripts/mcp_servers/mdq/mdq_service.py`.
  - Remove or rewrite the legacy-shape tests, keeping the tests for fresh creation, idempotent re-run, data survival on re-run, and error handling.
  - Update the database and deployment documents that describe automatic legacy detection, the unconditional drop, and the data-loss warning.
- **Out-of-Scope**:
  - The workflow and EventBus migrations and the legacy offset import (separate plans).
  - Changing the MDQ schema, index content, the re-indexing procedure, or the MDQ health check semantics.
  - Adding any replacement shape detection (see UNK-01).

## Background
The database design document (Supported Upgrade Baseline) states that the minimum supported source schema of `mdq.sqlite` is the current `chunks` shape keyed by `chunk_id`; a read-only inspection of the single host on 2026-10-21 found `chunks` starting with `chunk_id`. Verified against current source: `create_production_tables()` is called from `MdqService._init_db()` (the only production caller) and runs `_migrate_legacy_chunks_schema()` first, which drops `chunks`, `chunks_fts`, and the three sync triggers when the first `chunks` column is `id`, then creates the current tables with `IF NOT EXISTS`. MDQ is a derived store recovered by re-indexing.

## Problem
A destructive branch runs on every service start for a shape that no supported database has, and it needs its own test and documentation. Adversarial verification of the Issue found three things it does not state:
- After removal, a legacy-shape database is no longer rebuilt, and `CREATE TABLE IF NOT EXISTS chunks` leaves the old table in place. `_check_schema_health()` in `scripts/mcp_servers/mdq/health_check.py` only checks table and trigger names and an FTS5 query, not the `chunks` column shape, so such a database would report healthy while queries fail. The Issue forbids a replacement detection and forbids changing health semantics, so this becomes an accepted limit that must be recorded (UNK-01).
- `docs/41_db/db_07_api_and_operations-recovery-and-reference.md` states that the legacy `id` shape "is rebuilt by the MDQ service at start", and `docs/41_db/db_03_architecture_and_schema-migration-and-scaling.md` section 10 calls the module the "auto-update source"; neither is in the Issue's file list.
- Section 8d of `db_03` is titled "Automatic Legacy Schema Detection for `mdq.sqlite` Only" and section 8e still says the mdq migration code "stays until the change that removes it lands".

## Reason for Change
Removing a destructive startup path that serves no supported database lowers risk and lets the create-only setup stand alone. The earlier work item to make the rebuild observable and document its recovery becomes unnecessary.

## Implementation Intent
Delete the detection and rebuild, keeping creation of the current tables, triggers, and index state exactly as before. Recovery for an out-of-baseline store is deleting the file and re-indexing, which `db_08_active_databases.md` already documents and which stays unchanged. Documentation states the create-only behavior and the recovery statement only, leaving no history of the removal.
