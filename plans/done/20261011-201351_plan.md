## Background
- The ACK route answers a duplicate ACK with HTTP 200 and an `already_acked: true` flag; a first ACK omits the flag.
- The ACK/NACK endpoint reference documents the duplicate-ACK response as `newly_acked: false`; the delivery-semantics document documents `already_acked: true`. The two documents disagree.
- Three test modules assert `already_acked`: the ACK endpoint, the ACK/NACK, and the concurrent-ACK tests.
- The name `newly_acked` is the internal boolean in the repository function's return tuple, not an HTTP field.
- The mismatch was recorded as UNK-03 in `plans/done/20261011-153619_plan.md` and filed as the source issue.

## Problem
- A client written from the ACK/NACK endpoint reference checks `newly_acked`, never sees it, and cannot detect a duplicate ACK; a client written from the delivery-semantics document checks `already_acked`.

## Reason for change
- Documentation/code mismatch on a public API response; two documents contradict each other, so the contract cannot be read from the documentation alone.

## Implementation intent
- Keep `already_acked` (it matches the route, three test modules, and the delivery-semantics document) and correct the endpoint reference. Renaming the route field would be a public response-shape change and is not chosen.
