# Plan — Extend secret masking beyond key=value and header shapes

## Goal
Broaden `_mask_secrets()` in `scripts/agent/secrets_masker.py` so it masks secrets in
common modern formats beyond the three existing shapes (`key=value`, `Authorization:`
header lines, standalone `Bearer` tokens) — at minimum JSON object values for known
secret key names (`"token"`, `"api_key"`, `"password"`, ...) with `:` and `,`
separators — while preserving the existing patterns verbatim and avoiding false
positives on legitimate non-secret output.

## Priority
High

## Scope
- **In-Scope**: Adding narrow, high-confidence regex patterns to `SECRET_PATTERNS` for
  JSON-style secret values (`"key": "value"`) for known secret key names, covering both
  `:` and `,` separators. Keeping the three existing `key=value` patterns (plus the
  `Authorization:` and `Bearer` patterns) unchanged. Adding unit tests for the new
  patterns, regression coverage for the existing shapes, and a non-secret stderr no-op
  test. Updating the "Secret Masking in MCP Subprocess Failure Reports" section and its
  Known Limitations bullet.
- **Out-of-Scope**: Bare/inline high-entropy tokens with no recognizable key name
  (deferred — see open question); base64/hex API keys; non-ASCII or multi-line secret
  values; replacing the regex approach with a structured secret detector; changing any
  call site or their masking invocation.

## Background
When an MCP subprocess fails to start, the tail of its stderr is included in the
startup failure report and logged. Both pass through `agent/secrets_masker.py`
`_mask_secrets()`. Per `docs/23_agent/agent_10_01_...startup-and-health.md`
("Secret Masking in MCP Subprocess Failure Reports"), masking covers three
case-insensitive shapes: `key=value` for key names like `password`, `api_key`,
`secret`, `token`; `Authorization:` header lines; and standalone `Bearer` tokens.
`_mask_secrets` is also used in `http_lifecycle.py`, `http_lifecycle_errors.py`,
`shared/retry_helper.py`, and `startup_mcp_starter.py`.

## Problem
The regex set `SECRET_PATTERNS` matches only:
- `key = value` for a fixed list of key names (`password|passwd|pwd`,
  `api[_-]?key|apikey`, `secret|token`),
- `Authorization: <scheme> <token>`,
- `Bearer <token>`.

It does NOT mask:
- JSON-formatted secrets such as `"token": "abc123"` or `"api_key":"xyz"` (the
  separator is `:`, not `=`),
- bare/inline tokens with no recognizable key name,
- base64 or hex API keys,
- secrets embedded in URLs without a known key name (`?token=...` is partially covered
  via the `token=` pattern, but unknown-key query strings are not),
- non-ASCII or multi-line secret values.

A failed MCP subprocess that prints such a secret leaks it into the startup failure
report and logs.

## Reason for change
Secret masking is a security control whose effectiveness is only as strong as its
coverage. The current regex surface misses common modern secret encodings, so the
control gives a false sense of protection. Leaked credentials in logs are a direct
exposure. This is security-sensitive.

## Implementation intent
Add narrow, high-confidence patterns to `SECRET_PATTERNS` for the most common unmasked
format — JSON object values for known secret key names — both with `:` and `,`
separators. Keep the existing five patterns intact. Structure each new pattern so group
1 captures the key + separator + opening quote (preserved by the substitution) and group
2 captures the secret value (redacted). Guard against false positives by restricting to
known secret key names and quoted keys; do not introduce over-broad patterns that mask
legitimate non-secret output. Defer bare high-entropy token matching (no
low-false-positive heuristic) and record it as an open question.

Two equivalent mechanisms satisfy this; implement one:
- **(a) Quoted-key JSON patterns (recommended):** For each known secret key name, match
  `"key"\s*[:,]\s*["\']` followed by the value, e.g.
  `(?i)("(?:password|passwd|pwd|api[_-]?key|apikey|secret|token)"\s*[:,]\s*["\'])([^"\']*)`.
  Group 1 = `"token": "`; group 2 = `abc123`; substitution yields `"token": "***MASKED***"`.
- **(b) Unquoted-key `:`/`,` variants:** Also match `key\s*[:,]\s*\S+` for known names
  (YAML/CSV-ish). Higher false-positive risk; prefer (a) unless coverage demand warrants
  it.

## Requirements
- `REQ-001`: `_mask_secrets()` masks JSON-style secret values for known secret key

## Assumptions
- `SECRET_PATTERNS` entries are applied in order and each preserves group 1 while
  redacting group 2; new patterns follow the same two-group convention.
- Known secret key names are a stable, bounded list; adding a new key name later is a
  one-pattern addition.
- Quoted-key JSON is the highest-confidence format; unquoted-key variants carry higher
  false-positive risk and are deferred unless coverage demand warrants them.
- The non-secret sample must not contain any known secret key name followed by a
  `:`/`,` and a quoted value.

## Design
Path A (affects ≤ 3 files; no public/runtime interface change; no DB schema change).
Adversarial verification (Step 2) confirmed the issue's claims against current source:
`SECRET_PATTERNS` (secrets_masker.py lines 6-12) holds exactly five patterns — three
`key=value` variants, `Authorization:`, and `Bearer` — and `_mask_secrets` (lines 15-20)
applies each via `pattern.sub(lambda m: m.group(1) + "***MASKED***")`. None match the
JSON `:` separator, bare tokens, base64/hex, or unknown-key query strings. Call sites
(`startup_mcp_starter.py`, `retry_helper.py`, `http_lifecycle.py`,
`http_lifecycle_errors.py`) all import and use `_mask_secrets`, so adding patterns to
`SECRET_PATTERNS` is backward compatible. Existing tests
(`tests/agent/test_secrets_masker.py`) already assert the three key=value shapes,
Authorization/Bearer shapes, no-secret unchanged, empty string, and
`test_arbitrary_text_never_raises` (arbitrary bytes must not raise) — the new patterns
must preserve all of these. The primary risk is false positives on legitimate output;
mitigated by restricting new patterns to known secret key names with quoted keys and by
the non-secret no-op test (REQ-003). Bare high-entropy token matching is deferred
(REQ-006).

## Risks
- **Risk**: New patterns cause false positives on legitimate non-secret output (e.g. a
  log line containing `"token": "..."` that is not a credential). → **Mitigation**:
  Restrict to known secret key names with quoted keys; add a representative non-secret
  stderr no-op test (REQ-003); review the diff against sample logs before committing.
- **Risk**: A new pattern over-consumes (greedy capture across quotes/values). →
  **Mitigation**: Use `[^"\']*` for the value capture (stops at the next quote); test
  multi-field JSON.
- **Risk**: Adding patterns changes behavior for existing callers that relied on the
  exact prior output. → **Mitigation**: Only ADD patterns; existing five are verbatim;
  regression tests lock prior behavior (REQ-002).
- **Risk**: `test_arbitrary_text_never_raises` breaks if a new pattern has an invalid
  construct. → **Mitigation**: Re-run that test after Phase 1.
