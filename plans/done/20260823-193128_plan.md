# Plan: Add guard tests for eventbus/db.py schema migration

## Goal

Add regression tests for `scripts/eventbus/db.py::_migrate()` that verify column
add/drop, data preservation across migration, and idempotency of repeated calls,
closing the currently-untested migration code path — with no production code change.

## Scope

**In-Scope**
- Create `tests/eventbus/test_eventbus_db_migration.py` with three test functions:
  `test_migrate_adds_new_columns`, `test_migrate_preserves_data`,
  `test_migrate_is_idempotent`.

**Out-of-Scope**
- Any change to `scripts/eventbus/db.py` or `scripts/eventbus/schema.sql` — this is a
  test-only requirement; the migration logic itself is not being modified.
- Testing the `CREATE INDEX IF NOT EXISTS` branch beyond confirming `_migrate()` does
  not raise when it runs — index-creation correctness is not in the original
  requirement's acceptance criteria.

## Assumptions

- The dev/production SQLite version (3.46.1, confirmed via `python3 -c "import sqlite3;
  print(sqlite3.sqlite_version)"`) supports `ALTER TABLE ... DROP COLUMN`, so the
  `_migrate()` drop-column path is reachable and testable without a version guard in
  the test itself.
- No existing test under `tests/eventbus/` exercises `_migrate()` or `_init_schema()`
  directly (confirmed via `rg "_migrate|_init_schema" tests/`) — this is net-new
  coverage, not a duplicate of existing tests.

## Unknowns

None blocking. One non-blocking design detail resolved during planning: the "old
schema" fixture for `test_migrate_adds_new_columns` and `test_migrate_preserves_data`
must reflect the pre-migration `events` table (with `retry_count`, without
`delivery_failure_count`, `dlq_requeue_count`, or the two `idx_events_dlq_*` indexes) —
built inline in the test via `CREATE TABLE` + `ALTER TABLE ... ADD COLUMN retry_count`,
not by loading `schema.sql` (which already reflects the post-migration schema).

## Design

Each test opens a file-based `sqlite3.Connection` against a `tmp_path`-provided
temporary file (not `:memory:`, to match the production on-disk I/O path that
`_init_schema`/`_migrate` actually run against):

1. **`test_migrate_adds_new_columns`**: create the `events` table with the
   pre-migration column set (`retry_count` present; `delivery_failure_count`,
   `dlq_requeue_count` absent), call `_migrate(conn)`, then assert via
   `PRAGMA table_info(events)` that both new columns exist and `retry_count` is gone.
2. **`test_migrate_preserves_data`**: same pre-migration schema, insert 1+ rows before
   calling `_migrate(conn)`, assert the same rows (by `event_id`) are readable
   afterward with unchanged `topic`/`payload`/`published_at` values and
   `delivery_failure_count`/`dlq_requeue_count` defaulted to `0`.
3. **`test_migrate_is_idempotent`**: call `_migrate(conn)` twice in a row on the same
   connection; assert the second call does not raise and the schema/data after the
   second call is identical to after the first (this covers the `try/except
   OperationalError` duplicate-column and no-such-column branches added since the
   requirement was first filed — see requirement's Problem section update).

Import `_migrate` directly from `scripts.eventbus.db` (same import pattern as other
`tests/eventbus/test_eventbus_*.py` files that reach into `scripts.eventbus.db`).

## Risks

- **Risk**: `ALTER TABLE ... DROP COLUMN` support is SQLite-version-dependent (added
  in SQLite 3.35.0); a test written against 3.46.1 could pass locally but fail on an
  older deployed SQLite. → **Mitigation**: this is a pre-existing property of the
  production `_migrate()` code, not something introduced by this test; the test
  documents the version dependency in its module docstring rather than adding a
  runtime version guard, matching how `_migrate()` itself has no guard.
- **Risk**: Using an in-memory DB (`:memory:`) instead of a file-based temp DB could
  hide file-locking or WAL-mode-specific behavior differences from production.
  → **Mitigation**: tests use `tmp_path / "test.sqlite"` file-based connections, not
  `:memory:`.
