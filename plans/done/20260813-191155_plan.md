# Plan: Extract shared console-processor-attach helper in otel_tracer.py

## Goal
Remove the duplicated "create `_ConsoleProcessor`, call `add_span_processor`" code that appears
at both `_attach_console_exporter` and the OTLP-unavailable fallback branch inside
`_attach_otlp_exporter` in `scripts/shared/otel_tracer.py`, by extracting it into one shared
private helper — without changing the exact log text or log level emitted at either call site.
The refactor must be provably behavior-preserving via characterization tests added *before* the
extraction.

## Scope

### In-Scope
- Add characterization tests in `tests/shared/test_otel_tracer.py` that lock the exact current
  log text and level produced by `_attach_console_exporter` and by the OTLP-unavailable fallback
  branch inside `_attach_otlp_exporter`.
- Add one shared private helper function in `scripts/shared/otel_tracer.py` that performs
  `_ConsoleProcessor()` construction + `provider.add_span_processor(processor)` + the log call,
  with log level/callable and message/args passed in explicitly by each caller.
- Update `_attach_console_exporter` and the fallback branch of `_attach_otlp_exporter` to call
  the new helper instead of duplicating the two-line pattern.
- Re-run the full `tests/shared/test_otel_tracer.py` suite before and after the change.

### Out-of-Scope
- The OTLP-available success path inside `_attach_otlp_exporter` (lines 117-123) — it does not
  duplicate the console-processor pattern and is not touched.
- Any change to fallback *decision* logic (when console vs. OTLP vs. OTLP-fallback-to-console is
  chosen) — only the structural code path for attaching a console processor + logging.
- `build_tracer()`'s public signature/behavior, `_import_sdk`/`_import_otlp`, and
  `_ConsoleProcessor`'s delegation methods — unchanged.
- Any `docs/*.md` update — verified below that no doc references the private function names.

## Assumptions
- "Byte-identical" in the source requirement's acceptance criteria means the fully-formatted log
  message (after `%`-substitution) is unchanged, not the raw template string object identity.
- The helper may be called with a bound logger method (`logger.info` / `logger.warning`) rather
  than a `logging` level constant — the requirement explicitly allows either ("a `logging` level
  (or a bound `logger.info` / `logger.warning` callable)"); a bound callable is chosen (see
  Design) since it avoids a `getattr(logger, ...)` dispatch and keeps mypy happy without an
  overload.
- This is a same-process, same-module refactor with no new external dependency, so no
  `pip-audit` / `lsof` operational-dependency inspection is warranted.

## Design
The change stays entirely within `scripts/shared/otel_tracer.py`'s existing internal-helper
layering: `build_tracer()` (public) → `_attach_exporter()` (dispatch) → `_attach_console_exporter()`
/ `_attach_otlp_exporter()` (per-exporter) → `_import_sdk()`/`_import_otlp()` (lazy imports). The
new helper sits at the same level as `_attach_console_exporter`/`_attach_otlp_exporter` and is
called *by* them, so it introduces no new import-boundary crossing and no change to
`PYTHONPATH=scripts uv run lint-imports` contracts — everything stays inside `scripts/shared/`.

Concretely:

```python
def _attach_console_processor(provider: Any, log_fn: Callable[..., None], message: str, *args: Any) -> None:
    """Attach a ConsoleSpanExporter-backed processor and log the given message."""
    processor = _ConsoleProcessor()
    provider.add_span_processor(processor)
    log_fn(message, *args)
```

- `_attach_console_exporter` becomes:
  `_attach_console_processor(provider, logger.info, "OTel tracer configured: ConsoleSpanExporter service=%s", service_name)`
- `_attach_otlp_exporter`'s fallback branch becomes:
  `_attach_console_processor(provider, logger.warning, "opentelemetry-exporter-otlp not installed; falling back to ConsoleSpanExporter")`

This preserves the exact message templates and `%s`-args per call site (per `rules/coding.md`'s
f-string/logging conventions — these are `%`-style lazy logging calls, which is the pre-existing
style in this file and must not change to f-strings, since that would change how `%`-args are
substituted and risk breaking the lazy-evaluation contract `logging` relies on).
`Callable` needs importing from `typing` (already imports `Any, Protocol, cast` from `typing` at
line 20 — add `Callable` to that import line).

## Risks
- **Risk**: Choosing a bound-callable (`logger.info`/`logger.warning`) parameter instead of a
  `logging` level int could be seen as under-specified relative to the requirement's literal
  example signature `_attach_console_processor_with_log(provider, level, message, *args)`. →
  **Mitigation**: The requirement text itself offers the callable form as an explicit alternative
  ("a `logging` level (or a bound `logger.info` / `logger.warning` callable)"); this plan commits
  to the callable form in the Design section so implementation has no remaining ambiguity to
  resolve mid-flight. Likelihood: low.
- **Risk**: Tightening the existing `test_falls_back_to_console_when_otlp_unavailable` assertion
  from substring to exact match could break if OTel's `caplog` record formatting differs from a
  plain `%`-substitution (e.g., extra context injected by a logging filter/formatter elsewhere in
  the suite). → **Mitigation**: Phase 1 runs this exact tightened assertion against current,
  pre-refactor code first and requires it to pass before any production-code edit — if it fails,
  the assertion itself needs adjustment before proceeding, which is caught before Phase 2 rather
  than after. Likelihood: low.
- **Risk**: A future contributor extends `_attach_console_processor` with more responsibilities
  over time, re-introducing coupling between the two call sites' log wording (defeating the
  purpose of keeping message/args as explicit call-site arguments). → **Mitigation**: The helper's
  signature keeps `log_fn`/`message`/`*args` as required, explicit parameters (no defaults, no
  hardcoded message inside the helper), which structurally discourages hardcoding a message inside
  the helper; this is a documented design constraint in this plan for future reviewers. Likelihood: low.
