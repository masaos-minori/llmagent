## Background
This Plan follows the same Implementation-Notes classification review that produced
`plans/done/20260915-145322_plan.md` (ADR-004's Known Deviations gap). This issue
covers the one pattern common to all 13 ADRs: a redundant file/class/config/test list
at the top of `## Implementation Notes` that duplicates the same ADR's own
`### Implementation References`.

## Problem
Every ADR under `docs/adr/` opens `## Implementation Notes` with a bulleted
file/class/config/test list, immediately followed by boilerplate stating this detail's
canonical home is Implementation Reference. The same ADRs also carry a
`### Implementation References` subsection under `## Related Documents` that
duplicates the same file/symbol list — but, confirmed by direct investigation of all
13 files (see Design below), the two copies are not always simple duplicates:
several ADRs have real discrepancies (a file/symbol/test present in one copy but
missing from the other), and at least one ADR (ADR-006) has *both* copies citing
files and symbols that no longer exist in current source at all.

## Reason for change
Maintaining the same list in two places is pure duplication with a real cost: a
rename or removal must be applied twice, and nothing currently catches drift between
the two copies (confirmed: `tools/check_adr_reference.py` only checks that a cited
*source file* contains an ADR-ID backreference — it does not cross-check the two
lists within the same ADR against each other). The ADR's own boilerplate already
designates Implementation Reference as the canonical home for this detail.

## Implementation intent
For each of the 13 ADRs, treat `### Implementation References` as the reconciliation
target: add anything genuinely missing there (whether cited only in Notes, or true to
current source but cited nowhere), correct anything stale against current source
where discovered, then delete the now-fully-reconciled list from `## Implementation
Notes`. Where an ADR's list contains an item that is not actually a duplicate — a
fact not derivable from a file/symbol name alone, and not present in References at
all — treat it as protected content to migrate into References rather than deleted
outright, since it fails this issue's own "delete" criterion (must be a true
duplicate). Preserve every ADR's own already-out-of-scope non-list prose untouched.

## Design
This is a Path B task (13 target files > 3-file Path A threshold). Architecture,
dependency-graphing, and operational-dependency-inspection analysis (per
`skills/issue-to-plan/workflow-path-b.md`) largely do not apply to a pure
documentation restructuring with no `scripts/`/`config/` changes — no import graph,
call graph, or process/socket inspection is relevant. The concrete dependency-
graphing deliverable ("these N files will require changes") is the 13-row
Implementation Target Files table itself, produced by direct, per-file investigation
(delegated to a research pass covering all 13 files, then independently spot-verified
against current source for the highest-risk findings — see below). Historical
analysis (git churn, author count) is recorded in Affected areas above.

- **Investigation method**: every one of the 13 ADRs was read in full for both its
  `## Implementation Notes` list and its `### Implementation References`
  subsection, and the two were diffed file-by-file and symbol-by-symbol. Findings
  were then spot-verified directly against current source (not merely trusted as
  reported) for every case involving a discrepancy: `ls`/`grep` confirmed the
  existence of every file and symbol REQ-001, REQ-003, REQ-006, REQ-011, REQ-012,
  and REQ-013 propose adding to References, and confirmed ADR-014's own test-path
  hedge was justified (the cited glob does not resolve).
- **Not every list item is a true duplicate**: this issue's own "delete" criterion
  requires an item be (a) file/line/function-only description, (b) fully derivable
  by reading the source, and (c) becoming stale on implementation change. A single-
  line operational fact like ADR-008's WAL/checkpoint mode, or ADR-006's DLQ
  promotion-loop interval, or ADR-007's HTTP endpoint list, fails criterion (b) — it
  is not derivable merely from knowing which file/function implements it. These are
  migrated into References (as new canonical content) rather than silently dropped,
  per REQ-006/007/008 above, since Implementation References is this issue's own
  designated canonical home for such detail, not merely reused as a container for
  what does not fit criterion (b) but instead a place where its now-canonical,
  non-duplicated statement lives once.
- **Cross-copy agreement is not proof of correctness (found during adversarial
  re-verification of the initial investigation, not by the initial investigation
  itself)**: ADR-005 and ADR-009 both cite a "`scripts/rag/repository.py` —
  `RagRepository.delete_existing_document()`, `RagRepository.delete_document(url)`"
  entry in Implementation References that is wrong against current source —
  `RagRepository` has no delete method at all; the real symbols
  (`DocumentManager.delete_existing_document()`, `delete_document_chain()`) live in
  `scripts/rag/ingestion/document_manager.py`, a file neither ADR's Notes nor
  References list. Because this same wrong text appears in *both* ADRs' References
  sections (apparently copied from one to the other) and was never contradicted by
  either ADR's own Notes list, a same-file cross-copy comparison alone would not
  catch it — only direct verification against current source did. Similarly,
  ADR-010's Notes cites `AugmentStage.run()` without listing its containing file
  (`scripts/rag/stages/augment.py`), and References omits it entirely — again only
  caught by checking actual source, not by comparing the two copies to each other.
  This is the same category of risk as ADR-006 below, just smaller in scope — see
  Risks for the resulting general caution this implies for the other, "clean" rows.
- **ADR-006 is a materially different risk class from the other 12**: for every
  other ADR, cross-referencing the two existing copies against each other was
  sufficient to find and fix any gap. For ADR-006, *both* copies cite a file/module
  layout (`publish.py`, `subscribe.py`, `ack.py`, `nack.py`, `EventBroker.notify_subscribers()`)
  that does not exist in current source at all — the actual code was reorganized
  into `*_route.py` files and `db.py` without either copy being updated. Cross-
  referencing the two stale copies against each other would not have caught this;
  only reading the actual current `scripts/eventbus/*.py` source did. This is called
  out explicitly (REQ-006, Implementation Target Files row, Reference Files rows) so
  the implementer does not assume "the two copies agree, therefore both are correct."
- **Pre-existing checker baseline**: `tools/check_docs_structure.py` already reports
  pre-existing, unrelated findings against several of these 13 ADRs (confirmed for
  ADR-004 in the prior Plan this session: 9 findings — size limit, missing
  `## Keywords`, broken links, unresolved front-matter `related` entries; other ADRs
  are expected to show a similar pattern per the same template, though not
  individually re-confirmed here). `AC-3` requires no *new* finding beyond each
  file's own pre-existing baseline — establish that baseline for each of the other
  12 files at implementation time (run the four tools once before editing, record
  the count, then again after) rather than assuming zero.
- **Placeholder consistency**: the one-line pointer text is used verbatim across
  every ADR that needs it (ADR-001, 003, 005, 009, 010, 011→ADR-012, 012→ADR-013,
  013→ADR-014 per Requirement numbering above) so a future reader sees one
  consistent convention, not 8 differently-worded placeholders.

## Risks
- **Risk**: Blindly deleting a list from all 13 files in one mechanical pass without
  first diffing against Implementation References (the source issue's own explicit
  warning) could silently drop unique content. → **Mitigation**: this Plan's
  Requirements are per-ADR, evidence-specific, and were independently spot-verified
  against current source rather than derived only from the two copies' mutual
  agreement — see Design "ADR-006 is a materially different risk class."
- **Risk**: Two copies agreeing with each other is not proof either is correct — this
  Plan's own initial per-ADR investigation (a delegated research pass) reported
  ADR-005/008/009/010 as clean or requiring only deletion, but this Plan's own
  subsequent adversarial re-verification against actual current source found: ADR-005
  and ADR-009 cite a nonexistent-method/wrong-class entry
  (`RagRepository.delete_existing_document()` — `RagRepository` has no delete
  method); ADR-008 cites a nonexistent filename (`helpers.py` instead of `helper.py`)
  in both copies and omits `create_schema()`'s file entirely from both; ADR-010
  omits a real file/symbol (`AugmentStage.run()`/`scripts/rag/stages/augment.py`)
  from both. None of these four would be caught by comparing an ADR's two copies to
  each other — only direct verification against current source found them, and in
  three of the four cases (005, 008, 009) the error exists identically in *both*
  copies, so cross-copy agreement actively masked it. → **Mitigation**: all four
  (REQ-005, REQ-008, REQ-009, REQ-010) were corrected in this same Plan before
  finalizing (see Design). Given this pattern was found in 4 of the 13 rows this
  Plan deep-checked — a high enough rate that "the fork's report found no
  discrepancy" cannot be trusted as sufficient on its own — every remaining row
  (including ADR-002 and ADR-004, whose citations were independently spot-checked
  and found correct in this Plan's own adversarial pass, and ADR-001/003/007/012/013/014,
  whose additions were confirmed to exist but not exhaustively re-verified
  symbol-by-symbol against every unrelated existing entry) MUST have every file path
  and symbol name in its Implementation References re-verified against actual
  current source (via `ls`/`grep`, not by re-reading the ADR text) immediately
  before that row's edit is applied at implementation time — not merely trusted from
  this Plan's own evidence-gathering pass, which itself was demonstrated to have
  missed real errors initially.
- **Risk**: ADR-006's References rewrite could itself introduce a new inaccuracy if
  the source-audit is incomplete. → **Mitigation**: Validation plan's dedicated
  manual source-existence re-check step for ADR-006, run again at implementation
  time (source may have changed further since this Plan's evidence-gathering).
- **Risk**: A test file path carried forward from an ADR's own text (rather than
  independently verified) could be stale, propagating a broken reference into the
  now-canonical Implementation References. → **Mitigation**: `UNK-02`/`UNK-03` flag
  every not-yet-independently-verified test path; REQ-002/011/012 each explicitly
  require verification before addition, matching the discipline REQ-013 already
  demonstrated was necessary (found a real stale glob).
- **Risk**: `docs/00_governance_01_documentation-policy.md`'s exact non-empty-content
  requirement was resolved by absence of an enforcing rule, not by an explicit
  governing statement — a future policy update could contradict this Plan's
  Assumption. → **Mitigation**: the one-line pointer is used regardless (a
  conservative choice that satisfies a stricter reading too), per Assumptions above.
