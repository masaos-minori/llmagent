## Goal
- Resolve INV-015 potential violation: prevent local fallback on RAG 401/403 errors while preserving existing 4xx-fallback behavior for other client errors.

## Background
ADR-010 defines the external RAG service failure fallback policy. Its Decision #4 states "HTTPエラー（401, 403, 4xx, 5xx）と空結果（""）を区別する" and Decision #6 states "技術的失敗（タイムアウト、接続エラー、HTTPエラー）のみをフォールバック条件とする". However, INV-015 specifically states "No local fallback on RAG 401/403" as an invariant — authentication errors should not be hidden by fallback, as doing so masks security issues.

The current code in `pipeline_service.py` line 152-161 treats ALL 4xx errors uniformly: returns `None` (which triggers fallback) with a warning log. This means 401/403 errors are silently converted to in-process fallback, hiding authentication failures.

## Problem
INV-015's invariant ("No local fallback on RAG 401/403") is potentially violated because `call_rag_service()` in `pipeline_service.py` returns `None` for ALL 4xx errors (including 401/403), triggering in-process fallback. This conceals authentication errors from the caller, making it impossible to distinguish between "no result found" and "authentication failed".

## Reason for change
Authentication errors (401/403) indicate credential problems that should be surfaced to the user rather than masked by fallback. Silent fallback on auth errors could lead to users seeing stale data without knowing their credentials have expired or been revoked.

## Implementation intent
1. Modify `call_rag_service()` to distinguish 401/403 errors from other 4xx errors: return a sentinel value indicating "auth error" instead of `None` for 401/403.
2. Propagate the auth error up through `http_augment.py` so callers can handle it appropriately.
3. Update INV-015 verification status in `adr-index.md`.
4. Add tests covering the new 401/403 error handling.

## Requirements

## Design
Two design points from Step 3's inspection:

- **INV-015 vs. ADR-010 Decision #4 tension**: Decision #4 states "HTTPエラー（401, 403, 4xx, 5xx）と空結果（""）を区別する". The listing of "401, 403" separately from "4xx" suggests they were intentionally called out as special cases — possibly because auth errors should be handled differently than other client errors. INV-015 ("No local fallback on RAG 401/403") confirms this interpretation. The fix should treat 401/403 distinctly from other 4xx errors.

- **Propagation mechanism**: Extending `HttpResultKind` with an `AUTH_ERROR` variant is preferred over raising exceptions because:
  1. Minimal caller impact — callers already check `result is None`; adding an extra `kind == AUTH_ERROR` check is additive, not breaking.
  2. Consistent with existing pattern — `HttpAugmentResult.http_result_kind` already carries classification information.
  3. Observable — metrics/logging can distinguish auth errors from other failures.
