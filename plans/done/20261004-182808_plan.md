# Plan: Preserve original exception type through retry

## Goal
Preserve the original exception type when `retry_once_with_delay` fails on second attempt, instead of always wrapping in `RuntimeError`.

## Priority
High

## Scope
- **In-Scope**: Modify `retry_once_with_delay` to re-raise the original exception; update callers that depend on `RuntimeError`; add regression tests
- **Out-of-Scope**: Changing retry count or delay behavior; adding exponential backoff

## Background
The shared retry helper `retry_once_with_delay` in `scripts/agent/shared/retry_helper.py` catches all exceptions from the first attempt and retries once. On second failure it always raises `RuntimeError` regardless of the original exception type.

## Problem
When the first attempt raises `TimeoutError` and the retry raises `ConnectionRefusedError`, both are silently converted to `RuntimeError`. The caller cannot distinguish between transient network errors and configuration errors.

## Reason for change
Error diagnosis becomes impossible — the root cause is lost. Callers cannot implement targeted recovery logic based on exception type. Monitoring/alerting systems cannot differentiate error categories.

## Implementation intent
Change the second-failure path in `retry_once_with_delay` to re-raise the original exception after logging, preserving its type information. Update callers that currently catch `RuntimeError` to handle the broader set of possible exception types.

## Requirements
- `REQ-001`: Original exception type is preserved through retry
- `REQ-002`: Test verifies `TimeoutError` remains `TimeoutError` after retry failure
- `REQ-003`: Test verifies `ConnectionRefusedError` remains `ConnectionRefusedError` after retry failure
- `REQ-004`: Existing callers reviewed for compatibility (some may rely on `RuntimeError`)
