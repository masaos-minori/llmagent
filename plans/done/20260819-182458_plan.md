## Design

**Sequencing dependency (must be honored by the implementation phase):**

This plan's implementation must **not start before** the implementation of
`plans/20260819-182209_plan.md` (source requirement
`requires/done/20260818-223342_require.md`, which deletes the dead
`RuntimeToolRegistry.is_side_effect()`/`classify_operation_type()` methods)
is complete. Reason: this plan's `tool_constants.py` docstring rewrite states,
as a factual claim, that "the only other candidate classifier
(`RuntimeToolRegistry.is_side_effect()`) had zero production callers and is
being removed as dead code" — sourced from that requirement's own
conclusion. If that deletion has not yet landed, the corrected docstring's
claim about the *current* state of the codebase would be describing a
still-open removal as done, which is itself a fresh docstring-accuracy
defect of the same kind this requirement exists to fix. The docstring text
must be worded to match whichever state is true at implementation time:
either "removed as dead code" (if `plans/20260819-182209_plan.md` has landed)
or "identified as dead code and scheduled for removal, see
`plans/20260819-182209_plan.md`" (if it has not). The implementer must check
`plans/done/` for `20260819-182209_plan.md` before writing the final wording.

This plan has **no dependency** on `plans/20260819-181912_plan.md` (the
`ToolRouteResolver` dead-argument removal, source
`requires/done/20260818-223204_require.md`) — that plan does not touch
`tool_registry.py`, `tool_constants.py`, or their docstrings, and this plan's
text does not reference `ToolRouteResolver`'s constructor arguments. It is
listed here only because the task instructions require noting the
relationship; the two plans may land in either order relative to each other,
but this plan (tool_registry.py/tool_constants.py docstrings) must follow
`plans/20260819-182209_plan.md` (RuntimeToolRegistry dead-method removal) as
described above.

**Docstring content design:**

1. `scripts/shared/tool_registry.py` module docstring: replace the
   single-role sentence with two enumerated roles:
   (a) drift-detection input for `McpToolDiscoveryService`
   (`validate_routing_against_live`) and config drift checks
   (`validate_routing_against_config`, `check_tool_safety_tiers`,
   `check_unknown_tool_safety_tiers` via `production_config_validator.py` and
   `repl_health.py`);
   (b) the fail-safe "is this a known tool at all" membership check consulted
   by `agent.tool_policy.classify_operation_type()`
   (`scripts/agent/tool_policy.py:69`) to distinguish `OperationType.READ`
   from `OperationType.UNKNOWN` on the live risk-classification path.
   Add one sentence recording the maintain-vs-abolish decision as resolved
   (maintain), citing `repl_health.py`, `mcp_tool_discovery.py`, and
   `production_config_validator.py` as the active wiring evidence. Leave the
   "Ownership model" bullet list and the "Drift detection" function list
   untouched — only the opening role-description paragraph changes.
2. `scripts/shared/tool_constants.py` module docstring: replace the closing
   "fallback/compatibility... never the first-checked source" paragraph with
   three per-consumer statements (registry seed = one-time import-time seed,
   not a fallback; side-effect detection = sole first-checked classifier used
   by `ToolExecutor.execute()`; risk classification = direct first-checked
   WRITE/DELETE/EXECUTE/API_WRITE tiers). Keep the existing "Not a routing
   fallback source" sentence about live `/v1/tools` discovery — that sentence
   is independently accurate and orthogonal to the paragraph being replaced.
3. `docs/04_mcp_03_02_tool-registry.md`: adjust the opening paragraph (line
   20) and the closing paragraph of the "`RuntimeToolRegistry` とライブ検出"
   section (line 138) to add the `tool_policy.py:69` consumer, mirroring the
   corrected `tool_registry.py` docstring's two-role framing, so the doc and
   code agree. This doc edit is explicitly in scope per the requirement's
   Implementation instructions #4 and Acceptance criteria — unlike the
   `require-to-plan` workflow's general rule against touching `docs/*.md`,
   which governs this *plan-writing* phase only, not the implementation phase
   this plan describes.

No method bodies, function signatures, imports, or test files change in any
of the three files.

## Risks

- **Risk**: The implementation phase starts before
  `plans/20260819-182209_plan.md` lands, causing the `tool_constants.py`
  docstring to falsely claim `RuntimeToolRegistry.is_side_effect()` "is being
  removed as dead code" when it has not yet been touched, or worse, to
  reference it after it has already been deleted using present-tense
  "candidate" wording that no longer matches reality.
  **Mitigation**: Design section and Implementation step 1 explicitly require
  checking `plans/done/` before writing final wording; the two valid wording
  forms are spelled out so the implementer does not need to re-derive them.
  Low likelihood, low impact (docstring wording only, easily corrected in a
  follow-up edit).
- **Risk**: Editing `docs/04_mcp_03_02_tool-registry.md` line 138 could
  disturb the surrounding Japanese prose structure (mixed Japanese doc, code
  identifiers, and inline citations), introducing an inconsistent or broken
  sentence.
  **Mitigation**: Design step 3 scopes the edit to the two named sentences
  only; `git diff` review (Implementation step 3) and `check-mcp-docs`
  (link/reference-consistency checks) catch structural breakage before
  commit.
- **Risk**: A future maintainer re-reads the corrected docstrings and
  reopens the "maintain vs. abolish" question despite the requirement's
  evidence-based resolution.
  **Mitigation**: Design step 1 explicitly requires the corrected
  `tool_registry.py` docstring to state the maintain decision and cite the
  three active-wiring call sites, so the resolution is visible in the same
  place a future reader would look. No `issues/` filing needed — this is a
  documentation completeness measure already built into the plan, not an
  unresolved risk.
- **Risk**: Confusing the *within-scope* `agent.tool_policy.classify_operation_type()`
  free function with the *out-of-scope*, separately-deleted
  `RuntimeToolRegistry.classify_operation_type()` method when writing the
  corrected docstring text, given the two symbols share a name.
  **Mitigation**: Design step 1 and the Affected areas section both
  explicitly cite full qualified paths (`agent.tool_policy.classify_operation_type()`
  vs. `RuntimeToolRegistry.classify_operation_type()`) and line numbers to
  prevent ambiguity; Implementation step 3's diff review is a second
  independent check that no file outside the three named targets was touched.

No risk above is blocking or unmitigated; none requires a separate
`issues/` filing.
