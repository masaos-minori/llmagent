# Plan: Narrow redundant except-clause and add constructor-arg validation in RobustSSEParser

## Goal
Close two small correctness/robustness gaps in `RobustSSEParser`
(`scripts/shared/sse_parser.py`), the stateful SSE parser used by the LLM streaming path:
1. Narrow `_is_valid_json`'s `except (orjson.JSONDecodeError, ValueError):` clause to
   `except ValueError:` (behavior-neutral clarity fix — `orjson.JSONDecodeError` is confirmed a
   `ValueError` subclass).
2. Add constructor-time validation to `RobustSSEParser.__init__` that rejects negative
   `malformed_retry` / `heartbeat_timeout`, closing a real (if currently unexercised) gap: the
   hot-config-reload path (`config_reload.py::_apply_sse_reload_params`) writes
   `ctx.cfg.llm.sse_heartbeat_timeout` / `sse_malformed_retry` directly, bypassing the
   `LLMConfig.__post_init__` validators that guard the normal construction path.

## Design
`RobustSSEParser` (`scripts/shared/sse_parser.py`) is a leaf class in `scripts/shared/` with no
outgoing imports besides `codecs`, `time`, `orjson`, and `shared.llm_exceptions.LLMTransportError`.
It has exactly one production caller, `LlmSseStreamHandler.stream_once`
(`scripts/shared/llm_sse_stream.py:65`), which constructs it once per SSE connection attempt using
`malformed_retry`/`heartbeat_timeout` values threaded down from `LLMConfig`
(`scripts/agent/config_dataclasses.py`). Because `RobustSSEParser` sits below the config layer in
the import graph (`scripts/shared/` is imported by `scripts/agent/`, not the reverse), adding a
`ValueError` guard directly in `__init__` does not create any new import-boundary or layering
concern — it is a defensive check local to the class's own constructor, consistent with how
`config_validators.py`'s `validate_llm_sse_heartbeat_timeout`/`validate_llm_sse_malformed_retry`
already validate the same two values one layer up (at `LLMConfig.__post_init__` time). The two
validators live in different layers for different reasons: `config_validators.py` validates at
config-construction time (covers the normal startup path), while the new `__init__` check
validates at parser-construction time (covers the hot-reload path, which mutates `ctx.cfg.llm.*`
directly via `config_reload.py::_apply_sse_reload_params` without re-running
`__post_init__`). Both checks use the same `f"{param} must be >= 0, got {value}"` message
convention already established in `config_validators.py` (lines 71–84), so the second guard reads
as an intentional belt-and-suspenders pair rather than a divergent new convention.

The except-clause narrowing is a pure clarity fix with no design implication: `_is_valid_json`
(line 84) already only ever raises `orjson.JSONDecodeError` from `orjson.loads`, and that type's
MRO (independently verified this session) already includes `ValueError`, so `except ValueError:`
catches the identical set of exceptions the current tuple catches.

## Risks

- **Risk**: The `>= 0` constructor check could theoretically reject a value that a future caller
  intentionally passes as negative for some not-yet-existing use case. → **Mitigation**: Grep-verified
  (this session and per the source requirement) that zero call sites currently pass a negative
  value; the check only closes an existing validation gap, it does not narrow any currently
  exercised behavior. Likelihood: low.
- **Risk**: Narrowing the except clause to `ValueError` could silently stop catching a future
  orjson version's decode-error type if that type ever stops subclassing `ValueError` upstream.
  → **Mitigation**: Independently reconfirmed the current MRO this session
  (`orjson.JSONDecodeError.__mro__` includes `ValueError`); `pyproject.toml` pins orjson via
  `uv.lock`, so an upstream MRO change would only take effect on an explicit dependency bump, at
  which point `uv run pytest tests/agent/test_llm_client.py -k RobustSSEParser` (which includes
  malformed-JSON tests) would surface the regression immediately. Likelihood: low.
- **Risk**: Placing the new boundary tests in `tests/agent/test_llm_client.py` per UNK-01's
  resolution, rather than `tests/shared/test_llm_sse_helpers.py`, could be seen as splitting
  `RobustSSEParser`'s test coverage across two files inconsistently with future expectations.
  → **Mitigation**: `tests/agent/test_llm_client.py` already owns the full behavior suite for this
  class (`TestRobustSSEParserFeed`, `TestRobustSSEParserHeartbeat`); adding constructor-validation
  tests there keeps all `RobustSSEParser`-behavior tests in one file, consistent with the existing
  organization. Likelihood: low.
