## Goal
- Make the web-search server authenticate tool calls with the same shared secret the agent sends (the main `auth_token`, as the git, cicd, and rag-pipeline servers already do), so web-search is usable when its credentials are configured as documented, and retire the redundant `browser_auth_token`.

## Priority
High

## Scope
- **In-Scope**:
  - Add a server-side `auth_token` setting to `config/web_search_mcp_server.toml` that references the same environment variable as the agent's web-search entry, and make the web-search middleware validate it.
  - Remove `browser_auth_token` (config key, `WebSearchConfig` field, the unused `BrowserConfig.auth_token` field, and the separate `MCP_WEB_SEARCH_BROWSER_AUTH_TOKEN` requirement); a configuration that still carries the removed key fails with a clear error instead of silently running unauthenticated.
  - Keep the loopback `/health` admission from mcp004 unchanged.
  - Test updates: a real-application test with a configured token, the config and provider unit tests, and the shared test environment defaults (`tests/conftest.py`) so web-search follows the git and cicd pattern.
  - Update the six documents that describe the browser token.
- **Out-of-Scope**:
  - Authentication of the other MCP servers and the eventbus, the `browser_allowed_domains` allowlist, `BrowserAuthorization`, and how secrets are loaded from the environment.
  - Removing the now-redundant loopback `/health` admission for web-search (see `UNK-02`).
  - A per-tool credential, or accepting several tokens (rejected in Design).
  - Deploying to `/opt/llm/` (a separate step with the deploy skill).

## Background
- Plan `plans/done/20261012-175600_plan.md` (mcp004) fixed the startup health check only and recorded this gap as `UNK-03`; issue `issues/20261012-182600_mcp005_web-search-tool-calls-return-401-when-browser_auth_token-differs-from-auth_token.md` tracks it.
- The git, cicd, and rag-pipeline server configurations each hold `auth_token` as a reference to the same environment variable the agent uses, so client and server share one secret. web-search alone holds only `browser_auth_token`, a separate secret.
- The user decided the credential model for this Plan: align web-search with the other servers (shared `auth_token`) and retire the browser token.

## Problem
Verified against current source and by running the application (`Confirmed by repository evidence`):
- **Tool calls are rejected (reproduced)**: with the agent's main token and a distinct browser token set, the real web-search app answers `/v1/tools` and `/v1/call_tool` with 401 when given the main token and 200 when given the browser token; `/health` from loopback is admitted (mcp004).
- **Cause (explicit in code)**: `web_search_server.py` registers the shared middleware with the browser token for the whole server, while the agent's transport sends the main token (`HttpTransport` takes `cfg.auth_token`).
- **No route separation is possible**: both tools enter through the single `/v1/call_tool` endpoint with the tool name in the request body, so a per-tool credential would need body inspection in the middleware and a per-tool token in the agent's transport (one token per server today).
- **The browser token has no other consumer (explicit in code)**: `BrowserConfig.auth_token` is built by `from_web_search_config` and never read; the only effect of `browser_auth_token` is the middleware.
- **Docs contradict the code**: `mcp_04_01` says the browser token covers `browser_fetch` only, while the middleware enforces it on `search_web` and every other route.
- **Test impact measured by experiment**: with a non-empty token enforced by the web-search app, 27 existing tests in five files fail (their `TestClient` calls carry no token); with the shared test environment default for `MCP_WEB_SEARCH_AUTH_TOKEN` set to empty (the git and cicd pattern), only 3 tests in two files fail, because they build the real agent configuration and need a non-empty value (they already set the git and cicd variables the same way).
- **Pre-flight needs no change**: `deploy/start_agent.sh` derives the required environment variables from the `${ENV:...}` references in the deployed configuration files, so the browser variable stops being required once the key is removed.

## Reason for change
- A deployment that follows the documented setup (two distinct tokens) starts but cannot use web-search, a failure the health check cannot reveal; with equal values it works, so the second token is redundant.
- Aligning with the other servers removes a special case instead of adding a second accepted credential.

## Implementation intent
- One credential per server: the web-search server validates the shared `auth_token` on every protected route; `/health` keeps the loopback admission.
- Remove the browser token everywhere (config, model, docs) rather than leaving a dead field; fail closed on a stale configuration that still names the removed key.
- Follow the git and cicd conventions for the test environment: the shared default for the web-search variable is empty (accept-all), and the few tests that build the real agent configuration set a real value locally.
- Keep the change to the web-search server; the shared middleware is untouched.

## Requirements
- `REQ-001`: A tool call carrying the main `auth_token` the agent sends is accepted by the web-search server, and a protected route called without it or with another token is rejected with 401, including from a loopback client.
- `REQ-002`: `browser_auth_token`, `BrowserConfig.auth_token`, and the requirement for `MCP_WEB_SEARCH_BROWSER_AUTH_TOKEN` are removed; a web-search configuration that still contains `browser_auth_token` raises a clear error naming the replacement key.
- `REQ-003`: The web-search startup health check still passes (the mcp004 loopback `/health` admission is unchanged), and the other MCP servers and the `browser_allowed_domains` and `BrowserAuthorization` behavior are unchanged.
- `REQ-004`: Tests cover the real application with a configured token, the configuration and error cases, and the test environment follows the git and cicd pattern; the whole suite passes.
- `REQ-005`: The six documents that describe the browser token state the shared-credential model and no longer require a second secret.

## Design
- Path B (15 target files, changes a configuration interface). Architecture analysis: the change stays inside the web-search package, its configuration file, and tests; `web_search_models` imports only the shared config helpers, and `lint-imports` covers `scripts/` and is run in validation. Dependency graph: `WebSearchConfig` is consumed by the server, the service, and the provider; `BrowserConfig` only by the service and the provider, which never read its token. Historical analysis: the configuration and model files are quiet; `tests/conftest.py` and the server file are the busiest. Operational dependencies: the agent supplies `MCP_WEB_SEARCH_AUTH_TOKEN` to the subprocess; no listening-port or package-audit concern.
- Credential model (user decision, UNK in the Issue resolved): one shared secret per server, matching git, cicd, and rag-pipeline. The server config adds `auth_token` referencing `MCP_WEB_SEARCH_AUTH_TOKEN` with a comment in the style of `git_mcp_server.toml`.
- Rejected alternatives: accept either token (keeps a second secret and an ambiguous meaning; the server still needs the main token); per-tool credential (needs body inspection in the middleware and a per-tool token in the agent's transport, high blast radius for no consumer); documentation only (leaves a redundant secret and contradicts the code).
- Config loading: `WebSearchConfig.from_dict` loads `auth_token` like the git model (`get_str`, environment reference resolved, absent or null gives empty). If `browser_auth_token` is present it raises `ValueError` with a message naming `auth_token` as the replacement. An empty token keeps the middleware's accept-all fallback, the same as the other servers, which is why tests default the variable to empty.
- Test environment: the shared default for `MCP_WEB_SEARCH_AUTH_TOKEN` becomes empty (set before the loop of dummy values, and removed from that loop), the browser default is dropped, and the three tests that build the real agent configuration set a real value locally, as they do for git and cicd (measured: exactly these three fail otherwise).
- Real-application test: the application reads its token at import time, so the test starts a separate interpreter with the variable set, loads the application, and reports the status codes; it avoids reloading the module in-process.
- Validation quality baseline (Path B tools): `radon` finds no function above grade B in the model file; the plan changes no function's structure materially.
