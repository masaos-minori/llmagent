since `PLC0415` is confirmed inert and will remain unenforced), and a `RUF100` (`select`) decision

## Risks & Mitigations

- **Risk**: Stripping 101 `# noqa: PLC0415` comments by hand/script across 40 files could
  accidentally delete a co-located `# noqa: BLE001` on the same line if the transform is not
  precise.
  → **Mitigation**: Assumption 4 already confirms no line combines both codes (verified via `rg`);
  the transform only ever targets the `PLC0415`-specific substring, never a whole-line delete, so
  even in files carrying both codes on different lines (`repl_health.py`, `mcp_status.py`,
  `startup.py`) the `BLE001` lines are untouched by construction.

- **Risk**: This plan's `pyproject.toml`/`rules/coding.md` edits (RUF100 rationale) and the sibling
  plan's edits (BLE001 activation + PLC0415 exclusion rationale) touch the same file regions,
  risking a merge conflict or two contradictory inline comments if implemented independently and
  out of order.
  → **Mitigation**: Implementation Steps Phase 1 explicitly instructs sequencing this plan's edit
  in the same or immediately-following commit as the sibling plan's Phase 1, with a joint diff
  review before merge (see Phase 3 verification step).

- **Risk**: A future reviewer could decide to select `PLC0415` after all (overruling the sibling
  plan's decision), which would make this plan's Phase 2 comment-removal the wrong direction
  (path (b) would instead require re-adding accurate noqa comments for genuinely new findings).
  → **Mitigation**: UNK-01 already documents this as a low-probability, cheaply-reversible
  scenario (comment-only changes are pure `git revert` candidates); no additional mitigation
  needed beyond that documented reversibility.

- **Risk**: `RUF100`'s 167-finding blast radius spans rule codes beyond just `BLE001`/`PLC0415`
  (per sibling plan's own citation), so enabling it later — even after this plan's PLC0415 cleanup
  — will still surface unrelated findings that must be triaged separately.
  → **Mitigation**: this plan explicitly defers `RUF100` activation (not just PLC0415) and records
  the rationale; any future `RUF100` enablement is scoped as its own dedicated requirement, matching
  the same evidence-based-deferral pattern used for `PLC0415` in the sibling plan.

All risks above have mitigations stated directly in this plan; no `issues/*_risks.md` file is
filed (Step 6 skipped).
