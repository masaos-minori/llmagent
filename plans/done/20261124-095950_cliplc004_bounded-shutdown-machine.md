## Goal
- Make REPL shutdown one bounded, ordered sequence owned by a single coordinator: arm one global deadline when shutdown begins, stop accepting turns, commands, and SQLite writes, settle the writers that are already running, persist one immutable session snapshot, run the final WAL checkpoint and publish its backup atomically, then terminate MCP subprocesses and HTTP clients with only the time that is left, and report every step as `completed`, `timed_out`, `failed`, `not_started`, or `outcome_unknown` so unfinished work is never presented as success.

## Priority
High

## Scope
- **In-Scope**:
  - A shutdown budget and step-result model (`scripts/agent/shutdown_budget.py`): one monotonic deadline armed at the first shutdown request, `remaining()` clamping for every step, an acceptance state (`accepting`, `draining`, `closed`), and one `ShutdownStepRecord` per step.
  - A db-owned write gate (`scripts/db/write_gate.py`) enforced inside `SQLiteHelper`'s write path: new SQLite writes are refused once shutdown begins, in-flight write steps are interrupted through the existing progress-handler mechanism, and only the operations authorized by the shutdown sequence (snapshot persist, checkpoint, backup) are permitted inside it.
  - A turn, command, and transition acceptance gate at the single REPL dispatch point (`scripts/agent/repl_input_loop.py` `_dispatch_line`), so no new turn or command starts after the shutdown phase is set. Pending approval waits already resolve through `ReplInputController.shutdown()` (`scripts/agent/repl_input_controller.py:246-249`) and are covered by tests.
  - A fixed step order owned by `ResourceShutdownCoordinator.close_resources()`: settle writers, persist one snapshot, checkpoint, publish the backup, terminate MCP and HTTP clients, run close hooks off the event loop.
  - Atomic WAL backup publication: write a temporary file in the destination directory, flush and fsync it, verify the copied size, and publish with `os.replace`, naming the backup for the database it belongs to rather than for the session that was open.
  - Propagating the remaining deadline into MCP process termination (`shutdown_all()` and `terminate_with_timeout()` call sites), clamping the per-process confirm windows, and recording processes whose termination was not confirmed.
  - Second-SIGINT semantics: the second SIGINT interrupts the step that is running now and advances the sequence; the existing `force_exit_on_second_sigint` behavior stays opt-in configuration.
  - One shutdown summary: a short user-visible line per step plus the detailed step records in the warning stream and logs.
  - Configuration for the global deadline, the writer-settle window, and the force-exit opt-in, as `AgentConfig` fields surfaced in `config/agent.toml`.
  - Test and documentation work required by the changed shutdown surface, including regeneration of the reference-api documents and `registry/manifests/agent_api.yaml`.
- **Out-of-Scope**:
  - Job recording, maintenance job commands, and maintenance cancellation (`MaintenanceJobRegistry`): owned by the frozen Plan `20261124-001800_cliplc003_maintenance-job-framework`. This Plan adds no `/jobs` command and no `MaintenanceJobRegistry`.
  - Durable shutdown state for `agent restart`: `issues/done/20261021-093421_restart001_durable-agent-restart-state-required.md`.
  - The eventbus process and its SSE stream: `scripts/eventbus/db_conn.py` already holds its own bounded shutdown (`docs/10_adr/adr_02_04_006_eventbus-sqlite-persistence-and-sse-delivery.md:289`, INV-01) and is not part of the REPL shutdown sequence.
  - MCP transport hardening or reconnect policy.
  - Windows shutdown paths: `scripts/agent/signal_handler.py:116-205` behavior is unchanged and the Windows console-event path is not restructured.
  - Retention or cleanup policy for WAL backup files.

## Problem
- Shutdown is a sequence of independent timeouts rather than one bounded machine. A 30 s guard covers two of the seven steps; the persist step, MCP termination, HTTP client close, and close hooks are unbounded, so total shutdown time is the sum of worst cases instead of a deadline, and a slow checkpoint leaves no time for MCP termination.
- A step that is cut off does not report that it was cut off. `asyncio.wait_for` cancellation cannot interrupt the SQLite work running on a worker thread (`wal_checkpoint_manager.py:66`, `:134`), so the guard reports failure while the work continues, and the retry loop's sleeps (`:121`) can consume the whole window without progress.
- Work keeps arriving while shutdown is running: `_dispatch_line` accepts commands and turns regardless of shutdown state, `SignalHandler` never starts shutdown on SIGINT, and an unresolved approval or transition prompt keeps the input loop waiting because nothing calls `ReplInputController.shutdown()`.
- Writers are not settled before the final checkpoint, so the checkpoint can race a live writer, and the checkpoint's result is not attributable to a settled or unsettled store.
- Backup publication is not atomic: `shutil.copy2` (`:187`) leaves a partial file under the final, test-pinned, trustworthy-looking name.
- MCP termination runs with its own fixed windows while the shutdown deadline expires, and SIGINT is absorbed for the whole termination phase, so a user cannot interrupt a hung termination.

## Reason for Change
- Data loss and false success reports are the failure modes: a checkpoint that never finished, a truncated WAL copy, or an unterminated MCP process each currently surface as an ordinary session end.
- The bounded sequence is a prerequisite for the maintenance-job work in the frozen cliplc003 Plan: job cancellation and job states are only meaningful if the shutdown machine stops accepting work, settles writers, and records step outcomes.
- The shutdown machine is High priority because it is on every exit path (`scripts/agent/repl.py:157-171`) and because the existing guard is known to be unable to fire (`issues/done/20261021-093421_shutdown001-wal-checkpoint-timeout-guard-cannot-fire.md`).

## Implementation Intent
One budget object owns the shutdown clock: it is armed by the first shutdown request, publishes the phase that decides whether work is still accepted, and hands every step only the time that is left. One coordinator owns the order: settle the writers, persist one snapshot, checkpoint, publish the backup, terminate the lifecycles, run the close hooks, report. The db layer owns the write refusal, so a write cannot slip past the gate from any call site, and the REPL dispatch point owns turn and command refusal, so no new work is queued while the sequence runs. Each step reports one outcome from one vocabulary, and any outcome that is not `completed` is surfaced as incomplete work rather than as a session that ended cleanly.

## Requirements
- REQ-001: One shutdown owner and sequence. `ResourceShutdownCoordinator.close_resources()` runs the ordered steps `enter_shutdown` (arm the budget, set the acceptance phase, close the write gate), `settle_writers`, `persist_snapshot`, `checkpoint`, `backup`, `terminate_lifecycles`, `close_hooks`, `report`, each recorded in a `ShutdownReport`. `scripts/agent/repl.py` registers the snapshot-persist step instead of persisting in its own `finally`.
- REQ-002: One global deadline. `ShutdownBudget` (`scripts/agent/shutdown_budget.py`) is armed when shutdown is first requested (by SIGTERM, `ConsoleEvents.SHUTDOWN`, `exit`, `quit`, `bye`, or `/exit`) and is idempotent: the first request sets the deadline, later requests do not extend it. `remaining()` returns the time left and `0.0` after expiry, clamped to `>= 0`. The default total is `AgentConfig.shutdown_deadline_seconds` (default `45.0`), and the REPL graceful-turn window (`repl_input_loop.py:63 _GRACEFUL_TIMEOUT_S`) is drawn from the same budget so both share one deadline.
- REQ-003: Acceptance stops at the start of shutdown. `ShutdownBudget.phase` moves `accepting` -> `draining` -> `closed`. `_dispatch_line` (`scripts/agent/repl_input_loop.py:229-246`) refuses new commands and new turns once the phase is not `accepting`, reporting the refusal through `ViewController`; `CommandRouter.execute_command` and `AgentOrchestrator.handle_turn` are not reached. `ReplInputController.shutdown()` is called during `enter_shutdown` so a pending approval or transition wait resolves with `InputOutcome.SHUTDOWN`.
- REQ-004: SQLite writes are gated by the db layer. `scripts/db/write_gate.py` provides `WriteGate` (states `open`, `closing`, `closed`) and `WriteGateClosed`. `SQLiteHelper` consults the gate on every write path: `open(write_mode=True)` (`scripts/db/helper.py:350-409`), `execute` (`:508`), `executescript` (`:517`), `executemany` (`:522`), `commit` (`:540`), `begin_immediate` (`:458`), `begin_exclusive` (`:464`), `checkpoint` (`:486`), `vacuum` (`:502`). Read-only paths are never gated. The gate classifies an operation as shutdown-authorized only inside an explicit context manager (`gate.authorize(operation_name)`); every other write during `closing` or `closed` raises `WriteGateClosed` and increments a refused-write counter.
- REQ-005: In-flight writers are interrupted, not awaited without bound. `settle_writers` interrupts each tracked SQLite connection through `SQLiteHelper.interrupt_when` (`scripts/db/helper.py:158-184`) with the deadline the budget leaves, cancels and joins the tracked tasks (existing `_cancel_tracked_tasks`, `resource_shutdown_coordinator.py:173-196`), and waits at most `AgentConfig.shutdown_settle_seconds` (default `10.0`). A writer that is still running when the settle window ends is recorded as `outcome_unknown` with its task name.
- REQ-006: The final checkpoint only runs after settling. If any writer is still running when `settle_writers` ends, the checkpoint step is not started and is recorded `not_started` (owner decision OD-02); the backup step then follows the existing "checkpoint did not truncate" branch.
- REQ-007: One immutable snapshot is persisted once. `SessionPersister.capture_snapshot()` (`scripts/agent/session_persister.py:118-138`) is called exactly once in `persist_snapshot`, and `persist_session_memories()` and `persist_session_diagnostics()` receive that snapshot (`session_persister.py:211-214` already accepts one) instead of each generating its own. The step is authorized on the write gate, is bounded by `remaining()`, and its outcome is recorded.
- REQ-008: The checkpoint and backup are bounded by the remaining deadline and are interruptible. `WalCheckpointManager.checkpoint_sync()` and `backup_sync()` take the remaining budget, pass it to the TRUNCATE retry loop so its sleeps cannot exceed it (`wal_checkpoint_manager.py:96-127`), and register an interrupt via `interrupt_when` so the worker thread's SQLite work actually stops. The coordinator waits for the offloaded worker to finish (or to report that it stopped) before advancing to the next step; an abandoned worker is recorded, never assumed finished. Outcomes: `completed`, `timed_out`, `failed`, or `outcome_unknown`.
- REQ-013: Step reporting is safe to print. `ShutdownStepRecord.detail` carries a reason category and a bounded, path-free summary for the console; absolute paths, connection strings, and raw exception text stay in the logger, which already carries the redaction filter (`scripts/shared/logger.py:64` `attach_redaction_filter`, `register_secret`). Stderr diagnostics of MCP servers are not redacted here (that is cliplc009's scope).
- REQ-009: Backup publication is atomic and the artifact is named for the database it belongs to. `backup_sync()` writes to a temporary file in the destination directory (`<final>.partial`), flushes and `os.fsync`s it, verifies the copied size against the source, publishes with `os.replace`, and deletes the temporary on any failure while recording `failed`. The final name drops the session identifier: the WAL sidecar belongs to `session.sqlite`, not to one REPL session, so the name becomes `{db_basename}-wal-backup-{timestamp}-{token}` where `{token}` is a per-process uniqueness token (`scripts/agent/wal_checkpoint_manager.py:177-186` currently embeds `session_tag`). The existing allowed-root and symlink checks (`:147-160`) are unchanged, and no other code or document consumes the name today (`rg -n "db-wal-backup"` matches only test strings).
- REQ-010: The remaining deadline reaches MCP termination. `shutdown_all()` and its protocol/router surface accept an optional remaining-deadline argument; each per-process call uses `min(remaining(), _DEFAULT_KILL_CONFIRM_TIMEOUT_SEC)` for the confirm window and clamps `terminate_with_timeout(timeout=...)` so SIGTERM and SIGKILL are always sent even when the remaining time is small. A process whose exit was not confirmed keeps the existing `TerminationOutcome.EXIT_UNCONFIRMED` state (`scripts/agent/http_lifecycle_errors.py`) and is reported as `timed_out` / `outcome_unknown`, never as terminated.
- REQ-011: The second SIGINT interrupts the running step. During shutdown the second SIGINT requests interruption of the step that is currently running (through the same interrupt and cancellation mechanism as `settle_writers`) and lets the sequence advance to the next step. `os._exit` is used only when `AgentConfig.shutdown_force_exit_on_second_sigint` is `true` (default `false`). SIGINT keeps not starting shutdown, so an accidental Ctrl-C still does not end a session.
- REQ-012: Shutdown reports every step. `ShutdownReport` holds one `ShutdownStepRecord` per step (`name`, `outcome`, `elapsed_s`, `detail`), the refused-write count, and the unsettled-writer list. The user sees one line per step plus a summary line; the detail text goes through `ViewController.write_warning` and `logger.warning` as it does today (`resource_shutdown_coordinator.py:168-171`). `docs/23_agent/agent_10_01_operations-and-observability-startup-and-health.md` and `docs/01_overview/overview_01_03-arch-features.md` describe the machine instead of the current three-step wording.

## Acceptance Criteria
- `AC-1` (REQ-001, REQ-002): shutdown returns within the configured global deadline and MCP termination cannot extend it; the measured wall time of `close_resources()` never exceeds `AgentConfig.shutdown_deadline_seconds` plus the step-quantization slack, and `shutdown_all()` receives only `budget.remaining()`. - `AC-2` (REQ-003, REQ-004, REQ-005): after shutdown begins, no new turn, command, transition, approval prompt, or SQLite write is accepted; a pending approval wait resolves with `InputOutcome.SHUTDOWN`; every refused write increments the gate counter, and each unsettled writer is recorded `outcome_unknown`. Verified by `tests/agent/test_repl_shutdown_machine.py`, `tests/db/test_write_gate.py`, `tests/db/test_sqlite_helper.py`, `tests/agent/test_resource_shutdown_coordinator.py`.
- `AC-3` (REQ-006, REQ-007, REQ-008, REQ-009): no writer runs after the final checkpoint starts (otherwise the checkpoint is recorded `not_started` and the backup step still runs), one snapshot is persisted once, and an interrupted backup never leaves a file under the final name: only the temporary exists, and it is deleted. Verified by `tests/agent/test_resource_shutdown_coordinator.py`, `tests/agent/test_repl.py`, `tests/agent/test_wal_checkpoint_manager.py`, `tests/agent/test_wal_backup_security.py`, `tests/agent/test_session_persister.py`.
- `AC-4` (REQ-010, REQ-011, REQ-012, REQ-013): a termination task that times out or is cancelled keeps its process tracked and reports `EXIT_UNCONFIRMED` / `timed_out` rather than success; the console shows one bounded line per step plus a summary that distinguishes incomplete work from success; a second SIGINT interrupts the running step and advances the sequence instead of calling `os._exit` unless configured. ## Design
- **One budget, many consumers.** `ShutdownBudget` is created when the REPL wires its components (`scripts/agent/repl.py:85-92`) and armed by the first shutdown request. The same object reaches `SignalHandler` (arming and second-SIGINT routing), `ReplInputLoop` (acceptance phase and the graceful-turn window that today is `_GRACEFUL_TIMEOUT_S` at `scripts/agent/repl_input_loop.py:63`), `ResourceShutdownCoordinator` (per-step `remaining()`), and through it the lifecycle surface. Arming is idempotent: `arm()` records the first request and returns `False` for later ones, which is what makes the first signal win and keeps `remaining()` from being extended by a user pressing Ctrl-C repeatedly.
- **Acceptance is a phase, not a flag.** `ShutdownPhase` has `accepting`, `draining`, `closed`. `_dispatch_line` (`scripts/agent/repl_input_loop.py:229-246`) is the single point through which every command and turn passes, so one check there covers commands, turns, and transitions without touching `CommandRouter` or `AgentOrchestrator`. Entering `draining` also calls `ReplInputController.shutdown()` (`scripts/agent/repl_input_controller.py:246-249`), which resolves a pending approval or transition read with `InputOutcome.SHUTDOWN` through the existing `_stop_active()` cancellation (`:251-257`) instead of adding a new unblocking mechanism. `closed` is set when the sequence finishes, so a late dispatch is refused rather than queued.
- **The write gate is db-owned.** `WriteGate` lives in `scripts/db/write_gate.py` and is consulted by `SQLiteHelper`'s write methods (`scripts/db/helper.py:350-409`, `:458-466`, `:486-506`, `:508-543`), because the Issue's rule is a database rule and `.importlinter` forbids `db` importing `agent`. The agent layer hands the gate to the db layer (the helper gains a gate attribute assigned by the shutdown wiring), never the reverse. States: `open` (normal), `closing` (only shutdown-authorized operations, set when the sequence starts), `closed` (no write at all). Authorization is explicit and scoped: `with gate.authorize("wal_checkpoint"):` sets one authorized operation name for the current context, which is how the checkpoint, backup, and snapshot-persist steps pass while everything else is refused. Refusals raise `WriteGateClosed` and increment a counter that the shutdown report prints, following the precedent already in the repository at `scripts/eventbus/db_conn.py:34-81` (`set_shutdown_flag`, `is_shutting_down`, refused-user counter) and the bounded-close invariant `docs/10_adr/adr_02_04_006_eventbus-sqlite-persistence-and-sse-delivery.md:289`.
- **One sequence, one vocabulary.** `close_resources()` becomes a loop over named steps, each executed through a helper that measures elapsed time, calls `budget.remaining()` for the step bound, and stores a `ShutdownStepRecord`. Step outcomes are `completed`, `timed_out`, `failed`, `not_started`, `outcome_unknown`; the MCP step maps the existing `TerminationOutcome` values (`EXITED`, `ALREADY_EXITED`, `SIGNAL_NOT_DELIVERED`, `EXIT_UNCONFIRMED`, `scripts/agent/http_lifecycle_errors.py`) into them rather than inventing a second vocabulary. `not_started` exists so a step blocked by an unsettled writer is visible as a decision, not as a silent skip.
- **Settling before the checkpoint (OD-01, OD-02).** `settle_writers` interrupts tracked connections through `interrupt_when` (`scripts/db/helper.py:158-184`), cancels and joins the tracked tasks with the existing `_cancel_tracked_tasks` (`scripts/agent/resource_shutdown_coordinator.py:173-196`), and stops when the settle window expires. Only if every writer reached a terminal state does `checkpoint` start; otherwise it is recorded `not_started`. The backup then follows today's branch for a checkpoint that did not truncate (`:103-122`), so the ordering `checkpoint before backup` from `docs/10_adr/adr_02_05_008_db-six-sqlite-store-separation.md:98` is untouched.
- **Bounded, interruptible checkpoint and atomic publish.** `checkpoint_sync()` and `backup_sync()` already run on worker threads (`scripts/agent/wal_checkpoint_manager.py:66`, `:134`); `asyncio.wait_for` cancels the await, not the thread, which is the archived defect (`issues/done/20261021-093421_shutdown001-wal-checkpoint-timeout-guard-cannot-fire.md`). The step therefore registers an interrupt on the connection and bounds the retry loop's sleeps (`:96-127`, `time.sleep(2 ** attempt)` at `:121`) by the remaining budget, then waits for the worker to report. Backup publication writes `{db}-{…}.partial` in the same directory, flushes, fsyncs, compares the size against the source, `os.replace`s into the final name, and unlinks the temporary on any failure. The final name drops the session tag (`:177-186`) and adds a per-process token so the artifact is named for the database while staying unique across concurrent writers.
- **Termination with the time that is left (OD-05).** `shutdown_all()` gains one optional remaining-deadline argument on all five definitions (`scripts/agent/http_lifecycle_shutdown_coordinator.py:100`, `scripts/agent/http_lifecycle.py:413-420`, `scripts/agent/lifecycle_router.py:79-81`, `:257-260`, `scripts/agent/lifecycle_protocol.py:36`); existing call sites without a budget keep today's behavior, which is why `scripts/agent/http_lifecycle_health_checker.py:76,166,210,226` and `tests/integration/test_mcp_transport_crash.py:210-225` keep working. Inside the coordinator, each server's confirm wait becomes `min(remaining(), _DEFAULT_KILL_CONFIRM_TIMEOUT_SEC)` and `_absorb_sigint_during_shutdown` (`scripts/agent/http_lifecycle_shutdown_coordinator.py:44-48`, `:129`, `:135`, `:171-176`) is replaced by routing the signal to the budget's interrupt channel, so SIGTERM and SIGKILL are always delivered and only the waiting is clamped. Servers whose exit is not confirmed stay tracked and are reported, which is the Issue's "remain tracked" requirement. The INV-07 order (HTTP client closed before subprocess termination, `docs/10_adr/adr_02_03_007_mcp-http-adoption-and-stdio-non-support.md:259`) is preserved by keeping `svc.http.aclose()` in the same step as today (`scripts/agent/resource_shutdown_coordinator.py:133-135`).
- **Second SIGINT as a step interrupt (OD-04).** Today the second SIGINT can only reach `os._exit(130)` (`scripts/agent/signal_handler.py:53-55`) and only when `force_exit_on_second_sigint` is true (`:74`), and during MCP shutdown the handler is replaced so even that is unreachable. The new behavior: the second SIGINT marks the running step interrupted (same interrupt and cancellation channels as `settle_writers`), the step records `timed_out` or `outcome_unknown`, and the sequence advances. `os._exit` remains available through `shutdown_force_exit_on_second_sigint`, default `false`. SIGINT keeps not starting shutdown (`:105-114`), so an accidental Ctrl-C still does not end a session.
- **Reporting.** `ShutdownReport` renders one short line per step plus a summary; detail text is a reason category plus a bounded, path-free note (REQ-013), while paths and exception text stay in the logger that already carries `attach_redaction_filter` (`scripts/shared/logger.py:64`). This replaces today's `write_warning` dump of collected error strings (`scripts/agent/resource_shutdown_coordinator.py:168-171`) and makes "timed out" and "completed" distinguishable on the console, which is the Issue's fourth acceptance criterion.

## Risks
- **Risk**: The write gate refuses a write that a legitimate shutdown step needs (snapshot persist, checkpoint, backup), so shutdown loses session data or leaves the WAL uncheckpointed → **Mitigation**: authorization is explicit and scoped per operation (REQ-004), the three shutdown steps are the only authorized names, and `tests/db/test_write_gate.py` asserts both the refusal and the authorized pass before the gate is wired into `SQLiteHelper`.
- **Risk**: `interrupt_when` fires only at SQLite progress callbacks, so a single long `PRAGMA wal_checkpoint(TRUNCATE)` or `VACUUM` may not stop, making the settle step look broken → **Mitigation**: UNK-01 measures this in the Phase 2 and Phase 5 tests; the OD-02 rule guarantees the unsafe case (checkpoint started while a writer runs) never happens, and the unfinished work is reported `outcome_unknown` instead of success.
- **Risk**: Replacing `tests/agent/test_repl.py:1331-1372` removes the guard that `REQ-RSC001B-1` added against the LIFO-order defect, so a regression could reintroduce a worse order → **Mitigation**: the replacement test asserts a stronger property (a named step order plus the `not_started` rule), lands in the same commit as the coordinator change, and the superseded provenance is recorded in `Issue Verification` so the reasoning is recoverable.
- **Risk**: Removing the session id from the backup name breaks a naming assumption an operator or a runbook relies on → **Mitigation**: `rg -n "db-wal-backup"` and `rg -n "wal-backup"` show no code, retention, or deployment consumer; the uniqueness property the old tests asserted is preserved by the per-process token, and `docs/23_agent/agent_10_01_operations-and-observability-startup-and-health.md` is updated in the same phase.
- **Risk**: Adding a parameter to five `shutdown_all()` definitions touches `tests/agent/test_lifecycle.py` (15 references), `tests/agent/test_startup_rollback.py` (25 references), and `tests/agent/test_http_lifecycle_integration.py` (36 references) at once → **Mitigation**: the parameter is optional with today's behavior as the default, the existing `MagicMock` stubs in `tests/agent/test_startup_rollback.py` keep working, and Phase 6 changes the whole surface in one commit.
- **Risk**: A second SIGINT that interrupts a checkpoint could leave the WAL in a state the next open must replay, and the user could read the interruption as a clean exit → **Mitigation**: today's documented rule already states that a timed-out checkpoint is "not rolled back", never "left clean" (`docs/23_agent/agent_10_01_operations-and-observability-startup-and-health.md:162`); the step record states `timed_out` or `outcome_unknown` explicitly, and `force_exit_on_second_sigint` stays the only path that skips the remaining steps.
- **Risk**: `config/agent.toml` (20 commits in 30d) and `scripts/agent/config_dataclasses.py` (14 commits in 30d) are the highest-churn files in the target set, and `scripts/agent/repl.py` plus the generated artifacts are also targets of the frozen cliplc003 Plan → **Mitigation**: land cliplc003 before this Plan's Phases 1, 4, and 7 touch those files; `tools/check_plan_target_overlaps.py` is a gate row, and this Plan's edits to `repl.py` are limited to the `finally` block and the component wiring.
- **Risk**: The gate is process-wide while `SQLiteHelper` is used from worker threads (the checkpoint and backup run on threads; `tests/db/test_helper_thread_safety.py` exercises that), so an authorization scope bound to the wrong thread could refuse a legitimate step → **Mitigation**: the authorization context is documented and tested against a worker thread in Phase 2 (`tests/db/test_helper_thread_safety.py` row), and the authorized operation name is matched by the operation, not by the caller's identity.
- **Risk**: A bounded MCP termination window could make slow-to-exit servers look hung more often than today → **Mitigation**: the deadline default (45 s) is larger than today's 30 s checkpoint-and-backup window and the termination step runs after the bounded steps, so the time available to termination is the configured remainder; the per-server outcomes are reported so an operator can see which server was slow.
