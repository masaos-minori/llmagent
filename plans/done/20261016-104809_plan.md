## Goal
- Confining HTTP-subprocess command validation to a trusted binary directory removes the PATH-injection surface of a basename-only allowlist. Add a strict mode that allows a command only when its resolved real path is a regular file directly inside a trusted directory (the basename allowlist alone is no longer sufficient), while preserving the current permissive behavior behind an explicit opt-in flag.

## Priority
Medium

## Scope
- **In-Scope**:

  - Gate strict mode behind an explicit opt-in flag sourced from an environment variable read in `CommandValidator.__init__`. Default is permissive (current behavior preserved).

## Background
`scripts/agent/http_lifecycle_command_validator.py::CommandValidator.validate` performs: (1) `shutil.which(cmd_name)` PATH lookup, (2) `os.path.realpath` symlink resolution, (3) regular-file check, and (4) allow if `base_name in self._allowed_commands`, or the basename matches the `python3[.N]` interpreter pattern, or the resolved path passes `_inside_allowed_binary_dir` (regular file directly inside `/opt/llm/bin` or `LLMAGENT_BINARY_DIR`, directory not group/world-writable). The directory branch is behind an `or`, so it can only ADD an allowed path; it cannot reject a basename-allowlisted binary located elsewhere. The launcher (`scripts/agent/http_lifecycle.py::_create_and_validate_proc`) then runs whatever `validate` approves. In the deployed configuration every MCP server `cmd` is `/opt/llm/bin/mcp_<name>` (`config/agent.toml`, `docs/90_deployment/deployment_01_deployment.md`); those basenames are not on the allowlist and pass only through the directory branch.

## Problem
A basename-only allowlist silently degrades to "run whatever is first on `PATH` with an allowed name." Because `filter_env` inherits the parent agent's `PATH` (only blocking `PATH`/`PYTHONPATH`/`LD_LIBRARY_PATH`/`HOME`/`USER` overrides), any directory writable by an attacker that appears in `PATH` becomes an injection point for a malicious `node`/`python3`/`npx`. Confining to a trusted directory hardens the control without changing the allowlist contents.

Adversarial verification on 2026-10-16 (step 3a of the next phase) corrected three points of the original analysis: (1) Strict mode defined as "basename allowlist AND inside the trusted directory" would reject every deployed server, because the `/opt/llm/bin/mcp_*` basenames are not on the allowlist; strict mode therefore allows a command only through the directory check. (2) The "production inspection" that found `node`, `python3`, `uvx`, `npx`, `npm`, and `uv` under `/usr/bin` and `/opt/llm/bin` empty describes the development host (`/opt/llm/bin` does not exist here), not the deployed layout in `deployment_01`. (3) `validate` resolves symlinks before the check, so a symlink placed in the trusted directory that points to `/usr/bin/node` resolves outside it and is rejected (existing test `test_reject_symlink_in_allowed_dir_pointing_elsewhere`); the trusted directory must hold real files, not symlinks.

## Reason for change
The basename allowlist is a soft control. Making directory confinement mandatory (or opt-in) closes the PATH-injection surface. Production inspection (below) determines whether the stricter mode can be the default or must remain opt-in.

## Implementation intent
Add a strict mode to `CommandValidator` that, after realpath resolution, allows a command only when the existing `_inside_allowed_binary_dir` check passes (the basename allowlist branch no longer suffices). Gate strict mode behind an opt-in environment variable read in `__init__`, defaulting to permissive so current deployments are unaffected. Reuse the existing `LLMAGENT_BINARY_DIR` override as the trusted-directory source. Do not touch the launch path, env filtering, or health polling.

Two wiring designs are possible (see Unknowns UNK-01):
- **Design A (recommended): environment-variable driven.** Read an opt-in flag from an environment variable inside `CommandValidator.__init__`. Touches only the validator + tests. Honors the issue's "do not touch launch/env/health" constraint. Process-global scope.
- **Design B (follow-up): config-field driven.** Add a `strict_command_confinement` field to `McpServerConfig`, populate it in `_build_single_server`, and pass it to `CommandValidator` at the construction site in `http_lifecycle.py`. Per-server scope, but requires modifying the launch-path construction site (`http_lifecycle.py:82`), which conflicts with the "do not touch launch" constraint. Requires explicit approval to relax that constraint.

## Design
- **Strict/permissive gating (Design A).** `CommandValidator.__init__` reads the opt-in flag from `LLMAGENT_STRICT_COMMAND`. A private attribute (e.g., `self._strict_confinement`) stores the resolved boolean. Default `False`.
- **Strict-mode path.** In `validate`, when `self._strict_confinement` is true, after `os.path.realpath` resolution the resolved real path MUST be inside the trusted directory (`_allowed_binary_dir()` → `LLMAGENT_BINARY_DIR` if set, else `/opt/llm/bin`). If not, raise a descriptive `StartupFailure` (reason: command resolved outside the trusted binary directory). In strict mode the basename allowlist does not apply; the existing `_inside_allowed_binary_dir` is the only gate, so non-allowlisted `mcp_*` binaries in the trusted directory still work.
- **Permissive path.** When strict is disabled, behavior is unchanged: allow if the basename is allowlisted, matches the `python3[.N]` pattern, or the realpath passes `_inside_allowed_binary_dir` (current `or` semantics).
- **Symlink handling.** The check uses the already-resolved realpath, so a symlink inside the trusted directory pointing outside it is rejected in strict mode (`REQ-003`, `AC-003`).
- **Backward compatibility.** Default permissive means no breaking change and no config migration for current deployments. Strict-default would require a prerequisite deployment step (populate `/opt/llm/bin` or set `LLMAGENT_BINARY_DIR` globally); see Risk.
- **Import-linter.** Adding logic to `command_validator.py` does not introduce new imports; the 6 existing contracts stay KEPT. No new module/package.
