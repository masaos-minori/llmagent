# Work Plan: Separate session-not-found vs no-messages error paths in restore_session

## Goal
Distinguish between "session does not exist" and "session exists but has no messages" in `restore_session()`, enabling precise error reporting and differentiated caller handling.

## Scope
- Modify `fetch_messages()` in `scripts/agent/session_message_repo.py` to return `(messages, session_found)` tuple
- Update `fetch_messages()` wrapper in `scripts/agent/session.py` to propagate the new return type
- Update `restore_session()` in `scripts/agent/services/session_restore.py` to use distinct error messages
- Add `SessionNoMessagesError` exception class in `scripts/agent/services/exceptions.py`
- Update all call sites of `fetch_messages()` in production code
- Update tests to handle the new return type

## Assumptions
1. A `sessions` table exists with `session_id` column (confirmed in `scripts/agent/session.py:122`)

3. Callers currently expect `fetch_messages()` to raise `SessionNotFoundError` — they need updating to catch both exception types

## Design
The key insight is that the `sessions` table exists separately from the `messages` table. Currently `fetch_messages()` only queries `messages`, so an empty result set is ambiguous. By first checking whether the session exists in the `sessions` table, we can distinguish the two cases:

```python
def fetch_messages(self, session_id: int) -> tuple[list[LLMMessage], bool]:
    """Fetch messages for a session. Returns (messages, session_found)."""
    with SQLiteHelper("session").open(row_factory=True) as db:
        row = db.fetchone(
            "SELECT 1 FROM sessions WHERE session_id = ?",
            (session_id,),
        )
        session_found = row is not None
    if not session_found:
        return ([], False)
    rows = db.fetchall(...)  # existing logic unchanged
    ...
    return (messages, True)
```

In `restore_session()`:
```python
messages, session_found = ctx.session.fetch_messages(session_id)
if not session_found:
    raise SessionNotFoundError(f"Session {session_id} not found.")
if not messages:
    raise SessionNoMessagesError(f"Session {session_id} has no messages.")
```

## Risks
1. **Performance**: Adding a `sessions` table lookup adds one extra query per `fetch_messages()` call. If this becomes a hotspot, consider caching or batching.
2. **Breaking change**: All callers must be updated to handle the new tuple return type. Missing a call site will cause silent failures or incorrect behavior.
3. **Exception hierarchy**: If `SessionNoMessagesError` should be catchable alongside `SessionNotFoundError`, inheritance choice matters. If callers want to handle both cases uniformly, making `SessionNoMessagesError` a subclass of `SessionNotFoundError` would allow `except SessionNotFoundError` to catch both.
4. **Test coverage gaps**: Many tests mock `fetch_messages()` or call it directly. Each needs verification against the new contract.
