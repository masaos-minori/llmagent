# Work Plan: Document and Optionally Synchronize ConversationState.history Access

## Goal

Make the asyncio single-threaded assumption explicit for ConversationState.history access, and optionally introduce lightweight synchronization to align with the existing pattern used by TurnState.tool_calls.

## Scope

- scripts/agent/context.py — ConversationState class only
- Add optional class-level asyncio.Lock to ConversationState
- Update docstrings to document the asyncio single-threaded assumption
- Ensure append_message(), extend_messages(), replace_history() use the lock consistently

## Assumptions

1. asyncio is single-threaded; coroutines do not interleave except at await points
2. All history mutations within a single turn execute sequentially without yielding
3. Background tasks spawned during a turn may access history after await points, creating potential interleaving windows
4. The existing TurnState._lock pattern is the preferred approach for similar mutable state
5. Adding a Lock will not change runtime behavior under normal operation, only make the assumption explicit

## Unknowns

1. Are there any code paths where history is accessed concurrently from background tasks vs. the main event loop? Need to verify.
2. Does adding a Lock affect performance in hot paths (e.g., append_message called frequently)?
3. Should the Lock be created eagerly or lazily (like jsonl_store.py's lazy lock creation)?
4. Can the Lock be shared between append_message and replace_history, or should they use separate locks?

## Affected areas

- scripts/agent/context.py — ConversationState class
- Any tests that mock ConversationState.history access
- Diagnostic output that references history synchronization status

## Design

### Option A (preferred): Add class-level asyncio.Lock to ConversationState

Add a class-level `_history_lock: asyncio.Lock | None` field to ConversationState, initialized lazily after the event loop starts (following the pattern in jsonl_store.py). Provide three public methods:

```python
@dataclass
class ConversationState:
    _history_lock: asyncio.Lock | None = None
    
    @property
    def _ensure_lock(self) -> asyncio.Lock:
        if self._history_lock is None:
            self._history_lock = asyncio.Lock()
        return self._history_lock
    
    async def append_message(self, msg: LLMMessage, *, source: str = "") -> None:
        async with self._ensure_lock:
            # existing logic...
    
    async def extend_messages(self, msgs: list[LLMMessage], *, source: str = "") -> None:
        async with self._ensure_lock:
            # existing logic...
    
    async def replace_history(self, msgs: list[LLMMessage], *, source: str = "") -> None:
        async with self._ensure_lock:
            # existing logic...
```

Change the existing synchronous methods to async, consistent with TurnState's pattern.

### Option B (minimal): Document the assumption only

Add a class-level docstring to ConversationState explaining that:
- asyncio's single-threaded model means no concurrent access within a turn
- The absence of locking is intentional and relies on this invariant
- If concurrent access ever becomes possible (e.g., multi-loop), locking must be added

## Risks

1. **Breaking change**: Converting synchronous methods to async changes the public API. Callers must update to use `await`.
2. **Deadlock risk**: If a caller already holds the Lock and calls another method that tries to acquire it, deadlock occurs. Need to verify no nested call chains exist.
3. **Performance impact**: Lock acquisition adds overhead in hot paths. Profile before and after.
4. **Test double compatibility**: Existing mocks/stubs of ConversationState may not implement the new async methods or Lock.
5. **Lazy lock initialization**: If the event loop hasn't started when `_ensure_lock` is called, asyncio.Lock() creation may fail.
