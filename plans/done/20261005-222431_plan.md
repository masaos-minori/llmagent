Resolve the inconsistency between `config/shell_mcp_server.toml`, its comment, the `ShellConfig` default value, the agent startup security audit, and the MCP documentation regarding the `shell_sandbox_backend` `none` value, by adopting and propagating a single explicit policy (`none` is never permitted) across config, code default, tests, and documentation.

## Background
The checked-in `config/shell_mcp_server.toml` sets `shell_sandbox_backend = "none"` with a comment stating this yields a WARNING at startup. The agent startup security audit (`audit_security_defaults`) instead raises `RuntimeError` for `none` regardless of environment, which the startup pipeline records as a FATAL outcome. The shell server itself performs no `none` enforcement (only `firejail` is validated), and the two primary MCP documents disagree: `mcp_04_02` lists `none` as "Local development only" while `mcp_05_02` states `none` is "Not permitted in any environment". Both documents carry a pointer to issue `issues/20261005-102246_mcp001_shell-sandbox-none-config-contradicts-startup-audit.md`.

## Problem
- With the checked-in config the agent startup fails at the security audit (FATAL), contradicting the config comment (WARNING only) and the documented "Development" use case.
- The code default for the key is also `none`, so an omitted key hits the same fatal check — the default configuration is not startable.
- Multiple MCP documents state the `none` policy inconsistently (`mcp_04_02`: "Local development only"; `mcp_05_02`: "Not permitted in any environment"; `mcp_05_03`: "RuntimeError in production if none", implying non-production is allowed).
- Whether the checked-in `none` is an expected-to-fail development placeholder or the audit is meant to allow `none` outside production is not decided.

## Reason for change
Config value, comment, code default, audit policy, and documentation are mutually inconsistent. Operators following the config comment receive a fatal startup failure, and the documented policy is ambiguous across three MCP documents.

## Implementation intent
Adopt Option A: `none` is never permitted in any environment (the current audit behavior and the `mcp_05_02`/`mcp_06_16` policy). Change the checked-in config to `firejail`, fix the comment, make the model default consistent, keep the audit's raise-for-`none` intact, align the documents to a single policy, and add tests asserting the checked-in config against the audit. Do not weaken the audit; any relaxation would be an explicit, separate decision (Option B).

## Design
**Policy decision (Option A).** The audit raises `RuntimeError` for `none` regardless of environment, and `mcp_05_02`, `mcp_06_16` already state `none` is never permitted. Option A keeps this policy and removes the contradictory `none` value from the checked-in config and the code default. Option B (allow `none` in development) would add an environment branch to the security audit — a security-check relaxation that must not be done silently and would further increase the audit's already-high cyclomatic complexity (radon E/38); it is recorded here only as an alternative, not adopted.

**Why the config, not the audit, changes.** Under Option A the audit's raise-for-`none` is correct and stays. The fix therefore targets the inputs the audit consumes: the checked-in config value/comment (`config/shell_mcp_server.toml`) and the model default (`shell_models.py`). The audit load path (`security_audit_config.load_shell_audit_config`) surfaces `ShellConfig.shell_sandbox_backend` unchanged, so the new default flows through to the audit automatically.

**Firejail interaction.** `init_sandbox` validates only `firejail` and is a no-op for `none`; `build_argv` wraps commands in firejail only for `firejail`. Setting the config to `firejail` means startup additionally requires the firejail binary (`init_sandbox` raises if absent). This is by design (fail-fast when requested isolation cannot be provided) and is captured as UNK-01 plus the deployment step.

**Boundary safety.** `shell_models` imports only leaf modules (`shared.config_loader`, `shared.protocols.shell`); changing a default value does not cross any import-linter boundary, and `security_audit.py` is unmodified, so no architecture contract changes.
