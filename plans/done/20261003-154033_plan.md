# Plan: Fix TransportDTO from_transport() error_type default value

## Goal
Fix the `error_type` default value in `ToolCallResult.from_transport()` to correctly reflect transport-level errors instead of tool-level errors.

## Priority
Medium

## Scope
- **In-Scope**: Fixing the `error_type` default value in `ToolCallResult.from_transport()`; updating related documentation if needed.
- **Out-of-Scope**: Changing the retry logic itself; modifying other transport layers; changing error handling behavior.

## Background
`scripts/shared/transport_dto.py` line 18-30:
```python
@classmethod
def from_transport(
    cls, output: str, is_error: bool, request_id: str = ""
) -> "ToolCallResult":
    """Construct a ToolCallResult with default server_key and error_type."""
    return cls(
        output=output,
        is_error=is_error,
        request_id=request_id,
        server_key="",
        source="mcp",
        error_type="tool" if is_error else "",
    )
```

The issue claims:
1. `server_key=""` is set by default, which could be incorrect if called directly
2. `error_type="tool"` is set by default, but should be `"transport"` for transport-level errors

However, looking at the usage in `http_transport.py`:
```python
parsed = self._parse_http_response(resp)
return dataclasses.replace(parsed, server_key=self._server_key)
```

The `server_key` is overwritten after calling `from_transport`, so the default value doesn't matter in practice. The `error_type` is also not overwritten, so it remains as `"tool"` even for transport-level errors.

The issue's claim about `error_type` being incorrect is valid. If the error is a transport-level error, the `error_type` should be `"transport"`, not `"tool"`.

## Problem
When `from_transport()` is used for transport-level errors, the `error_type` field incorrectly indicates `"tool"` instead of `"transport"`. This can lead to confusion during debugging and incident investigation.

## Reason for change
Accuracy improvement. Ensuring the `error_type` field correctly reflects the type of error helps developers identify the root cause of failures more quickly.

## Implementation intent
Either:
1. Change the default `error_type` value from `"tool"` to `"transport"` in `from_transport()`
2. Add a parameter to allow callers to specify the `error_type` explicitly

Approach 1 is preferred as it's simpler and more maintainable.
