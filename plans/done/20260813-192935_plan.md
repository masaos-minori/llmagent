# Plan: Fix `ToolTransportInvoker.__init__` to honor `call_timeout_sec=0` as "no timeout"

## Goal
Make `ToolTransportInvoker.__init__` (`scripts/shared/tool_transport_invoker.py:54-58`) pass
`McpServerConfig.call_timeout_sec` straight through to `HttpTransport` unchanged, so that
`call_timeout_sec=0` ("no timeout", per the field's own documented contract) is honored instead of
being silently overridden to `60.0` by a truthy check that treats `0` as "unset." Remove the
now-provably-dead `hasattr(cfg, "call_timeout_sec")` guard in the same change.

## Scope

### In-Scope
- `scripts/shared/tool_transport_invoker.py` — `ToolTransportInvoker.__init__`, the `timeout_sec`
  resolution expression only (lines 54-58).
- `tests/shared/test_tool_transport_invoker.py` — new test coverage for `call_timeout_sec=0`,
  a positive value, and the default-unset case; extend the `_http_cfg` test helper to accept
  `call_timeout_sec`.
- Running (not modifying) `tests/shared/test_mcp_config_validation.py` and
  `tests/shared/test_mcp_config.py` to confirm no regression in `McpServerConfig` itself.

### Out-of-Scope
- `scripts/shared/http_transport.py` — its `self._timeout > 0` handling is already correct and is
  not touched.
- `scripts/shared/mcp_config.py` — `McpServerConfig`'s dataclass default and `__post_init__`
  validation (`>= 0`) are already correct and are not touched.
- `scripts/shared/tool_executor.py` (`ToolExecutor`, which subclasses `ToolTransportInvoker`) — it
  calls `super().__init__(http, server_configs, concurrency_limits, lifecycle)` unchanged
  (`scripts/shared/tool_executor.py:61`) and needs no code change; it inherits the fix for free.
- Any `docs/*.md` file — `docs/04_mcp_06_03_mcpserverconfig-fields-agenttoml-mcp_servers.md:28`
  already documents `call_timeout_sec`'s "0 = no timeout" contract correctly; verified no
  contradiction exists (see Unknowns/UNK-03).
- Any `config/*.toml` file — repo-wide search confirms no shipped config currently sets
  `call_timeout_sec` to any value, so no config migration is needed.

## Design
The fix stays entirely within `scripts/shared/`'s existing layering: `ToolTransportInvoker` already
depends on `McpServerConfig` (`shared.mcp_config`) and `HttpTransport` (`shared.http_transport`) —
no new import is introduced, and no import-boundary/layering rule is crossed (`shared/` → `shared/`
only). The constructor signature of `ToolTransportInvoker.__init__` is unchanged (same parameters,
same return type `None`), so this is not a public/runtime interface change — callers (`ToolExecutor`
and any test double) are unaffected except for the corrected internal value passed to
`HttpTransport`.

The design intentionally centralizes "what does an unset/zero timeout mean" in exactly one place
downstream: `HttpTransport.call` (`scripts/shared/http_transport.py:104`,
`timeout = httpx.Timeout(self._timeout) if self._timeout > 0 else None`). Before this fix,
`ToolTransportInvoker` pre-empted that decision with its own conflicting truthy check; after, it
becomes a pure pass-through, and `McpServerConfig`'s dataclass default (`60.0`,
`scripts/shared/mcp_config.py:55`) plus the config loader's default
(`scripts/shared/mcp_config.py:218`, `float(v.get("call_timeout_sec", 60.0))`) remain the single
source of truth for "what's the default when unset." No second default is added to
`ToolTransportInvoker`, avoiding drift between two defaults over time.

### Phase 1 — Preparation
1. Extend the `_http_cfg` helper in `tests/shared/test_tool_transport_invoker.py:22-23` to accept an

2. Add a characterization test (e.g. `test_call_timeout_sec_zero_currently_falls_back_to_60`) that
   builds an invoker with `call_timeout_sec=0` and asserts
   `invoker._transports["srv"]._timeout == 60.0` — the current (buggy) value. Run
   `uv run pytest tests/shared/test_tool_transport_invoker.py -k call_timeout -v` and confirm it
   PASSES against pre-fix code, per this project's characterization-test-first discipline
   (`AGENTS.md` → `skills/python-refactoring/workflow.md` §Phase 2). This step is independently
   revertable (a test-only commit) and testable on its own.

### Phase 2 — Core logic
3. In `scripts/shared/tool_transport_invoker.py:54-58`, replace:
   ```python
   timeout_sec = (
       cfg.call_timeout_sec
       if hasattr(cfg, "call_timeout_sec") and cfg.call_timeout_sec
       else 60.0
   )
   ```
   with:
   ```python
   timeout_sec = cfg.call_timeout_sec
   ```
   Do not add any new fallback/default logic in this class (see Design).

   `_timeout == 0` (not `60.0`) now that the fix is in place. Add the two remaining cases from the

   - default-unset (`_http_cfg()` with no `call_timeout_sec` arg) → `_timeout == 60.0`.

## Risks
- **Risk**: A careless characterization test could assert the *already-correct* value from the
  start, failing to actually pin the pre-fix bug, defeating the test-first discipline's purpose.
  → **Mitigation**: Step 2 explicitly requires running the test against pre-fix code and confirming
  it PASSES with the buggy `60.0` assertion before touching `tool_transport_invoker.py`; only then
  flip the assertion in step 4. Likelihood: low.
- **Risk**: Some other, not-yet-written config or caller could set `call_timeout_sec=0` unintentionally
  (e.g. a copy-paste default of `0` instead of omitting the key), now genuinely disabling timeouts in
  production once this fix ships, where previously the bug silently protected against that mistake.
  → **Mitigation**: This is the documented, validated, intended contract (`__post_init__` accepts
  `>= 0`, field comment says "0 = no timeout"), not a new risk introduced by this fix — it is the
  bug this requirement exists to close. No shipped config currently sets `0` (confirmed in UNK-01),
  and the new tests make the "0 disables timeout" behavior explicit and visible in test output for
  future reviewers. Likelihood: low.
- **Risk**: Bus factor is effectively 1 (`Masao SUGIMOTO`/`Masao Sugimoto`, same person under two
  case variants) for this file, so review coverage relies on the same author who wrote the original
  bug and the fix. → **Mitigation**: Out of scope to fix within this plan (an organizational
  concern, not a code concern); mitigated procedurally by the characterization-test-first
  discipline making the before/after behavior explicit and reviewable independent of author
  familiarity. Likelihood: low (this is a narrow, well-evidenced, low-complexity change — `radon cc`
  reports `ToolTransportInvoker.__init__` at complexity B(6), no High/Medium bandit findings).

No risk required filing a separate `issues/*_risks.md` — all three are fully mitigated within this
