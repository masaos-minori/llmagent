## Background
This Plan's source Issue was discovered while compiling the related-document impact analysis for the 2026-08-31 `docs/adr/ADR-004-environment-failure-handling-policy.md` rewrite. `docs/04_mcp_04_02_file-write-file-delete-shell.md` documents the `shell_sandbox_backend = "none"` `RuntimeError` enforcement as applying only "In production mode (`security_profile = "production"` in `agent.toml`)". ADR-004 (Decision Group 1, item 3) requires that environment names not change Fail-Fast conditions, and (Decision Group 2, item 6) prohibits converting a safety/integrity failure into warning-only continuation. The source Issue asked whether the code genuinely conditions this `RuntimeError` on `security_profile`, or whether only the documentation's framing is environment-specific.

## Problem
(Evidence: Confirmed by repository evidence) Direct read of `scripts/agent/repl_health.py`'s `audit_security_defaults()` confirms the `RuntimeError` for `shell_sandbox_backend == "none"` is genuinely conditioned on its `production_mode` parameter: when `production_mode` is `True` it raises `RuntimeError`; otherwise it only logs a warning and appends it to the returned warnings list. `scripts/agent/startup.py` derives `production_mode = ctx.cfg.mcp.security_profile == SecurityProfile.PRODUCTION` before calling `audit_security_defaults()`. This means a non-production environment with `shell_sandbox_backend = "none"` currently starts up successfully with only a warning — the same safety/integrity condition (shell commands running completely unsandboxed) is Fail-Fast in one environment and warning-only in another, which is exactly the environment-conditional relaxation ADR-004 Decision Group 1/2 prohibits. (Evidence: Explicit in config) `config/shell_mcp_server.toml` explicitly sets a `shell_sandbox_backend` value (see that file for the current setting) rather than leaving it unset — so this gap is not merely theoretical for whichever environment currently loads that file; if the configured value is `"none"`, this Plan's fix (REQ-001) will newly fail startup there, which is why REQ-004's sign-off gate exists (see Requirements, Risks). This Plan does not restate the concrete configured value here; the sign-off step must read it directly from the file at implementation time.

The documentation passage the source Issue named is, itself, currently accurate: `docs/04_mcp_04_02_file-write-file-delete-shell.md`'s "Enforcement in Production" passage correctly describes today's conditional code behavior. The gap is in the code's conformance to ADR-004, not in the document's accuracy — per the source Issue's own instruction, this is therefore raised as a code-level ADR-004 conformance fix (not a silent doc reword to hide the relaxation), with the named documentation passage updated to match the corrected, unconditional behavior once implemented.

## Reason for change
Leaving this check conditioned on environment keeps a genuine safety/integrity control (shell command sandboxing) weaker in whichever environment is not currently classified `production`, contradicting ADR-004's explicit requirement that environment names never change Fail-Fast boundaries for safety/integrity failures. Fixing it now, while the ADR-004 rewrite's document/code alignment work is already in progress (see the sibling `adr004_04`/`adr004_05`/`adr004_06` Plans), keeps this conformance sweep from leaving a known, evidenced gap unaddressed.

## Implementation intent
Remove the `if production_mode:` branch that currently gates the `RuntimeError` for `shell_sandbox_backend == "none"`, so the function raises unconditionally whenever this value is configured, regardless of `security_profile`. Update the message text to drop the "in production mode" framing. Update the two existing tests in `tests/agent/test_repl_health.py` that exercise this specific check so both assert `RuntimeError`, parametrized (or otherwise proven) over both `production_mode` values, replacing the current warning-only assertion for the non-production case. Update `docs/04_mcp_04_02_file-write-file-delete-shell.md`'s "Enforcement in Production" passage and its nested Note to describe the corrected, unconditional behavior. Because the currently configured environment (`config/shell_mcp_server.toml`) would newly fail startup once this lands, gate the deployment of this change behind an explicit operations/architecture-owner sign-off (REQ-004) rather than assuming it is safe to roll out immediately — this mirrors the sign-off-gate pattern already used in the sibling `adr004_05` Plan for a comparably consequential change.
