## Background
`governance_03` requires fifteen fields per NC entry, including `Blocking`, but defines no meaning or allowed values for it; Priority and Status have value sections. `check_blocking_reference` in `tools/check_needs_confirmation_inventory.py` treats `Blocking` as a reference to a known NC id and warns, for an `open` entry, when a non-empty value is not a known NC id; the regex reading the field requires at least one character after the label, so an empty value yields no value and no warning. NC-041 is currently the only active entry, and its `Blocking` label has no value. The `Blocking status` field with `Blocking` / `Non-blocking` values belongs to Part 3, not Part 2. Related convention: `templates/unknowns-issue.md` describes "Blocking for:" as what an Unknown blocks, which matches the Issue's Option A reading (the item this entry blocks).

## Problem
The meaning of `Blocking` is undefined, so an empty value cannot be distinguished from "not yet assessed". Adversarial verification found a gap in the Issue's Option A: it proposes "a reference to the NC id that this item blocks, or an explicit none value", but the checker warns on any non-empty value that is not a known NC id, so an explicit "none" value written for NC-041 would itself trigger a warning. Option A therefore needs a small checker change as well as a definition. The Issue also names the test file as `tests/test_check_needs_confirmation_inventory.py`; the file is `tests/tools/test_check_needs_confirmation_inventory.py`. Under Option A, the release/deployment impact of NC-041 (a disabled mandatory component), which the Issue's Problem statement mentions, remains unrecorded; only Option B would record it.

## Reason for Change
The inventory's purpose is that entries are trackable and actionable. A mandatory field with no definition cannot be used for release decisions, and a reviewer can reasonably misread it. Fixing the semantics first also prevents a wrong checker rule from being added.

## Implementation Intent
Follow the Issue's preference for Option A: `Blocking` names the single NC id that this item blocks, or the value `None` when the item blocks no other NC item, and an empty value means not yet assessed. This matches the existing checker semantics (NC-id reference), reuses the `None` convention of the `Related NC` field, and requires no migration of the existing entry beyond giving NC-041 an explicit value. The checker accepts `None` and keeps warning on an unknown NC id; empty stays accepted, so no new finding is introduced on the existing corpus. Because the Issue's Required Changes begin with obtaining the owner's decision, the first implementation step is a gate: if the owner chooses Option B or another definition, stop and amend this Plan.

## Design
- Path A (three files; a report-only checker's warning rule changes but no runtime-facing interface or schema); baseline recorded: 29 existing tests pass, `bandit` is clean, and `_parse_inventory_entries` and `check_untracked_inline_markers` are the only functions at complexity grade C (not modified).
- The checker change is one extra condition in `check_blocking_reference`; its exit code contract (warnings exit 0) is unchanged, so the existing corpus cannot newly fail.
- The `Blocking` regex needs at least one character after the label, so an empty label parses as no value; the definition relies on that existing behavior for "not assessed".
- The definition uses the existing `None` convention of `Related NC` and does not import the Part 3 vocabulary.
