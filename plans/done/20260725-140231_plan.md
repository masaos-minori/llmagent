## 1. Goal

Prevent silent overwrites of `pending_approval_task_id` and add validation for restored task status. Ensure that when multiple approvals exist, each approval's associated task is correctly restored and halted tasks are rejected with proper error messages.

## 2. Scope

### In-Scope
- Log warning before overwriting `pending_approval_task_id` if non-None value exists
- Clear `pending_approval_task_id` immediately after use by `_init_workflow_task()`
- Validate retrieved task status in `_init_workflow_task()`; reject halted tasks with error
- Add support for queue-based pending task IDs to handle multiple concurrent approvals

### Out-of-Scope
- Changes to approval request logic
- Changes to approval record schema
- Changes to per-tool interactive approval (tool_approval.run_approval_checks)
- Database migration for existing records

## 3. Assumptions

- Warnings should be logged at INFO level with task ID details redacted
- Halted tasks should be rejected with a specific error message indicating the task was halted
- Queue-based approach should maintain FIFO ordering for pending approvals
- Existing callers of `_init_workflow_task()` can handle the new RuntimeError with specific error message

## 8. Risks & Mitigations

- **Risk**: Queue-based approach adds complexity to existing single-value implementation. → **Mitigation**: Start with overwrite warning only; upgrade to queue-based approach in separate PR after validation period.
- **Risk**: Rejecting halted tasks may break existing workflows that expect halted tasks to be processed. → **Mitigation**: Document breaking change; provide configuration option to allow halted task processing during transition.
- **Risk**: Warning logs may contain sensitive task IDs that should be redacted. → **Mitigation**: Redact task IDs in warning logs; log full IDs only at DEBUG level.
