## Goal
- Make a programming error inside the startup memory-injection step visible as such: classify it as a distinct `PROGRAMMING_ERROR` category, log it at error level with a traceback, and show the user an internal-error warning, while startup still completes without memory exactly as it does for the documented runtime failures.

## Priority
Low

## Scope
- **In-Scope**:
  - Add a `PROGRAMMING_ERROR` category to `PromptSetup._classify_memory_failure()` for `AttributeError`, `NameError`, `TypeError`, `LookupError` and `AssertionError`.
  - In `PromptSetup.setup_prompt()`, handle that category with an error-level log that includes the traceback and a distinct view warning; keep the documented runtime categories and the benign `UNKNOWN` path as they are.
  - Tests for the classification and for the new log and warning.
  - Update the one document line that states the memory failure behavior.
- **Out-of-Scope**:
  - Narrowing or removing the catch around the memory call: startup must continue, so the catch stays.
  - The log level and message of the `UNKNOWN` category (an existing test pins them) and the classification of `ValueError` and other types as `UNKNOWN`.
  - The memory service itself, `StartupOrchestrator` and its rollback, and the per-turn `handle_memory_injection` (same broad catch, outside the Issue).

## Background
- `PromptSetup.setup_prompt()` calls the memory service for the startup snippets inside `try/except Exception`; any exception sets `ctx.conv.memory_disabled`, is classified into one of three string categories, logged at a level chosen by category, and shown as one view warning (`scripts/agent/startup_prompt_setup.py:57-87`).
- Issue `issues/20261012-124838_start004_startup-prompt-setup-swallows-all-memory-injection-errors-as-a-generic-disabled-flag.md` asks to stop treating programming errors as benign and leaves the policy open.
- Decision recorded with the user on 2026-10-12: startup still completes and memory is disabled, but an unexpected programming error gets its own category and prominent reporting; `PROGRAMMING_ERROR` covers an explicit list of exception types only.

## Problem
Verified against current source (`Confirmed by repository evidence`):
- **Confirmed**: `except Exception` at `startup_prompt_setup.py:67` catches everything; `_classify_memory_failure` returns `NETWORK_TRANSIENT`, `DATABASE_OR_IO` or `UNKNOWN`; an `AttributeError` or `TypeError` is classified `UNKNOWN` and logged at `info` with the same single view warning as any failure. `info` is below the level used for the known transient network case (`warning`) and the database case (`error`), so the least explained failures are the least visible.
- **Why propagating is not an option (Issue Unresolved Question 1)**: `StartupOrchestrator.run()` calls `_setup_prompt()` inside its `try` (`scripts/agent/startup.py:78`), whose handler rolls back and re-raises, so an exception that propagates aborts startup. The documented behavior is graceful degradation: `docs/23_agent/agent_12_reference-api.md` says "Errors are logged. REPL continues without memory". The memory layer is optional, so a memory bug must not stop the agent; the fix is visibility, not abort.
- **`UNKNOWN` has no downstream behavior (Issue Unresolved Question 2)**: the category string is read only inside `setup_prompt()` to choose the log level (`rg` over `scripts/`, `tests/` and `docs/`); `StartupOrchestrator._classify_memory_failure` only delegates to it.
- **Correction to the Issue (narrowing the catch)**: the Required Changes say to narrow `except Exception`, but the constraints require startup to complete, and the catch also covers non-memory lines (snippet truncation, text formatting). Narrowing would make an unexpected exception abort startup. The Issue's intent (do not file a defect as benign) is met by classification and visibility instead, so the catch stays.
- **Existing tests constrain the change**: `tests/agent/test_startup_prompt_setup.py` pins `ValueError` to `UNKNOWN` (line 64 and the parametrized logging test: `info`, "(unknown error)"), requires the view warning to contain "Memory injection failed", and `test_memory_disabled_flag_on_failure` uses `RuntimeError`. Keeping `UNKNOWN` as it is and limiting `PROGRAMMING_ERROR` to an explicit type list keeps them passing.
- **Documentation**: the Issue's conditional update of `docs/23_agent/agent_10_01_operations-and-observability-startup-and-health.md` does not apply: it does not mention the memory failure categories (checked with a search). The one statement of the behavior is the "On Failure" line in `agent_12_reference-api.md`.

## Reason for change
- A defect in the memory service is currently indistinguishable from a transient network or database condition, so it is unlikely to be investigated.
- Fail-safe on runtime conditions is correct and stays; fail-safe on programming errors needs to be loud.

## Implementation intent
- Add one category and one branch; do not change which exceptions are caught or whether startup continues.
- Log the new category at error level with `exc_info=True`, and show a view warning that names the exception type, says memory is disabled, and says it indicates a defect to look into in `agent.log`; keep the existing `[non-fatal]` tag because startup continues, and keep the text "Memory injection failed" so existing expectations hold.
- Classify by `isinstance` on an explicit tuple, checked after the network and database categories.
