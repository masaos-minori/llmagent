## Background
- Commit `c0a589e19` added a conditional assignment in `ApprovalRecovery.recover()` (`scripts/agent/startup_approval_recovery.py:66-70`): `pending_approval_task_id` is set only when the current value is `None` or equals the recovered `task_id`. When they differ, the existing value is **preserved** and a `"Keeping existing pending_approval_task_id %s instead of overwriting with %s"` WARNING is logged.
- This fixed the core defect reported by this issue: the pre-`c0a589e19` unconditional `ctx.turn.pending_approval_task_id = task_id` made the "Keeping existing" log untruthful. That defect is resolved; all 11 tests in `TestStartupOrchestratorRecoverPendingApprovals` pass.
- `docs/23_agent/agent_10_01_operations-and-observability-startup-and-health.md` ("Restoration of Pending Post-Execution Approvals") still states: *"a WARNING level log is emitted, but the value is overwritten (the process does not abort)."* This contradicts the current preservation behavior.
- Plan `20261004-113000` REQ-001 (StateStore existence check for staleness) was never implemented; the committed code uses simple value equality, not StateStore existence.

## Problem
- Documentation inconsistency: the ops guide says the value is **overwritten**, but the tested/implemented behavior **preserves** the existing value when it differs from the recovered id. Operators relying on the guide would expect overwrite.
- The core behavioral defect is already fixed (see Background); no test failure remains attributable to this issue (all 11 recovery tests pass).

## Reason for change
Observability and source/doc consistency: the documented contract contradicts the implemented and tested contract. Under `governance_01` (Claim Type Taxonomy), runtime behavior is canonical in source under `scripts/` with tests as evidence; the doc currently describes the old (pre-fix) behavior and must be corrected.

## Implementation intent
Two options were considered; **Option B (current state) is recommended**.
- **Option A**: implement the StateStore-based staleness check (assign only when the existing value is `None`, equal to the recovered one, or stale — its approval record no longer exists in StateStore, per plan `20261004-113000` REQ-001). Higher cost, changes runtime behavior, and requires an owner decision on which approval is wired for `/approve` when two exist. Static analysis indicates the "differs" branch is unreachable at startup in production, so Option A would add production-untested code.
- **Option B (recommended)**: keep the current conditional assignment (preservation via value equality) and update the doc to describe preservation. Lower risk; no code change.

The owner decides; this Plan encodes Option B.

## Design
