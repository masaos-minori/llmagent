## Goal
- Make the Web Search MCP configuration and tool schemas strict and consistent with the runtime models, remove sensitive query and URL content from audit records through a shared redaction helper, and emit exactly one audit record for every authenticated `/v1/call_tool` call, including rejected ones, through a shared audit-emission guard that the CI/CD and MDQ servers can reuse.

## Priority
High

## Scope
- **In-Scope**:
  - One allowlist normalization function (lowercase, IDNA ASCII, trailing dot removed) used by configuration loading, the posture check, and runtime authorization; strict load-time validation that rejects scheme, path, query, fragment, user information, port, non-string, blank, malformed, and duplicate entries (an empty list stays the intentional `browser_fetch` disabled configuration).
  - Strict request models (`StrictRequestModel`) for `search_web` and `browser_fetch`, with both tool `inputSchema` values generated by `build_input_schema()` and drift tests for both tools; a non-empty `url`; the `max_response_kb` maximum aligned with the server hard ceiling and the clamping described in the schema.
  - Audit redaction: a normalized hash replaces the raw query target, query previews are removed, URL targets keep the scheme, normalized host, and a redacted path only; non-sensitive metadata only.
  - Request-context extraction before the disabled-tool rejection, and exactly one audit record for disabled, unknown-tool, validation, authorization, envelope-validation, and other rejections; rejected calls never change provider health counts.
  - A shared audit-emission contract in `scripts/mcp_servers/audit.py`: an exactly-once emission guard, a hash helper for query-like values, and a URL redaction helper; removal of the plaintext query-preview example from the audit module docstring.
  - Documentation: allowlist normalization and matching, the rule that search-result URLs are not automatically authorized for `browser_fetch`, audit redaction and the exactly-once rule, health wording, and Bearer authentication in `/v1/tools` examples.
- **Out-of-Scope**:
  - Network authorization, DNS and redirect handling, and resource limits of `browser_fetch` (the fetch-boundary issue of the same backlog).
  - CI/CD and MDQ audit adoption (those issues consume the helpers).
  - MDQ's own `query_preview` handling.
  - Plumbing result metadata (result count, status class, truncation flags) from the service into the audit record (see UNK-02).
- **Dependencies**: Every issue this one depends on (the shared strict schema generator, the shared strict configuration helpers, and the audit identifier fields from the GitHub write retry-policy work) is archived and merged, so no ordering dependency remains. The fetch-boundary issue may run in parallel; its Plan edits the fetch path of the same provider and the same models module (see Assumptions). This Plan blocks the CI/CD error audit coverage and MDQ server boundary issues, which reuse the shared audit-emission contract and redaction helper.

## Problem
- Raw queries and URLs, which can carry signed parameters, tokens, OAuth data, or personal data, are retained in audit records; disabled-tool and envelope-validation rejections are invisible to operators; malformed allowlist entries start the server with only a warning although they can never match; the `browser_fetch` schema does not reflect its model or the effective server limit, and unknown arguments are silently dropped.

## Reason for Change
- Privacy and security: sensitive content is persisted in logs, and rejected attempts leave no trace.

## Implementation Intent
- One normalization function and one strict model per tool serve configuration, posture, discovery, and runtime. The audit layer gets a small shared contract (exactly-once guard plus redaction helpers) and the web search server uses it, so every authenticated call produces one safe record.

## Requirements
- `REQ-001`: One function MUST normalize an allowlist host (lowercase, IDNA ASCII, one trailing dot removed) and MUST be the only normalization used by configuration loading, the posture check, and runtime authorization; the URL host MUST be normalized by the same function before comparison.
- `REQ-002`: Configuration loading MUST reject, with a startup error that names the setting and the entry index but not the value, any allowlist entry that is not a string, is blank, contains a scheme, path, query, fragment, user information, or port, fails normalization, or duplicates another entry after normalization; an empty list MUST stay valid and MUST disable only `browser_fetch`.
- `REQ-003`: `SearchRequest` and `BrowserFetchRequest` MUST derive from `StrictRequestModel` (unknown fields rejected), `browser_fetch.url` MUST be non-empty, `max_response_kb` MUST be bounded by the server hard ceiling, and both tool `inputSchema` values MUST be generated from those models by `build_input_schema()`; drift tests MUST cover both tools.
- `REQ-004`: The audit target for `search_web` MUST be a normalized hash and no query preview MUST be recorded; the audit target for `browser_fetch` MUST keep only the scheme, the normalized host, and a redacted path, with query, fragment, and user information removed; the detail MUST carry only non-sensitive metadata available at the server layer (query length, host, latency, and the existing key-value fields that carry no raw input).
- `REQ-005`: The server MUST extract the request context before the disabled-tool check and MUST emit exactly one audit record for every authenticated call: success, disabled tool, unknown tool, validation error, authorization error, envelope validation error, and unexpected failure; a rejected call MUST NOT change provider health counts.
- `REQ-006`: `scripts/mcp_servers/audit.py` MUST provide the shared audit-emission contract: an exactly-once emission guard, a hash helper for query-like values, and a URL redaction helper that strips query, fragment, user information, and redacts path segments by one documented rule; no helper may return a raw sensitive value; the module docstring MUST NOT contain a plaintext query-preview example.
- `REQ-007`: The documentation MUST describe allowlist normalization and matching, that search-result URLs are not automatically authorized for `browser_fetch`, the audit redaction and exactly-once rules, health wording that does not imply constant health and separates current health from historical error metadata, and Bearer authentication in `/v1/tools` examples.

Module sizes: `audit.py` 6041 B, `web_search_models.py` 12451 B, `web_search_server.py` 16582 B, all below the 24576 B gate with headroom for the additions.

Decisions (each lists alternatives and compatibility impact):
- **D-1 Normalization location.** A new leaf module `host_normalization.py` imported by the models (load-time validation), the posture check, and the provider. Alternative: put it in `web_search_models.py` (rejected: the provider and posture module would import a large config module for one function, and the posture module already imports it, creating a wider cycle risk). The IDNA step uses the stdlib `encodings.idna` codec; no dependency.
- **D-2 Load-time failure, not warning.** A malformed allowlist entry raises `ValueError` from `WebSearchConfig.from_dict`, which already runs at import (`_cfg = WebSearchConfig.load()`); the posture allowlist check keeps only the NOT_APPLICABLE and OK outcomes. Alternative: keep a posture FAILED (rejected: the config object would still carry unusable entries). Compatibility: the shipped list is empty, so the shipped configuration still starts.
- **D-3 Schema source.** Request models derive from `StrictRequestModel`; `inputSchema` is `build_input_schema(model)` (already used by the GitHub server). Alternative: keep dict schemas with a drift test only (rejected: the issue asks for one generator). Compatibility: unknown arguments are now rejected instead of dropped.
- **D-4 `max_response_kb` bound.** The model maximum becomes `HARD_BROWSER_MAX_RESPONSE_KB` (4096) and the description states that the server clamps to the configured maximum. Alternative: expose the configured maximum in the schema (rejected: it would make the schema depend on a value the clamp already handles and change clamping into rejection).
- **D-5 Audit target and detail.** `search_web`: target `sha256:<16 hex>`, detail `query_len`, `max_results`, `latency_ms`; `browser_fetch`: target `<scheme>://<host><redacted path>`, detail `host` and `latency_ms`; no preview fields. Alternative: keep a truncated preview (rejected by the issue).
- **D-6 Shared audit-emission contract.** `audit.py` gains `AuditEmission` (a small per-call guard whose `emit()` writes once and refuses a second write), `hash_query_value()`, and `redact_url()`. The server wraps one `AuditEmission` around the whole handler body so every return and raise path emits through it exactly once. Alternative: emit from a middleware (rejected: the outcome and error type are known only inside the handler).
- **D-7 Gate ordering.** `call_tool` extracts the request context first; the disabled-tool check becomes a rejected outcome (`error_type="tool_disabled"`) inside the same guarded block, so it is audited once and never reaches the service, leaving health untouched.
- **D-8 Envelope validation.** A `RequestValidationError` handler scoped to `/v1/call_tool` emits one audit record (`validation_error`) and returns the framework's 422 body unchanged. Alternative: leave envelope errors unaudited (rejected: the issue requires every authenticated rejection).

## Risks
- **Risk**: An operator's existing allowlist contains an entry the strict loader rejects and the server no longer starts (likelihood: low; the shipped list is empty) → **Mitigation**: the error names the setting and entry index, the config comment documents the rules, and the deploy hand-off checks the host configuration before the restart.
- **Risk**: External log tooling parses `query_preview` or `url_preview` (likelihood: low-medium) → **Mitigation**: UNK-01 check before deployment and a documented field removal; the issue's instruction to stop and report applies if a consumer is found.
- **Risk**: The redaction helper leaks a token-shaped path segment that the rule does not match (likelihood: medium) → **Mitigation**: the rule keeps only short plain segments and replaces the rest; tests use signed-URL, token, OAuth, and personal-data fixtures.
- **Risk**: The exactly-once guard double-emits or misses an outcome on a path with an early return (likelihood: medium) → **Mitigation**: one guard wraps the whole handler body and a parametrized test asserts one record per outcome category.
- **Risk**: Tightening `max_response_kb` or rejecting unknown fields breaks a client that sent extra arguments (likelihood: low-medium) → **Mitigation**: the Agent builds arguments from the published schema; the change is documented and covered by tests.
- **Risk**: `audit.py` and `web_search_models.py` have a high blast radius (likelihood: medium) → **Mitigation**: additive changes only to `audit.py`, independently revertable phases, and the full suite per phase.
- **Risk**: The IDNA codec rejects an unusual but legitimate label (likelihood: low) → **Mitigation**: a normalization failure is a load-time rejection with a clear message; the entry can be rewritten as its ASCII form.
