# Plan: Make the startup sequence interruptible by SIGINT/SIGTERM

## Goal
A `SIGINT`/`SIGTERM` sent while `StartupOrchestrator.run()` is blocked in `_start_servers()`
(subprocess spawn, stagger delay, retry delay) or `_verify_mcp_health()` (health-check retry
delay) — or, per the evidence gathered below, blocked inside
`HttpServerLifecycleManager.start()`'s per-server 0.5s health-poll loop — causes the startup
sequence to abort and roll back within a few seconds, instead of blocking for the full
per-server `startup_timeout_sec` (default 30s) across all configured servers, by reusing the
`asyncio.wait(..., return_when=FIRST_COMPLETED)` task-race pattern already proven in
`AgentREPL._repl_loop()`.

## Assumptions
1. `AgentREPL.run()` always constructs exactly one `asyncio.Event` (`self._shutdown_event`,
   `scripts/agent/repl.py:755`) before constructing `StartupOrchestrator` (line 829), so the same
   event object used later by `_repl_loop()` is available to pass into the orchestrator at
   construction time. Falsifiable by re-reading `repl.py:743-829` — confirmed in Step 3.
2. `StartupOrchestrator` has no existing constructor parameter for a shutdown signal — confirmed
   by `grep -n "shutdown_event|shutdown_requested" scripts/agent/startup.py` returning zero
   matches (Step 3), matching the requirement's own verification.
3. All 10 currently configured MCP servers in `config/agent.toml`
   (`shell, git, web_search, file_delete, file_write, file_read, github, cicd, rag_pipeline, mdq`)
   use `transport = "http"` and `startup_mode = "subprocess"` (confirmed via
   `grep -n "startup_mode|transport" config/agent.toml`), and none override
   `startup_timeout_sec` (confirmed via `grep -n "startup_timeout_sec" config/agent.toml` — no
   matches outside the schema-comment block), so all 10 use the `McpServerConfig` default of 30s
   (`scripts/shared/mcp_config.py:56`). This means, without modifying
   `HttpServerLifecycleManager.start()`'s internal poll loop, worst-case shutdown latency during
   the currently-polling server is bounded by up to 30s, not "a few seconds" — falsifying the
   "accepted latency bound" option the requirement offers as an alternative to modifying
   `http_lifecycle.py`. This drives Design §4/Scope's inclusion of `http_lifecycle.py`.
4. `HttpServerLifecycleManager._http_procs[server_key] = proc` is set (line 409, confirmed in
   Step 3) *before* the health-poll loop begins, i.e. before any shutdown-interruption inside that
   loop could occur. This means a shutdown fired mid-poll still leaves the subprocess reachable
   through `_http_procs` for `HttpServerLifecycleManager.shutdown_all()` to terminate — no separate
   termination call is needed inside `start()`'s interruption path; raising and letting the
   existing (sibling-fixed) rollback in `run()`'s `except` block handle it is sufficient.
5. This plan is written to be layered on top of the sibling plan
   (`plans/20260804-140300_plan.md`), which changes `run()`'s except block to call
   `lifecycle.shutdown_all()` unconditionally and makes `self._spawned_subprocesses` accumulate
   incrementally inside `_start_servers()`. As of this plan's writing, neither fix is yet applied
   to `scripts/agent/startup.py` (confirmed: the file still contains the `_servers_started` flag
   and a local `spawned` list, per Step 3 read) — both are plan-stage only. Implementation order
   matters: see Risk 1.

## Design

1. **`StartupOrchestrator.__init__()`** — add
   `shutdown_event: asyncio.Event | None = None` as a keyword-capable parameter and store it as
   `self._shutdown_event`. Default `None` preserves every existing direct-construction call site
   in `tests/agent/test_startup.py` (20+ sites) without modification.

2. **Shared race helper — `StartupOrchestrator._interruptible_sleep(self, delay: float) -> bool`.**
   Reuses the exact `asyncio.wait({task_a, task_b}, return_when=asyncio.FIRST_COMPLETED)` pattern
   already established in `AgentREPL._repl_loop()` (`scripts/agent/repl.py:538-556`), generalized
   to race a plain `asyncio.sleep(delay)` against `self._shutdown_event.wait()`:

   ```python
   async def _interruptible_sleep(self, delay: float) -> bool:
       """Sleep for `delay` seconds, or return early if shutdown_event fires first.

       Returns True if shutdown was signaled before the delay elapsed; False if the
       full delay elapsed normally (or no shutdown_event was configured).
       """
       if self._shutdown_event is None:
           await asyncio.sleep(delay)
           return False
       sleep_task = asyncio.ensure_future(asyncio.sleep(delay))
       shutdown_task = asyncio.ensure_future(self._shutdown_event.wait())
       done, pending = await asyncio.wait(
           {sleep_task, shutdown_task}, return_when=asyncio.FIRST_COMPLETED
       )
       for task in pending:
           task.cancel()
       return shutdown_task in done
   ```

   This is introduced specifically to satisfy the requirement's instruction not to introduce a
   *new* cancellation abstraction while still avoiding tripling the same inline `asyncio.wait`
   block across the stagger delay, the `_start_servers()` retry delay, and the
   `_verify_mcp_health()` retry delay — each call site becomes a single `if await
   self._interruptible_sleep(delay): raise StartupInterrupted(...)` line, keeping the CC increase
   at each of the two methods to roughly one branch per race point (UNK-03).

3. **`StartupInterrupted` exception** — add `class StartupInterrupted(RuntimeError):` (module
   level in `startup.py`, alongside `HEALTH_CHECK_RETRY_DELAY_SEC`). Raised at every
   shutdown-interruption point in `_start_servers()`/`_verify_mcp_health()`/(via propagation)
   `http_lifecycle.py`'s `start()`. Deliberately a plain `RuntimeError` subclass, not a new
   control-flow mechanism: it flows through `StartupOrchestrator.run()`'s existing
   `except Exception as setup_err:` block unchanged, so it triggers the same rollback path the
   sibling plan hardens (Assumption 5) — no second, divergent rollback path is introduced, per the
   requirement's explicit instruction.

4. **`_start_servers()` changes** (lines 133-204):
   - At the top of the `for key, cfg in ctx.cfg.mcp.mcp_servers.items():` loop, check
     `if self._shutdown_event is not None and self._shutdown_event.is_set(): raise
     StartupInterrupted(f"shutdown requested before starting MCP subprocess {key!r}")` — stops
     starting further servers once a shutdown is already pending.
   - Replace the stagger-delay `await asyncio.sleep(stagger_delay)` with
     `if await self._interruptible_sleep(stagger_delay): raise StartupInterrupted(...)`.
   - Replace the retry-delay `await asyncio.sleep(HEALTH_CHECK_RETRY_DELAY_SEC)` (line 179) with
     the same pattern.
   - Pass `self._shutdown_event` into
     `ctx.services_required.lifecycle.start_http_subprocess(key, cfg, shutdown_event=self._shutdown_event)`
     at both the first-attempt and retry call sites, so a shutdown firing while a subprocess is
     mid-health-poll (inside `http_lifecycle.py`, Design §6) is also honored.

5. **`_verify_mcp_health()` changes** (lines 206-252): same `_interruptible_sleep()` substitution
   for its retry-delay `await asyncio.sleep(HEALTH_CHECK_RETRY_DELAY_SEC)` (line 231), plus a
   shutdown check at the top of the `for server_key, cfg in subprocess_servers:` loop mirroring
   `_start_servers()`'s pattern.

6. **`HttpServerLifecycleManager.start()` changes** (`scripts/agent/http_lifecycle.py:286-451`) —
   included in scope despite the requirement listing it as conditional, per Assumption 3/UNK-01:
   add `shutdown_event: asyncio.Event | None = None` as a new keyword parameter; inside the poll
   loop (`while time.monotonic() < deadline:`), replace `await asyncio.sleep(0.5)` with a
   local equivalent of the same race (a private module-level or method-local helper mirroring
   `StartupOrchestrator._interruptible_sleep()` — not shared as one function across two classes
   to avoid adding a cross-module coupling for a 6-line helper; each class keeps its own copy of
   the identical pattern, consistent with how `_repl_loop()`'s original pattern was itself
   inlined, not extracted, before this plan). On shutdown-fire, raise `HttpStartupError` (the
   existing exception type used for both "exited early" and "timeout" failures in this method) with
   a distinct `reason="shutdown requested"` `StartupFailure`, so callers already handling
   `HttpStartupError` do not need a new except clause. Per Assumption 4, `_http_procs[server_key]`
   is already populated at this point, so the existing `lifecycle.shutdown_all()` rollback (once
   the sibling plan's unconditional-call fix lands) terminates this subprocess without any new
   direct-termination code in `start()` itself.

7. **`_ServerLifecycleRouter.start_http_subprocess()`** (`scripts/agent/factory.py:174-193`) — add
   the same optional `shutdown_event` parameter and forward it to `self._http_mgr.start(server_key,
   cfg, shutdown_event=shutdown_event)`. `restart()` (line ~196) is not changed — it does not
   accept or forward `shutdown_event`, consistent with Scope/UNK-04.

8. **`LifecycleManagerProtocol.start_http_subprocess()`** (`scripts/agent/lifecycle_protocol.py:
   48-51`) — widen the signature to match, so the Protocol stays truthful to its sole
   implementer.

9. **`AgentREPL.run()`** (`scripts/agent/repl.py:829`) — change
   `StartupOrchestrator(self._ctx, self._view)` to
   `StartupOrchestrator(self._ctx, self._view, shutdown_event=self._shutdown_event)`. No other
   change to `run()` or `_repl_loop()` (out of scope per requirement §8).

## Risks

- **Risk 1 (implementation-order dependency)**: This plan's `StartupInterrupted` relies on
  `StartupOrchestrator.run()`'s `except Exception as setup_err:` block to call
  `lifecycle.shutdown_all()` for cleanup. In the *current* code, that call is still gated by the
  `_servers_started` flag (only `True` after `_start_servers()` returns normally) — the exact bug
  the sibling plan (`plans/20260804-140300_plan.md`) fixes. If this plan's changes are implemented
  and shipped *before* the sibling plan's fix, a shutdown-interruption that fires while
  `_start_servers()` is still in its per-server loop (i.e. `_servers_started` is still `False`)
  would raise `StartupInterrupted` without triggering rollback — reproducing the sibling's orphan
