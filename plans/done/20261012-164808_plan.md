## Goal
- Make the relationship between `pending_approval_id` and `pending_approval_task_id` explicit in startup approval recovery: document, in the code and in the startup document, why `pending_approval_id` is assigned without a stale-check while `pending_approval_task_id` is guarded, and pin that contract with a test, without changing recovery behavior.

## Priority
Low

## Scope
- **In-Scope**:
  - A comment in `ApprovalRecovery.recover()` stating why the id assignment needs no stale-check.
  - One characterization test pinning the documented contract.
  - One paragraph in the startup document's approval-restoration section.
- **Out-of-Scope**:
  - Adding a stale-check or any other behavior change to `pending_approval_id` (the Issue's alternative, rejected on evidence below).
  - The existing `pending_approval_task_id` guard, `find_all_pending_approvals()`, the StateStore, and other startup checks.
  - The wording of the existing "Overwriting pending_approval_task_id" log line for equal values.

## Background
- `ApprovalRecovery.recover()` assigns `ctx.turn.pending_approval_id` unconditionally (`scripts/agent/startup_approval_recovery.py:49`) and guards `pending_approval_task_id` against overwriting an existing value (lines 50 to 70).
- Issue `issues/20261012-124847_start005_startup-approval-recovery-overwrites-pending_approval_id-without-checking-current-turn-state.md` asks to confirm the intent and either document the asymmetry as safe by construction or align the two, with a rule for choosing: if `recover()` runs once at startup against a fresh turn, document; otherwise add the guard.

## Problem
Verified against current source (`Confirmed by repository evidence`):
- **The rule's condition holds, so the asymmetry is safe by construction (Issue Unresolved Question 1)**:
  - `recover()` has one caller: `StartupOrchestrator.run()` (`scripts/agent/startup.py:77`), and `StartupOrchestrator` is instantiated once, in `AgentREPL.run()` (`scripts/agent/repl.py:120`).
  - Before that call nothing sets either field: they are written only at runtime, by the workflow engine adapter when an approval gate pauses a turn (`workflow_engine_adapter.py:345`) and by `/approve` and `/reject` (`commands/cmd_workflow.py`); no turn runs during startup. The factory and component initialization do not touch them.
  - So both fields are unset when `recover()` runs.
- **The two fields have different roles, which explains the different handling**: `ctx.turn.pending_approval_id` is documented as a "display cache for the current pending approval ID", populated at startup and re-derived from durable storage, with `StateStore.find_latest_pending_approval()` as the authoritative source (`scripts/agent/context.py:186-190`); `pending_approval_task_id` is the "task ID to resume after /approve" (`context.py:191-192`), a live value that must not be clobbered. Overwriting a display cache with the authoritative record is correct; overwriting a live resume target is not. `docs/23_agent/agent_03_03_turn-processing-flow-workflow-engine.md` agrees ("in-memory only; approval is persisted in `workflow.sqlite`").
- **The `pending_approval_task_id` guard is reachable only in tests**: every existing recovery test starts with `pending_approval_id` set to `None`, and the cases that pre-set `pending_approval_task_id` (for example `test_startup_recovery_keeps_existing_pending_approval_task_id`) construct a non-fresh state that production never produces at startup. No existing test pins `pending_approval_id` in a non-fresh state, so aligning would not break a test, but it would add a branch for an unreachable state.
- **Observation, not changed here**: in that unreachable non-fresh state the code would keep the old task id and still set the recovered approval id, so the pair could describe different approvals. This is the one real inconsistency, and it is dormant.
- **Documentation**: the startup document describes only the task-id guard (`agent_10_01_operations-and-observability-startup-and-health.md:76`); the operations and troubleshooting document only links to that section, so it needs no change.

## Reason for change
- The asymmetry looks like an oversight to a reader of `recover()`, and a future caller or a well-meant "fix" could add a guard that silently changes the display-cache semantics. Stating the reason in the code and the document, and pinning it with a test, removes the guesswork at the lowest cost.
- Aligning the guard would add behavior for a state that cannot occur at the only call site and would blur the two fields' different roles.

## Implementation intent
- Document, do not align: add a WHY comment above the id assignment and a short paragraph in the startup document; add one test that makes the contract executable.
- The comment states the precondition (single call at startup, before any turn) and the roles (display cache refreshed from the authoritative record versus the live resume target), and that the guard below protects only the latter.
- Keep the code diff to comment lines.
