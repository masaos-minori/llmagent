# Plan: Document ToolExecutor concurrency_limits behavior for future extension

## Goal
Document the behavior of `ToolExecutor.__init__()` when `concurrency_limits` is not set, ensuring developers understand the implications for future extensions.

## Priority
Low

## Scope
- **In-Scope**: Updating the docstring of `ToolExecutor.__init__()` to document the behavior when `concurrency_limits` is not set; ensuring consistency between documentation and implementation.
- **Out-of-Scope**: Changing the retry logic itself; modifying other transport layers; changing error handling behavior.

## Background
`scripts/shared/tool_executor.py` line 43-54:
```python
def __init__(
    self,
    http: httpx.AsyncClient,
    server_configs: dict[str, McpServerConfig],
    concurrency_limits: dict[str, int] | None = None,
    lifecycle: LifecycleProtocol | None = None,
) -> None:
    """Initialize with HTTP client and server configurations."""
    super().__init__(http, server_configs, concurrency_limits, lifecycle)
    self._server_configs = server_configs
    self._resolver = ToolRouteResolver()
```

And line 122-123:
```python
self._ensure_semaphores()
sem = (self._semaphores or {}).get(server_key)
```

When `concurrency_limits` is not set, `_semaphores` remains `None`, which means no concurrency limiting is applied. This is intentional in the current design, but the docstring doesn't mention this behavior.

## Problem
Developers who extend the system may assume that `concurrency_limits` can be dynamically changed later, but the current design doesn't support this. This can lead to confusion during debugging and incident investigation.

## Reason for change
Documentation clarity improvement. Ensuring consistent documentation prevents misinterpretation during code reviews and refactoring.

## Implementation intent
Update the docstring of `ToolExecutor.__init__()` to document the behavior when `concurrency_limits` is not set.

- REQ-002: Documentation remains consistent with implementation

## Design
Path A classification applies: direct verification inspection only, no architecture/dependency/historical/operational analysis.

Two possible approaches:
1. **Update docstring**: Add clarification about `concurrency_limits` behavior to the docstring:
   ```python
   def __init__(
       self,
       http: httpx.AsyncClient,
       server_configs: dict[str, McpServerConfig],
       concurrency_limits: dict[str, int] | None = None,
       lifecycle: LifecycleProtocol | None = None,
   ) -> None:
       """Initialize with HTTP client and server configurations.

       Args:
           http: AsyncHTTPClient instance for making requests.
           server_configs: Server configurations for MCP servers.
           concurrency_limits: Optional concurrency limits per server. If None, no
               concurrency limiting is applied. Note: this value is fixed at
               initialization time and cannot be changed later.
           lifecycle: Optional lifecycle protocol for MCP servers.
       """
   ```
2. **Keep current documentation**: Keep the current documentation as-is, since the parameter-level docstring already correctly explains the `strict_mode` behavior.

Approach 1 is preferred as it provides better visibility for developers who only read the class-level docstring.
