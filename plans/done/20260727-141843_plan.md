## Goal

Fix `StartupOrchestrator._recover_pending_approvals()` in `scripts/agent/startup.py` so it actually selects the most recent (newest `created_at`, tie-broken by highest `rowid`) pending approval on restart, instead of the oldest, and add a regression test that pins this behavior.

## Scope

**In-Scope:**
- `scripts/agent/startup.py:518-519` — change `results[-1]` to `results[0]` (since `find_all_pending_approvals()` already returns rows `ORDER BY a.created_at DESC, a.rowid DESC`, `results[0]` is the newest).
- Verify comment at `scripts/agent/startup.py:518` and log/warning text at `scripts/agent/startup.py:529-540` still accurately describe the selection after the fix (no wording change expected, but must be verified).
- Update the existing test `tests/test_startup.py::TestStartupOrchestratorRecoverPendingApprovals::test_startup_recovery_shows_last_of_multiple_pending_approvals` — its mocked `find_all_pending_approvals` return value is currently ordered oldest-then-newest (`[("task-old", approval1), ("task-new", approval2)]`), which only produces the correct assertion (`approval-new`) because the *old* buggy code read `results[-1]`. Once the code reads `results[0]`, this mock ordering must be flipped to `[("task-new", approval2), ("task-old", approval1)]` to stay consistent with the real DESC-ordered contract of `find_all_pending_approvals()`, while keeping the same assertions (`approval-new`/`task-new` selected).
- Add a new regression test (in `tests/test_startup.py`, alongside `TestStartupOrchestratorRecoverPendingApprovals`) that creates/mocks multiple pending approvals with distinct `created_at`-implied ordering and asserts the newest (first in the DESC-ordered list) is selected, and that it fails against the old `results[-1]` behavior.

**Out-of-Scope:**
- `scripts/agent/workflow/approval_ops.py::find_all_pending_approvals()` — no change; requirement's "option 2" (flip `ORDER BY` to `ASC`) is explicitly de-prioritized since option 1 (minimal fix) is sufficient and no other caller depends on `DESC` ordering.
- `find_latest_pending_approval()` (the single-row helper near line 170 of `approval_ops.py`) — already correctly uses `LIMIT 1` with `DESC` ordering and `rows[0]`; out of scope, not affected by this bug.
- Any other approval/workflow command handling (`/approve`, `/reject` implementations in `agent/commands/`) — unaffected, they operate on an approval_id already resolved.
- Broader refactor of `StartupOrchestrator` or `approval_ops.py`.
