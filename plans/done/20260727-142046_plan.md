## Goal

Make `StartupOrchestrator._spawned_subprocesses` (and the third element of `run()`'s
return tuple) actually reflect the subprocesses spawned by `_start_servers()`, on both
the success and exception paths, so the existing `repl.py` fallback-termination loop can
do real work when `lifecycle.shutdown_all()` fails.

## Scope

**In-Scope:**
- `scripts/agent/startup.py` — `StartupOrchestrator.run()`:
  - Line 68: capture the return value of `await self._start_servers()` into
    `self._spawned_subprocesses` instead of discarding it.
  - Line 89: return `self._spawned_subprocesses` instead of a hardcoded `[]` on the
    success path.
- A regression test (in `tests/test_startup.py`, alongside the existing
  `TestStartupRollback` class) that injects a failure in a later startup step and in
  `lifecycle.shutdown_all()`, and asserts `self._spawned_subprocesses` is populated
  with the fake processes after `run()` raises.
- A success-path test asserting `run()`'s third return value equals the list of
  processes actually spawned by `_start_servers()`.

**Out-of-Scope:**
- `scripts/agent/repl.py` — no code changes. The `finally` block's termination loop
  (lines 743-752) is left exactly as-is per the requirement's Implementation
  Instructions #3-#4. Note: this file's `finally` block currently runs the
  termination loop unconditionally (on both success and failure), which is a
  **separate, already-tracked bug** — see Assumptions and Risks below.
- Any change to `lifecycle.shutdown_all()` or `_ServerLifecycleRouter._http_procs`
  internal tracking.
- Any change to which processes get spawned or how `_start_servers()` builds its
  `spawned` list (`scripts/agent/startup.py:128-167`) — that logic is already correct.
- Any change to `_verify_mcp_health`, `_check_services`, `_recover_pending_approvals`,
  `_setup_prompt`, or other startup steps.

## Assumptions

1. `_start_servers()` (`scripts/agent/startup.py:128-167`) already returns the correct
   `spawned` list of `subprocess.Popen` objects — verified by direct reading of the
   method; no changes are needed there.
2. No other caller depends on `run()`'s third tuple element always being `[]` on
   success. Verified via `grep -rn "StartupOrchestrator" scripts/ tests/`: the only
   production call site is `scripts/agent/repl.py:736-739`
   (`self._cmds, self._orchestrator, _spawned_subprocesses = await startup.run()`),
   which already unpacks the value generically and does not assume it is empty.
3. **This plan is scoped strictly to `requires/20260727-132138_require.md`.** A
   sibling requirement, `requires/20260727-132720_require.md` (source issue
   `issues/20260727_06_issue.md`), documents that `AgentREPL.run()`'s `finally` block
   (`scripts/agent/repl.py:743-752`) unconditionally terminates every process in
   `all_procs`, regardless of whether `startup.run()` succeeded or raised — the
   termination loop is not gated on failure. Today that loop is inert only because
   `all_procs` is always empty (the bug this plan fixes). Once this plan's fix lands,
   `all_procs` will be non-empty on **successful** startups too, and — until the
   sibling requirement is also implemented — `AgentREPL.run()` will immediately
   `terminate()` every just-spawned, healthy MCP HTTP subprocess after every
   successful startup, breaking all HTTP-subprocess-mode MCP tools for the rest of
   the session. This plan's implementation MUST NOT be deployed independently of the
   corresponding plan for `requires/20260727-132720_require.md`; the two
   implementation procedures should land in the same change set (this plan's fix
   first or together, never this plan's fix alone in production). See Risks below.
4. Existing tests in `tests/test_startup.py::TestStartupRollback` (lines 498-576) stub
   `orch._start_servers = AsyncMock()` with no explicit `return_value`; after this fix,
   `self._spawned_subprocesses` in those tests will be set to the `AsyncMock`'s
   default `MagicMock` return value rather than a real list, but since none of those
   tests assert on `_spawned_subprocesses` or iterate over it, they will not break.
5. `tests/test_repl.py` (lines 466-469, 492-495, 831-837) mocks
   `agent.startup.StartupOrchestrator` itself (not `_start_servers()`) and hardcodes
   `run()`'s return tuple, so those tests are unaffected by this change.

## Risks

- **Risk**: Deploying this fix without also fixing `scripts/agent/repl.py`'s
  unconditional `finally`-block termination loop (tracked separately in
  `requires/20260727-132720_require.md`) causes `AgentREPL.run()` to terminate every
  successfully-started MCP HTTP subprocess immediately after a healthy startup,
  breaking all HTTP-subprocess-mode MCP tools for the session.
  → **Mitigation**: Documented explicitly in Assumptions #3 above and cross-referenced
  in Traceability; the implementation procedure derived from this plan must not be
  deployed to production ahead of or without the implementation procedure for
  `requires/20260727-132720_require.md`. Recommend landing both in the same commit/PR
  or in immediate succession with a combined test run
  (`uv run pytest tests/test_startup.py tests/test_repl.py -q`) before either reaches
  production.
- **Risk**: `self._spawned_subprocesses` being set only inside the `try` block means
  if `_start_servers()` itself raises before returning, the attribute keeps its
  pre-call default (`[]` from line 66), so no partially-spawned processes from within
  `_start_servers()`'s own loop are tracked in that specific sub-case.
  → **Mitigation**: This matches the existing, explicitly-scoped behavior in the
  requirement's Implementation Instructions #1 ("keep the existing
  initialization... as the pre-call default, in case `_start_servers()` itself raises
  before returning") — `_start_servers()`'s internal loop already catches
  `(OSError, RuntimeError)` per-server and continues (`scripts/agent/startup.py:154-166`),
  so it only propagates an exception in `SecurityProfile.PRODUCTION` after having
  already appended failed-to-verify processes is not a concern; this is accepted
  as out-of-scope per the requirement and not a new regression introduced by this
  plan.
- **Risk**: New unit tests could become flaky or brittle if they over-mock
  `StartupOrchestrator` internals.
  → **Mitigation**: Follow the existing `TestStartupRollback` pattern
  (`tests/test_startup.py:498-576`), which already stubs individual coroutine methods
  (`_start_servers`, `_check_services`, etc.) rather than the whole class, keeping new
  tests consistent with established conventions and low-maintenance.
