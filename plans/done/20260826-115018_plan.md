## Goal
- Make each declared configuration value equal the value actually enforced at runtime,
  for two independent "declared vs. enforced" defects: (1) `FileReadConfig` silently

## Background
- `config/file_read_mcp_server.toml`'s own inline comment (`# max_read_bytes: maximum
  bytes read per file`) states the key is bytes, but `FileReadConfig.from_dict`
  (`scripts/mcp_servers/file/read_models.py`) divides the raw value by 1024 before
  storing it, and `build_service` (`scripts/mcp_servers/file/read_service.py`)
  multiplies it back by 1024 — a round-trip that silently truncates.
- `RagPipelineConfig` (`scripts/mcp_servers/rag_pipeline/rag_pipeline_models.py`) is
  the sole config DTO for `rag-pipeline-mcp`; its dataclass field defaults are meant to
  be sensible fallbacks for when a key is absent from
  `config/rag_pipeline_mcp_server.toml`, but five of them currently diverge from that
  TOML's real operational values, which today are always supplied so the divergence has
  no live effect — until the TOML is trimmed.
- Both discrepancies are already documented as "[Explicit in code]" facts in
  `docs/04_mcp_04_01_web-search-file-read-github.md` (Implementation Details,
  file-read-mcp) and `docs/03_rag_05_1-configuration-reference.md` (rag-pipeline-mcp
  configuration table), per `rules/coding.md`'s "Current behavior" classification —
  this Plan reclassifies both from "documented current behavior" to "implementation fix
  required," consistent with that rule's default for ambiguous cases.

## Problem
- **M-3 (unit mismatch), confirmed by repository evidence**: with the default
  `max_read_bytes = 1000000` in `config/file_read_mcp_server.toml`,
  `FileReadConfig.from_dict` computes `1000000 // 1024 = 976` and stores it in
  `max_file_size_kb`; `build_service` then computes `976 * 1024 = 999424`. The
  operator-configured value of 1,000,000 bytes is enforced as 999,424 bytes — a silent,
  undocumented-to-the-operator 576-byte shortfall purely from integer-division
  round-tripping.
- **M-7 (default divergence), confirmed by repository evidence**: exactly five
  `RagPipelineConfig` fields have a code default that differs from
  `config/rag_pipeline_mcp_server.toml`'s current value:

  | Field | Code default | Operational TOML value |
  |---|---|---|
  | `top_k_search` | `5` | `20` |
  | `top_k_rerank` | `10` | `15` |
  | `rag_min_score` | `0.0` | `2.0` |
  | `semantic_cache_max_size` | `128` | `100` |
  | `refiner_max_chars_per_chunk` | `800` | `300` |

  All other `RagPipelineConfig` fields with a meaningful default (i.e. excluding the
  environment-specific `llm_url`/`embed_url`/`rag_db_path`/`sqlite_vec_so`/
  `rag_auth_token` empty-string sentinels) were individually checked against the TOML
  and match. No harm today because the TOML always supplies these five values, but a
  future edit that removes or "simplifies" the TOML would silently change production
  behavior with no test to catch it.

## Reason for change
- The unit mismatch actively misleads whoever edits `max_read_bytes`, since the key
  name promises bytes but the enforced value differs from what was configured.
- The default divergence has a single point of failure: nothing in the codebase
  asserts that the TOML and the code defaults agree, so a future TOML cleanup could
  silently change RAG retrieval behavior (`top_k_search`/`top_k_rerank`/`rag_min_score`
  control what gets retrieved and ranked) with no test failure to flag it.

## Implementation intent
- **M-3**: make `max_read_bytes` mean exactly what its name says — remove the hidden
  KB round-trip entirely rather than renaming the TOML key. Interpret the configured
  value as bytes end-to-end, and rename the `FileReadConfig` dataclass field itself
  from `max_file_size_kb` to `max_read_bytes` so the Python attribute name also stops
  lying about the unit. Add a test that a non-1024-aligned byte count survives
  unchanged, proving no hidden conversion remains.
- **M-7**: set `RagPipelineConfig`'s five divergent dataclass field defaults (and their
  matching `from_dict` fallback literals) to the current operational TOML values, so
  the code and the TOML agree by construction. Add a guard test that pins both sides to
  the same values so a future edit to either one without the other fails loudly.

### M-3 decision: interpret `max_read_bytes` as bytes; drop the KB conversion (do not rename the key)
Resolved using repository evidence, not left as an Unknown:
- `config/file_read_mcp_server.toml`'s own inline comment already states the key is
  bytes ("`max_read_bytes`: maximum bytes read per file") — the TOML author's intent is
  unambiguous and predates the current from_dict implementation.
- A precedent in the same codebase shows the alternative naming convention already in
  use elsewhere: `github_mcp_server.toml`'s `max_file_size_kb` field is named for KB and
  behaves as KB (`github_models_config.py`, `github_service_security.py`) — this project
  already has a correctly-named KB config key when KB semantics are intended, which is
  evidence against renaming `max_read_bytes` to a new KB-suffixed key; the simpler,
  lower-risk fix is to make the byte-named key behave as bytes.
- No caller depends on the KB intermediate value for anything other than immediately
  multiplying it back by 1024 (`read_service.py` `build_service`); removing the
  round-trip is behavior-preserving for every caller except the intended fix itself.
- The Issue's own Fix Intent states a preference for bytes ("Prefer bytes to match the
  existing key name; backward compatibility may be dropped per project policy"), and
  this project has an established no-compat-shim policy (`tools/check_compat_shims.py`)
  that supports dropping the old truncating behavior outright rather than
  version-gating it.
- Concretely: `FileReadConfig.from_dict` keeps calling
  `get_typed(d, "max_read_bytes", int, "an integer", default=1024000)` but stores the
  result directly (no `// 1024`) into a field renamed `max_read_bytes` (dataclass
  top-level default also changes from `1000` to `1024000` so that
  `FileReadConfig()`'s direct-construction default matches `from_dict({})`'s default);
  `read_service.py`'s `build_service` changes
  `max_read_bytes=cfg.max_file_size_kb * 1024` to `max_read_bytes=cfg.max_read_bytes`.

### M-7 decision: align code defaults to the operational TOML values (not just annotate)
Resolved using repository evidence: the Issue's Fix Intent offered two options — align
defaults, or annotate each divergence and centralize canonical values. This Plan takes
the align option because (a) the codebase has no existing "centralized canonical
config values" pattern to extend, so introducing one would be a larger, unrequested
architectural change; (b) aligning the defaults directly makes `RagPipelineConfig()`
itself the single source of truth with zero extra indirection, satisfying the Issue's
underlying "no single source of truth" concern with the smallest change; (c) a
straightforward guard test (`T-2`) is sufficient to prevent future re-divergence without
any new abstraction.
