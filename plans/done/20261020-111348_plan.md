# Plan: Event Bus auth token environment indirection and a startable `setup_services.sh` Event Bus block

## Goal
- Make the shipped Event Bus configuration startable without writing a secret into a deployed TOML
  file, and make `deploy/setup_services.sh` actually able to launch `eventbus.app`: `auth_token`
  becomes an environment reference, the Event Bus package resolves that reference before its
  fail-closed validation, the deployment script loads `.env` and fails fast when the referenced
  variable is missing, and the Event Bus is started with the script's own production `uv run`
  invocation instead of a bare `python`.

## Priority
High

## Scope
- **In-Scope**:
  - `config/eventbus.toml`: `auth_token = "${ENV:EVENTBUS_AUTH_TOKEN}"`; no literal token value in
    any file under `config/`.
  - `scripts/eventbus/config.py`: resolve `${ENV:...}` references for all six token keys
    (`auth_token`, `publisher_token`, `consumer_token`, `operator_token`, `monitoring_token`,
    `admin_token`) through `shared.config_utils.resolve_env_ref` before the non-empty validation,
    keeping the fail-closed behavior and producing an error that names the unset variable.
    This is a measured deviation from the source issue's assumption; see Background and Design.
  - `deploy/load_env.sh` (new): the `.env` parse and required-variable collection semantics already
    implemented in `deploy/start_agent.sh`, extracted as shell functions with no `/opt/llm`
    hardcoding so a deployment-host-independent test can execute them.
  - `deploy/setup_services.sh`: source `deploy/load_env.sh`, load `/opt/llm/.env` or `<repo>/.env`
    without overriding already-exported variables, fail fast when a variable referenced by the
    Event Bus configuration is unset or empty, start the Event Bus with
    `uv run "${UV_PROD_FLAGS[@]}"`, and present the bearer credential on the Event Bus health probes.
  - Tests: environment-reference resolution (variable set / unset / set-but-empty, shared token and
    per-role tokens) in `tests/eventbus/test_eventbus_config.py`; the `.env` gate behavior of
    `deploy/load_env.sh` in `tests/deploy/test_load_env_gate.py`; the subprocess-environment allowlist
    boundary in `tests/agent/test_http_lifecycle_env_allowlist_integration.py` (`REQ-008`, added by the
    20261020-115153 amendment).
  - Documentation: `docs/24_eventbus/eventbus_07_configuration-and-operations.md` and
    `docs/90_deployment/deployment_01_deployment.md`.
- **Out-of-Scope**:
  - Starting or configuring `embed-llm`, and the `setup_services.sh` remote-LLM health gate
    (`issues/20261019-210938_ebops002_setup_services_llm_gate_blocks_eventbus.md`).
  - Writing a real token value into `/opt/llm/.env` or any other deployed file, and starting the
    Event Bus on the production host (owner decision 2026-10-20: repository-side only; production
    validation requires separate approval).
  - Changing `deploy/start_agent.sh`'s MCP token gate semantics (it keeps its own inline copy).
  - Widening `_DEFAULT_ALLOWED_ENV_VARS` in `scripts/agent/http_lifecycle_command_validator.py`: the Event
    Bus control-plane token stays out of every MCP subprocess environment (owner decision 20261020-115153).
  - Wiring a publisher or consumer into the agent, and the unused `publish_url` / `subscribe_url`
    keys of `scripts/agent/eventbus_client.py`, `scripts/agent/eventbus_subscriber.py`, and
    `scripts/agent/eventbus_topic_admin_client.py`.
  - Changing Event Bus roles, token semantics, `consumer_authorization` mappings, or the envelope schema.
  - Running the Event Bus as a systemd unit or any supervisor outside `deploy/`.

## Background
- Found on 2026-10-19 while investigating why `deploy/setup_services.sh` never produced an Event Bus
  process (`/opt/llm/logs/eventbus.log` did not exist). Source issue:
  `issues/20261019-210937_ebsec001_eventbus_auth_token_startup_block.md`.
- Verified runtime state on 2026-10-20: nothing listens on 8015 (`lsof -i :8015` and `ss -ltnp` both
  empty), no `eventbus` process exists, `/opt/llm/.env` is mode 600 / 1004 bytes and contains only the
  eleven `MCP_*_AUTH_TOKEN` variables, and `/opt/llm/config/eventbus.toml` is identical to the
  repository copy (`auth_token = ""` at line 13, per-role tokens empty at lines 24-28).
- `deploy/deploy.sh:165` copies `config/eventbus.toml` over `/opt/llm/config/eventbus.toml` on every
  deploy, so a token written into the deployed file by an operator is silently lost. Every other
  control-plane credential in the repository is injected through `${ENV:...}`
  (`config/agent.toml:357-441`, `config/*_mcp_server.toml`).
- **Measured correction of the source issue's Implementation Intent.** The issue states that
  `_load_config_from_path` already builds config through `shared.config_loader.ConfigLoader`, so
  "`${ENV:...}` expansion is available without new code in the Event Bus package" (issue lines 65-67),
  and instructs "Stop and report if `${ENV:...}` expansion does not reach `auth_token` before line
  308's check" (issue line 160). Probe `/tmp/opencode/probe_eventbus_env_ref.py` (2026-10-20):
  - `scripts/shared/config_loader.py` contains no `os.environ` reference at all; it does not expand
    `${ENV:...}`.
  - Expansion lives in `scripts/shared/config_utils.py::resolve_env_ref` (line 22) and `get_str`
    (line 42), and every consumer calls it in its own model layer
    (`scripts/mcp_servers/cicd/cicd_models.py:39`, `scripts/mcp_servers/file/read_models.py:47`, and
    nine sibling call sites). `scripts/eventbus/config.py` does not import `shared.config_utils`.
  - With `auth_token = "${ENV:EVENTBUS_AUTH_TOKEN}"`: variable set → `cfg.auth_token ==
    '${ENV:EVENTBUS_AUTH_TOKEN}'`; variable unset → same literal, no error; variable set but empty →
    same literal, no error. The placeholder string would become the real bearer token registered in
    `scripts/eventbus/auth.py::_TOKEN_PRINCIPAL_MAP`, and line 308's non-empty check would be
    bypassed.
- Owner decision (2026-10-20): apply the resolution in `scripts/eventbus/config.py` for all six token
  keys; repository-side implementation only.

## Problem
- The Event Bus cannot start as shipped: `config/eventbus.toml:13` ships `auth_token = ""` and
  `scripts/eventbus/config.py:308` rejects it, and `deploy/setup_services.sh:133-135` launches
  `python -m eventbus.app` with the system interpreter rather than the project `uv run` invocation the
  rest of the script uses, so the background process dies before binding 127.0.0.1:8015.
- The only documented ways to supply the token are "its environment or configuration file"
  (`docs/24_eventbus/eventbus_07_configuration-and-operations.md`, Token Distribution). Because
  `setup_services.sh` loads no `.env`, the environment path is unreachable from the deployment
  script, leaving the operator only the deployed-TOML edit that `deploy.sh` overwrites.
- Adding the environment reference without resolving it in the Event Bus package would convert a
  fail-closed startup guard into a fail-open one and would register the placeholder text as a
  control-plane credential.

## Reason for Change
- Deployment failure: the documented service-startup script cannot start a service it claims to start.
- Configuration consistency: every other control-plane credential uses `${ENV:...}`; this one is a
  literal empty string in a deployed file.
- Security posture: without resolution the placeholder becomes a usable admin-scope bearer token, and
  the non-empty guard stops applying.
- Usability: `scripts/agent/eventbus_*.py` clients exist and are tested, but no startable service
  exists to point them at.

## Implementation Intent
- Keep the repository convention rather than inventing one: the config file holds the reference, the
  owning package resolves it in its own model layer (the same shape every MCP server uses), and an
  unset variable produces an actionable `ValueError` that names the variable.
- Do not change `ConfigLoader`: expanding it would alter config loading for every layer and would move
  resolution away from the owning-model convention that `ADR-002` records.
- Reuse `deploy/start_agent.sh`'s `.env` semantics exactly (existing exported variables win, unsafe
  lines skipped with a warning, permission warnings, secret values never printed) by lifting them into
  `deploy/load_env.sh` as functions that `deploy/setup_services.sh` sources; `start_agent.sh` is not
  modified.
- Scope the pre-check to what this script actually launches: the variables referenced by the Event Bus
  configuration file the Event Bus process will read, not the full MCP token set (which
  `start_agent.sh` already enforces).
- Keep the fail-closed behavior and the loopback-bind checks intact.

## Requirements
- `REQ-001`: `config/eventbus.toml` supplies `auth_token` as `"${ENV:EVENTBUS_AUTH_TOKEN}"` and names
  the variable in a comment; no file under `config/` contains a literal token value.
- `REQ-002`: `scripts/eventbus/config.py` resolves `${ENV:...}` references for the six token keys
  before validating them, so a set variable yields its value, an unset variable raises `ValueError`
  naming the variable, and a variable set to an empty string still reaches the existing
  `'auth_token' must not be empty` error.
- `REQ-003`: `deploy/setup_services.sh` loads `/opt/llm/.env` (or `<repo>/.env`) without overriding
  already-exported variables, and stops with a `[FATAL]` message that names each missing or empty
  variable and shows `openssl rand -hex 32` as the generation example, before any Event Bus process is
  launched.
- `REQ-004`: `deploy/setup_services.sh` starts the Event Bus with
  `PYTHONPATH=/opt/llm/scripts UV_SYSTEM_CERTS=true uv run "${UV_PROD_FLAGS[@]}" python -m eventbus.app`
  so the process uses the production venv.
- `REQ-005`: The script's Event Bus health probes present the bearer credential, because `/health`
  requires the MONITORING role and returns 401 without it.
- `REQ-006`: `tests/eventbus/test_eventbus_config.py` locks the environment-reference behavior and
  fails if the resolution step is removed; `tests/deploy/test_load_env_gate.py` locks the `.env` gate
  semantics with no `/opt/llm` access and no network.
- `REQ-007`: The Event Bus configuration document and the deployment document state the variable name
  and where the token is set, and no wording implies the operator must edit the deployed TOML file.
- `REQ-008`: `tests/agent/test_http_lifecycle_env_allowlist_integration.py` asserts the allowlist over the
  configurations an agent subprocess server actually reads, and states explicitly that the Event Bus token
  names are not admitted into that environment; `_DEFAULT_ALLOWED_ENV_VARS` itself is not modified.

## Acceptance criteria
- `AC-1` (REQ-002, REQ-004): With `EVENTBUS_AUTH_TOKEN` defined in `.env`, `bash deploy/setup_services.sh`
  reaches `--- Event Bus 起動 ---`, launches `eventbus.app` through `uv run "${UV_PROD_FLAGS[@]}"`, and a
  bearer-authenticated `GET /health` request to 127.0.0.1:8015 returns a health response. Deferred to a
  separately approved production pass; verified offline in this cycle by `bash -n` plus the script-level
  gate test, and recorded as unverified in Execution Status until that pass runs.

  naming `EVENTBUS_AUTH_TOKEN` and showing `openssl rand -hex 32` as the generation example, prints no
  secret value, and leaves no Event Bus process listening.
- `AC-3` (REQ-001, REQ-007): `grep -n 'auth_token' config/eventbus.toml` shows the environment reference
  and no literal token value anywhere under `config/`, and both documents name `EVENTBUS_AUTH_TOKEN` as
  the place the token is set.
- `AC-4` (REQ-004): The Event Bus launch line in `deploy/setup_services.sh` is the production `uv run`
  invocation, and `bash -n deploy/setup_services.sh` succeeds.
- `AC-5` (REQ-002, REQ-006): `uv run pytest tests/eventbus -q` passes, and the new environment-reference
  test fails when the resolution step in `scripts/eventbus/config.py` is reverted.
- `AC-6` (REQ-002, Constraints): `uv run lint-imports` reports all contracts kept, and the loopback-bind
  and cross-field validations in `scripts/eventbus/config.py` keep their current messages.
- `AC-7` (REQ-008): `uv run pytest tests/agent/test_http_lifecycle_env_allowlist_integration.py -q` passes

  fails if `EVENTBUS_AUTH_TOKEN` is ever added to `_DEFAULT_ALLOWED_ENV_VARS`.

## Design
- **Where resolution belongs.** `ADR-002` Decision 9 permits the shared Config Loader while keeping
  per-process file ownership, and the repository's established shape is: the config file holds a
  `${ENV:...}` reference and the owning process's model layer calls `shared.config_utils` to resolve it.
  Resolving inside `ConfigLoader` would change loading for `agent`, `db`, `mcp_servers`, and `rag` in one
  step and would break that convention, so resolution is added to `scripts/eventbus/config.py` instead.
- **Resolution point and order.** `load_config` validates unknown keys (lines 283-288), required keys
  (291-295), and per-key types (298-305) before touching `auth_token` (307-309). Resolution is inserted
  after the type loop and before the non-empty check, so type and unknown-key diagnostics keep their
  current precedence. All six token keys are resolved through `resolve_env_ref`, which returns the input
  unchanged when it is not a reference — literal configurations are unaffected.
- **Fail-closed chain.** Unset variable → `resolve_env_ref` raises `ValueError: Config value references
  environment variable 'EVENTBUS_AUTH_TOKEN', which is not set.` Variable set to empty → resolves to `""`
  → existing `eventbus config 'auth_token' must not be empty`. Both stop startup before any process binds
  8015, satisfying the issue's constraint that fail-closed validation must not be weakened.
- **Why all six keys.** A per-role key written as a reference would otherwise be registered verbatim in
  `_TOKEN_PRINCIPAL_MAP` as a valid role credential. Resolving all six closes that failure mode without
  changing which keys the shipped file configures.
- **`.env` gate placement.** `deploy/setup_services.sh` has `set -euo pipefail` at line 12 and defines
  `REPO_ROOT` at line 17; the gate runs after the workflow pre-flight block and before the Event Bus block,
  scanning the configuration file the Event Bus process will read. Existing exported variables win over
  `.env` values, matching `start_agent.sh`.
- **One parser, not two.** `deploy/load_env.sh` holds `parse_env_file`, `collect_required_env_vars`, and a
  `require_env_vars` gate function. `setup_services.sh` sources it; `start_agent.sh` is untouched, so the
  agent startup path is not exercised by this change. Duplication between the two deploy scripts is
  recorded as a risk rather than resolved here.
- **Authenticated probes.** `/health` resolves a bearer token and requires MONITORING
  (`scripts/eventbus/app.py:168-171`, `scripts/eventbus/auth.py:201-235`); an anonymous probe returns 401
  (or 500 when `auth_token` is unconfigured). The two probe lines in the Event Bus and health-check blocks
  must send `Authorization: Bearer ${EVENTBUS_AUTH_TOKEN}`, otherwise the script reports a failure for a
  service that started correctly.
- **Deployment consequence.** Because `deploy.sh:165` re-copies `config/eventbus.toml`, the environment
  variable becomes the only durable place for the token, which is the intended posture.

## Risks
- **Risk**: the resolution step changes `load_config`'s error surface for an unset variable (a new
  `ValueError` message instead of the existing `'auth_token' must not be empty`) → **Mitigation**: `T-1`
  asserts both messages, one for the unset case and one for the set-but-empty case, and the existing empty
  message stays reachable.
- **Risk**: adding a reference to `config/eventbus.toml` could break a caller that reads the file directly
  → **Mitigation**: `grep -rn "eventbus.toml" scripts/ tests/ deploy/ tools/` shows only
  `scripts/eventbus/config.py`, `scripts/eventbus/auth.py` message text, and test fixtures; no other reader.
- **Risk**: `deploy/setup_services.sh` gates on variables the Event Bus will actually need, so a host with
  no `.env` now fails earlier than before → **Mitigation**: the failure is actionable (names the variable and
  shows a generation command) instead of a dying background process, which is the issue's stated goal; the
  gate is scoped to the Event Bus configuration only.
- **Risk**: two implementations of the same `.env` semantics (`start_agent.sh` inline, `load_env.sh` shared)
  can drift → **Mitigation**: `tests/deploy/test_load_env_gate.py` pins the shared implementation's behavior,
  `UNK-02` records the consolidation decision, and a follow-up issue candidate is listed here rather than
  performed.
- **Risk**: `AC-1` and `AC-2`'s runtime half cannot be verified this cycle because the token write and the
  Event Bus start are deferred pending owner approval, and the remote-LLM health gate currently aborts
  `setup_services.sh` before the Event Bus block is reached (`ebops002`) → **Mitigation**: repository-side
  validation covers the logic, the runtime ACs stay `Pending` in Execution Status, and `ebops002`'s Plan is
  sequenced next so the two can be verified in one production pass later.
- **Risk**: the deployed `eventbus.toml` is overwritten on every deploy → **Mitigation**: intended posture;
  documented in `deployment_01_deployment.md` so operators set the variable in `/opt/llm/.env` (mode 600).
- **Risk**: narrowing the allowlist-coverage scan could hide a future config that really does need a new
  allowlist entry → **Mitigation**: the scan still covers `agent.toml` and every `*_mcp_server.toml` (the
  files a subprocess server reads and the only ones whose `${ENV:...}` names reach `filter_env`), and the new
  exclusion case fails loudly if an `EVENTBUS_*` token name is ever admitted.
