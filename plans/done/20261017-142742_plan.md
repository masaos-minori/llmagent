# Plan — Block ephemeral-key injection through session history restore

## Goal
Close the ephemeral-key control bypass in `ConversationState.replace_history()` so
tampered/corrupted session rows cannot inject reserved ephemeral keys (`_ephemeral`,
`_memory_injected`) into conversation history. During restore, treat every restored
message as untrusted so an embedded trusted `source` can no longer authorize ephemeral
keys; the key is rejected/stripped and the filter fails closed.

## Priority
High

## Scope
- **In-Scope**: Making `replace_history()` independent of any `source` carried inside
  restored rows so ephemeral keys are always rejected/stripped on restore, while leaving
  the live-append path (`append_message()` / `extend_messages()` via normal turn flow)
  unchanged. Adding a regression test that restores a row carrying `source="cmd_handler"`
  + `_ephemeral` and asserts the key is absent from history.
- **Out-of-Scope**: Changing `message_schema.py`'s `validate_message`/`TRUSTED_SOURCES`
  semantics for the normal path; changing how ephemeral keys are injected during normal
  turns; the `undo` path; `extend_messages()` unless a later audit shows it shares the
  same DB-restore gap (assessed below as a live, in-process path — out of scope here).

## Background
`message_schema.py` prevents the LLM (or any untrusted source) from manipulating
ephemeral message filtering by injecting/removing keys such as `_ephemeral` or
`_memory_injected`. Ephemeral key injection is restricted to trusted sources listed in
`TRUSTED_SOURCES` (`cmd_handler`, `memory_injection`, `loop_guard`).
`docs/23_agent/agent_04_01_...state-model.md` Known Limitations notes that session
restoration via `replace_history()` allows corrupted/tampered DB rows to introduce
reserved ephemeral keys. This is an ADR-backed integrity boundary; a local
session-DB tamperer gaining the ability to inject filtered-class messages weakens
conversation-history integrity and should fail closed.

## Problem
`replace_history()` appends each message through `_append_message_locked()`:

```python
result = validate_message(check_view)
if result.success:
    self.history.append(msg)   # appends the ORIGINAL msg, keys intact
    return
```

`validate_message()` decides ephemeral-key legitimacy using the message's OWN embedded
`source` field:

```python
source = msg.get("source", "")
if source not in TRUSTED_SOURCES:
    return ValidationResult(False, ...)
allowed_ephemeral = TRUSTED_SOURCES[source]
unauthorized = ephemeral_keys - allowed_ephemeral
if unauthorized:
    return ValidationResult(False, ...)
```

`replace_history(msgs, *, source="")` is called with the default empty `source`, so
`_append_message_locked()` builds `check_view = dict(msg)` and validation reads the
**embedded** `source`. A session row carrying `source="cmd_handler"` together with
`"_ephemeral": True` therefore passes validation and is appended with the ephemeral key
intact. An actor who can write to `session.sqlite` (corruption or tampering) can inject
ephemeral-keyed messages that survive inter-turn cleanup, defeating the protection
`message_schema.py` enforces. The sanitization path (`_sanitize_message`) only strips
keys when validation fails — and validation passes here because the embedded source looks
trusted.

## Reason for change
Security-sensitive control bypass. The ephemeral-key filter is an explicit integrity
boundary (ADR-backed); a local session-DB tamperer gaining the ability to inject
filtered-class messages weakens conversation-history integrity. Fail closed.

## Implementation intent
Make session restore independent of any `source` carried inside restored rows. Treat
every restored message as untrusted by routing restore through an untrusted-source
validation path so ephemeral keys are always rejected and stripped by the existing
sanitization machinery. Prefer the minimal change that makes restore fail closed without
altering the live-append path used by trusted in-process sources. Name the boundary
(restore = untrusted vs. live append = trusted) as the design decision.

Two equivalent mechanisms satisfy this; implement one:
- **(a) Force an untrusted source on restore (recommended):** In `replace_history()`,
  call `_append_message_locked(msg, source=_UNTRUSTED_RESTORE_SOURCE)` where
  `_UNTRUSTED_RESTORE_SOURCE` is a module constant not present in `TRUSTED_SOURCES`. The
  non-empty source overwrites the embedded `source` in the validation view, so
  `validate_message()` rejects ephemeral keys and `_sanitize_message()` strips them.
  Messages without ephemeral keys still pass validation unchanged (backward compatible).
- **(b) Explicit strip:** In `replace_history()`, remove reserved ephemeral keys from
  each restored message before appending. Reuse `_ALL_EPHEMERAL_KEYS` from
  `message_schema.py` rather than hardcoding the set.

Do NOT modify `message_schema.py`'s `validate_message`/`TRUSTED_SOURCES` or the
live-append validation path.

## Requirements
- `REQ-001`: `replace_history()` does not honor an embedded `source` that would authorize
  ephemeral keys; ephemeral keys on restored rows are rejected/stripped (fail closed).
- `REQ-002`: The live-append path (`append_message()` / `extend_messages()` via normal
  turn flow) is unchanged; trusted in-process sources still work.
- `REQ-003`: Restored rows without ephemeral keys are unaffected (backward compatible).
- `REQ-004`: A regression test restores a row carrying `source="cmd_handler"` +

## Assumptions
- Restore is inherently untrusted: data comes from `session.sqlite`, which a local actor
  may corrupt or tamper with.
- No caller legitimately relies on preserving ephemeral keys across a restore/resume
  (confirmed: all three `replace_history()` callers use default `source=""`).
- Approach (a)'s non-empty sentinel source only affects ephemeral-key authorization; it
  does not alter validation of non-ephemeral messages or the appended (original) message.
- `_UNTRUSTED_RESTORE_SOURCE` must be a value guaranteed absent from `TRUSTED_SOURCES`.

## Design
Path A (affects ≤ 3 files; no public/runtime interface change; no DB schema change).
Adversarial verification (Step 2) confirmed the issue's claims against current source:
`replace_history()` (lines 170-177) calls `_append_message_locked(msg, source=source)`
with default `source=""`; `_append_message_locked()` (lines 132-156) then builds
`check_view = dict(msg)` when source is empty, so `validate_message()` reads the
message's **embedded** `source` (message_schema.py lines 68-80). A row with
`source="cmd_handler"` + `_ephemeral` passes validation and is appended with the key
intact (`self.history.append(msg)`). `_sanitize_message()` (context.py lines 61-80)
strips ephemeral keys only when source is untrusted — hence the fail-open on restore.
The fix routes restore through an untrusted source (approach (a)) so the existing
validation+sanitization machinery fails closed. Caller audit confirms no trusted-resume
path: `session_restore.py` (lines 64, 66) and `startup_prompt_setup.py` (line 114) all
use default `source=""`. `extend_messages()` (called from `tool_runner.py:424` with
in-process `denied_history`) is a live, in-process path and does not share the DB-restore
gap — assessed out of scope for this plan. The boundary (restore = untrusted vs. live
append = trusted) is the named design decision.

## Risks
- **Risk**: Forcing a non-empty sentinel source changes the `source` used in validation
  logs for restored messages (cosmetic reason-string change). → **Mitigation**: The
  sentinel is a stable internal constant; log format is unaffected beyond the reason
  string, which is acceptable for a security fix.
- **Risk**: A future caller relies on preserving ephemeral keys across restore. →
  **Mitigation**: Document the restore-is-untrusted boundary; re-audit callers if a new
  `replace_history` caller is added (UNK-01).
- **Risk**: Approach (a) overwrites the embedded `source` in the validation view for ALL
  restored messages, including non-ephemeral ones. → **Mitigation**: Embedded `source`
  only authorizes ephemeral keys; non-ephemeral validation is unchanged (verified against
  `validate_message` logic). Appended message retains its embedded `source` field
  unchanged (only the validation view is overridden).
