## Goal
- Make every Agent-side MCP `/health` probe send the server's configured Bearer token, so that authenticated MCP servers (all subprocess servers in `config/agent.toml`, now including rag-pipeline) pass startup polling, post-startup verification, liveness re-checks and `/mcp` status probes, without weakening ADR-007 INV-09.

## Priority
High

## Scope
- **In-Scope**:
  - Add one helper that builds the `Authorization: Bearer <auth_token>` header from `McpServerConfig` (empty when the token is empty).
  - Pass that header from the startup readiness poll (`_health_poll_until_ready`), the periodic liveness check (`verify_running_async`), the post-startup verification (`verify_health`, `_verify_single_health`) and the `/mcp` status probe (`_probe_mcp_health_detail`).
  - Tests that a server with a non-empty token passes each probe, and that a wrong token still fails.
  - A one-sentence documentation update describing that probes authenticate.
- **Out-of-Scope**:
  - Exempting `/health` from authentication in `attach_auth_middleware()` (rejected by the user decision of 2026-10-08; ADR-007 INV-09 stays unchanged).
  - `port_is_responding()` in `scripts/mcp_launcher.py` (treats any status below 500 as up).
  - LLM / embed-llm service health probes (`check_service_health`), which are not MCP servers.
  - Circuit-breaker logic and `HealthChecker.startup_poll()` (unused; not touched).

## Background
Found while implementing plans/done/20261008-095953_plan.md (rag-pipeline inbound authentication). Attaching the middleware to rag-pipeline made its `/health` return 401, which exposed that no Agent probe sends a token. The issue is `issues/20261008-165923_mcphealthauth01_send-the-bearer-token-in-the-post-startup-mcp-health-check.md`. The user chose, on 2026-10-08, to keep `/health` authenticated and to add the token to the probes.

## Problem
- `_health_poll_until_ready()` calls `client.get(health_url)` with no headers and accepts only HTTP 200 (Explicit in code — `scripts/agent/http_lifecycle.py` lines 404-426). With a non-empty server token the poll can never succeed, so subprocess startup times out.
- `HttpServerLifecycleManager.verify_running_async()` delegates to `HealthChecker.verify_running_async(server_key, cfg, url=url)` without client kwargs, so the liveness re-check returns False on 401 (Explicit in code — `scripts/agent/http_lifecycle.py` line 129; `scripts/agent/http_lifecycle_health_checker.py` lines 43-81).
- `verify_health()` and `_verify_single_health()` raise `RuntimeError("HTTP 401")` on any non-200 status and then abort startup with a FATAL message (Explicit in code — `scripts/agent/startup_mcp_starter.py` lines 136-139, 175-179).
- `_probe_mcp_health_detail(http, base_url)` calls `http.get(f"{base_url}/health")` with no headers, so `/mcp` status cannot read the health body of authenticated servers (Explicit in code — `scripts/agent/services/mcp_health.py` line 33; called from `scripts/agent/services/mcp_status.py` line 168).
- `attach_auth_middleware()` has no path exemption, so `/health` requires the token whenever it is non-empty (Explicit in code — `scripts/mcp_servers/server.py`; verified: with `MCP_GIT_AUTH_TOKEN=abc` the git app returns 401 on `/health`).
- `McpServerConfig.auth_token` is required to be non-empty for Agent-managed servers (Explicit in code — `scripts/shared/mcp_config.py` `_validate_auth_token`), so the token is always available to the probes.
- Whether production currently works through a different path is unknown; no deployment was inspected.

## Reason for change
- Authenticated servers cannot be started, verified or monitored by the Agent; the rag-pipeline change makes this reachable for one more server and blocks its deployment.

## Implementation intent
- Add `McpServerConfig.auth_headers()` returning `{"Authorization": f"Bearer {token}"}` or `{}`, and use it at every probe call site. Keep probe signatures backward compatible (optional `headers` argument) so existing callers and tests keep working.
- `HealthChecker.verify_running_async()` already forwards `**client_kwargs` to `httpx.AsyncClient`, so the lifecycle manager can pass `headers=` without changing the checker.

## Requirements
- `REQ-001`: `McpServerConfig` exposes a helper that returns the Bearer header for its `auth_token` (empty dict for an empty token). (`scripts/shared/mcp_config.py`)
- `REQ-002`: The startup readiness poll and the liveness re-check send that header. (`scripts/agent/http_lifecycle.py`)
- `REQ-003`: The post-startup verification (`verify_health`, `_verify_single_health`) sends that header. (`scripts/agent/startup_mcp_starter.py`)
- `REQ-004`: The `/mcp` status probe sends that header. (`scripts/agent/services/mcp_health.py`, `scripts/agent/services/mcp_status.py`)
- `REQ-005`: Tests show that a correct token passes every probe, a wrong or missing token fails, and the token is not logged. (test files below)
- `REQ-006`: The startup and health documentation states that probes authenticate with the configured token. (`docs/23_agent/agent_10_01_operations-and-observability-startup-and-health.md`)

## Design
The helper lives on `McpServerConfig` because every probe already holds the `cfg` for its server, and `HttpTransport` already builds the same header from the same field. A module-level helper in `agent/` was rejected because `scripts/shared/` cannot import from `agent`, and the config model is the single owner of `auth_token`.

Probe call sites keep their signatures backward compatible: `_probe_mcp_health_detail()` gains an optional `headers: dict[str, str] | None = None`, and the lifecycle manager passes `headers=cfg.auth_headers()` through the `**client_kwargs` that `HealthChecker.verify_running_async()` already forwards. A 401 is still treated as not healthy, so a wrong token is detected.

The token is never logged: the existing log lines print the URL and status only, and the new code must not add the header to any log.
