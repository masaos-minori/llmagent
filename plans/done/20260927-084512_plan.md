## Goal
Fix `tests/shared/test_mcp_config_validation.py::test_auth_token_empty_string_raises`, which fails because its `_http_cfg(auth_token="")` helper implicitly builds a config with `startup_mode=StartupMode.NONE` (the class default) — and `McpServerConfig._validate_auth_token`'s empty-string check is deliberately skipped for disabled (`is_disabled`, i.e. `startup_mode == NONE`) servers, so the test never actually exercises an enabled server's validation.

## Priority
Medium

## Scope
- **In-Scope**: Add an explicit non-`NONE` `startup_mode` (e.g. `StartupMode.PERSISTENT`, matching HTTP transport per `StartupMode`'s own docstring) to `test_auth_token_empty_string_raises`'s `_http_cfg(...)` call.
- **Out-of-Scope**: `scripts/shared/mcp_config.py::_validate_auth_token`'s `not self.is_disabled` gate — confirmed intentional (a disabled server, per `StartupMode.NONE`'s own docstring "server is unusable", legitimately does not need a real `auth_token`). `_http_cfg`'s own default `startup_mode` omission for other, currently-passing tests — not touched, since changing the shared helper's defaults could affect other tests; this Plan fixes only this one test's call.

## Background
`McpServerConfig`'s class-level default is `startup_mode: StartupMode = StartupMode.NONE` (`scripts/shared/mcp_config.py:82`). `tests/shared/test_mcp_config_validation.py::_http_cfg`'s `defaults` dict never overrides `startup_mode`, so every config it builds (unless a test explicitly passes `startup_mode=...`) has `is_disabled == True`. `_validate_auth_token` (`scripts/shared/mcp_config.py:188-196`) raises on a non-string `auth_token` unconditionally, but only raises on an *empty* `auth_token` `if not self.auth_token and not self.is_disabled` — i.e. deliberately allowing a disabled server to have no token. `test_auth_token_non_string_raises` (the sibling test just above) passes because the type check has no such `is_disabled` gate; `test_auth_token_empty_string_raises` fails because its scenario is, by construction, always "disabled," so the empty-string check never fires.

## Problem
`Failed: DID NOT RAISE <class 'ValueError'>` at `pytest.raises(ValueError, match="auth_token")` around `_http_cfg(auth_token="")` — confirmed via Read that this call implicitly builds a `startup_mode=StartupMode.NONE` (disabled) config, for which `_validate_auth_token`'s empty-string check is deliberately not applied.

## Reason for change
This is confirmed test-fixture staleness/oversight, not a production validation gap: the validation correctly distinguishes "disabled server, token optional" from "enabled server, token required" — the test simply never puts the config into the "enabled" state its own name/intent (`_http_cfg`, i.e. an HTTP-transport server config) implies.

## Implementation intent
Add `startup_mode=StartupMode.PERSISTENT` (the mode `StartupMode`'s own docstring associates with HTTP-transport, URL-enforced servers) to this one test's `_http_cfg(auth_token="")` call, so the config represents a genuinely-enabled server and the empty-string check fires as intended.

## Requirements
- `REQ-001`: Add an explicit non-`NONE` `startup_mode` to `test_auth_token_empty_string_raises`'s `_http_cfg(...)` call.
