## Background
ADR-009 (`docs/adr/ADR-009-rag-ft5-text-separation.md`) defines 10 invariants for the
`chunks`/`chunks_fts` text-separation design. CI-007
(`docs/00_governance_03_issue-and-uncertainty-management.md:257-274`) tracks that
INV-07 ("FTS trigger and manual rebuild use identical text selection rules") and
INV-09 ("document the behavior for non-normalized cases, e.g. Markdown heading
chunks") have not been validated against the actual implementation, and that DESIGN-2
("no test guarantees application code never directly manipulates `chunks_fts`") is an
open gap. `Status: open`, `First Found: 2026-09-03`.

## Problem
Step 3 investigation (adversarial verification against current source) found the
Issue's Target Files section names stale paths (`scripts/db/recovery.py::check_rag_consistency()`,
`tests/test_rag_index_integrity.py`, `tests/test_fts_fallback.py` — all either wrong
module or wrong directory; corrected locations confirmed via `fd`/`rg`: the function
is in `scripts/db/rag_consistency.py`, and the tests are under `tests/agent/services/`
and `tests/rag/` respectively). More significantly, three concrete findings emerged
from directly comparing the trigger-based and manual-rebuild code paths:

1. **INV-07 (trigger vs. manual rebuild text selection) is correct in the code that
   actually runs, but has no real test.** The trigger (`scripts/db/schema_sql.py:62-66`,
   `chunks_ai`) and the production manual-rebuild path
   (`scripts/agent/services/rag_maintenance_service.py::rebuild_fts()`, called by
   `/session rag-rebuild-fts` via `scripts/agent/commands/cmd_session.py`) both apply
   `COALESCE(normalized_content, content)` — confirmed identical by direct reading of
   both. However, the existing test named for this invariant,
   `tests/rag/test_fts_sync.py::test_fts_trigger_and_manual_rebuild_use_same_text_selection_rule`
   (lines 171-208, confirmed via Read), never calls `rebuild_fts()` at all — its body
   only asserts Python's own `or`-operator fallback semantics on local variables
   (`fts_text1 = None or "test"`, `fts_text2 = "日本 語" or "日本語"`), which is
   tautologically true regardless of the production code and provides zero regression
   protection for INV-07.
2. **A second, dead-code implementation of the manual rebuild path diverges from the
   real one and could corrupt the FTS schema if it were ever wired up.**
   `scripts/rag/maintenance.py::RagDbMaintenanceService.rebuild_fts()` drops and
   recreates `chunks_fts` *without* the `content='chunks', content_rowid='chunk_id'`
   content-mapping the original schema uses (`scripts/db/schema_sql.py:56-60`), and
   only recreates the `chunks_ai` trigger (not `chunks_ad`/`chunks_au`). `rg -n
   "RagDbMaintenanceService"` confirms its only reference outside its own file is
   `tests/db/test_db_maintenance.py`; `vulture scripts/rag/maintenance.py
   --min-confidence 60` flags the entire class and all three of its methods as unused.
   `git log` shows no importer was ever added after this file's creation. This is
   filed as a new, non-blocking Issue (see Unknowns) rather than fixed here, per Scope.
3. **INV-09's behavior is correctly implemented but nowhere documented.**
   `scripts/rag/ingestion/chunk_splitter.py::_build_text_triples()` (lines 215-227,
   confirmed via Read) returns `norm_content=""` for Markdown-heading-chunked text
   (`self._is_markdown_source(data)` branch), which `_build_chunk_payload()` converts
   to `None` (line 292, `norm_content or None`) — the same `NULL`-then-`COALESCE`-
   fallback-to-`content` behavior INV-04 documents for English/code. ADR-009's body
   mentions INV-09's *requirement* to document this (Decision Details item 10,
   Invariants line 225) but never actually describes the behavior itself anywhere in
   the document — confirmed via full-text search for "Markdown"/"見出し", which found
   only the two references to INV-09's own requirement text.
4. **DESIGN-2 has no guarding test.** `rg -l "chunks_fts"` across `scripts/` confirms
   the only RAG-layer write sites are the trigger DDL, the production
   `rebuild_fts()`, and the dead-code duplicate in finding 2 above; `scripts/rag/repository.py`
   (confirmed via Read, lines 139-144) only ever `SELECT`s from `chunks_fts`. No
   existing test asserts this invariant holds, so a future change adding an
   unsanctioned direct write would go undetected.

## Reason for change
CI-007 has sat `open` since 2026-09-03 with no automated verification of INV-07/INV-09/
DESIGN-2, and the one test whose name claims to cover INV-07 does not actually
exercise the code it names — a future refactor of `rebuild_fts()` that broke INV-07
would pass the full test suite today. Left uncorrected, this is a false sense of
security: the governance inventory and the test suite both suggest the invariant is
checked when it is not.

## Implementation intent
Replace the non-functional INV-07 test with a real end-to-end comparison of
trigger-populated vs. rebuild-populated `chunks_fts` rows, add a static-analysis test
for DESIGN-2's write-site allowlist, and close the two documentation gaps (ADR-009's
missing INV-09 behavior description, and its stale Verification-section file paths) —
all additive changes; no production code path changes, since the code itself was
found correct.

## Risks
- **Risk**: The rewritten INV-07 test could be flaky if `rebuild_fts()`'s `delete-all`
  FTS5 special command interacts unexpectedly with an in-memory `:memory:` SQLite
  connection (vs. the file-backed connection production uses) → **Mitigation**: reuse
  the same `_FTS_SCHEMA_SQL`/connection-setup pattern the file's other passing tests
  (e.g. `test_rebuild_fts_preserves_normalized_content_semantics`) already use
  successfully against `:memory:`, rather than inventing a new setup.
- **Risk**: The DESIGN-2 text-scan test (REQ-002) could produce false positives on an
  unrelated SQL string that happens to contain the substring `chunks_fts` in a comment
  or docstring → **Mitigation**: scope the scan pattern to actual SQL statement
  keywords (`INSERT INTO chunks_fts`, `DELETE FROM chunks_fts`, `UPDATE chunks_fts`,
  and the FTS5 special-command form `INSERT INTO chunks_fts(chunks_fts) VALUES`) via
  regex, and manually verify zero false positives against the current tree before
  finalizing (per REQ-002's implementation step).
