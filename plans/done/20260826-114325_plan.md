## Goal
- Make the MCP failure-recovery documentation accurately and completely describe the
  post-watchdog reality: no code consumes "Watchdog" restart signals anymore, recovery
  for subprocess-mode servers is purely reactive (next-tool-call-triggered), and
  persistent-mode servers get zero automatic recovery — then require operators to close
  that gap with external process supervision that carries an explicit restart policy.

## Background
The MCP watchdog (background health-poll + auto-restart loop) was removed on
2026-07-16 (`plans/done/20260716-144940_plan.md`, "Remove the MCP watchdog feature").
That removal Plan's own Risk log explicitly flagged, as a non-blocking follow-up, that
removing the watchdog "removes the only automatic recovery path for a crashed
subprocess-mode MCP server" and recommended confirming with the operator whether an
external process supervisor should be configured — tracked as future operational
work, not resolved by that Plan. This Issue is that follow-up.

## Problem
Two concrete gaps remain in the current documentation, confirmed by direct reading of
current source and docs:
1. `docs/04_mcp_02_02_startup-modes-and-health.md`'s `restart_recommended` and
   `operator_action_required` field descriptions (lines ~26 and ~30) still describe an
   active "the Watchdog" consumer in the present tense ("informs the Watchdog that
   restarting the process may resolve the issue"; "The Watchdog logs a WARNING ... it
   will not perform a restart") — even though the same document's line ~44 states the
   `/mcp status` interpretation of these fields is "a display-only operation and does
   not trigger automatic restarts," and line ~49 separately notes the watchdog was
   removed on 2026-07-16. This is an internal contradiction within one document, not
   just a stale cross-reference.
2. No document states, in one place, the recovery-expectation split between
   subprocess-mode and persistent-mode MCP servers. `docs/04_mcp_06_09_mcp-failure-
   diagnosis.md`'s "`ensure_ready` behavior during tool dispatch" section correctly
   describes subprocess-mode's reactive-on-next-call recovery, but does not state that
   persistent-mode servers get none at all.

The pre-production checklist (`docs/04_mcp_06_16_pre-production-fail-open-
checklist.md`, line 28) already carries a note recommending external process
monitoring, but it is phrased as an informal note ("Ensure external process
monitoring (e.g., systemd) is set up for liveness monitoring and restarts") rather
than an explicit checklist requirement with a stated restart policy, and it does not
differentiate the two startup modes' differing urgency.

## Reason for change
Stale or incomplete documentation misleads operators into believing more automatic
resilience exists than the code actually provides, especially for persistent-mode
servers where `ensure_ready()` performs no recovery action at all. Availability can
degrade silently until an operator notices manually. This is worse for persistent-
mode servers, which have no reactive fallback whatsoever.

## Implementation intent
Correct the specific stale claim, add the missing subprocess-vs-persistent contrast in
the doc that already covers `ensure_ready()`, and convert the checklist's advisory note
into an explicit, mode-differentiated requirement. All three changes are additive edits
to existing sections of existing docs — no new document, no code change, no schema
change.

## Requirements
- `REQ-001`: `docs/04_mcp_02_02_startup-modes-and-health.md`'s `restart_recommended`
  and `operator_action_required` field descriptions must no longer describe an active
  "Watchdog" consumer; they must be consistent with the document's own removal note and
  its "display-only" `/mcp status` interpretation.
- `REQ-002`: `docs/04_mcp_06_09_mcp-failure-diagnosis.md`'s "`ensure_ready` behavior
  during tool dispatch" section must explicitly state the recovery-expectation
  difference between subprocess-mode servers (reactive recovery, gated on the next
  tool dispatch) and persistent-mode servers (zero automatic recovery — `ensure_ready()`
  returns immediately for non-subprocess servers).
- `REQ-003`: `docs/04_mcp_06_16_pre-production-fail-open-checklist.md`'s existing
  watchdog-removal note must become an explicit checklist requirement stating a restart
  policy is needed, differentiated as REQUIRED for persistent-mode MCP servers (no
  fallback recovery exists) and RECOMMENDED as defense-in-depth for subprocess-mode
  servers (covers the idle-crash window before the next tool call triggers
  `ensure_ready()`).

## Design
**Path A (Small Task).** All three criteria are satisfied: affects exactly 3 files (≤3),
no public or runtime-facing interface change (documentation prose only), no database
schema change. No architecture/dependency/historical/operational analysis was performed
per `SKILL.md` Routing; only direct verification of the three target docs and their
cited source evidence (`scripts/agent/factory.py::_ServerLifecycleRouter.ensure_ready()`,
`scripts/agent/services/mcp_status.py`, `scripts/agent/commands/cmd_mcp.py`) was
performed in Step 3.

**Chosen approach (resolving the Issue's open design question):** the Issue's Fix
Intent lists three possible actions. This Plan implements the first two (require
external supervision via the checklist; document subprocess-vs-persistent recovery
expectations) and explicitly declines the third (re-adding a health-driven restart)
because the Issue itself marks it "Optional ... if reactive recovery proves
insufficient," and no evidence of insufficiency was found during Step 3 — `ensure_ready()`
already exists and is exercised on every tool dispatch for subprocess-mode servers
(confirmed: `agent/factory.py` lines 128-166). Re-adding automatic polling would
recreate the exact background-loop mechanism the prior Plan
(`plans/done/20260716-144940_plan.md`) deliberately removed, without new evidence that
reactive recovery is inadequate. This keeps the Plan doc-only and Path A rather than
introducing a new supervision module (which would have been Path B).

**Evidence for the subprocess/persistent split (REQ-002):**
`_ServerLifecycleRouter.ensure_ready()` in `scripts/agent/factory.py` (lines 128-142)
returns immediately whenever `cfg.transport != TransportType.HTTP or cfg.startup_mode
!= StartupMode.SUBPROCESS` — i.e., for any persistent-mode server, the function is a
no-op. There is no other code path in `scripts/agent/` that attempts to restart a
persistent-mode server. This confirms the Issue's claim that "externally-managed
(persistent) servers have no auto-recovery at all" and grounds `REQ-002`'s required
doc text.

**Evidence for the stale Watchdog claim (REQ-001):** `docs/04_mcp_02_02_startup-modes-
and-health.md` line ~44 already states `McpStatusService.probe_all()`'s interpretation
of these fields "is a display-only operation and does not trigger automatic restarts or
change server states (Explicit in code)" — confirmed against
`scripts/agent/services/mcp_status.py` and `scripts/agent/commands/cmd_mcp.py`, which
only log/display `restart_recommended`/`operator_action_required`, never act on them.
This directly contradicts the same document's lines ~26/~30, which is the defect
`REQ-001` fixes.
