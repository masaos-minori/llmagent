## 8. Risks & Mitigations
- **Risk**: Monkeypatching `_BASE_CONFIG_FILES` in the rewritten test could leak into other tests if `monkeypatch` teardown fails or if test execution order changes. → **Mitigation**: `pytest`'s `monkeypatch` fixture auto-reverts after each test function; this pattern is already proven safe in the sibling test `test_different_subsections_in_load_all_merged` and in `tests/shared/test_config_loader.py::TestMergeOrder::test_nested_dict_merge`, both of which pass today alongside other tests that read `_BASE_CONFIG_FILES`. No new mitigation needed beyond following the existing pattern exactly.
- **Risk**: The rewritten test could silently lose one of the two semantic assertions the original hand-rolled version made (later file's `timeout` present, earlier file's `url` absent from the merged `github` subsection), producing a weaker regression guard than before. → **Mitigation**: Implementation Step in Section 6 explicitly enumerates all three assertions to carry over (`"github" in result...`, `"url" not in ...`, `timeout == 30`); Validation Plan re-runs the class-level test suite to confirm 5/5 still pass.
- **Risk**: `load_all()` iterates only over `_BASE_CONFIG_FILES`, so if the monkeypatch target string (`"shared.config_loader._BASE_CONFIG_FILES"`) is mistyped, the test would silently load the real `config/agent.toml` instead of the fixture files, and assertions would fail with a clear KeyError/AssertionError (not a silent false-pass) — low risk of a false-positive-passing broken test. → **Mitigation**: Copy the exact monkeypatch target string from the already-working sibling test rather than retyping it.
