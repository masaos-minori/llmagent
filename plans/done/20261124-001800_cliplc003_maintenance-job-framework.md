## Goal
- Put every long-running Session, RAG, and Memory maintenance action behind one tracked job framework: a job id, target store, approval level, cancelability class, state, and a result that is reported only after its postconditions pass — so a cancelled CLI task can never leave an untracked SQLite writer, a destructive Memory run cannot proceed on a flag alone, and a reported success means the store was re-measured.
## Priority
High
## Scope
- **In-Scope**:
  - A `MaintenanceJobRegistry` (`scripts/agent/services/maintenance_jobs.py`) that records a job id, operation name, target store, approval level, cancelability class, state, progress, and terminal outcome for every maintenance run; at most one running write job per target store; states `pending`, `running`, `completed`, `failed`, `cancelled`, `outcome_unknown`.
  - Cooperative cancellation that actually stops the SQLite work, built on the existing `shared.db.SQLiteHelper.interrupt_when` progress-handler mechanism (`scripts/db/helper.py:158-162`), wired into the Session, RAG, and Memory maintenance paths, plus the top-level `/jobs`, `/jobs status <id>`, and `/jobs cancel <id>` commands.
  - Approval levels (`none`, `confirm`, `guard`) enforced by the registry through the request-bound confirmation API that cliplc001 established (`scripts/agent/repl_input_controller.py`), instead of a `--confirm` / `--allow-loss` flag interpreted at parse time.
  - Verified results: every maintenance handler reports only after its own postcondition check, and an interrupted run reports the interrupted state rather than success.
  - Memory maintenance moved off the event loop and reached only through `MemoryServices` / `MemoryStore`, including an atomic pinned-count limit, a single-transaction prune select-and-delete, and jsonl import and delete that keep the SQLite and jsonl stores consistent.
  - RAG vector maintenance renamed to `/session rag-prune-vec` (service method `prune_orphan_vectors()`) to match what it does, with its orphan-prune behavior, pruned count, and remaining count documented and verified.
  - Repair guidance that names commands that exist, and generated API tables and manifests regenerated.
- **Out-of-Scope**:
  - The global shutdown deadline and shutdown WAL checkpoint policy (cliplc004); session transition and generation semantics (cliplc002, complete); export command contracts (cliplc011); turn persistence (cliplc010).
  - Running a maintenance worker in a separate process (recorded as UNK-01).
  - Any change to the persisted SQLite schema, or to what a maintenance operation means for the data.

## Background
- Maintenance is split by database today: `DbMaintenanceService` covers `session.sqlite` (stats, health, checkpoint, vacuum, purge, recover) and `RagMaintenanceService` covers `rag.sqlite` (stats, FTS and vector rebuild, consistency, recovery); both are thin wrappers over `scripts/db/maintenance.py` (`docs/23_agent/agent_04_03_state-and-persistence-platform-databases.md:58`). There is no job, registry, cancellation, or approval layer anywhere in this path: `rg -l "job_registry|JobRegistry|job manager" scripts/` returns nothing.
- `/session` maintenance subcommands dispatch through `DbMaintenanceOps.db_dispatch` (`scripts/agent/commands/cmd_session.py:224-243`), which runs the synchronous SQLite call with `asyncio.to_thread`. Cancelling the awaiter leaves the worker running, which is why `docs/23_agent/agent_07_07_cli-and-commands-slash-commands-session-mcp.md:73` states these subcommands are not cancellable.
- Memory maintenance handlers are synchronous (`MemoryRebuildOps.rebuild`, `reindex` — `scripts/agent/commands/memory_rebuild_ops.py:46,151`), use `--confirm` and `--allow-loss` flags, and bypass the Memory service layer by opening `SQLiteHelper` directly (`memory_data_ops.py:205-207,386-395,425-428`; `scripts/agent/commands/memory_status.py:85-87`), while `agent/memory/store.py` exposes no rebuild, index, prune, or limit accessor.
- Success is currently reported before the postcondition that would prove it: `scripts/agent/commands/memory_rebuild_ops.py:126` prints success before `check_consistency` runs at lines 140-141, and `RagMaintenanceService.rebuild_fts()` returns `None` (`scripts/agent/services/rag_maintenance_service.py:44-57`). `/session rag-rebuild-vec` prunes orphan vector rows and returns the remaining count (`scripts/agent/services/rag_maintenance_service.py:92-109`), so its name does not describe the operation.
- Two repair messages point at commands that do not exist: `memory_rebuild_ops.py:236,239` advise `/memory rebuild-fts` and `/memory rebuild-vec`.

## Problem
- Cancelling a `/session` maintenance command stops the REPL's await, not the SQLite writer: `DbMaintenanceOps.db_dispatch` runs the synchronous call through `asyncio.to_thread` (`scripts/agent/commands/cmd_session.py:224-243`), and `docs/23_agent/agent_07_07_cli-and-commands-slash-commands-session-mcp.md:73` records the consequence — these subcommands are not cancellable.
- No maintenance run is recorded anywhere: there is no job id, state, progress, or owner, so a run that outlives its command cannot be seen, attributed, or stopped. `rg -l "JobRegistry|job manager" scripts/` returns nothing.
- Destructive Memory runs are approved by a flag interpreted at parse time (`--confirm`, `--allow-loss` at `scripts/agent/commands/memory_rebuild_ops.py:54-55`), while `memory_delete` and `memory_prune` in the same command family already use request-bound confirmation — two different approval models for the same command group.
- Success is reported before the postcondition that would prove it: `scripts/agent/commands/memory_rebuild_ops.py:126` prints the success line before `check_consistency` and `check_index_consistency` run at `:140-141`, and `RagMaintenanceService.rebuild_fts()` returns `None` with no postcondition at all (`scripts/agent/services/rag_maintenance_service.py:44-57`).
- Memory maintenance blocks the event loop (`def reindex`, `def rebuild` at `memory_rebuild_ops.py:46,151`), bypasses the Memory service layer by opening `SQLiteHelper` directly (`memory_data_ops.py:205-207,386-395,425-428`, `scripts/agent/commands/memory_status.py:85-87`), rebuilds an index by deleting the whole table and re-inserting row by row with no transaction boundary (`scripts/agent/memory/rebuild_ops.py:8-43`), selects prune candidates in one connection and deletes them in another, and enforces `memory_max_pinned` with an unlocked read-then-write pair (`scripts/agent/commands/memory_data_ops.py:316-327`).
- `/session rag-rebuild-vec` prunes orphan `vec0` rows and returns the remaining count (`scripts/agent/services/rag_maintenance_service.py:92-109`), so its name does not describe what it does; repair guidance in `memory_rebuild_ops.py:236,239` names `/memory rebuild-fts` and `/memory rebuild-vec`, neither of which is registered.

## Reason for Change
Every long-running maintenance action writes to one of the two stores the agent persists to, and today none of them is tracked, cancellable, or verified before it reports success. The bounded-shutdown (cliplc004) and turn-persistence (cliplc010) work both need a recorded job to reason about what is still running.

## Implementation Intent
One registry instance owns every maintenance run: it assigns the job id, declares the operation's approval level and cancelability class, refuses a second concurrent writer against the same store, hands the worker a cancellation event that `SQLiteHelper.interrupt_when` turns into a real interruption, and records a terminal outcome that only says success after the operation's own postcondition check. Command handlers keep their messages but report the job outcome instead of assuming completion. Memory maintenance stops reaching into SQLite directly and goes through `MemoryServices`/`MemoryStore` inside transactions.

## Requirements
- `REQ-001`: A `MaintenanceJobRegistry` records every Session, RAG, and Memory maintenance run with job id, operation, target store, approval level, cancelability class, state, and terminal outcome; at most one running write job per target store; `/session` maintenance subcommands are registered through it.
- `REQ-002`: A declared-cancellable job is interrupted by `/jobs cancel <id>` through the existing `SQLiteHelper.interrupt_when` progress mechanism, ends in state `cancelled`, and leaves the store in either the pre-run or the post-run state; a job whose operation cannot be interrupted is declared `not_cancelable` at registration and says so when cancellation is requested.
- `REQ-003`: Approval is a property of the operation, enforced by the registry through the request-bound confirmation API: `none`, `confirm`, `guard`. A `--confirm` or `--allow-loss` flag does not by itself authorize a destructive run, and an approval is bound to the run that requested it.
- `REQ-004`: A maintenance operation reports success only after its own postcondition check has run and passed; an interrupted or partially applied run reports an `cancelled` or `outcome_unknown` outcome and never reports success. Each maintenance call returns a result object rather than `None`.
- `REQ-005`: Memory maintenance reaches SQLite only through `MemoryServices` / `MemoryStore`; the Memory command mixins construct no `SQLiteHelper` and issue no raw maintenance SQL.
- `REQ-006`: Memory maintenance runs off the event loop as a tracked job, and rebuild, reindex, prune select-and-delete, and delete plus its jsonl change event each complete inside one transaction boundary, so an interruption never leaves a half-written index. The Memory jsonl archive stays append-only.
- `REQ-007`: The RAG vector maintenance operation has a name that matches its behavior, and its orphan-prune count and remaining-row count are reported and documented; the sanctioned `chunks_fts` write path in `tools/check_chunks_fts_invariant.py` stays accurate.
- `REQ-008`: `memory_max_pinned` is enforced atomically inside the pin transaction, and prune candidates are re-validated inside the same transaction that deletes them.
- `REQ-009`: Repair, recovery, and failure guidance names commands that are actually registered (`/memory reindex --fts`, `/memory reindex --vec`, `/memory rebuild`, the job commands).
- `REQ-010`: `/jobs`, `/jobs status <id>`, and `/jobs cancel <id>` are registered, completable, and pass the command-contract and docs-consistency checkers; documentation, generated API tables, and API manifests are updated to match.

## Design
- **Framework decision**: one registry, one owner. `MaintenanceJobRegistry` is constructed in `factory.py` and carried on `AppServices`, so every command mixin reaches the same registry instance and the one-writer-per-store guard is process-global. A registry held per command mixin would not see a Memory rebuild started from a different mixin.
- **Job record**: `job_id` (short uuid), `operation` (`checkpoint`, `vacuum`, `purge`, `recover`, `rag-rebuild-fts`, the renamed vector operation, `reindex`, `rebuild`, `prune`, `delete`, `import`), `store` (`session`, `rag`), `approval_level`, `cancelability` (`cooperative`, `not_cancelable`), `state`, `started_at`, `progress`, `outcome`, `verified` (bool), `session_target` (the cliplc002 generation identity, so a job can be attributed to the session that started it).
- **States**: `pending → running → {completed | failed | cancelled | outcome_unknown}`. `outcome_unknown` is the state a job enters when the awaiter was cancelled or the process died while the SQLite worker was still running; it is never reported as success and never re-run automatically.
- **One writer per store**: `session.sqlite` already has a single-writer contract in this repository (the four-database separation contract (`docs/10_adr/adr_02_05_008_db-six-sqlite-store-separation.md`)). The registry enforces the same rule in-process: a second write job against the same store is rejected with the running job id in the message, not queued.
- **Cancellation**: the registry owns a `threading.Event` per cancellable job and passes it to `SQLiteHelper.interrupt_when`, which is already the mechanism that makes a long SQLite step raise at the next progress callback (`scripts/db/helper.py:158-162`; used once today, at `scripts/agent/services/rag_maintenance_service.py:69` — not in `scripts/db/maintenance.py`, corrected at procedure time). `/jobs cancel <id>` sets the event; the worker converts the interrupt into a `cancelled` outcome. Operations that SQLite cannot interrupt (a `VACUUM` already past its last progress callback, a WAL checkpoint) are recorded `not_cancelable` at registration, so the UI says so instead of appearing to hang.
- **Approval**: `none` (read-only or reversible), `confirm` (one request-bound confirmation per run), `guard` (confirmation plus a stored precondition that must hold, used for `vacuum` where the free-space and single-writer conditions are checked before the run starts). The level is a property of the operation, declared in the registry, not of the command line: a `--confirm` flag no longer grants approval by itself, and an approval is bound to the run that requested it.
- **Verified results**: each maintenance operation returns a result object carrying its postcondition outcome — `checkpoint` re-measures `journal_mode` and WAL size; `vacuum` re-measures `page_count` and reports the delta; `purge` re-counts the removed rows; `recover` re-runs the existing consistency check; `rag-rebuild-fts` re-counts `chunks_fts` rows against `chunks`; the vector operation reports the orphan rows removed and the remaining count it already computes; Memory `reindex` and `rebuild` run `check_consistency` and `check_index_consistency` before the success line. `RagMaintenanceService.rebuild_fts()` returning `None` is replaced by a result object. Its name is not part of the rename, so `tools/check_chunks_fts_invariant.py` is not a target: it sanctions the whole `rag_maintenance_service.py` file (`SANCTIONED_PATHS`), and the function-name check it defines is not called.
- **Memory layering decision**: the command mixins stop opening `SQLiteHelper` directly and gain the accessors they need on `MemoryStore` / `MemoryServices`. `/session` commands keep their existing service wrappers (`DbMaintenanceService`, `RagMaintenanceService`); `scripts/agent/commands/cmd_session.py:156-158` builds a `RagMaintenanceService` per call and is routed through the injected registry so the same instance carries the job.
- **Memory atomicity decision**: rebuild, reindex, prune selection-and-delete, and pin-limit enforcement each run inside one transaction with a cancellation boundary, so an interruption leaves either the previous state or the new state, never a half-written index. The Memory jsonl archive stays append-only (`tests/agent/memory/test_jsonl_store.py:2`): the rebuild replays it, it never rewrites it.
- **Rename decision (owner, 2026-11-24)**: `rag-rebuild-vec` performs orphan pruning and returns a remaining count, not a vector rebuild, and no re-embedding primitive exists (`UNK-05` closed). The subcommand becomes `/session rag-prune-vec` and `RagMaintenanceService.rebuild_vec()` becomes `prune_orphan_vectors()`, returning the pruned and remaining counts. The nine documents, `config/doc_quality_rules.json:30-34`, `scripts/db/rag_consistency.py`, and `tests/agent/commands/test_agent_cmd_session.py:1158,1175` change in the same step as the code (R6), which is why they appear as target rows rather than a note.
- **Repair guidance**: `memory_rebuild_ops.py:236,239` name `/memory rebuild-fts` and `/memory rebuild-vec`, which are not registered. The registered forms are `/memory reindex --fts` and `/memory reindex --vec` (`scripts/agent/commands/command_defs_list.py:190-194`). The guidance text is corrected to the registered names.

## Risks
- **Risk**: An interruption lands between the `DELETE` and the re-insert of a rebuilt index, leaving a partially populated index → **Mitigation**: REQ-006 puts rebuild and reindex inside one transaction (`scripts/agent/memory/rebuild_ops.py` is a target row for exactly this), and UNK-02 verifies the commit boundary before the wiring lands.
- **Risk**: `interrupt_when` fires only at SQLite progress callbacks, so a single long statement may not be interruptible and cancellation looks broken → **Mitigation**: cancelability is declared per operation at registration (UNK-04), and a `not_cancelable` job refuses the request with an explicit reason instead of appearing to hang.
- **Risk**: Replacing `tests/agent/commands/test_command_blocking_offload.py` removes the current proof that an abandoned await does not stop the writer, which is the behavior a cancelled job must now guarantee → **Mitigation**: the new `outcome_unknown` and `cancelled` tests land in Phase 1 before that lock is amended.
- **Risk**: Renaming a documented repair command breaks nine documents, a doc-quality rule, and a sanctioned-path checker if the rename lands without them → **Mitigation**: Phase 6 is a single release unit (R6) that changes code, documents, rule, and checker together, and `tools/check_docs_quality.py` gates it.
- **Risk**: `scripts/agent/context.py` (11 commits in 30d) and `scripts/agent/commands/cmd_session.py` are the highest-churn conflict points with the active Plan `plans/20261123-234341_mcpdl006_two-layer-failure-verification.md` and with the other open CLI Issues → **Mitigation**: the registry is added as a new `AppServices` field rather than changing existing fields; run `tools/check_plan_target_overlaps.py` after freeze and land cliplc003 before the cliplc004 and cliplc011 edits to the same files.
- **Risk**: Approval moved into the registry could block legitimate non-interactive recovery runbooks (`docs/90_deployment/deployment_01_deployment.md` names no maintenance command; the flags are documented at `docs/23_agent/agent_07_10_cli-and-commands-slash-commands-memory-other.md:49`) → **Mitigation**: the owner decision of 2026-11-24 keeps the flags as a recorded grant rather than removing them, so the runbook stays executable.
- **Risk**: `scripts/db/maintenance.py` is 20367 B, close to the 24576 B module-size gate, and cancellation plus verified results add parameters → **Mitigation**: pass the cancellation event through existing helpers and add no new branch-heavy helper in that file; `tools/check_module_size.py` is a gate row.
- **Risk**: `VACUUM` and WAL checkpoint run while another writer holds the store, and the one-writer guard only sees registry-tracked jobs → **Mitigation**: the guard covers Agent-initiated maintenance; the shutdown checkpoint remains cliplc004's scope and is recorded as UNK-03 rather than silently handled here.
