# Plan: Preflight Gate Coverage Map — Document and Test All Execution Paths

## Goal
Create a complete coverage map of all execution paths gated by `check_preflight()` calls across the Agent subsystem, add missing tests for uncovered paths, resolve gateway-bypass gaps identified across multiple execution patterns, and document the preflight gate architecture in Agent documentation.

## Priority
Medium

## Scope

- **In-Scope**: Enumerate all `check_preflight()` call sites mapped to caller chains; verify each path has either a passing test or documented justification; add tests for uncovered paths; resolve gateway-bypass gaps across all execution patterns (tool_runner.py, cmd_mdq.py, cmd_context.py); update Agent architecture documentation; update REQ-003 Known Issue status.
- **Out-of-Scope**: Modifying the `check_preflight()` function logic itself; adding new gate conditions beyond what already exists; changes to MCP server preflight behavior; changes to Event Bus preflight behavior.

## Background

Preflight gates (`check_preflight()`) have been added to multiple locations in the Agent subsystem to prevent unauthorized tool access. However, there is no documentation or test coverage verifying that all execution paths are properly gated. Untested execution paths could bypass the gate, allowing unauthorized tool access.

## Problem

It is unclear whether all execution paths are covered by the preflight gate. Untested execution paths could bypass the gate, allowing unauthorized tool access.

## Reason for change

The scope of the preflight gate additions needs to be documented and tested. Without verification, the security boundary may have gaps that are not visible until an incident occurs.

## Implementation intent

Create a coverage map documenting all `check_preflight()` call sites, their caller chains, and their test status. Add missing tests for uncovered paths. Resolve gateway-bypass gaps identified across three execution patterns (not limited to `tool_runner.py`). Update Agent architecture documentation to describe the preflight gate coverage.

### Approach Selection

The plan follows a structured enumeration → verification → remediation workflow.

### Coverage Map Architecture

The coverage map will enumerate each `check_preflight()` call site with:

1. **Call site location**: File path + line number.
2. **Caller chain**: How the call is reached (e.g., `/mdq search` → `_execute_mdq` → `check_preflight`).
3. **Gate status**: Whether the gate is enforced (yes/no).
4. **Test coverage**: Whether a test exists for this path.
5. **Exemption justification**: If exempted, why.

### Gateway-Bypass Gap Analysis

Three distinct patterns exist where `tools.execute()` is called directly without going through the gateway:

**Pattern 1: Preflight gate present, gateway bypass** (cmd_mdq.py, cmd_context.py)
```python
# cmd_mdq.py:67-71
check_preflight(self._ctx.cfg, tool_name, tool_args)   # ← preflight gate present
result = await tools.execute(tool_name, tool_args)       # ← bypasses gateway
```
```python
# cmd_context.py:206-214
check_preflight(ctx.cfg, "git_diff", {})                 # ← preflight gate present
...
result = await ctx.services.tools.execute(               # ← bypasses gateway
    "git_diff", {"repo_path": repo_root, "commit": ""}
)
```
These paths have `check_preflight()` gates but bypass the gateway. They are partially covered but inconsistent with the gateway-centric enforcement model.

**Pattern 2: No preflight gate, no gateway** (tool_runner.py)
```python
# tool_runner.py:116-119
if ctx.services_required.gateway is not None:
    result = await ctx.services_required.gateway.execute(ctx, name, args)
else:
    result = await ctx.services_required.tools.execute(name, args)  # ← no preflight, no gateway
```
This is the critical gap: neither preflight nor gateway protection.

**Resolution priorities**:
- **Priority 1 (critical)**: Resolve Pattern 2 — either add preflight check in the `else` branch (Option A) or document why this path is safe (Option B). Option A must be attempted first since it is a security concern.
- **Priority 2 (moderate)**: Standardize Patterns 1 and 2 to route all write/delete/API-write operations through the gateway for consistent enforcement.

2. Triggers the specific execution path.
