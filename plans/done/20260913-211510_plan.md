# Categorize AugmentRefiner constructor dependencies by observational vs. functional necessity

## Goal
Add a short note after `docs/03_rag_03_05_query_pipeline-augment-stages.md`'s
`AugmentRefiner` Constructor Dependencies table, categorizing the optional
parameters into two groups by consequence of omission: observational callbacks
(`on_status`/`set_fetch_result`/`set_fallback_reason` — safe to omit, only lose
visibility) versus functionally-required-when-used (`llm` — omitting it while
`use_refiner=true` causes a runtime `ValueError`).

## Background
The Issue's cited claim
(`docs/03_rag_03_05_query_pipeline-augment-stages.md:66-74`: the Constructor
Dependencies table listing `http`/`cfg` as required, and 5 other parameters as
optional) is confirmed accurate.

**Re-verified 2026-09-13** (this cycle): the Issue's premise that "the
distinction between required and optional parameters isn't explained" and "the
rationale [for defaults] isn't documented" needs significant correction — the
existing table and surrounding text already answer 3 of the Issue's 4 requested
points:
- Point 1 (why required vs. optional): line 74 already states `llm` is
  "required when `use_refiner=true`" — the one parameter whose optionality has a
  non-obvious condition
- Point 2 (what happens on default): lines 70-73 already state each callback
  "defaults to no-op" and `search_diagnostics` "defaults to empty
  `SearchDiagnostics()`"
- Point 4 (known edge case): line 95 already states "Raises `ValueError` if `llm`
  dependency not injected" — the exact edge case the Issue asks about

Only point 3 ("how the class behaves differently based on which dependencies are
injected") is genuinely under-addressed — the table lists each parameter's
individual default but does not group them by what omission actually costs.
Confirmed via direct reading of `AugmentRefiner.__init__`
(`augment.py:46-67`) and each callback's one use site
(`augment.py:60-62,80,110,146`): `on_status`/`set_fetch_result`/
`set_fallback_reason` are purely observational — each is invoked only to forward
information to an external caller (status updates, fetch-result/fallback-reason
propagation); omitting any of them (leaving the no-op default) does not change
`AugmentRefiner`'s own HTTP-augment or refiner behavior, it only means the caller
loses that observability. `llm`, by contrast, is read directly by `run_refiner()`'s
own logic (`if self._llm is None: raise ValueError(...)`) — omitting it changes
functional behavior (an exception) the moment `run_refiner()` is invoked with
`use_refiner=true`. `search_diagnostics`'s default (a fresh `SearchDiagnostics()`)
is functionally inert either way — it only affects what starting values the
diagnostics object carries before the first update.

## Problem
A reader of the Constructor Dependencies table sees 5 "optional" parameters
without a way to distinguish, at a glance, that 3 of them are safe to omit with no
functional consequence (only lost observability) while 1 (`llm`) has a real
functional dependency that surfaces as a runtime error under a specific condition.

## Reason for change
Add a short categorization note distinguishing observational-callback parameters
from the functionally-required `llm` parameter, so a developer deciding whether to
wire up a given dependency understands the actual consequence of omission for
each, beyond what the per-parameter table cells already state individually.

## Implementation intent
Add a short note after the Constructor Dependencies table (after line 74) stating:
(1) `on_status`/`set_fetch_result`/`set_fallback_reason` are purely observational
— each forwards information to an external caller and has no effect on
`AugmentRefiner`'s own HTTP-augment/refiner behavior if omitted; (2) `llm` is
functionally required whenever `run_refiner()` is invoked (i.e. `use_refiner=true`)
— omitting it does not silently degrade behavior, it raises `ValueError` at call
time; (3) `search_diagnostics`'s default only affects the diagnostics object's
starting values, with no other functional consequence.
