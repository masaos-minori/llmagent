# Plan: Add nosec annotations for bandit B608 false positives (eventbus/mdq)

## Goal

Add em-dash-delimited `# nosec B608 — <justification>` annotations to the 6 SQL
expressions in `scripts/eventbus/` and `scripts/mcp_servers/mdq/` that bandit flags as
B608 false positives (all values are bound via `?` placeholders), so `uv run bandit -r
scripts/ -c pyproject.toml` reports 0 medium/high issues, with no change to SQL logic.

## Scope

- `scripts/eventbus/db.py:210`

  correctly-formatted em-dash `# nosec B608` annotation; confirmed via `grep -n "nosec"
  scripts/mcp_servers/mdq/search.py`. No change needed.
- Any change to SQL query construction, parameter binding, or logic — annotation-only
  change.

## Assumptions

- The em-dash character (U+2014, `—`) is mandatory for `tools/check_suppression_
  justification.py` to accept the annotation — confirmed by reading the tool's docstring
  and `EM_DASH = "—"` constant, and by the existing `scripts/db/maintenance.py:169` /
  `scripts/db/store_impl.py:259` / `scripts/mcp_servers/mdq/search.py:152,167`
  annotations, all of which use `—` not `-`.
- All 6 flagged SQL expressions genuinely bind every value via `?` placeholders (no
  f-string-interpolated user input) — confirmed by reading each flagged line and its
  surrounding function in full during requirement verification.

## Design

No code-structure design needed — this is a pure annotation addition. For each of the 6
locations, append `  # nosec B608 — <justification>` (two spaces before `#`, matching
the existing db-layer style) to the line bandit flags, using the justification text
already agreed in the requirement:

| Location | Justification |
|---|---|
| `eventbus/db.py:210` | all values bound via ? placeholders |
| `eventbus/subscribe_route.py:51` | all values bound via ? placeholders |
| `mdq/db_grep.py:70` | WHERE clause built from fixed column names; values bound via params |
| `mdq/health_check.py:35` | STALE_SQL_CONDITION is a fixed string constant |
| `mdq/mdq_service.py:209` | where_clauses fragments from fixed constants; values bound via params |
| `mdq/mdq_service.py:340` | STALE_SQL_CONDITION is a fixed string constant |

Verify line length stays ≤ 88 chars per `rules/coding.md` after appending the comment; if
a line would exceed it, wrap using the same multi-line f-string style already used at
that call site (all 6 sites are already multi-line f-strings/parenthesized expressions,
so the comment can attach to the closing line without reflowing the SQL text).

## Risks

- **Risk**: Appending the comment pushes a line past the 88-char limit, requiring a
  reflow that touches the SQL string itself and risks an unintended logic change.
  → **Mitigation**: all 6 sites are multi-line expressions (f-string continuation or
  parenthesized `.execute()` call) per Design above, so the comment attaches to the
  closing line/paren without touching the SQL text; verify with `ruff format --check`
  after each edit.
- **Risk**: A 7th or 8th B608 location appears after this change (e.g. if bandit's
  scan picks up a location suppressed by a broader `# nosec` today). → **Mitigation**:
  Phase 2's `bandit -r scripts/` re-run over the whole tree, not just the 5 files,
  catches this before the task is reported complete.

## Adversarial verification notes

Running `uv run bandit -r scripts/ -c pyproject.toml` against current source found only 6
unannotated B608 findings, not the 8 the requirement originally listed: the 2
`scripts/mcp_servers/mdq/search.py` locations already carry a correctly-formatted,
em-dash `# nosec B608` annotation and are no longer findings. The requirement's line
numbers for `db.py`, `subscribe_route.py`, and both `mdq_service.py` locations had also
drifted from the code's current line numbers. Separately, the requirement's own
Implementation Instructions example used a hyphen (`# nosec B608 - <justification>`)
where `tools/check_suppression_justification.py` requires an em dash (`—`, U+2014) —
confirmed against that tool's source and every existing nosec annotation in the
repository, all of which use the em dash. The requirement was corrected in place: scope
narrowed to 6 locations, line numbers updated, `search.py` moved to Out of Scope, and the
em-dash requirement made explicit with a suppression-justification-checker verification
step added to Implementation Instructions and Acceptance Criteria.
