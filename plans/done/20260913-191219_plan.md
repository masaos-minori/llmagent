# Add runtime validation for critical RagConfigImpl fields when search is enabled

## Goal
When `use_search=True`, make `resolve_rag_config()` fail fast with a clear `ValueError`
if any of `rag_db_path`, `llm_url`, `embed_url` resolves to an empty value, instead of
silently constructing a `RagConfigImpl` that will fail confusingly deep in the pipeline.

## Priority
Medium

## Scope
- **In-Scope**: Adding a post-resolution check in `resolve_rag_config()` for
  `rag_db_path`/`llm_url`/`embed_url` non-emptiness, gated on `use_search=True`
- **Out-of-Scope**: Adding default values to `RagConfigImpl` fields (would change the
  dataclass contract); changing `RagConfigValidator`'s existing checks (separate
  concern; it validates cross-file consistency, not field presence); a missing-keys
  check for `_ALL_FIELDS` (see Background — this cannot actually happen); type
  validation for other fields (e.g. rejecting `rag_top_k=0` or `rag_min_score=-1.0` —
  the Issue's own Unresolved Questions correctly flags this as a separate, more
  complex concern); runtime hot-reload of config

## Background
The Issue claimed that a config source omitting a required field causes
`resolve_rag_config()` to raise a confusing `TypeError` from
`RagConfigImpl(**filtered_cfg)`, and proposed adding a missing-keys check after
`filtered_cfg` construction.

**Re-verified 2026-09-13** (this cycle, against the current repository state): this
specific claim does NOT hold. `resolve_rag_config()` (`config_resolution.py:130-132`)
already unconditionally back-fills every key in `_ALL_FIELDS` from `_DEFAULTS_FOR_ALL`
before `filtered_cfg` is built:
```python
for k in _ALL_FIELDS:
    if k not in _raw_cfg:
        _raw_cfg[k] = _DEFAULTS_FOR_ALL[k]
```
Confirmed by direct inspection that `_ALL_FIELDS == set(_DEFAULTS_FOR_ALL.keys())`
(both 27 keys, no mismatch) — so `_DEFAULTS_FOR_ALL[k]` can never raise `KeyError`, and
`RagConfigImpl(**filtered_cfg)` always receives every field. `TypeError` from a missing
field is therefore not reachable. Existing tests
(`tests/rag/test_config_resolution.py::test_dict_input_uses_defaults_for_missing_fields`
and `test_object_with_dict_uses_defaults_for_missing_fields`) already confirm this
defaulting behavior.

However, the Issue's underlying concern is partially valid: `_DEFAULTS_FOR_ALL` sets
`llm_url` and `embed_url` to `""` and `rag_db_path` to `":memory:"` when absent — so a
config source that omits these fields (or a `use_search=True` deployment pointed at
`":memory:"` unintentionally) silently produces a `RagConfigImpl` with an empty/dummy
`llm_url`/`embed_url`/`rag_db_path`, which will fail later and less clearly (e.g. an
HTTP client error on an empty URL, or a SQLite connection to a throwaway in-memory DB)
rather than at config-resolution time. `RagConfigValidator.validate()`
(`shared/config_validator.py:26-40`) confirmed to check only `use_rrf` and removed
semantic-cache keys — it does not check field presence, emptiness, or type, consistent
with the Issue's Background claim about this validator's scope.

## Problem
When `use_search=True` and `rag_db_path`/`llm_url`/`embed_url` resolve to their
default/empty values (via a config source that omits them, or an explicit empty
string), `resolve_rag_config()` returns a `RagConfigImpl` that will fail later, deeper
in the pipeline, with an error that does not point back to the missing configuration.

## Reason for change
Fail fast with a clear, actionable error message at config-resolution time when search
is enabled but a field it structurally depends on (DB path, LLM URL, embed URL) is
empty — before the pipeline reaches a confusing downstream failure.

## Implementation intent
In `resolve_rag_config()`, after `filtered_cfg` is built and `RagConfigImpl` fields are
known, if `filtered_cfg["use_search"]` is `True`, check that `rag_db_path`, `llm_url`,
and `embed_url` are each a non-empty string; raise `ValueError` naming every empty
field found (not just the first) if any check fails.

## Requirements
- `REQ-001`: `resolve_rag_config()` must raise `ValueError` naming every empty
  critical field (`rag_db_path`, `llm_url`, `embed_url`) when `use_search=True` and any
  of them is empty

## Design
This task is classified as **Path A** (small task): affects 1 file, no public interface
changes (return type and success-path behavior unchanged; only a new failure path is
added), no database schema changes.

This cycle's re-verification found the Issue's specific technical claim (`TypeError`
from a missing field) does not hold — `resolve_rag_config()`'s existing back-fill loop
guarantees every `_ALL_FIELDS` key is present before `RagConfigImpl(**filtered_cfg)`.
The Plan is narrowed to the part of the Issue's concern that does hold: critical fields
silently defaulting to empty/dummy values when `use_search=True`.

Key design decisions:
1. Gate the check on `use_search=True` only — a non-search pipeline instance has no
   structural need for `rag_db_path`/`llm_url`/`embed_url` to be non-empty, and the
   Issue's own Constraints require backward compatibility with configs that work today
2. Collect and report every empty field in one `ValueError`, not just the first — this
   matches the Issue's own Implementation Intent phrasing ("validate ... raise
   ValueError with the list of missing fields") applied to emptiness rather than
   presence
3. Do not touch `RagConfigValidator` — its scope (cross-file consistency: `use_rrf`,
   removed keys) is a different concern than per-field emptiness on the already-merged
   `filtered_cfg`; conflating them would widen this Plan's blast radius unnecessarily
4. Do not add type validation (e.g. rejecting `rag_top_k=0`) — the Issue's own
   Unresolved Questions flags this as adding complexity beyond this fix's scope
