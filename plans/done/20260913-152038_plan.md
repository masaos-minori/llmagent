## Problem
`_make_test_app()` (`tests/eventbus/test_eventbus_auth.py`) registers its own local
FastAPI routes (`/publish`, `/subscribe`, `/dlq`, `/dlq/{event_id}/requeue`,
`/replay`, `/events/{event_id}/ack`, `/nack`) that call the real route logic
directly (e.g. `eb_app.publish_route(request)`), but none of the seven declares
`Depends(require_role(...))` or, where the real route also has it,
`Depends(require_consumer_identity)` — confirmed by reading all seven local
handlers. `scripts/eventbus/app.py`'s corresponding real routes do declare both
(confirmed by reading `app.py`). FastAPI only resolves a dependency a route handler
itself declares, so every "authorized role" test in this file currently exercises
Bearer-token authentication only (via `attach_auth_middleware`), never role-based
authorization.

## Reason for change
Confirmed by direct reproduction: attempting to add the missing
`Depends(require_role(Role.PUBLISHER))` to the local `/publish` route surfaced that
a `consumer_token` bearer could otherwise reach it and receive `200 OK` — this
file's own docstring claims to test "Positive/negative authorization tests for
every EventBus route category," but currently cannot distinguish "authorized for
this specific role" from "merely authenticated." This undermines confidence in the
per-role-token authorization fix already landed
(`implementations/done/20260913-122501_05_scripts_eventbus_auth.py.md`), since this
file's own tests would not catch a regression in role enforcement.

## Implementation intent
Mirror `scripts/eventbus/app.py`'s seven real route declarations exactly onto
`_make_test_app()`'s seven local routes: same `Depends(require_role(Role.<X>))` per
route, plus `Depends(require_consumer_identity)` on the three routes that also have
it (`/subscribe`, `/events/{event_id}/ack`, `/nack`), and thread `_role`/`_identity`
through to each delegated-to route function call the same way `app.py` does. Add
at least one wrong-role-token negative test per role-gated route. Land this only
after `plans/20260913-151824_plan.md` (Issue `eb005`) is implemented, since
activating `require_consumer_identity`'s dependency chain on the three
consumer-identity routes will otherwise surface that Plan's still-open bug in
currently-passing tests.

## Design
Add `_role: Role = Depends(require_role(Role.<X>))` to each of the seven local
route handlers, matching the role `app.py`'s corresponding real route requires
(`/publish` → `Role.PUBLISHER`; `/subscribe`, `/events/{event_id}/ack`, `/nack` →
`Role.CONSUMER`; `/dlq`, `/dlq/{event_id}/requeue`, `/replay` → `Role.OPERATOR`).
Add `_identity: dict[str, Any] = Depends(require_consumer_identity)` to the three
`Role.CONSUMER` routes, matching `app.py`. Thread both parameters through to each
delegated-to route function call exactly as `app.py` already does (e.g.
`eb_app.publish_route(request, _role=_role)`). Import `Depends`, `Role`,
`require_role`, and `require_consumer_identity` at the top of the fixture function
(mirroring the module-level imports `app.py` already uses).

Sequencing: land this Plan's three consumer-identity routes only after
`plans/20260913-151824_plan.md` lands, since `require_consumer_identity`'s current,
still-buggy topic-allowlist check would otherwise reject topics for tokens with no
configured restriction the moment its dependency chain activates here. The four
non-consumer-identity routes (`/publish`, `/dlq`, `/dlq/{event_id}/requeue`,
`/replay`) have no such dependency and can land independently if needed, but this
Plan treats all seven as one Requirement set for a single, reviewable change.
