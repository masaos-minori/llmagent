# Implementation Plan: A failed or cancelled turn is recorded as `completed` in the workflow task table

## Goal

- Make `tasks.status` in `workflow.sqlite` record what actually happened in a turn:
  - a turn whose stage raised a plain exception is recorded `failed`, not `completed`
  - a turn cancelled by the REPL is recorded `halted`, not `completed`
  - the `completed` transition is written exactly once, by the component that observed it
- Give `WorkflowEngineAdapter.execute_turn` one explicit exit-reason classification instead of a
  single `engine_status_handled` flag plus inference from `error_kind`.
- Keep every other observable behavior of `execute_turn` identical: signature, returned tuple,
  exception propagation, halt handling, audit events, and the `attempts` table.

## Priority

High

## Scope

- **In-Scope**:
  - `execute_turn`'s `finally` block (`scripts/agent/workflow_engine_adapter.py:189-202`): stop it
    overwriting a terminal status the engine already wrote, and stop it writing `completed` at all.
  - An explicit exit-reason classification (halt/timeout, engine-classified exception,
    `asyncio.CancelledError`, normal return, failure before the engine started) replacing
    `engine_status_handled` (`:142`, `:187`, `:192`).
  - A new `except asyncio.CancelledError` branch that records `halted` and re-raises, so a
    cancelled turn is distinguishable from a successful one.
  - One private classification helper, so the classification does not push `execute_turn` past the
    `radon` complexity gate or the module past the module-size gate (`DEFAULT_LIMIT = 20480`;
    see `Assumptions`).
  - Escalating the best-effort status-write failure log from `warning` to `error` with the task id
    and the intended status.
  - Migrating the one existing test that asserts the adapter writes `completed`, and adding a
    real-engine / real-store test class covering all six exit paths.
  - Documenting the status state machine in the two chapters that already describe parts of it.
- **Out-of-Scope**:
  - Closing the `attempts` row a cancelled turn leaves `running`; that is
    `StateStore.recover_stale_attempts()` (`scripts/agent/workflow/state_store.py:279-316`,
    `_STALE_GRACE_SEC = 30` at `:22`) and belongs to the shutdown issue.
  - Resume semantics for a task marked `halted` by cancellation. `_init_workflow_task` rejects a
    `halted` task (`scripts/agent/workflow_engine_adapter.py:284-290`) and no production caller
    passes `existing_task_id`.
  - Any change to `WorkflowEngine.run()` (`scripts/agent/workflow/workflow_engine.py:108-132`),
    `StateStore`, `task_ops.py`, `scripts/db/schema_sql.py`, or `config/workflows/default.json`.
  - A new status string (`cancelled`) or a schema-level `CHECK` on `tasks.status`.
  - `error_kind` for halts (the issue's open question; resolved as "unchanged" — see DR-003).
  - `turn_start` / `turn_end` event correctness, task identity and idempotency-key generation, and
    REPL-level cancellation behaviour: `turn004`, `turn001`, and the REPL shutdown issues.
  - Registering `docs/23_agent/agent_03_03_*` and `agent_06_04_*` in `docs/00_index.md`'s
    task-scope table (see Documentation Impact).

## Background

`tasks.status` is written from two places, and only one of them knows the whole outcome.

| Writer | Sites | What it knows |
|---|---|---|
| `WorkflowEngine.run()` (`scripts/agent/workflow/workflow_engine.py`) | `:121` `running`, `:127` `halted`, `:130` `failed`, `:132` `completed` | the transition it just observed, immediately before re-raising |
| `WorkflowEngineAdapter.execute_turn()` `finally` (`scripts/agent/workflow_engine_adapter.py`) | `:194` `failed`, `:196` `completed` | only `error_kind`, and the boolean `engine_status_handled` |

The engine classifies every outcome: `WorkflowHaltError` / `WorkflowTimeoutError` are re-raised after
writing `halted`, any other `Exception` after writing `failed` (`workflow_engine.py:124-133`).
`asyncio.CancelledError` derives from `BaseException`, so the engine's `except Exception` does not
catch it and the engine writes no terminal status for a cancelled turn.

The adapter's `finally` runs for every path. `engine_status_handled` is set to `True` only in the
halt/timeout branch (`:187`), so for every other path `:192` admits the write and `:193-196` picks
the value from `error_kind` alone: `failed` when it is set, `completed` when it is not. A plain
exception that the engine already recorded as `failed`, and a cancellation that produced no engine
write at all, both fall into the `completed` branch.

`tasks.status` has exactly one production reader today: the halted-resume guard in
`_init_workflow_task` (`:284-290`). `existing_task_id` is passed only by tests
(`tests/integration/test_orchestrator_integration.py:718-790`).

## Reason for Change

- The defect is real but currently latent: `/opt/llm/db/workflow.sqlite` has 0 rows in `tasks` and
  `attempts` (measured), and the only reader of `tasks.status` is unreachable in production. The
  reason to fix it now is sequence: `turn001` (idempotency key), `turn002` (once-per-turn entry
  work), `turn004` (turn events) and `turn005` (background-task cancellation at shutdown) all add
  behaviour that either reads this table or depends on its meaning. Building recovery logic on a
  column that records failures as successes would make the later work unverifiable.
- Cancellation is a live path in production code: `scripts/agent/repl_input_loop.py:279`
  `dispatch_task.cancel()` after `_GRACEFUL_TIMEOUT_S = 10.0` (`:55`), handled at `:282`. Today the
  durable record of that event says the turn completed.
- The adapter's `completed` write is redundant on the success path (case A writes it twice), so
  removing it is both a correctness fix and a reduction in the number of statements the `finally`
  has to keep correct.

## Implementation Intent

Make the engine the single writer of the transitions it can observe, and leave the adapter exactly
the writes the engine cannot observe.

- The adapter classifies why `execute_turn` is exiting (halt, engine-classified exception,
  cancellation, normal return, engine never started) instead of inferring a status from `error_kind`.
- From that classification, one pure decision function returns either the status the adapter must
  write or `None` when the engine already wrote the correct one.
- The adapter therefore stops writing `completed` entirely, never overwrites `halted` or `failed`,
  keeps the one downgrade the engine cannot see (a soft turn error), and records a cancellation as
  `halted` using the existing vocabulary.

## Requirements

- `REQ-001`: The adapter's `finally` never writes a status that contradicts a terminal status
  already written by the engine (`halted` from `workflow_engine.py:127`, `failed` from `:130`).
- `REQ-002`: `completed` is written only by `WorkflowEngine.run()` (`workflow_engine.py:132`); the
  adapter contains no `update_task_status(..., "completed")` call.
- `REQ-003`: A turn exiting through `asyncio.CancelledError` records `tasks.status = "halted"`
  using the existing vocabulary, and the `CancelledError` still propagates out of `execute_turn`
  unchanged.
- `REQ-004`: The adapter keeps the one write the engine cannot make for itself: when the engine
  completed normally and `error_kind` is not `None`, the task is recorded `failed`.
- `REQ-005`: The exit reason is classified explicitly in one place in `execute_turn`, and the
  status decision is a single pure helper rather than inline branches.
- `REQ-006`: A failed best-effort status write is surfaced as an `logger.error` including the task
  id and the intended status, is not routed to `self._on_error`, and still does not raise.
- `REQ-007`: `execute_turn`'s public contract is unchanged: signature and return tuple, halts
  returning `("", None, False)`, plain exceptions and `CancelledError` propagating, and
  `_handle_workflow_halt` (`:311-321`) untouched.
- `REQ-008`: No change to `WorkflowEngine`, `StateStore`, `task_ops.py`, `scripts/db/schema_sql.py`,
  `config/workflows/default.json`, or the status vocabulary.
- `REQ-009`: A turn that fails before the engine starts keeps `tasks.status = "pending"` (measured
  behavior today), and is pinned by a characterization test rather than silently changed.
- `REQ-010`: The status state machine is documented: which component writes which value and when,
  that cancellation is recorded `halted`, that status writes are best-effort, and that
  `recover_stale_attempts()` repairs `attempts` rows only and never a `tasks` row.
- `REQ-011`: Tests cover every exit path in the table in Problem with a real engine and a real
  store, and the test that pinned the removed adapter `completed` write is migrated to the real
  engine instead of being deleted.

## Assumptions

- The engine's own writes are the authoritative ones for the transitions the engine can observe,
  because they are made at the moment of the transition and before re-raising
  (`workflow_engine.py:124-133`). The adapter can only know the engine's outcome indirectly, through
  the exception type.
- `error_kind` being non-`None` with a normally-completing engine means a soft turn error the
  engine cannot observe (case C). That combination is the only case where the adapter is allowed to
  make the record worse-than-reported (`completed` → `failed`).
- `asyncio.CancelledError` reaching `execute_turn` is always an external cancellation (REPL
  graceful timeout, signal handler) and never an internal control-flow device; nothing in
  `scripts/agent/` raises it deliberately (only `tests/agent/test_orchestrator.py:1754` constructs
  one).
- A task row whose engine never started keeps `pending` (measured, case H). `pending` is the schema
  default (`task_ops.py:52`), and no production reader distinguishes it from `running`; treating it
  as a failure would be a new behavior, not a fix.
- Status writes stay best-effort: a persistence failure must not abort a turn that already produced
  an answer.

## Design

### The ownership boundary

```
execute_turn(...)                                    unchanged public contract
  try:
      _init_workflow_task / _activate_workflow         failure here  -> engine never started
      engine.run(task, plan_fn, execute_fn, verify_fn)
          workflow_engine.py:121  running              engine-owned
          workflow_engine.py:127  halted   (halt/timeout re-raised)   engine-owned
          workflow_engine.py:130  failed   (any Exception re-raised)  engine-owned
          workflow_engine.py:132  completed                           engine-owned, sole writer
  except WorkflowHaltError | WorkflowTimeoutError -> exit reason "halted"      (no adapter write)
  except CancelledError                            -> exit reason "cancelled"  (adapter writes halted)
  except Exception                                 -> exit reason depends on whether engine.run started
  finally -> one pure decision: status to write, or None
```

The decision function has one rule set, evaluated in this order:

| Exit reason | `error_kind` | Status the adapter writes | Why |
|---|---|---|---|
| cancelled | any | `halted` | the engine cannot see `CancelledError` (`workflow_engine.py:129` catches `Exception` only); reuse of the existing terminal vocabulary |
| halted | any | none | written by the engine at `:127` |
| failed (engine started) | any | none | written by the engine at `:130` |
| completed | not `None` | `failed` | a soft turn error the engine cannot observe; keeps today's case-C behavior and `test_writes_failed_on_execute_failure` |
| completed | `None` | none | written by the engine at `:132` |
| engine never started | `None` | none | the row keeps `pending`, exactly as today (case H) |

### Decisions

- `DR-001` — **A cancellation is recorded `halted`.** User decision, 2026-10-23. Rejected
  alternatives: `failed` (conflates a deliberate stop with a stage error, and `failed` is what case
  B is being corrected to); a new `cancelled` status (the vocabulary is a code convention with no
  schema enforcement, `schema_sql.py:171-181`, so a new value would silently spread to the resume
  guard at `:284-290`, `agent_03_03:40` and `:108`, and `agent_06_04:49` before any resume path
  exists to consume it). A cancelled turn is distinguishable from a retry-exhausted halt by the
  `attempts` rows (no `error_kind` on the abandoned attempt) and by the new log line.
- `DR-002` — **The engine owns its transitions; the adapter keeps only the two writes it can justify.**
  Rejected alternatives: (a) the adapter recomputes the status from the exception type and writes it
  again — keeps the double write of case A and keeps two owners; (b) the engine returns a status
  object or adds a `CancelledError` transition — puts the change in `scripts/agent/workflow/`, which
  the engine's own tests already pin, and the engine still cannot see soft turn errors (case C);
  (c) a guarded `UPDATE ... WHERE status NOT IN (...)` in `task_ops.py` / `state_store.py` —
  `task_ops.py` is already owned by the frozen `plans/20261023-084918_plan.md`, and a silent no-op
  write would hide which owner declined to write.
- `DR-003` — **No `error_kind` is produced for halts.** User decision, 2026-10-23. Halts stay
  visible only through the log and `attempts.status`; `execute_turn` keeps returning
  `("", None, False)` so `orchestrator.py:167-172` and the four existing halt/timeout tests are
  untouched (REQ-007, AC-7).
- `DR-004` — **A failed status write escalates to `logger.error`, and is not routed to
  `self._on_error`.** `on_error` is wired to `view.write_llm_error`
  (`scripts/agent/startup_component_init.py:81`), so routing a persistence failure through it would
  tell the operator an LLM call failed. The issue's "observable error rather than only a warning" is
  met by level plus context (task id, intended status) at `:197-198`.
- `DR-005` — **The classification is extracted into one private pure helper** that maps
  `(exit reason, error_kind)` to `str | None`. `execute_turn` is `B (9)` on radon today; keeping the
  mapping in a separate function is what allows the new `except CancelledError` branch to be added
  without reaching `C (11)`, and it makes the whole rule set testable without a database.
- `DR-006` — **The abandoned `attempts` row is not closed by the adapter.** Closing it would make
  the adapter responsible for a resource it did not open, and it would collide with
  `recover_stale_attempts()`'s optimistic-locking path (`state_store.py:279-316`). The defect is
  documented in `## Known Limitations` instead (REQ-010).
- `DR-007` — **`import asyncio` is added to the adapter's stdlib import group** (`:11-19`, style
  compared against `repl_input_loop.py:10-12`). `asyncio.CancelledError` has no builtin equivalent,
  and `except BaseException` with an `isinstance` test would be less readable and would change which
  exceptions the function re-raises.

  `completed` write is removed, because both live in the same `if/else`. Mitigated by `AC-5`, by
