## Goal
- Make the deploy flow correct for the binary-based production runtime: add a rebuild step for affected binaries, make binary freshness detectable (build info recorded at build time and checked at deploy time, deployed revision recorded), make binary replacement staged and reversible (smoke-checked set swap, previous set kept, rollback command), and make the deploy skill and deployment documents describe this runtime.

## Priority
High

## Scope
- **In-Scope**:
  - A new stdlib-only tool `tools/manage_binaries.py` that holds the build-info, freshness-check, swap, rollback, and revision-record logic, with tests that use fake binaries.
  - `deploy/build_binaries.sh`: write build info, build into a staging directory, swap after every requested binary passes, keep the previous set, and provide a rollback option.
  - `deploy/deploy.sh`: freshness check (warn by default, strict opt-in), staged swap when binaries come from a separate build directory, and a deployed-revision record.
  - `skills/deploy/SKILL.md`, `skills/deploy/workflow.md`, `docs/90_deployment/deployment_01_deployment.md`, `rules/env.md`, and `tools/TOOL_DESCRIPTIONS.md`.
- **Out-of-Scope**:
  - Rebuilding, redeploying, or reading anything under `/opt/llm`; a deploy stays a separate approved action.
  - Nuitka flags, the entry table, binary names, the MCP server launch design, or packaging other than Nuitka onefile.
  - Adding a `--version` or smoke mode to the agent or MCP servers (follow-up, UNK-01).
  - The `tests/` copy in `deploy.sh`, `setup_services.sh` behavior changes (it is only described correctly), and `init_db.sh`.
  - Container or orchestration tooling.

## Background
- Origin: review of the deploy scripts and skill on 2026-10-19, prompted by the session sqlite-vec fix (`plans/done/20261019-094625_plan.md`) that has not reached the production `agent` binary. The owner chose all three improvement groups: A (skill and documents), B (freshness and revision record), C (staged swap and rollback).
- Production runs the agent and the 10 MCP servers as Nuitka onefile binaries under `/opt/llm/bin/`. `deploy/start_agent.sh` launches the compiled `agent` directly; `config/agent.toml` `cmd` entries point to `/opt/llm/bin/mcp_<server>`.
- The Event Bus (`setup_services.sh`), the ingestion pipeline, the workflow validation in `start_agent.sh`, and `init_db.sh` run from the deployed `scripts/` source instead.

## Problem
- Following the skill exactly leaves production on old code with every step reporting success: `deploy.sh` places binaries from `BUILD_OUTPUT_DIR`, which defaults to `/opt/llm/bin`, so source and destination are the same file and the step only checks existence. No step rebuilds a binary.
- Binaries carry no build revision and nothing records the deployed commit.
- `build_binaries.sh` moves each finished binary straight into `/opt/llm/bin/` (`mv "${produced}" "${BIN_DIR}/${final_name}"`) with no backup, no check, and no all-or-nothing behavior; a failure part-way leaves a mixed set and there is no fast rollback.
- The skill's rollback note and its claim that reverting `cmd` entries to `uv run` restores the launch path are stale for the agent, its restart criteria are source-file based with no binary mapping, and it describes `setup_services.sh` as starting services while it only checks the remote LLM health and starts the Event Bus.
- Confirmed by this plan's source inspection (2026-10-19): neither the agent entry (`main()` in `scripts/agent/repl.py`) nor `MCPServer.run_http()` takes arguments, so no `--version` or `--help` smoke mode exists for any binary. No test references `deploy.sh` or `build_binaries.sh`, and `shellcheck` and `bats` are not installed.

## Reason for Change
- Production reliability: a deploy that succeeds without delivering the change is a silent failure, and recovery from a bad binary needs a rebuild of up to 11 binaries.
- The skill and deployment document describe a source-based flow for a binary-based runtime.
- The first change waiting on this is the session sqlite-vec fix.

## Implementation Intent
- Put the logic in one testable Python tool (`tools/manage_binaries.py`, standard library only) and keep the shell scripts thin: they call the tool, so the freshness, swap, and rollback logic is covered by pytest, ruff, and mypy, which shell scripts are not (`AGENTS.md` Global Rule 7).
- Freshness is per binary and path-scoped: a binary is stale only when files in the source paths it embeds changed between its recorded build commit and the revision being deployed, so unrelated commits (documents, tests) do not make every binary stale. The source-path table lives only in the tool; the skill points to it.
- Defaults stay backward compatible: existing environment variables keep working, a missing build info is a warning, and only an opt-in strict mode fails on stale or unknown binaries. The staged swap changes failure behavior (all-or-nothing, previous set kept) but not the end state of a successful build.
- Smoke check is structural (executable file, ELF header, recorded checksum, directory permissions) because no runtime smoke mode exists.

## Design
- Path B (more than 3 files; adds a tool; changes deploy scripts). Analyses run: architecture (`lint-imports`, run in the preceding session on an unchanged `scripts/`, 6 contracts kept; this plan adds no `scripts/` code), dependency graphing (an `ast` scan of `scripts/` shows `agent` imports `agent`, `db`, `mcp_servers`, `shared`; `mdq` adds `db`; `rag_pipeline` adds `db` and `rag`; the other MCP servers import `mcp_servers` and `shared`; the Event Bus is not imported by any entry point), historical (churn above; single author), operational (no production read was possible; production inspection is excluded by scope).
- Source-path table (single source of truth, in the tool): each binary lists the `scripts/` packages it embeds plus `pyproject.toml` and `uv.lock`; `scripts/shared/` affects all 11 binaries; `scripts/db/` affects `agent`, `mcp_mdq`, `mcp_rag_pipeline`; `scripts/rag/` affects `mcp_rag_pipeline`; `scripts/agent/` affects `agent`; each `scripts/mcp_servers/<server>/` affects its binary, and the agent conservatively embeds all of `scripts/mcp_servers/`. The Event Bus runs from deployed source and has no row; it is reported as needing a process restart instead. A drift test compares the table with `ENTRIES`, `BINARY_NAMES`, and the `ast` import scan so it cannot silently go stale.
- `check` logic: read the recorded commit from build info; run `git diff --name-only <commit> <rev>` filtered to the binary's paths; stale if any path changed or the build was dirty; unknown if no build info; mismatch if the recorded checksum differs from the file; invalid if not an executable ELF file or the directory is group/world-writable. The check never calls the network.
- `swap` logic: verify every staged binary (structural check and checksum against its build info); copy the current binaries to `bin.prev`; copy each staged binary to a temporary name in the bin directory and `os.replace` it into place; on any failure restore from `bin.prev` and exit non-zero. `rollback` copies `bin.prev` back the same way.
- Shell changes are limited to calling the tool and moving files to the staging directory; Nuitka flags and the entry table are untouched.
- Failure behavior: integrity problems (mismatch, invalid) always fail; freshness problems warn unless strict, consistent with ADR-004 (no silent fallback).

## Risks
- **Risk**: The hand-maintained source-path table drifts from the real imports, hiding a stale binary. → **Mitigation**: A drift test compares it with `ENTRIES`, `BINARY_NAMES`, and an `ast` import scan of `scripts/`; unknown packages fail the test.
- **Risk**: A swap failure mid-way leaves a mixed set. → **Mitigation**: The set is verified before any rename, the previous set is saved first, and the tool restores it automatically on failure; tests simulate a failing rename.
- **Risk**: Keeping a previous set doubles the binary disk use (about 270 MB). → **Mitigation**: One previous generation only; the tool reports sizes; the operator checks space (UNK-02).
- **Risk**: Strict mode blocks a deploy because existing binaries have no build info. → **Mitigation**: Warn by default; strict is opt-in and documented to follow the first rebuild (UNK-03).
- **Risk**: Changing `build_binaries.sh` breaks the real Nuitka build, which tests do not run. → **Mitigation**: Keep Nuitka flags, entry table, and candidate-name search unchanged; limit the change to the move/staging step; the first real build is run by the operator with `BUILD_ONLY="agent"` and checked before any production swap.
- **Risk**: The tool's `subprocess` and file operations trigger bandit findings or unsafe paths. → **Mitigation**: Use list-form commands with fixed executables, validate that target directories are not group/world-writable, and justify any `nosec` per `rules/coding.md`.
