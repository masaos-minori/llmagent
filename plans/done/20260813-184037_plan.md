# Plan: Fail-Closed Tool-Call Preparation Phase, Remove `tool_definitions` Runtime Fallback

## Goal

Introduce an explicit, fail-closed "preparation" phase in the agent tool-execution pipeline that
runs for every tool call *before* approval: parse call id/name, parse `arguments` JSON exactly
once, require the parsed result to be a JSON object, resolve the tool through
`RuntimeToolRegistry` only, validate args against the live `RuntimeTool.input_schema`, and build a
per-call `ToolSpec`. A call that fails any of these steps becomes a synthetic tool-error result
and never reaches `_run_approval_gate()`, DAG planning, `RepositoryGateway`, or `ToolExecutor`.
Remove the `except KeyError: pass` fallthrough and the `ctx.cfg.tool.tool_definitions` loop from
`_validate_tool_args()` in `scripts/agent/tool_runner.py`, so an unregistered tool can no longer be
silently accepted just because a stale/malformed static config entry happens to match its name.

## Scope

### In-Scope
- Add a new preparation module (`scripts/agent/tool_preparation.py`) that runs before
  `_run_approval_gate()` in `execute_all_tool_calls()`.
- Add a `PreparedToolCall` dataclass (`call_id`, `name`, `args`, `spec: ToolSpec`,
  `original_call: dict`) representing a call that has passed preparation.
- Delete `_validate_tool_args()`'s `KeyError` fallthrough and `ctx.cfg.tool.tool_definitions` loop
  (`scripts/agent/tool_runner.py:154-172`); remove `_validate_tool_args()` entirely once its logic
  is subsumed by preparation.
- Change `execute_one_tool_call()` to consume already-parsed `args` from a `PreparedToolCall`
  instead of calling `orjson.loads()` on `func.get("arguments")` itself
  (`scripts/agent/tool_runner.py:193-199`).
- Change `run_approval_checks()` (`scripts/agent/tool_approval.py:187-219`) to accept prepared
  calls (with already-parsed `args`) instead of re-parsing `tc["function"]["arguments"]` itself
  (`scripts/agent/tool_approval.py:200-208`) — removes the second, inconsistent JSON-parsing path.
- Remove `_build_tool_meta()` (`scripts/agent/tool_runner.py:60-79`) and its call site in
  `_execute_with_dag()` (`scripts/agent/tool_runner.py:325-326`); `_execute_with_dag()` builds its
  `tool_meta: dict[str, ToolSpec]` from the `spec` field already carried by each prepared call
  instead of re-deriving it from `ctx.cfg.tool.tool_definitions`.
- Introduce distinct, machine-readable preparation-error kinds (`configuration`, `unknown_tool`,
  `validation`, `schema`, `metadata`), each converted to a synthetic `ToolCallResult` via the
  existing `_reject_validation()` pattern (`scripts/agent/tool_runner.py:115-125`).
- Preserve original call order when merging preparation errors, approval denials, and execution
  results in `_collect_tool_result_msgs()` (`scripts/agent/tool_runner.py:234-263`).
- Update the `tool_definitions` field docstring in `scripts/agent/config_dataclasses.py:190-194` to
  state plainly it is compatibility-only (startup drift validation + test fixtures), removing the
  "(a) a fallback if the registry construction is empty/unavailable" framing, which contradicts the
  post-fix behavior.
- Audit and classify every remaining `ctx.cfg.tool.tool_definitions` reference under
  `scripts/agent/` (see Affected areas) per: startup drift validation / test fixture /
  display-count-only (no change) / prohibited runtime dependency (flag as follow-up, see
  Unknowns/Risks).
- New/updated tests: `tests/agent/test_tool_preparation.py` (new), `tests/agent/test_tool_runner.py`,
  `tests/agent/test_tool_arg_validator.py` (only if the validator's public surface changes),
  `tests/agent/test_tool_approval_*.py` (signature change for `run_approval_checks`).

## Design

**Where preparation sits in the pipeline.** `execute_all_tool_calls()`
(`scripts/agent/tool_runner.py:506-538`) currently does: (1) `_run_approval_gate()` →
(2) `_execute_with_dag()`/`_execute_standard()` → (3) `_collect_tool_result_msgs()`. Each of those
delegates re-derives per-call data from the raw `tc: dict` (`tc["function"]["arguments"]` parsed
independently in both `execute_one_tool_call()` and, separately, in
`run_approval_checks()`'s own preview-only parse). The new preparation phase is inserted as step
(0), before `_run_approval_gate()`: for each raw `tc`, build either a `PreparedToolCall` or a
synthetic `ToolCallResult` error, exactly once per call, and never again re-parse `arguments` JSON
downstream.

**`PreparedToolCall` shape** (new, in `scripts/agent/tool_preparation.py`):
```python
@dataclass(frozen=True)
class PreparedToolCall:
    call_id: str
    name: str
    args: dict[str, Any]
    spec: ToolSpec          # from shared.tool_spec — reused, not reinvented
    original_call: dict     # the raw tc, kept for audit/logging call sites that still want it
```

**Preparation steps, matching requirement item 1, using existing building blocks rather than new
ones:**
1. Validate `tc` has an `"id"` and `tc["function"]["name"]` — `configuration`/`validation` kind on
   failure.
2. `orjson.loads(func.get("arguments", "{}"))` exactly once; reject non-`dict` results —
   `validation` kind.
3. Require `ctx.services_required.runtime_tools is not None` — `configuration` kind.
4. `registry.get(name)` — catch `KeyError` → `unknown_tool` kind. This is the change that removes
   the current silent-success path: today, `_validate_tool_args()` returns `None` when the name is
   in neither the registry nor `tool_definitions`, which `execute_one_tool_call()`
   (`tool_runner.py:201-202`) reads as "no validation error" and proceeds to execution. After this
   change, an absent registry entry is rejected in preparation, before approval, full stop — no
   `tool_definitions` fallback path exists anymore.
5. `validate_tool_arguments(tool_name=name, args=args, input_schema=runtime_tool.input_schema,
   allow_extra_fields=runtime_tool.allow_extra_fields)` (reused unchanged from
   `agent/tool_arg_validator.py`) — `schema`/`validation` kind on failure.
6. `registry.tool_spec_for_call(call_id, name, args)` (reused unchanged from
   `shared/runtime_tool_registry.py:156-164`) to build `spec: ToolSpec` — this already folds in
   `resource_scope`, `requires_serial`, `is_write` from the live `RuntimeTool`, so it replaces both
   `_build_tool_meta()`'s per-name `ToolSpec` construction *and* `_validate_tool_args()`'s registry
   lookup in one call. `KeyError` here is defensive (already caught in step 4) — `metadata` kind if
   scope resolution otherwise fails.

**Downstream wiring.**
- `execute_all_tool_calls()` calls `prepare_tool_calls(ctx, tool_calls) -> tuple[list[PreparedToolCall],
  list[ToolCallResult-with-original-index]]` before `_run_approval_gate()`. Preparation failures are
  converted immediately to result tuples in the same 6-tuple shape `execute_one_tool_call()`
  currently returns (`tc_id, name, args, full_text, is_error, llm_text`), so
  `_collect_tool_result_msgs()` needs no shape change — only the merge/ordering logic in
  `execute_all_tool_calls()` changes to interleave prep-failures, approval-denials, and
  execution-results back into original order (requirement item 6), using the same
  `call_order = {tc["id"]: i for i, tc in enumerate(tool_calls)}` pattern already used in
  `_execute_with_dag()` (`tool_runner.py:357,373`).
- `_run_approval_gate()` / `run_approval_checks()` now take `list[PreparedToolCall]` and return
  `(approved: list[PreparedToolCall], denied_ids: list[str])` — `run_approval_checks()` drops its own
  `orjson.loads`/`except orjson.JSONDecodeError` block (`tool_approval.py:200-208`) entirely, reading
  `pc.args` directly (UNK-04).
- `execute_one_tool_call()` takes a `PreparedToolCall` instead of a raw `tc: dict`, dropping its own
  `orjson.loads()` call (`tool_runner.py:193-199`) and the `_validate_tool_args()` call
  (`tool_runner.py:201`) — both are now guaranteed to have already happened in preparation.
- `_execute_with_dag()` builds `tool_meta: dict[str, ToolSpec]` as `{pc.name: pc.spec for pc in
  approved_calls}` instead of calling `_build_tool_meta(ctx.cfg.tool.tool_definitions)`
  (`tool_runner.py:325-326`), then passes the same raw `[pc.original_call for pc in approved_calls]`
  list into `build_execution_groups()` (whose signature, `tool_calls: list[dict]`, is unchanged —
  confirmed via `scripts/agent/tool_scheduler.py:70-73`).

**Layering.** `scripts/agent/tool_preparation.py` lives in the `agent` package and imports from
`shared.runtime_tool_registry`, `shared.tool_spec`, and sibling `agent.tool_arg_validator` /
`agent.tool_exceptions` — all consistent with the existing `agent → shared` dependency direction in
`.importlinter`'s `shared-is-leaf` contract; no new contract is needed, and the pre-existing (and
unrelated) `eventbus`-vs-`shared`/`db` contract violations reported by
`PYTHONPATH=scripts uv run lint-imports` are baseline noise, not something this change touches or
must fix (confirmed by running the command before any change — see Validation plan).

**Documentation.** No `docs/*.md` file is edited in this plan (document-only phase, and out of
scope per task rules), but the implementer should update
`docs/05_agent_06_01_tool-execution-and-approval-execution.md` (and, if it separately narrates
approval ordering, `docs/05_agent_06_02_tool-execution-and-approval-approval.md`) once code lands,
per `rules/coding.md`'s "Documentation notes" classification (this is an "Implementation fix
required" style change to documented behavior, not a doc-only fix) — called out as Implementation
step 8 below.
