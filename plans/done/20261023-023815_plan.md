# Plan: make the tool-result batch-order step total for malformed tool call ids

## Goal
- Remove the only strict `tc["id"]` indexing left in `scripts/agent/tool_runner.py` so that a `tool_calls`
  batch containing an entry without an `id` key completes the round and answers that entry with the
  prepared rejection message, instead of aborting the whole turn with `KeyError: 'id'`.
- Make the merge that restores results to the declared batch order total: every entry of the batch gets a
  distinct position, including entries whose `id` is absent, empty, or repeated, and results that match no
  entry are appended instead of being moved to the front.

## Background
Preparation is deliberately lenient and fail-closed per call, not fatal for the batch:
`scripts/agent/tool_preparation.py:77-84` reads `tc_id = tc.get("id")` and, when it is absent or empty,
returns `_reject(tc_id or "", name or "", {}, "configuration", "tool call is missing an id")`. That tuple is
a `_PrepFailure` and is later rendered as an ordinary `tool` result message, so the model is told which call
was malformed. `execute_all_tool_calls()` does not return early on preparation failures:
`scripts/agent/tool_runner.py:369` collects `(prepared, prep_failures)` and `:384` merges both lists so that
every declared call is answered exactly once.

The ordering step that sits directly after that merge is the only place in the file that still indexes the
raw provider dict strictly, so the graceful rejection the pipeline has already produced is destroyed a few
lines before it reaches the model.

## Problem
`scripts/agent/tool_runner.py:383`:

```python
call_order = {tc["id"]: i for i, tc in enumerate(tool_calls)}
results = list(results) + list(prep_failures)
results.sort(key=lambda r: call_order.get(r[0], 0))
```

Two distinct defects, both reproduced at HEAD `064e77fd9` by a temporary probe that ran
`execute_all_tool_calls()` with the existing test fixtures (`_make_ctx()` / `_tc()` in
`tests/agent/test_tool_runner.py`; the probe file was removed after the run):

- `D-1` strict indexing: a batch entry with no `"id"` key raises `KeyError('id')` out of
  `execute_all_tool_calls()` before `:384` runs. `ctx.session.save_many()` is never called, so no tool
  message is produced for any call in the batch. Probe output:
  `CASE A declared=[no id] raised: KeyError 'id' saved_called: False`.
  In the REPL the assistant message has already been persisted (`scripts/agent/llm_turn_runner.py:107-112`)
  before `execute_all_tool_calls()` is called (`:115-120`), so the exception surfaces through
  `ReplInputLoop._surface_turn_error` (`scripts/agent/repl_input_loop.py`) as `[fatal] KeyError: 'id'`, with
  the reason for the failure hidden from both the model and the user.
- `D-2` a dict cannot hold two positions for one id: `{tc["id"]: i ...}` keeps the **last** index for a
  repeated key, and `.get(r[0], 0)` maps anything that is not in the map to position `0`. With declared
  order `["", "call_b", ""]` the map is `{"": 2, "call_b": 1}` and the persisted order becomes
  `[call_b, "", ""]`. Probe output:
  `CASE C declared: ['', 'call_b', ''] saved: [('tool', 'r', None, 'call_b'), ('tool', 'tool call is missing an id', None, ''), ('tool', 'tool call is missing an id', None, '')]`.
  The same collapse applies to a provider that repeats a real id: `["x", "y", "x"]` sorts both `x` results
  after `y`. With a single empty id the current code happens to be correct (`CASE B`), which is why the
  defect is invisible in single-malformed-call batches.

No test asserts the merged batch order when preparation failures are present (`grep` for `missing an id` or
`unregistered` over `tests/` returns no tool_runner case), and no document states the merge behavior; only
the auto-generated API table restates the docstring ("append results in original order",
`docs/23_agent/agent_13_reference-api-generated.md:185`).

## Reason for Change
Provider responses occasionally contain malformed tool calls, and this repository has already absorbed several
provider-malformation defects by making the round tolerate them and answer them explicitly rather than crash.
As it stands one malformed entry destroys an entire tool round, and the error message that the preparation
phase carefully built ("tool call is missing an id") is never delivered. The fix is a few lines and restores
the contract the surrounding code already claims.

## Implementation Intent
Keep the preparation contract untouched and make the ordering step total instead of id-keyed. An id-keyed
map cannot satisfy the requirement even with lenient key access, because a dict cannot express two positions
for the same id (`D-2`); the ordering step needs a positional pass over the declared batch that consumes
results in that order. Pairing by walking the batch is also what the `_PrepFailure` docstring in
`scripts/agent/tool_preparation.py:152-159` already assumes ("the caller can reinsert it at its original
batch index"). No `try/except` wrapper: the crash disappears because nothing indexes the raw dict strictly.

## Requirements
- `REQ-001`: `execute_all_tool_calls()` must not index a raw `tool_calls` dict with `tc["id"]`; the batch
  order must be derived with lenient id access so a batch containing an entry without an `id` key completes
  and answers that entry with the prepared rejection text. Source: issue `Required Changes` bullet 1,
  `Acceptance Criteria` bullet 1, `AI Implementation Instruction`.
- `REQ-002`: Every entry of the declared batch must be given a distinct position in the merged result list,
  including entries whose `id` is absent, empty, or equal to another entry's id; the merged order must equal
  the order of `tool_calls`. Source: issue `Required Changes` bullet 2, `Acceptance Criteria` bullet 2;
  defect `D-2`.
- `REQ-003`: A result tuple that no batch entry consumed must be appended after all matched entries instead
  of being dropped or defaulted to position `0`. Source: `.get(r[0], 0)` default at `:385`; repository
  evidence.
- `REQ-004`: The tool message emitted for an id-less entry keeps `tool_call_id == ""` — the value
  `_reject()` already produces (`tool_preparation.py:83`) — and no synthetic id is introduced anywhere.
  Source: issue `Required Changes` bullet 3 ("state the chosen behavior explicitly"); decision recorded in
  Design.
- `REQ-005`: For batches where every `id` is present, non-empty, and unique, observable behavior is
  unchanged: result order, `_collect_tool_result_msgs()` output, `ctx.stats.stat_tool_calls` /
  `stat_tool_errors` accounting, `out_failed_keys` contents, denial handling through
  `_build_denied_messages()` (`:388-390`, `:412`), one `save_many()` call per round, and the DAG plan built
  by `build_execution_groups()`. Source: issue `Constraints` bullet 3.
- `REQ-006`: `scripts/agent/tool_preparation.py` is not modified: id-less calls stay rejected with kind
  `configuration` and never reach approval, planning, or execution, and the `_PrepFailure` tuple shape is
  unchanged. Source: issue `Constraints` bullets 1-2; verified against `tool_preparation.py:75-84`.
- `REQ-007`: Add regression and characterization coverage in `tests/agent/test_tool_runner.py`, including a
  mutation check that a restored `tc["id"]` makes the new tests fail. Source: issue `Testing Expectations`.
- `REQ-008`: The tool-execution documentation states that a malformed provider tool call is answered per
  call, in batch position, and never aborts a turn. Source: issue `Documentation Impact`.
- `REQ-009`: `scripts/agent/tool_runner.py` stays inside `tools/check_module_size.py`'s 16384 B gate and its
  radon complexity does not worsen. Source: `routing.md` Tools → "When to run which tool"; measured
  headroom (Design).

## Design
**Why positional, not id-keyed.** `D-2` shows the map itself is the problem: `{tc["id"]: i ...}` cannot hold
two positions for one id, and `.get(r[0], 0)` silently assigns position `0` to anything unmatched. Making the
key access lenient (`tc.get("id") or ""`) would remove `D-1` while leaving `D-2` untouched, and would also put
id-less entries at the front by default. So the ordering step becomes a walk over the declared batch: for each
entry, take the earliest not-yet-consumed result whose `tool_call_id` equals that entry's id (an absent id is
treated as `""`), and append whatever no entry consumed. This is total for every batch shape, needs no ids at
all to be correct for entries whose id is missing, and stays identical to today's behavior when ids are unique
and non-empty (each entry matches its own result in order). The algorithm was validated against the five
shapes in `Problem` before this plan was written: all five returned declared order, and an unmatched result
was appended last.

**Boundary and purity.** The merge is a pure function over `(tool_calls, results)` with no `ctx`, no I/O, and
no import outside the module — so it is testable directly and does not move responsibility out of the round
owner (`skills/DESIGN.md` Import Layer Contract, `tool002 REQ-013`'s purity requirement). Preparation,
approval, scheduling, execution, stats, denial handling, and persistence sites are not touched.

**Attribution limit.** A result can only be paired positionally when its call carries no usable id; if a
provider emitted several id-less calls and the execution order differed from the declaration order, the
pairing could be wrong. Since id-less calls are rejected before execution (`REQ-006`), the entries that
actually need positional pairing are preparation failures, which `prepare_tool_calls()` already produces in
declaration order — so the limit is documented rather than engineered around.

**Size and complexity budget.** `scripts/agent/tool_runner.py` is 15526 B against the 16384 B gate, and it is
not baselined: 858 B of headroom, which the two sibling plans also want to spend. The helper is therefore
budgeted at 25-35 lines including its docstring (net ≈ +400 to +700 B over the three lines it replaces),
with `check_module_size.py` as a hard gate inside the implementation phase, and `radon cc` bounded as stated
in `AC-8`. If the gate fails, the answer is not a larger file and not a new module invented here: stop and
record the blocker (`UNK-04`), because the module split is `tool002`'s already-frozen decision.

**Sequencing with the sibling plans.** All three open plans edit this one function. `tool002` `REQ-011`
explicitly preserves the `KeyError` and defers it to this issue; `tool003` `AC-4` freezes the *form* of the
sort at `:385`, which this plan removes. `tool002`'s `pair_round_results()` would subsume this merge entirely
if it landed first. `UNK-03` records the decision; the recommendation is this plan first, then a scoped
revision of the two frozen sibling criteria when those plans are re-frozen, so no plan is silently overtaken.
