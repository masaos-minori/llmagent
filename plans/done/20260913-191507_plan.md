# Fix SearchDiagnostics.degraded field inconsistency during search execution

## Goal
Make `_search_all_queries()` (`scripts/rag/stages/search.py`) set `SearchDiagnostics.degraded`
based on `embed_failed`/`fts_errors` at construction time, so `ctx.search_diagnostics.degraded`
is accurate immediately after `SearchStage.run()`, instead of only becoming accurate later
when `PipelineDiagnostics.from_run_result()` recomputes it independently.

## Priority
Medium

## Scope
- **In-Scope**: Setting `degraded=embed_failed > 0 or fts_errors > 0` in
  `_search_all_queries()`'s `SearchDiagnostics(...)` construction
- **Out-of-Scope**: Changes to the `SearchDiagnostics` dataclass definition
  (`models_result.py`); changes to `PipelineDiagnostics.from_run_result()`'s existing
  (correct) recomputation in `diagnostics.py`; changes to existing warning log
  messages; unifying the two same-named but distinct `SearchDiagnostics` classes
  (`rag.models_result.SearchDiagnostics` vs. `rag.diagnostics.SearchDiagnostics` — see
  Background; a real naming collision, but out of scope for this fix)

## Background
`rag.models_result.SearchDiagnostics` (`models_result.py:100-112`) has a
`degraded: bool = False` field. `_search_all_queries()`
(`scripts/rag/stages/search.py:26-73`) constructs and returns this class without
setting `degraded`:
```python
return all_results, SearchDiagnostics(
    embed_ok=embed_ok,
    embed_failed=embed_failed,
    fts_errors=fts_errors,
)
```
This is stored on `ctx.search_diagnostics` (`search.py:110`, confirmed) and later
copied to `RagPipeline.last_search_diagnostics` and `PipelineRunResult.diagnostics`
(`stage_lifecycle.py:143,161`, confirmed) — both still holding `degraded=False`
regardless of actual failures.

**Re-verified 2026-09-13** (this cycle): a second, distinct class also named
`SearchDiagnostics` exists in `rag.diagnostics` (`diagnostics.py:21-46`,
`@dataclass(frozen=True)`, `degraded: bool` with no default). Its
`from_run_result()` classmethod correctly computes
`degraded = embed_failed > 0 or fts_errors > 0`. `RagPipeline.get_diagnostics()`
(`pipeline.py:355-364`, the only public-facing diagnostics API found) calls
`PipelineDiagnostics.from_run_result(embed_ok=..., embed_failed=..., fts_errors=...)`,
which internally reconstructs `rag.diagnostics.SearchDiagnostics` correctly —
so the public `get_diagnostics()` dict's `degraded` value is NOT affected by this bug.
The bug is confined to the `rag.models_result.SearchDiagnostics` instance living on
`ctx.search_diagnostics` / `RagPipeline.last_search_diagnostics` /
`PipelineRunResult.diagnostics`, whose `.degraded` attribute a caller could read
directly (bypassing `get_diagnostics()`) and get a stale `False`.

No current caller was found reading `.degraded` on this object directly (checked
`scripts/rag/`, `scripts/mcp_servers/rag_pipeline/`, and `tests/rag/` — only
`embed_ok`/`embed_failed`/`fts_errors` are read from `PipelineRunResult.diagnostics` in
existing tests, e.g. `tests/rag/test_rag_quality_regression.py:108-110,172-173,245`).
This is a latent bug: the field carries a name that promises live, correct information
but is stale-by-construction until this fix.

## Problem
`ctx.search_diagnostics.degraded` (and its copies on `RagPipeline.last_search_diagnostics`
and `PipelineRunResult.diagnostics`) is always `False` immediately after
`SearchStage.run()`, regardless of `embed_failed`/`fts_errors`, because
`_search_all_queries()` never sets it. Any future caller reading this field directly
(rather than going through `get_diagnostics()`) would silently get a wrong answer.

## Reason for change
Set `degraded` at the point `SearchDiagnostics` is constructed in
`_search_all_queries()`, matching the calculation already used correctly in
`rag.diagnostics.SearchDiagnostics.from_run_result()`, so the field is accurate at
every point in its lifecycle rather than only after a separate recomputation.

## Implementation intent
In `_search_all_queries()`, compute `degraded = embed_failed > 0 or fts_errors > 0`
immediately before the return statement and pass `degraded=degraded` to the
`SearchDiagnostics` constructor call.

## Requirements
- `REQ-001`: `_search_all_queries()` must set `SearchDiagnostics.degraded` to
  `embed_failed > 0 or fts_errors > 0` at construction time

## Design
This task is classified as **Path A** (small task): affects 1 file, no public interface
changes, no database schema changes.

This cycle's re-verification confirmed the Issue's technical claim is accurate — this
is a genuine (if currently dormant) bug, unlike the sibling issues from the same review
batch (bugs001-003, cfg002) whose claims did not hold against current code. The
additional finding (a second, distinct `SearchDiagnostics` class in `rag.diagnostics`)
explains why the public `get_diagnostics()` API is unaffected, narrowing this fix's
urgency but not its correctness — the bug is real on the object callers could read
directly.

Key design decisions:
1. Compute `degraded` inline in `_search_all_queries()` rather than importing
   `rag.diagnostics.SearchDiagnostics.from_run_result()`'s logic — the two
   `SearchDiagnostics` classes are unrelated types; duplicating a one-line boolean
   expression is simpler and safer than cross-importing between them
2. Do not touch `rag.diagnostics.SearchDiagnostics` or unify the two classes — that is
   a larger refactor with its own blast radius, out of this Plan's scope
