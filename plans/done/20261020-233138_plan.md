## Goal
Record, per SQLite database that carries an upgrade path (`workflow.sqlite`, `eventbus.sqlite`, `mdq.sqlite`), the minimum source schema the current release must still upgrade from, why each migration is kept, the removal condition, and the owner — in the canonical database design document and the operator document. This is a decision-recording task; it removes or changes no migration.

## Background
- Source: an investigation of the design documents dated 2026-10-20 listing backward-compatibility features and persistent-data migrations. Every claim below was re-checked against current code on 2026-10-20.
- The migrations are data-preserving upgrade paths, not compatibility shims for an old API. Removing one without knowing which schemas still exist in deployment would make the service fail to start on, or silently misread, an older database. Keeping all of them indefinitely grows the startup path and the test matrix.
- Workflow: incremental migrations `_WORKFLOW_MIGRATIONS` are applied by `apply_workflow_migrations()` in `scripts/db/schema_sql.py` and invoked from `scripts/db/create_schema.py`. A `workflow_schema_version` table records the version, and `scripts/agent/services/workflow_schema.py` rejects a version mismatch at startup. (Confirmed by code)
- EventBus: two migration paths exist. `_EVENTBUS_MIGRATIONS` / `apply_eventbus_migrations()` in `scripts/db/schema_sql.py` runs from `create_schema.py`; `_init_schema()` / `_migrate()` in `scripts/eventbus/schema.py` runs when the service starts against an existing `events` table. Both drop retired columns; the second also converts legacy `consumer_delivery.acked_at`. No schema-version table exists for EventBus. `tests/db/test_eventbus_schema_equivalence.py` checks that bulk initialization and first start produce the same schema. (Confirmed by code, Verified by test)
- MDQ: `_migrate_legacy_chunks_schema()` in `scripts/mcp_servers/mdq/db_schema.py` detects the legacy `chunks` shape through `PRAGMA table_info(chunks)` and recreates the tables. It carries no version marker. (Confirmed by code)
- A search of `docs/` for a minimum supported schema version, a supported-from version, or a baseline schema found nothing. (Confirmed by code: absence verified by search)
- Owner decision recorded 2026-10-21 (user, as owner): the minimum supported source schema of every database is the current release schema; the only deployment is the single host using `/opt/llm`. Inventory of that host on 2026-10-21 (read-only): `workflow.sqlite` records `workflow_schema_version` `1.1.0`, equal to `WORKFLOW_SCHEMA_VERSION` in `scripts/db/schema_sql.py`; `eventbus.sqlite` was recreated from the current DDL (its previous file held test-written data with a `consumer_offsets.last_offset` shape found only in `tests/db/test_create_schema.py`); `mdq.sqlite` `chunks` starts with `chunk_id` (current shape, not the legacy `id`). The legacy offsets directory `/opt/llm/offsets` is empty. (Confirmed by code and by read-only inspection)
- Owner naming follows `docs/41_db/db_08_active_databases.md`, where a database's Owner is the component that owns it (workflow engine, EventBus service, `mdq-mcp` server); decisions without a component owner belong to the repository maintainers.

## Problem
No document or code defines the oldest schema each database must still be upgraded from. Without that baseline nobody can say which migration is removable, and there is no recorded owner or removal condition for any of them. EventBus additionally has two migration paths and no version marker, so "which version is this database" cannot be answered from the database itself.

## Reason for Change
Migration removal is a data-integrity decision that must rest on a stated baseline, not on the absence of recent complaints. Recording the baseline now lets later cleanup work be filed and reviewed against a fixed criterion, and exposes whether the duplicated EventBus path and the missing version marker are intentional.

## Implementation Intent
- Treat this as a decision-recording task. The output is a short, present-tense statement per database in the canonical database design document: the minimum supported source schema, the reason migrations are kept, the removal condition, and the owner.
- Keep the document at the level of intent and constraints. Do not copy migration identifiers or DDL into documentation; they are derivable from the code.
- The deployed-database inventory lives outside the repository. The issue asks the owner to supply it; it must not be guessed.
- Any follow-up that deletes code is a separate issue, filed only after the baseline shows the migration is unreachable.
