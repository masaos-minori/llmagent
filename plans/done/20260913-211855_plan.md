## Background
The Issue's cited claim
(`docs/03_rag_03_04_query_pipeline-search-stages.md:79`: "**Warning:**
`use_rrf=False` is NOT a harmless fallback; it represents a **significant
degradation in quality**.") is confirmed accurate — this exact warning exists,
alongside a qualitative mechanism/impact table (lines 83-86) and usage guidance
(lines 88-92).

**Re-verified 2026-09-13** (this cycle): confirmed no quantitative data backs the
severity claim: `grep -rln "recall@k|precision@k"` across `docs/` and `tests/`
found no match anywhere in the repository — no retrieval-quality benchmark of any
kind comparing `use_rrf=True`/`False` exists. `grep -rl` across `docs/adr/` for
"use_rrf" and related terms found no ADR referencing this trade-off. The existing
warning's severity ("significant degradation") and the qualitative mechanism
description (RRF's cross-list ranking vs. dedup-only's `rrf_score=0.0` for all
hits) are accurate as *mechanism* descriptions — confirmed against
`FusionStage`'s actual implementation — but the *magnitude* claim ("significant")
is not backed by any measured comparison.

## Problem
An operator deciding whether disabling RRF is an acceptable trade-off for their
use case has only a qualitative severity claim ("significant degradation") with
no quantitative basis, no measured threshold for when the trade-off is acceptable,
and no design-review record — the warning cannot inform an actual go/no-go
decision beyond "be cautious."

## Reason for change
Add a note stating plainly that no quantitative data, threshold, or ADR backs this
warning's severity claim, so an operator knows any decision to disable RRF would
need its own quality measurement for their specific use case, rather than relying
on an unquantified "significant" characterization.

## Implementation intent
Add a note after the existing "Search Quality Trade-off" section (after line 96)
stating: (1) no recall@k/precision@k or other quantitative benchmark comparing
`use_rrf=True`/`False` exists in this repository; (2) no ADR documents specific
thresholds for when disabling RRF is acceptable; (3) if RRF is disabled for
latency reasons, the actual quality impact for the specific use case should be
measured rather than assumed from this qualitative warning alone.
