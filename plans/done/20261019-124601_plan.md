## Goal
- Make `deploy/build_binaries.sh` resolve nuitka on hosts whose certificates are only in the system store, by exporting `UV_SYSTEM_CERTS` with an overridable default of `true` before its first `uv` call, and verify it with a test that needs neither Nuitka nor network access.

## Priority
Medium

## Scope
- **In-Scope**:
  - One overridable `UV_SYSTEM_CERTS` export (with a comment) in `deploy/build_binaries.sh`, next to the existing `UV_NO_DEV` export.
  - One sentence in `skills/deploy/workflow.md` Phase 1b about the default and the override.
  - A behavioral test in `tests/tools/test_manage_binaries.py` that runs the script against a stub `uv` and checks the exported value.
- **Out-of-Scope**:
  - Certificate handling for any other tool or script, and the host's certificate bundle itself.
  - Changing how the other deploy scripts set `UV_SYSTEM_CERTS` (they set it inline for their own `uv run` calls).
  - Nuitka flags, the entry table, `tools/manage_binaries.py`, and the deployment document (it lists no build prerequisites).
  - Running a real build or touching `/opt/llm`.

## Background
- Plan Gap recorded while implementing `plans/done/20261019-104249_plan.md` (deploybin001): the owner asked on 2026-10-19 to add it as a requirement; the original plan and its procedures were already archived, so it was filed as `issues/20261019-123439_deploybin002_build-script-needs-system-certificates.md`.
- The project already runs `uv` with the system certificate store: `AGENTS.md` documents `uv sync --dev --system-certs`, and `deploy/deploy.sh`, `deploy/start_agent.sh`, `deploy/init_db.sh`, and `deploy/setup_services.sh` set `UV_SYSTEM_CERTS=true` inline for their `uv run` calls. `deploy/build_binaries.sh` sets `UV_NO_DEV` only.

## Problem
- Observed on the build host on 2026-10-19: `BUILD_ONLY="agent" NUTKA_JOBS=2 bash deploy/build_binaries.sh` failed at once with `nuitka not available`; the fallback `uv run --with nuitka[onefile]==4.2.2 nuitka` reported `Failed to fetch: https://pypi.org/simple/nuitka/ ... invalid peer certificate: UnknownIssuer`. With `UV_SYSTEM_CERTS=true` the same command succeeded (agent build 383 s, then a full 11-binary build of 2561 s), so the certificate store is the only difference.
- The failure message points at nuitka, not at certificates, and neither the skill nor the deployment document mentions the variable.
- Confirmed by source inspection (2026-10-19): `export UV_NO_DEV="${UV_NO_DEV:-1}"` precedes every `uv` execution in the script (`command -v uv`, `uv python find`, `uv python dir`, and the nuitka resolution); the `uv run` text before it only defines the `NUTKA_PRIMARY_CMD` and `NUTKA_FALLBACK_CMD` arrays and does not execute.

## Reason for Change
- Operational reliability: the build host cannot build without a variable the operator must know to set, and the failure message misleads.
- Consistency: every other deploy script already requests the system certificate store.

## Implementation Intent
- Export `UV_SYSTEM_CERTS` with a default of `true` in the same style as `UV_NO_DEV` (`"${UV_SYSTEM_CERTS:-true}"`), so an operator-set value, including `false`, wins.
- Test behavior rather than text order: run the script with a stub `uv` first on `PATH` that records `UV_SYSTEM_CERTS` and fails, so the script stops at its nuitka resolution without Nuitka or network access.
- Keep the change minimal: no other `uv` or Nuitka behavior changes.

## Requirements
- `REQ-001`: `deploy/build_binaries.sh` exports `UV_SYSTEM_CERTS` with an operator-overridable default of `true` before its first `uv` execution, with a short comment saying why.
- `REQ-002`: The deploy workflow's Phase 1b states that the build sets `UV_SYSTEM_CERTS=true` by default and how to override it.
- `REQ-003`: A test proves the default (`true`) and the override (an explicit value is kept) without Nuitka, network access, or `/opt/llm`.

## Risks
- **Risk**: Forcing the system certificate store breaks a build host whose system store lacks the needed certificates. → **Mitigation**: Respect an operator-set value, so `UV_SYSTEM_CERTS=false` restores the old behavior; documented in Phase 1b (UNK-01).
- **Risk**: The stub-`uv` test depends on the script's pre-check order. → **Mitigation**: The test asserts only the recorded variable and that the script exits non-zero without creating build directories; if the order changes, the test fails visibly.
- **Risk**: The test accidentally reaches a real `uv`, Nuitka, or `/opt/llm`. → **Mitigation**: A restricted `PATH` with the stub first, and `BIN_DIR`/`OUTPUT_DIR` in `tmp_path`.
