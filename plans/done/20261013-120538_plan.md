## Goal
- Make the shell, github, file-read, file-write, and file-delete MCP servers fail closed: each refuses to start when its server-side `auth_token` is empty or absent, and otherwise rejects every request that does not carry the configured Bearer token (including `/health`). Each server gets a server-side `auth_token` and registers the shared authentication middleware, so that ADR-007 INV-09 holds and Known Issue MCP-001 can be removed.

## Priority
High

## Scope
- **In-Scope**:
  - A server-side `auth_token` field in the configuration models of the five servers, loaded from `${ENV:...}` like the git and cicd servers.
  - `auth_token` entries in the five server-side TOML files, using the environment variable names already used by `config/agent.toml`.
  - In each of the five server modules: a startup refusal when the configured token is empty (fail closed), followed by one `attach_auth_middleware()` call.
  - Test updates that keep the existing suites valid under authentication: a shared Authorization-header helper, the existing test files that call these apps, and the one integration test that starts the real shell server.
  - New real-application tests for the five servers: rejection and success paths, and the fail-closed startup refusal.
  - Documentation: removal of Known Issue MCP-001, the ADR-007 Known Deviations and INV-09 verification, the `adr_01_index.md` rows, and the per-server authentication descriptions.
  - A rebuild-and-deploy verification step for the compiled binaries and the deployed configuration.
- **Out-of-Scope**:
  - Any change to the shared middleware (`scripts/mcp_servers/server.py`), the loopback health admission (covered by `mcp006`), or token comparison logic.
  - The git, cicd, rag-pipeline, and web-search servers (their empty-token behavior is unchanged).
  - Per-tool authorization, role-based tokens, token rotation.
  - The mdq-mcp exception and the EventBus authentication model.

  - Plan-mode tool blocking and the workflow status display.

## Background
- Known Issue MCP-001 records that the five servers never register `attach_auth_middleware()`. A runtime check (in-process requests, no network) confirmed it: `/v1/tools` without a token returns 200 for these servers and 401 for the git server, which registers the middleware.
- The Agent already treats these servers as authenticated: startup validation rejects an empty `auth_token` for every enabled MCP server, the HTTP transport and the post-startup health check send the Bearer token (closed issue `mcphealthauth01`), and the servers are started with an inherited environment, so the variables the Agent requires are present for them.
- The protected servers (cicd, git, rag-pipeline, web-search) read an `auth_token` from their own `config/*_mcp_server.toml`, resolved from the same environment variable the Agent configuration uses. mdq-mcp is the documented exception. For git and cicd an empty value makes the middleware skip authentication.
- Decision (user, 2026-10-13, resolving the former UNK-02): the five servers in this Plan fail closed on the server side, so they must not copy the git/cicd accept-all behavior for an empty value.
- `mcp006` (Frozen Plan `plans/20261012-185654_plan.md`, implementation not started) removes the loopback health admission from the shared middleware and edits `docs/22_mcp/mcp_06_14_mcp-authentication-setup.md`.

## Problem
- Evidence (`Verified by run`): requests made in-process to each server application without an Authorization header returned 200 on `/v1/tools` for shell, github, file-read, file-write, and file-delete; the git server returned 401 without a token and 200 with the correct Bearer token.
- Evidence (`Explicit in code`): `attach_auth_middleware()` is called only by the cicd, git, rag-pipeline, web-search, and mdq servers; the five affected servers create their FastAPI application without it, and their configuration models and TOML files define no `auth_token`.
- Consequence: the Agent-side token requirement gives these servers no protection. Any local process that can reach the loopback port can call tools that read, write, delete, or run commands.

## Reason for change
- ADR-007 INV-09 and the MCP security chapter state that every MCP server except mdq-mcp verifies the Bearer token. The shell and file-write/delete servers expose the most dangerous tools, so their missing check matters most.
- Failing closed removes the silent path (an empty value or an absent key leaving a server unauthenticated), which is how this defect would otherwise recur, for example during a partial deployment.
- The fix aligns the code with the adopted design instead of weakening the ADR, and closes an open High-severity Known Issue.

## Implementation intent
- Per server: a `get_str`-resolved `auth_token` field in the configuration model, an `auth_token = "${ENV:...}"` entry in the server TOML, and, in the server module right after the application is created, a refusal to start when `_cfg.auth_token` is empty followed by `attach_auth_middleware(...)` with that token.
- Enforce fail-closed in the server module, not in the configuration model's `from_dict` (see Design for the evidence): the models are built from minimal dictionaries by many existing tests, while only the application import path should refuse an empty token.
- Keep `/health` behind the same token; do not add an exemption. The Agent's health poll already sends the server token.
- Keep the existing suites meaningful: send the Authorization header from the existing tests that call these applications (including the integration test that starts the real shell server, which would otherwise be skipped silently), and leave `tests/conftest.py` unchanged.
- Land the test changes first (an extra header is harmless before the servers change), then add the servers one at a time (each step independently revertable), then documentation, then the deployment verification.

## Design
- Path B (more than three files). Analyses run: architecture (`lint-imports`: 5 contracts kept, 0 broken; the change adds no import across a contract boundary because the servers already import `mcp_servers.server`), dependency graphing (the five server modules, their configuration models, the five TOML files, and the tests that import the server applications, build the configuration models, or start the shell server), historical analysis (30-day churn in the Affected areas table; one maintainer under two name spellings authors nearly all commits, so Bus Factor is High; `git-fame` is not installed), and operational inspection (no process listens on the MCP ports in the development environment; `lsof` and `pydeps` are not installed, recorded as N/A; `pip-audit` is not needed because no dependency changes).
- Quality baseline: `radon cc` reports no block of grade C or worse in the five server modules; `vulture` reports only two findings outside the target files (`rag_pipeline_service.py` `debug_fn`, `server.py` `middleware_type`); `bandit` on the three server packages reports three pre-existing findings (an assert in `read_static_helpers.py`, a hardcoded-string false positive for `'not_set'` in `github_server.py`, and the `subprocess` import in `shell_service.py`), none introduced by this change. The diff-cover baseline is taken in Step 1.
- Pattern: the configuration side is identical to the git and cicd servers: each configuration model gets `auth_token: str = ""` loaded with `get_str(d, "auth_token")` (which resolves `${ENV:...}` and raises when the variable is unset). Each server module imports `_FastAPIApp` and `attach_auth_middleware` from `mcp_servers.server`, and right after `FastAPI(...)` and before any exception handler or route it raises `RuntimeError` when `_cfg.auth_token` is empty and then calls the middleware with that token. The two statements are repeated in the five modules (uniform, two lines each); no shared helper is added because `scripts/mcp_servers/server.py` belongs to `mcp006`.
- Where fail-closed is enforced (decision with evidence): three places were compared. (a) In each model's `from_dict`: rejected, because the models are built from minimal dictionaries by many existing tests (11 call sites in 8 test files for `GitHubConfig.from_dict`, 3 for `FileReadConfig.from_dict`, plus the service fixtures built from them), so every one would need a token or a test-only escape hatch. (b) In each server module before the middleware call: chosen; only importing the application is affected, and `tests/conftest.py` already sets the five variables to a non-empty value, so test collection is unaffected. (c) A shared helper: rejected for now (it would need a new module or an edit to `server.py`). A server TOML that lacks the key, or a variable set to an empty string, both resolve to an empty token and are refused by (b); an unset variable is refused earlier by `get_str`.
- Measured impact (scratch copy outside the repository, with the models, TOML files, and server modules patched as designed, `tests/conftest.py` unchanged): the baseline for `tests/mcp_servers` plus six other importing test files (`tests/agent/services/test_mcp_tool_discovery.py`, `tests/agent/test_rag_get_cfg.py`, `tests/agent/test_security_audit_config_isolation.py`, `tests/docs/test_github_config_consistency.py`, and the two Agent tests that build the real agent configuration) is 2049 passed, 6 skipped. With the design and no test edits: 71 failed, 1976 passed, 8 skipped. Of the 71 failures, 70 are requests without an Authorization header (HTTP 401, or a `KeyError` on the 401 body) in 10 files (counts in the Affected areas table) and 1 is the `FileReadConfig` field-set test. The 2 additional skips are the shell cases of `test_mcp_tools_validation.py`, which start the real shell server and wait for `/health` without a token, so they report "did not become healthy" and are skipped without failing (the reason `test_mcp_tools_validation.py` is a target). With the header helper at 43 `TestClient` construction sites in the 10 files plus the corrected field set: 2047 passed, 8 skipped, 0 failed; the skips return to 6 once `test_mcp_tools_validation.py` sends the token (to be confirmed in Step 3). The two Agent tests pass unchanged, so `tests/conftest.py` and those tests are not edited. The rest of the suite (all other directories, 6542 tests) in the same scratch copy: 6521 passed, 16 skipped, 5 failed; the 5 failures are tests under `tests/tools` that read the live `docs/` tree, which the scratch copy did not contain, and they pass in the repository.
- Runtime evidence for the environment: no `[mcp_servers.*]` entry in `config/agent.toml` sets `env`, `filter_env(None)` returns `None`, and `subprocess.Popen(env=None)` inherits the Agent environment, so the variables the Agent requires reach the servers. Agent startup rejects an empty token, the transport and health checker send the Bearer token, and the launcher's port probe treats any response below 500 (including 401) as "responding" (documented in the `mcp006` Plan), so protected servers start and are polled correctly.
- Real-application tests run in a separate interpreter with the variable set (the application reads its token at import time), like the web-search test; the fail-closed tests use the same mechanism with an empty or unset variable.
- Sequencing with `mcp006`: this Plan does not edit `scripts/mcp_servers/server.py`. The only shared target is `docs/22_mcp/mcp_06_14_mcp-authentication-setup.md`, so the documentation step for that file runs after the `mcp006` implementation.
- Deployment and partial deployment: production starts compiled binaries (`/opt/llm/bin/mcp_*`, built by `deploy/build_binaries.sh` from `scripts/`) and reads configuration from `/opt/llm/config`, which `deploy.sh` already copies for these five files. The code change therefore needs a binary rebuild, and the new binaries and the new configuration must be deployed together. A new binary with an old configuration now fails closed: the key is absent, the token is empty, and the server process refuses to start; the Agent then cannot spawn it, and Known Issue AGENT-004 (a non-required subprocess MCP server aborts Agent startup when it fails to spawn) means the Agent start aborts rather than running without that server. An old binary with a new configuration ignores the new key (no unknown-key rejection was found in the configuration loading) and stays unauthenticated as today, so it is not a regression. Rollback is the reverse: restore the previous binaries and configuration together.

- **Risk**: A real-application test in a separate interpreter is slower or environment-dependent (the shell server needs its sandbox backend to start) → **Mitigation**: reuse the web-search test's pattern and timeout; the in-process check already imported all five applications in the development environment.
- **Risk**: The header helper's token value drifts from the value in `tests/conftest.py` → **Mitigation**: the helper's docstring names `tests/conftest.py`, and AC-4 fails visibly (401 everywhere) if they diverge.
