## Background
NC-035 originally asked why crawl depth is limited to 3 hops and max pages to 200, and a 2026-09-27 deep-dive additionally found that `crawler.py`'s fallback default for `max_pages` (500) diverges from the deployed `config/crawler.toml` value (200) — every other `cfg.get(key, default)` fallback in the same file (`fetch_timeout`, `crawl_concurrency`, `sqlite_timeout`, `sqlite_busy_timeout_ms`, `skip_external`) exactly mirrors its deployed config value; `max_pages` is a confirmed outlier.

This Plan's own Step 3 verification corrected one causal claim in the Issue: the Issue attributes the 500-vs-200 divergence to commit `e184208c` ("chore: apply recommended default values to config files", 2026-07-05) having "retuned" the deployed config from 500→200 without the code being updated to match. Direct inspection found `e184208c`'s diff touches only `config/common.toml`, `memory.toml`, `rag.toml`, `rag_pipeline.toml`, `security.toml`, and `tools.toml` — it never touches `config/crawler.toml` at all. Tracing `config/crawler.toml`'s (and its pre-split predecessor `rag_pipeline.toml`'s) full history shows `max_pages = 200` has been the deployed value since its earliest appearance, and `crawler.py`'s `cfg.get("max_pages", 500)` fallback has likewise been `500` since it was first introduced — the two values were never in sync at any point in history; this was never a case of "config retuned, code left behind," but of the two defaults simply having been chosen independently and never reconciled. This does not change the bug itself (the mismatch is real and still breaks the file's established fallback-mirrors-deployed-value convention) — only the historical narrative, which this Plan's Background records accurately in place of the Issue's stale causal claim.

Separately, the user, acting as owner for this Plan cycle, confirmed no historical rationale exists for the `max_depth=3`/`max_pages=200` operational limits themselves and selected "no rationale, accepted as-is" — since this closes NC-035's remaining open question in the same cycle as the bug fix, the entry can be removed entirely rather than merely trimmed (per the Issue's own conditional Documentation Impact instruction, which anticipated this outcome: "NC-035 is resolved or reduced to only the still-unknown 3/200 rationale question").

## Problem
`scripts/rag/ingestion/crawler.py`'s `max_pages` fallback (`cfg.get("max_pages", 500)`) would silently revert to 500 pages per site instead of the intended 200 if the `max_pages` key were ever removed or misconfigured in `config/crawler.toml` — a behavior change with no warning, breaking the file's own "fallback mirrors deployed value" convention that every other fallback in the same constructor follows.

## Reason for change
This is a real, evidence-confirmed bug (not merely an unknown-rationale documentation gap): the code's fallback default should follow the same convention as every sibling config value in the same file, to avoid a silent behavior change on missing config. Per the governance doc's own Part 2 "Status Values" rule, once both the bug and the rationale question are resolved, the NC-035 entry must be removed rather than retained with a closed-out status.
