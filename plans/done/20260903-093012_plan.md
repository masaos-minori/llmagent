## Goal
- Add a layered, process-level regression suite proving the system runs one
  Production-grade policy, requires MCP authentication, and exposes Agent-internal
  HTTP services only through loopback — complementing, not duplicating, the
  per-file unit tests already specified by `localremoval`, `loopbackonly`, and
  `mcpauth`'s own Plans.

Medium

## Problem
Configuration-only tests cannot prove actual process behavior: a value may be
correct in TOML while a startup argument, environment override, or framework
default causes a wildcard listener (source Issue Problem). The three dependency
Plans already specify unit-level tests for their own changes
(`localremoval` REQ-011: 10 test files; `loopbackonly` REQ-005: 2 test files;
`mcpauth` REQ-007: 3 test files) — none of those are process-level or exercise the
actual shipped `config/agent.toml`. `tests/integration/` already exists with
process-level patterns (`test_agent_mcp_integration.py`,
`test_mcp_transport_crash.py`), but no network-namespace-isolation or equivalent
external-unreachability test pattern exists anywhere in `tests/` (repository
evidence: `rg` for `unshare`/`netns`/network-namespace patterns found no match).
Per `loopbackonly`'s and `localcleanup`'s own Step 3 inspections
(`plans/20260903-091921_plan.md`, `plans/20260903-092746_plan.md`), no Docker,
systemd, nginx, Caddy, or Kubernetes manifest exists in this repository — the
source Issue's "deployment validation scripts and CI workflows" and "Docker
host-port mappings... ingress/service publication" targets do not apply here.

## Reason for Change
Synthetic policy tests may pass while the shipped configuration or actual startup
path behaves differently; only layered, process-level tests catch that gap (source
Issue Reason for Change) — this is exactly the coverage the three dependency
Plans' unit tests do not provide on their own.

## Implementation intent
Add a new `tests/integration/test_production_security_regression.py` covering, at
the process/integration level: a full Agent startup using the actual (or a copied,
disposable) `config/agent.toml` under a `SecurityProfile`-removed/Production-only
build (per `localremoval`), asserting startup succeeds only with valid, non-empty
`auth_token`s (per `mcpauth`) and loopback-only MCP server bindings (per
`loopbackonly`); a process-level socket-inspection test using `socket.getsockname()`
against a spawned MCP server subprocess, confirming the actual bound address; an
external-unreachability test using the strongest isolation mechanism available in
this environment (network namespace via `unshare` if permitted, otherwise a
documented equivalent — e.g. binding a probe socket to a non-loopback interface and
confirming connection refusal) with a documented fallback manual-verification
procedure per the source Issue's Documentation Impact. Add a new section to
`docs/05_agent_10_04_operations-and-observability-validation-and-troubleshooting.md`
documenting the suite's coverage, which tests require elevated/platform
capabilities, and the manual socket-check fallback.

## Requirements

  (per `localremoval`) using a full Agent startup, not a synthetic config object,

  (tool tiers, ownership, routing, workflow definitions, database schemas,

  inspecting its actual bound socket address via `socket.getsockname()`, covering
  accepted (`127.0.0.1`) and — if the subprocess can be made to attempt one for the
  test — rejected (private-LAN, wildcard) bind attempts.
- `REQ-004`: Add process-level tests for required-vs-optional MCP startup failure
  (required-component failure aborts startup; optional-component failure disables
  only that tool) and for disabled-tool LLM-visibility exclusion.
- `REQ-005`: Add process-level MCP authentication tests (missing/invalid/valid
  Bearer token against a spawned MCP server subprocess) and a log-capture test
  confirming token redaction in actual emitted log output.
- `REQ-006`: Add an external-unreachability test using the strongest isolation
  mechanism available in the test environment, with a documented, tested manual
  fallback verification procedure if true network-namespace isolation is
  unavailable.
- `REQ-007`: Confirm (no test needed — see Problem) that deployment-manifest lint
  for Docker/systemd/nginx/Kubernetes does not apply, since none of those artifacts
  exist in this repository.
- `REQ-008`: Document the regression suite's coverage, platform-capability

the Issue's Target Files or Areas lists 6 broad areas across `tests/agent/`,
`tests/mcp_servers/`, `tests/integration/`, Event Bus tests, configuration-

deployment manifests exist). The core design decision is layering: this Plan
creates one new process/integration-level test file rather than scattering
process-level assertions across the existing per-module unit test files the three
dependency Plans already specify — keeping "layer" (unit vs. process/integration)
as the boundary between this Plan's scope and theirs, per the source Issue's own
Constraint ("Do not replace focused unit tests with only a large end-to-end test")
applied in the opposite direction (do not scatter process-level tests into the
unit-test files either). No architecture/dependency-graphing findings apply beyond
the cross-Plan reference map above, since this Plan introduces no production
code — historical/bus-factor analysis is not applicable to a new file with no
