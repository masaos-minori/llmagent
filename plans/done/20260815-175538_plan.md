# Work Plan: Mitigate CLIView Writer Protocol partial test double risk

## Goal

Prevent AttributeError at runtime when test doubles implement only a subset of Writer Protocol methods, by making the protocol compatible with partial implementations.

## Scope

- `scripts/agent/cli_view.py`: Writer Protocol definition and CLIView implementation
- Any existing test doubles that use Writer Protocol
- Protocol usage sites that call Writer methods

## Assumptions

1. Test doubles are created by developers who may only care about the methods they need to mock
2. `@runtime_checkable` enforcement is currently relied upon as a safety check
3. Default implementations should be no-op (do nothing) rather than raise errors
4. The Reader Protocol does not have the same risk (only 1 method)

## Unknowns

1. How many existing test doubles in the codebase implement only partial Writer Protocol? Need to search for usages.
2. Should optional methods be marked with `typing.Optional` or use `abc.ABC` with default implementations?
3. Are there any non-test consumers of Writer Protocol that might rely on `isinstance(obj, Writer)` checks?
4. Would adding default implementations change the contract for legitimate implementations?

## Affected areas

- `scripts/agent/cli_view.py` — Writer Protocol definition (line 24), CLIView implementation (line 88+)
- Test files that create Writer test doubles
- Callers that pass Writer instances to CLIView or related services

## Design

Two approaches are considered:

**Approach A: Add default implementations via ABC mixin**
Create a base class with no-op implementations of all methods, then have both Writer Protocol and CLIView inherit from it. This preserves `@runtime_checkable` semantics while allowing partial implementations.

**Approach B: Use `typing.Protocol` with `__getattr__` fallback**
Add a `__getattr__` to the Protocol that raises a descriptive error only when an unimplemented method is actually called. This keeps the Protocol pure but provides better diagnostics.

**Chosen approach: Approach A** — ABC mixin with no-op defaults. This is the cleanest solution because:
- Partial test doubles automatically satisfy the protocol (they inherit the base class)
- `isinstance(obj, Writer)` works correctly for partial implementations
- No silent failures — calling an unimplemented method still raises AttributeError with a clear message
- Minimal changes to existing code

## Implementation steps

1. Create an abstract base class `WriterBase` in `cli_view.py` with no-op implementations of all 10 Writer methods
2. Make `Writer` Protocol inherit from `WriterBase` (Protocol + ABC pattern)
3. Make `CLIView` inherit from `WriterBase` instead of implementing methods independently
4. Ensure `WriterBase.__init_subclass__` or metaclass prevents instantiation directly
5. Search for existing Writer test doubles and update them to inherit from `WriterBase` where applicable
6. Add type hints for optional method overrides in Writer Protocol docstrings
7. Run lint and typecheck to verify no regressions

## Validation plan

- **Unit test**: Create a partial Writer test double inheriting from `WriterBase` with only `write_token` overridden, verify `isinstance(partial, Writer)` returns True
- **Unit test**: Verify that calling an unimplemented method on a partial double raises AttributeError with a clear message
- **Unit test**: Verify `CLIView` instance satisfies `isinstance(view, Writer)`
- **Integration test**: Verify normal operation with full CLIView writer still works
- **Manual**: Check that no existing tests break after the change

## Risks

1. Adding a base class changes the MRO (method resolution order). If multiple inheritance is used elsewhere, this could cause subtle issues.
2. If `@runtime_checkable` is relied upon for strict checking, Approach A weakens that guarantee. However, the trade-off is worth preventing silent AttributeErrors.
3. Existing test doubles that do NOT inherit from `WriterBase` will still fail `isinstance` checks, but they will also get better error messages when calling unimplemented methods.
4. If the Protocol is used outside of tests (e.g., for structural typing in production), the no-op defaults could mask bugs.
