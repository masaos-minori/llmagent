# Plan: Remove unused `kwarg` parameter from `LlmHotConfigHandler.apply_one`

## Goal
Simplify `LlmHotConfigHandler.apply_one`'s signature from 4 parameters to 3 by dropping
the unused `kwarg: str` parameter, since only `instance`, `field`, and `value` are read
inside the method body (`setattr(instance, field, value)`). This removes dead surface
area from a public `staticmethod` without changing any observed behavior.

## Scope

### In-Scope
- `scripts/shared/llm_hot_config.py`: change `apply_one`'s signature (drop `kwarg`
  parameter); update the sole call site inside `apply_config`'s loop.
- `tests/shared/test_llm_hot_config.py`: update the three existing `apply_one(...)` call
  sites (`test_apply_one_sets_field`, and two calls inside
  `test_apply_one_sets_non_float_field`) to the new 3-argument form.
- Re-verification via `rg "apply_one"` that no other call site exists before and after
  the change.

### Out-of-Scope
- `LlmHotConfigHandler.apply_config`'s own public keyword-only signature — unchanged.
- `HOT_CONFIG_FIELDS` tuple contents/shape — unchanged.
- `scripts/shared/llm_client.py`'s `LLMClient.apply_config` (the runtime-facing wrapper
  that delegates to `LlmHotConfigHandler.apply_config`) — unchanged, not touched by this
  plan; it calls `apply_config`, not `apply_one`, directly.
- Any other module's `apply_config` (`scripts/agent/services/config_reload.py`,
  `scripts/agent/history.py`, `scripts/shared/tool_executor.py`) — unrelated classes with
  their own `apply_config` methods, confirmed via `rg "apply_config\("` to be independent
  of `LlmHotConfigHandler`.
- Documentation (`docs/90_shared_03_04_runtime_and_execution-caching-and-reference-part2.md`)
  — this is a document-only planning phase; doc text does not reference the `kwarg`
  parameter by name/arity, so no doc edit is implied by this change (verify at
  implementation time; do not edit docs in this phase).

## Design
`LlmHotConfigHandler` (`scripts/shared/llm_hot_config.py`) is a plain internal helper
class with no inheritance, no dynamic dispatch, and two `staticmethod`s: `apply_one`
(single-field `setattr`) and `apply_config` (keyword-only public entry point that loops
over `HOT_CONFIG_FIELDS` and calls `apply_one` for each non-`None` value). It sits in
`scripts/shared/`, imported by `scripts/shared/llm_client.py`'s `LLMClient.apply_config`
(read at `scripts/shared/llm_client.py:89-114`), which is the actual runtime-facing
surface used by callers such as `scripts/agent/services/config_reload.py`. That wrapper
calls `LlmHotConfigHandler.apply_config(self, temperature=..., ...)` — it never calls
`apply_one` directly, so `LLMClient`'s own public API and all of its callers
(`config_reload.py`, tests) are fully insulated from this change.

The change is a pure intra-module signature simplification:
- `apply_one`'s only caller is `apply_config`'s `for attr, kwarg in HOT_CONFIG_FIELDS`
  loop (line 53), which currently passes `(instance, attr, kwarg, value)`. The loop
  variable `kwarg` remains necessary there as the dict lookup key (`args.get(kwarg)`); only
  the trailing argument passed *into* `apply_one` is dropped.
- No import-boundary or layering concern: `apply_one` is not exported/re-exported
  elsewhere, and `scripts/shared/` is a leaf-ish shared-utilities layer already imported
  one level up by `llm_client.py` — this change doesn't add or remove any import edge.
- `radon cc scripts/shared/llm_hot_config.py -s` shows `apply_one` at complexity **A (1)**
  and `apply_config` at **A (3)** — both already at the lowest complexity grade, so this
  change has no complexity implication either way.
- `mypy scripts/shared/llm_hot_config.py` and `bandit scripts/shared/llm_hot_config.py`
  both currently pass clean (0 mypy errors, 0 bandit issues) — the plan's job is to keep
  both clean after the 3-argument change.

  under `tools/`, or doc-embedded code sample treated as executable) is missed by the
  `rg` scan. → **Mitigation**: `rg "apply_one"` was run against the full repository root
  (not scoped to `scripts/`/`tests/`) in this planning pass and turned up only the two

  field-name typo (since the args are positional and easy to reorder). → **Mitigation**:
  the requirement document and this plan both specify the exact before/after argument
  list per call site; step 2's checklist enumerates each of the three edits individually
  and the validation plan re-runs the full `test_llm_hot_config.py` suite (10 tests) to
  catch any value regression immediately. Likelihood: low.

  realizing it was deliberately removed, re-creating the original dead-parameter issue.
  → **Mitigation**: `apply_one`'s docstring already describes it as "Set a single config
  field on an instance" (matching the 3-argument behavior); no further mitigation is
  in scope for this plan since it is a coding-convention/code-review concern rather than
  something this change can enforce mechanically. Likelihood: low.
