# Plan: tool005 - Args masking: decide the boundary, extend masking to nested args, document the decision

## Goal
- Decide and implement the intended behavior of tool-argument masking: `mask_args()` masks
  recursively through nested dicts and lists so no configured value reaches a logged or audit sink
  unmasked; the interactive approval preview intentionally stays unmasked, and this boundary is
  documented. This removes the divergence the issue reports between what is masked, what is
  logged, and what the user sees.

## Priority
Medium (issue Severity: MEDIUM, Score: 3)

## Scope
- **In-Scope**:
  - Recursive masking in `scripts/agent/tool_result_formatter.py::mask_args` (dicts, lists, any
    nesting depth; copy-on-write, input never mutated).
  - An updated `mask_args` docstring stating the logging-only scope of masking.
  - Characterization tests pinning the boundary: nested masking in unit and audit paths; the
    preview path never masks.
  - Documentation update making the boundary explicit in the Agent tool-configuration docs.
- **Out-of-Scope**:
  - Changing the default `masked_fields` value (recorded as `UNK-01`).
  - Applying masking to preview output (issue Option 1 — rejected, see Design).
  - `agent/secrets_masker` (auth-token masking in LLM-bound text) — a separate feature.
  - Adding an env-var override or renaming config keys; the issue's `agent.settings.*` /
    `AGENT_MASKED_FIELDS` naming does not exist in this repository (verified absent).
  - Any change to the call sites (`tool_runner.py`, `tool_audit.py`, `tool_approval.py`) or to
    `build_preview` behavior.

## Background
`masked_fields` exists to keep sensitive argument values out of persistent logs. The issue
observes that `mask_args()` only masks top-level keys, so values nested inside dict or list
arguments pass through unmasked into audit records and console output. The decision of *where*
masking should apply at all (logs only, or also the user-visible approval preview) was never made
explicit anywhere in code or docs. Verification against the current source confirmed both facts
and found the preview gap is larger than the issue states: no masking at all is applied to
approval previews (see Problem). The user decided the semantics on 2026-10-23: **Option 2 —
masking is a logging concern only; it must cover nesting; previews stay raw by documented
decision.**

## Problem
Verified defects at HEAD (2026-10-23):

1. `scripts/agent/tool_result_formatter.py:32` is a top-level-only dict comprehension:
   `{k: ("***" if k in masked_fields else v) for k, v in args.items()}`. A nested value such as
   `{"edits": [{"file_content": "..."}]}` is written verbatim into every sink that consumes the
   masked dict.
2. The approval-preview path never applies masking, not even top-level: `check_approval()` builds
   the preview from the raw args (`scripts/agent/tool_approval.py:174`, fallbacks `:181`, `:184`
   → `build_preview`, which for `write_file`/`edit_file` renders `args["content"][:200]` —
   `tool_result_formatter.py:47-52`). The only use of `mask_args` in the approval flow is the
   plan-mode blocked message (`tool_approval.py:213,215`). So today the boundary between "masked"
   and "unmasked" output is accidental, not designed.
3. The default masked name `file_content` (`scripts/agent/config_dataclasses.py:182`,
   `scripts/agent/config_section_builders.py:204-205`) matches no current tool-argument schema:
   file-mcp write tools expose `path`, `content`, `edits`
   (`scripts/mcp_servers/file/write_tools.py:50,73`); no `file_content` argument key exists
   anywhere in `scripts/` (verified by grep). Under the default config the masking feature is
   inert.
4. `docs/23_agent/agent_08_03_configuration-tools-memory.md:32` describes `masked_fields` only as
   "argument keys masked in console output" — incomplete and imprecise relative to (1)-(3).

## Reason for Change
The issue exists to turn an accidental, half-applied behavior into a decided one. With tool args
increasingly carrying structured payloads (edit batches, MCP tool arguments), top-level-only
masking misses exactly the values a user would configure `masked_fields` for; and the undocumented
preview/log split will keep producing "why is it masked here but not there" confusion for every
future approval-flow change. The fix is small (one function) and settles the semantics.

## Implementation Intent
Extend `mask_args` with a private recursive helper so every call site — which already funnels
through `mask_args` unchanged — gains nested coverage for free. Keep the feature's scope as its
own docstring already states ("Used before logging to prevent sensitive data leakage"): all
log/audit sinks mask; the interactive approval preview does not, because its purpose is to show
the user the actual operation they are approving. Record the decision in code (docstring) and in
the Agent configuration docs. No call-site or preview-builder changes.

## Design
**The decided boundary (user decision, 2026-10-23; issue Option 2).** Masking applies to every
persistent or transcript-style output: audit events (`tool_audit.py:46,157`), the REPL tool-call
line (`tool_runner.py:204-205` → `_log_and_emit_tool_call`), and the plan-mode blocked notice
(`tool_approval.py:213,215`). It does not apply to the interactive approval preview
(`check_approval` → dry-run preview or `build_preview`, `tool_approval.py:174,181,184`).
Rationale, grounded in verified facts: `mask_args`'s own docstring scopes the feature to logging
("Used before logging to prevent sensitive data leakage"); the preview exists precisely so the
user can judge the operation they are approving, and the preview's reader is the same person who
supplied the arguments — masking it (Option 1) would remove the approval signal while protecting
nothing. Option 1 was therefore rejected. This plan turns today's accidental split into the
documented rule without changing any observable preview behavior.

**Recursive helper, copy-on-write.** `mask_args` delegates to a private
`_mask_value(value, masked_fields)`: for a dict, build a new dict masking keys whose name is in
`masked_fields` and recursing into the rest; for a list, build a new list recursing into items;
scalars pass through. Containers are rebuilt unconditionally — the simple comprehension is not
reused — so the input args tree is never mutated; the same `args` object continues to flow to
approval, planning, and execution (`tool_runner.py`, `tool_approval.py`). Top-level output shape
is identical to today's for flat args, so `REQ-003` holds. `_extract_resource_scope`
(`tool_audit.py:30`) iterates the top level only; unchanged.

**Why the helper lives inside `mask_args`.** All four sink call sites already import and call
`mask_args`; extending this one function is the only change that propagates to every sink without
touching the scheduler, approval, or audit modules (the import-layer contract is untouched: no new
imports, no new module — the file is 3458 B against the 16384 B gate).

**Inert default is documented, not changed.** `file_content` matches no current argument key
(verified against `write_tools.py` and a repo-wide grep), so masking is opt-in in practice. The
docs update states which real key names exist so the feature is usable; changing the default is
`UNK-01`, explicitly out of scope.

**Complexity and size budget.** Measured baseline at HEAD: `mask_args` radon A(3); file's worst
block is `build_github_preview` B(9); `vulture`/`bandit`/`semgrep` clean; file 3458 B, not
baselined. The helper is budgeted at ≤ 12 lines, complexity ≤ A(6); the new worst block must
remain the pre-existing B(9) (`AC-7`/`AC-8` gates).
