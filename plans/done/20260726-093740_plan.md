# Plan: Eliminate the redundant per-call approval prompt in `RepositoryGateway._gate_write`

## Goal

For every risky/write tool call, `run_approval_checks()` (and thus the interactive
approval prompt it drives) executes at most once per logical call, in every mode —
by removing the redundant, provably-unreachable-without-prior-approval second call in
`RepositoryGateway._gate_write()`, keeping `tool_runner._run_approval_gate()` as the
single authoritative approval gate.

## Scope

**In scope:**
- Remove the `run_approval_checks()` call (and the now-unused `classify_risk`
  branch) from `RepositoryGateway._gate_write()` in `scripts/agent/repository_gateway.py`.
- Update `RepositoryGateway`'s module docstring and `_gate_write()`'s docstring to
  describe the new, single-gate reality instead of the current "policy → approval →
  execution → audit" claim.
- Correct the stale docstring on `tool_runner._run_approval_gate()` (currently
  describes an unimplemented `skip_in_workflow_mode`-based skip) to state plainly
  that this is the sole per-tool-call approval gate for the batch.
- Remove the dead `skip_in_workflow_mode` parameter from
  `tool_approval.run_approval_checks()` (confirmed unused by any real caller —
  see Unknowns/Assumptions).
- Update/remove the tests that assert the now-deleted behavior:
  `tests/test_repository_gateway.py::TestReadBypass... test_write_tool_denied_by_user`
  (gateway no longer denies independently) and
  `tests/test_tool_approval_paths.py::TestRunApprovalChecksSkipInWorkflowMode`
  (parameter no longer exists).
- Add a regression test proving `run_approval_checks` is invoked exactly once for a
  risky tool call that goes through `tool_runner.execute_all_tool_calls` end-to-end
  (batch gate → gateway execute).
- Add a code comment on `RepositoryGateway` documenting the now-load-bearing
  precondition: callers must route write/risky tool calls through
  `tool_runner.execute_all_tool_calls()` (or otherwise call
  `tool_approval.run_approval_checks()` themselves) before invoking
  `RepositoryGateway.execute()`, since the gateway no longer gates approval itself.

**Out of scope:**
- Any change to `tool_policy.check_preflight()` or `classify_operation_type()` — the
  gateway's non-interactive policy preflight check (`repository_gateway.py:90`)
  is kept as-is; it is idempotent/non-interactive so calling it twice (once inside
  `run_approval_checks`→`check_approval`, once directly in `_gate_write`) causes no
  double-prompt and is left untouched. Not the subject of this requirement.
- Any change to `check_approval()`, `_prompt_user_approval()`, or the risk
  classification rules themselves in `tool_approval.py` / `tool_policy.py`.
- Introducing a new "already-approved tool-call-id" signal threaded through
  `RepositoryGateway.execute()`'s signature (Option (a) from the requirement doc) —
  rejected; see Design for justification.
- Any workflow-mode-specific wiring — confirmed dead / not applicable (see Unknowns).
- Changes to `docs/*.md` (document-only phase; out of scope for this plan-creation
  cycle per workflow rules).

## Assumptions

1. `review_mode` for this planning cycle is `autonomous` (per task instructions), so
   Step 7 (moving the requirement file) proceeds without an approval gate.
2. No production code path exists today, or is expected in the near term, that
   invokes `RepositoryGateway.execute()` / `_gate_write()` for a write/risky tool call
   without first passing through `tool_runner.execute_all_tool_calls()`'s
   `_run_approval_gate()`. This is verified for all current call sites (see Unknowns
   U1), but is an assumption about future code, not a structural guarantee — flagged
   as a risk below with a mitigating code comment + regression test.
3. `check_preflight()` being called twice per write tool call (once inside
   `check_approval()` at `tool_approval.py:151`, once directly in `_gate_write()` at
   `repository_gateway.py:90`) is acceptable residual redundancy: it is a pure,
   non-interactive policy check with no user-facing side effect, so it does not
   contribute to the double-prompt defect this plan fixes, and removing it is not
   required by the acceptance criteria.

## Design

**Decision: Option (b) — eliminate the redundant call site in
`RepositoryGateway._gate_write()`; `tool_runner._run_approval_gate()` remains the
single authoritative interactive approval gate.**

Justification:

1. **U1 proves it is safe today.** The call graph shows `RepositoryGateway.execute()`
   is reachable in production only via `execute_one_tool_call()`, which is only
   reachable via `execute_all_tool_calls()`, strictly after `_run_approval_gate()` has
   already filtered `tool_calls` into `approved_calls`/`denied_ids`. A tool call that
   was denied at the batch gate never reaches `_gate_write()` at all — it is not in
   `approved_calls`, so `execute_one_tool_call` is never invoked for it. There is no
   currently-existing code path where `_gate_write()` sees a tool call that hasn't
   already been approved.

2. **Option (a) (threading an approved-call-id signal) was considered and rejected
   for this pass** because it requires a larger, more invasive change than the
   defect warrants: `RepositoryGateway.execute(ctx, tool_name, args)` and
   `_gate_write(ctx, tool_name, args, op)` do not currently receive the tool call's
   `id` at all — only `tool_name`/`args` are passed from `execute_one_tool_call()`
   (`tool_runner.py:139`, which has `tc["id"]` available but does not forward it).
   Implementing (a) would require changing the public `RepositoryGateway.execute()`
   signature (to accept `tool_call_id` or the full `tc` dict), touching every
   call site and every test that constructs/calls `gateway.execute()` directly
   (`tests/test_repository_gateway.py`), plus adding new mutable state on
   `AgentContext` (or `TurnState`) to hold the "already-approved" id set and clearing
   it at the right lifecycle boundary (start of each `execute_all_tool_calls()` call,
   to avoid stale approvals leaking across turns/rounds). That is materially more
   surface area, more places to get wrong, and more state to reason about than
   Option (b), for a benefit (defense-in-depth against a *hypothetical* future
   direct caller) that Option (b) also covers via a documented precondition and a
   regression test, per the mitigation below.

3. **What is preserved:** `_gate_write()` keeps its non-interactive
   `check_preflight()` call (line 90) as a cheap, idempotent defense-in-depth policy
   check — it has no interactive/user-facing side effect, so keeping it causes no
   double-prompt and requires no test rewrites beyond what U4 already identifies.

4. **Docstring corrections required by the requirement doc's Implementation
   Instructions #4:**
   - `repository_gateway.py` module docstring (lines 3-10): change step 2 from
     "Approval prompt (tool_approval.run_approval_checks per call)" to something
     like: "Approval is enforced upstream, once, by
     `tool_runner.execute_all_tool_calls()`'s batch-level gate before any tool in
     the batch reaches this executor; `_gate_write()` no longer re-runs it."
   - `_gate_write()`'s docstring ("Enforce policy, prompt for approval, execute,
     audit.") becomes "Enforce policy, execute, audit. Approval is expected to have
     already been granted by the caller's batch-level gate (see module docstring);
     this method does not prompt."
   - `tool_runner._run_approval_gate()`'s docstring (lines 480-482) drops the
     inaccurate `skip_in_workflow_mode`/"per-tool approval is skipped during the
     execute stage" claim and instead states: "This is the single approval gate for
     the batch — approved calls proceed to execution (including through
     `RepositoryGateway`) without any further approval check."

5. **`skip_in_workflow_mode` removal satisfies Implementation Instructions #5:**
   U2 confirms it is dead (never set `True` by any real caller). Since Option (b)
   does not repurpose it as the dedup mechanism, it is removed entirely from
   `run_approval_checks()`'s signature rather than wired up, per the requirement
   doc's explicit "if... unused after the fix, remove" instruction.

## Risks

- **Risk:** Removing `_gate_write()`'s independent approval check weakens
  `RepositoryGateway`'s "single enforcement boundary" design intent (per its own
  module docstring) — a future code path that calls `RepositoryGateway.execute()`
  for a write tool *without* first going through `tool_runner.execute_all_tool_calls()`
  would silently skip interactive approval entirely (only non-interactive
  `check_preflight()` would still run).
  **Likelihood:** low today (U1 confirms no such path exists now), medium over time
  as the codebase grows.
  **Mitigation:** (1) the updated module docstring and inline comment (Implementation
  step 2) explicitly document this precondition so it is visible to future authors;
  (2) the new regression test (Implementation step 6) pins the current single-path
  invariant and will need conscious updating if a second call path is ever added,
  surfacing the gap at review time rather than silently; (3) tracked as a residual,
  documented risk rather than escalated to `issues/*_risks.md`, since it is fully
  mitigated by the above and not an active/unmitigated defect.
- **Risk:** Deleting `test_write_tool_denied_by_user` could reduce test coverage if
  its assertions were subtly broader than "gateway denies independently" (e.g. also
  covering result-shape/error-type conventions for denied results).
  **Likelihood:** low — the equivalent denied-result shape (`_denied_result(...)`,
  `is_error=True`) is still exercised by the policy-denial test
  (`test_write_tool_blocked_by_policy`) which remains unchanged.
  **Mitigation:** Implementation step 4 rewrites rather than blindly deletes;
  reviewer should confirm no unique assertion is lost, per the Validation plan's
  gateway test run.
- **Risk:** Removing `skip_in_workflow_mode` is a public-signature change to
  `run_approval_checks()`. If any external/plugin code outside `scripts/agent/`
  and `tests/` calls it with that keyword argument, removal would break it.
  **Likelihood:** very low — `run_approval_checks` is an internal `agent.*` module
  function with only two production call sites, both inside `scripts/agent/`
  (confirmed by repo-wide grep in U2), and it is not exported via any public API
  surface (no `__init__.py` re-export found for `agent.tool_approval`).
  **Mitigation:** Implementation step 7's full-suite run would surface any missed
  caller as an immediate `TypeError`.

No risk identified above is unmitigated/blocking, so no `issues/*_risks.md` file is
required for this plan.
