## Background
ADR-003「RuntimeToolRegistry を唯一のルーティング権威とする」は、Decision #8 で「Safety Tier と Write 属性は Routing、承認、監査で同一の RuntimeTool を参照する」と定め、INV-04 で「静的 ToolRegistry は実行時 Routing に使用せず、Drift 検証・テスト・文書生成に限定する」と定めている。しかし `classify_operation_type()` は、承認判定（`classify_risk()` 経由）に使われる UNKNOWN/READ の分岐において、静的 ToolRegistry の `get_all_tool_names()` を参照している。

## Problem
- `scripts/agent/tool_policy.py:69` で `get_registry().get_all_tool_names()`（静的 ToolRegistry）を使い、対象 Tool 名がそこに存在しなければ `OperationType.UNKNOWN`（→ `classify_risk()` で `RiskLevel.HIGH` に直結、line 152-156）、存在すれば `OperationType.READ` を返す。
- `cfg.approval.tool_safety_tiers` は `agent.toml` の手動設定値であり（`scripts/agent/config_builders.py:397`）、RuntimeToolRegistry の Discovery 結果から自動生成されない。したがって、MCP から動的に発見されたが (a) `tool_safety_tiers` に未設定、かつ (b) 静的 ToolRegistry にも未登録、の Tool は、実際には `RuntimeTool.agent_safety_tier` が `READ_ONLY` であっても `UNKNOWN`（`RiskLevel.HIGH`）に分類される。これは issue の Impact 記載どおり再現することを確認した。
- `plans/done/20260819-182458_plan.md` は同じコード（`tool_policy.py:54-71`, line 69 の `get_all_tool_names()` 呼び出し）を分析済みだが、その Scope は「docstring のみ、振る舞い変更なし」であり、static ToolRegistry を fail-safe 用途として「維持」する決定を記録しただけで、ADR-003 INV-04/Decision #8 との整合性は評価していない。本 Plan はこの点を初めて扱う。

## Reason for change
ADR-003 は Accepted 済みであり、Decision #8 の「同一の RuntimeTool を参照する」という不変条件は現状コードで満たされていない。承認判定に使われる risk 分類が、ルーティング権威（RuntimeToolRegistry）とは別の情報源（静的 ToolRegistry の存在確認）に依存している状態を解消する必要がある。

## Implementation intent
- `classify_operation_type()` に `registry: RuntimeToolRegistry | None` パラメータを追加する。`registry` が非 None かつ対象 Tool が登録済みなら `OperationType.READ`、登録が無い（`KeyError`）か `registry` が `None` なら `OperationType.UNKNOWN` とする。ADR-003 Decision #6「静的 RegistryへのFallbackを設けない」に従い、`registry` が None の場合に静的 ToolRegistry へフォールバックしない（fail-closed で UNKNOWN 扱い）。
- `classify_risk()` にも同様に `registry` パラメータを追加し、`classify_operation_type()` へ橋渡しする。
- 呼び出し元（`tool_audit.py` 2箇所、`repository_gateway.py` 1箇所、`tool_approval.py` 1箇所）は、いずれも既に `ctx: AgentContext` を保持しているため、`ctx.services_required.runtime_tools` を新パラメータへ渡すだけで済む。

## Design
- `classify_operation_type(tool_name: str, registry: "RuntimeToolRegistry | None" = None) -> OperationType`: WRITE/DELETE/EXECUTE/API_WRITE の frozenset 判定（既存コード、変更なし）の後、`registry is None` なら `UNKNOWN` を返す。`registry` が非 None なら `try: registry.get(tool_name)` し、`KeyError` を捕捉して `UNKNOWN`、成功すれば `READ` を返す。デフォルト値 `None` を付けるのは、既存の直接呼び出し（存在すれば）との後方互換性のためではなく、呼び出し元すべてを本 Plan の Implementation steps で更新するため実質的に必須引数として扱う（型ヒント上は Optional のまま、fail-closed のデフォルトとして意味を持たせる）。
- `classify_risk(cfg, tool_name, args, registry)`: `registry` を Priority 3 の `classify_operation_type()` 呼び出しへ橋渡しするのみ。Priority 1（`approval_risk_rules`）・Priority 2（`tool_safety_tiers`）の既存優先順位は変更しない。
- ADR-003 Known Deviations には現在「確認済みの差異なし」と記載されている（line 375）。本 Issue の内容は ADR-003 に対する Known Issue として未登録だったため、実装完了後に Known Deviations へ RT-001 を一時登録し解決済みとして記載する運用は取らず、実装が Decision に適合させる本流の修正であるため ADR-003 側の変更は不要と判断する（ADR は「維持すべき Decision」であり、コード側を Decision に合わせる本 Plan はドキュメント差異の記録ではなく実装の是正にあたる）。
