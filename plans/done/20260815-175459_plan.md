# Work Plan: Include StartupFailure details in HttpStartupError message

## Goal
Override `__str__` or `__repr__` on `HttpStartupError` so that printing the exception displays full `StartupFailure` details (server_key, reason, stderr_full) instead of just the reason string.

## Scope
- Add `__str__` method to `HttpStartupError` class in `scripts/agent/http_lifecycle.py`
- Ensure the output includes server_key, reason, and a truncated stderr_tail for readability
- No changes to other modules unless they catch and re-format the exception

## Assumptions
1. `StartupFailure.stderr_full` can be large; truncating to a reasonable tail (e.g., last 512 chars) keeps the message readable
2. The existing `.failure` attribute on `HttpStartupError` is always populated after initialization
3. No downstream code currently relies on the RuntimeError message containing only the reason string

## Unknowns
1. Are there existing consumers of `HttpStartupError` that parse the exception message text? If so, adding fields could break them.
2. Should sensitive information in `stderr_full` be masked before inclusion in the message?
3. Is `__str__` preferred over `__repr__` here? `__str__` is used by `print(exc)` and `str(exc)`, while `__repr__` is used by `repr(exc)` and interactive REPL. For user-facing messages, `__str__` is appropriate.

## Affected areas
- scripts/agent/http_lifecycle.py (HttpStartupError class)
- Any code that catches HttpStartupError and inspects `str(e)` (need to verify none rely on the old format)

## Design
Add a `__str__` method to `HttpStartupError` that formats the full `StartupFailure` dataclass into a human-readable string. The format will include:
- server_key: identifies which MCP server failed
- reason: the high-level cause
- stderr_tail: last ~512 characters of stderr_full for context, masked if needed

This approach keeps programmatic access to the full data intact via `self.failure` while improving the default display.

Example output:
```
HttpStartupError(server_key='my-server', reason='exited early', stderr_tail='...')
```

## Implementation steps
1. Read `scripts/agent/http_lifecycle.py` to confirm the current `HttpStartupError` implementation (lines 44-50)
2. Check if `StartupFailure` has any sensitive fields that need masking (review dataclass definition at lines 35-41)
3. Implement `__str__` on `HttpStartupError`:
   - Format as `f"{self.failure.server_key}: {self.failure.reason}"` for the primary message
   - Append `stderr_tail` if present, truncated to last 512 chars
   - Optionally mask secrets using `_mask_secrets` from `agent.secrets_masker`
4. Search for consumers of `HttpStartupError` that might depend on the old message format
5. Write unit tests covering:
   - `str(HttpStartupError(failure))` includes all three fields
   - `stderr_full` truncation works when content exceeds 512 bytes
   - Empty `stderr_full` does not append trailing whitespace/punctuation
6. Run existing tests to verify no regressions

## Validation plan
- Unit test: `str(HttpStartupError(failure))` contains server_key, reason, and stderr_tail
- Unit test: stderr_tail truncation when stderr_full > 512 bytes
- Unit test: no trailing separator when stderr_full is empty
- Integration test: verify error messages in logs show full context when HttpStartupError is caught and logged
- Manual verification: no consumer parses `str(exc)` expecting only the reason string

## Risks
1. **Breaking change**: If any code parses `str(exc)` expecting only the reason, the new format breaks it. Mitigation: search for such consumers first.
2. **Information leakage**: Including raw stderr in the exception message could expose sensitive data. Mitigation: use `_mask_secrets` on the stderr_tail portion.
3. **Message length**: Very long stderr could make the exception message unwieldy. Mitigation: truncate to last 512 bytes.
