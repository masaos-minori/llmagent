## Goal
- Authorize the resolved remote URL (not merely the remote name) for `git_pull`/
  `git_push`, serialize write operations per canonical repository path, and reject
  execution when the repository's HEAD identity has changed since authorization —
  none of which exist in the current codebase.

## Priority
Medium

## Scope
- **In-Scope**: remote-URL authorization configuration and enforcement for pull/push;
  credential redaction for remote URLs in logs/audit; per-repository-path write
  serialization; a HEAD-identity re-check immediately before mutation; documenting
  the external-process lock limitation; redacted remote identity in audit records.
- **Out-of-Scope**: protected-branch/ref authorization content (`gitauth`, whose
  operation-target model this Plan consumes for the resolved remote — see
  Dependencies/Design); the write-protection pipeline's stage ordering
  (`gitpipeline`); repository-path containment/audit (`gitpathaudit`); extending this
  Plan's remote-authorization/locking to `GitService`'s dead-code dispatch path
  (deferred until `gitdispatch` makes it live, consistent with `gitpathaudit`'s Plan
  precedent — see Design).

## Background
No prior issue covers remote-identity authorization or Git MCP write concurrency —
this is a new gap, not an overlap. This Plan's Step 3 investigation (per the issue's
own AI Implementation Instruction: `rg "remote" scripts/mcp_servers/git/git_service.py
config/git_mcp_server.toml`) confirmed: `git_pull`/`git_push`'s `remote` request field
(`git_models.py:181,195`, default `"origin"`) is validated only by
`_validate_ref(req.remote)` — a check for option-like strings (leading `-`), not
authorization of any kind. No `allowed_remote_urls` or equivalent configuration
exists in `GitConfig` or `config/git_mcp_server.toml` (confirmed by full read of both
— the file documents `allowed_repo_paths`, `read_only`, `max_log_entries`,
`auth_token`, `protected_branches`; no remote-related key). No GitPython
`repo.remotes[...]`/`repo.remote(...)` call exists anywhere in
`scripts/mcp_servers/git/` — remote URL resolution is entirely unimplemented. No
locking primitive (`asyncio.Lock`, `threading.Lock`, `Semaphore`) exists anywhere in
this module — concurrent writes to the same repository are entirely unserialized.
`tests/test_git_concurrency.py` (the issue's cited target) does not exist under
either its cited path or `tests/mcp_servers/git/`.

## Problem
A remote *name* like `"origin"` is only an alias — `git remote set-url origin
<attacker-url>` (or a repository configured with an unexpected origin from the
start) can redirect a pull or push to an unauthorized destination with no detection,
since nothing validates the URL the name currently resolves to. Concurrent write
requests to the same repository can interleave without serialization, and the
`RepositoryState` snapshot captured for authorization is never re-checked against the
repository's actual state immediately before the mutating Git command runs — a
window in which another process (or another concurrent MCP request) could have
changed the repository out from under the authorized assumption.

## Reason for Change
Remote-identity authorization and repository-level concurrency control must land
together: the resolved remote identity and a repository-level lock both need to
remain stable across authorization, execution, and audit — an authorization decision
made against a URL or HEAD state that has since changed is not meaningfully an
authorization at all.

## Implementation intent
Add `allowed_remote_urls: list[str]` (or an equivalent normalized-URL allowlist) to
`GitConfig`/`config/git_mcp_server.toml`, following the existing
`protected_branches`/`allowed_repo_paths` documentation pattern. Resolve the actual
URL a `pull`/`push` request's remote name currently points to (via GitPython's
`repo.remotes[name].url`), normalize it, redact embedded credentials before any
logging, and reject unknown/missing/changed/unauthorized remotes — consuming
`gitauth`'s structured operation-target model (which already resolves pull's
"selected remote" and push's "remote destination ref") rather than defining a second
remote-resolution mechanism. Add a per-canonical-repository-path lock (keyed by the
resolved path, so independent repositories do not serialize against each other) held
across the authorization-to-execution window for write operations. Re-capture HEAD
identity immediately before the mutating Git call and reject if it has drifted from
the state authorization was based on. Document, in code comments and the eventual
doc update, that this lock is process-local and does not constrain a Git process
running outside this MCP server.

## Requirements
- `REQ-001`: Define remote authorization as URL-based (not name-based alone) — a
  remote name is only an alias; authorization must validate what it currently
  resolves to. Recorded as a Design decision per the issue's own unresolved framing
  ("Define whether remote authorization is based on remote name, normalized URL, or
  both").
- `REQ-002`: Add `allowed_remote_urls: list[str]` to `GitConfig`, with a
  fail-closed-when-empty convention consistent with `allowed_repo_paths`, and a
  documented example in `config/git_mcp_server.toml`.
- `REQ-003`: Resolve the actual URL a `pull`/`push` request's `remote` name points to
  (via GitPython), normalize it for comparison, and redact embedded credentials
  (`https://user:token@host/...`) before it appears in any log or audit field.
- `REQ-004`: Reject `pull`/`push` when the resolved remote is unknown, missing,
  changed since a prior authorized value, or not present in
  `allowed_remote_urls`.
- `REQ-005`: Add a per-canonical-repository-path lock (e.g. a process-wide
  `dict[str, asyncio.Lock]` keyed by the resolved repo path) held for the duration of
  a write operation, serializing concurrent writes to the same repository without
  serializing independent repositories.
- `REQ-006`: Re-capture HEAD identity immediately before the mutating Git call and
  reject execution if it differs from the state authorization was based on (a
  TOCTOU guard between Stage 3/5 authorization and Stage 6 execution).
- `REQ-007`: Document, in code comments (and flagged for the deferred doc update),
  that this lock is process-local and does not constrain a concurrent Git process
  running outside this MCP server (e.g. a human's local `git` CLI).
- `REQ-008`: Include the resolved (redacted) remote identity in the audit record for
  `pull`/`push` operations.
- `REQ-009`: Consume `gitauth`'s structured operation-target model
  (`plans/20260904-162951_plan.md` REQ-005, which resolves pull's local branch/
  tracking branch/selected remote and push's local source/remote destination ref)
  for the "selected remote" input to REQ-003/REQ-004, rather than defining a second,
  independent remote-resolution mechanism.

## Design
This is the fifth Plan filed against `scripts/mcp_servers/git/` this session
(`gitauth`, `gitpipeline`, `gitdryrun`, `gitdispatch`, `gitpathaudit` precede it), and
the first to add genuinely new capability (remote authorization, locking) rather than
fix an existing, broken mechanism. It therefore has the fewest direct file-level
conflicts with the other four — it extends `RepositoryState`/`format_output.py`
alongside, not instead of, their other planned edits.

REQ-009's consumption of `gitauth`'s operation-target model is the key coordination
point: `gitauth`'s Plan already resolves *which* remote a pull/push targets (the
"selected remote" for pull, the "remote destination ref" for push) as part of its own
Stage 3 authorization work. This Plan does not re-resolve that — it takes the
already-resolved remote name as input and adds a new question on top: does the URL
that name currently points to match an authorized entry. Building this as a
second, independent remote-name-resolution mechanism (ignoring `gitauth`'s model)
would violate the issue's own Constraint against introducing a second authorization
path.

The lock scope decision (UNK-01) defaults to a process-local `asyncio.Lock` registry
because git-mcp, like the other MCP servers surveyed this session, is a single
FastAPI process per the repository's established pattern (`MCPServer.run_http()`);
a cross-process lock would be over-engineering absent evidence of a multi-worker
deployment. REQ-007's explicit documentation of the external-process limitation
(a human running `git` directly, or another tool entirely, is never constrained by
this MCP server's internal lock) is the honest acknowledgment the issue's own
Required Changes calls for, not a gap to silently paper over.

## Risks
- **Risk**: An in-memory lock registry (UNK-01's default) provides no protection if
  git-mcp is ever deployed with multiple worker processes → **Mitigation**: REQ-007
  documents this limitation explicitly; confirm the single-process deployment
  assumption against `config/agent.toml` before implementation, per UNK-01's
  resolution path.
- **Risk**: Concurrency tests (new file, `test_git_concurrency.py`) can be flaky if
  not carefully constructed (timing-dependent assertions) → **Mitigation**: use
  explicit synchronization primitives (e.g. `asyncio.Event`) to force the interleaving
  under test rather than relying on wall-clock timing.
- **Risk**: This Plan's remote-URL resolution depends on `gitauth`'s operation-target
  model (REQ-009) landing with a compatible shape — if `gitauth`'s implementation
  diverges from its Plan's stated design, this Plan's consumption point may need
  adjustment → **Mitigation**: re-verify `gitauth`'s actual landed interface
  immediately before implementing REQ-009, per this issue's own AI Implementation
  Instruction to re-confirm evidence before editing.
- **Risk**: Deferring remote-authorization/locking enforcement on `GitService`'s
  dead-code path (per Assumptions) means that if `gitdispatch` lands before a
  follow-up extends this Plan's protections there, write tools reached via that path
  would temporarily lack remote authorization and locking → **Mitigation**: flagged
  explicitly in Assumptions/Design so implementers sequencing `gitdispatch` are aware;
  consistent with the same trade-off `gitpathaudit`'s Plan already accepted for
  path-containment (mitigated there by REQ-007's preemptive fix, which this Plan
  found no equivalent need for since neither path currently has remote
  authorization to preserve).
