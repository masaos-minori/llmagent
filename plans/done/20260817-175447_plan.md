## 1. Goal
Unify `[DENIED]`/`read_only=true` guard-denial message formatting into a structured error-code scheme across `git_security.py`'s guard implementations and `git_service.py`'s 10 handlers, enabling MCP clients to handle denials programmatically rather than relying on fragile string parsing.

## 2. Scope
- **In-Scope**: Designing the target structured shape (or deciding not to change); rewriting characterization tests for every guard-denial message; updating `_check_repo_path`/`_check_write` and all 10 `git_*` handlers to use the new shape.
- **Out-of-Scope**: Extending to `scripts/mcp_servers/file/*_service.py`'s analogous guards (requires separate scoping decision); changing which conditions trigger a denial (only the message format changes).

## 3. Assumptions
- A maintainer-approved target shape exists and is documented before implementation begins.
- The current denial conditions remain unchanged — only the message/response shape changes.
- MCP clients currently parse the `[DENIED]` prefix; any new shape must be explicitly communicated as a breaking change.
- The `RepoValidationResult.error_message` field will transition from `str` to a structured type (e.g., `dict` or Pydantic model).

## 5. Affected Areas & Tool Evidence
- **Affected Files**: 
  - `scripts/mcp_servers/git/git_security.py` — guard implementations (`_check_repo_path`, `_check_write`)
  - `scripts/mcp_servers/git/git_service.py` — 10 handlers consuming guard results via `RepoValidationResult`
  - `tests/mcp_servers/git/test_mcp_git.py` — existing guard-denial message assertions
- **Blast Radius**: Any MCP client that parses denial response strings; any code that consumes `RepoValidationResult.error_message`
- **Risk Metrics**: Medium churn — guard-denial paths have stable assertion patterns in tests; low risk of regression if characterization tests are written first
- **Deploy Impact**: None — no config changes, ports, or environment variables affected. However, this is a breaking change for MCP clients that depend on the current string format.

## 8. Risks & Mitigations
- **Risk**: MCP clients parse the `[DENIED]` prefix and break on the new structured shape. → **Mitigation**: Phase 1 must confirm whether any MCP client does this; if so, document as a breaking change and coordinate migration.
- **Risk**: Changing `RepoValidationResult.error_message` from `str` to a structured type breaks other consumers. → **Mitigation**: Phase 2 must verify all callers; if any do, provide backward-compatible adapter.
- **Risk**: Product-level design input is required but unavailable. → **Mitigation**: Phase 1 includes explicit scoping decision; if unavailable, close issue as "not proceeding" until design is available.
- **Risk**: Extending repo-wide creates additional work and potential for inconsistency during rollout. → **Mitigation**: Phase 1 includes scope decision; start with git-only if repo-wide extension is deferred.
