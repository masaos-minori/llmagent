## Goal
- Document the relationship between WorkflowEngine's stage retry
  (`retry_policy.max_attempts`), `ToolLoopGuard.check_retry()`'s in-memory
  per-turn retry-block, and the LLM transport-level retry/reconnect
  parameters, closing ADR-014's own open Known Deviation entry for this gap
  — no behavior change.

## Priority
Medium

## Scope
- **In-Scope**:
  - Adding a distinguishing note near `docs/05_agent_06_03_tool-execution-and-approval-concurrency-safety.md`'s existing `tool_error_retry_max` table row.
  - Adding the three-layer retry landscape description to `docs/05_agent_03_02_turn-processing-flow-llm-tool-loop.md`'s existing ToolLoopGuard section, citing the now-located LLM transport-level retry/reconnect enforcement code path by file/class/function name.

  - Recording, as a non-blocking follow-up question (not silently resolving it), whether the LLM transport-level retry exhausting can compose multiplicatively with WorkflowEngine's stage-retry.
- **Out-of-Scope**:
  - Any change to `ToolLoopGuard`'s actual blocking behavior, `tool_error_retry_max`'s default, or `WorkflowEngine`'s `retry_policy` semantics.

  - The Tool Call idempotency/execution-ID gap and the timeout-hierarchy gap — tracked by separate issues from the same design review.

## Background
This Issue follows a design review (memo2.md) covering "retry ownerの一意化"
(unique retry ownership). The investigation found three distinct retry-shaped
mechanisms at different granularities rather than one, and classified this as
a documentation gap (ADR-014 already records it as a Known Deviation,
directly cross-referencing this Issue's file path) rather than an
implementation defect.

## Problem
Adversarial verification confirmed every Issue claim against current source,
and additionally **resolved** the Issue's own primary open fact-finding item
(the LLM transport-level retry code path, which the Issue states was "not
conclusively located during this issue's investigation"):
- `scripts/agent/workflow/workflow_engine.py`'s `_run_stage_with_retry()`
  (line 231) retries a stage up to `self._wdef.retry_policy.max_attempts`
  (line 244), escalating on exhaustion — confirmed as stated.
- `scripts/agent/tool_loop_guard.py`'s `check_retry()` (line 281) blocks (does
  not retry) a repeated failing `(tool_name, args)` pair once
  `ctx.cfg.tool.tool_error_retry_max` is exceeded (line 288) — confirmed as
  stated.
- **Resolved**: `llm_max_retries`/`llm_retry_base_delay` are enforced by
  `LlmRetryHandler.request_with_retry()` (`scripts/shared/llm_retry.py`,
  static method), invoked from `LLMClient.request_with_retry()`
  (`scripts/shared/llm_client.py`) for the non-streaming call path.
  `sse_reconnect_max` is enforced by `LlmReconnectHandler.stream()`
  (`scripts/shared/llm_reconnect.py`), invoked from `LLMClient.stream()`
  (`scripts/shared/llm_client.py`) for the SSE streaming call path. Neither
  lives in `llm_turn_runner.py`/`llm_turn_executor.py`, confirming the
  Issue's "0 grep hits" finding while correcting its "unresolved as of this
  issue's filing" status — this Plan resolves it.
- `docs/adr/ADR-014-agent-control-plane-responsibility-boundaries.md`'s Known
  Deviations section (confirmed present) already states this exact
  three-mechanism gap in prose and cross-references this Issue's file path
  directly — the Issue's Required Change #2 ("add a short cross-reference
  note to ADR-014") is therefore already partially done; what remains is
  resolving that entry once the underlying docs (below) are written, per
  `rules/coding.md`'s "Documentation notes — Current behavior classification"
  (this is a "Documentation fix required" case: the docs are incomplete, not
  the code behaving incorrectly).
- `docs/05_agent_03_02_turn-processing-flow-llm-tool-loop.md` already
  documents `ToolLoopGuard`'s five guards including the "retry" guard's
  suppression semantics, but does not yet cross-reference
  `WorkflowEngine.retry_policy` or the LLM transport-level retry.
  `docs/05_agent_06_03_...md`'s "ToolLoopGuard Design Decisions" table already
  lists `tool_error_retry_max` (its current row, confirmed present) with no
  distinguishing note from `WorkflowEngine.retry_policy`.

An additional finding beyond the Issue's own text: `LlmRetryHandler`
exhausting `llm_max_retries` raises, which propagates up through
`LLMClient` → the LLM turn path → `WorkflowEngineAdapter._process_turn()`'s
`execute` stage — meaning a fully-exhausted transport-level retry currently
manifests as ONE failed stage attempt to `_run_stage_with_retry()`, which may
then independently retry the whole stage (a fresh `LLMClient` call with its
own fresh transport-retry budget). Whether this multiplicative composition
(`retry_policy.max_attempts` × `llm_max_retries` upper-bounding total LLM
calls for one logical operation) is intended is not evident from either
mechanism's own code or configuration — this is exactly the kind of finding
the Issue's own Unresolved Questions/Constraints anticipated and asked to be
flagged rather than silently resolved (see Unknowns, UNK-01).

## Reason for change
An unstated relationship between three same-named ("retry") mechanisms at
different layers risks a future maintainer either duplicating
WorkflowEngine's retry logic elsewhere (violating ADR-014) or removing a
layer's legitimate, differently-scoped guard on the mistaken belief that
ADR-014 already prohibits it. ADR-014 already carries an open Known Deviation
for this exact gap — closing it (rather than leaving it open indefinitely)
matches `rules/coding.md`'s classification, which requires that a
"documentation fix required" case be fixed directly, not left as a
perpetual, unresolved deviation note.

## Implementation intent
Add the three-layer retry landscape explanation to the two `docs/05_agent_*`
files identified above (near their existing, already-correct retry-related
content, not as new standalone sections), add a short clarifying docstring
note to `ToolLoopGuard`, and then resolve ADR-014's existing Known Deviation
entry for this gap by replacing it with a pointer to the now-complete docs
(per `rules/coding.md`'s "Documentation fix required" handling — fix the docs
directly, then remove the stale deviation note, per that same rule's guidance
not to silently patch around a resolved discrepancy). Record the
multiplicative-retry composition question as a flagged, unresolved follow-up
rather than resolving it, per the Issue's own Constraints.
