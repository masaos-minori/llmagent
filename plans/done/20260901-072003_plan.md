# Plan: Decide whether Routing Drift validation (tool_routing_validation.py) is a current architectural decision or should be deprecated

## Goal
Determine whether `scripts/shared/tool_routing_validation.py`'s drift-validation role is a legitimate current architectural decision requiring formalization, or should be deprecated because it contradicts ADR-003 INV-04.

## Priority
Medium

## Scope
- **In-Scope**: Verify current callers/tests of `tool_routing_validation.py`; confirm ADR-003 INV-04 status; decide formalize vs. deprecate based on architecture-owner direction.
- **Out-of-Scope**: Any other `ToolRegistry` responsibility (its tests/documentation-generation use is already covered by ADR-003 as-is); redesigning `RuntimeToolRegistry` itself.

## Background
The ADR-003/ADR-013 consolidation instructions explicitly required removing all ADR content that assigns ToolRegistry/tool_names a drift-validation role, and required reporting — not silently retaining — any case where the implementation still contains this validation. This issue is that reported follow-up.

Key evidence:
- ADR-003 INV-04 (line 290): "静的`ToolRegistry`は実行時Routingに使用せず、テスト・文書生成に限定する。" — Static ToolRegistry is limited to tests/documentation generation only.
- ADR-003 line 141: "静的`ToolRegistry`または`tool_names`によるDrift検証、静的RegistryへのRoutingフォールバック、名前推測によるRoutingを再導入しない。" — Do not reintroduce drift validation using static ToolRegistry or tool_names.
- However, `tool_registry.py` docstring (lines 6-12) claims ToolRegistry has a drift-detection role: "ToolRegistry serves one verified production role: (a) drift-detection input for McpToolDiscoveryService...".
- `tool_routing_validation.py` is actively imported by `mcp_tool_discovery.py`, `repl_health.py`, and `production_config_validator.py`.
- Tests reference this behavior: `tests/agent/test_startup_routing_drift.py`, `tests/mcp_servers/cicd/test_tool_server_layer_consistency.py`, `tests/mcp_servers/mdq/test_mdq_routing.py`, `tests/shared/test_tool_registry.py`, `tests/shared/test_tool_safety_tiers.py`.

## Problem
An actively-running validation mechanism (`tool_routing_validation.py`) with no governing ADR is an undocumented architectural decision. A future reader of ADR-003 could assume Drift validation is not part of the current design and remove or bypass it without realizing `mcp_tool_discovery.py` still depends on it, or could leave it un-reviewed indefinitely because no document tracks it as a live decision.

Additionally, there is a direct contradiction: ADR-003 INV-04 limits ToolRegistry to tests/documentation generation, but the codebase actively uses ToolRegistry for drift validation — a role not documented in any ADR.

## Reason for change
A decision is needed on whether to formalize this drift-validation role as a current architectural decision (adding it back to ADR-003 or creating a new ADR), or to deprecate and remove it because it conflicts with ADR-003's explicit prohibition on reintroducing drift validation via static ToolRegistry.
