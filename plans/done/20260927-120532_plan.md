## Problem
No SSE client exists anywhere in `scripts/agent/` (confirmed via `rg` — zero references to `eventbus`/`EventBus`, and zero existing SSE-consumption pattern of any kind in `scripts/agent/`). Event Bus's server side already exposes a working SSE stream via `scripts/eventbus/subscribe_route.py::subscribe()` and `scripts/eventbus/replay_route.py::replay()` (`format=sse`). `subscribe_route.py` enforces one active connection per `consumer_id` (`scripts/eventbus/broker.py::ConsumerAlreadyConnectedError`, raised at line 64) — a reconnecting client must not reuse a still-open `consumer_id`.

## Reason for change
Without this integration, the Agent cannot react to Event Bus events in real time; the current workaround (polling via `/replay` or MCP tool calls) adds latency for any workflow needing near-real-time event awareness.

## Implementation intent
Add a dedicated SSE client module under `scripts/agent/`, using `httpx`'s streaming response support to consume Event Bus's existing SSE stream. Handle disconnection by fully releasing the prior connection (respecting `ConsumerAlreadyConnectedError`'s one-connection-per-consumer constraint) before reconnecting. Since no existing Agent-side SSE consumption pattern exists to follow, this is new capability, not a variation on an established local convention — model it after `scripts/agent/memory/embedding_client.py`'s config/error-handling conventions where they apply (dataclass config, typed errors), but the streaming loop itself is new.

## Design
No existing Agent-side SSE/streaming consumption pattern exists to reuse (confirmed via `rg` — zero matches for `text/event-stream`/`StreamingResponse`/`aiter_lines` under `scripts/agent/`), so the streaming-loop and reconnection logic is new implementation, not an adaptation of an established local convention. The client still follows `embedding_client.py`'s surrounding conventions (dataclass config, typed error surface) to stay consistent with how the Agent already wraps other external HTTP dependencies.

`ConsumerAlreadyConnectedError` (confirmed at `scripts/eventbus/broker.py` line 64) is the key correctness constraint: a reconnect attempt using the same `consumer_id` as a not-yet-fully-closed prior connection will fail. The client's reconnection logic (REQ-002) must account for this — either by confirming the prior connection's closure before reconnecting, or by using a fresh `consumer_id` per connection attempt (simpler, avoids a closure race, at the cost of the server treating each reconnect as a new consumer for any consumer-scoped state Event Bus tracks — check `scripts/eventbus/broker.py`'s consumer-tracking scope during implementation to confirm this trade-off is acceptable).

No Python-level import boundary is crossed (same finding as the EVENTBUS-005 Plan: `.importlinter`'s `eventbus-is-isolated` contract only forbids `eventbus` importing `agent`, not the reverse; this client uses HTTP).
