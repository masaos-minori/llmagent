# Plan: Add ast-grep Constraint to Prevent git.exc Import False Positive Recurrence

## Goal

Add a repo-local constraint check that flags any file matching `import git` where `git\.exc\.` appears in the body but `import git.exc` does not. Wire it into `.pre-commit-config.yaml` as a low-cost hook. This prevents future contributors from silently reintroducing the pyright `reportAttributeAccessIssue` false positive on `git.exc.<Name>` attribute access.

## Scope

### In-Scope
- Add a constraint check pattern in `rules/coding.md` §Constraint checks (alongside the existing `ast-grep` one-liners).
- Wire the constraint into `.pre-commit-config.yaml` as a low-cost hook, mirroring how `check-suppression-justification` is wired in.
- Verify the constraint passes on the current codebase after the sibling fix (`plans/20260813-185356_plan.md`) lands.

### Out-of-Scope
- Adding a `types-GitPython`-style stub package to `pyproject.toml`/`uv.lock`.
- Any change to which exception types are caught, their order, or control flow.
- Any change to runtime behavior, log messages, or the `RepoInfoResult`/`GitServiceError` contracts.
- `# type: ignore` suppression — only a fallback if the import-based fix is proven not to resolve the error at a given site.
- Any file outside the constraint-check mechanism itself (the constraint applies to all future files, not just the 2 current ones).

## Assumptions

- The sibling plan (`plans/20260813-185356_plan.md`) has NOT been implemented yet; this plan includes Phase 1 (sibling fix) as a prerequisite so the constraint can be verified immediately upon wiring.
- `ast-grep` is available in the dev environment (already used for other constraint checks per `rules/coding.md`).
- The constraint check is low-cost enough to run on every commit without noticeable CI latency — a single `rg` + `grep` pipeline over `scripts/` takes <1 second.
- No database schema change and no new MCP server are involved; this is a pure tooling/process addition.

## Design

**Phase 1: Sibling fix (prerequisite).** Before the constraint can pass, the 2 known call sites must be fixed. This is exactly what `plans/20260813-185356_plan.md` describes:
- In `git_helper.py`: add `import git.exc` inside the same lazy, function-local scope as the existing `import git` (line 39), preserving the "fast startup when gitpython is unused" property.
- In `git_service.py`: add `import git.exc` at the top level, next to the existing `import git` (line 19).

**Phase 2: Constraint check.** After the sibling fix lands, add the constraint check:

```bash
# git.exc import guard — requires explicit `import git.exc` alongside `import git`
rg "git\.exc\." scripts/ | while read f; do grep -qv "^import git\.exc" "$f" && echo "$f"; done
```

This reads each file containing `git.exc.` and checks whether `import git.exc` appears anywhere in the file. If not, the file is flagged.

Alternative using `ast-grep` (preferred, consistent with existing constraint checks):

```bash
# git.exc import guard — requires explicit `import git.exc` alongside `import git`
ast-grep --pattern 'import git' --lang python scripts/ | while read f; do grep -qv "import git\.exc" "$f" && echo "$f"; done
```

Actually, the simplest approach that works reliably:

```bash
# git.exc import guard — requires explicit `import git.exc` alongside `import git`
rg -l "git\.exc\." scripts/ | while read f; do ! grep -q "import git\.exc" "$f" && echo "$f"; done
```

This finds all files with `git.exc.` usage and flags any that don't contain `import git.exc` anywhere in the file.

**Phase 3: Pre-commit wiring.** Mirror the `check-suppression-justification` hook pattern:

```yaml
- id: git-exc-import-guard
  name: git.exc import guard
  entry: bash -c 'rg -l "git\\.exc\\." scripts/ | while read f; do ! grep -q "import git\\.exc" "$f" && echo "$f"; done'
  language: system
  pass_filenames: false
  always_run: true
```

## Risks

- **Risk**: The constraint check command uses shell piping (`rg | while read ...`) which may behave differently on different shells/environments. → **Mitigation**: use a small inline script or `ast-grep` if available, which is already used for other constraint checks in this project. Likelihood: medium.
- **Risk**: Adding `import git.exc` to `git_helper.py` inside the lazy import scope could cause an `ImportError` if gitpython is not installed (the `except ImportError` handler would catch it, but the behavior might differ from the current silent failure). → **Mitigation**: verified that `git.exc` is a submodule of `git` itself — importing `git.exc` does NOT raise `ImportError` independently of `import git`; the `except ImportError` around `import git` handles the case where gitpython is not installed at all. Likelihood: low.
- **Risk**: A future contributor could add `git.exc` references via a dynamic import (e.g., `__import__("git.exc")`) that the static constraint check wouldn't catch. → **Mitigation**: out of scope for this plan — dynamic imports are rare and should be documented separately. The constraint covers the common copy-paste scenario. Likelihood: very low.
- **Risk**: The sibling plan (`plans/20260813-185356_plan.md`) has not been implemented yet. Without it, adding the constraint now would fail on the current codebase. → **Mitigation**: Phase 1 of this plan includes the sibling fix, ensuring the constraint passes immediately upon wiring. Likelihood: high (mitigated by including Phase 1).
