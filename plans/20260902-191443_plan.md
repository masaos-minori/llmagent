## Goal
Wire `ConfigLoader`'s existing fail-closed primitive (`load_all(strict=True)`) into every
production call site, close two related silent-skip paths (`ProductionConfigValidator`'s
`security_profile` branch ambiguity and `MCPServer.run_http()`'s falsy `own_config_file`
skip), add unknown-top-level-key rejection derived from `agent/config_dataclasses.py`, and
add the ADR-002/ADR-004 test coverage and per-process config table those ADRs' own
Verification sections already flag as missing.

## Priority
High

## Background
`scripts/shared/config_loader.py::ConfigLoader.load_all(strict: bool = False)` only raises
`ConfigMissingError` for a missing file in `_REQUIRED_CONFIG_FILES` (currently the
single-element `frozenset(("agent.toml",))`, matching `_BASE_CONFIG_FILES = ("agent.toml",)`
exactly) when `strict=True`; otherwise it logs at `DEBUG` (line 88: `logger.debug("Config
file not found: %s", name)`) and continues. `ConfigParseError`/`ConfigReadError` are not
caught by this method's `try/except ConfigMissingError` block, so those two failure modes
already propagate and abort the process unconditionally — confirmed by direct read,
`scripts/shared/config_loader.py` lines 68-89.

Re-verified 2026-09-02 (per the Issue's own AI Implementation Instruction to re-confirm
before editing): `grep -rn "load_all(" scripts/` confirms exactly 5 call sites, all
omitting `strict` — `scripts/agent/config_builders.py:60`, `scripts/agent/commands/cmd_config.py:59`,
`scripts/rag/pipeline.py:75`, `scripts/rag/llm_client.py:68`, `scripts/rag/llm_client.py:81`.
`scripts/mcp_servers/git/git_models.py:65` confirms `ConfigLoader().load()` (used by every
MCP server) has no `strict` parameter and is already fail-closed via `_load_single()`
(line 131: `raise ConfigMissingError(...)` unconditionally) — the defect is isolated to
`load_all()`'s default and its 5 callers.

`scripts/agent/config_builders.py:447` confirms `security_profile_val =
SecurityProfile(cfg.get("security_profile", "local"))`, and
`scripts/shared/production_config_validator.py:125` confirms `is_production =

## Problem
`ConfigLoader`'s fail-closed primitive (`load_all(strict=True)`) exists and works correctly
in isolation but no production code path invokes it, and the one downstream check meant to
catch a production misconfiguration (`ProductionConfigValidator`) can itself be silently
routed onto its non-fatal branch by the same missing-file condition, because it depends on a
`security_profile` value read from the very file that might be missing. Additionally,
`MCPServer.run_http()`'s Config Isolation restriction can be silently skipped by a falsy
`own_config_file`, and no config loader rejects unknown/mistyped top-level keys. Together a
missing config file, a misnamed config file, or a mistyped key can currently reach
production silently, contrary to ADR-002/ADR-004's explicit Fail-Fast requirements
(ADR-004 INV-01/INV-02: single failure-handling policy across all environments, no
environment-based relaxation).

## Reason for change
This is a security-relevant gap in the system's fail-closed guarantee: a deployment mistake
as simple as a missing or misspelled `agent.toml` would not stop the Agent process from
starting, and would additionally suppress the one config-content validator that could have
caught related problems. ADR-002 and ADR-004 both already mandate Fail-Fast for exactly this
scenario; ADR-004's own Known Deviations section recommends filing new Known Issues for the
untested INV-09/INV-14 scenario class (this Plan's predecessor Issue is that follow-up for
the `ConfigLoader`-specific portion — see Dependencies).

## Implementation intent
Make a missing/misnamed `agent.toml` fail closed unconditionally at all 5 `load_all()` call
sites (not conditioned on `security_profile`, per ADR-004 INV-01/INV-02 — this also sidesteps
the bootstrapping problem of needing to read `security_profile` from the same file to decide
whether to be strict about it). Fix `MCPServer.run_http()` to fail when `own_config_file` is
falsy. Add unknown-top-level-key rejection in `ProductionConfigValidator`, deriving valid keys
from `agent/config_dataclasses.py` via `dataclasses.fields()` introspection (decided by the
Issue; not a pydantic `extra="forbid"` mechanism — closer in shape to
`ProductionConfigValidator`'s existing bidirectional `tool_safety_tiers` check, generalized).
Add a per-process required-file/required-key/empty-allowed-key table directly in
`docs/adr/ADR-002-config-isolation.md` (decided; not a new standalone doc). Add startup
tests for missing/empty/malformed/permission-denied/misnamed config file scenarios, mapped to
the specific Invariants each verifies, and update ADR-004's INV-07 and ADR-002's
INV-01/INV-02 Verification `Status`/test citations accordingly.

## Requirements
- `REQ-001`: A missing or misnamed `agent.toml` MUST abort `load_config()`/`build_agent_config()`
  (and the other 4 `load_all()` call sites) unconditionally, in every environment — not only
  under a production check.
- `REQ-002`: With `agent.toml` missing, `ProductionConfigValidator`'s checks MUST NOT be
  reachable at all — the process aborts before `security_profile_val` is computed. (Verified
  by test as a consequence of REQ-001's fix, not a separate code change.)
- `REQ-003`: `MCPServer.run_http()` MUST fail (not silently skip) when `own_config_file` is
  falsy, so Config Isolation can never be silently unrestricted.
- `REQ-004`: Production config loading MUST reject an unknown/mistyped top-level config key,
  with valid keys derived from `agent/config_dataclasses.py` via introspection.
- `REQ-005`: A per-process table of required config file(s), required keys, and keys that may
  legitimately be empty MUST exist as a new section in `docs/adr/ADR-002-config-isolation.md`.
- `REQ-006`: Startup tests MUST exist for missing/empty/malformed/permission-denied/misnamed
  config file scenarios (Agent `load_all()` path and at least one MCP server `load()` path),
  each mapped to the specific ADR-004/ADR-002 Invariant(s) it verifies, and both ADRs'
  Verification sections MUST be updated to cite the new tests for the scenarios they newly
  cover (ADR-004 INV-07 only — INV-08/INV-09 already `Confirmed` via unrelated prior work;
  ADR-002 INV-01/INV-02).

## Design
Path B classification (large task): affects > 3 files (13 target files), and the change is
security-relevant (fail-closed startup behavior) though it does not add a new module,
change a public/runtime interface's shape, or touch a database schema. Full architecture,
dependency, historical, and operational analysis performed per `workflow-path-b.md`:

- **Architecture analysis**: `PYTHONPATH=scripts lint-imports` surfaced one pre-existing,
  unrelated violation (`shared.production_config_validator -> agent.tool_policy`, a
  deferred/function-local import at line 77) — recorded as an Assumption/Unknown (UNK-03),
  not fixed by this Plan. REQ-004's new introspection of `agent/config_dataclasses.py` from
  the same file follows the same already-established deferred-import pattern, so it does not
  introduce a new violation category.
- **Dependency graphing**: `rg "restrict_to\("  scripts/` confirmed the falsy-skip pattern is
  isolated to `scripts/mcp_servers/server.py::MCPServer.run_http()` — every other caller
  (`agent/context.py`, `rag/ingestion/{crawler,ingester,chunk_splitter}.py`) already calls
  `restrict_to()` unconditionally. `grep -rn "load_all("` confirmed exactly 5 callers, all
  bare (no `strict` argument).
- **Historical analysis**: `git log --diff-filter=M` on the 4 core source target files shows
  82 combined modifying commits — high churn, consistent with these being frequently-touched
  shared/core modules; no single-author dominance flag raised (bus factor not separately
  measured — `git-fame` unavailable in this environment).
- **Operational dependency inspection**: not applicable — this Plan changes source-level
  fail-closed logic and adds tests/docs; it does not touch a running process, DB file, or
  MCP server socket that would require a lock check before editing.

The fix makes `load_all()`'s missing-required-file behavior unconditional across all 5
callers (removing the `strict=False` default's silent-continue path for required files,
per ADR-004 INV-01/INV-02's "no environment-based relaxation" mandate), which transitively
closes the `ProductionConfigValidator` branch-ambiguity gap (REQ-002) without a separate code
change to that validator itself. `MCPServer.run_http()`'s fix mirrors the pattern already
used unconditionally by every other `restrict_to()` caller in the codebase. The unknown-key
check (REQ-004) generalizes `ProductionConfigValidator`'s existing bidirectional
`tool_safety_tiers` pattern to the top-level (and relevant nested) config-key set, using
runtime dataclass introspection rather than a hand-maintained allowlist.

  fixture or a CLI tool run outside the normal Agent startup path) → **Mitigation**: run the

  call site (a CLI command) is explicitly re-verified in Phase 1 rather than assumed safe.

  legitimately-optional key that is read via a non-obvious `cfg.get()` path inside a
  `_build_*` helper → **Mitigation**: UNK-02 explicitly defers exact-mapping resolution to
  implementation time with a stop-and-report escape hatch, per the Issue's own instruction.
- **Risk**: Fixing `MCPServer.run_http()`'s falsy-skip could break a legitimate use case
  where `own_config_file` is intentionally empty (e.g. a server with no dedicated config
  file) → **Mitigation**: `scripts/agent/context.py` and the RAG ingestion processes
  (Reference Files) confirm every other Config-Isolation caller always has a concrete
  filename; no legitimate always-empty case was found during this Plan's Path B analysis,
  but Phase 2's implementer should re-confirm no subclass currently ships with an
  intentionally-empty `own_config_file` before applying the fix.
