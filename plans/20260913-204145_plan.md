## Background
The Issue's cited claim
(`docs/03_rag_03_02_query_pipeline-rag-pipeline-class.md`, "Documentation vs.
Implementation Mismatch" note: "`sanitize_document` is a function from `rag/utils.py`
and does not exist in `rag.pipeline`") is confirmed accurate —
`sanitize_document()` is defined in `scripts/rag/utils.py:51-56` and imported by
`scripts/rag/stages/augment.py:9`, not by `pipeline.py`.

**Re-verified 2026-09-13** (this cycle): `sanitize_document()`'s actual
implementation (`utils.py:51-56`) is a simple pass over five compiled regex
patterns (`_INJECTION_PATTERNS`, `utils.py:30-38`) matching common prompt-injection
phrasings (`"ignore ... instructions"`, `"system:"`, `"[SYSTEM OVERRIDE]"`,
`"disregard ... instructions"`, `"new instructions:"`), each replaced with the
literal string `"[REMOVED]"`. It returns a plain `str` (the sanitized text), unlike
its sibling `sanitize_document_full()` (`utils.py:59-68`), which additionally
returns a `SanitizeResult` audit trail (`was_sanitized: bool`,
`patterns_detected: list[str]`). Existing tests
(`tests/rag/test_rag_pipeline.py:25-72`) already exercise each pattern and confirm
clean text passes through unchanged — this Plan's new documentation section draws
directly on this code and its existing test coverage, not on new investigation.

Two unrelated documentation/code defects were also found in this cycle's
investigation, both out of this Plan's scope (see Unknowns): (1) a stale, apparently
copy-pasted comment at `scripts/rag/utils.py:53` ("Contract: returns 0.0 equivalent
— no error on clean text" — `0.0` is meaningless for a function returning `str`);
(2) `docs/03_rag_03_02_query_pipeline-rag-pipeline-class.md` itself has the same
three-way duplicate-section structure (`## 2.`, `## 2a.`, `## 2b.` — all titled
"RagPipeline Class") found in a sibling issue processed this same cycle
(`issues/done/20260913-183002_duplicate_section_headers_chunksplitter.md`), with
section `2a`'s Mismatch note (line 75) containing a self-referential link back to
its own file.

## Problem
`sanitize_document()` is a security-relevant function (it is the RAG pipeline's only
defense against prompt-injection content reaching the LLM via retrieved document
chunks), but its contract — which patterns it matches, what it does not catch, and
its return format — exists only as a one-line docstring in `utils.py`, with no
dedicated documentation section a reader investigating the augment stage's output
formatting would find it from.

## Reason for change
Add a documentation sub-section under the existing `### 5.5 AugmentStage` section
(where `sanitize_document()` is already referenced twice) describing its contract in
detail, so a reader does not need to open `utils.py` to understand what protection
this function does and does not provide.

## Implementation intent
Add a `**sanitize_document() Contract**` sub-block immediately after the existing
`### 5.5 AugmentStage` bullet list (after the `Content-only Invariance Rule` note),
covering: (1) the five injection-pattern categories it matches (paraphrased from
`_INJECTION_PATTERNS`, not the raw regex); (2) that matches are replaced with the
literal string `"[REMOVED]"`, not removed entirely; (3) its return type (`str`) and
its relationship to the audit-trail variant `sanitize_document_full()` (which
`AugmentStage` does not use); (4) known limitations — pattern-based matching only
catches the five specific phrasings it checks for, is case-insensitive but not
semantic, and provides no protection against injection phrasings outside its
pattern list.
