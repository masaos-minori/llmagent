## Background
`TurnCoordinator` was extracted from `Orchestrator`'s `_handle_turn_start`/`_handle_turn_end` handlers during the 2026-08 orchestrator separation (see `implementations/done/20260829-175109_02_turnd_coordinator.md`). It was never wired into the turn flow: no production code constructs it, no test instantiates it, and the behavior it once documented (system-prompt synchronization, ephemeral-message cleanup, user-message append) was reassigned to `ConversationStateManager` in the same refactor batch. It survives only as a module, a package re-export, one stale comment, and two document mentions. A closely related concern was surfaced during the wfstartup01 cycle (`issues/20261007-153934_wfstartup01_...`, plan `plans/done/20261008-143632_plan.md`), which corrected the Orchestrator docstring and the turn-flow overview; this plan is the focused follow-on that removes the class itself.

## Problem
- `TurnCoordinator` is defined in `scripts/agent/turnd_coordinator.py` and re-exported from the package (`scripts/agent/__init__.py`), with zero construction sites, zero call sites, and zero dynamic-use sites across `scripts/` and `tests/`.
- `scripts/agent/workflow_engine_adapter.py:173` carries a no-op placeholder docstring claiming planning is done by `TurnCoordinator.handle_turn_start`, which nothing calls.
- `docs/23_agent/agent_13_reference-api-generated.md:198` lists the class as a component (generated row).
- `docs/10_adr/ADR-014-agent-control-plane-responsibility-boundaries.md:132` names the class among the extracted concern classes.
- Dead code that looks active misleads maintainers and contradicts the repository's policy against leftover compatibility layers.

## Reason for change
Dead code that looks active contradicts the no-compatibility-layer policy and invites maintainers to assume a live turn-coordination path that does not exist. The real owner of the behavior the class documents is `ConversationStateManager`.

No new code is introduced; no shim is added.

Architecture: `TurnCoordinator` was a leaf concern extracted from `Orchestrator` but never composed into the turn flow; the owning behavior now lives in `ConversationStateManager`. Historical analysis: low churn on the target module (3 commits, last 2026-09-14); `ADR-014` is higher-churn (15 commits) as a living ADR, so its edit must be surgical. Operational dependency inspection: not applicable (no MCP server or DB involvement). The change introduces no import and no runtime behavior.
