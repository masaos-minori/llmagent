# MCP-006: Implement Missing Guard Layers for High-Risk Tool Categories

## Goal
- Close the Layered protection coverage gap registered as Known Issue MCP-006: give every
  high-risk MCP tool category an explicit, evidence-backed status for each of the five
  protection layers, implement the concrete gaps that the re-audit found in `file-write`,
  `file-delete`, and `git`, and remove the MCP-006 ledger entry once every layer is either
  implemented or documented as not applicable with a stated reason.

## Priority
Medium

## Scope
- **In-Scope**:
  - `file-write-mcp` and `file-delete-mcp` emitting a shared `mcp_tool_exec` audit record
    from `POST /v1/call_tool`.
  - Emitting the `requested_target` value that `_audit_log` already accepts but discards.
  - Postcondition verification for `write_file`, `edit_file`, `move_file`, `delete_file`,
    `delete_directory`.
  - Command-specific guard completion for `edit_file` (byte limit, atomic write) and
    `delete_directory` (allowed-root protection on the non-recursive path).
  - A real (lightweight) Stage 5b TOCTOU re-check in the Git write-protection pipeline.
  - Recording the five-layer coverage for `file-write`, `file-delete`, `shell`, `git`,
    `github`, `mdq`, and `cicd` in each tool's own document, including a stated reason for
    every layer recorded as not applicable.
  - Documenting the approval-correlation join path in the audit-logging document.
  - Removing the "coverage is uneven" statement from the security policy and the MCP-006
    entry from the Known Issue inventory.
- **Out-of-Scope** (inherited from the issue):
  - Changes to the common guard layer, allowlists, or denylists (including shell
    dangerous-option rejection).
  - Changes to Agent-side approval flow, risk classification, or approval prompts.
  - New MCP servers, new tools, or new tool parameters.
  - Changes to command validation, subprocess launch, health polling, or process termination
    in `scripts/agent/http_lifecycle.py`.
  - Per-server MCP auth-token isolation (separate track; blocked by the same
    `scripts/agent/http_lifecycle.py` constraint).
  - `github-mcp` and `mdq-mcp` and `cicd-mcp` source changes: these categories are
    documentation-only in this Plan.

## Background
`docs/91_security/security_02_high-risk-tool-common-policy.md` defines five protection
layers (Agent approval, common per-server guard, command-specific guard, postcondition
verification, audit). Line 56 of that document states coverage is uneven and points to
Known Issue MCP-006. `docs/00_governance/governance_01_documentation-policy.md`'s Known
Issue Registration Rule requires such a discrepancy to stay tracked until resolved, so the
ledger entry at `docs/00_governance/governance_03_issue-and-uncertainty-management.md:94`
can only be removed once every governed category has a resolved per-layer status.

The issue text is a V22-01 snapshot. Several of its claims are stale against current source
(verified in this analysis):
- `AuditRecord` already has `pre_condition`, `post_condition`, and `canonical_target`
  (`scripts/mcp_servers/audit.py:44-58`); `requested_target` is accepted by
  `_build_audit_record` but never written into the record (`scripts/mcp_servers/audit.py:100-121`).
- Postcondition verification already exists for `git_pull`
  (`scripts/mcp_servers/git/repository_state.py:192-217`) and for `git_checkout`
  (`scripts/mcp_servers/git/format_output.py:155-161`).
- `github-mcp` already ships command-specific guards
  (`scripts/mcp_servers/github/github_service_security.py:57-145`).

## Reason for change
- MCP-006 is an open Medium design-gap in the governance ledger, and the security policy
  document advertises an unresolved coverage gap to every reader of the high-risk tool
  policy.
- The file-write and file-delete categories are the two high-risk categories that emit no
  shared audit record, so their operations cannot be traced through the documented
  end-to-end audit path.
- The file categories report success from the absence of an exception, which is exactly the
  "partial results reported as success" failure the postcondition layer exists to prevent.

## Implementation intent
- Keep every change additive on the audit schema: no field is removed or renamed, and
  `requested_target` is emitted only when non-empty, matching the existing
  `canonical_target` pattern.
- Implement postconditions as narrow, operation-specific state confirmations that fail only
  when the state actually deviated, so legitimate calls keep their current success/failure
  semantics.
- Extend existing guards rather than adding new guard kinds: apply the already-configured
  `max_write_bytes` limit to `edit_file`, and apply the already-implemented allowed-root
  check to every `delete_directory` path.
- Implement the Stage 5b re-check as a single live HEAD-identity read inside the existing
  repository lock, not as a second full `RepositoryState` snapshot.
- For layers that cannot be implemented for a category, record "not applicable" in that
  category's own document together with the reason, so no layer is left unaddressed.

## Requirements
- `REQ-001`: `file-write-mcp` emits one shared `mcp_tool_exec` audit record per
  `POST /v1/call_tool` call, using the request context it already extracts.
- `REQ-002`: `file-delete-mcp` emits one shared `mcp_tool_exec` audit record per
  `POST /v1/call_tool` call, while its dedicated plain-text audit log is kept unchanged.
- `REQ-003`: the shared audit record emits `requested_target` when a caller supplies it, so
  requested and canonical targets can be correlated; the field is added to `AuditRecord` and
  documented.
- `REQ-004`: `write_file`, `edit_file`, and `move_file` verify their resulting state
  (written byte length matches the intended UTF-8 length; destination exists and source is
  gone) and raise instead of reporting success when verification fails.
- `REQ-005`: `edit_file` enforces the configured `max_write_bytes` limit on the resulting
  content and writes atomically through the same temporary-file-plus-`os.replace` path used
  by `write_file`.
- `REQ-006`: `delete_file` and `delete_directory` verify the target no longer exists after
  the operation and raise instead of reporting `deleted=True`.
- `REQ-007`: allowed-root deletion protection applies to every `delete_directory` call, not
  only the recursive one.
- `REQ-008`: the Git write-protection pipeline re-reads HEAD identity inside the repository
  lock immediately before the mutating call and rejects when it drifted since authorization.
- `REQ-009`: each high-risk category document records the status of all five layers for that
  category (`file-write`, `file-delete`, `shell`, `git`, `github`, `mdq`, `cicd`), and every
  layer recorded as not applicable states why.
- `REQ-010`: the audit-logging document records the approval-correlation join path
  (`tool_approval` → `tool_exec` → `mcp_tool_exec`) and states that no MCP server performs an
  approval check itself.
- `REQ-011`: the security policy no longer describes an open coverage gap, and the MCP-006
  entry is removed from the Known Issue inventory.

## Acceptance criteria
- `AC-001` (REQ-001): a `POST /v1/call_tool` request to `file-write-mcp` produces exactly one
  parseable `mcp_tool_exec` record containing `session_id`, `request_id`, `tool`, `target`,
  `outcome`, and `server_key`, for both accepted and rejected calls.
- `AC-002` (REQ-002): the same holds for `file-delete-mcp`, and its dedicated plain-text
  audit log still receives its existing line.
- `AC-003` (REQ-003): when a caller passes `requested_target`, the emitted record contains
  `requested_target`; when it does not, the key is absent. `docs/22_mcp/mcp_02_03_audit-logging-and-errors.md`
  documents the field.
- `AC-004` (REQ-004): `write_file` and `edit_file` fail with a file-validation error when the
  written file's byte length does not match the intended UTF-8 byte length, and `move_file`
  fails when the destination does not exist or the source still exists after the move;
  legitimate calls keep their current success responses.
- `AC-005` (REQ-005): `edit_file` rejects content whose resulting UTF-8 length exceeds the
  configured `max_write_bytes`, and writes through a temporary file plus `os.replace`.
- `AC-006` (REQ-006): `delete_file` and `delete_directory` raise instead of returning
  `deleted=True` when the target still exists after the operation.
- `AC-007` (REQ-007): `delete_directory` rejects an allowed root directory for both
  `recursive=True` and `recursive=False`.
- `AC-008` (REQ-008): the Git pipeline rejects with a Stage 5b denial when HEAD identity
  changes between authorization and execution, and passes unchanged; no legitimate call
  changes outcome.
- `AC-009` (REQ-009): each of `mcp_04_02`, `mcp_04_05`, `mcp_04_01`, `mcp_04_03`,
  `mcp_04_04` contains a five-layer coverage statement for its high-risk categories, and
  every "not applicable" entry states a reason.
- `AC-010` (REQ-010): `docs/22_mcp/mcp_02_03_audit-logging-and-errors.md` states the
  approval-correlation join path and that no MCP server performs an approval check.
- `AC-011` (REQ-011): `docs/91_security/security_02_high-risk-tool-common-policy.md` contains
  no open-gap statement, `grep -rn "MCP-006" docs/` returns no match, and

## Assumptions
- Approval is an Agent-side gate for every MCP server: `scripts/mcp_servers/server.py:136-150`
  reads only `x-session-id`, `x-request-id`, and `x-idempotency-key`, and no approval
  identifier is sent by `scripts/shared/http_transport.py:158-159`. Server-side approval
  checks are therefore recorded as not applicable rather than implemented.
- Approval correlation is achievable by documented join keys, not by a new field:
  `tool_approval` and `tool_exec` share `session_id` and `task_id`, and `tool_exec.mcp_request_id`
  equals the server-side `request_id`.
- Audit-schema changes are additive only; existing consumers rely on key-sorted JSON lines.
- The dedicated plain-text audit logs for `file-delete`, `shell`, and `github` are kept; the
  shared `mcp_tool_exec` record is added alongside them, not in place of them.
- `file-write` and `file-delete` servers already call `extract_request_context`, so no new
  request plumbing is required.

- **Per-layer decision table** (the contract the documentation rows must record):

| file-write | Agent-side; not applicable server-side | Implemented (`allowed_dirs`, `resolve_safe`) | Implemented after REQ-005 (`max_write_bytes` on `write_file` and `edit_file`) | Implemented after REQ-004 (byte length, move endpoints) | Implemented after REQ-001 |
| file-delete | Agent-side; not applicable server-side | Implemented (`allowed_dirs`, `resolve_safe`) | Implemented after REQ-007 (allowed-root protection on every path) | Implemented after REQ-006 (target gone) | Implemented after REQ-002, dedicated plain-text log retained |

| git | Agent-side; not applicable server-side | Implemented (`allowed_repo_paths`) | Implemented (ref allow-list, remote pattern, protected-branch policy, dirty/detached preconditions) | Implemented: `git_pull` conflict check, `git_checkout` refreshed-state comparison in `format_output.py`, Stage 5b re-check after REQ-008 | Implemented (`pre_condition`, `post_condition`, `canonical_target`; `requested_target` after REQ-003) |

| mdq | Agent-side; not applicable server-side | Implemented (reference implementation: `allowed_dirs`, traversal and symlink containment) | Implemented (`authorize_path`, stale-document check) | Per UNK-01 | Implemented (shared record, `extract_audit_target`) |
| cicd | Agent-side; not applicable server-side | Implemented (`allowed_repos`) | Implemented (repository and workflow allowlists, invalid-workflow patterns) | Not applicable: pipeline triggering is asynchronous; the server returns the created run identity and run state is read through separate read tools | Implemented (shared record only) |

- **Audit schema**: `requested_target` follows the existing `canonical_target` pattern —
  `NotRequired[str]`, emitted only when non-empty, so no consumer sees a new key for servers
  that do not supply it. Callers are responsible for redaction; `git_server.py` already passes
  `_sanitize_for_audit(...)` output.
- **Postcondition shape**: each check is a narrow confirmation of the operation's own
  observable end state (byte length, endpoint existence, target absence) that raises the
  category's existing error type (`FileValidationError`), so the HTTP status mapping
  (422) and the Agent-side handling stay unchanged.
- **Guard widening shape**: reuse the existing check implementations instead of adding new
  configuration keys or new guard kinds, keeping the common guard layer untouched.
- **Stage 5b shape**: one live identity read (`HEAD` detached/attached) inside the existing
  `_get_repo_lock(self._state.path)` block, skipped when the snapshot has no live repository
  object, so mocked tests and read-only paths are unaffected. No second `RepositoryState`
  snapshot is introduced.
- **Documentation shape**: each tool document gains one layer-coverage section in the shape
  already used by `docs/22_mcp/mcp_04_05_git.md` (Common guard / Command-specific guard
  status / Postcondition verification / Audit), so the policy document can point at tool
  documents instead of describing a gap.

## Risks
- **Risk**: New postconditions turn previously successful calls into failures. → **Mitigation**:
  each check fires only on an actual state deviation; happy-path tests are kept and extended,
  and AC-004/AC-006 explicitly require unchanged legitimate-call semantics.
- **Risk**: Widening allowed-root protection rejects a call some existing test relies on. →
  **Mitigation**: enumerate such cases first (UNK-03) and treat them as characterization tests
  that must be updated to the new rejection rather than relaxing the guard.
- **Risk**: The Stage 5b live read breaks tests that use `MagicMock` snapshots. →
  **Mitigation**: guard the re-read on a live repository object and add the mocked-snapshot
  case required by T-005 (UNK-04).
- **Risk**: `requested_target` could leak an unresolved caller path into the audit log. →
  **Mitigation**: only callers that already redact (`_sanitize_for_audit`) pass it; the field
  is emitted only when non-empty; the field's semantics are documented in the audit document.
- **Risk**: Recording a layer as "not applicable" could be read as accepting an unguarded
  behavior. → **Mitigation**: every not-applicable entry must state its reason in the tool
  document, and the residual risks (shell option rejection, github ref-movement verification)
  are recorded here as follow-up candidates.
- **Risk**: Removing MCP-006 while a category status is still unresolved would violate the
  Known Issue Registration Rule. → **Mitigation**: the ledger row is the last step of Phase 5
  and is gated by AC-009 and AC-011 plus `check_known_deviation_sync.py`.
