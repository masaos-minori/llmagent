## Background
`prompts/04_refactor.md` currently defines exactly two paths at its
`##### Path classification` subsection (Step 2): `[Path A] Minor change` (single file,
no import boundary change, no behavior change, not in `deploy.sh`) and
`[Path B] Higher-impact change` (>1 file, OR an import-boundary/module-layer change, OR
referenced in `deploy.sh`, OR shared/extracted logic used by more than one caller).
Neither path is designed for structural, multi-file architectural work — module
relocation, module merge/split, responsibility transfer, or a deliberate
dependency-direction change — where the "one file at a time" processing model (Step 1:
"Refactor strictly one file at a time, in the order given") can itself make the
migration impossible to validate safely, because no single member file of such a
change can pass Step 7 validation in isolation while its siblings are still unchanged.

## Problem
Today, any refactoring idea that involves relocating a module, merging or splitting
modules, transferring responsibility/ownership between components, or deliberately
changing a dependency direction has no home in `prompts/04_refactor.md`'s Path
classification. Such a change is forced into Path B (if it happens to touch more than
one file or an import boundary) even though Path B's pre-implementation expectations
(none beyond the Step 2 declaration) and Step 1's one-file-at-a-time processing model
were never designed for a change where the intermediate state of a partially-migrated
codebase can be invalid. There is also no requirement, today, that such a
structural change be explicitly approved, scoped, given a migration/rollback strategy,
or backed by an ADR before any transformation begins.

## Reason for change
Without a dedicated Path C, an AI running `prompts/04_refactor.md` on an architectural
idea either (a) misclassifies it as Path B and applies Path B's lighter
pre-implementation bar to a change that needs much more scaffolding (approval, scope,
boundaries, migration strategy, rollback strategy, documentation impact, ADR), or
(b) attempts to satisfy Step 1's one-file-at-a-time rule literally, which can produce
an invalid intermediate codebase state for changes that are only valid when applied as
a set. Path C, plus the atomic migration group concept, closes both gaps while keeping
architectural migrations themselves fully out of scope for this document-only Plan.

  (`prompts/04_refactor.md`), no public/runtime interface change in the code sense, no
  database schema change. Per `skills/issue-to-plan/SKILL.md` Routing, Path A is
  determined by these three criteria alone, not by subjective content size — the
  substantial content of the new Path C subsection does not change the classification.
  This is the same classification and reasoning issue 01's Plan used for the same
  target file.
- **Duplicate-check performed** (see Traceability / Report): searched `plans/*.md`,
  `plans/done/*.md`, `skills/python-refactoring/`, and `skills/python-design/` for an
  existing Path-C-equivalent architectural-refactoring classification.
  `rg -l "04_refactor" plans/*.md plans/done/*.md` returns only
  `plans/20260826-151739_plan.md` (issue 01's Plan) — no other plan, pending or done,
  references `prompts/04_refactor.md` at all. `rg -il "path c"` and `rg -il
  "architectural"` across `plans/` and `plans/done/` return many hits, but every hit
  outside `plans/20260826-151739_plan.md` is either unrelated prose ("architectural
  change" describing an unrelated config-alignment or diagnostics-config decision in
  `plans/20260826-115018_plan.md` / `plans/20260826-120102_plan.md`) or coincidental
  substring matches in unrelated plans (RAG, MCP, eventbus, config-reload topics) —
  none define a Path C or equivalent classification, and none touch
  `prompts/04_refactor.md`. `plans/20260826-151739_plan.md` itself explicitly lists
  "Path C (architectural refactoring classification — reserved for a later issue in
  this sequence, `issues/20260826_02_issue.md`)" under its own Out-of-Scope — i.e. it
  confirms Path C is reserved for, not already covered by, this issue.
  `skills/python-refactoring/*.md` contains no match for "path c" or "architectural" at
  all — its 6-phase toolchain (Dependency Mapping / Behavior Lock / Semantic
  Transformation / Semantic Validation / Incremental Migration / CI Gate) does not
  define any path classification. `skills/python-design/SKILL.md` is a general Python
  design skill; its "Composes with" / "Called by" sections list `issue-to-plan` and
  `python-documentation` / `plan-to-implementation-procedure` only — it does not
  compose with `python-refactoring` or `prompts/04_refactor.md`, and it does not state
  anything like "large refactors should first go through python-design" that would
  make a Path C classification redundant. It offers general architecture-design
  process, not a routing rule inside the refactor workflow itself. This confirms no
  duplicate or superseding coverage exists; this Plan proceeds as new work.
- **Insertion-order design to avoid colliding with issue 01's Plan**: issue 01's Plan
  reserves the exact same insertion point (immediately before `#### Step 3:
  Preparation`) for its future "Discovery Vocabulary" section. Since issue 01's Plan is
  only `Awaiting approval` (not yet implemented) as of this Plan's creation, this Plan
  fixes the relative order explicitly — `##### Path classification` (extended) ->
  `##### Path C: Architectural Refactoring` (this Plan) -> `Discovery Vocabulary`
  (issue 01's Plan) -> `#### Step 3: Preparation` — so whichever Plan is implemented
  first leaves an unambiguous append point for the other, and neither
  implementation-procedure document needs to guess the other's eventual placement.
- **Path B/Path C boundary reasoning**: Path B's existing "Changes an import boundary
  or module layer" criterion already overlaps textually with Path C's
  "dependency-direction change" / "architectural boundary change" criteria. Without an
  explicit precedence rule, an AI could classify a genuine module relocation as Path B
  merely because Path B's criteria are checked first in the document's reading order.
  `REQ-002` resolves this with a single precedence sentence: any Path C criterion match
  wins over a Path B match, and a "narrower" import fix (not part of a structural
  relocation/merge/split/ownership-transfer/boundary change) stays Path B. This mirrors
  how Path A's own criteria already fully exclude it from either B or C (Path A
  requires "no import boundary changes" at all).
- **Atomic migration group reconciliation — the core design decision of this Plan**:
  Step 1's rule ("Refactor strictly one file at a time, in the order given") and the
  Tasks preamble's "one complete Steps 1-10 cycle per file" rule are written for
  behavior-preserving, independently-validatable changes — the normal Path A/B case,
  where each target file can pass Step 7 validation on its own before the next file is
  touched. A genuine architectural migration (e.g., relocating a module used by five
  callers) breaks that assumption: no single file in the set can independently pass
  Step 7 validation while its siblings still reference the old location/shape. Treating
  the one-file-at-a-time rule as an absolute barrier would make such migrations
  impossible to execute safely under this workflow at all; discarding the rule for
  Path C entirely would remove the safety property (rollback-safety, incremental
  reviewability) it exists to protect. `REQ-005`-`REQ-007` resolve this by scoping the
  rule rather than repealing it: an approved, explicitly enumerated **atomic migration
  group** becomes the unit the one-file-at-a-time rule applies to — one Path
  classification, one Steps 3-7 pass, one Completion gate for the whole group — while
  the group's members are still read, transformed, and reported one at a time in a
  fixed order (never in parallel; Step 6 Transformation and the Global Safety
  Restriction against parallel target-file processing are unaffected). This preserves
  the letter of the existing rule at the level it actually protects (no concurrent,
  unordered edits) while making the level it does not protect (independent
  per-file validation) the one axis Path C is explicitly allowed to relax, and only
  for a group that was declared and approved in advance. Silent expansion (`REQ-007`)
  is prohibited for the same reason ordinary scope creep is prohibited elsewhere in
  this workflow: the approval in `REQ-003`/`REQ-004` is for a specific, bounded
  scope, and an unapproved addition mid-execution would bypass that gate exactly the
  way an unapproved behavior change would.
- **Step 3/4 depth-gating gap**: Step 3's and Step 4's existing text branches only on
  "Path A" vs "Path B" ("**Path A**: skip ... **Path B**: run ..."). With a third path
  now defined at Step 2, that text would not say what to do for a change classified
  Path C, leaving a literal gap. `REQ-008` closes it with the minimal possible edit — a
  trailing clause on each existing sentence pointing Path C at "at least Path B depth"
  — without touching Step 7's Required/Conditional validation list (which already runs
  unconditionally on Path) or restating Path A's/Path B's own criteria. This is
  necessary for `templates/plan.md`'s "detailed enough for
  `prompts/02_plan-to-implementation-procedure.md` to produce file-level implementation
  procedures" requirement — without it, the next pipeline phase would have to invent
  Path C's Step 3/4 depth itself.
- **ADR requirement kept intentionally shallow**: per the epic's stated split (issue 05
  owns "ADR support"), `REQ-003` requires only that an ADR exist/be referenced before
  Path C implementation — it does not define what an ADR file looks like, where it
  lives, or how it is created. This is recorded explicitly (not left implicit) so a
  future reader does not mistake the absence of ADR-template detail for an oversight.
