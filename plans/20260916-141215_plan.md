## Goal
- Close the confirmed subprocess-cancellation-safety gap in the shell MCP
  server (an in-flight subprocess is never killed if its awaiting coroutine is
  cancelled from outside its own internal timeout), complete the full
  MCP-server-vs-Workflow-stage timeout audit the Issue's Required Changes
  asked for, and document the resulting hierarchy and its still-open
  numeric-resolution decision — without unilaterally picking a resolution
  direction, per the Issue's own explicit instruction.

## Priority
High

## Scope
- **In-Scope**:
  - Fixing `scripts/mcp_servers/shell/subprocess_runner.py`'s `run_subprocess()`
    so external cancellation (not just its own internal `TimeoutError`) still
    terminates the subprocess process group.
  - Completing the cross-server timeout audit (shell, web_search, mdq,
    rag_pipeline, file/git/github/cicd) against all `config/workflows/default.json`
    stage `timeout_sec` values.
  - Adding unit tests confirming the cancellation-safety fix, at both the
    `subprocess_runner.py` level and the `WorkflowEngine` stage-timeout level.
  - Documenting the audited hierarchy, the confirmed inversion (shell) and
    boundary violation (rag_pipeline), and the still-open numeric-resolution
    question in `docs/05_agent_10_04_operations-and-observability-validation-and-troubleshooting.md`
    and as a new ADR-014 Known Deviation entry.
- **Out-of-Scope**:
  - Deciding whether to lower `shell_mcp_server.toml`'s `max_timeout_sec` or
    raise/restructure the Workflow execute stage's `timeout_sec` — no
    historical shell-command-duration usage data was found (see Problem), and
    the Issue's own AI Implementation Instruction forbids picking a direction
    without it; this Plan documents the tradeoff instead (REQ-003; UNK-01).
  - Adding a per-operation timeout ceiling to the file/git/github/cicd MCP
    servers, which currently have none configured at all — a distinct,
    unbounded-operation gap, not an inversion, and not asked for by this Issue.
  - Establishing an Agent/turn-level time budget distinct from
    `sse_heartbeat_timeout` — a separate design question per the Issue's own
    Out of Scope.
  - A full live, cross-process integration test (real shell MCP server
    process + real `WorkflowEngine`, over actual HTTP) verifying that a
    `WorkflowTimeoutError` on the agent side actually propagates a
    cancellation to the shell server process — see Risks; this Plan verifies
    cancellation-safety at the unit level on each side instead.

## Background
This Issue follows a design review (memo2.md) covering "Workflow、Agent、MCPの
タイムアウト階層" (a Workflow/Agent/MCP timeout hierarchy). The investigation
found a concrete inversion: shell's `max_timeout_sec=300` exceeds the Workflow
execute stage's `timeout_sec=120`, with no evidence the in-flight subprocess
is cancelled when the enclosing stage times out first.

## Problem
Adversarial verification confirmed every Issue claim against current source,
and additionally confirmed the exact mechanism of the orphaned-process gap
(not just its plausibility) and completed the cross-server audit the Issue's
Required Changes asked for but did not itself complete:

- **Workflow layer** (confirmed): `workflow_engine.py` line 304
  (`timeout = stage_def.timeout_sec if stage_def else 60`), line 321
  (`asyncio.wait_for(fn(), timeout=timeout)`), line 330
  (`raise WorkflowTimeoutError`). `config/workflows/default.json`: plan=30s,
  execute=120s, verify=10s — confirmed exact values. Only the **execute**
  stage invokes LLM/tool-call activity (`workflow_engine_adapter.py`'s
  `plan_fn` is a no-op placeholder; `verify_fn` only runs turn-end
  processing) — so **execute's 120s is the only stage timeout relevant to
  this audit**, not plan/verify's 30s/10s.
- **Agent layer** (confirmed): no turn-wide or Tool-Call-wide time budget in
  `llm_turn_runner.py` (0 grep hits for `timeout`/`time_budget`/`deadline`).
  `llm_sse_stream.py` line 35 (`asyncio.wait_for(coro, timeout=heartbeat_timeout)`)
  enforces `sse_heartbeat_timeout` (`config/agent.toml` = 60.0s) — an
  inter-chunk silence detector, not an upper bound on total duration, as the
  Issue states.
- **MCP Server layer — full audit completed** (the Issue's own Required
  Changes asked for this but left it undone; resolved here):

  | Server | Effective max operation duration | vs. execute's 120s |
  |---|---|---|
  | shell (`config/shell_mcp_server.toml` line 7, `max_timeout_sec`) | 300s | **Inverted** (180s over) |
  | web_search (`config/web_search_mcp_server.toml`, `search_timeout_sec`/`browser_timeout_sec`) | 10s / 15s | OK (105s/90s margin) |
  | mdq (`config/mdq_mcp_server.toml`, `search_timeout_sec`) | 30s | OK (90s margin) |
  | rag_pipeline (`scripts/mcp_servers/rag_pipeline/rag_pipeline_service.py` line 105, `http_timeout = 120.0` hardcoded) | 120.0s | **Boundary violation** — equal to, not strictly less than, execute's 120s (no margin) |
  | file (read/write/delete), git, github, cicd | no per-operation timeout ceiling configured (confirmed: no `timeout` key in any of their `config/*.toml`) | not an inversion — a distinct, unbounded-operation gap, out of scope (see Scope) |

- **Orphaned-process gap — confirmed by code reading, not just suspected**:
  `subprocess_runner.py`'s `run_subprocess()` (line 54) wraps only
  `proc.communicate()` in `try: ... except TimeoutError:` (its own internal
  timeout). It has **no `except asyncio.CancelledError` and no `finally`
  clause**. If the awaiting coroutine is cancelled for any reason other than
  its own internal timeout firing (most relevantly, the outer HTTP
  request/ASGI handler being cancelled because the agent's own
  `asyncio.wait_for` in `_run_stage_with_retry()` timed out and its
  connection to the shell MCP server was subsequently torn down), the
  cancellation propagates straight through with no call to
  `_kill_timed_out_process()` — the subprocess (created with
  `start_new_session=True`, its own process group) is left running,
  orphaned. This confirms the Issue's suspicion as an actual code defect,
  independent of which direction the numeric inversion is eventually
  resolved in.
- No historical shell-command-duration usage data is available to inform the
  numeric-resolution decision: `/opt/llm/logs/audit.log` (568 lines) contains
  no `tool_exec`-shaped structured events at all (it is a generic
  service/startup log, not the `ctx.services_required.audit_logger` stream
  `ToolExecEvent`s are written to) — `grep -c "shell_run"` returns 0.

## Reason for change
A layer that has already reported failure (Workflow stage timeout) while an
inner subprocess is still running creates both an observability gap (audit
trail says "failed" while a side-effecting process keeps executing) and a
confirmed resource leak (the orphaned process is never explicitly killed).
This is worth fixing independently of the numeric-inversion question, since
the same cancellation-safety gap would leak a subprocess on any external
cancellation (not only a Workflow timeout) — e.g. a server shutdown or a
client disconnect for an unrelated reason.

## Implementation intent
Fix `run_subprocess()`'s cancellation-safety directly (a small, mechanical,
independently-revertable change). Complete and document the cross-server
audit and the still-open numeric-resolution tradeoff, so a future maintainer
has the full picture and an explicit decision point rather than a silent
unilateral choice. Add tests at the two tractable unit levels the Issue's own
Testing Expectations call for, and record the full live cross-process
integration test (the Issue's literal ask) as a recommended follow-up rather
than assuming existing test infrastructure supports it without further
investigation (see Risks).

## Risks
- **Risk**: Fixing `run_subprocess()`'s cancellation-safety (REQ-001) does
  not by itself prove that a `WorkflowTimeoutError` on the agent side
  actually propagates a cancellation across the HTTP boundary into the
  shell MCP server's own request-handling coroutine — that cross-process
  propagation chain (agent's `asyncio.wait_for` → httpx client cancellation →
  TCP/ASGI-level disconnect detection → server-side coroutine cancellation)
  was not verified end-to-end in this Plan → **Mitigation**: REQ-001 makes
  the fix correct and safe regardless of whether that propagation currently
  occurs (any cancellation, from any cause, is now handled); a full live
  cross-process integration test (out of this Plan's scope, see Scope) is
  the recommended follow-up to confirm the propagation itself.
- **Risk**: Documenting the shell-vs-execute inversion as an open,
  undecided tradeoff (REQ-003, UNK-01) rather than fixing it leaves the
  Issue's core Acceptance Criterion ("no MCP server's maximum allowed
  operation duration exceeds the Workflow stage timeout_sec that encloses
  it") unmet by this Plan alone → **Mitigation**: this is a deliberate,
  explicit deferral matching the Issue's own AI Implementation Instruction,
  which forbids picking a direction without usage data that was confirmed
  unavailable; the documented tradeoff is this Plan's correct, complete
  contribution to that specific Acceptance Criterion.
