## Design
This plan does not modify `_check_tool_definitions_finding()`, the module docstring, the
doc bullet, or any test — those changes remain fully specified in
`plans/20260819-184236_plan.md` (Option B) and `requires/done/20260818-224947_require.md`
(Option A fallback), and are executed only after the sign-off recorded here resolves which
option applies. The design decision this plan makes is procedural, not technical: where the
sign-off record lives.

Per `rules/coding.md`'s "Explicit sign-off gates" section, the preferred channel is "a
comment on the corresponding `plans/` entry." Since no in-repo mechanism was found for
attaching a comment to a plan file (see Unknowns UNK-01), the practical implementation is:
append a `## Sign-off` section directly to the bottom of `plans/20260819-184236_plan.md`
recording the question asked, the answer received (or its absence), and the resulting
option to implement — functionally equivalent to a "comment on the plan entry" for a
plain-Markdown, git-tracked document, and more discoverable than a separate `issues/` note
since it lives on the gated plan itself. This is the primary recommended channel; the
`issues/` note is the documented fallback if a future workflow constraint prohibits editing
an already-produced plan file directly.

## Risks
- **Risk**: The sign-off note could be added to `plans/20260819-184236_plan.md` but never
  actually routed to a real operations/product-owner conversation — i.e., the paperwork
  gate is satisfied without the substance (an actual answer) behind it. Likelihood: medium
  (this plan cannot force an external human conversation to happen). Impact: same as the
  original risk this gate was meant to close — Option B could ship without genuine
  confirmation.
  **Mitigation**: The Sign-off section template mandates recording either a real answer or
  an explicit maintainer statement accepting the in-repo-evidence inference as sufficient
  (per the source requirement's Implementation instructions item 4) — a blank or
  perfunctory sign-off section that skips this statement should be treated as incomplete
  by whoever reviews it before starting `plans/20260819-184236_plan.md`'s Phase 1.
- **Risk**: This plan and `plans/20260819-184236_plan.md` could drift out of sync if the
  latter is edited again (e.g. re-planned) before the sign-off is recorded, since this plan
  references specific line numbers and phase names in the other plan as of this writing.
  Likelihood: low (no other open requirement currently targets that plan for further
  edits, per the duplicate-check search performed before creating this plan). Impact: low
  (a future reader would notice the referenced phase names no longer match and would
  re-verify).
  **Mitigation**: None needed beyond normal review discipline; not escalated to an issue
  since likelihood and impact are both low and no corrective action is actionable ahead of
  time.
