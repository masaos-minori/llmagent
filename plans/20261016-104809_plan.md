## Goal
- Confining HTTP-subprocess command validation to a trusted binary directory removes the PATH-injection surface of a basename-only allowlist. Add a strict mode that requires the resolved real path of an allowlisted-named binary to live inside a trusted directory, while preserving the current permissive behavior behind an explicit opt-in flag.

## Priority
Medium

## Scope
- **In-Scope**:
  - Add a strict validation mode to `CommandValidator` that requires the realpath of an allowlisted-named binary to be inside a trusted binary directory, in addition to the basename allowlist match.
  - Gate strict mode behind an explicit opt-in flag sourced from an environment variable read in `CommandValidator.__init__`. Default is permissive (current behavior preserved).
  - Preserve the existing `LLMAGENT_BINARY_DIR` override as the trusted-directory source in strict mode; fall back to `/opt/llm/bin` when unset.

  - Changes to which commands are on the allowlist.

## Background
`scripts/agent/http_lifecycle_command_validator.py::CommandValidator.validate` performs: (1) `shutil.which(cmd_name)` PATH lookup, (2) `os.path.realpath` symlink resolution, (3) regular-file check, and (4) allow if `base_name in self._allowed_commands` OR the resolved path is inside `/opt/llm/bin`. The directory branch is behind an `or`, so it can only ADD an allowed path; it cannot reject a basename-allowlisted binary located elsewhere. The launcher (`scripts/agent/http_lifecycle.py::_create_and_validate_proc`) then runs whatever `validate` approves.

## Problem
A basename-only allowlist silently degrades to "run whatever is first on `PATH` with an allowed name." Because `filter_env` inherits the parent agent's `PATH` (only blocking `PATH`/`PYTHONPATH`/`LD_LIBRARY_PATH`/`HOME`/`USER` overrides), any directory writable by an attacker that appears in `PATH` becomes an injection point for a malicious `node`/`python3`/`npx`. Confining to a trusted directory hardens the control without changing the allowlist contents.

## Reason for change
The basename allowlist is a soft control. Making directory confinement mandatory (or opt-in) closes the PATH-injection surface. Production inspection (below) determines whether the stricter mode can be the default or must remain opt-in.

## Implementation intent
Add a strict mode to `CommandValidator` that, after realpath resolution, requires the real path to be inside a trusted directory in addition to matching the allowlist basename. Gate strict mode behind an opt-in environment variable read in `__init__`, defaulting to permissive so current deployments are unaffected. Reuse the existing `LLMAGENT_BINARY_DIR` override as the trusted-directory source. Do not touch the launch path, env filtering, or health polling.

Two wiring designs are possible (see Unknowns UNK-01):
- **Design A (recommended): environment-variable driven.** Read an opt-in flag from an environment variable inside `CommandValidator.__init__`. Touches only the validator + tests. Honors the issue's "do not touch launch/env/health" constraint. Process-global scope.
- **Design B (follow-up): config-field driven.** Add a `strict_command_confinement` field to `McpServerConfig`, populate it in `_build_single_server`, and pass it to `CommandValidator` at the construction site in `http_lifecycle.py`. Per-server scope, but requires modifying the launch-path construction site (`http_lifecycle.py:82`), which conflicts with the "do not touch launch" constraint. Requires explicit approval to relax that constraint.

## Design
- **Strict/permissive gating (Design A).** `CommandValidator.__init__` reads the opt-in flag from an environment variable (e.g., `LLMAGENT_STRICT_COMMAND`). A private attribute (e.g., `self._strict_confinement`) stores the resolved boolean. Default `False`.
- **Strict-mode path.** In `validate`, when `self._strict_confinement` is true, after `os.path.realpath` resolution the resolved real path MUST be inside the trusted directory (`_allowed_binary_dir()` → `LLMAGENT_BINARY_DIR` if set, else `/opt/llm/bin`). If not, raise a descriptive `StartupFailure` (e.g., reason: command resolved outside the trusted binary directory). The basename allowlist match remains necessary but no longer sufficient.
- **Permissive path.** When strict is disabled, behavior is unchanged: allow if basename matches OR realpath is inside the trusted directory (current `or` semantics).
- **Symlink handling.** The check uses the already-resolved realpath, so a symlink inside the trusted directory pointing outside it is rejected in strict mode (`REQ-003`, `AC-003`).
- **Backward compatibility.** Default permissive means no breaking change and no config migration for current deployments. Strict-default would require a prerequisite deployment step (populate `/opt/llm/bin` or set `LLMAGENT_BINARY_DIR` globally); see Risk.
- **Import-linter.** Adding logic to `command_validator.py` does not introduce new imports; the 6 existing contracts stay KEPT. No new module/package.

## Risks
- **Risk**: Adopting strict as the DEFAULT would reject every current subprocess server, because production allowlisted binaries live in `/usr/bin` (verified: `node`, `python3`, `uvx`, `npx`, `npm`, `uv` all resolve under `/usr/bin`; `/opt/llm/bin` is empty; `LLMAGENT_BINARY_DIR` is never set). → **Mitigation**: Default to permissive (opt-in). Strict-default is deferred until a deployment populates a trusted directory (`/opt/llm/bin` symlinks or global `LLMAGENT_BINARY_DIR`); treat that as a separate, gated change.
- **Risk**: Env-var flag (Design A) is process-global, not per-server, so one setting applies to all servers in a process. → **Mitigation**: Acceptable for a global hardening posture; per-server control is Design B (follow-up, requires relaxing "do not touch launch").
- **Risk**: A typo in the opt-in flag name or truthy semantics could leave strict permanently off (fail-open). → **Mitigation**: Explicit, documented truthy set (`1`/`true`/`on`); default falsy; test `AC-004` asserts the default is permissive.
