# Plan: Remove legacy backward-compatibility arguments and unreachable diagnostic path from ToolRouteResolver

## Goal
Remove the unread `server_configs`, `discovery_map`, and `known_tools` parameters
(and the `_log_routing_coverage()` diagnostic method they exist to support) from
`ToolRouteResolver.__init__`, and update the sole production caller
(`ToolExecutor.__init__`) and all test call sites to the new, smaller constructor
signature — with no change to runtime routing behavior.

## Design
- `ToolRouteResolver.__init__` new signature:
  `def __init__(self, *, warn_on_missing: bool = False, strict_mode: bool = False, runtime_registry: RuntimeToolRegistry | None = None) -> None:`
  — all keyword-only, matching what `resolve()` actually consults. Dropping the
  leading positional `server_configs` also drops the need for callers to pass
  an (unused) dict; existing test call sites currently passing a `configs`
  dict positionally must switch to omitting it entirely or (if the test suite
  prefers explicit intent) simply drop the argument.
- `ToolExecutor.__init__` keeps `server_configs` as a required parameter (used
  by `_check_startup_mode()`) but drops `discovery_map`. Its
  `ToolRouteResolver(...)` construction call becomes
  `ToolRouteResolver(warn_on_missing=..., strict_mode=...)` (whatever defaults
  `ToolExecutor` currently uses — verify no `warn_on_missing`/`strict_mode`
  kwargs are threaded through `ToolExecutor.__init__` today; if not, call with
  no arguments, matching current implicit defaults).
- Docstring updates in `route_resolver.py` must drop all references to
  `server_configs`, `discovery_map`, `known_tools`, and
  `_log_routing_coverage()` (module docstring already correctly states
  `RuntimeToolRegistry` is the sole authority; only the `__init__` docstring's
  per-arg documentation needs pruning).
- Test rewrites preserve intent: `TestDiscoveryMap...`/`TestLogRoutingCoverage`
  classes test only the removed compatibility surface (per requirement's
  Implementation instructions §3) and should be deleted outright rather than
  rewritten, since there is no remaining behavior to assert once
  `discovery_map`/`known_tools` are gone. `TestRoutingSourceIsolation`,
  `TestDuplicateToolRegistration`, and all `RuntimeToolRegistry`-based
  resolution/strict_mode/warn_on_missing tests are unaffected in intent and
  only need their `ToolRouteResolver(...)` call sites updated to drop the
  removed kwargs/positional arg.

## Risks
- **Risk**: Deleting `TestDiscoveryMap...`/`TestLogRoutingCoverage` test
  classes wholesale could silently drop coverage for a still-relevant behavior
  (e.g., "RuntimeToolRegistry wins even when discovery_map would map
  elsewhere") if that assertion is not re-homed elsewhere.
  → **Mitigation**: Before deleting `TestDiscoveryMap...`, confirm each test's
  assertion is specifically about `discovery_map`/`known_tools` precedence
  (all six tests inspected in Step C assert only on the now-removed args), and
  that "RuntimeToolRegistry is the sole authority" is already covered by
  `TestRoutingSourceIsolation.test_constants_not_used_directly_by_resolver`
  and other resolver tests that remain. Likelihood: low (already verified by
  direct read); residual risk tracked, not blocking.
- **Risk**: A caller outside `scripts/`/`tests/` (e.g. a notebook, script under
  `tools/`, or a doc example) references the removed constructor signature and
  breaks at runtime without test coverage.
  → **Mitigation**: Step 3's full-repo re-grep is not limited to `scripts/`/
  `tests/` — extend it to the whole repository (`grep -rn "ToolRouteResolver("`
  with no path restriction) before considering the change complete, per the
  requirement's Implementation instruction §4. Likelihood: low (component is
  internal to `scripts/shared/`).
- **Risk**: `ToolExecutor.__init__`'s call to `ToolRouteResolver(...)` may need
  to pass `warn_on_missing`/`strict_mode` values that are currently implicit;
  if `ToolExecutor` itself doesn't expose these as constructor params today,
  no behavior changes, but this must be double-checked during implementation
  since the plan only verified the `discovery_map`/`server_configs` passing,
  not every keyword.
  → **Mitigation**: Implementation step 1 must re-read the exact current
  `ToolRouteResolver(server_configs, discovery_map=discovery_map or {})` call
  (confirmed: no `warn_on_missing`/`strict_mode` currently passed) and preserve
  identical defaults post-edit. Likelihood: low; already spot-checked in
  Step C, but flagged for implementation-time re-verification since defaults
  are load-bearing for `resolve()`'s error behavior.
