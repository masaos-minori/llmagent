# Plan: Provide reproducible startup for LLM services

## Goal

Document and validate, at deploy time, the restart/recovery of the embed-llm and agent-llm services (which run as remote services per config) so recovery and rebuild are reproducible, and correct the misleading local-subprocess comment in `setup_services.sh`.

## Priority

Medium

## Scope

- **In-Scope**:
  - `deploy/setup_services.sh`: replace the placeholder LLM `echo` stubs (lines 74-83) with remote health validation against the URLs defined in config
  - `deploy/setup_services.sh`: fix the misleading header comment (line 7) that states LLM services are started as agent-managed local subprocesses
  - `docs/90_deployment/deployment_01_deployment.md`: update the deployment procedure with remote LLM service prerequisites and validation steps
- **Out-of-Scope**:
  - Downloading / training the LLM models (external services)
  - Creating repo-local systemd definitions for the remote LLM services (see Unknown)
  - Health check endpoint changes on the LLM services themselves
  - LLM configuration file creation

## Background

Source: local investigation notes (memo1.md, ISSUE-12), from DEPLOY-001.

## Problem

- `deploy/setup_services.sh` has placeholder `echo` loops for the LLM services (lines 74-83) that output text only — no real startup, reachability check, or validation exists.
- The comment in `setup_services.sh` (line 7) states the LLM services are started as agent-managed local subprocesses, but `config/*.toml` defines them as remote services (`embed_url = http://192.168.11.238:8081`, `llm_url = http://192.168.11.197:8080`). There is no `embed_llm` / `agent_llm` module in `scripts/` to start locally.
- The health-check echoes in `setup_services.sh` (lines 95-96) hit `127.0.0.1:8080/8081`, which the remote services do not serve, so they can never report true readiness.
- Operators cannot learn from the documentation how to recover/rebuild given the remote LLM prerequisites (e.g. the embedding model dimension must match the RAG schema), so recovery and rebuild are not reproducible.

## Reason for change

- Operators cannot learn from the documentation how to start/recover the LLM services, so recovery and rebuild are not reproducible.

## Implementation intent

- Record in the repository how the remote LLM services are reached and validated at deploy time, and correct the misleading local-subprocess comment, so recovery and rebuild are reproducible. The repo validates/reaches the services; it does not spawn them.

## Design

### Decision matrix

| Condition | Outcome |
|---|---|
| Remote LLM `/health` responds OK | Proceed to next step |
| Remote LLM `/health` fails after retries | Abort with a clear error pointing at the configured URL |
| Config URL missing or unset | Abort (fail-closed) |

### Decision details

1. **Replace the placeholder LLM stub**: In `deploy/setup_services.sh`, replace the `echo` loops at lines 74-83 with a reachability check that curls the remote `/health` endpoints read from config.
2. **Add a retry loop**: Poll the remote `/health` endpoints until they respond or a bounded retry budget is exhausted, then proceed or abort accordingly.
3. **Fix the misleading comment**: Correct line 7 so it no longer claims the LLM services are local agent-managed subprocesses.
4. **Update documentation**: Add the remote LLM prerequisites (model dimension) and the deploy-time validation steps to `deployment_01_deployment.md`.
