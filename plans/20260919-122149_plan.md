## Goal
Add stale detection to the `code-implementation` skill to prevent execution of procedures whose referenced code constructs no longer exist, and add automatic archiving of successfully executed procedures to `implementations/done/`.

## Priority
Medium

## Scope
- **In-Scope**: Adding pre-execution stale detection step to `code-implementation` workflow, adding post-execution auto-archive step, documenting both behaviors in the SKILL.md
- **Out-of-Scope**: Moving existing stale procedures out of `implementations/`, archival policies for `implementations/done/`, changes to the `code-implementation` skill's input/output contract, changes to other pipeline phases

## Background
The `implementations/*.md` directory contains file-level implementation procedures generated by `plan-to-implementation-procedure`. After execution, procedures should move to `implementations/done/`. However, two problems were identified:

1. Stale procedures persist in `implementations/` because `code-implementation` does not verify whether the referenced code changes already exist before attempting execution. Example: `implementations/20260916-232443_01_scripts_agent_orchestrator.py.md` (now archived to `implementations/done/`) references line numbers and symbols that were removed in commit `09091e4e` ("fix: remove dead _llm_runner/_guard code from Orchestrator").

2. Execution-complete procedures remain in `implementations/` indefinitely. Currently, archival to `implementations/done/` relies on either manual action or implicit git commit history tracking. No automated mechanism moves completed procedures.

As of 2026-09-19, `implementations/done/` had accumulated approximately 4444 files (currently 4478 as of verification), indicating long-term drift between execution state and archive location.

## Problem
- `code-implementation` can attempt to execute a procedure whose target code has already been modified by another process or prior execution, wasting effort and potentially causing confusion.
- Procedures that have been executed remain in `implementations/`, making it unclear which procedures are pending vs. completed without cross-referencing git history.
- `implementations/done/` grows unboundedly with no cleanup policy.

## Reason for change
Maintainability risk: stale procedures mislead implementers into thinking work remains when it is already done. Archive drift makes auditing and cleanup difficult. Both issues compound over time as more procedures are generated and executed.

## Implementation intent
Two independent but complementary improvements within the existing `code-implementation` skill:

1. **Stale detection**: Before executing a procedure, verify that the code constructs it references (line numbers, symbol names, import paths) still exist in the current source. If they do not, mark the procedure as stale and skip execution. This prevents wasted effort and alerts operators to potential drift.

2. **Auto-archive**: After a procedure executes successfully, automatically move its source file from `implementations/` to `implementations/done/`. This ensures the archive reflects execution state rather than requiring manual intervention or git history inspection.

Both changes operate within the existing `code-implementation` skill's scope — no new infrastructure is required.

## Design
The stale detection feature adds a pre-execution validation step to the `code-implementation` workflow. Instead of relying solely on Step 3a's adversarial verification (which only corrects the procedure and continues), the new step explicitly checks whether the procedure's referenced code constructs still exist in the current source.

Key design decisions:
- Use simple regex/string matching against the cited line ranges in the procedure document — avoid AST parsing as specified in the issue
- Any single mismatch constitutes "stale" — the procedure cannot be reliably executed if even one referenced construct is missing
- Report all failures in a single pass for better operator feedback
- Auto-archive reuses the existing `tools/manage_workitem_stage.py close-implementation` tool for the actual file move, ensuring consistency with the existing archival mechanism
- Collision avoidance follows `rules/filename-collision.md` — if the destination already exists, apply the zero-padded sequence rule
