## Goal
- Classify RAG consistency startup exceptions by root cause so a programming defect is not masked as a benign "check skipped", matching the memory-injection failure classification.

## Priority
Medium

## Scope
- **In-Scope**:
  - Add exception-type classification to the RAG consistency check's non-timeout failure path in `scripts/agent/startup_validation.py`.
  - Record a `SKIPPED` outcome carrying the category in its message so a programming error is distinguishable from a timeout or a missing embedding endpoint.
  - Preserve the existing `TimeoutError -> SKIPPED (timeout)` behavior exactly.
  - Add a regression test for the programming-error path in `tests/agent/test_startup_validation.py`.
- **Out-of-Scope**:
  - Changing the fail-fast behavior of any other pipeline check (security audit, MCP auth, readiness, tool discovery, routing drift/safety tiers).
  - Making the RAG consistency check fatal.

  - Surfacing the per-category RAG indicator in the human-readable readiness summary (reporter) — see Unknowns.

## Background
The startup pipeline is the fail-fast gate for service health. The RAG consistency check is intentionally soft: it must never abort startup. Currently both the `TimeoutError` branch and the broad `except Exception` branch of `StartupValidationPipeline.check_services()` record a `SKIPPED` outcome via `pipeline.add_skipped("rag_consistency", ...)`, and the broad branch carries only the raw exception with no category. The project already separates programming errors from benign conditions elsewhere: `PromptSetup._classify_memory_failure()` returns distinct categories (`NETWORK_TRANSIENT`, `DATABASE_OR_IO`, `PROGRAMMING_ERROR`, `UNKNOWN`) so a `PROGRAMMING_ERROR` is logged and surfaced differently from a transient condition. The RAG check has no equivalent classification.

## Problem
A bug inside `RagMaintenanceService().consistency()` (for example a `KeyError`, `AttributeError`, or `TypeError`) raises one of the caught exception types and is turned into a generic `SKIPPED` outcome. The operator sees only "RAG consistency check skipped" with no signal that the skip was caused by an internal defect rather than a timeout, a missing embedding endpoint, or a transient IO error. Startup still proceeds, so the defect is easy to miss until downstream RAG behavior breaks.

## Reason for change
The startup pipeline is the fail-fast gate for service health. The RAG check is intentionally soft (it must not abort startup), but soft does not mean unclassified. Without classification operators cannot triage a skipped RAG check, and the one unclassified code path (`except Exception`) has no regression coverage — only the `TimeoutError` path is covered by `tests/agent/test_startup_validation.py`.

## Implementation intent
Add exception-type classification to the RAG consistency check that mirrors the existing memory-failure model. On `TimeoutError` keep the current `SKIPPED (timeout)` behavior. For other exceptions, classify by root cause (network/timeout vs DB/IO vs programming error vs unknown) and record the outcome so a programming error is distinguishable in logs and the outcome message. Keep the check non-fatal in all cases — startup must still proceed.

## Requirements
- `REQ-001`: Classify non-timeout exceptions raised by the RAG consistency check by root-cause category (`NETWORK_TRANSIENT`, `DATABASE_OR_IO`, `PROGRAMMING_ERROR`, `UNKNOWN`), reusing the same exception type lists as the memory-failure classification where sensible.
- `REQ-002`: Record a `SKIPPED` outcome for every non-fatal RAG failure, with the category carried in the outcome message so a programming error is distinguishable from a timeout or a missing embedding endpoint.
- `REQ-003`: Never promote a RAG failure to `FATAL`; the check stays soft in all cases.
- `REQ-004`: Add a regression test asserting a programming-error exception (e.g. `KeyError`) is recorded as a classified `SKIPPED` outcome, not an unclassified one.

## Design
The change is confined to the RAG consistency block of `StartupValidationPipeline.check_services()`. The `except TimeoutError` branch is left byte-for-byte unchanged. The broad `except Exception` branch is rewritten to classify `exc` before recording the outcome.

Classification mirrors `PromptSetup._classify_memory_failure()` in `startup_prompt_setup.py`:
- `ConnectionError` (and, defensively, `TimeoutError` if it reaches this branch) -> `NETWORK_TRANSIENT`.
- `sqlite3.Error`, `OSError` -> `DATABASE_OR_IO`.
- `AttributeError`, `NameError`, `TypeError`, `LookupError`, `AssertionError` -> `PROGRAMMING_ERROR`.
- otherwise -> `UNKNOWN`.

The `_PROGRAMMING_ERROR_TYPES` tuple is private to `startup_prompt_setup.py`; importing it would couple `startup_validation.py` to another module's internals and invite an import-layer concern outside this scope. The plan therefore re-declares the same small type list inline in `startup_validation.py`, documented as mirroring the memory-failure model. Sharing the tuple would require a small refactor of `startup_prompt_setup.py` (out of scope).

The category is conveyed through the `message` field of the `SKIPPED` `StartupCheckOutcome` produced by `StartupValidationResult.add_skipped()`. `health_models.py` was inspected and `StartupCheckOutcome` carries only `source`, `status`, `message`, `remediation`; adding a dedicated category column is intentionally out of scope because it would be a data-model/interface change. Encoding the category in the message keeps the change interface-neutral while remaining machine-distinguishable.

Message construction adds only the category label and the exception type name (e.g. `f"RAG consistency check skipped: PROGRAMMING_ERROR ({type(exc).__name__}): {exc}"`). No new sensitive data is introduced; the pre-existing `{exc}` interpolation is retained for parity with the memory-failure path.

Startup remains non-fatal in every case: no branch calls `add_fatal`.

## Risks
- **Risk**: `check_services()` is already cyclomatic-complexity grade D(26); adding branches may push it higher. → **Mitigation**: keep the classification inline and minimal; if radon grades it C or worse, extract the classifier into a small module-level helper function to contain the complexity.
- **Risk**: The inline exception type list may drift from `startup_prompt_setup.py`'s `_PROGRAMMING_ERROR_TYPES`, producing inconsistent classification. → **Mitigation**: document the list as mirroring the memory-failure model; a shared-reference refactor of `startup_prompt_setup.py` is an optional follow-up, out of scope here.
- **Risk**: Carrying `{exc}` in the message could surface a secret if an embedding/DB error embeds credentials. → **Mitigation**: add only the category label and exception type name; retain the pre-existing `{exc}` interpolation unchanged (parity with the memory-failure path) and rely on the project's existing log masking.
- **Risk**: A programming error whose type is not in the list falls to `UNKNOWN`, which is still classified and logged but not flagged as a defect. → **Mitigation**: `UNKNOWN` remains distinguishable from a timeout/missing-endpoint; the regression test pins the common `PROGRAMMING_ERROR` case.
