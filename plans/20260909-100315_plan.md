## Goal
- Make Event Bus DLQ requeue an actual, traceable redelivery operation: a requeued
  event must reach active and reconnecting subscribers, receive a fresh
  cycle-specific retry budget while its lifetime failure history stays auditable,
  and leave SQLite and the DLQ JSON file in a mutually consistent state.

## Priority
High

## Background
`scripts/eventbus/dlq.py`'s `_atomic_write()` writes a `{event_id}.json` file to
`deadletter_dir` when an event is promoted to the DLQ (`promote_to_dlq()`,
`sweep_orphans()`, `promote_single()` — confirmed by direct read, all three share
this write path). `scripts/eventbus/db.py::requeue_event()` (confirmed by direct
read) only runs
`UPDATE events SET dlq_requeue_count = dlq_requeue_count + 1, dlq_at = NULL WHERE
event_id = ? AND dlq_at IS NOT NULL` — it never calls `EventBroker.publish()`, never
touches `delivery_failure_count`, and never reconciles the JSON file.
`docs/06_eventbus_04_dlq_offsets_and_delivery_semantics.md` (line ~36) documents
exactly this behavior as the current, intended specification — the doc is not wrong,
the implementation it describes is the defect this Plan fixes.

## Problem
- A requeued event's `seq` is unchanged and already behind every subscriber's
  `since_seq`/live-delivery cursor — confirmed via `subscribe_route.py`, whose SSE
  generator only delivers rows with `seq > since_seq` at connection time or new
  events pushed live via `broker.publish()`; a cleared `dlq_at` flag matches neither
  path, so a requeued event is invisible to any consumer.
- `nack_event()` (confirmed by direct read) unconditionally increments
  `delivery_failure_count` on every NACK with no reset path. Because `requeue_event()`
  never resets this column, the very next NACK against the requeued event can push it
  back over `cfg.max_retry` and re-promote it to the DLQ almost immediately.
- The `{event_id}.json` file written at promotion time is never removed, archived, or
  updated on requeue, so SQLite (`dlq_at IS NULL` after requeue) and the filesystem
  (a DLQ record still present) diverge.

## Reason for change
Requeue must become a real retry operation: reachable delivery, a well-defined retry
budget, preserved lineage/audit history, and consistent persistence state across
SQLite and the filesystem DLQ representation.

## Implementation intent
Add a lineage column and a cycle-scoped failure counter alongside the existing
lifetime counter; on requeue, atomically gate on the existing `dlq_at IS NOT NULL`
guard (preserving today's "only one concurrent requeue succeeds" behavior), then
insert a new row carrying a freshly generated UUID v4 `event_id` (required by
`schemas/event_envelope.json`'s strict UUID v4 pattern, which every row in `events`
must satisfy) with `redelivered_from` pointing at the original event, a fresh
cycle-failure count, and the lifetime count copied forward for continuity. Publish
that new row to `EventBroker` in the same operation, and archive the DLQ JSON file to
a `requeued/` subdirectory of `deadletter_dir` using SQLite as canonical state. Switch
the DLQ-promotion predicate (`promote_single()`, `sweep_orphans()`, `promote_to_dlq()`)
from the lifetime count to the new cycle count so the retry budget is genuinely reset
on redelivery.

## Design
Split the single failure counter into a lifetime counter (`delivery_failure_count`,
unchanged meaning, never reset) and a cycle counter (`cycle_failure_count`, reset to
`0` on every successful redelivery) so the DLQ retry budget genuinely resets after a
requeue while lifetime history stays intact for auditing. Model redelivery on the
existing publish pattern (`publish_route.py`'s `insert_event()` + `broker.publish()`)
rather than inventing a new delivery mechanism: `redeliver_event()` performs the same
conditional-update guard `requeue_event()` uses today (`dlq_at IS NOT NULL`) so the
existing single-winner-under-concurrency guarantee is preserved, then inserts a new
row with a freshly generated UUID v4 `event_id` (required by the envelope schema's
strict pattern) and a `redelivered_from` lineage pointer, and the route handler
publishes that new row exactly as a fresh `/publish` call would. This keeps the
change additive at the schema level (two new nullable/defaulted columns, no
`event_id` uniqueness relaxation) and reuses `run_with_db_lock()`'s existing
serialization instead of introducing new locking. DLQ JSON-file reconciliation is
implemented as an archive (move to a `requeued/` subdirectory), not a delete, so the
audit trail of "this event was once in the DLQ" is preserved on disk as well as in
SQLite's `dlq_requeue_count`.

## Risks
- **Risk**: This Plan's REQ-008 (switching `promote_single()`/`sweep_orphans()`/
  `promote_to_dlq()`'s SQL predicate to `cycle_failure_count`) and
  `issues/20260907-125042_eb_m06_consolidate_dlq_promotion_paths.md` (a separate,
  not-yet-planned issue outside this batch) both modify the same three functions in
  `scripts/eventbus/dlq.py` — that issue's own Background confirms
  `promote_to_dlq()`/`sweep_orphans()` share a near-duplicate `WHERE
  delivery_failure_count >= ?` query it intends to consolidate. → **Mitigation**:
  whichever lands first must apply its change to the current predicate name
  (`delivery_failure_count` today, `cycle_failure_count` after this Plan); the
  implementer of the second should re-read `dlq.py`'s current state rather than
  assuming this Plan's description of the predicate name still holds verbatim.
- **Risk**: This Plan and `eb_h01`'s Plan (`plans/20260909-094115_plan.md`) both add
  `CREATE TABLE`/`ALTER TABLE` DDL to the same two files
  (`scripts/eventbus/schema.sql`, `scripts/db/schema_sql.py`). → **Mitigation**:
  confirmed no column-name or table-name overlap between the two Plans (`eb_h01`
  explicitly leaves `delivery_failure_count`/`dlq_at` untouched); whichever Plan is
  implemented second must re-read both DDL files' latest state at implementation
  time and add its DDL alongside the other's, not by reverting to a stale diff base.
- **Risk**: `tests/eventbus/test_eventbus_ack_endpoint.py::TestAckMonotonicOffset::test_older_seq_ack_moves_offset_backward`
  already fails on `master` before any change in this Plan (confirmed independently
  by running the full suite: 169 passed, 1 pre-existing failure) — it asserts
  behavior contradicting `write_offset()`'s current code and ADR-006's Monotonicity
  Invariant, and was already flagged in `eb_h01`'s Plan. → **Mitigation**: treat as a
  pre-existing, out-of-scope regression for this Plan (per `AGENTS.md` Global Rule 5
  and `rules/ai-execution.md` Step-Level Failure Triage); do not fix it as part of
  this Plan's implementation, and do not let it block this Plan's own validation
  sequence, which must otherwise show no *new* failures.
- **Risk**: Changing `nack_event()`'s return type from `int` to a two-value shape is
  a signature-breaking change for any caller not covered by `rg` in this Plan's
  research. → **Mitigation**: `rg "nack_event"` across `scripts/` and `tests/`
  confirmed the only callers are `ack_route.py`'s `_nack_and_promote()` and the unit
  tests already listed as target files; re-run the same `rg` at implementation time
  to catch any caller introduced since this Plan was written.
- **Risk**: A redelivered event's new UUID v4 `event_id` diverges from the original
  `event_id` a client used to submit the NACK/DLQ chain, which could surprise a
  caller expecting the same `event_id` to remain valid indefinitely. → **Mitigation**:
  `redelivered_from` makes the lineage traceable; the Issue's own "preserve lineage"
  Implementation Intent explicitly permits a new identity as long as lineage is
  recorded, and UNK-01 covers exposing the new `event_id` in the requeue response so
  callers can follow it forward.
