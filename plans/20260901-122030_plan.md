# Plan: Write manual operator recovery runbook for workflow.sqlite / eventbus.sqlite

## Goal
Create an Operations runbook documenting the manual recovery procedure for `workflow.sqlite` and `eventbus.sqlite`, based on confirmed backup coverage from `rotate_all_dbs()`.

## Priority
Medium

## Scope
- **In-Scope**: Document the manual recovery procedure for `workflow.sqlite` and `eventbus.sqlite`; cross-reference from ADR-008's Related Documents.
- **Out-of-Scope**: Implementing backup coverage for workflow/eventbus if none currently exists; changing ADR-008's recovery policy itself; implementing automatic backup or recovery code.

## Background
ADR-008 (post-merge, 2026-08-31) Decision Details #20 / INV-18 establishes that `workflow.sqlite` and `eventbus.sqlite` corruption recovery is a manual operator action — automatic restoration is prohibited. Repository evidence confirms that `rotate_all_dbs()` archives all four databases including `workflow.sqlite` and `eventbus.sqlite` (`scripts/db/rotation.py:69-78`), so backups exist. However, no document describes what manual recovery procedure operators should follow when corruption occurs.

## Problem
The only Operations-facing statement about workflow/eventbus recovery today is the error detail string returned by `recover_corruption(target="workflow"|"eventbus")`: `"Automatic recovery is prohibited for {target}. Manual intervention required."` — there is no step-by-step procedure (e.g., what backup exists, if any; how to validate a candidate; how to manually apply it; what to do if no backup exists).

## Reason for change
A documented policy without an accompanying runbook leaves operators unable to act when the documented scenario (workflow/eventbus corruption) actually occurs, defeating the purpose of documenting the policy at all.

## Implementation intent
Write an Operations runbook section describing the manual recovery procedure for `workflow.sqlite` and `eventbus.sqlite`, covering: what backups currently exist for these two databases (confirmed via `rotate_all_dbs()`), the manual steps an operator should take to validate and apply a backup if one exists, and what to do if no backup exists (data-loss acknowledgment / escalation path).

## Design
Path A classification: affects ≤ 3 files, no public/runtime interface changes, no DB schema changes. Architecture analysis skipped per Path A rules.

Backup coverage confirmed by repository evidence:
- `rotate_all_dbs()` archives all four databases (rag, session, workflow, eventbus) using WAL-consistent SQLite online backup API (`scripts/db/rotation.py:69-78`).
- Each archived file uses timestamp suffix format `{db_stem}_{timestamp}.{suffix}` (`scripts/db/rotation.py:36`).
- Archives are stored in `/opt/llm/db/archive` by default (`scripts/db/rotation.py:20`).

Manual recovery procedure design:
1. Operator identifies corruption via `recover_corruption()` returning `action="no_recovery_allowed"`.
2. Operator locates latest valid archive in `/opt/llm/db/archive/` matching `{db_stem}_*.sqlite`.
3. Operator validates archive integrity using `PRAGMA integrity_check` against the archive.
4. Operator archives corrupt DB as `{db_stem}_corrupt_{timestamp}.sqlite` (same pattern as `scripts/db/recovery.py:126`).
5. Operator copies validated archive to original DB path.
6. Operator re-verifies restored DB integrity.
7. If no valid archive exists: data-loss acknowledgment and escalation path.
