## Goal
- Stop shell-mcp from passing its own process environment (and the MCP Bearer tokens and `GITHUB_TOKEN` it contains) to the commands it runs, so a model-chosen command can no longer read other servers' credentials.

## Priority
High

## Scope
- **In-Scope**: Build the command environment from an explicit allowlist of runtime basics instead of `os.environ.copy()`; drop secret-shaped variables unconditionally, including ones supplied through `req.env`; document the environment contract in the shell server config comments and the shell MCP documentation; add tests.
- **Out-of-Scope**: Changing firejail options or the sandbox backend; narrowing which tokens the Agent hands to each subprocess server (recorded as UNK-02, a separate follow-up); the posture gate bypass, empty-token fail-open, config-isolation ordering, audit logging, and rag-pipeline lifecycle (separate issues).

## Background
The Agent starts each MCP subprocess with an environment built by `CommandValidator.filter_env()`. Its default allowlist (`_DEFAULT_ALLOWED_ENV_VARS`) passes `MCP_*_AUTH_TOKEN` and `GITHUB_TOKEN` to every server by design, and `McpServerConfig.env` defaults to an empty dict, so the allowlist always applies to a configured server. shell-mcp then builds each command's environment in `ShellService.run_command()` as `os.environ.copy() | {"PATH": ...} | filtered_env`. The firejail wrapper (`--private --net=none --noroot`) isolates filesystem and network but does not clear the environment. `env_allowlist` / `env_denylist` filter only caller-supplied `req.env`.

## Problem
A probe that set `MCP_GITHUB_AUTH_TOKEN`, `GITHUB_TOKEN` and `MCP_SHELL_AUTH_TOKEN` in the server process and ran the allowlisted command `python3 -c "..."` through `ShellService.run_command()` returned all three variable names in the command output. `python` and `python3` are in the shipped `command_allowlist`, so a prompt-injected or misbehaving model can read every token the shell server holds and carry it into the tool result, conversation history and logs. (The probe ran inside another sandbox, so firejail's own isolation was not exercised; the environment pass-through does not depend on it.)

## Reason for Change
The shell tool is the one server designed to run model-chosen code, yet it receives the credentials of higher-privilege servers (git, cicd, file-write, file-delete, github). This is a security exposure at a trust boundary and defeats per-server token separation.

## Implementation Intent
Replace the inherited environment with a minimal base environment built from an explicit key allowlist, pin `PATH` to the configured value, keep the existing `req.env` filtering, and apply a final secret-pattern drop to the merged result so no configuration or caller input can re-introduce a credential. Put the pure environment-building logic in the existing static helper module so it is unit-testable without spawning a process.

## Requirements
- `REQ-001`: `ShellService.run_command()` builds the command environment from an explicit allowlist of base keys (`HOME`, `USER`, `LOGNAME`, `SHELL`, `LANG`, `LC_*`, `TMPDIR`, `TMP`, `TEMP`) and the configured `PATH`; it never copies `os.environ` wholesale.
- `REQ-002`: Variables that look like secrets are dropped from the final environment unconditionally, even when named in `req.env` or `env_allowlist`: `MCP_*`, `GITHUB_TOKEN`, and any name containing a `TOKEN`, `SECRET`, `PASSWORD`, `PASSWD`, `CREDENTIAL` or `API_KEY` word segment (matched on `_`-delimited segments so `TOKENIZERS_PARALLELISM` is kept).
- `REQ-003`: The existing `req.env` allowlist/denylist filtering and the pinned `PATH` behavior are unchanged.
- `REQ-004`: The environment contract is documented in `config/shell_mcp_server.toml` comments and in the shell section of the MCP documentation (boundaries, failure behavior).
- `REQ-005`: Tests prove a command cannot observe token variables present in the server process and that legitimate variables and filtering still work.

## Design
Path B (more than three files). Architecture analysis: `lint-imports` reports all 6 contracts kept; `shell_service.py` imports `shell_service_static_helpers` (same package), so the helper placement adds no cross-layer import. `shell_service.py` is 13523 bytes (limit 16384), so the logic goes into the existing static helper module rather than growing the service. The environment is built as: base keys copied from `os.environ` by exact name or glob (`LC_*`), `PATH` set to the configured value, `req.env` merged after the existing allowlist/denylist filter, then a final pass removes any key matching the secret rule. The secret rule is word-segment based: split the key on `_`, drop when any segment equals `TOKEN`, `SECRET`, `PASSWORD`, `PASSWD`, `CREDENTIAL`, `CREDENTIALS`, or the key starts with `MCP_`, or `API` is followed by `KEY`. This keeps `TOKENIZERS_PARALLELISM`. Operational dependency: production starts `/opt/llm/bin/mcp_shell`, a binary built from `scripts/`, so a deploy requires rebuilding binaries (see Implementation steps). Historical analysis (30 days): `shell_service.py` 0 commits, the static helper 1, `config/shell_mcp_server.toml` 2, the MCP shell document 21 (the highest-churn target, so keep its edit small and rebase before committing).
