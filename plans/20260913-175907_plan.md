# Fix HTTP augment fallback chain identity vs truthiness inconsistency

## Goal
Ensure the RAG pipeline's fallback chain reliably distinguishes "no result available"
(`None`, triggers fallback) from "valid empty result" (empty string, used as-is) by
adding assertions where the contract is enforced but undocumented, and by correcting
a stale assumption about `PipelineContext.reranked`'s nullability.

## Priority
Medium

## Scope
- **In-Scope**: Adding an assertion enforcing the identity-vs-truthiness contract in
  `pipeline.py`'s `augment()`; adding docstring + assertion to `http_augment.py`'s
  `HttpAugment.run()`; correcting `PipelineContext.reranked`'s docstring to state it is
  never `None` (always a `list`, possibly empty) — the opposite of the Issue's original
  assumption
- **Out-of-Scope**: Changing the fallback order; adding new fallback stages; changing
  HttpAugment's return values; implementing sentinel objects like `_NO_RESULT`;
  `pipeline_service.py` (see Background — its docstring already fully documents the
  contract, no further action needed)

## Background
The RAG pipeline has a multi-stage fallback chain: HTTP augment → semantic cache →
search pipeline → refiner → raw chunks. Each stage must signal either "success with
result" or "fallback needed." The critical distinction is between:
- `None`: No result available, trigger fallback
- Empty string `""`: Valid result, just empty content

The Issue claimed `pipeline_service.py`'s `call_rag_service()` used `or` chaining that
conflates `None` with falsy values. Repository evidence shows this claim does NOT hold
against the current codebase — `call_rag_service()` returns a tuple
`(result: str | None, status_code: int | None, elapsed_ms: float)`, and its docstring
(lines 60-86) already documents the full return contract in a table, distinguishing
`str` (non-empty), `""` (valid empty), and `None` (triggers fallback) explicitly. No
`or` chaining exists anywhere in the current pipeline code.

**Re-verified 2026-09-13** (this cycle, against the current repository state):
- `pipeline_service.py`'s `call_rag_service()` docstring (lines 60-86) already fully
  satisfies what the original Issue/Plan draft asked for — no further documentation
  change is needed here. This file is therefore removed from `Implementation Target
  Files` (see Requirements below).
- `pipeline.py`'s `augment()` (lines 247-283) already carries an "Identity vs
  truthiness" docstring section explaining the `is not None` contract. What remains
  missing is a runtime assertion enforcing it — the docstring alone does not catch a
  future regression.
- `http_augment.py`'s `HttpAugment.run()` (lines 84-122) correctly implements the
  identity-vs-truthiness distinction in its `_http_result_kind` classification
  (`remote_nonempty` / `remote_empty` / `in_process_fallback`), but its docstring is a
  single line with no explanation, and no assertion enforces the contract.
- `stage.py`'s `PipelineContext.reranked` (line 44) is declared as
  `reranked: list[RagHit] = dataclasses.field(default_factory=list)` — **not**
  `list[RagHit] | None` as the original Plan draft assumed. This field can never be
  `None`; an empty list is its only "no results" representation. The original Plan
  draft's REQ-004 (documenting `reranked` as "identity-checked: None = fallback, empty
  list = valid") was based on a factual error and has been corrected below to state the
  opposite: `reranked` is guaranteed never-`None`, so no identity check applies to it at
  all — this itself is worth documenting, since the Issue's core confusion (None vs.
  empty) is exactly the kind of assumption a reader could wrongly project onto this
  field without the correction.

## Problem
While the specific `or`-chaining bug cited by the Issue does not exist in current code,
two of the four originally-identified locations (`pipeline.py`, `http_augment.py`) lack
a runtime assertion backing their already-correct identity-vs-truthiness logic, leaving
that contract to erode silently under future changes. A third location
(`PipelineContext.reranked`) was mischaracterized in the original Plan draft as
nullable when it is not.

## Reason for change
Add defensive assertions at the two locations where the identity-vs-truthiness
contract is enforced by code but not backed by a runtime check, and correct the
`PipelineContext.reranked` documentation to state its true (never-`None`) contract —
preventing exactly the kind of None/empty confusion the Issue raised, but scoped to
where it actually applies.

## Implementation intent
1. Add an assertion in `pipeline.py`'s `augment()` enforcing `result is not None or
   result == ""` before returning from the HTTP-mode branch
2. Add docstring + assertion to `http_augment.py`'s `HttpAugment.run()` documenting and
   enforcing the same contract
3. Correct `PipelineContext.reranked`'s field-level comment to state it is never
   `None` — always a `list`, possibly empty — the inverse of what the original Plan
   draft assumed

## Design
This task is classified as **Path A** (small task): affects 3 files, no public interface
changes, no database schema changes.

This cycle's re-verification against current repository state found two material
corrections to the prior Plan draft:
1. **REQ-001 dropped**: `pipeline_service.py`'s docstring already fully documents the
   None/""/str contract (added by a change unrelated to this Plan, prior to this
   cycle). No further documentation work is needed there.
2. **REQ-004 corrected**: the prior draft assumed `PipelineContext.reranked` was typed
   `list[RagHit] | None` and needed to be documented as "identity-checked." Direct
   inspection shows it is declared `list[RagHit]` with `default_factory=list` — it can
   never be `None`. The requirement is corrected to document the opposite fact.

Key design decisions:
1. Use assertions rather than runtime `if`/raise checks — assertions are stripped in
   production (`python -O`) but provide developer-facing safety during development,
   consistent with how this class of defensive check is used elsewhere in this Plan's
   target files
2. Do not modify `call_rag_service()`'s return type or `HttpAugmentResult`'s fields —
   the existing contracts already encode the distinction correctly; only the two
   under-asserted call sites and the one mischaracterized field get changes
3. Do not introduce a sentinel object (e.g. `_NO_RESULT`) — the Issue raised this as an
   unresolved question; deferred since the current `None`/`""` approach already works
   correctly at all three target locations

## Risks
- **Risk**: An assertion added in Phase 2 could fail in production if any stage returns
  an unexpected falsy value (e.g. `0`, `False`) → **Mitigation**: assertions use the
  `is not None or == ""` pattern which only accepts `None` or empty string, rejecting
  other falsy values
- **Risk**: Assertions are stripped under `python -O`, providing no production
  enforcement → **Mitigation**: this is a known, accepted trade-off — the assertions are
  a development-time safety net, not a production guarantee; the existing docstrings
  and correct current logic are the actual production-time contract
- **Risk**: The corrected REQ-004 comment could still be misread as implying `reranked`
  behaves like the other identity-checked fields → **Mitigation**: the comment
  explicitly states "no identity check applies to this field," distinguishing it from
  `pipeline.py`/`http_augment.py`'s `result` variables
