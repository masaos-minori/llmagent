# Fix HTTP augment fallback chain identity vs truthiness inconsistency

## Goal
Align the fallback logic across both code paths used by the RAG pipeline to distinguish between "no result available" (None) and "empty result" (empty string or empty list). Ensure callers can reliably determine whether a stage produced a valid result versus signaling fallback.

## Priority
Medium

## Scope
- **In-Scope**: Documenting the current identity-vs-truthiness handling in the RAG pipeline's fallback chain; adding clarifying assertions/docstrings where the distinction matters
- **Out-of-Scope**: Changing the fallback order; adding new fallback stages; changing HttpAugment's return values; implementing sentinel objects like `_NO_RESULT`

## Background
The RAG pipeline has a multi-stage fallback chain: HTTP augment → semantic cache → search pipeline → refiner → raw chunks. Each stage must signal either "success with result" or "fallback needed." The critical distinction is between:
- `None`: No result available, trigger fallback
- Empty string `""` or empty list `[]`: Valid result, just empty content

The Issue identified that `pipeline.py`'s `augment()` method uses explicit `is not None` checks (line 298, 336), while the Issue claimed `pipeline_service.py` used `or` chaining which conflates None with falsy values. However, repository evidence shows the current codebase does NOT have `or` chaining — `pipeline_service.py`'s `call_rag_service()` returns a tuple `(result: str | "", status_code: int | None, elapsed_ms: float)` where empty string is a valid result, not a fallback signal.

## Problem
While the specific `or` chaining bug cited in the Issue has been resolved in the current codebase, the underlying design concern remains: the fallback chain's contract relies on callers correctly distinguishing None from empty results. Without clear documentation and assertions, future modifications could reintroduce the confusion.

## Reason for change
The current codebase handles the identity-vs-truthiness distinction correctly but lacks explicit documentation and defensive assertions. Future developers may inadvertently introduce truthiness-based comparisons when modifying the fallback chain.

## Implementation intent
1. Add explicit docstring documentation to `call_rag_service()` clarifying the None vs empty-string contract
2. Add assertions in `pipeline.py`'s `augment()` method to enforce the identity-vs-truthiness contract
3. Add similar assertions in `http_augment.py`'s `HttpAugment.run()` method
4. Update `PipelineContext` docstring to document the expected semantics of `reranked` field

## Requirements
- `REQ-001`: `call_rag_service()` must clearly document that empty string `""` is a valid result (not a fallback signal)
- `REQ-002`: `pipeline.py`'s `augment()` method must enforce identity-vs-truthiness checks consistently

- `REQ-004`: `PipelineContext.reranked` must be documented as an identity-checked field (None = fallback, empty list = valid)

## Design
This task is classified as **Path A** (small task): affects ≤ 3 files (actually 4), no public interface changes, no database schema changes. The primary finding from Step 2 adversarial verification is that the Issue's core claim about `or` chaining is NOT confirmed by repository evidence — the current codebase already uses explicit `is not None` checks in all relevant locations.

The Plan therefore focuses on documenting the existing correct behavior rather than fixing a bug. This is consistent with the Issue's underlying intent (preventing future regressions) without making unnecessary code changes.

Key design decisions:
1. Use docstring additions rather than sentinel objects — the Issue raised the `_NO_RESULT` question as an unresolved item; we defer that decision since the current approach works
2. Use assertions rather than runtime checks — assertions are stripped in production (`python -O`) but provide developer-facing safety during development
3. Do not modify `call_rag_service()`'s return type — the tuple `(str | "", int | None, float)` already encodes the contract correctly
