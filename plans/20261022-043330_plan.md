# Replace the Shutdown Path's Unreachable Checkpoint Timeout with an Awaitable Worker Step and One Stated Bound

**Plan ID**: 20261022-043330
**Source Issue**: issues/20261021-093421_shutdown001-wal-checkpoint-timeout-guard-cannot-fire.md
**Generated**: 2026-10-22 04:33 JST

## Goal

Make the shutdown path's checkpoint bound real: stop the event loop at a stated
time, keep the SQLite work intact on a worker thread, and make the outcome of a
stopped shutdown visible instead of log-only.

## Priority

- **Primary goal**: make the existing `asyncio.wait_for` at
  `scripts/agent/resource_shutdown_coordinator.py:72-87` able to reach its
  `TimeoutError` branch, which it cannot today because the awaited step blocks
  the loop.
- **Must be resolved first**: the single question of *which* timeout the shutdown
  path states. One bound is in force (`_GRACEFUL_TIMEOUT_S = 10.0`,
  `resource_shutdown_coordinator.py:29`); the two constants beside the checkpoint
  step are never read (`_WAL_CHECKPOINT_TIMEOUT_S = 30.0`,
  `_WAL_BACKUP_TIMEOUT_S = 10.0`, `wal_checkpoint_manager.py:32-33`); and a bare
  literal `5` decides the PASSIVE-to-TRUNCATE fallback inline
  (`wal_checkpoint_manager.py:73`).
- **Secondary goals**: fold the two unread constants and the inline `5` into the one
  bound the coordinator reads; make a `TimeoutError` reaching the coordinator mean
  only "the bound expired"; surface collected shutdown errors through the `CLIView`
  the coordinator already holds; stop discarding the checkpoint counts.
- **Out of scope**: tuning the bound (choosing a number is UNK-01, not this
  Plan); WAL mode policy for the maintenance path (it already reads
  `sqlite_wal_checkpoint_mode`, `scripts/db/maintenance.py:140-148`); `busy_timeout`
  or `timeout` values; the shutdown-order docs rewrite `docs/23_agent/agent_10_01_*`
  already carries for `repl001`; `background_tasks` draining
  (`resource_shutdown_coordinator.py:114-131`) — that is `turn005`, which also
  owns the `Repl._active_ctx` question `repl001` UNK-03 defers.

## Background

The source issue claims the `except asyncio.TimeoutError` at
`scripts/agent/resource_shutdown_coordinator.py:85-87` is unreachable. That is
true at HEAD, and the reason is mechanical: `checkpoint_sync`
(`scripts/agent/wal_checkpoint_manager.py:57-113`) contains no `await`, so
`await asyncio.wait_for(step, timeout)` runs the whole step as one continuous
block on the loop thread. `wait_for` can only resume when the awaited step
yields, and it never yields.

Measured directly (a throwaway probe, not a repo file): with a 1.0 s bound
around a 3.0 s blocking body, HEAD's shape awaited for 3.00 s and took no
timeout branch; the same step through `asyncio.to_thread` returned after 1.00 s
with `TimeoutError` raised and the branch taken. A plain daemon thread behaves
the same for the bound.

The second measurement is why this matters at all: `time.sleep` appears exactly
once in the whole `scripts/` tree — `wal_checkpoint_manager.py:101`, `2 ** attempt`
between retries, up to 2 sleeps. Those sleeps sit on the loop thread, inside a
step with no await point, inside the very span the bound is meant to limit.

What the real SQLite behavior is on a contended database was also measured with a
second connection holding an open read transaction over 5,000 committed rows:

| Measurement | Value |
|---|---|
| `-wal` size while a reader holds the database | 53,592 bytes (13 frames) |
| `PRAGMA wal_checkpoint(TRUNCATE)`, production `busy_timeout=30000` | blocked 30.05 s, returned `(busy=1, log=13, checkpointed=0)` |
| Same, `busy_timeout=0` | returned a busy row (busy=1) rather than raising |
| Production `checkpoint_sync()` under the same contention | returned `(True, [])` in 0.00 s, WAL unchanged |

The last row is the issue's most important correction: `PRAGMA
wal_checkpoint(PASSIVE)` returns `(0, 13, 0)` without raising. The code treats a
non-raise as success (`wal_checkpoint_manager.py:80`), so a PASSIVE checkpoint
that copied **zero** frames of a non-empty WAL is recorded as success, the
TRUNCATE fallback and both retry sleeps are never reached, and
`checkpoint_sync` returns `True` — which makes `backup_sync` skip its step
entirely (`resource_shutdown_coordinator.py:81-83`). The silent no-op is real;
the blocking retry path that the guard was written for is what never runs.

The live `/opt/llm/db/session.sqlite-wal` is 0 bytes, so the success path works
today. This is a failure-path defect.

## Problem

`checkpoint_sync` blocks the event loop for its entire duration (SQLite calls plus
`time.sleep` backoff). The 10.0 s `asyncio.wait_for` wrapped around it therefore
measures nothing: it cannot interrupt the step it awaits, and a shutdown that
stalls waits for SQLite instead of for the bound. The only time value in this step
that has any effect is the inline `elapsed > 5` comparison at
`wal_checkpoint_manager.py:73`, which runs *after* the blocking call has already
finished.

## Reason for Change

- A guard that cannot fire is not a guard; the constant next to it invites the
  next reader to believe a bound exists.
- The same defect makes the existing tests false: `tests/agent/test_repl.py:928-955`
  and the four tests in `tests/agent/test_resource_shutdown_coordinator.py` stub
  `checkpoint_sync` with an `AsyncMock` whose `await` yields, so they exercise a
  shape the production method does not have. `test_resource_shutdown_coordinator.py`
  has no non-stubbed test for either step.
- Three time values sit around this path and only one of them is read.
  `_WAL_CHECKPOINT_TIMEOUT_S = 30.0` and `_WAL_BACKUP_TIMEOUT_S = 10.0`
  (`wal_checkpoint_manager.py:32-33`) appear in no other file and no expression;
  `_GRACEFUL_TIMEOUT_S = 10.0` (`resource_shutdown_coordinator.py:29`) is the value
  both `wait_for` calls actually use. `rg -n "_WAL_CHECKPOINT_TIMEOUT_S|_WAL_BACKUP_TIMEOUT_S"
  scripts/ tests/` returns only the two definition lines: no expression, no test,
  and no import reads them. `uv run vulture scripts/ --min-confidence 80`
  (`rules/toolchain.md:137`) reports nothing, so no tool notices. Removing unused
  module-level constants is what `rules/coding.md:130-132` asks for: its dead-code
  exemption is scoped to the `logger = logging.getLogger(__name__)` boilerplate and
  explicitly does not extend to unused constants. There is no `NoQA`/`W031` marker
  anywhere in this repository to read instead.

## Implementation Intent

Run blocking shutdown work where blocking work belongs (a worker thread) so the
loop is free to enforce a bound; state that bound once; and report the result.
No change to the cleanup *order*, to `SQLiteHelper`'s open/use/close discipline, or
to which component owns the sequence.

**Naming and concept boundaries**
- Keep the names `WalCheckpointManager`, its `checkpoint_sync` / `backup_sync`
  methods, and `ResourceShutdownCoordinator.close_resources`; only the internals of
  the two `*_sync` bodies change. `checkpoint_sync` returns
  `tuple[bool, list[tuple[str, str]]]` (`:57`) and `backup_sync` returns
  `tuple[str | None, list[tuple[str, str]]]` (`:115`); there is no `CommandStep`
  type in this repository. Keeping those signatures is what keeps
  `resource_shutdown_coordinator.py:64-151` and the existing test call shapes
  unchanged.
- "Unbound blocking call": a call with no await point, so no timeout can be
  applied to it from the awaiting side. The fix is to give the step await points,
  not to enlarge a bound.
- "Bound expired": the only meaning a `TimeoutError` from `wait_for` may carry
  after this Plan. A SQLite failure is a different type: `sqlite3.OperationalError`
  resolves to `DatabaseError` → `Error` → `Exception` (verified in the project venv;
  `sqlite3.TimeoutError` does not exist in this interpreter), and the measured
  contended `PRAGMA wal_checkpoint` returns busy counts instead of raising.
- Reuse what is already there: `SQLiteHelper.open()` (`scripts/db/helper.py:166`),
  `.checkpoint(mode)` (`:267`, returns `WalCheckpointCounts`), `.close()` (`:207`),
  and the `errors: list[tuple[str, str]]` that `close_resources` builds locally
  (`resource_shutdown_coordinator.py:67`) and summarizes at `:149-151`. There is no
  `SQLiteHelper.backup_to` and no `ShutdownErrorCollector` class; the backup step is
  a `shutil.copy2` of the `-wal` file (`wal_checkpoint_manager.py:167`). No new
  error type, no new accumulator.

**Architectural boundaries**
- Layer contract unchanged: `agent/*` → `db/*`. `wal_checkpoint_manager.py` keeps
  importing `db.helper` and `db.models`; `scripts/db/*` is not a target.
- The whole `open()` / use / `close()` sequence stays on one worker thread:
  `SQLiteHelper._connect` (`scripts/db/helper.py:127-135`) creates a
  thread-affine `sqlite3.Connection`, so a connection may not be created on the
  loop thread and used on a worker. The unit handed to the worker is the complete
  step body, not a connection.
- One worker per step (checkpoint, then backup) rather than one worker running
  both: with one worker, cancelling the outer await could not stop before the
  backup half started. The residual cost is stated in Risks.

## Requirements

- REQ-001: the step the coordinator awaits must yield control to the event loop
  while its SQLite and retry work runs elsewhere, so `wait_for` can reach its
  timeout branch.
- REQ-002: all SQLite connection use within a step must happen on the worker
  thread that opened the connection, including `close()`.
- REQ-003: exactly one shutdown-path timeout value must be read by the code that
  enforces a bound, and it must be defined in exactly one place. That means the two
  unread constants (`wal_checkpoint_manager.py:32-33`) and the inline `elapsed > 5`
  comparison (`:73`) are folded into it, per `rules/coding.md:130-132`.
  `ReplInputLoop._GRACEFUL_TIMEOUT_S` (`repl_input_loop.py:55`, read at `:125` and
  `:290`) is a bound on a different path, is in force, and is not a target here —
  `repl001` keeps its value.
- REQ-004: the entry recorded for an abandoned step must say that the bound expired,
  and must stay distinguishable from an entry recorded for a failure raised by the step
  body itself. `wait_for` raises the builtin `TimeoutError`; a SQLite failure raises
  `sqlite3.OperationalError`, and a contended checkpoint raises nothing at all.
- REQ-005: a checkpoint that raises no exception but copies zero frames while the
  WAL is non-empty must produce an entry in `close_resources`'s shutdown error list
  with enough detail to tell a contended checkpoint from a successful no-op.
- REQ-006: the `WalCheckpointCounts` values returned by `SQLiteHelper.checkpoint()`
  (`scripts/db/helper.py:267-281`) must be read, not discarded.
- REQ-007: errors collected during shutdown must reach the human-visible channel
  the coordinator already holds, in addition to the log.
- REQ-008: no `time.sleep` may run on the event loop thread. `skills/DESIGN.md:292-293`
  states the rule and the intended remedy: "In `async def` functions, never introduce
  blocking I/O (`time.sleep()`, sync file/network calls) — use `await asyncio.sleep()`
  or run blocking paths in executors." So every retry backoff must run on a worker
  thread. Note that this is a documented convention, not a gate: `[tool.ruff.lint]
  select` is `["E", "W", "F", "I", "UP", "BLE001"]` (`pyproject.toml:96`) and
  `uv run ruff check scripts/agent/wal_checkpoint_manager.py` passes at HEAD.
- REQ-009: the order and grouping of cleanup steps (checkpoint, backup, context
  flush, MCP, memory, background drain, runtime close, vector store, metrics,
  audit) must not change.
- REQ-010: an abandoned step's already-written effects must stay consistent with
  its own success signal. `backup_sync` copies the `-wal` file with
  `shutil.copy2` (`scripts/agent/wal_checkpoint_manager.py:167`) into the path it
  builds at `:141-153`, and `wait_for` cannot stop a worker that has already
  started, so a bound-expired backup can leave a partial copy behind while the
  coordinator records a timeout error. The behavior chosen must be stated in the
  module docstring.
- REQ-011: a test that asserts a timeout branch fired must be built from the
  production step body, not from a stub whose await behavior the production code
  does not have.

## Acceptance Criteria

- AC-1: a step whose SQLite work exceeds the bound is cancelled at the bound, with
  evidence measured from the production step body (a real WAL under contention),
  not from a stub.
- AC-2: exactly one shutdown-path timeout value is defined and read by the code
  that enforces a bound; `rg -n "Timeout" scripts/agent/wal_checkpoint_manager.py`
  and `_GRACEFUL_TIMEOUT_S` no longer coexist as unused constants.
- AC-3: no `time.sleep` runs on the event loop thread; `rg -n "time\.sleep"
  scripts/` still returns exactly the one retry site and that site is inside the
  worker function.
- AC-4: a zero-frame checkpoint over a non-empty WAL produces a recorded
  `ShutdownError` naming the frame count; a zero-frame checkpoint over an empty
  WAL does not.
- AC-5: collected shutdown errors are visible to the user through the coordinator's
  `CLIView`, and the existing log line still appears.
- AC-6: the cleanup order in `close_resources` is unchanged, verifiable against the
  order table in `docs/23_agent/agent_10_01_*` at `:74-82`.
- AC-7: the abandoned-step behavior of REQ-010 is stated in the module docstring,
  and the docstring claims match the code.
- AC-8: `uv run mypy --no-namespace-packages scripts/agent/wal_checkpoint_manager.py
  scripts/agent/resource_shutdown_coordinator.py` passes, and `vulture` reports no

## Unknowns

- UNK-01: which bound the shutdown path states. Blocking at a bound is a policy
  choice, not an implementation detail: `sqlite_busy_timeout_ms = 30000`
  (`config/agent.toml:12`) plus a TRUNCATE fallback means a real checkpoint can
  legitimately take ~30 s, while `_GRACEFUL_TIMEOUT_S = 10.0` and the two 5.0 s
  constants all suggest less. Any value under the busy timeout converts a slow but
  successful checkpoint into a cancelled one. Options: (a) one value ≥ the busy
  timeout, so the bound only catches truly stuck work and the busy timeout is the
  mechanism that handles contention; (b) keep 10.0 s as the outer bound and lower
  the busy timeout used by the shutdown connection; (c) keep 5.0 s per step.
  Decide before Phase 3. Blocking: no. Blocks: Phase 3 (REQ-003 can proceed by
  collapsing the constants without choosing a new number).
- UNK-02: whether "the bound is enforceable" means the await returns within the
  bound (the measured `asyncio.to_thread` and daemon-thread behavior) or the
  process finishes within the bound. Measured: a 1.0 s bound around a 3.0 s step
  returned in 1.0 s by both routes, but a process that abandoned a default-executor
  worker took 6.0 s total wall time, because `concurrent.futures.thread._python_exit`
  (`/usr/lib/python3.14/concurrent/futures/thread.py:23-31`) joins worker threads
  at interpreter exit. Only a daemon thread bounds the process. `backup_sync` is plain
  synchronous code inside an `async def` (`wal_checkpoint_manager.py:115-172`,
  `shutil.copy2` at `:167`) and no code in this module uses threads today, so either
  route is new here. There is no lint rule to retire in either route:
  `pyproject.toml:96-99` selects no `ASYNC` rule. Decide during Phase 1, from a
  measurement in the new test file. Blocking: no.
  Blocks: Phase 1's shape.
- UNK-03: what a step must record when the *bound* expires versus when the step body
  itself raises. The two are distinguishable by type — `wait_for` raises the builtin
  `TimeoutError` (which `asyncio.TimeoutError` has been since 3.11), while a SQLite
  failure raises `sqlite3.OperationalError`, and the measured contended
  `PRAGMA wal_checkpoint` raises nothing and returns busy counts. What is not decided
  is which label each branch records, because a worker abandoned by `wait_for` keeps
  running and may finish after the coordinator has already reported a timeout. This is
  REQ-004. Options: label only the `wait_for` cancellation and let any other exception
  keep its own type name (what `close_resources` does today at
  `resource_shutdown_coordinator.py:78-86`), or wrap the cancellation in a private
  marker. Decide during Phase 2. Blocking: no. Blocks: Phase 2.
- UNK-04: whether a zero-frame PASSIVE checkpoint over a non-empty WAL is a failure
  or an acceptable no-op. The measured `(busy=1, log=13, checkpointed=0)` row is a
  contended database; a `(0, 0, 0)` row is a clean one. REQ-005 currently requires
  recording only the first. If instead the shutdown path should retry the PASSIVE
  attempt when a reader is holding the database, that is a behavior change to
  `wal_checkpoint_manager.py:65-79` and needs its own decision. A related decision
  is recorded here rather than as its own unknown: if a checkpoint is cancelled
  mid-retry, should the backup step still run? Running it after an abandoned
  checkpoint is safe but expensive, and skipping it is what today's
  `truncated_or_ok` short-circuit does for a *reported* failure
  (`resource_shutdown_coordinator.py:81-83`); UNK-01 and this unknown both change
  what that branch means, so it is decided together with them. Decide before
  Phase 1. Blocking: no. Blocks: Phase 1.

## Design

**Components and data ownership**
- `WalCheckpointManager` owns *how* a checkpoint or backup is performed, including
  where the blocking work runs and what counts as a meaningful outcome. It owns no
  timeout value after Phase 3.
- `ResourceShutdownCoordinator` owns *whether* a step is allowed to continue and
  owns the only bound. It already holds `self._view` (`:43`, `:57`) and builds the
  `errors` list it summarizes at `:149-151`.
- `SQLiteHelper` owns connection construction and pragmas; nothing about this Plan
  changes it. It is the reason the whole step body must move to one thread.
- The local `errors: list[tuple[str, str]]` (`:67`) stays the only accumulator;
  REQ-007 is a delivery change (`self._view`), not a new sink or a new class.

**Timeout boundary (the decision this Plan exists to make)**
Three values exist; after this Plan one remains and it is the one the `wait_for`
calls read. The relationship that matters is between that value and
`busy_timeout`: with `busy_timeout=30000` and a bound of 5 s or 10 s, the bound
fires *because* SQLite is still waiting, and the checkpoint is abandoned while it
is making progress. With a bound above the busy timeout, the busy timeout is what
ends the wait and the bound only catches work that never finishes. UNK-01 is the
choice between those two designs; the Plan's phases do not depend on the number,
only Phase 3's single-source step does.

**Why the existing tests pass**
`AsyncMock`'s `await` yields to the loop, so `wait_for` can time it out.
Production's `checkpoint_sync` never yields. `asyncio.TimeoutError` being the
builtin `TimeoutError` (since 3.11) is what lets a stub reach the branch by
raising directly. That is the whole mechanism behind
`tests/agent/test_repl.py:928-955` and the four coordinator tests, and it is why
AC-1 demands evidence from the real body.

**Verification surface**
A test is a regression test for this defect only if it fails when the `time.sleep`
backoff or the zero-frame recording is removed while the stubs stay in place — that
is what forces it through the real body. The Phase 1 test must observe the loop
being free during a blocking step; the Phase 2 test must observe the counts being
read.

## Risks

- Abandoning a checkpoint mid-write leaves a partially checkpointed WAL. That is
  safe for SQLite (the WAL is replayed or checkpointed on the next open) but it
  means "timed out" is not "rolled back", and a reader of the logs must not be led
  to think the database was left clean. Mitigation: REQ-007's wording, and AC-7's
  docstring statement.
- `asyncio.to_thread` uses the shared default executor whose threads are joined at
  interpreter exit (measured: 6.0 s total wall time from a 3.0 s abandoned step), so
  the *await* would be bounded while the *process* is not. UNK-02 decides the shape;
  the daemon-thread route introduces the first worker thread in this module (it has no
  `threading` code today) and would follow `signal_handler.py`'s existing
  `loop.call_soon_threadsafe` pattern (`:75`, `:102`). No lint rule retires either way:
  `pyproject.toml:96-99` selects no `ASYNC` rule.
- Worker threads are not cancellable, so Phase 1 makes the bound enforceable from
  the awaiting side only. A worker that never finishes can still hold a SQLite
  connection open after the loop moves on. Mitigation: the step body's `try/finally`
  keeps `close()` on the worker, so the connection is released by the worker itself.
- Adding an unstubbed real-database test to `tests/agent/` risks slow tests and
  file-handle leaks. Mitigation: `tmp_path`, `@pytest.mark.integration` for the
  end-to-end variant, and `uv run pytest tests/ -q --durations=10` as a check.
- `check_plan_target_overlaps.py` reports this Plan against `repl001`, `repl002` and
  `repl003` on `tests/agent/test_repl.py`, and against `repl003` on
  `skills/python-test-and-fix/SKILL.md`. The Notes section declares both
  intentional, region-disjoint, and ordered. The opposite risk is the one the checker
  cannot see: the shutdown coordinator files are named "unchanged" by `repl001` and
  "changed" here, which produces no finding but is a real ordering constraint
  (Notes).
