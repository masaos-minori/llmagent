## Background
`tests/agent/test_session_message_repo.py` defines a module-level `repo` fixture (lines 74-84) that creates an in-memory SQLite DB, runs the schema, inserts a `sessions` row (`session_id=1`), patches `SQLiteHelper` to route to that DB, and yields `SessionMessageRepository(session_id=1)` — exactly the setup `test_default_roles_fallback` needs. `TestCustomRoles`'s 3 tests instead directly construct their own `SessionMessageRepository(...)` (to pass custom constructor kwargs like `roles_source=custom`/`strict_mode=True` the shared fixture doesn't parameterize), bypassing both the DB patching and the `sessions` row insert. This is harmless for the other 2 tests (they call `.save()` with an invalid role, which `session_message_repo.py`'s `save()` rejects and returns from *before* reaching the database `INSERT`), but `test_default_roles_fallback` calls `repo.save("user", "content")` with a *valid* role, reaching the real `INSERT INTO messages (session_id, ...) VALUES (1, ...)` against a `session_id` that was never created — violating the `messages.session_id -> sessions.id` foreign key.

## Problem
`sqlite3.IntegrityError: FOREIGN KEY constraint failed` at `scripts/agent/session_message_repo.py:84`'s `db.execute(_INSERT_MESSAGE_SQL, (self.session_id, role, norm_content, tc_json, tool_call_id))`, with `params = (1, 'user', 'content', None, None)` — confirmed via Read that no `sessions` row exists for this test's own directly-constructed `SessionMessageRepository(session_id=1)`, unlike the shared `repo` fixture other test classes use.

## Reason for change
This is confirmed test-fixture staleness/inconsistency: `test_default_roles_fallback` needs the same DB-backed setup its sibling test classes already get via the `repo` fixture, but doesn't use it, since it was likely copy-adapted from `test_custom_roles_injection`/`test_strict_mode_with_custom_roles` (whose direct-construction pattern happens to work only because they never reach the database).

## Implementation intent
Add the `repo: SessionMessageRepository` fixture parameter to `test_default_roles_fallback` and use it directly, since it needs no custom constructor kwargs beyond `session_id=1` (which the fixture already provides). Do not change `TestCustomRoles`'s other 2 tests, which correctly don't need database access for their invalid-role-rejection scenarios.
