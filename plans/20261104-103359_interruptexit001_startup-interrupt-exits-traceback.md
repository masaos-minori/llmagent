## Goal
- End a process whose startup was interrupted by a shutdown request (SIGTERM or SIGINT) quietly with exit status 0 and no traceback, through one entry function shared by `python -m agent` and the compiled binary, while a genuine startup failure keeps its non-zero exit and visible fatal message.

## Background
A signal sets the shutdown event, a startup step raises `StartupInterrupted`, and `AgentREPL.run` prints a non-fatal warning, runs its `finally` cleanup, and re-raises. `StartupInterrupted` is a `BaseException` (deliberately, so broad startup handlers do not swallow it). Neither `repl.main` nor `__main__` catches it, so `asyncio.run` propagates it, the interpreter prints a traceback, and the exit status is 1 (checked in Step 2; the interpreter behavior is the Issue's own throwaway verification, not re-run here).

## Problem
Service managers and init scripts treat a non-zero exit status as a failed run, and the traceback is indistinguishable from a real crash. A requested shutdown during startup is a normal operation.

Verification corrections and findings:
1. The compiled binary's launcher, generated by `deploy/build_binaries.sh`, is `from agent.repl import main` followed by `main()`; the return value is discarded and no `sys.exit(main())` wrapper exists. An exit status could therefore only come from `main()` raising `SystemExit` itself. Because the owner chose status 0, `main()` returning normally is sufficient for both `python -m agent` and the binary, and no launcher change is needed (this answers the Issue's second unresolved question).
2. `deploy/start_agent.sh` starts the binary directly as its last command, so the process status is the binary's status; no wrapper rewrites it (read in Step 3).
3. No document lists agent exit statuses (a search of `docs/` for exit status and exit code terms found none about the agent); the only startup-interrupt text is one section of the startup and health document, which does not state the process outcome.
4. `pyproject.toml` omits `scripts/agent/repl.py` from coverage with the comment "no unit tests by design", but `tests/agent/test_repl.py` has tests for it; the new test is added there and the omission is not changed (out of scope).
5. `SignalHandler` does not record which signal arrived, which is why a 128-plus-signal status would widen the scope.

## Reason for Change
A normal service stop during startup must not look like a crash in logs or in the service manager.

## Implementation Intent
Handle the exception in the single process entry function, after `AgentREPL.run` has already warned and cleaned up, and let the process end by returning normally. `__main__` imports and calls that function.

## Design
Decision 1, where to handle the exception. Alternatives: (a) inside `AgentREPL.run`; (b) a new entry module or function; (c) in `repl.main`, with `__main__` calling it. Chosen: (c). (a) would break the contract that `run()` re-raises and that cleanup precedes the exception leaving it; (b) adds a module for a three-line function. Compatibility: `main` keeps its name and signature, which the generated launcher imports.

Decision 2, how the status is produced. The owner chose 0, so `main()` returns normally; no `SystemExit` is raised. A genuine failure keeps propagating, which keeps the traceback and status 1 that signal a real crash.

Decision 3, deployment effect. The agent runs as a compiled binary built from `main`, so the behavior reaches production only after the binary is rebuilt and deployed; the deploy hand-off names that.

No persisted schema, public API, or shared constant is changed.
