## Goal
- Wire the `x-idempotency-key` header extracted by `extract_request_context()` through all ten MCP server route handlers to `dispatch_tool()`, enabling end-to-end duplicate detection for side-effecting tool calls.

## Priority
Medium

## Scope
- **In-Scope**:
  - Fix the three-value unpack bug in six handlers using `extract_request_context()` (capture the third return value as `idempotency_key` instead of discarding it).
  - Add `request: Request` parameter to the `call_tool` function signature in four handlers that don't currently have it, then add `extract_request_context()` import/call and propagate the key.
  - Update `_dispatch_*_tool()` helper signatures across all ten files to accept an optional `idempotency_key: str | None` parameter and forward it to `dispatch_tool()`.
- **Out-of-Scope**:
  - Modifying `dispatch.py`'s duplicate-detection logic itself (only wiring changes).
  - Adding the `x-idempotency-key` header to outgoing HTTP requests.
  - Adding idempotency support to non-side-effecting tool calls beyond what `dispatch.py` already handles via `_is_side_effecting()`.
  - Changing audit logging semantics or FastAPI route registration/response model contracts.

## Background
REQ-003/REQ-004 added an opt-in duplicate-check mechanism to `scripts/mcp_servers/dispatch.py`'s `dispatch_tool()` and extended `scripts/mcp_servers/server.py`'s `extract_request_context()` to extract a new `idempotency_key` field. However, REQ-003 deliberately left wiring that header into each MCP server route-handler out of scope. The source Issue's Acceptance Criterion ("a retried side-effecting Tool Call... does not execute the underlying operation twice") remains only partially satisfied by the core-mechanism Plan alone. This follow-up completes the wiring gap.

## Problem
Without this follow-up, the idempotency-key mechanism ships but is inert: every one of the ten MCP server route handlers keeps calling `dispatch_tool()` with no `idempotency_key`, so the duplicate-check added by REQ-003 never actually fires for any live server, and a retried side-effecting Tool Call (file write, git operation, external API call) can still execute twice in production.

## Reason for change
The idempotency guard is a correctness feature for side-effecting operations. Without propagation to all handlers, retry safety is broken and data integrity risks remain unaddressed.

## Implementation intent
For each of the ten MCP server route-handler files:
1. Confirm whether the handler already calls `extract_request_context()` and how it uses the returned tuple.
2. For handlers that call `extract_request_context()` (Group A: 6 files): ensure the third return value (idempotency_key) is captured and passed to `dispatch_tool()`. Currently, six files call this helper but discard the third value:
    - `shell/shell_server.py:155`: `request_id, session_id, request_id = extract_request_context(request)` — third value overwrites `request_id`
    - `git/git_server.py:185`: same pattern (note: no `_dispatch_git_tool` wrapper exists; idempotency_key must be passed directly to `dispatch_tool()`)
    - `mdq/mdq_server.py:81,343`: `request_id, session_id, _ = extract_request_context(request)` — discarded via `_`
    - `web_search/web_search_server.py:221`: same as shell/git (note: must verify `dispatch_web_tool` accepts `idempotency_key` parameter first)
    - `cicd/cicd_server.py:119`: same as shell/git
    - `github/github_server.py:174`: same as shell/git
3. For handlers that do NOT call `extract_request_context()` (Group B: 4 files): additionally add `request: Request` parameter to the `call_tool` function signature (currently missing), then add the shared extraction call, capture the idempotency_key, and pass it to `dispatch_tool()`:
   - `file/read_server.py:279`: `async def call_tool(req: CallToolRequest)` — no `request` param
   - `file/delete_server.py:143`: same
   - `file/write_server.py:183`: same
   - `rag_pipeline/rag_pipeline_server.py:191`: same
4. Update the `_dispatch_*_tool()` helper signatures to accept an optional `idempotency_key: str | None` parameter and forward it to `dispatch_tool()`.

## Design
Classified **Path B**: affects more than 3 files (11 target files including dispatch.py) and changes runtime-facing interface (the `dispatch_tool()` call contract across all MCP servers). Full architecture/dependency/historical analysis performed.

**Group A vs. Group B distinction**: The core design decision is recognizing two distinct patterns among the ten handlers:
- Group A (6 files): Already call `extract_request_context()` which returns `(session_id, request_id, idempotency_key)`, but discard the third value. Fix: capture the third value and pass it through.
- Group B (4 files): Don't call `extract_request_context()` at all AND lack the `request: Request` parameter in their `call_tool` function signatures. Fix: add the parameter, import/call `extract_request_context()`, capture the key, and pass it through.

**Backward compatibility**: The `_dispatch_*_tool()` helper signatures gain an optional `idempotency_key: str | None = None` parameter with a default of `None`. This is backward-compatible because:
1. Existing callers within the same file already pass positional arguments `(name, args)` — adding an optional trailing parameter does not break them.
2. `dispatch_tool()` already has `idempotency_key: str | None = None` as an optional parameter (REQ-003).
3. When `idempotency_key` is `None`, `dispatch.py:116` skips duplicate detection entirely — no behavioral change for current callers.
4. `git_server.py` has no `_dispatch_git_tool` wrapper; the direct `dispatch_tool()` call change is still backward-compatible (optional parameter), but requires separate handling.
5. `web_search_server.py`: adding `idempotency_key` to `_dispatch_web_tool` call requires `dispatch_web_tool` to also accept it — verify before applying.

**Validation quality baseline**:
- `radon cc` on modified files: all grade A except pre-existing complexity in `shell_server.py`'s `_execute_with_dag` (pre-existing, out of scope).
- `vulture --min-confidence 80`: no new findings expected (only minor variable additions).
- `bandit`: no new findings expected (no secret exposure or unsafe operations introduced).

## Risks
- **Risk**: Adding `request: Request` parameter to Group B handlers' `call_tool` functions may interact with FastAPI's dependency injection in unexpected ways if other middleware depends on the absence of this parameter → **Mitigation**: FastAPI explicitly supports injecting `Request` objects into route handler parameters (see FastAPI docs); this is the standard pattern used by Group A handlers and is safe.
- **Risk**: The `_mdq_error_handler` exception callback at `mdq/mdq_server.py:76` also calls `extract_request_context()` but is not a route handler — it may not receive the `request` object in the same way → **Mitigation**: confirmed during implementation that the error handler receives `request: Request` from FastAPI's exception handler mechanism (same as route handlers). If this turns out not to be the case, the error handler is excluded from REQ-001 wiring.
- **Risk**: An in-process, non-persistent duplicate-check cache (`dispatch_tool()`) loses its dedup history on a server-process restart → **Mitigation**: accepted for this increment (Assumptions above); no Acceptance Criterion requires crash-durability; a DB-backed cache can be added later if operational data shows crash-induced duplicate side effects.
