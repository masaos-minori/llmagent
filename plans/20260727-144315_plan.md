## Goal

In `HttpServerLifecycleManager.start()`, when `os.getpgid(proc.pid)` raises `OSError`, terminate (and, if needed, kill) the spawned subprocess before dropping its tracking entries, so a live process can never be silently orphaned outside `_http_procs`/`_http_pgids`.

## Assumptions

1. `_terminate_with_timeout(proc, server_key, timeout=3.0)` (lines 111-146) is safe to call directly in the `except OSError:` branch: it reads `self._http_pgids.get(server_key)`, and since the failing line is the very assignment `self._http_pgids[server_key] = os.getpgid(proc.pid)`, `server_key` is guaranteed to be absent from `_http_pgids` at this point — so the method's `pgid is None` branch (plain `proc.terminate()` / `proc.kill()`) executes, which is exactly the behavior the requirement asks for. Reusing this helper avoids duplicating the terminate/escalate logic inline. Falsifiable: if any future code path populates `_http_pgids[server_key]` before this line moves, this assumption breaks.
2. A default timeout of 3.0s (the existing default of `_terminate_with_timeout`) is an acceptable bound for this branch; the requirement does not specify a different value and no caller currently threads a custom timeout through `start()`.
3. `self._http_procs[server_key] = proc` (line 256) is only reached on the non-exception path, i.e. `_http_procs` never contains `server_key` while this except-branch runs — confirmed by reading the surrounding code — so no extra pop-guard is needed there beyond what already exists.
4. The requirement's "before popping" ordering only requires termination to happen before the four `.pop()` calls in this branch; it does not require blocking `start()`'s return beyond the existing bounded timeout.

## Risks

- **Risk**: Calling `await self._terminate_with_timeout(proc, server_key)` inside the `except OSError:` branch adds a bounded (up to ~2x3s = 6s worst case with kill escalation) delay to `start()`'s failure path in the rare case `getpgid()` fails. → **Mitigation**: This delay only occurs in an already-exceptional, rare branch (getpgid failing is not the common case); it is strictly bounded by the same 3.0s/3.0s terminate/kill timeout pattern already used elsewhere in this file (`restart()`, `shutdown_all()`), so no unbounded-hang risk is introduced. No change needed beyond what's planned.
- **Risk**: The existing test's `mock_proc` (a `MagicMock`) with a fixed `poll.return_value` would make the updated code path spin for the real 3-second timeout in `_wait_exited`, slowing or hanging the test suite. → **Mitigation**: Implementation step explicitly requires switching to the `side_effect=lambda: 0 if mock_proc.terminate.called else None` pattern already proven in `TestProcessGroupShutdown` (`tests/test_lifecycle.py:791`), which reports exit immediately after `terminate()` fires — no waiting.
- **Risk**: This is a high-churn file (26 commits total, 15 in the last 30 days per `git log`) — a concurrent unrelated change to `start()` could conflict with this fix during implementation. → **Mitigation**: Keep the diff minimal and isolated to the exact `except OSError:` branch as instructed; do not refactor surrounding code, reducing merge-conflict surface.
- **Risk**: Reusing `_terminate_with_timeout()` relies on the invariant that `_http_pgids[server_key]` is never set before this branch runs; if a future refactor moves the `os.getpgid()` call or changes assignment order, the reused helper could silently pick up a stale/wrong pgid. → **Mitigation**: Add a code comment at the call site in `start()` noting this invariant explicitly, so future changes to the ordering are flagged for a reviewer; no test currently guards this invariant directly, but `test_getpgid_failure_cleans_up_resources` will fail loudly (asserts `server_key not in _http_pgids`) if the ordering assumption is violated.
