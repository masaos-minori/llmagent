## Background
A repository-wide grep across `docs/*.md` and `docs/adr/*.md` (174 files as of this
Plan's creation — see Assumptions for the count drift from the source Issue's 178)
found: `area:` front matter present in 128 files; `category:` present in 4 files
(same value vocabulary as `area:` — `overview`, `mcp` — confirming a naming
inconsistency, not a distinct field); both present in 0 files; neither present in 42
files. `tools/check_docs_structure.py`'s `check_front_matter()` hardcodes the
required-field tuple as `("title", "area", "tags", "related")` (line 67) —
`category` is referenced nowhere in `tools/`. `tools/manage_frontmatter.py`'s
`add-missing` logic (`extract_area_from_filename()`, `has_area`) only ever
writes/checks `area:`, with no knowledge of `category`. `keywords:` as a
front-matter key appears in exactly one file — the governance document's own
illustrative Front Matter Example block (`docs/00_governance_02_documentation-metadata.md:124`)
— zero real documents use it that way; every real document instead uses a
`## Keywords` body-section heading, which is what `check_docs_structure.py` actually
checks (`re.search(r"^## Keywords", ...)`). The seven other "Recommended Additional
Fields" (`scope`, `audience`, `status`, `priority`, `version`, `last_updated`,
`author`, `completeness`) all show zero real-document adoption outside that same
illustrative block. Current `area:` value distribution: `agent`(33), `rag`(31),
`mcp`(25), `adr`(11), `overview`(8), `eventbus`(7), `shared`(6), `governance`(5),
`security`(2), `deployment`(1) — `adr` and `security` are not part of the document's
stated 8-value enum, and the enum spells the shared-DB area `shared-db` while every
real file uses `shared`. A related, already-closed issue
(`issues/done/20260802-072818_governance_06_metadata_fields_usage_unverified.md`)
raised the same underlying question against a since-renumbered/merged predecessor
document that no longer exists, without the requested usage-reality statement ever
landing in the successor document.

## Problem
Three sources disagree on the canonical category-style field
(`docs/00_governance_02_documentation-metadata.md` documents `category`, its own
Front Matter Example and actual front matter use `area`, and all enforcement tooling
recognizes only `area`); `keywords` is documented as a front-matter key but
implemented everywhere as a body section; and seven "Recommended Additional Fields"
carry zero real-world adoption, producing maintenance noise and false signals for
anyone using the governance document as an authoring checklist.

## Reason for change
Document search, structural validation, and AI-agent doc routing all need one
authoritative field set to validate against. As long as the governance document and
the tooling diverge, the two dependent follow-on efforts (bulk migration, CI
enforcement) have no single source of truth to implement against.

## Implementation intent
Treat `area` as the canonical field — it is what the tooling already enforces and
what the large majority of documents already use — and correct the governance
document and its illustrative examples to match, rather than migrating the ecosystem
onto the unused `category`/`scope` names. Remove documentation for
zero-adoption fields instead of leaving aspirational guidance nothing implements.
Author `schemas/doc_front_matter.json` (following the repository's existing JSON
Schema convention — see `schemas/event_envelope.json` — draft-07,
`additionalProperties`, a `required` array) expressing exactly the finalized field
set; do not wire it into any validation path, since programmatic enforcement is
`docmeta03`'s explicit responsibility, not this Plan's. Register the three open
questions this finalization surfaces as new Needs Confirmation entries rather than
resolving them.
