## Goal
- Fix the six `tests/agent/test_startup.py` fixtures (`TestStartupMemoryFailures::test_memory_injection_categorized_logging` x3 parametrizations, `TestStartupOrchestratorSetupPrompt` x3) that fail with `TypeError: object MagicMock can't be used in 'await' expression` when `StartupOrchestrator._setup_prompt()` awaits `ctx.conv.replace_history(...)`, by giving each fixture an `ctx.conv` object whose `replace_history()` is genuinely awaitable.

## Problem
(Evidence: Verified by test — reproduced by running `uv run pytest tests/agent/test_startup.py -k "TestStartupMemoryFailures or TestStartupOrchestratorSetupPrompt" -q`)

All six tests currently fail identically:
```
tests/agent/test_startup.py:1534 (and :561, :576, :612): await startup._setup_prompt()
scripts/agent/startup.py:670: await ctx.conv.replace_history([{"role": "system", "content": initial_prompt}])
TypeError: object MagicMock can't be used in 'await' expression
```
Confirmed by direct execution: the reproduced traceback (test/exception identity and call chain) and the exact failing-test list match the Issue's claims (`Confirmed by repository evidence`). Full-file baseline: `uv run pytest tests/agent/test_startup.py -q` -> `6 failed, 66 passed` (72 collected), matching the Issue's implicit claim that only these six tests are affected.

Root cause (`Confirmed by repository evidence`): in each of the six failing tests, `ctx = MagicMock()` and `ctx.conv` is never reassigned to a concrete object — `ctx.conv` therefore remains an auto-generated `MagicMock` attribute, so `ctx.conv.replace_history` is a synchronous `MagicMock` callable rather than an awaitable. `ConversationState.replace_history()` (`scripts/agent/context.py`) is declared `async def` and is genuinely awaited inside `StartupOrchestrator._setup_prompt()` (`scripts/agent/startup.py`). Two sibling tests in the same class, `test_no_pinned_notes_block_injected` and `test_history_set_to_system_message`, already pass because they explicitly set `ctx.conv = ConversationState()` (a real dataclass instance, not a mock) before invoking `_setup_prompt()` — this is the existing in-file pattern the fix should reuse.

## Reason for change
A failing test suite for memory-injection/prompt-setup behavior (categorized logging on memory-load failure, snippet truncation, enable/disable behavior) means regressions in this area would go undetected. The fixture is out of sync with `replace_history()`'s genuinely async interface.

## Implementation intent
For each of the six affected tests, assign `ctx.conv = ConversationState()` (already imported at module level in `tests/agent/test_startup.py`) immediately after `ctx = MagicMock()`, before any `ctx.conv.<attr> = ...` assignment — mirroring the pattern already used by `test_no_pinned_notes_block_injected` and `test_history_set_to_system_message` in the same file. This makes `ctx.conv.replace_history()` resolve to the real async `ConversationState.replace_history()` coroutine, and additionally makes the state-based assertions (`ctx.conv.history`, `ctx.conv.system_prompt_content`, `ctx.conv.memory_disabled`) reflect actual `ConversationState` mutation logic rather than arbitrary `MagicMock` attribute writes. Do not construct a partial async mock (e.g. an `AsyncMock`-only patch of `replace_history`) — reusing the real `ConversationState` is the lower-risk, already-precedented approach and requires no new import.

## Design
No architectural or interface change. The design decision is which mocking strategy to use for `ctx.conv` in the six affected fixtures: reuse the real `ConversationState()` dataclass (already imported and already the precedented pattern used by `test_no_pinned_notes_block_injected`/`test_history_set_to_system_message` in the same file) rather than introduce a new partial-mock strategy (e.g. `AsyncMock(spec=ConversationState)` or patching only `replace_history`). This is lower-risk because (a) it requires no new import, (b) it is already proven to work for two sibling tests in the same class, and (c) it makes the assertions exercise real `ConversationState` state-mutation logic (`append_message`/`_append_message_locked` validation, history replacement) instead of arbitrary mock-attribute writes, which is a strictly more faithful test of `_setup_prompt()`'s actual contract.

## Risks
- **Risk**: Reusing `ConversationState()` could expose a latent validation-rejection path inside `ConversationState.append_message`/`_append_message_locked` (e.g. the system message dict being sanitized or dropped) that a plain `MagicMock` silently tolerated, causing a new, different assertion failure rather than the original `TypeError`. → **Mitigation**: Run the targeted test selection (`T-1`) immediately after the edit and inspect any new failure; the two already-passing sibling tests (`test_no_pinned_notes_block_injected`, `test_history_set_to_system_message`) using the identical `ConversationState()` + system-message pattern demonstrate this path is safe for a `{"role": "system", "content": ...}` message, which is exactly what all six fixtures pass through `_setup_prompt()`.
- **Risk**: A shared `pytest` fixture change intended for six tests could accidentally affect an unrelated test if `ctx` were built by a shared helper instead of inline per-test code. → **Mitigation**: `Confirmed by repository evidence` (Step 3 inspection) that each of the six tests builds `ctx = MagicMock()` inline with no shared fixture function; the edit is scoped to exactly those six test bodies.
