## Goal
- Stop `tools/stale_detector.py` from reporting prose and to-be-created names as stale references, by (a) recognizing an import citation only when a line begins with a full import statement and (b) letting a procedure mark a symbol or import it will create with `` `name` (new) ``, while every genuinely stale reference is still reported.

## Priority
Medium

## Scope
- **In-Scope**:
  - Anchor `_IMPORT_RE` to line-leading import statements (optionally behind a list marker and one backtick) so a sentence containing "from X import ..." is no longer captured.
  - Exempt a backticked symbol or import immediately followed by `(new)` from the existence check.
  - Regression tests for both false-positive classes, plus tests that the true positives are unchanged.
  - Document the `(new)` convention in `templates/implementation-procedure.md`, in `skills/code-implementation/workflow.md` Step 3, and in the `tools/TOOL_DESCRIPTIONS.md` entry.
- **Out-of-Scope**:
  - Making import detection consistent for line-leading imports that are not followed by a heading, a comment, or the end of the text (see `UNK-02`).
  - Changing the abort-on-any-mismatch policy or the rule against correcting a procedure and continuing.
  - The `.claude/worktrees/` copy of the tool, archived procedures under `implementations/done/`, and any other detector heuristic that already passes.

## Background
- `skills/code-implementation/workflow.md` Step 3 aborts a procedure on any `tools/stale_detector.py` mismatch. In the mock001 batch, 2 of 9 procedures were reported stale with source unchanged, and the cycle could proceed only after the user approved rewording the procedures.
- Issue `issues/20261012-132457_stale001_fix-stale-detector-false-positives.md` names two false-positive classes (prose matched as an import; a symbol the procedure creates matched as missing) and leaves the marker convention open.

## Problem
Verified against current source and by running the detector (`Confirmed by repository evidence`):
- **Prose import (confirmed)**: `_IMPORT_RE` (`tools/stale_detector.py:43`) is `from\s+(\S+)\s+import\s+(.+?)(?:\s*$|\s+#)` with no `MULTILINE` flag and no line anchor. The terminator `\s+#` spans newlines, so a prose line containing "from X import ..." that is followed by a blank line and a heading is captured and reported. Experiment: the line "- Keep `from __future__ import annotations` style; no CLI option." followed by a heading is reported `import_missing`; the same line followed by plain text is not.
- **New symbol (confirmed)**: `_check_symbol_refs` (line 448) checks every backticked snake_case or CamelCase token against the repository; a name the procedure itself introduces cannot exist yet, so it is reported `symbol_missing`.
- **Correction to the Issue (new finding)**: import detection is also position-dependent in the other direction. A real line-leading import citation that is missing from source is reported only when the next non-blank text is a heading or comment; followed by ordinary text, or inside a fenced block followed by text, it is not reported (experiment, all five cases). Making detection consistent would flag a large number of procedures: 940 of 6024 archived procedures contain a line-leading import citation, most of them imports the procedure adds. This plan therefore removes the false positives without widening what is reported (`UNK-02`).
- **Convention evidence resolving the Issue's open question**: `` `path` (new) `` already appears 204 times in archived plans and procedures to mark new files, so the same marker can mark new symbols and imports without introducing a new syntax.

## Reason for change
- A gate that raises false alarms on a routine kind of procedure (adding a test or function) is bypassed or reworded around, which weakens it for the real case it exists for.
- The cause is mechanical (an unanchored regex; no notion of "to be created"), so a small, testable change removes both classes.

## Implementation intent
- Narrow, do not broaden: after the change the detector reports a subset of what it reported before, minus the false positives, plus nothing new.
- Anchor the import pattern to the start of a line (after an optional list marker and one optional backtick) and to a statement that is the whole line content, keeping the existing terminator semantics so true-positive coverage is unchanged.
- Treat `(new)` immediately after a backticked symbol or import statement as a declaration that the construct will be created; skip the existence check for it. Undeclared names absent from the repository are still reported.
- Keep the detector regex-based and dependency-free; report all findings in one pass.

## Requirements
- `REQ-001`: A sentence containing "from X import ..." must not be reported as a missing import; a line that begins with a full import statement that is missing from source is still reported as before.
- `REQ-002`: A backticked symbol or import statement immediately followed by `(new)` is exempt from the existence check; the same name without the marker, absent from the repository, is still reported.
- `REQ-003`: Regression tests cover both false-positive classes using the verbatim text from the mock001 procedures, and the unchanged true positives (removed existing symbol, out-of-range line, missing import statement, missing "Before:" block).
- `REQ-004`: The `(new)` convention is documented where procedures are authored and consumed: the procedure template notes, `code-implementation` Step 3, and the tool's `TOOL_DESCRIPTIONS.md` entry.
- `REQ-005`: The 60 existing detector tests pass unchanged; the new tests, ruff, mypy, and the tool-description sync check pass; detector verdicts on current procedures do not regress.

## Assumptions

## Design
- Path B (5 target files). Architecture analysis: `tools/stale_detector.py` imports only the standard library; `lint-imports` covers `scripts/`, which this plan does not touch. Dependency graph: the detector is referenced by `tests/tools/test_stale_detector.py`, `tools/TOOL_DESCRIPTIONS.md`, and the `code-implementation` workflow text; no hook or CI job runs it, and the only other copy is under `.claude/worktrees/` (out of scope). Historical analysis: moderate recent churn on the detector, its test, and `code-implementation/workflow.md`; the template is quiet. Operational dependencies: none (`lsof` and `pip-audit` not applicable).
- Import pattern (prototyped on seven sample texts): `(?i)(?:^|\n)[ \t]*(?:[-*][ \t]+|\d+\.[ \t]+)?`?from\s+(\S+)\s+import\s+(.+?)`?([ \t]*\(new\))?(?:\s*$|\s+#)`. It anchors to the start of a line, strips the closing backtick of a backtick-wrapped statement (the old pattern left it in `names`, so a wrapped import that exists in source was compared with a trailing backtick), and captures an optional `(new)` as a third group. Line-leading matches are identical to the old pattern's; only mid-sentence matches disappear. `_check_import_refs` is updated to read the third group and skip a `(new)` import.
- New-marker: a small helper that returns true when the text right after a match (one optional space) starts with `(new)`; used by `_check_symbol_refs` (after the match end of the backticked token) and `_check_import_refs`. Extracting the helper keeps `_check_symbol_refs` (already complexity C, 16) from growing.
- Validation quality baseline (`tools/stale_detector.py`): radon grade C for `_check_symbol_refs` (16) and `_check_before_blocks` (14); vulture and bandit report nothing; the 60 existing detector tests pass before any change.

## Risks
- **Risk**: The anchored pattern drops a real citation that was written mid-sentence and used to be reported → **Mitigation**: such matches only fired when a heading followed them, so coverage was already accidental; recorded in Assumptions and covered by a test that documents the new behavior.
- **Risk**: `(new)` is used to hide a reference that is actually stale → **Mitigation**: the marker exempts only the existence check for that exact token; line references and "Before:" blocks are unaffected, and an unmarked absent name is still reported.
- **Risk**: Authors of earlier procedures did not write `(new)` and still get flagged → **Mitigation**: no regression (behavior is unchanged for them); the template note tells new procedures to mark creations, and generated procedures pick it up through the template.
- **Risk**: Widening import detection by mistake aborts many correct procedures (`UNK-02`) → **Mitigation**: keep the old terminator; a test asserts that a line-leading import followed by ordinary text is still not reported, so any accidental widening fails.
