## Goal
- Split `scripts/agent/services/config_reload.py` into four focused modules (field registry, section reload, service sync, outcome classification) while preserving `ConfigReloadService`'s public API (`apply_config()`, `apply_config_dict()`, `ConfigReloadOutcome`) unchanged, reducing `apply_config_dict()`'s size/complexity and enabling standalone unit tests for the previously entangled helpers.

Medium

## Background
`config_reload.py` was consolidated from `_ConfigMixin._apply_*` helpers during a prior `/reload` command refactor into a single `ConfigReloadService.apply_config_dict()` entry point. The file (confirmed 481 lines) now mixes schema definition (`CONFIG_FIELD_REGISTRY`), section-reload control flow, service-instance sync, and outcome classification in one module.

## Problem
`apply_config_dict()` mixes section iteration, validator invocation, service propagation, and outcome assembly in one method, and the classification helpers (`_classify_mcp_server_changes`, `_classify_startup_only_fields`, `_detect_diagnostics_live_fields`) are bound methods that reach into `self._ctx` (the latter two) or take a whole `ctx` object (the first), preventing isolated unit testing.

## Reason for change
- `apply_config_dict()` measured at cyclomatic complexity C(18) via `radon cc` (Issue claimed ">20"; corrected — see Unknowns/evidence below), still grade C and a maintainability concern.
- `CONFIG_FIELD_REGISTRY` contains 46 entries across 6 sections (llm=14, rag=6, tool=10, approval=10, memory=4, mcp=2), confirmed by direct count against the source (Issue claimed 48 — corrected).
- No unit tests exercise `_diff_mcp_server_config`, `_detect_diagnostics_live_fields`, or `_classify_startup_only_fields` independently of the full `ConfigReloadService`.
- Validator imports are spread across `config_validators.py` (defines), `config_dataclasses.py` (imports as `_v_*`), and `config_reload.py` (re-imports by full name) — confirmed by reading `config_reload.py`'s import block.

## Implementation intent
Extract four concerns into new modules under `scripts/agent/services/`, leaving `ConfigReloadService` as a thin orchestrator that still owns `self._ctx` (a fully stateless service is not achievable without changing the frozen public constructor signature, which the Issue's Constraints prohibit). Each new module's functions accept only the specific values they need (e.g. `ctx.cfg.llm`, not `ctx`) rather than an entire context object, going one step further than the current `_classify_mcp_server_changes()` (which already avoids `self._ctx` but still takes the whole `ctx`).

## Design
`ConfigReloadService` keeps `self._ctx` and becomes a thin orchestrator: `apply_config_dict()` calls `reload_validated_section()`/`reload_direct_fields()` per section, then `ServiceSyncer` for live-instance propagation, then the three classification functions for the outcome report — mirroring the current method's existing call order (L223-288) without changing behavior. The two distinct section-reload algorithms (`dataclasses.replace()` + validator for llm/rag/tool vs. direct `setattr` for approval/memory/mcp) stay as two named functions in one file (`config_section_reload.py`) rather than being merged or split further by domain, matching the Issue's own resolved Unresolved Questions. `_build_mcp_servers`'s move to a module-level import in the new classification module is safe because `shared/mcp_config.py` has zero `agent.*` imports (confirmed via `rg "^from|^import"` and a direct interpreter import test) — the historical "avoids circular import at module level" comment on the current lazy import no longer reflects a real constraint.
