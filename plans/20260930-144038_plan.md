## Background
`scripts/agent/http_lifecycle.py` refactored `HttpServerLifecycleManager` into a composition facade that delegates concern-specific work to six modules (`CommandValidator`, `StderrLogManager`, `ProcessTerminator`, `HealthChecker`, `ProcessSnapshotProvider`, `ShutdownCoordinator`). Its module docstring explicitly states it retains "zero pure-delegation wrappers" and keeps custom logic only for `_read_stderr_tail` (seek/read/decode) and `_wait_exited`.

`StderrLogManager` already owns the canonical stderr-log tail logic via `read_tail` (seek-to-end, size comparison against the configured tail bytes, read, `OSError` -> empty). `HttpServerLifecycleManager._read_stderr_tail` re-implements the same algorithm directly against the log path instead of calling the owned method.

## Problem
`_read_stderr_tail` duplicates `StderrLogManager.read_tail`: both seek to end, compute `size - tail_bytes`, read the window, and return empty on `OSError`. The two copies can drift apart, and the duplication contradicts the class's own documented contract ("delegating all concern-specific work ... zero pure-delegation wrappers"). A second artifact, the module constant `_STDERR_TAIL_BYTES`, duplicates `StderrLogManager._DEFAULT_STDERR_TAIL_BYTES` and is used only by the duplicated method.

## Reason for change
- Architecture/reality mismatch: the class claims to delegate all log concerns but keeps one hand-written copy of log-tail logic.
- Maintainability: two sources of truth for the same byte-window algorithm invites divergence.
- Dead constant: `_STDERR_TAIL_BYTES` becomes unused once delegation happens.
- No correctness/security/data-integrity impact today; this is a quality and consistency fix.

## Implementation intent
Make `HttpServerLifecycleManager` read the stderr tail through `StderrLogManager` instead of opening the file itself. The responsibility ("return the last N decoded bytes of the stderr log") moves entirely to the owning module; the manager calls `self._stderr_log_manager.read_tail(server_key)` and decodes the returned `bytes`. Preserve the observable contract of `_read_stderr_tail`: returns "" when the server key is untracked, decodes with `errors="replace"`, and never raises on `OSError`.

Remove the `_read_stderr_tail` wrapper entirely (to honor the "zero pure-delegation wrappers" claim) and inline the single delegation call in its only caller, `_cleanup_server_resources`. Update the three integration-test sites that patched `type(mgr)._read_stderr_tail` so they patch `StderrLogManager.read_tail` instead, returning `bytes` (since the inlined call decodes), without changing the assertions' intent.

## Design
`HttpServerLifecycleManager` is documented as a composition facade with "zero pure-delegation wrappers." Keeping a hand-written seek/read/decode copy of log-tail logic in `_read_stderr_tail` violates that contract and creates a second source of truth for the byte-window algorithm that `StderrLogManager.read_tail` already owns.

Behavior equivalence is preserved because the two implementations are algorithmically identical for every reachable input:
- Untracked key: `_read_stderr_tail` returns "" when `get_log_path` is falsy; `read_tail` returns `b""` when the key is absent from `_log_paths`. Both yield an empty decoded string.
- File size <= tail bytes: `_read_stderr_tail` seeks to `max(0, size - bytes)` == 0 and reads the whole file; `read_tail` explicitly seeks to 0 and reads the whole file. Identical.
- File size > tail bytes: both seek to `size - bytes` and read the remainder. Identical.
- `OSError`: both return empty. Identical.

The only type difference is that `read_tail` returns `bytes` while `_read_stderr_tail` returned `str`; the inlined call decodes with `errors="replace"`, matching the previous decode.

Decision: remove the `_read_stderr_tail` wrapper rather than replace its body with a one-line delegation. Rationale — the Issue prefers honoring the "zero pure-delegation wrappers" claim, and `_read_stderr_tail` has exactly one internal caller (`_cleanup_server_resources`, confirmed via `rg`), so inlining the single delegation into that caller removes the wrapper cleanly. The three integration-test sites that patched `type(mgr)._read_stderr_tail` are retargeted to patch `StderrLogManager.read_tail`, returning `bytes` literals (since the inlined call now decodes).

`_STDERR_TAIL_BYTES` becomes unreferenced once the method body that used it is removed (its only use was within `_read_stderr_tail`); it is deleted. It duplicates `StderrLogManager._DEFAULT_STDERR_TAIL_BYTES` and serves no independent purpose.
