# Work Plan: Enforce Encryption for Diagnostic Data Containing Secrets

## Goal

Ensure that diagnostic data containing sensitive fields is always encrypted before being saved. If encryption is not available, refuse to save the data.

## Scope

- Modify `scripts/agent/repl.py` to enforce encryption for sensitive diagnostic data
- Potentially modify `scripts/agent/diagnostic_store.py` to add encryption enforcement

## Assumptions

1. The current `encryption_key` configuration exists but may not be enforced
2. Adding encryption enforcement won't break existing diagnostic save operations
3. Refusing to save sensitive data without encryption is acceptable behavior

## Resolved Unknowns

1. **Current encryption behavior**: It is currently opt-in via `encryption_key`. An empty string disables it.
2. **Legitimate use cases**: Unencrypted diagnostics are used for non-sensitive runtime events, but sensitive tool outputs require protection.
3. **Impact on deployments**: Mandatory encryption for sensitive data is a breaking change for existing unencrypted logs.

## Design

### Approach: Enforce encryption for sensitive diagnostic data

Implement a mechanism in `DiagnosticStore.save()` to detect sensitive information. 
If sensitive information is detected and no `encryption_key` is provided (opt-in mode), 
the save operation must be refused (raise an error or log a critical failure).

### Implementation Steps

#### Step 1: Define "Sensitive Information" criteria

Establish clear rules for what constitutes sensitive data (e.g., presence of API keys, tool arguments, or specific metadata tags).

#### Step 2: Implement detection and enforcement in `DiagnosticStore.save()`

1. Check if `encryption_key` is present in the configuration.
2. If `encryption_key` is empty, scan the content for sensitive patterns defined in Step 1.
3. If sensitive content is found without an encryption key, raise a security exception or refuse the save.

#### Step 3: Add tests

- Test that sensitive data triggers refusal when `encryption_key` is empty
- Test that sensitive data is successfully encrypted when `encryption_key` is provided
- Test that non-sensitive data is saved normally without encryption
- Test that errors are handled gracefully in the calling code (e.g., `repl.py`)

## Validation Plan

1. Unit tests: Verify each encryption scenario works correctly
2. Integration tests: Verify complete diagnostic save sequence works correctly
3. Manual testing: Test with various encryption configurations
4. Regression testing: Verify normal diagnostic save still works correctly

## Risks

| Risk | Mitigation |
|------|------------|
| Breaking existing deployments that rely on unencrypted diagnostics | Document as breaking change; provide migration guide |
| May cause data loss if encryption fails | Implement graceful degradation with clear error messages |
| Performance impact from encryption | Monitor encryption overhead; consider caching keys if needed |
