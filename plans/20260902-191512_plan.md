## Goal
Replace the single, self-contradictory "Area Dependency Graph" (governs runtime calls,
deployment, documentation cross-references, and governance applicability all as one
cyclic graph) with four separated, individually-defined relation graphs, remove the
resulting cycle and duplicate definitions, correct the Conflict Resolution Rule and
Change Impact Rule to stop using a cyclic graph for authority/impact decisions, and add
automated CI cycle-detection scoped to the one graph type where cycles are actually
prohibited (software runtime dependencies).

## Background
`docs/00_governance_01_documentation-policy.md`'s `## Area Dependency Graph` (currently
at line 302) and `docs/00_governance_04_documentation-checks.md`'s `### 12. Area
Dependency Graph Validation` (currently at line 182, mermaid form) define the identical
edge set in two places. Re-verified 2026-09-02 directly against current source (all line
numbers below are current, not the Issue's originally-cited ones — content is unchanged,
only line position drifted):

```
Overview → Deployment, RAG, MCP, Agent, EventBus, Shared/DB, Governance
Deployment → RAG, MCP, Agent, EventBus, Shared/DB
RAG → Agent, EventBus
MCP → Agent, EventBus
Agent → EventBus, Shared/DB
EventBus → Shared/DB
Governance → Overview, Deployment, RAG, MCP, Agent, EventBus, Shared/DB
```

`Overview → Governance` (line 306) and `Governance → Overview` (line 311) coexist in
this same list, directly contradicting the immediately-following "**Cycles
prohibited**: No circular dependencies allowed." and "**Direction constraint**:
Dependencies only flow downward (Overview → Governance)." (lines 314-315).

This single graph is used for two decisions that should not both depend on a mixed,
cyclic edge set:
- **Conflict Resolution Rule**, rule 3 (line 147): "If documents span different areas,
  check whether one area's specification supersedes another's based on dependency
  direction" — uses dependency direction as an authority/precedence signal.
- **Change Impact Rule**, step 2 (line 200): "Map the change to affected areas using the
  area dependency graph" — uses the same graph for impact-scope determination.

`docs/00_governance_01_documentation-policy.md` line 253 already has a
`## Software Dependency Graph vs Documentation Reference Graph Separation` section
stating governance documents are excluded from "the software component dependency
graph" (scoped to Agent/MCP Server/RAG/EventBus/Shared-DB) and instead form their own
reference graph — but this section defines no edges of its own and never states whether
it is describing the same graph as `## Area Dependency Graph` or a different one. Given
the identical name ("dependency graph") and the Change Impact Rule/Conflict Resolution
Rule both citing "the area dependency graph" by that exact name, the cyclic graph is the
one actually in effect for both decisions today.

`docs/00_governance_04_documentation-checks.md`'s Governance Verification Matrix
self-reports both `GV-015` ("Software vs Documentation dependency graph separation",
line 287) and `GV-016` ("No unimplemented auto-checks documented as implemented", line
288) as `Status: Missing`, `Follow-up: Register Known Issue` — confirmed by direct read;
no corresponding Known Issue exists in `issues/`/`issues/done/` for either.

Confirmed by direct inspection 2026-09-02: no file under `tools/` contains cycle or
graph-traversal logic (the two `grep` hits for "cycle" were false positives on the
unrelated word "lifecycle"); no `.github/workflows/*.yml` step runs a dependency-graph
check; `uv run python tools/check_docs_structure.py` does not flag the Overview⇄
Governance cycle. `## 12. Area Dependency Graph Validation` is correctly classified as a
Manual Check (not claimed as automated), so this is a real, tracked-but-unaddressed gap
(GV-015/GV-016), not a false "automated but not implemented" claim (GV-016 itself is
about auditing for exactly that latter failure mode).

Confirmed by `grep -rl "eventbus" scripts/agent/ scripts/mcp_servers/ scripts/rag/`: 0
matches — the graph's `RAG → EventBus`, `MCP → EventBus`, `Agent → EventBus` edges have
no corresponding import or HTTP-publish call in current code. Confirmed by direct
inspection: `scripts/agent/` calls MCP servers over HTTP (Agent → MCP), but the graph
states `MCP → Agent`, the reverse direction, with no corresponding `RAG → Agent` call
path found either (RAG is consumed via the separate `mcp_servers/rag_pipeline` MCP
server, not a direct import).

## Problem
A single graph that mixes runtime-call, deployment-management, documentation-reference,
and governance-applicability semantics under one arrow notation, while also containing a
direct two-node cycle, is used as the deciding input for both canonical-source
determination (Conflict Resolution Rule) and change-impact scoping (Change Impact Rule).
This risks wrong-document-wins outcomes and incomplete/incorrect impact-scoping for any
change touching Governance or Overview, and leaves the graph's own stated invariant
("Cycles prohibited") permanently false. The gap is self-acknowledged (GV-015/GV-016 both
`Missing`) but not tracked as a Known Issue as those entries' own `Follow-up` field
requires.

## Reason for change
`docs/00_governance_01_documentation-policy.md` is the canonical governance-policy
document; a structurally self-contradictory core mechanism in it (a graph that violates
its own no-cycle invariant) undermines every downstream decision that cites it by name,
and the two self-reported audit gaps (GV-015/GV-016) require a Known Issue per the
matrix's own Follow-up column, which this Plan (as the required follow-up) provides.

## Implementation intent
Split the one mixed graph into four independently-defined relation types, each scoped to
the nodes and cycle-tolerance that actually apply to it, replacing (not duplicating)
across the two governance documents:
- **Software Runtime Dependency Graph**: Agent, MCP, RAG, EventBus, Shared/DB only
  (Governance, Overview, Deployment excluded, per the existing but previously
  unconnected Software-Dependency-Graph-vs-Documentation-Reference-Graph-Separation
  section). `A → B` means "A calls B at runtime, or requires B's data/functionality to
  function." Cycles prohibited (this is the only graph this Plan cycle-checks). Edges
  corrected to match confirmed call direction (`Agent → MCP`, not `MCP → Agent`; no
  direct `RAG → Agent`; EventBus edges marked `Needs Confirmation` per the 0-import
  finding above, not asserted as fact).
- **Deployment Management Graph**: Deployment → each component, meaning "Deployment
  places, starts, stops, or validates this component's runtime" — a management relation,
  not a call dependency. Not cycle-checked (a management graph is not expected to be
  acyclic in the same sense).
- **Documentation Reference Graph**: cross-reference relations between documents
  (Overview ↔ Governance's existing mutual reference is expected and retained here, not
  treated as a violation). Checked only for broken links/self-reference/duplicate
  reference — not for the runtime "no cycles" invariant.
- **Governance Applicability Matrix**: Governance's relationship to each area, expressed
  as a matrix (area × applicable-policy-topic), not as directed graph edges — removing
  Governance from graph traversal entirely rather than special-casing it.

`Conflict Resolution Rule` rule 3 is changed to reference the document's own existing
`Canonical Source Precedence` → `Decision Target Canonical Source Matrix` (line 67) for
per-decision-target authority, removing the dependency-direction mechanism rather than
trying to fix it for a now-multi-graph world.

`Change Impact Rule` and `Change Impact Assessment` are changed to select which graph to
consult by change category: architecture/runtime-behavior → Software Runtime Dependency
Graph; deployment → Deployment Management Graph; documentation-only →
Documentation Reference Graph; governance-policy → Governance Applicability Matrix;
configuration/API changes continue to use the existing Canonical Source Precedence
matrix (no new Configuration Ownership Map / API Consumer Map is created — registered as
a new Needs Confirmation entry per Out-of-Scope, since the Issue itself does not decide
whether these are needed).

A new tool, `tools/check_dependency_graph_cycles.py`, parses the Software Runtime
Dependency Graph's edge list from `docs/00_governance_01_documentation-policy.md` (same
plain-text `A → B, C` bullet format the current graph already uses — no new data format
introduced) and fails if a cycle exists among its 5 in-scope nodes; wired into
`.github/workflows/governance-docs-consistency.yml` as an additional step. The remaining
genuinely-unresolved edge-semantics and scope questions (3 EventBus edges,
`rag`/`rag_pipeline` relationship, Security-area runtime-component status, Configuration
Ownership Map / API Consumer Map necessity) are registered as new Needs Confirmation
entries per `docs/00_governance_03_issue-and-uncertainty-management.md`'s existing
inventory format, rather than guessed.

## Design

unbounded number of other documents cite by name (Conflict Resolution Rule, Change
Impact Rule) — a policy-mechanism change, not a narrow content fix. Full architecture,
dependency, historical, and operational analysis performed per `workflow-path-b.md`:

- **Architecture analysis**: the four-graph separation directly maps each of the
  Issue's own proposed options A-E to a concrete document location, rather than
  inventing a new taxonomy — this Plan implements the Issue's own already-decided
  resolution policy verbatim, only making the placement/scope decisions the Issue left
  open (new sections within existing docs, not new files; config/API impact continues
  via the existing Canonical Source Precedence matrix rather than new maps).
- **Dependency graphing**: confirmed via direct source grep (see Background) that
  `Agent → MCP` (not the graph's stated `MCP → Agent`) and 0 EventBus imports exist
  anywhere in Agent/MCP/RAG — the graph's edges are corrected to match, with genuinely
  unconfirmed edges marked `Needs Confirmation` rather than silently corrected to a
  guess.
- **Historical analysis**: `git log` was not needed beyond the Issue's own already-cited
  evidence (the contradiction is structural and present in current source, not a
  regression needing history to explain).
- **Operational dependency inspection**: the new CI step is additive (a new `steps:`
  entry in an existing, already-passing workflow) — no existing step is modified in a
  way that could break current CI behavior.

  non-runtime intent (e.g. "MCP failures affect Agent" rather than a call direction) →
  **Mitigation**: the new graph's own stated `A → B` meaning ("A calls B at runtime, or
  requires B's data/functionality") makes this an explicit, checkable definition going
  forward, and the correction is grounded in a direct source grep, not inference.

  (e.g. a future editor reformatting the bullet list) → **Mitigation**: unit tests cover
  the parser against the real current text (REQ-008), and a parse failure should raise a
  clear error rather than silently passing (Design decision for Phase 2 implementation).

  new Configuration/API map) could be judged wrong by an architecture owner after the
  fact → **Mitigation**: both decisions are recorded as Assumptions with their rationale,
