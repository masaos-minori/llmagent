## Goal
- Make the agent and each MCP server buildable and runnable as Nuitka `--onefile` binaries deployed to `/opt/llm/bin/`, while keeping `config/`, the Sudachi dictionary, and `sqlite-vec` as external data under `/opt/llm/`; keep `uv run` development and the existing deployment path working until the binary path is verified.

## Priority
Medium

## Scope
- **In-Scope**:
  - A single runtime path-resolution module that resolves the config directory (env var > binary-adjacent > `__file__`-based) and the Sudachi dictionary path (absolute path, fail-fast).
  - Replacing every `__file__`-based `config/` resolution that breaks under onefile (`ConfigLoader`, `WORKFLOWS_DIR`, config display/error-message paths).
  - Passing an external absolute dictionary path to the two `Dictionary(dict="core")` call sites.
  - Extending `CommandValidator` so MCP binaries under a fixed install directory pass validation without weakening the existing allowlist.
  - Declaring `PyYAML` as a production dependency (used by `mdq`).
  - A build script producing 11 binaries (agent + 10 MCP servers) and a PoC gate on the real binaries.
  - Switching `config/agent.toml` MCP `cmd` entries, `deploy/` scripts, `skills/deploy/SKILL.md`, and the deployment doc to the binary layout after the PoC gate passes.
- **Out-of-Scope**:

  - `scripts/agent/commands/cmd_skill.py` `skills/` resolution (see UNK-05).
  - Plugin mechanism (already removed).

## Background
Deployment currently rsyncs `scripts/`, `config/`, `schemas/` to `/opt/llm/` and resolves dependencies at run time with `uv run`. The goal is faster startup and simpler distribution through Nuitka onefile binaries. Phase 0 (a PoC with a minimal script) confirmed that Nuitka 4.2.2 on Python 3.13 builds `sudachipy`, `orjson`, `pydantic_core`, `lxml`, `PyGithub`, and `gitpython`, that an external absolute Sudachi dictionary, an external config directory, and an external `vec0.so` all work from inside a onefile binary, and that `sudachipy/resources/*` must be bundled via `--include-package-data=sudachipy`.

## Problem
- Under onefile, `__file__` points to a temporary extraction directory, so `ConfigLoader.__init__` and `WORKFLOWS_DIR` no longer find the external `/opt/llm/config/`.
- `Dictionary(dict="core")` requires `sudachidict_core` inside the package, which is not bundled and not wanted (about 217 MB).
- `CommandValidator` rejects any `cmd[0]` whose basename is not in a fixed allowlist, so a binary such as `/opt/llm/bin/mcp_shell` is rejected.
- `mdq/parser.py` imports `yaml`, but `PyYAML` is not a declared production dependency (it is present only as a transitive development dependency).

## Reason for change
Phase 0 showed the approach is technically feasible; the remaining work is the code-side prerequisites, which are backward compatible with `uv run`, followed by build and deployment changes gated on a PoC of the real binaries.

## Implementation intent
Introduce one leaf module under `scripts/shared/` that owns runtime path resolution, and make every existing call site delegate to it. Keep the explicit `ConfigLoader(config_dir=...)` argument as the highest-priority override for tests. Treat deployment changes as a later, gated phase: the config `cmd` rewrite and deploy script changes happen only after the real binaries are built and smoke-tested, with rollback being a revert of `config/agent.toml` plus redeploy.

## Requirements
- `REQ-001`: Provide a single config-directory resolver with the precedence `LLMAGENT_CONFIG_DIR` (must exist, else explicit error) > directory adjacent to the running Nuitka binary > legacy repository-root `config/`, and make `ConfigLoader` use it while keeping its explicit `config_dir` argument as top priority.
- `REQ-002`: Make `WORKFLOWS_DIR`, the `/config` command display path, and the config-load error message use the same resolver so no `__file__`-based `config/` resolution remains outside it.
- `REQ-003`: Provide a Sudachi dictionary resolver: `LLMAGENT_SUDACHI_DICT` set means that absolute path is used and must exist (explicit error otherwise); unset in a compiled binary means `/opt/llm/dict/system.dic` must exist; unset in a non-compiled run keeps `dict="core"`. Both `Dictionary(...)` call sites use it.
- `REQ-004`: Let `CommandValidator` accept an executable whose fully resolved real path is a regular file directly inside an allowed binary directory (default `/opt/llm/bin`) that is not group/world-writable, without changing the existing basename allowlist behavior for other commands.
- `REQ-005`: Declare `PyYAML` as a production dependency in `pyproject.toml` and `uv.lock`.
- `REQ-006`: Provide `deploy/build_binaries.sh` that builds the agent and the 10 MCP servers with Nuitka onefile (including `--include-package-data=sudachipy`, `--onefile-no-compression`, and an output directory that is not `/tmp`), and verify via a PoC of the real binaries that they start, serve HTTP health, and run RAG search with the external dictionary and `vec0.so`.
- `REQ-007`: After the REQ-006 gate passes, switch the 10 MCP `cmd` entries to the binary paths, update the deploy scripts and the agent start script to deploy binaries and external data (`config/`, `dict/system.dic`, `sqlite-vec/`) and to export the external-data environment variables, and update `skills/deploy/SKILL.md` and the deployment document including the `uv run` rollback procedure.

## Design
- **Layering**: `scripts/shared/runtime_paths.py` depends only on the standard library, so it satisfies the `shared-is-leaf` contract in `.importlinter`; `agent`, `rag`, and `shared.config_loader` may import it. `lint-imports` currently reports one pre-existing violation (`shared.production_config_validator -> agent.tool_policy`) that is unrelated to this Plan and must not be mistaken for a regression.
- **Config directory**: resolver precedence is explicit environment variable, then (only when running as a Nuitka-compiled binary, detected via `__compiled__`) the directory adjacent to the install root of the binary, then the legacy repository-root `config/`. Gating the adjacent lookup on the compiled marker prevents an accidental match during `python -m agent.repl` development runs. `ConfigLoader(config_dir=...)` stays the top-priority override.
- **Sudachi dictionary**: `LLMAGENT_SUDACHI_DICT` set means use it and fail fast if missing; unset and compiled means `/opt/llm/dict/system.dic` and fail fast if missing; unset and not compiled means `dict="core"` (development). A silent fallback is rejected because `sudachidict_core` is not bundled in the binary, so a silent fallback would only delay the failure. `sudachipy` package resources must still be bundled in the binary (Phase 0 finding), via the build script.
- **Environment propagation**: MCP servers are children of the agent process started by `HttpServerLifecycleManager`; with `cfg.env` unset the child inherits the full environment, and when it is set the filter removes only `LD_PRELOAD`, `LD_LIBRARY_PATH`, and `PYTHONPATH`, so `LLMAGENT_*` propagate without code change.
- **Command validation**: keep the existing basename allowlist and add an allowed-binary-directory rule evaluated on the fully resolved real path, requiring a regular file directly in the directory and a directory not writable by group or others. Symlinks are resolved before the check, so a link planted in the install directory pointing elsewhere is rejected.
- **Hybrid deployment** (UNK-04): only the agent and the 10 MCP servers become binaries; `scripts/`, `pyproject.toml`, and `uv` stay deployed for the peripheral `uv run` entry points. This is a deliberate, smaller first step, not the final single-binary end state.
- **Build host**: needs a Python with development headers (`Python.h`) and `patchelf`; low-memory hosts need `--onefile-no-compression`; the output directory must not be a small tmpfs.
- **Rollback**: revert `config/agent.toml` and redeploy; `scripts/` is still deployed, so the `uv run` path keeps working.

## Risks
- **Risk**: A lax directory rule in `CommandValidator` weakens a security control (likelihood: medium) → **Mitigation**: exact real-path directory match, regular-file check, reject group/world-writable directories, keep the basename allowlist unchanged, and cover the reject cases in tests (AC-06).
- **Risk**: The real binaries fail to build because of lazy imports or missing package data (likelihood: medium) → **Mitigation**: the Phase 2 gate (Step 9) blocks every production-affecting change until the PoC passes; Phase 1 changes are backward compatible with `uv run`.
- **Risk**: A missing external file fails late and obscurely (likelihood: medium) → **Mitigation**: fail-fast explicit errors for a missing config directory or dictionary (AC-01, AC-05).
- **Risk**: The 11-binary build is too slow or exhausts `/tmp` (likelihood: high, about 10 minutes per binary was measured) → **Mitigation**: `--onefile-no-compression`, a non-tmpfs output directory, and optional `ccache` (UNK-06); not on the critical path of Phase 1.
- **Risk**: A dictionary version mismatch with `sudachipy` breaks tokenization (likelihood: low) → **Mitigation**: extract the dictionary from the same build environment and verify it in the Step 9 RAG search.
- **Risk**: A production regression after the `cmd` switch (likelihood: low) → **Mitigation**: `scripts/` stays deployed, rollback is a `config/agent.toml` revert plus redeploy, rehearsed in Step 12.
- **Risk**: `config_loader.py` has about 20 call sites, so a resolver bug has a wide blast radius (likelihood: low) → **Mitigation**: keep the legacy repository-root fallback as the final branch, so source runs behave exactly as before, and run the full suite.
- **Risk**: `http_lifecycle.py` has high churn (15 commits in 30 days) and is adjacent to the validator change (likelihood: medium) → **Mitigation**: the Plan does not modify `http_lifecycle.py`; the default binary directory lives in the validator.
