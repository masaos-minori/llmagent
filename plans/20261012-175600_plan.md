## Goal
Make the web-search MCP subprocess pass its startup `/health` check when `browser_auth_token` differs from the client-facing `auth_token`, so the agent starts successfully with web-search enabled, without weakening bearer-token auth on protected endpoints.

## Priority
High

## Scope
- **In-Scope**:
  - Fix the `/health` credential mismatch for web-search only, via an opt-in loopback exemption on the shared Bearer-auth middleware (`scripts/mcp_servers/server.py::attach_auth_middleware`).
  - Wire the opt-in flag from `scripts/mcp_servers/web_search/web_search_server.py`.
  - Add/adjust tests for the health-check authentication path (`tests/agent/test_http_lifecycle_health_check.py`, `tests/mcp_servers/web_search/test_web_search_health.py`).
  - Update the authentication/deployment docs to record that web-search additionally requires `MCP_WEB_SEARCH_BROWSER_AUTH_TOKEN` and that the health-check mismatch is resolved.
- **Out-of-Scope**:
  - Changing the auth model for non-web-search servers (default preserves current behavior).
  - Revisiting the pre-flight logic in `deploy/start_agent.sh` (already implemented).
  - Altering `browser_allowed_domains` allowlist behavior or `BrowserAuthorization` handling.
  - Modifying the generic `auth_headers()` contract in `scripts/shared/mcp_config.py`.

## Background
HTTP MCP servers run as agent-managed subprocesses and must pass a startup health check against their `/health` endpoint before the agent treats them as ready (`scripts/agent/http_lifecycle.py`). The health checker authenticates with the server's configured main `auth_token` via `McpServerConfig.auth_headers()`, which returns `{"Authorization": "Bearer {self.auth_token}"}`.

The web-search server attaches bearer-token auth middleware using `_cfg.browser_auth_token` (loaded from `config/web_search_mcp_server.toml`), so every endpoint — including `/health` — is validated against `browser_auth_token`. The deployment records `browser_auth_token` as a distinct credential from the client-facing `auth_token`. Both are still required to be set; they are simply different secrets.

A recent `deploy/start_agent.sh` change added a startup pre-flight that requires both `MCP_WEB_SEARCH_AUTH_TOKEN` and `MCP_WEB_SEARCH_BROWSER_AUTH_TOKEN` to be set before launching. Previously startup aborted earlier on the missing-token check, which masked this health-check failure. With the pre-flight in place, startup now proceeds far enough to hit the broken health check.

## Problem
web-search never becomes healthy, so the agent fails to start whenever `browser_auth_token` differs from the main `auth_token`. This makes the web-search server unusable in any normal deployment, where the two credentials are intentionally distinct.

## Reason for change
The pre-flight now surfaces this code path (previously hidden behind the missing-token abort). web-search is a core search capability, and its startup failure blocks the whole agent. This is a correctness/startup bug, not an environment or operator error.

## Implementation intent
Apply a minimal, opt-in loopback exemption to the shared Bearer-auth middleware: when a server opts in, requests to `/health` whose client address is on a loopback range are admitted without a Bearer token, while every other endpoint keeps strict Bearer validation. The agent's health poll reaches the subprocess over `127.0.0.1`, so the exemption covers the startup (and liveness) poll without exposing `/health` externally — all MCP servers bind to `127.0.0.1` only, and no `0.0.0.0` bind exists in the repo.

The new middleware parameter defaults to disabled, so non-web-search servers keep their exact current behavior. See the `Design` section for the rejected alternatives and rationale.

## Requirements
- `REQ-001`: web-search passes its startup `/health` check within `startup_timeout_sec` when both `MCP_WEB_SEARCH_AUTH_TOKEN` and `MCP_WEB_SEARCH_BROWSER_AUTH_TOKEN` are set.
- `REQ-002`: `/health` still returns `401` for a request presenting an incorrect or unauthenticated token, and for any request that is not on a loopback address.
- `REQ-003`: other HTTP subprocess servers still pass their startup health checks; their `/health` behavior is unchanged from before this Plan.
- `REQ-004`: the `browser_allowed_domains` allowlist and `BrowserAuthorization` semantics are unchanged.

## Design

Root cause (confirmed against current source): the agent's health checker sends the
server's main `auth_token` (`McpServerConfig.auth_headers()` → `Bearer {auth_token}`),
while `web_search_server.py` registers the shared Bearer-auth middleware with
`_cfg.browser_auth_token`, so `/health` is validated against `browser_auth_token`.
Because the two are distinct secrets, the startup poll always receives `401` and the
agent aborts.

The issue leaves the fix direction open ("pick one, this is a design decision"). Three
directions were evaluated:

1. **Opt-in loopback exemption on the shared middleware (chosen).** Add a keyword-only
   `exempt_health_on_loopback=False` parameter to `attach_auth_middleware`. When a server
   opts in, requests to `/health` whose client address is loopback are admitted without a
   Bearer token; all other routes keep strict validation. `web_search_server.py` passes
   `True`. Rationale: minimal (2 source files), does not couple the generic health
   checker to web-search specifics, keeps `auth_headers()` untouched, and the opt-in
   default preserves every other server's exact behavior. Secure because all servers bind
   `127.0.0.1` only, so `/health` is never externally reachable; the exemption adds no
   external attack surface.
2. **Health checker sends `browser_auth_token`.** Would require exposing a browser-token
   field on the client-side `McpServerConfig` and routing it through `auth_headers()`.
   Rejected: broadens blast radius across high-churn shared code (`mcp_config.py`, ~48
   commits; `http_lifecycle.py`, ~55 commits) and couples the generic checker to a
   web-search-only credential.
3. **Align server-side health credential with the main `auth_token`.** Would require
   passing the client-facing `auth_token` into the web-search subprocess. Rejected:
   largest change; the web-search server is configured with `browser_auth_token` by
   design and would need a new credential wired in.

Loopback detection: use `ipaddress.ip_address(request.client.host).is_loopback`
(covers IPv4 `127.0.0.0/8` and IPv6 `::1`); confirm the request exposes the client host
via `request.client` in the middleware closure. The `/health` path is matched by
`request.url.path`; keep the exemption scoped to that path only.

The parameter is additive and keyword-only with a disabled default, so this is a
backward-compatible interface addition, not a breaking change.

## Risks
- **Risk**: Modifying the shared `attach_auth_middleware` could inadvertently change behavior for non-web-search servers. → **Mitigation**: the new flag defaults to disabled (keyword-only, additive), so callers that do not opt in keep exact current behavior; regression tests cover the other HTTP servers (`REQ-003`).
- **Risk**: Exempting `/health` on loopback could expose health details externally if a server ever binds a non-loopback address. → **Mitigation**: all servers bind `127.0.0.1` only (verified); the exemption is further scoped to loopback client addresses via `ipaddress.is_loopback`, and `/health` is matched by path. Document the loopback-dependence as an assumption.
- **Risk**: High churn on `mcp_config.py` (~48 commits) and `http_lifecycle.py` (~55 commits) raises the chance of touching related code. → **Mitigation**: the chosen design does not modify either file; they are reference-only in this Plan.
