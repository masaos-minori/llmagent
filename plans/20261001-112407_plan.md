## Background
Found during an adversarial review of `scripts/rag/ingestion/etag_manager.py`. Both `_is_stale_update()` raise sites use the same `ValueError` type — the message text (`"Invalid incoming timestamp: ..."` vs `"Invalid stored timestamp: ..."`) is the only current distinguishing mechanism; no separate exception classes exist for the two cases. `docs/21_rag/rag_02_06_ingestion_pipeline-supporting-components.md` records this as a Needs Confirmation item (added 2026-09-03, per `implementations/done/20260903-122926_02_docs_03_rag_02_06...md`) with no owner follow-up. Repository-wide search found no issue, plan, or implementation procedure targeting this specific question.

## Problem
Any caller that needs to distinguish "the crawler just fetched a corrupt/malformed timestamp" from "a previously stored timestamp in the database is corrupt" today has no reliable way to do so except parsing the exception's message string — a fragile pattern that breaks silently if the message wording changes.

## Reason for change
This is a design question that has sat undecided since 2026-09-03, documented only as an inline Needs Confirmation marker with no owner follow-up. Left unresolved, it risks being silently treated as permanent design ("this is just how it works") when the current behavior may simply be an unexamined accident. The fix is a decision, not a code change yet.

## Implementation intent
Phase 1 is decision-gathering: present both branches below and record the owner's selection. Phase 2 implements exactly one branch once selected — option (a) formalizes the current single-`ValueError` behavior into documentation; option (b) splits the two raise sites into distinct exception subclasses and updates every affected file. Neither branch is started before the decision is captured.

## Design
The undecided element is the exception *type* raised by `_is_stale_update()` at its two raise sites (line 60, invalid incoming; line 76, invalid stored). Both currently raise bare `ValueError`; only the message text differs. The owner selected option (b) on 2026-10-01 (UNK-01 resolved), so this Plan commits to option (b); option (a) is documented below for historical context only.

**Option (a) — Formalize current behavior (no code change).** Leave `_is_stale_update()` raising a single `ValueError` for both cases. Replace the open Needs Confirmation marker in the ingestion-pipeline supporting-components doc with a definitive statement documenting that the shared `ValueError` is intentional and the message text is the distinguishing mechanism. Update the shared error-handling reference table entry accordingly. Downside: callers still cannot distinguish the two cases programmatically; the fragile message-parse pattern remains sanctioned.

**Option (b) — Split into distinct exception types.** Introduce two narrow subclasses of `ValueError` (e.g. `InvalidIncomingTimestampError`, `InvalidStoredTimestampError`) and raise the appropriate one at lines 60 and 76. Because there is a single caller chain (`document_manager.py:112` → `ETagManager.update` → `_is_stale_update`), blast radius is small; audit whether that caller needs to catch the new types. Update the doc and the shared error-handling reference table to document the two types, and add tests asserting the distinction. Downside: introduces a small public API surface and requires the caller audit; must not be done without explicit owner sign-off.

Both branches keep `_is_stale_update()`'s existing return-path semantics (returns `False` for empty/missing timestamps, strict `<` staleness comparison) untouched.
