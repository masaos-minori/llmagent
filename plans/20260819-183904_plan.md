# Plan: Fix AttributeError on sqlite3.Row.get() in find_all_pending_approvals

## 1. Goal

Eliminate the unconditional `AttributeError: 'sqlite3.Row' object has no attribute 'get'`
raised by `find_all_pending_approvals()` in `scripts/agent/workflow/approval_ops.py`
whenever a pending approval gate exists from a previous session, so that
`StartupOrchestrator._recover_pending_approvals()` — and therefore agent startup as a
whole — no longer fails in this scenario.

## 2. Scope

**In-Scope:**
- Fix the unsafe `r.get("expires_at")` access in `find_all_pending_approvals()`
  (`scripts/agent/workflow/approval_ops.py`).
- Add a direct, non-mocked unit test for `find_all_pending_approvals()` in
  `tests/agent/workflow/test_approval_ops.py`.
- Add a non-mocked integration test for `_recover_pending_approvals()` in
  `tests/agent/test_startup.py` that exercises the real `find_all_pending_approvals`
  implementation via a real `StateStore`/temp SQLite DB.

**Out-of-Scope:**
- Any change to `find_all_pending_approvals()`'s or `_approval_from_row()`'s public
  signature or return type.
- The unrelated `WorkflowDef.require_approval` production-policy / expiry-enforcement
  work already covered by `plans/20260819-180036_plan.md` (adds `is_expired()`,
  changes `_gate_approval()`) — that plan touches the same file
  (`approval_ops.py`) but for a distinct feature; this plan does not depend on or
  duplicate it.
- Any change to `resolve_approval()`, `get_latest_approval()`,
  `find_pending_approval_by_session()`, `count_pending_approvals()`,
  `find_approval_by_id()`, or `find_latest_pending_approval()` — none of these call
  `.get()` on a `sqlite3.Row` (verified by reading the full file, see §5).

## 3. Assumptions

1. `StateStore.__init__()` always opens its connection with `row_factory=True`
   (`scripts/agent/workflow/state_store.py:31`), so every row reaching
   `find_all_pending_approvals()` in production is a `sqlite3.Row`, never a `dict` or
   plain tuple. Falsifiable: re-read `state_store.py:28-31` and
   `scripts/db/helper.py`'s `open()`/`fetchall()` — confirmed, no other row-factory path
   exists for the `workflow` DB target.
2. `sqlite3.Row` has no `.get()` method in the Python versions this project targets
   (project targets `py313` per `rules/coding.md`). Falsifiable and confirmed directly:
   `python3 -c "..."` reproduction below raises `AttributeError: 'sqlite3.Row' object
   has no attribute 'get'`.
3. No behavioral change to the returned `ApprovalRecord.expires_at` value is intended —
   only the access mechanism changes. The existing codebase convention for optional
   `sqlite3.Row` key access is `"key" in r.keys()` (used at
   `approval_ops.py:28` for `workflow_id`), not `dict(r).get(...)`; this plan follows
   that convention for consistency within the same file, per the requirement's stated
   preference.

| UNK-02 | Does any other caller of `find_all_pending_approvals()` rely on `expires_at` being populated in a specific way that this fix could disturb? | Call sites of `find_all_pending_approvals` | Resolved by `rg` below | False |

Resolution detail for UNK-01: `scripts/db/schema_sql.py` defines `approvals.expires_at`
as a normal nullable column (`TEXT`) that is always present in the `SELECT` column list
used by `find_all_pending_approvals()`'s query (`a.expires_at` is explicitly selected at
line 188). Since the column is explicitly selected, the key `"expires_at"` is always
present in `r.keys()` for every row `find_all_pending_approvals()` produces — the
`"key" in r.keys()` guard is defensive/consistent with the codebase idiom but the `NULL`
case (not "missing key" case) is the one that actually occurs in practice; both are
handled correctly by `r["expires_at"] if "expires_at" in r.keys() else None`, since
`sqlite3.Row.__getitem__` returns Python `None` for a SQL `NULL` value.

Resolution detail for UNK-02:

Only one call site exists in production code: `scripts/agent/startup.py:585`
(`_recover_pending_approvals`). It only reads `results[0]` as `(task_id, approval)` and
uses `approval.approval_id` / `approval.reason` — it never reads `expires_at` directly.
No other caller exists. No blocking unknowns remain.

## 6. Design

The fix is a single-line access-pattern change with no design alternatives worth
weighing at length — the requirement document (`requires/done/20260818-224751_require.md`
§Implementation intent) already narrowed it to one of two idioms and explicitly
prefers the `"key" in r.keys()` form for in-file consistency with `_approval_from_row()`
(`approval_ops.py:28`). This plan adopts that preference:

```python
# Before (approval_ops.py:201, inside find_all_pending_approvals()):
_approval_from_row(r, status="pending", expires_at=r.get("expires_at")),

# After:
_approval_from_row(
    r,
    status="pending",
    expires_at=r["expires_at"] if "expires_at" in r.keys() else None,
),
```

No change to `_approval_from_row()`'s signature, `ApprovalRecord`, or the SQL query is
needed. Test design: both new tests must use a real (not mocked) `sqlite3.Row`-backed
path — mocking `find_all_pending_approvals` or its row factory would defeat the purpose
of closing this test gap. The existing `workflow_db`/`store` fixtures in
`tests/agent/workflow/test_approval_ops.py` (temp-file SQLite DB, `create_workflow_schema()`,
`build_db_config` patched to point at the temp paths) are the correct, already-established
pattern to reuse for the new `find_all_pending_approvals()` test — do not add a second,
divergent fixture. For `tests/agent/test_startup.py`, the new integration test must likewise
patch `db.helper.build_db_config` to a temp-path `DbConfig` (mirroring the same fixture
pattern) rather than relying on the shared, non-isolated `/opt/llm/db/workflow.sqlite`
that some pre-existing `_start_servers` tests in that file implicitly touch — this keeps the
new test hermetic and avoids polluting the shared dev DB.
