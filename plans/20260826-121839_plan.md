## Problem

- REQ-001: `/skill`-injected system context can persist in conversation history
  for more turns than intended (until the next `/skill` invocation's own
  narrower filter runs), because the generic per-turn ephemeral sweep only
  checks `_ephemeral`/`_memory_injected`, not `_skill_ephemeral`.
- REQ-002: `RETENTION_DAYS` and `read_active()` implement a per-source-type
  memory-expiry filter that is fully unreachable in production — no caller
  anywhere invokes it — making the retention policy appear enforced to a
  reader when it is not, and carrying maintenance cost (a `read_active()`
  method with its own datetime-parsing/error-handling logic) for a code path
  nothing exercises.

## Reason for change

Both are small, independently verifiable agent-layer defects explicitly called
out for cleanup in `issues/20260821_08_issue.md` (`L-5`, `L-7`), each already
flagged by prior review cycles as requiring a dedicated follow-up decision that
this Plan now makes.

  `_skill_ephemeral`, rather than changing `agent.message_schema.TRUSTED_SOURCES`

- REQ-002: remove the unreachable retention-filter code (`RETENTION_DAYS`,
  `read_active()`) rather than wiring in a caller, since no concrete,

  plan/doc, and inventing one would be speculative.

## Design

**REQ-001 — where to fix the gap.** Two options exist, per the Issue's own Fix
Intent and the prior implementation-procedure doc's "Alternatives considered"
section (`implementations/done/20260726-101004_mode_classification_and_cmd_skill.py.md`):

1. *Authorize `_ephemeral` for `source="skill_mixin"`* by changing
   `TRUSTED_SOURCES["skill_mixin"]` to `{"_skill_ephemeral", "_ephemeral"}` in
   `scripts/agent/message_schema.py`. Fully restores the original message
   shape, but touches a security-relevant, explicitly-tested contract
   (`TRUSTED_SOURCES["skill_mixin"] == {"_skill_ephemeral"}` is asserted by
   name in `tests/agent/test_ephemeral_filtering_security.py:398` and
   `tests/agent/test_message_schema.py:251`), and the `cmd_skill.py` code
   comment explicitly warns against this exact change "without review."
2. *Align the clearing logic with `_skill_ephemeral`* by adding it to
   `Orchestrator._EPHEMERAL_KEYS` in `scripts/agent/orchestrator.py`. Achieves
   the same end-user-visible fix (skill context cleared at the next turn
   boundary) without touching `message_schema.py` at all — `_ephemeral` is
   still stripped from the stored message (that assertion in
   `test_cmd_skill.py` stays valid), but the orchestrator's sweep no longer
   needs to see `_ephemeral`; it now also matches on `_skill_ephemeral`
   directly.

**Chosen: option 2.** It satisfies the Issue's Fix Intent ("align the clearing
logic with `_skill_ephemeral`"), touches exactly one file for the functional
fix, and avoids the specific security-relevant change the existing code
comment flags for extra review. This narrows REQ-001's implementation to a
one-line frozenset literal change plus a comment update — no
`message_schema.py` edit, no change to any of the three security/schema test
files (they are re-run for regression confirmation only, per Tests above).

Per `rules/coding.md`'s Explicit sign-off gates: because the current
`cmd_skill.py` comment (lines 50-59) explicitly gates *any* change to this
area behind "review," the implementation step for REQ-001 requires an
explicit maintainer sign-off (a comment on this Plan's `plans/` entry
confirming the option-2 approach above is acceptable) before the code change
lands — this is not a generic Plan-approval formality, it is the specific
gate the prior implementation cycle asked for.

**REQ-002 — remove, not wire in.** No concrete, already-planned caller exists
for `read_active()` anywhere in the repository (verified by repo-wide `rg`
across `scripts/`, `tests/`, `plans/`, `requires/`, `issues/`); three
independent prior verification cycles (spanning 2026-07-27 through
2026-08-19) each reconfirmed zero callers and each deferred the "wire in or
remove" decision rather than resolving it. Per `rules/coding.md`'s
Deprecation policy — "Deprecated symbols are removed the next time `plans/`
touches the corresponding file for an unrelated reason, provided a
zero-caller `rg` re-check still holds" — this Plan is exactly that trigger:
it already touches `jsonl_store.py`/`enums.py` for this Issue's cleanup, and
the zero-caller check (re-run during this Plan's Step 3 inspection) still
holds. This mirrors the directly analogous precedent in
`plans/done/20260819-163404_plan.md`, which removed
`McpServerHealthRegistry.record_degraded()`/`get_degraded_reason()` under the
same "confirmed zero production callers, no proposed future caller" reasoning.
