## Goal
Decide when the EventBus startup step that imports legacy file-based consumer offsets (`migrate_legacy_offsets()`) may be retired, what happens to the old offset files, which side is authoritative after the import, and who owns the decision — then record the decisions in the operations and database documents. This is a decision-recording task; it removes or changes no code.

## Priority
High

## Scope
- **In-Scope**:
  - Record the end condition for the legacy offset import.
  - Record the retention policy for the old offset files (keep for rollback/audit, archive, or delete) with the permissions and backup treatment that follows.
  - Record that the database is authoritative after import and the files are never a resume source.
  - Record decisions on collision handling, a completion marker, and removal of the unused `write_offset()`/`read_offset()` helpers; file a follow-up issue for any behavior change.
  - Update `docs/24_eventbus/eventbus_07_configuration-and-operations.md`, `docs/24_eventbus/eventbus_05_dlq_offsets_and_delivery_semantics.md`, and `docs/41_db/db_03_architecture_and_schema-migration-and-scaling.md`.
- **Out-of-Scope**:
  - Changing `migrate_legacy_offsets()`, its startup call, or the file-based helpers.
  - Deleting any offset file or changing `offsets_dir`.
  - The schema migrations of `eventbus.sqlite` (`compat001`).
  - The Event Bus post-start verification failure (`ebstart003`).
  - Any file under `scripts/`, `config/`, or `tests/`.

## Background
- Source: an investigation of the design documents dated 2026-10-20 listing persistent-data migrations. Facts below were re-checked against current code and documents on 2026-10-20.
- `migrate_legacy_offsets()` in `scripts/eventbus/offset_migrator.py` reads each offset file under `offsets_dir`, recovers the consumer id from the `.map` companion (or from the sanitized file name when the companion is missing/empty), and inserts into `consumer_offsets` with `INSERT OR IGNORE`. It never modifies or deletes the files. (Confirmed by code)
- The EventBus lifespan in `scripts/eventbus/app.py` calls it on every start (line 77) inside a `try` that only logs `failed to migrate legacy offsets` (line 79) and lets startup continue. (Confirmed by code)
- When two legacy files without a `.map` companion sanitize to the same consumer id, the function raises `ValueError` from inside its loop; the lifespan catches it, so the rest of the import is skipped and startup continues. (Confirmed by code)
- The current runtime no longer writes offset files: `scripts/eventbus/ack_route.py` states `write_offset` was replaced by the transactional `ack_event_for_consumer()` path; `write_offset()`/`read_offset()` in `scripts/eventbus/offsets.py` have no production caller outside tests and themselves. (Confirmed by code)
- `migrate_legacy_offsets()` is covered by several tests in `tests/eventbus/test_eventbus_offsets.py`. (Verified by test)
- Documentation: the database document describes the import as idempotent and not modifying/deleting files, and the EventBus ADR lists the offset files as read only by this function. No document states why the files are kept, who owns them, which side wins after import, or when the import ends. (Confirmed by code: absence verified by search of `docs/`)
- Note (out of scope): `offset_migrator.py`'s module docstring says it "reads its offset via `read_offset()`", but line 84 reads directly from the on-disk file. This docstring/code discrepancy is outside this issue's scope (no `scripts/` change permitted here).

## Problem
The import runs on every start with no completion marker and no stated end. The legacy files stay in place indefinitely, so an operator cannot tell whether they are still authoritative, a rollback aid, or garbage. A collision aborts the whole import silently relative to startup, leaving some consumers unmigrated with only a log line. Nothing records when the import may be removed.

## Reason for Change
Consumer offsets decide where each consumer resumes; losing or mis-restoring one repeats or skips events. The import is a data-integrity path that cannot be deleted on a guess, and it should not stay on the startup path forever without an owner and an exit condition. Writing the decisions down now lets the removal be reviewed against a fixed criterion.

## Implementation Intent
- Record decisions, not code: the end condition, the retention policy for the files, the authority rule after import, and the owner.
- State the authority rule in present tense: after the import, the database is the source of truth, and the files are never read again for resume.
- Decide whether the import keeps running on every start or stops once a completion condition holds, and whether a collision should block startup or only be reported. Implementing either decision is a separate follow-up issue.
- Decide whether the unused file-based offset helpers are removed together with the import.
