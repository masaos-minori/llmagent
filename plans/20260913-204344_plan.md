## Background
The Issue's cited claim
(`docs/03_rag_03_02_query_pipeline-rag-pipeline-class.md`, "Documentation vs.
Implementation Mismatch" note: "`fetch_full_document` (`rag/repository.py`) ... [is]
not provided by `rag.pipeline`") is confirmed accurate —
`fetch_full_document()` is a module-level function defined in
`scripts/rag/repository.py:265-306`, not a method of `pipeline.py`'s `RagPipeline`.

**Re-verified 2026-09-13** (this cycle): the Issue's premise that this function is
entirely undocumented needs correction — `docs/03_rag_03_06_query_pipeline-helpers-and-cache.md`
(the Issue's own suggested destination) already mentions it **twice**:
1. Under "Public Methods" (line 85): `` `fetch_full_document(chunk_id, db,
   window=None)` → Fetches chunks for the same document in ascending order of
   `chunk_index`; `window=N` → ±N``
2. Under "Module-level Standalone Wrappers" (line 92): identical wording

This is not the same duplicate-section defect found in sibling issues this cycle
(`03_rag_02_03_ingestion_pipeline-chunksplitter.md`,
`03_rag_03_02_query_pipeline-rag-pipeline-class.md`) — the two mentions here sit in
two deliberately distinct sub-lists within one coherent section (`### 7.1
RagRepository`), not duplicated top-level sections. However, the first mention is
**mis-categorized**: `RagRepository` (`repository.py:121-249`) confirmed to define
only `vector_search()` and `fts_search()` as instance methods
(`repository.py:167,191`) — `fetch_full_document()`, along with
`deduplicate_chunks()` (`repository.py:311`) and `cosine_sim()` (`utils.py:41`), are
all module-level functions, not `RagRepository` methods, yet all three are listed
under "Public Methods" as if they were. The second mention ("Module-level Standalone
Wrappers") correctly places `fetch_full_document()`, but both mentions are equally
terse (one clause) and neither documents the not-found behavior, return type, or
ordering guarantee in the detail the Issue requests.

`fetch_full_document()`'s actual docstring (`repository.py:270-276`) already states
the full contract this Plan documents: `chunk_id: int`, `db: SQLiteHelper`,
`window: int | None = None`; `window=None` returns all chunks from the same
document, `window=N` returns chunks within N positions (±N); results ordered by
`chunk_index` ascending; returns `[]` when `chunk_id` is not found. Existing tests
(`tests/rag/test_fetch_order.py`) confirm each of these behaviors, including the
not-found case (lines 92, 131) and multiple window values (lines 99, 107, 116, 125).

## Problem
1. `fetch_full_document()`'s two existing mentions in
   `docs/03_rag_03_06_query_pipeline-helpers-and-cache.md` are both too terse to
   satisfy the Issue's request (no return-type, ordering-guarantee, or not-found
   documentation)
2. The first mention mis-categorizes it as a `RagRepository` "Public Method," which
   could mislead a reader into believing it is called as `repo.fetch_full_document(...)`
   when it is actually a standalone function

## Reason for change
Expand the correct (module-level) mention into a full contract description per the
Issue's request, and remove the incorrect "Public Methods" mention rather than
expanding a mis-categorized duplicate.

## Implementation intent
1. Remove `fetch_full_document`'s entry from the "Public Methods" bullet list (it
   does not belong there)
2. Expand its entry under "Module-level Standalone Wrappers" into a full

   (`None` = full document, `N` = ±N chunk-index range), return format (ordered by
   `chunk_index` ascending) and ordering guarantee, and the not-found case
   (`chunk_id` not found → `[]`)

## Design

interface changes, no database schema changes, no source code changes at all
(documentation-only).

needed correction — the function already has two terse mentions in its own
suggested destination file, one of which is mis-categorized. This Plan corrects the

Key design decisions:
1. Remove the mis-categorized "Public Methods" entry rather than also expanding it
   in place — keeping a mis-categorized entry, even if expanded, would still mislead
   a reader about how to call the function (`repo.fetch_full_document(...)` would
   not work; it must be called as `fetch_full_document(...)`, imported directly)

   new sub-section — this list is already the correct location and format for a
   standalone function's contract, consistent with how its sibling entries
   (`vector_search`, `fts_search`, `deduplicate_chunks`, `cosine_sim`) are listed
   there
