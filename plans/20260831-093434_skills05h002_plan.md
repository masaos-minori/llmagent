## Background
`### Canonical Ownership Model` (lines 65-107) defines what each of `AGENTS.md`,
`routing.md`, `skills/DESIGN.md`, `rules/*.md`, and `skills/<task>/SKILL.md` may
contain. `### Deduplication Rules`' content-type table (lines 149-158) maps the
same five destinations to content types, and its "Acceptance criteria:" bullet
list (lines 160-172, confirmed at that exact line range on direct re-read) restates
the boundaries a third time in constraint form. `### Validation` (lines 225-234)
then restates a compressed version of the same boundary check again in one bullet
(lines 229-232).

One correction carried over from the source Issue: the source task list this
Issue was based on described "Acceptance Criteria" as an independent top-level
section. It is not — it is a labeled bullet list ("Acceptance criteria:") inside
`### Deduplication Rules`. The duplication itself is real; only the
section-boundary description needed correcting, and that correction is preserved
here.

## Problem
The same ownership/boundary rule is independently written out four times across
three sections (`Canonical Ownership Model`, `Deduplication Rules`' table,
`Deduplication Rules`' acceptance list, `Validation`'s bullet), using different
wording and different levels of compression. Any future change to the ownership
boundaries requires updating all four locations to stay consistent, and nothing
enforces that they stay in sync.

## Reason for change
- Maintenance risk: four independent restatements of the same rule, no single
  source of truth to update.
- Consistency risk: the four restatements already differ slightly in
  wording/precision.
- Context cost: `prompts/05_skills.md` is loaded in full by its own Step 0; every
  restatement adds fixed per-invocation cost with no new information.

## Implementation intent
Treat `### Canonical Ownership Model` as the single canonical definition,
including the `AGENTS.md` vs. `rules/*.md` boundary test it already contains.
Apply the equivalence test to `Deduplication Rules`' content-type table before
deciding whether to keep it (it may serve a distinct type-to-destination mapping
purpose rather than restating what each destination contains). Reduce the
"Acceptance criteria:" list and `Validation`'s corresponding bullet to short
references to `Canonical Ownership Model`, keeping only language that states a
deduplication *outcome* rather than an ownership *boundary*.
