## Goal
Remove `scripts/agent/services/config_reload.py`'s confirmed-dead field-collection
method and its now-orphaned magic-string constants, consolidate its three duplicated
inline validator-import blocks to module level, and resolve the one genuine
raw-string/constant inconsistency found — restoring a single, unambiguous
field-collection path per config section without introducing a new abstraction layer.

## Priority
Medium

## Scope
- **In-Scope**: the two files listed in Implementation Target Files below; deleting
  `ConfigReloadService._collect_field_changes()` and its discarding call site; deleting
  the magic-string constants that become fully unused once that method is removed (plus
  a small number already fully unused today); converting the file's last two
  constant/raw-string inconsistencies to raw strings, matching the dominant pattern
  already used everywhere else in the file; moving the file's three inline validator
  import blocks to module level; removing the test class that exercises only the
  deleted dead method.
- **Out-of-Scope**: introducing a new `FieldKeyRegistry` (dict- or enum-based) or any
  other new abstraction layer — Step 3's investigation found the originating issue's
  premise for this (see Background) does not hold against current source; the 15
  approval/tool-safety/memory/security constants used by `_reload_section()`'s
  `field_mappings` tuple-list pattern (unrelated code path, no problem found — see
  Design); modifying `ConfigReloadRequest`/`ConfigReloadOutcome` or any public method
  signature; modifying `config_validators.py`'s own content (only where
  `config_reload.py` imports from it changes); modifying
  `_classify_mcp_server_changes()`/MCP server lifecycle handling; adding new config
  fields.

## Background
The originating issue (`issues/20260905-192444_refactor_config_reload_deduplicate_field_collection.md`)
describes `_collect_field_changes()` (used by `apply_config_dict()`) and
`_apply_llm_prompt_params()` (used by `_apply_rag_tool_params()`) as two **actively
duplicated** field-collection paths that must be merged, motivating a new
`FieldKeyRegistry` abstraction to prevent the two from drifting apart.

**Step 3 verification against current source (2026-09-06) found this premise does not
hold**: `apply_config_dict()` calls `_collect_field_changes(new_cfg, {}, {}, {})` with
three freshly-created, immediately-discarded empty dicts (`config_reload.py:177`) —
the populated values are never captured into a variable and never read afterward. This
method's own docstring ("Replaces `_collect_request_values()` and
`_apply_llm_prompt_params()`") is itself stale: `_apply_llm_prompt_params()` is still
actively called, from `_apply_rag_tool_params()` (`config_reload.py:376-378`), with
real mutable dicts that *are* applied via `dataclasses.replace()` afterward. The
evidence indicates an incomplete prior refactor: `_collect_field_changes()` was wired
into `apply_config_dict()` but the switch-over to using its output was never completed
(or was reverted), leaving it as inert, fully dead code — confirmed via `radon cc`,
which grades it `D (27)`, the single highest-complexity method in the file (next
highest: `_apply_rag_tool_params` at `C (13)`).

The six methods `_apply_llm_prompt_params()` actually coexists with —
`_apply_llm_context_params`, `_apply_tool_params`, `_apply_rag_params`,
`_apply_llm_retry_params`, `_apply_llm_prompt_params`, `_apply_sse_reload_params`
(all called from `_apply_rag_tool_params()`, `config_reload.py:372-379`) — were
verified to collect **disjoint, non-overlapping field sets**; no duplication was found
among them. The real "3+ locations to update per new field" maintenance risk the issue
describes (Reason for Change) is caused entirely by the dead method requiring a mirror
update alongside the active one, not by genuine duplication in the active path — so
deleting the dead method resolves the maintenance risk directly, without a new registry.

`_collect_field_changes()` is directly unit-tested by
`tests/agent/services/test_config_reload.py::TestCollectFieldChangesConsolidation`
(5 tests, calling the method directly and asserting on its populated dicts) — these
tests currently pass but provide no actual regression protection for
`apply_config_dict()`'s real behavior, since production code discards every value they
verify gets collected.

Of the ~46 `FIELD_*` magic-string constants (lines 46-91), `rg` confirms: 24 are
referenced only inside `_collect_field_changes()` (would become fully unused once it is
deleted); 2 (`FIELD_CONTEXT_CHAR_LIMIT`, `FIELD_CONTEXT_COMPRESS_TURNS`) already have
zero references anywhere in the file today, unrelated to the dead method; 3
(`FIELD_USE_MEMORY_LAYER`, `FIELD_ROUTING_DRIFT_STRICT`, `FIELD_MEMORY_EMBED_ENABLED`)
are likewise already fully unused — `_detect_startup_only()` reads their corresponding
keys via raw string literals instead (`config_reload.py:701,705,709`); 2
(`FIELD_CONTEXT_TOKEN_LIMIT`, `FIELD_SYSTEM_PROMPT_TOOL`) are used both inside the dead
method and exactly once each in live code (`_apply_llm_context_params`'s
`context_token_limit` field at line 476-477, and `_sync_services()`'s membership check
at line 352-353) — each of those two live call sites sits inside a method that
otherwise uses raw string literals for its sibling fields, the one concrete instance of
the issue's Problem #3 ("inconsistent key references") found in the active code. The
remaining 15 constants (`FIELD_APPROVAL_*`, `FIELD_TOOL_SAFETY_TIERS`,
`FIELD_ALLOWED_ROOT`, `FIELD_ALLOWED_TOOLS`, `FIELD_GITOPS_PUSH_BLOCKED`,
`FIELD_MEMORY_RETENTION_DAYS`, `FIELD_MEMORY_LOCAL_ONLY`, `FIELD_SECURITY_PROFILE`,
`FIELD_SECURITY_LOCKDOWN_ENABLED`) are consistently used, each exactly once, inside
`_reload_section()`'s `field_mappings` tuple-list pattern (`_reload_approval_config`,
`_reload_tool_allowlist`, `_reload_memory_runtime`) — no inconsistency or duplication
found there; a constant name typo in this pattern would be a `NameError` at parse time
rather than a silently-ignored key, a small but genuine safety benefit this Plan
preserves by leaving these 15 constants unchanged.

The issue's three inline `from agent.services.config_validators import (...)` blocks
(`config_reload.py:387-398`, `425-429`, `444-452`, all inside `_apply_rag_tool_params()`)
are confirmed real, current duplication — `config_validators.py` has zero runtime
imports (only a `TYPE_CHECKING`-gated import of `agent.config_dataclasses`, already
safely imported at module level elsewhere in `config_reload.py`), so moving all three
blocks to module level carries no circular-import risk.

## Problem
1. **Confirmed-dead field-collection method**: `_collect_field_changes()` duplicates
   field-collection logic already covered by six active `_apply_*_params` methods, but
   its own output is discarded at its only call site — it is inert, untestably-relevant
   dead code carrying the file's highest cyclomatic complexity (`D`, 27).
2. **Orphaned magic-string constants**: 31 of ~46 `FIELD_*` constants have (or, after
   this Plan's REQ-003, will have) zero remaining references — dead weight requiring no
   maintenance benefit.
3. **One genuine key-reference inconsistency**: `_apply_llm_context_params()` and
   `_sync_services()` each mix a `FIELD_*` constant with sibling raw-string field
   references for no apparent reason, the one confirmed instance of the issue's
   "inconsistent key references" concern in currently-active code.
4. **Repeated validator imports**: three near-identical inline `from
   agent.services.config_validators import (...)` blocks inside
   `_apply_rag_tool_params()`, one per config section (LLM/RAG/Tool).

## Reason for Change
- Maintenance risk: a change to a field currently collected inside the dead
  `_collect_field_changes()` requires a developer to also (uselessly) update that
  method to keep it internally consistent, even though doing so has no effect —
  wasted effort and a confusing signal about where the real logic lives.
- Readability: 31 unused/soon-to-be-unused constants and a 27-complexity dead method
  obscure the six small, genuinely active `_apply_*_params` methods a reader actually
  needs to understand hot-reload behavior.
- Correctness risk (narrow): the one confirmed raw-string/constant inconsistency is a
  latent trap if a constant's value and a sibling raw string ever drift apart during a
  future edit.

## Implementation intent
Delete the confirmed-dead `_collect_field_changes()` method and its discarding call
site; delete every `FIELD_*` constant confirmed to have zero remaining references
after that (re-confirming zero-caller status against then-current code, not this
Plan's authoring-time snapshot); resolve the file's one confirmed constant/raw-string
inconsistency by converting both remaining call sites to raw strings (the file's
dominant pattern) before deleting those two constants; move the three inline validator
import blocks to module level; remove the test class that exercised only the deleted
method. Do not introduce a new field-key registry, `Enum`, or other abstraction — Step
3's investigation found no genuine duplication in the active code path that a registry
would meaningfully prevent (see Background); the six active `_apply_*_params` methods
already collect disjoint field sets with no drift risk between them.

## Design
This Plan corrects a mismatch between the originating issue's framing and current
source: the issue frames `_collect_field_changes()` as an *actively duplicated*
collection path requiring a new `FieldKeyRegistry` to keep in sync with
`_apply_llm_prompt_params()`; direct verification instead found
`_collect_field_changes()` is fully dead code (its output is discarded at its only
call site) with no live behavioral role. Its six sibling `_apply_*_params` methods
already collect disjoint field sets with no duplication between them — the
architecture the issue's Implementation Intent assumed needs a registry (many call
sites racing to stay in sync) does not exist. This Plan therefore favors the smaller,
directly-evidenced fix (delete dead code, remove orphaned constants, fix the one real
inconsistency, consolidate imports) over the issue's larger speculative one, per
`AGENTS.md` Global Rule 5's scope discipline — introducing a registry now would add an
abstraction layer to solve a problem that no longer exists once the dead code is gone.

The 15 constants used by `_reload_section()`'s `field_mappings` tuple-list pattern are
deliberately left unchanged: they already serve a real purpose (a typo in a constant
name is a `NameError` at parse time, versus a silently-accepted-but-ignored key if a
raw string were mistyped inside a `field_mappings` list) and exhibit no drift or
duplication risk this Plan needs to address.
