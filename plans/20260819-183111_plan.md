# Plan: Remove test-compatibility re-export shim for TransportError in tool_executor.py

## Goal

Remove the `TransportError` re-export (and its `# noqa: F401` justification comment)
from `scripts/shared/tool_executor.py`, and update every test module that currently
imports `TransportError` from `shared.tool_executor` to import it from its true
defining module, `shared.http_transport`, with no behavior change.

## Scope

**In-Scope**
- `scripts/shared/tool_executor.py`: drop `TransportError` from the
  `from shared.http_transport import (...)` block; drop the `# noqa: F401`
  re-export comment; keep `HttpTransport` (still used at line 108's
  `_resolve_transport` return-type annotation and in `_resolve_transport`'s body).
- `tests/shared/test_tool_executor.py`: import `TransportError` from
  `shared.http_transport` instead of `shared.tool_executor`.
- `tests/shared/test_tool_executor_order.py`: import `TransportError` from
  `shared.http_transport` instead of `shared.tool_executor` (this file was not
  listed in the source requirement's Target files, but was found during Step C
  source-file verification to depend on the same re-export — see Unknowns below).
- Verify (via `rg`) that no other production or test module depends on obtaining
  `TransportError` from `shared.tool_executor`.

**Out-of-Scope**
- Any change to `TransportError`'s definition, semantics, or location in
  `scripts/shared/http_transport.py`.
- Any change to `HttpTransport`'s public interface.
- Any behavior change to retry logic, error classification, or caching in
  `scripts/shared/tool_executor.py`.
- Broader import-hygiene cleanup across the rest of `scripts/shared/`.

## Assumptions

- `TransportError` is not referenced anywhere in `tool_executor.py`'s own logic
  (only imported for re-export) — confirmed by reading the full file: the only
  use of the `shared.http_transport` import block's names inside the file body is
  `HttpTransport` (via `_resolve_transport`'s type annotation and dict lookup).
- `HttpTransport` remains required as a direct import in `tool_executor.py` after
  the change, since `_resolve_transport(self, server_key: str) -> HttpTransport | None`
  and `self._transports: dict[str, HttpTransport]` (via `ToolTransportInvoker`
  base) reference it directly.
- Removing the re-export is a pure import-hygiene change: no runtime behavior,
  no public API surface of `ToolExecutor` changes.

## Design

`TransportError` is defined in `scripts/shared/http_transport.py` (line 18) and is
the canonical error type raised by `HttpTransport.call()` on transport-level
failures. `scripts/shared/tool_executor.py` currently imports it solely to
re-export it for test convenience, marked with an explicit `# noqa: F401`
justification comment (per `rules/coding.md` §Suppression governance, this
justification is required and currently present — but the requirement is that the
re-export itself should not exist).

The design is a straight import-source correction:
- `tool_executor.py` keeps importing only what it uses (`HttpTransport`).
- Every test file that needs `TransportError` imports it from its defining
  module, `shared.http_transport`, matching the pattern already used by
  `tests/shared/test_tool_executor.py` (line 16) and
  `tests/shared/test_tool_executor_stampede.py`/`test_tool_executor_routing.py`
  style imports (which import `ToolExecutor` directly and do not need
  `TransportError`).

No new abstractions, no behavior change: `TransportError` remains the same class,
raised from the same call sites in `http_transport.py`; only the import path used
by test files changes.

## Risks

- **Risk**: A test file outside `tests/shared/` (not caught by the `rg` scope
  used above) also imports `TransportError` from `shared.tool_executor`, causing
  an `ImportError` at collection time after the re-export is removed.
  → **Mitigation**: The `rg "from shared.tool_executor import\|tool_executor\.TransportError"`
  search was run across the full `scripts/` and `tests/` trees (not scoped to
  `tests/shared/`), and it found exactly two importers of `TransportError` via
  `shared.tool_executor` — both listed in Affected areas and both updated in
  Implementation step 1. Low residual risk; low likelihood.
- **Risk**: Future contributor re-introduces the re-export pattern for a
  different symbol without justification.
  → **Mitigation**: Not mitigated by this change (out of scope); covered by the
  existing suppression-governance check
  (`tools/check_suppression_justification.py`) which requires any future
  `# noqa` to carry an inline justification, same as the one being removed here.
  No follow-up issue filed — this is a general governance mechanism already in
  place, not a gap introduced by this change.
