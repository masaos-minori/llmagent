## Goal
Make the per-logical-call vs per-attempt gate-evaluation model explicit and asserted in code and tests for the `HttpTransport.call` retry path, resolving the ambiguity that in-call HTTP retries bypass the pre-call health/lifecycle/semaphore gates.

## Priority
Low

## Scope
- **In-Scope**:
  - Document in `scripts/shared/tool_transport_invoker.py` that `_run_precall_gates` runs the gate chain exactly once per logical call and that in-call HTTP retries inside `HttpTransport.call` intentionally bypass these gates (option (a)).
  - Clarify in `scripts/shared/http_transport.py` that the retry loop performs multiple HTTP attempts without re-entering the pre-call gates.
  - Add a test asserting that when `call()` retries, the health, lifecycle, and semaphore gates execute exactly once (not per attempt).
- **Out-of-Scope**:
  - Changing the retryable-status set, exponential backoff (`2**attempt`), or `_RETRY_MAX`.
  - Re-evaluating readiness between attempts (option (b)).
  - Any change to server-side dedup or idempotency (`X-Idempotency-Key` / `dispatch.py::_duplicate_cache`).
  - Retry behavior for non-MCP HTTP calls.

## Background
`ToolExecutor.execute` -> `ToolTransportInvoker._raw_execute` -> `_run_precall_gates` performs, in order: health registry check, disabled-server check, lifecycle `ensure_ready`, transport lookup, and semaphore acquisition. It then calls `_invoke_and_record`, which runs `HttpTransport.call`. All HTTP-level retries live inside `call`; none of the gates are re-entered between attempts. This was verified against current source: `_run_precall_gates` (lines 231-278) runs the gate chain once and then delegates to `_execute_with_semaphore` -> `transport.call`, whose retry loop (lines 163-217, `_RETRY_MAX = 3`) contains no gate re-entry.

## Problem
The pre-call gate chain is a per-logical-call boundary, but the retry loop is a per-HTTP-attempt mechanism. When the first attempt fails, the subsequent attempts inside the same `call` do not re-check health or re-run `lifecycle.ensure_ready`. Consequences:

- Redundant requests can be sent to a server that has gone unhealthy during the call.
- A mid-call crash does not trigger a lifecycle restart until the exhausted call surfaces a single `TransportError` that `_record_transport_error` turns into one health-failure count, so reaching the failure threshold takes more wall-clock failures than one might expect.

Clarification (adversarial review): these are expected properties of the retry design, not active defects. The retry loop exists precisely to resend failing requests, and `record_failure` runs only after `call` exhausts (`_record_transport_error`, line 190) — so state cannot flip to unavailable mid-retry-loop within the same logical call. The "already-unhealthy" window therefore opens only under concurrent calls whose failures flip state, and the tail-latency risk applies to long-timeout servers only. Both the priority (Low) and the issue's own Unresolved Questions treat the operational harm as theoretical.

## Reason for change
The asymmetry is easy to misread: `_run_precall_gates` reads like a guard around every request, but it guards only the first. For a long-timeout server this can mean several blocked requests against an already-dead endpoint before the breaker trips, degrading tail latency under partial outages. The per-logical-call gating is already implied by existing semantics, so the ambiguity can be removed with a minimal document-and-assert change without redesigning the retry/backoff policy.

## Implementation intent
Adopt option (a): keep gates per logical call and make it unambiguous in code and tests that in-call retries intentionally bypass them. Do NOT re-evaluate readiness between attempts (option (b)); per-logical-call gating is already implied by existing semantics — the health gate enforces a single HALF_OPEN trial per logical call (`_check_health`, lines 131-170) and the semaphore is acquired per logical call (`_execute_with_semaphore`, lines 204-213), so re-running the gate before each retry would re-enter trial ownership and re-acquire the semaphore, which is non-minimal and semantically inconsistent. Prefer the minimal change that removes the ambiguity; do not redesign the retry/backoff policy. Preserve the retryable-status set, exponential backoff, `_RETRY_MAX`, health-failure counting, and the overall timeout budget.

## Design
Option (a) vs option (b). The issue presents two models: (a) gates per logical call, retries intentionally bypass; (b) re-evaluate readiness between attempts. Repository evidence resolves this to option (a):

- `_run_precall_gates` (lines 231-278) runs the gate chain once, then delegates to `_invoke_and_record` -> `_execute_with_semaphore` -> `transport.call`. The retry loop lives entirely inside `HttpTransport.call` (lines 163-217, `_RETRY_MAX = 3`). No gate is re-entered between attempts.
- The health gate enforces a single HALF_OPEN trial per logical call (`_check_health`, lines 131-170; `acquire_trial`/`trial_in_flight`), and the semaphore is acquired per logical call (`_execute_with_semaphore`, lines 204-213). Re-running the gate before each retry (option (b)) would re-enter trial ownership and re-acquire the semaphore, which is non-minimal and semantically inconsistent with the per-logical-call model.
- `record_failure` (via `_record_transport_error`, line 190) runs only after `call()` returns/raises, i.e. after all retries are exhausted. So health state cannot flip to unavailable mid retry-loop within one logical call; the "already-unhealthy" window opens only under concurrent calls. This makes per-logical-call gating self-consistent.

Therefore option (a) is the lower-risk, minimal resolution: document and assert the existing behavior, and add a test that pins it. No change to retryable-status set, exponential backoff (`2**attempt`), `_RETRY_MAX`, health-failure counting, or timeout budget. The change is additive docstrings/comments plus one test (Path A: <= 3 files, no interface or DB change).
