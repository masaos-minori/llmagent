## Goal
Fix a security-relevant regex gap in `scripts/agent/tool_policy.py::_METACHAR_RE`: it fails closed on a raw command containing a newline (`\n`) but not a carriage return (`\r`), while `shlex.split()` (used immediately afterward for safe-prefix matching) treats `\r` as whitespace — letting a carriage-return-separated command (e.g. `"cat\r/etc/passwd"`) parse into tokens that match an approved safe prefix (`["cat", "/etc/passwd"]`) and classify as `RiskLevel.NONE` instead of `HIGH`.

## Priority
High

## Scope
- **In-Scope**: Add `\r` to `_METACHAR_RE`'s fail-closed metacharacter set in `scripts/agent/tool_policy.py`.
- **Out-of-Scope**: `_match_executable_identity`/`shlex.split`'s own tokenization behavior — `shlex` treating `\r` as whitespace is standard Python library behavior, not something to change; the fix is to fail closed *before* reaching `shlex.split`, consistent with `_has_metacharacters`'s own existing "REQ-002: fail closed on any shell metacharacter" design intent for exactly this class of bypass.

## Background
Commit `cba047fe` ("feat(agent): replace shell_run prefix matching with parsed-token authorization (REQ-001–006)") introduced `_has_metacharacters()`/`_METACHAR_RE` specifically to fail closed on shell metacharacters *before* the parsed-token safe-prefix match, and separately introduced `\n` to that set (visible in the regex: `r"[;|&]|&&|\|\||`|\$\(|<\(|>\(|>>|<<|[<>]|\n"`) — presumably because a raw newline could also be used to smuggle a second command past naive prefix-matching. `\r` was never added alongside it, and Python's `shlex.split()` (confirmed empirically: `shlex.split("cat\r/etc/passwd")` returns `['cat', '/etc/passwd']`) treats `\r` as a token separator exactly like `\n`/space — so a command using `\r` instead of a space or `\n` bypasses the metacharacter fail-closed check while still being tokenized by `shlex` into an innocent-looking, safe-prefix-matching sequence.

## Problem
`test_prefix_collision_carriage_return_rejected` and `test_carriage_return_in_command_rejected` both call `classify_risk(cfg, "shell_run", {"command": "cat\r/etc/passwd"})` expecting `"high"`, but observe `<RiskLevel.NONE: 'none'>` — confirmed via Read that `_METACHAR_RE` (line 42) omits `\r`, and empirically that `shlex.split` treats `\r` as whitespace, so `_match_executable_identity` sees `argv = ["cat", "/etc/passwd"]`, which exactly matches the `approval_shell_safe_prefixes=["cat"]` fixture and returns `RiskLevel.NONE`.

## Reason for change
This is a genuine security-classification regression/gap: a command-injection-style evasion technique (substituting `\r` for a space/newline to bypass the metacharacter fail-closed check while still benefiting from `shlex`'s whitespace-splitting behavior) currently causes a potentially-dangerous `shell_run` invocation to be classified as `RiskLevel.NONE` (no approval required) instead of `HIGH`. Per this session's earlier full-suite investigation, this was flagged as the highest-priority security finding among the 97 original failures.

## Implementation intent
Add `\r` to `_METACHAR_RE`'s alternation (e.g. `r"...|[\r\n]"` or `r"...|\r|\n"`), so any raw command containing a carriage return fails closed to `RiskLevel.HIGH` before ever reaching `shlex.split`/prefix matching — mirroring the existing, already-correct `\n` handling exactly.
