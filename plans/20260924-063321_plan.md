# Plan: Enforce ADR-009 Invariant — No Direct `chunks_fts` Operations Outside Sanctioned Paths

## Goal
Add static analysis enforcement that application code never directly operates on the `chunks_fts` table outside sanctioned write paths, closing the gap identified in DESIGN-2's Known Deviation.

## Priority
Medium

## Scope

- **In-Scope**: Create a lint rule/script that detects direct `INSERT/UPDATE` operations against `chunks_fts` outside the two sanctioned write paths; add regression tests; integrate into CI pipeline; update ADR-009 and DESIGN-2 documentation.
- **Out-of-Scope**: Refactoring the FTS wrapper itself; adding new FTS functionality; changing the `chunks_fts` schema; modifying MDQ's separate database access patterns; enforcing read-only `SELECT` statements against `chunks_fts`; adding enforcement for `chunks_fts_docsize` table operations.

## Background

ADR-009 establishes that application code must never directly operate on the `chunks_fts` table — all FTS operations must go through the FTS wrapper. ADR-009's Known Deviations section cites DESIGN-2 as an Architectural Limitation: no test verifies that application code respects this boundary. Zero direct-write bypasses have been found so far, but the absence of violations does not prove the invariant holds.

## Problem

No test or lint rule enforces the invariant established by ADR-009. Without enforcement, new code can inadvertently operate on `chunks_fts` directly, breaking the abstraction boundary between the RAG ingestion pipeline and the full-text search layer.

## Reason for change

The current state relies entirely on developer discipline. As the codebase grows, the risk of accidental bypass increases. Static analysis catches violations at development time rather than runtime.

## Implementation intent

Create a custom lint script under `tools/` that scans Python source files for direct `INSERT INTO chunks_fts` / `UPDATE chunks_fts` SQL strings outside the two sanctioned write paths. Integrate the script into the existing CI pipeline via `tox.ini`. Add a regression test demonstrating that unsanctioned direct writes are detected. Update ADR-009's Known Deviations section and DESIGN-2 status.

## Design

### Approach Selection

Approach 1 (lint rule/script) is preferred over Approach 2 (integration test with mocked DB) because it catches violations at development time rather than runtime.

### Lint Script Architecture

The lint script (`tools/check_chunks_fts_invariant.py`) will:

1. Use `rg` (ripgrep) to scan all `.py` files under `scripts/` for patterns matching `INSERT INTO chunks_fts` or `UPDATE chunks_fts`.
2. For each match, determine whether the occurrence is in a sanctioned write path or MDQ out-of-scope directory.
3. Report violations with file path, line number, and the offending SQL statement.

#### Whitelist logic

- **Sanctioned write paths** (must NOT be flagged):
  - `scripts/agent/services/rag_maintenance_service.py::rebuild_fts()` — sanctioned `/session rag-rebuild-fts` command path
  - `scripts/db/schema_sql.py` — schema initialization SQL (executed once during setup, not runtime)
- **Out-of-scope read/write paths** (not flagged):
  - `scripts/mcp_servers/mdq/` — targets a separate database (`/opt/llm/db/mdq.sqlite`)

#### Implementation details

- Use `rg -n "INSERT INTO chunks_fts\|UPDATE chunks_fts" scripts/` to get matches with line numbers.
- Filter results: skip lines within sanctioned paths (check file path + function context via AST parsing).
- Skip `scripts/mcp_servers/mdq/` entirely.
- Skip test files (`tests/`).
- Output format: `{file}:{line}: {sql_statement}` for each violation.
- Exit code: 0 if no violations, 1 if violations found.

#### CI Integration

Add a new tox environment or extend the existing `lint` environment in `tox.ini`:

```ini
[lint-chunks-fts]
commands = uv run python tools/check_chunks_fts_invariant.py
```

Or extend the existing `lint` environment:

```ini
    lint: uv run python tools/check_chunks_fts_invariant.py
```

### Test Design

The regression test (`tests/test_chunks_fts_invariant_lint.py`) will:

1. Create a temporary Python file containing an unsanctioned `INSERT INTO chunks_fts` statement.
2. Run the lint script against the temp file.
3. Assert that the script returns exit code 1 and reports the violation.
4. Clean up the temp file.

## Risks

- **Risk**: The lint script may produce false positives if it cannot distinguish between sanctioned writes inside `rag_maintenance_service.py::rebuild_fts()` and other functions in the same file. → **Mitigation**: Use AST-based function context detection to identify which function contains each `chunks_fts` reference, not just file-level filtering.
- **Risk**: Adding the lint step to CI may slow down the pipeline. → **Mitigation**: The script uses `rg` which is fast (< 1 second on this codebase); validate with timing before merging.
- **Risk**: New sanctioned write paths may be added later, requiring whitelist updates. → **Mitigation**: Document the whitelist update procedure in the script's docstring; require PR review for whitelist changes.
- **Risk**: The lint script may miss `chunks_fts` references written as f-strings or variable interpolation. → **Mitigation**: Use regex pattern that matches both literal strings and f-string prefixes (`f"...chunks_fts..."`, `rf"...chunks_fts..."`).
