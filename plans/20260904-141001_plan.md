## Goal
- Remove `use_semantic_cache`, `semantic_cache_threshold`, and `semantic_cache_max_size`
  from every active Agent, RAG, and RAG MCP configuration contract and conversion path,
  and make supplying any of the three removed keys produce a clear configuration error
  instead of a silent no-op.

## Priority
Medium

## Scope
- **In-Scope**:
  - Remove the three fields from `RagConfigImpl`, the shared `RagConfig` protocol, the
    Agent `RAGConfig` dataclass, and `RagPipelineConfig`.
  - Stop reading/forwarding the three keys in `_build_rag_config()`,
    `build_rag_cfg_adapter()`, `_build_module_cfg()`, and config reload.
  - Remove `AgentConfig._validate_semantic_cache_url()` and the SemanticCache-specific
    checks in `RagConfigValidator`.
  - Add explicit, consistent rejection of the three removed keys (with a migration
    message) to both the Agent and RAG MCP configuration-loading paths.
  - Remove the three keys from `config/rag_pipeline_mcp_server.toml` and any other
    active configuration/example file that sets them.
  - Update every test file that constructs a config fixture containing the three keys
    or asserts on the removed behavior.
- **Out-of-Scope**:
  - Removing the `SemanticCache` implementation itself and its invalidation paths —
    covered by issue `semcacherm`
    (`issues/done/20260902-150339_semcacherm_remove_semanticcache_implementation_and_invalidation_paths.md`),
    which this Plan depends on landing first.
  - Test and documentation replacement beyond this Plan's own fixture/assertion updates
    — covered by issue `semcachedocs`.
  - Redesigning remote/local RAG fallback behavior.
  - Removing `embed_url`.

## Background
Investigation confirmed `use_semantic_cache`, `semantic_cache_threshold`, and
`semantic_cache_max_size` exist in `scripts/rag/models_config.py`'s `RagConfigImpl`,
`scripts/shared/types.py`'s `RagConfig` protocol,
`scripts/agent/config_dataclasses.py`'s `RAGConfig` dataclass, and
`scripts/mcp_servers/rag_pipeline/rag_pipeline_models.py`'s `RagPipelineConfig` — the
same duplication this issue's Background describes across the RAG configuration DTO,
shared protocol, Agent configuration, cross-field validation, and the RAG MCP
configuration adapter.

## Problem
SemanticCache configuration is duplicated across the concrete RAG configuration DTO,
the shared `RagConfig` protocol, Agent configuration dataclasses and builders,
cross-field validation, shared RAG validation, the RAG MCP configuration adapter, and
module configuration translation. Leaving these fields after `semcacherm` deletes the
runtime cache would advertise a feature that cannot operate and would force adapters,
fixtures, and callers to provide obsolete values.

## Reason for change
Once `semcacherm` removes the runtime cache, these configuration fields have no
implementation to configure; retaining them either silently discards operator input or
misleads operators into believing the feature is still tunable.

## Implementation intent
Remove the three fields from every active configuration contract and conversion path.
Treat the removed keys consistently rather than silently ignoring an operator's
obsolete configuration — this Plan's investigation (Step 3) confirmed `ConfigLoader`
(`scripts/shared/config_loader.py`) performs no per-key schema validation; it is a bare
TOML/JSON-to-dict merge (`load()`/`load_all()`), so unknown keys are silently ignored
downstream unless a caller explicitly checks for them. This Plan centralizes that check
in `RagConfigValidator` (`scripts/shared/config_validator.py`) and wires it into both
the Agent and RAG MCP configuration-loading paths, since today only the RAG MCP
in-process path (`scripts/rag/pipeline.py`) calls it. Preserve `embed_url`.

## Assumptions
- This Plan's implementation must not begin until `semcacherm`'s implementation has
  landed (per the originating issue's Dependencies) — while `RagPipeline` still reads
  `self._cfg.semantic_cache_max_size`/`threshold` to construct `SemanticCache`, removing
  these fields from `RagConfigImpl`/`RagConfig` would break pipeline construction. This
  Plan's authoring (this document) does not require that ordering; only its
  implementation does.
- `config/agent.toml` does not currently set any of the three removed keys (confirmed,
  Reference Files); if a future edit to `config/agent.toml` adds one before this Plan's
  implementation, REQ-003's new rejection will surface it as a configuration error
  rather than a silent acceptance.
- Centralizing removed-key rejection in `RagConfigValidator` (REQ-003) and calling it
  from both `build_agent_config()`'s `_build_rag_config()` path and
  `RagPipelineConfig.load()` (REQ-002, REQ-004) is the intended single point of
  enforcement — no second, independent rejection mechanism is introduced.

## Design
Investigation (Reference Files: `scripts/shared/config_loader.py`) confirmed
`ConfigLoader.load()`/`load_all()` perform no per-key schema validation — they merge
TOML/JSON into a plain `dict`, filtering only keys starting with `_`. This means the
originating issue's Unresolved Question resolves to: **unknown keys are silently
ignored today**, by every caller that reads via `.get(key, default)` (which is how
`_build_rag_config()`, `RagPipelineConfig.from_dict()`, and
`ConfigReloadService._apply_rag_params()` all read config). The one exception is
`scripts/rag/pipeline.py`'s `RagConfigImpl(**_raw_cfg)` construction, where an
unexpected keyword argument raises `TypeError` — but that is an accidental side effect
of `RagConfigImpl` currently declaring every field the raw dict might contain, not a
deliberate validation mechanism, and it does not apply to the Agent or `RagPipelineConfig`
paths at all (both use `.get()`-based construction, which would silently ignore a
leftover removed key).

This Plan therefore centralizes rejection in `RagConfigValidator`
(`scripts/shared/config_validator.py`), which already normalizes both config shapes
(`{"rag": {...}}` for `agent.toml`, flat `{...}` for MCP `module_cfg`) via
`_extract_rag_section()`. REQ-003 adds one new check there; REQ-002 and REQ-004 add a
`RagConfigValidator().validate()` call to the two paths that do not call it today
(`_build_rag_config()`'s caller in `config_builders.py`, and `RagPipelineConfig.load()`).
`scripts/rag/pipeline.py` needs no change (Reference Files) because it already calls
`RagConfigValidator().validate(_raw_cfg)` before constructing `RagConfigImpl` — REQ-003's
new check propagates through that existing call automatically.

Field removal order follows dependents-then-dependency within a single implementation
pass, since (per Assumptions) this Plan's *implementation* — not its authoring — is
gated on `semcacherm` having already landed: by the time this Plan is implemented,
`RagPipeline` no longer reads `semantic_cache_max_size`/`semantic_cache_threshold`, so
removing them from `RagConfigImpl`/`RagConfig` is safe.

## Risks
- **Risk**: 33 test files require the same mechanical 3-line/1-line fixture removal —
  a manual pass risks missing one → **Mitigation**: Implementation step 3 uses a single
  reviewed one-off script (`tools/`, per `AGENTS.md` Global Rule 7), followed by a
  repository-wide `rg` re-check for zero remaining matches outside the two new
  rejection tests.
- **Risk**: Adding a new `RagConfigValidator().validate()` call to
  `build_agent_config()` could reject a currently-working deployed `config/agent.toml`
  if it happens to set one of the three keys → **Mitigation**: this Plan's Reference
  Files confirmed `config/agent.toml` does not currently set any of them; re-verify at
  implementation time immediately before wiring the call in, since the file could
  change between this Plan's authoring and its implementation.
- **Risk**: Implementing this Plan before `semcacherm` lands would break
  `RagPipeline.__init__`'s `SemanticCache(max_size=self._cfg.semantic_cache_max_size, ...)`
  construction, since the fields it reads would no longer exist → **Mitigation**: this
  Plan's Assumptions state the ordering requirement explicitly; the implementer must
  confirm `issues/done/20260902-150339_semcacherm_...md` exists (i.e. `semcacherm` has
  been archived as completed) before starting Phase 2.
- **Risk**: Centralizing rejection in `RagConfigValidator` and calling it from a new
  location (`build_agent_config()`) could surface pre-existing, unrelated config
  warnings/errors that were previously never triggered on the Agent path (e.g. the
  `use_rrf=false` warning) → **Mitigation**: Implementation step 1 raises only on
  `validation_result.errors`, matching `scripts/rag/pipeline.py`'s existing pattern;
  warnings are logged, not raised, so no new failure mode is introduced for pre-existing
  warnings.
