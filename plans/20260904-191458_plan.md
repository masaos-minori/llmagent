## Goal
- Make every one of the 10 Git MCP tools `TOOL_LIST` advertises via `/v1/tools`
  actually callable through `/v1/call_tool`, through exactly one dispatch
  implementation, with write tools routed through `WriteProtectionPipeline` and
  read-only tools routed without its write-only rejection rules.

## Priority
High

## Scope
- **In-Scope**: enumerating and comparing advertised/dispatched/callable tool sets;
  selecting one canonical dispatch implementation; extending it to cover all 10
  tools; removing the unreachable alternative; a contract test proving advertisement
  and dispatch cannot drift apart again.
- **Out-of-Scope**: protected-branch/ref authorization content (`gitauth`); the
  write-protection pipeline's internal Stage 3/Stage 7/dry-run correctness
  (`gitpipeline`, `gitdryrun`) — this Plan routes write tools *into* that pipeline,
  it does not change what happens inside it; repository-path containment/audit
  (`gitpathaudit`); tool names, arguments, or read-only output format beyond what
  unifying dispatch requires.

## Background
This Plan's Step 3 investigation (continuing evidence already established this
session by `gitauth`'s Plan) enumerated the three tool inventories the issue's AI
Implementation Instruction asks for:
- **Advertised** (`scripts/mcp_servers/git/git_tools.py::TOOL_LIST`): 10 tools —
  `git_status`, `git_log`, `git_diff`, `git_branch`, `git_show` (read-only, per
  `shared/tool_constants.py::GIT_READ_TOOLS`), `git_add`, `git_commit`,
  `git_checkout`, `git_pull`, `git_push` (write, per `GIT_WRITE_TOOLS`).
- **Live HTTP dispatch** (`git_server.py`'s `POST /v1/call_tool`, confirmed the only
  route FastAPI actually serves): its `handlers` dict covers exactly 3 tools —
  `git_checkout`, `git_pull`, `git_push` — via inline `RepositoryState.snapshot()` +
  `WriteProtectionPipeline`. Only `format_checkout`/`format_pull`/`format_push` are
  imported into this file; `format_status`/`format_log`/`format_diff`/
  `format_branch`/`format_show`/`format_add`/`format_commit` are not imported at all.
  Any of the other 7 tool names return `"Unknown tool: {name}"`.
- **Service dispatch table** (`GitService.get_dispatch_table()` via
  `GitMCPServer.dispatch()`/`_dispatch_git_tool()`): covers all 10 tools, but
  `GitMCPServer.dispatch()` has zero external callers anywhere in the codebase
  (confirmed by repository-wide `rg "\.dispatch\("`) — dead code, per `gitauth`'s
  Plan's same finding.
`/v1/tools` (`_annotate_tool`) reports all 10 as `enabled` (subject only to
`allowed_repo_paths`/`read_only` gating), so a caller sees 7 tools advertised as
usable that in fact always fail.

## Problem
Two dispatch implementations exist for the same 10-tool inventory; the one that is
actually live serves only 3 of them, and the one that serves all 10 is unreachable.
Selecting and completing one canonical path is required before `gitauth`'s Stage 3
fix, `gitpipeline`'s Stage 7 fix, and `gitdryrun`'s Stage 5 fix can matter for
anything beyond checkout/pull/push — those three Plans all target
`RepositoryState`/`WriteProtectionPipeline`, which both dispatch implementations
already share, but only the live path currently invokes them at all.

## Reason for Change
Tool advertisement, availability, validation, dispatch, and protection must share one
canonical registry, or a write tool could reach execution through a path that skips
the protection pipeline `gitauth`/`gitpipeline`/`gitdryrun` are hardening — and today,
7 of 10 advertised tools cannot be reached through *either* path in a way that both
executes them and applies appropriate (write vs. read-only) rules.

## Implementation intent
Select the live `POST /v1/call_tool` path's underlying mechanism
(`RepositoryState`/`WriteProtectionPipeline`) as canonical — not because the endpoint
function itself is worth keeping as-is, but because `gitauth`/`gitpipeline`/
`gitdryrun`'s Plans already target that mechanism, and `GitService`'s alternative
dispatch table, while structurally complete, has never been reachable in production.
Concretely: reuse `GitService`'s existing per-tool request-model construction and
validation logic (it already has correctly-typed handlers for all 10 tools), but
route every call through `GitService._run_tool()` — modified so read-only tools skip
`WriteProtectionPipeline`'s write-only preconditions/postconditions entirely (per
`GIT_READ_TOOLS`) while write tools continue through it — and make `POST
/v1/call_tool` dispatch through `GitService.get_dispatch_table()` instead of its own
inline 3-tool `handlers` dict. Remove `GitMCPServer.dispatch()`/`_dispatch_git_tool()`
only after confirming nothing else depends on them (Reference Files).

## Design
Four Plans (`gitauth`, `gitpipeline`, `gitdryrun`, this one) were filed alongside each
other against the same `scripts/mcp_servers/git/` module and were investigated
independently this session, converging on the same underlying fact each time: the
live dispatch path is `POST /v1/call_tool`'s inline `RepositoryState`/
`WriteProtectionPipeline` logic, and `GitService`'s dispatch table is unreachable
dead code. The first three Plans all fix defects *inside*
`RepositoryState`/`WriteProtectionPipeline` (Stage 3, Stage 7, Stage 5) without
changing which tools reach them. This Plan is the one that decides *how many* tools
reach them and *through which HTTP-layer code*.

The canonical choice — reuse `GitService`'s per-tool method bodies (correct,
complete, just never called) but make `POST /v1/call_tool` dispatch through
`GitService.get_dispatch_table()` instead of its own hand-written 3-entry dict —
avoids two worse alternatives: (a) hand-porting all 7 missing tools' request
construction directly into `git_server.py`, duplicating logic `GitService` already
has correctly, or (b) keeping both dispatch mechanisms and trying to keep them in
sync manually, which is the exact drift this issue exists to eliminate. Per the
Deletion-First spirit (this is a `python-refactoring`-adjacent structural change,
though executed via the issue-to-plan pipeline, not `prompts/04_refactor.md`
directly): responsibility moves to an *existing* boundary (`GitService`), not a new
one — no new class or abstraction is introduced.

REQ-003's read-only bypass is necessary because `GitService._run_tool()` today wraps
*every* call — including `git_status`/`git_log`/etc. — in
`WriteProtectionPipeline`, which applies dirty-worktree/detached-HEAD preconditions
meant for write operations. Without this change, unifying dispatch through
`GitService` would newly *break* read-only tools in dirty/detached repositories
(regression), not just make them reachable — the issue's own Required Changes
anticipates exactly this ("Route all read-only tools through the canonical path
without applying write-only rejection rules").

## Risks
- **Risk**: This Plan depends on `GitService`'s existing per-tool logic being
  correct, but it was never exercised via HTTP — routing it live for the first time
  could surface latent bugs in the 7 previously-unreachable tools (analogous to
  `gitpipeline`'s discovery that `format_checkout()` itself had an argument-order bug)
  → **Mitigation**: REQ-007's contract test plus new per-tool HTTP tests (Tests
  section) specifically exercise each of the 7 tools for the first time; treat any
  failure found as an in-scope fix for this Plan, not a deferred follow-up, since
  "actually callable" is this Plan's core Acceptance Criterion.
- **Risk**: Four Plans (`gitauth`, `gitpipeline`, `gitdryrun`, this one) all touch
  `scripts/mcp_servers/git/` — landing this Plan's dispatch unification before the
  other three's `WriteProtectionPipeline` fixes could mean the newly-reachable write
  tools (`git_add`/`git_commit`) inherit the *unfixed* Stage 3/5/7 gaps → **Mitigation**:
  this Plan's Design explicitly notes it does not change pipeline internals; sequence
  awareness is the implementer's responsibility across all four Plans' Dependencies
  sections, not a defect in any single one.
- **Risk**: Removing `GitMCPServer.dispatch()`/`_dispatch_git_tool()` (REQ-006) could
  break an as-yet-undiscovered caller if the "zero external callers" finding
  (established in `gitauth`'s Plan, re-used here) becomes stale by implementation
  time → **Mitigation**: re-run `rg "\.dispatch\("` immediately before deleting, per
  this issue's own AI Implementation Instruction to re-confirm evidence before
  editing.
