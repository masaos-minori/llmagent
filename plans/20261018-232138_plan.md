## Goal
Guard `_LoopbackVerifyingServer.startup()` in `scripts/mcp_servers/server.py` so a FastAPI lifespan startup failure surfaces uvicorn's own clean diagnostic instead of an `AttributeError` from iterating the unset `self.servers` attribute, and add regression tests for the failing-lifespan path and the normal loopback-start path.

## Priority
High

## Scope
- **In-Scope**:
  - Add an early-exit / unset-`self.servers` guard to `_LoopbackVerifyingServer.startup()` so the socket iteration is skipped when uvicorn requested exit or has not yet assigned `self.servers`, while preserving the loopback-only bind verification for the normal start path.
  - Add a unit test that drives the real `_LoopbackVerifyingServer.startup()` override with a FastAPI app whose lifespan raises during startup and asserts the process fails without raising `AttributeError`.
  - Add a unit test asserting the normal loopback start still performs the post-start bind verification, and that a stubbed non-loopback bind raises.
  - Add a small test-only fixture module exposing a failing-lifespan FastAPI app and a healthy-lifespan FastAPI app.
- **Out-of-Scope**:
  - Changing which servers define a lifespan.
  - Changing the loopback-only bind policy or the pre-bind `http_host` check in `run_http()`.
  - Restructuring `run_http()` or the uvicorn wiring beyond the override guard.
  - Modifying `rag_pipeline_server.py` or any other server.

## Background
`scripts/mcp_servers/server.py` defines `MCPServer.run_http()`, which launches every MCP server via uvicorn. It wraps `uvicorn.Server` in a local subclass named `_LoopbackVerifyingServer` whose `startup()` override calls `await super().startup(sockets=sockets)` and then iterates `self.servers` to verify each bound socket address is loopback. In uvicorn 0.49.0, `Server.startup()` runs the ASGI lifespan startup first; if the lifespan requests exit (`should_exit` becomes True), `Server.startup()` returns early and does NOT assign `self.servers`. `Server.__init__` also never initializes `self.servers`. Only servers that define a FastAPI lifespan can therefore reach the early-return path. Of the MCP servers, `rag-pipeline-mcp` (in `scripts/mcp_servers/rag_pipeline/rag_pipeline_server.py`) defines a lifespan (`_lifespan`) that awaits `RagPipelineMCPService.start()`, which initializes HTTP/DB resources and can raise.

## Problem
When a server whose lifespan startup fails reaches `run_http()`, uvicorn logs its own clean diagnostic (`ERROR: Application startup failed. Exiting.`), `super().startup()` returns with `should_exit=True` and leaves `self.servers` unset, and the override's `for srv in self.servers:` then raises `AttributeError`. The `AttributeError` propagates out of `run_http()` (its `try/except` catches only `KeyboardInterrupt`) and out of the server's `__main__`, producing an unhandled traceback and exit code 1. The real cause (embedding/LLM endpoint unreachable, DB missing, invalid config) is masked behind an `AttributeError` about a missing attribute, making startup failures hard to diagnose.

## Reason for change
The RAG pipeline server's lifespan can legitimately fail at startup, and every such failure currently surfaces as an `AttributeError` rather than uvicorn's diagnostic. This is a startup-failure diagnosis regression with no functional upside — the process still exits, but the operator gets the wrong error.

## Implementation intent
Add a guard at the top of `_LoopbackVerifyingServer.startup()` after `await super().startup(sockets=sockets)` that returns early when `self.should_exit` is True or `self.servers` is not yet set (for example `if self.should_exit or not getattr(self, "servers", None): return`), skipping the `self.servers` iteration in that case. The loopback-only bind verification MUST remain intact for the normal start path. Frame the fix as a guard on the early-exit / unset-`self.servers` case, not as a change to the loopback policy.

## Design
Path A (small task): affects 3 files, no public or runtime-facing interface change, no database schema change. Architecture/dependency/historical analysis is skipped per the issue-to-plan Routing rules; the evidence below comes from Step 3 direct verification.

The defect is a correctness gap in an async lifecycle hook, not an architecture boundary issue. `_LoopbackVerifyingServer` is a local subclass inside `run_http()`; its `startup()` override assumes `super().startup()` always assigns `self.servers`, which is false on the lifespan-failure early-return path. The minimal fix narrows the assumption: skip the verification precisely when the server did not reach the serving state. This keeps the loopback policy and the pre-bind `http_host` check in `run_http()` untouched, and changes nothing on the normal (successful) start path where `self.servers` is assigned and `self.started` becomes True.

Repository evidence (Step 3):
- `scripts/mcp_servers/server.py` `_LoopbackVerifyingServer.startup()` iterates `self.servers` unconditionally after `await super().startup(sockets=sockets)`; `run_http()` catches only `KeyboardInterrupt`.
- uvicorn 0.49.0 `Server.startup()` sets `self.should_exit = True` and returns before assigning `self.servers` when `self.lifespan.should_exit` is True; `Server.__init__` initializes only `started` and `should_exit`, never `servers`.
- `scripts/mcp_servers/rag_pipeline/rag_pipeline_server.py` `_lifespan` awaits `RagPipelineMCPService.start()` and is the only MCP server defining a lifespan.
- Runtime reproduction (throwaway, outside the repo) with a subclass of the real `uvicorn.Server` and a failing-lifespan FastAPI app produced `ERROR: Application startup failed. Exiting.` followed by `AttributeError: '_LoopbackVerifyingServer' object has no attribute 'servers'`; the guarded variant eliminated the `AttributeError` while preserving the diagnostic.
- Baseline: `ruff check`, `mypy --no-namespace-packages scripts/`, and `bandit` on `server.py` are clean; `tests/mcp_servers/test_mcp_server_base.py` passes (36 tests); `radon`/`vulture` findings are pre-existing and unrelated.

- **Risk**: `_serve()` calls `capture_signals()`, which uses `signal.signal` and can fail outside a main thread. → **Mitigation**: Tests run on the main thread; if flaky under a test runner, patch `capture_signals` for the duration of the drive.
