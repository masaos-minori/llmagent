# Plan: Move git-mcp blocking operations off the event loop

## Goal

Run GitPython's synchronous operations outside the event loop and use an async-safe lock, so `/health` and other requests stay responsive during push and pull.

## Priority

Medium

## Scope

- **In-Scope**:
  - `scripts/mcp_servers/git/git_service.py`: wrap git operations in `asyncio.to_thread()`
  - `scripts/mcp_servers/git/repository_state.py`: replace `threading.Lock` with `asyncio.Lock`
  - `scripts/mcp_servers/git/format_output.py`: add timeouts to push and pull
  - `tests/mcp_servers/git/test_repository_state.py`: async test with slow fake git operation
  - `docs/22_mcp/mcp_04_05_git.md`: update locking/timeout documentation
- **Out-of-Scope**:
  - Ref validation, audit, and error-path changes
  - Changes to read-only tools (status, log, diff, branch, show)
  - Changes to MCP server lifecycle

## Background

Source: local investigation notes (memo1.md, ISSUE-09), from an earlier review finding.

## Problem

- Async handlers run GitPython synchronous operations (`push`, `pull`, `fetch`, `snapshot`) directly (per investigation notes, not re-verified).
- `_get_repo_lock()` returns a `threading.Lock` that is awaited from async code (Explicit in code — `scripts/mcp_servers/git/repository_state.py` defines `threading.Lock` based per-repo locks).

## Reason for Change

- A network push or pull blocks the whole server event loop, so `/health` stops responding; the Agent then sees timeouts and health failures and may mark the server unavailable.
- Waiting on a synchronous lock in the event-loop thread risks deadlock or total stall.

## Implementation Intent

- Keep long-running git operations off the event loop so health checks and read operations remain responsive.

## Design

### Decision matrix

| Condition | Outcome |
|---|---|
| Write operation (push/pull/fetch) | Run via `asyncio.to_thread()` with timeout |
| Read operation (status/log/diff/branch/show) | Keep synchronous (fast, no network) |
| Per-repo lock | Replace `threading.Lock` with `asyncio.Lock` |
| Timeout exceeded | Raise `TimeoutError` with clear message |

### Decision details

1. **Wrap write operations in `asyncio.to_thread()`**: In `git_service.py`, wrap the `op()` callable in `WriteProtectionPipeline.run()` with `asyncio.to_thread()`. This moves the blocking git operation to a worker thread while keeping the event loop responsive.
2. **Replace `threading.Lock` with `asyncio.Lock`**: In `repository_state.py`, replace `_repo_locks` from `dict[str, threading.Lock]` to `dict[str, asyncio.Lock]`. Update `_get_repo_lock()` to create `asyncio.Lock` instances.
3. **Add timeouts to push and pull**: In `format_output.py`, add configurable timeout parameters to `format_pull()` and `format_push()` functions. Use `asyncio.wait_for()` to enforce the timeout.
4. **Preserve per-repository mutual exclusion**: The lock scope remains the same — around the full pipeline body (precondition → execution → postcondition). Only the lock type changes.

## Assumptions

- Read-only operations (status, log, diff, branch, show) are fast enough to remain synchronous — they don't involve network I/O.
- The `asyncio.Lock` acquired inside `asyncio.to_thread()` is safe because the lock is only held during the pipeline body, not across await points.
- GitPython's `git.Repo` instance is thread-local — it should not be shared across threads. The `RepositoryState` snapshot holds a reference to the repo, so the repo must be opened/closed within the same thread.
- The timeout value should be configurable via `GitConfig` (e.g., `push_timeout`, `pull_timeout`).
