## Goal
Extend `tools/check_docs_quality.py`'s existing `check_content_similarity`
check to also compare document sections across files, not only within a
single file, so a governance rule (or other normative content) copied
verbatim into a second document is automatically flagged, while leaving
the check's existing within-file behavior byte-for-byte unchanged.

## Background
`tools/check_docs_quality.py` already implements `check_content_similarity`
(confirmed unchanged 2026-09-20), which flags near-duplicate section bodies
using `_compute_section_similarity` (Jaccard word-set overlap, threshold
0.85, code blocks/inline code stripped before tokenizing) — but its loop
structure compares sections only *within* the same `DocFile`, never across
different files, even though the function already receives the full
`files: list[DocFile]` for the entire corpus as its second argument (no
signature change is needed to add cross-file comparison).

Running the tool against
`docs/00_governance_01_documentation-policy.md` and
`docs/00_governance_04_documentation-checks.md` together (confirmed
2026-09-20) produces 10 warnings, all within `documentation-policy.md` —
zero comparing the two files against each other, despite 3 sections of
near-verbatim duplicate rule text between them (Merge Conditions/Merge
Workflow vs. Merge Condition Validation; Change Impact Rule/Matrix vs.
Change Impact Assessment/Matrix, word-for-word identical 4-row table;
Review Rule vs. Review Gate Conditions, word-for-word identical 4-bullet
list) — see the companion documentation-remediation issue for full detail.
`documentation-checks.md` already correctly avoids duplicating a different
section (the dependency-graph taxonomy, line 240) by linking to
`documentation-policy.md` instead — demonstrating the target end state is
achievable and partially modeled already.

**Full-corpus baseline** (confirmed 2026-09-20): running
`uv run python tools/check_docs_quality.py` against the entire `docs/` tree
takes ~1.87 seconds wall-clock, reports 229 total warnings, 206 of which
are existing within-file "Content similarity detected" findings. This is
the baseline against which both correctness (within-file findings
unchanged) and performance (no material regression) are measured.

## Problem
No existing tool detects that the same substantive content has been copied
into more than one `docs/*.md` file. `check_content_similarity` has the
right underlying mechanism already built, tested, and even already
receiving the full corpus as input — its scope is artificially limited to
within-file comparisons by its own loop structure, not by any architectural
constraint.

## Reason for change
Cross-file rule duplication carries the same drift-risk category the
existing within-file check already guards against, evidenced concretely:
the governance_01/governance_04 duplication has already begun to diverge
(one file has a bullet — a `GV-020`-related non-blocking condition — the
other lacks), confirmed unchanged during this Plan's own verification.

## Implementation intent
Extend `check_content_similarity` in place (not a new sibling function,
per this Plan's Design decision — see Design) to perform two comparison
passes over the same extracted-sections data: (1) the existing within-file
pass, left byte-for-byte unmodified, and (2) a new cross-file pass that
compares every section from one `DocFile` against every section from every
other `DocFile` in the same `files` list, using the identical
`_compute_section_similarity` call and the identical minimum-body-non-empty
guard the within-file pass already uses. Extract each document's sections
once (already how the existing code works — no double-extraction), and
build the cross-file comparison from that same per-document sections cache
rather than re-parsing. Report a cross-file finding with a message format
distinguishable from the within-file one (e.g. naming both files:
`"Content similarity detected between {file_a}#{heading_a} and
{file_b}#{heading_b}"`).

After implementing the naive cross-file comparison (reusing the existing
0.85 threshold unchanged), run it against the full `docs/` tree as a
mandatory Implementation step and manually review the resulting finding
list. Only if that review finds the noise level unacceptably high (many
findings on generically-similar-by-design sections, e.g. "Related
Documents" or "Keywords" headings, rather than genuine rule duplication),
add a targeted mitigation: a small heading-name exclusion list (skip
sections whose heading, case-insensitively, is a known-generic name) and/or
a minimum body-length filter — whichever the actual observed noise pattern
calls for, not both preemptively.

## Design
This is a small, single-module Plan (2 target files) — Path A per
`skills/issue-to-plan/SKILL.md` Routing (≤3 files, no public/runtime
interface change — this is an internal report-only tool's warning-message
text, not a public API — no DB schema change). Direct-verification
inspection only was performed.

- **In-place extension vs. sibling function**: see Assumptions — chosen to
  avoid re-extracting sections per document.
- **Correctness-preservation strategy**: the existing within-file loop
  (`for i in range(len(sections)): for j in range(i+1, len(sections))`,
  operating on one `doc`'s own `sections` list) is left completely
  untouched in the implementation; the new cross-file loop is additive code
  operating on a second, separately-built data structure (all documents'
  sections, tagged with their owning `DocFile`), so there is no code path
  where the new logic could alter an existing within-file comparison's
  inputs, iteration order, or output. This is why AC-2 can assert the exact
  same 206-count rather than merely "no fewer than 206."
- **Noise-mitigation strategy**: deliberately deferred to an empirical,
  post-implementation review (REQ-003, UNK-01) rather than speculatively
  designed now — the source Issue's own Unresolved Questions named specific
  candidate mitigations (heading exclusion, minimum body length) without
  picking one, since neither is justified without seeing actual full-tree
  output from the real implementation. Implementing first and measuring
  avoids over-engineering a mitigation the actual data might not need, or
  under-engineering one a different noise pattern actually requires.
- **Performance**: the existing full corpus is small enough (~1.87s for the
  entire tool, all checks) that even a naive O(total-sections²) cross-file
  pass is expected to remain fast in absolute terms; no memoization or
  indexing structure is planned unless the full-tree run in Implementation
  step (Phase 2) shows an actual, material slowdown — matching the source
  Issue's own Constraints ("do not over-engineer... at the current corpus's
  actual size").

## Risks
- **Risk**: The cross-file pass produces excessive noise on generically
  similar sections (e.g. "Related Documents", "Keywords", or numbered
  subsection scaffolding repeated by convention across many unrelated
  files), making the check's output too noisy to be useful signal →
  **Mitigation**: Phase 2's mandatory review step (UNK-01) catches this
  before the Plan is considered complete; a scoped mitigation (heading
  exclusion list or minimum body length) is added only if actually needed,
  per Design.
- **Risk**: All-pairs cross-file comparison at full corpus scale is slow
  enough to make the tool impractical for routine use → **Mitigation**:
  Phase 2's performance check (AC-3) catches this; the corpus's current
  small absolute size (~1.87s baseline for the whole tool) makes a severe
  regression unlikely, but the check is still mandatory before considering
  the Plan complete.
- **Risk**: A future contributor mistakes a new cross-file finding for a
  false positive and disables the check entirely, discarding its value for
  genuine cases like the governance_01/governance_04 duplication →
  **Mitigation**: this Plan's Design section and the new function's own
  docstring (to be written during implementation) should record the
  governance_01/governance_04 case as a concrete example of a true
  positive, so a future reviewer has a reference point.
