# Plan: Consolidate duplicated token-ratio constants in context_view.py

## Goal

Remove the duplicated character-to-token ratio constants (`_RATIO_TEXT`, `_RATIO_TOOL_CALL`,
`_RATIO_SYSTEM`) currently redefined inside `scripts/agent/services/context_view.py`'s
`_token_breakdown` function, and make it import the canonical `RATIO_TEXT`, `RATIO_TOOL_CALL`,
`RATIO_SYSTEM` constants from `scripts/shared/token_estimation.py` instead. This closes a
maintenance/correctness risk (two independently-maintained copies of the same ratio values that
could silently diverge) without changing any observable behavior.

## Scope

### In-Scope
- `scripts/agent/services/context_view.py`: add module-level import of `RATIO_TEXT`,
  `RATIO_TOOL_CALL`, `RATIO_SYSTEM` from `shared.token_estimation`; remove the three local
  `_RATIO_*` constants inside `_token_breakdown`; substitute the four usages of the old names
  with the imported ones.
- Adding a unit test that exercises `_token_breakdown` directly (or via `_build_budget` /
  `collect_context_state` with `token_is_exact=False`) with a representative mixed message list,
  asserting the token counts match the pre-change values, since no existing test currently covers
  this code path.
- Re-running the full affected test set plus lint/type/security checks on both changed files.

### Out-of-Scope
- Any change to the numeric ratio values (`4.0` / `2.5` / `3.5`) themselves — that is a behavior
  change, explicitly excluded by the requirement.
- Any change to `scripts/shared/token_estimation.py`'s public constants or function signatures —
  this plan only adds a consumer, it does not modify that module's contract.
- The optional Step 5 in the requirement (replacing the inline `int(len(text) / ratio)`
  expressions inside `_token_breakdown` with calls to `estimate_tokens_for_text`) — see Design
  section for why this is deliberately not attempted in this pass.
- Any change to `ContextBudget`'s field names/shape (`token_system`, `token_history`,
  `token_tool_messages`) or to `budget_breakdown`'s character-counting logic.
- Any docs/*.md update — this is a pure internal duplication removal with no interface change,
  so no `docs/00_index.md` §タスク別ドキュメント参照 target applies.

## Assumptions

- The two ratio-constant sets are currently value-identical (`4.0`/`2.5`/`3.5` in both files),
  confirmed by direct source reading of both files during this planning pass — this is a pure
  refactor, not a bugfix.
- `context_view.py`'s existing imports from `shared.git_helper`, `shared.json_utils`, and
  `shared.types` establish that `agent/services/` importing from `shared/` is the established,
  already-used pattern in this file — the new import follows the same convention.
- No other module redefines these ratio constants independently (only `token_estimation.py` and
  `context_view.py` were named in the requirement and found via `rg` search below).

## Design

`context_view.py` already follows the layering convention used throughout `scripts/agent/`:
business-logic modules under `agent/` import shared, side-effect-free helpers from `shared/`
(confirmed here by the file's existing `from shared.git_helper import get_repo_info`, `from
shared.json_utils import serialized_length, tool_call_serialized_length`, and `from shared.types
import LLMMessage` imports at the top of the file). The `.importlinter` contract enforces the
inverse direction only ("shared must not import from agent, mcp_servers, rag, or db" —
confirmed via `PYTHONPATH=scripts uv run lint-imports`, which currently reports 4 kept
contracts and 1 pre-existing unrelated break in `eventbus`, untouched by this plan). Adding
`from shared.token_estimation import RATIO_TEXT, RATIO_TOOL_CALL, RATIO_SYSTEM` to
`context_view.py`'s existing `from shared...` import group is therefore architecturally
consistent — no new import-boundary risk.

Inside `_token_breakdown` (`scripts/agent/services/context_view.py:93-133`), the three local
constants are used at exactly four call sites: `_RATIO_SYSTEM` (line 119, system-role text),
`_RATIO_TEXT` (line 122, assistant text when tool_calls present; line 127, tool-role text; line
131, user/plain-assistant text), and `_RATIO_TOOL_CALL` (line 124, serialized tool-call JSON).
Substituting the imported names for the local ones is a pure identifier rename — no arithmetic,
branching, or return-shape change. `radon cc scripts/agent/services/context_view.py -s` currently
grades `_token_breakdown` as `C (14)` — the highest complexity in the file — but this plan's
change does not touch any branch or loop, so the complexity grade is expected to stay the same
(no new branches added; two lines removed for the constant deletions, ~3 lines changed for the
substitutions).

The optional dedup with `estimate_tokens_for_text` (requirement Step 5) is intentionally not
implemented: that function's signature is `(text, breakdown_key, ratio, breakdown: dict[str,
int])` and mutates a caller-supplied dict keyed by `token_estimation.py`'s own categories
(`"text"`, `"tool_calls"`, `"system"`). `_token_breakdown`'s bucket semantics differ (its `role ==
"tool"` branch routes into `tool_tokens`, i.e. the display "tool_messages" bucket, not the
generic `"text"` key `estimate_tokens_for_text` would use) — forcing reuse here would mean either
restructuring `_token_breakdown`'s per-role routing or passing a throwaway dict per call site
purely to satisfy the function signature, with no additional duplication removed beyond what the
constant import already achieves. This matches the requirement's explicit guidance to skip the
optional step when it would require restructuring bucket semantics.

## Risks

- **Risk**: The new test asserting exact token counts could be brittle if a future ratio-constant tuning is intentional (the test would then "correctly" fail, requiring an update) → **Mitigation**: document in the test's docstring that it is an equivalence/regression guard tied to the current ratio values, not a spec of what the ratios must forever be — likelihood: low.
- **Risk**: A reviewer expects the optional Step-5 dedup (function-level reuse via `estimate_tokens_for_text`) to be implemented since it's mentioned in the requirement → **Mitigation**: the Design section above documents concretely why it was skipped (bucket-key mismatch, no net duplication removed); reference this plan's Design section in the PR description — likelihood: low.
- **Risk**: Import addition could be misplaced relative to ruff's isort-compatible import-order rule (`I` rules) causing a lint failure → **Mitigation**: run `uv run ruff format` immediately after adding the import and before finalizing the diff; `ruff check` will auto-fix or flag ordering issues — likelihood: low.
- **Risk**: The pre-existing `eventbus` import-linter break could be mistaken for a regression introduced by this change during review → **Mitigation**: Implementation step 3 explicitly checks `lint-imports` output against the documented pre-existing baseline (4 kept / 1 broken, `eventbus`-only) so the diff in contract status is confirmed to be zero — likelihood: low.

No risk in this list requires mitigation beyond this plan's scope, so no `issues/*_risks.md` filing was needed.
