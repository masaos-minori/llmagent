# Plan: Extend duplicate-heading detection to alphabetic-suffix numbering and add merge-boundary content-similarity check

## Goal
Extend `tools/check_docs_quality.py` to detect alphabetic-suffix duplicate headings (e.g., `## 7c.` appearing twice at the same level) and add a content-similarity check to flag sections with heavily overlapping prose, catching merge-boundary duplication defects.

## Priority
Medium

## Scope
- **In-Scope**: 
  - Extend `check_duplicate_heading_numbers` regex to match alphabetic-suffix numbering (`2a.`, `2b.`, etc.) and flag same-base-number duplicates
  - Add a new `check_content_similarity` core check that flags sections within the same document whose body text overlaps above a threshold
  - Create tests covering true-positive and false-positive cases for both checks
  - Register both checks with the existing `@register_core_check` mechanism
- **Out-of-Scope**: 
  - Retroactively scanning all of `docs/` for existing content-similarity duplicates
  - Any change to `check_duplicate_heading_numbers`'s existing purely-numeric detection behavior
  - Adding cross-document content-similarity checks (only intra-document)

## Background
`tools/check_docs_quality.py`'s `check_duplicate_heading_numbers` uses the regex `\d[\d.]*\.` which only matches purely-numeric heading numbers. Alphabetic-suffix numbering (e.g., `## 2a.`, `## 2b.`) is invisible to this check. Adversarial verification confirmed this gap causes real undetected defects: `docs/90_shared_02_02_types_and_protocols-tool-and-execution-dto.md` contains two `## 7c.` headings (lines 54 and 87) with different content, and 28 alphabetic-suffix headings exist across the docs tree. Additionally, no tool checks whether content merged at a document's section boundary introduces duplicated prose.

## Problem
The current `check_duplicate_heading_numbers` regex `^(#{1,6})\s+(\d[\d.]*\.)\s+` only matches digits and dots — `## 2.` matches but `## 2a.` does not. Running `uv run python tools/check_docs_quality.py --only duplicate_heading_numbers` reports zero issues despite the `## 7c.` duplicate being present. No tool exists for content-similarity-based merge-boundary duplication detection.

## Reason for change
An automated check that only catches the purely-numeric case leaves the alphabetic-suffix case undetected until manual review happens to notice it. A content-similarity check would catch the underlying failure mode (repeated content from independent edits landing in the same document).

## Implementation intent
1. Add a SECOND regex pattern alongside the existing purely-numeric one: `r"^(#{1,6})\s+(\d+[a-z]+)\.\s+"` for alphabetic-suffix headings (`## 2a.`, `## 2b.`). Keep the original `r"^(#{1,6})\s+(\d[\d.]*\.)\s+"` unchanged. Group headings by `(level, base_number)` where base_number = digits before the alphabetic suffix (e.g., `2a` → base `2`). Flag pairs where base numbers match but full heading numbers differ (e.g., `## 2.` and `## 2a.` at the same level). The two regexes are mutually exclusive — no overlap between pure numeric and alphabetic-suffix patterns.
2. Add a new `check_content_similarity` function that extracts section bodies, computes pairwise similarity using token overlap (e.g., Jaccard similarity on word tokens), and flags pairs exceeding a configurable threshold.
3. Place shared similarity-computation utility as a private helper in `check_docs_quality.py`; place both check functions in `check_docs_quality.py` using the existing `@register_core_check` pattern.
4. Create `tests/tools/test_check_docs_quality.py` with test cases for both checks.

## Requirements
- `REQ-001`: The extended check detects same-base-number, same-level headings with differing alphabetic suffixes (e.g., `2.`/`2a.`/`2b.`) as a probable near-duplicate.
- `REQ-002`: The extended check does not flag legitimate numeric subsections (`2.1`, `2.2`) as duplicates.
- `REQ-003`: The content-similarity check flags two sections in the same document whose body text overlaps above a defined threshold.
- `REQ-004`: The content-similarity check does not flag legitimately repeated boilerplate (e.g., templated Verification/Out-of-Scope sections).
- `REQ-005`: Both checks run as part of `tools/check_docs_quality.py`'s standard invocation with no changes to how the tool is called.
- `REQ-006`: Tests cover true-positive and false-positive cases for both checks, including the known `## 7c.` duplicate.

## Assumptions
- The alphabetic suffix follows the pattern `[a-z]+` (lowercase letters only), consistent with the observed `## 7c.` pattern.
- Content similarity will use token-level Jaccard similarity (intersection over union of word sets) on section body text, which is simple and avoids dependency on external NLP libraries.
- The content-similarity threshold should be set conservatively (e.g., 0.8–0.9) to avoid false positives on short, intentionally-templated sections; the exact value should be validated empirically during implementation.
- Section boundaries are determined by Markdown heading markers (`#` through `######`), consistent with the existing heading-detection logic.
- The existing `@register_core_check` decorator mechanism in `check_docs_quality.py` is the correct registration point for both checks.
- The `_compute_section_similarity` utility is placed as a private helper in `check_docs_quality.py` rather than in `_docs_consistency_lib.py`, because the latter's existing functions all follow the `(docs_dir: Path, files: list[DocFile]) -> list[Issue]` signature which does not match a pure text similarity utility.

## Design
**Path A classification**: This task affects exactly 3 files, introduces no public/runtime interface changes (the CLI remains unchanged; only new checks are added), and makes no database schema changes. Architecture analysis, dependency graphing, historical analysis, and operational dependency inspection are skipped per Path A rules.

**Alphabetic-suffix detection design**: Use TWO mutually exclusive regex patterns instead of one: (1) keep the original `r"^(#{1,6})\s+(\d[\d.]*\.)\s+"` for purely-numeric headings (`## 2.`, `## 2.1`); (2) add `r"^(#{1,6})\s+(\d+[a-z]+)\.\s+"` for alphabetic-suffix headings (`## 2a.`, `## 2b.`). These do not overlap — a heading like `## 2.1` matches only the first pattern, while `## 2a.` matches only the second. For the alphabetic-suffix check, extract the base number (digits before the alphabetic suffix, e.g., `2a` → base `2`) and group by `(level, base_number)`. Flag pairs where base numbers match but full heading numbers differ (e.g., `## 2.` and `## 2a.` at the same level). This avoids the critical flaw of parsing `## 2.1` as base number `2` with empty suffix.

**Content-similarity design**: Extract section bodies using Markdown heading markers. Compute pairwise Jaccard similarity on word-token sets for sections within the same document. Flag pairs exceeding the threshold. Skip fenced code blocks and inline code. Use a conservative threshold (validated empirically) to minimize false positives on templated sections.

**Shared utility placement**: The similarity-computation logic goes in `check_docs_quality.py` as a private helper function (`_compute_section_similarity`). This avoids placing it in `_docs_consistency_lib.py`, whose existing functions all follow the `(docs_dir: Path, files: list[DocFile]) -> list[Issue]` signature — a pure text similarity utility doesn't fit this pattern. Both check functions are registered via `@register_core_check`.

## Risks
- **Risk**: Content-similarity threshold too low → excessive false positives on templated sections → user trust erosion → **Mitigation**: Set initial threshold conservatively (0.85+); validate empirically against full `docs/` tree before finalizing; allow threshold adjustment via config if needed.
- **Risk**: Content-similarity threshold too high → miss real merge-boundary defects → **Mitigation**: Validate against known defect case (`## 7c.` duplicate has different content, so similarity check should catch similar-but-not-identical sections); adjust threshold based on empirical results.
- **Risk**: Regex edge cases — headings like `## 2.1a.` or `## 2a1.` — **Mitigation**: Two mutually exclusive patterns eliminate the original flaw: `(\d[\d.]*\.)` handles `## 2.1` (pure numeric subsection), `\d+[a-z]+\.` handles `## 2a.` (alphabetic suffix). A heading like `## 2.1a.` does not match either pattern and is silently skipped (acceptable — such edge cases can be handled later if needed).
