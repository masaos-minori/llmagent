# Plan: Replace Dual Tool Execution Paths with One Correct DAG Execution Plan

## Goal

Replace the two disagreeing tool-execution engines in `scripts/agent/tool_runner.py`
(`_execute_standard()` gated by `is_side_effect()`/`SHELL_TOOLS`, and `_execute_with_dag()`
gated by `ToolSpec`/`build_execution_groups()`) with a single deterministic DAG execution
planner that is the sole execution path for every prepared, approved tool-call batch. Fix
the eight concrete correctness defects in the current `build_execution_groups()` (scope-less
writes racing each other, `requires_serial` calls hoisted out of position, reads never
conflicting with writes, tool-name-keyed metadata, desyncable parallel arrays, a
metadata-vs-return-value split the runner only half-uses, over-firing/misreporting audit
events) so concurrent tool execution is actually safe and its audit trail is actually
truthful.

## Scope

### In-Scope
- Delete `_execute_standard()` (`scripts/agent/tool_runner.py:423-503`) and the
  `serial_tool_calls` branch in `execute_all_tool_calls()` (`tool_runner.py:526-530`).
- Rewrite `build_execution_groups()` (`scripts/agent/tool_scheduler.py:70-189`) into a
  phase-building planner that: preserves original call order; treats `requires_serial` as
  an in-place barrier (not a leading bucket); includes reads in conflict detection; replaces
  the `write_first`/no-scope bucket with a `global:write` scope that conflicts with every
  other state-changing call in its phase; is keyed by `call_id`, not tool name.
- Replace `ScheduledBatch(groups: list[list[dict]], serialize_flags: list[bool])` and the
  `(groups, metadata)` two-return-value shape with bound dataclasses (`ScheduledGroup`,
  `ScheduledBatch`, `ExecutionPlan`) so execution mode can never separate from its calls.
- Add a `force_serial` planner input, replacing today's `ctx.cfg.tool.serial_tool_calls`
  branch-selection use; when true, emit one sequential phase per call in original order with
  reason `forced_serial`.
- Correct serialization-event emission: only when concurrency was actually prevented,
  explicit reason codes (`forced_serial`, `requires_serial`, `resource_read_write_conflict`,
  `resource_write_write_conflict`, `global_write_scope`), real `is_write` (never hard-coded).
- Update `ToolConfig.serial_tool_calls` docstring (`scripts/agent/config_dataclasses.py:161`)
  to describe the single-engine, force-serial semantics.
- Update `_execute_with_dag()` (`scripts/agent/tool_runner.py:315-420`) to consume one
  `ExecutionPlan` and restore results to original call order before they reach
  `_collect_tool_result_msgs()`.
- Rewrite the four tests that currently assert the eight defects as correct
  (`tests/agent/test_tool_scheduler.py:61-72,293-305`,
  `tests/agent/test_tool_scheduler_serialization.py:93-101,112-120`) plus the new tests listed
  in the requirement's Tests section.

## Design

**Layering.** `tool_scheduler.py` and `tool_runner.py` both live in `scripts/agent/`
(agent layer), which is already permitted to import `scripts/shared/` (leaf layer) —
`lint-imports` currently reports zero violations touching these two files (the only
existing `lint-imports` violations are pre-existing `eventbus`→`shared`/`db` boundary
breaks, unrelated to this change; verified via `PYTHONPATH=scripts uv run lint-imports`).
Importing `shared.resource_scope`'s scope-overlap predicate (once Issue 01 lands it) from
`tool_scheduler.py` keeps that predicate in exactly one place and respects the existing
import direction; do not duplicate ancestor/descendant path comparison inside
`tool_scheduler.py`.

**Planner input contract.** Today `build_execution_groups(tool_calls: list[dict],
tool_meta: dict[str, ToolSpec])` takes raw `tc["function"]["name"]`-keyed lookups
(`tool_scheduler.py:90-96`) built by `_build_tool_meta()` from
`ctx.cfg.tool.tool_definitions` (`tool_runner.py:60-79`) — a tool-name-keyed, static,
optionally-absent map. The new signature takes `call_specs: dict[str, ToolSpec]` keyed by
`call_id`, sourced from `PreparedToolCall.spec` (Issue 02) once that lands:
```python
tool_meta_by_call_id = {pc.call_id: pc.spec for pc in prepared_calls}
```
A `call_id` with no entry in `call_specs` must raise (`KeyError` propagated or a dedicated
`SchedulingError`), never fall back to a synthetic all-`False` `ToolSpec` — this removes the
current `meta = tool_meta.get(name)` / `if meta is not None else` defaulting pattern
throughout `tool_scheduler.py:91-102` and `tool_runner.py:334-343`.

**Phase-building algorithm** (replaces the current four-bucket
serial_barrier/resource_groups/write_first/parallel split):
1. Walk `tool_calls` in original order, accumulating a `current_phase: list[ToolSpec]`.
2. On a `requires_serial=True` call: close `current_phase` (if non-empty) as a normal
   phase, emit the serial call as its own single-call phase (reason `requires_serial`,
   real `is_write`), start a fresh `current_phase`.
3. On any other call: if it is state-changing (`is_write=True`) with `resource_scopes ==
   ()`, treat its scopes as `("global:write",)` per Issue 01's `resolve_resource_scopes()`
   contract (this planner does not invent the fallback itself — it consumes the tuple
   `PreparedToolCall.spec` already carries); append to `current_phase`.
4. Close any trailing `current_phase`.
5. Within each normal phase, build a conflict graph: for every pair, if either side is a
   write and any of their `resource_scopes` overlap (via the shared overlap predicate,
   equal-or-ancestor/descendant), they conflict; read/read pairs never conflict. Partition
   the phase into `ScheduledGroup`s such that conflicting calls land in the same
   sequential group and non-conflicting calls can share a concurrent group. (Simplest
   correct construction: union-find over conflict pairs → one sequential `ScheduledGroup`
   per connected component with `len > 1`, one concurrent `ScheduledGroup` for the
   remaining singletons all pooled together with `sequential=False`.)
6. `force_serial=True` short-circuits all of the above: emit one phase per call, in
   original order, each phase a single-call `ScheduledGroup(sequential=True, reason=
   "forced_serial")`.

**Result-order restoration.** `_execute_with_dag()` already sorts by `call_order` at
`tool_runner.py:373` (`results.sort(key=lambda r: call_order.get(r[0], 0))`) — this
mechanism is correct and is retained unchanged; only the loop that produces `results` (over
`ExecutionPlan.batches` instead of `metadata.concurrent_groups`) changes.

**Audit-event correctness.** `SerializationEvent` gains no new fields beyond what
`_SerializationEvent` already has (`trigger_tool`, `reason`, `tools_count`,
`resource_scope`→pluralized or kept singular-per-event-since-one-conflict-pair,
`is_write`, `requires_serial`, `scheduling_decision`); the fix is behavioral: only emit
when `len(group.calls) > 1` or a barrier actually displaced calls, and always source
`is_write` from the triggering call's real `ToolSpec.is_write` instead of the current
hard-coded `True` (`tool_scheduler.py:151`).

## Risks

- **Risk**: Implementing this plan before Issue 01 (`plans/20260813-183049_plan.md`) or
  Issue 02 (`plans/20260813-184037_plan.md`) has landed forces either inline reimplementation
  of `resource_scopes`/`PreparedToolCall` (recreating the duplication this three-issue chain
  exists to remove) or a stalled Phase 2. — **Mitigation**: Implementation Step 1 is an
  explicit verification gate that halts before any `tool_scheduler.py` rewrite if either
  precondition is missing. Likelihood: med (three plans were generated in the same session
  and may be picked up out of order by an implementer).
- **Risk**: The union-find/connected-component grouping in the new phase-building algorithm
  is a new, non-trivial piece of logic (`build_execution_groups()` is already graded `D
  (23)` cyclomatic complexity by `radon` before this rewrite) and could introduce a subtle
  correctness bug (e.g. transitive conflicts not merged into one group) that ships in place
  of the eight documented defects. — **Mitigation**: the requirement's own Tests section
  enumerates the exact conflict scenarios (same-scope R/W, W/W, R/R, ancestor/descendant,
  different-scope concurrency) as required test cases; treat 100% of those as a merge gate,
  not optional coverage. Likelihood: med.
- **Risk**: Removing `_execute_standard()` removes the only remaining live consumer of
  `is_side_effect()`/`SHELL_TOOLS` for *scheduling* purposes, but both are also used
  elsewhere for approval-tier classification (per Issue 01's requirement text, instruction
  10) — an over-eager removal could break approval-tier classification, which is out of
  this plan's scope. — **Mitigation**: `grep`-verify remaining `is_side_effect()`/
  `SHELL_TOOLS` usages before deleting any import, per Issue 01's own instruction 10
  ("verify with grep before deleting"); only remove the scheduling-path import from
  `tool_runner.py:26`, not the helper definitions themselves. Likelihood: low.
- **Risk**: `diagnostic_store.py::save_serialization_event()` callers elsewhere (verified
  consumers: `tests/agent/test_diagnostic_store.py`,
  `tests/agent/test_diagnostic_store_security.py`, `cmd_mcp.py`, `context.py`) could be
  affected if the new reason codes or event cardinality change what gets persisted in ways
  those tests don't expect. — **Mitigation**: `save_serialization_event()`'s signature
  takes primitive values, not the event dataclass, so no signature change is needed; run
  `tests/agent/test_diagnostic_store*.py` as part of the targeted validation pass in
  addition to the scheduler/runner tests. Likelihood: low.
