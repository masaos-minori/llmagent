## Goal
- Make a failing slash-command handler surface as a command-scoped error (named command, usage-aware tag, log entry) instead of a turn-level `[fatal]` failure.

## Priority
Medium

## Scope
- **In-Scope**:
  - Catching handler-invocation errors at the `CommandRegistry` dispatch boundary.
  - Rendering them through the existing `OutputPort.write_error` / `write_validation_error` methods with the matched command name and its usage line.
  - Mapping `sqlite3.Error` from storage-touching commands to a message that names the subcommand and states the effect may be partial.
  - Logging the attributed command error.
  - Regression tests for the command-error surface and for the unchanged turn-failure `[fatal]` surface.
  - Documenting the REPL output tag taxonomy (`[fatal]` vs `[error]` vs `[usage]` vs `[non-fatal]`) and which component emits each.
- **Out-of-Scope**:
  - Argument parsing/validation rules (filed separately as `cmd002`).
  - Event-loop blocking and cancellability of command handlers (`cmd003`).
  - Adding new commands or changing command output layouts.
  - Changing `[fatal]` semantics for turn-level failures, and `_surface_turn_error` behavior.

## Background
`CommandRegistry.dispatch()` has no error handling: `_invoke_handler` calls the handler and any exception propagates. `ReplInputLoop._dispatch_line` does not catch it either, so the per-turn `except Exception` in `_repl_loop` handles it and `_surface_turn_error` renders `self._view.write_fatal(f"{exc.__class__.__name__}: {exc}")` using the `[fatal]` tag.

## Problem
- A command error and a turn failure share one output channel and one tag. `FATAL`, `NON_FATAL`, `ERROR` and `USAGE` all exist as distinct tags, and the command output port already exposes `write_error` and `write_validation_error` (the latter renders `[usage]`), but no command path uses them for a dispatch failure.
- No command module handles database errors: `grep -rn 'sqlite3|OperationalError|IntegrityError' scripts/agent/commands/` returns no source matches, so a `sqlite3.Error` from `/session delete`, `/session purge`, `/session vacuum` or `/memory prune` surfaces as `OperationalError: …` with no statement of which subcommand failed or whether anything changed. Several of these mutate state before failing.
- The exception type name is the only message, which is unreadable for an operator and not attributable to a command in logs.
- Unknown-command handling is the one path that already behaves correctly (`write_warning` with a `/help` hint), showing the intended pattern is a command-scoped message.

## Reason for Change
Commands are the operator's main interface. Reporting an input or storage problem as a fatal turn failure makes an ordinary mistake look like a session-ending error and hides what actually went wrong.

## Implementation Intent
Handle command dispatch errors where the command boundary is: classify them inside `dispatch()` around the handler invocation only, render them through the existing error/usage severities with the matched `CommandDef` name and its `usages()` line, and log the attributed error. Do not move error handling into the REPL loop.

## Requirements
- `REQ-001`: `CommandRegistry.dispatch()` catches exceptions raised by a matched handler invocation and, after rendering the error, returns `True` (the line was matched) instead of propagating. The `not isinstance(line, str) -> TypeError` guard and the `bool` return contract are unchanged, and handler *lookup* (`_get_handler`) stays outside the guarded region.
- `REQ-002`: A rendered command error names the matched command (`CommandDef.name`) and, for prefix commands, includes the usage line from `CommandDef.usages()`.
- `REQ-003`: Command domain errors that describe bad input (`CommandValidationError`, `CommandParseError`, and their subclasses such as `UnknownPresetError` / `UnknownTierError`) render through `write_validation_error` (`[usage]`); every other handler exception renders through `write_error` (`[error]`). Tag strings in `scripts/agent/output_tags.py` are not changed.
- `REQ-004`: A `sqlite3.Error` raised by a handler renders through `write_error` with the command name and an explicit statement that the effect may be partial.
- `REQ-005`: Every handled error produces a log entry that names the command and the exception type (module `logging` logger, matching the pattern already used in `cmd_config.py` / `cmd_mcp.py` / `cmd_memory.py`).
- `REQ-006`: Turn failures keep their current surface: `_surface_turn_error` still renders `[fatal]` for non-command failures, and no command-handler error reaches it.
- `REQ-007`: Regression tests assert the tag and the presence of the command name (assertions on tags, not message bodies), plus the unchanged `[fatal]` behavior for a turn failure.
- `REQ-008`: The REPL output tag taxonomy and the component that emits each tag are documented.

## Design
Path A (small task): 3 files, no new module, no DB schema change, `dispatch()`'s public signature and `bool` return contract unchanged — the change is confined to how a matched handler's exceptions are surfaced. Step 3's direct verification bounds the blast radius: no test calls `dispatch()` and asserts an exception propagates (`tests/agent/commands/test_command_def_sync.py` lines 112-188 either assert the `bool` result or call handlers directly), and the six test call sites that construct `CommandRegistry` reach the new error path only when a handler raises.

Design decisions, grounded in Step 2/3 evidence:
- The guard wraps only the handler invocation (`_invoke_handler`), not handler lookup: `__init__` (lines 67-72) already fail-fasts on missing handlers, and `_get_handler` failures are a registry-integrity bug, not a command error.
- `CommandDef`-driven attribution: the matched `CommandDef` is in scope at the catch site, so the command name and `usages()` line come from the declarative registry rather than from re-parsing the line.
- Classification uses the existing domain hierarchy in `scripts/agent/commands/exceptions.py` (`ValueError`-derived command validation → `[usage]`), plus an explicit `sqlite3.Error` branch → `[error]` with a partial-effect statement, plus a final `Exception` branch → `[error]`. `BaseException` is not caught, so `asyncio.CancelledError` and `KeyboardInterrupt` keep propagating to `_repl_loop`'s shutdown handling (`repl_input_loop.py` lines 254-284).
- Error rendering is factored into a small private helper on `CommandRegistry` so `dispatch()`'s cyclomatic complexity does not grow past its current radon grade B (8).
- Validation quality baseline recorded before implementation: `uv run radon cc scripts/agent/commands/registry.py -s` → `dispatch` B (8), `CommandRegistry` A (5), `__init__` A (4), `_cmd_help` A (3), others A (2); `uv run bandit -c pyproject.toml scripts/agent/commands/registry.py` → 0 findings at all severities; `uv run vulture scripts/agent/commands/registry.py --min-confidence 80` → no findings. `scripts/agent/commands/registry.py` is 5320 B, below the 16384 B module-size gate and absent from `tools/check_module_size_baseline.txt`, so growth is gated by the default limit. No changed-line coverage number exists for this change yet; per `rules/toolchain.md` §7 the Plan requires raising diff-cover coverage for changed lines to the 90% threshold in `rules/toolchain.md`'s Completion checklist.

- **Risk**: Swallowing exceptions at the command boundary could hide real defects that today surface loudly as `[fatal]`. → **Mitigation**: REQ-005 requires a log entry naming the command and exception type for every handled error; the issue's constraint "do not swallow exceptions silently" is enforced by AC-7 and the `caplog` test.

- **Risk**: Message-text coupling in existing tests that assert exact prefixes (issue Constraints). → **Mitigation**: assertions target tags and command-name presence only; existing tag strings in `scripts/agent/output_tags.py` are not modified.
