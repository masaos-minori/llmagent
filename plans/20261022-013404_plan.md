## Goal
- Make every numeric slash-command argument (`/history [n]`, `/session list [n]`, `/session purge --max-sessions/--max-age-days`, `/memory list [n]`) validated by one shared rule set, so a malformed or out-of-range value is reported as a usage error instead of being silently replaced by a default or reinterpreted, and so the amount of data a destructive maintenance command removes is never decided by a misread argument.

## Priority
High

## Scope
- **In-Scope**:
  - One numeric argument parser in `scripts/agent/commands/utils.py` that raises the existing domain
    validation error for invalid/out-of-range input and returns "absent" only for an omitted argument.
  - Adoption of that parser in `_cmd_history`, `_session_list`, `DbSessionOps.purge`, and
    `_parse_list_options`.
  - Removal of the superseded numeric helpers (`utils.parse_flag_int`, `utils.parse_flag_str`,
    `db_session_ops._parse_optional_int`) so that no second numeric rule set remains.
  - Per-command accepted ranges written down and tested, including the bare-flag case and negative values.
  - Deliberate updates of the two tests that currently lock the silent fallback.
  - Documentation of the accepted values in the per-command chapters.
- **Out-of-Scope**:
  - `ArgSpec`/`SubcommandSpec` token names and usage-line rendering (`scripts/agent/commands/command_defs.py`,
    `scripts/agent/commands/command_defs_list.py`).
  - `RetentionConfig` defaults and the retention algorithms in `scripts/db/maintenance.py`.
  - `/memory prune --days` (`memory_data_ops._parse_prune_days`), `/mcp status`, `/token`, `/replay`.
  - Command-error tagging and dispatch-level error handling (decided in `cmd001`).
  - Event-loop blocking and cancellability of command handlers (`cmd003`).

## Background
The issue `issues/20261021-093421_cmd002-invalid-command-args-silently-reinterpreted.md` was verified
against the current tree. Numeric argument handling exists as five independent rule sets:
`cmd_context.py:138-149`, `cmd_session.py:77-88`, `db_session_ops.py:11-16` + `:50-55`,
`memory_data_ops.py:64-88` (`_parse_list_options`), and — as the only correct example — the 1..200
bounds check at `memory_data_ops.py:86-88`. `utils.py:60-68` (`parse_flag_int`) and `utils.py:71-76`
(`parse_flag_str`) exist, are exported in `__all__` (`utils.py:15-20`), and have no call sites.

## Problem
- `/history [n]` slices with any integer: `n = int(raw)` at `cmd_context.py:143`, `recent = turns[-n:]`
  at `:149`. `/history 0` prints every message (`turns[-0:]`), `/history -3` prints the oldest messages.
  Non-integers already produce a usage error (`:144-145`); out-of-range values do not.
- `/session list abc` becomes 20 with no message (`cmd_session.py:85-87`). Negative limits reach
  `Session.list_sessions`'s `LIMIT ?` (`scripts/agent/session.py:183-185`).
- `_parse_optional_int` (`db_session_ops.py:11-16`) cannot distinguish "absent" from "invalid", and a
  bare `--max-sessions` parses as `True` (`utils.py:43-50`) → `int(True) == 1` → keeps exactly one
  session. Verified against the retention implementation: `--max-sessions 0` deletes every session
  (`maintenance.py:185-202`, `len(rows) <= 0` is false, `rows[0:]`), `--max-sessions -3` deletes only
  the 3 oldest (`rows[-3:]`), while `--max-age-days 0` or a negative value means "disabled"
  (`maintenance.py:167-170`). `None` is the only value that selects the `RetentionConfig` defaults
  (`max_sessions=100`, `max_age_days=90`, `maintenance.py:104-105`) via `_build_retention_config`
  (`scripts/agent/services/db_maintenance_service.py:87-96`).
- Accepted token grammar differs: `/memory list` requires `tok.isdigit()` (`memory_data_ops.py:85`),
  accepting `'٣'`/`'１'` and rejecting `'+5'`/`'1_0'`, while the other paths use `int()`.

## Reason for Change
Silent reinterpretation makes operator mistakes invisible, and for `/session purge` it silently changes
how much data a destructive command deletes. The repo already contains one correct bound check
(`/memory list`), so the fix is consolidation, not invention.

## Implementation Intent
State the numeric rules once, in the module that already owns command token parsing, and let each command
call it with its own bounds and usage string. Distinguish three outcomes strictly: absent (use the
documented default), valid (use the value), invalid (usage error and no action).

## Requirements
- `REQ-001`: `scripts/agent/commands/utils.py` exposes one numeric argument parser with the signature
  `parse_int_arg(raw: str | bool | None, *, usage: str, default: int | None = None, minimum: int | None = None, maximum: int | None = None) -> int | None`.
  It returns `default` when `raw` is `None` (argument absent), returns the parsed value when it is within
  bounds, and otherwise raises `agent.commands.exceptions.CommandValidationError` (`exceptions.py:13`). It
  never returns a default in place of an explicitly invalid value, and `None` as a return value means only
  "absent and no default".
- `REQ-002`: `utils.parse_flag_int` and `utils.parse_flag_str` and `db_session_ops._parse_optional_int`
  are removed together with their `__all__` entries, so no numeric parse path other than `parse_int_arg`
  remains under `scripts/agent/commands/`.
- `REQ-003`: `/history [n]` accepts `1..200`; `0`, negative values, and values above `200` produce a usage
  error and print nothing; omitting `n` keeps the current default of 5.
- `REQ-004`: `/session list [n]` accepts `1..200`; a non-integer, `0`, a negative value, or a value above
  `200` produces a usage error and calls `Session.list_sessions` zero times; omitting `n` keeps 20.
- `REQ-005`: `/session purge` validates `--max-sessions` as an integer `>= 1` (a bare flag, `0`, a negative
  value, and a non-integer are all errors) and `--max-age-days` as an integer `>= 0` (a bare flag, a
  negative value, and a non-integer are errors; `0` keeps its documented "disabled" meaning,
  `maintenance.py:102`, `:169-170`). An absent flag keeps passing `None` so `RetentionConfig` defaults
  still apply. On any invalid value, `DbMaintenanceService.purge` is not called.
- `REQ-006`: `/memory list [n]` uses `parse_int_arg` with `minimum=1, maximum=200, default=20`; the
  1..200 bound is preserved, the accepted grammar becomes the same as every other command (`int()`
  grammar: `'٣'`/`'１'` rejected, `'+5'` accepted), and any other token in that position stays a
  validation error.
- `REQ-007`: Validation failures render through the existing `OutputPort.write_validation_error` with the
  command's existing usage string (`/history [n]`, `/session list [n]`, `/session purge …`,
  `/memory list [n]`); no tag, message format, or output method is added, and `cmd001`'s `[usage]`
  mapping stays the only path a raised `CommandValidationError` can take once it reaches `dispatch()`.
- `REQ-008`: `ArgSpec`/`SubcommandSpec` tokens and `format_usage` output are unchanged; the accepted ranges
  are recorded in prose in the per-command doc chapters, never inside a usage code span.
- `REQ-009`: Every currently valid invocation (`/history` with no argument, `/session list` with no
  argument, `/session purge` with no flags, `/memory list` with no argument, `--max-age-days 0`) behaves
  exactly as today.

## Assumptions
- **A1**: The grammar to standardize on is `int()`-based (a leading sign accepted, underscores per Python literal rules, non-ASCII digits rejected). Four of the five existing paths already use `int()`; `/memory list`'s `isdigit()` is the outlier.
- **A2**: `--max-age-days 0` stays valid because `RetentionConfig` documents `0=disabled` (`maintenance.py:102`, honored at `:169-170`); `--max-sessions 0` is rejected as an operator argument because the implementation treats it as "keep none" (`:188-190`) and no documented meaning exists. Both are verified facts, not guesses.
- **A3**: `1..200` is the reference bound for the display-size arguments, because `/memory list`'s bound is the only one that exists in code and is already documented (`agent_07_10:39`).
- **A4**: Raising `CommandValidationError` and catching it at the call site is safe with existing tests because those tests call handlers directly (`test_agent_cmd_session.py` constructs `_SessionMixin` directly); an uncaught domain error would surface in tests instead of a usage line.
- **A5**: `parse_int_arg` stays free of output/rendering responsibilities: it raises, and the call site renders. This keeps `utils.py` free of an `OutputPort` import and keeps `cmd001`'s boundary intact.

## Design
Path B: one new shared contract adopted by four command modules, an intentional observable behavior change (previously accepted inputs are rejected), and existing tests that lock the current behavior must be rewritten deliberately. Classification evidence: the issue names five independent rule sets, and `grep -rn "parse_flag_int\|parse_flag_str\|_parse_optional_int" scripts tests` shows the two shared helpers are dead while `_parse_optional_int` is live — consolidation cannot be done inside one file.

Design decisions, grounded in the read above:
- `parse_int_arg` raises the declared-but-unused `CommandValidationError` (`exceptions.py:13`) instead of returning `None` or an error string. Returning `None` is exactly the defect (`_parse_optional_int` cannot tell "absent" from "invalid"), and an error-string field would repeat the `ParsedArgs.error` pattern (`utils.py:30`) that no caller checks today. `cmd001`'s Plan already maps `CommandValidationError` to `[usage]`, so the raised type is the one the pipeline is designed to render.
- Each call site keeps its own `try/except CommandValidationError` → `self._out.write_validation_error(<its own usage string>)`. This preserves today's per-command usage text byte-for-byte (`/history [n]`, `/session list [n]`, `/memory list [n]`), keeps handlers testable when called directly, and does not depend on `cmd001` being implemented first. The rules (grammar + bounds) exist once; only the rendering is local.
- Bounds are call-site constants, not fields of `ArgSpec`: adding a range field would change the declarative contract that `tools/check_docs_consistency.py:285-430` and `test_command_def_sync.py:207`/`:219` guard, which is a larger contract change than this issue asks for (UNK-03).
- Absent vs invalid is preserved end to end: `None` still means "flag absent" all the way to `_build_retention_config` (`db_maintenance_service.py:87-96`), so `RetentionConfig` defaults (100 / 90) keep applying only when the operator really omitted the flag.
- `--max-sessions` gets `minimum=1` and `--max-age-days` gets `minimum=0` because the retention layer gives `0` a documented meaning only for the age flag (`maintenance.py:102`, `:169-170`); the destructive `--max-sessions 0` (delete everything) and the confusing `--max-sessions -3` (delete the 3 oldest) become rejected arguments rather than surprises.
- Removing `parse_flag_int`/`parse_flag_str`/`_parse_optional_int` is part of the same plan as adding `parse_int_arg`: the issue's own acceptance criterion is that no second numeric parser remains, and leaving the dead helpers would leave a fifth rule set that the next author can pick by accident.
- Validation quality baseline recorded before implementation: `uv run radon cc scripts/agent/commands/utils.py scripts/agent/commands/cmd_session.py -s -n B` → `parse_command_args` B (6); `_session_list` C (14), `_cmd_session` C (13); `radon cc` on `memory_data_ops.py` → `_parse_list_options` C (13), `memory_list` C (11), `_parse_prune_days` B (8); `_cmd_history` B (9). `uv run vulture scripts/ --min-confidence 80` reports no finding for the two helpers because they are exported in `__all__` — that is the reason they survive today. Module sizes: `utils.py` 2141 B, `cmd_context.py` 6359 B, `cmd_session.py` 10305 B, `db_session_ops.py` 3035 B, `memory_data_ops.py` 15232 B against the 16384 B gate (`tools/check_module_size_baseline.txt` contains only `mcp_servers/mdq/mdq_server.py`), so the near-gate file is `memory_data_ops.py` and this change is net-negative there (it replaces a branch with a call). No changed-line coverage number exists yet; per `rules/toolchain.md` §7 the Plan requires diff-cover coverage of changed lines at the 90% threshold.

## Risks
- **Risk**: Inputs that work today are rejected after the change (`/session list abc`, a bare `--max-sessions`, `--max-sessions 0`, `/history 0`), which could break muscle memory or scripted input. → **Mitigation**: every newly rejected form is enumerated as a test (AC-1..AC-4) and documented in the per-command chapters before shipping; nothing is rejected that is not covered by a test.
- **Risk**: `/memory list`'s accepted grammar widens (`'+5'` becomes valid) while narrowing elsewhere (`'٣'` becomes invalid). → **Mitigation**: REQ-006 makes the direction explicit in both directions with tests, and the doc row states the grammar; UNK-02 records the alternative so the decision is reversible in one place.
- **Risk**: Catching `CommandValidationError` at call sites could mask a real defect the way the current silent defaults do. → **Mitigation**: the catch is limited to `CommandValidationError` only, so `sqlite3.Error` and every other exception keep propagating (`test_purge_error_raises` stays green, AC-6); the rendered message is the command's own usage string, not a generic error.
- **Risk**: Removing `_parse_optional_int` changes a module-level exported helper. → **Mitigation**: `grep -rln "db_session_ops" tests` shows only `test_agent_cmd_session.py` reaches this path, and `grep -rn "_parse_optional_int" scripts` shows no other caller; the removal is a separate step (Step 2's last bullet) so it can be reverted independently.
- **Risk**: `memory_data_ops.py` is 15232 B against the 16384 B module-size gate. → **Mitigation**: the change replaces a branch with a call; the module-size check runs in the validation plan and the net change is expected negative. If it grows, the bounds constants move to the existing module constants block rather than adding code.
- **Risk**: Two commands' doc rows could contradict the `ArgSpec`-derived usage lines the consistency checker compares. → **Mitigation**: ranges go in prose, never inside usage code spans (`tools/check_docs_consistency.py:285-430`), and the docs checkers plus `test_command_def_sync.py` are run in the same step as the edit.
