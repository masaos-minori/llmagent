## Goal

Remove the dead degraded-reason bookkeeping in `McpServerHealthRegistry`
(`record_degraded()`, `get_degraded_reason()`, `_degraded_reasons`) and simplify
`cmd_mcp.py::_write_servers_in_state()` accordingly, because no production code
writes a degraded reason today, so the "degraded reason" ever shown in `mcp
status` output is permanently blank.

## Design

**Decision: (a) remove, not (b) wire in a caller.**

Rationale, grounded in re-verified evidence:
- `record_degraded()` has zero production callers anywhere in `scripts/`
  (re-confirmed 2026-08-19).
- The only production caller of `get_degraded_reason()` is
  `cmd_mcp.py:163`, but since nothing writes `_degraded_reasons` in production,
  that call always returns `None`, making the "degraded reason" column in `mcp
  status` output permanently blank — a real (if minor) UX defect, not just an
  unreachable code path.
- No concrete, already-planned caller exists. The watchdog that used to call
  `record_degraded()` was permanently removed (commit `6bc329cb7`, "feat: remove
  MCP watchdog"), and no plan/doc in the repository proposes reinstating a
  watchdog or adding a new degraded-probe caller. `scripts/agent/services/mcp_status.py`
  (the module that builds `mcp status` rows) does not call `record_degraded()`
  either. Inventing a speculative caller is explicitly disallowed by the
  requirement.
- Per `rules/coding.md`'s Deprecation policy, a zero-caller `rg` re-check at the
  time `plans/` touches the file is exactly the trigger condition for removal —
  satisfied here.

**On the prior "keep everything" cycle (UNK-01):** an earlier requirement/plan/
implementation chain (`requires/done/20260818-170800_require.md` →
`plans/done/20260818-182130_plan.md` → `implementations/done/20260818-212457_mcp_health.py.md`)
examined the same three symbols and concluded to keep `record_degraded()`
because "it has test coverage" and to keep `get_degraded_reason()` because it is
"paired with `record_degraded()`". That reasoning does not hold: test-only
coverage is exactly the dead-code signature `rules/coding.md`'s deprecation
policy and the source issue (`issues/done/20260817_03_issue.md`) target, and
that prior analysis never identified the "always returns `None` in production"
defect that the current requirement's Background section surfaces. No code
change resulted from that prior cycle (verified — the file is byte-for-byte
unchanged in this respect), so this plan does not conflict with an in-flight or
already-implemented resolution; it corrects a superseded decision using
evidence the earlier cycle missed. This plan proceeds with removal rather than
treating the prior "keep" conclusion as binding.

**cmd_mcp.py change:** `_write_servers_in_state()` currently builds
`reason = registry.get_degraded_reason(key) if registry else None` then
`reason_str = f": {reason}" if reason else ""` then writes
`f"    [{label.upper()}] {key}{reason_str}"`. After removal, `reason`/`reason_str`
are deleted and the line becomes `f"    [{label.upper()}] {key}"`. This affects
both call sites (`state=DEGRADED` and `state=UNAVAILABLE`), since both funnel
through the same helper — the requirement's Target files list only mentions
`get_degraded_reason()`'s effect on the DEGRADED path, but the fix is in the
shared helper so the UNAVAILABLE path's reason suffix is removed too. This is
consistent with the requirement's intent (the helper's only reason source is
`get_degraded_reason()`, which is being removed) and does not expand scope: it
is the same code line, used by both callers.

## Risks

- **Risk**: Deleting `tests/shared/test_mcp_health_degraded.py` outright could
  silently drop a unique regression check (e.g. the "does not downgrade
  UNAVAILABLE/HALF_OPEN" guard behavior inside `record_degraded()` itself, which
  disappears along with the method — this is expected and correct, since the
  guarded code path no longer exists) → **Mitigation**: Implementation Step 2
  requires reading the two adjacent test files first and aborting a full-file
  delete if any unique, still-relevant behavior would be lost; only tests whose
  subject method is removed are deleted.
- **Risk**: Renaming/merging `test_unavailable_server_shown_with_reason` and
  `test_unavailable_server_without_reason` could reduce test-name clarity or
  accidentally drop the "no unavailable block when healthy" style coverage if
  done carelessly (Likelihood: low) → **Mitigation**: Step 6 explicitly keeps
  `test_no_unavailable_block_when_all_healthy` as a separate test; only the two
  reason-specific tests are candidates for merge, and only after confirming
  their post-edit bodies are identical.
- **Risk**: A future contributor might reintroduce a `record_degraded()`-style
  writer without realizing the reader/storage pair was removed for exactly this
  reason (Likelihood: low, Impact: repeat of the same tech-debt cycle) →
  **Mitigation**: none added to code per the requirement's instructions (no
  speculative docstring warning was requested); the removal itself, plus this
  plan's Traceability trail, is the record. Not escalated to a tracked risk
  issue — likelihood and impact are both low and the requirement's Acceptance
  criteria do not ask for a preventive comment.
- **Risk**: This plan supersedes a prior cycle's explicit "keep everything, no
  code change" decision (`plans/done/20260818-182130_plan.md` /
  `implementations/done/20260818-212457_mcp_health.py.md`) without a maintainer
  sign-off reconciling the two conclusions (Likelihood: the disagreement is
  real and already exists in the repo history; Impact: a reviewer encountering
  both records might question which is authoritative) → **Mitigation**: this
  plan's Design section documents the reasoning gap explicitly (test-coverage-only
  ≠ live production caller; the prior cycle missed the always-`None` defect).
  No separate risk issue filed — the mitigation is documentation within this
  plan and its Traceability trail, which is sufficient per `rules/coding.md`'s
  Explicit sign-off gates guidance (that guidance requires a sign-off record
  only when a requirement itself gates a sub-task behind explicit sign-off,
  which this requirement does not).
