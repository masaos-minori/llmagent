## Background
`ToolExecutor(ToolTransportInvoker)` (`scripts/shared/tool_executor.py:40`) inherits `ToolTransportInvoker.__init__` (`scripts/shared/tool_transport_invoker.py:40-62`), which builds `self._transports[key] = HttpTransport(...)` for each server config in `server_configs.items()`, but explicitly `continue`s (skips) any config where `cfg.is_disabled` is `True`. `McpServerConfig`'s class default is `startup_mode = StartupMode.NONE` (`scripts/shared/mcp_config.py:82`), and `is_disabled` returns `True` exactly when `startup_mode == StartupMode.NONE` (`:110-112`). Both failing tests construct `McpServerConfig(transport=TransportType.HTTP, url=..., auth_token="test-token")` without an explicit `startup_mode`, so their configs are (silently) disabled, and no transport is ever created for server key `"srv"`.

## Problem
- `test_session_id_injected_into_http_transport_header`: `ex._transports["srv"]` raises `KeyError: 'srv'` (line 359) — confirmed via Read that the transport-building loop skipped this key because `cfg.is_disabled` was `True`.
- `test_set_session_id_empty_string_does_not_inject_header`: identical `KeyError: 'srv'` (line 377), same cause.

## Reason for change
This is the same test-fixture-staleness pattern as `shared001` (relying on `McpServerConfig`'s disabled-by-default `startup_mode`, which silently short-circuits enabled-server code paths) — confirmed test-only, not a production defect: `ToolTransportInvoker`'s skip-if-disabled behavior is correct and intentional.

## Implementation intent
Add `startup_mode=StartupMode.PERSISTENT` to both tests' `McpServerConfig(...)` calls, so `is_disabled` is `False` and a real `HttpTransport` is built for `"srv"`, matching each test's evident intent (verifying `X-Session-Id` header injection into that transport).

## Requirements
