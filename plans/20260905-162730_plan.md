## Background
The system uses four independent SQLite persistence domains (`rag.sqlite`, `session.sqlite`, `workflow.sqlite`, `eventbus.sqlite`), each with its own ownership, backup policy, and recovery semantics per `docs/adr/ADR-008-sqlite-4db-separation.md` (read in full; Confirmed by repository evidence). The ADR already defines substantial recovery policy in prose form (Decision Details #14-20, Invariants INV-13 through INV-18, and a `Known Deviations` section covering `SHARED-002`/`SHARED-003`), but does not use a single normative vocabulary for the different recovery-related operations it distinguishes informally.

## Problem
Confirmed by reading `docs/adr/ADR-008-sqlite-4db-separation.md` and `docs/90_shared_05_04_db_api_and_operations-recovery-and-reference.md` in full: the six terms the Issue requires (`initialization`, `schema-repair`, `logical-repair`, `derived-data-rebuild`, `physical-recovery`, `operator-restore`) are not defined anywhere in the corpus, even though the underlying distinctions already exist informally — e.g. `scripts/db/recovery.py`'s `DbCondition` enum (`HEALTHY`/`CORRUPTION`/`LOCK_CONTENTION`/`PERMISSION_FAILURE`/`INVALID_FORMAT`/`UNKNOWN`, confirmed by reading `docs/90_shared_05_04_...` section 9.3) already separates physical-corruption classification from other failure modes, and ADR-008 Decision Details #20 already states a domain-by-domain automatic-restore policy without using a stable term for "restore from an operator-supplied backup" (`operator-restore`) versus "recreate empty schema" (`initialization`, documented separately in `docs/90_shared_05_04_...` section 11 "DB Recreation Procedure"). No single table currently presents the 18 policy fields the Issue lists side-by-side for all four databases — the same information is split across ADR-008's Decision Details (prose), Invariants (prose), and `docs/90_shared_05_04_...` section 9.7 (prose), each covering a different subset.

Adversarial verification (per `rules/ai-execution.md` Adversarial Verification (Base)) found one stale claim in the Issue itself: its `AI Implementation Instruction` cites `docs/90_shared_90_inconsistencies_and_known_issues.md` for `SHARED-001`/`SHARED-002` evidence, but this file does not exist in the current repository — its content was consolidated into `docs/00_governance_03_issue-and-uncertainty-management.md` (Confirmed by repository evidence: `ls` fails on the cited path; `grep` confirms `SHARED-002`/`SHARED-003` entries exist in the replacement file). Separately, `SHARED-001` does not exist as a heading in the replacement file either — only `SHARED-002` and `SHARED-003` are present (Confirmed by repository evidence, see Unknowns UNK-01). This Plan uses the corrected path and the two entries that do exist.

## Reason for change
Without one authoritative terminology and policy matrix, operators and implementers must infer which recovery category a given action belongs to from scattered code and documentation, risking a `physical-recovery` action being applied where only `schema-repair` or `derived-data-rebuild` was intended, or vice versa. `docs/adr/ADR-008-sqlite-4db-separation.md`'s own Rationale section (§4, "Correctness (Recovery Safety)") already states that a recovery mechanism that cannot distinguish failure categories is more dangerous than no recovery mechanism at all — the same argument applies to a *documentation* corpus that does not consistently distinguish these categories by name.

## Implementation intent
Treat `docs/adr/ADR-008-sqlite-4db-separation.md` as the single canonical source for the new taxonomy and matrix — it already functions as the "canonical recovery policy" per `docs/90_shared_05_04_...` section 9.7's own cross-reference ("See ADR-008 Decision Details #20 for the canonical recovery policy across all four DB domains"), so this Plan extends that existing role rather than introducing a second, competing canonical location. Do not restate the matrix's content a second time in `docs/90_shared_05_04_...` — replace that document's own persistence-domain-policy prose (section 9.7) with a short pointer to the ADR's new matrix, keeping only the API-reference-specific detail (which function/parameter maps to which domain) that does not belong in an ADR. Apply the same term substitution consistently: every remaining use of bare "recovery"/"リカバリ" in the four target documents must be replaced by one of the six defined terms, or left as the general umbrella word only where the sentence is genuinely category-agnostic (e.g. a section heading spanning multiple categories).

The new matrix is additive documentation restructuring, not a new design decision — every policy value it will state (automatic-restore permission per domain, system of record, recovery source) is already an accepted decision recorded in ADR-008's Decision Details #1-20 and Invariants INV-01 through INV-18 (Confirmed by repository evidence, full ADR read 2026-09-05). This Plan's design work is purely representational: (a) name six categories that the existing prose already distinguishes informally, (b) project the existing prose onto the Issue's 18-field schema as one table per persistence domain, and (c) remove the resulting duplication from `docs/90_shared_05_04_...` section 9.7 in favor of a pointer, consistent with `skills/DESIGN.md` Avoid implementation-reference duplication applied at the documentation-cross-reference level.

Term-to-evidence grounding (used when drafting REQ-001's glossary):
- `initialization` → `create_schema()` behavior, `docs/90_shared_05_04_...` section 11 ("Recreated DBs are empty").
- `schema-repair` → `docs/90_shared_04_03_...`'s incremental migration mechanisms for `workflow.sqlite`/`eventbus.sqlite`/`mdq.sqlite`, distinct from `rag`/`session`'s recreate-only path.
- `logical-repair` → `RagMaintenanceService`'s consistency-check/rebuild operations (`docs/90_shared_05_04_...` section 9.7, "Reconstructable derived data").
- `derived-data-rebuild` → same section, FTS/vector index rebuild from the `chunks` table (`rag.sqlite` only).
- `physical-recovery` → `recover_corruption()`'s `DbCondition.CORRUPTION` path (`docs/90_shared_05_04_...` sections 9.3-9.5).
- `operator-restore` → the manual, operator-triggered nature of `recover_corruption()` itself (section 9.8), and `workflow`/`eventbus`'s manual-only policy (Decision Details #20).
