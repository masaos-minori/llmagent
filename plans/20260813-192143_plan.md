# Plan: Unify TOOLS/READ/WRITE derivation direction in tool_constants.py

## Goal
Make every TOOLS/READ/WRITE(/DANGEROUS) group in `scripts/shared/tool_constants.py` use the
same derivation direction (derive the umbrella `*_TOOLS` set from the literal READ/WRITE/
DANGEROUS subsets), with **zero membership change** to any exported frozenset or to
`get_all_mcp_tool_names()`. This removes the current inconsistency where `CICD_*`/`RAG_*`
derive READ as `TOOLS - WRITE` while `GIT_*`/`GITHUB_*` derive TOOLS as `READ | WRITE
(| DANGEROUS)`, which invites copy-paste mistakes when a new tool group is added.

## Scope

### In-Scope
- `scripts/shared/tool_constants.py`: re-derive `CICD_TOOLS` and `RAG_TOOLS` as
  `CICD_READ_TOOLS | CICD_WRITE_TOOLS` and `RAG_READ_TOOLS | RAG_WRITE_TOOLS` respectively
  (making `CICD_READ_TOOLS` / `RAG_READ_TOOLS` the literal sets and `CICD_TOOLS` / `RAG_TOOLS`
  the derived ones), matching the direction already used by `GIT_TOOLS` and `GITHUB_TOOLS`.
- Decide and document whether `MDQ_TOOLS`/`MDQ_WRITE_TOOLS` needs an `MDQ_READ_TOOLS` — see
  Design section (decision: leave as-is, documented below).
- A one-off, non-committed baseline-membership-comparison script (scratchpad only) used to
  verify zero membership drift before/after the edit.

### Out-of-Scope
- `scripts/shared/route_resolver.py`, `scripts/shared/tool_executor.py`,
  `scripts/shared/tool_executor_helpers.py`, `scripts/shared/tool_registry.py`,
  `scripts/agent/tool_policy.py`, `config/agent.toml` — none of these are modified; they only
  consume the frozensets and are unaffected because membership is unchanged.
- Introducing `MDQ_READ_TOOLS` (explicitly deferred — see Design).
- Any change to which tool names belong to which classification (pure internal-consistency
  refactor, no behavior change).
- Editing any test file — `tests/shared/test_tool_constants.py` and
  `tests/shared/test_tool_registry.py` must pass unchanged.

## Assumptions
- "Canonical direction" means: every group with a TOOLS/READ/WRITE(/DANGEROUS) shape derives
  the umbrella `*_TOOLS` set from the narrower literal sets, per the requirement's recommended
  direction (matches the majority-shape groups GIT/GITHUB already in the file).
- The requirement's own membership-verification method (dump-and-diff baseline script) is
  sufficient; no additional test file needs to be added since acceptance criteria explicitly
  forbid new permanent test files.
- `uv run python -m compileall` / `pytest` are available locally to validate before/after
  (confirmed by successful `uv run ruff check` / `uv run bandit` runs during evidence
  gathering below).

## Design
`scripts/shared/tool_constants.py` is a leaf, data-only module in the `shared` package. Per
`.importlinter`'s `shared-is-leaf` contract, `shared` must not import from `agent`,
`mcp_servers`, `rag`, or `db`; this file has no internal imports at all (only
`from __future__ import annotations`), so re-deriving two frozensets introduces no new imports
and cannot violate any import-linter contract — confirmed by reading the full file
(`scripts/shared/tool_constants.py`, 187 lines) and `.importlinter`.

Current state (verified by direct read):
- `RAG_TOOLS` (lines 52-59) is a literal; `RAG_WRITE_TOOLS` (line 73) is a literal subset;
  `RAG_READ_TOOLS = RAG_TOOLS - RAG_WRITE_TOOLS` (line 74) — READ derived by subtraction.
- `CICD_TOOLS` (lines 61-68) is a literal; `CICD_WRITE_TOOLS` (line 70) is a literal subset;
  `CICD_READ_TOOLS = CICD_TOOLS - CICD_WRITE_TOOLS` (line 71) — same subtraction pattern.
- `GIT_READ_TOOLS` (lines 92-100) and `GIT_WRITE_TOOLS` (lines 102-110) are both literals;
  `GIT_TOOLS = GIT_READ_TOOLS | GIT_WRITE_TOOLS` (line 112) — union pattern (target direction).
- `GITHUB_READ_TOOLS` (128-143), `GITHUB_WRITE_TOOLS` (145-155), `GITHUB_DANGEROUS_TOOLS`
  (157-162) are all literals; `GITHUB_TOOLS` (164-166) is their union — union pattern (target
  direction).
- `MDQ_TOOLS` (77-87) and `MDQ_WRITE_TOOLS` (89) are both literals with no `MDQ_READ_TOOLS` and
  no derived umbrella set — this is a two-set group, not a TOOLS/READ/WRITE triple, so there is
  nothing to unify here. Confirmed by reading `tests/shared/test_tool_constants.py`: it has a
  `TestGitToolClassification`, `TestGithubToolClassification`, and `TestRagToolClassification`
  each asserting a union/disjointness invariant, but only a single
  `TestMdqToolClassification.test_mdq_write_tools_are_side_effect` test with no union assertion
  — consistent with MDQ never having had a three-set shape. **Decision: leave MDQ unchanged**,
  and note this explicitly in the code comment/PR description per the requirement's guidance.

Target design: adopt "derive `*_TOOLS` as the union of the READ/WRITE(/DANGEROUS) literals" as
the canonical direction repo-wide (matches GIT/GITHUB, the majority shape already present).
Concretely:
- Swap `RAG_TOOLS` to become the literal-turned-nothing: `RAG_READ_TOOLS` becomes a literal
  frozenset containing exactly `{"rag_run_pipeline", "rag_debug_pipeline",
  "rag_list_documents"}` (the members of current `RAG_TOOLS - RAG_WRITE_TOOLS`), `RAG_WRITE_TOOLS`
  stays a literal (`{"rag_delete_document"}`), and `RAG_TOOLS = RAG_READ_TOOLS | RAG_WRITE_TOOLS`
  becomes the derived set.
- Same transformation for `CICD_TOOLS`: `CICD_READ_TOOLS` becomes a literal containing exactly
  `{"get_workflow_runs", "get_workflow_status", "get_workflow_logs"}` (current
  `CICD_TOOLS - CICD_WRITE_TOOLS`), `CICD_WRITE_TOOLS` stays `{"trigger_workflow"}`, and
  `CICD_TOOLS = CICD_READ_TOOLS | CICD_WRITE_TOOLS` becomes derived.
- No change to `GIT_*`, `GITHUB_*`, `MDQ_*`, `READ_TOOLS`, `WRITE_TOOLS`, `DELETE_TOOLS`,
  `SHELL_TOOLS`, `WEB_SEARCH_TOOLS`, or `get_all_mcp_tool_names()` — the latter already sums
  frozensets by name and is agnostic to how each summand is derived internally.
- No layering/import-boundary considerations beyond the leaf-module confirmation above — this
  is a pure data-literal reshuffle inside one already-leaf file.

## Risks

- **Risk**: Manual transcription of the 3-member `RAG_READ_TOOLS` / `CICD_READ_TOOLS` literals
  introduces a typo or drops a member during the direction swap. → **Mitigation**: the Phase 1/2
  baseline-dump-and-diff script is mandatory and specifically designed to catch exactly this;
  treat any non-empty diff as a stop condition, not something to patch around. Likelihood: low
  (small, well-scoped edit with an automated verification gate).
- **Risk**: A future contributor adds a new tool group and copies the wrong (pre-existing GIT-
  style vs. newly-unified) block as a template, re-introducing inconsistency. → **Mitigation**:
  the added inline comment near `MDQ_TOOLS` plus the now-single consistent pattern across
  RAG/CICD/GIT/GITHUB reduces the chance of copying a stale pattern; no further mitigation is in
  scope for this narrowly-defined cleanup (matches the requirement's stated intent to keep this
  cycle narrowly scoped). Likelihood: low.
- **Risk**: Hidden consumer relies on `RAG_TOOLS`/`CICD_TOOLS` being defined *before*
  `RAG_READ_TOOLS`/`CICD_READ_TOOLS` at module-import time (e.g. via some non-standard import
  order dependency). → **Mitigation**: Python module-level execution is strictly top-to-bottom
  and all consumers import by name (not by attribute access during partial-init), confirmed by
  `rg` evidence showing all 18 importers use `from shared.tool_constants import <NAME>` after
  the module fully loads; no consumer does `import shared.tool_constants` and accesses names
  mid-load. Likelihood: low.
