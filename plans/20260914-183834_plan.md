## Design

### Determine Where Handlers Genuinely Require Authorization Context (REQ-001)
Current state: All four handlers accept `_role` and/or `_identity` parameters, but none use them in their function bodies.

**Decision**: No handler currently requires authorization context beyond what endpoint-level enforcement provides. Therefore:
- No handler needs a typed principal parameter
- All `_role` and `_identity` parameters should be removed
- Security boundaries remain explicit via endpoint-level `Depends(require_role(...))` dependencies

### Keep Security Boundaries Explicit in Function Contracts (REQ-003)
Current state: Comments like `# set by app.py wrapper` imply that authorization context is passed from the wrapper, but this is misleading because the actual enforcement happens at the endpoint level via FastAPI dependencies.

**Decision**: Update stale comments to accurately reflect where enforcement occurs:

Remove all `# set by app.py wrapper` comments (since the parameters they reference are being removed).

If any handler were to genuinely require authorization context in the future, add a docstring comment explaining why:

```python
async def some_handler(...) -> SomeResponse:
    """Handle request.
    
    Note: Authorization is enforced at the endpoint level via
    Depends(require_role(...)), not within this handler.
    If this handler ever needs typed principal access, add a
    `principal: Principal` parameter and document the requirement.
    """
```
