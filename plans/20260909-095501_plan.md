## Goal
- Make Event Bus backpressure fail safely (a slow consumer's overflowing subscription is
  disconnected instead of silently dropping an event), and give consumer identity one
  explicit concurrency policy (reject a second concurrent connection for the same
  non-empty `consumer_id` with HTTP 409, per ADR-006 INV-10/INV-11 — no consumer-group
  model), so an undetected permanent delivery gap can no longer occur.

## Priority
High

## Scope
- **In-Scope**:
  - `EventBroker.publish()` disconnecting (not silently dropping into) an overflowing
    subscriber's stream.
  - Tracking active non-empty `consumer_id`s and rejecting a second concurrent
    connection with HTTP 409.
  - Releasing consumer registration on cancellation, disconnect, generator failure, and
    shutdown.
  - Confirming reconnect-after-disconnect resumes from the last committed offset.
  - Observability (metrics/structured logs) for overflow-disconnect and
    duplicate-connection-rejection events.
  - Updating the EventBus operations/delivery-semantics documentation to state the
    finalized policy as canonical.
- **Out-of-Scope** (per Issue, tracked separately in this batch):
  - Transactional ACK/offset redesign.
  - DLQ retry/requeue redesign.
  - Capacity-limit/threshold configuration (the existing hardcoded `maxsize=1000` /
    `_SLOW_CONSUMER_THRESHOLD = 100` in `scripts/eventbus/broker.py` are unchanged).
  - ACK-contiguity enforcement (see `UNK-01`) — no ADR-006 invariant requires it, and
    the Issue's own Required Changes phrase it conditionally ("if ACKs must be
    contiguous"); not implemented in this Plan.
  - Consumer-group model — ADR-006's Alternative C ("no consumer ID conflict
    detection") is already rejected, and INV-10 already decides the policy.
  - `EventBroker.shutdown()`'s own `except asyncio.QueueFull: pass` swallow (see Risks)
    — a related but distinct latent gap the Issue's Required Changes do not name.

## Background
`scripts/eventbus/broker.py`'s `publish()` silently drops an event and logs a warning
when a subscriber's bounded queue (`maxsize=1000`) is full, while leaving the SSE
connection open — confirmed by direct read, `EventBroker.publish()` has no path that
disconnects or invalidates an overflowing subscription. `EventBroker.subscribe()` has no
`consumer_id` parameter or tracking at all; `consumer_id` is only used, elsewhere, by
`scripts/eventbus/subscribe_route.py` (offset-replay lookup) and
`scripts/eventbus/ack_route.py`/`scripts/eventbus/offsets.py` (offset persistence and
raw-string-collision detection) — none of these three call sites register or check for
a second concurrent connection under the same `consumer_id`.

ADR-006 (`docs/adr/ADR-006-eventbus-sqlite-persistence-and-sse-delivery.md`, Accepted)
already decided this exact policy: INV-10 "同一Consumer IDの並行使用を禁止する" (prohibit
concurrent use of the same Consumer ID) and INV-11 "Consumer ID衝突を検出する" (detect
Consumer ID collision), with Alternative C ("no consumer ID conflict detection") already
recorded as rejected. The current code does not implement INV-10, and
`docs/06_eventbus_02_operations.md`/`docs/06_eventbus_04_dlq_offsets_and_delivery_semantics.md`
currently describe today's gap ("last write wins", queue-overflow silent discard) as
accepted, intentional behavior — contradicting ADR-006's own already-decided invariants.
This Plan closes that ADR-vs-code-vs-operational-docs gap, not just the Issue's
originally-stated code gap.

## Problem
- A consumer whose queue overflows continues receiving events after the gap with no
  signal that an event was dropped — its offset can later advance past the dropped
  event via a normal ACK, permanently losing it from that consumer's perspective. This
  violates ADR-006 INV-07 ("At-Least-Once Delivery... 欠落は許容しない" — loss is not
  permitted).
- `tests/eventbus/test_eventbus_slow_consumer.py` (confirmed by direct read) only
  verifies `maxsize=1000` and that the health endpoint's `slow_consumers`
  counter/503 status reflects queue depth — it does not test that an overflowing
  subscription is disconnected, nor that a dropped event is ever surfaced to the
  consumer. These tests pass under today's drop-and-continue behavior.
- No test or code path in `scripts/eventbus/subscribe_route.py`/`broker.py` tracks
  active `consumer_id`s across concurrent SSE connections — two processes could
  subscribe with the same `consumer_id` simultaneously with no rejection, contradicting
  ADR-006 INV-10.

## Reason for change
Make backpressure fail safely: a slow or duplicate consumer must never create an
undetected permanent gap. The server must terminate the affected subscription (so the
client can resume from its last committed position) rather than silently continuing.
Consumer identity must have the one explicit concurrency policy ADR-006 already decided.

## Implementation intent
Define the disconnect-on-overflow mechanism and the consumer-connection registry, then
wire both into the existing SSE subscribe/unsubscribe lifecycle.

**Correction to the Issue's own suggested mechanism** (adversarial-verification
finding): the Issue's Implementation Intent suggests reusing "the sentinel-then-unsubscribe
pattern `broker.py` already uses for shutdown" for the overflow-disconnect path. This
does not work as stated: `EventBroker.shutdown()`'s sentinel is a `None` value
`put_nowait()`'d into each subscriber's queue — but the overflow case is, by definition,
the one case where that same queue is already full, so `put_nowait(None)` would itself
raise `asyncio.QueueFull` (the existing `shutdown()` code already silently swallows this
exact same failure via `except asyncio.QueueFull: pass` — see Risks). A full queue
cannot carry a sentinel without evicting already-buffered data (itself a form of loss).
The disconnect signal must therefore be a channel independent of the bounded queue.

Concretely: give `_Subscriber` a disconnect signal (e.g. an `asyncio.Event`) alongside
its existing `queue`. `EventBroker.publish()`, on `QueueFull`, sets that subscriber's
disconnect signal and removes it from the active-subscriber list immediately (instead of
attempting to enqueue anything) — this stops further deliveries to it. In
`subscribe_route.py`'s SSE generator, replace the unconditional `await sub.queue.get()`
with a race between `queue.get()` and the disconnect signal (e.g. `asyncio.wait(...,
return_when=asyncio.FIRST_COMPLETED)`), so a subscriber whose queue is not growing after
disconnect does not block forever; on disconnect-signal completion, cancel the pending
`queue.get()` and end the generator (closing the SSE response), which is exactly what
signals the client to reconnect using its last committed offset.

For consumer-connection tracking: add an in-memory `dict[str, _Subscriber]` (or
equivalent) inside `EventBroker` keyed by non-empty `consumer_id`, populated by
`subscribe()` and cleared by `unsubscribe()`. `subscribe_route.py` calls a new
broker method (e.g. `EventBroker.subscribe(topics, consumer_id=...)`) that raises (or
returns a sentinel the route translates into) HTTP 409 when the key is already present
— following the existing `HTTPException(status_code=409, ...)` pattern already used in
`scripts/eventbus/dlq_route.py` for `ERR_EVENT_NOT_IN_DLQ`. Release the registry entry
in the same `finally: broker.unsubscribe(sub)` block `subscribe_route.py` already runs
on cancellation, disconnect, generator failure, and shutdown — extending that one
existing call site to also clear the consumer-connection registry, rather than adding a
second, parallel release path.

Reconnect-after-disconnect already resumes from the last committed offset today: `since_seq`/
`read_offset(cfg.offsets_dir, consumer_id)` in `subscribe_route.py` is unconditional on
why the prior connection ended. This Plan's job for that behavior is to confirm it holds
once disconnect-on-overflow exists (via a new test), not to add new code for it.

## Design
**Disconnect signal, not a queue sentinel.** `_Subscriber` gains a disconnect signal
(e.g. `asyncio.Event`) independent of its bounded `queue`. `EventBroker.publish()`, on
`asyncio.QueueFull`, sets that subscriber's disconnect signal and removes it from
`self._subscribers` immediately — it does not attempt `put_nowait()` again, since the
queue is by definition already full. This is the corrected version of the Issue's own
suggested "reuse the shutdown sentinel pattern" approach (see Implementation intent) —
a full queue cannot carry a `None` sentinel without evicting buffered data, which
`EventBroker.shutdown()`'s own `except asyncio.QueueFull: pass` already silently
tolerates as a pre-existing, out-of-scope gap (see Risks).

**Consumer-ID registry.** `EventBroker` gains a `dict[str, _Subscriber]` (or equivalent)
keyed by non-empty `consumer_id`. `subscribe(topics, consumer_id="")` — the default
empty string is never registered (an anonymous/no-`consumer_id` connection is exempt
from duplicate-rejection, matching the Issue's "non-empty consumer ID" framing) — checks
the registry before appending to `self._subscribers`; a non-empty key already present
raises (the route layer translates this into HTTP 409, following the existing
`ERR_EVENT_NOT_IN_DLQ` 409 pattern in `dlq_route.py`). `unsubscribe()` removes both the
subscriber-list entry and, when present, its registry key.

**SSE generator race.** `subscribe_route.py`'s `_sse_gen()` currently does
`event = await sub.queue.get()` unconditionally. Once the queue can no longer guarantee
an eventual item after a disconnect (since `publish()` will not attempt to enqueue a
sentinel into it), the generator must race `queue.get()` against the disconnect signal
(e.g. `asyncio.wait({queue.get(), disconnect_signal.wait()},
return_when=asyncio.FIRST_COMPLETED)`), ending the stream on whichever completes first
and cancelling the other. This ends the `StreamingResponse`, which is the client-visible
disconnect signal prompting a reconnect with `since_seq`/`consumer_id`.

**Release path stays singular.** `subscribe_route.py`'s existing
`finally: broker.unsubscribe(sub)` already runs on cancellation (`asyncio.CancelledError`
is explicitly caught, and `finally` still runs), disconnect, generator failure, and
(via the sentinel path) shutdown. Extend `unsubscribe()` itself to also clear the
consumer-ID registry key, rather than adding a second release call site — this keeps
`REQ-003`'s "no leaked registrations" guarantee anchored to the one place release
already happens.

**Health surfacing.** `health_route.py`'s `health_check()` already surfaces
`broker.slow_consumer_count()` as a plain field read (not new branching logic); the new
overflow-disconnect/duplicate-rejection counters follow the identical pattern (a plain
getter call, no new `if` branches) to avoid growing `health_check()`'s cyclomatic
complexity beyond its current pre-existing `C (11)` radon grade (baseline recorded
below, not itself a target of this Plan).

## Risks
- **Risk**: `EventBroker.shutdown()`'s own `except asyncio.QueueFull: pass` has the
  identical silent-swallow failure mode this Plan fixes for `publish()` — a subscriber
  whose queue is already full at shutdown time never receives the `None` sentinel and
  its generator can hang. → **Mitigation**: Out of scope for this Plan (the Issue's
  Required Changes target the `publish()`-path overflow specifically, not `shutdown()`);
  noted here so a future Plan can decide whether `shutdown()` should also use the new
  disconnect-signal mechanism instead of a queue sentinel.
- **Risk**: Racing `queue.get()` against a disconnect signal via `asyncio.wait` must
  correctly cancel the losing task in every completion order, or a cancelled-but-not-
  awaited `queue.get()` task could log an "exception never retrieved" warning. →
  **Mitigation**: `REQ-006`'s unit tests must cover both completion orders (item arrives
  first; disconnect arrives first) and assert no unretrieved-exception warnings.
- **Risk**: A future multi-process/multi-worker Event Bus deployment would make the
  single-process in-memory `consumer_id` registry insufficient (each worker would have
  its own registry, allowing the exact duplicate-connection race this Plan closes to
  reappear across workers). → **Mitigation**: documented as an Assumption above; no
  multi-process deployment exists today (confirmed via `app.py`'s single
  `EventBroker()` instantiation), so this is not a current gap — flag if a multi-worker
  deployment is ever introduced.
