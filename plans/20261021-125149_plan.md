## Background
`memo4.md` ("Remaining work", item 6) is cited as recording that the identifier matching used to verify the docs cleanup covers CamelCase names and `name()` forms only, and that snake_case-only references and config key names are not matched exhaustively. The issue itself flags this as an assumption from the memo that must be confirmed. `tools/check_docs_consistency.py` (and its shared lib `tools/_docs_consistency_lib.py`) already provides port-drift, tool-name drift, `scripts/`-path existence, and backtick-quoted function-reference existence across domains (see `rules/toolchain.md`).

## Problem
A doc that names a snake_case function, variable, or config key that no longer exists in `scripts/` or `config/` can pass the verification used for the docs cleanup.

## Reason for Change
Docs compression removes inventories and keeps references to representative symbols and keys. If those references are not checked, they can go stale unnoticed.

## Implementation Intent
First measure, then extend. Determine what `check_docs_consistency.py` already catches for snake_case-only and config-key references on the live `docs/`. Close only the remaining gap, preferably by extending that existing tool rather than adding a new script (`routing.md` "When to run which tool": extend the existing tool, do not write a new one-off script). Config key checks should use the canonical config model or `config/*.toml` as source, not a hardcoded list. Run any new check at Warning level first and triage findings on the live corpus.

### Planning-phase evidence (adversarial verification)
- **No `memo4.md` exists.** Only `memo-etc.md`, `memo-test.md`, `memo1.md`, `memo2.md`, `memo3.md` are present. None reference identifier matching, snake_case, or config keys. The issue's entire "Background" premise is sourced from a non-existent file.
- **snake_case *function calls* are already caught.** `check_function_references` (a generic check in the `funcrefs` group, run for every domain) uses `_FUNC_REF_RE = r"`(?:[a-zA-Z_][a-zA-Z0-9_]*\.)?([a-zA-Z_][a-zA-Z0-9_]{3,})\(\)`"`, which matches **any** identifier followed by `()` — including snake_case names. Empirically, 824 such backtick `name()` references exist in live `docs/`, and the tool reports "No issues found" for every domain (all names are defined under `scripts/`). So the claim "snake_case-only references are not matched" is **false** for `name()` forms.
- **Config keys: only `*_db_path` covered.** `check_config_key_presence` (deployment domain, `configkey`) only flags keys ending in `_db_path`. A search of the live deployment docs finds **zero** non-`_db_path` config-ish snake_case references. So there is no observed config-key gap on the current corpus.
- **The only genuine gap is bare snake_case *variable* references** (backtick names with no trailing `()`, e.g. `` `my_var_name` ``), which no mechanism checks. Adding bare-variable existence checking is high false-positive risk against prose words in backticks — a risk the issue itself flags and requires an allowlist for. No existing mechanism covers it.
- **Tests for the generic checks** live in `tests/tools/test_check_agent_docs_consistency.py` (the named `tests/tools/test_check_docs_consistency.py` does not exist).
- **Validation baseline (installed tools):** `radon cc` rates both target modules A (low complexity); `vulture --min-confidence 80` is clean on the two targets (one pre-existing finding is in an unrelated file, `check_canonical_source_conflicts.py`); `bandit` reports zero on the targets. `semgrep` is not installed in this environment (noted; baseline otherwise complete).
- The verifiable core — "is there a mechanical gap for SOME snake_case/config references" — is confirmed: yes for bare variables and non-`_db_path` config keys, but **no** for `name()` function calls.

## Design
Document-driven, Path A decide task. The planning-phase verification established that the issue's premise — "snake_case-only references and config key names are not matched exhaustively" — does not hold as stated:

- **snake_case function calls are already covered.** `check_function_references` (generic `funcrefs` check, all domains) matches any `[a-zA-Z_][a-zA-Z0-9_]{3,}` identifier followed by `()`, including snake_case. 824 such references exist in live `docs/`; the tool reports no issues for any domain, confirming they are all defined under `scripts/`.
- **Config keys are covered where they occur.** `check_config_key_presence` handles `*_db_path` keys; zero non-`_db_path` config-ish snake_case references exist in the live deployment docs, so no config-key gap is observed on the current corpus.
- **The only real gap is bare snake_case variable references** (backtick names with no trailing `()`), which no mechanism checks. Checking them mechanically is high false-positive risk against prose words in backticks (the issue requires an allowlist for exactly this).

Two candidate approaches are to be evaluated on a real past docs diff (UNK-02):
- **Mechanical**: extend `tools/check_docs_consistency.py` (via `tools/_docs_consistency_lib.py`) with report-only (Warning) detection for bare snake_case names and/or non-`_db_path` config keys, using the canonical config model or `config/*.toml` as the source of truth. Per `routing.md` and `AGENTS.md` Global Rule 7, this must extend the existing tool, not add a new one-off script, and must start report-only (Warning) with an allowlist to control false positives.
- **Accept the limit**: record the uncovered forms (bare variables, non-`_db_path` config keys) as an accepted detection limit with an owner, optionally in `docs/00_governance/governance_04_documentation-checks.md`.

The decision (UNK-01) and its rationale are recorded in a canonical place. The critical constraints are that no blocking gate is introduced, no new one-off script is added against the routing policy, and no `docs/` content is edited in the same change as a tool extension.

Path classification is **Path A**: the likely outcome given the evidence (record an accepted limit) touches ≤3 files with no runtime interface change. If the owner instead chooses the mechanical branch, that branch touches >3 files and would require the full Path B architecture/dependency/historical analysis at implementation time (plan-to-implementation-procedure); this Plan documents the branch but does not perform that deeper analysis now.
