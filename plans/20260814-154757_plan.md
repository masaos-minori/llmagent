## Design

**How this fits the existing architecture**: This plan operates at the governance level rather than the code level. Sub-task 2 (the shared three-branch helper extraction) is a higher-risk refactoring because it touches two files (`llm_transport_errors.py` and `llm_reconnect.py`) and changes the call pattern between them. The requirement explicitly gates this behind "explicit sign-off before implementation." This plan defines what that means concretely.

**Sign-off mechanism design rationale**: The requirement recommends using a comment on `plans/20260813-190710_plan.md` since it is the most discoverable location for future implementers working on this plan. This approach has several advantages:
1. It ties the sign-off directly to the plan that documents the work, making it easy to find during normal workflow.
2. It uses an existing artifact (plan comments) rather than creating a new one.
3. It provides a clear, traceable record that can be referenced by future implementers.
4. It is consistent with the repo's existing practice of using `plans/` entries as implementation tracking artifacts.

**Why not alternative channels**: 
- A PR review approval could work but requires a PR to exist first, which may not align with the timing of when someone decides to implement sub-task 2.
- A separate maintainer message lacks discoverability compared to a comment on the plan itself.
- An issue comment on the original issue works but is less discoverable than a plan comment for someone actively working on the plan.

**Repo-wide convention design**: The requirement recommends adopting a repo-wide convention for "requires explicit sign-off before implementation" gates. The proposed convention:
1. When a requirement splits work into independently schedulable sub-tasks and gates a later sub-task behind "explicit sign-off," document the required sign-off channel in the follow-up issue/plan entry.
2. The preferred channel is a comment on the corresponding `plans/` entry (most discoverable for implementers).
3. Alternative channels: comment on the original issue, or a short-lived approval note in `issues/` referencing both the issue and the plan.
4. The record must be a maintainer statement (not just an acknowledgment) that the risk assessment for the gated sub-task is acceptable.
