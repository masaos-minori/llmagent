# Plan: ApprovalRecovery respects existing pending_approval_task_id

## Goal
- Ensure `ApprovalRecovery.recover()` does not overwrite `pending_approval_task_id` when an active approval is already wired up, preventing silent state corruption.

## Priority
Medium

## Scope
- **In-Scope**: Add conditional logic to preserve existing `pending_approval_task_id`; improve logging to clarify decision rationale
- **Out-of-Scope**: Changes to `find_all_pending_approvals()` query logic; changes to StateStore API

## Background
`ApprovalRecovery.recover()` in `scripts/agent/startup_approval_recovery.py` restores workflow approval-pending state from a previous session during startup. It sets `ctx.turn.pending_approval_task_id` to the most recent pending approval's task ID.

## Problem
The method overwrites `pending_approval_task_id` without checking whether the Orchestrator has already set it for a different approval. The warning log is emitted but the overwrite proceeds regardless. If the Orchestrator has already set `pending_approval_task_id` for a different approval, the recovery silently overwrites it. The user sees the wrong approval wired up for immediate action. Inconsistent state between what the user expects and what the system acts on.

## Reason for change
Silent state overwrites during startup are a reliability concern. Users expect the approval they interacted with to remain active. Overwriting it causes confusion and potential data loss.

## Implementation intent
Only overwrite `pending_approval_task_id` if the current value is stale (from a previous session). Compare the recovered task ID against the current value and prefer the newer one. Alternatively, require explicit user confirmation before auto-wiring a recovered approval.

## Requirements
- `REQ-001`: Recovery does not overwrite an active approval without justification
- `REQ-002`: Test verifies recovery respects existing approval state
- `REQ-003`: Test verifies recovery correctly overwrites stale state
- `REQ-004`: Warning message includes both old and new values

## Design
### Current Behavior (Verified Against Source)
1. `startup_approval_recovery.py` line 50-56: Try to recover pending approvals
2. Line 50: Check if `pending_approval_task_id` is already set
3. Line 51-55: Log warning about overwriting
4. Line 56: Always overwrite — regardless of whether the current value is active or stale

### Proposed Change (Revised after adversarial validation)

The original proposal added `_is_current_approval()` method but did not define its logic. Before implementation, the exact criterion for determining whether a pending approval is "active" vs "stale" must be specified. Options include:
- Timestamp comparison (current value is newer than recovered value)
- Approval record existence in database (current value's record still exists)
- Approval resolution status (current value has not been resolved/expired)

Until this is defined, the proposed change is incomplete. Revised approach:

```python
if ctx.turn.pending_approval_task_id is not None:
    logger.warning(
        "Overwriting pending_approval_task_id %s with %s during recovery",
        ctx.turn.pending_approval_task_id,
        task_id,
    )
    # TODO: Define _is_current_approval() logic before implementing
    # Option A: Compare timestamps — prefer the more recent one
    # Option B: Check if current value's approval record still exists in DB
    # Option C: Require explicit user confirmation before auto-wiring
    # For now, keep the unconditional overwrite with enhanced logging
ctx.turn.pending_approval_task_id = task_id
```

Key changes:
1. Keep the warning log (already present)
2. Mark `_is_current_approval()` as TBD until the criterion is defined
3. Consider requiring explicit user confirmation (Option C) as a safer default
