## Goal
- Add `tools/check_workitem_traceability.py`, a read-only checker that walks
  `issues/`, `plans/`, and `implementations/` (including their `done/` subdirectories),
  parses each document's Traceability section, and reports (a) referenced source paths
  that no longer exist, (b) issues with no plan yet, (c) plans with no implementation
  procedure yet, and (d) a best-effort heuristic flag for issues whose referenced target
  document may have been substantially edited or deleted since the issue was filed.

## Priority
Medium

## Scope
- **In-Scope**:
  - New script `tools/check_workitem_traceability.py` implementing the four report
    categories.
  - `--format json|csv` (or `json|text`, see Design) output mode alongside a
    human-readable summary, following the `generate_mcp_inventory.py` `--format`
    precedent.
  - Configurable age threshold (in days) for the "no plan yet" / "no procedure yet"
    reports, defaulting to a generous value.
  - New test file `tests/tools/test_check_workitem_traceability.py` using fixture
    directories (not the live `issues/`/`plans/`/`implementations/` trees).
  - Entry added to `tools/TOOL_DESCRIPTIONS.md`'s checker table.
- **Out-of-Scope**:
  - Automatically fixing, closing, or superseding any stale issue/plan/procedure file.
  - Auto-resolving the stale-target heuristic (item 4) — it must only surface a
    candidate for human/agent review, never an automatic verdict.
  - The other tools proposed alongside this one in the same investigation
    (`tool004_manage_workitem_stage_transitions`, `tool005_rename_doc_and_update_references`,
    `tool006_check_known_deviation_sync`) — tracked as separate issues, not touched here.
  - `tools/generate_workitem.py` (tracked separately; confirmed absent from `tools/` at
    plan time — see Assumptions).
  - Any modification to `issues/*.md`, `plans/*.md`, or `implementations/*.md` files
    (including their `done/` subdirectories) — this tool is read-only: it discovers and
    reports findings, and MUST NOT write, rename, move, or delete any file in those
    trees.

## Background
During the 2026-08-31 ADR-004 rewrite, `issues/20260831-173019_adr004_01_mcp_config_failure_model_alignment.md`
was found to instruct the opposite of what the later-revised current ADR-004 requires.
This drift (a stage-N document whose upstream source changed underneath it) was caught
only because an agent happened to notice it during unrelated work
(`issues/done/20260831-192510_adr004_05_mcp_config_alignment_superseded_by_policy_reversal.md`),
not by any automated check.

## Problem
`skills/issue-to-plan`'s Step 1.5 duplicate detection and
`skills/plan-to-implementation-procedure`'s Step 3 duplicate-work check both rely on
Traceability fields being accurate, but no tool verifies the fields themselves stay
accurate over time as referenced files change, move to `done/`, or are superseded by a
later issue.

## Reason for change
Without this check, staleness like the `adr004_01`/`adr004_05` case is found only by
chance during unrelated work. A dedicated checker turns "an agent happened to notice"
into a repeatable, on-demand verification step, consistent with the other `check_*`
tools already documented in `tools/TOOL_DESCRIPTIONS.md`.

## Implementation intent
Add a standalone script under `tools/` that:
1. Discovers every `issues/*.md`, `issues/done/*.md`, `plans/*.md`, `plans/done/*.md`,
   `implementations/*.md`, `implementations/done/*.md` file.
2. Parses each file's `## Traceability` section (canonical field format:
   `- **Field Name**: value`, per `templates/traceability.md` and the confirmed live
   examples in `plans/20260831-221114_plan.md`, `plans/20260831-222003_plan.md`, and
   `implementations/20260829-185043_09_docs_adr_ADR-012-git-mcp-server-side-write-enforcement_md.md`)
   and extracts `Source issue` / `Source plan` / `Source implementation procedure` /
   `Source requirement` values, treating any value starting with `N/A` as not-applicable
   rather than a path to validate.
3. Reports any referenced source path that does not exist on disk (missing-source-file
   finding).
4. Reports any `issues/*.md` file (not already in `issues/done/`) with no plan
   referencing it as `Source issue`, filtered by a configurable age threshold parsed
   from the file's timestamp-prefixed filename.
5. Reports any `plans/*.md` file (not already in `plans/done/`) with no implementation
   procedure referencing it as `Source plan`, same age-threshold filtering.
6. Applies the best-effort stale-target heuristic: for an issue whose title/summary
   references a named document (e.g. an ADR by number, matched via a regex such as
   `ADR-\d+` or a `docs/...\.md` path mention), check whether that referenced document
   still exists and, if it does, whether it has been modified after the issue's own
   filename timestamp (via `git log -1 --format=%ct -- <path>` or file mtime as a
   fallback) — surface as a candidate for manual review, never an automatic
   resolution/closure.
7. Emits a human-readable summary by default, and machine-readable output under
   `--format json|csv`, mirroring `generate_mcp_inventory.py`'s existing `--format`
   convention (`tools/generate_mcp_inventory.py` — Repository Evidence: confirmed
   `--format` choices `json`/`csv` with `json` as default).

Follow the parsing/CLI conventions already used by sibling `tools/check_*.py` scripts
(argparse-based CLI, `pathlib.Path`-based repo-root resolution, plain-function
structure with a `main()` entry point, as seen in `tools/check_compat_shims.py` and
`tools/check_tool_descriptions_sync.py`) rather than introducing a new pattern.

## Design
This is a new, self-contained, read-only `tools/check_*.py` script — it MUST NOT write,
rename, move, or delete any file under `issues/`, `plans/`, or `implementations/`
(including `done/` subdirectories); its only output is stdout (human-readable summary
or `--format json|csv`). It has no runtime/production interface exposure — it is invoked ad hoc or in CI-style validation, never imported by
`scripts/`. It follows the same shape as existing sibling tools
(`tools/check_compat_shims.py`, `tools/check_tool_descriptions_sync.py`): a small set of
pure functions (discovery, parsing, per-category checking) plus an argparse-based
`main()`. Traceability-field parsing targets the documented format in
`templates/traceability.md` (`- **Field Name**: value` bullet lines under a
`## Traceability` heading), tolerant of the field-set variance already observed between
Plan-level Traceability (no `Requirement ID` field) and implementation-procedure-level
Traceability (`Requirement ID` present) — confirmed via the two live examples cited in
Reference Files. A value is treated as "not a path to validate" whenever it starts with
`N/A` (case-insensitive), matching every sampled Traceability section's convention.

The four report categories are independent passes over the same parsed graph:
1. Missing-source-file: for every non-`N/A` `Source *` field value, check
   `Path(value).exists()` relative to repo root.
2. No-plan-yet: for every `issues/*.md` file (excluding `issues/done/`), check whether
   any parsed `plans/*.md` or `plans/done/*.md` file's `Source issue` field points back
   to it; if not, and the issue's filename timestamp is older than the age threshold,
   report it.
3. No-procedure-yet: symmetric to (2), for `plans/*.md` (excluding `plans/done/`)
   against `implementations/*.md`/`implementations/done/*.md`'s `Source plan` field.
4. Stale-target heuristic: best-effort regex extraction of a referenced document name
   from an issue's title/summary, existence + modified-time comparison against the
   issue's own filename timestamp, surfaced as a candidate finding only (never an
   automatic resolution).

`--format json|csv` serializes the same finding objects the human-readable summary is
built from, so both paths share one internal data structure — this avoids the
finding-shape drifting between the two output modes.

## Risks
- **Risk**: The stale-target heuristic (REQ-005) produces false positives (flagging an
  issue as stale when its target document changed for an unrelated reason, e.g. a
  typo fix) → **Mitigation**: design it strictly as a surfaced candidate for
  human/agent review, never an automatic resolution/closure (per the Issue's own
  Constraints), and document this limitation in the tool's own help text and in the
  `tools/TOOL_DESCRIPTIONS.md` entry.
- **Risk**: A hardcoded or poorly-chosen default age threshold causes noisy "no plan
  yet"/"no procedure yet" findings against normal, recently-filed work → **Mitigation**:
  make the threshold a CLI flag with a generous default (UNK-01), and explicitly
  document in the tool's output that these findings are informational, not errors (per
  the Issue's own Constraints).
- **Risk**: Traceability-field parsing assumes a rigid schema and breaks on
  未見の (not-yet-observed) field-name or formatting variants across the corpus (the
  Issue's own Background evidence shows two live variants already: Plan-level vs.
  implementation-procedure-level Traceability) → **Mitigation**: Phase 1's survey step
  explicitly samples a broader set before finalizing the parser; parsing failures on an
  individual file should be reported as a per-file parse-error finding, not a silent
  skip or a hard crash of the whole run.
- **Risk**: `radon`/`vulture` unavailability in this environment means the validation
  quality baseline is incomplete at Plan time → **Mitigation**: `bandit` was run as the
  available substitute (0 findings); the implementer must re-attempt `radon`/`vulture`
  during `plan-to-implementation-procedure`/implementation in case the target
  environment differs, and record `Tool [name] not available` again if still absent.
