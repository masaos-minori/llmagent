# Plan: Automate metadata field usage policy enforcement (GV-016)

## Goal
Add a new checker under `tools/` that scans `docs/*.md` front matter and workitem files
(`issues/`, `plans/`, `implementations/`) for metadata/status fields outside the sanctioned
field set, then mark GV-016 `Existing`. Keep the check non-blocking and `Warning`-level.

## Priority
Low

## Scope
- **In-Scope**:
  - Define the permitted metadata/status field set per domain from authoritative sources.
  - Scan `docs/*.md` front matter for keys outside the front-matter schema's property set.
  - Scan workitems for `## ` sections outside their template's canonical section set.
  - Flag out-of-set fields at `Warning`.
  - Add unit tests with extra-field and compliant fixtures; run against the current `docs/`
    and `issues/` corpora.
  - Update the GV-016 matrix row to `Existing` and clear its Follow-up note.
- **Out-of-Scope**:
  - Changing the sanctioned field set or the templates.
  - Adding new required fields.

## Background
`governance_04_documentation-checks.md` maps GV-016 ("No unnecessary Metadata or Status fields
added") to human review on a periodic basis, status `Partial`, with the follow-up
"Automate metadata field usage policy enforcement (currently manual)". Permitted fields are
defined by the front-matter policy (`tools/manage_frontmatter.py`,
`tools/check_docs_structure.py`) for `docs/*.md` and by the workitem templates
(`templates/issue.md`, etc.) for `issues/`/`plans/`/`implementations/`.

## Problem
Authors add ad-hoc metadata or status fields to documents and workitems that are not part of
the sanctioned schema, causing drift and inconsistency across the corpus. Manual review between
sweeps does not reliably catch these.

## Reason for Change
GV-016 is a periodic `Warning` gate. Automating field-usage enforcement keeps metadata
consistent and removes reliance on manual sweeps.

## Implementation Intent
Consult the sanctioned field sets for `docs/*.md` front matter and workitem templates, then add
a checker that scans documents and workitems for metadata or status fields outside the
permitted set and flags them. Distinguish the two domains (doc front matter vs workitem
template fields). Keep the check non-blocking.

## Assumptions
- The check is `Warning`-level and non-blocking, consistent with GV-016's existing gate.
- The permitted front-matter set is the schema's defined `properties`: `title`, `area`,
  `tags`, `related`, `status`, `class` (the four required plus the two optional defined
  properties). The corpus currently uses only `title`, `area`, `tags`, `related`, `class`.
- Workitem files map to templates by directory: `issues/` → `issue.md`, `plans/` → `plan.md`,
  `implementations/` → `implementation-procedure.md`.
- Sub-template fragments (`requirement-traceability.md`, `traceability.md`, `risks-issue.md`,
  `unknowns-issue.md`, `execution-status.md`) embedded in `plan.md`/`implementation-procedure.md`
  contribute their sections to the parent's permitted set.

## Design
New standalone CLI following the `tools/check_*.py` convention (argparse, `Issue` results,
`Warning`/`ERROR` severities). Two independent scanners share one reporting path.

1. **Front-matter scanner (REQ-001, REQ-003).** Parse each `docs/*.md` YAML front matter and
   compare its keys against the permitted set derived from `schemas/doc_front_matter.json`'s
   `properties`. Flag keys outside the set. Do not flag the four required fields or the two
   optional defined properties (REQ-005).
2. **Workitem scanner (REQ-002, REQ-004).** Map each workitem file to its template by
   directory. Derive the permitted section set from the template: top-level `## ` sections minus
   meta/instructional sections, unioned with embedded sub-template sections. Flag any `## `
   section in the workitem not in that set (UNK-02, UNK-03).
3. **Reporting.** `Warning`-only; preserve the non-blocking contract.

No change to `schemas/doc_front_matter.json`, `templates/`, or the sanctioned field set.

## Risks
- **Risk**: The workitem section-derivation (meta-section exclusion, sub-template embedding) is
  fuzzy and may false-positive on legitimate workitems. → **Mitigation**: Derive sets from the
  templates themselves (single source of truth), validate against the current corpus first, and
  triage pre-existing extra sections separately (UNK-02, UNK-03).
- **Risk**: Interpreting `additionalProperties: true` as "extra fields are unnecessary" may
  conflict with the schema's intent. → **Mitigation**: Document this interpretation explicitly as
  the GV-016 reading of the schema; revisit if the corpus shows legit extra fields (UNK-01).
- **Risk**: Extending enforcement to workitems may surface many pre-existing variations. →
  **Mitigation**: `Warning`-level (non-blocking); report, do not fail the build; triage
  separately (UNK-03).
