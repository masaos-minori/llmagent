## Goal
- Make `tests/mcp_servers/mdq/test_mdq_incremental_refresh.py::TestRefreshIncrementalBranches::test_failed_reindex_does_not_record_the_new_mtime` deterministic by guaranteeing that the second write gives the file a newer modification time than the first, instead of relying on elapsed time.

## Priority
Low

## Scope
- **In-Scope**:
  - In that one test, set an explicit later modification time with `os.utime` after the second `write_text`, and import `os` in the module.
  - Verify by repeated runs that the test no longer fails.
- **Out-of-Scope**:
  - Changing `_refresh_changed_file`, `index_state`, or any production change detection (including whether size or content should also count); a same-tick, same-size edit is also missed in production, which is a separate design question.
  - Any other test (every other test in the file that rewrites a file already waits with `time.sleep(0.05)`).
  - Adding a characterization test for the same-mtime behavior.

## Background
- The test failed once in a full-suite run on 2026-10-19 (after a rebase) and passed on every rerun; the failure output was not captured. 40 consecutive isolated runs all passed.
- `_refresh_changed_file` in `scripts/mcp_servers/mdq/indexer.py` records `mtime:<path>` as `st_mtime_ns` in `index_state` and skips a file whose stored value equals the current one.

## Problem
- Confirmed on 2026-10-19 with a throwaway test (removed afterwards) that follows the test's steps: when the second write ends with the same `st_mtime_ns` as the first, the refresh counts the file as skipped and the counters are `(0, 1, 0)`; when the mtime is later, they are `(0, 0, 1)`, which is what the test asserts. A tie on the two writes' mtimes therefore reproduces the observed failure condition deterministically.
- The test writes `"# A\n\nOne"`, refreshes, and writes `"# A\n\nTwo"` (same size, 3 bytes) with nothing that forces a newer mtime. The natural tie likely comes from coarse filesystem timestamps on this WSL2 host combined with a fast first refresh; the natural occurrence rate is unmeasured.
- Confirmed by a scan of the module (2026-10-19): this is the only test that writes the same path twice without a guard; `test_directory_refresh_reindexes_changed` already has `time.sleep(0.05)`, and `test_reindexes_changed_file` waits with `time.sleep(0.05)` before its rewrite of the fixture file.

## Reason for Change
- An intermittently red test wastes investigation time (it was investigated as a possible regression after an unrelated rebase) and can fail CI at random.
- The fix is one small, deterministic change that mirrors the intent of the existing sleeps in the same file.

## Implementation Intent
- Make the newer mtime explicit rather than time-based: read the first write's `st_mtime_ns`, write the second content, then call `os.utime(target, ns=(later, later))` with `later` one second after the first value. This works regardless of timestamp granularity and adds no sleep.
- Keep both assertions as they are.
- Do not touch the indexer.

## Requirements
- `REQ-001`: After the second write, `test_failed_reindex_does_not_record_the_new_mtime` sets the file's modification time to a value strictly greater than the first write's, using `os.utime`.
- `REQ-002`: The test stays fast (no sleep) and its assertions are unchanged.
- `REQ-003`: The test passes in 200 consecutive runs, with the machine under CPU load for part of them.
