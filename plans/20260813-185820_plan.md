# Plan: Fix HttpTransport retrying non-retryable HTTP statuses and losing HTTPStatusError context

## Goal

`HttpTransport.call()` (`scripts/shared/http_transport.py`) must stop retrying HTTP status
codes that are not in its own `_RETRYABLE_STATUS` set, and its failure messages must retain
the originating exception type/status code instead of collapsing into a generic
`"[Retry exhausted] ..."` string. Today a 400/404/500 response is retried up to 3 times
(wasting time and risking side effects on non-idempotent calls) and, once retries are
exhausted, the raised `TransportError` message discards the real cause, making incident
diagnosis harder.

## Scope

### In-Scope
- `scripts/shared/http_transport.py::HttpTransport.call` — branch the
  `except httpx.HTTPStatusError` handler on `e.response.status_code in self._RETRYABLE_STATUS`:
  retryable statuses keep the current retry behavior; non-retryable statuses raise
  `TransportError` immediately (fail fast), consuming no further attempts.
- Same method's `for...else` "retry exhausted" branch — include the last caught exception's
  context (status code / exception type) in the raised message instead of the bare
  `"[Retry exhausted] tool=... url=... after N attempts"` string.
- `tests/shared/test_tool_executor.py` — fix
  `TestHttpTransportRetry::test_non_retryable_http_status_not_retried` (currently asserts
  `call_count == 1` for a 500 response but observes 3); add/confirm coverage for a second
  non-retryable status (e.g. 400 or 404) alongside the existing 500 case.
- `tests/shared/test_tool_executor_routing.py` — fix
  `TestHttpTransportErrors::test_http_status_error_raises_transport_error` (currently asserts
  `"HTTPStatusError" in str(exc_info.value)`, which fails against today's generic message).

### Out-of-Scope
- `_RETRYABLE_STATUS = frozenset({429, 502, 503, 504})` membership — not changed unless a
  test explicitly requires it (none found; see Design/Unknowns).
- Retry loop control flow, backoff timing/formula (`2 ** (self._RETRY_MAX - attempt - 1)`),
  and attempt-count semantics — unchanged.
- `scripts/shared/tool_executor.py` / `scripts/shared/tool_transport_invoker.py` — unchanged;
  evidence gathered below shows neither depends on the exact old message text (see Affected
  areas).
- Any `docs/*.md` file — this is a bug fix in existing internal retry classification logic,
  not a documented public contract change; no doc update identified as required.

## Design

`HttpTransport` lives in `scripts/shared/` — the shared transport layer consumed by
`scripts/shared/tool_transport_invoker.py` and `scripts/shared/tool_executor.py`, both of which
sit above it and depend on it only through the public `TransportError` type and `.call()`
coroutine contract, never on internal message formatting. This fix is entirely internal to
`HttpTransport.call()`'s exception-classification logic — no new imports, no new module, no
change to the `_transport_error()` helper's signature or the `TransportError` type itself, so
there is no import-layering or boundary concern (`scripts/shared/` stays self-contained; no
`scripts/agent/` or `scripts/rag/` code touches this).

Concretely, the current `except httpx.HTTPStatusError` handler
(`scripts/shared/http_transport.py:133-139`) always calls `self._transport_error(...,
health_check=False)` without inspecting `e.response.status_code`, so it never uses the
`break_flag=True` early-raise path that `except httpx.TimeoutException`
(`http_transport.py:129-132`) already exercises. The fix makes `HTTPStatusError` follow the
same established pattern used for timeouts: check `e.response.status_code in
self._RETRYABLE_STATUS`; if not retryable, call `_transport_error(..., break_flag=True,
health_check=False)` to raise immediately (mirroring the timeout branch's existing idiom, so no
new control-flow shape is introduced). If retryable, keep today's behavior — set `last_exc` and
fall through to the next loop iteration.

For the "retry exhausted" `for...else` branch (`http_transport.py:142-145`), `last_exc` (an
`Exception | None` already populated inside the loop) is threaded into the final message —
e.g. `f"[Retry exhausted] tool={name} url={self._base_url} after {self._RETRY_MAX} attempts:
{last_exc}"` — so the `TransportError` type and "retry exhausted after N attempts" framing are
preserved (satisfying `test_retries_exhausted_returns_error`'s `"Retry exhausted" in
str(exc_info.value)` and `test_http_503_retry_exhaustion_is_transport_error`'s `"Retry
exhausted" in result.output`) while also satisfying
`test_http_status_error_raises_transport_error`'s `"HTTPStatusError" in str(exc_info.value)` —
because `str(last_exc)` for an `HTTPStatusError`-sourced `_transport_error(...)` call already
embeds the literal string `"[HTTPStatusError]"` in its message (`http_transport.py:136`).

Quality baseline (Path A basic check, `radon cc scripts/shared/http_transport.py -s`):
`HttpTransport.call` is already grade `C (11)` — the most complex method in the file. Adding
one status-code branch is a small, localized increment (roughly +1 decision point) and is not
expected to cross into grade D; `bandit scripts/shared/http_transport.py` reports zero
findings, and `vulture --min-confidence 80` reports no dead code, so there is no pre-existing
issue this change must also clean up.

## Risks

- **Risk**: Enriching the "retry exhausted" message with `last_exc` could unintentionally
  break a test elsewhere that asserts the *exact* old bare-string format.
  → **Mitigation**: `rg` search (Affected areas / UNK-01) found only two tests asserting on
  this message's content — `test_retries_exhausted_returns_error` (`"Retry exhausted" in
  ...`) and `test_http_503_retry_exhaustion_is_transport_error` (`"Retry exhausted" in
  result.output`) — both use substring containment, not exact-match, so appending detail is
  safe. Re-run both explicitly in Phase 2/3. Likelihood: low.
- **Risk**: `HttpTransport.call` is already at cyclomatic-complexity grade C (11); adding a
  branch nudges it further without refactoring, degrading long-term readability.
  → **Mitigation**: keep the added branch minimal (single `if`/`else` inside the existing
  `except` block, mirroring the pre-existing `TimeoutException` `break_flag=True` idiom) rather
  than introducing new helper abstractions in this fix; a follow-up refactor of `call()`'s
  overall structure is out of scope here and can be filed separately if grade D is ever
  reached. Likelihood: low.
- **Risk**: A future status code could be added to `_RETRYABLE_STATUS` without a matching test,
  silently changing retry semantics.
  → **Mitigation**: the new 400 (or 404) test case added in Phase 2 documents the
  non-retryable contract explicitly; existing per-status tests (429/502/503/504) already cover
  every member of the retryable set individually. Likelihood: low.
- **Risk**: The repository currently has many unrelated staged/unstaged changes across
  `scripts/shared/` and `scripts/db/` (per `git status` at plan time), so this fix will land on
  a non-clean tree and could be harder to isolate in review.
  → **Mitigation**: stage only the three files named in this plan's scope
  (`scripts/shared/http_transport.py`, `tests/shared/test_tool_executor.py`,
  `tests/shared/test_tool_executor_routing.py`) individually with `git add <file>`, never
  `git add -A`/`git add .`, per `rules/coding.md`. Likelihood: med (pre-existing repo state,
  not introduced by this plan).
