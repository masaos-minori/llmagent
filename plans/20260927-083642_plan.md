## Background
The test first subscribes with `since_seq=0`, deliberately looping until it has received **all 5** published events (`if len(event_ids_first) == 5: break`), confirms via `/replay` that the consumer offset is now 5, then reconnects with the SAME `consumer_id` but an explicit `since_seq=3`, expecting (per its own comment) "events from seq=4 onwards (2 events: seq 4 and 5)" — i.e., re-delivery of events the first subscription already fully consumed — and finally asserts `event_ids_first.isdisjoint(event_ids_override)` ("No duplicate events between subscriptions").

## Problem
These two expectations cannot both hold: if `since_seq=3` correctly overrides the stored consumer offset and re-delivers events with seq 4 and 5 (as the test's own comment says it should), those event IDs are, by the test's own setup, already members of `event_ids_first` (which was forced to contain all 5 events, including 4 and 5, via the `len(event_ids_first) == 5` break condition). Therefore `event_ids_first.isdisjoint(event_ids_override)` is mathematically guaranteed to be `False` whenever the `since_seq` precedence behavior works exactly as the test's own comment says it should — the test cannot pass as currently written regardless of the correctness of the underlying `since_seq`/consumer-offset resolution logic.

## Reason for change
This is a test-authoring defect (a self-contradictory pair of assertions), not a production regression — no evidence was found that EventBus's actual subscribe/reconnect logic delivers duplicates incorrectly; the test's own scenario makes duplication with the first batch unavoidable by construction. Left unfixed, this test can never pass and provides no real verification of `since_seq`-vs-consumer-offset precedence (T-7 semantics per its own docstring).

## Implementation intent
Redesign the scenario so the two subscriptions' expected event sets are genuinely disjoint by construction: e.g., have the first subscription intentionally disconnect after receiving only a subset of events (e.g., break after 3, corresponding to `event_ids_first = {1,2,3}`), so the stored consumer offset would naturally resume at seq 4 — then the reconnect's explicit `since_seq=3` (identical to what the offset would already produce) does not by itself prove precedence. To genuinely test precedence, the reconnect should instead pass a `since_seq` value *different from* what the stored offset would produce (e.g., offset is 3 after the first subscription disconnects early, but reconnect explicitly requests `since_seq=1`, so the override is provable: the second subscription should receive events 2 and 3 again — an intentional, expected re-delivery — while genuinely NOT receiving event 1, proving the explicit `since_seq` param, not the stored offset, determined the resume point). Confirm the exact intended T-7 semantics against any Requirement/design doc referencing "since_seq precedence" before finalizing the corrected scenario (see Unknowns).
