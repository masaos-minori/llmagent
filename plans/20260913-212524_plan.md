# Improve the RAG artifact JSON verification command's usability and explanation

## Goal
Replace `docs/03_rag_02_01_ingestion_pipeline-overview.md`'s terse `orjson`
verification one-liner with a worked example using a concrete placeholder path,
an explanation of why binary mode (`'rb'`) matches the production code's own
reading pattern, why `orjson` (not the standard `json` module) is used, and a
description of the expected output shape.

## Priority
Low

## Scope
- **In-Scope**: Rewriting the existing one-line verification command note (line
  77) into a short worked example plus explanation covering: placeholder usage,
  why binary mode is used, why `orjson` is used, and what the expected output
  looks like
- **Out-of-Scope**: Building a dedicated verification helper script/tool (the
  Issue's Recommended Action offers this as a "consider" — a weak,
  optional suggestion, not a firm request; no such tool exists in `tools/` today,
  and adding one is a source-code change with its own design/testing scope beyond

  parsing implementation

## Background
The Issue's cited claim
(`docs/03_rag_02_01_ingestion_pipeline-overview.md:77`: "JSON files are parsed
using `orjson.loads()`. For verification: `python -c \"import orjson;
print(orjson.loads(open('FILE', 'rb').read()))\"`") is confirmed accurate — this
exact one-liner exists, with `FILE` as a literal placeholder requiring manual
substitution and no explanation of the `'rb'` requirement.

**Re-verified 2026-09-13** (this cycle): confirmed the binary-mode requirement's
rationale is not arbitrary — `scripts/rag/ingestion/pipeline_utils.py`'s actual
artifact readers (`read_crawl_json()`/`read_chunk_json()`, confirmed at lines
100-113) call `path.read_bytes()` (binary read) and pass the resulting `bytes`
directly to `orjson.loads()` (line 110). The verification command's `'rb'` mode
mirrors this exact production reading pattern — using text mode (`'r'`) would
still work functionally (orjson accepts `str` or `bytes`), but would not
faithfully reproduce how the actual ingestion code reads the file. No comment in
the codebase states an explicit "why orjson over the standard `json` module"
rationale — this is standard, well-known Python ecosystem knowledge (orjson is a
Rust-backed, significantly faster JSON library), not a project-specific design
decision requiring its own citation.

## Problem
The current one-liner requires a reader to manually substitute `FILE` with a real
path, does not explain why binary mode is required (as opposed to being an
arbitrary detail), and gives no indication of what a successful/failed
verification looks like — making it harder to use in practice than necessary.

## Reason for change
Replace the bare one-liner with a worked example using a concrete placeholder
path format, explain the binary-mode requirement by referencing the actual
production reading pattern it mirrors, and describe the expected output shape —
so an operator can use the command directly with minimal adaptation.

## Implementation intent
Replace line 77 with: (1) a worked example using a placeholder in the actual
artifact path format documented in the same table (e.g.
`{rag_src_dir}/{timestamp}-{slug}.json`), substituted into the command; (2) a
one-clause explanation that binary mode matches `read_crawl_json()`/
`read_chunk_json()`'s own `path.read_bytes()` reading pattern; (3) a one-clause
note that `orjson` is used for its performance characteristics versus the
standard `json` module; (4) a description of the expected output (a Python `dict`
printed to stdout, or an exception if the file is not valid JSON).

and found the binary-mode requirement has a concrete, code-backed rationale (it

Key design decisions:
1. Explain binary mode via the production code pattern it mirrors, rather than a
   generic "orjson prefers bytes" statement — the concrete tie to
   `read_crawl_json()`/`read_chunk_json()` gives the explanation a verifiable
   basis, and tells a reader the verification command is deliberately faithful to
   production behavior, not an arbitrary detail
2. Do not build a helper script (per Design decision in Scope) — the Issue's own
   phrasing ("Consider adding") marks this as optional; a one-line worked example
   plus explanation already resolves the stated usability complaint without
   introducing new source code to maintain
