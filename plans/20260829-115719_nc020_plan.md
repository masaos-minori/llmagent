# Plan: NC-020 Git MCP Audit Log Target Resolution

## Goal
- Establish canonical, validated repository identity as the audit log `target` field for Git MCP write operations, covering pre-validation rejection paths and post-validation failure paths, while ensuring no remote-URL credential material reaches the Git-MCP-server-side audit record.

## Priority
Medium

## Scope
- **In-Scope**: Implement common canonical target resolution in `git_server.py::call_tool()` modeled on `mdq`'s `extract_audit_target()` pattern; resolve cross-server pre-dispatch-audit convention question; add unit/integration/log-verification tests; update tracking docs (`NC-020`, `MCP-005`) and all four `ADR-012` locations.
- **Out-of-Scope**: Extending canonical-target-resolution to other 7 MCP servers; Agent-side `tool_audit.py`/`mask_args()` credential-masking gap redesign; changing `AuditRecord` schema in a way that breaks other MCP servers; Dirty-Worktree/Detached-HEAD/postcondition-verification guards tracked separately as `GIT-001`/`GIT-002`/`NC-019`.

## Background
Git MCP server has a protected-branch enforcement mechanism documented in `ADR-012-git-mcp-server-side-write-enforcement.md` Decision Details #7, which requires that "Audit records for Git MCP write operations MUST include the correct repository identity." However, the current audit `target` field uses whatever raw string the caller supplied, not a validated/canonical identity. Additionally, pre-dispatch rejections (disabled tool gate, validate_args ValueError) are never audited at all -- a systemic pattern across MCP servers, not Git-specific, with at least one server defending it as intentional. The `mdq` MCP server already implements almost exactly the "common, canonical target-resolution function used by every tool" pattern needed here via `scripts/mcp_servers/mdq/audit_target.py::extract_audit_target()`.

## Problem
Confirmed by reading current source code:

- **Key-mismatch status is stale in the tracking docs.** `git_server.py` line 137 currently reads `target=cast(str, req.args.get("repo_path", ""))` -- the correct key -- as of commit `a53e9c62d` (2026-08-21). `NC-020`'s Evidence and `MCP-005`'s Summary/Current Description still describe the call site as reading `"repo"`. This specific claim needs correcting in both tracking entries regardless of what live-log capture finds.
- **Target is the raw, unvalidated caller string, not a canonical identity.** `GitSecurityGuards._check_repo_path()` (`scripts/mcp_servers/git/git_security.py`) already computes `target = Path(repo_path).resolve()` to validate the path against `allowed_repo_paths`, but only returns `(bool, str)` -- the resolved path is discarded rather than reused for the audit record. The audit `target` is therefore whatever string the caller supplied, before validation.
- **Pre-dispatch rejections are never audited at all -- and this is a systemic pattern across MCP servers, not Git-specific, with at least one server defending it as intentional.** In `call_tool()`, the "Tool disabled" early return and the `validate_args()` `ValueError` early return both `return CallToolResponse(...)` before `_audit_log()` is ever called -- no audit record is emitted for either case. The same gate-before-audit placement exists in `shell_server.py` and `cicd_server.py`. `web_search_server.py` has the identical placement, but with an explicit code comment defending it. Fixing this for Git MCP alone will make Git MCP diverge from what looks like a deliberate cross-server convention -- this needs a decision, not just an implementation, before Phase 2 proceeds.
- **`remote` is unvalidated free text that could carry credentials -- but this risk is currently prospective on the Git-MCP-server side specifically.** On the Git-MCP-server side, `remote` is never actually logged today -- `git_server.py`'s `_audit_log()` call only ever passes `repo_path` as `target`, so there is no live MCP-server-side leak yet; the risk is design-time, tied to how Phase 2's "canonical target" gets built. **However**, `scripts/agent/tool_audit.py::audit_approval()`/`audit_tool_exec()` both call `mask_args(args, ctx.cfg.tool.masked_fields)` and write the resulting `args_preview` -- effectively the full args dict, only fields named in `masked_fields` are redacted -- verbatim into the Agent-side `tool_approval`/`tool_exec` audit log. `config/agent.toml`'s `masked_fields = ["file_content"]` does not include `remote`. So a credential-bearing URL passed as `remote` to `git_push`/`git_pull` is written in plaintext into the Agent-side audit JSON **today**, independent of anything this issue's Git-MCP-server-scoped fix would touch.
- **A correlation mechanism may already exist but does not currently join the way one might assume.** The MCP-server `AuditRecord` carries `request_id` (a per-call ID minted by each server's own middleware), and `scripts/agent/tool_audit.py::audit_tool_exec()` records the same value as `mcp_request_id`. Confirmed: `approval_id` (from `audit_approval_requested()`) and `mcp_request_id`/`request_id` are **not** the same key -- they are minted at different points by different mechanisms. So `request_id`/`mcp_request_id` already correlates an MCP execution record back to the Agent's own tool-exec log entry, but does **not** currently provide a path from an approval decision (`approval_id`) to the MCP execution record.
- **`error_type` is not a new field to add -- it already exists in the shared `AuditRecord` schema, with two already-inconsistent vocabularies in use.** `mdq` uses Python exception-class names via `type(exc).__name__`; `web_search` uses lowercase-snake strings like `"validation_error"`. The real design question for Phase 2 is which vocabulary style Git MCP should adopt, not whether the field needs to be introduced.
- **No existing test anywhere in the MCP test suite parses real emitted JSON audit-log lines -- not even `mdq`'s.** `tests/mcp_servers/mdq/test_mdq_exception_handlers.py::test_logs_audit_entry_with_error_type` only mocks `_audit_log` and asserts on the call's kwargs; it does not parse actual log output. This means the Acceptance Criteria item "a test exists that verifies actual emitted JSON audit-log content" has zero precedent anywhere in this codebase to copy -- it is a genuinely novel test shape.

## Reason for change
Git MCP's write tools (`git_checkout`, `git_pull`, `git_push`, plus `git_add`/`git_commit`) mutate repository state and are documented as a High-Severity write surface (`MCP-003`). An audit trail for that surface that cannot reliably identify which repository was affected and cannot distinguish a rejected call from a failed one is a real gap in the operability posture ADR-012 is meant to establish, independent of whether the originally-suspected key-mismatch bug is already fixed. Priority is Medium rather than Low primarily for that operability reason; it is **not** primarily because of an active, already-observed credential leak on the component this issue actually touches -- on the Git-MCP-server side specifically, the credential-exposure risk is prospective, tied to how Phase 2's target-resolution design turns out, not something currently happening.

## Implementation intent
Three phases, in order -- do not skip Phase 1 based on the code-reading evidence above; it is necessary to establish current ground truth before designing the fix, and to correct the stale tracking-doc claims either way.

1. **Capture real logs to confirm current behavior.** Run representative Git MCP calls (success, rejection via disabled tool, `validate_args()` failure, dispatch failure) against a live instance and capture the actual emitted `AuditRecord` JSON lines. Confirm whether `target` is now non-empty for the already-fixed `repo_path` key, and confirm the pre-dispatch-rejection gap (no audit line emitted at all) reproduces as read from the code. Update `NC-020` and `MCP-005`'s Evidence/Current-Description text to reflect what was actually observed, including correcting the stale `"repo"`-key claim.
2. **Implement common, canonical target resolution -- modeled on `mdq`'s existing pattern.** Read `scripts/mcp_servers/mdq/audit_target.py::extract_audit_target()` and `mdq_server.py`'s exception-handler flow first; do not design from a blank slate. At the single `call_tool()` chokepoint in `git_server.py`, introduce one target-resolution step used by every Git tool that: (a) uses the validated/canonical repository identity (reusing or exposing the `Path(repo_path).resolve()` value already computed in `GitSecurityGuards._check_repo_path()` instead of the raw caller string), (b) is invoked on the pre-dispatch-rejection paths too -- **only after resolving the cross-server convention question in Unresolved Questions below**, since `web_search_server.py` defends the current placement as intentional and changing only Git MCP's behavior would create a new inconsistency, (c) never includes remote-URL credential material in the Git-MCP-server-side audit record specifically -- scrub or reject credential-shaped `remote` values before they can reach the target or any log line on this side, while treating the Agent-side `tool_audit.py` exposure as a separate, out-of-scope finding to be filed independently, (d) adopts a deliberate `error_type` vocabulary choice (matching one of `mdq`'s or `web_search`'s existing styles, or documenting a reason to introduce a third) rather than treating the field as new, and (e) confirms that `request_id`/`mcp_request_id` already correlates MCP execution records with the Agent's tool-exec log -- and, separately, decides whether `approval_id` specifically also needs a new plumbing path, since it does not currently share a key with `request_id`.

## Design
Three-phase approach modeled on `mdq`'s existing pattern:

**Phase 1: Capture real logs.** Run representative Git MCP calls against a live instance and capture the actual emitted `AuditRecord` JSON lines. This establishes ground truth before designing the fix.

**Phase 2: Implement canonical target resolution.** At the single `call_tool()` chokepoint in `git_server.py`, introduce one target-resolution step used by every Git tool. The key design decisions:
- Reuse the `Path(repo_path).resolve()` value already computed in `GitSecurityGuards._check_repo_path()` instead of the raw caller string -- modify `_check_repo_path()` to return `(bool, str, str)` where the third element is the resolved path (or empty string on validation failure).
- Invoke the target-resolution on pre-dispatch-rejection paths too -- **only after resolving the cross-server convention question in Unresolved Questions**.
- Never include remote-URL credential material in the Git-MCP-server-side audit record -- scrub or reject credential-shaped `remote` values before they can reach the target or any log line on this side.
- Adopt a deliberate `error_type` vocabulary choice -- document which style is chosen and why.
- Confirm `request_id`/`mcp_request_id` correlation suffices for the acceptance criterion, or add `approval_id` plumbing if needed.

```python
# Proposed design sketch (subject to Phase 1 findings):

def _check_repo_path(self, repo_path: str) -> tuple[bool, str, str]:
    """Return (ok, error_message, resolved_path).
    
    ok=True when repo_path is within an allowed path prefix.
    resolved_path is the canonical identity (empty string when ok=False).
    """
    if not self._allowed:
        return False, _repo_denied_msg(repo_path), ""
    target = Path(repo_path).resolve()
    for allowed in self._allowed:
        if target.is_relative_to(allowed):
            return True, "", str(target)
    return False, _repo_denied_msg(repo_path), ""

def call_tool(req: CallToolRequest, request: Request) -> CallToolResponse:
    """Handle a generic MCP call_tool request with audit logging."""
    enabled, reason = _git_tool_availability(_cfg, req.name)
    if not enabled:
        # Audit pre-dispatch rejection AFTER resolving cross-server convention
        session_id, request_id = extract_request_context(request)
        _audit_log(logger, session_id, request_id, req.name,
                   target="-", outcome="rejected", server_key="git",
                   error_type="tool_disabled", detail=reason)
        return CallToolResponse(result=f"Tool disabled: {reason}", is_error=True)
    try:
        req.validate_args()
    except ValueError as e:
        # Audit pre-validation rejection AFTER resolving cross-server convention
        session_id, request_id = extract_request_context(request)
        _audit_log(logger, session_id, request_id, req.name,
                   target="-", outcome="rejected", server_key="git",
                   error_type="validation_error", detail=str(e))
        return CallToolResponse(result=f"Validation error: {e}", is_error=True)
    t0 = time.perf_counter()
    session_id, request_id = extract_request_context(request)
    r = await _dispatch_git_tool(req.name, req.args)
    ms = (time.perf_counter() - t0) * 1000
    # Use canonical target resolution here
    ok, err, resolved_path = _service.security._check_repo_path(
        cast(str, req.args.get("repo_path", "")))
    target = resolved_path if ok else "-"
    _audit_log(
        logger,
        session_id=session_id,
        request_id=request_id,
        action=req.name,
        target=target,
        outcome=r.outcome,
        server_key="git",
        error_type=_classify_error(r),  # deliberate vocabulary choice
    )
    return _to_call_tool_response(r)
```
