## Goal
- Make Bearer-token authentication mandatory (non-empty, validated at startup
  before tool discovery) for every HTTP MCP service, load tokens from environment
  variables rather than committed TOML values, and redact token values from logs
  and diagnostics — closing a confirmed, currently active no-auth gap.

## Priority
High

## Scope
- **In-Scope**: the files listed in Implementation Target Files below; startup-time
  non-empty `auth_token` validation before tool discovery; environment-variable-
  based secret loading; `auth_token`/`Authorization`-header redaction in logs;
  documenting authentication as restart-only.
- **Out-of-Scope**: Event Bus authentication implementation (Event Bus stays
  loopback-only, per source Issue Constraints); public HTTP access, TLS, or
  reverse-proxy deployment; general secret-management redesign beyond MCP
  authentication; changing public API payloads.

## Background
This Issue's rationale depends on `loopbackonly`'s direction
(`plans/done/20260903-091921_plan.md`, archived 2026-09-04) but is independently
implementable, since
authentication should already be mandatory regardless of bind-address scope
(source Issue Dependencies).

## Problem
`scripts/mcp_servers/server.py`'s `attach_auth_middleware()` (repository evidence,
full read) implements `_is_authorized()` as `if not token: return True` — an empty
`auth_token` disables authentication entirely for that server, by design
(docstring: "When token is empty, auth is skipped"). Every MCP server's `auth_token`
is currently set to `""` in the live configuration: all 10 `[mcp_servers.*]`
entries (**corrected 2026-09-04**, was miscounted as 9) in `config/agent.toml`
(lines 299-391) and the 3 standalone MCP server configs
(`config/git_mcp_server.toml:16`, `config/cicd_mcp_server.toml:23`,
`config/web_search_mcp_server.toml:26`) set an empty token — meaning every MCP
server in this deployment currently runs with authentication effectively disabled,
not merely latently disable-able. `scripts/shared/http_transport.py:99-100`'s
client-side `Authorization: Bearer {token}` header logic is correct and
unaffected — the gap is entirely on the empty-token-is-accepted server side and
the all-empty deployed configuration. No environment-variable or secret-file
loading path for `auth_token` exists anywhere in `scripts/shared/config_utils.py`
or `scripts/shared/mcp_config.py` (repository evidence: `rg` found none) — tokens
can only be set as plain TOML values today. No `auth_token`/`Bearer`-specific
redaction exists in `scripts/agent/tool_result_formatter.py`'s `mask_args()` (that
mechanism masks tool-call arguments like `file_content`, not HTTP headers or
config values) or in logging call sites (repository evidence: `rg` found no match).

**Corrected 2026-09-04** (`plan-to-implementation-procedure` Step 2/3
revalidation): `config/agent.toml` actually has **10**, not 9, `[mcp_servers.*]`
sections with an empty `auth_token` (`shell`, `git`, `web_search`, `file_delete`,
`file_write`, `file_read`, `github`, `cicd`, `rag_pipeline`, `mdq` — confirmed via

## Reason for Change
Removing authentication because external publication is prohibited (per
`loopbackonly`) would weaken defense in depth. The current all-empty-token
deployment already has this gap today, independent of `loopbackonly`'s outcome, so
closing it does not wait on that Plan's implementation.

## Implementation intent
Add a startup-time check (before tool discovery) that every configured HTTP MCP
server's `auth_token` is non-empty, failing startup with a clear error if any is
empty — reusing `ProductionConfigValidator`'s strict-mode pattern
(`scripts/shared/production_config_validator.py`) or a new dedicated check in
`scripts/agent/startup.py`. Add environment-variable-based token loading (e.g. a
`${ENV:VAR_NAME}`-style TOML value or a documented env-var-per-server convention)
to `scripts/shared/config_utils.py`/`scripts/shared/mcp_config.py`, so
`config/*.toml` files reference secret sources rather than embedding tokens
directly — actual token values are supplied only via environment/secret files at
deploy time, never committed. Add `auth_token`/`Authorization`-header redaction to
logging, exception messages, diagnostics, and configuration previews. Document
that `auth_token`, MCP server definitions, and bind-address changes require full
restart, extending `config_reload.py`'s existing `needs_restart` classification
(already flags changed `mcp_servers/{key}.{field_name}` entries) to explicitly
name `auth_token` in its documentation.

## Design
Path A/B classification (see `skills/issue-to-plan/SKILL.md` Routing): **Path B** —
this Plan changes a runtime-facing authentication interface across 10+ source/config
files plus 3 test files, exceeding every Path A criterion. Architecture analysis
confirmed the authentication data flow is one-directional:
`config/*.toml` → `mcp_config.py` (parse/validate) → `server.py`
(`attach_auth_middleware`, server-side enforcement) and → `http_transport.py`
(client-side header injection) — no circular dependency. The core design decision
is where to enforce the non-empty check: this Plan places it in
`scripts/agent/startup_validation.py`'s `StartupValidationPipeline.check_services()`
pre-discovery validation phase (alongside the existing Security audit step —
**corrected 2026-09-04**, replaces the stale `scripts/agent/startup.py:330-334`
citation; see Implementation Target Files), not inside `mcp_config.py`'s
per-field `_validate_auth_token`, because Path A's "no config change" test-only
paths (e.g. deliberately empty tokens in isolated unit tests unrelated to startup)
must not be broken — the enforcement point is "can this configuration start a real
Agent process," not "can this dataclass be constructed at all." Historical
analysis (`git log --since=30.days`) found `scripts/agent/startup_validation.py`
at 1 commit/1 author (a new file from the unrelated upstream refactor, re-measured
2026-09-04, replacing the stale "`startup.py` (11 commits) highest-churn" claim);
`scripts/shared/logger.py` and the two zero-churn standalone MCP configs carry
lower change-conflict risk. Operational
dependency inspection: this Plan changes 4 live deployed `config/*.toml` files, so
a deploy step is mandatory (Implementation steps Phase 3) — confirm no MCP server
process holds a stale empty-token config after the environment-variable migration
lands, per `rules/ai-execution.md` Repository Tool Usage.

## Risks
- **Risk**: Migrating `auth_token` to environment-variable references without
  first setting the actual environment variables in the deployment environment
  would make every MCP server fail to start (by design, per `REQ-001`) →
  **Mitigation**: Phase 3's deploy step explicitly sets the actual token values as
  environment variables before restarting affected services; sequence config
  migration and environment setup together, not config-first.
- **Risk**: The startup-time non-empty check (REQ-001) could be placed too late
  (after discovery) or too early (before all config is loaded), producing a
  confusing failure → **Mitigation**: Design places it explicitly in `startup.py`'s
  pre-discovery validation phase, alongside the existing Security audit step.
- **Risk**: Adding redaction to `scripts/shared/logger.py` could inadvertently mask
  legitimate non-secret log fields if the redaction pattern is too broad →
  **Mitigation**: `REQ-004`'s redaction targets the specific `auth_token` value and
  `Authorization: Bearer <token>` header pattern, not a generic keyword-based
  filter; `tests/shared/test_mcp_config_validation.py`/new log-capture tests (Phase
  3) must confirm no unrelated field is masked.
- **Risk**: `UNK-01`'s environment-variable naming convention, if chosen
  inconsistently across the 4 config files, could make secret management harder to
  audit → **Mitigation**: `plan-to-implementation-procedure` must apply one
  consistent naming convention across all 4 files in the same implementation pass.
