## Goal
- Add RAG-specific and Session-specific logical (application-level) verification as a stage in `_restore_from_backup()`'s existing post-restore sequence, executed after the current physical `_run_integrity_check()` re-check succeeds and before `success=True` is reported, so a restored `rag.sqlite`/`session.sqlite` cannot be reported recovered while missing required tables, having FTS/vector orphans, or containing invalid session/message/memory relationships.

## Priority
Medium

## Scope
- **In-Scope**:
  - A new result model distinguishing physical-integrity outcome from logical-verification outcome.
  - RAG logical verification, reusing `check_rag_consistency()`/`is_consistent()` (`scripts/db/rag_consistency.py`) — no new RAG-side consistency logic.
  - A new Session logical verification function (new module, mirroring `rag_consistency.py`'s structure) covering: required tables exist, sessions readable, message→session referential validity, memory/memory-link validity, session diagnostics readable, a read smoke test, and a conditional write smoke test.
  - Integrating both into `_restore_from_backup()` as a stage after the existing physical re-check, gated so a logical-verification failure prevents `success=True`.
  - Propagating the distinguishable physical/logical result through `DbRecoverResult` (`scripts/agent/services/models.py`) and the two maintenance-service `recover()`/`recover_session()` methods, and surfacing it in the `/session recover` CLI output.
  - Fault-injection tests for both domains' logical-corruption cases.
  - Documentation stating which checks are automated vs. operator-only.
- **Out-of-Scope** (per Issue's own Out of Scope and Constraints):
  - Workflow or EventBus logical verification (tracked by `H-07-08`).
  - Any change to RAG ingestion or Session retention policy.
  - Any silent repair of authoritative data, or rebuilding authoritative data from a derived index.
  - Re-implementing or modifying `_restore_from_backup()`'s existing physical-verification sequence (backup validation, atomic staging, corrupt-archive, physical re-check) — already correct and resolved (`SHARED-002`).
  - Adding a `/session rag-recover`-style CLI dispatch entry for `RagMaintenanceService.recover()` — that method is currently unreachable from any CLI command (see Unknowns UNK-01); wiring it up is a separate concern this Issue did not request.
  - Fixing the three pre-existing failing tests in `tests/integration/test_session_recovery.py` found during Step 3 inspection (see Risks) — unrelated to this Issue's change.

## Background
Physical restoration and its verification are already implemented and resolved: `scripts/db/recovery.py`'s `_restore_from_backup()` validates the backup's physical integrity before use (`_run_integrity_check()`), performs atomic staged replacement (`shutil.copy2()` to a temp file, then `os.replace()`), archives the prior corrupt database, and re-runs `_run_integrity_check()` on the restored file before reporting success — returning `action="restore_verify_failed"` on failure (Confirmed by repository evidence, full read of `scripts/db/recovery.py`). This closed `SHARED-002` (`docs/00_governance_03_issue-and-uncertainty-management.md`, Status: resolved).

Does not depend on further physical-recovery implementation work.

## Problem
Confirmed by full reading of `scripts/db/recovery.py` and `scripts/db/rag_consistency.py`: `_restore_from_backup()`'s post-restore re-check (line 140, `_run_integrity_check(db_path, target)`) calls only SQLite's `PRAGMA integrity_check` — it does not call `check_rag_consistency()` or any Session-specific check. A restored `rag.sqlite` can therefore report `action="restored", success=True` while `chunks_vec`/`chunks_fts` are out of sync with `chunks` (`check_rag_consistency()` already detects exactly this — `fts_gap`, `fts_orphan_count`, `orphan_vec_count`, `documents_without_chunks_count`, per `scripts/db/rag_consistency.py`, Confirmed by repository evidence). A restored `session.sqlite` can similarly report success with orphaned `messages`/`memory_links` rows, since no Session-side consistency function currently exists anywhere in the repository (Confirmed by repository evidence: no file under `scripts/db/` or `scripts/agent/services/` implements Session-equivalent logical checks; `scripts/db/schema_sql.py`'s `_SESSION_SCHEMA_TEMPLATE` defines `messages.session_id REFERENCES sessions(session_id) ON DELETE CASCADE` and `memory_links.src_id/dst_id REFERENCES memories(memory_id) ON DELETE CASCADE`, but SQLite `PRAGMA integrity_check` does not evaluate declared foreign keys for the general referential-validity question this Issue asks for, only physical B-tree consistency).

Separately, `check_rag_consistency(db)` takes an already-open `SQLiteHelper` connection, not a `target` parameter — it operates only against `rag.sqlite`'s schema (`chunks`/`chunks_fts`/`chunks_vec`/`documents`) and cannot be reused as-is for `session.sqlite` (Confirmed by repository evidence, full read of `scripts/db/rag_consistency.py`). This confirms the Issue's own instruction to write a new Session-specific function rather than generalizing `check_rag_consistency()`.

`DbRecoverResult` (`scripts/agent/services/models.py`) currently has only `integrity_ok: bool`, `recovered: bool`, `detail: str` — no field can currently distinguish a physical-recovery failure from a logical-verification failure at the CLI-facing layer (Confirmed by repository evidence, full read of `scripts/agent/services/models.py`), so this Plan's `Implementation Target Files` includes that DTO and its two producers/one consumer, not only `scripts/db/recovery.py`.

## Reason for change
Define and enforce the minimum logical conditions required before a restored RAG or Session database may be returned to service, closing the gap between "physically valid" (SQLite B-tree structure intact) and "usable by the application" (referential/derived-index consistency intact) — the same "recovery mechanism that cannot distinguish failure categories is more dangerous than none" argument `docs/adr/ADR-008-sqlite-4db-separation.md` Rationale §4 already makes for physical-vs-transient failure classification applies here to physical-vs-logical failure classification.

## Implementation intent
Integrate both domains' logical verification into the existing post-restore step in `_restore_from_backup()`, immediately after the current physical `_run_integrity_check()` re-check succeeds (line 140-152) and before `RecoveryResult(success=True, action="restored", ...)` is returned (line 155-157) — do not restructure the preceding physical-verification sequence. For RAG, reuse `check_rag_consistency()`/`is_consistent()` directly against the freshly-restored `rag.sqlite` connection; do not duplicate its counting/orphan-detection logic. For Session, implement a new, narrowly-scoped `check_session_consistency()` in a new `scripts/db/session_consistency.py` module (mirroring `rag_consistency.py`'s existing shape: a report dataclass, a `check_*` collector function, an `is_consistent()` predicate) covering only the checks the Issue lists — do not invent additional Session invariants beyond what the schema and Issue require. Keep the physical (`DbCondition`) and logical (new report type) results as separate fields on the return value so a caller can distinguish "physically corrupt" from "physically fine but logically broken," per Constraints.

## Risks
- **Risk**: `_restore_from_backup()` is already at cyclomatic complexity B(10) (`radon cc`, measured 2026-09-05) and `recover_corruption()` at B(8); adding a `target`-gated logical-verification branch could push either into C or worse, increasing future-maintenance risk. → **Mitigation**: Extract the new RAG/Session branch dispatch into a small private helper function (mirroring `_classify_error()`'s existing extraction pattern) rather than inlining an `if/elif` chain directly into `_restore_from_backup()`; re-run `radon cc scripts/db/recovery.py -s` after implementation and treat a jump to C or worse as a signal to extract further, not accept silently.
- **Risk**: 3 pre-existing test failures were found in `tests/integration/test_session_recovery.py` during the Step 3/5 baseline run (`test_e02_recover_corruption_raises_uncaught_database_error`, `test_e03_recover_corruption_no_backup_raises_uncaught_database_error`, `test_e04_recover_corruption_dry_run_raises_before_mutation_check` — all expect `sqlite3.DatabaseError` to propagate uncaught, but `_classify_error()` now catches and classifies it as `DbCondition.CORRUPTION`, per current code) — unrelated to this Issue, but risk of being conflated with new test results or accidentally "fixed" as an unrelated scope-creep change. → **Mitigation**: Explicitly exclude these 3 from this Plan's scope (see Out-of-Scope); record their pre-existing failure count before implementation and confirm it is unchanged (not increased, not silently "fixed") after this Plan's new tests are added.
- **Risk**: `RagMaintenanceService.recover()` has no CLI dispatch entry (UNK-01) — RAG logical-verification integration can only be exercised via direct unit/integration test calls to `recover_corruption(target="rag")`, not via manual `/session`-style operator testing. → **Mitigation**: Rely on `tests/db/test_db_recovery.py`'s fault-injection coverage as the primary verification for the RAG path (`REQ-007`) rather than manual CLI verification; flag the CLI-reachability gap as a candidate follow-up issue rather than silently expanding this Plan's scope to fix it.
- **Risk**: A Session write smoke test (UNK-02) executed against a freshly-restored, already-committed `session.sqlite` file could itself introduce a stray row if a test/implementation bug leaves it uncleaned. → **Mitigation**: Implement the write smoke test as insert-then-delete within the same connection/transaction scope, and add a dedicated unit test asserting the table's row count is unchanged after the smoke test runs (before-count == after-count).
