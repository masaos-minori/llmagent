# Implementation Plan: history compression reorders messages by importance and duplicates the summary block

**Plan ID**: 20261023-183637
**Source Issue**: `issues/20261021-093421_turn006_history-compression-reorders-and-duplicates-summary.md`
**Generated**: 2026-10-23 18:36 JST

## Goal

Make `HistoryManager.compress()` produce a compressed history that keeps the conversation in the order it
happened, never separates an `assistant` `tool_calls` message from the `tool` results that belong to it, and
contains exactly one `[Conversation summary]` message that replaces the previous summary instead of accumulating
copies. Report the size of the summary block the compression produced. Replace the value-equality filtering that
silently discards distinct messages with position-based accounting, and delete the category/importance partition
machinery the rewritten selection does not use.

## Priority

High

## Background

- The compression path is one call chain: `ConversationStateManager.compress_context()` →
  `HistoryManager.compress()` (`scripts/agent/history.py:261-291`) →
  `HistorySelectionPolicy.select_turns_to_compress()` (`scripts/agent/history_selection_policy.py:121-160`). The
  new history is written back through `ConversationStateManager.replace_messages()`, and
  `conversation_state_manager.py:148-165` records `undo_floor = len(history)` after the replacement, so whatever
  this Plan changes is what `/undo` and the next request see.
- `SelectionResult` (`history_selection_policy.py:18-24`) has exactly three fields — `system_msgs`,
  `to_compress`, `remaining` — and is read only by `history.py` and the tests
  (`grep -rn "SelectionResult" scripts/ tests/`). No other consumer depends on its contents.
- A tool round is contiguous in stored history: `scripts/agent/tool_runner.py:242-246` appends each `tool` result
  immediately after the assistant message that declared the call. `scripts/agent/tool_result_pairing.py` pairs
  only the live round (`pair_round_results(declared, answered, …)`) and nothing in the repository repairs an
  orphaned `tool` row in stored history, so a split round is what the next request sends to the provider.
- Ephemeral system messages (`_ephemeral`, `_memory_injected`) are removed at the start of the next turn by
  `conversation_state_manager.clear_previous_turn_ephemeral_messages()` (`conversation_state_manager.py:30,76`),
  so they are not a carrier for the summary and stay protected by the system-role split
  (`history_selection_policy.py:129-135`).
- Counters reach the user through `CompressResult` → `stat_compress_count` /
  `stat_fallback_truncate_count` → `scripts/agent/commands/cmd_config_stats.py:84-87` and `/compact`
  (`cmd_rag_export.py:47-51`), and through `scripts/agent/session_persister.py:136-138`.
- Contract text that describes today's behavior: `history.py:53-55` ("the oldest `compress_turns * 2` messages
  are summarised") and `docs/23_agent/agent_04_02_state-and-persistence-history-compression.md:35-58,101-107`.
- Production state, measured 2026-10-23: `/opt/llm/db/session.sqlite` holds 6 sessions with 0 messages and 0
  rows whose content starts with `[Conversation summary]`. There is no deployed witness of a duplicated summary
  and no deployed history large enough to compress; every witness in `## Problem` is a probe against the current
  code.

## Problem

- **The retained history is not chronological.** With `compress_turns=1, protect_turns=1` and the input
  `[system, user "question one", assistant tool_calls c0, tool c0, user "always remember this rule", assistant
  "understood, I will always comply", user tail, assistant tail]`, `to_compress` takes the 0.9-scoring policy
  user message *and the older 0.6-scoring assistant tool-call message*, while the answer to that policy message
  is retained. The retained turn messages carry input indices `[5, 1, 3, 6, 7]` — "retained order is
  chronological: False" (`/tmp/opencode/turn006_probe6.py`, `turn006_probe6.out`). Mechanism:
  `compressible = self.sort_by_importance(…)` then `remaining = compressible[n_compress:] + protected_tail`
  (`history_selection_policy.py:142-157`).
- **A tool round is split, and the split reaches the provider.** The same probe's retained history contains
  `tool_call_id=c0` with no declaring assistant. End-to-end through `compress()`: `declared ids: []`,
  `answered ids: ['t1']` (`/tmp/opencode/turn006_probe5.py`, `turn006_probe5.out`).
- **The category partition is dead.** `classify()` is never reached with a `system` message from this path
  (`history_selection_policy.py:129-135`), so `factual` is always empty: `partition sizes: temporary=2
  temporary_reasoning=2 factual=0 history=10`, "factual is empty in this method: True", and the `remaining =
  factual + remaining` prepend at `:154` adds nothing (`turn006_probe1.out`).
- **Messages are silently dropped.** The old partition is re-joined with `not in` value-equality filters, so
  distinct messages that happen to have identical content disappear: measured 16 input messages, 14 accounted,
  2 `user "duplicate identical text"` lost (`turn006_probe1.out`).
- **The summary accumulates instead of replacing.** `_build_summary_msg()` concatenates the new summary onto the
  existing summary message (`history.py:237-259`) and `_build_compressed_result()` appends a new one
  (`:380-398`). Over three `force_compress()` cycles a history went 0 → 1 → 2 → 3 summary messages; its message
  count dropped 41 → 34 → 27 → 20 while its total content length grew 403 → 564 → 931 → 1296 characters, the
  individual summary blocks grew 233 → 445 → 445
  characters, and the probe reports "newest summary re-includes the previous one verbatim: True"
  (`/tmp/opencode/turn006_probe2.py`, `turn006_probe2.out:38-49`). Compression keeps growing the context it
  exists to shrink.
- **The fallback splits a round too.** `_fallback_truncate()` dropped only the `tool` output for `a1` and kept the
  assistant message declaring `a1` (`/tmp/opencode/turn006_probe3.py`, fallback case, output
  `turn006_probe3c.out`: `compressed_count=1`, 678 → 464 chars, no summary added,
  "assistant tool_calls kept WITHOUT their tool result: ['a1']"). Mechanism: candidates are single messages sorted
  by `classify_importance` (`history.py:306-309`).
- **`protected_count` is misreported.** `_build_compressed_result()` computes `len(remaining) -
  len(system_msgs)` (`history.py:387`) although `SelectionResult.remaining` never contains system messages
  (`history_selection_policy.py:22-24`): measured `protected_count: 3` with 4 retained turn messages
  (`turn006_probe5.out`).
- **`/compact` and the policy disagree about "enough turns".** A 10-turn-message history passes the
  `cmd_rag_export.py:38-39` gate while `select_turns_to_compress()` returns `None` at the production
  `context_compress_turns = 4` / `history_protect_turns = 3` (`turn006_probe4.out`): the command reports success
  and writes nothing.
- **No test pins the intended behavior.** No test asserts chronological retained order, group atomicity, a single
  summary across cycles, or full message accounting; `grep -n "compressed_count" tests/agent/` matches only
  stub-constructed `CompressResult` values and `> 0` checks.

## Reason for Change

- The feature's stated purpose is to keep the context under a limit while preserving usable conversation state. The
  measured behavior does neither: each cycle adds a summary block instead of removing one, and the retained
  history is no longer a conversation — it is an importance-sorted bag in which an assistant tool-call can be
  summarized away while its tool result is kept, and the answer to a user instruction can be kept while the
  instruction itself is summarized away.
- The importance machinery that causes the reordering is also the machinery that makes the selection
  un-understandable: the `factual` bucket is unreachable, so the documented four-category model
  (`agent_04_02:40-44`) describes a partition that never happens.
- The issue's four acceptance criteria (chronological order, no split round, exactly one summary, no silent loss)
  are each currently false and each is measurable, so the change can be gated by tests rather than by judgment.

## Implementation Intent

- Build one shared unit model: a **turn unit** is one `user` message plus everything produced until the next
  `user` message (assistant text, assistant `tool_calls`, and their `tool` results). Both the selector and the
  fallback use it, so "never split a round" is a property of one primitive rather than two call sites.
- Select whole units oldest-first for compression and protect whole units at the end; keep `remaining`
  chronological. Importance survives only where the issue asks for it: `pinned` protection and the fallback's
  drop order.
- Make the summary a single, replaced message: the previous summary text is fed into the summarization transcript
  and the old summary message is removed. No prompt-wording change, no new config key.
- Make the summary block's size visible (`CompressResult.summary_chars`, an INFO line, and a WARNING when the
  block is not smaller than the text it replaced) so the growth the issue describes is measurable in production
  logs.
- Delete the unreachable API instead of leaving it behind: `classify()`, `partition_by_class()`,
  `sort_by_importance()`, `_DEFAULT_PROTECT_IMPORTANCE`, and their 12 tests.

## Requirements

- `REQ-001` (turn-unit primitive): `HistorySelectionPolicy` gains a static method
  `group_turn_messages(turn_msgs: Sequence[LLMMessage]) -> list[list[LLMMessage]]` that returns the turn units in
  input order — each unit starts at a `user` message and contains every message up to the next `user` message;
  messages before the first `user` message form a leading unit. It drops nothing, reorders nothing, and
  concatenating the units reproduces `turn_msgs` exactly. No new public class or module-level function is added
  (the generator that produces `agent_13` lists classes and module-level functions, not class methods —
  `tools/generate_reference_table.py`, `docs/23_agent/agent_13_reference-api-generated.md:83-84`).
- `REQ-002` (group-atomic chronological selection): `select_turns_to_compress()` keeps the system/turn split and
  the `len(turn_msgs) < n_compress + n_protect` guard, and then (a) protects whole units from the end whose
  cumulative size reaches `n_protect` (the boundary rounds outward, it never splits a unit), (b) selects whole
  units from the front until the cumulative count reaches `n_compress` (the last unit may overshoot), (c) returns
  `to_compress` and `remaining` in chronological order, (d) returns `None` when no whole unit can be selected.
  `SelectionResult`'s three fields are unchanged.
- `REQ-003` (`pinned` protection): a unit containing a message whose `pinned` key is set (the `inf` branch of
  `classify_importance`, `history_selection_policy.py:66-94`) is never placed in `to_compress`; it stays in
  `remaining` in place. `classify_importance()` and `_POLICY_KEYWORDS` (`:27-31`) stay unchanged.
- `REQ-004` (position-based accounting): selection identifies messages by unit index, never by `m not in list`
  value equality; `len(system_msgs) + len(to_compress) + len(remaining) == len(history)` for every input, and
  two messages with identical content are both retained.
- `REQ-005` (exactly one summary message): `history.py` removes a module-level `_SUMMARY_PREFIX =
  "[Conversation summary]"` duplicate-literal pair (`:251,258`) in favor of one constant, adds a private helper
  that splits `system_msgs` into (non-summary system messages, prior summary texts in order), passes the prior
  summary texts as their own block into `_get_summary_text()` (before `_build_history_text()`'s per-message cap),
  and builds the new summary message from the new summary text alone. The returned history contains exactly one
  summary message even when the input contains several. The prompt wording (`:207-210`) and the message shape
  (`role="system"`, `[Conversation summary]` prefix) are unchanged, so `session_message_repo` and
  `test_orchestrator.py:1286` fixtures keep working.
- `REQ-006` (group-atomic fallback): `_fallback_truncate()` and `_build_protected_ids()` (`history.py:297-345`)
  protect all system messages plus the whole units covering the last `n_protect` turn messages, and drop whole
  units ordered by a new static `HistorySelectionPolicy.group_importance(group) -> float` (the maximum member
  `classify_importance`) ascending. `is_fallback`, the soft-limit WARNING, `stat_fallback_truncate_count`, and
  `compressed_count` as a *message* count stay as they are; the fallback never creates an orphan `tool` row.
- `REQ-007` (reported counters): `CompressResult` gains `summary_chars: int = 0` (last field, so existing
  keyword construction is unaffected); the compression path sets it to the new summary message's content length,
  logs it in the existing INFO line, and logs a WARNING when `summary_chars >= self.count_chars(to_compress)`;
  the fallback path leaves it 0. `protected_count` becomes `len(remaining)` (the measured wrong value is 3 vs 4,
  `history.py:387`).
- `REQ-008` (delete the machinery the new selection does not use): delete `HistorySelectionPolicy.classify()`
  (`:44-63`), `partition_by_class()` (`:95-112`), `sort_by_importance()` (`:114-119`), and
  `history.py`'s `_DEFAULT_PROTECT_IMPORTANCE` (`:31-32`), plus the 12 tests that reference them. Rewrite the
  two module docstrings and `history.py`'s class docstring (`:53-55`) that state the old contract.
- `REQ-009` (documentation of the contract): rewrite the selection (`agent_04_02:35-45`), compression-result
  (`:47-49`), fallback-decision (`:51-58`), and Key Constraints (`:101-107`) sections; correct the Token
  Counting claim (`:82-84`) — `compress()` never passes `last_input_tokens`, and with `tokenize_url = ""`
  (`config/agent.toml:65`) the gate uses a `chars // 4` estimate; add the `docs/00_index.md` Agent task-scope
  row.

## Design

### DR-001 — one unit model, oldest-first selection (user decision, 2026-10-23)

A turn unit is the smallest thing that can be moved without breaking a conversation: one `user` message plus
everything that was produced before the next `user` message. The primitive is a static method on the class that
already owns selection, so `history.py` reaches it through `self._selection_policy` exactly as it reaches
`classify_importance` today (`history.py:308`), and no new module or public type appears.

```
system_msgs, turn_msgs   unchanged split (history_selection_policy.py:135-136)
if len(turn_msgs) < n_compress + n_protect: return None            unchanged (:139-140)

units = group_turn_messages(turn_msgs)                             # chronological
protect_from = first unit index whose tail run covers >= n_protect messages
window, taken = [], 0
for i in range(protect_from):
    if taken >= n_compress: break
    if any(m.get("pinned") for m in units[i]): continue           # REQ-003
    window.append(i); taken += len(units[i])
if not window: return None                                         # UNK-02 path
to_compress = flatten(units[i] for i in window)                    # chronological
remaining   = flatten(units[i] for i in range(len(units)) if i not in window and i < protect_from …) + tail
```

Every membership test is on unit indices, never on message values, which is what removes the silent loss (REQ-004).
`n_compress` becomes a floor ("compress at least this many messages"), and the overshoot is bounded by one unit.
`compressed_count` may therefore exceed `compress_turns * 2`; no consumer asserts an exact value (measured:
`cmd_config_stats.py:84-87` and `cmd_rag_export.py:47-51` only print counters, and no test asserts one from a real
compression).

Importance keeps exactly the two roles the issue asks for: the `pinned` signal (REQ-003) and the fallback's drop
order (REQ-006). It no longer decides conversation order.

### DR-002 — the summary is replaced, not accumulated (user decision, 2026-10-23)

`_build_compressed_result()` becomes: split `system_msgs` into non-summary system messages and prior summary
texts; pass the prior texts as a `PREVIOUS SUMMARY:` block ahead of `_build_history_text(to_compress)`; summarize;
emit one new summary message; return `preserved_system + [summary_msg] + remaining`. The single `[Conversation
summary]` prefix literal (`:251,258`) moves to a module constant so "what counts as a summary message" has one
definition. `_build_summary_msg()`'s append-to-existing branch (`:246-258`) is deleted rather than kept as an
option: keeping it would keep the defect. Input histories that already contain several summary rows (a legacy
shape; measured none in `/opt/llm/db/session.sqlite`) are merged, which is the repair path.

Why the prompt stays as it is: the prompt already asks for "one paragraph, preserving key context". Feeding the old
summary in as material is what makes the replacement safe — the model condenses old summary plus newly compressed
turns, instead of the code concatenating them.

### DR-003 — the fallback uses the same units (user decision, 2026-10-23)

`_fallback_truncate()` orders whole units by `group_importance(unit) = max(classify_importance(m) for m in unit)`
ascending and drops units; `_build_protected_ids()` protects system messages and the whole units covering the last
`n_protect` turn messages. `max` (not a mean) is the rule because a unit is only as safe as its most valuable
member: a policy statement must not be dropped because its tool result scores 0.3. Two consequences are accepted
and documented: the fallback can drop more messages than the strict minimum, and `protected_count` can be larger
than the configured `protect_turns`-based value. Soft-limit behavior, `is_fallback`, and the counters stay
(`history.py:311-330`).

### DR-004 — delete what the new selection does not use (user decision, 2026-10-23)

`classify()`, `partition_by_class()`, `sort_by_importance()` have exactly one caller each, all inside
`select_turns_to_compress()` (`:142`, `:145`, `:105`), and `_DEFAULT_PROTECT_IMPORTANCE` has none (its comment
promises protection for messages scoring `>= 0.7`; the measured behavior compresses 0.9-scoring messages). Keeping
them would leave a four-category vocabulary in the code and in `agent_04_02:40-44` that the measured behavior
contradicts. `classify_importance` and `_POLICY_KEYWORDS` stay — the fallback still scores by them. No doc or
generated-table reference names the deleted symbols (`grep -rn "partition_by_class|sort_by_importance" docs/` is
empty; `agent_13` lists classes and module-level functions only), so deletion does not touch `agent_13`.

### Observability

`CompressResult.summary_chars` is set on the compression path and logged in the existing INFO line; a WARNING
fires when the summary block is not smaller than the messages it replaced (`count_chars(to_compress)`). No new
config key and no magic threshold is introduced. The field is data, not a gate: `/stats` surfacing of it is
`WI-005`.

### Boundaries

`tool_result_pairing.py` keeps ownership of live-round pairing; this Plan changes only what gets stored.
`context_view.py`'s cumulative-token argument (`UNK-01`) is a separate defect and is not touched. Undo semantics
(`conversation_state_manager.py:148-165`) and persistence are unchanged; `test_history_compression_consistency.py`
is the guard that this stays true.

## Risks

- **Behavior change for existing sessions.** Every compressed history becomes different: the same limit can keep a
  different (larger, group-rounded) set of messages. Mitigation: the unchanged witness files in `T-6` are run
  before and after, and `_log_skip_warning` already tells the user when nothing is compressible.
- **Compression can now skip where it used to act** (group rounding / all-pinned candidates, `UNK-02`), and
  `/compact` already reports success in that situation today. Mitigation: the skip is logged; the gate itself is
  `WI-002`. Confirm with the owner before implementing `WI-002`.
- **The fallback can delete more than the minimum** because it drops whole units (DR-003). Mitigation: drop order
  is still lowest-group-importance first, protection is group-rounded so the most recent turns stay, and `T-5`
  pins the boundary.
- **`compressed_count` and `protected_count` values change** (at-least semantics, corrected arithmetic). Any
  operator reading historical `/stats` output sees a discontinuity. Mitigation: `AC-7` and the chapter document the
  change; no code depends on the old values.
- **Doc contention.** `agent_04_02` has 17 commits and `docs/00_index.md` 28 commits in the last 30 days, and
  `check_plan_target_overlaps.py` reports 6 pre-existing cross-plan overlaps (none names either file, measured
  2026-10-23), so this Plan's doc rows are currently uncontested — but that must be re-checked before each doc
  edit. Mitigation: re-run the overlap checker at Phase 4.
- **Summarizer behavior is only stub-verified.** The real model's handling of a `PREVIOUS SUMMARY:` block cannot be
  verified offline (`UNK-04`). Mitigation: the relative guard (`summary_chars` vs. what it replaced) surfaces a bad
  outcome in production logs rather than assuming the prompt works.
