## Background
N/A: covered by Summary — this Issue is a direct code-level finding comparing `build_discovery_map()`'s behavior against production discovery's duplicate-exclusion policy, confirmed by direct repository inspection in this cycle.

## Problem
Adversarial verification (Step 2) confirmed every claim in the Issue and resolved its one stated Unresolved Question:
- `build_discovery_map()` (`scripts/shared/route_resolver.py:33-62`) returns `(route_map, duplicates)`. For a tool name reported by more than one server, `route_map` keeps the **first-registered** server (`if name not in route_map: route_map[name] = server_key`), only logging a WARNING and recording the name in the separate `duplicates` dict — the duplicated tool is **not** excluded from `route_map`. This resolves the Issue's Unresolved Question: `build_discovery_map()` genuinely implements first-wins routing for duplicates; it does not already exclude them.
- `McpToolDiscoveryService._dedupe_and_build()` (`scripts/agent/services/mcp_tool_discovery.py:329-381`) implements the opposite, already-correct policy: a tool name claimed by more than one server is excluded from the built registry entirely, and one `StartupCheckStatus.FATAL` finding is emitted per duplicated name, unconditionally (`# Always fatal — tool is unusable when duplicated across servers`), regardless of `strict` mode. The module's own docstring (lines 27-38) states this was a deliberate design decision made in preference to "the alternative, first-wins-with-a-warning."
- `build_discovery_map()` has **zero production callers**: `rg -n "build_discovery_map" scripts/ tests/` found it defined and consumed only by three test files — `tests/shared/test_route_resolver.py` (`TestBuildDiscoveryMap`, asserting `test_duplicate_tool_first_wins`/`test_duplicate_tool_different_key_logs_warning`), `tests/shared/test_routing_duplicate_ownership.py` (a file dedicated entirely to this function, including `test_duplicate_route_map_uses_first_server`), and `tests/shared/test_tool_registry.py` (one test, `test_duplicate_live_ownership_detected`, inside `TestStartupValidationStrictMode`). No `scripts/` file other than `route_resolver.py` itself imports it. `ToolDescriptor` (the TypedDict parameter type `build_discovery_map()` uses) is likewise referenced nowhere else.
- `ToolRouteResolver` (the class in the same module that IS used in production, via `ToolExecutor`) does not use `build_discovery_map()` at all — it consults only `RuntimeToolRegistry`, which is populated from `McpToolDiscoveryService`'s already-correct exclude-and-FATAL result. The two functions in `route_resolver.py` are otherwise unrelated; removing `build_discovery_map()` does not touch `ToolRouteResolver`.
- Two `docs/*.md` locations reference the state this Plan corrects, found during Step 3 evidence search (not in the Issue's original Target Files list): `docs/90_shared_03_03_runtime_and_execution-llm-and-mcp-clients.md:62` documents `build_discovery_map()`'s current `(route_map, duplicates)` return signature — this line becomes stale once the function is removed. `docs/00_governance_03_issue-and-uncertainty-management.md`'s known-issue entry CI-015 ("ADR-003 INV-01 — duplicate tool ownership fails agent startup, verified but needs test coverage") states "there is no automated test covering this invariant" — this claim is already false today (`tests/agent/services/test_mcp_tool_discovery.py::test_duplicate_name_production_is_fatal_and_excluded` and several related tests at lines 1335-1459/1611-1649 already cover it), independently of anything this Plan changes; per `rules/coding.md`'s "Current behavior" classification this is "Obsolete and removable," surfaced here because this Plan's Acceptance Criteria (`AC-3`) also depends on that same test suite being the recognized canonical one.

## Reason for change
Production discovery excludes duplicate tool names and marks them fatal; `route_resolver.py`'s `build_discovery_map()` and its dedicated tests instead assert first-wins routing is correct. Both represent the same ownership invariant and must not disagree — leaving the contradicting, unused function and its tests in place risks a future caller (or a reader auditing routing behavior) taking the wrong one as authoritative.

## Implementation intent
Remove the dead, policy-contradicting `build_discovery_map()` function and its `ToolDescriptor` type from `route_resolver.py` rather than fixing its internals, since it has no production caller to preserve; delete or correct every test that currently asserts its first-wins behavior as intended; leave `McpToolDiscoveryService`'s existing exclude-and-FATAL implementation and its existing dedicated test suite untouched, since Step 2/3 confirmed both are already correct and already satisfy the Issue's Acceptance Criteria on their own once the contradicting legacy code and tests are gone.

## Design
`route_resolver.py` contains two unrelated pieces: `ToolRouteResolver` (the production routing class, consulted only via `RuntimeToolRegistry`) and `build_discovery_map()` (a standalone function with no caller outside its own tests). Because production discovery's duplicate policy is already implemented and correctly enforced in `McpToolDiscoveryService._dedupe_and_build()` — which builds the `RuntimeToolRegistry` that `ToolRouteResolver` actually consults — `build_discovery_map()` is not a second routing path that needs reconciling with the first; it is dead code whose only remaining effect is that its tests assert an incorrect policy as correct. The design choice is therefore removal (per the Issue's own "remove ... if it is obsolete" option), not modification: modifying `build_discovery_map()` to also exclude duplicates would leave in place a second, redundant duplicate-detection implementation with no caller to justify its maintenance cost, working against the Issue's Reason for Change ("must not disagree" — best satisfied by there being only one implementation at all). `tests/agent/services/test_mcp_tool_discovery.py`'s existing suite already satisfies Acceptance Criterion "one test suite defines and verifies the duplicate-ownership policy" on its own; this Plan's test-file changes are entirely subtractive (removing the second, contradicting suite), not additive.
