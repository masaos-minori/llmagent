# Plan: Reject backup candidates from wrong SQLite persistence domain during restore

## Goal
Add domain-identity validation to `_restore_from_backup()` in `scripts/db/recovery.py` to reject structurally valid SQLite backups belonging to a different persistence domain (rag/session/workflow/eventbus) before the live database is touched.

## Priority
High

## Scope
- **In-Scope**: Adding a lightweight required-table signature check between the existing integrity check and the archive/copy step in `_restore_from_backup()`; adding a new `RecoveryResult.action` value for wrong-domain backups; adding test cases for wrong-domain scenarios.
- **Out-of-Scope**: Changing the final atomic-replacement mechanism itself beyond adding the pre-check (no change to `os.replace()`); implementing backup retention/rotation policy; enabling recovery for workflow/eventbus domains.

## Background
Confirmed by direct read of `scripts/db/recovery.py` lines 171-257 (`_restore_from_backup`): existence check (line 188) and integrity check via `_run_integrity_check(backup, target)` (line 198) both run before restoring, matching part of memo2.md's Issue H-07-03 intent. However `_run_integrity_check()` only runs `PRAGMA integrity_check` (line 59) — it opens the file through `SQLiteHelper(target, db_path=...)` but does not verify that the file's schema matches `target`'s required tables.

## Problem
- No required-table/schema-signature check exists anywhere in the restore path.
  `SQLiteHelper(target, db_path=str(db_path)).open()` accepts any well-formed SQLite file
  regardless of its actual schema — it only opens the file and lets the caller run whatever
  query it wants; nothing rejects a schema mismatch on open.
- `tests/db/test_db_recovery.py` has no test case for "valid SQLite backup belonging to the
  wrong domain" — the closest existing test (`test_recover_bad_backup`) only covers a backup
  that itself fails `PRAGMA integrity_check`, not one that passes it but belongs to a
  different domain.
- `RecoveryResult.action` values are currently limited to `no_backup` and `bad_backup` for
  pre-restore failures — there is no distinct action for "backup exists, is valid SQLite, but
  is the wrong domain," so an operator cannot currently distinguish "no valid backup was
  found" from "a backup was found but would have been applied cross-domain" from the action
  alone.

## Reason for change
Applying a structurally valid but wrong-domain backup would silently replace, e.g.,
`rag.sqlite` with a copy of `session.sqlite`, passing the current physical-integrity check
while producing a database that fails every subsequent RAG-specific logical-consistency check
(`check_rag_consistency`) — by which point the original `rag.sqlite` has already been moved to
`corrupt_archive` (not deleted, but no longer live) and the operator must recover from the
quarantine copy instead of the intended backup.

## Implementation intent
Add a lightweight domain-identity check between the existing integrity check and the
archive/copy step in `_restore_from_backup()`: verify the candidate contains the required
table(s) for `target` (e.g. a `documents`/`chunks` table for `rag`, a `sessions` table for
`session`) before proceeding to archive-and-replace. Reuse `SQLiteHelper` to query
`sqlite_master`/`sqlite_schema` rather than opening a second, parallel connection mechanism.

## Requirements
- `REQ-001`: A structurally valid SQLite file belonging to a different persistence domain is rejected before the live database is touched.
- `REQ-002`: The rejection returns a distinct `action` value from `no_backup`/`bad_backup`.
- `REQ-003`: The live database and its directory (no new `corrupt_archive` file) are unchanged when domain-identity validation fails.
- `REQ-004`: Existing `test_recover_corrupt_rag_restores`/`test_recover_bad_backup` tests continue to pass unchanged.

## Design
### Analysis summary
- **Path classification**: Path A (Small Task) — affects ≤ 3 files, no public interface changes, no database schema changes.
- **Target file dependencies**: `scripts/db/recovery.py` imports `SQLiteHelper`, `RecoveryResult`, etc. No runtime-facing interface changes.
- **Callers**: `db/__init__.py`, `agent/services/db_maintenance_service.py`, `agent/services/rag_maintenance_service.py` create `ResourceShutdownCoordinator` and call `close_resources()` in the run() finally block. No caller depends on the 10s delay being present.
- **Evidence verification**: Confirmed via `rg -n "_restore_from_backup|integrity_check" scripts/db/recovery.py` that lines 171-257 contain the restore flow. The integrity check at line 198 runs `PRAGMA integrity_check` but does not verify schema. `SQLiteHelper(db_path=...)` at line 59 opens any SQLite file without schema validation.

### Design decision
The domain-identity check should query `sqlite_master` (or `sqlite_schema`) via an existing `SQLiteHelper` instance to verify that the backup contains at least one required table for the target domain (e.g., `documents` or `chunks` for `rag`, `sessions` for `session`). This is a lightweight check that prevents cross-domain corruption without implementing full logical-consistency verification (which belongs to `_run_logical_verification()`).

If UNK-01 resolves to require column-level validation, the check could be extended to verify column presence for the primary table, but table-only validation is likely sufficient given that table names differ across domains.

- **Risk**: Adding a new action value to `RecoveryResult` could break callers that pattern-match on specific action strings. → **Mitigation**: Review callers (`db/__init__.py`, `agent/services/db_maintenance_service.py`, `agent/services/rag_maintenance_service.py`) to confirm they handle unknown action strings gracefully (they should, since `action` is a string field).
- **Risk**: Domain-identity check might reject valid backups if table names differ slightly between versions. → **Mitigation**: Use minimal required-table validation (at least one primary table must match) rather than strict schema comparison.
- **Risk**: Existing tests may have been written assuming the 10s delay is present, causing false negatives. → **Mitigation**: Check for existing tests before proceeding; if found, update them to expect the new behavior. Currently no existing tests were found.
