## Goal
- Add regression tests for the git MCP push error path so a failing push is covered end-to-end: the formatter re-raises the git command error, the service wraps it into a tool-named `GitServiceError`, and the push postcondition passes for any result text.

## Priority
Low

## Scope
- **In-Scope**: add a formatter test asserting `format_push` re-raises a `git.exc.GitCommandError` raised by `git.push`; add a service-dispatch test asserting a push command error becomes `GitServiceError("git_push failed: ...")`; add a postcondition test asserting `verify_postcondition` passes for any push result text; add a formatter test asserting a successful push whose output merely contains rejection-like text is returned unchanged.
- **Out-of-Scope**: changing production code (`scripts/mcp_servers/git/format_output.py`, `git_service.py`, `repository_state.py`); adding tests for non-push tools; redesigning the write-protection pipeline; pinning the rejection-text behavior without owner confirmation.

## Background
An upstream change removed the stdout rejection-marker detection for pushes (a rejected push normally exits non-zero, so the git library raises and the pipeline reports an error). The three tests that asserted the old behavior were deleted. During the work that led to this issue, replacement tests were written and then dropped to avoid duplicating the upstream fix; the saved drafts covered the points below. No live test currently exercises the push error path.

## Problem
- No test asserts that a command error raised by the push call propagates out of `format_push` unchanged.
- No test asserts that the pipeline turns an exception raised by the push operation into a service error that names the tool (here the push tool, `git_push`).
- No test records the intended removal: a successful push whose output merely contains a rejection-like text is returned as a normal result.
- No test pins that the push postcondition passes for any result text (documents the removal of rejection-text matching).

## Reason for change
Dead coverage gap: the push error path and the rejection-text-removal behavior are exercised by production code but asserted by no test.

## Implementation intent
Model the new tests on the existing fixtures/helpers in the two target files; assert the formatter re-raises, the service wraps into a tool-named `GitServiceError`, and the postcondition passes for any push result. Do not modify production code.

## Requirements
- `REQ-001`: `tests/mcp_servers/git/test_format_output.py` gains a test where a mocked `git.push` raises `git.exc.GitCommandError` and `format_push` re-raises it unchanged.
- `REQ-002`: `tests/mcp_servers/git/test_format_output.py` gains a test where a mocked `git.push` returns output containing rejection-like text and `format_push` returns it unchanged.
- `REQ-003`: `tests/mcp_servers/git/test_git_service_dispatch.py` gains a test where a push command error surfaces as `GitServiceError("git_push failed: ...")`.
- `REQ-004`: `tests/mcp_servers/git/test_repository_state.py` gains a test where `verify_postcondition(..., "git_push", ...)` returns `(True, "")` for any result text.

Operational dependency inspection: not applicable (no MCP server or DB beyond the git MCP service already tested). Validation quality baseline: existing per-tool dispatch tests and `TestFormatPush` provide fixture patterns to model; `TestWrapGitOp` provides the `GitServiceError` assertion pattern.
