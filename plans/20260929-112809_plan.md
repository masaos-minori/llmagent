## Background
Filed as `issues/20260929-111152_agent007_orchestrator-memory-injection-error-no-longer-propagates-as-runtimeerror-under-workflow-engine-retry-halt.md`, which flagged this as an ambiguous case (stale test vs. possible regression where errors are silently swallowed).

Deeper investigation during this planning cycle (adversarial verification of the Issue's own Unresolved Question) traced the full call path and confirms the retry-then-halt-and-log behavior is the current, intentional architecture, not a regression:

- `scripts/agent/orchestrator.py::_process_turn()` (lines ~262-291) calls `await self._conversation_manager.handle_memory_injection(line)` directly inside `with self._tool_override(self._allowed_tools):` (lines ~269-291). `_tool_override()` (lines ~296-303) is a `@contextmanager` whose `finally` restores `ctx.cfg.tool.allowed_tools` regardless of exceptions — this part is unaffected by anything below.
- This turn-processing call is wrapped by `scripts/agent/workflow/workflow_engine.py::_run_stage_with_retry()` (lines ~230-265+), which retries a failing `retryable` stage (the `execute` stage, per `docs/23_agent/agent_03_03_turn-processing-flow-workflow-engine.md` "Retry Mechanism") up to `policy.max_attempts` (observed: 2 retries logged, 3rd attempt fails), then raises `WorkflowHaltError(...) from exc`, chaining the original exception as `__cause__` rather than re-raising it directly.
- `scripts/agent/workflow_engine_adapter.py::_handle_workflow_halt()` (lines ~358-369) catches `WorkflowHaltError | WorkflowTimeoutError`, logs `"Turn halted by workflow engine: %s"`, resets `ctx.workflow` state, and calls `self._on_error(exc)` **only if an `on_error` callback was supplied** (line 368) — it never re-raises.
- The failing test's `Orchestrator(ctx, allowed_tools=["search_web"])` (line 1271) passes no `on_error` callback, so `self._on_error` is `None` for this test — meaning the halt is logged only, with no callback and no exception, exactly matching the observed `Failed: DID NOT RAISE <class 'RuntimeError'>`.
- `docs/23_agent/agent_03_03_turn-processing-flow-workflow-engine.md`'s "Retry Mechanism" section documents the retry-then-halt policy for `retryable` stages as an existing, designed contract (`retry_policy.max_attempts`, `backoff_sec`, stage-level `retryable` flag) — the halt-and-report path this test exercises is not an undocumented accident.

This confirms the Issue's Unresolved Question: the swallow-on-halt behavior is intentional (an optional-callback design), and the test is stale — written for (or never updated from) an assumption that `handle_memory_injection`'s exception propagates directly, which no longer holds once the call is wrapped by the workflow engine's retry stage.

A secondary, non-blocking observation from the same investigation: the two adjacent tests in the same class, `test_original_allowed_tools_restored_after_turn` and `test_allowed_tools_none_leaves_config_unchanged`, patch `orch._handle_memory_injection` (a thin wrapper method not actually called by `_process_turn()`, which calls `self._conversation_manager.handle_memory_injection(...)` directly instead) — meaning those two tests currently pass without their patch having any effect on the real call path. This is out of scope for this Plan (see Out-of-Scope) but is recorded here as a related test-hygiene gap worth a separate look.

## Problem
`test_original_config_restored_even_on_error` expects `orch.handle_turn("test")` to re-raise the `RuntimeError` injected into `handle_memory_injection`, but the current architecture retries the failing stage 3 times and then converts the failure into a `WorkflowHaltError` that is caught, logged, and (absent an `on_error` callback, as in this test) silently discarded — `handle_turn()` returns normally. The test's actual intent (confirming `ctx.cfg.tool.allowed_tools` restoration on error) is never reached because the `pytest.raises(RuntimeError)` expectation fails first.

## Reason for change
A stale test masks whether the config-restoration behavior it was meant to verify actually still holds under the current architecture, and produces persistent CI noise unrelated to any real defect. Fixing it restores a meaningful, passing regression test for the config-restore-on-halt behavior specifically.

## Implementation intent
Rewrite the test to exercise the halt path as it actually behaves: keep the `side_effect=_raise` injection (still a realistic way to force a stage failure), but replace `with pytest.raises(RuntimeError): await orch.handle_turn("test")` with a plain `await orch.handle_turn("test")` call (no exception expected) followed by assertions against the halt's observable effects — at minimum `ctx.cfg.tool.allowed_tools == []` (the test's original point), and additionally confirm the halt was actually reached (e.g. via `ctx.workflow.active is False` after the call, or by passing an `on_error` callback/`MagicMock` to `Orchestrator(...)` and asserting it was invoked with a `WorkflowHaltError`) so the test still fails if the retry/halt path itself breaks in the future. Do not weaken the test to merely check the config value without confirming the halt path was actually exercised — that would silently drop the "confirm halt actually occurred" coverage the original test's `pytest.raises` was (imperfectly) providing.

## Requirements
- `REQ-001`: Rewrite `test_original_config_restored_even_on_error` to assert the workflow-engine halt outcome (e.g. `ctx.workflow.active is False` and/or an `on_error` callback invocation with the raised error) instead of `pytest.raises(RuntimeError)`, while still asserting `ctx.cfg.tool.allowed_tools == []`.
