## Goal
Close the EVENTBUS-008 fail-open: an empty `consumer_authorization`/`topic_authorization`
pair for the EventBus CONSUMER token must resolve to deny-all instead of unrestricted.

## Priority
Medium

## Background
`EVENTBUS-008` (governance known-issue ledger, `open` / `Medium` / `design-gap`) tracks
that the EventBus `CONSUMER`-role token is unrestricted across every `consumer_id` when
`consumer_authorization` and `topic_authorization` in `config/eventbus.toml` are both
empty, because `_populate_token_maps()` in `scripts/eventbus/auth.py` assigns
`allowed_consumer_ids=None` ("any consumer_id") instead of denying all. Related
documents are `ADR-013` (consumer-topic authorization, INV-02) and `ADR-006` (ACK/NACK
token binding, INV-10), both of which rely on the CONSUMER token being restricted to its
allowlist. `eventbus03` introduced the fail-closed consumer/topic model across subscribe,
ACK, and NACK but did not close the specific empty-mapping case: `_populate_token_maps()`
still treats an empty `consumer_authorization`/`topic_authorization` pair as "no
restriction" rather than "deny all", so `EVENTBUS-008` remains open.

## Problem
With `consumer_token` configured and both `consumer_authorization` and
`topic_authorization` present but empty, startup does not reject the configuration and the
resolved `Principal.allowed_consumer_ids` is `None`. `require_consumer_identity()` then
never rejects a `consumer_id`, so the CONSUMER token can act as any `consumer_id`.

## Reason for change
An empty authorization mapping is most naturally read as "no one is authorized", but the
current code reads it as "everyone is authorized". Any operator who clears the allowlist
(or ships an empty mapping) silently disables consumer-identity enforcement without a
startup error, and the ACK/NACK binding of `ADR-006` INV-10 and the topic restriction of
`ADR-013` INV-02 both depend on that enforcement. The gap is a genuine code/config mismatch
that contradicts the fail-closed intent documented in `ADR-013`.

## Implementation intent
Change how an empty `consumer_authorization`/`topic_authorization` pair is interpreted for
the `CONSUMER` role only. Adopt deny-all at runtime: when both mappings are empty, resolve
`allowed_consumer_ids`/`allowed_topics` to an empty `frozenset()` (rejects every
`consumer_id`/`topic`) instead of `None`. Keep the existing `None`→startup-raise check for
a *missing* key distinct from an *empty* mapping. Do not touch the `auth_token`/`admin_token`
superuser path, the union-apply path for non-empty mappings, or other roles.

## Design
Path A (small task): affects ≤ 3 files, no public/runtime interface change, no DB schema
change.

Root cause: `_populate_token_maps()` initializes `consumer_allowed_ids`/`consumer_allowed_topics`
to `None` (line 124-125) and only overwrites them inside
`if consumer_authorization or topic_authorization:` (line 136). Empty dicts are falsy, so
the overwrite is skipped and the `None` ("any") sentinel survives.
`require_consumer_identity()` rejects only when `allowed_consumer_ids is not None`
(line 302-306), so `None` = unrestricted and `frozenset()` = deny-all.

Fix: add handling so that when neither mapping is populated, both resolve to
`frozenset()` for the CONSUMER role. The `None`→raise check for a missing key (lines
130-134) is preserved, keeping empty distinct from missing. The `auth_token`/`admin_token`
superuser branches (lines 111-117, 187-195) are untouched. `require_consumer_identity()`
needs no logic change (an empty `frozenset()` already triggers rejection); only its stale
comment (line 298-301, which claims an explicit empty set means "no restriction") must be
corrected to reflect `None`=unrestricted / `frozenset()`=deny-all.

Validation baseline (radon/cc): `_populate_token_maps` is complexity D(22) — keep the
added branch shallow. bandit: 1 pre-existing high-confidence/low-severity finding
(unrelated to this change).
