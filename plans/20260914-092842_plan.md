## Background

What is not yet connected explicitly: `scripts/rag/exceptions.py` itself defines `ChunkFormatError(RagLayerError, ValueError)` with a docstring distinguishing it from 5 sibling classes (`EmbeddingSchemaError`, `PipelineValidationError`, `SearchQueryError`, `TokenizationError`, `UnknownMetadataError`), each with its own docstring-defined purpose, and every current catch site in the repository (`chunk_splitter.py:197`, `file_routing.py:52,101`, `ingester.py:217,235,348`, `chunk_grouping.py:30`) catches `ChunkFormatError` specifically, never the `RagLayerError` base or `ValueError`.

## Problem
A developer adding new validation logic has no documented guidance on which of the 6 sibling `RagLayerError` subclasses to raise, or whether to catch the specific class or a base class — despite this guidance being fully derivable from `scripts/rag/exceptions.py`'s existing docstrings and the codebase's consistent catch-site pattern.

## Reason for change
Per the Issue's Impact: developers adding new validation logic may not know which exception to raise, and error-handling code may miss catching `ChunkFormatError` if written against the wrong base class. Documenting the already-consistent codebase pattern directly reduces this risk.

## Implementation intent
Add a new subsection immediately after "Pipeline Utils — Artifact Validation" (after line 55, before "## RagIngester" at line 57), covering: (1) `ChunkFormatError`'s position in the hierarchy — `RagLayerError` (base) + `ValueError` (mixin), sibling to `EmbeddingSchemaError`/`PipelineValidationError`/`SearchQueryError`/`TokenizationError`/`UnknownMetadataError`; (2) when to raise `ChunkFormatError` versus each sibling, using each class's own docstring as the distinguishing rule (e.g. `ChunkFormatError` for chunk-document structure, `SearchQueryError` for an unexecutable search query); (3) that every current caller in the repository catches `ChunkFormatError` specifically rather than `RagLayerError` or `ValueError`, citing this as the established pattern new code should follow; (4) the already-documented hierarchy deviation (`RagRerankError`/`RagPipelineError` defined outside `scripts/rag/exceptions.py`, per Implementation Notes line 79) as the one known edge case, without inventing others.
