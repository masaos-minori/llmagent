## Goal
- Introduce one machine-readable Canonical Source Registry (a TOML file plus a validating tool with a versioned, code-defined schema) that becomes the single system of record mapping each decision target and claim type to its canonical source.

## Priority
Medium

## Scope
- **In-Scope**: selecting a registry file format and location consistent with existing repository conventions; defining the registry's schema (fields, naming convention, hierarchy, `source`/`sources` semantics) as a versioned, code-defined structure; writing a validation tool that checks schema conformance, resolves and confirms registered source paths exist, verifies `source`-vs-`sources` single-normative-source constraint, and verifies Accepted status for ADR canonical entries; unit tests for that tool; registering the registry as the documented system of record in `docs/00_governance_01_documentation-policy.md` (including the normative rule that area guides must not maintain an independent hand-edited canonical-source mapping going forward); registering the new tool in the Governance Verification Matrix and `tools/TOOL_DESCRIPTIONS.md`/`routing.md`.
- **Out-of-Scope**: fully populating the registry with every existing decision target (one illustrative entry only, reusing the source Issue's own `agent.tool-routing` example — complete migration is `M-01-06`'s scope); rewriting any area document-guide's own Canonical Source Rule(s) section to link to or display the registry (also `M-01-06`'s scope — this Plan only establishes, in policy text, that area guides must not maintain independent mappings going forward); building a documentation-generation tool that renders registry entries into area guides (deferred — Design records the direction, not an implementation); changing application routing or runtime ownership; using the registry to declare code compliant with design.
- **Constraint**: use a single `source` field for normative document claims; permit a `sources` list only for claim types whose canonical implementation necessarily spans multiple files (e.g. `runtime-behavior`) — never use `sources` to allow multiple competing normative documents for the same target and claim type (source Issue's Constraints section).

## Background
Area-level Primary/Secondary tables (in `docs/00_governance_01_documentation-policy.md`'s "Area Canonical Maps" section) and each area guide's own "Canonical Source Rule(s)" section do not identify what each document is primary *for* — multiple documents can be labeled Primary without a deterministic way to resolve overlapping claims.

## Problem
A machine-readable registry is required to enforce the rule that each decision-target-and-claim-type pair has at most one canonical source; without one, canonical-source ownership stays distributed across hand-maintained area tables that can silently drift out of sync with each other and with the target-based resolution model (`M-01-02`).

## Reason for change
`M-01-01` (claim-type taxonomy) and `M-01-02` (target-based resolution) define the conceptual model; this issue provides the concrete, machine-checkable artifact that model needs to be enforceable rather than aspirational prose.

## Implementation intent
Add `config/documentation_canonical_sources.toml` as the registry (TOML, not YAML — see Design for why), and `tools/check_canonical_source_registry.py` as the tool that parses it, validates it against a versioned schema defined as Python dataclasses in that same tool (no new external schema-library dependency), confirms every registered source path exists, enforces the single-normative-source constraint, and checks Accepted status for ADR-sourced entries by reading each referenced ADR's `## Status` section. Add unit tests, register the tool in the Governance Verification Matrix and tool-inventory docs, and add the "system of record" / "no independent area-guide mappings going forward" rule to `docs/00_governance_01_documentation-policy.md`.

## Design
**Registry format decision**: `config/documentation_canonical_sources.toml`, not `.yaml` — every existing `config/*` file in this repository is TOML, and TOML's nested-table syntax (`[targets."agent.tool-routing".architecture-decision]`) expresses the source Issue's proposed nested structure without a new dependency. `tomllib` (Python 3.11+ standard library) parses it, so no new dependency is added.

**Schema decision**: defined as Python `dataclasses` inside `tools/check_canonical_source_registry.py` (e.g. `RegistryEntry`, `CanonicalSourceRegistry`), not a separate `.schema.json` file — this avoids adding a `jsonschema` dependency and follows the existing pattern where `tools/check_docs_quality.py`'s custom rules are Python-defined, not a separate schema-validation library. The registry's own `version` top-level field satisfies "registry has a versioned schema" (AC1) without a second schema-version file.

**Decision-target naming**: `<area>.<concern>` (e.g. `agent.tool-routing`), where `<area>` is one of `docs/00_governance_03_issue-and-uncertainty-management.md`'s Area Values (lowercased) and `<concern>` is a free-form kebab-case identifier — this makes identifiers hierarchical by construction (area, then concern) without a separate hierarchy mechanism (`REQ-003`).

**Source-path resolution**: every `source`/`sources` path is interpreted relative to the repository root (matching how `Implementation Target Files` paths are already written throughout this Plan and the rest of the pipeline) — no separate resolution-root config is needed (`REQ-004`).

**`source` vs. `sources` enforcement**: the dataclass schema itself only exposes a `sources: list[str]` field internally, but the parser rejects more than one entry unless the claim type is in an explicit allow-list (initially just `runtime-behavior`) — this directly encodes `REQ-005`/the Constraint without needing two separate schema fields.

**ADR-status check**: for an entry whose `source_kind` is `adr`, the tool reads the target file, finds the `## Status` heading (the format confirmed in `docs/adr/ADR-003-...md`), and reads the next non-blank line as the status value; anything other than `Accepted` fails validation (`REQ-006`).

**Deployment note**: `config/documentation_canonical_sources.toml` is a governance/tooling config, not a service config consumed by any running process — unlike other `config/*.toml` files (which pair with an MCP server or the agent), this one has no runtime reader. Per `rules/coding.md`'s "Module addition"/"config/*.toml" convention, a new `config/*.toml` file needs only a `cp` line in `deploy/deploy.sh` if it is meant to be deployed; since this file is consulted only by the CI/governance tool (`tools/check_canonical_source_registry.py`, itself never deployed to `/opt/llm/`), no `deploy/deploy.sh` change or service restart is required — this is recorded explicitly rather than silently assumed (Affected areas above).

**Documentation-generation display (Required Changes item 10)**: deferred. This Plan records, as a design note for whoever scopes `M-01-06`, that a future generation step would most naturally follow the existing `tools/generate_reference_table.py --type <domain>` pattern (auto-generated block replacement) rather than a new mechanism — no such tool is built in this Plan (Out-of-Scope).
