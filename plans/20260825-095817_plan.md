## Background
This Plan's source Issue was generated from a documentation-sync review of DB
corruption recovery (H-3), Git MCP write protection (H-4), and MCP tool-availability
metadata (M-1), listing candidate follow-up tasks. Per this workflow's Step 2
verification, several listed tasks were already closed by a subsequent code change
(evidenced by `tests/mcp_servers/git/test_git_security_compliance.py` and the
current state of `db/recovery.py`, `git_service.py`, `git_models.py`,
`git_server.py`) — those are moved to Scope > Out-of-Scope above rather than
re-planned. This Plan covers only the remainder that source-code inspection
confirmed is still open.

## Problem
Several confirmed gaps remain even though the most severe, security-exploit-shaped
items (Git option-injection, protected-branch bypass, audit-field mismatch) are
already fixed:
- DB recovery: a restored database is never re-verified after the atomic restore
  completes, and an unsupported `recover_corruption()` `target` value is silently
  treated as `session` instead of being rejected.
- Documentation: `docs/04_mcp_04_05_git.md` still describes Git MCP as having "no
  protected-branch policy source," which no longer matches the implemented
  behavior; `docs/adr/ADR-001-workflow-engine-mandatory.md` still forward-references
  ADR numbers that are now assigned to unrelated, already-`Accepted` decisions.
- MCP tool-availability metadata: `rag_pipeline`, `cicd`, `mdq`, and `shell` do not
  compute per-tool `enabled`/`disabled_reason`, unlike the other MCP server
  categories; no `list_tools()` handler passes `include_disabled`/`disabled_code`
  through to `build_tools_response()`, even though that function already accepts
  both parameters.
- Two fields (`RuntimeToolRegistry.degraded_servers`, `RuntimeTool.requires_approval`)
  are constructed/written but have no effect on runtime behavior, and one function
  (`LLMTurnRunner._filter_disabled_tool_definitions()`) is a confirmed no-op filter.
- The Git write-tool approval-tier gap (`git_checkout`/`git_pull`/`git_push`
  resolving to the `y/N` tier instead of the full-word-`yes` tier) is already
  accurately documented as an open gap, but no decision has been recorded in
  `config/agent.toml`.
- Corrupt-database archives created by `_restore_from_backup()` accumulate with no
  retention or cleanup policy.

## Reason for change
Stale documentation misleads operators and future implementers about what
protection actually exists; dead fields invite a future reader to assume behavior
that is not active; unbounded archive growth and an unverified restore path are
operational risks; incomplete tool-availability metadata makes some MCP server
categories behave inconsistently with the rest.

## Implementation intent
Group the remaining work by subsystem so each phase is independently revertable:
DB recovery hardening (REQ-001, REQ-002, REQ-010), MCP tool-availability completeness
(REQ-004, REQ-005, REQ-007, REQ-008), and documentation/config corrections (REQ-003,
REQ-006, REQ-009). No new module or public interface is introduced; all changes are
localized edits to existing functions/config, plus one documentation correction and
one ADR correction.

## Requirements
- `REQ-001`: `db/recovery.py::_restore_from_backup()` must re-verify the restored
  database's integrity after the atomic replace, before returning `success=True`.
- `REQ-002`: `db/recovery.py::recover_corruption()` must reject a `target` value
  that is not one of the values it actually supports, instead of silently treating
  an unrecognized value the same as `"session"`.
- `REQ-003`: `docs/04_mcp_04_05_git.md` §Protected branch authority must be updated
  to describe the implemented `GitConfig.protected_branches` policy instead of
  stating that no policy source exists.
- `REQ-004`: `rag_pipeline`, `cicd`, `mdq`, and `shell` MCP servers must compute
  per-tool `enabled`/`disabled_reason` the same way `git`/`file_read`/`file_write`/
  `file_delete`/`github`/`web_search` already do.
- `REQ-005`: every MCP server's `list_tools()` handler must accept and pass through
  `include_disabled` and `disabled_code`-shaped query parameters to
  `build_tools_response()`.
- `REQ-006`: `config/agent.toml`'s `approval_risk_rules` must record an explicit,
  owner-level decision for `git_checkout`/`git_pull`/`git_push`'s approval tier
  (raise to the full-word-`yes` tier, or explicitly confirm the `y/N` tier is
  intended) — see Unknowns (`UNK-01`) for the open design choice.
- `REQ-007`: `RuntimeToolRegistry.degraded_servers` and `RuntimeTool.requires_approval`
  must either be wired to real runtime behavior or removed — see Unknowns
  (`UNK-02`) for the open design choice.
- `REQ-008`: `LLMTurnRunner._filter_disabled_tool_definitions()` must be removed (its
  filtering is already fully covered by `RuntimeToolRegistry.llm_tool_definitions()`)
  or replaced with a genuine second check.
- `REQ-009`: `docs/adr/ADR-001-workflow-engine-mandatory.md` must be corrected to
  stop forward-referencing ADR-002 and ADR-003 for future workflow-schema/monitoring
  topics, since those numbers are now `Accepted` decisions for unrelated topics
  (process-level config isolation and RuntimeToolRegistry routing authority).
- `REQ-010`: a retention/cleanup policy must be defined and implemented for the
  timestamped corrupt-database archives `_restore_from_backup()` creates.

  supported set receives an explicit rejection, not a silent `session`-path result.
- `REQ-003`: `docs/04_mcp_04_05_git.md` §Protected branch authority no longer states
  that no policy source exists, and instead names `GitConfig.protected_branches` and
  its enforcement point.

- `REQ-005`: a test asserts `include_disabled=false` omits a known-disabled tool

  `disabled_code` is present alongside `disabled_reason`.

## Design
- **REQ-001/REQ-002/REQ-010** (`db/recovery.py`, `db/rotation.py`/`maintenance.py`):
  additive changes to existing functions — add a post-`os.replace()` integrity
  check call (reusing `_run_integrity_check()`), add an explicit `target`
  allow-list check before the existing rag/session ternary, and add a
  count-or-age-bounded cleanup pass for `*_corrupt_*` archive files alongside the
  existing session-retention logic in `maintenance.py`. No new module.
- **REQ-004/REQ-005** (MCP servers): reuse the existing per-tool availability
  pattern already implemented for `git`/`file_read`/`file_write`/`file_delete`/
  `github`/`web_search` (an `_annotate_tool`/`<server>_tool_availability`-shaped
  helper) rather than inventing a new mechanism; reuse `build_tools_response()`'s
  existing `include_disabled`/`disabled_code` parameters rather than changing its
  signature.
- **REQ-006** (`config/agent.toml`): add `"high"` overrides for the three Git write
  tools in `approval_risk_rules`, matching the pattern already used for
  `delete_file`/`shell_run`/`github_push_files` (see UNK-01 for the alternative).
- **REQ-007**: default to removing `degraded_servers` from `RuntimeToolRegistry`
  and `requires_approval` from `RuntimeTool`, since neither has a live consumer
  today (see UNK-02 for the alternative).
- **REQ-008**: remove `_filter_disabled_tool_definitions()` and its call site,
  since `RuntimeToolRegistry.llm_tool_definitions()` already performs the real
  Stage-1 filtering this function was a redundant second pass over.
- **REQ-003/REQ-009**: documentation-only corrections; no code change.

## Risks
- **Risk**: raising the Git write-tool approval tier (REQ-006) could disrupt an
  automated/non-interactive caller that currently relies on the `y/N` prompt →
  **Mitigation**: require the UNK-01 sign-off before merging this change, and
  confirm via `04_mcp_05_03_fail-open-fail-closed-and-risk-tiers.md`'s existing
  cross-reference to `04_mcp_04_05_git.md` Approval level that no documented
  caller depends on the current tier.
- **Risk**: removing `degraded_servers`/`requires_approval` (REQ-007) forecloses a
  mechanism a future feature might have wanted → **Mitigation**: require the
  UNK-02 sign-off before merging; the fields can be re-added later with a concrete
  design once a real consumer exists.
- **Risk**: a corrupt-archive retention policy (REQ-010) that deletes too
  aggressively could remove diagnostic evidence needed for an active incident →
  **Mitigation**: default to a conservative, documented retention window and log
  every deletion.
