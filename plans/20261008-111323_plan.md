## Goal
- Make the production EventBus application reject unauthenticated and wrong-role requests to the health and publish routes, prove it with tests that use the production application object, and remove the now-resolved Known Issue (EVENTBUS-016) from the documentation.

## Priority
High

## Scope
- **In-Scope**: role dependencies on the two route declarations in the EventBus application module; new production-wiring tests; removal of EVENTBUS-016 from the Known Issue ledger and from ADR-013's Known Deviations; the INV-01 verification note in ADR-013.
- **Out-of-Scope**: the token model and the mandatory shared token (EVENTBUS-015); consumer-identity allowlists (EVENTBUS-008); other routes; creating a production publishing client configuration; the health reference document (it already states the Monitoring role).

## Background
Found while verifying ADR-013 and registered as EVENTBUS-016: route introspection shows no dependency on the health and publish routes, while all others carry a role dependency. The existing authentication tests build their own fixture app, so they never covered this.

## Problem
- Any local process that can reach the loopback port can publish events and read health state without a token (ADR-013 INV-01; documented Monitoring role for health).
- No test fails when a production route lacks its dependency.

## Reason for change
Authentication is the EventBus security boundary, and the Known Deviation should not outlive a small, bounded fix.

## Implementation intent
- Declare the Publisher dependency on publish and the Monitoring dependency on health in the application module, in the same style as the other routes; leave handler logic untouched.
- Add tests that enumerate the production application's routes and assert each protected route has a role dependency, plus 401/403/200 behavior for the two routes through the production app.
- After the fix, delete the ledger entry and the ADR deviation, as the Current-Specification-Only policy requires.

## Requirements
- `REQ-001`: Add the Publisher role dependency to the publish route and the Monitoring role dependency to the health route in the production application.
- `REQ-002`: Add production-wiring tests: no token returns 401, a wrong-role token returns 403, the right per-role token and the shared token succeed, for both routes; plus a guard test that every route except documented exceptions has a role dependency.
- `REQ-003`: All existing EventBus tests still pass (existing clients send the shared token through the shared test helper).
- `REQ-004`: Remove EVENTBUS-016 from the ledger (table row and detail section).
- `REQ-005`: Remove the EVENTBUS-016 line from ADR-013 Known Deviations, drop the EVENTBUS-016 notes from Problem, Failure Policy, and the INV-01 Verification item, and describe the new production-wiring tests as INV-01 evidence.
- `REQ-006`: Documentation and tool checks pass; lint, type, and import checks introduce no new findings.

## Design
Path B (four files). Architecture: `eventbus` is isolated by the `eventbus-is-isolated` import contract; the change adds no new import because the dependency helpers and role enum are already imported by the application module. Dependency graph: the application module's only production importer is itself the entry point; about 20 test modules import it, almost all through one shared helper that sets a default shared-token header, which is why existing tests are expected to keep passing. History: the application module and auth tests are high-churn and single-author. Operational: no live process inspection was needed (document-only phase; no change to a running service); the fix requires an EventBus service restart after deployment and every caller to present a token. `lint-imports` shows a pre-existing violation unrelated to this change. The Python validation baseline (radon, vulture, bandit) applies to the application module at implementation time.
