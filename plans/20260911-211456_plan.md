## Goal
Wire `on_turn_start`/`on_turn_end`/`on_llm_wait_start`/`on_llm_wait_end` — currently
stored by four classes but never invoked anywhere — to their single correct owning
class each, consolidating four redundant copies of the same constructor
parameters into two.

## Priority
Medium

## Scope
- **In-Scope**: Invoke `on_turn_start`/`on_turn_end` from inside
  `AuditEventEmitter.emit_turn_start()`/`emit_turn_end()`. Invoke
  `on_llm_wait_start`/`on_llm_wait_end` from inside
  `LlmTurnExecutor.handle_llm_turn()`, bracketing the `LLMTurnRunner.run()` call.
  Remove the now-redundant duplicate storage of `on_turn_start`/`on_turn_end` from
  `Orchestrator`, `ConversationStateManager`, and `LlmTurnExecutor`, and of
  `on_llm_wait_start`/`on_llm_wait_end` from `Orchestrator` and
  `AuditEventEmitter` — each callback pair is owned by exactly one class after
  this Plan. Correct `on_llm_wait_start`'s type annotation from
  `Callable[[], Any] | None` to `Callable[[], None] | None` (return value is
  discarded, matching `on_llm_wait_end`'s existing no-argument signature — no API
  change needed). Un-skip and correct the 3 tests in
  `TestHandleLlmTurnOptionalCallbacks`.
- **Out-of-Scope**: `on_error` wiring (already fixed and verified in a prior
  session cycle — `LlmTurnExecutor.handle_llm_turn()`'s existing
  `self.call_on_error(result.exception)` call is untouched).
  `LLMTurnRunner`'s own stale docstring claim ("Accepts the same ctx/callbacks
  used by Orchestrator...") — it does not actually accept any of these callbacks
  and never will under this design (they live in the wrapping `LlmTurnExecutor`
  layer, not `LLMTurnRunner` itself); flagged as a pre-existing inaccuracy in
  Assumptions, not corrected here since `llm_turn_runner.py` is not a target file
  for this issue's actual behavior change.
- **Dependencies**: N/A: none.

## Background
Three design questions this issue explicitly declined to guess unilaterally on
(the issue's own AI Implementation Instruction: "Do not guess the call site
unilaterally") were confirmed with the user before this Plan was written:
1. `on_turn_start`/`on_turn_end` wiring location: `AuditEventEmitter` internally
   (not an independent call site in `Orchestrator._execute_turn()`).
2. `on_llm_wait_start`/`on_llm_wait_end` wiring location:
   `LlmTurnExecutor.handle_llm_turn()` (the same method `on_error` was already
   correctly wired into, per this issue's own Background section).
3. `on_llm_wait_start`'s `Any`-typed return value: discarded, no signature change
   to `on_llm_wait_end`.

Investigation beyond the issue's own text found the duplication is worse than
described: the issue names 3 classes (`Orchestrator`, `AuditEventEmitter`,
`LlmTurnExecutor`) holding `on_turn_start`/`on_turn_end`/`on_llm_wait_start`/
`on_llm_wait_end`, but `ConversationStateManager` independently stores
`on_turn_start`/`on_turn_end` too (a 4th copy, confirmed at
`conversation_state_manager.py:62-63,73-74`) — also entirely dead.

## Problem
`rg` confirms zero invocations of any of these four callbacks anywhere in
`scripts/` (excluding their own storage/forwarding) except
`LlmTurnExecutor.call_on_turn_end()`/`call_on_llm_wait_end()`, which are
themselves never called from anywhere (`rg` for these two helper names finds only
their own definitions). `Orchestrator._execute_turn()` — the real, live
turn-processing entry point — calls only `AuditEventEmitter.emit_turn_start()`/
`emit_turn_end()`, which currently ignore the `on_turn_start`/`on_turn_end`
callbacks they already store.

## Reason for change
`tests/agent/test_orchestrator.py::TestHandleLlmTurnOptionalCallbacks` (3 tests,
explicitly documented as prior-uncovered "characterization tests") are currently
skip-marked pending this exact fix. Any caller configuring
`Orchestrator(..., on_turn_start=..., on_turn_end=..., on_llm_wait_start=...,
on_llm_wait_end=...)` today silently gets no invocations at all, contradicting
the constructor's own documented parameter surface.

## Implementation intent
Per the confirmed design: `AuditEventEmitter` becomes the sole owner of
`on_turn_start`/`on_turn_end`, invoking them at the start/end of
`emit_turn_start()`/`emit_turn_end()` respectively (the same call sites
`Orchestrator._execute_turn()` already uses once per real turn).
`LlmTurnExecutor` becomes the sole owner of `on_llm_wait_start`/
`on_llm_wait_end`, invoking them immediately before and after the
`LLMTurnRunner.run()` call inside `handle_llm_turn()` — wrapped in `try/finally`
so `on_llm_wait_end` fires symmetrically even if `run()` raises (matching test
`test_wait_end_invoked_in_except_branch`'s intent, even though the current call
chain does not actually propagate `LLMTransportError` out of `run()` — see
Design). `Orchestrator.__init__` keeps accepting all four as constructor
parameters (its existing public API) but stops storing them itself, forwarding
each pair only to its new single owner.

## Assumptions
- `LLMTurnRunner`'s docstring ("Accepts the same ctx/callbacks used by
  Orchestrator so it can be wired in without changing the call-site interface")
  is a pre-existing inaccuracy — it does not actually accept any of the 4
  callbacks in its current constructor, and this Plan's design deliberately keeps
  it that way (the wrapping `LlmTurnExecutor` layer owns the wait callbacks, not
  `LLMTurnRunner` itself). Not corrected here since `llm_turn_runner.py` is not a
  target file for this issue's behavior change; worth a follow-up documentation
  fix, not filed here since it is not blocking.
- `LLMTurnRunner.run()` fully absorbs `LLMTransportError` internally (via its own
  `except LLMTransportError` at line 85, converting to a `TurnResult`) and does
  not propagate it to `handle_llm_turn()` under any code path found during
  investigation — the `try/finally` design (rather than a
  `except LLMTransportError`-specific clause) is chosen specifically because it
  guarantees `on_llm_wait_end` fires symmetrically regardless of whether `run()`
  ever does raise something in a path not found here, matching the bracketing
  semantics implied by the "wait_start/wait_end" naming.

## Design
Investigation (Step 2/3, Path B full analysis) proceeded in this order:

1. **Confirmed the issue's core claim**: `rg` for all 4 callback names across
   `orchestrator.py`, `audit_event_emitter.py`, `llm_turn_executor.py` found only
   constructor-parameter assignments (dead storage) and the 2 existing
   `call_on_turn_end()`/`call_on_llm_wait_end()` helpers, themselves uncalled.
2. **Found a 4th redundant copy beyond the issue's own description**:
   `ConversationStateManager.__init__` (`conversation_state_manager.py:62-63`)
   independently declares and stores `on_turn_start`/`on_turn_end`, also entirely
   dead — the issue named only 3 classes.
3. **Confirmed `Orchestrator._execute_turn()` is the real, live turn boundary**:
   it calls `self._audit_emitter.emit_turn_start()`/`emit_turn_end(...)` exactly
   once per `handle_turn()` invocation (`orchestrator.py:213-220`) — the natural
   single call site for `on_turn_start`/`on_turn_end`, and `AuditEventEmitter`
   already stores these callbacks without using them.
4. **Confirmed `handle_llm_turn()` as the correct `on_llm_wait_*` site**: it is
   where `on_error` was already correctly wired in a prior session cycle
   (`self.call_on_error(result.exception)`), constructs a fresh `LLMTurnRunner`
   per call, and calls `runner.run(...)` — the exact LLM-network-wait boundary.
5. **Asked the user to confirm the design** rather than choosing unilaterally,
   per the issue's own explicit instruction. All three questions (wiring
   location for each callback pair, and the return-value question) were
   confirmed with the recommended options above (see Background).
6. **Found the two "success"/"error" characterization tests' mocking strategy
   conflicts with the confirmed wiring location**: both
   `test_wait_and_turn_callbacks_invoked_on_success` and
   `test_wait_end_error_and_turn_end_invoked_when_run_returns_exception` use
   `patch.object(orch._llm_executor, "handle_llm_turn", AsyncMock(...))`, which
   replaces `handle_llm_turn()`'s entire body — including the new
   `on_llm_wait_start`/`on_llm_wait_end` wiring this Plan adds inside it. These 2
   tests must be corrected to patch `agent.llm_turn_executor.LLMTurnRunner`
   instead (letting `handle_llm_turn()`'s real body execute with a controlled
   `runner.run()` return value), per the issue's own explicit allowance:
   "adjusting them only if the exact call site changes their expected call
   counts."
7. **Confirmed the 3rd test needs no such correction**:
   `test_wait_end_invoked_in_except_branch` mocks
   `ctx.services_required.llm.stream` directly (not `handle_llm_turn` or
   `LLMTurnRunner`), exercising the real end-to-end call chain including this
   Plan's new wiring.
8. **Confirmed `runner.run()` never actually raises `LLMTransportError` out to
   `handle_llm_turn()`**: `LLMTurnRunner.run()` (`llm_turn_runner.py:83-88`)
   catches it internally via its own try/except and converts it to a `TurnResult`
   with `.exception` set — so test 3's docstring framing ("except LLMTransportError
   branch... reached when run() itself raises") does not describe a path that
   currently exists in the call chain at the `handle_llm_turn()` level. A
   `try/finally` (rather than a type-specific `except` clause) around the
   `runner.run()` call in `handle_llm_turn()` satisfies this test's underlying
   intent (guarantee `on_llm_wait_end` fires) regardless, without depending on an
   exception path that does not exist.
9. **Blast radius confirmed narrow**: all 4 target classes are constructed only
   from `Orchestrator.__init__`, and no other file in `scripts/`/`tests/`
   constructs `AuditEventEmitter`/`ConversationStateManager`/`LlmTurnExecutor`
   directly with these kwargs (confirmed via architecture/dependency analysis —
   the only regression surface is the 2 test files already in Implementation
   Target Files / Reference Files).

## Risks
- **Risk**: Correcting the 2 characterization tests' mocking strategy could
  itself introduce a subtly wrong test (e.g. `LLMTurnRunner` construction
  arguments not matching what `handle_llm_turn()` actually passes) →
  **Mitigation**: `handle_llm_turn()`'s exact `LLMTurnRunner(self._ctx, guard,
  tracer=self._tracer)` construction was read in full during Step 2/3; the
  corrected test only needs to control the `.run(...)` return value, not
  replicate the constructor call.
- **Risk**: Wrapping `runner.run(...)` in `try/finally` could mask an
  unexpected exception type by still calling `call_on_llm_wait_end()` before it
  propagates, changing existing error-handling behavior for callers relying on
  exception propagation timing → **Mitigation**: `finally` only adds a call to
  `call_on_llm_wait_end()` (a no-op unless a callback is configured); it does not
  catch, swallow, or alter the exception itself — the exception still propagates
  identically after the `finally` block runs, per Python's `try/finally`
  semantics.
- **Risk**: Removing `ConversationStateManager`'s `on_turn_start`/`on_turn_end`
  parameters could break an external caller passing them →
  **Mitigation**: `rg` confirms `Orchestrator.__init__` is the only constructor
  of `ConversationStateManager` anywhere in `scripts/`/`tests/`; this Plan
  updates that single call site in the same step.
