## Goal
- Cap code chunks to the same `max_chunk` upper bound as text chunks by adding an upper
  guard to the shared `merge_text_items` helper, so a single code item longer than
  `max_chunk` is split at a language-independent boundary instead of passing through
  unbounded and being silently dropped by the embedding service.

## Background
`ChunkSplitter` composes `ChunkEnglishMixin` and `ChunkJapaneseMixin` via multiple
inheritance and adds a code path in `_chunk_code`. The two text paths accumulate into
buffers bounded by `min_chunk`/`max_chunk`; the code path routes through
`merge_text_items` in `scripts/rag/ingestion/chunk_utils.py`. That helper enforces
`min_chunk` at the tail but has no upper guard: its `else: buf = item` branch
(`chunk_utils.py`, line 42-43) accepts a single item larger than `max_chunk` and emits it
as-is. `_chunk_code` (`scripts/rag/ingestion/chunk_splitter.py`, lines 215-227) calls
`merge_text_items` with the real `min_chunk`/`max_chunk`, so a `.py`-style source with few
blank lines and long lines yields one code chunk larger than `max_chunk`.
`config/chunk_splitter.toml` marks the whole sizing area an "unvalidated heuristic,
pending performance tuning", so this sits inside an area the owner has accepted as
unvalidated.

## Problem
Text and code are treated inconsistently under the same sizing policy: text is always
capped, code is not. For a repository whose corpus is largely source code, this produces
the largest chunks precisely for the content type most likely to contain long single-line
blocks. `EmbeddingService.get_embedding` returns `None` on input exceeding the model's
length limit and `embed_and_store` maps that to `EMBEDDING_FAILED`, so an oversized code
chunk is silently dropped while the run reports success.

Verified at HEAD with `max_chunk=500`: `merge_text_items(["X"*600], ...)` returns
`["X"*600]` (exceeds `max_chunk`). `_chunk_code` is the only production caller of
`merge_text_items`.

## Reason for Change
The fix is small and reversible, removes an untested assumption about code-chunk size, and
prevents the largest code chunks from being silently dropped. Text and code should obey
the same `max_chunk` bound.

## Implementation Intent
Extend `merge_text_items` so that when a single item cannot fit and the running buffer is
below `min_chunk` (the `else` branch), the item is split into chunks each within
`max_chunk` at a language-independent boundary rather than assigned to `buf` whole.
Preserve `min_chunk` tail-merge, the `\n\n` separator, and `chunk_overlap` behavior for
normal-sized items. Do not touch the text chunkers.

## Requirements
- `REQ-001`: A single code item longer than `max_chunk` never produces a chunk longer than
  `max_chunk` when routed through `merge_text_items` / `_chunk_code`.
- `REQ-002`: Splitting uses a language-independent boundary (whitespace/line or fixed
  character); no stopword removal or Sudachi morphological analysis is applied to code.
- `REQ-003`: Normal-sized items keep their existing `min_chunk`/`max_chunk`/overlap
  behavior; existing `test_chunk_utils.py` and `test_chunk_splitter.py` cases pass.

## Design
Path B: `merge_text_items` is a shared runtime helper (imported by `chunk_splitter.py`
and unit tests; docstring claims three importers). Changing it is a runtime-facing
interface change on a shared helper, so Path B applies even though it has one production
caller.

**Design decision — cap vs. documented exemption (open in the Issue).**
- **Alternative A (recommended): cap.** Split a single oversized item into chunks each
  within `max_chunk` at a language-independent boundary. Prefer splitting on the first
  whitespace/line break within `max_chunk`; fall back to a hard character split at
  `max_chunk` when no whitespace exists. Never apply stopword removal or Sudachi
  analysis (code stays language-independent, per Issue constraint).
  - Compatibility impact: code chunks become bounded; chunk counts may rise for
    code-heavy sources; embeddings no longer drop the largest code chunks. Downstream
    `embed_and_store`/index accept smaller chunks.
- **Alternative B: documented exemption.** Keep empty-line-only splitting, add an
  explicit commented intentional-exemption at the `else` branch and a test pinning it.
  - Compatibility impact: no behavior change; the oversized-chunk-drop risk remains.
- **Choice**: prefer A unless the owner documents a reason for B (recorded as UNK-02).

**Blast radius evidence** (Step 3): `rg`/consumer scan shows `merge_text_items` is
imported only by `scripts/rag/ingestion/chunk_splitter.py` (production) and

import only `start_next_buf`. `lint-imports` is clean. Complexity `radon cc`:

## Risks
- **Risk**: Changing `merge_text_items` alters code-chunk sizes/counts for every code
  chunk, potentially shifting downstream embedding/index expectations. → **Mitigation**:
  targeted unit + integration tests and a full `tests/rag/ingestion` run before merge;
  blast radius scoped to the code path (verified single caller).
- **Risk**: A hard character split at `max_chunk` can break a code token in half. →
  **Mitigation**: prefer whitespace/line-boundary splits; document the hard-split fallback
  as a known limitation in the plan, not the doc.
- **Risk**: The Issue's stated premise that "the English equivalent `merge_text_items`
  never drops" is inaccurate — `merge_text_items` is the *code*-path helper (not the
  English text path, which uses `_merge_paragraphs_en`) and it also drops a short lead
  before an oversized item (verified at HEAD). → **Mitigation**: this plan fixes the code
  path only; the Japanese-path instance of the same defect is handled by sibling issue
  `ragc002`. No scope expansion without owner approval.
