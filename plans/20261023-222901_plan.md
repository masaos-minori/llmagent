## Goal
Provide one repeatable entry point that, after a plan's implementation procedures have been executed, archives every procedure of that batch, marks the matching plan rows `Completed`, and leaves the result ready for a single `chore:` commit — replacing the repeated manual sequence of one `close-implementation` per file plus a plan-table update.

## Priority
Medium

## Scope
- **In-Scope**: discover a batch's procedure files from a plan path or a shared timestamp prefix in deterministic order; refuse atomically when any procedure still has a `Pending` row; mark each discovered procedure's `### Execution Status` rows `Completed` and archive it through the existing `close-implementation` code path; update the matching plan's `### Execution Status` rows; `--dry-run` mode; `--stage-only` support; idempotency on a second run; register the tool in `tools/TOOL_DESCRIPTIONS.md`; reference it from `skills/code-implementation/workflow.md`; add tests under `tests/tools/`.
- **Out-of-Scope**: generating the commit message or running `git commit` (the layer stays `--stage-only`); changing the `### Execution Status` table format or `templates/execution-status.md`; archiving issues (`close-issue`) or plans (`close-plan`); touching `implementations/superseded/` handling or the `done/` directory structure (`rules/ai-execution.md` Global Safety Restrictions); any other workflow stage.

## Background
`git log --grep='archive the executed'` returns 12 commits of the same shape (examples: `46078e90f`, `c50dc24d9`, `8f879463c`, `ae0052f43`, `300cada5d`). Each moves a whole batch of `implementations/*.md` files into `implementations/done/`, sets each procedure's `### Execution Status` rows from `Pending`/`In Progress` to `Completed` with a `YYYYMMDD-HHMMSS` timestamp, and rewrites the matching plan rows of one `plans/done/*_plan.md` `### Execution Status` table to `Completed` with the same timestamp. A representative batch (`46078e90f`) archived 8 procedures sharing the prefix `20261023-112037` and updated 4 plan rows in one commit.

Repository tools already cover the individual operations (`Explicit in code`, per `tools/TOOL_DESCRIPTIONS.md` and the module docstrings):
- `manage_workitem_stage.py close-implementation` archives one file at a time via `move_to_done()` and refuses while any row is `Pending`, unless both `--force` and `--reason` are supplied.
- `manage_workitem_stage.py set-status` / `set-step-status` and `update_execution_status()` edit a workitem's `### Execution Status` rows.
- `set_execution_status.py` marks selected rows `Completed` and stamps `Started`/`Completed` (its `--date` uses `YYYY-MM-DD`).
- `manage_workitem_stage.py` subcommands share `move_to_done()` (auto-commit dirty source, remote-conflict check, `--stage-only`) and `_report_move_result()`.

`skills/code-implementation/workflow.md` already tells the implementer to prefer `close-implementation` per target file (lines 24, 33, 141, 397). No tool or documented step runs the whole batch plus the plan-status update as one operation (`Needs confirmation`: this was judged from `tools/TOOL_DESCRIPTIONS.md` and the workflow text only, not from reading every tool body).

## Problem
Closing one batch means one `close-implementation` call per procedure file (7 to 9 files in the latest commits), then a plan-table update, then a commit. `AGENTS.md` Global Rule 7 (an operation performed three or more times is to be extracted into a `tools/` script) applies: this sequence has been performed at least 12 times as a whole but exists only as individual tool calls. The manual form invites omissions, such as a plan row left `In Progress` or one procedure left unarchived.

## Reason for Change
The repetition is already established by history (12 commits), and the building blocks exist, so the remaining cost is orchestration only. A single entry point lowers the chance of a half-closed batch and shortens the end of every implementation cycle. Local feedback before commit is cheaper than a red CI run, and the rule set already exists in prose, so the only missing piece is an executable form.

## Implementation Intent
Add a thin orchestration layer on top of the existing tools, not a second implementation of archival or table editing. The layer discovers a batch's procedure files and calls the existing `move_to_done()` / `update_execution_status()` logic for each. It keeps the existing refusal behavior (the `Pending` row check) and adds an atomic pre-check so a batch is never half-archived. Committing stays with `skills/git-commit-and-sync`; the layer stages only (`--stage-only` semantics) so the commit message remains a human or agent decision.

## Requirements
- `REQ-001`: Given a plan path or a shared timestamp prefix, discover that batch's procedure files in `implementations/` in deterministic (sorted) order.
- `REQ-002`: Before moving any file, check every discovered procedure; refuse with no file moved if any row is `Pending`.
- `REQ-003`: Mark each discovered procedure's `### Execution Status` rows `Completed` and archive it through the existing `close-implementation` (`move_to_done()`) code path.
- `REQ-004`: Update the matching plan's `### Execution Status` rows to `Completed` with timestamps.
- `REQ-005`: `--dry-run` prints the intended moves and edits without changing any file.
- `REQ-006`: `--stage-only` is passed through to the archival move.
- `REQ-007`: A second invocation on an already-closed batch is a no-op or a clear refusal, not a partial re-run.
- `REQ-008`: Register the tool in `tools/TOOL_DESCRIPTIONS.md` and reference it from `skills/code-implementation/workflow.md`.

## Design
**Architecture.** `tools/` scripts are not under `scripts/`, so the import-layer contract does not constrain them. Cross-import between `tools/` scripts is established precedent (`tools.check_*.py` import `tools._docs_consistency_lib` and `tools.check_canonical_source_registry`), so `close-batch` may import `move_to_done()` / `update_execution_status()` from `manage_workitem_stage.py` directly.

**Historical.** 12 manual `archive the executed` commits, all by a single author (single-author ⇒ low bus-factor risk; the chore pattern is high-churn but mechanical). No regression to bisect.

**Design decision — subcommand vs separate tool.** Recommended: a new `close-batch` subcommand on `manage_workitem_stage.py`. It reuses `move_to_done()` (auto-commit, remote-conflict check, `--stage-only`), the argparse conventions, and `_report_move_result()`, and keeps the `close-*` family together. The alternative (a separate `tools/close_batch.py`) separates concerns but duplicates the move plumbing the family already shares. Record whichever is chosen in this section at plan-to-implementation time.

**Batch identification.** A shared timestamp prefix in `implementations/<prefix>_NN_*.md` filenames is the programmatic key (confirmed: `20261023-112037_*`). The same set is derivable from the owning plan's `Implementation Target Files` table. Accept either input: a plan path (derive the prefix from its target files) or a bare timestamp prefix (glob `implementations/<prefix>_*.md`).

**Atomicity.** Validate the whole batch first (the `Pending` pre-check), then mark all rows `Completed`, then archive all files. This ordering means a failure mid-batch cannot leave a partially archived batch, and the destructive `git mv` never runs against a batch that failed its pre-check.

**Timestamp format.** Stamp `Started`/`Completed` with `date +%Y%m%d-%H%M%S` (`YYYYMMDD-HHMMSS`) to match the `close-*` family and the historical batch-close commits, not `set_execution_status.py`'s `YYYY-MM-DD` (resolves UNK-02).

**Idempotency.** After archiving, the batch's files no longer exist under `implementations/`, so a second discovery finds nothing and the run is a no-op. If the plan rows are already `Completed`, re-marking is idempotent; surface a clear "already closed" message rather than a partial re-run.

## Risks
- **Risk**: A plan may own more than one batch, so marking all its plan rows `Completed` could over-mark a not-yet-done batch. → **Mitigation**: tie the plan-status update to the specific batch (find the plan referencing this batch's files); if a multi-batch plan is detected, scope the row update to this batch's rows or refuse and require manual handling (UNK-03).
- **Risk**: Marking rows `Completed` inside the batch-close could bypass the human "verify each step" gate. → **Mitigation**: the atomic `Pending` pre-check still blocks incompletely-executed batches; marking only proceeds after the check passes, and the working-tree diff is reviewed before the `chore:` commit.
- **Risk**: Importing `manage_workitem_stage.py` internals couples the new command to its implementation. → **Mitigation**: import only the stable public functions (`move_to_done`, `update_execution_status`, parse helpers) and keep the subcommand thin; a refactor of those helpers is covered by the existing `test_manage_workitem_stage.py` suite.
