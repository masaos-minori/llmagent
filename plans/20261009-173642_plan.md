# Plan: Validate workflow definition content in the startup preflight

## Goal
- Make the startup preflight (`check_workflow_definition`) reject a malformed workflow definition file (invalid JSON, wrong shape, missing required keys or required stages) with a `RuntimeError` naming the file and cause, instead of passing it through to fail later in the Orchestrator constructor.

## Priority
Low

## Scope
- **In-Scope**: extend `check_workflow_definition` to load the definition through the existing loader and re-raise `WorkflowLoadError` as `RuntimeError`; add content-validation tests to `tests/agent/test_repl_health.py`; fix the existing `test_present_file_passes` fixture that writes an invalid `{}`.
- **Out-of-Scope**: changing the loader's validation rules (`_validate`); changing the Orchestrator constructor; other startup validations; the schema preflight (`check_workflow_schema`); any public interface change.

## Background
ADR-001 makes the Workflow Engine mandatory and forbids a fallback path (Decision 4); ADR-004 requires fail-fast for a missing or invalid workflow (INV-03). The wfstartup01 plan (`plans/done/20261008-143632_plan.md`) made a workflow load failure a fatal startup error in the Orchestrator constructor. The preflight (`check_workflow_definition`) runs earlier but currently checks only file existence, so a malformed definition slips past it and fails only when the Orchestrator is constructed.

## Problem
- The preflight function checks `default.json` existence only; invalid JSON, a wrong shape, or missing required stages pass it.
- The failure is still fatal (the Orchestrator constructor fails), but it is reported from a different place and message than the other preflight failures, and some preflight-time cleanup/reporting that runs only for preflight failures does not run.

## Reason for change
Consistent, early failure reporting: a malformed definition is caught by the preflight with its usual message rather than surfacing later from the Orchestrator constructor. The change also strengthens ADR-001 INV-01 ("a missing or invalid workflow raises RuntimeError"), which currently only proves the *missing* and *Orchestrator-constructor* cases.

## Implementation intent
Reuse the existing loader's validation rather than duplicating its rules. After the existing existence check, call `WorkflowLoader(workflows_dir=target_dir).load("default")` inside a `try` that catches `WorkflowLoadError` and re-raises it as a `RuntimeError` naming the file and cause. Keep the existing missing-file message unchanged. The loader is side-effect free (pure read + in-memory construct), so calling it from the preflight is safe.

## Requirements
- `REQ-001`: When `default.json` contains invalid JSON, `check_workflow_definition` MUST raise a `RuntimeError` naming the file and cause.
- `REQ-002`: When `default.json` has the wrong shape or is missing a required key or required stage, `check_workflow_definition` MUST raise a `RuntimeError` naming the file and cause.
- `REQ-003`: A valid `default.json` (matching the shipped definition shape) MUST pass `check_workflow_definition` without raising.
- `REQ-004`: The existing missing-file `RuntimeError` message (naming the file and remediation hint) MUST be unchanged.

## Design
- `check_workflow_definition` keeps its signature and lazy-import pattern. After the existing existence check, it imports `WorkflowLoader` and `WorkflowLoadError` lazily and calls `WorkflowLoader(workflows_dir=target_dir).load("default")`. Any `WorkflowLoadError` is caught and re-raised as `RuntimeError(f"Workflow definition invalid: {workflow_file}: {exc}") from exc`.
- The loader's validation rules are reused, not duplicated (per the issue's constraint).
- The missing-file branch and its message are unchanged.
- `test_present_file_passes` is updated because `"{}"` is now invalid; it writes a complete valid definition instead.
