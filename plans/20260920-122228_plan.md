## Background
Direct, full-file reading (2026-09-20) of both source files, both
dedicated test files, and all 4 call/reference sites confirms:

- `scripts/shared/config_validator.py` (79 lines) defines
  `RagConfigValidator`, whose `validate()` performs exactly 2 semantic
  checks against a RAG config dict: `use_rrf` disabled (quality warning)
  and removed semantic-cache keys present (migration error). Called from
  exactly one site: `scripts/agent/config_builders.py`'s
  `_build_rag_config()` (line 198), while constructing the `RAGConfig`
  sub-object from a raw dict — a construction-time semantic sanity check
  scoped to that one sub-config.
- `scripts/shared/production_config_validator.py` (340 lines) defines
  `ProductionConfigValidator`, whose `validate()` performs structural/
  security validation against a config dict: required strict-mode keys,
  bidirectional tool-safety-tier consistency, approval risk-floor
  enforcement for git-write tools, and unknown-top-level-key rejection via
  dataclass-field introspection across 9 sub-config classes (including
  `RAGConfig` itself — confirmed at line 161 of
  `_get_valid_production_keys()`). Called from 2 sites:
  `scripts/agent/config_builders.py`'s `_run_production_validation()`
  (line 484, against the full merged production config, exit(1) on error)
  and `scripts/agent/services/security_audit.py` (line 142, against a
  small, hand-constructed 4-key subset dict for an audit-specific check —
  legitimate reuse of the same validator class for a narrower invocation,
  not evidence of confusion).

**Architectural conclusion**: the two validators check fundamentally
different concerns — `RagConfigValidator` performs semantic/value
validation scoped to RAG only; `ProductionConfigValidator` performs
structural/key-existence and security-policy validation across the entire
config (RAG included, via its dataclass introspection, but only for
key-set membership, never RAG-specific semantics). This is a clean
separation by validation *kind* (semantic value checks vs. structural/
security checks), not an accidental duplication. `ProductionConfigValidator`
already imports `ConfigValidationResult` from `config_validator.py`
(confirmed at line 9) — the two modules share this one small, appropriate
piece of common infrastructure; nothing else is shared or duplicated.

**Test-footprint evidence**: `RagConfigValidator` is exercised only by its
own dedicated `tests/shared/test_config_validator.py` (13 tests, confirmed
via this Plan's own baseline run). `ProductionConfigValidator` is exercised
by its own dedicated `tests/shared/test_production_config_validator.py`
(46 tests) plus 4 additional files (`tests/agent/test_startup.py`,
`tests/integration/test_production_security_regression.py`,
`tests/shared/test_config_loader.py`,
`tests/shared/test_shared_boundary_conditions.py`) — confirmed via `grep`,
2026-09-20: none of these 4 additional files reference `RagConfigValidator`
at all. This asymmetric test footprint (1 dedicated file for RAG vs. 5
files touching production validation) reflects the genuinely different
scope and criticality of each validator, not overlap.

**Test-file boundary documentation** (resolves the source Issue's own
Unresolved Question, already answered during the Issue's own adversarial
verification and reconfirmed here): neither test file's module docstring
documents the intended scope boundary — `test_config_validator.py`'s
docstring only restates `config_validator.py`'s own scope;
`test_production_config_validator.py` has no module docstring at all. This
confirms the boundary is not documented anywhere today and this Plan's
docstring update is net-new, not a duplicate of existing documentation.

**Naming-clarity observation** (not fixed by this Plan — see Scope):
`config_validator.py`'s generic name does not signal its RAG-specific scope
the way `production_config_validator.py`'s name signals its scope. A future
rename (e.g. to `rag_config_validator.py`) would remove this asymmetry, but
is deliberately deferred (see Scope's Out-of-Scope).

## Problem
The source Issue's own Reason for Change names a real (if modest) risk:
two similarly-named validator modules in the same directory, one already
importing from the other, with no documented statement of which module
owns which validation concern — a future contributor could plausibly add a
check to the wrong module, or duplicate a check across both, without
realizing the existing intentional boundary.

## Reason for change
This Plan resolves the source Issue's investigation with a concrete,
evidenced conclusion (no consolidation needed) and closes the
documentation gap that made the investigation necessary in the first place
(neither validator's docstring, nor either test file's docstring,
currently states the boundary).
