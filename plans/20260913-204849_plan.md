## Background
The Issue's cited claim
(`docs/03_rag_03_03_query_pipeline-context-and-diagnostics.md:54-57`: "the name
`http_result_kind` is used in two different value systems ... `get_diagnostics()["http_result_kind"]`
... uses 3 string literals: `"remote_nonempty"` / `"remote_empty"` /
`"in_process_fallback"`") is quoted accurately from the document, but the underlying
technical claim does not hold against the current implementation.

**Re-verified 2026-09-13** (this cycle, against the current repository state):
- `SearchDiagnostics.http_result_kind` (`models_result.py:109`) is typed
  `HttpResultKind` (4 enum values: `SUCCESS`/`EMPTY`/`ERROR`/`NOT_USED`,
  `models_result.py:29-35`) — accurate as documented
- `get_diagnostics()` (`pipeline.py:342-366`) does NOT return the raw string
  literals. It explicitly normalizes the value before returning it:
  ```python
  http_result_kind_raw = getattr(self.last_search_diagnostics, "http_result_kind", None)
  if isinstance(http_result_kind_raw, HttpResultKind):
      http_result_kind = http_result_kind_raw
  else:
      http_result_kind = _map_http_result_kind(http_result_kind_raw)
  ```
  `_map_http_result_kind()` (`http_augment.py:18-32`) maps
  `"remote_nonempty"→SUCCESS`, `"remote_empty"→EMPTY`,
  `"in_process_fallback"→ERROR`, `None→NOT_USED` — a complete, 1:1, deterministic
  mapping covering every value each vocabulary can take. The resulting
  `http_result_kind` variable — always an `HttpResultKind` enum, never a raw string
  literal — is what `get_diagnostics()`'s returned dict actually contains
  (`PipelineDiagnostics.to_dict()`, `diagnostics.py:108`).
- The three string literals (`"remote_nonempty"` etc.) exist only as
  `HttpAugment._http_result_kind`'s internal type (`http_augment.py:110`,
  `Literal["remote_nonempty", "remote_empty", "in_process_fallback"]`) — an
  implementation-internal representation inside a different class
  (`rag.http_augment.HttpAugment`), never exposed through `get_diagnostics()`.
- The Note's cited call sites (`RagPipeline._run_http_augment()`,
  `RagPipeline._http_result_kind`) do not exist anywhere in `pipeline.py` — confirmed
  via `grep -n "_http_result_kind" scripts/rag/pipeline.py`, which found only the
  `_map_http_result_kind` import and its one call site (`pipeline.py:354`); no
  `RagPipeline` instance attribute by either name exists. `self._http_result_kind`
  (`http_augment.py:110`) belongs to `HttpAugment`, a distinct class.

This is the same class of defect found in a sibling issue processed earlier this
cycle (`issues/done/20260913-183005_stale_fetch_result_http_mode.md`): the
documentation describes an earlier state of the implementation that a later,
unrelated code change (introducing `_map_http_result_kind()`) has since resolved,
without the documentation being updated to match.

## Problem
The documented Boundary Conditions note warns readers that
`get_diagnostics()["http_result_kind"]` uses a different, incompatible vocabulary
from `SearchDiagnostics.http_result_kind`, and cites non-existent methods/attributes
as the mechanism. In fact, both fields already carry the same `HttpResultKind` enum
value at the point a caller of `get_diagnostics()` would read it — the warning is
not just imprecise, it actively describes a confusion that does not exist at the
public-API level, potentially causing a reader to over-engineer defensive handling
for a vocabulary mismatch that has already been resolved by
`_map_http_result_kind()`.

## Reason for change
Correct the note to describe the actual current relationship: both fields carry the
same `HttpResultKind` enum vocabulary by the time either is read from
`get_diagnostics()` or `last_search_diagnostics`; the three string literals are a
separate, internal-only representation confined to `HttpAugment`, never part of any
documented public field's actual value.

## Implementation intent
Rewrite section 4.2's Boundary Conditions note
(`docs/03_rag_03_03_query_pipeline-context-and-diagnostics.md:54-57`) to state: (1)
`SearchDiagnostics.http_result_kind` and `get_diagnostics()["http_result_kind"]` both
carry `HttpResultKind` enum values — they are not two different vocabularies at the
public-API level; (2) `HttpAugment` (`http_augment.py`) internally classifies HTTP
call results using three string literals (`"remote_nonempty"`/`"remote_empty"`/
`"in_process_fallback"`), but `_map_http_result_kind()` converts this to the
`HttpResultKind` enum before either public field is set — the string literals never
reach a caller reading either field.
