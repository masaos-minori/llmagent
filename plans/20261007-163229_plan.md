## Goal
- Make the MCP idempotency cache serve only its intended purpose (suppressing duplicate execution of a re-sent logical call) and make the Agent-side retry and the server-side cache cooperate, so side-effecting tools are neither silently skipped nor executed twice.

## Priority
High

## Scope
- **In-Scope**: Rewrite the `_duplicate_cache` semantics in `scripts/mcp_servers/dispatch.py` (empty-key guard, key by key+tool+normalized-args, reject key reuse with different content, TTL, max-entry eviction, no caching of error/dry-run results). Generate one idempotency key per logical call in `scripts/shared/http_transport.py`, send it as `X-Idempotency-Key` on every retry, and gate write-tool post-send retries on key presence. Add unit tests for both layers. Update the MCP dispatch/transport documentation and ADR-004/ADR-007 when their wording changes.
- **Out-of-Scope**: Changes to git-mcp ref validation, audit records, or the RAG HTTP path. Redesign of the retry policy for read-only tools. Persisting the idempotency cache across server restarts. Any change to `extract_request_context()` in `scripts/mcp_servers/server.py` beyond reading it (the empty-key normalization is handled at the dispatch layer).

## Background
- Source: local investigation notes (memo1.md, ISSUE-01); a new finding, not yet registered as a Known Issue. The HTTP MCP transport retries failed calls, and the MCP server keeps a duplicate-detection cache for side-effecting tools. The two mechanisms were designed independently.

## Problem
- The Agent-side `HttpTransport.call()` does not send an `X-Idempotency-Key` header (Confirmed by repository evidence — `scripts/shared/http_transport.py`: `call()` builds only `Authorization` and `X-Session-Id`; no occurrence of the header anywhere under `scripts/`).
- The server-side `extract_request_context()` falls back to an empty string when the header is absent (`scripts/mcp_servers/server.py` line 142: `request.headers.get("x-idempotency-key", "")`), and `dispatch_tool()` tests `idempotency_key is not None` (`scripts/mcp_servers/dispatch.py` lines 99/111/119), so an empty string is treated as a valid key.
- Consequence (Derived from confirmed evidence): every side-effecting call in a long-running server process shares cache key `""`, keyed only by that key (not by tool name or arguments), so the first such call wins and every later side-effecting call returns the first result without executing.
- The cache has no TTL and no size bound, and it caches both error results (`is_error=True`) and `dry_run` results. `dry_run` is emitted inside each tool service's output JSON (e.g. `scripts/mcp_servers/shell/shell_service.py`, `scripts/mcp_servers/git/*`), so `dispatch_tool()` cannot distinguish a dry-run result from a real one today.
- `HttpTransport.call()` retries up to `_RETRY_MAX = 3` on `{429, 502, 503, 504}` and swallows `httpx.RequestError` into another silent retry (line 175-176), without distinguishing write tools.

## Reason for change
- Writes (git commit/push, file writes, `rag_delete_document`, etc.) can appear to succeed without being executed — the "report non-execution as success" failure that ADR-004 prohibits.
- A cached `dry_run` result can be returned as the response to a real execution.
- The unbounded cache grows without limit in a long-running server.
- Fixing only the cache would expose double execution on retry, so the cache fix and the retry fix must ship together.

## Implementation intent
- The caller (Agent) owns key generation: one key per logical call, reused across retries of that call.
- A call without a key is never cached and always executes.
- The cache is keyed by idempotency key plus tool name plus a normalized hash of the arguments; a call that reuses a key with different content is rejected rather than served.
- The cache carries a TTL and a maximum entry count with oldest-first eviction.
- Error results (`is_error=True`) and `dry_run` results are not cached.

## Requirements
- `REQ-001`: In `dispatch_tool()`, a `None` or empty-string `idempotency_key` means "no key": the function neither reads nor writes `_duplicate_cache` for that call, and the call always executes. (`scripts/mcp_servers/dispatch.py`)
- `REQ-002`: The cache is keyed by (idempotency_key, tool name, normalized hash of arguments). A call whose key already maps to a stored entry but whose content differs is rejected (returned as an error result) instead of serving the stale entry. (`scripts/mcp_servers/dispatch.py`)
- `REQ-003`: The cache enforces a TTL and a maximum entry count with oldest-first eviction. Values are configuration/constants decided during implementation. (`scripts/mcp_servers/dispatch.py`)
- `REQ-004`: Error results (`is_error=True`) and `dry_run` results are not stored in the cache. (`scripts/mcp_servers/dispatch.py`)
- `REQ-005`: `HttpTransport.call()` generates one UUID per logical call and sends the same value as the `X-Idempotency-Key` request header on every retry of that call. (`scripts/shared/http_transport.py`)
- `REQ-006`: For write tools, retry after a post-send error occurs only when an idempotency key is present; retry behavior for read-only tools is unchanged. (`scripts/shared/http_transport.py`)
- `REQ-007`: Unit tests for `dispatch_tool()` cache behavior (empty/None key, same key executes once, same key with different content rejected, TTL expiry, eviction, no error/dry-run caching) and a transport-level test that retries reuse the same key, covering every Acceptance criterion below.
- `REQ-008`: Update the MCP dispatch/transport documentation (idempotency ownership, retry rules, cache semantics) and refresh ADR-004/ADR-007 references when their wording changes.

## Acceptance criteria
- Two consecutive write-tool calls without the `X-Idempotency-Key` header both execute (REQ-001).
- A re-sent call with the same key executes exactly once; a later call with the same key but different tool name or arguments is rejected rather than served (REQ-002).
- A real execution after a `dry_run` call with otherwise identical input actually executes, because the `dry_run` result is not cached (REQ-004).
- Error results are not served from the cache (REQ-004).
- A re-sent write call retries reuse the same `X-Idempotency-Key` value (REQ-005).
- Read-only retry behavior is unchanged from current (REQ-006).
- The MCP dispatch/transport doc reflects the new idempotency ownership, cache keying, TTL/eviction, and retry rules (REQ-008).

## Assumptions
- The normalized-argument hash uses a deterministic serialization (sorted keys) so logically identical arguments hash identically regardless of insertion order.
- The idempotency key is generated per `HttpTransport.call()` invocation and delivered to the server via the `X-Idempotency-Key` request header; the server keys the cache on the received header value.
- Retry semantics for non-side-effecting (read) tools stay exactly as today; only write-tool post-send retry gating changes.
- The existing `lint-imports` broken contract (`shared` must not import from `agent`) is pre-existing on master and unrelated to this change; it is not fixed here.
