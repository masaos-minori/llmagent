## Goal
- Extend `tools/check_docs_structure.py` with schema-driven front-matter validation
  (required fields, finalized `area` enum, `status` enum) that reuses `docmeta01`'s
  `schemas/doc_front_matter.json` artifact as the single source of truth, and wire it
  into CI in report-only (non-blocking) mode — since no existing CI workflow
  currently runs this tool at all, contrary to the source Issue's assumption, and
  `docmeta02`'s corpus migration has not yet landed.

## Priority
Medium

## Scope
- **In-Scope**: adding schema-validation logic to `tools/check_docs_structure.py`
  behind a new, backward-compatible `--schema PATH` flag; adding a new test file for
  it; wiring the check into `.github/workflows/governance-docs-consistency.yml` in
  report-only mode; updating `tools/TOOL_DESCRIPTIONS.md`'s entry for the tool.
- **Out-of-Scope**: deciding the schema or `area` enum (`docmeta01`'s scope);
  migrating any individual document (`docmeta02`'s scope); adding new metadata
  fields beyond what `docmeta01` finalizes; making the check CI-blocking (deferred
  until `docmeta02` is verified landed — a follow-on cutover, not this Plan's own
  work); fixing the unrelated stale `paths:` trigger references this Plan's
  investigation found in 5 other workflow files (see Background) — out of this
  Plan's scope, a separate pre-existing issue.

## Background
`tools/check_docs_structure.py`'s `check_front_matter()` already requires
`title`/`area`/`tags`/`related` to be present and can check a single file's `area`
against an expected value via `--area`, but does not validate against a schema file,
does not enumerate allowed `area`/`status` values, and does not check any date-format
field. Contrary to the source Issue's Background/Target Files assumption ("whichever
existing workflow already runs `check_docs_structure.py`"), a full audit of
`.github/workflows/*.yml` (10 files) and `.pre-commit-config.yaml` at Plan time found
**no existing CI wiring for `check_docs_structure.py` at all** — the closest match,
`governance-docs-consistency.yml`, only runs `tools/check_needs_confirmation_inventory.py`;
`.pre-commit-config.yaml` only runs `tools/check_docs_quality.py`. Several workflow
files (`overview-docs-consistency.yml`, `rag-docs-consistency.yml`,
`deployment-docs-consistency.yml`, `mcp-docs-consistency.yml`, `rag-docs-quality.yml`,
`backward-compat-check.yml`) have `paths:` trigger references to tool files that do
not exist in `tools/` (e.g. `check_overview_docs_consistency.py`,
`check_doc_quality.py`) — pre-existing drift unrelated to this Plan, not fixed here.
No `jsonschema` library is a project dependency (`pyproject.toml` lists only
`pydantic`); the source Issue's own Constraints allow a hand-written equivalent when
no library is available and adding one is not justified for a single use case —
justified here, since `docmeta01`'s schema shape (a `required` array plus two small
enums) does not need a general-purpose JSON-Schema evaluation engine.
`tests/tools/` exists with one test file per tool (`test_manage_frontmatter.py`,
`test_rename_doc.py`, etc.) but has no `test_check_docs_structure.py` — this tool
currently has zero test coverage under that convention.

## Problem
Without CI enforcement, the consistency `docmeta01`/`docmeta02` establish is not
durable — a future document could reintroduce `category:`, use an `area` value
outside the finalized enum, or omit a required field, and nothing would catch it
before merge, since `check_docs_structure.py` is not currently invoked by any CI
mechanism.

## Reason for change
Per `rules/ai-execution.md` Repository Tool Usage and this repository's convention of
automating well-defined structural rules rather than relying on reviewer memory, a
fixed field set and a fixed enum should be enforced mechanically once `docmeta01`
produces a machine-readable definition of them.

## Implementation intent
Add a new, optional `--schema PATH` flag to `tools/check_docs_structure.py` and a
sibling validation function that loads the given JSON file (`json.loads`, no new
dependency) and checks: every field in its `required` array is present; `area`'s
value (when the schema defines an `enum` for it) is a member of that enum; `status`'s
value (when present and the schema defines an `enum` for it) is a member of that
enum. Only run this validation when `--schema` is supplied, so default invocations
(including the tool's own future or hypothetical existing tests) are unaffected —
satisfying the source Issue's Constraint against breaking `check_front_matter()`'s
current `--area` single-file-expected-value usage. Report violations via the same
`f"{path.name}: ..."` string format the tool already uses. Add a new step to
`.github/workflows/governance-docs-consistency.yml` invoking the tool with
`--schema schemas/doc_front_matter.json` against the full `docs/*.md docs/adr/*.md`
corpus, marked `continue-on-error: true` (report-only) since `docmeta02` has not yet
landed — flipping this to blocking is an explicit follow-on cutover once `docmeta02`
is verified complete, not part of this Plan's own Implementation steps. Add
`tests/tools/test_check_docs_structure.py`, matching the sibling test files'
`tests/tools/` convention, covering the new schema-validation logic against a
compliant and a non-compliant fixture. Update `tools/TOOL_DESCRIPTIONS.md`'s entry
for the tool to describe the new capability.

## Design
This Plan adds a backward-compatible extension to an existing CLI tool, a new test
file, a CI workflow step, and a documentation-row update — no new module or package,
no database schema change, but 4 Implementation Target Files exceeds Path A's "≤ 3
files" threshold. Path A/B classification (see `skills/issue-to-plan/SKILL.md`
Routing): **Path B**.
- **Architecture analysis**: N/A — `tools/check_docs_structure.py` is a standalone
  CLI script with no importers among `scripts/` runtime modules (`grep -rn "check_docs_structure"
  scripts/` returns no matches); the new `--schema` flag is purely additive to its
  own `main()`.
- **Dependency graphing**: The concrete file list is the 4-row Implementation Target
  Files table above, built directly from this Plan's own investigation (CI workflow
  audit, `tests/tools/` convention check, `pyproject.toml` dependency check) rather
  than an automated import-graph tool, since none of the 4 files import each other
  in a way graphing would surface new information.
- **Historical analysis**: All 4 target files show 0 commits in the last 30 days
  (low recent churn); bus factor is 1 (single-author repository, consistent with
  `docmeta02`'s finding) — low risk for a small, additive change reviewed by the
  same owner who authored the surrounding tooling.
- **Operational dependency inspection**: N/A — no running process depends on
  `tools/check_docs_structure.py` or the CI workflow at runtime; both only execute
  in CI/dev-time contexts, not production.

The substantive design decision is validating against the raw JSON Schema dict via a
minimal, targeted reader (`required`/`enum` keys only) instead of adding a
`jsonschema` dependency (see Assumptions) — kept intentionally narrow to match the
simple shape `docmeta01`'s schema is expected to have, per that Plan's own REQ-006.
