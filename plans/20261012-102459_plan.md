## Goal
- Enforce the ADR-006 INV-13 multi-consumer promotion rule in both promotion paths: an event is promoted to the DLQ only when every consumer that has a delivery record for it has exhausted its retry budget and none has ACKed.

## Priority
High

## Scope
- **In-Scope**:
  - One shared promotion predicate in `scripts/eventbus/dlq.py`, used by the background sweep and made available to the inline path.
  - The inline path in `scripts/eventbus/ack_route.py` promotes only when the predicate holds.
  - Multi-consumer tests for both paths.
  - Documentation updates: define "attempting consumer" in `eventbus_05`, cite the new tests in ADR-006 INV-13's verification entry, and refresh the generated reference block.
- **Out-of-Scope**:
  - Changing the per-consumer failure counting, the retry budget, requeue semantics, the DLQ listing, or the schema.
  - A timeout for a consumer that stops responding (see UNK-02).
  - Changing `promote_single`'s signature or the single-consumer behavior.

## Background
- Owner decision (`Explicit in user instruction`, 2026-10-12): the ADR-006 rule is adopted.
- ADR-006 INV-13 and `eventbus_05_dlq_offsets_and_delivery_semantics.md` state that an event promotes only when every attempting consumer has exhausted its budget and none has ACKed.
- Repository evidence (`Explicit in code`): the sweep query in `dlq.py` joins `consumer_delivery` and promotes when any one row has `consumer_delivery_failure_count >= max_retry`; the inline path in `ack_route.py` promotes when the nacking consumer's own count reaches `max_retry`; `promote_single` checks only `dlq_at IS NULL`.
- Repository evidence (`Explicit in code`): `consumer_delivery` rows are created only by the ACK upsert and the NACK upsert in `delivery_repo.py`, so an "attempting consumer" in the code's terms is a consumer that has ACKed or NACKed the event.
- Source issue: `issues/20261012-100156_eb019dlqmulti_*`; related: `plans/done/20261012-101129_plan.md` (eventbus_03 points to `eventbus_05` for the rule).

## Problem
- One consumer exhausting its budget moves an event to the DLQ even when another consumer is still working through its retries or has already ACKed it; a later requeue can redeliver the event to a consumer that already acknowledged it.
- No test pins the multi-consumer case in either direction.

## Reason for change
- Correctness risk on a delivery guarantee: premature DLQ promotion in multi-consumer setups, and a documented invariant that the code does not satisfy.

## Implementation intent
- Define the rule once as a predicate over the event's `consumer_delivery` rows, apply it in the sweep query and as a pre-check in the NACK route, and leave the promotion routine, DLQ record format, and `events.dlq_at` semantics unchanged.
- The predicate: the event has at least one delivery row, no row has `acked = 1`, and every row has `consumer_delivery_failure_count >= max_retry`.

## Requirements
- `REQ-001`: `scripts/eventbus/dlq.py` provides one public predicate for the rule above that takes a connection, an event id, and the retry limit, and the sweep selects events by the same rule.
- `REQ-002`: The background sweep promotes an event only when the predicate holds, and an event with no delivery rows is never promoted.
- `REQ-003`: The NACK route promotes inline only when the nacking consumer's count has reached the retry limit and the predicate holds.
- `REQ-004`: Tests cover two consumers of one event for both paths: one consumer exhausted while another is below the limit (no promotion); one exhausted while another has ACKed (no promotion); all exhausted (promotion); and the single-consumer behavior stays unchanged.
- `REQ-005`: `eventbus_05_dlq_offsets_and_delivery_semantics.md` states that an attempting consumer is one with a delivery record (created by its ACK or NACK) and what that implies for promotion; ADR-006 INV-13's verification entry cites the new tests; the generated reference block lists the new predicate.
- `REQ-006`: `promote_single`'s signature, the DLQ record format, and the single-consumer behavior are unchanged.

## Design
- **Decisions (REQ-001 to REQ-006)**: one predicate over the event's delivery rows (at least one row, none ACKed, all at or above the limit) shared by the sweep and the NACK route; the NACK route keeps its trigger (the nacking consumer's count reached the limit) and adds the predicate as a pre-check; `promote_single` is left unchanged so direct callers and existing tests behave as before.
- **Path classification**: Path B. Six files, including two production modules and a behavior change on a delivery guarantee.
- **Architecture analysis**: `lint-imports` reports 5 contracts kept, 0 broken; the change stays inside `eventbus` and adds no import from `agent`, `mcp_servers`, `rag`, or `db`.
- **Dependency graphing**: `sweep_orphans` is called from the background loop in `app.py` and by tests; `promote_single` is called from the NACK route and `test_eventbus_dlq.py`; `_shared_promote` is reached only through `sweep_orphans`. Files requiring change: the six above. Existing tests calling `sweep_orphans` seed a single consumer row at the limit and are expected to keep passing; this is confirmed at implementation.
- **Historical analysis**: `ack_route.py` changed in 15 commits in the last 30 days and `dlq.py` in 2, so `ack_route.py` is the riskier file and its change is kept to one pre-check.
- **Operational dependency inspection**: the change affects the eventbus service process only; no other process shares its SQLite connection design beyond what exists. `deploy.sh` rsyncs `scripts/`, so no copy-line change; the service needs a restart to load the change. No dependency upgrade is involved, so `pip-audit` is not applicable.
