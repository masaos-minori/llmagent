## Background
`llm_visibility_base` is an immutable, discovery-time visibility field on
`RuntimeTool` (`scripts/shared/runtime_tool.py:53,72,76-77`; `frozen=True` dataclass,
set once in `__post_init__` when not explicitly supplied). REQ-001
(`docs/00_governance_03_issue-and-uncertainty-management.md:499-516`) was filed to
track a gap where config reload could re-enable a tool hidden from the LLM at
discovery time, and remains `Status: open`.

## Problem
Step 3 investigation (adversarial verification against current source) found the
Issue's central factual claim — "no enforcement prevents config reload from
overriding this field" — is now stale. `RuntimeToolRegistry.apply_policy()`
(`scripts/shared/runtime_tool_registry.py:150-175`) already computes:

```python
resolved_llm_visibility_base = _or_default(tool.llm_visibility_base, True)
new_enabled = resolved_llm_visibility_base and (
    not allowed_tools or name in allowed_tools
)
new_tools[name] = dataclasses.replace(
    tool, agent_safety_tier=tier, enabled_for_llm=new_enabled
)
```

`dataclasses.replace()` does not touch fields it isn't given, so `llm_visibility_base`
itself is carried over unchanged into the new `RuntimeTool` instance, and the `and`
against `resolved_llm_visibility_base` means a tool with `llm_visibility_base=False`
can never end up `enabled_for_llm=True` regardless of `allowed_tools` content. `git
blame` confirms this exact logic was introduced by commit `520c9b39f9` ("feat: tool
policy comprehensive tests and mdq command improvements", 2026-09-17) — three days
before this Issue was filed (2026-09-20).

What is still missing, confirmed by reading `tests/shared/test_runtime_tool_registry.py`
in full: every existing `apply_policy()` test constructs its `RuntimeTool` fixtures
with `enabled_for_llm=True` (so `llm_visibility_base` defaults to `True` too) — no
test exercises the `llm_visibility_base=False` path at all, so the invariant the Issue
cares about has no regression coverage. Separately, `apply_policy()` never logs
anything when it suppresses a would-be-enabled tool, and REQ-001's governance entry
was never updated to reflect the 2026-09-17 fix.

## Reason for change
Leaving REQ-001 `open` after the underlying enforcement was already implemented
creates governance drift: the tracked risk (a hidden tool becoming visible again)
looks unaddressed to anyone reading `docs/00_governance_03_issue-and-uncertainty-management.md`,
and the invariant has no test pinning it in place against a future refactor of
`apply_policy()`.

## Implementation intent
Add a narrow, additive test plus one diagnostic log line to the already-correct
`apply_policy()` logic, then close REQ-001's governance entry with a citation to the
new evidence — no behavior change to the enforcement itself, since it is already
correct.

## Design
The core design decision — enforcing `llm_visibility_base` as an immutable AND-gate
over `enabled_for_llm` inside `apply_policy()` — was already made and implemented in
commit `520c9b39f9`; this Plan does not revisit that design, only adds the missing
observability (warning log) and regression coverage around it, and corrects the
governance record.

`scripts/shared/config_loader.py` is explicitly excluded as a target file: reading it
(Step 3) found it contains no `RuntimeToolRegistry`/`apply_policy` reference at all —
the Issue's claim that it is "the config reload entry point" does not match current
source. The actual call site, `scripts/agent/services/config_reload.py`'s
`_sync_services()`, calls `runtime_tools.apply_policy(tier_map=..., allowed_tools=...)`
unconditionally on every reload when a registry is present — it does not need any
change, since the enforcement lives entirely inside `apply_policy()` itself and this
call site already passes through to it correctly (confirmed by the existing
`TestRuntimeToolPolicyReapplication` test class).

The warning log is placed inside `apply_policy()` (not at the `_sync_services()` call
site) because that is the single place where the "would this tool have been enabled by
`allowed_tools` alone" computation already exists (`resolved_llm_visibility_base and
(...)` — the log only needs to check the case where the second operand is `True` but
`resolved_llm_visibility_base` is `False`).

## Risks
- **Risk**: The new warning log could be noisy in production if many tools are
  legitimately hidden and `allowed_tools` is broad → **Mitigation**: the log only
  fires when a hidden tool's name specifically appears in `allowed_tools` (an
  operator's config explicitly, if mistakenly, trying to re-enable it) — not on every
  reload for every hidden tool, keeping the signal rare and actionable.
- **Risk**: Marking REQ-001 `resolved` could be seen as retroactively validating an
  unreviewed 2026-09-17 change → **Mitigation**: the Resolution note will cite the
  exact commit SHA and the new tests, so the claim is independently checkable, not an
  assertion of trust.
