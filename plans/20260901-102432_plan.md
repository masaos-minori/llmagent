## Goal
- Make `McpServerConfig`'s required/non-required classification environment-independent (remove the `security_profile`-conditioned branch in `McpToolDiscoveryService.discover_all()`), replacing `adr004_01`'s now-obsolete unconditional-Fail-Fast instruction, while deferring `failure_policy`'s fate to an explicit architecture-owner sign-off and leaving per-component classification values untouched pending the companion criticality-Specification issue.

## Priority
High

## Scope
- **In-Scope**:
  - Collapse `McpServerConfig.required_in_production` / `required_in_local` into a single environment-independent field (`required: bool`, default `True`), preserving the current effective classification for every configured server.
  - Update `McpToolDiscoveryService.discover_all()`'s unreachable-server classification branch to read the single field directly, removing its `security_profile == PRODUCTION` read for this purpose.
  - Update existing unit tests that construct `McpServerConfig` with `required_in_local=...`; add tests proving classification is identical regardless of `security_profile`.
  - Mark `issues/20260831-173019_adr004_01_mcp_config_failure_model_alignment.md` superseded and archive it once this Plan's implementation lands.
  - Update ADR-004's Known Deviations entry `ADR-004-D1-profile-config-model-still-present` once implementation lands.
  - Gate the `failure_policy` (`FailurePolicy` enum) fate decision behind an explicit architecture-owner sign-off; document the sign-off channel.
- **Out-of-Scope**:
  - Defining which specific MCP servers are classified required vs. non-required (tracked in `issues/20260831-192510_adr004_06_missing_component_criticality_specification.md`, per this issue's own Dependencies).
  - Removing, renaming, or otherwise changing `FailurePolicy` / `failure_policy` values — deferred to the sign-off-gated follow-up (see Requirements REQ-003).
  - `McpToolDiscoveryService._is_fatal_severity()`'s unrelated use of `security_profile` for drift/tool-definition finding severity — this is a different mechanism from the required/non-required classification branch and is not named in the source Issue's Target Files or Areas.
  - Redesigning MCP server startup retry/backoff behavior.
  - Any `config/agent.toml` edits — repository evidence confirms no server entry currently overrides `required_in_local`, `required_in_production`, or `failure_policy` (all use defaults), so the field collapse requires no config-file change.

## Background
ADR-004 (`docs/adr/ADR-004-environment-failure-handling-policy.md`) has been fully rewritten twice in the same working session. `issues/20260831-173019_adr004_01_mcp_config_failure_model_alignment.md` was written against the first revision ("Production is the only mode; no required/optional distinction; every configured component's unavailability is Fail-Fast"). The current, second revision reverses this: components ARE classified required/non-required (Decision Group 3), a non-required component's availability failure is permitted to disable it and continue with partial availability (Decision Group 7, Group 18), while safety/integrity failures remain Fail-Fast/Fail-Closed regardless of classification (Decision Group 6, Group 19). Implementing `adr004_01` as written would now move the codebase away from the current approved architecture.

## Problem
(Evidence: Explicit in code, confirmed by direct read of `scripts/agent/services/mcp_tool_discovery.py`) `McpToolDiscoveryService.discover_all()` selects between `cfg.required_in_production` and `cfg.required_in_local` based on `self._ctx.cfg.mcp.security_profile == SecurityProfile.PRODUCTION`:
```
is_prod = self._ctx.cfg.mcp.security_profile == SecurityProfile.PRODUCTION
is_required = cfg.required_in_production if is_prod else cfg.required_in_local
```
This directly contradicts current ADR-004 Decision Group 1 (environment names must not change classification outcomes) and Decision Group 3 item 13 ("承認済みの分類は... 環境非依存の性質である" — classification must be an environment-independent property), even though the current *effective* result is identical across profiles today (Evidence: confirmed via `config/agent.toml` inspection — no server entry sets `required_in_local`, `required_in_production`, or `failure_policy`; both required-fields default to `True` for every configured server, so `is_prod`/`is_required` currently resolve identically regardless of branch taken). ADR-004's own Known Deviations entry `ADR-004-D1-profile-config-model-still-present` records exactly this gap and recommends this alignment as a follow-up issue.

`adr004_01` instructs the opposite direction (remove the required/non-required distinction entirely, collapse to a single unconditional Fail-Fast) — Evidence: `issues/20260831-173019_adr004_01_mcp_config_failure_model_alignment.md`'s Implementation Intent ("keep a single required/enabled flag per server... whose unavailability always causes startup to abort") and Constraints ("Do not introduce a new required/optional distinction"), and its Summary/Background cite a now-nonexistent ADR-004 filename (`ADR-004-environment-profile-fail-fast-fail-open.md`), confirming it was written against a superseded revision.

## Reason for change
Leaving `adr004_01` open and actionable risks a future implementer executing it and creating a larger conformance gap against the current, approved ADR-004 (re-introducing an unconditional-Fail-Fast model the current ADR explicitly rejects in favor of required/non-required classification with partial availability for non-required components).

## Implementation intent
1. Collapse the two environment-branched booleans into one environment-independent field on `McpServerConfig`, keeping the current effective value (`True`) as the default so no configured server's observed behavior changes.
2. Update the one classification call site (`McpToolDiscoveryService.discover_all()`) to read the new field directly, with no `security_profile` read in that branch.
3. Leave `FailurePolicy`/`failure_policy` untouched in this Plan's implementation steps — its fate (remove, collapse to a single value, or keep as a per-server override) requires an explicit architecture-owner decision per `rules/coding.md` "Explicit sign-off gates", since it is an independently schedulable sub-task the source Issue itself declines to resolve ("Confirm this with the architecture owner rather than assuming").
4. Do not invent or change any specific server's required/non-required classification value — every server currently defaults to `required=True`, and assigning non-required status to any specific server depends on the not-yet-existing per-component criticality Specification (`issues/20260831-192510_adr004_06_missing_component_criticality_specification.md`).
5. Once the field collapse lands, update ADR-004's Known Deviations entry and mark `adr004_01` superseded.

## Design
The collapse follows the narrowest change that satisfies ADR-004 Decision Group 1/3 without pre-empting the still-open `failure_policy` and per-component-classification questions:
- `McpServerConfig` keeps exactly one boolean classification field (`required`), replacing two profile-scoped booleans that were read via an environment branch. Because every currently configured server defaults both old fields to `True` (Evidence: `config/agent.toml` grep, zero overrides), the new field's default (`True`) is a behavior-preserving rename, not a reclassification — this Plan does not decide any specific server's non-required status, consistent with the Issue's own Out of Scope and its dependency on `issues/20260831-192510_adr004_06_missing_component_criticality_specification.md`.
- `McpToolDiscoveryService.discover_all()`'s classification branch becomes a direct field read (`cfg.required`) with no `security_profile` involved, closing the specific `ADR-004-D1` gap. `_is_fatal_severity()`'s separate, pre-existing use of `security_profile` (for drift/tool-definition finding severity, not required/non-required classification) is a distinct mechanism the source Issue does not name as a target and is left untouched — flagged in Scope/Out-of-Scope to prevent scope creep during implementation.
- `FailurePolicy`/`failure_policy` is left structurally and behaviorally unchanged. The Issue's own Implementation Intent #3 explicitly asks that its fate be confirmed with the architecture owner rather than assumed; `rules/coding.md`'s "Explicit sign-off gates" section directly covers this pattern (an independently schedulable sub-task gated behind sign-off) and is used here rather than inventing a resolution.
- Pre-existing, unrelated condition noted for completeness: `PYTHONPATH=scripts uv run lint-imports` currently reports one broken contract (`shared.production_config_validator -> agent.tool_policy`), in a file this Plan does not touch. This is out of scope and not introduced by this change; it is recorded here so the post-implementation validation run is not misread as a regression caused by this Plan.
