# Plan: Make RuntimeToolRegistry the Sole Scheduling Authority and Resolve Call-Level Resource Scopes

## Goal

Replace the codebase's four disagreeing sources of tool write/serial/scope metadata
(name-keyed `_build_tool_meta()`, static `is_side_effect()`/`SHELL_TOOLS`, the unused
`RuntimeToolRegistry.tool_spec_for_call()`, and the singular `resource_scope: str` field)
with one fail-closed, per-call metadata flow — every MCP tool explicitly declares
`is_write`/`requires_serial`/`resource_scope_kind`/`resource_scope_keys`, a validator
rejects incomplete declarations, and `scripts/agent/tool_scheduler.py::build_execution_groups()`
schedules using call-id-keyed `ToolSpec`s with resolved multi-resource scopes instead of
tool-name-keyed metadata with an unsafe silent default.

## Assumptions

- `ctx.services_required.runtime_tools` (a `RuntimeToolRegistry`, wired in
  `scripts/agent/startup.py:367`) is populated before any tool call reaches
  `execute_all_tool_calls()`/`_execute_with_dag()` — confirmed by reading
  `scripts/agent/startup.py` and `scripts/agent/tool_runner.py:141`, where
  `_validate_tool_args()` already depends on it being present. Falsifiable: if a call
  path exists where tool execution runs before discovery completes, the new fail-closed
  scheduler would incorrectly reject legitimate calls.
- No MCP server other than the ten listed in Scope exports tools requiring scheduling
  metadata — confirmed via `rg -l "^TOOL_LIST" scripts/mcp_servers/` (10 files) and
  `ls scripts/mcp_servers/` (no server directory omitted).
- SQLite-backed RAG/MDQ mutation concurrency is out of scope to verify here; the fixed
  store-level scope (`rag_store:default` / `mdq_store:default`) is a conservative
  placeholder, matching the requirement's own "favor conservative correctness" directive
  — not a claim that finer-grained RAG/MDQ concurrency has been analyzed.
- `resource_scope_kind`/`resource_scope_keys` namespacing (e.g. every filesystem scope
  string is prefixed `"filesystem:"`) is sufficient to guarantee two different kinds
  never accidentally compare equal or overlap — falsifiable by a unit test constructing
  colliding strings across kinds.

## Design

**Layering.** The new `scripts/shared/resource_scope.py` module sits in `shared/`, which
`.importlinter`'s `shared-is-leaf` contract forbids from importing `agent`, `mcp_servers`,
`rag`, or `db` (confirmed: `.importlinter` §`shared-is-leaf`). `resolve_resource_scopes()`
must therefore take only `RuntimeTool` (already in `shared/`) and a plain `Mapping[str, Any]`
of call arguments — no `AgentContext`, no config dataclasses. This mirrors the existing
precedent in `runtime_tool_registry.py`'s module docstring (`classify_operation_type()`
returns a plain string instead of importing `agent.tool_enums.OperationType` for the same
reason).

**Scope-string shape.** Every resolved scope is a kind-prefixed string:
`f"{resource_scope_kind}:{normalized_value}"` (e.g. `"filesystem:/data/a.txt"`,
`"git_repo:/home/x/repo"`, `"github_repo:org/name"`, `"cicd_workflow:org/repo:ci.yml:main"`,
`"rag_store:default"`, `"mdq_store:default"`, `"process:global"`). This namespacing
resolves UNK-05: two different kinds can never accidentally compare equal, so the conflict
predicate only needs to special-case the `"filesystem:"` prefix for ancestor/descendant
overlap (via `PurePosixPath.is_relative_to()` on the post-`":"` remainder) — all other
kinds use plain string equality. A known-write tool with no resolvable scope (e.g. its
declared keys are absent from `args`) falls back to `("global:write",)`, never the tool
name, per the requirement's explicit acceptance criterion.

**Per-call flow.** `execute_all_tool_calls()` → `_execute_with_dag()` currently rebuilds a
name-keyed `dict[str, ToolSpec]` once per batch via `_build_tool_meta(ctx.cfg.tool.tool_definitions)`
(tool_runner.py:60-79), which `build_execution_groups()` (tool_scheduler.py:70-189) looks up
by `tc["function"]["name"]`, silently defaulting to an all-`False` synthetic `ToolSpec` on a
miss (tool_scheduler.py:91-96, via `.get(name)` with no error path). The new flow builds, for
each approved call, `ctx.services_required.runtime_tools.tool_spec_for_call(tc["id"], name, args)`
(already implemented, currently unused, at `runtime_tool_registry.py:156-164`) into a
call-id-keyed `dict[str, ToolSpec]`; a call whose tool name has no registry entry raises
`KeyError` from `.get()` today — the scheduler must propagate this as a scheduling failure
rather than swallow it, satisfying the "raise, don't default" acceptance criterion.

**Grouping algorithm.** `build_execution_groups()`'s current 4-bucket approach (serial
barrier / same-exact-scope resource groups / write-first / parallel) assumed one scope
string per tool *name*. With per-call, possibly-multi-valued `resource_scopes` tuples, exact
dict-keying by scope string is no longer sufficient (e.g. `move_file`'s two scopes must each
independently conflict with unrelated calls, and a directory read must conflict with a
descendant-path write despite unequal scope strings). The rework builds a conflict graph over
the write-relevant calls in a batch — an edge exists between two calls when at least one is
`is_write=True` and any pair of their `resource_scopes` overlaps (exact match, or
ancestor/descendant for `"filesystem:"` scopes) — and takes connected components as the
serialized resource groups, preserving the existing `requires_serial` global-barrier and
write-tools-without-scope write-first buckets unchanged. Read/read pairs are never edges
(UNK-05), so read-only calls stay in the trailing parallel group exactly as today.

**`_execute_standard()` (non-DAG path).** Resolves UNK-02: its `has_side_effect` detection
switches from the static `is_side_effect(name)` to
`(ctx.services_required.runtime_tools.get(name).is_write if registered else True)` — the
`True` fallback for an unregistered tool preserves today's conservative behavior (an unknown
tool name is currently *also* treated as side-effecting via the same frozenset-membership
default-false-means-"not found"-means-not-flagged logic, so this is at least as conservative,
not less). This still leaves `_execute_standard`'s batch-level downgrade mechanism distinct
from `ToolSpec.requires_serial`'s per-call DAG barrier, per `tool_scheduler.py`'s module
docstring.

**Discovery-time enforcement.** `McpToolDiscoveryService._validate_and_normalize_entry()`
(mcp_tool_discovery.py:204-259) currently type-checks `is_write`/`requires_serial`/
`resource_scope` only `if field_name in entry` — absence is not an error. It becomes a hard
requirement check (missing → per-tool WARNING/FATAL finding per the module's existing
severity scheme) plus `resource_scope_kind`/`resource_scope_keys` validation (keys must
exist in the tool's own `inputSchema.properties`, reusing the same entry dict already
fetched — no second HTTP round-trip). `_dedupe_and_build()` (line ~300) stops passing
`entry.get("is_write")` through to `build_runtime_tool()`'s silent `_or_default`; an
incomplete tool is excluded from the built registry, mirroring the existing duplicate-tool
exclusion pattern one paragraph above it in the same method.

## Risks

- **Risk**: The multi-resource-scope conflict-detection rework of `build_execution_groups()`
  (already CC=D/23 per `radon cc scripts/agent/tool_scheduler.py -s`, before adding
  connected-component logic) is a genuine algorithmic redesign, not a mechanical rename —
  raising correctness risk of silently over- or under-serializing tool calls in production.
  Likelihood: high. → **Mitigation**: port every existing scenario from the three
  `tests/agent/test_tool_scheduler*.py` files (390+175+164 lines) as regression fixtures
  before adding the new multi-scope cases; do not merge until all pre-existing scheduler
  tests pass with equivalent intent under the new call-id keying.
- **Risk**: Renaming `ToolSpec.resource_scope`→`resource_scopes` and
  `RuntimeTool.resource_scope`→`resource_scope_kind`/`resource_scope_keys` touches 24
  files repo-wide that reference `resource_scope` in some form (11 importers of
  `runtime_tool`, 7 of `tool_spec`, 11 of `runtime_tool_registry`, plus 6 further test
  files found by `rg`), risking a half-migrated merge that breaks unrelated tests.
  Likelihood: medium. → **Mitigation**: perform the rename as one atomic implementation
  step across `shared/` + `runtime_tool_registry.py` + all direct consumers (not
  incrementally across separate commits left half-done); re-run
  `rg "\.resource_scope\b" scripts/ tests/` after the rename to confirm zero remaining
  references to the removed singular field before running the suite.
- **Risk**: Fail-closed rejection of schema-2.0-incomplete tools in
  `McpToolDiscoveryService` could silently drop a tool from the LLM-visible surface in
  production if any single server's `TOOL_LIST` update (10 files, Phase 2) has a typo or
  omission, with no existing test asserting full tool-name coverage. Likelihood: medium.
  → **Mitigation**: add `tests/mcp_servers/test_tool_schema_contract.py` asserting every
  name in `shared.tool_constants.get_all_mcp_tool_names()` is present and schema-2.0-valid
  in its owning server's `TOOL_LIST`, run before merge; treat any FATAL discovery finding
  under the `local` security profile as merge-blocking during manual verification.
- **Risk**: The two line-citation ambiguities in the requirement (UNK-02: `_execute_standard`'s
  `is_side_effect()` check; UNK-03: `_validate_tool_args`'s `tool_definitions` fallback loop)
  could be implemented more broadly than intended if a future contributor follows the literal
  line list in instruction #10 instead of this plan's Design resolution. Likelihood: medium.
  → **Mitigation**: both resolutions are recorded explicitly in this plan's Unknowns/Design
  sections with the reasoning; implementers should re-read UNK-02/UNK-03 before touching
  `_execute_standard()` or `_validate_tool_args()`.
- **Risk**: `scripts/mcp_servers/browser/*.py`, named in the requirement's target-file list,
  does not exist as a TOOL_LIST-bearing module (already resolved — UNK-01). Likelihood: low
  (already mitigated, listed for completeness). → **Mitigation**: none needed; `web_search_tools.py`
  is the correct target, already reflected in Scope and Affected areas above.
- **Risk**: This repository's `git log --format='%an'` shows all commits to every affected
  file attributed to name-variants of a single author (`Masao SUGIMOTO`/`Masao Sugimoto`/
  `Sugimoto Masao`/`sugimoma-c`) — an effective bus factor of 1 across the entire scheduling
  stack. Likelihood: low impact on this specific plan (pre-existing project characteristic,
  not introduced by this change). → **Mitigation**: none required for this plan; noted for
  awareness only, not filed as a separate issue since it is not a consequence of this change.
