## Goal
- `/reload` が `LLMConfig`/`RAGConfig`/`ToolConfig` の各フィールドを更新する際、起動時(`__post_init__`)と同じバリデータを再実行し、範囲外の値を拒否する。

## Priority
High

## Scope
- **In-Scope**:

- **Out-of-Scope**:

  - 新規バリデーションルールの追加

## Background
`scripts/agent/config_dataclasses.py` は複数のconfig dataclassに `__post_init__` を定義しており、`config_validators.py` の `validate_*` 関数を呼び出している。`ConfigReloadService` は既に構築済みのdataclassインスタンスのフィールドを直接 `setattr` で変更するため、`__post_init__` もバリデータも再実行されない。

## Problem
現在のソースを再確認した結果:
- `cfg.llm`/`cfg.rag`/`cfg.tool` への `setattr` 呼び出しは、`_apply_llm_context_params`・`_apply_tool_params`・`_apply_rag_params`・`_apply_llm_retry_params`・`_apply_llm_prompt_params`・`_apply_sse_reload_params` の複数の関数にまたがって分散している(grep で26箇所確認)。
- `LLMConfig.__post_init__`(line 139-149)、`RAGConfig.__post_init__`(line 165-169)、`ToolConfig.__post_init__`(line 230-237)は、いずれも `validate_*` 関数の呼び出しのみで構成されており、キャッシュ生成・リソースオープン・可変共有状態の初期化などの副作用を一切持たないことを確認した。これにより `dataclasses.replace()` によるこれら3サブconfigの再構築は安全であると判断できる(issue が Option A/B の判断を Plan 生成時に委ねていた Unresolved Question はこれで解決)。
- `validate_*` 関数はすべて `ValueError` を送出する(`config_validators.py` 内で確認)。`ConfigReloadValidationError`(`scripts/agent/services/exceptions.py:17`、`ValueError` のサブクラス)は既に `config_reload.py`・`config_builders.py`・`typed_validators.py` で使われており、`config_builders.py:374` には「`ConfigReloadValidationError` へ変換してリロード経路のエラーハンドリングに使う」という既存パターンが存在する。

## Reason for change
起動時に拒否される値が `/reload` では黙って受け入れられてしまう、起動時とリロード時の不変条件の不一致を解消する。

## Implementation intent
`_apply_llm_context_params`・`_apply_llm_retry_params`・`_apply_llm_prompt_params`・`_apply_sse_reload_params`(`cfg.llm` を変更する箇所)、`_apply_tool_params`・`_apply_llm_prompt_params`(`cfg.tool` を変更する箇所)、`_apply_rag_params`・`_apply_llm_prompt_params`(`cfg.rag` を変更する箇所)を、直接 `setattr` する代わりに変更差分を `dict[str, Any]` に集約するよう変更する。`_apply_rag_tool_params()`(現在これらのヘルパーを呼び出している親関数)で、llm/rag/tool それぞれについて集約した辞書を使い `dataclasses.replace(cfg.llm, **llm_changes)` 等を1回ずつ呼び出し、`ctx.cfg.llm` 等を新しいインスタンスに差し替える。`ValueError`(`__post_init__` 内のバリデータ由来)を捕捉し `ConfigReloadValidationError` として再送出し、失敗時は `ctx.cfg` を変更前の状態のまま保持する(部分適用を防ぐため、辞書への集約は行うが実際の差し替えは全フィールド収集後に1回で行う)。

## Design
各 `_apply_*` ヘルパーは、現在の `lambda v: setattr(cfg.llm, "field", v)` パターンを `lambda v: changes["field"] = v` 相当(辞書への書き込み)に置き換える。ヘルパーは呼び出し元(`_apply_rag_tool_params`)と辞書を共有するか、辞書を返す形にリファクタリングする(実装時にどちらが既存コード構造に自然に馴染むか判断する)。`_apply_rag_tool_params()` の末尾:
```
if llm_changes:
    try:
        cfg.llm = dataclasses.replace(cfg.llm, **llm_changes)
    except ValueError as e:
        raise ConfigReloadValidationError(str(e)) from e
```
を llm/tool/rag それぞれについて行う。3サブconfigの検証順序(どれを先に検証するか)は、既存の呼び出し順序(llm context → tool → rag → llm retry → llm prompt → sse)から自然に導かれる完了順とし、恣意的な順序変更はしない。
