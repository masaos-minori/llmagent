## Goal
- Extract the config-resolution logic currently inline in `RagPipeline.__init__`
  (`scripts/rag/pipeline.py`) into a module-level `resolve_rag_config()` function,
  remove the `_ModuleConfig` class-level singleton, and remove the redundant
  `cast(RagConfig, self._cfg)` — with no change to `RagPipeline`'s public
  constructor signature or runtime config-resolution behavior.

## Background
`RagPipeline.__init__` (`scripts/rag/pipeline.py:91`-`211`, confirmed by Read — 121
lines) performs 10 distinct responsibilities: HTTP client setup, status-callback
wiring, per-run state field initialization, config resolution from three input
types, `SemanticCache` instantiation, `RagLLM` instantiation, embed-URL
construction, DB-path field storage, `AugmentRefiner` instantiation, and startup
logging. `radon cc scripts/rag/pipeline.py -s` (run during this Plan's analysis)
reports `RagPipeline.__init__` at complexity grade C (14), the second-highest in
the file after `augment` (C, 19).

The `_ModuleConfig` class (`scripts/rag/pipeline.py:63`-`77`, confirmed by Read)
implements a class-level singleton cache for `ConfigLoader().load_all()`,
coupling the pipeline to a global config source with no injection point for
tests.

`RagConfig` is a `Protocol` at `scripts/shared/types.py:75` (confirmed by Read).
`RagConfigImpl` (`scripts/rag/models_config.py:13`, confirmed by Read) is a
frozen dataclass satisfying it. `RagConfigValidator` (`scripts/shared/config_validator.py:23`,
confirmed by Read) validates the resolved raw config dict.

## Problem
Config-resolution logic (`scripts/rag/pipeline.py:117`-`178`, confirmed by
Read) handles three input types (`RagConfigImpl`, `dict`, object with
`__dict__`), fills 14 missing fields from hardcoded defaults, validates via
`RagConfigValidator`, and logs warnings/errors — all inline inside the
constructor. This makes the constructor hard to test, understand, and
maintain in isolation from `RagPipeline`'s other setup responsibilities.

Line 182 contains `cast(RagConfig, self._cfg)` passed into `RagLLM(...)`.
Confirmed by Read: `self._cfg` is declared `RagConfig` at line 118 and is
assigned either directly (the `RagConfigImpl` branch, no cast) or via
`cast(RagConfig, RagConfigImpl(**_raw_cfg))` at line 178 (the fallback
branch) — by the time line 182 runs, `self._cfg`'s static type is already
`RagConfig` in both branches, so the second cast at line 182 is redundant.

## Reason for change
- Maintainability: a single change to config handling currently requires
  reading the entire 126-line constructor.
- Testability: config resolution cannot be unit-tested or mocked without
  instantiating the full `RagPipeline`.
- The `_ModuleConfig` singleton blocks dependency injection and hides the
  pipeline's config source.
- The redundant cast at line 188 signals lingering type uncertainty in the
  original design.

## Implementation intent
Create a module-level function `resolve_rag_config(cfg, *, module_cfg=None,
config_loader=None)` in `scripts/rag/pipeline.py` that accepts the same raw
inputs `RagPipeline.__init__` currently handles and returns a validated
`RagConfigImpl`. It preserves the exact current priority order — explicit
`cfg` > `module_cfg` > `config_loader()` (defaulting to
`ConfigLoader().load_all()` when `config_loader` is `None`, matching
`_ModuleConfig.get()`'s current fallback, including its
`FileNotFoundError`/`ValueError` → `{}` catch) — and moves the 14-field
defaulting, `RagConfigValidator` call, and warning/error logging into this
function. `RagPipeline.__init__` is reduced to
`self._cfg = resolve_rag_config(cfg, module_cfg=module_cfg)` and otherwise
only wires the resolved config into its collaborators (`SemanticCache`,
`RagLLM`, `AugmentRefiner`). `_ModuleConfig` is removed entirely; its role is
replaced by `resolve_rag_config`'s injectable `config_loader` parameter.

This resolves both of the Issue's Unresolved Questions from the Implementation
Intent's own explicit function signature: `resolve_rag_config` returns
`RagConfigImpl` directly (not a dict), and validation/warning/error logging
moves with the resolution logic into `resolve_rag_config`, since
`RagPipeline.__init__` is stated to "only wire up the resolved config" — see
Assumptions.

## Design
- `RagPipeline.__init__` currently spans `scripts/rag/pipeline.py:91`-`211`
  (121 lines) and mixes 10 responsibilities; `radon cc` grades it C (14)
  complexity, second only to `augment` (C, 19) in this file.
- Extract config resolution into a new module-level function
  `resolve_rag_config(cfg, *, module_cfg=None, config_loader=None) ->
  RagConfigImpl`, preserving:
  - Priority order: `cfg` (if already `RagConfigImpl`, used directly) > `cfg`
    (if `dict`) > `cfg` (if object with `__dict__`) > `module_cfg` > 
    `config_loader()` (defaults to `ConfigLoader().load_all()` when
    `config_loader` is `None`, matching `_ModuleConfig.get()`'s current
    fallback).
  - The 14-field default-filling for any non-`RagConfigImpl` input path
    (unchanged field names/values, per Issue Constraints).
  - The `RagConfigValidator().validate()` call and its
    warning/error logging, plus the `ValueError` raised on validation
    failure.
- `RagPipeline.__init__` reduces to `self._cfg = resolve_rag_config(cfg,
  module_cfg=module_cfg)`, then only wires `self._cfg` into `SemanticCache`,
  `RagLLM`, `AugmentRefiner`, and the startup log lines — unchanged from
  today except for the deleted redundant cast.
- `_ModuleConfig` (lines 64-78) is deleted; its sole caller
  (`RagPipeline.__init__`'s fallback branch) is replaced by
  `resolve_rag_config`'s injectable `config_loader` parameter, which defaults
  to a fresh `ConfigLoader().load_all()` call (same production behavior,
  now injectable for tests).
- `cast(RagConfig, self._cfg)` at line 182 is removed: `self._cfg`'s
  declared type is already `RagConfig` (line 118 annotation), satisfied by
  either the direct `RagConfigImpl` branch or `resolve_rag_config`'s return
  type — no cast is needed at the `RagLLM(...)` call site.
- Import-linter contract (`.importlinter`, confirmed: `rag → db, shared`,
  `rag` forbidden from importing `agent`/`mcp_servers`) is unaffected:
  `resolve_rag_config` uses only symbols already imported into
  `scripts/rag/pipeline.py` (`ConfigLoader`, `RagConfigValidator`,
  `RagConfigImpl`) and introduces no new cross-layer import.
- Of the 4 test files patching `rag.pipeline._ModuleConfig.get`, 3
  (`test_stage_observability.py`, `test_rag_pipeline.py` ×2 call sites,
  `test_rag_quality_regression.py` ×3 call sites) construct `cfg` as a
  `SimpleNamespace` (which has `__dict__`), so the current code never
  actually reaches the `_ModuleConfig.get()` branch in these tests at
  runtime — the patch is defensive/inert there, and removing the
  now-invalid `with patch(...)` wrapper (dedenting the `RagPipeline(...)`
  call) is sufficient. `tests/agent/test_rag_get_cfg.py`'s
  `test_get_cfg_error_path` is the one test that directly and meaningfully
  exercises the `ConfigLoader`-failure fallback; it is rewritten to call
  `resolve_rag_config` with a failing `config_loader` and assert the same
  `{}`-then-defaults behavior.
