## Goal
- Introduce a stable, retry-invariant Tool Call idempotency key alongside the
  existing per-HTTP-request trace ID, add a duplicate-check capability at the
  MCP dispatch choke point (`dispatch_tool()`) for side-effecting tools, and
  record the key plus a WorkflowEngine task linkage in the audit log — as the
  first, core increment of the design review gap this Issue tracks. Wiring the
  new key into each individual MCP server route handler is scoped out (see
  Risks) as a necessarily separate follow-up, once each server's own
  request-context extraction pattern is confirmed file-by-file.

## Priority
Medium

## Scope
- **In-Scope**:
  - Deriving a stable idempotency key at the agent layer
    (`scripts/agent/tool_runner.py`), distinct from the existing per-HTTP-request
    `uuid.uuid4()` trace ID.
  - Extending `ToolExecEvent` (`scripts/agent/shared/models.py`) and
    `audit_tool_exec()` (`scripts/agent/tool_audit.py`) to record the new key
    and a WorkflowEngine task-level linkage field.
  - Adding an opt-in duplicate-check capability to `dispatch_tool()`
    (`scripts/mcp_servers/dispatch.py`), scoped to tool names classified
    side-effecting via `shared/tool_constants.py`'s existing write/dangerous
    tool-name sets (no new agent-layer dependency in `mcp_servers`).
  - Extending `extract_request_context()` (`scripts/mcp_servers/server.py`) to
    also extract the new idempotency-key header, for callers that adopt it.
- **Out-of-Scope**:
  - Wiring the extracted idempotency-key header into each of the ten
    individual MCP server route handlers that call `dispatch_tool()` directly
    (`scripts/mcp_servers/{cicd/cicd_server,git/git_server,shell/shell_server,
    github/github_server,mdq/mdq_server,rag_pipeline/rag_pipeline_server,
    web_search/formatters,file/read_server,file/write_server,
    file/delete_server}.py`) — see Risks; tracked as separate follow-up work.
  - Stage-level idempotency (`begin_stage_if_new()`) — already implemented,
    documented as ADR-001 INV-08/INV-026.
  - Redesigning the retry-ownership model across
    WorkflowEngine/ToolLoopGuard/LLM transport layers — tracked by a related
    issue from the same design review.
  - The Workflow/Agent/MCP timeout hierarchy — tracked by a related issue from
    the same design review.
  - Exposing WorkflowEngine's true per-attempt identifier
    (`state_store.py`'s `attempts.attempt_id`) on `AgentContext` — not
    currently exposed there (confirmed: `scripts/agent/context.py` has no
    `attempt_id` field); this Plan links to `ctx.workflow.current_task_id`
    instead (see Design and UNK-02).

## Background
This Issue follows a design review (memo2.md) covering Agent/Workflow design
questions, converging two independent investigations (Tool Call ID, and
duplicate-execution prevention) on the same gap. Stage-level idempotency is a
related but distinct, already-implemented concern
(`begin_stage_if_new()`, ADR-001 INV-08/INV-026) and required no new issue.

## Problem
Adversarial verification confirmed every factual claim in the Issue against
current source — no stale claim found (unlike this Plan's companion Issue,
`issues/done/20260914-121616_...`, whose central claim had gone stale):
- `scripts/mcp_servers/server.py`'s `_auth_middleware` (line 118-120) generates
  a fresh `uuid.uuid4()` per HTTP request unconditionally, including retries.
- `scripts/agent/tool_runner.py`'s `execute_one_tool_call()` (line 90, 113-115)
  reads `result.request_id` and passes it to `audit_tool_exec()` purely for
  audit-trail recording.
- `scripts/agent/tool_audit.py`'s `audit_tool_exec()` (line 161-199) sets
  `ToolExecEvent.task_id = ctx.turn.current_turn_id` (a turn-level identifier)
  and `ToolExecEvent.workflow_id = ctx.workflow.workflow_id` (a
  whole-workflow identifier) — neither is WorkflowEngine's own
  `TaskRecord.task_id`/`attempts.attempt_id` identifier space
  (`scripts/agent/workflow/state_store.py`, `attempts` table).
- No dispatch-layer or MCP-server-layer code checks an incoming request
  against previously-processed requests: `grep -n
  "duplicate\|idempot" scripts/mcp_servers/dispatch.py scripts/mcp_servers/server.py`
  returns no matches.

Path B architecture/dependency analysis (this Plan's own investigation, not in
the Issue) surfaced two constraints the Issue's Implementation Intent did not
account for:
1. **Import-layer boundary**: `.importlinter`'s `mcp_servers-no-agent` contract
   (confirmed `KEPT`/clean via `lint-imports`) forbids `dispatch.py`/`server.py`
   from importing `agent.*` types (e.g. `WorkflowEngine`, `AgentContext`). The
   idempotency key and any side-effecting-tool classification used inside
   `mcp_servers` must therefore come from data already available in the
   `shared`/`mcp_servers` layers, not by importing agent-layer modules.
   `shared/tool_constants.py`'s `WRITE_TOOLS`/`DELETE_TOOLS`/`GIT_WRITE_TOOLS`/
   `RAG_WRITE_TOOLS`/`CICD_WRITE_TOOLS`/`GITHUB_WRITE_TOOLS`/
   `GITHUB_DANGEROUS_TOOLS`/`SHELL_TOOLS` sets are importable by `mcp_servers`
   (confirmed precedent: `scripts/mcp_servers/git/git_server.py` and
   `git_service.py` already import `shared.tool_constants`), so `dispatch_tool()`
   can self-classify a tool name as side-effecting without any agent-layer
   dependency or per-caller flag.
2. **Blast radius of `dispatch_tool()`**: it is the single choke point called
   by ten distinct MCP server route-handler files (confirmed via
   `grep -rl "dispatch_tool(" scripts/mcp_servers/`), each with its own,
   inconsistent request-context extraction: six
   (`cicd_server.py`, `git_server.py`, `shell_server.py`, `github_server.py`,
   `web_search_server.py`, `mdq_server.py`) call the shared
   `extract_request_context()` helper; at least one confirmed exception
   (`scripts/mcp_servers/file/write_server.py`) defines its own standalone
   FastAPI routes with no `request_id`/`extract_request_context` reference at
   all. Per `rules/toolchain.md`'s impact-radius-check guidance (>10 files),
   this blast radius is recorded here rather than discovered mid-implementation.

## Reason for change
An audit-only identifier gives the illusion of idempotent Tool Call execution
without the substance: nothing today lets the system say "this is the same
logical attempt, do not run it again." The existing stage-level idempotency
guard (`begin_stage_if_new()`) already established the pattern
(deterministic key + check-then-insert); this Plan brings the same pattern one
level down, at the Tool Call, within the constraints the architecture analysis
above surfaced.

## Implementation intent
Add the idempotency-key generation, audit-log linkage, and dispatch-layer
duplicate-check capability as one reviewable, self-contained increment,
opt-in at the `dispatch_tool()` boundary (a caller that does not yet supply a
key gets today's unguarded behavior — no regression). Defer wiring every
individual MCP server route handler to a follow-up plan, once each server's
own request-context pattern is confirmed (see Risks).

## Requirements
- `REQ-001`: In `scripts/agent/tool_runner.py`, derive a stable, retry-invariant
  idempotency key per Tool Call from `ctx.workflow.workflow_id`,
  `ctx.workflow.current_task_id`, `ctx.turn.current_turn_id`, and a per-call
  sequence discriminator (exact composition resolved at implementation time,
  see UNK-01); keep the existing per-HTTP-request trace ID unchanged; pass the
  new key into `audit_tool_exec()`.
- `REQ-002`: In `scripts/agent/shared/models.py`, add `ToolExecEvent.idempotency_key: str`
  and a WorkflowEngine task-linkage field populated from
  `ctx.workflow.current_task_id` (see UNK-02 for the attempt-level gap); in
  `scripts/agent/tool_audit.py`'s `audit_tool_exec()`, populate both new
  fields alongside the existing `mcp_request_id`.
- `REQ-003`: In `scripts/mcp_servers/dispatch.py`, add an optional
  `idempotency_key: str | None = None` parameter to `dispatch_tool()`; when
  provided and `name` is classified side-effecting via a helper built on
  `shared/tool_constants.py`'s write/dangerous tool-name sets, check an
  in-process cache keyed by `idempotency_key` before invoking the handler; on
  a cache hit, short-circuit and return the cached `DispatchResult`; on a
  cache miss, invoke normally and cache the result.
- `REQ-004`: In `scripts/mcp_servers/server.py`, extend
  `extract_request_context()` to also extract a new idempotency-key header,
  following the same pattern as the existing `request_id` extraction, for
  adoption by callers updated in the follow-up plan (Out-of-Scope).

## Acceptance criteria
- AC-1 (REQ-001): A Tool Call retried within the same logical attempt (same `workflow_id`/`current_task_id`/`current_turn_id`/sequence) produces the same idempotency key across the retry; a different Tool Call (different sequence, turn, task, or workflow) produces a different key.
- AC-2 (REQ-002): The audit log JSON for a `tool_exec` event contains the new `idempotency_key` field and the new task-linkage field, alongside the unchanged `mcp_request_id`.
- AC-3 (REQ-003, REQ-004): `dispatch_tool()` invoked twice with the same `idempotency_key` and a tool name in a side-effecting set returns the cached `DispatchResult` on the second call without re-invoking the handler; invoked with a tool name not in a side-effecting set, or with no key, behaves exactly as before (no regression).
- AC-4 (REQ-001, REQ-002): `uv run pytest tests/agent/test_tool_runner.py tests/agent/test_tool_audit.py tests/agent/test_audit_log_format.py -q` passes, including new tests for the new fields/key derivation.

## Risks
- **Risk**: Wiring the idempotency-key header into each of the 10 individual
  MCP server route handlers (Out-of-Scope) requires confirming each server's
  own request-context pattern first — six follow `extract_request_context()`,
  at least one (`file/write_server.py`) does not, and the remaining three
  (`file/read_server.py`, `file/delete_server.py`, `rag_pipeline_server.py`)
  were not yet confirmed either way during this Plan's Path B analysis →
  **Mitigation**: filed as a required follow-up (a new issue), scoped to a
  per-server investigation before any per-server wiring plan can freeze its
  own Implementation Target Files; this Plan's own Acceptance Criteria (AC-1
  through AC-5) do not depend on that follow-up landing.
- **Risk**: This Plan's `dispatch_tool()` duplicate-check is opt-in
  (fail-open when no `idempotency_key` is supplied) rather than fail-closed,
  so until the follow-up wiring plan lands, no MCP server actually exercises
  the new protection end-to-end, leaving the Issue's own Acceptance Criterion
  ("a retried side-effecting Tool Call... does not execute the underlying
  operation twice") only partially satisfied by this increment →
  **Mitigation**: explicit, stated trade-off (Implementation intent above) in
  favor of a small, independently-revertable first increment per
  `skills/issue-to-plan/SKILL.md`'s Incrementalism rule; full closure requires
  the follow-up plan.
- **Risk**: An in-process, non-persistent duplicate-check cache
  (`dispatch_tool()`, REQ-003) loses its dedup history on a server-process
  restart → **Mitigation**: accepted for this increment (Assumptions above);
  no Acceptance Criterion requires crash-durability; a DB-backed cache can be
  added later if operational data shows crash-induced duplicate side effects.
