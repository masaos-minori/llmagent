## Background
Discovered while investigating `build_agent_config()`'s exact input-shape contract during
`plans/done/20260908-221312_plan.md` (cfgval001)'s freeze-validation re-entry.
`ProductionConfigValidator` contains two separate implementations of "check for unknown
top-level config keys": `_check_unknown_top_level_keys()` (an instance method) and
`_check_unknown_production_keys()` + `_get_valid_production_keys()` (a static method plus
a module-level function). Only the second pair is wired into `validate()`.

## Problem
`_check_unknown_top_level_keys()` (`scripts/shared/production_config_validator.py:194-224`)
has zero callers anywhere in `scripts/` or `tests/` — confirmed via
`rg -n "_check_unknown_top_level_keys" scripts/ tests/`, which returns only its own
definition line. `validate()` (the sole call site of either check, at line 290) calls
`_check_unknown_production_keys()` exclusively. The two implementations also derive a
different "known fields" set, evidence they were never kept in sync: the dead method
additionally includes `AgentConfig`'s own dataclass field names (`llm`, `rag`, `tool`,
`memory`, `mcp`, `approval`, `obs`, `diagnostics`, `messages`,
`agent_memory_max_startup_snippets`) via `dataclasses.fields(AgentConfig)`, while the
active `_get_valid_production_keys()` instead hardcodes exactly two extra strings
(`"system_prompt_tool"`, `"security_profile"`) plus `"agent_memory_max_startup_snippets"`
individually.

## Reason for change
Dead code that closely resembles the live code path it duplicates is a confirmed source
of confused future edits and wasted investigation time (occurred in this session while
establishing `build_agent_config()`'s exact contract for cfgval001). Removing it
eliminates that risk and leaves a single, unambiguous implementation of the check.

## Implementation intent
Delete `_check_unknown_top_level_keys()` outright (not reconcile) — Design below records
the git-history and field-derivation-correctness investigation that resolves the issue's
own "predates or postdates" and "is its field derivation more correct" open questions in
favor of deletion, not replacement.

## Design
Investigation (Step 2/3, Path A direct verification) resolved both open questions the
issue raised:

1. **Predates or postdates?** `git log -S"_check_unknown_top_level_keys" --format="%H %ai %s" -- scripts/shared/production_config_validator.py`
   shows exactly one commit touching this string: `b4ff8fcc1` ("feat: REQ-004 unknown-key
   rejection, config isolation, resource shutdown coordinator", 2026-09-08 16:48:58). The
   active pair was introduced earlier the same day by `9a7cdb40e` ("REQ-004: Add
   _check_unknown_production_keys() method to ProductionConfigValidator", 2026-09-08
   11:15:51). `git merge-base --is-ancestor 9a7cdb40e b4ff8fcc1` confirms the active pair
   is an ancestor of the commit that added the dead method — i.e. the dead method
   **postdates** the active pair. `b4ff8fcc1`'s own commit message describes it as
   implementing unknown-key rejection ("Add `_check_unknown_top_level_keys()` to
   ProductionConfigValidator: rejects configuration keys not present among valid
   top-level keys...") without acknowledging the already-existing, already-wired
   implementation from the same day — consistent with the later commit's author
   re-implementing the same requirement without noticing the prior implementation, then
   never wiring the new one into `validate()`.
2. **Is the dead method's field derivation actually more correct?** No. Its one
   substantive addition beyond the active check is including `AgentConfig`'s own
   dataclass field names via `dataclasses.fields(AgentConfig)` — `llm`, `rag`, `tool`,
   `memory`, `mcp`, `approval`, `obs`, `diagnostics`, `messages`, and
   `agent_memory_max_startup_snippets`. Of these, only `agent_memory_max_startup_snippets`
   is a flat scalar field that could plausibly appear as a real top-level `config/agent.toml`
   key — and the active `_get_valid_production_keys()` already adds it explicitly (line
   153). The other nine names (`llm`, `rag`, `tool`, etc.) are `AgentConfig`'s internal
   Python attribute names holding parsed sub-config *objects*, not real
   `config/agent.toml` keys: confirmed via `grep -n "^\[" config/agent.toml`, whose actual
   top-level TOML tables are `[diagnostics]`, `[system_prompts]`,
   `[approval_risk_rules]`, `[approval_resource_keys]`, `[tool_safety_tiers]`,
   `[mcp_servers.*]`, and `[tool_definitions]` — none of `llm`/`rag`/`tool`/`memory`/
   `mcp`/`approval`/`obs`/`messages` appear as a section header. Treating these Python
   attribute names as valid top-level config keys would validate against the wrong key
   namespace, not a superior one. Conclusion: delete the dead method outright; no
   reconciliation is warranted.
