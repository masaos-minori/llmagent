## Background
`governance_03` Part 2 records NC-041: the deployed `github` configuration (not required, startup disabled, `config/agent.toml`, commit `4e2442a75`) disagrees with the approved classification (`github` = required in `docs/23_agent/agent_08_04_configuration-mcp-approval-obs.md`, ADR-004 Decision Group 3 item 13). Part 4 defines Configuration Drift as a discrepancy between deployed and approved operational values, and still states that no active drift items remain. Adversarial verification found the Issue's premise outdated: the Issue treats the disagreement as undecided and offers "NC-041 as the sole record while the owner decides" as an alternative, but NC-041's Evidence now records an owner decision on 2026-10-21 to restore `required = true`, with the restore deferred until `MCP_GITHUB_AUTH_TOKEN` is provisioned. The approved value is therefore settled, the deployed value differs, and the restore is pending, which is exactly the Part 4 definition. The sibling NC-041 issue referenced as "open" is already archived.

## Problem
Part 2 (NC-041) and Part 4 give contradictory pictures of the same state: NC-041 carries concrete evidence of a deployed-versus-approved disagreement while Part 4 says there is none. Release and deployment decisions that read only Part 4 would conclude there is no drift. Part 4 has no entry format example and no ID convention, and `tools/check_issue_inventory_conformance.py` validates Part 4 only for status values (`open`/`investigating`) written as `- **Status**: <value>`; it does not validate Part 4 entry fields.

## Reason for Change
An inventory whose parts contradict each other cannot be trusted for release gating. The disagreement concerns a mandatory component disabled by configuration alone, which ADR-004 prohibits, so its visibility in the drift inventory matters.

## Implementation Intent
Choose the Issue's preferred option (register a Drift entry) because the owner decision removes the premise of the alternative. Use the ID `DRIFT-001` (matches the `[A-Z]+-\d+` ID shape used by the inventory checkers), write the six template fields with the `- **Field**: value` bullet form that the Part 4 status check reads, describe the deployed and approved values in words instead of literal configuration values (per the docs content policy), point to NC-041 for evidence and to Part 4's removal rule for how long the entry stays, and add a one-line back-reference in NC-041. Severity is `Medium`, matching NC-041's Priority, and is flagged for owner confirmation because the reviewer rated the finding High.

## Requirements
- `REQ-001`: Part 4 "Active Items" contains one entry `DRIFT-001` for the `github` MCP server with the six fields ID, Decision target, Deployed value description, Approved operational value description, Severity, and Status (`open`), and the "No active Configuration Drift items remain." line is removed.
- `REQ-002`: The entry cross-references NC-041 for evidence and the restore dependency, does not duplicate NC-041's evidence text, and states that it is removed under Part 4's existing removal rule (deployed and approved values agree, or the approved value is formally changed).
- `REQ-003`: NC-041's Resolution Target cross-references `DRIFT-001` so Part 2 and Part 4 describe the same state consistently; no other NC-041 field changes.
