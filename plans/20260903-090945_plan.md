## Problem
`docs/00_governance_02_documentation-metadata.md`'s "Terminology Glossary" defines
only spelling/capitalization conventions (11 rows, e.g. American-English spelling
rules) — it contains no semantic distinction between Backward Compatibility,
Operational Fallback, Default, Lenient Parsing, Migration, Deprecated, and
Obsolete/Dead Code (confirmed by full read). `docs/00_governance_04_documentation-checks.md`'s
Governance Verification Matrix (`GV-001` through `GV-019`) has no rule for
detecting a removed identifier's reintroduction into current specifications, and no
temporary-exception process with owner/justification/expiration exists in either
governance document. Contrary to the Issue's Summary, a direct search for
"backward compat"/fallback-related misclassification found only one confirmed
instance (`docs/05_agent_13_reference-api.md:114`, already scoped to
`toolroutedoc`) — the three other examples the Issue names (RAG in-process
recovery, Memory FTS-only degradation, Workflow DB migrations) are already
correctly described using "fallback"/"incremental migration" terminology, not
"backward compatibility" (repository evidence: see Reference Files).

## Reason for Change
Combining terminology and documentation-check guidance ensures the vocabulary used
to classify compatibility behavior is the same vocabulary a future check script
enforces — defining them separately risks the check script inventing its own
categories that drift from the glossary.

Add the seven term definitions (with one project-relevant example each, drawn from
already-confirmed current behavior: RAG in-process fallback for Operational
Fallback, `workflow.sqlite`'s incremental mechanism for Migration, `read_json_file()`'s
retained-but-superseded status for Obsolete — **corrected 2026-09-03**: not

## Design
This Plan is documentation/governance-only; there is no code architecture change.
Path A/B classification (see `skills/issue-to-plan/SKILL.md` Routing): **Path B** —
the Issue's Target Files or Areas lists 8 files, exceeding Path A's "≤ 3 files"
threshold, even though Step 3 inspection found only 3 files need edits (the other 5
are already correct or out of scope pending a follow-up issue, and are carried as
Reference Files). The core design decision is the asymmetric detection-rule design
in `REQ-003`: names fully absent from source (`_update_null_fill`,
`ToolRouteResolver`+`server_configs`) can be detected by simple grep-vs-source-
absence, while a name still present in source but demoted from "current production
path" to "superseded" (`read_json_file`) requires a context-aware check (is the
identifier presented as *current* in a non-historical section?), not a plain string
search — this asymmetry must be documented in the rule design so a future
implementer does not build a single naive grep rule that either misses `read_json_file`
reintroduction or false-positives on its legitimate historical mentions. Historical
analysis (`git log --since=30.days`) found
`docs/00_governance_02_documentation-metadata.md` has a single author (Bus Factor
1, elevated risk — see Risks); the other two target files have 2 authors each.
