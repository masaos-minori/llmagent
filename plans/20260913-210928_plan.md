# Add a per-step fallback-chain table to augment()'s documentation

## Goal
Replace the bulleted 4-step `augment()` fallback chain description in
`docs/03_rag_03_01_query_pipeline-overview.md` with a table documenting each
step's possible return values, its fallback trigger, what the final result looks
like, and which diagnostics field records that step's outcome.

## Priority
Low

## Scope
- **In-Scope**: Converting the existing 4-step bulleted list (`augment() Fallback
  Chain` section) into a table with columns for return values, fallback
  trigger, final-result description, and the diagnostics field/mechanism tracking
  each step's outcome
- **Out-of-Scope**: Changing `augment()`'s implementation; adding new diagnostics
  fields (this Plan documents the existing `last_stage_results`/
  `last_search_diagnostics` mechanism, it does not extend it); restructuring the
  existing "Identity vs Truthiness" note (already accurate, per Background — kept
  as-is, referenced rather than duplicated)

## Background
The Issue's cited claim
(`docs/03_rag_03_01_query_pipeline-overview.md:53`: "Each step only falls back to
the next if it returns `None`") is confirmed accurate, and the Issue's own
per-step return-value descriptions (Step 1: `str`-including-empty or `None`;
Step 3: compressed text or `None`; Step 4: formatted text, final) match the
existing bulleted list (lines 55-58) almost exactly.

**Re-verified 2026-09-13** (this cycle): the Issue's claim that "the distinction
between empty string and None is critical but not documented per-step" is only
partially accurate — the existing "Identity vs Truthiness" note (line 60)
already explains this distinction, just as prose rather than per-step table cells.
What is genuinely missing, confirmed by direct reading of `augment()`
(`pipeline.py:247-341`, already read in full during a sibling issue's
investigation this same cycle): a mapping from each fallback step to the specific
diagnostics mechanism that records its outcome:
- Step 1 (HTTP mode) outcome is recorded via `self.last_stage_results`
  (`list[StageResult]`, populated from `self._augment_refiner.last_stage_results`,
  `pipeline.py:297`) and `self.last_search_diagnostics`
  (`SearchDiagnostics`, `pipeline.py:296`) — both exposed via `get_diagnostics()`
- Step 2 (Search Pipeline) is not itself a fallback/final step — it produces
  `ctx.reranked`, which subsequent steps consume; its own diagnostics (embed/FTS
  counters) are recorded in `SearchDiagnostics` via `RagPipelineStageLifecycle`
  (`pipeline.py:237-240`)
- Step 3 (Refiner) outcome is recorded as a `StageResult` entry
  (`stage_name="Refiner"`, confirmed at `augment.py:159-166` inside
  `AugmentRefiner.run_refiner()`, appended to `self.last_stage_results` — a
  different mechanism than `RagPipeline.run()`'s generic `_run_stage()` helper,
  which handles the 5-stage in-process search pipeline, not `augment()`'s own
  HTTP/Refiner fallback branches) within `self.last_stage_results`
- Step 4 (Raw Chunks) has no dedicated diagnostics entry — it is the unconditional
  final fallback, reached only if Step 3 (or Step 1) did not already return; its
  occurrence is inferable from the absence of a "success"/"fallback" `StageResult`
  for Refiner combined with `use_refiner=False`, or from `Refiner`'s own
  `StageResult` showing `status="fallback"`

## Problem
A developer debugging fallback behavior can find the sequence and the
identity-vs-truthiness rule, but has no documented way to determine, from
diagnostics alone, which step actually produced the augment result for a given
call — the mapping from step to diagnostics field exists in code but not in this
document.

## Reason for change
Add a table that consolidates the fallback chain's step order, return values,
fallback trigger, final-result shape, and diagnostics mapping in one place, making
this document sufficient on its own for a developer diagnosing which step produced
a given result.

## Implementation intent
Replace the bulleted list (lines 55-58) with a table with columns: Step | Produces
| Fallback Trigger | Final Result | Diagnostics. Keep the existing "Identity vs
Truthiness" and "On DB Connection Failure" notes unchanged, positioned after the
new table as they are now.

## Design
This task is classified as **Path A** (small task): affects 1 file, no public
interface changes, no database schema changes, no source code changes at all
(documentation-only).

This cycle's re-verification found the Issue's claim about the empty-string/None
distinction being undocumented only partially accurate (an existing note already
covers it), but confirmed a genuine gap in mapping fallback steps to their
diagnostics mechanism — this Plan focuses on that gap plus reformatting for
per-step clarity, rather than duplicating the already-accurate identity/truthiness
explanation.

Key design decisions:
1. Keep the "Identity vs Truthiness" note as prose after the table rather than
   folding it into a table cell — it explains a cross-cutting rule (applies to
   both Step 1 and Step 3), not a single step's specific behavior, so prose
   remains the clearer format for it
2. State "not directly tracked" for Step 4's diagnostics rather than implying a
   field exists — accurately representing an instrumentation gap is more useful
   to a debugging developer than implying complete diagnostics coverage
