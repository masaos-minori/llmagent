# Plan: Refactor startup.py — separation of concerns

## Goal
Split `scripts/agent/startup.py`'s `StartupOrchestrator` class into focused modules to separate its eight combined concerns and eliminate duplicated retry-once-with-delay logic.

## Priority
Medium

## Scope
- **In-Scope**: Extract six concern groupings into separate modules/classes; consolidate duplicated retry-once-with-delay helper; replace `_report_readiness()` per-source counting with shared helper; reduce `StartupOrchestrator` to thin sequencer; reorganize affected test files
- **Out-of-Scope**: Changing startup sequence order; changing timeout/retry values; adding new validation checks; modifying `scripts/agent/repl_health.py`, `scripts/agent/http_lifecycle.py`, or `scripts/agent/factory.py` internals; performance optimization

## Background
The module docstring states this file was "Extracted from agent/repl.py so that AgentREPL contains only input loop, command dispatch, and output display logic." After that extraction, `StartupOrchestrator` accumulated the full startup sequence in one class rather than being split further. Similar splits were already completed for `scripts/agent/orchestrator.py`, `scripts/agent/repl.py`, and `scripts/rag/ingestion/ingester.py`.

## Problem
`StartupOrchestrator` exceeds the 400-line threshold defined in `skills/DESIGN.md` File Split Rule trigger condition (670 lines) and combines at least eight distinct concerns: DI wiring/component init, workflow preflight checks, MCP subprocess startup, post-startup health verification, service-validation pipeline, readiness reporting, approval recovery, and system-prompt/memory setup.

## Reason for change
- `_check_services()` and `_report_readiness()` together account for roughly a third of the file and mix five independent validation concerns with formatting/aggregation logic
- `_report_readiness()`'s repeated per-source/per-status counting pattern is a maintenance risk
- MCP subprocess startup and post-startup health verification duplicate retry-with-delay logic in two different methods
- Approval recovery and memory/prompt setup are functionally unrelated to server startup but currently require reviewing the same 670-line file

## Implementation intent
Extract the eight concerns into separate modules/classes following the constructor-injection/delegation pattern used in `orchestrator.py` and `ingester.py` splits. Suggested grouping:
- **Component initializer** — owns `_initialize`, `_init_command_registry`, `_init_orchestrator`, `_check_workflow_definition`, `_check_workflow_schema`
- **MCP server starter** — owns `_start_servers`, `_start_http_subprocess_once`, `_verify_mcp_health`, `_interruptible_sleep`; factor shared retry-once-with-delay helper
- **Startup validation pipeline** — owns `_check_services`, delegating each of its five checks to existing services
- **Readiness reporter** — owns `_display_pipeline_results`, `_report_readiness`; replace repeated per-source counting with shared helper
- **Approval recovery** — owns `_recover_pending_approvals`
- **Prompt/memory setup** — owns `_setup_prompt`, `_classify_memory_failure`

`StartupOrchestrator.run()` should remain a thin sequencer calling into these components in the same order as today, preserving its public return contract (`tuple[CommandRegistry, Orchestrator, list[subprocess.Popen]]`) and rollback-on-failure behavior.

## Design
### Architecture decisions (Path B analysis)

**Import graph**: `startup.py` imports from 15+ modules across agent/, agent/services/, agent/shared/, agent/workflow/, and shared/. Extracted modules will each have narrower import dependencies aligned to their concern.

**Caller/callee relationships**: Only `scripts/agent/repl.py` consumes `StartupOrchestrator`. This limits blast radius to a single consumer but requires careful interface preservation.

**Historical churn**: Recent commits touch startup.py for formatting, drift fixes, diagnostics, and rollback behavior — moderate churn indicating active maintenance.

**Test coverage**: Four test files exist with extensive coverage (~24 occurrences of StartupOrchestrator in test_startup.py alone). Behavior-lock tests are critical for preserving rollback-on-failure semantics.

**Dependency graph**: 
- Direct callers: `scripts/agent/repl.py`
- Dependencies: `build_agent_context`, `init_tracer`, `Orchestrator`, `CommandRegistry`, `audit_security_defaults`, `check_readiness`, `McpToolDiscoveryService`, `check_routing_drift`, `check_routing_safety_tiers`, `RagMaintenanceService`, `find_all_pending_approvals`, `StateStore`, `StartupCheckStatus`, `StartupValidationResult`

**Operational constraints**: Production-profile MCP subprocess start failures raise `RuntimeError`; non-production only warn. `StartupInterrupted` exception must preserve raise conditions. `shutdown_event`-racing behavior must be preserved.
