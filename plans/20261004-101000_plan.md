# Plan: retry_once_with_delay preserves original exception type on second failure

## Goal
- Preserve the original exception type when `retry_once_with_delay` fails on its second attempt, enabling callers to distinguish between transient network errors and configuration errors.

## Priority
High

## Scope
- **In-Scope**: Modify `retry_once_with_delay` to re-raise the original exception instead of wrapping in `RuntimeError`; add regression tests.
- **Out-of-Scope**: Changing retry count or delay behavior; adding exponential backoff; modifying other retry helpers.

## Background
The shared retry helper `retry_once_with_delay` in `scripts/agent/shared/retry_helper.py` catches all exceptions from the first attempt and retries once. On second failure it always raises `RuntimeError` regardless of the original exception type.

## Problem
When the first attempt raises `TimeoutError` and the retry raises `ConnectionRefusedError`, both are silently converted to `RuntimeError`. The caller cannot distinguish between transient network errors and configuration errors. Error diagnosis becomes impossible — the root cause is lost. Callers cannot implement targeted recovery logic based on exception type. Monitoring/alerting systems cannot differentiate error categories.

## Reason for change
EventBUS-001 resolution established seq-ordered ACK as a consumer obligation; similarly, preserving exception types is necessary for reliable error classification in the agent startup pipeline. Without this fix, monitoring systems cannot alert on specific error categories (e.g., connection refused vs timeout).

## Implementation intent
On second failure, re-raise the original exception after logging. Instead of wrapping in `RuntimeError`, preserve the original exception type. If callers need a consistent wrapper, they can catch and wrap at their level.

## Requirements
- `REQ-001`: `retry_once_with_delay` must preserve the original exception type on second failure
- `REQ-002`: Tests must verify `TimeoutError` remains `TimeoutError` after retry failure
- `REQ-003`: Tests must verify `ConnectionRefusedError` remains `ConnectionRefusedError` after retry failure
- `REQ-004`: Existing callers reviewed for compatibility

## Design
### Current Behavior (Verified Against Source)
1. `retry_helper.py` line 59: `raise RuntimeError(masked_msg) from retry_err` — always wraps in `RuntimeError`
2. Caller `startup_mcp_starter.py` line 88: `except (OSError, RuntimeError)` — catches first attempt failures
3. Caller does not have a try-except around the retry call itself — exception propagates up
4. No test coverage for `retry_once_with_delay` — verified via grep across all test files

### Proposed Change
Replace line 59 of `retry_helper.py`:
```python
# Before:
raise RuntimeError(masked_msg) from retry_err

# After:
raise retry_err
```

This preserves the original exception type while keeping the log message intact (the log was already written before the raise).
