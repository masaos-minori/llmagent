## Design
- **Doc update**: insert a bullet between the existing `encryption_key` and
  `retention_days` lines (or immediately after `retention_days`) in
  `docs/05_agent_08_04_configuration-mcp-approval-obs.md`'s 診断設定 section:
  `- \`sensitive_fields\`: _filter_sensitive_fields()が追加でリダクションする
  フィールド名の集合（ハードコードされたデフォルトとの union）`. No concrete
  default value (matches the existing style for this section and satisfies
  the requirement's acceptance criterion of not embedding the default).
- **`test_config_builders.py` test**: follow the existing
  `test_overrides_are_applied` pattern — call
  `_build_diagnostics_config({"diagnostics": {"sensitive_fields": ["custom_field"]}})`
  and assert
  `cfg.sensitive_fields == frozenset({"custom_field"})`
  is wrong per current implementation (current code does NOT union with the
  dataclass default inside `_build_diagnostics_config()` itself — union
  happens later, inside `_filter_sensitive_fields()`). The test must assert
  what the code actually does: `cfg.sensitive_fields == frozenset(["custom_field"])`
  (the raw configured value, not yet unioned with `_SENSITIVE_FIELDS` — union
  is deferred to `_filter_sensitive_fields()` at use time). This must be
  confirmed by reading `_build_diagnostics_config()` once more immediately
  before writing the test (see Validation plan) to avoid asserting a
  behavior the code does not have.
- **`test_diagnostic_store.py` test**: follow the existing
  `test_save_encrypt_true_with_configured_key` pattern (same `fake_db` +
  `_FakeConfigLoader` setup), but instead of decrypting the stored row
  manually with `Fernet(...).decrypt(...)`, call `store.fetch(1)` and assert
  `entries[0]["content"] == '{"turn": 1}'` — this is the assertion currently
  missing anywhere in the test suite.

## Risks
- **Risk**: The new `test_config_builders.py` assertion could be written
  against the wrong expected value if the union-with-defaults behavior is
  assumed to happen inside `_build_diagnostics_config()` rather than inside
  `_filter_sensitive_fields()` (Likelihood: medium — this is an easy mistake
  given the two functions are easy to conflate) → **Mitigation**: added as an
  explicit re-read step in Implementation step 2 before the test is written;
  the test asserts on whatever `_build_diagnostics_config()` actually returns,
  verified fresh.
- **Risk**: Confirmed via `pyproject.toml` line 105:
  `[tool.mypy] files = ["scripts/"]` does NOT cover `tests/`, so a direct
  `uv run mypy scripts/` invocation will not type-check the two new test
  methods → **Mitigation**: rely on the pre-commit gate for test-file type
  checking, per `rules/coding.md`'s "`tests/` is also covered by
  pre-commit's mypy run"; the Validation plan's final row
  (`uv run pre-commit run --all-files`) is the actual gate for this, not the
  direct `mypy scripts/` command.
- **Risk**: This plan's scope overlaps with unimplemented items in
  `plans/done/20260818-170728_plan.md` (the two test additions) — a future
  reader could mistake that plan as already covering this work and skip it,
  or duplicate effort by implementing the same tests twice (Likelihood: low,
  now that this plan documents the gap explicitly) → **Mitigation**: this
  plan's Unknowns section records the exact reason the prior plan's test
