# Plan: Fix myPy "Source file found twice under different module names" error

## Goal
Resolve the myPy configuration conflict where `scripts/shared/tool_constants.py` is detected under two different module names (`shared.tool_constants` and `scripts.shared.tool_constants`), restoring myPy type checking across the project.

## Priority
High

## Scope
- **In-Scope**: Fix myPy configuration to eliminate duplicate module detection; update CI/CD invocation if needed
- **Out-of-Scope**: Changing import styles in source code; modifying the editable install configuration; adding `__init__.py` files to resolve the conflict

## Background
myPy reports the following error for every file checked:

```
scripts/shared/tool_constants.py: error: Source file found twice under different module names: "shared.tool_constants" and "scripts.shared.tool_constants"
```

The root cause is a conflict between myPy's `mypy_path = scripts` setting and the `files = ["scripts/"]` setting in `pyproject.toml`. Both mechanisms independently detect `shared.tool_constants` as a valid module path pointing to the same physical file.

Adversarial verification confirmed that removing `mypy_path = scripts`, adding `shared/` to myPy's ignore list, using `--explicit-package-bases`, or excluding specific files all fail to resolve the conflict. The correct solution is adding `--no-namespace-packages` flag to myPy invocations.

## Problem
Every invocation of myPy fails with the duplicate-module-name error, making type checking impossible for the entire project. This blocks CI pipelines and developer workflows that rely on myPy for static analysis.

## Reason for change
Without resolving this, no myPy-based tooling can function. The error affects all Python files in the project.

## Implementation intent
Add `--no-namespace-packages` flag to myPy invocations. This disables PEP 420 namespace package support, preventing myPy from treating `shared` as a top-level package when scanning `scripts/`. Verified working on all previously failing files.

## Design
The fix is straightforward: add `--no-namespace-packages` to myPy invocations. This flag disables PEP 420 namespace package support, which prevents myPy from treating directories without `__init__.py` as namespace packages. In this case, it prevents myPy from finding `shared` as a top-level package when scanning `scripts/`, eliminating the duplicate detection.

Two unknowns remain: whether this affects other namespace packages in the project, and whether the flag should be added to `pyproject.toml` or just the CI workflow. These are low-risk and do not block implementation.
