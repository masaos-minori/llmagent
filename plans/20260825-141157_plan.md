## Goal
- `scripts/agent/services/config_reload.py:_reload_approval_settings()` を、実際の責務に一致する4つの独立したヘルパー関数に分割する。振る舞いは変更しない純粋なリファクタリング。

## Priority
Medium

## Scope
- **In-Scope**:
  - `scripts/agent/services/config_reload.py`: `_reload_approval_settings()` を `_reload_approval_config()`(既存、変更なし)、`_reload_tool_allowlist()`、`_reload_memory_runtime()`、`_reload_security_profile()` の4関数に分割し、`apply_config_dict()` から4関数すべてを個別に呼び出す
- **Out-of-Scope**:
  - どのフィールドがホットリロード可能かの変更
  - フィールド更新ロジック自体の変更(関数境界・命名のみ変更)
  - `gitops_push_blocked` の追加(別issue `issues/20260825_cfgreload_gitops_push_blocked_not_reloadable_issue.md` で対応)

## Background
`_reload_approval_settings()` の責務混在は、複数の独立した過去の計画サイクルによる段階的な追加の結果である。`plans/done/20260623-151200_plan.md`/`plans/done/20260623-151300_plan.md` により `security_profile`/`security_lockdown_enabled` の処理がこの関数に追加された経緯を確認した。`allowed_tools`・`memory_retention_days`・`memory_local_only` がいつ追加されたかは本調査では特定していないが、命名と実装済みの意図(承認設定専用)から乖離した状態が積み重なっている。

## Problem
- `scripts/agent/services/config_reload.py:447` の `_reload_approval_settings()` は、`_reload_approval_config(ctx, new_cfg)` の呼び出しに加え、同一関数本体内で `ctx.cfg.tool.allowed_tools`、`ctx.cfg.memory.memory_retention_days`、`ctx.cfg.memory.memory_local_only`、および(ネストした `try`/`import` 経由で)`ctx.cfg.mcp.security_profile`/`security_lockdown_enabled` を直接更新している。これら4グループのフィールドは4つの異なる設定ドメイン(tool、memory、memory、mcp/security)に属し、`ApprovalConfig` とは無関係である。
- `_reload_approval_settings()` の呼び出し元はリポジトリ全体で `apply_config_dict()`(line 122)の1箇所のみであることを確認済み(`grep -rn "_reload_approval_settings" scripts/ tests/`)。他に直接呼び出す箇所は存在しないため、分割後に薄いラッパーとして残す必要はなく、完全に削除して4つの新規ヘルパーを `apply_config_dict()` から直接呼び出せる。

## Reason for Change
`allowed_tools` や `security_profile` がどこでリロードされるかを探す読者は、`_reload_approval_settings` という承認専用に見える関数名の中を探そうとは思わない。これは保守性を下げ、ある関心事への将来の変更が共有コードを介して別の関心事に意図せず影響するリスクを高める。

## Implementation intent
`_reload_approval_settings()` の本体を4つに分割する:
- `_reload_approval_config()` — 承認フィールドのみ(既存、変更なし、正しく命名済み)
- `_reload_tool_allowlist()` — `allowed_tools`
- `_reload_memory_runtime()` — `memory_retention_days`、`memory_local_only`
- `_reload_security_profile()` — `security_profile`、`security_lockdown_enabled`
`apply_config_dict()` からこの4関数を明示的に呼び出す形に置き換える。`_reload_approval_settings()` は呼び出し元が1箇所のみであることが確認できたため、完全に削除する。

## Requirements
- `REQ-001`: `scripts/agent/services/config_reload.py` に `_reload_tool_allowlist(ctx, new_cfg)`、`_reload_memory_runtime(ctx, new_cfg)`、`_reload_security_profile(ctx, new_cfg)` の3新規ヘルパーを追加し、`_reload_approval_settings()` からそれぞれの担当フィールドのロジックを移植する。
- `REQ-002`: `apply_config_dict()`(line 122付近)の `self._reload_approval_settings(ctx, new_cfg)` 呼び出しを、`self._reload_approval_config(ctx, new_cfg)` + 新規3ヘルパーの計4呼び出しに置き換える。
- `REQ-003`: `_reload_approval_settings()` 本体を削除する(呼び出し元が `apply_config_dict()` の1箇所のみであることを確認済みのため、薄いラッパーとして残す必要なし)。

## Acceptance criteria
- AC-01(REQ-001対応): 新規3ヘルパーがそれぞれ単一の関心事のみを扱い、既存のフィールド更新ロジック(`_get_bool`/`_get_list`/`_get_int`/`_get_str` によるdiff-apply パターン)を変更せずに移植されていることをコードレビューで確認できる。
- AC-02(REQ-002対応): `apply_config_dict()` が4関数すべてを呼び出し、`allowed_tools`・`memory_retention_days`・`memory_local_only`・`security_profile`・`security_lockdown_enabled`・既存の承認フィールドすべてについて、リロード時の挙動が変更前と完全に同一であることを既存テストで確認できる。
- AC-03(REQ-003対応): `_reload_approval_settings` という名前の関数がリポジトリ全体に存在しないことを確認できる。

## Tests

## Design
各ヘルパーは既存の `_reload_approval_config()` と同じシグネチャパターン(`self, ctx: AgentContext, new_cfg: dict[str, Any]) -> None`)に従う。フィールド更新ロジック(`_get_bool`/`_get_list`/`_get_int`/`_get_str` を使った diff-apply)はそのまま移植し、ロジック自体は変更しない。`apply_config_dict()` 内の呼び出し順序は、分割前の実行順序(承認 → allowed_tools → memory → security)を維持する。
