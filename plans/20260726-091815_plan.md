## Goal

Wire the existing, currently-dead `validate_tool_arguments()` (in `scripts/agent/tool_arg_validator.py`) into `execute_one_tool_call()` (in `scripts/agent/tool_runner.py`) so every tool call — read and write alike — is schema-validated against its `RuntimeTool.input_schema` immediately after JSON parsing and before any executor/gateway dispatch, with lenient fallback preserved when no schema is registered.

## Scope

**In scope:**
- `scripts/agent/tool_runner.py::execute_one_tool_call()` — add a validation step between `orjson.loads()` and dispatch.
- `scripts/shared/runtime_tool.py` — add a new `allow_extra_fields: bool = False` field to the `RuntimeTool` dataclass and to `build_runtime_tool()`.
- `scripts/agent/services/mcp_tool_discovery.py::_dedupe_and_build()` — the sole production `build_runtime_tool(...)` call site; no change required (new field defaults to `False`), but confirm it still constructs cleanly.
- Test fixture updates in `tests/test_tool_runner.py` and `tests/test_tool_approval_preflight.py` (`_make_ctx()` helpers) to explicitly default `ctx.services_required.runtime_tools = None`, preventing `MagicMock` auto-vivification from feeding garbage into `jsonschema.validate()`.
- One additional test exercising the gateway/write dispatch path (validation rejection must prevent `gateway.execute()` from being called), since existing pre-written tests only exercise the direct `tools.execute()` path.

**Out of scope:**
- Any change to `scripts/agent/repository_gateway.py::_gate_write()`'s policy/approval responsibilities (`check_preflight`, `classify_risk`, `run_approval_checks`) — explicitly forbidden by the requirement; validation stays a single chokepoint in `tool_runner.py`.
- Any change to `scripts/agent/tool_arg_validator.py`'s validation logic itself — it is already correct and covered by `tests/test_tool_arg_validator.py`; only its call site is missing.
- Changing how `RuntimeToolRegistry` is populated/wired at startup (`agent/startup.py`, `McpToolDiscoveryService`) — out of scope, registry wiring already exists.
- Adding `allow_extra_fields` as a configurable per-tool value sourced from MCP server tool advertisements — no such field exists in any server's tool metadata today; this task only adds the dataclass field with a safe default, not a discovery-time population mechanism.
- Any docs updates (`docs/*.md`) — this is a document-only planning phase; doc updates (if any) belong to the implementation phase, not this plan.

## Assumptions

1. `ctx.services_required.runtime_tools` is the correct, sole source of per-tool `input_schema` for validation purposes (confirmed: `AppServices.runtime_tools: RuntimeToolRegistry | None`, populated in `agent/startup.py:293` from `McpToolDiscoveryService`).
2. `RuntimeToolRegistry.get(name)` raising `KeyError` for unregistered names is the correct signal to fall through to lenient (skip-validation) behavior, not to error the call (mirrors `RuntimeToolRegistry.resolve()`'s "unknown → None" convention conceptually, but `get()` itself raises by design — confirmed in `scripts/shared/runtime_tool_registry.py:87-97`).
3. Adding `allow_extra_fields: bool = False` as a new **trailing, defaulted** field on the frozen `RuntimeTool` dataclass is backward-compatible with all existing keyword-based construction sites (`build_runtime_tool()`, and direct `RuntimeTool(...)` calls in `tests/test_cmd_mcp.py`), since none of them rely on positional-only construction and a defaulted trailing field cannot break them.
4. Setting `source="validation"` (non-empty) on the synthetic `ToolCallResult` produced for a validation rejection is the intended way to make `audit_tool_exec()` emit a `tool_exec` audit event for rejected calls, since `audit_tool_exec()` early-returns when both `mcp_request_id` and `source` are empty (`scripts/agent/tool_audit.py:172-173`), and a validation-rejected call has no real `mcp_request_id`.
5. The pre-existing test class `tests/test_tool_runner.py::TestExecuteOneToolCallValidation` (lines 693-854) was authored in advance of this wiring work as the acceptance spec for it and is currently failing (verified: all 7 tests fail against current `master`, independent of the local `pytest-asyncio` plugin gap — see Validation Plan). The implementation should satisfy this class's exact expectations (mock shapes, attribute names, error-text substrings) rather than redesigning the contract.
6. This environment currently lacks `pytest-asyncio` (only `anyio` plugin present, `pip show pytest-asyncio` → not found), even though `pyproject.toml` declares `pytest-asyncio>=0.23` as a dependency and configures `asyncio_mode = "auto"`. This is treated as a local environment gap, not a scope concern — the implementation phase must run tests in an environment where `pytest-asyncio` is actually installed.

2. **What exact registry lookup API does `tool_runner.py` need to call, and how does it signal "not found"?**

3. **What is the expected shape/contract of the validation integration (return value on failure, which dispatch branch is skipped, exact error-text expectations)?**
   Resolution: Fully specified by the pre-existing (currently failing) `TestExecuteOneToolCallValidation` test class in `tests/test_tool_runner.py`. Resolved — treated as the authoritative contract.
4. **Does introducing a `ctx.services_required.runtime_tools` read in `execute_one_tool_call()` risk breaking any currently-passing tests that construct `ctx` as a bare `MagicMock()` without configuring `runtime_tools`?**
   Resolution: Yes — confirmed a real regression risk. `tests/test_tool_runner.py::_make_ctx()` (used by ~21 other test methods before the new validation test class) and `tests/test_tool_approval_preflight.py::_make_ctx()` (used by tests that call `execute_one_tool_call()` directly, e.g. the gateway-path test at line ~688) do not set `runtime_tools`. See Risks. Resolution: update both `_make_ctx()` helpers to set `ctx.services_required.runtime_tools = None` as their baseline default (this is now an Implementation step, not left as a residual unknown).
5. **Does audit logging need any change to satisfy "ensure audit logging still fires appropriately for rejected calls" from the requirement's Implementation Intent?**
   Resolution: Yes — a validation rejection must produce a synthetic `ToolCallResult` with a non-empty `source` (e.g. `"validation"`) so `audit_tool_exec()`'s early-return guard (`if not mcp_request_id and not source: return`, `scripts/agent/tool_audit.py:172-173`) does not suppress the audit event. Resolved via source inspection; captured in Design.
6. **Is there existing test coverage for the write/gateway dispatch path being skipped on validation failure?**
   Resolution: No. All 7 pre-written tests in `TestExecuteOneToolCallValidation` run with `ctx.services_required.gateway = None` (set in `_make_ctx()`), so they only exercise the direct `ctx.services_required.tools.execute(...)` branch. The requirement's own "Tests" section explicitly asks for a write-classified/gateway-path rejection test. Not blocking (doesn't require asking the user — solvable by writing one more test during implementation), but flagged as an implementation-step gap to close. Resolved by adding an implementation step.

## Design

### Where validation runs

Inside `execute_one_tool_call()`, immediately after the existing `orjson.loads(args_str)` block (current lines 131-136) and before the existing dispatch branch (current lines 138-141):

```python
try:
    args = orjson.loads(args_str)
except orjson.JSONDecodeError as e:
    raise ToolArgumentsDecodeError(...) from e

validation_error = _validate_tool_args(ctx, name, args)
if validation_error is not None:
    result = validation_error
elif ctx.services_required.gateway is not None:
    result = await ctx.services_required.gateway.execute(ctx, name, args)
else:
    result = await ctx.services_required.tools.execute(name, args)

text, is_error, x_request_id = result.output, result.is_error, result.request_id
audit_tool_exec(...)
```

This applies uniformly to both dispatch branches (gateway and direct-executor) — validation happens once, before the `if/else`, not duplicated into each branch and not pushed into `repository_gateway.py`.

### `_validate_tool_args()` helper (new, private, in `tool_runner.py`)

```python
def _validate_tool_args(ctx: AgentContext, name: str, args: dict) -> ToolCallResult | None:
    """Validate args against the tool's registered schema.

    Returns an error ToolCallResult if validation fails, or None to proceed
    with normal dispatch (including all lenient-fallback cases: no registry,
    tool not registered, or no schema on the registered tool).
    """
    registry = ctx.services_required.runtime_tools
    if registry is None:
        return None
    try:
        runtime_tool = registry.get(name)
    except KeyError:
        return None

    result = validate_tool_arguments(
        tool_name=name,
        args=args,
        input_schema=runtime_tool.input_schema,
        allow_extra_fields=runtime_tool.allow_extra_fields,
    )
    if result.success:
        return None

    logger.warning(
        "tool_arg_validation_rejected tool=%r reason=%s", name, result.reason
    )
    return ToolCallResult(
        output=result.reason,
        is_error=True,
        request_id="",
        server_key="",
        source="validation",
        error_type="validation",
    )
```

Design notes:
- Only `KeyError` is caught around `registry.get(name)` — matching `RuntimeToolRegistry.get()`'s documented contract (raises `KeyError` only). No broad `except Exception` is added, keeping behavior predictable and matching the pre-written test `test_validation_passes_for_unknown_tool` (`side_effect = KeyError(...)`).
- `source="validation"` is set (non-`""`) specifically so `audit_tool_exec()` does not early-return on empty `mcp_request_id`/`source` (see Assumption 4). `error_type="validation"` distinguishes this from `"transport"`/`"tool"` error types already in use.
- The synthetic `ToolCallResult` flows through the *rest* of the existing function unchanged (`text, is_error, x_request_id = result.output, ...`, `audit_tool_exec(...)`, the transport-failure diagnostics branch — which is skipped because `error_type == "transport"` is false — and the `llm_text` truncation logic), so no other code path needs special-casing for the validation-rejected case. This satisfies the requirement's "matching the existing error-result shape" instruction.
- `import` of `validate_tool_arguments` from `agent.tool_arg_validator` is added as a normal top-of-file import in `tool_runner.py` (not a local/deferred import) — `tool_arg_validator.py` has no `agent`-layer imports itself (only `jsonschema`/`logging`), so there is no circular-import risk and no need for the `# noqa: PLC0415` deferred-import pattern used elsewhere in this file for `agent.tool_approval`.

### `RuntimeTool.allow_extra_fields` field addition

Add to `scripts/shared/runtime_tool.py`:
- `RuntimeTool` dataclass: new field `allow_extra_fields: bool` appended after `capabilities`, with the dataclass docstring updated to describe it (`allow_extra_fields: True when unexpected/unschemad argument fields should be tolerated instead of rejected by validate_tool_arguments()`).
- `build_runtime_tool()`: new parameter `allow_extra_fields: bool | None = None`, resolved the same way as the existing boolean-flag parameters (`resolved_allow_extra_fields = allow_extra_fields if allow_extra_fields is not None else False`), documented in the "Safe-default rules" docstring block (`allow_extra_fields defaults to False — extra/unschemad fields are rejected unless a tool explicitly opts in`).
- No change needed at the sole production call site (`mcp_tool_discovery.py:317`, which uses keyword args and does not pass `allow_extra_fields`) — it will pick up the new default (`False`) automatically. This is intentionally conservative: today no MCP server advertises an "allow extra fields" flag, so every currently-discovered tool defaults to strict (reject-extra-fields) validation.
- Existing direct `RuntimeTool(...)` constructions in `tests/test_cmd_mcp.py` (lines ~530, ~546) use keyword arguments and will continue to work once `allow_extra_fields` has a dataclass-level default — no source change required in that test file (verify at implementation time that dataclass field defaults are respected for all-keyword construction with a trailing new field; if `RuntimeTool` is `@dataclass(frozen=True)` without `kw_only=True`, a defaulted field can safely trail non-defaulted fields as long as it is added last, which this design does).

### Audit logging for rejections

Per Assumption 4/Design above: setting `source="validation"` on the synthetic `ToolCallResult` is sufficient — no change to `audit_tool_exec()`'s signature or body is needed. The existing call `audit_tool_exec(ctx, name, args, is_error, x_request_id, result.error_type, source=result.source)` (current line 143-145) already forwards `error_type` and `source` from whatever `result` object it's given, so it needs no changes at all — only the upstream `result` construction changes.

### Test fixture fix (regression prevention)

In both `tests/test_tool_runner.py::_make_ctx()` and `tests/test_tool_approval_preflight.py::_make_ctx()`, add:
```python

```
to the fixture body (alongside the existing `ctx.services_required.tools = ...` line). This makes the "no registry wired" lenient-fallback path the default for every test in both files that doesn't explicitly opt into validation testing, matching real production behavior when a run has no `RuntimeToolRegistry` wired (`agent/startup.py:293` only sets it when discovery succeeds).

## Risks

- **Risk (high, now mitigated by design): `MagicMock()`-based test fixtures silently break.** `tests/test_tool_runner.py::_make_ctx()` and `tests/test_tool_approval_preflight.py::_make_ctx()` build `ctx = MagicMock()` without configuring `runtime_tools`. Once `execute_one_tool_call()` reads `ctx.services_required.runtime_tools`, a bare `MagicMock()` auto-vivifies a truthy mock whose `.get(name)` never raises `KeyError`, feeding a non-dict `MagicMock` into `jsonschema.validate()` and very likely raising an uncaught, non-`ValidationError` exception — breaking ~21+ currently-passing tests across both files. **Mitigation:** Implementation step 2 makes both fixtures default `runtime_tools = None` *before* the production code changes, so the fix lands ahead of (and is verified independently of) the feature wiring.
- **Risk (medium): other test files with `MagicMock()`-based `ctx` and a direct (unpatched) call to `execute_one_tool_call`/`execute_all_tool_calls` were missed.** Six other files reference these functions (`tests/test_agent_repl_tool_exec.py`, `tests/test_llm_turn_runner.py`, `tests/test_orchestrator.py`, `tests/integration/test_rag_llm_integration.py`, `tests/integration/test_rag_turn_integration.py`, plus `scripts/agent/llm_turn_runner.py` itself as production code). Preliminary inspection during this planning cycle found `test_agent_repl_tool_exec.py` patches `execute_one_tool_call` directly (safe) and the integration test raises `ToolArgumentsDecodeError` before validation runs (safe), but this was not exhaustively verified for every file. **Mitigation:** Implementation step 8 explicitly re-runs all of them and requires zero new failures before considering the change complete.
- **Risk (low): `jsonschema.validate()` behavior against a genuinely malformed (but non-empty, non-`MagicMock`) real-world schema from an MCP server could raise an exception type `_check_type_validation()` doesn't catch** (it only catches `jsonschema.ValidationError`; a schema itself that is structurally invalid raises `jsonschema.SchemaError`, a different exception class, which would propagate up uncaught through the new `_validate_tool_args()` call). This is pre-existing behavior in `tool_arg_validator.py` (out of scope to fix per this plan's scope boundary), but wiring it into the live dispatch path means a malformed schema from any MCP server could now crash a tool call it previously would have executed leniently. **Mitigation:** flag as a residual risk for the implementer to consider widening the except clause in `tool_arg_validator.py::_check_type_validation()` to also catch `jsonschema.SchemaError` in a follow-up, or catch it defensively at the `_validate_tool_args()` call site in `tool_runner.py` and treat a schema error the same as "no schema" (lenient skip) rather than raising. Not fixed in this plan because `tool_arg_validator.py`'s internals are explicitly out of scope, but documented here since the risk only becomes live once this wiring lands.
- **Risk (low): `pytest-asyncio` not installed in the sandbox used for this planning cycle** prevents actually running the async test suite to observe pass/fail status beyond confirming the collection-time failure mode is unrelated to plugin issues. **Mitigation:** implementation must be validated in the project's real dev/CI environment where `pytest-asyncio>=0.23` is installed (per `pyproject.toml`); this is a planning-cycle environment gap, not a code risk.
- **Risk (low): bus factor / churn is not a differentiating risk here** — `tool_runner.py` (49 commits) and `tool_arg_validator.py` (1 commit) are both effectively single-author (case-variant name spellings of the same author across commits), so cross-author coordination risk is negligible for this repo.
