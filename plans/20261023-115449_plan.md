## Goal
- Make config isolation effective for MCP server processes by applying `ConfigLoader.restrict_to()` before a server module reads any configuration, and stop package imports from executing other servers' modules.

## Priority
Medium

## Scope
- **In-Scope**: Lazy package `__init__` files for the seven server packages that import server modules (keeping the existing aliases); the binary launcher template applying the restriction before the server import; `mcp_launcher.py` resolving a server without importing any server module; tests; the configuration-inventory documentation.
- **Out-of-Scope**: Changing the config file layout, ADR-002 itself, or the keys each server reads; per-server token distribution by the Agent; the posture gate (`mcpstart002`), empty-token rule (`mcpstart003`), audit logging (`mcpstart005`) and rag-pipeline lifecycle (`mcpstart006`); calling `restrict_to()` at the top of server modules (it would break tests, see Design).

## Background
ADR-002 (platform config isolation) requires each server process to read only its own config file. `MCPServer.run_http()` enforces it with `ConfigLoader.restrict_to(own_config_file)`, but server modules load their config, build their service and compute their posture at import time, and the production binary launchers import the server module before calling `run_http()`. `scripts/mcp_servers/file/__init__.py` imports `delete_server`, `read_server` and `write_server`; the cicd, git, shell, mdq, rag_pipeline and web_search `__init__` files import their own server module. `ConfigLoader.restrict_to()` accepts only one file set per process, and the test suite imports many servers in one process.

## Problem
Importing only `mcp_servers.file.read_server` loaded `file_delete_mcp_server.toml`, `file_read_mcp_server.toml` and `file_write_mcp_server.toml`, left `delete_server` and `write_server` in `sys.modules`, and found `ConfigLoader._allowed_files` still `None`. The read process therefore reads the delete and write configs and builds their services, and a delete-server configuration error (for example an empty delete token) stops the read server at import. In an Agent-managed start every `MCP_*_AUTH_TOKEN` reaches every subprocess, so that outage does not occur today, but the isolation invariant is already violated. Separately, `python -m mcp_servers.git.git_server` executes the module twice (the package `__init__` imports it, then runpy runs it as `__main__`), and a probe counted two loads of `git_mcp_server.toml`; production binaries import once. `mcp_launcher.py` imports every server module in one process, including for `--list`, which runs each module's import-time side effects.

## Reason for Change
The isolation rule is the stated defense against one misconfigured or compromised server reading another's secrets and settings, and the file servers differ sharply in privilege. Import-time work outside the isolation window defeats the rule, and double execution makes startup state harder to reason about.

## Implementation Intent
Apply isolation at the process entry point, before the server module is imported, using the config file name the entry already knows; make package imports side-effect free by loading submodules lazily; make the development launcher import only the server it starts. Keep `run_http()`'s own `restrict_to()` call (idempotent for the same set).

## Requirements
- `REQ-001`: `mcp_servers/file/__init__.py` no longer imports `delete_server`, `read_server` or `write_server` eagerly; importing one file server loads only its own config file.
- `REQ-002`: The cicd, git, shell, mdq, rag_pipeline and web_search `__init__` files load their submodules lazily through module `__getattr__`, keeping the existing aliases (`server`, `models`, `service`, `tools`), so `python -m <server module>` executes the module once.
- `REQ-003`: The binary launcher generated by `deploy/build_binaries.sh` calls `ConfigLoader.restrict_to(<own config file>)` before importing the server module, with the config file name carried in the `ENTRIES` table, and a test keeps that table consistent with each server class's `own_config_file`.
- `REQ-004`: `mcp_launcher.py` resolves a server key to its module and own config file by static source analysis (no import), applies the restriction, imports only that module, and `--list` imports no server module.
- `REQ-005`: Tests prove each server module loads only its own config file when imported, importing one file server does not import the others, the lazy aliases still resolve, and the `ENTRIES` table matches the server classes.
- `REQ-006`: The configuration-inventory documentation states when isolation takes effect for each launch path.

## Design
Path B (more than three files; start-path change). Architecture analysis: `lint-imports` reports all 6 contracts kept; the changes add no cross-layer import (the launcher uses `shared.config_loader`, already imported by `server.py`). The restriction cannot move to the top of each server module because `restrict_to()` allows one file set per process and the test suite imports many servers; it belongs at the process entry point. The binary launcher is the only production entry, and it already knows which server it starts, so `ENTRIES` carries the config file name (a fifth `:`-separated field parsed in `build_one`) and the template emits `ConfigLoader.restrict_to("<file>")` before `from <module> import <Class>`; a test pins `ENTRIES` against `own_config_file` so the two cannot drift. Lazy package imports use module `__getattr__` mapping the existing alias names to submodules, so `from mcp_servers.git import server` and `from mcp_servers.web_search import health` keep working while import no longer executes server code. `mcp_launcher.py` replaces import-based discovery with an `ast` scan of `scripts/mcp_servers/**/*_server.py` reading literal class attributes (`server_key`, `server_name`, `own_config_file`, `http_port`), so `--list` has no side effects and launching imports one module after restricting. `python -m <server module>` stays a development path with unrestricted pre-import loading apart from the single-execution fix; this is documented rather than changed. Historical analysis (30 days): the seven `__init__` files and `mcp_launcher.py` have 0 commits; `build_binaries.sh` has 10 and is also edited by `mcpstart002` (comment line), so apply sequentially. Operational dependency: production runs binaries, so the change needs a rebuild (Phase 5).
