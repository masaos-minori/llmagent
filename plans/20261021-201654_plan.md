## Background
`tool_approval.check_approval` builds a preview for MEDIUM/HIGH-risk calls via `_build_preview_with_dry_run`, then prompts the user interactively via `_prompt_user_approval`. `_build_preview_with_dry_run` calls `ctx.services_required.tools.execute(tool_name, {**args, "dry_run": True})` to enrich the preview with a simulated result. This is gated by `cfg.approval.approval_dry_run_tools` and limited to `_KNOWN_DRY_RUN_CAPABLE_TOOLS`. The preview is built (and therefore the tool executed) before the user approves.

## Problem
The preview is shown before the approval decision, yet the tool actually executes. The security boundary ("execute only after approval") is relaxed for preview enrichment. If any whitelisted tool treats `dry_run` as advisory (performs the write/delete/network action anyway), the preview becomes an unapproved execution. The contract that `dry_run=True` performs zero side effects is assumed but not enforced or documented per tool.

## Reason for Change
Dry-run preview enrichment is enabled by config, so the pre-approval execution is now part of the runtime path. The no-op contract is currently assumed, not verified per tool, and not documented at the point of the whitelist definition or in the Known Limitations.

## Implementation Intent
- Enumerate every tool in `_KNOWN_DRY_RUN_CAPABLE_TOOLS` and confirm each server honors `dry_run=True` as a hard no-op. Record the result per tool.
- Where a tool cannot guarantee a no-op dry_run, remove it from the whitelist (or drop it from the default `approval_dry_run_tools`) so it falls back to a text-only preview.
- Add a comment at the whitelist definition asserting the no-op contract, so future additions must satisfy it.
- Document the pre-approval execution boundary and the no-op requirement in the approval subsystem Known Limitations.
- Extend the existing dry-run test to assert `execute` is called with `dry_run=True` and that no downstream mutation occurs under a fake executor.

## Requirements
- `REQ-001`: Every tool in `_KNOWN_DRY_RUN_CAPABLE_TOOLS` is audited and confirmed to perform zero side effects under `dry_run=True` (no write/delete/network/database side effect). The per-tool result is recorded.
- `REQ-002`: A whitelisted tool that cannot guarantee a no-op dry_run is removed from `_KNOWN_DRY_RUN_CAPABLE_TOOLS` (or dropped from the default `approval_dry_run_tools`) so its preview degrades to text-only. Applies only if the audit finds such a tool.
- `REQ-003`: The whitelist definition carries a comment/assertion stating that membership requires a guaranteed no-op `dry_run=True`.
- `REQ-004`: The pre-approval dry-run execution boundary and the per-tool no-op contract are documented in the approval subsystem Known Limitations.
