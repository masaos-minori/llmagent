# Plan: Implement principal-based authentication and role authorization

## Goal

Consolidate EventBus credential resolution into one typed principal used uniformly for every endpoint's authorization decision, eliminating the split design that permits inconsistent decisions between middleware and dependencies.

## Priority
High

## Scope
- **In-Scope**: Authentication/authorization resolution in `scripts/eventbus/auth.py`, `scripts/eventbus/app.py`, config (`scripts/eventbus/config.py`, `config/eventbus.toml`), and directly-dependent tests
- **Out-of-Scope**: Unrelated route handlers' business logic, rewriting existing route handler implementations, `EVENTBUS-008` governance entry correction (belongs to `eventbus10`)

## Background
`docs/00_governance_03_issue-and-uncertainty-management.md` EVENTBUS-008 states no production authentication model exists for the Event Bus HTTP API, while `scripts/eventbus/auth.py` already defines a `Role` enum, route-to-role map, and per-role token maps. The current split design — middleware checking `auth_token` separately from endpoint dependencies checking per-role tokens — permits inconsistent authorization conclusions for the same request.

## Problem
Authentication, per-role tokens, route authorization, and end-to-end authorization verification are currently split across middleware and per-endpoint dependencies in `scripts/eventbus/auth.py` and `scripts/eventbus/app.py`, with no single typed principal object carrying resolved roles/identity through the request. This permits the middleware and a dependency to reach different authorization conclusions for the same request.

## Reason for change
Authentication, per-role tokens, route authorization, and end-to-end authorization verification are one security boundary. The current split design permits inconsistent decisions between middleware and dependencies.

## Implementation intent
Resolve each credential to one typed principal and use that principal for every endpoint authorization decision. Choose one authentication authority for the whole EventBus process rather than duplicating the check between middleware and dependencies.

## Requirements
- `REQ-001`: Introduce an authenticated principal containing roles, allowed consumer IDs, allowed topics, and a non-secret token identifier or fingerprint.
- `REQ-002`: Resolve the principal from the presented token.
- `REQ-003`: Compare the endpoint's required role with the principal's roles.
- `REQ-004`: Return HTTP 401 for unknown tokens and HTTP 403 for insufficient roles.
- `REQ-005`: Choose one authentication authority for all EventBus requests.
- `REQ-006`: Accept configured per-role tokens and map them to principals.
- `REQ-007`: Remove duplicate authentication checks between middleware and dependencies, or make the middleware populate the principal for dependencies.
- `REQ-008`: Define and document the compatibility behavior of `auth_token`.
- `REQ-009`: Remove string-prefix route authorization where the endpoint dependency already declares the required role.
- `REQ-010`: If route metadata is required, use the FastAPI route name or path template.
- `REQ-011`: Add authorization tests for routes containing path parameters.
- `REQ-012`: Create end-to-end tests using the actual FastAPI application and configured role tokens.
- `REQ-013`: Cover authentication, role checks, consumer identity, topic restrictions, and dynamic routes.
- `REQ-014`: Verify that authorization failures occur before persistent state changes.

## Design

### Principal Class (REQ-001)
Introduce a typed `Principal` dataclass carrying resolved identity:
```python
@dataclass(frozen=True)
class Principal:
    """Authenticated identity carrying roles, consumer IDs, topics, and token fingerprint."""
    roles: frozenset[Role]
    allowed_consumer_ids: frozenset[str]  # empty = unrestricted
    allowed_topics: frozenset[str] | None  # None = unrestricted
    token_fingerprint: str  # non-secret identifier for audit logging
```

The `token_fingerprint` provides an audit trail without exposing raw token values. It could be derived from a hash prefix of the token or a token alias stored in config.

### Principal Resolution (REQ-002, REQ-006)
Replace `verify_bearer_token()` with `resolve_principal()`:
```python
async def resolve_principal(
    request: Request,
    credentials: HTTPAuthorizationCredentials = Depends(HTTPBearerDep),
) -> Principal:
    """Resolve a bearer token to a Principal, or raise 401."""
```

This function:
1. Validates the token exists in `_TOKEN_ROLE_MAP`
2. Returns a `Principal` with resolved roles, consumer IDs, topics, and fingerprint
3. Raises HTTP 401 for unknown/missing tokens

### Role Comparison (REQ-003, REQ-004)
Replace `require_role()` with a principal-aware dependency:
```python
def require_role(role: Role):
    """FastAPI dependency factory: verify caller's principal has the required role."""
    async def _check_role(
        request: Request,
        principal: Principal = Depends(resolve_principal),
    ) -> Principal:
        if role not in principal.roles:
            logger.warning("Authorization failed: requires %s, caller has %s", role, principal.roles)
            raise HTTPException(status_code=403, detail=f"Forbidden: requires {role} role")
        return principal
```

Key differences from current `require_role()`:
- Uses `Depends(resolve_principal)` instead of `Depends(verify_bearer_token)` — principal is resolved once
- Compares against `principal.roles` instead of `_TOKEN_ROLE_MAP.get(token, set())`
- No string-prefix route matching — FastAPI's route name/path template handles this
- Always returns HTTP 403 for insufficient roles (never 401, since auth was already validated)

### Single Authentication Authority (REQ-005, REQ-007)
**Decision**: Endpoint dependencies (`require_role`, `require_consumer_identity`) become the sole authentication authority. The middleware continues injecting `X-Request-Id` but delegates authentication to endpoint dependencies.

Rationale:
- Middleware currently checks `auth_token` only — it cannot validate per-role tokens
- Endpoint dependencies already check per-role tokens via `_TOKEN_ROLE_MAP`
- Consolidating at endpoint dependencies eliminates the split where middleware accepts a request that an endpoint dependency would reject
- The middleware's `X-Request-Id` injection is orthogonal to authentication and should be preserved

### `auth_token` Compatibility (REQ-008)
The shared `auth_token` grants all roles (confirmed by `_populate_token_maps()` line 77). This must be:
1. Explicitly documented in `config/eventbus.toml`
2. Tested as both a positive case (all endpoints accessible) and a negative case (no degradation when per-role tokens are configured alongside)
3. Preserved for backward compatibility — deployments using only `auth_token` must continue working

### String-Prefix Route Authorization Removal (REQ-009, REQ-010)
Remove the string-prefix route matching in `require_role()` (current code lines 154-170):
```python
# Current (to be removed):
path = request.url.path
for route_path, allowed_roles in _ROUTE_ROLE_MAP.items():
    if path.startswith(route_path):
        if role not in allowed_roles:
            raise HTTPException(...)
        return role
raise HTTPException(status_code=403, detail="Forbidden: unknown route")
```

Replace with FastAPI-native route metadata:
- Use `request.url.path` comparison against FastAPI's route path template (e.g., `/events/{event_id}/ack`)
- Or use FastAPI's `route.name` attribute for named routes
- The `_ROUTE_ROLE_MAP` can remain as a supplementary check for edge cases

### Consumer Identity Authorization (REQ-003)
`require_consumer_identity()` should also receive the `Principal` dependency:
```python
async def require_consumer_identity(
    request: Request,
    consumer_id: str = "",
    topics: list[str] | None = None,
    principal: Principal = Depends(resolve_principal),
) -> dict[str, Any]:
```

Use `principal.allowed_consumer_ids` and `principal.allowed_topics` directly instead of querying `_TOKEN_CONSUMER_MAP` and `_TOKEN_TOPIC_MAP`.
