# Implementation Plan: background tasks are never cancelled at shutdown, and the completion callback cannot read a cancelled task

**Plan ID**: 20261023-151742
**Source Issue**: `issues/20261021-093421_turn005_background-tasks-not-cancelled-at-shutdown.md`
**Generated**: 2026-10-23 15:17 JST

## Goal

Make the shutdown path's tracked-task cancellation reachable from the code that creates the tasks, by
giving the Agent one background-task registry instead of two, and make `BgTaskMonitor.on_task_done`
total over a task's terminal states so a cancelled task is released from that registry and its
consecutive-failure counter is reset.

High

## Reason for Change

- The one place the Agent promises to stop its own background work does nothing, and the one place that
  promises to release a finished task stops working exactly when the task was cancelled. Both are
  invisible in the current suite because the tests supply the shape the code expects rather than the
  shape asyncio produces.
- The defect is user-visible at the only point it matters: a session that is closed while its title
  request is in flight leaves an LLM request abandoned at loop close, and any consecutive-failure count
  built up across a cancelled task is not cleared, so the next failure is treated as a continuing streak.
- Four Plans have already handed the ownership question to this Plan; leaving it unanswered keeps
  `resource_shutdown_coordinator.py:113-137` unreachable even though the code that owns the rest of the
  shutdown sequence has now landed. `repl001`'s `UNK-03` is answered in code (`repl_input_loop.py:282`,
  `:294`) and by `DR-003` here.

## Implementation Intent

- Make the contract physical: one object, created once with the context, written by the producer, read by
  exactly two consumers, and named in the docs that describe the turn flow and the shutdown sequence.
- Make the callback total by ordering the terminal-state check the way asyncio requires, and keep the
  failure ladder exactly as it behaves today by moving it unchanged into private methods — the change to
  `on_task_done` is the cancellation branch, not the counting.
- Delete the guard, the second set, the unused import, and the four ordering claims rather than
  documenting around them.

## Requirements

- `REQ-001`: `ctx.turn.background_tasks` is the only tracked-task registry. `Orchestrator.__init__` no
  longer creates `self._background_tasks` (`orchestrator.py:89`) and passes `ctx.turn.background_tasks`
  to `BgTaskMonitor` (`:96`) and `ConversationStateManager` (`:113`). `import asyncio` (`:24`), used only
  by the deleted annotation, is removed. No other component gains a task registry.
- `REQ-002`: `ResourceShutdownCoordinator` reads the registry as a guaranteed field
  (`AgentContext.turn` is assigned at `context.py:320`), not through `hasattr`
  (`resource_shutdown_coordinator.py:119`). The snapshot-then-clear (`:121-122`), the cancel loop
  (`:129-130`), and the `asyncio.gather` join (`:132`) move into one private
  `async def _cancel_tracked_tasks() -> list[tuple[str, str]]`, called at the same position in
  `close_resources()` so `errors` keeps its current content and ordering.
- `REQ-003`: `BgTaskMonitor.on_task_done` handles every terminal state and never calls
  `Task.exception()` on a cancelled task: check `task.cancelled()` first, treat it as a reset
  (`consecutive_failures[task_name] = 0`, user decision in `DR-002`), otherwise read
  `task.exception()`. In every branch the task is discarded from the registry.
- `REQ-004`: the failure ladder is unchanged for a failed task — first failure logs a warning and calls
  `on_error` once; failures 2..`BG_FAILURE_THRESHOLD - 1` are silent; exactly the failure that makes the
  count `== BG_FAILURE_THRESHOLD` triggers `_notify_threshold_breach` once; later multiples-of-5
  repetitions log at error level without re-notifying; a `BaseException` that is not an `Exception`
  leaves the count unchanged; a successful task resets it to 0. This ladder moves unchanged into private
  methods. A two-way split is measured to leave the counting helper at radon `C (11)`, so the split is
  the three-way one that was measured: the counter arithmetic in `_count_failure()`, the first-failure
  report in `_report_first_failure()`, and the threshold/repeat report in `_report_threshold_failure()`
  (`on_task_done` `A (2)` plus three `A` helpers). Their parameters are typed `Exception`, because the
  call site gates on `isinstance(exc, Exception)`; typing them `BaseException` fails mypy against the
  `on_error: Callable[[Exception], None]` annotation (`bg_task_monitor.py:46`) at its call site (`:90`,
  measured).
- `REQ-005`: a clean cancellation produces no `task_cancellation` shutdown-error record, no
  `Resource close errors` summary line, and no asyncio `Exception in callback
  BgTaskMonitor.on_task_done()` error. The existing `task_cancellation` recording stays as the
  defensive branch for a task that surfaces a real failure while unwinding.
- `REQ-006`: the false claims are removed from the code's own text: the module docstring's
  "Cancelling pending tasks in LIFO order" line (`resource_shutdown_coordinator.py:7`), the class
  docstring's "LIFO (last-created-first-cancelled)" and "including a history-write task" example
  (`:41`, `:43-44`), and the inline comments at `:113-118` and `:128` state what a `set`-backed registry
  actually guarantees (no ordering) or nothing; the `TurnState.background_tasks` comment
  (`context.py:199`) states the registry's real lifetime. `reversed(pending_tasks)` at `:129` stays as an
  arbitrary-order reversal and is described as one.
- `REQ-007`: tests assert terminal-state behavior against real `asyncio.Task` objects. Every
  `MagicMock(spec=asyncio.Task)` task in `tests/agent/test_orchestrator_bg_failure_threshold.py` and
  every `_fake_task` use in `tests/agent/test_orchestrator.py::TestDiscardAndLogConsecutiveFailures` is
  replaced by a real task created on the running loop (`asyncio_mode = "auto"` is already configured).
  `test_resource_shutdown_coordinator.py::TestSelectiveTaskCancellation` (`:114-181`) asserts against real
  tasks in a real `TurnState` registry, and the guard test `test_no_turn_attribute_no_crash`
  (`:170-181`) is replaced by a test that an empty registry cancels nothing.
- `REQ-008`: the two documents named in `Documentation Impact` state the registry and its owner, the
  cancellation-and-reset policy, and the tracked-task step in the shutdown order the code actually
  performs.
- `REQ-009`: the questions the four Plans deferred to `turn005` are answered in this document — the
  dispatch-task question (`DR-003`), and the statement that `resource_shutdown_coordinator.py:113-137` is
  this Plan's to restructure. Those four Plans are implemented and archived under `plans/done/` and are
  not edited.

## Assumptions

- `TurnState` is process-lifetime state: `AgentContext.__init__` (`context.py:320`) is the only
  construction site and no code re-creates or clears it, so a registry living there lives for the process.
  Verified by `grep -rn "TurnState(" scripts/`.
- The session-title task is the only registered task today, so the registry holds at most one task at a
  time; every ordering claim in the coordinator is therefore untestable in production and is removed
  rather than implemented.
- A cancelled task is neither a failure nor a success, and a streak of failures is broken by it — the
  policy the existing (mock-based) tests already assert and that the user confirmed.
- `asyncio.gather(*tasks, return_exceptions=True)` returns a `CancelledError` instance for each cleanly
  cancelled task, and `CancelledError` is not an `Exception` (measured), so a clean cancellation cannot add
  an error record.
- Tests may use `async def` without a marker (`asyncio_mode = "auto"` in `pyproject.toml`).
- Real cancelled/failed tasks are reachable in tests without an LLM or a DB; no fixture beyond the
  existing `_make_ctx` / `_make_orchestrator` harness is required.

### One registry, three readers


  reads that object, the two constructor sites already accept an injected set, and the field already
  exists with the right type; the change is a deletion plus two re-pointed arguments. Measured working end

- `DR-004` (rejected): keep the Orchestrator's set as the registry and inject it into the coordinator.

- `DR-005` (rejected): make the registry insertion-ordered (list or dict) to make the documented LIFO

  tree. The claim is deleted instead (`REQ-006`).

### Why the callback is not total today

`on_task_done` (`bg_task_monitor.py:73-120`) reads `task.exception()` first. For a cancelled task that
call raises `CancelledError` instead of returning it, so the two bookkeeping lines at `:119-120` are never
reached and asyncio logs the callback failure. The `isinstance(exc, asyncio.CancelledError)` branch
(`:79-81`) is therefore dead for real tasks; it is reachable only through a mock. The fix is ordering, not
new logic: `task.cancelled()` first, `exception()` only otherwise, and the same
`_consecutive_failures[task_name] = count` / `self._tasks.discard(task)` pair at the end of every branch.
Keeping `isinstance(exc, asyncio.CancelledError) → 0` as the first guard of `_count_failure` preserves the
edge where a coroutine surfaces a `CancelledError` without the task being cancelled.

### Cancellation is not an error, and the error branch stays

`CancelledError` derives from `BaseException` (measured `issubclass(...) is False`), which is why the
coordinator's `gather(return_exceptions=True)` results filter (`isinstance(res, Exception)`) never records a
clean cancellation. `REQ-005` makes that a documented invariant rather than an accident, and `UNK-01`
records that after `REQ-003` the branch is defensive: the only way a failed task is in the registry at
shutdown is that it failed while being cancelled.

### Interaction with the done callback

Because the producer attaches `add_done_callback(self._on_discard)` (`conversation_state_manager.py:118`),
cancelling a task makes `on_task_done` run during the coordinator's `gather`. Snapshot-then-clear means the
registry is already empty at that moment, so the callback's `discard` is a no-op and no task is cancelled
twice. That ordering is part of `REQ-002` and is asserted by `T-1`.

## Risks

- **Risk**: making cancellation live changes what a user sees when a session ends during title generation —
  `ctx.session.set_title` (`services/session_title.py:59`) is not reached, so the session keeps its
  fallback title. **Mitigation**: today the same request is simply abandoned at loop close (measured
  `task.done() is False` after `close_resources()`), which is strictly worse: no cancellation cleanup, and
  an unretrieved task destroyed warning. The change also cancels before `http.aclose()`, so the HTTP
  request is unwound rather than destroyed. Documented in `agent_03_01`'s Known Limitations.
- **Risk**: the migration touches 17 tests in three files, one of them (`tests/agent/test_orchestrator.py`)
  shared with three other active Plans, and the temptation is to weaken an assertion to make it pass.
  **Mitigation**: `T-3` must pass against both the
  current and the changed code; every migrated test keeps its original counter and notification-count
  assertions, and only the way the task is produced changes. `check_mock_patch_targets.py` guards the patch
  targets.
- **Risk**: removing the `hasattr` guard makes the coordinator raise if a caller ever passes a
  context-shaped object without `turn`. **Mitigation**: the only two production callers are `repl.py:88`
  and the startup-failure path, both with a real `AgentContext`; the parameter is typed `AgentContext`
  (`resource_shutdown_coordinator.py:54-59`) and `context.py:320` guarantees the field. `test_repl.py`'s
  `ctx = MagicMock()` fixtures (`_make_bare_repl`, `:30-37`) keep working because `list(MagicMock)`
  iterates empty.
- **Risk**: `bg_task_monitor.py` grows as the ladder moves into three private helpers (6537 B today) and
  `close_resources` stays a `C` block. **Mitigation**: both files are far below the 20480 B module-size gate
  (`tools/check_module_size.py` reports no violation at this baseline); the measured net effect on
  `radon cc scripts/ -s -n C` is 3 findings in these files becoming 1 (`on_task_done` `C (11)` and
  `ResourceShutdownCoordinator` `C (12)` leave the report; `close_resources` `D (21)` → `C (15)`), and the
  residual is the WAL branch another Plan's landed code owns (`UNK-07`). No new public surface is added.
- **Risk**: a `Risks`-class surprise from `gather` semantics (UNK-01) — a task that fails while being
  cancelled may be recorded as a cancellation rather than as its own error. **Mitigation**: `REQ-005` only
  promises that a *clean* cancellation is not recorded; `UNK-01` records the rest instead of asserting it,
