## Goal
- Add a single, normative claim-type taxonomy to `docs/00_governance_01_documentation-policy.md` so canonical authority for a documentation/code conflict is determined by the type of claim and its decision target, not by a universal artifact-type ranking.

## Priority

## Scope

## Background
The current documentation uses three competing authority models at once: a universal ranking in `docs/00_governance_01_documentation-policy.md`'s "Canonical Source Precedence" table (Code > Tests > ADRs > Specifications > Configuration > Documentation); a "Decision Target Canonical Source Matrix" in the same document that assigns different canonical sources per decision target; and per-area "Canonical Source Rule(s)" sections in each area's `_00_document-guide.md` file. A fourth, related but distinct inconsistency exists in `docs/00_governance_04_documentation-checks.md` Manual Check 9, which states "the most recently reviewed document is authoritative among conflicting documents" — a recency-based rule not present in the other two models.

## Problem
None of the existing models can consistently resolve a case such as code contradicting an Accepted ADR: code describes current runtime behavior, while the ADR describes the adopted architectural decision, and both statements can be valid simultaneously for different claim types. Without a shared claim-type vocabulary, each area or reviewer may apply a different, undocumented authority model.

## Reason for change
A normative claim-type taxonomy is a prerequisite for `M-01-02` (replacing the universal ranking with target-based resolution), `M-01-03` (removing the document-recency rule), and the remaining `M-01` issues — none of them can define a consistent replacement rule without first agreeing on what a "claim type" is and which canonical source kind applies to it.

## Implementation intent
Add a new "Claim Type Taxonomy" section to `docs/00_governance_01_documentation-policy.md`, placed after the existing "Canonical Source Precedence" table and before "Decision Target Canonical Source Matrix" (so a reader encounters the new normative vocabulary immediately after the legacy ranking it will eventually replace). The section defines all 13 required claim types, a resolution matrix with the six required columns, and the required normative rules (claim-level analysis, authority-vs-evidence separation, multi-type-per-document allowance). A short cross-reference note is added to the existing "Canonical Source Precedence" table's introduction, marking it as pending replacement by `M-01-02` under the new taxonomy, so the two coexisting models are explicitly linked rather than silently contradictory during the transition.

## Requirements
- `REQ-001`: Add a normative definition for each of the 13 required claim types (`architecture-decision`, `functional-requirement`, `external-behavior`, `api-contract`, `runtime-behavior`, `verification-contract`, `production-effective-value`, `configuration-schema`, `database-schema`, `operational-procedure`, `security-policy`, `documentation-metadata`, `unconfirmed-claim`).
- `REQ-002`: Define the boundary between each pair of potentially overlapping claim types, at minimum between `architecture-decision`, `functional-requirement`, `runtime-behavior`, and `verification-contract`.
- `REQ-003`: Build the required resolution matrix (columns: Claim type, Definition, Canonical source kind, Auxiliary evidence, Conflict destination, Notes or constraints) covering all 13 claim types and encoding the 10 specific rules the issue enumerates (e.g. Accepted ADRs canonical for adopted architecture; source code canonical only for current runtime behavior; tests authoritative as executable verification, not as an automatic replacement for normative requirements; Needs Confirmation inventory canonical for active unconfirmed claims).
- `REQ-004`: Explicitly distinguish "authority" (the canonical source for a claim type) from "evidence" (auxiliary evidence permitted for that claim type) as separate, non-interchangeable concepts.
- `REQ-005`: State explicitly that a single document may contain claims of more than one type.
- `REQ-006`: Require conflict analysis at claim level, not whole-document level, and add the cross-reference note linking the existing whole-document "Canonical Source Precedence" table to the new taxonomy as its pending replacement (`M-01-02`).
- `REQ-007`: Ensure claim-type terminology introduced by this taxonomy is used consistently within the new section (no mixed vocabulary between the new resolution matrix and its own definitions).

## Design
This Plan adds one new `##` section, "Claim Type Taxonomy", positioned between the existing "Canonical Source Precedence" (`##`) and "Decision Target Canonical Source Matrix" (`###`, currently a subsection of "Canonical Source Precedence") headings. The new section is a peer `##` heading, not nested under "Canonical Source Precedence", since it introduces a distinct, forward-looking model rather than elaborating the legacy ranking.

Structure of the new section:
1. A short introductory paragraph stating the taxonomy's purpose (claim-level, not document-level, canonical-source resolution) and that it supersedes the whole-document "Canonical Source Precedence" ranking once `M-01-02` completes the replacement (explicit forward cross-reference, satisfying REQ-006's "not silently contradictory" requirement).
2. 13 claim-type definitions, each as its own `####` subsection or a definition-list entry, naming: the claim type; its normative definition; its boundary against the nearest overlapping type(s) (only for the four types the Issue calls out: `architecture-decision`, `functional-requirement`, `runtime-behavior`, `verification-contract` — REQ-002).
3. The six-column resolution matrix (REQ-003) as a single Markdown table, one row per claim type, encoding the 10 specific rules the Issue lists verbatim in its matrix rules (Accepted ADRs canonical for adopted architecture; Canonical Specifications authoritative for normative functional requirements; official API schemas/contracts authoritative for external interfaces; source code canonical only for current runtime behavior; tests authoritative as executable verification only; deployed configuration canonical for effective production values; configuration schemas canonical for valid configuration structure; official DDL/schema generators canonical for DB schema; Operations documents/runbooks canonical for operator procedures; Needs Confirmation inventory canonical for active unconfirmed claims).
4. A short "Authority vs. Evidence" note (REQ-004) stating the canonical source kind column is authority, the auxiliary evidence column is evidence, and the two are never interchangeable.
5. A short "Multi-Type Documents" note (REQ-005) stating a single document may carry claims of more than one type, and readers/reviewers must classify by claim, not by the document as a whole (REQ-006).
6. A one-sentence cross-reference note appended to the existing "Canonical Source Precedence" table's introduction (immediately before its table), stating that this table is pending replacement by the Claim Type Taxonomy above per `M-01-02`, and that new authority questions should consult the taxonomy first.
