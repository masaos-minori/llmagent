# Plan: StartupValidationPipeline avoids blocking thread pool on RAG consistency check

## Goal
- Ensure `StartupValidationPipeline.check_services()` does not block the thread pool during RAG consistency checks, enforces a timeout, and reuses the `RagMaintenanceService` instance.

## Priority
Medium

## Scope
- **In-Scope**: Add timeout to RAG consistency check; reuse `RagMaintenanceService` instance instead of creating per-call
- **Out-of-Scope**: Changes to `RagMaintenanceService.consistency()` internal logic; changes to the validation pipeline order

## Background
`StartupValidationPipeline.check_services()` in `scripts/agent/startup_validation.py` runs multiple validation checks sequentially. The RAG consistency check is executed in the default executor thread pool.

## Problem
`RagMaintenanceService().consistency()` is a synchronous operation run in the default executor thread pool. If this operation is slow (e.g., scanning large RAG indices), it blocks a thread in the limited thread pool. Since the default executor uses a bounded number of threads, this can stall other async operations. Additionally, the lambda creates a new `RagMaintenanceService` instance each time, which may have side effects (opening database connections) that aren't cleaned up if the operation fails.

## Reason for change
Thread pool exhaustion during startup is a reliability concern. Slow RAG consistency checks can delay startup and affect other async operations. Resource leaks from unclosed database connections compound the problem.

## Implementation intent
Add a timeout parameter to prevent indefinite blocking. Reuse an existing `RagMaintenanceService` instance rather than creating one per call. Consider making `consistency()` async in a future iteration.

## Requirements
- `REQ-001`: RAG consistency check does not block the thread pool indefinitely
- `REQ-002`: Timeout enforced on the RAG check operation
- `REQ-003`: Test verifies no thread pool starvation under concurrent startup
- `REQ-004`: Test verifies timeout behavior

## Design
### Current Behavior (Verified Against Source)
1. `startup_validation.py` line 128-145: RAG consistency check without timeout
2. Line 130-133: `loop.run_in_executor(None, lambda: RagMaintenanceService().consistency())` — new instance per call, no timeout
3. `rag_maintenance_service.py` line 46-54: `consistency()` opens SQLite connection, runs check, returns result
4. No explicit cleanup of `RagMaintenanceService` instance — relies on GC for cleanup

### Proposed Change
```python
# 6. RAG consistency
try:
    loop = asyncio.get_running_loop()
    rag_service = RagMaintenanceService()
    rag_check = await asyncio.wait_for(
        loop.run_in_executor(
            None,
            rag_service.consistency,
        ),
        timeout=30.0,
    )
    if rag_check.is_consistent:
        pipeline.add_ok("rag_consistency")
    else:
        for issue in rag_check.issues:
            pipeline.add_warning(
                "rag_consistency", f"[RAG] Consistency issue: {issue}"
            )
except TimeoutError:
    logger.warning("RAG consistency check timed out after 30.0s")
    pipeline.add_skipped(
        "rag_consistency", "RAG consistency check timed out"
    )
except Exception as exc:  # noqa: BLE001 — non-critical maintenance check must not abort startup
    logger.warning("RAG consistency check failed: %s", exc)
    pipeline.add_skipped(
        "rag_consistency", f"RAG consistency check skipped: {exc}"
    )
```

Key changes:
1. Extract `RagMaintenanceService()` outside the lambda — reuse instance
2. Wrap `run_in_executor()` with `asyncio.wait_for(timeout=30.0)` — enforce timeout
3. Handle `TimeoutError` separately with appropriate log message
