# Fix greedy regex JSON extraction in MQE and rerank score parsing

## Goal
Replace the greedy, `re.DOTALL`-flagged bracket/brace regex patterns in
`_parse_mqe_response()` and `_apply_rerank_scores()` with non-greedy, no-nested-bracket
patterns that extract only the innermost JSON structure, so LLM output containing
brackets/braces outside the JSON data does not silently cause a spurious parse failure
and fallback.

## Priority
Medium

## Scope
- **In-Scope**: Replacing the two regex patterns in `_parse_mqe_response()` and
  `_apply_rerank_scores()` (`scripts/rag/llm_prompts.py`) and removing the now-unneeded
  `re.DOTALL` flag from both
- **Out-of-Scope**: Support for multi-line/nested JSON extraction (would require a
  proper JSON-parser-based approach, e.g. `json.JSONDecoder.raw_decode()` — the Issue's
  own Unresolved Questions flags this as a separate, more complex concern); changes to
  how fallback is triggered when no JSON is found; changes to `orjson` parsing itself

## Background
`_parse_mqe_response()` (`llm_prompts.py:148`) and `_apply_rerank_scores()`
(`llm_prompts.py:189`) each use a greedy regex with `re.DOTALL` to locate a JSON
array/object inside raw LLM output:
```python
m = re.search(r"\[.*\]", raw, re.DOTALL)   # _parse_mqe_response
m = re.search(r"\{.*\}", raw, re.DOTALL)   # _apply_rerank_scores
```

**Re-verified 2026-09-13** (this cycle): the Issue's cited patterns
(`r"\[\d.*\d\]"` / `r"\{\d.*\d\}"`, with digit boundaries) do not match the actual
source — the real patterns (`r"\[.*\]"` / `r"\{.*\}"`) have no digit-boundary
requirement, making them even more permissive than the Issue described. Reproduced
directly:
```python
>>> re.search(r"\[.*\]", '[Query 1: What is X?]\n[Query 2: How does Y work?]', re.DOTALL).group()
'[Query 1: What is X?]\n[Query 2: How does Y work?]'
```
The greedy `.*` with `re.DOTALL` spans from the first `[` to the last `]` in the
entire input, so any content containing multiple bracket/brace pairs (LLM commentary
with bracketed references, multiple JSON-like fragments, etc.) is captured as one
string that fails `orjson.loads()` and triggers a fallback (`MqeParseError` /
`None` return) even when a valid, extractable JSON structure was present.

Confirmed the proposed fix pattern (`r"\[[^\]]*\]"`) both rejects the multi-bracket
case above (extracts only the first `[...]`) and correctly extracts a well-formed
array from realistic input (`'Here are the queries: ["query one", "query two"]'` →
`["query one", "query two"]`, parses via `orjson.loads()`).

No existing unit test directly exercises `_parse_mqe_response()` or
`_apply_rerank_scores()` (checked `tests/rag/test_rag_pipeline_stage.py`,
`tests/rag/test_stage_observability.py`, `tests/rag/test_rag_stages.py` — none call
these functions directly; existing coverage is indirect via
`RagLLM.expand_queries()`/`cross_encoder_rerank()` with mocked LLM output).

## Problem
When LLM output for MQE expansion or rerank scoring contains bracket/brace characters
outside the actual JSON payload (e.g. bracketed citations, multiple separate JSON-like
fragments), the greedy `re.DOTALL` regex captures from the first opening character to
the last closing character in the entire response, producing a string that is not
valid JSON and silently triggering fallback — degrading MQE expansion or reranking
quality without any indication to the caller that extraction, not the LLM call itself,
failed.

## Reason for change
Use a non-greedy character-class pattern that matches only the innermost
bracket/brace pair, so the extraction correctly isolates a well-formed JSON
array/object even when surrounding text or multiple bracket/brace pairs are present in
the raw LLM output.

## Implementation intent
1. In `_parse_mqe_response()`: replace `r"\[.*\]"` (with `re.DOTALL`) with
   `r"\[[^\]]*\]"` (no `re.DOTALL` needed)
2. In `_apply_rerank_scores()`: replace `r"\{.*\}"` (with `re.DOTALL`) with
   `r"\{[^{}]*\}"` (no `re.DOTALL` needed)
3. No other logic change — fallback behavior when no match is found is unchanged

## Requirements
- `REQ-001`: `_parse_mqe_response()` must extract only the innermost `[...]` JSON
  array, not span across multiple bracket pairs
- `REQ-002`: `_apply_rerank_scores()` must extract only the innermost `{...}` JSON
  object, not span across multiple brace pairs

## Design
This task is classified as **Path A** (small task): affects 1 file, no public interface
changes, no database schema changes.

This cycle's re-verification found the Issue's core technical claim accurate (though
its cited regex text was itself inaccurate) and reproduced the failure mode directly —
this is a genuine latent bug, similar in nature to `diag001` from the same review
batch (accurate core claim, inaccurate supporting detail).

Key design decisions:
1. Use a character-class-exclusion pattern (`[^\]]`/`[^{}]`) rather than a
   fully general JSON-aware parser (e.g. `json.JSONDecoder.raw_decode()`) — the
   Issue's own Unresolved Questions correctly identifies the general approach as
   more complex; the flat-array/flat-object payload shapes here don't need it (see
   Assumptions)
2. Drop `re.DOTALL` from both calls — it is no longer needed once the pattern itself
   excludes the closing delimiter, and keeping it would not change behavior since the
   new patterns don't use `.` at all

## Risks
- **Risk**: The new pattern cannot match a JSON array/object containing nested
  brackets/braces (e.g. `[[1,2],[3,4]]` or `{"a": {"b": 1}}`) → **Mitigation**: confirmed
  neither MQE's flat string-array payload nor rerank's flat score-map payload requires
  nested structures (see Assumptions); if a future prompt template changes this shape,
  this restriction would need re-evaluation, but that is outside this Plan's Issue-driven
  scope
- **Risk**: Removing `re.DOTALL` could theoretically change behavior for JSON containing
  literal newlines inside string values → **Mitigation**: the new patterns exclude `]`/`{`/`}`
  characters, not newlines — a newline inside a JSON string value is still matched by
  `[^\]]`/`[^{}]` since it is not one of the excluded characters, so multi-line JSON
  *values* within a single well-formed array/object are still handled correctly
