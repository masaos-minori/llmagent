## Problem
`check_port_drift()` and `check_port_range_claim()` currently operate on the
premise that `docs/*.md` files legitimately state port numbers and that the
check's job is to catch when a stated number drifts from the real
configuration. Under the new policy, the correct end state for most of these
files is that the port number is removed entirely, not merely kept accurate.
Left unreconciled, these two checks would continue enforcing accuracy of
content the new policy says should not exist — an internal contradiction in
this repository's own governance tooling.

**Corrected during this Plan's Step 2/3 adversarial verification**: the
source Issue's Testing Expectations assumes "existing unit tests for
`check_port_drift()`/`check_port_range_claim()`" exist and need updating or
removing. Repository-wide search (`grep -rln "check_port_drift\|check_port_range_claim" tests/`)
found no dedicated unit test file for either function — the closest
candidate, `tests/tools/test_check_agent_docs_consistency.py`, contains zero
`test_*` functions. There is no existing test suite to update; if the chosen
option changes either function's behavior, this Plan must add new tests
rather than modify existing ones.

## Reason for Change
Leaving `check_port_drift()`/`check_port_range_claim()` unreconciled would
mean the repository simultaneously tells writers "do not document port
numbers" (new policy) and "keep documented port numbers accurate" (existing
check) — a direct contradiction that would confuse both human writers and any
future automation relying on either signal being authoritative.

## Implementation intent
Using the sibling detection-tool Plan's violation inventory as evidence once
available, choose one of: (a) deprecate `check_port_drift()`/
`check_port_range_claim()` entirely once the corresponding `docs/*.md` files
no longer state port numbers; (b) narrow their scope to only the files the
new policy explicitly exempts (e.g. a worked example explicitly labeled
illustrative, per `skills/DESIGN.md` "No concrete configuration values"'s
carve-out); or (c) leave them active pending a documented, explicit
exemption list, if the content-migration follow-up work has not yet landed.

**Provisional evidence-based direction (subject to re-verification once the
violation inventory lands — see Unknowns)**: as of this Plan's creation, no
`docs/*.md` content has been migrated away from stating port numbers (the
content-migration follow-up this Plan explicitly excludes from its own
scope, per Out-of-Scope, has not started), so option (a)'s precondition
("no longer state port numbers") and option (b)'s precondition (a confirmed,
finite exempt-file list) cannot yet be satisfied — only option (c) matches
the current repository state. This is a provisional reading pending the
actual violation inventory, not a final decision — see Unknowns and Phase 2
below.

Record the chosen option and its rationale directly in
`docs/00_governance_04_documentation-checks.md`'s existing description of
these checks, so the decision is visible alongside the checks themselves.

  would silently stop catching real port-configuration drift in files that

  ("no longer state port numbers") is checked explicitly in Phase 2 against
  the actual inventory, not assumed.
