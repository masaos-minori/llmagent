## Background
ADR-001 and ADR-008 define a mandatory approval stage after `execute` and persist pending approvals in `workflow.sqlite`. The source Issue (derived from `memo2.md`) was verified adversarially against code, DB, ADRs, docs, and checkers, then its open questions were investigated. Production currently runs an older loader with `require_approval: false`, so the gate is disabled there today; deploying the repository state without this change would enable it. This Plan re-checks the Issue's claims below and was itself reviewed against the file inventory produced by a repository-wide search (90 target files).

## Problem
- The gate cannot stop an operation: every Tool of the turn has already run when it is reached (`workflow_engine.py` stage order), and rejection only marks the task `halted`.
- Nothing runs only after approval (`verify_fn` only emits `turn_end` and clears the turn ID), and `/approve` does not resume anything (`pending_approval_task_id` is never read to resume).
- A pending approval blocks every write (`repository_gateway.py:98-111`) and the next turn (`orchestrator.py:160-161`) and needs persistent state, startup recovery, and expiry handling.
- A per-turn approval trains operators to approve without reading, weakening tool-level approval.

## Reason for change
Approval belongs where it can prevent an operation, before a Tool runs. Removing the post-execution stage removes dead and blocking behavior, one table, one recovery path, and operator burden, and makes the already-deployed no-gate behavior the documented one.

## Implementation intent
Record the owner's decision first (Step 1), then land the code, migration, deploy scripts, tests, docs, and ADR text as one commit unit, as the ADR Change Protocol requires. Keep the tool-level approval path and every name on the keep list. Guard reintroduction with unregistered-command tests, an INV-10 loader-rejection test, and `COMPAT_PATTERNS` entries for code identifiers only, added last so the guard never fires on a half-removed tree.

## Design
Path B (90 target files). Findings:
- Architecture: the gate spans the Workflow Engine, the adapter, the orchestrator, the write gateway, the startup sequence, the CLI views, and the DB; tool-level approval is a separate path (`tool_policy`, `tool_approval`) and stays. `lint-imports` reports 6 contracts kept at baseline; removing modules does not add imports.
- Dependency graph: 22 gate-code files, 25 test files (4 deleted wholesale: 49 tests; the startup recovery file is split: 12 approval tests removed, 16 MCP tests moved), 29 documents, 4 ADR files. The keep list is `ApprovalDecisionType`, `ApprovalDecisionEvent`, `audit_approval`, `log_approval_decision`, `OutputTag.APPROVAL`, `require_approval_for`, `WorkflowHaltError`, `WorkflowTimeoutError`, and the `halted` status.
- Behavior after the change: the engine stage order is plan, execute, verify; `verify` keeps emitting `turn_end` and clearing the turn ID; a rejected task state no longer exists; `halted` remains for retry exhaustion and timeout.
- Migration: `_WORKFLOW_MIGRATIONS` entries hold one statement each and run on every `create_workflow_schema()`; add the UPDATE entry first and the DROP entry second, and bump `WORKFLOW_SCHEMA_VERSION` from 1.0.0. The startup check compares the latest version row, so new and old databases both converge. Nothing references `approvals` (no foreign key, view, or trigger).
- Production state (read-only): the production loader and `default.json` predate the mandatory-true loader and disable the gate; the production `workflow.sqlite` has schema 1.0.0, 2 tasks (completed, running), 1 approved approval row, and no pending task, so the UPDATE changes 0 rows and the DROP deletes 1 historical row.
- Deployment: `deploy.sh` validates and copies `config/workflows/`; `init_db.sh` must run before `setup_services.sh` because the latter fails on a table or version mismatch; both scripts list `approvals` as required today.
- Historical: single maintainer; churn is high in `agent_03_03`, `governance_03`, `registry.py`, and the ADRs, so fetch and rebase before the docs and ADR steps. Another work item edits `governance_03` (EVENTBUS-008 procedure documents); sequence the ledger edit after that cycle.
- Test isolation hazard (found by a trial removal in an isolated worktree): the four `*_schema_timestamps` tests in `tests/db/test_create_schema.py` patch only the DDL builder, so `create_workflow_schema()` runs against the real `/opt/llm/db/workflow.sqlite`; the trial's full-suite run applied the new migrations to production (`approvals` dropped, version 1.1.0 recorded, tasks unchanged, no backup). Before the new entries the call was idempotent and harmless; with the UPDATE and DROP entries it is destructive. The rag, session, and eventbus tests of the same file share the pattern.
- Trial removal results: all code, test, DB, deploy, config, compat, and checker steps passed in the trial (only the 8 baseline failures remained). Not covered by the original target list: `test_workflow_stage_persistence.py` (its migration test builds a database without `tasks`), `overview_01_03` (stage list), and the non-approval tests inside `test_startup_approval_recovery.py` and `TestWorkflowEngineApprovalExpiry`.
- Pending work items touching the same files: the EVENTBUS-008 procedure edits `governance_03`, and the agmask01 procedure edits `agent_10_01` lines 96-98; apply those first or re-cite lines at procedure time.
- Validation baseline (pre-existing, not fixed here): 8 failing eventbus tests (`test_eventbus_subscribe.py` 7, `test_eventbus_dlq_pagination.py` 1) after the EVENTBUS-008 change; `--check-removed-names` reports 2 findings; `check_docs_structure.py` and the other checkers pass.
- Checker constraints measured: ADR-008 is 33636 bytes against a 33647-byte ceiling and the edits save 130 bytes, leaving 141 bytes for the `Decision Change` line; ADR-001 (17381 bytes) and ADR-014 (15665 bytes) are under the 24576 limit; `check_adr_invariant_matrix.py` only checks that cited test files exist, so the INV-11 row must cite an existing file such as `tests/agent/test_tool_audit.py`; index rows must cite tests only because `scripts/` files lack the ADR reference.

## Risks
- **Risk**: A file outside the 90 targets references a removed name (the `/skill` and `/mdq` removals each exposed one) → **Mitigation**: the target list comes from a repository-wide search; the full suite runs once after Steps 2-10, and any extra file is reported as an additional target before editing.
- **Risk**: Implementation starts before the owner decision is recorded, leaving ADR text and code inconsistent → **Mitigation**: Step 1 is an explicit gate and every ADR procedure names the decision as its precondition.
- **Risk**: `approvals` stays in `REQUIRED_WORKFLOW_TABLES`, so startup or deploy aborts after the drop → **Mitigation**: those three places are targets and the production-copy check in Step 12 exercises the startup and deploy checks.
- **Risk**: The loader inversion rejects a deployed definition that still has the key → **Mitigation**: `deploy.sh` copies the repository definition and validates it first; Step 12 verifies the deployed file.
- **Risk**: A migration with two statements in one entry aborts startup → **Mitigation**: two entries, UPDATE first, DROP second; both are idempotent and tested twice.
- **Risk**: Deleting `ApprovalDecisionType` or other tool-level names by pattern → **Mitigation**: the keep list is part of Scope and the `COMPAT_PATTERNS` entries use identifiers only; the guard test includes tool-level negative samples.
- **Risk**: The ADR-008 edit exceeds the size ceiling → **Mitigation**: the new line is limited to 141 bytes; `check_docs_structure.py` is run after the edit.
- **Risk**: High-churn documents or the ledger conflict with concurrent work (EVENTBUS-008 procedures also edit `governance_03`) → **Mitigation**: fetch and rebase before Step 9, edit by section, and apply the ledger edit last.
- **Risk**: Removing `approval_events` or the recovery code hides a diagnostics consumer → **Mitigation**: `rg` shows its only reader is `session_persister.py`; `docs` for the key are updated in the same step.
- **Risk**: The 8 pre-existing eventbus failures mask a new regression → **Mitigation**: compare failing test names to the baseline list; any other failure is new.
- **Risk**: Tests write to the production databases (the trial full-suite run already migrated production) → **Mitigation**: fix the four unpatched schema tests first (the `test_create_schema.py` row), compare database modification times around every test run, and run schema tests against temporary databases only; UNK-05 records the decision to leave production as is.
