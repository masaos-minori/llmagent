## Problem
`test_ack_event_principal_ownership_validation` fails: an ACK request with a `consumer_id` not owned by the calling principal returns `200` instead of the expected `403`/`409`. The resolved `Principal.allowed_consumer_ids` is `None` at the ownership-check call site in `_do_ack`, not the fixture's configured `frozenset({"consumer-A"})`.

## Reason for change
The failing test asserts an authorization boundary (a `403` for an unowned `consumer_id`). The current fixture state makes that boundary unreachable, so the test passes trivially by returning `200` while asserting `in (403, 409)` only because the assertion itself is wrong-shaped for the broken state. The fix restores the precondition the test depends on.

## Implementation intent
Investigate how `_principal` is resolved for the `/events/{event_id}/ack` route and confirm why `allowed_consumer_ids` does not carry through to the `Principal` instance `_do_ack` receives. Root-cause the resolution rather than loosening the test's expected status codes. Apply the narrowest fix that makes the restriction propagate to the request-time principal.

## Design
Root cause (confirmed by repository evidence, not the issue's own claim):

1. `resolve_principal()` in `auth.py` looks up `_TOKEN_PRINCIPAL_MAP[token]` and returns a new `Principal` copying `roles`, `allowed_consumer_ids`, `allowed_topics`, and `token_fingerprint`. So whatever is in the map at request time is what `_do_ack` sees.
2. `_populate_token_maps()` in `auth.py` calls `_TOKEN_PRINCIPAL_MAP.clear()` and repopulates from config on every invocation. With no `consumer_authorization` configured, the consumer token is populated with `allowed_consumer_ids=None` (unrestricted).
3. The `principal_client` fixture builds its config, calls `_populate_token_maps(cfg)`, then overwrites `_TOKEN_PRINCIPAL_MAP["consumer-token"]` with `allowed_consumer_ids=frozenset({"consumer-A"})` — but it does this BEFORE entering `with TestClient(eb_app.app) as c:`.
4. Entering the `TestClient` context triggers the FastAPI lifespan (`app.py`), which calls `_populate_token_maps(app.state.config)` again, wiping the fixture's override and resetting `allowed_consumer_ids` to `None`.
5. At request time the resolved principal therefore has `allowed_consumer_ids=None`, so `_do_ack`'s `and _principal.allowed_consumer_ids` guard is falsy and the ownership check is skipped → `200`.

Git history confirms this is a regression: commit `3bd5b9d0` ("fix principal_client token override race") placed the override INSIDE the `TestClient` block with a comment explaining exactly step 3–4; commit `aea575fe` ("resolve merge conflict") deleted that in-block block, leaving only the pre-context override.

Why the fix works: re-applying the override inside the `TestClient` context runs AFTER the lifespan's `_populate_token_maps()`, so nothing clears it before the request. This is the minimal change that makes the restriction propagate to the request-time principal without touching production code.

Verification performed during planning (read-only reproduction under `/tmp`, since deleted): feeding the exact fixture sequence showed `allowed_consumer_ids=None` after context entry, and re-applying the override inside the block restored `frozenset({'consumer-A'})`. Baseline: `uv run pytest tests/eventbus/test_eventbus_ack_endpoint.py` = 1 failed (`test_ack_event_principal_ownership_validation`), 9 passed.

Known related gap (out of scope, `UNK-01`): `load_config()` in `config.py` constructs `EventBusConfig(...)` without passing `consumer_authorization`/`topic_authorization`, so those TOML keys never reach the config object and consumer/topic restrictions never take effect in production even when configured. This is a separate concern from the fixture ordering bug and is explicitly excluded from this Plan.
