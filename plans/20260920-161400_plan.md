## Goal
Add `"fail-safe"`, `"fail-closed"`, and `"fail-open"` to
`tools/check_docs_content_policy.py`'s `_RATIONALE_MARKERS` allowlist so
`check_default_value_restatement()` stops flagging security-boundary/fail-safe-default
sentences as mechanical content to remove, while continuing to flag genuine
default-value restatements that lack a rationale marker.

## Priority
Low

## Scope
- **In-Scope**: extending `_RATIONALE_MARKERS` with the three new marker strings, and
  adding/extending a test covering the new markers.
- **Out-of-Scope**: any other `check_docs_content_policy.py` detection function
  (`check_literal_port_number`, field/type table detection, etc.); re-running or filing
  the `docs/05_agent_06_02`/`05_agent_06_03` documentation cleanup itself (those files
  require no edit — this Plan only stops the tool from flagging them); auditing the
  full corpus for other possible marker gaps beyond fail-safe/fail-closed/fail-open.

## Background
While investigating `docs/00_governance_01_documentation-policy.md` Docs content
policy findings for a separate cleanup issue (now
`plans/20260920-160327_plan.md`, generated earlier in this same batch), three findings
were confirmed to be false positives: sentences stating a fail-safe default (e.g.
"Fail-safe: Undefined tools in `tool_safety_tiers` default to `WRITE_DANGEROUS`")
inside `## Key Constraints` sections. `skills/DESIGN.md` Docs content policy — retain
explicitly protects "security boundary ... fail-closed/fail-open default judgment"
content; the checker's `_RATIONALE_MARKERS` docstring already states its intent is to
skip exactly this kind of "explaining *why* a default was chosen" content, but its
marker list did not include the "fail-safe"/"fail-closed"/"fail-open" vocabulary this
project's own documents actually use for that purpose.

## Problem
`check_default_value_restatement()` in `tools/check_docs_content_policy.py`
(`_RATIONALE_MARKERS` defined at line 58, re-confirmed 2026-09-20) flags any line
matching `` `x` defaults? to `y` `` that lacks one of its current rationale markers.
Confirmed false-positive findings from a 2026-09-20 tool run, re-confirmed still
current during this Plan's Step 2:
- `docs/05_agent_06_02_tool-execution-and-approval-approval.md:46`, `:117`
- `docs/05_agent_06_03_tool-execution-and-approval-concurrency-safety.md:86`

All three are `## Key Constraints` bullets labeled "Fail-safe:" — design-intent content
per Docs content policy — retain, not mechanical restatement. A genuine finding this
change must continue to flag was also re-confirmed still present:
`docs/00_governance_03_issue-and-uncertainty-management.md:451`.

Step 3's direct verification additionally confirmed `tests/tools/test_check_docs_content_policy.py`
exists and already contains two directly relevant test cases:
`test_default_value_restatement_detected` (asserts a plain restatement is flagged) and
`test_default_value_restatement_not_flagged_with_rationale` (asserts a `because`-marked
restatement is not flagged) — the new test case this Plan adds should follow the same
pattern.

## Reason for change
Without this fix, every future `check_docs_content_policy.py` run keeps re-flagging
legitimate, already-reviewed fail-safe-default documentation as a warning, creating
noise that makes genuine new findings harder to spot and risks a future cleanup issue
mistakenly deleting this content (as almost happened while drafting the source Issue
for `plans/20260920-160327_plan.md`, before manual investigation caught it).

## Implementation intent
Extend `_RATIONALE_MARKERS` (a `frozenset[str]`) with the three missing terms. Keep the
existing conservative, substring-match design — no new regex or control flow is needed,
only additional marker strings, per the function's own documented intent.
