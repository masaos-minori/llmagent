# Plan: Define workflow-level `require_approval` production policy and lifecycle

## Goal

production default in `docs/05_agent_03_03_turn-processing-flow-workflow-engine.md` by stating an
explicit, decided policy: a per-operation-category approval-requirement table, documented
local-development exceptions, a fully specified approval lifecycle (approve / reject / expire /
missing / cancel / resume), and config enforcement — plus the minimal code change needed to make
the expiration behavior actually work as documented.

## Design

### 1. Production policy for `require_approval` (resolves the Needs-Confirmation note)

Decision: **category-conditional**, not a blanket `true`/`false`. Rationale:
- A blanket `require_approval=true` would pause *every* task after execute, including read-only
  and low-risk workflows, which contradicts the "自動実行" (no-human-gate) category already
  established in ADR-001 for low-risk operations.
- A blanket `false` (today's default) leaves high-impact categories (shell execution, git
  push, GitHub writes, CI/CD triggers) with no workflow-level gate at all in production — this is
  the actual gap the requirement is pointing at.
- The existing `WorkflowDef.require_approval` is a single boolean per *workflow definition*, not
  per operation category. Since `config/workflows/default.json` is the one workflow definition
  currently deployed, category-conditional enforcement for this plan means: **document that a
  production deployment whose default workflow's execute stage can perform any category marked
  "Yes" or "Conditional" below MUST set `require_approval: true` in its `config/workflows/*.json`,
  or use a per-environment override file** (this plan documents the override path; it does not
  invent a new per-category runtime flag inside `WorkflowDef` — that would be a larger schema
  change outside this plan's "small change" budget).
- Stated explicitly in the doc (replacing "Needs Confirmation"): *"Production deployments whose
  default workflow can reach any `require_approval: yes` category below MUST set
  `require_approval: true` in the deployed `config/workflows/*.json`. The bundled
  `config/workflows/default.json` ships `require_approval: false` because it is also used for
  local development; per-environment override files (e.g.
  `config/workflows/production.json`, selected via the existing workflow-name/version loading
  path in `workflow_loader.py`) are the documented mechanism for production to opt in without
  changing the local-dev default."*

### 2. Operation-category → workflow-level approval mapping

| Category | Workflow-level approval | Tool-level risk tier (cross-link) | Notes |
|---|---|---|---|
| File writes | Conditional | `WRITE_SAFE` (`docs/04_mcp_05_03_...`) | No workflow-level gate required by default; required only if the workflow's execute stage also performs a category marked "Yes" in the same task (batch decision applies to the whole execute-stage result, not per-tool-call) |
| File deletion | Yes | `WRITE_DANGEROUS` | Workflow-level gate required in production |
| Shell execution | Yes | `WRITE_DANGEROUS` | Workflow-level gate required in production |
| Git commits/pushes | Yes | `WRITE_SAFE` (commit) / `WRITE_DANGEROUS` (push, checkout, pull) | Gate required whenever the execute stage includes a push; commit-only workflows may rely on tool-level gate alone |
| GitHub changes | Yes | `WRITE_DANGEROUS` (`github_push_files`, merge) / `medium`-tier creates | Gate required for merge/push; conditional for issue/PR creation |
| CI/CD execution | Yes | `WRITE_DANGEROUS` (`trigger_workflow`) | Gate required in production |
| Database maintenance | **Gap — flagged, not filled** | None exists | No MCP tool or risk-tier entry exists for DB maintenance today; this plan documents the gap explicitly per the requirement's instruction rather than inventing a tool or tier. Workflow-level policy for this category cannot be enforced until a DB-maintenance tool exists; documented as "N/A — no execution path exists yet." |

### 3. Local-development exceptions

Document, distinctly from the tier-validation severity rules in `docs/04_mcp_05_03_...`
(which govern missing `tool_safety_tiers` entries, not this gate): local/development deployments
(`MCPConfig.security_profile == LOCAL`) MAY leave `require_approval: false` for all categories,
including those marked "Yes" above, because tool-level pre-execution approval remains active
regardless and is deemed sufficient friction for local iteration. This mirrors the existing
local/production distinction already used for `tool_safety_tiers` validation severity.

### 4. Lifecycle: approve / reject / expire / missing / cancel / resume

- **Approve**: unchanged, existing `/approve` behavior (`cmd_workflow.py:136-162`) — resolves to
  `approved`, workflow resumes on next turn via `_gate_approval()`'s `existing.status == "approved"`
  branch.
- **Reject**: unchanged, existing `/reject` behavior — resolves to `rejected`, task halted
  immediately by `after_resolve` callback, and defensively again by `_gate_approval()`.
- **Missing** (no approval record yet): unchanged — `_gate_approval()` creates one via
  `request_approval()` and raises `WorkflowPendingApprovalError`.
- **Expire** (new behavior, code change): when `_gate_approval()` finds an existing record with
  `status == "pending"` and `expires_at` in the past, it must not re-raise indefinitely. New
  behavior: mark the stale record accordingly (either update its status to `"expired"` via a
  small addition to `approval_ops.py`, or simply treat it as absent and call `request_approval()`
  again — **decision: update status to `"expired"` for audit-trail completeness**, then call
  `request_approval()` to create a fresh pending record, and raise
  `WorkflowPendingApprovalError` for the new one). Document: "an expired approval is
  automatically re-requested on the next turn the task is evaluated; the operator sees a new
  approval id and must re-approve."
- **Cancel**: **decision: unsupported by design.** Document explicitly: "`/cancel` does not
  exist and is not planned; `/reject` is the sole way to terminate a pending workflow-level
  approval. This keeps the approval status space small (`pending`/`approved`/`rejected`/
  `expired`) and avoids a fourth terminal state whose semantics would overlap with `rejected`."
  This also avoids reopening the "three-category" complexity that
  `decisions/20260819_three_category_separation_decision.md` already rejected.
- **Resume**: unchanged — next turn's `WorkflowEngine.run()` re-evaluates `_gate_approval()`,
  which now additionally handles the expired case as above.

### 5. Config enforcement

`config/workflows/default.json` keeps `require_approval: false` (local-dev-compatible default,
per §3). The plan documents — but does not implement — a per-environment override file
convention (`config/workflows/production.json` or similar), since no such loader switch
currently exists; implementing an environment-selection mechanism for workflow definitions is
flagged as a follow-up, not built in this cycle (see Risks).

## Risks

- **Risk**: Expanding `ApprovalRecord.status` to include `"expired"` could break any caller that
  assumes only `pending|approved|rejected` (Likelihood: low — only `_gate_approval()`,
  `cmd_workflow.py`, and tests read `.status`, all checked in Step C reading above) →
  **Mitigation**: grep all `.status ==` / `status=` usages on `ApprovalRecord` before merging the
  code change; update any exhaustive-looking conditionals.
- **Risk**: Documenting a "per-environment override file" convention without implementing an
  environment-selection loader leaves a documentation/capability gap of its own (the doc would
  describe a mechanism that doesn't yet exist) (Likelihood: medium) → **Mitigation**: word the doc
  as a recommended operational convention layered on the existing `workflow_loader.py` API
  (which already accepts an arbitrary path/name), not as a claim that automatic environment
  detection exists; explicitly note in `docs/05_agent_03_03_...` that environment selection is a
  deployment-time choice of which file to point `config/workflows/` at, not a runtime feature.
- **Risk**: `docs/05_agent_03_03_turn-processing-flow-workflow-engine.md` appears to contain
  duplicated content blocks (see UNK-05) unrelated to this change; editing only one occurrence
  could leave a stale, contradictory copy of the old Needs-Confirmation note elsewhere in the same
  file (Likelihood: medium — confirmed two near-identical occurrences today) → **Mitigation**:
  during implementation, `grep -c` the exact Needs-Confirmation sentence in the file immediately
  before and after editing to confirm all occurrences were replaced; if the duplication turns out
  to be a larger structural documentation bug, file it separately as a documentation-fix issue
  rather than silently leaving a second stale copy.
- **Risk**: The prior plan cycle for the same source issue (`plans/done/20260818-185336_plan.md`)
  is already filed as "done" with mismatched content; a future audit might assume that source
  issue was already fully handled (Likelihood: low) → **Mitigation**: this plan's Traceability
  section and Assumptions §3 record the mismatch explicitly for future auditors.
