## Problem
`repository_state.py` contains empty service, dispatch, formatter, and tool-handler
methods outside the module's stated responsibility (an immutable state snapshot plus
a 9-stage pipeline orchestrator). Several return success-like values
(`_check_write()` → `True, ""`; `_protected_branches()` → `[]`; `_allow_detached_head()`
→ `False`, silently permissive in the negative-check sense) that can be mistaken for
active security behavior. ADR-012 and `docs/00_security_02...`'s current text
describe safeguards as complete and verified using evidence that does not actually
exercise the live code path — a documentation-governance violation this session's
seven sibling investigations surfaced concretely, not speculatively.

## Reason for Change
This cleanup is intentionally sequenced after `gitauth`/`gitpipeline`/`gitdryrun`
land, because removing a placeholder before its functional replacement exists would
delete the only code location the replacement is meant to occupy — cleanup and
documentation alignment both depend on identifying the canonical (post-fix)
implementation first, not the current (pre-fix) one.

## Design
This Plan is the eighth and last of a coordinated set filed alongside the same
originating issue batch, and the only one explicitly gated on the others landing
first. Its own investigation (re-confirming, per the issue's own AI Implementation
Instruction, rather than assuming from filing-time text) found the dead-method
surface is substantially larger than the issue's three named examples
(`verify_authorization()`, `_is_protected_branch()`, `verify_postcondition()`) — the
full ~60-method catalogue `gitauth`'s Plan documented. This Plan's REQ-002/REQ-003
scope covers that full catalogue, not only the three named methods, since the issue's
own Implementation Intent frames the goal broadly ("Remove empty service-construction,
dispatch, formatter, and tool-handler methods... after confirming they have no active
callers") rather than narrowly to the three examples given.

The two-tier gating structure mirrors `adrprodonly`'s Plan
(`plans/done/20260903-093353_plan.md`): REQ-001 (confirming Phase 0) is a
precondition with no file modification; REQ-002 through REQ-010 execute only once
cleared. Unlike `adrprodonly`'s Plan, no single Requirement here is "independently
actionable now" — every requirement in this Plan depends on the functional fixes
existing first, since removing a placeholder or correcting a "this is verified"
claim before the verification is real would either delete needed code or produce a
new inaccurate claim in the opposite direction.

REQ-007's coordination with `gitpipeline`'s Plan REQ-011 (which already plans a
corrected Known Issue entry for the MCP-003-equivalent finding) is deliberate: filing
a second, independent entry for the same underlying gap would itself be the kind of
documentation drift this issue exists to prevent. This Plan's REQ-007 is scoped to
confirming that entry's completeness and filing only a genuinely distinct gap, if one
remains after Phase 0 and this Plan's own cleanup.
