# Plan: Keep Each Tool Call's Failure Inside That Call

**Plan ID**: 20261023-004538
**Source Issue**: issues/20261021-093421_tool003-gather-without-return-exceptions-drops-sibling-results.md
**Generated**: 2026-10-23 00:45 JST

## Goal
Make one tool round produce exactly one persisted result for every call it started, whatever one of those
calls raises. A call's exception is captured at the per-call execution boundary and turned into the same
error-result shape the preparation phase already produces, so a sibling's results, already-applied side
effects, the round's ordering, and the round's own audit records all survive a single failing call.

## Priority
High

## Background
`execute_all_tool_calls` is the only production entry point for a tool round (`scripts/agent/llm_turn_runner.py:20`,
`:115-120`), and a round is executed as batches of groups (`scripts/agent/tool_runner.py:274-298`). Neither
group shape contains a `try`: the sequential branch awaits each call in a loop (`:69-73`) and the concurrent
branch gathers them without `return_exceptions` (`:74`). Everything that records the round — the order-restoring
sort at `:332`, the merge and second sort at `:384-385`, `_collect_tool_result_msgs` at `:387`, and
`ctx.session.save_many(tool_msgs)` at `:391` — sits after the whole batch has returned. A measured probe
(`/tmp/opencode/probe_gather.py`, repo venv Python 3.14.7) confirms the consequence: `asyncio.gather` with one
failing child raises the first exception, discards a sibling that had already completed, and cancels a sibling
that had not.

## Problem
One failing call erases the round's other outcomes:
- A completed sibling's result never exists, even though its side effect (a file write, a shell command, an
  MCP mutation) is already applied. A sibling cancelled mid-call can have applied its effect with no
  `ToolCallResult` at all, so neither `_record_transport_failure` (`scripts/agent/tool_runner.py:122-137`) nor
  `audit_tool_exec` (`:169-178`) ever sees it.
- Calls after the failing one in a sequential group never run, and every later batch in the plan never runs
  (`:281`).
- The model is told nothing. It re-issues calls whose effects already happened, and the session history
  disagrees with the filesystem, the shell, and the MCP servers.
- The round leaves no audit record either: `_record_serialization_stats` (`:328`),
  `_record_round_serialization_events` (`:335`), and `_record_round_exec` (`:336-343`) are all after
  `_run_plan_batches` (`:331`).
- The round counts zero tool errors, because `_update_stats_for_result` (`:225-237`) runs only inside
  `_collect_tool_result_msgs` (`:203`), which never runs. `LLMTurnRunner.run()` derives its error count from
  the `ctx.stats.stat_tool_errors` delta (`scripts/agent/llm_turn_runner.py:114-124`) and feeds
  `check_error_limit` (`:129`; `scripts/agent/tool_loop_guard.py:392-405`) — so the guard
  `docs/23_agent/agent_03_02_turn-processing-flow-llm-tool-loop.md:100` documents cannot fire for this
  failure class.

## Reason for Change
Partial results are the normal case for a concurrent tool batch, and the failure of one call is not
information about the others. Silently dropping them is the largest remaining source of history-versus-world
divergence in the tool loop, and it is the cause `plans/20261022-105432_plan.md` names as its own Phase 2
dependency ("tool003 owns sibling loss"). No test at HEAD locks the current behavior, so the fix can land
without a regression signal unless one is added first.

## Implementation Intent
Add one per-call boundary instead of two batch-level conversions. Every call a group starts is awaited through
a single wrapper that returns the same six-field result tuple the preparation phase already produces
(`scripts/agent/tool_preparation.py:37`, `:51-72`), converting only that call's exception into an error row and
logging it with its traceback. With nothing raised at that boundary, both `asyncio.gather` sites keep their
current form, the two order-restoring sorts keep their current form because every element is still a tuple, and
every downstream consumer (`_collect_tool_result_msgs`, `_update_stats_for_result`, the guard recording,
`save_many`) is unchanged — it already handles `is_error=True` rows.

## Assumptions
- A `tool` message with `is_error` semantics carried in its text is sufficient for the model to act on a failed
  call; the persisted shape does not need a structured error field. This is how preparation rejections and
  transport errors are represented today (`scripts/agent/tool_preparation.py:51-72`,
  `scripts/shared/tool_transport_invoker.py:209`).
- `ToolExecutorUnavailableError` is captured like any other failure rather than treated as a special case, so
  the batch-total rule does not depend on the exception class. It remains observable through `REQ-005` logging
  and the `REQ-009` guard.
- `Exception` (not `BaseException`) is the correct catch class for a per-call boundary in this codebase, matching
  `scripts/agent/tool_arg_validator.py:134` and `scripts/agent/context.py:327`.
- Implementation-order assumption stated for the downstream workflow, not for this Plan's validity: this Plan
  lands before `plans/20261022-105432_plan.md` Phase 2 (see UNK-01).

## Design
- One boundary, not two. The issue's Required Changes proposed `return_exceptions=True` at both `gather` sites
  plus a conversion of any returned exception. At HEAD that ordering does not work: `return_exceptions=True`
  returns exception objects inside the results list (probe Q4), and the two consumers that shape the round —
  the sort at `scripts/agent/tool_runner.py:332` and the six-field unpack at `:202` — run before any conversion
  could be inserted. Capturing inside a per-call wrapper means the values that reach those consumers are always
  tuples, so no conversion step is added anywhere and the batch-level gather at `:291-296` is left alone.
  Rejected alternative: batch-level `return_exceptions=True`, which additionally launders a programming error
  inside `_run_group_calls` into a fabricated tool result.
- The wrapper's `try` covers only the awaited call. Its own row-building is outside the `try`, so a bug in this
  Plan's new code is not converted into a tool error. `except Exception` is deliberate: `BaseException` would

## Risks
- **Risk**: A `requires_serial=True` barrier group carries an implicit value dependency the plan graph does not
  model (for example `shell("git add")` followed by `shell("git commit")`), and continuing after a failure runs
  the dependent call anyway. → **Mitigation**: both calls get explicit error rows, so the model sees the first
  failure and its `check_retry`/`check_dedup` guards and the failed-key hashing at
  `scripts/agent/tool_runner.py:236-237` act on it; today the alternative is that the whole round is discarded.
  If the product decision is to stop barrier groups, that is a narrow change to the sequential branch only and
  needs its own issue.
- **Risk**: A genuine programming error inside `execute_one_tool_call` is converted into a tool error row and
  the round continues. → **Mitigation**: `REQ-002` keeps the wrapper's own code outside the `try`, and `REQ-005`
  logs the captured exception with its traceback and the tool name and call id, so a laundered bug is visible in
  logs and diagnostics even though the round survives.
- **Risk**: Exception messages can contain paths or URLs, and they now reach the conversation as text. →
  **Mitigation**: this is the same exposure the round already has for transport and lifecycle failures
  (`scripts/shared/tool_transport_invoker.py:209`, `:219`); the logging path is redacted by
  `scripts/shared/logger.py:64` `_RedactionFilter`, and the row is truncated like any other result.
- **Risk**: A turn that previously failed with an exception now continues and can be stopped by
  `check_error_limit` after 3 all-failing rounds (`config/agent.toml:59`), which is a user-visible behavior
  change in the REPL. → **Mitigation**: it is the behavior already documented at
  `docs/23_agent/agent_03_02_turn-processing-flow-llm-tool-loop.md:100`, it is pinned by a test in
  `tests/agent/test_llm_turn_runner.py`, and `tool_error_max_consecutive <= 0` disables it
  (`scripts/agent/tool_loop_guard.py:396`).
- **Risk**: `scripts/agent/tool_runner.py` has only 858 B of headroom before the 16384 B gate, so a slightly
  larger implementation fails `check_module_size.py`. → **Mitigation**: the failure-text builder is placed in
  `scripts/agent/tool_result_formatter.py`; if the gate still fails, move `_truncate_for_llm` and the row
  construction into that module (both private, so no generated-reference drift) rather than shrinking behavior.
- **Risk**: Two `Frozen` plans own the same code body and the same documentation section, so whichever lands
  second can duplicate or overwrite the first. → **Mitigation**: the ordering is stated in Scope, Design, and
  UNK-01; this Plan adds only the per-call failure semantics and must not restate the pairing invariant owned
  by `plans/20261022-105432_plan.md`.
- **Risk**: `coverage.xml` is stale (2026-10-19), so `diff-cover` currently reports no diff lines and would
  pass vacuously. → **Mitigation**: Phase 1 regenerates it before any production change, and the validation
  table runs `diff-cover --fail-under=90` against the regenerated file.
