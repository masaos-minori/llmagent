# Make an MCP Subprocess Shutdown Report What Actually Happened, with Exit Confirmation as the Only Success

**Plan ID**: 20261022-082349
**Source Issue**: issues/20261021-093421_shutdown003-subprocess-termination-failures-report-success.md
**Generated**: 2026-10-22 08:23 JST

## Goal

Make the failure "an MCP subprocess I started did not stop" observable at the level
where the REPL already collects shutdown errors. One typed outcome describes what was
proved about one process, one place decides whether that outcome counts as a
completed shutdown, and everything above it carries the result instead of discarding
it. A clean exit then means "every server I started was confirmed gone", and a
server that survived the escalation is named — server key, pid, process group —
instead of leaving a log line and a deleted tracking entry.

## Priority

- **Primary goal**: stop reporting success where no termination was observed.
  `ProcessTerminator.terminate_with_timeout()` (`scripts/agent/http_lifecycle_process_terminator.py:115-211`)
  returns `True` from eight of its nine exits, including after a failed `os.killpg`
  and immediately after sending SIGKILL, and `_terminate_one()`
  (`scripts/agent/http_lifecycle_shutdown_coordinator.py:55-77`) never reads the
  value: `manager.cleanup_server_key(server_key)` runs at `:69` for every
  non-exception return.
- **Must be decided first**: what "terminated" means. This Plan's answer is exit
  confirmation, not signal delivery. The judgment already exists in the tree in
  `wait_exited()` (`http_lifecycle_process_terminator.py:83-113`), which returns
  `False` when its deadline passes, and no production path calls it.
- **Secondary goals**: one timeout authority per call site (four call sites use three
  values and one implicit default today); the false log text at
  `http_lifecycle_shutdown_coordinator.py:71-77` and the false docstring at
  `http_lifecycle_subprocess_launcher.py:133-135` corrected to the rule the code
  actually applies; the startup-rollback console message given its cause
  (`scripts/agent/startup.py:81-87`); the `_spawned_subprocesses` decision the issue's
  acceptance criteria demand.
- **Out of scope**: orphan prevention when the REPL itself is force-killed
  (`repl001`, `plans/20261022-030840_plan.md`); which signal mechanism owns the
  session (`SignalHandler.register`'s `loop.add_signal_handler`,
  `scripts/agent/signal_handler.py:51-63`, versus the `signal.signal` swap at
  `http_lifecycle_shutdown_coordinator.py:104-110`, `:141-146`) — the issue itself
  puts the SIGINT guard out of scope; the WAL/backup steps and the *presentation* of
  the shutdown error summary (`shutdown001`, `plans/20261022-043330_plan.md`, REQ-007);
  `ctx.turn.background_tasks` (`turn005`); health-check and restart policy; the
  content of MCP server startup configuration.

## Background

`ShutdownCoordinator.shutdown_all()` (`scripts/agent/http_lifecycle_shutdown_coordinator.py:79-146`)
iterates `manager.iter_processes()`, removes each process entry up front at `:122`,
then terminates the remaining servers concurrently through `_terminate_one()` at
`:132-139`, and clears every health timestamp at `:140`. `_terminate_one()` calls
`ProcessTerminator.terminate_with_timeout()` and, if no exception was raised, calls
`manager.cleanup_server_key(server_key)` (`:69`).

The terminator escalates SIGTERM → wait → SIGKILL inside the group that
`start_new_session: True` created for each server
(`scripts/agent/http_lifecycle_subprocess_launcher.py:99`, pgid recorded at `:113`).
Because those servers are not in the REPL's process group, this path is the only way
they are stopped; `grep -rn "atexit" scripts/` → no match, and the only shutdown
entry point is `AgentREPL.run()`'s `finally` (`scripts/agent/repl.py:162-163`).

Two facts define the size of the fix:

- The value is destroyed at `http_lifecycle_shutdown_coordinator.py:65-69`, and no
  `shutdown_all` in the chain returns anything: `ShutdownCoordinator` (`:79-84`),
  `HttpServerLifecycleManager` (`scripts/agent/http_lifecycle.py:338-343`),
  `_SubprocessLifecycleManager` and the router (`scripts/agent/lifecycle_router.py:76-78`,
  `:254-256`), `ServerLifecycleProtocol` (`scripts/agent/lifecycle_protocol.py:35`).
  `grep -rn "def shutdown_all" scripts/` returns exactly those five definitions.
- The place that *does* collect shutdown failures already exists:
  `ResourceShutdownCoordinator.close_resources()` builds `errors: list[tuple[str, str]]`
  (`scripts/agent/resource_shutdown_coordinator.py:67`), extends it from each step
  (`:76`, `:86`, `:95`, `:130`), collects exceptions from the concurrent service
  shutdown at `:137-145`, and summarizes at `:149-151`. It holds a `CLIView`
  (`:61`). A failed MCP termination never enters that list, because nothing about it
  is returned or raised.

## Problem

## Reason for Change

An orphaned MCP server keeps its port and its database connections while the REPL
reports a clean exit, and the record that would have pointed an operator at it
(`_http_pgids`, the stderr log path) is deleted in the same step. The operator's only
trace is a `logger.error` line in `/opt/llm/logs/agent.log`, and the exit status is
0. The issue's Reason for Change is confirmed at HEAD: the servers are started with
`start_new_session: True`, so no other mechanism stops them.

Reporting is also the cheapest part of this defect to fix. The escalation algorithm
is already bounded and already tested with real children
(`tests/agent/test_http_lifecycle_process_terminator.py:231-277`); what is missing is
a value that says what was proved, and a caller that acts on it.

## Implementation Intent

Turn one untyped bool into a stated outcome with four values, produce it only from
evidence, and make the shutdown chain carry it to the place that already aggregates
shutdown errors. Concretely:

- `TerminationOutcome`, a `StrEnum` beside the existing HTTP-lifecycle error types in
  `scripts/agent/http_lifecycle_errors.py`: `EXITED` (exit observed within the
  bound), `ALREADY_EXITED` (observed before any signal), `SIGNAL_NOT_DELIVERED`
  (no signal call succeeded), `EXIT_UNCONFIRMED` (a signal call succeeded, exit not
  observed within the confirmation bound).
- The escalation order, the concurrency, the SIGINT guard and the existing bounds are
  unchanged; only the value each arm produces, and one caller's decision, change.
- The chain stops returning `None`, and the shutdown error list gains one entry per
  unconfirmed server naming the key, pid and process group.

```
ProcessTerminator.terminate_with_timeout  -> TerminationOutcome      # evidence, one process
ShutdownCoordinator._terminate_one        -> TerminationOutcome      # settles tracking for one key
ShutdownCoordinator.shutdown_all          -> list[tuple[str, TerminationOutcome]]
HttpServerLifecycleManager.shutdown_all   -> same
_SubprocessLifecycleManager / router      -> same
ServerLifecycleProtocol.shutdown_all      -> same (the contract the consumer reads)
ResourceShutdownCoordinator.close_resources -> one ("http_termination", …) entry per item
```

## Requirements

- REQ-001: `terminate_with_timeout()` returns `TerminationOutcome`, not `bool`. Each
  of the nine current exits maps to exactly one value, and the mapping is stated in
  the method docstring, which replaces the false `Raises: HttpStartupError`
  (`http_lifecycle_process_terminator.py:125-126`) with a `Returns:` section. The
  SIGTERM → wait → SIGKILL order and the wait loop are unchanged.
- REQ-002: success requires evidence of the exit. `ALREADY_EXITED` (`:130-132`,

## Design

**Why exit confirmation and not signal delivery.** The operator's question is "is a
process still holding my port?". Signal delivery cannot answer it: `os.killpg`
succeeding says a signal was queued, `Popen.terminate()` cannot fail except by raising,
and a SIGKILL-ignoring D-state process is exactly the case this path exists for. The
tree already contains the exit-confirmation judgment in `wait_exited()`
(`http_lifecycle_process_terminator.py:83-113`) and the liveness probe it needs
(`_reap` + `os.killpg(pgid, 0)`, `:192-195`); this Plan makes the shutdown path use
that judgment instead of inventing a new one. `ALREADY_EXITED` stays a success because
it answers the same question affirmatively.

**Why the value is returned instead of raised.** The issue offers "raise the
documented `HttpStartupError`" as one option. It is rejected: `shutdown_all()` must
terminate every server and must not abort the remaining ones because one could not be
stopped — that is what `tests/agent/test_http_lifecycle_shutdown_coordinator.py:137`
and `test_lifecycle.py:883 test_shutdown_all_continues_after_terminate_error` protect,
and `close_resources()` already treats a shutdown step's failure as non-fatal. A raised
exception also collapses "this server did not stop" into "the shutdown step failed",
which is the ambiguity being removed.

**Why the value is returned instead of stored.** A `manager.unconfirmed_terminations`
attribute was the alternative. It was rejected because it is mutable state held across
an await boundary in a path that runs concurrently (`resource_shutdown_coordinator.py:137-145`),
it would need a protocol member to be readable, and it has no consumer that needs it
after the shutdown completes. Returning the list touches the same five definitions and
lands directly in the `errors` list that already exists.

**Where the decision lives.** Exactly one place acts on the outcome:
`ShutdownCoordinator._terminate_one` (`http_lifecycle_shutdown_coordinator.py:55-77`).
Everything above it transports; everything below it reports evidence. The
`TerminationOutcome` type lives in `http_lifecycle_errors.py` because that module is
already the home of this subsystem's failure vocabulary (`StartupFailure`, `HttpStartupError`),
which keeps `http_lifecycle_process_terminator.py` free of a type the coordinator also
has to import.

**Import layer.** No new cross-layer import: `http_lifecycle_errors.py` is already a
leaf of the `agent/` HTTP-lifecycle cluster, and `resource_shutdown_coordinator.py`
already imports `agent.cli_view`. `scripts/agent/http_lifecycle_*` importing
`agent/http_lifecycle_errors` is the existing pattern (`http_lifecycle.py` raises

## Risks

- **Locked behavior in high-churn tests.** `tests/agent/test_lifecycle.py` (1496 lines,
  30d churn 11) and `tests/agent/test_http_lifecycle_process_terminator.py` assert the
  current bool from five places. Changing them is the point of the work, so each
  re-asserted arm is named in the Tests section and no assertion may be dropped
  without a replacement (AC-11). Mitigation: Phase 1 changes only the terminator and
  its own test file, so a wrong mapping shows up immediately and locally.
- **Over-mocking hides the contract.** The existing stub tests assert which signals were
  sent, never what was proved about the process; a purely stub-based redesign could
  encode the same blind spot. Mitigation: the two claims that matter are asserted
  against real children with the existing `_spawn`/`_cleanup` harness, and the
  mutation gates name the four rules that must fail when removed.
- **Added shutdown time.** The confirmation pass runs only after SIGKILL, so the
  expected cost is one or two poll intervals (0.1 s each) and only for a server that
  survived SIGTERM; the worst case is the UNK-01 window. `test_lifecycle.py:1040`
  protects the no-thread property, and AC-3 bounds the test-side cost. If the 30.0 s
  graceful bound plus this window must stay under `_GRACEFUL_TIMEOUT_S`, that is
  `shutdown001`'s ordering question (UNK-06), not a hidden assumption here.
- **False failures become visible.** Reporting arms that were silently successful will
  produce `http_termination` entries for situations that are today invisible — for
  example a process group that vanished between SIGTERM and the probe. The outcome
  values distinguish these, and `ALREADY_EXITED`/`ProcessLookupError` arms remain
  successes, so a genuinely-stopped server is not reported as a failure. AC-2's per-arm
  tests are what keep this from becoming noise.
- **Return-type ripple.** Five `shutdown_all` definitions and one consumer change
  together; a half-done propagation is a mypy error, not a silent bug. Phase 2's gate
  is the full mypy run for that reason.
- **Shared target files with earlier Plans.** `scripts/agent/repl.py`,
  `scripts/agent/resource_shutdown_coordinator.py`,
  `tests/agent/test_resource_shutdown_coordinator.py` and
  `docs/23_agent/agent_10_01_operations-and-observability-startup-and-health.md` are
  also named by `cmd001-003`, `doc001`, `repl001-002`, `shutdown001-002`. This Plan
  edits only the listed lines in each (the `errors` consumption at
  `resource_shutdown_coordinator.py:137-145`, the assertions that follow it in its
  test file, the two named doc statements, and the startup console message at
  `startup.py`). `repl.py` is named only to verify the 2-tuple unpack is unchanged
  (REQ-009, already implemented by `de0fbc4a4`); it is not edited. Declared intentional;
  `check_plan_target_overlaps.py` is expected to report them.
