## Background
This Plan's source Issue was discovered while `docs/adr/ADR-004-environment-failure-handling-policy.md` was rewritten on 2026-08-31. `docs/adr/ADR-004-environment-failure-handling-policy.md` Decision Group 3 (items 9-13) defines the criteria for classifying a component as required or non-required, and states (item 13) that "the approved classification of each component is recorded by the applicable Startup, Agent, or MCP Specification" and that configuration may only supply effective values within what an approved Specification permits. ADR-004's own `## Known Deviations` section already states, in its own words, that no such approved Specification currently exists ("コンポーネント単位の必須／非必須分類を記録する現行の承認済みSpecificationも存在しない（Decision #13が要求する分類記録の主体が未整備）") and recommends filing this as a new issue — which is the issue this Plan is derived from.

**Dependencies** (from the source Issue): this Plan's output is a prerequisite for `issues/20260831-192510_adr004_05_mcp_config_alignment_superseded_by_policy_reversal.md` (currently in `issues/`, not processed by this Plan) — that issue's `McpServerConfig` runtime-alignment work depends on the classification Specification this Plan produces existing first. This Plan has no unresolved dependency of its own beyond the 2026-08-31 ADR-004 rewrite already being in place, which it is.

## Problem
`scripts/shared/mcp_config.py`'s `McpServerConfig` dataclass has `required_in_production` and `required_in_local` boolean fields (both defaulting to `True`), and `scripts/agent/services/mcp_tool_discovery.py` branches on `security_profile` to select between them (`is_required` computation). No Specification document explains, per configured MCP server, which of these fields should be `True` vs `False`, or the criteria for that choice. `docs/05_agent_08_04_configuration-mcp-approval-obs.md` (the Specification that documents `McpServerConfig`'s other Agent-side MCP Fields) does not mention `required_in_production` / `required_in_local` at all. `config/agent.toml` does not override either field for any `[mcp_servers.*]` entry, so every currently configured server is effectively required today.

## Reason for change
Without an authoritative record of which components are non-required, ADR-004's partial-availability model (Decision Groups 3, 7, 8) cannot be operated as designed: a maintainer either has to invent a classification (which ADR-004 Decision item 12 explicitly forbids treating as a basis for continuing startup) or leave every component required indefinitely. ADR-004 itself flags this as an open gap in its Known Deviations section.

## Implementation intent
Extend the existing MCP configuration Specification (`docs/05_agent_08_04_configuration-mcp-approval-obs.md`) with a new subsection that: (a) documents `McpServerConfig.required_in_production` / `McpServerConfig.required_in_local` and the criteria from ADR-004 Decision Group 3 items 9-11, and (b) provides a table with one row per currently configured MCP server, each row citing its classification and a rationale referencing the specific Decision Group 3 criterion it satisfies. The actual classification values are a substantive architecture decision that must come from the architecture/component owner applying ADR-004's criteria to each server — this Plan defines the documentation structure and the review step, not the classification values themselves (see Unknowns). Once the Specification exists, add a one-line cross-reference to it from ADR-004's `### Specifications` subsection, and update ADR-004's existing Known Deviations entry so it no longer states that no such Specification exists.

## Requirements
- `REQ-001`: `docs/05_agent_08_04_configuration-mcp-approval-obs.md` must contain a subsection that documents `McpServerConfig.required_in_production` / `McpServerConfig.required_in_local` and lists, for every MCP server currently configured under `[mcp_servers.*]` in `config/agent.toml`, an explicit required/non-required classification and a rationale that cites the specific ADR-004 Decision Group 3 criterion (items 9-11) it is based on.
- `REQ-002`: `docs/adr/ADR-004-environment-failure-handling-policy.md`'s `## Related Documents` → `### Specifications` subsection must reference the Specification updated under `REQ-001`, and the existing Known Deviations entry describing the absence of such a Specification must be updated to reflect that it now exists.

## Design
This Plan classifies as **Path A** (2 target files, no public/runtime interface change, no database schema change — see `skills/issue-to-plan/SKILL.md` Routing). Per Path A, architecture/dependency/historical/operational analysis is skipped; only direct verification of the two target files and their immediate cross-references was performed (Step 3), which is what the Reference Files table above records.

Two placement candidates were considered for REQ-001 and ruled out or confirmed by direct evidence, not assumption:
- `docs/04_mcp_03_06_tool-runtime-availability-metadata.md` — ruled out: this document's own front matter and body scope it to `config_dependent`/`enabled`/`disabled_reason`, a distinct, ADR-003-governed, per-tool concept (static availability vs. dynamic health), not ADR-004's component-level required/non-required classification. ADR-004 Decision item 24 explicitly warns against collapsing these two distinct concepts.
- `docs/05_agent_08_04_configuration-mcp-approval-obs.md` — confirmed: this is the Specification that already documents other `McpServerConfig` fields under the same "Responsibility Boundary" statement (`Source of Truth: MCP/Approval/Observability/Diagnostics sections in config/agent.toml`), making it the document `required_in_production`/`required_in_local` already belong in but are currently missing from.

The Issue's own "Unresolved Questions" field flagged the placement decision as needing an owner decision. This Plan resolves that placement question directly from repository evidence (above) without requiring further owner input, because document placement is an editorial/organizational judgment, not a substantive ADR-004 classification decision. The substantive classification values themselves (which the Issue's AI Implementation Instruction explicitly reserves for the owner) remain UNK-01, deferred to implementation.

The Known Deviations update (second part of REQ-002) is included because leaving that sentence unedited after REQ-001 closes the gap would immediately make ADR-004 self-contradictory (stating no Specification exists when one does) — this is judged in-scope as a direct, minimal consequence of the same file edit, not a separate unrelated cleanup.
