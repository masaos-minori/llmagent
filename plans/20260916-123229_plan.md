## Goal
- Unify the exception contract and configuration-validation semantics that surround the MCP invocation gate chain — enumerate `LifecycleProtocol`'s permitted exceptions, make lifecycle-exception handling and health-recording identical between `ToolTransportInvoker.invoke()` and `ToolExecutor.execute()`, make an unvalidated/unknown routed server key fail closed, and make `McpServerConfig`'s per-mode required fields, `required`/`failure_policy` roles, and timeout-zero semantics explicit and consistent — without duplicating the startup-mode gate relocation already planned in `plans/20260916-114735_plan.md` (mcpagent01).

## Priority
Medium

## Scope
- **In-Scope**:
  - Enumerating and centralizing `LifecycleProtocol`'s permitted exception set (`scripts/shared/tool_lifecycle.py`).
  - Unifying the lifecycle-exception catch clause and health-registry failure recording used by `ToolTransportInvoker.invoke()` and `ToolExecutor._raw_execute()` into one shared implementation.
  - Making `ToolExecutor`'s routed-server gate fail closed when no validated `McpServerConfig` exists for a resolved `server_key` (currently silently passes — see `rules/workflow-lifecycle.md` Adversarial Verification finding below).

## Background
This Issue is a direct code-level finding across the MCP invocation/lifecycle path (not derived from a prior design-decision document); confirmed no separate background document exists.

## Problem
Verified against current source (all findings below are `Confirmed by repository evidence`):
- **Two invocation entry points, divergent lifecycle-exception handling**: `ToolTransportInvoker.invoke()` (`scripts/shared/tool_transport_invoker.py:187-215`) catches only `ServerCooldownError` around `self._lifecycle.ensure_ready(server_key)` (lines 197-203) and never calls `self._health_registry.record_failure()` on that path. `ToolExecutor._ensure_lifecycle_ready()` (`scripts/shared/tool_executor.py:69-81`), used by `_raw_execute()`, catches the broader `(OSError, RuntimeError)` and does call `health_registry.record_failure()` (line 79). Since `ServerCooldownError` subclasses `RuntimeError`, `ToolExecutor`'s path handles it as a generic lifecycle failure with health recording, while `invoke()`'s path handles the same exception type differently and skips health recording — and any exception outside both catch sets (e.g. a `subprocess`-level exception not subclassing `OSError`/`RuntimeError`) propagates uncaught out of `invoke()`. The production `LifecycleProtocol` implementation, `_ServerLifecycleRouter.ensure_ready()` (`scripts/agent/factory.py:128-159`), raises `ServerCooldownError` explicitly (cooldown case) and re-raises whatever `HttpServerLifecycleManager.start()`/`.restart()` raise via a bare `except Exception: ... raise` in `_run_lifecycle_transition` (`scripts/agent/factory.py:98-108`) — so the true exception surface is not bounded to `LifecycleProtocol`'s two-line docstring-only contract (`scripts/shared/tool_lifecycle.py:14-19`).
- **Unvalidated routed server key does not fail closed**: `ToolExecutor._check_startup_mode()` (`scripts/shared/tool_executor.py:60-67`) does `cfg = self._server_configs.get(server_key); if cfg is not None and cfg.startup_mode == StartupMode.NONE: ...` — when `cfg is None` (server key not present in the validated configuration), the condition short-circuits and the method returns `None` (i.e., "not disabled," gate passes). This is exercised by an *existing, currently-passing* test that documents the gap as intended behavior: `tests/shared/test_tool_executor.py:503-505` (`test_returns_none_for_unknown_server_key`, `class TestCheckStartupMode` at line 480). The call only fails later, coincidentally, when `_resolve_transport()` also returns `None` — not via an explicit "unvalidated configuration" gate.
- **Disabled server still requires `auth_token`**: `McpServerConfig._validate_auth_token()` (`scripts/shared/mcp_config.py:177-184`) unconditionally rejects an empty `auth_token`, with no exception for `startup_mode == StartupMode.NONE` (`is_disabled` property at lines 98-101). `StartupMode.NONE`'s own docstring states "no subprocess spawn, no health check; server is unusable" (`scripts/shared/mcp_config.py:44`), so requiring a connection secret for it is inconsistent with the mode's own documented meaning. No server in `config/agent.toml` currently uses `startup_mode = "none"` (verified via `grep`), so this is a latent, not currently-triggered, defect.
- **`required` vs `failure_policy` overlap**: `FailurePolicy` (`scripts/shared/mcp_config.py:29-32`) has exactly one member, `FAIL_FAST`. The only production read of `cfg_entry.failure_policy` is `scripts/agent/startup_reporter.py:127` (`getattr(cfg_entry, "failure_policy", None)`), used for display only — no runtime branch differentiates behavior by `failure_policy` value. `required` (bool, default `True`) is consumed at `scripts/agent/services/mcp_tool_discovery.py:133` to escalate a WARNING finding to FATAL. The two fields' roles are not documented as distinct anywhere in `mcp_config.py`.
- **Timeout-zero semantics diverge across three fields**: `call_timeout_sec=0` → confirmed "no timeout" (`scripts/shared/http_transport.py:104`: `timeout = httpx.Timeout(self._timeout) if self._timeout > 0 else None`), matching its inline comment (`mcp_config.py:77`). `startup_timeout_sec=0` → confirmed "skip the health-check poll entirely" (`scripts/agent/http_lifecycle.py:450,460`: `if cfg.startup_timeout_sec > 0: ... else: logger.info("... skipping health check ... (timeout=0)")`) — a materially different semantic (disables the check) from "no timeout" (waits indefinitely). `health_timeout=0` → `get_effective_health_timeout()` (`scripts/shared/mcp_config.py:228-241`) returns `0` unchanged (only `None` triggers the 5.0 default; `_validate_timeouts` at lines 151-160 accepts `>= 0`), and both call sites (`scripts/agent/services/mcp_tool_discovery.py:189`, `scripts/agent/services/mcp_status.py:71-77`) pass this value straight into `httpx.Timeout(timeout=...)` with no zero-guard — the opposite of `call_timeout_sec`'s "0 = no timeout" convention (httpx interprets a numeric `0` as an immediate deadline, not "unbounded"; this is precisely why `http_transport.py:104` converts `0` to `None` before calling `httpx.Timeout` at all). This is an undocumented, inconsistent, and practically harmful (near-instant health-check failure) behavior.
- **Misleading validation message**: `_build_single_server()`'s `health_timeout` conversion `except` (`scripts/shared/mcp_config.py:270-278`) raises `"... health_timeout must be a positive number or null, got {type}"` on a type-coercion failure only (non-numeric input) — it does not itself reject zero or negative values (that happens later, in `_validate_timeouts`, with the accurate wording `"health_timeout must be >= 0, got {value}"`). The phrase "positive number" in the build-time message is inaccurate given the dataclass's own `>= 0` acceptance.

## Reason for Change
Invocation APIs, startup modes, required-server behavior, failure policy, lifecycle exceptions, timeout semantics, and missing server configuration all determine whether a call may proceed; leaving these checks scattered and divergent (as confirmed above) risks contradictory gating between call paths, per the Issue's Reason for Change.

## Implementation intent
Centralize the lifecycle-exception contract as a named, importable exception tuple in `tool_lifecycle.py`; make both invocation entry points (`invoke()` and `_raw_execute()`) call one shared lifecycle-handling helper defined on `ToolTransportInvoker` (the common base class) instead of duplicating divergent try/except blocks; add an explicit "no validated configuration for this server key" gate ahead of the existing startup-mode check; relax and document `McpServerConfig`'s per-mode/secret/timeout-zero validation without changing its external TOML schema; and add regression/parity tests for every change. This Plan explicitly builds on top of `plans/20260916-114735_plan.md`'s (mcpagent01) REQ-004 gate relocation rather than re-specifying it — see Assumptions/Risks for the coordination dependency.

## Requirements
- `REQ-001`: Enumerate `LifecycleProtocol`'s permitted exceptions as a named, importable tuple/type in `scripts/shared/tool_lifecycle.py` (covering `ServerCooldownError` and the `(OSError, RuntimeError)` set already used by `ToolExecutor`), with a docstring stating this is the closed set any `ensure_ready()` implementation may raise to be normalized into a `ToolCallResult`.
- `REQ-002`: Unify the lifecycle-exception handling and health-registry failure recording used by `ToolTransportInvoker.invoke()` and `ToolExecutor._raw_execute()` into one shared method on `ToolTransportInvoker`, using REQ-001's exception set, so both paths produce the same `error_type` and the same `health_registry.record_failure()` behavior for an equivalent lifecycle failure.
- `REQ-003`: Add a fail-closed check in `ToolExecutor`'s gate chain: when `self._server_configs.get(server_key)` returns `None` (no validated configuration for the resolved server key), return a documented `ToolCallResult` error instead of silently passing the startup-mode check.
- `REQ-004`: Change `McpServerConfig._validate_auth_token()` to skip the non-empty `auth_token` requirement when `self.is_disabled` (`startup_mode == StartupMode.NONE`).
- `REQ-005`: Document, in `McpServerConfig`'s class docstring/field comments, that `required` governs startup criticality (FATAL vs WARNING escalation at discovery) and `failure_policy` is a reserved, currently single-valued (`FAIL_FAST`) runtime-call-failure-behavior field with no current branching — non-overlapping, explicitly stated roles.
- `REQ-006`: Make timeout value `0` mean "no timeout" consistently for `call_timeout_sec` (already correct) and `health_timeout` (currently incorrect) — fix `get_effective_health_timeout()` and its two call sites so `health_timeout=0` yields no health-check deadline instead of an near-immediate one; document `startup_timeout_sec=0`'s distinct "skip the health-check poll" meaning explicitly as intentionally different from the other two fields' "no timeout" meaning (already correct behavior, needs only documentation).
- `REQ-007`: Correct `_build_single_server()`'s `health_timeout` type-conversion error message so it accurately describes only the type-coercion check it performs (not a value-range claim that the code does not enforce at that point).
- `REQ-008`: Add parity tests asserting `ToolTransportInvoker.invoke()` and `ToolExecutor.execute()` normalize the same lifecycle-exception inputs (from REQ-001's set) into equivalent `ToolCallResult` outputs (same `error_type`, same health-registry recording call).
- `REQ-009`: Add regression tests for REQ-003 (fail-closed unknown/unvalidated server key — this changes `test_returns_none_for_unknown_server_key`'s current assertion), REQ-004 (disabled server does not require `auth_token`), REQ-006 (health_timeout=0 no longer causes near-instant failure, at both the `mcp_config.py` unit level and the two call sites), and REQ-007 (corrected message text).
- `REQ-010`: Add explicit per-`StartupMode` required-field documentation to `McpServerConfig` (a class-level comment or docstring table: `NONE` requires none of `url`/`cmd`/`auth_token`; `PERSISTENT` requires `url` (already enforced via the HTTP-transport check); `SUBPROCESS` requires `cmd` (already enforced) and `url`), reconciling wording with the validation methods that already exist.
- `REQ-011`: Update the identified Documentation Impact target (`docs/90_shared_03_02_runtime_and_execution-tool-executor-and-infrastructure.md`) to describe the unified lifecycle-exception contract (REQ-001/REQ-002) and the corrected timeout-zero semantics (REQ-006) — deferred to the implementation phase, after REQ-001–REQ-010 pass executable verification, per the Issue's own Documentation Impact instruction ("update ... only after executable verification is available").
