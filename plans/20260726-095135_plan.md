# Plan: Bound `AgentREPL._close_resources()`'s WAL checkpoint sequence with a timeout and fix the `PRAGMA database_list` column bug

## Goal

`AgentREPL._close_resources()` in `scripts/agent/repl.py` no longer runs its blocking
WAL-checkpoint sequence (PASSIVE checkpoint -> TRUNCATE retries -> WAL file backup)
directly on the event loop with no aggregate time bound, and the WAL backup safety net
actually copies the correct file because `PRAGMA database_list`'s file-path column
(index 2, not 1) is read.

## Scope

**In scope:**
- Move the blocking WAL-checkpoint sequence (currently `scripts/agent/repl.py:251-319`)
  off the event loop via `loop.run_in_executor(None, ...)`, bounded by
  `asyncio.wait_for(..., timeout=<configurable>)`.
- Introduce a configurable overall timeout for the checkpoint stage as a class
  attribute on `AgentREPL` (not a constructor parameter — see Design/Unknowns for why).
- Split the current single try/except block into two independently-executed,
  independently-bounded synchronous stages so the WAL backup step is attempted even
  when the checkpoint stage itself times out: (1) checkpoint stage (PASSIVE + TRUNCATE
  retries/backoff), (2) backup stage (`PRAGMA database_list` + `shutil.copy2`).
- Fix `db_path = db.execute("PRAGMA database_list").fetchone()[1]` (`repl.py:297-299`)
  to read index `[2]` (the file path column), not `[1]` (the database name column).
- Change the TRUNCATE retry backoff from `await asyncio.sleep(2**attempt)` to
  `time.sleep(2**attempt)`, since the backoff now runs inside a synchronous function
  executed in a worker thread, not on the event loop.
- Preserve existing logging and `errors` list entries; add new entries for the new
  timeout conditions (`wal_checkpoint_timeout`, `wal_backup_timeout`).
- Add/update unit tests in `tests/test_repl.py` (`TestCloseResourcesWALCheckpoint`)
  covering: existing behaviors (PASSIVE success, TRUNCATE fallback, non-WAL skip)
  continue to pass under the new executor-wrapped structure; a new timeout-path test;
  a new `PRAGMA database_list` column-index test.

**Out of scope:**
- Changing the PASSIVE -> TRUNCATE -> backup escalation order or TRUNCATE's retry
  count (3) / backoff shape (`2**attempt`).
- Changing behavior on non-WAL journal modes (`repl.py:315-316`, the `else` branch).
- Any change to `scripts/db/helper.py` (`SQLiteHelper.checkpoint()`,
  `apply_connection_pragmas()`, `_DEFAULT_BUSY_TIMEOUT_MS`, `sqlite_timeout`) — read
  for reference only, per the requirement doc's target-files list.
- Wiring the timeout through `agent.toml` / `AgentConfig` — out of scope; see
  Assumption 3.
- `docs/*.md` updates — out of scope for this document-only planning phase.

## Assumptions

1. `review_mode` for this planning cycle is `autonomous`, so Step 7 (moving the
   requirement file) proceeds without a manual approval gate.
2. The requirement doc refers to the target function as `SessionRunner._close_resources()`,
   but no `SessionRunner` class exists anywhere under `scripts/` (`grep -rn "class SessionRunner" scripts/`
   returns no hits). The actual class is `AgentREPL` (`scripts/agent/repl.py:78`), and
   `_close_resources()` is a method on it (`repl.py:245`). This plan treats
   `AgentREPL._close_resources()` as the intended target — the requirement doc's class
   name is treated as a naming slip, not a signal that a different function exists.
   Falsifiable: a repo-wide grep for `SessionRunner` before implementation should
   continue to return no hits; if it later returns a hit, this assumption is wrong.
3. The configurable timeout is implemented as a **class attribute** on `AgentREPL`
   (e.g. `_WAL_CHECKPOINT_TIMEOUT_S: float = 30.0`), not a constructor parameter and
   not an `agent.toml`/`AgentConfig` field. Reasons: (a) `tests/test_repl.py`'s
   `_make_bare_repl()` helper constructs test instances via `AgentREPL.__new__(AgentREPL)`,
   bypassing `__init__` entirely — an instance attribute set only inside `__init__`
   would not exist on these bare instances and `_close_resources()` would raise
   `AttributeError` the first time any of the three existing
   `TestCloseResourcesWALCheckpoint` tests ran; a class attribute is visible to
   `__new__`-constructed instances without requiring `__init__` to run. (b) `AgentREPL()`
   is instantiated with zero arguments at exactly two call sites
   (`scripts/agent/__main__.py:14`, `scripts/agent/repl.py:632`), and `AgentREPL.__init__`
   currently takes no config object — plumbing a new config source through would be a
   larger, out-of-scope change for a bug-fix-sized task. (c) This mirrors an existing
   in-repo convention: `scripts/agent/http_lifecycle.py:62` defines
   `_TERMINATE_POLL_INTERVAL_SEC: float = 0.05` as a class attribute for exactly this
   purpose (a tunable constant that tests can override per-instance by plain attribute
   assignment, e.g. `repl._WAL_CHECKPOINT_TIMEOUT_S = 0.01`, without touching the
   constructor). This is a documented design decision, not a blocking unknown.
4. Default timeout value: `30.0` seconds. Rationale: `SQLiteHelper` bounds any single
   blocking SQLite call to ~30s (`busy_timeout=30000` in `apply_connection_pragmas()`,
   `sqlite3.connect(..., timeout=30)` in `SQLiteHelper._connect()`), so 30s is "at most
   one busy-timeout's worth of extra wait" beyond a single blocked call — enough for
   one full-length PASSIVE or TRUNCATE attempt to complete, while still cutting off the
   worst case (PASSIVE + 3×TRUNCATE + backoff ≈ up to ~2 minutes per the requirement
   doc) well before it reaches that extreme. This is a placeholder default reflecting
   the requirement doc's own reasoning; it is not derived from measured production
   shutdown-latency data (none was available during planning — see Unknowns U2).
5. `shutil.copy2(wal_file, wal_backup_path)` failing when no `-wal` file exists (e.g.
   TRUNCATE actually succeeded in fully checkpointing before the last retry's exception
   was raised, or the WAL file was already removed) is expected/handled by the existing
   `except Exception as backup_err: logger.error(...)` — this plan does not change that
   error-swallowing behavior, only the column-index bug feeding `db_path`.
6. The two-stage split (checkpoint stage / backup stage, each its own
   `run_in_executor` + `wait_for` call, each opening its own `SQLiteHelper("session")`
   connection) is safe because SQLite supports multiple independent connections to the
   same WAL-mode database file; the backup stage does not need to touch the checkpoint
   stage's (possibly still-blocked) connection object.

## Design

### 1. Timeout mechanism (concrete)

Add two class attributes directly on `AgentREPL`, next to the existing
`_REPL_RESERVED_COMMANDS`-style module constant pattern already used in this file,
mirroring `http_lifecycle.py:62`'s `_TERMINATE_POLL_INTERVAL_SEC: float = 0.05`
class-attribute convention:

```python
class AgentREPL:
    ...
    _WAL_CHECKPOINT_TIMEOUT_S: float = 30.0
    """Overall bound on the PASSIVE+TRUNCATE WAL checkpoint sequence during shutdown."""
    _WAL_BACKUP_TIMEOUT_S: float = 10.0
    """Bound on the WAL-file-backup safety net (PRAGMA database_list + shutil.copy2)."""
```

Both are read as `self._WAL_CHECKPOINT_TIMEOUT_S` / `self._WAL_BACKUP_TIMEOUT_S` inside
`_close_resources()`, so tests can override per-instance
(`repl._WAL_CHECKPOINT_TIMEOUT_S = 0.01`) without needing `__init__` to run — required
because `_make_bare_repl()` constructs via `AgentREPL.__new__(AgentREPL)` (see U3).

### 2. Two-stage split (why, and how it satisfies "backup still attempted on timeout")

The requirement's acceptance criteria require that "When the overall timeout is
exceeded, the WAL backup step is still attempted." If the entire current block
(open connection -> checkpoint attempts -> backup) were wrapped as a single
`run_in_executor` + `wait_for` call, a checkpoint-side timeout would mean the whole
executor task — including the not-yet-reached backup step — is abandoned; the
backup would only run if/when the stuck worker thread eventually unblocks on its own,
which defeats "still attempted." Instead, split into two independent
synchronous helper methods, each opened/closed inside its own `run_in_executor` call
with its own connection and its own timeout:

```python
def _wal_checkpoint_sync(self) -> tuple[bool, list[tuple[str, str]]]:
    """Run PASSIVE, then TRUNCATE-with-retry on failure. Opens/closes its own
    connection (must not share a sqlite3.Connection across threads).
    Returns (truncated_or_passive_ok, errors).
    """
    errors: list[tuple[str, str]] = []
    with SQLiteHelper("session").open(write_mode=True) as db:
        wal_mode = db.execute("PRAGMA journal_mode").fetchone()[0]
        if wal_mode.lower() != "wal":
            logger.debug("WAL checkpoint skipped: journal mode is %r", wal_mode)
            return True, errors
        try:
            db.checkpoint("PASSIVE")
            logger.info("WAL checkpoint completed (PASSIVE) on shutdown")
            return True, errors
        except sqlite3.Error as passive_err:
            logger.warning(
                "WAL PASSIVE checkpoint failed, falling back to TRUNCATE: %s",
                passive_err,
            )
        for attempt in range(3):
            try:
                db.checkpoint("TRUNCATE")
                logger.info(
                    "WAL checkpoint completed (TRUNCATE) on shutdown after %d retries",
                    attempt + 1,
                )
                return True, errors
            except sqlite3.Error as truncate_err:
                if attempt < 2:
                    logger.warning(
                        "WAL TRUNCATE checkpoint attempt %d failed, retrying: %s",
                        attempt + 1,
                        truncate_err,
                    )
                    time.sleep(2**attempt)  # was: await asyncio.sleep — now runs in a worker thread
                else:
                    logger.error(
                        "WAL TRUNCATE checkpoint failed after 3 attempts: %s",
                        truncate_err,
                    )
                    errors.append(
                        (
                            "wal_checkpoint_truncate",
                            f"{type(truncate_err).__name__}: {truncate_err}",
                        )
                    )
    return False, errors


def _wal_backup_sync(self) -> tuple[str | None, list[tuple[str, str]]]:
    """Best-effort WAL file backup; opens its own independent connection."""
    errors: list[tuple[str, str]] = []
    wal_backup_path: str | None = None
    try:
        with SQLiteHelper("session").open(write_mode=True) as db:
            db_path = db.execute("PRAGMA database_list").fetchone()[2]  # fixed: was [1]
            if db_path:
                wal_file = f"{db_path}-wal"
                backup_dir = os.path.dirname(db_path) or "/tmp"
                wal_backup_path = os.path.join(
                    backup_dir,
                    f"{os.path.basename(db_path)}-wal-backup-{int(time.time())}",
                )
                shutil.copy2(wal_file, wal_backup_path)
                logger.warning("WAL file backed up to %s", wal_backup_path)
    except Exception as backup_err:
        logger.error("Failed to backup WAL file: %s", backup_err)
        errors.append(("wal_backup", f"{type(backup_err).__name__}: {backup_err}"))
    return wal_backup_path, errors
```

`_close_resources()` becomes:

```python
async def _close_resources(self) -> None:
    """Close all session resources. Called in the run() finally block."""
    self._view.write_history()
    errors: list[tuple[str, str]] = []
    loop = asyncio.get_running_loop()

    truncated_or_ok = False
    try:
        truncated_or_ok, checkpoint_errors = await asyncio.wait_for(
            loop.run_in_executor(None, self._wal_checkpoint_sync),
            timeout=self._WAL_CHECKPOINT_TIMEOUT_S,
        )
        errors.extend(checkpoint_errors)
    except TimeoutError:
        logger.error(
            "WAL checkpoint sequence exceeded %.1fs timeout on shutdown; "
            "abandoning wait (worker thread may still complete in the background)",
            self._WAL_CHECKPOINT_TIMEOUT_S,
        )
        errors.append(
            (
                "wal_checkpoint_timeout",
                f"TimeoutError: exceeded {self._WAL_CHECKPOINT_TIMEOUT_S}s",
            )
        )
    except sqlite3.Error as e:
        errors.append(("wal_checkpoint", f"{type(e).__name__}: {e}"))
        logger.error("WAL checkpoint failed on shutdown: %s", e)

    if not truncated_or_ok:
        try:
            _wal_backup_path, backup_errors = await asyncio.wait_for(
                loop.run_in_executor(None, self._wal_backup_sync),
                timeout=self._WAL_BACKUP_TIMEOUT_S,
            )
            errors.extend(backup_errors)
        except TimeoutError:
            logger.error(
                "WAL backup step exceeded %.1fs timeout on shutdown",
                self._WAL_BACKUP_TIMEOUT_S,
            )
            errors.append(
                (
                    "wal_backup_timeout",
                    f"TimeoutError: exceeded {self._WAL_BACKUP_TIMEOUT_S}s",
                )
            )

    # ... unchanged: svc = self._ctx.services; lifecycle.shutdown_all(); http.aclose();
    #     final `if errors:` summary log.
```

Notes:
- `except TimeoutError` (not `except asyncio.TimeoutError`) is used because on
  Python >= 3.11 `asyncio.TimeoutError` is an alias of the builtin `TimeoutError`,
  which `asyncio.wait_for` raises; this repo targets `requires-python = ">=3.13"`
  (`pyproject.toml`), so the builtin form is correct and matches existing usage
  elsewhere in the file (`repl.py:365`, already uses `asyncio.wait_for` without a
  bespoke exception alias).
- `not truncated_or_ok` covers three cases uniformly: PASSIVE/TRUNCATE genuinely
  failed after 3 retries (`truncated_or_ok=False` returned normally), and the
  checkpoint stage timed out (`truncated_or_ok` stays at its initial `False` because
  the `try` block never completed assignment) — both correctly trigger the backup
  attempt, satisfying "on overall timeout expiry ... proceed straight to the WAL
  backup path."
- The backup stage opens its own fresh `SQLiteHelper("session")` connection,
  independent of whatever state the (possibly abandoned) checkpoint-stage worker
  thread/connection is in (see Assumption 6, U4).
- `errors` entries preserve the existing tuple shape (`(name, "ExcType: message")`)
  used by the final summary log, so Implementation instruction #3 ("consistent with
  existing entries like `wal_checkpoint_truncate`") is satisfied.

### 3. The `PRAGMA database_list` fix

`PRAGMA database_list` returns rows shaped `(seq, name, file)` — `.fetchone()[1]` is
the database name (e.g. `"main"`), `.fetchone()[2]` is the file path. This plan uses
the index fix (`[1]` -> `[2]`) as literally specified in the requirement doc, rather
than the simpler alternative of calling `SQLiteHelper.DB_PATH` (a property already
exposing `self._db_path` directly, `helper.py:112-115`, which would avoid the PRAGMA
query and the column-index class of bug entirely). The index-fix approach is kept
because the requirement doc's Tests section explicitly expects verification "via a
mocked `PRAGMA database_list` result," so the plan stays faithful to the specified
test surface; the `DB_PATH`-property alternative is noted here for awareness only, not
adopted, and is available as a lower-risk follow-up if this code path is revisited
later.

## Risks

- **Risk:** An abandoned `run_in_executor` worker thread (checkpoint stage timed out
  but the underlying blocking SQLite/OS call is still running) is a live, non-daemon
  `ThreadPoolExecutor` worker; if it never returns (e.g. genuine OS-level I/O stall not
  bounded by `busy_timeout`), it could delay CPython's interpreter-shutdown atexit hook
  (`concurrent.futures.thread._python_exit`) at process exit — the same class of issue
  `scripts/agent/http_lifecycle.py:95-103` explicitly documents avoiding for
  `proc.wait()`.
  **Likelihood:** low — unlike `proc.wait()` (unbounded by design), every SQLite call
  in this path is independently bounded (~30s) by `busy_timeout`/`sqlite_timeout`; the
  scenario requires an OS/filesystem-level stall outside SQLite's own lock-contention
  handling, which is a narrower failure mode.
  **Mitigation:** default `_WAL_CHECKPOINT_TIMEOUT_S`/`_WAL_BACKUP_TIMEOUT_S` are kept
  well below typical process-supervisor SIGTERM->SIGKILL grace periods, so even if a
  worker thread is abandoned, the process-level shutdown path (outside Python's own
  atexit machinery, e.g. a supervisor's SIGKILL) still bounds total shutdown time; this
  residual risk is accepted and tracked (see `issues/20260726-095326_risks.md`) rather
  than solved in this change, consistent with the requirement doc's explicit direction
  to use this exact mechanism.
- **Risk:** Splitting one connection/one `with` block into two independent
  `SQLiteHelper("session")` connections (checkpoint stage, backup stage) doubles the
  number of connection open/close cycles during shutdown versus the current
  single-connection implementation.
  **Likelihood:** low — `SQLiteHelper.open()`/`close()` are lightweight
  (`sqlite3.connect()` + a few `PRAGMA` statements); this already happens once per
  session shutdown, not in a hot loop.
  **Mitigation:** none needed structurally; covered by the full-suite regression run
  and the manual real-DB validation step (no lock contention) in the Validation plan,
  which would surface any unexpected double-open failure.
- **Risk:** Existing tests patch `agent.repl.SQLiteHelper` as a single mock reused
  across the whole `_close_resources()` call; with two separate `SQLiteHelper("session").open(...)`
  call sites (checkpoint stage, backup stage), a test's mock configuration (e.g.
  `mock_db.execute.return_value.fetchone.return_value = ("wal",)` reused for every
