# Plan: Triage Widespread Test Suite Drift Clusters

## Goal
Triage 10 distinct test drift clusters identified in the test suite, determine whether each cluster represents a stale test or an implementation regression, and split each into its own follow-up issue for resolution.

## Priority
High

## Scope
- **In-Scope**: Triage of the 10 error signature clusters documented in the source issue; root-cause determination (stale test vs. implementation bug); creation of follow-up issues for actionable items.
- **Out-of-Scope**: Fixing the clusters themselves (handled by follow-up issues); resolving the separate `test_repl.py` KeyboardInterrupt defect (tracked separately).

## Background
A full `uv run pytest tests/ -q --timeout=20 --ignore=tests/agent/test_repl.py` run against `origin/master` reported 579 failed, 6399 passed, 16 skipped, 3 errors. Distinct error signatures indicate at least 10 separate root causes — mostly renamed/removed attributes, methods, or constructor keyword arguments that the corresponding tests were never updated for. Several clusters have since been resolved by commits that removed the stale symbols.

## Problem
The test suite does not reflect the current state of the implementation for a large fraction of the `scripts/agent/` and related test surface. Several clusters identified in the original run have since been resolved by commits that removed the stale symbols; remaining clusters require triage to determine whether they represent stale tests or implementation regressions.

## Reason for change
A test suite this far out of sync defeats its purpose as a safety net — any cluster could be masking either a real implementation bug or dead/incorrect test expectations. Several clusters have been resolved since the original run; remaining clusters require triage before they can be assumed safe.

## Implementation intent
Verify each cluster's claims against current repository evidence, classify each as stale test or implementation regression, and produce follow-up issues for actionable items. Do not attempt fixes during this phase.

## Requirements
- `REQ-001`: Confirm which of the 10 clusters remain valid (reproducible against current source) and which are outdated.
- `REQ-002`: For each valid cluster, determine authoritative behavior (implementation vs. test).
- `REQ-003`: Create a follow-up issue for each actionable cluster requiring resolution.
- `REQ-004`: Document the validation quality baseline for the affected modules.
- `REQ-005`: Verify Cluster 9 (RegistryEntry.__init__) — RegistryEntry class no longer exists in current source.

## Design
This is a Path B task (> 3 files affected, interface changes, DB schema changes). Architecture analysis shows the affected modules span multiple layers: shared config (mcp_config), agent services (security_audit, startup), RAG ingestion (ingester), database consistency (session_consistency), and orchestration (orchestrator). Dependency graphing reveals that stale test references create cascading failures across the test surface. Historical analysis would show high churn in these areas due to recent refactors. Operational dependency inspection confirms no running processes hold locks on these files.

The design approach is read-only verification: confirm each cluster's claim against current source, classify as stale test or implementation regression, then produce follow-up issues. No code modifications during this phase.
