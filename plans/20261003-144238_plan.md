## Background
The Needs Confirmation Inventory in `docs/00_governance/governance_03_issue-and-uncertainty-management.md` is the single central place for unresolved items; a marker left only in an individual document is not allowed. The checker reports orphaned markers at WARNING severity but exits 0 regardless of findings. This was observed on 2026-10-01 with 8 warnings in `docs/23_agent/` and `docs/21_rag/`.

## Problem
Whether warnings from the checker should cause a non-zero exit is currently undecided. The original issue (`issues/20261001-103602_ncinv001_detect-orphaned-needs-confirmation-markers-in-governance-docs.md`) states "Whether warnings should fail verification is Needs confirmation," so the decision was deferred and remains open.

## Reason for change
The checker's exit status affects CI/CD pipelines and automated verification workflows. If warnings should block verification, the exit code must reflect that; if warnings are informational only, exit 0 is correct. A decision is needed to avoid ambiguity in downstream consumers. The classification rule this check depends on (ncinv001) is already implemented in current source, so the remaining gap is solely the unresolved exit-status decision.

## Implementation intent
Make a decision based on the checker's intended role (detection vs enforcement), then record it at three touchpoints: the checker's module docstring (code-level record), the documentation-checks reference (governance record), and a regression test (behavioral lock). No behavioral change to `report_and_exit()` is made — the decision confirms and documents the existing exit-0-for-warnings behavior.

## Design
Owner decision (recorded by this Plan, ncinv002): **warnings → exit 0 (detection mode).**

Evidence supporting the recorded decision:
- The checker author deliberately assigned `severity="WARNING"` to untracked inline
  markers (`check_needs_confirmation_inventory.py:274,288`), distinct from the
  `severity="ERROR"` used for declared-field-count mismatches (`:318`). Combined with
  `report_and_exit()` failing only on ERROR (`tools/_docs_consistency_lib.py:414-427`),
  this is a deliberate non-blocking design, not an oversight.
- Backward compatibility: `check-needs-confirmation` is a registered
  `[project.scripts]` console script invoked as a workflow gate (`pyproject.toml`,
  `routing.md`). Retroactively flipping warnings to non-zero would turn already-passing
  runs red without migration.
- Enforcement of the "no orphaned markers" policy is achieved through the inventory
  registration requirement plus the warning surfacing them, not through the exit code.
  The checker's role is detection/remediation-triggering, not gating.

Alternative path (documented for a later enforcement decision, not implemented here):
if the team later decides warnings should block CI, reassign the untracked-marker and
missing-field findings from `WARNING` to `ERROR` severity in
`check_untracked_inline_markers()` / `check_missing_nc_fields()`. That single-class
change makes `report_and_exit()` fail on those findings, converting detection into an
enforcement gate. The regression test added under `REQ-003` covers whichever posture is
adopted.

## Risks
- **Risk**: Recording exit 0 may lead consumers to assume exit 0 means "all clean," while orphaned markers still exist. → **Mitigation**: Document explicitly that exit 0 does NOT imply zero untracked items; the WARNING count remains visible in output; remediation is tracked in the Needs Confirmation Inventory. - **Risk**: A future refactor of `report_and_exit()` could silently invert the exit contract. → **Mitigation**: The module-docstring note (REQ-001) plus the regression test (REQ-003) jointly document and lock the contract.
- **Risk**: If the team later adopts enforcement (non-zero), already-passing CI runs flip to red. → **Mitigation**: The decision is reversible; the test and doc make the transition safe and reviewable. No CI config file changes are involved.
