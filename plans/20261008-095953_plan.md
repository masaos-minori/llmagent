## Goal
- Put the rag-pipeline MCP server and the Agent's RAG HTTP delegation under the same shared Bearer authentication as every other MCP server, and make authentication failures and error responses fail closed instead of falling back to local execution or being injected as retrieval context.

## Priority
High

## Scope
- **In-Scope**:
  - Attach `attach_auth_middleware(app, <auth_token>)` to the rag-pipeline FastAPI app from its own configured token, following the pattern used by the other MCP servers.
  - Switch `call_rag_service()` from the private `X-RAG-Token` header to the shared `Authorization: Bearer <token>` header.
  - Introduce a dedicated RAG result type that classifies success / empty / auth-error / transient-failure; on auth error `RagPipeline.augment()` raises `RagPipelineError` without any local fallback.
  - Set `http_result_kind="auth_error"` on 401/403 and treat `is_error=True` responses as failures whose fallback is decided by result kind.
  - Replace the `==` token comparison in `server.py` with `hmac.compare_digest`.
  - Replace `assert`-based type validation with explicit exceptions; fix the stale docstrings; make the per-attempt request timeout a named module constant.
  - Wire `auth_token` into `rag_pipeline_mcp_server.toml` (sourced from the environment) so the middleware has a non-empty token to enforce.
  - Update the security and ADR documentation and remove the resolved Known Issues from the governance ledger.
- **Out-of-Scope**:
  - Changing RAG retrieval or ranking behavior.
  - Authentication for any MCP server other than rag-pipeline.
  - Redesigning the two-stage fetch / `selected_hits` mechanism beyond what the fail-closed change requires.

## Background
This Plan consolidates three findings from the MCP/EventBus/Agent investigation notes into one release: RAG-001 (a 401/403 from the RAG service currently falls back to the in-process pipeline), a finding that `rag_pipeline_server.py` attaches no authentication middleware, and a finding that the response `is_error` flag is not honored on the RAG path. ADR-007 INV-09 and `security_01` require Bearer authentication across MCP servers; ADR-004 and ADR-010 INV-04 forbid masking a failure behind local execution. RAG-001 is currently tracked as an open Known Issue in the governance ledger (`governance_03_issue-and-uncertainty-management.md`) and in ADR-010 INV-04.

## Problem
- `rag_pipeline_server.py` never calls `attach_auth_middleware()`, so `/v1/call_tool`, `/rag_run_pipeline`, and `/rag_debug_pipeline` are reachable without a token, including the destructive `rag_delete_document` tool. Every other MCP server already registers the middleware (`web_search`, `git`, `cicd`, ...); rag-pipeline does not.
- `call_rag_service()` sends `X-RAG-Token`, not the shared `Authorization: Bearer` header, so even when a token is configured it is not recognized by the shared auth contract.
- On 401/403 `call_rag_service()` returns `None`; the caller treats `None` as "fall back to local execution". This is latent today because no token is required, and becomes a real fail-open hole once Bearer auth is added.
- Nothing sets `http_result_kind` to `"auth_error"`; a 401/403 is classified identically to a transient failure.
- The request timeout is a bare literal, the per-attempt header construction and the return contract are undocumented against current behavior, and `HttpAugment.run()` / `RagPipeline.augment()` use `assert` for runtime type validation (removed under `python -O`).

## Reason for change
- Missing authentication violates ADR-007 INV-09 and `security_01`; on loopback another local process can delete documents or run the pipeline unauthenticated.
- Hiding an authentication failure behind local execution masks token misconfiguration and revoked access (ADR-004, ADR-010 INV-04) and leaves RAG broken between the auth switch and any later fix.
- `assert`-based validation cannot enforce runtime invariants, and a non-constant-time token comparison does not meet the basic security bar.

## Implementation intent
- Register the existing `attach_auth_middleware()` on the rag-pipeline app from `RagPipelineConfig.auth_token`, mirroring the other servers' module-level registration.
- Route the RAG client through the shared `Authorization: Bearer` header.
- Replace the `str | None` return contract of `call_rag_service()` with a small tagged result type carrying `(kind, result, status_code, latency_ms)`; thread the `auth_error` kind up through `HttpAugment.run()` and `AugmentRefiner.run_http_augment()` so `RagPipeline.augment()` raises `RagPipelineError` instead of falling back.
- Keep the success/empty/transient paths behavior-preserving; only the auth-error branch changes control flow.

## Design

### Result type (REQ-003, REQ-004)
The current `call_rag_service()` returns a bare `(str | None, int | None, float)`
tuple. The `None` payload is overloaded: it means both "the service returned an
empty body" and "the service rejected us with 401/403", and the caller collapses
both into "fall back to local execution". Two designs were considered:

- **Option A — tagged result object.** Replace the tuple with a frozen dataclass
  `CallRagResult(kind, result, status_code, latency_ms)` where `kind` is one of
  `success` / `empty` / `auth_error` / `transient_failure`. Callers branch on
  `kind`; `auth_error` raises `RagPipelineError`, the others preserve current
  behavior.
- **Option B — raise on auth error inside `call_rag_service()`.** Simpler control
  flow, but it moves the auth-error decision out of the classification layer and
  makes the retry loop harder to reason about.

**Decision: Option A.** It matches the issue's stated intent ("introduce a
dedicated result type"), keeps the success/empty/transient paths behavior-
preserving, and lets `http_result_kind` carry an explicit `auth_error` value
(`HttpResultKind.AUTH_ERROR` already exists in `models_result.py`). The `kind`
value maps to `HttpResultKind` via the existing `_HTTP_RESULT_KIND_MAP` in
`http_augment.py`.

### Auth middleware registration (REQ-001)
Mirror the established module-level registration used by the other servers
(`web_search_server.py`, `git_server.py`, `cicd_server.py`): call
`attach_auth_middleware(cast(_FastAPIApp, app), <token>)` once, at module scope,
immediately after `app` is created. The token comes from `RagPipelineConfig.auth_token`
populated by `rag_pipeline_mcp_server.toml`. An empty token yields the same
accept-all fallback the other servers already have, so the config change
(`auth_token` populated from the environment) is what actually turns auth on.

### Bearer header (REQ-002)
`call_rag_service()` builds its header dict and sends `Authorization: Bearer
<token>` instead of `X-RAG-Token`. No conditional `if auth_token:` guard should
drop the header when a token is configured; keep the existing "no header when no
token" behavior for the unconfigured case.

### Fail-closed propagation (REQ-003)
`HttpAugment.run()` reads the new `kind`; `run_http_augment()` surfaces it;
`RagPipeline.augment()` raises `RagPipelineError` on `auth_error` before the
in-process DB is opened, so no partial retrieval context is produced. The
`is_error=True` body flag (REQ-005) is folded into the same classification: an
`is_error=True` response is classified as a failure whose fallback is decided by
result kind, never injected as context.

### Timeout constant (REQ-007)
Extract the per-attempt timeout literal into a named module constant in
`pipeline_service.py` (e.g. `_REQUEST_TIMEOUT_SECONDS`); reference it in the
docstring so the documented value matches the code.

## Risks
- **Risk**: Changing `call_rag_service()`'s `(str | None, int | None, float)` return contract breaks every caller and the three RAG tests that unpack the tuple. → **Mitigation**: Update `test_pipeline_http_result_kind.py`, `test_rag_http_mode.py`, and `test_rag_pipeline_service.py` together with the implementation; keep the success/empty/transient payloads identical so only the auth-error branch changes control flow.
- **Risk**: Registering `attach_auth_middleware()` with an empty token leaves rag-pipeline accept-all (same as now), defeating REQ-001. → **Mitigation**: Populate `auth_token` in `rag_pipeline_mcp_server.toml` from the environment before enabling the middleware; verify via the subprocess auth test that a non-empty token is enforced.
- **Risk**: The shared base-class change in `server.py::_is_authorized()` affects every MCP server. → **Mitigation**: Keep the comparison semantics identical except for constant-time; run the full `tests/mcp_servers/` suite and the production security regression suite.
- **Risk**: UNK-01 — the external RAG service may not accept the shared `Authorization: Bearer` header. → **Mitigation**: Confirm the external service's auth contract during implementation; scope REQ-002 to the local rag-pipeline server if the external service uses a different scheme.
- **Risk**: UNK-02 — the residual `is_error`/`selected_hits` gap behind REQ-005 is unconfirmed and current source shows both are already handled. → **Mitigation**: Confirm with the issue author which gap remains; narrow or drop REQ-005 if none, so the release is not blocked on an ambiguous requirement.
- **Risk**: Fail-closed on 401/403 changes observable behavior for any deployment where `rag_service_url` is set. → **Mitigation**: Verify UNK-03 (whether `rag_service_url` is configured anywhere); since both current TOMLs leave it empty, the fail-closed path is exercised only once a URL is configured, limiting blast radius.
- **Risk**: Implementers log the bearer token while wiring auth (issue constraint: "Do not log tokens"). → **Mitigation**: Route the token through `attach_auth_middleware`'s existing redaction; add a regression assertion that no token appears in logs; treat token logging as a blocking finding.
- **Risk**: Releasing auth, the Bearer switch, and the fail-closed result type in separate changes leaves RAG broken mid-release (issue constraint: "released together"). → **Mitigation**: Ship all three as one change; enforce via the single-change implementation instruction and a combined test pass before release.
