## Goal
Define and enforce an explicit, documented meaning for a `0`/negative per-server concurrency limit in `ToolTransportInvoker._ensure_semaphores` (treating it as "unlimited" with a visible warning), removing the silent filter that currently leaves such a server without a semaphore.

## Priority
Low

## Scope
- **In-Scope**:
  - Document in `scripts/shared/tool_transport_invoker.py` that a `0`/negative `tool_concurrency_limits` value means "unlimited" (no semaphore is created), consistent with the unconfigured default.
  - Emit a warning when a `0`/negative limit is seen for a known server key, making the chosen semantics visible instead of a silent drop.
  - Add a test asserting the chosen behavior for a `0` limit (unlimited + warning) and for a positive limit (bounded semaphore).
  - Note the `0` semantics in the `tool_concurrency_limits` config reference doc.
- **Out-of-Scope**:
  - Changing the semantics of a positive limit.
  - Changing semaphore acquisition order (`_execute_with_semaphore` / `_maybe_semaphore`).
  - Any change to how unknown server keys are warned about.
  - Non-MCP concurrency controls.

## Background
`ToolExecutor` accepts `concurrency_limits: dict[str, int] | None`, keyed by server key, to bound how many tools run concurrently per MCP server. Semaphores are created lazily in `_ensure_semaphores` and acquired in `_execute_with_semaphore` around each transport call. The config field is `ToolConfig.tool_concurrency_limits: dict[str, int]` (`scripts/agent/config_dataclasses.py`), loaded via `_get_dict` in `scripts/agent/config_builders.py` (no per-value validation) and wired to the invoker in `scripts/agent/factory.py`.

## Problem
```python
self._semaphores = {
    key: asyncio.Semaphore(n)
    for key, n in self._concurrency_limits.items()
    if n > 0          # <-- 0 and negatives are dropped here
}
```
A config entry such as `{ "server": 0 }` produces no semaphore for that server, so `_execute_with_semaphore` acquires nothing and concurrency is unlimited. There is no warning for a known server key whose limit is `0` (the existing warning only fires for keys absent from `server_configs`). So `0` is an ambiguous, silent "no limit" rather than an error or an explicit "1" cap.

Clarification (adversarial review): the resulting behavior is self-consistent rather than silently wrong — a `0` limit resolves to exactly the same state as omitting the key entirely (no semaphore, unbounded), which is the documented default for unconfigured servers, and matches the common `0` = "unlimited" convention. The defect is therefore narrow: an operator who sets `0` receives no feedback about which meaning applied, and `0` cannot be used to express "serial only". It is a clarity / config-convention gap, not a correctness, safety, or crash defect.

## Reason for change
`0` is a natural value to type when someone wants "no concurrency" or "serial only", and either reading yields the opposite of the other. Under high fan-out this can let far more parallel requests hit a server than operators assumed, defeating the backpressure the config exists to provide.

## Implementation intent
Pick and document one semantics for `0` and enforce it consistently. Adopt the lower-risk option: treat `0`/negative as "unlimited" (explicitly, with a clear comment and a warning when a `0`/negative limit is seen) rather than coercing to a minimum of `1`. Coercing to `1` can regress a deployed config that currently relies on `0` meaning "unlimited" by capping that server at a single in-flight call, whereas documenting "unlimited" cannot cause a throughput regression. No established serial-only (`0` -> 1) convention exists in the repo (searched `docs/` and config loaders), and the codebase's `0` = "disabled/throttle-off" convention for integer fields supports the "unlimited" reading. Keep the change minimal and backward compatible with existing passing tests; do not touch positive-limit handling or semaphore acquisition.

## Design
**Chosen semantics.** Adopt option (a): a `0`/negative `tool_concurrency_limits` value means "unlimited" — no semaphore is created — and a warning is emitted when such a value is seen for a known server key. Do NOT coerce to a minimum of `1`.

**Rationale (Step 5 analysis):**
- **Asymmetric risk.** Coercing `0` → `1` caps a server at a single in-flight call. If any deployed config currently relies on `0` meaning "unlimited", coercion silently regresses its throughput under high fan-out. Documenting "unlimited" produces exactly the state as omitting the key (the unconfigured default), so it cannot cause a throughput regression. Lower risk wins.
- **No established serial-only convention.** Searched `docs/` and the config loaders; no convention maps `0` → `1` for concurrency. The closest codebase convention — `0` = "disabled / throttle-off" for integer config fields — reads naturally as "no throttle" = unlimited, supporting option (a).
- **Self-consistency.** The current behavior is not silently wrong: a `0` limit already resolves to the unconfigured default (no semaphore, unbounded). The defect is a clarity/convention gap (no feedback to the operator; `0` cannot express "serial only"), not a correctness/safety/crash defect. Option (a) closes the gap without changing observable behavior for valid configs.

**Mechanism.** Keep the existing `if n > 0` filter (0/negative → no semaphore = unlimited, unchanged). In `_ensure_semaphores`, detect `0`/negative limits for known server keys and emit a `logger.warning` stating they are treated as unlimited (no semaphore). Because `_ensure_semaphores` is guarded by `if self._semaphores is None`, the warning fires once per process. Update the `_ensure_semaphores` docstring to state the `0`/negative = unlimited semantics explicitly.

**Scope boundary.** `mcp_03_02_tool-registry.md` documents the runtime `concurrency_limits` mechanism; it is read to avoid contradiction but is deliberately excluded from the frozen modification scope (it describes the general mechanism, not the `tool_concurrency_limits` config key). Only the config reference `agent_08_03_configuration-tools-memory.md` is updated. This keeps the change at 3 target files (Path A).
