## Problem
The test patches `orch._conversation_manager.handle_memory_injection` to raise `RuntimeError("unexpected error")`, then wraps `await orch.handle_turn("test")` in `pytest.raises(RuntimeError)`. The turn does not raise, so the assertion block never executes and pytest reports `DID NOT RAISE`.

Root cause (confirmed by reproduction): `handle_turn` routes through `WorkflowEngineAdapter.execute_turn`, which runs the turn inside the workflow engine. The engine's `_run_stage_with_retry` catches the `RuntimeError`, retries up to `max_attempts` (3), then converts it to `WorkflowHaltError`. `execute_turn` catches `WorkflowHaltError` and routes it through `_handle_workflow_halt`, which logs and invokes the `on_error` callback without re-raising. The exception therefore never escapes `handle_turn`.

Config restoration itself already works: `_process_turn` wraps the turn body in the `_tool_override` context manager, whose `finally` clause restores `allowed_tools` to its original value before any exception leaves the block. So the property under test holds; only the propagation assertion is stale.

## Reason for change
The test asserts a stale premise (that the exception propagates) that contradicts the engine's deliberate retry/halt design and the live REPL caller's expectation that `handle_turn` does not raise.

## Design
The failure is a test/contract mismatch, not a broken config-restore path. The current call chain is:

`Orchestrator.handle_turn` -> `Orchestrator._execute_turn` -> `WorkflowEngineAdapter.execute_turn`, which starts the turn inside `WorkflowEngine.run`. The engine runs the `execute` stage through `_run_stage_with_retry`; when the stage function raises, the engine retries per `RetryPolicy(max_attempts=3)` and, once attempts are exhausted, raises `WorkflowHaltError`. `execute_turn` catches `WorkflowHaltError` (and `WorkflowTimeoutError`) and calls `_handle_workflow_halt`, which logs and fires the `on_error` callback but does not re-raise. Any other exception type is re-raised by `engine.run`, but it is still not propagated past `execute_turn` unless it is one of those handled types — in practice the engine consumes the error and returns a normal `(answer, error_kind, is_partial)` tuple.

Because the turn body runs inside `_tool_override`, `allowed_tools` is restored regardless of how the exception exits the body. The test's only incorrect assumption is that the exception escapes `handle_turn`.

Two resolution branches exist:
- **Catch-and-halt (recommended)**: The engine's retry/halt subsystem is comprehensive and clearly deliberate, and the REPL caller does not guard `handle_turn` against exceptions. Under this contract the correct fix is to rewrite the test to assert the observed, intended behavior: `handle_turn` completes without raising, `allowed_tools` is restored, and `on_error` is fired (or the task is halted). This is a single-file test change (Path A).
- **Propagate (fallback)**: Only adopt if evidence shows propagation was intended. This would require special-casing memory-injection errors to bypass the retry/halt conversion and escape `handle_turn`, scoped strictly to this call site. It changes a runtime interface and escalates to Path B.
