# Plan: Limit HALF_OPEN trial calls to one

## Goal

Allow only a single trial call while a server's circuit breaker is HALF_OPEN, and make other calls wait or be rejected until the result is known.

## Priority

Low

## Scope

- **In-Scope**:
  - `scripts/shared/mcp_health.py`: add a per-server in-flight trial flag (`_half_open_trials`) and acquire/release to `McpServerHealthRegistry`; set the flag atomically at the UNAVAILABLE→HALF_OPEN transition in `is_unavailable()`.
  - `scripts/shared/tool_transport_invoker.py`: gate `_check_health()` HALF_OPEN dispatch on the trial flag and release it on every exit path (success, failure, cancellation).
  - `docs/22_mcp/mcp_03_01_dispatch-and-routing.md`: update the circuit-breaker description if it states trial behavior.
- **Out-of-Scope**:
  - Breaker thresholds and timing.
  - Other circuit breaker states (HEALTHY, DEGRADED, UNAVAILABLE entry).

## Background

Source: local investigation notes (memo1.md, ISSUE-13), from an earlier review finding.

## Problem

- When the circuit breaker is HALF_OPEN, `_check_health()` lets all calls through, so any number of trial calls can flow concurrently (Explicit in code — `scripts/shared/tool_transport_invoker.py` logs "allowing trial dispatch" for every call in that state).

## Reason for change

- HALF_OPEN exists to test recovery with one call; sending many at once concentrates load on a recovering server and can cause another failure.

## Implementation intent

- Restrict HALF_OPEN to one in-flight trial. The in-flight flag must be set atomically at the UNAVAILABLE→HALF_OPEN transition (inside `is_unavailable()`) and released on success/failure/cancellation, so a concurrent burst yields exactly one trial. Gating only `_check_health()`'s HALF_OPEN branch is insufficient because the first trial call enters via the transition path, not that branch.

## Assumptions

- The dispatch layer is asyncio (single event loop), so a plain `set` is atomic between awaits; the gate must therefore be established at the transition point where no `await` intervenes, not in a downstream branch that runs after the state has already become HALF_OPEN.
- The "unavailable" error message for rejected calls should clearly indicate the reason (e.g. "trial in progress").
- The existing `is_unavailable()` transition logic (UNAVAILABLE → HALF_OPEN) remains the single place the trial window opens.

## Design

### Decision matrix

| Condition | Outcome |
|---|---|
| Server in HALF_OPEN + no in-flight trial | Allow this call as the trial |
| Server in HALF_OPEN + in-flight trial active | Reject with "unavailable" error |
| Trial succeeds | Transition to HEALTHY, release trial flag |
| Trial fails | Transition to UNAVAILABLE, release trial flag |
| Trial cancelled | Release trial flag |

### Decision details

1. **Add a per-server in-flight trial flag to `McpServerHealthRegistry`**: Add a set `_half_open_trials: set[str]` plus `_acquire_trial(server_key)` / `_release_trial(server_key)` methods.
2. **Set the flag atomically at the transition (not in `_check_health()`)**: In `is_unavailable()` (mcp_health.py:88-94), when transitioning UNAVAILABLE→HALF_OPEN, set the in-flight flag in the same synchronous step (no `await` between the check and the set). This is where the single trial window opens; the first trial call enters here, so gating must live here.
3. **Gate `_check_health()` on the flag**: In `tool_transport_invoker.py`, when state is HALF_OPEN, allow the call only if no trial is already in flight; otherwise return an "unavailable" error result. Subsequent calls after the first observe HALF_OPEN and are rejected because the flag is set.
4. **Release the flag on every exit path**: Hook release into `record_success` (→HEALTHY) and `record_failure` (→UNAVAILABLE), and wrap the invoke path in `try/finally` so cancellation also releases.
5. **Update documentation**: Update `mcp_03_01_dispatch-and-routing.md` if it states that multiple trial calls are allowed.
