## Goal

Add a denylist-based validation for `McpServerConfig.env` in `scripts/shared/mcp_config.py`, mirroring the existing `env_denylist` pattern in `config/shell_mcp_server.toml`, so that dangerous env var keys (`LD_PRELOAD`, `LD_LIBRARY_PATH`, `PYTHONPATH`) cannot be silently merged into an MCP server subprocess environment via `config/agent.toml`.

## Scope

**In-Scope:**
- Extend `McpServerConfig._validate_cross_fields()` in `scripts/shared/mcp_config.py` (the existing `env` type-check loop at lines 115-119) to also reject keys matching a denylist of dangerous glob patterns, raising `ValueError` with a message identifying the offending key.
- Hardcode the denylist as a module-level constant reusing the same default values as `config/shell_mcp_server.toml`'s `env_denylist` (`LD_PRELOAD`, `LD_LIBRARY_PATH`, `PYTHONPATH`), matched via `fnmatch.fnmatch` (consistent with `scripts/mcp_servers/shell/shell_service.py::_filter_env`).
- Add a short code comment at `HttpServerLifecycleManager.start()` (`scripts/agent/http_lifecycle.py:224-226`) noting that env is validated upstream at config-load time in `McpServerConfig`, so no duplicate filtering is needed there.
- Add unit tests in `tests/test_mcp_config_validation.py` covering: a denylisted key raises `ValueError`; a non-denylisted key continues to validate successfully.

**Out-of-Scope:**
- Adding a new configurable `env_allowlist`/`env_denylist` TOML option scoped to `[mcp_servers.<key>]` (option (b) from the requirement) — approach (a), a hardcoded shared denylist, is chosen instead since it is the smaller, immediately-testable change and no current `config/agent.toml` entry defines `env`, so there is no configurability need yet.
- Any change to `scripts/mcp_servers/shell/shell_service.py` or `config/shell_mcp_server.toml` (the precedent, left untouched).
- Any change to `HttpServerLifecycleManager.start()`'s env-merge logic itself (`env = {**os.environ, **cfg.env}` stays unchanged; only a documentation comment is added).
- Runtime/behavioral changes to MCP server startup for any currently configured server (none define `env` today).

## Assumptions

1. `cfg.env`/`cfg.cmd` in `config/agent.toml`-family files are admin-controlled, not derived from untrusted runtime input (stated in the requirement's Background/Problem sections).
2. Rejecting (raising `ValueError`) rather than silently filtering is preferred, per Implementation Instructions point 3 ("prefer config validation, since it fails fast at startup rather than at subprocess-spawn time") — fail-fast at config-load beats silent filtering that could mask a misconfiguration.
3. No currently deployed `[mcp_servers.<key>]` section in `config/agent.toml` sets `env`, so this change has zero behavioral impact on existing valid configs (verified below).
4. The denylist only needs to match the three key names cited in the requirement (`LD_PRELOAD`, `LD_LIBRARY_PATH`, `PYTHONPATH`) plus glob-pattern support for consistency with the shell precedent; no additional dangerous keys were specified and none are added speculatively.

## Risks

- **Risk**: A future `config/agent.toml` entry legitimately needs an env var whose name happens to match a denylist glob pattern (unlikely for `LD_PRELOAD`/`LD_LIBRARY_PATH`/`PYTHONPATH` specifically, but possible if the denylist is later broadened) → **Mitigation**: Keep the denylist scoped to the three explicitly named dangerous loader/interpreter variables from the requirement; do not speculatively add more patterns. Document the rationale in the code comment so future maintainers understand why these three are blocked.
- **Risk**: Raising `ValueError` at `McpServerConfig` construction time (inside `__post_init__`) could crash agent startup entirely if a config file is misconfigured with a denylisted key, rather than degrading gracefully → **Mitigation**: This matches the existing fail-fast behavior of every other `_validate_cross_fields()` check (missing `url`, missing `cmd`, negative timeouts, etc.) — consistent with the codebase's existing config-validation posture, and preferred per the requirement's own guidance to fail fast at startup rather than at subprocess-spawn time.
- **Risk**: Duplicating filtering logic in both `McpServerConfig` and `HttpServerLifecycleManager.start()` if a future contributor doesn't realize validation already happens upstream → **Mitigation**: Add the explicit code comment at `http_lifecycle.py:224` (Phase 2 step) referencing `McpServerConfig._validate_cross_fields()` as the single enforcement point, per Implementation Instructions point 3 ("do not duplicate filtering logic in both places").
- **Risk**: `fnmatch`-based matching could have unintended false positives if a legitimate env var name happens to match a glob wildcard pattern in the denylist → **Mitigation**: The three default entries (`LD_PRELOAD`, `LD_LIBRARY_PATH`, `PYTHONPATH`) contain no wildcard characters, so they only match exact names; risk is negligible with the current denylist contents.
