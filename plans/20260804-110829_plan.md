# Plan: Correct the stale "cosine distance" docstring in `SQLiteVectorStore.vec_search`

## Goal
`scripts/db/store_impl.py:39`'s `vec_search` docstring names L2 (Euclidean) distance instead of
"cosine distance", while `scripts/db/schema_sql.py`'s `chunks_vec` DDL and
`scripts/rag/repository.py:144`'s docstring remain byte-for-byte unchanged, and
`grep -rn "cosine" scripts/db scripts/rag` no longer attributes cosine semantics to the
`chunks_vec` / `vec_search` search path.

## Scope

**In scope:**
- `scripts/db/store_impl.py:39` — rewrite the one-line docstring of `SQLiteVectorStore.vec_search`
  to name L2/Euclidean distance, matching the wording style of `repository.py:144`.
- Post-edit grep verification that no sibling docstring in `scripts/db`/`scripts/rag` still
  attributes cosine semantics to `chunks_vec`.

**Out of scope:**
- `scripts/db/schema_sql.py`'s `chunks_vec` DDL — already correct (`distance_metric=L2`, added by
  commit `556490796`), must not change.
- `scripts/rag/repository.py:144`'s docstring — already correct, must not change.
- Any behavior, SQL, signature, or return-value change to `vec_search` — this is a comment-only
  fix; `vec_search`'s actual runtime behavior is already L2 and is not being altered.
- A new empirical `sqlite-vec` extension test — the metric is already settled at the source level
  (explicit `distance_metric=L2` clause plus two independently-correct docstrings referencing L2
  for the same table); no runtime ambiguity remains to justify writing one.
- `rag/utils.py::cosine_sim` and its callers (`rag/cache.py:61`) — genuinely cosine-based, unrelated
  embedding-cache dedup logic; out of scope and expected to still match "cosine" in the verification
  grep.
- `docs/*.md` — document-only planning phase; also this is a source docstring fix with no
  user-facing behavior change, and the one `docs/` file that historically tracked this ambiguity
  (`docs/00_governance_07_needs-confirmation-inventory.md`, NC-004) is already marked
  `Status: resolved` with a resolution note naming `distance_metric=L2` — no doc update is needed or
  in scope here.

## Assumptions

   `scripts/db/schema_sql.py:47-51`. **Verified**: the `CREATE VIRTUAL TABLE ... USING vec0(...)`
   statement carries an explicit `distance_metric=L2` clause (confirmed present at those exact
   lines), added by commit `556490796` ("fix: resolve NC-001 through NC-021 needs-confirmation

   `+        distance_metric=L2` to the `chunks_vec` block (and, in the same diff, to the sibling
   `memories_vec` block).

   make L2 and cosine distance equivalent (which could otherwise make the old docstring "harmlessly
   wrong"). Falsifiable by reading the ingestion insert path. **Verified**:
   `SQLiteVectorStore.vec_insert` (`scripts/db/store_impl.py:30-36`) inserts the raw embedding bytes
   directly via `INSERT INTO chunks_vec (chunk_id, embedding) VALUES (?, ?)` with no call to
   `cosine_sim` or any normalization helper.
3. `scripts/rag/repository.py:144`'s docstring is already correct and is the right style reference.
   Falsifiable by reading it. **Verified**: line 144 reads `"""Retrieve top_k chunks by L2-distance
   KNN (smaller distance = higher similarity)."""` (method is `RagRepository.vector_search`, not
   `search_vec` as the requirement doc loosely named it — a naming slip in the requirement's own
   text, not a defect; the requirement itself hedges with "or equivalent").

   `memories_vec` path. **Verified**: line 185 reads `# Negate L2 (Euclidean) distance: MemoryHit.score
   convention is higher-is-better`, confirming the same NC-004 commit updated both sides.
5. No other file in the repository currently misattributes cosine semantics to `chunks_vec` or
   `vec_search`. Falsifiable by a repo-wide grep. **Verified**: `grep -rn "cosine" scripts/db
   scripts/rag` returns exactly one hit needing this fix (`store_impl.py:39`); the other four hits
   (`rag/utils.py:41-42`, `rag/cache.py:15,61`) are the genuinely cosine-based, unrelated
   embedding-cache dedup path. A broader repo-wide grep (`.py`/`.md`, excluding `.venv`,
   `node_modules`, `__pycache__`) surfaces only historical/done plan and issue files
   (`issues/done/*`, `plans/done/*`, `implementations/done/*`) that correctly describe this same
   docstring defect as a past-tense finding, plus unrelated `cosine_sim`/`SemanticCache` material —
   none of which is a live, uncorrected second instance of the defect.
6. `tests/db/test_db_store_impl.py::test_vec_search_*` (5 tests, lines 301-341) assert delegation
   behavior against a mocked DB layer and do not assert on docstring text or actual distance values,
   so they cannot regress from this change and require no edits.
