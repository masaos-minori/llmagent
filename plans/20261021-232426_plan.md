# Plan

## Goal
Make `StartupInterrupted` distinguishable from ordinary startup failures by rebasing it onto `BaseException`, so broad `except RuntimeError` / `except Exception` handlers in the startup path can no longer intercept a shutdown-request signal. Preserve the current rollback-on-interrupt behavior and the existing message/format.

## Priority
Low

## Scope
- **In-Scope**:
  - Rebase `StartupInterrupted` from `RuntimeError` to `BaseException` in `scripts/agent/startup.py`.
  - Add an explicit `except StartupInterrupted: raise` guard in `McpServerStarter.start_servers()` before the broad first-attempt tuple, so a shutdown signal is never routed through the retry helper.
  - Add an explicit `except StartupInterrupted` rollback branch to `StartupOrchestrator.run()` so subprocess cleanup still runs on a startup-time interrupt (preserving current fail-closed behavior now that the generic `except Exception` no longer matches).
  - Correct the now-inaccurate mechanism comment in `test_startup_rollback.py::test_startup_interrupted_triggers_rollback_like_any_other_exception`.
- **Out-of-Scope**:
  - Removing `RuntimeError` from the first-attempt tuple (see Design / adversarial finding — it preserves genuine-RuntimeError retry).
  - Any change to signal registration, the shutdown event, or graceful-shutdown timing.
  - Renaming `StartupInterrupted` or changing its message / string repr.
  - Refactoring other startup exceptions.
  - Governance documentation updates.

## Background
`StartupInterrupted` (`scripts/agent/startup.py:30`) is `class StartupInterrupted(RuntimeError)`. It is raised by `McpServerStarter` (`startup_mcp_starter.py:63,77,138`) when a shutdown event fires during MCP subprocess startup/stagger/health, and by `retry_once_with_delay` (`shared/retry_helper.py:49,54`) when shutdown fires during a retry delay. `AgentREPL.run()` (`repl.py:134`) has an explicit `except StartupInterrupted` branch treating a startup-time shutdown as non-fatal.

## Problem
Because `StartupInterrupted` is a `RuntimeError`, handlers that intend to catch ordinary startup errors also catch shutdown signals. In `McpServerStarter.start_servers()` the first-attempt clause is `except (OSError, RuntimeError, TimeoutError, ConnectionRefusedError, ConnectionResetError, BrokenPipeError) as e:`. A `StartupInterrupted` propagating from deep inside the lifecycle start matches this clause, routes through `retry_once_with_delay()`, and incurs an unnecessary retry window before surfacing. New broad `except RuntimeError` handlers added later can silently swallow or delay a shutdown request.

## Reason for Change
A shutdown-request exception is control flow, not a failure. Encoding it as `RuntimeError` lets generic error handlers intercept it — a Fail-Closed / graceful-shutdown correctness concern even though the current exit path happens to still raise.

## Implementation Intent
Change the base class to `BaseException`; add an explicit `except StartupInterrupted: raise` guard in `start_servers()`; add an explicit `except StartupInterrupted` rollback branch in `run()`. Do not rename the class, change messages, or alter retry behavior for genuine failures.

## Requirements
- `REQ-001`: `StartupInterrupted` inherits from `BaseException` and is not a subclass of `RuntimeError`.
- `REQ-002`: A `StartupInterrupted` raised inside `_start_http_subprocess_once()` is NOT caught by the first-attempt tuple in `start_servers()` and does NOT trigger a retry delay.

## Design
Changing `StartupInterrupted` to `BaseException` is the core fix: it is automatically excluded from every `except Exception` / `except RuntimeError` clause, so `retry_once_with_delay()` (line 42) and `run()`'s generic `except Exception` (line 77) no longer intercept it. Two follow-on effects must be handled:

1. **`start_servers()`**: The issue proposes removing `RuntimeError` from the first-attempt tuple. Adversarial review rejects this: `RuntimeError` also matches *genuine* transient errors that are intentionally retried (REQ-005). Removing it would regress that handling. Instead, keep `RuntimeError` and add an explicit `except StartupInterrupted: raise` guard *before* the tuple. Because `StartupInterrupted` is now `BaseException` the guard is defense-in-depth (and makes the intent visible to readers, the issue's stated motivation), while `RuntimeError` retry is preserved.

2. **`run()` rollback**: With `StartupInterrupted` no longer matched by `except Exception`, `run()` would stop rolling back on a startup-time interrupt. To preserve fail-closed behavior (REQ-004, and the "do not change shutdown timing" constraint), add an explicit `except StartupInterrupted` branch that calls `lifecycle.shutdown_all()` and re-raises, placed before the generic handler. This keeps the behavior locked by `test_startup_interrupted_triggers_rollback_like_any_other_exception` intact.

`AgentREPL.run()` needs no change: its explicit `except StartupInterrupted` (line 134) catches either base class, and the outer `finally` closes resources.

- **Risk**: mypy flags a `BaseException` that is not caught anywhere. → **Mitigation**: explicit `except StartupInterrupted` in `run()` and `start_servers()`; `mypy` in the validation gate.
- **Risk**: Double `shutdown_all()` on interrupt (current behavior) vs. single. → **Mitigation**: Option B preserves current double-call; `shutdown_all()` is idempotent; noted for the implementation phase to confirm idempotency.
