# Plan: Clarify AppServices invariant vs defensive null checks

## Goal
- Resolve the inconsistency between `AppServices` docstring ("All required services are non-None") and defensive null checks in `ReadinessReporter.report_readiness()`.

## Priority
Low

## Scope
- **In-Scope**: Document why defensive null checks exist despite the invariant; consider removing checks if invariant is enforced elsewhere
- **Out-of-Scope**: Changes to `services_required` property implementation; changes to the readiness report format

## Background
`ReadinessReporter.report_readiness()` in `scripts/agent/startup_reporter.py` reports aggregated readiness status after startup checks complete. It accesses `self._ctx.services_required.runtime_tools` and `self._ctx.services_required.health_registry`.

## Problem
While the code does have null checks for `services_required` in some places (lines 97-101, 107-111), there is a subtle issue: the `services_required` property is accessed multiple times within the same method, and between accesses the context could theoretically be in an inconsistent state (though unlikely in single-threaded asyncio). More importantly, the docstring says "All required services are non-None" but the reporter still performs defensive null checks, suggesting the invariant is not guaranteed.

## Reason for change
Defensive checks add complexity without clear benefit if the invariant holds. If the invariant doesn't hold, the null checks mask the real problem (missing service injection). The inconsistency between docstring claims and defensive coding suggests uncertainty about the invariant.

## Implementation intent
Either enforce the invariant at construction time (via `AppServices.__init__()` validation) or document why defensive checks are needed despite the docstring claim. If the invariant is enforced elsewhere, remove the redundant null checks.

- `REQ-002`: No ambiguity between docstring claims and implementation behavior
- `REQ-003`: Test verifies consistent behavior under both scenarios
- `REQ-004`: Code review confirms no other callers depend on the current null-check behavior

## Design
### Current Behavior (Verified Against Source)
1. `startup_reporter.py` line 97-101: Null check for `services_required` before accessing `runtime_tools`
2. Line 107-111: Null check for `services_required` before accessing `health_registry`
3. `context.py` line 251: Docstring claims "All required services are non-None"
4. Inconsistency: defensive checks suggest the invariant might not hold

### Proposed Change
Option A: Enforce invariant + remove null checks
```python
# In context.py — enforce invariant
class AppServices:
    """Fully-initialized service references built by factory.py.

    Required services (must be non-None): http, llm, tools, lifecycle, hist_mgr, audit_logger
    Optional services (may be None): memory, health_registry, gateway, runtime_tools
    """
    # ... constructor validation added (see AS010) ...

# In startup_reporter.py — remove null checks
runtime_tools = self._ctx.services_required.runtime_tools
registry = self._ctx.services_required.health_registry
```

Option B: Keep null checks + document rationale
```python
# In startup_reporter.py — add docstring comment
# Note: null checks retained because factory.py may inject None during
# early startup phases before all services are fully initialized.
# See AppServices docstring for the invariant contract.
runtime_tools = (
    self._ctx.services_required.runtime_tools
    if self._ctx.services_required
    else None
)
```

I recommend Option A since it eliminates redundancy and makes the invariant explicit.
