# Plan: Refactor config_builders.py — eliminate _extract_fields anti-pattern and consolidate

## Goal

Eliminate the `_extract_*_fields` → dict → `{**...}` → dataclass constructor anti-pattern in `scripts/agent/config_builders.py`, consolidate default value sources, and separate concerns (loading, validation, building, assembly).

## Priority

Medium

## Scope

- **In-Scope**: Remove 13 `_extract_*_fields` functions, replace 6 `{**...}` spreading patterns with explicit keyword arguments, consolidate default values, move inline validation to dedicated validators, remove `sys.exit(1)` side effect, extract module-level imports from functions
- **Out-of-Scope**: Adding new configuration options, changing config file format or schema, modifying dataclass field names or types, adding new validators beyond what's needed for current fields

## Background

`config_builders.py` has grown organically over time with multiple patterns introduced without architectural alignment. The primary anti-pattern is extracting config fields into intermediate dicts and then spreading them into dataclass constructors. Evidence: 13 `_extract_*_fields` functions (lines 126–429) each return intermediate dicts that are spread via `{**a, **b, **c}` (6 occurrences at lines 192, 290, 359, 388, 437) before being passed to dataclass constructors. This creates a gap between config key names and their destination fields.

## Problem

The `_extract_*_fields` → dict → `{**...}` → dataclass constructor anti-pattern makes it difficult to understand which defaults come from where, breaks type safety, and obscures the relationship between config keys and their destinations.

## Reason for change

- **Maintainability risk**: 542 lines with mixed responsibilities (loading, validation helpers, builders, assembly)
- **Correctness risk**: Default values exist in two overlapping locations — `_extract_*_fields` extractors (e.g., line 129 `"llm_url": _get_str_or_default(cfg, "llm_url", "")`) and `constants.py` (canonical source for `_DEFAULT_APPROVAL_RISK_RULES`, `_DEFAULT_DRY_RUN_TOOLS`, etc.) — creating ambiguity about which defaults are authoritative
- **Testability risk**: Hard to verify individual config paths due to dict-spreading; mutations can silently alter behavior
- **Developer impact**: New contributors struggle to trace config value flow through the indirect dict-spreading pattern

## Implementation intent

- Eliminate the `_extract_*_fields` → dict → spread anti-pattern entirely
- Move to direct field-by-field construction in builder functions
- Consolidate default value sources into a single location per config domain
- Separate concerns: loading, validation, building, assembly into distinct modules
- Preserve public API: `build_agent_config()`, `load_config()`, `ConfigLoadError` remain unchanged

## Requirements

- `REQ-001`: Remove all 13 `_extract_*_fields` functions and replace with direct field extraction in builders
- `REQ-002`: Replace 6 `{**a, **b, **c}` spreading patterns with explicit keyword arguments to dataclass constructors
- `REQ-003`: Consolidate default values — move defaults from extractors to dataclass definitions or a dedicated defaults module
- `REQ-004`: Move inline validation from `_build_approval_config` (tier check at lines 406–411) and `_extract_approval_tool_fields` (dry-run validation at lines 399–402) to `ApprovalConfig.__post_init__` or dedicated validator functions
- `REQ-005`: Extract `_resolve_config_source_and_registry` import logic (line 464: `from shared.tool_registry import get_registry`) to top-level
- `REQ-006`: Remove `sys.exit(1)` side effect from `_run_production_validation` (line 491); return error results instead
- `REQ-007`: Consider splitting into separate modules (e.g., `config_loader.py`, `config_builders.py`, `config_validators.py`)

## Design

### Architecture decisions

1. **Path A classification**: This task affects ≤ 3 files, no public interface changes, no DB schema changes → limited to direct-verification inspection only
2. **Default consolidation strategy**: Move defaults from `_extract_*_fields` extractors to their respective dataclass field defaults where domain-appropriate. For cross-domain defaults (approval-related), keep them in `constants.py` as `_DEFAULT_*` tables
3. **Validation migration**: Move inline validation from `_extract_approval_tool_fields` (tier check) and `_build_approval_config` (dry-run validation) to `ApprovalConfig.__post_init__`. Use existing validator functions from `agent.services.config_validators` where available
4. **Import extraction**: Move `from shared.tool_registry import get_registry` from `_resolve_config_source_and_registry` (line 464) to module-level import alongside other shared imports
5. **Error handling**: Replace `sys.exit(1)` in `_run_production_validation` with raising `ConfigReloadValidationError` or returning error results tuple

### Data ownership model

After refactor:
- `constants.py`: Canonical source for 6 `_DEFAULT_*` tables (already established)
- Dataclass field defaults: Domain-specific defaults for each sub-config
- `_get_or_default` / `_get_str_or_default`: Runtime fallback mechanism only — no default values should be duplicated between these helpers and dataclass defaults

## Risks

- **Risk**: Moving defaults from extractors to dataclass defaults may change runtime behavior if a config key explicitly sets an empty value that was previously overridden by extractor defaults → **Mitigation**: Audit each default carefully; preserve current semantics by keeping `_get_or_default` / `_get_str_or_default` fallbacks where needed
- **Risk**: Inline validation moved to `__post_init__` may change error timing (validation now happens at construction time vs. build time) → **Mitigation**: Verify that `ConfigReloadValidationError` is raised consistently in both paths
- **Risk**: Removing `sys.exit(1)` changes error propagation from process termination to exception → **Mitigation**: Ensure callers handle `ConfigReloadValidationError` appropriately; update any code depending on `sys.exit(1)` behavior
- **Risk**: Module-level import of `shared.tool_registry` may cause circular import issues → **Mitigation**: Test import order; use lazy import pattern if circular dependency detected
