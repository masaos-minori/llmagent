## Goal
- Fix the contradiction where `_TOKEN_TOPIC_MAP`'s documented "empty means any
  topic" semantics are not honored by `require_consumer_identity`/
  `subscribe_route.py`, which currently reject every subscribe topic when no
  topic restriction is configured for the caller's token.

## Problem
`scripts/eventbus/auth.py`'s `_populate_token_maps()` comments an empty
`_TOKEN_TOPIC_MAP` entry as meaning "any topic is allowed" for that token
(mirroring the same convention already used for `_TOKEN_CONSUMER_MAP`), but
`require_consumer_identity`'s topic-allowlist block (lines 204-217, confirmed by
reading the function) only populates `allowed_topics` from
`_TOKEN_TOPIC_MAP.get(token, set())` when its own `topics` parameter is
non-empty, and otherwise defaults `allowed_topics` to `set()`. `subscribe_route.py`
(lines 56-62, confirmed by reading the file) then reads that returned `"topics"`
value as `caller_topics` and rejects (403) every element of the request's own
`topic` query list not already in `caller_topics` — with no way to distinguish "no
restriction configured" from "explicitly zero topics allowed," since both produce
the same empty set.

## Reason for change
Confirmed by direct reproduction:
`tests/eventbus/test_eventbus_subscribe.py::test_subscribe_duplicate_consumer_id_returns_409`
(a test whose only intent is to check consumer_id-duplicate rejection, topics
aside) currently fails with `403 Forbidden: topic 't' not allowed` instead of
reaching its own intended `409 Conflict` assertion — a caller holding a
validly-configured `consumer_token` (with no topic restriction configured) cannot
subscribe to any topic today, which defeats the purpose of configuring per-role
tokens at all for `/subscribe`.

## Implementation intent
Change `require_consumer_identity`'s returned `"topics"` value to distinguish "no
restriction" (`None`) from "an explicit, non-empty allowlist" (a `set[str]`) —
never an empty `set()` for the "no restriction" case. Update
`subscribe_route.py`'s topic-allowlist check to skip enforcement when the value is
`None`, and to enforce it (unchanged logic) when it is a non-empty set.

## Requirements
- `REQ-001`: `require_consumer_identity` must return `"topics": None` (not
  `set()`) when the caller's token has no `_TOKEN_TOPIC_MAP` entry, or an entry
  that is an empty set — signaling "no topic restriction," distinct from an
  explicit, non-empty allowlist.
- `REQ-002`: `subscribe_route.py`'s topic-allowlist check must treat
  `_identity["topics"] is None` as "no restriction — allow every requested topic,"
  not iterate/reject against it.
- `REQ-003`: A token with a genuinely non-empty `_TOKEN_TOPIC_MAP` entry must
  still be rejected (403) for a topic outside that entry — no regression to
  existing enforcement.

## Design
`require_consumer_identity`'s topic-allowlist block changes from:
```python
allowed_topics = set()
if topics:
    allowed_topics_from_map = _TOKEN_TOPIC_MAP.get(token, set())
    for topic in topics:
        if topic not in allowed_topics_from_map:
            raise HTTPException(...)
    allowed_topics = allowed_topics_from_map
```
to resolving `allowed_topics_from_map = _TOKEN_TOPIC_MAP.get(token, set())` first
(unconditionally, not gated on `topics`), then: if `allowed_topics_from_map` is
empty, set the returned value to `None` (unrestricted); otherwise enforce the
existing per-topic check against it (unchanged for the non-empty case) and return
the set. `subscribe_route.py`'s check changes from unconditionally iterating
`caller_topics = _identity.get("topics", set())` to first checking `caller_topics
is not None` before iterating — `None` short-circuits to "every topic allowed."

`None` (rather than reusing empty-set-with-a-side-channel-flag) is chosen because
it requires no second field, is a natural "absence of restriction" sentinel in
Python, and cannot be confused with "restricted to zero topics" (which no
existing code path can produce today: `_TOKEN_TOPIC_MAP`'s only current writer,
`_populate_token_maps`, never assigns a token an empty set as anything other than
"unset" — mirroring `_TOKEN_CONSUMER_MAP`'s parallel convention).
