## Background
This Plan's source is `issues/20260901-104253_risks.md`, a Risk follow-up filed by the
`issue-to-plan` run that produced `plans/20260901-104253_plan.md` (source issue
`issues/20260831-192510_adr004_07_shell_mcp_sandbox_production_only_enforcement.md`). That
sibling Plan's REQ-001 will remove the `if production_mode:` gate around
`shell_sandbox_backend == "none"`'s `RuntimeError` in `audit_security_defaults()`, making it
unconditional. Its own Scope explicitly excludes
`docs/04_mcp_05_02_auth-profiles-and-sandboxing.md`, deferring that doc's matching passages
to this follow-up (`issues/20260901-104253_risks.md`, Suggested resolution).

`plans/20260901-104253_plan.md`'s `## Execution Status` still shows every step `Pending`,
and direct evidence confirms REQ-001 has not landed: `scripts/agent/repl_health.py` is now
a backward-compatibility re-export shim (`"""Backward-compatibility re-exports for
repl_health consumers."""`), and the real `audit_security_defaults()` implementation lives
in `scripts/agent/services/security_audit.py`, where the `shell_sandbox_backend == "none"`
`RuntimeError` (message `"shell_sandbox_backend=none is not permitted in production mode"`)
is still gated by `if production_mode:`. This confirms this Plan's fix is not yet ready to
execute for the passages that depend on REQ-001 landing.

Re-reading `docs/04_mcp_05_02_auth-profiles-and-sandboxing.md` in full (adversarial
verification beyond the source risk issue's own scope) found two additional passages
describing the same pre-fix conditional behavior that the risk issue did not name: the
"Sandbox Backend (shell-mcp)" table's `none` row ("Logs a WARNING; `RuntimeError` in
production mode") and the "Startup Enforcement" bullet list's third bullet ("If
`backend == "none"` in production mode → `RuntimeError`"). Both are folded into this
Plan's REQ-002 rather than left for a further follow-up, since they are the same
file/passage-family the source risk issue already targets.

Separately, the "Enforcement Point" sentence's module-path reference
(`agent/repl_health.py::audit_security_defaults()`) is stale **today**, independent of
REQ-001's landing status: the function has already moved to
`agent/services/security_audit.py` (confirmed above), and `repl_health.py` only re-exports
it for backward compatibility. This is a separate, immediately-actionable correction
(REQ-001 of this Plan) that does not need to wait for the sibling Plan.

## Problem
`docs/04_mcp_05_02_auth-profiles-and-sandboxing.md` names a module path
(`agent/repl_health.py::audit_security_defaults()`) that is no longer where the real
implementation lives, and describes `shell_sandbox_backend == "none"` as warning-only
outside production in four places — accurate today, but scheduled to become false the
moment the sibling Plan's REQ-001 lands, with no mechanism currently in place to update
this doc in step with that change.

## Reason for change
Per the source risk issue: if this doc is not updated in the same rollout as
`plans/20260901-104253_plan.md`'s code change, a reader following its "Development: ...
WARNING at startup; no isolation" example (or the table's "Logs a WARNING" row, or the
"Startup Enforcement" bullet) would be misled into believing local/non-production
deployments can safely run with `shell_sandbox_backend = "none"` and only get a warning,
when startup would actually abort. The module-path staleness independently risks sending a
reader to `repl_health.py` looking for logic that is no longer there.

## Implementation intent
Split the fix into two independently-timed parts within one Plan for one target file:
first, correct the already-stale module path immediately; second, gate the
conditional-enforcement wording fix behind an explicit precondition check (re-reading
`scripts/agent/services/security_audit.py` to confirm the `if production_mode:` gate
around the `"none"` case is actually gone) before rewording the four passages — mirroring
the sign-off-gate pattern `plans/20260901-104253_plan.md` itself uses for its own
deployment-timing concern (REQ-004), rather than either rewording prematurely (describing
behavior that does not yet exist) or leaving the doc to drift silently once the code
changes.
