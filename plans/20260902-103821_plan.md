## Problem
`docs/04_mcp_05_02_auth-profiles-and-sandboxing.md` names a module path
(`agent/repl_health.py::audit_security_defaults()`) that is no longer where the real
implementation lives, and describes `shell_sandbox_backend == "none"` as warning-only
outside production in four places — accurate today, but scheduled to become false the
moment the sibling Plan's REQ-001 lands, with no mechanism currently in place to update
this doc in step with that change.

## Reason for change
Per the source risk issue: if this doc is not updated in the same rollout as
`plans/20260901-104253_plan.md`'s code change, a reader following its "Development: ...
WARNING at startup; no isolation" example (or the table's "Logs a WARNING" row, or the
"Startup Enforcement" bullet) would be misled into believing local/non-production
deployments can safely run with `shell_sandbox_backend = "none"` and only get a warning,
when startup would actually abort. The module-path staleness independently risks sending a
reader to `repl_health.py` looking for logic that is no longer there.

## Implementation intent
Split the fix into two independently-timed parts within one Plan for one target file:
first, correct the already-stale module path immediately; second, gate the
conditional-enforcement wording fix behind an explicit precondition check (re-reading
`scripts/agent/services/security_audit.py` to confirm the `if production_mode:` gate
around the `"none"` case is actually gone) before rewording the four passages — mirroring
the sign-off-gate pattern `plans/20260901-104253_plan.md` itself uses for its own
deployment-timing concern (REQ-004), rather than either rewording prematurely (describing
behavior that does not yet exist) or leaving the doc to drift silently once the code
changes.
