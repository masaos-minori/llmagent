## Goal
Add `enabled`/`disabled_reason` fields to every tool in the `GET /v1/tools` response of
web-search-mcp (`scripts/mcp_servers/web_search/web_search_server.py`) and github-mcp
(`scripts/mcp_servers/github/github_server.py`), and gate `POST /v1/call_tool` on both
servers so a disabled tool is rejected before dispatch — matching the pattern already
implemented by git-mcp and the three file servers.

## Scope

### In-Scope
- `scripts/mcp_servers/web_search/web_search_server.py`:
  - Add an availability check function (analogous to `_git_tool_availability()`) that
    returns `(enabled, disabled_reason)` per tool name: `browser_fetch` gated on
    `_cfg.browser_allowed_domains` being non-empty; `search_web` always
    `(True, "")`.
  - Replace the `build_tools_response(TOOL_LIST, "web_search")` call in `list_tools()`
    with an annotated response that includes `enabled`/`disabled_reason` for every tool
    (including disabled ones — see Design note on `build_tools_response` filtering).
  - Add a server-side gate in `call_tool()` that rejects a disabled tool with
    `CallToolResponse(result=f"Tool disabled: {reason}", is_error=True)` before
    `_dispatch_web_tool()` is called.
- `scripts/mcp_servers/github/github_server.py`:
  - Add an availability check function based on `_GITHUB_TOKEN` (the same signal
    `/health` already uses), applied uniformly to all `TOOL_LIST` tools (all are
    `config_dependent: True` today, confirmed in `tools_repository.py`, `tools_file.py`,
    `tools_issues.py`, `tools_pull_requests.py`).
  - Replace the `build_tools_response(TOOL_LIST, "github")` call in `list_tools()` with
    the annotated version.
  - Add the equivalent server-side gate in `call_tool()`.
- Tests: extend/add tests analogous to `tests/mcp_servers/git/test_tools_endpoint.py` for
  both servers (config-present and config-absent/empty fixtures), plus a call-tool
  rejection test per server confirming the underlying dispatch table is never reached.
- Judgment call (left to implementer, not mandatory): whether to extract a shared
  "compute (enabled, reason) then merge" helper into `scripts/mcp_servers/server.py`
  given this would be the 3rd/4th bespoke copy of the same shape (git, file, web-search,
  github).

## Assumptions
- `enabled`/`disabled_reason` are plain dict keys merged into each `McpTool` dict, not a
  `McpTool` TypedDict/model field — falsifiable: `mcp_servers/models.py`'s `McpTool`
  definition has no such fields today, and git-mcp/file-servers add them only at the
  `_annotate_tool()` dict-merge layer (`git_server.py:87-95`,
  `read_server.py:255-260`), not on the `McpTool` type itself.
- No client currently depends on `/v1/tools` NOT having `enabled`/`disabled_reason` on
  web-search-mcp/github-mcp tool dicts — falsifiable by grepping client code
  (`scripts/agent/**`) for exact-key tool-dict assertions; git-mcp/file-servers already
  ship these fields with no reported breakage, which is precedent this holds.
- `MCP_TOOL_SCHEMA_VERSION` does not need a bump — falsifiable: git-mcp and the file
  servers already carry `enabled`/`disabled_reason` while `MCP_TOOL_SCHEMA_VERSION`
  remains `"1.0"` (`scripts/mcp_servers/server.py:39`), establishing precedent that this
  field addition is not a "shape change that matters to Agent-side discovery/validation"
  per the docstring's own bump criterion.
- `_GITHUB_TOKEN` (from `github_service_init.py`, imported into `github_server.py:53`) is
  the single correct signal for github-mcp tool availability — falsifiable: it is the
  exact signal the existing `/health` endpoint already uses
  (`github_server.py:105-113`), so reusing it introduces no new divergent check.

## Design
Follow the two existing patterns verbatim; do not invent a third shape:

1. **Availability function**, mirroring `git_server.py:73-79`
   (`_git_tool_availability(cfg, tool_name) -> tuple[bool, str]`) and
   `file/common.py:101-105` (`availability_flags(allowed_dirs) -> tuple[bool, str]`):
   - web-search-mcp: `_web_search_tool_availability(cfg: WebSearchConfig, tool_name: str) -> tuple[bool, str]`
     returning `(False, "browser_allowed_domains is empty")` when `tool_name ==
     "browser_fetch"` and `not cfg.browser_allowed_domains`, else `(True, "")`. This
     mirrors the fail-closed check already enforced at dispatch time in
     `search_provider.py::_check_domain()` (an empty `allowed_domains` set rejects every
     hostname), and reuses the exact same underlying config field
     (`WebSearchConfig.browser_allowed_domains`, projected into `BrowserConfig.allowed_domains`
     via `BrowserConfig.from_web_search_config()` in `web_search_models.py:157-167`).
   - github-mcp: `_github_tool_availability(tool_name: str) -> tuple[bool, str]` (or
     accepting no `cfg` param, since the signal is the module-level `_GITHUB_TOKEN`)
     returning `(False, "GITHUB_TOKEN is not set")` when `not _GITHUB_TOKEN`, else
     `(True, "")`, applied identically to every entry in `TOOL_LIST` (all are
     `config_dependent: True`). Reuse `_GITHUB_TOKEN` exactly as imported at
     `github_server.py:53` — do not add a second, possibly-diverging check.
   - Reason-string convention: lower-case, `<field> is empty` / `<FIELD> is not set`
     form, consistent with existing strings (`"allowed_dirs is empty"`,
     `"allowed_repo_paths is empty"`, `"read_only=true"`).

2. **`/v1/tools` annotation — critical gotcha found during this plan's source review**:
   `build_tools_response()` (`scripts/mcp_servers/server.py:224-261`) already has
   `include_disabled: bool = False` / `disabled_code: str | None = None` parameters (the
   MCP-001 groundwork), and with the default `include_disabled=False` it **drops any
   tool dict whose `enabled` key is `False`** from the response entirely
   (`server.py:249-251`). If an implementer pre-annotates `TOOL_LIST` with
   `enabled`/`disabled_reason` and then calls
   `build_tools_response(annotated_tools, "web_search")` with the default argument, a
   disabled `browser_fetch` would silently disappear from `/v1/tools` instead of
   appearing with `enabled=false` — directly violating this requirement's acceptance
   criteria ("`GET /v1/tools` ... returns `enabled`/`disabled_reason` for every tool").
   This is almost certainly *why* git-mcp (`git_server.py:103-109`) and the file servers
   (`read_server.py:263-270`) both bypass `build_tools_response()` entirely for
   `list_tools()` and hand-build `{"schema_version": MCP_TOOL_SCHEMA_VERSION, "tools":
   [...]}` directly. **Follow that same bypass pattern** for web-search-mcp and
   github-mcp: do not route the annotated list back through
   `build_tools_response()` unless `include_disabled=True` is passed explicitly (which
   would still be safe, just an unnecessary indirection given MCP-001 itself is
   out-of-scope here).

3. **`/v1/call_tool` gate**, mirroring `git_server.py:112-117`: compute
   `(enabled, reason)` from the same availability function at the top of the handler,
   and if not enabled return `CallToolResponse(result=f"Tool disabled: {reason}",
   is_error=True)` before calling `_dispatch_web_tool()` / `_dispatch_github_tool()`.
   For web-search-mcp, place this check before the existing `try/except` block so a
   disabled-tool rejection is not misclassified into the audit log's error-type
   taxonomy (it is a distinct, non-error "disabled" outcome, matching how git-mcp's
   equivalent check returns before its own dispatch/audit path).

4. **Shared helper (implementer judgment, not required)**: with this change, four
   servers (git, file-{read,write,delete} via one shared `common.py` helper,
   web-search, github) each carry a "compute (enabled, reason) then merge into tool
   dict" shape. A small helper such as
   `annotate_tool_availability(tool: McpTool, server_key: str, enabled: bool, reason:
   str) -> dict[str, Any]` in `server.py` would remove the last bit of duplication, but
   per the requirement text this is explicitly left to the implementer's discretion —
   do not treat it as a mandatory step.

5. **Schema version**: do not bump `MCP_TOOL_SCHEMA_VERSION` (see Assumptions —
   precedent already set by git-mcp/file-servers shipping these fields at version
   `"1.0"`).

## Risks
- **Risk**: Implementer reuses `build_tools_response()` with its default
  `include_disabled=False` for the annotated response, silently dropping disabled tools
  from `/v1/tools` and violating the acceptance criteria.
  **Mitigation**: Design §2 above explicitly documents this gotcha and mandates the
  hand-built-dict bypass pattern (matching git-mcp/file-servers); the new contract tests
  in Phase 5 would also catch this regression immediately (a disabled tool missing from
  the response, rather than present with `enabled=false`, fails the parametrized test).
- **Risk**: Placing the `call_tool()` disabled-tool gate after the existing
  `try/except`/audit-log scaffolding in `web_search_server.py` (rather than before it)
  could cause a disabled-tool rejection to be misclassified as an audit "error" outcome
  with the wrong `error_type`, or double-count in `metrics`/`health` degradation
  counters.
  **Mitigation**: Design §3 specifies the gate must sit before the `try` block, mirroring
  git-mcp's placement; the call-tool rejection test in Phase 2 asserts the exact
  `CallToolResponse` shape independent of the audit/metrics path.
- **Risk**: A future reader mistakes `plans/done/20260818-182859_plan.md` (broader,
  partially superseded prior plan covering the same two files plus out-of-scope servers
  and MCP-001) as already having delivered this work, and skips re-verification.
  **Mitigation**: this plan's Unknowns section records that the prior plan's relevant
  steps were never implemented (confirmed by direct source read at planning time); the
  Traceability section below and the requirement's own "Correction to the source issue"
  note preserve this history for future readers.
- **Risk**: `_GITHUB_TOKEN` is a module-level constant captured at import time
  (`github_service_init.py`); if it is later refactored to be reloadable at runtime
  without updating this new availability check, `/v1/tools` could report stale
  availability.
  **Mitigation**: low likelihood — the existing `/health` endpoint has the identical
  exposure today and is treated as the source of truth per the requirement's own
  instruction to reuse "that same signal rather than adding a second, possibly-diverging
  check"; no new risk is introduced beyond what already exists.
