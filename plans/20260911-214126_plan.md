# Plan: StartupBanner workflow-status reporting fix

## Goal
Implement a real `Orchestrator.workflow_status()` method that reports the actual workflow tracking state, and update `StartupBanner._get_workflow_status()` to remove the `getattr(..., None)` defensive fallback since the method will always exist.

## Background
`StartupBanner._get_workflow_status()` was meant to show the startup banner's workflow-tracking status as "enabled", "not loaded", or "unknown". However, `Orchestrator` had no `workflow_status()` method anywhere in the codebase. The banner therefore always reported "not loaded" once an orchestrator instance existed. After a previous fix that passed the orchestrator explicitly to `_get_workflow_status()`, the `getattr(orchestrator, "workflow_status", None)` defensive fallback became reachable but still returned "not loaded" because the method doesn't exist.

Repository evidence confirms: `workflow_mode` has been removed as a concept (tests assert it is NOT mentioned in error messages), and `workflow_tracking` does not appear anywhere in the codebase. However, `AgentContext.workflow.active` (a `bool` on `WorkflowState`) tracks whether a workflow is currently active, providing a concrete signal for "workflow tracking enabled/disabled".

## Problem
The startup banner's "workflow tracking" status has never meaningfully reflected anything — it either short-circuited to "not loaded" via the dead `ctx._orchestrator` check, or (after that particular fix) would call a method that doesn't exist. There is no current concept of "workflow tracking enabled/disabled" exposed through the `Orchestrator` API.

## Reason for change
Decide whether this banner field should report something real, or be removed as vestigial. This plan chooses to implement a real `workflow_status()` method based on `AgentContext.workflow.active`.

## Implementation intent
Add `workflow_status()` to `Orchestrator` that returns `{"tracking": "enabled"}` when `ctx.workflow.active == True`, otherwise `{"tracking": "not_loaded"}`. Update `StartupBanner._get_workflow_status()` to call the method directly without the `getattr` fallback. Update tests accordingly.

## Design
### Decision: Implement `workflow_status()` rather than removing the banner field

Rationale:
1. `AgentContext.workflow.active` (bool on `WorkflowState`, context.py:241) provides a concrete, existing signal for "is workflow tracking active"
2. The startup banner already has display infrastructure for workflow status (`cli_view.py:66,116,251-259`)
3. The MCP server has a `get_workflow_status` tool using similar concepts
4. Removing would lose useful operational visibility at startup
5. `workflow_mode` being removed elsewhere does not eliminate the need to report workflow state

### Implementation approach

`Orchestrator.workflow_status()` returns:
- `{"tracking": "enabled"}` if `self._ctx.workflow.active == True`
- `{"tracking": "not_loaded"}` if `self._ctx.workflow.active == False`

`StartupBanner._get_workflow_status()` simplified logic:
```python
if orchestrator is None:
    return "unknown"
status = orchestrator.workflow_status()["tracking"]
return status if status != "not_loaded" else "not loaded"
```

Note: The `"not_loaded"` → `"not loaded"` mapping preserves backward compatibility with the existing CLI output format.
