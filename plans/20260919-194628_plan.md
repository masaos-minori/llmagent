## Goal
Audit every `## Implementation Notes` bullet across the 20 `docs/*.md` files that
currently carry one, classify each against `docs/00_governance_02_documentation-metadata.md`'s
existing Decision Categories (Delete / Compress / Replace with Source Reference / Retain
/ Move to Known Issues / Move to Needs Confirmation), and apply the corresponding action
— so that design rationale currently misfiled as implementation trivia is preserved in
the right place, and mechanical trivia is removed.

## Priority
Medium

## Scope
- **In-Scope**: Reading and reclassifying every bullet in the `## Implementation Notes`
  section of the 20 identified `docs/*.md` files; deleting/compressing mechanically
  verifiable trivia in place; promoting design-rationale bullets into the file's own
  design body (or, for an ADR, its `## Rationale`/`## Invariants` section); filing new
  Known Issues entries (`docs/00_governance_03_issue-and-uncertainty-management.md` Part
  1) for implementation/design mismatches found; filing new Needs Confirmation entries
  (same document, Part 2) for bullets whose designer intent is unknown; deciding whether
  to build a lightweight inventory-assist tool under `tools/` and recording that decision.
- **Out-of-Scope**: Defining new classification criteria (the criteria already exist);
  auditing any section other than `## Implementation Notes` (e.g. `## Known Limitations`,
  an ADR's `## Known Deviations`) even if similar drift is suspected there; any change to
  `scripts/` runtime behavior; building the inventory tool itself if the decision is to
  proceed by hand/AI instead (that becomes its own follow-up if decided against here).

## Background
Filed from `issues/20260919-193722_impln01_audit-and-reclassify-docs-implementation-notes-items-per-existing-decision-categories.md`,
itself derived from a user request (`memo3.md`) proposing 4 classification buckets for
`Implementation Notes` content. Those buckets were confirmed (Issue Step 2 assessment,
carried forward here) to closely mirror `docs/00_governance_02_documentation-metadata.md`'s
existing "Decision Categories" table:

| memo3.md bucket | Existing policy row |
|---|---|
| 削除 (file/line/function-name-describable, unambiguous from source, easily stale, mere execution order) | `Delete` / `Compress` |
| ADRまたは設計本文へ昇格 (explains why an order matters; breaking it risks data corruption/security; multiple implementations must honor it; should survive refactoring) | `Retain` |
| Known Issueへ移動 (design/implementation mismatch; unclear if intentional or a bug; implementation is provisional) | `Move to Known Issues` |
| Needs Confirmationへ移動 (basis for a value/behavior is unknown; behavior visible in code but designer intent is not) | `Move to Needs Confirmation` |

A confirmed promotion candidate was already surfaced during Issue drafting:
`docs/04_mcp_01_system_overview.md:162` states `record_degraded()` does not overwrite
`UNAVAILABLE`/`HALF_OPEN` state "to avoid breaking the circuit breaker and trial window"
— a rationale statement (why, and what breaks if violated) that belongs in the design body
under the `Retain` criteria, not in a code-derived Implementation Notes bullet.

## Problem
`Implementation Notes` sections were populated ad hoc across `docs/*.md` without applying
the classification criteria `docs/00_governance_02_documentation-metadata.md` now defines.
Some items are pure code trivia (deletable), some carry design rationale at risk of being
overlooked (a reviewer checking ADR/design-body constraints would not think to also check
Implementation Notes for binding rules) or lost in a future documentation-slimming pass
that targets Implementation Notes as inherently disposable, and some may describe stale
implementation/design mismatches that belong in the Known Issues inventory instead.

## Reason for change
Misfiled rationale is easy to overlook during design review and easy to lose during
documentation slimming. Correctly bucketing each Implementation Notes item now, while the
existing Decision Categories policy is fresh, prevents both failure modes and establishes
a repeatable pattern other design docs' non-Implementation-Notes sections can follow later
(tracked separately, out of scope here).

## Implementation intent
Process the 20 files individually — 14 ADRs under `docs/adr/` and 6 non-ADR design docs —
reading each file's `## Implementation Notes` bullets in full and classifying each one:

- **Delete/Compress**: remove, or shorten to a brief pointer, in place. Applies when the
  bullet is verifiable from code/config/schema alone, changes only when the code changes,
  and a wrong statement about it would be caught by execution (a test failing), not review.
- **Retain (promote)**: move into the file's own design body — for a non-ADR doc, into
  the section discussing that component's behavior; for an ADR, into its existing
  `## Rationale` or `## Invariants` section (confirmed present in all 14 target ADRs) per
  `docs/00_governance_01_documentation-policy.md`'s ADR Section Header Standardization.
  Do not leave a duplicate copy in both places.
- **Move to Known Issues**: file a new entry per `docs/00_governance_03_issue-and-uncertainty-management.md`
  Part 1's Entry Template, then remove or replace the Implementation Notes bullet with a
  short cross-reference.
- **Move to Needs Confirmation**: file a new entry per that document's Part 2 Inventory
  Entry Fields, then remove or cross-reference from Implementation Notes.

Historical analysis (below) found 6 of the 14 target ADRs have double-digit commit counts
in the last 30 days (highest: `ADR-004`, 19 commits), indicating active concurrent editing
by other work outside this Plan's control — process each file as its own small,
independently committable step so a conflict on one file does not block the others.

Before deciding whether to build the inventory-assist tool the Issue raised, note the
asymmetry across the 4 buckets: `Delete`/`Compress` candidates are the most mechanically
detectable (the same signal `tools/check_docs_content_policy.py`'s existing
`check_default_value_restatement` already uses — it skips a line containing a rationale
marker such as "to avoid", confirmed present in `_RATIONALE_MARKERS`); `Retain`, `Known
Issues`, and `Needs Confirmation` classification require semantic judgment a pattern
match cannot reliably perform. Given this asymmetry, and given the audit's total scope is
small (29 bullets across the 20 files, counted directly), this Plan does not build a new
tool — the one-off audit is small enough to classify by hand/AI without one. If a *future*,
larger-scale documentation-slimming pass needs this same classification repeated across
more sections, building the lighter inventory tool described in the source Issue becomes
worth reconsidering then, not now.

## Design
### Path A/B classification
This Plan was classified **Path B** at Step 3 (20 target files, exceeding the ≤3-file
Path A threshold). Path B's four analyses were performed:
- **Architecture analysis**: `.importlinter` inspected — its contracts govern only
  `scripts/` package boundaries (`agent`, `db`, `mcp_servers`, `rag`, `shared`,
  `eventbus`); this Plan touches no `scripts/` file, so no architecture-boundary
  concern applies. `rg "^from|^import"` against a `<module>.py` was not run — there is
  no single Python module this Plan changes.
- **Dependency graphing**: the "N files requiring changes" list is exactly the 20-row
  `Implementation Target Files` table above, confirmed via
  `grep -rl "^## Implementation Notes" docs/*.md docs/adr/*.md`.
- **Historical analysis**: `git log --since="30 days ago" --oneline -- <file>` run
  against each of the 20 target files (results in Affected areas above). 6 of the 14
  target ADRs show double-digit 30-day commit counts, meaning other concurrent work is
  actively editing them — this directly motivates the per-file, independently
  committable step granularity in Implementation steps below.
- **Operational dependency inspection**: N/A — this Plan does not touch any MCP server,
  database, or long-running process; `lsof`-based checks do not apply to a
  documentation-only change.
