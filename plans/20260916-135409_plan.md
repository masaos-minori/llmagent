## Goal
- Complete the deprecation-to-removal cycle for `Orchestrator._llm_runner` and its
  sole supporting field `Orchestrator._guard` in `scripts/agent/orchestrator.py`, so
  `Orchestrator.__init__` no longer constructs `LLMTurnRunner`/`ToolLoopGuard`
  instances that no code path uses, and no longer emits `DeprecationWarning` noise on
  every `Orchestrator` instantiation as a side effect of that dead construction.

## Priority
Medium

## Scope
- **In-Scope**:
  - Removing the `_llm_runner` deprecated property pair (getter/setter) and the
    `self._llm_runner = LLMTurnRunner(...)` construction in `Orchestrator.__init__`.
  - Removing the `_guard` deprecated property pair (getter/setter) and the
    `self._guard = ToolLoopGuard(ctx)` construction in `Orchestrator.__init__` — this
    field's only remaining purpose in the file was supplying `_llm_runner`'s
    constructor argument; once that construction is gone, `_guard` becomes an
    equally unused, equally dead field, and leaving it would recreate the same
    anti-pattern this Plan removes.
  - Removing the now-unused `LLMTurnRunner` and `ToolLoopGuard` imports from
    `scripts/agent/orchestrator.py`, confirmed unused by nothing else in the file.
  - Correcting the module docstring's "Delegates LLM streaming and tool-loop
    guarding to: llm_turn_runner.py / tool_loop_guard.py" claim, which becomes stale
    once neither module is referenced by `Orchestrator` at all.
- **Out-of-Scope**:
  - Any change to `LlmTurnExecutor`'s own construction of its `LLMTurnRunner`
    instance (`scripts/agent/llm_turn_executor.py`) — that is the live, correct path.
  - Any redesign of how `Orchestrator` and `LlmTurnExecutor` share state.
  - `docs/*.md` changes — ADR-014 already documents the responsibility boundary
    this Plan's removal completes; no doc content requires updating.

## Background
A prior architecture responsibility-boundary review recorded ADR-014
(`docs/adr/ADR-014-agent-control-plane-responsibility-boundaries.md`): Orchestrator
delegates the LLM/tool-call loop to `LlmTurnExecutor` rather than owning an
`LLMTurnRunner` instance itself. A predecessor issue
(`issues/done/20260913-172211_unused_orchestrator_llm_runner.md`) identified the
same dead `_llm_runner`/`_guard` fields this Plan's source Issue re-raises, and was
already converted to a plan and implemented
(`implementations/done/20260914-113352_01_scripts_agent_orchestrator_py.md`).

## Problem
Adversarial verification against current source
(`scripts/agent/orchestrator.py`, read in full) found the source Issue's central
factual claim is now stale: the prior implementation did not delete
`self._llm_runner`'s construction outright. It instead converted both
`_llm_runner` and `_guard` into deprecated properties (`@property` getter +
setter, each emitting `DeprecationWarning` and storing the value in
`self.__dict__`), per the comment at line 188 ("These properties emit
DeprecationWarning ... during the deprecation phase"). Concretely, in
`Orchestrator.__init__`:
- Line 116: `self._guard = ToolLoopGuard(ctx)` still constructs a `ToolLoopGuard`
  (now routed through the deprecated setter).
- Lines 120-124: `self._llm_runner = LLMTurnRunner(ctx, self._guard, tracer=tracer)`
  still constructs an `LLMTurnRunner` (also routed through the deprecated setter;
  `self._guard` on the right-hand side is itself a deprecated-getter read).

So the Issue's claim "no code path in Orchestrator ever reads or calls
`self._llm_runner`" is corrected, not confirmed: nothing reads it as a plain
attribute (`grep -rn "\._llm_runner\b" scripts/ tests/ --include="*.py" | grep -v
scripts/agent/orchestrator.py` returns no matches, and no test references
`Orchestrator._llm_runner`/`Orchestrator._guard`), but the deprecated property
machinery itself both writes and reads `_guard` inside `__init__`, meaning every
`Orchestrator()` call currently fires three `DeprecationWarning`s
(`_guard` set, `_guard` get for the `_llm_runner` constructor arg, `_llm_runner`
set) as an unintended side effect of the previous fix — a regression the Issue's
author did not account for, since the Issue predates awareness of this shim (the
source Issue was filed 2026-09-14 12:16:16, after the deprecation-shim
implementation completed the same day at 11:33:52).
`rules/coding.md`'s Deprecation policy ("Deprecated symbols are removed the next
time `plans/` touches the corresponding file for an unrelated reason, provided a
zero-caller `rg` re-check still holds") directly applies here: this Plan is
touching `scripts/agent/orchestrator.py` for the same symbol the prior deprecation
targeted, and the zero-caller re-check for both `Orchestrator._llm_runner` and
`Orchestrator._guard` still holds (confirmed above; also confirmed no test asserts
a `DeprecationWarning` is raised for either property). Full removal is therefore
in scope now, not merely a re-statement of the original "delete one assignment"
request.

## Reason for change
An unused, deprecated-shimmed construction of a stateful class
(`LLMTurnRunner` holds an SSE/streaming loop guard) still wastes one object
construction per `Orchestrator` instantiation and now additionally emits
misleading `DeprecationWarning` noise on every instantiation with no caller to
migrate away from it (the zero-caller check confirms there is no external caller
left to warn). Completing the removal the prior implementation deferred finishes
the deprecation cycle ADR-014 and the predecessor issue started, consistent with
the repository's own stated Deprecation policy.

## Implementation intent
Delete both deprecated property pairs and their `__init__` constructions in one
pass, remove the two now-unused imports, and correct the one docstring line that
would otherwise misdescribe `Orchestrator`'s dependencies once neither module is
referenced. No behavioral change to the live LLM-turn execution path
(`LlmTurnExecutor`) is intended or required.
