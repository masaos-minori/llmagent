# Plan: ShutdownCoordinator keeps tracking data on termination failure

## Goal
- Ensure `ShutdownCoordinator.shutdown_all()` preserves tracking entries when process termination fails, allowing subsequent shutdown attempts to target the orphaned process.

## Priority
High

## Scope
- **In-Scope**: Modify `shutdown_all()` to conditionally call `cleanup_server_key()` only after confirmed process termination; keep `remove_process_entry()` before the try block (intentional safety mechanism)
- **Out-of-Scope**: Changes to `ProcessTerminator.terminate_with_timeout()` itself; changes to `cleanup_server_key()` implementation; removal of `remove_process_entry()` from before the try block

## Background
`ShutdownCoordinator.shutdown_all()` in `scripts/agent/http_lifecycle_shutdown_coordinator.py` coordinates graceful shutdown of HTTP subprocess MCP servers. It delegates termination to `ProcessTerminator.terminate_with_timeout()` and then calls `cleanup_server_key()` to remove tracking entries.

## Problem
When `terminate_with_timeout()` fails (caught by the except block), `cleanup_server_key()` is still called unconditionally. This removes tracking entries while the process may still be running, creating orphaned processes. Process continues running without tracking — zombie process. Subsequent attempts to shut down the same server will not find it. Resource leak (file descriptors, ports, memory).

Note: `remove_process_entry()` is intentionally called BEFORE termination (line 92) to avoid double-shutdown if termination fails. This is an intentional safety mechanism, not a bug. The fix should move `cleanup_server_key()` inside the except block only, not remove `remove_process_entry()`.

## Reason for change
Orphaned processes during startup/shutdown are a reliability concern. Without tracking data, there is no way to clean up the process later. Monitoring systems cannot detect or alert on orphaned processes.

## Implementation intent
Keep `remove_process_entry()` before the try block (intentional safety mechanism). Move `cleanup_server_key()` inside the try block so it is only called after confirmed process termination. On failure, log the issue but keep the tracking entry so subsequent cleanup attempts can target the process.

## Requirements
- `REQ-001`: Tracking data is removed only after confirmed process termination
- `REQ-002`: Failed termination leaves tracking entry intact for retry
- `REQ-003`: Test verifies no zombie process after shutdown failure scenario
- `REQ-004`: Test verifies tracking entry persists on termination failure

## Design
### Current Behavior (Verified Against Source)
1. `http_lifecycle_shutdown_coordinator.py` line 92: `manager.remove_process_entry(server_key)` — called BEFORE termination, unconditionally
2. `http_lifecycle_shutdown_coordinator.py` line 105-108: Try to terminate the process
3. `http_lifecycle_shutdown_coordinator.py` line 109-110: If termination fails, log warning
4. `http_lifecycle_shutdown_coordinator.py` line 111: Always call `cleanup_server_key()` — even if termination failed

### Proposed Change (Revised after adversarial validation)

The original proposal removed `remove_process_entry()` from before the try block, but this is an intentional safety mechanism (comment on line 92: "Pop before termination to avoid double-shutdown if terminated fails"). The revised approach moves `cleanup_server_key()` inside the except block only:

```python
for server_key, proc in list(manager.iter_processes()):
    if proc is None:
        continue
    # Pop before termination to avoid double-shutdown if terminated fails
    manager.remove_process_entry(server_key)
    if proc.poll() is not None:
        logger.debug("Lifecycle: %r already exited; removing entry", server_key)
        manager.cleanup_server_key(server_key)
        continue
    logger.info("Shutting down %s...", server_key)
    terminate_kwargs: dict[str, Any] = {
        "timeout": _SHUTDOWN_TIMEOUT_SEC,
    }
    if fields:
        terminate_kwargs.update(fields)
    try:
        await terminator.terminate_with_timeout(
            proc, server_key, **terminate_kwargs
        )
        # Only clean up AFTER successful termination
        manager.cleanup_server_key(server_key)
    except (OSError, TimeoutError) as e:
        logger.warning(
            "Lifecycle: error terminating %r: %s; keeping tracking entry for retry",
            server_key, e
        )
        # Do NOT call cleanup_server_key — process may still be running
        # Note: remove_process_entry was already called above (intentional)
```

Key changes:
1. Keep `remove_process_entry()` before the try block (intentional safety mechanism)
2. Move `cleanup_server_key()` from outside the try block to inside the try block (only after successful termination)
3. On failure, don't call `cleanup_server_key()` — leave tracking entry intact for retry
