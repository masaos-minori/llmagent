## Goal
- Document the value-based log-redaction coverage boundary (`_RedactionFilter`: Bearer headers + registered secrets) and its residual gap (unregistered in-body secrets pass through unmasked), including why tool results cannot be regex-masked, in the logging subsystem Known Limitations.

## Priority
Low

## Scope
- **In-Scope**:
  - Add a Known Limitations subsection to the Logger section of the logging config doc documenting: (a) what `_RedactionFilter` covers (Bearer + registered secrets), (b) that tool-result full-text logs pass through it, (c) the residual gap for unregistered in-body secrets, and (d) why tool results cannot be regex-masked (they must reach the LLM intact).
  - Note that registering additional high-value secrets via `register_secret()` extends coverage.
- **Out-of-Scope**:
  - Changing `_RedactionFilter` or `register_secret` behavior (would alter production logging).
  - Adding regex masking to the tool-result path.
  - Masking tool results or conversation history (they must reach the LLM unmasked by design).

## Background
`scripts/shared/logger.py` attaches `_RedactionFilter` to every entry-point logger (`Logger._configure_logger`, line 174). It redacts `Bearer <token>` headers and secret values registered via `register_secret()`. Auth tokens are registered at startup: `scripts/shared/mcp_config.py:312` (MCP auth token) and `scripts/shared/http_transport.py:84` (HTTP auth token). Tool-result full-text logs (`scripts/agent/tool_runner.py:250`, inside `_emit_tool_result`) pass through this filter. The logging config doc (`shared_03_01_runtime_and_execution-config-and-logging.md`, Section 3 `Logger`) documents the redaction bullet but has no Known Limitations section.

## Problem
Value-based redaction only covers known/registered secrets plus Bearer headers. A tool that returns an unregistered secret (e.g., an API key embedded in a response body) writes it to the log file unmasked. This is an inherent limitation of value-based redaction, not a code defect, but it is undocumented, so maintainers may assume full coverage.

## Reason for Change
The dry-run / approval review surfaced the tool-result log path. The redaction behavior is correct for registered secrets, but the boundary (what IS and IS NOT covered) is not documented anywhere.

## Implementation Intent
- Add a Known Limitations subsection to the Logger section of the logging config doc describing: (a) what `_RedactionFilter` covers (Bearer + registered secrets), (b) that tool results pass through it, (c) the residual gap for unregistered secrets, and (d) why tool results cannot be regex-masked (they must reach the LLM intact).
- Note that registering additional high-value secrets via `register_secret()` extends coverage.

## Requirements
- `REQ-001`: The redaction coverage boundary is documented (what is/is not covered) in the logging subsystem Known Limitations.
- `REQ-002`: The Known Limitations notes that registering additional high-value secrets via `register_secret()` extends coverage, and that tool results cannot be regex-masked because they must reach the LLM intact.
