## Goal
Replace the permissive, defaulting/coercing JSON-boundary contract of the RAG
ingestion pipeline (crawl artifact -> chunk-splitter -> chunk artifact ->
ingester -> store) with two independent strict schemas — one for crawler
output (`CrawlJsonPayload`/`CrawlDocument`/`read_crawl_json()`), one for
chunk-splitter output (`ChunkJsonPayload`/`ChunkDocument`/`read_chunk_json()`)
— so that any missing mandatory key, wrong type, or coerced value is rejected
at the boundary instead of silently defaulted/coerced and propagated into
chunking, embedding, and storage.

## Scope
- **In-Scope**:
  - `scripts/rag/ingestion/pipeline_utils.py`: replace `ChunkJsonRaw`,
    `read_json_file()`, `_read_chunk_json_raw()`, `_get_str_with_default()`,

  existing exception type already imported in `pipeline_utils.py` from
  `rag.exceptions`) on any validation failure, consistent with the existing
  exception-based contract `read_json_file()` already uses today (falsifiable:
  verify `rag.exceptions.ChunkFormatError` remains the appropriate exception
  type, or whether a more specific exception is warranted — see UNK-01).
- `CrawlDocument`'s fields mirror the "Required Crawl Payload" list from the
  requirement document minus the schema/artifact-type/created-by envelope
  fields (validated at the boundary but not carried on the DTO), matching how
  `ChunkDocument` already omits those same three fields today (falsifiable:
  confirmed by reading `models_data.py:31-46` — `ChunkDocument` has no
  `schema_version`/`artifact_type`/`created_by` fields).
- No external/legacy artifact files on disk need to remain readable after this
  change — the requirement's "Reason for change" explicitly states no legacy
  data is supported, so pre-existing malformed JSON files under
  `rag-src/`/`rag-src/chunk/` are expected to start failing ingestion (a
  behavior change, not a bug) after this lands.
- `strict=True`'s current behavior (all three of `schema_version`,
  `artifact_type`, `created_by` required) becomes the *only* behavior once
  `_validate_artifact()` is removed and folded into the new readers — i.e. no
  caller currently depends on the `strict=False` relaxed path in production
  code (only tests exercise `strict=False`, per the `rg` evidence below).

## Design
Two independent strict TypedDicts replace the one shared/near-duplicated
permissive shape family:

- `CrawlJsonPayload` (in `pipeline_utils.py`): all keys mandatory except none
  — `etag`/`last_modified` are mandatory *keys* with `str | None` values (not
  `NotRequired`). Validated and parsed by `read_crawl_json(path: Path) ->
  CrawlDocument`.
- `ChunkJsonPayload` (in `pipeline_utils.py`): same pattern; `etag`,
  `last_modified`, `normalized_content` are mandatory keys with nullable
  values. Validated and parsed by `read_chunk_json(path: Path) ->
  ChunkDocument`.

Both readers perform, in order: (1) JSON parse via `orjson.loads` (existing
convention per `rules/coding.md` §Key library choices), (2) top-level dict
type check, (3) exact key-set check (no missing mandatory key, no unknown
key — unknown-field rejection is the explicit policy chosen by the
requirement over the alternative of silently ignoring unknown fields), (4)
per-field type/value validation (e.g. `lang in {"ja","en"}`, `chunk_index`
non-negative int with `isinstance(x, bool)` explicitly rejected before the
int check, `chunk_type in {"text","code"}`, `chunking_strategy in
{"text","heading"}`), (5) cross-field rule for crawl payloads only (`content`
may be empty only if `code_blocks` is non-empty). Any violation raises
`ChunkFormatError` (reusing the existing exception type — see Assumptions;
this is a plan-level default, not a blocking unknown).

`crawler.py` constructs `CrawlJsonPayload`-shaped dicts directly (or
validates via `read_crawl_json`-equivalent logic before writing) so crawl
output is guaranteed to satisfy the same schema the chunk-splitter will read
back. `chunk_splitter.py` becomes a pure consumer of `read_crawl_json()` and
producer of `ChunkJsonPayload`/`ChunkDocument`; it no longer defines its own
payload TypedDicts. `ingester.py` becomes a pure consumer of
`read_chunk_json()`.

`CrawlDocument` (new, in `models_data.py`) carries the crawl-payload fields
that survive validation (`url`, `title`, `lang`, `fetched_at`, `content`,
`code_blocks`, `etag`, `last_modified`) — the envelope fields
(`schema_version`, `artifact_type`, `created_by`) are validated but not
retained, matching how `ChunkDocument` already omits them today.
`ChunkDocument` keeps its current field set but loses the four now-mandatory
fields' defaults (`chunk_type`, `source_file`, `chunk_index`,
`chunking_strategy`).

Layering: this design keeps all new/changed types inside `rag` (`pipeline_utils.py`,
`models_data.py`) and `db` (`store_protocols.py`, `store_impl.py`). Per
`.importlinter`, `rag` is permitted to import `db` (existing direction,
unchanged) and `db` must not import `rag` (unaffected — no new import from
`db` to `rag` is introduced by this change). No new cross-package import is
added by this plan, so no `import-linter` contract is at risk.

## Risks
- **Risk**: Removing `_normalize_chunk_index()`'s silent `0`-fallback means
  any pre-existing malformed chunk JSON file on disk under `rag-src/chunk/`
  (from before this change) will now raise instead of ingesting with
  `chunk_index=0`, potentially halting a batch ingestion run partway through
  (likelihood: medium — depends on whether any stale/malformed files exist in
  a given deployment's `rag-src/` at upgrade time) → **Mitigation**: This is
  the explicitly intended behavior change per the requirement's "Reason for
  change" (no legacy data supported); document the behavior change in the
  PR/commit description so an operator investigating a sudden ingestion
  failure after deploying this change immediately understands the cause is a
  pre-existing malformed artifact, not a regression, and knows to inspect/
  regenerate that specific crawl/chunk file rather than roll back the change.
- **Risk**: `ingester.py` is the highest-churn file in scope (5 commits/30d)
  and single-author (bus factor risk) — a mistake in the `_read_chunk_json()`
  migration or `chunk_index` validation could silently break ingestion in a
  way existing tests don't catch if a rejection-path test is missed
  (likelihood: low-medium) → **Mitigation**: Implement Phase 2's `ingester.py`
  changes as their own independently-revertable commit, separate from
  `crawler.py`/`chunk_splitter.py` changes, and require all of the new
  rejection-path unit tests listed in the requirement document's Tests
  section (bool/negative/string `chunk_index`, missing-key-per-field) to be
  added before removing `_normalize_chunk_index()`.
- **Risk**: Unknown-field rejection (the chosen policy) could break ingestion
  for any crawl/chunk JSON artifact already on disk that happens to carry an
  extra field not in the Required Payload lists (e.g. a leftover field from
  a previous schema version) (likelihood: low — no such extra field was
  observed in current `crawler.py`/`chunk_splitter.py` output during source
  verification) → **Mitigation**: Run the Phase 5 full-repo `rg` sweep and,
  additionally, spot-check any real `rag-src/*.json` / `rag-src/chunk/*.json`
  files present in a live/staging environment before rollout, per the
  deployment/verification step.
- **Risk**: `DocumentStore.chunk_insert()` is a `Protocol` — removing the
  default in `store_protocols.py` without an exactly matching edit to
  `store_impl.py` (or any other future `DocumentStore` implementation) would
  make the implementation structurally incompatible with the protocol at
  type-check time only, not at runtime, since Python `Protocol` does not
  enforce default-value parity at runtime (likelihood: low — only one
  implementation exists today per the requirement's scope) → **Mitigation**:
  Change both files in the same commit (Phase 3) and rely on `uv run mypy
  scripts/` (per `rules/toolchain.md`) to catch any signature drift between
  the Protocol and its implementation.
