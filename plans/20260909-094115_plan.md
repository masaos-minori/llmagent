## Goal
- Replace the single global `acked_at`/offset model with a per-consumer delivery-state
  and offset model, and make the ACK write and the offset advancement commit or roll
  back together in one SQLite transaction, so independent consumers can each ACK the
  same event and a partial ACK/offset failure can never leave the two diverged.

## Priority
High

## Scope
- **In-Scope**:
  - A new per-consumer delivery-state table (tracks `acked_at` per `(consumer_id,
    event_id)` instead of one global `events.acked_at` column).
  - A new per-consumer offset table in SQLite, replacing `offsets_dir` files as the
    live-service store, with monotonic (non-decreasing) advancement enforced by a
    single atomic SQL statement rather than a read-then-compare check.
  - A single-transaction ACK+offset write path in `ack_route.py`'s `_ack_and_offset()`.

  - `subscribe_route.py`'s offset-read path switched to the new SQLite-backed store.
  - Both DDL sources for `eventbus.sqlite` (`scripts/eventbus/schema.sql`, used by
    `open_db()`'s live-service bootstrap, and `scripts/db/schema_sql.py`'s

  - Updating `docs/adr/ADR-006-eventbus-sqlite-persistence-and-sse-delivery.md`,

## Background
`scripts/eventbus/db.py`'s `events` table (defined in `scripts/eventbus/schema.sql`)
stores `acked_at` as a single global column per event row, and
`scripts/eventbus/offsets.py` persists each consumer's last-committed sequence offset
as a separate file under `offsets_dir`, not as SQLite rows. `ack_route.py`'s
`_ack_and_offset()` calls `ack_event()` (which commits to SQLite immediately) and then
`write_offset()` (a separate, unguarded filesystem write) as two independent
operations, with no shared transaction or rollback between them — confirmed by
reading `ack_event()`, `write_offset()`, and `_ack_and_offset()` directly.

## Problem
- `acked_at` is an event-row column, not a per-consumer record: `ack_event()`'s
  `UPDATE ... WHERE event_id = ? AND acked_at IS NULL` is a single global flag, so a
  second independent consumer cannot ACK the same event without colliding on the first
  consumer's ACK state.
- If `write_offset()` raises (e.g. the `ValueError` it raises on a consumer-ID
  filename collision) after `ack_event()`'s own `conn.commit()` has already succeeded,
  the exception propagates out of `_ack_and_offset()` uncaught — confirmed: no
  try/except wraps the `write_offset()` call — so the caller receives an error even
  though the ACK is already durably committed in SQLite.
- `tests/eventbus/test_eventbus_offsets.py` exercises `write_offset()`/`read_offset()`
  in isolation and confirms today's file-based behavior, but no test in the suite
  forces the offset-write step to fail after the ACK's SQLite commit — confirmed by
  reading `tests/eventbus/test_eventbus_crash_ack.py` (only covers
  disconnect-before-ack, not a post-commit offset-write failure).
- A second, independent DDL source for `eventbus.sqlite` exists at
  `scripts/db/schema_sql.py`'s `_EVENTBUS_SCHEMA`, used by
  `db/create_schema.py::create_eventbus_schema()` (a separate bootstrap path from
  `open_db()`'s live-service `_init_schema()`/`_migrate()`) — both must define the new
  tables identically, or a freshly bootstrapped `eventbus.sqlite` and a live-service
  upgraded one would diverge (this duplication is documented as an intentional
  two-path design in `docs/90_shared_04_03_db_architecture_and_schema-migration-and-scaling.md`
  section 8b, not something this Plan removes).

## Reason for change
Separate immutable event data from consumer-specific delivery state, store consumer
progress in SQLite, and update the delivery record and offset atomically. This is
foundational: independent consumers, monotonic offsets, deterministic concurrent ACK
behavior, and a safe migration path are all needed before this issue batch's DLQ
retry-state redesign can build on a per-consumer model.

## Implementation intent
Add a per-consumer delivery-state table and a per-consumer offset table (or an
equivalent normalized schema), both keyed by `consumer_id`. Extend `ack_route.py`'s
`_ack_and_offset()` to call one new `eventbus.db` function that performs the
per-consumer delivery write and the per-consumer offset advancement using the same
SQLite connection, committing once at the end (or rolling back explicitly on
failure) instead of the current two-commit, two-resource pattern. Enforce monotonic
offset advancement with a single conditional `UPDATE`/`INSERT ... ON CONFLICT` SQL
statement rather than `write_offset()`'s current read-then-compare. Add an additive,
idempotent startup migration that reads existing `.map`/offset files via the retained
`offsets.py` functions and seeds the new offset table, without deleting any legacy
file or function. Update `subscribe_route.py` to read from the new table. Keep
`scripts/eventbus/schema.sql` and `scripts/db/schema_sql.py`'s `_EVENTBUS_SCHEMA` in
sync for the new tables.

## Design
- **Schema**: add a per-consumer delivery table (e.g. `consumer_delivery`, primary key
  `(consumer_id, event_id)`, tracking `acked_at`) and a per-consumer offset table (e.g.
  `consumer_offsets`, primary key `consumer_id`, storing the last-committed `seq`).
  Both are additive `CREATE TABLE IF NOT EXISTS` statements in both DDL sources
  (`scripts/eventbus/schema.sql` and `scripts/db/schema_sql.py`'s `_EVENTBUS_SCHEMA`);
  `scripts/eventbus/db.py::_migrate()` gets the same `CREATE TABLE IF NOT EXISTS`
  additions so an existing `eventbus.sqlite` picks them up on next startup, following
  the same idempotent-migration pattern already used for column/index additions.
- **Transactional ACK+offset**: add one new function in `eventbus.db` (e.g.
  `ack_event_for_consumer(conn, event_id, consumer_id, now)`) that performs the
  per-consumer delivery UPSERT and, only when newly-acked, the offset advancement
  UPDATE/INSERT, calling `conn.commit()` once at the end (or `conn.rollback()` on
  exception) instead of `ack_event()`'s current per-call commit. `ack_route.py`'s
  `_ack_and_offset()` calls this single function instead of `_ack_event()` +
  `write_offset()`.
- **Atomic monotonic enforcement**: the offset advancement uses a single conditional
  statement (e.g. `INSERT ... ON CONFLICT(consumer_id) DO UPDATE SET offset = excluded.offset
  WHERE excluded.offset > consumer_offsets.offset`, or an `UPDATE ... WHERE offset < ?`
  checked via `cur.rowcount`) rather than `write_offset()`'s current
  read-then-compare, per the Issue's explicit requirement. This is a
  correctness-independent-of-locking property; the existing `get_db_lock()`
  serialization already prevents concurrent-request interleaving within one process
  (see Assumptions).
- **Migration**: a new function (e.g. `migrate_legacy_offsets(conn, offsets_dir)`),
  called once from `app.py`'s `lifespan()` right after `open_db()`, enumerates `.map`
  files under `offsets_dir`, reads each real `consumer_id` and its offset via the
  existing `read_offset()`, and `INSERT OR IGNORE`s a row per consumer into
  `consumer_offsets` — idempotent (`OR IGNORE` skips already-migrated consumers) and
  additive (never touches or deletes the legacy files). Falls back to the sanitized
  filename as `consumer_id` for any offset file with no `.map` companion (`UNK-02`).
- **subscribe_route.py**: replaces `read_offset(cfg.offsets_dir, consumer_id)` with a
  new `eventbus.db` read function against `consumer_offsets`.
- **Out of scope confirmed by evidence**: `dlq.py`/`dlq_route.py`/`nack_event()` do not
  reference the new tables (Reference Files above) — `delivery_failure_count`/`dlq_at`
  stay global, consistent with the Issue's Out-of-Scope DLQ-redesign exclusion.

## Risks
- **Risk**: The two independent DDL sources (`scripts/eventbus/schema.sql` and
  `scripts/db/schema_sql.py`) can drift again in the future if only one is updated. →
  **Mitigation**: update both in this Plan and add a regression test
  (`tests/db/test_create_schema.py`) asserting the bootstrap path also produces the
  new tables.
- **Risk**: A legacy offset file written before `.map`-based collision detection was
  introduced (commit `87a84c8a3`) has no `.map` companion, so the migration cannot
  recover its original, un-sanitized `consumer_id`. → **Mitigation**: fall back to the
  sanitized filename as `consumer_id`, log a warning, and cover this case in
  `tests/eventbus/test_eventbus_offsets.py` (`UNK-02`).
- **Risk**: All target `eventbus`/`db` files have a bus factor of 1 (single author
  across name-case variants); a subtle commit-ordering bug in the new transactional
  function (e.g. committing before both writes complete) would silently reintroduce
  the exact bug this Plan fixes. → **Mitigation**: request a second reviewer
  specifically for the commit/rollback ordering in `ack_event_for_consumer(...)`.
- **Risk**: `tests/eventbus/test_eventbus_ack_endpoint.py::TestAckMonotonicOffset::test_older_seq_ack_moves_offset_backward`
  is a pre-existing failing test (confirmed failing on `master` before this Plan's
  changes) that asserts an offset SHOULD roll back on an older-seq ACK — contradicting
  both ADR-006's stated Monotonicity Invariant and `write_offset()`'s current
  behavior. → **Mitigation**: none required by this Plan (pre-existing, unrelated
  failure per `rules/ai-execution.md` Step-Level Failure Triage); it will continue to
  fail identically after this change since REQ-002 preserves monotonic enforcement.
