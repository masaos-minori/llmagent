## Problem
`prompts/04_refactor.md` currently has no explicit preference for removal/simplification
over new abstraction in its transformation step (Step 6 only covers `libcst` mechanics,
`ruff`, and "no legacy symbol names remain" — verified by reading the current file in
full). It has no ADR mechanism at all, and its Step 10 report format
(`## Files to Change`: `04_refactor.md`) has no sections for the analysis introduced by
the four sibling issues (technical debt findings, responsibility analysis, documentation
drift, architecture baseline). Its Completion gate (verified: nine existing bullet
items, none Path-C-specific) has no way to prevent an incomplete Path C change from
being reported as complete, since Path C itself, the Architecture Baseline, and the
new-abstraction justification did not exist before this epic.

## Reason for change
Without a deletion-first rule, refactoring work can default to adding abstraction
rather than removing responsibility or duplication, contrary to `AGENTS.md` intent. The
epic already introduced Path C, Architecture Baseline, and structured findings across
issues 01-04; without this issue, none of that new evidence has a required reporting
destination, and Path C work could be marked complete without its Architecture Baseline
or ADR ever having been produced.

fact, not an assumption: `adr-template.md` (repo root) defines the canonical template
body; `docs/adr/ADR-001` through `ADR-013` are thirteen files following it;
`docs/adr-index.md` maintains the ADR List table, dependency graph, and invariant

repository ADR convention when available"), this Plan's ADR Requirement
(`REQ-005`-`REQ-008`) uses that convention, not the issue's own 14-field list, as the
required template shape.

Explicit field-by-field reconciliation (issue's suggested field -> existing convention):

| Issue's suggested field | Existing convention section | Notes |

### Deletion-First placement and Path-independence
Unlike Step 3/4's existing Path A/B(/C) tooling-depth clauses, `REQ-004` makes
Deletion-First Evaluation apply identically regardless of Path classification. This
is a deliberate design choice, not an oversight: the existing Path-gated clauses
control how much *investigation tooling* runs (a cost/thoroughness tradeoff scaled to
blast radius), whereas Deletion-First Evaluation controls a *design decision* (does
this change need a new type) that has no such scaling relationship to blast radius — a
single-file Path A change can introduce an unjustified new class just as easily as a
Path C change can.

### Interaction with `plans/20260826-151739_plan.md`'s Proposal mechanism

state and format already defined by `plans/20260826-151739_plan.md` `REQ-001`, rather
