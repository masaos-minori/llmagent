## Goal
Add the failed-lifespan guard to the Event Bus's `_LoopbackVerifyingServer.startup` override so a uvicorn startup failure returns cleanly instead of raising a secondary `AttributeError`, matching the already-tested MCP server base class behavior.

## Priority
Low

## Scope
- **In-Scope**:
  - Modify `scripts/eventbus/app.py` — add the early-return guard to `_LoopbackVerifyingServer.startup`.
  - Add a regression test to `tests/eventbus/test_eventbus_startup.py` for the failing-lifespan case.
- **Out-of-Scope**:
  - Unifying the two `_LoopbackVerifyingServer` classes into one shared class.
  - Touching the MCP server base class (`scripts/mcp_servers/server.py`).
  - Changing uvicorn or its pinned version.
  - The Event Bus auth token / deployment-script sibling issues (`ebsec001`, `ebops002`).

## Background
- Found on 2026-10-20 while investigating a CI failure: `tests/eventbus/test_eventbus_startup.py::test_main_post_start_verification_binds_loopback` failed on the runner. The subprocess printed the real cause first (`FileNotFoundError: /opt/llm/schemas/event_envelope.json`, then `Application startup failed. Exiting.`) and then a second traceback ending in `AttributeError: '_LoopbackVerifyingServer' object has no attribute 'servers'`.
- The real cause was a test-environment issue already fixed (the test now forwards `EVENTBUS_SCHEMA_PATH`). This plan covers only the secondary error.
- `scripts/mcp_servers/server.py` defines the same `_LoopbackVerifyingServer` and already guards this case; the Event Bus copy in `scripts/eventbus/app.py` (`_main`) does not.

## Problem
- In the installed uvicorn (0.49.0), `Server.startup()` awaits `self.lifespan.startup()`; if the lifespan reports failure it sets `self.should_exit = True` and returns before creating the listening sockets. `Server.__init__` does not define `servers`, so the attribute does not exist at that point.
- The Event Bus override iterates `self.servers` unconditionally and raises `AttributeError`.
- Effect: the process still exits non-zero and the real error is still logged before it, so the failure is not silent. But the log ends with a misleading traceback pointing at the verification code, which costs time during diagnosis.

## Reason for Change
- Operational clarity: the last error in a failed start should be the cause, not a defect in a defense-in-depth check.
- Consistency: two copies of the same override exist; only one handles a failed startup.
- Low risk: the fix mirrors code that already exists and is tested for the MCP servers.

## Implementation Intent
- Apply the same early-return condition the MCP server base class uses, so verification runs only when startup completed and sockets exist.
- Keep the verification semantics unchanged for a successful start: a non-loopback bound socket must still raise `RuntimeError`.
- Do not merge the two copies into one shared class in this plan; that is a separate refactoring decision.

## Requirements
- `REQ-001`: The Event Bus `_LoopbackVerifyingServer.startup` returns immediately after `super().startup()` when `self.should_exit` is set or `servers` is missing or empty, so a failed lifespan does not raise `AttributeError`.
- `REQ-002`: A regression test drives the Event Bus override with a lifespan that fails and asserts no `AttributeError` is raised and the server does not report started.
- `REQ-003`: With a successful start and a non-loopback bound socket, the override still raises `RuntimeError`; the existing loopback-violation test keeps passing.
- `REQ-004`: With a successful start and a loopback bound socket, the override logs the post-start verification message as before; the existing loopback-success integration test keeps passing.

## Risks
- **Risk**: The guard could theoretically mask a real failure if `should_exit` semantics differ across uvicorn versions. → **Mitigation**: The guard only returns before the loopback check; it does not change the exit contract (`_main` still checks `server.started` and calls `sys.exit(1)`). The fix mirrors the tested MCP base class, so `should_exit` behavior is already proven in this codebase.
- **Risk**: The asyncio/subprocess test driver could be flaky. → **Mitigation**: Model the test exactly on the passing `TestStartupOverride` driver in the MCP base test rather than inventing a new one.
