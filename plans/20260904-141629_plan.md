## Background
`docs/03_rag_03_06_query_pipeline-helpers-and-cache.md` and
`docs/03_rag_05_1-configuration-reference.md` currently describe SemanticCache behavior
and configuration (confirmed by this Plan's Step 3 inspection). The originating issue's
Background names `docs/03_rag_90_inconsistencies_and_known_issues.md` as the place a
cache-freshness Known Issue would be registered — this Plan's investigation found that
file no longer exists: commit `b053a8644` ("docs: consolidate area Known Issues into
governance_03, remove resolved entries...", 2026-09-03, one day after this issue was
filed) consolidated it into `docs/00_governance_03_issue-and-uncertainty-management.md`.
No cache-freshness entry, and no entry unambiguously identifiable as the "remote/local
corpus-mismatch concern," was found there (see Unknowns UNK-02) — `ADR-010-rag-fallback.md`
discusses a related "Separate Corpus for Local" alternative but this Plan did not
confirm it is the same tracked concern the issue refers to.

## Problem
Deleting the implementation and settings (`semcacherm`, `semcacheconfig`) is not
sufficient if active tests, API references, runbooks, ADRs, or Known Issues continue to
describe `SemanticCache`, FIFO eviction, similarity thresholds, generation counters,
cache invalidation, or the `/rag_invalidate_cache` endpoint. The current cache has no
TTL, and its generation value is not used as a corpus freshness check — retaining those
descriptions would preserve incorrect implementation claims and obsolete operational
procedures.

## Reason for change
Code and configuration alone do not prevent a reader or AI agent from relying on stale
test assertions or documentation that still describes SemanticCache as current
behavior.

## Implementation intent
Replace cache-centric verification and documentation with the current design: local RAG
performs retrieval for every query, does not reuse a prior RAG context block, and
reflects the currently visible committed local RAG database state without a cache
invalidation action or service restart. Keep the remote/local corpus mismatch concern
documented as a separate, untouched issue. This Plan's implementation must not begin
until `semcacherm` and `semcacheconfig` have landed (both are already archived to
`issues/done/` as of this Plan's authoring, with their own Plans at
`plans/20260904-140151_plan.md` and `plans/20260904-141001_plan.md` — but those Plans'
*implementations* have not yet occurred; this Plan's own implementation must wait for
those, not merely for their Plan documents).

## Design
This Plan's Step 3 inspection found that the originating issue's Target Files list for
tests overlaps almost entirely with the `semcacherm` Plan's own Implementation Target
Files (`tests/rag/test_rag_cache.py`, `test_semantic_cache_invalidate.py`,
`test_semantic_cache_eviction.py`, `test_semantic_cache_concurrency.py`,
`test_rag_pipeline.py`, `test_rag_pipeline_stage.py`, `test_rag_pipeline_mcp_service.py`,
`test_rag_pipeline_server_endpoints.py`) — all eight already have a modification or
deletion plan under `semcacherm`. Re-doing that work here would either duplicate it or
race it, depending on implementation order. This Plan therefore treats those eight
files as **Reference Files**: re-verified after `semcacherm`/`semcacheconfig` land, and
only re-opened (per REQ-006) if a residual reference is found — not re-planned as
first-class edits.

In exchange, this Plan's own adversarial repository-wide search (`rg -n "SemanticCache"
tests/`) surfaced two files absent from *both* the originating issue's list and the
`semcacherm`/`semcacheconfig` Plans: `tests/rag/test_rag_quality_regression.py` (4 tests
directly importing and exercising `SemanticCache`) and `tests/rag/test_rag_repository.py`
(a `TestSemanticCache` class with 8 direct constructions). These become this Plan's
REQ-004 — the genuinely new scope this Plan contributes beyond re-verification.

The documentation half (REQ-001 through REQ-003) replaces, rather than merely deletes,
the SemanticCache section in `docs/03_rag_03_06_query_pipeline-helpers-and-cache.md`
with a concise description of the no-cache freshness guarantee (per the originating
issue's "Document the freshness guarantee precisely as retrieval from the currently
visible committed local RAG database state") — an empty section or a bare deletion note
would leave the query-pipeline helpers document incomplete, since this section is one
of the document's numbered top-level sections (`## 6.`).

REQ-008's Known-Issues cleanup targets `docs/00_governance_03_issue-and-uncertainty-management.md`
instead of the originating issue's literal `docs/03_rag_90_inconsistencies_and_known_issues.md`
reference, since that file was consolidated away one day after the issue was filed
(Assumptions). This Plan does not perform a removal now because no cache-freshness
entry currently exists there to remove (Reference Files) — REQ-008 is conditional,
matching the originating issue's own "only after implementation and replacement
regression tests are complete, if one is registered by the time this issue is
implemented" instruction.
