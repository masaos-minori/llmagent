# Plan

## Goal
Remove the legacy event-level failure counters (`delivery_failure_count`, `cycle_failure_count`) from the EventBus schema, DLQ listing, dead-letter records, redelivery, and result types, make the NACK result an explicit status, and rename the NACK response key to the per-consumer counter it already reports (`consumer_delivery_failure_count`), leaving DLQ promotion on the per-consumer counter unchanged.

## Priority
High

## Scope
- **In-Scope**:
  - Replace the `-1` / `-2` sentinels of `NackResult` with an explicit status and update the NACK route and its response key.
  - Remove the counters from `GET /dlq` items, the dead-letter record, the promotion SELECTs and log, the redelivery INSERT/SELECT, the `events` DDL, and the shared constants.
  - Update the tests and the four EventBus documents; deploy.
- **Out-of-Scope**:
  - DLQ promotion rule (`consumer_delivery_failure_count`), offset handling, and DLQ lineage redesign.
  - Dropping the two columns from the deployed `eventbus.sqlite` (see UNK-02).
  - Editing ADR text that mentions the counters (UNK-03).

## Background
`delivery_repo.py` documents both event-level counters as legacy values that NACK does not modify; the per-consumer counter `consumer_delivery_failure_count` is the only one that gates DLQ promotion. The owner decided on 2026-10-22 (answers recorded in this session) to remove the event-level counters (Option A) and to rename the NACK response key to `consumer_delivery_failure_count`. The EventBus schema-migration removal is already implemented (commit `31f8c3be9`), so no migration code references the counters or the column constants any more.

## Problem
Adversarial verification corrected and extended the Issue:
- The NACK response key `delivery_failure_count` does not return the unchanged event-level value: the route returns `consumer_failure_count` under that key whenever a consumer id is given, and `consumer_id` is mandatory for NACK. The key name is therefore misleading, not the value; removing the key without a replacement would remove the only count the response reports, which is why the key is renamed.
- `NackResult.delivery_failure_count` doubles as the status signal of the route (`-1` not found, `-2` invalid state), so the sentinels cannot be removed without a status field; the idempotent repeat NACK currently reports `ok` with the stored per-consumer count and must keep doing so.
- Three public surfaces carry the legacy field: the NACK response, the items of `GET /dlq` (`dict(r)` of the `fetch_dlq` row), and the JSON dead-letter files written by `DlqEventRecord`. Replay and SSE event payloads do not carry the counters (`_row_to_dict` selects fixed columns).
- No module outside `scripts/eventbus/` and no test outside `tests/eventbus/` plus `tests/db/test_create_schema.py` references the counters; external consumers are unknown.
- The deployed database keeps both columns (`NOT NULL DEFAULT 0`); inserts that omit them keep working.

## Reason for Change
The authoritative counter is per-consumer. Keeping a differently named, unmodified event-level counter in schema, listings, and records invites misuse, keeps redelivery copy/reset logic alive for no behavior, and the overloaded sentinels make the NACK result ambiguous.

## Implementation Intent
Implement the removal in dependency order. First the result model and the route (status instead of sentinels, renamed key), then the DLQ record, listing, promotion, and redelivery, then the DDL and constants, then tests and documents, then deployment. DLQ promotion keeps using `consumer_delivery_failure_count` and the promotion tests stay.

## Design
- Path B (more than three files; public NACK and DLQ response contract and the `events` DDL change).
- Evidence: `ack_route.py` is the only production caller of `nack_event`; `consumer_id` is mandatory for NACK; `NackResult` is re-exported by `db.py`; `dlq_route.py` serializes the `fetch_dlq` row directly; `DlqEventRecord` is written as JSON by `_atomic_write` and read by no code; replay and SSE payloads use fixed columns.
- `nack_event()` has complexity grade C (14); the status model removes branches that return paired sentinels, so it must not grow.
- Status model: `ok` carries the per-consumer count (also for an idempotent repeat), `not_found` and `invalid_state` carry no count; the route keeps the existing 404/409 mapping and the ACKed-versus-DLQ'd detail selection.
- The DDL change affects only new databases; the deployed database keeps inert columns, which `INSERT` statements that omit them tolerate.
