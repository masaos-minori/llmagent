## Background
`ADR-004-environment-failure-handling-policy.md` defines two cross-cutting invariants:
- INV-15: Fallbackは、他のAccepted ADRが明示的に定義する場合に限り許可される。
- INV-16: ADR-010は、承認済みRAG Fallbackの権威であり続ける。

Its Verification Matrix lists exactly one Integration-test row for both invariants ("ADR-010で定義される場面以外でFallbackが発生しないこと", `Blocking: Yes`), but the recorded Status is `Needs confirmation（本タスクでは個別に再実行していない）`. Every other row in the same matrix cites a specific test file and class; this row cites none. No existing issue, plan, or implementation procedure in the repository targets INV-15 or INV-16 specifically (confirmed by repository-wide search).

## Problem
The ADR-004 Verification Matrix marks a `Blocking: Yes` invariant as unverified, and records the verification gap itself as `Needs confirmation`. Left as-is, a future change could introduce a fallback path outside ADR-010's defined scope without being caught by any test or documented review step. This is the same class of gap as the (now-resolved) `CI-014` family: an ADR marks a Blocking invariant but the tracking document records the verification status as unconfirmed.

## Reason for change
The last document update left this row's Status as `Needs confirmation` without re-running or re-citing whatever verification exists. Closing the gap restores the matrix's integrity: every `Blocking: Yes` row must cite a concrete, checkable verification mechanism rather than a bare "needs confirmation" marker.

## Implementation intent
First enumerate ADR-010's defined fallback scenarios and every fallback code path in the repository, then classify each occurrence as either (a) an ADR-010-sanctioned RAG fallback or (b) an ADR-004-scope fallback that must be backed by an Accepted ADR. Map the classification to the most practical verification mechanism:
- The mechanically-verifiable subset (the RAG pipeline does not fall back on non-transport errors such as HTTP 401/403 and JSON parse errors) is already covered by existing tests; cite them in the matrix and ground the citation with the repo's existing ADR-matrix checker.
- The whole-codebase assertion ("no other ADR-004-scope fallback exists") is cross-cutting and cannot be robustly asserted by a single automated test; document a Manual Review checklist item for it, with re-review cadence and an explicit owner reference, and record why automation alone was not chosen.
Update the matrix row's Status to reflect this hybrid outcome.

**Task-size classification: Path A.** The change affects ≤ 3 files, introduces no public or
runtime-facing interface change, and touches no database schema. The breadth of the
repository-wide fallback search does not change this impact-based classification; it only

**Why a single automated test cannot fully cover INV-15/INV-16.** The invariant asserts
"no fallback anywhere outside ADR-010's scope." Enforcing this automatically requires
classifying every `fallback` occurrence in the codebase as either (a) an ADR-010-sanctioned
RAG fallback or (b) an ADR-004-scope fallback requiring an Accepted ADR. The word "fallback"
appears 221 times across `scripts/` (110 in `scripts/rag/` for ADR-010-sanctioned RAG fallback;
111 outside `scripts/rag/`). Of the 111 non-RAG occurrences, the overwhelming majority are
defensive patterns (bare-except fallthrough, default-value substitution, `_or_default`) that
are NOT ADR-004-scope fallbacks. Any pattern-based automated detector would produce
unmanageable false positives, so the whole-codebase assertion cannot be robustly asserted by
one test. This mirrors the `CI-014` family's original problem and its resolution lesson:
cross-area ADR-invariant verification ultimately needs an accountable owner plus documented
review, not just a test.

**The hybrid mechanism (recommended).** Split coverage along what is mechanically
verifiable versus what requires judgment:
- *Mechanically verifiable subset* — the RAG pipeline correctly distinguishes transport
  errors (which trigger in-process RAG fallback) from non-transport errors (401/403 auth
  errors, JSON parse errors) which do NOT trigger in-process RAG fallback. Existing tests
  (`test_401_no_fallback`, `test_403_no_fallback`, `test_json_parse_error_does_not_call_set_fallback_reason`)
  verify this by asserting that the `set_fallback_reason` callback is invoked for non-transport
  errors but the result remains None (no augmentation). Note: these tests verify the callback
  invocation pattern, not directly that `ResultSource.FALLBACK` is not set — the latter is
  enforced by the production code logic at `http_augment.py` line 141-148 which checks
  `status_code in (401, 403)` before calling `_set_fallback_reason`. REQ-002 cites them in
  the matrix and grounds the citation with `check_adr_invariant_matrix.py`.
- *Whole-codebase assertion* — "no other ADR-004-scope fallback exists" requires enumerating
  and classifying every path, which is a review activity. REQ-003 documents a Manual Review
  checklist item with re-review cadence and an owner reference.
- *Regression guard (confirmed; resolves UNK-01)* — REQ-005 adds a narrow test locking the
  ADR-010 marker (`ResultSource.FALLBACK` / `in_process_fallback`) to the sanctioned RAG
  augment path, so the single allowed fallback cannot silently relocate. It guards against
  regressions in the one automatable spot; it does not claim to cover the full invariant.

**Marker identity.** The ADR-010-sanctioned fallback is uniquely identifiable by the
`ResultSource.FALLBACK` / `in_process_fallback` markers. In production code,
`ResultSource.FALLBACK` is assigned only at `scripts/rag/augment.py` line 87;
`in_process_fallback` appears in `scripts/rag/http_augment.py` as a string literal mapping
to `HttpResultKind.ERROR`. Both markers are confined to the ADR-010-sanctioned RAG pipeline
and nowhere else in production code. Test files reference these markers in assertions but
do not assign them.

**Matrix Status update.** The row's Status becomes a precise hybrid statement rather than a
single value: the covered subset is `Confirmed` (existing tests), and the cross-cutting
remainder is covered by a documented Manual Review with a cadence — satisfying the issue's
requirement that the marker no longer be a bare `Needs confirmation`.
