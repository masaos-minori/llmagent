## Goal
- Keep the event loop responsive while `/session` storage work runs, and make `CommandDef.is_async` a contract validated at registry construction instead of metadata that only fails when the command is invoked.

## Priority
Medium

## Scope
- **In-Scope**:
  - Fail-fast validation in `CommandRegistry.__init__` that every `CommandDef.is_async` matches the kind of its handler (`inspect.iscoroutinefunction`).
  - Running the `/session` storage/maintenance/export/RAG group (`db_dispatch` at `cmd_session.py:215-232`) off the loop via `asyncio.to_thread`, awaited by `_cmd_session`.
  - Tests for the construction-time mismatch, for loop responsiveness during a stubbed long command, and for the cancellation semantics that offloading actually produces.
  - Documenting the `is_async` contract and the long-running/shutdown behavior of the `/session` group.
- **Out-of-Scope**:
  - Making an in-progress SQLite call interruptible (`sqlite3.Connection.interrupt()` or any DB-layer plumbing). `scripts/agent/db/helper.py` connection handling is not touched.
  - The `is_async=False` command groups (`/memory`, `/context`, `/history`, `/clear`, `/undo`, `/stats`, `/config`, `/reload`, `/debug`, `/help`, `/plan`) and the separate question of whether `/memory` should become async.
  - Signal handling and `_shutdown_event` wiring (`repl001`), persist-on-shutdown (`repl002`), input-timeout semantics (`repl003`). `scripts/agent/repl_input_loop.py` and `scripts/agent/repl.py` are not modified.
  - Argument parsing and validation (`cmd002`) and command-error rendering (`cmd001`); speeding up the DB operations themselves.

## Background
Slash commands are dispatched inside the running event loop: `ReplInputLoop._repl_loop` wraps `_dispatch_line` in a task (`scripts/agent/repl_input_loop.py:254`) and either races it against the shutdown event (`:255-284`) or awaits it directly (`:285-297`). `CommandRegistry._invoke_handler` awaits or calls the handler inline depending only on `cmd.is_async` (`scripts/agent/commands/registry.py:105-113`). Three commands declare `is_async=True` (`/compact`, `/mcp`, `/session`: `scripts/agent/commands/command_defs_list.py:85`, `:93`, `:104`); of those only `/session` reaches storage, through the sync sub-handlers in its `db_dispatch` table (`scripts/agent/commands/cmd_session.py:215-232`).

`is_async` is a required field of `CommandDef` (`scripts/agent/commands/command_defs.py:65`, no default), so all 14 registered command entries state it explicitly. `CommandRegistry.__init__` already validates handler *names* fail-fast (`registry.py:67-72`); nothing validates handler *kind*.

## Problem
- Blocking storage work runs on the loop thread. `_cmd_session` calls `DbSessionOps.health`/`checkpoint`/`vacuum`/`purge`/`recover` and `_db_session_stats`, `_rag_consistency`, `_rag_rebuild_fts`, `_rag_rebuild_vec`, `_session_export` as plain callables and invokes them with `handler()` (`cmd_session.py:215-232`). Each of those opens its own SQLite connection and runs to completion (`scripts/agent/services/db_maintenance_service.py:35`, `:42`, `:52`, `:61`, `:69`; `scripts/agent/services/rag_maintenance_service.py:38`, `:48`, `:68`; `scripts/db/helper.py:267` `checkpoint`, `:283` `vacuum`). A `VACUUM` or a `chunks_vec` rebuild holds the loop for its whole duration.
- `is_async` is unvalidated by production code: awaiting a sync handler raises `TypeError: 'NoneType' object can't be awaited` (verified at runtime), so a mismatch is a per-command runtime failure rather than a startup error. The invariant is checked only after the fact by tests (`tests/agent/commands/test_command_registry_consistency.py:35-49`), i.e. only when the test suite runs, never when the agent starts.
- The shutdown path the issue points at is not live, and its bound is weaker than it looks. `ReplInputLoop` is constructed with `None` (`scripts/agent/repl.py:82`, `:85`) and `Repl.run()` rewires only `self._signal` (`repl.py:113-114`) and the shutdown coordinator (`:121`), so `self._shutdown_event` stays `None`, `repl_input_loop.py:256-257` is always false, and the live path is `await asyncio.wait_for(dispatch_task, ...)` (`:285-297`). Its `timeout` is evaluated when the await starts, so a signal arriving while a command is running does not bound that command; `scripts/agent/signal_handler.py:56` sets `ctx.conv.shutdown_requested`, which bounds only the next dispatch. On expiry the loop logs `_log_graceful_shutdown_timeout()` (`repl_input_loop.py:125`) and breaks (`:298-304`) without cancelling the task.
- Cancelling an await does not cancel the work. Measured with the project's Python: a task awaiting `asyncio.to_thread(time.sleep(1.0))` cancelled after 0.1s leaves the worker running, and `asyncio.run()` returns at 1.002s because loop shutdown joins the default executor. Any statement that a running storage call can be cancelled by a shutdown request is therefore false under offloading, and the issue's acceptance criterion had to be corrected to state that.

## Reason for Change
The commands most likely to run for seconds are maintenance commands an operator runs while the REPL is live. While one of them holds the loop, no other coroutine (title generation, audit writes, the input watcher) can progress, and no shutdown bound applies to the call that is actually blocking. Separately, a `CommandDef`/handler kind mismatch is the kind of mistake a future contributor will make while adding a command, and today it is invisible until that command is typed.

## Implementation Intent
Do not restructure the command layer. Add the missing startup check where the other startup checks already are (`CommandRegistry.__init__`), and move blocking storage work off the loop at the one place where the `/session` group already collects its callables (`db_dispatch`), by making that table produce awaitables that `_cmd_session` awaits through `asyncio.to_thread`. State the resulting behavior instead of implying stronger cancellation than the mechanism provides.

## Requirements
- `REQ-001`: `CommandRegistry.__init__` raises `TypeError` when `cmd.is_async` does not equal `inspect.iscoroutinefunction(getattr(self, cmd.handler))`, with a message naming the command name, the handler name, and the mismatched kind. The check runs for every entry of `_COMMANDS` at construction, before the registry is usable.
- `REQ-002`: The existing handler-name `AttributeError` check (`registry.py:67-72`) keeps its behavior and message, and the new check reuses the same lookup path as `_get_handler` (`registry.py:74-81`) rather than introducing a second lookup. `_invoke_handler` (`:105-113`) is not changed: `is_async` keeps describing only how the dispatcher calls the handler.
- `REQ-003`: Every entry of the `/session` `db_dispatch` table (`cmd_session.py:215-232`) becomes a zero-argument callable returning an awaitable, produced by `asyncio.to_thread(<the existing sync callable>, <its arguments>)`, and `_cmd_session` awaits it (`await handler()`). The table has one value type; no entry stays a plain sync call.
- `REQ-004`: Only whole callables that open and close their own SQLite connection inside the call are offloaded. No connection object, cursor, or `SQLiteHelper` instance is created on one thread and used on another. This holds for the current targets (`db_maintenance_service.py:35`, `:42`, `:52`, `:61`, `:69`; `rag_maintenance_service.py:26`, `:38`, `:48`, `:68`, `:82`; `scripts/agent/session.py:126`, `:168`, `:181`, `:208`, `:250`), which is what makes offloading compatible with `sqlite3.connect(..., timeout=...)`'s default `check_same_thread=True` (`scripts/db/helper.py:135`).
- `REQ-005`: Output for successful runs is unchanged: same messages, same order, same `OutputPort` methods and tags. No new output method, tag, exception class, or command is introduced. The `/session` subcommands that are not in the table (`list`, `load`, `rename`, `delete`: `cmd_session.py:187-212`) keep their current call form.
- `REQ-006`: The behavior is stated, not implied: an offloaded call continues to run after its await is cancelled or abandoned, and interpreter shutdown joins the worker before returning. A command's storage call is therefore bounded by the operation itself, not by `_GRACEFUL_TIMEOUT_S` (`repl_input_loop.py:55`), which bounds only the await.
- `REQ-007`: No `is_async=False` handler changes kind, and no `CommandDef.is_async` value changes. `/session` already declares `is_async=True` (`command_defs_list.py:104`), so `REQ-003` requires no metadata change. `command_defs_list.py` is not modified.
- `REQ-008`: The `is_async` contract (it selects the dispatcher's call form; it is validated at construction; a mismatch is a startup error) and the long-running nature of the `/session` maintenance group are documented in the chapters that already own those statements.

## Assumptions
- **A1**: `TypeError` is the right startup exception for a kind mismatch: it is the exception class the current failure already produces (`'NoneType' object can't be awaited`), so the change moves the same failure earlier with an attributable message instead of introducing a new error surface. `CommandDispatchError` (`scripts/agent/commands/exceptions.py`) is not used: those classes belong to the dispatch/render boundary decided in `cmd001`, and a registry that never constructed has no command boundary to attribute to.
- **A2**: Offloading whole callables is safe with this project's SQLite model because every command-side storage operation opens and closes its own connection inside the call (verified in the `Reference Files` rows). A shared connection would need `check_same_thread=False` plus a lock, which is the Event Bus model (`scripts/eventbus/db_conn.py:22-38`) and is not introduced here.
- **A3**: Writing command output from the worker thread (the existing success/KV/error calls live inside `DbSessionOps` and the `_rag_*` sub-handlers) is acceptable because the REPL dispatches one line at a time (`repl_input_loop.py:254` creates one dispatch task per input line and awaits it before reading the next). No concurrent command execution is introduced.
- **A4**: The loop's default executor is the right executor (no dedicated pool): commands are sequential, so at most one worker is in flight at a time, and `asyncio.run()` joins it at shutdown. `cli_view.py:278-291`'s dedicated executor exists for unbounded human input, which is a different problem (UNK-04).
- **A5**: The existing whole-registry scans in `test_command_registry_consistency.py` stay valuable after the production check is added (they assert today's metadata is consistent, which is AC-2); they are kept rather than deleted, so the change removes no coverage.

## Design
Path B: two independent changes (a startup contract and an execution-boundary change) in two production modules, an observable behavior change (a mismatch now fails at startup; `/session` maintenance work now runs on a worker thread), and an existing test suite that encodes the old assumption. Classification evidence: the issue's target list spans `registry.py`, `cmd_session.py`, `db_session_ops.py`, the memory modules, and `repl_input_loop.py`, and the verification shows the live blocking surface is exactly one dispatch table reached from one async handler — so the scope narrows to two files while the reasoning stays cross-module.

Design decisions, grounded in the reads above:
- Validate at construction, in the loop that already validates handler names (`registry.py:67-72`), because that is the only place all 14 entries are seen before use. Raising `TypeError` (A1) keeps the failure class identical to today's invoke-time failure and only moves it earlier, so no new error-handling surface is needed and `cmd001`'s dispatch-boundary design is untouched.
- Offload at the `db_dispatch` table (`cmd_session.py:215-232`), not inside `DbSessionOps` or the services: no signature changes, no new async API, and the existing patch targets stay valid (`test_agent_cmd_session.py` patches `agent.commands.db_session_ops.DbMaintenanceService`, which a worker-thread call still resolves). Converting the service methods to `async def` instead would move the concurrency decision into the storage services, which the issue's Constraints forbid.
- Wrap **every** entry of the table so it has one value type (`Callable[[], Awaitable[None]]` via `asyncio.to_thread`) instead of mixing sync and awaitable entries. A mixed table would let the next added sub-command silently block the loop, and the whole point of the change is that the boundary is not a per-entry judgement call. `list`/`load`/`rename`/`delete` are outside the table and keep their current form (UNK-03 records the boundary).
- Offload the whole callable rather than its DB part, because the connection is created inside it (`A2`); splitting "compute in thread, print on loop" would require restructuring five methods for no additional safety (A3 states why the current shape is acceptable).
- Keep `repl_input_loop.py`, `repl.py`, and `signal_handler.py` read-only. The cancellation half of the issue is not implementable there before `repl001` makes the shutdown event reachable, and the measured join behavior (`REQ-006`) is a property of `asyncio`, not of this codebase.
- Cross-plan overlap, recorded deliberately: `scripts/agent/commands/registry.py` is also a Frozen target of `plans/20261021-110616_plan.md` (`cmd001`), and `scripts/agent/commands/cmd_session.py` plus `docs/23_agent/agent_07_07_*` are also Frozen targets of `plans/20261022-013404_plan.md` (`cmd002`). The touched regions are disjoint (`__init__` vs `dispatch`; `db_dispatch` vs `_session_list`), but the implementation order must be `cmd001` → `cmd002` → this Plan so neither rebase touches another plan's frozen region in the same pass. `check_plan_target_overlaps.py` reports these pairs and they are not resolved by editing either other plan.

## Risks
- **Risk**: A new startup failure turns a per-command defect into a whole-REPL startup failure. → **Mitigation**: AC-2 proves the 14 registered entries already satisfy the invariant, so nothing that starts today stops starting; the message names the command and handler, and the failing test is one line of `CommandDef` metadata.
- **Risk**: Offloading makes process exit slower than today, because `asyncio.run()` joins the default executor and the storage call cannot be cut short (measured: 1.002s for a 1.0s call). → **Mitigation**: the behavior is stated in `REQ-006` and in `agent_07_07` instead of being hidden, and AC-5 tests it so it cannot be mistaken for a regression later. `deploy/deploy.sh` service restarts use their own timeout, which is unchanged.
- **Risk**: `VACUUM` and `REBUILD` hold SQLite locks while other connections (Event Bus, workflow, session persistence) are live, and offloading lets them overlap in wall-clock time instead of serializing on the loop thread. → **Mitigation**: `_DEFAULT_BUSY_TIMEOUT_MS = 30000` (`db/helper.py:21`) and WAL are already applied to every connection (`apply_connection_pragmas`, `helper.py:32-43`); no new concurrency is introduced at the command level because the REPL dispatches one line at a time (A3), and the risk is documented rather than assumed away.
- **Risk**: The new `Awaitable`-typed table could hide a mistake if a future entry returns a non-awaitable. → **Mitigation**: `mypy --no-namespace-packages scripts/agent` is run against the typed table in the validation plan, and `await handler()` fails loudly for a non-awaitable.
- **Risk**: Output statements executing inside a worker thread could interleave with loop-thread output. → **Mitigation**: A3 records that only one command executes at a time; `test_agent_cmd_session.py`'s `capsys` assertions are the existing guard that the exact message text and order are unchanged (AC-4).
- **Risk**: `cmd_session.py` and `agent_07_07` are also Frozen targets of the `cmd002` Plan, and `registry.py` of the `cmd001` Plan. → **Mitigation**: the regions are disjoint and the implementation order is fixed in `Design` (`cmd001` → `cmd002` → this Plan); `check_plan_target_overlaps.py` is run in the validation plan so an unintended overlap is visible, not inferred.
- **Risk**: The docs row could state a stronger guarantee than the mechanism provides (e.g. "commands can be cancelled"). → **Mitigation**: the wording is derived from `REQ-006` and UNK-01's confirmed policy, and AC-6 checks the two chapters against that wording.
