## Goal
Split the monolithic `scripts/eventbus/db.py` (678 lines, 14 responsibilities) into 6 layered modules while preserving backward-compatible import paths and resolving the nack_event() return type breaking change.

## Priority
Medium

## Scope
- **In-Scope**: Splitting `db.py` into 6 modules, creating `NackResult` dataclass, replacing magic tuples, scoping column constants, keeping `db.py` as thin re-export stub, updating all callers' import paths
- **Out-of-Scope**: Changing HTTP API surface, adding new database indexes beyond `_migrate()`, migrating from SQLite to another engine, adding connection pooling/async drivers, changing `_db_lock` serialization strategy, modifying `schema.sql` DDL definitions

## Background
`scripts/eventbus/db.py` was written incrementally without explicit architectural boundaries. Each new feature (per-consumer delivery tracking, DLQ promotion, legacy offset migration) was added directly into the same module. The module currently handles:
- SQLite connection lifecycle (`open_db`, `check_db`, `get_db_lock`)
- Schema initialization and additive migration (`_init_schema`, `_migrate`)
- Event CRUD operations (`insert_event`, `get_seq`, `fetch_events_since`, `fetch_dlq`, `count_dlq`)
- Ack/nack semantics (`ack_event`, `nack_event`, `ack_event_for_consumer`)
- DLQ operations (`requeue_event`, `redeliver_event`)
- Legacy offset migration (`migrate_legacy_offsets`)
- Module-level constants for column names (11 `_COL_*` identifiers)

This violates the single-responsibility principle and makes it difficult to reason about which callers depend on which functions.

## Problem
1. **Fragile SQL pattern**: Multiple functions use `f"...{col}..."` patterns with `# nosec B608` comments. While column names come from module-level constants (not user input) and is currently safe, this pattern is fragile — any future developer adding a user-derived value would introduce a real SQL injection vulnerability.
2. **No clear ownership boundary**: A reader cannot determine which functions belong together without reading every docstring. For example, `ack_event_for_consumer` and `get_consumer_offset` both deal with per-consumer delivery state, but they are interleaved with unrelated event operations.
3. **Migration logic entangled with business logic**: `_migrate()` contains DDL statements for three different tables (`consumer_delivery`, `consumer_offsets`, plus index creation) alongside column ALTER statements. This makes schema evolution hard to audit.
4. **`migrate_legacy_offsets()` performs file I/O**: It reads `.map` and `.offset` files from disk, which is a completely different concern from database operations.
5. **Magic return-value conventions**: `nack_event()` returns `(-1, -1)` or `(-2, -2)` for error states — tuples with no type safety, requiring callers to remember magic values.

## Reason for change
The module has grown to 678 lines across 14 public functions and 3 private helpers. Adding new features requires understanding all of these responsibilities simultaneously. The f-string column-name pattern, while currently safe, should be made uniform across layers to prevent future bugs as the team grows. A clean separation of concerns now prevents future technical debt accumulation.

## Implementation intent
Apply a **layered architecture** approach: each layer owns its own data access and exposes only the operations consumers need. The layers are:

1. **Connection layer** (`db_conn.py`): Connection lifecycle, locking, pragma application. Only exports `open_db()`, `check_db()`, `get_db_lock()`.
2. **Schema layer** (`schema.py`): Schema definition, migration logic. Exports `_SCHEMA_PATH`, `_apply_pragmas()`, `_init_schema()`, `_migrate()`.
3. **Event repository** (`event_repo.py`): All event read/write operations. Exports `insert_event()`, `get_seq()`, `fetch_events_since()`, `fetch_dlq()`, `count_dlq()`.
4. **Delivery repository** (`delivery_repo.py`): Ack/nack semantics and per-consumer delivery state. Exports `ack_event()`, `nack_event()`, `ack_event_for_consumer()`, `get_consumer_offset()`.
5. **DLQ repository** (`dlq_repo.py`): Dead-letter queue operations. Exports `requeue_event()`, `redeliver_event()`.
6. **Offset migrator** (`offset_migrator.py`): Legacy offset migration. Exports `migrate_legacy_offsets()`.

Each layer uses parameterized queries exclusively for values. Column names may remain as module-level constants within each layer; columns shared across multiple layers (e.g., `_COL_EVENT_ID` used by all layers) may stay in a shared location. Return types should use `dataclasses` or `NamedTuple` instead of raw tuples for error states.

`db.py` becomes a thin re-export stub that delegates to the 6 new layers, satisfying both "monolithic file removed" and "backward-compatible imports" constraints simultaneously.

## Design
### Layered Architecture Decision
Each layer owns its own data access and exposes only the operations consumers need. This follows the Repository Pattern — each layer is responsible for a single bounded context within the event bus domain.

### Connection Layer (`db_conn.py`)
- Exports: `open_db()`, `check_db()`, `get_db_lock()`
- Responsibility: SQLite connection lifecycle, locking, pragma application
- Rationale: These functions manage the database connection itself and are used by all other layers

### Schema Layer (`schema.py`)
- Exports: `_SCHEMA_PATH`, `_apply_pragmas()`, `_init_schema()`, `_migrate()`
- Responsibility: Schema definition, migration logic
- Rationale: Migration logic is tightly coupled with schema evolution; separating it makes schema auditing easier

### Event Repository (`event_repo.py`)
- Exports: `insert_event()`, `get_seq()`, `fetch_events_since()`, `fetch_dlq()`, `count_dlq()`
- Responsibility: All event read/write operations
- Rationale: Events are the primary data entity; they have their own CRUD surface area

### Delivery Repository (`delivery_repo.py`)
- Exports: `ack_event()`, `nack_event()`, `ack_event_for_consumer()`, `get_consumer_offset()`
- Responsibility: Ack/nack semantics and per-consumer delivery state
- Rationale: Delivery state is orthogonal to event storage; ack/nack operations modify event state based on consumption

### DLQ Repository (`dlq_repo.py`)
- Exports: `requeue_event()`, `redeliver_event()`
- Responsibility: Dead-letter queue operations
- Rationale: DLQ operations are a distinct concern from normal event flow

### Offset Migrator (`offset_migrator.py`)
- Exports: `migrate_legacy_offsets()`
- Responsibility: Legacy offset migration with isolated file I/O
- Rationale: File I/O is a completely different concern from database operations; isolating it prevents coupling

### Re-export Stub (`db.py`)
- Becomes a thin delegation module that imports from the 6 new layers and re-exports all public symbols
- Satisfies both "monolithic file removed" and "backward-compatible imports" constraints simultaneously
- Example structure:
```python
from eventbus.db_conn import check_db, get_db_lock, open_db
from eventbus.event_repo import count_dlq, fetch_dlq, fetch_events_since, insert_event, get_seq
from eventbus.delivery_repo import ack_event, ack_event_for_consumer, get_consumer_offset, NackResult
# ... etc.
__all__ = ["open_db", "check_db", "get_db_lock", "insert_event", "get_seq", ...]
```

### NackResult Dataclass Design
```python
from dataclasses import dataclass
from typing import Literal

@dataclass(frozen=True)
class NackResult:
    delivery_failure_count: int | Literal[-1]
    cycle_failure_count: int | Literal[-2]
```
Rationale:
- `frozen=True` prevents accidental mutation of error state
- `Literal[-1]` / `Literal[-2]` make error states explicit at the type level
- Exception-based approach rejected because it breaks backward compatibility with existing callers that use tuple unpacking
- `Enum` rejected because error states are not mutually exclusive — a single call can produce different failure counts independently

### Column Constant Scoping
- Shared columns (`_COL_EVENT_ID`, `_COL_SEQ`, `_COL_ACKED_AT`, `_COL_DLQ_AT`) → common location (`_constants.py` or similar)
- Layer-owned columns (`_COL_DELIVERY_FAILURE_COUNT`, `_COL_CYCLE_FAILURE_COUNT`, `_COL_CONSUMER_DELIVERY_FAILURE_COUNT`) → `delivery_repo.py`
- Layer-owned columns (`_COL_DLQ_REQUEUE_COUNT`, `_COL_REDISTRIBUTED_FROM`) → `dlq_repo.py`
- Layer-owned columns (`_COL_CONSUMER_ID`, `_COL_OFFSET`) → `delivery_repo.py`
