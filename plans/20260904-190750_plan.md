## Goal
- Turn `RepositoryState.WriteProtectionPipeline`'s documented nine-stage sequence into
  the actually-executed sequence for `git_checkout`/`git_pull`/`git_push` — record real
  stage outcomes, capture a genuine post-operation snapshot, and verify
  operation-specific postconditions instead of an unconditional-success placeholder.

## Priority
High

## Scope
- **In-Scope**: defining the canonical stage sequence in one location; capturing a
  fresh post-operation `RepositoryState` instead of reusing the pre-state; replacing
  `verify_postcondition()`'s placeholder with real per-operation checks
  (checkout/pull/push); wiring `record_stage()` so `stages`/`all_stages_succeeded`/
  `last_failed_stage` report real data; fixing the checkout argument-order bug this
  Plan's investigation found (`git checkout -- <branch>` does not switch branches);
  bypass-proof tests through the HTTP dispatch path; correcting the record of the
  prematurely-resolved-and-since-deleted MCP-003 Known Issue.
- **Out-of-Scope**: protected-branch/ref authorization content itself and the Stage 3
  call site (`gitauth`, already scoped as that Plan's REQ-001 — this Plan coordinates
  with, not duplicates, it; see Design); detached-HEAD/dry-run precondition behavior
  (`gitdryrun`); tool dispatch unification, i.e. making `GitService`'s dispatch table
  or `git_add`/`git_commit` reachable via `POST /v1/call_tool` (`gitdispatch`);
  repository-path containment/audit (`gitpathaudit`); remote authorization/concurrency
  (`gitremote`); re-executing `plans/done/20260901-223706_plan.md`'s own scope (that
  Plan already landed — see Background for what it actually did).

## Background

planned to mark `docs/04_mcp_90_inconsistencies_and_known_issues.md`'s `MCP-003`

`plans/done/20260901-223706_plan.md` landed (commit `62b12afd1`, 2026-09-03,
"doc: update MCP-003/MCP-004/MCP-005 status to resolved with verified evidence"),

`test_is_safe_ref` as verification — both of which exercise `GitService` directly, a
path this Plan's sibling (`gitauth`, `plans/20260904-162951_plan.md`) confirmed has
zero external callers in production (`GitMCPServer.dispatch()` is never invoked; the
live `POST /v1/call_tool` route uses `RepositoryState`/`WriteProtectionPipeline`
instead). The "resolved" determination was therefore made against the wrong code
path. One day later, commit `b053a8644` ("consolidate area Known Issues into
governance_03, remove resolved entries...") deleted
`docs/04_mcp_90_inconsistencies_and_known_issues.md` entirely, including the (wrongly)
resolved MCP-003 entry — it was not carried into the consolidated
`docs/00_governance_03_issue-and-uncertainty-management.md` (confirmed absent by
repository-wide search for "MCP-003", "GIT-002", and "WriteProtectionPipeline" there).
The underlying gap is now undocumented anywhere.

Direct inspection of `WriteProtectionPipeline.run()` (`repository_state.py:510-531`)
confirms: it calls Stage 5 (preconditions), Stage 6 (execution), and Stage 7
(`verify_postcondition()`, which unconditionally returns `(True, "")` at line
157-164) — Stage 3 (`verify_authorization()`) is never called (this is `gitauth`'s
Plan to fix, see Dependencies/Design below), and `record_stage()` (line 533) has zero
call sites anywhere in `repository_state.py`, so `stages`, `all_stages_succeeded`, and
`last_failed_stage` are permanently empty/vacuously-`True`/`None`.

## Problem
The pipeline's own bookkeeping cannot be trusted: `verify_postcondition()` always
succeeds regardless of what Stage 6 actually did; `PipelineResult.reject()`/
`ok_result()` store only the pre-operation `RepositoryState` (no post-state field
exists on `PipelineResult` at all); and `record_stage()` is dead code, so
`all_stages_succeeded` is always `True` by vacuous truth (`all(...)` over an empty
list) regardless of what actually happened. Real postcondition enforcement instead
happens through a separate mechanism — `format_checkout()`/`format_pull()`/
`format_push()` (`format_output.py`) raising `GitServiceError` — which itself has a
confirmed bug this Plan's investigation reproduced directly: `format_checkout()`
calls `state._repo.git.checkout("--", req.branch)`, i.e. `git checkout -- <branch>`.
Git's argument grammar treats everything after `--` as a pathspec, not a branch name
— reproduced directly (`git checkout -- other` on a real repo with an `other` branch
fails with `error: pathspec 'other' did not match any file(s) known to git`; the
correct form, `git checkout other --`, succeeds). This means `format_checkout()`'s own
non-dry-run branch-switch path is broken independent of the pipeline gaps above — no
existing test caught this because `test_format_output.py`'s checkout tests use
`MagicMock` repos that never execute real Git commands, and no HTTP-level
non-dry-run checkout test exists.

## Reason for Change
The pipeline's own stage list and result reporting should describe what actually
executes, not an aspirational nine-stage design — trusting
`PipelineResult.all_stages_succeeded` as ground truth today is actively misleading
(it is always `True`), and the underlying gap has no tracked record after MCP-003's
deletion.

## Implementation intent
Define the canonical pipeline stages and responsibilities in
`WriteProtectionPipeline.run()`, execute repository validation, write permission
checks, state capture, command-specific preconditions, execution, real postcondition
verification, audit preparation, and structured-result generation in the documented
order (Stage 3 authorization itself is `gitauth`'s Plan to wire — REQ-009 below
defines the coordination), record each stage's outcome via `record_stage()`, capture a
fresh post-operation `RepositoryState` for postcondition checks instead of reusing the
pre-state, and fix `format_checkout()`'s argument-order bug so postcondition checks
have a real branch switch to verify in the first place.

## Design
This Plan's central coordination decision concerns `gitauth`
(`plans/20260904-162951_plan.md`), filed alongside the same originating issue and
touching the same `WriteProtectionPipeline.run()` method: `gitauth`'s REQ-001 already
adds the missing Stage 3 (`verify_authorization()`) call. This Plan does not duplicate
that addition — REQ-009 records the coordination explicitly, and REQ-008 (stage
recording) is written to cover whatever stages `run()` executes after `gitauth`'s
change lands, without assuming a specific line number or exact insertion point that
could drift. This split matches the originating issues' own textual division: `gitauth`
owns "authorization and target resolution... must be consumed by this pipeline rather
than reimplemented" (gitpipeline's Implementation Intent) — i.e. gitauth produces the
authorization result, gitpipeline (this Plan) ensures the pipeline correctly records
and orders around it.

The `verify_postcondition()` redesign consolidates with `format_output.py`'s existing
checks per the issue's Required Changes ("consolidating with or replacing
format_output.py's existing, working checks rather than leaving both as separate,
partially-overlapping mechanisms") and per the issue's own Unresolved Question. This
Plan resolves that question in favor of consolidation into `format_output.py`'s
existing exception-raising mechanism (which already has operation-specific logic
for checkout/pull/push) rather than building a second, parallel postcondition
mechanism in `verify_postcondition()` — `verify_postcondition()` is changed to
actually reflect whether the operation raised `GitServiceError` (i.e., whether Stage 6
completed without a postcondition-triggered exception), using the fresh post-state
(REQ-002) to add an independent verification layer (e.g. confirming the post-state's
`active_branch` actually matches, as a second check beyond `format_checkout()`'s own
now-fixed check) rather than a redundant reimplementation.

The `format_checkout()` argument-order bug (REQ-007) was not stated in the originating
issue and was found only by directly reproducing the checkout call against a real
`git.Repo` — the existing test suite's `MagicMock`-only checkout tests could not have
caught it, since they stub the Git call itself. Fixing this is a precondition for
REQ-004's postcondition check to have anything meaningful to verify: a checkout that
never actually switches branches makes "does the resulting branch match the request"
trivially always-false or always-erroring, not a real Stage 7 check.

## Risks
- **Risk**: Fixing `format_checkout()`'s argument order (REQ-007) could reveal that
  production has never successfully performed a non-dry-run branch checkout via this
  path, meaning downstream callers may be depending on the current (broken) failure
  behavior → **Mitigation**: the fix restores documented Git semantics (`git checkout
  <branch>` switching branches); any caller depending on checkout always failing was
  depending on a bug, not a contract — flag prominently in the Step 10 report.
- **Risk**: Adding real postcondition checks could reject operations that
  `format_output.py`'s existing checks currently allow through, if the two mechanisms
  disagree on edge cases → **Mitigation**: REQ-003's consolidation approach reuses
  `format_output.py`'s existing logic rather than building an independent, possibly
  conflicting second implementation.
- **Risk**: This Plan and `gitauth`'s Plan both modify
  `scripts/mcp_servers/git/repository_state.py`; implementing them out of coordination
  order (this Plan's `record_stage()` wiring assuming a Stage 3 call site `gitauth`

  site itself; implementers should land `gitauth`'s Plan first or coordinate the two
  diffs manually, per both Plans' Dependencies sections.
- **Risk**: Filing a new Known Issue entry for a corrected-premature-resolution could
