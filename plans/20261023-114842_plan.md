## Goal
- Make every launch path of an MCP server (generated binary launchers, `mcp_launcher.py`, `python -m mcp_servers.mdq`, `python -m <server module>`) refuse to bind when the server's security posture is not validated, by enforcing the gate in the one method they all call, `MCPServer.run_http()`.

## Priority
Medium

## Scope
- **In-Scope**: Call the existing per-module posture gate from `MCPServer.run_http()` for servers in the `mcp_servers.` namespace, failing closed when a server module defines none; fix `mdq/__main__.py` so it cannot start the server without the gate and has a correct docstring and a `__main__` guard; correct the launcher comment in `deploy/build_binaries.sh`; add tests; update the startup documentation.
- **Out-of-Scope**: Changing which posture checks are FAILED versus WARNING; posture checks inside request handlers (UNK-01); removing the per-module `__main__` gate calls (UNK-02); the empty-token, config-isolation, audit-log and shell-environment issues.

## Background
Each of the ten server modules defines `_enforce_posture_gate()` (exit 1 when `_security_posture.validated` is false) and calls it only from `if __name__ == "__main__":`. The production start path is the Agent launching `/opt/llm/bin/mcp_*` binaries; `gen_launcher()` in `deploy/build_binaries.sh` writes a launcher doing `from <module> import <Class>` and `<Class>().run_http()`. `scripts/mcp_launcher.py` also calls `instance.run_http()`, and `mdq/__main__.py` runs `MdqMCPServer().run_http()` at import time. `MCPServer.run_http()` validates loopback binding and config isolation but does not consult the posture.

## Problem
A server with a FAILED posture binds and serves when started through any path except `python -m <server module>`. For shell-mcp with `shell_sandbox_backend = "none"`, `validate_shell_security()` returns `server.sandbox_backend: FAILED` while `SubprocessRunner.build_argv()` returns the argv unwrapped. The MCP documentation says a shell-mcp started independently of the Agent still refuses to bind; that is false for the binary and `mcp_launcher.py` paths. Verification narrowed the impact: the Agent reads the posture from `/health` (`collect_server_postures()` in `scripts/agent/services/mcp_health.py`), excludes any non-green server from `allowed_server_keys()`, and blocks its own startup on a Safety or Integrity failure (`_is_fatal_gate()`), so Agent-managed use is protected. The residual exposure is a bound, serving, unsafe process that any token holder (or any manual start) can call directly, plus the documentation contradiction. `mdq/__main__.py` also documents a non-existent module path (`mcp_servers.mdq.server`) and runs the server at import time.

## Reason for Change
The posture gate is the documented fail-closed control for server startup. It currently depends on how the process is launched, and the passing posture tests give false assurance because they call `_enforce_posture_gate()` directly rather than going through a launch path.

## Implementation Intent
Enforce the gate where every launcher converges (`run_http()`), after loopback and config-isolation validation and before uvicorn starts, by resolving the server module's existing `_enforce_posture_gate` from `app_module`. Keep the per-module functions (they hold the server-specific failure logging and existing tests) and keep importing a server module free of side effects such as process exit. Servers outside the `mcp_servers.` namespace (test fakes) are not gated, and a real server module without the function fails closed.

## Requirements
- `REQ-001`: `MCPServer.run_http()` runs the server module's `_enforce_posture_gate()` for any `app_module` in the `mcp_servers.` namespace, after the loopback and config-isolation checks and before the uvicorn server is created, so a FAILED posture exits with status 1 without binding.
- `REQ-002`: A server module in the `mcp_servers.` namespace that does not define `_enforce_posture_gate` makes `run_http()` fail closed (raise) rather than start.
- `REQ-003`: `mdq/__main__.py` starts the server only under `if __name__ == "__main__":` and its docstring names the real entry point (`python -m mcp_servers.mdq`).
- `REQ-004`: The comment in `gen_launcher()` of `deploy/build_binaries.sh` no longer claims the launcher reproduces `__main__` behavior; it states that the posture gate is enforced inside `run_http()`.
- `REQ-005`: The MCP startup documentation states that the posture gate is enforced in the common start path for every launch route.
- `REQ-006`: Tests prove that, for each discovered MCP server class, `Class().run_http()` with a FAILED posture raises `SystemExit(1)` before uvicorn starts, that a missing gate fails closed, and that importing `mdq/__main__.py` does not start a server.

## Design
Path B (more than three files and a runtime start-path change). Architecture analysis: `lint-imports` reports all 6 contracts kept. The gate lives in the base class so no per-launcher logic is duplicated; it resolves `_enforce_posture_gate` from the module named in `app_module` with `importlib`, only for the `mcp_servers.` namespace, which keeps test fakes (`test:app`) working and makes a real server without the function fail closed. The call sits after the loopback check and `ConfigLoader.restrict_to()` so isolation is already active when the module is imported by the gate, and before the uvicorn server object exists so a failed gate never binds a socket. Dependency graphing: callers of `run_http()` are the ten server `__main__` blocks, `mcp_launcher.py`, the generated launchers and `mdq/__main__.py`. Historical analysis: `server.py` 5 commits and `build_binaries.sh` 10 commits in 30 days. Operational dependency: production runs binaries, so the change takes effect only after rebuilding them (Implementation steps, Phase 4). `mdq_server.py` is size-baselined at 17987 bytes and is deliberately not edited.
