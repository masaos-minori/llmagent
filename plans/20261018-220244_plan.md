# Plan

## Goal
Fail fast on a non-string `mqe_prompt_template` or `rerank_prompt_template` by validating prompt-template types at RAG config-load time, instead of letting a bad value surface as an uncaught `TypeError` deep in the MQE/rerank pipeline.

## Priority
Medium

## Scope
- **In-Scope**: Add prompt-template type validation to `RagConfigValidator.validate`; add unit and integration tests covering the validator and `resolve_rag_config`.
- **Out-of-Scope**: Stage-handler defense-in-depth guards (`except TypeError`) in the MQE/rerank path; refactoring MQE/rerank prompt-building logic; changing default template values or the `{query}` format contract; validating other RAG config fields; any `docs/*.md` change.

## Background
The RAG pipeline builds its multi-query-expansion and cross-encoder prompts via `_mqe_prompt()` and `_build_rerank_prompt()` in `scripts/rag/llm_prompts.py`. Both raise `TypeError` when the corresponding `cfg` template attribute is not a `str`. They are invoked from `RagLLM.expand_queries()` (MQE) and `RagLLM.cross_encoder_rerank()` (rerank).

The resolved config flows through `resolve_rag_config()` in `scripts/rag/config_resolution.py`, which fills defaults and delegates to `RagConfigValidator.validate()` in `scripts/shared/config_validator.py`. That validator currently checks only `use_rrf` (warning) and removed semantic-cache keys (error); it never inspects the type or shape of the prompt-template strings.

## Problem
A non-string template reaches the pipeline stages as an uncaught `TypeError`:
- `_mqe_prompt` / `_build_rerank_prompt` raise `TypeError` for a non-str template.
- `expand_queries` catches only `(httpx.HTTPStatusError, httpx.RequestError, orjson.JSONDecodeError, MqeParseError)`; `MqeStage.run` catches only `RagExpansionError`; the shared `_run_stage` wrapper in `scripts/rag/stage_lifecycle.py` catches only `(RuntimeError, sqlite3.OperationalError, httpx.HTTPStatusError, httpx.RequestError, TimeoutError)`. `TypeError` is absent from every handler and propagates out of `RagPipelineStageLifecycle.run()`.
- The rerank side mirrors this: `cross_encoder_rerank` catches `(httpx.HTTPStatusError, httpx.RequestError, ValueError)`; `RerankStage.run` catches only `RagRerankError`.

Under the typed-config policy in `rules/coding.md` (Type-coercion policy), config loaders must validate field types and reject wrong types at load time. Prompt templates are the one class of RAG config that currently slips through validation entirely.

## Reason for change
The typed-config policy requires config loaders to validate field types and reject wrong types at load time. Prompt templates bypass validation, so a misconfigured value aborts the whole pipeline run with an unhandled `TypeError` instead of failing fast at startup with an actionable config error.

## Implementation intent
Add prompt-template type validation at the config-validation boundary so a non-string template fails fast with a clear, key-naming error. Fix at `RagConfigValidator.validate` rather than adding broad `except TypeError` handlers, because fail-fast at startup is the intended control and matches the typed-config policy. Both production entry points that build `RagConfigImpl` call the validator and raise on `ok=False`, so the fix closes the gap without touching the stage handlers.

## Requirements
- `REQ-001`: `RagConfigValidator.validate` rejects a non-string `mqe_prompt_template` or `rerank_prompt_template` by appending an error naming the offending key and setting `ok=False`.
- `REQ-002`: `resolve_rag_config` raises `ValueError` naming the key when a template is non-string, before any pipeline run, and resolves normally when templates are valid strings.

## Design
Path A (small task): affects ≤ 3 files, no public/runtime interface change, no database schema change. The `validate()` signature and `ConfigValidationResult` shape are unchanged; only the errors list grows.

`RagConfigImpl` is a plain dataclass with no `__init__` coercion, so type validation cannot live in the DTO. It must live in `RagConfigValidator.validate`, which is called by both production entry points (`resolve_rag_config` and `RagPipelineConfig.load`) before any `RagConfigImpl` is built; both raise `ValueError` on `ok=False`. Adding a `str` check for the two template keys therefore fails fast at startup on every entry point without touching the MQE/rerank runtime path. The `{query}`/`{n_queries}` format contract and default template values are preserved.
