# Plan: Refactor scripts/agent/config_builders.py — split large file, centralize defaults, reduce repetition

## Goal
Split `scripts/agent/config_builders.py` into focused modules with clear responsibility boundaries: extract inline default constant tables to a new `constants.py`, consolidate structurally identical extraction helpers, decompose long builder functions, and separate factory orchestration from validation in `build_agent_config`.

## Priority
Medium

## Scope
- **In-Scope**: Splitting `config_builders.py`, creating `constants.py`, updating `config_dataclasses.py` imports, updating tests
- **Out-of-Scope**: Adding new config sections or fields, changing the TOML configuration schema, modifying `shared/` modules, performance optimization of config loading

## Background
`scripts/agent/config_builders.py` was written incrementally over multiple iterations. Each iteration added fields and builders without restructuring, resulting in a file where responsibility boundaries are unclear and the cognitive load per function exceeds what is reasonable for a single reviewer. The adversarial verification confirmed that all six `_DEFAULT_*` tables have exact copies in `config_dataclasses.py` dataclass defaults, creating two sources of truth.

## Problem
Three concrete problems:
1. **Inline default tables duplicate dataclass defaults** (lines 71-127): All 6 `_DEFAULT_*` tables (`_DEFAULT_PLAN_BLOCKED_TOOLS`, `_DEFAULT_APPROVAL_RISK_RULES`, `_DEFAULT_PROTECTED_PATHS`, `_DEFAULT_SHELL_SAFE_PREFIXES`, `_DEFAULT_RESOURCE_KEYS`, `_DEFAULT_DRY_RUN_TOOLS`) have exact copies in `config_dataclasses.py` dataclass defaults, creating two sources of truth that can drift apart silently.
2. **Structural repetition in `_get_*_or_default` helpers** (lines 135-177): Six nearly-identical wrapper functions that differ only in type and return annotation. However, `_get_str_or_default` has special semantics for empty-string defaults (`None vs ""` distinction) that must be preserved.
3. **Builder functions vary in complexity**: `_build_llm_config` (55 lines), `_build_tool_config` (52 lines), `_build_memory_config` (48 lines), and `_build_approval_config` (48 lines) exceed typical function length guidelines; however, `_build_rag_config` (27 lines) and `_build_diagnostics_config` (18 lines) are within reasonable bounds.

## Reason for change
- Maintainability: a 507-line file with 6+ distinct responsibilities is difficult to review and extend safely.
- Correctness risk: duplicated defaults between inline tables and dataclasses can drift apart silently.
- Testability: the tight coupling between extraction, validation, and construction in each `_build_*` function means tests must cover every path through every builder rather than testing concerns independently.
- Medium priority: this affects developer experience and future feature velocity but does not impact runtime correctness today.

## Implementation intent
1. Extract all `_DEFAULT_*` constant tables to a new `constants.py` module. Have dataclasses import these as their defaults instead of defining inline literals. Remove duplicates from `config_builders.py`.
2. Consolidate the five `_get_*_or_default` helpers (excluding `_get_str_or_default` which has special semantics) into a single generic helper or inline pattern. Preserve the `None vs ""` distinction for `_get_str_or_default`.
3. Decompose the four long builder functions (>30 lines) into smaller sub-functions (<30 lines each). Exclude `_build_rag_config` (27 lines) and `_build_diagnostics_config` (18 lines) as they are already within reasonable length.
4. Split `build_agent_config` into three parts: (1) config loading + security profile computation, (2) production validation, (3) builder orchestration + AgentConfig assembly.

## Design
### Architecture decisions

1. **Constants extraction**: Move all `_DEFAULT_*` tables to `constants.py`. Dataclasses import these as `default_factory=lambda: _DEFAULT_X` instead of inline literals. This eliminates the two-sources-of-truth problem identified in the Issue.

2. **Helper consolidation**: Replace five of the six `_get_*_or_default` helpers with a single generic `_get_or_default(cfg, key, getter, default)` where `getter` is the typed validator (e.g., `_get_int`). Preserve `_get_str_or_default` as a separate function due to its `None vs ""` semantics. This is the conservative choice — a single generic helper replacing all six would conflate the two semantics.

3. **Builder decomposition**: Extract field-group logic into private helpers (e.g., `_extract_llm_transport_fields`, `_extract_llm_context_fields`). Each helper handles one cohesive group (LLM transport fields vs. LLM context fields). Exclude `_build_rag_config` (24 lines) and `_build_diagnostics_config` (15 lines) from decomposition.

4. **`build_agent_config` splitting**: Three sub-functions rather than two, based on actual responsibility distribution within the function:
   - `_resolve_config_source_and_registry(cfg_override)` — config loading + tool registry resolution (14 lines: cfg source branching + try/except registry fetch)
   - `_run_production_validation(cfg, security_profile_val, known_tools)` — production validation (9 lines: validator call + error/warning logging)
   - `_assemble_agent_config(cfg, system_prompt_tool, security_profile_val)` — builder orchestration + AgentConfig assembly (22 lines: top-level bool extraction + 9 builder calls + AgentConfig construction)

5. **Import boundary**: `constants.py` is a leaf module — no other module imports from it except `config_dataclasses.py`. `config_builders.py` imports from both `constants.py` and `config_dataclasses.py`.
