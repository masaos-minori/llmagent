# Plan: filter_env strips inherited loader/interpreter env vars via shared denylist

## Goal
Prevent `CommandValidator.filter_env()` from propagating dangerous loader/interpreter environment variables (`LD_PRELOAD`, `LD_LIBRARY_PATH`, `PYTHONPATH`) inherited from the parent agent process into HTTP subprocess MCP servers, by stripping them from the seeded environment using the same canonical denylist the config layer uses.

## Priority
Medium

## Scope
- **In-Scope**:
  - Modify `scripts/agent/http_lifecycle_command_validator.py` (`filter_env`) to drop denylisted keys from the inherited environment before applying config overrides.
  - Add unit tests for `CommandValidator.filter_env()`.
- **Out-of-Scope**:
  - Adding other env vars (`TZ`, `PYTHONHASHSEED`, `PYTHONHOME`, `PYTHONSTARTUP`) to the denylist — evaluate separately.
  - Changing how `cfg.env` overrides interact with allowed inherited vars beyond the denylisted set.
  - Changing `validate()`, the subprocess launch path, or protected-var override logging semantics.

## Background
HTTP subprocess MCP servers are launched by `HttpServerLifecycleManager._create_and_validate_proc()`, which builds the child environment via `env = self._command_validator.filter_env(cfg.env)` in `scripts/agent/http_lifecycle.py`. `filter_env()` lives in `scripts/agent/http_lifecycle_command_validator.py` and seeds its result with the full parent environment (`dict(os.environ)`), then applies protection only to keys present in the incoming `env` dict. Separately, `scripts/shared/mcp_config.py` defines `_ENV_KEY_DENYLIST = ("LD_PRELOAD", "LD_LIBRARY_PATH", "PYTHONPATH")` and enforces it only when *building* config (`_validate_env`), never on the runtime env-passing path.

## Problem
Because `filter_env()` seeds `result` with the entire parent environment and only filters config-supplied keys, inherited values such as `LD_PRELOAD`, `LD_LIBRARY_PATH`, and `PYTHONPATH` pass through unchanged when they originate from the agent process (startup, container, or prior injection). These subprocesses execute arbitrary configured commands (node/python/etc.), so an inherited `LD_PRELOAD` enables shared-library hijacking and `PYTHONPATH` enables module injection. The config-layer denylist gives a false sense of coverage because it never observes inherited variables.

## Reason for change
The defense-in-depth denylist at the config layer does not cover the runtime env-passing path. Since these subprocesses are arbitrary-code-execution sinks, uncontrolled inheritance of ELF/preload and Python-path variables materially widens the attack surface. The runtime path must apply the same denylist.

## Implementation intent
After seeding `result = dict(os.environ)` in `filter_env()`, remove any key matching the canonical loader/interpreter denylist before applying config overrides. Import the single canonical `_ENV_KEY_DENYLIST` from `shared.mcp_config` rather than redefining a local copy, so both layers agree. Preserve None-input handling, benign inherited var inheritance, and the existing protected-var override logging. Add dedicated unit tests for `CommandValidator.filter_env()`.

## Requirements
- `REQ-001`: In `CommandValidator.filter_env()`, after seeding `result` from `os.environ`, strip every key matching the loader/interpreter denylist (`LD_PRELOAD`, `LD_LIBRARY_PATH`, `PYTHONPATH`) before merging config overrides; preserve benign inherited vars and None-input handling.
- `REQ-002`: Add unit tests for `CommandValidator.filter_env()` covering inherited-denylist stripping (even when keys are absent from `cfg.env`), preserved benign vars, and config-provided non-protected var merge.
- `REQ-003`: Do not change `validate()`, the subprocess launch path, protected-var override logging, or handling of non-denied inherited/config vars.
- `REQ-004`: Centralize the denylist by importing the canonical `_ENV_KEY_DENYLIST` from `shared.mcp_config` into the validator; do not maintain a duplicate local definition.
