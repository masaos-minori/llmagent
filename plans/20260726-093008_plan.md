# Plan: Wire `validate_message()` into the conversation-history append path

## Goal

Every code path in `scripts/agent/` that adds a message to `ctx.conv.history` calls
`agent.message_schema.validate_message()` (directly or via one shared append helper)
before the message is stored, so a forged `_ephemeral`/`_memory_injected`/`_skill_ephemeral`
key from untrusted (e.g. LLM-influenced) content can no longer survive into history or
influence `_clear_previous_turn_ephemeral_messages()`'s trust decisions.

## Scope

**In scope:**
- Add a single validated append entry point on `ConversationState`
  (`scripts/agent/context.py`), since that is the shared object all call sites already
  hold as `ctx.conv` — no existing helper exists today (confirmed in Step 3).
- Route the following confirmed message-construction call sites through it:
  - `scripts/agent/orchestrator.py`: `_handle_memory_injection()` (append, ~L385-391),
    `_sync_system_prompt()` (insert, ~L563-565), `_append_user_message()` (append, ~L571)
  - `scripts/agent/tool_runner.py`: `_collect_tool_result_msgs()` (append, L193),
    `execute_all_tool_calls()` (extend, L469)
  - `scripts/agent/llm_turn_runner.py`: tool-call branch (append, L95),
    `_finalize_answer_text()` (append, L202)
  - `scripts/agent/mode_classification.py`: mode-hint append (L38)
  - `scripts/agent/commands/cmd_skill.py`: `_cmd_skill()` ephemeral append (L50)
  - `scripts/agent/startup.py`: initial-history assignment (L572)
  - `scripts/agent/services/session_restore.py`: history rebuild (L39-L44)
  - `scripts/agent/history.py`: compressed-summary message construction (L260, feeds
    the reassignment at `orchestrator.py` L402-403)
- Define and log validation-failure behavior (strip offending key(s) or drop the
  message; never raise/crash the turn).
- Add/extend unit tests for the new append path and for each audited call site.

**Out of scope:**
- Changing `message_schema.py`'s public API, `ROLE_KEY_WHITELIST`, or `TRUSTED_SOURCES`
  values (per requirement doc instruction #6 — this pass wires in the existing
  validator, it does not change its rules).
- Changing `_clear_previous_turn_ephemeral_messages()`'s filter logic beyond confirming
  it still only needs to trust keys set through the validated path (no new
  `validate_message()` call inside the filter — avoids the redundant-validation
  pattern the requirement doc explicitly warns against, consistent with commit
  `7c7bbe47d`).
- Any persistence/DB schema change to `ctx.session` (SQLite message storage).
- Extending `ROLE_KEY_WHITELIST` to cover `pinned`/`importance`/`name` (see Risks) —
  tracked as a follow-up, not fixed in this pass.

## Assumptions

1. `ConversationState` (in `scripts/agent/context.py`, class body ~L56-72) is the
   correct place for the new helper because every call site already accesses history
   via `ctx.conv.history`, and no `Conversation`/history-append class exists anywhere
   else in the repo (confirmed: no `class Conversation` hits repo-wide).
2. The `source` value passed to `validate_message()` (e.g. `"memory_injection"`,
   `"cmd_handler"`, `"skill_mixin"`) is transient, validation-only metadata — it must
   **not** be persisted into the stored message dict, because (a) `"source"` is not a
   member of any `ROLE_KEY_WHITELIST` entry, so leaving it in the stored dict would
   make the *next* validation pass over that same message fail with "Unexpected
   keys", and (b) `ctx.conv.history` is passed to `ctx.services_required.llm.stream()`
   with no key-stripping in between (confirmed in `shared/llm_client.py`), so an
   unstripped `"source"` key would be sent to the LLM API verbatim.
3. Messages built by `llm_turn_runner.py` from streamed LLM responses only ever carry
   `role`/`content`/`tool_calls` for assistant messages — the streaming accumulation
   logic in `shared/llm_client.py` / `LlmReconnectHandler` constructs these dicts
   in-repo rather than passing through arbitrary provider JSON, so they already match
   `ROLE_KEY_WHITELIST["assistant"]` and will not be spuriously stripped.
4. No current call site sets `pinned`, `importance`, or `name` on a `ctx.conv.history`
   message (confirmed via repo-wide grep of assignment sites — those fields are only
   ever set on unrelated memory-subsystem records in `agent/memory/*.py`), so enabling
   strict `ROLE_KEY_WHITELIST` enforcement will not break any existing call site today.
5. `review_mode` for this planning cycle is `autonomous` (per task instructions), so
   Step 7 proceeds without an approval gate.

## Design

1. **Single validated append helper, owned by `ConversationState`.**
   Add to `scripts/agent/context.py`:

   ```python
   from agent.message_schema import validate_message

   ...
   class ConversationState:
       ...
       def append_message(self, msg: LLMMessage, *, source: str = "") -> None:
           """Validate msg via message_schema.validate_message() before appending.

           `source` is validation-only metadata (see TRUSTED_SOURCES) and is never
           persisted on the stored message. On validation failure, the offending
           reserved/ephemeral key(s) are stripped and the sanitized message is
           appended instead of the raw one; the turn never crashes.
           """
           check = dict(msg)
           if source:
               check["source"] = source
           result = validate_message(check)
           if not result.success:
               logger.warning(
                   "append_message: rejected/sanitized message (role=%s): %s",
                   msg.get("role"), result.reason,
               )
               msg = _sanitize_message(msg)
           self.history.append(msg)

       def extend_messages(self, msgs: list[LLMMessage], *, source: str = "") -> None:
           for m in msgs:
               self.append_message(m, source=source)

       def replace_history(self, msgs: list[LLMMessage], *, source: str = "") -> None:
           self.history = []
           self.extend_messages(msgs, source=source)
   ```

   `_sanitize_message()` is a small private helper (in `context.py` or
   `message_schema.py`) that drops any key not in
   `ROLE_KEY_WHITELIST.get(role, {"role", "content"})` plus any ephemeral key not
   authorized for the given `source`, guaranteeing the stored message is always
   schema-conformant. If `role`/`content` themselves are missing, the message is
   dropped entirely (logged at `error`) rather than partially stored.

2. **Why a method on `ConversationState` rather than a free function in
   `orchestrator.py`:** the requirement doc's own audit list spans five modules
   (`orchestrator.py`, `tool_runner.py`, `llm_turn_runner.py`, `mode_classification.py`,
   `commands/cmd_skill.py`) plus three more found in this plan's audit
   (`startup.py`, `services/session_restore.py`, `history.py`'s caller). All of them
   already hold `ctx` and therefore `ctx.conv`; putting the helper on `ConversationState`
   means every call site's fix is a one-line substitution (`ctx.conv.history.append(x)`
   → `ctx.conv.append_message(x, source=...)`) with no new imports beyond what
   `context.py` itself needs, and it structurally prevents new call sites from
   bypassing validation by construction/convention (matches the requirement doc's
   "prefer a single centralized append helper" instruction).

3. **`source` is never stored.** Only used transiently for the `validate_message()`
   check; the stored message dict is the caller-supplied `msg`, unmodified except for
   sanitization on failure. This avoids polluting `ctx.conv.history` entries (and thus
   the LLM API payload and DB persistence) with a non-schema field.

4. **`_clear_previous_turn_ephemeral_messages()` stays a pure filter.** Per requirement
   doc instruction #5 and existing code comment (L543-546: "must run before this
   turn's own injections... so it never strips content just added for the current
   turn"), it continues to trust `_ephemeral`/`_memory_injected` at face value — but
   now that trust is well-founded because every message reaching history was validated
   at append time. No `validate_message()` call is added inside the filter (avoids
   redundant validation, consistent with commit `7c7bbe47d`'s consolidation intent).

5. **Bulk-reassignment sites** (`startup.py:572`, `services/session_restore.py:39-44`)
   use the new `replace_history()` wrapper for defense in depth (e.g. against a
   tampered/corrupted DB row surfacing an ephemeral key on session restore), even
   though the requirement doc's primary threat model is LLM-influenced content within
   a live turn, not persisted data.

   Leave the two ephemeral-filter list comprehensions (`cmd_skill.py:47-49`,

   **`tool_runner.py:469`** (`extend_messages()`, no `source`).
5. **Route `llm_turn_runner.py:95` and `:202`** through `append_message()`, no `source`.
6. **Route `startup.py:572`** and **`services/session_restore.py:39-44`** through
   `replace_history()`.
7. **Add unit tests** (new `tests/test_context_append_message.py` or extend
   `tests/test_message_schema.py`):
   - well-formed system message with `source="memory_injection"` appends with
     `_memory_injected: True` intact and no `source` key persisted;
   - forged `_ephemeral`/`_memory_injected` key with no/untrusted `source` is
     stripped before reaching `.history`;

## Risks

- **Risk:** `ROLE_KEY_WHITELIST` does not cover `name`/`importance`/`pinned`, which are
  declared on the `LLMMessage` TypedDict (`shared/types.py` L17-29) and read by
  `history_selection_policy.classify_importance()`. If a future change starts setting
  `pinned`/`importance` directly on a `ctx.conv.history` message, the new validation
  would silently strip those keys, silently degrading compression-priority behavior.
  **Likelihood:** low today (no current call site sets these fields on history
  messages, confirmed by grep) but real for future work.
  **Mitigation:** `append_message()` always logs a `warning` (not silent) when it
  sanitizes a message, so any future regression surfaces in logs immediately;
  documented in the method's docstring and in this plan. Tracked as a follow-up
  question (extend `ROLE_KEY_WHITELIST` vs. reconcile `LLMMessage`) rather than
  resolved in this pass, per requirement doc instruction #6 (schema changes are
  out of scope unless implementation reveals a genuine need). See
  `issues/20260726-093008_risks.md`.
- **Risk:** Routing `llm_turn_runner.py`'s streamed assistant messages through strict
  validation could reject/strip a legitimate provider-specific field if the LLM
  client's accumulation logic ever changes to pass through raw provider JSON.
  **Likelihood:** low (Assumption 3 — messages are constructed in-repo from typed
  deltas, not passed through raw).
  **Mitigation:** the regression test in Implementation step 7 pins current behavior;
  `append_message()`'s warning log will surface any future drift immediately rather
  than silently corrupting tool-call turns.
- **Risk:** Missing a history-construction call site during the audit (scope creep /
  incomplete coverage is the core failure mode this task exists to close).
  **Likelihood:** low — this plan's audit re-ran the repo-wide search
  (`rg "\.history\.(append|extend|insert)|\.history\s*=\s*\["`) across all of
  `scripts/agent/` and found 4 sites beyond those named in the requirement doc; all
  are now included in Affected areas/Implementation steps.
  **Mitigation:** re-run the same `rg` search as part of code review before closing
  the eventual implementation PR, to catch any site added between planning and
  implementation.
- **Risk:** Behavior change to `_clear_previous_turn_ephemeral_messages()` was
  explicitly ruled out of scope, but a reviewer could still be tempted to add a
  redundant `validate_message()` call there "for extra safety," reintroducing the
  double-validation pattern the requirement doc (and commit `7c7bbe47d`) explicitly
  avoided. **Likelihood:** low. **Mitigation:** documented explicitly in Design point 4
  and Implementation step 3; acceptance criteria in the eventual implementation
  procedure should call this out as a non-goal.
